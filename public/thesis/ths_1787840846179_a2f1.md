# Verified eBPF Programs with Separation Logic: Symbolic Execution, Memory Safety Proofs, and Compositional Verification in Coq

## Abstract
The Linux eBPF verifier is a critical security boundary, yet its 10,000+ LOC C implementation has historically contained soundness bugs in range analysis and memory safety checking. This thesis presents a framework for verified eBPF programs using separation logic, symbolic execution, and compositional verification mechanized in Coq. We unify insights from PREVAIL's abstract-interpretation verifier, bit-precise CHC encoding via bpfverify, latent unsoundness studies in the kernel verifier, Certi rBPF's end-to-end Coq interpreter, Iris 3.1's higher-order concurrent separation logic, and the Verified Software Toolchain's C semantics. We formalize eBPF machine state as separation-logic resources, prove memory isolation via points-to and map invariants, and compose helper-call specifications using Iris invariants and VST-style weakest preconditions. Symbolic execution over bitvectors and maps yields decidable verification conditions discharged by SMT. The result is a modular, foundational approach to eBPF safety beyond the in-kernel verifier.

# Verified eBPF Programs with Separation Logic: Symbolic Execution, Memory Safety Proofs, and Compositional Verification in Coq

## Abstract
The Linux eBPF verifier is a critical security boundary, yet its 10,000+ LOC C implementation has historically contained soundness bugs in range analysis and memory safety checking. This thesis presents a framework for *verified eBPF programs* using separation logic, symbolic execution, and compositional verification mechanized in Coq. We unify insights from PREVAIL's abstract-interpretation verifier, bit-precise CHC encoding via bpfverify, latent unsoundness studies in the kernel verifier, Certi rBPF's end-to-end Coq interpreter, Iris 3.1's higher-order concurrent separation logic, and the Verified Software Toolchain's C semantics. We formalize eBPF machine state as separation-logic resources, prove memory isolation via points-to and map invariants, and compose helper-call specifications using Iris invariants and VST-style weakest preconditions. Symbolic execution over bitvectors and maps yields decidable verification conditions discharged by SMT. The result is a modular, foundational approach to eBPF safety beyond the in-kernel verifier.

## 1. Introduction

Extended BPF (eBPF) lets unprivileged-tinged user code run at kernel privilege after static verification. The in-kernel verifier enforces *termination, memory safety, and control-flow integrity* before JIT compilation to native code [1][3]. Verification failures are frequent and diagnostic-poor: 47% of rejections surface only as `EINVAL` [7], motivating tooling like bpfix and PREVAIL [1][2].

**Why separation logic?** Traditional verifiers rely on abstract interpretation over intervals, tnums, and zone domains. While efficient, they suffer latent unsoundness when abstract operators are unsound in isolation but corrected by a shared reduction operator [8]. A *foundational* alternative models eBPF state as ownable resources.

This work argues:

- **eBPF state is separation-logic friendly:** 11 registers, 512-byte stack, packet and map value pointers form disjoint heaps.
- **Compositional specs enable helper verification:** `bpf_map_lookup_elem`, `bpf_probe_read` have subtle ownership transfer.
- **Coq + Iris + VST gives a path to end-to-end proofs:** CompCert Clight semantics, Iris ghost state, VST Floyd tactics [5][6][4].

> Theorem 1.1 (Memory Safety Goal): If ⊢ {P} prog {Q} in eBPF separation logic, then any execution from a state satisfying P never accesses out-of-bounds memory, never leaks uninitialized registers, and respects map invariants.

## 2. Background

### 2.1 eBPF Machine Model

| Component | Description | Safety Condition |
|-----------|-------------|------------------|
| R0–R9 | 64-bit general purpose, R10 read-only frame pointer | No uninitialized read, no pointer leak |
| Stack | 512 bytes, grows down from R10 | R10+off ∈ [-512,0), aligned |
| Packet | `ctx->data .. data_end` | Checked via range analysis, tnum precise |
| Maps | Key/value via helpers | Value pointer valid only after non-null check |
| Code | ≤ 1M insns, no unbounded loops | DAG or bounded loop with verifier proof |

*eBPF execution model: loader → verifier → JIT → hook attachment* [3][1].

### 2.2 Kernel Verifier and Its Bugs

The kernel verifier simulates all paths, tracking register types, bounds, and liveness in `bpf_check()` (~10k LOC). Recent work automatically generates verification conditions from C source and synthesizes counter-example eBPF programs when abstract semantics diverge from concrete bitvector semantics [2][3][8].

- Range analysis unsoundness fixed in kernels 4.14–5.19: interval + tnum combination non-modular [2].
- Latent unsound operators: individual abstract domain operators unsound in isolation, masked by shared refinement [8]. Patches upstreamed make operators sound modularly, enabling faster automated verification.

### 2.3 PREVAIL and bpfverify

**PREVAIL** [1] is a polynomial-runtime verifier using abstract interpretation over Crab domains (`zoneCrab`, intervals, octagons). It exposes CFG, invariants, and proves equivalence to Linux verifier on Cilium and kernel samples while providing formal soundness arguments for its abstract domain.

**bpfverify** [0] translates eBPF to Constrained Horn Clauses (CHC) over bitvectors + arrays, discharging functional properties with Z3. It is *bit- and memory-precise*, covering almost all eBPF ISA, proving termination of translation and demonstrating full automatic verification on real code.

### 2.4 Certi rBPF: Verified Interpreter in Coq

Nelson et al. [4] present the first end-to-end mechanized proof of an rBPF VM for RIOT on micro-controllers. Syntax, semantics, and defensive interpreter are in Gallina; CompCert C extraction yields verified C. TCB excludes offline verifier—critical for IoT where authenticated upload is impractical.

### 2.5 Iris and VST

**Iris** [5][6] is a higher-order concurrent separation logic framework in Coq. Core ideas: resource algebras (cameras), invariants `⎡P⎤`, weakest preconditions `WP e {{ Φ }}`, later modality `▷`, ghost state. Iris 3.1 narrative (Jung et al., JFP 2018) provides complete foundation [5].

**VST** [4][6] connects separation logic to CompCert Clight, proving C programs safe w.r.t. CompCert operational semantics. VST-Floyd offers semi-automatic tactics for Verifiable C. Recent integration brings Iris ghost state and proof mode into VST [6].

> Theorem 2.1 (Iris Adequacy): If `⊢ WP e {{ v, Φ v }}` in Iris and Φ implies safe postcondition, then execution of e is safe (no UB) and satisfies Φ.

## 3. Methodology

We propose a three-layer verification stack:

1. **Concrete:** Gallina model of eBPF semantics (rBPF subset + maps)
2. **Separation:** Resource model of registers, stack, maps as `ℓ ↦ v` and `map ↦ (k↦v)`
3. **Compositional:** Iris invariants + symbolic execution engine emitting CHC/SMT

### 3.1 Formal Model

Define state `σ = (regs, stack, mem, maps, pc)`.

- `regs : Reg → Val` where `Val = Int64 | Ptr(typ, base, off, len)`
- `stack : [0..512) → byte` owned via `stack_token`
- `maps : MapId → MapSpec` with protocol state machine

*eBPF resource algebra:* `eBPF_RA = RegRA × StackRA × MemRA × MapRA × GhostRA` where each component is a partial commutative monoid with maximal idempotent for persistent facts (e.g., code immutability).

**Separation assertion examples:**

- `r1 ↦_ptr packet(base, off, len)`
- `stack_slice off len ↦_s bytes`
- `map_fd ↦_map (K → V)`

### 3.2 Symbolic Execution over Bitvectors

We lift concrete execution to symbolic states `Σ_sym = (path_cond, sym_regs, sym_mem)` where `path_cond : Formula_BV+Array`.

Path-sensitive memory safety reduces to implication check:

```python
def check_access(sym_ptr, sym_len, path_cond):
    # sym_ptr = base + off, base has invariant len
    query = And(path_cond, Or(sym_ptr.off < 0, sym_ptr.off + sym_len > sym_ptr.len))
    return unsat(query)  # safe iff no counterexample
```

This mirrors bpfverify CHC encoding [0] but embedded in separation logic: memory access requires `l ↦ _ * l+len ↦ _` and proof of bounds via tnum refinement.

### 3.3 Helper Specifications

Helper calls are the *most subtle* — they transfer ownership and may return nullable pointers.

*Example: map lookup:*

```haskell
-- Separation-logic spec in Iris style
spec_map_lookup :: MapId -> Key -> WP
spec_map_lookup m k =
  { map_token m * k |-> _ }
  bpf_map_lookup_elem(m,k)
  { ret. (ret = 0 * emp) \/ (exists v. ret |-> v * v |-> Value * map_token m) }
```

We encode as Iris `WP` with fancy updates and persistent invariants for map well-formedness, following VST-on-Iris approach [6].

## 4. Deep Dive

### 4.1 eBPF Verifier Pipeline as Separation Logic Checking

![eBPF verifier pipeline](sandbox://workspace/goals/post-more-hourly-thesis/public/thesis/ths_17878404750000_a2f1-0.webp)

Traditional pipeline: `C → Clang/LLVM → bytecode → verifier → JIT → native` [1][3]. Our pipeline inserts a *foundational verifier*:

1. **Lift:** `llvm-objdump` → CFG → Gallina `ebpf_prog`
2. **Annotate:** User provides map specs, pre/post via `#[ebpf_spec]` attributes
3. **Symbolize:** Symbolic execution engine explores paths up to bound (bounded loops verified via variant)
4. **Prove:** Separation obligations discharged via `lia`, `bitvector`, Iris Proof Mode

*Advantage over kernel verifier:* Compositional; helper specs reused across programs, not re-analyzed per load.

### 4.2 Separation Logic Heap Reasoning for eBPF Memory

![heap reasoning](sandbox://workspace/goals/post-more-hourly-thesis/public/thesis/ths_17878404750000_a2f1-1.webp)

Memory safety in eBPF is not trivial heap reasoning — stack aliasing, packet re-writes, and `R10` frame pointer require precise ownership.

We define:

- **Stack as linear resource:** `stack_all : [0..512) ↦ bytes` splittable via `∗` into slices. Spill/fill of registers uses `stack_off ↦_s reg_val`.
- **Packet as borrowed resource:** `packet_token len * (data ↦_p _ * data_end ↦_p data+len)` with lifetime tied to program type (e.g., `BPF_PROG_TYPE_XDP`). Write requires `data + off + size ≤ data_end` — exactly the check kernel range analysis attempts [2][8].
- **Maps as protocol resource:** Ghost state tracks key existence, value ownership transfer on `lookup` returning pointer invalidated by next `update`.

> Theorem 4.1 (Stack Safety): If program holds `stack_slice o l ↦_s _` and accesses `R10+o'` with `o' ∈ [o, o+l)`, then access preserves `∗` frame and does not clobber unrelated slices.

Proof sketch uses `frame rule`: `{P} c {Q} ⇒ {P∗R} c {Q∗R}` where `R` is disjoint stack slice.

**Rust shim for VST integration:**

```rust
// Verified C wrapper extracted from Coq via CompCert
// Spec corresponds to separation logic triple
/*@ requires map_token(m) * key |-> k
    ensures  ret==0 \/ (ret |-> v * v |-> val * map_token(m)) @*/
void *bpf_map_lookup_elem_verified(void *m, void *k);
```

### 4.3 Symbolic Execution Tree and Path Conditions

![symbolic tree](sandbox://workspace/goals/post-more-hourly-thesis/public/thesis/ths_17878404750000_a2f1-2.webp)

Symbolic execution enumerates path conditions, each leaf a verification condition (VC). Branching occurs on `BPF_JEQ/JGT`, `map lookup null check`, and `data_end` comparison.

*Branch pruning:* Use tnum abstract domain from kernel [2] as over-approximation to prune infeasible branches early. Our symbolic domain refines tnum: `tnum(known_bits, mask)` → symbolic formula `∃ x. x & mask = known_bits`.

**TLA+ spec for termination of symbolic exploration:**

```tla
---------------- MODULE EBPF_Symbolic ----------------
VARIABLES pc, pathCond, fuel
Init == pc = 0 /\ pathCond = TRUE /\ fuel = MAX_FUEL
Step == \/ pc' \in Successors(pc) /\ pathCond' = pathCond \land Guard(pc)
        \/ pc' = Error /\ UNCHANGED <<pathCond>>
Next == fuel > 0 /\ fuel' = fuel -1 /\ Step
Spec == Init /\ [][Next]_<<pc, pathCond, fuel>> /\ WF_fuel(Next)
================================================================
```

*Fuel ensures decidability; bounded loops proved decreasing via lexicographic variant on loop counter + map size.*

**Path explosion mitigation (proposed):**

- Merge states at join points via `∗` disjunction and weak updates (PREVAIL zone domain inspiration [1])
- Map abstraction: collapse multiple keys into summary predicate `∀ k ∈ S. map k ↦ v_k`
- Packet length symbolic, not concrete: `len = data_end - data`

### 4.4 Coq Proof Composition and Iris Invariants

![Coq composition](sandbox://workspace/goals/post-more-hourly-thesis/public/thesis/ths_17878404750000_a2f1-3.webp)

Final composition uses Iris *invariants* for global map well-formedness, *ghost state* for tracking allocation, and *logicals* for contextual refinement [5][6].

1. **Local specs:** Each basic block proved via `WP` in Iris Proof Mode:
   ```coq
   Lemma block_check_bounds : ⊢ {{{ packet_len ↦ l ∗ data ↦ d ∗ d+l ↦ end }}}
     r1 <- data; r2 <- data_end; if r1+10 > r2 then exit else ...
     {{{ RET tt; packet_len ↦ l ∗ ... }}}.
   ```
2. **Frame across calls:** Helper calls frame out irrelevant stack slices using `iFrame`.
3. **Invariant opening:** Map access opens `inv_map m` invariant, performs ghost update, closes invariant.
4. **Adequacy to CompCert:** Via VST embedding [6], Gallina semantics → Clight → CompCert assembly semantics, yielding end-to-end theorem: *verified eBPF C shim + JIT preserve semantics* similar to verified JIT methodology [7].

> Theorem 4.2 (Composition): If each helper satisfies spec `S_h` and each block satisfies `{P_i} b_i {Q_i}` with `Q_i ⇒ P_{i+1}`, then whole program satisfies `{P_0} prog {Q_n}` and is safe.

## 5. Theoretical Proofs / Proposed Evaluation

*No invented measurements are reported. This section presents provable lemmas and a proposed evaluation grounded in literature [0-8].*

### 5.1 Lemmas

**Lemma 5.1 (Points-to disjointness ⇒ isolation):** `ℓ1 ↦ v1 ∗ ℓ2 ↦ v2 ⇒ ℓ1 ≠ ℓ2` in eBPF stack model, hence spill of `r1` cannot clobber `r2` spill slot if offsets differ.

*Proof:* By definition of separating conjunction over finite map domain [5].

**Lemma 5.2 (Map pointer validity):** If `map_lookup` returns non-null `p` and invariant `map ↦ vals` holds, then `p ↦ val` with `val ∈ vals` until next map operation invalidating ghost generation.

*Proof sketch:* Ghost generation counter incremented on `update/delete`, tying pointer validity to generation via Iris `auth` RA [5].

**Lemma 5.3 (Packet bounds preservation):** Symbolic condition `data + off + size ≤ data_end` is equivalent to concrete safety for all concretizations of symbolic `data`, `data_end` respecting `path_cond`.

### 5.2 Proposed Evaluation (Literature-Grounded)

*To be conducted, not claimed:* Evaluate on PREVAIL benchmark suite [1][2] (Cilium `bpf_lxc`, `bpf_netdev`, kernel samples `cpustat_kern`, 200+ programs from [7]):

- **Metric 1 (Soundness):** Count programs where our verifier proves safety and kernel verifier accepts, vs where kernel rejects but our proof shows safe (diagnostic gap). Compare to Verifying-the-Verifier synthesis [2].
- **Metric 2 (Precision):** Measure false positives vs bpfverify CHC [0] (bit-precise). Expect fewer false rejects on tnum-heavy patterns.
- **Metric 3 (Modularity):** Lines of spec vs lines of proof for helper-rich programs; reuse of map specs across 10+ programs.
- **Metric 4 (Extraction):** Size and performance of extracted C via CompCert vs CertrBPF [4] (reported 2-3× smaller than hand-written defensive VM).

*Methods:* Run `check` from PREVAIL [1] for baseline, `bpfverify` for CHC SAT time, and our Coq `Qed` time. No runtime numbers invented; literature indicates PREVAIL <0.1s per program on zoneCrab [1], bpfverify Z3 seconds-scale [0].

## 6. Limitations

- **ISA coverage:** Current model excludes `BPF_ALU64 | BPF_X` with 32-bit subreg tricks, `bpf_loop`, and BTF-assisted `kfunc` calls. PREVAIL and CertrBPF also omit some atomics [1][4].
- **Unbounded loops:** We require bounded loops or explicit variant; kernel now allows bounded loops with verifier tracking [2]. Supporting general unbounded loops would need step-indexed invariants beyond simple fuel.
- **Map concurrency:** Real maps are concurrent with RCU; our invariant assumes sequential consistency within single eBPF program. Iris concurrent reasoning [5][6] can model RCU but proof burden high.
- **Helper TCB:** Helper implementations in kernel C remain unverified; we axiomatize specs, similar to VST's axiomatization of atomic operations before foundational integration [6]. Full connection to kernel C via VST-Clight requires verified map implementation.
- **Coq proof effort:** Manually proving 200+ sample programs would be prohibitive; automation via `diaframe`, `RefinedC`, or VST-Floyd tactics needed [4][6].
- **JIT trust:** Even with verified source-to-CompCert correctness [7], final JIT to native (kernel's JIT, not CompCert) remains in TCB unless using verified JIT approach of Barrière et al. [7].

---

## 7. Conclusion

We presented a *separation-logic-centric* approach to verified eBPF programs: model state as resources, use symbolic execution over bitvectors for path conditions, and compose proofs in Coq via Iris invariants and VST-style weakest preconditions. By learning from PREVAIL's abstract interpretation [1], bpfverify's CHC precision [0], latent unsoundness studies [8][2], and CertrBPF's end-to-end Coq extraction [4], we outline a path to a foundational eBPF verifier where memory safety is a theorem, not a best-effort check.

**Key contributions hypothesized:**

1. Resource algebra for eBPF registers/stack/packets/maps in Iris
2. Helper specs with ownership transfer and ghost generations
3. Symbolic execution engine emitting decidable VCs, bridging to SMT
4. Proposed evaluation on Cilium/kernel corpus linking to existing verifiers

Future work includes integrating Turbo-SMT bitvector reasoning, scaling automation with *Iris Proof Mode*, and verifying JIT lowering via CompCert backend reuse as in verified JIT [7]. The ultimate goal: eBPF programs whose safety proof is checked by Coq, not trusted C in the kernel.
