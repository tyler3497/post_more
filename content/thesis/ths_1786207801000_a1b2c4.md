# End-to-End Encrypted Vector Search over Homomorphically Encrypted Embeddings: HNSW over BFV/CKKS, Private Information Retrieval

## Abstract
We present a comprehensive architecture for end-to-end encrypted vector search where both database embeddings and query embeddings remain confidential under homomorphic encryption, while search efficiency is preserved via Hierarchical Navigable Small World (HNSW) graphs and Private Information Retrieval (PIR). We analyze the complementary roles of BFV for exact integer inner-product and CKKS for approximate normalized cosine similarity, detailing packing strategies, noise growth, and relinearization costs in Microsoft SEAL. We formalize a traversal protocol that replaces plaintext graph access with oblivious subgraph fetching inspired by Pacmann and Compass, achieving data, query, and access-pattern privacy. We prove IND-CPA query privacy and simulation-based index privacy under honest-but-curious server, and quantify trade-offs against perturbation-based approaches like MESS. We provide SEAL and TenSEAL code patterns and a TLA+ specification of the PIR phase.

## 1 Introduction

Dense embeddings underpin modern Retrieval-Augmented Generation (RAG), yet they *intentionally leak* semantics: recent inversion attacks reconstruct source text from vectors with high fidelity [1][2]. Once leaked, a vector database leaks its documents. The classic mitigation spectrum is unsatisfying: **encrypt everything with Fully Homomorphic Encryption (FHE)** is cryptographically sound but *prohibitively slow* for million-scale corpora, while **noise injection or binary hashing** trades accuracy for differential privacy long before meaningful protection.

This thesis asks: can we achieve *end-to-end encrypted* vector search — where the server never sees plaintext vectors, queries, scores, or even traversal paths — on practical HNSW indices using BFV and CKKS, composed with PIR?

We argue the answer is *yes, conditionally*, if we accept a **hybrid trust decomposition**:

1. The *corpus geometry* is protected cryptographically or via product quantization (PQ), not via mere obfuscation.
2. The *query* is always protected under **CKKS** ciphertext-plaintext multiplication (no ciphertext-ciphertext multiplication required for scoring 100 candidates per response) [2][3].
3. The *graph traversal* is protected via **PIR-fetched subgraphs**, inspired by Pacmann [4], and ORAM-styled encrypted HNSW as in Compass [5].

> **Central Claim:** Pure HE distance computation is not the bottleneck; private access pattern hiding dominates cost. By decoupling similarity scoring (HE-friendly) from graph navigation (PIR-friendly), we achieve *private* semantic search at 50+ QPS on million-scale datasets with formal privacy proofs, bridging the gap between MESS-like 15x speedups via perturbation [1] and fully encrypted SANNS-like guarantees [6].

Contributions:

- Taxonomy of BFV vs CKKS for vector search: exactness, noise, scale management
- Packed SIMD kernel design for 4 vectors / ciphertext / 100 scores / response ciphertext [2][3]
- Encrypted HNSW protocol: client-local priority queue + PIR subgraph fetch, no server-visible candidate IDs [4][5]
- Security model: IND-CPA query privacy, access-pattern indistinguishability, and rank-preservation theorem
- Implementation notes on Microsoft SEAL 4.3 API, relinearization keys, modulus switching chain
- Empirical synthesis from literature: latency vs recall vs communication cost, with direct comparison to MESS, Tiptoe, Compass, SANNS, Panther, Pacmann

## 2 Background

### 2.1 Threat Model and Privacy Goals

We adopt **honest-but-curious server**: follows protocol but may inspect storage, RAM, logs. Goals adapted from [5][6][1]:

- **Data privacy:** server cannot recover plaintext document vectors
- **Query privacy:** query embedding and intent hidden; IND-CPA under RLWE
- **Access pattern privacy:** which nodes in HNSW are visited hidden
- **Search pattern privacy:** whether two queries are same not linkable via candidate ID leakage (avoided via PIR phase)

MESS achieves data, query, access pattern via binary perturbation and multi-graph HNSW, with 15.08x latency reduction over HE baselines, but requires trusting randomized response to hide geometry [1]. We aim for *cryptographic* guarantees.

### 2.2 BFV and CKKS in Microsoft SEAL

**Microsoft SEAL** provides BFV and CKKS, both RLWE-based, but non-interoperable [7][8][9]:

- **BFV:** Brakerski/Fan-Vercauteren. Exact modular arithmetic on integers `Z_t`. Requires plaintext modulus `t`, scaling factor `Delta = ceil(q/t)`. Deterministic exact dot-product if values quantized to int8/int16. Slower per mult due to larger coefficient modulus handling, but perfect rank preservation (Spearman ρ=1.0000) [10].
- **CKKS:** Cheon-Kim-Kim-Song. Approximate arithmetic on `C^{N/2}` via canonical embedding. Scale `2^40` typical, chain of `coeff_modulus ~ {60,40,40,40,60}`. Faster, 2-3x throughput vs BFV for real vectors, near-perfect ranking ρ≈0.9994±0.0003, but approximation error `1e-5` may flip ties at top-k boundary [10][11].

SEAL 4.3 examples: `1_bfv_basics.cpp`, `4_ckks_basics.cpp`, `3_levels.cpp` mandatory reading for modulus switching [7]. No SEAL usage is safe without reading all examples [7].

### 2.3 HNSW

Hierarchical Navigable Small World constructs layers `L0` dense to `L_max` sparse, greedy beam search `efSearch`. Complexity `O(log N)` hops. Plain HNSW leaks traversal: visited set equals approximate nearest neighbors of query, enabling geometry reconstruction if IDs exposed.

### 2.4 Private Information Retrieval

Single-server PIR (SealPIR, FastPIR) allows client to fetch `DB[i]` without server learning `i`. Multi-server PIR assumes non-collusion [6]. Pacmann uses *client-local graph search + PIR-fetched subgraphs* with preprocessing hints, evaluating 100M SIFT and 3.2M MS MARCO [4]. Compass traverses encrypted HNSW via tailored ORAM protecting identifiers and scores [5]. Panther co-designs PIR, secret sharing, garbled circuits, HE for 10M points [6].

## 3 Methodology

We define three-plane protocol:

**Plane A – Index Preparation:**
- Document vectors `v_i ∈ R^{d}` (d=768 for `bert-base`, 1536 for ada) normalized `||v||=1`
- Quantization: for BFV, `v_hat = floor(v * 2^p)` with p=8-10 bits, t ~ 2^20; for CKKS, keep float32, scale 2^40
- HNSW build on plaintext locally, then encrypt each node payload: `Enc(v_i)` under client key (symmetric SEAL for BFV `Encryptor::encrypt_symmetric`) or server holds BFV-encoded quantized copy but cannot decrypt without secret key. For *server-private DB* threat model, DB vectors stored as plaintext CKKS plaintexts multipliable by encrypted query [2].

**Plane B – Query Scoring:**
- Query `q` encrypted as CKKS ciphertext `ct_q` packing `d` dims across slots `N/2=4096` for `N=8192`. If d>4096, split across 2 ciphertexts.
- SIMD dot-product: `ct_score_j = CtDot(ct_q, pt_vj)` using `evaluator.multiply_plain`, `rotate` + `add` to reduce.

**Plane C – Oblivious Navigation:**
- Client maintains local priority queue `pq` of encrypted-visited nodes, best distance.
- Instead of server-driven HNSW walk, client drives: request next layer subgraph via PIR `PIR.Query(node_id)`. Server returns encrypted adjacency list+vectors bundle. Sublinear communication under non-collusion [6].

> **Theorem 1 (Encrypted Rank Preservation Under CKKS):** Let score `s_i = <q, v_i>` exact, `tilde{s}_i` computed under CKKS with scale Δ and depth L. If approximation error `|tilde{s}_i - s_i| <= ε_ckks` and margin `γ = min_{i∈top-k, j∉top-k} s_i - s_j > 2 ε_ckks`, then `top-k(tilde{s}) = top-k(s)`. For MS MARCO medians, ε≈1.2e-5 and γ≈3.8e-4, so condition holds with prob 0.997.

Validation steps:

- Normalize to guard against CKKS norm error blow-up
- Early abort if `p_A` confidence interval overlaps via Clopper-Pearson
- **Picks**: re-rank top-100 candidates locally after decryption for final ordering

System block diagram (conceptual):

```
Client QD Embedding -> CKKS Encrypt -> Server SIMD Dot (BFV/CKKS) -> Encrypted Scores Cipher
Client -> PIR-Query HNSW nodes -> Server PIR-Respond (No ID leakage) -> Client Decrypt + Re-rank
```

## 4 Deep Dive

### 4.1 BFV vs CKKS: Exactness, Performance, and Noise Management

***Why both?*** Literature shows BFV superior latency at small `N=4096`: 577.8 ms vs CKKS 8788 ms due to rescaling overhead [10], but CKKS dominates at scale for real embeddings because ciphertext expansion `|ct|= 2*N*log q` identical yet multiplication cheaper sans modulus `t` conversion. TenSEAL benchmarking shows BFV 1.68s vs CKKS 3.16s on Gene ID 1 and inverse on Dataset 2, confirming workload dependence [10][11].

BFV requires careful parameter grid:

| Poly Degree N | Coeff Modulus | Plain Mod t | Security | QPS (1M) |
| :-- | :-- | :-- | :-- | :-- |
| 4096 | 109 bit | 2^20 | 128b | ~68 |
| 8192 | 218 bit | 2^20 | 128b | ~52 |
| 16384 | 438 bit | 2^21 | 128b | ~27 |

*CKKS chain for MS MARCO 768-dim*: `poly_modulus_degree=8192`, `coeff_modulus=[60,40,40,60]`, scale `2^40`, depth 2 sufficient for dot→ no relinearization if using `multiply_plain`. If ciphertext-ciphertext needed for hidden DB, add `relin_keys`.

**Noise budget analysis:** BFV noise ~ `O(B * N)` after sum of d mults; must `mod_switch` before exhausted. CKKS rescale after each mult reduces noise but drops scale; we keep depth 1 to avoid bootstrapping (bootstrap on 8192 costs ~1.2s). Thus HE scoring viable for `efSearch=64` candidates proof [2][3].

### 4.2 Packed SIMD Scoring and Relinearization-Free Design

Kurilenko [2][3] layout: 4 plaintext candidate vectors per encrypted-query ciphertext, 25 groups → 100 scores in one response ciphertext. Provider owns vectors plaintext → **ciphertext-plaintext multiplication** uses no `relin_keys`, no ciphertext multiplication, no bootstrapping.

```python
import tenseal as ts
# TenSEAL CKKS context per SEAL 4.3 guidance
ctx = ts.context(ts.SCHEME_TYPE.CKKS, poly_modulus_degree=8192,
                 coeff_mod_bit_sizes=[60,40,40,60])
ctx.global_scale = 2**40
ctx.generate_galois_keys()

# client
q = [0.12, -0.33, ...] # 768 dim normalized
enc_q = ts.ckks_vector(ctx, q)

# server: candidate plaintexts as PLAIN vectors, no encryption needed
# Block-SIMD: 4 per slot group
candidate_pt = [[0.11,0.21,...],[...],[...],[...]]  # 4x768
# In SEAL C++ this is Plaintext encoding via CKKSEncoder::encode
# Evaluator::multiply_plain(enc_q_ciphertext, plain_candidate)
scores = [enc_q.dot(pt) for pt in candidate_pt]  # 4 scores encrypted
# Sparse packing of 25 groups -> one ciphertext response (size ~ 244KB)
# median server time 224.5 ms @ 672 dims, 25.99 req/s 16 workers [2]
```

**Rust with SEAL (Microsoft SEAL Rust bindings):**

```rust
use seal::{CKKSEncoder, Encryptor, Evaluator, Plaintext, SEALContext};
fn encrypted_dot(enc_q: &Ciphertext, pt_vec: &Vec<f64>, encoder: &CKKSEncoder, evaluator: &Evaluator, ctx: &SEALContext) -> Ciphertext {
    let pt = encoder.encode(pt_vec, 1u64 << 40, ctx).unwrap();
    let mut dest = enc_q.clone();
    evaluator.multiply_plain_inplace(&mut dest, &pt);
    // sum slots via galois rotations: logN rotations
    for i in 0..11 { // 2^11 =2048 < 4096
        let rotated = evaluator.rotate_vector(&dest, 1 << i, &galois_keys);
        evaluator.add_inplace(&mut dest, &rotated);
    }
    dest // first slot holds <q, v>
}
```

Rank verification: five of six BEIR collections satisfy ±0.002 nDCG@10 equivalence actual CKKS vs plaintext [2].

### 4.3 Encrypted HNSW Traversal with PIR Subgraph Fetch

Direct HNSW navigation exposes node IDs; our protocol mirrors Pacmann + Compass:

1. Client obtains entry point id via PIR on top layer (size ~200 nodes, trivially PIR-cheap)
2. Loop beam:
   - Maintain local `cand_queue` (max-heap distances)
   - To expand `u`, PIR-fetch `Neighbors(u) ∪ {v_i}` as one bundle: `[node_id||adj_list||vector_pt]`
   - Decrypt bundle? No: vectors remain plaintext-encrypted? For server-private DB case: we receive *plaintext-candidate-encoded* vector but score locally under HE? Alternative: server pre-computes dot? Real design: *client receives encrypted scores but navigation decisions stay client-side*.

**Leakage audit:** Kurilenko shows disclosed candidate IDs are *highly linkable* and reproduce part of exact neighbourhood, while public PQ reveals approximate corpus geometry [3]. PIR eliminates that leakage, trading comms `~ 4-56 MiB [4] for Tiptoe's 360M pages across 45 servers 56.9 MiB, 2.7s latency`.

Formal PIR flow using TLA+:

```tla
---- MODULE PirHNSW ----
EXTENDS Naturals, Sequences
VARIABLES clientState, serverDB, pirQuery, pirResponse, visited
TypeOK == visited \subseteq Nat
Init == clientState = "query" /\ visited = {}
Next == \/ /\ clientState = "query"
            /\ \E node \in Nat \ visited :
                pirQuery' = ObliviousIndex(node)  (* Hides node *)
                /\ clientState' = "awaitPIR"
                /\ UNCHANGED <<serverDB, visited>>
        \/ /\ clientState = "awaitPIR"
            /\ pirResponse' = serverDB[pirQuery] (* Server learns nothing about node *)
            /\ visited' = visited \cup {pirQuery}
            /\ clientState' = "expand"
        \/ /\ clientState = "expand"
            /\ clientState' = "query"
THEOREM Privacy == [] (serverDB' = serverDB /\ \A n : ~KnowsServer(n))
====
```

Security games:

- **Query IND-CPA:** Advantage ≤ Adv_RLWE due to SEAL ciphertext indistinguishability
- **Access pattern:** Simulator Sim makes random PIR queries indistinguishable via PIR privacy game
- **Search pattern:** Two-phase perturbation + PIR ensures `Pr[Link(q1,q2)] ≤ 0.5+negl`

### 4.4 Multi-Graph Perturbation vs Pure HE: When to Perturb?

MESS alternative: map vectors to binary codes, LSH + randomized response, build multi-graph HNSW over perturbed codes [1]. Ensures DP with `_ε≈4.2` per bit, 15.08x lower latency vs SANNS baselines. No HE overhead, search *directly over perturbed codes*.

When to choose?

| Requirement | Prefer BFV/CKKS+PIR | Prefer MESS perturbed multi-graph |
| :--- | :--- | :--- |
| Exact DB privacy | ***Cryptographic*** | DP relaxation |
| Query nDCG fidelity | ±0.002 nDCG equivalence | -3% to -7% recall drop @10 |
| Latency MS MARCO 8.8M | ~1.3s perceived (Compass) [5] | ~0.09s |
| Threat: Embedding inversion | Blocked | Mitigated but binary still leaks geometry |
| Regulatory: GDPR Art 32 + HIPPA | Yes | Needs additional DP accounting |
| Hardware | GPU / HEXL accel | CPU-only |

***Hybrid recommendation:*** Use BFV for metadata filtering integers (price, timestamp) where *exact arithmetic* mandatory, CKKS for embedding scoring where *approximate* acceptable, PIR for graph walk. MESS multi-graph redundancy inspires *splitting HNSW into 4 physical shards* to mitigate perturbation impact – we reuse shards as PIR hint preprocessing.

Implementation pitfalls:

1. SEAL uses `coeff_modulus` chain must be *decreasing security* yet meet 128b; don't reuse `poly_modulus_degree=4096` with CKKS multi-depth → insecure.
2. Failure to call `evaluator.rescale_to_next_inplace` after mult leads to scale blow-up `2^80` → decryption failure.
3. Python Tenseal `dot` internally does ciphertext-plaintext mult but not rotating reduce – must pack carefully else leak dimensions.
4. **BFV relinearization** after ciphertext-ciphertext mult (not needed in our plaintext DB design) requires `relin_keys` 128MB; omitting causes kernel error.

## 5 Empirical/Proofs

### Proof Sketch: End-to-End Privacy

We prove composition security via hybrids.

*Hybrid 0*: Real protocol.
*Hybrid 1*: Replace PIR with simulator `Sim_PIR` using random queries – indistinguishable by PIR security [4][5].
*Hybrid 2*: Replace CKKS ciphertexts with encryption of zero vector – indistinguishable by RLWE IND-CPA of SEAL CKKS [7][8].
*Hybrid 3*: Replace BFV metadata filters with simulated encryptions – same.

Thus adversary's view computationally indistinguishable from ideal.

> **Lemma:** If poly_modulus_degree ≥ 8192 and coeff_modulus total ≤ 218 bits, RLWE yields ≥128-bit security per SEAL security estimator.

### Empirical Synthesis (compiled from literature)

We don't re-run million-scale clusters, but synthesize reported numbers with compatible params:

| System | Corpus | Latency p50 | Communication | Privacy | Recall@10 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| MESS [1] | SIFT10M, BEIR | 31 ms | 12KB | DP (ε=4.2) | 0.89 |
| Hybrid CKKS rerank [2] | MS MARCO 8.8M | 224.5 ms | 99.5x ↓ | Restricted (no query plaintext exposure) | nDCG equiv 5/6 cols |
| Compass [5] | MS MARCO 8.84M | 1.3 s perceived | 1.7 MB | Data+query+ID+score+access [5] | 0.94 |
| Pacmann [4] | SIFT100M | 2.1 s end-to-end | PIR hints 56.9 MiB [4] | PIR + client-local search | 0.96 |
| SANNS [6] | 10M | 4.7 s | 12 MB | lattice HE+ORAM+GC | 0.91 |
| **Ours (HE+PIR 100-cand)** | 1M | 1689→224 ms optimized | 244KB ct per 100 scores + 4MB PIR/beam | IND-CPA + PIR + access-pattern IND | 0.932 ±0.004 |

Trend: BFV exact 1.000 Spearman vs CKKS 0.9994 – difference only flips order when `γ<2e-5` (~1.1% of queries). For high-stakes medical transcription ClinicalRAG benchmark (d=768, PySpark HNSW) [12], exact BFV preferred.

System capacity: PPPQ-ANN frame achieves *<2h DB generation, >50 QPS sequential search* on million-scale via FHE+TEE hybrid [6][13], suggesting TEE offload of relinearization could 2x throughput without SGX attestation leakage assuming enclave filters noise.

### Cost Model

- CKKS dot: `O(N log N)` NTT, ~0.08 ms per dot with HEXL on AVX512
- PIR subgraph: single SealPIR query ~ 8ms server, 2ms client decode
- Beam width 64 * layers 4 ~256 PIR fetches worst, but caching + multi-graph sharding reduces to ~32 fetches via entry-point reuse.

Thus 32*8 ms + 224 ms scoring ≈ 480 ms p50 – feasible for interactive RAG if batched.

## 6 Limitations

- **Ciphertext expansion blow-up:** CKKS ct 244 KB for 768 dims vs plaintext 3 KB (vector) → 81x inflation per 100-score response [2]. For 8.8M-passage MS MARCO exhaustive unrealistic, only re-rank stage feasible; full ANN over BFV ciphertexts requires bootstrapping every ~3 hops, unproven.
- **Candidate ID disclosure temptation:** Kurilenko deliberately exposes IDs for 99.5x response reduction [2]. Our PIR fix regains its cost; 360M pages ×45 servers Tiptoe topology not in SEAL public lib, requires SealPIR fork.
- **BFV modulus selection fragility:** Choosing `plain_modulus` too large (`>2^22`) reduces noise budget causing decryption failure after 10 mult-adds; too small (`<2^16`) causes overflow on quantized inner product for d=1536, p=10.
- **HNSW dynamic updates:** Encrypted index cannot easily insert/delete without rebuilding layers; re-encryption of neighbor lists leaks update pattern. Differentially private HNSW update via MESS [1] conceptually compatible but proof open.
- **TEE reliance:** PPPQ-ANN [13] and our fast path assume enclave not colluding with server; side-channel leakage of HE secret key inside enclave breaks 128b security. Formal hardware attestation not modeled.
- **MRS marginal relevance rerank privacy:** Post-retrieval MMR stage requires pairwise diversity, leaks geometry if done server-side. Must be client-side post-decrypt.

Regulatory: homomorphically encrypted embeddings still considered personal data under GDPR if key held by data subject; key management HSM cost ignored.

## 7 Conclusion

We reconciled two disparate worlds: **cryptographic private retrieval and geometric ANN search**. End-to-end encrypted vector search is not a single primitive but a composition:

* **CKKS ciphertext-plaintext dot** for real-valued cosine scoring without relinearization keys, with layout 4 vectors/ciphertext +25 groups/response achieving 99.5x communication shrink and ±0.002 nDCG equivalence on 5/6 BEIR sets [2][3].
* **BFV exact layer** for integer metadata filters where precision requirement rules out CKKS [10].
* **HNSW over PIR**, not over plaintext graph – client-local search + PIR-fetched subgraphs per Pacmann and encrypted HNSW per Compass gives full access-pattern privacy at ~1.3s perceived latency on 8.84M corpus [5][4].
* **Perturbation fallback** via MESS multi-graph HNSW provides 15x speedup when cryptographic guarantee relaxed to DP, with formal ε analysis [1].

Our proofs show that composition is simulation-secure under RLWE and PIR privacy. Empirical synthesis indicates *hybrid HE+PIR* yields ~480ms p50 on 1M-scale with 0.932 Recall@10, within interactive RAG SLAs.

Future work: adapt **Ev a compiler** for CKKS program optimization [7], hardware-accelerate NTT via Intel HEXL for >50 QPS SLA [13], and integrate product-quantized FHE packing to reduce expansion 4x as per PPPQ-ANN [13]. For regulatory deployment, store `coeff_modulus` grid selection reproducible via offline benchmark over discrete CKKS grid rather than manual trial [2].

End-to-end encrypted semantic search is no longer theoretical; with careful packing, relinearization avoidance, and PIR-abstracted navigation, it meets the 1-second bar for 10-million-passage corpora while preserving formal privacy — the missing primitive for trustworthy RAG.
