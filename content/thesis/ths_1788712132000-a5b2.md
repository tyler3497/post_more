# Hardware Transactional Memory: Intel TSX RTM/HLE, Best-Effort Semantics, Transient-Execution Vulnerabilities, and the Retreat to Software Lock Elision

## Abstract

This thesis analyzes Intel's Transactional Synchronization Extensions (TSX) — the Restricted Transactional Memory (RTM) and Hardware Lock Elision (HLE) interfaces shipped with Haswell in 2013. We trace the lineage from Herlihy and Moss's 1993 architectural proposal for lock-free synchronization through the software transactional memory era to TSX's pragmatic realization as a *best-effort* mechanism: transactions are tracked via read-sets and write-sets in the L1 data cache, conflicts are detected at cache-line granularity, and a broad class of abort conditions — data conflicts, capacity overflow, interrupts, unsupported instructions — silently rolls back the transaction to a software-provided fallback. We dissect the RTM instruction semantics (*XBEGIN*/*XEND*/*XABORT*/*XTEST*) and the HLE prefix hints (*XACQUIRE*/*XRELEASE*), evaluate published results including the 1.41x average speedup on HPC workloads, and examine the TSX Asynchronous Abort catastrophe (TAA, CVE-2019-11135), which weaponized the abort path into a transient-execution side channel. We conclude with the deprecation timeline — TSX disabled by default via 2021 microcode updates, removal from client parts, and the industry's retreat to software-based lock elision — and derive lessons for future speculative synchronization hardware.

## 1 Introduction

The history of concurrent programming is, in large measure, the history of the lock: a brutally effective mechanism for serializing access to shared state that exacts its price in *priority inversion*, *convoying*, and *deadlock* [2]. In 1993, Maurice Herlihy and J. Eliot B. Moss proposed a radical alternative: *transactional memory*, an architectural extension letting a processor apply a customized read-modify-write operation to multiple, independently chosen words of memory atomically [2] — implemented, they argued, through "straightforward extensions to any multiprocessor cache-coherence protocol" [2].

The intervening two decades saw the idea refracted through software: Nir Shavit and Dan Touitou's *Software Transactional Memory* (1995/1997) delivered the abstraction without hardware support [3], and Dice, Shalev, and Shavit's *Transactional Locking II* (TL2) pushed software implementations near hand-crafted fine-grained locking via commit-time locking plus a global version-clock [11] — albeit with per-access instrumentation costs and malloc/free integration difficulties [11].

Intel's 2013 announcement that the Haswell microarchitecture would ship Transactional Synchronization Extensions (TSX) was therefore a watershed: for the first time, a mass-market processor would expose hardware transactional memory directly to software [1]. TSX arrived in two flavors [1]:

- **Restricted Transactional Memory (RTM)**: new instructions *XBEGIN*, *XEND*, *XABORT*, and *XTEST* giving the programmer explicit control over transactional regions, at the cost of a mandatory software fallback path;
- **Hardware Lock Elision (HLE)**: legacy-compatible *XACQUIRE*/*XRELEASE* prefixes letting existing lock-based code run transactionally unmodified.

What Intel shipped, however, was a deliberately weakened *best-effort* variant: transactions might abort at any time, for any of a dozen microarchitectural reasons, with no forward-progress guarantee [1]. That compromise — plus transient-execution vulnerabilities that turned the abort machinery into an information-disclosure primitive — set the stage for one of the most striking reversals in modern architecture: the systematic disabling and removal of a shipped ISA extension. This thesis analyzes that arc: the semantics, the mechanism, the evidence, the catastrophe, and the retreat.

## 2 Background

### 2.1 From Lock-Free Ambitions to Best-Effort Hardware

Herlihy and Moss's original scheme extended load-linked/store-conditional semantics to multi-word transactions, tracked in per-processor transactional caches and validated through the coherence protocol [2]. Their simulations showed transactional memory matching or outperforming the best known locking techniques [2].

Modern HTM abandoned that ambition. Intel TSX adopts *best-effort* semantics: the hardware guarantees atomicity and isolation only when a transaction happens to fit within microarchitectural resources and encounters no aborting event; otherwise it aborts, discards speculative state, and transfers control to a fallback path. The rationale is economic — bounding the hardware's obligation bounds its cost — but it shifts the burden of *liveness* entirely onto software.

> **Theorem:** *Best-effort progress.* In a best-effort HTM, no transaction is guaranteed to commit. Liveness must be established by the fallback path, which must be a *correct* (typically lock-based) implementation of the same critical section, because the hardware may abort every attempt.

### 2.2 The Two Interfaces of Intel TSX

Intel TSX exposes two software interfaces whose differences shaped the technology's fate [1]:

| Property | HLE (Hardware Lock Elision) | RTM (Restricted Transactional Memory) |
|---|---|---|
| Interface | *XACQUIRE*/*XRELEASE* prefixes | *XBEGIN*/*XEND*/*XABORT* instructions |
| Backward compatibility | Runs on legacy CPUs (prefixes ignored) | #UD on CPUs without RTM |
| Fallback path | Implicit: re-executes with lock taken | Explicit: programmer-supplied abort handler |
| Lock variable | Elided (left free) on success | Managed entirely by software |
| Nesting | Supported | Supported (7 levels on Haswell) |
| Status reporting | None (transparent) | *EAX* abort-status encoding |

**HLE** is a hint-based interface: prefixing the lock-acquire instruction with *XACQUIRE* and the lock-release with *XRELEASE* asks the processor to elide the lock — execute the critical section speculatively without ever writing the lock variable — committing atomically at the release point [1]. On legacy hardware the prefixes decode as ordinary *REPNE*/*REPE* prefixes, so HLE binaries run (non-transactionally) everywhere. If the transaction aborts, hardware transparently re-executes, typically taking the lock for real [1].

**RTM** gives the programmer explicit control: *XBEGIN* specifies a fallback address; on abort, control transfers there with an abort-status code in *EAX*. The programmer — not the hardware — decides whether to retry or to take a lock [1].

## 3 Methodology

This thesis employs a *historical-architectural methodology*: we reconstruct TSX's semantics from primary Intel documentation [1], validate microarchitectural claims against published measurement studies (notably Yoo et al.'s SC13 evaluation of TSX on Haswell [8]), and analyze the security literature surrounding transient-execution attacks on the abort path [4][5][6]. Our analytical lens is comparative: we contrast TSX's best-effort model with Herlihy and Moss's unbounded vision [2] and with software alternatives such as TL2 [11], and we reconstruct the deprecation timeline from Intel's own platform-update advisories and kernel documentation [7][9].

We organize the analysis around four questions — *semantics* (what the hardware guarantees), *mechanism* (how read-sets/write-sets are tracked and why aborts fire), *security* (how the abort path became an attack surface), and *fate* (why a shipped ISA extension was disabled by microcode and removed from silicon) — each addressed with reference to primary sources and published empirical data.

## 4 Deep Dive

### 4.1 Restricted Transactional Memory: XBEGIN, XEND, XABORT, XTEST

The RTM programming model is deceptively simple. A transactional region is delimited by *XBEGIN* (with a relative offset to the fallback handler) and *XEND*; *XABORT* with an 8-bit immediate explicitly aborts; *XTEST* reports whether the processor is in transactional execution [1][10]. A canonical lock-elision pattern in C, using the TSX intrinsics, is:

```c
#include <immintrin.h>

void elided_critical_section(lock_t *l) {
    unsigned status;
    int retries = 0;
    while (retries < MAX_RETRIES) {
        status = _xbegin();
        if (status == _XBEGIN_STARTED) {
            if (l->locked)          /* lock was taken: abort */
                _xabort(0xff);
            /* --- transactional critical section --- */
            do_work();
            /* -------------------------------------- */
            _xend();
            return;                 /* committed */
        }
        /* fallback: inspect status, maybe retry */
        if (!(status & _XABORT_RETRY))
            break;
        retries++;
    }
    lock_acquire(l);                /* slow path: real lock */
    do_work();
    lock_release(l);
}
```

The abort-status encoding delivered in *EAX* at the fallback is the source of most RTM bugs [10]:

| *EAX* bit | Meaning |
|---|---|
| 0 | Set if abort caused by *XABORT*; bits 31:24 then carry the immediate operand |
| 1 | Set if the transaction *may succeed on retry*; always clear when bit 0 is set |
| 2 | Set if another logical processor conflicted with an address in the transaction's read- or write-set |
| 3 | Set if an internal buffer overflowed (capacity abort) |
| 4 | Set if a debug breakpoint was hit |
| 5 | Set if abort occurred during nested transactional execution |
| 6-23 | Reserved |
| 24-31 | *XABORT* immediate (valid only if bit 0 set) |

> **Theorem:** *Status-bit discipline.* Correct RTM fallback logic must treat *EAX* as advisory. Bit 1 ("may succeed on retry") is a heuristic; the hardware may set it and then abort every retry. Only a *bounded* retry followed by lock acquisition preserves liveness.

The x86 assembly view makes the control-flow transfer explicit:

```asm
    xbegin  fallback        ; C7 F8 <rel32>: begin RTM region
    ; ... transactional body ...
    xend                    ; 0F 01 D5: attempt commit
    jmp     done
fallback:
    ; EAX = abort status; decide retry vs. lock
    test    eax, 1
    jz      take_lock
    ; ... bounded retry ...
take_lock:
    ; ... conventional lock acquire ...
done:
```

Nested transactions are supported — Haswell tracks up to 7 nesting levels — but an abort at any depth rolls back the outermost transaction [1].

### 4.2 Hardware Lock Elision: XACQUIRE/XRELEASE and the Legacy Contract

HLE takes the opposite tack from RTM: instead of exposing transactions to the programmer, it *hides* them inside the existing locking protocol. The processor recognizes the *XACQUIRE*-prefixed lock-acquire and *XRELEASE*-prefixed lock-release as transactional-region boundaries; it executes the critical section without modifying the lock variable, adding the lock's cache line to the read-set so that any *other* thread taking the lock non-speculatively triggers a conflict abort [1].

This design yields a remarkable compatibility property: because *XACQUIRE* (*F2*) and *XRELEASE* (*F3*) are ordinary string-operation prefixes on older CPUs, an HLE binary runs correctly — merely without elision — on pre-Haswell hardware [1]. On abort, the hardware re-executes the region and, in the simple policy, takes the lock for real [1].

HLE's weakness is its opacity. The programmer gets *no* abort status, *no* retry control, and *no* visibility into why elision failed — a debugging nightmare that practitioners consistently cited. Combined with its susceptibility to the same abort pathologies as RTM (Section 4.3) and the same security vulnerabilities (Section 4.4), HLE was the first casualty of the retreat: it was removed from 10th-generation client parts (Comet Lake, Ice Lake) and later steppings, while RTM lingered on server silicon [10].

### 4.3 Best-Effort Conflict Detection in the L1 Data Cache

The heart of TSX's implementation — and the source of its most punishing limitations — is the decision to track transactional state in the **L1 data cache**. On Haswell, the 32 KB L1D buffers speculative writes, while read-set membership is tracked via coherence-protocol extensions at *cache-line granularity* (64 bytes) [8]. A conflicting access is defined precisely: another logical processor either reads a line in the transaction's write-set or writes a line in its read- *or* write-set [1].

This yields the abort taxonomy that every TSX programmer had to internalize:

1. **Data conflicts** — genuine sharing, including *false sharing*: two threads touching different words of the same 64-byte line abort each other.
2. **Capacity aborts** — the read-set or write-set exceeds L1 tracking (EAX bit 3); write-sets beyond a fraction of the 32 KB L1D reliably abort [8].
3. **Explicit aborts** — *XABORT*, or the software pattern of aborting when the lock appears taken.
4. **Asynchronous aborts** — interrupts, page faults, system calls, CPUID, and disallowed instructions [1].
5. **Nesting overflow** — beyond 7 nested levels on Haswell.

The capacity limit is the cruelest because it is *workload-dependent and microarchitecture-specific*: a transaction that commits on one stepping may capacity-abort on another. Yoo et al.'s SC13 study confirmed that on real HPC workloads, transactions fitting comfortably in the L1 commit reliably, while footprint growth past the L1 boundary produces a sharp abort cliff [8].

> **Theorem:** *The capacity wall.* For best-effort HTM with L1-resident tracking, there exists a footprint threshold beyond which the abort probability approaches 1 *regardless of contention*. No retry tuning crosses this wall; the remedies are shrinking the transaction or abandoning the fast path.

### 4.4 Transient Execution and the TSX Asynchronous Abort Catastrophe

In November 2019, Intel disclosed **TSX Asynchronous Abort (TAA)**, assigned **CVE-2019-11135** with CVSS 6.5 (Medium), under advisory INTEL-SA-00270 [4]. TAA belongs to the Microarchitectural Data Sampling (MDS) family — alongside RIDL/ZombieLoad and Fallout — but exploits a *novel* mechanism rooted in the abort path itself [4].

The mechanism, as documented by Intel and the Linux kernel [4][5], is as follows. Intel TSX transactions may abort *asynchronously*: when another logical processor writes a line in the transaction's read-set, when buffering space is exceeded, or for other microarchitectural reasons, the abort is raised without an explicit faulting instruction [4]. Critically, *while a TAA is pending, certain loads inside the transaction that have not yet completed may read data from microarchitectural structures — the store buffer, fill buffers, and load-port writeback data bus — and speculatively pass that data to dependent operations* [4]. Those dependent operations leave cache-residency side effects that the attacker later measures, e.g., via Flush+Reload, inferring the sampled data [5].

Three properties made TAA devastating:

- **The victim need not use TSX.** Only the *attacker* begins a transaction and induces the asynchronous abort; the sampled buffers may contain data from the sibling hyper-thread, including kernel data [5].
- **It pierced existing MDS mitigations.** Cascade Lake parts unaffected by Fallout/RIDL were nonetheless vulnerable to TAA, because the abort path provided a fresh sampling primitive [4].
- **Mitigation was expensive.** The recommended mitigations — microcode plus OS/VMM updates — imposed performance costs, and the blunt alternative was disabling TSX outright [6].

TAA was not an implementation bug in the narrow sense; it was a *consequence of the architecture*. Any best-effort HTM that (a) permits asynchronous aborts and (b) leaves a speculative window between abort detection and pipeline flush creates a sampling primitive. The abort path, designed as a correctness mechanism, had become an oracle.

### 4.5 The Retreat: Force-Abort Microcode, Deprecation, and Software Lock Elision

The end of TSX came not with a single announcement but with a sequence of microcode-driven amputations. The timeline, reconstructed from Intel advisories and press analysis [7][9]:

1. **2019-2020**: TAA mitigations ship; Windows and Linux gain TSX disable toggles [6].
2. **June 2021 (IPU 2021.1)**: microcode **disables TSX by default** on Skylake through Coffee Lake client and Xeon E3 parts, citing a *memory-ordering issue* documented since 2018 [7][9]. The microcode *force-aborts all RTM transactions by default* and enumerates CPUID.07H.0H.EDX[11] (*RTM_ALWAYS_ABORT*); MSR 0x10F (*TSX_FORCE_ABORT*) allows clearing the feature bits entirely [7].
3. **2021 (IPU 2021.2)**: two more CPU families (Whiskey/Comet/Amber Lake, Coffee Lake-H) join the disabled-by-default list [7].
4. **10th generation onward**: Comet Lake, Ice Lake, and Tiger Lake client parts ship **without TSX in hardware at all**; HLE is discontinued [10].

The irony is exquisite: *RTM_ALWAYS_ABORT* preserves the *instruction-set* contract while voiding its *performance* contract. An RTM binary still runs — every transaction simply aborts immediately and falls through to the software fallback [7]. TSX became, by microcode fiat, a very expensive way to execute a branch.

The industry's response was a quiet return to software: STM runtimes, improved locks, and restricted RTM use on server silicon with TAA mitigations active. The lesson is not that transactional memory is useless, but that *best-effort hardware speculation without a security model* is a liability: every speculative structure is a potential side channel, and the abort path is the widest one of all.

## 5 Empirical Evidence

The empirical record on TSX divides into two eras: the *performance* era (2013-2018) and the *security* era (2018-present).

**Performance.** The landmark study is Yoo, Hughes, Lai, and Rajwar's SC13 paper, the first evaluation of production TSX silicon [8]. On a 4-core Haswell with 2-way SMT, TSX-based lock elision on real HPC workloads yielded an **average speedup of 1.41x** [8]. The authors emphasized *ease of application*: eliding existing locks required minimal code change [8].

**Security.** The TAA disclosure (CVE-2019-11135, CVSS 6.5 Medium) demonstrated practical information disclosure via the abort path on CPUs including Cascade Lake, which prior MDS mitigations had left exposed [4]. The response was measurable in code: Linux's `tsx=on/off/auto` parameter, MSR-based disable, and the eventual default-off posture [6].

**Deprecation.** Intel's IPU 2021.1 microcode disabled TSX by default across the Skylake-to-Coffee-Lake client and E3 lineup, with *RTM_ALWAYS_ABORT* enumeration and MSR 0x10F controls; IPU 2021.2 extended coverage; and 10th-generation client silicon removed TSX entirely [7][9].

| Era | Representative result | Source |
|---|---|---|
| Performance (2013) | 1.41x avg. speedup, HPC workloads, Haswell | Yoo et al., SC13 [8] |
| Performance (2013) | 1.31x bandwidth, user-level TCP/IP stack | Yoo et al., SC13 [8] |
| Security (2019) | TAA: CVE-2019-11135, CVSS 6.5, cross-HT leakage | Intel SA-00270 [4]; kernel docs [5] |
| Mitigation (2019-20) | tsx=on/off/auto, MSR disable, OS/VMM updates | Red Hat [6] |
| Deprecation (2021) | TSX off by default, RTM_ALWAYS_ABORT, MSR 0x10F | Intel IPU 2021.1/2021.2 [7] |
| Removal (2020-) | No TSX in 10th-gen+ client silicon; HLE discontinued | TSX documentation [10]; press [9] |

## 6 Limitations

This thesis has several limitations, which we state plainly.

First, **scope of measurement**: we synthesize published results rather than presenting new microarchitectural measurements; abort-rate curves and TAA exploit parameters are taken from the cited primary sources [4][5][8].

Second, **vendor asymmetry**: our analysis centers on Intel TSX because it is the only mass-market HTM with a full public rise-and-fall arc. IBM's POWER8/POWER9 HTM and other vendors' proposals receive less attention than they deserve; a comparative multi-vendor study remains future work.

Third, **software counterfactuals**: we argue that the industry "retreated to software lock elision," but the claim is qualitative. Quantifying how much of TSX's 1.41x-class gains [8] were recaptured by STM runtimes like TL2 [11] or by improved locks would require a controlled benchmark study we do not undertake.

Fourth, **architectural what-ifs**: we treat best-effort semantics as a design choice with security consequences but do not prototype alternatives (bounded-but-guaranteed HTM, abort-free commit protocols, speculative taint tracking) that might rehabilitate hardware speculation.

Finally, **security modeling**: our account of TAA follows Intel's and the kernel community's public descriptions [4][5]. A formal information-flow model of the abort path remains an open research problem.

## 7 Conclusion

Hardware transactional memory, as shipped by Intel, was a study in the gap between abstraction and implementation. Herlihy and Moss promised atomicity as a first-class architectural primitive [2]; Intel delivered a *hint* — a best-effort speculation that might commit, might abort for a dozen reasons, and guaranteed nothing [1]. For five years that hint paid off on the workloads it suited, with lock elision delivering 1.41x speedups on real HPC codes with minimal programmer effort [8].

But the best-effort contract contained the seeds of its own destruction. The abort path — the very mechanism that made best-effort semantics *safe* — proved to be a transient-execution oracle: TAA (CVE-2019-11135) showed that the speculative window around an asynchronous abort could sample the store buffer, fill buffers, and load ports across hyper-threads, with the victim needing no involvement in TSX at all [4][5]. Mitigation meant costly buffer hygiene or disabling the feature; Intel chose, stepwise, to disable it [6][7][9].

Three lessons endure. **First**, speculative hardware structures need a security model *before* they ship; every "transparent" rollback is a potential side channel. **Second**, best-effort semantics push liveness onto software — the slow path is the *real* path [11]. **Third**, ISA extensions are not forever: when microcode can turn *XBEGIN* into an unconditional branch to the fallback, the line between "supported instruction" and "deprecated fiction" is thinner than architects admit. The retreat to software lock elision is not a defeat for transactional memory as an idea — Herlihy and Moss's abstraction remains as compelling as in 1993 [2][3] — but it is a verdict on one particular bargain between hardware ambition and hardware honesty. Future HTM, if it comes, will have to earn back the trust that TAA spent.
