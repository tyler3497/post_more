# Algebraic Effects and Handlers as Modular Computational Effects: Row-Polymorphic Effect Typing, Scoped Handlers, and Denotational Semantics in Koka, Eff, and Frank

## Abstract
We present a systematic account of algebraic effects and handlers as a foundation for modular effectful programming, unifying theory and practice across Koka, Eff, Frank, and OCaml 5. Centered on Koka's row-polymorphic effect system with scoped duplicate labels, we formalize effect signatures as algebraic theories, handlers as folds over free monads, and effect rows as kinded polymorphism with heap parameters for safe state encapsulation. We trace denotational semantics from Plotkin-Pretnar to Bauer-Pretnar's effect system and contrast compilation strategies: generalized evidence-passing yielding O(1) dictionary dispatch, capability-passing in Effekt, and fiber-based resource-safe continuations in OCaml. Scoped effects such as once and local, whose continuations split into inside versus outside, are distinguished from algebraic ones, motivating our calculus λ_sc with explicit forwarding clauses. We prove type safety, effect safety, and evidence coherence, and analyze performance characteristics showing handler abstraction can be zero-cost for tail-resumptive programs.

## 1 Introduction

Since Plotkin and Power's observation that computational effects arise from algebraic theories [3], the separation of **effect interface** from **effect interpretation** has become a central design principle [2][7]. Algebraic effects model operations like `get`, `put`, `choose`, `raise` as uninterpreted symbols with arities `A -> B`; their intended equations generate a free monad `Free_E`. A handler then supplies a model of the theory, folding computations into pure values [3].

> **Motivating tension:** *Monad transformers compose poorly, while effect handlers compose by row concatenation. Yet without a disciplined type system, effect composition degenerates into dynamic handler search and untyped continuation capture.*

Three languages anchor this study:

- **Koka** [1]: row-polymorphic effect typing with duplicate labels for shadowing, Hindley-Milner inference extended to effect rows, scalable to tier-split web apps.
- **Eff / coreEff** [2][7]: first-class effect instances and handlers, effect system based on sets of operations tracked via denotational semantics and Twelf formalization.
- **Frank, Links, OCaml 5** [5][6]: Frank's handler adaptors and left/right adjustments; OCaml's retrofitted deep/shallow handlers atop fibers for zero-cost abstraction.

This thesis unifies them. We show why **scoped effects** such as `once`, `local`, `catch` whose continuation is *two-layered* (inside vs outside scope) cannot be algebraic [6], and require explicit forwarding clauses [6]. We then develop:

1. Formal syntax and kinding for Koka-style row polymorphism with heap parameter `h` for safe `st<h>` encapsulation.
2. Denotational semantics of handlers via Plotkin-Pretnar [3] and Bauer-Pretnar effect system [2].
3. Compilation strategy: *generalized evidence passing* [4] converting effect rows to evidence vectors `Ev<E>`, enabling **O(1)** dispatch to handler clauses without traversing stack [4].
4. Empirical analysis of dispatch cost vs OCaml fiber capture and Parallel Eff's `for` construct [8].

Contributions summarized: typed elaboration preserving row equivalence under scoped duplicate, soundness proof for row-polymorphic let-generalization, and performance model.

## 2 Background / Preliminaries

### 2.1 From Monads to Algebraic Theories

Computational effects classically modeled as monads `M` [Moggi 1991]. Algebraic perspective refines: an effect signature `Σ = { op_i : A_i → B_i }` defines a functor `F_Σ X = Σ_i A_i × (B_i → X)`. Its free algebra `Free_Σ X = μY. X + F_Σ Y` is the syntax tree of effectful computations with `Return : X → Free_Σ X` and `Op : A × (B → Free_Σ X) → Free_Σ X`. Any other `Σ`-algebra gives semantics.

**Handler** `h : Free_Σ X → C` defined by clauses:

```koka
handler h {
  return x -> e_ret
  op1(x; k) -> e_op1  // k : B1 -> C is resumption
  finally(x) -> e_fin
}
```

Deep handlers recursively re-handle resumption; shallow handlers do not [5]. Plotkin and Pretnar prove handling corresponds to unique homomorphism `fold` from free model [3].

*Example nondeterminism:*

```koka
effect choice {
  fun choose() : bool
}

fun toss() : <choice> string {
  if choose() then "Heads" else "Tails"
}

with handler {
  return x -> [x]
  choose() k -> k(true) ++ k(false)
} toss()
```

This recovers list monad, but as interpretation, not encoded monad.

### 2.2 Koka's Effect System Heritage

Leijen [1] proposes language where every function arrow carries its effect row:

```
t ::= a | () | t1 -><e> t2 | ref<h,t> | list<t>
e ::= <> | <l|e> | μ
l ::= exn | div | st<h> | io | l1
```

Rows may contain **duplicate labels** `<exn|<exn|μ>>`. Duplication enables shadowing: inner handler masks outer occurrence, modeled not by set exclusion but ordered scoping [1]. Kinding `Δ ⊢ t : κ` ensures heap variable `h` of kind `h` does not escape `runST` encapsulation: `run : forall h a e. (() -> <st<h>|e> a) -> e a` safe only if `h ∉ ftv(a,e)` [1].

Row polymorphism generalizes *open effects*: `map : forall a b e. (a -><e> b, list<a>) -><e> list<b>` says `map` works in any effect context, `e` remains polymorphic, instantiated to `<exn|μ>` or `<io|μ>`.

### 2.3 Eff and Denotational Effect System

Eff [7] tracks effects as sets `Δ = { op1: A1→B1, ... }`. Bauer and Pretnar [2] give effect system `Γ ⊢ c : A ! Δ` where handler type `A!Δ ∪ O → B!Δ'` transforms effects. Non-monotone: handler can **remove** operations, enabling pure result from impure body. Denotational semantics uses domains with partial equivalence relations, proven adequate and safe in Twelf [2].

Frank refines: effect operations are *abilities* with ambient handling, parameterized handlers are first-class values, left/right adjustments control forwarding [literature].

## 3 Methodology / Formalism

### 3.1 Syntax of λ_eff^row

We define core calculus inspired by Koka [1] and λ_sc [6]:

```
v ::= x | () | \x.e | handler h
e ::= v | v1 v2 | let x = e1 in e2
    | perform op v
    | handle e with h
    | mask<l> e
```

Effect constants `c^κ` include `exn`, `div`, `st`. Row formation ` ε ::= <> | μ | <l|ε>` with kind `e`. Type scheme `σ ::= forall a μ. t`.

Kinding rules:

- `Δ, μ:e ⊢ μ : e`
- `Δ ⊢ <> : e`
- `Δ ⊢ l: k , Δ ⊢ ε:e ⇒ Δ ⊢ <l|ε>:e`

Typing judgment `Γ ⊢ e : t | ε`.

**Operation rule:**

```
op : A -> B ∈ Σ_l    Γ ⊢ v : A | ε
------------------------------------ T-Op
Γ ⊢ perform op v : B | <l|ε>
```

**Handler rule:**

```
Γ, x:A ⊢ e_r : C | ε'
Γ, x:A_i, k:B_i -><ε'>C ⊢ e_i : C | ε'  for each op_i
-------------------------------------------------------- T-Handler
Γ ⊢ handler{ return x->e_r ; op_i(x;k)->e_i } : A!<l|ε> ⇒ C!ε'
```

This ensures handler discharges label `l` from incoming row.

### 3.2 Elaboration to System F^ev

Following Xie and Leijen [4], elaboration `Γ ⊢ e : t|ε ↝ e' : t'` translates effect abstraction to explicit evidence parameter `w : Ev<ε>`.

Evidence vector:

```
Ev<> = ()
Ev<l|ε> = (Marker l, Handler l, Ev ε)
```

Operations compiled to `yield m w[off(l)] arg` where `off(l)` static offset computed from row shape, enabling O(1) lookup rather than linear search [4]. Handler introduction creates prompt `prompt m h`.

Bauer-Pretnar safety theorem lifts: if `∅ ⊢ e : A | <>`, then evaluation never stuck on unhandled `perform`.

### 3.3 Scoped Effects vs Algebraic

Wu et al. [6] classify **scoped** operations whose syntax carries a *scoped* computation: `once : M A -> M A`, `local : (R -> M A) -> M A`. Algebraic form `A -> B` insufficient because continuation splits in two: inside scope and outside. λ_sc calculus extends signature with `scop : A -> (M B -> M C)`. Its handler must handle inner scope explicitly:

```haskell
-- Haskell sketch scoped handler for once (remove nondet duplicates)
data Scoped sig = forall a. Once (FreeScoped sig a)
handlerOnce :: FreeScoped (Choice :+: sig) a -> FreeScoped sig [a]
handlerOnce (Return x) = return [x]
handlerOnce (Op (Inl Choose) k) = do
  xs <- handlerOnce (k True)
  ys <- handlerOnce (k False)
  return (xs ++ ys)
handlerOnce (Sc (Once p) k) = do
  xs <- handlerOnce p
  case xs of [] -> handlerOnce (k Nothing)
             (y:_) -> handlerOnce (k (Just y))
handlerOnce (Op (Inr op) k) = Op op (handlerOnce . k)
-- forwarding required for unknown scoped ops
handlerOnce (Sc op k) = Sc op (handlerOnce . k) -- explicit
```

Without last clause, unknown scoped ops silently dropped – λ_sc forces explicit forwarding [6]. This motivates Koka's `mask` and Frank's adaptors.

## 4 Deep Dive: Row Polymorphism, Evidence Passing, and OCaml Fibers

### 4.1 Scoped Rows with Duplicate Labels

Leijen's key invention: rows are **scoped**, not set-based [1]. Consider:

```koka
fun outer(): <exn,exn> int { perform exn("a"); perform exn("b") }

with handler { exn(s) -> 1 } in
with handler { exn(s) -> 2 } in
outer()  // yields 2 for first perform, shadows outer
```

Type `<exn|<exn|μ>>` distinguishes inner occurrence at offset 0 from outer at offset 1. Masking operator removes nearest occurrence:

```
mask<exn> : forall a e. (() -> <exn|e> a) -> e a
```

Operationally, masking drops evidence vector head, allowing abstraction `lift : forall e. (() -> e a) -> e a` without losing polymorphism.

> **Theorem 4.1 (Effect Safety, Leijen [1] Lemma 5.2):** If `Γ ⊢ e : t | <>` and `e ⇓ v` then `v` value; if `e ⇓ perform op` stuck then `op` not closed – impossible for empty row. Moreover if `exn ∉ ε` then eval never performs `exn`.

*Proof sketch via logical relation indexed by effect row length; progress and preservation lemmas preserving kinding `Δ ⊢ ε:e` under substitution.*

Row unification algorithm: `unify(<l1|ε1>, <l2|ε2>)` if `l1=l2` then unify tails; if `l1≠l2` and `ε1 = μ` variable, instantiate `μ := <l2|μ'>` preserving order. Duplicates complicate: `<l|μ>` unifies with `<l|μ>` with same duplication pattern, not collapsed. Complexity O(n α(n)) practical.

### 4.2 Generalized Evidence Passing Compilation

Xie et al. [4] show naive CPS compilation to `Cont` allocates closures per operation (10× slowdown). Their pipeline:

1. elaborated λ^ε to λ_ev (evidence passing)
2. multi-prompt delimited control `prompt/yield`
3. yield bubbling translation
4. monadic translation to System Fω
5. C backend via Perceus reference counting

Crucial insight: evidence vector layout known statically. Function type `A -><ε> B` compiles to `Ev ε -> A -> B`. Tail-resumptive handler `op -> k e` where `k` applied exactly once in tail position optimized to not reify continuation [4] – 56% operations in Koka corpus tail-resumptive.

Performance claims from PLDI experiments [4][5]:

| System | Dispatch | Continuation Capture | GC Interaction |
|--------|----------|---------------------|--------------|
| Koka/evidence | O(1) field load `w->h_op` | No alloc for tail-resumptive | Perceus reuse, no pauses |
| OCaml 5 fibers | O(depth) linear scan depth ≤4 typical | Fiber segment linked list O(1) switch | OCaml minor heap |
| Eff old | O(depth) find handler | Copy stack + CPS | OCaml GC |
| Links (handler closures) | O(depth) | Closure chain | GC |

This table aligns with Dolan et al. [5] measuring fiber `perform` 6.5ns vs Haskell 35ns.

Python simulation of evidence dispatch illustrates O(1) vs O(n):

```python
# Empirical evidence dispatch microbench (simplified)
import time
class Handler:
    def __init__(self, name): self.name=name
    def handle(self, x): return x+1

# evidence vector as tuple of handlers
ev = (Handler("exn"), Handler("st"), Handler("io"), Handler("div"))

def dispatch_op_ev(op_index, arg):
    # O(1) direct index from type derivation
    h = ev[op_index]
    return h.handle(arg)

def dispatch_op_linear(stack, op_name):
    # linear search simulation
    for h in reversed(stack):
        if h.name == op_name:
            return h.handle(1)
    raise Exception("unhandled")

# micro timing
t0=time.perf_counter()
for _ in range(1000000): dispatch_op_ev(2, 1)
t1=time.perf_counter()
print(f"O(1) 1M dispatches {(t1-t0)*1e6/1e6:.3f} µs/op")

stack = [Handler("exn"), Handler("div"), Handler("io")]
t0=time.perf_counter()
for _ in range(1000000): dispatch_op_linear(stack,"io")
t1=time.perf_counter()
print(f"O(n) linear {(t1-t0)*1e6/1e6:.3f} µs/op")
```

Predicted ratio ~2-3×; with depth 20 as in Links nesting, O(1) wins clearly.

### 4.3 OCaml 5 Fiber Implementation

Retrofitting handlers onto OCaml [5] required preserving DWARF unwind tables, C stack interop, and backtrace compatibility – impossible with CPS. Dolan et al. use **fibers**: heap-allocated stack chunks with parent pointer, handler frame, exception pointer.

Deep handler semantics: `try_with f handler` installs fiber, `perform e` unwinds to matching handler via assembly that switches stacks. Formal small-step:

```
<Perform op v; EffCont k; Fiber chain> -> <Handler clause op v k>
<Continue k v> pushes captured chain back
```

One-shot continuation restriction (affine) avoids exponential copying on multi-shot search trees; multicont clone explicitly.

Eio library builds directly atop: `Mutex.acquire = perform (Suspend)`, scheduler handler loops over runnable queue. Effect handler therefore unifies async I/O, generators, cooperative threads without callback hell.

### 4.4 Parallel Handlers and Frank's Adjustments

Xie et al. [8] extend handlers with `for` expression modeling data-parallel loop parallelizable across cores similar to Dex. Operation `traverse` effect handles `for n. e` with fusion of accumulations. Handler type signature adds parallel continuation `k : forall i. A -> Par B`.

Frank language central idea: ambient ability *must* be handled; inability to handle is type error. Adaptors handle effect polymorphism: `map : <X> { [A] -> [B] }` where `<X>` adjustment passes ambient through. This resembles Koka's `e` row variable but with left/right bias: `<x>` vs `<-x>`.

## 5 Empirical Evaluation / Proofs

### 5.1 Type Safety Proof Outline

We prove soundness of λ_eff^row.

1. Kinding preservation under substitution: `Δ ⊢ τ:κ` and substitution respects kind.
2. Progress: If `Γ ⊢ e : t | ε` then either `e` value, or `e = E[perform op v]` with `op∈ε`, or `e → e'`.
3. Preservation: Step maintains type modulo row equivalence `ε =_ρ ε'` where duplicate-permitting equivalence allows permutation only of distinct labels (Leijen Fig 6).
4. Evidence coherence: two elaborations with different row derivations yield operationally equivalent target programs via logical relation `w1 ≃ w2 : Ev ε` up to marker renaming [4].

> **Corollary:** *Encapsulation.* If `⊢ e : a | <>` and `a` ground without `st<h>`, then `e` never allocates state that escapes via `run`. Formal: `run : (() -> <st<h>|e> a) -> e a` safe if `h ∉ ftv(a,e)`.

### 5.2 Benchmark Correspondence (Analytical)

Construct analytical model for throughput of 10k `perform` loop:

- Koka evidence: per operation 1 load + indirect call = ~3 cycles + tail-resumption eliminates cont alloc.
- OCaml fiber: 6.5ns measured [5] due to assembly switch, comparable.
- Haskell `mtl` via Ev.Ex: 35ns closure alloc per bind.

Thus handler abstraction reaches zero-cost for tail-resumptive bulk – aligns with Eio echo benchmark 112k req/s matching Lwt hand-optimized state machine [5].

Tree walk counting nondet benchmark mentioned in Xie et al. ICFP artefacts: Koka 0.71s tail-optimized vs 1.2s unoptimized vs 1.4s OCaml – factor 1.7 improvement important.

### 5.3 Scoped Handler Correctness

β reduction for scoped operation must preserve forwarding shape:

```
handle (sc op p k) with h
 = clause_sc (handler (p) ) (λ x. handle (k x) with h)   if op handled
 = sc op (λ _. handler p) (λ x. ...)                      else forwarded
```

Condition explicit forwarding ensures *modular composition* – adding new scoped operation does not silently change semantics of existing handlers, solving expression problem noted in Wu et al. [6] Sec 2.

### 5.4 Handler Fusion Laws

State handler combined with exception handler commutes when `st<h>` does not appear in `exn` handler result type – follows from row disjointness and heap parameter freshness. Proof via handler fusion law `h_st ∘ h_exn = h_exn ∘ h_st` when row labels distinct and handlers pure [3].

## 6 Limitations and Future Work

**Duplicate row confusion.** Programmers struggle understanding `<exn,<exn|μ>>` vs `<exn|μ>`. Koka prints collapsed row `<exn|μ>` hiding shadowing, causing diagnostics opacity when masking needed. Remy's presence polymorphism [literature] alternative more explicit but inference heavier [1].

**OCaml effect safety absent.** OCaml 5 exposes handlers via library `Effect.Deep` with extensible variant `type _ Effect.t += _`, but compiler does not ensure all effects handled; unhandled `perform` raises `Unhandled` exception [5]. Jane Street draft proposal [5] for static effect system not yet mainline – unsound default remains industrial compromise.

**One-shot restriction limits multi-shot search.** Implementing backtracking `choose` returning list results via deep handler with resume loop works, but multi-shot `amb` needs cloning fiber chain O(depth) memory – static affine kind system proposed future work [5].

**Perceus GC interaction with continuations.** Koka's Perceus reference counting deallocates promptly, but captured continuation holding reference to large structure extends lifetime until resumed, breaking timeliness guarantees if continuation leaked in async queue.

**Existential heap masking unsoundness.** Current Koka permissive condition `h` fresh check DIV [1] can be circumvented via higher-rank polymorphically masked state inside polymorphic function awaiting instantiation – requires full rank-2 polymorphism tracking, not yet implemented.

**Deep recursion blow-up.** Deep handler recursion where inner immediately performs outer effect grows fiber chain unbounded; shallow loop preferred but less compositional.

**Parallel contention.** λ^p [8] assumes race-free `traverse` that reduces via associative operator; non-associative case unclear.

Future directions combine three threads:

- OCaml static row system enabling evidence constant-folding while retaining fiber performance [4][5]
- Koka fiber backend avoiding heap allocation via stack switching on architectures supporting `call/cc` assembly
- First-class handler names with rank-2 polymorphism handling multiple same-label instances without shadowing trick – explored in Koka named handlers branch.

> **Open Problem:** *Linear continuation types integrating row polymorphism and affine kinds to statically enforce single-use resumption while preserving Hindley-Milner inference remains unsolved.*

## 7 Conclusion

We traced row-polymorphic algebraic effects from Remy's record heritage to Koka and OCaml 5, linking theoretical roots in free monad algebras [3] to practical compilation via **generalized evidence passing** [4] and **segmented stacks** [5]. Scoped rows with duplicate labels offer simplest Hindley-Milner compatible composition without presence variables, while kinding with heap labels enables safe local-state encapsulation mirroring `runST` without value restriction [1]. Evidence vectors flatten handler search to static offsets, enabling Koka compile to plain C preserving Perceus reuse, while OCaml fibers preserve debugger and C FFI compatibility with ~1% baseline overhead [5][6].

Both systems demonstrate disciplined effects can be *type-apparent, composable, and competitive* with monadic or Lwt code while preserving direct style. As Wang concluded for OCaml, **effects handlers provide native substrate for scalable concurrent apps** [5]. For Koka, they provide typed foundation for tier-split cloud programming where effect row documents IO, exceptions, and mutable heap – making side-effects explicit.

The field moves toward linear resource rows enforcing single use of file handles, cancellation tokens, and channels – combining row polymorphism with affine kinds toward verified IO pipelines, where *effect operation signature diagram* becomes capability token, *handler forwarding* becomes evidence plumbing, and *row polymorphism* becomes effect variable discipline – a triumvirate visualized.
