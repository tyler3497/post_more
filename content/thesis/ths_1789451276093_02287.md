## Abstract

Compilers are among the most consequential trusted components in the software stack: a single miscompilation can silently invalidate every property proved about a program's source code. This thesis examines the state of the art in *verified compilation*, in which a machine-checked proof guarantees that compilation preserves observable program behavior. We survey the two dominant architectures — the **fully verified compiler** exemplified by CompCert [1], whose Coq-certified backend transforms C through intermediate languages to assembly, and the **HOL4-based CakeML compiler** [2], whose end-to-end theorem reaches concrete machine code on several real instruction set architectures. We develop the central proof technology, **forward simulation** between labeled transition systems, showing how it composes across passes and yields backward simulations under deterministic target semantics [1]. We contrast a-priori verification with **translation validation** [3], the per-run certification approach of Pnueli, Siegel, and Singerman, and analyze the **semantic gap**: undefined behavior, abstract memory models, resource limits, and foreign-function interference. The synthesis identifies where mathematical certainty has been achieved and what still separates verified source code from trustworthy executables.


##1 Intro

Every formal verification effort that stops at the source code level rests on an unexamined foundation: the compiler that translates the verified source into executable machine code. The uncomfortable truth, articulated memorably in Thompson's *Reflections on Trusting Trust*, is that a compromised or buggy compiler can undermine arbitrarily strong source-level guarantees [4]. For safety-critical and high-assurance software — avionics control laws, cryptographic implementations, operating-system kernels — testing the compiler, however rigorous, cannot deliver the certainty that the toolchain itself is semantics-preserving. The field of **verified compilation** exists to close this gap by producing a *machine-checked proof* that a compiler preserves program behavior.

Two landmark projects define the modern landscape. **CompCert**, developed principally by Xavier Leroy and collaborators, is a realistic optimizing compiler for the C language whose backend — from the Cminor intermediate language down to assembly — is verified in the Coq proof assistant [1]. Its top-level theorem states that every observable behavior of the generated assembly code is a behavior of the source program, modulo the caveat that source programs must avoid undefined behavior. **CakeML**, developed in the HOL4 theorem prover, takes a functional language of a different character — a subset of Standard ML — and verifies compilation all the way to *concrete machine code* for several commercial architectures including ARMv8, x86-64, MIPS-64, ARMv6, and RISC-V [2]. Where CompCert stops at assembly and trusts the assembler, CakeML's end-to-end theorem relates source-level behavior to the behavior of bits executing under validated ISA models.

This conversion is the technical heart of the field.

Yet a-priori verification of the compiler is not the only route to trustworthy compilation. **Translation validation**, introduced by Pnueli, Siegel, and Singerman [3], takes the opposite stance: instead of proving the compiler correct once, each individual compilation run is followed by a *validation phase* that checks that the particular target code produced correctly implements the particular source program submitted. CompCert itself hybridizes the two philosophies: while its translation passes carry direct proofs, auxiliary heuristics like graph coloring and control-flow-graph linearization are checked by verified validators [1].

Between the source program as the programmer conceives it and the machine code as the processor executes it lies the **semantic gap**: undefined behavior, abstract versus concrete memory models, out-of-memory exits, interference from foreign code and interrupts, and the assembler and linker themselves. Understanding exactly where the gap has been closed and where it remains open is the central analytical task of this thesis.

##2 Background

### Labeled transition systems and program semantics

The lingua franca of verified compilation is the **labeled transition system (LTS)**: a set of states, a set of labels (observable events such as system calls), and a step relation describing how states evolve while emitting labels. Program behavior is then defined *coinductively* as the set of finite or infinite traces of observable events a program can produce [1]. Each language in a compiler pipeline is equipped with a small-step operational semantics presented as an LTS [5]. CompCert, for example, assigns formal semantics to roughly eight intermediate languages, from CompCert C and Clight through Cminor, RTL, LTL, Linear, and Mach, to Asm [1]. The *target-side* languages are deterministic: given a state and a trace prefix, at most one successor state exists. Determinism of the target is not a mere convenience; it is the hypothesis that makes the forward-to-backward simulation theorem go through.

### Forward and backward simulations

A **forward simulation** from a source LTS *S* to a target LTS *T* is a relation *R* between source and target states such that (i) initial states are related, and (ii) whenever a source state *s* related to a target state *t* takes a step to *s'*, the target can take zero or more steps to some *t'* with *s'* related to *t'* [5]. The direction matters: forward simulation says that every source behavior is reproducible by the target. A **backward simulation** reverses the quantifiers: every *target* behavior is matched by some source behavior. For compiler correctness, the backward direction is the one we want — it rules out the compiled program doing something the source could never do — but forward simulations are far easier to prove, because the proof follows the compiler's own direction of transformation.

The celebrated bridge theorem, due to Leroy and mechanized in Coq, states:

> **Theorem:** If the target LTS is deterministic (its step relation is a partial function on states), then every forward simulation from source to target yields a backward simulation from target to source [1].

The proof is elegant: determinism means the target's execution from a related state is unique, so any target trace must be the image of a matching source trace; a target step that the source could not match would contradict the forward simulation [5]. This theorem is the reason CompCert's entire proof architecture is organized around forward simulations of individual passes, composed transitively into an end-to-end forward simulation, and flipped once at the very end.

```coq
Theorem transf_c_program_correct : forall p tp,
  transf_c_program p = OK tp ->
  backward_simulation (Csem.semantics p) (Asm.semantics tp).
```

The backward simulation implicitly quantifies only over non-wrong source behaviors: programs that go wrong — dereferencing null, dividing by zero — are excluded from the guarantee, the formal "garbage in, garbage out" stance [1][5].

### Translation validation as an alternative

Translation validation abandons the ambition of proving the compiler correct in general. Instead, for each compilation of a program *P* into *P'*, a *validator* — itself a verified program — checks a refinement or equivalence relation between the two specific artifacts [3]. If the validator accepts, the user obtains a per-run certificate of correctness; if it rejects (or the compiler crashes), no claim is made. The validator's proof obligation is typically a *simulation check* discharged by symbolic execution, model checking, or decision procedures over the two control-flow graphs. Because the validator only ever reasons about one pair of programs at a time, it can handle optimizations whose general correctness is hard to prove — the validator simply needs to succeed on the instances the compiler actually produces [3].

##3 Methodology

This thesis is a *comparative analytic study* of primary mechanized artifacts and their accompanying publications.

1. **Primary-source analysis.** We examine the proof developments and papers for CompCert [1], the CakeML compiler [2], the original translation-validation proposal [3], and recent extensions including verified space-cost semantics [6] and the nominal-memory-model variant of CompCert [7].
2. **Theorem-level comparison.** We normalize the correctness statements of the different projects into a common vocabulary — source and target LTSs, simulation relations, side conditions on definedness, and resource bounds — so their guarantees can be compared apples-to-apples (see the table in Section 4).
3. **Gap analysis.** We enumerate the assumptions each end-to-end theorem makes — determinism, defined behavior, memory-model fidelity, assembler trust, resource sufficiency, environment interference — and classify each as *discharged by proof*, *checked per run*, or *trusted*.

We do not attempt new mechanized proofs; our contribution is analytic and synthetic, grounded in statements that have been machine-checked rather than merely asserted.

##4 Deep Dive

### Forward simulation: the mathematical backbone

The forward simulation is to verified compilation what the loop invariant is to program verification: the workhorse proof pattern that makes the whole enterprise tractable. Its power comes from two compositionality properties. First, **forward simulations compose transitively**: given a simulation *R1* from language *A* to language *B* and *R2* from *B* to *C*, the relational composition *R2 ∘ R1* is a forward simulation from *A* to *C* [5]. This is what lets CompCert prove each of its roughly twenty passes independently and obtain the whole-pipeline theorem by chaining. The mechanized composition proof is delicate — it must handle the case where one source step maps to *zero* target steps (a "stuttering" step, as when a pass deletes a no-op) — and CompCert's library therefore provides several simulation *diagram shapes*: lock-step (one-to-one), plus (one-to-many), star (one-to-zero-or-more), and option variants, each with its own measure argument to rule out infinite stuttering [1].

Second, as discussed in Section 2, forward simulations **flip to backward simulations under target determinism**. The flip is applied exactly once, at the boundary of the whole compiler, which is why every intermediate language in CompCert is designed with deterministic semantics even where the real machine is not deterministic — nondeterminism is pushed below the verified abstraction boundary (into the assembler, the operating system, or the hardware model) [1].

### CompCert: a verified C compiler backend

CompCert compiles a large subset of ISO C99 — **CompCert C** — to assembly for x86 (32 and 64 bit), ARM, RISC-V, and PowerPC [1]. The pipeline has a *frontend* (CompCert C → Clight → Cminor, handling C's expression evaluation order, memory model, and the defined/undefined distinction) and a *backend* (Cminor → RTL → … → Asm) with classic optimizations: constant propagation, common-subexpression elimination, dead-code elimination, inlining, tail-call optimization, graph-coloring register allocation, and CFG linearization [1].

Each pass is proved sound by a forward simulation; the development totals on the order of one hundred thousand lines of Coq, the proof dominating the compiler itself [1]. Two design decisions deserve emphasis. First, CompCert optimizes lightly by industrial standards, trading optimization power for proof tractability. The verified-validator pattern is used where heuristics resist direct proof: the graph-coloring allocator runs *unverified* code to choose a coloring, and a *verified checker* confirms it; only the checker's correctness is proved [1]. Second, CompCert's C semantics is a *deterministic* refinement of the standard — evaluation order is fixed — so programs depending on unspecified order receive one specific behavior [5]. The remaining distance to the ISO standard's nondeterministic specification is documented rather than proved.

The end-to-end theorem, quoted in Section 2, delivers **behavioral preservation for defined programs**: every observable behavior of the assembly program (a trace of system calls and termination/divergence outcomes) is a behavior the source program could exhibit [1]. "Observable" here means system calls and volatile accesses — the compiler is free to transform everything else.

The CakeML statement is correspondingly nuanced: if the source program has no *Fail* behavior (the analogue of going wrong), then any machine-code execution from a properly initialized state produces only behaviors contained in the source program's behavior set, *extended with early exits due to resource limits* [2]. The resource clause is essential, since the compiler cannot guarantee memory suffices for GC and bignum arithmetic. Recent work strengthens this with a **verified space-cost semantics**: a source-level cost model proved sound for compiled code *including the GC implementation*, so programmers can prove space bounds at the source level and transfer liveness properties to machine code [6] — the first result of its kind.

CakeML's proof architecture also models the environment: the top-level theorem accounts for **interference** from foreign code and per-instruction interference from external processes such as interrupt handlers, keeping the theorem valid for programs embedded in OS-like environments [2].

### Translation validation: certifying each compilation

The original proposal by Pnueli, Siegel, and Singerman targeted the SIGNAL synchronous-language compiler: after each run, a validator compares source and generated code, establishing a refinement relation fully automatically [3]. The approach shines for optimizations that are correct in practice but resistant to general proof — aggressive loop transformations, instruction scheduling, heuristic register allocation. Rather than verifying the optimizer, one verifies the *checker*, which is typically far simpler.

CompCert internalizes this idea at the pass level. Its register allocator performs graph coloring with unverified heuristics, then a verified validator checks the coloring; its CFG linearization enumerates nodes with an unverified heuristic, then a verified validator checks the enumeration [1]. This hybrid architecture — direct proofs where feasible, validated heuristics where not — is arguably the most important methodological export of the CompCert project: it shows how to scale verification to compilers that use genuinely clever algorithms without paying the full proof cost of those algorithms.

Modern translation validation uses SMT solvers and symbolic execution to check refinement between unoptimized and optimized functions automatically. The validator's trusted base is small, but the approach has a structural weakness: *coverage*. A validator bug, or one that silently fails open, undermines every compilation it touches, whereas the verified compiler's proof is checked once by the proof assistant's kernel. In practice the two are complementary: verify the stable translation passes, validate the heuristic optimizations.

### The semantic gap: undefined behavior, memory models, and the trusted base

The **semantic gap** is the distance between what the correctness theorem talks about and what actually executes. We decompose it into five strata:

1. **Undefined behavior.** C programs that go wrong are excluded from CompCert's guarantee [1]; CakeML excludes *Fail* behaviors [2]. The compiler is verified relative to a *defined* semantics, so source-level tools must prove absence of undefined behavior — the compiler amplifies source guarantees but cannot create them.

2. **Memory models.** CompCert's abstract block memory must be *realized* by the machine's flat address space; the Asm semantics bridges this, but assembly, linking, and loading are trusted [1]. CakeML closes more of the gap with verified instruction encoding but still abstracts above caches, TLBs, and memory-mapped I/O [2].

3. **Resources.** Stack overflow, heap exhaustion, and GC pauses are the classic resource gaps. CompCert's nominal-memory-model extension threads explicit stack-space requirements through the theorem [7]; CakeML models resource-limit exits explicitly and offers a verified cost semantics for space [6]. Execution time and timing side channels remain outside every surveyed theorem.

4. **The environment.** System calls, foreign functions, interrupts, and concurrent threads are modeled to varying degrees. CakeML's interference-aware theorem is the state of the art [2]; CompCert's concurrent extension must reformulate the simulation framework because the determinism hypothesis — the linchpin of the forward-to-backward flip — fails for multithreaded semantics [7].

5. **The toolchain below the theorem.** Assemblers, linkers, loaders, operating systems, and hardware are trusted; even CakeML trusts its ISA models to describe the silicon faithfully. The *de Bruijn criterion* applies: we trust the proof checker's kernel, and everything else must be argued, not assumed.

> **Theorem (informal synthesis):** No existing verified compiler closes all five strata simultaneously. CompCert closes strata 1–2 for its defined fragment modulo assembler trust; CakeML additionally closes instruction encoding and models interference and resource exits; translation validation closes none in general but certifies arbitrary optimizations per run. The residual trusted base — assembler, linker, OS, hardware, and the proof assistant kernel — is irreducible without extending verification downward.

##5 Empirical/Proofs

The empirical content of verified compilation is measured in proof artifacts, not benchmarks. CompCert's development is on the order of one hundred thousand lines of Coq — the proof dominating the compiler — representing multiple person-decades, and it compiles real avionics-grade C used in safety-critical embedded software [1]. The CakeML development is of comparable scale in HOL4 and uniquely demonstrates *proof-producing bootstrapping*: the verified CakeML compiler is applied to its own source inside the logic to produce verified machine code, so the resulting binary's correctness is itself a theorem [2] — the closest the field has come to Thompson's trusting-trust challenge.

Case studies sharpen the picture. The **nominal memory model** work re-engineers CompCert's memory injections around explicit stack-space oracles, yielding a final theorem parameterized by per-function stack requirements extracted from the generated assembly [7]. The **space-cost semantics** for CakeML proves that a source-level cost model soundly predicts heap and stack consumption of compiled code *including the garbage collector and bignum library*, enabling the first verified space bounds for programs with unbounded allocation [6].

Translation validation's empirical record is complementary: validators for LLVM-level optimizations routinely catch real miscompilations in production compilers, showing per-run certification finds bugs testing misses [3]. The two cover different risks: verified compilers eliminate *systematic* unsoundness in the translation scheme; validators catch *instance-level* bugs in heuristic optimizers.

##6 Limitations

Honesty about what the theorems do *not* say is as important as the theorems themselves.

- **Undefined behavior voids the warranty.** A C program with a single buffer overflow is outside CompCert's theorem; the compiled code may do anything [1]. Verified compilation is therefore *parasitic* on source-level verification of definedness — it amplifies source guarantees but cannot create them.
- **Determinism is assumed, not proved, at the boundary.** The forward-to-backward flip requires deterministic target semantics [1]. Real hardware is not deterministic, so the theorem applies to an *idealized* target; the distance between the idealized Asm semantics and the silicon is trusted, not verified.
- **Concurrency breaks the framework.** The standard simulation setup assumes sequential, deterministic execution. Extending CompCert to multithreaded C requires reformulating the proof architecture around nondeterministic semantics, a research problem addressed only partially [7].
- **Performance and timing are out of scope.** No surveyed theorem says anything about execution time, timing side channels, or energy consumption. A verified compiler may legally produce arbitrarily slow code.
- **The trusted computing base is non-trivial.** It includes the proof assistant's kernel and elaborator, the formal semantics' fidelity to the language standard, the assembler/linker/loader, the operating system, the ISA model's fidelity to silicon, and — for translation validation — the validator's decision procedures [3]. Each is a residual assumption, not a proved fact.
- **Proof brittleness and evolution.** Verified compilers are hard to extend: adding an optimization pass requires a new simulation proof, and changes to intermediate-language semantics can invalidate large proof libraries. This is a genuine engineering cost that explains why CompCert optimizes lightly.

##7 Conclusion

Verified compilation has crossed from research prototype to engineering reality. CompCert demonstrates that a realistic C compiler backend can carry a machine-checked, end-to-end behavioral-preservation proof [1]; CakeML demonstrates that the proof can reach concrete machine code on commercial ISAs while modeling interference and resource limits [2]; translation validation tames optimizations too heuristic to verify directly [3]; and recent extensions carry quantitative properties like stack and heap usage through the simulation framework [6][7].

The semantic gap is narrower than it has ever been, but it is not closed. Undefined behavior, concurrency, timing, and the toolchain below the theorem remain regions where trust replaces proof. The research frontier is therefore clear: compositional, quantitative, concurrency-aware simulation frameworks; verified assemblers and linkers that push the trust boundary down to the ISA model; and cost semantics that make resource consumption a first-class verified property. Until then, the correct reading of a compiler correctness theorem is not "this compiler cannot be wrong" but the more precise and more useful: *for defined source programs, every observable behavior of the compiled code is a behavior the source program already had* — and we know this with the certainty of machine-checked proof.
