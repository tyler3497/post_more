# The Store Model and Its Discontents: Functional Package Management, Full-Source Bootstrapping, and Attested Provenance as Foundations of Reproducible Builds

## Abstract

Reproducible builds — the guarantee that a given source tree, built in a defined environment, always produces bit-identical artifacts — have evolved from an idealistic goal of the reproducible-builds.org project into an architectural prerequisite for trustworthy software supply chains. This thesis argues that reproducibility cannot be bolted onto conventional package managers after the fact: it must emerge from the *store model*, in which every build artifact is a pure function of its inputs, keyed by cryptographic hash, as pioneered by Nix and GNU Guix. We formalize the Nix store as a content-addressed derivation algebra, analyze fixed-output derivations as the principled boundary between deterministic and network-dependent computation, and develop a taxonomy of toolchain nondeterminism — timestamps, file ordering, address-space layout randomization, and unseeded randomness — together with its mitigations, most notably `SOURCE_DATE_EPOCH`. We then address the deeper epistemic problem reproducibility alone cannot solve: the *trusting trust* attack, in which the compiler itself is compromised. Here we survey bootstrappable builds — the Stage0/M2-Planet/Mes chain culminating in Guix's full-source bootstrap rooted in a 357-byte auditable seed — and examine complementary verification mechanisms: SLSA provenance, binary transparency via Sigstore/Rekor, and Guix's in-band authentication of its own git history. Empirical analysis of contemporary rebuild campaigns shows reproducibility rates above 95% for mature distributions, with residual failures dominated by the identified taxonomy. We conclude that the store model plus bootstrapping plus attestation constitutes a coherent, layered defense against supply-chain compromise, and identify open problems in content-addressed derivation outputs and hardware-rooted provenance.

## 1 Introduction

In 1984, Ken Thompson delivered his Turing Award lecture, *"Reflections on Trusting Trust,"* demonstrating that a compromised compiler can inject undetectable backdoors into every program it compiles — including future versions of itself — in a way that no amount of source-code review can detect [1]. For four decades, the entire edifice of open-source security rested on the tacit assumption that the compiler binary was trustworthy. The reproducible-builds movement, the functional package managers Nix and Guix, and the recent supply-chain security frameworks (SLSA, Sigstore) can be read as three successive attempts to discharge that assumption: first by making builds *deterministic*, then by making toolchains *bootstrap from auditable seeds*, and finally by making build provenance *publicly verifiable*.

Reproducibility is defined operationally: a build is reproducible if rebuilding the same source with the same toolchain in the same environment yields bit-for-bit identical output. Bit-identity matters because it converts the question "was this binary built from this source?" from a trust judgment into a *computable check*. Any independent party can rebuild and compare hashes; disagreement between the published artifact and an independent rebuild is constructive proof of tampering or nondeterminism.

Yet reproducibility is fragile. Compilers embed timestamps (`__DATE__`, `__TIME__`), archive tools iterate directory entries in filesystem order, linkers record build paths, and hash tables iterate in randomized order (deliberately, as a defense against algorithmic-complexity attacks). Each of these introduces entropy into the output. The reproducible-builds.org project catalogued these failure modes and developed mitigations, of which `SOURCE_DATE_EPOCH` — an environment variable fixing the canonical build time — is the most widely adopted [2].

This thesis makes three contributions. First, we formalize the *store model* of Nix and GNU Guix, showing that content-hash-keyed store paths convert reproducibility from a per-package property into a *compositional invariant* of the whole distribution. Second, we give a unified treatment of bootstrappable builds — from Stage0's hex0 through M2-Planet and GNU Mes to Guix's full-source bootstrap — as an answer to Thompson's attack. Third, we situate reproducibility within the broader attestation landscape: SLSA provenance, binary transparency, and Guix's git authentication, arguing that reproducibility *plus* provenance closes the loop that either alone leaves open.

## 2 Background

### 2.1 The trusting trust attack

Thompson's attack proceeds in two stages. First, a modified C compiler recognizes when it is compiling the login program and injects a backdoor (e.g., a universal password). Second, the same compiler recognizes when it is compiling the C compiler itself and injects both the login backdoor and the self-replicating compiler backdoor into the new compiler binary. Once the original tainted source is discarded, *no inspection of any source in the system can reveal the attack*, because every compiler binary in existence carries the payload [1]. David A. Wheeler's *diverse double-compiling* (DDC) proposed a countermeasure: compile the compiler source with a second, trusted compiler, then use the result to recompile the original; if the output matches the original binary, no self-replicating payload exists. DDC reduces trust in the compiler to trust in a *second* compiler — bootstrappable builds push this reduction to its limit by shrinking the trusted seed to hundreds of bytes.

### 2.2 The reproducible-builds project

The reproducible-builds.org effort, active since roughly 2013, defines the goal and the methodology: build twice, in deliberately *varied* environments (different paths, times, locales, timezones, user names), and require byte-identical outputs [3]. The project's `diffoscope` tool produces human-readable diffs of binary artifacts, enabling root-cause analysis of nondeterminism. Debian's rebuild infrastructure tracks the fraction of packages that reproduce; at maturity, this exceeded 95%, with the long tail dominated by a small taxonomy of recurring defects [3].

### 2.3 Functional package management

Nix, created by Eelco Dolstra in his 2006 PhD thesis *"The Purely Functional Software Deployment Model,"* treats package builds as pure functions: given identical inputs, the output is identical, and the output's identity is *derived from* the inputs' identities [4]. GNU Guix, launched in 2012, reimplements the model in GNU Guile Scheme with stronger commitments to bootstrappability and user freedom [5]. Both systems store every build product in a *store* (`/nix/store` or `/gnu/store`) under a path of the form `<hash>-<name>-<version>`, where the hash is computed over the complete derivation — builder, arguments, environment, and the hashes of all input store paths [4].

## 3 Methodology

Our method is analytic and constructive rather than experimental: we formalize the store model, classify nondeterminism sources against published toolchain documentation and the reproducible-builds.org issue tracker, reconstruct the bootstrap chain from primary sources (the Guix manual, FOSDEM proceedings, and the GNU Mes literature), and evaluate attestation frameworks against explicit threat models.

> **Theorem (Compositional reproducibility):** In the store model, if every derivation's build function is deterministic with respect to its declared inputs, then every store path is reproducible, and reproducibility is preserved under composition (derivation DAG closure).

*Proof sketch.* Each store path's hash commits to its full input closure transitively. A deterministic build function maps the same input closure to the same bytes; hence any two builds of the same derivation yield the same store path and identical contents. Since derivations reference only store paths, composition preserves the property. ∎

The proof's premise — determinism of each build function — is precisely what the toolchain taxonomy of Section 4.3 must secure, and the base case — trust in the seed inputs — is what Section 4.4 must discharge.

We validate factual claims about specific tools and timelines through web search against primary sources (project manuals, conference archives, and the packages' own documentation), cited inline throughout.

## 4 Deep Dive

### 4.1 The store as a content-keyed derivation algebra

In Nix, a *derivation* (`.drv` file) is a persistent, machine-readable specification of a build: the builder executable, its arguments, environment variables, and the set of input store paths it may read [4]. The daemon executes the builder in a sandbox that *prohibits network access and forbids writes outside the designated output path*; the only files visible are the declared inputs. The output path is computed *before* the build as:

```
storePath = /nix/store/<sha256(derivation) truncated to 160 bits, base32>-<name>
```

This is *input-addressing*: the address commits to the recipe, not the result. Nix additionally supports *content-addressed* derivations (experimental in recent releases), where the output path is the hash of the output itself — the fixed point of the store algebra.

Four consequences follow, each load-bearing for reproducibility:

1. **Memoization.** If the output path already exists in the store (or in a binary cache — a substituter serving store paths over HTTP), the build is skipped entirely. The store is a memo table for a pure function [4].
2. **Coexistence.** `/nix/store/a9xn0gx…-glibc-2.37/` and `/nix/store/b2ym1p…-glibc-2.35/` coexist without conflict, eliminating dependency hell; different compiler flags produce different hashes, hence different paths [4].
3. **Atomicity and rollback.** User environments are generations of symlinks into the store; switching generations is a symlink swap — atomic and instantly reversible [4].
4. **Garbage collection.** Unreferenced store paths are unreachable nodes in the reference DAG and are collected by tracing GC from GC roots [4].

The hash also encodes the *platform*, so cross-compilation variants do not collide [4]. Crucially, because the derivation hash commits to the entire input closure, any change anywhere in the dependency graph — a compiler flag, a library patch, an environment variable — yields a different output path rather than silently overwriting a shared location. Reproducibility becomes *structural*: it is impossible, by construction, for two different input closures to share an output path.

```nix
# A minimal derivation: the store path commits to builder, args, and inputs
derivation {
  name = "hello-2.12";
  system = "x86_64-linux";
  builder = ./builder.sh;              # part of the hash
  args = [ ./builder.sh ];
  src = ./hello-2.12.tar.gz;           # fixed-output derivation, hash-pinned
  stdenv = ./stdenv;                   # input store path, hash-committed
  # output: /nix/store/<sha256 of all of the above>-hello-2.12
}
```

### 4.2 Fixed-output derivations: the network boundary

Pure functions cannot fetch from the network — yet real builds begin by downloading sources. Nix resolves this with *fixed-output derivations* (FODs): a derivation may declare `outputHash`, `outputHashAlgo`, and `outputHashMode`, asserting the expected hash of its output in advance [4]. The daemon then performs the fetch through a privileged path and *verifies* that the produced output hashes to the declared value.

FODs are the membrane between the deterministic interior and the nondeterministic exterior. Changing a URL in a `fetchurl` call does not change the derivation hash (the hash commits to the *expected output hash*, not the URL), preventing spurious rebuilds of the world; but a hash mismatch is a hard build failure, so source substitution attacks are detected at fetch time [4]. This design is what makes it feasible to have `nixpkgs` — tens of thousands of packages — pin every upstream tarball by hash while keeping the derivation graph stable.

> **Theorem (FOD integrity):** Under collision resistance of the output hash function, a fixed-output derivation's store path contains exactly the content the package author pinned, regardless of what the network served.

The theorem's assumption is doing real work: Nix migrated from SHA-1 to SHA-256-family hashes for store addressing precisely because collision resistance is a security property here, not merely a checksum.

```bash
# Querying the derivation DAG: every dependency is a hash-committed store path
$ nix-store -q --tree $(nix-store -qd $(which firefox))
# /nix/store/<drv-hash>-firefox-1.0.1.drv
#   +-- /nix/store/<drv-hash>-glibc-2.37.drv
#   +-- /nix/store/<drv-hash>-openssl-3.0.8.drv ...
```

### 4.3 A taxonomy of toolchain nondeterminism

Even with the store model securing *composition*, each individual build function must be deterministic. The reproducible-builds.org project identified the recurring offenders [3]; we organize them below with mitigations.

| # | Nondeterminism source | Mechanism | Canonical mitigation |
|---|---|---|---|
| 1 | **Timestamps** | `__DATE__`/`__TIME__` macros, archive mtimes, ELF notes, `.pyc` headers, image layer config | `SOURCE_DATE_EPOCH`: tools read the canonical epoch from the environment instead of the wall clock [2] |
| 2 | **File ordering** | `readdir()` order in `tar`/`zip`, glob expansion, `ld` archive member order | Sort inputs (`LC_ALL=C sort`), `--sort-name` in GNU tar, deterministic link order |
| 3 | **Absolute paths** | `__FILE__`, DWARF `DW_AT_comp_dir`, RPATH, debug prefix maps | `-ffile-prefix-map`, `--remap-path-prefix`, `-fdebug-prefix-map` |
| 4 | **Build IDs / UUIDs** | Random or ambient-entropy-derived ELF build IDs and GUIDs | `--build-id=none` or deterministic `--build-id=sha1` over normalized inputs |
| 5 | **ASLR / hash randomization** | Hash-seed randomization affecting `dict`/`set` iteration order in code generators; address-embedded outputs | `PYTHONHASHSEED=0`, fixed seeds, GCC `--frandom-seed` |
| 6 | **Parallelism** | `make -j` interleaving log or artifact order; thread-pool scheduling in codegen | Serialize the nondeterministic phase or sort its outputs |
| 7 | **Locale & timezone** | `sort` collation, date formatting in generated docs | `LC_ALL=C`, `TZ=UTC` |
| 8 | **Uninitialized memory / padding** | Struct padding bytes, uninitialized buffers embedded in outputs | `-ftrivial-auto-var-init=zero`, explicit zeroing |

`SOURCE_DATE_EPOCH`, specified by reproducible-builds.org, deserves emphasis: it is an environment variable containing seconds since the Unix epoch, conventionally set to the last-modification time of the source tree (e.g., `git log -1 --format=%ct`), which build tools consult *instead of* the current time when embedding timestamps [2]. Its power lies in being a *coordination point*: rather than patching every tool's timestamp behavior idiosyncratically, the ecosystem converges on one variable, and compliance becomes checkable. Modern build systems — dpkg, GCC (via `-Wdate-time` warnings), Python's archive handling, Go's `-trimpath` builds — honor it [2][3].

```bash
# The canonical reproducible-build invocation pattern
export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
export LC_ALL=C TZ=UTC PYTHONHASHSEED=0 CARGO_INCREMENTAL=0
./configure --prefix=/usr && make -j"$(nproc)" && make install
```

ASLR merits a clarifying note: address-space layout randomization does not usually affect build *outputs* directly, but it interacts with reproducibility through (a) hash tables seeded from addresses, (b) profile-guided optimization whose profiles embed addresses, and (c) build tools that record pointer-derived values. The mitigation is the same in spirit as elsewhere: replace ambient entropy with declared, fixed inputs [3].

### 4.4 Bootstrappable builds: answering Thompson

Reproducibility verifies that a binary matches its source — but Thompson's attack lives *below* that check, in the compiler that both the original and the rebuild use. If the seed compiler is tainted, every rebuild faithfully reproduces the taint. The answer is *bootstrappable builds*: shrinking the trusted binary seed until it is small enough to audit by hand, then growing a full toolchain from source atop it.

The state of the art is the chain developed by the Stage0, M2-Planet, and GNU Mes projects and integrated into GNU Guix as the **full-source bootstrap** [5][6]:

1. **hex0-seed (357 bytes).** The seed is a tiny binary whose *source* is `hex0_x86.hex0`, an ASCII file of hexadecimal digits with comments. Hex0 is self-hosting: feeding the hex0 source to the hex0 binary reproduces the binary. Because the binary is the byte-for-byte ASCII decoding of its own source, the 357-byte blob can be "blessed as source" — auditing it is equivalent to reading a few dozen lines of hex [5].
2. **Stage0 / MesCC-Tools.** hex0 builds hex1, then M0 (a macro assembler), then M1, then the C compiler `cc_x86` — each stage written in the language of the previous, each auditable, climbing from hex to a minimal C [6].
3. **M2-Planet.** A more capable C compiler written in that minimal C, able to compile larger programs [6].
4. **GNU Mes.** A Scheme interpreter and C compiler written in Scheme/C, built by M2-Planet. Mes then compiles **TinyCC**, which compiles an old **GCC (2.95.3)**, which climbs the GCC version ladder to a modern compiler [5][6].
5. **The GNU system.** From the bootstrapped GCC: Binutils, glibc, Coreutils, and eventually the entire distribution — every binary traceable to the 357-byte seed plus reviewed source [5].

The Guix manual is explicit about the threat model: the traditional bootstrap binaries (shell, Coreutils, Awk, GCC, glibc, …) totaled roughly **250 MB** of unauditable binary — "taken for granted" as trustworthy [5]. The full-source bootstrap replaces them with the seed chain above, merged into Guix's mainline for `i686-linux`/`x86_64-linux` [5][7]. FOSDEM 2021 marked the milestone where the binary seeds for MesCC-Tools and GNU Mes themselves were eliminated in favor of Stage0 and M2-Planet [7].

This is diverse double-compiling taken to its logical conclusion: instead of trusting *a* compiler, you trust 357 bytes plus the entire auditable source chain. Residual trust concentrates in the hardware and the seed — a vastly smaller attack surface than 250 MB of binaries.

### 4.5 Provenance, transparency, and authentication: closing the loop

Reproducibility answers "does this binary match this source?"; it does not answer "who built it, from which commit, on what infrastructure?" — and a reproducible build of *attacker-controlled source* is faithfully malicious. Three mechanisms close this gap:

**SLSA provenance.** The SLSA framework (Supply-chain Levels for Software Artifacts) defines provenance attestations: signed metadata binding an artifact to its source repository, commit, build configuration, and builder identity [8]. At SLSA Build Level 3+, builds run on hardened, ephemeral, hermetic infrastructure with non-falsifiable provenance; verifiers (e.g., `slsa-verifier`) check the attestation before trusting the artifact [8]. Provenance complements reproducibility: provenance says *where it came from*; reproducibility lets *anyone* check the claim independently.

**Binary transparency.** Borrowed from Certificate Transparency, binary transparency appends artifact hashes to an append-only, publicly auditable log (Sigstore's Rekor is the leading implementation), with monitors and witnesses gossiping to detect equivocation — serving different binaries to different users [9]. Keyless signing via Fulcio (OIDC-bound short-lived certificates) removes long-term key management, and `cosign verify` checks signatures against the transparency log [9]. Transparency converts targeted attacks into globally visible events.

**Guix authentication.** Guix authenticates its *own source*: `guix pull` verifies that every commit in the channel's git history is signed by an authorized key listed in the `.guix-authorizations` file of its parent commits — in-band, bootstrapped from a pinned introductory commit [5]. This defeats history-rewriting and unauthorized-push attacks without a centralized PKI, and it means the package definitions feeding the store model are themselves tamper-evident.

Together: the store model makes builds compositional and deterministic; bootstrapping minimizes the trusted seed; SLSA provenance records the build's pedigree; transparency makes substitution detectable; git authentication secures the definitions. No single layer suffices — defense in depth is the point.

## 5 Empirical Results

We synthesize published rebuild data rather than running a new campaign (the distributions' CI already does this continuously):

- **Debian / reproducible-builds.org:** at maturity, over 95% of Debian packages in the archive reproduced bit-for-bit under the project's adversarial rebuild harness (varied time, path, locale, timezone, UID) [3]. Residual failures clustered in the taxonomy of Section 4.3, with timestamps and file ordering dominant — precisely the classes `SOURCE_DATE_EPOCH` and input sorting address.
- **Guix:** `guix challenge` compares locally built store items against substitute servers; the distribution's CI rebuilds the package graph continuously, and the content-hash addressing means any divergence is immediately visible as a hash mismatch rather than a silent behavioral difference [5].
- **NixOS / Hydra:** the binary cache model means most users never build at all — they download store paths whose hashes commit to their derivations; trust in the cache is trust in the hash, checkable by local rebuild [4].
- **Industry adoption of provenance:** SLSA provenance generation is now built into major CI systems (e.g., GitHub Actions' build-provenance attestation), and Sigstore/Rekor logging is increasingly default for release artifacts, indicating convergence on the attestation layer [8][9].

A notable pattern: each layer's adoption *reduces the cost* of the next. Deterministic toolchains (layer 1) make rebuild-based verification cheap; cheap verification makes transparency logs meaningful (there is something checkable to log); meaningful logs make provenance worth signing.

## 6 Limitations

1. **Reproducibility ≠ correctness or safety.** A bit-identical binary built from backdoored source is faithfully backdoored. Reproducibility detects *build-time* substitution, not *source-time* malice; it must be paired with source review and authentication (Section 4.5).
2. **The hardware and seed floor.** The full-source bootstrap bottoms out at the 357-byte hex0-seed and the CPU it runs on. Microcode, firmware, and hardware Trojans remain outside the model — Thompson's attack applied to silicon is unaddressed.
3. **Non-determinism by design.** Some outputs are *intended* to vary: cryptographic keys generated at install time, UUIDs, profile-guided optimization data from production traffic. These must be carefully excluded from the reproducibility claim rather than forced deterministic.
4. **Content-addressed outputs are incomplete.** Nix's content-addressed derivations remain experimental; input-addressing means a *different but equivalent* build (e.g., a benign toolchain upgrade producing identical binaries) still changes every downstream path, causing mass rebuilds. True content addressing would deduplicate these, at the cost of a harder trust story for the build farm.
5. **Ecosystem coverage.** Reproducibility is a property of the *whole closure*. One nondeterministic leaf (a code generator embedding `time.Now()`) poisons every derivation above it. Achieving >95% required years of per-package fixes across Debian; long-tail ecosystems (npm, PyPI) remain far behind.
6. **Provenance is only as strong as the builder.** SLSA Level 3 requires hardened builders; a compromised CI runner can emit valid-looking provenance for tainted builds. Transparency detects equivocation but not a uniformly malicious builder — independent rebuilders remain essential.

## 7 Conclusion

This thesis has argued that reproducible builds are not a feature to be added to package managers but an *architectural consequence* of the store model: when every artifact's address commits to its complete input closure, and builders run sandboxed with only declared inputs, determinism composes and verification reduces to hash comparison. Fixed-output derivations extend the model across the network boundary without breaking its invariants. The residual nondeterminism of real toolchains — timestamps, ordering, paths, build IDs, hash randomization, parallelism, locale — yields to a small, standardizable set of mitigations anchored by `SOURCE_DATE_EPOCH`. Beneath all of this, bootstrappable builds answer Thompson: Guix's full-source bootstrap grows a modern toolchain from a 357-byte auditable seed through Stage0, M2-Planet, and GNU Mes, replacing 250 MB of trusted binaries with reviewed source. And above it, SLSA provenance, binary transparency, and in-band git authentication bind artifacts to their pedigree and make substitution publicly visible.

The open problems are now precise rather than philosophical: completing content-addressed derivation outputs, extending the bootstrap to new architectures, hardening builders to SLSA's higher levels, and — hardest — bringing long-tail language ecosystems up to the reproducibility bar the distributions have demonstrated is achievable. The store model gave us the mathematics of trust; the remaining work is engineering.
