# Formalizing Unsafe Rust: Stacked Borrows, Tree Borrows, and the Operational Semantics of Aliasing Discipline

## Abstract

Rust's ownership type system enforces a strict aliasing discipline, yet the language's *zero-cost* promise hinges on a question the type system alone cannot answer: what may the compiler assume when unsafe code is in play? This thesis formalizes Rust's aliasing discipline as an *operational semantics*. We reconstruct Stacked Borrows, the borrow-stack aliasing model of Jung et al. [1] — tagged pointers validated against a per-location stack, violations classified as undefined behavior — and its successor Tree Borrows [2], which replaces the stack with a permission tree (*Reserved*, *Active*, *Frozen*, *Disabled*), trading restrictiveness for compatibility with idiomatic systems code. Drawing on the Unsafe Code Guidelines [3], the MiniRust formal semantics [5], and Miri, the reference interpreter that executes candidate semantics as dynamic checks [6], we examine how experimental semantics function as executable specifications. We then derive implications for unsafe-code verification: once aliasing is an operational model, it becomes a correctness criterion against which both programs and compiler optimizations can be proved sound, extending the Iris/RustBelt program [7] across the unsafe boundary.

## 1 Introduction

Memory safety without garbage collection is Rust's defining achievement, and its enforcement mechanism — ownership, borrowing, lifetimes — is arguably the most widely deployed linear-ish type system in history. The borrow checker guarantees that every *safe* Rust program obeys a rigid aliasing discipline: at any program point, either there is exactly one live mutable reference to a location, or any number of shared references. Compilers dream of such discipline, because aliasing information is the principal enabler of the most valuable optimizations: reordering loads and stores, eliminating redundant reads, hoisting loop-invariant accesses, and exploiting LLVM's `noalias` and `dereferenceable` attributes.

There is a catch. Rust also has `unsafe`, and unsafe code may fabricate raw pointers, transmute representations, and call foreign functions — bypassing every syntactic check the borrow checker performs. The Rust compiler nevertheless optimizes unsafe code aggressively, *assuming* the aliasing discipline holds even where no checker verified it. This is sound only if the unsafe-code author and the compiler agree on a precise contract: a set of rules such that, *if unsafe code follows the rules, the compiler's optimizations preserve its meaning*. Without a formal contract, every such assumption is a bug waiting to be filed: either the compiler miscompiles correct code, or authors cannot know what "correct" means.

This thesis formalizes that contract. Its central claim is that Rust's aliasing discipline is best understood not as a type-system artifact but as an **operational semantics of memory access** — a dynamic model, in the spirit of Stacked Borrows and Tree Borrows, that assigns a meaning to every pointer operation and declares violations to be undefined behavior. Operational semantics here play a role borrowed from the semantic turn in C standardization debates: the model is the *definition* of the contract, and everything else — compiler passes, verification tools, style guides — is evaluated against it. We reconstruct the two leading candidate models, situate them within the Unsafe Code Guidelines process, examine Miri as an *executable semantics*, and extract consequences for unsafe-code verification.

## 2 Background

To formalize Rust's aliasing discipline we need three ingredients: a notion of *pointer provenance*, a vocabulary for *undefined behavior*, and the methodological stance of the Unsafe Code Guidelines.

**Provenance.** In modern C semantics, a pointer is not merely an address: it carries *provenance*, the allocation (and derivation history) from which it was created, and dereferencing a pointer with the wrong provenance is undefined behavior even if the address is right [4]. Rust inherits and sharpens this idea. In Stacked Borrows and Tree Borrows, every pointer value at runtime is a pair *(address, tag/provenance)*, and the abstract machine tracks, per allocation, the permissions associated with each tag. A raw pointer cast from an integer cannot legally access memory even when the address coincides — provenance, not the address alone, determines legality.

**Undefined behavior as a contract device.** In this thesis we treat undefined behavior not as a hazard but as the *instrument of specification*. When a model declares a program to have undefined behavior, it declares that the compiler owes that program nothing — the set of well-defined programs is exactly the set for which the compiler's assumptions must hold. The art of aliasing-model design is therefore a balancing act: rule out *enough* programs to justify the desired optimizations, while permitting *as many* real-world unsafe programs as possible.

**The Unsafe Code Guidelines.** The UCG is the Rust project's forum — primarily the opsem team — for resolving what unsafe code may and may not do [3]. Its output is not a static document but a process: open questions tracked as issues, consensus recorded in t-opsem final-comment-period decisions and the Language Reference, and candidate semantics prototyped in Miri and MiniRust. Two UCG commitments shape everything below. First, *semantics before syntax*: the question is what the abstract machine does, not what the borrow checker accepts. Second, *experiment before commitment*: a candidate model must be implemented in an interpreter and validated against the ecosystem before hardening into a specification.

**MiniRust and Miri.** MiniRust [5] is a formal, small-step operational semantics for a core fragment of MIR (Rust's mid-level IR), mechanized with the aliasing model as a pluggable memory component. Miri [6] is the reference interpreter for MIR; it implements candidate aliasing models as dynamic instrumentation and has become the ecosystem's de facto oracle for "does this unsafe code violate the current best understanding of the rules?" Together they close the loop between paper semantics and running code.

## 3 Methodology

Our method is *model reconstruction with comparative evaluation*. We treat Stacked Borrows and Tree Borrows as successive approximations to a single unknown — the eventual, stabilized aliasing contract of Rust — and evaluate each along four axes:

1. **Mechanism.** How does the abstract machine track permissions? What is the state per allocation, what events mutate it, and what constitutes a violation?
2. **Expressiveness.** Which idioms of real unsafe code does the model accept or reject? Where do the two models disagree, and why?
3. **Optimization power.** Which compiler transformations does the model justify? We pay special attention to transformations the Rust/LLVM pipeline already performs, since any viable model must validate the status quo.
4. **Verification utility.** Can the model serve as a foundation for proving unsafe code correct — both deductively (in a program logic) and dynamically (in an interpreter)?

Our evidence base: the Stacked Borrows paper (POPL 2020) [1] with its Coq mechanization; the Tree Borrows paper (PLDI 2025) [2] with its Rocq mechanization and Simuliris logic; the Miri implementation and ecosystem studies [6, 8]; the MiniRust specification [5]; and the UCG record [3]. We restate the core transition rules in simplified form and the central theorems as blockquote claims, grounding the comparison in concrete examples where the models diverge.

## 4 Deep Dive

### 4.1 Stacked Borrows: the borrow stack

Stacked Borrows [1] associates with every memory location a *borrow stack*: a sequence of items, each item a pair *(tag, permission)* where the permission is one of `Unique` (mutable borrow), `SharedReadOnly` (shared borrow), or `SharedReadWrite` (shared borrow of interior-mutable data). Creating a reference performs a **retag**: a fresh tag is generated and pushed onto the stack, with all items below it representing borrows the new reference was derived from. Every memory access is then validated against the stack:

- A *read* through tag *t* requires *t* to be present in the stack; items above *t* that are `Unique` are popped (the read "invalidates" conflicting mutable borrows above it).
- A *write* through tag *t* requires *t* to be present; all items above *t* are popped regardless of permission.

Any access through a tag not on the stack — i.e., a tag that has been popped — is undefined behavior.

The intuition is a runtime analogue of the borrow checker's region discipline: the stack order encodes *derivation*, and accesses enforce a last-in-first-out validity regime. Consider the canonical example:

```rust
let mut x = 0i32;
let xraw = &mut x as *mut i32;      // retag: push Unique tag U1
let xref = unsafe { &mut *xraw };   // retag: push Unique tag U2 (child of U1)
*xref = 1;                          // write via U2: stack [.., U1, U2]
*xraw = 2;                          // write via U1: pops U2; stack [.., U1]
*xref = 3;                          // ERROR: U2 no longer on the stack → UB
```

The final write is undefined behavior, mirroring the borrow checker's rejection of the analogous safe program. The model also governs *function calls*: when a reference is passed to a function, a **protector** forbids the callee from invalidating the caller's borrow for the call's duration — what makes optimizations across unknown code sound.

> **Theorem (Stacked Borrows optimization soundness, Jung et al. [1]):** Under the Stacked Borrows semantics, a compiler may, using only intraprocedural reasoning, (a) move reads through `&mut` references across function calls and unknown code, and (b) eliminate redundant reads, without changing the observable behavior of any well-defined program. The proof is mechanized in Coq.

The theorem is architectural: the model is *strong enough* to justify real optimizations. Its empirical companion: Stacked Borrows, implemented in Miri and run over large parts of the standard library test suite, accepts the overwhelming majority of real-world unsafe code [1].

But Stacked Borrows has a documented blind spot: it is too strict for certain widespread, arguably legitimate patterns. The famous case is *reborrowing through a raw pointer stored in a struct field* — e.g., a `&Header` used to access dynamically-sized trailing data, a pattern the `uefi-rs` guidelines explicitly note is "rejected by the Stacked Borrows model, but allowed by Tree Borrows" [3]. The stack discipline conflates *derivation order* with *permission*, and real code derives pointers in orders the LIFO discipline cannot accommodate.

### 4.2 Tree Borrows: permissions as a tree

Tree Borrows [2] (Villani, Hostert, Dreyer, Jung; PLDI 2025) keeps the core ideas — provenance, retagging, protectors, UB on violation — but replaces the stack with a **tree** of permissions per allocation, and replaces the three stack permissions with a richer state machine. Each node in the tree corresponds to a pointer; children are pointers derived from their parent. Node states:

| State | Meaning |
|---|---|
| `Reserved` | A mutable borrow not yet written through (models two-phase borrows) |
| `Active` | A mutable borrow that has been written through; grants exclusive access |
| `Frozen` | A shared borrow; grants read access, invalidated by foreign writes |
| `Disabled` | Dead: any access is UB |

The key innovation is *relativity*: whether an access invalidates a node depends on whether the accessor is **foreign** or a **child** relative to that node. A child write through a mutable borrow transitions a `Reserved` parent to `Active`; a *foreign* write (from an unrelated branch) disables it. Reads are similarly distinguished: a foreign read downgrades `Active` to `Frozen` (the borrow is no longer exclusive but remains readable), while child reads are harmless.

This relativity admits the patterns Stacked Borrows rejected: validity flows along derivation *paths* rather than a global stack order, so a pointer stored in a struct field and later reborrowed stays usable absent *foreign* conflicting accesses. The tree records *who derived from whom* — a strictly more faithful model of aliasing, which is fundamentally a relation between pointers, not a timeline.

Tree Borrows also fixes a subtle optimization gap in Stacked Borrows. Under Stacked Borrows, *reordering adjacent reads* cannot be shown sound — a surprising weakness. Tree Borrows' state machine, by distinguishing foreign from child accesses, supports the proof that adjacent-read reordering is sound [2]. The tradeoff: Tree Borrows is *weaker* in one dimension. A mutable reference is considered writable only after it has actually been written through (`Reserved` → `Active` on first child write), so optimizations that *introduce* a write where none existed — e.g., collapsing a conditional increment loop into an unconditional `*x = *x + n` — are not justified under Tree Borrows, whereas Stacked Borrows permitted them [2]. This is not an oversight but the price of ecosystem compatibility: current work explores a "strong mode" for Tree Borrows that recovers such optimizations at the cost of rejecting more code.

> **Theorem (Tree Borrows optimization soundness, Villani et al. [2]):** Almost all optimizations proven sound under Stacked Borrows remain sound under Tree Borrows, with the exception of transformations that insert writes before the first write of the original program. Additionally, reordering of adjacent reads — unsound under Stacked Borrows — is sound under Tree Borrows. The proof is mechanized in Rocq using the Simuliris relational program logic.

The empirical headline of the Tree Borrows paper is striking: evaluated in Miri over the test suites of the 30,000 most-downloaded crates, **Tree Borrows rejects 54% fewer test cases than Stacked Borrows** [2]. An independent large-scale study of UB across foreign-function boundaries likewise found Tree Borrows "significantly more permissive" than Stacked Borrows on real library code [8].

### 4.3 Protectors: interprocedural reasoning from a local model

Both models face the same fundamental problem: how can *intraprocedural* reasoning justify optimizations across *unknown* code (function calls, whose bodies the optimizer cannot see)? The answer is **protectors**, and they deserve attention because they are the device that turns a dynamic model into an optimization license.

When a reference is passed as a function argument, the model installs a protector on the corresponding node: for the duration of the call, any access that would invalidate the protected node is UB — *even if* the callee obtained the pointer through some other channel. The caller is thus entitled to assume its borrow survives the call, and the optimizer may hoist reads across the call site. Protectors expire when the call returns (their protection is scoped to the dynamic extent of the call), so the callee's own derived borrows remain governed by the ordinary rules.

Formally, protectors convert a *whole-program* property into a *modular* one — the operational analogue of the borrow checker's region reasoning — which is what lets the optimization theorems in [1, 2] go through with only local reasoning. In Miri, a protector violation is reported at the exact triggering access, with a full backtrace of the borrow tree.

### 4.4 Miri as experimental semantics

A semantics that exists only on paper constrains nobody. Miri [6] is what makes Stacked Borrows and Tree Borrows *real*: it is an interpreter for MIR that implements the candidate aliasing model as dynamic borrow tracking, so that running a test suite under Miri is literally *executing the operational semantics* on real programs.

This inverts the usual specification/tool relationship: rather than a standard dictating behavior that tools approximate, the UCG process uses Miri as an **experimental semantics** — a candidate model is implemented, the ecosystem is run against it, and the accept/reject data *informs* whether the model is viable. The 30,000-crate study [2] and the FFI-boundary study [8] are the empirical leg of a standardization process: Tree Borrows' 54% fewer rejections is evidence, presented to the opsem team, about which contract the ecosystem can live under.

The "experimental" label in Miri's docs [6] reflects provisional *rules*, not shaky implementation: running Miri with Tree Borrows tests compliance with a candidate contract, not a stabilized standard. Miri findings are data for the UCG process, not verdicts.

### 4.5 Toward verification: from dynamic model to proof artifact

The deepest implication of the operational-semantics approach is for *verification*. Once aliasing is a mathematical object — a transition system over borrow trees — it becomes something one can reason about formally, in both directions:

**Verifying programs against the model.** The Simuliris framework [2] builds a *relational program logic* over the Tree Borrows semantics, enabling machine-checked proofs that specific optimizations preserve behavior — verification *of the compiler's assumptions*, not just of programs. Longer term, an unsafe library's safety argument can be stated as "all executions are well-defined under Tree Borrows," replacing folklore ("everyone does it") with a theorem.

**Verifying the model against reality.** MiniRust [5] embeds the aliasing model as a parameter of a full language semantics, turning "does this MIR transformation preserve Tree Borrows validity?" into a formal conjecture. Miri provides the testing complement: every unsafe crate's test suite is a potential counterexample to an over-strict model; every accepted miscompilation, one to an over-weak model.

The trajectory is visible in the RustBelt lineage [7]: RustBelt gave a semantic model of *safe* Rust's types in Iris and proved type soundness; Stacked Borrows and Tree Borrows extend the semantic method to the *unsafe* boundary; RefinedRust and related efforts push toward functional correctness. The aliasing models are thus not an isolated episode but the current frontier of a decade-long program: **replace syntactic trust with semantic proof**, all the way down to raw pointers.

## 5 Empirical Evaluation and Proofs

We consolidate the quantitative and formal evidence for the two models.

| Dimension | Stacked Borrows [1] | Tree Borrows [2] |
|---|---|---|
| Publication | POPL 2020 (Jung, Dang, Kang, Dreyer) | PLDI 2025 (Villani, Hostert, Dreyer, Jung) |
| Core structure | Per-location borrow *stack* | Per-allocation permission *tree* |
| Permission states | `Unique`, `SharedReadOnly`, `SharedReadWrite` | `Reserved`, `Active`, `Frozen`, `Disabled` |
| Mechanization | Coq | Rocq (formerly Coq), via Simuliris |
| Ecosystem evaluation | Large parts of std test suite: mostly accepted | 30,000 most-downloaded crates: **54% fewer rejections** than Stacked Borrows |
| Adjacent-read reordering | Not provably sound | Provably sound |
| Write-introducing optimizations | Sound | Not sound (deliberate tradeoff) |
| Protectors | Yes (call-scoped) | Yes (call-scoped) |

Both models' optimization theorems are *mechanized* — checked by a proof assistant, not merely argued on paper. Simuliris goes further, providing a reusable relational logic in which future optimizations can be proven sound. The model is thus not just a contract for programmers but *proof infrastructure* for compiler engineers.

Two empirical caveats. First, "rejects fewer test suites" measures *compatibility*, not *correctness* — a model accepting everything would score perfectly and justify nothing. The 54% figure matters because Tree Borrows simultaneously retains nearly all optimization power. Second, both studies measure executed test paths; untested unsafe code may violate either model silently, motivating complementary static verification.

## 6 Limitations

No honest formalization omits its boundaries. We identify five.

1. **The model is not the standard.** As of this writing, neither Stacked Borrows nor Tree Borrows has been adopted as Rust's official aliasing semantics; both remain *candidate* models under UCG discussion [3]. Code accepted by Miri today could, in principle, be declared UB by the eventual standard.

2. **Interior mutability and concurrency are partially modeled.** `UnsafeCell` introduces a parallel permission regime, and the interaction with atomics and weak memory remains active research (cf. [7]). Data-race detection in Miri is itself experimental [6].

3. **FFI is the open frontier.** The models govern Rust code; foreign functions are opaque. The FFI-boundary study [8] found 46 instances of undefined or undesired behavior across 37 libraries, many invisible to Miri's Rust-side tracking. A complete contract must eventually specify what Rust may assume about foreign code.

4. **Provenance remains underspecified at the edges.** Integer-to-pointer casts and exposed-provenance APIs are still being worked out in the UCG process; the corners are where the next papers live.

5. **Verification scale.** Mechanized proofs cover the models' metatheory and selected optimizations, but end-to-end verification of a real unsafe abstraction against Tree Borrows remains research-scale. Simuliris lowers the cost; it does not eliminate it.

## 7 Conclusion

Rust's aliasing discipline began as a type-system invariant — the borrow checker's "one mutable xor many shared" rule — and has matured, through Stacked Borrows and Tree Borrows, into something more ambitious: an **operational semantics of unsafe code** — executable in Miri, formalized in MiniRust, mechanized in Coq/Rocq, deliberated in the UCG process. The progression from stacks to trees is not merely a technical refinement; it is a methodological lesson. The stack conflated derivation order with permission and thereby rejected real code; the tree models aliasing as what it is — a relation between pointers — and recovers compatibility while preserving nearly all optimization power and even strengthening it for read reordering.

Three theses emerge for the field. First, *operational semantics are the right medium for unsafe-code contracts*: they are precise enough to prove optimizations against, executable enough to test ecosystems against, and modular enough (via protectors) to support local reasoning. Second, *experimental semantics work*: Miri's role as an executable candidate model turned standardization from armchair debate into a data-driven process, with the 54% compatibility figure as its emblematic result. Third, *verification is the destination*: once the contract is a transition system, both programs and compiler passes become amenable to proof — the RustBelt program extended, at last, across the unsafe boundary.

The contract is not yet signed — the UCG process continues, FFI and weak memory await their models, and no compiler enforces Tree Borrows in release builds today. But the shape of the answer is now visible, and it is a tree.
