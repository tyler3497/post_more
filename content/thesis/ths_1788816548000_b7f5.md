# Proof-Carrying Code and Typed Assembly Language: Foundational PCC, LF-Based Certificate Checking, and the Mechanics of Trust-Minimized Mobile Code

## Abstract

Proof-carrying code (PCC) lets a host determine with certainty that it is safe to execute a binary supplied by an untrusted source — without cryptography or external agents. The producer ships a *safety proof*, a machine-checkable certificate attesting adherence to a predefined safety policy, and the host validates it with a small, easily audited checker before execution. This thesis reconstructs the foundational arc of PCC: Necula's POPL 1997 protocol [1]; its expression in the Edinburgh Logical Framework (LF), where proofs become LF objects of type `pf SP` checked by a fifteen-rule type checker; the parallel line of *typed assembly language* (TAL), in which type-preserving compilation carries typing derivations to object code [7]; and the refinement of *foundational* PCC (Appel [2], Appel and Felty [3]), which shrinks the trusted computing base to machine semantics, higher-order-logic axioms, and the LF checker. We examine oracle-based validation [6], the adequacy metatheory of LF [4][8], the central theorems — adequacy, LF-checking soundness, TAL type safety, the foundational safety theorem — and evidence from the Touchstone compiler, TALx86/SpecialJ, and the Twelf implementation of foundational PCC.

## 1 Introduction

The *mobile code* problem is among the oldest in systems security: a host must execute programs arriving from untrusted sources — browser scripts, kernel packet filters, device drivers, over-the-air sensor updates — quickly, expressively, and above all *safely*, with respect to a precise policy such as memory safety or control-flow integrity.

The industrial answers have been *trust the producer* (code signing: the host trusts a vendor's key, hence the vendor's entire toolchain) and *constrain the language* (the Java bytecode verifier [6]: the host trusts a fixed, built-in type system). Both concentrate trust in large, complex artifacts. Necula's proof-carrying code proposal [1] rejects this concentration with a disarmingly simple insight: **instead of trusting the code producer, trust a small proof checker, and require the producer to supply a proof**.

The PCC protocol has three roles and four artifacts:

1. The *safety policy* — a formal specification of acceptable behavior, agreed in advance.
2. The *code producer* (untrusted) generates binary code **and** a safety proof: a formal derivation that the code satisfies the policy.
3. The *code consumer* (the host) runs a *proof validator* — small, simple, policy-independent — that checks the proof and permits execution only on success.

Because the validator is tiny (its logical core fits in a few pages of C [1]) and the proof is mere data, the trusted computing base (TCB) collapses to the validator plus the policy statement. Everything else — compiler, verification-condition generator, theorem prover — is untrusted: a bug there yields a proof that fails to check, i.e. a *rejected* program, never an unsound acceptance.

This thesis develops the full arc: background on VCGen, LF, and typed intermediate languages (Section 2); a comparative methodology (Section 3); the deep dive into the protocol, LF adequacy, TAL, foundational PCC, and oracle validation (Section 4); theorems and empirical evidence (Section 5); limitations (Section 6); and conclusions (Section 7).

## 2 Background

### 2.1 The mobile-code safety problem

Before PCC, safe mobile code meant the JVM's bytecode verifier: a dataflow type checker built into every host, guaranteeing one fixed property — type safety — with soundness resting on an informal argument about a large program. Alternatives (software fault isolation, sandboxing) pay steady-state run-time costs and offer coarse policies. Missing was a mechanism that is *policy-flexible*, *checkable by a tiny TCB*, and *zero-overhead at run time*.

### 2.2 Verification conditions: Floyd, Hoare, Dijkstra

PCC's proof machinery descends from program verification. Floyd assigned meanings to programs via assertions on control-flow edges; Hoare axiomatized them as triples `{P} c {Q}`; Dijkstra systematized weakest-precondition computation. A verification-condition generator (VCGen) consumes annotated code and emits a formula — the *verification condition* (VC) — whose validity entails policy compliance. Classically the VC is discharged by hand, and the VCGen's own soundness is taken on faith. PCC's first subversion: **if the VC's proof ships with the code and is checked mechanically, the VCGen need not be trusted** [1]. A buggy VCGen produces a false VC, whose "proof" will not check.

### 2.3 The Edinburgh Logical Framework

The second ingredient is a proof representation that makes checking trivial. The Edinburgh Logical Framework (LF) of Harper, Honsell, and Plotkin is a dependently typed λ-calculus built on *judgments as types*: object-logic judgments become LF type families, derivations become LF inhabitants, and object-level binding is represented by LF-level binding (higher-order abstract syntax), eliminating encoding bureaucracy [4][8].

What makes LF a certificate format is **adequacy**: a compositional bijection between object-logic derivations and *canonical forms* of the corresponding LF type. Adequacy must be proved per encoding, and LF's metatheory was built for it — Harper and Pfenning's type-directed equivalence algorithm gives decidable definitional equality and canonical forms strong enough for adequacy proofs, proved complete by a Kripke-style logical-relations argument that depends only on type *shapes* [4][8].

LF type checking is *decidable, simple, and policy-independent*: one checker validates proofs about memory safety, termination, or resource bounds, because the policy is just data (an LF signature). Necula and Lee's checker "can be completely described by fifteen inference rules and implemented in less than five pages of C code," and a single unmodified implementation served PCC experiments across widely varying policies [6].

### 2.4 Type-preserving compilation and System F

The TAL lineage starts from a compiler writer's complaint: conventional compilers *erase* the types that made the source safe. The TIL compiler showed types surviving optimization; Morrisett, Walker, Crary, and Glew pushed the idea to its limit — **down to assembly language** [7]. In TAL, machine code carries types: register files have types, code blocks have preconditions as polymorphic types, the stack has a type describing its shape — and a TAL type checker plays exactly the PCC validator's role. As Crary observed, both traditions apply logic, type theory, and verification to the security problem, differing in how much of the certificate is proof versus type derivation [7].

## 3 Methodology

This thesis is an analytical reconstruction, so its methodology is comparative and criterion-driven. Every PCC-family system decomposes into four components:

1. **Safety policy** — the formal guarantee (e.g., "no out-of-bounds access"). Is it stated independently of the enforcement mechanism?
2. **Certificate format** — what ships with the code (LF proof object, TAL annotations, oracle-augmented proof). Is it self-describing, needing no per-policy checker code?
3. **Checking algorithm** — what the consumer runs. Is it simple, decidable, and complete w.r.t. the policy?
4. **Trusted computing base** — the decisive question: **what is the smallest set of components whose compromise permits accepting an unsafe program?**

Evaluation criteria:

- **Expressiveness**: which policies are certifiable (memory safety only? liveness? resource bounds?).
- **Certificate economy**: proof size vs. code size; checking time vs. execution time.
- **TCB minimality**: trusted lines of code, and the semantic gap between what is trusted and what is proved.
- **Producer burden**: annotation and proof effort demanded of the untrusted producer.

Evidence is *formal* (adequacy [4][8], LF-checking soundness [1], TAL type safety [7], the foundational safety theorem [2]) and *empirical* (Touchstone [1][6], TALx86/SpecialJ [7], Twelf foundational PCC [2][3]).

> **Theorem (Methodological invariant):** *Moving a component from the TCB into the certificate strictly decreases host assurance burden while weakly increasing producer burden. PCC's history is this frontier advancing: from trusting the VCGen (classical verification), to trusting typing rules plus VCGen (early PCC), to trusting only logic axioms, machine semantics, and the LF checker (foundational PCC).*

## 4 Deep Dive

### 4.1 The original PCC protocol: Necula, POPL 1997

The founding paper [1] defines the producer pipeline in three stages. First, a **VCGen** processes the binary with policy-derived annotations, emitting a first-order **verification condition** whose validity implies policy compliance. Second, a **theorem prover** proves the VC. Third, the proof is encoded as an **LF object**: for safety predicate `SP`, the certificate is a term `PRF` with `⊢ PRF : pf SP`.

The consumer performs one LF type-checking query. The trust asymmetry is the point: VCGen, prover, compiler, annotations — all untrusted. Trusted: the LF checker, the policy's LF signature, and the small informal claim that the signature captures the intended policy. Case studies certified packet filters and kernel extensions at native speed: the proof is checked once at load time, with zero run-time overhead [1][6].

A minimal LF signature fragment illustrates the certificate language (Twelf concrete syntax):

```twelf
tp   : type.                    % object-logic types
o    : tp.                      % propositions
tm   : tp -> type.              % object terms, indexed by type
pf   : tm o -> type.            % proofs, indexed by proposition
imp  : tm o -> tm o -> tm o.
imp_i : (pf A -> pf B) -> pf (imp A B).
imp_e : pf (imp A B) -> pf A -> pf B.
```

Checking `⊢ PRF : pf SP` verifies both that the proof uses only declared constants and that it proves *the right predicate* — the two properties a certificate must have.

### 4.2 LF: judgments as types, adequacy, canonical forms

Why does type-checking an LF object constitute *proof* checking? The **adequacy theorem**, the central obligation of every LF encoding:

> **Theorem (Adequacy of LF encodings):** *For a well-designed signature Σ encoding object logic L, there is a compositional bijection between derivations of judgment J in L and canonical LF objects M with Γ ⊢Σ M ⇑ A, where A represents J. The bijection respects substitution.*

Without adequacy, a well-typed term might correspond to no genuine derivation, and the checker's verdict would be meaningless. Adequacy needs *canonical forms* — βη-long normals where every subterm's type is manifest — which Harper and Pfenning's type-directed equivalence algorithm supplies, decidably and practically [4][8].

![Figure 3: The LF judgments-as-types encoding — signatures, proof families, and the adequacy correspondence](/thesis/ths_1788816548000_b7f5-1.webp)

Two engineering consequences: (i) one checker serves all policies [6]; (ii) the signature configuration file must itself pass the LF checker before use.

### 4.3 From System F to Typed Assembly Language

TAL [7] reaches the same trust structure via compilation: **preserve types through every phase** — System F → CPS → closure conversion → allocation → TAL — so object code carries a typing derivation as its certificate. The technical content is types for machine entities:

- **Code types**: `∀[ᾱ]{r₁:τ₁, …, rₙ:τₙ}` — a precondition on the register file. Jumping to a label is well-typed exactly when the current register file matches the target's precondition: *control-flow safety as a typing rule*.
- **Stack types**: type-level lists (`τ :: σ`), with polymorphic stack variables letting one function type describe calls under any stack suffix — low-level polymorphic recursion.
- **Existentials and tuples** for heap invariants surviving to machine code.

TALx86 demonstrated a full functional language compiled to typed x86; SpecialJ compiled Java bytecode to TAL, enforcing JVM safety guarantees through TAL typing rather than a built-in verifier. The PCC/TAL contrast is crisp: PCC certificates are *proofs* in a general logic (expressive, but large and hard to produce); TAL certificates are *typing derivations* in a fixed system (compact, compiler-generated, but limited to type-expressible properties). Foundational PCC [2] synthesizes them: keep the general logic, but *prove the type system sound inside it* rather than trusting it.

A TAL-flavored typing rule for an indirect jump shows the low-level discipline:

```haskell
-- TAL typing: jump to a code label requires matching the precondition
--   Δ; Γ ⊢ r : ∀[ᾱ]{r₁:τ₁..rₙ:τₙ}     Δ; Γ ⊢ vᵢ : [σ̄/ᾱ]τᵢ  (for each i)
--   ─────────────────────────────────────────────────────────────
--   Δ; Γ ⊢ jmp r  (well-typed; control transfers only to valid code)
```

### 4.4 Foundational PCC: semantic models and the minimal TCB

Early PCC still trusts the typing rules/VCGen axioms in the LF signature. Appel and Felty [3] and Appel [2] refuse that trust. **Foundational PCC** trusts only: (1) the machine's operational semantics, (2) higher-order-logic axioms, (3) the LF checker. The type system, VCGen, and safety argument are *proved in the logic* and shipped in the certificate.

The mechanism is a **semantic model of types as predicates over machine states**: a type denotes a set of "good" machine configurations, defined by induction over a step-indexed approximation of machine behavior. Typing rules become *lemmas* in HOL — e.g., "if `r₁` holds a value in ⟦τ₁⟧, this instruction sequence leaves the machine in the postcondition's interpretation" — each proved from the operational semantics. Appel's LICS 2001 system [2] machine-checked the whole chain in Twelf: object logic (Church's HOL + arithmetic), small-step machine semantics, type-soundness lemmas, safety theorem.

![Figure 4: Foundational PCC — machine semantics, step-indexed type model, and safety policy as proved layers](/thesis/ths_1788816548000_b7f5-3.webp)

> **Theorem (Foundational PCC safety [2]):** *Let → be the machine's operational semantics, Safe a HOL-expressible safety predicate, and π an LF object with ⊢ π : pf (SafeProg P) in the foundational signature. Then every execution of P from a precondition-satisfying state remains within Safe. The proof depends only on HOL-encoding adequacy, LF-checker correctness, and machine-semantics fidelity.*

Crary's metalogical comparison [7] distinguishes Appel–Felty's *denotational* approach (semantic type model over machine instructions) from Hamid et al.'s *operational* one (preservation/progress in the Calculus of Inductive Constructions): both conduct policy, intermediate system, and compliance proof inside one logic, reasoning about the intermediate system through its encoding.

### 4.5 Oracle-based validation: making proofs small

Fully explicit LF proofs are large — every instantiation and conversion recorded. Necula and Lee's *oracle-based validation* [6] observes that most of a proof is deterministically reconstructible; only genuinely nondeterministic choices (which lemma, which existential witness) need recording. The certificate becomes *program + compact oracle bit-string* guiding the checker's reconstruction. Soundness holds because oracle bits are *hints*: every reconstructed step is re-validated against the signature, so a malicious oracle causes rejection, never unsound acceptance. Necula and Rahul extended this to *untrusted theorem provers* [6]: the prover emits an oracle trace of its search; the consumer reconstructs a checkable LF proof — the trust-shifting pattern applied one level down. Certificate sizes drop by orders of magnitude versus explicit proofs.

The producer/consumer protocol, abstractly:

```tla+
---------------------------- MODULE PCC ----------------------------
VARIABLES code, cert, checked
Init == code \in Binaries /\ cert \in Certificates /\ checked = FALSE
Check == /\ checked' = LFValid(code, cert)   \* 15-rule LF type check
         /\ UNCHANGED <<code, cert>>
Execute == /\ checked = TRUE                 \* runs only if proof valid
            /\ checked' = TRUE /\ UNCHANGED <<code, cert>>
Next == Check \/ Execute
Safety == [](checked => LFValid(code, cert)) \* never execute unchecked
=============================================================================
```

```python
def validate(code: bytes, cert: OracleCert, sig: LFSignature) -> bool:
    """Oracle-based LF validation: hints guide, signature decides."""
    proof = reconstruct(sig, code, cert.oracle_bits)  # deterministic replay
    if proof is None:          # oracle inconsistent -> reject, never accept
        return False
    return lf_typecheck(sig, proof, cert.safety_predicate)  # the 15 rules
```

## 5 Empirical Results and Formal Proofs

### 5.1 The metatheoretic core

> **Theorem (Soundness of LF-based checking [1][6]):** *If Σ adequately encodes safety logic L and the checker derives ⊢ PRF : pf SP for program P, then L derives P's safety. Trusted assumptions: adequacy of Σ, checker correctness, machine-model fidelity.*

> **Theorem (TAL type safety [7]):** *If ⊢ P : ok in TAL, execution never gets stuck: progress (every non-terminal configuration steps) and preservation (stepping preserves typing). Memory and control-flow safety follow as corollaries.*

> **Theorem (Adequacy enables certificate reuse [4][8]):** *Adequacy's bijection means any complete proof-search procedure for the object logic composes with the encoding into a complete certificate producer — while the checker stays fixed.*

### 5.2 Systems evidence

- **Touchstone / PCC infrastructure [1][6]:** certified packet filters and kernel extensions at native speed; checking cost a fraction of compile time; TCB measured in pages of C against tens of thousands of lines of untrusted toolchain; oracle validation cut certificate sizes by orders of magnitude.
- **TALx86 / SpecialJ [7]:** functional-language compilation to typed x86 with every binary TAL-checked; Java safety via TAL typing instead of a built-in verifier.
- **Foundational PCC in Twelf [2][3]:** the entire chain — machine semantics, semantic type model, typing lemmas, safety theorem — machine-checked in LF; consumer TCB = Twelf checker + HOL axioms. The high-water mark of TCB minimization.
- **Foundational proof certificates [5]:** Miller's generalization beyond code — a universal certificate format with a simple checker into which resolution, tableaux, and natural-deduction provers compile evidence; the producer/consumer asymmetry lifted from programs to proofs.

| System | Certificate | Consumer check | Trusted base | Policy flexibility |
|---|---|---|---|---|
| Java bytecode verifier | None (built-in) | Dataflow type check | Whole verifier (large) | Fixed: type safety |
| Original PCC [1] | LF object `pf SP` | LF type checking | LF checker + signature adequacy | Any encodable policy |
| Oracle PCC [6] | Code + oracle bits | Guided reconstruction + LF check | LF checker + adequacy | Any encodable policy |
| TAL [7] | TAL annotations | TAL type checking | TAL checker + safety proof | Type-expressible properties |
| Foundational PCC [2][3] | HOL proof incl. soundness lemmas | LF check of one judgment | Machine semantics + HOL axioms + LF checker | Any HOL-expressible policy |

## 6 Limitations

**Proof-production burden.** PCC shifts work rather than eliminating it: producers need a VCGen and a prover that discharge VCs for real binaries — unreliable for loop/arithmetic-heavy code without human-supplied invariants. TAL mitigates this for type-expressible properties (the compiler *is* the prover) but only within its type system's reach.

**Policy authoring and adequacy.** The policy signature and its adequacy argument are trusted and human-made; a signature/machine-semantics mismatch voids everything, and machine-checked adequacy for realistic ISAs remains rare. Foundational PCC shrinks but never eliminates this gap.

**Expressiveness boundaries.** Classical PCC/TAL certify *safety* ("nothing bad happens"). Liveness, information flow, and quantitative resource bounds are encodable in principle [6] but thinly automated. Concurrency is a further frontier: original machine models are sequential, and weak memory models multiply metatheoretic cost.

**The LF straitjacket.** LF's constructive, predicative character simplifies checking but complicates proof production — classical steps must be simulated. Focused certificate frameworks [5] generalize the format at the cost of a more elaborate checker.

**Adoption.** The built-in verifier won industrially: fixed policy and zero producer burden beat flexibility and a smaller TCB. PCC's ideas survive where assurance justifies cost — verified toolchains, high-assurance kernels — and reappear in proof-carrying data and succinct cryptographic proofs, where the producer/consumer asymmetry is enforced mathematically.

## 7 Conclusion

Proof-carrying code reframed mobile-code security as applied metatheory: the host trusts neither producer, compiler, VCGen, nor prover — only a fifteen-rule checker and a signature's adequacy. Typed assembly language showed the same trust structure emerging from type-preserving compilation, with typing derivations as certificates. Foundational PCC completed the arc, reducing the TCB to machine semantics, logical axioms, and the checker, with the type system proved sound inside the logic. Oracle-based validation made certificates shippable.

The deeper lesson is architectural and outlives any checker: **structure systems so trust is proportional to simplicity, and let complexity live where it can be checked rather than believed**. Untrusted components may be arbitrarily clever, because their output is verified, not trusted. That principle [1][2][3][7] now underwrites verified compilation, proof-carrying data, and succinct proofs. The certificates changed — from LF objects to STARKs — but Necula's 1997 protocol is instantly recognizable: *the producer proves, the consumer checks, and the checker stays small*.
