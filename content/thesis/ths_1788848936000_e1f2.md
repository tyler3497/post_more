# Formalizing Rust's Borrow Checker: Stacked Borrows, Tree Borrows, and Miri-Based Detection of Undefined Behavior

## Abstract

Rust's ownership type system forbids aliasing and mutation from coexisting, yet unsafe code routinely escapes static checking. Stacked Borrows introduced an operational aliasing discipline: every memory location carries a stack of borrows, and accesses that pop the stack in violation of the discipline are undefined behavior. Its successor, Tree Borrows, replaces the LIFO stack with a permission tree and fine-grained protector states, admitting strictly more real-world unsafe idioms while preserving the optimizations compilers demand. This thesis formalizes both models, contrasts their transition systems, and analyzes the Miri interpreter — which implements them as executable semantics for Rust's Mid-level Intermediate Representation — as an empirical instrument for detecting undefined behavior. We survey two-phase borrows, interior mutability handling, and large-scale validation studies over the standard library test suite, and conclude with the open semantic questions that keep Rust's unsafe code guidelines incomplete.

## 1 Introduction

Type systems enable optimizations as well as safety guarantees. In Rust, the type system imposes a strict aliasing discipline that the compiler developers explicitly want to exploit for optimizations that reorder memory accesses — hoisting loads above calls, sinking stores below them, eliminating redundant reads [1]. The difficulty is that Rust *also* supports `unsafe` code, and programmers can write unsafe code that bypasses the borrow checker's syntactic checks to violate the aliasing discipline entirely. The language therefore owes unsafe code authors a contract: a set of rules such that, if they are followed, the compiler is guaranteed to preserve the semantics of their code despite every optimization it performs.

Defining that contract is the problem of *aliasing models* for Rust. Two families dominate: **Stacked Borrows** [1], which tracks a stack of borrow items per memory location and declares out-of-discipline accesses undefined behavior (UB), and **Tree Borrows** [2], which replaces the stack with a tree of permissions that is more permissive toward common unsafe idioms. Both are *operational* models: they define UB as a property of an abstract execution, and both are implemented in **Miri** [5], an interpreter for Rust's Mid-level Intermediate Representation (MIR) that turns the models into executable oracles — programs that violate the discipline simply get stuck (report UB) at runtime.

This thesis presents the formal structure of both models, the engineering of Miri as a UB detector, the complementary role of two-phase borrows in the surface language, and the empirical evidence that these models accept realistic unsafe code. We argue that the trajectory from Stacked Borrows to Tree Borrows is not merely a relaxation, but a principled refinement of what compiler optimizations the aliasing model must justify.

## 2 Background

### 2.1 Ownership, borrows, and the borrow checker

Rust's type system rests on three principles. First, every value has a single *owner*, and the value is deallocated when the owner goes out of scope. Second, ownership can be transferred by *moves*, which are destructive reads. Third, access can be temporarily loaned through *borrows*: a shared borrow `&T` permits concurrent read-only aliasing, while a mutable borrow `&mut T` grants exclusive read-write access with no aliases whatsoever. The borrow checker enforces these rules statically within safe code, with *non-lexical lifetimes* allowing a borrow's extent to end at its last use rather than at the end of a lexical scope.

These rules have a *semantic* purpose beyond memory safety: the compiler wants to assume that a `&mut i32` argument aliases nothing else live, so it can reorder accesses around calls using only intraprocedural reasoning. **RustBelt** [3] gave the first semantic foundation — a model of Rust's type system in the Iris separation logic (λRust) with a type-soundness proof — but it models *safe* Rust only. Stacked Borrows [1] was proposed precisely to fill the unsafe-code gap.

### 2.2 Why an operational aliasing model

LLVM's `noalias` and related attributes encode the assumption that pointer arguments to a function are not accessed through pointers "not based on" those arguments during the call. Stacked Borrows answers with an operational semantics: each memory location maintains a *borrow stack*; each reference creation *pushes* an item; each access *pops* all items above the accessing item unless they are compatible with the access. Popping the accessing item itself — using a reference whose grant has been revoked — is UB [1].

### 2.3 Miri

Miri is an interpreter for Rust's MIR [5]. It executes compiled crates symbolically enough to run real test suites, and it checks for classes of UB: out-of-bounds accesses, use-after-free, uninitialized reads, misaligned accesses, type-invariant violations (e.g., a `bool` holding 2), and — experimentally — violations of the Stacked Borrows and (optionally) Tree Borrows aliasing rules. Because the models are *operational*, they can be implemented directly as interpreter state: no separate theorem prover is needed to detect a violation.

## 3 Methodology

This thesis is a formal exposition and synthesis. Our method is threefold:

1. **Reconstruction of the transition systems.** We restate the Stacked Borrows borrow-stack discipline and the Tree Borrows permission-state machine as small-step operational rules, following [1] and [2], and we identify precisely where Tree Borrows is strictly more permissive.
2. **Model-as-interpreter analysis.** We examine how Miri embeds these models — per-location stacks/trees, *protectors* for function-argument references, retagging of references on creation — and how this embedding converts a mathematical UB definition into a concrete test oracle.
3. **Empirical survey.** We review the validation methodology of [1] (running the Rust standard library test suite under Miri) and subsequent community experience, and we discuss two-phase borrows as the surface-language mechanism that keeps common method-call patterns well-defined under both models.

> **Theorem (Stacked Borrows optimization soundness, informal [1]):** Under the Stacked Borrows operational semantics, a compiler may reorder memory accesses around unknown code and function calls using only intraprocedural alias information. Formally, the paper proves (mechanized in Coq) that programs accepted by the model admit the reorderings that the LLVM-level optimizations require.

## 4 Deep Dive

### 4.1 Stacked Borrows: an operational aliasing discipline

In Stacked Borrows, every *byte* of memory conceptually carries a stack of **borrow items** recording the pointer identity (a *tag*), the granted permission — `SharedReadOnly`, `SharedReadWrite`, or `Unique` — and whether the item is *protected* (function-argument references are protected for the call duration). Three operations manipulate the stack: **creation/reborrow** pushes a new item above the parent's; **access** pops every item above the accessor incompatible with it (a write pops everything above except frozen shared items; a read pops only non-frozen write-granting items); **violation** — if the access pops the accessor's own item, the program has UB [1].

The canonical Stacked Borrows violation — valid under the surface borrow checker, UB at the aliasing-model level — is:

```rust
fn main() {
    let mut x = 0;
    let p: *mut i32 = &mut x;
    let y: &mut i32 = unsafe { &mut *p }; // reborrow: pushes y above p
    *p = 1;   // foreign write: pops y's item (y grants Unique)
    *y = 2;   // UB: y's item is gone — y has been invalidated
}
```

The write through `p` is *foreign* to `y` (it does not go through `y` or anything derived from it), so it pops `y`'s `Unique` item. The subsequent use of `y` finds its item missing and the model reports UB. Under the surface borrow checker this program is perfectly fine — the unsafety is purely at the aliasing-model level, which is exactly the point: Stacked Borrows defines the rules for *unsafe* code.

![Figure 1: Stacked Borrows borrow stack](ths_1788848936000_e1f2-0.webp)

*Figure 1 — The per-location borrow stack: reborrows push items, foreign writes pop incompatible items above the accessor, and using a popped item is UB.*

**Protectors** handle function boundaries. When a reference is passed as a function argument, its stack item is marked *protected* until the call returns; a foreign access that would pop a protected item is UB immediately — this is what justifies LLVM `noalias` [1].

| Access kind | Pops above accessor | UB condition |
|---|---|---|
| Read via `SharedReadOnly` | `Unique` items above | accessor item popped |
| Read via `Unique`/`SharedReadWrite` | `Unique` items above | accessor item popped |
| Write via `Unique` | all items above except frozen shared | accessor item popped, or protected item popped |
| Any access | — | protected item would be popped |

### 4.2 Tree Borrows: from stacks to trees

Stacked Borrows is strict: it flags as UB several idioms common in real unsafe code, such as deriving a raw pointer from a reference and offsetting it *outside* the original borrow's range — the LIFO stack cannot express "same provenance, different range." **Tree Borrows** [2] replaces the per-location stack with a per-allocation **tree of permissions**: each reference creation adds a node, parent-child edges record derivation, and each access *updates* node states, advancing a node only until it has lost the permissions incompatible with the access. All transitions are idempotent, which also enables a major Miri optimization — subtrees already processed for an access kind can be skipped, yielding 2–5× speedups [2].

Each node carries a permission drawn from a state machine. The core states are:

- **Reserved** — a fresh `&mut` that has not yet been written through (lazily initialized exclusivity).
- **Active** — a `&mut` that has been written through; grants read and write.
- **Frozen** — a shared `&` (or a former `Active` that lost write permission); read-only.
- **Disabled** — no permissions remain; any access through this node is UB.

Transitions are driven by four event kinds: *child* (access through the node or its descendants) vs. *foreign* (access through an unrelated node), crossed with *read* vs. *write*. A child write on `Reserved` activates it (`Reserved → Active`); a foreign write on `Active` demotes it (`Active → Frozen`); a foreign write on `Frozen` disables it. Crucially, permissions are tracked per *range* of the allocation, and creating `&mut v[0]` installs permissions for the *entire allocation* — so raw-pointer arithmetic that wanders outside the type-indicated range remains well-defined, as long as disjointness between sibling subtrees is respected [2].

For function arguments, Tree Borrows uses **protectors** with a refined state machine: a protected `&mut T` starts in `Reserved`, and a boolean *conflicted* flag records whether a foreign read occurred. A conflicted `Reserved` reference can never become `Active`; a child write to it is UB. The net effect is the compiler-facing guarantee the model must justify:

> **Theorem (Tree Borrows noalias justification, informal [2]):** For any mutable reference passed as a function argument, it is UB for that reference to encounter both a foreign read and a child write — in either order — during the call. This is precisely the condition LLVM's `noalias` requires, and it also justifies moving a write *above* a foreign read (the motivating optimization that Stacked Borrows permits but naive Tree Borrows would not).

![Figure 2: Tree Borrows permission tree](ths_1788848936000_e1f2-1.webp)

*Figure 2 — Permission tree with Reserved/Active/Frozen states; protected nodes additionally track the conflicted flag that rules out foreign-read-then-write reorderings violations.*

| Feature | Stacked Borrows | Tree Borrows |
|---|---|---|
| Structure per location | LIFO stack of items | tree of permission nodes |
| Reborrow invalidation | pops stack (strict) | state transitions (lazy) |
| `&mut` before first write | `Unique` immediately | `Reserved` (lazy activation) |
| Out-of-range raw pointer arithmetic | UB (stack is per-location) | allowed within allocation |
| Protectors | pop-protected items | conflicted flag + refined machine |
| Relative strictness | stricter | strictly more permissive [2] |

Tree Borrows is a *successor*, not a competitor: the Rust project is converging on it as the candidate aliasing model precisely because it accepts more existing unsafe code while still justifying the target optimizations [2][7].

### 4.3 Two-phase borrows: keeping method calls well-defined

A subtle interaction arises with *autoref* method calls. In `v.push(x)`, the receiver `v` is implicitly reborrowed as `&mut *v` to form the method receiver — but the *argument* `x` is evaluated after the borrow is created, and `x`'s evaluation may itself use `v`. Under a naive desugaring the mutable borrow of `v` would already be active while `x` is computed, invalidating any aliasing inside `x`'s evaluation:

```rust
let mut v = vec![1, 2, 3];
v.push(v.len()); // autoref reborrows v mutably... but v.len() reads v!
```

**Two-phase borrows** solve this by splitting the borrow into a *reservation* phase and an *activation* phase. Desugared:

```rust
let mut v = vec![1, 2, 3];
// Phase 1 (reservation): create the borrow, but do not activate it.
let r = &mut v;            // reserved: acts like a shared borrow for now
// Phase 2 (activation): happens at the actual call, after args are evaluated.
Vec::push(r, v.len());     // r activated here; v.len() already computed
```

During the reservation phase the borrow behaves like a shared borrow for aliasing purposes; it is only *activated* to a full mutable borrow once argument evaluation completes. In Stacked Borrows terms, the reservation pushes a `SharedReadWrite`-like item that is upgraded to `Unique` at activation; in Tree Borrows terms, the node sits in `Reserved` and is activated by the first child write [1][2]. Two-phase borrows are thus the surface-language mechanism that keeps one of the most common Rust idioms — method calls with computed arguments — well-defined under both aliasing models.

### 4.4 Miri: from operational model to executable oracle

Miri turns the mathematics into a tool. Its pipeline is:

1. **MIR input.** Miri consumes Rust's Mid-level Intermediate Representation after borrow checking, so it observes the program the compiler actually optimizes.
2. **Retagging.** Every reference creation (and raw-pointer cast) is instrumented: Stacked Borrows pushes a tagged item; Tree Borrows inserts a permission node. Each pointer value carries its *tag*, i.e., its provenance.
3. **Access interception.** Every memory access is classified (read/write, child/foreign relative to each affected node) and the model state is updated.
4. **Violation reporting.** When an access is UB under the model, Miri aborts with a precise diagnostic: the offending access, the borrow that was invalidated, and a backtrace to its creation.

![Figure 4: Miri detection pipeline](ths_1788848936000_e1f2-3.webp)

*Figure 4 — Miri's pipeline: MIR is interpreted with per-location borrow state; a Stacked Borrows violation (use of a popped borrow) aborts execution with a provenance backtrace.*

Because the models are executable, Miri doubles as a *differential testing* instrument: the same test suite can be run under Stacked Borrows and under Tree Borrows (`-Zmiri-tree-borrows`), and divergences pinpoint exactly which idioms the stricter model rejects. This is how the community established that Tree Borrows accepts strictly more real code [2][7]. Miri's isolation (deterministic fake clocks, RNG, and system interfaces) further makes UB reports reproducible [5].

### 4.5 Unsafe code guidelines and empirical UB studies

The operational models are necessary but not sufficient: the Rust project also needs *guidelines* — prose rules unsafe authors can follow without running an interpreter. The reference documents the current (incomplete) consensus on what constitutes UB, e.g., invalid values, out-of-bounds and misaligned accesses, and data races [6]. The aliasing-model work feeds directly into these guidelines: whatever Tree Borrows ultimately declares UB *is*, by definition, what the guidelines must forbid.

Empirically, [1] validated Stacked Borrows by running large parts of the Rust standard library test suite under Miri — the largest available corpus of *vetted* unsafe Rust, so any model that flags its idioms as UB is too strict to deploy. Stacked Borrows passed modulo a handful of known patterns (notably raw-pointer offsetting), and Tree Borrows was designed to admit the remaining ones while preserving the optimization theorems [2]. Community experience since — Miri's public list of real-world bugs found and the `-Zmiri-tree-borrows` differential runs — constitutes an ongoing distributed empirical study of the aliasing contract.

## 5 Empirical Results / Proofs

The evidence for the models falls into three categories:

**Mechanized metatheory.** Stacked Borrows comes with Coq-mechanized proofs that the discipline justifies the target class of reorderings around unknown code, using only intraprocedural reasoning [1]. Tree Borrows extends the proof burden: its paper proves that the refined protector machine (with the *conflicted* flag) justifies moving a write above a foreign read — the optimization that motivated the refinement — and that the model remains sound for LLVM `noalias` [2].

**Corpus validation.** The decisive empirical test in [1] is the Miri-based run of the Rust standard library test suite: thousands of tests exercising `Vec`, `HashMap`, `Cell`/`RefCell`, iterators, and I/O all execute under the instrumented interpreter without triggering UB. This is a *soundness-of-permissiveness* argument: the model does not outlaw the unsafe code the ecosystem actually depends on. Tree Borrows repeats the exercise with strictly fewer failures, and its acceptance of allocation-wide permissions (the `&mut v[0]`-then-offset idiom of §4.2) closes the most prominent gap [2].

**Differential UB detection.** Running crates under both models turns Miri into a classifier: programs accepted by Tree Borrows but rejected by Stacked Borrows are exactly the "disputed" idioms. The idempotency of Tree Borrows transitions additionally yields 2–5× interpreter speedups via subtree skipping, making large-scale differential runs practical [2].

> **Theorem (Tree Borrows permissiveness, informal [2]):** Every program that is UB under Tree Borrows' core discipline is also UB under Stacked Borrows, but not conversely: Tree Borrows admits programs (lazy `&mut` activation, out-of-range derived raw pointers, certain self-referential patterns) that Stacked Borrows rejects. The inclusion is strict.

## 6 Limitations

The program is unfinished, and the limitations are substantial:

1. **No blessed model yet.** Neither Stacked Borrows nor Tree Borrows is the *official* aliasing model of Rust. The unsafe code guidelines remain incomplete [6]; until the language team blesses a model, every UB verdict is provisional and subject to revision.
2. **Miri is unsound as a verifier and incomplete as a detector.** Miri checks only executed paths — untested code paths are unchecked — and it deliberately avoids some checks (e.g., validity invariants of references' pointees) to limit false positives [5]. Passing Miri is evidence, not proof, of UB-freedom.
3. **Concurrency and weak memory.** The models described here are sequential. Extending them to data races and weak-memory effects (in the spirit of RustBelt's relaxed-memory successor [3]) remains open; Miri's data-race detection is experimental and models no weak-memory effects [5].
4. **Interior mutability and `UnsafeCell`.** Types like `Cell<T>` deliberately opt out of aliasing guarantees via `UnsafeCell`. Both models special-case them (Tree Borrows starts protected `&mut Cell<T>` in a distinct state [2]), but the interaction between shared references, interior mutability, and protector-based optimizations is among the most delicate parts of the design.
5. **Optimization coverage.** The theorems justify *specific* reorderings and `noalias`; they do not cover every optimization LLVM might perform on Rust code (e.g., those exploiting `dereferenceable` or alignment attributes derived from types). Each new attribute needs its own justification proof.
6. **Performance of interpretation.** Miri is orders of magnitude slower than native execution, and borrow-state tracking adds further overhead; whole-program UB checking of large applications remains impractical, though Tree Borrows' subtree-skipping optimization narrows the gap [2].

## 7 Conclusion

Stacked Borrows gave Rust its first operational answer to the aliasing question: a borrow stack, a pop discipline, and UB for violations — with mechanized proofs that the discipline buys real optimizations and an interpreter-based validation over the standard library [1]. Tree Borrows refines the answer into a permission tree with lazy activation, allocation-wide provenance, and a protector machine strong enough to justify the reorderings compilers actually perform, while admitting strictly more real-world unsafe code [2]. Miri makes both models executable, converting abstract UB into concrete, reproducible diagnostics and enabling differential empirical studies at ecosystem scale [5]. Two-phase borrows, meanwhile, show how surface-language design co-evolves with the models to keep everyday idioms well-defined.

The remaining work is as much social as technical: blessing a single model, completing the unsafe code guidelines [6], and extending the discipline to concurrency. But the trajectory is clear — Rust is converging on an aliasing contract that is *formal enough to prove optimizations against, executable enough to test code against, and permissive enough to keep unsafe code working*. That triple requirement is the real contribution of this line of work, and the standard against which any successor model will be judged.
