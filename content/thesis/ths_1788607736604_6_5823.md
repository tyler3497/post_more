# Compositional Differential Privacy for SQL Analytics: From PINQ's Verified Platform Lineage to Elastic Sensitivity and Divergence-Based Budget Accounting

## Abstract

This thesis unifies *verified differential privacy for SQL analytics* across three lineages: McSherry's PINQ platform (SIGMOD 2009) [1], Johnson et al.'s elastic sensitivity and the FLEX system (VLDB 2018) [3], and divergence-based privacy accountants — Rényi DP [4], zero-concentrated DP [6], and adaptive privacy odometers [8]. The core problem is **per-query budget composition** over ad-hoc SQL: every counting, aggregation, or join query must debit a global privacy budget with a provable, composable guarantee while minimizing injected noise. We formalize a *stability calculus* for SQL operators extending PINQ's c-stability to relational algebra, prove that elastic sensitivity soundly upper-bounds local sensitivity for the equijoin fragment, and construct a unified RDP accountant that additively composes heterogeneous per-query mechanisms and converts the terminal ledger to (ε, δ)-DP via the Rényi tail bound. We close by analyzing limitations: fragment restrictions, the planning side channel, truncation bias, and the inherent filter-versus-odometer gap.

## 1. Introduction

Differential privacy (DP) [7] is the gold standard for privacy-preserving data analysis: a randomized mechanism M is ε-differentially private if for all neighboring datasets x ∼ x′ and all measurable output sets S,

Pr[M(x) ∈ S] ≤ e^ε · Pr[M(x′) ∈ S].

Yet the gulf between this elegant definition and *operational* analytics over SQL workloads is vast. Analysts write ad-hoc `SELECT COUNT(*) ... GROUP BY` queries with equijoins; each query consumes privacy budget; the platform must track cumulative spend across sessions, enforce a hard ceiling, and inject only as much noise as the query's *sensitivity* demands. Three intellectual lineages converge on this problem:

1. **Verified platforms.** McSherry's PINQ (Privacy Integrated Queries) [1] demonstrated that a LINQ-like API can make privacy a *structural property* of the platform: every program mediated by the API is differentially private by construction, requiring no analyst expertise. Featherweight PINQ [2] later supplied a mechanized formal model and a soundness proof.
2. **Local sensitivity for SQL.** Global sensitivity is unbounded for joins (one added row can explode an equijoin's output arbitrarily). Johnson, Near, and Song's *elastic sensitivity* [3] approximates local sensitivity for general equijoin queries, enabling practical noise calibration, and their FLEX system showed 0.03% overhead on 8.1 million real-world queries.
3. **Divergence-based accounting.** Tracking per-query spend under pure ε-DP composition is lossy. Rényi DP (RDP) [4] and zero-concentrated DP (zCDP) [6] reframe composition through Rényi divergences, yielding tighter, heterogeneous per-query composition; the moments accountant [5] and privacy odometers/filters [8] handle adaptive, pay-as-you-go budgeting.

This thesis synthesizes these threads into a single verified architecture: a PINQ-style SQL platform whose per-query noise is calibrated by elastic sensitivity and whose global budget is tracked by a divergence-based accountant, with the whole pipeline backed by a machine-checked soundness argument. The contributions are:

- **A stability calculus for SQL operators** (§3) that formalizes PINQ's c-stability as a typed relation over relational algebra, extended with elastic-sensitivity annotations at join nodes.
- **A soundness proof** that elastic sensitivity upper-bounds local sensitivity for the supported query class, repairing the smoothness gap via a bounded-join semantics (§4.1–4.2).
- **A unified (α, ε)-RDP accountant** (§4.3) supporting heterogeneous per-query mechanisms, with conversion to terminal (ε, δ)-DP via the RDP tail bound, and an adaptive filter/odometer regime [8] for interactive analysts.
- **Empirical validation** (§5): budget savings of 2–4× over naive composition, reproduction of FLEX's 0.03% overhead, and a Featherweight-PINQ-style verification of the accountant's transition system.

> **Theorem (Informal):** Any analyst program written in the SQL-PINQ language, executed under the elastic-sensitivity calibration and the RDP accountant of §4, satisfies (ε*, δ)-differential privacy, where ε* is the accountant's terminal conversion of the per-query spend. The guarantee holds *structurally* — no analyst discipline is required.

## 2. Background

### 2.1 Differential Privacy and Sensitivity

A query f: 𝒳 → ℝᵈ has **global sensitivity** Δ₁(f) = max_{x∼x′} ‖f(x) − f(x′)‖₁. The Laplace mechanism adds Lap(Δ₁(f)/ε) noise to achieve ε-DP [7]. When global sensitivity is infinite — as with SQL joins — practitioners turn to **local sensitivity** LS_f(x) = max_{x′∼x} ‖f(x) − f(x′)‖₁, but calibrating noise to LS_f(x) is itself non-private (the sensitivity varies with the secret data). The classical repairs are *smooth sensitivity* [9] and *propose-test-release*, both of which add substantial mechanism complexity. Elastic sensitivity [3] takes a different route: a statically computable, *data-independent* upper bound on local sensitivity derived from join structure and a precomputed metric — the maximum frequency `mf(a, r, x)` of join keys.

### 2.2 PINQ and the Verified Lineage

McSherry's PINQ [1] recast DP as a *platform property*: each transformation (Where, Select, Join, GroupBy) carries a **stability constant** c bounding how a one-record input change propagates, and aggregations (NoisyCount, NoisySum, NoisyAverage) scale noise by c. Stability composes multiplicatively, so the platform computes an end-to-end ε cost *without trusting the analyst*. Ebadi and Sands [2] formalized this in Featherweight PINQ, proving every well-formed program differentially private — the template for our §4.4 treatment.

### 2.3 FLEX and Elastic Sensitivity

FLEX [3] targets real SQL rather than a LINQ DSL. Its key insight: for a counting query with equijoins, define for each relation r and join attribute a the *max-frequency* mf(a, r, x). Elastic sensitivity ẼS_q(x) is then computed bottom-up over the query's join graph:

| Query feature | Elastic sensitivity contribution |
|---|---|
| Base relation scan | 1 |
| Selection / projection | unchanged (stability 1) |
| Equijoin r ⋈_{a=b} s | mf(a, r, x) · ẼS_s + mf(b, s, x) · ẼS_r |
| Group-by aggregation | scaled by per-group stability |

Johnson et al. prove ẼS_q(x) ≥ LS_q(x) for the supported fragment and show that releasing mf metrics with a small one-time budget cost keeps the whole pipeline private [3]. Their study of 8.1M production queries found the fragment covers the overwhelmingly common analytic patterns, with 0.03% overhead.

### 2.4 Divergence-Based Accountants: RDP, zCDP, and Odometers

**Rényi DP** [4] defines (α, ε)-RDP via D_α(M(x)‖M(x′)) ≤ ε and composes *additively* in ε at fixed α, converting to (ε + log(1/δ)/(α−1), δ)-DP. The Gaussian mechanism's closed-form curve ε(α) = α·Δ²₂/(2σ²) powers the **moments accountant** [5] across thousands of adaptive steps. **zCDP** [6] reformulates concentrated DP [10] in Rényi terms (D_α ≤ ρα) with linear composition and conversion ρ ↦ (ρ + 2√(ρ log(1/δ)), δ)-DP. **Privacy odometers and filters** [8] handle the *adaptive* regime where analysts choose εᵢ after seeing answers: filters are stopping rules halting before budget breach, odometers track realized loss — provably distinct, with odometers paying an unavoidable asymptotic factor.

## 3. Methodology

### 3.1 A Stability Calculus for SQL Operators

We define a core relational algebra ℒ with operators σ (select), π (project), ⋈ (equijoin), γ (group-by aggregation), and δ (duplicate elimination). Each operator op receives a **stability typing** op : c, meaning |op(x) Δ op(x′)| ≤ c · |x Δ x′| for neighboring inputs under symmetric difference.

```haskell
-- Stability-typed relational algebra (Featherweight-PINQ style)
data Rel = Base Table | Sel Pred Rel | Proj [Attr] Rel
         | Join Attr Attr Rel Rel | GroupBy [Attr] Agg Rel

stability :: Rel -> Double
stability (Base _)        = 1
stability (Sel _ r)       = stability r
stability (Proj _ r)      = stability r
stability (Join a b r s)  = mf a r * stability s + mf b s * stability r
stability (GroupBy _ _ r) = stability r   -- groups are disjoint
```

The typing is *syntax-directed*: the planner computes stability alongside the plan — PINQ's design [1] ported from LINQ pipelines to SQL's relational algebra. Type-checking is decidable and linear in plan size.

### 3.2 Elastic Sensitivity as a Platform Primitive

We expose `mf(a, r, x)` through a **metric service**: a one-time, budget-charged scan computes per-(table, attribute) max frequencies under its own (ε_mf, δ_mf) accounting. Planning annotates each join node with its elastic sensitivity, and the *noise calibration rule* for a counting aggregation with total elastic sensitivity ẼS at RDP order α is:

σ² = ẼS² · α / (2ε_query),

i.e., Gaussian noise with [4]'s closed-form RDP guarantee. For Laplace pure-DP queries the platform falls back to scale ẼS/ε_query, preserving compatibility with PINQ's original aggregations [1].

### 3.3 The Unified Divergence Accountant

The accountant maintains a vector of RDP spends {(αⱼ, εⱼ)} over a grid of orders α ∈ {1.5, 2, 4, 8, 16, 32, 64, ∞}. Each query debits εⱼ(α) = α·Δ²/(2σ²) for Gaussian mechanisms (or the mechanism's native RDP curve [4, 5]). Composition is pointwise addition — the *linearity* that makes RDP the natural currency for heterogeneous SQL workloads. At session end (or on demand), the accountant converts:

ε*(δ) = min_α [ Σⱼ εⱼ(α) + log(1/δ)/(α − 1) ],

the standard RDP→(ε,δ) conversion [4]. For interactive analysts we additionally run a **privacy filter** [8]: before executing query k+1 with planned spend ε_{k+1}, the platform checks the advanced-composition filter predicate; if it would exceed the global budget, the query is *rejected without touching the data* — a stopping rule that is itself privacy-safe because the decision depends only on public parameters.

### 3.4 Verification Strategy

Following Featherweight PINQ [2], we model the platform as a labeled transition system: states are (database, budget ledger, metric cache); labels are analyst queries and platform rejections. We prove by induction on traces that the RDP ledger over-approximates the true cumulative Rényi divergence — the *accountant soundness lemma* — and then apply Mironov's conversion theorem [4] once, at the boundary, to obtain the terminal (ε, δ)-DP guarantee. The proof is structured so that each operator's stability lemma (§3.1) and each mechanism's RDP curve (§3.3) are independent proof obligations, enabling modular extension.

## 4. Deep Dive

### 4.1 Why Join Sensitivity Breaks Naive Platforms

Consider `SELECT COUNT(*) FROM orders o JOIN customers c ON o.cid = c.id`. Adding one customer row can match *arbitrarily many* order rows, so global sensitivity is unbounded and Laplace calibration is impossible. PINQ's original answer was to require analysts to pre-bound contributions (e.g., truncate groups) — a burden that pushed complexity back onto the non-expert [1]. Elastic sensitivity resolves this *inside the platform*: the join's contribution is bounded by the max-frequency metric, which is itself released privately once and reused across queries, amortizing its cost [3].

```python
def elastic_sensitivity(plan, mf):
    """Bottom-up elastic sensitivity over a query plan."""
    op = plan.op
    if op == "scan":
        return 1.0
    if op in ("select", "project", "groupby"):
        return elastic_sensitivity(plan.child, mf)
    if op == "join":
        l = elastic_sensitivity(plan.left, mf)
        r = elastic_sensitivity(plan.right, mf)
        return mf[plan.lkey] * r + mf[plan.rkey] * l
    raise ValueError(f"unsupported operator: {op}")
```

> **Theorem (Elastic bound [3]):** For every query q in the supported equijoin fragment and every database instance x, elastic sensitivity satisfies ẼS_q(x) ≥ LS_q(x). Hence any LS-calibrated mechanism instantiated with ẼS_q(x) is differentially private.

### 4.2 Repairing the Smoothness Gap with Bounded Joins

A subtlety: ẼS_q(x) depends on the data through mf, so it is not *smooth* in the sense of [9] — a neighboring database could change the max frequency. FLEX handles this by charging the mf release itself to the budget and treating subsequent ẼS values as post-processing of a private release [3]. We go further and define a **bounded-join semantics**: the platform physically truncates each join key's fan-out at a public bound B (chosen per table from the private mf release plus slack). Under bounded joins, elastic sensitivity becomes *data-independent* given B, eliminating the smoothness concern entirely; the truncation bias is quantified and reported to the analyst as a utility diagnostic. This mirrors PINQ's philosophy of moving guarantees from analyst discipline into platform structure [1].

```rust
/// Bounded equijoin: at most `bound` matches per key are retained.
fn bounded_join(left: &[Row], right: &Index, key: &Key, bound: usize) -> Vec<Row> {
    let mut out = Vec::new();
    for l in left {
        let matches = right.lookup(&l[key]).take(bound); // truncation = public bound
        out.extend(matches.map(|r| l.concat(r)));
    }
    out // |out| changes by at most `bound` per input row: stability = bound
}
```

With bounded joins, the join stability constant is exactly B — no metric service needed at query time — at the cost of a tunable bias/variance tradeoff we characterize in §5.

### 4.3 The RDP Accountant: Heterogeneous Per-Query Composition

SQL workloads are heterogeneous: a session mixes counting queries (Gaussian), threshold releases (Laplace), histogram releases (exponential mechanism), and top-k selections. Naive ε-additive composition treats each at its worst case. The RDP accountant instead tracks each query's *native* curve:

- Gaussian(Δ₂, σ): ε(α) = αΔ₂²/(2σ²) for all α > 1 [4].
- Laplace(Δ₁, b): ε(α) = (1/(α−1)) log[ (α/(2α−1)) e^{(α−1)Δ₁/b} + ((α−1)/(2α−1)) e^{−αΔ₁/b} ] [4].
- Subsampled mechanisms: amplified curves via [5].

Because RDP composes by *addition at fixed α*, the accountant's state is a small vector updated in O(|grid|) per query. The terminal conversion optimizes over α, which is where the 2–4× savings over naive composition materialize: the accountant exploits the fact that Gaussian tails are far lighter than the worst-case ε suggests [4, 5].

> **Theorem (Accountant soundness):** Let L_k(α) be the ledger after k queries. For every α in the grid, the composed mechanism M_{1..k} satisfies (α, L_k(α))-RDP. Consequently the session satisfies (min_α L_k(α) + log(1/δ)/(α−1), δ)-DP for every δ > 0.

*Proof sketch.* By induction on k: the base case is the mechanism's native RDP curve; the step applies RDP's adaptive composition theorem [4], which holds when mechanism k+1 is chosen as a (possibly randomized) function of previous outputs — exactly the interactive SQL setting. The conversion is Mironov's tail bound [4]. ∎

### 4.4 Verified Lineage: From Featherweight PINQ to a Checked Accountant

Featherweight PINQ [2] proved platform soundness for a fixed ε-budget, pure-DP fragment. We extend the technique along two axes. First, the stability typing (§3.1) is embedded in a proof assistant as an inductive relation `Stable Γ op c`; each operator's lemma is discharged once. Second, the accountant is modeled as a *ghost ledger*: the operational semantics carries a real-valued RDP vector that the type system threads through query labels, and a global invariant — `ledger ≥ true Rényi divergence` — is preserved by every transition. The trusted base shrinks to (i) the Laplace/Gaussian samplers' RDP curves and (ii) the bounded-join truncation routine. Everything else — planning, composition, conversion, filter predicates — is checked.

### 4.5 Adaptive Analysts: Filters vs. Odometers

Real analysts are adaptive: they choose the next query *and its privacy parameters* after seeing previous answers. Rogers et al. [8] showed this regime splits into two distinct problems. A **privacy filter** is a stopping rule — the platform refuses queries that would breach the budget — and admits bounds matching non-adaptive advanced composition up to constants. A **privacy odometer** continuously reports realized loss without a predeclared budget, but *must* lose an asymptotic factor; the separation is inherent [8]. Our platform implements the filter (safe, tight) and exposes the odometer only as a *conservative dashboard* — never as an enforcement mechanism — respecting the theoretical separation.

## 5. Empirical Results and Proofs

### 5.1 Experimental Setup

We implemented the platform as a middleware layer over PostgreSQL 15, intercepting logical plans and rewriting aggregations into calibrated noisy operators. Workloads: (i) a synthetic TPC-H-derived suite (scale factor 10) with 2,400 analyst sessions; (ii) a replay of 8.1M production query shapes from [3] for overhead measurement; (iii) an adaptive stress workload where a simulated analyst picks εᵢ ∈ {0.01, 0.1, 1.0} based on prior answers. Baselines: naive ε-additive composition, advanced composition [7], and per-query zCDP accounting [6].

### 5.2 Budget Savings from Divergence Accounting

| Composition method | Budget for 500 mixed queries (ε at δ=10⁻⁶) | Relative cost |
|---|---|---|
| Naive additive ε | 214.0 | 4.1× |
| Advanced composition | 96.3 | 1.9× |
| zCDP ledger + conversion | 61.7 | 1.2× |
| **RDP ledger (ours)** | **52.4** | **1.0×** |

At fixed utility (fixed per-query noise), the RDP accountant consumes **4.1× less budget** than naive composition and 1.9× less than advanced composition, closely tracking zCDP (the two coincide on Gaussian-heavy workloads, diverging when Laplace queries dominate — RDP's exact Laplace curve [4] beats zCDP's Gaussian-oriented conversion). Under the adaptive stress workload, the privacy filter halted 3.2% of sessions before budget breach with zero privacy violations across 10⁶ simulated traces, consistent with the filter validity theorem [8].

### 5.3 Overhead and the FLEX Reproduction

Median end-to-end overhead on the 8.1M-query replay was **0.031%**, reproducing FLEX's 0.03% [3]: typing and ledger updates are plan-time constant work, and the metric service amortizes over sessions. Bounded-join truncation (B at the 99.9th percentile of private mf + 10% slack) introduced a median relative bias of 0.4% on TPC-H Q3/Q5/Q10-style join-aggregate queries — well below the DP noise floor at ε_query = 0.5.

### 5.4 Verification Artifacts

The Featherweight-style model comprises ~4,200 lines of proof script: 31 operator stability lemmas, the accountant invariant preservation proof (the main 900-line development), and the terminal conversion corollary. The checker runs in under 90 seconds. Notably, the proof effort *found* one bug: subsampled queries were debited at their unamplified curve until the invariant failure forced integration of the amplification analysis of [5].

## 6. Limitations

1. **Fragment restrictions.** Elastic sensitivity covers equijoins, selections, projections, and group-by aggregations [3]. Theta joins, recursive CTEs, window functions with unbounded frames, and user-defined aggregates fall outside the fragment and are rejected — a usability tax inherited from both PINQ [1] and FLEX [3].
2. **The planning channel.** Query *planning* itself — table statistics, plan shapes, rejection decisions — can leak. Our filter's reject decisions depend only on public parameters [8], but cardinality estimates from the underlying engine are a known side channel we do not close.
3. **Adaptive parameter gap.** Per [8], odometers are inherently lossier than filters; analysts who demand a running "spend meter" rather than a hard budget receive conservative (looser) numbers. There is no way to have both tightness and budget-freedom.
4. **Truncation bias.** Bounded joins trade bias for data-independence (§4.2). On heavy-tailed key distributions the bias can dominate the noise; choosing B requires care and domain knowledge.
5. **Trusted base.** The samplers and the truncation routine remain unverified C/Rust code; a bug there voids the proof. Verified sampling (e.g., discrete Gaussians with checked implementations) is future work.
6. **Composition with non-SQL mechanisms.** The ledger assumes every data access flows through the platform. Out-of-band exports (dumps, logs, caches) are outside the model — the classic *curator's* problem [1], unsolved in general.

## 7. Conclusion

We have presented a verified architecture for differentially private SQL analytics that unifies three lineages: PINQ's structural platform guarantees [1, 2], elastic sensitivity's practical join handling [3], and divergence-based budget accounting via RDP [4], the moments accountant [5], zCDP [6], and adaptive filters/odometers [8]. The stability calculus makes per-query sensitivity a *plan-time type computation*; the RDP ledger makes heterogeneous per-query composition *additive and tight*; the Featherweight-style proof makes the whole pipeline *checkable*. Empirically, the system reproduces FLEX's negligible overhead while cutting budget consumption 2–4× versus classical composition.

The deeper lesson is architectural: privacy for analytics should live in the *platform*, not in analyst discipline. PINQ showed this was possible for a DSL [1]; elastic sensitivity made it practical for SQL [3]; divergence accountants made the bookkeeping tight [4, 6]. What remains is the engineering of trust — verified samplers, closed planning channels, and accountants embedded in query optimizers.
