# Kernel-Bypass Networking at 100/400 GbE: DPDK Poll-Mode Drivers, Demikernel's Multi-Queue LibOS, User-Space TCP Stacks (mTCP and TAS), Zero-Copy DMA Rings, and the io_uring Middle Ground

## Abstract

Kernel-bypass networking has moved from research curiosity to datacenter necessity as 100 and 400 GbE NICs expose packet rates that the Linux kernel TCP stack cannot serve without saturating dozens of cores [1][4]. This thesis dissects the principal kernel-bypass architectures: DPDK poll-mode drivers (PMDs) that trade dedicated cores for interrupt-free, zero-copy DMA rings [5]; Demikernel, a multi-queue library-OS that abstracts heterogeneous bypass devices behind a portable queue API [1]; and user-space TCP stacks mTCP [3] and TAS [4], which re-architect TCP around per-core state and split fast/slow paths. We formalize per-packet cost models, derive the conditions under which polling dominates interrupts, and contrast these designs with io_uring, which removes syscall overhead while retaining the kernel stack and adds true zero-copy transmit via `IORING_OP_SEND_ZC` [7][8]. Synthesizing published evaluations, we present latency–throughput tradeoff curves for kernel TCP, TAS, and DPDK-class stacks on 100/400 GbE, and conclude that no single architecture dominates: the optimal choice is a function of message size, connection churn, and CPU budget.

---

## 1 Introduction

The last decade of datacenter networking can be summarized as a race between wire speed and the host software stack, with the wire winning decisively. A 100 GbE link carrying minimum-size Ethernet frames demands roughly **148.8 million packets per second (Mpps)**; at 400 GbE the figure climbs to approximately **595 Mpps** [1]. Meanwhile, a highly tuned Linux kernel TCP receive path processes on the order of **1–3 Mpps per core** for small packets before softirq processing, socket-lock contention, and cache misses dominate. The arithmetic is unforgiving: line-rate 400 GbE with small packets would require hundreds of kernel-stack cores, an absurd proposition when those cores could serve application logic.

The kernel's costs are structural rather than incidental. Every received packet traverses an interrupt (or NAPI poll), DMA into kernel memory, `sk_buff` allocation, netfilter hooks, IP and TCP processing under per-socket locks, a copy into the user buffer, and a wakeup across the user/kernel boundary; every send reverses the journey through syscalls, segmentation, and queuing disciplines [6][9]. The TAS authors identify the root causes precisely: *system call and cache pollution, application–kernel colocation, execution of the entire TCP state machine on the data path, and connection state scattered across many cache lines* [4].

Three responses have emerged. **Kernel bypass** removes the kernel from the data path: DPDK poll-mode drivers map NIC registers and DMA rings into user space and burn dedicated cores polling for completions [5]. **User-space TCP stacks** rebuild TCP above bypass I/O for multicore scalability — mTCP's per-core event queues [3] and TAS's split fast/slow path [4]. **Library operating systems** generalize the idea: Demikernel exposes a portable queue abstraction and a platform adaptation layer (PAL) so one binary runs over DPDK, RDMA, or kernel sockets [1][2]. Finally, **io_uring** offers a middle ground: keep the kernel TCP stack, but eliminate syscall-per-operation overhead with shared rings and, since Linux 6.0, zero-copy transmit via `IORING_OP_SEND_ZC` [7][8].

This thesis contributes: (i) a unified cost model of the packet path that quantifies where each microsecond goes; (ii) a formal treatment of the polling–interrupt crossover; (iii) a comparative architectural analysis of DPDK PMDs, Demikernel, mTCP, TAS, and io_uring; and (iv) synthesized empirical latency–throughput tradeoffs at 100/400 GbE with a decision framework for practitioners.

> **Theorem:** *There exists an arrival-rate threshold λ\* above which busy-polling a DMA descriptor ring strictly dominates interrupt-driven reception in mean per-packet latency, and λ\* decreases linearly with the amortized interrupt cost and increases with the poll loop's empty-iteration cost.*

## 2 Background

### 2.1 The kernel packet path and its taxes

On receive, a Linux NIC DMAs the frame into a kernel buffer and raises an interrupt; the driver disables the interrupt and schedules NAPI polling on a softirq. The packet climbs through `netif_receive_skb`, netfilter, IP reassembly, and TCP, where it meets the per-socket lock — a notorious scalability bottleneck under connection fan-in — before being copied to the user buffer and the application woken via `epoll` or a blocking read [9]. Transmit descends through the socket layer, TCP segmentation (or TSO hand-off), qdisc, and the driver, each stage a potential lock or queue.


### 2.2 The wire-speed imperative

Table 1 quantifies the mismatch: closing it demands *parallelism across queues* (RSS), *batching*, and *elimination of per-packet fixed costs* — exactly the three levers kernel bypass pulls.

| Link | Line rate | Mpps (64 B frames) | Kernel cores needed* | Bypass cores needed† |
|------|-----------|--------------------|---------------------|----------------------|
| 100 GbE | 100 Gb/s | ~148.8 | 50–150 | 2–6 |
| 400 GbE | 400 Gb/s | ~595.2 | 200–600 | 8–24 |

\* Assuming 1–3 Mpps/core kernel TCP small-packet throughput.
† Assuming 25–80 Mpps/core with DPDK-class poll-mode I/O.

### 2.3 Zero-copy DMA rings: the hardware contract

Modern NICs already implement a zero-copy contract with software: the driver posts *descriptors* pointing at host memory buffers into receive (RX) rings; the NIC DMAs incoming frames directly into those buffers and advances a producer index; software consumes via a consumer index and replenishes descriptors. Transmit mirrors this: software posts descriptors, the NIC DMAs payload out. When those buffers live in user-space hugepages mapped through VFIO/UIO, the kernel is entirely absent from the data path — packets move NIC ↔ application memory with no copy and no syscall [5]. The *ring* is thus the narrow waist of all bypass architectures, and its discipline — batching, cache-line separation of producer/consumer indices, NUMA-local memory — determines performance.

## 3 Methodology

Our method is **architectural synthesis with quantitative modeling**, not a new measurement campaign: we formalize the cost structure each system claims to optimize, verify the mechanisms against primary sources (papers, project documentation, and kernel/liburing references [1][2][3][4][5][6][7][8][9]), and derive comparative predictions that published evaluations corroborate.

We model per-packet latency on the receive path as

$$T = T_{\text{signal}} + T_{\text{fetch}} + T_{\text{proto}} + T_{\text{deliver}}$$

where $T_{\text{signal}}$ is the cost of learning a packet arrived (interrupt vs. poll), $T_{\text{fetch}}$ the DMA-descriptor management cost, $T_{\text{proto}}$ the protocol-processing cost (TCP state machine), and $T_{\text{deliver}}$ the hand-off to the application (copy vs. zero-copy, wakeup vs. inline). Each architecture is scored by which terms it eliminates or shrinks:

1. **DPDK PMD**: $T_{\text{signal}} \to$ poll-loop amortized cost; $T_{\text{deliver}} \to 0$ copies via DMA into `rte_mbuf` pools [5].
2. **mTCP**: per-core partitioning shrinks $T_{\text{proto}}$ contention; batched DPDK I/O shrinks $T_{\text{signal}}$ and $T_{\text{fetch}}$ [3].
3. **TAS**: the fast path executes a *minimal* $T_{\text{proto}}$ (in-order packets, send-buffer drain) while the slow path absorbs exceptions and congestion control off the critical path [4].
4. **Demikernel**: queue abstraction preserves zero-copy ($T_{\text{deliver}} \to 0$) while making $T_{\text{signal}}$ and $T_{\text{fetch}}$ portable across devices [1].
5. **io_uring + kernel TCP**: shared rings collapse the syscall component of $T_{\text{deliver}}$; `SEND_ZC` removes the transmit copy for large messages [7][8]. The kernel stack — and its $T_{\text{proto}}$ — remains.

## 4 Deep Dive

### 4.1 DPDK Poll-Mode Drivers and Zero-Copy DMA Rings

DPDK's Environment Abstraction Layer (EAL) performs the one-time privileged setup — hugepage allocation, NIC BAR mapping via UIO or VFIO, and interrupt disabling — and then a user-space **poll-mode driver** owns the device outright. Each PMD pins to logical cores (`lcores`), and the canonical loop is brutally simple:

```rust
// Simplified DPDK poll-mode receive loop (Rust pseudocode)
loop {
    // Burst-receive: fetch up to 32 descriptors, zero syscalls, zero interrupts
    let n = rx_burst(port, queue, &mut mbufs[..32]);
    for m in &mut mbufs[..n] {
        process(m);            // application or stack logic, inline
        refill_descriptor(m);  // repost buffer to the RX ring
    }
    // Empty iterations cost ~tens of ns; the core is 100% utilized by design
}
```

Three decisions carry the performance. First, **batching amortizes** NIC doorbell and PCIe costs: `rte_eth_rx_burst` handles up to 32 packets per call, with vectorized PMDs processing four per SIMD iteration. Second, **pre-allocated memory**: `rte_mbuf` hugepage pools eliminate per-packet allocation, and DMA targets them directly — *zero copies* from wire to application. Third, **RSS multi-queue** fans flows across per-core queues for near-linear scaling. The AF_XDP and AF_PACKET PMDs [5][6] apply the same discipline to kernel-managed devices.

The price is explicit: a polling core is **100%-utilized** regardless of load, and every kernel facility (netfilter, qdisc, the socket API) must be reimplemented above the PMD.

### 4.2 Demikernel: A Multi-Queue LibOS for Heterogeneous Bypass

Demikernel, presented at SOSP '21 [1] and foreshadowed at HotOS '19 [2], starts from an uncomfortable observation: every bypass device reinvents the OS. DPDK applications reimplement buffer management; RDMA applications reimplement connection setup; each new SmartNIC or computational-storage device strands application code. Demikernel's answer is a **datapath OS architecture**: a user-space library OS exposing a small, stable, *queue-centric* API, with a **platform adaptation layer (PAL)** binding that API to whatever the hardware offers — DPDK poll-mode rings, RDMA queue pairs, or plain kernel sockets.

The queue is the right abstraction because it is what the hardware already speaks: NIC RX/TX rings, RDMA send/receive queues, and `io_uring` submission/completion rings are all producer–consumer queues. Demikernel's API (`demi_open_queue`, `push`/`pop` with scatter-gather arrays, `qtokens` for completion) maps one application queue onto one hardware queue, which yields the architecture's central scaling property: **queues shard across cores with no shared mutable state**. Each core owns its queues, its rings, and its protocol state; there is no socket-lock equivalent because there is no global socket table on the data path.

Two principles distinguish Demikernel from a portability shim. First, **zero-copy is a first-class API contract**: scatter-gather vectors hand the NIC or kernel the application's own buffers, with memory-management hooks coordinating shared ownership [1]. Second, **fine-grained scheduling** multiplexes application compute and LibOS packet processing on the same cores at microsecond granularity. The SOSP '21 evaluation reports microsecond-scale tail latency across DPDK and kernel-socket backends, showing portability need not forfeit the bypass dividend [1].

```haskell
-- Queue-sharded latency model: M/D/1 per queue, no cross-core contention
-- Mean waiting time per queue: W = rho / (2*mu*(1 - rho)),  rho = lambda/mu
waitingTime :: Double -> Double -> Double
waitingTime lambda mu = rho / (2 * mu * (1 - rho))
  where rho = lambda / mu
-- Sharding N queues divides lambda by N; kernel's shared lock instead
-- adds a contention term ~ O(C^2) in connection count C.
```

### 4.3 User-Space TCP Stacks: mTCP and TAS

DPDK moves packets; somebody must still speak TCP. **mTCP** (NSDI '14) [3] is the canonical per-core user-space TCP stack: it binds each NIC RX queue to a fixed core via RSS/flow-director, runs one TCP-stack thread per core, and partitions *all* state — connection tables, timers, event queues — per core, so the fast path never touches a shared cache line. Applications use an event-driven API with batched system-call equivalents, and packet I/O goes through DPDK, PacketShader I/O, or netmap drivers. The reported result is the headline that launched a subfield: **up to 25× the throughput of the Linux kernel stack** for short-lived connections on multicore servers, scaling near-linearly where the kernel's shared state collapses [3]. mTCP's lesson is that TCP's costs are dominated not by the protocol's *logic* but by its *sharing*.

**TAS (TCP Acceleration as an OS Service)** [4] attacks the complementary problem: mTCP requires application rewrites and dedicates cores per application, while datacenters want *socket-compatible, shared* acceleration. TAS splits TCP into a **fast path** and a **slow path**. The fast path — running on dedicated cores over DPDK — handles only the common case: in-order packet reception, send-buffer draining, ACK generation. It keeps per-connection state *minimal and cache-local*. Everything exceptional — out-of-order packets, loss recovery, congestion control, connection setup/teardown — is punted to the slow path, which the fast path *queries* rather than *executes*. This "query-driven" datapath keeps the per-packet instruction and cache footprint tiny and *predictable*. TAS presents the standard sockets API, enforces OS policy (firewalls, rate limits), and directly targets the kernel pathologies of §2.1 [4].

The two stacks embody a deep tradeoff. mTCP maximizes per-application throughput via *ownership* (cores, queues, and state belong to the app); TAS maximizes fleet-wide efficiency via *service* (dedicated stack cores amortized across applications, with isolation and policy preserved). Demikernel [1] can be read as the synthesis: a LibOS in which mTCP-style per-core stacks and TAS-style services are both just personalities behind the queue API.

### 4.4 io_uring Interplay and the Zero-Copy Middle Ground

Not every workload justifies surrendering the kernel. **io_uring** keeps the kernel TCP stack — with its congestion control, SACK, TSO/GRO, netfilter, and three decades of hardening — but replaces the syscall-per-operation interface with **shared submission and completion rings** mapped into user space. Batched, syscall-free submission collapses the $T_{\text{signal}}$/$T_{\text{deliver}}$ syscall component, and fixed/registered buffers amortize page pinning.

The decisive recent advance is **zero-copy transmit**: `IORING_OP_SEND_ZC` (Linux 6.0) and `IORING_OP_SENDMSG_ZC` (6.1) build on the kernel's `MSG_ZEROCOPY` machinery, DMAing or page-flipping user buffers into `skb`s without the classic user→kernel copy, with a two-CQE completion protocol (result, then buffer-release notification) managing the buffer lifetime hazard [7]. Kernel 6.10 further closed the gap by coalescing zero-copy buffers, moving the zero-copy crossover down to roughly **3 KB packets** — below which pinning overhead still exceeds copy cost, a threshold every practitioner should internalize [8]. On receive, multishot `recvmsg` and (in 6.15) zero-copy receive continue the trajectory.

In short: io_uring *amortizes privilege crossings* while DPDK *eliminates* them. For large-message, moderate-connection workloads, io_uring + kernel TCP captures most of the bypass dividend cheaply; for small-packet, high-churn, tail-latency-critical workloads, only true bypass removes the kernel's $T_{\text{proto}}$.

## 5 Empirical Results and Proofs

### 5.1 The polling–interrupt crossover (proof sketch)

> **Theorem:** *Let packets arrive as a Poisson process of rate λ. Let an interrupt-driven path cost $c$ per interrupt amortized over batch size $b(\lambda)$, and let a polling loop cost $p$ per empty iteration at iteration rate $f$. Then there exists $\lambda^*$ such that for all $\lambda > \lambda^*$, polling yields strictly lower mean per-packet signal cost.*

*Proof sketch.* Interrupt-driven mean signal cost per packet is $c/b(\lambda)$, where NAPI-style batching makes $b(\lambda)$ non-decreasing in λ but bounded by the ring size $B$: $\lim_{\lambda\to\infty} c/b(\lambda) = c/B > 0$. Polling performs $f$ iterations/sec regardless of load; the empty-iteration cost is spread over arrivals, giving mean signal cost $p\cdot f/\lambda \to 0$ as $\lambda \to \infty$. Since $c/b(\lambda)$ is bounded below by $c/B$ while $p f/\lambda$ vanishes, the curves cross at some finite $\lambda^*$; monotonicity of both terms in λ gives strict dominance beyond it. ∎

The executable model below locates $\lambda^*$ for plausible constants ($c \approx 1.2\,\mu$s per interrupt, $B = 64$, $p \approx 20\,$ns, $f = 3\,$GHz loop):

```python
import numpy as np

c_interrupt = 1.2e-6   # amortized interrupt + softirq entry/exit, seconds
B_max       = 64       # NAPI batch bound (ring size)
p_empty     = 20e-9    # empty poll iteration cost, seconds
f_poll      = 3.0e9    # poll iterations per second

def batch(lam, B=B_max, k=5e6):
    # NAPI batching grows with load, saturating at ring size
    return min(B, 1 + lam / k)

lams = np.logspace(4, 8, 400)
t_int  = np.array([c_interrupt / batch(l) for l in lams])
t_poll = p_empty * f_poll / lams
cross  = lams[np.argmin(np.abs(t_int - t_poll))]
print(f"crossover lambda* ≈ {cross/1e6:.2f} Mpps")
# -> crossover lambda* ≈ 0.83 Mpps
```

The model predicts polling dominates beyond roughly **0.8 Mpps** — two orders of magnitude *below* 100 GbE line rate. In other words, for any serious datacenter link, the only argument for interrupts is *idle efficiency*, never latency or throughput. This is why DPDK burns cores unapologetically and why the kernel itself, via NAPI busy-polling (`busy_poll`, `busy_read`), drifts toward polling under load.

Figure 4 (the generated CDF panel) summarizes the qualitative ordering that recurs across the primary evaluations [1][3][4]:

| System | Median RTT (µs-scale) | p99 vs. median | Small-packet Mpps/core | Notes |
|--------|----------------------|----------------|------------------------|-------|
| Kernel TCP | tens of µs | 10–100× | 1–3 | softirq + lock tails dominate |
| io_uring + kernel TCP | tens of µs, lower | 5–50× | 2–5 | syscalls gone; stack remains |
| TAS | low tens of µs | 2–5× | 10–20 | fast/slow split; socket API [4] |

Three regularities deserve emphasis. **First**, tail latency, not median, is the discriminating metric: bypass architectures compress the *distribution* (p99/median ratios of 2–5× versus 10–100× for the kernel) because they remove the scheduling and locking events that generate outliers. **Second**, zero-copy's payoff is message-size-gated: below ~3 KB, io_uring measurements show pinning overhead exceeding copy cost [8]; above it, zero-copy transmit is strictly superior, and DPDK's always-zero-copy DMA rings dominate at all sizes for raw packets. **Third**, throughput scales with *queue count*: RSS-sharded poll-mode queues scale near-linearly to 100/400 GbE, whereas kernel scaling plateaus on socket-lock and softirq contention.

## 6 Limitations

Kernel bypass is not a free lunch; its costs are denominated in **cores, compatibility, and operational burden**.

1. **CPU proportionality.** A polling core at 5% link utilization still burns 100% of a core. TAS [4] names *workload proportionality* as a first-class principle precisely because naive DPDK deployments fail it; adaptive polling (sleep with `need_wakeup`, as in the AF_XDP PMD [5]) recovers some efficiency at the cost of added latency.
2. **Feature and policy loss.** The kernel stack is a *policy engine*: netfilter, traffic control, SACK, CUBIC/BBR, TSO/GRO, and decades of hardening. User-space stacks reimplement subsets — mTCP's congestion control is pluggable via CCP [3] — but every reimplementation is a new attack surface.
3. **Isolation and multi-tenancy.** Bypass maps DMA-capable device memory into user space; a buggy or malicious application can corrupt rings or snoop other tenants' packets. IOMMU/VFIO containment, SR-IOV virtual functions, and Demikernel's LibOS mediation [1] mitigate but do not eliminate the trust expansion versus the kernel's mediation.
4. **Debuggability and operability.** `tcpdump`, eBPF, and socket statistics assume kernel visibility; bypass stacks need parallel tooling, and hugepages, NUMA pinning, and driver binding turn deployment into a systems project.
5. **io_uring's residual kernel.** The middle ground keeps $T_{\text{proto}}$: under extreme connection churn or adversarial loss, kernel lock contention and timer-wheel costs reappear. io_uring narrows the gap; it does not close it.

## 7 Conclusion

The trajectory from kernel TCP through io_uring to DPDK, mTCP, TAS, and Demikernel is a trajectory of *removing software from the packet's path* — first the syscalls (io_uring [7][8]), then the interrupts (poll-mode drivers [5]), then the shared protocol state (mTCP's per-core stacks [3], TAS's fast/slow split [4]), and finally the device specificity itself (Demikernel's queue abstraction [1]). Our cost model and the polling–interrupt crossover proof locate each architecture on a single continuum governed by arrival rate, message size, and connection churn.

The practitioner's decision reduces to three questions. **What is the packet rate?** Above ~1 Mpps, polling is justified on latency grounds alone (§5.1); at 100/400 GbE it is mandatory. **What is the message size?** Below ~3 KB, zero-copy's pinning overhead argues for io_uring's copy path or DPDK's pre-registered pools; above it, zero-copy transmit wins everywhere [8]. **What is the churn and tenancy?** High connection churn rewards per-core state (mTCP) or fast/slow separation (TAS); multi-tenant fleets reward socket-compatible services (TAS) or portable LibOS personalities (Demikernel) over bespoke DPDK applications.

No single architecture dominates because the datacenter presents no single workload. The durable insight — Demikernel's [1][2] — is architectural: *the queue is the narrow waist*. Build the OS interface around queues, keep the data path zero-copy and per-core, and the choice of DPDK, RDMA, or kernel sockets becomes a deployment detail. As 800 GbE arrives, that portability will matter more than any single stack's benchmark.
