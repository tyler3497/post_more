# Crash-Safe File Systems by Construction: FSCQ's Crash Hoare Logic, Log-Based Atomicity, and the DFSCQ Concurrent Extension

## Abstract

This thesis studies crash-safe file systems by construction, centered on FSCQ — the first file system with a machine-checkable Coq proof that its implementation meets its specification even under fail-stop crashes. The key intellectual contribution is Crash Hoare Logic (CHL), which extends Hoare logic with crash conditions, recovery procedures, and namespaces that let developers specify disk states at multiple abstraction levels. We reconstruct FSCQ's verified architecture as a stack of certified layers — physical disk, write-ahead log, block allocator, block-level files, directories, and the file-system layer — where logging encapsulates crash atomicity so higher layers reason sequentially about transactions. We then examine DFSCQ, which scales the approach to a high-performance concurrent design with a precise fsync specification over tree sequences, group commit, and log-bypass writes. Finally, we contrast Coq-based proof with Yggdrasil's push-button crash refinement via SMT solvers, and survey the enduring gap between verified specifications and full POSIX semantics.

---

## 1. Introduction

File systems are the most bug-dense components of modern operating systems, and their bugs are the most consequential: a single ordering mistake in crash recovery can silently destroy user data. It took ext4 developers *six years* to realize that two individually reasonable optimizations — data writes that bypass the journal and checksumming of journal entries — could, taken together, disclose previously deleted data after a crash [4]. The moral endures: crash safety is a property of the *interaction* between optimizations, and no test suite covers the space of crash interleavings.

Testing finds crash bugs but cannot certify their absence; manual proof certifies absence only for idealized models with no formal connection to shipped code — as Ziegler observed of FSCQ's predecessors, "there is no file system that we can be sure represents what the proof is about" [1].

**FSCQ** (Chen, Ziegler, Chajed, Chlipala, Kaashoek, Zeldovich, SOSP 2015) broke this impasse: the first file system whose *executable implementation* carries a machine-checked Coq proof that it meets a *crash-inclusive* specification [1][2]. Its enabling invention is **Crash Hoare Logic (CHL)** — Hoare logic extended with *crash conditions*, *recovery procedures*, and *namespaces* for describing one disk at multiple abstraction levels. **DFSCQ** (SOSP 2017) then scaled the approach to a high-performance, concurrent file system with a precise, verified `fsync`/`fdatasync` specification [4], while **Yggdrasil** (OSDI 2016, Best Paper) showed that *crash refinement* makes verification amenable to fully automated SMT-based reasoning with no manual proofs [5].

This thesis reconstructs CHL's judgment forms and recovery specifications (§4.1), FSCQ's write-ahead logging protocol and its commit-bit optimization (§4.2), the seven-layer verified stack (§4.3), DFSCQ's concurrent extension with its metadata-prefix specification (§4.4), and the honest gap between verified specifications and POSIX (§6).

## 2. Background

### 2.1 Hoare logic and why crashes break it

Classical Hoare logic reasons about partial correctness with triples `{P} c {Q}`: if precondition `P` holds before command `c`, and `c` terminates, then postcondition `Q` holds after. But a file-system operation may be *interrupted at any instruction* by a crash, after which a *recovery procedure* runs and the system resumes from a state that is neither the precondition nor the postcondition. Standard Hoare logic has no vocabulary for "the set of disk states reachable if the power fails between instruction 3 and instruction 4." A crash introduces a non-deterministic choice at *every* program point, and recovery must be correct from *every* such point — a space no hand enumeration can cover. Capturing crash points *parametrically* is the central technical problem CHL solves.

### 2.2 Journaling and the write barrier contract

Crash-safe file systems in practice are almost all *journaling* file systems (ext3/ext4, NTFS, XFS): batch metadata updates into a transaction, write them to a *journal* first, then checkpoint them to home locations once the journal commit is durable. Recovery replays the journal. Correctness hinges on *ordering* — the commit must reach stable storage before checkpointed data — enforced with *write barriers* that drain the drive's volatile write cache.

Two recurring real-world bug classes: **missing barriers** (writes "without sufficient barriers" get reordered, exposing uninitialized metadata after a crash [1]) and **uninitialized structures** (un-zeroed directory blocks resurrect stale pointers).

### 2.3 The verification landscape before FSCQ

Three lines of prior work set the stage: **seL4** and **CompCert** proved full functional correctness (of a microkernel and a C compiler) but their specifications never mention crashes or persistent state; **eXplode** (OSDI 2006) systematically explored crash interleavings and found real bugs, but is inherently incomplete; and **crash-consistency models** (Bornholt et al., ASPLOS 2016) were specified and *checked*, not proved against an implementation. FSCQ's novelty is the conjunction: a *complete executable implementation*, a *crash-inclusive specification*, and a *machine-checked proof* connecting them [1][3].

## 3. Methodology

### 3.1 The Coq development and proof architecture

FSCQ is implemented *in Coq's Gallina language* — the same language as its proofs — and extracted to Haskell for execution as a user-space FUSE file system [1]. The proof assistant type-checks the proof *against the actual code*; there is no separate "model" that might drift from the implementation.

The development is organized around **CHL specifications at every layer boundary**. Each layer exports an abstract state and each procedure carries a CHL judgment; layer *N+1*'s proof may assume layer *N*'s specification but never its implementation — the "modular development" contribution that makes the proof effort tractable [1].

### 3.2 Anatomy of a CHL judgment

A CHL specification for a procedure `c` has four parts — precondition `P`, postcondition `Q`, crash condition `X` (disk states a crash *during* `c` may produce), and recovery spec `R` (valid from any state in `X`):

| Component | Role |
|---|---|
| Precondition `P` | Abstract state before `c` runs (in some namespace) |
| Postcondition `Q` | Abstract state after `c` completes without crashing |
| Crash condition `X` | Set of disk states a crash *during* `c` may produce |
| Recovery spec `R` | Specification of recovery, valid from any state satisfying `X` |

> **Theorem 1 (CHL soundness, informal).** *If every procedure satisfies its CHL specification, then for any sequence of crashes interleaved with execution, running the recovery procedure after each crash restores a state satisfying the top-level invariant, and every completed system call appears either fully applied or fully absent.*

The flagship instance is the file-system-call atomicity theorem:

> **Theorem 2 (FSCQ syscall atomicity).** *After recovery, either all disk writes from a file system call are on disk, or none are. A crash can never leave a system call half-applied.* [1]

### 3.3 Namespaces: one disk, many descriptions

The log layer sees "log region + data region"; the file layer sees "each file is a list of blocks"; the directory layer sees a tree. **Namespaces** let one CHL judgment relate these views: a file-system-layer crash condition is stated in terms of *trees*, the log layer's in terms of *blocks*, with a verified *refinement* connecting them. Without namespaces, every layer's proof would reason about raw disk blocks, destroying modularity.

### 3.4 The recovery obligation

Every layer defines a `recover` procedure, and every layer's crash condition must imply the *precondition* of the layer below's recovery. Recovery is itself a verified stack — disk recovery, then log recovery, then file-system recovery — each re-establishing its layer's invariant for the layer above. A crash *during* recovery is covered too: recovery procedures are specified to be idempotent with respect to their own crash conditions.

## 4. Deep Dive

### 4.1 The Formal Core of Crash Hoare Logic

Traditional Hoare logic's sequence rule is:

```
{P} c1 {Q}    {Q} c2 {R}
-------------------------
     {P} c1; c2 {R}
```

CHL extends each triple with a crash condition and threads a *recovery* specification through composition: `{P} c {Q} [X / R]` means `c` takes `P` to `Q` normally, but a crash at any point yields a state in `X`, from which recovery `R` restores the invariant. The sequence rule must handle crashes inside `c1` (recover, then run `c2` from the recovered state), crashes inside `c2`, and crashes during recovery itself.

The programmer writes the crash condition *once per procedure*; CHL's rules *compute* compound crash conditions from the parts — just as Hoare logic computes postconditions. Consider the log layer's `log_write`:

```coq
(* Simplified CHL spec of a transactional block write *)
Spec log_write (a : addr) (v : block) :
  PRE  (log_state ↦ LogIdle ∧ disk !! a ↦ _)
  POST (log_state ↦ LogTxn (a ↦ v))
  CRASH (∃ s, log_state ↦ s ∧ (* crash may lose the volatile txn buffer *)
         disk = old_disk ∨ disk = apply_partial_txn old_disk s)
  RECOVERY log_recover : {CRASH} ~> {log_state ↦ LogIdle ∧ disk ∈ {old_disk, committed}}
```

The crash condition says: the volatile in-memory transaction buffer is lost, and the on-disk state is either the pre-transaction disk or a *partially applied* transaction. Recovery then collapses that disjunction to a clean either/or — the atomicity the layers above depend on. Crucially, higher layers never learn how many disk writes `log_write` performs, where the log region lives, or what a commit bit is; they see only the transactional abstraction. This information hiding let the FSCQ team merge the log's length field and commit bit to eliminate a barrier by changing only ~50 lines of code and ~100 lines of proof, with upper layers untouched [1].

CHL also models *asynchronous* disk writes: FSCQ's disk model exposes `dsync` explicitly, so crash conditions quantify over all disk states consistent with issued-but-unsynced writes.

### 4.2 Write-Ahead Logging: Atomicity Through the Commit Bit

FSCQ's log layer implements classical write-ahead logging with one crucial decision: **the log length field doubles as the commit bit**.

1. **Buffer.** `log_begin` opens a transaction; `log_write(a, v)` records `(a, v)` pairs in a volatile buffer.
2. **Persist entries.** `log_commit` writes buffered blocks to the on-disk log region, then a barrier.
3. **Commit.** One disk write sets the header length to nonzero. *This is the commit point*: before it, a crash means "no transaction"; after it, "committed."
4. **Apply.** Logged blocks are copied to home locations, then a barrier.
5. **Truncate.** Length reset to zero; the log region is freed.

Recovery: if the length field is nonzero, replay the log region to home locations and truncate; else do nothing.

```python
def log_recover(disk):
    """Verified recovery: idempotent, correct from any crash point."""
    hdr = disk.read(LOG_HEADER)
    if hdr.length != 0:                       # committed txn present
        for i in range(hdr.length):
            entry = disk.read(LOG_DATA + i)   # (addr, block) pair
            disk.write(entry.addr, entry.data)  # replay to home location
        disk.barrier()
        hdr.length = 0
        disk.write(LOG_HEADER, hdr)           # truncate
        disk.barrier()
    # else: nothing to do -- txn never committed
```

The subtlety the proof must discharge is the *torn commit*: a crash *during* the commit write itself. FSCQ's disk model assumes atomic sector writes (see §6), so the length field is either old (zero) or new (nonzero): the commit is one atomic step in the model, and the crash condition is a clean disjunction. The earlier design used a *separate* commit bit requiring an extra barrier between writing the length and the commit bit; merging them eliminated that barrier, with the modular proof architecture absorbing the change locally [1].

Whether the crash lands during entry writes (length still 0, so nothing is replayed), during the atomic commit write (length 0 or N), during apply (replay completes it), during truncate, or even during recovery itself, every case is an instance of the single crash condition `disk ∈ {old_disk, apply_partial_txn old_disk s}`. The proof never enumerates crash points — which is exactly why CHL's parametric crash conditions scale where case analysis cannot.

### 4.3 The Verified Stack: From Disk Blocks to System Calls

FSCQ's implementation is a tower of seven verified layers, each exposing only its CHL specification to the layer above:

| Layer | Abstract view | Key responsibility |
|---|---|---|
| `Disk` | Array of 4 KB sectors, `dsync` barrier op | Atomic sector writes; volatile vs. durable distinction |
| `Log` | Transactional block device (`begin`/`write`/`commit`) | Crash atomicity of multi-block updates |
| `Balloc` | Bitmap allocator over block ranges | Allocate/free with no double-allocate after crash |
| `BFile` | Each file = list of blocks | Grow/shrink files inside transactions |
| `Dir` | Directories as special files mapping names to inodes | Directory entry atomicity |
| `DirTree` | Hierarchical tree of files and directories | Path resolution, tree invariant |
| `FS` | POSIX-like syscalls (`create`, `write`, `rename`, …) | Each syscall runs in one transaction |

The discipline is strict: `BFile` calls `Balloc` for data blocks but reasons only about its *specification* ("allocated blocks are distinct; freed blocks reusable after commit"). `DirTree` builds the hierarchy, allocating inodes through `Balloc`. Finally, `FS` implements every system call *inside a single log transaction* — which is exactly Theorem 2: log-layer transaction atomicity plus one-transaction-per-syscall yields crash-atomic syscalls, with no per-syscall crash reasoning.

The buffer cache (~300 lines of proof in the log layer, ~600 above) re-established the write-through invariant without changing any layer's *specification*: a verified optimization invisible to clients [1][8].

> **Theorem 3 (End-to-end crash safety).** *For any sequence of crashes and reboots, FSCQ's recovery restores the file system to the state of the last completed transaction; no committed data is lost and no uncommitted data is visible.* [1][2]

### 4.4 DFSCQ: Concurrency, Log Bypass, and the Metadata-Prefix Specification

FSCQ's simplicity was a deliberate proof-engineering choice, but every syscall is a fully synchronous transaction and the implementation is single-threaded. **DFSCQ** (SOSP 2017) asks whether CHL-style verification survives a *fast* file system — group commit, concurrent syscalls, log-bypass writes — and answers affirmatively [4].

**The specification problem.** `fsync` has subtle semantics: on Linux, `fsync` on one file also persists *metadata* changes to other files made before the `fsync` began. DFSCQ captures this with a **metadata-prefix specification** over **tree sequences**: the logical state is a *sequence* of trees (snapshots), and after a crash the recovered tree must be a *prefix* of the pre-crash sequence with respect to metadata — a suffix of recent operations may be lost, but what survives is a consistent prefix, never a torn mixture. This mirrors ext4's observable behavior while staying precise enough to prove against.

**The optimization problem.** DFSCQ verifies three optimizations FSCQ lacks:

1. **Group commit** — concurrent transactions batched into one journal commit, amortizing barrier cost.
2. **Log-bypass writes** — file *data* blocks written directly to home locations, bypassing the journal (metadata only) — the optimization implicated in ext4's six-year bug.
3. **Journal checksumming** — entries carry checksums so recovery detects torn writes.

The ext4 disaster is the cautionary tale: log-bypass data writes plus journal checksums *together* disclosed previously deleted file contents after a crash, because a stale data block could be misread as part of a new file [4]. DFSCQ's proof *rules out this class of interaction bug* — the metadata-prefix specification constrains the data/metadata combinations reachable after recovery, and the machine-checked proof covers all interleavings of bypass writes, checksums, and crashes. The bugs that matter live in the optimizations; DFSCQ verifies the optimizations.

**The concurrency problem.** DFSCQ supports concurrent operations with fine-grained locking. Its proof extends CHL with concurrency-aware reasoning: each layer's operations are specified as *atomic actions* on shared abstract state, so threads verify independently and compose. Crash conditions now cover "a crash at any program point *of any thread*," with recovery restoring the invariant from the interleaved state. DFSCQ is the first file system with a machine-checked crash-safety proof for a concurrent, optimizing implementation against a precise `fsync` specification [4].

## 5. Empirical Results and Formal Proofs

### 5.1 What was proved, and at what cost

FSCQ's Coq development spans tens of thousands of lines of specification and proof — the proof dwarfs the implementation. It buys three theorems no testing regime provides: per-layer CHL correctness, syscall atomicity (Theorem 2), and end-to-end crash safety (Theorem 3), all checked by Coq's kernel against the extracted code [1][3]. DFSCQ's proof is larger still: the tree-sequence model, the metadata-prefix property, and concurrent composition each add obligations FSCQ's synchronous design avoids. Its central claim is qualitative but strong: the *first* file system with (a) a precise `fsync`/`fdatasync` specification and (b) a machine-checked proof the implementation meets it [4].

### 5.2 Performance: usable, then competitive

FSCQ runs as a user-space FUSE file system (after Haskell extraction) and, despite its deliberately simple design, runs real Unix applications — including mail-server-like workloads — with usable performance [1]. DFSCQ closes the remaining gap: group commit and log bypass target the throughput regime of ext4-style journaling file systems, showing verification need not tax performance relative to unverified peers [4].

### 5.3 The push-button alternative: Yggdrasil

Yggdrasil (Sigurbjarnarson, Bornholt, Torlak, Wang, OSDI 2016, Best Paper) replaces interactive proof with **crash refinement**: the set of disk states the implementation can produce — *including* crash and reordering states — must be a subset of what the specification allows [5]. Crash refinement is decidable by SMT solvers (Z3): given a specification, an implementation, and consistency invariants, Yggdrasil either verifies the code or emits a *concrete counterexample trace* of writes, flushes, and a crash.

The results are striking for essentially zero manual proof effort:

- Yggdrasil verified **Yxv6** (journaling, modeled on xv6/ext3) and **YminLFS** (minimal log-structured FS).
- It *found two real bugs* in YminLFS — counterexample traces made them immediately diagnosable.
- Its greedy flush optimizer removed three of five disk flushes from YminLFS's `mknod` within three minutes *while preserving the verified guarantee* [6].

| System | Method | Manual proof | Concurrency | Crash spec style | Executable |
|---|---|---|---|---|---|
| FSCQ (2015) | CHL in Coq | Large | No | Crash conditions + recovery | Yes (FUSE) |
| DFSCQ (2017) | CHL + concurrency in Coq | Larger | Yes | Metadata-prefix over tree sequences | Yes |
| Yggdrasil/Yxv6 (2016) | Crash refinement via SMT | None | No (single-threaded) | State-set inclusion | Yes (via Cython) |
| DaisyNFS (2022) | Sequential reasoning for concurrent crash-safe NFS | Large | Yes (NFS server) | Crash refinement over a verified journal | Yes |

Later work continues both lines: **DaisyNFS** (Chajed et al., OSDI 2022) verifies a concurrent crash-safe NFS server via sequential reasoning over a verified journal, and **SquirrelFS** encodes crash-consistency rules in Rust's type system [7].

## 6. Limitations

What the theorems do *not* cover:

1. **The POSIX gap.** FSCQ implements a *subset* of POSIX-like calls: no `mmap`, no verified treatment of the `fsync` ordering subtleties Linux applications depend on (DFSCQ narrows but does not close this gap), no hard-link races or permission-check TOCTOU. Verified specifications are *simpler and stricter* than POSIX — what makes them provable limits drop-in compatibility.
2. **The disk model.** Sector writes are atomic, barriers are honored, and the disk never corrupts data silently — but real drives have lied about barriers, which would void the theorems.
3. **The trusted computing base.** Coq's kernel, Haskell extraction, the GHC runtime, and the FUSE glue are unverified. Small relative to the file system, but nonzero.
4. **Proof economics.** Person-years of expert interactive-theorem-proving effort — a cost few projects can bear. Yggdrasil attacks this directly, at the price of a weaker guarantee (SMT-decidable invariants, single-threaded code) [5].
5. **Failure-model scope.** Fail-stop crashes only: no Byzantine faults, no network partitions, no operator error, no bugs *above* the verified stack.

These limitations do not diminish the results; they delimit them. The theorems are conditional, but the conditions are *explicit* — more than can be said for the implicit assumptions of any tested-but-unverified file system.

---

## 7. Conclusion

The arc from FSCQ to DFSCQ to Yggdrasil is the arc of the field: from *can we prove it at all*, to *can we prove the fast version*, to *can we prove it cheaply*. The POSIX gap remains the open frontier — a fully verified, fully POSIX-compatible, high-performance file system does not yet exist. But the theorems, once checked, stay checked: unlike test suites, proofs do not rot.
