# Formal Semantics of Rust Async/Await: Generator Resumption, Pin Invariants, Waker Contract Soundness, and Executor Fairness under Miri's Stacked Borrows

## Abstract

Rust's `async`/`await` lowers asynchronous control flow to coroutine state machines whose resume protocol is governed by `Future::poll`. This thesis develops a small-step operational semantics for that lowering: `async fn` bodies compile to generators with yield points as suspension states, `Pin<&mut Self>` invariants preserve self-referential borrows across resumptions, the `Waker` vtable contract carries a soundness and liveness obligation to the executor, and work-stealing executors layer cooperative fairness budgets on top. We formalize the Pin projection rules distinguishing structural from non-structural pinning, characterize when `wake_by_ref` may replace `wake`, and prove that poll-once-per-wake plus a bounded poll budget yields starvation-free scheduling under fair wake delivery. Miri's Stacked Borrows model validates the aliasing claims, showing how pointer tags, borrow stacks, and protectors interact with intrusive task lists of the kind Tokio uses. We close by mapping the limits: poll-after-`Ready`, executor-defined fairness, and the unresolved `Resume`-argument design space that once motivated moving `Context` off thread-local storage.

## 1 Introduction

Rust's futures are *lazy*, unlike the "hot future" model of C# and JavaScript: an `async fn` returns immediately, evaluating nothing, and progress occurs only when an executor actively polls the resulting value [1]. Cancellation is mere value dropping; combinator structure is ordinary ownership; and the compiler's desugaring of `async` blocks to generator-like state machines is the load-bearing bridge between surface syntax and the `Future` trait.

The thesis argues that three intertwined invariants make this design sound: **(1) the generator invariant** — every `await` is a yield point of a coroutine whose resume argument carries the polling context, and the `!Unpin` state machine must never move while holding cross-yield borrows; **(2) the pin invariant** — `Pin<&mut T>` pins the value, structural pinning decomposes the guarantee fieldwise, and the projection contract governs `unsafe` re-pinning; **(3) the waker invariant** — `Poll::Pending` transfers a liveness obligation to the executor, and the task deadlocks if no reachable `Waker` clone fires.

Beyond the single future, the *executor* imposes its own semantics — ready queues, work stealing, and cooperative budgets — which interact with the per-future contract. A soundness argument that stops at `Future` is therefore incomplete: we must reason about the joint system, and about how the borrow checker and Miri's aliasing model constrain the `unsafe` machinery underneath.

Our contribution is a unified operational treatment. Section 2 fixes notation and prior art; Section 3 presents the method; Section 4 develops the four deep dives (generator lowering, Pin projections, waker lifecycle, executor fairness); Section 5 states theorems with proof sketches and reports Miri experiments; Section 6 is honest about what the model does not cover; Section 7 concludes.

## 2 Background

### 2.1 The `Future` trait and the poll contract

The primitive is small:

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

`poll` may return `Poll::Ready(output)` exactly once, after which the future must not be polled again — a protocol the type system does not enforce but executors and combinators rely upon. `Poll::Pending` suspends the future; the contract demands that the future arrange for `cx.waker()` to be woken when progress becomes possible [5]. Note the asymmetry: readiness is *pulled* by the executor, wakeup is *pushed* by the resource. The entire runtime is a reactor-pattern loop over this boundary.

### 2.2 RFC 2394: async/await as generators

RFC 2394 defines `async fn` as returning `impl Future<Output = T>` where the body compiles to a state machine with one state per await point [1]. The RFC is explicit about the pinning strategy: async futures do *not* implement `Unpin`, so moving them out of a `Pin` is `unsafe`; this is what permits borrows across await points. The RFC also anticipates the generator connection — async generators yielding values rather than completing with them — and notes that eager "hot" execution was rejected precisely because laziness makes cancellation-as-drop work [1].

### 2.3 Generators with resume arguments

The `Generator` trait in its RFC-2229/2230-era form was:

```rust
fn resume(self: Pin<&mut Self>, args: Self::Resume)
    -> GeneratorState<Self::Yield, Self::Return>;
```

The resume-args design [4] exists to thread the `Context` into a resumed generator without thread-local storage: `GenFuture::poll` would call `gen.resume(NonNull::from(cx).cast())` instead of stashing `cx` in TLS. The `await!` desugaring then becomes a loop that fetches the most recent context, polls the pinned inner future with it, and on `Pending` yields — pausing the *outer* generator so the *outer* waker is what the resource wakes. This is the precise mechanism by which context propagates down nested awaits without global state.

### 2.4 Pin, projections, and structural pinning

`Pin<P>` is a wrapper whose API contract guarantees the pointee is not moved *after* it has been pinned, provided `T: !Unpin`. The fundamental operations are:

- `Pin::new(&mut T) -> Pin<&mut T>` — safe only when `T: Unpin`.
- `Pin::new_unchecked` — `unsafe`, discharges the pin contract on the caller.
- `Pin::get_mut` — moves out, allowed when `T: Unpin` or for shared pins.

**Structural pinning** refines this: a field is structurally pinned if pinning the parent pins the field. `pin_project` generates projections `Pin<&mut Field>` exactly for structurally-pinned fields, preserving the invariant by construction. A non-structurally-pinned field may only be accessed via `&mut` after `Unpin` is established — the famous footgun where implementing `Unpin` for a self-referential struct silently legitimizes moves that invalidate interior borrows.

### 2.5 Stacked Borrows and Miri

Stacked Borrows [2][3] is the aliasing model operationalized in Miri. Every pointer carries a *tag*; every location carries a *borrow stack* of items, each with a permission (`Unique`, `SharedReadWrite`, `SharedReadOnly`, `Disabled`) and an optional *protector* tied to a call frame. Reads and writes "retag" and pop incompatible items; violating a protected item is undefined behavior. The model is what makes statements like "reborrowing a `Pin<&mut Self>` inside `poll` invalidates the waker clone derived from a previous borrow" *checkable* rather than merely philosophical [7].

### 2.6 Executors, work stealing, and cooperative budgets

Executors maintain ready and wait queues; the reactor (epoll/kqueue/IOCP) turns OS events into `Waker::wake` calls that re-enqueue tasks [5]. Tokio's multi-threaded scheduler gives each worker a local run queue and steals when idle — good for locality, demanding care for fairness [6]. Tokio further imposes a *cooperative scheduling budget*: a task that polls too many times without yielding is forcibly descheduled, bounding the damage of a greedy task. Yielding (`tokio::task::yield_now`) is a hint, not a strict ordering guarantee — the runtime may re-poll the same task first [6].

## 3 Methodology

We proceed in three registers: **(1) operational semantics** — a small-step abstract machine $\langle S, q, \rho \rangle$ (coroutine state, pending-wake flags, borrow-stack environment) with `RESUME`, `YIELD(Pending)`, `RETURN(Ready)`, and `WAKE` transitions, letting us state the pin invariant as a preservation property; **(2) contract analysis** — the three contracts as pre/postconditions on `poll`; **(3) empirical validation** — the key `unsafe` patterns (intrusive task lists, waker vtables, reborrow chains) run under Miri with Stacked Borrows, reproducing failures reported in the wild [7]. Our theorems are paper-proof sketches, not mechanized proofs (see [2] for the mechanized model).

## 4 Deep Dive

### 4.1 Generator lowering: from `await` to state machines

Consider:

```rust
async fn fetch_twice() -> (Data, Data) {
    let a = get().await;   // yield point Y1
    let b = get().await;   // yield point Y2
    (a, b)
}
```

The compiler produces, schematically, an enum `__FetchTwice { Start, Y1 { fut: GetFut, ... }, Y2 { fut: GetFut, a: Data }, Done }` plus a `poll` that matches on the discriminant. The crucial semantic points:

- **The future's locals live in the state machine.** The borrow `&a` across `Y2` is a borrow *into the generator's own storage*. Moving the generator would move `a` and invalidate any outstanding reference — hence `!Unpin` [1].
- **Nested awaits delegate.** `a = get().await` desugars (in the resume-args formulation [4]) to a loop: pin the inner future, `poll` it with the *most recent* context, and on `Pending` `yield` — suspending the outer generator. The outer generator's *caller* (ultimately the executor) holds the waker that the inner resource will fire. Context flows *down* the await chain; wakeups flow *up* from the resource to whichever waker the leaf registered.
- **Drop is cancellation.** Dropping the state machine runs field destructors in reverse declaration order. No protocol message is sent; the resource's waker simply becomes a dead handle whose `wake` is a no-op. This is why `wake` must be safe to call on abandoned tasks: the vtable's `wake` implementation owns an `Arc<Task>` (or weak variant) and checks liveness internally.

> **Theorem:** (Resume-argument soundness.) If every generator in an await chain forwards the most recent `Context` pointer as its `Resume` argument, then the `Waker` observed by any leaf resource belongs to the executor frame that will re-poll the root future.

*Proof sketch.* By induction on the await-nesting depth. Base: `GenFuture::poll` passes its own `cx` as the resume argument [4]. Step: the `await!` loop polls the child with the context recovered from the last yield, which by the induction hypothesis is the root's context; on `Pending` the parent yields, preserving the association between suspension and context. ∎

The historical TLS alternative (`set_task_context`) makes this property ambient rather than explicit, with reentrancy hazards under nested executors; resume arguments make the data flow visible to the borrow checker and to Miri.

### 4.2 Pin invariants: projections and the structural/non-structural divide

The pin contract, stated operationally: once `Pin<&mut T>` has been dereferenced to `&mut T` (via `get_unchecked_mut`) or projected, the `T` must not be moved for the remainder of the region in which any such derived reference is live. In Stacked Borrows terms, pinning *protects* the location against moves — but moves in Rust are not memory accesses, so the model captures this only indirectly through the references derived from the pinned pointer. The real enforcement is a *social* contract on `unsafe` code, which is why the distinction below matters so much.

**Structural pinning.** Given:

```rust
#[pin_project]
struct Timeout<Fut> {
    #[pin] future: Fut,
    #[pin] delay: Delay,
}
```

the generated projection is:

```rust
fn project(self: Pin<&mut Self>) -> TimeoutProj<'_> {
    // for #[pin] fields: Pin<&mut Fut>, Pin<&mut Delay>
}
```

Because `Pin<&mut Timeout>` guarantees the `Timeout` is not moved, each `#[pin]` field is likewise not moved, so handing out `Pin<&mut Fut>` is sound. The invariant is *compositional*: the proof obligation for the struct reduces to the obligation for each pinned field.

**Non-structural pinning** is the dangerous case. A field without `#[pin]` may be projected only to `&mut Field`, and only when the projection method can prove the field is never self-referenced across a suspension. The classic soundness bug pattern [7]:

```rust
// UNSOUND if Self is !Unpin and field borrows across await:
let this = self.get_unchecked_mut();  // &mut Self from Pin<&mut Self>
let ptr = &mut this.buf as *mut _;    // raw pointer derived from reborrow
```

Under Stacked Borrows, the second `get_unchecked_mut` (or any fresh `&mut` reborrow) *retags*, popping the borrow stack and invalidating `ptr`. Miri flags exactly this: "not granting access to tag … because that would remove [SharedReadOnly …] which is strongly protected" [7]. The waker path is the production-grade instance: an intrusive task list stores a raw pointer to the task node; each `poll` reborrows `Pin<&mut Task>`; the stored pointer must be derived from an `UnsafeCell`-protected or otherwise aliasing-tolerant provenance, or Miri reports UB. Tokio's intrusive linked lists carry precisely this burden — the linked-list node is *inside* the pinned task allocation, and list manipulation must not invalidate the task's own borrow stack entries.

> **Theorem:** (Projection soundness.) If `T` is pinned and every projection of a field `f` through `Pin<&mut T>` yields either `Pin<&mut F>` (when `f` is structurally pinned) or `&mut F` under a proof that no reference into `f` is live across a suspension point, then no move of `T` or `f` is observable by safe code.

*Proof sketch.* By case analysis on projections. Structural case: the pin guarantee on `T` transitively pins `f`; `Pin<&mut F>` operations preserve it. Non-structural case: the side condition ensures no outstanding borrow can observe a move; any move is therefore observationally equivalent to no move within the abstract machine. ∎

The `Unpin` auto-trait is the escape hatch to audit: `impl Unpin` for a self-referential generator future is a soundness hole the trait solver cannot see, since the cross-yield borrow hides in the state machine's discriminant-indexed layout.

### 4.3 The waker contract: vtables, `wake_by_ref`, and liveness

A `Waker` is a fat pointer to a vtable:

```rust
pub struct RawWaker {
    data: *const (),
    vtable: &'static RawWakerVTable,
}
pub struct RawWakerVTable {
    clone: unsafe fn(*const ()) -> RawWaker,
    wake: unsafe fn(*const ()),
    wake_by_ref: unsafe fn(*const ()),
    drop: unsafe fn(*const ()),
}
```

**The soundness half** of the contract governs construction: `RawWaker::new(data, vtable)` is `unsafe` because the implementor must guarantee that `data` remains valid for the vtable's lifetime discipline (typically reference-counted), that `clone`/`drop` maintain the count, and that `wake`/`wake_by_ref` never dangle. `Waker::from(Arc<Task>)` via the `ArcWake` pattern discharges this by tying `data` to an `Arc` whose clone/drop are the vtable's clone/drop.

**The liveness half** governs use: if `poll` returns `Pending`, the future *must* ensure that a clone of `cx.waker()` is woken when progress is possible; otherwise the task never re-polls and the program deadlocks [5]. Note the subtlety: the obligation attaches to *some clone reachable by the resource*, not to the exact `Waker` value passed in — executors routinely replace the waker between polls (the `AtomicWaker` pattern), and only the latest registration is live.

`wake_by_ref(&self)` vs `wake(self)`: the former avoids consuming the `Waker`, which matters in hot paths where re-cloning per poll is measurable. Soundness-wise they are equivalent provided the vtable's `wake_by_ref` does not assume ownership. A frequent micro-optimization — calling `wake_by_ref` and then returning `Pending` — is sound *only if* the wake is not the sole registration mechanism; waking the *current* task's waker unconditionally causes a busy-loop (the bug in the first `Delay` iteration in Tokio's tutorial [5]), because the executor will immediately re-poll a task that has made no progress.

> **Theorem:** (Wake-then-pending liveness.) Let $F$ be a future whose `poll` returns `Pending` only after registering a waker clone $w$ with a resource $R$, and suppose $R$ wakes $w$ whenever the awaited condition transitions false→true. Then the executor re-polls $F$ after every such transition, provided the executor polls every woken task at least once before dropping it.

*Proof sketch.* Registration establishes the channel $R \to \text{executor}$ labeled by $w$. The transition fires `wake`, enqueuing the task. Executor fairness (Section 4.4) guarantees the queued task is polled. If the condition still holds, `poll` returns `Ready`; otherwise it re-registers and the invariant is restored. ∎

Spurious wakes are explicitly permitted: waking without progress is always safe (it only costs a poll), while failing to wake on progress is always a bug. This asymmetry is why `AtomicWaker::wake` is idempotent and why executors tolerate duplicate queue entries.

### 4.4 Executor fairness: queues, stealing, and budgets

The executor closes the loop with three obligations: **poll every ready task** (queue liveness), **never poll a completed task** (`Ready`-once), and **bound consecutive polls per task** (fairness). Tokio implements the third via a cooperative budget of poll tokens — exhaustion forces a yield [6] — and the first via work stealing, with idempotent wake-enqueueing giving weak fairness: *every wake eventually causes a poll*.

The interaction with the per-future contract is the subtle part. A future that returns `Pending` *without* registering a waker violates liveness no matter how fair the executor is. Conversely, a future that busy-`wake_by_ref`s defeats the budget: each wake re-enqueues, each poll consumes budget, and the task burns its budget spinning. The budget is thus not merely a performance feature — it is the executor's *defense* against a task that weaponizes the waker contract, converting a potential livelock into bounded waste.

```rust
// Cooperative fairness, executor-side sketch
loop {
    while let Some(task) = worker.local_queue.pop().or_else(|| steal()) {
        task.budget = BUDGET;                       // e.g. 128 poll tokens
        match task.poll() {
            PollOutcome::Ready => { /* drop task */ }
            PollOutcome::PendingNoBudget => worker.global_queue.push(task),
            PollOutcome::Pending => { /* waker registered; park task */ }
        }
    }
}
```

Under Miri, the executor's intrusive queues are the aliasing stress test: nodes are `*mut Task` raw pointers manipulated while `Pin<&mut Task>` borrows are live elsewhere. The sound pattern routes all list mutation through the allocation's `UnsafeCell` or re-derives pointers from a single owning provenance per critical section — the same discipline [7] demands of any pinned intrusive structure.

## 5 Empirical Results and Proofs

### 5.1 Proof summary

We proved (sketches in §4): **resume-argument soundness** (context reaches the leaf), **projection soundness** (structural pinning composes), and **wake-then-pending liveness** (registered wakes cause re-polls). The joint corollary:

> **Corollary:** (End-to-end progress.) Under the three contracts plus weakly-fair wake delivery, every future whose awaited conditions eventually hold is polled to `Ready`. Each failed hypothesis yields a known bug class: wrong-context wakes, use-after-move of `!Unpin` futures, and lost wakeups (`Pending` without registration).

### 5.2 Miri experiments

We wrote targeted test programs exercising each contract and ran them under Miri with Stacked Borrows:

1. **Pin reborrow invalidation.** A raw pointer derived from `get_unchecked_mut`, then reborrowed on the next `poll`: Miri reports a protector violation on the stale tag — the shape of the failure in [7]. Re-deriving per poll (or via `UnsafeCell`) passes.
2. **Intrusive waker list.** An `AtomicWaker`-like cell manipulated via raw pointers while pinned: passes only when all accesses share one `UnsafeCell` provenance; a second `&mut` path fails — intrusive structures must centralize aliasing authority.
3. **Waker vtable refcounting.** An `Arc<Task>`-backed `RawWaker`: passes with balanced clone/drop; a double-drop is caught as use-after-free — the vtable `unsafe` contract is load-bearing.
4. **Spurious-wake tolerance.** Waking tasks without progress: no UB, tasks converge — confirming the permitted direction of the wake asymmetry.

We additionally note the Tree Borrows migration: several patterns accepted under Stacked Borrows (notably certain `SharedReadWrite` protector interactions) are rejected or accepted differently under Tree Borrows; executor authors should test under both models, since the language's eventual aliasing model is still being selected.

## 6 Limitations

1. **Poll-after-`Ready`/drop is out of model.** Our machine halts at `Ready`; double-poll bugs need fused wrappers, which our theorems do not cover.
2. **Fairness is executor-defined.** Weak fairness of wake delivery is an executor *assumption*, not a `Future` property — a `block_on` that never yields to a reactor thread satisfies our per-future theorems while deadlocking on cross-task wakeups.
3. **The `Resume` type is unstable design space.** Resume arguments [4] were never stabilized; current rustc threads `Context` through desugared `poll` opaquely rather than via a public `Generator::Resume` type.
4. **Stacked Borrows is not the final model.** Tree Borrows differs in acceptance; our Miri results are model-relative [2][3].
5. **No mechanization.** Proof sketches are not machine-checked; full formalization would embed the borrow-stack environment in a proof assistant [2].
6. **`Send`/`Sync` assumed.** Single-threaded executors throughout; cross-thread wake adds a happens-before dimension abstracted as fair delivery.

---

## 7 Conclusion

Rust's async/await rests on an unusually explicit contract stack: generators lowered to state machines, `Pin` preserving self-referential borrows across yields, wakers carrying a liveness obligation from resource to executor, and schedulers bounding greed with budgets and stealing. We gave this stack an operational semantics, proved the three core contract theorems and their end-to-end composition, and validated the aliasing discipline under Miri's Stacked Borrows — including the intrusive-list patterns that real executors like Tokio depend on. The practical takeaways: forward contexts explicitly [4]; project pins structurally; never return `Pending` without a registered waker; treat `wake_by_ref` as a hot-path tool, not a progress signal; and test every `unsafe` executor structure under Miri under both borrow models.
