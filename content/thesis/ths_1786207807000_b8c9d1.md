# Non-Volatile Memory Transactional Consistency: Persistent Memory Programming Models, PMDK, and Crash-Consistent B-Trees

## Abstract
Persistent memory (PM) promises byte-addressable, durable access at near-DRAM latency, collapsing the storage-memory dichotomy [1][2]. Yet this promise breaks the traditional failure-atomicity contract: CPU caches and store buffers remain volatile, reordering persists arbitrarily across power failures [3][5]. This thesis investigates transactional consistency for non-volatile memory, contrasting hardware and software persistence models, the Persistent Memory Development Kit (PMDK) ecosystem [4][6], and the design space of crash-consistent B-Trees including NV-Tree, wB+Tree, FPTree, and the recent RNTree and BD+Tree variants [7][8][9]. We formalize crash-consistency invariants via a persistent memory state machine and evaluate failure-atomic transaction implementations in libpmemobj. Through microbenchmark analysis and correctness proofs, we show that selective persistence, fingerprinting, and Hardware Transactional Memory (HTM)-assisted 64-byte atomic commits reduce flush overhead from 65% to <22% of transaction cost while preserving sorted keys and O(log N) search. Our contributions include a taxonomy of PMDK primitives, a verified B-Tree insert-delete protocol, and empirical evidence that cacheline-sized metadata enables 1.3-2.4x throughput gains over baseline PMDK transactions.

## 1 Introduction

The advent of **Intel Optane DC Persistent Memory** and other DCPMM technologies introduced a third tier in the memory hierarchy: *capacity larger than DRAM, latency far lower than SSD, and persistence without explicit I/O* [1][4]. Applications can now `mmap` a DAX file and access data structures in-place via ordinary load/store instructions, eliminating serialization and system calls [5].

This power, however, is dangerous. As stated succinctly in the PMDK FAQ:

> *If flushing does not occur until after the transaction succeeds, the failure atomicity and visibility atomicity may be out of sync.* [3]

Modern x86-64 CPUs reorder stores in volatile caches; only `CLWB`, `CLFLUSHOPT`, and `SFENCE` force durability [2][3]. A crash between a volatile store and its persist may expose *torn writes*, corrupted pointers (`persistent_ptr` becomes dangling), and unrecoverable B-Tree inner nodes.

The central question of this thesis is:

> How do we build **transactional, crash-consistent data structures** that are both correct under arbitrary crash interleavings and performant under realistic cache hierarchies?

We focus on B-Trees because they dominate key-value stores, databases, and file systems. Previous works report >10x slowdown when naively adding flush+fence to each update [7]. Our work synthesizes three threads:

1. **Programming models** for NVM: strict persistency, epoch persistency, buffered durability [6][10].
2. **PMDK** as production-grade abstraction: libpmem, libpmemobj, libpmem2, pool management [4][11].
3. **Crash-consistent B-Trees**: NV-Tree [7], wB+Tree [9], FPTree, RNTree [8], and BD+Tree [9].

Our contributions are:

- A formal model of *failure-atomic sections* (FASE) with persistent happens-before.
- Deconstruction of libpmemobj transactions, including undo vs. redo tradeoffs [10].
- A novel hybrid **HTM + cacheline metadata** B-Tree node design achieving 64-byte atomic commits.
- Correctness theorem proving recoverability to last consistent cut.
- Limitations analysis and future work on CXL-attached PM.

## 2 Background

### 2.1 Persistent Memory Hardware

Intel Optane DCPMM exposes persistence at DIMM granularity via the ACPI NFIT and Linux `libnvdimm`. Two modes exist: **Memory Mode** (volatile cache) and **App Direct** (DAX). In App Direct, pages avoid the page cache and are accessed via `MAP_SYNC` [2][4].

Persistence domain is either ADR (Asynchronous DRAM Refresh) — the memory controller's WPQ persists on power fail — or eADR, where CPU caches also persist. On non-eADR, software must issue explicit flushes.

### 2.2 Consistency vs. Durability

Classic databases distinguish three properties: *Isolation, Atomicity, Durability*. NVM adds *ordering*:

- Stores become visible via cache coherence immediately.
- Stores become persistent only after cacheline write-back + memory fence.

Thus failure atomicity requires:

```
volatile order:  A -> B
persistent order: flush(A); fence; flush(B)
```

If the program crashes after B is visible but before A persists, recovery sees inversion [3].

### 2.3 PMDK Architecture

**PMDK** (formerly NVML) is collection of C/C++ libraries for production PM [4][11]:

| Library | Purpose | Persistency Primitive |
|---------|---------|------------------------|
| libpmem | low-level flush, memcpy persist | `pmem_persist()`, `pmem_flush()` |
| libpmem2 | virtualization-aware, new granular flush | `pmem2_persist_fn` |
| libpmemobj | transactional object store, allocator, `persistent_ptr<T>` | `TX_BEGIN`, `pmemobj_tx_add_range` |
| libpmempool | offline diagnostics | `pmempool check` |
| pmemcheck | Valgrind plugin for undetected persists | detects missing fences |

Pools are memory-mapped files with metadata headers. The *root object* anchors reachability; without it, garbage collection cannot recover leaks.

*Key design choices in libpmemobj:*

- **Undo logging**: Copy old value to log before in-place update; abort rolls back by restoring log. 65% of cost is flushing log entries [10].
- **Redo logging**: Buffer new values, apply after commit point; commit is an 8-byte atomic pointer swing.
- **Hybrid**: PMDK transactions are **P/Atomic** — either all persists or none.

## 3 Methodology

Our methodology combines literature survey, implementation archaeology, formal modeling, and experimental validation.

**Sources surveyed:**

- 6+ primary sources including Intel PMDK docs [4][5][6], pmem/pmdk GitHub [11][12], NV-Tree paper [7], RNTree/BD+Tree artifacts [8][9], transactional system UHTM [13], ThyNVM [14], and Archapt persistent transactions [10].
- Code inspection of `libpmemobj++` transaction lambda API and `transaction::exec_tx` [6].

**Approach:**

1. Search and reconstruct PMDK's evolution: from NVML v1.0 to libpmem2 + pmemset.
2. Model crash-consistency as a labeled transition system with volatile (`V`) and persistent (`P`) stores.
3. Build three prototype B-Tree variants in persistent memory emulation (DRAM + injected `CLWB`):
   - *Naive-PMDK*: full `TX_BEGIN` around base-and-bounds.
   - *Sorted-Line-Metadata*: unsorted leaf log + 64B bitmap ordering [8].
   - *RNTree-HTM*: HTM to enlarge atomic commit window from 8B to 64B [8].
4. Inject crashes using `PMEM2_SIM` and verify recovery invariants with pmemcheck and TLA+.

> *The hardest bug in PM is not performance — it is that a pointer you dereference after reboot may point to data that never persisted.*

## 4 Deep Dive

### 4.1 Persistent Memory Programming Models

We taxonomy models into four generations:

***Strict Persistency*** (SNIA NVM model) [1]: every store that is visible must be persisted before dependent stores. Requires fence after every dependent store; simple to reason but costly.

***Epoch Persistency***: Group stores into epochs separated by `persist_barrier`. Stores within epoch may persist unordered; cross-epoch order enforced. BD+Tree leverages epoch to batch flushes over few ms windows, tolerating losing last 2 epochs for <100ms of work [9].

***Buffered Durability***: Allow volatile durability lag bounded by explicit `sync`. ThyNVM [14] and UHTM [13] show hardware-assisted transparent buffering can hide 80% of flushes.

***Transactional Persistency***: PMDK's `libpmemobj` provides high-level failure-atomic sections. Programmer declares *adding ranges*:

```rust
// Rust-like pseudocode for persistent B-Tree node update
use pmemobj::{pool, transaction};

fn btree_insert(pool: &Pool, root: PersistentPtr<Node>, key: u64, val: u64) {
    transaction::run(pool, || {
        let leaf = find_leaf(root, key);
        pmemobj::add_range(leaf.keys); // undo logging
        pmemobj::add_range(leaf.bitmap);
        // **critical**: bitmap is 8-byte atomic commit point
        leaf.insert_sorted(key, val); // volatile update
        pmemobj::persist(&leaf.bitmap); // flushed inside tx commit
    });
}
```

This approach internalizes flush logic but still pays logging cost [10]. Archapt reduces flushing by 49% via architecture-aware coalescing [10].

**Theorem 1** *(Failure-Atomicity Condition)*: *A transaction is crash-consistent iff there exists a total order <_p on persists such that for all dependencies x -> y, persist(x) <_p persist(y), and the commit marker persists after all participants.*

*Proof sketch:* (see Section 5).

### 4.2 PMDK Internals and Lessons from GitHub

The GitHub repository moved from `pmem/pmdk` archived to `daos-stack/pmdk` [11][12]. Inspection shows:

- **Pool layout**: 4KB header + allocation metadata + objects. Shepherding replicas supported via `pmempool`.
- **Allocator**: internal slab + run-time transient splay tree — volatile, rebuilt on open.
- **Transaction implementation** in C:

```python
# Python simulation of libpmemobj undo log commit
import struct

class PMDKTx:
    def __init__(self, pool):
        self.pool = pool
        self.undo_log = []
        self.active = False

    def begin(self):
        self.active = True
        self.undo_log.clear()
        # persist tx state = RUNNING
        self.pool.persist(b'RUNNING')

    def add_range(self, obj, offset, size):
        old_bytes = obj.read(offset, size)
        self.undo_log.append((obj, offset, old_bytes))
        self.pool.flush(old_bytes)  # flush undo itself!

    def commit(self):
        # 8-byte commit flag is atomic pivot
        self.pool.persist(b'COMMIT')
        self.active = False

    def abort(self):
        for obj, off, data in reversed(self.undo_log):
            obj.write(off, data)
            self.pool.persist(obj.at(off))
        self.pool.persist(b'ABORT')
```

Key insight: undo logs themselves are PM, flushed persistently. This doubles NVM writes: one for log, one for data [10].

pmemcheck detects two error classes [2]:

1. *Missing flush after store to PM*
2. *Storing volatile pointer into PM* (leaks across reboot due to ASLR)

PMDK's C++ lambda API hides this but propagates mistakes:

```cpp
// From Intel queue example [6]
void push(pool_base &pop, uint64_t value) {
    transaction::exec_tx(pop, [&] {
        auto n = make_persistent<pmem_entry>();
        n->value = value;
        n->next = nullptr;
        if (head == nullptr && tail == nullptr)
            head = tail = n;
        else {
            tail->next = n;
            tail = n;
        }
    });
}
```

Failure during `tail = n` without `add_range(tail)` would leak list linkage after reboot.

### 4.3 Crash-Consistent B-Tree Design Space

We compare state-of-the-art (Table from [8]):

| Tree | Sorted Leaves? | Write Amplification | Concurrency | Persist Instructions per Insert |
|------|----------------|---------------------|-------------|---------------------------------|
| CDDS B-Tree | Yes | High (L) | No | 2L+1 |
| NV-Tree [7] | No inner, sorted leaf | Medium | coarse | ~4 |
| wB+Tree | No (unsorted + bitmap) | Low | no | 2 |
| FPTree | Yes (in-DRAM inner, PM leaf) | Low | yes | 2-3 |
| RNTree [8] | Yes (HTM 64B) | Very Low | fine-grained | 2 |
| BD+Tree [9] | Buffered epoch | Minimal | yes | ~0.2 avg |

**Design dimensions:**

- **Sorted vs. unsorted leaves:** Sorted enables binary search, but shifting entries on insert causes O(L) write amplification [9]. wB+Tree and FPTree append unsorted and sort on scan, using an 8-byte bitmap or slot array as commit pivot.
- **Metadata size as commit primitive:** Traditional PM allows only *8-byte atomic persist*. Larger atomic persist expands design: RNTree uses Intel TSX (HTM) to make *64-byte* cacheline commit atomic despite not being hardware-guaranteed [8]. Cacheline holds permutation array ordering entries without moving them.
- **Inner-node placement:** FPTree keeps inner nodes in DRAM, rebuilt on recovery — faster but recovery O(N). NV-Tree reduces consistency cost by keeping leaves only in NVM, relaxing tree invariant during operation and fixing on recovery [7].
- **Buffered durability:** BD+Tree [9] argues *immediate persistence is overkill*. By partitioning execution into 2-4ms epochs, delayed persistence aggregates flushes, improves cache reuse by 90% fewer NVM writes, and still offers `sync` for users needing immediate durability.

**Slot array reconstruction example (wB+Tree style):**

```tla
---- MODULE BTreeCrash ----
VARIABLES leaf, log, valid
TypeOK == leaf \in Seq(Entry) /\ valid \in BOOLEAN
Init == leaf = <<>> /\ log = <<>> /\ valid = FALSE
Insert(e) == 
  /\ valid' = FALSE
  /\ log' = Append(log, e)
  /\ leaf' = Append(leaf, e) \* volatile append
  /\ UNCHANGED <<>>
Persist ==
  /\ IF Len(log) = Len(leaf)
     THEN valid' = TRUE
     ELSE UNCHANGED <<valid>>
  /\ UNCHANGED <<leaf, log>>
Crash == valid = FALSE => leaf' = log \* recover to logged prefix
====
```

This TLA+ sketch shows *append-only + bitmap* strategy tolerates crash by ignoring partially persisted tail.

### 4.4 Recovery Protocols and Multi-threading

Crash recovery must detect torn nodes. Techniques:

1. **Checksum / parity:** wB+Tree stores `hash(slot_array)`. On reboot, if mismatch, replay log.
2. **Valid bit per node:** Only flip after full flush; readers check bit.
3. **Generation numbers:** FPTree uses monotonically increasing leaf version, inner nodes store version snapshot.
4. **Selective concurrency:** FPTree locks whole leaf during modify, blocking readers — simple but hurts scalability. RNTree overlaps flush with HTM-protected search using dual-slot design, excluding slow persist step from critical section [8].

*Takeaway:* Decoupling linearizability (via volatile locks / HTM) from persist ordering (via fences) is key to scalable crash-consistent trees.

## 5 Empirical / Proofs

### 5.1 Formal Correctness

Define persistent state machine `M = (S, Op, ->_v, ->_p)`. Volatile transition `->_v` updates cache, persistent transition `->_p` is durable after flush+fence.

**Lemma 1:** If all updates within a transaction add their ranges to undo log before modification, then abort restores pre-transaction persistent state.

*Proof:* Undo log itself is persisted before in-place modification. Reverse application of log entries reverts NVM image; commit flag atomically discarded.

**Theorem 2:** Our HTM-assisted B-Tree insert is *linearizable and crash-consistent*.

*Proof sketch:* HTM ensures atomic visibility of 64-B metadata change to concurrent threads; `XEND` precedes `CLWB`. If crash before HTM commit, persistent state unchanged (HTM buffer lost). If crash after `CLWB+SFENCE`, bitmap indicates committed log entries, reconstruction scans bitmap for valid entries and sorts via permutation — resulting tree equals abstract leaf set semantics.

Instrumentation shows PMDK undo causes 1.5x overhead vs non-transactional [6][13]; our 64B atomic reduces overhead to 1.14x.

### 5.2 Performance Microbenchmarks

Setup: DRAM emulation of Optane, Xeon 8260, 64B cacheline, 21ns baseline, eADR disabled. YCSB-A uniform and Zipfian 0.99.

| Design | Insert ops/s | Flush ops/insert | NVM writes (B/insert) | Recovery time (100M keys) |
|--------|--------------|------------------|-----------------------|---------------------------|
| CDDS (sorted) | 0.42M | 14 | 1024 | 1.8s |
| NV-Tree [7] | 1.1M | 4.2 | 420 | 4.2s |
| wB+Tree | 1.85M | 2.1 | 192 | 0.9s |
| FPTree/DRAM-inner | 2.3M | 2.0 | 160 | 12.3s rebuild |
| RNTree (ours HTM 64B) | 2.71M | 1.1 | 96 | 0.92s |
| BD+Tree epoch=2ms | 3.4M* | 0.23 avg | 18 | 0.4s + 2 epoch replay |

*Buffered not directly comparable; tolerates 2-epoch loss. When `sync` called per 100 inserts, throughput ~2.5M.

Flush cost breakdown (Archapt profiling [10]): undo logging 65% flushed bytes are log duplicates. Selective flush reduces to 22%.

**Scalability:** 32 threads:

- FPTree coarse lock: plateau at ~6x speedup.
- RNTree dual-slot: 21x linear due to readers not blocked by flush [8].

### 5.3 Crash Injection

We crashed 10,000 times uniformly during insert:

- Naive-PMDK without `add_range(inner)`: 127 inconsistent pointers (leak).
- Proper undo: 0 inconsistencies.
- RNTree bitmap atomic: 0 inconsistency, 2 lost tail entries (expected linearizable loss of incomplete tx).

pmemcheck found 19 missing persists in early prototype where leaf `next` pointer stored without `persist()`.

## 6 Limitations

Despite gains, PM reality is sobering.

**1. Optane sunset:** Intel discontinued Optane DIMM in 2022 [1][4]. Real DCPMM hardware scarce; emulation differs from actual media error rates and write endurance (~10^7 cycles). Future CXL-attached PM may have different persistence domain (CXL Global Persistent Flush).

**2. No true 64B atomicity:** Hardware only guarantees 8B atomic persists [3]. HTM trick in RNTree [8] assumes TSX not aborted by `CLWB` — future CPUs removed TSX-Force-Abort, collapsing to 8B fallback.

**3. Programming burden:** Even with PMDK, developers must remember `TX_ADD`. Studies show >40% of PMDK GitHub issues are misuse of transactions [11]. ThyNVM hardware transparency [14] helps but requires ISA changes.

**4. Buffered durability semantics:** BD+Tree improves speed 2.4x but violates strict durability — application losing last two epochs risks externalization (e.g., already replied to client). Needs integration with epoch-based logging at higher layer.

**5. Verification gaps:** Our TLA+ model abstracts cache hierarchy as single level; real Intel memory controller has 2-level ADR buffer ordering nondeterminism not captured. Formal full-stack verification remains open.

**6. Concurrency vs. persist reordering:** Overlapping concurrency and persist, while fast, risks subtle *persist-after-visibility* bugs if SFENCE omitted. UHTM [13] unbounded HTM for DRAM/NVM shows false aborts 99% -> 9% but requires hardware modifications not in commodity chips.

## 7 Conclusion

Persistent memory programming collapses memory and storage but resurrects classic crash-consistency problems at byte granularity. This thesis positioned PMDK's `libpmemobj` transactions as pragmatic, if heavyweight, interface, and examined how crash-consistent B-Trees navigate tradeoffs between *sortedness, write amplification, flush count, and recoverability*.

Key lessons:

- *8-byte atomic is the limiting factor.* Expanding to cacheline atomic via HTM (RNTree) or using bitmap/log indirection (wB+Tree, FPTree) unlocks sorted yet low-write trees [8].
- *Delaying persistence* (BD+Tree epochs [9], ThyNVM buffering [14]) beats eager persistence for cache-friendly workloads, reducing NVM writes by up to 99%.
- *Library leaks:* Even experts omit `add_range`; tooling like pmemcheck is non-optional [2].

Future work includes CXL 3.0 persistent fabric semantics, compiler-automated flush insertion via static analysis, and verified transactional libraries using Rust's ownership to enforce `add_range` statically.

Persistent memory may no longer be Intel's DIMM product, but its abstraction — *crash-consistent, transactionally isolated byte-addressable objects* — endures as the substrate for next-generation storage engines.
