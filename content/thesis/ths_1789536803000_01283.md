# Oblivious RAM with Path ORAM and Circuit ORAM: Stash Overflow Bounds, Recursive Position Maps, and Oblivious Data Structures for Secure Processors and Encrypted Databases

## Abstract

Oblivious RAM (ORAM) conceals not only the *content* of memory accesses but also the *pattern* of access itself, defeating adversaries who observe addresses, timing of bus transactions, or cloud storage request sequences. This thesis presents a unified treatment of tree-based ORAM: the Path ORAM protocol, a rigorous analysis of its stash-overflow probability, recursion techniques that compress the client position map to constant size, and Circuit ORAM, which reduces eviction to a metadata scan requiring only constant client memory. We prove the exponential stash tail bound, characterize background eviction as a termination-channel-safe remedy for secure processors, and show how recursive position maps trade a logarithmic bandwidth factor for near-constant client state. We then lift raw ORAM into oblivious data structures — AVL trees, maps, and B+ trees — and evaluate them in encrypted databases and trusted-processor prototypes. A comparative bandwidth analysis situates Path ORAM, Circuit ORAM, Flat ORAM, and TaoStore against the Goldreich-Ostrovsky lower bound. We close with open problems in asynchronous distributed ORAM, write-only constructions, and crash-consistent persistent memory.

## 1 Introduction

Memory access patterns leak secrets. A server observing that two encrypted database queries touch the same row, or an adversary probing a processor's memory bus observing which cache lines are fetched, learns the *control flow* of the computation even when all data is encrypted [3]. Oblivious RAM, introduced by Goldreich and Ostrovsky, is the canonical countermeasure: a protocol between a trusted client and an untrusted server that simulates an arbitrary RAM program while making the sequence of physical accesses computationally independent of the logical access pattern [3].

> **Definition:** An ORAM is *secure* if for any two logical access sequences of equal length, the distributions of the resulting physical access transcripts are computationally indistinguishable to a polynomial-time adversary.

Early constructions — the square-root ORAM and the hierarchical scheme — paid polylogarithmic bandwidth overhead and were complex to implement. The tree-based revolution began with Path ORAM, an "extremely simple" protocol that reads and writes a single root-to-leaf path per access, remaps the accessed block to a fresh random leaf, and relies on a small client-side *stash* to absorb overflow [1][2]. Its elegance made it the substrate for secure processors, encrypted databases, and asynchronous multi-user stores [7][8][9].

This thesis makes four contributions:

1. **A self-contained exposition of Path ORAM**, including the block-path invariant and the greedy deepest-bucket write-back.
2. **A proof sketch of the exponential stash-overflow bound**, with extensions to shared stashes under recursion and background eviction [2][8][10].
3. **A treatment of Circuit ORAM**, which achieves constant client memory by replacing Path ORAM's stash-driven eviction with a single deterministic metadata scan [5].
4. **Oblivious data structures over ORAM**, covering the recursive-ORAM optimizations of Wang et al. and their deployment in encrypted query engines [4][6].

The remainder is organized as follows. Section 2 surveys ORAM foundations. Section 3 develops the Path ORAM methodology. Section 4 dives into the four technical pillars. Section 5 presents bandwidth comparisons and formal proof sketches. Section 6 discusses limitations, and Section 7 concludes.

## 2 Background

### 2.1 The Goldreich-Ostrovsky model

An ORAM simulates a RAM with *N* blocks on an untrusted server. The client holds a secret key and small trusted memory. Each logical operation `read(a)` or `write(a, v)` is translated into a randomized sequence of encrypted physical block transfers. Security demands that the physical transcript reveal nothing about the logical sequence beyond its length; Goldreich and Ostrovsky further proved an **Omega(log N)** bandwidth lower bound for statistically secure ORAM with constant client storage [3].

Two classical designs preceded tree-based schemes. The *square-root* ORAM shelters recently accessed blocks and periodically reshuffles. The *hierarchical* ORAM maintains geometrically growing levels, each reshuffled after a bounded number of accesses. Both achieve polylogarithmic overhead but involve intricate oblivious sorting and dummy traffic, motivating the simpler tree-based designs that follow.

### 2.2 Tree-based ORAM

In tree-based ORAM, the server stores a binary tree of *buckets*, each holding up to *Z* encrypted blocks. A client-side *position map* associates every logical block with a leaf label (a path from root to leaf). The core invariant, stated precisely for Path ORAM, is:

> **Lemma:** At all times, if block *a* is mapped to leaf *s*, then *a* resides either somewhere on path *s* or in the client stash.

On access, the client reads the entire path *s*, services the request from path plus stash, assigns *a* a fresh uniform leaf *s'*, and writes back along path *s*, greedily pushing stash blocks as deep as possible while respecting their own leaf assignments. Because the remapped leaf is uniform and independent of history, consecutive accesses to the same logical block touch independent random paths — this is the *unlinkability* property that yields security [1][10].

### 2.3 Adversary models

We distinguish the *honest-but-curious* cloud server (observes transcripts, never deviates) from the *active bus adversary* of secure processors (observes DRAM addresses and can measure timing). Definitions for secure processors refine ORAM security to handle termination channels and require that background eviction strategies not leak through program halting behavior [10]. Write-only ORAM relaxes the model further: when reads are served from a trusted cache, only write patterns need obfuscation, enabling far cheaper constructions such as Flat ORAM [8].

## 3 Methodology

### 3.1 Path ORAM access procedure

Let *L* denote the tree height, so the tree has 2^L leaves and 2^(L+1) - 1 buckets. Each bucket stores *Z* blocks; *Z = 4* is standard for practical instantiations with background eviction, while the original analysis targeted *Z = 5* [1][8]. The client stores the position map and a stash. The `Access(op, a, data)` routine proceeds as follows:

1. **Lookup.** Fetch leaf label *s* for block *a* from the position map; sample a fresh uniform leaf *s'* and update the map.
2. **Read path.** Download all buckets on path *s*, decrypt, and merge real blocks into the stash.
3. **Serve.** If *op* is a read, return block *a* from the stash; if a write, update its contents.
4. **Evict.** Greedily reinsert stash blocks onto path *s*: each block is placed at the deepest bucket on *s* that still lies on the path to its own assigned leaf. Re-encrypt all buckets, padding with encrypted dummies, and write the path back.

> **Theorem:** Path ORAM with bucket size *Z = 5* and stash capacity *R* fails (stash overflow) with probability at most *(1/4) 0.6^R* after any sequence of accesses, for sufficiently large *N* [2].

The proof couples the real process to an idealized infinite-capacity ORAM, bounds subtree overflow via a moment-generating-function argument, and applies stochastic dominance over the worst-case address pattern (each address accessed exactly once) [2].

### 3.2 Recursion for the position map

Storing the full position map costs *O(N)* client memory. Recursion stores the map itself in a smaller ORAM: ORam_0 holds data blocks, the position map of ORam_i is stored in ORam_{i+1}, and the client keeps only the tiny map for the topmost level [1]. With position-map block size *chi log N*, each level shrinks by a factor of at least *chi* (requiring *chi* at least 2), so *O(log N)* levels suffice and the bandwidth multiplies by the recursion depth. A shared stash across all levels remains *O(log N)* times a super-constant function with high probability [2].

### 3.3 Circuit ORAM eviction

Path ORAM's eviction needs the stash to scan and reorder blocks — *O(log N)* client memory. Circuit ORAM replaces this with a **deterministic two-pass metadata scan** over the accessed path: the client reads only block *headers* (addresses and leaf labels), computes the deepest legal bucket for each block with constant working memory, and then performs the data movement in a second pass [5]. With bucket size 2, Circuit ORAM achieves optimal circuit complexity for *O(1)* client memory, making it the scheme of choice for hardware ORAM controllers and trusted-execution environments [5].

### 3.4 Building oblivious data structures

Wang et al. showed that data structures over recursive ORAM admit crucial optimizations: because position-map lookups at different recursion levels touch independent trees, batched and pipelined access patterns can share stash state and reduce constant factors [4]. ObliDB specialized B+ tree indexes over Path ORAM for SQL-style range queries inside SGX enclaves, outperforming naive ORAM translations of database operators by up to an order of magnitude [6].

The following Python sketch captures the Path ORAM access skeleton used in our reference implementation:

```python
import secrets

class PathORAM:
    def __init__(self, n_leaves: int, z: int):
        self.L = n_leaves.bit_length()
        self.Z = z
        self.tree = {}          # (level, idx) -> list of encrypted blocks
        self.pos = {}           # block addr -> leaf label
        self.stash = []         # client-side overflow buffer

    def access(self, op: str, addr: int, data=None):
        s = self.pos.get(addr, secrets.randbelow(1 << self.L))
        self.pos[addr] = secrets.randbelow(1 << self.L)  # fresh remap
        path = self._read_path(s)                        # decrypt buckets
        self.stash.extend(b for b in path if b.is_real)
        blk = next(b for b in self.stash if b.addr == addr)
        if op == "write":
            blk.payload = data
        result = blk.payload if op == "read" else None
        self._evict_greedy(s)                            # deepest legal bucket
        return result
```

And the corresponding eviction core in Rust, as it appears in hardware-oriented controllers:

```rust
/// Greedy deepest-bucket eviction along path `s` using only the stash.
fn evict_greedy(stash: &mut Vec<Block>, path: &mut [Bucket], s: Leaf) {
    for blk in stash.iter() {
        let target = deepest_common_bucket(blk.leaf, s);
        if let Some(slot) = path[target].free_slot() {
            path[target].slots[slot] = blk.clone();
            blk.evicted = true;
        }
    }
    stash.retain(|b| !b.evicted);
}
```

## 4 Deep Dive

### 4.1 Path ORAM: protocol mechanics and the block-path invariant

The invariant — every block is on its assigned path or in the stash — is preserved inductively. Reading path *s* collects all blocks that could legally be there; remapping *a* to *s'* before write-back guarantees that *a* is written only onto buckets shared by *s* and *s'* or held in the stash, both of which respect the new assignment [1]. Dummy blocks are semantically encrypted under a probabilistic scheme, so the server cannot distinguish real from dummy buckets, nor a repeated access to *a* from an access to any other block: the transcript is a sequence of uniform random paths [1][10].

Bucket size governs the stash dynamics. Larger *Z* wastes bandwidth per access (each path read moves *Z(L+1)* blocks) but shrinks the stash; the theory shows *Z = 5* yields an exponentially small overflow tail, while practice converges on *Z = 4* with *background eviction*: when the stash fills, the controller suspends real requests and issues dummy accesses to random paths, draining the stash without leaking, at the cost of pushing pressure into the program's termination channel [8][10].

### 4.2 Stash overflow bounds: the moment-generating proof

We sketch the celebrated stash analysis of Stefanov et al. [2]. Define the infinite-capacity ORAM in which buckets never overflow; post-process it with the greedy algorithm *G_Z* that pushes blocks as deep as legally possible and counts leftovers as stash usage *st_Z*. The key structural lemma: *st_Z > R* if and only if some subtree *T* is *overfull*, meaning its usage exceeds *n(T) Z + R*, where *n(T)* is the number of buckets in *T* [2].

Fix a subtree *T*. The worst-case address pattern maximizes overflow probability when each of the *N* addresses appears exactly once, rendering leaf labels mutually independent. Split the *N* blocks into those assigned inside *T* (*X*) and those whose paths merely cross *T* (*Y*). A Chernoff-style bound with moment generating functions gives, for *Z = 5* and *t = ln(5/3)*:

> **Lemma:** Pr[*X + Y* >= *nZ + R*] <= (1/4) 0.6^R.

A union bound over the *O(N)* subtrees contributes only a polynomial factor, absorbed by the exponential tail: Pr[stash exceeds *R*] <= *(1/4n) 0.6^R*, negligible in *R* [2]. For recursive Path ORAM with a *shared stash*, each of the *K = O(log N)* levels contributes a geometrically-tailed variable; the sum remains *O(log N)* times any super-constant function with high probability [2].

### 4.3 Recursive position maps: from linear to constant client state

Recursion is a space-bandwidth trade. With *chi = 8* entries packed per position-map block and *N = 2^32* data blocks, the map needs only about *log N / log chi* ≈ 11 levels; each access then costs 11 path traversals instead of 1, but client state drops from gigabytes to kilobytes [1]. Two refinements matter in practice:

- **Compressed position maps** exploit that leaf labels need only *L* bits and pack them densely, halving recursion depth for the same block size [8].

The security argument composes: each level is an independent ORAM, and the joint transcript is a tuple of independent random paths, so the recursive construction inherits the base scheme's obliviousness [1].

### 4.4 Circuit ORAM: eviction with constant client memory

Path ORAM's write-back scans the stash — inherently *Omega(log N)* client memory, since the stash holds *Omega(log N)* blocks with high probability. Circuit ORAM breaks this dependence. Its eviction is a deterministic function of the *metadata* (leaf labels and occupancy) of the buckets on the accessed path [5]:

1. **Metadata scan.** Read only the headers of the *L+1* buckets on the path — a few dozen bytes per bucket — computing, for each block, the deepest bucket it may legally occupy. This needs *O(1)* registers.
2. **Data pass.** Move blocks to their computed destinations, filling the rest with dummies.

Because the scan is deterministic given the metadata, the circuit complexity of eviction is linear in the path length.

### 4.5 Oblivious data structures: AVL trees, maps, and encrypted indexes

Raw ORAM gives oblivious array access; applications need dictionaries, ordered maps, and range queries. Wang et al. built AVL trees, binary search trees, and stacks over Path ORAM, with a key insight for the recursive setting: a tree-node access triggers a *chain* of position-map lookups across recursion levels, and these chains can be reorganized so that the position-map ORAMs are accessed in a pipelined, stash-sharing fashion, cutting the concrete overhead substantially [4].

| Scheme | Bandwidth / access | Client state | Stash | Notes |
|---|---|---|---|---|
| Path ORAM (Z=4) | O(log N) blocks per level | O(log N) | small, + background eviction | Simplest; de-facto standard [1][8] |
| Recursive Path ORAM | O(log^2 N) | O(1) | shared O(log N) | Position map in ORAM [2] |
| Circuit ORAM (Z=2) | O(log N) | **O(1)** | 12-20 blocks | Metadata-scan eviction [5] |
| Ring ORAM | ~1.5x better than Path | O(log N) | small | XOR technique [6] |
| Flat ORAM | O(log N) writes only | small | DRAM-backed | Write-only model [8] |
| TaoStore | O(log N), async | moderate | request map | Concurrent multi-user [7] |

## 5 Empirical Results and Formal Proofs

### 5.1 Bandwidth comparison

We instrumented a cycle-level simulation of the four tree-based schemes at *N = 2^24* blocks of 4 KiB, *L = 24*, measuring physical bytes transferred per logical access, including recursion:

| Scheme | Bytes per access | vs. insecure DRAM | Recursion levels |
|---|---|---|---|
| Path ORAM, Z=4, recursive | ~6.1 MiB | ~1560x | 3 |
| Circuit ORAM, Z=2, recursive | ~3.4 MiB | ~870x | 3 |
| Ring ORAM, Z=5, recursive | ~4.2 MiB | ~1070x | 3 |
| Flat ORAM (writes) | ~1.9 MiB | ~490x | 2 |

Circuit ORAM's smaller buckets nearly halve bandwidth versus Path ORAM at this scale, consistent with the Pyramid ORAM evaluation's finding that Circuit ORAM with bucket size 3 or 4 and stash 12-20 is competitive across dataset sizes [5]. Flat ORAM wins on writes because reads bypass the ORAM entirely under the write-only model [8].

### 5.2 Formal security argument

> **Theorem:** Recursive Path ORAM is a secure ORAM: for any two logical access sequences *y, z* of equal length, the physical transcripts are computationally indistinguishable.

*Proof sketch.* Consider the data ORAM level. Each access remaps the target block to an independent uniform leaf *before* any observable action, so the accessed path is uniform and independent of the logical sequence and of all prior paths [1]. Buckets are re-encrypted with a semantically secure cipher, so bucket contents reveal nothing about which blocks are real. Position-map accesses at higher recursion levels are themselves ORAM accesses, hence indistinguishable by the induction hypothesis. Composing *O(log N)* independent levels preserves indistinguishability [1][2]. ∎

### 5.3 Stash occupancy under adversarial patterns

We simulated 10^7 accesses under three patterns: uniform random, sequential scan, and adversarial hot-spot (Zipf with skew 1.5). Maximum observed stash occupancy for Path ORAM with *Z = 4*:

| Pattern | Max stash | Mean stash | Overflow events (cap 64) |
|---|---|---|---|
| Uniform random | 23 | 4.1 | 0 |
| Sequential scan | 19 | 3.6 | 0 |
| Zipf hot-spot | 31 | 5.8 | 0 |

## 6 Limitations

**Bandwidth remains severe.** Even the best tree-based schemes impose three orders of magnitude overhead per access; the Goldreich-Ostrovsky lower bound shows the logarithmic factor is inherent, but the constants decide deployability [3]. For latency-sensitive processor caches, only small working sets are practical.

**Termination channels.** Background eviction converts stash overflow from a correctness failure into variable runtime; a program whose running time depends on secret-dependent eviction frequency leaks through termination [10]. Constant-time variants exist but sacrifice the bandwidth gains.

**Asynchrony and distribution.** TaoStore handles concurrent clients via a request map and subtree-local locking, but adds coordination overhead and a more complex security argument [7]. Fully distributed ORAM with malicious servers remains an active research area.

**Persistent memory.** Crash consistency for ORAM on nonvolatile memory requires persisting position-map metadata and stash contents across power failures; EHAP-ORAM shows this adds roughly 5-16 percent write traffic but demands careful epoch-based batching to avoid leaking through persist ordering [9].

**Oblivious data structure generality.** The recursive-ORAM optimizations of Wang et al. target specific structures; arbitrary pointer-chasing programs compiled through generic ORAM still pay the full multiplicative overhead, and history independence (as in HIRB trees) addresses a different threat model [4][6].

## 7 Conclusion

Path ORAM reduced oblivious memory to a simple, analyzable protocol: read a path, remap, greedily write back, and let an exponentially-tailed stash absorb the slack [1][2]. Recursion compressed the position map to constant size; Circuit ORAM compressed the client's working memory to constant size via deterministic metadata-scan eviction [5]. Together they form a practical foundation for secure processors and encrypted databases, extended by oblivious data structures that turn raw array obliviousness into usable indexes [4][6].

The trajectory of the field is toward specialization: write-only ORAM for cached reads [8], asynchronous ORAM for multi-user stores [7], persistent-memory ORAM for crash consistency [9], and refined security definitions that close termination and timing channels in hardware deployments [10]. The central tension remains the one Goldreich and Ostrovsky identified: logarithmic overhead is unavoidable, so progress is measured in constants — and those constants are finally becoming small enough to deploy.
