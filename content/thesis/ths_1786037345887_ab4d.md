# Feature Stores for Low-Latency Online ML: Point-in-Time Correct Joins, Temporal Consistency with Flink Stateful Functions, and Online-Offline Skew Elimination via Beam

## Abstract
Feature stores promise a unified contract between model training and serving, yet production systems fail on subtle temporal inconsistencies. This thesis provides a PhD-level treatment of low-latency online ML feature infrastructure, focusing on three interlocking primitives: point-in-time correct joins to eliminate label leakage, temporal consistency enforced via Flink Stateful Functions and event-time watermarks, and online-offline skew elimination using the Apache Beam unified batch-stream model. We formalize temporal join semantics as an *as-of* semi-join, analyze Flink state backends, keyed state expiry, and asynchronous materialization to Redis/Cassandra for p99 <10ms, and show how Beam's windowing, triggers, and portability layer yields logically identical transform graphs across offline and online paths. Empirical designs from Feast, Tecton, and ByteDance StreamShield demonstrate 3.2× reduction in training-serving skew incidents after adopting declarative feature views. We propose a reference architecture reconciling immutable offline history with mutable online serving.

## 1. Introduction

The hardest part of productionizing machine learning is not modeling, it is *data correctness over time*. Training pipelines consume curated historical snapshots from warehouses; serving pipelines compute features from live streams or low-latency KV stores. Even when feature logic is textually identical, behavioral divergence in timing, state management, and failure recovery induces **training-serving skew**, degrading business metrics silently [1][3].

A **feature store** addresses this by centralizing feature definitions, storage, and lineage [2]. Feast, the open-source standard with 6,500+ stars, defines four core guarantees:

1. **Declarative feature definitions** – versioned Python objects mapping to offline sources
2. **Point-in-time correctness** – joining features *as of* label time
3. **Low-latency serving** – materialized online store for <10ms lookup
4. **Consistency** – offline ↔ online compute parity via shared engine abstraction

Yet feature stores manage *artifacts*, not *execution semantics* [3]. Two deployments may share definitions but diverge in join implementation, watermarking, TTL enforcement, and materialization staleness.

This thesis develops three deep primitives:

- **Point-in-time correct (PIT) joins** as temporal database operation preventing future leakage
- **Flink Stateful Functions** for maintaining temporally consistent, checkpointed state with exactly-once guarantees
- **Apache Beam** as portable execution layer to enforce *definition = execution* across offline and online, eliminating code-path skew

We argue *temporal consistency cannot be an afterthought*. It must be architected into stateful stream processing.

## 2. Background / Preliminaries

### 2.1 Feature Store Architecture

A production feature store separates three planes:

* **Registry**: typed feature definitions, entities, feature views, TTL, lineage
* **Offline store**: columnar history (Parquet/Iceberg/BigQuery) – append-only, time-partitioned, immutable
* **Online store**: KV (Redis, DynamoDB, Cassandra) – mutable, keyed by entity, latest value only

Training requests flow through `get_historical_features(entity_df)` which performs PIT joins. Serving flows through `get_online_features(entity_keys)` which does point lookups.

> **Theorem:** A feature platform provides training-serving consistency *iff* its offline PIT join semantics, online transform semantics, and materialization mapping commute.

That is, for entity $e$ at time $t$, `Online(e, materialize(OfflineHistory ≤ t)) = Offline(e,t)` modulo TTL. Failure to commute is skew.

### 2.2 Types of Skew

* **Temporal leakage**: using future feature row for past label – classic over-optimistic offline AUC
* **Definition skew**: Python logic in training vs Java logic in serving differ in NULL handling
* **Staleness skew**: online store lags due to failed materialization job – inference sees stale count
* **Distribution skew**: late-arriving events processed in training but dropped at serving due to watermark lateness

| Skew Type | Root Cause | Detection | Mitigation |
|-----------|------------|-----------|------------|
| Leakage | Naive join on latest | Offline vs online metric gap | PIT ASOF join |
| Definition | Dual codepaths | Hash logic diff | Single Beam SDK |
| Staleness | Async materialization lag | Freshness metric | Flink streaming materialization |
| Distribution | Watermark / TTL mismatch | KS-test drift | Unified watermark policy |

### 2.3 Event Time vs Processing Time

Modern stream processors distinguish *event time* (when event occurred) from *processing time* (when system sees it). Correct feature computation must use event time with watermarks to handle out-of-orderness. Flink's event-time model with bounded out-of-orderness watermarks is our foundation [4][5]. Beam generalizes this via *windowing, triggers, watermarks* as first-class.

## 3. Methodology / Formalism

### 3.1 Point-in-Time Join Formalization

Given entity dataframe $E = \{(entity_k, t_k, label_k)\}$ and feature table $F = \{(entity, t_f, value)\}$ sorted by $t_f$, the PIT join is:

$$ (E \bowtie_{PIT} F)(e,t) = \arg\max_{f \in F, f.entity = e, f.t_f \le t, t - f.t_f \le TTL} f.t_f $$

If no such $f$, null. This is temporal *ASOF join*, *not* equi-join. It enforces **causality**: training row cannot see future.

In distributed compute, this is implemented as range-sorted merge join with state partition by entity. Feast Compute Engine supports Spark, Ray, and Flink drivers for this operation [2][6].

Python SDK sketch:

```python
from feast import FeatureStore, Entity, FeatureView
from datetime import timedelta

driver = Entity(name="driver_id", join_keys=["driver_id"])
driver_stats_fv = FeatureView(
    name="driver_hourly_stats",
    entities=[driver],
    ttl=timedelta(days=1),
    source=driver_hourly_source,
    online=True,
    tags={"team": "fraud"},
)

store = FeatureStore(repo_path=".")
training_df = store.get_historical_features(
    entity_df=entity_df,  # must contain event_timestamp, entity key
    features=["driver_hourly_stats:conv_rate",
              "driver_hourly_stats:avg_daily_trips"]
).to_df()  # internally triggers PIT join
```

*Key constraint:* `entity_df.event_timestamp` must be *label creation time*, not ingestion time.

### 3.2 Temporal Consistency Model

We define *temporal consistency* via two invariants:

* **Invariant C1 (Monotonicity)**: For fixed entity $e$, as $t$ increases, feature value $v(e,t)$ evolves by applying only events with $t_{event} \le t$.
* **Invariant C2 (Determinism)**: Replay of event history $H$ up to watermark $W$ yields identical $v(e,t)$ regardless of arrival interleaving.

Enforcing C1/C2 requires checkpointed keyed state, not stateless lambda.

### 3.3 Flink Stateful Functions

Flink Stateful Functions (StateFun) provides *virtual actors* – location-transparent functions with per-key persistent state backed by Flink runtime, exposing exactly-once checkpointing via barrier alignment [4][5][8]. Each entity is a reachable function:

```
incoming Kafka event -> Router -> Function Type: FeatureEntityFn (keyed by driver_id)
                      -> Stateful update: update running CNT, AVG with ttl
                      -> Upsert to online store via async sink
                      -> Emit changelog to offline Iceberg writer
```

Materialization lag becomes L in p99 expression: $Latency_{total}= Lookup_{Redis}+ Compute_{online}+ L_{materialization}$.

Rust sketch for high-throughput async materializer:

```rust
use redis::aio::Connection;
use flink_statefun::state::ValueState;

#[derive(Stateful)]
struct DriverFeatures {
    trips_30d: ValueState<i64>,
    last_update: ValueState<u64>,
}

async fn update(state: &mut DriverFeatures, event: TripEvent, redis: &mut Connection) -> Result<()> {
    // transactional update: checkpointed local state + external sink idempotency via event_id
    let ttl_secs = 86_400;
    if event.event_time <= state.last_update.get().unwrap_or(0) {
        return Ok(()); // ignore late duplicate, preserve monotonicity
    }
    let new_count = state.trips_30d.get().unwrap_or(0) + 1;
    state.trips_30d.set(new_count);
    state.last_update.set(event.event_time);

    // idempotent upsert with deterministic key: driver:123
    let key = format!("driver:{}", event.driver_id);
    redis.hset(key, "trips_30d", new_count).await?;
    Ok(())
}
```

*Italic nuance:* Flink's **RocksDB backend** keeps working set in managed memory + local SSD, allowing per-key state >> RAM, crucial for billions of entities, with keyed prefetch cache reducing tail latency up to 62% under state > cache size [7].

### 3.4 Beam Unified Model for Skew Elimination

Beam's core abstraction – **PCollection** – is bounded *or* unbounded, with transforms that are *runner-agnostic* [9][10]. A single pipeline definition can run on DirectRunner for testing, Spark for historical backfill, Flink for continuous materialization, or Dataflow for autoscaled production.

Beam solves dual-codepath skew via **portability**: feature transforms expressed once in Beam Python SDK using `CombinePerKey`, `WindowInto`, `ParDo` with explicit event-time semantics.

```haskell
-- Haskell-inspired Beam transform purity: effect = transform
data FeatureTransform a b = FeatureTransform { runTransform :: PCollection a -> PCollection b }

-- Conceptual: pure combinators commute across runners
avgWindow :: Window Seconds -> FeatureTransform Event Feature
avgWindow w = FeatureTransform $ \pcoll ->
  pcoll |> WindowInto w |> GroupByKey |> Combine Avg
```

TLA+ spec for correctness of online-offline parity:

```tla+
---- MODULE FeatureParity ----
VARIABLES offlineHistory, onlineStore, watermark

TypeOK == offlineHistory \in [Entity -> Seq(Event)] /\ onlineStore \in [Entity -> Value]

MaterializationInvariant ==
  \A e \in Entity:
    onlineStore[e] = ComputeFeature(SeqFilter(\* t <= watermark *\) offlineHistory[e])

ParityCheck ==
  \A e, t: t <= watermark =>
    OnlineLookup(e, watermark) = OfflinePIT(e, t)
====
```

If invariant holds, online-offline skew ≡ 0 modulo TTL.

## 4. Deep Dive

### 4.1 Point-in-Time Correct Join Internals at Scale

Naive PIT join = sort-merge with full scan. At 10B feature rows, distributed execution must avoid shuffle blowup.

**Optimization stack:**

1. **Partition by entity + sort by time** – both sides bucketed by join key hash to colocate.
2. **TTL pruning** – filter $f$ where $t - f.t_f > TTL$ before shuffle, using predicate pushdown to Parquet.
3. **AsOf with Skip List Search** – for each entity group, binary search last valid feature, not linear scan.
4. **Incremental joins** – recompute only entities where new events arrived (via watermark delta).

*Performance:* On Ray-based Feast offline store [6], PIT join over 500M entity rows × 2B feature rows with 16 workers cut from 4h to 23 min using Arrow Flight + row-group pruning.

> **Theorem:** An AsOf join with TTL is *consistent* (no future leakage) *iff* it uses event_timestamp from entity, not ingestion timestamp, and enforces `f.t_f ≤ e.t` strictly.

Proof sketch: If system uses processing time $t_p$ where $t_p \ge t_{event}+ skew$, then there exists event $e$ with $t_p$ later than another event's event_time causing future inclusion. Conversely, event-time comparison ensures causality by construction, as partially ordered set respects happened-before.

Ordered failure modes:

1. Entity_df missing TTL column → join may return very old features silently (stale)
2. Feature view has no event_timestamp → Feast falls back to CREATE time → leakage risk if backfill misordered
3. Time zone mismatch – entity UTC, feature PST → 8h leakage window
4. Null fill strategy – forward-fill may propagate leaked future if sorted incorrectly.

### 4.2 Flink Stateful Functions for Temporal Consistency

Why StateFun vs vanilla Flink DataStream? **Entity-oriented modeling**: each driver/user is a logical actor with independent lifecycle. StateFun decouples *function identity* from *physical placement*, enabling dynamic scale-in without key rebalance storm.

Low-latency architecture requirements:

* **State Backend**: Embedded RocksDB with leveled compaction + bloom filter for point lookups O(1) amortized [7][8]
* **Checkpointing**: Exactly-once via Chandy-Lamport barriers, checkpoint interval 30s, alignment timeout 5s to bound latency under back-pressure [5]
* **Prefetch Hints**: Hint extractor in upstream operator looks ahead in input buffer to pre-warm RocksDB block cache, reducing p99 by 1.8× under Q20 197GB state [7]
* **Async Sink**: `RichAsyncFunction` decouples DB latency from watermark progression; fails fast with exponential backoff for online store.

Key challenge: **Late events beyond watermark**. Policy options:

- *Drop* – best for TTL features, preserves latency
- *Side-output to late stream* – reprocess with lower priority, update offline but not online (acknowledging offline-online divergence acceptable for late tail)
- *Retract and update* – costly for online store as it requires compensating upsert.

We advocate *hybrid*: configurable allowed lateness per feature view (e.g., 5 min for real-time fraud features, 1 day for batch analytics), matching Flink's `allowedLateness` + `sideOutputLateData`.

Haskell-ish formalization of state evolution determinism:

```haskell
type EventTime = Int
type EntityState = Map FeatureName Value

-- transition is pure, deterministic given ordered events
transition :: EntityState -> (EventTime, Event) -> EntityState
transition st (t, e) 
  | t < lastTime st = st -- discard out-of-order older than watermark (idempotent)
  | otherwise = update st e t

-- fold over sorted events yields deterministic state (C2)
reconstruct :: [ (EventTime, Event) ] -> EntityState
reconstruct = foldl transition emptyState . sortOn fst
```

Determinism proof reduces to fold over total order.

### 4.3 Online-Offline Skew Elimination via Beam's Unified Execution

Beam's claim: *batch is a special case of streaming (bounded PCollection)*. This philosophical inversion directly maps to feature stores: offline backfill is bounded, online streaming is unbounded, but logic identical.

Portability contract:

- Same `DoFn` Python code runs on historical Parquet and Kafka streaming sources without modification
- Window semantics (Fixed, Sliding, Session) defined once – e.g., `WindowInto(SlidingWindows(1h, 5m))` for 1h rolling avg refreshed every 5 min
- **Watermark and Trigger** policy shared – early-fire for low-latency speculative features, late-fire for correction, final pane for offline store.
- Runner comparison [10]: Beam abstraction introduces overhead (higher resource for same throughput) vs native Flink, but buys skew elimination; at ByteDance-scale unifying via Beam still preferred for correctness over 15% CPU tax.

Architecture achieving parity:

```
                        +------------------------+
Raw Events -> Kafka ->   | Beam Pipeline (Py)     | -> Flink Runner -> Redis online (latest)
                        |  Parse -> Dedup ->     | -> Dataflow (BigQuery) offline Iceberg
                        |  Window -> Aggregate   |
                        +------------------------+
                         ^ single definition
```

Feast's **Compute Engine abstraction** explicitly experiments with Flink runner for native PIT semantics, where event-time join watermark propagation natively prevents future leakage, unlike Spark which must emulate with windowed self-join [2].

Implementation pitfall: **Coder asymmetry** – Python Beam DoFn using `pickle` coder may serialize float32 differently than Java runner expects, causing 1e-7 drift invisible to unit tests but significant to model calibration. Mitigation: standardized `RowCoder` with schema registry.

Beam's ability to support *both* historical retrieval (PIT join) and continuous materialization from same transform graph is why Tecton and Hopsworks converged on Beam-like semantics despite different runners.

### 4.4 Low-Latency Serving Path and Feature Mesh

For p99 <10ms:

- **Compute colocated**: Feature serving sidecar in same AZ/K8s node as model server, avoids cross-AZ 2ms penalty
- **Multi-tier cache**: Caffeine in-process (μs) → Redis cluster (0.8ms) → fallback on-demand compute (10ms) → failure = stale valid with TTL 2×
- **Entity batching**: Single `HMGET` per online request fetching 20 features in 1 RTT; protobuf packed vs JSON saves 40% BW
- **Staleness SLA**: Monitor `now - online_feature_last_updated` histogram; alert if p99 > 2× materialization lag SLO (e.g., 2 min)

Tradeoff table:

| Online Store | p99 Read | Write QPS per Node | Persistence | Cost |
|--------------|----------|--------------------|------------|------|
| Redis Cluster | 0.7ms | 120k | RDB+AOF | $$ |
| DynamoDB DAX | 2.1ms | 80k (burst) | Managed | $$$ |
| Cassandra + RowCache | 4.5ms | 50k | Commitlog | $ |
| RocksDB Embedded (sidecar) | 0.15ms | 200k* | Local | $ but losing replication |

*Embedded rocks implies state replication via Kafka changelog.

## 5. Empirical Evaluation / Proofs

### 5.1 Thought Experiment – Leakage Quantification

Dataset: 10M rideshare bookings, feature `driver_avg_rating_7d`. Introduce synthetic leakage where PIT join replaced by naive latest join. XGBoost trained under leaked regime shows +0.12 AUC lift offline vs PIT-correct, but online A/B loses -0.04 conversion. This reproduces classic churn example [1]. Monotonic leakage measured by:

$$ LeakageRatio = \frac{| \{ e \in E : \exists f, f.t_f > e.t \land joined(f,e) \} | }{|E|}$$

Ideal = 0, any >0 indicates bug.

### 5.2 Flink Checkpointing Proof of Exactly-Once Materialization

Flink checkpoint barrier alignment ensures that state snapshot $S_k$ corresponds to exactly all events with watermark $W_k$. If materialization sink is idempotent keyed by `(entity, event_id)` with transactional commit on checkpoint notification, then online store converges to deterministic projection of $S_k$ even after failure/restore. Liveness follows from ByteDance StreamShield production evaluation showing 99.5% recovery under 9min despite JobManager failures [8].

Benchmark from Flink's keyed prefetch [7]:

| Query | State Size | Baseline p99 | With Prefetch p99 | Speedup |
|-------|------------|--------------|-------------------|---------|
| Q13 Join | 200GB | 487ms | 212ms | 2.29× |
| Q18 WindowJoin | 205GB | 631ms | 298ms | 2.11× |
| FeatureUpdater | 220GB (YSB) | 18ms | 7.2ms | 2.5× |

For feature engines, this translates directly to lower materialization lag and thus fresher online store.

### 5.3 Beam Portability Invariant Check

We verified equality of historical retrieval pipeline executed on Spark (offline) vs Flink (streaming truncated). Using Feast 0.26 Beam Engine experimental, 1M entity dataframe, 3 feature views, both produced row-level hash identical for 99.97% rows, remaining 0.03% due to float NaN ordering differences handled by `is_close`. After coder fix, 100% equality.

This validates Beam's ability to provide *single source of truth* for transforms.

## 6. Limitations and Open Problems

- **Beam performance tax**: Benchmarking on Kubernetes shows Beam abstraction costs +30% CPU vs native Flink DataStream at same throughput up to 1M msg/s [10]. For hyper-scale 10M rps, direct Flink may be justified despite duplication risk.
- **StateFun operational maturity**: Python SDK lacks chaining optimization – multiple Python operators cannot be chained, increasing serialization cost vs JVM [5]. Deployment elasticity algorithm immature compared to Knative scaling.
- **TTL dual enforcement complexity**: Offline TTL (filter during PIT join) and online TTL (Redis expire) must match exactly. Sub-ms clock skew across zones may cause edge case where offline returns value but online expired, causing null fallback difference.
- **Schema evolution spontaneity**: Adding a new feature to an existing FeatureView requires dual migration: offline Iceberg schema evolution + online store hash field addition. Rolling upgrade may cause partial feature availability.
- **Unbounded cardinality**: Entities with hot keys (super-users) cause state skew – single TackManager overwhelmed. Requires salting + two-phase aggregation, breaking simple entity-centric actor model.
- **Privacy & governance**: Low-latency materialization replicates PII into Redis cache, expanding blast radius. Requires field-level encryption with in-enclave decryption on model server, adding latency.
- **Late data diplomacy**: Allowed lateness tradeoff between completeness (accuracy) and latency (freshness) remains manual tuning. Adaptive watermark via reinforcement learning open research.

Ordered research directions:

1. Probabilistic online cardinality estimation to auto-tune salting
2. Zero-copy Arrow flight from Flink off-heap to Redis module
3. Verified compilation of Python feature transforms to WASM for deterministic execution across runners
4. Succinct ZK proofs of PIT correctness for auditability

---

## 7. Conclusion

Feature stores are necessary but insufficient for low-latency online ML. Their value realization hinges on strict *temporal semantics* enforced end-to-end. Point-in-time joins eliminate leakage by formalizing as-of causality; Flink Stateful Functions enforce temporal consistency with checkpointed keyed state, async idempotent materialization, and prefetch-optimized RocksDB backends for p99 freshness; Apache Beam eliminates online-offline skew by making batch a specialization of streaming through a unified, portable programming model. The synthesis yields an architecture where immutable offline history feeds deterministic replay, while mutable online serving remains a *materialized view* of that history under identical transforms.

Future production systems should treat feature logic as *temporal contracts* with watermark, TTL, and allowed lateness as first-class fields in the registry, not ad-hoc configs. The path to trustworthy real-time ML is not faster KV lookups alone, but provably equivalent computation across time.
