# Hardware Transactional Memory Best-Effort Fallback: Intel RTM/TXSX, POWER HTM, and HyTM Coherence Integration with Lock Elision

## Abstract

Best-effort Hardware Transactional Memory (HTM) introduces a profound tension between optimistic concurrency and architectural resource limits. This thesis dissects Intel Restricted Transactional Memory (RTM) and Hardware Lock Elision (HLE/TXSX), IBM POWER8/POWER9 HTM with suspended transactions and Rollback-Only Transactions (ROT), and Hybrid TM (HyTM) fallback integration. We formalize abort taxonomy, capacity overflows in L1 and TMCAM, coherence-protocol extensions for eager conflict detection, and the lock-elision correctness condition requiring subscription to the lock line. We characterize lemming effects, TAA mitigation via TSX_FORCE_ABORT, POWER TEXASR persistent vs. transient failure classification, and HyTM metadata design that avoids perturbation of hardware fast-path capacity. The result is a unified model for best-effort fallback that preserves opacity, liveness via non-transactional fallback, and serializability across heterogeneous HTM ISAs. ## 1 Introduction

Hardware Transactional Memory obviates conventional lock-based critical section serialization by exploiting dynamic data-independence. Both **Intel TSX** [1][2] and **IBM POWER HTM** [4][5] adopted a *best-effort* philosophy: no guarantee of eventual commit in hardware, abandoning classical bounded-transactional-memory completeness for implementability [6]. This best-effort semantics forces every transactional attempt to be paired with a *software fallback* that guarantees forward progress. Intel's TSX, introduced in Haswell 4th Generation Core in 2013 and deprecated via microcode after 2021 due to *Transactional Asynchronous Abort* (TAA) vulnerabilities [3], offered two ABIs: **HLE** — legacy compatible `XACQUIRE`/`XRELEASE` prefix hints on lock instructions — and **RTM** — explicit `XBEGIN`, `XEND`, `XABORT`, `XTEST` with status in `%EAX` [1]. POWER8/POWER9 HTM introduced richer facilities: `tbegin.`, `tend.`, `tabort`, `tabortwc`, `tcheck`, `tsr` suspend/resume, and Rollback-Only Transactions (ROT) for speculative lock elision that tracks only stores [4][7]. The central problem of this thesis is: *how to compose best-effort transactions, lock elision, and Hybrid TM (HyTM) such that coherence integration preserves correctness yet minimizes capacity perturbation?* We argue that naïve metadata access from the hardware fast path destroys capacity and that the correct composition rests on three invariants:

* **Subscription atomicity**: every lock-elision fast path must atomically read the lock as free *inside* the transaction before commit [1]. * **Strong isolation enforcement via coherence**: read-set and write-set tracking at L1 granularity must generate requests that trigger eager aborts before non-transactional stores become visible [5][6]. * **Failure oblivious fallback classification**: transient vs. persistent abort reasons must drive exponential backoff and fallback selection to avoid *lemming effects* [2]. ---

## 2 Background

### 2.1 Transactional Memory Lineage

Herlihy and Moss's 1993 formulation [6] proposed per-cache-line transactional state. Modern commercial HTM deviates: capacity limits, interrupt-induced aborts, and lack of guaranteed commit. As noted in SpringerLink's TM chapter, *as of 2023* commercial HTM survivors are contested: Intel TSX removed in Comet Lake onward when disabled by default, POWER HTM removed in Power10 ISA v3.1 [6]. ### 2.2 Intel TSX Implementation Envelope

Intel's first TSX implementation reused the **32-KB 8-way L1 data cache** for write-set buffering, holding dirty transactional lines in L1 until `XEND` [2]. Evicting a transactionally written line causes abort; read-set only lines may spill to a secondary structure for tracking but writes cannot [2]. Conflict detection is at **cache-line granularity using physical addresses** via the cache coherence protocol [2]. This design leads to capacity abort when writeset > ~L1 ways or readset > secondary tracker. Abort status in `%EAX` after `XBEGIN`:

* bit 0: abort due to conflict with other thread
* bit 1: debug breakpoint
* bit 2: buffer overflow / capacity
* bit 3: breakpoint hit
* bit 4: nesting exceeded
* bit 5: explicit `XABORT` with 8-bit immediate in bits 24-31 [1]

Microcode updates after IPU 2021.1 set `RTM_ALWAYS_ABORT` (`CPUID.07H.0H.EDX[11]`) and force all RTM to abort, with `IA32_TSX_CTRL` MSR `0x10F` `TSX_CTRL_RTM_DISABLE` and `TSX_CTRL_CPUID_CLEAR` [3]. ### 2.3 POWER8/POWER9 HTM: TEXASR, TFIAR, Suspended Mode

POWER ISA v2.07 introduced HTM as best-effort with:

* **Strong atomicity** with lazy version management and eager conflict detection [5]. * **8 KB Transactional Memory CAM (TMCAM)** per core nominally holding speculative lines, though spill and conflict resolution vary. * **ROT (Rollback-Only Transactions)**: a mode where only stores are tracked, aimed at lock elision where transaction should not observe non-speculative writes? In ROT, loads are not tracked, reducing capacity pressure [4]. Status:

* `TEXASR` (Transaction Exception and Summary Register) encodes abort cause: persistent vs. transient, conflict, disallowed, footprint overflow, nested, self-induced, etc. * `TFIAR` (Transaction Failure Instruction Address) points to faulting instruction. * Failure codes include `0001_0001` footnote: Footprint overflow, `0100_0001` conflict, etc. [7]. POWER supports *suspended* transactions: `tsuspend` / `tresume` allowing non-transactional loads/stores inside a transaction for escape actions, crucial for HyTM that needs to inspect software metadata without adding it to read-set [5][6]. This mirrors Intel Sapphire Rapids' `SUSLDTRK` for non-transactional loads [6]. > **Theorem 1 (Best-Effort Liveness):** For any best-effort HTM where commit is not guaranteed, no program using only hardware transactions can guarantee forward progress. There must exist a non-transactional fallback path that runs without HTM and guarantees termination. This folklore result justifies lock elision's dual-path design [1][2]. ### 2.4 Lock Elision and HyTM

Lock Elision transforms:

```c
lock(l);
critical();
unlock(l);
```

into:

1. *Fast*: `XBEGIN fallback; if(l==free) {critical; if(l==free) XEND else XABORT}` else fallback
2. *Slow*: `lock(l); critical(); unlock(l)` [1]

HLE automates this in microcode: `XACQUIRE` on lock acquire elides lock write and buffers updates; `XRELEASE` commits [1]. For correctness, the transaction must *subscribe* to lock to avoid inconsistent observation of a thread in fallback holding the lock while hardware transaction reads inconsistent intermediate state [2]. HyTM generalizes: hardware fast path (Type-H) and software slow path (Type-S) run concurrently. Design axes from Ruan & Spear [5]:

* *Metadata perturbation* — whether H modifies global counters/version locks (e.g., NOrec sequence clock)
* *Concurrency of H and S* — can they commit together? * *Safety*: opacity vs. weak isolation
* *Fairness*: starvation of S by frequent H commits

## 3 Methodology

We model each HTM as a tuple `M = (R,W, C, A, D)` where `R` is read-set CAM capacity, `W` write-set buffer (L1 associativity slices), `C` conflict resolution policy (requester-wins vs. requester-loses), `A` abort reasons space, `D` disallowed instructions. Method:

1. **Taxonomize abort reasons** across ISAs from vendor manuals and perforation studies: capacity, conflict, interrupts, disallowed ops (CPUID, SYSCALL, `XABORT`), nested transaction overflow, implicit abort via TLB shootdown [1][3][4]. 2. **Formalize fallback correctness** as opacity proof obligation: ∀ executions, there exists serial order consistent with real-time order where transaction lock subscription precedes commit. 3. **Implement HyTM prototypes** in GCC's HTM intrinsics (`htmintrin.h` for Power, `immintrin.h` for Intel) and profile abort distributions using `perf` counters `RTM_RETIRED.ABORTED`, `TX_MEM.ABORT_CONFLICT`, `TX_MEM.ABORT_CAPACITY` [3]. 4. **Coherence integration analysis** via MESIF extension: add T bit to lines to enforce transactional state, with transitions Transactional-Modified, Transactional-Shared. Code simulation artifacts in Python, Rust, Haskell, and TLA+ illustrate state machine encodings. ---

## 4 Deep Dive

### 4.1 Intel RTM / TXSX Abort Taxonomy and Hardware Structures

Intel TSX's capacity is *unnamed but physical*: 32KB L1 is not all usable transactionally because associativity conflicts and pre-existing lines consume ways. Empirically, write-set capacity ~ 22-23 cache lines for 4K aliasing avoidance, read-set ~ 2K lines depending on microarchitecture [2]. Abort classes:

* **Conflict**: another core requests transactional line in conflicting mode → coherence invalidation triggers abort before `XEND`. Requester wins: transaction aborts to allow conflicting non-transactional store to proceed [1]. * **Capacity**: write-set eviction → immediate abort. * **Unfriendly code**: `CPUID`, `PAUSE` in RTM, OS syscall, interrupt, `IRET`, `XBEGIN` nested too deep (implementation limit often 1 for RTM but defined as arbitrary). * **Explicit**: `XABORT imm8`. #### HLE vs RTM semantics

*HLE*:

```asm
; HLE lock elision legacy prefix
XACQUIRE lock   inc qword ptr [lock] ; elides, doesn't actually increment visible
... critical ... XRELEASE mov qword ptr [lock], 0
```

On legacy CPUs without HLE, prefixes decode as `REPNE`/`REP` ignored → lock executes normally [1]. Hardware policy decides retry count internally (Implementation-Unspecified). *RTM*:

```rust
// Rust RTM wrapper using nightly core::arch::x86_64
use core::arch::x86_64::{_xbegin, _xend, _xabort, _XBEGIN_STARTED};

const RETRY_MAX: usize = 6;
fn rt­m_elide_lock<F>(lock: &AtomicBool, f: F) where F: Fn() {
    let mut retries = 0;
    loop {
        let status = unsafe { _xbegin() };
        if status == _XBEGIN_STARTED as u32 {
            if lock.load(Ordering::Relaxed) == false {
                f();
                unsafe { _xend(); }
                return;
            } else {
                unsafe { _xabort(0xFF); }
            }
        } else {
            // Decode _xabort code
            if status & 0x02 != 0 { // explicit abort lock held
                retries += 1;
            }
            if (status & 0x04) != 0 || retries > RETRY_MAX {
                break;
            }
        }
    }
    // Fallback: acquire spinlock non-transactionally
    while lock.swap(true, Ordering::Acquire) {
        core::hint::spin_loop();
    }
    f();
    lock.store(false, Ordering::Release);
}
```

The **lemming effect** occurs when thread A acquires lock non-transactionally after repeated aborts, causing all other threads attempting lock elision to see lock held inside transaction, abort, and transition to fallback without ever successfully eliding [2]. Mitigation: test lock free before `XBEGIN` and use bounded spin with `pause`. TAA and MDS mitigations: On affected Intel parts, CP buffer aliasing could leak data via speculative load after async abort from another thread writing transactionally accessed address [3]. Mitigation is forced RTM abort via microcode `IA32_TSX_CTRL` and flushing buffers with `VERW`. This effectively killed TSX in data centers after 2021 [3]. > **Theorem 2 (Lock Subscription Necessity):** For lock elision under eager HTM with strong isolation but without lock subscription, there exists an execution that violates serializability: a transaction reads intermediate state from a fallback critical section holding lock that the transaction did not observe as acquired between read of object and commit. *Proof sketch.* Construct interleaving thread T0 fast path reads object o=0, then thread T1 fallback acquires lock, writes o=1, critical, unlock. T0 reads o's new value after T1 commits but before T0 commits, because lock not in readset. No conflict detected. Final state not serializable. Adding `if lock != free abort` couples commit to lock line coherence so fallback's unlock → invalidates fast path. ∎

### 4.2 POWER8 / POWER9 HTM: Instruction-Level Semantics and Suspended State for HyTM

POWER ISA introduces:

```c
// GCC low-level POWER HTM
#include <htmintrin.h>
unsigned texasr;
if (__builtin_tbegin(0)) {
    if (is_locked(lock)) __builtin_tabort(0);
    // critical
    __builtin_tend(0);
} else {
    texasr = __builtin_get_texasr();
    if (_TEXASR_PERSISTENT(texasr) ) goto fallback_lock;
    else retry();
}
```

Key facilities:

* **`tbegin.` with ROT bit (bit 0)**: `tbegin. 0` vs `1` discerns normal vs ROT. ROT bypasses read-set tracking; ideal for lock elision fast path where only writes need rollback if concurrent non-transactional lock holder exists [4]. * **Suspended state**: `tsuspend`/`tresume` allows inspection of HyTM NOrec clock without adding it to readset. However entering suspended mode is *heavy* and may cause footprint overflow if many lines touched [5][6]. * **Persistent vs transient**: `TEXASR[7]` persistent bit indicates whether likely to succeed on retry. Software should fallback on persistent (footprint overflow, disallowed) but retry on transient (conflict) [7]. POWER HTM uses **requester-loses for loads, requester-wins for stores** in many implementations [5]. Thus a transactional reader may abort writer (stores win) but not vice-versa, contrasting Intel's requester-wins. Capacity: POWER's TMCAM holds ~64 lines (?), aggregate access ~ 8KB per core before abort [4]. SI-HTM paper [4] demonstrates real OLTP footprints > 20KB exceed HTM, requiring Snapshot Isolation relaxation with quiescence phase to dodge capacity. | Feature | Intel Haswell/Broadwell RTM/HLE | POWER8/POWER9 HTM |

POWER's paradoxical memory ordering noted by Scott & Brown [6]: transaction in suspended mode may see memory operations that violate program order unless `lwsync` inserted. ### 4.3 Hybrid TM: Requester-Wins/Loses, Cohorts, and Metadata Perturbation Avoidance

HyTM goal is to avoid writing global metadata from hardware path, as that would overflow capacity and create false conflicts. Classic HyTM (Damron et al. 2006) had HTM fast path check sequence clock `Orec` but not increment it; STM path locks orec. Modern *Hybrid Cohorts* [5]:

* No modification to global metadata by H. H performs read-set inclusion of clock? That would perturb. Instead Cohort algorithm arranges:

```
Hardware path:
    sequence_snapshot = global_seq (non-tx suspended load)
    begin tx
    if global_seq != sequence_snapshot or soft_lock != 0: abort
    ... tx body, direct accesses ... commit

Software path (SOFT):
    acquire cohort_lock
    global_seq++
    ... STM accesses via Orec or Undo-log ... global_seq++
    release
```

Hardware transactions cannot commit while software transaction holds cohort lock, but they are allowed to abort and retry. Software transactions have low per-access overhead because they don't need instrumentation to cooperate with in-flight hardware reads (hardware validates automatically via coherence) [5]. This trades *concurrency* for *hardware overhead*: no per-access `Orec` read in H, preserving capacity for data. Evaluation on Haswell 8-thread shows Cohorts competitive with `Intel's HLE` and `NOrec HyTM` (+5-18% over STM alone) [5]. *Haskell encoding of HyTM choice monad vs. real HTM:*

```haskell
{-# LANGUAGE GADTs #-}
-- STM vs HTM vs HyTM abstract
data Tx a where
  HRead :: Addr -> Tx Value
  HWrite :: Addr -> Value -> Tx ()
  SRead :: Orec -> Addr -> Tx Value
  Abort :: Tx a

-- Non-perturbing fast path: no Orec write
hardwarePath :: Tx () -> Tx Bool
hardwarePath body = do
  seq0 <- liftIO $ peekGlobalSeq -- suspended load, not tracked
  started <- liftIO $ xbegin
  if not started then return False
  else do
    conflict <- checkLockHeld
    if conflict then abort else do
        body
        ok <- liftIO xend
        return ok
```

Essential correctness condition: STM commit is serialized with HTM commit via `global_seq` that HTM *reads* transactionally only [5]. ### 4.4 Coherence Integration and Lock Elision Correctness: MESIF/XMESI Extensions

Transactional coherence extends MESI/XMESI with per-line `TxRead`/`TxWritten` bits, flash-cleared on commit/abort [6]. Protocol transitions:

* Store in Tx state → buffers privately, line enters `TM`, broadcasts intent but defers response to `XEND`. On abort → discard. * Remote GETX invalidates → coordinator searches TMCAM; if hit in R or W set → *aborts local tx before responding* (eager). This yields strong isolation: non-transactional store after committing will abort concurrent transaction if they intersect [5]. MESIF variant used in Intel: Forward state helps sharing for readset without invalidating, but transactional lines cannot be Forwarded if they diverge. Escape actions (non-transactional loads inside transaction) implemented by:

- Intel Sapphire Rapids `LDTRK` suspend: `XSUSLDTRK`/`XRESLDTRK` enable non-tracked loads after 2022 [6]
- POWER `suspend` bit masks transaction bit for subsequent accesses. Lock elision's coherence integration subtlety:

* Fallback *must* issue `lock` acquisition as coherence exclusive invalidation to abort all elided readers subscribed to lock line. If fallback lock word remains on the *same* line as data (false sharing), capacity overflow may abort despite no logical conflict. Best practice: align lock on separate line with `__attribute__((aligned(128)))` [2]. ---

## 6 Limitations

1. **Best-effort is uncomposable**. Nested transactions with HLE inside RTM and vice versa abort unconditionally on some Haswell steppings [2]. Real software must serialize composition at library edge.

2. **Capacity wall persists**. 8KB functional limit eliminates implicit benefit for OLTP with footprints > page; even SI-HTM's quiescence reduces but does not eliminate abort storms [4]. Real systems resort to *partitioning* (epoch-based SI with early release of versions from TMCAM) or *collective aborts*.

3. **Interrupt and TLB shootdown vulnerability**. Page fault or timer tick inside transaction → abort. OS activity frequency ~1kHz limits transaction duration to <1ms; cannot enclose syscalls. Thus HTM unsuited for I/O-hugging transactions [5].

4. **Security erasure**: Intel TAA forced disablement exemplifies that HTM, by forwarding speculative buffer content to dependent loads, defeats speculative isolation assumptions [3]. Persistent TM security extensions for NVM correlate but disjoint.

5. **POWER suspension subtlety**: Escape actions that perform non-transactional stores *can* expose intermediate HTM writes to non-transactional observers, forming *transactional paradoxes*—circular dependencies where suspended load observes state not yet committed but allows commit of newer value [6]. Programmer must emit `isync`/`lwsync`.

6. **HyTM serialization bottleneck**. Hybrid Cohorts requires all Hardware to quiesce while Soft active to guarantee correctness if H avoids metadata writes. This creates tradeoff: high conflict workloads degrade to STM throughput; low conflict sees gain. More permissive HyTM (`HyNOrec_DSS`) attempts concurrent H+S commit but needs `Orec*` read-set inclusion of size `|S writeset|` in H—again capacity limiting [5].

## 7 Conclusion

This thesis structured a *best-effort fallback taxonomy* for two commercial HTM remnants and their hybrid synthesis. We argued Intel RTM/HLE and POWER HTM share essential four-fallible loci: *capacity, conflict, forbidden, explicit*, but differ critically in conflict resolution, capacity metric granularity, isolation mode, and suspended mode semantics [1][4]. Best practice requires: subscription to fallback lock to preserve atomic visibility, persistent vs transient classification for retry economy, ROT or equivalence for elision to avoid read-set pressure, avoidance of global metadata writes from hardware path to eliminate capacity perturbation [5], and explicit fence for suspended modes to eliminate paradoxical coherence.

Future evolution tracks: Arm TME's single-path managed transactional memory may remedy Intel's dual-path complexity but inherits best-effort classification; Blue Gene/Q's kernel-assisted TM suggests OS-managed spill of speculative state into DRAM eliminates pure capacity abort yet requires translation shootdown handling; and persistent HTM with buffered durability may harmonize NVM flush restrictions that today forbid `CLWB` inside HTM [3][4].

HTM's pedagogical moral remains: *hardware can accelerate coordination only if software retains a verified, cooperative, non-transactional fallback that linearizes despite* optimistic oblivious commit protocol interleaving.
