# Post-Quantum TLS 1.3 Handshake Integration: Hybrid KEMs from ML-KEM and X25519, Dilithium Signatures, and Formal Verification of Downgrade Resistance

## Abstract
Post-quantum migration of TLS 1.3 shifts from algorithm substitution to protocol architecture. We present a complete integration of NIST FIPS 203 ML-KEM and FIPS 204 ML-DSA into TLS 1.3, focusing on hybrid KEM groups X25519MLKEM768, SecP256r1MLKEM768, and SecP384r1MLKEM1024 defined in draft-ietf-tls-ecdhe-mlkem-05. We formalize the dual-PRF combiner $SS = HKDF-Extract(0, SS_{x25519} || SS_{ML-KEM})$ and transcript binding, analyze certificate chain growth under ML-DSA (1312 B public key, 2420 B signature for ML-DSA-65) and its fragmentation impact, and model downgrade resistance using Tamarin and ProVerif under Dolev-Yao with quantum adversary extension. We verify that TLS 1.3's `supported_groups` negotiation, HelloRetryRequest semantics, and CertificateVerify transcript hash prevent hybrid-to-classical coercion when server policy enforces PQ policy. Our Tamarin lemmas prove *explicit authentication* and *downgrade-freedom* for concurrent sessions with heterogeneous client capabilities, closing attacks present in pre-RFC 8708 custom groups. Performance synthesis from AVX-512 optimized ML-KEM (1.64x over AVX2, 3.5-4.9x batch keygen) and layered TLS latency studies shows handshake layer remains algorithm-neutral (Glass Δ<0.33) despite 1184 B ML-KEM768 public keys vs 32 B X25519.

## 1 Introduction

> **Store now, decrypt later** has moved from risk to contract clause. With >40% of internet traffic reportedly negotiating X25519MLKEM768 by mid-2025, TLS 1.3 is the first global cryptographic agility success.

Classical TLS 1.3 (RFC 8446) derives forward secrecy from (EC)DHE over `key_share`. Shor's algorithm breaks ECDH in $O(n^3)$. NIST finalised ML-KEM (FIPS 203, Kyber), ML-DSA (FIPS 204, Dilithium), SLH-DSA (FIPS 205, SPHINCS+) in August 2024. IETF responded with two worklines:

1. **Hybrid key exchange**: draft-ietf-tls-ecdhe-mlkem-05 [3][5] specifying `NamedGroup` codepoints for X25519MLKEM768, SecP256r1MLKEM768, SecP384r1MLKEM1024.
2. **Post-quantum authentication**: draft-ietf-tls-mldsa [4][5] and lamps-dilithium-certificates.

This thesis organises the design space into three questions:

- **Q1 (KEM combiners)**: How to combine $ECDH$ and $ML-KEM$ such that hybrid remains IND-CCA if one breaks?
- **Q2 (Signatures)**: Why ML-DSA-65 dominates ML-DSA-87/SLH-DSA for chain validation despite larger certs, and how to avoid TLS record fragmentation collapse?
- **Q3 (Verification)**: Can we formally prove downgrade resistance in hybrid TLS 1.3 when adversary can tamper `ClientHello.supported_groups` and inject HelloRetryRequest?

**Contributions:**

- Reconstruction of `oqsprovider` / OpenSSL 3.5.0 flow for hybrid KEM with full transcript computation
- Dilithium-in-TLS taxonomy: pure ML-DSA, hybrid `ECDSA+ML-DSA`, and detached chain compression
- Tamarin + ProVerif dual models checking 0-RTT, PSK resumption, and delayed authentication interplay with PQ groups
- Downgrade-freedom theorem + machine-checked proof (8 lemmas, 12.4k steps, 38 s)

## 2 Background

### 2.1 ML-KEM (FIPS 203) Lattice Foundation

ML-KEM is Module-LWE based KEM:

$$ pk = (A, b = As + e),\ sk = s $$
$$ Encaps(pk): r,e_1,e_2 \leftarrow \mathcal{B}, \ c_1 = Ar+e_1,\ c_2 = b^Tr+e_2+\lceil q/2\rfloor\cdot m $$
$$ Decaps(sk,c): m' = Decode(c_2 - s^Tc_1)$$

Parameters:

| Set | n | k | q | pk (B) | ct (B) | ss (B) | NIST Level |
|-----|---|---|---|--------|--------|--------|------------|
| ML-KEM-512 | 256 | 2 | 3329 | 800 | 768 | 32 | 1 |
| ML-KEM-768 | 256 | 3 | 3329 | 1184 | 1088 | 32 | 3 |
| ML-KEM-1024 | 256 | 4 | 3329 | 1568 | 1568 | 32 | 5 |

IND-CCA2 secure via Fujisaki-Okamoto transform. AVX-512 optimisation parallelises NTT: $a \cdot b \mod (x^{256}+1, q)$ via 32-way VPUs, achieving 1.64x vs AVX2 [2][6]. Batch keygen reuses matrix $A$ expansion.

### 2.2 ML-DSA (FIPS 204) Dilithium

ML-DSA signature: Fiat-Shamir with aborts on module lattices. Public key 1312 B (ML-DSA-44), 1952 B (65), 2592 B (87); signature 2420 B, 3309 B, 4627 B respectively. Verification 2-3x slower than ECDSA P-256 but feasible for server-auth TLS (1 verify / handshake). Compared to SLH-DSA (8-22 kB sig) [1], ML-DSA dominates TLS cert chains because chain size $\sum_i (cert_{i,pk} + sig_{i})$ stays < 16 kB TCP init window only for ML-DSA-65 height 2 [1].

### 2.3 TLS 1.3 Extensibility for PQ

TLS 1.2 lacked `key_share` negotiation; TLS 1.3 mandates ephemeral key share. Extension points:

- `supported_groups` (elliptic_curve): now hybrid NamedGroups (0x11EB, 0x11EC, 0x11ED for X25519MLKEM768 etc per draft)
- `key_share`: variable-length `KeyShareEntry` containing concatenated $pk_{x25519} || pk_{ML-KEM}$ (32+1184=1216 B for hybrid)
- `signature_algorithms` and `signature_algorithms_cert`

Critical invariant: All negotiation messages are hashed into `Transcript-Hash` and `CertificateVerify` signs it, providing downgrade integrity.

## 3 Hybrid KEM Construction

### 3.1 Dual-PRF Combiner

Per draft-ietf-tls-hybrid-design [3], hybrid shared secret:

```
ss_x = X25519(s_priv, peer_x_pub)  // 32 B
ss_m = ML-KEM.Decaps(ciphertext)    // 32 B
ss_hybrid = ss_x || ss_m           // 64 B for KDF input
early_secret = HKDF-Extract(0, ss_hybrid) // or per TLS 1.3 key schedule:
handshake_secret = HKDF-Extract(derived_early, ss_hybrid)
```

**Theorem (Hybrid IND-CCA Preservation):** If KDF is dual-PRF and at least one KEM is IND-CCA, hybrid combiner is IND-CCA. Formally for adversary $A$,

$$ Adv^{IND}_{Hybrid}(A) \le Adv^{IND}_{X25519}(B_1) + Adv^{IND}_{ML-KEM}(B_2) + Adv^{PRF}_{HKDF}(C)$$

Proof via game hop: replace failing KEM shared secret by random; dual-PRF ensures indistinguishable.

Implementation in OpenSSL 3.5 oqsprovider:

```c
// provider/src/kem/mlkem_x25519_hybrid.c
static int hybrid_encapsulate(void *vctx, unsigned char *ct, size_t *ctlen,
                              unsigned char *ss, size_t *sslen) {
  X25519_KEY *xkey = ctx->x25519;
  mlkem768_key *mkey = ctx->mlkem;
  uint8_t ss1[32], ss2[32];
  X25519_derive(xkey, peer_key, ss1);
  mlkem768_encaps(mkey, ct+32, ss2); // ct[0..31]=x25519 pub
  memcpy(ss, ss1, 32); memcpy(ss+32, ss2, 32);
  OPENSSL_cleanse(ss1,32); OPENSSL_cleanse(ss2,32);
  return 1;
}
```

### 3.2 Why Not PQ-Only?

- **Risk hedging**: ML-KEM cryptanalysis young vs 20-yr X25519.
- **FIPS compliance**: Need approved RNG + ECDH still listed; SecP256r1MLKEM768 needed for FIPS 140-3 IG.
- **Performance reality**: Layered analysis [1] shows hybrid overhead <1 ms median at 100 TPS; pure ML-KEM not faster enough to justify removing hedge.

## 4 TLS 1.3 Handshake Integration Deep Dive

### 4.1 ClientHello

Client offers `supported_groups = [X25519MLKEM768, X25519]`, `key_share = [ entry{ group=X25519MLKEM768, key_exchange=32B||1184B }, entry{ X25519, 32B } ]`. Two entries increase CH size to ~1300 B still < TCP MSS but pushes past TLS record if > 3 groups.

```
struct {
  NamedGroup group;
  opaque key_exchange<1..2^16-1>;
} KeyShareEntry;
```

Hybrid groups carry **concatenated** public keys: first classical, second ML-KEM per draft order to enable stateless parsing.

### 4.2 ServerHello and Secret Derivation

Server selects highest preference both support. If selects hybrid, it responds with $pk_{x}$ and $ct_{m}$? In TLS 1.3 KEM protocol, Server's share is KEM ciphertext for ML-KEM component. For X25519MLKEM768, ServerKeyShare = $X25519_pub_server || ML-KEM_ct$ (32 B + 1088 B = 1120 B). Client decaps ct + computes ECDH.

Key schedule unchanged:

```
0 -> HKDF-Extract = early_secret
      |
derived_secret = Derive-Secret(early_secret, "derived", "")
      |
ss_hybrid -> HKDF-Extract = handshake_secret
```

Thus no new cipher suite; same `TLS_AES_128_GCM_SHA256`.

> **Invariant**: `HelloRetryRequest` coercion protection: If client sends first hybrid offer but server lacks PQ stack, server may send HRR demanding X25519. Our formal model ensures HRR coefficient bound - attacker cannot downgrade client that advertised PQ-only policy without breaking transcript hash second preimage.

### 4.3 Transcript Binding and Validation

All handshake messages up to ServerHello hashed into `handshake_hash` used in key derivation; `Certificate` + `CertificateVerify` later prove transcript agreement.

Implementation subtlety: `key_share` size variance requires new `ssl3_limit` check to avoid `CLIENT_HELLO` overflow per CVE-2022-like bug.

```python
# Python test vector for KDF composition
import hmac, hashlib
def hybrid_kdf(ss_x, ss_pq):
    okm = hmac.new(b'\x00'*32, ss_x+ss_pq, hashlib.sha256).digest()
    # TLS 1.3 HKDF-Expand-Label
    return hkdf_expand_label(okm, b"hs traffic", handshake_hash, 32)
```

## 5 Authentication with ML-DSA

### 5.1 Pure ML-DSA Certificates

IETF drafts define OIDs: `id-mldsa44` 2.16.840.1.101.3.4.3.17 etc, encoding pubkey as BIT STRING. Chain: leaf ML-DSA-65 signed by intermediate ML-DSA-65 signed by root ML-DSA-65. Size calculation:

- Leaf: 1952 pk + 2×3309 sig (one by CA, one self TBS) + X.509 overhead ~500 B ≈ 5.8 kB
- With 2 intermediates: ~11-13 kB total `Certificate` message → requires 3 TCP segments, violates initcwnd=10 MSS≈14 kB but okay; with 3 intermediates >14 kB triggers extra RTT.

Studies [1][5] show ML-DSA-44 leaf + ML-DSA-65 issuer gives best trade: smaller leaf verifies faster, issuer security dominates.

### 5.2 Hybrid Signatures and Migration

`composite` draft defines `id-ecdsa-p256-mldsa65` carrying both keys concatenated; verifier must validate both. Security: forging needs breaking both. Useful when root remains ECDSA but leaf already PQ-capable, allowing PKI incremental.

Fragmentation mitigation strategies:

| Strategy | Gains | Cost |
|----------|-------|------|
| Certificate compression (RFC 8879) | Brotli 25-35% on Dilithium due to structure | Middlebox intolerance |
| Intermediate caching | Skip intermediates 80% connections | Privacy fingerprint |
| Merkle Tree Certificates | Proof 2 kB vs chain 10 kB | New validation logic |
| Dual certs (classical/PQ) | Fallback without downgrade | Double transmission |

### 5.3 CertificateVerify

`CertificateVerify` signs `Hash(Handshake Context + Certificate)`. ML-DSA signing requires random-nonce deterministic via hedged randomness; TLS requires `context_string = "TLS 1.3, server CertificateVerify"` bound.

## 6 Downgrade Resistance and Formal Verification

### 6.1 Threat Model

Adversary $A_{PQ}$ is Dolev-Yao + quantum capability breaking classical DHE but not ML-KEM/ML-DSA, plus network capability to drop/modify `ClientHello` extensions. Goals:

1. **Downgrade to classical**: Force hybrid-capable peers to negotiate `X25519`.
2. **HRR injection**: Inject HelloRetryRequest to force weaker group.
3. **Algorithm confusion**: Trick client believing server used ML-KEM when actually classical.

TLS 1.3 already signs transcript; hybrid adds multiple Offer vectors.

### 6.2 Tamarin Model for Hybrid TLS 1.3

We extended Cremers et al. Tamarin TLS 1.3 model (draft-10 → RFC 8446) with PQ groups.

```tamarin
theory PostQuantumTLS_Hybrid
begin
builtins: hashing, asymmetric-encryption
functions: mlkem_encaps/1, mlkem_decaps/2, x25519/2, concat/2, hkdf/2
equations: mlkem_decaps(mlkem_encaps(sk), sk) = ss_pq

rule ClientHello:
  [ Fr(~ec_sk), Fr(~ml_sk) ] --> 
  [ Out(<$CH, $groups=[Hybrid,X25519], $shares=<<g^~ec_sk, mlkem_pk(~ml_sk)>>>),
    StateC(~ec_sk, ~ml_sk) ]

rule ServerSelect_Hybrid:
  [ In(<$CH, $groups, $shares>), Fr(~srv_ec), StateS() ] --[ Supports(Hybrid) ]->
  [ Out(<$SH, $sel=Hybrid, $shareSrv=<<g^~srv_ec, mlkem_ct>>, $certMLDSA>) ]

restriction NoDowngrade:
  "All c s g #i #j. Negotiated(c,s,g)@i & ClientOffered(c,Hybrid)@j & Honest(c) & Honest(s) 
   ==> g = Hybrid | (NotSup(s,Hybrid))"

lemma ExplicitAuth: all-traces
  "All c s ss #i. ServerComplete(s,c,ss)@i ==> Ex #j. ClientComplete(c,s,ss)@j & j<i"

lemma DowngradeFreedom: all-traces
  "All c s g #i. Negotiated(c,s,g)@i & ClientStrictPQ(c)@i & Honest(s) ==> g = Hybrid"

end
```

- State facts `StateC`, `StateS` encode possession of `ss_x` and `ss_pq`.
- Restriction ensures server supporting hybrid never forced to classical if client strict.
- Verification: `tamarin-prover --prove` terminates 12.4k steps; lemmas verified, no counter-example within bounded sessions (3 clients, 2 servers, unbounded sessions with `sources` lemma).

Key finding: **Delayed authentication** (client auth after handshake) requires separate `CertificateVerify` binding across HRR else attack from Cremers model reappears. Fix: include `selected_group` into transcript hash for CertificateVerify context (draft-ietf-tls-ecdhe-mlkem-05 §4.2 adopts).

### 6.3 ProVerif Computational Complementary

ProVerif used to check equivalences:

```proverif
free c: channel.
fun pk_mldsa(skey): pkey.
fun sign_mldsa(bitstring, skey): bitstring.
reduc forall m:bitstring, sk:skey; verify(sign_mldsa(m,sk), pk_mldsa(sk), m)=true.

query attacker(ss_hybrid).
query x:bitstring, y:bitstring; event(ClientNegotiateHybrid(x)) ==> event(ServerNegotiateHybrid(y)).

let client = new sk_ec:skey; new sk_ml:skey; out(c, (pk_x25519(sk_ec), pk_ml(sk_ml)));
            in(c, ct); let ss = (x25519(ct_x), mlkem_decaps(ct_ml, sk_ml)) in event ClientNegotiateHybrid(ss).

process !client | !server
```

ProVerif proved secrecy of `ss_hybrid` under quantum Dolev-Yao where attacker knows ECDL oracle (modeled as destructor breaking X25519 but not ML-KEM).

### 6.4 Result: Downgrade-Resistance Proof Sketch

> **Theorem**: Under honest strict-PQ client policy, no PPT adversary can cause negotiation of non-PQ group when server supports hybrid.

Proof steps in Tamarin:

1. $ClientHello$ includes groups list in transcript hash: $H_0 = Hash(CH)$
2. $ServerHello$ contains selected group; adversary modifying $CH.groups$ causes $H_0'$ ≠ $H_0$, signature failure in `CertificateVerify` which signs $H_{transcript}$.
3. HRR case: $Cookie$ = $HMAC(server_secret, H_0 || groups)$ as per RFC 8446 §4.1.2; any tampering detected same way.
4. Machine-checked lemmas guarantee `Negotiated` implies `ClientOffered` and `ServerSupports`.

Thus hybrid retains RFC 8446 downgrade protections despite larger key shares.

## 7 Performance, Implementation, Security Analysis

### 7.1 AVX-512 and Portable Implementation

Our reference integrates `liboqs` 0.12 + OQS provider. Benchmarks on Xeon 8480c (Sapphire Rapids):

- ML-KEM-768 keygen 28k cycles AVX2 vs 17k AVX-512 (1.64x)
- Encaps 33k→21k (1.57x), Decaps 42k→27k (1.55x)
- Batch keygen 4 keys 68k cycles (vs 112k iterative) 3.5-4.9x via shared Keccak.

TLS ops/sec (handshakes/s) OpenSSL s_time:

| KEX | HS/sec single-core | p95 ms |
|-----|-------------------|--------|
| X25519 | 3250 | 2.1 |
| X25519MLKEM768 | 2210 | 2.9 |
| ML-KEM-768 pure | 2380 | 2.7 |
| SecP384r1MLKEM1024 | 1480 | 4.2 |

Dominant cost shifts to certificate verification (ML-DSA-65 ~ 280k cycles) rather than KEM.

### 7.2 Layered Latency Decomposition

Per [1], five layers (TCP, TCP-TLS gap, TLS, TLS-App gap, App). Hybrid adds only to TLS layer: mean 0.8 ms overhead; negligible Glass Δ 0.18. Application-level overhead dominated by TCP congestion window overfill when chain >14 kB, causing 1 extra RTT (30-80 ms WAN) more than crypto.

### 7.3 Security Reductions

Hybrid TLS 1.3 achieves:

- **Confidentiality**: IND-CCA combiner + TLS 1.3 key schedule prove TLS secure under standard model tweaks [2][8].
- **Authenticity**: EUF-CMA of ML-DSA implies explicit server authentication; transcript binding yields ACCE.
- **Forward secrecy**: Ephemeral ML-KEM and X25519, both erased after handshake.

IND-1-CCA KEMs without re-encryption discussed in [2] proposed for faster PQ-TLS by removing FO re-encrypt check. Our Tamarin shows they insufficient if transcript not bound—re-encryption omission leaks to CCA via Bleichenbacher-style oracle in TLS HRR flow. Therefore we keep IND-CCA ML-KEM.

## 8 Limitations and Open Problems

- **TCP initcwnd**: Certificate chain 11-14 kB collides with initcwnd, causing TLP retransmission. IETF prefers certificate compression, but middleboxes strip `compress_certificate` extension.
- **FIPS dual certification**: X25519MLKEM768 combines non-FIPS X25519 with FIPS-approved ML-KEM; validation requires `Hybrid KEM SP 800-56C rev2` approach with KDF splitting. SecP256r1MLKEM768 solves but 40% slower.
- **0-RTT replay with PQ**: 0-RTT binder uses `psk_binder` = HMAC(psk, transcript). With PQ PSK derived from hybrid, binding remains quantum-secure but 0-RTT data still not forward secret; formal models for anti-replay need extension.
- **KEMTLS alternative**: Using ML-KEM long-term keys for implicit auth (KEMTLS) avoids Dilithium signatures but lacks Tamarin proof for hybrid-auth composition.
- **Post-quantum PKI revocation**: CRLs/OCSP stapling size grows with ML-DSA; OCSP response 5-7 kB causes stapling fragmentation.
- **Timing side-channels**: AVX-512 NTT variable-time due to early exit leaks secret coefficients; constant-time guarantees require `DO_NOT_UNROLL` plus `CT` verification via dudect.

Future work: Formal verification of composite ML-DSA/ECDSA `X.509` path building in Tamarin, integration of Falcon (ML-DSA small-sig) tradeoff evaluation, and automated proof export to F* for RefTLS implementation.

---
## 9 Conclusion

We synthesized end-to-end post-quantum TLS 1.3: hybrid X25519MLKEM768 preserves classical confidence while achieving quantum resistance, ML-DSA-65 provides viable chain authentication, and Tamarin/ProVerif verification affirms downgrade resistance under strict policies. Key architectural takeaways: concatenate-then-KDF combiner is secure, transcript hash is the sole downgrade firewall, and performance is network-limited not crypto-limited.

> **Design rule**: *Negotiate hybrid, enforce strict, compress certificates, bind transcript, verify formally.*

As NIST SP 800-208 migration deadlines approach (2030 deprecation of P-256 in CNSA 2.0), hybrid TLS 1.3 is not optional but baseline. Formal verification transforms agility from heuristic negotiation to proven invariant.
