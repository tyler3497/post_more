# Zero-Copy Serialization and the Object-Capability RPC: A Comparative Analysis of Cap'n Proto and FlatBuffers — Arena Allocation, Pointer Swizzling Elimination, Schema Evolution, and Promise Pipelining

## Abstract

Conventional serialization frameworks interpose an expensive parse-and-allocate phase between wire bytes and usable data, incurring *O(n)* time and *O(n)* allocation even when an application inspects only a constant-sized subset of a message. This thesis analyzes two designs that reject that cost model: **Cap'n Proto** and **FlatBuffers**, whose on-wire layout *is* the in-memory layout, permitting *O(1)* random access with no deserialization. We formalize Cap'n Proto's pointer model — 64-bit relative pointers, far and double-far pointers across a segmented arena — and prove that **pointer swizzling is eliminated** because relative addressing is position-independent. We contrast this with FlatBuffers' forward-built buffer of tables, structs, and deduplicated vtables; analyze schema evolution via ordinals, default-XOR encoding, and vtable bounds checks; and examine Cap'n Proto's capability-based RPC, where *promise pipelining* collapses chained calls from *k* round trips to one. Published benchmarks and amplification-traversal security analysis complete the treatment. The wire-format-is-memory-format principle, constrained by bounds-checked accessors and schema-directed layout, is the asymptotically optimal design for high-throughput message passing.

---

## 1. Introduction

Serialization is the price of distribution. Whenever a process must move structured data across an address-space boundary — a socket, a pipe, a shared-memory region, or a persistent log — the data must be encoded into a linear octet stream and, conventionally, decoded back into heap-resident objects at the destination. Protocol Buffers, the industry standard for fifteen years, performs this decode eagerly and totally: parsing is an *O(n)* walk that allocates an object graph proportional to message size [2]. The cost is paid regardless of whether the receiver reads one field or all of them.

Two modern systems refuse this bargain. **Cap'n Proto**, designed by Kenton Varda (the principal author of Protocol Buffers v2) and first released in 2013 as the serialization substrate of Sandstorm.io, and **FlatBuffers**, developed at Google by Wouter van Oortmerssen and open-sourced in 2014 for game engines, both produce wire encodings that the CPU can read *directly*: the received buffer is cast, and generated accessors compute field addresses by fixed arithmetic [1][7].

This thesis (i) formalizes Cap'n Proto's wire format — segments, 64-bit relative pointers, far pointers — and proves **pointer swizzling is eliminated** because relative addressing is position-independent; (ii) contrasts FlatBuffers' vtable-based tables, its reverse arena builder, and the one-indirection cost of evolution-tolerant access; (iii) treats schema evolution in both systems; and (iv) analyzes Cap'n Proto's capability-based RPC, where **promise pipelining** collapses chained call graphs from *k* round trips to one [5].

## 2. Background

### 2.1 The parse-then-allocate cost model

In a classic tag-length-value codec (Protocol Buffers, Thrift's compact protocol, ASN.1 BER), deserialization performs two inseparable tasks: *walking* the stream and *materializing* native objects. Materialization allocates one heap object per composite node, one array per repeated field, one string copy per string field — an *O(n)* allocation storm that thrashes the allocator and pollutes the data cache.

> **Theorem:** *Zero-parse access.* If the wire encoding of a message is byte-identical to its in-memory representation under the reader's ABI, then reading any field requires only address arithmetic and memory loads, with no parse step and no allocation beyond the buffer itself.

The proof is by construction.

### 2.2 A brief history of the two systems

Cap'n Proto emerged from Varda's dissatisfaction with Protocol Buffers at Google and in the Sandstorm project: serialization consumed a dominant fraction of CPU in typical request handlers, and the cost was almost entirely avoidable [2]. FlatBuffers emerged independently from the game industry's need to *mmap* enormous static assets and read them without load-time parsing; van Oortmerssen's design prioritized optional fields and forward/backward compatibility across long-lived game binaries [6].

Both are *schema-driven*: a `.capnp` or `.fbs` schema file is compiled to typed accessors in C++, Rust, Go, Java, Python, and others. The schema is the *type map* that lets readers interpret the buffer; no per-instance metadata describes the layout beyond what the pointer words and vtables carry.

### 2.3 Pointer swizzling: the classical problem

Object graphs in RAM contain absolute addresses. When such a graph is written to a file or socket, absolute pointers are meaningless to the reader — a different virtual address space, randomized further by ASLR, invalidates every address. Classical solutions fall into two families:

- **Pointer swizzling at load time**: scan the buffer, find every pointer, rewrite it to a local address. *O(n)* and destructive.
- **Serialization by value with re-linking**: serialize objects with stable IDs and rebuild the graph on receipt. *O(n)* plus allocation.

Cap'n Proto's answer is to *never store absolute pointers at all*: every pointer on the wire is a **relative offset**, measured in 64-bit words, from the word following the pointer itself:

```
target_address = pointer_address + 8 + (offset × 8)
```

This single equation is the heart of the system [3]. It makes the message *relocatable*: `memcpy` the entire buffer anywhere in memory and every pointer remains valid, because every pointer is self-relative. **Pointer swizzling is eliminated** — there is no load-time fixup pass, no swizzle table, no relocation directory. The same arithmetic is what permits true zero-copy: the kernel can DMA the buffer into any page, and the reader's accessors work immediately.

## 3. Methodology

Our analysis combines (i) close reading of the normative specifications — the Cap'n Proto encoding specification [1] and the FlatBuffers internals documentation [4]; (ii) differential study of the reference implementations (capnproto C++, google/flatbuffers C++); (iii) published benchmarks and community zero-copy analyses [3][6][7]; and (iv) the RPC protocol description in `rpc.capnp` and the E-language capability literature behind promise pipelining [5]. We evaluate along four axes: **layout efficiency**, **access complexity**, **evolution semantics**, and **distribution semantics**.

## 4. Deep Dive

### 4.1 Cap'n Proto: segments, pointers, and the arena

A Cap'n Proto message is a sequence of **segments** — contiguous runs of 64-bit words. The stream begins with a *segment table*: a word count, then one (word count, padding) pair per segment, locating each segment in the stream. Pointers carry a two-bit *kind* tag in the low bits of the pointer word:

| Kind bits | Meaning |
|---|---|
| `00` | Struct pointer: offset to a struct's data section |
| `01` | List pointer: offset, element count, and 3-bit element size |
| `10` | Far pointer: lands in a *different* segment |
| `11` | Capability pointer: index into the RPC capability table |

A struct pointer word packs the offset (30 bits, in words, signed), the data-section size (16 bits, in words), and the pointer-section size (16 bits, in words). The data section holds all scalar fields packed tightly, aligned to their native sizes; the pointer section holds all reference fields as 64-bit pointer words. **Scalars group at the front, pointers at the back** — a deliberate locality optimization: the "hot" primitive data occupies the first cache lines of the struct, while the pointer tail is touched only when traversing [3].

Construction happens in a growable **arena**: the builder allocates from the current segment until it is exhausted, then appends a new segment (typically doubling in size, amortizing allocation to *O(1)* per word) and links it with a *far pointer* — a pointer word whose payload names a segment ID and an intra-segment offset. Because the arena never moves a live object, all previously emitted relative offsets remain valid — the essential invariant of incremental building.

Default values exploit a further compression: the schema compiler records each field's default, and the wire stores `value XOR default`, so default-valued fields consume **zero bytes** — the optional *packed* encoding then elides zero bytes entirely via a tag-byte run-length scheme [3].

```capnp
# addressbook.capnp — schema excerpt
@0x9eb32e19f86ee174;

struct Person {
  name @0 :Text;
  email @1 :Text;
  phones @2 :List(PhoneNumber);
  employment @3 :Employment;

  struct PhoneNumber {
    number @0 :Text;
    type @1 :Type = mobile;

    enum Type { mobile @0; home @1; work @2; }
  }
}
```

```cpp
// C++: build in the arena, then hand the segments to the transport.
capnp::MallocMessageBuilder message;
AddressBook::Person::Builder person =
    message.initRoot<AddressBook::Person>();
person.setName("Ada Lovelace");
auto phones = person.initPhones(2);
phones[0].setNumber("+1-555-0100");

// The wire bytes ARE the message. No serialize() call exists.
kj::Array<capnp::word> words = capnp::messageToFlatArray(message);
socket.write(words.asBytes());  // reader casts these bytes directly
```

Note what is absent: there is no `SerializeToString`, no marshaling pass. `messageToFlatArray` merely concatenates the already-final segments. Reading is equally direct — `capnp::FlatArrayMessageReader` wraps the received bytes and `getRoot<Person>()` returns an accessor whose field reads are pointer arithmetic plus bounds checks.

### 4.2 FlatBuffers: tables, vtables, and building backwards

FlatBuffers takes a different structural bet. A buffer begins with a `uoffset_t` to the root object. Objects come in two kinds [4]:

- **Structs**: inline, fixed-layout, manually aligned scalars with *no* evolution metadata. Maximum density, zero indirection — but no versioning.
- **Tables**: evolution-tolerant records. A table begins with a *signed* offset (`soffset_t`) to its **vtable**, followed by fields as aligned scalars or offsets. The vtable is an array of `voffset_t` (16-bit) entries: entry 0 is the vtable's byte length, entry 1 is the table's byte length, and entries 2..N are the byte offset of each field within the table — or **zero if the field is absent**.

This per-instance vtable is the crux of the FlatBuffers trade-off. It permits *optional fields*: a writer omits unset fields, and the reader's generated accessor checks the vtable entry, returning the schema default when the entry is zero or out of range (the latter case protects new code reading old data) [4][6]. Vtables are **deduplicated**: tables with identical field-presence patterns share one vtable, amortizing the metadata cost across instances.

The builder constructs the buffer **backwards** — from the end toward the front — because offsets are *forward* references: a parent must know the location of its children before it can write their offsets, and children written first (at higher addresses) make the parent's forward offset simply computable. This single-pass, no-rewrite construction runs in a growable buffer with the same amortized *O(1)* profile as Cap'n Proto's arena.

The comparative table summarizes the structural differences:

| Property | Cap'n Proto | FlatBuffers |
|---|---|---|
| Pointer representation | 64-bit relative word offsets | 32-bit forward offsets (`uoffset_t`) |
| Multi-region support | Multiple segments + far pointers | Single flat buffer |
| Evolution metadata | None per instance (ordinals + defaults) | Per-table vtable (deduped) |
| Struct density | Higher (no vtable) | Lower (vtable indirection) |
| Absent vs. default scalar | Indistinguishable (zero = default) | Distinguishable (vtable entry = 0) |
| Builder direction | Forward bump-allocate in arena | Backward from buffer end |
| Root access cost | Segment table + root pointer | One offset dereference |
| Field access cost | *O(1)* arithmetic | *O(1)* arithmetic + vtable indirection |
| RPC | Built-in capability RPC + pipelining | None (third-party only) |

The density comparison deserves care: Cap'n Proto structs carry no per-instance evolution metadata, so a message of a million small structs is strictly denser than the FlatBuffers equivalent, which pays a vtable pointer per table (deduped vtables amortize this to one 32-bit offset per instance) [1][4].

### 4.3 Schema evolution: ordinals, defaults, and the asymmetry of absence

Both systems reject Protocol Buffers' `required` fields — a lesson learned at Google, where flipping a field from optional to required caused cascading production failures [2]. Evolution rules follow from the layout.

**Cap'n Proto** identifies fields by **ordinal** (`@0`, `@1`, …), not by name. Safe changes: adding new fields (new ordinals appended; old readers ignore the longer sections, new readers see defaults in old data), renaming fields, and wire-compatible integer widening. Unsafe: reusing an ordinal for a different type. The schema file carries a 64-bit file ID and per-field ordinals to make the "don't reuse numbers" rule checkable. A subtle consequence of the no-metadata design: a scalar field set explicitly to its default value is **indistinguishable on the wire from an absent field** — the XOR-with-default encoding zeroes both, mirroring the Protobuf 3 scalar-presence controversy [1].

**FlatBuffers** identifies fields by **field ID** in the vtable. Safe changes: adding new fields (old readers never query the new vtable slots), deprecating fields (the writer stops emitting them; the entry becomes 0). The vtable-length check — "if the accessor's vtable offset exceeds the vtable size, return the default" — makes *new code reading old data* safe, and the zero-entry check makes *old code reading new data* safe [4].

> **Theorem:** *Evolution safety.* In either system, a reader compiled against schema version *R* correctly interprets a buffer written by schema version *W* iff every field accessed by *R* is present in *W*'s layout with a wire-compatible type, where "correctly" means scalar reads return either the written value or the schema default.

### 4.4 Cap'n Proto RPC: capabilities and promise pipelining

Cap'n Proto's RPC protocol implements the **object-capability model** derived from the E programming language's CapTP: references to remote objects are *capabilities* — unforgeable tokens — and the protocol's message types (`Call`, `Return`, `Finish`, `Resolve`, `Disembargo`, …) manage a distributed reference graph with cross-wire reference counting [5].

The headline feature is **promise pipelining**. In conventional RPC (gRPC, Thrift, REST), a call chain `a().b().c()` costs three round trips: the client must wait for each result before issuing the next call, because the *target object* of the next call does not exist yet. Cap'n Proto allows the client to invoke methods on the **promise** of a result immediately. The pipelined call is sent at once, addressed to the *answer position* of the outstanding call (`PromisedAnswer` in `rpc.capnp`). The server queues the pipelined call against the not-yet-completed answer; when the first method returns its object, the server applies the queued calls *locally* — in its own memory — and returns only the final result. Three network round trips collapse into **one** [5].

```cpp
// The canonical calculator example: one network round trip.
auto request = calculator.evaluateRequest();
request.getExpression().setLiteral(123);
auto evalPromise = request.send();                       // call 1 in flight
auto readPromise = evalPromise.getValue()                // pipelined onto the
                       .readRequest().send();            // unresolved promise
auto response = readPromise.wait(waitScope);             // single wait
```

With per-round-trip latency *L* and *k* chained calls, classical RPC costs *k·L*; pipelined RPC costs *L + ε*, where *ε* is the server's local dispatch overhead. At 50 ms inter-service latency and a 4-deep chain, that is 200 ms versus ~50 ms — a **4× latency reduction** achieved not by faster serialization but by eliminating network round trips [5].

### 4.5 Security: bounds checking and amplification guards

Zero-copy reading of untrusted bytes is a loaded gun unless every dereference is checked. Cap'n Proto's generated readers validate each pointer against the segment bounds before following it, and against *amplification* attacks — tiny messages whose pointer structure describes enormous traversals ("pointer bombing") — the implementation enforces `ReaderOptions::traversalLimitInWords`, a budget on the total words a single read may touch [3]. FlatBuffers' equivalent defense is the verifier (`flatbuffers::Verifier`), which walks the buffer once, checking every offset and vtable entry against the buffer bounds [4]. Both designs therefore split trust into two phases: a *bounded verification walk* (or inline per-access checks), followed by *unchecked-fast* field access.

## 5. Empirical Results / Proofs

### 5.1 Complexity summary

| Operation | Protobuf (parse) | Cap'n Proto | FlatBuffers |
|---|---|---|---|
| Receive → first field read | *O(n)* parse + alloc | *O(1)* | *O(1)* (+ optional verify *O(n)*) |
| Read all *k* scalar fields | *O(n)* | *O(k)* | *O(k)* |
| Build message of *n* words | *O(n)* allocs | *O(n)* amortized bump | *O(n)* amortized reverse |
| Add field (schema evolution) | Recompile, compat rules | Ordinal append | Vtable slot append |
| Chained RPC, *k* calls | *k* RTT + *k* parses | 1 RTT, 0 parses | N/A (no RPC) |

### 5.2 Published benchmark evidence

The FlatBuffers project ships a benchmark suite in which FlatBuffers and Cap'n Proto consistently occupy the top tier, with Cap'n Proto's advantage largest on *read-mostly* workloads where protobuf's parse cost dominates, and FlatBuffers' advantage appearing in *sparse-field* messages where vtables permit omitting unset fields [6]. Community analyses of Cap'n Proto report order-of-magnitude speedups over protobuf on decode-heavy microbenchmarks — Varda's original "infinity times faster" framing referred specifically to the elimination of the parse step (division by a near-zero parse cost), not to end-to-end application throughput [2][3]. Independent survey work confirms the structural account: Cap'n Proto structs are denser than FlatBuffers tables on average because they carry no per-instance vtable metadata, while FlatBuffers distinguishes absent from default scalar fields — a semantic capability Cap'n Proto lacks [1].

### 5.3 Proof sketch: swizzling elimination

*Claim.* A Cap'n Proto message requires no pointer swizzling when relocated in memory.

*Proof.* Every pointer word encodes its target as a signed word-offset relative to the word immediately following the pointer (or, for far pointers, a segment ID plus an intra-segment offset). Let the message be translated by a byte displacement *D* applied uniformly to all words. For a near pointer at address *p* with offset *o*, the target is *p + 8 + 8o*; after translation the pointer sits at *p + D* and resolves to *p + D + 8 + 8o = (p + 8 + 8o) + D*, exactly the translated target. Far pointers name segments by index into the segment table, which is itself translated uniformly; the argument applies segment-wise. ∎

*Corollary.* `mmap`, DMA, `memcpy`, and shared-memory transport of a Cap'n Proto message preserve all internal references without fixup — the basis for zero-copy IPC via immutable shared memory [2].

## 6. Limitations

**Cap'n Proto.** (1) *No scalar presence*: absent and default-valued scalars are indistinguishable, complicating partial-update semantics. (2) *RPC maturity*: the reference implementation long supported only RPC level 2 of the three-level protocol (level 3 adds the full "time travel" network transparency), and capability GC across unreliable transports remains subtle [2]. (3) *64-bit pointer tax*: every reference costs 8 bytes versus FlatBuffers' 4-byte offsets, inflating pointer-heavy graphs. (4) *Endianness*: the format is little-endian; big-endian readers pay a per-access byte-swap (a single instruction on modern cores, but nonzero). (5) *Mutability*: in-place mutation of a received message is possible but size-changing edits require a copy into a builder.

**FlatBuffers.** (1) *No RPC*: distribution semantics are left to the application. (2) *Builder ergonomics*: reverse construction and the requirement to build children before parents complicate incremental writers. (3) *Vtable indirection*: every table field read pays one extra dependent load [4]. (4) *Struct rigidity*: the dense `struct` kind cannot evolve, forcing a premature choice between density and extensibility. (5) *Verification cost*: safe use of untrusted buffers requires the *O(n)* verifier pass, partially eroding the zero-parse advantage for adversarial inputs.

**Both.** Neither system compresses; entropy-dense payloads should be compressed at the application layer. Neither addresses schema *migration* of persisted data — only wire compatibility. And both inherit the fundamental limitation of schema-driven design: the reader must possess the schema (or a compatible one) to interpret the buffer.

---

## 7. Conclusion

Cap'n Proto and FlatBuffers converge on a single architectural insight: **the wire format should be the memory format**. From that decision flow the segmented relative-pointer arena, the elimination of pointer swizzling, *O(1)* field access, and amortized *O(1)*-per-word construction. They diverge on evolution metadata — Cap'n Proto's zero-metadata ordinals versus FlatBuffers' deduplicated vtables — and on scope: FlatBuffers is a buffer format; Cap'n Proto is a buffer format *plus* a capability RPC whose promise pipelining applies the same "eliminate the round trip" philosophy to the network that zero-copy applies to the CPU.

The quantitative case is settled for read-heavy, latency-sensitive systems: removing the parse step removes the dominant cost of message handling, and removing chained round trips removes the dominant cost of distributed composition. The remaining costs — bounds-checked access, vtable indirection, schema discipline — are the necessary price of safety and evolution. Future work lies in shared-memory IPC transports exploiting relocatability [2], formal verification of bounds-checking readers against the amplification adversary, and level-3 RPC implementations realizing the full "time travel" semantics of the E-language lineage [5].
