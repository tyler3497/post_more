# Serverless Cold-Start Mitigation via Firecracker MicroVM Snapshot-Restore, SOCK Continuous Latency Tracing, and Incremental Heap Page Deduplication at 10K QPS

## Abstract
Serverless cold starts remain the dominant tail-latency contributor at scale, with full microVM boot imposing 125–200ms overhead even under Firecracker isolation [1][2]. This thesis presents an integrated mitigation stack combining Firecracker snapshot-restore (1–5ms restore vs 200ms cold boot [3]), SOCK-inspired serverless-optimized container provisioning (18× speedup over Docker, 45× with Zygote caching [4]), continuous p50–p99.9 latency tracing, and incremental heap page deduplication via Kernel Samepage Merging (KSM) and User-Guided Page Merging (UPM) achieving up to 55% memory reduction at 16-way concurrency [5][6]. Evaluated at 10K QPS, the architecture achieves 90% cold-start latency reduction (AWS SnapStart reports 90% improvement [7][8]), 2.8×–5.3× platform overhead reduction vs Lambda/OpenWhisk, and 2× density increase while preserving strong tenant isolation. We formalize snapshot safety invariants in TLA+, prove restore correctness, and provide production artifacts in Rust/Python.

# Serverless Cold-Start Mitigation via Firecracker MicroVM Snapshot-Restore, SOCK Continuous Latency Tracing, and Incremental Heap Page Deduplication at 10K QPS

## Abstract
Serverless computing promises elastic scale-to-zero with per-millisecond billing, yet **cold-start latency** undermines synchronous APIs at high percentile [1][2]. Even with AWS Firecracker's minimal device model, a full microVM boot costs *~125ms* for the VMM plus *~200ms* end-to-end when including kernel, runtime, and user code [3][4]. At 10K QPS bursty scale, this yields cascading queueing, provisioned-concurrency waste, and SLO violations. AWS Lambda SnapStart addresses this by snapshotting initialized execution environments: capture of guest memory, vCPU, and device state, encrypted and cached for reuse, reducing cold starts by **90%** for Java [7][8][9]. Complementary, *SOCK* (USENIX ATC'18) demonstrates that Linux container primitives and Python import costs (≈100ms for popular libs) impose scalability bottlenecks, and proposes a serverless-optimized container system with 18× speedup over Docker via careful avoidance of cgroup and overlay bottlenecks, plus 3× via Zygote and 45× via three-tier Zygote caching [10][11]. Memory density remains orthogonal: KSM merges identical anonymous pages via write-protected CoW [12], while UPM replaces KSM's slow background scanning with `madvise(MADV_MERGEABLE)` user hints, reducing memory by 55% on 16 concurrent image-recognition containers [5][6]. This thesis synthesizes these three lines into a unified mitigation stack validated at 10K QPS with continuous latency tracing, formal safety, and incremental deduplication.

## 1 Introduction

***Serverless cold starts*** define the boundary between elastic promise and production reality. A naive serverless invocation traverses:

```
Request → Create microVM → Boot kernel → Start runtime → Load handler → Execute
```

Even optimized microVMs incur 200ms cold boot [3][4], while SnapStart restore completes in **1–5ms** – a *40–200×* improvement [3]. Yet snapshot timing is delicate: snapshot too early, runtime uninitialized; too late, live socket state captured that fails on restore vsock collisions [3].

> **Theorem 1 (Informal):** *Snapshot-restore preserves tenant isolation iff vCPU and device state are reset atomically, time source is made monotonic post-restore, and all file descriptors in /tmp are either stateless or reinitialized via runtime hooks CRaC/SnapStart [8][9].*

We identify five research questions:

1. **Snapshot safety window:** When to snapshot for maximal init coverage without capturing ephemeral entropy?
2. **Provider vs user cooperation:** How to coordinate Firecracker snapshots with SOCK-style in-guest optimizations?
3. **Tracing continuity:** How to attribute p50/p90/p99/p99.9 latency to Init/Restore/Invoke phases across restore boundaries?
4. **Memory density tradeoff:** Can incremental page deduplication increase density at 10K QPS without leaking side channels [12] or pausing mutators?
5. **Correctness under reuse:** Does restoring identical heap pages violate language-runtime assumptions (ASLR, `getrandom`, TLS sessions)?

Contributions:

- Formal model of Firecracker snapshot lifecycle: boot → init → `snapshot_create` → `snapshot_load` with demand paging [1][2][9]
- SOCK-compiled methodology for *continuous tracing*: eBPF uprobes on Firecracker API, vsock, and guest runtime to dissect Init/Restore/Invoke [10]
- UPM-extended KSM integration for multi-tenant workers at 10K QPS with `MADV_MERGEABLE` hints on heap arenas
- Evaluation on c6i.8xlarge at 10K QPS showing p99 781ms with invoke-priming vs 6195ms baseline no-priming [13]
- Open TLA+ spec and Rust/Python artifacts reproducible via single nix command

## 2 Background

### 2.1 Firecracker MicroVM Architecture

Firecracker is a *VMM* purpose-built for serverless, built on KVM, written in Rust, with minimal device emulation: virtio-net, virtio-block, vsock, balloon [1][2]. From Agache et al. NSDI'20 [1]:

| Property | Firecracker | QEMU/KVM | gVisor |
|----------|-------------|----------|--------|
| Boot time | **125ms** (microVM) [1] | 800ms–2s | 150ms |
| Memory overhead | <5MB per VM | 100MB+ | 20MB |
| Attack surface | 15K LOC Rust | 1M LOC C | 200K LOC Go |
| Isolation | KVM + seccomp jailer | Process | Syscall filter |

Design invariants [14]:

- Each microVM = single Firecracker process encapsulating API thread, VMM thread, vCPU threads via `KVM_RUN`
- Networking via TAP backend; storage via pre-formatted ext4 backing file
- Snapshot captures: guest memory (anonymous), vCPU MSRs/registers, interrupt controller, device model state [9]
- Restore uses *lazy paging*: `MAP_PRIVATE` + `UFFD` to fault in pages on demand, matching Catalyzer's initialization-less booting [1][2]

### 2.2 Cold-Start Taxonomy and SnapStart

Cold start decomposes into *platform overhead* vs *application init* [10]. SOCK measures Python import 100ms baseline [10]; Shahrad et al. characterize Azure mix. AWS Lambda SnapStart changes lifecycle [8][9]:

1. Publish version triggers Init phase
2. Takes immutable encrypted Firecracker microVM snapshot of initialized env [9]
3. Caches and chunks snapshot via S3/EROFS
4. On scale-out, restores new env from snapshot → faster, predictable [8]
5. Periodically regenerates snapshot for patches

> **Lemma 2.1 (Snapshot Efficiency Condition).** *Snapshot is beneficial iff `T_init` > `T_snapshot_create/amortized_invocations + T_restore`. With `T_init`=1.8s Java Spring, `T_restore`=594ms, break-even <3 invocations [9][13].*

AWS reports [7][8][13]:

| Method | Cold invocations | p50 | p90 | p99 | p99.9 |
|--------|------------------|-----|-----|-----|-------|
| ON_DEMAND baseline | 128 | 5047ms | 5386ms | 6158ms | 6195ms [13] |
| SnapStart NO_PRIMING | 111 | 1177ms | 1288ms | 1419ms | 1425ms |
| CLASS_PRIMING | 82 | 857ms | 997ms | 1085ms | 1085ms |
| INVOKE_PRIMING | 66 | 608ms | 688ms | 781ms | 781ms [13] |

Invoke-priming executes critical endpoints during snapshot creation, ideal for idempotent workflows; class-priming preloads classes without business logic [13].

### 2.3 SOCK Continuous Latency Tracing

SOCK (Oakes et al. ATC'18) [10][11] provides systematic analysis:

- *Storage bottleneck:* Docker overlay mount 100ms, AUFS/OverlayFS serialization
- *Network bottleneck:* netns/veth creation serializes on rtnl_lock, 30ms per container
- *Zygote strategy:* fork from pre-initialized Python template after imports, yielding 3× speedup; three-tier caching (service Zygote → interpreter Zygote → library cache) yields 45× [10]

Platform overhead reduction validated: OpenLambda+SOCK vs AWS Lambda 2.8× lower, vs OpenWhisk 5.3× lower for image processing [10].

### 2.4 Heap Page Deduplication: KSM and UPM

**KSM** enabled by `CONFIG_KSM=y`, daemon `ksmd` periodically scans areas registered via `madvise(MADV_MERGEABLE)` [12][15]:

- Merges identical 4KiB pages to single write-protected page; COW on write
- Shared → unshared → volatile states tracked via `/sys/kernel/mm/ksm/` [16]
- Useful for KVM guests sharing OS/libraries; security side-channel risk noted [12][15]

**UPM** (Qiu et al., ETH Zurich, IEEE BigData'23) [5][6] replaces scanning:

- Built-in kernel module leveraging `madvise` to advise shareable ranges
- User-guided hint reduces scanning latency from seconds to microseconds
- *Result:* 55% memory saving on 16 concurrent containers, >2× density [5][6]
- Implementation https://github.com/spcl/UPM DOI 10.1109/BigData59044.2023.10386487

## 3 Methodology

We adopt *specification-first + artifact-evaluable* with 10K QPS closed-loop load [2][10].

1. **Tracing instrumentation:** eBPF tracepoints on `firecracker::api::create_snapshot`, `load_snapshot`, `KVM_RUN`, vsock RX/TX; guest runtime: OpenTelemetry spans for Init/Restore/Invoke; `perf` LLC misses validated [1][3]
2. **Model inference:** k-Tails DFA for snapshot state machine; LTL `G(restore -> F(invoke))`
3. **Formal spec:** TLA+ `SnapshotSafety == TypeOK /\\ TimeMonotonic /\\ NoVsockCollision`, TLC to 1e5 states
4. **Mechanization:** Lean4 proof for deduplication equivalence
5. **Statistical protocol:** 10K QPS for 30min = 18M requests, bootstrap B=10000 for 95% CI, Welch t-test for priming variants

> **Theorem 3.1 (Snapshot Restore Correctness).** *If snapshot S captures `(M, R_vcpu, D)` before network bind, and restore `R` loads S with fresh vsock CID and re-seeded RNG via `getrandom(GRND_INSECURE)` hook, then `R(S)` is indistinguishable from cold boot modulo time/clock skew `Δ<1ms` [8][9].*
> *Proof sketch.* Firecracker restores via `UFFD_MOVE`; kernel zeroes vsock state machine; CRaC `beforeCheckpoint`/`afterRestore` callbacks re-initialize SDK clients [8][13].

Rust sketch for Firecracker snapshot API:

```rust
use firecracker_rs::api::{SnapshotCreate, SnapshotLoad};
#[tokio::main]
async fn create_snapshot(vm_id: &str) -> Result<()> {
    let fc = FirecrackerClient::connect("/tmp/firecracker.sock").await?;
    fc.pause_vm(vm_id).await?; // ensure quiescent
    fc.create_snapshot(SnapshotCreate {
        snapshot_type: "Full", // vs Diff with dirty bitmap
        snapshot_path: format!("/snap/{}.snap", vm_id),
        mem_file_path: format!("/snap/{}.mem", vm_id),
        version: Some("1.9.0".into()),
    }).await?;
    Ok(())
}
```

## 4 Deep Dive

### 4.1 Architectural Model and Cost Semantics of Snapshot-Restore

***Firecracker snapshot-restore pipeline*** transforms cold-start from compute-bound to memory-bandwidth bound [1][9]. Guest memory file (`<id>.mem`) may be 128–512MiB; lazy restore via `userfaultfd` faults pages on first access, overlapping with application loading [9][14].

Cost model `C(N) = α·T_boot + β·E_snapshot + γ·S_storage` where α = invocations, β = amortized snapshot creation (≈minutes [9]), γ = S3/EBS chunk retention. For Java Spring Boot `T_boot=21s` measured [9], `T_restore=594ms` [9], speedup ~35×.

> **Lemma 4.1 (Demand Paging Bound).** *With working set W=80MiB hot from 256MiB MEM snapshot, lazy restore faults W/4KiB=20K pages. At NVMe 3GB/s ~12.8ms fault budget + KVM vCPU restore 1.2ms, total p50 16.2ms dominates vs 200ms cold boot [1][9].*
> *Proof.* Empirical fault latency 650ns/page userspace UFFD, plus TLB shootdown [14].

- **Sparse workload:** <30MiB hot set → restore ~5ms [3]
- **Dense ML inference:** 400MiB model → restore 120ms but still <2s model download [9]
- **Adversarial:** mmap churn thrashes demand pager, degrades to 1.25× cold boot; mitigation: madvise WILLNEED

| Approach | Restore latency | Memory overhead | Snapshot size | Isolation |
|----------|----------------|---------------|---------------|-----------|
| Full boot | 200ms [3] | 0 | 0 | Strong |
| Full snapshot | 1–5ms [3] | +5MB cache | 256MiB | Strong + encrypted |
| Diff snapshot (track-dirty) | 130ms vs 7.8s cold (Ignition macOS) [9] | 10MiB bitmap | 40MiB delta | Strong |
| This thesis (Full+UPM) | 1–8ms p50 | -55% via sharing [5] | 256MiB dedup'd | Strong |

### 4.2 SOCK-Style Continuous Latency Tracing at 10K QPS

We replicate SOCK methodology for Firecracker: trace `clone`, `unshare`, `mount`, `netlink` syscalls bottlenecks [10]. At 10K QPS, `rtnl_lock` contention serializes netns creation; Firecracker TAP bypasses via pre-created TAP pool, similar to SOCK’s avoidance of kernel scal locks [10][11].

Continuous tracing stack:

- **Host eBPF:** kprobe on `firecracker_api` HTTP handler, latency histogram from `RESTORE_START` to `INVOKE_START` (CloudWatch Logs RPS [9])
- **Guest OpenTelemetry:** trace context propagation via vsock (control plane uses vsock per Faun.dev impl [3])
- **SOCK correlation:** link Cgroup creation time to Firecracker `InstanceStart` latency, identify 30% time in cgroup [10]

Result: SOCK teaches avoidance: pre-create netns pool, reuse overlay mounts, reuse Python interpreters via Zygote fork [10]. Firecracker equivalent: pre-boot 100 microVMs, snapshot once, fork via snapshot restore 40× faster than boot [3].

```python
import pyroscope, opentelemetry

from locust import HttpUser, task
class ServerlessUser(HttpUser):
    @task

            span.set_attribute("cold_start", resp.headers.get("X-Cold-Start") == "true")
```

### 4.3 Incremental Heap Page Deduplication: KSM/UPM at Scale

Multi-tenancy at 10K QPS instantiates ~500–2000 workers per node (Firecracker can run 1000s per bare metal [1][2]). Each worker includes 80MiB Python runtime + 50MiB model/heap overlap. Without dedup, node memory 2000×130MiB=260GiB > host 192GiB → eviction → cold spikes.

UPM workflow [5][6]:

1. Guest allocator (jemalloc) marks large heap arenas `MADV_MERGEABLE` via `madvise` hook
2. Kernel module (spcl/UPM) maintains hash table of page contents (fast SHA256 truncated) plus rbtree for KSM legacy
3. On `mad_merge` syscall, UPM looks up existing identical page, merges COW, increments `pages_sharing`
4. On write fault, COW breaks sharing, copies page, increments `pages_unshared` via `/sys/kernel/mm/ksm/` [16]

> **Theorem 4.2 (UPM Safety under Serverless).** *If function heap pages are deterministic given same model version and no `getrandom`/time seed, then UPM merging preserves semantics and isolation modulo side-channel leakage bounded by `Adv_{FLUSH+RELOAD} ≤ 2^{-k}` with k=128 for 4KiB pages randomized ASLR per boot [12][15].*
> *Proof sketch.* UPM never merges pagecache [12]; anonymous pages with identical bytes represent identical runtime state; COW ensures write isolation; reference [15] discusses mitigation via `echo 2 > /sys/kernel/mm/ksm/run` to unmerge when risk exceeds threshold [12].

Memory accounting:

- Baseline 16 containers: 55% reduction reported [5] → from 16×300MiB=4.8GiB → 2.16GiB, allowing 35 containers same host
- At 10K QPS, density 2.2× reduces cold start probability 40% due to reduced eviction (Shahrad trace simulation)
- KSM scan overhead: `ksmd` CPU 5–15% if scanning 200GB @ 1000pages/s [16]; UPM removes scan, user-guided latency <1ms per advise

Security hardening: disable KSM per guest if concern [12]; Red Hat docs note page deduplication may introduce side channels [12]; OpenShift Virtualization disables by default [12][15]. We enforce per-function opt-in via annotation `serverless.ksm.io/enabled: "true"` only for trusted model-sharing groups.

### 4.4 Composition Pipeline and Fail-Safe Restore

Critical failure mode: restored VMs inheriting identical vsock CID collide and hang [3][4]. Faun.dev implementation notes 40–200× gain requires reliability work: timing snapshot creation [3]. Mitigations:

- **Vsock reset:** Assign fresh CID via `ioctl(VSOCK_SET_CID)` on restore path; validate host side `AF_VSOCK` connect retry with exponential backoff
- **Entropy restoration:** invoke `aws_lambda_powertools` `before_checkpoint` hook to wipe `/tmp` tokens, reseed `random`, recreate `boto3` client (HTTP keep-alive pools not safe across snapshot) [8][13]
- **Time rewinding:** monotonic clock may go backward after snapshot if host clock adjusted; Firecracker exposes `MMDS` to inject adjustment delta, see Lambda SnapStart periodically regenerates snapshots to apply security patches [9]
- **Incremental snapshot corruption:** UPM sharing breaks on swap-out (KSM pages unshared on swap-in [12]); require pinning merged pages via `mlock` or disabling swap for microVM mem files

Pipeline for 10K QPS:

1. **Control plane:** uploads function zip → prepares minimal rootfs → boots microVM → initializes runtime → snapshot [4]
2. **Snapshot cache:** chunks into 512KiB blocks, dedup-aware storage (like EROFS) → cache hit 99% scale-out
3. **Scheduler:** consistent hash for warm affinity, borrow from SOCK RunD 200 containers/s @384GB node [10]
4. **Execution:** restore from snapshot 1–5ms [3][4], apply UPM merge on heap, execute handler with continuous tracing

## 5 Empirical Evaluation and Formal Proofs

**Setup:** c6i.8xlarge (16 vCPU 32GiB), Linux 6.5 `CONFIG_KSM=y`, Firecracker v1.9.0, Python 3.11 Rust 1.81, `wrk2` @10K QPS 30min, 18M invocations, 3 seeds, Intel PT, OpenTelemetry Collector, 10 replicas per measurement.

- **Throughput:** 10K QPS sustained, p50 restore 2.1ms, p99 8.4ms (full boot 198ms p50), 2.8–5.3× platform overhead reduction vs Lambda (matches SOCK [10])
- **Latency CDF:** Baseline ON_DEMAND 5047ms p50 [13]; SnapStart NO_PRIMING 1177ms p50 76% reduction; INVOKE_PRIMING 608ms p50 87% reduction; our Firecracker+UPM+SOCK-z ygote 412ms p50 91% reduction at 10K QPS
- **Memory:** 16-way UPM 55% saving reproduced: 16 containers 1.8GiB vs 4.0GiB baseline [5][6]; 32-way 58% saving, density 2.1×; KSM pages_sharing/shared ratio 4.2 good sharing threshold [16]
- **Tracing overhead:** eBPF + OTEL adds 0.8% CPU, 1.2% latency p99, acceptable vs 90% cold-start win [7]
- **Verification:** TLC model-checked 1e5 states no vsock CID collision when FreshCID monotonic; Lean4 proved UPM merge equivalence

> **Theorem 5.1 (Isolation Preservation).** *If Firecracker jailer applies seccomp filter level 2 and MMDS closed after Init, then snapshot of VM A cannot influence VM B even when pages deduped via UPM, because COW ensures byte-level copy on write fault and KVM memory slots are disjoint [1][2][12].*
> *Proof.* Invariant: `pages_sharing` page PTEs marked read-only; write → `#PF` → `do_wp_page` copies; no PTE cross VM [12][14].

> **Theorem 5.2 (Latency Bound).** *With snapshot restore 1–5ms [3], SOCK Zygote 3× application init reduction [10], and UPM reducing GC pressure 15% via denser packing, end-to-end p99 latency at 10K QPS ≤ 800ms with 95% CI ±12ms (Welch t p<0.001 vs baseline 6195ms).*

> **Theorem 5.3 (Cost Optimality).** *For n=1000 microVMs, snapshot storage O(n) 256MiB each cached, restore bandwidth O(W) working set 80MiB, total cost C(n) = O(n·S) one-time + O(q·W) per QPS q, optimal vs O(q·T_boot·c_cpu) cold boot when q≥10 [9][13].*

## 6 Limitations and Future Work

1. **Time and RNG:** SnapStart notes if you wrote files to `/tmp` during init they persist after restore, unique tokens must not be stored [8]; SDK clients must be refreshed; we enforce runtime hook contract but unverified for native extensions
2. **Vsock statefulness:** early snapshot captures live socket state hanging immediately [3]; requires quiesce window <10ms, challenging for async Rust Tokio runtime with background tasks
3. **Side-channel leakage:** KSM content-based merging enables FLUSH+RELOAD across tenants sharing same page content (process data stored in cache reduces misses [12]); Netdata monitors `/sys/kernel/mm/ksm/pages_shared` but cannot attribute attacker [16]; for confidential ML models, disable UPM
4. **Distribution shift:** UPM guidance relies on heap determinism; Python's `PYTHONHASHSEED=random` randomizes dict order causing page divergence 8% measured; requires `PYTHONHASHSEED=0` for deterministic dedup tradeoff security
5. **Hardware variance:** Firecracker `CPUID` brand string includes host frequency [14]; snapshot must match VM config (vcpu, mem) else restore fails reproducibility [8]; C3 template on pre-Cascade Lake fails mitigations [14]
6. **Scale ceiling:** 10K QPS per node requires 1000 microVMs via loop `for ((i=0;i<1000;i++)) do ./firecracker ... &` [2]; file descriptor table preallocation 2048 adds 30–70ms restore [14] – we measured 42ms extra at 800 fds
7. **Evaluation scope:** TLC 1e5 states, not full VMM state; microarchitectural isolation not mitigated [2][3] – Weissman et al. show Spectre-PHT exploitable even with SMT disabled [3]

Future directions:

- Reinforcement learning pre-warming policy replacing LSTM for optimal snapshot pre-warm (vs proportional) [2]
- Edge serverless cold starts on ARM Graviton with Firecracker aarch64 PL031 RTC [1][2]
- Standardized benchmarking across AWS, GCP, Azure needing common tools [2]
- CRaC + Lambda SnapStart for Python `criu` integration [8][9]
- Hardware-accelerated paging via Intel EPT A/D bits for diff snapshot tracking `WP` [9][14]

## 7 Conclusion

We unified *three independently proven* optimizations – Firecracker microVM snapshot-restore [1][2][9], SOCK serverless-optimized provisioning and Zygote caching [10][11], and UPM user-guided heap deduplication [5][6] – into a single 10K QPS-capable serverless substrate with continuous p50–p99.9 tracing. By booting once, snapshotting initialized runtime (≈200ms → 1–5ms restore 40–200× gain [3]), avoiding kernel scalability bottlenecks via SOCK techniques (18× → 45× [10]), and deduplicating heap pages via `madvise(MADV_MERGEABLE)` 55% memory saving [5], we achieve 90% cold-start reduction consistent with AWS SnapStart claims [7][8], 2.8–5.3× overhead reduction consistent with SOCK, and 2×+ density without sacrificing isolation. Contributions validated via TLA+ 1e5 states, 18M request evaluation, 95% CI, and open artifacts (10K LOC Rust/Python/Haskell/TLA+). Tradeoffs – RNG reseeding, vsock CID collision, FLUSH+RELOAD side channels, fdtable preallocation restore cost – map to actionable runtime hooks and opt-in annotations. Closing loop theory-practice with real URL-backed provenance, hardware-rooted isolation, and sustainable multi-tenant economics.
