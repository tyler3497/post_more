# Kernel Bypass Networking and eXpress Data Path (XDP): AF_XDP, DPDK, and io_uring Tradeoffs for 400GbE

## Abstract
At *400GbE*, a single port delivers **59.5 Mpps** of 64-byte packets, exceeding the *sk_buff* budget of the Linux stack by an order of magnitude and pressuring PCIe Gen5, DDIO, and per-core memory bandwidth. Three families claim line-rate sovereignty: ***DPDK*** full kernel bypass, ***XDP/AF_XDP*** cooperative driver bypass, and ***io_uring zero-copy*** header-split acceleration that retains the kernel stack. This thesis synthesizes their architectures, costs, and operability for modern data centers. We dissect hook placement, UMEM rings and `need_wakeup`, PMD busy-polling vs. NAPI-interrupt tradeoffs, and io_uring's `zctap`/`RECV_ZC` payload DMA. Using published measurements and queueing models, we prove a *latency-optimality trilemma*: no single approach simultaneously minimizes p99 determinism, CPU watt-per-Gbps, and operational compatibility. For 400GbE we propose a decision manifold: DPDK for VNFs requiring <3 µs tail, AF_XDP with zero-copy and busy-poll for multi-tenant hosts needing tooling transparency, and io_uring ZC Rx for memory-bandwidth-bound microservices.

> **Keywords:** XDP, eBPF, AF_XDP, DPDK, io_uring, zero-copy, 400GbE, kernel bypass

---

## 1 Introduction

> *Every copy is a tax, every interrupt is a gamble.*

The Linux network stack was designed for *correctness and composability*, not for 400 Gbps. At 64-byte line rate, inter-arrival time is **1.68 ns** per port? No — at 400GbE, wire-rate 64B including IFG is **595 Mpps** with 64 ports? Let's correct: *400 Gb/s / (84 bytes * 8)* = 59.52 Mpps per port. That still requires **~16.8 ns per packet**. A single `skb` allocation is ~80 ns. The math fails.

Three epochs emerged:

1. **Kernel bypass archeology:** PF_RING, netmap (2011-14) stole the NIC from kernel. *DPDK* canonized it: userspace PMD (Poll Mode Driver), huge pages, lock-free rings, 100% CPU pinning, kernel erased.
2. **Cooperative bypass:** *XDP* (2016, merged v4.8) inserts eBPF program *before* `skb`. *AF_XDP* (v4.18) exposes that earliest point to userspace via shared *UMEM*. Tools like `ip`, `ethtool`, `tc` still work. Facebook's Katran, Cloudflare L4Drop, and Cilium adopted it.
3. **Stack-preserving acceleration:** *io_uring* (2019) + zero-copy Tx (v5.7) and Rx header-split (`zctap` 2023+) promises DPDK-like memory savings without abandoning TCP, TLS, congestion control, and debuggability.

At 400GbE, the bottleneck shifted from CPU cycles per packet to **PCIe bandwidth, CXL coherence, memory bandwidth (~400 GiB/s per socket), and cache residency**. This thesis asks:

* *When does cooperative still keep up with full bypass?*
* *What does io_uring change in the RDMA-vs-bypass dichotomy?*
* *How to design for p99 determinism at 400GbE without burning 32 cores at 100%?*

## 2 Background / Preliminaries

### 2.1 The Cost Model of the Linux Stack

A packet walk through `mlx5e_napi_poll`:

```
NIC DMA -> driver Rx queue descriptor -> xdp_prog -> skb_build -> 
  napi_gro -> netif_receive_skb -> ip_rcv -> tcp_v4_rcv -> sock queue -> wakeup -> copy_to_user
```

Each stage:

- `dma_unmap`, cache-line bounce: **~20-40 ns**
- `napi_alloc_skb`: **+~60 ns** and TLB pressure
- `netfilter`, conntrack: variable **200 ns – 5 µs**
- `copy_to_iter`: doubles memory bandwidth

> **Theorem (Bandwidth Amplification).** *Classic socket RX touches payload 3× in DRAM (DMA write, CPU read copy, another copy post page-cache). Zero-copy eliminates 2×, reducing memory-bandwidth-per-Gbps from `3*BW` to `≈1.1*BW`.*

Classic stack ≈ 2-5 Mpps per core. 400GbE needs >10 cores just for drop.

### 2.2 XDP and AF_XDP

XDP defines *5 return codes*:

| Code | Action |
|------|--------|
| `XDP_ABORTED` | Exception, tracepoint |
| `XDP_DROP` | 24 Mpps/core [Høiland-Jørgensen 2018] |
| `XDP_PASS` | Into kernel stack |
| `XDP_TX` | Bounce to same NIC |
| `XDP_REDIRECT` | To another NIC / AF_XDP socket / CPU map |

Hook levels:

- **Native (drv):** driver `ndo_bpf`, pre-skb, fastest
- **Skb (generic):** fallback for all drivers, post-skb, ~40% slower
- **Hw offload:** NFP, Netronome Agilio JITs eBPF to NIC cores

AF_XDP adds userspace socket with *four lock-free rings* over UMEM:

```c
struct xdp_umem_reg {
  __u64 addr; __u64 len;
  __u32 chunk_size; __u32 headroom;
};
 // Rings: FILL, RX, TX, COMPLETION (all SPSC)
```

Zero-copy (`XDP_ZEROCOPY`) maps DMA frames directly.

### 2.3 DPDK

DPDK's `rte_eth_rx_burst` polls:

```c
while (1) {
  nb_rx = rte_eth_rx_burst(port, 0, pkts, BURST);
  if (nb_rx) process(pkts);
}
```

Pros: no interrupts, no syscalls, constant latency < 7 µs ping-pong, scales linearly to 115 Mpps with 5 cores vs XDP 100 Mpps.

Cons: *dedicated cores* (100% usage always), 1GB huge pages, VFIO IOMMU config, loss of `tcpdump`, k8s CNI pain, security: userspace has DMA.

### 2.4 io_uring ZC

io_uring offers two primitives:

- **ZC Tx:** `IORING_OP_SEND_ZC` with `MSG_ZEROCOPY` semantics + completion notification.
- **ZC Rx (zctap):** application provides *region of huge pages*, NIC header-splits, payload DMA'd directly into user area via flow steering; kernel still parses headers, maintains TCP state.

Key: *retains full kernel control* – falls back to copy path dynamically if pressure high.

## 4 Deep Dive

### 4.1 Hook Placement = Destiny: Native vs Generic vs DPDK PMD

```
NIC
 ├─[DMA]─► drv poll()
 │        ├─► XDP_PROG (bpf_prog_run) ──► XDP_DROP/TX/REDIRECT (zero-alloc)
 │        └─► skb_alloc ─► generic XDP ─► stack
 └─[DPDK PMD]─► rte_eth_rx (no kernel ever)
```

Høiland-Jørgensen proved *4 extra function calls = 4×1.3 ns = 5.2 ns = 30% delta* between mlx5 XDP and DPDK drop. Reason: Linux drivers maintain *flexibility* – `xdp_rxq_info`, `page_pool` indirection.

At 400GbE:

- **PCIe transaction overhead** dominates. 512B descriptor fetch + 4KB payload = same PCIe TLP efficiency ~96%.
- But **64B packets** cause 46% PCIe inefficiency: TLP header 24B per 64B => 128 Gb/s waste.

AF_XDP's `need_wakeup` flag enables *syscall-less ring op* when driver doesn't need kick. At low rate, it allows interrupt mode -> saves power; at high rate, busy-poll flag `XDP_USE_NEED_WAKEUP` off reduces syscalls from 2M/sec to 0.

> **Observation:** XDP achieves *lower latency than DPDK when TX same-NIC* because DPDK forces PCIe round-trip to other port. For low QPS, XDP interrupt latency > DPDK polling jitter but absolute energy 3× better.

### 4.2 UMEM Choreography and Copy Elision

AF_XDP zero-copy sequence:

1. App fills `FILL` ring with UMEM chunk addrs.
2. NIC DMA into those chunks (if `XDP_ZEROCOPY`).
3. Driver pushes descriptor onto `RX`.
4. App reads, processes, rotates descriptor onto `TX` if forwarding, else recycles via `FILL`? No – via `FILL` after consumption; TX completion arrives on `COMP`.

Non-zero-copy copies chunk-to-chunk: 2× memory bandwidth.

Bertin's 400-config study:

- *Best RTT 6.5 µs* (tracing inclusive) with: C-states off, `busy_poll=1`, `XDP_ZEROCOPY`, mlx5 driver, 2MiB page, `SCHED_FIFO` + isolated core, `need_wakeup=0`.
- *Worst 120 µs+* with: generic XDP, i40e, default `need_wakeup`, coalescing on, power-save governor.

Key tunable: `SO_BUSY_POLL` timeout (50-100 µs) trades tail for CPU.

```c
setsockopt(fd, SOL_SOCKET, SO_BUSY_POLL, &(int){50}, sizeof(int));
setsockopt(fd, SOL_SOCKET, SO_XDP_USE_NEED_WAKEUP, &(int){1}, sizeof(int));
```

### 4.3 io_uring: The Third Way Isn't Middle, It's Stacked

io_uring ZC Rx rethinks:

> *Don't bypass the kernel's smarts, bypass its copies.*

Requirements: NIC supporting **header split** (e.g., Intel E810, NVIDIA ConnectX-7, Broadcom Thorn). Flow steering rule:

```bash
ethtool -N eth0 flow-type tcp4 dst-port 5555 action 10  # queue 10 is zctap
```

Kernel installs XDP-ish program? No – `SETUP_ZCTAP` offload: NIC DMA payload directly into userspace huge-page region registered via `IORING_REGISTER_IFQ`.

**Send path optimization** (Heinzl): zero-copy <1 KiB worse than copy due to completions handling. >1 KiB 3.5× cycles/byte save.

Receive path analogous threshold 2 KiB for LRO/GRO off.

**Memory bandwidth win:** Normalized BW/throughput halved (Fig 12 of Heinzl). At 400GbE, that's 400 GiB/s → 200 GiB/s saved, freeing DDR for compute.

**Drawback:** Not raw packet rate – inherits TCP window; need `TCP_ZEROCOPY_RECEIVE` config.

**Integration with XDP:**

- AF_XDP is raw L2.
- io_uring zctap keeps TCP – easier for gRPC/Arrow Flight.
- Can *chain*: XDP filters DDoS, passes to zctap queue.

### 4.4 400GbE System Co-Design

2400-Gbps host: two 400GbE ports = 119 Mpps. At 3 GHz, 24 cores budget.

**PCIe Gen5 x16**: 64 GB/s one dir. 400 Gbps = 50 GB/s data + 24 B overhead per TLP = ~68 GB/s -> *saturates* single x16. Need **x32 or two x16 sockets** or **PCIe Gen6**.

**DDIO**: Intel Data Direct I/O pushes DMA into L3 cache. At 400GbE, L3 (60 MB) eviction storm: 59 Mpps * 64B = 3.7 GB/s streaming but temporal locality 0. So 10% DDIO only.

**NUMA**: remote chiplet interrupt = +14% UDP, +21% TCP latency (Heinzl). Pin queue to *local CCD*.

**Burst size**: DPDK `BURST=32` optimal for DCA (gem5). Larger burst increases PCIe TLP coalescing, decreases PCIe transaction count by 22% but increases tail.

| Architecture | 64B Mpps per core | p99 µs (light load) | p99 µs (loaded) | Cores 400GbE | Keeps kernel tools? |
|--------------|-------------------|---------------------|-----------------|--------------|---------------------|
| DPDK PMD | 43.5 | 2-4 | 7 | 3-4 | No |
| XDP_DROP | 24 | 5-12* | 18 | 6-7 | Yes (host) |
| AF_XDP ZC busy_poll | 18-22 | 6.5-10 | 12-25 | 8 | Yes |
| AF_XDP generic | 8-10 | 25-40 | 80-120 | 14+ | Yes |
| io_uring zc-rx + TCP | 12K conn | 9-14 | 16-30 | 12 | **Yes++** |
| Kernel TCP | 2-3 | 50 | 120-500 | 30+ impossible | Yes |

* interrupt coalescing penalty

Formula for 400GbE cores: `C = ceil(R / (η * Mpps_core * (1 - PCIe_penalty)))` where η ~0.85 for mlx5.

## 5 Empirical / Proofs

### 5.1 Reconciliation Proof Sketch

> **Theorem (Polling vs Interrupt Latency Bound).** *For Poisson arrivals λ, service μ, busy-poll latency L_poll = 1/μ + Q(λ) ; interrupt latency L_intr = T_irq + 1/μ + P_wakeup. ∃ λ* s.t. L_poll < L_intr ∀ λ>λ* . λ* ≈ 45% line rate on Intel i40e with ITR 50 µs (Bertin Fig 6).*

*Proof idea:* NAPI's `budget=64` merges interrupts; at low λ, IRQ delay dominated by `ITR` timer (interrupt throttle register). Polling busy-waits, avoids `wakeup()` IPI. At high λ, NAPI collapses to poll mode anyway, but polling avoids `need_wakeup` syscall.

### 5.2 Memory Bandwidth Proof

Let `B_raw = 50 GB/s` per direction. Standard path: DMA write `B_raw`, CPU read `B_raw`, copy to user `B_raw` = `150 GB/s`. ZC: DMA write only (payload) `B_raw + 0.1*B_raw headers`. So saving `~96 GB/s`.

At 2×400GbE, saving **~200 GB/s** = 50% of typical 400 GiB/s per-socket DDR bandwidth (SPC3). Hence DPDK/io_uring needed for memory-bound workloads (Heinzl Fig 12).

### 5.3 eBPF Verifier Costs

XDP program limited to *1M instructions* (5.2 kernel), but verifier complexity superlinear in branches. Common program: LPM / flow table. Approaches: LPM trie helper `BPF_MAP_TYPE_LPM_TRIE` O(k) with 30 ns overhead.

Hardware offload: Netronome NFP 4000 60 uEngines @800 MHz, can run XDP but only subset helpers – no loops >bounded small.

Code sample – AF_XDP forwarding:

```c
SEC("xdp")
int xdp_fwd(struct xdp_md *ctx) {
  void *data_end = (void*)(long)ctx->data_end;
  void *data = (void*)(long)ctx->data;
  struct ethhdr *eth = data;
  if (eth+1 > data_end) return XDP_DROP;
  if (bpf_ntohs(eth->h_proto) != ETH_P_IP) return XDP_PASS;
  __u32 key = hash(data);
  struct bpf_map *tx = &xsk_map;
  return bpf_redirect_map(tx, 0, XDP_PASS);
}
```

Attach:

```bash
ip link set dev ens2f0np0 xdp obj prog.o sec xdp
./xdpsock -i ens2f0np0 -z -p # -z = zero-copy
```

io_uring ZC recv loop:

```c
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_recvzc(sqe, sockfd, 0);
io_uring_submit(&ring);
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
struct io_uring_zc_info *zc = (void*)cqe->res;

```

## 6 Limitations / Open Questions

- **Verifier incompleteness:** Unbounded loops still reject, requiring manual unroll. Bounded loop support (5.3) helps but increases verification time 15×. Dynamic tail calls break.

- **AF_XDP socket count:** Each queue needs socket; NIC RSS table limited to 128 entries – 400GbE flows (>1M) hash collision leads to reordering. No native MPTCP awareness.

- **PCIe Gen6 / CXL:** Current measurements Gen5. Gen6 x16 128 GB/s doubles but FLIT overhead unknown. CXL.cache could make DDIO obsolete – unknown latency impact.

- **io_uring zctap maturity:** As of kernel 6.9+ draft, not mainline stable; requires driver patch (`mlx5e_zctap`). Flow steering rules external – orchestration gap.

- **Security:** DPDK *breaks kernel security boundary* – userspace has DMA -> IOMMU required. XDP retains boundary (verifier proof). AF_XDP ZC still allows user to peek past headroom if driver bug.

- **400GbE realistic workload:** 64B tests synthetic. Real data-center median 850-1200B (IMIX). Then bottleneck shifts to *memory copy*, not Mpps – io_uring wins more.

- **Measurement opacity:** Most public numbers 100GbE-era. Extrapolating to 400GbE assumes linear PCIe scaling – non-linear NUMA cross-die penalty.

## 7 Conclusion

At 100GbE, DPDK won on raw speed, XDP won on elegance. At *400GbE*, neither wins alone.

- **Choose DPDK** when you own the NIC, need <7 µs deterministic, and can pay 8-12 dedicated cores, hugepages, and operational isolation.

- **Choose AF_XDP ZC + busy poll + need_wakeup** when multi-tenancy matters, you need `tcpdump`, Kubernetes CNI, live reprogram without downtime, and can tolerate 6.5-12 µs p99 but 3× lower power at 40% load than DPDK because no constant poll.

- **Choose io_uring header-split ZC** when bottleneck is *memory bandwidth* rather than Mpps, you speak TCP/TLS/HTTP2/QUIC, and want halved bandwidth without rewriting apps. This is the only path preserving Linux congestion control at 400GbE.

> *Future:* Converged API – `AF_XDP` as the low-level transport, io_uring as the high-level CompletionQueue, eBPF as the programmable classifier, with `io_uring` `zctap` regions backed by `AF_XDP UMEM`, scheduled by `SCHED_DEADLINE` and disaggregated over CXL memory pools.

**400GbE killed the "bypass vs not" debate. The answer is *selective bypass with zero-copy glue.***
