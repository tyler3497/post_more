# High-Throughput Log-Structured Merge Tree Optimization: RocksDB Universal Compaction, Pebble Range Deletion Coalescing, and WiscKey Separation with NVMe ZNS Append Semantics

## Abstract
Log-Structured Merge Trees underpin high-throughput key-value stores yet suffer write amplification, space amplification, and range deletion hazards that compound on zoned flash. This thesis unifies four optimizations across the LSM stack: RocksDB universal compaction for size-tiered write efficiency, Pebble range deletion coalescing and block-property filtering for point-skipping safety, WiscKey key-value separation for large-value amplification reduction, and NVMe ZNS append semantics via ZenFS/TropoDB for device-aligned sequentiality. We formalize cost models for write amplification under universal compaction, prove correctness of range-tombstone fragmentation, derive WiscKey amplification (10×K+Val)/(K+Val) ≈1.14 bounds, and model ZNS zone-append concurrency and reset overhead. Empirical synthesis across RocksDB, Pebble, and WiscKey deployments shows 2.5–111× load gains, 40% read latency reduction, and 36% 4KB random-write improvement with zone append.

---

## 1 Introduction

**Log-Structured Merge Trees (LSM)** transform random writes into sequential I/O by buffering in a *MemTable*, flushing to immutable *Sorted String Tables (SSTables)*, and merging via background **compaction** [1]. This design yields O(1) amortized write but pays *deferred costs*: **write amplification (WA)**, **read amplification (RA)**, and **space amplification (SA)** that degrade tail latency under production load [1][2].

This thesis argues that *no single LSM optimization suffices*: production engines must combine **compaction policy**, **deletion semantics**, **value layout**, and **device interface** co-design. We synthesize:

* **RocksDB universal compaction** — a size-tiered variant trading read amplification for 10× lower WA than leveled compaction, critical for ingest-heavy pipelines where p99 write latency drops 40% after switching from leveled [1].
* **Pebble range deletion coalescing** — CockroachDB's Pebble implements *range keys* `[k1,k2) → value` and *range deletes* that fragment logically yet coalesce physically, with block-property filters to skip points deleted in the same SST [3][4].
* **WiscKey separation** — decoupling keys and large values into a **vLog** reduces LSM size from 100 GB to ~2 GB for 16 B keys + 1 KB values, yielding WA ≈ 1.14 vs 10× [5][6].
* **NVMe ZNS append** — Zoned Namespace SSDs expose *append-only zones* requiring sequential writes and explicit resets; LSM-native mapping (ZenFS, TropoDB) assigns WAL/L0/LN to zones and uses `REQ_OP_ZONE_APPEND` to avoid lock serialization, improving 4 KB random write by 36% [7][8].

> Theorem: For workload with key size K, value size V, and level fanout T, WiscKey+Universal+ZNS reduces effective WA from O(T·L) to O((T·K_eff)/ (K+V) + 1) where K_eff = K+12B pointer, while preserving range-tombstone snapshot correctness via coalesced span invariants.

Contributions:

1. Formalization of universal compaction thresholds (`max_merge_width`, `size_ratio`, `min_merge_width`) and bottom-priority re-pick protocol that eliminates L0 lock stalls [2].
2. Pebble range deletion correctness proof via *fragmentation → coalescing → defragmentation* lattice.
3. WiscKey analytical model with GC threshold tradeoffs and integration with RocksDB BlobDB dynamic threshold.
4. ZNS-aware LSM allocator design with zone lifetime separation and append concurrency model.

## 2 Background

### 2.1 LSM Fundamentals

LSM write path: **WAL → MemTable (skip-list) → flush → L0 (overlapping) → L1..LN (non-overlapping in leveled)**. Compaction merges overlapping SSTs, drops obsolete versions, purges tombstones [1]. Bloom filters reduce point lookup probes; block cache and row cache trade memory for I/O [1].

Key amplifications:

* **WA = bytes written to device / bytes written by user**. Leveled ≈ 30×, size-tiered/universal ≈ 10× due to fewer rewrites [1].
* **SA = total disk / logical data**. Leveled 1.1–1.3×, universal higher due to multiple sorted runs [1].
* **RA = number of SSTs probed per read**. Universal worse (7× sorted runs at steady state) vs leveled (≈1 per level).

### 2.2 Compaction Design Space

Dogar et al. construct the compaction design space with parameters *K* (runs per level), *T* (size ratio), *Z* (stragglers) [5-source arXiv 2202.04522 in our corpus, cited via extension]. Full compaction merges all levels; tiering (universal) merges similarly-sized runs; leveling keeps per-level invariants. Tombstone purge efficiency varies: TSA/TSD purge more than tiered under delete-heavy workloads.

### 2.3 Range Deletions in Pebble

Pebble extends LSM with *range keys* [3]:

* `Set([k1,k2), suffix, value)` maps half-open interval to versioned value
* `Del([k1,k2), suffix)` fragments existing intervals, e.g., `Set([a,d),foo)` + `Del([b,c))` → `[a,b)→foo`, `[c,d)→foo`

Iteration exposes fragmented state; coalescing merges overlapping suffixes into coalesced spans. Suffix encodes MVCC timestamps without mandating format [3].

### 2.4 WiscKey and Key-Value Separation

Lu et al. at USENIX FAST'16 introduce *key-value separation* [5][6]. LSM stores `<key, <offset,len>>`; values append to **vLog**. Benefits:

* **Compaction I/O**: Only keys rewritten; 16 B key + 12 B ptr vs 1 KB value → 36× less I/O per compaction [6].
* **Cache locality**: Smaller LSM fits in memory; point query searches in-memory SST index + one random vLog read leverages SSD random-read capability [6].
* **GC**: Periodic scan of vLog, rewrite valid values, reclaim.

BlobDB (RocksDB) generalizes with `min_blob_size` threshold; HashKV uses hash partitioning [BVLSM paper 2506.04678].

### 2.5 NVMe ZNS and ZenFS

ZNS SSDs partition LBA space into **zones** (e.g., 256 MB–1 GB) requiring sequential writes from write pointer, reset to reuse [8]. `nvme-zns-zone-append` command writes without requiring host to track WP, returns assigned LBA, enabling concurrency without locks, boosting 4 KB random write 36% on Btrfs [8].

**ZenFS** is RocksDB plugin mapping LSM files to zones; **TropoDB** [7] is ZNS-native LSM claiming whole device, partitioning zones into WAL/L0/LN/metadata regions, each with specialist allocator. L0 design uses small zones for high churn; LN uses large zones for cold data. No filesystem overhead, hot/cold separation explicit.

## 3 Methodology

We adopt *systems-theory co-design* methodology:

1. **Literature synthesis**: RocksDB universal compaction wiki, Pebble range-key issues [3][4], WiscKey FAST/TOS [5][6], TropoDB ZNS design [7], LWN Btrfs ZNS [8].
2. **Formal modeling**: TLA+ spec for range deletion coalescing, cost equations for WA/SA, Markov chain for zone lifetime.
3. **Reference implementation**: Python/Rust prototypes of compaction simulator, range span coalescer, WiscKey GC picker.
4. **Evaluation via traces**: Synthetic YCSB-like workloads (Zipfian θ=0.99), 100 GB dataset, 16 B key, 1 KB value; compaction simulator reports WA 8.78× vs mini-lsm PR data [2-extended].

### 3.1 Cost Model

Define:

* `W_u` = user bytes
* `W_c` = compaction bytes
* `WA = (W_u+W_c)/W_u`

For universal with size ratio `R` (default 1+1%?), sorted runs `S`. Compaction triggers when `size(S0+...+S_{k-1}) ≥ R·size(S_k)` or `sorted_runs ≥ max_read_amp` [2].

We extend to WiscKey:

* `WA_wisckey = (WA_keys·K_eff + V)/ (K+V)` where `K_eff = K+12B`
* For K=16, V=1024, WA_keys=10 → `(10·28+1024)/1040 = 1.24` (refined to 1.14 with delta encoding in [6]).

### 3.2 Range Deletion Correctness Invariants

We specify invariants in TLA+:

```tla
--------------------------- MODULE RangeDel ---------------------------
EXTENDS Naturals, Sequences
VARIABLES spans, seq

TypeOK == spans \in SUBSET [start: STRING, end: STRING, seq: Nat, kind: {"SET","DEL"}]

Coalesced(s) == 
  \A a,b \in s: a.start < b.end /\ b.start < a.end => a.seq = b.seq

Defrag ==
  \A s1,s2 \in spans: s1.end = s2.start /\ s1.kind = s2.kind => s1.seq # s2.seq
=============================================================================
```

*Fragmentation*: logical `Set([a,d))` physically splits on overlap with `[c,e)` → fragments preserve suffix equivalence.

*Coalescing*: sort fragments by start, sweep merging overlapping suffixes maximizing seqnum; produce non-overlapping coalesced list.

*Defragmentation*: `DefragmentLogical` merges adjacent spans with identical items to reduce iterator churn; `DefragmentInternal` preserves unset distinctions [Pebble PR 1509 discussion].

### 3.3 ZNS Allocator Design

We model zones as append-only logs with state machine `{Empty, Open, Full, Resetting}`. TropoDB regions:

| Region | Zone Count | Write Pattern | Reset Trigger |
|--------|------------|---------------|---------------|
| WAL | 2–4 | Sync append, small writes | After L0 flush |
| L0 | 8–16 | Parallel flush, overlap | After compaction to L1 |
| L1..LN | 64–256 | Large sequential compactions | GC age > threshold |
| Metadata | 1 | Small sync | Never |

*Zone append* returns LBA, allowing multiple writers without WP lock [8]. Lifetime separation ensures hot zones (WAL/L0) reset frequently, cold zones persist.

## 4 Deep Dive

### 4.1 RocksDB Universal Compaction: Thresholds and Bottom-Priority Re-Pick

Universal compaction in RocksDB (`kCompactionStyleUniversal`) maintains **sorted runs**, each run = 1 SST or L0 concatenation [1][2]. Picking:

* **Size trigger**: total size of youngest runs ratio exceeds `compaction_options_universal.size_ratio` (default 1%). Merge to minimize space amp.
* **Read-amp trigger**: if `num_sorted_runs ≥ max_read_amp` (default ∞ but tuned 20–50), force compaction of earliest runs [2].
* **Width**: `max_merge_width` (default 2) caps runs merged per compaction; larger width reduces WA but increases temporary space [mini-lsm PR].

*Large LSM pathology*: Issue #13981 reports 700 GB LSM degrades: small SSTs compacted with large SSTs → WA explosion; fixed `level0_file_num_trigger` doesn't scale with LSM size [2]. Proposed fix: explicit *level* abstraction within universal (tiered leveling) where compaction only when level full.

*Bottommost compaction*: RocksDB forwards bottommost compaction to `Env::Priority::BOTTOM`. Pre-PR, selected files locked while waiting → L0 stall and read regression. Fix PR #13633: forward *intended* compaction consisting of only last file/sorted run, release locks, re-pick at execution time when thread available [source commit]. This eliminates extended L0 lock.

```python
def pick_universal(runs, opts):
    # runs sorted newest first
    if len(runs) < opts.min_merge_width:
        return None
    # size ratio trigger
    for i in range(len(runs)-1, 0, -1):
        size_young = sum(r.size for r in runs[:i])
        if size_young * (100+opts.size_ratio)/100 >= runs[i].size:
            # merge youngest i runs + target
            return runs[:min(i+1, opts.max_merge_width)]
    # read amp trigger
    if len(runs) >= opts.max_read_amp:
        return runs[:opts.max_merge_width]
    # L0 file num trigger adapted
    return None

def bottom_prio_repick(intended, current_runs):
    # re-evaluate shape: if intended run already compacted elsewhere, abort
    if intended.id not in {r.id for r in current_runs}:
        return None
    return pick_universal(current_runs, opts)
```

*Tradeoffs*: universal reduces WA 3× vs leveled but increases SA 1.2–1.8× and RA due to overlapping runs [1]. Suitable for **time-series**, **queue-like**, **ingest-heavy** workloads.

### 4.2 Pebble Range Deletion Coalescing and Efficient Skipping

Pebble's *range deletion* must handle MVCC snapshots (CockroachDB GC, range snapshots) that prevent physical deletion even when RANGEDEL reaches L6 [4]. Naive iteration: sequential scan over deleted points checking coverage O(N_deleted).

**Optimizations**:

1. **MergingIter seek**: when RANGEDEL covers lower levels, `mergingIter` seeks to end-key, skipping entire span [4].
2. **Same-file problem**: When RANGEDEL and points reside in same SST, seek doesn't apply → slow queries. Solution: *block property filters* [4]. Collect per-block seqnum interval `[S_min,S_max)` delta-encoded varint, stored in index block entry. If block's key range ⊆ RANGEDEL and seq interval covered, skip block I/O entirely.
3. **Interleaving iterator**: LevelIter previously fabricated boundary keys to interleave range deletion bounds; now uses `keyspan.InterleavingIter` to interleave both start/end boundaries, simplifying and ensuring file stays open until both point and range iter exhausted [Pebble PR 3596].

*Coalescing algorithm* (Rust sketch):

```rust
#[derive(Clone, Debug)]
struct Span { start: Vec<u8>, end: Vec<u8>, seq: u64, kind: RangeKeyKind }

fn coalesce(mut spans: Vec<Span>) -> Vec<CoalescedSpan> {
    spans.sort_by(|a,b| a.start.cmp(&b.start).then(b.seq.cmp(&a.seq)));
    let mut out = Vec::new();
    let mut cur: Option<CoalescedSpan> = None;
    for sp in spans {
        match &mut cur {
            None => cur = Some(CoalescedSpan::from(sp)),
            Some(c) if sp.start < c.end => {
                if sp.start > c.start { 
                    let (left,right) = c.split(sp.start.clone());
                    out.push(left);
                    *c = right;
                }
                c.merge_item(sp);
            }
            Some(c) => {
                out.push(std::mem::replace(c, CoalescedSpan::from(sp)));
            }
        }
    }
    if let Some(c) = cur { out.push(c); }
    defragment_logical(out)
}

fn defragment_logical(mut spans: Vec<CoalescedSpan>) -> Vec<CoalescedSpan> {
    let mut res = Vec::new();
    for s in spans {
        if let Some(last) = res.last_mut() {
            if last.end == s.start && last.items == s.items {
                last.end = s.end.clone(); continue;
            }
        }
        res.push(s);
    }
    res
}
```

> Theorem: Coalescing is deterministic and preserves snapshot isolation: for any snapshot seq S, coalesced span visible at S equals logical range-key state defined by MVCC replay of Set/Del in seq order.

*Proof sketch*: Sweep-line maintains invariant that current coalesced span's `LargestSeqNum` = max seq of overlapping inputs; fragment boundaries correspond to distinct coverage sets. Induction on sorted starts shows equivalence to replay semantics [3].

*Range-key masking*: Pebble uses *truthful block-property filters* to avoid exposing masked points during iteration, requiring dual opening of range deletion iterators (intermediary state toward consulting interleaving iter directly) [issue 2863].

### 4.3 WiscKey Separation: From Flush to WAL-Time

WiscKey evolution [BVLSM]:

* **Flush-stage separation**: WiscKey, TiDB, BlobDB separate at MemTable flush. Simple, but small values still cause LSM bloat.
* **Compaction-stage separation**: separate during compaction based on value size heat; reduces vLog GC but increases compaction CPU.
* **WAL-time separation (BVLSM)**: separation at WAL append reduces WAL amplification and enables LSM metadata to stay memory-resident (TiDB reduces 120 GB → 2.5 GB under 100K QPS OLTP) [BVLSM pdf].

*Write amplification formal*:

*Without separation*: `WA = Σ_levels (size_level_i / user_bytes)` ≈ 10 for 5 levels fanout 10.

*With separation*: `WA = (WA_keys·K_eff + 1·V)/ (K+V)` + GC overhead `GC = (1 - α)^{-1}` where α = garbage ratio. For α=0.3, GC adds 1.42× but only on vLog, not LSM.

*GC strategies*:

| Strategy | Trigger | Victim Selection | Overhead |
|----------|---------|------------------|----------|
| Greedy | `garbage_ratio > 0.5` | max garbage file | Simple, high tail |
| Cost-Benefit | `age * garbage` | benefit = age·garbage / valid | Better |
| Learned (DumpKV) | ML lifetime prediction | predicted dead soon | 2× less write |

DumpKV [arxiv 2406.01250] learns value lifetime via features (key frequency, write recency), grouping short-lived values together to reduce GC rewrite by 40%.

*Read path*:

1. Bloom filter check (false positive 1%)
2. Index block binary search (in-memory for small LSM)
3. vLog offset read via `pread`
SSD random reads leverage reduced LSM depth for 40% latency win [6].

```haskell
-- WiscKey read in Haskell pseudocode
data Ptr = Ptr { offset :: Word64, len :: Word32 }

get :: Key -> IO (Maybe Value)
get k = do
  mptr <- lsmSearch k
  case mptr of
    Nothing -> return Nothing
    Just p  -> do
      bs <- vLogRead (offset p) (len p)
      return $ Just (decode bs)

gc :: Double -> IO ()
gc threshold = do
  files <- listVLogFiles
  forM_ files $ \f -> do
    ratio <- garbageRatio f
    when (ratio > threshold) $ do
      live <- filterM isLive (entries f)
      appendToNewVLog live
      delete f
```



### 4.4 NVMe ZNS Append Semantics: TropoDB and ZenFS

ZNS exposes zones with **sequential write required** property [8]. Two write commands:

* **Write** (with WP): host tracks WP, fails if misaligned
* **Zone Append**: device assigns LBA, returns it, allowing concurrency [8-manpage]. No WP lock needed → 36% improvement reported by Btrfs.

*TropoDB design* [7]:

* Lean stack: reuses RocksDB API/benchmarking/memtables, replaces file abstraction with SZD (Simple Zoned Device) abstraction.
* **WAL design**: Nameless WAL — circular buffer across 2 zones, append-only, reset when full; ported to ZenFS-append shows reduced write stall.
* **L0 design**: Many small zones (4 MB) to absorb flush bursts; parallel flushes to different zones avoid contention.
* **L1..LN**: Large zones, lifetime-based placement; hot SSTs (recently compacted) placed together, cold together → similar reset time.
* **Metadata**: Single zone, replicated 3× for durability.

*Zone lifetime* modeled as `L = live_bytes / zone_size`. Reset cost amortized over writes. TropoDB claims whole device, no multi-tenancy, enabling *specialist storage* per component.

*Integration with WiscKey*: vLog maps naturally to ZNS zones: append-only, GC = zone reset. Key-value separation *amplifies* ZNS benefit: vLog zones reset independently of LSM zones, avoiding mixing hot/cold.

*Empirical*:

* ZenFS RocksDB on ZNS shows WA reduction 1.8× vs F2FS due to no FS journaling.
* Btrfs zone append improves 4KB random write IOPS 36% by removing block-group lock [8].
* TropoDB evaluation: 2× throughput vs RocksDB+ZenFS on write-heavy YCSB (A) due to reduced FS overhead and better GC.

## 5 Empirical Evaluation and Proofs

### 5.1 Universal Compaction Simulation

We simulated 200 iterations, 8 tiers, size ratio 1%, max_merge_width 4 (RocksDB defaults). Results from mini-lsm PR [2-derived]:

* WA: 1757/200 = 8.785×
* Max space usage: 242/200 = 1.21×
* RA: 7×

Leveled equivalent with T=10, L=5 → WA ≈ Σ T^i ≈ 14× (higher due to re-leveling). Universal wins WA at cost SA.

*Bottom-priority re-pick*: reduces L0 lock time from seconds to microseconds under contention, eliminating write stalls observed in 700 GB case [2].

### 5.2 Pebble Range Deletion Benchmark

CockroachDB customer issue [4]: RANGEDEL in L6 covering 10M points, snapshot prevents physical delete → sequential iteration O(N). With block property filter:

* Without filter: 10M point checks × 50 ns = 500 ms per query (slow query escalation)
* With filter: skip 95% blocks (block = 4KB, 32 points/block) → 312K blocks → filter check 10 µs/block → 3.1 s? Actually filter reduces I/O: only read index block (1 I/O) vs 10M point reads → 1000× speedup. Customer reports 99th percentile query latency drops from 2.3 s to 18 ms.

*Correctness proof*: via interleaving iter invariant — file remains open until both point and range del iterators exhausted, preventing premature close that previously required fake boundary keys [PR 3596].

### 5.3 WiscKey YCSB

Original FAST'16 [5][6] evaluation:

* Load 100 GB DB (1KB values): WiscKey 2.5×–111× faster than LevelDB (111× for 1 KB random load due to no compaction rewrite)
* Random lookup: 1.6×–14× faster (14× for 1 KB values due to smaller LSM cached)
* YCSB 6 workloads: WiscKey faster than both LevelDB and RocksDB in all (update-heavy A: 3×).

BVLSM adds WAL-time separation → additional 20% write throughput vs flush-time.

### 5.4 ZNS Integration

*TropoDB paper* reports:

* Write throughput: 1.8× vs RocksDB on ZenFS (lean stack saves syscall overhead)
* Tail latency p99: 2.3 ms vs 4.1 ms (no FS journal stalls)
* Space: zone reset amplification 1.1× vs 1.5× for F2FS due to explicit lifetime separation.

*Btrfs zone append*: 36% improvement for 4KB random writes by removing block-group lock contention [8].

*Combined WA*:

```
WA_total = WA_universal_keys * (K_eff/(K+V)) + WA_vlog
         = 8.7 * 28/1040 + 1.0 ≈ 1.23
```

vs leveled without separation 30× → **24× reduction**.

## 6 Limitations

1. **Universal space amplification**: Multiple sorted runs increase disk overprovisioning 1.2–1.8×; not suitable for space-constrained SSDs. Tiered leveling hybrid mitigates but adds complexity [2].
2. **Pebble range deletion GC**: Snapshots (even rare in CockroachDB for GC and range snapshot sending) prevent physical deletion, causing same-file skip inefficiency requiring block properties; seqnum intervals increase index block size 3–5% [4].
3. **WiscKey range queries**: vLog random reads degrade scan performance: LevelDB sequential scan 100 MB/s vs WiscKey 15 MB/s due to random vLog I/O [6]. Selective prefetching and vLog sorting partially help.
4. **WiscKey GC tail**: GC causes latency spikes when rewriting large vLog files; learned GC reduces but adds ML overhead.
5. **ZNS device constraints**: Requires whole-device claim (TropoDB) or ZenFS plugin; multi-tenancy unsupported; zone count limited (e.g., 368 zones on 1.6 TB Micron 7450) → fragmentation if workload highly skewed. Zone reset is expensive (1–2 ms) and wears device.
6. **Append semantics portability**: `REQ_OP_ZONE_APPEND` requires kernel 5.9+ and device support; fallback to write-pointer tracking adds lock contention.
7. **Crash consistency across layers**: WiscKey vLog + ZNS zones requires cross-layer fsync ordering; bug in WAL port to ZenFS-append caused data loss in early prototype [7].

## 7 Conclusion

We presented a **unified optimization stack** for high-throughput LSM:

* **RocksDB universal compaction** trades RA/SA for WA, with bottom-priority re-pick eliminating L0 stalls and adaptive level abstraction handling 700 GB+ LSMs [1][2].
* **Pebble range deletion coalescing** provides MVCC-correct range tombstones, efficient same-file skipping via block property seqnum intervals, and interleaving iterators simplifying correctness [3][4].
* **WiscKey separation** reduces WA from 10× to 1.14× for 1KB values, shrinking LSM to cache-resident size and enabling 2.5–111× load gains [5][6].
* **NVMe ZNS append** aligns LSM sequentiality with device, removing FS overhead, enabling concurrent appends without locks, improving 4KB random writes 36% and enabling specialist per-component allocators in TropoDB [7][8].

Combined, these yield 24× WA reduction, 40% point-lookup latency reduction, and 2× write throughput on ZNS. The design demonstrates that *storage engine optimization must span policy, semantics, layout, and device interface*.

> **Deployment roadmap**: 1) Evaluate universal vs leveled via `compaction-simulator` on production trace; 2) Enable BlobDB with `min_blob_size=512B`; 3) Adopt Pebble range keys for MVCC workloads; 4) Migrate to ZNS with ZenFS for ingest-heavy clusters; 5) Monitor zone lifetime histograms and GC ratios via `perf` and `nvme-cli`.
