# Event Sourcing at Scale with Apache Pulsar: Tiered Storage, Exactly-Once Transactional Producers, Avro Schema Evolution, and the Latency of CQRS Read-Model Rebuilds

## Abstract

Event sourcing demands an append-only substrate that preserves the total order of domain facts indefinitely, yet commodity stream-storage economics break down when ledgers grow without bound. This thesis presents a production-grade architecture for large-scale event sourcing built on Apache Pulsar, and analyzes it across four axes: (i) a tiered storage design in which BookKeeper-backed managed ledgers are offloaded segment-by-segment to long-term object stores while preserving transparent consumer access; (ii) exactly-once event publication through Pulsar's transactional producer, formalized with the marker-based commit protocol of PIP-31; (iii) a disciplined schema-evolution regime using Apache Avro's compatibility algebra, mapping backward, forward, and full compatibility onto the independent deployability of event producers and projectors; and (iv) an analytical and empirical model of CQRS read-model rebuild latency, deriving closed-form bounds on replay throughput, snapshot placement, and catch-up lag. We prove safety properties of the transaction commit path, quantify the cost/throughput trade-offs of tiering with a calibrated queuing model, and characterize the failure modes that remain, including coordinator recovery, schema-transit hazards, and the fundamental tension between infinite retention and bounded rebuild time.

## 1. Introduction

Event sourcing treats the sequence of domain events as the primary, immutable record of a system: *state* is a cached derivative, while the event log is the source of truth [7]. Command Query Responsibility Segregation (CQRS) separates the write path (commands validated against aggregates, appending events) from the read path (projectors folding events into query-optimized models) [8]; an event-sourced system *must* segregate reads from writes, because replaying a log is not a querying strategy [8].

The architectural question is what the log is physically built on. Apache Pulsar's two-layer architecture — stateless serving brokers atop Apache BookKeeper segment storage [9] — is unusually well suited: the event stream becomes a *managed ledger*, an ordered list of immutable segments (ledgers), of which only the tail accepts writes [2]. Sealed segments are self-contained and content-addressable, which makes *tiered storage* — copying old segments to object stores — a natural, lossless compaction of the hot tier [2][3].

Four problems dominate production deployments of this stack: (1) the unbounded-retention cost of monotonically growing logs; (2) exactly-once event publication across command handling and state updates; (3) schema evolution under independent producer/projector deployment; and (4) bounded CQRS read-model rebuild latency. We develop each in turn, grounding the design in Pulsar's actual mechanisms, and close with proofs, a calibrated latency model, and an honest account of limitations.

## 2. Background

### 2.1 Pulsar's storage model

A Pulsar topic is backed by a *managed ledger*: an ordered list of *segments*, each segment implemented as a BookKeeper ledger [2]. Pulsar appends only to the final segment; when a segment reaches a size or time bound it is *sealed* and becomes immutable. BookKeeper replicates each ledger entry across an ensemble (default 3 bookies) with configurable write and acknowledgement quorums, trading write latency against fault tolerance [9]. Crucially, because sealed segments never change, they can be copied verbatim to long-term storage and later served back to consumers transparently: the broker consults ledger metadata, fetches from the object store on a cache miss, and the consumer observes no difference [2].

After a configurable deletion lag (default four hours), the BookKeeper copies of offloaded ledgers are reclaimed [3].

### 2.2 Transactions and exactly-once semantics

The idempotent producer (monotonic sequence IDs, broker-side deduplication) gives exactly-once *within a single partition and session*, but no atomicity across partitions or across a produce/acknowledge pair [4].

Transactions carry a 128-bit TxnID: the high 16 bits identify the coordinator, the remainder is a per-coordinator monotonic counter [6]. The commit path uses the *marker approach*: transactional messages are written directly into the partition's managed ledger, tagged with the TxnID, and hidden from dispatchers; the coordinator appends a `<txn>-commit` or `<txn>-abort` marker when the transaction ends, and the marker acts as a fencing point [1]. Consumers choose an isolation level; `read_committed` subscriptions only dispatch messages whose transactions committed [6].

### 2.3 Avro schema evolution

Apache Avro serializes records in a compact binary format whose schemas are JSON documents; readers resolve writer schemas against reader schemas at deserialization time [5]. The compatibility algebra has three principal modes [5]:

- **Backward**: a new schema can read data written by the old schema (consumers upgrade first).
- **Forward**: the old schema can read data written by the new schema (producers upgrade first).
- **Full**: both directions hold.

Adding a field with a default is backward-compatible; removing a field with a default is forward-compatible; renaming requires an `aliases` annotation. Because the wire format carries only a schema identifier (not the full schema), producers and consumers negotiate through a registry, and version skew becomes a manageable, checkable property rather than an operational incident [5].

### 2.4 CQRS and event sourcing

Fowler's 2005 formulation defines event sourcing as persisting the *sequence of state-changing events* rather than current state; current state is recovered by replay [7]. Young's CQRS documents add the structural claim that, in an event-sourced system, the query side is a set of *projections* — deterministic folds over the event stream — and that these projections are transient and rebuildable [8], which makes rebuild latency a first-class service-level concern.

## 3. Methodology

Our method is constructive-analytic: we design a reference architecture — the *Pulsar-backed event store* — from documented Pulsar, BookKeeper, and Avro mechanisms [1][2][5][6][9]; prove safety properties of the commit and replay paths; derive a closed-form latency model for read-model rebuilds calibrated against published figures; and stress-test the design against coordinator crashes, mid-offload broker loss, schema-transit hazards, and adversarial version skew.

The reference event store is defined by five rules:

1. **One stream per aggregate type**, partitioned by aggregate ID, so ordering per aggregate is total and replay is partition-parallel.
2. **All publishes are transactional**: each command handler opens a transaction, appends its events, and commits; projectors consume at `read_committed`.
3. **All payloads are Avro**, registered with backward compatibility by default, full compatibility required at external bounded-context boundaries.
4. **Namespaces carry offload policies** with size thresholds, so the hot BookKeeper tier holds only the working set.
5. **Projectors are deterministic folds** over `(schemaId, event)` pairs, checkpointing per-partition positions transactionally with their writes.

## 4. Deep Dive

### 4.1 The tiered event log: segments, ledgers, and the economics of infinite retention

The managed ledger is the right primitive for an event store because its unit of immutability — the sealed segment — is exactly the unit of offload [2]. A stream receiving λ events/s at mean payload *s* grows its hot tier at 3·λ·s·*c*ₕₒₜ per second (triple replication); offloading a sealed segment replaces those copies with erasure-coded object storage at *c*ₒbⱼ ≪ *c*ₕₒₜ, while the segment stays addressable through the same cursor abstractions [2][3].

> **Theorem:** *Segment-sealed offload preserves consumer-visible ordering.* Let *L = ⟨S₁, …, Sₙ⟩* be the ordered segments of a managed ledger, with *Sₙ* the open tail. Offloading any *Sᵢ, i < n*, to immutable external storage and rewriting its ledger metadata to the external location does not change the sequence of entries observed by any cursor, because cursors address entries by *(ledgerId, entryId)* and the offload metadata maps the same identifiers to the new location.

The practical subtleties are operational. Brokers upload segments as multi-part objects and may crash mid-upload; operators should set bucket lifecycle rules expiring incomplete multi-part uploads after a day or two [2]. The offload deletion lag keeps BookKeeper copies for a grace period, giving a hot read window for recent replays at bookie latency rather than object-store latency [2].

```rust
// Sketch: offload eligibility over a managed ledger's segments
fn offload_candidates(ledger: &ManagedLedger, threshold: u64) -> Vec<SegmentId> {
    let total: u64 = ledger.segments().iter().map(|s| s.size).sum();
    if total < threshold { return vec![]; }
    ledger.segments().iter()
        .filter(|s| s.sealed && !s.offloaded)
        .map(|s| s.id)
        .collect()
}
```

Note the deliberate exclusion of the open tail: only sealed segments are eligible, which is what makes the copy race-free [2].

### 4.2 Exactly-once publication: the transactional producer and the marker protocol

In an event-sourced command handler, the unit of atomicity is *append events + update the outbox/aggregate checkpoint*. Without atomicity, a crash between the append and the checkpoint yields duplicate events (if the handler retries) or lost events (if it does not) [4]. PIP-31's transaction model makes the handler's work a single transaction: begin (TC allocates TxnID), produce events tagged with the TxnID into the partition's transaction buffer region, and commit [1].

The commit protocol, in the marker approach, proceeds as follows [1]:

1. **Prepare:** the client calls `txn.commit()`; the TC writes `COMMITTING` to the transaction log.
2. **End-partition phase:** the TC contacts the owner broker of each participating partition, which appends a `<txn>-commit` marker to the partition's managed ledger and materializes the buffered messages.
3. **Finalize:** once all partitions acknowledge, the TC writes `COMMITTED` to the transaction log.

Abort is symmetric: `<txn>-abort` markers are appended, and a background sweep reclaims the aborted entries [1]. The TxnID-as-producer-id trick lets the broker reuse its idempotent-producer deduplication logic, so even retried marker appends are applied exactly once [1].

> **Theorem:** *Committed visibility is atomic across partitions.* If the TC records `COMMITTED` for transaction *T*, then every partition participating in *T* has appended the `<txn>-commit` marker and materialized *T*'s messages; if the TC crashes before recording `COMMITTED`, recovery replays the transaction log and either completes or aborts *T*, but never materializes a strict subset of its partitions.

*Proof sketch.* Each partition's commit/abort decision is durable once its marker is appended under the broker's single-writer discipline, and the TC finalizes only after all partitions acknowledge. On TC crash, recovery replays the transaction log (itself a replicated Pulsar topic [6]) and drives any `COMMITTING` transaction to completion via idempotent TxnID-deduplicated end requests. No `read_committed` consumer can observe *T*'s messages before the markers exist, because dispatchers filter on marker presence [1][6]. ∎

The cost is latency: each commit adds at least two extra log appends (prepare + marker) and a TC round trip. The standard mitigation is *batching commands per transaction* — amortizing the commit overhead over *k* events, converting per-event overhead from *O(commit)* to *O(commit/k)* at the price of coarser atomicity granularity.

![Transactional producer exactly-once flow](/thesis/ths-1788805749359-9318-1.webp)

A TLA⁺ sketch of the coordinator's state machine captures the safety invariant:

```tla
---- MODULE TxnCommit ----
EXTENDS Naturals
VARIABLES txnState, \* [txn |-> "OPEN" | "COMMITTING" | "COMMITTED" | "ABORTED"]
          markers    \* [txn |-> SUBSET Partitions] partitions with commit markers
Safety == \A t \in DOMAIN txnState :
            txnState[t] = "COMMITTED" =>
              markers[t] = ParticipatingPartitions(t)
\* No consumer may dispatch uncommitted messages:
Dispatchable(t, p) == t \in DOMAIN markers /\ p \in markers[t]
====
```

### 4.3 Schema evolution as a compatibility algebra

Events are forever: unlike RPC payloads, a 2019 event must remain readable by a 2026 projector. Avro's reader/writer resolution makes this tractable, but only under discipline. We formalize the deployability constraints as a small algebra over schema versions:

| Change | Backward | Forward | Full | Event-store verdict |
|---|---|---|---|---|
| Add field *with default* | ✅ | ❌ | ❌ | ✅ safe (new producers, old projectors) |
| Add field *without default* | ❌ | ❌ | ❌ | ⛔ rejected by registry policy |
| Remove field | ❌ | ✅ | ❌ | ✅ safe only if field unused downstream |
| Rename via `aliases` | ✅ | ✅ | ✅ | ✅ safe (alias = declared isomorphism) |
| Widen `int` → `long` | ✅ | ❌ | ❌ | ✅ safe (Avro promotion rule) |
| Change field type arbitrarily | ❌ | ❌ | ❌ | ⛔ rejected |

Backward compatibility is the *default* posture of an event store: old projectors must keep reading while new producers deploy, because stopping the world to upgrade every consumer is precisely the lockstep the architecture exists to avoid [5]. Full compatibility is required at bounded-context boundaries — events published to external consumers — where neither side can be assumed to upgrade first [5].

The dangerous case is *schema transit*: a projector upgraded to schema *v3* reading a segment containing *v1* and *v2* events. Avro resolution handles this per-record, but the projector must retain resolution rules for every live schema version — and since tiered storage makes old segments *immortal*, the schema registry must be append-only and highly available; losing the registry is equivalent to losing the data [5].

![Avro schema compatibility matrix](/thesis/ths-1788805749359-9318-2.webp)

```haskell
-- Projector as a deterministic fold over versioned events
data VersionedEvent = VE { writerSchema :: SchemaId, payload :: ByteString }

project :: ReadModel -> VersionedEvent -> ReadModel
project rm (VE sid bytes) =
    let event = resolveWith readerSchema (lookupSchema sid) bytes
    in applyEvent rm event
-- resolveWith implements Avro's reader/writer resolution [5];
-- determinism of `project` is what makes rebuilds reproducible.
```

Determinism is load-bearing: the same event stream must always fold to the same read model. Projectors must therefore be pure functions of the event log plus the schema registry — no wall-clock reads, no random sampling, no unversioned external calls.

### 4.4 CQRS read-model rebuild latency

A rebuild has three phases: (1) load the latest snapshot (if any); (2) replay events from the snapshot position to the log tail; (3) catch up with the live stream while new events arrive. Let *N* be the number of events to replay, *R* the projector's sustained fold throughput (events/s), *S* the snapshot load time, *λ* the live arrival rate during replay, and assume *R > λ* (otherwise the rebuild never converges). The replay must also cover the events that arrive *during* the replay, giving the classic convergent series:

> **Theorem:** *Rebuild time bound.* With snapshot load *S*, replay throughput *R*, event count *N*, and arrival rate *λ < R*, the rebuild completes in time
>
> *T* ≤ *S* + *N*/(*R* − *λ*),
>
> and the bound is tight when arrivals are uniform.

*Proof sketch.* Replay of the initial *N* events takes *N/R*; during that interval *λN/R* new events arrive, requiring *λN/R²* more seconds, and so on. Summing the geometric series with ratio *λ/R < 1* gives *N/R · 1/(1 − λ/R) = N/(R − λ)*. Snapshot load is additive and independent. ∎

Four levers control the bound:

1. **Snapshot cadence.** Snapshots truncate *N*; a snapshot every *K* events bounds replay to *K + λT*. Snapshots should be written transactionally with projector checkpoints (rule 5, §3).
2. **Projector throughput *R*.** Replay is partition-parallel: with *P* partitions each sustaining *r* events/s, *R = P·r*. Tiered storage imposes a two-tier read profile — hot segments stream from bookies, cold segments fetch from object storage — so *R* is effectively a weighted mean over the hot/cold mix. The `bookkeeper-first` read priority [2] exists to keep *R* high during the hot portion of a rebuild.
3. **Segment granularity.** Smaller sealed segments offload sooner but increase metadata fan-out; larger segments amortize object-store GET latency. Offload thresholds and `managedLedgerMaxEntriesPerLedger` should be co-tuned.
4. **Arrival rate *λ*.** The *(R − λ)* denominator punishes rebuilding a hot stream; schedule rebuilds against low-traffic windows when possible.

![CQRS read-model rebuild latency timeline](/thesis/ths-1788805749359-9318-3.webp)

```python
# Calibrated rebuild estimator (parameters from operator-reported figures)
def rebuild_time(N, R, lam, S=0.0):
    assert R > lam, "rebuild diverges: projector slower than arrival rate"
    return S + N / (R - lam)

# Example: 2.4B events, 16-partition projector at 40k ev/s/partition,
# 8k ev/s live arrivals, 45 s snapshot load:
print(rebuild_time(2.4e9, 16*40_000, 8_000, S=45))  # ~3795 s ≈ 63 min
```

The example is instructive: a cold rebuild of a large domain completes in about an hour *if* the projector sustains ~640k events/s aggregate. Halving *R* (e.g., because the cold tier dominates and object-store fetch latency throttles the replayer) more than doubles the bound — rebuild latency is *superlinear* in projector degradation once *λ* is an appreciable fraction of *R*.

## 5. Empirical Results and Proofs

We validate the design along three axes: a safety proof for the commit path (given in §4.2), a cost model for tiering, and the calibrated rebuild estimator above.

**Tiering cost model.** For a stream retaining *D* GB with a hot working set of *H* GB: untiered cost is *3·D·c*ₕ per month; tiered cost is *3·H·c*ₕ *+ 1.3·(D − H)·c*ₒ per month, where *c*ₕ and *c*ₒ are the per-GB costs of bookie and object storage.

With representative cloud figures (*c*ₕ ≈ $0.10/GB-month for provisioned SSD, *c*ₒ ≈ $0.023/GB-month), a 50 TB event history with a 2 TB hot set costs ~$15,000/month untiered versus ~$2,035/month tiered — a **7.4× reduction** — while every byte remains consumer-addressable [2][3].

**Throughput calibration.** BookKeeper's quorum write path sustains single-digit-millisecond p99 append latency at high throughput on commodity hardware [9]. Transaction commit adds a measured 2–6 ms per transaction (TC round trip + marker appends) in production deployments [4][6]; batching *k* = 100 events per transaction amortizes this to tens of microseconds per event.

**Rebuild scaling law.** The estimator in §4.4 yields the following operating points for a 2.4B-event domain (*λ* = 8k ev/s, *S* = 45 s):

| Projector aggregate *R* | Cold-tier share | *T* rebuild |
|---|---|---|
| 640k ev/s | 0% | ~63 min |
| 320k ev/s | 50% | ~128 min |
| 160k ev/s | 80% | ~262 min |
| 100k ev/s | 95% | ~430 min |

The table makes the operational point bluntly: *rebuild latency is dominated by cold-tier read throughput*, not by event count alone. Keeping the hot set sized to the projector's working window — via the offload threshold [2] — is the single highest-leverage tuning knob.

**Correctness invariants.** Beyond the marker-approach theorem of §4.2, the reference architecture maintains two further invariants: (1) *replay determinism* — for a fixed schema registry state, folding over any log prefix yields a unique read model (follows from projector purity, §4.3); (2) *no phantom reads* — a `read_committed` projector never folds an event from an aborted or still-open transaction (follows from marker-gated dispatch [1][6]).

## 6. Limitations

**Coordinator availability.** The TC's state is recovered from the transaction log topic [6]; a total loss of the brokers hosting the TC partitions stalls all transactional publishing until recovery completes. Since rule 2 of our methodology (§3) makes the event store *transactional* publishing, this is a full write outage — mitigated, not eliminated, by multi-broker TC metadata initialization [6].

**Exactly-once is bounded.** PIP-31 delivers exactly-once *within the Pulsar substrate*: produce/ack atomicity across one transaction's partitions [1]. End-to-end exactly-once (handler → log → projector → read-model store) additionally requires idempotent projector sinks — typically a sink-database transaction writing the projector checkpoint and the read-model update together, keyed by *(partition, offset, TxnID)*.

**Schema registry as a single point of truth.** As argued in §4.3, tiered immortality of segments makes the registry's availability equivalent to data availability: an outage does not lose bytes, but renders every offloaded segment unreadable until restoration. The registry must be replicated, backed up, and versioned with the same rigor as the log itself [5].

**Rebuilds contend with the write path.** The *(R − λ)* bound assumes replay I/O does not degrade live serving; in practice a full-fidelity rebuild competes with live dispatch for broker and bookie I/O, so production systems throttle replays or rebuild from a dedicated reader cluster.

**Offload is not instantaneous archival.** Segments offload only when sealed *and* when the offload trigger fires (a new segment added past the namespace threshold) [2]. A low-traffic topic can hold sealed-but-unoffloaded segments in the hot tier indefinitely, silently inflating cost; monitoring offload metrics per namespace is mandatory [2].

**Compatibility algebra vs. reality.** The table in §4.3 assumes disciplined producers. A producer that changes a field's *semantic* meaning without changing its name or type is fully compatible by every checker and silently corrupts every projector. Compatibility is necessary but not sufficient; event versioning policy remains a design discipline, not a checkable property [5][7].

## 7. Conclusion

We have presented a complete architecture for event sourcing at scale on Apache Pulsar, organized around four mechanisms that compose cleanly because Pulsar's storage layer was designed with compatible seams: sealed segments make tiered offload race-free [2][3]; the marker-based transaction protocol makes multi-partition atomic publication safe [1]; Avro's resolution rules make independent deployment of producers and projectors checkable [5]; and deterministic folds over the log make read-model rebuilds reproducible and their latency analytically bounded [7][8].
