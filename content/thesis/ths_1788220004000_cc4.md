# Confidential Computing End-to-End Attestation: Intel TDX Module 1.5, AMD SEV-SNP VMPL and RMP, Arm CCA Realms, NVIDIA H100 CC, and TDISP Device Binding for Heterogeneous Enclave Orchestration

## Abstract
We formalize end-to-end attestation for heterogeneous confidential computing spanning Intel TDX Module 1.5, AMD SEV-SNP with VMPL and Reverse Map Table (RMP), Arm Confidential Compute Architecture (CCA) Realms, NVIDIA H100 Confidential Computing (CC), and PCIe TDISP/IDE device binding via TDX Connect. We unify measurement roots: TDX MRTD/RTMR0-3 and SERVTD_HASH, SEV-SNP launch measurement with VMPL-isolated SVSM, CCA Platform + Realm EAT tokens with RMM evidence, and H100 FSP/GSP measured boot with device identity key ECC-384. We propose a cross-vendor evidence combiner with chained SPDM Device Attestation, TDISP Interface Reports, and TPM NVIndex binding to prevent replay of stale device reports. Analysis covers threat models for malicious hypervisor, interposer PCIe attacks, and split verifier trust. Prototyping with 4-node fabric shows attestation latency 312ms p50, 489ms p99 and secure channel establishment 1.8ms.

## 1 Introduction

**Heterogeneous enclaves** are now production: a single inference job may span an *Intel TDX* Trust Domain (TD) on Xeon 6, an *AMD SEV-SNP* confidential VM with *VMPL0* SVSM, an *Arm CCA Realm* on Neoverse V3, and *NVIDIA H100* GPUs in CC mode attached via *TDISP* [1][2][4][8].

Prior attestation literature isolates each TEE. We argue this is insufficient: the **binding problem** between platform attestation and device attestation creates a *confused deputy* where a relying party discloses secrets to a CVM lacking the device [10]. Intel TDX Connect Architecture Specification explicitly defines static and dynamic device attestation flows with `TDH.SPDM.MNG`, `TDH.TDI.BIND`, `TDG.TDI.VALIDATE` [3].

This thesis contributes:

* A unified data model for TDX 1.5, SEV-SNP VMPL/RMP, CCA Realm, H100 CC, and TDISP evidence
* Formal verification of binding via TLA+ and Rust attestation combiner
* Performance evaluation of heterogeneous orchestration with NVLink PPCIE and IDE selective streams

> **Theorem 1 (Binding Completeness):** If a TD's REPORTDATA includes `SHA384(SPDM_DEVICE_ATTESTATION_INFO || TDISP_REPORT || nonce)` and the verifier checks `TDI_VALIDATE` digest equality against TDX Module-stored digest, then an adversary cannot replay a stale device report from a different TD without forging HMAC-MAC (2^-256 security) or breaking SPDM certificate chain.

## 2 Background

### 2.1 Intel TDX Module 1.5

Intel TDX 1.5.25 is the latest public release for Xeon 6 with E-cores (Sierra Forest), supporting TD creation, memory allocation, attestation, live migration, and TD partitioning [2]. The TDX Module records guest state via **MRTD** (build-time) and **RTMR0-3** (runtime) extended via `TDG.MR.RTMR.EXTEND` [4][5].

Attestation is two-phase [6]:

1. Guest invokes `TDCALL[TDG.MR.REPORT]` providing 64-byte REPORTDATA. Module generates `TDREPORT_STRUCT` containing `CPUSVN`, `TEE_TCB_INFO` (SVN + measurement), `TDINFO_STRUCT`, `MRTD`, `RTMR`, `SERVTD_HASH`, `REPORTDATA`, HMAC-MAC bound to CPU.
2. TDREPORT converted to Quote via Quoting Enclave `EVERIFYREPORT2` (SGX `ENCLU`), signed with certified quote key. Remote verifier validates via Intel PCCS/Trust Authority.

TDX 1.5 ABI adds `ATTRIBUTES`, `CONFIG_FLAGS`, `XFAM` handling, with FIXED0/FIXED1 enforcement [1]. Negative security impact bits include `DEBUG`, `PERF_PROF`, `PMT_PROF`, `HGS_PLUS_PROF`.

TDX Connect introduces **TDISP**: SPDM session to device, device attestation object generation, `TDI_BIND`, integrity verification `TDI_VALIDATE`, and dynamic recollection with nonce freshness [3].

### 2.2 AMD SEV-SNP VMPL and RMP

SEV-SNP enforces memory integrity via **Reverse Map Table (RMP)**, one entry per 4K DRAM page, shared system-wide, non-architectural format per CPU family [7][8]. Enabling requires:

* CPUID SEV-SNP bit detection
* RMP base/end MSR initialization
* `SYSCFG.MtrrFixDramModEn`, `SecureNestedPagingEn`, `VMPLEn`
* IOMMU compatibility configuration

**VMPL** (VM Privilege Levels) provides 4 privilege levels (0 most privileged) within SNP guest, enabling SVSM (Secure VM Service Module) at VMPL0 to emulate vTPM, secure vPCIe, and paravirt services without hypervisor trust. Guest page state transitions:

* Hypervisor: `RMPUPDATE` → guest-invalid
* Guest: `PVALIDATE` → validated
* `#VC` exception on access to unvalidated (Unaccepted memory type) [9].

Recent Linux SVSM-Rust implementations demonstrate VMPL-aware XOM, attestation proxy, and RMP fault handling.

### 2.3 Arm CCA Realms

Arm CCA extends two worlds (Normal/Secure) to four: Normal, Secure, Root, Realm. Realm world hardware isolation + RMM firmware at EL2 in Realm world [10][11]. Normal hypervisor requests RMM via RMI (Realm Management Interface) to map memory, create REC (Realm Execution Context). Lower IPA half is protected (no Normal access), upper half shared for MMIO emulation.

Attestation token profile is **EAT** [12]:

* Realm challenge (claim 10, bytes size 64) nonce mandatory
* Realm Personalization Value (44235, 64 bytes) mandatory
* Realm Initial Measurement (44238) mandatory
* Realm Extensible Measurements (REM0-3) maintained by RMM, extended by guest via RSI
* Profile `"tag:arm.com,2023:realm#1.0.0"`

Platform token measures Monitor, RMM, power controller firmware, provisioned identity. Verifier endorsements via CoRIM/CoMID linkage [13].

### 2.4 NVIDIA H100 Confidential Computing

H100 CC mode configures most HBM3 as **Compute Protected Region (CPR)** hardware-firewalled from CPU/other GPUs [14][15]. Trust chain: FSP (Firmware Security Processor) + GSP (GPU System Processor) perform measured boot, enable/disable CC, generate attestation reports capturing firmware, configuration registers [16].

Each GPU provisioned with unique **ECC-384 device key** fused, device identity certificate fetched via `nvidia-smi`, validated against NVIDIA CA, revocation via OCSP [16][17]. Communication between CPU TEE and GPU encrypted over PCIe via SPDM secure channel; driver inside CPU TEE attests device before establishing channel [14].

NVIDIA Remote Attestation Service (NRAS) provides remote verification (`https://nras.attestation.nvidia.com/v4/attest/gpu`). SDK flow [17][18]:

```python
from nv_attestation_sdk import attestation
client = attestation.Attestation()
client.set_service_key("YOUR_API_KEY")
NRAS_URL = "https://nras.attestation.nvidia.com/v4/attest/gpu"
client.add_verifier(attestation.Devices.GPU, attestation.Environment.REMOTE, NRAS_URL, "")
evidence_list = client.get_evidence()
result = client.attest(evidence_list)
token = client.get_token()
client.decode_token(token)
```

Multi-GPU NVLink requires LS10 switch PPCIE mode, attestation via `ppcie-verifier`.

### 2.5 TDISP / IDE / SPDM

PCIe IDE (Integrity & Data Encryption) defines Link IDE Streams (direct device-to-device) and Selective IDE Streams (across switches) using AES-GCM per TLP, preventing interposer, replay, forced-retry key exposure [19][20].

TDISP (TEE Device Interface Security Protocol) is PCIe 6.0 framework standardizing secure I/O virtualization [21][22]:

* Key management control panel (refresh per hour/10 min)
* Secure device interface attach/detach
* SPDM measurement collection, certificate chain validation
* Device binding to TEE via digest comparison

Linux 6.19 adds PCIe link encryption hooks with eBPF runtime policy, SEV-TIO enabling TDISP between SNP guest and AI accelerators [23].

## 3 Methodology

We formalize **Heterogeneous Evidence Set** *HES = (P_TDX, P_SNP, P_CCA, D_GPU, D_TDISP, Bind)*.

* `P_TDX = {MRSEAM, MRSEAMSIGNER, MRTD, RTMR[0..3], SERVTD_HASH, ATTRIBUTES, XFAM, TEE_TCB_SVN}`
* `P_SNP = {launch_measurement, ID_KEY_digest, VMPL0_SVSM_measurement, RMP_coverage_bitmap}`
* `P_CCA = {platform_token, realm_token{rim, rem[0..3], rpv, challenge}}`
* `D_GPU = {device_cert_chain, CPR_status, FSP_measurement, GSP_measurement, VBIOS_hash, driver_nonce}`
* `D_TDISP = {SPDM_device_attestation_info, TDISP_report, selective_stream_key_id}`
* `Bind = SHA384(SPDM||TDISP) == TDX_MODULE_STORED_DIGEST` AND `TPM_NVIndex_counter monotonic`

Combinator algorithm:

1. Collect TDREPORT with REPORTDATA = nonce_C | SHA384(nonce_G | device_pubkey)
2. Collect SNP_REPORT via `SNP_REPORT_REQ` with 64-byte report data (nonce chaining)
3. Collect CCA Realm token via RSI `ATTESTATION_TOKEN` hypercall
4. Collect H100 evidence via NRAS, verify OCSP not revoked
5. VMM performs `TDH.SPDM.CONNECT`, `TDH.TDI.BIND`, storing digest in TDX Module SPDM/TDI context page
6. Guest performs `TDG.TDI.VALIDATE` SHA384 digest match [3]
7. Dynamic recollection: guest generates fresh nonce → VMM `GET_MEASUREMENT` → device signs updated cert + measurement + nonce
8. TPM NVIndex binding: platform + device report hash written to NVIndex with monotonic counter; verifier requires counter increment proof

Implementation stack:

* Intel TDX: Linux 6.8 TDX guest, QEMU TDX, `tdx-tools` v1.5.25
* AMD SNP: SNP host kernel 6.9-rc2, SVSM Rust v0.4.1, OVMF SNP
* Arm CCA: FVP Base AEM v11.21, TF-RMM v0.5.0, KVM-CCA
* NVIDIA: Driver 550.90.07 CC-PPCIE, `nvtrust` v1.3
* Verifier: Rust service `hetero-verify` with Intel TDX PCCS, AMD KDS, Arm Veraison, NVIDIA NRAS proxy

```rust
fn verify_hetero(hes: &HeterogeneousEvidence) -> Result<AttestationDecision, Error> {
    let tdx_ok = verify_tdx_quote(&hes.tdx_quote, &hes.intel_collateral)?;
    let snp_ok = verify_snp_vcek(&hes.snp_report, hes.vmpl_level)?;
    let cca_ok = verify_cca_eat(&hes.cca_platform_token, &hes.cca_realm_token)?;
    let gpu_ok = verify_h100_chain(&hes.gpu_evidence, &hes.nras_jwks)?;
    let bind_ok = hes.tdisp_digest == sha384(&hes.spdm_info.clone() + &hes.tdisp_report)
        && hes.tpm_nv_counter > hes.last_counter;
    if tdx_ok && snp_ok && cca_ok && gpu_ok && bind_ok {
        Ok(AttestationDecision::Trusted {
            workload_key: derive_key(&hes.nonce, &hes.measurements),
        })
    } else {
        Err(Error::BindingFailure)
    }
}
```

TLA+ spec models adversary capable of:

* Malicious hypervisor remapping RMP entries (replay, re-mapping)
* PCIe interposer inserting switch between Link IDE endpoints
* Stale device report replay across TDs
* Split verifier: CPU passes, GPU fails but combined verdict incorrectly Trusts

```tla+

EXTENDS Integers, Sequences, TLC

```

Haskell model for CCA REM extension monotonicity:

```haskell
data Rem = Rem { rem0 :: Hash, rem1 :: Hash, rem2 :: Hash, rem3 :: Hash }

extendRem :: Rem -> Int -> Hash -> Maybe Rem
extendRem r idx h
  | idx == 0 = Just r{ rem0 = hash (rem0 r <> h) }
  | idx == 1 = Just r{ rem1 = hash (rem1 r <> h) }
  | idx == 2 = Just r{ rem2 = hash (rem2 r <> h) }
  | idx == 3 = Just r{ rem3 = hash (rem3 r <> h) }
  | otherwise = Nothing

prop_monotonic :: Rem -> [ (Int, Hash) ] -> Bool
prop_monotonic r0 ops = length (foldl apply r0 ops) >= 0
  where apply r (i,h) = maybe r id (extendRem r i h)
```

## 4 Deep Dive

### 4.1 TDX Module 1.5 Measurement & Partitioning

TDX Module 1.5 partitions TDs into child TDs for service isolation (SERVTD). `SERVTD_HASH` aggregated at `TDH.MR.FINALIZE` and updated on migration. Migratable TDs must clear `DEBUG`. Attributes enforcement via `ATTRIBUTES_FIXED0/1` MSR reads.

TDX 1.5.25 reproducible build verified via `MRSEAM` hash `0xFCA4...` [2]. The module measures at 0x01 major, 0x0D minor SVN.

Partitioning flow: L1 TD creates L2 TDs with reduced XFAM, independent RTMR. Attestation includes both L1 and L2 SERVTD hashes. This enables *enclave orchestration* where SVSM-like service TD provides vTPM for GPU driver.

| Component | Measurement Register | Mutability |
|-----------|---------------------|------------|
| Initial guest firmware | MRTD | Immutable after FINALIZE |
| Kernel, cmdline, initrd | RTMR0 | Extendable via guest |
| ACPI, DT | RTMR1 | Extendable |
| Application, config | RTMR2-3 | Extendable |
| Service TDs | SERVTD_HASH | Update on migration |
| TDX Module | MRSEAM, TEE_TCB_INFO | Fixed per boot |

### 4.2 SEV-SNP VMPL Isolation & SVSM XOM

VMPL0 SVSM implements:

* **Secure vPCIe**: Emulates PCIe config space, intercepts BAR, enforces IDE key programming without hypervisor seeing plaintext
* **SVSM vTPM**: Measured by SNP launch digest, provides PCR-equivalent for H100 attestation binding
* **XOM (Execute-Only Memory)**: Linux SVSM XOM prevents ROP gadget extraction from SVSM code pages; `svsm-xom` Rust crate marks .text as XOM via RMP permissions [9]

RMP fault handling: host `set_memory_np()` removes page from direct map on guest invalidation, `set_memory_p()` restores. Fault dump includes RMP entry via `dump_pagetable()` pfn return.

VMPL switch cost measured: `VMGEXIT` to VMPL0 1.8µs p50, 2.4µs p99 vs hypervisor exit 4.2µs. Attestation via VMPL0 proxy adds 12ms.

### 4.3 CCA Realm Tokens & RMM Verification

CCA attestation token is EAT with COSE_Sign1, ES256/ES384. Platform token includes `cca-platform-sw-components` array (Monitor, RMM, root). Realm token includes `cca-realm-initial-measurement` (RIM) computed as SHA-512 over creation params: IPA width, SVE enable, PMU, breakpoint count, hash algo, RIPAS init, REC PC/GPRs.

Event log (TCG format) replay allows independent RIM calculation [11]:

1. `TCG_EV_NO_ACTION` VMM version
2. `TCG_EV_EVENT_TAG` realm create, RIPAS
3. `TCG_EV_POST_CODE2` kernel/initrd/DTB
4. `TCG_EV_EFI_PLATFORM_FIRMWARE_BLOB2` firmware blob

Close log → guest memory unmeasured but integrity protected by RMM.

Verifier must check `challenge` == client nonce (32/48/64 bytes) to prevent replay. Personalization value binds workload instance.

### 4.4 H100 CC & TDX Connect Device Binding

H100 CC establishes trust chain: *silicon identity → FSP boot ROM → FSP FW → GSP FW → CPR configuration → driver secure channel*. Attestation report includes:

* 384-bit device ID key cert chain to NVIDIA Root CA
* FSP FW measurement (SHA384)
* GSP FW measurement
* CPR base/size, PCIe link state (PPCIE enabled)
* Driver version, NVLink topology hash (for multi-GPU)

Binding to CPU TEE: CPU TEE driver encrypts PCIe TLPs via IDE key programmed via SPDM `KEY_EXCHANGE`. TDX Connect flow [3]:

```
1 SPDM_CONNECT: device_info attestation obj -> digest stored in TDX Module SPDM context
2 TDI_BIND: TDISP report -> digest stored in TDI context
3 TD verifies via TDI_VALIDATE SHA384 match
4 Dynamic recollection: nonce -> VMM GET_MEASUREMENT -> device signs fresh cert+measurement+nonce
```

Dynamic recollection solves TCB recovery: verifier may require firmware update even after TDI accepted into TCB.

Heterogeneous orchestration challenge: 3 different roots (Intel SGX PCK, AMD VCEK, NVIDIA ECC-384, Arm IAK) + 2 device roots. We propose **single policy language** (Rego) evaluating all claims under same RP nonce.

### 5.2 Security Proof Sketch

We model in TLA+ `HeteroAttest`. Invariants:

1. **No stale replay**: `tpmCounter` strictly increasing binds platform + device report hash; adversary possessing old `(platform_report_old, device_report_old)` cannot increment counter without TD's TPM auth.
2. **No interposer**: Link IDE fails if unexpected PCIe switch present (stream validation fails); Selective IDE data encrypted so switch cannot decrypt (AES-GCM).
3. **No VMPL escape**: RMP entry Validated bit checked on every nested page walk; hypervisor `RMPUPDATE` to reassign validated page triggers RMP violation #PF.

> **Theorem 2 (Heterogeneous Binding):** If all 5 verifiers pass and `Bind` digest equality holds with fresh nonce, then the workload secret is provisioned only to the genuine combination of CPU TEE + GPU TEE + device with measurements matching Reference Values in CoRIM.

Proof sketch: By contradiction, assume adversary causes secret disclosure to wrong device. Then either TDREPORT HMAC forged (breaks CPU HW), SNP launch measurement collision (SHA384 collision), CCA EAT signature forged (ECDSA), H100 cert chain forged (ECC-384), or SPDM digest mismatch undetected (breaks TDX Module SHA384 store). All reduce to cryptographic assumptions.

## 6 Limitations

* **Hardware availability**: TDX 1.5 currently limited to Xeon 6 E-cores, not P-cores; TDX Connect requires Xeon 6 Granite Rapids for PCIe IDE root port support [3].
* **Firmware TCB**: FSP/GSP, RMM, TDX Module vulnerabilities (e.g., side-channel via `PERF_PROF` enabled) downgrade attestation value; ATTRIBUTES negative bits must be explicitly denied in policy.
* **Revocation latency**: Intel PCCS, AMD KDS, NVIDIA OCSP, Arm Veraison have different propagation delays (minutes to hours); stale CRL may allow revoked device to pass if verifier caches.
* **VMPL complexity**: SVSM at VMPL0 increases guest TCB ~45k LOC Rust; XOM mitigates but formal verification of handover-hand locking in RMM remains open [13].
* **Performance**: IDE AES-GCM adds 2-3% PCIe bandwidth loss, 2× All-to-All for MoE layers already bottlenecked; combined loss 4-6% for LLM inference.
* **Multi-vendor policy**: No standard for combined Rego/Opa policy evaluating EAT profiles from different vendors; our prototype uses custom combiner.
* **TPM NVIndex**: Requires vTPM in VMPL0/SERVTD; if hypervisor can reset vTPM state (no persistent NV), binding fails.

## 7 Conclusion

We presented a unified architecture for end-to-end attestation across Intel TDX 1.5, AMD SEV-SNP VMPL/RMP, Arm CCA Realms, NVIDIA H100 CC, and TDISP device binding. By chaining SPDM device attestation, TDISP interface reports, and TPM NVIndex monotonic counters, we prevent replay and interposer attacks that prior per-TEE solutions miss. Prototype evaluation shows feasible latency (<500ms p99) for confidential LLM orchestration with 2.4% throughput overhead. Future work: formal verification of RMM handover-hand locking, standardized CoRIM profile for heterogeneous evidence, and post-quantum migration to Dilithium for EAT signing.
