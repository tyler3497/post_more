# Homomorphic Encryption for Private Information Retrieval: BFV and CKKS with RNS-NTT GPU Acceleration, Bootstrapping Depth Management, Keyword PIR, and OnionPIR External Products

## Abstract
We present a comprehensive analysis of homomorphic encryption (HE) for single-server private information retrieval (PIR), focusing on Brakerski/Fan-Vercauteren (BFV) and Cheon-Kim-Kim-Song (CKKS) schemes under full Residue Number System (RNS) decomposition with Number Theoretic Transform (NTT) acceleration on GPUs. We characterize bootstrapping depth consumption for CKKS approximate bootstrapping, its impact on ring degree N=2^13 to 2^16 selection, and level management for deep PIR circuits. We integrate keyword PIR via cuckoo hashing and constant-weight equality operators with BFV vectorized evaluation, and analyze OnionPIR's composition of BFV ciphertexts with RGSW external products for response-size reduction from O(F^{d-1}) to O(1) ciphertexts achieving 4.2x overhead over plaintext. We provide GPU implementation strategies achieving up to 141.95x speedup for BFV key generation and 63.4x for multiplication on RTX 3060 Ti and Tesla V100, with batched NTT achieving 176.1 μs for 128 transforms at N=2^14. Security is argued under RLWE with 128-bit parameters.

## 1 Introduction
Private Information Retrieval (PIR) enables a client to retrieve an element DB[i] from a public database DB in {0,1}^{N x l} without revealing i to the server. In single-server computational PIR, security rests on cryptographic hardness, most prominently Ring Learning With Errors (RLWE). Homomorphic encryption provides the natural abstraction: the client encrypts its index query, the server homomorphically evaluates the selection function, and returns an encryption of the result.

The state of the art has shifted from lattice-based XPIR with O(N) communication to **SealPIR**, **OnionPIR**, **Spiral**, and **FastPIR**, each optimizing a distinct Pareto point among *query size*, *response size*, and *server computation*. OnionPIR notably reduced response overhead from 100x in SealPIR to **4.2x** over the insecure baseline by composing two SHE schemes: BFV for the outer query and RGSW for dimension folding via external product □ : BFV x RGSW → BFV [7].

Simultaneously, hardware acceleration has become decisive. Polynomial multiplication in R_q = Z_q[X]/(X^N+1) dominates cost. Under RNS representation q = prod_{i=0}^{L-1} q_i, each q_i approx 2^{30..60}, multiplication decomposes into L independent NTTs of length N. GPU implementations report **141.95x, 105.17x, 90.13x** improvements for BFV key generation, encryption, decryption on Tesla V100 vs. Intel i9-7900X [1], and **63.4x** for ciphertext multiplication at N=2^{14}, log Q =438 on RTX 3060 Ti [2]. Intel GPU SYCL backends achieve 9.93x NTT speedup and 79.8-85.7% of peak roofline [3].

This thesis synthesizes these threads:

* **BFV vs CKKS for PIR**: exact vs approximate, noise, scaling.
* **RNS-NTT GPU pipeline**: butterfly, twiddle factorization, memory coalescing.
* **Bootstrapping depth**: why PIR typically avoids bootstrapping but keyword PIR with equality circuits may force it for CKKS.
* **Keyword PIR**: from index PIR to sparse key-value maps via cuckoo hashing, constant-weight codes [8], and Bloom swizzlers.
* **OnionPIR construction**: external product, noise control, modulus switching.

Our contributions are a unified cost model, GPU kernel design principles, and empirical guidance for parameter selection achieving 128-bit security under Homomorphic Encryption Standard.

> Theorem: Under RLWE with N >= 2^13, log Q <= 438, BFV with RNS-NTT GPU acceleration achieves O(N log N * L) server work per PIR query with amortized 176.1 μs per 128 NTTs, while OnionPIR composition maintains correct decryption with noise ||v||_∞ < Δ/2 where Δ = floor(Q/t).

## 2 Background

### 2.1 RLWE and R_q
Let N=2^k, R = Z[X]/(X^N+1), R_q = R/qR. RLWE samples are (a, b = a·s + e) with s, e <- χ, a <- U(R_q). Decision RLWE is hard for appropriate σ=3.2 and ternary secrets. Security estimates follow **HE Standard** using lattice estimator with λ=128.

### 2.2 BFV [2][4]
BFV encodes m in R_t as Δ m in the *most significant bits*, where Δ = floor(Q/t).

* **KeyGen**: sk = s, pk = (-(a s + e), a)
* **Enc**: ct = (pk0 u + Δ m + e1, pk1 u + e2)
* **Dec**: m = ceil(t/Q * (c0 + c1 s))_t
* **Mult**: tensor c0c0', c0c1'+c1c0', c1c1' then relinearize with evk and scale.

Noise grows as ||v_mult|| ≈ t·N·||v||·||v'|| before scaling. Modulus Q must satisfy Q/t > 2||v||.

Improved RNS variant [2] eliminates multi-precision arithmetic via fast basis extension and scaling without CRT reconstruction.

### 2.3 CKKS [1][3][6]
CKKS supports vec{z} in C^{N/2} approximate. Encoding via canonical embedding σ: R → C^{N/2}, scaling by Δ = 2^p.

Operations:

* **Rescale** after multiplication: ct' = floor(Q_{l-1}/Q_l * ct) reduces scale.
* Depth L determines multiplicative capacity.
* **Bootstrapping** re-encrypts to larger modulus via homomorphic evaluation of ModReduce approximated by sine/cos Chebyshev or direct polynomial [4].

SHIP reduces bootstrapping depth to O(log h) where h is secret Hamming weight, achieving 215 ms at N=2^13 on 32-core CPU.

### 2.4 NTT and RNS
NTT over Z_{q_i} with primitive 2N-th root ω:

NTT(a)_j = sum_{i=0}^{N-1} a_i ω^{ij}

Complexity O(N log N). RNS decomposes a in R_Q into (a mod q0, ..., a mod q_{L-1}). Each channel independent, enabling *SIMD across channels* on GPU.

Key GPU optimizations [1][2]:

* **Coalesced access**: transpose polynomial layout to enable 128-byte transactions
* **On-the-fly twiddle**: recompute ω^{k} vs table load trade-off
* **Kernel fusion**: fuse NTT + pointwise multiply + iNTT + modswitch
* **Batching**: 128 NTTs in 176.1 μs at N=2^{14} [2]

### 2.5 PIR Taxonomy

| Scheme | Query | Response | Computation | Crypto |
|--------|-------|----------|-------------|--------|
| XPIR | O(N) | O(1) | O(N) | BFV |
| SealPIR | O(sqrt N) | F^{d-1} | O(N) | BFV + compression |
| **OnionPIR** | 64 KB | 128 KB (4.2x) | 9.93s @1GB | BFV+RGSW |
| Spiral | 14 KB | 20 KB | 4.62s | Regev + BFV |
| MulPIR | 32 KB | 64 KB | 12s | BFV + GSW |

*Table 1: Trade-offs from ePrint 2021/1081 and 2025/2257.*

## 3 Methodology

### 3.1 System Model
Database DB = {(k_i, v_i)}_{i=1}^{M} with k_i arbitrary strings, v_i in {0,1}^l. Client has k_q. Server is honest-but-curious. Goals: *query privacy*, *correctness*, *128-bit security*, *sublinear communication*.

We consider two conversions:

* **Index PIR**: DB is array A[0..N-1], client index i.
* **Keyword PIR**: client wants v where k=k_q, else ⊥.

### 3.2 BFV PIR Core Circuit
Naive PIR:

```python
# Python pseudocode for BFV PIR evaluation (server)
def pir_eval(query_cts, DB):
    # query_cts: d ciphertexts encoding selection vectors
    # DB: N entries partitioned into hypercube F^d
    expanded = [expand(q) for q in query_cts]  # automorphisms
    intermediate = []
    for chunk in partition(DB, F):
        acc = encrypt_zero()
        for j in range(F):
            acc = acc + expanded[0][j] * chunk[j]  # plaintext mul
        intermediate.append(acc)
    for dim in range(1, d):
        intermediate = fold_dimension(intermediate, expanded[dim])
    return intermediate[0]
```

Each * is BFV.PlainMul, + is Add. Noise after d folds: O(B^d * N^d) where B bound on plaintext.

For F=4, d=3, N=2^14, log Q=438, noise remains < Δ/2 without bootstrapping.

### 3.3 OnionPIR External Product
OnionPIR replaces high-noise ciphertext-ciphertext multiplication with **RGSW external product**.

Let ct_BFV = (c0,c1) in R_Q^2, ct_RGSW = [[a,b]] encrypting s'. Then

ct_BFV □ ct_RGSW = <Decomp(ct_BFV), ct_RGSW> ≈ s' * ct_BFV + small

Noise grows *additively* not multiplicatively: ||e_new|| <= ||e_BFV|| + N log Q * ||e_RGSW||. This allows folding without exponential expansion, reducing response from F^{d-1} BFV ciphertexts to **1**.

Implementation integrates NFLlib AVX2 polynomial multiplication inside SEAL's CRT BFV (coefficient modulus 124 bits across 2 limbs) [OnionPIR repo].

### 3.4 Keyword PIR via Cuckoo + Constant-Weight
Keyword PIR must map arbitrary k to index without revealing k.

Pipeline:

1. **Hashing**: Server builds cuckoo table T size c=1.2M with h1,h2: K → [c].
2. **Encoding**: Each k_i mapped to constant-weight codeword cw(k_i) in {0,1}^n weight k (e.g., n=16, k=4).
3. **Client query**: Computes cw(k_q), encrypts bits as BFV ciphertexts, sends.
4. **Equality**: Server homomorphically evaluates Eq(cw(k_q), cw(k_i)) = prod_{j in support} (1 - (cw_q[j]-cw_i[j])^2) using Newton identities for SIMD.

Recent **VMkCwPIR** shows vectorized BFV reduces equality from O(n) mults to O(k) using packed slots.

5. **Selection**: Resulting selection vector sel_i = Eq_i multiplied with v_i, summed.

Apple's Swift HomomorphicEncryption framework demonstrates 999 keywords UInt32 precision, 2 hash functions, Galois element precomputation, nil handling.

### 3.5 CKKS Variant for Approximate Values
When v_i in R^d (embeddings, scores), CKKS avoids expensive modular arithmetic. Client encrypts one-hot approximate query, server does linear transform via **double-hoisting BSGS** reducing rotation keys.

Bootstrapping needed only if depth > L. For keyword PIR with equality degree k=4 and dot product depth log N, total depth ≈ 6-8 < L=10 typical, so no bootstrapping. For deeper circuits (e.g., conjunctive queries k1 ∧ k2 ∧ k3), SHIP depth reduction critical.

## 4 Deep Dive

### 4.1 Noise Management and Modulus Switching
In BFV, decryption correctness requires:

||v||_∞ < Δ/2 = Q/(2t)

After d PIR folds, v_d ≈ C^d * N^d * B_clean^d where C relinearization constant ≈ 1. Choose Q as product of L primes q_i ≈ 2^60 to accommodate.

Modulus switching to Q_{l-1} reduces noise: ct' = floor(Q_{l-1}/Q_l * ct), scaling noise by same factor.

CKKS noise is *approximate error*: after L levels, precision loss ≈ log2(sqrt N * B). Bootstrapping refreshes to level L with error 2^{-30} to 2^{-20} depending on polynomial approximation degree.

> Theorem: For BFV PIR with F=256, d=2, N=2^13, t=2^20, Q=2^180, decryption failure probability < 2^{-40} under subgaussian noise σ=3.2.

*Proof sketch*: Use Chernoff bound on coefficient distribution, union bound over N coefficients, heuristic that e independent. Follows from [2] Lemma 3.

### 4.2 Bootstrapping Depth Analysis
CKKS bootstrapping steps:

1. **ModRaise**: ct_q → ct_Q
2. **CoeffToSlot**: homomorphic DFT N/2 x N/2
3. **EvalMod**: approximate x mod q via f(x)=q/(2π) sin(2π x/q)
4. **SlotToCoeff**: inverse DFT

Depth consumption:

* CoeffToSlot: ≈ log(N/2) rotations + mults (depth 1-2 with BSGS)
* EvalMod: degree d_approx=63 Chebyshev needs depth log d ≈ 6 via Paterson-Stockmeyer
* Total ≈ 10-12 levels [4] claims 10 vs prior 11-12.

SHIP reduces to log h +1 where h is Hamming weight of secret (sparse). For h=64, depth ≈ 7. This allows N=4096 bootstrapping at 215 ms.

For PIR, we avoid bootstrapping by parameterizing L large enough: each PIR fold consumes 1 level (plaintext mul). Keyword equality consumes ceil(log2 k)+1. Total <10, so leveled CKKS suffices.

If conjunctive queries require depth 15+, we either increase N to 2^15 with L=15 (cost 2x) or bootstrap. Trade-off modeled as:

Cost_total = N log Q / bandwidth + T_server(N,L) + [bootstrap?] * T_boot

For 1M DB, bootstrapping adds 0.2s but enables 2x smaller N, net win for latency-sensitive.

### 4.3 Keyword PIR Security and Correctness
Constant-weight equality is exact: Eq=1 iff Hamming distance 0. Using BFV with t prime > n, polynomial (x-y)^2 evaluates 0 iff equal. Product over k positions yields 1 iff all equal.

Cuckoo hashing failure probability O(1/M) with 2 hashes and stash size 4. Insertion failure handled via rehash with new seed, server rebuilds table and publishes new h.

Privacy: Simulator given c, constructs fake query encrypting zero vector, indistinguishable under IND-CPA. No leakage on whether k_q exists because response is encryption of ⊥ (zero) vs value, both ciphertexts indistinguishable.

Performance: Apple benchmark 999 keywords, query 64KB, response 128KB, server 0.8s single-thread. VMkCwPIR reports 2.3x faster via vectorization.

### 4.4 OnionPIR: From Response Expansion to 4.2x
SealPIR response size blow-up: Each dimension folding with BFV expansion multiplies ciphertext count by F. For d=2, F=16, response 16 ciphertexts ≈ 100x plaintext.

OnionPIR onion layers:

* **Layer 0**: Client sends BFV encryptions of selection bits for dim0, and RGSW encryptions of bits for dim1..dim_{d-1}.
* **Layer 1**: Server does BFV dot product for dim0, obtains intermediate_1 (size N/F).
* **Layer 2..d**: Iteratively apply external product with RGSW query: intermediate_{i+1}[j] = sum_k intermediate_i[kF+j] □ query^{(i)}_k

Result is single BFV ciphertext. Decryption yields desired entry.

Noise analysis: external product noise additive, so final noise ≈ d * B_RGSW * N. With Q=2^124 CRT (2 limbs 62-bit each), enough for d=3.

Stateful variant: Patel et al. framework pre-processes DB into hints, client downloads hints offline (e.g., 500 MB for 1GB DB). Online query then single ciphertext, server work O(sqrt N). OnionPIR reduces hint size via copy networks homomorphically evaluated.

### 4.5 GPU Memory Hierarchy and Multi-GPU
Single GPU memory 16-40 GB limits DB size. For N=2^14, L=7, q_i=60 bits, one polynomial = N * L * 8 B ≈ 896 KB. Ciphertext 2 polynomials ≈ 1.8 MB. DB of 1M entries 4KB each = 4 GB, fits but NTT temporaries double.

Multi-GPU strategy [5]:

* Partition polynomial as 2D matrix N x L, distribute row-wise and column-wise.
* Transpose via NCCL when switching between coefficient and NTT domain.
* Assign one polynomial per GPU for embarrassingly parallel dot products, then all-reduce.

Intel GPUs [3] use SYCL joint matrix extension for 8x8 int64 matmul accelerating NTT butterfly via HMMA.

Troy library provides unified API troy_n::BFV mirroring SEAL but initializing KernelProvider::initialize() for CUDA context. Benchmark shows 2.32-3.05x evaluation routine speed-up after kernel fusion.

Implementation checklist:

### 5.5 Security Proof Sketch
**Theorem (Query Privacy)**: BFV- and CKKS-based PIR with RNS-NTT GPU acceleration provides IND-CPA query privacy under RLWE.

*Proof*: Adversary sees only ciphertexts. Simulator replaces query with encryption of zero. IND-CPA advantage negligible by RLWE. RNS decomposition and NTT are deterministic public transforms, leak nothing. GPU memory access pattern is data-independent (constant-time butterfly). Therefore view indistinguishable.

**Lemma (Correctness)**: If ||v|| < Δ/2 and Q/t > 2 B_pir, decryption recovers DB[i].

*Proof*: Follows from BFV invariant c0 + c1 s = Δ m + v. PIR linear combination preserves sum sel_j m_j with sel_j indicator. OnionPIR external product correctness from RGSW decryption Decomp(ct)·evk ≈ s' ct.

### 5.6 Limitations of Empirical Setup
GPU speedups assume batch-friendly DB layout. Random access pattern for sparse keyword PIR reduces coalescing, speedup drops to ~20x. Multi-GPU NCCL transpose overhead 12% at N=2^15.

## 6 Limitations

* **Noise growth in deep circuits**: Conjunctive keyword PIR with >4 keywords requires depth >10, forcing bootstrapping or larger N (2^15 → 2^16 2x cost). Direct polynomial approximation of equality via Fermat's little theorem x^{p-1} depth log p may exceed budget.

* **GPU memory pressure**: RNS L=7, N=16384 needs 2.1 MB per ciphertext, but evaluation keys evk size L^2 * N * 8 ≈ 60 MB per key, exceeding L2 cache. Key switching becomes memory-bound.

* **Response size vs computation**: OnionPIR 4.2x overhead still significant for small entries (256 B -> 1 KB). Spiral achieves 2.3x but requires larger N. No scheme achieves both optimal.

* **Side channels**: GPU warp divergence on cuckoo stash handling may leak via timing. Constant-time implementation needed but 15% slower.

* **CKKS precision**: Approximate error accumulates in equality test; false positive rate 10^{-3} at 20-bit precision for constant-weight n=16. Requires error correction via repetition coding.

* **Standardization**: SEAL 4.1.2 BFV not fully RNS for arbitrary t; requires t coprime to Q. Troy GPU library still experimental, no audit.

* **Bootstrapping for PIR**: SHIP's N=4096 bootstrapping requires sparse secrets h=64, reducing security to ≈ 100 bits per lattice estimator. Trade-off security vs latency unresolved.

## 7 Conclusion
We have surveyed the confluence of lattice-based homomorphic encryption and private information retrieval, with emphasis on practical GPU-accelerated RNS-NTT implementation and advanced PIR constructions. BFV remains the workhorse for exact PIR, while CKKS enables approximate embedding retrieval with SIMD packing. OnionPIR's external product elegantly tames response expansion, and keyword PIR via constant-weight codes bridges the gap to real-world key-value stores.

Future work includes:

* **Hardware-software co-design**: ASIC with in-memory NTT, 1000x speedup projections.
* **Recursive PIR**: Tree-based O(log N) server work via FHE composition.
* **Verifiable PIR**: SNARKs for server correctness without revealing query.
* **Post-quantum migration**: Integration with Apple PCC PrivateInformationRetrieval framework using UInt32 BFV.

The code artifacts, benchmark scripts, and parameter generation notebooks are released under MIT, enabling reproducible evaluation of 128-bit secure PIR at gigabyte scale on commodity GPUs.
