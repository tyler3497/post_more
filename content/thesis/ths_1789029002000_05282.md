# Machine-Checked Safety Proofs for Consensus: TLA+ Specifications, Inductive Invariants, and the Ivy Decidable-Fragment Methodology

## Abstract

Formal verification of distributed consensus has matured from a research curiosity into an engineering discipline with industrial impact. This paper presents a unified methodological account of how machine-checked safety proofs for consensus protocols are actually constructed: temporal-logic specification in **TLA+** and its algorithmic front-end **PlusCal**, explicit-state exploration with the **TLC** model checker as a bug-finding and invariant-discovery instrument, deductive proof of inductive invariants (manually in **TLAPS** or interactively in **Ivy**), and end-to-end refinement from high-level specification to executable code as pioneered by **IronFleet** and **Verdi**. We focus on *methodology* rather than protocol design: how inductive invariants are discovered and generalized from counterexamples to induction, how the effectively propositional (**EPR**) fragment of first-order logic makes SMT-based verification conditions decidable in Ivy, how TLA-style refinement mappings bridge the formality gap between models and implementations, and where the current techniques break down — state-space explosion, the liveness gap, and the proof-maintenance burden. The treatment is illustrated with a TLA+ specification of a Paxos core, an EPR-disciplined Ivy module, and a worked refinement argument.

---

##1 Intro

Consensus is the fault line of distributed systems: the protocols that decide what is true fail in the most subtle ways, and a consensus implementation that decides two different values corrupts every service built on top of it. As the AWS formal-methods team documented, some of the most dangerous bugs are *errors in design*, and testing is inadequate because "the number of reachable states of the code is astronomical" [2].

The response developed over three decades is to treat the protocol as a mathematical object first and a program second: **specify** it as a state machine in TLA+, the *Temporal Logic of Actions* [2][6]; **explore** its reachable state space with the TLC model checker as a bug-finding instrument [2]; **prove** safety for *all* instances by exhibiting an inductive invariant [4][6]; and **refine** the abstract specification down to executable code, preserving the proved properties by refinement mappings [1][7].

This paper is a methodology paper. It does not introduce a new consensus protocol, nor does it survey protocol families. Instead, it explains *how* the verification artifacts — specifications, invariants, refinement steps, proofs — are produced, checked, and maintained in the two dominant traditions: the **TLA+ tradition** (Lamport's specification language, TLC, TLAPS) and the **decidable-fragment tradition** (Ivy's EPR-based deductive verification). We also cover the two frameworks that close the formality gap to running code: **IronFleet**, which blends TLA-style state-machine refinement with Hoare-logic verification in Dafny, and **Verdi**, which composes verified system transformers in Coq [1][8].
##2 Background

### 2.1 Safety, Liveness, and the State-Machine View

A distributed consensus protocol is modeled as a **state machine**: a set of states, initial states, and a next-state relation (a disjunction of *actions*). A *behavior* is an infinite sequence of states linked by the next-state relation. Two property classes structure all verification work:

| Property class | Definition | Consensus instance |
|---|---|---|
| **Safety** | "Nothing bad ever happens"; a property of finite prefixes | *Agreement*: no two nodes decide different values |
| **Liveness** | "Something good eventually happens"; a property of infinite behaviors | *Termination*: every correct node eventually decides (under fairness/timing assumptions) |
| **Validity** | Safety over inputs | A decided value must have been proposed |

Safety properties are amenable to **invariant proofs**: find a state predicate *Inv* that (a) holds initially and (b) is preserved by every action, and that implies the safety property. Liveness additionally requires fairness assumptions and well-founded ranking arguments; it is substantially harder to mechanize, and most of the methodology below targets safety first [1].

### 2.2 Refinement: Relating Levels of Abstraction

A refinement mapping (Abadi–Lamport) shows that every behavior of a *low-level* (concrete) specification is also a behavior of a *high-level* (abstract) specification, modulo a mapping *f* from concrete states to abstract states. The refinement proof obligation: for every concrete step *s → s′*, either *f(s′) = f(s)* (stuttering) or *⟨f(s), f(s′)⟩* is an abstract step.

Refinement is the engine that makes verification scale: prove safety once at the most abstract level, then carry it down through layers — abstract consensus, message-passing protocol, executable code — each step checked mechanically, as IronFleet demonstrated for full implementations including liveness [1].

### 2.3 The Formality Gap

A model of a protocol is not the code. The *formality gap* determines how much of the machine-checked guarantee survives into production. Three strategies close it: **model-check the design** (AWS/TLA+: bugs found in design never reach code [2]); **prove the model, then refine to code** (IronFleet: the code is proved to refine the verified spec [1]); **verify the implementation directly** (Verdi: the implementation is written inside Coq and extracted to executable code [8]).

##3 Methodology

The methodology has five stages — specification, model checking, invariant discovery, machine-checked proof, refinement — each with a well-defined input, output, and checking criterion, composing into a tool-executed pipeline where the human supplies creativity at the discovery steps.

**Stage 1 — Formal specification.** Write the protocol as a TLA+ specification (or a PlusCal algorithm translated to TLA+): variables capture protocol state (ballot numbers, vote sets, message pools), actions capture atomic steps (*Prepare*, *Promise*, *Accept*). The specification is *executable by the model checker*, not by a compiler.

**Stage 2 — Model checking.** Run TLC on finite instances. TLC enumerates reachable states, checks the safety invariant on every state, and on violation returns a *minimal error trace* — traces (sometimes 35+ steps) that exposed bugs surviving design reviews, code reviews, and extensive testing at AWS [2].

**Stage 3 — Inductive invariant discovery.** The model checker proves nothing about unbounded instances. Strengthen the safety property *P* into an inductive invariant *Inv* (initiation, consecution, strength). Discovery is the creative step: manual in the TLA+ tradition, *interactive generalization from counterexamples to induction* in Ivy [4].

**Stage 4 — Machine-checked proof.** Discharge initiation and consecution in TLAPS (hierarchical interactive proof for TLA+) [6], Ivy's decidable-fragment SMT checks [3][4], or Dafny/Coq for code-level proofs [1][8].

**Stage 5 — Refinement to implementation.** Connect the verified specification to running code via refinement mappings (IronFleet), system transformers (Verdi), or code generation (Ivy's C++ extraction) [1][3][8].

> **Theorem:** An inductive invariant that is not *inductive* is not a proof. The consecution obligation — that every action preserves the invariant — is where nearly all the work, and nearly all the failed attempts, concentrate.
##4 Deep Dive

### 4.1 TLA+ and PlusCal: Specifying Protocols as Mathematics

TLA+ is based on the *Temporal Logic of Actions*: a specification is a temporal formula `Init ∧ □[Next]_vars ∧ Fairness`, with variables ranging over ordinary mathematical values — sets, functions, records, tuples. A TLA+ specification *is* the mathematics of the protocol.

**PlusCal** is an algorithm language that compiles to TLA+: engineers write familiar pseudocode with processes, and the translator produces the TLA+ actions. This matters for adoption — Amazon engineers learned TLA+ and wrote detailed specifications "in a couple of weeks" [2].

Consider the ballot core of a Paxos-like protocol, specified in TLA+:

```tla
--------------------------- MODULE BallotConsensus ---------------------------
EXTENDS Integers, FiniteSets

CONSTANTS Acceptors, Quorums, Ballots, Values

VARIABLES
  maxBal, maxVBal, maxVal, decided   \* promises, votes, decided values

TypeOK ==
  /\ maxBal \in [Acceptors -> Ballots]
  /\ maxVBal \in [Acceptors -> Ballots]
  /\ maxVal  \in [Acceptors -> Values \cup {None}]
  /\ decided  \in SUBSET Values

Init ==
  /\ maxBal  = [a \in Acceptors |-> 0]
  /\ maxVBal = [a \in Acceptors |-> 0]
  /\ maxVal  = [a \in Acceptors |-> None]
  /\ decided = {}

Prepare(a, b) ==
  /\ b > maxBal[a]
  /\ maxBal' = [maxBal EXCEPT ![a] = b]
  /\ UNCHANGED <<maxVBal, maxVal, decided>>

Accept(a, b, v) ==
  /\ b >= maxBal[a]
  /\ maxVBal' = [maxVBal EXCEPT ![a] = b]
  /\ maxVal'  = [maxVal  EXCEPT ![a] = v]
  /\ maxBal'  = [maxBal  EXCEPT ![a] = b]
  /\ UNCHANGED decided

Decide(v) ==
  /\ \E Q \in Quorums :
       \A a \in Q : maxVBal[a] > 0 /\ maxVal[a] = v
  /\ decided' = decided \cup {v}
  /\ UNCHANGED <<maxBal, maxVBal, maxVal>>

Next ==
  \/ \E a \in Acceptors, b \in Ballots : Prepare(a, b)
  \/ \E a \in Acceptors, b \in Ballots, v \in Values : Accept(a, b, v)
  \/ \E v \in Values : Decide(v)

Agreement == Cardinality(decided) <= 1
Spec == Init /\ [][Next]_<<maxBal, maxVBal, maxVal, decided>>
=============================================================================
```

With 3 acceptors, 3 ballots, and 2 values, TLC enumerates every reachable configuration; on violation it returns the shortest error trace, and the same spec feeds the proof stage unchanged.

### 4.2 Inductive Invariants: The Anatomy of a Safety Proof

The safety property (agreement) is typically **not** inductive by itself: from "at most one value decided" plus one protocol step you cannot re-derive it, because the step's precondition encodes *why* the decision was safe — ballot structure, quorum intersection, the promise discipline. The invariant must be **strengthened** with auxiliary facts until consecution goes through. Strengthening is the entire game.

> **Theorem (Agreement via quorum induction):** Let *I* assert: (i) any two decided values are equal; (ii) if value *v* is decided in ballot *b*, then every acceptor that voted in any ballot *b′ ≥ b* voted *v*; (iii) promises are monotone in ballot order. Then *I* is inductive, and *I ⇒ Agreement*.

The consecution argument is action-by-action. For `Accept(a, b, v)`: the precondition `b ≥ maxBal[a]` plus the promise discipline implies no quorum decided a different value in a ballot `< b` without *a* having seen it; conjunct (ii) propagates the decided value forward. For `Decide(v)`: a quorum of matching votes exists by the guard, and (ii) forces any *other* quorum's votes to agree.

This structure is checkable mechanically. The Python sketch below encodes the two proof obligations for a miniature state machine — exactly what TLAPS, Ivy, and Dafny check at scale:

```python
from itertools import product

states = [(b1, v1, b2, v2, d)                       # 2 acceptors, ballots {0,1}
          for b1, v1, b2, v2, d
          in product(range(2), range(3), range(2), range(3), range(4))]

def init(s):
    b1, v1, b2, v2, d = s
    return b1 == 0 and v1 == 2 and b2 == 0 and v2 == 2 and d == 3

def steps(s):
    b1, v1, b2, v2, d = s
    succ = []
    for i, (b, v) in enumerate([(b1, v1), (b2, v2)]):
        for nb in range(b + 1, 2):
            for nv in range(2):
                t = [b1, v1, b2, v2, d]
                t[2*i], t[2*i+1] = nb, nv
                succ.append(tuple(t))
    if v1 == v2 and v1 != 2:
        succ.append((b1, v1, b2, v2, v1))
    return succ

def inv(s):
    b1, v1, b2, v2, d = s
    return (d == 3 or d in (v1, v2)) and \
           not (v1 != 2 and v2 != 2 and v1 != v2 and b1 == b2 == 1)

print("initiation:", all(inv(s) for s in states if init(s)),
      "| consecution:", all(inv(t) for s in states if inv(s) for t in steps(s)))
```

On the real protocols the state space is infinite (unbounded ballots, arbitrary values), so enumeration is replaced by symbolic checks — which is where decidable fragments enter.

### 4.3 Ivy and the Decidable Fragment: Making the Checks Predictable

Ivy's central design decision is to restrict the verification language so that **every verification condition is decidable** [3]. The fragment is **EPR** — *effectively propositional logic*, the Bernays–Schönfinkel–Ramsey class: first-order formulas over a relational vocabulary (no function symbols) with prenex prefix `∃*∀*`. EPR satisfiability is decidable, and every satisfiable EPR formula has a finite model bounded by its existential quantifiers and constants [4]. Stratified functions and careful Skolemization extend the fragment without losing decidability [3].

Why does decidability matter? In interactive theorem proving, automated tactics are *unpredictable*: they fail opaquely, giving the user no actionable information. Ivy's hypothesis is that the real obstacle is not unreliability but **opacity** [4]. Inside EPR, every check terminates with either a proof or a **finite counterexample model** — and a finite counterexample to induction is something a human can inspect, understand, and generalize from.

This yields Ivy's signature workflow, *interactive generalization* [4]: propose a candidate invariant; Ivy checks initiation and consecution with Z3 in the EPR fragment; on failure it displays a **concrete counterexample to induction**; the user generalizes, adding a conjunct ruling out the counterexample class, and repeats.

An Ivy module for the ballot core looks like this (simplified RML/Ivy syntax):

```
module ballot_consensus(val, node) = {
    individual b : ballot
    relation voted(N:node, B:ballot, V:val)
    relation promised(N:node, B:ballot)
    relation decided(V:val)

    action prepare(n:node, b:ballot) = {
        require ~exists B:ballot. promised(n,B) & B >= b;
        promised(n,b) := true
    }
    action accept(n:node, b:ballot, v:val) = {
        require promised(n,b);
        voted(n,b,v) := true
    }
    action decide(v:val) = {
        require exists Q:quorum. forall N:node.
            member(N,Q) -> exists B:ballot. voted(N,B,v);
        decided(v) := true
    }

    invariant [agreement]
        forall V1:val, V2:val. decided(V1) & decided(V2) -> V1 = V2
    # further invariants (vote coherence, promise monotonicity)
    # are added by generalizing counterexamples to induction
}
```

The methodology scales through **modular decomposition**: a protocol is split into modules (ballot layer, quorum layer, leader-election layer), each verified in EPR against the abstract interfaces of the others. Padon et al. verified a full Paxos variant this way, and the "Paxos Made EPR" line showed that invariants *with quantifier alternation* — previously thought to require heavier machinery — stay inside the decidable fragment under the right stratification [4][5]. Ma et al. later pushed toward *automatic* invariant inference for Lamport's Paxos via hierarchical strengthening, inferring the invariant level by level [7].

### 4.4 Refinement to Code: IronFleet and Verdi

A proved model is half the battle; the other half is the implementation.

**IronFleet** (SOSP 2015) blends *TLA-style state-machine refinement* with *Hoare-logic verification* in Dafny [1]. The methodology layers specifications — a concise high-level spec, intermediate protocol specs, the Dafny implementation — each layer connected by refinement proofs that Dafny's automated verifier discharges. IronFleet proves **liveness** as well as safety for a Paxos-based replicated state machine (IronRSL) and a sharded key-value store (IronKV), with performance competitive with unverified equivalents. Total effort: about 3.7 person-years for both systems.

**Verdi** (PLDI 2015) works inside Coq and introduces *verified system transformers*: functions from implementations to implementations, with proofs that the transformed system satisfies properties analogous to the original [8]. Application logic is verified under a simple network semantics; a transformer (e.g., adding retransmission) proved *once* then preserves correctness under harsher fault models. Woos et al. produced the first formally verified implementation of **Raft** in Verdi — at the cost of discovering and proving **90 system invariants**, and developing an explicit "planning for change" methodology for proof maintenance [9].

| Framework | Proof assistant | Refinement mechanism | Liveness | Notable artifact |
|---|---|---|---|---|
| TLA+/TLC/TLAPS | TLAPS | Manual refinement mappings | Fairness-based | Multi-Paxos proof [6] |
| Ivy | Z3 (EPR) | Modular decomposition + code gen | Limited | Verified Paxos [4][5] |
| IronFleet | Dafny | Layered state-machine refinement | Yes | IronRSL, IronKV [1] |
| Verdi | Coq | Verified system transformers | Via transformers | Verified Raft [8][9] |

##5 Empirical/Proofs

The methodology's claims rest on published artifacts.

**Bug-finding power (AWS).** Since 2011, AWS engineers used TLA+ and TLC on S3, EBS, and DynamoDB [2]. In one case, TLC found a 35-step failure/recovery interleaving that had survived design reviews, code reviews, and testing; the engineer judged the TLA+ effort *less* time-consuming than the informal proofs it replaced. A later retrospective: modeling an Aurora commit protocol in TLA+ identified a safe optimization from two network round-trips to 1.5 [2].

**Proof scale (IronFleet).** Machine-checked safety *and* liveness for two substantial systems, with verified implementations running correctly on first execution and performing competitively with unverified counterparts [1]. The lesson: refinement-based methodology makes full-implementation verification *tolerable* rather than heroic, though still measured in person-years.

**Decidable-fragment verification (Ivy).** Interactive generalization inside EPR verifies realistic protocols (Paxos variants, cache coherence) with predictable, transparent automation [4]. "Paxos Made EPR" showed invariants with quantifier alternation remain decidable under stratification [5]; McMillan and Padon's survey positions Ivy as supporting deductive verification, model checking, testing, and code generation from a single specification [3].

**Invariant inference (Ma et al.).** "Towards an Automatic Proof of Lamport's Paxos" showed the invariant need not be written by hand all at once: hierarchical strengthening infers it level by level, each level consuming the assertions proved above it [7] — the most promising direction for reducing the methodology's dominant cost.

**Proof maintenance (Raft/Verdi).** Woos et al.'s verified Raft is both triumph and caution: 90 invariants, iterative discovery, and proof breakage whenever one invariant was strengthened [9]. Their "planning for change" methodology — information hiding, affinity lemmas, structural tactics — addresses what happens *after* the first proof: the protocol evolves.

##6 Limitations

**State-space explosion bounds TLC.** TLC checks finite instances; unbounded confidence comes only from the deductive proof. Symmetry reduction and distributed TLC (AWS ran it on EC2 clusters [2]) push the boundary, but the boundary remains.

**Inductive invariants are hard to find.** Consecution fails opaquely in TLAPS, and even in Ivy the user must generalize correctly from counterexamples. Automatic inference [7] works for textbook protocols; production protocols with reconfiguration and membership change remain largely manual.

**Liveness is a second-class citizen.** Most of the machinery above targets safety. IronFleet's liveness proofs are genuine [1], but depend on fairness assumptions real networks only approximate, and Ivy's decidable-fragment story for liveness is far less developed than for safety [3].

**The EPR discipline constrains modeling.** Decidability is a design constraint on the specification: no unstratified functions, careful quantifier discipline, modular decomposition forced by decidability rather than software-engineering taste [4][5].

**Proof maintenance is unsolved at scale.** The Raft experience — 90 invariants, cascading re-proof on every change [9] — suggests verified protocols rot like unverified code unless the proof is engineered for change. Tooling for proof evolution lags far behind tooling for code evolution.

**The formality gap never fully closes.** TLC checks a model, not code; IronFleet and Verdi close the gap by proof, but their trusted bases (verifiers, extraction, compilers, runtimes, network shims) are themselves unverified. Verification moves trust; it does not eliminate it.

---

##7 Conclusion

Machine-checked safety proofs for consensus are now a repeatable engineering methodology with three mature pillars. **TLA+** gives a mathematical specification language with a push-button model checker that finds real bugs in real systems [2]. **Inductive invariants** — by hand, by interactive generalization, or by automated strengthening — lift finite-instance confidence to unbounded proof [4][6][7]. **Refinement** — IronFleet's layered Dafny proofs, Verdi's verified transformers, Ivy's modular EPR decomposition — carries the guarantee from model to running system [1][3][8].

The open problems are now of *scale and maintenance*: automatic invariant inference for production protocols, liveness as predictable as safety, and proofs that survive protocol evolution. Keep automation predictable, keep counterexamples visible, keep refinement layers thin. The standard for distributed systems is moving from "tested" to "correct" [1] — and this methodology is how that move is made.
