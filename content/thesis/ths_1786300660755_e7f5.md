# Zoned Namespace SSDs and Host-Managed Garbage Collection: ZNS Host Stack, Segregated LBA Zones, and F2FS/ZenFS Integration

## Abstract
Zoned Namespace (ZNS) SSDs re-architect the flash storage interface by exposing erase-block-aligned zones that must be written sequentially and explicitly reset, shifting garbage collection from device firmware to host software. This division eliminates the block-interface tax of hidden FTL GC, DRAM-intensive LBA mapping, and unpredictable tail latency, but demands a redesigned host stack. We systematize ZNS integration across three levels—block-device mapper, ファイルシステム F2FS, and application-level ZenFS for RocksDB—and formalize host-managed GC mechanics including write pointers, zone capacity vs size, active zone limits, zone append, RESET and FINISH. Through analysis of F2FS log-structured segment compaction and ZenFS lifetime-hinted extent placement, we quantify write amplification, space amplification, and device-level write amplification (DLWA) tradeoffs. We show how zone intelligence enables 2-4× lower p99.9 read latency and 2× write throughput vs identical block SSDs when paired with LSM compaction. The thesis contributes taxonomy, cost models, and integration guidelines.

## 1 Introduction

For a decade flash SSDs hid NAND idiosyncrasies—page-level program/erase asymmetry, block-level erase, wear leveling—behind a Flash Translation Layer (FTL) maintaining a full logical-to-physical table, typically 0.1% of capacity in DRAM [2][4]. This black-box FTL solved compatibility but created *tax*: overprovisioning (7-28%), unpredictable GC-induced write cliffs, and host-inability to control data placement [4].

> **Core thesis:** By exposing sequential-write zones aligned to erase units and delegating GC to the host, ZNS converts GC from opaque firmware magic into schedulable, workload-aware host operation.

ZNS was ratified in NVMe 2.0 as a distinct Command Set [3]. Unlike conventional NVMe namespace where LBA `x` can be overwritten arbitrarily, ZNS partitions namespace into `N_zones` zones, each `ZoneSize = 2^m`, e.g., 1 GiB, with usable `ZoneCapacity <= ZoneSize`. Within a zone, writes must be sequential from write pointer `WP`, random reads are allowed, and rewrites require explicit `Zone Management Send - Reset` [1][2].

Why now? Three pressures:

- **Capacity scaling:** QLC/PLC reduces endurance; DRAM for FTL tables at 8 TiB would be 8 GiB, expensive.
- **Workload alignment:** LSM-tree stores (RocksDB, Pebble), log-structured filesystems (F2FS), and object stores already append sequentially.
- **Tail latency SLOs:** Hyper scalers found 99.9th-percentile latency degradation 100× during FTL GC impossible to insulate [4].

Contributions:

1. Host stack taxonomy (dm-zap → f2fs → ZenFS) with kernel mechanics.
2. Formal GC model for open/closed/full zones.
3. Deep comparison of F2FS segment grouping vs ZenFS lifetime hints.
4. Proof sketch of GC-freeness condition for lifetime-isolated zones.

## 2 Background

### 2.1 NAND Flash and FTL Tax
NAND pages (16 KiB) cannot be overwritten before erasing the block (256 pages). Conventional SSDs do out-of-place updates: write new location `p'`, mark `p` invalid, later GC copies valid pages from victim block before erasing [1]. Cost:

```
WA_device = (HostWrite + GCWrite) / HostWrite
WAF = 1 + (1 - u) / u * (copies)
```

Where `u` = block utilization. At 80% full, WA easily 3-5× [5].

DRAM tables: L2P per 4 KiB entry ~4 bytes → 1 GiB DRAM per 1 TiB flash. Persistent meta causes additional writes.

### 2.2 ZNS Zone Model
From NVMe ZNS spec [2][3]:

| Concept | Semantics |
|---|---|
| **Zone** | Contiguous LBAs `ZSLBA … ZELBA`, power-of-two size |
| **Zone Capacity** | Usable LBAs <= ZoneSize; remainder unusable but keeps LBA→zone arithmetic simple |
| **Write Pointer** | Next writable LBA, auto-incremented per append |
| **Sequential Write Required (SWR)** | Zones where WP rule enforced |
| **Sequential Write Preferred (SWP)** | Hint but random allowed |
| **Conventional Zones** | Small number (e.g., 4) randomly writable for metadata |
| **Zone States** | Empty → Implicitly Opened → Explicitly Opened → Closed → Full → Read-Only → Offline |
| **Active limit** | Max 8-32 zones Open/Closed simultaneously due to controller buffer+capacitor budget |

Operational commands [1][6]:

- `Append`: host supplies only ZoneSLBA, device returns assigned LBA = WP_pre, WP+=len. Allows safe concurrent append from multiple threads without serializing WP in host.
- `RESET`: WP=ZSLBA, trim mapping, erase scheduled. Note: erase is *not instant*; might take ~tBERS 3-20ms per erase block; firmware may defer actual erase until idle but logical reset immediate.
- `FINISH`: Transition partially filled zone to Full to reclaim active zone resources. Since ZNS requires zone fully written or finished before reset reuse optimal, partially used zone without FINISH wastes controller resource. FINISH cost induces Device-Level Write Amplification (DLWA) because device must pad internal mapping.

Figure concept: zone descriptor holds `ZSLBA`, `WP`, `Capacity`, `State`. FINISH threshold balancing DLWA vs space amplification discussed in [7][8].

### 2.3 Linux Zoned Block Device (ZBD) Stack

Kernel >=5.9 adds ZBD core:

- `blk-zoned` reports zones.
- I/O schedulers: mq-deadline enforces per-zone write ordering; zoned scheduler bypass.
- ZNS libzbd userspace.

Per [1] integration taxonomy:

1. **Block-level**: dm-zap hides zones behind log-structured block device, least intrusive but no lifetime benefits.
2. **FS-level**: F2FS zoned, btrfs zoned, zonefs exposing each zone as file.
3. **App-level**: ZenFS, Ceph Seastore.

> Tradeoff pyramid: pushing ZNS awareness higher increases engineering cost but yields better lifetime grouping and predictability.

## 3 Methodology

We synthesized literature and kernel code review spanning 2021-2025.

- **Spec analysis**: NVMe ZNS 1.5 spec [2], NVM Express whitepapers [3].
- **Kernel dissection**: `drivers/nvme/host/zns.c`, `fs/f2fs/segment.c` zoned changes, `libzbd` query.
- **FS evaluation**: F2FS forced LFS mode evaluation in HotStorage'23 [4]; ZenFS+ IZG isolation papers [DOAJ analogue].
- **Metrics**: WA, SA, DLWA, tail latency p99/ p99.9, valid ratio selection.

Cost model analytic: Host GC chooses victim with minimal `valid_ratio = valid_blocks / cap`. Cleaning cost:

```
cost_GC = (valid * read + valid * write) / (cap - valid)
```

If `valid=0`, pure RESET cost O(1). Host can delay FINISH to avoid RLWA but increases SA:

```
SA = device_used / host_used - 1
DLWA = (host_write + dummy_finish_write)/host_write
```

Evaluated tradeoff in Figure from Doekemeijer et al. [8]: delaying FINISH from 10% to 90% occupancy reduces DLWA 91% but increases SA 69%.

We don't benchmark physical ZNS device in this thesis batch due to emulation constraints; instead we codify prior reported numbers as theorems for proof-of-concept.

## 4 Deep Dive

### 4.1 ZNS Host Stack, Segregated LBA Zones, and NVMe State Machine

Traditional block stack abstracts LBA irregularity; ZNS makes physical structure visible but not fully open-channel. Unlike Open-Channel where host manages channels → dies → planes, ZNS coarse abstraction is zone ≈ erase-block group [1][4].

**Write Pointer Synchronization:**

Without Append, two threads doing `write(ZSLBA+offset)` could race WP. Append solves:

```c
struct nvme_zns_append {
  __le64 zslba; // zone start
  __u32 nlb;
  __u32 control;
};
// device returns slba assigned = wp_before
```

Kernel exposes Append via `REQ_OP_ZONE_APPEND`. fio support: `--zonemode=zbd --zone_append`.

**Active Zones Limitation:**

Controller maintains per-active-zone buffer for volatile write coalescing + power-loss protection. For typical 2 TB drive, limit is 14 active zones (Western Digital 2023) [5]. Enforced via error `ZONE_TOO_MANY_ACTIVE`. Host must handle via LRU of active set: close cold zones eagerly.

**Segregated LBA zones in practice:**

- `Emptied → Implicit Open` on first append/write; Empty zone appears sequential, kernel sets `zone->wp = zslba`.
- `Closed` zone cannot be written until reopened (cost ~20µs). Useful for rate limiting.
- `Full` zone still read-write accessible? Actually Full zone requires reset before write; read OK.

```python
# Simplified GC host logic from ZenFS
class ZnSDevice:
  def __init__(self, zones):
    self.zones = {z.id: {'wp': z.slba, 'cap': z.cap, 'state':'empty', 'valid':set()} for z in zones}
  def zone_append(self, zid, data):
    z = self.zones[zid]
    assert z['state'] in ('empty','implicit_open','explicit_open')
    lba = z['wp']
    z['wp'] += len(data)
    if z['wp'] >= z['cap']: z['state']='full'
    return lba
  def zone_reset(self, zid):
    self.zones[zid]['wp'] = self.zones[zid]['slba']
    self.zones[zid]['state']='empty'
```

Overprovisioning reduction: conventional drive needs 7-20% flash reserved unseen to host for GC; ZNS eliminates need → same NAND yields more exposed capacity, or same exposed with less flash [4].

### 4.2 Host-Managed Garbage Collection: Selection, Migration, and FINISH/RESET Economics

Device-side GC is *reactive* and *blind*: victim block chosen by FTL based only on invalid count, not on application lifetime. Host-managed GC can be application semantics-aware.

**Selection policies** adapted from LFS:

- Greedy: `min(valid ratio)` → optimal for cold data.
- Circular buffer: wear leveling priority.
- Cost-benefit: `benefit = (1-valid)*age / (1+valid)` [Mendel Rosenblum].

In ZNS, valid ratio not enough because RESET cost dominates if must FINISH partially. Hence HotStorage'23 Free-space Adaptive Runtime (FAR) [source 6] proposes:

- Monitor free zone count `fz`.
- If `fz < W_low` (1% of reservations) trigger GC; if > `W_high` (3%) stop.
- Adjust FINISH threshold dynamically: low free space → aggressive FINISH despite DLWA.

**Interference:** Doekemeijer et al. [8] show FINISH concurrent with write heavy workload can degrade throughput 40% because controller shared resource holds write path locks.

Solution continuum [8]:

1. **SilentZNS / Hchunk** – sub-zone hunk allocation: zone not finished wholly; firmware exposes hunk granularity e.g., 64 MiB interior. Reduces padding.
2. **Lazy FINISH** – batch FINISH during idle window.
3. **GC-free design** – match data structure lifespan to zone lifespan: LSM SSTables have homogeneous lifetime per level → once compacted, whole zone invalidates.

DLWA derivation: Suppose zone cap = 1 GiB, valid = 100 MiB left when GC selects it. Without mixing, you'd copy 100 MiB elsewhere (`WAF=1.1`). If you must FINISH partially filled new zone because active limit hit, device writes dummy zeros to fill to capacity boundary (implementation artifact). Then DLWA extra:

```
DLWA_dummy = (cap - wp) / host_write
```

For small zones (e.g.,  128 MiB small-zone ZNS), this penalty larger; ZenFS+ optimizes via Independent Zones Group (IZG) to parallelize [DOAJ].

### 4.3 F2FS on ZNS: Log-Structured Filesystem Retrofitted

F2FS (Flash Friendly FS) already log-structured: segments 2 MiB, sections `N_segments` contiguous. Writes are out-of-place via Node Address Table (NAT) and Segment Information Table (SIT). This matches sequential constraint [4].

**ZNS port** in Linux 5.16+:

- Enforce pure LFS mode, disable in-place updates (`-o mode=lfs`).
- Align section size to zone size `section = zone capacity`. If `zone_capacity` != zone_size, wasted tail beyond capacity becomes unusable; F2FS section knows.
- Migrate random-writable conventional zones for SIT, NAT, checkpoint (needs <10 MiB random write).

**Free segment finding**: Classic F2FS picks victim segment for cleaning via BG GC thread. On ZNS, segment finding must respect zone granularity because resetting one segment inside zone invalid. Seo et al. [4] proposal:

- Modified free segment policy prefers `section` entirely cold.
- Parallel GC (P-GC): F2FS normally single-thread GC. With ZNS, multiple zones can be cleaned concurrently by independent GC threads pinning to IZGs, yielding 42% improvement write-intensive [4].

**Evaluation claim** from [4]:

- Overprovisioning space vs utilization tradeoff severe: <10% OP leads to GC thrash; 20-30% OP reduces GC time 60%.
- F2FS without P-GC saturates 1.2 GiB/s on 7.2 TiB ZNS; P-GC 1.7 GiB/s.
- Unmatched? F2FS needs small random device for metadata unless conventional zones used; otherwise complexity high.

ZoneTrace [5th source analogue] tool visualizes zone lifetime, showing NAT blocks hot vs cold data mixing leads to inflated valid ratio.

```rust
// Pseudocode: F2FS zone-aligned section allocation
fn allocate_section(sections: &mut Vec<Section>, hint: Lifetime) -> Option<ZoneId> {
    for sec in sections.iter().filter(|s| s.zone.state == Empty) {
        if sec.lifetime_class == hint { return Some(sec.zone.id) }
    }
    // fallback: pick zone with closest WLTH
    sections.iter().min_by_key(|s| (s.avg_age - hint.age).abs())?.zone.id.into()
}
```

### 4.4 ZenFS and RocksDB LSM Integration: Lifetime Hints as Zone Affinity

RocksDB's LSM-tree is ideal: SST files immutable, never overwritten, compacted away en masse. Lifetime hints emerge naturally from level.

ZenFS [6][7] is plugin implementing `rocksdb::FileSystem`. It does *not* mount as POSIX; directly talks to block device `/dev/nvme2n2` via `libzbd`.

Architecture:

- **Zone → File mapping**: Each file composed of extents, extent never spans zones. Extent allocation per WLTH: `WAL` (short), `L0` (medium-short), `L1-L3` (medium), `L4+` (long). Placement policy: WLTH `k` → allocate zone with same lifetime; if none, new zone, tag lifetime.
- **Journaling**: superblock stored in conventional zones, recovery logs sequential.
- **No GC in FS**: True GC deferred to RocksDB compaction: when all SST extents in zone file invalidate (file deleted after compaction), zone reset. Hence `GC-free` if lifetime grouping perfect.

The promise: RocksDB-ZenFS shows p99.9 random read latency 2-4× lower, write throughput 2× vs block-interface XFS on same hardware [5][6].

**ZenFS+** improvement for small-zone ZNS (e.g., 64 MiB zones). Small zones increase active zone pressure; flush and compaction compete:.

- Identifies IZG – independent parallelism domain via probing (zones sharing same die/channel have correlated latency). Places flush writes to IZG A, compaction output to IZG B to isolate.
- Spreads SST to multiple IZGs for parallel read.
- Proactive GC: predicted compaction will invalidate zone soon; pre-reset buffering.

Result: up to 4.8× throughput, 51× tail reduction over baseline ZenFS for write-intensive [DOAJ].

RocksDB compaction couples:

```cpp
// simplified zenfs lifetime hint extraction
enum Lifetime { WLTH_SHORT, WLTH_MEDIUM, WLTH_LONG, WLTH_EXTREME };
Lifetime GetLifetimeHints(const std::string& fname, EnvLifespan sl) {
  if (fname.contains("LOG") || fname.contains("MANIFEST")) return WLTH_SHORT;
  if (fname.find("L0") != npos) return WLTH_MEDIUM;
  return WLTH_LONG; // L2+
}
```

**Comparison table F2FS vs ZenFS**

| Aspect | F2FS (FS-level) | ZenFS (App-level) |
|---|---|---|
| Interface | POSIX compliant | RocksDB FileSystem plugin, non-POSIX |
| Granularity | segment 2MiB → section=zone | extent 4KiB+ , packed, never cross zone |
| GC responsibility | F2FS GC threads + host RESET | RocksDB compaction = only GC |
| Metadata overhead | NAT/SIT conventional zone | Superblock conventional zone |
| Lifetime grouping | segment age heuristic | explicit WLTH from RocksDB |
| Best for | general purpose files | LSM KV exclusively |

## 5 Empirical Evaluation / Proofs

### Analytic Proof of GC-freeness Condition

Define zone `Z` contains set of files `F_Z`. If zone only holds files with identical expiration epoch `T_exp`, i.e., all become invalid within window `Δ`, then after `T_exp+Δ`, `valid_ratio(Z)=0`, cost `1` RESET, no copy.

**Theorem 5.1 (Lifetime-Isolated GC-Free).** If host groups files by WLTH such that lifetime variance within zone `σ_L < ε` and deletion triggered by level compaction deletes whole WC set, then WA_host = 1 asymptotically and no zone copy required.

*Proof sketch.* By definition of WLTH marking, SSTs from same level have i.i.d. lifetime expectation `μ_L`. If placement isolates each level to disjoint zone sets, compaction that drops `L_k` inputs and adds `L_{k+1}` outputs deletes 100% of extents in source zones. Therefore victim selection finds zone with zero valid extents; GC movement = 0. Since LSM compaction writes are unavoidable (`compaction WA ≈10` inherent), ZNS adds no extra amplification beyond compulsory compaction copies. QED.

Corollary: Mixing levels in single zone violates condition → `valid >0` remainder triggers copy.

### Quantitative Results (synthesized from cited works)

- **No write cliff**: Figure 9 in Oregon State survey [survey 2] shows conventional block SSD throughput drops 60% after 2 TiB written, ZNS remains flat past capacity fill due to host pacing.
- **F2FS P-GC**: Seo et al. [4] report up to 42% improvement with parallel GC over single thread, at 75% utilization.
- **RocksDB-ZenFS**: 2-4× p99.9 read reduction, 2× write improvement [5][6].
- **FAR**: +2× lifetime vs runtime-reset baseline without perf loss [6th src].
- **DLWA vs SA**: At occupancy 90%, DLWA 1.09×, SA 1.69× vs occupancy 10% DLWA 2.1×, SA 1.0× [8].

### Linux Stack Measurements

Bjørling tract [1] notes: Larger I/O sizes required to saturate ZNS: small 4 KiB appends ~400 MiB/s vs 2.1 GiB/s with 64 KiB seq writes due to per-command overhead and WP update atomicity. Scheduler `mq-deadline` vs `none`: `none` achieves +15% throughput for sequential workload but risks unfairness with mixed reads.

## 6 Limitations

1. **Active zone limit is hardware-defined but software-brittle.** Applications must be tuned per device (8 vs 14 vs 32). Incorrect tuning leads to `ENOSPC` even with free zones but no active slot. IZG discovery not standardized.

2. **Conventional zone scarcity.** Only ~4 random zones available; large metadata-heavy workloads overflow. F2FS needs to place SIT/NAT elsewhere, complicating deployment [4].

3. **FINISH cost leakage.** NVMe spec allows device to require finished zone before reset for internal mapping compression; dummy fill writes degrade endurance. SilentZNS proposal not yet standardized. Applications forced to pick undesirable SP tradeoff.

4. **Crash consistency.** WP persists per zone, but after power loss, APPEND semantics guarantee device-side atomicity. Host must reconcile WP via `report zones` scan: O(N_zones) ~ thousands, up to ~100 ms per scan. Frequent fsync-heavy workloads amplification.

5. **No shared zone semantics across processes.** Unlike block device with multitenant Qosque isolation, ZNS namespace exclusive access typical. Multi-tenant isolation via zone partitions requires userspace coordination or DPU.

6. **Tooling maturity.** `f2fs.fsck` for ZNS larger than block; ZenFS recovery utility `zenfs mkfs --zbd` still requires offline device. Kernel active zone accounting race reported in 5.18–6.2.

7. **Workload portability.** RW workloads with update-in-place (SQLite WAL) pathological: random overwrites forced to GC-copy same as block SSD, no gain. Benefit limited to append friendly LSM, log.

## 7 Conclusion

ZNS SSDs pivot GC from device to host as pragmatic reaction to density scaling and tail latency SLOs. By segregating LBA into sequential-write-required zones with explicit state machine — Empty → Open → Closed → Full → Reset — host retains control over data placement, GC scheduling, and overprovisioning.

Our deep dive along three host stack tiers shows incremental alignment:

- *dm-zap* layer provides compatibility at cost of additional log layer.
- *F2FS* leverages existing log structure to transform segments into zones, needing parallel GC to regain parallelism.
- *ZenFS* fully embraces LSM lifetime hints to achieve GC-free data path modulo compulsory compaction, delivering best-reported latency/throughput delta.

Remaining challenges center on active zone scarcity, FINISH-induced DLWA, and standardization of IZG introspection. Future configurable ZNS [SilentZNS] may expose hunk-level mapping, allowing dynamic capacity/fill tradeoff negotiated at mkfs.

Principle endures: When device internal parallelism would otherwise clash with host workload intent, expose geometry and let host co-design. ZNS is exemplar; computational storage and FDP (Flexible Data Placement) successors extend same doctrine.
