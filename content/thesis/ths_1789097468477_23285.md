# io_uring: Asynchronous I/O Architecture in the Linux Kernel

## Abstract

io_uring is the completion-queue based asynchronous I/O interface introduced in Linux 5.1 that replaced the per-syscall model of POSIX AIO, libaio, and readiness-based `epoll` with two lock-free shared-memory rings — a submission queue (SQ) and a completion queue (CQ) — mapped into both user and kernel address space. This thesis analyzes the ring protocol in detail: 64-byte submission queue entries, 16-byte completion queue entries, head/tail index management with acquire-release memory ordering, fixed buffers, fixed files, registered personalities, and the per-opcode semantics of `IORING_OP_*`. It covers the zero-copy I/O path enabled by buffer pre-registration, the `IORING_SETUP_SQPOLL` and `IORING_SETUP_IOPOLL` modes that eliminate syscalls from the data path entirely, multishot operation semantics, and a rigorous benchmarking methodology for comparing io_uring against epoll and libaio. Finally, it examines the security surface of the io_uring syscalls — from buffer-registration overflows to syscall-evading malware — and the mitigations introduced in recent kernels, including `io_uring_disabled`, per-task restrictions, and seccomp integration.

## 1 Introduction

For decades, asynchronous I/O on Linux was a fractured landscape. POSIX AIO (`aio_read`/`aio_write`) scaled poorly because of its signal-driven completion model; libaio fixed part of the problem but supported only a narrow operation set (essentially O_DIRECT reads and writes) and still required one syscall per submission and one per harvest; `epoll` addressed readiness for sockets but could not make file or disk I/O asynchronous at all. Every one of these interfaces preserved the fundamental design of UNIX I/O: each request is a system call, and the kernel/user boundary is crossed twice per operation — once to submit, once to observe the result.

io_uring, designed primarily by Jens Axboe and merged in Linux 5.1 (2019), breaks with this tradition [1]. It is a *completion-based* interface rather than a *readiness-based* one: instead of polling file descriptors for readiness, the application posts operation descriptors into a shared ring and later harvests completion descriptors from a second shared ring. The rings are mapped into userspace with `mmap`, so submission and completion require **no copying and, in the common case, no syscalls at all**. The result is an interface that supports reads, writes, `sendmsg`/`recvmsg`, `accept`, `connect`, `openat`, `statx`, `timeout`, `poll`, `splice`, `sendfile`, `futex` waits, network zero-copy sends, and dozens more operations through a single submission mechanism, with latency and throughput that match or exceed hand-tuned epoll event loops [2].

This thesis examines io_uring from first principles: the ring protocol and its memory-ordering contract, the registration facilities (fixed buffers, fixed files, personalities) that make the fast path possible, the semantics of the `IORING_OP_*` operation set, the zero-copy paths, SQPOLL/IOPOLL syscall-free operation, multishot operations, benchmarking methodology, and the security surface that has made io_uring one of the most scrutinized subsystems in the kernel.

## 2 Background

### 2.1 The cost of a system call

A single `read(2)` on Linux costs on the order of 100–200 ns in syscall overhead alone on modern hardware, plus the work itself. For workloads issuing millions of IOPS — NVMe devices comfortably exceed 5M IOPS per device — syscall overhead becomes the dominant cost, and context-switching into the kernel serializes through per-task structures. Batching syscalls (e.g., `io_submit` from libaio, or `recvmmsg`) helps, but each batch is still a crossing of the privilege boundary with full argument validation.

io_uring amortizes this cost to near zero. In the standard configuration, an application submits requests by writing into shared memory and invokes `io_uring_enter` once per batch — or, with `IORING_SETUP_SQPOLL`, never invokes a syscall for submission at all; a kernel thread continuously polls the submission ring.

### 2.2 Ring buffers as the communication primitive

The name *io_uring* comes from the ring buffers that are the interface's central data structure. `io_uring_setup` returns a file descriptor and fills in `struct io_uring_params` with offsets that the application uses to `mmap` three regions: the SQ ring metadata plus the SQE array, and the CQ ring metadata plus the CQE array [3][4]. The rings are power-of-two circular buffers. The producer (application for SQ, kernel for CQ) advances the *tail*; the consumer advances the *head*. Consistency across the user/kernel boundary is maintained not with locks but with a strict memory-ordering protocol based on store-release/load-acquire semantics [5].

### 2.3 Evolution of the interface

Since 5.1, io_uring has grown aggressively: fixed files and buffers (5.1–5.3), `IORING_OP_ACCEPT`/`CONNECT`/`SEND`/`RECV` (5.5), provided buffers and buffer selection (5.7), `IORING_OP_RECV_MULTISHOT` (5.13), `sendmsg` zerocopy (5.18+), `IORING_OP_FUTEX_WAIT` (6.0), direct-task execution (`IORING_SETUP_TASKRUN`, 6.9), and per-task restrictions (7.0). Each addition preserved the same ring protocol, which is why the memory-ordering rules are the verifiable core of any io_uring client.

## 3 Methodology

This analysis is built from three sources. First, the authoritative interface documentation: the `io_uring(7)`, `io_uring_setup(2)`, and `io_uring_enter(2)` man pages [1][3][4]. Second, the kernel implementation in `io_uring/io_uring.c`, `io_uring/opdef.c`, and related files (request lifecycle, worker-thread fallback, CQ overflow handling), corroborated by detailed request-lifecycle documentation [2]. Third, published security analyses of the io_uring attack surface, including CVE records and vendor responses [6][7]. Performance claims are framed by standard methodology (see §5) rather than by repeating any single vendor benchmark: all comparisons use identical hardware, O_DIRECT block devices, and both syscall-based and SQPOLL configurations.

> **Theorem (Ring consistency):** Under the io_uring ring protocol, the consumer never observes a partially written queue entry, provided the producer issues entries with release ordering on the tail-index store and the consumer issues entries with acquire ordering on the tail-index load.

The protocol is: the producer writes the entry payload first, executes a store-release of the new tail index, and the consumer executes a load-acquire of the tail index before reading any entry payload. On x86/TSO the hardware provides sufficient ordering for most of this, but the protocol is specified for all architectures and must be honored explicitly (via `atomic_store_explicit(..., memory_order_release)` / `memory_order_acquire`) on weakly-ordered ones such as ARM.

## 4 Deep Dive

### 4.1 The shared-memory ring protocol

Three memory regions are mapped after `io_uring_setup`:

| Region | Element size | Producer | Consumer |
|---|---|---|---|
| SQE array | 64 bytes (`struct io_uring_sqe`) | application | kernel |
| SQ ring metadata | `struct io_sqring_offsets` + index array | application | kernel |
| CQ ring metadata + CQE array | 16 bytes (`struct io_uring_cqe`) | kernel | application |

The SQ is *indirect*: the application writes an SQE into the SQE array at index `tail & mask`, then writes that array index into the SQ ring's index array at `tail & ring_mask`, then advances the tail with release ordering. The kernel reads the index array, then the SQE. The CQ is *direct*: the kernel writes the 16-byte CQE (`user_data`, `res`, `flags`) at `tail & mask` and advances the tail; the application advances the head when it has consumed entries.

Flow control is explicit:

- **SQ full:** the kernel can only consume up to the tail it has observed; if `tail - head == ring_entries`, the application must wait or grow the ring.
- **CQ overflow:** if the CQ ring fills because the application is not draining completions, the kernel cannot post new CQEs. Rather than losing them, the kernel sets `IORING_SQ_CQ_OVERFLOW` in the CQ ring flags and queues the overflowed completions in a kernel-side list, replaying them once the application drains the ring [2]. Applications *must* check this flag after harvesting, or completions are silently delayed — a classic production failure mode.
- **SQPOLL wakeup:** with `IORING_SETUP_SQPOLL`, the kernel sets `IORING_SQ_NEED_WAKEUP` in the SQ ring flags when its poll thread has gone idle; the application must then call `io_uring_enter` with `IORING_ENTER_SQ_WAKEUP`. The flags word must be read with acquire (or at least relaxed-then-checked) semantics, or the application and kernel can disagree about wakeup state [4].

`struct io_uring_sqe` (64 bytes) carries the opcode, flags, file descriptor or fixed-file index, buffer address or fixed-buffer index, length, offset, `user_data` (an opaque 64-bit cookie echoed back in the CQE), personality, and per-opcode unions. The `user_data` field is the application's only reliable correlator between submission and completion.

### 4.2 Registered resources: fixed buffers, fixed files, personalities

The dominant cost of fast-path I/O is not the syscall — io_uring already removed that — but per-request validation: pinning user pages (`get_user_pages`), looking up `struct file` from an fd, and copying the SQE itself. Registration moves all of this to setup time:

- **Fixed buffers** (`IORING_REGISTER_BUFFERS`): the application registers an array of `struct iovec`; the kernel pins the pages once and stores them in a table. Requests then use `IORING_OP_READ_FIXED`/`WRITE_FIXED` with a buffer *index* instead of an address. This eliminates page pinning from the I/O path and is effectively mandatory for the zero-copy and IOPOLL paths.
- **Fixed files** (`IORING_REGISTER_FILES`): file descriptors are registered into a table; requests reference them by index with the `IOSQE_FIXED_FILE` flag, skipping the fd→file lookup and its reference counting. Historically, SQPOLL *required* fixed files before kernel 5.11 (`IORING_FEAT_SQPOLL_NONFIXED` marks the relaxation) [4].
- **Provided buffers** (`IORING_OP_PROVIDE_BUFFERS` + `IOSQE_BUFFER_SELECT`): instead of choosing the destination buffer at submit time, the application provides a pool of buffers grouped by an ID; the kernel selects one per completion and reports the chosen buffer's ID in the CQE flags. This is the foundation of multishot receive (see §4.5).
- **Personalities** (`IORING_REGISTER_PERSONALITY`): a registered credential set (`struct cred`) applied to requests via `IOSQE_ASYNC` semantics — originally designed for io_uring's use by network filesystems and containers that need requests executed under different user credentials than the submitter.

Together, registration converts per-request dynamic validation into per-ring static tables — the key enabler of the sub-microsecond submission path.

### 4.3 IORING_OP semantics and the request lifecycle

Each opcode has precise semantics. A request's lifecycle in the kernel is approximately [2]:

```c
/* io_uring/io_uring.c — simplified submit path */
SYSCALL_DEFINE6(io_uring_enter, unsigned int, fd, u32, to_submit,
                u32, min_complete, u32, flags, ...)
{
    ctx = /* ring_fd -> io_ring_ctx */;
    if (to_submit)
        ret = io_submit_sqes(ctx, to_submit);   /* consume SQ */
    if (flags & IORING_ENTER_GETEVENTS)
        ret = io_cqring_wait(ctx, min_complete, ...); /* harvest CQ */
    return ret;
}
```

`io_submit_sqes` iterates the newly submitted SQEs. For each: `io_get_sqe` advances the kernel's view of the SQ head, `io_alloc_req` obtains a `struct io_kiocb` from the slab cache, `io_init_req` copies SQE fields into the request, and `io_queue_sqe` dispatches it. `io_issue_sqe` attempts the operation **inline, non-blocking** (`IO_URING_F_NONBLOCK`, i.e., `IOCB_NOWAIT` semantics): if the operation completes immediately, its result is posted to the CQ at once. If it would block (returns `-EAGAIN`), the request is punted to the **io-wq** worker thread pool, which executes it asynchronously and posts the completion later [2].

Key opcode semantics worth stating precisely:

- `IORING_OP_READV/WRITEV` vs `READ/WRITE`: the vectored forms take an iovec array; the non-vectored forms take a single address/length.
- `IORING_OP_READ_FIXED/WRITE_FIXED`: operate on registered buffers by index — no page pinning, required for `IORING_SETUP_IOPOLL`.
- `IORING_OP_POLL_ADD`: arms a poll on an fd; unlike `epoll`, the completion is a one-shot event posted to the CQ.
- `IORING_OP_TIMEOUT` / `LINK_TIMEOUT`: absolute or relative timers, with link semantics described below.
- `IORING_OP_ASYNC_CANCEL`: cancels an in-flight request by `user_data`.
- `IORING_OP_SEND_ZC` / `RECV_ZC` (zerocopy network, 5.18+): transmit path avoids copying the payload; completion semantics are two-stage (`IORING_CQE_F_MORE`).
- Linked requests: `IOSQE_IO_LINK` chains SQEs so that request *n+1* is not issued until *n* completes; `IOSQE_IO_HARDLINK` additionally propagates failure. A `LINK_TIMEOUT` linked after a request fires only if the parent has not completed — the standard pattern for "operation with deadline."
- Drain: `IOSQE_IO_DRAIN` serializes the request against all previously submitted requests, providing a barrier for ordering-sensitive sequences.

The CQ entry is minimal by design: `{ __u64 user_data; __s32 res; __u32 flags; }`. `res` carries the result (bytes transferred, or negative errno); `flags` carries modifiers such as `IORING_CQE_F_MORE` (more completions coming, e.g., multishot or zerocopy) and `IORING_CQE_F_BUFFER` (buffer ID in the upper bits, for buffer selection).

### 4.4 Zero-copy paths and SQPOLL

"Zero-copy" in io_uring takes two distinct forms:

1. **Registered-buffer I/O** avoids the kernel's per-request copy of user pages into the page cache path's bounce handling and, critically, avoids `get_user_pages` pinning per request. The pages are pinned once at registration; DMA proceeds directly between the device and the pinned pages. For `O_DIRECT` block I/O this is a true zero-copy data path from the application's perspective: no intermediate kernel buffer is involved.
2. **Network zerocopy** (`IORING_OP_SEND_ZC`, and `MSG_ZEROCOPY`-style sendmsg): the payload pages are pinned and handed to the NIC via the socket's zerocopy machinery; the kernel notifies completion in two stages — first that the payload was queued to the device (`IORING_CQE_F_MORE` set), then that the pages may be reused. Misuse (reusing the buffer after the first but before the second completion) is a data-corruption bug, not merely a performance issue.

`IORING_SETUP_SQPOLL` removes syscalls from the submit path: a kernel thread (optionally pinned with `IORING_SETUP_SQ_AFF` and `sq_thread_cpu`) polls the SQ ring, submitting entries as they appear. Combined with `IORING_SETUP_IOPOLL` (kernel-side completion polling for O_DIRECT block I/O, no interrupts), the entire I/O path becomes syscall-free: the application writes SQEs and reads CQEs, and all kernel interaction happens through shared memory [5]. The costs are a permanently occupied CPU thread and the `IORING_SQ_NEED_WAKEUP` handshake; SQPOLL historically required `CAP_SYS_NICE` for unprivileged use (relaxed in 5.11+) [4].

### 4.5 Multishot operations

Classical io_uring is one-shot: one SQE yields exactly one CQE. For high-frequency event sources (accepting connections, receiving datagrams), re-arming after every completion doubles submission traffic. **Multishot** operations break this symmetry: a single SQE remains armed and posts one CQE per event until explicitly canceled:

- `IORING_OP_ACCEPT_MULTISHOT` (5.13+): each incoming connection posts a CQE.
- `IORING_OP_RECV_MULTISHOT` (5.13+): each received datagram/message posts a CQE, combined with provided-buffer selection so each datagram lands in a fresh kernel-chosen buffer.
- `IORING_OP_RECVMSG_MULTISHOT`, `IORING_OP_SEND_ZC` follow the same pattern.

Every CQE except the terminal one carries `IORING_CQE_F_MORE`; the application reaps completions without ever re-submitting. Multishot accept/recv is what lets io_uring-based servers (e.g., experimental HTTP servers, proxies) match epoll-based designs with dramatically less submission overhead, and it composes with buffer selection so the application never manages receive buffers per datagram.

## 5 Empirical Results / Proofs

A credible io_uring benchmark must control the variables that dominate I/O performance. The methodology that the serious published comparisons follow is:

1. **Fix the device and the access pattern.** Use raw NVMe or `O_DIRECT` files; buffered I/O measures the page cache, not the interface. Report queue depth, block size, and read/write mix explicitly — io_uring's advantage grows with queue depth and shrinks for single outstanding requests.
2. **Isolate the interface, not the application.** Compare identical workloads across `pread(2)` loops, libaio `io_submit`, `epoll`+nonblocking, and io_uring in at least three configurations: plain (syscall submit), `IOSQE_FIXED_FILE`+fixed buffers, and SQPOLL (+IOPOLL for block I/O).
3. **Measure both latency and throughput.** Report per-operation latency distributions (p50/p99/p999), not just IOPS: SQPOLL reduces tail latency by removing wakeup jitter, while batch submission primarily raises throughput. Pin threads, disable frequency scaling, and report CPU utilization per MIOP — io_uring's headline wins are often stated in IOPS, but the *efficiency* win (IOPS per core) is the architecturally interesting number.
4. **Account for the completion model honestly.** epoll measures readiness; the subsequent `read`/`write` syscall is part of epoll's true cost and must be included. libaio's `io_getevents` harvest cost must be included symmetrically with io_uring's CQ drain.

Under this methodology, the established qualitative results are: io_uring matches or beats libaio on block I/O at all queue depths while supporting a far wider operation set; against epoll-based networking it wins primarily through batched submission, multishot operations, and zerocopy sends rather than through any single dramatic factor; and SQPOLL+IOPOLL achieves the lowest achievable latency on NVMe at the cost of dedicated polling CPUs [5]. Claims beyond these qualitative statements must be re-measured on the target hardware — storage performance is not portable across devices.

> **Theorem (Submission amortization):** With batched submission of *n* SQEs per `io_uring_enter`, the per-request syscall cost is *O(1/n)*; with SQPOLL it is *O(0)* syscalls in steady state, bounded below only by the shared-memory protocol overhead.

## 6 Limitations

io_uring is not a universal replacement, and its limitations are architectural, not incidental:

- **Linux-only.** There is no portable equivalent; applications needing Windows/macOS/BSD must abstract over io_uring, IOCP, and kqueue anyway.
- **CQ overflow is a correctness hazard, not just a performance one.** An application that submits in bursts and harvests lazily will hit `IORING_SQ_CQ_OVERFLOW`; the kernel-side overflow list is bounded by memory, and a pathological producer can exhaust it [2].
- **IOPOLL is O_DIRECT block I/O only**, requires device/driver polling support (NVMe), and forbids most non-polled opcodes on the ring [3].
- **SQPOLL costs a CPU.** A polling kernel thread per ring (or shared via `IORING_SETUP_ATTACH_WQ`) is justified only when the IOPS density amortizes it; at low rates it is pure waste heat.
- **Buffered file I/O still blocks the issuer.** The fast path (`IOCB_NOWAIT`) punts page-cache misses to io-wq workers; the async model hides this, but throughput on cold cache is worker-pool bound, and `IOSQE_ASYNC` exists precisely to force the worker path when the application knows better.
- **Debuggability.** Requests are data in shared memory, not syscalls; `strace` sees only `io_uring_setup`/`enter`/`register`. Tracing requires io_uring tracepoints (e.g., `io_uring:io_uring_submit_sqe`) via bpftrace or ftrace [2].
- **Security surface.** The shared-memory design and the breadth of the opcode set make io_uring a uniquely large attack surface (see §7's discussion): parsing untrusted SQE content in the kernel, at ring-setup privileges, has produced a long CVE history [6][7].

## 7 Conclusion

io_uring's contribution is architectural: it moved the kernel/user I/O contract from *syscalls carrying operations* to *shared memory carrying operation descriptors*, with syscalls retained only for setup, teardown, and wakeup. The ring protocol — release-ordered tails, acquire-ordered heads, explicit overflow signaling — is simple enough to implement correctly in userspace yet expressive enough to subsume libaio, aio, epoll-driven disk I/O, and large parts of the socket API. Registered buffers, fixed files, and personalities push per-request validation to setup time; multishot operations and zerocopy paths push per-event costs toward zero; SQPOLL and IOPOLL push syscalls out of the steady state entirely.

The price of this power is a security surface proportional to its ambition. Every opcode is a kernel parser for userspace-supplied descriptors, and the CVE record — buffer-registration overflows, fixed-file use-after-free, identity-handling flaws — shows what happens when those parsers are wrong [6]. The kernel community's response (`io_uring_disabled` sysctl, per-task restrictions, seccomp filtering, Android/ChromeOS lockdowns) is converging on a workable model: io_uring as a privileged-by-default facility, available to applications that need it and denied to those that do not [7]. For systems programmers, the lesson is that the fastest I/O interface is the one that does the least per operation — and that "the least" must include the security review.
