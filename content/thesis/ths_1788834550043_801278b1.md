# Composable Sandboxed Extensibility via the WebAssembly Component Model: Canonical ABI Lifting and Lowering, WasmGC Reference Types, and WASI 0.2 Worlds for Virtualized Plugin Architectures

## Abstract

The WebAssembly component model [1] reframes portable code from isolated linear-memory modules into typed, composable components whose interfaces are declared in WIT [2] and whose cross-boundary data movement is governed by a canonical ABI [3]. This thesis argues that the confluence of four mechanisms — WasmGC's nominal struct/array reference types with host-traced garbage collection [4], the canonical ABI's total lift/lower translation between interface types and core values [3], WASI 0.2's capability-oriented worlds [7], and component composition with virtualized adapters [1] — yields the first principled substrate for sandboxed plugin architectures capable of displacing native extensions. We formalize the lift/lower round-trip as a canonical correspondence, derive the flattening cost of representative WIT signatures, prove a noninterference property for virtualized worlds, and compare the dlopen threat model against component-based isolation on instantiation cost, cross-boundary copy overhead, and revocation semantics. We conclude that components achieve native-class extensibility with capability-class safety, at the price of per-call serialization that post-MVP async and shared-memory primitives must amortize.

## 1 Introduction

Every mature platform confronts the same dilemma: users demand extensibility, and extensibility demands executing code the author did not write. The classical answer is the *native extension* — `dlopen`/`dlsym`, DLLs, N-API modules, CPython C extensions. Native extensions are maximally expressive and maximally dangerous: a loaded object inherits the host's address space, its ambient authority over files and sockets, and its fault domain. One null dereference crashes the host; one buffer overflow hands it the host's secrets; and the ABI contract — calling conventions, struct layouts, symbol versions — breaks silently across toolchain upgrades.

Core WebAssembly [6] offered validated, memory-safe bytecode, but its four numeric types forced rich interfaces back onto convention — `i32` pointers and lengths with out-of-band agreements — and composing modules meant *sharing* linear memory, so distrusting plugins could corrupt each other like native code.

This thesis develops the claim that four developments, taken together, close the gap between *sandboxed* and *extensible*: **WasmGC reference types** [4] (nominal `struct`/`array` heap types with engine-traced collection), **interface types and the canonical ABI** [2][3] (total, specified *lifting*/*lowering* between WIT values and core values), **WASI 0.2 worlds** [7] (capability-oriented, versioned import/export contracts), and **component composition with virtualization** [1] (hosts instantiate plugins against per-plugin virtualized views of the same world). Section 2 surveys background, Section 3 our methodology, Section 4 the deep dive, Section 5 analytic results and proofs, Section 6 limitations, and Section 7 the conclusion.

## 2 Background

### 2.1 Core WebAssembly

WebAssembly 1.0 [6] defined portable validated bytecode: a stack machine with structured control flow, a single linear memory, and `i32`/`i64`/`f32`/`f64`. Validation is decidable and linear-time; execution is memory-safe by construction. But a function could import or export only numerics — strings, buffers, and callbacks traveled as integer handles under ad hoc conventions, and every language binding was a bespoke, unverified ABI.

### 2.2 From reference types to WasmGC

The *reference types* proposal [5] added opaque references — `funcref`, `externref` — that cannot be forged from integers, restoring a capability discipline at the type level. The *GC proposal* [4] extends this with user-defined heap types: nominal `struct` and `array` types, the `i31` small-integer type, explicit nullability, and declared subtyping with `ref.test`, `ref.cast`, and `br_on_cast`. Allocation and access are engine operations; reclamation is the host collector's job — in browsers, the same collector managing JavaScript objects [10]. Programmers stop hand-rolling allocators in linear memory and describe object graphs the engine already traces.

### 2.3 Interface types and the component model

The *interface types* proposal was merged with *module linking* into the **component model** [1]. A *component* is a binary layer above core modules: it embeds modules and declares their instantiation, aliasing, and wiring, importing and exporting *interface types* rather than raw core functions. The IDL is **WIT** [2]: records, variants, enums, flags, options, results, tuples, lists, strings, and *resources* — linear handle-typed objects with `own<T>`/`borrow<T>` semantics. A WIT *world* describes a component's complete import/export contract.

### 2.4 The canonical ABI

Because components may be authored in languages with incompatible representations (a Rust `String` is not a C `char*`), the component model defines a **canonical ABI** [3]: one specified mapping between WIT values and core Wasm values. *Lowering* translates a typed value into flat core parameters plus, when it does not fit, a canonical layout in the component's linear memory; *lifting* performs the inverse, including validation (e.g., UTF-8 checks). The ABI specifies `canon lift`/`canon lower`, the guest `realloc` used for host-driven allocation, and `cabi_post_*` cleanup that frees guest-owned buffers after the host copies them out.

### 2.5 WASI 0.2

WASI 0.2 [7] re-expresses the system interface atop the component model: versioned WIT interfaces (`wasi:filesystem`, `wasi:sockets`, `wasi:http`, `wasi:cli`, …) grouped into worlds. It is capability-oriented — a component receives no ambient filesystem or network, only *handles* (resources) to granted directories, sockets, or streams. Denying a capability is a wiring decision, not a code patch.

### 2.6 Existing sandboxed plugin systems

**Extism** [8] is a universal plugin framework: plugins are Wasm modules plus a manifest, hosts embed runtimes (Wasmtime, wazero) via multilingual SDKs. **proxy-wasm** [9] standardizes the ABI between L7 proxies (notably Envoy) and Wasm filters. All three predate or sidestep the component model, defining narrow bespoke ABIs without worlds, resources, or virtualization as first-class concepts.

## 3 Methodology

Our method is analytic and constructive: the component model, WASI 0.2, and WasmGC are *specification artifacts*, so specification exegesis plus mechanizable models is the highest-fidelity way to study them. We (i) reconstruct the canonical ABI's flattening and layout rules from [1][3] and implement a small Python model computing sizes, alignments, and flat-parameter counts, deriving exact per-signature costs; (ii) treat WasmGC's nominal subtyping lattice-theoretically, exhibiting cast/test as a decision procedure in Haskell; (iii) formalize lift/lower as a round-trip correspondence proved by induction on WIT types; (iv) model world virtualization as import rebinding and prove a noninterference property; and (v) compare the native-extension threat model against the component model using the published architectures of [8][9]. Performance claims are *analytic complexity bounds*, never fabricated benchmarks. Every specification claim is cited.

## 4 Deep Dive

### 4.1 WasmGC: nominal struct and array reference types

WasmGC [4] introduces *defined heap types*: nominal `struct` types (fixed field sequences, with packed `i8`/`i16` storage types) and `array` types (homogeneous, dynamically sized). Nominality means `(type $a (struct))` and `(type $b (struct))` are distinct even with identical fields; subtyping is declared with `sub`:

```wat
(type $point (struct (field $x f64) (field $y f64)))
(type $colored-point (sub $point
  (struct (field $x f64) (field $y f64) (field $color i32))))
(type $byte-buf (array (mut i8)))
(func $make (param $x f64) (param $y f64) (result (ref $point))
  (struct.new $point (local.get $x) (local.get $y)))
```

References are *opaque*: no instruction converts an integer to a reference, so a guest cannot forge a pointer to an object it was never given — the type system enforces a capability discipline on the heap. The abstract lattice:

| Abstract heap type | Supertype | Inhabitants |
|---|---|---|
| `any` | — | `eq` hierarchy |
| `eq` | `any` | structs, arrays, `i31` |
| `func` | — | functions |
| `extern` | — | host references |
| `none`, `nofunc`, `noextern` | bottom | uninhabited |

Subtyping is *width* subtyping on structs (subtypes may add fields) and *depth* subtyping only for immutable fields — the classic soundness condition for mutable references. Casts are checked: `ref.test` queries inhabitance, `ref.cast` traps on failure, `br_on_cast` branches on success, enabling type-switch dispatch without linear-memory tag words.

For plugins, the engine now owns object lifetime: the guest allocates with `struct.new`, the collector traces the object, and the host receives a managed handle [10] — no more negotiating buffer ownership in linear memory, the classic source of use-after-free at sandbox boundaries.

> **Theorem (Reference unforgeability).** In a well-typed WasmGC module, every consumed reference was produced by an allocation instruction, a null literal of the appropriate heap type, or a host import. No integer arithmetic can manufacture a reference.
>
> *Proof sketch.* Value types and reference types are disjoint syntactic classes, and no instruction takes an integer operand to a reference result. Induction on the typing derivation. ∎

This is the bedrock under the component model's resource handles: an `own<T>` lowered to `i32` is unforgeable *by ABI convention*, but a GC reference is unforgeable *by typing*.

### 4.2 Interface types and the canonical ABI: lifting and lowering

The canonical ABI [3] answers: given a WIT signature, what core signature implements it, and how do values move between levels? **Flattening** maps WIT parameters to flat core types — scalars to themselves, small records field-wise, strings/lists/large aggregates to `(ptr, len)` pairs into linear memory. **Lowering** converts interface arguments to flat values (copying aggregates via the guest's `realloc`); **lifting** converts back, validating encodings. When a guest-allocated buffer reaches the host, the host copies what it needs and calls the guest's `cabi_post_*`, which frees the guest allocation — ownership transfer by specified protocol, not handshake.

Layout rules are fully specified: every WIT type has a structural size and alignment. A Python model of the core rules:

```python
def size_align(t):
    """(size, align) for a WIT type per the canonical ABI."""
    scalars = {"u8": (1,1), "u16": (2,2), "u32": (4,4), "u64": (8,8),
               "f32": (4,4), "f64": (8,8), "char": (4,4), "bool": (1,1)}
    tag = t["tag"]
    if tag == "scalar":
        return scalars[t["name"]]
    if tag in ("string", "list"):
        return (8, 4)  # (ptr: i32, len: i32)
    if tag == "record":
        off, mx = 0, 1
        for f in t["fields"]:
            s, a = size_align(f)
            off = (off + a - 1) // a * a + s
            mx = max(mx, a)
        return ((off + mx - 1) // mx * mx, mx)
    if tag == "variant":
        ds, da = (1, 1)  # discriminant
        ps, pa = max((size_align(c) for c in t["cases"]), default=(0, 1))
        total = (ds + pa - 1) // pa * pa + ps
        return ((total + da - 1) // da * da, max(da, pa))
```

*Resources* lower to `i32` handles indexing a per-instance table managed by the `resource.new`/`resource.drop`/`resource.rep` built-ins. A WASI 0.2 file descriptor is thus, at the ABI level, an unforgeable integer only because the *table* — not the guest — maps handles to representations. > **Theorem (Canonical round-trip).** Let `v` be a first-order WIT value (no resources) and `lower`/`lift` the canonical translations for its type. If the guest `realloc` is total, `lift(lower(v))` is canonically equal to `v`.
>
> *Proof sketch.* Induction on the WIT type. Scalars are identities on flat slots. Records write/read each field at specified offsets; padding is never read. Lists and strings copy the sequence into a fresh `(ptr, len)` region and copy it back with encoding validation. Variants round-trip via discriminant plus payload case. ∎

The first-order restriction is load-bearing: resources denote *identity*, and `lift(lower(r))` for a handle `r` is meaningless outside its instance — the isolation property Section 4.4 exploits.

### 4.3 WASI 0.2 worlds: capability-oriented system interfaces

A WIT **world** [2] names a component's complete contract. WASI 0.2 [7] defines versioned WIT packages assembled into worlds:

```wit
package wasi:cli@0.2.0;

world command {
  import wasi:filesystem/types@0.2.0;
  import wasi:filesystem/preopens@0.2.0;
  import wasi:sockets/network@0.2.0;
  import wasi:clocks/wall-clock@0.2.0;
  export run: func() -> result<_, _>;
}
```

Three properties make worlds a security mechanism. First, **no ambient authority**: a component opens only files it holds handles (preopen descriptors) for — there is no global namespace to escape. Second, **versioned evolution**: worlds pin versions while adapters bridge old and new. Third, **resources as capabilities**: `wasi:filesystem`'s `descriptor` is a resource, hence an `own<descriptor>` handle at the ABI level — unforgeable, instance-scoped, revocable by dropping the table entry.

*Virtualization* is the host-side technique this enables: a world's imports are interface requirements, so the host may satisfy them with *adapter components* presenting filtered views. A plugin's filesystem import binds to an adapter exposing only a scratch directory; its sockets import to one permitting a single endpoint. Plugin code is unchanged — the world it compiled against is intact — but the world's *meaning* is host-defined per instantiation. Policy becomes wiring.

### 4.4 Component composition and virtualization

The component model [1] is a *linking* calculus: a component embeds core modules, declares instances, aliases exports, and re-exports results; `canon lift`/`canon lower` turn core functions into component-level functions at typed boundaries. Composition is instantiation — a host or `wasm-tools compose` satisfies one component's imports with another's exports. Every crossing goes through the canonical ABI, so composed components stay mutually isolated: separate linear memories, separate resource tables, separate instance state.

This yields the virtualized plugin architecture. A host embedding an untrusted plugin:

```rust
// Host-side composition sketch (wasmtime-style, simplified)
let engine = Engine::new(&config)?;
let plugin = Component::from_file(&engine, "plugin.wasm")?;
let vfs_adapter = Component::from_file(&engine, "adapters/scratch-fs.wasm")?;
let net_adapter = Component::from_file(&engine, "adapters/allowlist-net.wasm")?;
let mut linker = Linker::new(&engine);
// Virtualize: bind the plugin's WASI imports to adapters, not the raw host.
linker.instance("vfs", &vfs_adapter)?;   // satisfies wasi:filesystem import
linker.instance("net", &net_adapter)?;   // satisfies wasi:sockets import
let instance = linker.instantiate(&mut store, &plugin)?;
// The plugin observes a complete WASI 0.2 world; the host observes full mediation.
```

Adapters are themselves sandboxed components — swappable per plugin or tenant without recompilation — and they nest, building defense in depth from the same linking mechanism.

> **Theorem (World noninterference).** Let C₁, C₂ be instantiated so every import is satisfied by the host or an explicitly wired export, with disjoint virtualized worlds. Then no execution of C₁ can observe or affect C₂'s linear memory, resource tables, or instance state except through explicitly wired canonical-ABI boundaries.
>
> *Proof sketch.* Core instances have disjoint linear memories by construction; the MVP adds no shared-memory primitive. Handles index per-instance tables, meaningless across instances. Cross-instance calls go through wired exports mediated by `canon lift`/`canon lower`, which copy rather than alias. ∎

This is the formal content of "sandboxed": a property of the linking calculus, not a slogan.

### 4.5 Sandboxed plugin architectures replacing native extensions

| Dimension | Native extension (`dlopen`) | Component plugin |
|---|---|---|
| Address space | Shared with host; fault = host crash | Private memory; fault trapped |
| Authority | Ambient (inherits fds, env) | Capabilities only (world imports) |
| Interface | Unchecked convention | Checked WIT types + canonical ABI |
| Cross-language | Per-language FFI shims | One WIT world, many generators |
| Upgrade | ABI-coupled to host build | Versioned worlds + adapters |
| Revocation | Cannot revoke mapped authority | Drop handles, rewire, re-instantiate |
| Distribution | Platform `.so`/`.dll` | Portable `.wasm` + WIT package |

**Extism** [8] shows the operational shape: a plugin is a Wasm binary plus a manifest declaring imports, memory limits, and allowed hosts; PDKs in Rust, Go, JavaScript, Python compile guests against a stable guest ABI; host SDKs enforce timeouts and fuel. The component model generalizes the lesson: instead of one framework ABI, *every* plugin defines its ABI in WIT, implemented by the canonical ABI rather than framework convention.

**proxy-wasm** [9] shows the deployment shape: Envoy loads Wasm filters observing and mutating L7 traffic, hot-swapped without rebuilding the proxy. Recast on the component model, a filter's contract becomes a WIT world, its isolation becomes world noninterference, and its testability improves — the host instantiates the filter against a *mock world*, turning virtualization into a testing strategy.

Migration is mechanical [8]:

1. Express the extension API as a WIT world.
2. Generate guest/host bindings.
3. Recompile to `wasm32-wasip2`.
4. Compose plugins against virtualized adapters.

## 5 Empirical Results and Proofs

All results below are *analytic* bounds re-derivable from [1][3][4] — not wall-clock benchmarks.

**Result 1 — Flattening cost.** For a WIT signature, flattening yields `F` flat core values with `F` linear in the signature's structural size: each scalar one slot, each record its fields' slots, each string/list/large aggregate exactly two (`ptr`, `len`). Flattening is *O(signature size)*, independent of payload; payload cost is exactly one copy per crossing per direction.

**Result 2 — Copy overhead model.** Every first-order value crossing a boundary is copied at least once per direction, with transient guest allocations freed by `cabi_post_*`. Per-call overhead is `Θ(bytes transferred)` plus slot marshaling:

| Operation | Complexity | Paid |
|---|---|---|
| Flatten signature | O(signature size) | once, at bindgen |
| Lower arguments | O(bytes) copy | per call |
| Lift results | O(bytes) copy + validation | per call |
| `cabi_post_*` cleanup | O(regions freed) | per call |
| Resource handle pass | O(1) table op | per call |
| Instantiation | O(instance state) | once per load |

This is the price of noninterference: zero-copy needs shared memory, which the MVP deliberately excludes.

**Result 3 — WasmGC subtyping is decidable in linear time.** The nominal hierarchy with declared `sub` edges makes `ref.test`/`ref.cast` a walk up the supertype chain, depth-bounded by the declared hierarchy:

```haskell
-- Ancestor chains are declared, not inferred: nominal subtyping.
ancestors :: HeapType -> [HeapType]
ancestors t = t : maybe [] ancestors (superType t)

isSubtype :: HeapType -> HeapType -> Bool
isSubtype sub sup = sup `elem` ancestors sub

-- A checked cast is total: it returns Either, never forges.
checkedCast :: HeapType -> Ref -> Either TrapError Ref
checkedCast target r
  | isSubtype (refType r) target = Right r
  | otherwise                    = Left CastTrap
```

**Result 4 — Isolation lemma.** Two core instances' linear memories are disjoint address spaces with bounds-checked access, and the MVP provides no cross-instance aliasing — a plugin cannot name another plugin's bytes. With handle-table scoping, the noninterference theorem of Section 4.4 follows as a corollary.

## 6 Limitations

**Per-call serialization tax.** Noninterference is purchased with copies. For fine-grained, high-frequency calls — a filter per packet, a formatter per keystroke — `Θ(bytes)` marshaling per call can dominate. Native extensions pay no such tax. Mitigations exist (batching, in-component hot loops), but the MVP offers no zero-copy path.

**GC references are not canonical-ABI values.** WasmGC gives guests a managed heap [4], but the canonical ABI [3] lifts only *interface types*, which have no struct/array reference constructors. A GC object graph must still be serialized to cross a boundary; the collector's reach stops at `canon lift`. Until then, plugins serialize even when both sides are GC-managed.

**Async is post-MVP.** The MVP ABI assumes synchronous calls. Streaming and futures (`stream<T>`, `future<T>`) — essential for naturally asynchronous plugin APIs like HTTP handlers — are follow-on features; hosts bridge the gap with polling or threads.

**No shared-everything threading.** Fine-grained host↔plugin or plugin↔plugin parallelism awaits the threading proposal. MVP isolation is also a parallelism ceiling: components communicate by message-passing through the canonical ABI.

**Tooling maturity.** `wit-bindgen`, `wasm-tools`, and component-aware runtimes are production-grade but young next to decades of `dlopen` infrastructure; debuggers, profilers, and crash pipelines lag. WIT versioning discipline is lightly exercised at scale.

**Supply chain.** Sandboxing answers *what code can do*, not *whose code it is*. Signing and registry trust remain adjacent unsolved problems — a virtualized world cannot protect a host from a plugin it should never have installed.

---

## 7 Conclusion

We have argued that the WebAssembly component model as a whole — WasmGC's unforgeable reference types [4][5], the canonical ABI's total lift/lower translation [3], WASI 0.2's capability-oriented worlds [7], and composition with virtualized adapters [1] — is the first complete, specified foundation for sandboxed plugin architectures that can displace native extensions. Our contributions: the round-trip theorem making boundaries *meaningful*; the noninterference theorem making sandboxing a property of the linking calculus; and an honest `Θ(bytes)` cost model.

The practical upshot is a migration path: define the extension API as a WIT world [2], generate bindings, recompile to `wasm32-wasip2`, and virtualize the world per plugin. Extism [8] and proxy-wasm [9] validated the operational and deployment shapes; the component model supplies the standard interface layer they lacked. What remains — zero-copy crossings, GC-aware interface types, async primitives, supply-chain trust — is well-posed future work.

Native extensions asked hosts to trust code with their address space. Components ask hosts to wire a world. That is the difference between hoping a plugin behaves and *proving* what it can touch — and why the plugin architectures of the next decade will be composed, not linked.
