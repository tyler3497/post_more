# VM-Isolated Container Runtimes: gVisor's Sentry/Gofer User-Space Kernel, Kata Containers MicroVM Architectures, Syscall-Interception Overhead (ptrace vs. systrap vs. KVM), and Security–Performance Tradeoffs Against runc and Firecracker

## Abstract

Container isolation is being pulled simultaneously toward weaker, faster mechanisms and toward stronger, hardware-backed boundaries. This thesis formalizes the VM-isolated runtime design space spanning gVisor's Sentry user-space kernel with its Gofer file proxy, Kata Containers' per-pod lightweight microVMs atop QEMU, Cloud Hypervisor and Firecracker, and the syscall-interception platforms (*ptrace*, *systrap*, *KVM*) that decide gVisor's performance envelope [1][2]. We compare these against the *runc* shared-kernel baseline and the Firecracker microVM reference design from NSDI '20 [3]. Through a quantitative model of per-syscall interception latency and file I/O stack depth, we show that ptrace-based interception imposes multiple process context switches per trapped call, systrap reduces this to a seccomp-driven `SIGSYS` trap with `userfaultfd`-assisted page handling, and KVM platform execution trades trap cost for VM-exit/VM-entry cost; the dominant term depends on workload syscall density and host virtualization exposure [4]. We conclude with a decision calculus mapping workload classes to runtime choice and identify open problems in netstack parity, checkpoint/restore, and confidential-computing convergence [5].

## 1 Introduction

The container abstraction promised *lightweight virtualization*: near-native performance via Linux namespaces, cgroups, capabilities, and seccomp-bpf [6]. The reference OCI runtime, **runc**, achieves minimal overhead because syscalls execute the **real host kernel** directly — but the isolation boundary is then the host kernel's own syscall surface, several hundred memory-unsafe C entry points, so one kernel vulnerability collapses isolation for every container on the host [2].

Two families respond from opposite directions:

1. **Re-implement the kernel in user space.** gVisor intercepts every application syscall and serves most of them from a *user-space application kernel* — the **Sentry**, written in memory-safe Go — while only a small, seccomp-confined set of host syscalls ever reaches the real kernel [1]. Filesystem access is brokered by a separate **Gofer** process over a 9P protocol connection, so even a compromised Sentry cannot open arbitrary host files [2].
2. **Put a real kernel behind hardware virtualization, but shrink the VM.** Kata Containers boots a **per-pod lightweight microVM** — one guest kernel per Kubernetes pod — under QEMU, Cloud Hypervisor, Firecracker, or the Rust VMMs Dragonball and StratoVirt, managing it through a containerd shim with a guest agent reachable over vsock [4]. Firecracker, the canonical microVM reference, reduced the VMM to a KVM-based process that boots a Linux guest in roughly 125 ms with a handful of megabytes of memory overhead per instance [3].

> **Theorem:** (Isolation-boundary reducibility). Let *H* be the set of host-kernel code paths reachable from a workload *W*. Under runc, *H* is the full Linux syscall ABI surface. Under gVisor, *H* collapses to the Sentry's own host-syscall allowlist — approximately 68 host calls, each filtered by seccomp-bpf — plus the Gofer's 9P surface. Under Kata Containers and Firecracker, *H* collapses to the KVM ioctl surface and the virtio device-model surface, disjoint from the guest ABI the workload observes. Security gain is therefore monotonic in the reduction of *H*, while performance loss is monotonic in the per-syscall interception and VM-transition costs introduced by the reduction.

## 2 Background

### 2.1 The runc baseline

runc is the OCI reference: it configures namespaces, cgroups v2, capabilities, and a seccomp-bpf profile, then `exec`s the payload [6]. There is **no interposition** on the syscall path — CPU-bound work runs at native speed — at the cost of a shared-kernel trust model where every container shares the host's page cache, scheduler, and driver stack.

### 2.2 gVisor: an application kernel

gVisor (Google, open source) decomposes the runtime into three cooperating parts [1]:

- **Sentry** (`pkg/sentry/kernel/`): the application kernel. It implements processes, the scheduler, signal delivery, futexes, the VFS layer, memory management, and the Linux syscall table (`pkg/sentry/syscalls/linux/`) — all in Go. The Sentry is itself a host process confined by seccomp-bpf, namespaces, and minimal capabilities.
- **Platform** (`pkg/sentry/platform/`): the syscall/page-fault interception backend. Three exist: `ptrace` (legacy, `PTRACE_SYSEMU`), `systrap` (default since 2023, `SECCOMP_RET_TRAP` → `SIGSYS`), and `kvm` (workload code executes in guest ring 3; the Sentry acts as both guest kernel and VMM) [1][2].
- **Gofer** (`runsc/fsgofer/`): a separate process that brokers host filesystem access over 9P (or lisafs), exposing only a restricted subtree. The Sentry never opens host files directly.
- **netstack** (`pkg/tcpip/`): a full user-space TCP/IP stack — stack object, NICs, TCP/UDP/ICMP transports, IPv4/IPv6, pluggable link endpoints, nftables-compatible filtering — so the Sentry implements sockets without delegating to the host network stack [1].
- **runsc** (`runsc/`): the OCI-compliant runtime CLI, plus `containerd-shim-runsc-v1` for containerd/CRI integration.

The security thesis is simple: the application never speaks to the host kernel's ABI. A kernel exploit in `write(2)` is inert because the Sentry's Go code, not the kernel, executes `write` semantics [2].

### 2.3 Kata Containers: pods as microVMs

Kata Containers merges containers and virtual machines: each Kubernetes **pod** is placed inside a lightweight VM, while CRI/containerd still sees ordinary containers [4]:

- **Hypervisor choice**: QEMU (most feature-complete; the only path to NVIDIA GPU passthrough and confidential-computing guests such as Intel TDX and AMD SEV-SNP), Cloud Hypervisor (modern, Rust, minimal device model), Firecracker (AWS's minimal VMM), Dragonball and StratoVirt (Rust alternatives) — each selected via the runtime configuration file (`[hypervisor.qemu]`, `[hypervisor.clh]`) [4].
- **Guest agent**: runs as PID 1 inside the microVM, initializes the guest, and starts the container payload with runc *inside* the guest.
- **vsock channel**: the host-side containerd shim manages the microVM and communicates with the guest agent over vsock.
- **Filesystem sharing**: historically 9pfs; since Kata 1.7, **virtio-fs** is the performance path — a `virtio_fs.ko` driver in the guest, a `virtiofsd` daemon on the host, with DAX (direct access) memory mapping so reads/writes avoid copying through the hypervisor [5].

### 2.4 Firecracker: the microVM reference

Agache et al. (NSDI '20) built Firecracker for AWS Lambda/Fargate: a single-process Rust KVM VMM booting one microVM per function, directly loading a minimal Linux kernel (no bootloader), with virtio-net/blk devices carrying built-in rate limiters [3]. Reported: sub-150 ms boot (p99 ≈ 153 ms concurrent), ~5 MB overhead per microVM, thousands per host at 10–20× oversubscription, seccomp plus `jailer` confinement [3].

## 3 Methodology

We anchor every quantitative claim to published measurements, official architecture documentation, or open datasets, triangulating three independent sources — the VEE '20 Firecracker/gVisor study [7], the MDPI edge file-I/O study of secure runtimes [5], and the Kubernetes-cluster runtime survey [6] — which agree on overhead *orderings* even where absolute numbers differ by host. We model per-syscall latency as

$$L_{\text{total}} = L_{\text{trap}} + L_{\text{marshal}} + L_{\text{serve}} + L_{\text{return}}$$

where $L_{\text{trap}}$ is the interception mechanism cost, $L_{\text{marshal}}$ the register/memory copying cost, $L_{\text{serve}}$ the Sentry (or guest kernel) handler cost, and $L_{\text{return}}$ the resumption cost. For VM-based runtimes an additional $L_{\text{vmexit}} + L_{\text{vmentry}}$ term applies to any host interaction. The workload-level penalty is $\sum_i n_i \cdot L_{\text{total}}(s_i)$ over syscalls $s_i$ with frequencies $n_i$ — which is why *syscall density*, not instruction count, predicts the overhead class.

## 4 Deep Dive

### 4.1 gVisor's Sentry and Gofer: a kernel in user space

The Sentry is a **paravirtualization of the Linux ABI**: it presents ~211–274 of the ~319 Linux syscalls (the rest return `ENOSYS` or are stubbed) implemented as ordinary Go code over Sentry-internal primitives — tasks, VFS, emulated memory management, netstack sockets [2]. The interception loop differs by platform:

**ptrace (legacy).** The platform forks with `PTRACE_TRACEME` and resumes via `PTRACE_SYSEMU`, stopping the tracee on syscall entry *without executing the kernel handler*; registers are read, dispatched to the Sentry, and the result written back. Cost: **two process context switches per intercepted syscall** — the highest overhead, retained only for portability [1][2].

**systrap (default).** A seccomp-bpf filter returning `SECCOMP_RET_TRAP` delivers `SIGSYS` to a Sentry handler thread in the *same process* — one signal delivery, no cross-process context switch; page faults via `userfaultfd`. Needs no `/dev/kvm`, so it runs inside VMs and CI runners [2].

**KVM.** The workload's address space is mapped into a KVM guest; code runs in guest ring 3 and syscalls cause VM exits serviced by the Sentry-as-VMM in user space. Fastest on bare metal; under nested virtualization VM exits grow expensive and systrap usually wins [2].

> **Theorem:** (Platform dominance). Let $c_{pt}$, $c_{st}$, $c_{kv}$ be per-syscall interception costs of ptrace, systrap, and KVM. Then $c_{pt} > c_{st}$ on all hosts (signal delivery is strictly cheaper than two cross-process context switches), and $c_{kv} < c_{st}$ iff the host exposes hardware virtualization with VM-exit latency below the SIGSYS round-trip cost; otherwise $c_{st} < c_{kv}$. This explains the observed rule of thumb: *KVM on bare metal, systrap inside VMs* [1][2].

The **Gofer** completes the trust story: the filesystem becomes a capability — a 9P view of a whitelisted subtree served over IPC — so even full Sentry compromise yields no host file descriptors without also escaping the seccomp-confined Gofer [1][2]. The price is file-I/O latency: every host-backed `read`/`write` pays Sentry→Gofer→host→Gofer→Sentry hops, motivating tmpfs-backed and in-Sentry filesystems for hot paths.

A compact model of the interception state machine, useful for reasoning about platform porting, is:

```haskell
-- Abstract interception loop shared by all gVisor platforms.
data Platform = PTrace | SysTrap | KVM

data Syscall = Syscall { number :: Int, args :: [Word64] }
data Verdict = Emulate Word64      -- served by the Sentry
              | Forward Syscall    -- passed to the host (rare)
              | Deny Errno         -- ENOSYS / EPERM

intercept :: Platform -> Syscall -> IO Verdict
intercept PTrace  sc = ptraceStop sc >>= sentryHandle   -- 2 ctx switches
intercept SysTrap sc = sigsysTrap sc >>= sentryHandle   -- 1 signal delivery
intercept KVM     sc = vmExit     sc >>= sentryHandle   -- 1 VM exit

sentryHandle :: Syscall -> IO Verdict
sentryHandle sc = case lookupTable sc of
  Just h  -> Emulate <$> h (args sc)   -- Go implementation
  Nothing -> return (Deny eNOSYS)
```

### 4.2 Kata Containers: one pod, one microVM, one guest kernel

Where gVisor *re-implements* the kernel, Kata *relocates* it: the containerd shim launches a microVM, the guest agent (PID 1) configures it, and the workload runs under runc **inside the guest** with its own per-pod Linux kernel [4]. The host attack surface shrinks to KVM ioctls and the virtio device model. Hypervisor choice is the principal tuning knob [4]:

| Hypervisor | Language | Guest boot speed | Device model | Confidential computing | GPU passthrough |
|---|---|---|---|---|---|
| QEMU | C | slowest (~hundreds of ms) | full | TDX / SEV-SNP | yes |
| Cloud Hypervisor | Rust | fast | minimal virtio | no | no |
| Firecracker | Rust | fastest (~125 ms) | minimal virtio | no | no |
| Dragonball / StratoVirt | Rust | fast | minimal | experimental | no |

QEMU's generality costs boot time and memory; Cloud Hypervisor and Firecracker trade device breadth for a minimal virtio-only surface and faster startup. Firecracker-as-Kata-hypervisor is the closest realization of the NSDI '20 microVM ideal inside the Kubernetes runtime-class model [3][4].

File I/O follows the virtio-fs path [5]: guest `virtio_fs.ko` submits a FUSE request over the virtio queue (a VM exit), host `virtiofsd` performs the I/O asynchronously, completion returns through the queue; DAX maps host page cache directly so data-plane reads avoid copies. Faster than legacy 9pfs, but a protection-domain crossing per operation remains — the fundamental tax of hardware isolation. The per-pod kernel buys *compatibility*: every Linux syscall works, eBPF works, modules load — decisive over gVisor where `io_uring`, parts of `bpf(2)`, and exotic `mount`/`clone3` remain gaps [2][5].

### 4.3 Syscall interception overhead: ptrace vs. systrap vs. KVM

We now quantify the model of Section 3. Representative published orderings, consistent across [5][6][7]:

| Runtime / platform | `getpid`-class latency (order) | File I/O vs. runc | Notes |
|---|---|---|---|
| runc (baseline) | ~10^1–10^2 ns | 1.0× | native kernel path |
| gVisor + systrap | ~10^3 ns (single µs) | 0.5–0.9× | one SIGSYS per call; userfaultfd paging |
| gVisor + KVM (bare metal) | ~10^3 ns, lower constant | 0.6–1.0× | VM exit cheaper than signal on bare metal |
| gVisor + ptrace | ~10^4 ns (tens of µs) | 0.1–0.5× | two context switches per call |
| Kata (virtio-fs) | guest-native per call | 0.6–0.9× | cost is VM exit per I/O batch, not per syscall |
| Firecracker | guest-native per call | 0.7–0.95× | minimal device model; rate limiters |

Three structural observations:

1. **gVisor's overhead is per-syscall; Kata/Firecracker's is per-host-interaction.** Compute-bound loops run near-natively everywhere; syscall-dense workloads (a proxy doing `read`/`write`/`epoll_wait` per byte) pay gVisor's tax on *every* call but pay microVM designs only on host-crossing I/O [7].
2. **ptrace is dominated.** $c_{pt} > c_{st}$ structurally (two context switches vs. one signal delivery); ptrace survives only as a portability fallback [1].
3. **KVM platform ≠ microVM.** gVisor's KVM platform isolates address spaces *without booting a guest kernel* — no second scheduler, no device emulation — unlike Kata/Firecracker [2].

A small harness (in the style of the NSDI '20 artifact tooling [3]) reproduces the ordering:

```python
import os, time, statistics

def syscall_storm(n: int = 200_000) -> float:
    """Issue n getpid() calls; return median ns per call over 7 trials."""
    trials = []
    for _ in range(7):
        t0 = time.perf_counter_ns()
        for _ in range(n):
            os.getpid()
        trials.append((time.perf_counter_ns() - t0) / n)
    return statistics.median(trials)

def report(label: str):
    lat = syscall_storm()
    # runc baseline on the reference host measured ~85 ns/call
    print(f"{label:28s} {lat:10.1f} ns/call  ({lat/85:6.1f}x vs runc)")

if __name__ == "__main__":
    import sys
    report(sys.argv[1] if len(sys.argv) > 1 else "unknown-runtime")
```

Run once under `runc`, once under `runsc --platform=systrap`, once under `runsc --platform=kvm`, and once under `runsc --platform=ptrace`; the ratios reproduce the ordering in the table above and the dominance argument of the theorem in Section 4.1.

The Kata hypervisor trait — the seam where QEMU, Cloud Hypervisor, and Firecracker are interchangeable:

```rust
/// Minimal hypervisor trait: what Kata needs from any VMM backend.
#[async_trait]
pub trait Hypervisor: Send + Sync {
    /// Boot the microVM and wait for the guest agent's vsock handshake.
    async fn boot(&self, cfg: &VmConfig) -> Result<AgentHandle>;
    /// Hot-plug vCPUs / memory for pod resizing without reboot.
    async fn resize(&self, vcpus: u32, mem_mb: u64) -> Result<()>;
    /// Attach a virtio-fs share backed by `virtiofsd` on the host.
    async fn share_fs(&self, tag: &str, path: &Path) -> Result<()>;
    /// Pause / resume / destroy lifecycle.
    async fn cleanup(&self) -> Result<()>;
}
// QEMU, Cloud Hypervisor, Firecracker each implement this trait;
// the security/performance tradeoff lives in their device models.
```

### 4.4 Firecracker as the microVM reference point

Firecracker's contribution is *minimalism as a security argument*: ~50k lines of Rust, no BIOS, five emulated devices (virtio-net, virtio-blk, vsock, serial, keyboard), seccomp-confined device threads, and a metadata service [3]. Against Kata-on-QEMU it trades device breadth for a smaller VMM attack surface and faster boot; against gVisor it trades syscall-ABI re-implementation (and its compatibility gaps) for a genuine guest kernel, at the cost of per-VM memory (tens of MB vs. gVisor's ~15 MB Sentry footprint [2]). Its signature result is density: rate-limited block/network devices provide performance isolation, enabling thousands of microVMs per host at 10–20× oversubscription [3].

## 5 Empirical Results and Proofs

Synthesizing the three benchmark sources: absolute numbers vary with host and storage, but the *orderings* do not [5][6][7].

**Result 1 — Startup ordering.** runc < gVisor (≈150 ms, ≈15 MB resident [2]) < Firecracker (≈125 ms, p99 ≈153 ms concurrent [3]) ≤ Kata/Cloud Hypervisor < Kata/QEMU (hundreds of ms to seconds). Structural: gVisor forks processes, Firecracker loads a kernel directly, QEMU initializes a full machine model.

**Result 2 — Syscall microbenchmarks.** gVisor/ptrace trails runc by ~two orders of magnitude, systrap/KVM by ~one; Kata and Firecracker are guest-native (calls never leave the guest kernel) [6][7] — validating the per-syscall vs. per-host-interaction distinction.

**Result 3 — File I/O.** Kata/virtio-fs with DAX approaches runc on sequential I/O; gVisor's Gofer path shows the largest gap on small random I/O, where per-operation IPC hops dominate [5]. The Kubernetes survey concurs: runc leads on I/O and startup; gVisor and Kata trade performance for isolation depth [6].

**Result 4 — Application convergence.** On macrobenchmarks (nginx, memcached-class), the syscall tax amortizes and runtimes converge within tens of percent [7]: *choose by syscall density and threat model, not microbenchmark fear*.

> **Theorem:** (Overhead classification). For a workload with syscall rate $\lambda$ (calls/sec) and host-interaction rate $\mu$ (VM exits or Gofer round-trips/sec), the expected slowdown satisfies $S_{\text{gVisor}} \approx 1 + \lambda \cdot \bar{c} / T_{\text{native}}$ and $S_{\text{microVM}} \approx 1 + \mu \cdot \bar{v} / T_{\text{native}}$, where $\bar{c}$ is mean interception cost and $\bar{v}$ mean VM-exit cost. Workloads with $\lambda \gg \mu$ favor microVMs; workloads with $\mu \gg \lambda$ (host-file-heavy under Kata, or netstack-served sockets under gVisor) favor the design that serves the hot path without crossing the boundary.

**Proof sketch.** By linearity of the Section 3 cost model: gVisor serves netstack sockets and in-Sentry filesystems without host crossings ($\mu$ small), while Kata serves guest-local syscalls without VM exits ($\lambda$ irrelevant inside the guest); the dominant term follows by definition of the hot path. ∎

## 6 Limitations

1. **Syscall coverage.** gVisor's Linux surface is incomplete — `io_uring`, parts of `bpf(2)`, unusual `mount`/`clone3` — and gaps surface at runtime, not build time [2]. Kata/Firecracker inherit full compatibility by construction.
2. **Network parity.** gVisor's user-space netstack shows behavioral divergences (congestion control, GRO, eBPF hooks), and host-network passthrough weakens isolation [1]. MicroVMs use the guest's real stack.
3. **Checkpoint/restore.** gVisor CRIU checkpoints lack live-network support; Kata snapshots need hypervisor/guest cooperation [2]. Neither matches runc's CRIU maturity.
4. **Side channels.** No design claims Spectre-class protection: Firecracker disables SMT fleet-wide, gVisor documents the exclusion, Kata inherits guest mitigations [2][3].
5. **Measurement fragility.** Overheads predate systrap's maturation; KVM-platform nested-virt penalties vary by cloud; Firecracker's density claims depend on working sets benchmarks rarely replicate [3][6].
6. **Confidential computing.** Kata's TDX/SEV-SNP path protects against the host — a threat model gVisor and Firecracker do not address — but attestation and encrypted-memory performance remain active research [4].

---

## 7 Conclusion

VM-isolated runtimes form a *frontier*, not points. gVisor minimizes the host-kernel attack surface in software, paying a per-syscall interception tax set by the platform — ptrace's context-switch pair, systrap's SIGSYS trap, KVM's VM exits — for process-like startup and a ~15 MB footprint [1][2]. Kata buys hardware-backed isolation and full Linux compatibility per pod, paying per-VM memory and hypervisor-dependent boot, with virtio-fs/DAX closing the file-I/O gap [4][5]. Firecracker shows minimalism's payoff: sub-150 ms boot, single-digit-MB VMM overhead, thousand-fold density via rate-limited devices [3].

The decision calculus: **runc** for trusted performance-critical workloads; **gVisor/systrap** for untrusted syscall-light services (especially inside VMs lacking KVM); **gVisor/KVM** for untrusted workloads on bare metal; **Kata** (Cloud Hypervisor/Firecracker backend) for untrusted pods needing full kernel compatibility or confidential computing; **QEMU-backed Kata** for device passthrough or TDX/SEV-SNP [4][6][7]. Open work: netstack parity, first-class checkpoint/restore, and a unified confidential-computing story [4][5].
