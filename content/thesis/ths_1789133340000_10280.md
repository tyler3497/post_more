# Verified Microkernels: seL4's Refinement Calculus, Capability Security, and the Path to General-Purpose Verified Operating Systems

## Abstract

The seL4 microkernel is the first general-purpose operating-system kernel with a machine-checked proof of functional correctness over its complete C implementation, comprising roughly 8,700 lines of C. Its verification strategy rests on a three-level refinement calculus — an abstract specification in Isabelle/HOL, an executable design specification derived from a Haskell prototype, and the C implementation itself — linked by forward-simulation proofs that propagate any abstract-level property down to the running binary. Layered on this foundation are machine-checked proofs of integrity, authority confinement, and intransitive noninterference (confidentiality) for the abstract specification, plus translation-validation evidence that the compiled binary refines the C semantics. This thesis reconstructs the refinement calculus, the capability model with its derivation tree, and the security theorems, reports the empirical cost of verification (≈117,000 lines of Isabelle proof for the abstract invariants alone, with 460 defects uncovered in the process), and assesses the remaining obstacles — timing channels, multicore, device drivers, and the trusted computing base — on the path to a fully general-purpose verified operating system.

## 1. Introduction

Operating-system kernels are the archetypal *trusted computing base*: every application, library, and security policy in a system depends on their correct behavior, yet they are among the most bug-prone artifacts in software engineering. The 2009 result of Klein et al. changed the terms of this discussion permanently: they reported the first *complete, machine-checked proof of functional correctness of a general-purpose OS kernel implementation* — seL4, a third-generation microkernel in the L4 family — proving that its ~7,500 (later ~8,700) lines of C faithfully implement a precise formal specification [1][5]. Functional correctness means *behavioral* correctness: every system call executes exactly as the abstract model says it should; the kernel never crashes, never dereferences null pointers, never accesses arrays out of bounds, and never enters an undefined state.

That achievement is only the beginning of the story. Correctness with respect to a specification is useful only to the extent that the specification itself is *worth* proving things about. The seL4 project therefore pursued two further campaigns: (i) proving that the abstract specification enforces high-level security properties — integrity, authority confinement, and confidentiality — so that these properties transfer, by refinement, to the C implementation [2][4]; and (ii) extending the refinement chain downward to the *binary*, eliminating the compiler from the trusted computing base [3]. Each layer is machine-checked in Isabelle/HOL; each assumption is explicit, as formal methods demand [4].

This thesis reconstructs the seL4 verification story as a case study in *refinement-based assurance*: what the refinement calculus actually is, why capabilities and their derivation tree are the load-bearing structure of the security proofs, what the security theorems say and — just as importantly — what their explicit assumptions leave out, and how far the path now runs toward general-purpose verified operating systems.

## 2. Background

### 2.1 Why microkernels

The microkernel design minimizes the code that runs in privileged mode, moving drivers, file systems, and protocol stacks into isolated user-level components [4]. The kernel then provides only the primitives that *must* be privileged: address spaces, threads, and inter-process communication (IPC). The payoff is a minimal trusted computing base: if the kernel is small enough, it becomes *verifiable* in the strong sense that seL4 achieved. The L4 family, founded by Jochen Liedtke in the 1990s, demonstrated that microkernels can also be *fast*, with IPC latencies competitive with monolithic kernels — demolishing the received wisdom that structure must be traded for performance.

seL4 is a third-generation L4 microkernel: it generalizes its predecessors' address spaces into a uniform *capability* system, in which every resource reference is an unforgeable token carrying explicit rights [2].

### 2.2 The provable-security dream

The ambition of provable operating-system security is nearly half a century old. Feiertag and Neumann [6] articulated it in 1979 with PSOS (Provably Secure Operating System); the KSOS and KIT efforts of the 1980s attempted it by hand and collapsed under the weight of manual proof [1]. Their failure taught the field that OS verification without mechanization is hopeless, and mechanization without a disciplined methodology is merely hopeless *slower*. seL4's answer to that history is the refinement calculus of §3: a chain of machine-checked refinement proofs, each bridging a small semantic gap, so that no single proof obligation is unmanageable.

### 2.3 The verification problem statement

Formally, the project had to show the following. Let **A** be the abstract specification (a nondeterministic state machine over abstract kernel objects), **E** the executable design specification (a deterministic Haskell-derived model), and **C** the C implementation with a formalized operational semantics. The required theorems are:

> **Theorem (Functional correctness):** C refines E, and E refines A. In particular, every behavior of the C implementation is a behavior permitted by the abstract specification; the implementation never fails (no undefined behavior, no assertion failures) [1].

> **Theorem (Security enforcement):** The abstract specification A enforces integrity, authority confinement, and intransitive noninterference under a configurable access-control policy [2][4].

By the transitivity of refinement, the security theorems of A descend to C — provided the refinements preserve the relevant structure, which the proof obligations explicitly establish.

## 3. Methodology

### 3.1 The three refinement levels

The seL4 methodology decomposes the semantic gap between mathematics and machine code into three manageable steps [1]:

| Level | Artifact | Size | Role |
|---|---|---|---|
| **Abstract (A)** | Isabelle/HOL state machine | ≈4.9 kLOC Isabelle + 117 kLOC proof | Precise, nondeterministic model of *what the kernel does*, omitting implementation detail |
| **Executable (E)** | Haskell prototype → Isabelle | ≈5.7 kLOC Haskell → 13 kLOC Isabelle + 50 kLOC proof | Deterministic design model mirroring control flow and data layout |
| **Concrete (C)** | C99 source + formalized semantics | ≈8.7 kLOC C | The deployed implementation, parsed into Isabelle's Simpl language |

The Haskell prototype occupies a subtle position in the proof chain: it is the artifact the engineers actually iterated on (the C implementation was written in roughly *two person-months* once the prototype stabilized), but it is formally *cut out* of the proof — E is translated automatically from Haskell, and the refinement E ⊑ C is proved entirely within Isabelle [1][7].

### 3.2 Forward simulation

The refinement relation is proved by **forward simulation**. For each abstract state σ and concrete state *s* related by a state-relation *R*, every concrete transition *s → s′* must be matchable by an abstract transition σ → σ′ with *R(σ′, s′)*. In Isabelle, the corresponding lemma has the schematic form:

```isabelle
lemma forward_sim:
  assumes "R σ s" and "s → s'"
  shows "∃σ'. σ → σ' ∧ R σ' s'"
```

proving, per operation, that the concrete behavior is a subset of the abstractly permitted behaviors. The full refinement then composes: every trace of the C program is a trace of A. Because A is *nondeterministic*, the refinement simultaneously proves that C *resolves* that nondeterminism consistently — the implementation cannot do anything the specification forbids, including crashing [1].

### 3.3 The tool stack

The proofs were carried out in **Isabelle/HOL**, supported by a substantial custom toolchain [1][3]:

1. **C-parser**: translates the C subset into Isabelle's Simpl language with a formalized C memory model.
2. **AutoCorres**: an automated, proof-producing abstraction tool that lifts the parsed C into higher-level Isabelle/HOL functions, dramatically simplifying the refinement target.
3. **Crunch**: a recursive invariant prover for the state-monad formalization.
4. **SMT backends (Z3, Sonolar)**: used in the binary-verification translation validation [3].

The choice of Isabelle — a higher-order logic with a small trusted kernel — was deliberate: unlike automated tools that reason *about* a model, the refinement proofs relate the *actual artifact* at each level, and the small-kernel architecture of Isabelle concentrates trust in a few thousand lines of proof-checker code [1].

## 4. Deep Dive

### 4.1 The refinement tower, in detail

The abstract specification is written as a *state monad with nondeterminism and exceptions* in Isabelle/HOL. Kernel objects — threads (TCBs), endpoints, notifications, page tables, capability nodes — appear as abstract records; operations are total functions from state to (return value × state) sets. Nondeterminism appears wherever the specification deliberately underspecifies: e.g., the *choice* of which eligible thread to schedule next is modeled as an arbitrary selection among runnable threads, so that *any* concrete scheduler refining the spec satisfies the proof [1].

The executable specification E is generated from the Haskell prototype and is deterministic by construction: it fixes data representations (machine words, pointer arithmetic) and control flow, while still omitting C-level detail such as stack frames. The refinement proof A ⊒ E is the *largest* intellectual artifact of the project: ≈117,000 lines of proof script establishing invariants of A and the simulation relation [1][7].

The C-level refinement E ⊒ C proceeds through the C-parser and AutoCorres: the parser produces a Simpl program with a formalized memory model; AutoCorres abstracts it to a shallow embedding where each C function becomes an Isabelle/HOL function; the simulation proof then relates these functions to E's Haskell-derived counterparts [1]. The final theorem chain yields:

```
  Abstract spec (A)  ⟸  security proofs (integrity, confinement, confidentiality)
         ⇑ forward simulation (≈117k lines proof)
  Executable spec (E)
         ⇑ forward simulation (≈50k lines proof)
  C implementation (parsed semantics)
         ⇑ translation validation (binary ≡ C)
  Binary code
```

### 4.2 Capabilities, untyped memory, and the derivation tree

seL4's authority model is a *capability system*: every object a thread may touch — a page, a thread, an endpoint, an interrupt — is referenced through an unforgeable capability stored in a per-thread *CSpace* (a guarded page table of CNode objects), and each capability carries a rights mask (read, write, grant, and object-specific rights) [2]. Capabilities cannot be forged because the kernel stores them in kernel-only memory and user code can name them only by slot index. Authority can only ever *decrease*: a thread may *mint* a derived capability with a subset of its rights, but never amplify them — the **monotonicity of derivation** that underwrites every security theorem.

All kernel memory is allocated from **Untyped** objects: initially, every free page is an Untyped capability, and creating any kernel object (a TCB, an endpoint, a page table, a CNode) requires *retyping* an appropriately sized Untyped region. Retyping records parent–child edges in the **capability derivation tree (CDT)**; when a capability is revoked, the kernel walks the CDT and destroys every derived descendant — which is how memory is safely reclaimed without dangling references [2][4]. A simplified sketch of the retype discipline:

```rust
// Conceptual sketch of the untyped → object discipline
enum KernelObject { Tcb, Endpoint, Notification, CNode, PageTable, Frame }

fn retype(untyped: &Untyped, kind: KernelObject, size: usize) -> Result<Cap, Error> {
    if untyped.watermark + size > untyped.capacity { return Err(Error::NoMemory); }
    let obj = allocate_object(kind, size)?;          // zeroed, aligned, typed
    cdt_insert(parent = untyped.cap, child = obj.cap); // derivation edge
    untyped.watermark += size;
    Ok(obj.cap.with_rights(RIGHTS_ALL))
}

fn revoke(cap: &Cap) {
    for child in cdt_descendants(cap) { destroy(child); } // recursive, in CDT order
}
```

The CDT is also the mechanism of the security proofs: authority confinement is literally a statement that the set of capabilities reachable from a subject can only shrink or be explicitly granted, never silently grow — and the CDT is the data structure the proof reasons over [2].

### 4.3 Integrity and authority confinement

Sewell et al. [2] proved two high-level access-control properties over the abstract specification, each machine-checked in Isabelle/HOL and transferred to the C implementation by refinement:

> **Theorem (Integrity):** Given an access-control policy *P* describing each subject's authority, every state transition of the kernel only writes objects that the acting subject has write authority over under *P*. Integrity is an *upper bound* on the set of possible state mutations [2].

> **Theorem (Authority confinement):** Authority in the system can only change in ways bounded by *P*: a subject cannot acquire authority it was not explicitly granted, and capability propagation is confined to the derivation relation. Authority confinement is an *upper bound* on how authority spreads dynamically [2].

Both theorems are proved against an *abstract access-control policy model*: the kernel is general-purpose, so the proofs do not fix one policy; instead they show that *whatever* policy the system designer configures, the kernel's behavior stays within the bounds that policy implies. This is what makes the results usable as a *framing property* for verifying user-level system composition: the kernel gives you a guaranteed ceiling on interference, and your system design decides where the floor is [2][4].

### 4.4 Confidentiality as intransitive noninterference

The confidentiality campaign (Murray et al., 2013) proved that seL4 enforces **intransitive noninterference**: information may flow from domain *A* to domain *B* only if the configured information-flow policy permits *A ⇝ B* (possibly *via* an explicit declassifier *D*, hence *intransitive* — the classical transitive Goguen–Meseguer condition is too strong for systems with legitimate downgraders) [4]. Concretely:

> **Theorem (Confidentiality):** In a correctly configured system, no entity can read — or otherwise *infer through storage channels* — data without explicit read authority, modulo the permitted intransitive flows [4].

The proof rules out *covert storage channels* but explicitly not *covert timing channels*: the abstract specification models time only loosely, and Spectre-class microarchitectural channels postdate the proof and violate its hardware assumptions [4]. This honesty about scope is characteristic of the project: the whitepaper enumerates every proof assumption — correct hardware (MMU and caches modeled abstractly), a semantics-preserving compiler (closed by translation validation), trusted boot code, and single-core execution — because machine-checked proof *forces* assumptions into the open [4].

### 4.5 Closing the compiler gap: translation validation

Functional correctness of the C code still trusts the C compiler. Sewell, Myreen, and Klein [3] closed that gap for the ARM build with **translation validation**: for each compiled function, they proved that the *binary* refines the C semantics used in the correctness proof. The pipeline lifts both the C (via the C-parser) and the ARM binary (via a formalized ISA model) into a common graph language, then discharges the equivalence with SMT solvers (Z3 and Sonolar) over a *decompilation into logic* [3]:

```python
# Schematic of the translation-validation pipeline (Sewell et al., PLDI'13)
c_graph   = lift_to_graph(parse_c("kernel.c"), c_semantics)      # trusted C semantics
asm_graph = lift_to_graph(disassemble("kernel.elf"), arm_model)  # formalized ARM ISA
vc = refinement_obligation(c_graph, asm_graph)                    # per-function VCs
assert z3_prove(vc) and sonolar_prove(vc)                         # both SMT solvers agree
```

Because the binary refinement composes with the C-level refinement, the full chain — binary ⊑ C ⊑ E ⊑ A — means the *running machine code* satisfies the abstract specification [3][4]. Exclusions at the time: kernel initialization code, multicore execution, and the abstract modeling of the MMU and caches — each an explicit, documented assumption rather than a silent gap [7].

## 5. Empirical Results and Proofs

The seL4 verification produced hard numbers that recalibrated the field's sense of what formal OS verification costs [1][7]:

| Metric | Value |
|---|---|
| C implementation size | ≈8,700 SLOC |
| Abstract spec size | ≈4.9 kLOC Isabelle |
| Executable spec | ≈5.7 kLOC Haskell → 13 kLOC Isabelle |
| Abstract invariant + refinement proof | ≈117,000 lines of proof script |
| C-level refinement proof | ≈50,000 lines of proof script |
| Defects found during verification | ≈460 (160 in C, 150 in design, 150 in spec); 16 found earlier by shallow testing |
| Verification effort | ≈20–30 person-years (SOSP'09 reported ~20 at completion) |
| Implementation effort (post-prototype) | ≈2 person-months |

Three observations deserve emphasis. **First**, verification found defects that years of testing had missed — including in the *specification itself* — vindicating the claim that proof is a discovery procedure, not merely a certification procedure [1]. **Second**, the C code was written in two person-months *because* the Haskell prototype had absorbed the design iteration: the methodology front-loads design risk into a malleable artifact. **Third**, the proof is *maintained*: the l4v proof repository tracks the kernel, and the refinement is re-run as the kernel evolves — verification as a living regression suite rather than a one-off certificate [7].

The security theorems rest on the same foundation: integrity and authority confinement [2] and confidentiality [4] are proved over A and inherited by C, making seL4 the first *general-purpose* kernel with implementation-level proofs of the classic security properties — realizing the thirty-year-old dream of Feiertag and Neumann [6].

Real-world deployment followed: seL4 was released as open source in 2014, flew on DARPA HACMS program demonstrators (including autonomous helicopter missions with verified isolation between critical and untrusted components), and now underpins the seL4 Foundation's ecosystem of verified systems work [4].

## 6. Limitations

A verified kernel is not a verified *system*, and the project's own documentation is explicit about the boundaries [4][7]:

1. **Timing and termination channels.** The confidentiality proof is termination-insensitive and excludes covert timing channels — including Spectre-class microarchitectural leakage, discovered five years after the information-flow proof and violating its hardware assumptions [4].
2. **Hardware and initialization.** The MMU and caches are modeled abstractly; kernel boot/initialization code was excluded from the binary verification; device drivers and firmware sit outside the proof entirely.
3. **Concurrency.** The verified configuration is single-core; the multicore (SMP) kernel is a separate, ongoing verification target.
4. **Availability and timeliness.** The classic proofs cover integrity and confidentiality; availability/timeliness guarantees are addressed by the newer MCS (mixed-criticality systems) kernel variant, not the mainline proofs [4].
5. **The specification gap.** Refinement proves the code matches the specification — not that the specification matches the *intent*. The 150 specification-level issues found during verification show this gap is real, though the proof process itself is the best known tool for shrinking it.
6. **Trusted computing base.** Isabelle's kernel, the C-parser, AutoCorres, the SMT solvers, and the hardware remain trusted. Proof shrinks the TCB; it does not eliminate it.

These limitations define the research frontier rather than diminishing the result: each is an *explicit, formalized* assumption — the precise contribution that machine-checked verification makes over informal assurance [4].

## 7. Conclusion

seL4's verification demonstrates a thesis with consequences beyond one kernel: **refinement is a scalable assurance methodology**. By decomposing the gap between abstract intent and running binary into small, machine-checked simulation steps — abstract to executable, executable to C, C to binary — the project made the verification of a general-purpose OS kernel tractable, auditable, and, crucially, *maintainable* as the artifact evolves. The capability model with its derivation tree shows how to design a kernel so that its security properties are *provable*, not merely plausible; the integrity, authority-confinement, and noninterference theorems show what those proofs can buy; and the explicit assumption ledger shows intellectual honesty about what they cannot.

The path to general-purpose verified operating systems now runs through the limitations of §6: multicore verification, timing-channel resistance, verified drivers, and verified user-level services composed under the kernel's framing guarantees. None of these is a small problem. But seL4 moved the question from "can an OS kernel be verified at all?" — answered, definitively, in the affirmative — to "how far up the stack can the refinement tower reach?" That is the research program of the next decade.
