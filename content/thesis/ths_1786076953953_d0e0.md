# Strong Consistency in Geo-Replicated Databases Without TrueTime: Hybrid Logical Clocks, Deterministic Sequencing, and Calvin-Style Transaction Ordering in CockroachDB and FoundationDB

## Abstract
Geo-replicated transactional databases traditionally rely on tightly synchronized physical clocks and TrueTime-style uncertainty windows to achieve external consistency. We rigorously deconstruct three families that avoid physical-clock dependence while preserving strict serializability: Hybrid Logical Clocks (HLC) as deployed in CockroachDB, deterministic sequencing in the Calvin/FaunaDB lineage, and sequencer-centric optimistic validation in FoundationDB. We formalize TrueTime's interval model [TT.now()=(earliest,latest)] and its commit-wait rule, prove why HLC maintains causality (e→f ⇒ hlc(e)<hlc(f)) while staying close to wall time, analyze Calvin's epoch-batched global log with deterministic lock acquisition order eliminating distributed 2PC, and dissect FoundationDB's GetReadVersion and GRV-proxy to commit-proxy pipeline for monotonic version allocation. Synthesis reveals latency-availability tradeoffs: HLC pays uncertainty-driven lease uncertainty, deterministic sequencing pays single-log bottleneck but achieves zero clock dependence, optimistic sequencer pays abort rate under contention. We provide TLA+ specs, Haskell and Rust implementations, complexity bounds, and deployment guidance.

## 1 Introduction

Geo-replicated SQL is the **holy grail** of distributed systems: *scale across continents*, *survive region loss*, and *preserve single-image semantics*. Google Spanner [1] demonstrated that externally consistent strictly serializable transactions are feasible at planetary scale, but its key enabler — **TrueTime** — rests on non-commodity hardware: GPS receivers and atomic clocks per datacenter plus a sophisticated time-synchronization daemon that maintains a bounded uncertainty window \\( \\epsilon \\approx 1\\!-\\!7ms \\) [2][3].

> **Theorem (TrueTime intuition):** If physical time is available with bounded uncertainty, commit-wait guarantees external consistency by waiting out uncertainty before exposing transaction effects [1][3].

Yet TrueTime is a **cost and operational burden** that most operators cannot replicate. The central question of this thesis is: *How do we achieve equivalent strict serializability and linearizability without TrueTime, GPS hardware, or tight clock synchronization?*

We answer by comparing three production-proven paradigms that **eliminate physical-clock dependence**:

1.  **Hybrid Logical Clocks (HLC)** — *CockroachDB* lineage [4][5]. Combine coarse NTP wall time with Lamport logical counters to provide monotonic, causality-preserving timestamps while remaining close to wall time for snapshot usability.
2.  **Deterministic Sequencing** — *Calvin* [7], *FaunaDB* [8][10], *SLOG*. Pre-order transactions through a single global log (or partitioned log) and then deterministically execute in identical order on all replicas, removing two-phase commit (2PC) entirely.
3.  **Optimistic Sequencer + MVCC** — *FoundationDB* [9]. Centralize version allocation via a sequencer / GRV proxy / master and resolve conflicts optimistically at commit via resolvers.

**Contributions:**
- Formal reconstruction of TrueTime's `TT.now()`, `TT.after()`, `TT.before()` and commit-wait correctness envelope
- Proof of HLC monotonicity and bounded drift from physical time: \\( \\forall e, \\; l.e \\ge pt.e \\land c_e < C_{max} \\)
- Analysis of Calvin's sequencing layer achieving 500k+ TPS via batching and Paxos-replicated log
- FoundationDB's GetReadVersion (GRV) protocol guaranteeing external consistency without clock sync
- Comparative table of latency, availability, fault tolerance, and operational cost
- Rust, Haskell, Python reference implementations and TLA+ safety spec

## 2 Background / Preliminaries

### 2.1 External Consistency, Strict Serializability, Linearizability

*External consistency* [1] is stronger than serializability: if transaction \\(T_1\\) commits before \\(T_2\\) starts in wall-clock time, then \\(T_1\\)'s timestamp < \\(T_2\\)'s timestamp. This implies clients observe a database indistinguishable from a single machine.

- **Linearizability** applies to single operations; **strict serializability** to transactions [3].
- Spanner achieves it via TrueTime + Paxos + 2PC.
- Without TrueTime, we must achieve same ordering via *logical ordering* or *deterministic ordering*.

### 2.2 Lamport, Vector, and Physical Clocks

Lamport clocks capture *happens-before* \\( e \\rightarrow f \\Rightarrow L(e) < L(f) \\) but are disconnected from wall time, making snapshots unintuitive for users (“read as of 3:00pm”).

Vector clocks capture causality precisely but are \\( O(N) \\) space and still not wall-time anchored.

Physical (NTP) clocks are wall-time close but not causally safe: two events with \\( pt.e < pt.f \\) may still violate causality due to skew up to 100-250ms [4].

### 2.3 TrueTime Model

TrueTime API [2][3]:

```
TT.now() -> TTInterval { earliest: Timestamp, latest: Timestamp, uncertainty = latest-earliest = 2ε }
TT.after(t) -> true iff t < TT.now().earliest  // t definitely in past
TT.before(t) -> true iff t > TT.now().latest   // t definitely in future
```

True absolute time \\( t_{abs} \\) satisfies \\( earliest \\le t_{abs} \\le latest \\) with high probability (>1-1e-7). Implementation uses time masters with GPS + atomic clocks, time slaves polling masters, Marzullo's algorithm [1].

Commit protocol:

1.  Choose \\( s = TT.now().latest \\)
2.  Log prepare via Paxos
3.  **Commit-wait**: wait until \\( TT.now().earliest > s \\) — guarantees \\( s \\) is in past [3]

Thus any later transaction seeing \\( s \\) must have timestamp > \\( s \\).

Cost: \\( commit \\ latency \\approx 2\\epsilon + 2*Paxos RTT \\). With \\( \\epsilon=4ms \\), wait ≈ 8ms, acceptable inter-DC (30-100ms) [6].

> **Problem:** Requires custom hardware, privileged time daemons, monitoring of clock divergence, and premium cloud pricing. CockroachDB explicitly rejects this [4].

## 4 Deep Dive

### 4.1 TrueTime Intervals — Why We Want to Remove Them

TrueTime's guarantee looks simple but hides complexity:

```rust
// Rust conceptual model of TrueTime
struct TTInterval {
    earliest: u64, // ns since epoch - ε
    latest: u64,   // ns since epoch + ε
}
impl TT {
    fn now() -> TTInterval {
        let local = physical_clock();
        let uncertainty = estimate_drift() + network_delay_bound();
        TTInterval { earliest: local - uncertainty, latest: local + uncertainty }
    }
    // Spanner commit timestamp selection
    fn pick_commit_ts() -> u64 {
        let tt = Self::now();
        tt.latest // upper bound ensures future reads > it eventually
    }
    fn commit_wait(s: u64) {
        // spin until definitely past s
        while Self::now().earliest <= s { 
            std::thread::sleep(std::time::Duration::from_micros(100));
        }
    }
}
```

Spanner's transaction timeline with 3 Paxos groups:

| Step | Action | Timestamp Rule |
|------|--------|----------------|
| Exec | Acquire shared locks on participants | - |
| Prepare | Participants pick prepare ts > read ts, within lease | Lease-bound |
| Commit | Coordinator picks s >= max(prepare ts, TT.now().latest) | s monotonic |
| Commit-wait | Wait till TT.after(s) | Guarantees external consistency |
| Log | Paxos log COMMIT(s) to all groups | Durability |

**Operational cost** cited by FaunaDB [10]: IT staff must manage time infra, handle Leap Second smearing, handle VM migration clock jumps. Clock skew alarms become P0 incidents.

Hence need for *logical* substitution.

### 4.2 Hybrid Logical Clocks in CockroachDB

**HLC** introduced by Kulkarni et al. [5] combines:

```
HLC = (l : wall-time ns, c : logical counter 18-bit)
Comparison lexicographic: (l1,c1) < (l2,c2) iff l1<l2 ∨ (l1==l2 ∧ c1<c2)
```

Algorithm [5][12]:

```python
# Python reference HLC (simplified from CockroachDB hlc package [12])
class HLC:
    def __init__(self, max_offset_ms=500):
        self.l = 0 # physical component
        self.c = 0 # causality
        self.max_offset = max_offset_ms * 1_000_000

    def now(self, pt): # pt = physical time from node
        l_prime = self.l
        self.l = max(l_prime, pt)
        if self.l == l_prime:
            self.c += 1
        else:
            self.c = 0
        self._check_overflow()
        return (self.l, self.c)

    def update(self, msg_hlc, pt):
        # On receiving message with remote HLC
        l_prime = self.l
        l_msg, c_msg = msg_hlc
        self.l = max(l_prime, l_msg, pt)
        if self.l == l_prime == l_msg:
            self.c = max(self.c, c_msg) + 1
        elif self.l == l_prime:
            self.c += 1
        elif self.l == l_msg:
            self.c = c_msg + 1
        else:
            self.c = 0
        return (self.l, self.c)

    def _check_overflow(self):
        if self.c > (1<<18):
            raise Exception("HLC logical overflow - degrade to max wall")
```

*Properties proved in [5]:*

> **Theorem (HLC Causality):** If \\( e \\rightarrow f \\) (Lamport happens-before), then \\( HLC(e) < HLC(f) \\). Lexicographically.
> 
> **Theorem (Bounded Drift):** \\( |l.j - pt.j| \\) bounded by NTP uncertainty + causality bursts; logical component \\( c \\) bounded with high probability under clock synchrony.

CockroachDB integration details [4][12]:

- Each node maintains HLC Clock `pkg/util/hlc`
- HLC passed on 3 channels: Store Liveness, Raft, BatchRequest header
- Transactions: read timestamp = HLC.Now(). Client tracks provisional commit ts. Writes buffered. Commit: coordinator runs parallel commit (reduces 1 RTT) then advances HLC to ensure commit ts > all read ts.
- Closed timestamps: followers track max closed ts to serve follower reads (bounded staleness) without leaseholder.

Closed timestamp mechanism replaces TrueTime leases: follower can serve read at ts ≤ closed_ts if no in-flight tx overlapping. Unlike Spanner's TrueTime lease (10s), CockroachDB uses *stasis* via range lease + uncertainty window computed as `max_offset` (default 500ms). No atomic clocks needed; offset derived from NTP monitoring.

**Latency model:**

```
CockroachDB commit = 1 RTT to leaseholder + parallel commit 1 RTT + closed timestamp propagation (async)
Spanner commit = 2PC 2 RTT + commit-wait ε (0-7ms)
```

No commit-wait stall in HLC path, but *read restart*: if read encounters newer write with higher timestamp due to clock skew, transaction retries with higher read timestamp (uncertainty restart). Tail latency under skew.

```haskell
-- Haskell spec of HLC monotonicity invariant (TLA+ style translated)
data HLC = HLC { phys :: Integer, logical :: Int } deriving (Eq, Ord)

hlcSend :: HLC -> Integer -> HLC
hlcSend (HLC l c) pt =
  let l' = max l pt
  in if l' == l then HLC l' (c+1) else HLC l' 0

hlcRecv :: HLC -> HLC -> Integer -> HLC
hlcRecv (HLC l1 c1) (HLC l2 c2) pt =
  let l' = maximum [l1, l2, pt]
  in case () of
       _ | l' == l1 && l' == l2 -> HLC l' (max c1 c2 + 1)
         | l' == l1 -> HLC l' (c1 + 1)
         | l' == l2 -> HLC l' (c2 + 1)
         | otherwise -> HLC l' 0
```

### 4.3 Deterministic Sequencing: Calvin, FaunaDB, SLOG

Calvin [7] radically *reorders operations*: instead of executing concurrently then agreeing on commit outcome (2PC), it **agrees on order before execution**.

Architecture:

1.  **Sequencing Layer**: Clients submit transactions → ordered log via Paxos. Batch 10ms epochs → atomic append. No need to know read/write sets yet for WAN replication.
2.  **Scheduling Layer**: Analyzes batch to build dependency graph; if read/write sets unknown, performs *reconnaissance* — optimistic execution to discover sets, then resubmit with sets known.
3.  **Execution Layer**: Deterministic locking: transactions acquire locks in global order. Deadlock-free because order total. Partitions execute in parallel.

Key insight:

> **Calvin's Theorem:** If all replicas receive identical input log and execution is deterministic, replicas converge without coordination. No 2PC during execution.

```
Client → [Sequencer (Paxos log)] --replicated log--> All DB nodes
                                      ↓
                          Scheduler builds graph per epoch
                                      ↓
                          LockManager in log order (deterministic)
                                      ↓
                          Workers execute, replicate effects
```

FaunaDB adaptation [10][13]: Uses Calvin over 3 replicas (log) plus data partitioned after log replay. Single-phase commit: transaction's effects applied only after log commit, no prepare phase.

Performance: Paper shows 500k Txn/sec via batching [10][7]. Latency = batch accumulation (10ms) + log replication (1 WAN RTT) + execution. Throughput scales with batch size, unlike 2PC which is per-txn.

TLA+ core invariant:

```tla
------------------------------ MODULE Calvin ------------------------------
VARIABLES log, executed, txnState
TypeOK == log \in Seq(Txn) /\ executed \subseteq 0..Len(log)
Determinism == \A i,j \in DOMAIN log:
                 i < j => ~Conflicts(log[i], log[j]) \/ AcquiresBefore(i,j)
Safety == \A r1,r2 \in Replicas: executed[r1]=executed[r2] => state[r1]=state[r2]
```

Limitation: Reconnaissance for unmaterialized reads; stored procedures needed to know read set. Cross-partition transactions still need deterministic lock ordering (all-or-nothing).

Comparison with TrueTime: Calvin requires *no* time synchronization assumption (ε = ∞ acceptable) [10]. Clock skew cannot violate serializability because order derived from log, not time. Tradeoff: log append is global bottleneck; cannot have partitioned independent commit as Spanner does.

### 4.4 FoundationDB Sequencer-Optimistic Hybrid Without TrueTime

FoundationDB [9][14][15] achieves strict serializability via *centralized versioning* without clocks:

Flow:

1.  **GRV Proxy**: Client `GetReadVersion()` → GRV proxy asks Master for latest committed version + ensures log set alive. Returns read version RV = max committed version. Simultaneously Ratekeeper throttles.
2.  **Resolver & Commit Proxy**: Client buffers writes locally; on commit sends read-conflict ranges + write ranges to Commit Proxy. Commit Proxy batches, asks Master for commit version CV = RV+1 monotonic. Resolvers shard by key range, check if any read range modified in `[RV+1, CV)`. If yes, conflict → abort.
3.  **Log System**: Commit proxy writes mutation to transaction logs, replicated via disk quorum. Master reports committed version.

Properties:

- **Monotonic version**: Master generates version via `Int64++` at ~1M/sec, durable via sequencer lease. No clock needed.
- **External consistency**: Because GRV = latest committed as of receipt time and commits strictly increasing, if T1 finishes before T2 starts, T2's RV ≥ CV(T1). Proof via master serialization of GRV and commit.
- **Optimistic concurrency**: High throughput under low contention; aborts under hotspot.

```rust
// Conceptual GRV path (Rust)
struct Master {
    commit_version: u64,
    live_logs: Vec<LogId>,
}

impl Master {
    fn get_read_version(&mut self) -> u64 {
        // FoundationDB ensures read version = latest committed version
        self.commit_version // plus causality check logs alive
    }
    fn get_commit_version(&mut self, batch_size: usize) -> u64 {
        self.commit_version += 1; // actually allocates range, but atomic bump
        // batch shares same version in real FDB, but for concept
        self.commit_version
    }
}

// Resolver conflict check
fn has_conflict(read_ranges: &[(Key, Key)], writes_since_rv: &std::collections::BTreeMap<u64, Vec<KeyRange>>) -> bool {
    for (ver, ws) in writes_since_rv.iter() {
        // if ver > read_version
        for rr in read_ranges {
            if ws.iter().any(|w| overlaps(w, rr)) { return true; }
        }
    }
    false
}
fn overlaps(a: &KeyRange, b: &(Key, Key)) -> bool { true } // placeholder
type Key = Vec<u8>;
type KeyRange = (Key, Key);
type LogId = u64;
```

Simulation testing [11] enables FoundationDB's correctness without physical clocks: deterministic simulation of 1 trillion CPU-hour equivalents finds concurrency bugs via actor model Flow language. No wall-clock dependency in tests.

Latency: 1 RTT GRV + 1 RTT commit (batching amortizes master). No wait. Contention leads to abort exponent.

For geo-replication, FoundationDB uses asynchronous log shipping to satellite DCs; primary remains strict serializable, not multi-primary like Spanner/Cockroach. Regional loss requires manual failover.

## 5 Empirical / Proofs

### 5.1 Proof Sketch: HLC Causality Preservation

*Claim:* HLC algorithm [5] satisfies \\( e \\rightarrow f \\Rightarrow HLC(e) < HLC(f) \\).

Proof by induction over event sequence:

- Local event: `l` = max(l_old, pt). Since pt non-decreasing (ignoring NTP backward steps, masked via max), `l_new ≥ l_old`. If equal, `c++`, so tuple strictly increases.
- Send: message carries HLC(e). Receiver sets `l_f = max(l_{f-1}, l_e, pt_f)`. If `l_f = l_e`, then `c_f = c_e+1 > c_e`. Else `l_f > l_e`. Either lexicographically larger.
- Transitive closure via repeated application.

Bounded drift: `l` never drifts more than max physical skew + logical growth. Since `c` increments only when multiple events share same wall time, worst-case growth limited by event rate × max skew window.

### 5.2 Proof: Calvin Determinism Implies Strict Serializability

*Lemma:* Log order defines total order. Lock acquisition in log order prevents cycles.

Assume log `[T1,T2,...,Tn]`. Each partition acquires locks for Ti before Tj if i<j (if they conflict). Execution respects lock order → serialization order = log order. Since log replication is Paxos total order, all replicas agree. Therefore execution equivalent to serial execution in log order → serializable.

External consistency: Client receives acknowledgment only after log entry persisted and executed. Next transaction's log append occurs after, hence order respects wall-clock commit dependencies.

### 5.3 FoundationDB Conflict Serializability

Define version order: transactions commit with version CV. Overlapping read-write check ensures no history has read from stale version. Standard optimistic concurrency proof: Build dependency graph where edge T1→T2 if T2 writes key read by T1 after T1's RV but before T2's CV. Resolvers abort Ti if such edge forms a cycle with commit order? Actually FDB uses first-committer-wins: resolvers maintain last commit per key range, abort on write-write or read-write conflict since RV. Graph remains acyclic as conflicts resolved via abort.

For external consistency: Linearize history at commit version assignment point (master). GRV request linearizes at master read path. If T1 commits before T2 GRV, master's CV(T1) ≤ GRV(T2) hence T2 observes T1.

### 5.4 Quantitative Model

- **Commit wait cost saved**: Eliminating TrueTime wait saves mean 6ms per transaction at p99 ε [3]. At 10k TPS, that's 60 sec of CPU spin saved per second cluster-wide.
- **HLC restart rate**: Under 500ms max offset, restart probability ≈ skew-induced causality violation rate <0.1% in production [4].
- **Calvin batching gain**: TPS scales as `batch_size / (Paxos RTT + schedule)`. At 500k Txn/s [10], batch 5k incurs 10ms, vs Spanner 2PC needing 2 RTT per txn (~20ms intra-DC).
- **FoundationDB simulation**: 10:1 simulated vs real time acceleration [11]; flaw detection rate 10× higher than integration tests.

## 6 Limitations

1.  **HLC unbounded logical component**: Under sustained causality storm (e.g., 1M RPC/s with identical wall ms), logical counter may overflow 18-bit. CockroachDB handles by artificially bumping wall time forward, trading timestamp accuracy.
2.  **Single-log bottleneck (Calvin)**: Global log limits write scalability to sequencer throughput. Fauna mitigates via hierarchical and partitioned log [10], but cross-partition deterministic scheduling NP-hard for optimal concurrency.
3.  **FoundationDB single master**: Commit version allocation via single master (though not data bottleneck) caps total commit rate ~2M versions/sec. Geo multi-primary not natively supported; asynchronous secondary sacrifices external consistency across regions.
4.  **No wall-time semantic in deterministic**: Reading “as of wall time” requires mapping logical log index to wall estimate — not precise.
5.  **NTP vulnerability remains for HLC**: While HLC tolerates skew, massive sudden jump > max_offset (e.g., VM live migration resetting clock) triggers node self-fencing; Spanner's TrueTime hardware mitigates this with redundant time sources.
6.  **Closed timestamp lag**: CockroachDB follower reads may lag up to `closed_timestamp_target_duration` (3s default) behind leader, impacting bounded staleness freshness vs Spanner's TrueTime staleness bound (≤ε).
7.  **No Byzantine tolerance**: All three assume non-Byzantine clocks / logs. Verifiable logical clocks needed otherwise [future work].

## 7 Conclusion

Spanner proved external consistency is possible worldwide, but its recipe tied to atomic clocks and custom time infrastructure is **not universally portable**. We dissected three commodity-friendly families achieving identical isolation guarantees without TrueTime:

- **HLC (CockroachDB)** preserves most Spanner-like API (wall time + causal monotonicity) with tunable max offset and no hardware. Cost: occasional uncertainty-induced transaction retries and closed-timestamp staleness.
- **Deterministic Sequencing (Calvin/FaunaDB)** removes clocks from correctness path entirely by establishing total order before execution, replicating inputs not effects. Single logical sequencer batching yields exceptional throughput (500k Txn/s) at cost of log bottleneck and reconnaissance for unknown read sets.
- **Sequencer-Optimistic (FoundationDB)** simplifies time to integer versions from master + resolver conflict check, supported by deterministic simulation for bug finding. Extremely performant for low-contention workloads but aborts hot keys and remains single-primary.

*Operational guidance*: If your workload needs PostgreSQL compat and low-ops without time hardware → HLC; if you need active-active multi-region strict serializable with partitionable deterministic workload (ledger, Fauna) → Calvin; if you need high-throughput intra-DC ACID with simulation-tested resilience and layered architecture → FoundationDB.

No single solution dominates; the *infinite KV* principle — keep ordering source infinite — applies to log or KV layers.
