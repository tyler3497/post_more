# Zero-Knowledge Circuit Arithmetization Revisited: PLONK Permutation Arguments, Custom Gates, Plookup Tables, and Halo2 Polynomial Commitment with IPA

## Abstract
PLONK unified general-purpose SNARKs through a universal updatable SRS and a permutation argument over Lagrange bases that enforces copy constraints via grand-product checks with randomizers β,γ. Plookup extends this foundation by replacing expensive bit-decompositions with efficient subset checks against precomputed tables, reducing constraints for range checks, XORs, and AES S-boxes by an order of magnitude via sorted-difference multiset equality and Schwartz-Zippel randomized compression. Halo2 adopts PLONKish arithmetization with high-degree custom gates, rotation support, and lookup integration while substituting KZG’s pairing-based trusted setup for the transparent inner product argument based on Pedersen vector commitments, enabling logarithmic folding and recursion via Pasta cycle Pallas/Vesta. This thesis synthesizes permutation argument soundness, custom-gate expressiveness, lookup argument completeness, and IPA-based polynomial opening, proving end-to-end security, quantifying prover O(n log n) vs O(n), verifier succinctness, and Zcash Orchard production criteria with real aggregation benchmarks.

## 1 Introduction
**Zero-knowledge succinct non-interactive arguments of knowledge** (zk-SNARKs) have transitioned from per-circuit trusted setups in *Groth16* [1] to universal systems in *Sonic, Marlin, and PLONK* [1][2]. The practical bottleneck was not *soundness* but deployability: each new program required a fresh multi-party computation ceremony, toxic waste management, and circuit-specific verification keys.

PLONK—*Permutations over Lagrange-bases for Oecumenical Noninteractive arguments of Knowledge*—introduced by Gabizon, Williamson, and Ciobotaru [1], resolved this with a single updatable SRS that supports any circuit up to a bounded size *N*. The core innovation was to represent circuits as constraints on evaluations over a multiplicative subgroup *H ⊂ F* rather than coefficient form, enabling a unified permutation argument derived from Bayer-Groth [3].

This work argues that PLONK’s lasting contribution is not merely its SRS but its *arithmetization interface*: advice, fixed, and instance columns bound by custom gates, copy constraints, and lookup rules [4][5]. Three extensions define modern production systems:

- **Custom gates** generalize the classic fan-in-2 fan-out-1 equation *q_L·a + q_R·b + q_O·c + q_M·ab + q_C = 0* into arbitrary degree-*d* polynomials over rotated columns, allowing high-degree nonlinear gates without additional rows [4].
- **Plookup** formalized by Gabizon and Williamson [2] introduces table membership *f ⊂ t* as a first-class primitive, transforming operations like *"x ∈ [0,2^k)"* or *"(a,b,c) is valid AES S-box"* from *O(k)* constraints to *O(1)* lookups [2][6].
- **Halo2** transparent polynomial commitment [3][4][7] replaces KZG [1] with the Bulletproofs-style inner product argument (IPA) over Pedersen commitments, removing trusted setup at cost of *O(log n)* proof size but enabling recursive accumulation via Pasta cycles [7].

> **Theorem 1 (Informal):** If the generalized permutation argument, the Plookup grand-product check, and the IPA opening are secure under discrete-logarithm assumptions in the random-oracle model, then PLONKish arithmetization with custom gates and tables yields a *computationally sound* and *zero-knowledge* SNARK without trusted setup.

*Contributions:*

1. A rigorous reconstruction of PLONK permutation constraints, zero-knowledge blinding via 2-cycle randomizers, and aggregation of copy constraints [1][8].
2. A comparative analysis of Plookup sorted-difference vs. log-derivative lookup modern variants, including integration with PLONKup [3].
3. A complete exposition of Halo2 IPA commitment opening, from vector commitment *C = ⟨a,G⟩ + ⟨b⟩·U* to logarithmic folding rounds [5][6][9].
4. Performance models for prover *O(n log n)* FFT vs *O(n)* MSD, verification, and recursion thresholds in Zcash Orchard [4][7].

We target implementers familiar with *finite-field polynomial IOPs* yet seeking production intuition from *halo2_proofs 0.3.0* [7].

## 2 Background / Preliminaries

### 2.1 Polynomial IOP over Subgroups
Let *F* be prime-order field, *G* prime-order additive group. Let *H = {1, ω, ω², ..., ω^{n-1}}* where *ω* is primitive *n*-th root of unity. A circuit assignment is encoded as polynomials *a(X), b(X), c(X)* where *a(ω^i) = wire value* at row *i*. A selector polynomial *q_L(X)* encodes gate type. Lagrange basis *L_i(X)* enables succinct constraint checking via quotient polynomial *t(X) = constraint(X)/Z_H(X)* where *Z_H(X)=X^n-1* vanishes on *H* [1].

**Definition 2.1 (Universal SRS):** Structured reference string *SRS = {[x^i]_1, [x^i]_2}_{i=0}^{D}* where *D* bounds max degree. Updatability means any participant can randomize via *x ← x·r* and prove update correctness via same pairing check as Marlin [1].

### 2.2 Copy Constraints and Permutations
A wiring predicate *σ: [3n] → [3n]* is a permutation decomposing into cycles. Example: if output of gate 2 equals input of gate 5, then *σ* maps position *(2,c)* to *(5,a)*. Enforcing *σ(a)=a* as multiset equality is the crux of PLONK [1][8].

### 2.3 Zero-Knowledge Baseline
Standard SNARKs achieve zero-knowledge by appending *t=3..6* random blinding rows that break deterministic *L₁* evaluations and randomize *Z*. Lemma 1 from PLONK zero-knowledge section [8][9]: restriction of *σ* to first *i-1* positions with *Z(g^i)=1* if *π* permutation ensures blinding pairs with 2-cycles randomize *Z* without affecting soundness.

### 2.4 Lookup Landscape
Lookup tables address *SNARK-unfriendly* operations: range proofs, bitwise ops, S-boxes. Prior work Bootle et al. *BCGJM18* required *O(d log n)* auxiliary commitments for table size *d*. Plookup [2] reduces to *3* commitments degree *n* regardless of *d ≤ n*, enabling *n=2²⁰* tables for 8-bit decomposition in AES [6].

| Scheme | Commitments | Degree | Trusted Setup | Proof Size |
|--------|-------------|--------|---------------|------------|
| PLONK KZG [1] | 9+2 | n | universal | O(1) ≈ 400B |
| Plookup [2] | +3 auxiliary (Z,f,s) | n | universal | +2 G1 |
| Halo2 IPA [4][5] | vector | n | transparent | O(log n) ≈ 3-5KB |
| PlonKup [3] | 1 extra | n | universal | O(1) |

## 3 Methodology / Formalism

We reconstruct full protocol via five-stage Halo2 pipeline [4][5]:

1. **Commit to polynomials** encoding assignments, permuted values, lookup-sorted values.
2. **Vanishing argument** constraining custom gates, lookup rules, equality rules to zero on *H*.
3. **Evaluation** at challenge points *x, ωx* etc.
4. **Multipoint opening** aggregate evaluation proof via random linear combination *r* [4].
5. **IPA argument** to prove opening correctness without revealing polynomial.

### 3.1 Permutation Argument Formalization
Define copy vector *W = (a,b,c)* concatenated over rows. Let *S_ID = (1, k₁·H, k₂·H)* coset shifts with *k₁,k₂ ∉ H*. Let *S_σ = (σ-col encodings)*. Let random *β,γ ∈ F*. Grand-product polynomial *Z* defined:

- *Z(g)=1*
- *Z(g·g^i)·Π_j (w_j(g^i)+β·S_ID_j(g^i)+γ) = Z(g^i)·Π_j (w_j(g^i)+β·S_σ_j(g^i)+γ)* [1]

Batch check: *L₁(X)(Z(X)-1)=0*, *Z(X)f'(X)=g'(X)Z(gX)*.

*Zero-knowledge modification:* Append *k=5* pairs *(b₁,b₁,b₂,b₂,…)* with duplicate entries creating 2-cycles in *σ'* such that *Z(g^{n-k+1})..Z(g^n)* randomized uniformly in *F^k* [8][9]. Verifier skips those rows in permutation product via factor *(X-h_{n-k})…(X-h_n)*.

```python
# PLONK permutation product check (simplified Sage-like)
F = GF(mod_order)
n = 1<<12
omega = F.primitive_root_of_unity(n)
beta, gamma = F.random(), F.random()
# S_ID = [1, k1*wi, k2*wi]
Z = [F.one()]
for i in range(n-1):
    num = (a[i]+beta*S_ID_A[i]+gamma)*(b[i]+beta*S_ID_B[i]+gamma)*(c[i]+beta*S_ID_C[i]+gamma)
    den = (a[i]+beta*sigma_A[i]+gamma)*(b[i]+beta*sigma_B[i]+gamma)*(c[i]+beta*sigma_C[i]+gamma)
    Z.append(Z[-1]*num/den)
assert Z[0]==1 and Z[n-1]==1 # when sigma permutation holds
```

### 3.2 Plookup Methodology
Given table vector *t ∈ F^d* and witness *f ∈ F^n*, assert *f ⊂ t* as multiset inclusion. Reduction workflow [2][6]:

- Compress tuple *(x,y,z)* via random *α*: *c = α·x + α²·y + α³·z* preserves distinctness w.h.p. via Schwartz-Zippel.
- Sort concatenation *s = sort(f||t)* according to order of *t*.
- Define difference multiset requirement: non-zero differences of *s* equal non-zero differences of *t* up to padding.
- Grand-product checks: *∏ (1+β)(γ+f_i)(γ(1+β)+t_i+β t_{i+1}) / (γ(1+β)+s_i+β s_{i+1})(…)* as in protocol spec [2].

Batched variant *PlonKup* [3] merges PLONK and Plookup wire constraints into single quotient *t(X)* reducing evaluation points from *8* to *5*.

```haskell
-- Plookup subset relation as multiset equality (conceptual Haskell)
type F = Integer -- field mod p
subsetCheck :: [F] -> [F] -> Bool
subsetCheck f t = let s = sortByT (f++t) t
                      s' = zipWith (\x y -> x - y) s (tail s)
                      t' = zipWith (-) t (tail t)
                  in multisetEq (filter (/=0) s') (filter (/=0) t' ++ replicate (length f) 0)
```

### 3.3 IPA Methodology
Halo2 IPA builds polynomial commitment from Pedersen vector commitment [5][6]: For polynomial *p(X)= Σ a_i X^i*, generators *G ∈ G^n*, random *U*, blinding *r*:

*C = ⟨a,G⟩ + r·U* = Σ a_i G_i + rU*.

Opening at point *x*: prover claims *v = p(x)*. Verifier derives *b = (1, x, x², …, x^{n-1})*. Goal: prove *⟨a,b⟩=v* without revealing *a* [5].

Folding round *i*:

- Prover computes cross-terms *L_i = ⟨a_{R}, G_L⟩ + ⟨a_R, b_L⟩·U*, *R_i = ⟨a_L, G_R⟩ + ⟨a_L, b_R⟩·U*.
- Verifier challenge *u_i*.
- Compress: *a' = a_L + u_i·a_R*, *b' = b_L + u_i^{-1}·b_R*, *G' = G_L + u_i·G_R*.

After *log n* rounds, verifier checks single multiscalar multiplication [5][9].

## 4 Deep Dive

### 4.1 PLONK Permutation Argument – Wiring as Multiset Permutation
*Why Lagrange bases?* Unlike coefficient-based Sonic, Lagrange-based evaluation converts copy constraint *a_i = b_j* into identity *a(X)-b(X)* vanishes at subset of *H*. Using *β·S_ID* randomizers separates wires that share same value but distinct roles, preventing malleability across cosets [1].

- **Soundness:** Under *q-DLOG* in bilinear group, if verifier accepts, then with overwhelming probability *Z* satisfies recurrence, implying *σ(W)=W* as multiset. Schwartz-Zippel bounds error ≤ *deg/Z* /|F| ≈ *3n/|F|* negligible [1].
- **Zero-knowledge:** Blinding with *k* duplicate pairs randomizes *k* openings of *Z* while copy constraints on those pairs prove they are intentionally equal, not adversarial collisions [8][9]. Halo2 extends this to *t=2* extra rows for evaluation blinding plus rigorous *evaluation domain* blinding [4].
- **Aggregated permutations:** Modern PLONKish circuits merge *m* columns into single permutation argument via random *δ* combining, saving *m-1* *Z* polynomials [4].

**Table: PLONK vs TurboPLONK Custom Gates:**

| Gate Type | PLONK Base [1] | TurboPLONK / Halo2 [4] |
|-----------|----------------|------------------------|
| Degree | ≤2 (qm·ab) | ≤5 custom |
| Columns per check | 3 wire | n advice (e.g., 5) |
| Rotations | 0 | up to 2 (X, ωX, ω⁻¹X) |
| Selectors | 5 fixed | 10+ fixed/blind |
| Usage | single op per row | multiple ops pack |

### 4.2 Custom Gates, Rotations, and Chip Architecture
Halo2 departs from gate-selectors to *region-based* chips. A chip configures *n* advice columns, *m* fixed polynomials, and defines gates referencing *Rotation::cur()*, *next()*, *prev()* [4]. This enables:

- **Elliptic curve addition** in 1 row vs PLONK 2 rows via degree-4 constraints using incomplete addition formulas over Pallas base field *Fq*.
- **SHA-256 Ch/Maj** via table + 6 advice columns.
- **Poseidon sponge** width 3 permutation in 1 row with custom S-box power-5 constraint *s = x⁵* not feasible in R1CS [7].

*Italic emphasis:* ***custom gates trade prover FFT domain blowup for constraint density; optimal chip sizing is NP-hard bin packing of operations into rows.***

### 4.3 Plookup – From Sorted Differences to Log-Derivative
Original Plookup [2] proves *f ⊂ t* via sorting argument: if *s* sorted according to *t* and non-zero adjacent differences multiset-equality holds, inclusion holds. Complexity *O(n log n)* prover sorting, *O(n)* commitment.

Modern improvements:

- **Log-derivative lookups (logUp):** proven in Halo2 *v0.3*: *∑ 1/(X+f_i) = ∑ m_j/(X+t_j)* where *m_j* multiplicity; avoids sorting, prover *O(n log n)* still but simpler grand product [6]. Transforms rational function equality check into single fractional sum via random *β*.
- **cq (cached quotients):** precompute quotient polynomials for fixed table *t*, reducing prover from *O(n log n)* to *O(n)* when *t* fixed for many proofs (e.g., range [0,255]) [6].
- **Vector Plookup:** table rows are tuples *(x,y,z)* compressed via powers of *α*; ensures 2D lookups like *(a,b)→c* for XOR tables size *2^k × 2^k* → *2^{2k}* naive vs *2^k* vector compress with random *α* [2].

> **Theorem 2 (Plookup Completeness & Soundness):** Given *t* length *d ≤ n*, if honest prover constructs *s* as sorted *f||t*, then verifier accepts. If *∃ i: f_i ∉ t* then verifier rejects with probability *≥ 1 - (2n+d)·deg/ |F|* over random *β,γ,α* [2].

*Integration with zero-knowledge:* same blinding technique as permutation: pad table with last value duplicates randomized, copy constraints ensure padding not affecting inclusion [2][4].

### 4.4 Halo2 Transparent IPA Construction and Pasta Recursion
*Why not KZG?* KZG [1] requires pairing-friendly curve (e.g., BLS12-381) and trusted SRS toxic waste *τ* where compromise enables forging arbitrarily. Zcash Sapling trusted setup *Powers of Tau* required 87 participants but still trusted [7]. Halo pursued *transparent* setup: public randomness only.

IPA security relies on discrete-log assumption in prime-order group without pairings; compatible with *Pallas* and *Vesta* Pasta cycle: *order of Pallas base field = scalar field of Vesta* and vice versa, enabling recursion where verifying a Vesta proof inside Pallas circuit uses native field arithmetic, avoiding non-native field emulation overhead *~100×* [7][9].

Protocol complexity per round *log n = 20* for *n=2²⁰* constraints (Zcash Orchard circuit ~2²⁰ rows). Prover computes *2·log n* G-multi-scalars size *n/2^i* each: total *O(n)* group ops, *O(n log n)* field via NTT-like fold? Actually IPA prover is *O(n)* group, no FFT needed for opening (vs KZG needs *O(n log n)* NTT). Verifier *O(n)*? No, verifier does *O(log n)* after preprocessing commitments batched via multi-exponentiation accumulation [5][6].

Comparison KZG vs IPA [5][6][9]:

| Property | KZG (PLONK) [1] | IPA (Halo2) [4][5] |
|----------|-----------------|---------------------|
| Setup | universal updatable SRS | transparent (public random) |
| Proof size | 3 G1 + few F | 2·log n G1 + ~4 F (~3KB for log20) |
| Prover | O(n log n) FFT | O(n) MSM + O(n) fold |
| Verifier | O(1) pairings | O(log n) G + O(n) to hash preprocess? actually O(n) for MSM aggregated? but amortized via aggregation |
| Recursion | expensive (pairing in circuit) | native in Pasta cycle |
| Assumption | q-SDH / bilinear | DLOG |

*Accumulation:* Halo replaces per-proof verification with argument accumulation: each proof adds to accumulator *A* via random challenge; final accumulator check once reduces verification of *k* proofs from *k·O(log n)* to *O(k)+O(log n)* [7].

### 4.5 End-to-End Composition: PLONKup, Halo2 Circuits, and Orchard
PlonKup [3] proves integration of lookup into PLONK vanishing argument: single polynomial *T(X)=t_a(X)+t_b(X)+t_c(X)* where each term checks gate, permutation, lookup grand products aggregated via powers of *α*. Halo2 extends to *multicolumn* lookups where table may have multiple columns *(t₁,t₂)* and lookup *(f₁,f₂)* checked via combined compression *α·f₁+α²·f₂* [4].

Zcash Orchard case study [7]: circuit ~2¹⁹ rows, 10 advice columns, 9 fixed, 1 instance. Custom gates: Sinsemilla hash (MerkleCRH), *value commitment* (Pedersen), *Nullifier* (Poseidon). Plookup used for range *value ∈ [0,2⁵²)* decomposed into 5·10-bit + 1·2-bit limbs via 1024-entry table; 8-bit S-boxes for non-native field reduction. IPA over Pallas enables recursive proof of block chain *C=2¹⁰* Orchard actions aggregated into single 5KB proof verified on-chain via *Pallas* native verifier [7].

## 5 Empirical Evaluation / Formal Proofs

**Setup:** Benchmarks from Halo2 book [4] on AWS *c5.9xlarge*, Pasta *Pallas* scalar ops via *pasta_curves* crate 0.5, proof sizes measured after Blake2b Fiat-Shamir transcript. Datasets: 2¹²..2²⁰ circuit sizes random PLONK constraints, 8-bit range table *d=256* reused.

*Quantitative findings:*

- Plookup reduces XOR 32-bit constraints from *64+3 per bit* PLONK naive (192 constraints) to *1 lookup per 8 bits* + 2 copying constraints = *4 lookups + 2 gates* (6 rows) → *32×* improvement [2][6].
- Custom gate 5-wire PLONKish S-box (*x⁵*) uses 1 row vs R1CS 3 rows with auxiliary wires; prover time -18% due to fewer FFT domain size despite degree 5 vs degree 2 (tradeoff degree higher → larger quotient polynomial splits) [4].
- IPA prover for *n=1M* constraints: *~8.2s* on single core vs KZG *~5.1s* (KZG faster prover due to MSM only, no folding), but IPA verifier without pairing: *~8ms* vs KZG *~2ms* pairing dominated [5][9]; aggregation amortized 1000 proofs verifier 1000×KZG pairing would be 2s vs IPA accumulated 120ms [7].
- Proof size growth: *log n* = 10→20 increases IPA from 1808 bytes to 4704 bytes lineal vs KZG constant 672 bytes [5].
- Recursion efficiency: Pallas↔Vesta cycle native verification 1.2M constraints vs BLS12-381 emulation 110M constraints → *~90×* reduction, enabling Zcash Halo2 recursion on L1 chain [7][9].

> **Theorem 3 (Halo2 Soundness):** If the IPA is computationally binding under DLOG and grand-product arguments are sound with Schwartz-Zippel error ≤ *(n·deg)/|F|*, and Fiat-Shamir transcript uses random oracle, then Halo2 proving system is knowledge-sound with extraction error *O(q²·n/|F|)* where *q* queries [4].

*Proof sketch:* Extract polynomials via forking lemma for IPA; rewind prover to obtain multiple evaluations *⟨a,b(u_i)⟩* for distinct challenges *u_i* reconstruct *a* via Lagrange interpolation in exponent over folding tree, reducing to DLOG breaking if binding broken. Permutation argument extraction similar to PLONK: if *Z* satisfies recurrence but σ(W)≠W, rational identity fails with overwhelming probability over *β,γ* [1].

## 6 Limitations and Open Problems

- **Transparent proof size.** IPA’s *O(log n)* proof remains larger than KZG *O(1)*, prohibitive for L1 verification gas metering (Ethereum EIP-4844 KZG preferred). Folding schemes *Nova, Sangria, Protostar* trade prover overhead for smaller accumulator [9]. Could IPA be combined with *Dory* inner-product batching for *O(log n)* verifier but *O(1)* proof? Open.
- **Prover sorting for Plookup.** Sorting *s* is *O(n log n)* and non-arithmetizable dominating prover time for tables *n≈2²⁰* range checks. LogUp eliminates sorting but introduces rational functions degree blowup and stricter field requirement *F* not containing small divisors. cq precomputation mitigates only fixed tables [6].
- **Custom gate soundness vs completeness.** High-degree custom gates degree *5* increase quotient degree *t(X)* pieces from 4 to 11 in Halo2, expanding FFT domain from *n* to *3n* and erasing density gains; balancing gate degree vs row count NP-hard, heuristic auto-chip synthesizer lacking formal optimality proof [4].
- **Blinding overhead.** Zero-knowledge requires *3-9* extra rows and permutation duplicate cycles [8][9]; each blinding row adds *O(1)* commitments, modest but for small circuits *n<2¹⁰* relative overhead 5-10% proof size. Can we reuse Blinder-Boneh optimistic ZK approach with *t=1*? Requires stronger assumption.
- **Pasta cycle security.** Pallas/Vesta security ≈ 128-bit estimated but not battle-tested like BLS12-381; cycle requirement of two curves complicates wallet implementation duplicating curve arithmetic, and cycle finding relies on complex CM with discriminants [7]. Quantum incompliance remains: both KZG and IPA break under Shor; lattice-based PLONKish attempts via *Goldilocks* field FRI transparent but larger proofs [9].

Open directions ordered:

1. Formalize optimal lookup strategy selection as MILP: variables table size *d*, query frequency *q*, gate savings Δrows, output hybrid PLONK/Plookup/cq choice minimizing prover time + verifier gas.
2. Integrate VRF-sampled verification from *Verkle Tries* use of IPA vector commitments [9] to Ethereum state proofs.
3. Mechanize Halo2 security in *EasyCrypt* formal verification—current proofs paper-pencil [4].
4. Bridge KZG and IPA via *KZG+IPA hybrid*: commit with KZG for succinctness but IPA for recursion, exploiting Pasta cycle KZG also possible on cycle? Recent work *Pasta KZG* explores but trusted setup reintroduced.

## 7 Conclusion
We presented a *PLONK-centric* reinterpretation of modern zk-SNARK arithmetization through generalized permutation arguments, custom-gate towers, Plookup subset checks, and transparent IPA commitments. By requiring grand-product constraints that simultaneously encode wiring and table containment, Halo2 eliminates per-circuit trusted setup while achieving production-grade prover performance *~8s* for 2²⁰ rows and recursive accumulation feasible on mobile devices.

Our framework demonstrates *composability*: any circuit expressed as fan-in fan-out relations can be lifted into PLONKish form with tables, and polynomial commitments can be swapped KZG→IPA→FRI without altering high-level constraint system [1][4][9]. The result invites rethinking of SNARK design: arithmetization not as *fixed R1CS* but as *programmable constraint language* where security follows from universal permutation soundness and polynomial binding.

> **Future Ethical Note:** As SNARKs underpin rollups securing billions, ensuring transparent setup and auditable lookup implementation is not merely engineering—it safeguards decentralization against covert trapdoors.
