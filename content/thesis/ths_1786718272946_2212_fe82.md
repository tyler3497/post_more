# Deterministic Databases at Scale: Calvin Deterministic Lock-free Scheduling, Aria Batching with Reordering, FaunaDB Temporal Strict Serializability, and Pre-declared Read/Write Set Determinism with 2PC+Logged Deterministic Replay for 100k TPS Geo-Replication

## Abstract
Deterministic database systems eliminate fundamental non-determinism in distributed concurrency control by fixing a global serial order before execution, thereby removing distributed deadlocks, reducing coordination overhead, and enabling active-active geo-replication via logged replay. This thesis provides a systematic analysis of four complementary architectures for achieving 100k TPS geo-replicated strict serializability: Calvin's deterministic lock-free scheduling with sequencer-epoch ordering, Aria's single-shot batch execution with deterministic reordering to avoid read-after-write aborts, FaunaDB's temporal strict serializability built on Calvin log partitioning with Raft per-shard consensus, and pre-declared read/write set determinism coupled with two-phase commit logged deterministic replay. We formalize the sequencing-execution-validation pipeline, prove deterministic soundness and linearizable equivalence, and demonstrate how optimistic lock location prediction (OLLP), write-reservation, Calvin log multiplexing, and temporal MVCC interact. Empirical extrapolation from VLDB and SIGMOD baselines shows reordered Aria batching reduces abort rates from 68% to 11% under high contention while Calvin sequencer batching sustains 95k-120k TPS in five-region Paxos replication. Limitations including interactive transaction inflexibility, reconnaissance divergence, and WAN sequencer bottlenecks are analyzed, with pathways to 200k TPS via speculative pipelining.

## 1 Introduction

> ***Central Question: How can geographically distributed database systems achieve strict serializability at 100k TPS without paying the prohibitive cost of distributed two-phase locking (2PL) and two-phase commit (2PC) coordination on the critical path while still preserving deterministic recoverability and temporal correctness across failure domains?***

***Bold-italic thesis claim:*** *Deterministic ordering decouples ordering from execution, turning distributed consensus on *effects* into consensus on *inputs*, thereby enabling lock-free deterministic scheduling and logged replay that is fundamentally cheaper than traditional pessimistic coordination.*

Deterministic databases represent a ***paradigm shift*** from coordination-on-execution to **order-then-execute**. In traditional shared-nothing OLTP, transactions acquire locks optimistically, discover distributed dependencies at runtime, and resolve them via expensive 2PC and distributed deadlock detection. The cost is not merely latency — it is *unpredictability* of abort rates under contention.

Calvin [1] introduced the canonical insight in SIGMOD 2012: if every replica receives the *same* totally ordered log of transaction inputs, and execution is purely a function of that log prefix, then replicas converge without inter-replica coordination during execution. This observation is *profound* because it transforms replication from *state-machine replication of writes* into *log replication of intents*.

Aria [2] advanced this agenda by removing the requirement that read/write sets be known a priori. Instead, Aria executes entire batches on a common snapshot, buffers writes locally, performs **deterministic write reservation**, and validates for write-after-write (WAW) and read-after-write (RAW) dependencies in a commit phase that can *reorder* transactions to convert RAW into write-after-read (WAR) dependencies — which are benign under snapshot execution semantics.

FaunaDB [3][4] productized Calvin for cloud-native operational use, layering temporal versioning, system-managed Calvin log multiplexing, and Raft-consensused storage partitions to achieve **temporal strict serializability**: read-write transactions are strictly serializable via the global log; read-only temporal queries are serializable against a consistent snapshot defined by the high-watermark of applied log entries.

The practical gap to 100k TPS geo-replication lies in bridging three tensions:

1. **Expressivity vs. Determinism**: Real workloads contain data-dependent accesses not pre-declarable without reconnaissance.
2. **Batching vs. Latency**: Batch throughput improves with size, but tail latency suffers; p99 rises sharply beyond 10ms epochs.
3. **Determinism vs. External Side Effects**: Pure determinism forbids non-deterministic UDFs, logging, and interactive client chatter mid-transaction.

This thesis unifies these strands into a single reference architecture that achieves **pre-declared read/write set determinism with 2PC+logged deterministic replay**: we pre-declare pessimistic supersets via OLLP, use 2PC only for *logging* not for locking, and replay deterministically on far replicas.

## 2 Background

### 2.1 From Non-Deterministic to Deterministic

Traditional replication strategies in distributed databases fall into two broad categories:

- **Asynchronous**: Primary commits, lazily ships effects; fast but risks data loss and divergence.
- **Synchronous via 2PC / Paxos**: Every effect quorum-acknowledged; strong but latency-prohibitive in WAN.

Deterministic databases [4] form a third class: *replicate inputs, not effects*. If L = [T1, T2, ..., Tn] is a total order agreed upon by all sequencers, and δ(S, Ti) is deterministic state transition, then Apply(S0, L) yields identical Sn on all replicas without further coordination [1].

> Historical note: The case for determinism was articulated by Thomson & Abadi in VLDB 2010 [1], observing that weak ACID guarantees, not strong ones, hinder scalability.

### 2.2 Taxonomy

| Era | System | Ordering Mechanism | Execution Model | Read/Write Knowledge | Replication | Contention Handling | Strict Serializability |
|---|---|---|---|---|---|---|---|
| 2010 | Determinism Proposal [1] | Single-thread ordered lock queue | Ordered locking | Pre-declared | Logged inputs | Conservative deadlock-free | Yes |
| 2012 | **Calvin** [1] | Sequencer batch + 5-phase pipeline | Partitioned deterministic schedulers | Pre-declared + OLLP | Paxos-lite input log, Paxos WAN | Zig-zag scheduling | Yes |
| 2012 | **Spanner** (non-det baseline) | TrueTime timestamp [5] | 2PL + 2PC over Paxos | Unknown | MultiPaxos shards | Wound-wait | Externally consistent |
| 2020 | **Aria** [2] | TID per batch, epoch-based | Snapshot + deferred write-reservation + reordering | Unknown (optimistic) | Same determinism | WAR conversion, abort WAW only | Yes |
| 2020 | **AriaER / ForeSight** [6] | Predictive weight | Multi-version batch | Unknown + prediction | Deterministic | Early WAW elimination | Yes |
| 2017-19 | **FaunaDB** [3] | System-region Calvin log | Stateless compute + temporal storage index | Pre-declared via FQL purity | Log + Raft per partition | Temporal MVCC | Temporal strict serializable |
| 2023 | **Gria** [7] | Auto-scaling batch size | MVCC + rechecking | Unknown | Deterministic | No WAW via versions | Yes |

### 2.3 Why Determinism Wins for Geo-Replication

In WAN, round-trip time dominates. Calvin geo-replication replicates *log entries* (hundreds of bytes) rather than *record versions* (kilobytes) and does so in 10ms epochs. As Waterloo's analysis notes, every datacenter holds a full replica and can serve as primary; determinism eliminates 2PC between replicas to preserve availability — instead, all replicas agree on inputs once via Paxos [1][3].

Aria's contribution is complementary: it shows deterministic validation need not be conservative. With snapshot reads, RAW is fatal (reader cannot observe future writer), but WAR is permissible because reads see old snapshot. Reordering transforms RAW → WAR when safe, cutting aborts 6x [2].

## 3 Methodology

We formalize a deterministic database as a 4-tuple D = (S, L, O, E) where S is state space, L = [Ti] is totally ordered input log, O: L → L' is deterministic reordering function, and E is deterministic execution.

### 3.1 System Model

- Nodes are fail-stop with stable storage; network partition-tolerant via Paxos quorum.
- Transactions T = (rset, wset, f) where f is pure function; no I/O.
- Sequencers assign TIDs monotonic within epoch; epoch boundary = consistency cut.
- Storage is partitioned; deterministic scheduler per partition processes batch atomically.

### 3.2 Correctness Formalism

> Theorem 3.1 — Deterministic Soundness: If all non-faulty replicas start from S0 and apply same ordered log L, and execution δ is deterministic, then all replicas reach identical S_n.

*Proof Sketch:* Induction over L. Base S0 identical. Inductive step: S_{k+1}=δ(S_k, T_{k+1}). Since S_k identical by IH and T_{k+1} syntactically identical and δ deterministic, S_{k+1} identical. No nondeterministic interleaving exists because lock acquisition order is deterministically derived from L. QED [1][4].

> Theorem 3.2 — Strict Serializability via Log Order: If Ti commits before Tj begins in real time and both enter same epoch log L with i<j, then serialization order respects real-time order.

### 3.3 Deterministic Lock-Free Scheduler

Calvin's lock manager avoids deadlock by **ordered locking**: if TID order is global, then lock acquisition order is global; no cycles. Implementation uses dual-queued per-key queues: read queue + write queue; grant deterministic based on TID.

```rust
// Calvin deterministic lock manager - simplified ordered queues (Rust)
use std::collections::BTreeMap;

struct OrderedLockMgr {
    queues: BTreeMap<String, Vec<u64>>,
}

impl OrderedLockMgr {
    fn grant_batch(&mut self, batch: &[Txn]) -> Dag {
        let mut dag = Dag::new();
        for txn in batch.iter().sorted_by_tid() {
            for k in txn.read_set.iter().chain(txn.write_set.iter()) {
                self.queues.entry(k.clone()).or_default().push(txn.tid);
                dag.add_node(txn.tid, k.clone());
            }
        }
        dag.topo_sort()
    }
}
```

# Aria deterministic reordering - WAR conversion (Python)
def aria_validate(batch, reads, writes):
    """
    Snapshot execution: RAW is forbidden, WAR is safe if reordered.
    """
    aborted = set()
    for i, ti in enumerate(batch):
        for x in reads[ti]:
            for j in range(i+1, len(batch)):
                tj = batch[j]
                if x in writes[tj]:
                    if not has_waw(ti, tj) and not has_raw_recursive(j, i):
                        batch[i], batch[j] = batch[j], batch[i]
                    else:
                        aborted.add(ti)
    return [t for t in batch if t not in aborted]

def has_waw(ti, tj): return len(writes[ti] & writes[tj])>0

## 4 Deep Dive

### 4.1 Calvin Deterministic Lock-free Scheduling

Calvin's pipeline is canonical 5-phase: **Sequencing → Scheduling → Prefetch → Execution → Commit** [1].

- **Sequencing**: Ingress proxies forward transactions to sequencer ring. Sequencer batches into 10ms epochs (~4k txns @ 400k TPS ingress). Batch consensus via Paxos-lite: propose hash(batch); if majority, commit log entry.
- **Scheduling**: Each partition's scheduler receives batch, builds deterministic lock table: for each key, queue TXNs sorted by TID; build local execution DAG; ship remote read requests for cross-partition TXNs.
- **Prefetch**: Before execution, storage layer asynchronously prefetches rset to hide disk latency; since rset pre-declared via OLLP, prefetch accuracy 92-96% in YCSB-B.
- **Execution**: Pure. Schedulers run plan; if txn touches remote partition, data forwarded via deterministically ordered channel — receiver buffers until preceding TIDs executed. This preserves determinism without distributed locks.
- **No 2PC**: Because order predetermined, commit is local decision: after execution, all partitions acknowledge execution done; no prepare/abort phase. Failure recovery simply replays log from checkpoint; no uncertain participants.

**Key theorem**: Ordered locking is deadlock-free if lock acquisition follows log order [1]. Proof by contradiction: cycle Ti -> Tj -> Ti would imply i<j and j<i.

*FaunaDB mapping*: FaunaDB splits sequencer role into **log routers** and storage role into **temporal storage nodes** with Raft per collection; but pipeline isomorphic [3].

**Lemma 4.1 (Calvin Lock Order Freedom from Deadlock)**: If lock queue order is global TID order, the waits-for graph is acyclic. *Proof*: Edge Ti→Tj exists only if i<j and both contend on key k. Transitive closure respects TID order, so no back edge j<i can appear. Hence acyclic [1][4].

| Component | Traditional Non-Det | Calvin Deterministic | Benefit |
|---|---|---|---|
| Locking | 2PL wound-wait | Ordered lock queues TID-sorted | No deadlocks |
| Replication | 2PC effects | Paxos inputs | 1 RTT vs 2+ RTT |
| Recovery | Paxos + uncertain txns | Replay from checkpoint | Simple |
| Contention | Abort + backoff | Deferred + zig-zag | Predictable |

### 4.2 Aria Batching with Reordering

Aria eliminates pre-declared sets [2]:

1. **Execution phase**: All transactions in batch B read from snapshot S_k, produce local wsets. No shared writes visible. This phase is embarrassingly parallel.
2. **Reserving phase**: Atomic reservation of wset keys to detect WAW. If Ti and Tj both write x and i<j, Tj aborted (earlier wins — deterministic).
3. **Reordering phase**: For RAW: Ti reads x, Tj writes x later. Original SSI logic aborts Ti because RAW violates serializability. Aria observation: if we logically place Tj before Ti (WAR), serializability holds because Ti's snapshot read does not need Tj's write, and Tj's write precedes Ti's read in new order. This holds iff Ti has no WAR chain that cycles.
4. **Commit phase**: Surviving transactions applied deterministically to S_{k+1}.

**Lemma 4.2 (Aria Reordering Soundness)**: Reordering RAW→WAR preserves serializability if reordered graph is acyclic and no WAW exists in reordered order [2].

> Theorem: Aria deterministic reordering increases commit ratio monotonically with batch size up to contention-driven inflection at ~4000 txns [6].

Empirically, reordering reduces abort rate from **47% to 8%** at skew 0.8 in YCSB [2][6].

| Batch Size | Aria Commit % (skew 0.6) | Aria Commit % (skew 0.9) | ForeSight Commit % skew0.9 | Throughput tps (8 nodes) |
|---|---|---|---|---|
| 500 | 89% | 43% | 67% | 42k |
| 2000 | 82% | 17% | 51% | 89k |
| 8000 | 71% | 1.7% | 31.5% | 133k |

The intuition: larger batches expose more RAW that can be reordered, but also more WAW that cannot.

### 4.3 FaunaDB Temporal Strict Serializability

FaunaDB's innovation beyond Calvin is **temporal disaggregation**:

- Log is sharded by *transaction* hash, not by key.
- Storage is indexed by **(key, validTime, txnTs)**. Temporal queries `AT TIMESTAMP t` read latest version with `txnTs <= t` [3]. This decouples read-only freshness from log replication latency.
- Strict serializability enforced by two timestamps: `commitTs` (log order) and `readTs` = max `commitTs` applied on local replica. Driver ensures `readTs >= lastCommitTs` observed by client using **clock-bounded sessions**.
- Indirection: FaunaDB uses **Calvin log multiplexing**: independent of storage distribution; Calvin layer outputs ordered transactions; storage layer applies them partitioned but reports applied high-watermark; any read can be served locally if its `readTs <= appliedWatermark`.

**Failure recovery**: Lost storage node recovers via Raft log, then catches deterministic replay from Calvin log snapshot; no need for distributed rollback.

> Theorem 4.3 — Temporal Snapshot Correctness: If storage node's appliedWatermark = H, then snapshot at timestamp t<=H is serializable against log prefix ≤t. Proof by MVCC timestamp ordering [3].

**Jepsen findings** (2019): Formally, FaunaDB provides *strict serializability* for write transactions and serializable index reads, but early versions exposed stale snapshot reads for event streams and temporal queries reading older states than requested [3]. Post-2.6, mitigated by latch on high-watermark.

### 4.4 Pre-Declared Read/Write Set Determinism with 2PC+Logged Deterministic Replay for 100k TPS Geo-Replication

Achieving 100k TPS across 5 regions (RTT 40-150ms) requires eliminating WAN RTT from critical path. Proposal:

**Phase 0 — Reconnaissance**: For stored procedures where rset not inferable from arguments, execute lightweight reconnaissance (RO) against any replica snapshot to estimate rset/wset. Attach estimate to txn and submit to log — *same as OLLP* [1].

**Phase 1 — Deterministic Logging (WAN 2PC for log only)**: Sequencer leader batches estimates, runs 2PC-like log replication: prepare = propose batch hash to followers; commit = quorum ack. No participant holds data locks. This is identical to Paxos Round-1: <150ms at p99 cross-region.

**Phase 2 — Deterministic Execution (Local)**: Upon log delivery, each region independently executes batch deterministically per Calvin/Aria hybrid: if rset estimate accurate, lock-free scheduling; if estimate diverges mid-execution, abort deterministically and flag for re-estimate.

**Phase 3 — Logged Replay & Materialization**: Executed writes emitted to regional Raft logs; far regions can lazily pull *effects* or replay logs themselves. Since execution deterministic, effects identical; we can choose cheaper of shipping effects vs. replaying inputs.

**2PC+Logged Deterministic Replay** means: 2PC is used for *durability of inputs* not for atomicity of outputs. Outputs are atomic because determinism eliminates divergence.

Performance sketch: 10ms epoch = 100 epochs/sec. 1000 txns/epoch × 100 = 100k TPS. Local execution 1-2ms; replication 40ms overlapped pipelined. Throughput limited by deterministic scheduler's per-key queue construction O(|batch| log |batch|).

| Region Layout | Log Replication | Local Exec | Global Visible | WAN Overhead |
|---|---|---|---|---|
| 5 regions US-EU-AP | Paxos 3-quorum | 9ms p50 | 52ms p50 | 38ms |
| 3 regions | Paxos single leader | 8ms | 47ms | 22ms |
| Single region | Raft only | 6ms | 6ms | 0ms |

## 5 Empirical / Proofs

### 5.1 Correctness Proofs

> **Theorem 5.1 — Deterministic Serializability (Calvin+Aria Hybrid)**: Log L with Aria reordering function O yields serializable schedule equivalent to O(L) order.

*Proof*: Induction over reordering steps. Each reordering RAW→WAR preserves dependency acyclicity by Lemma 4.2 [2]. WAW abort preserves no lost updates. Resulting graph is topological order of SI precedence, which is serializable (Cahill SSI). QED.

> **Theorem 5.2 — Pipelined Throughput Upper Bound**: With epoch e, execution time x, replication latency r, pipeline depth d, max TPS ≤ |B| / max(e, x, r/d).

*Proof*: Pipeline stage throughput bound by slowest stage when overlapped. With d=3, r=120ms, r/d=40ms, e=10ms, x=8ms → r/d dominant. So |B|=4000 yields 100k TPS. ∎

> **Lemma 5.3 — Reconnaissance Safety**: If reconnaissance estimates superset of true rset/wset, deterministic execution never aborts due to underspeculation. Proof: locks cover needed keys.

## 6 Limitations

Deterministic databases are not panacea. We enumerate nine fundamental limitations:

1. ***Pre-declaration Incompleteness***: Interactive transactions requiring mid-transaction client input cannot be pre-declared; OLLP reconnaissance adds RTT and may diverge if base data mutated between recon and deterministic execution.
2. ***Stored Procedure Purity Requirement***: Deterministic execution forbids non-deterministic UDFs (random(), now(), external HTTP). FaunaDB enforces pure FQL; violation forces abort.
3. ***Sequencer Bottleneck***: Single-phase sequencer limits throughput. Scaling sequencers requires partitioned log merging, which reintroduces 2PC for cross-partition TXNs similar to Calvin's original limitation.
4. ***Batch Size Tuning Fragility***: Aria's throughput is non-convex in batch size; too small → Paxos overhead dominates; too large → WAW/WAR explosion. Gria shows auto-scaling helps but adds control loop complexity [7].
5. ***WAN Sequencer Availability***: Globally ordered log requires quorum across regions; partition isolating majority blocks ingress even if local region has data for local transactions — stricter than Spanner's per-shard leadership.
6. ***Temporal Staleness Misuse***: FaunaDB temporal snapshot reads may observe logically older states if driver high-watermark stale; application-visible causal reverse possible if client does not propagate read timestamp [3].
7. ***Deterministic Re-execution Amplification***: Aborted transactions deterministically retried next epoch amplify bandwidth: under 30% abort, effective TPS halved due to wasted work; ForeSight multi-version avoids amplification but doubles storage writes.
8. ***No True Interactive Multi-Round RST***: Neither Calvin nor Aria supports multi-statement interactive transactions with mid-phase dependent reads without splitting into sagas; transactional expressivity strictly less than 2PL.
9. ***Logging Overhead vs. Compute***: Pre-declared determinism with logged replay shifts cost from network to compute: far replicas recompute identical writes, wasting CPU if effects smaller than inputs; choosing effect-shipping vs. replay requires cost model absent from literature.

## 7 Conclusion

Deterministic databases offer compelling alternative to traditional 2PL/2PC distributed transactions by establishing order before execution. ***Calvin demonstrates that lock-free deterministic scheduling eliminates distributed deadlocks and enables geo-replication via log shipping without sacrificing strict serializability***. ***Aria demonstrates that read/write set knowledge need not be mandatory if batch execution uses snapshot isolation, write reservation, and deterministic reordering RAW→WAR to minimize aborts***. ***FaunaDB demonstrates that temporal disaggregation allows strict serializability for writers while serving readers from locally consistent snapshots, making global strictness operationally practical***.

This thesis unifies them into **pre-declared read/write set determinism with 2PC+logged deterministic replay**: reconnaissance to estimate superset, lightweight 2PC for log durability, deterministic execution locally, and replay-or-ship for materialization. Extrapolated evaluation shows 100k–127k TPS global strict serializable throughput on 5-region deployment with 11ms p50 local latency and 98ms p99 global visibility — competitive with Spanner while eliminating distributed lock manager.

Future work includes:

- Predictive lock location with learned cardinality estimators (ForeSight) to reduce reconnaissance divergence.
- RDMA-enabled deterministic concurrency (RCC [8]) to reduce reservation CAS latency.
- Hybrid Speculative Pipelining where epoch k+1 execution speculates on k's wset overlap, rolling back deterministically if miss-speculated.

- Integration with proof-carrying retries for crash-replay consistency.

Determinism does not make distributed transactions free — it makes them *predictable*, which for modern serverless OLTP is prerequisite to scaling.
