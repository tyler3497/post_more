# Unikernel Specialization with MirageOS and Solo5: Compile-Time Configuration, Single-Address-Space Memory Safety, and Attack Surface Reduction for Cloud Microservices

## Abstract

Unikernels restructure the operating system as a library linked directly against application code, producing virtual machine images specialized at compile time for a single service. This thesis develops a rigorous account of unikernel specialization through the MirageOS library operating system and the Solo5 sandboxed execution environment, the most mature components of the modern OCaml unikernel stack [1][5]. We formalize the compilation pipeline by which MirageOS functor-based configuration selects exactly the drivers, protocol stacks, and storage backends a service requires, analyze how single-address-space execution converts language-level memory safety into whole-system guarantees, and dissect the Solo5 tender architecture that decouples guest unikernels from host virtualization with a minimal hypercall surface. We evaluate specialization empirically: megabyte-scale images, millisecond boot latencies, and an attack surface measured in tens of thousands rather than millions of lines of code [3][4]. Finally, we prove a sealing theorem establishing that a correctly initialized unikernel cannot transition any page to a writable-and-executable state, and we delineate the boundary conditions and ecosystem gaps limiting unikernel adoption for general cloud microservices.

## 1 Introduction

Cloud computing consolidated on the virtual machine as the unit of deployment: a full guest operating system, carrying decades of accumulated drivers, system calls, and user-space tooling, booted to run a single application. This layering is economically convenient but technically incoherent. When an application is the sole tenant of its kernel, the generality of that kernel is not an asset; it is unexercised code that consumes memory, lengthens boot, and, most seriously, widens the attack surface available to adversaries [2].

The unikernel proposes the opposite construction. Rather than multiplexing one general-purpose kernel among many applications, it *specializes* the kernel to the application at compile time, links the two into a single binary, and runs that binary directly on a hypervisor as a minimal virtual machine [1]. MirageOS realizes this program in the OCaml programming language, and Solo5 provides the portable hypervisor abstraction beneath it [5][7]. Together they demonstrate that an operating system need not be a fixed artifact: it can be a *configuration* of library components, synthesized per service.

> Definition: A **unikernel** is a single-address-space machine image, produced by statically linking application logic against a selected set of library operating-system components, that executes directly on a hypervisor with no intervening general-purpose kernel and no user-kernel privilege separation [1].

This thesis makes four contributions. First, we give a precise semantics of MirageOS compile-time configuration, showing how OCaml functors and the Functoria device-description language turn service specifications into link-time component selections with whole-program dead-code elimination. Second, we analyze the single-address-space memory-safety argument, separating what the language guarantees from what the runtime and hypervisor must still enforce. Third, we dissect the Solo5 architecture — its guest-facing API, bindings, and tenders — as the mechanism that makes one unikernel binary portable across Xen, KVM, and hardware-virtualized targets. Fourth, we prove a page-table sealing theorem and quantify attack-surface reduction against containers and full virtual machines, using published measurements from the Unikraft and Jitsu projects as calibration points [3][4].

## 2 Background

### 2.1 From virtual machines to containers to unikernels

Hardware virtualization gives strong isolation at the cost of a full guest kernel per tenant. Containers invert the tradeoff: they share one host kernel and partition applications with namespaces and control groups, achieving near-native density but inheriting every vulnerability in the shared kernel. Unikernels occupy the third point of the triangle: each application carries its own minimal kernel, so tenants are isolated by the hypervisor exactly as virtual machines are, while image sizes approach those of containers because only the used components are compiled in [2].

The following table summarizes the design space:

| Property | Virtual machine | Container | Unikernel |
|---|---|---|---|
| Isolation boundary | Hypervisor | Shared kernel (namespaces) | Hypervisor |
| Kernel generality | Full guest kernel | Shared host kernel | Per-application libOS |
| Image size | Gigabytes | Tens of megabytes | Kilobytes to megabytes |
| Boot latency | Tens of seconds | Milliseconds | Milliseconds |
| Attack surface | Full guest kernel | Host kernel syscalls | Linked libraries only |

### 2.2 MirageOS in brief

MirageOS is a library operating system written in OCaml. Every MirageOS service — a DNS server, a TLS endpoint, a web server — is compiled into a unikernel image targeting Xen, KVM via Solo5, or a Unix binary for development [7]. The entire stack, from device drivers through the TCP/IP implementation to the application, is ordinary OCaml code: there is no C kernel underneath, no system-call boundary, and no separate process abstraction. The project self-hosted its own infrastructure on unikernels from its earliest releases, and Docker's desktop products later shipped MirageOS-based unikernels for VPN networking, demonstrating industrial viability [1].

### 2.3 Solo5 in brief

Solo5 began as Dan Williams' project at IBM Research to run MirageOS on Linux/KVM, and grew into a general sandboxed execution environment for unikernels [5]. Its design distinguishes three roles: a *guest-facing API* (a small C header, `solo5.h`, offering block, network, console, clock, and lifecycle operations), *bindings* that implement that API for a given target, and *tenders* — small host-side monitor processes that instantiate the guest. The `hvt` tender, for example, uses hardware virtualization to run the unikernel with a minimal device model: virtio or a still simpler paravirtual interface. Because the tender is deliberately small (a few thousand lines), the trusted computing base between guest and host is orders of magnitude smaller than a conventional virtual-machine monitor [5].

## 3 Methodology

Our method combines archival analysis of the primary literature and source repositories with constructive modeling and a small formal argument [1][3][4][5][6][7].

1. **Component census.** We reconstruct the MirageOS configuration pipeline from its module-signature layer through Functoria's device graph to the final link step, identifying exactly which compile-time decisions determine the runtime attack surface.
2. **Memory-safety decomposition.** We separate the safety claim into language-level guarantees (type safety, bounds checking, garbage collection), runtime guarantees (page-table layout, cooperative scheduling), and hypervisor guarantees (isolation between guests), so that each can be evaluated independently.
3. **Architectural reconstruction of Solo5.** We map the guest API to its bindings and tenders, enumerating the hypercall-equivalent surface a guest can exercise.
4. **Quantitative comparison.** We normalize published measurements — image sizes, boot latencies, lines of code — from the Unikraft EuroSys evaluation and the Jitsu NSDI deployment onto a common attack-surface metric [3][4].
5. **Formal sealing argument.** We prove that, under stated assumptions, a unikernel that seals its page tables at initialization cannot thereafter introduce a writable-and-executable mapping.

All quantitative claims are traceable to cited measurements; where we extrapolate (for example, projecting Solo5 tender line counts onto CVE exposure), we label the extrapolation explicitly.

## 4 Deep Dive

### 4.1 Functor-driven compile-time configuration

The central technical idea of MirageOS is that operating-system construction is *module composition*. OCaml's module system provides functors — functions from modules to modules — and MirageOS expresses every OS service as a functor parameterized over its dependencies. A TCP/IP stack is a functor over an Ethernet device; a TLS endpoint is a functor over a TCP flow; a web server is a functor over a network stack and a filesystem. The application author writes a `config.ml` describing the desired service graph, and Functoria elaborates it into concrete module applications [7].

```ocaml
(* config.ml: a TLS-terminating static web server, specialized at compile time *)
open Mirage

let stack = generic_stackv4 default_network
let https =
  http_server (conduit_direct ~tls:true stack)
  |> crunch "htdocs"
  |> http (`HTTPS (`Port 443))

let () = register "web" [ https ]
```

At build time, `mirage configure` evaluates this description and emits a `main.ml` that applies the functors in dependency order. Crucially, any component not reachable from the configuration is never compiled: there is no linker-visible DHCP client in a unikernel with a static IP, no filesystem code in a pure packet forwarder. This is whole-program dead-code elimination applied to the operating system itself, and it is the mechanism by which compile-time configuration becomes attack-surface reduction [1][2].

> Lemma: Let `G` be the device dependency graph elaborated from a MirageOS `config.ml`, and let `L(G)` be the set of object files linked into the final image. Then every element of `L(G)` is reachable from the declared service roots of `G`, and no unreachable library component contributes code to the image.

The lemma is a direct consequence of OCaml's separate compilation with cross-module inlining and dead-code elimination: unreferenced compilation units are dropped by the linker. Its security significance is that *configuration errors fail closed*: omitting a component removes functionality rather than silently enabling a default.

### 4.2 Single-address-space memory safety

A MirageOS unikernel runs in a single address space with a single virtual CPU. There is no user-kernel boundary, no address-space separation between the application and its TCP stack, and no preemptive scheduler: concurrency is cooperative, implemented with an event loop over promises (the `Lwt` library). This design looks, at first glance, like a retreat to the insecurities of MS-DOS. Its safety rests on a different foundation: the *language*.

Because everything in the image is OCaml, every memory access in the steady state is mediated by the language's guarantees: static type safety prevents interpreting integers as pointers, bounds checking prevents buffer overruns, and the garbage collector prevents use-after-free [1]. The attacker's classic primitives — corrupting a return address, overflowing a heap buffer into adjacent metadata — are not expressible in safe OCaml. The residual risk concentrates at three narrow interfaces: the foreign-function interface to C (used sparingly, for example in cryptographic primitives), the OCaml runtime itself, and the paravirtual device interface to the hypervisor.

To harden the runtime layer, MirageOS employs two mechanisms. *Sealing* fixes the page tables at initialization so that no page is both writable and executable, and then invokes a hypercall that forbids all further page-table modification [2]. *Compile-time address-space randomization* lays out the image differently on every build, so that even an attacker who discovers a memory-corruption primitive in the C FFI cannot reliably target code addresses. We formalize sealing in Section 5.

### 4.3 Solo5: the hypervisor abstraction layer

Portability is the historic weakness of unikernels: a libOS written against the Xen hypercall interface cannot run on KVM. Solo5 solves this by interposing a stable, minimal guest API between the unikernel and the host [5].

The architecture has three strata. At the top, the guest links against `solo5.h`, whose surface is deliberately tiny: `solo5_net_write`, `solo5_block_read`, `solo5_console_write`, `solo5_clock_monotonic`, `solo5_yield`, `solo5_abort`, and a handful of others. In the middle, *bindings* translate these calls into target-specific mechanisms: hypercalls on Xen, `vmcall`-style exits under the `hvt` tender, plain system calls under the `spt` (sandboxed process tender) target. At the bottom, the *tender* is a small host process that sets up guest memory, loads the ELF image, creates the virtual CPU, and services exits. Because the tender implements only a paravirtual device model — no emulated IDE controller, no VGA, no legacy BIOS — its code size stays in the low thousands of lines, and each tender is independently auditable [5].

```python
# Conceptual model of the Solo5 exit path (illustrative, not the C source)
def solo5_net_write(handle, buf):
    # 1. guest copies packet into a shared ring (no hypervisor involvement)
    ring.enqueue(handle, buf)
    # 2. single hypercall-equivalent exit notifies the tender
    tender.notify(NET_TX, handle)
    # 3. tender performs the host-side I/O; guest never touches host syscalls
```

The security consequence is *defense in depth with small components*: the guest's reachable host interface is the dozen functions of `solo5.h`, and the host's guest-facing code is the tender. Compare this with a container, where the application can invoke hundreds of host system calls through the shared kernel.

### 4.4 Quantifying attack-surface reduction

We now make the reduction quantitative. Three independent evaluations give us calibration data. The Unikraft EuroSys 2021 paper reports application images around one megabyte, resident sets under ten megabytes, and boot times of one to forty milliseconds, with throughput improvements of 1.7x to 2.7x over Linux guests for nginx, SQLite, and Redis [3]. The Jitsu NSDI 2015 deployment booted MirageOS unikernels in the low hundreds of milliseconds on ARM boards, small enough to summon services on demand in response to DNS queries [4]. The MirageOS project itself reports HTTPS-serving images of roughly two megabytes with no C library inside [1].

Attack surface can be approximated by reachable lines of code. A minimal Linux guest carries tens of millions of lines across kernel and user space; a container shares the host kernel's roughly thirty million lines; a MirageOS unikernel links on the order of hundreds of thousands of lines of OCaml, of which the trusted core (runtime plus Solo5 tender) is a few tens of thousands. The ratio is not merely quantitative: the unikernel's code is *selected per service*, so a vulnerability in an unlinked component (say, the DHCP client) is not merely unexploited — it is *absent from the image*.

| Deployment unit | Reachable kernel/TCB code (order) | Per-tenant generality |
|---|---|---|
| Full Linux VM | Tens of millions of lines | General-purpose guest |
| Container on shared kernel | Tens of millions (host kernel) | General-purpose host kernel |
| MirageOS unikernel on Solo5 | Tens of thousands (tender + runtime) | Exactly the linked service |

> Theorem (informal): For a fixed service specification, the set of executable bytes reachable by an attacker who compromises a MirageOS unikernel is bounded above by the linked image size, which is monotone in the Functoria device graph; removing a device from the configuration strictly reduces the bound.

## 5 Empirical Results and Formal Proofs

### 5.1 Empirical results

We consolidate the published measurements into a single comparison. Boot latency determines whether unikernels can serve as the unit of *elastic* scaling — booting per request rather than per deployment. Jitsu demonstrated DNS-triggered unikernel boot on ARM hardware fast enough to mask startup behind connection establishment, effectively making boot latency invisible to clients [4]. Unikraft pushed this further on x86, with total boot times of three to forty milliseconds including virtual-machine-monitor overhead, and showed that specialization need not sacrifice application compatibility: unmodified nginx, SQLite, and Redis ran faster on Unikraft than on Linux guests [3].

Memory footprint determines density. A two-megabyte MirageOS image serving HTTPS [1] means a host with a gigabyte of RAM can in principle hold hundreds of tenants, each isolated by hardware virtualization rather than by kernel namespaces. This is the density argument that makes unikernels competitive with containers while retaining the isolation model of virtual machines [2].

### 5.2 Formal proof: page-table sealing

We now prove the sealing property precisely. Consider a unikernel executing on a hypervisor that provides a `seal` operation with the following semantics: after `seal` is invoked, any guest attempt to modify page tables traps to the hypervisor and is denied.

> Theorem: Let `P` be the page-table configuration established by a MirageOS unikernel during initialization, with the invariant that no page in `P` is simultaneously writable and executable. If the unikernel invokes `seal` before transferring control to untrusted input handling, then for all subsequent execution, no page is writable and executable, and no new executable mapping can be introduced.

*Proof.* We proceed by case analysis on the ways a writable-and-executable (W+X) mapping could arise after sealing. (1) *Modification of an existing mapping*: changing the permissions of a mapped page requires a page-table write, which after `seal` traps and is denied by the hypervisor. (2) *Creation of a new mapping*: installing a new page-table entry likewise requires a page-table write, denied as in case (1). (3) *Modification of a mapping's contents to alter code*: a page containing code is, by the initialization invariant, not writable; writing to it faults. Hence no execution path available to the guest can produce a W+X page. The only remaining vector is the hypervisor itself violating the `seal` semantics, which is excluded by assumption. ∎

The theorem's assumptions are explicit and falsifiable: it trusts the hypervisor's enforcement of `seal`, the correctness of the initialization code that establishes `P`, and the absence of DMA-capable devices that bypass page tables (Solo5's paravirtual model exposes no such device to the guest [5]). Under these assumptions, code injection — the payload of most memory-corruption exploits — is structurally impossible, even if a residual bug exists in the C foreign-function interface. This is the formal core of the unikernel security argument: *language safety removes most bug classes, and sealing removes the exploitability of the remainder* [1][2].

### 5.3 Threat-model boundaries of the proof

The proof does not cover side channels, physical attacks, or hypervisor compromise — the standard exclusions of the virtualization threat model. It also does not cover logic bugs in the application itself: a unikernel implementing an authorization check incorrectly is exactly as vulnerable as any other implementation. What the architecture guarantees is *containment of memory unsafety*, not correctness of application logic.

## 6 Limitations

Unikernels are not a universal replacement for containers, and the limitations are substantive.

**Debuggability.** A single-address-space image with no shell, no `ptrace`, and no core-dump tooling is hard to debug in production. Solo5 mitigates this with live and post-mortem debugging support [5], but the tooling remains primitive compared with Linux's observability ecosystem.

**Ecosystem and POSIX.** MirageOS deliberately eschews POSIX compatibility, which liberates its design but confines it to applications written (or ported) to its libraries [1]. Unikraft takes the opposite approach, pursuing POSIX compatibility to run unmodified applications, and demonstrates that the specialization benefits survive [3]. The community has not converged on which tradeoff is correct.

**Single-core execution.** Classic MirageOS unikernels run on one virtual CPU with cooperative scheduling. Multicore and symmetric multiprocessing support exists in newer targets but complicates the memory-safety story, since data races become possible even in safe languages at the FFI boundary.

**State and persistence.** Unikernels are happiest as stateless services; the Irmin branchable store provides a git-like persistent layer [1], but operating stateful systems (databases with crash-consistency requirements) on unikernels remains research-grade.

**Supply-chain trust.** Dead-code elimination removes *unlinked* code, but every *linked* line is trusted absolutely, including the OCaml compiler and runtime. A compiler bug or a compromised OPAM package affects the entire image, and reproducible-build tooling for the unikernel pipeline is still maturing.

**Operational maturity.** Orchestrators speak containers; there is no Kubernetes-native unikernel scheduler in wide use, though projects have demonstrated integration prototypes. Until deployment tooling matches Docker's ergonomics, unikernels will remain a specialist choice [6].

## 7 Conclusion

This thesis has developed the case for unikernel specialization through MirageOS and Solo5 as a principled response to the mismatch between general-purpose kernels and single-service cloud deployments. Compile-time configuration via OCaml functors turns the operating system from a fixed artifact into a per-service synthesis, with dead-code elimination as its security mechanism. The single address space converts language-level memory safety into a system property, and page-table sealing — which we proved sound under explicit assumptions — removes code injection even in the presence of residual unsafe code. The Solo5 tender architecture shows that portability need not compromise minimality: a dozen-function guest API and a few-thousand-line monitor suffice to run the same image on Xen, KVM, and paravirtual targets [5].

The empirical record supports the theory: megabyte-scale images, millisecond boot times, and measured performance wins over Linux guests [3][4]. The limitations — debugging, POSIX, multicore, orchestration — are real but engineering-shaped, not fundamental. As confidential computing and edge deployment push isolation requirements downward in scale and upward in rigor, the unikernel's founding wager looks increasingly sound: *the most secure code is the code that was never compiled* [1][2].
