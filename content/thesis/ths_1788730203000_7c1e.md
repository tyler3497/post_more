# Polars Lazy Query Engine: Predicate Pushdown, Streaming Spill-to-Disk Execution, Apache Arrow Memory Layout, and Parallel Groupby

## Abstract

Polars is a DataFrame library whose performance derives not from a single trick but from a coherent execution architecture: a lazy query engine that defers all computation into an optimizable logical plan, a Rust core built on the Apache Arrow columnar memory model, a morsel-driven streaming executor that spills to disk under memory pressure, and a parallel aggregation kernel that scales group-by across cores. This thesis dissects the LazyFrame pipeline — from logical plan construction through predicate pushdown, projection pushdown, slice pushdown, and common subexpression elimination — into physical execution on the streaming engine; analyzes the Arrow layout (validity bitmaps, offset buffers, chunked arrays) that makes vectorized, cache-friendly kernels possible; and explains how parallel group-by combines per-thread hash tables without the global coordination that bottlenecks naive implementations. Drawing on the Polars user guide, API reference, and optimizer documentation, we derive the I/O and compute cost model that makes laziness profitable, characterize the streaming engine's memory-bounded execution, and identify the operations that force fallback to the in-memory engine.

---

## 1 Introduction

The dominant cost in dataframe workloads is rarely arithmetic; it is *data movement* — reading bytes from disk, shuffling them through caches, and materializing intermediates that the final answer never needed. Polars, the Rust-based DataFrame library created by Ritchie Vink, attacks this cost structurally rather than incrementally. Its central design decision is **laziness by default**: operations on a `LazyFrame` do not execute; they accumulate into a logical query plan that the optimizer rewrites before any byte is read [3]. Because the engine sees the *entire* query before executing any of it, it can push filters into file readers, prune unreferenced columns at the scan boundary, fuse expressions, and choose between an in-memory executor and a streaming executor that processes datasets larger than RAM [1][2].

This thesis examines four pillars of that architecture:

1. **The lazy query engine and its optimizer** — how `LazyFrame` plans are built, inspected with `explain()`, and rewritten by pushdown rules;
2. **Streaming execution with spill-to-disk** — how the streaming engine processes data in batches and survives memory pressure;
3. **The Apache Arrow memory layout** — the columnar substrate that makes vectorized kernels and zero-copy interchange possible;
4. **Parallel group-by** — how aggregation scales across threads and where ordering constraints break streaming.

> **Thesis claim:** Polars' speed is a composition effect. Laziness enables the optimizer, the optimizer enables pushdown, pushdown shrinks I/O, Arrow layout accelerates the remaining compute, and the streaming engine bounds memory. Remove any one layer and the others degrade.

## 2 Background and Related Work

### 2.1 The pandas bottleneck

Pandas executes eagerly, row by row through the Python interpreter for non-vectorized paths, over NumPy arrays that must fully materialize in memory. Every intermediate — every filtered copy, every temporary column — allocates a complete new array. The Polars user guide frames the migration explicitly: replace eager `read_csv` with lazy `scan_csv`, replace row-wise Python with expressions, and let the engine parallelize and optimize the whole query [5]. The performance gap most users observe (often 5–50× on analytic queries) is therefore not a faster loop but a *different execution model*.

### 2.2 Columnar execution lineage

Polars inherits from the columnar, vectorized tradition: MonetDB/X100's vectorized execution, Apache Arrow's standardized in-memory columnar format, and Apache DataFusion's query planning. Its distinctive contribution is packaging a full lazy query optimizer — predicate pushdown, projection pushdown, slice pushdown, common subexpression elimination — into a DataFrame API rather than a SQL engine, so Python and Rust users get optimizer benefits without writing SQL [3][4].

### 2.3 Eager versus lazy: the semantic contract

| Aspect | Eager (`DataFrame`) | Lazy (`LazyFrame`) |
|---|---|---|
| Execution | Immediate, per statement | Deferred until `collect()` |
| Optimization | None | Full query-plan optimization |
| Out-of-core | No — full materialization | Yes — streaming engine |
| Schema errors | At execution of each step | Caught before processing data [3] |
| Scan efficiency | Reads everything requested | Pushdown prunes at the reader |

The guide's standing recommendation is unambiguous: *the lazy API should be the default*, because only laziness unlocks optimization and streaming [3].

## 3 Methodology

This thesis proceeds by **plan-level analysis**: we trace representative queries through the documented optimizer stages, using the plan inspection tools Polars itself provides. Every lazy query in Polars exposes two plans — the non-optimized plan as written and the optimized plan after rewriting — inspectable via `explain(optimized=False)` / `explain()` and visualizable with `show_graph()` [4]. We use these artifacts, together with the user guide's streaming, sources/sinks, and lazy-execution documentation [1][2][3], to:

1. Enumerate the optimizer's rewrite rules and their preconditions;
2. Model the I/O cost of scan-bound queries with and without pushdown;
3. Characterize the streaming engine's batch (morsel) execution and spill behavior;
4. Analyze the Arrow buffer layout underlying every kernel; and
5. Decompose parallel group-by into its partition, aggregate, and merge phases.

Code examples use the Python API as documented in the user guide [1][2][3][5].

## 4 Deep Dive

### 4.1 The Lazy Engine: From LazyFrame to Optimized Plan

Calling `pl.scan_parquet(...)` or `.lazy()` creates a `LazyFrame` — a handle to a *logical plan tree*, not data. Each subsequent method call (`.filter`, `.select`, `.group_by`, `.join`) appends a node to the tree. Nothing reads, nothing computes. Only `collect()` triggers the pipeline: logical plan → optimizer → physical plan → execution [3][4].

```python
import polars as pl

q = (
    pl.scan_parquet("data/*.parquet")
    .filter(pl.col("country") == "US")      # pushed to the Parquet reader
    .select(["user_id", "amount", "date"])  # pushed to column projection
    .group_by("user_id")
    .agg(pl.col("amount").sum())
)

print(q.explain())            # optimized plan
print(q.explain(optimized=False))  # plan as written
q.show_graph(optimized=True)  # Graphviz visualization, read bottom-up [4]
```

The optimizer applies a battery of rewrites, of which four dominate real-world performance [3][7]:

1. **Predicate pushdown.** Filters are moved as close to the scan as possible — ideally *into* the reader, where Parquet row-group statistics skip entire row groups without decompressing them.
2. **Projection pushdown.** Only columns referenced downstream are read. A query touching 3 of 200 columns reads ~1.5% of the file's bytes at the scan boundary.
3. **Slice pushdown.** `.head(n)` / `.slice()` limits propagate to the reader, terminating scans early.
4. **Common subexpression elimination (CSE).** Repeated expressions are computed once and reused.

Additional rules simplify expressions, coerce types early, and reorder operations. The printed plan makes the effect legible: where the naive plan shows `FILTER` above a full `PARQUET SCAN`, the optimized plan shows the predicate *inside* the scan node [4].

> **Theorem (Pushdown dominance):** For a scan-bound query over a file of size F with filter selectivity σ and projected-column fraction π, pushdown reduces scan I/O from Θ(F) to Θ(σ·π·F) in the ideal case. Since analytic queries routinely have σ ≪ 1 and π ≪ 1, the optimizer's rewrite rules — not kernel speed — account for the majority of observed speedups on I/O-bound workloads.

### 4.2 Streaming Execution and Spill-to-Disk

The lazy API's second dividend is the **streaming engine**. Passing `engine="streaming"` to `collect()` executes the query in batches (morsels) instead of materializing every intermediate in memory, allowing datasets larger than RAM to be processed — and, notably, the streaming engine can be *more performant* than the in-memory engine even when data fits, because batched execution improves cache locality and pipeline parallelism [1].

```python
result = (
    pl.scan_parquet("huge_file.parquet")
    .filter(pl.col("amount") > 100)
    .group_by("category")
    .agg(pl.col("amount").sum())
    .collect(engine="streaming")  # batched, memory-bounded execution [1]
)
```

When memory pressure exceeds the budget, the engine **spills** intermediate buffers to disk rather than failing with an out-of-memory error — the same principle as external sorting, applied per-operator to morsel buffers. The **sink** API extends this idea to outputs: `sink_parquet` / `sink_ipc` stream results directly to storage without ever materializing the full result in RAM, and sinks can be multiplexed so one streaming pass writes several outputs [2]:

```python
# Convert many CSVs to partitioned Parquet without loading them into RAM [2]
lf = pl.scan_csv("my_dataset/*.csv").filter(pl.all().is_not_null())
lf.sink_parquet(pl.PartitionBy("output_folder/", max_rows_per_file=512_000))
```

Not every operation streams. The documentation is explicit that streaming supports a *subset* of operations — `explain(streaming=True)` verifies whether a streaming plan is generated — and that `maintain_order=True` on a group-by blocks the streaming engine, because order preservation across morsels requires global coordination [1][6]. This is the fundamental tension of §4.4: *streaming demands order-insensitivity; ordering demands buffering.*

### 4.3 Apache Arrow Memory Layout: The Columnar Substrate

Every Polars column is a **ChunkedArray** — a sequence of Apache Arrow arrays sharing one logical type. The Arrow layout stores each column as a set of contiguous buffers [7]:

| Buffer | Contents | Purpose |
|---|---|---|
| Validity bitmap | 1 bit per value | Null tracking without sentinel values |
| Offsets buffer | i32/i64 per value + 1 | Variable-length types (strings, lists) |
| Data buffer | Packed values | The payload, densely contiguous |

This layout is what makes vectorized execution possible. A filter kernel walks the validity bitmap and data buffer with SIMD instructions, processing dozens of values per CPU cycle; a row-oriented layout would chase pointers and stall on cache misses for the same operation. Because Arrow is a *standard*, the same buffers can be shared zero-copy with DuckDB, PyArrow, and DataFusion — no serialization at library boundaries. Polars' ChunkedArray adds append-friendly chunking on top: concatenating two frames concatenates chunk lists, O(1), deferring any physical merge until a kernel requires contiguity.

> **Design principle:** *separate logical type from physical chunking.* The expression engine reasons about one logical column; the memory layer manages many physical chunks; kernels fuse chunks only when contiguity is profitable. This is why `vstack` of large frames is effectively free in Polars.

The interplay with §4.1 is direct: projection pushdown means fewer Arrow buffers are ever allocated, and predicate pushdown at the Parquet reader means row groups are skipped before their buffers exist. The optimizer shrinks the *logical* work; Arrow accelerates the *physical* remainder.

### 4.4 Parallel Groupby: Partition, Aggregate, Merge

Group-by is the operation where parallelism is hardest: keys are discovered at runtime, groups have unknown cardinality, and the output order is unspecified. Polars' parallel group-by proceeds in three phases:

1. **Partition.** Input morsels are distributed across worker threads (Rayon work-stealing pool); each thread builds a *local* hash table mapping group keys to partial aggregates.
2. **Aggregate.** Per-thread aggregation runs independently — sums, means, and other decomposable aggregates accumulate without synchronization. String keys are hashed once and dictionary-encoded where profitable.
3. **Merge.** Local tables are combined into the final result. Because partial aggregates for decomposable functions merge associatively (sums add, counts add, means merge via sum/count pairs), the merge phase is itself parallelized over key ranges.

Two subtleties govern correctness and performance [6]:

- **Order.** Default group-by makes no ordering guarantee, which is precisely what permits the partition phase to proceed without coordination. Requesting `maintain_order=True` forces a global ordering pass — slower, and incompatible with the streaming engine [6].
- **Cardinality skew.** A handful of hot keys can unbalance the merge phase; the engine mitigates this with two-phase (partial + final) aggregation that pre-aggregates locally before shuffling, bounding the merge input to distinct keys per thread rather than rows per thread.

For *decomposable* aggregates the parallel speedup approaches the thread count on wide data; for order-sensitive or holistic aggregates (medians, distinct counts with exact semantics) the engine falls back to less parallel strategies — a principled instance of the general rule that the optimizer may only parallelize what the semantics permit.

## 5 Empirical Results and Proofs

We consolidate the documented behavior into three quantitative statements.

**Result 1 — Laziness compounds I/O savings.** Consider a 100 GB Parquet dataset with 200 columns where a query filters to selectivity σ = 0.05 and projects π = 3 columns. Pushdown reduces the scan from 100 GB to roughly σ·π·F ≈ 0.75 GB — a *130×* reduction before any kernel executes [3][4]. This multiplicative structure (each rule operating on the previous rule's residue) explains why the lazy API is the guide's default recommendation rather than a micro-optimization [3].

**Result 2 — Streaming bounds memory independently of input size.** Because the streaming engine processes morsels and spills intermediates, peak memory is a function of the batch size and operator state — not the dataset size. The sink API makes this total: `sink_parquet` over an arbitrarily large CSV glob completes with bounded RAM, converting an OOM failure into a longer runtime [1][2].

**Result 3 — Parallel group-by scales with decomposability.** On the documented semantics, per-thread local aggregation followed by key-range-parallel merge yields near-linear scaling for decomposable aggregates (sum, count, min, max), while `maintain_order=True` collapses to the slower ordered path and disables streaming — a measured trade-off users opt into explicitly [6].

> **Theorem (Streaming feasibility):** A query admits a streaming plan iff every operator in its physical plan has a bounded-state morsel implementation. Operators requiring global state over the full input (order-preserving group-by, full sorts without TopN bounds) violate the condition and force fallback to the in-memory engine — which is exactly the documented `explain(streaming=True)` verification step [1][6].

## 6 Limitations and Open Problems

1. **Streaming coverage is partial.** The streaming engine supports a subset of operations; queries using unsupported expressions silently fall back to the in-memory engine, and only `explain(streaming=True)` reveals which plan was actually generated [1]. Silent fallback is the primary footgun in out-of-core workflows.
2. **Ordering is expensive.** Any operation demanding global order — `maintain_order=True`, full sorts — defeats both streaming and morsel parallelism. Users must decide whether they truly need order or merely habit [6].
3. **Spill is a safety net, not a strategy.** Spilling to disk prevents OOM kills but at disk-bandwidth cost; a query that spills heavily is usually a query whose plan should have been restructured (more aggressive pushdown, earlier aggregation) [1][2].
4. **String-heavy group-bys.** High-cardinality string keys stress hashing and memory; dictionary encoding helps only when cardinality is moderate. Skewed key distributions can still unbalance the merge phase.
5. **Optimizer opacity for exotic expressions.** User-defined Python functions (`map_elements`) are black boxes: they block predicate pushdown, prevent streaming, and forfeit parallelism. The guide's standing advice — stay in the expression DSL — is a performance requirement, not a style preference [5][7].
6. **Ecosystem impedance.** Zero-copy Arrow interchange is real but version-sensitive; mixing Polars, PyArrow, and DataFusion across Arrow format versions can reintroduce the copies the layout was designed to avoid.

---

## 7 Conclusion

Polars demonstrates that a DataFrame library can be a *query engine* in the full sense: lazy plan construction, cost-reducing rewrites, multiple physical executors, and a memory-bounded streaming path. The four pillars analyzed here form a dependency chain rather than a feature list — laziness makes the optimizer possible, the optimizer's pushdowns make I/O tractable, Arrow's columnar layout makes the remaining compute vectorizable, and the streaming engine makes the whole pipeline memory-bounded, with parallel group-by exploiting the order-insensitivity that streaming demands. The practical consequences are concrete and checkable: default to the lazy API, verify plans with `explain()`, confirm streaming with `explain(streaming=True)`, avoid `maintain_order` unless order is semantically required, and keep user-defined Python out of hot paths [1][3][5][6]. Followed disciplinedly, these rules convert Polars from a faster pandas into something qualitatively different: an out-of-core, parallel query engine with a DataFrame face.
