# Deterministic Simulation Testing for Distributed Systems in the FoundationDB Tradition: Simulated Time, Buggify Fault Injection, the Flow Actor Model, and Deterministic Replay for Heisenbug Hunting versus Jepsen and Elle

## Abstract

Distributed systems fail in ways that unit tests cannot foresee and chaos experiments cannot reproduce. FoundationDB's answer, developed over more than a decade, is deterministic simulation testing (DST): the entire cluster — processes, network, disks, clocks — is simulated inside a single process under a fully controlled, seeded source of randomness, so that every production binary and every test harness execute the identical code [1][2]. This thesis formalizes the DST architecture pioneered by Will Wilson and the FoundationDB team: simulated virtual time, deterministic pseudo-randomness, wholesale fault injection, and the Buggify mechanism for exercising rare code paths. We examine the Flow actor language that makes the approach practical, analyze how seeded sweeps cover combinatorial spaces of rare event interleavings, derive the probabilistic guarantees of two-phase buggify activation, and present the deterministic replay methodology that converts Heisenbugs into reproducible, time-travel-debuggable failures. A rigorous comparison with Jepsen and Elle — the leading black-box consistency-testing frameworks — establishes when each methodology dominates [5][6], and empirical evidence from FoundationDB, TigerBeetle, Dropbox, and Antithesis quantifies the technique's defect-finding power [7][8].

## 1 Introduction

A distributed database is a concurrent program whose inputs include the weather: network latencies, disk stalls, clock drift, and machine deaths arrive from an environment the developer neither controls nor observes. The resulting defects are *Heisenbugs* — failures that vanish under observation because instrumentation perturbs the very timing that produced them. Traditional quality assurance is structurally mismatched to this adversary. Unit tests exercise components in isolation; integration tests sample a negligible fraction of the interleaving space; chaos engineering injects real faults but surrenders reproducibility; and formal verification proves properties of a *model*, not of the shipped implementation [3].

FoundationDB took a different path: as Will Wilson explains in his seminal StrangeLoop 2014 talk, the team spent roughly the first two years building not the database but its *testing apparatus* — a deterministic simulator and the Flow actor language in which the database would be written [1]. The radical decision was that **the simulation and the production system are the same program**. Every source of nondeterminism — wall-clock time, random number generation, thread scheduling, network I/O, disk I/O — is abstracted behind interfaces with two implementations: a real one for deployment and a simulated one for testing. The simulator drives a whole virtual cluster inside a single OS process, advancing a virtual clock from event to event, delivering messages through a simulated network, failing disks and machines on a schedule drawn from a seeded pseudo-random number generator (PRNG), and checking global invariants after every step.

The payoff is captured in Wilson's oft-quoted claim: the team has run the equivalent of trillions of hours of simulation, and *every bug ever found in production could be reproduced in simulation* [3]. A failing seed is a *proof* of a defect, replayable bit-for-bit by any engineer on any machine.

This thesis makes five contributions: a formalization of the DST architecture and its seed-determinism invariant; a dissection of the Flow actor language; an analysis of Buggify, the two-phase probabilistic fault-injection mechanism, with derived coverage properties; a presentation of deterministic replay as a debugging discipline; and a rigorous comparison of DST against Jepsen and its Elle isolation checker.

## 2 Background

### 2.1 The Rare-Interleaving Problem

Consider a minimal failure: a Raft follower applies a log entry, crashes before persisting its voted-for state, restarts, and votes twice in one term — a window measured in microseconds, occurring perhaps once per 10^9 operations, which no human-written test targets and no stress test hits reliably.

> **Theorem (Interleaving Explosion).** *For a system of n processes exchanging m causally unordered messages, the number of distinct linear extensions of the execution partial order grows super-exponentially in both n and m. Exhaustive enumeration is infeasible for any realistic m; only statistical or symbolic coverage is attainable.*

| Approach | Execution source | Reproducible | Tests implementation | Coverage claim |
|---|---|---|---|---|
| Unit / integration tests | Hand-written scenarios | Yes | Yes | Negligible interleaving coverage |
| Chaos engineering | Real faults, real time | No | Yes | Real distribution, no replay |
| Model checking (TLA+/TLC) | Exhaustive state enumeration | Yes | No — tests a model | Complete over model, zero over code |
| Jepsen + Elle | Black-box workloads + fault injection | Partially | Yes | Consistency violations post hoc |
| **Deterministic simulation** | Seeded PRNG over simulated environment | **Yes — bit-for-bit** | **Yes — same binary** | Statistical over interleavings x faults |

### 2.2 Jepsen and Elle: The Black-Box Alternative

Kyle Kingsbury's Jepsen framework is the most influential alternative tradition [6]. Jepsen deploys a real cluster, generates concurrent client workloads (notably the transactional list-append workload), injects real faults — network partitions, process crashes and pauses, clock skew — and records a *history* of operation invocations and responses. The Elle checker then analyzes the history for isolation anomalies [5]. Elle's key insight is that from client-observable histories alone, one can infer Adya-style dependency graphs and detect phenomena like G2-item (anti-dependency cycles), aborted reads, and dirty updates. The Elle paper (arXiv:2003.10554) proves soundness of several of these inferences: certain anomalies are *unavoidable* conclusions from the observed history regardless of the unobserved internal interleaving [5].

Jepsen's strength is *fidelity* — testing the real deployment artifact under real OS behavior — while its weakness is *reproducibility and cost*: a run takes hours, exercises one fault schedule, and anomalies must be re-triggered by re-running the nemesis, making Jepsen superb for *validating* consistency claims but poor for *debugging* [2].

### 2.3 The Simulation Lineage

Deterministic simulation did not remain a FoundationDB secret: Dropbox reimplemented it; TigerBeetle built its testing strategy around it; the Pragma project documented a clean-room formulation [1]; and Wilson co-founded Antithesis, whose deterministic hypervisor generalizes DST to unmodified binaries [8]. Aiven applied DST to diskless Apache Kafka, reporting ~9,700 logical hours from 200 wall-clock hours — ~48x time compression [7].

## 3 Methodology

### 3.1 Architectural Invariant

> **Theorem (Seed Determinism).** *Let B be a fixed simulator binary, S a seed, and W a workload. If every source of nondeterminism in B — time, randomness, scheduling, I/O — is mediated by the simulator and derived from a PRNG stream keyed by S, then the execution trace T(B, S, W) is a pure function of (B, S, W). Re-executing (B, S, W) reproduces T exactly, including the manifestation of any defect.*

Achieving this requires fanatical hygiene, codified in FoundationDB's development rules [2][4]:

1. **No wall-clock reads.** All time comes from `now()`: virtual time in simulation, real time in production. Timers are simulator events.
2. **No unseeded randomness.** All randomness flows from the simulator's PRNG — including randomized backoff and gossip peer selection.
3. **No real I/O in the data path.** Storage engine, network transport, and resolution are abstracted; simulation substitutes in-memory models with programmable fault behavior.
4. **Single-threaded cooperative scheduling.** Each simulated process runs actors on one thread; context switches occur only at explicit `wait` points, so scheduling is a deterministic function of event order.

In production builds the same code links real implementations of these interfaces; the simulator binary (`fdbserver -r simulation`) links the simulated ones [4]. There is no separate test version of the database logic — the unit under test *is* the product.

### 3.2 The Simulation Loop

The simulator initializes its PRNG with the seed, constructs a virtual topology (machines, datacenters, processes with per-process globals and endpoint registrations), and instantiates an adversarial workload issuing random operations against the virtual cluster [4]:

```cpp
// Conceptual simulation loop (cf. Sim2 in fdbrpc/sim2.cpp [4])
while (!workload.done() && virtualTime < deadline) {
    Event e = eventQueue.popEarliest();  // deterministic: seeded tie-breaks
    virtualTime = e.time;                // virtual time jumps, never wall-clock
    maybeInjectFault(e, prng);           // kill process, partition net, ...
    e.process->deliver(e);               // run actors to quiescence
    checkLocalInvariants(e.process);     // assertions fire deterministically
}
workload.check();  // global invariant: linearizability, data equality
```

Because virtual time advances directly to the next event, idle periods cost nothing: years of cluster operation — elections, compactions, re-replication after simulated disk loss — compress into minutes of wall-clock time [7][8]. Network, disk, and machine behaviors are programmable fault models parameterized by the PRNG stream [3].

### 3.3 Workloads and Oracles

FoundationDB pairs each workload with checkers at two levels [2]: **local assertions** (`ASSERT` macros) verifying data-structure invariants continuously, firing deterministically on the offending seed; and **global workload checks** at the end — e.g., every simulated node converging to identical data, or the observed history being linearizable. The workload generates random operations, sizes, key distributions, and *timing*, so operations interleave with faults in seed-dependent ways; modern practice additionally cross-checks histories with Elle-family checkers.

## 4 Deep Dive

### 4.1 Taming Nondeterminism: Time, Randomness, and I/O

DST's deepest claim is that *all* relevant nondeterminism is captured by three simulated resources. **Time** is virtualized: `delay(d)` enqueues a task at `now() + d`, and the simulator may add buggified jitter (`FLOW_KNOBS->MAX_BUGGIFIED_DELAY`) to expose timer races; timers can fire up to 0.1 s early to model jitter [4]. **Randomness** is a single seeded stream, partitioned into independent sub-streams per subsystem so one subsystem's consumption never perturbs another's — essential for seed stability [4]. **I/O** is modeled: the simulated disk can lose writes, return corruption, or report fullness; the simulated network is a priority queue of in-flight messages with programmable latency, loss, duplication, and partition maps.

Thread-level nondeterminism is eliminated structurally: all virtual processes share one OS thread and actors yield only at `wait` points [4], so their interleaving is exactly the simulator's event order — DST *reduces* the interleaving space from uncountable thread schedules to countable seed space.

### 4.2 The Flow Language and the Actor Model

Enforcing Section 3.1's discipline by convention alone would fail. FoundationDB's solution was linguistic: **Flow**, a C++ dialect with an `ACTOR` construct compiling to a state machine, making asynchronous deterministic code the path of least resistance [1][3]:

```cpp
// Flow actor: every suspension point is visible to the simulator [3]
ACTOR Future<Optional<Value>> readWithRetry(Database db, Key key) {
    loop {
        try {
            state Transaction tr(db);
            // 'wait' suspends the actor; the simulator chooses resume order
            Optional<Value> v = wait(tr.get(key));
            wait(tr.commit());
            return v;
        } catch (Error& e) {
            wait(tr.onError(e));  // deterministic backoff via simulated RNG
        }
    }
}
```

The `ACTOR` macro rewrites the function into a resumable state machine; `Future<T>`/`Promise<T>` are composition primitives; `wait` marks scheduler re-entry. With cooperative actors there are no preemptive context switches — the scheduler is a priority queue with PRNG tie-breaks. The `fdbrpc` layer maps actors across processes via `(NetworkAddressList, Token)` endpoints; in simulation the `Sim2` transport routes the same traffic in-process, so actors cannot distinguish simulated from real deployment [4]. Determinism is thus a *language property*, not a testing-phase retrofit — which is why retrofitting DST onto syscall-heavy codebases is often prohibitive [7].

### 4.3 Buggify: Two-Phase Probabilistic Fault Injection

Beyond environmental faults, DST must exercise *rare code paths*: branches handling impossible-seeming conditions — a short read, a shrinking buffer, a reply from a shard that should not have answered. The mechanism is the `BUGGIFY` macro [3][4]:

```cpp
if (BUGGIFY) {
    // Taken randomly in simulation; never in production.
    wait(delay(g_random->random01() * 10));  // extra delay exposes races
}
```

Firing every site on every hit would produce total chaos with no progress. The design is therefore **two-phase** [4]:

- **Phase 1 — Activation.** The first time a site (file:line) is reached in a run, a seeded coin flip *arms* it for the whole run (~10% probability).
- **Phase 2 — Firing.** Each time an armed site is reached, a second flip (~10%) decides whether it fires.

> **Theorem (Buggify Coverage across Seeds).** *With k sites armed independently with probability p and firing with probability q per hit, the armed set per run is a p-biased random subset. Over N seeds, the probability that a particular subset of j sites is never simultaneously armed is (1 - p^j)^N, vanishing exponentially in N. Seed sweeping therefore explores the combinatorial space of fault interactions — swarm testing — with quantifiable coverage.*

With p = q = 0.1, across 10^5 seeds any given *pair* of sites is jointly armed in ~1,000 runs — how DST finds *interaction* bugs (a slow disk *and* a dropped heartbeat *and* a short timeout) that single-fault injection cannot produce. The kill hierarchy complements buggify at the process level: `killProcess`, `killMachine`, `killZone`, `killDataCenter`, `killDataHall`, with kill types from `KillInstantly` through `FailDisk` to `RebootAndDelete`, each checked against replication policy [4].

| Fault class | Examples | Injection mechanism |
|---|---|---|
| Network | Partitions, delays, reordering, duplication, clogging | Simulated transport (Sim2) |
| Process/machine | Instant death, reboot +/- data, hangs | Kill hierarchy (process to data hall) |
| Disk | I/O errors, corruption, full disk, lost writes | Simulated storage interface |
| Clock | Skew, jumps, NTP failure, timer jitter | Virtual clock + buggified delays |
| Logic paths | Short reads, wrong-shard replies, tiny buffers | BUGGIFY two-phase sites |

### 4.4 Covering Rare Interleavings: Seed Sweeps and Swarm Testing

DST's statistical power comes from *sweeping seeds* 1..N across a build farm, each seed exploring a different interleaving x fault-combination x buggify-subset. Runs are deterministic and independent — embarrassingly parallel — and virtual time compression lets a farm execute centuries of cluster operation per day [3][8]:

```python
# Seed sweep: embarrassingly parallel, fully reproducible
import subprocess, concurrent.futures

def run_seed(seed: int, workload: str = "Cycle") -> tuple:
    p = subprocess.run(["fdbserver", "-r", "simulation",
                        "-f", "tests/fast/" + workload + ".toml",
                        "-s", str(seed), "-b", "off"],
                       capture_output=True, text=True)
    # Nonzero exit or ASSERT text: a defect whose reproducer is the seed itself
    return seed, (p.returncode != 0 or "ASSERT" in p.stderr)

with concurrent.futures.ThreadPoolExecutor(max_workers=64) as ex:
    failures = [s for s, f in ex.map(run_seed, range(100_000)) if f]
print(str(len(failures)) + " failing seeds -> replay any with -s <seed>")
```

Two properties make this more than fuzzing: **fault-interaction coverage** — seeds jointly sample the power set of buggify sites — and **regression by seed**: every historically failing seed is re-run on every commit as an exact reproducer [2]. If a defect manifests with per-seed probability pi, its escape probability over N seeds is (1 - pi)^N ~ e^(-pi*N) — about 4.5 x 10^-5 for pi = 10^-4, N = 10^5 — turning tested extensively into a *numerical* claim, conditional on the workload resembling production.

### 4.5 Deterministic Replay and Time-Travel Debugging

When a seed fails, the engineer re-runs it under a debugger and the failure recurs on the first try; combined with `rr`-style record-and-replay, this yields effective *time-travel debugging*: watchpoint the corrupted structure, run backward to the corruption, read the causal chain [1][8]. **Seed bisection** further localizes faults: because buggify arming and fault schedules are deterministic functions of the seed, engineers binary-search over *which* injected fault is necessary by disabling fault classes while holding the seed fixed. Wilson reports this workflow made even his early, bug-ridden contributions harmless: defects were caught, reproduced instantly, and fixed before merge [8].

## 5 Empirical Results and Formal Arguments

### 5.1 Evidence from the Field

- **FoundationDB**: trillions of simulated hours; every production defect reproducible in simulation; simulation as a continuous blocking gate on every commit [1][3].
- **Antithesis**: the deterministic hypervisor found multiple serious bugs in Ethereum's 2022 Merge, missed by conventional testing [8].
- **Aiven (Kafka)**: ~9,700 logical hours from ~200 wall-clock hours per campaign, catching ordering and failure-handling defects in diskless Kafka [7].
- **TigerBeetle / Dropbox**: independent reimplementations converging on simulated time, seeded faults, and invariant checking — the design is not an artifact of one codebase [1].

### 5.2 DST versus Jepsen/Elle: A Decision Framework

| Dimension | Deterministic simulation | Jepsen + Elle |
|---|---|---|
| System under test | Same binary, simulated environment | Real deployment, real OS/faults |
| Defects found | Races, fault-interaction bugs, rare-path logic errors | Consistency/isolation violations, real fault modes |
| Reproducibility | Bit-for-bit from seed | Best-effort; nemesis re-runs |
| Cost per scenario | Seconds (virtual time) | Minutes to hours |
| Scenarios per day | 10^5 to 10^6 (farm) | 10^1 to 10^2 |
| Blind spots | Unmodeled faults; simulator bugs | Interleavings too rare to sample |
| Soundness basis | Statistical (seed coverage) | Formal (Elle's proven inferences [5]) |

The principled pipeline is *layered*: DST as the inner loop — millions of cheap, reproducible scenarios per commit — and Jepsen/Elle as the outer loop, where Elle's formal anomaly inferences provide guarantees no sampling argument can [5][6]. DST workloads can even *emit* Elle-compatible histories, checkable by both a white-box oracle and a black-box verifier.

> **Theorem (Complementarity).** *Let D be defects detectable by DST under workload W and fault model F, and J those detectable by Jepsen under nemesis N. Neither D subset of J nor J subset of D holds in general: DST misses defects outside F (kernel bugs, unmodeled hardware), while Jepsen misses defects needing interleavings rarer than its sampling budget. The union D union J strictly dominates either alone, and deterministic replay makes defects in the intersection cheaper to diagnose via DST.*

## 6 Limitations

**The fault model is a model.** The simulator only injects faults its authors imagined. A disk that *lies* — acknowledging writes it discards — is caught only if the disk model includes lying; real SSDs have done exactly this. Jepsen's real-fault approach has no such ceiling [6]; the mitigation is enriching fault models from production incidents.

**Determinism is relative to the binary.** The seed-determinism theorem assumes identical binaries; compiler nondeterminism, ASLR-influenced iteration order, and floating-point non-associativity across architectures can break bit-for-bit replay. FoundationDB pays this tax via pinned toolchains and banned nondeterministic constructs [4].

**The abstraction tax.** Flow-style discipline forbids raw threads, direct syscalls, and clock-reading libraries; retrofitting DST onto existing codebases is often prohibitive [7]. Antithesis's hypervisor attacks exactly this limitation by determinizing unmodified binaries [8].

**Coverage is statistical, not exhaustive.** A defect with per-seed manifestation probability 10^-9 likely escapes 10^6 seeds. Symbolic execution and model checking give the complementary exhaustive-over-model guarantee — over a model, not the code.

**Simulator correctness.** A bug in the network model can hide real defects or manufacture false ones. The backstop: any production incident *not* reproducible in simulation is treated as a simulator bug of the highest priority [3].

## 7 Conclusion

Deterministic simulation testing reframes distributed systems QA from scenario-writing into *controlled sampling over a reproducible execution space*. Its pillars — total mediation of nondeterminism, virtual time, seeded randomness, two-phase buggify injection, the Flow actor discipline, seed-swept swarm coverage, and deterministic replay — convert Heisenbugs into routine, seed-identified, debuggable test failures, with defect-finding power unmatched by any single competing methodology [1][3][8].

Yet DST is half of a complete strategy, complemented precisely where Jepsen and Elle are strong: real faults, real deployments, and formally sound inferences of isolation anomalies from observable histories [5][6]. The mature organization runs both — simulation as the high-frequency inner loop that makes developers fearless, and black-box verification as the outer loop that keeps the fault model honest. As Wilson observed, the deepest effect is cultural: when testing is this powerful, teams can take risks that would elsewhere be reckless [8]. *Certainty is a feature you can engineer*.
