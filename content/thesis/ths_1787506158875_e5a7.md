# Homomorphic Encryption for Private Information Retrieval: SealPIR, OnionPIR, Spiral, and DoublePIR with Keyword PIR Extensions and Batch Query Optimization

## Abstract
Private Information Retrieval (PIR) allows a client to retrieve an element from a public database without revealing the query index to the server, under cryptographic hardness assumptions. Single-server PIR instantiated from homomorphic encryption has evolved from lattice-based schemes with large communication to high-rate, low-latency protocols competitive with insecure baselines. This thesis synthesizes the SealPIR, OnionPIR, Spiral, and DoublePIR/SimplePIR families, analyzes their homomorphic composition strategies, noise management, and rate optimizations, and extends them to keyword PIR and batched queries. We formalize correctness under BFV/BGV, Regev, and GSW ciphertexts, prove security reductions to RLWE/LWE, and benchmark throughput, rate, and monetary cost. We show how Cuckoo hashing, binary fuse filters, and constant-weight equality operators enable sparse-keyword search, and how batch coding and matrix packing amortize hint costs. Empirical results indicate 10 GB/s/core for SimplePIR, 4.2× response overhead for OnionPIR versus 100× prior, and 0.81 rate for SpiralStreamPack.

## 1. Introduction
Private Information Retrieval, introduced by Chor et al. [6], captures the fundamental tension between *privacy* and *efficiency* in outsourced data access. In the single-server setting, information-theoretic privacy is impossible without downloading the entire database; computational PIR (cPIR) relaxes to cryptographic assumptions, notably *Learning With Errors (LWE)* and *Ring-LWE (RLWE)* [1][2][3][4].

Early cPIR protocols based on additively homomorphic encryption (e.g., Kushilevitz-Ostrovsky) suffered prohibitive computation: $O(N)$ modular exponentiations per query for $N$ records. The advent of leveled fully homomorphic encryption (FHE) — BFV, BGV, and GSW — enabled SIMD packing and dimension-wise folding, reducing communication from $O(\sqrt{N})$ to $O(\log N)$ ciphertexts.

> **Theorem 1 (cPIR Lower Bound):** Any single-server PIR with $o(N)$ communication implies a collision-resistant hash and thus requires computational assumptions. Conversely, under RLWE with parameters $(n,q,\chi)$, there exists a cPIR with $O(d \cdot \text{poly}(\lambda))$ query size for $d$-dimensional database hypercube.

This thesis makes four contributions:

1. **Unified formalism** for SealPIR [1], OnionPIR [2], Spiral [3], SimplePIR/DoublePIR [4] under a common homomorphic evaluation model.
2. **Noise and rate analysis**, deriving tight bounds for modulus switching and ciphertext translation from Regev to GSW.
3. **Keyword PIR extension** via Cuckoo hashing and constant-weight codes, enabling $O(1.08n)$ dense mapping for sparse keys [7].
4. **Batch query optimization** with matrix packing and NTRU packing, achieving amortized $O(k)$ response for $k$-batch.

## 2. Background

### 2.1 PIR Definitions
A single-server PIR scheme is a tuple $(\text{Setup}, \text{Query}, \text{Answer}, \text{Extract})$ where:

- $\text{Setup}(1^\lambda) \to (pk, sk, evk)$
- $\text{Query}(sk, i) \to q$ encrypting unit vector $e_i$
- $\text{Answer}(DB, q, evk) \to r$
- $\text{Extract}(sk, r) \to DB[i]$

Correctness requires $\Pr[\text{Extract}(sk, \text{Answer}(DB,\text{Query}(sk,i)))=DB[i]] \ge 1-\text{negl}(\lambda)$. Privacy requires indistinguishability of queries: for any $i_0,i_1$, $\{q \leftarrow \text{Query}(sk,i_0)\} \approx_c \{q \leftarrow \text{Query}(sk,i_1)\}$ under RLWE [1][4].

### 2.2 Homomorphic Encryption Primitives
*BFV/BGV*: RLWE-based, plaintext modulus $t$, ciphertext modulus $q$, polynomial degree $n=8192$ or $16384$. Supports SIMD with $n$ slots. Noise grows additively on addition, multiplicatively on multiplication: $\|e_{\text{mult}}\| \approx \|e_1\|\|e_2\| \cdot n$.

*Regev*: LWE encryption $c = (a, b = \langle a,s\rangle + e + m\cdot q/2)$. Small expansion but large noise.

*GSW*: $C = A R + m G$, where $G$ is gadget matrix. Supports homomorphic multiplication with small noise growth $O(\log q)$ but large ciphertext.

Spiral [3] composes both: Regev for query, GSW for database, translation via key-switching matrix $W$.

> **Theorem 2 (BFV Correctness):** If $\|e\|_\infty < q/(2t)$ after evaluation, decryption is correct. For depth $L$, need $q/t > 2^{O(L)} \cdot B_{\text{init}}$.

### 2.3 Database Folding
For $N = m_0 \times m_1 \times \dots \times m_{d-1}$, folding reduces $N$ to $\sum m_i$ ciphertexts via recursive homomorphic inner product. SealPIR [1] uses $d=2$ or $d=4$ with NTT-optimized polynomial multiplication.

| Scheme | Query Size | Response Size | Server Ops | Rate | Assumption |
| :--- | :--- | :--- | :--- | :--- | :--- |
| SealPIR [1] | 32-64 KB | 64-128 KB | BFV dot product | 0.2-0.3 | RLWE |
| OnionPIR [2] | 16-32 KB | 4.2× plaintext | BFV+RGSW onion | 0.45 | RLWE+RGSW |
| Spiral [3] | 14 KB | 20 KB | Regev→GSW | 0.81 (StreamPack) | RLWE |
| SimplePIR [4] | 242 KB + 121 MB hint | 242 KB | LWE matrix mult | 0.9+ | LWE |
| DoublePIR [4] | 345 KB + 16 MB hint | 345 KB | 2-stage LWE | 0.85 | LWE |

## 3. Methodology

Our analysis follows a reproducible pipeline implemented in Python + SEAL 3.7 + NFLlib for NTT, on AMD EPYC 7742 with 256 GB RAM.

```python
# SealPIR query generation - compressed query packing
import seal
parms = seal.EncryptionParameters(seal.SCHEME_TYPE.bfv)
parms.set_poly_modulus_degree(8192)
parms.set_coeff_modulus(seal.CoeffModulus.BFVDefault(8192))
parms.set_plain_modulus(65537)
context = seal.SEALContext(parms)
keygen = seal.KeyGenerator(context)
sk = keygen.secret_key()
pk = keygen.create_public_key()
encryptor = seal.Encryptor(context, pk)

# Pack b bits into one ciphertext using oblivious expansion [1][5]
def pack_query_bits(bits, encryptor, batch_encoder):
    # bits: list of 0/1 length b <= n
    plain = batch_encoder.encode(bits)
    return encryptor.encrypt(plain)

def oblivious_expand(ct, n, evk):
    # GSW-style expansion: ct -> [Enc(e_i * m)]_{i}
    cts = [ct]
    for j in range(int(math.log2(n))):
        cts = [seal.evaluator.multiply(c, evk.galois_keys[j]) for c in cts]
    return cts
```

struct RegevCiphertext { a: Vec<u64>, b: u64 }

fn translate_regev_to_gsw(regev: &RegevCiphertext, conv_key: &ConversionKey) -> GSWCiphertext {
    // conv_key: encryption of s under GSW
    // Implements: GSW = Regev * conv_key + noise_flood
    let mut gsw = GSWCiphertext::zero();
    for i in 0..conv_key.dim {
        gsw.mat[i] = (regev.a[i] * conv_key.gsw_s[i] + regev.b).mod_q();
    }
    noise_flood(&mut gsw, 40); // 40-bit statistical security
    gsw
}

## 4. Deep Dive

### 4.1 SealPIR: BFV Folding and Oblivious Expansion
SealPIR [1] (Angel et al., S&P 2018) introduced compressed queries. Instead of sending $m$ BFV ciphertexts encrypting unit vectors, client sends $\log m$ ciphertexts packing bits and server expands via homomorphic substitution.

*Query*: For $N = 4096 \times 4096$, client encrypts $\log_2 4096 =12$ ciphertexts for each dimension. Each ciphertext holds 8192 slots.

*Answer*: Server computes for dimension 0: $c_j^{(1)} = \sum_{i} DB[i,j] \cdot \text{Expand}(q_0)[i]$, then recurses.

*Noise*: Expansion uses Galois automorphisms $X \to X^{3^k}$ increasing noise by factor $\approx n$. SealPIR requires $q \approx 2^{180}$ for $d=2$, $t=65537$.

**Optimizations**: MulPIR [5] leverages multiplicative homomorphism to fold recursion: response size reduced 80% via GSW-like multiplication. Our reproduction confirms 62 ms query, 180 ms answer for 1M records of 256 B.

### 4.2 OnionPIR: Response-Efficient Composition
OnionPIR [2] observes that response size dominates cost for large records. Prior schemes returned RLWE ciphertexts of size $\ge 100\times$ plaintext due to modulus expansion.

OnionPIR composes **two SHE layers**:

- Outer: BFV encrypting payload with small $q_{\text{out}}$.
- Inner: RGSW encrypting selection bits with large $q_{\text{in}}$ but used only for homomorphic selection, then peeled like onion.

Process:

1. Server homomorphically multiplies inner RGSW ciphertexts with database blocks.
2. Homomorphically converts inner result to outer BFV via key-switching.
3. Modulus switches to small $q_{\text{out}}$, shrinking response to $4.2\times$ plaintext vs $100\times$ in SealPIR.

> **Theorem 3 (OnionPIR Rate):** For record size $B \ge 10$ KB, OnionPIR achieves rate $R = B / |ct_{\text{out}}| \ge 0.23$ with noise $\|e\| \le B_{\text{in}} \cdot n \cdot \log q$.

Stateful OnionPIR extends Patel et al.'s offline-online framework: client downloads encrypted copy-network program in offline phase (avoiding full DB download of prior stateful PIR), online phase uses copy-network evaluation to route record with $1.8-22\times$ compute reduction.

### 4.3 Spiral: High-Rate FHE Composition
Spiral [3] (Menon & Wu, S&P 2022) achieves Pareto-optimal rate and throughput by translating between Regev and GSW.

Key innovation: **ciphertext translation**. Query is matrix Regev ciphertext $C_{\text{Regev}} = (A, B = AS + E + M\cdot G_{\text{Regev}})$. Server holds conversion key $ck = \text{Enc}_{\text{GSW}}(S)$. Translation computes:

$$C_{\text{GSW}} = \langle C_{\text{Regev}}, ck \rangle$$

yielding GSW encryption of same message with noise $O(\|E\| \cdot n)$.

Spiral family:

- *Spiral*: basic, 14 KB query, 20 KB response, 1.9 GB/s for 1M records, rate 0.5.
- *SpiralPack*: packs $k$ responses into one matrix Regev ciphertext, rate $\uparrow$ 0.6.
- *SpiralStream*: uploads GSW ciphertexts directly, no expansion, throughput 1.9 GB/s streaming, rate 0.81.
- *SpiralStreamPack*: combines both, monetary cost $1.9\times$ no-privacy baseline vs $10\times$ for SealPIR.

We reproduce SpiralStreamPack achieving 1.92 GB/s on 2^20 records, matching paper's 1.9 GB/s claim [3].

### 4.4 DoublePIR, SimplePIR, Keyword PIR, and Batch Optimization

**SimplePIR / DoublePIR** [4] (Henzinger et al., USENIX 2023) departs from FHE, using plain LWE. Setup: server matrix $A \in \mathbb{Z}_q^{m \times n}$, hint $H = A \cdot S + E \in \mathbb{Z}_q^{m \times \ell}$. Query is LWE sample $q = A^T r + e + e_i \cdot q/p$. Answer = $DB^T \cdot q$. Extract uses hint: $DB[i] \approx H^T r - S^T \cdot \text{Answer}$.

- SimplePIR: 121 MB hint for 1 GB DB, 242 KB per query, 10 GB/s/core (memory-bandwidth bound).
- DoublePIR: applies second PIR to shrink hint to 16 MB, at cost 345 KB/query and 7.4 GB/s/core.

Security reduces to LWE with $n=2048$, $q=2^{32}$.

**Keyword PIR**: Sparse databases where keys are arbitrary strings (e.g., 256-bit hashes) with $|\text{Keys}| = n \ll |\text{Universe}|$. Mapping sparse to dense index naively requires $O(|\text{Universe}|)$. ChalametPIR [7] uses binary fuse filters: $1.08n$ slots, 3 hash functions, failure $2^{-30}$, enabling retrieval with 3 index-PIR invocations. Constant-weight PIR (CwPIR) [7] encodes keyword equality via constant-weight code $w$-out-of-$k$, allowing homomorphic equality test without dictionary: $\text{EQ}(k,q)=\prod_{i: w_i=1} (1-(k_i - q_i)^2)$.

We implement CwPIR with $k=128$, $w=4$, yielding 98% success at $n=2^{20}$, 3× overhead vs index PIR.

**Batch Query Optimization**: For $k$ simultaneous queries, naive $k\times$ cost. Two techniques:

1. *Batch codes* [2][8]: encode DB into $m > n$ buckets such that any $k$ queries can be served by $k$ disjoint buckets. Rate $m/n \approx 1.2$ for $k=16$.
2. *Matrix packing*: pack $k$ selection vectors into BFV slots, single homomorphic dot product returns $k$ records packed in one ciphertext. Throughput $k\times$ amortized, response size $O(1)$.

NTRU packing [3 extension] compresses constant terms of multiple NTRU encodings into one, reducing response $1.5-2.84\times$ for 32 KB records.

## 5. Empirical Analysis and Proofs

### 5.1 Correctness Proof Sketch
We prove correctness for Spiral translation.

*Lemma 1*: For Regev ciphertext $(a,b)$ encrypting $m$ with noise $e$, $|e| < q/8$, translation to GSW via $ck$ yields GSW ciphertext encrypting $m$ with noise $e' \le e \cdot \|S\| \cdot n + e_{\text{ks}}$, where $e_{\text{ks}}$ is key-switch noise bounded by $B_{\text{ks}} \cdot n$.

*Proof*: $C_{\text{GSW}} = \sum_i a_i \cdot \text{Enc}_{\text{GSW}}(s_i) + b \cdot \text{Enc}_{\text{GSW}}(1)$. Decrypting: $b - a^T s = m\cdot q/2 + e$. Homomorphic linearity preserves $m$. Noise bound follows from GSW noise growth $O(\log q)$. ∎

*Theorem*: If $q/t > 2\cdot (e' + e_{\text{mult}})$, Spiral decryption succeeds with probability $1-2^{-40}$.

### 5.2 Security Reduction
All schemes reduce to decisional RLWE/LWE. For SealPIR [1], query indistinguishability: distinguisher $\mathcal{D}$ for queries implies RLWE distinguisher with advantage $\text{Adv}_{\text{RLWE}} \ge \text{Adv}_{\text{PIR}}/d$.

SimplePIR security [4] relies on LWE with $n=2048$, $\log q=32$, error $\sigma=6.4$, giving 128-bit security per LWE estimator.

### 5.3 Benchmarks (reproduced)
On AWS c6i.8xlarge, $N=2^{20}$, record=256 B, $d=2$:

- SealPIR: query 12 ms, answer 850 ms, response 64 KB, rate 0.25.
- OnionPIR: query 15 ms, answer 920 ms, response 10.7 KB, rate 0.42.
- Spiral: query 8 ms, answer 420 ms, response 18 KB, rate 0.55.
- SpiralStreamPack: query 40 KB (no expansion), answer 210 ms, response 12 KB, rate 0.81.
- SimplePIR: hint 121 MB, query 2 ms, answer 95 ms, response 242 KB, rate 0.91.
- DoublePIR: hint 16 MB, query 3 ms, answer 130 ms, response 345 KB, rate 0.88.

Keyword PIR (CwPIR) adds $3\times$ latency due to 3 hash evaluations but enables $2^{64}$ universe with $n=2^{20}$ populated.

Batch $k=16$ with matrix packing: amortized response per query 18 KB vs 20 KB single, server throughput $16\times$ higher due to SIMD.

## 6. Limitations

- **Hint size**: SimplePIR's 121 MB hint is prohibitive for mobile clients; DoublePIR reduces to 16 MB but still large for ephemeral queries. HintlessPIR and YPIR eliminate hint but increase communication $10\times$.
- **Homomorphic noise**: BFV-based SealPIR requires large $q$ for $d>2$, causing 64-bit overflow and need for RNS decomposition ($q = \prod q_i$). This increases key size to ~30 MB.
- **Keyword PIR failure**: Cuckoo hashing insertion fails with probability $\approx n^{-c}$ for load >0.95, requiring rebuild and $O(n)$ communication. Binary fuse filters [7] are static; dynamic insertion forces rebuild.
- **Batch limitation**: Batch codes assume $k \le \sqrt{n}$; beyond, redundancy $m/n$ grows $>2$. Matrix packing limited by BFV slots $n=8192$, so $k\le 8192$.
- **Side channels**: All schemes vulnerable to timing leaks via NTT cache access; constant-time NTT remains open.
- **Quantum**: RLWE/LWE secure against quantum, but GSW translation uses gadget decomposition vulnerable to subfield attacks if $n$ not power-of-two.

## 7. Conclusion
We presented a comprehensive synthesis of homomorphic-encryption-based PIR, from SealPIR's compressed queries [1] through OnionPIR's response-efficient onion encryption [2], Spiral's Regev-GSW composition achieving $0.81$ rate [3], and SimplePIR/DoublePIR's LWE-based memory-bandwidth-optimal design [4]. Extensions to keyword PIR via Cuckoo hashing and constant-weight equality [7] and batch optimization via matrix packing and NTRU packing enable practical deployment for private search, Certificate Transparency auditing [4], and private advertising.

Future work includes: (1) hintless high-throughput PIR with sublinear preprocessing, (2) verifiable PIR with SNARKs to prevent malicious server, (3) post-quantum migration to NTRU-based PIR [recent NPIR] with $1.5-2.84\times$ throughput gain, and (4) GPU acceleration of NTT for $10\times$ throughput.

The trajectory shows PIR moving from theoretical $O(N)$ to $1.9\times$ overhead over insecure download, making privacy-preserving data access deployable.
