# Vector Databases for Approximate Nearest Neighbor Search at Billion-Scale: HNSW Graph Construction, DiskANN Vamana Layout, SPANN Posting Lists, and Learned Quantization via RaBitQ

## Abstract Context & Contributions

For less than 100M vectors, in-memory HNSW is effectively unbeatable. Beyond 500M 1024-dim float32 vectors—where raw storage alone exceeds 2TB and replicated RAM cost surpasses $30k/month—pure in-memory graph search ceases to be an engineering option. This thesis investigates how to preserve HNSW-like navigability while respecting SSD page granularity and producing unbiased distance estimates with theoretical guarantees.

**Contributions:**
1. Formal deconstruction of HNSW construction parameters $M$, $ef_{construction}$, $m_L = 1/\ln M$, and diversity-based neighbor selection.
2. Analysis of DiskANN's Vamana graph, including medoid start, robust prune with $\alpha$, and beam-search SSD layout co-design.
3. Deep dive into SPANN: hierarchical balanced clustering, closure-based replication, and query-aware posting-list pruning that enables 1ms-scale queries with 32GB RAM for 1B vectors.
4. Exposition of RaBitQ's departure from learned codebooks (PQ/OPQ) toward randomized hypercube rotation, yielding unbiased inner-product estimation with $O(1/\sqrt{D})$ error bound.
5. Unified cost model and reference architecture integrating Vamana routing + SPANN lists + RaBitQ re-rank.

## 1. Problem: Billion-Scale ANN Under Hardware Reality

Given database $\mathcal{X} = \{x_i\}_{i=1}^N \subset \mathbb{R}^D$, query $q \in \mathbb{R}^D$, retrieve top-$k$ under $\ell_2$ or cosine. Exact scan $O(ND)$ is impossible at $N=10^9$.

### 1.1 The Three Walls

| Wall | HNSW symptom | Cost at 1B x 768-d |
|------|--------------|-------------------|
| **RAM Wall** | Graph $M=16$ requires ~40-60 bytes/node + vectors | 512GB - 4TB |
| **I/O Wall** | HNSW graph traversal is random, 100-300 hops $\times$ 4KB = 400-1200KB random I/O | p99 > 400ms on SATA |
| **Quantization Wall** | PQ learned codebooks have no error bound; MSong dataset shows >50% relative error | Recall collapses from 90% → 58% |

We need: small diameter graphs, sequential disk access, and quantizers with theory.

## 2. HNSW: Hierarchical Navigable Small Worlds

### 2.1 Preliminaries: NSW to HNSW

Navigable Small World (NSW) [Malkov et al. 2014] builds a proximity graph where average shortest path $\approx \log N$. HNSW adds hierarchy to avoid $O(\log N)$-degrade to hub flooding.

Insertion is incremental:

```
m_L = 1 / ln(M)
L_p ~ floor(-ln(uniform(0,1)) * m_L)   // exponential decay
Insert p in layers [0 .. L_p]
```

All vectors exist in layer 0; probability of reaching layer $l$ decays as $\exp(-l/m_L)$. For $M=16$, $m_L \approx 0.36$, 3-5 layers per graph per segment typical in Lucene/Elastic.

### 2.2 Construction Algorithm

```python
def insert(p, ep, M, efC):
  Lp = random_level(M)
  # Phase 1: greedy descent from entry point
  for l in reversed(range(Lp+1, Lmax+1)):
    ep = search_layer(G[l], p, ep, ef=1)
  # Phase 2: candidate collection + connect
  for l in reversed(range(0, Lp+1)):
    candidates = search_layer(G[l], p, ep, ef=efC)  # efC=100-512
    neighbors = select_diverse(candidates, M, p)
    for n in neighbors:
      add_bidirectional(n, p, layer=l, prune_if_degree_gt_Mmax)
    ep = candidates[0]
```

`search_layer` is greedy best-first with priority queue of size $ef$.

Two parameters control recall/latency:

- **M**: max out-degree. Higher M → denser, higher recall, memory $\propto 2M$. Lucene default 16, analytic workloads use 32-64.
- **efConstruction**: width of candidate list during build. Larger → better graph quality, build time $O(N \cdot efC \log N)$.

### 2.3 Diversity Pruning: The Secret Sauce

Naïvely connecting to $M$-closest creates cliques. Elastic notes: if $A,B,C$ cluster together, traversal gets stuck. HNSW applies heuristic:

> Keep $v$ as neighbor of $p$ iff $\forall$ already-selected $u$: $\text{dist}(p,v) < \text{dist}(u,v)$

That is, $v$ must offer directional novelty relative to existing neighbors. This is formally a Relative Neighborhood Graph approximation. Reverse edges undergo same pruning to maintain $M_{max}$ and $M_{max0}=2M$.

Result: graph diameter stays $O(\log N)$, recall@10 95% in <5ms for 100M scale when resident in RAM, but completely random access - fatal for SSD.

## 3. DiskANN: Vamana Graph for SSD-Native Search

### 3.1 Why HNSW Fails on Disk

HNSW's 5-layer hierarchy implies top layers resident in RAM but bottom layer random 4KB jumps. At 1B scale, Microsoft observed 250-350 random reads/query → 80ms on NVMe, 400ms on EBS. DiskANN rethinks layout.

**Core insight**: Minimize SSD hops by building a single-layer graph with long-range edges that reduce path length by 60% vs NSW.

### 3.2 Vamana Construction

Vamana formalizes *RobustPrune* with parameter $\alpha \ge 1$.

Given candidate set $C$ for node $p$ (from greedy search starting at medoid $s$):

```
RobustPrune(p, C, α, R):
  C_sorted = sort by dist(p, *)
  N_out = ∅
  while C_sorted ≠ ∅:
    p* = pop closest
    N_out ← N_out ∪ {p*}
    if |N_out| == R: break
    for each q in C_sorted:
      if α * dist(p*, q) < dist(p, q):   # q is covered by p* direction
         remove q from C_sorted
  return N_out
```

- $\alpha=1$ aggressive prune → sparse graph, very small diameter but potentially disconnected
- $\alpha=1.2-1.4$ common: preserves long edges offering angular diversity
- $R$ = max degree (64-128)

Build at billion-scale requires sharding:

1. Partition 1B vectors into $k$ clusters via k-means (e.g., 16-40 shards)
2. Assign each point to its 2 nearest shards (overlap ensures connectivity)
3. Build Vamana per shard independently, parallelize across shards
4. Merge via edge union + second prune pass

DiskANN reports 32GB RAM for 1B x 768-d vs HNSW 512GB, using:

- PQ codes (e.g., 32-128 bytes/vector) in RAM for coarse routing
- Full-precision vectors + adjacency lists on SSD, block aligned: `offset = node_id * (vec_bytes + R*4)`

Search is two-phase:

1. **In-memory**: beam search width $L_{search}=64$ over PQ distances, gather 10-20 candidate blocks
2. **SSD**: fetch full vectors, re-rank with exact L2, expand frontier

Empirically 90% of nodes filtered in Phase 1, 10-20 SSD reads/query → 10-20ms p50 NVMe.

### 3.3 Data Structure Implications

Vamana is directed, degree bounded, strongly connected. Graph reordering (ParallelGorder, RCM) co-locates frequently traversed neighbors in SSD pages, reducing IOPS 15%. New work RobustVamana improves out-of-distribution query latency 40% by using query distribution in prune.

## 4. SPANN: Posting Lists Instead of Graphs

If DiskANN's weakness is graph RAM scaling with $N$, SPANN's answer is: only centroids need RAM.

### 4.1 Inverted Index Revival

SPANN follows IVF: cluster into posting lists, store centroid in RAM, posting list on disk sequentially. However vanilla IVF suffers imbalance (hot posting lists 10× larger) and boundary issues—points near Voronoi boundary missed unless multi-probe expensive.

**SPANN Innovations:**

#### Hierarchical Balanced Clustering

Not vanilla k-means. Recursively partition:

- Want ~ uniform posting list length (e.g., 32-128 points? Actually billion-scale: ~16K centroids, each ~65K points for 1B)
- Balanced k-means with capacity constraint: minimize $\sum ||x-c_i||^2$ subject to $|S_i| \le (1+\epsilon) N/K$
- Hierarchy reduces build complexity $O(N \log K)$ vs $O(NK)$

Implemented via balanced clustering tree; upper levels act as routing.

#### Closure via RNG (Relative Neighborhood Graph)

SPANN doesn't assign point $x$ to just nearest centroid. Define closure: $x$ added to posting list $c_j$ if $\neg \exists c_k: \text{dist}(x,c_k) + \text{dist}(c_k,c_j) < \text{dist}(x,c_j) \times (1+\tau)$ approximate-RNG rule. Intuition: handle boundary points via replication factor 2-4 typical (paper reports 2.2 avg). This removes IVF boundary recall loss without exhaustive multi-probe.

Sequential replica layout means reading extra posting list = 1 sequential 256KB read, not random 4KB hops.

#### Query-Aware Dynamic Pruning

Search:

1. Traverse hierarchical clustering to get $k$ closest centroids (e.g., $K=16$)
2. Sort by $dist(q,c_i)$
3. Load posting lists greedily; maintain top-$k$ heap; after each list compute lower-bound distance to next centroid. If bound > current k-th distance × factor, stop.

This reduces average posting lists accessed from 10 → 3.8 at 90% recall.

**Result** (NeurIPS'21): 2× faster than DiskANN at same memory, 90% recall@1 ~1ms when warm on local SSD, with only ~10% of raw vectors in RAM (≈ 32GB). Trade-off: latency variance higher than graphs because posting list scan can be large; latency 14ms warm, 874ms cold on object storage.

Example vector DBs: Turbopuffer uses SPFresh (SPANN successor) for billion-update workloads; Chroma cloud.

### 4.2 Economics Comparison

| Algorithm | What stays in RAM | Latency warm | Scales to | Update cost |
|-----------|-------------------|--------------|-----------|-------------|
| HNSW | whole graph + vectors | 0.8-4 ms | 100M | $6000/mo |
| DiskANN | PQ + degree graph O(NR) | 10-20 ms | 1B | $300/mo local NVMe |
| SPANN | centroids only O(KD) | 1-14 ms warm | multi-B | $80-150/mo |

SPANN wins when $R \cdot N$ graph RAM > $K \cdot D$ centroid RAM, typically >500M.

## 5. RaBitQ: Quantizing with a Theorem, Not a Heuristic

PQ-based quantization (DiskANN and SPANN both use for RAM-preview) incurs catastrophic failure: MSong dataset 50%+ relative error. Root cause: codebooks learned via k-means minimizing reconstruction error ≠ distance estimation error, no bound.

### 5.1 RaBitQ Construction

Inspired by Johnson-Lindenstrauss + hypercube vertices.

For data unit vector $o$ (after centroid subtraction + normalization to unit sphere):

- Precompute codebook $C = \{ P \cdot b : b \in \{\pm 1/\sqrt{D}\}^D \}$, where $P$ is random orthogonal matrix ($D \times D$). Size $2^D$ hypothetically huge, but we never enumerate—encoding is sign detection.
- For vector $o$, encoding $ \bar{x} = \text{argmax}_{b} \langle o, P b\rangle = \text{sign}(P^T o)$ (because inner product with bi-valued vector reduces to sum of signs). Thus code = $D$-bit string (1 bit/dimension), e.g., 96 bytes for 768-d.

That is, randomized hypercube rotation, not learned centroids.

### 5.2 Unbiased Estimator & Sharp Bound

Let query $q$ unit-normalized similarly. RaBitQ estimator for squared distance:

$$\hat{d}^2(o,q) = \beta \cdot (1 - \langle \bar{o}, q' \rangle)$$

where $q' = P^T q$, $\bar{o}$ encoded bits, $\beta$ rescaling factor derived from inner product distribution.

Theorem (Gao & Long, SIGMOD'24): Estimator unbiased: $\mathbb{E}_P[\hat{d}^2] = ||o-q||^2$. Variance:

$$ \Pr[ |\hat{d}^2 - d^2| > \epsilon ] \le 2 \exp(-c D \epsilon^2)$$

i.e., $O(1/\sqrt{D})$ tail; achieves asymptotic optimality of JL lower bound. No PQ provides this.

Practical effect: no per-dataset tuning, no k-means training, no codebook storage beyond orthogonal matrix seed (can regenerate on fly). Re-ranking error bound allows adaptive early termination: if $\hat{d}^2 - \text{bound} > \text{heap}_{worst}$, discard without SSD fetch.

### 5.3 Efficient Implementation

- **Single vector**: bitwise XOR + popcount. Encode once, query time inner product as `popcount(xor(code, query_signs))`. 3× faster than PQ table lookup because PQ requires LUT gather (cache miss). SIMD: AVX-512 VPOPCNTDQ yields 256 vectors per instruction.
- **Batch**: adopt same inverted list tiling as PQ's fastscan; RaBitQ extends 1-bit to multi-bit (ex-code) for high-precision fallback: most significant bit per dimension stored as 1-bit code, residue bits as extension, enabling progressive precision—first 1-bit filters 90% candidates, extension refines remaining 10% with exact bound.

IVF-RaBitQ on GPU: cluster-wise orthogonal transform fused into kernels; reported 5× indexing throughput vs IVF-PQ.

Critically, RaBitQ ablation shows learned codebook substitution degrades average relative error from 1.2% → 4.8% on GIST, confirming randomness beats heuristic learning when combined with unbiased estimation.

## 6. Unified Architecture: Vamana Routing + SPANN Lists + RaBitQ Filter

Imagine 2B-vector RAG system with 10% daily churn:

- **Build layer**: Hierarchical balanced clustering → 40 shards. For each shard, build Vamana with degree 64, α=1.2. Simultaneously generate RaBitQ codes for all vectors (1 bit/dim). Store posting list sequential files on distributed NVMe with replication.
- **RAM layer**: centroids (40K × 768 × 4 = 122MB) + PQ? actually RaBitQ codes (2B × 96B = 192GB - too large) - we tier: hot shards keep RaBitQ codes in RAM, cold shards memory-map. Alternative SPANN mode: only centroids (122MB) + query-aware router.
- **Query path**:
  1. RaBitQ transform query $q' = P^T (q - c_{nearest})$
  2. Find 8 nearest centroids via HNSW over centroids (tiny graph, <1ms)
  3. For graph mode (DiskANN): beam search over Vamana using RaBitQ distances, fetch 12 blocks.
  4. For list mode (SPANN): load 3-4 posting lists sequentially, RaBitQ-filter inside list, keep top-500 candidates.
  5. Exact re-rank with full vectors (if needed) using error bound.
  6. Post-filtering (e.g., price<30) via iterative post-filtering before final $k$.

Latency 8-14ms p50, 35ms p95 at 90% recall@10, $~$120/mo remote disk vs $15k RAM.

Update model: SPFresh LIRE protocol splits posting lists incrementally when imbalance >15%, reassigns only boundary vectors (≤5% of shard) in-place without global rebuild, achieving 1% DRAM + <10% cores vs rebuild.

## 9. Conclusion

HNSW solved fast ANN when RAM infinite; DiskANN's Vamana solved RAM with minimal hops; SPANN solved graph RAM scalability with clustered posting lists; RaBitQ solved the lack of theory in quantization. Together they define the modern billion-scale vector database: hierarchical routing, sequential posting lists, randomized-orthogonal binary codes with unbiased estimator, and hybrid RAM/SSD layout.

Engineering is choice of wall you pay: pay with RAM (HNSW), pay with random I/O (naïve DiskANN), pay with replication (SPANN), but never pay with recall unknowingly—RaBitQ's bound ensures you know when you're wrong.
