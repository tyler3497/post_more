# CHERI Hardware Capabilities for Spatial and Temporal Memory Safety: Capability Compression, Compartmentalization via Sealed Capabilities, and Porting C/C++ Codebases to Pure-Capability ABIs

## Abstract

Capability Hardware Enhanced RISC Instructions (CHERI) rearchitects the pointer as an unforgeable, hardware-checked capability carrying bounds, permissions, and an object type, enforced on every load, store, and instruction fetch through out-of-band validity tags. This article examines how CHERI delivers deterministic spatial memory safety for C and C++ while furnishing architectural primitives for temporal safety and fine-grained software compartmentalization. We dissect CHERI Concentrate, the floating-point-style compression scheme that encodes base and top bounds into 27 bits of a 128-bit capability using a 14-bit mantissa, an internal exponent bit, and an implicit exponent, preserving single-cycle pointer arithmetic without load-to-use delay. We analyze sealed capabilities and object-type-keyed unsealing as the mechanism for cross-compartment calls, sentry capabilities for zero-cost library isolation, and tag-sweep revocation as the foundation for heap and stack temporal safety. We compare hybrid and pure-capability application binary interfaces, document a porting methodology for legacy codebases including capability-aware linkage, capability tables, and global visibility enforcement, and evaluate measured performance data and formal verification results from deployed prototypes.

## 1 Introduction

Memory-safety defects remain the dominant source of exploitable software vulnerabilities. Spatial violations such as buffer overflows and temporal violations such as use-after-free and use-after-return routinely defeat software-only mitigations, and studies of reported defects continue to attribute a large share of memory-safety vulnerabilities to classes like uninitialized reads, which account for up to one in ten such defects in C and C++ codebases [4]. The conventional response — software instrumentation, sanitizers, and control-flow integrity — trades away performance, compatibility, or completeness.

CHERI (Capability Hardware Enhanced RISC Instructions), a joint research program of SRI International and the University of Cambridge, takes a different approach: it extends conventional instruction-set architectures with hardware-supported capabilities that enforce memory protection on every memory access [1]. Rather than retrofitting safety through compiler instrumentation alone, CHERI changes the architectural meaning of a pointer. A CHERI capability is twice the width of a native pointer — 128 bits on 64-bit platforms — plus one validity tag bit stored out of band so that non-capability-aware instructions cannot forge capabilities [1]. The hardware checks bounds, permissions, and validity on each dereference, making spatial safety a property of the machine rather than a convention of the software.

This article provides a deep technical treatment of three facets of the CHERI design that are most relevant to systems builders. First, we explain CHERI Concentrate, the bounds-compression scheme that makes 128-bit capabilities practical by encoding base and top bounds relative to the capability address in a floating-point-like format [1]. Second, we analyze sealed capabilities — the limited, disciplined non-monotonicity that enables fine-grained software compartmentalization and controlled cross-domain calls [7]. Third, we present a methodology for porting existing C and C++ codebases through hybrid execution to full pure-capability application binary interfaces, drawing on the CheriABI process environment and the CHERI ELF platform ABI [5][6].

> **Definition:** A *capability* is an unforgeable hardware-managed token of authority. It bundles an address with the bounds of the memory region it may access, a permission mask governing permitted operations, and an object type used for sealing. Possession of a valid, tagged capability is both necessary and sufficient to access the referenced memory [1].

The remainder of this article is organized as follows. Section 2 reviews the capability protection model and its architectural realization. Section 3 describes our methodology for evaluating the design. Section 4 presents the deep technical analysis across four dimensions: compression, compartmentalization, temporal safety, and ABI porting. Section 5 surveys empirical results and mechanized proofs. Section 6 discusses limitations, and Section 7 concludes.

## 2 Background

### 2.1 From access control to capabilities

Classical hardware protection is built on *access control*: a security monitor tracks the currently executing authority (a privilege ring, an enclave, a virtual machine) and consults an explicit policy on each access [2].

### 2.2 The CHERI protection model

The CHERI ISA specification organizes its guarantees around three pillars [1]:

- **Spatial safety.** Every heap allocation, stack frame, and global receives a capability describing its valid range and permissions. The compiler narrows bounds at allocation sites, so out-of-bounds accesses trap in hardware. Pointer integrity — including return addresses and C++ vtable entries — follows from the same mechanism.
- **Temporal safety.** CHERI provides instruction-set *foundations* for temporal safety rather than a complete solution: validity tags allow pointers to be reliably located in memory and atomically revoked, and acceleration features make sweeping for capabilities cheaper than scanning raw memory [1]. Heap non-reuse via revocation or garbage collection, and compiler clearing of stack capabilities, build on these foundations.
- **Software compartmentalization.** Sealed capabilities provide the hardware basis for decomposing large programs into isolated components, each holding only the capabilities for the resources it genuinely requires [1].

> **Theorem:** Under the CHERI monotonicity invariant, no sequence of capability-manipulation instructions can produce a capability whose bounds or permissions exceed those of the capabilities from which it was derived. The sole exceptions are sealed capabilities and controlled exception paths, which introduce limited, auditable non-monotonicity [1].

### 2.3 Execution modes: hybrid and pure-capability

CHERI supports two execution modes that structure the entire porting strategy [7]. In *hybrid mode*, capabilities and capability-aware instructions coexist with ordinary integer pointers; legacy loads and stores are bounds-checked against the Default Data Capability (DDC), so unmodified code runs while individual components are progressively hardened. In *pure-capability mode*, the compiler replaces every pointer with a capability — `uintptr_t` and `void *` grow to 16 bytes alongside the new `uintcap_t` type — and procedure linkage is rebuilt around capability registers, capability-aligned stacks, and capability tables with dedicated relocations [6].

## 4 Deep Dive

### 4.1 Capability Anatomy and CHERI Concentrate Compression

A 128-bit CHERI capability on a 64-bit platform is laid out as follows [1]:

| Field | Width (bits) | Purpose |
|---|---|---|
| Address (`a`) | 64 | Current pointer value |
| Permissions | 16 | 12 hardware-defined + 4 software-defined permission bits |
| Object type (`otype`) | 18 | Sealing domain identifier; `-1` when unsealed |
| Bounds | 27 | Compressed base and top, relative to `a` |
| Tag | 1 (out of band) | Validity bit, one per 16-byte granule |

Storing two 64-bit bounds naively would demand a 256-bit capability, doubling pointer memory traffic and cache pressure. CHERI Concentrate solves this with a floating-point-inspired encoding that exploits redundancy between the address and the bounds: because bounds are typically near the address, only their significant bits need storage, and alignment requirements grow proportionally with object size [1].

The encoding is governed by a small set of parameters. `MW` is the mantissa width — 14 bits for 128-bit capabilities in CHERI ISA version 9 — determining bound precision [1]. `B` and `T` are `MW`-bit values substituted into the address to reconstruct base `b` and top `t`. The internal-exponent bit `IE` selects between two formats: when set, a 6-bit exponent `E` occupies the low three bits of each of `B` and `T`, trading three bits of precision for the ability to describe much larger regions; when clear, the exponent is implicitly zero and the full mantissa width is available [1]. The top bound `t` is further compressed by two bits, derived from the identity `T = B + L` together with a carry implied whenever the low bits of `T` are less than those of `B`, since `t` is known to exceed `b` [1]. Decoding substitutes the `MW` bits at positions `E` through `E + MW` of the address and clears the low `E` bits, yielding bounds that are always at least as wide as the true object — compression is *conservative*, never *unsound*.

Crucially, the format supports pointer arithmetic directly on the compressed representation. Adding an offset to a capability adjusts the address field while the bounds fields ride along, requiring no decompression in the common case and introducing no additional load-to-use delay in the pipeline [1]. The published Concentrate design was accompanied by a HOL4 machine-checked proof of the decode and pointer-modify operations, and reported 50 to 75 percent reductions in L2 misses on compiled C-language benchmarks relative to the uncompressed 256-bit format, demonstrating that compression is a performance feature as well as a compatibility one [1].

> **Lemma:** For any capability with address `a`, mantissa fields `B` and `T`, and exponent `E`, the decoded bounds `(b, t)` satisfy `b <= a < t` whenever the capability is within its object, and every representable object admits an encoding whose decoded bounds contain the true object bounds. Precision loss from compression therefore widens bounds but never narrows them [1].

Imprecision has a security consequence worth stating plainly: because bounds are rounded outward, a compressed capability can authorize access to slightly more memory than the underlying object occupies. In the CHERI-128 format this over-approximation has been shown to interact with transient-execution analysis, where an imprecise bound may admit speculative access beyond the intended object [5]. The rounding is bounded and deterministic, and the pure-capability toolchain minimizes it by choosing tight exponents, but it is inherent to any compressed fat-pointer scheme.

### 4.2 Sealed Capabilities and Software Compartmentalization

Monotonicity alone cannot express *delegation with confinement*: handing a component a callback it may invoke but neither inspect nor forge. Sealed capabilities provide this. The `CSeal` instruction binds a capability to an object type (`otype`); the sealed capability cannot be dereferenced, only passed around opaquely. `CUnseal` reverses the operation, but only when presented with a second capability whose object type matches — the type acts as a cryptographic-style key, enforced entirely in hardware [7]. This is the primitive on which CHERI compartmentalization is built.

A representative design pattern appears in CHERI-enabled RTOS messaging. A channel-manager compartment allocates synchronization primitives from a secure heap, then seals each primitive's capability with a unique type such as a mutex-seal or semaphore-seal type before distributing it. Compartments invoke operations through cross-compartment calls: the sealed capability arrives as an argument, is unsealed inside the trusted stub using `CUnseal`, and the futex-based lock or semaphore operation proceeds against the now-accessible state [9]. The stub footprint is roughly two hundred bytes, keeping the trusted computing base small and auditable compared with verifying entire compartments [9].

Compartment transitions themselves use dedicated calling conventions. The classical `CCall` mechanism passes a sealed code capability and a sealed data capability; hardware atomically unseals both, installs them as the new program-counter and invoked-data capabilities, and transfers control [7]. More recent work introduces *sentry* capabilities, which provide code and data isolation at library boundaries at essentially no additional cost: a sentry wraps an entry point so that jumps through it cannot be abused to reach arbitrary offsets, enabling basic compartmentalization at naturally occurring boundaries — libraries, compilation units, even individual functions — without modifying application source [8]. Complementary *Global Visibility Enforcement* (GVE) shrinks ambient authority further by ensuring each function can access only the globals its source code actually references [8].

The design space spans two granularities:

1. **Library and module compartmentalization**, using sentry capabilities and restricted capability tables to isolate mutually distrusting libraries within one address space [8].
2. **Object-granularity compartmentalization**, using sealed capabilities with distinct object types per resource class, as in the RTOS messaging framework [9].

Both rest on the same invariant: unsealing requires possession of a capability carrying the matching object type, so the authority to cross a boundary is itself a capability that can be delegated, attenuated, or withheld [7].

### 4.3 Temporal Safety: Tags, Revocation, and Stack Coloring

CHERI's architectural contribution to temporal safety is the validity tag. Because every 16-byte granule carries an out-of-band tag bit that only capability-aware instructions can set, the system can reliably *locate* all pointers in memory and atomically *invalidate* them — the two operations that software-only temporal safety cannot perform without whole-program cooperation [1]. Heap temporal safety then reduces to a revocation problem: on `free`, sweep memory for capabilities pointing into the freed region and clear their tags before the memory is reallocated.

The CAPSTONE project generalizes this into a *revocation tree* maintained in DRAM regions inaccessible to software. Each capability records the identifier of its revocation node; freeing a region invalidates the corresponding subtree, transitively revoking every derived capability regardless of where copies have propagated [2]. This design directly addresses CHERI's trustless-allocation gap: ordinarily, an allocator cannot be certain that an application has relinquished every copy of a reclaimed capability, and the application cannot be certain the allocator will not retain access — revocation trees give both parties a hardware-rooted guarantee [2].

Stack temporal safety — use-after-return — is harder, because frames retire orders of magnitude more frequently than heap allocations are freed. FRESCO, a recent hardware/software co-design, attacks it by *coloring* the stack pointer with a per-invocation provenance identifier: every capability derived from the stack pointer inherits that invocation's color and is hardware-invalidated the moment the function exits, no matter how or where the capability escaped [3]. Two mechanisms make this scalable. First, a *Color Saver* static escape analysis confines coloring to functions that actually need it, and its core algorithm is mechanically verified in Rocq. Second, *capability-color segmentation* partitions memory into disjoint segments with independent color namespaces, letting stack and heap temporal safety coexist on one system [3]. FRESCO's evaluation spans SPEC CPU benchmarks and real-world SQLite, PostgreSQL, and gRPC workloads [3].

A distinct temporal-adjacent property is initialization safety.

### 4.4 Hybrid and Pure-Capability ABIs: Porting C/C++ Codebases

Porting is staged through the two execution modes.

**Pure-capability mode** is the destination.

1. **Adopt capability-sized pointer types.** `uintptr_t`, `intptr_t`, and `void *` become 16 bytes; new code uses `uintcap_t` where provenance matters. Code that assumes `sizeof(void *) == sizeof(long)`, serializes pointers as integers, or round-trips pointers through `long` must be repaired — these are the classic *provenance* bugs that pure-capability compilation surfaces.
2. **Rebuild the linkage model.** Global access moves through capability tables (`.captable`) with `__cap_relocs` processed at startup; dynamic tags (`DT_MIPS_CHERI_*` on MIPS, with RISC-V and Morello analogues) describe the tables to the loader [6]. The calling convention keeps caller- and callee-saved capability registers disjoint from integer temporaries, and the stack pointer remains capability-aligned [6].
3. **Harden the kernel boundary.** CheriABI implements the pure-capability process environment as a compatibility layer: userspace pointers crossing into the kernel are annotated `__capability`, selected structures (such as `iovec`) are converted to carry capabilities, and capability-aware copy routines (`copyin_c`, `copyout_c`, `fueword_c`) replace their legacy counterparts so that capabilities are never copied across the boundary unintentionally [5].
4. **Minimize privilege.** Enable sentry-based library isolation and Global Visibility Enforcement so each component receives only the capabilities its source references, adjusting the compartmentalization granularity at compile time or run time without application changes [8].
5. **Close temporal gaps.** Layer revocation or coloring (Section 4.3) over the spatially safe baseline, prioritizing allocators and long-lived servers where use-after-free dominates.

Empirically, the CheriABI effort demonstrated that large existing programs — including full operating-system userlands — run as pure-capability binaries with simple recompilation plus targeted provenance fixes, with the kernel changes contained in a compat layer rather than a rewrite [5].

## 5 Empirical Results and Formal Proofs

Published evidence for CHERI clusters into three categories: performance of the compressed format, efficacy of compartmentalization, and mechanized correctness. The table below summarizes representative results; all figures are drawn from the cited publications.

| System | Property evaluated | Reported result |
|---|---|---|
| CHERI Concentrate | Cache behavior vs 256-bit capabilities | 50–75% fewer L2 misses on compiled C benchmarks [1] |
| CHERI Concentrate | Functional correctness | HOL4 machine-checked proof of decode and pointer-modify [1] |
| CHERI RTOS messaging | Trusted computing base size | ~200-byte stub footprint per compartment boundary [9] |
| FRESCO | Workload coverage | SPEC CPU plus SQLite, PostgreSQL, gRPC benchmarks [3] |
| FRESCO | Escape analysis | Core algorithm mechanically verified in Rocq [3] |
| CAPSTONE | Memory-model soundness | Refinement proof from abstract to concrete model [2] |
| Pure-capability linkage | Compatibility | Full userland runs with recompilation plus provenance fixes [5][8] |

Several patterns emerge. First, the performance story is favorable precisely where skeptics expected pain: compressing capabilities to 128 bits not only halves pointer footprint but *improves* cache behavior relative to the uncompressed design, because the encoding was co-designed with the pipeline to avoid load-to-use penalties [1]. Second, compartmentalization overheads are dominated by domain-crossing frequency rather than by the mechanism itself; sentry capabilities make the common case of library isolation nearly free, while sealed-capability calls cost a small constant per transition [8][9]. Third, the verification story is unusually strong for a hardware/software co-design: machine-checked proofs cover the compression codec, the escape analysis underpinning stack coloring, and the refinement between abstract and concrete memory models [1][2][3].

> **Theorem:** FRESCO's coloring discipline guarantees that no capability derived from a stack frame's colored stack pointer remains dereferenceable after the creating function returns, regardless of the escape path taken. The guarantee is established by the combination of hardware invalidation on function exit and the verified escape analysis that determines coloring placement [3].

What remains unmeasured in the public literature is a head-to-head comparison of full-system pure-capability overhead against mature software-only sanitizer stacks on identical workloads; the published numbers evaluate components (compression, revocation, coloring) rather than the integrated whole.

## 6 Limitations

CHERI is not a panacea, and its limitations shape deployment decisions. **Compression imprecision**, discussed in Section 4.1, means bounds are rounded outward; adversarial analysis must treat the decoded bound, not the source-level object size, as the security boundary [1]. **Temporal safety is incomplete by default**: baseline CHERI provides revocation foundations, but a stock pure-capability system without sweeping, coloring, or garbage collection still permits use-after-free — the tag mechanism is necessary but not sufficient [1][2]. **Provenance-unsafe idioms** pervasive in systems C — pointer-integer-pointer round trips, out-of-bounds pointer construction before narrowing, custom memory managers — require source changes that hybrid mode tolerates but pure-capability mode rejects [5][6]. **Side channels** are largely out of scope: CHERI constrains the architectural privileges an attacker holds, but transient-execution attacks remain possible wherever a capability legitimately authorizes access to the secret, and compressed-bound imprecision can widen the speculative window [5]. Finally, **ecosystem maturity** lags the architecture: debuggers, profilers, and language runtimes must all become capability-aware, and the porting tax, while bounded, is real for million-line codebases with hand-rolled allocators [8].

## 7 Conclusion

CHERI demonstrates that memory safety can be an architectural property rather than a software convention. By fusing bounds, permissions, and sealing into the pointer itself and enforcing them in hardware on every access, it converts the largest class of C and C++ vulnerabilities from probabilistic mitigations into deterministic traps [1]. CHERI Concentrate shows that this need not cost a factor of two in memory traffic: a carefully designed compressed encoding preserves pipeline performance while admitting machine-checked correctness proofs [1]. Sealed and sentry capabilities turn the same machinery into a compartmentalization substrate with per-boundary trusted bases measured in hundreds of bytes [8][9]. And the path from legacy code to safety is engineered, not aspirational: hybrid execution, the CheriABI compat layer, and capability-aware linkage give teams an incremental migration with a well-understood checklist [5][6]. The open problems — complete temporal safety at production overhead, ecosystem tooling, and speculative-execution interaction — are active research fronts, with systems like FRESCO and CAPSTONE showing that the capability model extends naturally to meet them [2][3]. For systems where memory safety is non-negotiable, CHERI is the most credible hardware foundation available.
