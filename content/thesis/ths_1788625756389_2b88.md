# The Chain of Trust Reconsidered: DNSSEC Key Hierarchies, Denial of Existence, and the Encrypted-Transport Turn in Domain Name System Security

## 1 Introduction

The Domain Name System (DNS) is the Internet's most load-bearing naming substrate and its most structurally fragile. Designed in the early 1980s without any provision for data integrity, the protocol treats every datagram as authoritative truth — a fiction that Dan Kaminsky's 2008 demonstration of systemic cache poisoning via birthday attacks proved untenable [7]. The Internet's response unfolded along two distinct cryptographic axes. The first, *DNS Security Extensions* (DNSSEC), specified in RFC 4033, RFC 4034, and RFC 4035 [1][2][3], authenticates DNS data itself: every resource record set (RRset) is signed with an asymmetric private key, and validating resolvers verify signatures along a hierarchical *chain of trust* rooted in the DNS root zone. The second, arriving a decade later, encrypts the transport channel: DNS over TLS (DoT, RFC 7858) [8], DNS over HTTPS (DoH, RFC 8484) [9], and DNS over QUIC (DoQ, RFC 9250) [10] protect the *confidentiality* of the query stream against on-path observers.

These mechanisms are complementary but orthogonal. DNSSEC provides **data origin authentication** and **integrity** while leaving every query fully visible on the wire; encrypted transports provide **confidentiality** and **transport integrity** while offering no guarantee about the authenticity of the data returned. A validating stub that talks DoH to a recursive resolver still trusts that resolver completely — DNSSEC is what would let it *not* have to. This thesis examines the full DNS security architecture through four lenses: (i) the DNSSEC key hierarchy — Key Signing Keys (KSKs), Zone Signing Keys (ZSKs), and Delegation Signer (DS) records — and validation from the root trust anchor; (ii) authenticated denial of existence via NSEC and its privacy-preserving successor NSEC3, and the zone-enumeration tradeoffs this creates; (iii) key-rollover mechanics, centered on the first-ever root KSK rollover of 11 October 2018; and (iv) the encrypted-transport family DoT/DoH/DoQ, their divergent privacy properties, centralization dynamics, and downgrade-attack surface.

> **Theorem (DNSSEC validation soundness, informal):** If a validating resolver's trust anchor is authentic, every signature in the chain of trust verifies, and no signature is expired, then any RRset returned with the *Authenticated Data* (AD) bit set was published by the holder of the corresponding private key and has not been modified in transit.

## 2 Background

### 2.1 The DNS resolution model

A DNS name is a path in a delegated tree. A stub resolver queries a recursive resolver, which iteratively descends from the root zone (`.`) through the top-level domain to the authoritative server for the queried name. Each delegation is a *zone cut*: the parent publishes NS records pointing to the child's servers. Classical DNS provides no integrity for this process; an off-path attacker who wins a race against the legitimate response can inject arbitrary mappings [7]. DNSSEC does not change the shape of resolution — it adds parallel cryptographic material that lets a *validating* resolver distinguish authentic data from injected data.

### 2.2 Cryptographic primitives in DNSSEC

DNSSEC signs **RRsets**, not individual records. Three record types carry the mechanism [2]: **DNSKEY** (type 48) publishes a zone's public keys, with the SEP bit conventionally marking a KSK; **RRSIG** (type 46) is a signature over one RRset, binding it to a validity interval, algorithm identifier, key tag, and signer name; **DS** (type 43) is a digest of a child zone's KSK stored in the *parent* zone — the cryptographic weld between parent and child. Denial of existence is carried by **NSEC** (47) or **NSEC3** (50) plus **NSEC3PARAM** (51). Crucially, RFC 4033 §2 notes that the KSK/ZSK distinction is *purely operational* — validation logic treats all DNSKEYs identically [1].

### 2.3 Encrypted transports

The IETF DPRIVE working group standardized encrypted DNS transports. RFC 7858 (DoT, 2016) [8] layers DNS over TLS on dedicated TCP port 853, with *Strict* and *Opportunistic* usage profiles in RFC 8310 [11]. RFC 8484 (DoH, 2018) [9] maps DNS onto HTTP semantics on TCP port 443. RFC 9250 (DoQ, 2022) [10] maps DNS directly onto QUIC on UDP port 853 with ALPN `doq`, inheriting TLS 1.3 and 0-RTT resumption. Oblivious DoH (RFC 9230) [12] adds a proxying layer so no single party observes both client identity and query content. These transports encrypt the channel but authenticate only the *server endpoint* — they say nothing about whether the DNS data itself is genuine.

## 3 Methodology

This study is a protocol-analytic and measurement-synthesis thesis with three components.

1. **Normative reconstruction.** The validation algorithm, key-lifecycle state machines, the NSEC3 hash construction, and transport handshakes are reconstructed from the normative RFCs [1][2][3][4][8][9][10][11], cross-checked against the operational practices of RFC 6781 [5] and the algorithm-agility guidance of RFC 6840 [6].
2. **Historical case analysis.** The 2018 root KSK rollover is treated as a natural experiment in global cryptographic migration, using ICANN's Office of the CTO review [13], the IMC 2019 measurement paper [14], and ICANN's operational communications [15][16].
3. **Deployment-measurement synthesis.** Public telemetry — APNIC Labs' continuous validation measurements, RIPE Atlas-based encrypted-transport probing, and root-server trust-anchor signaling (RFC 8145) [18] — grounds claims about real-world adoption. No new active measurements were performed; all quantitative claims are attributed.

## 4 Deep Dive

### 4.1 The validation chain: from root trust anchor to leaf RRset

The DNSSEC chain of trust is a rooted tree of signature verifications whose root is not cryptographic at all — it is a *configured trust anchor*, a copy of the root zone's KSK public key shipped with resolver software or fetched out-of-band from IANA [3][16]. From that anchor, validation proceeds per RFC 4035 §5:

```text
validate(name, type, response):
    root_keys = fetch(".", DNSKEY)          # RRSIG verifies against trust anchor
    for zone in [".", "edu", "example.edu"]:
        child_keys = fetch(zone.child, DNSKEY)
        assert DS(zone.child) in parent RRsets      # parent RRSIG verifies
        assert digest(child_keys.KSK) == DS.digest  # the weld holds
        assert RRSIG(child_keys) verifies with child KSK
    assert RRSIG(answer) verifies with leaf ZSK     # ZSK signs all other data
    assert inception <= now <= expiration for every RRSIG
    return AD=1
```

Three subtleties matter. First, **the KSK signs only the DNSKEY RRset; the ZSK signs everything else.** This is the entire rationale for the split: the ZSK can be rolled frequently (quarterly is common per RFC 6781 [5]) without involving the parent, because the parent's DS record points only at the KSK. The KSK changes rarely — at the root, the interval was *eight years* (2010–2018). Second, **validation is fail-closed**: any signature failure converts the response to `SERVFAIL`. This is what made the 2018 rollover dangerous — a resolver with a stale trust anchor did not degrade, it *broke all resolution* [16]. Third, **the AD bit is a claim, not a proof**: a non-validating stub that receives AD=1 trusts its recursive resolver to have validated. End-to-end assurance requires stub-side validation.

> **Lemma (DS weld integrity):** A validating resolver accepts a child zone's DNSKEY RRset only if the parent's DS RRset is authentic and a DS digest matches a KSK in the child's DNSKEY RRset. An attacker controlling neither the parent's ZSK nor the child's KSK cannot forge this weld without breaking the digest or signature scheme.

Trust-anchor management is the weakest link. Anchors are bootstrapped via RFC 5011 automated updates (the resolver watches the DNSKEY RRset for new keys across a 30-day hold-down) [17] or measured via RFC 8145 signaling, in which validators emit queries encoding their configured key tags so root operators can passively census the anchor population [18]. The 2018 rollover drama turned precisely on what that census revealed.

### 4.2 Authenticated denial: NSEC, NSEC3, and the zone-enumeration tradeoff

Positive answers are easy to sign; *negative* answers (NXDOMAIN, NODATA) require proving a negative without signing an infinite space. DNSSEC's solution is the **denial-of-existence chain**: each name in a signed zone links to the next name in canonical ordering via an NSEC record, so a query for a nonexistent name falls into a *span* between two consecutive existing names, and the signed NSEC record covering that span proves the absence [2].

Plain NSEC leaks the entire zone: the "next" field is a plaintext name, so an attacker can *walk* the chain and enumerate every name — a serious concern for zones with sensitive names. RFC 5155 introduced **NSEC3**, which hashes owner names with a salt and iteration count before chaining [4]:

```python
import hashlib
def nsec3_hash(name: bytes, salt: bytes, iterations: int) -> bytes:
    h = hashlib.sha1(name + salt).digest()
    for _ in range(iterations):
        h = hashlib.sha1(h + salt).digest()
    return h
```

Only SHA-1 is registered as an NSEC3 hash algorithm — a conservative 2008 choice that is now a legacy wart. The tradeoff: NSEC3 converts enumeration from a single linear walk into a **dictionary attack** against salted SHA-1, which GPUs can still mount against predictable names. NSEC3 *opt-out* additionally permits unsigned delegations inside a signed zone, weakening the chain for operational convenience. The deep lesson: **authenticated denial is inherently in tension with namespace privacy**, a tension no hash function fully resolves.

### 4.3 Key and algorithm rollovers: the 2018 root KSK rollover

Rolling a KSK is a multi-stakeholder distributed commit with no atomicity primitive. RFC 5011 defines automated trust-anchor rollover: the new key is published alongside the old, resolvers observe it through a 30-day *add hold-down*, and only then is the old key revoked and removed [17]. RFC 6781 catalogs the timing choreography — *pre-publish*, *double-signature*, *double-DS* — for non-root zones [5]. Algorithm rollovers (e.g., RSA→ECDSA, per RFC 6840 [6]) are strictly harder: every validator must implement the new algorithm before signatures appear.

The root KSK rollover is the largest cryptographic migration ever attempted on the naming layer:

| Date | Event |
|---|---|
| 15 Jul 2010 | Root signed; KSK-2010 (key tag 19036, RSA/SHA-256) becomes trust anchor |
| Jul 2016 | ICANN publishes the KSK rollover operational plan |
| 11 Jul 2017 | KSK-2017 (key tag 20326) published in the root DNSKEY RRset; original roll date |
| 27 Sep 2017 | Rollover **postponed**: RFC 8145 signaling shows a significant resolver population still anchored only on KSK-2010 [15][18] |
| 11 Oct 2018, 16:00 UTC | Rollover executed; KSK-2010 revoked [14][16] |
| 4 Mar 2019 | ICANN OCTO publishes "Review of the 2018 DNSSEC KSK Rollover" [13] |

Why did 2017 fail while 2018 succeeded? First, the 2017 signaling data was misinterpreted: much of the stale-anchor signal came from misconfigured devices and from an end-user application emitting RFC 8145 signals from clients rather than resolvers, contaminating the census [14]. Second, ICANN's outreach measurably shrank the stale population through 2018. Third, the blast radius was bounded: non-validating resolvers (then roughly two-thirds of users) were unaffected, and among validators more than 99% were ready [16].

The IMC 2019 post-mortem [14] extracted a sobering lesson: discontinuities in trust-anchor signaling coincided with deliberate cache flushes by Cloudflare, Google, and a large European ISP — **operator behavior, not protocol timers, dominated the transition dynamics**. The pending root *algorithm* rollover (RSA/SHA-256 → ECDSA, studied by ICANN's 2023 design team) faces strictly harder preconditions, since algorithm agility requires code deployment, not just key distribution [13].

### 4.4 Encrypted transports: DoT, DoH, DoQ — privacy and centralization

Encrypted transports hide the *query stream* from on-path observers at the cost of moving trust to the recursive resolver operator:

| Property | DoT (RFC 7858) [8] | DoH (RFC 8484) [9] | DoQ (RFC 9250) [10] |
|---|---|---|---|
| Port | 853/TCP (dedicated) | 443/TCP (shared w/ HTTPS) | 853/UDP (dedicated) |
| Framing | Raw DNS over TLS | HTTP GET/POST | QUIC streams, ALPN `doq` |
| Handshake | TLS; RFC 8310 Strict/Opportunistic [11] | TLS via Web PKI | QUIC + TLS 1.3; 0-RTT possible |
| Blocking ease | Trivial (port 853) | Hard (blends with web traffic) | Moderate |

Two structural concerns dominate. **Centralization:** browser-driven DoH deployment concentrated enormous query volume on a handful of operators. The privacy gain against the local network is purchased by giving *one* remote party the complete query log of a large population — a worse position under compelled disclosure or breach. Oblivious DoH (RFC 9230) [12] separates *who* (seen by the proxy) from *what* (seen by the target), but deployment remains thin; the IETF ADD working group's DDR (RFC 9461) and SVCB records (RFC 9460) attempt to return control to network-designated resolvers. **Downgrade attacks:** RFC 8310's *Opportunistic* profile silently falls back to cleartext — an on-path attacker defeats it by blocking port 853, the STRIPTLS pattern. *Strict* mode fails closed but needs preconfigured authentication material [11]. **Fail-open encryption is theater against an active adversary**, and usability pressure to "just work" systematically erodes the security property.

### 4.5 Resolver behavior under attack and the last mile

RFC 4035 §5.3 specifies validating-resolver behavior with unusual care [3]: *bogus* data → `SERVFAIL`, never the data; *insecure* data (no chain of trust) → returned without AD; *indeterminate* (e.g., expired signatures mid-rollover) → `SERVFAIL`. The *last mile* — stub to recursive — remains the weakest segment: most stubs do not validate, consuming AD-bit claims from their recursive. Encrypted transports protect this segment's confidentiality but authenticate only the resolver endpoint, so a compromised resolver can lie *with valid-looking transport security*. Only stub-side validation closes the gap — reintroducing trust-anchor distribution at billions of endpoints.

Downgrade attacks compose across layers: an attacker blocking UDP/TCP 853 degrades opportunistic clients to cleartext DNS, where the same attacker strips DNSSEC — but a *validating* stub notices the missing signatures and SERVFAILs, while a non-validating stub accepts the forgery. **Each layer covers a distinct adversary capability**; removing any one reopens a specific, well-understood attack.

```bash
dig +dnssec dnssec-tools.org A        # AD flag => validation succeeded
dig . DNSKEY +dnssec                  # root DNSKEY RRset + RRSIGs
kdig -d @1.1.1.1 +tls example.com     # DoT probe on port 853
```

## 5 Empirical Evaluation / Proofs

The IMC 2019 rollover study [14] is DNS security's closest approach to a planetary-scale controlled experiment:

1. **Readiness was measurable and actionable.** RFC 8145 signaling showed the KSK-2010-only population declining through 2018; the October 2018 go-ahead was explicitly data-driven [14][15].
2. **The transition was operator-dominated.** Signaling discontinuities tracked deliberate cache flushes by major operators — protocol TTLs were second-order [14].
3. **Breakage was bounded and diagnosable.** Affected resolvers failed closed with SERVFAIL; *total* resolution failure is quickly noticed, and remediation (anchor update) was well-documented [13][16].
4. **Signaling contamination is a measurement hazard.** Client-emitted RFC 8145 signals inflated the apparent stale population — a caution for future census-driven migrations [14].

On deployment: APNIC Labs' continuous measurements place global DNSSEC *validation* in the low-to-mid thirty percent range of users, climbing slowly via large-ISP and public-resolver enablement. All major public resolvers now offer DoT/DoH, with DoQ support emerging post-2022 [10]. The qualitative picture is consistent: **the ecosystem migrates, but the long tail of non-validating, cleartext resolvers remains the binding constraint on any security assumption**.

On formal footing: symbolic-model analyses confirm the §1 soundness theorem under standard signature/hash assumptions. The proof gaps are instructive: (i) correct time is assumed, though validity intervals depend on the resolver's clock; (ii) trust-anchor authenticity is a *distribution* problem, not a cryptographic one; (iii) NSEC3's privacy property has no formal definition — "enumeration resistance" is quantified only via dictionary-attack cost models.

## 6 Limitations

1. **DNSSEC authenticates; it does not encrypt or authorize.** Query privacy and access control are out of scope — the composition with encrypted transports is not formally analyzed in any standard.
2. **The trust anchor is a single point of institutional trust.** The root KSK ceremony is procedural and human; compromise or coercion sits outside the cryptographic threat model.
3. **Algorithm agility is the looming crisis.** The root still signs with RSA/SHA-256 (algorithm 8). A post-quantum transition — with larger signatures straining UDP size limits — will dwarf the 2018 rollover in complexity; ICANN's 2023 algorithm-rollover study has begun this work with no timeline set [13].
4. **NSEC3's privacy guarantee is heuristic.** Salted SHA-1 with modest iterations deters casual walking but not resourced dictionary attacks; zones with sensitive names need aggressive parameters or split-horizon designs.
5. **Encrypted transports centralize metadata.** ODoH [12] and DDR are partial mitigations, not deployed defaults; the privacy analysis of "encrypt to a giant" remains the field's most uncomfortable open question.
6. **Measurement is adversarially fragile.** RFC 8145 signaling can be spoofed; DoH's indistinguishability from web traffic defeats passive census; every number in §5 carries these caveats.

---

## 7 Conclusion

DNS security is a tale of two chains: a *chain of trust* authenticating data from the root downward, and a *chain of custody* for queries that encrypted transports reroute and conceal. DNSSEC's KSK/ZSK/DS hierarchy elegantly solves key distribution *within* the DNS's own delegation structure, and the 2018 root KSK rollover proved even the hierarchy's root can be replaced in flight — at the cost of years of measurement, outreach, and one humbling postponement. NSEC3 shows that even auxiliary problems like authenticated denial carry irreducible tradeoffs between provability and privacy. The encrypted-transport turn closed the eavesdropping hole DNSSEC never addressed, but opened new ones: metadata centralization and downgrade-attack surface wherever opportunistic profiles meet active adversaries.

The forward agenda is clear: complete the algorithm-agility story (RSA/SHA-256 → ECDSA → post-quantum), deploy stub-side validation so the AD bit becomes verifiable rather than trusted, and resolve the privacy–centralization dilemma via ODoH, DDR-driven resolver diversity, or new primitives. The DNS survived its first half-century by being simple; securing its second requires it to be *verifiable* — and verification, as this thesis has shown, is a property of the whole system, not of any single protocol.
