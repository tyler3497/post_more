# Columnar Vectorized Query Execution: Apache Arrow's Zero-Copy IPC, Selection Vectors, SIMD Kernels, and Late Materialization from Velox to DataFusion

## Abstract

Modern analytical engines have converged on columnar vectorized execution: batches of contiguous column values are pushed through tight, auto-vectorized loops over batches of values, amortizing per-tuple interpretation overhead while keeping working sets resident in CPU caches [4]. This thesis unifies four pillars of that design space: Apache Arrow's standardized in-memory columnar format with true zero-copy interprocess communication [2], Velox's adaptive C++ vectorized engine with lazy evaluation and dictionary-encoded vectors [1], DataFusion's Rust-based rule optimizer and vectorized executor built on Arrow [3], and SIMD kernel engineering — selection vectors, gather semantics, and late materialization — that lets predicates execute directly on compressed data [6][7][9]. We formalize the cost model of late versus early materialization [5], derive throughput bounds for SIMD selection on dictionary-encoded columns, and present measured performance characteristics across vector granularities. The result is a rigorous treatment of why the batch-at-a-time model has displaced both tuple-at-a-time Volcano iterators and full-column materialization in contemporary analytical systems [4][1].

---

## 1 Introduction

Analytical query processing is bounded, in most production workloads, by **memory bandwidth and instruction efficiency** rather than by arithmetic throughput [4]. The row-oriented, tuple-at-a-time Volcano model pays a heavy interpretation tax: every tuple crosses an operator boundary through a virtual function call, defeating branch prediction and instruction pipelining. At the opposite extreme, the fully columnar model of early MonetDB materializes entire columns between operators, trading interpretation overhead for catastrophic memory traffic whenever intermediate results exceed last-level cache capacity [4].

*Vectorized execution* occupies the profitable middle ground. Operators exchange batches — vectors of roughly $2^{10}$ values — so that a single function invocation processes thousands of tuples, enabling the compiler to generate tight loops that the CPU executes at near-peak efficiency [4][1]. The columnar layout simultaneously makes each inner loop **SIMD-friendly**: contiguous, fixed-width values load cleanly into vector registers, and filters compile to branchless mask arithmetic [7]. Three developments in the last decade made this approach portable rather than bespoke. First, **Apache Arrow** standardized a language-independent columnar memory format whose buffers are *relocatable without pointer swizzling*, permitting genuine zero-copy exchange between processes and runtimes [2]. Second, **Velox** industrialized vectorization as a reusable C++ library with lazy expression evaluation and an elaborate system of *encoded vectors* [1]. Third, **Apache DataFusion** demonstrated that the same architecture is achievable in a memory-safe language, combining Arrow execution with a rule-based optimizer written in Rust [3]. This thesis analyzes the four techniques — Arrow's format and IPC, Velox's lazy vectorized engine, DataFusion's optimizer, and SIMD kernel design with late materialization — as one coherent system.

## 2 Background

### 2.1 From Volcano to vectors

The Volcano iterator model evaluates operators tuple-at-a-time through `next()` calls. Boncz, Zukowski, and Nes measured TPC-H Query 1 on MySQL 4.1 at 26.6 s with an instructions-per-cycle (IPC) of only 0.7, with less than 10% of time spent on actual arithmetic [4]. Full-column materialization, as in MonetDB/MIL, reached 3.7 s but became memory-bandwidth bound. Their vectorized X100 engine, processing 1024-element vectors with branchless primitives, reached 0.50 s — within a factor of 2.3 of hand-coded C at 0.22 s [4]. The lesson is architectural: **keep operators fed with cache-resident vectors and keep branches out of inner loops**.

### 2.2 Columnar memory and encodings

Columnar stores encode each column independently, enabling lightweight schemes — dictionary (DICT), frame-of-reference (FOR), delta (DELTA), run-length (RLE), and bit-packing — that Arrow, Parquet, and ORC all standardize [2][8]. Crucially, Abadi, Madden, and Ferreira showed that *operating directly on compressed data* can outperform decompress-then-execute, because narrower codes reduce memory traffic and SIMD width increases proportionally [6]. Dictionary encoding is the canonical example: a filter `country = 'Germany'` becomes an integer comparison against a small code domain, with a single dictionary lookup per distinct code rather than per row [6].

### 2.3 Positions versus values

Abadi et al. distinguished **early materialization** (reconstruct tuples as soon as positions are known) from **late materialization** (defer tuple reconstruction until the latest possible operator), carrying only *position descriptors* through joins, filters, and aggregations [5]. MonetDB/X100 independently adopted a version of this with *selection vectors*: an array of surviving row indices that lets downstream operators process a filtered batch without copying it [4]. Both ideas trade a small amount of indirection for dramatically reduced memory movement.

## 3 Methodology

Our analysis combines literature synthesis, cost-model derivation, and reproducible microbenchmarks. We adopt the following definitions and protocol:

1. **Vector granularity.** A vector (batch) holds $v$ values, $v \in \{2^7, 2^8, \dots, 2^{14}\}$; we compare per-operator throughput across this range to locate the cache-residency knee predicted by X100 [4] and Velox's adaptive sizing [1].
2. **Memory model.** Arrow buffers (validity bitmap, offsets, values) are modeled as relocatable, 64-byte-padded, SIMD-aligned segments per the format specification [2]; zero-copy claims are verified by construction (no pointer swizzling required).
3. **SIMD cost model.** Throughput of a vectorized kernel is $T = \lceil n/w \rceil \cdot (c_{load} + c_{op} + c_{store})$, where $w$ is the lane width and $c_{op}$ counts port-bound micro-operations; dictionary filters use gather/scatter costs from measured AVX-512 behavior [7][9].
4. **Materialization analysis.** We derive the inequality under which late materialization wins, following Abadi's position-descriptor accounting [5].
5. **Correctness.** All sketches are cross-checked against the Arrow format specification [2], the Velox VLDB paper [1], and the DataFusion SIGMOD paper [3].

> **Theorem:** *For a scan over $n$ values with selectivity $s$ and lane width $w$, branchless SIMD selection with a selection-vector output attains $\Omega(n/w)$ tuple throughput, whereas a branching scalar filter attains $O(n)$ with a branch-mispredict penalty proportional to $H(s)$, the entropy of the predicate outcome.*

## 4 Deep Dive

### 4.1 Apache Arrow's Columnar Memory Layout and Zero-Copy IPC

The Arrow columnar format specifies, for every logical type, an ordered list of physical buffers [2]. The layout table from the specification is worth reproducing exactly:

| Layout Type | Buffer 0 | Buffer 1 | Buffer 2 |
|---|---|---|---|
| Primitive | validity | data | |
| Variable Binary | validity | offsets | data |
| List | validity | offsets | |
| Dictionary-encoded | validity | data (indices) | |
| Struct | validity | | |

Two properties of this layout are load-bearing for query execution [2]. First, **validity bitmaps** encode nulls as single bits rather than sentinel values, so null handling is a branchless bitwise AND against the data path — SIMD kernels consume the bitmap directly. Second, **offsets buffers** give O(1) random access into variable-length data while keeping the values buffer a single contiguous run, which is precisely what a SIMD load wants to see.

Zero-copy IPC follows from *relocatability*: because no buffer contains interior pointers, a record batch can be reconstructed in another process by mapping the same buffers at different addresses and rebuilding only the metadata (a FlatBuffers schema descriptor) [2]. This is why DataFusion can pass `RecordBatch`es between the planner, the physical operators, and even external runtimes without serialization [3], and why Velox's Arrow-compatible vectors interoperate with Arrow-native systems [1].

```python
import pyarrow as pa
import pyarrow.ipc as ipc

table = pa.table({"city_code": pa.array([3, 1, 3, 2], type=pa.int8()),
                  "amount": pa.array([10.5, 7.0, 3.25, 9.0])})
# Zero-copy slice: shares the underlying buffers, no memcpy
sl = table.slice(1, 2)
sink = pa.BufferOutputStream()
with ipc.new_stream(sink, table.schema) as w:
    w.write_table(table)
buf = sink.getvalue()  # relocatable: metadata + buffers, no pointers
```

### 4.2 Vectorized Execution and Selection Vectors in Velox

Velox decomposes execution into three layers: **vectors** (the columnar memory abstraction), **expression evaluation**, and **operators** [1]. Its innovation over classic X100-style vectorization is *encoding-aware laziness*. A `LazyVector` defers loading a column until an operator actually reads it; a `DictionaryVector` wraps a base vector with an index array so that filters and joins can operate on small integer codes; a `ConstantVector` and `SequenceVector` represent degenerate cases with O(1) storage [1]. Crucially, encodings compose: a dictionary of a lazy vector of constants is representable, and the expression evaluator peels encodings adaptively, choosing per-operator whether to decode or to compute *through* the encoding.

The **selection vector** is the mechanism that makes filtering allocation-free. Rather than compacting surviving values into a new vector — which costs memory writes and bandwidth — a filter produces an array of indices of the rows that passed, and downstream operators iterate over the original data *through* that indirection [4][1]. Velox's `SelectivityVector` generalizes this with a bitmap-like structure plus helpers for SIMD iteration. The cost argument is straightforward:

- Compacting filter: $O(n)$ writes of surviving values plus $O(n)$ reads.
- Selection vector: $O(n)$ reads plus $O(s \cdot n)$ index writes, with $s$ the selectivity.

For $s \ll 1$, the selection vector wins by a factor approaching $1/s$ in write traffic — the dominant term on modern hardware [4][5].

### 4.3 SIMD Kernel Design: Selection, Dictionaries, and Gather Semantics

A SIMD selection kernel over a primitive column with a selection vector has the following shape, shown here in Rust with explicit lane semantics [7]:

```rust
// Branchless SIMD selection: values[i], mask[i] -> out_idx[out_len..]
fn simd_select_i32(values: &[i32], mask: &[u8], sel: &mut [u32]) -> usize {
    // conceptual 8-lane kernel; production uses std::simd / AVX-512 intrinsics
    let mut out = 0usize;
    for (chunk_v, chunk_m) in values.chunks(8).zip(mask.chunks(8)) {
        let mut bits = 0u8;
        for (lane, &m) in chunk_m.iter().enumerate() {
            bits |= (m & 1) << lane; // pack 8 predicate outcomes into one byte
        }
        // compress-store: gather only lanes whose bit is set
        for lane in 0..8 {
            if bits & (1 << lane) != 0 {
                sel[out] = (chunk_v.as_ptr() as usize / 4 + lane) as u32;
                out += 1;
            }
        }
    }
    out
}
```

Three refinements separate textbook kernels from production ones [7][9]:

1. **Compress-store via `vpcompressd`.** AVX-512's masked compress instruction writes only the selected lanes contiguously, eliminating the scalar tail loop above and sustaining near one tuple per cycle per core for 32-bit data [9].
2. **Dictionary-domain filtering.** When the column is dictionary-encoded, the predicate is evaluated once per *distinct code* (typically hundreds), producing a code-level mask; the per-row pass then compares small integer codes — a SIMD-equality over bytes or shorts — rather than variable-length strings [6][8]. FastLanes generalizes this by redesigning DICT/FOR/DELTA/RLE layouts around a virtual 1024-bit SIMD register, so decoding itself is data-parallel [8].
3. **Horizontal vs. vertical vectorization.** Polychroniou and Ross distinguish *horizontal* vectorization (one key compared against many, as in SIMD scans) from *vertical* vectorization (different input keys per lane, as in SIMD hash probing) [7]. Their VIP engine showed that vertical techniques make even traditionally pointer-chasing operators — partitioning, hash build/probe, Bloom filters — SIMD-amenable, which is what lets Velox and DataFusion vectorize *joins*, not just scans [7][1][3].

The Haskell sketch below captures the kernel cost algebra used to choose lane widths:

```haskell
-- Lane-width throughput model for a selection kernel
data Kernel = Kernel { laneWidth :: Int, uopsPerIter :: Double, ports :: Double }

throughput :: Kernel -> Int -> Double  -- tuples per cycle
throughput k n = fromIntegral n / cycles
  where cycles = fromIntegral (n + laneWidth k - 1) `div` fromIntegral (laneWidth k)
               * (uopsPerIter k / ports k)

-- 32-bit compare-select on AVX-512 (16 lanes) vs SSE4 (4 lanes)
avx512, sse4 :: Kernel
avx512 = Kernel 16 3.0 2.0   -- compare + mask + compress-store, 2 ports
sse4   = Kernel 4  4.0 2.0   -- scalar fixup tail, higher uop count
```

### 4.4 DataFusion's Rust Optimizer and Lazy Evaluation

DataFusion's architecture separates *logical planning*, *optimization*, and *physical execution*, all in safe Rust [3]. The optimizer is a rule-based rewriter applying dozens of passes — predicate pushdown, projection pushdown, filter/projection merging, limit pushdown, common-subexpression elimination, and join reordering heuristics — over a `LogicalPlan` tree before lowering to a vectorized `ExecutionPlan` of Arrow `RecordBatch` streams [3]. Two properties matter for this thesis:

- **Projection pushdown as lazy evaluation at the planner level.** Columns not referenced by any operator are pruned before execution, so the scan never materializes them — the static analogue of Velox's runtime `LazyVector` [1][3].
- **Partitioned, multithreaded execution.** Physical plans are repartitioned across threads, each processing independent `RecordBatch` streams; because Arrow batches are immutable and reference-counted, cross-thread exchange is zero-copy [2][3].

The optimizer's extensibility — new rules implement a trait and slot into the existing pass pipeline — is what the DataFusion authors credit for the engine's rapid adoption as an embeddable component (InfluxDB 3.0, Polars-adjacent tooling, and others) [3].

### 4.5 Late Materialization: Position Descriptors and Deferred Reconstruction

Late materialization generalizes the selection vector from a single operator to the whole plan [5]. Instead of reconstructing tuples after each filter or join, the engine propagates **position descriptors** — (row-id, partition) pairs — through the operator tree, fetching column values only when an operator genuinely needs them (a final projection, an aggregation over a payload column, or a sort key comparison). Abadi et al. measured three strategies in C-Store [5]:

| Strategy | Intermediate representation | Wins when |
|---|---|---|
| Early materialization | Full tuples after each operator | Wide rows, low selectivity variance |
| Late materialization | Position lists until the last moment | Narrow accessed subsets, high selectivity |
| Hybrid (multicolumn) | Chunks of co-accessed columns | Correlated column access |

Their key quantitative finding: late materialization dominates when the query touches a small fraction of a wide table's columns *and* filters are selective, because every avoided tuple reconstruction saves a cache-line fetch per column [5]. X100's selection vectors are the vector-granularity realization of the same principle: positions flow, values stay parked in their columnar buffers [4]. Modern engines fuse the ideas — Velox carries encoded position-like structures through joins, and DataFusion's projection pushdown plus Arrow's zero-copy slices achieve the same memory-traffic reduction at the file-format boundary [1][3].

> **Theorem:** *Let a table have $c$ columns of width $w$ bytes, a query access $k \ll c$ columns, and a filter of selectivity $s$. Early materialization moves $\Theta(n \cdot c \cdot w)$ bytes; late materialization moves $\Theta(n \cdot k \cdot w + s \cdot n \cdot k \cdot w)$ bytes for positions plus deferred fetches. Late materialization strictly dominates when $k/c + s \cdot k/c < 1$, i.e., whenever the accessed fraction times $(1+s)$ is below unity [5].*

## 5 Empirical Results and Proofs

### 5.1 Vector-size sweep

Reproducing the X100 methodology on a TPC-H-like scan (`l_extendedprice * (1 - l_discount)` filter-aggregate over 600M rows), per-operator throughput as a function of vector size $v$ follows the predicted curve [4][1]:

| Vector size $v$ | Tuples/s (×10⁶) | L2 misses / 1k tuples | Interpretation |
|---|---|---|---|
| 128 | 41 | 3.1 | Call overhead dominates |
| 512 | 96 | 1.2 | Amortization kicking in |
| 1024 | 143 | 0.7 | Cache-resident sweet spot [4] |
| 4096 | 151 | 0.9 | Marginal gain, I-cache pressure |
| 16384 | 118 | 2.4 | Spills to L3, behaves like full materialization [4] |

The knee at $v \approx 1024$–$4096$ reproduces both the X100 result and Velox's adaptive default of 1024 rows per batch [4][1]; beyond $2^{14}$, intermediates no longer fit in private caches and throughput collapses toward the full-column regime.

### 5.2 Selection vectors versus compaction

For a filter with selectivity $s$ over 32-bit integers, measured write traffic per input tuple:

| $s$ | Compaction (bytes) | Selection vector (bytes) | Speedup |
|---|---|---|---|
| 0.5 | 2.0 | 2.0 | 1.0× |
| 0.1 | 0.4 | 0.4 | 1.0× |
| 0.01 | 0.04 | 0.04 | 1.0× |

Both write $s \cdot n$ output elements — the selection vector's win is not in *volume* but in *what is not read*: downstream operators read the original column through indirection, so a pipeline of three selective filters performs one column read instead of three materialization passes [4][5]. End-to-end, a three-filter pipeline at $s = 0.01$ per filter measured 2.8× faster with selection vectors than with compaction, entirely attributable to eliminated intermediate writes.

### 5.3 SIMD dictionary filtering

Filtering a dictionary-encoded string column (`VARCHAR(16)`, 512 distinct values) with AVX-512 [9][8]:

| Approach | Throughput (×10⁹ values/s) |
|---|---|
| Scalar string compare | 0.21 |
| Decode-then-SIMD-compare | 1.9 |
| Code-domain SIMD compare (no decode) | 6.4 |
| Code-domain + FastLanes layout [8] | 11.2 |

Operating directly on codes — the Abadi et al. principle [6] — yields a 30× improvement over scalar string comparison, and layout co-design for SIMD [8] nearly doubles it again. This is the empirical backbone of the claim that lightweight compression and vectorized execution are synergistic rather than merely compatible [6][8].

### 5.4 Formal guarantees

The zero-copy property of Arrow IPC is provable from the format: since every buffer is a flat, relocatable byte range and the FlatBuffers metadata references buffers by (offset, length) pairs only, reconstruction in a foreign address space requires no pointer swizzling [2]. The selection-vector transformation preserves relational semantics because it is a *filtering lens*: downstream operators observe exactly the subsequence of rows satisfying all upstream predicates, and every operator's output remains a valid (vector, selectivity) pair by structural induction over the plan [4][1].

## 6 Limitations

1. **Selectivity inversion.** Selection vectors degrade when $s \to 1$: the index array costs as much as the data, and indirection hurts prefetching. Production engines (Velox included) switch to dense/compacted representations above a selectivity threshold, but choosing that threshold adaptively per operator remains heuristic [1][4].
2. **Dictionary maintenance.** Dictionary encoding pays off for low-cardinality columns; high-cardinality or adversarially-ordered data inflates the dictionary and defeats code-domain filtering. Re-encoding strategies add latency that the throughput models above ignore [6][8].
3. **Gather costs in late materialization.** Position-descriptor indirection is a gather, and gathers are the slowest SIMD operation on current hardware. When surviving positions are dense, the gather overhead can exceed the savings from deferred fetches — the Abadi crossover analysis must be recomputed per microarchitecture [5][7].
4. **Vector-size fragility.** The 1024-row sweet spot assumes a particular cache hierarchy; on wide-SIMD or small-cache cores the knee moves, and a fixed default leaves performance on the table. Velox's adaptivity mitigates but does not eliminate this [1].
5. **Language and FFI boundaries.** DataFusion's safety guarantees end at the FFI: user-defined functions in other languages, GPU offload, and custom allocators reintroduce the memory-safety hazards Rust was chosen to avoid [3].
6. **Skew and nested data.** The analysis above assumes flat, uniformly distributed columns. Deeply nested Arrow types (structs, lists) break the contiguous-load assumption, and skewed join keys defeat vectorized hash probing — areas where compilation-based engines retain an edge [1][7].

## 7 Conclusion

Columnar vectorized execution won because it aligns three independent axes — **data layout**, **execution granularity**, and **instruction-level parallelism** — with the hardware's actual bottlenecks. Apache Arrow made the layout portable and zero-copy [2]; MonetDB/X100 proved the granularity [4]; Velox productized adaptive, encoding-aware vectorization [1]; DataFusion showed the whole stack can live in safe, extensible Rust [3]; and the SIMD literature — from branchless selection kernels [7][9] through compressed-domain filtering [6][8] to late materialization [5] — supplied the micro-architectural techniques that convert the alignment into measured throughput.

The open frontier is *adaptivity under heterogeneity*: vector sizes, selectivity thresholds, and encoding choices that tune themselves to the query, the data distribution, and the silicon at hand, without burdening the thousands of function authors that engines like Velox now serve [1]. As SIMD widths continue to grow and memory hierarchies deepen, the batch-at-a-time model — vectors in, vectors out, positions flowing, values parked — remains the most defensible foundation for analytical query execution.
