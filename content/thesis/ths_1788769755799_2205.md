# RISC-V Vector Extension 1.0: LMUL Register Grouping, Segmented Memory Access, and Auto-Vectorization in LLVM

## Abstract

The RISC-V "V" vector extension (RVV 1.0), ratified in 2021, introduces a fundamentally different vector processing model from fixed-width SIMD ISAs such as x86 AVX-512 and Arm NEON: vector-length-agnostic execution, register grouping via the *LMUL* parameter, and polymorphic instructions configured at runtime through the `vsetvli`/`vsetvl` configuration instructions [1][2]. This thesis provides a rigorous analysis of three core architectural pillars of RVV 1.0: (i) LMUL register grouping, including fractional LMULs and their constraints relative to the minimum supported element width (SEW~min~) and ELEN; (ii) segmented memory access — unit-stride, strided, and indexed (gather/scatter) loads and stores — together with whole-register and fault-only-first transfers; and (iii) the auto-vectorization path in LLVM, where scalable vectors, VPlan, and LMUL-aware cost models drive loop vectorization for RVV targets [4][7]. We develop a formal model of VLMAX and stripmining correctness, present verified code patterns in assembly and C intrinsics, and synthesize recent empirical evidence — including a 2026 evaluation of GCC 15 and Clang/LLVM 21 auto-vectorization on real RVV 1.0 hardware [5] — to quantify the performance behavior of LMUL selection, predication overhead, and strided access. The work concludes with limitations of the current ecosystem: cost-model gaps, masked-operation overheads, and the partial maturity of compilers on irregular memory patterns.

## 1 Introduction

Vector processing has been a fixture of high-performance computing since the Cray-1, yet commodity ISAs have historically exposed vectors as fixed-width SIMD registers: SSE, AVX, AVX-512, and NEON all bind software to a *specific* register width. Portability across implementations of the same ISA requires recompilation for each width, or the lowest common denominator. The RISC-V Vector Extension (RVV) rejects this binding entirely. RVV 1.0, ratified by RISC-V International in 2021 and now integrated into the ratified unprivileged ISA [1][3], defines a *vector-length-agnostic* programming model: the hardware parameter VLEN (bits per vector register, a power of two, ≥ 8) is unknown to portable software, and the `vsetvli` instruction queries the implementation to obtain the application vector length `vl` — the number of elements per operation — at runtime [2].

This design decision has deep consequences. Because a single binary must execute correctly on VLEN=128 and VLEN=512 implementations alike, loops are *stripmined*: each iteration processes `vl` elements, `avl` (the application vector length, i.e., the remaining element count) is decremented by `vl`, and the loop repeats until exhaustion. The vector configuration — selected element width (SEW), LMUL, tail/mask agnostic policies, and rounding mode — is held in the `vtype` CSR, and every vector instruction's behavior is a function of the current `(vtype, vl)` state [2].

Three mechanisms distinguish RVV 1.0 most sharply from competing vector ISAs, and they form the subject of this thesis:

1. **LMUL register grouping.** The 32 architectural vector registers `v0`–`v31` may be *grouped* so that a single logical operand spans 1, 2, 4, or 8 physical registers (LMUL ∈ {1, 2, 4, 8}), or a fraction of one register (LMUL ∈ {1/2, 1/4, 1/8}). Grouping multiplies the effective vector length: VLMAX = LMUL × VLEN / SEW — a tunable knob trading register pressure against stripmine iteration count, with no analogue in fixed-width SIMD.
2. **Segmented memory access.** Beyond unit-stride loads/stores, RVV provides strided, indexed (gather/scatter), segment, and whole-register transfers, plus fault-only-first loads for speculative vectorization. Segment operations address *array-of-structures* layouts in a single instruction stream.
3. **LLVM auto-vectorization for scalable vectors.** LLVM's loop vectorizer models RVV through scalable vector types, the VPlan framework, and LMUL-aware cost models [7][8] — imperfectly, as recent hardware studies show [5].

Our contributions are: (a) a consolidated formal account of LMUL grouping constraints and the VLMAX invariant; (b) a taxonomy of segmented memory access with correctness arguments; (c) verified assembly and intrinsic code patterns; (d) an empirical synthesis of compiler auto-vectorization quality on real RVV 1.0 silicon; and (e) an honest accounting of limitations.

> **Theorem: Stripmining Termination.** *Let `avl_0 > 0` be the initial application vector length and let each loop iteration execute `vsetvli rd, rs1, e<SEW>, m<LMUL>` with `avl = rs1`. The hardware guarantees `1 ≤ vl ≤ min(avl, VLMAX)`. Then the stripmined loop terminates after finitely many iterations and processes exactly `avl_0` elements.*

*Proof sketch.* Each iteration sets `vl ≥ 1` whenever `avl > 0` (the `vsetvli` contract: if `avl > 0` then `vl > 0` [2]), and the loop decrements `avl ← avl − vl`. The sequence of `avl` values is a strictly decreasing sequence of non-negative integers, hence finite; the sum of consumed `vl` values telescopes to `avl_0`. ∎

## 2 Background

### 2.1 The vector programmer's model

RVV adds 32 vector registers and seven unprivileged CSRs — `vstart`, `vxsat`, `vxrm`, `vcsr`, `vtype`, `vl`, `vlenb` — to the base scalar ISA [3]. The central configuration instruction is `vsetvli rd, rs1, vtypei`, which writes `vtype` and `vl` and returns the granted `vl` in `rd`; `vsetivli` and `vsetvl` are immediate and register-`avl` variants. SEW takes values 8, 16, 32, 64 (up to ELEN), and register state is reinterpreted per instruction under the current SEW.

Two agnostic policies govern elements an instruction does not actively write: *tail-agnostic* (`ta`) permits the tail (elements `vl..VLMAX-1`) to be overwritten or left undisturbed, and *mask-agnostic* (`ma`) does the same for masked-off body elements. Setting both gives implementations maximum freedom to avoid read-modify-write hazards and is the default in the modern intrinsic API [4].

### 2.2 Related vector ISAs

Arm SVE/SVE2 shares RVV's length-agnostic philosophy but lacks LMUL-style grouping and segment memory operations, using first-class predicate registers instead of RVV's single mask register `v0` [2]. AVX-512 offers masking and scatter/gather but is fixed-width. The distinctive RVV combination — *runtime-configurable width × grouping × segments* — is what this thesis analyzes.

### 2.3 Toolchain state

RVV 1.0 is supported by upstream LLVM (Clang 19 supports the v1.0 intrinsic specification; scalable auto-vectorization was enabled by default in LLVM 16) and GCC 14+, with the intrinsic API standardized by the RISC-V C intrinsics task group [4]. Real RVV 1.0 hardware — e.g., SpacemiT X60 / Milk-V Jupiter — now permits cycle-level validation of compiler output [5].

## 3 Methodology

Our analysis proceeds along three axes. **Formal**: we extract invariants (VLMAX, LMUL legality, mask layout) directly from the ratified specification [1][2][3] and prove termination and configuration-safety properties. **Constructive**: we exhibit canonical code patterns — stripmined DAXPY in assembly, segment-load transpose in C intrinsics [4] — verified against documented instruction semantics. **Empirical**: we synthesize published measurements from (i) the Euro-Par 2026 study of GCC 15 and LLVM 21 auto-vectorization on real RVV 1.0 hardware [5], (ii) the RAVE vector-execution analyzer [6], and (iii) the VecIntrinBench intrinsic-migration study [9].

## 4 Deep Dive

### 4.1 LMUL register grouping: mechanics and legality

LMUL is encoded as a signed 3-bit field `vlmul` in `vtype`, with LMUL = 2^`vlmul`. The derived quantity

```
VLMAX = LMUL × VLEN / SEW
```

is the maximum number of elements any single vector instruction can operate on under the current configuration [2][3]. For LMUL > 1, architectural registers are grouped: with LMUL=2, register specifier `n` denotes the pair `(v_{2n}, v_{2n+1})`, and only even-numbered specifiers are legal; LMUL=4 and LMUL=8 group four and eight registers respectively. This preserves the encoding space: the 5-bit register field still addresses 32 registers, but only aligned groups are valid operands.

**Fractional LMUL** (1/2, 1/4, 1/8) permits *narrow* element operations to occupy part of a register — e.g., processing `i8` data with `m8` semantics is impossible, but `mf8` with SEW=8 uses one eighth of a register per operand. Legality is governed by the fundamental constraint [3]:

> **Theorem: Fractional LMUL Legality.** *A configuration with LMUL < SEW~min~/ELEN is reserved (implementations may set `vill`). For standard extensions with ELEN=32, fractional LMULs 1/2 and 1/4 must be supported; with ELEN=64, 1/2, 1/4, and 1/8 must be supported. For any supported fractional LMUL, SEW settings between SEW~min~ and LMUL × ELEN inclusive must be supported.*

The rationale is physical: with VLEN=ELEN=32 and SEW~min~=8, LMUL=1/8 would provide only four bits of storage per register — insufficient for even one element. The constraint guarantees that every legal configuration can hold at least one element per register group.

| `vlmul[2:0]` | LMUL | # register groups | VLMAX (VLEN=128, SEW=32) |
|---|---|---|---|
| `001` | 1/8 | 32 | 0.5 (reserved unless ELEN=64) |
| `010` | 1/4 | 32 | 1 |
| `011` | 1/2 | 32 | 2 |
| `000` | 1 | 32 | 4 |
| `100` | 2 | 16 | 8 |
| `101` | 4 | 8 | 16 |
| `110` | 8 | 4 | 32 |

*Table 1: LMUL encodings and effective vector lengths. Fractional rows assume ELEN ≥ 64 where required [2][3].*

The practical significance of LMUL is that it decouples *software vector length* from *hardware VLEN*. A compiler targeting unknown VLEN can request LMUL=8 to multiply the elements per stripmine iteration, amortizing loop overhead — at the cost of register pressure (only 4 groups available) and potential spill. LLVM's cost model treats LMUL as a first-class vectorization-factor multiplier [7].

### 4.2 Segmented memory access: unit-stride, strided, indexed, segment

RVV 1.0 defines the richest vector memory-access repertoire of any commodity ISA [2]: **unit-stride** (`vle*`/`vse*`, contiguous, the fast path); **strided** (`vlse*`/`vsse*`, elements separated by a byte stride); **indexed** (`vluxei*`/`vloxei*`, `vsuxei*`/`vsoxei*`, gather/scatter with per-element offsets); **segment** (`vlseg2e*`…`vlseg8e*`, unit-stride and strided variants) — the hardware transpose primitive for array-of-structures data; **whole-register** (`vlm.v`/`vsm.v`, VLEN/8 × NFIELDS bytes irrespective of `vtype`, for spill/fill); and **fault-only-first** (`vle*_ff`), which reports via `vl` how many elements loaded before a fault, enabling speculative vectorization.

Segment loads deserve emphasis. Consider an AoS array of RGB pixels:

```c
// Scalar AoS loop: 3 address computations + 3 loads per pixel
for (i = 0; i < n; i++) { r[i] = px[3*i]; g[i] = px[3*i+1]; b[i] = px[3*i+2]; }
```

A single `vlseg3e8.v v0, (a0)` loads `vl` bytes into each of `v0`, `v1`, `v2` — the *transpose is performed by the memory unit*, not by shuffle instructions. The intrinsic form is:

```c
#include <riscv_vector.h>
void deinterleave_rgb(uint8_t *px, uint8_t *r, uint8_t *g, uint8_t *b, size_t n) {
    size_t vl;
    for (size_t i = 0; i < n; i += vl) {
        vl = __riscv_vsetvli(n - i, __riscv_v_u8m1, __riscv_v_ta_ma);
        vuint8m1x3_t rgb = __riscv_vlseg3e8_v_u8m1x3(px + 3*i, vl);
        __riscv_vse8_v_u8m1(r + i, __riscv_vget_v_u8m1x3_u8m1(rgb, 0), vl);
        __riscv_vse8_v_u8m1(g + i, __riscv_vget_v_u8m1x3_u8m1(rgb, 1), vl);
        __riscv_vse8_v_u8m1(b + i, __riscv_vget_v_u8m1x3_u8m1(rgb, 2), vl);
    }
}
```

Segment operations consume multiple register groups (NFIELDS groups of LMUL), so their interaction with LMUL grouping is direct: `vlseg8e32` with LMUL=8 is illegal (8 fields × 8 registers exceeds the file), and the spec constrains NFIELDS × LMUL ≤ 8 [2] — a *hard* architectural coupling between the memory system and register grouping that a compiler must co-select.

### 4.3 Masking, predication, and tail policies

Every vector arithmetic instruction admits a masked form (`, v0.t`), where `v0` holds the mask; inactive elements obey the mask-agnostic policy and tail elements (`vl..VLMAX-1`) the tail policy. The modern intrinsic API defaults to `_ta/_ma` unless `_mu`/`_tu` undisturbed variants are explicitly requested [4]. With `ta`, the tail of the last partial iteration may be clobbered — safe because the stripmine idiom never re-reads it once `avl` reaches zero.

Masked execution is also the mechanism for *tail folding*: instead of a scalar epilogue, the compiler emits a final vector iteration with an active-lane mask, eliminating the remainder loop entirely [8]. RVV's mask model — one bit per element packed into `v0` at SEW-dependent bit positions — requires mask-layout awareness when SEW changes mid-kernel (spec §4.5) [2].

### 4.4 Stripmined DAXPY in assembly: the canonical pattern

The following hand-written RVV 1.0 DAXPY (`y[i] = a*x[i] + y[i]`, double precision) exhibits the complete configuration idiom — `vsetvli` query, grouped loads, fused multiply-add, and stripmine bookkeeping:

```asm
# a0=n, a1=x, a2=y, fa0=a  (RV64, ABI: args in a0-a2/fa0)
daxpy:
    beqz   a0, done
loop:
    vsetvli t0, a0, e64, m8, ta, ma   # vl = min(n, 8*VLEN/64); LMUL=8
    vle64.v  v0, (a1)                  # x[i..i+vl), group v0-v7
    vle64.v  v8, (a2)                  # y[i..i+vl), group v8-v15
    vfmacc.vf v8, fa0, v0              # y += a*x  (fused, masked-off agnostic)
    vse64.v  v8, (a2)                  # store y
    slli   t1, t0, 3                   # vl * sizeof(double)
    add    a1, a1, t1
    add    a2, a2, t1
    sub    a0, a0, t0                  # n -= vl
    bnez   a0, loop
done:
    ret
```

Note the LMUL=8 choice: each iteration moves `8·VLEN/64` doubles per stream with only four memory instructions in the loop body, amortizing the `vsetvli` + branch overhead. On VLEN=128 this processes 16 doubles per iteration; on VLEN=512, 64 — *the same binary*. This is the portability dividend fixed-width SIMD cannot pay [1][5].

### 4.5 Auto-vectorization in LLVM: scalable vectors, VPlan, and LMUL-aware cost modeling

LLVM models RVV through *scalable* vector types: `<vscale x 4 x i32>` denotes 4×`vscale` lanes where `vscale` is the runtime ratio VLEN/128 [8]. The loop vectorizer's VPlan framework selects a vectorization factor (VF) expressed as a `(fixed, scalable)` pair, and for RISC-V the scalable VF is multiplied by the chosen LMUL. Key mechanisms [7][8]:

1. **Scalable vectorization by default** (LLVM 16+): the loop vectorizer may choose scalable VFs when profitable [8].
2. **Vector-length-specific mode**: `-mllvm --riscv-v-vector-bits-min=N` pins a minimum VLEN, letting the vectorizer assume `vscale ≥ N/128` [7].
3. **Tail folding with active-lane masks**: the vectorizer prefers folding the remainder into a masked final iteration over scalar epilogues [8].
4. **Interleave factor selection**: UF is chosen alongside VF; combined with LMUL this yields the "effective VF" the cost model prices.
5. **Intrinsic lowering**: Clang's RVV intrinsics [4] lower to the same scalable IR, so hand-intrinsified and auto-vectorized code share the backend.

The discourse among LLVM developers highlights LMUL's unique role: unlike SVE, where the vectorizer picks one width, RVV's LMUL lets the *same* loop nest use LMUL=8 for wide `f32` streams and fractional LMUL for narrow `i8` streams simultaneously [7]. The cost model must therefore solve a small integer optimization — choose per-statement LMUL to minimize estimated cycles under the register-file constraint — a problem with no SIMD precedent.

## 5 Empirical Results and Formal Arguments

### 5.1 Formal arguments: configuration safety

Beyond termination (§1), two safety properties follow from the spec:

> **Theorem: Configuration Monotonicity.** *`vsetvli` guarantees `vl > 0 ⟺ avl > 0` and `vl ≤ min(avl, VLMAX)`. A stripmined loop recomputing `vl` from the residual `avl` each iteration never overruns the arrays.*

> **Theorem: Group Alignment Safety.** *If every vector operand specifier `n` satisfies `n mod LMUL == 0` for LMUL ∈ {2,4,8}, no two operands of one instruction alias the same physical register. The intrinsic type system (`vint32m2_t` etc.) enforces this by construction [4].*

### 5.2 Empirical: GCC 15 vs. LLVM 21 on RVV 1.0 hardware

The most rigorous recent evaluation is Shi et al. (Euro-Par 2026), who built assembly microbenchmarks to establish performance ceilings on real RVV 1.0 hardware (Milk-V Jupiter / SpacemiT X60, BPI-F3) and then compared GCC 15 and Clang/LLVM 21 auto-vectorization across six HPC/ML proxy applications (stream, spmv, sgemm, dgemm, YOLOv3, AlexNet), with `perf` counter validation [5]. Salient findings:

| Application | GCC 15 autovec speedup | Clang 21 autovec speedup | Winner |
|---|---|---|---|
| sgemm | ~1.85× | ~2.4× | Clang 21 |
| dgemm | moderate | better | Clang 21 |
| AlexNet | ~1.45× | ~1.2× | GCC 15 |
| YOLOv3 | better | worse | GCC 15 |
| stream (mem-bound) | ~1.0× (no benefit) | ~0.8× (regression) | neither |
| spmv (irregular) | ~1.0× | ~1.0× | neither |

*Table 2: Auto-vectorization speedups vs. GCC 15 scalar baseline, synthesized from [5]. Values approximate; see original Fig. 5.*

Three conclusions bear directly on this thesis. **First**, Clang 21's GEMM advantage is attributed to *more aggressive instruction reduction* (4.7× fewer retired instructions in SGEMM) driven by better LMUL selection and scheduling — LLVM's LMUL-aware cost model paying off on regular, compute-bound loops [5]. **Second**, the *default* LMUL selection in both compilers performs close to optimal across the studied kernels [5]. **Third**, *predication overhead and strided loads* are identified as challenges current cost models do not fully capture, and Clang 21's vectorized `stream` is ~20% *slower* than scalar — a cost-model failure on a memory-bound kernel [5].

### 5.3 Empirical: simulation, analysis, and migration studies

Complementary evidence comes from three directions. The RAVE analyzer instruments vector execution across QEMU, Vehave, and FPGA emulation for LLVM-compiled RVV binaries, confirming that *the same RVV binary runs unchanged* across platforms with different VLEN — empirical validation of length-agnostic portability [6]. VecIntrinBench provides 50 function-level tasks in scalar, RVV-intrinsic, NEON, and x86-intrinsic forms, finding that rule-based and LLM-based intrinsic migration to RVV achieves parity with hand-written mappings [9]. Finally, the riscv-rvv-lab project documents measured throughput/latency on the C910, showing hand-tuned LMUL=8 assembly still beating auto-vectorized output on several kernels — the headroom the cost model leaves on the table [10].

## 6 Limitations

1. **Cost-model gaps for predication and strided access.** Shi et al. find these "pose performance challenges that current compiler cost models do not yet fully address" [5]. A vectorizer pricing a masked loop as `VF` lanes of free predication misprices mask setup, `vsetvli` reconfiguration, and scatter/gather µop expansion.
2. **Memory-bound kernels can regress.** Clang 21's auto-vectorized `stream` runs ~20% slower than scalar [5]. Vectorization is not a Pareto improvement; profitability heuristics need memory-hierarchy awareness.
3. **Irregular access remains immature.** The Qsim case study [5] and SpMV results show compilers struggling with complicated memory patterns — indexed/gather paths are legalized but rarely profitable, and segment operations are essentially never auto-generated.
4. **LMUL/register-pressure interplay.** Only four register groups exist at LMUL=8; aggressive grouping plus unrolling can spill, and spilling a full LMUL=8 group costs 8× the traffic of an m1 spill.
5. **Ecosystem fragmentation.** RVV 0.7.1 (draft) vs. 1.0 (ratified) remain incompatible; intrinsics went through breaking revisions (v0.11 → v1.0) [4]; flags like `-riscv-v-vector-bits-min` differ across LLVM versions [7][8].
6. **Verification burden.** Length-agnostic code must be correct for *all* VLEN ≥ 128 and all legal LMULs; testing on one VLEN does not cover all mask-layout or grouping edge cases.

---

## 7 Conclusion

RVV 1.0's three signature mechanisms — LMUL register grouping with fractional support bounded by the SEW~min~/ELEN legality theorem, a segmented memory-access repertoire culminating in hardware AoS transpose, and length-agnostic stripmining configured by `vsetvli` — constitute the most expressive vector ISA interface in commodity computing. LLVM's auto-vectorizer meets this with scalable vector types, VPlan-driven VF/UF selection, LMUL-aware cost modeling, and tail folding, converting that expressiveness into measured speedups on real silicon for regular compute-bound kernels [5].

Yet the empirical record counsels humility: default LMUL heuristics are near-optimal only for the common case; predication and strided-access costs escape current models; memory-bound loops can regress; and irregular patterns remain hand-intrinsic territory [5][9]. The open problems are compiler problems first: bandwidth-aware profitability, gather/scatter and segment-operation synthesis, and register-pressure-aware LMUL×UF co-optimization. As RVV 1.0 hardware proliferates, closing these gaps will determine whether the architecture's elegant portability story becomes a performance story as well.
