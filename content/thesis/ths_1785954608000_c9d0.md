# From CFS to EEVDF: The Evolution of Fair Queuing and Latency-Aware Scheduling in Linux with sched_ext and BPF-Driven Policies

## Abstract
The replacement of the Completely Fair Scheduler (CFS) by Earliest Eligible Virtual Deadline First (EEVDF) in Linux 6.6 marks the first major re-architecture of the Linux normal scheduling class in sixteen years, fundamentally altering fairness, latency control, and extensibility. This thesis traces the lineage from weighted fair queuing and idealized fluid-flow fairness to practical virtual time tracking, formalizes EEVDF's lag-based eligibility and virtual deadline selection with bounded lag guarantees inherited from Stoica and Abdel-Wahab [1], and examines how Peter Zijlstra's 2023 adaptation resolves CFS's heuristic creep around latency-nice. We then analyze **sched_ext**, Tejun Heo's BPF extensible scheduler class merged in 6.12 [6][7], as a structural response to the rigidity and experimentation cost of monolithic in-kernel schedulers. Through detailed source walkthroughs of enqueue/dispatch dispatch-queues (DSQ), we evaluate safety, determinism, and performance isolation. Empirical synthesis from kernel documentation and LWN analysis [2][3][8] demonstrates how EEVDF plus sched_ext together enable fine-grained latency-quality tradeoffs without compromising throughput. We argue that this combination represents a *paradigm shift*: from static fairness in kernel C to programmable scheduling with verifiable fallback.

## 1. Introduction
For over 16 years, Linux's `SCHED_NORMAL` workloads relied on the **Completely Fair Scheduler (CFS)**, authored by Ingo Molnár and merged in 2.6.23 [4][5]. CFS crystallized a powerful idea: model an *ideal, precise multi-tasking CPU* that executes $N$ tasks simultaneously at $1/N$ speed, tracking each task's **virtual runtime** ($vruntime$) normalized by weight derived from nice values. The task with smallest $vruntime$ runs next, maintained via per-CPU red-black tree. This yielded proportional fairness with $O(\log N)$ pick complexity.

Yet CFS accumulated tension. It excelled at throughput fairness but struggled with *latency semantics*, *migration heuristics*, *NUMA balancing*, and an increased need for per-workload customization in heterogeneous Meta/Google fleets. As Corbet summarized in LWN [2], CFS gave no principled way to say *"I need CPU quickly, but not more CPU overall"* — nice values conflated share with urgency. Latency-nice patches attempted to patch this by queue-jumping, but added heuristic complexity without formal guarantees.

In 2023, Peter Zijlstra proposed replacing CFS with an adaptation of **Earliest Eligible Virtual Deadline First (EEVDF)**, first published by Ion Stoica and Hussein Abdel-Wahab in 1995 [1]. EEVDF had already placed Linux's `SCHED_DEADLINE` research lineage, but Zijlstra repurposed its core for fair scheduling [2][3]. Simultaneously, Tejun Heo and Meta's scheduler team advanced **sched_ext (SCX)** — a BPF extensible scheduler class that allows schedulers to be implemented in BPF and hot-swapped at runtime [6][9]. Merged in 6.12, sched_ext decouples *policy innovation* from *kernel release cadence* [8].

> **Theorem 1 (EEVDF Fairness Bound):** For $N$ clients with weights $w_i$, EEVDF guarantees max lag for any backlogged client bounded by $max\_packet + quantum$ in virtual time domain, ensuring proportional fairness irrespective of request pattern [1].

This thesis answers three questions:
- *Why does EEVDF provably resolve CFS's latency-vs-share conflation?*
- *How does virtual deadline and eligibility semantics change wakeup, preemption, and placement?*
- *Why is sched_ext not a performance regression but a correctness and safety achievement, and what invariants must BPF schedulers maintain?*

## 2. Background

### 2.1 CFS: Virtual Time Fluid Model
CFS is derived from **Weighted Fair Queuing (WFQ)** [4][5]. In WFQ/PGPS:

- Each runnable entity $e$ maintains `vruntime += delta_exec * NICE_0_WEIGHT / weight`.
- Ideal time advances as `virtual_time += delta_exec / sum_weights`.
- Red-black tree keyed by vruntime ensures task with *minimum* vruntime runs next.

**Key properties:**
- *Proportional share*: long-term CPU fraction $\propto weight$.
- *No explicit deadline*: fairness amortized over wall-clock.
- Heuristic augmentations for sleeper fairness (`GENTLE_FAIR_SLEEPERS`), `sched_min_granularity`, `sched_latency`, autogroups, NUMA.

Table: CFS vs EEVDF design choices

| Dimension | CFS | EEVDF |
|-----------|-----|-------|
| Time base | vruntime normalized by load | lag = ideal - actual service |
| Selection key | min(vruntime) | earliest virtual deadline among eligible |
| Latency control | indirect (slice granularity) | explicit per-task request via `sched_setattr` slice |
| Sleeping handling | vruntime catch-up bounded | deferred dequeue + decaying lag over VRT |
| Data structure | rb-tree | rb-tree + double rbtree for non-eligible? currently rb-tree with eligibility check |

### 2.2 Fair Queuing Lineage and WF2Q+
EEVDF originates from Zhang and Parekh-Gallager's work on **Generalized Processor Sharing (GPS)** fluid model [1]. GPS serves backlogged flows proportionally in infinitesimal quantum. Practical approximations:

- **WFQ/PGPS**: Serve packet with earliest finish tag.
- **WF2Q+**: Only eligible packets where service already started in fluid model.
- **EEVDF**: Generalization: Eligibility time $ve_e$ = time when client becomes eligible in fluid model; Deadline $vd_e = ve_e + q / w$, where $q$ is packet length / slice. Earliest deadline among eligible runs first.

This gives both fairness bound and *delay bound decoupling*. As Stoica proved, EEVDF reduces worst-case delay vs WFQ by factor $\propto$ weight distribution.

### 2.3 Real-Time, Deadline, and Latency Nice
Linux maintains hierarchy: `DL > RT (FIFO/RR) > CFS/EEVDF/EXT > IDLE`. CFS latency was handled via tunables but without formal service-level guarantee. The community proposed `latency_nice` [-20,19] mapping to shorter time-slice request. In CFS, this required heuristics to avoid starvation. In EEVDF, it naturally maps to smaller request size $r = slice$ → closer virtual deadline $vd = ve + r / w$, so task becomes eligible more often but total share unchanged [2][3].

### 2.4 Why sched_ext?
Schatzberg at SCALE/LPC argued: *iterating scheduler needs kernel rebuild & reboot* is untenable for fleet-specific optimization [6][8]. Heterogeneous hardware (big.LITTLE, asymmetric Intel Hybrid, chiplets), workloads (gaming FPS, ML serving, interactive microVMs), and power constraints require rapid policy search. **sched_ext** exports `struct sched_ext_ops` via BPF `struct_ops`, with callbacks `enqueue`, `dispatch`, `running`, `stopping`, `enable`, `select_cpu`.

> *Philosophical shift: Scheduler becomes a BPF program, kernel core becomes a safety substrate.*

## 4. Deep Dive

### 4.1 EEVDF Formalism: Lag, Eligibility, Virtual Deadline
Let $W = \sum_j w_j$ total weight, $t$ wall-clock.

Ideal service for task $i$: $S_i^{ideal}(t) = \int_0^t (w_i / W(\tau)) \cdot \mathbb{1}_{runnable}(i,\tau) d\tau$

Actual service $S_i(t)$ from CPU accounting.

**Lag**:
$$lag_i(t) = S_i^{ideal}(t) - S_i(t)$$

- $lag > 0$: owed service → must be eligible.
- $lag < 0$: over-served → ineligible until wall-clock catches up.

EEVDF maintains **virtual time** $V(t)$ advancing at rate $1/W$ when CPU busy. Then:

$$ve_i = \max(V(t) + lag_i / w_i, previous\_vd)$$

$$vd_i = ve_i + slice_i / w_i$$

where $slice_i$ derived from `sysctl_sched_base_slice` (default 3ms EEVDF vs variable CFS) and scaled by `latency_nice` and weight [3].

Selection rule: Among tasks where $ve_i \le V(t)$ (eligible), pick min $vd_i$. If none eligible → advance $V(t)$ to min $ve_i$.

This elegantly solves starvation: a task cannot request arbitrarily small slice to gain disproportionate share because weight still normalizes long-term share; slice only controls *burstiness*.

*Implementation nuance in Linux 6.6*: To avoid over-penalizing long-sleeping tasks, EEVDF uses **deferred dequeue**: sleeping task stays enqueued but marked for lazy removal. Its lag decays as $V(t)$ advances without it. Upon wakeup after long sleep, lag ≈ 0, so it does not get infinite compensation. This replaces CFS's `GENTLE_FAIR_SLEEPERS` heuristic with semi-formal decay [3].

```rust
// Simplified EEVDF pick (Rust pseudocode mirroring kernel)
fn eevdf_pick(rq: &RunQueue, now_v: u64) -> Option<Task> {
    // eligible: ve <= now_v
    let eligible: Vec<_> = rq.tasks.iter()
        .filter(|t| t.ve <= now_v)
        .collect();
    if eligible.is_empty() {
        // jump virtual time to earliest ve
        let next_ve = rq.tasks.iter().map(|t| t.ve).min()?;
        rq.advance_virtual_time(next_ve);
        return None; // reschedule
    }
    // EDF among eligible
    eligible.into_iter().min_by_key(|t| t.vd)
}
```

### 4.2 From CFS Heuristics to EEVDF Invariants
CFS accumulated heuristics over 16 years: tunables for cache locality (`sched_migration_cost`), `wake_affine`, `next_buddy`, `last_buddy`, `skip_buddy`. Many manipulated vruntime placement on wakeup.

In EEVDF, many become unnecessary *in core* because:

1. **Request size controls preemption**: Tasks with 1ms slice preempt 24ms slice tasks iff $vd$ earlier. No need for `WAKEUP_PREEMPTION` tunables; preemption decision is $vd_{waker} < vd_{current}$ plus $lag$ check.
2. **Placement via lag averaging**: Child task inherits parent avg lag rather than capping to min vruntime.
3. **Latency-nice integration**: Formal: `slice = sysctl_base_slice * (1 + latency_nice_factor)`. As Peter Zijlstra argued in [2], this deletes ~300 LOC of `sched_features(SIS_PROP, TTWU_QUEUE)`.

However EEVDF introduces new discussions: lag accounting on load-weighted group hierarchies (cgroups), where share propagation across subtree must maintain monotonic $V(t)$ per cgroup.

### 4.3 sched_ext: Architecture, DSQ, and Safety Model
sched_ext's core insight: Define minimal but complete scheduler ABI that BPF can implement [9].

**Scheduling flow**:
1. `ops.enqueue(task, enq_flags)` enqueues to BPF — task can be put into *dispatch queue* DSQ.
2. `ops.dispatch(cpu, prev_task)` called on CPU to choose next task. BPF typically consumes from global DSQ via `scx_bpf_dsq_move_to_local()` or `scx_bpf_consume()`.
3. `ops.running`/`stopping` notify.

**DSQ**: Abstract queues identified by `u64 dsq_id`. 2 built-ins: `SCX_DSQ_LOCAL` (per-CPU) and `SCX_DSQ_GLOBAL` (fallback). Scheduler can create up to $2^{15}$ custom DSQs for e.g., LLC domain, node domain. This allows topology-aware dispatch without kernel maintaining topology.

```python
# scx_lavd style latency heuristic in Python-esque BPF pseudocode
def scx_lavd_enqueue(task):
    # latency-critical if short runtime + frequent wakeup
    lat = bpf_map_lookup(task.lat_hist)
    if lat.wakeup_freq > 100 and lat.avg_runtime < 1_000_000: # ns
        dsq = SCX_DSQ_LAT_CRIT
        task.slice_ns = 500_000  # 0.5ms -> early vd-like
    else:
        dsq = my_cpu_llc_dsq()
        task.slice_ns = 3_000_000
    scx_bpf_dsq_insert(task, dsq, task.slice_ns, 0)

def dispatch(cpu, prev):
    # prioritize latency DSQ
    if scx_bpf_dsq_move_to_local(SCX_DSQ_LAT_CRIT):
        return
    scx_bpf_dsq_move_to_local(local_llc_dsq(cpu))
    scx_bpf_dsq_move_to_local(SCX_DSQ_GLOBAL)
```

**Safety**: Kernel watchdogs.

- If any CPU stalls > 30 sec (configurable), default EEVDF behavior restored; BPF scheduler ejected.
- If task starved >? irrespective of BPF bug, global DSQ fallback ensures forward progress — any non-consumed task implicitly in GLOBAL.
- `SysRq-S` forces fallback.
- BPF verifier ensures no loops, bounded stack.
- Dispatch loop capped to `SCX_DSP_MAX_LOOPS=32` after patch 2024-05-01 [6] to prevent live-lock via repeatedly ineligible dispatch.

Performance isolation: scx schedulers run in `BPF_MAY_GOTO` limited context; enqueue path called with `rq` lock held — must be bounded and cannot block.

```haskell
-- TLA+ invariant for DSQ forward progress
Invariant NoStarvation ==
  \A t \in Tasks :  \/ t \in LocalDSQ
                   \/ t \in GlobalDSQ
                   \/ t \in BpfDSQ
                   \/ t.state = Running

Next(dispatch) ==
  /\ \E dsq \in DSQs : Len(dsq) > 0
  /\ cpu.next = Head(dsq)
  /\ dsq' = Tail(dsq)
```

This ensures *any* task enqueued is eventually dispatched.

### 4.4 Convergence of EEVDF and sched_ext: Programmable Latency
Intriguingly, EEVDF inspired DSQ prioritizing: scx_lavd uses virtual deadline-like metric but adds *latency* driven by user knowledge (e.g., game window focus, audio IRQ thread). The combination suggests future: Task can request via `sched_setattr` both `sched_runtime`, `sched_deadline` (for DL) and new `sched_slice` (for EEVDF) and BPF decision can override slice via `scx_bpf_dispatch`.

Benchmarks cited in LPC 2024 [6]: `scx_rustland` running mostly in Rust userspace achieves +12% FPS in Terraria while kernel compilation parallel (`make -j32`) vs reference EEVDF, because it can detect gaming thread and pin it progn = isolated DSQ.

## 5. Empirical / Proofs

### 5.1 Lag Bound Proof Sketch
Given Stoica definition [1], show lag bounded.

> **Lemma:** For backlogged flow $i$, with weight $w_i$, max service lag after time $t$:
$$ -r_{max} \le lag_i(t) \le r_{max} + \max_{j} r_j * w_i / w_j $$

*Proof sketch (adapted)*: Define eligibility $ve_i$ as start tag in fluid system. Packet transmission consumes request. Since EEVDF chooses min deadline among eligible, any packet's fluid start ≤ wall. By induction on transmission order, service deviation ≤ one quantum plus max heterogeneity. Formal steps use ordering argument: sorting of $ve$ yields FIFO in fluid domain; $vd$ ensures release monotonicity. See [1] Theorem 6. ∎

In Linux adaptation, $r_{max}$ = `sched_base_slice` up to 48ms (tunable), bounding jitter.

### 5.2 EEVDF vs CFS Consistency Evaluation
From kernel tests [3][2]:

- 10 latency-sensitive `schbench` tasks (99th wakeup latency): EEVDF improved P99 latency 8-20% at equal throughput vs CFS because earlier $vd$ avoids `vruntime` collapse after batch.
- `hackbench -g 10 -l 10000`: CFS scored by `min_vruntime` de-factor could over-schedule batcher → 3% higher context-switch; EEVDF 2% lower throughput but more predictable latency distribution.
- `stress-ng --cgroup` > 64 cgroups:  CFS hierarchical load handling: O(depth) vruntime propagation with lossy share distribution; EEVDF per-cgroup virtual time tracking reduced scheduling anomaly reports by 40% on Meta's TAO workload.

### 5.3 sched_ext Overhead
Measure from Schatzberg [8]:

- BPF `ops.enqueue` avg 180 ns (vs native CFS enqueue ~80 ns) on x86_64 Zen4; dispatch 320 ns vs 120 ns. Total overhead 0.3-0.8% CPU at 60k enq/s/core simulated.
- With `scx_bpfland`, P50 web request latency on nginx + `wrk` improved 18% vs EEVDF default due to custom waking CPU selection using BPF cpumask custom logic — something EEVDF cannot encode statically.
- Safety: Chaos test: malformed BPF scheduler returning `NULL` dispatch indefinitely → watchdog kicked in 5 sec, system returned to EEVDF without crash (500 iterations).

```tla
---- MODULE EEVDF ----
EXTENDS Reals
VARIABLES lag, ve, vd, V
Eligible(t) == ve[t] <= V
NextV == IF \E t \in Tasks : Eligible(t)
        THEN V
        ELSE Min({ve[t]: t \in Tasks})
TypeOK == \A t \in Tasks : vd[t] = ve[t] + slice[t]/weight[t]
```

## 6. Limitations

1. **cgroup decay complexities**. Interaction of per-entity virtual time with hierarchical weight still evolving; patch threads Q4 2024 debated whether decay should be per-cgroup virtual or global [3]. Long-idle cgroup members can distort lag mass if weight recalculated after many V steps.

2. **BPF verifier constraints**. Many sophisticated scheduling algorithms (e.g., size-based oracles using ML prediction) exceed BPF complexity limits (8k insns, limited loops). `scx_rustland` workaround moves heavier logic to userspace daemon via BPF ringbuf, introducing 8-15 µs latency penalty negating nano-level decision gains.

3. **Priority inversion via DSQ misspecification**. A BPF scheduler that incorrectly partitions DSQs (e.g., never draining GLOBAL) can de-facto reintroduce starvation before watchdog detection. Current guarantee is *system liveness*, not *per-task* fairness — intentional for extensibility but violates EEVDF's formal bound.

4. **Energy and frequency coupling**. sched_ext's integration with cpufreq (schedutil) lands post-6.12; without it, BPF-driven frequency hints may be stale. EAS (Energy Aware Scheduling) + EEVDF + sched_ext triple interaction remains under-explored for Arm big.LITTLE.

5. **Formal verification gap**. No machine-checked proof that Linux's EEVDF implementation preserves Stoica's delay bound under SMP migration and `SCHED_BATCH` throttling; testing is heuristic, not exhaustive.

6. **API instability**. As documentation warns [9], `sched_ext_ops` ABI is unstable; schedulers built for 6.12 broke on 6.13 due to `cpu_acquire` signature change, imposing maintenance tax.

## 7. Conclusion
Linux's scheduling journey from **O(1) → CFS → EEVDF → sched_ext** mirrors a broader operating systems lesson: *fairness alone is insufficient; need controlled latency and programmable policy*.

- **CFS** demonstrated that modeling ideal fluid CPU via vruntime eliminates priority-array tuning while achieving proportional fairness [4][5].
- **EEVDF** shows that adding *explicit eligibility* and *request-length-derived deadlines* eliminates conflation of share and latency, providing bounded lag and enabling latency-nice as first-class without heuristic bloat [1][2][3].
- **sched_ext** argues that scheduler policy should be an *eBPF extension*, not immutable kernel code, with performance competitive and safety via fallback and watchdog [6][7][8][9].

For systems builders, the practical intake is:

- If you need fleet-specific SLOs (gaming, p99 tail for search), invest in `scx` scheduler; start from `scx_lavd` or `scx_bpfland`.
- Tune task latency via `sched_setattr(..., sched_flags=SCHED_FLAG_SLC_REQUEST, slice)` rather than renicing.
- Understand lag decay semantics when debugging wakeup latency spikes: `tracepoint:sched:sched_stat_runtime` + `eevdf lag` via `debugfs /sys/kernel/debug/sched/debug`.

> *Future work*: Provably safe BPF scheduler synthesis via program sketching, verifying lag bound under DSQ dispatch, energy-aware virtual deadline (multiplying $vd$ by predicted energy cost), and integration with `io_uring`'s wait nuance for I/O-bound latency.
