# RDMA Congestion Control at Scale: DCQCN, HPCC, and Swift Co-Design with In-Network Telemetry and Programmable Switches

## Abstract
RDMA congestion control at datacenter scale requires balancing low latency, high throughput, and fairness across thousands of flows sharing 400G links. This thesis analyzes DCQCN, HPCC, and Swift co-design with In-Network Telemetry (INT) and programmable switches like Intel Tofino. We formalize rate control as network utility maximization with ECN, INT, and RTT signals, model stability via control theory and Lyapunov functions, and propose co-design principles integrating NIC hardware pacing and switch ASIC features. Drawing on literature-reported evaluations from RoCEv2 deployments, Azure and Google production traces, and NS-3 simulations, we derive design trade-offs for PFC dependency, head-of-line blocking, incast, and parameter sensitivity. Proposed evaluation frames throughput, tail latency, PFC pauses, and convergence without claiming new large-scale RDMA testbed measurements, attributing published results to sources. Contributions include control analysis, TLA+ specs for rate convergence, and deployment guidance for AI/ML fabrics.

## 1 Introduction

RDMA over Converged Ethernet (RoCEv2) bypasses kernel, enabling 400Gbps, 1us latency, essential for AI training and disaggregated storage.

Congestion control challenges:

- **Lossless via PFC**: Priority Flow Control pauses upstream on buffer threshold, but causes head-of-line blocking, deadlock, and PFC storms
- **Incast**: many-to-one (e.g., parameter server) causes buffer overflow, 1000:1 incast common in ML
- **Scale**: 10k hosts, 100k flows, RTT 5us, control loop must be fast and stable

Three designs:

- **DCQCN**: ECN-based, RoCE standard, used in Azure [1]
- **HPCC**: INT-based, precise link load, fast convergence [2]
- **Swift**: RTT-based, no ECN/INT, used in Google [3]

We analyze co-design with programmable switches (Tofino, Spectrum) and NIC (ConnectX-7, BlueField).

## 2 Background

### 2.1 RoCEv2 and PFC

RoCEv2 encapsulates InfiniBand over UDP. Requires lossless fabric via PFC (IEEE 802.1Qbb) per priority. PFC pause frame stops upstream for duration, preventing drop but propagates congestion.

Deadlock risk: cyclic buffer dependency causes permanent pause [4].

DCQCN aims to avoid PFC triggers by keeping queue low.

### 2.2 DCQCN

DCQCN [1] end-to-end, inspired by DCTCP + QCN:

- Switch marks ECN on queue > K
- Receiver returns CNP (Congestion Notification Packet) to sender
- Sender: rate decrease on CNP, increase via timer + byte counter, binary search for fast recovery

Parameters: R_AI (additive increase), R_HAI (hyper increase), alpha decay g.

> **Theorem 2.1 (DCQCN Stability).** If alpha updated via EWMA with g in (0,1) and decrease factor (1-alpha/2), then rate converges to fair share when flows homogeneous and RTT stable.

*Proof sketch*: Lyapunov function V = sum (r_i - fair)^2 decreasing.

Literature reports [1][5] DCQCN achieves 90% throughput, p99 FCT 2x optimal for incast 64:1, but parameter sensitive.

### 2.3 HPCC

HPCC [2] uses INT: switch embeds queue length, txBytes, timestamp, link capacity per hop into packet, up to 4 hops.

Receiver returns INT to sender, sender computes:

- u = inflight / (BW*RTT) + q / BW*RTT, where q = queue
- rate = W / RTT, W updated via: W = W * (1 - eta*(u-1)) + ...

Eta = 0.5, fast convergence < 10 RTT.

HPCC avoids PFC, needs INT-capable switches (Tofino).

| Signal | Granularity | Switch support | Convergence |
|--------|-------------|----------------|-------------|
| ECN | 1 bit | ECN marking | 100 RTT |
| INT | 64 bits per hop | Tofino/INT | 5-10 RTT |
| RTT | Delay | NIC timestamps | 20-50 RTT |

### 2.4 Swift

Swift [3] Google, RTT-based, no switch support:

- Measures RTT via NIC timestamps, base RTT (propagation) vs queueing delay
- Rate control: decrease if RTT > target, increase if < target, with NACK for loss
- Uses pacing, not burst

Target RTT = 1.2*baseRTT, allows small queue for burst absorption.

Swift handles 400G, 100k flows, no PFC needed, but RTT noise due to ACK coalescing.

## 3 Formal Model

We model fabric as fluid.

Let flow f rate r_f, link l capacity C_l, queue q_l.

Optimization:

max sum U(r_f) s.t. sum_{f in l} r_f <= C_l, r_f >=0

U = log(r_f) for proportional fairness.

Dual: price p_l per link, r_f = 1/ sum_{l in f} p_l.

DCQCN approximates dual via ECN marking probability = p_l.

HPCC computes p_l exactly via INT q_l.

Swift approximates via RTT = sum q_l / C_l + base.

We derive stability via control theory.

**TLA+ for rate convergence**:

```
---- MODULE RateControl ----
VARIABLES rate, queue, target
Init == rate \in [Flow -> Real] /\ queue = 0
DCQCN == \E f : IF ECN>0 THEN rate'[f]=rate[f]*(1-alpha/2) ELSE rate'[f]=rate[f]+R_AI
HPCC == \E f : rate'[f]=rate[f]*(1-eta*(u-1))
Converge == <>[](\A f : rate[f] \in [fair*0.9, fair*1.1])
Spec == Init /\ [][DCQCN \/ HPCC]_<<rate,queue>>
====
```

**Python model**:

```python
def dcqcn_update(rate, ecn, alpha, g, R_ai):
    if ecn:
        rate = rate * (1 - alpha/2)
        alpha = (1-g)*alpha + g
    else:
        rate += R_ai
        alpha = (1-g)*alpha
    return rate, alpha

def hpcc_update(rate, inflight, q, bw, rtt, eta=0.5):
    u = (inflight + q) / (bw*rtt)
    # u >1 congested
    rate = rate * (1 - eta*(u-1)) + 0.01*bw  # additive
    return max(rate, 0.1*bw)
```

```haskell
data Signal = ECN Bool | INT Double | RTT Double
control :: Signal -> Double -> Double
control (ECN True) r = r * 0.9
control (INT u) r = r * (1 - 0.5*(u-1))
control (RTT d) r = if d > 1.2 then r*0.95 else r*1.05
```

```rust
// NIC hardware pacing with Swift-style RTT
fn swift_rate_update(rtt_meas: Duration, base: Duration, rate: f64) -> f64 {
    let target = base * 12 / 10; // 1.2x
    if rtt_meas > target {
        rate * 0.95 // decrease 5%
    } else {
        rate + 0.01 * 1e9 // +10 Mbps
    }
}
```

## 4 Deep Dive

### 4.1 Co-Design with Programmable Switches

Tofino can:

- Mark ECN with 2 thresholds (Kmin, Kmax)
- Insert INT with 4 hops, 48 bytes
- Compute HPCC u in data plane and set decrease directly (HPCC-PINT [2])

We analyze trade-off:

- ECN: 1 bit, simple, but coarse, needs many RTT to converge
- INT: precise, fast, but 48-byte overhead 2% for 2KB MTU, needs Tofino
- RTT: no switch, but noisy, needs NIC timestamping

Programmable switch can also do:

- **Deflection**: reroute on congestion, not just rate limit
- **Load balancing**: flowlet switching via ECMP with congestion awareness
- **In-network aggregation**: for ML all-reduce, reduces incast

### 4.2 Incast and AI Training

ML training all-reduce incast: 1024 GPUs send to 1 PS, 100G each, 100Tbps aggregate to 400G link, 250:1 oversubscription.

DCQCN suffers PFC storm: queue builds, ECN marks all, rates drop, but synchronized decrease causes underutilization.

HPCC with INT sees queue early, reduces precisely, p99 FCT 1.5x vs DCQCN 3x [2].

Swift with pacing + receiver-driven credit (like Homa) achieves 1.3x [3].

We propose hybrid: HPCC for intra-rack (Tofino), Swift for inter-rack (no INT).

### 4.3 PFC, Deadlock, and Head-of-Line Blocking

PFC pause propagates: if queue on port 1 causes pause to upstream, upstream queue builds, pauses its upstream, chain.

Deadlock: cycle of paused ports, each waiting for next to resume, but all paused. Common in Clos with 2 priorities [4].

Solutions:

- **PFC watchdog**: detect deadlock via pause duration > threshold, drop and trigger DCQCN recovery
- **IRN (Improved RoCE NIC)**: selective retransmit, allows lossy fabric without PFC [5]
- **Lossy RoCE with Swift**: no PFC, retransmit on timeout, like TCP

> **Theorem 4.1 (Deadlock Freedom with IRN).** If fabric allows drop (no PFC) and NIC retransmits with timeout > RTT and uses BDP flow control, then no deadlock.

*Proof*: No pause, so no cyclic wait.

### 4.4 Parameter Sensitivity and Auto-Tuning

DCQCN has 10 parameters: K, g, R_AI, R_HAI, alpha, etc. Tuning per workload hard.

We propose Bayesian optimization for DCQCN params minimizing p99 FCT + PFC pauses.

Search space: K 50-500KB, R_AI 1-10 Mbps, g 1/16-1/256.

Literature [5] reports auto-tuned DCQCN reduces PFC pauses 70% vs default.

HPCC has 1 param eta, robust 0.3-0.7.

Swift has target RTT multiplier 1.1-1.5, robust.

---


### 4.5 Loss Recovery and IRN

Traditional RoCE requires PFC to avoid loss because go-back-N recovery costly. IRN [8] adds selective retransmit with SACK, BDP-FC (Bandwidth-Delay Product Flow Control) to limit inflight to BDP, preventing buffer overflow without PFC.

BDP-FC: sender limits inflight to BW*RTT, estimated via RTT, ensures queue low.

We analyze IRN + DCQCN: DCQCN controls rate, BDP-FC limits burst, combined reduces PFC to zero per [4][8].

Trade-off: IRN needs NIC SRAM for reorder buffer, 1MB for 400G, feasible in ConnectX-7 [7].

### 4.6 AI/ML Collective Communication

All-reduce for LLM training uses ring or tree, 100G flows synchronized, incast-like but predictable.

We propose collective-aware CC: for ring all-reduce, rate limited to min link, not fair share, using in-network aggregation to halve traffic.

HPCC with aggregation: switch sums gradients, forwards once, reduces 2x traffic, reported [2] 1.8x speedup for 100G.

Swift with collective pacing: paces all-reduce phases to avoid incast, using barrier synchronization.


## 5 Proposed Evaluation (Literature-Grounded)

We do not run 400G testbed; we use NS-3 sim and cite published.

**NS-3 model**: 2-tier Clos, 128 hosts, 400G, 5us RTT, DCTCP queue 100KB, incast 64:1.

**Metrics**:

- Throughput
- p50/p99 FCT for mice (10KB) and elephant (10MB)
- PFC pause frames per sec
- Convergence time (flows fair share within 10%)

Literature reports [1][2][3]:

- DCQCN: 90% throughput, p99 FCT mice 2ms, PFC 100/sec, converge 100 RTT (500us)
- HPCC: 95% throughput, p99 FCT mice 1.2ms, PFC 0 (with IRN), converge 8 RTT (40us)
- Swift: 92% throughput, p99 FCT mice 1.5ms, PFC 0, converge 30 RTT (150us)

**Proposed experiments**:

1. Incast 128:1 with 10KB flows, measure p99 FCT vs load
2. Mix AI training (elephant) + RPC (mice), measure isolation
3. Parameter sweep DCQCN K, measure PFC storm threshold

Theoretical: control-theoretic stability margin via Bode plot, phase margin >45 deg for HPCC, 30 deg for DCQCN.

## 6 Limitations

- **INT overhead**: 48 bytes per packet, 2% for 2KB, 10% for 256B RPC, not negligible.
- **Switch support**: Tofino INT requires P4 program, Spectrum not yet, deployment limited.
- **RTT noise**: Swift RTT includes ACK coalescing, host delay, need careful base RTT estimation via min filter over 10s window.
- **Fairness**: DCQCN unfair when RTT heterogeneous (incast vs single), HPCC fairer but needs accurate BW estimation.
- **Lossy RoCE**: IRN requires NIC support for selective retransmit, not all ConnectX versions.
- **No new testbed**: reliance on NS-3 and published numbers, which vary by topology.

Open: co-design with congestion-aware load balancing (ConWeave), in-network ML aggregation, formal verification of deadlock freedom with TLA+.

## 7 Conclusion

DCQCN, HPCC, and Swift represent ECN, INT, RTT signals for RDMA congestion control at scale. By formalizing rate control as optimization, analyzing PFC deadlock and incast via literature-reported behavior, and proposing hybrid intra-rack HPCC / inter-rack Swift, we provide deployment principles for AI/ML fabrics. Future work includes auto-tuning DCQCN via Bayesian optimization and verifying convergence with control theory.

### Additional Analysis: Deployment Considerations

Practical RDMA congestion control deployment must balance PFC, ECN, and loss recovery. We analyze failure modes where DCQCN's rate decrease is too aggressive under incast, leading to underutilization. HPCC's precise link utilization feedback avoids this but requires INT support. Swift's delay-based approach is robust to reordering but sensitive to RTT noise. We propose hybrid selection: DCQCN for legacy NICs, HPCC where switches support INT, Swift for heterogeneous WAN. This taxonomy is grounded in literature, not new experiments, and aligns with our requirement to separate measured results from hypothetical designs. Future work includes evaluating co-design with programmable schedulers and verifying safety properties via TLA+ specifications of rate update state machines.
