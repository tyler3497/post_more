# The Rust Borrow Checker: Region Inference, Non-Lexical Lifetimes, and the Polonius Formulation

## Abstract

Rust's borrow checker is the most ambitious aliasing analysis ever shipped in a production compiler: it statically guarantees memory safety and data-race freedom for safe code without garbage collection. This article dissects the machinery behind it. We begin with the foundations — region-based type systems, place expressions, and the Mid-level Intermediate Representation (MIR) on which checking runs — then reconstruct the checking pipeline: constraint generation from MIR type checking, liveness-seeded region inference, outlives propagation, and universal-region validation. We explain *non-lexical lifetimes* (NLL), the 2018 reformulation that replaced lexical scopes with liveness-driven regions, working through its constraint grammar and flow-sensitive inference algorithm. Finally, we present *Polonius*, the Datalog-based reformulation that replaces regions with *origins* — sets of *loans* — and show how its rules (subset closure, loan-requirement propagation, liveness-gated error detection) admit programs that NLL rejects. We close with soundness evidence from RustBelt, Oxide, and Stacked Borrows, and the limitations that remain. [1][3][4]

## 1 Introduction

Every value in Rust has exactly one *owner*; values are *moved* rather than shared by default; and references obey a strict discipline — *aliasing XOR mutability* — for as long as they are used [1]. The borrow checker is the static analysis that enforces this discipline. It is unusual among production compiler analyses in three respects: it runs over the entire program, it must be both *sound* (no accepted program can exhibit use-after-free or data races in safe code) and *complete enough* to accept idiomatic code, and its rejections are surfaced directly to programmers as diagnostics, making the analysis part of the language's user interface.

The modern checker operates on MIR, Rust's mid-level intermediate representation: a control-flow graph (CFG) of basic blocks in which borrows, moves, drops, and function calls are explicit [1][9]. Checking a function body therefore reduces to answering one question at every CFG point: *is any live loan violated here?* A **loan** is the borrow checker's record of a single borrow expression — what place was borrowed, how (shared or mutable), and where the resulting reference was stored [9]. A loan is **live** at a point if the reference it created may still be used downstream; it is **violated** at a point if that point accesses the borrowed place in a way incompatible with the loan's terms (e.g., writing through or around a shared borrow, or touching anything under a mutable borrow).

This article reconstructs how rustc answers that question, across three generations of the analysis:

1. **Region inference** — lifetimes as variables ranging over sets of CFG points, solved by constraint propagation [3].
2. **Non-lexical lifetimes (NLL)** — regions seeded by liveness rather than lexical scope, so borrows end at their last use instead of at the closing brace [1][2].
3. **Polonius** — a reformulation of the whole analysis in Datalog, where lifetimes become *origins* (sets of loans) and the algorithm becomes a small set of declarative rules [4][5][6].

We then examine the auxiliary machinery — two-phase borrows, the drop checker, and the boundary with `unsafe` code — the empirical and formal evidence for soundness, and the frontiers where the checker still says "no" to programs a human can see are safe.

## 2 Background

### 2.1 Ownership, moves, and places

Rust's ownership system assigns every value a unique owner. Assignment and argument passing *move* ownership by default; the previous owner can no longer be used. Borrowing creates a temporary, non-owning view: `&T` (shared) or `&mut T` (exclusive). The fundamental rule enforced everywhere is:

> **The aliasing discipline.** While a shared borrow is live, the borrowed place may not be mutated. While a mutable borrow is live, the borrowed place may not be accessed at all through any other path. [1]

The unit the checker reasons about is the **place expression**: a path to memory such as `x`, `x.field`, `*p`, or `a[i]`. Places form a tree ordered by the *prefix* relation: `x` is a prefix of `x.field`, and conflicting with a prefix conflicts with everything beneath it. When a borrow `&mut x.field` creates a loan, the checker records the loan's path and treats accesses to any *supporting prefix* or overlapping path as potential violations [9]. This place-based granularity is what lets the compiler accept disjoint field borrows of the same struct while rejecting overlapping ones.

### 2.2 Regions: the Tofte–Talpin heritage

Rust's lifetimes are *region variables* in the tradition of Tofte and Talpin's region-based memory management, where types are annotated with the region in which values live and a region inference algorithm computes the smallest regions satisfying the constraints. Cyclone extended the idea with dynamically scoped regions. Rust's innovation was to apply region inference not to allocation but to *borrowing*: a lifetime `'a` denotes the set of program points during which a borrow must be respected.

In the current compiler, a **region** is a set of CFG *points* (locations: a basic block plus a statement index) [3]. Lifetimes appearing in function signatures are **universal regions** — placeholders the caller instantiates, about which the checker knows only the declared `where`-clauses. Lifetimes created during checking (one per borrow expression, one per inferred type) are **existential regions** — variables whose values the inference algorithm must compute.

### 2.3 MIR: the checker's input language

The borrow checker does not see source syntax; it sees MIR, where control flow is a graph, temporaries are explicit, and every borrow is a `Rvalue::Ref` with a designated region variable [1]. This matters because *all* of the checker's subtlety is control-flow subtlety: loops, branches, and joins determine where regions must extend and where loans die. MIR also makes *drops* explicit, which is why the drop checker and borrow checker share infrastructure.

## 3 Methodology

The checking pipeline for one function body proceeds in ordered phases [3][9]:

1. **MIR type checking** walks the MIR and emits **outlives constraints** (`'a: 'b`, read "`'a` outlives `'b`") wherever subtyping demands them — e.g., assigning `&'a T` to a variable of type `&'b T` requires `'a: 'b`.
2. **Constraint generation** (`generate_constraints`) walks the CFG again and emits **liveness constraints**: each region variable must contain every point at which it is live, i.e., points from which a use of the corresponding reference is reachable [3].
3. **Region inference** (`propagate_constraints`) computes the least solution: seed each region with its liveness points, then repeatedly apply outlives edges — if `'a: 'b`, add all of `'b`'s points (including its end point) to `'a`.
4. **Validation** checks that *type tests* (`T: 'a`, "type `T` is valid for region `'a`") hold, and that *universal regions* are not "too big": if an inferred region `'a` contains `end('b)` for a universal `'b`, the signature must already declare `'a: 'b`, else the program is rejected [3].
5. **Loan checking** walks the CFG once more; at each point, for each loan live there, it asks whether the statement invalidates the loan. If so, it reports an error.

The conceptual core is step 3: *region inference as constraint solving*. Regions are inferred, never annotated, inside function bodies; the programmer writes types with named lifetimes only at boundaries, and the solver fills in the rest. The genius of NLL was changing what seeds the solver.

| Phase | Input | Output |
|---|---|---|
| MIR type checking | MIR body, signatures | Outlives constraints `'a: 'b` |
| Constraint generation | CFG, liveness analysis | Liveness constraints (region ⊇ live points) |
| Propagation | Both constraint sets | Least region assignment |
| Universal-region check | Inferred regions, `where`-clauses | Accept / reject |
| Loan checking | Loans, liveness, CFG | Borrow errors |

*Table 1: The borrow-checking pipeline. Each phase feeds the next; only the final phase reports user-facing errors.*

## 4 Deep Dive

### 4.1 Region inference as constraint solving

A region variable's value is a *set of CFG points*. The constraints over these variables come in three shapes, following the grammar given in the NLL RFC [1][2]:

- **Outlives constraints**, `'a: 'b`: everything in `'b` must also be in `'a`. Generated by the type checker at subtyping coercions, function calls (relating argument and parameter regions), and return-position covariance.
- **Liveness constraints**, `'a: point`: the region must contain the given point. Generated wherever a variable whose type mentions `'a` is live.
- **Type tests**, `T: 'a`: every region occurring in `T` must be contained in `'a` (so that, e.g., a value stored somewhere does not smuggle out a shorter-lived reference).

Inference computes the *least* fixed point: start each region at exactly its liveness points, then propagate along outlives edges until closure [3]. Leastness is deliberate — smaller regions mean fewer restrictions, hence more programs accepted. If no solution satisfies all constraints (e.g., a universal region would need to grow beyond its declared bounds), the body is rejected.

Consider the canonical example from the RFC [1]:

```rust
let mut foo: T = ...;
let mut bar: T = ...;
let mut p: &'p T;
p = &'foo foo;      // borrow 1, region 'foo
if condition {
    print(*p);
    p = &'bar bar;  // borrow 2, region 'bar
}
print(*p);
```

The inference algorithm assigns `'foo` the points before the branch where `p` may still refer to `foo`, and `'bar` the points after the second borrow; `'p` becomes their union, since `p`'s type must be valid wherever `p` is used.

### 4.2 Non-lexical lifetimes: liveness instead of scope

Before NLL (the pre-2018 checker), a borrow's region was its *lexical scope*: `let x = &v[0];` held the borrow of `v` until the end of the enclosing block, so `v.push(4)` two lines later — after the last use of `x` — was an error. NLL replaced scopes with **liveness**: a loan's region covers precisely the points from which the reference is still live, computed by a backward dataflow analysis over the CFG [1][9]. The motivating example:

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];
println!("{}", first); // last use of `first`
v.push(4);             // OK under NLL: loan is dead here
```

Under NLL the loan's region is `{borrow point, use point}`; the `push` falls outside it, so no error. The analysis is a standard *live-variable* computation lifted to regions: seed each region with the points where its reference is used, propagate backward through CFG predecessors, and stop at the borrow [9].

Yet NLL retains a fundamental imprecision, and it is the reason Polonius exists. In NLL, when two borrows flow into the same variable along different branches, their regions are *unified under a single lifetime parameter* appearing in the variable's type. That parameter then "encodes" the union of the branches' regions, so a use of the variable on one branch keeps *both* branches' loans alive. The classic demonstration [6][7]:

```rust
let (r1, r2) = (&s1, &s2);
if cond {
    use_ref(r1);
    drop(s1);      // NLL rejects: r2's region was unified with r's,
    use_ref(r2);   // so dropping s1 looks like killing a live loan
    drop(s2);
} else {
    use_ref(r2);
    drop(s2);
    use_ref(r1);
    drop(s1);
}
```

On the `cond == true` branch, `s1` is dead after `use_ref(r1)` and could be dropped — but NLL's region for the merged lifetime spans both branches, so the drop appears to invalidate a live loan. A human sees the program is safe; the checker cannot. Polonius fixes exactly this class of false positive.

### 4.3 The Polonius formulation: origins, loans, and Datalog

Polonius reframes the analysis around **origins**: an origin is a *set of loans* — the set of borrows a reference might have come from [6]. Where NLL asks "which points are in region `'a`?", Polonius asks "which loans does origin `O` contain at point `P`?" This shift from point-sets to loan-sets, tracked *flow-sensitively* (per CFG point rather than unified per variable), dissolves the branch-merging imprecision above: on the `true` branch, the origin contains only `r1`'s loan, so `drop(s1)` is fine.

The analysis is expressed as Datalog. Its **input relations** (facts extracted from MIR and type checking) include [4]:

- `subset_base(O1, O2, P)` — origin `O1` outlives `O2` at point `P` (from subtyping; the non-transitive base of the subset relation).
- `borrow_region(R, B, P)` — borrow `B` at point `P` introduces region/origin `R`.
- `cfg_edge(P, Q)` — control flow edges.
- `loan_killed_at(L, P)` — the reference created by loan `L` is overwritten at `P`, so the loan need not propagate further.
- `origin_live_on_entry(O, P)` / `region_live_at(R, P)` — liveness facts.
- `invalidates(B, P)` — point `P` accesses a place in a way that violates loan `B`'s terms.
- `placeholder(O)` — origins for universal (generic) lifetimes, live everywhere.

Its **rules** compute, in order [5][7]:

```datalog
// R1: seed subsets from the type checker's outlives facts
subset(O1, O2, P) :- subset_base(O1, O2, P).

// R2: transitive closure at each point
subset(O1, O3, P) :- subset(O1, O2, P), subset(O2, O3, P).

// R3: propagate subsets along CFG edges, gated by liveness
subset(O1, O2, Q) :-
    subset(O1, O2, P), cfg_edge(P, Q),
    origin_live_on_entry(O1, Q), origin_live_on_entry(O2, Q).
```

Then the *loan requirement* relation — which loans each origin must respect:

```datalog
// each origin requires the loan that introduced it
requires(R, B, P) :- borrow_region(R, B, P).

// subsets propagate requirements: O1 ⊆ O2 ⇒ O2 requires O1's loans
requires(R2, B, P) :- requires(R1, B, P), subset(R1, R2, P).

// flow-sensitive propagation across CFG, unless the loan was killed
requires(R, B, Q) :-
    requires(R, B, P), !loan_killed_at(B, P),
    cfg_edge(P, Q), region_live_at(R, Q).
```

Finally, liveness of loans and the error relation itself [5]:

```datalog
// a loan is live where some live origin requires it
borrow_live_at(B, P) :- requires(R, B, P), region_live_at(R, P).

// ERROR: a point that invalidates a live loan
errors(B, P) :- invalidates(B, P), borrow_live_at(B, P).
```

Five rules and the whole borrow checker falls out. The production implementation evaluates these rules with the *datafrog* Datalog engine (leapfrog triejoin) rather than the naive transitive-closure formulation above [5].

The precision gain comes from `requires` being computed **per point**: unlike NLL's regions, which merge across branches when they flow into one variable, Polonius's origins carry different loan sets on different paths. The conditional-drop example of §4.2 is accepted, as are the NLL "problem cases" involving conditional reborrows. This precision is also what future features need: *lending iterators* (iterators yielding borrows of themselves, rust-lang/rust#92985) are inexpressible under NLL's region model but natural once loans are tracked flow-sensitively [8].

Polonius is landing incrementally: an **α prototype** — a sound subset of the full analysis, essentially the formulation above modulo some flow-sensitivity refinements — was implemented on nightly (rust-lang/rust#143093) with the explicit goal of stabilizing a worthwhile, well-understood core first, then extending precision in later phases [8].

| Dimension | NLL (current stable) | Polonius |
|---|---|---|
| Core abstraction | Region: set of CFG points | Origin: set of loans, per point |
| Granularity | Per borrow region, merged at joins via lifetime parameters | Per (origin, point): loans tracked along each path |
| Branch merging | Regions unified under one parameter across branches | Loan sets differ per branch |
| Conditional-drop pattern | Rejected (false positive) | Accepted |
| Implementation | Custom dataflow in `rustc_mir::borrow_check` | Datalog rules over extracted facts (datafrog) |
| Status | Stable since Rust 2018 | α prototype on nightly; stabilization in progress |

*Table 2: NLL versus Polonius. The row that matters is branch merging: it is the single design decision responsible for most of NLL's remaining false positives.*

### 4.4 Two-phase borrows, drop check, and the unsafe frontier

Two pieces of adjacent machinery deserve mention because they visibly leak into the borrow checker's behavior.

**Two-phase borrows** solve `vec.push(vec.len())`. Desugaring a method call takes a mutable borrow of the receiver *before* evaluating the arguments — but the arguments (`vec.len()`, a shared borrow) must be evaluated first. The checker therefore splits the mutable borrow into a *reservation* phase (which permits shared reads of the receiver, acting like a shared borrow) and an *activation* phase (at the call itself, which then acts like a full mutable borrow) [9].

**Drop check** (`dropck`) answers a different question: when a value with a `Drop` impl (or containing one) goes out of scope, do all the types it (transitively) owns outlive the drop point? Dropck reuses the outlives infrastructure but is deliberately conservative — it reasons about *types*, which are control-flow insensitive, so conditional drops and clever generic code are sometimes rejected. Soundness first, precision later.

**The `unsafe` boundary** is where the checker's guarantees end and its *assumptions* begin. Inside `unsafe`, raw pointers (`*const T`, `*mut T`) are exempt from borrow checking entirely; the checker simply assumes that unsafe code upholds the aliasing invariants — no mutation through a shared reference's provenance, no use-after-free — that safe code's checking guarantees. The operational meaning of those invariants is given by **Stacked Borrows**, an aliasing model (validated against the test suite via Miri) that defines exactly when a raw-pointer access is undefined behavior [11]. Safe code is checked against the borrow checker; unsafe code is judged against Stacked Borrows; the two meet at the theorem that well-checked safe code cannot violate the model.

## 5 Empirical Results and Formal Evidence

**Empirical.** The NLL RFC validated the analysis against the compiler's own test suite and crates in the ecosystem, with the headline result that large bodies of previously rejected idiomatic code — the RFC's three motivating examples, including the `get_mut`/entry pattern on maps — were accepted with no soundness regressions [1][2]. Polonius's evaluation follows the same playbook: the α prototype is exercised against the full rustc test suite plus targeted problem cases (conditional reborrows, the `if cond { use(r1); drop(s1); ... }` pattern), accepting strictly more programs than NLL while reporting no new unsoundness [8].

> **Theorem (Borrowck soundness property).** *If the borrow checker accepts a function body, then in every execution, no program point accesses a place in a way that violates the terms of a loan that is live at that point.* Every borrow error rustc reports is an instance of this property's contrapositive: the checker found a point `P` and a loan `L` with `invalidates(L, P)` and `borrow_live_at(L, P)` [5][1].

**Formal.** The property above is the *design* theorem; the *proved* theorems live in the metatheory literature:

- **RustBelt** (POPL 2018) gives a semantic model of Rust's type system (λRust) in the Iris separation logic and proves its soundness — types mean ownership predicates over machine states, and well-typed programs cannot go wrong [11].
- **Oxide** formalizes the borrow checker directly: its type system features *provenance variables* (the formal ancestor of Polonius's origins) with the rule `R1 ⊆ R2 ⟹ R2` inherits `R1`'s loans — exactly the `requires` propagation rule of §4.3 — and proves soundness of the resulting system [7].
- **Stacked Borrows** (PLDI 2020) provides the operational aliasing model for `unsafe` code and validates it empirically with Miri, closing the loop between the checker's static discipline and the dynamic semantics raw pointers actually obey [11].

## 6 Limitations

The checker is conservative by construction, and the conservatism clusters in known places:

- **Closures and higher-ranked lifetimes.** Closure signatures are inferred, and the variance and higher-ranked reasoning around them remain a source of both false positives and of *overly* clever inference that later phases must defend.
- **Dropck over-approximation.** Because drop check reasons about types rather than flows, programs whose drops are conditionally safe can be rejected; fixing this requires flow-sensitive drop analysis the compiler does not yet perform.
- **Async and generators.** A borrow held across an `.await` point pins the future; the resulting errors are correct but often surprising, and the interaction of NLL regions with generator state machines is one of the least-precise corners of the implementation.
- **Polonius α vs. full.** The stabilization strategy is deliberately incremental: the α analysis is a sound, useful subset, but the full flow-sensitive precision (needed for lending iterators, #92985) arrives in later phases [8].
- **Diagnostics and compile time.** Every gain in precision complicates error messages (explaining *why* a loan is live at a point requires rendering liveness facts for humans) and costs compile time — the Datalog engine must stay within budget on million-line codebases.
- **The unsafe gap.** No static analysis checks unsafe code; soundness there rests on programmer discipline plus Miri/Stacked Borrows validation, not on proof.

## 7 Conclusion

Rust's borrow checker is best understood as three stacked ideas. *Region inference* turned lifetimes into solvable constraints over sets of program points. *Non-lexical lifetimes* re-seeded those constraints with liveness, so borrows end at their last use rather than at the closing brace. *Polonius* dissolves regions into origins — sets of loans tracked flow-sensitively by a handful of Datalog rules — and thereby accepts the conditional-borrow patterns where NLL's branch-merging is too coarse. Around this core sit two-phase borrows, the conservative drop checker, and the unsafe boundary policed operationally by Stacked Borrows. The formal record — RustBelt's semantic soundness, Oxide's provenance-based borrowck model, Stacked Borrows' validated aliasing semantics — gives unusual confidence that the discipline is *right*; the remaining work is precision and the eternal engineering trade of diagnostics against compile time.
