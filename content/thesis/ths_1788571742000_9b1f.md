# The CUDA Execution Model at Scale: SIMT Warps, Memory Coalescing, Tensor Cores, and NVLink Fabrics for Distributed Training

## Abstract

Modern large-scale deep learning rests on the CUDA execution model, whose single-instruction-multiple-thread (SIMT) discipline, hierarchical memory system, and specialized matrix-math units jointly determine the attainable throughput of distributed training. This thesis provides a rigorous treatment of the GPU hardware-software contract from the warp level upward: we formalize warp scheduling and divergence costs, derive the coalescing conditions under which a warp's 32 memory requests collapse into minimal DRAM transactions, analyze shared-memory bank-conflict serialization via XOR-based address permutations, and model Tensor Core `mma` throughput as a function of register-fragment layout and warp-tiling geometry. We then extend the analysis beyond the single device, characterizing NVLink/NVSwitch topology, the ring and tree algorithms used by NCCL collectives, the HBM bandwidth ceiling of the roofline model, and the overlap of compute with communication via CUDA streams. The work synthesizes microbenchmark literature, vendor architecture specifications, and landmark distributed-training systems to yield quantitative rules of thumb for practitioners and a set of open problems for future interconnects.

## 1. Introduction

The training of contemporary frontier models — systems with tens of billions to trillions of parameters — is overwhelmingly a GPU computation problem, and more precisely a *memory-movement* problem executed under the constraints of the CUDA programming model [1][3][4]. The raw floating-point throughput of a modern accelerator (e.g., hundreds of TFLOPS of dense FP16 on a single device) is rarely the binding constraint; the binding constraints are the rate at which operands can be delivered to the arithmetic units and the rate at which devices can exchange gradients, activations, and parameters [2][5][6].

This thesis argues that distributed-training performance can only be understood — and optimized — through a *layered* model of the hardware-software interface:

1. **The execution layer**: threads are grouped into warps of 32 that execute in SIMT lockstep; divergence serializes execution and must be modeled as a schedule-length penalty [1][2].
2. **The memory layer**: global accesses coalesce into sector transactions only under strict address-pattern constraints; shared memory avoids bank conflicts only through careful padding and swizzling [1][5].
3. **The arithmetic layer**: Tensor Cores execute warp-cooperative `mma` (matrix multiply-accumulate) instructions with rigid fragment-layout requirements; achieving peak throughput requires specific warp tiling, as exposed by microbenchmarking [2][6].
4. **The fabric layer**: NVLink, NVSwitch, and InfiniBand interconnects define a bandwidth hierarchy; NCCL selects ring or tree collective algorithms based on message size and topology, and the alpha-beta cost model predicts crossover points [7].
5. **The scheduling layer**: CUDA streams, double buffering, and communication-computation overlap hide transfer latency behind GEMM execution [3][4].

> **Thesis statement:** *Peak distributed-training throughput is achieved if and only if each layer of this stack is simultaneously saturated: divergence-free warps, coalesced accesses, conflict-free shared memory, fully occupied Tensor Cores, bandwidth-optimal collectives on a balanced fabric, and overlapped communication. A deficit at any layer leaks directly into end-to-end step time.*

The remainder of this work develops this claim formally. Section 2 reviews the CUDA machine model and the distributed-training parallelism taxonomy. Section 3 describes our analytical methodology. Section 4 conducts the deep dive across the five layers. Section 5 presents empirical results and proof sketches. Section 6 discusses limitations, and Section 7 concludes with open problems.

## 2. Background

### 2.1 The CUDA machine model

CUDA exposes a hierarchy of *threads*, *warps*, *blocks*, and *grids* [1]. The warp — a group of 32 threads executing one common instruction at a time — is the fundamental scheduling unit of the streaming multiprocessor (SM). Under the SIMT model, threads of a warp that diverge via a data-dependent branch serialize: each taken path executes with the off-path threads masked, and the warp reconverges only when all paths complete [1][2]. Branch divergence thus occurs only *within* a warp; different warps execute independently.

Since the Volta architecture, *independent thread scheduling* maintains per-thread program counters, permitting a warp to remain diverged outside a conditional region; explicit `__syncwarp()` reconverges threads when required [1][5].

### 2.2 Tensor Cores and mixed precision

Tensor Cores are specialized datapaths that compute small matrix products `D = A·B + C` per instruction. On Volta, the `mma` PTX instruction performs an 8×8×4 FP16→FP32 operation cooperatively across a *quadpair* of threads; on Turing and Ampere, tile shapes expanded (e.g., 16×8×16, 32×8×16) with new precision modes [2][6]. Because fragments are distributed across threads in an interleaved, architecture-specific pattern, correct usage requires warp-level synchronization and exact adherence to the documented operand layouts [2][6].

### 2.3 Distributed training and collectives

Data parallelism replicates the model on each GPU and synchronizes gradients with an **AllReduce**; tensor (model) parallelism shards individual layers across GPUs, requiring only a few AllReduce operations per transformer block in the Megatron-LM design [3]. The **ZeRO** optimizer instead partitions optimizer states, gradients, and parameters across data-parallel ranks, gathering them just-in-time via AllGather/ReduceScatter pairs [4]. All of these patterns are implemented by **NCCL**, NVIDIA's topology-aware collective-communication library, which probes the machine (NVLink, PCIe, InfiniBand) and selects ring or tree algorithms with Simple, LL, or LL128 protocols [7].

### 2.4 The roofline model

The roofline model bounds kernel performance by `min(π, β·I)`, where `π` is peak compute throughput, `β` is peak memory bandwidth, and `I` is the kernel's arithmetic intensity (FLOP per byte) [5]. Kernels with `I` below the *ridge point* `π/β` are memory-bound; above it, compute-bound. Tensor Cores raise `π` dramatically without changing `β`, pushing the ridge point rightward and making *more* kernels memory-bound — a central fact motivating coalescing, tiling, and quantization.

## 3. Methodology

Our analysis is *analytical and synthetic* rather than experimental: we derive performance models from published architecture specifications and microbenchmark studies, and validate the derived rules against reported measurements in the literature.

- **Sources of ground truth.** We rely on the CUDA C++ Programming Guide and Best Practices Guide for the normative SIMT and coalescing rules [1][5]; on Jia et al.'s microbenchmark dissection of Volta for instruction-level and memory-hierarchy geometry [2]; on the Megatron-LM and ZeRO papers for distributed-training communication volumes [3][4]; on NCCL documentation for collective algorithms and transports [7]; and on the SemiAnalysis survey of Tensor Core evolution for `mma` tile shapes across generations [6].
- **Cost models.** Divergence is modeled as schedule inflation; coalescing as transaction counts per warp; bank conflicts as serialization degree; collectives with the alpha-beta model `T(n) = α + n·β`.
- **Scope.** Ampere/Hopper-class hardware is the reference point; generational differences are noted where material. We do not model power or thermal constraints.

## 4. Deep Dive

### 4.1 Warps, SIMT divergence, and the independent thread scheduling model

A warp executes one common instruction at a time, so *full efficiency is realized when all 32 threads of a warp agree on their execution path* [1]. When threads diverge on a data-dependent branch, the warp serially executes each taken path with non-participating threads masked; when all paths complete, threads converge back to a common path [1].

> **Theorem:** *For a warp executing a two-way branch with per-thread condition `c(t)`, the schedule length is the sum of the instruction counts of all taken paths. The divergence penalty is zero iff `c(t)` is constant over the warp.*

The practical consequence, emphasized in the Best Practices Guide, is that the controlling condition should be written to *minimize the number of divergent warps*: because warp membership is deterministic (`threadIdx / 32`), a condition depending only on the warp index yields zero divergence [5]. For short branches the compiler may use *predication* instead — all instructions are scheduled but gated by per-thread predicates, so no branch ever occurs [5]. Volta's independent thread scheduling complicates the picture: a warp may remain diverged past the conditional, so code that previously relied on implicit lockstep reconvergence must now call `__syncwarp()` explicitly [5].

The mitigation strategy is *warp-uniform control flow*: restructure so that the branch condition is a function of `warp_id` rather than `thread_id`, or pad the workload to multiples of 32.

### 4.2 Memory coalescing and the global-memory transaction model

Global memory is accessed via fixed-size *transactions* (32-byte sectors on modern architectures). When a warp's 32 threads request words from global memory, the hardware coalesces the requests into the minimal number of transactions covering the requested addresses [1]. If consecutive threads access consecutive 4-byte words, the warp's 128 bytes are fetched in four 32-byte transactions — 100% utilization [1]. A strided or permuted pattern generates additional transactions, wasting bandwidth proportionally.

The coalescing rules can be summarized:

| Access pattern (32 threads, 4 B each) | Transactions | Utilization |
|---|---|---|
| Consecutive, 128-B aligned | 4 | 100% |
| Consecutive, misaligned by 4 B | 5 | 80% |
| Stride-2 (every other word) | 8 | 50% |
| Random / gather | up to 32 | ~12.5% |
| Broadcast (all threads, same address) | 1 | 100% (via cache) |

Two classical pitfalls deserve emphasis [1][5]:

1. **Array-of-structures (AoS) layouts.** If each thread loads a struct larger than 16 bytes, the access cannot coalesce; the fix is structure-of-arrays (SoA) or splitting the struct.
2. **2-D tiles with unpadded width.** Coalescing requires the row pitch to be a multiple of the transaction granularity; `cudaMallocPitch` exists precisely to guarantee this [1].

A coalesced GEMM prologue in CUDA C++ looks like this:

```cpp
// Coalesced global -> shared tile load; consecutive threads read consecutive words.
__global__ void gemm_tiled(const float* __restrict__ A,
                           const float* __restrict__ B,
                           float* __restrict__ C, int N) {
    __shared__ float As[32][33];  // +1 column pads away bank conflicts (see 4.3)
    __shared__ float Bs[32][33];
    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * 32 + ty, col = blockIdx.x * 32 + tx;
    float acc = 0.0f;
    for (int k0 = 0; k0 < N; k0 += 32) {
        // Perfect coalescing: thread (tx,ty) reads A[row][k0+tx], B[k0+ty][col]
        As[ty][tx] = A[row * N + (k0 + tx)];
        Bs[ty][tx] = B[(k0 + ty) * N + col];
        __syncthreads();
        #pragma unroll
        for (int k = 0; k < 32; ++k) acc += As[ty][k] * Bs[k][tx];
        __syncthreads();
    }
    C[row * N + col] = acc;
}
```

The `__syncthreads()` barriers are correctness-critical: all warps of the block must finish writing the shared tile before any warp reads it [1]. Note the `[32][33]` declaration — the extra column is the bank-conflict padding analyzed next.

### 4.3 Shared memory bank conflicts and swizzling

Shared memory is divided into 32 banks, with successive 4-byte words mapped to successive banks. When the threads of a warp access shared memory, requests to *distinct* banks proceed in parallel, but multiple threads addressing the *same bank* (different words) serialize — an *n-way bank conflict* costs *n* times the throughput [1][5].

> **Theorem:** *For a warp accessing 32 distinct 4-byte words with bank indices `b(t) = (base + t·s) mod 32`, the access is conflict-free iff `gcd(s, 32) = 1`. In particular, stride-1 access is always conflict-free, and column access into a `[32][32]` row-major tile with stride 32 is a 32-way conflict.*

The canonical fix is **padding**: declaring the tile as `[32][33]` changes the column stride to 33, and `gcd(33,32) = 1`, eliminating the conflict at the cost of one wasted column [1]. For larger or more complex access patterns, **XOR swizzling** permutes the bank mapping:

```python
def swizzled_bank(row: int, col: int, tile_cols: int = 32) -> int:
    """XOR-based bank index: spreads 2-D tile accesses across banks."""
    return ((row * tile_cols + col) ^ (row * 7)) % 32
```

XOR swizzles are the standard technique in high-performance GEMM epilogues and in CUTLASS's shared-memory layouts; they convert structured conflict patterns (diagonal, column) into uniform bank distributions without padding overhead [6].

### 4.4 Tensor Cores: the `mma` dataflow

Three properties dominate performance modeling:

1. **Fragment residency.** Operands must live in registers in the exact per-thread fragment layout; loading them requires the interleaved access pattern discovered by microbenchmarking [2]. A mislaid fragment silently computes garbage — correctness demands layout fidelity.
2. **Warp tiling.** Peak throughput requires multiple warps per block cooperating on a large output tile (e.g., 128×128×32), with double-buffered shared-memory staging so that global→shared loads overlap `mma` issue [6].
3. **The ridge-point shift.** Tensor Cores multiply `π` (peak FLOPs) by roughly 8–16× over FP32 CUDA cores while `β` (HBM bandwidth) grows only ~1.5× per generation. The roofline ridge point `π/β` therefore marches rightward each generation, and kernels that were compute-bound on FP32 become memory-bound under Tensor Cores — which is why operator fusion and quantization are not optional refinements but *first-order* requirements [5].

```haskell
-- Roofline bound: attainable GFLOPS as a function of arithmetic intensity
roofline :: Double -> Double -> Double -> Double
roofline peakFlops memBw arithIntensity = min peakFlops (memBw * arithIntensity)
-- Ridge point: intensity at which the kernel transitions memory->compute bound
ridgePoint :: Double -> Double -> Double
ridgePoint peakFlops memBw = peakFlops / memBw
```

### 4.5 NVLink/NVSwitch topology and NCCL collectives

Within a node, GPUs connect via **NVLink** (point-to-point, hundreds of GB/s bidirectional per link) and, at larger scale, **NVSwitch**, which provides all-to-all connectivity among 8–256 GPUs with full bisection bandwidth [7]. Across nodes, InfiniBand (often with GPUDirect RDMA) carries traffic at an order of magnitude lower bandwidth — the central asymmetry of cluster design.

**NCCL** is topology-aware: it probes PCIe/NVLink/IB connectivity and selects algorithms and transports (NVLink, RDMA, sockets) per collective [7]. The two canonical algorithms are:

- **Ring.** Each rank sends to its successor and receives from its predecessor; bandwidth-optimal for large messages, with time `≈ 2·(n-1)/n · S/B` for AllReduce of `S` bytes at bandwidth `B`.
- **Tree (double binary tree).** Logarithmic latency, preferred for small messages where the `α` term dominates.

> **Theorem (alpha-beta crossover):** *With per-message latency `α` and per-byte cost `β`, the ring beats the tree for AllReduce when `S ≳ α/(β·log n)`-scale thresholds — i.e., large gradient buckets favor rings over NVLink, while small control messages favor trees.*

NCCL's three protocols — **Simple** (large messages, near-peak bandwidth), **LL** (low latency, small messages), and **LL128** (a compromise) — are selected by an internal tuner based on message size [7].

### 4.6 HBM bandwidth ceilings and compute-communication overlap

HBM stacks deliver multi-TB/s of aggregate bandwidth at hundreds of nanoseconds of latency; sustaining it requires thousands of in-flight transactions, which is exactly what high-occupancy kernels provide [1][2]. When a kernel's arithmetic intensity falls below the ridge point, no amount of additional FLOPS helps; the only remedies are *moving fewer bytes* (fusion, recomputation, quantization) or *overlapping* the movement with useful work.

Overlap is achieved with **CUDA streams** and **double buffering**: while stream 0 executes the GEMM for micro-batch *k*, stream 1 issues the asynchronous copy (or NCCL collective) for micro-batch *k+1* [4]. The ZeRO-3 design explicitly relies on this: per-layer parameter AllGather and gradient ReduceScatter are prefetched and overlapped with the compute of adjacent layers, so the extra communication volume does not appear on the critical path [4]. In Megatron-LM, the two AllReduces per transformer layer are the communication to hide; with 8-way tensor parallelism inside an NVLink domain, their cost is a small fraction of the GEMM time [3].

```rust
// Conceptual overlap schedule (pseudo-Rust): comm of layer k+1 hides behind compute of layer k.
fn train_step(layers: &[Layer]) {
    for (k, layer) in layers.iter().enumerate() {
        // issued asynchronously on a copy/nccl stream; completes before layer k+1 needs it
        prefetch_params_async(layers[k + 1]);   // AllGather, ZeRO-3 style
        compute_forward(layer);                  // GEMM-bound, overlaps the prefetch
        synchronize_copy_stream();
    }
}
```

The quantitative condition for perfect overlap is simple: `T_comm(k+1) ≤ T_comp(k)`. When it holds, communication is *free*; when it fails, the exposed remainder `T_comm − T_comp` adds directly to step time. This inequality is the lens through which all distributed-training optimizations — gradient bucketing, activation checkpointing, ZeRO staging — should be evaluated [3][4].

## 5. Empirical Results / Proofs

We now instantiate the models with representative published measurements (rounded; see references for exact configurations).

### 5.1 Kernel-level efficiency

| Kernel / configuration | Bound | Achieved vs. roofline | Key enabler |
|---|---|---|---|
| FP16 GEMM 4096³, cuBLAS, A100 | Compute (Tensor) | ~85–90% of 312 TFLOPS | Warp tiling + `mma` |
| Fused attention forward, 8k seq | Memory (HBM) | ~70% of 2.0 TB/s | Tiling + online softmax |
| AllReduce 1 GB, 8×A100 NVLink | Fabric | ~90% of NVLink BW | Ring + Simple protocol |
| ZeRO-2 GPT-13B, 64 GPUs | Mixed | ~10× throughput vs. DP baseline | Sharded optimizer+grads |
| Megatron-LM GPT-8.3B, 512 V100 | Compute | 15.1 PFLOPS, 76% scaling eff. | Tensor+pipeline parallel [3] |
| ZeRO 100B params, 400 GPUs | Compute | 15 PFLOPS super-linear | Stage-1 sharding [4] |

### 5.2 Proof sketch: coalescing optimality

*Claim.* For a warp of 32 threads each loading one 4-byte word, the minimal possible number of 32-byte transactions is `⌈span/32⌉` where `span` is the address range covered, and this bound is achieved iff the addresses form a contiguous 128-byte aligned block [1].

*Proof.* Each transaction covers a disjoint aligned 32-byte sector; covering `span` bytes requires at least `⌈span/32⌉` sectors. The warp's 32 words span at least 128 bytes, with equality iff contiguous. A contiguous 128-byte block aligned to 128 bytes occupies exactly 4 sectors. ∎

### 5.3 Proof sketch: ring AllReduce bandwidth optimality

*Claim.* The ring AllReduce of `S` bytes over `n` ranks completes in `2(n−1)·α + 2(n−1)/n·S·β` and is bandwidth-optimal up to the `(n−1)/n` factor [7].

*Proof sketch.* The operation decomposes into reduce-scatter (each rank sends `S/n` chunks around the ring, `n−1` steps) followed by all-gather (`n−1` steps). Each step moves `S/n` bytes per link concurrently on all links; total per-link traffic is `2(n−1)·S/n`, giving the time above. No algorithm can move less than `2(n−1)/n·S` bytes per rank for AllReduce (each byte must be sent and received), hence optimality. ∎

### 5.4 The overlap inequality in practice

Consider a transformer layer with GEMM time `T_g` and tensor-parallel AllReduce time `T_c`. Megatron-LM's measurements on 512 V100s show sustained 39 TFLOPS/GPU (30% of peak) with 76% scaling efficiency [3] — the 24% loss decomposes into exposed communication, pipeline bubbles, and kernel inefficiency. Raising the gradient bucket size shifts NCCL into the ring+Simple regime, cutting `T_c` until `T_c ≤ T_g` and the communication vanishes behind compute [7].

## 6. Limitations

1. **Vendor specificity.** The entire analysis is NVIDIA-centric. AMD's CDNA/RDNA (wavefronts of 64, Infinity Fabric) and Intel's Xe (sub-groups, Xe Link) share the SIMT idea but differ in warp size, bank counts, and collective libraries (RCCL, oneCCL); the quantitative results do not transfer directly.
2. **Static models.** The alpha-beta model ignores congestion, adaptive routing, and multi-tenant noise; real clusters exhibit 5–15% run-to-run collective jitter that static analysis cannot predict.
3. **Microbenchmark fragility.** Results like Jia et al.'s [2] are tied to specific driver/CUDA versions; undocumented behaviors (e.g., exact `mma` fragment layouts) can change across releases, and reverse-engineered details carry no vendor guarantee.
4. **Power and thermals.** We model time, not energy. At datacenter scale, the energy cost of moving a byte across NVLink vs. recomputing it can invert purely time-based decisions.
5. **Software stack gaps.** Our treatment assumes ideal overlap; in practice, CUDA graphs, stream priorities, and NCCL's internal proxy threads introduce scheduling artifacts that the simple `T_comm ≤ T_comp` inequality elides.
6. **Generational drift.** Hopper's `wgmma`, thread-block clusters, and NVLink SHARP in-network reductions change several constants used here; the *methods* transfer, but the *numbers* must be re-derived per generation [6][7].

## 7. Conclusion

We have developed a layered performance model of CUDA-based distributed training, spanning SIMT warp scheduling, memory coalescing, shared-memory bank conflicts, Tensor Core dataflow, NVLink/NVSwitch fabrics, NCCL collectives, HBM bandwidth ceilings, and compute-communication overlap. The central result is a *conjunction thesis*: end-to-end training throughput is the minimum over per-layer efficiencies, so optimization must be holistic.

Three research directions stand out. First, *in-network computing* (NVLink SHARP-style reductions) moves collectives off the SMs entirely, changing the overlap calculus [7]. Second, *quantized communication* (as in ZeRO++ successors) attacks the `β` term directly by moving fewer bits [4]. Third, *compiler-automated overlap* — inferring prefetch schedules from dataflow graphs rather than hand-placing them — remains largely unsolved at production scale. The hardware-software contract described here is the foundation on which all three must build.
