# The eBPF Verifier: Abstract Interpretation with Tnum Domains, Bounded Loop Unrolling, and Provably Safe Kernel Extensions

## Abstract

The Linux eBPF verifier is one of the most consequential static analyzers ever deployed in production: a whole-program abstract interpreter that must prove, before a single instruction executes in kernel context, that untrusted bytecode cannot crash, hang, leak, or corrupt the kernel. This thesis dissects its design from first principles. We formalize the verifier as a **forward abstract interpretation** over a product domain of register types, interval bounds, and *tristate numbers* (tnums), and we explain the soundness and precision properties that make tnum arithmetic the load-bearing element of pointer-arithmetic reasoning [1]. We characterize the verifier's exploration strategy — bounded loop unrolling, instruction-complexity limits, and *state-equivalence pruning* — as a path-sensitive symbolic simulation with explicit termination arguments [3][4], and we analyze the speculative-execution extension that inserts Spectre v1/v4 mitigations by reasoning about bounds under transient execution [5][6]. Finally, we document systematic rejection pathologies (precision loss, false positives, path explosion), survey alternative verifiers such as PREVAIL [7], and chart the emerging verification frontier of kernel functions (kfuncs), BTF-anchored types, and control-flow graph verification of callbacks.

## 1 Introduction

Few artifacts carry as much safety responsibility per line as `kernel/bpf/verifier.c`. An eBPF program is untrusted bytecode — sometimes from *unprivileged* users — that the kernel JIT-compiles and runs at ring 0, with no hardware memory protection between program and kernel. Safety must be established *statically*, by proof, before execution: the verifier's acceptance of a program claims every reachable machine state is memory-safe and terminating [3].

This thesis makes three contributions. *First*, a rigorous account of the verifier's numeric core: the **tnum** (tristate number) abstract domain, with the soundness proofs and precision characterizations of Vishwanathan et al. [1]. *Second*, an analysis of the verifier's control-flow exploration — bounded-loop restrictions, a one-million-instruction complexity budget, and **state-equivalence pruning** — explaining both guaranteed termination and characteristic rejection pathologies [3][4]. *Third*, an examination of the Spectre-era extension, which duplicates the abstract interpretation onto the speculative path, situated against PREVAIL's polynomial-runtime abstract interpretation [7] and VeriFence's lightweight speculative defenses [5].

We begin with the necessary background, then describe our methodology for reconstructing the verifier's formal structure, and finally descend into the five deep-dive topics that follow.

## 2 Background

### 2.1 From BPF to eBPF: the trust problem

The Berkeley Packet Filter, introduced by McCanne and Jacobson, was a minimal virtual machine for packet filtering: a tiny instruction set, a two-register accumulator model, and a deliberately restricted semantics that made naive verification feasible. Extended BPF (eBPF), merged in kernel 3.18 (2014), generalized this into a *general-purpose in-kernel execution environment*: eleven 64-bit registers, a 512-byte stack, maps, tail calls, and eventually bounded loops, function calls, and callbacks. The trust problem correspondingly exploded. Whereas classic BPF filters could be validated by a few dozen lines of checks, eBPF programs are compiled C code whose pointer arithmetic, memory accesses, and control flow must be proven safe at load time [2][8].

The canonical architecture [3] has two phases. *Phase one* validates the control-flow graph: a DAG *modulo bounded-loop back-edges*, no unreachable instructions, no out-of-range jumps, calls only to whitelisted helpers or verified subprograms. *Phase two* simulates execution over all paths, tracking the abstract state of every register and stack slot.

### 2.2 The register state lattice

For each register and stack slot, the verifier maintains a `struct bpf_reg_state` unifying type and value information [3]:

> **Definition 2.1 (Register state).** A register state is a tuple *(type, off, var_off, smin, smax, umin, umax)* where *type* ∈ {NOT_INIT, SCALAR_VALUE, PTR_TO_CTX, PTR_TO_MAP_VALUE, PTR_TO_STACK, PTR_TO_PACKET, ...}, *off* is the exactly-known fixed offset, *var_off* is the *tnum* variable offset, and *(smin, smax, umin, umax)* are the signed and unsigned interval bounds.

This is already recognizably an abstract-interpretation design: the concrete domain is the set of 64-bit machine states; the abstract domain is a **product lattice** of a flat type lattice, the interval domain, and the tnum domain. The transfer functions for ALU operations, jumps, and memory accesses update this tuple; the join operation merges states at control-flow confluence points. Soundness of the whole verifier reduces to soundness of each transfer function plus a correct (conservative) join.

### 2.3 What "safe" means: the verifier's proof obligations

The verifier must establish five properties for every path through the program [2][3]:

1. **Type safety.** Pointers and scalars are never confused; arithmetic on pointers is restricted to well-defined patterns.
2. **Memory safety.** Every load and store falls within an accessible, initialized region owned by the program (stack frame, packet bounds, map value bounds).
3. **Initialization.** No register or stack slot is read before being written (the NOT_INIT type).
4. **Termination.** Every path executes within the instruction-complexity budget; loops provably terminate.
5. **Speculative safety** (Spectre v1/v4). No path *under speculative execution* can perform out-of-bounds accesses usable for side-channel exfiltration [6].

Note what is *not* required: functional correctness — a program that drops every packet is perfectly safe. The verifier promises safety, not sense [2].

## 3 Methodology

Three sources: *first*, the kernel source (`kernel/bpf/verifier.c`, `include/linux/bpf_verifier.h`, `kernel/bpf/tnum.c`) and its documentation — ground truth of the *implemented* domain [3]; *second*, the formalization literature — Vishwanathan et al.'s tnum semantics and proofs [1], VeriFence's speculative-safety formalization [5], PREVAIL's polynomial-runtime reconstruction [7]; *third*, the historical record — LWN on bounded loops and `bpf_loop()` [4], Borkmann's Spectre systematization [6], the iovisor bpf-internals JIT lineage [8].

Analytically, we re-derive the verifier as **Cousot-style abstract interpretation**: concrete collecting semantics, abstraction/concretization maps, sound transfer functions, and the exploration algorithm (worklist DFS with state pruning) as a fixed-point computation. Where the kernel deviates from the textbook — *path-sensitive* rather than *flow-sensitive* exploration, an explicit complexity budget — we read the deviation as a deliberate trade of asymptotic elegance for precision and deployability.

## 4 Deep Dive

### 4.1 The Verifier as an Abstract Interpreter over Register States

The kernel verifier is a **forward abstract interpreter** in the Cousot–Cousot sense: it lifts the small-step operational semantics of the eBPF ISA (concrete register files `R : Reg → u64`, memories) to abstract states `σ̂ : (Reg ∪ Stack) → State` over the product domain of Definition 2.1, computing reachable abstract states by symbolic execution.

The decisive design choice is *path sensitivity*: instead of joining abstract states at CFG merge points, the kernel verifier performs an explicit **depth-first enumeration of paths**, pushing `bpf_verifier_state` records onto an exploration stack. When it reaches an instruction with a previously recorded state, it invokes the *state-equivalence* test (`states_equal`): if the current abstract state is *subsumed* by a previously explored state at the same point — every register's abstract value componentwise ≤ in the product lattice — the path is pruned, since the prior exploration already covered all behaviors reachable from a *more general* state [3].

> **Theorem (Pruning soundness).** If abstract state `σ̂₁ ⊑ σ̂₂` at program point *p*, then every concrete state reachable from *p* under `σ̂₁`'s concretization is also reachable under `σ̂₂`'s; hence pruning the `σ̂₁` path preserves the verification verdict.

This buys enormous precision — no join-induced widening at merge points — at the cost of potential **path explosion**, controlled by the complexity budget (Section 4.3): an inversion of the usual tradeoff, accepting analysis non-termination (rejection on budget exhaustion) for maximal precision on accepted programs.

```c
/* kernel/bpf/verifier.c — exploration core, schematically */
while ((state = pop_stack(env))) {          /* worklist DFS */
    while (insn_idx < insn_cnt) {
        err = do_check_insn(env, &state);
        if (env->insn_processed > BPF_COMPLEXITY_LIMIT_INSNS)
            return -E2BIG;
    }
}
```

The verifier's "analysis" is thus a **proof search**: each accepted path is a verified execution, and acceptance is the conjunction of all path verdicts. Its failure modes are failures of proof search — timeouts, imprecision, search-space exhaustion — not type errors in a decidable type system [7].

### 4.2 The Tnum Domain: Bitwise Reasoning via Tristate Numbers

The verifier's numeric heart is the **tnum** (tristate number) domain. Intervals `[smin, smax]` cannot express eBPF's pointer arithmetic: `r1 = r2 | 0x3c00` needs *alignment* (known bits), `r1 = r2 << 3` needs exactly-zero low bits. Intervals forget *which bits* are known; tnums remember [1].

> **Definition 4.1 (Tnum).** A tnum is a pair `(value, mask)` of 64-bit words with the wellformedness invariant `value & mask == 0`. Bit *i* is *known-0* if `valueᵢ = 0, maskᵢ = 0`; *known-1* if `valueᵢ = 1, maskᵢ = 0`; and *unknown* (denoted χ) if `maskᵢ = 1`. The concretization `γ((v,m)) = { x : x & ~m == v }`.

The abstraction `α(S)` sets `mask` to the OR of all pairwise differences in `S` and `value` to the agreed bits; `(v₁,m₁) ⊑ (v₂,m₂)` iff `m₂ ⊆ m₁` and known bits agree — a lattice of height ≤ 65 with 3⁶⁴ elements.

Addition follows the algorithm analyzed in [1]:

```c
/* kernel/bpf/tnum.c */
struct tnum tnum_add(struct tnum a, struct tnum b)
{
    u64 sm = a.mask + b.mask;
    u64 sv = a.value + b.value;
    u64 sigma = sm + sv;
    u64 chi = sigma ^ sv;
    u64 mu = chi | a.mask | b.mask;

    return TNUM(sv & ~mu, mu);
}
```

> **Theorem (Vishwanathan et al. [1]).** `tnum_add` is *sound*: for all wellformed `a, b` and all `x ∈ γ(a), y ∈ γ(b)`, `x + y ∈ γ(tnum_add(a,b))`. Moreover it is *representationally optimal*: `tnum_add(a,b)` is the most precise tnum containing `{x+y : x ∈ γ(a), y ∈ γ(b)}` — no tighter tnum exists.

The subtlety is carry propagation through unknown bits: `chi = sigma ^ sv` marks exactly the positions where unknown-region carries *could* diverge. Multiplication is harder — the kernel's original implementation was sound but imprecise, and Vishwanathan et al. give an SMT-verified replacement that is both sound and *maximally precise relative to the kernel's version* [1]. Division and modulo remain conservative, and these precision cliffs directly cause verifier rejections (Section 4.5).

The tnum domain is what makes **pointer arithmetic verifiable**: a derived pointer is `base + off + var_off` with tnum `var_off`, and an access at `ptr + t` is safe iff `γ(t)` lies within the object's bounds. Because tnums track *alignment* (low known-zero bits) exactly, they accept programs whose intervals alone would be too coarse — e.g., aligned access into map values after masking. Intervals bound *magnitude*; tnums bound *bit patterns* [3].

| Operator | Sound | Optimal | Notes |
|---|---|---|---|
| `tnum_add` | ✓ | ✓ | carry analysis via `chi` [1] |
| `tnum_sub` | ✓ | ✓ | via negation + add |
| `tnum_and/or/xor` | ✓ | ✓ | bitwise exact |
| `tnum_lshift/rshift` | ✓ | ✓ | shift amount must be known |
| `tnum_mul` | ✓ | ✗ (kernel) / ✓ (new [1]) | original imprecise; SMT-verified replacement |
| `tnum_div/mod` | ✓ | ✗ | conservative; precision cliff |

### 4.3 Bounded Loops, Complexity Limits, and State-Pruning Exploration

For its first five years, the verifier simply *rejected* programs with CFG back-edges (for unprivileged programs): without a fixed-point argument, the path-sensitive exploration could not terminate on a loop. Kernel 5.3 introduced **bounded loops**: back-edges are permitted if the verifier can prove the loop bounded — in practice by simulating until state-equivalence pruning fires, i.e., the abstract state at the loop head is subsumed by a previously seen state and further iteration provably adds no new behavior [2][4].

State pruning does double duty: loop "unrolling" is *semantic*, not syntactic — each iteration explored with its precise abstract state — and verification terminates by the **finite lattice height** at the loop head plus the complexity budget. Two mechanisms bound the search:

1. **`BPF_COMPLEXITY_LIMIT_INSNS`** — one million processed instructions (up from 4096 in 5.2); exceeding it rejects with `E2BIG`. Not a mere timeout but a *proof-theoretic* bound: verification terminates in bounded time regardless of program structure.
2. **State pruning** — revisiting a program point with a subsumed state prunes the path. The test compares all live registers and stack slots componentwise: the verifier's analogue of widening, except that instead of *accelerating* convergence by over-approximating, it *recognizes* convergence by subsumption and stops [3].

The LWN-documented **`bpf_loop()`** alternative takes loop mechanics out of the bytecode entirely: the kernel iterates a callback, so termination holds by construction and the verifier checks only the callback body [4]. When path-sensitive proof search fails to scale, the system recovers decidability by *restricting the language* rather than weakening the analysis.

Conceptually, loop verification accumulates loop-head abstract states and accepts when a new state is subsumed by a seen one, rejecting on budget exhaustion. In practice, bounded-loop verification remains the verifier's most fragile feature: small changes in loop structure (unrolling depth, induction-variable arithmetic through imprecise tnum operators) can push a program over the complexity budget or defeat subsumption, producing rejections of *safe* programs — the false-positive pathology analyzed in Section 4.5 [4][7].

### 4.4 Speculative Bounds and Spectre v1/v4 Mitigation in Verification

Spectre (2018) reframed the threat model: architectural safety — no out-of-bounds access on any *executed* path — no longer sufficed, since a mispredicted branch could transiently load out of bounds and exfiltrate through a cache side channel. The fix was to extend the abstract interpretation onto the **speculative path** [6].

The kernel's approach, systematized by Borkmann [6], has three layers:

1. **Speculative path analysis.** The verifier duplicates path exploration onto mispredicted branches, tracking attacker-influenced registers under speculation. A load safe architecturally but unsafe transiently — the Spectre v1 gadget `if (x < bound) y = arr[x]` — is *detected at verification time* [6].
2. **Mitigation by transformation.** Detected gadgets are *rewritten*: register-offset pointer ALU becomes constant-offset ALU where possible, indirect jumps become direct (retpolines avoided), and speculation barriers or masking are inserted otherwise [6].
3. **Spectre v4 handling.** Stack spill/fill sequences and initial stack reads receive targeted mitigations, since speculative store bypass could resurrect stale stack data across the spill boundary [6].

In 2021, researchers showed the verifier's own pointer-arithmetic reasoning performed *undesirable out-of-bounds speculation*, defeating its Spectre mitigations and enabling kernel-memory exfiltration by unprivileged programs — requiring deep fixes in `verifier.c` itself. The verifier is thus both *enforcer* and *member* of the speculative-safety attack surface.

**VeriFence** [5] formalizes the speculative-safety requirement the kernel verifier *should* enforce, shows the upstream defenses are both incomplete (missed gadgets) and over-conservative (rejecting safe programs), and proposes a lightweight alternative: targeted taint-driven analysis of speculative data flows, inserting barriers only where a genuine speculative gadget exists. It is simultaneously *stronger* and *cheaper* — this thesis's recurring theme that monolithic proof search yields to more precise abstract domains [5].

### 4.5 Precision Loss, Rejection Pathologies, and the KFunc/CFG Verification Frontier

The verifier is *sound but incomplete*, and its rejections fall into systematic pathologies traceable to design decisions in the abstract interpretation:

- **Precision cliffs.** Tnum division/modulo and the original multiplication are imprecise; intervals are non-relational. A loop counter through `div` may widen to ⊤, defeating loop-head subsumption and exploding the path count past budget — forcing programmers into "verifier-friendly" arithmetic, a folk abstract-interpretation discipline [7].
- **Path explosion.** Path-sensitive exploration with no joining turns *n* independent branches into up to 2ⁿ paths. Real programs (XDP parsers with sequential header checks) hit `E2BIG` despite being obviously safe; the remedy is restructuring or splitting — programming *against* the analyzer [2][7].
- **Pruning failures.** Subsumption needs componentwise ⊑ over all live state; one oscillating register (a tnum whose mask never stabilizes) prevents pruning, degrading verification to full unrolling — the mechanism behind most bounded-loop rejections [4].

These pathologies motivate two frontiers. *First*, **kfuncs**: kernel functions typed by BTF, with the verifier enforcing reference-counting, locking, and lifetime disciplines *at verification time* — an ownership type system growing atop the abstract interpreter, whose soundness argument is correspondingly less settled. *Second*, **CFG verification of callbacks**: `bpf_loop()`, timer callbacks, and iterators demand *higher-order* control-flow reasoning — the callback is verified once, the kernel's iteration trusted — and formalizing this as sound modular analysis, in the proof-carrying-code style, remains open [7].

PREVAIL [7] is the most complete alternative: a from-scratch abstract interpreter with *polynomial* runtime, conventional joins and widening, and a mechanized soundness argument — trading path-sensitive precision for predictable verification time and a trustworthy proof. That tension — precision-first proof search versus predictable polynomial analysis — is the central open question of eBPF verification research.

## 5 Empirical Results and Proofs

The key formal results underwriting the verifier's soundness claims:

1. **Tnum soundness and optimality.** Vishwanathan et al. [1] give SMT-based (bitvector-encoded) machine-checked proofs that all kernel tnum operators are sound and that `add`, `sub`, and bitwise operators are representationally optimal; their new multiplication is proven sound and precise relative to the kernel's.
2. **Register-domain soundness.** The product lattice is sound *provided* each transfer function over-approximates its concrete semantics — by inspection for ALU ops, by the tnum proofs [1] for bitwise reasoning. End-to-end soundness of `verifier.c` remains *unmechanized*: the largest unverified trusted component, as the 2021 speculative-bounds flaws [5] remind us.
3. **Termination.** The 10⁶-instruction budget trivially terminates the analysis; the subtle claim — that *legitimate* programs verify within budget — holds for kernel selftests and Cilium-class workloads but fails on adversarial branch structures [2][7].
4. **Empirical precision.** PREVAIL's 111-benchmark evaluation [7] shows intervals alone are *insufficiently precise* while relational domains (octagons, polyhedra) are prohibitively expensive — justifying the tnum-plus-interval product as the practical sweet spot. VeriFence [5] shows upstream Spectre defenses miss real gadgets while rejecting safe programs.

> **Theorem (Summary soundness claim).** *Modulo the unmechanized transfer functions and the speculative-execution model, the kernel verifier accepts only programs whose every reachable concrete execution is memory-safe, initialized, and terminating within bounded steps* [1][3][5].

The "modulo" clauses are doing real work — they are exactly where the CVE history lives.

## 6 Limitations and Open Problems

1. **No mechanized end-to-end soundness proof.** Tnum operators are verified [1] and the JITs have formal treatment, but `verifier.c` — tens of thousands of lines of intricate C — has no machine-checked proof. Every verifier CVE reminds us the analyzer is in the trusted computing base.
2. **Structural incompleteness.** Safe programs are always rejected; only *which* varies. The path-sensitive design makes the rejection set unpredictable and version-dependent, taxing developers and tooling (BCC, Cilium, bpftrace all carry verifier-workaround lore).
3. **Informal speculative model.** The kernel's speculative analysis approximates microarchitectural transient execution; VeriFence [5] shows false negatives *and* positives against a more precise model. A verified speculative semantics for the eBPF ISA is open.
4. **Nascent compositionality.** Kfuncs, callbacks, and tail calls use ad-hoc modular reasoning; a uniform compositional framework — verified function summaries in the proof-carrying-code style — does not exist upstream.
5. **Budget cliffs.** The 10⁶-instruction budget is arbitrary; near-boundary programs exhibit chaotic accept/reject behavior across kernel versions. A *predictable-cost* analysis in the PREVAIL spirit [7], adopted upstream, would stabilize the ecosystem.

## 7 Conclusion

The eBPF verifier is abstract interpretation at planetary scale: forward, path-sensitive analysis over types × intervals × tristate numbers, extended — uniquely among production analyzers — onto the speculative path to contain transient execution. Its tradeoffs are deliberate: path sensitivity over joins for precision, an explicit complexity budget over fixed-point elegance for guaranteed termination, a bitwise tnum domain over relational domains for the expressiveness/speed sweet spot [1][3][7].

The formal record is impressive — machine-checked soundness and optimality for the numeric core [1], a polynomial-runtime reconstruction [7], a precise speculative-safety formalization [5] — yet the center is unverified: `verifier.c` itself. As eBPF grows toward kfunc-mediated kernel extension and higher-order control flow, the frontier is compositional, mechanized, predictable verification that preserves the kernel verifier's precision while earning its soundness claims by proof rather than audit. Until then, every accepted program is a theorem whose proof checker is written in C — and whose bugs are CVEs.
