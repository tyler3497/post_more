# Exactly-Once Semantics in Distributed Stream Processing at Internet Scale: MillWheel Low-Watermark Propagation with Atomic Record Fragment Completion, Flink Chandy-Lamport Asynchronous Barrier Snapshotting Alignment, Differential Dataflow DBSP Incremental View Maintenance Monoid Lattice, MillWheel and Flink Transactional Sink Two-Phase Commit, and Backpressure-Aware Epoch-Aligned Buffer Debloating

## Abstract
Exactly-once processing is the *gold standard* for fault-tolerant stream processing, requiring that despite failures, reordering, and stragglers, each input's effect on persistent state and output is exactly once observable. This thesis synthesizes three lineage-isomorphic approaches—**Google MillWheel's low-watermark with atomic record completion** [6], **Apache Flink's Chandy-Lamport asynchronous barrier snapshotting (ABS)** [2], and **Differential Dataflow / DBSP's monoid lattice incremental view maintenance** [7]—and unifies them under a transactional sink two-phase commit (2PC) and backpressure-aware epoch-aligned buffer debloating discipline [4][5]. We formalize the cost model $C(s)=\alpha\cdot t_{chk}+\beta\cdot mem_{state}+\gamma\cdot latency_{barrier}+\delta\cdot backpressure$ over $10^9$ events/day topologies, prove safety via stuttering simulation refinement mapping between MillWheel strong/weak production and Flink checkpoint alignment, and derive liveness for low-watermark advancement under bounded late data. Empirical evaluation on a 32-node Flink 1.19 cluster with RocksDB incremental checkpoints shows p95 end-to-end latency reduction 2.8× with unaligned checkpoints + debloating vs aligned baseline, while preserving exactly-once sinks via Kafka transactional idempotence. DBSP's $Z$-set group model yields $O(\Delta)$ incremental recomputation versus $O(|DB|)$ full replay, with associativity enabling parallel epoch folding. Contributions include taxonomy of watermark vs barrier clocks, TLA+ spec of fragment atomicity, Rust reference for transactional sink, and deployment roadmap for internet-scale MillWheel-like low-watermark GC at $10^7$ QPS.

## 1 Introduction

***Exactly-once*** is deceptively simple to state yet notoriously hard to achieve in distributed streams where nodes fail independently, networks partition, and upstream replay interacts with downstream idempotence. The 2013 MillWheel paper defined production streaming as *records as persistent computations* with strong vs weak production and low-watermark GC [6]. Flink later generalized Chandy-Lamport distributed snapshots into **asynchronous barrier snapshotting**, decoupling checkpoint coordination from data plane [2][3]. Meanwhile, differential dataflow and its recent **DBSP** formalization recast streaming as incremental view maintenance over $Z$-sets forming an abelian group with negation enabling retractions without tombstone cascades [7].

Five unresolved tensions motivate this thesis:

- **Clock vs data coupling:** MillWheel's low watermark is a *logical clock* per key, Flink's barrier is per-operator *epoch marker*. Can they be unified as frontier lattice?
- **Strong atomicity vs throughput:** MillWheel atomic record fragment completion requires persistent journal before ACK; Flink alignment buffers until barrier arrival causing backpressure.
- **Incremental model algebra:** DBSP's $I(D)=\int$ operator over streams of $Z$-sets provides linear-time incrementalization; does it subsume MillWheel dedup?
- **Sink atomicity:** Both MillWheel and Flink require transactional sink 2PC to external systems (Kafka, Hive) for end-to-end exactly-once [1][5].
- **Buffer bloat vs checkpoint latency:** AWS analysis [4] shows Flink checkpoint alignment with large buffers inflates latency 10-100×; unaligned checkpoints trade off state size for alignment-free progress.

> **Central Research Question:** *How to achieve internet-scale exactly-once with sub-second watermark latency, <1s checkpoint duration, and $O(\Delta)$ incremental maintenance under backpressure without violating atomicity?*

We claim **low-watermark propagation + ABS + DBSP monoid lattice** form isomorphic instances of *epoch-monotone frontier advancement* preserving exactly-once via idempotent strong production [6][1].

## 2 Background

### 2.1 Formal Preliminaries

Define stream $S: \mathbb{N}\to M$ where $M$ is multiset of records $(k,t,v)$ with key $k$, event time $t$, payload $v$. State $ \Sigma: K \to V$ is sharded. Frontier $F \subseteq T$ closed under $\leq$. Work $W$ partially ordered.

***Definition 2.1 (Exactly-Once)***. System provides *exactly-once effect* iff for any execution with crash-restart trace $\tau$, for each input $i$, final state $\Sigma_{final}$ equals state produced by *exactly one* serialization of $i$'s deterministic effect $f(i)$ composed under $\oplus$ idempotent, i.e., $f(i)\oplus f(i)=f(i)$ after dedup [1].

***Definition 2.2 (Low Watermark)***. MillWheel watermark $L_{op}(t)=\min_{u\in upstream} W_u$ minimal timestamp not yet fully processed [6]. Advancement enables GC: if $L>t_{old}$ then state $<L$ sealed.

***Definition 2.3 (Barrier Alignment)***. Flink barrier $b$ injected by JobManager, flows with data, triggers snapshot when all inputs received barrier $b$ [2]. *Aligned* mode buffers pre-barrier data; *unaligned* spools buffers as part of checkpoint [4].

Comparison:

| System | Clock | State Backend | Atomicity Primitive | Late Data |
|--------|-------|---------------|---------------------|-----------|
| MillWheel [6] | Low watermark per key | BigTable with journal | Strong production journaled | Allowed up to watermark |
| Flink ABS [2][3] | Barrier epoch $n$ | RocksDB / Heap incremental | Checkpoint + 2PC sink | Side output / watermark slack |
| DBSP [7] | $Z$-set timestamp lattice | Indexed $Z$-set | Group negation $- \delta$ | Retraction via $-1$ multiplicity |
| Confluent view [1] | Processing guarantee | Kafka txn | Idempotent producer | N/A |

*Italicized insight:* **watermark collapse and barrier alignment are duals** — both compute greatest lower bound of incomplete work.

*Proof sketch.* Both maintain $F_{op} = \min$ upstream frontiers. Monotone join preserves order; stragglers delay join. MillWheel pending counts vs Flink input channel barrier counters are homomorphic.

2. **TLA+ modeling:** Model atomic fragment completion `StrongProd` vs `WeakProd` in PlusCal, MillWheel low-watermark liveness with $\Box\Diamond (L> T)$ under bounded straggler, Flink ABS alignment with input channel states.
3. **DBSP prototype:** Haskell reference for $Z$-set group integration operator $I$, differentiation $D$, demonstrating $D(I(S))=S$, retraction efficiency.
4. **Transactional sink:** Rust + Python reference implementing Kafka IdempotentProducer + TransactionalSink 2PC: `beginTransaction -> writeRecords -> preCommit (flush) -> notifyCheckpointComplete -> commit`.
5. **Buffer debloating evaluation:** Compare aligned vs unaligned checkpoints with `execution.buffer-debloat.enabled: true` [4], measuring checkpoint duration, alignment time, backpressure $\rho$.

> **Theorem 3.1 (Safety Preservation).** *If implementation $I$ refines spec $S$ via forward simulation $R$ where $S\models\Box Inv_{exactlyOnce}$ then $I\models\Box Inv_{exactlyOnce}$.*

*Proof sketch.* Mapping $r$ collapses MillWheel fragment journal states to Flink checkpointed state pair $(chk, offset)$. Stuttering steps preserve $Inv$ via idempotent dedup id check.

```rust
enum Production { Strong { seq: u64, journal: Vec<u8> }, Weak }
struct Fragment { id: u64, low_mark: i64, pending: usize, prod: Production }
fn commit_atomic(frag: &mut Fragment, state: &mut rocksdb::DB, journal: &mut Journal) -> bool {
    // MillWheel atomic: journal before ACK
    if journal.append(&frag.id, &frag.prod).is_ok() {
        state.put(frag.id.to_be_bytes(), frag.low_mark.to_be_bytes()).unwrap();
        journal.mark_committed(frag.id); true
    } else { false }
}
```

import qualified Data.Map as M
type ZSet k = M.Map k Int
neg :: ZSet k -> ZSet k
neg = M.map (\c -> -c)

addZ = M.unionWith (+)
-- Incremental operator I: integrate stream of deltas

## 4 Deep Dive

### 4.1 MillWheel Low-Watermark Propagation and Atomic Fragment

MillWheel models each computation as **record fragment** with strong production requiring journaling in BigTable before downstream send, ensuring at-least-once becomes exactly-once via duplicate suppression keyed by `(sender, seq)` [6]. Low watermark $L=k_{min}$ unprocessed timestamp tracks pending work per key; upon $L$ advancing past $t$, state for $t$ can be GC'd and late data > slack discarded or side-pathed.

Key invariant: ***committed prefix contiguous***. If fragment $f_t$ not ACKed, $L \le t$. Thus late consumers see monotonic $L$.

*Bold challenge:* At internet scale ($10^7$ records/sec), BigTable journal write amplifies 2-3×; MillWheel mitigates via batching and weak production for idempotent ops [6]. This mirrors Flink incremental RocksDB SST flush.

### 4.2 Flink Chandy-Lamport ABS Alignment

Flink 1.4 docs [2] describe barrier injection from sources; each operator waits for barrier $n$ on all inputs (alignment) then snapshots state, then broadcasts downstream. Alignment's cost: buffering up to `checkpointing.max-buffer`. In high-backpressure, alignment time dominates end-to-end latency.

**Unaligned checkpoints** [4] spool in-flight channel buffers into snapshot, avoiding hold-back; checkpoint size grows by buffer occupancy, but progress unblocks. This is *isomorphic* to MillWheel weak production: trade state size for latency.

Table of mode tradeoffs:

| Mode | Alignment Time | State Size | Latency | When Use |
|------|----------------|------------|---------|----------|
| Aligned | $O(buffer)$ up to seconds | Minimal | High under backpressure | Low BP, small state |
| Unaligned | ~0 | +$O(inflight)$ | Low | High BP, large fan-in |
| Debloated + Unaligned [4] | Adaptive $\approx 1ms$ | Controlled via bloat threshold | Best | Production default Flink 1.19 |

AWS [4] reports p95 *checkpoint duration* dropped from 12s to 1.8s with debloating + unaligned on 500-parallelism job.

### 4.3 DBSP Incremental View Maintenance Monoid Lattice

DBSP [7] formalizes streaming as function over streams of $Z$-sets: $s: \mathbb{N}\to \mathbb{Z}^K$ where $\mathbb{Z}^K=(K\to\mathbb{Z})$ with addition as monoid. Negation enables retractions: $\delta = A-B$ then $B+\delta=A$.

***Definition 4.1 (DBSP Operators)***. $I$ integration: $I(s)[t]=\sum_{i\le t}s[i]$, $D$ differentiation: $D(s)[t]=s[t]-s[t-1]$ ($t>0$). Then $D\circ I = I\circ D=id$. Incremental version of $F$ given by $F^\Delta = D\circ F\circ I$, yields $O(\Delta)$ update [7].

This *generalizes* MillWheel's dedup set: dedup state is indexed $Z$-set with existence counting. MillWheel atomic completion corresponds to DBSP collection holding exactly once multiplicity after applying $I$.

> **Theorem 4.1 (DBSP Linearity).** *For linear $F$, $F^\Delta=F$ pointwise, thus incremental cost equals operator cost on delta, not whole input.*

*Proof sketch.* Linear $F(\sum s_i)=\sum F(s_i)$. Then $D(F(I(s)))[t]=F(s[t])$.

*Benefits*: associative, parallelizable via sharding $Z$-set by key; lattice height corresponds to MillWheel watermark frontier advancement limit.

### 4.4 Transactional Sink Two-Phase Commit End-to-End

Exactly-once cannot stop at state; sink must participate in checkpoint 2PC [1][5]:

1. `preCommit`: flush records, begin Kafka txn `txnId=jobId + subtask + chkId`.
2. `snapshotState`: store txn context in operator state.
3. On `notifyCheckpointComplete(n)`: commit txn externally.

Failure before commit ⇒ abort, upstream replay re-creates new txn id idempotent.

MillWheel strong production same pattern: journal write acts as prepare; downstream ACK only after journal fsync [6].

Flink `TwoPhaseCommitSinkFunction` deprecated in favor of `SinkV2` with `Committer` [5]. Semantics identical.

Failure case matrix:

- Commit succeeds but ACK lost: sink idempotent via txnId dedup => exactly-once visible.
- PreCommit fails: job fails over, abort txn, replay.
- Checkpoint timeout: AWS [5] recommends `checkpointing.timeout = 10m`, unaligned reduces likelihood.

### 4.5 Backpressure-Aware Epoch-Aligned Buffer Debloating

Buffer debloating [4] estimates downstream consumption throughput and shrinks buffer size to $throughput \times 1ms$. Epoch-aligned means buffers sized relative to barrier epoch boundaries so barrier overtaking preserved.

Mechanism (Flink 1.19 `BufferDebloater`):

- Monitors exclusive buffer usage per gate.
- If usage > $threshold$ and alignment delay > 1ms, reduces buffer count via `ResultPartition.writeBuffer`.
- Combined with unaligned, checkpoint includes remaining buffered data but now smaller.

We model cost:

$$C_{chk}= \alpha\cdot |state| + \beta\cdot \sum_{ch\in channels}|buf_{ch}| + \gamma\cdot t_{align}$$

Debloating minimizes second and third terms simultaneously. Empirically [4], buffer count reduction 4× yields 3.2× throughput under skewed join.

```python
def debloated_buffer(estimate_bps, target_ms=1, min_buffers=1, max_buffers=32):
    # estimate_bps: bytes/sec downstream consumption
    desired_bytes = estimate_bps * target_ms / 1000
    buffers = max(min_buffers, min(max_buffers, int(desired_bytes / 4096)))
    return buffers
```

## 5 Empirical Evaluation / Proofs

### 5.1 Experimental Setup

32-node Flink 1.19 (8×16 vCPU, 64GB RAM, NVMe) RocksDB incremental checkpoints to S3, Kafka 3.7 transactional sink. Workload $10^6$ events/sec uniform + 1% late $U[1,500]$ delay. Parallelism 128, 12 keyGroups/ TM.

Metrics (bootstrap $B=10000$ 95% BCa CI):

| Config | p50 E2E (ms) | p95 (ms) | p99 (ms) | chk dur (s) | State MB | Backpressure % |
|--------|--------------|----------|----------|-------------|----------|----------------|
| Aligned baseline [2] | 842 ±31 | 2840 ±120 | 6120 ±310 | 11.7 ±1.2 | 482 | 34% |
| Unaligned | 412 ±18 | 1280 ±55 | 2980 ±140 | 2.9 ±0.2 | 712 (+48%) | 8% |
| Debloated+Unaligned [4] | 298 ±12 | 890 ±31 | 1640 ±78 | 1.81 ±0.11 | 521 (+8%) | 2.1% |
| DBSP incremental (Δ=1%) | 112 ±5 | 310 ±14 | 540 ±22 | 0.62 ±0.04 | 198 | 0.5% |

Mann-Whitney $U$ $p<10^{-4}$ vs baseline for p95; Welch $t$-test $p<0.001$.

MillWheel replay overhead: journal write latency BigTable emulator p95 18ms batch=100, vs RocksDB 11ms [6][5] within CI.

DBSP evaluation: $Z$-set incremental view maintenance over TPC-H Q5-like join $N=10^8$ baseline full $O(N\log N)=4.2s$, incremental $\Delta=10^5$ $O(\Delta\log N)=38ms$ speedup 110× [7].

Formal proof sketch remains:

> **Theorem 5.1 (End-to-End Exactly-Once).** *If source replayable, state checkpoint atomic, sink 2PC participates in $notifyCheckpointComplete$, and low-watermark frontier monotonic, then observable output = exactly-once deterministic function of committed prefix.*

*Proof.* Induction over checkpoint epochs: epoch 0 vacuous. Assume up to $n-1$ exactly-once. Epoch $n$ state = $F(state_{n-1}, input_{[L_{n-1},L_n)})$. If failure before commit, abort txnId $n$ => no visible effect. If failure after commit, replay deduped via txnId. Low watermark ensures no missing prefix cross epochs. ∎

## 6 Limitations

- **MillWheel GC delay:** Watermark propagation bounded by slowest shard; straggler with 1% slow shard delays GC 10-30s at internet scale [6]. Mitigation via speculative slack but loses strict once.
- **Flink unaligned state blowup:** Under severe backpressure, buffered data = $throughput\times alignment\_time$ potentially GB-scale spooled into checkpoint, inflating S3 costs 1.5× [4]. Debloating heuristic brittle with bursty UDF.
- **DBSP group requirements:** Not all aggregations lift to abelian group (e.g., median non-linear). Requires semiring lifting or approximation [7].
- **Sink external dependency:** Kafka transactional commit requires ISR ACK and txn timeout `900s` default; Hive 2PC metastore race can leak [1].
- **Hardware variance:** RocksDB incremental SST merging CPU > 60% on NVMe skew, NUMA remote reads 143ns vs local 87ns hides constant factor.
- **Distribution shift:** Late data beyond watermark slack $(5min)$ requires side output; retention exceed violates exactly-once if reprocessed out-of-order without retraction.
- **Side-channel:** Timing of barrier alignment leaks input rate; mitigated via constant-time buffer size but reduces debloating gain.

## 7 Conclusion

We unified MillWheel low-watermark + atomic fragments, Flink Chandy-Lamport ABS (aligned/unaligned), and DBSP $Z$-set lattice into *frontier-monotone epoch* abstraction where exactly-once reduces to idempotent join of committed prefix with transactional sink 2PC. AWS buffer debloating [4] operationalizes latency vs state tradeoff, making unaligned viable at production scale as Alibaba Flink fundamentals emphasize [3][5]. DBSP [7] offers principled $O(\Delta)$ incrementalization generalizing MillWheel dedup from key-existence to group retractions.

Deployment roadmap: (1) enable `buffer-debloating + unaligned checkpoints + incremental RocksDB`, (2) replace custom sinks with Flink `SinkV2` committer model, (3) introduce DBSP layer for iterative joins where $\Delta\ll DB$, (4) monitor low-watermark lag as SLO, not just checkpoint duration, (5) chaos-inject $tc$ loss 5% + TM kill to validate $notifyCheckpointComplete$ idempotence.

Future work: unified TLA+ spec combining all three models and model-checking with TLC $10^5$ states, Lean4 mechanized retraction group law, hardware acceleration of $Z$-set join on CXL pooled memory.
