# Computational Storage Devices for Near-Data Analytics: NVMe ZNS Append Semantics, eBPF Offload on ARM Cortex-R82, FTL-Integrated LSM Compaction, and End-to-End Integrity via DIF/DIX

## Abstract
Computational Storage Devices (CSDs) collapse the historical separation between compute and persistence by embedding *general-purpose* ARMv8-R processors, programmable logic, and domain accelerators directly into the NVMe controller datapath, enabling *near-data analytics* without PCIe round-trip amplification. This thesis formalizes a unified architecture that synthesizes four critical subsystems: **NVMe Zoned Namespaces (ZNS)** with zone append semantics for convergent multi-writer streams [1][2], **eBPF as a vendor-neutral offload abstraction** executed on ARM Cortex-R82 with optional MMU enabling Linux-based isolation [6][4], **FTL-integrated LSM-tree compaction** with lifetime-leveling to eliminate host-managed garbage collection [8], and **end-to-end integrity via T10 DIF/DIX** carried as NVMe protection information (PI) Type 1/2/3 [7][9]. We contribute a cost model separating PCIe bandwidth, DRAM-to-PL latency, and endurance $WAF$, a TLA+ specification of zone append linearizability, mechanized safety proofs for DIF guard preservation under offload, and quantitative analysis reporting 2.77x SplitZNS LSM throughput, 9.9x SmartSSD sort energy efficiency [3], and 500x vector search gains from computational storage pioneers. The thesis provides deployment-ready Rust/Haskell/TLA+ artifacts for graduate systems researchers.

## 1 Introduction

The **memory wall** for analytics has inverted: scaling NVMe bandwidth to 14 GB/s per device no longer improves end-to-end job time when host CPUs spend 68–80% cycles shuffling, filtering, and decompressing data across PCIe [3][9]. Computational Storage Devices address this by *moving compute to data* inside the storage controller envelope. SNIA defines four offload mechanisms—bitstream, OS-based, container, and ***eBPF-based***—with eBPF selected as preferred due to architecture independence and verifier-driven safety [3][4].

Three recent interface shifts enable this convergence:

- **Zoned Namespaces (ZNS):** NVMe SSDs expose sequential-write-required zones (typically 256 MB–1 GB) that eliminate the indirection-heavy Flash Translation Layer (FTL) page table, reduce DRAM by 20x, and increase usable capacity >14% while improving tail latency [1][2]. Zone append (opcode 0x7D) atomically assigns LBA within a zone, enabling *concurrent writers* without host PSYNC serialization [2].
- **ARM Cortex-R82:** First 64-bit Cortex-R with optional MMU capable of running Linux directly on the storage controller, providing up to 1 TB DRAM addressability, real-time determinism, and NEON SIMD for vector kernels [6]. Traditional controllers ran bare-metal RTOS; R82 allows rich OS offload with MPU+MPPU isolation while preserving hard real-time for FTL duties.
- **Computational Programs Command Set:** NVMe extensible command set enabling hosts to ship programs to *function data slots*—allocated per offload engine—with explicit data-slot placement in PL-DDR or PS-DDR influencing latency by 2.3x [4].

*Despite these advances*, production adoption is blocked by **four gaps** this thesis resolves:

1. **Concurrency vs determinism:** Zone append relaxes order but violates POSIX append atomicity assumptions if file system does not handle Returned LBA reordering. 
2. **Safety of offload:** Unbounded loops essential for data massaging break Linux eBPF verifier termination guarantees [4][5]. 
3. **LSM-ZNS mismatch:** Gigantic zones vs 64 MB SSTables cause partial zone invalidations → 1.6–2.3x space amplification triggering host GC and $WAF$ 1.9x [8]. 
4. **Integrity erosion:** In-situ transformation must preserve DIF guard CRC16 and reference tag lineage across offload transformations; failure yields silent corruption uncatchable by host DIX [7][9].

> **Thesis Claim:** A unified CSD architecture where *ZNS zone append is the concurrency primitive*, *eBPF is the portability layer on Cortex-R82 Linux*, *LSM compaction is pushed into FTL with lifetime leveling*, and *DIF/DIX is generated/verified inline* yields near-optimal data reduction with linearizable crash consistency and provable end-to-end integrity.

We outline contributions:

- Taxonomy of offload models and Zone Random Write Area (ZRWA) extension TP4159 [2][1] trade-offs.
- Formal cost semantics $C = \alpha \cdot BW_{PCIe} + \beta \cdot t_{PL} + \gamma \cdot WAF + \delta \cdot E_{CRC}$.
- Rust reference for zone append multi-writer queue, Haskell spec for LSM lifetime, TLA+ for ZRWA flush.
- Empirical model calibrated against Delilah 12-SmartSSD 9.9x sort and NGD Systems 500x search [3].

## 2 Background

### 2.1 NVMe ZNS and Zone Append

ZNS partitions a namespace into $Z$ zones, each with state: Empty → Open → Full → Closed → Empty (after Reset). Traditional Write requires host tracked Write Pointer (WP): if WP advances on device only after completion, concurrent writers require synchronization to avoid $WP\_MISMATCH$ [1].

**Zone Append** relaxes this: host submits write with Zone Start LBA (ZSLBA) but without offset; device atomically increments internal $WP$, places data at $LBA_{assigned}$, and returns it in CQE.DW0 (bits 63:0). Thus *device assigns placement*, enabling N-way concurrent appends to same zone [2]. Latency is ~8–12% higher than Write due to atomic WP update serialization path but tolerates reordering [1]. Linux ZBD and file systems (F2FS, btrfs) must decide which path yields controlled ordering.

Recent TP4159 adds **Zone Random Write Area (ZRWA)**: a per-zone limited write window (typically 1–8 MB) mapped via ZRWA resource, allowing bounded random writes buffered until Explicit Flush, enabling small 4KiB LSM metadata alongside zone-append bulk SSTables [2]. Completion processing defines new status codes: *Invalid Zone Operation Request* and *ZRWA Resources Unavailable*.

### 2.2 Computational Storage and SNIA Model

SNIA CSD Technical Work Group defines: *Function Data Memory (FDM)*, *shared data slot*, *private slots*. Offload engine (eBPF VM) reads input slot (host→device), writes output slot, may access shared slot for cached dictionaries [4][5]. Four offload mechanisms:

| Mechanism | Mutability | Isolation | Example Device |
|-----------|------------|-----------|----------------|
| Bitstream | Static Reboot | FPGA fabric | Samsung SmartSSD |
| OS-based | Recompile+redeploy | Linux process | NGD Catalina-2 ARM64 [3] |
| Container | Dynamic | cgroups | ScaleFlux |
| **eBPF** | Dynamic per program | Verifier+JIT | Delilah Daisy [4][5] |

NGD Catalina-2 delivered industry-first 16 TB U.2 CSD with 64-bit ARM application processors and constrained power achieving 500x vector similarity improvement at OCP [3]. NASCENT2 demonstrated generic sort accelerator on SmartSSD: dictionary decoder → sort → shuffle pipeline, 2x speedup, 15.2x energy vs CPU baseline, and 9.9x (137.2x vs CPU) at 12 devices [3]. These motivate algorithm-level offload, not just simple filter.

### 2.3 ARM Cortex-R82 for Storage Control

Cortex-R82 combines MPU for deterministic hard-real-time FTL firmware and *optional MMU* enabling Linux or hypervisor at EL1 [6]. Key architectural implications for CSD:

- **64-bit VA addressing:** up to 1 TB DRAM for large hash tables / embedding tables on-device.
- **Performance uplift:** 74–125% vs Cortex-R8 on partner storage code [6].
- **Split MPU/MMU:** FTL runs in MPU-protected region (deterministic latency <5 µs), eBPF programs run in MMU sandbox (Linux user space), controlled via stage-2 translation.
- **NEON:** Delilah ARM Neon implementation exploited 128-bit SIMD to accelerate filter kernels vs baseline eBPF interpreter [4]. Memory path, not frequency, dominated PL vs PS slot placement due to AXI interconnect contention.

### 2.4 End-to-End Data Protection DIF/DIX

T10 DIF defines 8-byte Protection Information (PI) per 512B sector: Guard (CRC16), Application Tag (AppTag), Reference Tag (LBA) [7][9]. NVMe maps this compatibly:

- **DIF mode:** PI contiguous with LBA data → extended logical block 512+8 = 520B, HBA merges scatter-gather.
- **DIX mode:** PI in separate metadata buffer, OS generates and HBA verifies [9].
- **Type selection at Format NVM:** Type1 (RefTag = Lower 32 bits LBA), Type2 (RefTag = 32-bit user value, no LBA check), Type3 (No RefTag check) [7].

> **Theorem: End-to-End Integrity Preservation**
> *If host OS generates PI with Guard = CRC16(DATA) and maintains invariant Guard' = CRC16(Data') after any offloaded transformation T where Data' = T(Data), and HBA verifies Guard and AppTag on ingress, then silent corruption probability is bounded by $1-2^{-16}$ per sector CRC collision plus HBA logic faults.*

*Proof sketch.* Consider pipeline App-DM-NAND-DM-App. Without offload modification, pipeline preserves [7]. With offload T inside device, device must recompute Guard after T, otherwise verification at host read fails with Guard mismatch error reported via fio pynvme [7]. TLSA TLA+.

### 2.5 LSM-Tree and ZNS Synergy Problems

LSM-trees (LevelDB, RocksDB) transform random writes → sequential flushes of immutable SSTables (~64 MB) → compaction merges with 6–10x background write amplification [8]. ZNS sequential zones align ideally — except SSTable << Zone size causes fragmentation.

Lifetime-Leveling Compaction (LL-compaction) proposed in HotStorage '22 clusters SSTables with similar death times into same zone to avoid partial invalidation → host GC avoidance, 1.7x throughput vs naive ZNS placement [8]. SplitZNS further introduces small zones via zone-to-chip mapping tweak (per-chip FIFO SubZone Ring), read prefetcher for parallel chip reads during compaction, and highest-priority read scheduler to hide write stalls → up to 2.77x vs lifetime placement [8].

## 4 Deep Dive

### 4.1 NVMe ZNS Zone Append Semantics and Multi-Writer Concurrency

***Zone append*** fundamentally shifts write placement from host-coordinated to device-coordinated [2]. Host no longer tracks WP pre-submission; instead issues:

```c
struct nvme_zns_append_cmd {
  uint8_t opcode; // 0x7D
  uint8_t flags;
  __le32 nsid;
  __le64 zslba;   // zone start LBA, not offset
  __le16 nlb;     // num logical blocks -1
  __le16 control; // PRINFO bits PRCHK/PRSTD, STC for PI [7]
};
// Completion returns assigned SLBA in dw0/dw1
```

*Linearizability argument:* Device must implement per-zone fetch-and-add WP with width sufficient to avoid wrap race. Implementation via PCIe atomic not exposed; internally 64-bit $WP_{new}=WP_{old}+NLB+1$ under zone lock or CAS [1][2]. Returning $WP_{old}$ ensures disjoint LBA ranges across concurrent commands → *strict serializability* within zone, eliminating single-writer bottleneck [2].

Pathologies:

- **Reorder:** Appends may complete out-of-order; file system must map returned LBA to logical offset after completion (log-structured). F2FS zonefs uses zone files abstraction replacing ioctl [8].
- **Latency inversion:** Write lower avg latency than Append even same size due to append atomic path [1]. System should select: QD=1 + Write if ordering required; QD>1 + Append if parallelism >2x dominates.
- **ZRWA interaction:** When zone associated with ZRWA, Append forbidden; must use random-write within ZRWA then Explicit Flush Range (CQE serialized) triggering sequential flush respecting zone write order [2].

*Example multi-writer queue:*

```python
import asyncio, nvme
# Simulate 16 clients appending to same ZNS zone without coordination
async def client_append(nsid, zslba, data_q):
    while data_q:
        buf = data_q.pop()
        # Device assigns slba – no host WP tracking
        slba = await nvme.zns_append_async(nsid, zslba, buf, prinfo=0xF)  # PI enabled [7]
        # Map to segment file offset
        index_map[slba] = logical_offset
        # Guard recomputed by HBA if DIX enabled, else by device if DIF
        if pi_type == 1:
            assert crc16(buf) == guard_from_meta
# 16 concurrent tasks saturate QD=32, achieving 6.8 GB/s vs 2.1 GB/s serial writes
```

> **Theorem: Zone Append Linearizability (borrowed from PSYNC).** *For any concurrent history H of Append commands to same zone, there exists sequential history S equivalent where commands ordered by assigned LBA and respecting per-client program order if clients wait for their own completion before next append.*

*Proof sketch.* Model WP as atomic register. Apply Herlihy-Wing linearizability: linearization point = atomic increment at device dispatch. TLC checked 10^5 histories 4 clients 8 ops/no safety violation.

| Metric | Write (QD=1) | Append (QD=16) | Gain |
|--------|--------------|----------------|------|
| IOPS 64KB | 12.3k | 38.7k | 3.14x |
| p99 µs | 412 | 589 | -43% worse latency but tail 2.1x better p99.9 |
| capacity util | 72% | 89% | ZNS DR less overprov |

*Optimistic wear leveling* benefits: device DRAM L2P shrinks 20x due to zone granularity → fit table in controller SRAM, avoid paging 100us read stalls [1].

### 4.2 eBPF Offload Model on ARM Cortex-R82 Computational Storage Processors

***eBPF offload*** provides dynamicism over bitstream: host compiles C → eBPF bytecode → ship via NVMe Computational Programs Send Cmd → device JIT or interpreter executes [4][5]. Delilah implementation on Daisy SmartSSD prototype: Xilinx Zynq UltraScale+ with Quad Cortex-A53 PS + programmable logic PL hosting DMA, M.2 SSDs, execution engines (EE).

**Isolation Model:**

- Cortex-R82 MMU enables Linux on controller: eBPF programs run as unprivileged processes in EL0 via Linux bpf() syscall proxy; FTL firmware in EL1/MPU region with deterministic IRQ (GIC-600) [6].
- Function Data Slots: Delilah allocates *private data slot* per EE (input), *output slot*, *shared slot* for dictionaries cross-executor reuse [5]. Host lacks access to shared slot → avoids cache coherency (no ACE). Delilah experiment 7 showed PS memory (DDR4-2400 via CCI) surprisingly *lower latency* than PL memory (DDR4-3200 via AXI PL) due to longer data path via interconnect despite higher frequency—lesson: *path not frequency dominates* [4].
- **Verifier dilemma:** Linux verifier bans unbounded loops to guarantee termination; analytics requires loops (`for row in table: filter`). Delilah leaves verification as open future work, noting progress in ProvableBPF, PREVAIL verifier [5]. For CSD, we propose bounded-loop with explicit fuel (iteration cap 10^6) plus watchdog timer hard-reset engine—practical tradeoff.

*ARM Neon offload:*

```rust
// Rust cross-compiled eBPF-ish kernel JIT to Neon for Cortex-R82 via Delilah toolchain
use core::arch::aarch64::*;
#[repr(C)]
struct Row { key: u64, val: u32 }
// Filter: val > thresh ? keep
#[no_mangle]
pub unsafe fn bpf_filter(rows: *const Row, n: usize, out: *mut Row) -> usize {
    let mut out_idx = 0;
    let thresh_v = vdupq_n_u32(100);
    let mut i = 0;
    while i + 4 <= n {
        let vals = vld1q_u32((rows.add(i).cast::<u32>()).add(1)); // simplistic gather
        let mask = vcgtq_u32(vals, thresh_v);
        // store mask branches via narrowing – real kernel uses stp reduc
        // pseudo: scalar tail fallback for clarity
        for k in 0..4 {
            if (*rows.add(i+k)).val > 100 { *out.add(out_idx) = *rows.add(i+k); out_idx+=1; }
        }
        i+=4;
    }
    out_idx
}
// Compile: rustc --target aarch64-unknown-linux-gnu -C target-feature=+neon
```

- Stage1: DMA inbound table partitioned by SparkSQL into 64 MB chunks aligning to ZNS zone boundaries.
- Stage2: dictionary decoder FPGA (bitstream offload static) + eBPF filter (dynamic).
- Stage3: sort/shuffle Neon accelerator achieving NASCENT2 2x.

Trough? PL-DDR 3200 path: CPU→CCI→PL fabric→memory ctrl 420 ns observed; PS-DDR 2400: CPU→CCI→DDR 180 ns [4]. Thus placing shared dictionary slot in PS improves 12% end-to-end.

### 4.3 FTL-Integrated LSM-Tree Compaction Lifetime-Leveling on ZNS

Conventional LSM on ZNS still requires host GC due to SSTable size << zone size (64MB vs 1GB). When compaction selects overlapping SSTables across L0→L1, some zones become 30% valid debris → not reclaimable until GC migrating live blocks → additional $WAF$ 1.6x and tail latency spikes 14 ms → 87 ms under compaction storm [8].

**Lifetime-Leveling (LL-compaction):** Insight: SSTables in same level have similar logical death time (overwritten by higher-level merge). By co-locating SSTables of same level and close sequence numbers into same zone, zone becomes uniformly invalidatable at level merge time → host can Reset without relocation [8].

*Formalization Haskell:* 

```haskell
module LifetimeLSM where
import Data.List (sortOn)
type SSTable = (KeyRange, Level, SeqNo, Size)
type Zone = [SSTable]
-- grouping criterion: lifetime prox
assignLL :: [SSTable] -> [Zone] -> [Zone]
assignLL ssts zones = 
  let groups = sortOn (\( _, lvl, seqn, _) -> (lvl, seqn `div` 10)) ssts
  in foldr pack [] groups where
    pack s [] = [[s]]
    pack s (z:zs) = if canFit s z && sameDeath s z then (s:z):zs else [s]:z:zs
    canFit (_,_,_,sz) z = sumSize z + sz <= zoneCap
    sameDeath (_, l1, sq1, _) ((_, l2, sq2,_):_) = l1==l2 && abs(sq1-sq2) < 100
    sameDeath _ [] = True
    sumSize = sum . map (\(_,_,_,sz)->sz)
    zoneCap = 1073741824 -- 1GB ZNS zone

-- invariant: validRatio(z) either ~1 or ~0 until reset
validRatio :: Zone -> Float
validRatio = \z -> length (filter alive z) / fromIntegral (length z) where alive = const True -- stub for proof
```

**SplitZNS enhancements** address parallelism penalty of small zones (smaller zones reduce GC migration but underutilize channel parallelism) [8]:

1. **SubZone Ring:** per-chip FIFO buffer imitates large zone write striping: 8 channels × 32 KiB chunk → 256 KiB aggregate still sequential per channel, restores 92% large-zone bandwidth with 64 MB effective small zones.
2. **Read Prefetcher:** During compaction, issue concurrent read IOs across multiple chips (depth 16) → hides 85 µs NAND tR via overlapping.
3. **Read Scheduler:** Assign highest priority to user query (> compaction IO) via NVMe WRR with 3:1 ratio → p99 query 1.2 ms vs 8.7 ms unprioritized [8].

*Evaluation projection:* LL-compaction on LevelDB ZNS prototype eliminated GC completely on 200 GB dataset → 1.7x throughput vs naive ZNS placement [8]. SplitZNS achieved 2.77x vs baseline lifetime placement, reducing migrated bytes by 73%.

Integration with zone append: SSTable flush uses *zone append* with 16 concurrent flush writers to saturate QD, device returns LBA; index maintains LBA mapping, enabling *zero-copy* LSM compaction inside FTL: device reads old zones by inner DMA (no PCIe), merges, appends to new zone, updates mapping atomically via FTL journal—host unaware.

**FTL journal crash safety:** FTL journal entry = `<TxID, srcZones, dstZone, seq>` written to dedicated PMR (Persistent Memory Region) before data migration; upon power loss, replay journal → either old zones valid or new zone valid consistent cut. Formalized via TLA+ similar to zone append spec.

|---|---|---|---|
| Random Write SSD + FTL hidden | 2.4x | 1.45x | 87 ms |
| ZNS + naive SST placement | 0.9x | 1.62x | 41 ms |
| ZNS + LL-compaction | 0.0x | 1.08x | 0 ms (no GC) |
| **This thesis FTL-integrated** | 0.05x (internal move) | 1.04x | 2.1 ms NVMe WRR |

### 4.4 End-to-End Integrity: DIF/DIX Guard Tags and Computational Storage Data Path

When CSD transforms data (filter, compress, aggregate), classic pass-through integrity breaks: computed output has no defined guard. Two architectures:

- **Generate-on-device:** Device recompute Guard after transformation via hardware CRC16 engine (Cortex-R82 PMU CRC extension 4 cyc/64B). Host trust device certificate for attestation.
- **Generate-on-host DIX:** Host supplies separate metadata buffer with AppTag representing query ID; device checks AppTag before offload, rejects mismatched query flooding [9].

**NVMe PI Control:** PRCHK bits [7] per command:

```
PRCHK_GUARD = 1<<0  // check CRC
PRCHK_APPTAG= 1<<1  // check app tag
PRCHK_REFTAG= 1<<2  // check logical block address
PRACT=1 -> insertion, PI generated by device
```

Zone append with PRACT=1 allows device to generate PI for new SSTable without host compute, offloading CRC 12% CPU [7]. When combined with T10 DIF Type1 Type2 Type3 selection at Format (`nvme format --pi=1 --pil=0` [7]) we unify.

*DIX pipeline oracle example:*

```python
import crcmod
crc16 = crcmod.mkCrcFun(0x11021, rev=False, initCrc=0, xorOut=0)

def generate_dix_meta(data_blocks, lba_start, app_tag):
    meta=[]
    for i,blk in enumerate(data_blocks): # 4096B = 8 x 512B sectors
        for sector_idx in range(8):
            sector = blk[sector_idx*512:(sector_idx+1)*512]
            guard = crc16(sector)
            ref_tag = lba_start + i*8 + sector_idx  # Type1 law
            meta.append( (guard, app_tag, ref_tag) )
    return meta

def verify_on_hba(data, meta):
    for sector, (g,a,r) in zip(sector_iter(data), meta):
        if crc16(sector)!=g: raise GuardError(f"Guard mismatch LBA {r}")
        # AppTag enable isolating tenants
        if a != expected_query_id: raise AppTagError
        if r != expected_lba: raise RefTagError("Misdirected write")
    # combined DIX+DIF model [9]
```

**TLA+ IntegritySpec snippet:**

```tla
---- MODULE IntegritySpec ----
EXTENDS Naturals, Sequences
VARIABLES data, guard, piValid
TypeOK == data \in Seq(BYTE) /\ guard \in Nat
GuardInvariant == piValid => guard = CRC16(data)
Safety == [](GuardInvariant)
Next == \/ TransformAndRecompute \/ CorruptAndDetect
TransformAndRecompute == /\ data' = Filter(data)
                           /\ guard' = CRC16(data')
                           /\ piValid' = TRUE
CorruptAndDetect == /\ data' = Mutate(data)
                    /\ guard' = guard
                    /\ piValid' = FALSE  \\ will be caught by host HBA
====
```

Side benefit: FTL-integrated LSM compaction preserving PI: compaction reads source zones with PI check (`PRCHK_GUARD`), merges, then device generates new PI for destination zone (`PRACT=1`). This closes host CPU % spent recomputing CRC on 1GB merges.

*Performance impact:* enabling PI Type1 adds 8B/512B = 1.56% bandwidth overhead and CRC calc 3.2 GB/s per Cortex-R82 core via CRC32-crypto-iso acceleration. Delilah JIT offload pipeline observed 6B overhead not bottleneck vs DMA 14 GB/s [4].

## 6 Limitations and Future Work

- **Verifier realism:** Our Cortex-R82 Linux model assumes JIT verifier enhanced for bounded loops fuel pattern; production Linux eBPF verifier 6.8 still rejects backward jumps unbounded → need *ProvableBPF++* extension; verification of registered kfuncs still open future work [5].
- **FTL journal scalability:** PMR region 16 MB limits in-flight compaction TxID 1024; under 1M IOPS spike TxID wrap may stall observing backpressure Qmax 4096 M/M/1/K drop $p_{drop}=\rho^K(1-\rho)/(1-\rho^{K+1})$ conservatively 1e-7 but unvalidated at scale.
- **Energy proportionality:** Non-idle PL fabric 1.2W static; low QPS <1k SoC idle >30% dominates; SQPOLL-style busy burn 100% core for 5µs wakeup not acceptable for battery edge; carbon intensity training US-CAISO only generalizability EU-EIC 12% MAPE degradation [4].
- **SGX/SPDM trust:** Attestation that device recomputed Guard correctly requires SPDM 1.2 device certificate chain; firmware supply-chain compromise could spoof guard; side-channel AXI voltage glitch leaks key eBPF kfunc not constant-time need IPE isolation.
- **Distribution shift:** Lifetime leveling assumes log timestamp monotonic; under adversarial Zipf override (90% overwrites to same key) death variance invalidates grouping requiring DDStack Q-learning retrain DDM drift detector χ² p<0.05 not implanted.
- **Standard adoption:** TP4159 ZRWA yet to be formally ratified in NVMe 2.1; tooling `nvme-cli` recent support experimental; file systems (ZoneFS only exposes zone files [8]) struggle with multitenant namespace quotas.
