# Inside the Modern Linker: ELF Relocation, Symbol Resolution, Identical Code Folding, and Link-Time Optimization in mold and lld

## Abstract

The ELF linker sits at the narrowest point of the build pipeline: it must reconcile millions of independently compiled fragments into a coherent, loadable image. This thesis presents a comparative study of two modern linkers — LLVM's **lld** and **mold**, both largely authored by Rui Ueyama — focusing on four pillars: ELF relocation processing, symbol resolution, identical code folding (ICF), and link-time optimization (LTO). We examine how mold's clean-slate design replaces lld's interleaved, largely serial pipeline with data-parallel passes, including eager archive parsing and atomic compare-and-swap symbol resolution [1][2]. We formalize relocation application as a set of closed-form address expressions, contrast lld's optimistic hash-bucket ICF algorithm with mold's digest-based variant, and dissect the trade-offs between monolithic and ThinLTO. Drawing on published benchmarks and architectural documentation, we show that mold links multi-gigabyte binaries 2.4–16.1× faster than lld [1], and argue that the decisive factor is not any single optimization but the systematic elimination of serial bottlenecks in every pass. We close with open problems: ICF soundness, archive-ordering semantics, and the tension between determinism and parallelism.

## 1. Introduction

Linking is frequently described as the most intellectually neglected phase of the compilation toolchain. Compilers receive decades of sustained research attention; linkers inherit a fifty-year accumulation of ad-hoc features and are expected, simply, to work. Yet for large C++ programs the link step dominates the edit–compile–debug cycle, and its cost grows super-linearly with program size because every cross-module reference must be resolved against a global symbol table.

Two linkers define the current state of the art on Unix systems. **lld**, the LLVM project's linker, demonstrated that a carefully engineered linker could outperform the venerable GNU BFD `ld` by an order of magnitude. **mold**, written by Rui Ueyama — the original developer of lld [2] — is a from-scratch redesign whose explicit goal is to make linking as close to instantaneous as hardware permits. The two projects share a lineage but diverge architecturally: lld interleaves input scanning with symbol resolution in a largely serial main thread, parallelizing only selected phases, while mold applies *data parallelism systematically across the entire pipeline*, from eager parallel parsing of every archive member to parallel relocation scanning, garbage collection, ICF, and output generation [1].

This thesis examines four mechanisms that determine what a modern linker is:

1. **ELF relocation processing** — the closed-form address arithmetic that patches machine code, plus the PLT/GOT machinery required for position-independent and dynamically linked binaries.
2. **Symbol resolution** — the global name-binding problem, including archive semantics and the atomics-based parallel resolution strategy introduced by mold.
3. **Identical code folding (ICF)** — the size optimization that merges textually identical sections, and the pessimistic/optimistic algorithmic split between GNU gold, lld, and mold.
4. **Link-time optimization (LTO)** — whole-program optimization at link time, contrasting monolithic LTO with ThinLTO's summary-based, parallel-backend design.

Our central claim is that mold's headline speedups — 2.4–16.1× over lld and up to 112× over GNU ld on large real-world programs [1] — are best explained not by any individual optimization but by the removal of serial phases, an argument grounded in Amdahl's law and supported by the paper's ablation study.

## 2. Background

### 2.1 The ELF object model

An ELF relocatable object (`.o`) is a collection of *sections* — `.text`, `.data`, `.rodata`, `.bss`, `.symtab`, `.strtab` — each carrying a fragment of the final address space. Because a compiler sees only one translation unit at a time, every reference to an external symbol is left as a *relocation record* in a companion section (`.rela.text` for RELA-style records on x86-64), which instructs the linker to "fill the offset X of section Y with a computed function of symbol Z" [3]. The linker's two fundamental operations are therefore **combining object files into a single file** and **applying relocations**; as Ueyama's design notes put it, everything else is secondary [3].

Each relocation record carries four fields: the *offset* P within its section, the *type* (e.g. `R_X86_64_PC32`), the referenced *symbol* S, and an *addend* A. The linker computes the final value according to the type's defining expression [4]:

| Relocation type | Computation | Typical use |
|---|---|---|
| `R_X86_64_64` | `S + A` | Absolute 64-bit addresses |
| `R_X86_64_PC32` | `S + A − P` | PC-relative 32-bit references |
| `R_X86_64_PLT32` | `L + A − P` (L = PLT entry) | Calls to external functions |
| `R_X86_64_GOTPCREL` | `G + A − P` (G = GOT entry) | GOT-relative data access |
| `R_X86_64_32S` | `S + A` (sign-extended) | Signed 32-bit absolute |
| `R_X86_64_RELATIVE` | `B + A` (B = load bias) | Dynamic, position-independent |

### 2.2 Dynamic linking: PLT, GOT, and symbol versioning

When a binary is linked against shared objects, some addresses cannot be known until load time. The linker therefore synthesizes *stubs*: the **Global Offset Table (GOT)** holds addresses the dynamic loader fills in, and the **Procedure Linkage Table (PLT)** holds trampolines that lazily resolve function calls on first use. The linker emits *dynamic relocations* (`.rela.dyn`, `.rela.plt`) into the output so the runtime loader can complete the binding [4]. **Symbol versioning** (`.gnu.version`, `.gnu.version_r`) further annotates dynamic symbols so that multiple ABI revisions of the same library can coexist — a mechanism lld carefully preserves in its synthetic-section pipeline [4].

### 2.3 What the pipeline looks like

A canonical ELF link proceeds through these stages: parse input files; resolve symbols; run global transforms (garbage collection, ICF); synthesize sections (`.got`, `.plt`, `.dynsym`, `.rela.dyn`); map input sections to output sections; scan relocations; finalize layout; assign file offsets; and write the output [4]. The interesting engineering questions are which of these stages are serial, which admit data parallelism, and where the asymptotic costs hide.

## 3. Methodology

This thesis is an *architectural comparative study* rather than a re-implementation. Our evidence base consists of:

- **Primary design documents**: the mold design notes [3] and the lld "NewLLD" design documentation [4].
- **A peer-reviewed performance study**: Ueyama's ASPLOS 2027 paper on mold, including its ablation study isolating per-pass speedups [1].
- **Practitioner analysis**: MaskRay's (Fangrui Song's) detailed dissection of lld's ICF algorithm and its costs [5], and the LLVM ThinLTO design document [6].
- **Engineering notes**: notes on linker pipeline structure, ICF algorithm families, and symbol-resolution passes [7].

We adopt three analytical lenses. First, *complexity analysis*: we express the cost of symbol resolution, relocation scanning, and ICF in terms of the number of symbols *n*, relocations *r*, and sections *s*. Second, *parallelism accounting*: for each pipeline stage we ask whether its data dependencies permit a parallel `for_each` decomposition, following Amdahl's law — parallelizing only a subset of passes leaves the serial remainder as a hard ceiling on speedup [1]. Third, *semantic fidelity*: we track which optimizations are provably sound, which are observably benign, and which (notably ICF) are technically unsound but empirically safe [4].

> **Theorem:** (Amdahl bound on linker parallelism). If a fraction *f* of link time is spent in inherently serial phases and the remainder is perfectly parallelizable over *p* cores, speedup is bounded by 1 / (*f* + (1 − *f*) / *p*). Hence, for large *p*, speedup → 1/*f* regardless of how aggressively the parallel portion is optimized.

This bound is the mathematical spine of the mold paper's argument [1]: lld's serial phases — symbol resolution interleaved with archive scanning, sequential garbage collection, layout — constitute a fixed *f* that no amount of per-pass tuning can overcome.

## 4. Deep Dive

### 4.1 Symbol Resolution at Scale: from Interleaved Scans to Atomic Compare-and-Swap

Symbol resolution is the linker's central naming problem: given millions of defined and undefined symbols spread across object files, archives, and shared libraries, bind each undefined reference to exactly one definition according to precedence rules (strong over weak, first-seen archives lazily extracted, dynamic symbols shadowed by definitions).

Classical linkers process inputs in command-line order, interleaving parsing with resolution: when an archive is encountered, members are extracted on demand as undefined symbols accumulate. This entanglement is the fundamental obstacle to parallelism — the decision to parse archive member *i* depends on resolution state produced while parsing member *i − 1* [7]. lld follows this model: it finds and scans input files (`.o`, `.so`, `.a`) interleaved with symbol resolution on the main thread, then runs global transforms [5].

mold breaks the entanglement by *eager* parsing: it parses **all** input files — including **every** member of **every** archive — in parallel *before* performing any symbol resolution, then resolves symbols as a separate parallel pass using atomic compare-and-swap [1]. Conceptually, each symbol-table slot is claimed by the winning definition via a CAS loop:

```rust
// Simplified model of mold's parallel symbol resolution.
// Each thread processes its own files; claims are arbitrated by CAS.
fn resolve_symbol(slot: &Atomic<Slot>, candidate: &Symbol) {
    let mut current = slot.load(Ordering::Relaxed);
    loop {
        let winner = precedence(current, candidate); // strong > weak, etc.
        match slot.compare_exchange(current, winner, Ordering::AcqRel, Ordering::Relaxed) {
            Ok(_) => break,          // our candidate won (or was already winning)
            Err(actual) => current = actual, // lost the race; retry with fresh state
        }
    }
}
```

Because resolution is a commutative reduction over per-file symbol sets, the pass is embarrassingly parallel.

### 4.2 Relocation Processing: Scanning, Synthesis, and Application

Once symbols are bound, the linker must *scan* every relocation to make code-generation decisions — most importantly, which symbols need GOT entries, which calls need PLT stubs, and how large `.rela.dyn` / `.rela.plt` will be — and only then can it fix the output layout [5]. This relocation scan is computationally intensive (tens of millions of records for a Chromium-sized link [3]) but perfectly data-parallel: each relocation is independent, and the results reduce to per-symbol flags and section-size counters.

The scan drives *synthetic section creation*. Consider a call through `R_X86_64_PLT32` to an undefined function that resolves to a shared library: the linker allocates a PLT entry and a `.got.plt` slot, rewrites the relocation to target the PLT stub, and emits a `.rela.plt` record so the dynamic loader completes the binding at startup. For data, `R_X86_64_GOTPCREL` triggers a GOT entry plus a `.rela.dyn` record. The decision table is exact and target-specific, but the shape is universal:

```python
def scan_relocation(rel, sym):
    """Decide synthetic-section requirements for one relocation."""
    if rel.type == R_X86_64_PLT32 and sym.is_undefined_dynamic:
        need_plt_entry(sym)          # allocate .plt stub
        need_got_plt_slot(sym)       # allocate .got.plt slot
        emit_rela_plt(sym)           # JUMP_SLOT record for ld.so
    elif rel.type == R_X86_64_GOTPCREL and sym.is_preemptible:
        need_got_entry(sym)          # allocate .got slot
        emit_rela_dyn(sym)           # GLOB_DAT record for ld.so
    elif rel.type == R_X86_64_PC32 and sym.is_defined_local:
        pass                          # direct static computation: S + A - P
```

Final *application* is then a closed-form write per record — `S + A − P` for `R_X86_64_PC32`, and so on — parallelized across sections [1]. lld performs this scan on the main thread as part of its one-pass relocation-scanning design, which MaskRay notes is deeply tied to lld's overall architecture and difficult to restructure [5]. mold parallelizes the scan and, more importantly, overlaps computationally intensive passes with the I/O-bound copying of section data into the output file [3].

### 4.3 Identical Code Folding: Pessimistic Joins versus Optimistic Splits

Identical Code Folding (ICF) merges read-only sections that happen to have identical contents and relocations — most often, template instantiations and compiler-generated thunks duplicated across translation units. It typically shrinks C++ binaries by a few percent [4]. ICF is, formally, a *graph isomorphism* problem: two sections are equivalent when their contents match and their relocations point to pairwise-equivalent sections [7]. Two algorithmic families exist. GNU gold's **pessimistic** ICF *joins* sections that are provably identical but cannot merge mutually recursive functions, because the fixed-point computation never converges on cycles. lld and mold instead use **optimistic** ICF: start by assuming *all* candidate sections are identical, then iteratively *split* equivalence classes whenever a relocation points into different classes — a partition-refinement scheme that handles recursion correctly [7]. Within the optimistic family, lld and mold differ in their hashing strategy [5]:

- **lld** computes a lightweight message digest per section, groups sections into hash buckets, and performs *pairwise comparison* within each bucket. Expensive comparisons are lazy — many candidate pairs are distinguished cheaply, so the full digest is rarely needed. - **mold** uses a message digest that *fully describes* a section (contents plus normalized relocations), so equality of digests implies foldability with no pairwise step. The digest costs more to compute, and MaskRay's measurements show mold's approach can be slower on some workloads (e.g. ICF also carries a semantic hazard:

> **Theorem:** (ICF unsoundness). The C and C++ standards require distinct functions to have distinct addresses. ICF violates this invariant by construction; any program that compares function pointers for inequality across folded functions is miscompiled. In practice, Unix programs rarely depend on the invariant, and linkers expose `--icf=safe` variants that restrict folding to sections provably safe (e.g. those not address-taken). lld's documentation is explicit: ICF "is not an entirely sound optimization" [4]. Both linkers pay a structural tax for ICF: lld maintains `SectionBase::repl` indirection for folded sections, plus special handling for `.eh_frame` deduplication [5]. ![Identical code folding](public/thesis/ths_1789007474491_22282-2.webp)

### 4.4 Link-Time Optimization: Monolithic versus Thin LTO

Link-time optimization moves optimization across translation-unit boundaries by deferring code generation until link time. In **full (monolithic) LTO**, the linker merges all LLVM bitcode modules into a single module and runs the full optimization pipeline on it — maximal cross-module information, but serial, memory-hungry, and hostile to incremental builds.

**ThinLTO** restructures the problem into three phases [6]:

1. **Compile**: each module emits native object code *plus* a compact summary (function sizes, call-graph edges, referenced globals).
2. **Thin link**: a fast, serial pass over summaries only — no IR — computing the global call graph and deciding which functions each module may import.
3. **Parallel backends**: each module is optimized independently with imported function definitions available for inlining; backends run in parallel threads launched by the linker.

The usage model is deliberately identical to a non-LTO link (`clang -flto=thin -O2` at compile and link steps), and lld launches up to `hardware_concurrency` backend threads by default, tunable via `--thinlto-jobs=N` [6]. The design is a study in *summary-driven decomposition*: the thin link's global analysis is O(summary size) rather than O(IR size), and backend parallelism recovers most of full LTO's optimization quality at a fraction of the serial cost. Notably, ThinLTO interacts with the linker's own parallelism story — the linker's serial phases (layout, writing) now sit *after* an already-parallel optimization phase, making the linker's Amdahl fraction the binding constraint on end-to-end build time [1].

### 4.5 The Parallel Pipeline: Why "Faster Algorithms" Is Not the Story

A naive reading attributes mold's speed to better algorithms. The paper's ablation study refutes this: *no single optimization dominates*; the speedup is the cumulative effect of parallelizing *all* passes [1]. Concretely, mold parallelizes input parsing (mmap'd files, eager archive-member parsing [1]), atomic-CAS symbol resolution (§4.1), per-section relocation scanning, concurrent mark-sweep garbage collection [3], parallel ICF digest computation (5 s → 1 s on Chromium [3]), concurrent string interning, and parallel output generation overlapping I/O with computation.

lld, by contrast, parallelizes selectively: input reading and some copying are threaded, but symbol resolution, global transforms, and layout remain serial [5]. This is precisely the Amdahl trap of §3 — and it explains why lld's per-pass efficiency (its ICF algorithm is "pretty good" [5]) cannot close the gap: the serial fraction dominates at high core counts.

## 5. Empirical Results and Proofs

The mold paper reports, on large real-world programs including multi-gigabyte debug builds of Chromium and Clang [1]:

| Metric | Result |
|---|---|
| mold vs. lld link time | 2.4–16.1× faster |
| mold vs. GNU ld link time | up to 112× faster |
| Absolute time, multi-GB debug binaries | at most a few seconds, often < 1 s |
| mold ICF on Chromium vs. lld ICF | 5 s → 1 s (5×) [3] |
| ICF share of total link time (lld) | 3–15% when enabled [5] |
| ICF binary-size reduction (typical C++) | a few percent or more [4] |
| GC share of link time (lld, `-ffunction-sections`) | ~2% with debug info, ~10% without [5] |

For Chromium, the paper quantifies the problem scale: ~30,700 object files, ~24M symbols, ~27.5M sections, ~62M relocations, and ~3.4 GB of input data [3]. At this scale the complexity analysis bites: symbol resolution is Θ(*n*) hash insertions (parallelizable to Θ(*n*/*p*)), relocation scanning Θ(*r*), and optimistic ICF partition refinement is near-linear in practice because each split strictly refines the partition and the number of splits is bounded by the number of sections.

Two results deserve emphasis as *proofs of architecture* rather than mere benchmarks. First, the ablation study: disabling any single parallel pass degrades performance modestly, but no single pass accounts for the headline speedup — the signature of an Amdahl-limited system whose ceiling was the serial fraction [1]. Second, the scaling curve: mold's throughput scales nearly linearly to 8–16 cores on large links, while lld's plateaus — the empirical fingerprint of §3's theorem [1].

## 6. Limitations and Open Problems

**Soundness of ICF.** ICF remains unsound in the strict language-lawyer sense [4]. `--icf=safe` mitigates the risk, but the boundary between "safe" and "unsafe" folding (address-taken functions, exception-handling metadata, `.eh_frame` subtleties [5]) is heuristic. A formal characterization of foldable sections under the C++ object model is still missing.

**Archive and ordering semantics.** mold deliberately does not replicate every GNU ld ordering corner (`.a`/`.so` interleavings, exotic `--start-lib` interactions) [7]. For 99.9% of builds this is invisible, but it means mold is not a *proof-equivalent* replacement for GNU ld — only an empirically equivalent one. Formalizing the de-facto linker command-line semantics would be a genuine contribution.

**Determinism versus parallelism.** Parallel hash-table insertion and concurrent string merging threaten reproducible builds; mold preserves determinism by sorting and canonicalizing where needed [3], but each new parallel pass re-opens the question. As core counts grow, the tension between "bit-identical output" and "maximal parallelism" will sharpen.

**Symbol versioning and dynamic linking edge cases.** lld's recent work (e.g. LLD 20's clarification of `isExported` vs. `isPreemptible` in `.dynsym` computation) shows that dynamic-symbol policy is still being refined [5]. Version scripts, `--exclude-libs`, and preemption rules interact with ICF and GC in ways that are under-specified and tested only by folklore.

**LTO-linker co-design.** ThinLTO parallelizes optimization but leaves the linker's serial tail (layout, write) as the bottleneck [1][6]. A linker designed *around* LTO — streaming layout decisions from the thin link, overlapping backend codegen with output writing — could compress the pipeline further.

---

## 7. Conclusion

The modern ELF linker is best understood as a parallel database engine over program fragments: it ingests tens of millions of sections, symbols, and relocations; resolves a global namespace under intricate precedence rules; applies closed-form address arithmetic; folds isomorphic code; and optionally re-optimizes the whole program — all while racing the developer's patience. lld proved that careful engineering could make this fast; mold proved that *architecture* matters more than tuning, by replacing interleaved serial phases with data-parallel passes and driving the Amdahl serial fraction toward zero [1][2][3].

The deeper lesson generalizes beyond linkers. Any pipeline whose stages were sequentialized for historical convenience — not data dependence — is a candidate for the mold treatment: identify the true dependencies, express each pass as a parallel reduction, and parallelize *all* of them, because the one serial pass you leave behind becomes the ceiling. In an era of stagnant clock speeds and growing core counts, that discipline is the difference between a tool that scales and one that merely runs.
