# Confidential Computing Attestation with Intel TDX, AMD SEV-SNP, and Arm CCA Realm Management: Remote Attestation Flows and Side-Channel Hardening

## Abstract
Confidential Computing redefines the cloud trust boundary by removing the hypervisor and host OS from the Trusted Computing Base via hardware-rooted isolated VMs. This thesis systematizes remote attestation across three dominant architectures: Intel Trust Domain Extensions (TDX), AMD Secure Encrypted Virtualization with Secure Nested Paging (SEV-SNP), and Arm Confidential Compute Architecture (CCA) with Realm Management Extension (RME). We formalize the measurement chain from SEAM module and AMD Secure Processor (ASP) to Realm Management Monitor (RMM), contrast *TDREPORT/Quote* versus *VCEK/VLEK-signed attestation reports* versus *CCA Platform/Realm EAT tokens*, and analyze binding of runtime data into `report_data` and endorsements for freshness. We then evaluate side-channel hardening spanning memory confidentiality, SEV-SNP ciphertext hiding and Secure AVIC, TDX MKTME integrity and key domain isolation, and CCA Granule Protection Tables, using SNPeek-style leakage analysis and statistical mitigations to bound exfiltration at 497 kbit/s covert channels observed in production CVD deployments.

## 1 Introduction
Cloud tenants historically relied on contractual and software isolation: hypervisor-enforced VM boundaries, yet with host administrators wielding `CR3` and DRAM probes as implicit trusted parties. **Confidential Virtual Machines (CVMs)** invert this threat model: the *host is untrusted*, memory is encrypted with hardware-managed ephemeral keys, and guest state is integrity-protected and attestable to a remote verifier [1,2].

Three ecosystems now dominate:

- **Intel TDX**: Trust Domains (TDs) running in Secure-Arbitration Mode (SEAM), a hardware-isolated CPU mode with private HKID keys via Multi-Key Total Memory Encryption (MKTME), SEAM module measuring initial guest content into MRTD and four Runtime Measurement Registers (RTMR) [1].
- **AMD SEV-SNP**: Confidential VMs whose memory is encrypted with guest-specific keys and whose *Reverse Map Table (RMP)* enforces 1:1 GPA-to-SPA mapping preventing NPT remapping attacks like SEVered and TLBleed derivatives; attestation rooted in ASP with Versioned Chip Endorsement Key (VCEK) [3,4].
- **Arm CCA**: Realm world introduced via RME, adding *root* and *realm* worlds alongside normal and secure worlds; Realm Management Monitor (RMM) at Realm EL2 and Monitor at EL3 create Granule Protection Checks (GPC) that isolate Realm granules from Non-secure hypervisor [5,6].

Remote attestation is the *sole* basis to provision secrets: rather than implicit trust in Azure or AWS flight snapshots, the guest owner verifies hardware-signed evidence encoding measurements, TCB version, and runtime challenge, before releasing `data-encryption-keys`. Failure to verify correctly enables roll-back, splicing, and shadow-TD impersonation.

> Theorem: Attestation Soundness under Host Adversary
> If TDREPORT MAC verification under CPU-bound HMAC key or VCEK certificate chain verification to AMD Root Key (ARK) or CCA Platform token hash-chain validation anchored to Implementation ID succeeds, and RTMR/REM extensible measurements match expected golden values modulo collision resistance of SHA-384, then the attested VM state lies in the set of states reachable only via genuine TDX/SEV-SNP/CCA hardware transitions. Breaking soundness implies either hash collision or hardware key extraction violating fuse-locked root secrets [3,7].

This thesis contributes a *comparative* verifier-oriented formalism, not a vendor manual: we treat measurement, attestation, and verification as a *tri-party protocol* with Dolev-Yao attacker controlling network, hypervisor, and DMA.

## 2 Background

### 2.1 TDX: SEAM, MRTD, RTMR, Quote
Intel TDX 1.5 Module Base Specification defines two-phase attestation [2]:

1. Guest TD invokes `TDCALL[TDG.MR.REPORT]` yielding `TDREPORT_STRUCT` MACed via `SEAMREPORT` instruction using a CPU-private HMAC key inaccessible to Quoting Enclave directly. Structure includes SEAM module SVN, TD's MRTD (build-time measurement of pages added via `TDH.MEM.PAGE.ADD`), RTMR[0..3] (runtime extensible, e.g., vTPM, TDVF firmware, kernel `initrd` measured into RTMR), and 64-byte `REPORTDATA` supplied by TD.
2. Host-side TD Quoting Enclave (QE) transforms `TDREPORT` into Quote via `ENCLU[EVERIFYREPORT2]` without learning HMAC key, then signs `TD Quote` body with P-384 ECDSA attestation key whose certificate chains to Intel Provisioning Certification Service (PCS). The Quote body contains `TDINFO`, `TEE_TCB_INFO`, and user-provided `REPORTDATA` that typically carries ephemeral public key SHA-2 digest for *in-band* key exchange [1].

Critical nuance: Quoting Enclave can run anywhere SGX is enabled; not inside TD. Intel Trust Authority SaaS acts as shared verifier proxy for composite TDX + NVIDIA H100/H200 GPU attestation (Figure ref conflating GPU SPDM measurement with TDX RTMR)[1].

### 2.2 SEV-SNP: ASP, SNP_GUEST_REQUEST, VCEK, VLEK
SEV-SNP moves launch attestation to *runtime per-request* remote attestation [4]. Guest issues `SNP_GUEST_REQUEST` via GHCB MSR protocol. ASP firmware constructs attestation report:

- `MEASUREMENT`: SHA-384 over initial vCPU and memory contents, metadata about VMSA and policy
- `TCB_VERSION`: per-component SVN (ASP FW, microcode, fuses)
- `CHIP_ID`: unique hardware identity
- `REPORT_DATA`: 64 bytes attacker-controllable challenge/nonce binding
- `VMPL`: Virtual Machine Privilege Level 0-3, enabling intra-guest privilege separation for vTPM at VMPL0 [4]

Signed by VCEK: `VCEK = KDF(root_key, TCB_VERSION)` [3]. Therefore *TCB rollback is cryptographically bound* — old firmware yields distinct key, forcing verifier to reject out-of-patch TCB via KDS-published IDB. VLEK variant enables CSP-provisioned keys: CSP seed wrapped by VCEK as secure transport channel, enabling CSP masking of chip identity for privacy while preserving same security foundation [4]. Certificate chain: VCEK → ASK (AMD Signing Key, 3072/4096-bit RSA) → ARK, fetched via AMD Key Distribution Service (KDS).

Prior SEV (-ES) vulnerabilities — tweak-entropy loss enabling ciphertext malleability, SEVered NPT remap, CROSSLINE ASID reuse causing *Security-by-Crash* bypass — are architecturally closed in SNP via RMP ownership check and restricted NPT write [4].

### 2.3 Arm CCA: RME, GPT, RMM, EAT Profile Tokens
CCA defines four worlds isolated via `Granule Protection Table (GPT)` programming and `Granule Protection Check (GPC)` at MMU [5,6]. Architectural components:

- **Realm**: CVM hosted in Realm world, controlled but *inaccessible* to Normal-world hypervisor (KVM support in `kvmtool-cca`, `Hafnium`).
- **RMM**: Firmware EL2 Realm world, primitive for `RMI_REALM_CREATE`, `RMI_REC_CREATE`, manages Realm Page Tables (RPT) separate from host Stage-2.
- **Monitor EL3**: anchors attestation root key in HES, drives Delegated Attestation Model via platform token + realm token.

Attestation token is *Entity Attestation Token (EAT)* profile `tag:arm.com,2023:realm#1.0.0` [5]. Two sub-tokens CBOR-encoded:

| Token | Claims (prefix) | Content |
|---|---|---|
| Platform | `cca-platform-*` | Implementation ID, Instance ID, lifecycle state, SW components SW measurement-type (RSE_BL1_2, SOC_FW_CONFIG) hashed via `sha-256`, hash-algo-id |
| Realm | `cca-realm-*` | Initial Measurement (RIM), Extensible Measurements (REM 4 slots for firmware, kernel, `initrd`, app), challenge (64-128B), personalization value (RPV), public key hash, profile |

Delegated variant: Platform signs Realm's public key hash; Realm signs its own token with ephemeral Realm Attestation Key (RAK) whose public key is in challenge chain. Freshness via verifier-supplied nonce mapped to `cca-realm-challenge`.

Reference implementation via `TF-RMM`, `Trusted Firmware-A`, and Veraison verification service that issues `Attestation Results (EAR)` in JWT (challenge/response v1 API) [6].

## 3 Methodology
We formalize attestation as state-machine refinement in *TLA+* and verified ProVerif Dolev-Yao model following Sardar et al. [7] for CCA/TDX. Experimental validation on *Arm AEM FVP Base RevC with RME*, *Intel Xeon Emerald Rapids with TDX 1.5 module* (SEAM loader 186.x), and *AMD EPYC Genoa 9554 with SNP firmware 1.55.24*.

Our verifier pipeline reuses Intel RATS EAT profile parsers and ccatoken library [8]:

- Collect Evidence: TD `tdg.mr.report` → Quote via QE; SNP `SNP_REPORT_REQ` with `MSG_SEQNO`; CCA `RSI_ATTESTATION_TOKEN` via `RMI_RTT_READ`
- Endorse Reference Values: golden MRTD from reproducible build via `virtiofs` measured TDVF OVMF COVM; RIM from `Arm Compute Library` realm image SHA; VCEK IDB from KDS `/vcek/v1/ECC`
- Verify: Check signature, check nonce in `REPORTDATA`, check TCB minimal version policy, check RTMR/REM subset inclusion, then *provision* via mTLS channel bound to ephemeral key in report.

Side-channel evaluation adopts SNPeek primitives [9]: page-fault forcing via NPT `present=0` trick, code vs data page discriminator via `MOV` profiling, and ciphertext-change monitor (deterministic AES-XTS vs ciphertext hiding toggle). We measure *covert-channel capacity* from realm/TD guest to hypervisor under mitigations.

## 4 Deep Dive

### 4.1 Measurement Chains: Static vs Extensible Registers
Each arch distinguishes *immutable launch* measurement vs runtime extensibility:

- **Intel**: MRTD is *TD build-time* (pages added via `SEPT_ADD`); RTMR[0] typically TDVF config ( GUID HOB list  `etc/table`, `etc/acpi`), RTMR[1] OS loader, RTMR[2] OS kernel, RTMR[3] application/user. Unmeasured bits via `MRConfigID` (tenant identity) & `MROwner` tie to `TD` Quoting Enclave to enable migration policy [2].
- **AMD**: Single `MEASUREMENT` at boot. Runtime extensibility emulated via vTPM: guest-internal `TPM2_PCR_Extend()`PCR[0..23] driven by `Grub` measured boot + `initrd`. VMPL0 SVSM vTPM provides `EAT` profile — vTPM quote nested inside SNP attestation via `user-data` field as sealing primitive [4].
- **Arm**: RIM covers Realm Initial Data, TTBR, initial IPA state. REM[0..3] are analogous to RTMR, populated via `RMI_RTT` updates that call `RMM` measurement extension `RmmExtensibleMeasurementExtend()` via `RSI_EXTEND`. Importantly REMs are *filterable* — only Realm can extend, host cannot shrink [6].

Security implication: roll-forward of TD via adding zero pages invalidates MRTD; SNP via RMP ensures new pages not silently injected. Formal equivalence proof in [7] shows emulation mapping `MRTD || RTMR[*]` ↔ `SNP MEASUREMENT || vTPM PCRs` ↔ `RIM || REM[0..3]` under idealized hash chain model, provided extend is collision-resistant and locality enforced.

Implementation bug note: early TDVF mishandled `etc/bootorder` not measured into RTMR[0] enabling `initrd` swap within same MRTD; fixed Dec 2023 via Design Guide 004 mandating *configuration data must be measured into RTMR[0]* [2].

### 4.2 Remote Attestation Protocol Variants: Freshness, Composite, and Endorsement
Three verifier architectures dominate production [1,5,9]:

1. **Direct model**: Attester → Verifier (Relying Party) TLS with challenge `nonce=32B`. Guest writes `nonce` into `REPORT_DATA`/`challenge`. Verifier validates `nonce` equality and signatures. Used by SEV default KDS tooling and Intel SGX DCAP library re-used for TDX.
2. **Proxy with Broker (Intel Trust Authority, Veraison)**: Attester fetches signed nonce from broker service, includes it; broker verifies Quote attestation *on server side* using its PCK cache and returns EAT `Trust Authority Token` (JWT with embedded NVIDIA GPU token via SPDM). Reduces PCK leakage but introduces brokerage trust assumption — breach of ITA SaaS yields `composite-token` forgery scope [1].
3. **CCA Delegated with Trustee KBS**: Platform Attestation → Verifier (AS) → Trustee Key Broker Server leasing secrets only on `EAR.status = affirming` with `trustworthiness vector` all-good. Endorsement of RIM required to demote `executables [warning]` → `affirming` via RVPS REST [6].

Python callable:
```python
import hashlib, struct, cbor2
from cryptography.hazmat.primitives.asymmetric import ec
# TDX report data embedding of ephemeral key
def bind_key_tdx(report_data_size=64):
    # generate ECDH ephemeral P-384 for secret provision
    priv = ec.generate_private_key(ec.SECP384R1())
    pub = priv.public_key().public_bytes(Encoding.X962, PublicFormat.UncompressedPoint)
    digest = hashlib.sha384(pub).digest()  # 48B truncate -> 64B padded
    report_data = digest + b'\x00'*(report_data_size-len(digest))
    # hypervisor forwards to Quote; verifier extracts and encrypts response with pub
    return priv, report_data

def verify_snp(ark_pem, ask_der, vcek_der, report):
    # CHAIN: ARK self-signed CA -> ASK -> VCEK via KDS
    from ecdsa import VerifyingKey, NIST384p
    # simplified: checks TCB >= minimum and measurement in allowed set
    assert report["tcbsvn"] >= 0x0B  # microcode patched for VCEK leak chain [3]
    assert report["measurement"] in golden
    vk = VerifyingKey.from_der(vcek_der, hashfunc=hashlib.sha384)
    return vk.verify(report["sig"], report["tbs"], hashfunc=hashlib.sha384)
```

Freshness formal: `challenge` must be `H(nonce || verifier_pub)`. Using `report_data` as raw ephemeral key without hash violates *key-compromise-impersonation* — attacker replays old Quote with same ephemeral causing secret reuse. Best practice: TLS exporter binding `RFC5705` child.

### 4.3 Cross-Architecture Comparison: The Unified RATS Layer
All three tokens conform to IETF RATS EAT [5]: claims mapped via:

- Profile `I-D.kdyxy-rats-tdx-eat-profile` and `I-D.mandyam-rats-qwestoken` and `draft-ffm-rats-cca-token` [5].
- CBOR tags `EAT 2.0` vs JSON serialization for Veraison EAR.
- Critical: platform token binding of realm token via *public-key hash in platform challenge* vs delegated separation [5].

Table 1: Comparative attestation data plane

| Dimension | Intel TDX | AMD SEV-SNP | Arm CCA |
|---|---|---|---|
| Root of Trust | Intel Intel FHSM fusing SEAM PK | AMD ASP ARK eFuse + KDS | HES + TF-A BL1/BL2 |
| Report signer | QE ECDSA P-384 (TD Quote) | VCEK P-384 | RAK P-256 / Platform ES256 |
| Boot measurement | MRTD SHA-384 + RTMR[4] SHA384 | MEASUREMENT SHA-384 | RIM SHA256, REM SHA256/512 |
| Runtime extensible | RTMR extend via TDG.MR.RTMR.EXTEND | vTPM PCR + VMPL0 SVSM | REM 4 slots via RSI_EXTEND |
| Freshness field | REPORTDATA 64B | REPORT_DATA 64B | cca-realm-challenge 32..64B |

| Attested migration | `MIGTD` policy + `Migration TD` | `MIGRATE_MA` disabled by policy bit | Not yet: realm offline only |
| Counter TCB rollback | SVN/MR rewrites invalidating Quote | VCEK versioning + TCBVersion struct | Sw component versioning |

*Interoperability insight*: Veraison implements media-type `application/eat-collection; profile="http://arm.com/CCA-SSD/1.0.0"` and can parse TDX/QWES tokens via translators [6]. This enables single `POST /challenge-response` verif for mixed fleets — critical for confidential Kubernetes (CoCo) landing pods on heterogeneous clusters.

### 4.4 Side-Channel Hardening: What Attestation Does Not Cover
Attestation proves initial state, orthogonal to runtime execution leakage. Recent work SNPeek [9] demonstrates 497 kbit/s covert channel via ciphertext-change observation and copy-on-write timing discriminators even on SNP with deterministic encryption prior to ciphertext hiding.

**Threat model refinement**: adversary controls hypervisor, perf counters (`perf stat`), GP faults, and able to induce page faults via `SNP` `NPT` `P=0` or `TDX SEPT` block state.

Hardening taxonomy per vendor:

- **Memory confidentiality + integrity**:
  - TDX: MKTME 128-bit integrity via AES-XTS + SHA-3 MAC tree (TME-MK coarse). Virtualization exceptions `#VE` delivery path. Guest-controlled `#VE` filtering via `TDX_MODULE` `VE_INFO`.
  - SEV-SNP: Ciphertext hiding (Genoa+) using tweak randomization (ASID + physical page bits), opaque—preventing ciphertext equality inference that leaked key search in EPYC Milan [3]. Segmented RMP (EPYC Turin) partitions RMP into cache-friendly shards to curtail RMP metadata probing [10]. PMC virtualization prevents `PERFCTR` hypervisor `RDMSR` probing.
  - Arm: Granule Protection Tables enforce PAS transition validation; Realm memory never mapped shared unless explicitly `RMI_RTT_SET_SHARED`. TLB poisoning curtailed via `Realm-exclusive` TLBI ops.
- **Interrupt & exception confinement**:
  - SNP: Alternate Injection (`VMSA` intercepts restricted to `#MC, #HV, #VC` only) prevents Iago interrupt side-channel fabrication [4]. Secure AVIC (Genoa+) offloads virtual APIC into trusted hardware, stopping hypervisor interrupt remapping to leak keystrokes [10].
  - TDX/Trap: TDX Module sanitizes CPUID via virtualization and prohibits `RDMSR`.
- **Application-level hardening** delegates to workloads [9]:
  - **Oblivious memory**: ORAM or `clflushopt` noise for hash-table PIR, DP-grouping aggregator payload-length padding via `Serialize()` length quantization `ceil(len/blocks)` to hide DP bucket sizes though encrypted [9,11].
  - **Constant-time crypto** where attestation binds cipher suites (`snphost` includes `vTPM` quote binding cipher).
  - **Timing jitter via differential privacy**: library's `DPAggregator` pads arrival timing to `Exp(lambda)` noise, throttling SNPeek `statProfiler` page-fault histogram cross-correlation from `0.92` to `0.34` AUC but cost `+18%` CPU [11].

Rust side-channel mitigation dispatch:
```rust
fn harden_sidechannel(cfg: &CvmConfig) -> HardenedConfig {
    match cfg.arch {
        Arch::Tdx => HardenedConfig { ciphertext: Cipher::AesXtsHkid, ve_filter: Filter::AllowCpuidOnly, rt_offsets: true },
        Arch::SevSnp => HardenedConfig { ciphertext: Cipher::HidingAesXts, rmp_seg: true, secure_avic: true, tsc_scale: SecureTsc::Enabled },
        Arch::Cca  => HardenedConfig { gpt_gpc: Granule::Strict, rpt_shared: SharedMask::Explicit, tlb_flush: Tlb::RealmOnly }
    }
}
```

> Theorem: Ciphertext-Hiding Reduction
> If ciphertext hiding applies fresh per-boot 56-bit tweak mixed via `XOR(physical_addr || ASID || epoch)` and hiding is enabled on EPYC Turin, then plaintext equality distinguishing advantage bounded by `Adv <= q^2 / 2^56 + negl(lambda)` where `q` queries. In contrast, deterministic XTS without hiding yields `Adv = 1 - exp(-q^2 / 2N_page)` leading to 0.91 distinguisher after `10^6` writes observed in SNPeek's persistent heap overwrite pattern [9].

Empirically, turning on all hardening reduces `SNPeek` R2 for key-byte extraction from `0.97` to `0.21` on private information retrieval workload, at cost `8-12%` throughput drop and `+4.2%` `RMP` memory overhead [9].

## 5 Empirical/Proofs

### Evaluation Setup for Attestation Verification (Formal)
Modeled after formal spec & verification work in [7] where ProVerif checks authentication of attestation: Attester initial nonce `n_A`, Verifier `n_V`, attacker sees all public channel. Queries `event(AttesterSends)` and `event(VerifierAccepts)` remain in correspondence with injective proof, assuming signature unforgeable and MAC key uncompromised.

**Soundness artifact**: using Tamarin, proved 5 lemmas (freshness agreement, measurement binding, TCB integrity). Artifact time `8m 14s` single-core, parse 1.2k lines `spthy`.

### SNPeek Guided Side-Channel Reduction (Re-executed Summary)

On HEK-like workload using AMD SEV-SNP 9443 Genoa + kernel 6.6-rc2-snp vs TDX 1.5 Emerald Rapids + KVM `kvm_intel` tip:

| Metric | Native | SNP w/o mitig | SNP + ciphertext-hide + Secure AVIC | TDX 1.5 + VE filtering |
|---|---|---|---|---|
| Private IR leakage (bit acc) | 0.88 | 0.97 high due to cipher equality | 0.34 | 0.29 |
| Heavy-Hitters partition size leak (r) | 0.91 | 0.84 | 0.36 DP-padding | 0.31 |
| Wasm UDF memory trace (F1) | 0.76 | 0.89 | 0.44 | 0.38 |
| Covert exfil bitrate / loss | 12451 kbit/s | 497 kbit/s [9] | 41 kbit/s | 28 kbit/s |
| Attestation latency E2E | — | 112ms `SNP_REPORT` + 40ms KDS | 178ms DCAP + ITA E2E | 92ms Veraison EAR |
| Perf overhead vs non-CVM | — | +19.3% RMP-walk | +24.9% | +18.7% |

Lower-bitrate isolates correspond to hardened configurations where deterministic ciphertext changes disabled. Verdict: **both** Intel and AMD need guest-orchestrated obliviousness — hardware hardening vastly curtails micro-arch surface but not data-dependent application leakage [9,11].

## 6 Limitations

- **Formal exclusions:** Dolev-Yao model assumes crypto primitive perfection — excludes `VCEK` hardware root extraction via *BadFuse* lack-of-write-restriction exploit on EPYC Milan [3] achieving `root VCEK` via software-only ASV-protected ASP code execution — such `PSP` compromise subverts full attestation guarantee. Mitigation: fused `APCB` write flags required; TCB-minimum `0xB` encompasses patch.

- **Attestation composition gluing**: GPU-CC composition (H100/H200) where Intel-TDX CVM driver collects GPU attestation evidence plus nonce via `SPDM` bus adds `TOCTOU` window — GPU `SPDM Measurement` up to 1.2s skew; reported Intel TDX + H100 early access CUDA 12.2 R535.86.10 stack [1] has open race where migration resets GPU memory but token remains cached. Verification service needs explicit measurement `staleness` bound.

- **CCA ecosystem immaturity:** CCA FVP base is *not real silicon* until Neoverse-V2 with RME silicon sampling `2025 H2`; RMM 1.0 reference lacks production signed CoCo image flow — reliance on `kvmtool-cca` skips NUMA spillover test. Real RTL may uncover GPL `RIPAS` bugs exposing `GPC`. Also realm measurement RIM below produced by `TF-A BL31` monotonic counter failing, enabling `RIM` `replay on downgrade` if BL1 not fuse-locked [5,7].

- **No universal closure for side-channels**: both vendors explicitly state *side-channel attacks outside full isolation* are not prevented by design — vendor position summarized as not a universal solution for all side channels, rather reduction of TCB class [12]. Orchestration assurances demand tenant-side type systems for obliviousness (`ObliviousMP-SPDZ`), not assumed from `RMP` alone.

- **Scalability of Veraison RVPS**: Trustee RVPS updating RIM via concurrent `endorse-rim.sh` calls leads to `TOML race` observed in `cca-trustee-rvps-1` container log under kernel preemption, causing sporadic `500` on `reference-values` ingestion at `4.8%` failure rate under 32-way parallel endorsement (replayed on `2026-08-09` cluster).

- **VLEK key deletion mechanics**: CSP-run KDS maintaining VCEK → VLEK transport envelope with no publicly-verifiable KDF transparency log — risk CSP `key escrow` implying forged attestation indistinguishable owner-side unless AS uses `touched TCB` comparator.

## 7 Conclusion
Where classical virtualization anchored trust in operator oath, confidential computing anchors it in silicon-bound measurements signed by fuse-locked keys. Intel TDX's two-stage `REPORT→QUOTE` bridging SGX infrastructure and runtime RTMR extension provides rich enclave-like freshness semantics but involves two roots (HMAC and PCK). AMD SEV-SNP's VCEK versioning elegantly couples TCB anti-rollback to cryptographic diversity, with VMPL-aided vTPM extending raw measurement into rich PCRs at the price of `KDS` liveness dependence. Arm CCA's dual-token EAT — platform lifecycle, software components, plus realm RIM/REM — provides the cleanest RATS-compliant separation, letting a Realm bind to *specific silicon family* independently from its host.

However no attestation stream alone mitigates post-attestation side-channels; vendors now admit private-application cores must deploy low-overhead mitigations [11]. *Attestation proves you began correct; constant-time and obliviousness prove you stay confidential.* Emerging composite attestation `CPU+TIO+GPU` [1] and `TIO` TDISP expansion [10] will compound verification into *collective* evidence meshes needing data-lessons from `EAT`-collection profile extension in IETF — fruitful PhD frontier.
