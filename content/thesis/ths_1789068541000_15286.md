# Oblivious RAM: The Square-Root Construction, Path ORAM, Stash Analysis, and Lower Bounds on Bandwidth Overhead

## Abstract

Oblivious RAM (ORAM) compiles any RAM program into one whose observable memory access pattern is independent of its secret inputs. We give a unified treatment of the field's three foundational pillars. First, the square-root construction of Goldreich and Ostrovsky, which stores $N$ blocks on a server under a secret permutation plus a $\sqrt{N}$-sized client buffer, achieving $O(\sqrt{N})$ amortized bandwidth overhead. Second, the hierarchical construction and its modern modular formulation via oblivious hashing, reducing overhead to $O(\log^3 N)$ and then to $O(\log^2 N)$. Third, Path ORAM, which organizes the server store as a binary tree of encrypted buckets and achieves $O(\log N)$ bandwidth per access with only $O(\log N)$ client storage, and whose security hinges on a delicate stash analysis: we present the $\infty$-ORAM subtree-overflow characterization and the exponential tail bound $\Pr[\mathrm{st} > R] \le 14 \cdot 0.6002^R$ for bucket size $Z=4$. Finally we survey bandwidth lower bounds, from the classical $\Omega(\log N)$ bound in the balls-and-bins model to the Boyle–Naor critique and the Larsen–Nielsen $\Omega(\log N)$ bound for general online ORAM, which together establish Path ORAM's near-optimality.

## 1 Introduction

Encryption alone does not hide *how* memory is touched. An adversary that observes the sequence of physical addresses read or written by a program — even when every block's content is ciphertext — can infer secret-dependent control flow, as in binary search over a classified array or lookups in a medical database [1]. *Oblivious RAM*, introduced by Goldreich and Ostrovsky in the context of software protection, is the cryptographic primitive that solves this problem: it compiles any RAM program $M$ into an oblivious program $M'$ whose access pattern reveals nothing about the data beyond, at most, the running time [1].

Formally, an ORAM consists of a client (trusted, with small private storage) and a server (untrusted, honest-but-curious) holding $N$ encrypted data blocks of $B$ bits each. The client translates each logical access $\mathrm{op}(a, v)$ — a read or write of block $a$ — into a randomized sequence of physical accesses. Security demands that for any two equal-length logical access sequences, the resulting physical access patterns be computationally (or statistically) indistinguishable. The price of this guarantee is the *bandwidth overhead*: the multiplicative factor by which the number of physical blocks transferred exceeds the number of logical accesses.

Three decades of research drove this overhead from $O(\sqrt{N})$ to $O(\log N)$, and lower-bound theory now tells us $\Omega(\log N)$ is essentially inherent for online ORAM [2]. This thesis reconstructs that arc: the square-root construction, the hierarchical refinement, the Path ORAM revolution, the stash analysis behind its security theorem, and the lower bounds that close the story.

## 2 Background

### 2.1 The threat model and the definition

Consider a RAM program executing $M$ logical operations on $N$ memory cells. The server observes the *physical access pattern*: the sequence of addresses read from and written to remote storage. Without ORAM, this pattern is a function of the program's secret inputs. A canonical example is binary search: the first probe is always the middle, but subsequent probes reveal whether the key lies above or below, leaking a comparison bit per step.

> **Definition (ORAM security).** An ORAM scheme is *secure* if for every probabilistic polynomial-time adversary and any two logical access sequences $\mathbf{y}, \mathbf{y}'$ of equal length, the distributions of the physical access patterns $\mathcal{A}(\mathbf{y})$ and $\mathcal{A}(\mathbf{y}')$ are computationally indistinguishable.

Crucially, the bound allows the adversary to see the *timing and count* of operations — ORAM hides only which addresses are touched. The client keeps only a small private memory (a stash plus a position map, made recursive if needed).

### 2.2 The trivial solutions

Two extremes frame the design space:

1. **Scan everything.** For each logical access, read and rewrite the entire memory. Overhead $\Theta(N)$: perfectly oblivious, perfectly useless.
2. **Encrypt and hope.** Encrypt each block under a semantically secure scheme but access addresses in the clear. Overhead $O(1)$, but the access pattern is fully revealed — no security at all.

Goldreich and Ostrovsky's insight was that between these extremes lies a hierarchy of constructions trading client storage against amortized and worst-case overhead [1].

## 4 Deep Dive

### 4.1 The square-root construction: ORAM begins

The simplest ORAM with sublinear overhead works as follows [1]. The client holds a *buffer* of $\sqrt{N}$ blocks. The server holds $N + \sqrt{N}$ blocks: the $N$ real blocks placed under a *secret random permutation* $\pi$ known only to the client, plus $\sqrt{N}$ dummy slots.

To access logical block $a$:

1. **Scan the buffer.** If $a$ is in the client buffer, fetch it locally; otherwise, fetch the server slot $\pi(a)$ (padding the interaction with a dummy read so the server cannot tell which case occurred). Either way, the physical pattern is one full buffer scan plus one server read — *independent of $a$*.
2. **Cache the result.** Place the (possibly updated) block $a$ into the client buffer.
3. **Reshuffle every $\sqrt{N}$ accesses.** Once the buffer fills, the client downloads the entire server array plus buffer, obliviously sorts the $N + \sqrt{N}$ blocks under a fresh permutation $\pi'$, and writes them back, emptying the buffer.

The reshuffle costs $O(N)$ blocks moved but is amortized over $\sqrt{N}$ accesses, giving an amortized overhead of $O(\sqrt{N})$ per access; the worst-case per-access cost is also $O(\sqrt{N})$ if the reshuffle is *deamortized* by spreading it across the epoch [1]. The construction generalizes to an $N^{1/k}$ hierarchy of buffers, yielding $O(N^{1/k})$ overhead for any constant $k$ — but the asymptotically interesting refinement is the *hierarchical* construction of Section 4.2.

A recent fine-grained result shows the square-root construction is not merely historically interesting but *optimal* within its natural class: Drucker and Hoover proved that any one-round balls-in-bins ORAM without block duplication requires either $\Omega(\sqrt{N})$ bandwidth or $\Omega(\sqrt{N})$ client memory [5]. The square-root scheme is therefore the best possible one-round construction.

```python
# Sketch: square-root ORAM access (amortized O(sqrt(N)) overhead)
def access(op, addr, val, state):
    # state = (buffer, perm, server, counter)
    block = scan_buffer(state.buffer, addr)          # O(sqrt(N)) scan
    if block is None:
        block = server.read(state.perm[addr])       # one server read
    else:
        server.read(dummy_slot())                   # indistinguishable dummy
    if op == "write":
        block = val
    state.buffer[addr] = block                      # cache it
    state.counter += 1
    if state.counter == int(sqrt(N)):
        oblivious_reshuffle(state)                  # O(N) every sqrt(N) accesses
    return block
```

### 4.2 The hierarchical construction and oblivious hashing

Goldreich and Ostrovsky's second construction arranges the server store as a hierarchy of $L + 1$ levels, where level $i$ is a hash table of capacity $2^i$ (so $L = \lceil \log_2 N \rceil$) [1]. Each level $i$ is keyed by a pseudorandom function $F_{k_i}$. The protocol:

1. To access block $a$, probe level $0, 1, \dots, L$ in order, searching for $a$ under $F_{k_i}(a)$ at each level (with dummy probes at levels already known not to contain $a$).
2. Insert the retrieved block into level $0$.
3. Whenever level $i$ fills, *merge* it into level $i+1$ via an oblivious sort, re-keying with a fresh PRF key.

Because level $i$ is rebuilt once every $2^i$ accesses at cost $O(2^i \log 2^i)$, amortized overhead sums to $O(\log^3 N)$ with the oblivious sort dominating, probes adding another $O(\log N)$ [1].

Modern work recasts this construction modularly: *any* oblivious hashing scheme (a hashing scheme whose Build and Lookup procedures have data-independent access patterns) yields a hierarchical ORAM as a black box [6]. Plugging in better hashing — cuckoo hashing with a small shared stash, or the oblivious two-tier hashing of Chan et al. — reduces the bucket sizes and the rebuild cost, driving hierarchical ORAM down to $O(\log^2 N)$ amortized overhead with $O(1)$ client storage [6]. The hierarchical line thus evolved from $O(\log^3 N)$ to $O(\log^2 N)$, but its amortized nature and periodic expensive rebuilds motivated a fundamentally different, *worst-case*-efficient design: Path ORAM.

### 4.3 Path ORAM: a tree, a stash, and a position map

Path ORAM, introduced by Stefanov, van Dijk, Shi, Fletcher, Ren, Yu, and Devadas [7][3], is the simplest ORAM with logarithmic *worst-case* overhead, and it displaced hierarchical schemes in nearly all practical deployments (secure processors, oblivious databases).

The server stores a **binary tree** of height $L = \lceil \log_2 N \rceil - 1$. Each node holds a *bucket* of $Z$ blocks (real or encrypted dummy). The client stores:

- a **position map** $\mathrm{position}[a] = x$: the random leaf label (path) currently assigned to block $a$;
- a **stash**: a small local buffer of blocks that could not be placed back into the tree.

The protocol maintains one invariant:

> **Invariant.** If block $a$ is mapped to leaf $x$, then $a$ is stored either somewhere on path $\mathcal{P}(x)$ (root to leaf $x$) or in the stash.

$\mathrm{Access}(\mathrm{op}, a, v)$ proceeds in five steps [7]:

1. Look up $x \leftarrow \mathrm{position}[a]$.
2. **Read path**: fetch all $Z(L+1)$ blocks on $\mathcal{P}(x)$; decrypt; add real blocks to the stash.
3. If $\mathrm{op} = \mathrm{read}$, return the block; if write, update it in the stash.
4. **Remap**: assign $\mathrm{position}[a] \leftarrow x'$ for a fresh uniform random leaf $x'$.
5. **Write back**: greedily evict blocks from the stash onto $\mathcal{P}(x)$, pushing each block as deep as possible toward its own mapped leaf; fill leftover bucket slots with encrypted dummies.

Security is simple: the physical pattern of every access is *one uniformly random root-to-leaf path*, regardless of the logical sequence, because each block is remapped to a fresh random leaf immediately after being touched [7]. This *unlinkability* means the whole security proof reduces to one question: can the stash overflow? If the stash grows without bound, the client storage assumption collapses. Answering it is the subject of Section 4.4.

The position map itself costs $O(N)$ client storage, which is fixed by **recursion**: store the position map in a smaller ORAM on the server, whose position map is stored in yet another ORAM, and so on. With block size $B = \Omega(\log N)$, a constant number of recursion levels suffices, yielding $O(\log^2 N)$ bandwidth with $O(1)$ client storage, and $O(\log N)$ when $B = \Omega(\log^2 N)$ [7][3].

### 4.4 Stash analysis: the $\infty$-ORAM argument

The stash analysis of Stefanov et al. is the technical heart of Path ORAM [3]. It abstracts the tree as $\infty$-ORAM — buckets of infinite capacity, so nothing overflows — then asks, *post hoc*, how many blocks would have exceeded capacity $Z$ in each bucket. A greedy postprocessing algorithm $G_Z$ pushes blocks as deep as possible, mirroring write-back; real Path ORAM's stash usage equals the overflow count of $G_Z$ on $\infty$-ORAM.

> **Theorem (Subtree overflow characterization [3]).** The stash usage $\mathrm{st}_Z$ of postprocessed $\infty$-ORAM exceeds $R$ if and only if there exists a subtree $T$ of the ORAM tree with usage $u(T) > n(T)\cdot Z + R$, where $n(T)$ is the number of buckets in $T$.

*Proof sketch.* ($\Leftarrow$) A subtree $T$ with $n(T)$ buckets holds at most $n(T)\cdot Z$ blocks after greedy postprocessing, since each block can only be assigned to an ancestor bucket; the excess $> R$ blocks must land in the stash. ($\Rightarrow$) Take the maximal subtree whose buckets are all exactly full ($Z$ blocks) after postprocessing; any block outside it can reach a non-full ancestor and never overflows, so all stash blocks originate inside it, giving the inequality. ∎

The second key lemma identifies the *worst-case access pattern*:

> **Lemma (Worst-case address pattern [3]).** Fix a subtree $T$ and $R$. Over all address sequences touching at most $N$ distinct blocks, $\Pr[u(T) > n(T)\cdot Z + R]$ is maximized when every address appears exactly once (e.g., a round-robin scan $1, 2, \dots, N, 1, 2, \dots$).

Under this pattern the leaf labels are independent and uniform, so $u(T)$ is a sum of independent Bernoulli variables with mean $N \cdot n(T)/2^L$, and a Chernoff bound applies. Combining the subtree characterization with a union bound over all subtrees yields the main result:

> **Theorem (Exponential stash tail [3]).** For bucket size $Z = 4$ and any address sequence over at most $N$ distinct blocks, $\Pr[\mathrm{st} > R] \le 14 \cdot (0.6002)^R$.

Failure probability decays *exponentially* in stash size and is *independent of $N$*: for $Z = 4$, $R \approx 89$ blocks suffice for $\Pr[\mathrm{overflow}] < 2^{-80}$ [3]. This is why Path ORAM needs only $O(\lambda)$ client storage — the stash is a constant-sized shock absorber, not a second memory.

### 4.5 Lower bounds on bandwidth overhead

How low can the overhead go? The classical answer, already in Goldreich and Ostrovsky [1], is an $\Omega(\log N)$ lower bound — but its scope was narrower than folklore suggested. Boyle and Naor showed that the GO96 argument applies only in the **balls-and-bins model**, where the ORAM treats data blocks as opaque indivisible balls and may not inspect their contents; moreover, they proved that any *general* lower bound for **offline** ORAM (where the whole access sequence is known in advance) would imply breakthrough lower bounds on sorting circuit size, far beyond current complexity-theoretic techniques [2].

The breakthrough for the practically relevant **online** setting came from Larsen and Nielsen [2]: adapting the *information transfer* technique of Pǎtraşcu and Demaine from cell-probe data-structure lower bounds, they proved an $\Omega(\log N)$ lower bound on the combined read/write overhead of any online ORAM — with no balls-and-bins restriction and even under computational security. Hubáček et al. later strengthened this to rule out even *hiding the boundaries* between input operations: obfuscating where one logical access ends and the next begins cannot beat $\Omega(\log N)$ either [2].

| Model | Security | Lower bound | Construction matching it |
|---|---|---|---|
| Balls-and-bins, perfect/statistical | Perfect | $\Omega(\log N)$ [1] | Hierarchical GO96 variants |
| Balls-and-bins, one-round | Any | $\Omega(\sqrt{N})$ bandwidth *or* memory [5] | Square-root ORAM (optimal) |
| General online | Computational | $\Omega(\log N)$ [2] | Path ORAM / OptORAMa ($O(\log N)$) |
| Offline, general | Computational | Open (implies sorting-circuit bounds) [2] | Boyle–Naor $O(\log N)$ offline |

The table's message is crisp: Path ORAM's $O(\log N)$ bandwidth overhead is asymptotically optimal for online ORAM, and the square-root construction is optimal among one-round schemes. The remaining frontier — general offline lower bounds — is entangled with fundamental open problems in circuit complexity [4].

## 5 Empirical Results and Proofs

The theory above is complemented by large-scale simulation in the Path ORAM literature [3]. We summarize the reported measurements (reproduced here as the paper's empirical claims, not new experiments):

1. **Stash occupancy distribution.** Over $\approx 2.5 \times 10^{11}$ accesses under the worst-case round-robin pattern, persistent stash occupancy (excluding the transient fetched path) stays in the low tens of blocks for $N = 2^{20}$, and the empirical tail matches the exponential $\infty$-ORAM prediction [3].
2. **$N$-independence.** The stash size required for $\Pr[\mathrm{overflow}] < 2^{-\lambda}$ is flat in $N$ (verified for $\lambda \le 26$ and extrapolated beyond): for $Z = 4$ and $\lambda = 80$, $R \approx 89$ blocks suffice regardless of whether the database holds a million or a billion blocks [3]. This is the property that makes Path ORAM deployable — client storage does not grow with the outsourced data.
3. **Bandwidth measurements.** With $Z = 4$ and $4\,\mathrm{KB}$ blocks, each access moves $\approx 2 \cdot Z \cdot (L+1)$ blocks (read path plus write-back): at $N = 2^{20}$ this is roughly $640\,\mathrm{KB}$ per $4\,\mathrm{KB}$ logical access, a $\approx 160\times$ concrete overhead that shrinks relatively as $B$ grows [7]. The path dominates; recursion adds only a small constant factor at typical parameters.
4. **Proof mechanization.** The $\infty$-ORAM argument has been re-verified in subsequent work (e.g., the resizable-ORAM analysis reproducing the $1.42 \cdot 0.5566^R$ tail for $Z = 6$ under variable tree shapes), confirming the analysis is robust to tree-shape perturbations [8].

> **Proof (Security of Path ORAM, sketch [7]).** Consider the hybrid in which every access reads a uniformly random path. By the remap step, the path read at access $t$ equals the leaf assigned at the *previous* access to the same block — a fresh uniform leaf independent of all history — so the real and hybrid patterns are identically distributed. Conditioned on stash non-overflow (negligible probability by the tail bound), correctness follows from the invariant: a block mapped to $x$ is either on $\mathcal{P}(x)$ (hence fetched) or in the stash (hence found). Semantic security of the encryption hides block contents and distinguishes real from dummy blocks. ∎

## 6 Limitations

Caveats that matter for deployment:

- **Honest-but-curious server.** Path ORAM as presented provides no integrity against a *malicious* server that returns wrong blocks, forks the tree, or drops writes. Malicious-secure variants (e.g., Ring ORAM with Merkle trees and MACs) add authentication at extra bandwidth cost.
- **Timing and volume leakage.** ORAM hides *which* addresses are accessed, not *how many* accesses occur or their timing. Constant-rate padding is required if the access count itself is sensitive.
- **The position map recursion constant.** Recursive Path ORAM's $O(\log^2 N)$ overhead carries a real constant: each logical access triggers $O(\log N / \log B)$ recursive ORAM accesses, each moving a full path. For small blocks this dominates; large blocks ($B = \Omega(\log^2 N)$) are effectively required for the clean $O(\log N)$ figure [7][3].
- **Client storage is small but trusted and persistent.** The stash and position map must live in trusted memory (e.g., an SGX enclave or secure processor); spilling them to the untrusted server breaks the model [8].
- **Lower bounds assume online access.** The $\Omega(\log N)$ bound of Larsen–Nielsen applies to online ORAM; exotic models — server-side computation (homomorphic encryption), multiple non-colluding servers, or differentially private relaxations — can and do beat it [8].

## 7 Conclusion

From the square-root construction's $O(\sqrt{N})$ to Path ORAM's $O(\log N)$, the history of oblivious RAM is the story of bandwidth overhead squeezed against a lower bound that took twenty years to prove in full generality. Three ideas carry the field: (i) *reshuffling* — hiding the present by periodically re-randomizing the past [1]; (ii) *path-invariant storage* — tying each block to a random leaf and touching exactly one full path per access, which makes obliviousness syntactic rather than amortized [7]; and (iii) *the stash tail* — the $\infty$-ORAM subtree analysis proving a constant-sized client buffer fails with probability exponentially small in its size, independent of $N$ [3]. The lower-bound arc — the balls-and-bins bound, the Boyle–Naor delineation of its limits, Larsen and Nielsen's general online bound and its strengthening to boundary-hiding adversaries [2] — certifies that Path ORAM's logarithmic overhead is essentially the end of the road for online ORAM. What remains is engineering: smaller constants, malicious security, and the tantalizing offline frontier where progress would ripple into circuit complexity itself.
