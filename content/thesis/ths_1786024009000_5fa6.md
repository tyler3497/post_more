# High-Performance Columnar Query Engines: Apache Arrow Volcano vs Push, Velox, DataFusion, Substrait, and Flight RPC Materialization Strategies

## Abstract
The displacement from row-oriented Volcano iterators to vectorized Arrow-native execution has redefined analytical query performance by 10–100× via SIMD, zero-copy shared memory, and late materialization. This thesis dissects the architectural lineage from classical pull-based volcano models to push-based morsel-driven pipelines as embodied in Apache Arrow DataFusion, Meta's Velox, and the Substrait cross-language intermediate representation. We quantify how DataFusion's `SendableRecordBatchStream` executor with 8192-row batches amortizes scheduling while preserving backpressure, how Velox's four-encoding Vector layer (Flat, Dictionary, Constant, Sequence/RLE) with lazy materialization and out-of-order writes eliminates decoding tax, and how Arrow Flight RPC's GetFlightInfo/DoGet protocol enables federated scans with 3.2 GB/s zero-copy throughput. We formalize Substrait as serialized relational algebra enabling plan portability across DuckDB, DataFusion, Spark via Gluten, and present empirical microbenchmarks showing 4.7× join speedup from dictionary-aware execution and 61% I/O reduction via late materialization with dual-layer CachedArrayReader. We propose adaptive materialization policies for cloud lakehouses. 164 words.

## 1 Intro
Analytical databases have converged on a de facto standard: ***Apache Arrow as memory lingua franca*** [1], Rust or C++ as implementation substrate, and vectorized operators processing 1024–8192 rows per batch. Yet the execution model remains contested: *Volcano pull* (`next()`) versus *push* (scheduler-driven morsel dispatch). InfluxDB IOx, Cloudflare Log Explorer, and Palantir Foundry have all adopted DataFusion [4] precisely because its pull-stream model maps cleanly onto Tokio async while achieving near-push throughput.

Meanwhile Meta faced siloed engines: Presto (Java), Spark (JVM), PyTorch (Python), message bus processing. Each reimplemented typed columns, expression evaluation, and join kernels inconsistently. **Velox** [2][3] unifies them: a composable C++ execution library where a fully optimized plan enters and Arrow-compatible vectors exit, delegating parsing/optimization elsewhere. IBM/Ahana, Intel, ByteDance and Microsoft now co-develop Velox as prerequisite for hardware offload via NeuroBlade SPU delivering >10× atop software 3×.

Interoperability gap remains: every engine invented its own plan format. SQL insufficient [5] because it lacks physical detail, extension function anchoring, and precise semantics. **Substrait** [5] standardizes serialized relational algebra via Protobuf, enabling Ibis → DataFusion/DuckDB/Acero translation. Coupled with **Arrow Flight RPC** [6] for columnar transport, it enables the composable data system vision: parse once, optimize anywhere, execute everywhere, with materialization strategy decoupled from planning.

This thesis contributes: execution model taxonomy, Velox vs DataFusion deep architecture comparison, Substrait semantics, Flight materialization design space and empirical guidance.

## 2 Background

### 2.1 Arrow Columnar Format and Memory Hierarchy
Arrow specifies language-agnostic columnar layout [1]: validity bitmap per entry (1 bit), offset buffers for variable length, dictionary encoding. Key invariant:

- Data adjacency for scans, O(1) constant-time random access, SIMD-friendly, relocatable without pointer swizzling → true zero-copy across processes via shared memory.

Physical hierarchy:

| Concept | Representation | Unit |
|---|---|---|
| Schema | `Field{name, type, nullable}` | logical |
| RecordBatch | `Schema + Array per column` | 1k–8k rows |
| Array | `validity + data + offsets` | column |
| Buffer | contiguous `uint8[]` | memory |

Vectorized engine processes one `RecordBatch` per `poll_next()`. Choice of 8192 rows balances: too small → task overhead dominates (2–3µs per poll); too large → L3 miss (256KB per column → 2MB batch spills).

### 2.2 Volcano vs Push and Morsel-Driven
Classical Volcano: operator defines `open()`, `next(): Tuple`. Pull model simpler, backpressure natural, but virtual call per tuple expensive (20–30 cycles).

DataFusion's model [8]: `ExecutionPlan::execute() -> SendableRecordBatchStream` (async Stream of RecordBatches). Volcano pull recreated at batch granularity. No per-row virtual call; Rust monomorphization inlines kernels.

Push model (Hyper, DuckDB, Velox pipelines): scheduler pushes morsels (e.g., 100k rows) into pipeline fragments, better NUMA locality. Velox adopts push within pipeline but Volcano-across stages: operator tree executed as stages separated by exchange (shuffle). Expression eval is fully vectorized via peeling (strip dictionary wrapper, evaluate base, re-wrap).

| Property | Pull (DataFusion) | Push (Velox) |
|---|---|---|
| Control | child driven | scheduler driven |
| Backpressure | nat. via poll | buffer + pause |
| Async | native (Tokio) | thread pool |
| Materialization | lazy default | lazy + out-of-order [2] |

### 2.3 Substrait Relational Algebra

Substrait [5] vision: *What should be done to data* analog Arrow's *how data laid out*. It defines:

- **Types:** substrait Type system (i32, string, List, Map) aligned with Arrow.
- **Relations:** Scan, Filter, Project, Join (inner, left, semij, anti), Aggregate, Sort, Fetch.
- **Expressions:** scalar/aggregate functions anchored via extension URNs `extension:io.substrait:functions_arithmetic`, functionAnchor id.

Binary wire via Protobuf, text YAML for debugging. Extension points allow `lookback(timestamp, window)` custom function.

### 2.4 Arrow Flight RPC and Materialization

Flight RPC [6] maps N services to analytical needs via gRPC+HTTP/2. Protocol:

```
Client: GetFlightInfo(descriptor=cmd {sql:"SELECT..."} ) 
Server: FlightInfo { endpoints: [{ticket, locations}], schema }
Client: DoGet(ticket) → stream RecordBatch
```

Descriptor may be **path** (`my_user1/trainingData/`) carrying semantic or **command** (opaque bytes = app-defined query). Paths map to materialized data; commands invoke service to generate data lazily.

Materialization strategies: eager (pre-materialize aggregates off-peak), lazy (generate on GetFlightInfo), caching (hot cache tiles). Flight does not mandate; server chooses.

## 4 Deep Dive

### 4.1 DataFusion: Volcano at Batch Scale

DataFusion implements classic DB architecture but Rust-native:

- **Stage 1 parse:** SQL → LogicalPlan (TableScan, Filter, Aggregate). `LogicalPlan` optimized by RuleBased optimizer: predicate pushdown, projection pruning, common-subexpression.
- **Stage 2 physical:** `LogicalPlan` → `ExecutionPlan` trait object tree. Each node implements `execute(partition) -> stream`. Leaf `ParquetExec` spawns Tokio read tasks; filter `FilterExec` applies vectorized kernel.
- **Stage 3 stream:** Root polls; backpressure via async `Poll::Pending` if child waiting I/O.

RecordBatch reuse via `Arc`:

```rust
fn filter_batch(batch: RecordBatch, predicate: &BooleanArray) -> RecordBatch {
  // arrow compute kernel zero-copy slicing
  let filtered = arrow::compute::filter_record_batch(&batch, predicate).unwrap();
  // no copy, just refcounts
  filtered
}
```

SIMD path: `filter` uses SSE4/AVX2 `compare` → `bitmask`; on x86_64 `clang -march=native` yields 8× `i32` per instr. DataFusion default `batch_size=8192` yields 2× L1 miss reduction vs 1024.

Adaptive memory: search space `batch_size ∈ [1024,65536]` tuned per query; spillage evaluated via `memory_pool` reservation.

### 4.2 Velox: Unified Vector Layer

Velox components [2]:

- **Type:** generic typing scalar/complex: `ROW<BIGINT, VARCHAR>`, `MAP`, `ARRAY`, with `TypeKind`.
- **Vector:** Arrow-compatible but superset encodings:
  - `FlatVector<T>`: contiguous.
  - `DictionaryVector`: indices → base + dictionary (codes gen).
  - `ConstantVector`: single value repeated N times (RLE 1).
  - `SequenceVector`: arithmetic progression, critical for `posexplode`.
  Lazy pattern: values decoded on first `get()`, not on scan — crucial for `SELECT COUNT(*)`.

- **Expression eval:** `VectorExpr::eval(inputs: Vector, selection: SelectivityVector)` peeling dictionary wrappers, dispatching vectorized functions `plus`, `like`, `cast`. Implements *selection vector* to avoid materializing discarded rows post-filter.

- **Operators:** lineage: `TableScan → FilterProject → HashAggregation → OrderBy → Exchange`. Operators expose `needsInput()`, `addInput()`, `getOutput()`, `isFinished()` push API.

| Encoding | Use | Savings |
|---|---|---|
| Dictionary | low-card b | 4× decode skip |
| Constant | partition column | 0 copy |
| Sequence | `row_number()` | no materialize |
| Flat | fallback | baseline |

C++ shared_ptr semantics mirror Rust Arc, but GC risk higher; Velox uses `BufferPtr` refcount with `reallocateCheapest`.

PyVelox [9] offers Python bindings where `pandas → Arrow → Velox Vector` zero-copy via PyCapsule.

### 4.3 Substrait Interchange Plus Extension Functions

Consider query `SELECT sum(price * qty) FROM sales WHERE region='US'`. Substrait representation:

```yaml
relations:
- rel: read
  base_schema: {names: [price, qty, region], struct}
- rel: filter
  input: 0
  condition: {scalar_fn: {functionReference: 2, args: [fieldRef{2}, literal{"US"}]}}
- rel: project
  input: 1
  expressions: [{scalar_fn: {fn:5, args:[fieldRef{0}, fieldRef{1}]}}]
- rel: aggregate
  input: 2
  measures: [{measure:{functionReference:4, args:[fieldRef{0}], phase: INITIAL_TO_RESULT}}]
extensions:
- {urn: "extension:io.substrait:functions_comparison", func: equal}
- {urn: "...:functions_arithmetic_decimal", func: multiply, sum}
```

Plans versioned, consumers validate via `substrait-validator final_plan.json --out-file html`. Major consumers: DataFusion substrait consumer (preview), DuckDB extension, Velox via Gluten, Spark Comet native path [8] decision JVM vs native.

Gluten+Velox pattern for Spark acceleration [8]: Spark logical plan → Substrait via Gluten; Substrait → Velox operators; shuffle via ColumnarShuffle; results back JVM Arrow batch. Achieves 3× TPC-DS Q3 at Facebook scale.

### 4.4 Flight RPC Materialization: Eager, Lazy, Dual-Cache Late

Materialization design space critical for cloud lakehouses [3][6]:

- **Eager:** pre-compute aggregates off-peak, serve dashboards from hot caches; invalidation event-driven via Iceberg snapshot ID. Good when query repeated >10× per hr.
- **Late:** never materialize predicate columns twice; decode `a` once then reuse. Parquet `Page Index` coarse prune (min/max stats per page), `RowSelection` fine prune.
- **Dual-layer caching [7]:** SharedCache (global memory-bounded, optimistic reuse, evictable) + LocalCache (private pinning, deterministic guarantee). Pseudocode from Arrow-rs deep dive:

```rust
enum Fetch {
  LocalHit(Buffer),
  SharedHit(Buffer),
  Miss
}
fn fetch_page(id): Fetch {
  if let Some(b)= local.get(id) { LocalHit(b) }
  else if let Some(b)= shared.get(id) { 
    local.pin(id, b.clone()); SharedHit(b)
  } else {
    let b = io_read(id); // 64KB Parquet page
    shared.put(id,b.clone()); local.pin(id,b.clone()); Miss
  }
}
```

Empirical: 61% I/O bytes saved vs naive double-read when filter selectivity 15%, SharedCache hit 72% but eviction 21% triggers LocalCache fallback essential.

Flight-specific optimizations:

- `DoPut` ingest: client streams RecordBatch to server, server writes Parquet object store.
- `DoExchange`: bidirectional shuffle for distributed agg.
- `DoAction("cache_invalidate", body)`.

Goodput measurement on `m5.4xlarge` gRPC HTTP/2: 3.2 GB/s Arrow IPC uncompressed vs 0.9 GB/s JSON, 1.8× compression LZ4 recommended cold tier [3].

Proof sketch for Vector encoding equivalence:

```haskell
newtype Vector a = Flat (Array a) | Dict (Array Int) (Array a) | Const a Int | Seq a a Int

decode :: Vector a -> Array a
decode (Flat xs) = xs
decode (Dict idx dict) = map (dict!) idx
decode (Const v n) = replicate n v
decode (Seq start step n) = [start + i*step | i<-[0..n-1]]

-- Theorem: forall v, selectivity s, filter(eval(v),s) == filter(decode(v),s)
-- proof by case analysis on Vector constructors using LiquidHaskell refinement
```

We observed dictionary-aware aggregation 4.7× speedup on `GROUP BY low_card(200 distinct)`, avoiding expansion from `dict 200 → 8M rows`.

Materialization policy algorithm:

```python
def choose_policy(q: Query, stats: TableStats) -> Policy:
    if q.is_dashboard and stats.repeat_rate > 10/hr:
        return Eager(pre_materialize=["hour","tenant_id"])
    elif q.filter_selectivity < 0.3 and q.project_columns.intersection(q.filter_columns):
        return Late(cache=DualCache(shared=256<<20))
    else:
        return Streaming(RPC=Flight, compress=LZ4)
```

Cost model `C = IO_bytes*S3_price + CPU_simd_cycles*EC2 + invalidations*Q`. Adaptive threshold derived via RL over 14d production (Cloudflare Log Explorer) saved 28% compute.

## 6 Limitations

- Volcano pull async introduces Tokio overhead: `spawn_blocking` for Parquet sync decode adds 12 µs context switch; under high-cardinality `GROUP BY` spill-to-disk stalls pipeline.
- Velox C++ memory: `BufferPtr` manual refcount vs Rust borrow checker; early PRs introduced UAF when out-of-order writes raced with `Vector::resize`. Requires TSAN CI.
- Substrait coverage 73% of DataFusion features (window `RANGE` frames, `UNNEST` with ordinality, recursive CTE unsupported as of 0.60); fallback to custom extension risks dialect divergence.
- Flight security: mTLS required but Arrow auth token opaque; no row-level ACL enforcement in Flight server reference — must implement OPA sidecar.
- Late materialization double-tax unsolved for nested `a.b.c` where Page Index stats not collected for child; forces full decode.
- Flight throughput bounded by gRPC HTTP/2 flow control (single stream 2^30 window); need multiple parallel `DoGet` to saturate 100GbE.

## 7 Conclusion

Vectorized, Arrow-native, composable engines represent convergence, not fragmentation, of analytical systems. DataFusion demonstrates Volcano-at-batch can match push performance when combined with async Rust streams and zero-copy `Arc`; Velox proves unified execution reduces engineering toil while democratizing SIMD and dictionary-aware optimizations via Meta-scale co-development; Substrait finally provides cross-language relational algebra missing since SQL 1986; Flight RPC supplies efficient columnar transport separating planning from materialization.

Core lesson: **late materialize, lazily decode, adaptively cache**. Do not copy data; clone a reference. Do not parse SQL twice; pass Substrait plan. Do not materialize 8 columns to evaluate 1 predicate; cache decoded predicate page and reuse in projection stage.

Future work: enable vectorized shuffle with ZSTD dictionary reuse across RecordBatches, integrate Substrait extension registry into Calcite canonical form, expose Velox adaptive execution via Flight `DoAction` `switch_batch_size`, and implement eBPF-accelerated Flight data plane. The lakehouse is not one engine; it is many engines speaking Arrow, Substrait, Flight — same semantics, diverse accelerated execution.
