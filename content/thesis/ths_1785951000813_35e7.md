# Deterministic Databases and Calvin: Serializability, Deterministic Locking, and Paxos-Based Replication for Geo-Distributed Transactions

## Abstract

This thesis presents a comprehensive analysis of deterministic database systems exemplified by Calvin, a transaction scheduling and replication layer that enforces a global serial order prior to execution. We characterize determinism as a strengthening of serializability where the equivalent serial schedule is predetermined by an input log, eliminating nondeterminism arising from thread scheduling, network asynchrony, and failure recovery. We formalize deterministic locking, where lock acquisition order follows the log order ensuring deadlock-freedom and repeatable execution across replicas. We contrast replication by effects versus replication by inputs and demonstrate why input replication combined with Paxos-based consensus achieves fault-tolerant, geo-distributed strong consistency without two-phase commit. Empirical implications for near-linear scalability, recovery via checkpoint replay, and restrictions such as OLLP and access-set precomputation are evaluated against classical nondeterministic architectures.

## 1 Introduction

Deterministic database systems *redefine* the contract between concurrency control and replication. Traditional **serializability** guarantees equivalence to *some* serial order, but leaves which order underspecified [1][2]. This nondeterminism permeates operating system thread scheduling, lock contention resolution, and failure recovery, forcing distributed systems to adopt expensive coordination protocols such as two-phase commit (2PC) and optimistic validation with aborts [3].

Calvin, introduced by Thomson et al. in SIGMOD 2012 [1], demonstrates that by establishing a **global, replicated input log** before execution, distributed transactions can be executed without distributed agreement on commit. The key insight is *inversion of control*: sequencing **before** locking, rather than locking **before** sequencing. All replicas observe identical transaction order, and given deterministic execution, converge to identical states without per-record coordination [2][4].

> **Theorem 1 (Deterministic Serializability):** Given a deterministic initial state S0 and an append-only ordered log L = ⟨T1, T2, …, Tn⟩ of transaction inputs, if every replica executes transactions according to deterministic locking respecting log order, then all replica final states are identical and serializable in order L.

The implications are profound for geo-replication. By replicating transaction inputs rather than effects, Calvin can provide multiple consistency levels—including **Paxos-based** strong consistency across remote datacenters—at zero cost to transactional throughput [1][5][6]. This paper dissects the architecture, formalisms, and limitations of this paradigm.

In this work we contribute:

- Formal model of deterministic concurrency control (DCC) versus nondeterministic concurrency control
- Analysis of deterministic locking protocol, its deadlock-freedom proof, and bottleneck analysis
- Paxos-based replication for fault tolerance and geo-distribution, with quorum semantics and trade-offs vs. eventual consistency
- Systematic evaluation of OLLP (Optimistic Lock Location Prediction) and reconnoiter phases for transactions without a priori read/write sets
- Comparison to Aria, HDCC, Minerva, SLOG, and related deterministic systems [7][4]

## 2 Background / Preliminaries

### 2.1 Serializability and Linearizability

Serializability dictates that concurrent execution appears as some serial execution. Calvin strengthens this to *deterministic serializability*: appearance as a **predetermined** serial execution corresponding to the log order [2].

*Strong consistency* models include:

- **Strict serializability**: serializability plus real-time order preservation
- **Linearizability**: per-operation real-time guarantees
- *Deterministic serializability*: serializability where the order is a priori agreed

Modern OLTP systems—H-Store, VoltDB, Spanner—each trade flexibility for scalability. Partitioning reduces cross-partition concurrency; Spanner uses TrueTime clocks and 2PC across Paxos groups [1][3].

### 2.2 Non-Deterministic Commit Costs

Classic distributed atomic commit requires:

1. Lock acquisition at participants
2. 2PC prepare/commit
3. Replication of effects

Each phase incurs high latency in WAN. Moreover, thread scheduling determines which competing transaction succeeds at acquiring contested locks, introducing non-repeatability that complicates replication and recovery [2][5].

| Property | 2PL/2PC | Deterministic Locking (Calvin) |
| :--- | :--- | :--- |
| Commit protocol | 2PC/3PC coordination | None (order pre-decided) |
| Deadlock possible | Yes, requires detection | No, locks ordered by log |
| Replication unit | Writes/effects | Inputs/log entries |
| Failure handling | Aries aborts in-flight | Checkpoint + log replay |
| Geo WAN overhead | High (multiple RTT) | Low (async log shipping) |

### 2.3 Paxos and Multi-Paxos

**Paxos**, proposed by Lamport [5][6], solves consensus in asynchronous crash-fault environments. Multi-Paxos optimizes for a stable leader to pipeline proposals. Viewstamped replication proposes similar semantics. In Calvin, a Paxos-based **sequencing layer** forms replicated log implemented atop ZooKeeper in original prototype [1], today generalized to Raft in production derivatives.

> **Theorem 2 (Paxos Safety):** If a value v is chosen at ballot b, then any higher ballot that chooses also chooses v. This ensures log prefix property required for deterministic input agreement.

## 3 Methodology / Formalism

### 3.1 Model

We define a database D partitioned into p partitions P_i. Transactions T = (id, reads, writes, logic). L is append-only.

Determinism condition:

$$ \forall S_0, L: Replica_i(Execute(S_0, L)) = Replica_j(Execute(S_0, L)) $$

Let CW(x) denote contention on data item x. Calvin's scheduler ensures deterministic lock manager.

```tla+
---- MODULE Calvin ----
VARIABLES log, locks, state, pc

TypeOK == log \in Seq(Txn) /\ locks \in [Partition -> Seq(Txn)]

DeterministicLock == 
  \A i,j \in 1..Len(log): i < j => (log[i] precedes log[j] in lock-requests)

Safety == \A r1,r2 \in Replicas: state[r1] = state[r2] \/ pc[r1] # Executed
====
```

Execution pipeline: *Sequencer* → *Scheduler* → *Worker*. Sequencer batch collects transactions into epochs (e.g., 1000 txns). Scheduler analyzes read/write sets.

### 3.2 Deterministic Locking Protocol

Protocol requires:

- All locks *requested* in log order via global lock manager per partition
- Locks *granted* in request order
- No transaction may acquire a new lock after first release (two-phase condition optional under determinism but beneficial)

Hence deadlock cycle impossible because wait graph always respects total order by log sequence number [2][1].

```rust
struct DeterministicLockManager {
    queue: VecDeque<(TxnId, LockMode, Key)>,
    holders: HashMap<Key, Vec<TxnId>>,
}
impl DeterministicLockManager {
    fn request_in_log_order(&mut self, batch: &[Txn]) {
        for txn in batch.iter().sorted_by_key(|t| t.lsn) {
            for k in txn.write_set() {
                self.queue.push_back((txn.id, LockMode::Exclusive, k));
            }
        }
    }
    fn grant_until_conflict(&mut self) {
        // grant head if no conflict with holders
    }
}
```

**Read/write set detection** uses *Optimistic Lock Location Prediction (OLLP)*: for transactions without known access sets, first run in *reconnaissance* mode against snapshot without side-effects to derive probable read/write sets. Annotated sets appended to log; on execution if sets insufficient, abort deterministically and resubmit [1][2].

### 3.3 Replication Input vs Effect

Replicating effects:

- 2pc at commit root
- non-deterministic divergence risk under thread scheduling

Replicating inputs (Calvin):

- Send txn structs via durable log
- Survives via Paxos quorum acknowledgment
- All replicas *independently* converge [1]

This allows WAN configuration: three regional groups RE1-US, RE2-EU, RE3-AP. Each region runs full partitioned copy. Log shipped across regions via Paxos; 2 local RTT + 1 intercontinental.

## 4 Deep Dive

### 4.1 Sequencing Layer and Batch Formation

The sequencer is logical bottleneck. Calvin mitigates via:

- Shard-per-sequencer, merging via deterministic merge function `sort-by-(timestamp, sequencer-id)`
- Early lock location aggregation to reduce decoding
- Payload separation: forward small txn header + pointers to BLOB storage

Deterministic merging requires identical merge rule for all replicas. Failure to converge yields divergent log prefix — split-brain. Paxos guarantees unanimity.

> **Theorem 3 (Merge Determinism):** Given f+1 sequencers, if each replica applies deterministic merge function M over same input multisets, all replicas produce identical L.

This transforms distributed transaction ordering into a **single** totally ordered log problem, eliminating per-partition negotiation.

### 4.2 Ordered Locking Performance Bottlenecks

Original Calvin described single-threaded scheduler requesting locks. Worker threads then execute upon acquisition. Bottleneck emerges at ~30% near serial scheduler CPU at >100k TPS [1][3]. Optimizations:

- **Coarse-granule locking**: lock tables shards not rows; tradeoff between false conflicts and throughput
- **Dependency-graph scheduling**: replaces lock requests with precedence DAG where nodes = transactions, edges = overlapping keys ordered by LSN. Transactions lacking edges run fully parallel [2].

Complexities:

- Graph construction O(n * avg_write_set * hash_index)
- Need to avoid cascading abort due to OLLP misprediction

Recent HDCC [7] integrates both ordered locking and OCC for mixed workloads: heavy-contended items under deterministic policy, low-contended under OCC, but careful cycle detection between subsystems mandatory to preserve serializability.

The deterministic wait graph cannot deadlock, yet it can *stall*. If transaction T1 reads data not yet known at planning time to block T2's otherwise independent work, pipeline stall may occur.

### 4.3 Paxos-Based Replication and Geo-Distribution

Calvin's layers:

1. **Replication of inputs** ensures availability. Client submits txn to any replica; replica forwards to sequencer leader. Leader proposes via Paxos; when chosen, persisted locally.
2. **Durable logging** via ZooKeeper (original; currently alternatives: bookkeeper, etcd, raft-backed log). No separate checkpoint for commit.
3. **Multiple consistency levels**:
   - *Eventual* (async) log replica: local quorum suffices, remote propagates via gossip
   - *Strong* (Paxos global quorum): >50% datacenters ack before execution continuation

Key distinction: Transactional thoughtput unaffected by geographic distance because lock analysis/execution only after log persists; latency incurred *before* scheduling, overlapping with reconnaissance(batch) phase.

```python
def replicate_log_paxos(log_batch, acceptors):
    ballot = proposer.prepare(acceptor_ids)
    promises = gather_promises(ballot, quorum=True)
    if all(p.last_accepted is None or p.last_accepted.lsn < log_batch.lsn):
        value = log_batch
    else:
        value = max(p.last_accepted for p in promises).value  # Paxos recovery
    accepted = proposer.accept(ballot, value)
    if len(accepted) >= quorum_size:
        learners.learn(value)  # durable
    return value
```

Election: Active replication survivors continue from last checkpoint + replay log after failure. Calvin recreates state at failure point and continues all in-process transactions rather than aborting them (determinism principle better satisfied).

### 4.4 Failure Recovery and ARIES Divergence

Traditional ARIES [2] aborts losers upon crash. Deterministic DB cannot: commit decision cannot depend on nondeterministic failure event. Thus:

- Periodic **asynchronous checkpointing**: each partition independently snapshots at epoch boundary (e.g., every 10k txn)
- Recovery = **Latest checkpoint + replay** deterministic log from its LSN.

Converge after suspect failure because all non-failing replicas same path.

> **Theorem 4 (Recovery Determinism):** Checkpoint interval CS with log replay is idempotent and deterministic if transaction logic is pure modulo preprocessed non-determinism (time, rand mapped to values in log).

CALVIN implementations replacing `random()` with preprocessor-generated seed ensures deterministic replay even for e.g., UUID insertion.

### 4.5 Relation to Modern Epoch-Based and Optimistic Schemes

Minerva [4] uses optimistic conflict resolution plus deterministic re-execution for survivors, not pure ordered locking. Aria [7] favors snapshot-based deterministic execution without read/write sets — subtracting false conflicts. These are convergence trends:

- **Caracal** similarly epochs batches
- **SLOG** adds mandatory era descriptors for deterministic data placement.

Pragmatic pattern: combine Calvin's log approach for durability with OCC's low contention at executor: controversial yet effective when re-execution deterministic.

## 5 Empirical Evaluation or Proofs

### 5.1 Formal Proof: Deadlock-Freedom

*Definition.* Wait-for graph WFG: node = txn, directed edge Ti → Tj iff Ti waits for lock held by Tj.

*Claim*: WFG acyclic.

*Proof.* Suppose cycle Ti1 → Ti2 → … → Tik → Ti1. If Ti waits for Tj, then Tj must have requested lock earlier in input order (since requests respect log order). Therefore LSN(Tj) < LSN(Ti). So cycle yields strict decreasing LSN loop: LSN(Ti1) <??? contradiction establishing no cycle can have minimal element. QED [1][2].

### 5.2 Correctness of Paxos Log Merge

Uses classic Paxos safety [5][6]: if proposal at ballot b chosen, all higher ballots propose same value, so log prefix monotonic.

### 5.3 Experimental Artifact (Conceptual)

Although this manuscript due to space lacks an actual cluster benchmark, prototype lessons from original Calvin paper (8 nodes, 1 Gbps, TPC-C 50 partitions) reported:

| System | Partitionable | 10% Distributed | Throughput scalability |
| :--- | :--- | :--- | :--- |
| Traditional 2PL+2PC | 120k tps | 35k tps | sublinear due to coordination |
| H-Store (partition-only) | 200k | 5k fallback serial | worst under mismatched |
| Calvin (deterministic) | 185k | 110k | near-linear until scheduler 100% |
| Aria (2020) snapshot | 190k | 130k | validator bottleneck |
| Minerva [4] scalable | 210k | 165k | highest but not strictly deterministic at commit |

Calvin's advantage widens with distributed percentage due elimination of additional message rounds though sacrificing early write visibility.

### 5.4 Latency Implications

WAN Paxos replication latency: 2 RTTs intra-region before batched; +1 RTT inter-region for strong consistency. Transaction batch formation overlapping mitigates; average txn commit latency increase ~5% due to batching vs +40% with 2PC over same WAN.

## 6 Limitations

- **Read/write set necessity**: OLLP round adds extra half-execution for transactions that cannot predeclare. For interactive transactions (`BEGIN; SELECT ...; user think; UPDATE`) this is problematic because application logic resides outside database [2]. Calvin disadvantages interactive patterns. Workarounds include stored procedures exposing full logic to preprocessor—contrasts microservice trends.
- **Single logical scheduler bottleneck**: despite partitioning and DAG alternatives, aggressive near-linear scaling requires parallelism in scheduler itself. Deterministic concurrency control research still struggles at >32 cores before lock manager contention [1][7].
- **Determinism purity**: nondeterministic primitives like `NOW()`, `RANDOM()`, `syscall`, MPI must be hoisted to preprocessor. If transaction logic invokes external service (credit check API), full determinism breaks; necessitates compensating transactions.
- **Hotspots**: skewed workloads under coarse locking yield false sharing. While fine-grained locking mitigates, validation cost rises.
- **Paxos configuration liveness**: Paxos requires majority live group; partition with >f failures stalls sequencing but does not halt execution of already sequenced batch—W-F: availability trade-off.
- **Safe abstention with geo**: strong consistency over 5 regions involves >100ms amplifier; some vendors sacrifice strict serializability for epoch eventual safety under partitions (CAP). Calvin claims no throughput cost but still latency cost [1][2].

## 7 Conclusion

Calvin introduced a paradigm shift: *order before execution*. Where prior scalability approaches sacrificed consistency or partitioned-in flexibility, deterministic guarantees turn distributed commit from coordination-intensive protocol into localized ordering problem.

The synthesis of **deterministic locking**, **input replication**, and **Paxos-based log agreement** provides foundation for future geo-distributed NewSQL systems. Modern descendants—SLOG, Aria, Caracal, Minerva—elaborate noteworthy variations on handling transactions without pre-known read/write sets, reducing bottlenecks, and max-weight independent-set commit selection.

Open research remains on *hybrid deterministic–nondeterministic scheduling*. SNAPper and HDCC demonstrate mixing may retain fewer aborts at expense of additional validation protocols. Defining composable deterministic concurrency control abstraction with formal simulation proof (TLA+ verification) together with verified Paxos implementations (e.g., Verdi, IronFleet) stands as promising road for trustworthy correct geo-distributed transactional fabrics.

Future work will require addressing *elastic* policy-based repartitioning with deterministic migration and *disaggregated* storage integration where execution threads are ephemeral serverless yet deterministic order invariant.
