# Billion-Scale Approximate Nearest Neighbor Search: HNSW Graphs, DiskANN's Vamana Index, and SPANN Partition-Based Retrieval

## Abstract

## 1. Introduction

Vector search is the *join operator* of the embedding era. Recommendation engines, duplicate detection pipelines, and — most consequentially — **retrieval-augmented generation (RAG)** systems all reduce, at their core, to the same primitive: given a query vector **q** ∈ ℝ^d, return the **k** database vectors minimizing a distance metric (typically Euclidean or maximum inner product). When Lewis et al. built the original RAG system over a dense FAISS index of 21 million Wikipedia chunks [6], the index fit comfortably in RAM. Production RAG corpora today, however, span hundreds of millions to billions of chunks, while embedding dimensions have grown from 128 (SIFT descriptors) to 768–4096 (dense neural encoders). At this scale the index *cannot* fit in DRAM: one billion 768-dimensional float32 vectors occupy ~3 TB. The field therefore had to solve ANN search under the constraint that most of the index lives on disk, while queries must still be answered in single-digit milliseconds with recall above 90% [2][3].

Three complementary answers emerged. **HNSW** [1] showed that a probabilistic hierarchical graph — a multi-resolution navigable small world — achieves logarithmic-time search scaling in memory with tunable recall. **DiskANN** [2] introduced the **Vamana** graph, with its α-RNG pruning rule and beam search, to build graphs so sparse and well-connected that serving them from SSD requires only ~100 random 4 KB reads per query — enabling 5,000+ QPS at <3 ms latency and >95% 1-recall@1 on the SIFT1B benchmark with a single 64 GB machine. **SPANN** [3] revived the inverted index for the disk era: hierarchical balanced clustering creates posting lists balanced enough that the centroid directory fits in memory while lists live on SSD, and a query-aware pruning scheme limits each query to a handful of disk accesses — reaching 90% recall@1 in ~1 ms, roughly **2× faster** than DiskANN at the same recall and memory budget.

This thesis presents these systems as a coherent design space rather than a horse race. Section 2 reviews the metric-search background: product quantization, IVF partitioning, and navigable small worlds. Section 3 formalizes the methodology — the problem definition, the evaluation metrics (recall, latency, QPS, memory footprint), and the complexity framework. Section 4 is the deep dive into HNSW, Vamana/DiskANN, SPANN, IVF-PQ hybrids, and beam search dynamics. Section 5 synthesizes the published empirical evidence, Section 6 discusses limitations, and Section 7 concludes with implications for RAG vector databases.

## 2. Background

### 2.1 Approximation as necessity

Exact nearest neighbor search in high dimensions is defeated by the *curse of dimensionality*: no index can guarantee both sublinear query time and sub-quadratic space for exact retrieval under standard assumptions [10]. ANN search relaxes correctness: an algorithm with recall **R@k** returns, on average, a fraction R of the true k nearest neighbors. Recall, not correctness, is the currency — a 95%-recall system serving 5,000 QPS is strictly more useful than an exact system serving 5.

### 2.2 Product quantization and IVFADC

Before graphs conquered ANN, compression did. **Product quantization (PQ)** [5] decomposes ℝ^d into a Cartesian product of m low-dimensional subspaces, each quantized by a 256-centroid codebook. A vector becomes m bytes; distances are estimated by **asymmetric distance computation (ADC)** — O(m) lookup-table operations instead of O(d) multiply-adds. Combined with an **inverted file (IVF)** coarse quantizer, IVF-PQ achieves 8–16 bytes per vector and scans only the nprobe nearest cells. Johnson et al.'s FAISS [4] indexed a billion vectors on four GPUs in under 12 hours, establishing the baseline DiskANN later attacked: on SIFT1B, FAISS's IVFOADC+G+P plateaued near ~50% 1-recall@1 [2].

### 2.3 Navigable small worlds

Kleinberg's *navigable small world* (NSW) model showed that graphs with long-range links sampled from the right distribution support greedy routing in O(log² n) hops. Malkov's NSW graph heuristic adapted this to metric search: insert each vector by greedy-walking from random seeds, connecting to the nearest candidates found. The key property is that insertion and search are the *same* procedure, and greedy descent approximates Delaunay-like local connectivity. HNSW then added hierarchy to bound node degree: long edges live on upper layers, short edges on lower layers, separating distance scales exactly the way a skip list separates rank scales [1].

### 2.4 Memory hierarchy as the design constraint

The billion-scale regime is fundamentally an *I/O* problem. DRAM holds ~10² GB at dollars-per-GB; NVMe SSD holds TBs at cents-per-GB but serves ~10–100 µs random 4 KB reads. Any index whose query path touches more than a few hundred pages cannot meet single-digit-millisecond latency — the constraint DiskANN and SPANN each navigate differently [2][3].

## 3. Methodology

### 3.1 Problem formulation

We consider a database **X** = {x₁, …, xₙ} ⊂ ℝ^d with n up to 10⁹ and a query set **Q** = {q₁, …, qₜ}. The *k-nearest neighbor problem* asks, per query, for the k points of **X** minimizing d(q, ·) under Euclidean distance or maximizing ⟨q, ·⟩ for MIPS. An *approximate* algorithm returns a candidate set **C**, |**C**| = k, and its quality is measured by

> **Definition (Recall@k).** *R@k = (1/t) Σᵢ |Cᵢ ∩ Kᵢ| / k, where Kᵢ is the ground-truth top-k set of qᵢ.*

The engineering metrics are: **latency** (mean/P99 per-query time), **QPS** (queries per second under parallel load), **index build time**, **memory footprint** (DRAM resident bytes), and **density** (points indexed per node) [2].

### 3.2 Graph-based ANN: the unifying view

Graph methods build a directed/undirected graph G = (X, E) where edges connect each point to its approximate neighbors. Search is *beam search*: start from an entry node, iteratively expand the unvisited candidate closest to q, and prune the list to the best L. The entire art is graph construction: edges must be **short enough** to reach the neighborhood and **diverse enough** to escape local minima. This is the tension that RNG pruning, HNSW layering, and Vamana's α-parameter all manage.

### 3.3 How this thesis evaluates claims

We synthesize complexity arguments and published benchmark results on the standard billion-scale corpora — **SIFT1B** (1B × 128-d SIFT descriptors) and **DEEP1B** (1B × 96-d GoogLeNet features) [4][2] — reporting each paper's own numbers and flagging where methodology differs (recall@1 vs recall@10, 16-core vs single-thread). We do not re-run experiments; we analyze them. Complexity claims are presented as asymptotic scaling validated by the papers' own measurements.

## 4. Deep Dive

### 4.1 HNSW: hierarchy as distance-scale separation

HNSW builds a *layered* graph: each element is assigned a maximum layer ℓ by sampling from an exponentially decaying distribution, P(ℓ) ∝ m_L^ℓ (m_L ≈ 1/ln M in the paper, typically parameterized so ~99% of points exist only at layer 0). Layer 0 contains all points with short-range edges; higher layers contain geometrically fewer points with progressively longer edges. Insertion proceeds top-down: greedy search descends each layer from the current best candidate, and at layer 0 the efConstruction nearest candidates found are heuristically pruned to the M nearest (M ≈ 16–64) [1].

The neighbor-selection heuristic is HNSW's quiet genius: instead of connecting to the M nearest candidates, it selects neighbors iteratively, keeping a candidate *e* only if e is closer to the inserted node than to any already-selected neighbor — the RNG (relative neighborhood graph) rule. This rejects *redundant* directions: in a tight cluster, pure nearest-neighbor linkage wastes edges on near-duplicate directions, trapping greedy search in the cluster. The heuristic guarantees directional diversity, which the paper shows dramatically improves recall on highly clustered data [1].

Query execution starts at the top-layer entry point and descends greedily, layer by layer, then runs beam search at layer 0 with candidate list efSearch. The result: **logarithmic complexity scaling** — the paper demonstrates O(log n)-ish growth of distance computations against n from 10⁶ to 10⁹, beating the polylogarithmic scaling of flat NSW. On SIFT1M/1B-class benchmarks HNSW dominated all open-source alternatives at high recall [1]. Its cost is memory: ~M edges per node with float32 vectors resident, roughly 1 GB per million 128-d vectors in hnswlib — prohibitive at 10⁹ points, which is precisely the gap DiskANN fills.

> **Theorem (informal, HNSW scaling):** *For data satisfying a weak local-intrinsic-dimensionality bound, greedy search on a hierarchically scale-separated NSW graph converges in O(log n) hops, because each layer transition contracts the expected distance to the query by a constant factor, mirroring skip-list descent [1].*

```python
# HNSW search: layer descent + beam search at layer 0 (hnswlib-style)
def hnsw_search(q, k, ef_search, entry, layers, M):
    cur = entry
    for level in reversed(range(1, len(layers))):   # greedy descent, ef=1
        cur = greedy_step(q, cur, layers[level])
    # layer 0: beam search with candidate list of size ef_search
    candidates = [cur]                      # max-heap by -dist
    visited = {cur}
    best = sorted_heap(candidates)
    while candidates:
        c = heappop_closest(candidates)     # expand nearest unvisited
        if dist(q, c) > dist(q, best[-1]) and len(best) >= ef_search:
            break
        for nb in layers[0][c]:
            if nb not in visited:
                visited.add(nb); push(candidates, nb, dist(q, nb))
    return top_k(best, k)
```

### 4.2 DiskANN: the Vamana graph and SSD-resident serving

**The three desiderata.** Jayaram Subramanya et al. observed that all prior high-recall ANN indices demanded main memory, which made billion-point search expensive and limited per-node dataset size. DiskANN targets three desiderata simultaneously: *high recall, low query latency, and high density* (points indexed per node) — and meets them on a single 16-core workstation with 64 GB RAM and one SSD [2].

**Vamana construction.** Vamana builds a graph in two phases. First, insert points in random order, linking each new point to its nearest candidates found by beam search. Second — and this is the differentiator — apply **RobustPrune** with an **α-RNG rule**: keep candidate edge p→x only if d(p, x) ≤ α · d(y, x) for all retained neighbors y (α ≥ 1). With α = 1 this is the classical RNG rule; with α > 1 (typical: 1.2) the rule *tolerates* keeping some edges to points slightly farther from x than an existing neighbor, preserving long-range shortcuts. The paper proves that α-RNG graphs contain paths that monotonically approach any target, with the number of hops bounded by O(n^{1/d} log Δ / α) — and empirically shows that α > 1 drastically *reduces* the hop count versus NSG's hard RNG constraint [2].

![DiskANN Vamana graph with SSD page layout and SPANN posting-list partitions](/thesis/ths_1788571748000_f335-1.webp)

**SSD serving via batched beam search.** The serving insight: beam search expands *several* candidates per iteration (the B closest unvisited), and each expansion is one random 4 KB page read — the point's vector plus its neighbor list co-located in one page. Because SSDs serve ~10⁵ random reads/sec, visiting ~100–300 pages yields ~2–5 ms latency. PQ-compressed vectors live in DRAM for distance estimation; candidates are *re-ranked* by exact full-precision vectors read from SSD. The headline result: **>5,000 QPS at <3 ms mean latency and >95% 1-recall@1 on SIFT1B**, where FAISS IVFOADC+G+P plateaued around ~50% recall at similar memory [2]. A merged variant (40 k-means shards, ℓ=2 overlap) cut build resources while staying within ~20% extra latency of the single index — demonstrating that Vamana is also a *versatile in-memory* index, not merely a disk hack [2].

| System | DRAM | Latency | Recall | QPS | Index medium |
|---|---|---|---|---|---|
| HNSW (in-memory) | ~1 TB for 1B pts | sub-ms | >95% R@10 | ~10⁴ | DRAM |
| DiskANN (single index) | 64 GB + SSD | <3–5 ms | >95% R@1 | >5,000 | SSD (PQ in DRAM) |
| DiskANN (merged, 40 shards) | 64 GB + SSD | +20% vs single | ~98.7% R@1 reported | ~4,000 | SSD |
| SPANN | 32 GB + SSD | ~1 ms | 90% R@1/R@10 | ~10⁴ | SSD posting lists |

*Representative numbers on SIFT1B-class billion-point corpora as reported in [1][2][3]; not directly comparable across hardware generations.*

### 4.3 SPANN: the inverted index strikes back

**The contrarian claim.** SPANN's authors argued that the *simple* inverted index, properly adapted to the memory–disk hybrid regime, could match or beat graph methods — and demonstrated it: SPANN is **2× faster than DiskANN at the same 90% recall with the same memory cost**, reaching 90% recall@1 and recall@10 in **~1 ms** with only 32 GB of memory [3].

**Build: hierarchical balanced clustering.** Classical k-means produces wildly imbalanced posting lists — a few giant lists destroy I/O predictability. SPANN instead uses a *hierarchical balanced* clustering algorithm (recursively partitioning with balance constraints) so posting lists are near-uniform in length, letting one page-size parameter serve the whole index. Then it **augments** each posting list with points in the *closure* of the cluster — boundary points that k-means would assign elsewhere but that queries near the boundary need — recovering the recall that hard partitioning loses [3].

**Search: query-aware pruning.** A query is routed by comparing it against in-memory *centroids* (only centroids live in DRAM), then SPANN reads posting lists sequentially from SSD. The query-aware scheme dynamically prunes which lists to read: it estimates, from query-to-centroid distances, the marginal recall gain of each additional list and stops when the expected gain falls below a threshold — typically reading only a *handful* of lists. Fewer, sequential reads beat many random reads: this is why SPANN halves DiskANN's latency at matched recall despite using the "simpler" data structure [3].

### 4.4 IVF-PQ: compression as a first-class citizen

Product quantization remains the most *memory-efficient* index family and the backbone of FAISS deployments [4][5]. The modern recipe — **IVF-PQ with OPQ rotation** (optimized PQ learns an orthonormal rotation R minimizing quantization error) plus re-ranking — compresses each vector to 8–32 bytes, so 1B vectors fit in 8–32 GB: entirely in DRAM. The cost is the *quantization gap*: ADC distances are estimates, so recall ceilings sit below graph methods; DiskANN itself uses PQ-compressed vectors in DRAM as its *distance oracle* during beam search, then re-ranks with exact vectors from SSD — a hybrid that marries PQ's memory efficiency to the graph's recall [2][5]. In practice, IVF-PQ dominates the low-memory regime (≤16 GB), Vamana/DiskANN the mid regime (32–64 GB + SSD), and HNSW the all-DRAM regime.

### 4.5 Beam search: the shared engine

All three systems run some form of **beam search**, and its single parameter — the candidate list size (efSearch in HNSW, L in DiskANN) — is the universal recall/latency knob. Where the graph contains a monotonic path to the true neighbor (Vamana's α-RNG guarantee, or HNSW's heuristic approximation), widening the beam monotonically non-decreases recall, because the list can only retain more of that path's vertices [1][2].

The *cost* model is QPS-relevant: each beam expansion issues distance computations (PQ lookups) and, for DiskANN, one SSD page read. Widening L from 20 to 200 roughly doubles-to-quadruples latency while moving recall from ~90% to ~98% — the classic knee of recall-vs-latency Pareto frontiers, and the reason production vector databases expose L/efSearch/nprobe as runtime-tunable parameters [2][3].

## 5. Empirical Results / Proofs

**Complexity summary.** The three systems occupy distinct points in the complexity space:

| Index | Build time | Query time | Memory (n=10⁹, d=128) | Proven guarantee |
|---|---|---|---|---|
| HNSW [1] | O(n log n) | O(log n) hops, sub-ms | ~1 TB (DRAM) | Logarithmic scaling (empirical, skip-list analogy) |
| Vamana/DiskANN [2] | ~2 days single / ~5 days merged on 64 GB box | ~100–300 SSD page reads, <5 ms | 64 GB DRAM + ~350 GB SSD | α-RNG monotonic paths; O(n^{1/d} log Δ/α) hops |
| SPANN [3] | Hierarchical balanced clustering + closure augmentation | Handful of posting lists, ~1 ms | 32 GB DRAM + posting lists on SSD | 2× DiskANN latency at matched recall/memory |
| IVF-PQ (FAISS) [4][5] | GPU k-means + encoding, <12 h for 1B on 4 GPUs | nprobe lists, tens of ms | 8–64 GB (DRAM) | ADC error bounds from quantization MSE |

**The recall–latency–QPS frontier.** No system dominates everywhere. At *matched memory* (32–64 GB DRAM + SSD), SPANN reports ~1 ms latency at 90% recall@1 where DiskANN needs ~2 ms — but DiskANN reaches higher absolute recall (>95–98% R@1) where SPANN's posting-list coverage saturates, and HNSW in DRAM beats both on latency wherever DRAM is affordable [1][2][3]. QPS scales near-linearly with cores because queries are independent; DiskANN's 5,000 QPS on 16 cores is the canonical data point [2].

**Why α-RNG beats hard RNG on SSD.** DiskANN's core lemma: under α-RNG, each hop geometrically contracts the distance to the target (by ~17% at α = 1.2), yielding O(log Δ / log α) hops from diameter Δ. The retained long-range edges mean fewer total hops — fewer SSD page reads. Hard RNG (α = 1) prunes those shortcuts, forcing detours that NSG pays for in hop count, i.e., disk I/O [2].

**Benchmark hygiene note.** Cross-paper comparisons must match dataset, k, recall metric (R@1 vs R@10), thread count, and mean vs P99 latency. DiskANN's headline is 16-core mean latency on SIFT1B [2]; SPANN's 2× claim is at 90% recall with equal memory [3]. Both are indicative, not exact.

## 6. Limitations

1. **Static-graph bias.** HNSW, Vamana, and SPANN are all optimized for *static* corpora. Real RAG vector databases are *streaming*: embeddings are re-computed, documents deleted, corpora versioned. Dynamic insertion into Vamana/SPANN degrades partition balance and graph quality over time; production systems (e.g., Azure Cognitive Search's DiskANN deployment) handle this with periodic rebuilds or merge-based compaction, but the theory of dynamic billion-scale ANN remains thin [2].

2. **Metric brittleness.** The guarantees assume Euclidean or inner-product metrics in spaces of bounded intrinsic dimensionality. Learned embeddings drift across model versions; a 768-d encoder replaced by a 1024-d one invalidates the entire index. Cross-encoder *late interaction* (ColBERT-style) retrieval does not reduce to ANN at all, bounding the approach's generality.

3. **Recall ceilings vs. exact needs.** At 95% R@1, one query in twenty returns the wrong top result. For RAG over factual QA this is acceptable — the generator sees top-k=10 and marginalizes (cf. RAG-Token [6]) — but for deduplication or compliance search, missed neighbors are silent failures. Exact verification layers (re-ranking, as DiskANN does with full-precision vectors [2]) mitigate but do not eliminate this.

4. **I/O variance.** SSD random-read latency has a long tail under concurrent load; P99 latency can be 5–10× the mean. The published numbers are means on quiet hardware — production SLOs must budget for GC pauses, page-cache pollution, and noisy neighbors, none of which appear in the papers.

5. **Quantization–graph interplay.** PQ-compressed distance oracles introduce systematic error that beam search can amplify down a suboptimal branch. DiskANN's re-ranking fixes the *output* but not the *path*; the interaction between ADC error and graph navigability is under-theorized [2][5].

## 7. Conclusion

The billion-scale ANN problem has no single winner — it has a *design space*, and this thesis has mapped its three principal attractors. **HNSW** [1] proved that hierarchy plus RNG-diverse linkage yields logarithmic search scaling in memory, and remains the default wherever DRAM suffices. **DiskANN** [2] proved — against the prevailing wisdom — that SSD-resident indices can satisfy high recall, low latency, and high density simultaneously, via the Vamana graph's α-RNG construction and batched beam search over 4 KB pages: 5,000 QPS at <3 ms and >95% recall on a single workstation. **SPANN** [3] proved that the inverted file, rebuilt around balanced clustering, closure augmentation, and query-aware pruning, can halve that latency at matched recall and memory — a reminder that data structures are not fashion cycles.

For the RAG vector database — the application that made all of this commercially urgent [6] — the synthesis is pragmatic: *PQ-compressed DRAM oracles, SSD-resident graphs or posting lists, exact re-ranking at the top-k*. As corpora scale toward tens of billions of vectors and query SLOs tighten below a millisecond, the next frontier is *learned co-design*: partitioners and graph constructors trained jointly with the embedding model, streaming updates without rebuilds, and hardware-aware layouts for computational storage. The navigable small world has many more layers to climb.
