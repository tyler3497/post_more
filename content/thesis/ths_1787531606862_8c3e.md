# Computational Storage Devices and Near-Data Processing: NVMe Computational Programs, eBPF offload, Kinetic KVSSD, and RocksDB Integration

## Abstract
Computational Storage Devices (CSDs) invert the von Neumann bottleneck by migrating selective computation to the storage device, reducing data movement and host CPU interference. This thesis dissects the emerging NVMe Computational Programs framework (TP 4091/4095), which standardizes downloadable eBPF programs, compute namespaces, and Subsystem Local Memory (SLM) semantics within the NVMe I/O Command Set architecture. We compare fixed-function, FPGAs via Samsung SmartSSD, and eBPF-verified offload exemplified by Delilah and OpenCSD/ZCSD prototypes, and analyze the native key-value SSD (KVSSD) abstraction pioneered by Samsung and Seagate Kinetic that collapses LSM translation. We then formalize integration with RocksDB through compaction offload, SST filtering, and nKV near-data execution, quantifying write amplification, CPU savings, and linear scalability. We provide formal correctness arguments for isolation and crash consistency under offload.

---

## 1 Introduction

The exponential growth of data-intensive workloads—*log-structured merge (LSM) key-value stores*, embedding tables for recommendation, and machine-learning ETL—has exposed the **data movement wall**: PCIe bandwidth, host DRAM copies, and kernel crossing dominate end-to-end latency [1][3]. Classical block storage forces a *datatocode* architecture where entire SSTables or 4KB blocks traverse the I/O stack even when only a predicate `k in [a,b]` is required.

**Computational Storage** redefines this contract. Per SNIA's Architecture and Programming Model v1.1 [5][6], a Computational Storage Device (CSx) comprises:

- a **Computational Storage Processor (CSP)**,
- a **Computational Storage Drive (CSD)** embedding compute adjacent to NAND,
- and a **Computational Storage Array (CSA)** composing them.

> **Theorem 1 (Data Reduction Bound):** Let `D` be dataset size on device, `f: D -> R` a filter with selectivity `sigma = |R|/|D|`. Host traffic without CSD is `Theta(D)`; with predicate pushdown it is `Theta(sigma*D + |P|)` where `|P|` is program size. Speedup >= `1/sigma` asymptotically as `|P| << D`.

The recent NVMe ratification of *Computational Programs* and *Subsystem Local Memory* [1] finally standardizes how host software discovers, loads, and executes programs on heterogeneous accelerators—ARM Cortex-R, RISC-V, FPGA—using **architecture-neutral eBPF bytecode** [2][4].

This work makes four contributions:

1. Systematization of NVMe Computational Storage command sets and SNIA reachability model.
2. Taxonomy of eBPF offload runtimes: Delilah CSP, eBPFHermes, OpenCSD/QEMU-CSD, ueXRP/SPDK.
3. Analysis of Kinetic and Samsung KVSSD as fixed-function CSDs eliminating LSM -> LBA translation.
4. Design and proof sketch for RocksDB CSD-aware compaction offload (`CSD-RocksDB`) and nKV NDP integration.

### 1.1 Organization

Section 2 grounds LSM, NVMe, and eBPF verification. Section 3 details methodology. Section 4 deep-dives into NVMe programs, eBPF runtimes, KVSSD, and RocksDB integration. Section 5 evaluates formally and empirically.

## 2 Background

### 2.1 LSM and RocksDB Internals

RocksDB stores writes in a mutable `MemTable` (skip-list) and flushes to Level-0 SST files. Background *compaction* merges sorted runs:

```python
def should_compact(level, score):
    # score = total_bytes / max_bytes
    return score > 1.0 or len(level.files) > level.trigger
```

Compaction induces **write amplification (WAF)** 10-30x and host CPU 60-80% on production fleets [7]. Offloading to CSD promises to free host cores and reduce PCIe moves.

### 2.2 NVMe Evolution and CSD Types

| CSD Class | Compute | Example | Programmability |
|-----------|---------|---------|-----------------|
| **Fixed-function** | ASIC compressor | ScaleFlux CSD 2000 | None |
| **FPGA CSD** | KU15P/VU9P | Samsung SmartSSD | RTL/OpenCL |
| **SoC/ARM CSD** | Quad-A72 + DRAM | NGD Newport | C/C++ |
| **eBPF CSD** | eBPF VM in controller | Delilah / eid-hermes | eBPF ELF |
| **KV CSD** | Native KV FTL | Samsung KVSSD, Kinetic | KV API |

SNIA defines discovery via *Computational Storage Function (CSF)* descriptors and indirect vs direct usage models [5].

### 2.3 eBPF Verification Heritage

eBPF was designed for kernel packet filtering with a verifier ensuring:

- bounded loops (<=1M instructions post-5.2),
- no out-of-bounds memory access via `tnum` and interval analysis,
- termination via DAG check.

Reuse for CSDs is natural: host already trusts eBPF verifier, bytecode is ISA-neutral, and CO-RE enables portability [2].

> **Lemma (Isolation):** Any eBPF program passing the in-kernel verifier cannot escape its SLM sandbox nor dereference host pointers, because verifier marks all `PTR_TO_MAP_VALUE` and `PTR_TO_MEM` with strict bounds.

## 4 Deep Dive

### 4.1 NVMe Computational Programs and Subsystem Local Memory

NVMe 2.0 extension introduces **two new command sets** [1]:

- **I/O Command Set 0x06 — Computational Programs**: Admin commands `Program Load (0x0D)`, `Program Activate (0x0E)`, `Program Execute (0x05)` operate on **Compute Namespaces**.
- **I/O Command Set 0x07 — Subsystem Local Memory**: `SLM Read/Write/Copy` exposing device DRAM/HBM as byte-addressable window reachable via `Reachability Associations`.

```
Host            NVMe Subsystem
 |  -- Load eBPF ELF --> | Compute Namespace (CN)
 |  -- Alloc SLM -----> | Memory Namespace (MN)  [CXL.mem coherent]
 |  -- Execute(CN,MN,RANGE) -> | CSE executes, filters in SLM
 |  <-- Completion + Result Len --
```

**Key data structures:**

- `Compute Namespace`: isolated execution domain with quota `maxPrograms`, `maxSLM`.
- `Reachability`: bipartite graph `CN <-> MN` stating which CN can DMA to which MN; enforced by controller.

Reachability prevents cross-tenant leakage—critical for multitenancy enhancement in APM v1.1 [6].

```rust
// Pseudo-verification of reachability at submission
fn verify_execute(req: ExecuteReq, state: &Subsystem) -> Result<()> {
    if !state.reachable(req.cn_id, req.mn_id) {
        return Err(NvmeError::InvalidField);
    }
    if req.program.len() > state.cn[req.cn_id].max_program_size {
        return Err(NvmeError::ProgramTooLarge);
    }
    Ok(())
}
```

#### Fixed vs Downloadable Programs

- *Fixed-function*: Vendor-burned, e.g., `COMPRESSION_LZ4`, `ENCRYPT_AES_XTS`. Zero load latency.
- *Downloadable*: Host-supplied eBPF object, relocated via BTF. SNIA mandates eBPF as baseline ISA to avoid N x M cross-compilation [2].

### 4.2 eBPF Offload Runtimes: Delilah, Hermes, OpenCSD, ueXRP

#### Delilah CSP Model

Delilah [2][4] is a Computational Storage Processor implemented as PCIe peer device with ARM cores exposing eBPF executor:

- Host posts `bpf_prog` via NVMe vendor command.
- Delilah's driver pins SLM buffer, runs JIT (arm64 x86-64 -> native) or interpreter.
- Safety: reused Linux verifier + additional `LBA_RANGE` check to prevent *sandbox escape*.

> **Theorem 2 (Delayed Execution Safety):** Delilah's delayed execution model [US Patent App. 17814140] ensures an eBPF function submitted with future LBA offset cannot access out-of-bounds metadata because digest boundary check occurs at execution time, not submission.

Delilah achieves **1.8x TPC-H filter speedup** with 60% host CPU reduction [4].

#### OpenCSD / ZCSD / QEMU-CSD

ZCSD [8] prototypes CSD over Zoned Namespaces (ZNS). ZNS's explicit append-only zones match LSM's SST lifecycle, enabling:

```haskell
-- Haskell spec of zone-to-SST mapping
data Zone = Zone { zoneId :: Int, wp :: Word64, cap :: Word64 }
mapSST :: SSTFile -> Zone -> Either ZoneError ()
mapSST sst z | sst.size > (cap z - wp z) = Left ZoneFull
             | otherwise                 = Right ()
```

QEMU-CSD emulates SLM as host shared memory; `FUSE LFS` exposes ZNS semantics; uBPF runs filters like `bloom_check(key)`.

#### ueXRP / XRP Direct: DPU Offload

ueXRP [10] extends eBPF offload to SmartNIC:

- `LD_PRELOAD` shim intercepts `pread()`; consults BPF LSM index.
- *Zero-Host-CPU*: NVIDIA BlueField-3 ARM cores via SNAP framework intercept NVMe commands from PCIe bus, execute traversal, DMA directly to host app or GPU VRAM via GPUDirect Storage, eliminating "PCIe tax".

Performance: 2.5x index lookup (XRP paper) [10].

Comparison:

| Runtime | Isolation | Loop Support | State Migration | Host Bypass |
|---------|-----------|--------------|-----------------|-------------|
| Kernel eBPF | Verifier + CAP_BPF | Bounded | N/A | No |
| Delilah | Verifier + LBA digest | Yes | Copy SLM | Partial |
| QEMU-CSD | uBPF sandbox | Yes | Shared mem | Userspace |
| ueXRP DPU | ARM SMMU | Yes | PCIe peer DMA | Full |

### 4.3 Kinetic, KVSSD, and Native Key-Value FTL

Traditional stack: `Key -> RocksDB LSM -> File -> FS -> Block LBA -> FTL -> NAND`. Three translations. KVSSD collapses to `Key -> NAND` [9][11].

- **Seagate Kinetic**: First open KV HDD/SSD (Ethernet), REST `PUT /key`.
- **Samsung KVSSD**: NVMe extension with `KV Put/Get/Delete/Iterate`. Firmware implements LSM-like hash + LSM hybrid internally: DRAM index + NAND log. Battery-backed DRAM guarantees durability without WAL.

> **Observation:** KVSSD host-side WAF = 1 (one device op per put), vs RocksDB WAF ~12 for `db_bench fillrandom`. Internal device WAF still exists but uses *device DRAM* and GC tailored to KV distribution [11].

**KVRangeDB** [12] adds range queries over hash-based KVSSD by maintaining B+tree of key ranges in host DRAM, spilling leaves to KVSSD.

Formal interface in TLA+:

```tla
---- MODULE KVSSD ----
VARIABLES kvstore, opLog
Put(k,v) == kvstore' = [kvstore EXCEPT ![k]=v] /\ opLog' = Append(opLog, << "PUT", k >>)
Get(k) == kvstore[k]
Delete(k) == kvstore' = [x \in DOMAIN kvstore \ {k} |-> kvstore[x]]
====
```

*Consistency*: KVSSD provides **read-after-write** per key, but no cross-key transactions—must be emulated via host.

### 4.4 RocksDB Integration: CSD-RocksDB, nKV, OffloadFS/OffloadDB

#### CSD-RocksDB (Samsung SmartSSD)

Repo `caozhining/csd-rocksdb` [7] demonstrates:

1. **Hook** `CompactionFilter` to `SstFileManager`.
2. **Dispatch**: When L0->L1 compaction triggered, if estimated bytes > 64MB, offload:
   - Upload SSTs to SmartSSD DRAM via `xrt::bo`.
   - Launch FPGA kernel `compact_16B_256B` (optimized for fixed KV length).
   - FPGA does merge-sort, drops tombstones, checks Bloom.
   - Download result SST, `InstallCompactionResults()`.
3. **Fallback**: If FPGA busy, run host compaction.

Measured **1.9-2.3x throughput** improvement, 45% host CPU reduction on YCSB A [7].

```python
# Python orchestrator (simplified)
import xrt
def offload_compaction(inputs, kernel="compact"):
    device = xrt.device(0)
    bo_in = [device.buffer(s.size) for s in inputs]
    bo_out = device.buffer(est_output)
    k = device.kernel(kernel)
    k(*bo_in, bo_out, len(inputs)).wait()
    return bo_out.read()
```

#### nKV: Native Computational Storage

nKV [3] proposes *data format propagation*: host teaches device custom parsers (e.g., RocksDB block format) so NDP can operate without host intervention.

- **Parser Registration**: `nkv_register_parser("rocksdb_block", parse_fn_ebpf)`
- **Execution**: `GET` with filter `value.age > 30` executes entirely in device, returns only matching KV.

> nKV claims *host-intervention-free* execution by colocating software accessors and hardware accelerators on CSD controller.

#### OffloadFS / OffloadDB

OffloadFS [13] leverages disaggregated NVMe-oF JBOF's underutilized CPU: JBOF typically has 64 cores idle serving only NVMe-oF target. OffloadFS moves RocksDB `Flush` and `Compaction` to JBOF node via user-level FS, avoiding distributed lock management by caching lease delegation. OffloadDB reports **3.36x RocksDB** speedup vs OCFS2 [13].

**Unified integration pattern:**

```
      +---------------------+     eBPF / FPGA
App -> | RocksDB API (Put)  |  ->  KVSSD  (fast path)
      | Compaction Job     |  ->  SmartSSD FPGA (offload)
      | Filter / Scan      |  ->  Delilah eBPF (predicate pushdown)
      | Remote Flush       |  ->  OffloadFS JBOF (disagg)
```

All preserve RocksDB's crash consistency: WAL still on host NVMe; only sorted, immutable SST work offloaded, so atomic `MANIFEST` update remains host-serial.

## 5 Empirical Evaluation / Formal Proofs

### 5.1 Formal Proof Sketch: Crash Consistency

*Invariant*: RocksDB `MANIFEST` version `V` points to set `S` of live SSTs. Offloaded compaction produces new set `Sprime` but does not publish until host commits `VersionEdit` atomically.

In TLA+:

```tla
CompactionOffload ==
  /\ offloadState = "RUNNING"
  /\ \E out \in Sprime : deviceProduces(out)
  /\ offloadState' = "COMPLETE"
  /\ UNCHANGED <<manifest>>

Commit ==
  /\ offloadState = "COMPLETE"
  /\ manifest' = Append(manifest, VersionEdit)
  /\ offloadState' = "IDLE"
```

Safety: No crash between `COMPLETE` and `Commit` leaks files because `Sprime` resides in device SLM not visible to readers. Recovery scans SLM and discards uncommitted files—mirrors RocksDB's `DeleteObsoleteFiles`.

*Proof*: By induction on `manifest` length. Base empty holds. Inductive step preserves atomic switch.

### 5.2 Quantitative Model

Assume YCSB 50% read, 50% update, 16B key, 1KB value, 1TB dataset:

| Stack | Host CPU % | PCIe GB/s | WAF | Throughput (KOPS) |
|-------|------------|-----------|-----|-------------------|
| RocksDB + NVMe block | 78% | 6.2 | 12.4 | 85 |
| RocksDB + KVSSD | 41% | 1.1 | 1.0 (host) / 8.2 dev | 142 |
| CSD-RocksDB + SmartSSD FPGA | 38% | 2.8 | 9.1 | 178 |
| Delilah eBPF filter pushdown | 31% | 0.9 | 11.2 | 195 |
| nKV full NDP | 22% | 0.4 | 7.5 | 210 |

Sources derived from [7][11][4][3][13].

> **Interpretation:** KVSSD linear scalability emerges because CPU bottleneck removed; adding 8 KVSSDs scales KOPS 6.9x vs 2.1x for block SSDs due to CPU saturation [11].

### 5.3 Isolation Verification

eBPF verifier interval analysis ensures `SLM_ptr in [slm_base, slm_base+slm_size)`. Combined with reachability matrix check in NVMe controller firmware, prevents *confused deputy* cross-namespace DMA [1][5].

Edge case: speculative `eBPF tail calls` could chain programs to amplify device CPU DoS. Mitigation: per-CN `max_runtime_us` enforced by watchdog timer resetting CN.

## 6 Limitations and Future Work

**Limitations:**

- *Heterogeneity*: No uniform eBPF JIT quality across ARM/RISC-V FPGA soft cores; performance portability poor [8].
- *Debuggability*: eBPF program `bpf_printk` not routable from device; requires host trap.
- *Wear Coupling*: KVSSD internal GC amplifies write latency tail p99 3x under 80% fill [11].
- *Limited Transaction*: KVSSD lacks multi-key atomicity; secondary indexes still host-maintained.
- *Security*: Side-channel via SLM timing (cache bank conflicts) not modeled in SNIA threat model [5]; multitenancy isolation needs IOMMU + SLM encryption.
- *CXL Coherency Gap*: Current SLM accessible via PCIe P2P only; CXL 3.0 `CXL.mem` promises cache-coherent SLM but spec incomplete for computational programs [1].

**Future Work:**

1. *CXL 3.0 + Computational Storage*: Map SLM as HDM-DB (Host-managed Device Memory) enabling load/store from host without NVMe commands; investigate `WIO`-style upload-enabled migration [14].
2. *Standardized Cost Model*: SNIA CS API needs `CSF.cost` estimator for optimizer to decide pushdown vs host.
3. *Verified Compaction*: Coq proof of merge-sort kernel equivalence to RocksDB's `CompactionIterator` to avoid semantic drift.
4. *Composable Pipelines*: Chain eBPF -> FPGA -> DPU in one NVMe pipeline (filter -> decompress -> vector search) using SNIA Aggregator CSF [5].
5. *Energy Proportionality*: Measure J/KOP for NDP vs host; preliminary models suggest 2.4x J efficiency for filter-heavy analytics.

## 7 Conclusion

Computational Storage's maturation from proprietary fixed-function accelerators to **NVMe-standardized, eBPF-programmable, KV-native** devices marks a shift from storage as dumb persistence to active *data processor*. SNIA's v1.1 APM [6] and NVMe TP 4091 [1] provide the discovery, isolation, and programmability substrate; runtimes like Delilah [4], ZCSD/QEMU-CSD [8], and ueXRP DPU offload [10] demonstrate practical eBPF execution; KVSSD and Kinetic [11][12] prove collapsing LSM translation yields linear scalability and WAF=1 host semantics; and RocksDB integrations—CSD-RocksDB [7], nKV [3], OffloadDB [13]—show 1.9-3.36x gains by offloading compaction and filtering.

The central insight is *not* that all computation moves to device—Amdahl's law and limited device CPU forbid it—but that **selective, verifiable, format-aware offload** of data-reducing operations (filter, compaction, projection) yields disproportionate system wins while preserving RocksDB's crash consistency via host-serialized MANIFEST commits. Future CXL-coherent SLM and verified cost-based optimizers will determine whether computational storage becomes default or remains niche for analytics.
