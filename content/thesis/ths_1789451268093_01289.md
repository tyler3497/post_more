# Proof-Carrying Code and Foundational Proof Certificates: LFSC, Dedukti, and the De Bruijn Criterion

## Abstract

Mobile code, SMT solvers, and interactive theorem provers all face one trust problem: the programs that *produce* proofs are far too complex to trust, while the programs that *check* them must be beyond suspicion. This thesis traces the arc from Necula and Lee's proof-carrying code to the modern certificate infrastructures realizing Barendregt and Barendsen's de Bruijn criterion. We examine the Logical Framework with Side Conditions (LFSC), which treats proof checking as typechecking in the Edinburgh Logical Framework extended with executable side-condition code; the Dedukti universal proof checker, built on the λΠ-calculus modulo theory, where definitional equality is generated by user-declared convergent rewrite rules; and the foundational proof certificates (FPC) framework of Chihani, Miller, and Renaud, which grounds certificate semantics in focused sequent calculus, separating deterministic clerk actions from expert-driven proof search. We analyze empirical evidence from LFSC's SMT deployments, Dedukti's cross-prover translations, and FPC elaboration experiments, closing with an assessment of residual trust gaps: side-condition code, rewrite-rule convergence, and the irreducible cost of proof reconstruction.

## 1 Introduction

In 1996, George Necula and Peter Lee proposed a disarmingly simple answer to one of the hardest questions in systems security: how can a host execute code written by a stranger? Their answer, *proof-carrying code* (PCC), inverts the usual trust relationship. Instead of the host analyzing untrusted code with a complex, trusted verifier, the *code producer* is required to ship the code together with a formal proof that the code satisfies the host's safety policy [1]. The host's trusted computing base shrinks to three small components: the program logic, the proof checker for that logic, and the formalization of the safety property itself. Neither the mobile code nor the accompanying proof needs to be trusted — a malicious proof is simply rejected by the checker, and a valid proof of a true statement is, by the soundness of the logic, harmless.

The original PCC publication used packet filters as its motivating example: a user-mode application hands machine code to the kernel to decide which network packets merit processing [1]. Because the filter runs in kernel mode, a single out-of-bounds memory write could compromise the entire system. Traditional defenses — interpretation, software fault isolation, in-kernel compilation — all impose runtime costs on every packet. PCC pays the verification cost once, at load time, and the code then runs at full speed with no further checks.

This producer/consumer asymmetry is an instance of a far older principle. In 1968, de Bruijn's Automath project articulated what Barendregt and Barendsen later named the **de Bruijn criterion**: the correctness of an entire mathematical system should be reducible to the correctness of a small, independently checkable kernel [3]. The LCF tradition of Milner achieved the same end by a different route — an abstract datatype of theorems whose constructors are exactly the primitive inference rules — while Automath and its descendants exploited the Curry–Howard correspondence to make the kernel a *typechecker* for proof objects [3]. PCC is the de Bruijn criterion applied to mobile code; the question this thesis investigates is how the criterion is best realized for *proof certificates* in the large.

Three modern answers dominate the landscape, and they embody three distinct philosophies of trust:

- **LFSC** (Logical Framework with Side Conditions) extends the Edinburgh Logical Framework with executable side-condition code, treating proof checking as *typechecking* and letting proof-system designers slide along a continuum from declarative to computational checking [4][6].
- **Dedukti** implements the λΠ-calculus modulo theory, where definitional equality is an arbitrary congruence generated by user-declared rewrite rules, making it a *universal* checker into which foreign logics are shallowly encoded [7][8].
- **Foundational proof certificates (FPC)** reject the fixed-logic approach entirely: certificates are documents whose semantics is defined proof-theoretically, in focused sequent calculus, with *clerks* performing deterministic steps and *experts* guiding search [9][10].

We analyze each in turn, compare their de Bruijn compliance, survey the empirical record, and identify what trust each still demands.

## 2 Background

### 2.1 The PCC architecture and its weaknesses

In Necula's original architecture, the code producer first runs a *verification condition generator* (VCGen) derived from a Hoare-style program logic: given a safety policy, the VCGen produces a set of lemmas whose proofs suffice to guarantee the policy [2]. The producer then generates machine-checkable proof terms for each lemma — typically with the aid of a theorem prover — and ships code plus proofs to the consumer. The consumer typechecks the proofs against the safety policy and either installs the code or rejects it.

One weakness of the initial design was that the soundness of the VCGen itself was assumed rather than proved — and errors in that untrusted component did escape testing [2]. Andrew Appel's *foundational* proof-carrying code (FPCC) answered by generating verification conditions directly from the operational semantics of the machine rather than from an axiomatized program logic, at the price of considerably more complex proofs [2]. Besson and colleagues later showed how *certified abstract interpretation* could generate PCC certificates for bytecode languages, proving absence of array-out-of-bounds accesses via interval analysis with the analyzer itself verified [2]. The trajectory is unmistakable: each generation pushes more of the trusted base into checkable, mechanically verified artifacts.

### 2.2 The de Bruijn criterion and kernel design

The skeptical approach to theorem proving predates PCC by decades. Automath introduced proof objects checked by a small kernel-as-typechecker; LCF introduced the abstract theorem datatype enforced by a functional language's type system [3]. Modern systems still choose one of these two styles: Coq's kernel checks proof terms via the Curry–Howard isomorphism, while the HOL family inherits LCF's abstract-datatype discipline.

> **Theorem (de Bruijn compliance, informal):** *A proof-producing system satisfies the de Bruijn criterion if there exists a checker C such that (i) the trusted code base of C is small enough for independent audit, (ii) C accepts a purported proof π of formula φ only if φ is valid in the stated logic, and (iii) every proof the system claims to have found can be exported in a form C accepts. The soundness of the whole system then reduces to the soundness of C.*

The third clause is where most systems fail: proof scripts, tactic languages, and solver-specific refutation formats are rarely exportable to an independent checker. This *interoperability gap* is precisely what LFSC, Dedukti, and FPC each attempt to close.

### 2.3 Logical frameworks as proof metaformats

The Edinburgh Logical Framework (LF) of Harper, Honsell, and Plotkin encodes logics via *judgments as types*: inference rules become type signatures, and proof checking becomes typechecking [4]. LFSC extends LF with *side conditions* — executable, simply-typed functional code attached to proof rules and evaluated each time the rule is applied [4]. This single mechanism addresses the two central problems of SMT proof checking: very large proofs, and compact representation in the presence of complex side conditions on rules [4]. Incremental checking, which fuses parsing and proof checking so that proof subterms are never fully materialized in memory, keeps memory usage bounded on solver-scale refutations [4].

## 3 Methodology

This thesis conducts a comparative, evidence-driven analysis of the three certificate frameworks along five axes: **(i)** the size and auditability of the trusted kernel; **(ii)** the expressiveness of the certificate language; **(iii)** the size of emitted certificates; **(iv)** the computational cost of checking; and **(v)** the maturity of cross-system interoperability. Our method is threefold.

First, we reconstruct the *formal core* of each system from primary sources: the LFSC signature and side-condition language [4][6], the typing rules of the λΠ-calculus modulo theory underlying Dedukti [7][8], and the focused sequent calculus with clerk/expert annotations underlying FPC [9]. Second, we compare kernel designs against the de Bruijn criterion, paying particular attention to where each system smuggles complexity back into the trusted base — compiled side-condition code in LFSC, user-declared rewrite rules in Dedukti, and proof-reconstruction search in FPC. Third, we survey the published empirical record: LFSC's SMT proof-checking benchmarks [5], Dedukti's translations of large proof libraries from HOL Light, Coq, Matita, Zenon, and iProver [8], and FPC's elaboration and distillation experiments [9].

Throughout, we distinguish *checking* (deciding validity of a presented certificate, which must be trustworthy) from *producing* (finding the certificate, which may use arbitrary untrusted heuristics). This separation — the essence of both PCC and the de Bruijn criterion — structures every comparison that follows.

## 4 Deep Dive

### 4.1 The LFSC checking pipeline: signatures, side conditions, and incremental typechecking

An LFSC proof system is declared as a *signature*: a collection of type and term constants together with proof rules written as dependent function types in the Edinburgh LF tradition. Consider propositional resolution, the workhorse of SAT/SMT refutations. In LFSC one declares clause and literal types, then a rule such as:

```lisp
;; LFSC signature fragment (.plf) for propositional resolution
(declare var sort)
(declare clause sort)
(declare lit (term var))
(declare resolve (! c1 clause (! c2 clause (! v var
  (side-condition (resolve-clauses c1 c2 v) clause)))))
```

The `side-condition` annotation is the heart of LFSC: `resolve-clauses` is a program in LFSC's small functional language — simply typed, call-by-value, with pattern matching, recursion, `markvar`/`ifmarked` primitives for variable occurrence tracking, and explicit failure [4]. When the checker applies the rule, it *runs* this code, computing the resolvent instead of demanding every literal spelled out in the proof term — shrinking certificates dramatically.

This yields what Reynolds, Stump, and colleagues call the **declarative–computational continuum** [5][6]. At one extreme, proofs are fully explicit and checking is pure typechecking; at the other, a single rule application may invoke substantial computation (e.g., Farkas-lemma arithmetic checks for linear real arithmetic). The signature author chooses the operating point per rule. Experiments on quantifier-free integer difference logic (QF_IDL) with the `clsat` solver showed proof-checking overhead of roughly 30% of solving time — evidence that the continuum can be tuned to solver-scale workloads [5].

Incremental checking completes the engineering picture: the `lfscc` checker fuses parsing and typechecking so that gigantic proof terms are never fully resident in memory [4]. Side-condition code can additionally be *compiled* to C++ (`--compile-scc` / `--run-scc`) rather than interpreted, trading a larger trusted step for order-of-magnitude speedups on arithmetic-heavy theories [12].

### 4.2 Dedukti: the λΠ-calculus modulo theory and rewriting kernels

Dedukti takes a more radical step.

> **Theorem (Conversion modulo rewriting):** *In the λΠ-calculus modulo theory, the conversion rule states that if Γ ⊢ M : A and A ≡* B where ≡* is the congruence generated by β-reduction together with the declared rewrite rules R, then Γ ⊢ M : B. Typechecking therefore reduces to rewriting both sides to a common normal form.*

Concretely, a Dedukti development declares symbols and rewrite rules in `.dk` files:

```dedukti
;; Dedukti: natural numbers with definitional addition by rewriting
nat : Type.
zero : nat.
succ : nat -> nat.
plus : nat -> nat -> nat.

rule plus zero     $n --> $n
with plus (succ $m) $n --> succ (plus $m $n)
```

Because conversion *computes*, encodings of foreign logics become shallow: the connectives and inference rules of HOL, Coq's Calculus of Inductive Constructions, or first-order logic modulo can be declared with rewrite rules that preserve their computational content, rather than deeply embedding them as inert syntax [8].

The price of this universality is well understood.

### 4.3 Foundational proof certificates: clerks, experts, and the focused sequent calculus

Where LFSC and Dedukti fix a logical framework and vary the logic, foundational proof certificates fix *proof theory itself* and vary the evidence.

A certificate is then a document that guides a generic checker through this focused search.

- **Clerks** handle the deterministic, invertible steps — they merely record which asynchronous rule to apply, requiring no search.
- **Experts** handle the nondeterministic choices — which formula to focus on, which term to instantiate, which branch of a disjunction to take — and may invoke bounded search when the certificate is *implicit* [9].

Miller's four desiderata for certificates frame the design: a *simple* checker must in principle be able to validate any certificate (D1); the format must accommodate a *wide range* of proof systems (D2); certificates should support *manipulation* such as elaboration and distillation; and checking should be *trustworthy* independent of the prover that produced the evidence [10].

The elaboration/distillation pair is FPC's most distinctive contribution.

```haskell
-- FPC checker architecture (schematic): the kernel never trusts the prover
data Certificate = Implicit Evidence SearchBounds | Explicit ProofTerm

check :: FPC_Definition -> Certificate -> Formula -> Bool
check def cert goal =
  let elaborated = elaborate def cert   -- untrusted search, may fail
  in kernelCheck def elaborated goal   -- tiny trusted core: focused sequent rules
```

The untrusted elaborator may use arbitrary heuristics, parallelism, or machine learning; only the kernel's verdict counts.

### 4.4 Three kernels, one criterion: de Bruijn compliance compared

The following table compares the three frameworks — plus the two classical kernel styles for reference — against the de Bruijn criterion's demands:

| System | Kernel idea | Trusted base | Certificate style | Interoperability |
|---|---|---|---|---|
| LCF (HOL) | Abstract theorem datatype | ML type system + primitive rules | Proof scripts (not portable) | Low |
| Coq | Proof objects via Curry–Howard | Small kernel typechecker | Proof terms (`.vo`) | Medium |
| **LFSC** | Checking = LF typechecking + side conditions | `lfscc` + side-condition code | Signatures + compact proofs | High (SMT) |
| **Dedukti** | Typechecking modulo rewriting | Rewriting/typechecking engine | `.dk` developments + rewrite rules | Very high |
| **FPC** | Focused sequent calculus + clerks/experts | Simple focused kernel | Implicit/explicit certificates | Very high |

Several contrasts deserve emphasis.

All three satisfy the letter of the de Bruijn criterion better than the systems they interoperate with: each reduces trust in sprawling provers — SMT solvers, Coq, HOL Light, Zenon — to trust in a small, auditable, independently reimplementable checker.

A TLA+-style sketch of the shared trust argument clarifies the common structure:

```tla+
---- MODULE TrustKernel ----
EXTENDS Naturals
VARIABLES cert, verdict
TypeOK == cert \in Certificates /\ verdict \in {"accept", "reject", "unknown"}
Soundness == [](verdict = "accept" => Valid(ClaimOf(cert)))
Completeness == <>(ProverFindsProof => <>(verdict = "accept"))
\* The de Bruijn criterion demands Soundness of the *checker* alone;
\* Completeness may rely on arbitrarily untrusted producers.
====
```

## 5 Empirical Results / Proofs

**LFSC and SMT proofs.** The LFSC program's empirical anchor is SMT proof checking at solver scale. Oe, Reynolds, and Stump reported that LFSC checking of QF_IDL refutations from their `clsat` solver added roughly 30% overhead relative to solving time, with incremental checking keeping memory bounded [5]. A follow-up study on linear real arithmetic mapped the declarative–computational continuum empirically: pushing Farkas-certificate validation into computational side conditions shrank proofs substantially while keeping checking times competitive, and the authors reported comparative generation/checking numbers across alternative LRA proof systems [6]. The checker remains actively maintained as the proof infrastructure of the cvc5 SMT solver [12], making LFSC arguably the most industrially deployed of the three frameworks.

**Dedukti as universal checker.** Dedukti's evidence is breadth of translation. Satellite tools — Krajono for Matita, Coqine for Coq, Holide for OpenTheory/HOL Light, Focalide for FoCaLiZe, plus translators for Zenon, iProverModulo, and ArchSAT — export whole libraries into Dedukti's rewriting framework, where a single small checker revalidates them [8][11]. The logical-framework paper documents successful checking of large translated developments across constructive and classical logics, simple type theory, and full CIC with universes [8]. The 2020 rewriting-engine redesign replaced naive matching with compiled decision trees over Miller patterns, addressing the performance bottleneck that rewriting-heavy encodings had exposed [11].

**FPC elaboration and distillation.** The FPC record is more foundational than benchmark-driven, but no less concrete: Chihani, Miller, and Renaud give FPC definitions covering resolution refutations (binary, hyper-, ordered resolution, paramodulation), natural deduction, Frege proofs, and equality reasoning, and demonstrate elaboration of implicit certificates into explicit ones checkable by a minimal kernel [9]. Blanco, Chihani, and Miller showed the elaboration/distillation round-trip can be automated as paired-certificate checking, so that one simple checker transitively vouches for provers with wildly different native evidence formats [9].

Taken together, the three programs supply complementary existence proofs: LFSC shows certificate checking can keep pace with industrial SMT solvers; Dedukti shows one kernel can absorb the proof libraries of a dozen mutually incompatible provers; FPC shows certificate *semantics* can be defined once, proof-theoretically, for nearly any evidence format in first-order logic.

## 6 Limitations

**LFSC: the side-condition trust gap.** LFSC's greatest strength — executable side conditions — is also its principal trust liability. Side-condition code is part of the trusted base *per signature*: a bug in a solver-specific `resolve-clauses` implementation is a soundness bug in every proof checked under that signature. The interpreted evaluator is small and auditable, but the compiled path (`--compile-scc`) enlarges the trusted base to include a C++ toolchain [12]. Moreover, each SMT solver effectively needs its own signature mirroring its solving algorithm, so the "universal" ambition is bounded by signature-engineering effort [6].

**Dedukti: convergence is the user's problem.** Dedukti's kernel is admirably small, but decidability of typechecking rests on properties — confluence, termination, product injectivity — that the checker does not verify [7]. A non-confluent rewrite system can make the checker accept invalid proofs *without any kernel bug*, because the kernel's soundness theorem assumes convergence. Faithfulness of encodings (does the `.dk` development really capture HOL's semantics?) is likewise external. These are not flaws so much as deliberate trust-boundary choices, but they mean Dedukti's de Bruijn story is conditional: *if* the rewrite system is convergent and the encoding faithful, *then* checking is sound.

**FPC: reconstruction cost and checker sophistication.** FPC minimizes the kernel but maximizes the checker's *algorithmic* sophistication: even the "simple" focused-sequent kernel must implement unification, focusing discipline, and bounded search [9]. Checking an implicit certificate can be as expensive as proving the theorem, and adversarial or merely sloppy certificates can send the checker into expensive search. The framework's first-order restriction also leaves higher-order evidence — the native language of Coq and HOL — without a canonical FPC treatment.

**Shared limitations.** All three inherit two irreducible gaps. First, the *formalized claim* is trusted: a perfect checker validating a proof of the wrong safety policy, or of a mistranslated theorem statement, proves nothing of value [2][10]. Translation validation for satellite tools remains an open engineering problem. Second, there is an economic dimension Miller makes explicit: proof checking at scale consumes real computational resources, and libraries that archive checked certificates become trust bottlenecks whose compromise is catastrophic [10]. The de Bruijn criterion shrinks trust; it does not eliminate it.

---

## 7 Conclusion

No single framework dominates on all axes, and the honest assessment is that the de Bruijn criterion is a *regulative ideal* rather than a finish line: each system draws its trust boundary in a different place — executable code, equational theories, or search bounds — and each leaves the formalized claim itself outside the boundary. The research frontier is *compositional* trust: verified translators, translation validation, and certificate-preserving compilation that let a proof checked by one kernel be rechecked by another. When the network of provers Miller envisioned [10] finally exists, it will be held together not by any single checker, but by certificates whose meaning no single system owns.
