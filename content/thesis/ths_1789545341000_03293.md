# Ownership, Borrowing, and Lifetimes: The Rust Type System, Affine Resources, and the Stacked Borrows Model

## Abstract

Rust achieves memory safety without garbage collection through a static discipline of ownership, borrowing, and lifetimes — a discipline best understood as an affine type system layered over a flow-sensitive borrow checker. This article presents the discipline from first principles and from the perspective of the formal models that justify it. We trace the affine treatment of resources — moves that transfer ownership, borrows that grant temporary shared or exclusive access, and lifetimes that bound the validity of those borrows — through the variance and outlives relations of the type system, the non-lexical lifetime analysis over the Mid-level Intermediate Representation, and the Datalog-derived Polonius engine that is replacing it. We then turn to unsafe code, where the borrow checker cannot reach, and examine the Stacked Borrows and Tree Borrows operational models that define which aliasing patterns constitute undefined behavior. We survey the mechanized soundness results, the empirical validation of these models against the standard library through the Miri interpreter, and the open problems that remain before the aliasing model can be declared final.

##1 Introduction

Memory safety without a garbage collector is one of the oldest ambitions in programming-language design. Manual memory management in C and C++ exposes dangling pointers, use-after-free errors, and data races; automatic management in Java or Go eliminates these hazards at the price of a runtime collector and its attendant pauses. Rust occupies the narrow ground between the two: the compiler statically proves that every program is free of dangling pointers and data races, while the generated code contains no collector, no runtime borrow accounting, and no mandatory reference counting.

The mechanism is a triple discipline. *Ownership* assigns every value to exactly one owner. *Borrowing* permits temporary, scoped access to a value without transferring ownership. *Lifetimes* are the compiler's static approximation of the regions of the program during which a borrow remains valid. Together these rules form what is recognizably an **affine type system**: a value of affine type may be used at most once along any execution path, so moving a value consumes it and the source binding becomes unusable.

The static analysis is not merely a safety net. Because the type system imposes a strict discipline on pointer aliasing, the compiler aspires to exploit that alias information for optimization: two accesses that cannot alias may be freely reordered, and loads may be hoisted across unknown function calls [1]. This ambition creates a contract. Unsafe code — the explicitly marked escape hatch through which raw pointers, foreign calls, and manual memory management enter the language — must still respect the aliasing discipline, or the optimizations the compiler performs on its authority become miscompilations. The question "what aliasing is legal in unsafe Rust?" therefore has the force of a language specification, and answering it required building operational models of memory access from scratch [1][2].

This article develops the full picture. Section 2 reviews the theoretical lineage of affine and linear types and region-based memory. Section 3 describes our method: a staged presentation from core calculus to borrow-checker constraints to operational aliasing models, each stage anchored in mechanized or empirical evidence. Section 4 works through the ownership discipline in depth — affine resources, the borrow rules, lifetimes and variance, the non-lexical lifetime analysis and its Polonius successor, and the Stacked Borrows and Tree Borrows models for unsafe code. Section 5 presents the soundness theorems and the empirical record: Coq-mechanized proofs, the Miri interpreter's validation of the standard library test suite, and a large-scale study of undefined behavior across foreign-function boundaries [3][4]. Section 6 turns to limitations and open problems, and Section 7 concludes.

##2 Background

The idea that types can track *use* as well as *shape* originates with Girard's linear logic and its affine fragment. In a linear type system, every value must be used exactly once; in an **affine** system, every value may be used *at most* once — weakening is permitted, contraction is not. Wadler showed that linear types can express resource protocols, including explicit memory management, without a collector. Rust's ownership is the affine idea industrialized: a non-`Copy` value has an affine type, and moving it is the single permitted use of the source binding.

Region-based memory management, explored in the ML Kit and in Cyclone, introduced the complementary idea of *lifetimes*: memory is partitioned into regions, each region is deallocated at a single program point, and the type system ensures no pointer outlives its region. Rust's lifetimes generalize regions from allocation arenas to arbitrary borrows: a lifetime is the set of program points during which a borrow is live, and the borrow checker verifies that no use of the borrow escapes that set.

The borrow checker itself evolved. The original lexical analysis tied borrows to syntactic scopes; a borrow lasted until the end of its enclosing block. Non-lexical lifetimes (NLL), which shipped in Rust 2018, moved the analysis to the Mid-level Intermediate Representation (MIR): a borrow is live only between the program points where it might actually be used, as determined by a liveness computation over the control-flow graph [7]. The current frontier is **Polonius**, a reformulation of the borrow check as a Datalog program over *loans* and *origins*, which computes borrow validity with full flow sensitivity at the statement level [5][7]. As of August 2026, a reformulated Polonius Alpha runs on nightly builds ahead of stabilization [5].

Finally, none of the static machinery reaches into `unsafe` blocks. Raw pointers (`*const T`, `*mut T`) carry no lifetime, no borrow discipline, and no aliasing contract from the type system. The Stacked Borrows project [1][2] supplied the missing contract: an operational semantics in which every memory location carries a *stack* of borrows, accesses pop incompatible entries, and using a popped borrow is undefined behavior. Its successor, **Tree Borrows**, replaces the stack with a tree of permissions to admit more real-world unsafe patterns [3][4].

##3 Methodology

We present the discipline in four stages, each tied to the evidence that justifies it.

**Stage 1 — Core calculus.** We describe ownership as an affine resource calculus: typing judgments carry a resource context, moves consume bindings, and borrows introduce scoped, tracked aliases. This stage is justified by the type-safety results of the RustBelt program logic, which gives a semantic model of Rust types in Iris and proves that well-typed safe code cannot go wrong.

**Stage 2 — Borrow-checker constraints.** We lift the calculus to the compiler's actual analysis: MIR control-flow graphs, loans (the creation of a borrow), origins (the inference variables standing for lifetimes), and the liveness-based NLL formulation together with the Datalog rules of Polonius. The evidence here is the compiler implementation itself and the Polonius test suite, including the long-standing "problem case" programs that NLL rejects and Polonius accepts [5].

**Stage 3 — Operational aliasing models.** For unsafe code we present Stacked Borrows and Tree Borrows as instrumented operational semantics: each memory access is checked against per-location borrow metadata, and violations are defined as undefined behavior. These models are validated in two directions — mechanized Coq proofs that they justify the desired compiler optimizations [1], and the Miri interpreter, which implements the models and runs large portions of the standard library test suite to confirm that real-world unsafe code is accepted [1][3].

**Stage 4 — Empirical record.** We survey the measured record: the Coq proof developments, Miri's standard-library validation, a study finding 46 instances of undefined or undesired behavior in 37 crates at foreign-function boundaries [3], and the ongoing effort to verify unsafe programs against the aliasing rules with separation logics [4].

> **Lemma: (Borrow exclusivity).** At any program point, for any live memory place, either exactly one live mutable borrow exists and no other borrow of that place is live, or arbitrarily many live shared borrows exist and no mutable borrow of that place is live. This invariant is the static counterpart of a compile-time reader–writer lock [6].

##4 The Ownership Discipline: A Deep Dive

###4.1 Affine Resources and Move Semantics

Every value in Rust has exactly one *owner* — the binding that controls its lifetime. When the owner goes out of scope, the value is dropped: its destructor runs and its storage is reclaimed. Ownership can be transferred by *moving*:

```rust
let s = String::from("affine");
let t = s;              // move: ownership of the string transfers to t
// println!("{}", s);    // ERROR: use of moved value
```

After the move, `s` is statically unusable. This is the affine rule made concrete: the binding `s` had its single permitted use, and the type system consumed it. Types implementing `Copy` — machine integers, booleans, shared references — are exempt; copying them is a duplication rather than a move, analogous to the exponential modality of linear logic marking duplicable resources.

The discipline extends to function calls and returns. Passing a `String` to a function by value moves ownership into the callee; returning a value moves it to the caller. The compiler therefore tracks a *moved-from* state for every binding along every path, and the NLL liveness analysis treats a move as a kill of the source. Drop order is deterministic — reverse declaration order within a scope — so resource cleanup composes predictably, and types with destructors cannot be `Copy`, since implicit duplication would double-run a destructor.

| Operation | Effect on source binding | Effect on destination |
|---|---|---|
| Move (`let t = s`) | Consumed; statically dead | Becomes sole owner |
| Copy (`let t = s` for `Copy` types) | Remains live | Independent duplicate |
| Shared borrow (`&s`) | Remains live; frozen against mutation | Temporary read access |
| Mutable borrow (`&mut s`) | Remains live; inaccessible except via borrow | Temporary exclusive access |
| Drop (end of owner scope) | Binding ends; destructor runs | Storage reclaimed |

###4.2 The Borrow Rules and Reborrowing

Borrowing grants temporary access without ownership transfer. A shared borrow `&T` permits reading through any number of aliases; a mutable borrow `&mut T` permits reading and writing through exactly one alias. The compiler enforces the reader–writer discipline statically, which is why the borrow checker is routinely described as a compile-time reader–writer lock [6].

Reborrowing refines the picture. Writing `let r2 = &mut *r1` does not create an independent borrow; it creates a borrow *derived from* `r1`, and `r1` is frozen until `r2`'s last use. This derivation structure is exactly what the operational aliasing models later reify as borrow stacks and permission trees [1][3]:

```rust
let mut x = 0;
let r1 = &mut x;
let r2 = &mut *r1;   // reborrow: r1 is frozen while r2 is live
*r2 += 1;
// r1 usable again only after r2's last use
*r1 += 1;
```

Two-phase borrows handle a subtle case: in `v.push(v.len())`, the autoref `&mut v` for the method receiver must be created before `v.len()` is evaluated, but it must not conflict with the shared borrow inside the argument. The compiler therefore splits the borrow into a *reservation* phase and an *activation* phase; the mutable borrow activates only after the arguments are evaluated. This reservation/activation split reappears, remarkably, in Tree Borrows as the `Reserved` permission state [3][6].

###4.3 Lifetimes, Variance, and the Outlives Relation

A lifetime `'a` names a region of the program — the set of points during which some borrow is live. The borrow checker reduces lifetime correctness to *outlives* constraints: `'a: 'b` requires that region `'a` contain region `'b`, i.e., every point in `'b` is also in `'a`. A reference `&'a mut T` is valid only if the referent outlives `'a`; the compiler proves this by solving the outlives constraints generated during type checking.

Variance determines how subtyping flows through type constructors. `&'a T` is *covariant* in `'a`: a longer-lived shared reference may be used where a shorter-lived one is expected, because shrinking the permitted region is always safe. `&'a mut T` is *invariant* in both `'a` and `T`: neither lengthening nor shortening is permitted, because a mutable reference supports both reads and writes, and either direction of subtyping would admit an unsound coercion. `Cell<T>`-style interior mutability likewise forces invariance. These variance rules are not arbitrary; they are the precise conditions under which the outlives relation remains sound in the presence of mutation.

Higher-ranked trait bounds (`for<'a>`) quantify lifetimes universally, letting functions accept references of any lifetime — the mechanism behind closures and iterator adapters that must work for borrows the caller has not yet created.

###4.4 From Non-Lexical Lifetimes to Polonius

NLL computes, for each MIR program point, the set of live loans; a borrow is an error only if a conflicting use occurs at a point where the loan is live. This flow sensitivity accepts programs the old lexical analysis rejected:

```rust
let mut v = vec![1, 2, 3];
let r = &v[0];
// ... no use of r here ...
v.push(4);      // OK under NLL: r is dead at this point
println!("{}", r); // last use of r
```

But NLL's liveness formulation is flow-*insensitive* in one crucial dimension: outlives relationships are computed without regard to where in the control flow they are needed. The canonical failure is the `get_mut_or_default` pattern, in which a borrow returned on one branch is wrongly considered live on the other branch, so a subsequent mutation is rejected [5]. Polonius reformulates the analysis in Datalog over loans and origins with full statement-level flow sensitivity, and accepts the program: it knows the borrow is not live in the `None` branch. The original Datalog implementation proved too slow for production, but the reformulated **Polonius Alpha**, a native rustc implementation requiring only minimal re-architecture of the NLL pipeline, was enabled on nightly in August 2026 ahead of stabilization [5].

###4.5 Stacked Borrows and Tree Borrows: Aliasing Models for Unsafe Code

Unsafe code can create arbitrary aliasing through raw pointers, so the compiler needs a *dynamic* statement of the aliasing rules — a definition of which executions count as well-defined, against which optimizations can be judged. **Stacked Borrows** [1][2] gives each memory location a *stack* of borrow items. Creating a reference pushes an item (`Unique` for `&mut`, `SharedReadOnly` for `&`, `SharedReadWrite` for two-phase reservations); each access must be granted by the item on top of the stack, and an access incompatible with items above pops them. Using a popped borrow afterward is undefined behavior:

```rust
let mut x = 0;
let p1 = &mut x as *mut i32;  // push Unique(p1)
let p2 = &mut x;              // push Unique(p2) above p1
unsafe { *p1 = 1; }           // ERROR under Stacked Borrows:
                              // p2's creation popped p1
```

The model was mechanized in Coq and proven strong enough to justify reordering memory accesses around unknown function calls using only intraprocedural reasoning; it was also implemented in the Miri interpreter, which ran large parts of the standard-library test suite to confirm that real unsafe code is accepted [1].

Experience showed Stacked Borrows to be too strict: it rejects unsafe patterns that the community considers legitimate, particularly around reborrowing through raw pointers.

##5 Empirical Results and Theoretical Proofs

The Stacked Borrows development is unusual among language-design proposals in being validated in both directions — by proof and by execution.

> **Theorem: (Stacked Borrows justifies intraprocedural optimization).** For any program that is valid under the Stacked Borrows instrumented semantics, every execution of the instrumented semantics coincides with the uninstrumented semantics, and a compiler may reorder memory accesses around unknown code and function calls using only intraprocedural alias reasoning. Mechanized in Coq [1][2].

The proof proceeds by showing that the borrow stack is a sound abstraction of the borrow checker's aliasing guarantees: any access the optimizer assumes non-aliasing is one the model would flag as a violation if it did alias. The practical consequence is the license for LLVM-level `noalias` annotations on Rust references — the optimization that motivated the entire project.

Miri provides the empirical complement. As an interpreter for MIR instrumented with the aliasing models, Miri executes real Rust code — including the standard library test suite — and reports any Stacked Borrows or Tree Borrows violation as undefined behavior [1][3]. This caught genuine bugs: the foreign-function-boundary study ran Miri jointly with an LLVM interpreter across widely used crates and found 46 instances of undefined or undesired behavior in 37 libraries, including crates with more than ten thousand daily downloads and one maintained by the Rust Project itself [3]. The study's three violation categories — expired permissions, insufficient permissions, and framing errors — give unsafe-code authors a concrete taxonomy of mistakes.

| Model | Metadata per location | Key mechanism | Strictness |
|---|---|---|---|
| Stacked Borrows [1][2] | Stack of borrow items | Conflicting access pops items above | Strict; rejects some accepted unsafe idioms |
| Tree Borrows [3][4] | Tree of permission nodes | Child vs. foreign access state machine | More permissive; still catches real bugs |

On the static side, the Polonius program has its own empirical record. The Datalog formulation was studied over tens of thousands of public repositories: roughly sixty percent of functions create no references at all and need almost none of the analysis, and control-flow-graph size correlates most strongly with solver time [7]. Polonius Alpha's nightly rollout is accompanied by crater runs checking for regressions across the ecosystem before stabilization [5].

##6 Limitations and Open Problems

The aliasing model remains, officially, unfinished. Neither Stacked Borrows nor Tree Borrows has been ratified as *the* definition of undefined behavior for unsafe Rust; the Unsafe Code Guidelines working group continues to deliberate, and Tree Borrows is described even by its proponents as a candidate gaining traction rather than a final answer [4]. Any unsafe code written today is therefore checked against a model that may yet be relaxed — or, in corner cases, tightened.

Several technical gaps persist. Self-referential types remain inexpressible in safe Rust and require the `Pin` API plus careful unsafe reasoning, because a borrow of a value that owns its own referent cannot be described by the outlives relation. The interaction of the aliasing models with compiler optimizations beyond simple reordering — vectorization, speculative loads — is only partially explored. Polonius Alpha, while dramatically more capable than NLL, is not a superset of the original Datalog Polonius: programs exist that each accepts and the other rejects [5], and solver performance on pathological inputs remains a stabilization risk. Verification tooling lags the models: separation logics for Tree Borrows compliance are under active development but incomplete, and existing verifiers for unsafe Rust largely ignore the aliasing rules and are therefore unsound with respect to them [4].

Finally, there is no complete formal specification of Rust. The language is defined by its reference manual, its test suite, and the behavior of rustc — an unusually rigorous trinity, but not a substitute for a mechanized language definition against which the borrow checker, Polonius, and the aliasing models could all be proven coherent.

##7 Conclusion

Rust's ownership discipline is a rare thing in production languages: an affine type system, enforced by a flow-sensitive static analysis, that delivers memory safety without runtime cost. The borrow rules — exclusive mutable access or shared read-only access, never both — are simple to state; their enforcement across lifetimes, variance, reborrowing, and two-phase borrows is anything but. NLL made the analysis practical, Polonius is making it precise, and the Stacked Borrows and Tree Borrows models extend the discipline's guarantees into unsafe code, where they double as the specification of undefined behavior that justifies the optimizer.

The through line is a single idea: *aliasing is a resource, and resources must be accounted for*. Whether the accounting is static, in the borrow checker's loans and origins, or dynamic, in Miri's borrow stacks and permission trees, the discipline is the same. The open problems — ratifying the aliasing model, completing the verification story, specifying the language — are substantial, but they are problems of finishing a foundation, not of finding one.
