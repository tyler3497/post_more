# LLM Inference Serving Systems: Continuous Batching, PagedAttention, Speculative Decoding, and Disaggregated Prefill–Decode

## Abstract

## 1 Introduction

The deployment of large language models as interactive services — chatbots, code assistants, search engines, agentic workflows — has transformed inference serving into a first-class distributed systems discipline. The central difficulty is deceptively simple to state: LLM inference is *autoregressive*, meaning that generating K tokens requires K serial forward passes of the model [1][3], and each pass must read the entire weight tensor from high-bandwidth memory (HBM). For a 70B-parameter model at FP16, that is roughly 140 GB of memory traffic per generated token; even at 3 TB/s of HBM bandwidth, the arithmetic intensity of single-token decode is bounded by the roofline to a small fraction of the GPU's peak FLOPS [6].

Two consequences follow. First, serving is **memory-bound**, not compute-bound, during decoding — GPU utilization during decode is notoriously low because each token touches all weights but performs little arithmetic per byte moved. Second, the system must manage a *dynamic* memory structure, the **KV cache**, whose size per request is unknown at arrival time and grows by exactly one slot per generated token. These two facts interact: to amortize the memory-bandwidth cost of weight reads, the system wants large batches (many tokens per weight read), but large batches require memory capacity for many growing KV caches, and the caches' unpredictability makes naive reservation schemes catastrophically wasteful.

The four systems-level ideas examined in this thesis address these problems from complementary angles:

## 2 Background

### 2.1 The Two Phases of LLM Inference

Every serving request passes through two phases with sharply different resource signatures [6]:

| Phase | Input per step | Work character | Bottleneck | Latency metric |
|---|---|---|---|---|
| **Prefill** | Entire prompt (L tokens) | Parallel matrix–matrix multiply | Compute (FLOPS) | Time-to-first-token (TTFT) |
| **Decode** | Single token + KV cache | Matrix–vector per token per layer | Memory bandwidth (HBM) | Time-per-output-token (TPOT) |

*Prefill* processes the whole prompt in one parallel pass, building the KV cache for every layer, and emits the first output token. Because all L prompt tokens are processed simultaneously, prefill achieves high arithmetic intensity and saturates GPU compute even at modest batch sizes [6]. *Decode* then generates one token per iteration, reusing the KV cache so that each step only attends to the new token. This is the phase that dominates cost in long generations: the weights must be streamed once per token, so decode throughput is fundamentally capped by $\text{bandwidth} \times \text{tokens per weight read}$.

> **Theorem (Batching amortization):** In the memory-bound decode regime, per-token latency is approximately $W / (\beta \cdot B)$, where $W$ is the model weight size in bytes, $\beta$ is memory bandwidth in bytes/second, and $B$ is the number of requests in the decode batch. Hence throughput scales with batch size until the KV cache capacity or compute limits bind.

This theorem — a direct consequence of the roofline model — explains why batching is the central lever of serving systems and why *memory management* (which determines the maximum feasible B) is the central bottleneck.

### 2.2 The KV Cache and Its Memory Dynamics

For a model with $n$ layers, $h$ attention heads, head dimension $d$, and a sequence of length $s$, the KV cache stores $2 \cdot n \cdot h \cdot d \cdot s$ values. At FP16 for LLaMA-13B with $s = 2048$, this exceeds several gigabytes per request [2]. Crucially, $s$ is **unknown at arrival**: the final length depends on the model's own generation. Pre-allocating for the worst case ($s_{\max}$) wastes the difference $s_{\max} - s_{\text{actual}}$ for every request; pre-allocating exactly and reallocating on overflow fragments memory and copies data.

Early serving systems (e.g., the request-level batch scheduler of FasterTransformer) suffered compounding pathologies [2]: **internal fragmentation** (reserved-but-unused cache slots), **external fragmentation** (free memory scattered in unusable fragments), and **no sharing** (beam search storing a full independent copy of the shared KV cache per branch). The net effect, measured by Kwon et al., was that only 20.4–38.2% of reserved KV-cache memory held useful data [2].

### 2.3 Service-Level Objectives and Goodput

Serving quality is judged by per-phase latencies, not aggregate throughput alone [5][7]: **TTFT** (time to first token, dominated by prefill queueing plus compute), **TPOT/TBT** (time per output token, the cadence of decode steps), and **goodput** — the requests (or tokens) served *within* their TTFT/TPOT SLOs per unit time [5]. A system maximizing raw tokens/second while violating tail latency has low goodput. The tension between throughput and latency is the fundamental scheduling tradeoff of this thesis [7].

## 3 Methodology

Our method is analytical and evidence-based: we reconstruct each technique's design from its primary publication, formalize the mechanism as a performance model, and derive the claimed speedups from first principles so that the empirical numbers reported by the authors are *explained*, not merely repeated.

**System model.** We consider a cluster of GPUs serving a Poisson (or trace-driven) arrival process of requests with prompt lengths $L_i$ and output lengths $O_i$ drawn from heavy-tailed distributions. Each GPU has compute capacity $C$ FLOPS, memory bandwidth $\beta$, and HBM capacity $M$ split between weights $W$, KV cache $K(t)$, and activations $A(t)$. The scheduler operates at *iteration granularity*: each iteration executes one model forward pass over the current batch, and requests may join or leave at iteration boundaries.

**Notation.**

- $B(t)$: number of requests in the batch at iteration $t$
- $b$: PagedAttention block size (tokens per KV block)
- $p(x)$: target model distribution; $q(x)$: draft model distribution
- $\alpha$: expected number of tokens accepted per speculative verification round
- $\gamma$: number of draft tokens proposed per round
- $c$: chunk size in chunked prefill
- $G$: goodput (SLO-satisfying requests per second)

**Verification of sources.** All performance figures cited are taken from the primary papers' evaluation sections on commodity hardware (A100/A6000 GPUs) and standard models (OPT, LLaMA, GPT-3); we reproduce the authors' headline numbers and identify the mechanism responsible for each.

## 4 Deep Dive

### 4.1 Continuous Batching: Iteration-Level Scheduling

Conventional *static batching* groups $B$ requests, runs them together, and admits new requests only when **all** $B$ finish — the "generation straggler" problem: if one request generates 512 tokens while another generates 8, the GPU idles on the short request's slots for the remaining 504 iterations, or worse, cannot admit queued work at all.

**Orca** (Yu et al., OSDI '22) replaced request-level with **iteration-level scheduling** [1]: at every iteration boundary, finished requests are evicted and waiting requests are admitted into the running batch. The batch is thus a dynamic set whose membership changes each step. Key design elements:

> **Theorem (Straggler elimination):** Under iteration-level scheduling with immediate refill, the expected idle slot-iterations per batch converge to zero as the arrival queue stays non-empty, independent of the output-length distribution.

In practice, memory (not the queue) becomes the binding constraint — which motivates the next technique.

### 4.2 PagedAttention: Virtual Memory for the KV Cache

PagedAttention (Kwon et al., SOSP '23) observes that the KV cache is exactly the kind of dynamically-sized, per-request structure that operating systems manage with **paging**, and imports the abstraction wholesale [2]. The KV cache of each sequence is divided into fixed-size *blocks* of $b$ tokens (e.g., $b = 16$). Blocks need not be contiguous in physical GPU memory; a per-sequence **block table** maps logical block indices to physical block IDs, and a **block manager** maintains free lists and reference counts:

```python
# PagedAttention block manager (simplified)
class BlockManager:
    def __init__(self, num_blocks: int):
        self.free_blocks = list(range(num_blocks))
        self.refcount = [0] * num_blocks

    def allocate(self, seq):
        # logical block i -> physical block, allocated lazily
        phys = self.free_blocks.pop()
        self.refcount[phys] = 1
        seq.block_table.append(phys)

    def append_slot(self, seq):
        # new token needs a new slot only when current block is full
        if seq.num_tokens % BLOCK_SIZE == 0:
            self.allocate(seq)

    def share(self, src_seq, dst_seq):
        # beam search / parallel sampling: share, don't copy
        for phys in src_seq.block_table:
            self.refcount[phys] += 1
        dst_seq.block_table = list(src_seq.block_table)

    def copy_on_write(self, seq, phys):
        # on divergence, copy only the diverging block
        if self.refcount[phys] > 1:
            new = self.free_blocks.pop()
            copy_kernel(phys, new)
            self.refcount[phys] -= 1
            self.refcount[new] = 1
            return new
        return phys
```

Three properties follow [2]:

- **Near-zero fragmentation.** Memory is allocated in block granularity as sequences grow; no request reserves $s_{\max}$ upfront. Measured waste falls from 60–80% to under 4% of allocated memory.
- **Memory sharing.** Sequences sharing a prompt prefix (parallel sampling, beam search) share physical blocks with reference counting; on divergence only the divergent blocks are copied (**copy-on-write**), yielding up to 55% memory savings on beam search.
- **Flexible scheduling.** Because allocation is dynamic, the scheduler can admit requests opportunistically and even *preempt* low-priority sequences by swapping their blocks to CPU memory, then resume them — enabling priority scheduling and preemption without data loss.

The attention kernel itself is rewritten to walk the block table (gathering scattered blocks), fusing naturally with the memory-efficient tiling of FlashAttention-style kernels. The headline result: vLLM achieves **2–4× the throughput** of FasterTransformer and Orca at equal latency, with the gap widening for longer sequences and larger models — precisely where KV memory dominates [2]. The implementation is open source and has become the industry standard substrate [8].

### 4.3 Speculative Decoding: Parallelizing the Serial

Speculative decoding (Leviathan et al., ICML '23; independently Chen et al. as *speculative sampling*) attacks the *other* fundamental limit: the seriality of autoregressive generation [3][4]. The insight is borrowed from speculative execution in processors: a cheap **draft model** $M_q$ proposes $\gamma$ candidate tokens quickly, and the expensive **target model** $M_p$ **verifies all $\gamma$ candidates plus one bonus token in a single parallel forward pass**. A novel rejection-sampling rule guarantees the accepted prefix is distributed *exactly* as $p(x)$ — the output distribution is bit-for-bit identical to target-only decoding [3]:

```python
def speculative_round(prefix, draft, target, gamma):
    # 1. draft gamma candidates autoregressively (cheap)
    drafts = [draft.sample(prefix + drafts) for _ in range(gamma)]
    # 2. target scores all positions in ONE parallel pass
    logits = target(prefix + drafts)  # gamma+1 distributions
    accepted = []
    for i, x in enumerate(drafts):
        r = random.random()
        # accept with probability min(1, p_i(x)/q_i(x))
        if r < min(1, p(logits[i], x) / q(draft_logits[i], x)):
            accepted.append(x)
        else:
            accepted.append(sample(residual(p(logits[i]) - q(draft_logits[i]))))
            return prefix + accepted  # reject rest
    # all accepted: bonus token from the last distribution
    accepted.append(sample(p(logits[gamma])))
    return prefix + accepted
```

The expected number of tokens produced per target-model call grows with $\alpha = \mathbb{E}[\text{accepted}]$, which depends on how well the draft approximates the target. With a well-aligned draft ($\alpha \approx 3$–$4$ for $\gamma = 5$) and cheap draft calls, one obtains the **2–3× end-to-end acceleration** measured on T5-XXL [3]. The acceptance rate is the critical parameter: it degrades as temperature rises and as the draft/target capability gap widens. Variants replace the separate draft model with the target model's own early exits, n-gram caches, or retrieval from prompt context (*prompt lookup decoding*), trading draft quality against deployment simplicity [4].

Crucially, speculative decoding is **orthogonal** to batching and paging: vLLM and others integrate it atop PagedAttention, and the verification pass itself benefits from continuous batching since unverified candidates of different requests share the same iteration structure.

### 4.4 Disaggregated Prefill–Decode and Chunked Prefills

The final technique addresses *phase interference*. Prefill is compute-bound and latency-sensitive (TTFT); decode is memory-bound and cadence-sensitive (TPOT). Colocating them means a long prompt's prefill iteration stalls every in-flight decode — a TPOT spike — while decode-heavy batches leave compute units idle. Two architectural answers have emerged.

**Disaggregation (DistServe).** Zhong et al. assign prefill and decode to **separate GPU pools** [5]. Each pool is provisioned and parallelized independently: prefill instances favor parallelism tuned for TTFT; decode instances favor configurations maximizing tokens-per-second-per-GPU under TPOT constraints. After prefill, the request's KV cache is transferred to a decode instance over the cluster interconnect — a cost shown to be insubstantial on modern fabrics relative to generation time. A placement optimizer co-designs GPU allocation, parallelism strategy, and instance placement against the TTFT/TPOT SLOs to maximize **goodput**, yielding up to **7.4× more requests** served within SLOs (12.6× tighter achievable SLOs) versus colocated systems [5].

**Chunked prefills (Sarathi / Sarathi-Serve).** Agrawal et al. offer a colocated alternative: split each prompt into fixed-size **chunks** of $c$ tokens and build *decode-maximal batches* — one prefill chunk plus as many decode tokens as fit [6]. The chunk saturates compute while decodes *piggyback* nearly for free; uniform chunk sizes also balance pipeline-parallel micro-batches, cutting pipeline **bubbles by 6.29×**. Sarathi-Serve adds **stall-free scheduling** (new requests join without pausing decodes) and a token-budget knob trading TTFT against throughput under explicit SLOs [7]. Measured gains: up to **10× decode throughput** and 1.25–1.33× end-to-end on LLaMA models, and up to 6.9× serving throughput within SLOs for Falcon-180B on 8×A100 [6][7].

The two approaches compose a design spectrum: disaggregation pays KV-transfer and provisioning complexity for full phase isolation; chunked prefill keeps one pool and smooths interference by construction.

## 5 Empirical Analysis and Proofs

### 5.1 Where the Speedups Come From: A Unified Accounting

| Technique | Primary paper | Headline result | Mechanism (derived) |
|---|---|---|---|
| Continuous batching | Orca [1] | Foundation of 2–4× system gains | $\eta$: 1/B → ~1 under length variance |
| PagedAttention | vLLM [2] | 2–4× throughput @ equal latency | Waste 60–80% → <4%; B grows 2–4× |
| Speculative decoding | Leviathan et al. [3] | 2–3× latency, identical outputs | Serial calls → parallel verify; $S \approx \alpha{+}1$ |
| Disaggregation | DistServe [5] | 7.4× requests within SLO | Interference → 0; per-phase optimal provisioning |
| Chunked prefill | Sarathi [6] | 10× decode, 1.33× E2E throughput | Decode piggyback ≈ free; bubbles ÷ 6.29 |
| Stall-free scheduling | Sarathi-Serve [7] | 2.6–6.9× throughput within SLO | No decode pauses; token-budget SLO knob |

*Why PagedAttention's 2–4× is essentially forced.* From the batching-amortization theorem, decode throughput $\propto B$. Prior systems achieved only 20–38% useful memory, capping the feasible batch at roughly a third of what memory allows; PagedAttention's 96%+ useful memory roughly triples feasible $B$, with the largest gains for long sequences and large models where KV dominates HBM [2]. This is a capacity argument, so it composes multiplicatively with kernel improvements like FlashAttention.

*Why speculation's 2–3× has a ceiling.* The speedup $S(\alpha,\gamma)$ is concave in $\gamma$: more drafts raise $\alpha$ sublinearly (each additional draft token is conditioned on earlier, possibly-wrong drafts) while linearly increasing wasted verification work on rejection. The optimum $\gamma^*$ satisfies $\partial S/\partial \gamma = 0$, typically 3–7 in practice. Furthermore $\alpha$ is bounded by the draft–target total-variation distance: no draft can beat the entropy of $p$ itself. This yields a *hard ceiling* of roughly one target-call per $\alpha+1$ tokens — speculation converts latency, never total FLOPs.

*Why disaggregation wins on goodput, not raw throughput.* Colocated systems must choose per-iteration batch composition to satisfy both TTFT and TPOT; under tight SLOs they over-provision. Disaggregation decouples the two optimization problems, so each pool runs at its own roofline-optimal point. The 7.4× figure is a *goodput* ratio (requests within both SLOs), which is the economically relevant metric: raw token throughput ratios are smaller, because disaggregation adds KV-transfer bytes [5].

### 5.2 Composition and Interaction Effects

The techniques are largely orthogonal and compose:

1. **Orca + PagedAttention** = vLLM's core: iteration-level scheduling needs dynamic memory; paging provides it. Continuous batching without paging reintroduces admission blocking via fragmentation; paging without continuous batching leaves straggler idleness.
2. **+ Speculative decoding** = fewer serial target calls per token; verification batches piggyback on the same continuous-batch iterations.
3. **+ Disaggregation or chunked prefill** = resolves the prefill/decode interference that all batching schemes otherwise suffer.

The open-source vLLM stack [8] embodies (1)–(3) plus chunked prefill, which explains its dominance: it is the composition, not any single trick, that defines the Pareto frontier.

## 6 Limitations

**The memory wall persists.** PagedAttention eliminates *fragmentation* waste, not the KV cache itself. Cache bytes still grow linearly in sequence length, layers, and batch size; at 128K–1M token contexts, the cache dwarfs weights and no paging scheme changes the arithmetic. Compression (quantization, eviction, MLA-style latent caches) is the necessary complement, and it trades quality for capacity.

**Speculation's acceptance ceiling.** As argued in §5.1, $\alpha$ is bounded by draft–target divergence and target entropy. At high sampling temperatures, acceptance collapses and speculation can *slow down* serving (verification work wasted). Draft-model serving also consumes memory and scheduling complexity of its own; the "free lunch" requires a well-aligned, cheap draft.

**Disaggregation fragility.** DistServe's gains assume the prefill/decode load ratio matches provisioning. Real workloads skew: a burst of long prompts idles decode GPUs; a burst of long generations idles prefill GPUs. Rebalancing requires request migration or elastic pools, and KV transfer, while "insubstantial" on NVLink fabrics, becomes a real cost across slower interconnects or very large caches [5].

**Scheduling complexity and tail risk.** Iteration-level schedulers with preemption, chunking, and speculation are intricate concurrent systems. Preemption decisions, token-budget tuning, and draft-length selection are all workload-dependent; misconfiguration converts theoretical gains into tail-latency regressions. The systems remain harder to operate than the static batchers they replaced.

**Evaluation generality.** Headline numbers come from specific model/hardware/workload triples (e.g., OPT-13B on A100, ShareGPT traces). Heavy-tailed production traffic, multi-LoRA serving, and prefix-heavy agentic workloads shift the bottlenecks; no single paper's ratio transfers verbatim.

## 7 Conclusion

LLM inference serving has matured from naive static batching into a principled systems discipline built on four pillars. **Continuous batching** [1] removed the synchronization tax of variable-length generation. **PagedAttention** [2] removed the memory tax by treating the KV cache as pageable virtual memory, with copy-on-write sharing as a bonus. **Speculative decoding** [3][4] removed the seriality tax, trading cheap draft compute for parallel verification with provably identical outputs. **Disaggregated prefill–decode** [5] and **chunked prefills** [6][7] removed the interference tax between two phases that share nothing but the GPU. Each technique is grounded in a crisp performance argument — batching amortization, fragmentation elimination, speculative parallelism, phase isolation — and each is validated by multi-fold empirical gains on real hardware.

The trajectory points toward serving systems that look increasingly like operating systems: virtual memory for caches, speculative execution for latency, scheduling with explicit SLO economics, and disaggregated resources connected by fast fabrics. The remaining hard problems — the linear growth of the KV cache itself, the entropy bound on speculation, and robust provisioning under skewed, bursty, agentic workloads — are where the next 10× will come from.
