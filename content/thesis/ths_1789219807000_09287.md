# The Dynamic End of the Spectrum: Contracts, Blame Assignment, and the Gradual Guarantee in Gradually Typed Languages

## Abstract

Gradual typing reconciles the precision of static type checking with the flexibility of dynamic typing by introducing an unknown type ? and a notion of type consistency that mediates between them. This thesis studies the dynamic end of that spectrum: the boundary where statically checked code meets values that arrive unchecked, and where runtime contracts enforce the guarantees that static analysis cannot. We trace the lineage from Findler and Felleisen's higher-order contracts, through Siek and Taha's gradually typed lambda calculus, to the blame calculus of Wadler and Findler, in which failed casts are attributed to the less precisely typed party. The centerpiece is the gradual guarantee of Siek, Vitousek, Cimini, and Boyland: changing type annotations toward either greater or lesser precision must not alter program behavior except through the introduction of new static or dynamic errors. We examine how contracts implement casts, how blame subtyping sharpens accountability, how space-efficient coercions tame wrapper overhead, and where the theory still strains against polymorphism, state, and the cost of soundness.

## 1 Intro

The oldest unresolved negotiation in programming language design is the one between *static* and *dynamic* typing. Static types buy early error detection, checked documentation, and aggressive optimization; dynamic typing buys expressiveness, rapid prototyping, and the freedom to write programs that are correct yet fit no particular type discipline.

**Gradual typing** refuses that bargain. Introduced by Siek and Taha [1], it embeds both disciplines in a *single* language: an unknown type, written `?`, marks where checking is deferred to run time. A fully annotated program behaves like a statically typed one, a fully unannotated one like a dynamically typed one, and every point in between is *principled*: migration from dynamic to static is smooth, and guarantees degrade gracefully rather than collapse.

This thesis is about the *dynamic end* of that spectrum — the machinery that makes the dynamic parts safe rather than merely unchecked. Three ideas carry the load:

1. **Contracts.** Runtime monitors, derived from higher-order contracts, that enforce type-like invariants on values crossing from untyped to typed code.
2. **Blame.** A discipline of error attribution: when a contract fails, the system must identify which party — the typed side or the untyped side — is at fault. The blame theorem states that the more precisely typed side can *never* be blamed [2].
3. **The gradual guarantee.** The contract between language designer and programmer: making annotations more precise (or less precise) must not change program behavior except by introducing new static type errors or new dynamic cast errors.

Our claim is that these three ideas form a single coherent story: contracts are the *mechanism*, blame the *accountability*, and the gradual guarantee the *specification* of what the dynamic end owes the programmer. We develop this story formally, survey its empirical footprint in real languages, and identify the places where the theory still strains.

## 2 Background

**The two disciplines.** In a statically typed language, every expression has a type known before execution, and the type checker rejects programs it cannot prove safe. In a dynamically typed language, types are properties of *values* observed during execution, and mismatches surface as runtime failures. The first discipline prevents entire classes of errors but rejects some correct programs; the second accepts every program but detects errors late. The practical consequence is a *migration cliff*: moving a codebase from dynamic to static typing is an all-or-nothing rewrite, because the two disciplines share no common vocabulary. Gradual typing supplies that vocabulary.

**Siek and Taha's gradual lambda calculus.** The core device of [1] is the unknown type `?`, with a *consistency* relation, written `~`, that relaxes type equality. Where a static system demands `T1 = T2`, a gradual system demands only `T1 ~ T2`: equality *up to occurrences of* `?`. Thus `Int ~ ?` and `Int -> ? ~ ? -> Bool`, but `Int` is not consistent with `Bool`. Consistency is reflexive and symmetric but deliberately *not* transitive — `Int ~ ? ~ Bool` is the canonical counterexample. Elaboration inserts *casts* wherever consistency justifies a use: a cast `⟨T ⇐ S⟩ e` checks at run time that a value produced at type `S` may be viewed at type `T`. First-order casts become tag checks; higher-order casts become *wrappers* that interpose checks on every future interaction. This handoff from static discipline to dynamic enforcement is the point this thesis examines.

**Contracts and interlanguage migration.** Casts descend from Findler and Felleisen's higher-order contracts: a contract on `Int -> Int` checks the argument at call time and the result at return time, *blaming* the caller for a bad argument and the function for a bad result. Tobin-Hochstadt and Felleisen applied this machinery to the typed/untyped boundary in Typed Racket, proving that contract failures there are always attributable to the untyped module. Gradual typing's casts are contracts specialized to type-shaped specifications, with a static type system deciding where they are needed.

**The precision order.** Siek and Taha also introduced a *precision* relation `⊑`: `T1 ⊑ T2` when `T2` is `T1` with some `?` occurrences replaced by more informative types (`? ⊑ Int`, `? -> ? ⊑ Int -> Bool`). Precision extends pointwise to programs — the vocabulary in which the gradual guarantee is stated.

## 3 Methodology

Our method is standard programming-languages metatheory: fix a core calculus, prove its properties, then check them against real implementations and alternative semantic frameworks.

**The object calculus.** We work with the Gradually Typed Lambda Calculus (GTLC) of [1]: the simply typed lambda calculus extended with the unknown type `?` and consistency-based typing rules. A representative rule is application:

```text
Γ ⊢ e1 : T1      Γ ⊢ e2 : T2      T1 ▷ T11 -> T12      T2 ~ T11
────────────────────────────────────────────────────────────────
Γ ⊢ e1 e2 : T12
```

where `T ▷ U` means `T` is consistent with the function shape `U` (either `T = U` or `T = ?`, in which case the domain and codomain are both `?`). Elaboration translates GTLC into a *cast calculus* in which every consistency step becomes an explicit cast term `⟨T ⇐ S⟩^p e` carrying a blame label `p`.

**The properties under test.** We organize the investigation around the refined criteria for gradual languages [5]:

| Criterion | Informal statement | Section |
|---|---|---|
| Type safety | Well-typed programs do not get stuck; they reduce to values or blame | §4.2 |
| Conservative extension | Fully static programs behave as in the static language | §5 |
| Blame safety | Blame is never assigned to the more precisely typed party | §4.3 |
| Static gradual guarantee | Removing precision preserves typeability | §4.4 |
| Dynamic gradual guarantee | Removing precision preserves behavior modulo new errors | §4.4 |
| Space efficiency | Casts do not accumulate unboundedly at run time | §4.2, §6 |

**The semantic frameworks.** We contrast three approaches: the *cast-calculus* semantics of [1, 2], in which elaboration inserts explicit runtime checks; *abstracting gradual typing* (AGT) [3], which derives consistency, precision, and dynamic semantics from a static type system via abstract interpretation; and the *coercion* approach of [4], which normalizes casts for space efficiency. AGT is methodologically valuable: by constructing gradual artifacts as the *optimal abstraction* of their static counterparts, it turns historically ad hoc design choices into theorems.

## 4 Deep Dive

### 4.1 The Unknown Type and Consistency

The unknown type `?` is neither a top type nor a dynamic tag: it is a *placeholder for a static type not yet known*, with meaning given entirely by the consistency relation:

- `? ~ T` and `T ~ ?` for every type `T`;
- `B ~ B` for every base type `B`;
- `T1 -> T2 ~ S1 -> S2` whenever `T1 ~ S1` and `T2 ~ S2`;
- nothing else is consistent.

The following table records the relation's characteristic behavior:

| Pair | Consistent? | Why |
|---|---|---|
| `Int ~ ?` | Yes | `?` is consistent with everything |
| `? -> Int ~ Bool -> ?` | Yes | Componentwise: `? ~ Bool`, `Int ~ ?` |
| `Int ~ Bool` | No | Distinct base types |
| `Int -> ? ~ ?` | Yes | `?` absorbs any shape |
| `Int ~ ?` and `? ~ Bool`, but `Int ~ Bool` | — | Consistency is **not transitive** |

Non-transitivity is a feature, not a bug. If consistency were transitive, `?` would relate every type to every other type and the static discipline would evaporate. The absence of transitivity is also the source of genuine subtlety: a chain of individually consistent steps can connect inconsistent types, and the *dynamic* semantics must detect exactly those chains at run time. This is why casts are inserted at *every* consistency use rather than only at `?` boundaries — a cast from `Int` to `?` followed by a cast from `?` to `Bool` must each be checked, and the second must fail.

### 4.2 From Contracts to Casts: Runtime Enforcement

Elaboration turns static uncertainty into dynamic vigilance: wherever the derivation used consistency instead of equality, a cast is inserted. Casts reduce in three cases:

1. **First-order casts** (`⟨Int ⇐ ?⟩ v`) inspect the value's tag immediately: an integer passes, anything else raises blame.
2. **Higher-order casts** (`⟨T1 -> T2 ⇐ ?⟩ v`) check that `v` is a function and return a *wrapper* — a proxy that casts arguments contravariantly and results covariantly on every subsequent call.
3. **Identity and collapse** (`⟨T ⇐ T⟩ v` reduces to `v`; nested casts through `?` may collapse when the intermediate type is ground).

In Haskell-like pseudocode, a function-cast wrapper has the familiar shape of a higher-order contract:

```haskell
-- castFun : (s1 -> t1) -> (s2 -> t2) -> BlameLabel -> (s2 -> t2)
castFun domCast codCast p f = \x ->
  codCast p (f (domCast (neg p) x))
```

The argument cast runs with the *negated* blame label, exactly as in higher-order contracts: a bad argument blames the wrapper's caller, not the function. This polarity — positive blame for the term, negative for its context — is the bridge from contracts to the blame theorem.

Naive wrappers have a notorious cost. Consider mutually recursive `even`/`odd` where one is typed and the other is not [4]: each recursive call crosses the boundary and accumulates another wrapper, so a tail-recursive loop that should run in constant space grows the heap linearly — and can even break proper tail calls. The response of Herman, Tomb, and Flanagan is to represent casts as *coercions* in Henglein's style: coercion sequences are normalized at run time, so a tower of wrappers collapses into one and space efficiency is restored [4]. Siek and colleagues later showed that blame tracking survives this normalization, though the interaction is delicate [7].

### 4.3 Blame Assignment and the Blame Theorem

Every cast carries a *blame label* naming the party responsible if the cast fails. In `⟨T ⇐ S⟩^p`, positive blame `+p` falls on the term, negative blame `-p` on the demanding context; when a higher-order cast decomposes, polarities flip contravariantly, as in the `castFun` sketch, so blame flows toward the party that supplied the offending value.

Wadler and Findler [2] connected blame to *subtyping*. They decompose naive subtyping into *positive* and *negative* subtyping, show the two recombine to yield naive subtyping, and prove blame can only arise on the side marked less precise. The slogan, generalizing Milner's "well-typed programs can't go wrong," is:

> **Theorem:** *(Blame safety [2].)* In a well-typed program of the blame calculus, a cast failure `blame p` can only blame a label whose polarity points at the *less precisely typed* side of the cast. In particular, a fully statically typed component can never be blamed.

The philosophical content is worth stating plainly: blame safety is the *correctness criterion for the dynamic end of the spectrum*. One cannot guarantee that a cast between typed and untyped code will never fail — the untyped code may genuinely violate the specification. But one can guarantee that when it fails, the *typed* code is exonerated: the unknown is permitted, but never permitted to implicate the known.

Follow-up work showed that the space-efficient coercion semantics is fully abstract with respect to naive wrappers and that blame safety survives the translation [7]: efficiency and accountability are compatible.

### 4.4 The Gradual Guarantee

The gradual guarantee, formulated as a criterion by Siek, Vitousek, Cimini, and Boyland [5], is the statement that *type annotations do not change behavior* — they only change which errors are caught statically versus dynamically. It comes in two parts, both stated with respect to the precision relation `⊑`:

> **Theorem:** *(Static gradual guarantee.)* If `e ⊑ e'` and `e` is well-typed, then `e'` is well-typed. Equivalently, *removing* precision (replacing types by `?`) never introduces a static type error.

> **Theorem:** *(Dynamic gradual guarantee.)* If `e ⊑ e'` and `e` reduces to a value `v`, then `e'` reduces to the same value modulo the insertion of casts — unless the added precision introduces a new cast failure, in which case `e'` raises blame.

Together: start from a working dynamic program, add types, and it keeps working; if it breaks, the breakage is *informative* — a genuine inconsistency between the new annotations and actual behavior, surfaced by the type checker or a cast at run time. This is the formal backbone of the "smooth migration" story, and it is what distinguishes gradual typing from merely bolting a type checker onto a dynamic language: the two disciplines are *behaviorally coherent*, not merely cohabiting.

Proving the dynamic guarantee is the hard part. It requires relating the reductions of two programs that differ only in annotations — typically via a logical relation or bisimulation over the cast calculus — and it is sensitive to language features: mutable references, exceptions, and control operators each threaten it in instructive ways [5]. Notably, systems enforcing hyperproperties such as noninterference are known *not* to satisfy the dynamic guarantee, which is why the refined criteria treat it as a requirement to be checked rather than a free theorem [5].

## 5 Empirical and Theoretical Results

The theory above is not merely notional: it has been implemented, measured, and in some cases found wanting. The empirical record divides into three strands — *implementations*, *performance*, and *metatheory*.

**Implementations.** Typed Racket is the flagship sound gradual language: it elaborates typed modules into contracts at module boundaries and inherits blame safety from the contract system. Reticulated Python explored *transient* versus *guarded* semantics — shallow tag checks versus full proxies — trading soundness for performance. TypeScript occupies the opposite pole: it is gradually *typed* but deliberately *unsound* by design, erasing types entirely and performing no runtime checks; it therefore offers no gradual guarantee in the technical sense, which is exactly the gap this thesis addresses. The comparison is instructive:

| Language | Sound? | Runtime checks | Blame | Gradual guarantee |
|---|---|---|---|---|
| Typed Racket | Yes | Contracts at boundaries | Yes | Yes |
| Reticulated Python (guarded) | Yes | Proxies | Partial | Yes |
| Reticulated Python (transient) | Partial | Shallow tag checks | No | Weakened |
| TypeScript | No (by design) | None (erasure) | No | No |

**Performance.** Soundness has a price. Takikawa and colleagues, in *"Is Sound Gradual Typing Dead?"*, benchmarked gradually typed programs across the spectrum and found boundary-check overhead in fully sound implementations can exceed an order of magnitude on realistic programs — concentrated exactly at the dynamic end this thesis studies. The space-efficiency program of [4] and the coercion-based refinements of [7] are best read as responses to this finding: the overhead is not intrinsic to gradual typing but to naive wrapper implementations, and normalized coercions recover much of the lost performance while preserving blame.

**Metatheory.** The last decade has systematized what was once folklore. AGT [3] derives consistency, precision, and dynamic semantics from a static counterpart by abstract interpretation, and has been applied to objects, polymorphism, effects, and security types. Siek and Chen [8] parameterized the cast calculus itself, proving type safety, blame safety, the gradual guarantees, and space consumption once and for all for a family of calculi, with the proofs mechanized in Agda. Castagna and colleagues [6] mapped the decidability frontier: gradual type inference with consistent subtyping is decidable for the core calculus but becomes delicate as features accumulate — a result with direct implications for how much of the dynamic end can be handled statically. The survey in [5] synthesizes these threads into the "static-first versus dynamic-first" taxonomy that now organizes the field.

The net empirical verdict is cautiously positive: the three pillars — contracts, blame, the gradual guarantee — survive contact with implementation, but their cost must be managed (coercions, transient checks) and their scope delimited (decidability, hyperproperties).

## 6 Limitations

A candid account must register where the story frays.

**Polymorphism.** The interaction of gradual typing with parametric polymorphism remains the deepest open problem. Sealing polymorphic values with runtime type names restores soundness but breaks the gradual guarantee and complicates blame: a type variable instantiated at `?` must not leak its instantiation, yet blame wants to name the offending party precisely. The tension between *graduality* (annotations don't change behavior) and *parametricity* (polymorphic code behaves uniformly) is not fully resolved [5].

**State and effects.** Mutable references force a choice between proxies — which preserve the gradual guarantee at the cost of indirection — and monotonic or transient designs that trade guarantee strength for performance. Exceptions and delimited control interact with blame polarities in ways the original blame calculus does not cover.

**Blame granularity.** The blame theorem attributes failure to a *label*, but labels name syntactic cast sites, not responsible *modules* or *authors*. In a large mixed codebase, "the less precisely typed side of the cast at line 412" is barely actionable; coarser module-level blame (as in Typed Racket) is more useful but less precise. The theory does not yet tell us the right granularity.

**The cost of soundness.** Even with coercions, fully sound gradual typing imposes overhead that unsound designs like TypeScript simply decline to pay. Whether programmers will accept that overhead in exchange for the gradual guarantee is an empirical question the theory cannot settle.

**Scope of the guarantee.** The dynamic gradual guarantee is stated for *safety* properties of complete programs. For hyperproperties (noninterference, observational determinism), the guarantee fails in general [5] — a limitation that matters as gradual techniques migrate into security-typed languages.

## 7 Conclusion

We have argued that the dynamic end of the gradual typing spectrum is governed by a single coherent discipline with three faces. *Contracts* supply the mechanism: casts elaborated from consistency checks, enforced at run time by wrappers or, more efficiently, by normalized coercions [4, 7]. *Blame* supplies the accountability: polarities track responsibility across higher-order boundaries, and the blame theorem guarantees that the statically typed party is never at fault [2]. *The gradual guarantee* supplies the specification: precision may be added or removed without changing behavior, except through informative new errors [5].

AGT [3] shows these are not accidents of one calculus but consequences of systematic derivation from static disciplines; the parameterized metatheory [8] shows they can be proved once and reused; decidability results [6] map their static limits; and the performance literature prices their cost. What remains is extension under pressure: polymorphism without sacrificing graduality, effects without breaking blame, and overhead low enough that soundness is a default rather than a luxury. The spectrum's dynamic end is no longer the absence of typing — it is typing's runtime conscience.
