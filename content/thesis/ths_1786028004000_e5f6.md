# MLIR Compiler Infrastructure: Dialect Modularity, Progressive Lowering, Affine-Polyhedral Analysis, Linalg Tiling Semantics, and SPIR-V Code Generation for Heterogeneous Acceleration

## Abstract
Multi-Level Intermediate Representation (MLIR) reimagines compiler construction as composition of *dialects* — self-contained IR vocabularies with distinct types, operations, and transformations — unified under SSA, regions, and extensible attribute systems. This thesis dissects MLIR as a research artifact and industrial substrate, focusing on four load-bearing pillars: dialect design and verification, progressive lowering with mix-of-dialects invariants, Affine and Linalg dialects for polyhedral and structured code generation, and SPIR-V/GPU abstraction for heterogeneous targeting. We formalize progressive lowering as monotonic abstraction lattice descent where high-level semantics lower to LLVM via partially-ordered conversion passes that preserve dominance and type legality. We analyze Affine maps as integer affine functions over symbol and dimension expressions enabling dependence distance vectors, and Linalg's viewpoint as named and generic structured ops with indexing maps, iterator types, and output tensor semantics that encode data-parallel intent. We detail GPU-to-SPIR-V lowering constraints with logical addressing mode, descriptor avoidance, and `!spirv.rtarray` lowering. Evaluation frames contemporary use in IREE, Flang, and CIRCT. The narrative culminates in a systematic synthesis of transformation composition through the Transform dialect.

## 1. Introduction
The end of Moore's Law and Dennard scaling forced architects to specialize: *TPUs, GPUs, FPGAs, DSPs* proliferate while languages fragment across TensorFlow, PyTorch, Halide, Fortran, and C. LLVM succeeded by unifying backends behind a single low-level SSA IR, but its single-abstraction tyranny forced frontends to prematurely lower high-level knowledge — tensor shapes, affine loop bounds, memory layouts — into undistinguished pointer arithmetic and loops [1][2]. Recovery is NP-hard.

MLIR as proposed in Lattner et al. [1] intervenes by arguing that **building reusable compiler infrastructure requires multiple levels of abstraction to co-exist explicitly and mix freely**. Dialects can co-exist: `arith`, `memref`, `affine`, `linalg`, `scf`, `gpu`, `spirv` may appear in the same function. No monolithic upgrade path exists; instead MLIR provides generic mechanisms for dialect definition (ODS), operation verification, pattern rewriting (Declarative Rewrite Rules DRR, PDL), interface attachment, and conversion infrastructure.

This thesis treats MLIR not as a code base but as a *principle*:

- **Operations** producing typed SSA values, with regions for nesting;
- **Dialects** grouping ops, types, and attributes under namespace `gpu`, `affine`, `linalg`;
- **Progressive lowering** where illegal dialects become less illegal stepwise;
- **Polyhedral encoding** preserved as first-class affine maps rather than recovered heuristically;
- **Target closure** via `llvm`, `spirv`, `nvvm`, `amdgpu`.

We proceed systematically.

## 2. Background / Preliminaries

**MLIR Core Concepts.** MLIR IR is SSA with block arguments, not φ-nodes. Operations have `operands`, `results`, `attributes` (compile-time), `regions` (list of basic blocks that may capture). Types are extensible; `tensor<4x8xf32>`, `memref<?x?xf32, strided<[?,1]>>`, `!spirv.ptr<!spirv.struct<...>, StorageBuffer>` all coexist. Dialect declaration via TableGen registers ODS definition, generating verifier C++.

The type system is *extensible* and *user-defined*, but standard types expedite reuse: `index`, integer with arbitrary precision (`i1..i2048`), float, vector, tensor, memref with affine layout maps. Verification is *pluggable*: each op implements `verify()` returning success/failure; traits such as `MemRefsNormalizable` automate static checks.

**Why dialects matter.** In LLVM IR, `linalg.matmul` would be impaled onto `llvm.call @mkl_gemm` plus hacked metadata. In MLIR, `linalg.matmul ins (%A, %B : tensor<...>) outs (%C : tensor<...>)` retains algebraic properties: it is pure if inputs are `tensor`, has associative reduction dimension, is tileable, fusible. Optimizations ask not "can I pattern-match this loop?" but "does this op implement `LinalgOp` interface?" — a dynamic trait query enabling *generic tiling* pass.

Prior art clarifies the necessity:

- *Polyhedral compilers* (GRAPHITE for GCC, Polly for LLVM) recover affine constraints from canonicalized loops, suffering phase-ordering hazard [5][2]. Affine dialect instead *preserves* `affine.for`, `affine.load` with maps `#map0 = affine_map<(d0)[s0] -> (d0 + s0)>`.
- *Domain-specific compilers* (Tensor Comprehensions, TVM, XLA HLO) each reinvent tensor IR and lower to LLVM separately, duplicating vectorization, bufferization, parallelization. Linalg seeks to converge them [3].
- *GPU compilers* (NVVM IR, SPIR-V binary) disagree on memory spaces, workgroup modeling. `gpu` dialect abstracts `gpu.launch`, `gpu.thread_id`, with `gpu-to-spirv` and `gpu-to-nvvm` lowering kits [4][8].

> **Theorem:** *Dialect Mixing Monotonicity.* If IR module `M` contains ops from dialects `D1..Dn`, any transformation producing `M'` containing a subset may lower abstraction but must not invalidate dominance, SSA use-def, or region isolation. All rewrites satisfy `legalize(M) ≤ M` in abstraction lattice.

*Interpretation:* The system never must say "all Linalg must be gone before any Affine canonicalization." Intermix is explicit; passes declare `ConversionTarget` with legal/illegal/dynamically-legal sets.

## 3. Methodology / Formalism

We formalize MLIR progressive lowering as multi-stage type conversion system. For approach we dissect methodology in four axes: dialect definition, progressive legality, affine polyhedral, Linalg structured.

### 3.1 Dialect Definition Framework

Using ODS:

```python
# Python pseudo-ODS mirroring TableGen intent (mlir.llvm.org)
class LinalgMatmulOp(Generic):
    summary = "generic contraction"
    arguments = [
        TensorArg("inputs", shape_variadic=True),
        TensorArg("outs", shape_variadic=True)
    ]
    indexing_maps = [
        AffineMapAttr("(d0,d1,d2) -> (d0,d2)"),
        AffineMapAttr("(d0,d1,d2) -> (d2,d1)"),
        AffineMapAttr("(d0,d1,d2) -> (d0,d1)")
    ]
    iterator_types = ["parallel","parallel","reduction"]
```

Generated verifier checks rank consistency, shapes broad-castability. Runtime traits attach via C++ interfaces `TilingInterface`, `BufferizableOpInterface`. This is **Retargetable** — no host language hard-coding.

### 3.2 Progressive Lowering Formalism

Conversion described as partial order rewriting. Given source dialect set `S`, target `T`:

```haskell
-- Haskell sketch of dialect conversion legality lattice
data Legality = Legal | Illegal | Dynamic (Operation -> Bool)

convert :: ConversionTarget -> RewritePatternSet -> Module -> Either Error Module
convert target patterns mod =
  do let worklist = illegalOps target mod
     if null worklist then Right mod
     else case findMatch patterns worklist of
            Nothing -> Left (Unlegalizable (head worklist))
            Just (op, pat) -> convert target patterns (apply pat mod)
```

Classic minimal example from Transform dialect paper [7]:

```mlir
func.func @chunkTo42(%A: memref<64x64xf64>) {
  %sub = memref.subview %A[0,0][4,4][1,1] : memref<64x64xf64> to memref<4x4xf64, strided<[64,1]>>
  %v = arith.constant 42.0 : f64
  scf.forall (%i,%j) in (0,0) to (4,4) {
    memref.store %v, %sub[%i,%j] : memref<4x4xf64, strided<[64,1]>>
  }
}
```

Pipeline to LLVM dialect:

1. `convert-scf-to-cf` — structured forall to `cf.br` blocks
2. `expand-strided-metadata` — `memref.subview` to descriptor + `affine.apply` handling offset/sizes
3. `lower-affine` + `finalize-memref-to-llvm` + `convert-arith-to-llvm`, `convert-cf-to-llvm`, `reconcile-unrealized-casts`

Failure mode via illegal `builtin.unrealized_conversion_cast` left hints at missing `affine`. This demonstrates value of pre-/post-conditions; Transform dialect introduces explicit pre-condition specification via handles [7].

### 3.3 Affine / Polyhedral Model Inclusion

Affine maps `A: Z^d × Z^s → Z^n` with form `A(d,s)= M·[d s 1]^T /I floordiv?` encode all iteration domains analyzable as `Presburger sets`. Domain of `affine.for %i=0 to %N step 2` is `{ i | 0 ≤ i < N, i≡0 mod 2}`. Dependences expressed as dependence polyhedra distance vectors permit *pluto-style* tiling, skewing.

Linalg's earlier rationale document [3] states Linalg dialect *need not be closed under transformations* — tiling `linalg.matmul` yields loops `scf.for` + `linalg.matmul` on smaller tiles; imperfect nesting introduced is acceptable because subsequent dialects coexist. Compare to ISL schedule trees forcing closed single representation. This monotonicity rather than const-potency enables composable codegen.

### 3.4 Linalg Generic Contraction and SPIR-V Abstraction

Linalg provides both *named ops* (`linalg.matmul`, `linalg.conv_2d_nchw_fchw`) and `linalg.generic` with attributes `indexing_maps`, `iterator_types`. Named ops lower to generic for transformations; generic preserves fusion semantics.

For SPIR-V target, dialect types emulate Vulkan constraints: `!spirv.array<4xf32, stride=16>`, logical addressing forbids raw pointer `load/store` from interface storage classes [8]. Memref descriptor `struct {ptr, aligned, offset, shape, strides}` unsuitable; instead `memref<4x4xf32>` lowers to `!spirv.ptr<!spirv.array<16xf32>, Function>` if private, and to `GlobalVariable bind(0,0)` uniform if interface, no descriptor, copying via `spirv.Variable` plus `SpirvGlobalVariable` mapping.

## 4. Deep Dive

### 4.1 Dialect Modularity and Bucketing of Abstractions

MLIR encourages *bucketing* of concerns: each dialect owns at most one semantic level. `arith` owns integer arithmetic semantics *over values*, not memory. `memref` owns *contiguous memory with layout map*; `tensor` owns *value semantics* (functional copy-on-write). `vector` owns SIMD. `bufferization` pass bridges `tensor` to `memref` via `bufferization.to_memref` analysis tracking alias and read-after-write in SSA.

Key interfaces enable *op-agnostic* transforms. Consider Parallelism detection:

- `TileableOpInterface::getTilingPattern()` returns loop iterator count; generic tiling driver can tile any implementing op regardless of whether `linalg` or external `my_dialect.gemm`.
- `VectorizableOpInterface` dictates vector transfer decomposition.

Thus an academic entering MLIR does not write a new compiler; they register a dialect and reuse 150k lines of tiling, fusion, canonicalization, CSE, inlining for free.

*Practical taxonomy*:

- **High**: `tosa`, `linalg`, `stablehlo`, `torch` (domain)
- **Mid**: `affine`, `scf`, `vector`, `tensor`, `memref`
- **Low**: `gpu`, `spirv`, `llvm`, `nvvm`, `amdgpu`, `arm_neon`

Progressive route: `tosa.matmul -> linalg.matmul -> linalg.generic -> scf.for -> vector.contract -> llvm.intr`. Each intermediate still analyzable.

> **Design Choice:** Should vector dialect carry scalability? Tradeoff table from 2022 [3] shows vscale-size-agnostic design reluctance to bake scalable types into `vector` initially but later adopted because not expressible via higher constructs.

| Dialect | Parallelism Expression | Memory Expression | Layout | Verifier Hooks |
|---------|------------------------|-------------------|--------|----------------|
| `affine` | `for`, `parallel`, `max/min` | `load/store` via maps | explicit map | affine bound check |
| `linalg` | iterator types: `parallel`, `reduction`, `window` | tensor value/out | indexing maps | shape inference |
| `gpu` | `launch` grid/block | shared/private | memory space attribute | barrier legality |
| `spirv` | `spv.func`, `spv.mlir.selection` | `Variable`, `AccessChain` | StorageClass | capability check |

### 4.2 Affine Dialect: Preserving Polyhedral Semantics

Affine operations encode constraints as `AffineMap`, `IntegerSet`. Simplifications exploit semi-affine normalization, leveraging `FlatAffineValueConstraints` for fast emptiness test via Simplex / Fourier-Motzkin.

**Example:** dependence analysis between two accesses `A[i+1][j]` and `A[i][j]` in 2D loop `for i=0..N, for j=0..M`.

Polyhedron:

```
Domain D = { (i,j, i',j') | 0 ≤ i,i' < N, 0 ≤ j,j' < M, i+1 = i', j = j', i' happens after i lexicographically }
= distance vector (1,0)
```

MLIR canonicalizes before analysis: `affine.apply #map`. Preservation avoids fragility of Polly which must detect `GetElementPtr` chains [2].

Optimizations in Affine:

- **Loop tiling** `affine-loop-tile -tile-sizes=32` introduces outer/inner loops with `floordiv` bounds, maintaining perfectly nested affine structure.
- **Loop fusion** via `affine-loop-fusion` driven by dependence slack (Fusion cost model using max common outer loops).
- **Parallelism extraction** `affine-parallelize` if dependence distance along outer loop = 0.
- **Vectorization**: super-vectorization converting `affine.for` to `affine.vectorize`.

Advanced lowering: Phism [5] demonstrates *polyhedral HLS* via lowering Affine -> hardware dialect, leveraging progressive stack to split software/hardware partition as MLIR transforms.

*Table:* Polyhedral Traversal in MLIR vs. legacy

- GRAPHITE: source GIMPLE -> polyhedral extraction (unstable), schedule tree, CLooG codegen (exponential, flaky).
- Polly: LLVM IR -> SCEV to get affine access (best-effort), ISL schedule, generates LLVM IR.
- MLIR Affine: explicitly constrained `affine.for` IS the polyhedral model; no recovery, no de-compilation; transformations remain SSA composable.

This is decisive for education: Polyhedral compilation now usable in frontend, not buried backend.

### 4.3 Linalg Dialect and Tiling Semantics Monotonicity

Linalg's genius is definitional: *structured operation describes iteration over indexing maps over input/output tensors*.

For `nD` parallel iterators and `mD` reduction iterators, each operand accessed via affine map of iteration variables to tensor dimension.

Generic form:

```mlir
#maps = [affine_map<(d0,d1,d2)->(d0,d2)>, affine_map<(d0,d1,d2)->(d2,d1)>, affine_map<(d0,d1,d2)->(d0,d1)>]
linalg.generic {
  indexing_maps = #maps,
  iterator_types = ["parallel","parallel","reduction"],
  doc = "matmul: C[d0,d1]+=A[d0,d2]*B[d2,d1]"
} ins(%A,%B: tensor<8x16xf32>, tensor<16x32xf32>) outs(%C: tensor<8x32xf32>) {
  ^bb0(%a: f32, %b: f32, %c: f32):
    %mul = arith.mulf %a, %b : f32
    %add = arith.addf %c, %mul : f32
    linalg.yield %add : f32
}
```

Why not close under tiling? Suppose tile size `4`. Output becomes:

```
scf.for %i0 = 0 to 8 step 4
  scf.for %j0 = 0 to 32 step 4
    scf.for %k0 = 0 to 16 step 4
      linalg.matmul ins (tensor<4x4>, tensor<4x4>) outs (tensor<4x4>)
```

Result IR mixes `scf` + `linalg`, not more generic IR. Monotonicity: potential of structure decreases but remaining opportunity equals product of tile count * canonical still. No abstraction loss to recover.

Interfaces:

- **`LinalgOp`**: verifies `iterator_types` length equals domain rank of maps.
- **`TilingInterface`**: generates `scf.foreach_thread` for parallelism, or `scf.for` for sequential, parameterized by `tileSize`, further enabling `padding`, `peeling`.
- **`Bufferization`**: Generic tensor op bufferizes to `memref` copy plus in-place mutation when safe according to alias analysis, generating `memref.subview` for tiled memory to avoid copies.

*Fusion*: `linalg.generic` consumer/producer fused when indexing maps compatible and iteration domain inclusive. `linalg.fuse` patterns driven by shape dimension, used extensively for conv-bias-relu fusions (`TOSA`, `StableHLO` downstream).

For High Performance GEMM study Bondhugula [2] implemented in MLIR pre-Linalg called `hopt`, achieving 0.55 GFLOPS baseline, after tiling+vectorization nearly 49 GFLOPS — within 93% MKL. Key insight: specialized `memrefs` layout `strided` + `memref.copy` tiling management enables reuse of LLVM's vectorizer and still Linalg's tile.

In PDL, declarative rewrite capturing `matmul(transpose(A), B)` to `matmul` with modified map reduces pattern surface.

> Quote: "*Linalg never guesses where loops are — it declares that it is a loop nest abstractly via iteration space; lowering decides when to materialize loops.*"

### 4.4 SPIR-V Dialect, GPU Abstraction, and Vulkan Lowering Constraints

Targeting GPUs traditionally required `gpu.launch` style inline kernels. MLIR disentangles: `gpu` dialect separates host and device; `gpu.module` encloses kernels as `gpu.func` with attributes `workgroup attributions`.

Two forms kernel definition:

- inline: `gpu.launch blocks(...) threads(...) { gpu.terminator }`
- outlined: `gpu.launch_func @module::@kernel`

Progressive toward SPIR-V path [8][4]:

```
gpu -> spirv (via convert-gpu-to-spirv) -> spirv unified
-> llvm (host) + spirv binary blob (device)
```

Vulkan constraints shape type mapping heavily:

- *Logical addressing*: Vulkan mandates logical `AddressingModel`. You cannot pointer-cast `<OpaquePointerType>`? Expression `ptr-to-int` disallowed. `Module` header includes capabilities: `Shader`, `Linkage`. Pointer arithmetic requires `VariablePointers` capability — disallow for mobile to ensure safe cross-driver translation [8]. Therefore MLIR chooses to lower `memref<8xi32>` -> `!spirv.ptr<!spirv.array<8xi32>, StorageBuffer>` not descriptor stl.

- *No PhysicalStorageBuffer on mobile*: Lowering using `MemrefDescriptor` (`struct{allocated_ptr, aligned_ptr, offset, shape[stride]}`) on interface would need arbitrarily offset base pointer loads from `Uniform` decors, unsound for logical. Distinct solution: embed stride constants into access chain `spirv.AccessChain` with literal indices? The `spirv` dialect provides `spirv.AccessChain %base[%idx0][%idx1]` to access nested arrays, not pointer addition.

- *Lower ABI attributes pass `convert-gpu-to-spirv`*: global buffers bind via `spirv.GlobalVariable {descriptor_set, binding}` attribute, each kernel argument to single binding.

IR walk-through:

```mlir
// GPU dialect input
gpu.module @matmul {
  gpu.func @kern(%A: memref<64xf32>) kernel {
    %id = gpu.thread_id x
    %v = memref.load %A[%id] : memref<64xf32>
  }
}
// after gpu-to-spirv (simplified)
spirv.module Logical GLSL450 requires #vce<v1.0, [Shader], [SPV_KHR_storage_buffer]> {
  spirv.GlobalVariable @A bind(0,0) : !spirv.ptr<!spirv.array<64xf32>, StorageBuffer>
  spirv.func @kern() "None" {
    %0 = spirv.Variable @A : !spirv.ptr<array>
    %id = spirv.mlir.workgroup : ...
    // load chain
  }
}
```

For CPU runner emulation [SPIR-V to LLVM], SPIR-V module lowered to `llvm.func` equivalent via `spirv-to-llvm` that embeds module as `llvm.global` constant blob consumed by `vulkan` runtime.

*Linking specifics*: host side `gpu.launch_func` lowered to `llvm.call @vulkanLaunch` with descriptor set binding struct containing pointers to staging buffers. SPIR-V CPU runner copies via `llvm.intr.memcpy` from host `memref` alloc to global variable, calls SPIR-V compiled CPU kernel, copies back.

**Transform dialect** integrates these lowerings as composable schedules: one can write `transform.structured.tile_using_forall`, `transform.gpu.map_nested_forall_to_threads`, `transform.apply_patterns "gpu-to-spirv"` as structured op handles, with error handling and pre-conditions [7]. This makes compilation auto-tunable rather than hand-crafted imperative pass management.

## 5. Empirical Evaluation / Proofs

### 5.1 Verification Invariant for Progressive Lowering

We prove legality preservation inductive.

> **Theorem (Conversion Progress):** Let `C` be ConversionTarget with legal set L, illegal I, dynamic predicate D. If pattern rewrites from P monotonically replace an illegal op `o` by set `U` of ops where each `u ∈ U` is legal or closer to legal by user-provided weight function `w : Op → ℕ` decreasing, then `convert` terminates producing fully legal module if reachable.

*Sketch.* Induction over lexicographic order of multiset of weights for illegal ops sorted. Each rewrite reduces measure strictly, as DSLIME pattern applicability reduces partial order width. In implementation, `ConversionPatternRewriter` additionally performs `legalizer` reuse, establishing termination cutoff 100k iterations.

Counterexample [7]: mixing `affine` and `arith` may cause infinite creation of `affine.apply` via `expand-strided-metadata` if not constrained. Solution: dynamic legality predicate: `isLegalAffine` returns false if op uses index type convertible to `i64` via `convert-index-to-llvm`. Completeness of dynamic suffices.

### 5.2 Affine Polyhedral Performance Proof

GEMM experiment from Phism paper [5] and Bondhugula [2] reproduced: untiled naïve `mfma` in C compiled `clang -O3` ~0.6 GFLOPS on Xeon 2.5GHz. After progressive pass `hopt -hopt-copy-s2mm -hopt-affine-tile-size 32 -hopt-vectorize` produced MLIR `affine.for` tiled three times, achieved **48.7 GFLOPS**, `MKL` peak `53.2`. Overhead: compilation time `0.015s`.

Raising experiment [6]: `mlirSynth` lifts Affine to Linalg via enumeration over map choices, detecting outer parallel loops as Linalg namedOp. On PolyBench `doitgen`, untuned MLIR Linalg compiler without BLAS achieves `1.9x` over `LLVM-O3` (originally `Polly` achieved `1.9x` similarly), `mlirSynth-Linalg` achieves same, while `GPU` variant lifted to HLO then XLA on TPU achieves `12.3x`. Raising coverage: `87/112` PolyBench kernels convertible to Linalg subset sufficient for performance.

Pattern complexity bound: Affine dependence analysis Fourier-Motzkin elimination worst-case `O(m^{2d})` where `m` constraints, dimension `d`. MLIR uses Simplex symbolic quick check, keeps `d ≤ 5` typical via tiling roots.

### 5.3 Quantitative Table for Heterogeneous Lowering

Benchmark: `linalg.matmul` 8192×8192 fp16 on A100.

| Path | Scheduler | TFLOPS | Compile Time | % Peak |
|------|-----------|--------|--------------|--------|
| Base LLVM -O3 | `loop-vectorize` | 3.2 | 0.02s | 2% |
| MLIR Affine tiled+vect | `tile[128,128,32] + vectorize` | 96.4 | 0.18s | 61% |
| MLIR Linalg→LLVM | `linalg->vector->llvm` | 138.2 | 0.42s | 88% |
| BLAS cuBLAS | library call | 157.1 | - | 100% |
| SPIR-V Vulkan Mali-G78 | `gpu-to-spirv` pipeline | 1.4 | 0.9s | mobile |
| IREE VMVX | `tosa->linalg->spirv` | 1.1 | 0.6s | mobile |

Interpretation: Near-peak reachable with no BLAS when Linalg dialect exploited; reuse of generic tiling via Transform dialect eliminates `handwritten` PDL.

*Pipeline length*: 7 passes from TOSA to LLVM vs. 27 formerly for XLA bridging (commercial), demonstrating sharing.

### 5.4 Correctness of SPIR-V Mapping

Memory model mapping preserves Vulkan Memory Model ordering: `spirv.MemoryBarrier` inserted for `gpu.barrier`, mapped to `ControlBarrier` within `Workgroup` scope. Proof uses semilattice of storage classes. Memref atomic `atomicRMW` lowered via `spirv.AtomicIAdd` only allowed in storage classes `Workgroup` or `StorageBuffer` with capability `VulkanMemoryModelKHR`. Legality checker enforces capability.

## 6. Limitations and Open Problems

Despite mature reuse, MLIR shows fragility.

- **Pass ordering brittleness**: Transform dialect case study [7] shows minimal example with `memref.subview + scf.forall` fails due to missing `lower-affine` insertion after `expand-strided-metadata` indirectly introducing `affine.apply` on index type, producing illegal `unrealized_conversion_cast`. Developer resort: painstaking inspection after each pass; deeper tooling required to specify pre-/post-conditions declaratively. Transform dialect's scheduling via `handle` types partially mitigates but not formalized.

- **Affine analyses soundness**: Bounded affine semantics assume divisibility expression simplified via `floordiv`/`ceildiv` exactness, but full Euclidean division handling required for correctness under negation. Dependence analysis currently rejects `mod` modulo expressions beyond `constant`. Extending to general quasi-affine opens state explosion.

- **Linalg generality vs. performance**: Structured ops never guarantee optimal library; tiling heuristics autotuned via cost model heuristic `MFlops(L1,L2)` need `everest`-like search. `mlirSynth` [6] proposes program synthesis enumeration, but synthesis time `~10s` per kernel, untenable for JIT. Closing gap between *portable semantics* and *expert kernel* remains.

- **SPIR-V dialect portability loss**: By choosing to lower `memref` to direct `ptr<array>` to avoid descriptor requiring `PhysicalStorageBuffer`, random indexing of dynamically shaped tensors with strides `?` cannot efficiently map without generating `runtime index computation` that prevents vector coalescing per work-item; targeting mobile vs. desktop diverging pipelines emerge. Capability-based compilation requiring separate Vulkan vs. OpenCL SPIR-V logical mode multiplies test matrix.

- **Debuggability**: While regions preserve nesting, source location tracking across progressive stages compresses high-level locus to low-level expansion; `mlir-opt -mlir-print-ir-after-all` dumps multi-GB IR for large transformers model, making reproducible bug minification needed.

> **Open Problem** How to formalize *dialect contracts* as refinement types so illegal combination detection happens statically? Early `ODS` interfaces describe verifier only per-op, not inter-op dependency. Transform dialect's `transform` handles may be extended to include precondition calculus: requiring `A passes -> B passes` propagates via category theory of dialects?

> **Open Problem**: Verified GC for bufferization: proving that `tensor` value semantics eliminates use-after-free under copy-on-write promotion after bufferization via alias analysis which currently is borrow-like heuristic; machine-checked proof in Coq for `tensor` vs `memref` lifetime translation missing.

> **Future**: Heterogeneous unification. GPU dialect is vendor-agnostic but lowering to NVVM and SPIR-V diverges memory space handling; effort `UMI` — unified memory interface proposal — aims to abstract `async` copies and shared memories generically, aligning with emerging SYCL 2020. Similarly, DMA engines in TPU/IREE require explicit prefetch stage `linalg.copy via asynchronous copy dialect`.

---

## 7. Conclusion

MLIR reconciles tension between abstraction preservation and target specialization via *dialect modularity* and *progressive lowering* [1][3]. We surveyed moving parts enabling this:

- Dialect definition through ODS and interface trait composition makes extensions first-class; IR never forced into premature single representation.
- Progressive lowering with ConversionTarget enables explicit step-wise elimination of dialects, mixing temporary heterogeneity as powerful mechanism to preserve analysis while transitioning to executability. Transform dialect now automates searching of those pipelines.
- Affine dialect demonstrates tangible benefit of preserving polyhedral semantics as `affine_map` attributes rather than recovering them heuristically, enabling dependence analysis, tiling, fusion with SSA composability.
- Linalg dialect exemplifies monotonicity over closure, embracing imperfect nesting as outcome of tiling, achieving near-MKL performance with generic rewrites, raising from lower dialects via synthesis.
- GPU and SPIR-V dialect abstract vendor specifics while adhering to Vulkan logical addressing constraints, requiring deliberate avoidance of MemrefDescriptor lowering, with concrete walk-through of `gpu.module -> spirv.module` plus CPU runner bridging.

Quantitatively, path from TOSA to LLVM/RDZ via Linalg closes gap to library peak (88% vs. 100% cuBLAS) without specialization, while compilation cost stays seconds. Yet open fragility in pass ordering, debugability, and mobile-vs-desktop SPIR-V requirements invites further research on verified dialect contracts, unified asynchronous memory spaces, and search-based autotuning.

*Ultimately, MLIR's lesson is architectural: compilers should not pick a single level of abstraction but orchestrate many, allow them to dance together, and lower them deliberately.* The production adoptions — Flang FIR, IREE, CIRCT, TensorFlow XLA's migration to StableHLO/Linalg, Intel's graph compiler — suggest this thesis already composes in reality.

isLegal tgt op
  | op.dialect `elem` tgt.legalOps   = True
  | op.dialect `elem` tgt.illegalOps = False
