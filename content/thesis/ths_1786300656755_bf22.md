# Just-In-Time Compiler Speculative Optimization Deoptimization: V8 TurboFan Sea-of-Nodes, Hidden Class Maps, and Deopt Checkpoint Reconstruction

## Abstract
Just-In-Time compilation of dynamic languages rests on an unavoidable tension: *performance requires certainty, but JavaScript provides none*. V8's tiered pipeline — Ignition, Sparkplug, Maglev, and TurboFan — resolves this by speculating on stable types and hidden class shapes, emitting aggressively optimized machine code under assumptions that may later fail. This thesis formalizes speculative optimization as a data-driven guarded optimization problem over V8's Sea-of-Nodes intermediate representation. We reconstruct the evolution from Crankshaft and Full-Codegen to TurboFan's soup-of-nodes model where control, effect, and data dependencies form a relaxed partial order amenable to global code motion. We analyze hidden class Maps as flow-sensitive approximate types encoding layout, transition trees, and inline cache feedback, and show how Map checks become speculative guards. We model deoptimization checkpoints, frame state translation, safepoint liveness, and materialization of JSInterpreter frames during bailout under Eager vs Lazy deopt semantics. We prove correctness conditions for reconstruction invariants and quantify deoptimization penalties, polymorphism tax, and code bloat mitigation via deopt grouping analogous to Graal.

## 1 Introduction

V8 in 2008 astonished by compiling JavaScript directly to machine code with hidden classes and inline caches, delivering a 10x leap over interpreters [4]. Yet this **Full-Codegen** non-optimizing JIT quickly plateaued: dynamic property access, polymorphic dispatch, and prototype walks defeated static heuristics. **Crankshaft** (2010) introduced type feedback and deoptimization, compiling hot functions only after observing runtime types [4][5]. Its Achilles' heel was coupling to a high-level AST that *did not scale* to ES2015+ semantics, and reliance on massive monolithic deoptimizations.

**TurboFan** (2015) replaced it with a new IR explicitly designed for speculative optimization [1][8]. Its core abstraction is a **Sea-of-Nodes** graph where the program is not a control-flow graph but a *soup* of values, effects, and control edges where ordering is emergent rather than prescribed [2][3]. This enables:

* *Bottom-up and top-down graph reducers* that pattern-match local dominator constraints into cheaper equivalents
* *Representation selection* via truncated range and type analysis to untag Small Integers (SMIs) inside loops
* *Escape analysis* that scalar-replaces `const o = {x:1,y:2}` into registers `o_x=1, o_y=2`
* *Checkpointed speculation* where Map checks become `DeoptimizeIf` nodes with associated **FrameState** chains describing how to reconstruct unoptimized frames [3][6]

Speculation is *freely chosen but not free*. Every `CheckMaps` guard incurs three costs: control-flow entropy, deoptimization metadata bloat, and worst-case abandonment cost when shape changes after promotion to optimized tier. Understanding this economy is central to modern web performance.

Contributions of this thesis:

* A unified formal model of Sea-of-Nodes scheduling with effect dependencies
* A taxonomy of Hidden Class transition trees and their monomorphic preservation tactics
* A reconstruction semantics for TurboFan deoptimization checkpoints and slack tracking
* Empirical principles for avoiding deopt storms in hot paths

## 2 Background

### 2.1 V8's Tiered Execution

V8 today is not one compiler but four:

* *Ignition* – bytecode interpreter with register-ish dispatch and inline cache (IC) site feedback collection
* *Sparkplug* – non-optimizing baseline compiler mirroring bytecode 1:1 for fast warm start
* *Maglev* – mid-tier optimizing compiler for faster peak without TurboFan cost
* *TurboFan / Turboshaft* – peak optimizing compiler consuming stable type feedback and producing specialized machine code [5]

Functions tier-up only when `invocationCount > threshold` (500 for Maglev, 6000 for TurboFan) and feedback is *stable* – i.e., no recent shape flips [5]. If unstable, tier-up is delayed, avoiding wasted compile bails.

> Theorem: Stable Feedback Convergence
> Let feedback vector F_t be sequence of observed Maps at IC site s. If entropy H(F_t) converges to 0 within window W and deopt count D < K, then tier-up is admissible; otherwise scheduling is delayed to preserve compilation cache efficiency. This captures Profile-Guided Tiering heuristic.

The execution diagram is:

```
JS source → Parser → AST → Ignition bytecode + ICs
        ↓ hot + stable
     Sparkplug → Maglev → TurboFan (Sea of Nodes → Scheduled CFG → Mach)
        ↘ guard fails → Deoptimize → Ignition (reconstruct frames)
```

### 2.2 Speculative Optimization Primer

*Unlike AOT compilers whose correctness rests on static proofs, JIT correctness rests on guards* [6]. Speculative compiler makes **educated guess**:

* `obj + 1` where `obj` observed as SMI for 1000 iterations – speculate int32 path, guard with integer check
* Property load `obj.x` where `obj` Map is `M1` 99% – speculate monomorphic `M1` with `CheckMaps`, eliminate dictionary lookup
* Array access `arr[i]` where `arr` elements kind is `PACKED_SMI_ELEMENTS` – speculate fast path

If guard fails, **deoptimization** restores interpreter state. Correctness is *observational equivalence* between versions under invariants that all optimizing assumptions are checked before committing effects [6].

Formal model by Barrière et al. [6] introduces CoreJIT with explicit `Assume` and `Deopt` instructions, proved in Coq to preserve weak bisimulation between speculative and origin program.

### 2.3 Hidden Classes (Maps)

JavaScript objects are hash bags, but V8 represents them as **Maps** aka Hidden Classes [7]. Each Map encodes:

* Property names and offsets
* Representation (Data, Accessor, Constant)
* Prototype identity
* TransitionArray – edges to child Maps on single property extension
* In-object vs out-of-object property count, elements kind

On `const o={}`, V8 allocates `M0`. On `o.x=1`, creates `M1=M0⊕{x}` and memoizes transition. Identical construction order reuses `M1`. Swapping order creates new tree branch, fragmenting ICs – the classic *order matters* tax.

*Inline Caches* track receiver Map at property site:

* Monomorphic – 1 Map – fast guard + offset load
* Polymorphic – 2-4 Maps – small polymorphic stub cascade
* Megamorphic – >4 Maps – slow dictionary / HashTable probe

Monomorphic sites inlining fuel TurboFan speculation. Constructor pattern initializing all fields in order in constructor preserves monomorphism.

| IC State | Map Cardinality | Cost (cycles) | TurboFan Treatment |
|----------|----------------|---------------|--------------------|
| Uninitialized | 0 | – | No feedback |
| Monomorphic | 1 | ~3 | Inlined `CheckMaps` guard |
| Polymorphic | 2-4 | ~15 | Polymorphic map check cascade, limited specialization |
| Megamorphic | >4 | ~80+ | Deoptimize to generic SlowPath |

## 4 Deep Dive

### 4.1 Sea-of-Nodes Soup and Graph Reduction Scheduling

Classic CFG enforces total order inside basic blocks, blocking code motion. **Sea-of-Nodes** [2] relaxes ordering, retaining only necessary dependencies:

* **Data edges** – value required: `Add(SmiAdd(x,y))` → `Add` depends on `x,y`
* **Control edges** – execution ordering: `IfTrue`, `Branch`, `Merge`, `Loop`
* **Effect edges** – side-effect ordering: writes, calls, property stores; must be serialized against observable JS effects

Thus pure integer ops float freely until scheduling assigns them to dominator blocks based on cheapest dominating control. This permits **global code motion**: lifting invariant loads out of loops without loop-invariant code motion analysis.

> Theorem: Scheduling Soundness
> Given Sea DAG G=<V, E_data ∪ E_ctrl ∪ E_effect>, any topological linearization L that respects E_ctrl ∪ E_effect and for each v has all data inputs scheduled before v and dominating v's scheduled block is semantics-preserving. Conversely, any valid schedule is realized by global code motion phase exploring placement by register pressure heuristic.

TurboFan pipeline stages [1][8]:

1. **Graph Builder** – translates Ignition bytecode to JSGraph with `JSCall`, `JSLoadProperty`, `CheckMaps` etc.
2. **TypedLowering** – reduces based on `Type` lattice and `Feedback`: e.g., `JSAdd` where both inputs int32 → `NumberAdd` + overflow check
3. **Simplified Lowering** – selects machine representations: `Int32`, `Float64`, `Tagged`, `Reference`
4. **Effect Control Linearizer / Scheduler** – assigns nodes to `Schedule` graph using `LoopFinder` + `BlockHeaps`; generates `Machine` IR
5. **CodeGen** – register allocation via greedy allocator, emits `DeoptimizationData` tables.

Graph reductions are **local rewrite rules** like `TypedOptimization`:

```python
def reduce_NumberAdd(node, type_feedback):
    """Bottom-up reducer example: eliminate range check if safe"""
    left_type, right_type = infer(node.inputs)
    if left_type.is_smi() and right_type.is_smi():
        # speculation: Smi addition cannot overflow into double?
        if range_analysis.proves_no_overflow(node):
            return Node(op='Int32Add', inputs=node.inputs, effect=node.effect)
        else:
            # introduce speculative check
            checked = Node(op='CheckedInt32Add',
                           inputs=node.inputs,
                           control=node.control)
            # Checkpoint materializes FrameState before deopt
            deopt = Node(op='DeoptimizeIf',
                         condition=checked.overflow,
                         reason='overflow',
                         frame_state=node.frame_state)
            return deopt
    return node  # no reduction
```

Scheduling for deopt checkpoints respects that effectful nodes cannot cross a `DeoptimizeIf` unless their effects are idempotent, else they'd be observable after bailout – violation of atomicity.

### 4.2 Hidden Class Maps as Flow-Sensitive Speculative Types

Maps are *speculative types* of object layout. Three invariants govern speculation:

* **Stability invariant** – object shape should not change during hot window. `class Point { constructor(x,y){ this.x=x; this.y=y; }}` respects this; ad-hoc `p.z=3` breaks.
* **Transition locality invariant** – single dominance chain of transitions maximizes sharing: `M0→M1→M2` repeated across 10k objects better than branching bush at `M0`.
* **Identity guard invariant** – polymorphic builtins (e.g., `Array.prototype.push`) specialized only when `prototype` chain unchanged; else `PrototypeMapCheck`.

TurboFan emits for `obj.x` when feedback monomorphic `M1`:

```rust
// Rust-like pseudocode for MapCheck lowering
fn lower_load_named(obj: Node, feedback_map: Map) -> Node {
    let maps = feedback_map; // e.g., 0x123400a
    let check = Node::CheckMaps {
        input: obj,
        maps: vec![maps],
        effect: effect,
        control: control,
    };
    // Deopt data stores interpreter pc, spill lives, context
    let frame = build_frame_state(pc: 42, lives: vec![obj, closure]);
    let deopt = Node::DeoptimizeIf {
        condition: check.failed,
        deopt_kind: DeoptKind::Eager,
        reason: "wrong map",
        frame_state: frame,
    };
    // If check passed, constant offset load (in-object)
    let load = Node::LoadField {
        object: obj,
        offset: feedback_map.offset_of("x"),
        rep: Representation::Tagged,
    };
    // Combine
    load.is_control_dependent_on(deopt);
    load
}
```

Degradation **megamorphic IC** forces Map poll elimination failure, falling to `LoadIC` runtime call; TurboFan refuses inlining → performance cliff 30-80x.

*Mitigation patterns*:

* Object pools reuse monomorphic shapes
* Initialize all fields in constructor; assign `null` placeholders for future optional fields
* Avoid `delete` removing property causing dictionary mode Map

Table of representation costs with exemplary optimization wins:

| Pattern | Hidden Class Tax | Speculation Strategy | TurboFan Lowering |
|---------|------------------|----------------------|-------------------|
| `this.x = x` in ctor only | Low, 1 transition | Monomorphic | `LoadField+CheckMaps` |
| `if (cond) this.y=..` | Medium, branching Maps | Polymorphic + deopt threshold | `Branch+MapCheck` cascade |
| `delete o.x` | High, dict mode | None – cold runtime | `CallRuntime DeleteProperty` |
| `Object.assign` spread | Very high | Seal polymorphism | Bailout to builtin |

### 4.3 Deoptimization Checkpoints: Eager, Lazy, and Checkpoint Reconstruction

Deoptimization is not `longjmp`. It must *reconstruct* unoptimized state faithful to ECMAScript abstract interpreter.

**Deopt taxonomy** [3][6]:

* **Eager** – on `CheckMaps`, `CheckSmi`, `CheckIfOverflow` failing; immediate bailout at guard site
* **Lazy** – on bailout from inlined callee or code object invalidated by GC/ prototype mutation; OSR unwinds multiple frames lazily
* **Soft / Continue** – transforms to interpreter trampoline continuing at same function, no inline unwind; used by Wasm speculative inlining [3]

Data structures:

* **FrameState** – SSA IR node describing all live values needed to reify a frame: `parameters, locals, stack, context, closure`. Form chain: `FrameState(osr, outer FrameState*)` capturing inliner stack.
* **DeoptimizationData** – side table per code: `DeoptInfo[]` mapping `deoptId → {bytecode_offset, translation_array, inlined_function_count}`. Translation array encodes abstract location → concrete: register `rax`, stack slot `s28`, constant `c7`, etc.
* **Safepoint** – register/stack live map at call/deopt: required for GC precise pointer identification during reconstruction walk.

Reconstruction algorithm (echoing V8 source `deoptimizer.cc`):

```haskell
-- Haskell sketch: FrameDescription translation
data Value = Reg String | Stack Int | Const Int | Literal Value deriving Show
data FrameDesc = FrameDesc { funcId :: Int, pc :: Int, values :: [Value] } deriving Show

translate :: [Value] -> DeoptTranslation -> [Value]
translate inputs (TranslatedBy table) = concatMap (eval inputs) table
  where eval inputs (RegLoc r) = [lookupReg r inputs]
        eval inputs (StackLoc s) = [lookupStack s inputs]
        eval inputs (Literal v) = [v]

reconstruct :: OptimizedFrame -> DeoptInfo -> [FrameDesc]
reconstruct optFrame info = 
  let inputValues = readRegisters optFrame ++ readStack optFrame
      outputs = map (\f -> translate inputValues f) info.translationEnvs
  in zipWith FrameDesc (info.funcIds) (info.bytecodes) outputs

-- Assume invariant: for any optimized state reaching deopt point,
-- translated interpreter states are weak-bisimilar under observable heap.
```

Crucially, due to nested inlining, one optimized frame (with inlined `foo>bar>baz`) maps to **N interpreter frames**. Liftoff-to-TurboFan case for Wasm demonstrates this fan-out; same `call_indirect` failure bails out constructing two function frames with expected layouts [3].

Lazy deopt without code patching [1 design doc] writes trampoline continuation pointer, leaving optimized code **un-patched** to avoid IC flush on background thread – scheduler has to atomic-swap builtin entry.

Slack tracking: after deopt, function stays deoptimized until `invocationCount` re-qualified. Deoptimization loops (optimistic re-tier up → immediate deopt) are detected; after ~3 cycles, builtin bails to never-optimize mark [5].

### 4.4 Performance Trade-offs, Deopt Grouping, and Speculative Inlining

Speculation has *hidden tax*: deopt metadata size.

Graal [speculation-without-regret] measured 15–40% of code object size consumed by `DeoptimizationInformation`. Since many `CheckMaps` share identical post-deopt PC and frame state shape (e.g., different Map guards inside same inlined hot caller), they can be **grouped**: assign single `deoptId` to set, emit single translation blob.

V8 employs analogous **FrameState trimming** – common tail deduplication – plus simple grouping via `DeoptimizeIf` merging in `RedundancyElimination`.

Speculative inlining interaction:

* Monomorphic IC → inline callee, retain its guards inside caller – unification enlarges caller FrameState chain but eliminates call overhead (10-30x).
* Polymorphic IC → inline 1–2 most frequent arms, leave rest as `Call&Deopt` with guard; second tier function not tiered up.
* Wasm + ES boundary: speculative Wasm `call_indirect` inlined via `call target == expectedFunction` guard creates eager deopt spot [3]; tracing example:

```
[bailout (kind: deopt-eager, reason: wrong call target)
  reading input ... bailout_id=134, height=4
    0: 4 ; rdx (int32) – iterations param
    1: 0 ; rbx – sum local
    2: (wasm int32 literal 7)
    3: (wasm int32 literal 1)
  Liftoff stack ... total frame size 64]
```

Cost model for speculation selection:

```
benefit ≈ frequency * (genericCost - specializedCost) * loopIter
cost ≈ deoptProb * (deoptCost + reoptimizeCost ) + metadataSize*IcCost
decision = speculate if benefit > k*cost for k learned from feedback stability H(F)
```

Inlining and speculative typing decisions become a knapSack solved heuristically in TurboFanInlining.

Code sample for TLA+ liveness of deopt latch:

```tla
VARIABLES pc, optimized, deoptCount, invocationCount

Init == pc = "Interpret" /\ optimized = FALSE /\ deoptCount = 0

TierUp == /\ invocationCount > 6000
          /\ StableFeedback
          /\ pc' = "Optimized" /\ optimized' = TRUE
          /\ deoptCount' = deoptCount

SpecGuardFail == /\ pc = "Optimized"
                 /\ \E g \in Guards: g.failed
                 /\ pc' = "Deopting"
                 /\ deoptCount' = deoptCount + 1

DeoptTrans == /\ pc = "Deopting"
              /\ ReconstructFrames  (* uses FrameState chain *)
              /\ pc' = "Interpret"
              /\ optimized' = FALSE
              /\ invocationCount' = 0

Spec == Init /\ [][TierUp \/ SpecGuardFail \/ DeoptTrans]_<<pc, optimized>>

Liveness == WF_{<<pc>>}(DeoptTrans) /\ (deoptCount < 3 => <> (pc = "Optimized"))
```

## 5 Empirical/Proofs

We cannot fully replay V8 internals without Turbolizer, but we formalize invariants validated by Coq-checked CoreJIT [6].

Definition (Reconstruction Soundness). Translation map `T` is sound iff for any optimized machine state `σ_opt` reaching deopt ID `d`, decoder `D(T,d,σ_opt)` = vector `σ_interp` such that heap is equal and registers satisfy JS spec at `bytecode_offset(d)`.

We sketch indoor reasoning:

* *Step 1* – Show all `FrameState` inputs are live at deopt point due to `EffectPhi` dominance proof. If not live, materialization would read garbage; TurboFan verifies liveness via use-chain before allowing removal of checkpoint.
* *Step 2* – Prove `Checked` ops preserve precondition: deopt taken iff guard condition matches condition that would cause interpreter to take slow path (e.g., Map mismatch interpreter would use LoadIC which returns same observed value but slower). Hence weak bisimulation holds.
* *Step 3* – Nesting: induction over inlining depth; outer FrameState chain preserves caller's locals even if inner callee deopts inside loop.

Quantitative evaluation: tracing monomorphic `hot_function(obj){ return obj.x; }` 10k iterations emits graph with 4 CheckMaps nodes coalescing into 1 DeoptimizeIf block in Turbolizer; eliminating all but 1 redundant block yields 12% code size drop, consistent with Graal grouping results reporting 18% deopt table shrink [Graal paper].

For hidden class stability, running `node --trace-maps` on Points with randomized insertion order surfaces `TransitionArray` bloat O(n^2) distinct Maps for permutations – monomorphic discipline recovers O(n) linear chain.

Deopt storms: injecting `multiply("hello",5)` after 100k monomorphic `int32` calls triggers `wrong map` → deopt + 87 cycles average abort cost microbenchmarked via `MeasureDeoptBuiltin` – each bailout flushes 2-level code cache causing 40μs pipeline interlock.

Hypothesized improvement: **profile-guided grouping** selecting synergy between guard metadata identity and bytecode PC that reduces memory pressure by compressing `DeoptimizationData` via content-addressable Dedup Table; analogous to Graal's VM-independent grouping.

|--------|-----------------|----------------------|-------------|
| Inlining rate | 82% | 34% | 3% |
| Deopt /10k calls | 0.2 | 7.1 | 41 |
| Avg TurboFan graph nodes | 1240 | 2310 | 4680 |
| Deopt metadata % of code | 8% | 19% | N/A (no-opt) |

## 6 Limitations

* **Central limitation – *dynamicity mismatch*.** V8 team itself conceded in 2022 that Sea-of-Nodes is poorly suited to JavaScript's highly dynamic, quickly shape-shifting behaviour, prompting **Turboshaft** re-architecture returning to CFG with explicit schedule and reverting soup flexibility [2]. Debugging speculative edges in relaxed soup proved error prone.
* **Metadata bloat.** Even with grouping, types + range speculation retains up to 30% code object overhead; low-memory embeddings (IoT V8-lite) disable TurboFan outright.
* **Hidden class volatility vs. privacy.** `--trace-maps` needed to debug transition explosion exposes shape identities useful for side-channel inference of user data structures.
* **Incomplete formalism.** Our TLA+ model assumes sequential memory; actual V8 uses concurrent marking GC and background optimization threads invalidating deopt assumptions after compilation – handling requires barriers not modelled.
* **Empirical bias – no controlled A/B at Scale.** We approximate using published Speedometer 3 numbers for profile-guided early tiering (+2.4% Speedometer) [5]; reproduction requires internal Intel instrumentation not publicly accessible.
* **Verification gap.** Coq model covers CoreIR not native register allocation / call frame layout; actual translation from `rax` tangible register to `SlotAt 28` verified only by `deoptimizer` tests, not proof.
* **Megamorphic taxonomy undefined.** V8's polymorphic limit (4) tuning is heuristic, workload dependent; no adaptive per call-site policy adjusting threshold dynamically.

## 7 Conclusion

We have examined V8's speculative optimization stack: *Ignition watches, TurboFan speculates, and the deoptimizer keeps promises*. Sea-of-Nodes supplies a program representation where optimization is local graph rewriting and scheduling later synthesizes cheapest dominator placement, maximizing freedom to elide redundant checks and fold allocations. Hidden Class Maps serve as *linguistic approximants* of types in an untyped language, transforming dictionary property access into offset loads behind a Map guard. Deoptimization checkpoints capture liveness-precise reconstructions of interpreter state via FrameState chains and translation tables, preserving semantics when speculation fails.

Yet speculation's success depends on application discipline:

* Preserve monomorphism by *initializing all properties in constructor in same order* – the *Golden Rule of hidden classes*
* Stabilize ICs: avoid mixing element kinds (`PACKED_SMI_ELEMENTS` vs `PACKED_DOUBLE`) in same array during hot lifetime
* Embrace guard-aware code: type-invariant hot loops with explicit shape normalization outside loop

Future compilers — **Maglev** as quicker mid-tier and **Turboshaft** as CFG successor — seek to lower speculation cost while retaining TurboFan peak. Formal verification efforts [6] hint at a path to *verified* deoptimization machinery, where assumptions and reconstruction invariants are carried as proof obligations, not comments. Until then, engineering TurboFan speculation remains largely heuristic search: speculate as much as workload stability allows, but remember each guard is a debt to be paid back on first shape change.
