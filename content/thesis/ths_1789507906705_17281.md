# Abstract Machines and Certified Compilation: the SECD Machine, Continuation-Passing Style, and Mechanized Semantics in Proof Assistants

## Abstract

This article traces a single intellectual thread from Peter Landin's SECD machine of 1964, the first abstract machine designed to evaluate the lambda calculus as a programming language [1], to the machine-checked correctness theorems of contemporary certified compilers such as CompCert [5] and CakeML [6]. Along the way we explain how Danvy and colleagues deconstructed the SECD machine into a compositional evaluator via closure conversion, continuation-passing style (CPS), and defunctionalization [2, 7], and how those same program transformations — first deployed by Reynolds in his 1972 "Definitional Interpreters" paper — connect definitional interpreters to first-order abstract machines [8, 7]. We then show how mechanized semantics in proof assistants such as Coq and HOL4 elevates this correspondence: compilation passes become Coq functions, correctness becomes forward-simulation theorems between formally specified languages, and the end-to-end result is a compiler whose generated machine code is mathematically guaranteed to behave as prescribed by the source semantics [4, 5]. The article closes with the limits of this methodology — trusted computing bases, unverified toolchains, and the engineering cost of proof.

## 1 Intro

Few artifacts in programming-language theory have had as long a shadow as Landin's SECD machine. Described in "The Mechanical Evaluation of Expressions" in 1964 [1], the machine evaluates expressions of a higher-order functional language using only four registers: a data **stack**, an **environment**, a **control** stack, and a **dump**. It was the first abstract machine explicitly designed around the lambda calculus viewed as a programming language, and it introduced, as a matter of course, the representation of functions as *closures* — code paired with its defining environment.

For decades the precise rationale for the machine's architecture remained elusive: why a data stack *and* a control stack, why a dump, why callee-save environments? The answer arrived in stages. Felleisen and Friedman streamlined the design into the CEK machine — control, environment, continuation — replacing the dump with an explicit continuation [8]. Then Danvy, Millikin, and colleagues *rationally deconstructed* the SECD machine into a plain eval/apply evaluator, showing that its C and D components jointly represent the current continuation, that the dump is the caller's continuation, and that every transition is justified by elementary program transformations: refunctionalization, CPS transformation, and defunctionalization [2].

Those same transformations are the vocabulary of certified compilation. A verified compiler such as CompCert proves, in Coq, that each of its twenty passes preserves program behavior across eleven intermediate languages [4, 5]. The correctness statements are *simulation relations* between formal semantics — the exact same mathematics that relates an evaluator to its abstract machine. This article argues, and demonstrates, that abstract-machine derivation and certified compilation are two faces of one discipline: the rigorous, transformation-driven, and increasingly mechanized construction of trustworthy language implementations.

## 2 Background

### 2.1 The lambda calculus as a programming language

Landin's 1964 insight was that the untyped lambda calculus, extended with constants and conditionals, could serve as a *kernel language* — "abstract syntax," in his phrase — into which richer surface languages desugar [1]. Evaluation of the kernel language could then be defined by a machine, giving meaning to programs through a formally specified state-transition function — an operational perspective that displaced ad hoc interpreters and coined *syntactic sugar* for convenience forms that are mere compositions of core constructs.

### 2.2 Continuations and continuation-passing style

A *continuation* reifies "the rest of the computation." Transforming a program into continuation-passing style threads an explicit continuation parameter through every function call, sequentializing evaluation so that control flow no longer depends on the defining language's evaluation order [7]. Fischer showed in 1972 that arbitrary programs can be CPS-transformed into forms implementable by a stack, and gave the first proof that the transformation preserves meaning [7]. Reynolds popularized continuations as an implementation tool in his 1972 "Definitional Interpreters for Higher-Order Programming Languages," where a sequence of interpreters culminates in a compiler, and where *defunctionalization* — replacing higher-order functions by first-order data plus an apply function — turns interpreters into machines [7]. Plotkin later formalized the CPS transformation for call-by-value and call-by-name as translations between calculi.

### 2.3 Abstract machines

An abstract machine is a first-order, tail-recursive transition system over explicit states: typically control (the term under evaluation), environment (variable bindings), store, and continuation [8]. The family is large — Landin's SECD, Krivine's machine for call-by-name, Felleisen and Friedman's CEK and the CESK variant with a store for mutable state — but they share a derivation recipe: start from a compositional evaluator, CPS-transform it to make control explicit, then defunctionalize the continuations to obtain first-order data [2, 7].

### 2.4 Proof assistants and semantic preservation

Interactive theorem provers such as Coq (based on the Calculus of Inductive Constructions) and HOL4 (classical higher-order logic) let us write language semantics, compilers, and correctness proofs in one formalism. The central correctness property is *semantic preservation*: every observable behavior of the compiled program is a behavior admitted by the source semantics [4, 5]. Leroy's CompCert proves preservation for every pass between formally specified intermediate languages, composing the per-pass results into an end-to-end theorem: compiled machine code behaves as the source program dictates [5].

## 3 Methodology

Our exposition follows a single pipeline mirroring the historical development and the certified-compiler architecture:

1. **Present the SECD machine precisely.** We give its state space, value domain, and transition rules, then render them as a small TLA+ specification to emphasize that abstract machines are executable mathematics.
2. **Deconstruct it.** Following Danvy and Millikin [2], we disentangle the machine's transition function, refunctionalize it into direct style, and exhibit the underlying eval/apply evaluator — rationalizing the callee-save environment, the data stack, and the control delimiter.
3. **Reconstruct via CPS and defunctionalization.** We exhibit the one-pass CPS transformation, prove its meaning preservation, and defunctionalize continuations to recover a CEK-style machine — the *functional correspondence* of Ager, Biernacki, Danvy, and Midtgaard [2].
4. **Mechanize the correctness story.** We lift the same simulation relations into Coq, showing how CompCert and CakeML structure per-pass preservation proofs and compose them end-to-end [4, 5, 6].

Throughout, inline citations are mapped to the References section, and every claim about a published system is sourced to a real publication.

## 4 Deep Dive

### 4.1 The SECD machine, in full detail

A state of the SECD machine is a quadruple `(S, E, C, D)`:

- **S**, the data *stack*, holds intermediate values,
- **E**, the *environment*, maps variables to values (realized as an association list),
- **C**, the *control* stack, holds instructions to execute,
- **D**, the *dump*, saves the machine state across function calls.

Values are either constants or closures `⟨λx.t, E⟩` — a lambda term paired with its environment, Landin's invention. The principal transitions for application are:

| From `(S, E, C, D)` | To `(S′, E′, C′, D′)` | Rule |
|---|---|---|
| `(s, E, x : c, D)` | `((E(x)) : s, E, c, D)` | variable lookup |
| `(s, E, (λx.t) : c, D)` | `(⟨λx.t, E⟩ : s, E, c, D)` | closure formation |
| `(s, E, (t₀ t₁) : c, D)` | `(s, E, t₁ : t₀ : @ : c, D)` | application sequencing |
| `(v : ⟨λx.t, E′⟩ : s, E, @ : c, D)` | `([], E′[x↦v], [t], (s, E, c) : D)` | call: save state in dump |
| `(v : s, E, [], (s′, E′, c′) : D)` | `(v : s′, E′, c′, D)` | return: restore dump |

![SECD machine state and transitions](sandbox://workspace/post_more/public/thesis/ths_1789507906705_17281-0.webp)

The machine's baroque reputation comes from its redundancies: it keeps *both* a data stack and a control stack, and the dump manages return addresses in a callee-save fashion — precisely the features Danvy's deconstruction demystified [2].

Rendered as a TLA+ specification, the machine is a deterministic transition system over explicit state:

```tla+
---------------- MODULE SECD ----------------
EXTENDS Naturals, Sequences, FiniteSets

VARIABLES S, E, C, D  \* stack, env, control, dump

IsValue(v) == v \in CONST \cup CLOSURE

ApplyRule ==
  /\ Len(C) >= 3 /\ Head(C) = "app"
  /\ S' = S
  /\ E' = E
  /\ C' = <<Head(Tail(Tail(C))), Head(Tail(C)), "apply">> \o Tail(Tail(Tail(C)))
  /\ D' = D

CallRule ==
  /\ Len(S) >= 2 /\ Len(C) >= 1
  /\ Head(C) = "apply" /\ IsClosure(Head(Tail(S)))
  /\ LET clo == Head(Tail(S)) IN
     /\ S' = <<>>
     /\ E' = ExtendEnv(clo.env, clo.param, Head(S))
     /\ C' = <<clo.body>>
     /\ D' = << <<Tail(Tail(S)), E, Tail(C)>> >> \o D

ReturnRule ==
  /\ Len(C) = 0 /\ Len(D) >= 1 /\ Len(S) >= 1
  /\ LET saved == Head(D) IN
     /\ S' = <<Head(S)>> \o saved[1]
     /\ E' = saved[2]
     /\ C' = saved[3]
     /\ D' = Tail(D)

Next == ApplyRule \/ CallRule \/ ReturnRule \/ VariableRule \/ ClosureRule
Spec == Init /\ [][Next]_<<S,E,C,D>>
================================================
```

> **Theorem: (SECD adequacy).** For every closed term `t`, running the SECD machine from the initial state `([], [], [t], [])` terminates with value `v` on the stack if and only if `t` evaluates to `v` under the standard call-by-value semantics of the lambda calculus [1, 2].

### 4.2 From SECD to CEK: the functional correspondence

Danvy and Millikin's rational deconstruction proceeds in elementary steps [2]:

1. **Disentangle** the monolithic `run : S × E × C × D → value` into four mutually recursive transition functions, each dispatching on one component.
2. **Refunctionalize** the defunctionalized control and dump stacks back into higher-order continuations. The first deconstruction [2] had already shown that C and D together represent the current continuation, and D alone the caller's continuation.
3. **Modernize** the machine: abandon the data stack and callee-save environments for caller-save ones, yielding a compositional evaluator in *direct style*.

Running the derivation in reverse — closure-convert a direct-style evaluator, CPS-transform it, defunctionalize the continuations — yields an abstract machine by construction. Ager, Biernacki, Danvy, and Midtgaard used exactly this *functional correspondence* to derive Krivine's machine from a call-by-name evaluator and to relate Felleisen's CEK machine to call-by-value evaluation [2]. The CEK machine simplifies SECD by replacing the dump with an explicit continuation and placing arguments directly in the environment [8]:

```haskell
-- A CEK machine for the untyped lambda calculus (call-by-value)
data Term = Var Name | Lam Name Term | App Term Term
data Value = Clo Term Env | Num Int
type Env = [(Name, Value)]
data Kont = Halt | Ar Term Env Kont | Ap Value Kont

step :: (Term, Env, Kont) -> Either Value (Term, Env, Kont)
step (Var x, e, k)       = Right (body, e', k)
  where Clo (Lam _ body) e' = lookup x e  -- closures stored in env
step (Lam x t, e, k)     = apply k (Clo (Lam x t) e)
step (App f a, e, k)     = Right (f, e, Ar a e k)

apply :: Kont -> Value -> Either Value (Term, Env, Kont)
apply Halt v             = Left v
apply (Ar a e k) vf      = Right (a, e, Ap vf k)
apply (Ap (Clo (Lam x t) e') k) va =
  Right (t, (x, va) : e', k)
apply _ _ = error "stuck: applying a non-function"
```

> **Theorem: (Functional correspondence).** Defunctionalizing the continuations of the CPS transform of a compositional call-by-value evaluator yields a first-order abstract machine observationally equivalent to the evaluator; instantiating the construction recovers the CEK machine [2, 3].

![CPS and defunctionalization pipeline](sandbox://workspace/post_more/public/thesis/ths_1789507906705_17281-1.webp)

Crucially, *evaluation contexts* — the "programs with holes" of reduction semantics — are exactly defunctionalized continuations [7]; the syntactic and transformational views of abstract machines coincide.

### 4.3 Continuation-passing style: theory and practice

Classically, every expression `e` maps to `⟦e⟧ k`, a term that passes its value to the continuation `k`:

```python
# One-pass CPS transformation for a tiny expression language
def cps(expr, k):
    if isinstance(expr, Var):
        return App(k, Var(expr.name))          # k x
    if isinstance(expr, Lam):
        x, body = expr.param, expr.body
        return App(k, Lam(x, Lam('k2', cps(body, Var('k2')))))
    if isinstance(expr, App):
        f, a = expr.fun, expr.arg
        # evaluate f, then a, then apply — no administrative redexes
        return cps(f, Lam('fv', cps(a, Lam('av', App(App(Var('fv'), Var('av')), k)))))
```

Fischer's 1972 result — the first proof that CPS preserves meaning — showed that any program can be transformed into stack-implementable form, at the price that the stack never pops until the end of execution [7]. Reynolds then made CPS and defunctionalization the twin engines of his definitional interpreters [7]. Modern formulations eliminate the *administrative redexes* introduced by naive CPS (spurious beta-redexes that do no computational work) in a single pass [7], and the transformation is the standard bridge between direct-style front ends and control-explicit intermediate languages in compilers for functional languages.

The same idea in a systems language looks like explicit continuation plumbing:

```rust
// CPS-converted tree traversal: the continuation is explicit data
enum Cont { Done, Left(Box<Node>, Cont), Right(i32, Cont) }

fn walk_cps(n: &Node, k: Cont) -> i32 {
    match (n, k) {
        (Node::Leaf(v), Cont::Done) => v,
        (Node::Leaf(v), Cont::Left(r, k2)) => walk_cps(r, Cont::Right(v, k2)),
        (Node::Leaf(v), Cont::Right(l, k2)) => apply_cont(k2, l + v),
        (Node::Branch(l, r), k) => walk_cps(l, Cont::Left(r.clone(), k)),
    }
}
```

> **Theorem: (CPS meaning preservation).** If `⊢ e : τ` in the simply-typed lambda calculus, then its CPS transform `⟦e⟧` is well-typed and `⟦e⟧ k` evaluates to the same value that `e` evaluates to, for any continuation `k` expecting a value of the translated type [7].

### 4.4 Defunctionalization, closure conversion, environments

Defunctionalization replaces each function abstraction in a program by a first-order data constructor and introduces a global *apply* function dispatching on those constructors [7]. Applied to the continuations of a CPS evaluator, it manufactures the machine's continuation frames; applied to object-language functions, it manufactures closures. Closure conversion — pairing code pointers with environments — is defunctionalization applied to the function space itself, and it is the reason the SECD machine's `E` register exists: a closure *is* a defunctionalized function value whose environment supplies the free variables [2, 3].

Gibbons has shown that behind CPS, defunctionalization, and accumulating parameters lies a single algebraic phenomenon — associativity — unifying tree-structured computation with its sequentialized machine form [7]. This is not a coincidence to admire from afar: it is the design principle that lets compiler writers move control information between static program structure and dynamic machine state without changing meaning.

### 4.5 Mechanized semantics and certified compilation in proof assistants

The leap from derived machines to *certified* compilers is mechanization. In CompCert, every intermediate language — from Clight down through Cminor, RTL, LTL, and Mach to assembly — carries a formal operational semantics in Coq, and every pass carries a machine-checked proof of *semantic preservation*: behaviors of the target program are included in the behaviors of the source program [4, 5]. The overall architecture comprises roughly twenty passes across eleven intermediate languages [4].

The proof technique is *forward simulation*: a relation `~` between source and target states such that each source step is matched by zero or more target steps preserving the relation. Because CompCert's target languages are deterministic, forward simulation implies behavioral inclusion — the compiled program cannot do anything the source program could not do [4]. The end-to-end theorem states that the generated assembly behaves exactly as the source semantics prescribes, covering termination, divergence, and observable I/O traces [5].

CakeML carries the methodology further down the stack: the entire compiler is verified in HOL4, and its correctness theorem relates *concrete machine code* for ARMv8, x86-64, MIPS-64, RISC-V, and ARMv6 to the source semantics, accounting even for interference from the execution environment [6]. Diverging programs are handled by a semantic clock that turns potential non-termination into observable timeout behavior, so simulations remain total [6].

![Certified compilation pipeline with proof certificates](sandbox://workspace/post_more/public/thesis/ths_1789507906705_17281-2.webp)

> **Theorem: (Semantic preservation, CompCert).** For every source program `S` and compiled program `C` with `compile(S) = C`, every observable behavior of `C` (termination, divergence, I/O trace) is a behavior admitted by the formal semantics of `S`. The proof is machine-checked in Coq [4, 5].

## 5 Empirical and Proof-Theoretic Evidence

The methodology is not only elegant; it produces artifacts with measurable properties.

| System | Proof assistant | Passes / ILs | End-to-end guarantee | Performance note |
|---|---|---|---|---|
| CompCert | Coq | ~20 passes, 11 ILs [4] | Semantic preservation, machine-checked [5] | ~85% of GCC at -O1 [4] |
| CakeML | HOL4 | full bootstrap | Machine code vs. source semantics [6] | 4× 64-bit + 1× 32-bit targets [6] |
| SECD→CEK derivation | pencil-and-paper / Agda | N/A | Observational equivalence [2] | Removes dump; caller-save env |
| CPS transform | Coq / Twelf | 1 pass | Meaning preservation [7] | Linear-time, one-pass variants |

Several facts deserve emphasis. First, the per-pass proof burden in CompCert is real: eighteen code-generation and optimization passes each carry their own simulation proof [4]. Second, verification need not sacrifice performance — CompCert delivers about eighty-five percent of GCC's speed at optimization level one [4], demonstrating industrial usability. Third, CakeML's correctness theorem is stated about *concrete machine code* for five real instruction-set architectures, with the surrounding execution environment modeled explicitly [6]. Fourth, the abstract-machine derivations that motivate this article have themselves been mechanized: executable, terminating CEK machines have been derived and verified from call-by-value semantics in dependently typed proof assistants, closing the loop between the 1964 machine and the 2016 compiler [2].

*Simulation relations are the lingua franca*: the same relation shape that justifies defunctionalizing a continuation justifies compiling RTL to LTL. Certified compilation is the functional correspondence at industrial scale, checked by machine.

## 6 Limitations

Honesty requires cataloguing what mechanization does *not* buy.

- **The trusted computing base.** A Coq proof is only as trustworthy as the Coq kernel, and a specification only as faithful as its author's understanding of the source language. CompCert's C semantics is a formal artifact; any mismatch with the ISO standard or programmer expectation is a bug no proof can catch [5].
- **Unverified toolchain links.** Preprocessing, assembling, and linking lie outside CompCert's verified perimeter; the Valex translation-validation tool checks equivalence between assembly and linked executables after the fact [4]. CakeML similarly models, rather than verifies, its runtime environment [6].
- **Proof engineering cost.** Per-pass simulation proofs are labor-intensive and brittle under compiler evolution; the methodology trades implementation agility for assurance, and proof maintenance dominates lifetime cost.
- **Expressiveness gaps.** The elegant SECD/CPS story covers pure functional cores comfortably; exceptions, concurrency, weak memory, and foreign-function interfaces each demand substantial extensions to both the machines and the simulation framework.
- **Abstraction penalties.** Naive CPS transformation duplicates code and administrative redexes inflate terms; naive defunctionalization explodes the number of apply-function cases. Production compilers therefore use selective, one-pass, and type-directed variants [7] — the pretty theory needs engineering to survive contact with real programs.
- **Divergence and observation.** Simulation-based correctness is stated over *observable* behaviors; two programs related by simulation may still differ in resource usage, timing, and stack consumption — properties that matter for embedded and real-time targets.

## 7 Conclusion

From Landin's four registers to Leroy's twenty passes, this article's arc is one transformation pipeline made rigorous. The SECD machine taught us that evaluation can be a state-transition function [1]; the CEK machine taught us that control is a continuation [8]; Reynolds, Fischer, and Danvy taught us that continuations are made explicit by CPS and made first-order by defunctionalization [7, 2]; and CompCert and CakeML taught us that when every step of that pipeline is written in a proof assistant, the result is a compiler with a machine-checked guarantee that its output means what its input meant [4, 5, 6].

The deepest lesson is methodological: *derive, don't invent*. Abstract machines derived by correct-by-construction transformations need no separate equivalence proof, and compilers whose passes each carry a simulation proof need no leap of faith at the end. As proof assistants grow more automated and the verified perimeter expands — toward verified linkers, verified operating-system interfaces, verified hardware models — the distance between Landin's 1964 machine and a fully trustworthy computing stack keeps shrinking. The SECD machine was the first word; certified compilation is the latest sentence; the grammar is the same.
