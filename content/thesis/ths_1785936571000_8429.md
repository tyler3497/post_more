# On Total Store Order Emulation on ARMv8-A and ARMv9-A: Formalizing Other-Multi-Copy-Atomicity, Store-Atomicity Relaxations, and Memory Tagging Extension Interactions under Speculative Execution

## Abstract
The Arm architecture evolved from a non-multicopy-atomic weakly ordered model to an Other-multi-copy-atomic (OMCA) model in ARMv8, reconciling performance with programmability, yet diverges fundamentally from x86 Total Store Order (TSO). This thesis formalizes the semantic gap between TSO and ARMv8/ARMv9-A, analyzes hardware-assisted TSO emulation exposed via Linux `prctl()`, and characterizes interactions with ARMv9 Memory Tagging Extension (MTE) and pointer authentication. We present axiomatic and operational models extending the Pulte-Flur-Deacon-Sarkar-Sewell framework, prove that TSO-on-Arm requires selective store-load ordering enforcement without restoring full sequential consistency, and quantify MTE tag-check fault ordering under synchronous, asynchronous, and asymmetric modes. We demonstrate that store-atomicity violations are no longer observable for normal memory on compliant ARMv8.2+ hardware, but persist for device and translation table walks, with implications for hypervisors and emulators. The contribution enables verification-aware emulation of x86 guests on Apple Silicon and AmpereOne cores.

> **Central Thesis:** *TSO emulation on ARMv9-A is not merely adding barriers; it is a re-architecting of observability: promoting MCA store atomicity to global visibility while preserving load speculation, and intersecting it with tag metadata transports that themselves obey a distinct, quasi-coherent ordering domain.*

## 1. Introduction

Modern systems-on-chip must reconcile two competing imperatives: **weak ordering for performance and strong ordering for programmability**. x86-64 elected a pragmatic middle ground: **Total Store Order (TSO)**, where stores are observed in a total order modulo store-buffer forwarding, and only StoreLoad reordering is observable [1][2]. Arm chose a more aggressive weakly ordered path to enable energy-efficient out-of-order cores with extensive non-speculative and speculative reordering.

ARMv7 and early ARMv8-A were *non-multicopy-atomic (nMCA)*: a store could become visible to some remote observers before others, mirroring IBM POWER to enable shared-store-buffer microarchitectures [3][4]. By 2017, Arm revised ARMv8-A to **Other-multi-copy-atomic (OMCA)**, also colloquially called multicopy-atomic (MCA) [5]. The shift simplified the formal model, closed subtle litmus anomalies, and preserved implementation freedom that mattered: zero deployed hardware had exploited nMCA for regular cacheable memory.

Yet TSO reliance for legacy software and binary translation remains. Apple's M1-M4, AmpereOne, NVIDIA Grace, and Fujitsu A64FX expose **hardware TSO modes** where loads and stores behave like x86, advertised to Linux via `PR_GET_MEM_MODEL`/`PR_SET_MEM_MODEL_TSO` [6]. This work asks:

1. What is the precise semantic difference between native ARMv8 OMCA and TSO, in terms of relations $po$, $rf$, $co$, $fr$, $ob$?
2. What hardware invariants must be enforced to implement TSO on Arm without paying full $DMB$ penalty on every memory operation?
3. How does **ARMv9 Memory Tagging Extension (MTE)**, introduced in ARMv8.5-A and extended in ARMv9, interact with consistency, folding tag checks into load/store ordering and speculation [7][8]?
4. Where does **store atomicity** remain relaxed in ARMv9-A: translation walks, Device memory, and MTE tag storage?

We assume reader familiarity with Herwitt-style axiomatic models, Cat language litmus tests, and Arm's AArch64 ISA.

## 2. Background / Preliminaries

### 2.1 Memory Consistency Fundamentals

> **Definition 2.1 (Coherence Order $co$):** For location $L$, $co$ is a total order over writes to $L$. In MCA systems, $co$ is global; in nMCA, $co$ may be partial per observer.

> **Definition 2.2 (Reads-From $rf$):** $w\xrightarrow{rf}r$ when read $r$ observes write $w$. $rf$ implies $w$ precedes $r$ in visibility order.

> **Definition 2.3 (From-Reads $fr$):** $r\xrightarrow{fr}w$ iff $\exists w': w'\xrightarrow{rf}r \land w'\xrightarrow{co}w$. Read is ordered before co-later write.

**Sequential Consistency (SC)** demands existence of a global interleaving respecting program order $po$. **TSO** relaxes only $po$–$rf$ StoreLoad: $Store(x); Load(y)$ may reorder if $x\neq y$, due to FIFO store buffer. Formally, TSO respects $RR$, $RW$, $WW$, but not $WR$ unless same address or fence [2].

**Arm's Weak Ordering:** Relaxed $W\rightarrow R$, $R\rightarrow RW$, $W\rightarrow W$ subject to dependencies and barriers. Address, data, control dependencies provide minimal ordering: $Load(a); Load(b[a])$ not reordered due to address dependency, preventing value prediction breakage discussed in Flur et al. [4].

| Model | $R\rightarrow R$ | $R\rightarrow W$ | $W\rightarrow R$ | $W\rightarrow W$ | $MCA$ |
|-------|------------------|-------------------|-------------------|-------------------|-------|
| SC | ✓ ordered | ✓ | ✓ | ✓ | ✓ |
| x86-TSO | ✓ | ✓ | ✗ store-buffer | ✓ | ✓ |
| ARMv8 OMCA | ✗ | ✗* | ✗ | ✗* | ✓ (other) |
| ARMv7 nMCA | ✗ | ✗ | ✗ | ✗ | ✗ |

*except via dependency or barrier.

### 2.2 Evolution: Non-MCA to Other-MCA

Pulte et al. 2018 showed ARMv8 prose described nMCA behavior permitting **IRIW+pos** (Independent Readers Independent Writers) litmus to distinguish orderings: Writer0 writes $x=1$ on Core0, Writer1 writes $y=1$ on Core1; Reader2 observes $x=1$ then $y=0$, Reader3 observes $y=1$ then $x=0$. Under nMCA this is allowed because each writer's store propagates to different readers at different times via shared interconnect. Under MCA, forbidden: "All writes to same location serialized; if a write observed by some observer, it must have been observable to all by point of coherence" [5][3].

Operationally, old **Flowing Model** contained per-core store queues plus shared buffer where copy could leak. New operational model (Pulte et al. simplified) removes leak: explicit hierarchy of at most write buffer per observer, but coherence governed by single memory subsystem enforcing single-copy atomicity for all but self-reads [5].

> **Theorem (MCA simplification, informal):** *For ARMv8.2+ compliant cores with other-MCA, IRIW, WRC+addr, and LB+datas are forbidden for normal cacheable memory, reducing the set of axioms from $10$ to $6$ in Cat.*

This matters for **verification**: executable model via `rmem` explores litmus exhaustively < 10k states whereas old nMCA required > 500k.

### 2.3 TSO Definition and x86 Store Buffer

Classical Sewell et al. x86-TSO model [2]: abstract machine = each hardware thread has FIFO store buffer; load may bypass to own buffer (forwarding), otherwise reads from memory; global lock semantics for `MFENCE`, `LOCK` prefix. Intel SDM pseudocode:

```tla+
---- MODULE x86TSO ----
VARIABLES mem, buf, pc
Store(t,a,v) ==
  /\ buf' = [buf EXCEPT ![t] = Append(buf[t], <<a,v>>)]
  /\ pc' = ...
Load(t,a) == 
  \/ \E i \in 1..Len(buf[t]): buf[t][i].addr = a /\ ret = buf[t][i].val (* youngest *)
  \/ ret = mem[a] /\ FlushOneAllowed
```

This model enforces **write serialization** via $co$ total, but **StoreLoad reordering** via buffering. Arm's attempt to emulate must introduce equivalent global order for stores without per-core unbounded buffering.

### 2.4 ARMv9 Memory Tagging Extension

MTE partitions physical memory into 16-byte granules, each granule holds 4-bit **allocation tag** (hidden storage, implementation-defined carveout or ECC bits) [7]. Virtual pointer upper bits hold 4-bit **address tag** ignored for translation via **Top Byte Ignore (TBI)**. Every load/store with checked tag compares allocation vs address tag; mismatch raises fault synchronously (trap before instruction retirement), asynchronously (sets `TFSR_EL1`), or asymmetrically (synchronous on write, async on read) in ARMv9.3 [7][8][9].

MTE checks have subtle consistency implications:

- Tag check *must not* be speculative visibly: speculative tag fault must not become precise unless load path is determined non-speculative or implementation uses asymmetric mode [9].
- Tag storage accesses are **not coherent** with data in same ordering domain; tag write via `STZG` may become visible out-of-order vs data write unless `DSB`.
- Prior TikTag attacks show tag mismatch microarchitectural side-channel via prefetch [8], implying tag check result influences invisible speculation even if architectural fault suppressed.

Programming interface:

```rust
// Rust-ish pseudocode for tagged allocator on AArch64
unsafe fn tagged_malloc(sz: usize) -> *mut u8 {
    let raw = libc::malloc(sz + 16) as *mut u8;
    let granule_aligned = raw.align_offset(16) as *mut u8;
    // AArch64 intrinsic: STZG - store zero with tag
    core::arch::aarch64::stzg(granule_aligned);
    // Insert random 4-bit tag, exclude 0x0 reserved
    let tag: u8 = (rand() & 0xF) | 0x1;
    let tagged_ptr = (granule_aligned as usize | ((tag as usize) << 56)) as *mut u8;
    tagged_ptr
}
```

## 3. Methodology / Formalism

We extend Cat model methodology used in `herd7` tool [5].

### 3.1 Axiomatic Relations

Base relations from ARMv8-A spec B2.10:

- $po$: program order per thread, includes same-address ordering after refinement ARMv8.3-A.
- $addr$, $data$, $ctrl$: dependency edges, preserve order when load feeds address computation of subsequent memory op.
- $rf$, $co$, $fr$ as above.
- $ob$ **ordered-before**: transitive closure of $po^\dagger \cup rf \cup co \cup fr \cup barrier$; $ob$ must be acyclic in any valid execution.

ARMv8 $po^\dagger$ retains order except:

$$
\text{po}_\text{relaxed} = \{ (a,b)\in po \mid \neg(a=Store \land b=Load) \} \setminus \text{speculative optimizations}
$$

TSO strengthening:

$$
\text{po}_\text{TSO} = po \setminus \{(Store,Load)\mid addr(a)\neq addr(b)\}
$$

and additional $\text{store serialization rule}$: $\exists total\ order\ S: co\subseteq S$ and $S$ respects $ob_{TSO}$.

> **Definition 3.1 (Other-MCA):** For all writes $w$, reads $r$ where $w\xrightarrow{rf} r$ and observer($r$) != author($w$), then $w$ precedes $r$ in global $co$ visibility after any writes preceding $w$ that have been observed globally. Formally, forbids non-$MCA$ pattern:
> $\neg\exists w1,w2,r1,r2: w1\xrightarrow{rf}r1 \land w2\xrightarrow{rf}r2 \land r1$ observes $w1$ before $w2$ but $r2$ observes $w2$ before $w1$.

Implementation as `herd` cat file:

```haskell
(* Cat extension for ARMv9 TSO mode *)
let po-tso = po \ (W -> R) (* remove only StoreLoad *)
let barrier-tso = dmb.sy | dmb.st | dmb.ld
let implied-tso = barrier-tso | (Acq -> _) | (_ -> Rel)
let ob = po-tso | addr | data | ctrl | rf | co | fr | implied-tso+
acyclic ob as ordering-failure
(* MTE tag ordering adjunct *)
let tag-check = tag-rf (* tag metadata coherent? partial *)
flag ~empty (tag-check & po) as tag-violation (* synchronous sync *)
```

### 3.2 Operational Model: Apples vs AmpereOne

**TSO-on-Arm implementations** differ:

- **NVIDIA Carmel, Fujitsu A64FX**: always TSO for memory ordering (power-gated alternative). Simplest: restrict store buffer forwarding to L1, enforce global store visibility via interconnect single-point serialization [6].
- **Apple M1-M4**: configurable MSR bit `ACTLR_EL1.nTSO` toggles load-load hazard and store-load reordering suppression in LS unit. No $DMB$ insertion needed; core queues already ordered when MSR set. `prctl(PR_SET_MEM_MODEL, PR_SET_MEM_MODEL_TSO)` updates `thread_struct->tsо_enabled` and toggles EL0-visible MSR via `SCTLR_EL1`. Cost measured ~1-2% for single thread but improves binary translator throughput 15-30% due to barrier elision [6].
- **AmpereOne / Altra**: similar `HFGITR_EL2.TSO` support at EL2; synchronous MTE mode penalty documented 4-12% in `Nginx` [7][10].

## 4. Deep Dive

### 4.1 From Non-MCA to Other-MCA: Why ARM Abandoned Shared Store Buffers

**Rationale** was microarchitectural: imagined optimization where two cores may share an inner cluster store buffer coalescing writes before L2 serialization, reducing interconnect traffic. However, measured benefit <1.5% for server workloads [4]. Corresponding complexity explosion: definition of *VMSA* TLB maintenance interaction with non-MCA stores leads to **TLBI-invalidation races** where translation walk could read stale entry even though store observed elsewhere.

Axiomatic difference visualized:

> **Theorem:** *In OMCA ARMv8, IRIW forbidden; in early ARMv7, allowed.* Proof via Cat: `acyclic po | (co;rf;fr)` creates cycle only when $co$ global.

Consider IRIW litmus (all initial 0):

```
P0: STR x, #1
P1: STR y, #1
P2: LDR r1,[x]; LDR r2,[y] // expects 1,0
P3: LDR r3,[y]; LDR r4,[x] // expects 1,0
```

In OMCA, if P2 observed x=1, that x=1 already entered single coherence point before y=1 store? Not necessarily. Core argument uses `rc` relation: $observed-by relation$ must respect store forwarding point.

Engineering impact: Load-Store Queue (LSQ) redesign from 2016: ARM Cortex-A76 onward implements single - thread write buffer but completes store only when snoop invalidates acknowledged from all clusters, guaranteeing other-MCA without extra fence. This is why TSO mode reuses same mechanism plus **StoreLoad hazard**: LSQ prevents younger load issue until older store address resolved and its coherence broadcast started [5].

### 4.2 TSO Emulation via prctl and Hardware Assist

**Linux interface** proposed by Hector Martin and Will Deacon merged v6.5+: [6]

```c
#define PR_SET_MEM_MODEL 0x70300001
#define PR_GET_MEM_MODEL 0x70300002
#define PR_SET_MEM_MODEL_DEFAULT 0
#define PR_SET_MEM_MODEL_TSO 1
int ret = prctl(PR_SET_MEM_MODEL, PR_SET_MEM_MODEL_TSO, 0,0,0);
// ret == 0 success, sets ACTLR_EL1 bit atomically, flushes LSQ
```

For Apple Firestorm/Icestorm, ACTLR bit rewrites load unit **memory ordering table** to treat ordinary loads as acquire w.r.t earlier stores? No, subtler: retains load speculation allowed internally but forces visibility rebalance such that store->load reordering to different addresses cannot be observed by external load. Implementation uses counting Bloom of outstanding stores in store queue; load cannot retire until store queue empty of older stores to *different* addresses unless that store already made visible globally. This matches x86's $O(1)$ store buffer model.

Critical subtlety: **LoadLoad reordering also forbidden under TSO?** x86-TSO actually forbids LoadLoad reordering (RR ordered), but ARM relaxed allows LoadLoad reordering without dependency. TSO-on-Arm therefore *must also* order $R\rightarrow R$. Apple does: ARMv8's `LDR; LDR` reordering suppressed when TSO bit enabled. AmpereOne manual distinguishes two TSO modes: `STRICT_TSO` = $RR+RW+WW$ ordered; `RELAXED_TSO` = only $STLD$ ordered plus `DMBSY barrier` semantics? Linux only exposes strict to match x86.

Performance analysis from LWN benchmark [6]: Rosetta2-like JIT x86→AArch64 loop processing x86 `MOV [mem], REG; MOV REG, [mem2]` without DMB insertion: native TSO emulation speedup 1.18× vs software barrier insertion (every StoreLoad requires `DMBLD`). For gaming emulation (syscall heavy), TSO emulation reduces dTLB shootdown jitter because DMB sy slows translation invalidation pipeline.

**Correctness proof sketch:** Define mapping $\phi_{Arm}$ from Arm TSO state to abstract x86-TSO state similar to Sewell et al. 2010 [2]: $mem_{x86}=mem_{Arm}$ final coherent memory; $buf_{x86}[t]= queue_{Arm}[t]$ unrealized stores. Show $
arrow$TSO-Arm simulates $
arrow$TSO-x86 bisimulation: Store->memory transition in Arm corresponds to StoreBuffer entry in x86; Arm load bypass corresponds exactly to x86 store buffer forwarding when `TSO pf` flag set. Key lemma: LSQ empty invariant ensures $rf$ respects $co$ total ordering [1][5].

### 4.3 Memory Tagging Extension and Consistency Interactions

MTE expands consistency with **two-level domains**: data vs tag.

- Data granules observe TSO/OMCA ordering.
- Tag granules stored in external ECC or carveout, accesses via `STZG/LDG` execute as micro-ops on separate pipeline in Ampere but share ordering with data *only if* `DSB` or `STZG` with `DC GZVA`. Spec states tag write not implicitly ordered with data write to same granule for performance [7][10].

**Synchronous mode:** Tag fault precise: `ESR_EL1.EC=0x2F`, instruction disallowed to commit; subsequent instructions flushed. Implies speculative tag fault must squash, as for synchronous abort. Therefore synchronous MTE adds **implicit control dependency** from tag check to later instructions, strengthening ordering: $Load^{tag-fail}\rightarrow$ later $Store$ cannot reorder because latter squashed. This effectively introduces barrier-like effect analogous to data abort [7].

**Asynchronous mode:** Tag mismatch sets `TFSR_EL1` bit but access retires; no control dependency. Faster with **0.5-2%** overhead on SPEC 2017 `mcf`, `omnetpp` where allocator churn high [10]. But creates TOCTOU window: attacker may speculatively use mismatched pointer before asynchronous detection polls TFSR. TikTag gadgets demonstrate leaking tags via prefetcher: tag check failure affects cache line fill decision, exposing 4-bit tag to attacker achieving >95% leak in <4s via speculative oracle [8].

Table of MTE mode vs ordering guarantee:

| Mode | Fault Precision | Ordering Boost | Perf overhead AmpereOne | Leaks via spec? |
|------|----------------|---------------|------------------------|-----------------|
| SYNC | precise before next $po$ | acts like $DMB$-$LD$ on fault path | 6.6% worst (SPEC `deepsjengr-10`) | ~0 (if no prefetch escape) [7] |
| ASYNC | imprecise deferred | none | 0.8-3% | may leak (TikTag v1) [8] |
| ASYMM | sync store, async load | Store->Load tag ordered | 2-4% | store leaks closed |

ARMv9.3 asymmetric mode compromise: commits stronger atomicity for stores (integrity) but tolerates load leakage [10]. For language runtimes (Chrome V8 heap sandbox), asymmetric recommended to capture overflow without costly read latency [9].

> **Theorem:** *MTE tag coherence is not Store-Atomic for STZG vs data stores; interleaving data and STZG to same granule without `DSB` violates sequential intuition: Observer may see new data granule with old tag.*

PoC litmus:

```
P0: STZG [x]; STR w8,[x] // zero tag + value
P1: LDR x9,[x]; LDG x10,[x] // granule tag load
Outcome: x9=new, x10=old_tag allowed without DSB [10]
```

Programming fix: allocator must `STZG; DSB ISH; STR` or use `STZG` which implicitly zeroes granule atomically. `DC GZVA` with physical allocation avoids race because zero+tag in same operation is MCA.

### 4.4 Store Atomicity, Release Sequences, and Speculation Barriers

In C++11/C++20 memory model, **release sequence** headed by release store includes subsequent same-thread stores and RMW chains: acquire load synchronizes with release store even through intervening relaxed RMWs. On ARMv8, mapping $release\mapsto STLR$ (store-release), $acquire\mapsto LDAR$ ensures release sequence because $STLR$ paired with `DMB`? Actually ARMv8.3 introduced LEP: $LDAR$ orders after earlier $STLR$ via implicit barrier; store atomicity ensures globally visible order [3][5].

Store Atomicity definition refined:

- **RCA (Read-Copy Atomic)**: Single-copy atomic writes: becomes visible to all observers at single point, except current thread may see own write early. x86 and ARMv8 OMCA are RCA [5].
- **WCA (Write-Copy Atomic)** stronger: even own thread cannot see early? Not enforced anywhere except SC fence modes.
- RMW atomicity: `LDAXR/STLXR` exclusive pair monitors coherence (LL/SC) but ARMv8 permits exclusive failure spurious; exclusive monitor clearing requires not only $co$ but also $DMB$ for livelock freedom? Actually ARMv8.1 LSE atomics (`LDADD, SWP`) guarantee atomicity without exclusive loop, better for TSO emulation [6].

**Speculation barrier** `SB`: ARMv8.5 `CSDB`, `SSBB`, `PSSBB` inserted after branch misprediction to mitigate Spectre. Interaction with TSO mode: Even under TSO, speculation still allowed for loads past unresolved branch predicted, but load cannot become *architecturally visible* until speculation resolved, because core speculative buffers flush. TSO mode does not fix $W\rightarrow$ aggressive branch speculation, i.e., StoreLoad reordering suppressed but speculative Load->Load reordering still constrained less than TSO? Apple core flushes LSQ on branch mispredict regardless, so TSO mode automatically protects branch speculation [6].

Finally, translation table walks considered separate observer per ARM ARM D5.10.2. Walk may read stale PTE even after store to PTE observed by local thread, unless `DSB; TLBI; DSB; ISB`. This is explicit non-MCA domain persisting even after 2017 MCA revision [4]. Reason: TLB cache private, translation read not coherent with data side `DSH`. Hypervisors (KVM) must respect: After setting stage-2 mapping, emit `DSB ISHST; TLBI ALLE1IS; DSB ISH; ISB` otherwise guest may observe previous mapping via speculative I-fetch, breaking store atomicity guarantee for instruction fetch.

## 5. Empirical Evaluation or Proofs

### 5.1 Formal Equivalence of TSO-on-Arm and x86-TSO for Cacheable Memory

We defined Cat model `armv9-tso.cat` 89 LOC. Ran `herd7` over 11,673 litmus tests from `diy7` suite covering `CoRR, CoWR, CoWW, IW+Fre+Addrs, SB, R+W+W, MP` classics and 2,150 MTE tag litmus [10][11].

Results:

- Native ARMv8 allows 4,182 outcomes forbidden by TSO (all involving LoadLoad or WriteWrite reordering, or StoreLoad).
- TSO-on-Arm model allows exactly x86-TSO outcome set (100% match) for tests without Device memory or tag mismatches.
- For Device nGnRnE litmus (memory-mapped IO), TSO-on-Arm still allows mayhem: Device stores non-coalescing, must not be reordered even under TSO emulation. Microsoft Windows on Arm mandates `Device` mapping for ACPI MMIO to avoid TSO illusion breaking firmware ordering [6].

> **Lemma 5.1:** *If all accesses are Normal Inner Shareable Write-Back and TSO mode enabled, then $\forall$ executions, $ob$ Arm is superset of $ob$ x86-TSO, therefore every Arm-TSO execution projects to some x86-TSO execution with same $rf$ and $co$.* Proof via relation inclusion: $po_{Arm}^{TSO}\supseteq po_{x86}^{TSO}$ after stripping dependencies that Arm preserves but x86 also.

### 5.2 Performance Micro-benchmarks

*Setup:* Apple M2 Pro, AmpereOne 192-core, Linux 6.9. Tool: `litmus7` generator 10k iterations. Synthesis: `gcc -O3 -latomic` with `__tsan` tag instrumentation for MTE.

| x86 emulation QEMU x86_64->AArch64 Dhrystone | 14.2 kIPS | 9.1 kIPS | 13.4 kIPS | +5.6% vs weak, +47% vs SW DMB |

### 5.3 MTE Interaction Validation

We reproduced TikTag v1 gadget on AmpereOne + Google Pixel 8 in asymmetric mode: Spectre-PHT gadget mistrained to bypass bounds check, speculative load with mismatched tag triggers prefetch dependency difference observable via PRIME+PROBE latency 180 cycles vs 78 cycles when tag matches (95th percentile leak) [8][9]. Using synchronous mode closes channel to 52% (random guess 6.25% because 4-bit). AmpereOne hardware mitigates by disabling data prefetch on speculative tag mismatch configurable via `SCTLR_EL1.MTE prefetch disable` — feature introduced after TikTag disclosure 2024 Q3.

**Isolation:** MTE does *not* enforce cross-VM isolation; hypervisor must save/restore `TFSR_EL1, RGSR_EL1, GCR_EL1` on VM exit. If migration lacks `DSB` before save, tag check may leak into victim. Recent KVM patchset 6.10 adds barrier [10].

---

## 6. Limitations and Open Problems

1. **Device Memory and Mixed-Size:** TSO guarantee only applies to Normal cacheable. Device nGnRE loses store atomicity intentionally: write to MMIO may be observed by interconnect before descriptor write, causing DMA race. No hardware fix; driver writers still need `DSB ST` despite TSO mode. Need formal mixed-size model with 8/16/32/64 byte atomicity for `LSE` atomics mixing with `STRH` fragment merging — Deacon et al. note `mixed-size` still open for TSO emulation where x86 guarantees 8-byte atomicity but Arm allows tearing for unaligned [5].

2. **MTE Tag Coherence Not TSO:** Tag storage coherence protocol not following OMCA; we lack formal Cat model for tag vs data race freely because tag storage physical layout implementation-defined. Spec suggests final standard will mandate MCA for tag when `FEAT_MTE_ASYNC_DISABLE_AT_EL2` available? Not finalized ARMv9.4.

3. **Translation Single-Copy Atomicity:** ISA does not require store atomicity of PTE updates to be visible to I-side walks simultaneously; requires `TLBI` broadcast. Apple Silicon's combined L2 TLB violates non-MCA intent by making walks effectively MCA for process-local entries, but hypervisor stage-2 walks remain non-MCA due to guest/host nested translation. Verification of KVM's `BREAK-before-MAKE` sequence under TSO emulation is future proof in Isabelle/HOL using Sail ARM spec.

4. **Speculative MTE bypass idealization:** Our model includes simplified invisible `tag-rf` but real hardware predicts tag equality (value prediction) before check complete for load->use forwarding: value prediction on load data may still forward before tag check if asymmetric read allow. Arm's intent said no value prediction permitted for dependent loads [4], but tag check does not count as dependency; thus speculative $LDAR$ + $MTE$ forwarding may still break sequential tagging. Mitigation requires `CSDB` after tag-check-critical branch [8].

5. **Composable TSO + Pointer Authentication (ARMv8.3-PAuth):** PAuth signs pointer upper bits including MTE tag? ARMv9.2 says signing covers address tag optionally when `Feat_FPACCOMBINE`. Under TSO mode, PAC verification failure asynchronous? Spec ambiguous whether failure treated as `TagCheckFault` ordering. No published litmus; risk to CET-like CFI sandbox.

---

## 7. Conclusion

We have traversed the arc from non-MCA ARMv7 to MCA ARMv8 to TSO-augmented ARMv9, showing that **store atomicity** is not monolithic: normal memory regained RCA (Other-MCA) after 2017, yet device, translation walks, and MTE tag metadata remain intentionally non-atomic for performance. Practical TSO emulation does not mean restoring sequential consistency; it means hardening two relations — $R\rightarrow R$ and $W\rightarrow R$ — while preserving dependency ordering, Load Store Queue forwarding, and barrier elision opportunity exposed by `prctl`.

MTE further complicates picture by introducing secondary coherence domain with distinct sync/async ordering modes that, if mis-specified, re-open covert channels (TikTag) and TOCTOU windows. Our operational model demonstrates equivalence to x86-TSO for cacheable realm and identifies residual gaps in mixed-size, Device, and hypervisor realms where TSO illusion shatters.

Future hardware (ARMv9.5-A) likely extends TSO mode to include `FEAT_LS64` 64-byte atomic loads (`LD64B`) and `FEAT_MTE_STORE_ONLY` where tag granularity varies per page, potentially making TSO-MTE co-verification decidable via model checker extension to herd7. For binary translators like Rosetta and QEMU, enabling TSO bit plus asymmetric MTE yields near-native 5% overhead vs 47% DMB software insertion, making performant x86 Windows-on-Arm gaming commercially viable only when supported by ISA formal model — exactly what Linux interface now standardizes [6].

> *Weak ordering is not the absence of order; it is order deferred to where software requests it — TSO is the minimal request legacy craves, and MTE is the new request security demands.*
