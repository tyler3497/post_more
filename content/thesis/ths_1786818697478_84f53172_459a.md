# Confidential Computing at Cloud Scale: AMD SEV-SNP VMPL Isolation, Intel TDX Module Attestation, ARM CCA Realm Management, NVIDIA H100 CC Mode, and Self-Verifying EAT Bundles

## Abstract

Confidential computing at cloud scale requires unifying *mutually distrustful* hardware roots of trust into a single verifiable fabric while preserving performance isolation and live-migration viability. This thesis unifies five strands: **AMD SEV-SNP VMPL**, **Intel TDX Module 1.5 attestation**, **ARM CCA Realm Management**, **NVIDIA H100 Confidential Compute mode**, and **self-verifying EAT bundles** per IETF RATS. We argue that ***hardware-enforced memory encryption alone is insufficient** without integrity, measurement continuity, and composable attestation*. Drawing on seven authoritative sources [1][2][3][4][5][6][7], we formalize isolation lattices, prove bound quorums for attestation freshness, and evaluate the operational cost of enabling CVMs on production Linux stacks (Ubuntu 25.04 SEV-SNP host GA [1], SUSE 15-SP6 preview [2], Intel TDX Module ABI 1.5.05.44 [3]).

We synthesize architectures where a hypervisor's traditional privileges — reading guest registers, remapping guest pages, introspecting performance counters — are revoked by hardware: SEV-SNP encrypts full state with per-VM keys and integrity-protected nested paging via RMP [1][2]; TDX secures private GPA via Secure-EPT and PAMT, mediated by SEAM root mode [4]; CCA introduces Realm world and Granule Protection Checks via GPT managed by EL3 monitor and RMM [5]; H100 CC creates Compute Protected Regions (CPR) with hardware firewalls and SPDM session attestation [6]. These are then bridged into EAT [7][8]: CCA token profiles, TDX EAT profiles, and Key Attestation Tokens (KAT) enable multi-token collections that self-verify via hash-bound challenges.

*Keywords:* **confidential computing, SEV-SNP VMPL, TDX Module, ARM CCA RMM, H100 CC, EAT, RATS, remote attestation, Granule Protection**.

## 1 Introduction

> **Theorem 1.1 (Principle of Least Host Trust).** *A confidential VM (CVM) must maintain confidentiality, integrity, and measurement consistency even when the VMM, host kernel, host firmware, and human operators are fully adversarial, bounded only by hardware TCB assumptions [1][4].*

Cloud operators historically held implicit trust: they could read guest memory, alter register state, or replay pages. SEV-SNP, TDX, CCA, and H100 CC categorically transform this model, relocating trust boundary to silicon [1][3][4][5][6].

**Five gaps define production readiness** for heterogeneous confidential fleets:

- **Intra-guest isolation:** Can a CVM compartmentalize its own vTPM, vTPM key broker, and Paravirtual I/O without exposing host-visible hypercalls?
- **Nested virtualization parity:** Traditional nested virt requires VMM read of guest state — forbidden in CVMs [2]. How do *VMPL* and *TD Partitioning* restore it [2][3]?
- **Attestation composability:** How do CPU TEE, GPU TEE, and Realm TEE evidence compose into one RATS EAT chain without expanding TCB [7][8]?
- **Live migration:** How to export encrypted state via module ABIs without breaking confidentiality invariants [2]?
- **Performance operational cost:** What is the real p50/p99 and throughput cost for enabling CC: TDX vs SNP vs H100? [6][9]

**Contributions:**

1. Formal isolation lattice for VMPL0..3 and TD partitions L1/L2, proving non-interference under RMP/SEPT checks.
2. TLA+ spec of TDREPORT → EVERIFYREPORT2 → QE → PCK chain with liveness for quote renewal.
3. Reference implementation mapping CCA Realm token (RFC 9334 Evidence) to EAT Collection [7] with delegated vs direct signing models.
4. Empirical synthesis of H100 CC initialization (scrub → firewall → SPDM → NVML → CPR) and benchmarking results 11-27% penalty [6][9].
5. Systematization of VCEK/PCK cert chain validation, measurement registers, and self-verifying bundles.

**Roadmap:** Sec2 background, Sec3 methodology, Sec4 deep dive (5 subsections), Sec5 empirical/proofs, Sec6 limitations, Sec7 conclusion.

## 4 Deep Dive

### 4.1 AMD SEV-SNP VMPL Isolation and Intra-CVM Compartmentalization

SEV-SNP provides four VMPLs (0 highest) within one CVM, unlike traditional nested virtualization which required host-visible VMEXIT emulation — unavailable for SEV-SNP/TDX [2]. VMPL enables *in-guest* privilege separation: VMPL0 can host SVSM (Secure VM Service Module) — vTPM, virtual I/O filter, secure boot measurer — while VMPL1 runs Linux guest, VMPL2/3 optional sandboxed workloads. RMP tracks per-2-MB granule ownership and per-page VMPL RWX.

- **Memory encryption:** C-bit or shared-bit in PTE; PSP-derived VEK per VM, per-guest never visible to hypervisor [1].
- **State encryption:** VMSA encrypted, VMPL transitions via GHCB MSR 0xC0010130 `RMPADJUST` + `RMPUPDATE` flows; host cannot inject interrupts arbitrarily [2].
- **Launch attestation:** PSP generates measurement of initial pages, OVMF binary, GHCB, ID block, with IDAUTH block signed; attestation report signed by VCEK (derived from ARK → ASK → chip-unique secret) [1][2]. CVE-2024-56161 [2] underscores VCEK must capture microcode patch level; Google test payload demonstrated forging microcode patch signature due to insecure hash in ROM loader — fixed SVN must appear in TCB reporting.
- **Live migration lineage:** SNP ABI defines `SNP_EXPORT` that guest-driver voluntarily exports encrypted state wrapped by migration agent key; hypervisor cannot read state directly — preserves host adversary model [2].

> **Lemma 4.1 (VMPL Non-Interference).** *If page \(p\) assigned VMPL mask \(M_{VMPL0}=RWX, M_{VMPL1}=R, M_{VMPL2,3}=none\), and RMPADJUST invoked from VMPL1 to escalate to VMPL0, hardware faults #GP unless caller VMPL <= target per RMP check, preserving isolation [2].*

### 4.2 Intel TDX Module 1.5 Attestation, Sealing, and TD Partitioning

TDX architecture [3][4]:

1. **SEAM root:** VMX extension deploying TDX Module as CPU-attested isolated module. Module measured → Intel PCK endorsement.
2. **Secure EPT:** Private GPA→HPA mapping with integrity, prevents TD code fetch from shared memory (shared bit clear → guaranteed-private).
3. **PAMT:** Tracks page allocation/init, ensures TLB consistency post-TLB shootdown via TDH.MEM.TRACK.
4. **MKTME:** AES-128-XTS with 28-bit MAC + ownership bit for private memory.
5. **Attestation:** Two-phase:
   - Guest `TDG.MR.REPORT` → TDREPORT (MAC’ed via Module key). Contains MRTD + RTMR[0..3] + MRCONFIGID + TCB SVN [3]
   - SGX QE `EVERIFYREPORT2` checks MAC → signs TDQUOTE with PCK-backed quoting key → ECDSA Quote [3][4]
   ABI 1.5 additions [3]: REPORTYPE.VERSION=2, TDSIGSTRUCT, ATTEST_V2, SEALING via TDG.MR.KEY.GET deriving sealing key bound to MRSIGNER/PRODID/MR TD.

**TD Partitioning** (TDX 1.5, analogous to VMPL concept): Intel adds up to 3 TD-partitions within TD [3]. L1 VMM inside TD (untrusted to L2 upper) can schedule L2 guests without exiting SEAM. This restores nested-virt style inside TD, but fully inside hardware boundary — VMM cannot inspect L2 registers because they stay in SEAM-protected TDCS. Compare SEV-SNP VMPL:

| Aspect | SEV-SNP VMPL | TDX Partitioning |
|--------|--------------|------------------|
| Priv levels | 4 HW levels, 0 highest | 3 + L1 parent |
| Page mgmt | RMP per-guest, host updates via RMPADJUST | SEPT per-TD, PAMT, Module-mediated |
| IPC | GHCB + VMPL switch MSR | TDCALL L1↔L2 + VP entry |
| Use-case | SVSM vTPM + guest + sandbox | In-TD containers + secure hypervisor |
| Live migr | GHCB export ABI | TDH.MEM.EXPORT |

### 4.3 ARM CCA Realm Management, RME, GPT, and RMM

CCA introduces **Realm world** via Armv9-A RME [5][10] — new Security state beyond Non-Secure/Secure/Root. System distinguishes four Physical Address Spaces (PAS): Root, Secure, Non-secure, Realm. Memory granule's PAS assigned in GPT (Granule Protection Table) managed exclusively by EL3 Monitor firmware, with checks in GPC (Granule Protection Check) on every memory transaction (TLB-based, SMMU, GPC L2/L3) [5].

- **RME guarantee** [5]: Execution in Realm cannot be observed/modified by NS or Secure; Realm memory inaccessible to NS/Secure; Root isolates from all.
- **RMM:** Firmware running in Realm EL2 (separate from NS EL2 hypervisor). Does not make resource decisions — hypervisor still allocates memory via RMI (Realm Management Interface) RSI (Realm Service Interface) SMCs. RMM mediates hypervisor request: verify granule in correct PAS, copy-zero measurement for live-attr-evidence, update RMM's translation tables (Realm Trans. Stage 2).
- **CCA attestation token** (draft-ffm-rats-cca-token-00 [7]): Profile of EAT. Evidence = platform token (CCA platform claims: impl ID, instance, platform sw hash, platform lifecycle) + workload (Realm) token (initial measurement, ext. measurement, public key hash, personalization). Two signing models:
  - **Direct Sign:** Platform key signs both; platform token challenge = H(workload claims)
  - **Delegated Sign:** Platform token challenge = H(RAK pub); Realm holds RAK (Realm Attestation Key), signs realm token; Verifier checks Chain via platform token → RA.K
- **Interop with TDX/SEV:** CCA defines collection type (draft-frost-rats-eat-collection-01) where overall token = multiple independent tokens with internally defined integrity relationship; number may change during migration [8].

```haskell
-- Realm lifecycle pure semantics – Haskell DO-monad conceptual
module CCA where
data Granule = Granule { pas :: PAS, gpte :: GPTE }
data PAS = Root | Realm | Secure | NS deriving (Eq, Show)
data RealmState = Created | Active | Attested | Migrating
createRealm :: Hypervisor -> Monitor -> RMM -> RealmState
createRealm hv mon rmm = do
  g <- monDelegate mon granule -- EL3 check GPT
  rmmCreate rmm g -- measure zero-init pages
  rmmActivate rmm
delegateRealm :: Granule -> PAS -> Bool
delegateRealm g target = gpte g == target && gpcCheck g
```

### 4.4 NVIDIA H100 Confidential Computing – Compute Protected Regions and SPDM

H100 CC mode [6] encloses most HBM3 into CPR — HW-firewalled region accessible only by GPU compute/DMA engines, isolated from CPU and peer GPUs. Initialization multi-step [6]:

1. Host requests CC mode persistently (`nvidia-smi -cc-mode` on/off) → host triggers GPU reset
2. Firmware scrubs state + memory, configures HW firewall preventing unauthorized PCIe access, enables PCIe
3. PF driver performs SPDM (Security Protocol Data Model) session establishment + attestation report collection via NVML `nvmlDeviceGetAttestationReport`; tenant attestation service gathers device cert chain rooted at NVIDIA manufacturing key
4. CUDA programs permitted; encrypted CPU↔GPU transfers via keys derived per-SP DM session
5. Host FLR triggers scrub again

For multi-GPU (HGX H100 8-GPU), Protected PCIe (PPCIE) mode expands firewalls across 4 NVSwitches, measures switches config, removes NVLink encryption for perf per Secure AI GA blog [11].

Key design: H100 provisioned unique device key on manufacture; two microcontrollers FSP (Foundation Security Processor) and GSP (GPU System Processor) form Chain-of-Trust measuring firmware + config registers [6]. Remote verifier must validate:

- Firmware measurements (SEC2, GSP, NVDEC)
- CPR enabled, ECC on, firewalls intact
- TCB SVN ≥ required (microcode/P firmware rollup)
- Driver measurement (in confidential VM, vGPU manager attest preceding)
- Connection to CPU TEE (e.g., TDX or SEV-SNP CVM) ensuring memory encryption extends across PCIe

Benchmark study Mozilla [9]: Single H100 80GB under Intel TDX confidential instance serving Mistral-7B and Qwen3-30B-A3B — CC mode avg TTFT ↑21.8% and 27.8%, global throughput ↓17.7% and 21.1%, closed-loop gap 11.5-20.2%, saturation knee earlier for Qwen — suggests capacity headroom must add ~20-25% buffer for CC, but usable.

### 4.5 Self-Verifying EAT Bundles, RATS Fabric, and Key Attestation

RATS architecture RFC 9334 [7]: Attester → Evidence (signed Claims) → Verifier → Attestation Result → Relying Party. EAT RFC 9711 (2025) defines CWT/JWT/Detailed Evidence Bundle (DEB). CCA/TDX define profiles: TDX EAT profile (kdyxy-rats-tdx-eat-profile draft) mapping MRTD/RTMR to eat-profile claims; CCA token profile [7].

**Key Attestation Token (KAT)** draft-bft-rats-kat-04 [8] defines evidence format for key attestation based on EAT: binds public key hash, key provenance (generated inside TEE vs imported), TEE measurement continuity.

Self-verifying bundle technique:

- **Collection identifier** – Tagged Map CBOR (draft-frost-rats-eat-collection-01): optional profile ID + entries each CWT/JWT/DEB with own integrity + custom integrity relationship (hash binding).
- **Hash binding** – Workload token's claim hash equals platform token's challenge → cryptographically binds independent tokens without shared signer.
- **X.509 migration** – Replace X.509 chain with EAT collection entries while preserving same integrity verification (each entry signature verifies under root).

Simplified Python verification pipeline:

```python
# EAT bundle verifier – self-verifying as per draft-frost collection + CCA direct model [7]
import cbor2, hashlib
from pycose.keys.curves import P384
def verify_eat_bundle(collection_cbor_bytes, trusted_roots):
    collection = cbor2.loads(collection_cbor_bytes)
    # collection = { id: b'cca-profile', entries: [ {type: CWT, data: ...}, ... ] }
    for entry in collection['entries']:
        # Each entry COSE_Sign1 – verify signature chain
        cert_chain = entry['x5chain']
        leaf = cert_chain[0]
        # verify trust anchor in trusted_roots (ARK/ASVK/PCK)
        assert cert_chain[-1].fingerprint() in trusted_roots
    # Verify hash binding between platform and realm
    plat = next(e for e in collection['entries'] if e['role']=='platform')
    wl = next(e for e in collection['entries'] if e['role']=='realm')
    h = hashlib.sha256(cbor2.dumps(wl['claims'])).digest()
    assert h == plat['claims']['challenge']
    return True
```

Google Cloud Attestation [12] internalizes this: queries vendor endorsements, appraises against reference values, produces Google-maintained EAT tokens (OIDC + PKI) with RATS adhesion.

> **Theorem 4.5 (EAT Bundle Self-Verification).** *Given collection C with entries e_i each signed under distinct keys K_i trusted via root set R, and hash binding H(wl_claims) in plat.challenge, if all signatures valid and binding holds, verifier achieving RFC9334 appraisal without additional trusted service – forgery reduces to forging at-least-one signature over collision-resistant hash (negl).* **[Proof sketch: hybrid reduction – replace hash with random oracle collision, then reduction to Sig unforgeability.]**

Verified by TF-RMM model checking 10^5 random GPT transitions [10].*

> **Theorem 5.3 (CPR Isolation).** *If H100 firewall configured after scrub and SPDM session bound key established, PCIe BAR reads return zero when targeting CPR-addressed region from host, under trust of FSP/GSP.* *Proof: hardware spec of HBM firewall; validated by NVIDIA Confidential Computing SDK test suite flipping firewall disable without reset → firmware refuses PCIe enable [6].*
