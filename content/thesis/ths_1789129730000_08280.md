# Durable Execution for Serverless Workflows: Event-Sourced Replay, Deterministic Reconstruction, and Saga Compensation in Temporal and the Durable Task Framework

## Abstract

Serverless computing couples *ephemeral execution* with *at-most-once billing granularity*, a combination that makes long-running, multi-step processes fragile by construction. Durable execution inverts the relationship between state and compute: rather than persisting snapshots, systems such as **Temporal** and the **Azure Durable Task Framework** persist an append-only *event history* and reconstruct all state by deterministically replaying it on resume [3][4][5]. This paper formalizes the model—workflows as pure functions over histories, side effects mediated through commands, recovery as re-execution from a log prefix—and compares its two dominant industrial realizations. We analyze the *determinism contract* (workflow code must be pure; only activities may touch the world), the *episode model* of Azure's orchestrator [4], and Temporal's command/event duality [3]. We give a formal treatment of **saga compensation** as the correct atomicity primitive for cross-service workflows [6][7], prove that exactly-once *effects* are unattainable and that idempotent activities plus dedup-ledgered intents are the sound substitute [1], and evaluate the central performance pathology: *replay cost* grows with history length, requiring truncation strategies such as Continue-As-New and sub-orchestrations.

## 1 Introduction

A cloud function is a pure handler of a single event: it starts cold, computes, and dies. Composing *N* such handlers into a reliable process—a checkout that reserves inventory, charges a card, and ships a parcel—exposes what we call the **serverless durability gap**. The function's process memory is the only place where "progress" exists, and process memory is precisely what the platform is allowed to destroy. Traditional remedies—checkpoints between steps, queues with dead-lettering, hand-rolled state machines—push the bookkeeping onto developers, who end up writing code that is simultaneously a business process and a bespoke distributed-systems runtime. These runtimes fail predictably: duplicated effects under retry, inconsistent state after partial crash, retry storms that convert transient faults into outages.

*Durable execution* is the thesis that **the runtime, not the application, should own progress**. The developer writes the workflow as ordinary procedural code—loops, conditionals, variables, `await sleep(30 days)`—and the platform guarantees that this code executes *to completion* despite the death of every process that ever ran it. Two systems dominate practice:

- **Temporal**, whose server persists an event-sourced history per workflow execution and whose workers reconstruct state by deterministic replay [3];
- the **Durable Task Framework (DTFx)** behind **Azure Durable Functions**, which checkpoints orchestrator progress as rows in an append-only history table and rebuilds orchestrator state by replaying it on wake-up [4][5].

Both rest on the same foundation: *event sourcing*. State is a fold over an immutable log; recovery is recomputation from a log prefix. This paper is a deep study of that foundation—its semantics, its guarantees, its failure modes, and its costs.

> **Thesis.** Durable execution does not make failures impossible; it makes *progress* a monotonic function of the persisted event log, decoupling the fate of the workflow from the fate of any compute host. The price is a determinism contract on workflow code and a replay cost linear in history length.

## 2 Background

### 2.1 Serverless ephemerality

Function-as-a-Service platforms expose *stateless* compute with hard execution ceilings and at-most-once invocation semantics. Orchestrating multiple functions therefore requires an external source of truth for "where the process got to." Zhang et al. observe that serverless routing is stateless—a follow-up message may be routed to a *different instance* than the one that processed the prior message—which rules out naive state-machine replication for stateful serverless functions [1]. The shared response across Beldi, Temporal, and DTFx: **state must live where hosts cannot take it with them**.

### 2.2 Event sourcing

Event sourcing stores *the full sequence of actions that led to a state* rather than the state itself [8]. Each transition appends immutable events to a log; current state is the left fold of that log. The pattern buys exactly what the durability gap demands: (i) **durability**—crash a host and the log survives; (ii) **scalability**—append-only writes avoid read-modify-write contention; (iii) **observability**—the audit trail is never lost, which is what makes compensating actions reliable (§4.3) [4].

### 2.3 Workflows as code

Temporal and DTFx share a second design decision: workflows are written in general-purpose languages, not YAML. A declarative DSL must enumerate the control-flow constructs it supports; a general-purpose language inherits loops, exceptions, and composition for free, and the *determinism contract* (§3.2) can be stated as a property of ordinary code. The cost is that the runtime must sandbox workflow code against host nondeterminism (clocks, randomness, thread scheduling, I/O).

## 3 Methodology

### 3.1 A formal model of history-based execution

We model a workflow execution as a deterministic transition system over an *event history* \(H = \langle e_1, e_2, \ldots, e_n \rangle\), an append-only sequence persisted in a strongly consistent store. The workflow program \(W\) is a pure function:

\[
(W, H) \;\mapsto\; (C, \delta)
\]

where \(C\) is a finite set of *commands* (schedule activity, start timer, complete workflow, …) and \(\delta\) is a decision: *block* or *continue*. When new events arrive, a new episode replays the *entire* history \(H'\) and issues the commands the workflow's control flow now demands. Commands already present in \(H'\) are recognized and *not* re-issued; only genuinely new commands take effect. This is the replay discipline.

In Haskell, the essence is a fold with a memo table:

```haskell
-- H: event history. Cmd: command the workflow wants to issue.
-- Deciding whether a command is *new* is the replay discipline.
data Event   = ActivityScheduled Int Payload | ActivityCompleted Int Result
             | TimerFired Int | WorkflowCompleted Result
             deriving (Eq, Show)

replay :: [Event]              -- ^ persisted history (immutable prefix)
       -> [Cmd]                -- ^ commands the code wants to issue now
       -> ([Cmd], [Event])     -- ^ (new commands, events to append)
replay hist wanted =
  let seen = [ i | ActivityScheduled i _ <- hist ]       -- already scheduled
      fresh = filter (\(Schedule i _) -> i `notElem` seen) wanted
      append = [ ActivityScheduled i p | Schedule i p <- fresh ]
  in (fresh, append)
```

### 3.2 The determinism contract

For replay to be sound, \(W\) must be a pure function of \((input, H)\). Concretely, workflow code must not:

1. read the system clock (use a workflow clock, which replays recorded timestamps);
2. generate randomness directly (use a seeded RNG or record the value via side-effect APIs);
3. perform I/O or spawn threads (side effects live in *activities*);
4. iterate over unordered collections or depend on scheduling order.

Temporal states the rule bluntly: workflow code must be deterministic and side-effect free; activities must be idempotent or non-retryable [3]. DTFx enforces the same contract on orchestrator functions, which are replayed from the history table on every wake-up [4]. Violations manifest as *non-deterministic errors*: during replay the code issues commands that do not match the recorded history, and the runtime cannot reconcile them. This fail-stop semantics is the correct one—silently accepting a divergent replay would fork the workflow's reality.

### 3.3 The command/event duality

Every interaction between the workflow and the world passes through the history as a *command/event pair*: the workflow issues a command (e.g., "schedule activity *charge_card*"), the history records a `Scheduled` event, and later the world answers with a `Completed` (or `Failed`, or `TimedOut`) event carrying the result. Timers, child workflows, signals, and queries all reduce to this duality [3]. It is what makes "sleep for 30 days" durable: the workflow issues a timer command, the runtime persists it and unloads the workflow entirely, and thirty days later a `TimerFired` event starts a new episode.

## 4 Deep Dive

### 4.1 Temporal: event history as the source of truth

Temporal's architecture separates *orchestration state* (the History service, backed by a strongly consistent database) from *execution* (stateless workers polling task queues) [3]. A workflow execution's history is an ordered sequence of events with monotonically increasing IDs; the server appends events transactionally with task dispatch, so a worker never observes a command without its recorded event. On wake-up, the worker replays the workflow code from the beginning, short-circuiting at recorded results: when the code calls an activity whose completion event already exists, the SDK returns the recorded result *without executing anything*.

Failure handling is layered on the same history. Activities carry retry policies (default: exponential backoff, unlimited attempts); each attempt is a separate history event. Heartbeats let long activities report progress as history events, enabling resume-from-heartbeat. Workflow-level failures surface as workflow task failures—recovery is replay with fixed code over old history, with versioning markers keeping old histories interpretable [3].

```python
# Temporal Python SDK: the determinism contract in miniature.
# workflow.* calls are replay-safe; anything else belongs in an activity.
from temporalio import workflow, activity

@workflow.defn
class OrderWorkflow:
    @workflow.run
    async def run(self, order_id: str) -> str:
        # Deterministic: recorded once, replayed forever.
        reserved = await workflow.execute_activity(
            reserve_inventory, order_id,
            start_to_close_timeout=timedelta(seconds=30),
            retry_policy=RetryPolicy(maximum_attempts=5),
        )
        # workflow.now() is replay-safe; datetime.now() is FORBIDDEN here.
        deadline = workflow.now() + timedelta(days=2)
        charged = await workflow.execute_activity(charge_card, (order_id, reserved))
        return f"charged={charged} by={deadline.isoformat()}"

@activity.defn
async def charge_card(payload) -> str:
    # Activities MAY be nondeterministic — but MUST be idempotent,
    # because the runtime may execute them more than once [3].
    return await gateway.charge(idempotency_key=payload[0], amount=payload[1])
```

### 4.2 The Durable Task Framework: episodes over table storage

DTFx implements the same mathematics on different infrastructure. An orchestration is processed as a sequence of *work items*; each completed work item commits to the task hub, appending history events and queueing the messages that drive the next work item [5]. The orchestrator runs only for the slice needed to advance to the next `await`: it schedules activities, yields control, and is *unloaded from memory*. On wake-up the dispatcher reloads the full history and replays the orchestrator from the top, fast-forwarding past completed awaits with recorded results [4].

The DTFx history table makes the event-sourcing structure unusually legible: rows carry `EventType` values such as `ExecutionStarted`, `TaskScheduled`, `TaskCompleted`, `TimerCreated`, `TimerFired`, and `ExecutionCompleted`, each with sequence numbers that totally order the orchestration's causal past [4][8]. This legibility is operationally valuable—debugging a stuck orchestration is reading its history table—but it exposes the model's central cost driver: **every wake-up replays every row**. A fan-out of 10,000 activities writes 20,000+ rows, and each subsequent episode re-reads them. The mitigation portfolio (sub-orchestrations to partition history, `ContinueAsNew` to truncate it, entities for fine-grained state) is, at bottom, history-sharding [5].

### 4.3 Saga compensation: atomicity without transactions

Neither Temporal nor DTFx can offer ACID transactions across services—at internet scale, two-phase commit is unavailable in practice, so systems must be built from *idempotent, retryable, compensable* steps [7]. The saga pattern (Garcia-Molina & Salem, 1987) is the formal answer: decompose a long-lived transaction into local transactions \(T_1, \ldots, T_n\), each paired with a compensating transaction \(C_i\) that semantically undoes \(T_i\); either all \(T_i\) complete or the compensations \(C_{k}, \ldots, C_1\) run in reverse over the completed prefix [6].

Durable execution is the natural substrate for orchestration-based sagas, because the history *is* the saga log. The orchestrator accumulates compensations as ordinary workflow state (durable by replay), and on failure executes them in reverse:

```rust
// Saga as ordinary control flow. The compensation stack is workflow
// state, hence durable under replay; reverse execution is just a loop.
struct SagaStep { forward: Activity, compensate: Activity, payload: Payload }

async fn run_saga(ctx: &WfCtx, steps: Vec<SagaStep>) -> Result<Outcome, SagaError> {
    let mut compensations: Vec<(Activity, Payload)> = Vec::new();
    for step in steps {
        // Idempotency keys make re-execution safe under at-least-once activities.
        let out = ctx.call_activity(&step.forward, &step.payload).await?;
        compensations.push((step.compensate, out.compensation_payload()));
        if out.failed() {
            for (comp, payload) in compensations.into_iter().rev() {
                // Compensation failures are retried, never skipped:
                // a half-compensated saga is worse than a slow one.
                ctx.call_activity_with_retry(&comp, &payload, RetryPolicy::unlimited()).await?;
            }
            return Err(SagaError::Compensated);
        }
    }
    Ok(Outcome::Committed)
}
```

> **Theorem 1 (Saga safety under replay).** *Let \(S = \langle T_1, C_1\rangle, \ldots, \langle T_n, C_n\rangle\) be a saga where each \(T_i\) is idempotent and each \(C_i\) is idempotent and retryable to completion. If the orchestrator crashes at any point and resumes by deterministic replay of its event history, the final observable state is either (a) all \(T_i\) applied, or (b) all \(T_i\) applied for \(i \le k\) followed by \(C_k, \ldots, C_1\) applied, for the maximal completed prefix \(k\). No other outcome is reachable.*

*Proof sketch.* Replay determinism re-derives the identical compensation stack from the history prefix: each completed \(T_i\) appends its \((C_i, \text{payload})\) pair before the next forward step, so the crash-point stack is exactly the re-derived stack. Forward steps are guarded by recorded completion events; compensations are retried to completion because \(C_i\) idempotence makes repeats harmless. ∎

Two subtleties. First, *semantic* compensation is not rollback: refunding a payment is not un-charging it, and the saga guarantees *business-meaningful* consistency—the history records both forward and compensating events, which is what auditors want [6]. Second, compensators themselves must be durable activities with their own retry policies; a saga whose compensations can be lost is not a saga but a hope.

### 4.4 Exactly-once effects: the impossibility and the workarounds

What is guaranteed exactly once is *workflow state progression*—the history advances monotonically and each command takes effect at most once *in the history* [3]. **Effects on the external world are at-least-once.** An activity may execute, crash after its side effect but before reporting completion, and be retried: the world observes the effect twice while the history records one completion. No framework can do better—this is the Two Generals problem wearing a workflow costume [7].

The sound engineering response has three layers:

| Layer | Mechanism | Guarantee obtained |
|---|---|---|
| Workflow code | Deterministic replay over event history | Each command *decided* exactly once |
| Activity dispatch | Recorded results short-circuit re-execution | Each command *issued to the world* at most once per recorded completion |
| Activity implementation | Idempotency keys + dedup ledgers | Duplicate executions are *observably* idempotent |

This is the honest formulation every durable-execution paper should carry: **exactly-once execution is impossible; exactly-once *effects* are achievable only when the effect's recipient cooperates via idempotence**.

### 4.5 Performance: replay cost and history growth

The model's elegance has a meter running. Let \(|H|\) be the history length in events and \(c\) the per-event replay cost. Each episode costs \(\Theta(|H| \cdot c)\), and a workflow with \(E\) episodes pays \(\Theta(E \cdot |H| \cdot c)\) in aggregate replay work—*quadratic* in the number of steps when every step wakes the orchestrator. For a 10,000-activity fan-out, the final episodes replay tens of thousands of events to make one scheduling decision; practitioners report this as the "stuck orchestration" pathology, where execution slices are consumed by replay rather than progress [5].

The mitigations form a coherent portfolio:

1. **Continue-As-New**: atomically replace the execution with a fresh one carrying a summary payload, truncating history to \(O(1)\). Temporal supports histories up to ~51,200 events / 50 MB; long-running "entity workflows" must restart periodically [3].
2. **Sub-orchestrations**: partition one large history into a tree of smaller ones; each replays only its own prefix [4].
3. **Durable entities** (DTFx): replace replay-heavy read-modify-write loops with addressed, message-driven stateful grains [5].
4. **History caching**: workers cache deserialized histories across episodes, amortizing \(c\) when episodes land on the same host [3].

## 5 Empirical Evaluation and Proofs

### 5.1 A cost model for replay

Consider a sequential orchestration of \(n\) activities, each waking the orchestrator once. Episode \(k\) replays \(2k\) events. Total replay work:

\[
W(n) = \sum_{k=1}^{n} 2k \cdot c = \Theta(n^2)
\]

With Continue-As-New every \(m\) steps, history never exceeds \(2m\) events and total work becomes \(\Theta(n \cdot m)\)—linear in \(n\).

> **Theorem 2 (Replay lower bound).** *Any history-based durable execution scheme in which episode \(k\) must distinguish the first \(k\) commands cannot process \(n\) sequential steps in \(o(n^2)\) replay work without a truncation operation.*

*Proof sketch.* Distinguishing \(k\) commands requires inspecting \(\Omega(k)\) history entries (adversary argument). Summation over \(k = 1..n\) gives \(\Omega(n^2)\). Truncation resets the adversary's budget. ∎

### 5.2 Comparative semantics

| Property | Temporal | Durable Task Framework | Beldi (library) |
|---|---|---|---|
| History substrate | Ordered event history in History service DB [3] | History table rows in task hub storage [4] | Intent + data logs in provider tables [1] |
| Replay trigger | Workflow task on new events | Orchestrator work item on new messages [5] | Function re-invocation on intent |
| Determinism rule | Workflow code pure; activities idempotent [3] | Orchestrator code deterministic [4] | SSFs written against Beldi API |
| Truncation | Continue-AsNew (~51k events) | ContinueAsNew, sub-orchestrations | Log garbage collection [2] |
| Exactly-once | State progression; effects at-least-once | Same | Observably exactly-once via intents [1] |
| Saga support | Workflow-level compensation stacks | Orchestrator-level compensation [8] | Transactional SSFs |

### 5.3 Failure-injection analysis

We model crash recovery as *adversarial episode scheduling*: the adversary may kill any host between any two persisted events. Under the determinism contract, the reachable states are exactly the history prefixes—a *safety* property by induction on episodes. Liveness needs fairness: a durable event store, a worker that eventually processes each task, and retry policies that do not give up before the world heals. Notably, *neither* Temporal nor DTFx guarantees liveness under permanent downstream failure—an activity with unlimited retries against a permanently dead dependency is a correct, durable, infinite loop. Durability is not a substitute for supervision.

## 6 Limitations

**The determinism contract leaks.** Real codebases fight it: a developer calls `uuid4()` inside a workflow or iterates a hash map, and the failure surfaces only under replay—often in production. Static enforcement helps but cannot cover every host-language nondeterminism source.

**History is a liability at scale.** The \(\Theta(n^2)\) replay pathology (§5.1) means naive "one orchestration per entity living forever" designs degrade superlinearly. Continue-As-New and sub-orchestration partitioning are effective but manual; automatic history compaction that preserves the audit trail's legal value remains an open problem.

**Exactly-once remains the developer's burden.** The frameworks guarantee exactly-once *decisions*; exactly-once *effects* require idempotent activities, and idempotence is a property of the downstream system. Payment gateways provide idempotency keys; most internal CRUD APIs do not, and retrofitting them is organizational, not technical, work.

**Versioning is unsolved in the general case.** Changing workflow code while old histories exist requires new code to interpret old event sequences. Patching/versioning APIs handle the common cases, but arbitrary code evolution over years-long histories has no complete solution—this is the *schema evolution problem* transposed onto executable code.

**Observability ≠ debuggability.** The history records everything, yet reconstructing *why* a workflow decided requires replaying code with recorded inputs—no current tooling makes this pleasant. Time-travel debugging over event histories is the next frontier.

## 7 Conclusion

Durable execution reframes reliability as a property of *logs* rather than *hosts*. By reducing workflow state to a pure function of an append-only event history, Temporal and the Durable Task Framework convert the hardest distributed-systems problems—crash recovery, exactly-once coordination, long-lived transactions—into consequences of deterministic replay. The saga pattern finds its natural home here: the history is the saga log, the compensation stack is replay-durable state, and Theorem 1 shows the combination is safe under arbitrary crash schedules.

The honest accounting is equally important. Replay costs \(\Theta(n^2)\) without truncation; exactly-once *effects* need downstream idempotence; and the determinism contract taxes every developer who touches workflow code. Beldi's intent-logged exactly-once effects [1] and the move toward managed history backends such as the Durable Task Scheduler [5] point at the trajectory: push more of the contract into the runtime, keep the history, and make the common path—write straightforward code, get durability for free—actually free.
