# Crash-Consistent Hardware Transactional Memory for Persistent Memory: Intel TSX Deprecation, ARM TME Successors, and Conflict-Aware Fallback Design

## Abstract

Hardware Transactional Memory (HTM) promised *atomicity by default* for concurrent programs, and Intel's Transactional Synchronization Extensions (TSX) embodied that promise from 2013 until their forced deprecation via microcode in 2021. Simultaneously, persistent memory (PM) subsystems built on Intel's PMDK exposed crash-consistent transactions whose durability ordering rests on explicit cache-line flushes and fences. This thesis unifies the two domains: it analyzes the architectural causes of the TSX collapse, extracts a portable design model from ARM's Transactional Memory Extension (TME), derives principled conflict-detection and fallback-path engineering, and constructs crash-consistent HTM atop PMDK-style logging. We formalize the *persistence-aware transaction* as a tuple of an optimistic HTM phase and an explicit durability phase, prove that best-effort HTM composed with undo/redo logging yields durable linearizability, and report emulation results showing 2.1–3.4× throughput gains over lock-based PMDK transactions under low contention. The result is a blueprint for the post-TSX era of transactional systems.

## 1. Introduction

The history of Hardware Transactional Memory is a study in how a beautiful abstraction can be undone by its interaction with the rest of the machine. Intel TSX, introduced with Haswell in 2013, offered **Restricted Transactional Memory (RTM)** and **Hardware Lock Elision (HLE)** as first-class architectural features, with early measurements reporting database transaction-throughput improvements of up to 4× [2]. Yet the very mechanism that made TSX fast — speculative execution tracked in the L1 cache — made it a vehicle for microarchitectural side channels. The TSX Asynchronous Abort (TAA) vulnerability of 2019 [4] proved decisive: Intel Platform Update 2021.1 shipped microcode that disables TSX by default and forces every RTM transaction to abort, advertising the new `RTM_ALWAYS_ABORT` CPUID bit so software can detect the carcass of the feature [1].

Meanwhile, the persistent-memory community developed its own transactional substrate. Intel's Persistent Memory Development Kit (PMDK) provides `libpmemobj`, whose `TX_BEGIN`/`TX_END` macro family implements crash-consistent transactions via **undo logging**, `CLWB`/`SFENCE` ordering, and a `jmp_buf`-based abort mechanism [5]. DUDETM (ASPLOS 2017) showed how durable transactions can be *decoupled* from the concurrency-control layer, allowing an off-the-shelf TM to supply atomicity while a separate component supplies durability [6]. This thesis argues the post-TSX world still needs HTM — re-conceived as a *best-effort accelerator* for persistent-memory transactions, with rigorous fallback design and explicit durability phases.

Our contributions are fourfold:

1. A root-cause taxonomy of the TSX deprecation, from the 2014 Haswell erratum to TAA, and its implications for ISA-level speculation (Section 4.1).
2. A portable **best-effort HTM** model distilled from ARM's TME (TSTART/TCOMMIT/TCANCEL), including the consequences of strong isolation and flattened nesting (Section 4.2) [3].
3. A conflict-detection and fallback-path design discipline with quantitative retry budgets and abort-cause taxonomy (Section 4.3).
4. A construction for **crash-consistent HTM** over PMDK-style logging, with a proof of durable linearizability and emulated evaluation (Sections 4.4, 5) [5][6][7].

## 2. Background

### 2.1 Hardware transactional memory

HTM exposes *atomic blocks* to software and executes them speculatively, rolling back on conflict. Intel TSX provided two interfaces [2]:

| Interface | Mechanism | Instructions | Commit semantics |
|---|---|---|---|
| HLE | `XACQUIRE`/`XRELEASE` prefixes | existing `LOCK`-prefixed ops | implicit at `XRELEASE` |
| RTM | explicit region | `XBEGIN`/`XEND`/`XABORT` | explicit at `XEND` |

Both track a **read-set** and **write-set** in the L1 data cache; any conflicting coherence event (or capacity overflow, interrupt, page fault, or explicit `XABORT`) aborts the region, restoring register and memory state. ARM's TME offers a parallel but cleaner design: `TSTART`, `TCOMMIT`, `TCANCEL`, strong isolation from non-transactional accesses, and flattened nesting where an inner abort kills the outer transaction [3].

### 2.2 The persistent-memory ordering model

Byte-addressable non-volatile memory sits behind a *volatile* cache hierarchy, so stores are not durable when they retire. Durability requires explicit ordering: cache-line flushes (`clflush`, `clflushopt`, `clwb`) followed by persistent barriers (`sfence`) [7]. PMDK's `libpmemobj` hides this machinery behind undo logging: every store inside `TX_BEGIN` first snapshots the old value into a persistent undo log (flushed and fenced), then performs the store; commit discards the log, recovery replays it [5]. The `TX_STAGE_*` stages form a strict state machine enforced by `pmemobj_tx_process()` [5].

### 2.3 Durable linearizability

A concurrent persistent data structure is *durably linearizable* if every operation that returns before a crash is linearized and its effects survive the crash [6]. DUDETM's central insight is that **atomicity** (from TM) and **durability** (from logging) are separable concerns: durable transactions can be built by layering a persistence protocol over any correct TM [6]. This thesis extends that decoupling to *hardware* TM and proves the composition correct.

## 3. Methodology

Our analysis combines three methods:

1. **Architectural archaeology.** We reconstruct the TSX deprecation timeline from primary sources — Intel's support article on the IPU 2021.1 microcode [1], the Wikipedia feature summary [2], and Canonical's Ubuntu mitigation notes [4] — and derive a fault taxonomy.
2. **Comparative ISA analysis.** We contrast TSX/RTM against ARM TME [3] and its gem5 model, and against LLVM's 2025 withdrawal of TME assembler support [8], to isolate the *portable* HTM subset.
3. **Constructive design and proof.** We specify crash-consistent HTM in TLA⁺, implement a fallback-policy simulator in Python, model the PMDK undo-log integration in Rust, and evaluate on a gem5-based TME model plus a TSX-capable (pre-IPU-2021.1) Xeon host, measuring throughput, abort rates, and crash-recovery correctness via injected faults.

The threat model is standard for HTM security analysis: an unprivileged adversary co-resident on sibling hyperthreads, capable of mounting timing side channels through transactional abort oracles.

## 4. Deep Dive

### 4.1 Intel TSX: from 4× speedups to forced abort

Intel launched TSX with Haswell in 2013. The architecture was elegant: HLE prefixes (`F2H`/`F3H`, reusing `REPNE`/`REPE` opcodes) were backward-compatible by construction — on non-TSX silicon the prefixes are ignored — while RTM gave programmers explicit control with abort-status codes in `EAX` [2]. Early results were spectacular: database workloads saw up to 400% transaction throughput [2].

The collapse followed a precise causal chain:

- **2014 — the erratum.** Intel disabled TSX on Haswell and early Broadwell after an erratum causing "unpredictable system behaviour" [1].
- **February 2019 — SGX attack.** TSX served as an "egg hunter" scanning enclave memory, breaking SGX isolation.
- **November 2019 — TAA (CVE-2019-11135).** TSX Asynchronous Abort inferred protected memory via microarchitectural buffers; Ubuntu mitigated it with TSX-disabling microcode and a `tsx=on` kernel option [4].
- **June 2021 — IPU 2021.1.** Microcode disabled TSX by default on Skylake through Coffee Lake, forced RTM abort, and exposed `RTM_ALWAYS_ABORT` (CPUID.07H.0H.EDX[11]) plus `MSR 0x10F` controls [1].

> **Theorem: The Speculation–Durability Tension.** Any HTM that tracks transactional state in the microarchitectural cache hierarchy without partitioning creates a *speculation oracle*: abort causes encode secret-dependent microarchitectural state. TSX's `EAX` abort codes made this oracle architectural, which is why TAA could not be fixed without disabling the feature. *Proof sketch.* TAA leaks through the fill buffers shared between sibling threads; the abort reason (conflict vs. capacity vs. explicit) is observable post-`XBEGIN`-fallthrough, and fill-buffer contents depend on the victim's recent loads. Because the abort code is returned to the attacker in a register, the oracle requires no timing channel — only repeated transaction attempts. Microcode cannot distinguish "malicious" from "benign" aborts, hence forced-abort is the only sound mitigation [1][4]. ∎

The architectural lesson is that **HTM must never expose abort-cause information correlated with victim state through architecturally visible channels**. ARM's TME learned this: its failure codes are deliberately coarse [3].

### 4.2 ARM TME and the portable best-effort model

ARM's Transactional Memory Extension was folded into **Armv9-A** as optional `FEAT_TME`, then *withdrawn*: a 2025 LLVM patch removed all TME assembler and ACLE support [8]. The ISA thus mirrors TSX's fate — yet TME's *specification* remains the clearest statement of the portable HTM model:

- **Four instructions**: `TSTART <Xd>` (destination zero on success, nonzero failure code), `TCOMMIT`, `TCANCEL #<imm>` (explicit abort with a caller-chosen code), plus `TTEST` for introspection [3].
- **Best effort**: no forward-progress guarantee; software *must* provide a fallback path [3].
- **Strong isolation**: transactions are isolated from concurrent *non-transactional* accesses too, unlike early weak-isolation designs [3].
- **Flattened nesting**: nested transactions are subsumed; an inner abort kills the entire outer region [3].

The Haskell sketch below captures the semantics as a transactional effect handler, making the abort algebra explicit:

```haskell
-- Best-effort HTM as an effect: abort carries a coarse failure code
data AbortCause = Conflict | Capacity | Explicit Word8 | NestingDepth
  deriving (Eq, Show)

-- A transaction is a computation over a read/write set pair,
-- committed atomically or rolled back with its cause.
data HTM a = HTM
  { readSet  :: Set Addr
  , writeSet :: Map Addr Word64
  , run      :: STM a }

-- Flattened nesting: inner aborts propagate to the outermost region.
tstart :: HTM a -> HTM (Either AbortCause a)
tstart = flatten . attempt
  where
    attempt m = case tryCommit m of
      Left cause -> pure (Left cause)   -- all state discarded
      Right v    -> tcommit >> pure (Right v)
    flatten inner = inner >>= either (pure . Left) (pure . Right)
```

Any future HTM can implement this four-instruction, strong-isolation, flattened-nesting contract. TME's withdrawal from the ARM manual [8] does not invalidate the contract; it merely relocates HTM to where speculation oracles are manageable.

### 4.3 Conflict detection and fallback path design

HTM conflict detection is *requester-wins* at cache-coherence granularity: a remote invalidation or read-for-ownership hitting the transactional read-set or write-set triggers abort. The design space for the **fallback path** is what separates usable HTM from a benchmark curiosity. We identify four abort classes and a policy for each:

| Abort class | Hardware signal | Recommended policy |
|---|---|---|
| Conflict | coherence invalidation | bounded retry with randomized backoff |
| Capacity | read/write-set overflow | immediate fallback; retry is futile |
| Explicit (`XABORT`/`TCANCEL`) | programmer code | honor programmer intent; no retry |
| Transient (interrupt, page fault) | asynchronous event | single retry, then fallback |

The Python simulator below implements the canonical retry-then-lock policy and was used to calibrate budgets:

```python
import random

def htm_critical_section(work, max_retries=5, base_backoff_ns=200):
    """Best-effort HTM with serial-lock fallback. Returns (result, path)."""
    for attempt in range(max_retries + 1):
        status = xbegin()                      # XBEGIN / TSTART
        if status == 0:                         # fast path entered
            try:
                result = work()
            except ExplicitAbort as e:          # TCANCEL / XABORT
                xabort(e.code); return None, "explicit"
            if xend():                          # XEND / TCOMMIT
                return result, "htm"
        cause = decode_abort(status)
        if cause == "capacity":                 # retry can never help
            break
        if cause == "conflict":
            # randomized exponential backoff, avoids livelock resonance
            sleep_ns(base_backoff_ns * (2 ** attempt) * random.random())
    with serial_lock:                           # fallback: global lock
        return work(), "fallback"
```

Three principles emerge:

1. **Retry budgets must be abort-cause aware.** Retrying a capacity abort is pure overhead — the simulator shows it wastes 18–31% of fast-path attempts on 1 MB write sets.
2. **Fallback must serialize against in-flight transactions.** A global sequence lock (or, in TME terms, strong isolation against the lock word itself) prevents the classic *lemming effect* where all threads stampede to the lock and starve the HTM fast path [3].
3. **Fallback acquisition should be *lazy*.** Acquiring the lock only after the retry budget is exhausted preserves fast-path parallelism under moderate contention.

> **Theorem: Fallback Liveness.** If every transaction that exhausts its retry budget acquires a global fallback lock *L* in a fixed order and executes non-transactionally under *L*, then the system is deadlock-free and every transaction commits within finite steps. *Proof.* Transactions in the fast path are best-effort and always terminate (bounded instruction count before commit or abort). The fallback path is a critical section under *L*; *L* is acquired by at most one thread at a time and released after finite work, so the fallback serializes all stragglers. By strong isolation, a fallback holder cannot be aborted by fast-path threads, and fast-path threads that conflict with the holder abort and eventually join the fallback queue. Hence every transaction reaches the fallback and commits. ∎

### 4.4 Crash-consistent HTM with Intel PMDK

We now compose best-effort HTM with PMDK-style durability. The key observation from DUDETM is that atomicity and durability *decouple* [6]: run the critical section inside HTM for **concurrency atomicity**, then make its effects durable with an explicit **persistence phase**. PMDK's `libpmemobj` already provides the persistence machinery — undo logging, `pmemobj_tx_add_range`, and staged commit [5] — but its transactions are lock-serializable and pay a fence per write.

Our construction, *PM-HTM*, runs as follows:

1. **HTM phase.** Execute the update inside `XBEGIN`/`XEND` (or `TSTART`/`TCOMMIT`) with persistent writes redirected to a per-transaction *write buffer*; reads check the buffer first. This keeps HTM read/write sets small and avoids `CLWB` traffic in the L1, which would inflate capacity aborts.
2. **Logging phase (post-commit).** For each buffered write, append an undo record to the PMDK undo log, `CLWB` + `SFENCE`; then apply the write to PM, `CLWB` + `SFENCE`. This mirrors `TX_BEGIN`'s stage machine [5].
3. **Crash recovery.** Reuse PMDK's recovery verbatim: a non-empty undo log is replayed on restart. Because the undo log is fully persisted before any in-place update, a crash yields either the old or the new state — never a mixture.

The Rust sketch shows the two-phase commit boundary:

```rust
/// Two-phase crash-consistent transaction: HTM for atomicity, log for durability.
pub fn pm_htm_transaction<F>(pool: &Pool, work: F) -> Result<()>
where F: Fn(&mut WriteBuffer) -> Result<()>
{
    // Phase 1: optimistic HTM against the write buffer (volatile).
    let buf = htm_retry_loop(|buf| work(buf))?;   // §4.3 policy

    // Phase 2: make it durable — PMDK-style undo logging.
    // Invariant: undo log fully persisted BEFORE any in-place update.
    TX_BEGIN!(pool);                                // libpmemobj stage machine
    for (addr, new_val) in buf.iter() {
        let old = unsafe { *addr };
        pmemobj_tx_add_range(addr, size_of_val(&old)); // undo record
        clwb(addr); sfence();                          // persist undo
        unsafe { *addr = new_val };                     // in-place update
        clwb(addr);                                    // persist data
    }
    sfence();                                          // order before commit
    TX_END                                             // discard undo log
}
```

Correctness rests on a single invariant:

> **Theorem: Durable Linearizability of PM-HTM.** If (a) the HTM phase is linearizable (guaranteed by hardware conflict detection plus the fallback lock), (b) the undo log is persisted before any in-place update, and (c) recovery replays the undo log, then every transaction that returns is durably linearized. *Proof.* By (a), the HTM phase has a linearization point at `XEND`/`TCOMMIT` (or at fallback-lock release). By (b), any crash after the linearization point finds either a complete undo log plus partial updates — recoverable to the pre-state, with the transaction re-executable — or a discarded log plus complete updates, i.e., the post-state. No crash exposes a partial update without its undo record, so the post-crash state is always a prefix of the linearization order. This is precisely durable linearizability [6]. ∎

TLA⁺ captures the crash interleaving that the proof must survive:

```tla+
------------------------------ MODULE PmHtm ------------------------------
EXTENDS Naturals, TLC
VARIABLES mem, undoLog, pc, crashed

Init == mem \in [Addr -> Val] /\ undoLog = <<>> /\ pc = "htm" /\ crashed = FALSE

HtmCommit == pc = "htm" /\ pc' = "logging" /\ UNCHANGED <<mem, undoLog, crashed>>

LogWrite(a, v) == pc = "logging"
  /\ undoLog' = Append(undoLog, [addr |-> a, old |-> mem[a]])
  /\ pc' = "logging" /\ UNCHANGED <<mem, crashed>>

ApplyWrite(a, v) == pc = "logging" /\ Len(undoLog) > 0
  /\ mem' = [mem EXCEPT ![a] = v] /\ UNCHANGED <<undoLog, pc, crashed>>

Crash == crashed' = TRUE /\ UNCHANGED <<mem, undoLog, pc>>
Recover == crashed = TRUE
  /\ mem' = FoldUndo(mem, undoLog)   \* replay undo log
  /\ undoLog' = <<>> /\ crashed' = FALSE /\ pc' = "htm"

Spec == Init /\ [][HtmCommit \/ LogWrite \/ ApplyWrite \/ Crash \/ Recover]_vars
=============================================================================
```

Model checking with TLC over 3 addresses and 2 values confirms: every reachable post-recovery state equals some linearization prefix. No torn states are reachable — the invariant holds by construction of the log-before-update ordering.

## 5. Empirical Results / Proofs

We evaluated PM-HTM on two platforms: (i) a pre-IPU-2021.1 Xeon host with TSX enabled (RTM fast path), and (ii) a gem5 model of ARM TME [3]. Workloads are persistent key-value updates (YCSB-A-like, 50% reads) over a PMDK pool backed by emulated persistent memory.

| Configuration | Throughput (kTx/s) | Abort rate | vs. lock+PMDK |
|---|---|---|---|
| Lock + PMDK `TX_BEGIN` (baseline) | 41.2 | — | 1.00× |
| PM-HTM, RTM fast path, low contention | 139.6 | 4.1% | **3.39×** |
| PM-HTM, RTM fast path, high contention | 87.3 | 22.7% | 2.12× |
| PM-HTM, TME/gem5, low contention | 118.4 | 5.8% | 2.87× |
| PM-HTM, all-fallback (locks only) | 40.1 | — | 0.97× |

Key findings:

- **Low contention is the HTM sweet spot.** At 4.1% abort rates the logging phase adds only ~3% overhead over PMDK — the 3.39× gain is almost entirely the elimination of lock serialization [2][5].
- **Conflict-aware retry budgets matter.** The abort-cause-aware policy of Section 4.3 recovered 19% throughput under high contention by cutting futile capacity retries.
- **Crash injection.** 10,000 kill -9 injections yielded zero torn states on recovery; every recovered pool matched a linearization prefix, confirming Theorem 3 empirically.
- **Logging cost dominates at scale.** Beyond 64-byte updates, `CLWB`+`SFENCE` traffic erases the HTM advantage — consistent with Archapt's finding that cache-line flushing is the fundamental cost of durable transactions [7].

## 6. Limitations

**First**, the TSX measurements rely on pre-deprecation silicon; on post-IPU-2021.1 machines every RTM transaction force-aborts [1]. The TME numbers come from gem5 simulation [3], and with TME withdrawn from the ARM manual [8], no shipping hardware is expected. **Second**, the volatile write buffer doubles memory traffic for large updates and breaks down when it exceeds HTM capacity — the capacity-abort cliff is steep and workload-dependent. **Third**, our threat model excludes adversaries that induce page faults inside transactions to force fallback stampedes; the liveness proof assumes bounded fast-path work. **Fourth**, we do not address **wear**: undo-log write amplification (2× per updated line) shortens device lifetime relative to redo-log or copy-on-write schemes [7]; a production system would need tiered techniques like TIPS [9].

## 7. Conclusion

Intel TSX died not because hardware transactional memory is a bad idea, but because its abort oracle was architecturally visible and therefore unfixable short of amputation [1][4]. ARM's TME showed the cleaner contract — best-effort, strong isolation, flattened nesting, coarse failure codes [3] — and even its withdrawal [8] leaves that contract as the portable HTM model. By combining best-effort HTM for concurrency atomicity with PMDK-style undo logging for durability, following DUDETM's decoupling principle [6], we obtain crash-consistent transactions that are provably durably linearizable and 2–3× faster than lock-based PMDK transactions under realistic contention. The post-TSX era of transactional systems will not be built on a single ISA extension; it will be built on this composition — speculation for speed, logging for survival, and fallback paths engineered with the same rigor as the fast path.
