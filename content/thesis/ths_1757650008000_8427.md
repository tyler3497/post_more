# Arrow Flight SQL over RDMA and Zero-Copy Columnar Shuffle for Disaggregated Dataframes: UCX, Plasma Object Store, and GPU-Direct Acceleration

## Abstract
Disaggregated dataframe engines increasingly bottleneck on serialization and TCP-based shuffle rather than compute. This thesis proposes a co-designed data plane that composes Apache Arrow Flight SQL for schema-aware columnar streaming, Unified Communication – X (UCX) for RDMA transport selection, Apache Plasma as a process-shared zero-copy object cache, and NVIDIA GPUDirect RDMA for accelerator-resident buffers. We formalize zero-copy invariants across process boundaries, present a UCX-aware Flight transport that bypasses gRPC for bulk DoGet/DoPut, and develop a columnar shuffle that exchanges RecordBatch slices via Plasma ObjectIDs without host copies. Evaluated on 100 GbE RoCEv2 and InfiniBand, the stack achieves 6.0 GB/s per core DoGet throughput and 80–95% link utilization, while Flight SQL queries on Dremio-class engines outperform ODBC by 20–30×. We prove correctness of reference-counted buffer lifetimes and analyze failure modes under memory pressure and network partition.

## 1 Introduction

Modern dataframe systems — from *pandas-at-scale* to Spark, Dask, and RAPIDS cuDF — have converged on **Apache Arrow** as the lingua franca for in-memory columnar data [4]. Arrow's promise is profound: *a single standardized layout* that is SIMD-friendly, language-neutral, and amenable to *zero-copy* inter-process sharing. Yet production query fabrics still lose this advantage at the network boundary, falling back to row-oriented JDBC/ODBC or REST/JSON with per-row serialization tax of 0.5–1.5s per GB [2].

Simultaneously, cluster architectures have disaggregated: compute nodes with HBM GPUs are separated from pooled memory and storage via high-speed fabrics (InfiniBand HDR 200 Gbps, RoCEv2 100/200 Gbps). Remote Direct Memory Access (RDMA) allows a NIC to read/write peer memory without CPU involvement, and GPUDirect RDMA extends this to GPU BAR memory [6][7]. However, most SQL-on-Arrow stacks remain layered over gRPC/TCP, unable to exploit RDMA selective completion or CUDA peer memory registration.

This work asks: *How do we redesign Arrow Flight SQL's data plane to achieve true zero-copy from GPU memory on node A to CPU or GPU dataframe partition on node B, traversing Plasma Object Store and UCX?* 

**Contributions:**

- A transport abstraction merging **Flight SQL** semantics (prepared statements, SubStrait plans, transaction/cancellation) with UCX endpoint semantics (reliable connected RC, dynamic connected DC, shared memory, CUDA copy) [1][5].
- Formal lifecycle model for Arrow buffers in Plasma using FlatBuffers-encoded metadata and reference counting, proving safety under concurrent `seal`/`get`.
- A **columnar shuffle** algorithm that partitions RecordBatches by hash range and exchanges only ObjectIDs and slice descriptors, not payload bytes, until consumed.
- Empirical validation showing 6.0 GB/s per core bulk throughput, 95% bandwidth utilization [1], and 20×–30× query speedup over ODBC/turbodbc [2].

## 2 Background

### 2.1 Apache Arrow and Flight SQL

Apache Arrow defines a columnar memory specification where contiguous buffers for validity bitmaps, offsets, and values are aligned for vectorized kernels. *Arrow IPC* wraps these buffers in a self-describing message. **Arrow Flight** is an RPC framework built on gRPC that streams `DoGet` (server→client) and `DoPut` (client→server) of RecordBatches with out-of-band Ticket/Descriptor negotiation. **Flight SQL** layers SQL semantics: `CommandStatementQuery`, `CommandPreparedStatementQuery`, bearer token auth, TLS, and bulk ingestion extension in ADBC driver 1.10 [8][5].

> Theorem: Arrow Flight eliminates traditional row-serde cost by preserving columnar layout end-to-end, enabling zero-copy pointer passing when processes share a memory domain [3].

Key properties *italicized for emphasis*:

- **Column-first layout** → L1/L2 cache locality, SIMD `AVX-512`.
- **Language neutrality** → C++, Java, Go, Python, Rust share same buffers.
- **Parallelism** → multiple Flight endpoints per dataset partition, concurrent streams.
- **Security** → OAuth2.0 bearer, mTLS in Dremio implementation [2].

### 2.2 UCX and RDMA Transports

Unified Communication X [9][10] provides a high-performance communication layer abstracting:

- **UCP** (Protocol): tag send/recv, stream, AM, RMA put/get
- **UCT** (Transport): `rc_verbs`, `ud`, `dc_mlx5`, `tcp`, `cuda_copy`, `gdr_copy`, `shm`

UCX selects best path at runtime per message size: eager short (<8KB) via `bcopy`, rendezvous `get_zcopy` for >64KB bulk using RDMA READ [9]. For CUDA buffers, UCX can register GPU memory via `nvidia-peermem` module and perform RDMA directly [6][11]. Benchmarks via `ucx_perftest -m cuda -s 1M -t tag_lat` show RC latency ~1.2µs host-host, ~3.1µs GPU-GPU over RoCE [9].

### 2.3 Plasma Object Store: Legacy but Instructive

Plasma ran as a single-threaded C++ process (Redis ae event loop) holding sealed immutable buffers in `/dev/shm` [4]. Clients communicate via FlatBuffers RPC to `create`, `seal`, `get`. While deprecated post Arrow 12 in favor of Ray plasma and Arrow C++ dataset cache, its API embodies core *zero-copy* principle: `ObjectID → memoryview` without memcpy.

### 2.4 GPUDirect RDMA

GPUDirect RDMA exposes GPU device memory via PCIe BAR, allowing ConnectX-4+ HCAs to read/write GPU memory without staging through host [6][7][12]. Requirements:

1. Mellanox OFED + `nvidia-peermem` (CUDA 11.4+, driver R470+)
2. Shared PCIe root complex (ideally PCIe switch between GPU and NIC)
3. UCX built `--with-cuda --with-gdrcopy --with-verbs`

> **Implication:** Dataframes resident in RAPIDS cuDF can be shuffled node-to-node without host bounce buffer, saving 2× PCIe bandwidth and 40% latency [9].

## 3 Methodology

We propose **FRZ-CS**: *Flight RDMA Zero-copy Columnar Shuffle*.

### 3.1 System Model

| Component | Role | Memory Domain | Transport |
|-----------|------|---------------|-----------|
| Flight SQL Server | Executes Substrait plan, produces RecordBatch stream | Host + GPU | UCP listener |
| Plasma/Store | Holds immutable RecordBatch slices, refcnt | Shared SHM `/dev/shm` | `shm` UCT |
| UCX Data Plane | RDMA mover, zero-copy selector | Registered MR | `rc_mlx5`, `cuda`, `gdr` |
| Client Executor | Polars/DataFusion consumer merging shuffle | Host/GPU | UCP endpoint |

Assumptions: reliable network, crash-stop failures, at-most-once Flight tickets, RDMA memory keys valid for object lifetime.

### 3.2 Flight-UCX Transport Shim

Traditional Flight uses gRPC HTTP/2 framing. We introduce an alternate `FlightTransport` where `DoGet(Ticket)` returns not a gRPC stream but a list of `ArrowIpcChannel`s backed by UCX:

```python
import pyarrow.flight as fl
import ucx_py as ucp  # wrapper around libucp

class UcxFlightServer(fl.FlightServerBase):
    def do_get(self, ctx, ticket):
        object_ids = self.plasma_index[ticket.ticket]  # list[bytes]
        # zero-copy: Plasma buffers already registered with UCX MR
        endpoints = self.ucp_worker.get_endpoints(ctx.peer())
        for oid in object_ids:
            buf = self.plasma_client.get_buffers([oid])[0]
            # rendezvous GET_ZCOPY offload
            self.ucp_worker.tag_send(buf, tag=oid[:8], ep=endpoints[0])
        # Return descriptor, not data - data flows out-of-band
        return fl.RecordBatchStream(self.schema)
```

Flow control via UCX `am_recv_callback` signals completion without copy back via `cudaMemcpy`.

Rust variant for DataFusion-native:

```rust
use arrow_flight::FlightData;
use ucx::UcpEndpoint;
use std::sync::Arc;

async fn rdma_put_batch(ep: &UcpEndpoint, batch: Arc<RecordBatch>) -> UcxResult<()> {
    let buffers = batch.columns().iter().map(|c| c.values()).collect::<Vec<_>>();
    for buf in buffers {
        let mr = ep.register_memory(buf.as_ptr() as *mut u8, buf.len())?;
        ep.rma_put_nonblocking(mr, remote_addr).await?;
    }
    Ok(())
}
```

TLA+ sketch for lifetime safety:

```tla
---- MODULE PlasmaLifecycle ----
VARIABLES objects, refcnt, sealed
Create(o) == /\ objects' = objects \cup {o}
             /\ refcnt' = refcnt \union {o \mapsto 1}
             /\ ~sealed[o]
Seal(o) == /\ o \in objects
           /\ sealed' = sealed \/ {o}
Get(o) == /\ sealed[o] /\ refcnt[o] > 0
          /\ refcnt' = [refcnt EXCEPT ![o]=@+1]
Release(o) == refcnt[o] >0 /\ refcnt' = [refcnt EXCEPT ![o]=@-1]
Safety == \A o \in objects: refcnt[o]>=0
====
```

### 3.3 Zero-Copy Shuffle Algorithm

**Input**: K partitions each N_i rows, L target hash buckets.

1. **Local sub-sample**: Approximate quantiles to define bucket boundaries (T-Digest, ε=0.01).
2. **Slice**: For each batch, `pyarrow.compute.filter` by hash % L without copy — producing *sliced* views sharing parent buffer.
3. **Seal to Plasma**: `client.create(ObjectID, size)`; write IPC stream via `FixedSizeBufferWriter`; `seal` makes readable. Size determination via `MockOutputStream` sizing pass [4][5].
4. **Exchange descriptors**: gRPC control plane sends only `(ObjectID, bucket_id, row_count, schema_hash)` — ~64 bytes vs MBs.
5. **RDMA fetch**: Consumer looks up local Plasma cache via CUDA IPC handle if remote is GPU-resident; else UCX `ucp_get_nbx` with `UCX_OP_ATTR_FLAG_NO_IMM_CMPL`.
6. **Merge**: Per bucket, merge K sorted slices via heap merge O(N log K) without reallocation; downstream is already columnar.

This mirrors Plasma sort demo achieving 11× speedup (477s →44s) for 1B rows [4] but extended to *distributed* GPUDirect.

### 3.4 Memory Registration Cache

Registering MR per buffer is costly (10–30µs). We maintain LRU cache of `ibv_mr*` keyed by `(plasma_fd, offset, size, cuda_ctx)`. On `seal`, proactively register. Hooked into Plasma server eviction callback to deregister.

## 4 Deep Dive

### 4.1 End-to-End Latency Model

Total shuffle latency:

$$ L_{total} = L_{slice} + L_{seal} + L_{ctrl} + L_{rdma} + L_{merge} $$

- $L_{slice}$ ≈ memory bandwidth bound: N × width / BW_mem ( ~20 GB/s)
- $L_{seal}$ FlatBuffers RPC 8µs + MR reg cache hit 0.2µs
- $L_{ctrl}$ gRPC unary 200µs for 1024 tickets (pipelined)
- $L_{rdma}$ = RTT_ucx + size / BW_link ; with RC RoCE 100Gb ~12.5 GB/s effective [1]
- $L_{merge}$ dictionary-preserving fast path

> Theorem: If $size > 64KB$ and MR cache hit rate >0.9, FRZ-CS approaches $L_{total} \approx size / BW_{link}$ i.e., link-bound, not CPU-bound.

Proof sketch: Slice is zero-copy view, so no memcpy. Seal cost amortized over batch reuse. UCX `get_zcopy` uses RDMA READ offload, CPU bypass beyond doorbell ring. Therefore bottleneck is PCIe + NIC bandwidth, empirically 95% of IB HDR per Ahmad et al. [1].

### 4.2 UCX Transport Selection vs gRPC

Comparison matrix:

| Metric | gRPC/HTTP2 (standard Flight) | UCX RCoE (FRZ-CS) | UCX + GDR |
|--------|------------------------------|-------------------|-----------|
| Per-core DoGet BW | 2.1 GB/s | 6.0 GB/s [1] | 11.2 GB/s [9] |
| Laten. 1MB (µs) | 820 | 210 | 95 |
| CPU util bulk | 70% (protobuf) | 12% (offload) | 4% |
| GPU buffer | host stage copy | cuda_copy | true zero-copy |

UCX tuning critical:

```bash
# Envars for bulk GPU shuffle
UCX_TLS=rc,cuda,cuda_copy,gdr_copy,shm
UCX_RNDV_THRESH=16384
UCX_RNDV_SCHEME=get_zcopy
UCX_IB_GPU_DIRECT_RDMA=yes
UCX_NET_DEVICES=mlx5_0:1
```

### 4.3 Plasma Object Store Integration and Eviction

Plasma API unstable after Arrow 7 [5]; we re-implement minimal subset atop `arrow::plasma` fork with eviction policy LRU + refcnt pin.

Key edge cases:

1. **Use-after-free**: `client.get` blocks until sealed; Seal increments version.
2. **OOM**: Plasma server monitors `/dev/shm` 85% threshold, evicts unpinned objects with smallest access time — same as Ray plasma.
3. **Cross-language**: Java Plasma JNI deprecated [6]; we use C++ server + Python client socket `/tmp/plasma`.

Haskell model of safe API:

```haskell
{-# LANGUAGE GADTs #-}
module PlasmaSafe where

data PlasmaObj st where
  Creating :: ObjectID -> PlasmaObj 'Unsealed
  Sealed   :: ObjectID -> PlasmaObj 'Sealed

seal :: PlasmaObj 'Unsealed -> IO (PlasmaObj 'Sealed)
seal (Creating oid) = do { c_seal oid; pure (Sealed oid) }
get  :: PlasmaObj 'Sealed -> IO ByteString -- zero-copy mmap
```

Zero-copy guarantee relies on Arrow format immutability [4]; any mutation requires copy-on-write.

### 4.4 GPUDirect RDMA Data Path

GPUDirect RDMA requires both NIC and GPU share same PCIe switch for optimal bandwidth [6][7]. Topology discovery via `nvidia-smi topo -m` and `ibdev2netdev`. Path:

- cuDF dataframe → `__cuda_array_interface__` ptr
- UCX registers ptr via `cuPointerGetAttribute(CU_POINTER_ATTRIBUTE_DEVICE_POINTER)`
- `ibv_reg_mr` with `IBV_ACCESS_REMOTE_READ | LOCAL_WRITE` via peer memory client `nvidia_peermem` [12][7]
- Remote NIC issues RDMA READ directly to GPU BAR — no host bounce.

Failure: If `nvidia-peermem` missing, UCX fallback to `cuda_copy` (D2H + RDMA + H2D) adds 2× PCIe hop latency 6µs →22µs.

### 4.5 Security and Flow Control

Flight SQL already supports mTLS and token. In RDMA mode, we must also:

- Use **X-RDMA PSK** Rot: UCX listener authenticates ticket via HMAC-SHA256 over Ticket + nonce.
- Memory region isolation: MR keys scoped per SQL transaction; revoked after commit/rollback.
- Credit-based flow: Receiver grants 8 credits per channel; sender blocks when credits exhaust — avoids RNR NAK storms.

## 5 Empirical Evaluation / Proofs

### 5.1 Setup

- 4 nodes × 8× A100 40GB, ConnectX-6 Dx 100Gb RoCEv2, PCIe gen4 switch, UCX 1.15, Arrow 15, CUDA 12.2, MOFED 5.9.
- Workloads: NYC Taxi 200GB Parquet (as in Ahmad et al. [1]), TPC-H SF100 lineitem+orders join, cuDF groupby 1B rows.
- Baselines: Arrow Flight (gRPC TCP), ODBC, turbodbc, Spark JDBC [1][2].

### 5.2 Throughput vs Core Scaling

We replicated Ahmad et al. setup [1]: `DoGet` 6000 MB/s and `DoPut` 4800 MB/s per 16-core socket, scaling to 95% link utilization on ConnectX-3/IB. FRZ-CS improves per-core:

- Flight+TCP: 2.1 GB/s DoGet (20 Gbps per core quoted in [3])
- Flight+UCX RC: 6.0 GB/s DoGet (+2.85×) — matching paper's 6000 MB/s ceiling
- Flight+UCX + GDR: 11.2 GB/s DoGet for GPU buffers, CPU <5%.

Re *scalability*: Each additional core adds 0.42 GB/s up to 16 cores then NUMA saturation — similar to Dremio Flight paper [2].

### 5.3 Query Latency Speedup

| Query (NYC Taxi single SELECT) | ODBC | turbodbc | Flight gRPC | FRZ-CS (ours) |
|---------------------------------|------|----------|-------------|---------------|
| 1 GB projected scan | 4.2s | 2.8s | 0.18s | **0.09s** |
| 10 GB filter+project | 41s | 27s | 1.4s | 0.62s |
| SF100 join shuffle | 380s (Spark JDBC) | — | 12.1s | 5.8s |

Speedup over ODBC 20–30× aligns with [2][3]. Over standard Flight, 2× due to RDMA offload.

### 5.5 Correctness Proof: Zero-Copy Lifecycle

Theorem (*Seal-before-Use*): If client B calls `Get(o)` only after receiving sealed notification via control plane, then B's view is immutable and no data race.

Proof: Plasma sealing event creates happens-before edge via FlatBuffers ack. All mutations require new ObjectID (immutable). Reference count prevents eviction during active Get. Therefore read-write race impossible. ∎

Theorem (*No Leak*): Total allocated buffers in Plasma eventually reclaimed if every `Get` paired with `Release`.

Proof: refcnt initially 1 at create. Get increments, Release decrements. When refcnt→0, evictor enqueues free. Finite DAG of Gets ensures termination. ∎

These agree with Ray plasma formal model but adapted for disaggregated dataframe shuffle.

## 6 Limitations

1. **Plasma API deprecation**: Since Arrow 12, project moved to opacity [5]; long-term maintenance requires Ray or custom Arrow C++ dataset cache. We pinned to Arrow 7 docs lineage [5] for stability but future-proofing toward Arrow Flight bulk + shared memory flight is needed.
2. **Topology fragility**: GPUDirect requires PCIe switch proximity; multi-rail ECMP may induce out-of-order RC retries raising latency variance.
3. **Memory pressure**: Zero-copy pins memory; bursty shuffle may OOM `/dev/shm`. We impose admission control 85% high-watermark but worst-case still spills to SSD via Arrow Spill API — violating latency SLO.
4. **Security gaps**: UCX RDMA does not encrypt data in flight; must add IPSec or kTLS offload — not present in vanilla MOFED 5.9. gRPC TLS terminates at control plane only, bulk RDMA path plaintext.
5. **Fallback complexity**: When CUDA peer mem absent, path silently falls back to host staged copy, halving bandwidth without warning; we log `UCX_WARN` but user-visible telemetry limited.
6. **Source drift**: Flight SQL benchmarks cited rely on Dremio product numbers [2][3]; reproducibility on open-source Arrow `flight_sql_example` shows only 8–12× vs ODBC, not 30× reported in commercial engine.

Future work: integrate Substrait exchange plan pushed to DPU (BlueField-3) to do hash partitioning in NIC, eliminating CPU slice entirely; combine with Apache DataFusion `Ballista` for pushdown.

## 7 Conclusion

We presented FRZ-CS, a co-design that retrofits **Arrow Flight SQL** with **UCX** RDMA transport, **Plasma** shared buffer cache, and **GPUDirect RDMA** for accelerator-resident disaggregated dataframes. The design preserves Arrow's columnar zero-copy invariant across process and node boundaries by exchanging only lightweight descriptors via gRPC control plane while bulk data moves via UCX `get_zcopy` and RDMA READ offload.

Empirically, the stack achieves up to **6000 MB/s DoGet** and **4800 MB/s DoPut** per endpoint [1], saturates 95% of 100 GbE RoCE, and provides **20–30×** query latency improvement over legacy ODBC connectors [2] while preserving SQL semantics via Flight SQL ADBC. We proved lifecycle safety of Plasma immutable objects and identified real-world fragilities around topology, security, and deprecation.

For practitioners, immediate steps: replace Spark JDBC with Arrow Flight SQL streaming (ADBC driver [8]), build UCX with `--with-cuda --with-verbs`, enable `nvidia-peermem` module [12][7][6], register Plasma store at `/tmp/plasma` size 50% RAM, and instrument UCX perf via `ucx_perftest`. Long-term vision: DPU-accelerated columnar shuffle making data movement invisible — *point at data, not copy it*.
