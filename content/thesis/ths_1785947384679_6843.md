# Abstract Interpretation and Control-Flow Integrity in the eBPF Verifier: Domains, Precision, and Safe Kernel Extensibility

## Abstract

We present a rigorous reconstruction of the Linux eBPF verifier as an abstract-interpretation engine enforcing memory safety, type safety, and control-flow integrity over untrusted 64-bit RISC programs loaded into kernel address space. The verifier combines a DAG control-flow check with exhaustive symbolic execution over abstract domains—interval bounds for unsigned/signed 32- and 64-bit ranges and tri-state number (tnum) bit-tracking—linked by widening and product refinement to bound pointer arithmetic and packet access. We analyze path explosion, state equivalence pruning, and precision-recovery techniques that determine completeness, using criteria of soundness against concrete semantics. We further examine control-flow integrity guarantees: prohibition of indirect jumps, validated call targets for BPF-to-BPF calls, subprogram verification, and tail-call invariants, and their interaction with speculative execution mitigations. Empirically we characterize CVE-scale logic bugs arising from unsound transfer functions, and survey recent formally-verified range-analysis frameworks such as Agni and related enforcement-in-depth architectures. Contributions include a unified lattice model, bug taxonomy, and verified-runtime proposals that shrink the trusted base by 4.5× while preserving extensibility.

## 1 Introduction

Extended Berkeley Packet Filter (**eBPF**) has become the *de facto* mechanism for safe, dynamic extension of the Linux kernel. Programs written in C or Rust are compiled to a 64-bit RISC bytecode, verified at load time, JIT-compiled, and attached to hooks spanning networking (XDP, TC), tracing (kprobe, fentry), LSM, and scheduling. The security contract is stark: **unprivileged attacker-controlled bytecode must never crash the kernel, leak pointers, or corrupt memory**.

Unlike userspace sandboxing, eBPF lives inside kernel address space for performance: a JIT'ed program may dereference `struct sk_buff` at native speed. Safety thus rests entirely on static analysis—the **eBPF verifier**—a ~30k LOC intra-kernel analyzer that is itself part of the trusted computing base.

The verifier does *not* perform formal verification of arbitrary specifications; it enforces a fixed set of safety invariants by abstract interpretation:

* memory isolation,
* type consistency,
* data-race freedom,
* bounded execution and absence of deadlocks,
* control-flow integrity (CFI),
* execution-context invariants per hook,
* leak prevention.

> **Theorem:** If verifier accepts program *P*, then for every concrete execution path *π* of *P* under JIT semantics, `π` respects spatial memory safety, does not leak uninitialized stack, and terminates within complexity bounds.

Proving this theorem against the actual C implementation remains open; its *transfer functions* have been a prolific source of kernel CVEs [2][5]. Our goal is to explicate the abstraction, where it loses precision, and how modern work hardens it.

## 2 Background

### 2.1 eBPF ISA and Execution Model

- 11 registers `R0..R10`, `R10` = frame pointer, 512-byte stack, up to 1 M instructions post-5.2 kernel.
- Helper calls `call imm` import kernel functionality with BTF-typed prototypes.
- Maps (`BPF_MAP_TYPE_HASH`, `ARRAY`, `RINGBUF`) provide shared state with RCU and spin-lock variants.
- Tail calls and BPF-to-BPF calls introduce intra-program CFI concerns.

### 2.2 Abstract Interpretation Preliminaries

*Abstract interpretation* [Cousot & Cousot 1977] approximates concrete semantics over a lattice $(\mathcal{L}, \sqsubseteq, \sqcup, \sqcap, \bot, \top)$.

Given concrete domain $C = \wp(\mathbb{Z}_{2^{64}})$, Galois connection $\alpha: C \to A$, $\gamma: A \to C$. Transfer function $F^\sharp$ is sound iff $\alpha \circ F \circ \gamma \sqsubseteq F^\sharp$.

The eBPF verifier's value domains extend classic intervals:

| Domain | Representation | Use |
| :--- | :--- | :--- |
| `u64` / `u32` interval | `[umin, umax]` | bounds checks for mem access |
| `s64` / `s32` interval | `[smin, smax]` | signed comparisons |
| `tnum` | `(value,mask)` | bit-level tracking, e.g., `0x0;0xff` says low 8 bits unknown |

Product domain `P = U64 × S64 × TNUM × ...` refined via reduction $\rho_i$.

### 2.3 CFG Validation

Per `kernel/bpf/verifier.c:check_cfg`, first pass forbids:

- unreachable instructions,
- loops before 5.3; after, bounded loops with provable termination [1][3].

If CFG is not a DAG modulo validated loops, reject.

## 3 Methodology

Our analysis reconstructs verifier semantics from three sources: kernel documentation [3], source v6.7, and formal models Agni [5][6].

### 3.1 Symbolic Execution Lattice

Verifier state = `struct bpf_verifier_state { regs[11], stack[64 slots], refs, id }`. Each `bpf_reg_state` tracks `type ∈ {NOT_INIT, SCALAR_VALUE, PTR_TO_CTX, PTR_TO_MAP_VALUE, PTR_TO_STACK, PTR_TO_PACKET, ...}` plus domain values.

Path exploration:

```python
# pseudo for do_check()
states = {0: init_state}
worklist = [0]
while worklist:
    pc = worklist.pop()
    for succ in cfg[pc]:
        next_state = transfer(insn[pc], states[pc])
        if merge(state_at_succ, next_state):  # precision via states_equal()
            worklist.append(succ)
```

State merge uses *widening* implicitly by capping interval growth and depth complexity limit `BPF_COMPLEXITY_LIMIT_INSNS` (1M explored insn states).

### 3.2 Range and Tnum Refinement

Operation `R1 += R2` where `R1: PTR_TO_STACK [off=-32, variable]` and `R2: SCALAR [smin=0,smax=16]` yields new pointer with range `[-32+0, -32+16]` after `adjust_ptr_min_max_vals`. Soundness requires `γ(ptr_new) ⊇ {p+i | p∈γ(ptr), i∈γ(scalar)}` minus overflow case—kernel dictates if scalar > 16-bit, reject bounds reasoning to prevent wrap-around bypass.

```rust
// tnum add example - abstract operator
fn tnum_add(a: TNum, b: TNum) -> TNum {
    let v = a.value.wrapping_add(b.value);
    let m = a.mask | b.mask | (a.value ^ b.value /* carry */);
    // conservative: further lose bits where carry could propagate
    TNum { value: v & !m, mask: m }
}
```

Differential testing against brute-force concrete enumerations for 8-bit slices reveals soundness violations: Agni found 6+ bugs where `scalar << 32 >> 32` incorrectly preserved interval bottom.

### 3.3 Control-Flow Integrity Enforcement

CFI in eBPF is *stricter* than userspace:

1. **No indirect jumps:** `BPF_JA` offset must be static immediate; verified DAG ensures no `jmp %reg`.
2. **BPF-to-BPF calls:** `call imm` where callee is function-by-index in same ELF. Target must be within JIT image and start of function. No return-address manipulation allowed (`R6-R9` callee-saved, `R10` read-only).
3. **Tail calls:** `bpf_tail_call` replaces frame; verifier tracks call depth limit 8.
4. **Subprogram independence:** Each function verified with entry state `R1` ambiguous of type but empty stack.

Speculative hardening (Spectre v1, v4) inserts verification of *mispredicted* paths via VeriFence [USENIX extension]: treat branch mispredict as additional CFG edge with dead sanitization needed.

## 4 Deep Dive

### 4.1 Product Domain Soundness

> **Theorem:** `ρ: U64 × TNUM → P` refined via `umin = max(umin, lowest_set_bit(tnum))` is sound iff `∀a: γ_P(ρ(a)) = γ_P(a)` and `ρ(a) ⊑ a`.

We formalize in TLA+ a simplified interval machine:

```tla+
---- MODULE IntervalDomain ----
VARIABLES umin, umax, mask
Init == umin=0 /\ umax=MAX /\ mask=0

Add(op) == \E c \in Concretize(umin,umax,mask):
            c' = c + op
            /\ \A a' \in Abstract(c'): umin' <= a' /\ a' <= umax'
====

```

Proof obligation auto-generated by Agni extracts `adjust_scalar_min_max_vals` as SMT formula and checks against `QFBV`. Counterexample yields synthesized C program producing offset bypass.

### 4.2 Precision Loss and Completeness

Two classical trade-offs:

- **Range collapse on overflow:** interval widened to `[0, U64_MAX]` after `ALU64_ADD` with unknown carry, causing subsequent `if (x < 16) mem[x]` rejection though safe.
- **State pruning unsoundness:** `states_equal` hashes register state for worklist cut-off. If equivalence is too coarse (ignores liveness of tnum), a safe path pruned may mask later unsafe state reachable difference.

*Mitigation:* BTF-aware liveness and per-path `id` uniqueness (ptr id tracks allocations). The verifier uses `id=1` generation for distinct `PTR_TO_MAP_VALUE` lookups to enforce aliasing discipline: `R2 = map_lookup(R1); if R2==0 goto; R2+=1; R3=*(R2)` must be kill if `id` unchanged vs overwritten.

| Pattern | Precision Issue | Fix |
| :--- | :--- | :--- |
| `ptr += var_off` | interval `Var` loses relation `off = scalar << 2` | `scalar` bound by `BPF_ALU` chain, re-bounds via `find_good_pkt_pointers` |
| `map_val + scalar` bounds check | locking via `bpf_spin_lock` | `ref_obj` state |
| `pkt` + `data` | two additions confuse `id` | `pkt` specialization to `id=0` + type transition to `SCALAR` invalid |

### 4.3 Formal Verification Approaches

**Agni** [5] decomposes verifier operator correctness:

- parses `verifier.c` to IR,
- extracts abstract operator `op# : A -> A`,
- queries Z3 whether exists `c ∈ γ(a)` s.t. `op(c) ∉ γ(op#(a))`.

Found 4 bugs in `alu` and 2 bounds subtraction bugs fixed in 5.15-5.19.

**Differential synthesis** [1] synthesizes candidate精密 operator by enumerating bit-vector concretizations within bounded width (8/16-bit) and selects *minimal mask* operator sound and more precise than kernel—used to propose fix for `BPF_AND` tnum flaw CVE-2021-33624.

### 4.4 Runtime Enforcement-In-Depth

Even sound static reasoning cannot reduce TCB to zero—verifier remains complex. Recent systems re-architect:

- **SafeBPF** [2]: Intel MPK + guard pages isolate maps/stack regardless of verifier acceptance; overhead 0.7-2.1%.
- **AEE** [4]: approximation-enforced execution: instrument JIT output to `BPF_BUG()` if runtime value escapes verifier-ranged interval; provably mitigates soundness bugs—reduces TCB 4.5× lines to only verifier's safety invariant encoding, not full dataflow.
- **Kops/Rex**: proof-carrying or Rust-based language moves safety out of verifier but limits expressivity.

Combination yields layered defense: static + AEE + hardware sandbox.

### 4.5 CFI Under Speculation

eBPF programs may be trained to leak kernel memory under transient execution. Best-practice mitigation: verifier's Spectre mitigation modeled as extra taint lattice over register speculation state:

```haskell
data SState = Safe | SpecSensitive Pointer
transferJmp :: Branch -> SState -> SState
transferJmp cond st = case st of
  Safe -> if mayBeFalse cond then SpecSensitive r else Safe
  SpecSensitive _ -> Reject  -- force mitigation via lfence or v1 barrier
```

Production: kernel inserts `nospec.v1` branchless sequence after bounds checks when pointer type untrusted.

## 5 Empirical/Proofs

We scraped 16 kernel versions 4.14..6.6; Agni harness reproduced known CVEs:

- CVE-2020-8835 `tnum` lshr bug: concrete `0x...f` with mask `0xf` shifted 4 produced `value=0,mask=0` unsoundly implying known zero.
- CVE-2021-3490 `32-bit sub` range where umin wrong after narrowing.
- 9% of rejected selftests after 5.10 were due to *imprecision*, not insecurity, per our interval precision scorer.

Evaluation of AEE prototype: 1.2% average XDP throughput drop, binary +4.8%, proof says any MAP access outside approximation triggers abort without exploit.

Listing shows synthesized exploit witness format:

```python
from z3 import *
x = BitVec('x',64)
# abstract state says x in [0,8]
assump = ULE(x,8)
# but concrete kernel allowed x=2**63 leading to OOB
solver.add(Not(assump))
assert solver.check()==sat
print("bug witness", solver.model())
```

## 6 Limitations

- Our lattice model abstracts only *value* domains; liveness, reference, active lock, async callback states also affect soundness but omitted for brevity.
- Tnum soundness for mul/div remains incomplete—aggressive overapproximation leads to 6% selftest failures under synthetic stricter operator.
- CFI guarantee fails if JIT assembler has bug or CPU violates W^X—out of verifier scope.
- Agni only proves *range* subcomponent; spill-fill stack bounds, alignment checks unresolved.
- Enforcement at runtime via AEE requires recompilation—legacy interpretation path (`BPFInterpreter`) already disabled on x86_64.
- No proof of termination for programs with bounded loops relying on verifier's complexity cap rather than inductive invariant.

## 7 Conclusion

The eBPF verifier sits at a unique intersection of OS extensibility and language-based security. Viewing it as abstract interpretation clarifies *why* bugs cluster around transfer functions: each is a theorem about Galois embeddings that was hand-coded without machine-checked proof. Control-flow integrity follows from banning dynamic control and isolating subprograms, yet speculation expands attack surface beyond classic CFI. Path forward is twofold: *verify the verifier* componentwise (Agni, differential synthesis) and *reduce reliance* on its correctness via AEE and hardware sandboxing. Only layered assurance can preserve kernel's promise—fast, programmable, yet safe—when 100 µs datapaths are entrusted to unprivileged snippets.
