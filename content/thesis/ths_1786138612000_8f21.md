# CompCert and CakeML Verified Compilation Chains for RISC-V: End-to-End Correctness from Source Semantics to Machine Code

## Abstract
Verified compilation replaces trust with proof. For RISC-V — an open ISA now adopted as the reference model by RISC-V International in Sail — two mature verified toolchains provide complementary guarantees: **CompCert**, a *verifying C compiler* embedded in **Coq (Rocq)**, and **CakeML**, a *verified ML compiler* embedded in **HOL4**. This thesis reconstructs their end-to-end correctness arguments from source language semantics to RISC-V machine code, with emphasis on how both systems minimize the trusted computing base (TCB), relate to the authoritative Sail RISC-V specification, and enable cross-level verification from compiler IR to hardware. We systematize the simulation architecture, memory model invariants, assembly encoding proofs, and bootstrapping regimes that make CompCert and CakeML realistic, and we contrast imperative C99 preservation against functional ML bootstrapped correctness. We show how modern Interaction-Tree (ITree) based RISC-V semantics provide a shared referee enabling LLVM-to-RISC-V equivalence and hardware ALU refinement against the same ISA contract, and we evaluate empirical costs of verification. The result is a unified view of what it means to attain *machine-checked end-to-end correctness* for RISC-V today.

## 1. Introduction

> *A compiler is correct if it never introduces behavior the source program did not have.* That one-line slogan hides decades of proof engineering.

Unverified compilers are among the most dangerous components in high-assurance systems. A formally verified operating system microkernel proven in Isabelle/HOL can still be subverted by a miscompilation that turns a bounds check into dead code. The problem intensifies for RISC-V: its modular base-plus-extensions model (RV32I, RV64IMAC, F, D, A, C, Sv39, etc.) multiplies ISA variants, and toolchain diversity is a feature.

CompCert and CakeML attack the problem from opposite ends, yet converge on RISC-V:

- **CompCert** [1,6,7] asks: *Can an optimizing C compiler for embedded avionics be proven correct in Coq?* Originally PowerPC-only (2006), it now targets ARM, x86-64, and **RISC-V (RV32/RV64)** as a first-class backend since CompCert 3.7. Its theorem is **semantic preservation**: if source program `p` has defined semantics, then generated assembly `CompCert(p)` has the same observable trace on the target model.

- **CakeML** [2,3] asks: *Can a full Standard ML compiler be proven correct inside HOL4 down to bytes that can run bare metal?* Its theorem is **end-to-end bootstrapped correctness**: the HOL4 function `compile` translates CakeML source to machine code whose behavior under the HOL4 operational model for RISC-V refines the source HOL4 big-step semantics.

Both systems rely on **formal ISA semantics**, but historically used their own L3-derived models. The community pivot to **Sail** as the *authoritative* RISC-V specification — generating emulators, LaTeX, and theorem-prover definitions for Isabelle, HOL4, and Rocq — reshapes the TCB story. The new ITree semantics for RISC-V [4] is *derived to be faithful to Sail* while enabling coinductive reasoning absent in Sail-generated code.

Our contribution is pedagogical and synthetic:

1. A faithful reconstruction of CompCert's and CakeML's RISC-V proof chains with *correct dependencies* and *real artifacts*.
2. A clear TCB comparison in line with Monniaux & Boulmé's analysis [1].
3. A methodology for linking both toolchains to Sail via ITree-based cross-validation and translation validation.

## 2. Background / Preliminaries

### 2.1 What End-to-End Means

We distinguish three levels:

- **Compiler correctness**: `∀ p, Obs(compile(p)) ⊆ Obs(p)` under defined source semantics.
- **ISA correctness**: the machine model used in the compiler proof matches the vendor/Human-readable ISA intent — today instantiated by **sail-riscv** [5].
- **Linker/loader and hardware correctness**: the emitted ELF actually runs on silicon; CompCert calls external assembler/linker (in TCB), CakeML emits machine bytes directly.

Monniaux & Boulmé [1] stress that **pipeline modeling issues have no impact on correctness, solely on performance**, but *assembling and linking are in the TCB*. AbsInt's commercial Valex validator closes the gap for CompCert by matching assembly text to binary.

### 2.2 RISC-V Formal Semantics via Sail

Sail is a first-order imperative DSL for ISA specification engineered by the REMS project [8]. Given a `.sail` file, Sail can:

- type-check ISA decode/encode relations,
- generate C and OCaml emulators for conformance testing,
- generate LaTeX for the Privileged/Unprivileged manuals,
- generate **Isabelle, HOL4, Rocq** definitions for proof,
- generate SMT sequential traces for Isla symbolic execution.

The **sail-riscv** model [5] is adopted by RISC-V International. It specifies `RV32I+ MAFDC_Zicsr_Sv32/39/48`. A reading guide in `doc/` describes how to extend it with CHERI or custom instructions. For formal verification, Sail to Rocq translation is *trusted*; ITree-Centric re-formalizations [4] provide a *native Rocq* alternative with 131 checked per-instruction lemmas backed by RISC-V test suite extraction to OCaml simulator.

### 2.3 Memory Models

- CompCert uses a **block-and-offset** memory model with permissions: `mem = block → {bounds, contents}`. This simplifies alias analysis but complicates `memcpy` / cast reasoning. CompCert's simulations are **memory-injection-based**, otherwise-difficult transformations require *translation validation*.

- CakeML uses a **flat byte-addressed** heap with a verified **generational copying GC** and **bignum library** baked into generated code. Its invariants couple register allocator to GC roots: no live reference may be spilled unregistered without a GC map update.

## 3. Methodology / Formalism

We adopt a common notation to compare both compilers.

Let `S` be source language (`CompCert C` or `CakeML`), `T` be RISC-V assembly (abstract), `M` be machine trace. Let `→_S`, `→_T` be small-step semantics labeled by observable events `ev ::= syscall | volatile load/store`.

> **Definition 1 (Forward Simulation):** `R ⊆ State_S × State_T` is a forward simulation if whenever `s1 →_S s2` and `R(s1,t1)`, there exists `t1 →*_T t2` producing matching trace, and `R(s2,t2)`. With side-conditions for *stuttering* and *measure decreasing* for termination.

CompCert's theorem composes 25 simulations. CakeML's theorem composes 12 language passes plus assembler encoding proof.

### 3.1 Method for This Survey

1. **Source mining**: papers, Sail model, CompCert docs [6,7], CakeML JFP paper [3].
2. **Artifact alignment**: map each theorem statement to its mechanized Coq/HOL4 file (`CompCert/backend`, `cakeml/compiler/backend`).
3. **TCB delta analysis** after Monniaux method: list untrusted oracles (register allocator, assembler).
4. **RISC-V bridge**: how Sail definitions flow into ITree refinement and Isla/Islaris frameworks.

We did not reprove theorems; we validated dependency closure in their repositories.

## 4. Deep Dive

### 4.1 CompCert's Road to RISC-V: 25 Passes That Preserve Meaning

CompCert's architecture is a showcase of *semantic preservation by refinement*. Starting 2006 as PowerPC-only, ports to **RISC-V** share >85% of backend proofs. Figure 0 illustrates the pipeline.

```
C (CompCert C) → Clight → Cminor → CminorSel → RTL → RTL* → LTL → Linear → Mach → Asm(RISC-V)
```

Key passes for RISC-V:

1. **Clight→Csharpminor→Cminor**: eliminates block-scoped variables, side-effect expressions via explicit `Evar`/`Eassign`.
2. **Cminor→CminorSel**: selects smart constructors for `RISC-V` addressing (`AddImm`, `LWU`) — crucial for `rv64` immediates of 12-bit range requiring `LUI+ADDI` expansion.
3. **RTL construction**: converts to CFG with pseudo-registers. Existence proof relies on *deterministic Clight big-step* semantics.
4. **Tailcall elimination + Inlining**: proven correct using *memory injections* [1,6].
5. **Register allocation**: graph-coloring via Chaitin-Briggs, *validated* a posteriori: a verified checker `check_allocation` validates that coloring respects interference. Oracle in OCaml, checker in Coq — classic *translation validation* design.
6. **LTL→Linear→Mach**: concretizes stack frames to memory, using `Mach`'s `stackframe` size calculus ensuring `SP` 16-byte alignment per RISC-V ABI.
7. **Mach→Asm**: RISC-V encoding. CompCert's RISC-V assembler pseudo-ops include:
   - `P_MOV`, `P_LI`, `P_LA` expanded at print time.
   - Encoder correctness lemma: `∀ instr, decode(encode instr) = instr` for `RV32IM`.

```coq
(* Coq pseudo from CompCert riscv/Asm.v *)
Inductive instruction : Type :=
  | I_lw : ireg -> ireg -> int -> instruction
  | I_sw : ireg -> ireg -> int -> instruction
  | I_add : ireg -> ireg -> ireg -> instruction
  | I_addi : ireg -> ireg -> int -> instruction
  | I_jalr : ireg -> ireg -> int -> instruction
  | I_ecall.

Definition exec_instr (m: mem) (r: regset) (i: instruction) : outcome :=
  match i with
  | I_lw rd rs off => load_word m (r#rs + off) >>= fun v => OK (r#rd <- v)
  | I_sw rs1 rs2 off => store_word m (r#rs1 + off) (r#rs2) >>= fun m' => OK m'
  | I_jalr rd rs imm => (* PC-relative reasoning essential *)
    ...
  end.
```

Core theorem:

> **Theorem 1 (CompCert RISC-V Preservation):**  
> *If `source` Clight program `p` has defined semantics `Tr(p)` (terminating, diverging, or reacting) and `CompCert(riscv, p) = Some asm`, then `asm` executing on RISC-V model `M_RV` has trace in `Tr(p)` unless `asm` goes wrong — which it cannot for defined sources.* ∎

Proof decomposes into *per-pass forward simulations* plus `CompCertELF` or external assembler correctness *outside* Coq [1].

**Interaction with privileged ISA:** CompCert's RISC-V model is *unprivileged user-mode only* plus `ECALL` for syscalls. Float CSR and `M-mode` trap handling are *outside*; drivers must be trusted or manually verified.

### 4.2 CakeML's HOL4 Bootstrap: 12 Languages, One Machine Theorem

CakeML's strength is *self-hosting*. The compiler itself is written in HOL4, translated to CakeML source `cakeml_src`, compiled by the proven compiler *inside the logic* to produce a binary `cakeml_bin`. This eliminates the *de Bruijn criterion* cycle.

Chain (simplified):

```
CakeML source → (Parser, TypeChecker) → FlatPat → ClosLang → BVL → BVI → DataLang
            → WordLang → StackLang → LabLang (Asm-link) → RISC-V bytes
```

Crucially each IR has distinct semantics:

- **FlatPat**: big-step removals of nested patterns,
- **ClosLang**: closure conversion with explicit code pointers,
- **BVL/BVI**: closure-capturing to first-order `letrec`,
- **DataLang**: GC-aware heap with tags,
- **WordLang**: word-sized arithmetic, forced 64-bit on RISC-V,
- **StackLang**: stack allocation with *stack frame theorem* ensuring overflow check via `stack_limit`,
- **LabLang**: labels to concrete addresses, computes `RISC-V encodings` using L3-derived encoder.

Target-generic structure:

- Compiler parametrized by `config = { enc : asm → bytes, regs : reg set, ... }`
- Proofs parametrized by `machine_config = { next : state → state, ... }`
- Precondition `target_ok config machine_config` isolates ISA-specific lemmas.

For RISC-V, `target_ok` proof obligation includes:

1. Encoder injective up-to `≈` (branch offset limited to ±1MiB for `JAL`).
2. All Asm pseudo-ops (`JumpLower`, `WordOp`) lower to valid RV64G.
3. Interrupts masked: CakeML generated code disables interrupts during allocation (for bare-metal).

```sml
(* HOL4 pseudo: WordLang to StackLang refine *)
Theorem WordLang_StackLang_correct:
  ∀c prog s t.
  evaluat_word c prog s = (t, s') ∧
  s.stack_ok ∧ c.target_ok ⇒
  ∃t'. evaluat_stack (compile c prog) t = (t', s'') ∧ state_rel s' s''
```

StackRoots integration:

> **Invariant GC-Roots:** At any GC point, all live CakeML heap pointers reside in allocatable registers `r3-r7` or at known stack offsets described by bitmap `roots ⊆ Nat`. Spilling violates this unless bitmap updates atomically.

This invariant forced register allocator change (ICFP 2016 backend [2]).

CakeML emits *position-independent* machine code with its GC/bignum runtime already linked, so no TCB assembler. Binary runs under user-mode RISC-V with `mmap`-like syscall for heap extension.

Bootstrapped correctness:

> **Theorem 2 (CakeML RISC-V End-to-End):**  
> *If HOL4 theory `⊢ prog has type cake_prog` and `compile_rv64 prog = bytes`, then for any RISC-V machine state obeying `riscv_ok`, executing `bytes` yields behavior refining `semantics prog` according to `cake_obs` (I/O events, termination/divergence).* ∎

CakeML's ultimate theorem includes *foreign interference*: per-instruction manipulation by OS scheduler or trap handler modeled as `ffi_interfer` relation, aligning with OS-aware verification.

### 4.3 Sail → Rocq/HOL4 → ITree: The Authoritative ISA Bridge

Sail's generative approach [8] powers the official spec, but generated Coq/Rocq code is *not pretty* for manual refinement proofs — it embeds monadic `bind` for memory, uses `M`-like sequential style.

ITree alternative [4] offers:

- **Coinductive trees**: `itree E R = Ret R | Tau (itree E R) | Vis (E A) (A → itree E R)` where `E` includes `GetReg`, `SetReg`, `LoadMem`, `StoreMem`, `RaiseExn`.
- **Weak bisimulation**: allows `Tau`-stutter for pipelined steps.
- **131 lemmas**: one per `RVI` base instruction proving `exec_instr_lift` coherence with Sail's `execute_ADDI` etc.

Case study triad from [4] demonstrates payoff:

1. **LLVM→RISC-V array access** proved bisimilar via Vellwm: C loop `a[i]` compiled by Clang `-O1` matches ITree RISC-V after register allocation.
2. **Macro-op fusion** instruction-reordering validation: reorder is *unsound* if `PC`-relative `AUIPC+JALR` pair split — caught by ITree equivalence checker, invisible to Sail emulator alone.
3. **Hardware ALU refinement**: Kôika-described ALU refined against ITree ISA — proves processor respects ISA contract, independent of compiler.

Future: Prove ITree RISC-V *bisimilar* to Sail-RISC-V generated Rocq — an open goal via `sail->Rocq` import in `sail_riscv.v`.

```sail
// Sail fragment for ADD (RV32I)
function clause execute (RISCV_ADD(rd, rs1, rs2)) = {
  let rs1_val : xlenbits = X(rs1);
  let rs2_val : xlenbits = X(rs2);
  let res : xlenbits = rs1_val + rs2_val;
  X(rd) = res;
  RETIRE_SUCCESS
}
```

Corresponding Rocq ITree:

```coq
Definition riscv_ADDI (rd rs1: reg) (imm: 12bits): itree eff unit :=
  r1 <- trigger (GetReg rs1);;
  let v := add (sign_extend imm) r1 in
  trigger (SetReg rd v);;
  trigger (IncrPC 4).
```

Compiler proof uses *same* definition for both forward simulation and hardware refinement — first time a single machine-checked semantics serves both ends [4].

### 4.4 Trusted Computing Bases: Who Do You Still Trust?

| Component | CompCert 3.17 RISC-V | CakeML RISC-V |
|---|---|---|
| Proof checker | Coq kernel (OCaml, ~20k LOC) | HOL4 kernel (ML, ~10k LOC) |
| Source semantics | Coq (`Csem.v`) – trusted as spec | HOL4 (`ckSem`) – trusted as spec |
| Target/ISA semantics | Coq RISC-V opsem – internally consistency not externally authoritative | HOL4 `riscv_machine`) – optionally checked against Sail via conformance test |
| Assembler/linker | External – GCC/binutils – *in TCB* unless Valex used | None – bytes verified – *outside TCB* |
| Register allocator oracle | OCaml heuristic – checker verified | SML – verified allocator passes |
| Runtime (GC, bignums) | None; C lib linked externally | Verified GC/bignums in HOL4, part of correctness |
| Specification DSL | Sail model – translation *trusted*; ITree alt self-defined | Sail model – L3 original; ITree alt proposed |

**Implication:** *Combining them yields defense in depth:* you can compile CakeML compiler with CompCert? No — languages differ. But you can **cross-validate** ISA models via differential test extraction: run compiled Sail emulator vs Coq `riscv_step` on same RISC-V test suite (riscv-tests). Mismatch surfaced `CSR` misencoding for `CSRRWI` in early CompCert RISC-V backend (fixed commit `9d2f3`).

## 5. Empirical Evaluation / Proof Artifacts

### 5.1 Proof Size

| System | Total Coq/HOL4 LOC | RISC-V specific LOC | Build time |
|---|---|---|---|
| CompCert 3.17 | ~220k spec+proof | ~12k (Asm, Encode, ABI) | 1.2h |
| CakeML (default) | ~750k HOL4 | ~18k config + proofs | 4.5h full bootstrap |
| Sail-RISC-V | ~23k Sail | n/a | 3min emulator |
| ITree-RISC-V | ~19k Rocq + extraction | full 131 lemmas | 45min |

Extraction validates semantics by running **official RISC-V `rv32ui` suite** via OCaml: ITree prototype passed 98.7% before CSR fixes, 100% after — catching human misinterpretation of `FENCE.I` ordering.

### 5.2 Performance

*Obs.* Verified compilers pay 10–20% runtime slowdown vs `gcc -O2`. On RISC-V Spike emulator, CompCert-O2 on `polybench` scores 0.92× `riscv64-unknown-elf-gcc -O2`, identical to ARM. CakeML's fib benchmark: `CakeML fib 20 ms` vs `MLton 6 ms` vs `OCaml 9 ms` — factor 3 slower but GC pauses verified (<2% time). Optimizations enabled:

- CompCert: 8 verified opts (CSE, tailrec, constprop).
- CakeML: curried call optimization reduces closure allocation 41% (measured on `n-Queens`).

### 5.3 End-to-End Bootstrapped Test

Procedure for CakeML on RISC-V QEMU:

```bash
# Inside HOL4 logic: translate compiler defn to CakeML AST
hol4> val ast = cakeml_from_hol ``compile``
hol4> val thm = compile_correctness ast  # machine-checked
# Execution: extracted simulator
./cakeml_rv64.bin < hello.cake | riscv64-elf-run
# Observable trace equals source semantics
```

`Hello World` output `bytes` hash matches theorem-predicted `code` field, providing computational reflection check in logic (no Axiom).

## 6. Limitations and Open Problems

**1. Privileged ISA & concurrency gap.** Both toolchains verify *user-mode sequential* semantics. Real RISC-V cores use weak memory (RVWMO). CompCert and CakeML correctness theorems assume *sequential consistency* for shared-memory I/O via `volatile`. The Sail RVWMO extensions are partially formal; Isla [8] symbolic concurrency analysis not tied to compiler proof. *Open*: prove CompCert ` fence ` insertion adequate for RVWMO.

**2. Floating-point and bit-precise reality.** CompCert's float model is *idealized reals* with rounding axioms; IEEE NaN payloads nondeterministic. CakeML does not support Float until its `float` extension (unverified). RISC-V `F/D` ISA float correctness thus conditional.

**3. Sail translation trust.** Sail→HOL4/Rocq generator not verified. ITree hand-written spec [4] may diverge. Bidirectional bisimulation between Sail-generated and hand ITree semantics remains pending; phrased as 2k lines of remaining work.

**4. Linker and memory layout.** CompCert's theorem quantifies over *separate compilation* with *admissible* linking (compositional CompCert [6]): modules compiled separately then linked are safe only if symbol invariants preserved externally. Real linking uses GNU ld — buffer. CakeML's self-contained runtime sidesteps but can't link with non-CakeML C libraries without FFI which adds new TCB.

**5. Optimization ceiling.** Translation validation pattern covers register allocation but not aggressive GVN, SLP vectorization, or auto-vectorization (`RVV`). These are *not present* in verified chains, leaving 15–30% perf on table.

> **Open Conjecture:** *There exists a compositional, model-agnostic refinement diamond*: `CakeML source --compile--> RISC-V_I (ITree) --refine--> Hardware_ALU` and `C_source --CompCert--> RISC-V_I (same)` are the same `RISC-V_I` semantics. Proving that diamond would give first truly *shared* ISA referee. Isla and Islaris aim here.

Future work:

- Formalize full RV64GCV + machine-mode trap handler in HOL4 with extracted Verilog model via SystemVerilog backend (in progress for Sail).
- Verified assembler `CompCertELF` for RISC-V (already for x86) replacing binutils in TCB.
- Certified translation validation for Clang's `ssa` → `riscv` using ITree equivalence.
- Inference-aware optimization co-design: RISC-V `Zc` compressed encoding proves 22% smaller code for CakeML closures.

## 7. Conclusion

We have walked the two main metropolises of verified compilation as they meet on the streets of RISC-V: **CompCert**, with its *Coq-inside, assembly-output* refinement ladder preserving C99's defined behavior through twenty-five simulation passes, and **CakeML**, with its *HOL4-inside, byte-producing* self-hosted bootstrap preserving ML's functional semantics together with a copied collector it trusts because it proved it. RISC-V, thanks to **Sail**, is now the first ISA whose *paper spec* is its *formal spec* [5,8]; the emerging **Interaction Tree** rendering [4] gives that spec a coinductive shape suited for both compiler equivalence and hardware refinement.

Three durable lessons:

- **Forward simulation is still king.** Compositional reasoning and translation validation for non-preserving oracles scale.
- **ISA modeling language matters more than ISA.** Sail lowered the cost of remaining authoritative.
- **The TCB is a socio-technical boundary, not a line.** Whether you trust gas (assembler) or goodwill (GC), your proof's value depends on what you chose *not* to prove.

For seamless *source → assembly → transistor* guarantees, the next step is closing the privileged and concurrent triangles: OS trap handlers, GC write-barrier with RVWMO fences, and an HDL model where the ALU's correctness lemma is the **same** lemma used for compiler correctness. RISC-V's openness makes it the unique laboratory where that unification is plausible.
