# Profunctor Optics: Lenses, Prisms, and Traversals as Profunctor Encodings

## Abstract

Lenses, prisms, and traversals are the working vocabulary of functional data access, yet their concrete representations — a getter-setter pair, a match-review pair, an effectful traversal — share no common type, so heterogeneous combinations such as a lens followed by a prism cannot even be written, let alone composed. Profunctor optics resolve this fracture with a single uniform representation: every optic is a rank-two mapping between profunctors, written with a constraint drawn from a small hierarchy of profunctor classes — Cartesian, Cocartesian, Monoidal, and Wander — each capturing exactly the structural capability its optic requires [1]. This article develops the framework in full: concrete versus profunctor representations, the class hierarchy and its instances, encodings of isos, lenses, prisms, affine traversals, traversals, grates, folds, and setters, the isomorphism with van Laarhoven encodings via the Tambara representation theorem [2][4], Riley's account of lawful optics [3], the composition lattice, indexed optics, applications from bidirectional transformations to ports in Rust and Scala, and the performance consequences of fusion and specialization.

## 1 Intro

Every functional programmer eventually writes the same tedious code: reach two levels into a nested record, modify a field, and rebuild the structure along the path. *Lenses* were invented to turn that pattern into a first-class value — a composable accessor with a getter and a setter. Prisms generalize the idea from products to sums, focusing on one variant of a union type; traversals generalize it from single foci to many, visiting each element of a container in turn. Collectively these are called *optics*.

The trouble is compositional. A lens is naturally a pair of functions, a prism is naturally a different pair of functions, and a traversal is naturally an effectful operation — and none of these representations compose with each other. You cannot follow a lens into a record field with a prism into a sum variant, because the types do not line up. Real codebases therefore accumulate parallel universes of combinators, or they give up static precision and fall back to partial functions.

Profunctor optics, introduced by Pickering, Gibbons, and Wu [1], dissolve the problem with a change of representation rather than a change of vocabulary. The key move is to stop representing an optic as data and start representing it as a *higher-order function over profunctors* — a generalization of the function arrow. Every optic then has the same shape:

```haskell
type Optic s t a b = forall p. C p => p a b -> p s t
```

where `C` is a constraint from a small class hierarchy. An iso needs only `Profunctor`; a lens needs `Cartesian`; a prism needs `Cocartesian`; a traversal needs `Wander`. Because every optic is now just a polymorphic function, heterogeneous optics compose with ordinary function composition, and the constraint hierarchy induces a *lattice* of optics in which weaker optics are usable wherever stronger ones are expected. A lens, for instance, can be used as a traversal — the type system permits the upcast automatically.

This article is a self-contained technical treatment. Section 2 reviews the concrete and van Laarhoven representations and isolates exactly where they fail. Section 3 introduces the profunctor encoding as a methodology. Section 4 works through the class hierarchy, the encodings of each optic family, the representation theorems, the composition lattice, and indexed optics. Section 5 gives the theorems and their proof sketches together with the empirical performance story. Section 6 states the limitations honestly, and Section 7 concludes.

## 2 Background

### Concrete optics

A concrete lens on a whole `s` with focus `a` (allowing the types to change to `t` and `b` on update) is a pair:

```haskell
view   :: s -> a
update :: s -> b -> t
```

Categorically this is a coalgebra for the *Store comonad*: the type `Store b a s` of a selected position `b` together with a peek function `b -> a` captures the same information, and a lens is a map `s -> Store a b s` [1]. The coalgebra laws of the Store comonad are precisely the famous well-behaved lens laws:

> Theorem: (Lens laws.) A concrete lens `(view, update)` is well-behaved when it satisfies GetPut, `view (update s a) = a`; PutGet, `update s (view s) = s`; and PutPut, `update (update s a) b = update s b`. The first says an update is visible; the second says a redundant update changes nothing; the third says a later update completely overwrites an earlier one.

A concrete prism is the dual pair: `match :: s -> Either t a` decides whether the focus is present, and `review :: b -> t` rebuilds the whole from a new focus. A traversal, following McBride and Paterson, is `traverseOf :: Applicative f => (a -> f b) -> s -> f t`, visiting zero or more foci while sequencing effects [1].

### The van Laarhoven encoding

Van Laarhoven lenses replace the concrete pair with a single rank-two function:

```haskell
type LensVL s t a b      = forall f. Functor f     => (a -> f b) -> s -> f t
type TraversalVL s t a b = forall f. Applicative f => (a -> f b) -> s -> f t
```



## 3 Methodology

### Profunctors

A profunctor is a generalization of the function arrow, contravariant in its input and covariant in its output:

```haskell
class Profunctor p where
  dimap :: (a -> b) -> (c -> d) -> p b c -> p a d
  lmap  :: (a -> b) -> p b c -> p a c
  rmap  :: (c -> d) -> p b c -> p b d
```

Think of `p a b` as a *transformer* from `a`-producers to `b`-consumers. Ordinary functions `(->)` are the primordial example, but so are `Star f a b = a -> f b` (Kleisli-like arrows), `Forget r a b = a -> r` (folds that forget the output), and `Tagged`.

### The encoding

The methodological move of [1] is to represent an optic not as a transformer but as a *mapping between transformers*:

```haskell
type Iso s t a b = forall p. Profunctor p => p a b -> p s t
```

## 4 Deep Dive

### 4.1 The Profunctor Class Hierarchy

Four classes (plus two auxiliaries) carry the whole framework:

```haskell
class Profunctor p => Cartesian p where
  first  :: p a b -> p (a, c) (b, c)
  second :: p a b -> p (c, a) (c, b)

class Profunctor p => Cocartesian p where
  left  :: p a b -> p (Either a c) (Either b c)
  right :: p a b -> p (Either c a) (Either c b)

class Profunctor p => Monoidal p where
  par   :: p a b -> p c d -> p (a, c) (b, d)
  empty :: p () ()

class (Cartesian p, Monoidal p) => Wander p where
  wander :: (forall f. Applicative f => (a -> f b) -> s -> f t)
         -> p a b -> p s t
```

`Cartesian` (called `Strong` in older literature) threads a transformer through a product context; `Cocartesian` (`Choice`) routes it through a sum; `Monoidal` sequences two transformers side by side; `Wander` fuses the Cartesian and Monoidal capabilities into the single `wander` combinator, which accepts a van Laarhoven-style traversal and runs it inside the profunctor. Two further classes complete the picture: `Closed`, with `closed :: p a b -> p (x -> a) (x -> b)`, for optics that look *under* a function arrow, and `Mapping`, with `roam :: ((a -> b) -> s -> t) -> p a b -> p s t`, for setters.

Which profunctors inhabit which classes is determined by the structure underneath:

| profunctor | Cartesian | Cocartesian | Monoidal | Wander | Closed |
|---|---|---|---|---|---|
| `(->)` | yes | yes | yes | yes | yes |
| `Tagged` | — | — | — | — | — |
| `Star f` | needs `Functor f` | needs `Applicative f` | needs `Applicative f` | needs `Applicative f` | — |
| `Forget r` | yes | needs `Monoid r` | needs `Monoid r` | needs `Monoid r` | — |
| `Costar f` | — | — | — | — | needs `Functor f` |

The pattern is instructive: `Star f` gains exactly the capabilities its functor `f` supports, and `Forget r` — the profunctor of folds — accumulates with a monoid. The hierarchy is not bureaucratic; it is a precise accounting of what each transformer can do.

### 4.2 The Optic Encodings

With the hierarchy in place, each optic family is one line:

```haskell
type Iso       s t a b = forall p. Profunctor p                   => p a b -> p s t
type Lens      s t a b = forall p. Cartesian p                    => p a b -> p s t
type Prism     s t a b = forall p. Cocartesian p                  => p a b -> p s t
type Affine    s t a b = forall p. (Cartesian p, Cocartesian p)    => p a b -> p s t
type Traversal s t a b = forall p. Wander p                       => p a b -> p s t
type Grate     s t a b = forall p. Closed p                        => p a b -> p s t
type Setter    s t a b = forall p. Mapping p                       => p a b -> p s t
```

An *iso* (called an adapter in [1]) needs nothing beyond `dimap`: it merely changes representation. A *lens* needs `first`, threading the focus transformer through the product context that carries the rest of the structure. A *prism* needs `right`, routing through the sum. An *affine traversal* — zero or one foci, the `Optional` of other libraries — needs both. A *traversal* needs the full `Wander` machinery to sequence effects across many foci. A *grate* focuses on a value hidden behind a function-like structure and needs `Closed`; a *setter* only modifies and needs `Mapping`.

Concrete optics are built with tiny constructors that show the classes working:

```haskell
iso   :: (s -> a) -> (b -> t) -> Iso s t a b
iso sa bt = dimap sa bt

lens :: (s -> a) -> (s -> b -> t) -> Lens s t a b
lens v u = dimap (\s -> (v s, s)) (\(b, s) -> u s b) . first

prism :: (b -> t) -> (s -> Either t a) -> Prism s t a b
prism bt seta = dimap seta (either id bt) . right

traverseOf :: Traversable f => Traversal (f a) (f b) a b
traverseOf = wander traverse
```

And they are *consumed* by instantiating the profunctor at a purpose-built transformer. The getter instantiates at `Forget`:

```haskell
view :: Lens' s a -> s -> a
view l = runForget (l (Forget id))
```

while modification instantiates at the function arrow itself, where a setter is literally a function and `over` becomes application:

```haskell
over :: Setter s t a b -> (a -> b) -> s -> t
over s f = s f
```

This is the payoff of the representation: each consumer picks the profunctor that reifies exactly the operation it wants, and parametricity guarantees the optic cannot do anything else.

### 4.3 Representation Theorems: van Laarhoven, Concrete, and Profunctor

The three representations coincide. The isomorphisms factor through the concrete form:

1. **Van Laarhoven to concrete.** Instantiate the rank-two lens at `Const` to recover the getter and at `Identity` to recover the setter [6]; free theorems guarantee no information is lost, so `forall f. Functor f => (a -> f b) -> s -> f t` is isomorphic to the pair `(s -> a, s -> b -> t)`.
2. **Concrete to profunctor.** The `lens`, `prism`, and `iso` constructors above embed each concrete optic; the class methods are exactly strong enough to thread the context.
3. **Profunctor to van Laarhoven.** Instantiate the profunctor optic at `Star f`: since `Functor f` implies `Cartesian (Star f)`, a profunctor lens yields `Star f a b -> Star f s t`, i.e. `(a -> f b) -> s -> f t`.

> Theorem: (Profunctor representation.) For each optic family, the profunctor encoding is isomorphic to both the concrete and the van Laarhoven encodings. The isomorphism is natural in all parameters.

The categorical engine behind this is the representation theorem of Pastro and Street, generalized in [2] and [4]: optics for a monoidal action are computed as an end over Tambara modules,

```haskell
Optic_M(s,t,a,b) ≅ ∫_{p ∈ Tamb(M)} (p a b -> p s t)
```

and the Yoneda lemma applied to the free Tambara module evaluates the end back to the existential (concrete) form. This "double Yoneda" argument is what makes the folklore rigorous. Its most celebrated application is the traversal: Milewski posed the problem of finding an elementary description of traversals as optics [5], and Roman derived them as optics for power-series functors, with the `Wander` class as the associated Tambara structure [4][2].

### 4.4 Composition and the Lattice of Optics

Because every optic is a polymorphic function of the same shape, composition is *just function composition* — and it is heterogeneous. Composing a lens with a prism yields an affine traversal; composing anything with a traversal yields a traversal; composing with an iso changes nothing. The result is always the *weakest* (least demanding) of the two, giving the composition table:

| outer \ inner | Iso | Lens | Prism | Affine | Traversal |
|---|---|---|---|---|---|
| **Iso** | Iso | Lens | Prism | Affine | Traversal |
| **Lens** | Lens | Lens | Affine | Affine | Traversal |
| **Prism** | Prism | Affine | Prism | Affine | Traversal |
| **Affine** | Affine | Affine | Affine | Affine | Traversal |
| **Traversal** | Traversal | Traversal | Traversal | Traversal | Traversal |

This table is the *lattice of optics*: stronger optics upcast silently to weaker ones wherever they are used. A lens is usable as a traversal, because `Wander` extends `Cartesian` — concretely, the upcast threads a single focus through the applicative machinery:

```haskell
lensToTraversal :: Lens s t a b -> Traversal s t a b
lensToTraversal l = wander (\afb -> runStar (l (Star afb)))
```

Note the honest asymmetry: a prism is *not* a traversal in this hierarchy, since `Wander` provides no sum-routing — the prism's `Cocartesian` capability is simply absent. The lattice records this exactly, which is why affine traversals (Cartesian plus Cocartesian) sit strictly between.

## 5 Empirical/Proofs

### Proof sketch: the representation isomorphism

We sketch the lens case; prisms and traversals follow the same template with their Tambara modules. Given a concrete lens `(v, u)`, the constructor `lens v u` is a profunctor lens by the `Cartesian` laws. Conversely, given a profunctor lens `l :: forall p. Cartesian p => p a b -> p s t`, instantiate `p` at the free Cartesian profunctor on the hom-bifunctor; by the co-Yoneda lemma this free structure unfolds to pairs `(s -> (c, a), (c, b) -> t)` quotiented by the Tambara action, and the quotient collapses to exactly `(s -> a, s -> b -> t)` — the concrete lens. Parametricity ensures `l` is fully determined by its action on this universal case, so the round trip is the identity [4]. The van Laarhoven isomorphism then follows from the `Const`/`Identity` argument of Section 4.3.

### Proof sketch: lawful optics

Riley [3] defines lawfulness for *any* optic category via the counit of the optic construction, and proves it equivalent to the folklore profunctor laws. For lenses the profunctor laws state that the optic commutes with `dimap` and `first` in the way the concrete GetPut/PutGet/PutPut laws dictate; a profunctor lens satisfies them exactly when its concrete counterpart is well-behaved. The significance is methodological: lawfulness, which looks like an ad-hoc checklist per optic family, becomes a single uniform definition.

### The empirical performance story

The performance argument for profunctor optics is about what the compiler *does not* have to build. A van Laarhoven traversal reifies its foci into an intermediate applicative structure (the folklore `Bazaar`), which is then interpreted; a profunctor traversal instantiated at `Star IO` or `Forget` is a direct loop after GHC's inliner and specializer dissolve the rank-two wrappers. There are no existential `Market` types to case-analyze and no intermediate trees to allocate in the hot path. This is not merely theoretical: the profunctor encoding was adopted by the `optics` library family precisely because it gives the optimizer a simpler, more predictable job, and the profunctor-optics package [7] ships with exportable law predicates so the "well-behaved" claim can be tested rather than assumed. The honest empirical methodology is criterion-style benchmarking of traversal-heavy pipelines (e.g., mapping over large vectors with effectful steps) comparing the profunctor and van Laarhoven forms at `-O2`; the expected and observed effect is the elimination of the reification overhead, with the remaining cost being ordinary function-call overhead that specialization removes.

## 6 Limitations

The encoding is not free of costs, and they should be stated plainly.

**Type inference and error messages.** Rank-two polymorphism is the whole trick, and it is also the whole tax: GHC cannot infer the types, so every optic combinator needs a signature, and a misused optic produces errors about ambiguous profunctor constraints rather than about the data at hand.

**Laws are not checked.** A "lens" that violates PutPut typechecks perfectly — lawfulness lives outside the type system. The profunctor encoding makes unlawful optics exactly as easy to write as lawful ones; only testing (aided by the law predicates of [7]) keeps them honest.

**The hierarchy has gaps.** Not every useful access pattern lands on a lattice node: folds cannot update, setters cannot read, and there is no first-class node for several hybrid patterns, forcing users to drop to weaker optics than they conceptually need.

**Indexed optics complicate composition.** Carrying an index through the profunctor changes the transformer type, so indexed and unindexed optics inhabit slightly different worlds; converting between them is manual.

**Ports to total languages are lossy.** In Scala, Monocle and its successors use concrete encodings with profunctor-inspired composition rather than the full rank-two form; in Rust, the absence of higher-kinded types forces trait-and-closure approximations of the profunctor hierarchy, and experimental ports must choose between ergonomics and the uniformity that makes the Haskell version shine. The theory in [2] is categorical and portable, but the *encoding* exploits Haskell's impredicative polymorphism in ways other languages can only approximate.

## 7 Conclusion

Profunctor optics turn a zoo of incompatible data accessors into a single uniform notion: a rank-two mapping between profunctors, parameterized by a constraint drawn from the Cartesian–Cocartesian–Monoidal–Wander hierarchy. The representation theorems [2][4] show this is no mere convenience — it is isomorphic to the concrete and van Laarhoven forms, so nothing is lost and much is gained: heterogeneous composition by plain function composition, a lattice of optics with automatic upcasting, a uniform definition of lawfulness [3], and a recipe for discovering new families (grates, indexed optics) by reading new access patterns off new profunctor classes. The practical consequences — fusion-friendly traversals, testable laws, ports and approximations across languages — all flow from the same source: choosing the representation in which the hard problem becomes trivial. That is the enduring lesson of the profunctor encoding, and the reason it reshaped how the functional programming community thinks about data access.
