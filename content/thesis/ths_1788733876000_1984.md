# seL4: Formal Verification of a Microkernel from Haskell Prototype to ARM/x86 Binary with Refinement Proof

## Abstract

We present a comprehensive technical account of the **seL4 microkernel**, the first general-purpose operating-system kernel to carry a machine-checked proof of *functional correctness* down to its compiled binary. Developed at NICTA (now CSIRO Data61), seL4 is a third-generation L4 microkernel of roughly 8,700 lines of C and 600 lines of assembler whose behaviour is formally captured by a three-level refinement stack: an **abstract specification** in Isabelle/HOL, an **executable specification** derived from a Haskell prototype, and the **C implementation** itself, linked by forward-simulation proofs totalling over 200,000 lines of proof script [1][7]. We trace the complete verification pipeline — from the Haskell prototyping methodology that made the design tractable, through the AutoCorres abstraction of the C semantics, the verified capability protection model [3], binary verification against the GCC-compiled ARM binary, and the mixed-criticality (MCS) temporal-isolation extension. Empirical data — 460 defects uncovered by proof versus 16 by testing, one-way IPC at 224 cycles, and verification cost near $400 per line of code — is assessed against the proof's explicit trust assumptions and its limits concerning concurrency, timing channels, and kernel initialisation.

## 1 Introduction

Operating-system kernels occupy a uniquely unforgiving position in the software stack: every line of kernel code runs with unrestricted privilege, and a single defect can collapse every isolation boundary the system claims to enforce. Conventional assurance techniques — testing, code review, even static analysis — sample the space of possible behaviours rather than covering it. The seL4 project asked a harder question: *can a real, deployable, high-performance microkernel be proved correct, in the mathematical sense, against a complete specification of its intended behaviour* [1]?

The answer, announced in 2009, reshaped the discourse on high-assurance systems. seL4 is a member of the L4 microkernel family, implementing threads, address spaces, inter-process communication (IPC), capabilities, and interrupt delivery in roughly 10,000 lines of code — small by OS standards, yet fully general-purpose: it has since flown in autonomous helicopters under DARPA's HACMS programme, shipped in secure mobile devices, and become the reference target for verified-systems research worldwide [4][5].

This thesis reconstructs the seL4 verification effort end to end. Our contributions are expository but technical: **(i)** we formalise the three-level refinement architecture — abstract specification, executable specification, C implementation — and explain why each level exists; **(ii)** we examine the Haskell prototyping methodology that preceded and shaped the verified code; **(iii)** we detail the machinery connecting C to logic, namely the C parser, the Simpl intermediate language, and AutoCorres; **(iv)** we analyse the verified capability protection model and its derived integrity and noninterference theorems; **(v)** we cover the *binary verification* that extends the proof to the compiler's output and the mixed-criticality extension that adds temporal isolation; and **(vi)** we quantify the empirical outcome — effort, defects found, performance, and cost — while honestly delimiting what the proof does and does not guarantee.

> **Theorem (Informal statement of the main result):** Every behaviour exhibited by the seL4 C implementation (compiled by a correct compiler, on correct hardware) is a behaviour permitted by the abstract specification. Equivalently, the kernel never crashes, never dereferences a null pointer, never overflows a buffer, and never leaks memory [1][2].

The remainder of this thesis proceeds as follows. Section 2 supplies background on microkernels and capability systems. Section 3 describes the verification methodology. Section 4 deep-dives into the refinement stack, the Haskell prototype, AutoCorres, the capability model, and binary verification. Section 5 presents empirical results, Section 6 limitations, and Section 7 concludes.

## 2 Background

### 2.1 Microkernels and the L4 lineage

The microkernel proposition, articulated by Jochen Liedtke in the 1990s, is that the privileged kernel should provide only the *mechanisms* that must be privileged — address spaces, thread scheduling, and fast IPC — while all policy (device drivers, file systems, network stacks) runs in unprivileged user processes [1]. The L4 family demonstrated that this decomposition need not sacrifice performance: carefully engineered IPC paths on L4 kernels achieved round-trip latencies an order of magnitude below contemporary monolithic kernels' system-call costs.

seL4 is a **third-generation** L4 kernel. Unlike its predecessors it was designed from the outset for verification. This shows up in concrete engineering choices: the kernel is *event-based* and mostly non-preemptible, using interrupt polling rather than nested interrupt handling; system calls run to completion or to an explicit preemption point; and the design minimises shared mutable state [1]. These decisions were not aesthetic — each removes a class of interleavings that would multiply proof obligations.

### 2.2 Capabilities as the authority model

seL4's protection model is a *capability system*. All kernel objects — thread control blocks (TCBs), endpoints, address-space roots, page tables, and the untyped memory from which objects are allocated — are named and accessed exclusively through **capabilities** held in per-thread capability spaces built from CNode objects. A capability bundles a reference to an object with a set of *rights* (read, write, grant). Authority can only be *derived* downward: from a capability to untyped memory, a thread may **retype** it into fresh objects, recording the derivation in the *capability derivation tree* (CDT); capabilities may be copied, minted with reduced rights, or revoked, and revocation cascades through the CDT [3].

The consequences are twofold. First, resource accounting becomes explicit: because every kernel object must be created from untyped memory by an explicit retype, the kernel cannot allocate behind a caller's back, and memory leaks are structurally impossible. Second, the authority state of the system is *fully reified* in data structures the proof can reason about — the precondition for a machine-checked protection model [3].

### 2.3 The verification landscape before seL4

Prior to seL4, machine-checked verification of systems code existed only at small scale or with weaker guarantees: verified compilers (CompCert), separation kernels proved to enforce data separation (e.g., the AAMP7G microprocessor [5]), and the Verisoft project's stacked verification of a simplified system. None had proved *functional correctness* — that the implementation does exactly what the specification says, no more and no less — for a general-purpose kernel at the 10-kLOC scale [1]. Common Criteria EAL7, the highest assurance level, had in practice never been achieved for a general-purpose OS kernel, precisely because its demand for a complete formal correspondence between design and implementation was considered infeasible [2].

## 3 Methodology

### 3.1 Isabelle/HOL and the refinement paradigm

All seL4 proofs are conducted in **Isabelle/HOL**, an interactive theorem prover for higher-order logic. The correctness statement is *classical refinement* [1][2]:

> **Theorem (Refinement):** Let `A` be the abstract specification (a state machine with nondeterministic transitions over an abstract state), and `C` the C implementation (given formal semantics by the C parser). Then every trace of observable behaviours of `C` is a trace of `A`. Formally, `C ⊑ A`: the concrete refines the abstract.

Refinement is proved by **forward simulation**: one exhibits a *state relation* `R` between abstract and concrete states and shows that every concrete step from related states can be matched by an abstract step to related states, preserving all invariants. The practical payoff is compositional: any property preserved by refinement that is proved of the abstract specification — e.g., integrity or noninterference — holds of the C code *for free* [4].

### 3.2 Why three levels

A direct proof from abstract specification to C would drown in the semantic gap between mathematical sets and C's bytes, pointers, and partial operations. seL4 therefore interposes an **executable specification**: a deterministic, functional model of the kernel at the level of C data structures, derived from the Haskell prototype. The proof then factors into two smaller simulations, `Abstract ⊑ Executable` and `Executable ⊑ C`, each bridging a narrower gap [1][2]. A later, fourth level — the **binary** — is handled by separate binary-verification work (§4.5).

### 3.3 The Haskell prototyping methodology

Before any C was written, the kernel was implemented as a **Haskell prototype** of roughly 5,700 lines. Haskell's purity, strong typing, and executable semantics made it an ideal design laboratory: the prototype could be linked against a QEMU-derived hardware simulator so that traps were delivered to the functional model and user-level state updated *as if a real kernel had executed*, yielding a binary-compatible simulation environment for low-level design evaluation [1]. The team reports that the Haskell detour *increased* productivity even ignoring verification: design flaws surfaced in days rather than months, and the prototype's structure transferred almost directly into the C implementation and the executable specification [1].

### 3.4 From C to logic: parser, Simpl, AutoCorres

The C implementation is imported into Isabelle/HOL by a **verified C parser** that translates a well-defined subset of C99 into **Simpl**, a generic imperative language with a formal small-step semantics. Reasoning directly in Simpl remains painful, so the **AutoCorres** tool automatically abstracts the Simpl embedding into a monadic, shallow embedding in higher-order logic — essentially, the same functional style as the executable specification [2][4]. The executable-to-C refinement proof is then conducted between two functional programs rather than between logic and raw imperative code, collapsing the proof burden by an order of magnitude.

### 3.5 Invariants: the proof's load-bearing walls

Refinement proofs of this size rest on *global invariants* — properties of the kernel state proved to hold initially and to be preserved by every system call. The seL4 invariant suite includes: capabilities are always *valid* (well-typed references to correctly aligned objects); the mapping database (MDB) is acyclic and consistent with the CDT; untyped memory regions *cover* all kernel objects with no overlap; the kernel's own memory is always mapped; and all system calls terminate [2][6]. Establishing these once, at the abstract level, and transporting them down the refinement chain is what makes the 200,000-line proof effort tractable at all.

## 4 Deep Dive

### 4.1 The three-level refinement stack, precisely

At the top sits the **abstract specification** (~4,900 lines of Isabelle, ~117,000 lines of proof): a state machine in which operations are total functions over an abstract state with *controlled nondeterminism*. Nondeterminism is used deliberately — e.g., the scheduler may choose *any* runnable thread — so the specification describes *what* is permitted rather than *how* it is implemented, while remaining precise enough to prove application-level correctness [2].

The **executable specification** (~5,700 lines of Haskell, translated to ~13,000 lines of Isabelle, ~50,000 lines of proof) is deterministic and mirrors the C code's data structures and control flow. It is genuinely executable: it runs, and its behaviour was validated against the Haskell prototype's test suite [2][6].

The **C implementation** (8,700 lines of C, 600 of assembler) is the artefact that ships. The refinement `Executable ⊑ C` is the proof's technical core: for each of the kernel's system calls, AutoCorres-generated correspondence lemmas align the monadic C model with the executable specification, discharging side conditions about pointer validity, alignment, and absence of undefined behaviour [1][2].

```
 Abstract Specification   (Isabelle/HOL, ~4.9 kLOC, ~117k lines of proof)
            ↕  forward simulation (Abstract ⊑ Executable)
 Executable Specification (Haskell-derived, ~13 kLOC Isabelle, ~50k lines of proof)
            ↕  forward simulation (Executable ⊑ C, via AutoCorres)
 C Implementation         (8.7 kLOC C + 600 LOC asm, via C parser → Simpl)
            ↕  binary verification (Sewell et al.)
 Compiled Binary          (GCC -O2, ARM/x86/RISC-V)
```

### 4.2 The Haskell executable model as a design artefact

The executable specification deserves emphasis because it inverts the usual relationship between prototype and product. In conventional development the prototype is discarded; in seL4 the prototype *became* a proof artefact. Its monadic structure — kernel operations as state-and-error monads over an explicit kernel state — is visible in both the Isabelle abstract model and the final C. Consider the abstract scheduler, rendered in Isabelle's do-notation [4]:

```haskell
schedule :: Kernel ()
schedule = do
  threads <- allActiveTCBs
  thread  <- select threads
  if thread == idleThread
    then switchToIdleThread
    else switchToThread thread
```

The corresponding C scheduler is spread across several functions and hundreds of lines, managing run queues, priorities, and bitmap optimisations. The refinement proof must show that this efficient machinery always selects a thread the abstract model *could* have selected — a canonical example of data refinement, where an abstract set becomes a concrete priority queue, mediated by a coupling invariant [2].

### 4.3 AutoCorres and translation correctness

The C parser's output lives in Simpl, whose deeply embedded representation of C statements resists large-scale reasoning. AutoCorres performs *abstraction*: it converts Simpl programs into monadic specifications in higher-order logic, proving as it goes that the abstraction is faithful. The generated lemmas have the shape [2]:

> **Theorem (AutoCorres correspondence):** For C function `f` with Simpl embedding `f_simpl` and abstracted function `f'`, under the precondition that all pointers are valid and aligned, executing `f_simpl` refines `f'`.

A subtle point: the original 2009 proof *assumed* the C compiler correct. The follow-on work of Sewell et al. (PLDI 2013) proved **translation correctness** for the C-to-Isabelle parser chain, and the **binary verification** project went further — verifying the actual ARM binary produced by GCC at `-O2` against the C semantics, thereby removing the compiler from the trusted computing base for the verified configuration [6][7]. The binary proof works by lifting the machine code into a formal model of the ARM ISA and showing it refines the same C-level specification AutoCorres produced.

### 4.4 The verified protection model: capabilities, integrity, noninterference

Elkaduwe, Klein, and Elphinstone gave the first formal protection model of seL4: roughly 300 lines of specification capturing how authority flows through capability derivation, with a machine-checked proof that the model enforces a precise *access-control* policy [3]. This model was then connected downward through the refinement stack, yielding two landmark security theorems [4][7]:

1. **Integrity** (Sewell et al., ITP 2011): formalised as a Hoare triple over the top-level kernel transition —
   > **Theorem:** `{ pas_refined ∧ invs ∧ authorised } call_kernel { integrity }`
   — i.e., a thread can only modify state it holds *write* authority to, and cannot affect the scheduling or authority of others beyond what its capabilities permit [4].

2. **Information-flow noninterference / confidentiality** (Murray et al., IEEE S&P 2013): partitions configured with no information-flow authority between them cannot infer each other's state through kernel behaviour — the first machine-checked noninterference proof for a general-purpose kernel [6][7].

Both are proved at the *abstract* level and transported to C by refinement, demonstrating the methodology's central economy: prove once, abstractly; inherit everywhere, concretely [4].

### 4.5 Binary verification, WCET, and the MCS extension

**Binary verification.** Sewell et al. extended the chain below C: the compiled binary (ARMv6, later x86-64 and RISC-V 64) is proved to refine the C semantics, so properties established at the abstract level — including integrity — hold of the *running machine code* produced by an untrusted GCC [6][7]. This is translation validation rather than compiler verification: each build's output is checked, sidestepping the need to verify GCC itself.

**Worst-case execution time.** Blackham et al. (RTSS 2011) produced a *sound* WCET analysis of seL4 system calls on ARM — the first for a memory-protected system — later tightened using infeasible-path information from the higher-level proofs (RTAS 2016). Soundness here means the bound is itself proved, not merely measured [6].

**Mixed-criticality systems (MCS).** The 2019 MCS extension generalises the capability model from space to *time*: a thread's access to the processor is governed by a **scheduling-context capability** carrying a *budget* and a *period*, so a component can never consume more than one budget per period regardless of priority — temporal isolation by construction, mirroring how capabilities already isolate memory [8]. The MCS kernel is integrated in mainline seL4; its C-level functional-correctness proof is scheduled work (targeted for 2027), and timing-channel ("time protection") verification remains active research [7].

## 5 Empirical Results and Formal Proofs

### 5.1 Scale of the proof

| Artefact | Size | Proof size (lines of proof) |
|---|---|---|
| Abstract specification (Isabelle/HOL) | ~4.9 kLOC | ~117,000 |
| Executable specification (Isabelle, from Haskell) | ~13 kLOC | ~50,000 |
| C implementation | 8.7 kLOC C + 600 LOC asm | (via AutoCorres) |
| Haskell prototype | ~5.7 kLOC | — (design artefact) |
| **Total proof** | | **~200,000+ lop** (later ~500,000 incl. security/binary proofs [5]) |

The proof-to-code ratio is roughly **20–50 lines of proof per line of C** [5][7] — the dominant cost driver of the entire endeavour.

### 5.2 Defects found

Proof is a defect-discovery engine of unusual power, because each failed proof attempt pinpoints a mismatch between intent and code. The project reports [2][6]:

| Discovery method | Defects found |
|---|---|
| Shallow testing of prototype/C | 16 |
| Proof attempt (total) | ~460 |
| — of which in C implementation | ~160 |
| — of which in design | ~150 |
| — of which in specification | ~150 |

That a *completed, tested* kernel still harboured 160 implementation bugs — invisible to testing — is arguably the proof's strongest empirical advertisement.

### 5.3 Performance: verification without slowdown

A persistent myth holds that verified code must be slow. seL4 refutes it: one-way IPC costs **224 cycles** on ARM, within a small factor of the fastest unverified L4 kernels, and round-trip IPC outperforms CertiKOS by more than 5×, Fiasco.OC by 2×, and Zircon by 9× in published comparisons [5]. The verification-friendly design decisions (event-based kernel, polling) cost essentially nothing in the fast path.

### 5.4 Effort and cost

Total effort is estimated at **31.2 person-years** (20.5 for functional correctness, 4.1 for the security proofs, the remainder for binary verification and tooling), at an imputed cost near **$400 per line of code** — *less* than the ~$1,000/LOC typical of EAL6-class (unverified) high-assurance kernels, and only about twice the cost of ordinary commercial kernel development [5]. Verification, done this way, is not infinitely expensive; it is merely expensive, and cheaper than the closest uncertified alternative.

## 6 Limitations

Intellectual honesty requires stating what the proof does *not* cover [1][2][6][7]:

1. **Trusted computing base.** The proof assumes correctness of the hardware, the assembler routines, the linker, and (for the C-level result) the compiler; binary verification removes the compiler for verified configurations but not the hardware model. Kernel *initialisation* and boot code were long excluded from the proof.
2. **Concurrency.** The landmark 2009 proof targets a *uniprocessor* kernel; the verified multicore story (a "static multikernel" roadmap with an incremental concurrency-verification framework) is in progress as of 2024–2026 [7].
3. **Timing and side channels.** Functional correctness and even noninterference say nothing about *timing* channels: a partition can still signal via execution-time modulation. Time-protection mechanisms exist but their verification is ongoing research [7].
4. **Specification risk.** Refinement proves the code matches the *specification* — if the specification misunderstands the requirement (e.g., an access-control rule the model omits), the proof is vacuous for that requirement. The 150 specification bugs found during the project are both reassuring and cautionary [2].
5. **Proof maintenance.** At 50 lines of proof per line of code, every kernel change incurs heavy re-verification cost; the MCS C-level proof's multi-year timeline illustrates the drag this imposes on evolution [7].

## 7 Conclusion

seL4 demonstrated that *full formal verification of a general-purpose OS microkernel is feasible*: a three-level refinement stack in Isabelle/HOL, rooted in a Haskell prototype and connected to C by AutoCorres, yields a machine-checked theorem that the implementation — and, via binary verification, the compiled ARM/x86/RISC-V binary — exhibits only behaviours the abstract specification permits [1][7]. The verified capability protection model further delivers machine-checked integrity and information-flow confidentiality, transported to the binary by the same refinement chain [3][4]. Empirically, the effort found 460 defects testing missed, preserved competitive performance, and cost less per line than high-assurance-but-unverified development [5][6].

The research programme continues: MCS temporal isolation awaits its C-level proof, multicore verification is underway, and timing-channel closure remains open [7][8]. But the central lesson stands — the Haskell-to-Isabelle-to-C-to-binary pipeline turned "verified OS kernel" from an oxymoron into an engineering discipline, and its methods (refinement-based proof, executable specifications, translation validation) now underpin the broader field of verified systems.
