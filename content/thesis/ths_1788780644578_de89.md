# CompCert and Verified Compilation: Small-Step Semantics, Forward Simulations, and Proof-Preserving Passes

## Abstract

CompCert is the first industrially realistic optimizing C compiler accompanied by machine-checked proofs of semantic preservation, mechanized in Coq [1][2]. This thesis reconstructs its technical core: small-step operational semantics for every intermediate language, expressed as labeled transition systems whose behaviors — termination, divergence with infinite I/O traces, and going wrong — define the preservation contract [1][9]. We develop the forward-simulation methodology: each of roughly twenty passes proves a commuting diagram relating source and target executions, in lock-step, plus, or star form, with measurement arguments ruling out infinite stuttering [1][4]. The block–offset memory model and its memory injections [3] generalize simulations across memory-rearranging passes such as stack layout and spilling. We examine the verified optimization suite — constant propagation and common subexpression elimination via certified Kildall dataflow [4][6] — and register allocation, whose George–Appel graph coloring [10] runs in OCaml and is validated a posteriori by a Coq checker [5][6]. We assess industrial qualification [8], the floating-point extension [7], and the remaining limits: unverified toolchain edges, undefined behavior, and absent concurrency.

---

## 1 Introduction

Compilers are generally assumed to be *semantically transparent*: the executable code should behave exactly as prescribed by the semantics of the source program. Yet compilers — and optimizing compilers in particular — are among the most complex symbolic-transformation programs in existence, and miscompilation bugs do occur. The consequences are severe: a miscompiled program is one whose verified properties at source level are silently invalidated by the compiler itself, defeating static analysis, testing, and formal verification of the application code.

> **Theorem (The CompCert Guarantee, informal):** If a CompCert source program `p` compiles successfully to assembly program `tp`, then every observable behavior of `tp` — including termination, divergence, and I/O traces — is a behavior permitted by the formal semantics of `p`, provided `p`'s semantics is deterministic in the relevant sense. [1][2]

The CompCert project [1][2] answers the question "Can you trust your compiler?" with a machine-checked proof in Coq: the generated machine code behaves as prescribed by the semantics of the source program. Three intellectual pillars support this result:

1. **Small-step operational semantics** for every language in the compilation pipeline, from Clight (a large subset of C) through 11 intermediate languages down to assembly. Small-step semantics — as opposed to big-step — can express divergence and interaction with the environment (system calls, volatile accesses) as *infinite traces* and *finite-but-unfolding executions* [1][9].
2. **Forward simulation diagrams** per pass. Rather than proving whole-compiler correctness directly, each pass `transf : L₁ → L₂` is equipped with a proof that executions of the source program are simulated by executions of the target program. Composition of passes is composition of simulations — the verified kernel is genuinely modular [4].
3. **A rich memory model** (the CompCert *block–offset* model) supporting reasoning about pointer arithmetic, allocation, and — crucially — *memory injections* that describe how transformations such as stack-frame layout and register spilling rearrange memory while preserving observable behavior [3].

The significance extends beyond compilers: CompCert shows that *proof-preserving transformations* are practical at industrial scale, providing a reusable methodology for linkers, binary translators, DSL compilers, and JITs.

## 2 Background

### 2.1 Operational semantics: big-step versus small-step

An *operational semantics* assigns mathematical meaning to programs by describing how they execute. Two styles dominate:

| Style | Form | Strengths | Weaknesses |
|---|---|---|---|
| **Big-step** (natural semantics) | `⟨c, σ⟩ ⇓ v` — whole program to result | Simple inductive proofs; easy termination reasoning | Cannot express divergence or intermediate I/O; silent about interleaving |
| **Small-step** (structural operational semantics) | `⟨c, σ⟩ → ⟨c′, σ′⟩` — one step at a time | Expresses divergence, I/O traces, nontermination; compositional step reasoning | More verbose; needs coinduction for infinite behaviors |

CompCert uses **small-step semantics in the form of labeled transition systems (LTS)** [1][9]. Each language is characterized by:

```coq
Record semantics : Type := Semantics {
  state     : Type;                       (* machine states *)
  genv      : Type;                       (* global environments *)
  step      : genv -> state -> trace -> state -> Prop;  (* transition relation *)
  initial_state : program -> state -> Prop;
  final_state   : state -> int -> Prop;   (* return codes *)
  globalenv     : program -> genv
}.
```

Here `trace` is a finite list of *events*: external function calls, volatile loads/stores, and annotations. A program's *behaviors* are then:

- `Terminates t n` — execution produces trace `t` and exits with code `n`;
- `Diverges T` — execution produces the *infinite* trace `T` (a coinductive object);
- `Goes_wrong t` — execution produces finite trace `t` then gets stuck on undefined behavior (e.g., dereferencing a null pointer) [1][2].

This behavioral view is the currency of the whole verification: semantic preservation means the set of behaviors of the compiled program is *included in* (modulo permitted refinements) the set of behaviors of the source program.

### 2.2 Why preservation is subtle: the two degrees of freedom

Leroy [1] identifies two degrees of freedom that make a naive "same behaviors" statement false:

1. **Nondeterminism of the source.** C permits several evaluation orders for expressions. The program `return f() + g();` (with `f`, `g` printing) has two behaviors (`fg` or `gf`); CompCert fixes one order, so the compiled code exhibits a *subset*. Refinement of nondeterminism is permitted.
2. **Undefined behavior and "going wrong."** A compiler may *optimize away* operations that would go wrong at source level — e.g., eliminating a dead division by zero. The target may therefore exhibit *fewer* going-wrong behaviors. The formal statement accounts for this via *improvement* [1][9].

Consequently, CompCert proves a *forward simulation*: every behavior of the target program is matched by a behavior of the source program, not necessarily conversely. Combined with a *determinacy* argument for the target language, forward simulation can be strengthened to behavioral inclusion.

### 2.3 The CompCert pipeline

CompCert C is structured as a pipeline of approximately 20 passes through 11 intermediate languages [2]:

```
C source → Clight → C#minor → Cminor → CminorSel → RTL → LTL → LTLin → Linear → Mach → Asm
```

Key phases: (i) the *frontend* (C to Cminor) simplifies expressions, pulls side effects out, fixes evaluation order, and allocates stack frames; (ii) the *middle end* at RTL performs classical optimizations (constant propagation, CSE, dead-code elimination, inlining, tail-call elimination); (iii) the *backend* (RTL to Asm) performs register allocation, linearization, stack layout, and assembly emission [2][4].

## 3 Methodology

Our methodology mirrors CompCert's own proof architecture, analyzed through its publications [1][2][3][4][5][6][7][8][9]: (1) reconstruct the simulation framework from Leroy's POPL 2006 / CACM 2009 papers [1] and the CompCert manual and Coq development [2]; (2) analyze the memory model and memory injections via Leroy and Blazy's *Journal of Automated Reasoning* treatment [3]; (3) study constant propagation and CSE through the verified Kildall dataflow framework [4][6][9], and register allocation as the paradigmatic *verified validator* [5][6]; (4) assess empirical impact via the ERTS 2018 experience report [8] and the floating-point extension [7].

## 4 Deep Dive

### 4.1 Small-step semantics and the labeled transition system

Each CompCert language `L` is given by a small-step semantics `(S, →, s₀)` where states include a memory `m` (the block–offset model of §4.2), a call stack or continuation, and a program point. Transitions are labeled with traces:

```coq
Inductive step : genv -> state -> trace -> state -> Prop :=
  | step_assign   : ...   (* one assignment = one step *)
  | step_call     : ...   (* external call emits event  *)
  | step_builtin  : ...   (* volatile access emits event *)
  ...
```

Behaviors are defined *coinductively* for divergence:

> **Definition (Program behaviors):** For program `p` with semantics `S`, the set `Behaviors(p)` is the set of `Terminates t n`, `Diverges T`, and `Goes_wrong t` derivable from the reflexive-transitive (resp. coinductive infinite) closure of `step`. [1]

Two design decisions deserve emphasis. First, *events* make I/O observable, so simulations must preserve them exactly — a compiler cannot reorder a `printf` past another `printf`. Second, *volatile* accesses are events too, which is why CompCert cannot optimize them away [1][2].

### 4.2 The block–offset memory model

CompCert's memory model [3] is one of its most influential contributions. Memory is a finite collection of *blocks*, each block a contiguous array of bytes with bounds; a pointer is a pair `(block, offset)`:

```
pointer  ::=  (b : block, ofs : Z)     with  0 ≤ ofs < size(b)
memory   ::=  blocks with permissions and contents
```

Values stored include integers, floats, pointers, and the special `Vundef` (undefined value). Permissions (`Readable`, `Writable`, …) control which operations are legal; `Vundef` models reading uninitialized memory without committing to a particular bit pattern — the load of `Vundef` may produce `Vundef`, and *only* `Vundef` [3].

The model's masterstroke is the notion of **memory injection** `j : block → option (block × Z)`:

> **Theorem (Memory injection, Leroy–Blazy [3]):** A memory injection maps source blocks to target blocks at some offset, or to `None` (dropped). If `m₁` injects into `m₂` via `j`, then corresponding loads, stores, allocations and frees commute with `j`, provided permissions are respected and the injected regions do not overlap.

Injections are the *matching relation on memories* used across passes that rearrange allocation: SimplLocals, Stacking, and register spilling [3][4]. They separate the *spatial* rearrangement of memory from the *temporal* simulation of execution.

### 4.3 Forward simulations: lock-step, plus, and star diagrams

For a pass `transf : program₁ → program₂`, CompCert proves a **forward simulation**:

```coq
Inductive forward_simulation (S1 S2: semantics) : Prop :=
  Forward_simulation :
    (forall p s1, initial_state S1 p s1 ->
       exists s2, initial_state S2 (transf p) s2 /\ match_states s1 s2)
    -> (forall s1 t s1', step S1 s1 t s1' -> forall s2, match_states s1 s2 ->
       exists s2', step_star S2 s2 t s2' /\ match_states s1' s2')
    -> (forall s1 r s2, match_states s1 s2 -> final_state S1 s1 r ->
       exists s2', step_star S2 s2 nil s2' /\ final_state S2 s2' r)
    -> forward_simulation S1 S2.
```

The *star simulation* is a commuting square with stuttering:

```
        match
   s1  ───────  s2
   │             │∗  (zero or more steps, same trace t)
   │t            │
   ▼             ▼
   s1' ───────  s2'
        match
```

CompCert distinguishes three diagram shapes, chosen per pass according to how the pass treats steps [1][4]:

| Diagram | Meaning | Used by |
|---|---|---|
| **Lock-step** | 1 source step ↔ 1 target step | RTLgen, Asmgen |
| **Plus** | 1 source step ↔ 1+ target steps | Register allocation (spills add steps) |
| **Star** | 1 source step ↔ 0+ target steps | Dead-code elimination, CSE (steps removed) |

Star diagrams admit *infinite stuttering*: the target could spin forever without the source moving, "proving" a diverging target from a terminating source — unsound. CompCert rules this out with a **measure** on source states that strictly decreases on stuttering steps, an argument formalized as *star simulation with measurement* [1][9]. This is the single most delicate proof obligation in several optimization passes.

From forward simulation plus *target determinacy* (the target language's step relation is deterministic up to trace), Leroy derives the main preservation theorem:

> **Theorem (Semantic preservation [1]):** If `transf_program p = OK tp` and the target semantics is determinate, then `Behaviors(tp) ⊆ Behaviors(p)` modulo refinement of going-wrong behaviors: every terminating/diverging behavior of `tp` with trace `t` is a behavior of `p` with the same trace, and if `tp` goes wrong after `t` then `p` either goes wrong after `t` or exhibits `t` as a prefix of a defined behavior.

Composition is the payoff: simulations compose, so twenty verified passes yield one end-to-end theorem from Clight to Asm [1][2].### 4.4 Verified optimizations: dataflow, constant propagation, and CSE

RTL-level optimizations in CompCert share a generic **forward dataflow solver** based on Kildall's worklist algorithm [6][9]. The solver computes, for each program point `l`, an abstract value `A(l)` satisfying:

```
A(s) ⊒ T(l, A(l))   for every successor s of l
A(l) ⊒ A₀(l)        for all l
```

where `T` is the abstract transfer function and `⊒` the lattice order. The solver is verified once; each optimization instantiates it with its own lattice and transfer function [4].

- **Constant propagation** tracks, per pseudo-register, an abstract value in the flat lattice `⊤ / Const(v) / ⊥`. When `A(l)(r) = Const(v)`, uses of `r` at `l` are rewritten to `v`. The proof shows the abstract values *over-approximate* the concrete values at every reachable state — a classic *agreement invariant* [4].
- **Common subexpression elimination** tracks available expressions and rewrites redundant computations to reuse previously computed values. It uses a *star* simulation diagram because eliminated instructions correspond to zero target steps; the measure argument ensures no infinite stuttering [4].
- **Dead-code elimination**, **inlining**, **tail-call elimination**, and **if-conversion** complete the suite — all proved, all inside the verified kernel [2].

Crucially, these optimizations are proved *within* the simulation framework: each pass's `transf_program_correct` lemma is a forward simulation over RTL's small-step semantics [4].

### 4.5 Register allocation as verified validation: coloring checked, not certified

Register allocation is CompCert's most instructive proof-engineering decision [5][6]. Allocation via interference-graph coloring uses the George–Appel iterated register coalescing heuristic [10] — an intricate algorithm nobody wants to verify directly. Instead, CompCert implements the allocator in **OCaml (unverified)** and verifies its *output* in Coq:

```
RTL function ──(OCaml, unverified)──▶ candidate LTL function
        │                                        │
        └──── Coq validator: coloring correct? ───┘
              yes → accept   no → fail compilation
```

The validator checks that the returned coloring is a proper coloring of the interference graph (computed by certified liveness analysis), that spilling/reloading preserves values, and that calling conventions are respected [5]. The pass theorem is then a forward simulation from RTL to LTL semantics.

This *certifying algorithm* pattern — verify the checker, not the search — recurs throughout verified systems work, and CompCert's register allocator is its flagship example [5][6]. Blazy, Dargaye, and Leroy's backend verification [6] extends the same discipline to instruction selection, linearization, and stack layout, with memory injections (§4.2) carrying the memory-layout reasoning.

## 5 Empirical Results / Proofs

### 5.1 The mechanized proof: scale and structure

The CompCert Coq development (as of recent versions) comprises on the order of **100,000+ lines of Coq** (specifications, proofs, and extracted compiler code), covering roughly 20 passes and 11 intermediate languages [2][8]. The verification statement is not a paper proof but a *machine-checked artifact*: `coqc` checks every lemma, and the compiler itself is extracted from the verified Coq definitions, so the code that runs is the code that was proved.

The pass inventory with proof obligations (from the CompCert documentation [2]) includes:

| Pass | Source → Target | Simulation shape | Key proof device |
|---|---|---|---|
| SimplExpr | CompCert C → Clight | star | evaluation-order fixing |
| SimplLocals | Clight → Clight | star | memory injection (block merging) |
| Cshmgen | Clight → C#minor | star | control simplification |
| Cminorgen | C#minor → Cminor | star | stack allocation injection |
| Selection | Cminor → CminorSel | lock-step | operator recognition |
| RTLgen | CminorSel → RTL | lock-step | CFG construction |
| Tailcall | RTL → RTL | star | calling-convention change |
| Inlining | RTL → RTL | plus | function-body splicing |
| Constprop | RTL → RTL | star | Kildall agreement invariant |
| CSE | RTL → RTL | star + measure | available-expression invariant |
| Deadcode | RTL → RTL | star + measure | liveness invariant |
| Allocation | RTL → LTL | plus | coloring validator [5] |
| Tunneling | LTL → LTL | star | branch shortcutting |
| Linearize | LTL → Linear | plus | CFG linearization |
| Stacking | Linear → Mach | plus | frame-layout injection [3] |
| Asmgen | Mach → Asm | lock-step | per-architecture expansion [6] |

### 5.2 Qualification and industrial use

The ERTS 2018 experience report [8] documents CompCert's deployment in critical embedded software (notably avionics), where it has been *qualified* as a development tool under standards such as DO-178C. Qualification arguments leverage the proof directly: instead of testing the compiler exhaustively, the verification evidence — machine-checked semantic preservation — serves as the qualification artifact. AbsInt's factsheet [2] notes performance comparable to GCC at `-O1` on typical embedded processors: verification costs roughly one optimization level, a striking price/performance point for the assurance gained.

The floating-point extension [7] pushed the guarantee further: by formalizing IEEE-754 in the Flocq Coq library, CompCert became the first verified compiler provably preserving floating-point semantics — eliminating the class of bugs where `-O2` versus `-O0` changes numerical results (a documented GCC phenomenon on x87).

### 5.3 What the proof rules out

The guarantee rules out *all* miscompilation within the verified passes: wrong code generation, miscompiled optimizations, incorrect register allocation, broken stack layout. Notably, the verification effort itself *found bugs* during proof development — passes whose simulation proofs failed revealed genuine miscompilations [1][8]. Proof does not merely certify; it *debugs*.

## 6 Limitations

1. **The trusted computing base.** The preprocessor, assembler, and linker are *outside* the verified kernel [2]. AbsInt's Valex tool validates assembly-to-executable translation a posteriori, but is not itself verified [8]. A bug in `as` or `ld` can still miscompile.
2. **Undefined behavior is a one-way door.** The preservation theorem only constrains *defined* behaviors. If the source has undefined behavior (buffer overflow, use-after-free), the compiled program may do anything [1][9].
3. **No concurrency.** CompCert's semantics and simulations are sequential; the mainline compiler offers no verified story for data races [9].
4. **Optimization ceiling.** Loop optimizations are absent; performance trails GCC `-O2`/`-O3`. Verified vectorization remains open research.
5. **Specification risk.** The proof is relative to the authors' formal semantics of C. If that semantics mis-models ISO C or the hardware, the theorem is vacuous in the relevant corner — verification moves trust from the compiler to the specification [1][2].
6. **Proof maintenance.** Each new optimization or target demands new simulation proofs; the ~100k-line development requires continuous expert maintenance [8].

---

## 7 Conclusion

CompCert redefined what it means to trust a compiler. Its lasting contributions are threefold: (i) **small-step labeled transition semantics with observable traces** as the right substrate for compiler correctness, capturing divergence and I/O where big-step semantics go blind [1][9]; (ii) the **forward-simulation methodology** — lock-step, plus, and star diagrams with measurement arguments — as a modular, composable proof discipline for program transformations [1][4]; and (iii) the **block–offset memory model with memory injections**, which turned reasoning about memory rearrangement into a reusable algebraic device [3]. The register allocator's *verify-the-checker* pattern [5] established that heuristic algorithms and formal guarantees are not enemies: certify the validator, and the search procedure can be as clever — and as unverified — as you like.

For critical software, the practical upshot [8] is a compiler that can be *qualified* rather than merely tested, collapsing an entire class of tool-chain risk. Open frontiers — concurrency, aggressive loop optimization, verified linkers — remain, but the methodology CompCert pioneered now underpins verified systems far beyond compilation: binary lifters, DSL compilers, and proof-carrying program transformations all speak its language of simulations and injections.
