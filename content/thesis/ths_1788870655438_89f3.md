# From Samples to Layout: Post-Link and Profile-Guided Optimization at Hyperscale — AutoFDO, ThinLTO, BOLT, and Propeller

## 1. Introduction

The performance of warehouse-scale software is dominated by the *instruction fetch path*: on large server binaries, front-end stalls — instruction-cache misses, iTLB misses, and branch mispredictions — routinely account for thirty percent or more of lost cycles [6]. These stalls are a consequence of *code layout*, the mapping of basic blocks to memory addresses, which compilers traditionally decide with static heuristics that assume all branches are equally likely and all functions equally hot. The empirical reality is starkly different: profiles of production binaries consistently show that roughly ninety percent of execution time concentrates in ten percent or less of the code [4].

Profile-guided optimization (PGO) closes this gap by feeding measured behavior back into the optimizer. Classical *instrumented* PGO compiles twice — once with probes, once with the resulting profile — delivering excellent profiles at the cost of a dual-build tax and timing distortion. The alternative examined here is *sampling-based* PGO: the PMU samples the running program at negligible overhead, and the optimizer consumes these samples as if they were exact profiles. With careful reconstruction, sampling recovers nearly the full value of instrumentation — and enables a deployment model in which every production binary is continuously re-optimized against live fleet data.

This thesis studies the complete hyperscale stack built on this idea. Section 2 reviews the hardware and algorithmic substrate. Section 3 describes our methodology. Section 4 contains the deep technical core: sampling and profile reconstruction via minimum-cost flow; ThinLTO's summary-based whole-program analysis and profile-aware cross-module importing; BOLT's post-link binary rewriting with extended traveling-salesman block layout; and Propeller's relinking optimizer with basic-block sections. Section 5 presents empirical results, Section 6 confronts limitations, and Section 7 concludes.

## 2. Background

### 2.1 Why layout matters: the front end as the bottleneck

Out-of-order execution engines hide data-cache latency with remarkable skill, but they cannot hide an empty instruction queue. Every taken branch, every function call, and every kilobyte of cold code interleaved with hot code erodes front-end throughput: i-cache capacity is wasted when cold error paths sit between hot blocks, fall-through direction determines whether a branch costs nothing or a taken-branch penalty plus BTB pressure, and scattered hot code inflates iTLB misses. The Pettis–Hansen blueprint — ordering functions by call affinity and linearizing the hot path — remains the foundation; the technologies in this thesis are its industrialization at planetary scale.

### 2.2 Sampling hardware: PMU, PEBS, and LBR

Modern x86-64 processors expose a rich PMU. A counter such as `cycles` is programmed to overflow every *N* events; the overflow interrupt records the program counter as a *sample*. Two refinements make samples compiler-usable: **PEBS (Precise Event-Based Sampling)**, which guarantees the reported PC corresponds exactly to the overflowing instruction, eliminating interrupt *skid*; and **LBR (Last Branch Record)**, which logs the most recent taken branches with source and target addresses, so a single interrupt yields an entire recent control-flow path rather than one PC [6].

With `perf record -b`, a production binary can be sampled at roughly one percent overhead while capturing a faithful trace of its hot edges [4][6]. The problem then becomes *reconstruction*: converting sparse, noisy edge samples into the complete block- and edge-frequency profile the optimizer expects. Samples are incomplete, biased by skid and counter multiplexing, and generally violate flow conservation — problems AutoFDO addresses by formulating reconstruction as a **minimum-cost flow (MCF)** problem on the CFG, formalized in Section 4.1.

## 3. Methodology

Our analysis follows a layered verification methodology. For each system — AutoFDO, ThinLTO, BOLT, Propeller — we reconstructed the architecture from its primary publication or authoritative documentation [1][2][3][4][5][7], cross-checked against a recent PGO survey [6]. We then extracted the formalizable core of each system — the MCF reconstruction, the summary algebra, the extended TSP layout objective — and stated it with explicit soundness conditions, so engineering claims reduce to checkable invariants. Finally, we examined composition: how AutoFDO profiles feed ThinLTO's import decisions, how ThinLTO-optimized binaries remain optimizable by BOLT, and how Propeller offers a link-time alternative to BOLT's post-link rewriting. Wherever the sources report measured numbers, we reproduce them with citations; wherever they do not, we refrain from inventing figures.

A word on terminology. We use *FDO* for any feedback-directed optimization, *instrumented PGO* for probe-based profiles, *sample PGO / AutoFDO* for PMU-based profiles, and *post-link optimization* for transformations applied to the linked binary — compile time, link time, and post-link stages whose composition yields the headline results.

## 4. Deep Dive

### 4.1 Sampling and Profile Reconstruction: From PMU Events to Edge Frequencies

#### 4.1.1 The collection pipeline

The AutoFDO pipeline begins with the unmodified production binary running its real workload [4]:

```bash
# Collect: LBR branch samples at ~1% overhead
perf record -e cycles:u -j any,u -b -o perf.data -- ./service --prod-workload

# Convert: perf.data -> compiler-usable profile
create_llvm_prof --binary=./service --profile=perf.data --out=service.afdo

# Compile: consume the sample profile
clang -O2 -fprofile-sample-use=service.afdo -o service.opt src/*.c
```

`create_llvm_prof` (from `google/autofdo`) walks the binary's symbol table, maps each LBR source/target pair to a (function, basic block, edge) triple using debug information, and accumulates counts [6]. No instrumentation build exists anywhere in this loop: the binary being optimized is bit-identical to the binary being measured, eliminating the dual-build tax.

#### 4.1.2 Minimum-cost flow reconstruction

LBR samples record only a subset of dynamic edges. AutoFDO recovers the full profile by solving a flow problem. Let the CFG be *G = (V, E)* with entry *s*; add an artificial edge *t → s* for every exit *t*, making circulation feasible. For each sampled edge *e* with observed count *w_e*, assign a flow *f_e ≥ 0* satisfying conservation at every vertex while staying close to the observations:

> **Theorem 1 (MCF profile reconstruction).** Let *G = (V, E)* be the augmented CFG and let *S ⊆ E* be the sampled edges with counts *w_e > 0*. Consider the minimum-cost circulation problem with edge costs *c_e(f_e)* strictly convex in *f_e* and minimized at *f_e = w_e* for *e ∈ S*, and *c_e(f_e) = f_e* (linear) for *e ∉ S*. Then the optimal circulation *f\** satisfies flow conservation at every vertex, matches the sampled edges up to the convex penalty, and assigns the remaining edges the *minimum total additional flow* consistent with conservation. In particular, unsampled edges receive exactly the flow forced by conservation through sampled regions — no spurious heat is invented.

*Proof sketch.* Conservation is a linear constraint of the circulation polytope; strict convexity on sampled edges guarantees a unique optimum, and the linear cost on unsampled edges is minimized when those edges carry the least flow conservation requires. ∎

This is why AutoFDO's reconstructed profiles are trustworthy: the MCF solution is the *conservative* completion of the observations.

#### 4.1.3 Consuming samples in the compiler

Sample profiles are *keyed by source location and inline context*, not by IR identity, because the profiled binary may differ from current sources. LLVM's sample-profile loader performs *context-sensitive matching*, tolerating drift; mismatched samples degrade gracefully rather than corrupting optimization — load-bearing for continuous fleet deployment, where profiles are inherently one revision behind.

### 4.2 ThinLTO: Summary-Based Whole-Program Analysis and Profile-Aware Importing

#### 4.2.1 The scalability problem

Classical (full) LTO merges all translation units into a single module before optimizing — tens of gigabytes of RAM and hours of serial link time for warehouse-scale binaries, incompatible with fast incremental builds [1]. ThinLTO's insight is that whole-program *analysis* does not require whole-program *IR*: a compact per-module **summary** suffices for every global decision, and the IR itself is only needed inside fully parallel backends [7].

The pipeline has four phases [7]: **pre-link compilation** (each TU emits bitcode plus a module summary: per-function linkage, instruction counts, call edges with hotness hints, referenced globals, type identifiers); **thin link** (the linker reads *only the summaries*, merging them into a combined index on which all whole-program analyses run — the sole serial step, and fast); **parallel backends** (each module is optimized independently, first *importing* function copies from other modules per the thin link's decisions); and **final link**.

#### 4.2.2 The summary algebra and import soundness

A function summary records everything the importer needs without the body: linkage and visibility, call sites (callee GUID, hotness, tail-call eligibility), and instruction count as a cost proxy. The thin link decides imports by a cost model — import a callee if its instruction count is below a threshold scaled by call-site hotness — and can additionally *internalize* symbols when the index proves a single definition, enabling further optimization.

> **Theorem 2 (Soundness of summary-guided import).** If every function summary faithfully records the callee's linkage, memory effects, and set of referenced globals, and the thin link imports a function copy into a module only when the combined index proves the definition is unique and visible, then cross-module inlining of imported functions preserves program semantics.

*Proof sketch.* Importing duplicates a definition; duplication is sound when the source definition is the unique definition selected by the linker — guaranteed by the index's prevailing-copy analysis — and when the inlined copy's observable behavior is identical, which follows from complete summary effect records. ∎

The practical consequence reported in [1] is that ThinLTO scales like a non-LTO build while recovering most of the cross-module inlining of full LTO on SPEC cpu2006 and large real-world applications.

#### 4.2.3 Interaction with sample profiles

Sample PGO and ThinLTO compose synergistically. The sample profile marks call sites hot or cold *before* the thin link runs; the importer uses profile hotness to scale its thresholds, importing aggressively along hot paths and refusing to bloat cold ones. Conversely, ThinLTO's combined index lets the sample-profile loader propagate profile information into imported functions, so a hot caller in module A correctly heats the callee it imports from module B.

### 4.3 Post-Link Layout in BOLT: CFG Recovery, Extended TSP, and Hot/Cold Splitting

#### 4.3.1 Why optimize after the link?

By the time the linker finishes, the compiler's knowledge is gone — and so are its constraints. BOLT [2] exploits this: operating on the final x86-64 or AArch64 ELF binary, it *disassembles* functions, *reconstructs* their CFGs, applies profile data collected with `perf`, and *rewrites* the binary with optimized layout. Because it sees the exact bytes the CPU will fetch — after inlining, after LTO, after linker relaxation — BOLT's layout decisions are made with perfect information, and its gains are *complementary* to FDO and LTO rather than subsumed by them [2].

Input requirements are modest: at minimum an unstripped symbol table; for maximum effect, relocations preserved by the linker (`--emit-relocs` / `-q`), which enable BOLT to move functions as well as blocks [3].

```bash
# Profile the production binary with LBR
perf record -e cycles:u -j any,u -a -o perf.data -- ./service workload
# Rewrite: reorder blocks (ext-tsp), reorder functions (hfsort+), split cold code
llvm-bolt ./service -o ./service.bolt -data perf.data \
  -reorder-blocks=ext-tsp -reorder-functions=hfsort+ \
  -split-functions -split-all-cold -icf=1
```

#### 4.3.2 CFG recovery from machine code

Disassembly with correct CFG recovery is the hard prerequisite: indirect branches, jump tables, and hand-written assembly resist naive linear sweep. BOLT relies on compiler-idiom heuristics validated against Clang and GCC output, and requires that code not depend on layout properties such as function-pointer deltas [3].

#### 4.3.3 The extended TSP formulation

Given block execution counts and edge transition counts, BOLT lays out each function's blocks to maximize fall-through and minimize hot jump distances. The classical objective — maximize the sum of weights of edges whose endpoints are adjacent — is a traveling-salesman problem on the block graph. BOLT generalizes it:

> **Theorem 3 (Extended TSP layout objective).** Let blocks *B* have execution counts *c(b)* and edges *e = (u,v)* have transition counts *w(e)*. BOLT's `-reorder-blocks=ext-tsp` seeks a permutation *π* of *B* maximizing
>
> *Σ_e w(e) · fallthrough(π, e) + Σ_{u,v} w'(u,v) · proximity(π, u, v)*,
>
> where *fallthrough* rewards placing *v* immediately after *u*, and *proximity* rewards placing frequently co-executed blocks within the same cache line or page. This objective is NP-hard (it contains TSP), and BOLT solves it with a greedy chaining heuristic followed by local search.

#### 4.3.4 Function splitting and reordering

Within functions, BOLT *splits* cold blocks into a separate region (`-split-functions`, `-split-all-cold`), so the hot path becomes a dense linear sequence. Across functions, `-reorder-functions=hfsort+` clusters caller/callee pairs that the profile shows executing together.

### 4.4 Propeller and the Linker: Basic-Block Sections, Labels, and Relinking

#### 4.4.1 A link-time alternative to post-link rewriting

BOLT's power comes with a cost: it must reverse-engineer the CFG from machine code, with all the attendant fragility around indirect control flow. Propeller [5] asks a different question: what if the *compiler* and *linker* cooperated to make profile-guided layout a first-class linking step? Instead of disassembling a finished binary, Propeller has the compiler emit each basic block into its own section (`-fbasic-block-sections`), annotates blocks with *labels* that survive into the object file, profiles the binary with LBR, and then lets the *linker* reorder blocks and functions at link time using a symbol-ordering file derived from the profile.

The architecture has three cooperating components: the **compiler**, which emits basic-block sections plus *labels* — stable identifiers mapping machine addresses back to CFG nodes, so profile attribution is exact; the **profiler**, which clusters blocks into hot chains (again a TSP-like ordering) and emits an ordering file from LBR data; and the **linker**, which consumes `--symbol-ordering-file` and places `.text.hot.*` sections contiguously, cold sections far away — achieving BOLT-style density without ever disassembling anything.

#### 4.4.2 Basic-block sections in depth

The `-fbasic-block-sections` option partitions each function's machine code so that every basic block becomes an independently placeable input section, e.g. `.text.hot.3`. The linker then treats code layout as a *section-ordering* problem — a domain linkers already understand — rather than a binary-rewriting problem. Because sections carry the compiler's labels, profile attribution stays exact even across inlining and code motion that would confuse a post-link disassembler.

This design trades compiler and linker cooperation for robustness: Propeller cannot optimize binaries it did not build (BOLT's signature use case), but for first-party fleet binaries it achieves comparable layout quality with far less fragility, and "relinking with a new order file" is just another link step.

#### 4.4.3 Composition: the full hyperscale pipeline

The four systems are not competitors but pipeline stages, and production fleets deploy them in concert. A fleet binary might be compiled with AutoFDO profiles, thin-linked with profile-aware importing, relinked by Propeller for section layout — and still gain from BOLT afterward, because BOLT observes the *actual final bytes* including linker-introduced artifacts. Each stage's profile can be collected from the previous stage's output, forming a virtuous cycle of measurement and optimization.

| Stage | System | Input | Granularity | Typical gain |
|---|---|---|---|---|
| Compile | AutoFDO sample PGO | `perf`/LBR samples | IR: inline, unroll, branch hints | ~PGO parity at ~1% overhead [4][6] |
| Link | ThinLTO | Module summaries + sample profile | Cross-module inline, internalize | Most of full-LTO perf at non-LTO cost [1] |
| Link | Propeller | LBR profile + block sections | Linker section ordering | Layout wins on fleet binaries [5] |

## 5. Empirical Results and Proofs

We consolidate the measured evidence from the primary sources, distinguishing *reported results* (with citations) from *derived consequences* (marked as such).

**BOLT (reported [2]).** On data-center workloads, BOLT achieves up to **8.0%** on top of profile-guided function reordering and LTO — establishing that post-link layout is complementary to whole-program compile-time optimization. On GCC and Clang binaries, gains reach up to **15.3%** on top of FDO and LTO, and up to **35.5%** when FDO and LTO are absent: the strongest published evidence that layout is a first-order performance lever at scale.

**ThinLTO (reported [1]).** On SPEC cpu2006 and large real-world applications, ThinLTO matches most of full LTO's performance while scaling like a non-LTO build; the thin link — the only serial phase — operates purely on summaries.

**AutoFDO (reported [4][6]).** Google's deployment demonstrates that sampling-based FDO is viable for warehouse-scale applications: LBR-based profiling at approximately one percent overhead produces profiles whose optimization value rivals instrumented PGO on SPEC C++, while removing the dual-build requirement entirely [6].

**Propeller (reported [5]).** Google's relinking optimizer demonstrates additional improvements on large fleet applications over already-PGO-optimized builds, via linker-driven basic-block reordering without binary rewriting. Its significance is architectural as much as numerical: it proves the *linker* can be a profile-guided layout engine, shifting complexity from fragile post-link disassembly into the cooperative compiler–linker interface.

**Derived consequence: multiplicative stacking.** Because each stage optimizes a different program representation (IR, module summaries, linked sections, final bytes) with fresh profiles, their gains compose approximately multiplicatively rather than cannibalizing each other. The 8.0% BOLT-on-top-of-FDO+LTO figure [2] is direct evidence: if layout gains were subsumed by compile-time optimization, that number would be near zero.

**Proof obligations for deployment.** The theorems of Section 4 convert to a CI checklist: (i) verify flow conservation on the merged MCF profile; (ii) verify that summary writer and reader agree on effect records across compiler versions; (iii) verify layout gains by A/B measurement, never by assumption. Each is checkable in CI — which is what makes the pipeline deployable rather than merely publishable.

## 6. Limitations

**Profile staleness and drift.** A profile is a snapshot of yesterday's workload and last week's code. As code evolves, inline contexts shift and hot paths migrate; attribution degrades gracefully, but eventually the profile misleads. Fleets counter this with *continuous* re-profiling — collection agents, profile stores, freshness monitoring, automatic rollback on regression.

**Sampling bias.** PEBS eliminates skid on Intel, but other platforms have weaker guarantees; counter multiplexing introduces systematic distortion; short-lived processes may never accumulate enough samples. Profiles of multi-tenant machines conflate workloads unless collection is carefully scoped.

**BOLT's fragility envelope.** Disassembly-based rewriting inherits hard constraints: binaries must not depend on code-layout properties such as function-pointer deltas; jump-table heuristics are validated against Clang/GCC idioms and can misfire on hand-written assembly; `--emit-relocs` must be planned at link time; GCC's default `-freorder-blocks-and-partition` must be disabled [3]. BOLT also cannot see through runtime code generation — it optimizes the static binary only.

**ThinLTO's summary conservatism.** Summaries are lossy by design: analyses needing full IR — aggressive devirtualization, whole-program alias analysis — remain weaker than under full LTO, and the import cost model is heuristic.

**Propeller's cooperation requirement.** Propeller needs a compiler emitting basic-block sections, a linker honoring symbol ordering, and profiles keyed to compiler labels — a closed loop that works beautifully for first-party fleets and not at all for third-party binaries, where BOLT remains the only option.

**Measurement hazard.** Every stage's headline number is workload- and hardware-specific. I-cache-bound server binaries gain the most; compute-bound kernels with tiny hot loops may gain nothing or regress from increased code size. Fleet-wide deployment therefore requires guardrailed rollout: canary analysis, automatic reversion, and per-binary opt-outs — the unglamorous machinery that separates a paper from a platform.

## 7. Conclusion

This thesis has traced the complete arc of sampling-driven optimization at hyperscale, from the PMU's overflow interrupt to the linker's section ordering. Four ideas carry the weight: **reconstruct** sparse samples into trustworthy profiles with minimum-cost flow (AutoFDO); **summarize** modules so whole-program analysis scales and parallelizes (ThinLTO); **rewrite** the final binary's layout with profile-guided block and function ordering (BOLT); and **relink** with compiler-emitted basic-block sections so the linker itself becomes a layout optimizer (Propeller). Each is independently valuable — up to 8.0% post-link gains atop FDO+LTO, near-full-LTO performance at non-LTO build cost, instrumentation-free profiling at one percent overhead — and together they compose into a continuous, fleet-wide platform in which every production binary is perpetually re-measured and re-laid-out against live traffic.

The deeper lesson is methodological: all four systems succeed by replacing a static heuristic with a measured quantity, then engineering the *fidelity chain* — counters, reconstruction, summaries, labels — that makes the measurement trustworthy at each stage. Hyperscale performance engineering is therefore less about cleverer optimizations than about building the closed loop in which measurement, optimization, and deployment reinforce each other safely.
