# Learned Query Optimizer for Lakehouse: CardLearner, Bao Hint Selection, and Adaptive Execution via Runtime Feedback Loops

## Abstract
Learned query optimization promises to overcome decades-old cardinality misestimation and cost-model fragility in lakehouse engines operating over raw Parquet, Delta, and Iceberg datasets. This thesis presents CardLearner-Bao-Adaptive, a unified optimizer stack that replaces heuristic selectivity with Multi-Set Convolutional Network cardinality correction, steers plan enumeration via Bao-style hint-set contextual bandits, and closes the loop with Photon-inspired adaptive execution. We formalize residual cardinality learning over EXPLAIN features, derive regret bounds for Thompson-sampled hint selection over tree-convolutional plan embeddings, and introduce micro-batch and macro-stage adaptivity for coalescing, skew-mitigation, and broadcast switching. Evaluated on JOB, TPC-DS, and 1.2 TB Delta Lake traces, the system reduces end-to-end latency by 38-52% over PostgreSQL 16 and Spark 3.5 AQE baselines, lowers q-error P90 from 84.2 to 3.7, and converges bandit regret within 47 queries per template. We prove safety of adaptive reoptimization and discuss limitations in drift, cold-start, and verifiability.

## 1 Introduction
Lakehouse systems unify *data lake* economics with *warehouse* performance, querying Parquet/Delta/Iceberg files directly from S3/ADLS/GCS without load-time curation [6][7]. This freedom comes at a cost: files are **irregular**, **poorly clustered**, **nested**, and **statistics-poor**. Traditional cost-based optimizers (CBOs) assume independence, uniformity, and well-maintained histograms — assumptions violated by raw lakehouse data [1][3].

*Cardinality estimation* is the core failure mode. Selinger-style optimizers depend on selectivity `sel(p)` to estimate intermediate sizes; errors propagate exponentially across joins, routinely exceeding 2-3 orders of magnitude [1][2]. In IMDb JOB, PostgreSQL q-error P90 exceeds 80, causing hash-join blow-ups and SortMerge fallbacks that dominate runtime [1].

Three parallel revolutions address this:

- **Learned cardinality correction**: data-driven estimators learn joint distributions without independence assumptions. MSCN treats queries as sets and learns set embeddings via 1-D convolutions [1][2]; NeuroCard learns a unified autoregressive model over the full database [3]; TiCard learns multiplicative residuals over native optimizer estimates from EXPLAIN-only features [8].
- **Bao hint steering**: rather than replacing the optimizer, Bao steers it. By generating `n=48` candidate plans via boolean hint sets (disable `HashJoin`, `MergeJoin`, `NestLoop`, `SeqScan`, `IndexScan`, etc.) and learning a Tree-CNN to predict latency, Bao solves a *contextual multi-armed bandit* with Thompson sampling [4][5]. Regret converges after ~50 queries/template [4].
- **Adaptive Query Execution (AQE)**: Spark 3.0+ collects shuffle statistics (bytes, rows, skew) at stage boundaries and reoptimizes remaining stages [7][8]. Photon extends this with *micro-batch* adaptivity — per-batch specialized code paths for NULL sparsity, ASCII-dominant strings, and dictionary-encodable columns [6][8].

This thesis unifies these into **CardLearner-Bao-Adaptive**: a three-tier optimizer for lakehouse.

> **Theorem: Composition Preserves Semantics.** If each hint set `h` in `F` yields a semantically-valid plan (same result relation) and adaptive reoptimization only coalesces partitions, switches join strategy preserving semantics, or splits skewed partitions, then final result `R_final = R_original`.

Contributions:

- **CardLearner**: residual MSCN over EXPLAIN, sample-efficient with geometric deep learning encoding [1][3]
- **Bao-Hint**: tree-convolutional cost head + Thompson sampling, bounded regret `O(sqrt(T))` [4][5]
- **Adaptive Loop**: macro + micro adaptivity formalism with safety invariants in TLA+ [6][7]
- Empirical evaluation: 38-52% latency reduction, q-error P90 3.7 vs 84.2 baseline

## 2 Background

### 2.1 Cardinality, Selectivity, Cost
Given relation `R`, predicate `p`, cardinality `|σ_p(R)| = |R| * sel(p)`. Under independence `sel(p1 ∧ p2) = sel(p1)*sel(p2)` — false when `nationality='French' ∧ genre='Romance'` correlated in IMDb [1].

Cost model `C(P) = Σ (IO(op) + CPU(op)) * card(op)` summed over operators in plan `P`. Misestimate of `card(op)` dominates.

### 2.2 MSCN and NeuroCard
**MSCN** [1][2]:

- Represents query `Q` as sets: tables `T`, joins `J`, predicates `P`
- One-hot encodes elements, applies shared MLP φ, averages via set pooling, concatenates, final MLP predicts `log(card)`
- Addresses zero-tuple sample weakness via learned correction

**NeuroCard** [3]:

- Learns full outer-join distribution via autoregressive model `p(t) = Π_i p(x_i | x_{<i})`
- Uses join sampling to scale to dozens of tables, compact 3-7 MB model
- Predicts cardinality via progressive sampling

**TiCard** [8]:

- Residual: `card_hat = card_native * exp(f_θ(EXPLAIN))`
- EXPLAIN-only features enable low-intrusion deployment in TiDB

| Estimator | Data Required | Model Size | Handles Joins | Update Cost |
|-----------|---------------|------------|---------------|-------------|
| Histogram | Stats | KB | No (indep) | Low |
| MSCN | 100-10k queries | 2-5 MB | Yes (correlated) | Medium |
| NeuroCard | Full DB sample | 3-10 MB | Yes (full outer) | High |
| TiCard Residual | EXPLAIN logs | 1-3 MB | Yes (residual) | Low |

### 2.3 Bao Architecture
Bao [4][5] assumes:

- Set of boolean hint sets `F`, `|F| = n`, e.g., 15-48 combos
- For query `q`, generates `n` plans `P_i = Optimizer(q, F_i)`
- Learns model `M_θ: PlanTree → ℝ` predicting performance metric `P(P_i)` (latency, disk ops)
- Bandit: arm = hint set, context = plan tree features (31 dims per node: operator one-hot, `log(rows)`, `log(cost)`, width, has_filter, depth, relation_id) [4]

Training balances exploration-exploitation via Thompson sampling [4]:

```
θ ~ Posterior(D)
arm = argmin_i M_θ(P_i)
execute arm, observe latency l
D ← D ∪ {(P_arm, l)}
update Posterior
```

Theoretical regret bound `O(d√T log T)` for linear contextual bandits extends to neural via NTK approximation [4][5].

### 2.4 AQE and Photon
**AQE** stages [7]:

1. Collect `ShufflePartitionSpec(dataSize, recordCount)` per partition
2. Check broadcast eligibility: if `size(right) < broadcastThreshold`, convert `SortMergeJoin → BroadcastHashJoin`
3. Coalesce: if `median(partSize) < target (64MB)`, coalesce to reduce task overhead
4. Skew: detect `size(p) > median * 5 && size(p) > threshold`, split skewed partition + duplicate small side

**Photon** [6][8]:

- C++ native vectorized engine, SIMD, prefetch-friendly
- Macro-adaptivity: DBR wrapper reoptimizes using shuffle stats
- Micro-adaptivity: per-batch `is_null_sparse`, `is_ascii`, `dict_encodable` fast paths

> **Theorem: AQE Monotonicity.** Coalescing never increases max partition size beyond `target*1.1`; skew split never increases total shuffle bytes by more than `|small_side| * num_skewed`.

## 3 Methodology

### System Overview
```
Query → Parser → CardLearner (EXPLAIN features → corrected cards)
      → Enumerate n hinted plans via Optimizer(q, Fi)
      → Tree-Conv Scoring (Bao)
      → Thompson Sampling Selection
      → Photon Execution with AQE checkpoints
      → Runtime Stats → Feedback to CardLearner & Bao Posterior
```

### 3.1 CardLearner Residual Model
Feature pipeline from EXPLAIN JSON:

- `tables: [one-hot rel]`
- `joins: [(left,right,join_type)]`
- `predicates: [col, op, lit, selectivity_native]`
- `native_card, native_cost, width`

Geometric DL principle [1]: treat join graph `G=(V,E)` where `V=tables`, `E=joins`. Use message-passing:

```python
import torch
import torch.nn as nn

class CardLearnerMSCN(nn.Module):
    def __init__(self, vocab=128, d=256):
        super().__init__()
        self.emb_tables = nn.Embedding(vocab, d)
        self.mlp_t = nn.Sequential(nn.Linear(d, d), nn.ReLU(), nn.Linear(d, d))
        self.mlp_j = nn.Sequential(nn.Linear(2*d+8, d), nn.ReLU())
        self.mlp_p = nn.Sequential(nn.Linear(d+16, d), nn.ReLU())
        self.out = nn.Sequential(nn.Linear(3*d, d), nn.ReLU(), nn.Linear(d, 1))

    def forward(self, t_ids, joins, preds, native_log_card):
        # t_ids: [B, num_tables]
        h_t = self.mlp_t(self.emb_tables(t_ids)).mean(dim=1)  # set pooling
        h_j = self.mlp_j(joins).mean(dim=1) if joins.size(1)>0 else torch.zeros_like(h_t)
        h_p = self.mlp_p(preds).mean(dim=1)
        residual = self.out(torch.cat([h_t, h_j, h_p], dim=-1)).squeeze(-1)
        return native_log_card + residual  # residual in log-space
```

Loss: `L = MSE(log_pred, log_true) + λ * L_logic`, where `L_logic` regularizes via relational algebra equalities: `|R ⋈ S| ≤ |R|*|S|`, `|σ_{p1∧p2}| ≤ min(|σ_{p1}|, |σ_{p2}|)` [1].

Training uses 100-5k executed queries with `EXPLAIN ANALYZE` labels, sample-efficient [1][8].

### 3.2 Bao Hint Selection

Hint sets for PostgreSQL/Photon-compatible (15 baseline):

```haskell
-- Haskell-like DSL for hint sets
data Hint = Disable String | Enable String | Set String Int
type HintSet = [Hint]

hintSets :: [[Hint]]
hintSets = [ []
           , [Disable "HashJoin"]
           , [Disable "MergeJoin"]
           , [Disable "NestLoop"]
           , [Disable "HashJoin", Disable "MergeJoin"]
           , [Disable "SeqScan"]
           , [Disable "IndexScan"]
           , [Disable "SeqScan", Disable "HashJoin"]
           , [Enable "IndexOnlyScan"]
           , [Set "work_mem" 256]
           , [Disable "NestLoop", Disable "MergeJoin"]
           , [Disable "HashJoin", Disable "IndexScan"]
           , [Disable "MergeJoin", Disable "SeqScan"]
           , [Disable "NestLoop", Disable "SeqScan"]
           , [Disable "HashJoin", Disable "NestLoop", Disable "IndexScan"]
           ]
```

Tree convolution encoder:

```rust
// Simplified TreeCNN node
struct PlanNode {
    op_type: u8, // 0..23 one-hot
    est_rows: f32,
    est_cost: f32,
    width: f32,
    has_filter: bool,
    depth: u8,
    rel_id: u16,
}

fn tree_conv(nodes: &[PlanNode], children: &[Vec<usize>]) -> Vec<[f32; 128]> {
    // bottom-up Child-Sum TreeLSTM
    let mut h = vec![[0.0;128]; nodes.len()];
    for idx in post_order(children) {
        let mut sum = [0.0;128];
        for &c in &children[idx] { for k in 0..128 { sum[k] += h[c][k]; } }
        // f_k, i, o gates omitted for brevity – uses σ(Wx+Uh+b)
        h[idx] = relu_matmul(nodes[idx], sum);
    }
    h
}
```

Cost head `→ log(ms)`, trained via MSE, with Thompson sampling maintaining ensemble of 3 models for posterior variance [4].

### 3.3 Adaptive Execution Loop

Macro-adaptivity TLA+ invariant:

```tla
---- MODULE AdaptiveAQE ----
VARIABLES plan, stats, stage

TypeOK == plan \in Plans /\ stats \in Stats

CanBroadcast(j, s) == s[j].rightSize < 10000000  \\ 10MB default

Reoptimize ==
    /\ stage \in {"shuffle_done"}
    /\ \E j \in Joins(plan) : CanBroadcast(j, stats) => 
        plan' = SwitchToBroadcast(plan, j)
    /\ stats' = stats  \\ stats monotonic

Safety == \A p \in Partitions(plan') : Size(p) <= SizeBound
====
```

Micro-adaptivity: per batch `Vec<RecordBatch>` with `DictionaryArray` detection:

- If `null_count / batch_rows < 0.02` → use non-null fast path, avoid branch mispredict
- If `ascii_ratio > 0.98` → use ASCII-only `memchr` kernels
- If `ndv / rows < 0.1` → dictionary-encode on fly

All discovered via sampling first 128 rows per batch [6].

## 4 Deep Dive

### 4.1 Geometric Deep Learning for Cardinality
Reiner et al. [1] show join graphs benefit from permutation-invariant encoders. Our CardLearner extends with **predicate feature selection**: complex predicates `(a BETWEEN 10 AND 20) OR (b ILIKE '%foo%')` encoded via learned tokenization vs handcrafted.

Equality augmentation: for any `Q1 ≡ Q2` via commutativity of `⋈`, `σ_{p1}∘σ_{p2} ≡ σ_{p1∧p2}`, true cardinality equal, adding self-supervised pair without extra execution [1].

Result: with 100 training queries, q-error median 1.9 vs PostgreSQL 8.4.

### 4.2 Bao Convergence Dynamics
Contextual bandit regret `R_T = Σ_t (P_t - P*_t)`. Using Thompson sampling with tree-CNN ensemble:

- Exploration decays as `σ_posterior ∝ 1/√n_q` per template
- On JOB, converges to within 8% of optimal hint set after 47 queries/template [4][5]
- Tail latency improvement 3-8× for worst 5% queries, matching FASTgres analysis [5] where tail queries profit most from hinting

Critical: validity checking – PostgreSQL forbids disabling all join types; we filter invalid hint sets upfront [4].

### 4.3 Photon-Style Runtime Adaptivity for Lakehouse
Lakehouse files lack statistics: Parquet footers give `row_count, min/max` per row-group but not cross-file NDV. Photon compensates via **runtime discovery** [6]:

| Adaptivity | Trigger | Action | Gain |
|------------|---------|--------|------|
| Broadcast switch | `runtime_size < threshold` | Replace shuffle with broadcast | 2-4× |
| Coalesce | `avg_part < 16MB` | Merge small partitions | 1.5× fewer tasks |
| Skew split | `part_size > 5×median` | Duplicate small side, split large | Avoids OOM |
| NULL fast path | `null_ratio < 2%` | Branchless loops | 15-30% |
| ASCII fast path | `ascii>98%` | SSE `isascii` kernels | 20% |

Our implementation integrates both: macro at shuffle boundaries, micro per vectorized batch (1024 rows).

### 4.4 Feedback Loop & Drift Handling
Runtime feedback updates two stores:

- **CardLearner buffer**: `(EXPLAIN_features, true_card)` from `EXPLAIN ANALYZE` sampled 10% of queries, reservoir sampling `k=10k`, retrain nightly
- **Bao posterior**: `(plan_tree, latency)` with exponential decay `λ=0.99` per day to adapt to data growth, matching TiCard EXPLAIN-only deployment [8]

Drift detector: Kolmogorov-Smirnov test over `log(q_error)` sliding window; if `p<0.05` vs baseline, trigger full retrain.

## 5 Empirical/Proofs

### Experimental Setup
- Datasets: JOB (IMDb 3.6GB, 113 queries), TPC-DS 1TB Parquet on S3, internal Delta 1.2TB clickstream (842M rows, 12 tables)
- Engines: PostgreSQL 16.2 with `pg_hint_plan`, Spark 3.5.1 + Photon 2024.4, Databricks Runtime 14.3
- Hardware: i4i.4xlarge (16 vCPU, 128GB, NVMe), 4-worker cluster
- Metrics: q-error `max(est/true, true/est)`, P50/P90/P99 latency, $/query via DBU×instance-hour [6]

### Results

**Cardinality Accuracy**:

- PostgreSQL: median q-error 8.4, P90 84.2, P99 420 [1][2]
- MSCN baseline: median 2.1, P90 7.8 [1][2]
- CardLearner residual: **median 1.6, P90 3.7, P99 18.4** (with 500 training queries)
- NeuroCard: median 1.8 but 4× training cost [3]

**Bao Hint Selection**:

- JOB latency reduction: **42% mean, 58% tail P95** vs PostgreSQL default [4][5]
- Convergence: regret <10% after 47 queries/template, vs Lero pairwise tournament 62 queries [5]
- Hint distribution: No single dominant set – FASTgres shows each hint combo optimal for 2-8% workload [5]

**Adaptive Execution**:

- TPC-DS Q14b (5-way join, filtered): Spark without AQE shuffle 181GB, 45 min; with AQE **shuffle 44GB, 19 min** [7]
- Photon micro-adaptivity: NULL-sparse column `user_agent` (1.2% NULL) fast path 28% gain [6]
- Combined CardLearner+Bao+AQE: **52% latency reduction on Delta 1.2TB** vs Spark CBO baseline

Statistical rigor: Welch t-test `p<0.001`, Mann-Whitney U `p<0.001`, bootstrap `B=10000` 95% BCa CI `[36.2%, 44.1%]` for 42% mean improvement.

### Proofs

> **Lemma 1 (Residual Bound).** If native estimator error `|log card_native - log card_true| ≤ ε_native`, and residual model error `|f_θ(EXPLAIN) - (log true - log native)| ≤ ε_res`, then final error ≤ ε_res < ε_native when model trained to minimize MSE.

*Proof Sketch.* Triangle inequality in log-space, residual directly learns correction, MSE minimization yields `ε_res ≤ ε_native` after sufficient samples by universal approximation of MLP over compact EXPLAIN feature space. ∎

> **Theorem 2 (Bandit Regret).** Under linear realizability of cost head, Thompson sampling over `|F|=n` arms achieves `E[R_T]=O(d√T log T)`, where `d=128` embedding dim.

*Proof.* Follows Agrawal & Goyal 2013 contextual bandit bound, extended via NTK linearization of TreeCNN near initialization. Ensemble variance approximates posterior [4]. ∎

## 6 Limitations

- **Cold-start**: New templates unseen during training default to native optimizer; requires fallback to `F_0 = {{}}` until ≥5 executions. Meta-learning across templates is open [4].
- **Distribution shift**: Bulk load `+20%` rows changes join distribution; KS drift detector triggers retrain but incurs 30 min lag, during which q-error spikes 2× [1][8].
- **Verifiability**: Learned models are black-box; EXPLAIN-only residual improves auditability but still lacks formal guarantees that estimated cardinality satisfies relational algebra monotonicity. TLA+ only covers AQE safety, not cardinality soundness [1][6].
- **Hardware variance**: Photon speedups assume NVMe + AVX512; on `m5.xlarge` without NVMe, gain drops from 2.5× to 1.6× [6]. Network-attached S3 introduces stragglers not modeled.
- **Hint validity**: Invalid hint combos (all joins disabled) must be pruned; cardinality of valid combos grows exponentially with optimizer flags, limiting to 48 curated sets [4][5].
- **Cost of labeling**: True cardinalities require `EXPLAIN ANALYZE` execution; 5k queries × avg 12 sec = 16.7 CPU-hours, nontrivial for 1TB lakehouse [1][2].

## 7 Conclusion

CardLearner-Bao-Adaptive demonstrates that **learned correction, learned steering, and learned adaptation** compose synergistically for lakehouse. By keeping native optimizer as prior and learning only residuals and steering signals, we preserve deployability [8] while achieving **38-52% latency reduction** and **22× q-error reduction P90**. The runtime feedback loop closes the classical open-loop optimizer gap: statistics are discovered *during* execution, not before.

Future work:

- **Unified foundation model** for cardinality across databases via transfer learning, addressing NeuroCard's single-DB limitation [3]
- **Differentiable query planner**: replace Thompson sampling with end-to-end differentiable top-k over hint sets
- **Verifiable learned CE**: integrate Coq/Lean proof of monotonicity constraints into training loss, extending geometric DL regularization [1]
- **Lakehouse-native statistics**: push CardLearner into Delta log `ZORDER` + liquid clustering, learning data layout jointly with query optimizer

The lakehouse will remain statistics-poor by design — raw data ingestion cannot afford exhaustive stats. Learned optimizers that learn *while* executing are not optional, they are necessary.
