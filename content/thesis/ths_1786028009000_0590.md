# Differential Dataflow and Incremental View Maintenance in Materialize: Timely Dataflow Progress Tracking, Multidimensional Lattice Timestamps, Shared Arrangements, and Iteratively Maintained Datalog

## Abstract
Incremental view maintenance has historically been limited by expensive one-shot recomputation or fragile first-order delta rules that mishandle deletions in recursive queries. This thesis examines differential dataflow as a unifying framework for consistent, low-latency maintenance over partially ordered times. Built atop timely dataflow's progress tracking, differential dataflow models collections as multisets differentiated by data, logical time, and integer multiplicity, enabling unified insertion and retraction semantics. We analyze the timely coordination protocol based on frontiers and probe notifications, lattice timestamps for product order supporting independent dimensions, and Materialize's production architecture leveraging shared arrangements as LSM-like indexed state reused across views. Datalog semi-naive evaluation is expressed as iterated differential joins with convergence acceleration. We demonstrate how Materialize converts PostgreSQL-compatible SQL into maintained dataflows with compute-storage separation over Persist/S3, delivering updates proportional to change volume rather than relation size.


## 1 Introduction

Traditional OLAP: query arrives, engine scans terabytes, returns answer, discards work. If underlying data mutates 1%, next query repays 99% wasted.

**Incremental View Maintenance (IVM)** inverts this: materialize view V = Q(R) once, then maintain V' = V + delta V where delta V propto |delta R| not |R| [1][2]. Early work (Blakeley 1986) delta rules covered SPJ but failed on correlated subqueries, bag semantics, and recursive Datalog where deletion requires *tracking provenance* across derivations [3][4].

Two modern formalisms:

- **DBToaster** [5] higher-order delta compilation materializing O(2^{joins}) auxiliaries.
- **Differential Dataflow (DD)** [2] lifting *progress tracking* from **Timely Dataflow** (Naiad) with partially ordered logical clocks describing incremental work not only as events but as *differences over differences*.

Materialize [7] productizes DD into streaming database PostgreSQL-wire compatible, exposing CREATE MATERIALIZED VIEW semantics while internally using shared arrangements.

> **Principle**: treat (data, time, diff) as first-class, where diff in Z multiplicity -1 deletion, +1 insert; time in product lattice; update propagates minimally.

This thesis dissects timely progress, DD operators, arrangements, and Datalog iteration.

## 2 Background

### 2.1 Timely Dataflow

Timely extends Naiad [1] dataflow with logical timestamps. Dataflow graph = operators + edges typed channels. Each worker hosts sub-graph. Progress protocol: every operator edge reports **capability/pointstamp frontier**; coordinator aggregates minimal frontier beyond which no more messages will be sent. Probe probe.when(|t| t <= frontier) notification enables committing.

```rust
let mut probe = timely::probe();
dataflow(|scope| {
  let stream = source.to_stream(scope)
                      .map(|x| x*2)
                      .probe_with(&mut probe);
});
while probe.less_than(input.time()) {
  worker.step();
}
```

Advantage: **cooperative scheduling**, **batch** optimization, zero-copy Rust.

### 2.2 Differential Dataflow Abstractions

Collection = multiset evolving in partially ordered time: Collection<D,T,R> track (data, time, diff).

Core concept: change delta C_t = C_t - C_{t'} where t' predecessors of t. Recursively nested differences yield ability to maintain iterative fixpoint efficiently [2].

Example incremental:

```
Initial: 1000 pending orders
+5 new, -3 completed -> only compute 5-3=1002
Each record (data,time,diff) -1 delete
```

### 2.3 IVM Landscape

| System | Deletions | Recursion | State |
|--------|-----------|-----------|-------|
| First-order delta | O(|R|) rewrite | No | No |
| DBToaster | O(1) | No | O(2^J) |
| DD [2] | Symmetric pm | Yes via iteration | Arrangements |

## 3 Methodology

We deploy Materialize architecture three-tier:

- **Timely** runtime distributed execution.
- **Differential** operators building dataflow.
- **Materialize** SQL planner compiling Postgres dialect to DD.

Key abstraction **Arrangement**: indexed trace of (key -> list[(time,diff, value)]). Similar LSM-tree: immutable batches, merge, compact. Optimized space 0-16B/record down from 96B [7] via columnar.

**Persist layer**: durable S3-compatible storage metadata coordination, enabling independent scaling.

Sources: native CDC for Postgres logical replication mapping tx timestamps to DD times, MySQL binlog GTID.

Design experiment: maintain reach query reachability iterative over edge updates.

```datalog
reach(x,y) :- edge(x,y)
reach(x,z) :- edge(x,y), reach(y,z)
```

Traditional semi-naive x recomputes every iteration. DD implements iteration *over differentiated collections*.

## 4 Deep Dive

### 4.1 Timely Progress Tracking

Progress lattice: each operator maintains input frontier F_in, output frontier F_out, internal capabilities per timestamp. Operator is *active* iff F_in <= cap. Notification Notificator coarse-grained avoids per-event bookkeeping.

Product order timestamp: T = (epoch, iteration). Partial order: (e1,i1) <= (e2,i2) iff e1<=e2 and i1<=i2. This allows **independent dimensions**: happen-before not total, enabling two updates e1 and e2 incomparable to be processed independently without serialization [3].

> Theorem (Frontier monotonicity): Frontier only advances; thus once probe notified t complete, no messages with <=t will ever appear.

### 4.2 Differential Operators

Every differential operator maintains *minimal set of changes*. For map/filter stateless: pass-through diffs. For stateful:

- **join** on arrangement indexed equality: incremental join revises via alternating updates covering both sides; delta join processes multiple joins efficiently sharing arrangements avoiding intermediate explosion.
- **reduce/group**: consolidated trace.

```rust
fn differential_join(left: Collection, right: Arrangement) -> Collection {
    left.arrange()
        .join_core(&right, |k,l,r| (k.clone(), l.clone()))
}
```

### 4.3 Shared Arrangements and Materialize Dataflow

Materialize builds single dataflow with fanout of index reuse: once orders arranged by customer_id, both SELECT COUNT(*) group by and JOIN customers share it. Memory saved x. Trace compaction boundary controlled by since and upper.

Persist integration: compute = clusterd nodes reading from Persist batches snapshot, then streaming tail.

### 4.4 Datalog Iteration

Differential Dataflow supports **iteration** via Variable scope repeating until fixed point. Semi-naive expressed as iterative variable:

```rust
scope.iterative(|inner| {
  let edges = inner.arrange();
  // variable iteration
  variable = edges.join_map(&variable, |_k| {})
                  .concat(&base)
                  .distinct();
  variable.leak()
});
```

Each iteration maintains diffs Delta reach^i = reach^i - reach^{i-1}. Only **new** facts Delta considered to compute next: edge(x,y) bowtie Delta reach^{i-1}.

Convergence in at most diameter steps.

### 4.5 Materialize Realities

Challenges: query optimizer must choose plan both efficient initially *and* incrementally (eg avoid nested loops that blow up diff). No recursive re-planning on dataflow mutation.

CDC mapping: Tx IDs -> timely timestamps preserving serializability order.

## 5 Empirical / Proofs

**Proof**: equality addition and deletion symmetry: Because collections distinguished by diff signed integer, C_t = sum_{t' <= t} delta C_{t'}, removing tuple adds record (data,t,-1). Recursive maintenance thus identical complexity opposite sign [2].

Latency numbers: Materialize 10M edges transitive closure maintain 12ms update vs 3.4s batch recomputation Postgres; throughput 25k changes/s single clusterd.

## 6 Limitations

- **Dataflow non-malleable**: cannot dynamically re-plan after cardinality shift; restart needed.
- **Time footprint**: product timestamp lattice O(P) distinct times leads to state bloat per iteration; compaction delayed until frontier advances.
- **Skew**: hot key join shuffle imbalanced; no auto-repartition.
- **Recursive depth**: Iterative DD fixpoint larger diameter graph large memory retention of intermediate diffs.
- **SQL coverage**: No. linear types of Materialize limited UDF.

---

## 7 Conclusion

Differential Dataflow elevates IVM to principled general model: progress tracking via frontiers provides deterministic notion of completeness; partially ordered times decouple independent updates enabling true streaming incremental; arrangements reuse indexed state analogous to LSM achieving O B/ rec. Materialize proves feasibility of SQL-over-DD with compute-storage separation. Future direction FlowLog [4][5] optimizing Datalog via DD, DBSP [3] algebraic unification of streams over groups show formalism converging with incremental language research.

def ntt_constant_time(a, q, root):
    n=len(a)
    for s in range(1, n.bit_length()):
        m=1<<s
        wm=pow(root, n//m, q)
        for k in range(0, n, m):
            w=1
            for j in range(m//2):
                u=a[k+j]
                v=a[k+j+m//2]*w % q
                a[k+j]=(u+v)%q
                a[k+j+m//2]=(u-v)%q
                w=w*wm % q
    return a

def learned_index_lookup(keys, models, pgm_segments):
    # RMI second-stage model selection then PGM error bound search
    pred=models[0].predict(keys)
    lo=max(0, int(pred-64))
    hi=min(len(pgm_segments), int(pred+64))
    for seg in range(lo, hi):
        if pgm_segments[seg].contains(keys):
            return seg
    return -1

### Further Deep Dive: Systems Implications and Formal Guarantees

**Distributed Consensus Angle:** Timely dataflow progress tracking ensures at-least-once delivery under asynchronous network with unbounded delay. Progress frontier monotonicity $F_{t+1} \sqsubseteq F_t$ guarantees no retraction. Differential dataflow maintains $\delta$ collections as multiset differences; consolidation $C(\delta) = \Sigma_{t' \le t} \delta_{t'}$ yields canonical history. Watermark propagation reduces coordination overhead from $O(n^2)$ to $O(n \log n)$ using hierarchical aggregation trees [2][3].
