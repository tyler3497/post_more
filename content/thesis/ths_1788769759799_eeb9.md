# SIMD-Accelerated JSON Parsing with simdjson: Two-Stage Structural Indexing, Carryless Character Classification, and the On-Demand Front End

## Abstract

The simdjson library demonstrates that JSON parsing — long considered an irreducibly serial, branch-heavy workload — can be restructured around *Single Instruction, Multiple Data* (SIMD) parallelism to exceed one gigabyte per second of throughput on a single commodity core [1]. This thesis dissects the three ideas that make this possible: (i) a **two-stage architecture** that separates branchless SIMD *structural indexing* from a scalar *tape-building* pass over a compact index of structural characters; (ii) **carryless character classification**, in which 64-byte blocks are classified with nibble-shuffle lookup tables and quoted regions are recovered via carryless multiplication (`PCLMULQDQ`), eliminating data-dependent branches from string-boundary detection; and (iii) the **On-Demand front end**, a lazy, forward-only iterator that exposes a DOM-like API while materializing values only as they are consumed [2]. We present the algorithms in detail, derive their cost models, survey the UTF-8 validation co-design [3] and the SIMD-parsing ecosystem it inspired, and report representative empirical results. We conclude with an honest account of the approach's limitations: mandatory UTF-8 validation cost, fixed-width index memory overhead, forward-only iteration constraints, and portability boundaries of the intrinsic-heavy design.

## 1 Introduction

JavaScript Object Notation (JSON) is the dominant data-interchange format of the web, and ingesting JSON documents is a well-documented performance bottleneck in databases, search engines, and API gateways [1]. Conventional parsers — *RapidJSON*, *sajson*, and their descendants — are written as recursive-descent or state-machine scanners that inspect the input one byte at a time, branching on every character class. Such designs are simple and portable, but they leave the wide vector units of modern processors almost entirely idle, retire several instructions per input byte, and suffer frequent branch mispredictions on structural punctuation.

In 2019, Langdale and Lemire introduced **simdjson**, the first standard-compliant JSON parser to sustain gigabytes-per-second throughput on a single core [1]. Its headline results — roughly a fourfold reduction in retired instructions relative to RapidJSON — were achieved not by micro-optimizing a scalar scanner, but by *restructuring the parsing problem itself* into two vectorizable subproblems:

1. **Stage 1 — structural indexing.** The input is scanned in 64-byte blocks with SIMD instructions only. The output is a flat *index* of the positions of *structural characters* (`{`, `}`, `[`, `]`, `:`, `,`, and the opening quotes of strings) together with *pseudo-structural characters* (the first byte of scalars such as numbers, `true`, `false`, `null`). No parsing decisions are made in this stage; it is pure classification.
2. **Stage 2 — tape construction.** A scalar recursive-descent pass walks the compact index (not the raw text) and emits a linear *tape*: an array of 64-bit records describing the document tree. Strings are normalized into a contiguous buffer; numbers are converted with a fast decimal-to-binary path.

A second major contribution, the **On-Demand front end** [2], rethinks the output of stage 1 entirely: instead of materializing the whole tape, a forward-only iterator lazily walks the structural index, validating and converting values only when the user asks for them. This yields a DOM-like programming model with streaming-like cost — an idea subsequently adopted by production systems including the Node.js runtime, Apache Doris, Milvus, and Meta's Velox [2].

This thesis provides a self-contained, PhD-level treatment of these ideas. Section 2 reviews the necessary background on SIMD execution and JSON syntax. Section 3 states the methodology of our analysis. Section 4 is the deep technical core: the two-stage pipeline, the carryless classification machinery, the co-designed UTF-8 validator, and the tape / On-Demand front ends. Section 5 gives empirical results and formal arguments; Section 6 discusses limitations; Section 7 concludes.

## 2 Background

### 2.1 SIMD execution and the memory wall

Modern x86-64 processors expose vector registers of 128, 256, and (on recent server parts) 512 bits, manipulated by SSE, AVX2, and AVX-512 instruction sets. A single `vpcmpeqb` compares 32 bytes against a constant in one instruction; `vpshufb` performs a 16-entry parallel table lookup per byte lane; `pclmulqdq` performs carryless multiplication of 64-bit polynomials. The catch is that SIMD is *data-parallel*: it rewards algorithms that apply the same operation to many independent inputs and punishes data-dependent control flow. Parsing is traditionally the opposite — a cascade of branches on byte values.

The simdjson insight is that the *lexical* layer of JSON parsing — "where are the interesting characters?" — is embarrassingly parallel, while only the *syntactic* layer — "does this index describe a valid document?" — is serial [1]. Splitting the two lets each run on the hardware substrate it suits.

### 2.2 JSON syntax and structural characters

JSON (RFC 8259) has six structural characters — `{`, `}`, `[`, `]`, `:`, `,` — plus strings delimited by `"`, numbers, the literals `true`, `false`, `null`, and insignificant whitespace (` `, `\t`, `\n`, `\r`). simdjson distinguishes **structural characters** from **pseudo-structural characters**: a pseudo-structural character is any non-whitespace byte that is *not* a structural character and *not* inside a string — i.e., the first byte of an atom (`-`, digits, `t`, `f`, `n`) [1]. Stage 2 begins its work at every structural or pseudo-structural position, so stage 1 must enumerate both classes exactly.

### 2.3 Prior art

State-of-the-art scalar parsers at the time of the original work included RapidJSON (SAX and DOM modes) and sajson [1]. Both are branch-heavy: profiling showed RapidJSON retiring on the order of *ten or more instructions per input byte* on typical corpora. simdjson's headline claim is to retire roughly a *quarter* of the instructions of RapidJSON while validating UTF-8 fully — a validation step sajson only partially performed [1].

## 4 Deep Dive

### 4.1 Stage 1: two-stage structural indexing

Stage 1 processes the input in independent 64-byte blocks and produces, for the entire document, a single array of 32-bit (or 64-bit) *indexes* — the positions of all structural and pseudo-structural characters. The design constraints are strict: the stage must be **branchless** (no data-dependent control flow, so the pipeline never stalls on mispredicted structure), and it must touch each input byte a small constant number of times with SIMD instructions.

For each 64-byte block, stage 1 computes four 64-bit masks:

| Mask | Meaning |
|---|---|
| `struct` | positions of structural characters (`{`,`}`,`[`,`]`,`:`,`,`) |
| `quote` | positions of unescaped `"` characters |
| `quoted` | positions of characters *inside* string regions |
| `ws` | positions of whitespace bytes |

The structural-character classification itself is done with a now-classic SIMD idiom: split each byte into low and high nibbles, use `vpshufb` as a 16-entry lookup on the low nibble, and combine with a high-nibble mask. The following sketch captures the essence (simplified from the AVX2 kernel):

```cpp
// Classify 32 bytes against the JSON structural/whitespace sets (AVX2 sketch)
__m256i classify_block(const uint8_t *ptr) {
    __m256i v = _mm256_loadu_si256((const __m256i *)ptr);
    __m256i low  = _mm256_and_si256(v, _mm256_set1_epi8(0x0F));
    // 16-entry nibble table: marks for { } [ ] : , " and ws chars
    __m256i tbl  = _mm256_setr_epi8(
        16,0,0,0, 0,0,0,0, 0,8,10,4, 1,12,0,0,
        16,0,0,0, 0,0,0,0, 0,8,10,4, 1,12,0,0);
    __m256i t0   = _mm256_shuffle_epi8(tbl, low);       // per-byte class bits
    __m256i hi   = _mm256_srli_epi16(v, 4);
    __m256i t1   = _mm256_shuffle_epi8(tbl, hi);        // high-nibble check
    return _mm256_and_si256(t0, t1);                     // structural => nonzero
}
```

The clever part is that each JSON structural character has a *unique low nibble* (`{`=0xB, `}`=0xD, `[`=0xB... ), so a single shuffle plus a high-nibble disambiguation distinguishes the whole structural set and the whitespace set simultaneously, at roughly **one SIMD instruction per classified byte class** [1]. The resulting per-byte marks are collapsed into 64-bit masks with `vpmovmskb`.

From these masks, the final structural index for the block is:

```
structural_or_pseudo = struct_bits | (scalar_starts & ~quoted & ~ws)
```

where `scalar_starts` marks the first byte of atoms, detected by comparing each byte against the *preceding* byte's class (a scalar starts where a non-whitespace, non-structural byte follows whitespace or a structural character). Positions are appended to the index array with a branchless "compress-store" (`tzcnt`/`blsr` loop over set bits, or AVX-512 `vpcompressd`). Because blocks are independent, stage 1 is trivially parallelizable and, in practice, memory-bandwidth bound.

> **Theorem:** Let *I* be the index array emitted by stage 1 for a UTF-8-valid input. Then *I* enumerates, in strictly increasing order, exactly the positions of the document's structural characters and pseudo-structural characters — each exactly once — irrespective of nesting depth or string content. *Proof sketch.* By construction, `quote` excludes escaped quotes (Section 4.2), so `quoted` marks precisely the interior of string literals; no structural character can occur inside `quoted`. The nibble-table classifier is exact on ASCII structural/whitespace sets, and pseudo-structural starts are defined purely on adjacent byte classes outside `quoted`. ∎

### 4.2 Carryless classification of quotes and escapes

The hardest part of stage 1 is determining, without branches, which `"` characters actually delimit strings. A quote preceded by an odd-length run of backslashes (`\"`) is escaped and does *not* delimit a string. simdjson solves this with two bit-parallel tricks.

**Odd backslash runs.** Let `bs` be the 64-bit mask of backslash positions in a block. A character is escaped iff it is immediately preceded by an odd-length run of backslashes. The runs are resolved branchlessly by shift-XOR folding:

```cpp
// Branchless escaped-character mask from backslash mask (conceptual)
uint64_t bs = backslash_mask(block);
uint64_t odd_starts = bs & ~(bs << 1);          // runs of even length start
uint64_t even_seq = odd_starts ^ (odd_starts << 1);
// fold until stable: propagates run parity across the word
even_seq ^= even_seq << 2; even_seq ^= even_seq << 4;
even_seq ^= even_seq << 8; even_seq ^= even_seq << 16;
even_seq ^= even_seq << 32;
uint64_t escaped = even_seq << 1;               // chars following odd runs
uint64_t quote = quote_mask(block) & ~escaped;  // true delimiters only
```

Cross-block runs are handled by carrying a single 64-bit `prev_escaped`-style state between blocks — the *only* serial dependency in stage 1, and a negligible one [1].

**Quoted regions via carryless multiplication.** Given the unescaped `quote` mask, the mask of characters *inside* strings is computed with a single `PCLMULQDQ`:

```cpp
// quoted = characters strictly inside "..." regions (conceptual)
__m128i q  = _mm_set_epi64x(0, quote_bits);
__m128i cl = _mm_clmull_epi64(q, _mm_set1_epi8(0xFF)); // q x all-ones, carryless
uint64_t quoted = (uint64_t)_mm_cvtsi128_si64(cl) ^ quote_bits;
```

Carryless multiplication of the quote bitset by all-ones XORs together every shift of the quote mask — quotes arrive in delimiter pairs, so the XOR of the two shifted ranges cancels outside the pair and leaves the interior set. One instruction replaces what would otherwise be a state machine tracking in-string/out-of-string state across 64 bytes, and it does so with **zero branches and zero data-dependent latency** beyond the multiply itself [1]. This is the paper's most elegant idea: *string-boundary detection as polynomial arithmetic over GF(2)*.

### 4.3 UTF-8 validation in less than one instruction per byte

JSON text must be valid Unicode, and simdjson validates UTF-8 *during* stage 1 rather than as a separate pass. The co-designed validator of Keiser and Lemire [3] processes ASCII runs at 64 bytes per iteration with a handful of SIMD instructions and falls back to a vectorized non-ASCII path only when high-bit bytes are present. The key results:

- **< 1 SIMD instruction per byte** on ASCII-heavy inputs — the validation is effectively free beside classification.
- Error detection covers overlong encodings, surrogates, and truncated sequences, matching the strictness RapidJSON applies [1].
- Because validation shares the block loop with structural indexing, the combined stage 1 remains bandwidth-bound: the CPU's vector units, not its decoders, are the bottleneck.

This co-design matters beyond simdjson: it refutes the folk belief that "validation is the expensive part" by showing that, vectorized, validation can be *cheaper than the branch mispredictions it replaces* [3].

### 4.4 The tape and the On-Demand front end

**The tape (DOM front end).** Stage 2 walks the structural index with a small recursive-descent parser and appends 64-bit *tape records*: type tags for `{`, `}`, `[`, `]`, plus records pointing into a contiguous string buffer (length-prefixed, escape-normalized) and parsed numeric values. The tape is a *linearized* tree — cache-friendly, pointer-free, and iterable without touching the original text. Numbers use a fast path: integers accumulate directly; decimals use a corrected Eisel–Lemire-style decimal-to-binary conversion that is exact for the common case and falls back to a precise routine otherwise [1].

**On-Demand: laziness as an API.** The On-Demand front end [2] keeps stage 1 but replaces eager tape construction with a *forward-only iterator* over the structural index. The programmer writes what looks like DOM navigation:

```cpp
// On-Demand: DOM-like syntax, streaming-like cost (simplified)
ondemand::parser parser;
ondemand::document doc = parser.iterate(json);
for (ondemand::object obj : doc["events"]) {
    std::string_view type = obj["type"].get_string();
    if (type == "push") { total += obj["count"].get_uint64(); }
    // unconsumed fields are skipped with SIMD-accelerated seeking
}
```

Under the hood, `doc["events"]` performs a *key lookup* that scans the index for the matching string without materializing sibling values; `get_uint64()` parses the number at the current position on first access. Skipping unwanted subtrees uses the structural index directly — depth counting over index entries, accelerated by SIMD — so a query touching 1% of a document pays for roughly 1% of the work plus the unavoidable stage-1 scan [2]. The trade-off is fundamental: iteration is *forward-only* (no revisiting), and error reporting is deferred to the point of consumption. In exchange, the paper reports On-Demand outperforming the DOM front end by 2× or more on selective-access benchmarks, and the design has since been adopted by the Node.js runtime, Apache Doris, Milvus, and Velox [2].

## 5 Empirical Results and Formal Arguments

### 5.1 Instruction-count model

The formal argument for simdjson is an *instruction-count* argument, and it is worth stating precisely. Let *n* be the input size in bytes. A scalar parser performs Θ(1) branches per byte and retires *c₁·n* instructions with *c₁* ≈ 8–15 on typical corpora [1]. simdjson's stage 1 retires Θ(*n*/64) vector instructions plus O(*n*/64) scalar fix-up instructions — i.e., *c₂·n* with *c₂* ≈ 1–3 — and stage 2 work is proportional to the number of *values*, not bytes. The measured consequence on Skylake hardware [1]:

| Corpus (jsonexamples) | simdjson (GB/s) | RapidJSON (GB/s) | Approx. speedup |
|---|---|---|---|
| `twitter.json` | ≈ 2.2 | ≈ 0.45 | ≈ 4.9× |
| `canada.json` | ≈ 2.5 | ≈ 0.55 | ≈ 4.5× |
| `citm_catalog.json` | ≈ 2.0 | ≈ 0.40 | ≈ 5.0× |
| `gsoc-2018.json` | ≈ 1.8 | ≈ 0.35 | ≈ 5.1× |

*Representative figures reported in [1]; exact numbers vary with microarchitecture and compiler.* The gap widens on the On-Demand selective-access benchmarks of [2], where skipping dominates.

### 5.2 Benchmark harness (reproducible pattern)

The standard measurement pattern, adapted from the simdjson benchmark suite [4], isolates parsing from I/O and reports the best of several runs:

```cpp
// Reproducible throughput harness (pattern after simdjson/benchmark [4])
#include "simdjson.h"
#include <chrono>
static double bench(std::string_view json, int iters = 200) {
    simdjson::dom::parser parser;
    auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < iters; i++) {
        simdjson::dom::element doc;
        if (parser.parse(json.data(), json.size()).get(doc)) return -1;
        volatile size_t n = doc["data"].get_array().size(); (void)n;
    }
    auto dt = std::chrono::steady_clock::now() - t0;
    double sec = std::chrono::duration<double>(dt).count();
    return (json.size() * iters / 1e9) / sec;   // GB/s
}
```

### 5.3 Why the speedup is structural, not incidental

Three properties make the advantage robust rather than benchmark-specific [1][2]:

1. **Branch elimination is algorithmic.** Stage 1 has no data-dependent branches by construction; branch-miss penalties — the dominant scalar-parser cost on irregular JSON — vanish rather than shrink.
2. **Work scales with structure, not bytes.** Stage 2 iterates over the *index* (size proportional to value count); whitespace-heavy or deeply-indented documents cost barely more than minified ones.
3. **Validation is amortized.** UTF-8 checking [3] rides the same block loop as classification, so the "validating parser" tax that slows scalar competitors disappears.

The ecosystem response corroborates the analysis: ByteDance's **sonic-cpp** independently adopted SIMD whitespace-skipping, SIMD escape scanning, and even a ParseOnDemand mode with SIMD-accelerated skipping [5], converging on the same design vocabulary from a different starting point.

## 6 Limitations

No serious treatment is complete without the debits column.

1. **Mandatory UTF-8 validation.** simdjson always validates UTF-8 [1][3]; workloads with pre-validated or trusted input (sonic-cpp explicitly skips verification by default [5]) pay for safety they may not need. There is no "trust me" mode in the classic API.
2. **Index memory overhead.** Stage 1 emits one index entry per structural character — for punctuation-dense documents this is a nontrivial auxiliary array (tens of percent of input size), with attendant allocation and cache pressure. The DOM tape adds its own copy of every string.
3. **Forward-only On-Demand iteration.** The lazy front end cannot revisit consumed values and defers error detection [2]; programs needing random access must either buffer results themselves or pay for the full DOM tape.
4. **Number-parsing edge cases.** The fast decimal path handles the overwhelmingly common cases exactly, but adversarial inputs (very long digit strings, extreme exponents) fall back to slower precise conversion — a deliberate, documented trade-off [1].
5. **Portability and maintenance burden.** The kernels are hand-written per instruction set (SSE4, AVX2, NEON, POWER, with AVX-512 variants); each new architecture is a porting project, and the bit-twiddling tricks in Section 4.2 are famously hard to review. Compiler auto-vectorization achieves none of this — the parallelism had to be designed in.
6. **Adversarial depth.** Deeply nested documents stress the recursive-descent stage 2 (bounded in practice by a depth limit, but the limit is a policy choice, not a theorem).

---

## 7 Conclusion

simdjson's enduring contribution is not a faster loop but a *re factorization of parsing into a parallelizable lexical stage and a serial syntactic stage* [1]. Carryless multiplication turns string-boundary detection into polynomial arithmetic; nibble-shuffle tables turn character classification into table lookup; the structural index turns syntax checking into a walk over a compact integer array; and the On-Demand front end turns the whole pipeline lazy, so programs pay only for the values they touch [2]. The co-designed UTF-8 validator [3] removes the last scalar tax, and independent reimplementations such as sonic-cpp [5] confirm that the design vocabulary — SIMD classification, structural indexes, on-demand skipping — generalizes beyond one codebase.

For the student of high-performance text processing, the lesson is methodological: *find the parallel subproblem hiding inside the serial one, and let the hardware do what it is good at*. JSON parsing looked irreducibly branchy until someone measured which branches were load-bearing. Few of them were.
