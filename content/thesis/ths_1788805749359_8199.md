# Vector-Length-Agnostic Acceleration of Machine-Learning Kernels on the RISC-V Vector Extension (RVV 1.0): LMUL Register Grouping, Masked Predication, Segmented Memory Operations, and VPlan-Driven Auto-Vectorization in LLVM 19

## Abstract

The RISC-V Vector Extension (RVV 1.0), ratified in late 2021, departs from fixed-width SIMD by making vector length an implementation parameter (VLEN), so a single binary runs unchanged across implementations from 128-bit embedded lanes to multi-kilobit HPC arrays [1]. This thesis gives a rigorous account of how RVV 1.0 accelerates machine-learning kernels. We formalize the LMUL register-grouping algebra that lets LMUL in {1/8, 1/4, 1/2, 1, 2, 4, 8} fuse consecutive vector registers into logical operands, analyze the *v0.t* masked-predication model with tail-agnostic and mask-agnostic policies, and show how segmented loads (`vlseg`) transpose array-of-structures data in hardware. We then dissect LLVM 19's auto-vectorizer: its VPlan infrastructure models candidate vectorizations as hierarchical plans of recipes, costs them against scalable-vector cost models, and materializes the winner for RVV's `vscale`-parameterized types [4][5][9]. Mapping GEMM, softmax, and quantized dot-product kernels onto these primitives, we derive register-tile sizing laws, prove strip-mining loop correctness, and report published Ara2 silicon results (37.8 DP-GFLOPS/W, 95% FPU utilization) as empirical ground truth [2].

## 1. Introduction

Single-instruction multiple-data (SIMD) execution is the workhorse of dense machine-learning kernels, yet classical SIMD ISAs — Intel AVX-512, Arm NEON — bind software to a *fixed* register width. A kernel tuned for 512-bit registers underutilizes 128-bit hardware and must be rewritten, re-tuned, or re-compiled for every new width. The RISC-V Vector Extension (RVV 1.0) breaks this coupling through **vector-length agnosticism**: the ISA exposes 32 architectural vector registers `v0`–`v31`, each `VLEN` bits wide, where `VLEN` is an implementation-defined power of two, and software discovers the usable element count at run time via the `vsetvli` instruction [1]. The same binary executes correctly on a 128-bit embedded core and a 4096-bit-class HPC lane array, with performance scaling automatically.

This flexibility is not free. It demands a programming model in which the *active vector length* `vl`, the *selected element width* `SEW`, the *length multiplier* `LMUL`, and the *mask/tail policies* are first-class, dynamically configured state. For ML kernels — matrix multiplication, softmax normalization, quantized dot products — the payoff is substantial: register grouping via `LMUL` exposes outer-product micro-kernels with dozens of accumulator registers; masked predication handles ragged sequence lengths in attention without scalar epilogues; segmented loads de-interleave multi-channel feature maps in a single instruction; and LLVM's VPlan-based auto-vectorizer increasingly generates such code without hand-written intrinsics [4][5].

**Contributions.** This thesis makes four:

1. A formal treatment of the LMUL register-grouping algebra (§4.1), including fractional LMUL and its interaction with register-file pressure in GEMM tiles.
2. A precise semantics of masked predication with *v0.t* masks and tail/mask-agnostic policies, with a correctness theorem for masked accumulation (§4.2).
3. A characterization of segmented load/store as a hardware AoS→SoA transpose, with a worked RGB/depth-to-planar example (§4.3).
4. An analysis of LLVM 19's VPlan auto-vectorization pipeline for RVV, from scalar IR through recipe-based plans to scalable-vector code generation (§4.4), plus a proof of strip-mining correctness and published Ara2 silicon measurements as empirical validation (§5).

## 2. Background

### 2.1 The RVV 1.0 architectural state

RVV 1.0 adds 32 vector registers and a small set of control registers to the RISC-V integer base [1]. The key dynamic state is:

| State | Register / CSR | Meaning |
|---|---|---|
| `VLEN` | *implementation parameter* | Bits per vector register (power of two) |
| `SEW` | `vtype.vsew` | Selected element width: 8, 16, 32, or 64 bits |
| `LMUL` | `vtype.vlmul` | Length multiplier: 1/8, 1/4, 1/2, 1, 2, 4, 8 |
| `vl` | `vl` CSR | Active vector length (elements) |
| `vta` / `vma` | `vtype` bits | Tail-agnostic / mask-agnostic policies |
| `vill` | `vtype[XLEN-1]` | Illegal-configuration trap bit |

The `vtype` register packs these fields: `vsew[2:0]` in bits 5:3, `vlmul[2:0]` in bits 2:0 (with encodings `000`=m1, `001`=m2, `010`=m4, `011`=m8, `101`=mf8, `110`=mf4, `111`=mf2, `100` reserved), `vta` in bit 6, `vma` in bit 7, and the illegal bit `vill` in the most significant bit [1]. Any `vsetvli`/`vsetivli`/`vsetvl` that requests an unsupported combination sets `vill` and zeroes `vl`, giving software a portable capability-probing mechanism.

The **maximum usable vector length** for a configuration is:

$$\mathrm{VLMAX} = \frac{\mathrm{LMUL} \times \mathrm{VLEN}}{\mathrm{SEW}}$$

and `vsetvli rd, rs1, vtypei` sets `vl = min(rs1, VLMAX)`, returning the granted length in `rd`. This single instruction is the fulcrum of vector-length-agnostic programming: every vector loop is a *strip-mining* loop that asks the hardware how many elements it can process per iteration [1][3].

### 2.2 The SiFive/LLVM intrinsic ecosystem

The RVV C intrinsic API (`riscv_vector.h`), co-developed by SiFive and the Barcelona Supercomputing Center against the 1.0 draft, exposes one intrinsic per machine instruction — e.g. `__riscv_vle32_v_i32m1`, `__riscv_vfmacc_vv_f32m4` — with LMUL encoded in the type suffix [6]. LLVM's RVV backend consumes these intrinsics directly and, increasingly, generates equivalent code from scalar C via auto-vectorization (§4.4). OpenCV's `riscv-rvv` HAL demonstrates production use: length-agnostic universal intrinsics dispatch the same source to RVV 1.0 hardware such as the 256-bit SpacemiT K1 [7].

### 2.3 Prior vector processors: Ara and Ara2

The PULP Platform's **Ara** (2019) was an early open-source RVV (draft 0.5) vector unit coupled to the Ariane RV64GC core, targeting 2 bytes of memory bandwidth per double-precision FLOP and demonstrating roofline-bound performance once the application vector length exceeded a few multiples of the lane count [3]. **Ara2** (2023) is, to the best of the authors' knowledge, the first fully open-source processor compliant with the frozen RVV 1.0 ISA, implemented in 22 nm FD-SOI across 2–16 lanes, reaching 1.35 GHz and 37.8 DP-GFLOPS/W with 95% average functional-unit utilization on compute-intensive kernels [2]. Its successor **AraXL** scales the same lineage to 64 lanes and 8192 double-precision elements per vector using a hierarchical pipelined interconnect [8]. These designs provide the empirical anchor for §5.

## 3. Methodology

Our method is threefold. **First**, we formalize: each RVV mechanism is reduced to an algebraic or operational semantics from which we derive theorems about loop correctness and register capacity. **Second**, we construct: for each of three canonical ML kernels — SGEMM micro-kernel, softmax, and INT8 dot product — we give the strip-mined intrinsic or assembly form and derive a tile-sizing law from the LMUL algebra. **Third**, we validate: we cite published post-silicon measurements from Ara2/AraXL [2][8] rather than fabricating microbenchmarks, and we trace the LLVM 19 compilation pipeline that a compiler engineer would observe with `-Rpass=loop-vectorize` and VPlan dumps [4][5][9].

We assume the ratified RVV 1.0 ISA [1] and the `riscv_vector.h` intrinsic naming [6].

## 4. Deep Dive

### 4.1 LMUL Register Grouping: The Register-File Algebra of RVV

Classical SIMD gives the programmer one register width; RVV gives a *register-grouping operator*. Setting `LMUL = m` fuses `m` consecutive architectural registers into one logical operand: with `LMUL=m8`, registers `v0`–`v7` (say) behave as a single 8·VLEN-bit operand, and the register specifier must be a multiple of the group size. Fractional LMUL (`mf2`, `mf4`, `mf8`) goes the other way, *subdividing* one physical register into 2, 4, or 8 logical operands — a boon for narrow kernels that would otherwise waste register-file capacity [1].

> **Theorem (LMUL capacity law).** For a configuration with element width SEW and multiplier LMUL, the number of elements in one register group is exactly VLMAX = LMUL·VLEN/SEW, and the number of independent logical operands available is 32/max(1, LMUL) for LMUL ≥ 1, or 32·|LMUL|⁻¹ logical sub-registers for fractional LMUL.

*Proof sketch.* Each architectural register holds VLEN/SEW elements at width SEW. A group of LMUL ≥ 1 consecutive registers holds LMUL·VLEN/SEW elements; the spec requires the group head to be LMUL-aligned, partitioning the 32 registers into 32/LMUL groups. For fractional LMUL = 1/k, each physical register yields k independent operands with disjoint element ranges, giving 32k logical operands; the EMUL (effective LMUL) of any widening operation must still satisfy EMUL ≤ 8 [1]. ∎

**Why ML kernels care.** A high-performance GEMM micro-kernel is an outer-product engine: it holds a tile of the accumulator matrix *C* in registers while streaming panels of *A* and *B*. On RVV, the natural tile uses one `m8` accumulator group (8 registers × VLEN/32 single-precision lanes each), giving a register tile of `8·VLEN/32 × 1` per broadcast, or with two `m4` groups, a `2`-wide *B*-panel reuse. The widening fused multiply-accumulate `vwmacc.vv` even permits INT8×INT8→INT32 accumulation within a single group, with EMUL accounting keeping the widened destination legal [1][6].

```c
#include <riscv_vector.h>
// SAXPY micro-kernel: y[i] = a*x[i] + y[i], vector-length agnostic
void saxpy(float a, const float *x, float *y, size_t n) {
    size_t vl;
    for (size_t i = 0; i < n; i += vl) {
        vl = __riscv_vsetvli(n - i, __riscv_v_u8mf8_unused, 0); // placeholder
        vl = __riscv_vsetvli(n - i, RVV_E32, RVV_M4);           // SEW=32, LMUL=4
        vfloat32m4_t vx = __riscv_vle32_v_f32m4(x + i, vl);
        vfloat32m4_t vy = __riscv_vle32_v_f32m4(y + i, vl);
        vy = __riscv_vfmacc_vf_f32m4(vy, a, vx, vl);            // vy += a * vx
        __riscv_vse32_v_f32m4(y + i, vy, vl);
    }
}
```

The loop asks the hardware for `vl` each iteration — the strip-mining idiom. With `VLEN=256`, `SEW=32`, `LMUL=4`, each iteration retires `vl = min(n−i, 32)` elements using four grouped registers, and the binary is unchanged on `VLEN=1024` hardware where `vl` becomes 128 [1][7].

A crucial subtlety: **LMUL interacts with masking and register allocation**. When `LMUL > 1`, the mask for the group still lives in `v0` (see §4.2), and the compiler's register allocator must respect group alignment — a constraint LLVM's RISC-V backend models with register classes per LMUL. Choosing LMUL is thus a three-way trade: larger groups raise per-instruction work (fewer loop iterations, better amortization of `vsetvli` and branch overhead) but reduce the number of independent operands, increasing spill risk in unrolled kernels.

### 4.2 Masked Predication: *v0.t* and the Agnostic Policies

RVV replaces branchy scalar epilogues with **predicated execution**. The vector register `v0` doubles as the mask register; a masked instruction appends the operand `, v0.t`, e.g.:

```asm
vsetvli t0, a0, e32, m4, ta, ma   # SEW=32, LMUL=4, tail/mask agnostic
vmseq.vi v0, v4, 0                # v0[i] = (v4[i] == 0)  -- build predicate
vadd.vv  v8, v8, v12, v0.t        # v8[i] += v12[i] only where v0[i] set
```

Mask bits are densely packed from bit 0 of `v0`, one bit per element, regardless of SEW [1]. Two policy bits govern what happens to *inactive* elements:

- **Tail policy** (`vta`): elements at indices `≥ vl` are *tail* elements. With `ta` (tail-agnostic), the implementation may overwrite them with 1s; with `tu` (tail-undisturbed), they are preserved.
- **Mask policy** (`vma`): body elements whose mask bit is clear are *masked-off*. With `ma`, they may be overwritten with 1s; with `mu`, preserved.

Setting both agnostic (`ta, ma`) is the performance choice: it frees the microarchitecture from read-modify-write dependences on the destination register, which is precisely what lets chained vector units sustain throughput [2].

> **Theorem (masked accumulation correctness).** Let `P` be a predicate with support `S = {i < vl : v0[i] = 1}` and let the mask policy be mask-undisturbed (`mu`). Then the sequence `vadd.vv vd, vd, vs2, v0.t` computes `vd[i] ← vd[i] + vs2[i]` for `i ∈ S` and `vd[i]` unchanged otherwise, for any tail policy.

*Proof sketch.* By the RVV 1.0 operational semantics, a masked arithmetic instruction applies its body operation exactly to elements whose mask bit is set and whose index is below `vl`; masked-off body elements follow the `vma` policy (here: undisturbed), and tail elements follow `vta` [1]. Induction over the strip-mined loop then yields the full reduction. ∎

For ML, predication shines in **ragged attention**: sequence lengths that are not multiples of VLMAX need no scalar cleanup — the final `vsetvli` naturally produces a short `vl`, and where finer control is needed (e.g. causal masking in softmax), `vmseq`/`vmslt` build data-dependent masks at vector speed. LLVM lowers its target-independent `llvm.vp.*` (vector-predication) intrinsics directly onto masked RVV instructions, so `#pragma clang loop vectorize` on a predicated loop can reach this hardware without intrinsics [4][9].

### 4.3 Segmented Loads and Stores: Hardware AoS→SoA Transposition

ML data is rarely a flat stream. Multi-channel images, RGB-D frames, and complex-valued feature maps arrive as **arrays of structures** (AoS): `RGBRGBRGB…`. Classical SIMD must shuffle this into planar (SoA) form with permute networks. RVV 1.0 instead provides **segmented (structured) memory operations**: `vlseg<NF>e<SEW>.v` loads NFIELDS contiguous *segments* from memory and de-interleaves them into NFIELDS consecutive vector register groups in one instruction; `vsseg` is the inverse [1].

```asm
# De-interleave RGBRGB... into v0=R, v1=G, v2=B  (NFIELDS=3, SEW=8, LMUL=1)
vsetvli t0, a0, e8, m1, ta, ma
vlseg3e8.v v0, (a1)      # v0<-R lane, v1<-G lane, v2<-B lane
```

> **Lemma (segment transpose).** `vlsegNF e.v vd, (rs1)` with NFIELDS = NF and LMUL = m writes `NF·m` consecutive registers starting at the `m`-aligned `vd`, where register `vd + f·m + k` receives memory segment field `f`, sub-register `k`. The total register budget satisfies NF·EMUL ≤ 8.

The constraint NF·EMUL ≤ 8 bounds the register footprint: with 8 fields you must use LMUL ≤ 1; with 2 fields you may use up to m4 [1]. For ML preprocessing — channel separation, complex FFT packing, multi-head attention head splitting — this eliminates entire shuffle prologues.

### 4.4 Auto-Vectorization via VPlan in LLVM 19

Hand-written intrinsics win benchmarks, but the economic argument for RVV rests on **auto-vectorization**: ordinary scalar C compiled well. LLVM's vectorization story was rewritten around **VPlan** (Vectorization Plan), a refactoring proposed by Intel to unify the loop vectorizer and SLP vectorizer in one flexible system [4][5].

A VPlan is a *hierarchical* control-flow graph — `VPBasicBlock`s containing *recipes* — that models a candidate vectorization **without mutating the IR** [4][5]:

1. **Legality & planning.** `LoopVectorize` analyzes the scalar loop (dependence, SCEV trip counts, runtime checks) and builds one or more VPlans: e.g. a *wide* plan (VF=scalable, fully unrolled), a *masked* plan (with `VPBlendRecipe`/`VPPredicatedRecipe` for control flow), and an *outer-loop* plan enabled by the VPlan-native path (`-enable-vplan-native-path`) [9].
2. **Costing.** Each recipe carries a `TargetTransformInfo` cost parameterized by the *vectorization factor*. For RISC-V, the cost model understands **scalable vectors** `<vscale x N x Ty>`: costs are expressed per `vscale` unit, and `vscale_range` (from `-mllvm --riscv-v-vector-bits-min/max` or the `Zve*` extension set) bounds the unknown [5].
3. **Materialization.** The cheapest plan is *executed*: recipes are expanded into vector IR — widened loads (`VPWidenLoadRecipe` → `llvm.masked.load` or RVV `vle`), predicated arithmetic (`llvm.vp.add` → masked `vadd`), and trip-count scaling by `vscale` — which the RISC-V backend then selects to `vsetvli`-based strip-mined machine code.

```
scalar LLVM IR loop ──► VPlan builder ──► {plan_wide, plan_masked, plan_outer}
        (LoopVectorize)      (recipes)            │ cost model (TTI, vscale)
                                                 ▼
                                   best plan ──► vector LLVM IR
                                   (execute)      <vscale x 4 x float>
                                                 ▼
                                   RISC-V backend ──► vsetvli / vle32.v /
                                                     vfmacc.vv / vse32.v
```

For RVV this pipeline has a decisive advantage over fixed-width targets: because `vscale` is left symbolic through most of optimization, **one compilation serves all VLENs** — the vector-length agnosticism of the ISA is mirrored by the length-agnosticism of the compiler's intermediate representation [5]. Practical notes for LLVM 19: RVV auto-vectorization requires `+v` in `-march` (e.g. `-march=rv64gcv`), benefits from `-mllvm -riscv-v-vector-bits-min=128` when the minimum VLEN is known, and its VPlan-native outer-loop path — the key to auto-vectorized GEMM nests — remains under active development behind flags [9].

## 5. Empirical Results and Proofs

### 5.1 Strip-mining correctness (proof)

> **Theorem (strip-mining coverage).** The idiom `for (i = 0; i < n; i += vl) { vl = vsetvli(n − i, SEW, LMUL); body(vl); }` executes `body` over each index `j ∈ [0, n)` exactly once, for any `n ≥ 0` and any legal `(SEW, LMUL)`.

*Proof.* `vsetvli` with AVL = `n − i > 0` grants `vl = min(n − i, VLMAX) ≥ 1` since VLMAX ≥ 1 for all legal configurations [1]. Thus `i` strictly increases and the loop terminates. Iteration `k` covers `[i_k, i_k + vl_k)` with `i_{k+1} = i_k + vl_k`; telescoping gives coverage of `[0, n)` with no overlap. When `n − i < VLMAX` the grant is exact, so the tail is a short vector — no scalar epilogue needed. ∎

This is the formal content of "write once, run at any VLEN": correctness is independent of the implementation's VLEN because `vl` is always granted, never assumed.

### 5.2 Published silicon: Ara2 and AraXL

Rather than synthetic microbenchmarks, we anchor performance claims in published post-implementation results [2][8]:

| Metric (Ara2, 22 nm FD-SOI) | Value | Source |
|---|---|---|
| Clock frequency | 1.35 GHz (critical path ≈ 40 FO4) | [2] |
| Energy efficiency | 37.8 DP-GFLOPS/W @ 0.8 V | [2] |
| FPU utilization (compute kernels) | ≈ 95% average | [2] |
| FPU utilization (AraXL `fmatmul`, 64 lanes) | up to 99% | [8] |
| Multi-core gain (8×2-lane vs 16-lane, 32³ matmul) | > 3× perf, 1.5× efficiency | [2] |

Two findings matter for ML. **First**, utilization saturates near the roofline once the application vector length is a few multiples of the physical lane count — the empirical counterpart of our LMUL capacity law: long logical vectors (large LMUL, or large `n`) amortize front-end and slide-unit overhead [2][3]. **Second**, the scalar core's issue rate bounds short-vector performance, and multi-core vector clusters mitigate it — a quantitative argument for keeping `vl` large via LMUL grouping and loop fusion rather than strip-mining tiny tiles [2].

### 5.3 Analytical model: GEMM tile sizing

Consider an FP32 SGEMM micro-kernel with an `m8` accumulator group on `VLEN=256` hardware: each group holds `8·256/32 = 64` accumulators; with a 4-deep *k*-loop unroll and `vfmacc.vv` (2 FLOP/instr), the kernel issues 64 FMAs per inner iteration = 128 FLOP per `vsetvli` epoch. Arithmetic intensity against the register file is `128 FLOP / (3 vector loads)` ≈ 42 FLOP per memory op — comfortably compute-bound on Ara-class hardware provisioned at 2 B/DP-FLOP [3]. The tile-sizing law follows directly:

$$\text{choose maximal LMUL with } (\text{accumulator groups} + \text{operand groups}) \times \mathrm{LMUL} \le 32$$

reserving `v0` for masks when predication is needed.

## 6. Limitations

**Compiler maturity.** VPlan's RVV cost model is younger than its x86/Arm counterparts; idioms like segmented accesses and widening reductions are reliably reached only via intrinsics today, and outer-loop vectorization still leans on the native path flag [9]. **Masked-off policy hazards.** Tail/mask-agnostic policies permit 1s in inactive elements; any kernel that later *reads* those elements (e.g. a reduction over a masked register without re-masking) must use undisturbed policies or explicit re-predication — a real correctness trap [1]. **LMUL fragmentation.** Group alignment constraints complicate register allocation in unrolled, multi-precision kernels. **Memory system.** Ara2's analysis shows the scalar core and memory system, not the vector datapath, dominate short-vector and bandwidth-bound kernels — vector ISA elegance does not repeal the roofline [2]. **Ecosystem breadth.** Production RVV 1.0 silicon (e.g. SpacemiT K1 at 256-bit [7]) remains narrower than the multi-kilobit designs the ISA scales to, so the longest-vector benefits are still largely demonstrated on research silicon [2][8].

---

## 7. Conclusion

RVV 1.0's contribution is architectural, not merely incremental: by parameterizing vector length and exposing LMUL grouping, masked predication, and segmented memory operations as first-class ISA citizens, it moves the vectorization contract from *compile-time width selection* to *run-time length discovery* [1]. We formalized the LMUL capacity algebra, proved strip-mining and masked-accumulation correctness, showed segmented loads as hardware AoS→SoA transpose, and traced how LLVM 19's VPlan infrastructure turns scalar loops into scalable-vector RVV code through recipe-based planning and costing [4][5][9]. Published Ara2/AraXL silicon — 37.8 DP-GFLOPS/W, ≥95% FPU utilization, near-perfect 64-lane scaling — demonstrates that the model delivers on real hardware [2][8]. The remaining work is in compilers: closing the gap between what VPlan can *model* and what it *profitably selects* for RVV will determine whether vector-length-agnostic ML performance becomes the default rather than the expert's craft.
