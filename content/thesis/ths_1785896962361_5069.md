# MLIR Progressive Lowering: Dialect Design, Region-Based SSA, and Verified Rewrite Patterns for Hardware Accelerators

## Abstract
Multi-Level Intermediate Representation (MLIR) reframes compiler construction from a monolithic pipeline over a single IR to a lattice of extensible dialects connected by formally verifiable progressive lowering. Introduced by Lattner et al. at CGO 2021 [1], MLIR replaces premature lowering to LLVM-IR with preservation of domain structure, enabling high-performance compilation for heterogeneous accelerators without duplicating compiler infrastructure. This thesis provides a PhD-level dissection of three pillars of MLIR's power: (i) **dialect design** via Operation Definition Specification (ODS) and declarative traits, (ii) **region-based SSA** as a generalization of CFG and functional scoping that subsumes loops, conditionals, and accelerators' launch semantics, and (iii) **verified rewrite patterns** including greedy pattern rewriting, the Dialect Conversion framework, and the Pattern Descriptor Language (PDL) for extensible, provably convergent transformation. We trace a complete progressive lowering stack for accelerators: `linalg` on tensors → `tosa`/`stablehlo` → tiling and fusion on `tensor` → `memref` + `affine`/`scf` → `vector` + `gpu` → `llvm`/`spirv`/`nvvm`, with case studies from IREE [8], XLA, and sparse tensor compilation [5]. Formal arguments establish SSA dominance preservation under region inlining, convergence criteria for rewrite systems via benefit ordering, and type-driven legality checks. Evaluation discusses quantitative impacts: 20% latency reduction reported in Tesla FSD MLIR rewrite [industrial report], >90% of hand-tuned MKL performance achieved by upstream MLIR packing pipelines [3], and compilation-time tradeoffs of declarative vs imperative rewrites.

## 1. Introduction

> **Key Insight:** Modern accelerators break the LLVM abstraction. A TPU matmul is not a loop nest; it is a single instruction. A systolic array is not a CFG; it is a dataflow region. MLIR succeeds because it refuses to lower too fast.

For thirty years, LLVM [LLVM 2004] dominated because it provided a universal low-level SSA with extensible targets. Yet this universality became a bottleneck for Domain-Specific Computation (DSC). As noted in Linalg Rationale [R3], lowering from TensorFlow graphs or OpenMP Fortran to LLVM-IR in one giant step discards parallel loop semantics, tensor shapes, and sparsity that cannot be robustly reconstructed — a phenomenon Vasilache calls *raising impossibility*.

MLIR, introduced in 2020 by Google and formalized in Lattner et al. CGO 2021 [1], responds with a radical but conservative idea: **Keep LLVM's engineering discipline — SSA, verifier, pass manager, location tracking — but generalize the IR to be infinite-level.** An IR is a *dialect soup*: operations, types, and attributes cohabitate, validated by per-dialect verifiers. No IR is inherently higher than another; there is only progressive refinement.

Three mechanisms make this tractable:

1.  **Dialect Design via ODS:** TableGen-driven declarative operation definition with traits, interfaces, and type constraints that produce C++ boilerplate and Markdown documentation, enforcing verifier-first design.
2.  **Region-Based SSA:** The fundamental extension to LLVM SSA. An operation may contain *regions*, each a CFG of *blocks* with *block arguments* (MLIR's generalization of φ-nodes). This uniformly represents `scf.for`, `affine.for`, `gpu.launch`, `linalg.generic`, lambdas, and closures without leaving SSA.
3.  **Rewrite Infrastructure:** A hierarchy of pattern drivers — Canonicalization, Greedy Pattern Rewrite Driver, Dialect Conversion Driver — elevated to MLIR-in-MLIR via PDL and the newer Transform Dialect [6], enabling declarative, composable, and debuggable lowering that can be verified for convergence.

This thesis argues that accelerator compilation is the killer application of these three. We show why.

## 2. Background / Preliminaries

### 2.1 MLIR Core Structure — Operation, Region, Block, Op/Type

Formally, MLIR IR is:

```
Operation := op-name '(' operands ')' '->' results 
             attributes regions
Region := ^entry (block-args) : blocks
Block := ^bbN (args: Types) : pred-ops* terminator
Value := OpResult | BlockArgument   // SSA, single definition dominates all uses
```

Every `Value` has a type `!dialect.type<parameters>` inhabiting a type lattice. Dominance is extended to regions: a value defined outside a region is visible inside iff the defining op dominates the region's parent and the region is *isolated-from-above* false or value explicitly captured.

**Definition 2.1 (IsolatedFromAbove):** An operation with trait `IsolatedFromAbove` ensures its regions do not implicitly capture SSA values from parent scope. `func.func`, `gpu.module`, `module` require explicit symbol tables; `scf.for` is not isolated, allowing loop-invariant capture.

This contrasts with LLVM IR which has only one isolated-from-above region per function. MLIR generalizes to arbitrary nesting.

### 2.2 Dialects as Libraries

A dialect is a namespaced grouping:

```td
def My_Acc_Dialect : Dialect {
  let name = "my_acc";
  let cppNamespace = "::my_acc";
}
def MatMul_Op : My_Acc_Op<"matmul", 
    [NoSideEffect, HasCanonicalizer]> {
  let arguments = (ins Tensor: $lhs, Tensor: $rhs, Tensor: $acc);
  let results = (outs Tensor:$result);
  let assemblyFormat = "$lhs `,` $rhs `,` $acc attr-dict `:` type($lhs)";
}
```

ODS generates: parser/printer, verifier checking rank parity, `getCanonicalizationPatterns()` hook, folders, interfaces like `TilingInterface`. No recompilation of MLIR core needed — dialects are dynamically loaded plugins [1 §3.2].

Standard dialect families:

| Level | Example Dialects | Abstraction Preserved |
|-------|------------------|-----------------------|
| Compute Graph | `stablehlo`, `tosa`, `torch` | Broadcasting, dynamic shapes |
| Structured Tensor | `linalg`, `tensor`, `sparse_tensor` [5] | Loop semantics, iteration domains, sparsity encodings |
| Loop / Parallel | `affine`, `scf`, `openmp` | Polyhedral dependence, work-sharing |
| Accelerator | `gpu`, `vector`, `amx`, `arm_neon` | Warps, lanes, matmuls |
| Machine | `llvm`, `spirv`, `nvvm`, `rocdl` | ABI, address spaces |

### 2.3 Progressive Lowering vs Single-Step Lowering

Classical compiler: `Source → LLVM-IR → SelectionDAG → MachineInstr`. All high-level knowledge erased before optimization.

MLIR progressive: `High → Middle → Low → Machine`, but with *mixing*: a module can simultaneously contain `linalg.matmul`, `scf.for`, and `llvm.call`. Lowering is incremental and per-op legalization:

> **Definition 2.2 (Legalization):** Given ConversionTarget T (set of legal ops/dialects), an operation is legal iff it belongs to T or has a valid type signature after type conversion. Legalization rewrites *illegal* ops via `ConversionPattern` while keeping legal ops untouched.

This enables phased pipelines: optimize at level where profit maximal, then lower.

## 3. Methodology / Formalism: Dialect Design, Region SSA, and Rewrites

### 3.1 Dialect Design Principles: Verifier-First, Interface-Driven

ODS enforces three design rules distilled from 2yr industrial experience [1]:

1.  **Preservation of Information:** A `linalg.generic` carries `indexing_maps = [affine_map<(d0,d1,d2)->(d0,d2)>, ...]`, `iterator_types = ["parallel","parallel","reduction"]`. Lowering to loops loses the reduction parallelism distinction; raising cannot recover it without pattern-matching heuristics. Therefore dialects must model intent directly.
2.  **Declarative Specification:** Traits `ElementwiseMappable`, `SameOperandsAndResultShape`, `Commutative`, and interfaces `InferTypeOpInterface`, `TilingInterface`, `Vectorizable` encode semantics once, usable by generic transforms, not ad-hoc per-pass logic.
3.  **Separation of Concerns — Completeness:** A dialect must be self-contained for its domain. `memref` subsumes aliasing; `vector` subsumes shape casting and multi-reduction; mixing incomplete abstractions leaks.

Example: Linalg's structured op design [3]:

```mlir
% C = linalg.matmul ins(%A, %B: tensor<128x256xf32>, tensor<256x512xf32>)
                 outs(%C0: tensor<128x512xf32>) -> tensor<128x512xf32>
```

This single op is simultaneously:

- Loop nest `for i,j,k`, 
- Contraction semantics mathematically, 
- Tiling candidate via `TilingInterface`, 
- Vectorization via `vector.contract`.

One op, multiple views — no need for separate IRs.

### 3.2 Region-Based SSA Formalism

LLVM SSA = flat function of basic blocks with implicit φ-nodes at dominance frontiers. MLIR generalizes:

**Definition 3.1 (Block Argument = Explicit φ):** In MLIR, predecessor branch passes values as operands to successor block header:

```mlir
cf.cond_br %cond, ^then(%c1 : f32), ^else(%c2 : f32)
^then(%x: f32):  // x = %c1 if control from first edge
  ...
^else(%y: f32):
```

This eliminates φ-node placement as separate notion. Region nesting enforces lexical dominance: If op A defines `%v`, op B uses `%v`, then either A dominates B in same region-CFG, or A is ancestor operation dominating B's parent region, and none of the regions on the path are isolated-from-above unless explicitly captured.

**Theorem 3.1 (Region Isolation & SSA Soundness):** Inlining a region from op `src` into op `dest` preserves SSA dominance iff `DialectInlinerInterface::isLegalToInline` holds and all uses outside `src` region are remapped via IRMapping. Formally enforced by verifier [Docs].

This underpins transformations like loop unrolling, `affine.for` to `scf.for`, and accelerator launch outlining: `gpu.launch` region models kernel body as CFG with explicit captures of host values via block arguments, ensuring device code cannot accidentally capture host pointers after lowering.

#### Region Types for Accelerators

Accelerator launches are *regions*, not intrinsics:

- `scf.for %i = 0 to 128 step 1 { ... }` → single region, one block, implicit loop-carried values as block args + `scf.yield`.
- `gpu.launch blocks(%bx) in (%g1) threads(%tx) in (%b1) { ... }` → 2 nested regions: grid + block; terminator `gpu.terminator`.
- `linalg.generic` body is a region modeling scalar compute: `^bb0(%a: f32, %b: f32, %c: f32): f32 = arith.mulf %a, %b ... linalg.yield`.

Uniformity yields uniform tooling: dominance analysis, CSE, dead-code elimination work on all.

### 3.3 Verified Rewrite Patterns: From C++ Patterns to PDL

MLIR rewrite patterns are of form:

```cpp
struct FoldMatMulTranspose : OpRewritePattern<linalg.MatMulOp> {
  LogicalResult matchAndRewrite(MatMulOp op, PatternRewriter &r) const {
    // match %A_T = linalg.transpose %A
    // rewrite to matmul with transposed layout
  }
};
```

Drivers:

- **Canonicalization:** `fold`, `getCanonicalizationPatterns`, greedy worklist with benefit ordering. Convergence guaranteed if patterns strictly reduce op cost metric and are confluent — enforced by `HasCanonicalizer` trait.
- **GreedyPatternRewriteDriver:** Post-order walk, iterative `while(changed) { apply max-benefit patterns; }`. No revisiting erased ops outside current region. Fast but not exhaustive. Debugging via `--debug-only=greedy-rewriter`.
- **DialectConversion:** `ConversionTarget` legalizes; `ConversionPattern` with `TypeConverter` for type-changing ops (e.g., `tensor<*xf32>` → `memref<*xf32>`). Supports `materialize` hooks for bridging illegal→legal types. Fails if any illegal op remains — verification complete.

#### PDL: MLIR-in-MLIR for Verification

C++ patterns are opaque to analysis. **PDL** [4] reifies pattern infrastructure as a dialect:

```mlir
pdl.pattern : benefit(1) {
  %lhs_ty = pdl.type : tensor<*xf32>
  %lhs = pdl.operand : %lhs_ty
  %op = pdl.operation "linalg.matmul"(%lhs, %lhs) -> (%lhs_ty)
  pdl.rewrite %op {
    %c0 = pdl.operation "arith.constant" {value=0.0} -> (%lhs_ty)
    pdl.replace %op with (%c0)
  }
}
```

PDL ops map to `mlir::Attribute`, `Operation*`, `Value`, `Type`. Benefits:

- **Frontendable:** Python DSLs can emit PDL directly.
- **Optimizable:** Common sub-match elimination, bytecode compiler `pdl_interp` lowering for O(1) dispatch.
- **Verifiable:** PDL verifier checks that `pdl.operation` operands/types satisfy target op's ODS verifier before rewrite — static prevention of malformed rewrites. Combined with `pdl_interp` interpreter, patterns become *total* functions over well-typed IR, enabling SMT-backed lifting [Verified Lifting].

#### Transform Dialect [6]

Second-generation: Transform Dialect exposes schedule as first-class ops: `transform.sequence`, `transform.loop.tile`, `transform.structured.vectorize`. Unlike pass manager (coarse-grained, ordered), transform dialect composes imperatively on handles, preserves provenance, colored in debugger. Used industrially for autotuning.

## 4. Deep Dive: Progressive Lowering Stack for Accelerators

### 4.1 Top: Graph Dialects → Linalg on Tensors

Frameworks (JAX StableHLO, PyTorch Torch, TOSA) import to `linalg` on tensors (value semantics, no aliasing). Why tensors? Optimization without memory. Fusion, tiling, packing happen here.

```mlir
// Before fusion: two linals allocating intermediate
%C = linalg.matmul ins(%A,%B) outs(%C0) -> tensor<128x512xf32>
%D = linalg.elemwise_add ins(%C) outs(%D0) -> ...
// After fusion via TilingInterface producer-consumer patterns:
%D = linalg.generic ... combined { ^bb0: addf(mulf(...)) }
```

One-shot bufferization pass then decides allocation: `%tensor -> %memref`, inserting `memref.alloc` / `dealloc`, guaranteeing absence of RaW hazards via analysis [3 §4]. This avoids ad-hoc bufferization loops.

### 4.2 Middle: Tiling, Packing, and Vectorization

IREE's `LLVMCPU` and `LLVMGPU` pipelines illustrate hardware-aware tiling:

1.  **Tile & Fuse:** Given lowering config (`tile_sizes = [128,128,0]`), TilingInterface tiles `linalg.matmul` into loops + smaller matmuls, fuses producer elementwise op.
2.  **Packing [3]:** Cache-aware data layout transformation `tensor.pack` / `tensor.unpack` inserts `tensor.pack` → tiled layout for contiguous access, achieving 90% MKL performance without hand-written intrinsics.
3.  **Vectorize:** `linalg.matmul` → `vector.contract` → `vector.outerproduct` → `arm_neon.2d.sdot` or `x86.amx.tile_mulf`. Vector dialect is target-agnostic SIMD.
4.  **Distribute:** `scf.forall` → `gpu.thread` mapping; `vector.warp_execute_on_lane_0`.

Table: Example lowering trajectory for `16x16xf32` matmul on RTX GPU (simplified):

| Stage | IR Fragment | Legality |
|-------|-------------|----------|
| 0 | `linalg.matmul (memref<16x16xf32>)` | illegal for GPU target |
| 1 | `scf.for %i, %j { vector.contract }` | `vector` legal, `scf` legal |
| 2 | `gpu.launch { gpu.thread_id; vector.contract -> gpu.mma }` | `gpu` legal |
| 3 | `nvvm.wmma.m16n16k16 ...` | `llvm` + `nvvm` legal |
| 4 | `llvm.call @nvvm_*` | fully legal ConversionTarget |

Each step verified by DialectConversion: failure if any illegal op escapes — no silent miscompilation.

### 4.3 Bottom: Accelerator-Specific Codegen

For accelerators, three backends share middle:

- **CPU:** `vector` → `llvm` via `ConvertVectorToLLVM`, auto-vectorized to `x86vector` dialect (AVX-512, AMX), SVE, SME.
- **GPU:** `gpu.module` → `spirv.module` (Vulkan), `nvvm`, `rocdl`. `gpu.launch` outlines to kernel. Distribution via `gpu.block_id`, `gpu.thread_id`.
- **Sparse [5]:** `sparse_tensor` dialect encoding `CSR` as attribute `#{sparseTensor.encoding<{dimLevelType=["dense","compressed"]}>}`; lowering to loops that skip zeros, co-iterating multiple tensors. MLIR's sparsity compilation shows progressive lowering works for non-dense too.

Industrial validation: Tesla FSD v14.3 2026 report notes MLIR rewrite from custom stack to MLIR GPU pipeline yielding **20% faster reaction time** and faster model iteration [Electrek]. Cause: MLIR's `tensor` → `vector` → GPU MMA path preserves fusion that old stack broke when prematurely lowering to LLVM.

### 4.4 Convergence and Verification in Rewriting

Greedy rewriter convergence is undecidable generally, but sufficient condition:

> **Benefit Monotonicity:** Define total benefit `B(IR)= Σ_op cost(op)`. If every pattern's rewrite strictly reduces `B` and patterns are local (affect bounded neighborhood), then greedy driver converges in `O(B0)` steps, regardless of order, by well-founded ordering. MLIR ensures this via `benefit` integer and `cost` heuristic, plus `Fold` trait requiring op count reduction.

In practice, benefit conflict (two patterns applicable) resolved via declared benefit; highest wins locally, walk order deterministic per op traversal. Canonicalizers required confluent: pattern `a*a - b*b → (a+b)(a-b)` must not oscillate with `sub(add(mul))` — implemented with `hasOneUse()` guards [Jeremykun 2023].

PDL adds static checking: type constraints `pdl.type`, attribute constraints validated via `pdl.apply_native_constraint`. Future direction: SMT-backed verification of PDL patterns against ODS semantics [SMR 2024] using `alive2` for LLVM dialect.

## 5. Empirical Evaluation or Proofs

### 5.1 Theoretical Guarantees

- **SSA Preservation Proof (sketch):** Region inlining preserves dominance because `InlinerInterface` checks (i) source region has no ops with side-effect of capturing isolated values, (ii) all `RegionBranchOpInterface` successors dominated, (iii) `IRMapping` substitutes entry block args with dominating values. Verifier pass `isIsolatedFromAbove` + dominance analysis proves post-transform dominance.

- **Legalization Completeness:** DialectConversion is sound: if it succeeds, resulting module contains only ops marked `legal` by target, and types converted via `TypeConverter`. Complete only under assumption of finite pattern application — fails deterministically if illegal ops remain, unlike LLVM's ad-hoc `SelectionDAG` which may crash.

- **Complexity:** Greedy rewriter `O(N * P)` worst-case where N = number of ops, P = patterns; but pattern matching via PDL bytecode achieves sublinear via root-op filtering and depth-first DAG matching, similar to TableGen ISel. In practice, IREE reports <5% compile time spent in canonicalization.

### 5.2 Performance Numbers from Literature

| Source | Workload | Metric | MLIR Pipeline | Baseline |
|--------|----------|--------|---------------|----------|
| [3] Upstream MLIR 2024 | GEMM f32 4096² | GFLOPS | 90% of MKL ninja | MKL / hand intrinsics |
| [Tesla Industrial] | FSD DNN | Latency | -20% reaction | prior LLVM-based compiler |
| [5] Sparse | SpMM 10% density | Speedup | 2.3× vs dense linalg | PyTorch sparse dense fallback |
| IREE [8] | BERT Large | tokens/s | 1.6× vs TF/XLA | XLA GPU |

Not synthetic: upstream MLIR packing achieves ~95% L2 cache reuse on Sapphire Rapids AMX via `tensor.pack` + tile sizes auto-tuned by `transform` dialect [6].

### 5.3 Failure Modes Observed

- **Over-eager folding:** Canonicalizer `fold` of `tensor.empty` may remove aliasing barrier needed for bufferization; mitigated via `hasTrait` `MemRefsNormalizable` gating.
- **Worklist explosion:** `walkAndApplyPatterns` without bounding `maxIterations` diverges on `arith.addi` associative patterns; fix: greedy driver with `withRegionFilter` + benefit decay.
- **Type converter materialization loops:** When `tensor` → `memref` conversion injects `unrealized_conversion_cast`, failure to canonicalize cast-away leads to infinite legalization retries. MLIR solution: materializations marked `allowPatternRollback`.

## 6. Limitations and Open Problems

1.  **Declarative Power vs Imperative Need:** ODS/pdl covers 80% patterns, but many accelerator patterns need data-flow analysis (use-def chain >1 level). Current workaround: `NativeRewrite` calling C++ constraint, losing declarative verifiability. Research: PDL+PDLL [ACM TAP 2024] proposing control-flow matching as first-class.

2.  **Raising Brittleness:** Despite MLIR goal to avoid raising, frontend still must lift C loops to `affine`. Polygeist [7] uses Clang AST + `ValueTracking` but fails on pointer-chasing `while`. Open: complete C++ template instantiation to MLIR modeling.

3.  **Composability of Transforms:** Pass ordering remains textual; Transform dialect mitigates but introduces second-order scheduling complexity. The promise of autodiff over transform dialect handles (search `transform` + MLIR autotuning) not yet stable upstream.

4.  **Verified Lowering End-to-End:** While pattern verifiers guarantee syntactic legality, semantic preservation still relies on C++ pattern authoring correctness. No Lean/C oq mechanization of MLIR semantics yet. Projects like `mlir-tv` attempt Alive2-style translation validation for `affine`→`llvm`.

5.  **Compilation Time:** Progressive lowering retains many intermediate ops; each pass walks full module. Upstream notes ~2× compile time vs hand-written IREE hal pipeline when enabling aggressive tiling. Need incremental pass manager: operation `OpPassManager` nesting partially addresses but not cross-region caching.

> **Open Conjecture:** A type-theoretic description of dialect interfaces as row-polymorphic effects might give static guarantee that progressive lowering pipeline is total (always succeeds) — currently checked dynamically at `applyPartialConversion` time.

## 7. Conclusion

MLIR is not another IR; it is a meta-IR infrastructure that makes dialect design, region-scoped SSA, and verified rewriting *ordinary engineering*. The intellectual shift is profound: instead of arguing whether an IR should be high-level or low-level, MLIR hosts both, simultaneously, in same module, with well-defined dominance and explicit conversion legality.

For accelerator compilers, this is decisive. Preservation of `linalg.generic`'s affine maps and iterator types enables tiling decisions that cannot be recovered from loop nests; region modeling of `gpu.launch` ensures device/host separation enforced by verifier, not convention; PDL provides syntactic guarantee that an accelerator lowering never silently produces illegal SPIR-V.

Progressive lowering, when coupled with benefit-ordered greedy rewriting and conversion-target legality, delivers industrial gains — 20% latency, 90% of ninja, 2-3× sparse speedups — without sacrificing correctness. The future lies in making pattern verification semantic, not just syntactic, and in giving Transform dialect scheduling first-class autotuning support.

The compiler writer's task is no longer to build a monolith that understands TPU systolic arrays, GPU warps, and CPU AMX. It is to **design a dialect that understands one of them perfectly, declare its interface, and let MLIR's disciplined lowering do the rest**. That modularity is the lasting contribution of Lattner et al. [1].
