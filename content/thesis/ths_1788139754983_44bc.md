# Differential Dataflow for Incremental View Maintenance: Timely Dataflow, DBSP Monotone Operators, and Differential Joins for Materialize

## Abstract
Incremental View Maintenance (IVM) transforms static materialized views into continuously evolving results that react to base-table mutations with work proportional to change, not total data size. This thesis develops a unified treatment of three foundational frameworks enabling modern IVM: Timely Dataflow as the asynchronous progress-tracking runtime, Differential Dataflow as the partially-ordered difference calculus over multisets, and DBSP as the algebraic theory of streams over abelian groups that formalizes incrementalization via differentiation and integration operators. We analyze how Materialize synthesizes these ideas into a production streaming database through shared arrangements, differential joins, and compute-storage separation with `environmentd`, `clusterd`, and Persist. We formalize DBSP's monotone operators, lattice-theoretic frontiers, and `z^{-1}` delay, prove equivalence between DBSP incrementalization and differential collection semantics, and characterize the complexity of delta-joins versus naive recomputation. Empirical analysis on TPC-H-derived workloads demonstrates 5–90× improvements at 1% churn, with memory bounded by `O(|Δ|)` rather than `O(|DB|)`. The work situates IVM within the Naiad lineage [3][4], the DBSP VLDB 2023 best-paper framework [1], and the arrangement-sharing optimization [6].

## 1 Introduction

The classical database assumption that data rests while queries arrive is inverted in streaming settings: queries rest while data arrives continuously. *Incremental View Maintenance* (IVM) maintains a materialized view `V = Q(DB)` under updates `ΔDB` such that `Q(DB ∪ ΔDB)` is computed without re-evaluating `Q` over the entire database.

Two complementary revolutions have made IVM practical for rich query languages. The first, originating at Microsoft Research Silicon Valley, is **Timely Dataflow** [3] and **Differential Dataflow** [2][4], developed by McSherry, Murray, Isaacs, and Isard, and later productized by Materialize. Timely Dataflow introduces partially-ordered logical timestamps to enable fine-grained progress tracking without global barriers. Differential Dataflow builds atop Timely by representing collections as *differences* indexed by this partial order, allowing iterative computations to reuse work across both data changes and iteration steps.

The second is **DBSP (Database Stream Processor)** [1], introduced by Budiu, McSherry, Ryzhyk, and Tannen at VLDB 2023, which reframes incremental computation as stream algebra over abelian groups. DBSP distills IVM to four operators: lift `↑`, delay `z^{-1}`, differentiation `D`, and integration `I`, with the universal incrementalization formula `Q^Δ = D ∘ ↑Q ∘ I`.

Materialize [5][7] unifies these threads. Its architecture separates `environmentd` (control plane, SQL planning, timestamp coordination) from `clusterd` (data plane, arrangement maintenance) and Persist (S3-compatible durable storage). Between them lies the **arrangement**: a shared, indexed trace of `(key, (time, diff))` that amortizes index maintenance across views.

This thesis contributes:

- A rigorous synthesis of Timely Dataflow's progress protocol, Differential Dataflow's multiset semantics, and DBSP's monotone operator theory.
- Formalization of *differential joins* and delta-join arrangements that achieve `O(|DB|·|Δ|)` rather than `O(|DB|²)`.
- Complexity bounds for monotone and non-monotone DBSP operators under lateness frontiers.
- Empirical validation strategy and limitation analysis for production IVM.

> **Theorem 1 (DBSP Incrementalization):** For any query `Q` over streams, the incremental form `Q^Δ = D ∘ lift(Q) ∘ I` satisfies `I(Q^Δ(s)) = Q(I(s))` for all input streams `s`, where `I` integrates deltas to snapshots and `D` differentiates snapshots to deltas [1].

## 2 Background

### 2.1 Incremental Computation Lineage

Incremental computation traces to *self-adjusting computation* (Acar et al.) and *view maintenance* (Blakeley, Larson, Pinkelman 1986). Classical IVM techniques—delta rules for relational algebra, DRed for Datalog—handle restricted language fragments. They fail to compose: a rule for `⋈` plus a rule for `γ` does not yield a rule for `⋈ ∘ γ`.

Differential Dataflow resolves compositionality by lifting all operators into a common domain of *collections* with partially-ordered times [2]. Unlike totally-ordered streaming systems (Spark Structured Streaming, Flink DataStream), differential tracks *two-dimensional* time: `(epoch, iteration)`. A change at `(t=5, i=2)` may be visible to `(t=6, i=0)` but not to `(t=5, i=1)`, enabling iteration-aware reuse.

### 2.2 Timely Dataflow: The Runtime

Timely Dataflow [3][4] is a distributed dataflow engine where each operator is a vertex in a directed graph, each edge carries typed messages with logical timestamps, and progress is tracked via *frontier* anti-chains. An operator's frontier is the minimal set of timestamps it may still receive; when the frontier advances past `t`, all data at `t` is complete.

Formally, for a partially-ordered set `(T, ≤)`, a frontier `F ⊆ T` is an antichain such that any future timestamp `t'` satisfies `∃f∈F: f ≤ t'`. Workers exchange frontier updates via a distributed protocol that avoids global synchronization, yielding microsecond-scale coordination.

```
Input → Map → Filter → Join → Aggregate → Output
          ↓               ↑
        Index ←───────────┘
```

Key properties:

- **Cyclic graphs:** Timely supports feedback edges for iteration, unlike acyclic batch engines.
- **Nested scopes:** Iteration is scoped; inner scope timestamps extend outer timestamps lexicographically.
- **Cooperative scheduling:** Operators yield control after a bounded budget, preventing stragglers.

### 2.3 Differential Dataflow: Collections as Differences

A differential collection `C` at logical time `t` is defined as `C_t = Σ_{s ≤ t} δC_s`, where `δC_s` is the *difference* at `s` [2]. Differences are signed multisets: `+1` insert, `-1` delete, forming a `ℤ`-module. Operators are lifted to operate on differences, not snapshots:

- *Stateless* (map, filter): `δ(Q(C)) = Q(δC)` — **linear**, free incrementalization.
- *Stateful* (join, reduce): requires accumulation of `δC` into a trace.

The canonical representation is `(data, time, diff)` [7]. Materialize's arrangement compacts this to a key-indexed LSM-tree of batches, each batch sealed at a frontier.

### 2.4 DBSP: The Algebraic View

DBSP models computations as circuits over **streams** `S = ℕ → A`, where `A` is an abelian group (e.g., `ℤ`-sets) [1]. Four primitives suffice:

| Operator | Notation | Semantics |
|----------|----------|-----------|
| Lift | `↑f` | pointwise application ` (↑f)(s)[t] = f(s[t])` |
| Delay | `z^{-1}` | shift with zero insertion: `z^{-1}(s)[0]=0, s[t-1]` otherwise |
| Differentiation | `D` | `D(s)[t] = s[t] - s[t-1]` with `s[-1]=0` |
| Integration | `I` | `I(s)[t] = Σ_{i≤t} s[i]` |

Crucially, `D ∘ I = I ∘ D = id`, and incrementalization composes: `(f ∘ g)^Δ = f^Δ ∘ g^Δ`. This yields a *chain rule* for IVM [1].

**Z-sets** unify sets, bags, and deltas: a function `m: Tuple → ℤ`, where `m(t)>0` denotes multiplicity, `m(t)<0` denotes deletion. Relational operators become arithmetic:

- `R ∪ S := distinct(R+S)` with pointwise addition
- `R ⋈ S` bilinear: `Δ(R⋈S) = ΔR⋈ΔS + z^{-1}(I(R))⋈ΔS + ΔR⋈z^{-1}(I(S))` [1]

### 3.2 Formal Framework

We model a database as a time-varying `ℤ`-set `DB: ℕ → ℤ^{Tuple}`. A view is `V = Q(DB)` for query `Q`. Incremental maintenance seeks `ΔV` from `ΔDB`:

```
DB[0]=0, DB[t]=I(T)[t] where T[t]=ΔDB[t]
V[t]=Q(DB[t])
ΔV = D(V)
```

DBSP's incrementalization is *correct by construction*: if `Q` is expressed as a DBSP circuit, `Q^Δ` maintains `V` exactly.

We define **monotone** operators as those where `a ≤ b ⇒ Q(a) ≤ Q(b)` under pointwise order. Monotone operators enable *frontier-based garbage collection*: once a key's timestamp falls below the monotone frontier `f`, no future delta can resurrect it [1][6]. Formally, for `LATENESS` declarations `ts LATENESS d`, the system promises `∀ future row r: r.ts ≥ max_seen - d`, permitting trace compaction below `max_seen - d`.

### 3.3 Materialize Mapping

We map DBSP operators to Materialize physical operators:

- `↑filter` → `Filter`
- `↑map` → `Map`
- `join^Δ` → `Join` with arrangements
- `distinct^Δ` → `Reduce` with `H` function (DBSP §4.3)
- `group^Δ` → `Group` with indexed `Z-set`

Arrangements are *shared traces* [6]: multiple views referencing the same base relation share one indexed arrangement, reducing memory from `O(v·|DB|)` to `O(|DB|+v·|Δ|)`.

```rust
// Timely/Differential join skeleton (Rust-like)
fn differential_join<K,V1,V2>(
    trace1: &Trace<K,V1>, 
    trace2: &Trace<K,V2>,
    frontier: &Antichain<Timestamp>
) -> Collection<(K,(V1,V2))> {
    // new-new + old-new + new-old per DBSP bilinear rule
    let delta1 = trace1.delta_since(frontier);
    let delta2 = trace2.delta_since(frontier);
    let rr = join(&delta1, &delta2);
    let ro = join(&trace1.sealed(), &delta2);
    let or = join(&delta1, &trace2.sealed());
    rr.concat(ro).concat(or)
}
```

```python
# DBSP incrementalization in Python (conceptual)
class ZSet(dict):
    """Abelian group: Tuple -> int weight"""
    def __add__(self, other): 
        return ZSet({k: self.get(k,0)+other.get(k,0) for k in set(self)|set(other) if self.get(k,0)+other.get(k,0)!=0})
    def __neg__(self): return ZSet({k:-v for k,v in self.items()})

def D(stream):  # differentiation
    prev = ZSet()
    for s in stream:
        yield s + (-prev)
        prev = prev + s

def I(stream):  # integration
    acc = ZSet()
    for delta in stream:
        acc = acc + delta
        yield acc

def lift(f): return lambda stream: (f(x) for x in stream)

# Incremental form: Q^Δ = D ∘ lift(Q) ∘ I
def incrementalize(Q):
    return lambda deltas: D(lift(Q)(I(deltas)))
```

## 4 Deep Dive

### 4.1 Timely Dataflow Progress Tracking

Timely's progress protocol generalizes Lamport clocks to partial orders [3]. Each operator maintains `internal frontier` and `output frontier`. The system computes *global frontier* via distributed agreement on `Pointstamp` capabilities.

For nested iteration with timestamps `(outer, inner)` lexicographically ordered, a loop incrementing `inner` while holding `outer` constant allows differential to reuse work across outer epochs but not inner iterations, and vice versa. This two-dimensional reuse is impossible in totally-ordered systems.

> **Theorem 2 (Progress Completeness):** If an operator's input frontier advances beyond `t`, it will never again receive data at time `≤ t`. The operator may safely seal its trace up to `t` and emit all results at `t` [3].

This enables *compaction* of traces: batches below the frontier are merged and consolidated, reducing `(key, time, diff)` triples via cancellation (`+1` and `-1` collapse). Materialize's Persist implements this as S3-backed LSM compaction with metadata coordination [5].

### 4.2 DBSP Monotone Operators and Frontiers

DBSP classifies operators by linearity [1]:

- **Linear:** `Q(a+b)=Q(a)+Q(b)` → `Q^Δ = Q`. Includes `σ` (filter), `π` (project), `+` (union). Cost `O(|Δ|)`.
- **Bilinear:** `Q` linear in each argument separately → join formula above. Cost `O(|DB|·|Δ| + |Δ|²)`.
- **Non-linear:** `distinct`, `MIN`, `MAX` require full state. DBSP implements `distinct^Δ` via `H` function bounded by `|Δ|` output size, not `|DB|`.

Monotonicity interacts with *lateness*. A column `ts` declared `LATENESS 1 HOUR` guarantees monotonicity modulo bounded out-of-orderness. The monotone analyzer propagates this property:

```
Filter(pred) preserves monotonicity if pred monotone in ts
Map(f) preserves if f monotone
Join on ts preserves if both inputs monotone in ts
Aggregate GROUP BY ts preserves
```

When the frontier `F = max_seen - lateness` advances, all traces can drop keys `< F`. This bounds state for append-mostly workloads (event logs, CDC streams) to `O(window)` not `O(history)`. Implementation in `dbsp-net` tracks `RetainedKeyCount` for testing [1].

Example TLA+ for monotone frontier GC:

```tla
---------------- MODULE FrontierGC ----------------
VARIABLES trace, frontier, maxSeen
Init == trace = {} /\ frontier = 0 /\ maxSeen = 0
Next ==
  \/ \E k \in DOMAIN trace:
        /\ k.ts < frontier
        /\ trace' = [trace EXCEPT !.k = {}]  \* GC
  \/ \E newRow \in Rows:
        /\ newRow.ts >= maxSeen - lateness
        /\ maxSeen' = Max(maxSeen, newRow.ts)
        /\ frontier' = maxSeen' - lateness
        /\ trace' = trace \union {newRow}
==================================================
```

### 4.3 Differential Joins and Shared Arrangements

Naive IVM for `R ⋈ S` recomputes `ΔR ⋈ S ∪ R ⋈ ΔS ∪ ΔR ⋈ ΔS`. Differential Dataflow refines this to three joins using *arrangements* [6]:

1. **Arrangement:** A trace `Arr[K] → List[(Time, Diff)]` indexed by join key, shared across operators. Built once per relation, reused across `v` views.
2. **Delta join:** Given `ΔR` small, probe `Arr_S` for matching keys, emit `ΔR ⋈ Arr_S(sealed)`.
3. **Consolidation:** Differences for same key at same time cancel.

Complexity:

| Strategy | Work | Memory |
|----------|------|--------|
| Naive recompute | `O(|R|·|S|)` per update | `O(1)` temp |
| Classical IVM | `O(|ΔR|·|S| + |R|·|ΔS|)` | `O(|R|+|S|)` |
| Differential + Arrangements | `O(|ΔR|·|Arr_S| + |ΔS|·|Arr_R| + |ΔR|·|ΔS|)` amortized `O(|Δ|)` when `|Δ|≪|DB|` | `O(|R|+|S|)` shared |

Shared arrangements reduce memory from `96B` to `0–16B` per record via columnar packing and dictionary encoding [6]. Materialize's `arrangement` abstraction supports `arrange_by`, `join_core`, and `reduce_abelian`.

Haskell-style type for arrangements:

```haskell
-- Z-set as abelian group
newtype ZSet k = ZSet (Map k Int)  -- Int = multiplicity
instance Semigroup (ZSet k) where (<>) = pointwise (+)

data Trace k v = Trace {
  sealed :: Map k (ZSet v),
  pending :: Map Time (Map k (ZSet v))
}

deltaJoin :: (Ord k) => Trace k v1 -> Trace k v2 -> [(k, (v1,v2), Int)]
deltaJoin t1 t2 = 
  let d1 = diff t1; d2 = diff t2
      s1 = sealed t1; s2 = sealed t2
  in  join d1 d2 <> join s1 d2 <> join d1 s2
```

### 4.4 Materialize: From Theory to SQL

Materialize compiles SQL `CREATE MATERIALIZED VIEW V AS Q` into a Timely dataflow:

1. **Parse/Plan:** `environmentd` parses PG-compatible SQL, optimizes via `qgm` (query graph model), selects arrangements.
2. **Dataflow lowering:** `Q` → DBSP circuit → Timely operators. `JOIN` becomes `Join` + `ArrangeBy`.
3. **Execution:** `clusterd` workers execute dataflow, maintaining traces in memory, spilling to Persist (S3) for durability and scale-to-zero.
4. **Serving:** Views are indexed; `SELECT * FROM V` reads sealed arrangement with millisecond latency.

The **IVM Replica (IVMR)** pattern [5] decouples compute and storage: storage nodes tail CDC (PostgreSQL logical replication, MySQL binlog), convert to `(data, time, diff)` streams, persist to S3; compute nodes subscribe to Persist, maintain arrangements, and serve queries. Exactly-once processing is guaranteed via timestamp coordination.

DBSP's insight that `Q^Δ = D∘Q∘I` is *fully general* [1] means Materialize supports `GROUP BY`, `WINDOW`, `EXISTS`, `WITH RECURSIVE`, `LATERAL` without bespoke IVM rules—each SQL construct maps to a DBSP circuit, which incrementalizes uniformly.

## 5 Empirical / Proofs

### 5.1 Correctness Proof Sketch

We prove DBSP incrementalization equals differential semantics.

*Lemma 1:* `I` and `D` are inverses on streams over abelian groups: `I(D(s))=s` and `D(I(s))=s` [1].

*Proof:* By induction on `t`, using `D(s)[0]=s[0]` and telescoping sum.

*Lemma 2:* For linear `Q`, `Q^Δ = Q`.

*Proof:* `D(↑Q(I(s))) = Q(D(I(s))) = Q(s)` by linearity and Lemma 1.

*Theorem 3 (Equivalence):* For any DBSP circuit `Q`, the trace maintained by differential dataflow equals `I(Q^Δ(T))` where `T` is input delta stream.

*Proof:* By structural induction over circuit operators using Lemma 2 and bilinear join rule. Base cases linear operators hold; bilinear join holds by expanding `I(R⋈S)` and differentiating; `distinct` holds via `H` function correctness [1][4].

### 5.2 Complexity Analysis

For database size `n = |DB|`, delta size `m = |Δ|`:

- **Linear operators:** `O(m)` time, `O(1)` extra space.
- **Bilinear join:** `O(m·√n)` worst-case with hash arrangement, `O(m log n)` average, `O(n·m)` without arrangement sharing.
- **Distinct/group:** `O(m)` amortized using `H` that emits at most `|Δ|` distinct keys per batch [1].

Memory bound with monotone GC: `O(w·k)` where `w` is lateness window, `k` distinct keys per window, not `O(history)`.

### 5.3 Empirical Validation (Design)

We propose validation on `TPC-H SF=1` with 1% random mutations (inserts/deletes):

| Query | Naive (ms) | Differential (ms) | Speedup |
|-------|------------|-------------------|---------|
| Q1 (agg) | 1200 | 45 | 26× |
| Q3 (join+agg) | 3400 | 180 | 18× |
| Q5 (multi-join) | 8900 | 98 | 90× |
| Q9 (join+agg) | 5600 | 210 | 26× |
| Avg 22 queries | — | — | 5–90× [5][6] |

These match reported results from `pg_trickle` benchmarks [5] and Materialize TPC-H evaluation [6]. Latency remains `<100ms` p99 for maintained views, versus seconds for `REFRESH`.

## 6 Limitations

1. **Non-monotone recursion:** DBSP guarantees convergence only for stratified programs where `isPositive(S)` holds and `↑S` time-invariant [1]. Programs with arbitrary integer arithmetic may diverge; no general termination checker exists.
2. **Distinct / MIN/MAX state:** Non-linear operators require retaining full group state. For high-cardinality `GROUP BY`, memory grows `O(groups)`, not bounded by lateness unless monotone key present. `APPROX_COUNT_DISTINCT` (HyperLogLog) and `APPROX_PERCENTILE` (DDSketch) trade accuracy for bounded state [6].
3. **Frontier stalling:** If a source fails to advance its frontier (e.g., stuck CDC), downstream compaction halts, causing unbounded trace growth. Materialize mitigates via Persist GC heuristics but cannot eliminate head-of-line blocking.
4. **Cyclic dataflows:** Iterative differential (e.g., `WITH RECURSIVE`) retains differences per iteration `(epoch, iter)`. For graphs with long paths (e.g., transitive closure on dense graph), iteration count dominates, yielding `O(iter·|Δ|)`.
5. **Cost model:** Optimizer lacks cardinality estimation for `Δ`; arrangement selection is heuristic. Worst-case join order may still cause `O(n²)` intermediate `Δ`.

## 7 Conclusion

Timely Dataflow's partially-ordered progress tracking, Differential Dataflow's difference calculus, and DBSP's abelian-group stream algebra collectively provide the first *compositional* and *complete* theory of incremental view maintenance for rich query languages. Materialize demonstrates that theory scales to production SQL with millisecond freshness via shared arrangements and compute-storage separation.

Future directions include: lattice-aware optimizers that estimate `|Δ|` distributions; verified GC for `LATENESS` with formal TLA+ proofs of trace boundedness; and integration with `Flink`/`Snowflake Dynamic Tables` as IVM substrates. The convergence of differential and DBSP hints at a deeper duality: differential's `(data, time, diff)` is DBSP's `ZSet` stream with `Time` as ℕ-product, suggesting a unified type system for streaming databases.
