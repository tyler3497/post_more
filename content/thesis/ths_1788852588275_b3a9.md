# History as Ground Truth: Deterministic Replay, Event-Sourced Orchestration, and Transactional Recovery in Temporal and DBOS

## Abstract

Durable execution promises that a program survives crashes, yet the mechanism that makes the promise credible is rarely the scheduler — it is the history. This thesis argues that *history reconstruction* — rebuilding program state by replaying an immutable event log — is the primitive from which durable workflow orchestration derives its guarantees. We compare two realizations: **Temporal**, which persists every workflow decision as an ordered event history and recovers workers by deterministic replay of workflow code [3][5][7]; and **DBOS**, which checkpoints transactional functions in PostgreSQL so workflows resume from the last completed step with exactly-once semantics [1][2]. We formalize *replay equivalence* — replaying a history reproduces the state trajectory of uninterrupted execution — and prove it for deterministic orchestration functions. We analyze versioning as the discipline keeping evolving code compatible with recorded histories, the transactional outbox as the atomic joint between history and side effects [8], and event sourcing as the theoretical substrate [4]. Empirical evaluation reports recovery latencies and replay overheads from the literature and instrumented reconstructions, quantifying the cost and limits of the history-as-truth design.

## 1 Introduction

A program that *cannot forget where it was* is qualitatively different from one that merely retries. Traditional fault tolerance — supervisor trees, retry loops, dead-letter queues — treats failure as an event to react to; **durable execution** treats failure as a state from which execution can be *continued*, as if the crash had never interrupted the control flow. 

The credibility of this guarantee rests on one architectural decision: *externalize the program's execution state as an immutable, ordered history, and reconstruct state by replaying it*. Everything else — retries, heartbeats, sagas, timeouts — is auxiliary. Two contemporary systems instantiate this principle from opposite directions. **Temporal** adopts a pure event-sourced core: the workflow function itself is re-executed from the beginning after a crash, and recorded event outcomes are substituted for real effects until the replay catches up with the failure point [3]. **DBOS** adopts a database-centric design: workflow progress is checkpointed transactionally in PostgreSQL, so recovery resumes from the last committed step rather than replaying orchestration code from scratch [2]. The original DBOS vision, presented at VLDB 2022, goes further — proposing that *all* operating-system state be managed by a distributed transactional DBMS, with IPC, scheduling, and filesystem metadata as queryable tables [1].

This thesis contributes:

1. A **formal model of replay equivalence** with a proof sketch establishing the conditions under which history replay reproduces uninterrupted execution.
2. A **comparative architecture analysis** of Temporal's history-reconstruction loop versus DBOS's transactional checkpointing, including versioning, exactly-once semantics, and queueing via the transactional outbox.
3. An **empirical evaluation** of recovery latency and replay overhead, with measurements and reported results from the literature.
4. A **limitations analysis** covering history growth, determinism violations, and the database bottleneck — the failure modes the history-as-truth design does not eliminate.

## 2 Background

### 2.1 Event sourcing: state as a fold over history

Martin Fowler's treatment of event sourcing defines the pattern crisply: instead of storing current state, persist the *sequence of state-changing events* that produced it; current state is a left fold over that sequence [4]. Rebuilding any past state is replaying a prefix of the log. The pattern's power — temporal queries, auditability, free rebuilds — comes at the price of discipline: *every* state change must be captured as an event, and external side effects performed during replay must be intercepted or stubbed.

Durable workflow engines are event sourcing applied to *program execution itself*. The "aggregate" is the workflow run; the "events" are workflow decisions (schedule activity, start timer, receive signal) and their outcomes (activity completed, timer fired). Temporal's event history is precisely this: an append-only log in which each workflow task's commands are durably recorded before execution [3].

### 2.2 The dual-write problem and the transactional outbox

Durable execution must cross a boundary the pure event-sourced model avoids: *notifying the outside world*. Persisting state in a database and publishing a message to a broker is a dual write — if one succeeds and the other fails, the system is inconsistent [8]. The **transactional outbox** resolves this by writing the outbound message into an *outbox table inside the same database transaction* that updates business state; a relay process then publishes outbox entries to the broker [8]. Delivery is at-least-once — a relay may crash after publishing but before recording progress — so consumers must be idempotent, typically by tracking processed message IDs [8]. This pattern is the load-bearing joint between transactional state and durable queues in systems like DBOS, and it is the mechanism by which history appends and external effects become atomic.

### 2.3 A formal model of histories and replay

Let a workflow run be characterized by:

- An **event alphabet** $\Sigma$ of history events (e.g., `WorkflowStarted`, `ActivityScheduled`, `ActivityCompleted`, `TimerFired`, `SignalReceived`).
- A **history** $H = \langle e_1, e_2, \dots, e_n \rangle \in \Sigma^*$, an append-only sequence.
- A **workflow function** $W$ mapping a history prefix to a *command* $c \in \mathcal{C}$ (schedule activity, start timer, complete, …) plus updated local state.
- A **state fold** $\sigma(H)$ giving the workflow's local state after replaying $H$.

> **Theorem (Replay Equivalence, informal):** Let $W$ be *deterministic* — i.e., for every history prefix $H'$, $W(H')$ yields the same command and state transition regardless of wall-clock time, randomness source, or machine identity. Let $H_n$ be the history produced by uninterrupted execution of $W$. Then replaying $H_n$ from an empty state with $W$ reconstructs exactly the state trajectory $\sigma(H_1), \dots, \sigma(H_n)$ of the original run.

The proof (Section 5) proceeds by induction on history length. The theorem's contrapositive is the entire *determinism contract* of durable execution: any nondeterminism in $W$ — `random()`, `time.now()`, unversioned code changes — can break the correspondence, and the engine must detect the mismatch (Temporal raises non-determinism errors surfaced as `Nondeterminism` workflow-task-failure causes [5]).

## 3 Methodology

This thesis follows a **comparative systems-analysis methodology** with three components:

1. **Literature synthesis.** We ground the analysis in primary sources: the DBOS VLDB 2022 paper describing the DBMS-oriented operating system and its system-replay capabilities [1]; DBOS Transact documentation describing Postgres-backed durable workflows, steps, and exactly-once primitives [2]; Temporal's official encyclopedia entries on event history, including the command/event walkthrough and determinism constraints [3]; replay-testing practice in the Temporal SDKs [7]; Fowler's event sourcing [4]; and AWS's prescriptive guidance on the transactional outbox [8].

2. **Architectural reconstruction.** For each system we reconstruct the recovery path end-to-end: what is persisted, when, under what atomicity; what replays, in what order, against what recorded data; and which invariants must hold for recovery to be correct. We validate the reconstructions against documented failure semantics (e.g., Temporal's worked non-determinism example in which replay produces `ScheduleActivityTask` where the history expects `StartTimer` [3]).

3. **Empirical measurement and proof.** We formalize replay equivalence and give a proof sketch (Section 5), then report recovery-latency and replay-overhead measurements from instrumented replays alongside throughput claims reported in the primary literature. We explicitly mark which numbers are ours and which are reported, and we state threats to validity.

## 4 Deep Dive

### 4.1 Temporal: the event history as the single source of truth

Temporal's execution model is the purest large-scale realization of history reconstruction in production workflow orchestration. Every workflow decision is recorded as an **immutable event** before it is executed [7]:

```
Event 1: WorkflowExecutionStarted
Event 2: WorkflowTaskScheduled / Started / Completed
Event 3: ActivityTaskScheduled (charge_card, args)
Event 4: ActivityTaskStarted / Completed → "auth_code_881"
Event 5: TimerStarted (30d)
        ← worker crashes here
```

The workflow function is ordinary code. When the worker dies, a new worker *re-executes the workflow function from the beginning*. But re-execution is not re-performance: for every command the code emits, the engine consults the recorded history. If `ActivityTaskCompleted` already exists for the corresponding `ActivityTaskScheduled`, the recorded result is returned to the code — **no real I/O occurs**. Execution fast-forwards through the prefix of completed work and resumes "for real" at the first command with no recorded outcome [7]. Temporal's own documentation describes the mechanism identically: on restart, the engine replays events 1–4, returns recorded results for completed activities, and resumes at the interrupted step [7].

The **determinism contract** is strict and load-bearing. Workflow code must produce the identical command sequence on every replay; `random`, `time.time()`, direct HTTP calls, and file reads are forbidden inside workflow code, and even module-level imports of I/O libraries are restricted in the Python SDK [7]. The canonical failure mode is instructive: if the original execution recorded `TimerStarted`/`TimerFired` (because a random draw was 84) but replay draws 14 and emits `ScheduleActivityTask` instead, the mismatch between the replayed command and the expected history event *fails the workflow task* — treated as a transient failure that retries, possibly forever, until the non-determinism is fixed or versioned away [3].

```python
# Temporal Python SDK: workflow code must be deterministic.
# Non-deterministic inputs are obtained via activities or safe APIs.
from temporalio import workflow
from datetime import timedelta

@workflow.defn
class BillingWorkflow:
    @workflow.run
    async def run(self, customer_id: str) -> str:
        # workflow.now() is replay-safe: recorded in history on first
        # execution, returned verbatim on replay.
        ts = workflow.now()
        # All I/O, randomness, and clock reads go through activities.
        auth = await workflow.execute_activity(
            charge_card, customer_id,
            start_to_close_timeout=timedelta(minutes=5),
        )
        return f"{auth}:{ts.isoformat()}"
```

Signals, queries, and timers all participate in the same history discipline: `SignalReceived` events are ordered into the log, queries read reconstructed state without mutating it, and timers are recorded as `TimerStarted`/`TimerFired` pairs so that a replayed sleep returns immediately when the recorded `TimerFired` exists [6].

### 4.2 Versioning: keeping evolving code compatible with recorded histories

Replay equivalence assumes the *same* workflow function $W$ across original execution and replay. Production systems violate this assumption constantly: code deploys while workflows are in flight. **Versioning** is the discipline that preserves the theorem's premise across code evolution. Temporal's `getVersion` / `patch` API records a **version marker** in the history at the point of divergence; on replay, the marker is read back and the code takes the recorded branch rather than the current default, so long-running executions finish on the semantics they started with [5]. Patches are later deprecated and removed once no live history can contain the old marker — a lifecycle the SDK skill guides describe explicitly: capture representative histories, add the patch, replay-test in CI, deprecate after retention expires [5][6].

The standard validation is **capture-then-replay**: record production (or test) histories as JSON fixtures and replay them against current code in CI, failing the build on mismatch [7]. The Java SDK ships `WorkflowReplayer` and `WorkflowExecutionHistory` for exactly this; the discipline generalizes to every SDK. In the formal model, versioning extends determinism to a *history-indexed* determinism: $W_v(H')$ must equal the command recorded when marker $v$ was written, for every version $v$ the history can reference.

### 4.3 DBOS: transactional functions and Postgres-backed recovery

DBOS inverts Temporal's trade. Where Temporal reconstructs state by re-executing orchestration code against an event log, DBOS **checkpoints workflow progress in PostgreSQL** and resumes from the last completed step [2]. The programming model annotates ordinary functions:

```python
from dbos import DBOS

@DBOS.step()
def reserve_inventory(order_id: str) -> None: ...

@DBOS.step()
def charge_payment(order_id: str) -> None: ...

@DBOS.workflow()
def fulfill_order(order_id: str) -> None:
    reserve_inventory(order_id)
    charge_payment(order_id)

# On crash, fulfill_order resumes after the last committed step.
```

Each step's completion is recorded transactionally; recovery does not re-run completed steps, it *skips* them by consulting the checkpoint table. This yields **exactly-once execution semantics** for steps: a step that completed before the crash is never re-executed, while a step interrupted mid-flight is retried with its recorded inputs. DBOS further provides Postgres-backed durable queues, notifications, scheduling, and event processing [2] — and queueing here is precisely the transactional outbox of Section 2.2: enqueue and state mutation commit atomically, with at-least-once delivery and idempotent consumers [8].

The deeper lineage is the DBOS operating-system project from Berkeley and collaborators: a four-level stack with a distributed transactional DBMS at the bottom, OS services (scheduler, filesystem, IPC) built on top as SQL applications, and all IPC messages and task state queryable as tables — enabling, among other things, *system replay* of the entire cluster's execution for debugging [1]. The VLDB 2022 paper reports that the prototype was exercised at large scale (the authors describe runs on MIT SuperCloud infrastructure) and that DBMS-backed OS services performed competitively with conventional implementations [1]. DBOS Transact, the current developer-facing incarnation, narrows this vision to application-level durability on standard Postgres while retaining the essential idea: *the database is the source of truth, and recovery is a query, not a replay*.

| Dimension | Temporal | DBOS (Transact) |
|---|---|---|
| Ground truth | Ordered event history (per workflow run) | Postgres checkpoint tables (per workflow/step) |
| Recovery mechanism | Re-execute workflow code; substitute recorded outcomes | Resume after last committed step |
| Replay cost | O(history length) per recovery | O(1) step lookup, bounded by un-checkpointed suffix |
| Determinism burden | On workflow code (strict contract) | On steps (idempotent retry); orchestration may be ordinary code |
| Exactly-once | Via recorded outcomes + idempotent activities | Via transactional step records |
| Queueing | Via workflow signals / child workflows | Durable queues on transactional outbox semantics |
| Time travel | History reset to a `WorkflowTaskCompleted` point | SQL time-travel debugging over recorded tables |

### 4.4 Exactly-once semantics: where they actually live

"Exactly-once" is routinely mislocated in the transport layer. Both systems place it correctly: **at-least-once delivery (or at-least-once scheduling) composed with idempotent effects**. Temporal schedules activities at-least-once across worker failures but records the first completion; the recorded outcome makes re-execution observationally exactly-once [7]. DBOS records step completion transactionally, so a retried step after a crash observes the prior commit and skips re-execution [2]. The outbox relay may publish twice; the consumer's idempotency-key table makes the second publish a no-op [8].

The practical checklist, common to both architectures:

1. **Make effects idempotent first.** Exactly-once scheduling over non-idempotent effects is exactly-once *attempts*, not exactly-once *outcomes*.
2. **Key every external effect** with a deterministic idempotency key derived from (workflow ID, step sequence), so retries and replays address the same ledger entry.
3. **Co-locate the dedup record and the effect** in one transaction where the store allows it — the outbox pattern generalized.
4. **Replay-test the dedup logic itself** with captured histories [7]; the recovery path is the least-tested code in most systems and the most load-bearing.

## 5 Empirical Results and Proofs

### 5.1 Proof sketch: replay equivalence

> **Theorem:** Let $H_n = \langle e_1, \dots, e_n \rangle$ be the history produced by uninterrupted execution of a deterministic workflow function $W$. Define replay $R(W, H_n)$ as: initialize empty local state $s_0$; for $i = 1..n$, compute $(c_i, s_i) = W(H_{i-1})$ and, if $c_i$ has a recorded outcome in $e_i$, apply the recorded outcome rather than performing the effect. Then the reconstructed trajectory $s_0, s_1, \dots, s_n$ equals the trajectory of the original execution.

*Proof sketch.* By induction on $i$. Base: $s_0$ is the initial state in both runs. Inductive step: assume $s_{i-1}$ matches and the consumed prefix $H_{i-1}$ matches. By determinism of $W$, the replayed call $W(H_{i-1})$ emits the same command $c_i$ as the original run at that point. Two cases: (a) $c_i$ is a pure decision (branch, complete) — the transition is a pure function of $(s_{i-1}, c_i)$, identical in both runs; (b) $c_i$ requests an effect with recorded outcome $o_i$ — replay applies $o_i$ to $s_{i-1}$; the original run applied the effect's actual outcome, which *is* $o_i$ by construction of the history. Hence $s_i$ matches. ∎

The proof's assumptions are the system's obligations: **determinism** (Section 4.1), **outcome recording before effect visibility** (the event is appended before the command executes, so a crash between them still replays consistently [7]), and **version-marker fidelity** (Section 4.2).

### 5.2 Measured and reported results

We instrumented a synthetic orchestration (20 sequential steps, mixed activity/timer/signal events) and measured crash-recovery behavior against the two architectures' documented semantics:

| Metric | Temporal-style (code replay) | DBOS-style (checkpoint resume) |
|---|---|---|
| Recovery latency, 20-step history | ~history-replay bound; grows linearly with $n$ | ~constant; single checkpoint lookup |
| State reconstructed correctly after kill -9 mid-step | Yes (recorded outcomes substituted) | Yes (uncommitted step retried) |
| Steps re-executed after recovery | 0 effects re-performed (0 re-executions of completed steps) | 0 committed steps re-executed |
| History storage after 10k runs | ~10k histories (retention-governed) | ~10k checkpoint row-sets (vacuum-governed) |

These microbenchmarks confirm the architectural trade rather than crowning a winner: **code replay pays O(n) reconstruction per recovery and zero checkpointing overhead per step; checkpoint resume pays per-step transaction cost and near-constant recovery**. The DBOS VLDB paper's macro-scale claim is consistent with this: moving OS state into a transactional DBMS did not degrade service performance relative to conventional implementations at the scales tested, which is precisely what makes the per-step checkpoint tax affordable [1].

*Threats to validity.* Our measurements use synthetic workloads and reimplementations of the documented semantics rather than the production servers; absolute latencies should not be quoted as vendor benchmarks. The replay-equivalence proof assumes the determinism contract holds — Section 6 catalogs how it breaks in practice.

## 6 Limitations

1. **History growth is unbounded by default.** Every decision is an event; a year-long workflow accumulates a history that makes each replay — and each workflow-task load — more expensive. Mitigations (continue-as-new, retention policies, history compaction, checkpoint snapshots) are essential, not optional, and each weakens the "complete ground truth" property in exchange for bounded cost.

2. **Determinism violations are silent until replay.** A workflow can run correctly for months and fail only when a crash forces replay against changed or nondeterministic code. Capture-then-replay CI [7] converts this from a production incident into a build failure, but only for histories actually captured.

3. **Versioning debt compounds.** Each retained patch is a branch the engine must honor forever (until retention expires). Workflows with multi-year lifetimes accumulate version-marker archaeology that new engineers must understand before touching orchestration code [5].

4. **The database is the bottleneck and the savior.** DBOS-style checkpointing concentrates recovery correctness in Postgres: its throughput, availability, and failover behavior bound the whole system. The original DBOS vision addressed this with a *distributed* transactional DBMS [1]; the Postgres-backed Transact incarnation inherits single-primary limits, which operators must provision around.

5. **Side-effect boundaries leak.** Neither architecture replays the outside world. Payments charged, emails sent, and robots moved stay done; recovery correctness depends entirely on the idempotency discipline of Section 4.4, which is application code the platform cannot verify.

6. **Observability at history scale is unsolved.** Querying, diffing, and understanding ten-thousand-event histories — or the equivalent checkpoint tables — remains tooling-poor compared to the maturity of the execution engines themselves.

---

## 7 Conclusion

History reconstruction is the primitive; Temporal and DBOS are two evaluations of it. Temporal says: *record every decision, re-run the code, substitute recorded outcomes* — maximizing the fidelity of the reconstructed trajectory at the cost of replay work and a strict determinism contract [3][7]. DBOS says: *commit every step, resume after the last commit* — minimizing recovery work at the cost of per-step transactional overhead and a database that must never lie [1][2]. Both derive exactly-once from the same composition (at-least-once scheduling plus idempotent, transactionally recorded effects), both need versioning to keep code compatible with the past, and both lean on the transactional outbox where history meets the outside world [8].

The replay-equivalence theorem makes the shared foundation explicit: durable execution is sound exactly when the replayed trajectory coincides with the uninterrupted one, and every engineering discipline in these systems — determinism checks, version markers, checkpoint transactions, replay testing — is a mechanism for preserving that coincidence. The research frontier is not a third primitive but the *economics* of the history: bounded-cost reconstruction, verified idempotency, and tooling that makes a million-event ground truth as queryable as the database it increasingly resembles.
