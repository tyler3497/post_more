# RDMA and Kernel-Bypass Networking for Distributed Systems: Verbs, Congestion Control, and One-Sided Disaggregation

## Abstract

Remote Direct Memory Access (RDMA) has become the dominant interconnect for large-scale datacenter systems, underpinning high-throughput key-value stores, disaggregated storage fabrics, and GPU-centric AI clusters. By moving the transport stack from the host CPU into the Host Channel Adapter, RDMA delivers single-digit microsecond latencies and line-rate bandwidth with near-zero CPU involvement, reshaping distributed consensus, replication, and memory disaggregation. This thesis presents the RDMA verbs architecture — queue pairs, completion queues, and memory registration — and characterizes one-sided READ, WRITE, and atomic operations enabling CPU-bypassing remote memory access. We analyze the shift from InfiniBand to routable RDMA over Converged Ethernet v2, where the absence of lossless link-layer flow control demands end-to-end congestion control, and detail Data Center Quantized Congestion Notification (DCQCN): its rate-update dynamics, stability, and pathologies under large-scale incast. Finally, we examine RDMA for disaggregated storage and far memory using production measurements and research prototypes, establishing RDMA as an architectural primitive that restructures how distributed systems reason about locality, failure, and coordination.

## 1. Introduction

The classical datacenter network stack — TCP/IP over Ethernet with interrupt-driven packet processing — imposes per-packet CPU costs that scale poorly with link rates. As per-link bandwidth climbed from 10 GbE to 400 GbE, the *bandwidth-delay-CPU* tension became acute: a single 400 Gbps link can deliver roughly 50 million packets per second at small message sizes, far exceeding what a kernel IP stack can service per core without head-of-line latency inflation and cache thrash [1]. Remote Direct Memory Access attacks this problem at its root by relocating the entire transport protocol — segmentation, acknowledgment, retransmission, flow control — from the kernel into specialized NIC hardware, the Host Channel Adapter (HCA).

The consequence is twofold. First, **kernel bypass**: applications post work requests directly to hardware queues via memory-mapped doorbells, eliminating system calls, interrupts, and data copies from the I/O path. Measurements from production clusters report ~1.7 µs latency for one-sided RDMA READ/WRITE operations, versus ~25.4 µs for an equivalent TCP transfer on the same fabric — an order-of-magnitude gap that is *qualitative*, not merely quantitative [1]. Second, **CPU bypass on the data path**: one-sided verbs allow an initiator to read or write remote application memory without involving the responder's CPU at all, breaking the request-response paradigm that has dominated distributed systems design since the inception of RPC.

These two properties have catalyzed an architectural shift. Systems such as FaRM [2] and Pilaf [3] rebuilt distributed storage around one-sided reads, replacing multi-round RPC protocols with direct remote memory inspection. The emergence of RDMA over Converged Ethernet v2 (RoCEv2) extended RDMA beyond proprietary InfiniBand fabrics into IP-routed datacenter networks, exposing congestion control as a first-class design problem and producing DCQCN [1], the dominant rate-based scheme in Microsoft's datacenters. More recently, RDMA has become the substrate of memory disaggregation and the backend of GPU collectives (NCCL) in AI training.

Section 2 covers the verbs model, §3 the methodology, §4 the deep dive (data path, one-sided protocols, DCQCN, disaggregation), §5 empirical results, §6 limitations, and §7 conclusions.

## 2. Background

### 2.1 The RDMA Verbs Programming Model

The RDMA verbs API exposes the HCA as a set of **queue pairs (QPs)**. A QP consists of a send queue (SQ) and a receive queue (RQ); applications post *work requests* (WRs) to these queues, and the HCA executes them asynchronously via DMA. Completions are reported through **completion queues (CQs)** as completion queue entries (CQEs) retrieved by polling (`ibv_poll_cq`), a design that deliberately avoids interrupts to preserve tail latency [8].

Three transport types dominate practice:

- **Reliable Connection (RC):** connection-oriented, ACKed, packet-ordered delivery with hardware retransmission. Supports all verbs including one-sided READ/WRITE and atomics. The workhorse of datacenter deployments.
- **Unreliable Connection (UC):** connection-oriented but unacknowledged; supports WRITE and SEND only, permitting loss.
- **Unreliable Datagram (UD):** connectionless, multicast-capable, message-oriented with a 4 KB practical MTU ceiling; used for connection setup and control planes.

Before any transfer, buffers must be **registered** with the HCA (`ibv_reg_mr`), pinning physical pages and installing virtual-to-physical translations in the NIC's memory translation tables. Registration returns a local key (*lkey*) and remote key (*rkey*); the rkey is the capability token that authorizes remote one-sided access. This capability model is central to RDMA security: *whoever holds the rkey can read or write the region without further CPU mediation*.

> **Theorem (Zero-Copy Completion):** For a posted SEND of *n* bytes over an established RC QP, the number of CPU-initiated data copies is zero, and the number of kernel transitions is zero, provided the buffer is pre-registered and the CQ is polled in user space. *Proof sketch.* The WR references the registered buffer by lkey; the HCA performs DMA from user pages directly to the wire. No system call occurs after doorbell write; no interrupt is raised on completion. ∎

### 2.2 InfiniBand to RoCE: The Fabric Transition

Native InfiniBand provides a lossless link layer via hop-by-hop credit-based flow control: a transmitter never sends unless the receiver has posted buffer credits, making buffer-overflow loss structurally impossible [1]. This is what permits the RC transport to be simple and efficient.

Modern datacenters, however, are built on IP/Ethernet. **RoCEv2** encapsulates InfiniBand transport packets inside UDP/IP datagrams (UDP destination port 4791), making RDMA traffic routable across L3 fabrics [8]. Ethernet is natively lossy, so RoCEv2 must *reconstruct* losslessness:

| Mechanism | Layer | Function |
|---|---|---|
| PFC (IEEE 802.1Qbb) | L2 | Priority-based pause frames; hop-by-hop backpressure per traffic class |
| ECN (RFC 3168) | L3 | Switch marks CE bits when queue exceeds threshold; proactive signal |
| CNP | Endpoint | Receiver notifies sender of congestion via Congestion Notification Packet |
| DCQCN | Endpoint | Rate-based controller: AIMD-style reaction to CNP arrivals |

PFC acts as an emergency brake, ECN/CNP as the proactive control loop, and DCQCN as the rate adaptation law. The interaction — and pathology — of these layers is the subject of §4.3.

### 2.3 One-Sided vs. Two-Sided Semantics

Two-sided verbs (SEND/RECEIVE) follow the message-passing model: the receiver must pre-post receive buffers, and its CPU is involved in matching and completion. One-sided verbs — READ, WRITE, and the 64-bit atomics (Fetch-and-Add, Compare-and-Swap) — carry the target virtual address, rkey, and length in the request itself; the responder's HCA executes the DMA *without waking the responder's CPU* [2][3]. This asymmetry is the defining capability of RDMA and the basis of the CPU-bypass designs surveyed in §4.2.

## 3. Methodology

Our analysis synthesizes three evidentiary sources. **(i) Production measurements:** published microbenchmarks from Microsoft's RDMA deployment [1], including the canonical 2 KB latency comparison (TCP 25.4 µs vs. RDMA 1.7 µs READ/WRITE) and DCQCN convergence traces under incast. **(ii) System prototypes:** FaRM [2], Pilaf [3], LegoOS [7], and NVMe-over-Fabrics deployments. **(iii) Analytical models:** the DCQCN rate-update equations and fluid-model stability analysis from [1], plus the many-to-one queueing analysis of incast collapse from [6].

All latency figures cited are user-level, measured with sub-microsecond timers on otherwise idle fabrics unless noted. We deliberately avoid extrapolating across NIC generations; where a claim depends on hardware behavior (e.g., atomic throughput), we state the NIC class.

## 4. Deep Dive

### 4.1 The Verbs Data Path: From Doorbell to Wire

A one-sided RDMA READ traverses the following pipeline, with approximate per-stage latencies on a ConnectX-class NIC:

1. **Post (user space, ~100 ns):** the application writes a WR into the SQ's memory-mapped work queue element (WQE) ring and rings the doorbell via an MMIO write (`ibv_post_send`).
2. **Fetch and translate (~200 ns):** the HCA DMAs the WQE, walks the memory translation table for the lkey, and validates the rkey against the remote region's protection domain.
3. **Packetize and inject (~300 ns):** the request is segmented into MTU-sized packets (typically 4 KB for IB, jumbo for RoCE), each carrying the base transport header (BTH) with destination QPN and packet sequence number (PSN).
4. **Wire transit:** propagation plus switch queueing; ~300 ns per hop in an uncongested Clos fabric.
5. **Responder HCA (~500 ns):** the responder NIC validates PSN ordering, performs the DMA read from host memory, and returns response packets — *with no CPU involvement*.
6. **Completion (~100 ns):** the initiator HCA DMAs payload into the registered buffer and posts a CQE to the CQ.

The total, ~1.5–2 µs intra-rack, is dominated by PCIe DMA round trips and wire propagation rather than software. Contrast with the TCP path: system call entry, socket buffer copy, IP stack processing, interrupt coalescing, and two context switches, each adding microseconds [1].

```c
/* One-sided RDMA READ: no remote CPU involved */
struct ibv_sge sge = {
    .addr   = (uint64_t)local_buf,
    .length = len,
    .lkey   = mr->lkey,
};
struct ibv_send_wr wr = {
    .wr_id      = READ_ID,
    .opcode     = IBV_WR_RDMA_READ,
    .sg_list    = &sge,
    .num_sge    = 1,
    .wr.rdma    = { .remote_addr = remote_va, .rkey = remote_rkey },
};
ibv_post_send(qp, &wr, &bad_wr);   /* doorbell: ~100ns, no syscall */
```

Memory registration is the costly step: `ibv_reg_mr` pins pages and programs the NIC's translation cache in tens of microseconds. Production systems amortize it with registration caches and huge pages.

### 4.2 One-Sided Operations and the Restructuring of Distributed Protocols

One-sided verbs invert the classical assumption that *accessing remote state requires remote computation*. The design consequences are profound:

- **Lock-free remote data structures.** Pilaf [3] demonstrated a key-value store where GETs are pure one-sided READs against self-verifying hash-table buckets: the client reads a bucket, validates a checksum, and retries on mismatch — no server CPU per read. FaRM [2] extended this to transactions, using RDMA atomics for lock acquisition and one-sided reads/writes for the data plane, achieving ~2 Mops/s per machine with 35 µs 99th-percentile transaction latency.
- **Consensus without message handlers.** One-sided WRITE enables *RDMA-based replication* where the primary writes log entries directly into followers' memory; followers' CPUs merely poll for new entries. This eliminates the interrupt and dispatch latency of the follower's network stack from the critical path of commit.
- **The atomicity gap.** One-sided operations are atomic only at 8-byte granularity via the NIC's atomic unit (Fetch-and-Add, Compare-and-Swap). Multi-word atomicity must be constructed in software — e.g., FaRM's versioned reads with optimistic concurrency — and NIC atomic throughput (typically ~1–10 Mops/s) becomes the bottleneck for contended locks, a fact that has driven hybrid designs combining one-sided data access with two-sided control messages [2].

The programming burden is real: without a remote CPU to enforce invariants, every remote memory layout becomes a concurrent data structure shared with an adversarial scheduler. Memory-model reasoning — ordering between a one-sided WRITE and a subsequent flag update — must be made explicit with RDMA fencing and the (weak) ordering guarantees of the verbs specification.

### 4.3 RoCEv2 Congestion Control: The DCQCN Dynamics

Because RoCEv2 runs over lossy Ethernet, congestion control is not optional: an uncontrolled incast of RDMA flows will overflow switch buffers, trigger PFC storms, and — through PFC's head-of-line blocking — stall *unrelated* traffic classes across the fabric (the well-known *PFC deadlock* and *victim flow* problems) [6].

**DCQCN** [1] is a rate-based, end-to-end scheme with three cooperating components:

1. **Congestion Point (CP):** the switch. When the egress queue exceeds a RED threshold (*K_min* = 5 KB, *K_max* = 200 KB typical [6]), the switch sets the ECN Congestion-Experienced bits.
2. **Notification Point (NP):** the receiver. Upon receiving ECN-marked packets, the receiver generates a Congestion Notification Packet (CNP) back to the sender, rate-limited to at most one CNP per ~50 µs per flow to bound feedback overhead.
3. **Reaction Point (RP):** the sender NIC. Each flow maintains a target rate *R_T*, current rate *R_C*, and byte counter. On CNP arrival, the RP executes a multiplicative decrease; absent CNPs, it performs staged additive increase and fast recovery.

The update law, per CNP epoch, is:

> **DCQCN rate update:** let *R_T* be the target rate and *R_C* the current rate. On receiving a CNP: *R_T ← R_C*, *R_C ← R_C·(1 − α/2)*, where *α* is an EWMA of the fraction of marked bytes (*α ← (1−g)·α + g·F*, *F* the marked fraction, *g* the estimation gain). On timer expiry without CNP: fast recovery *R_C ← (R_C + R_T)/2*, then additive increase *R_T ← R_T + R_AI*, *R_C ← (R_C + R_T)/2*, and hyper-increase stages thereafter [1].

This law converges to max-min fairness in the fluid limit with fast convergence and low queue oscillation — *provided* feedback delay is small relative to the control epoch. Its Achilles' heel is **large-scale incast**: when hundreds of senders converge on one receiver, CNP feedback arrives too late and too coarsely; DCQCN cannot suppress the aggregate burst before buffers overflow, and PFC engages. DCQCN+ [6] addresses this by making the rate reduction proportional to an estimate of incast scale, and subsequent schemes — TIMELY [4] (RTT-gradient based, no switch support needed), HPCC [5] (in-network telemetry with precise per-hop queue information), and IRN (loss-tolerant NIC transport eliminating PFC) — each attack a different corner of the design space:

| Scheme | Signal | Switch support | Key strength |
|---|---|---|---|
| DCQCN [1] | ECN + CNP | RED+ECN only | Deployable on commodity switches; Microsoft production |
| TIMELY [4] | RTT gradient | None | No switch config; robust to incast |
| HPCC [5] | INT telemetry | INT-capable | Fast, precise convergence; needs programmable switches |
| DCQCN+ [6] | ECN + CNP, scale-aware | RED+ECN | Fixes large-incast collapse of DCQCN |
| IRN | Loss as signal | None | Eliminates PFC entirely; efficient loss recovery |

> **Theorem (DCQCN stability, informal):** In a single-bottleneck fluid model with homogeneous RTTs, the DCQCN update law is locally asymptotically stable around the fair-rate equilibrium for gains *g* below a threshold depending on the bandwidth-delay product, and queue occupancy converges to a neighborhood of *K_min*. *The practical caveat:* heterogeneity in RTTs and incast fan-in violate the model assumptions, producing the oscillations documented in [5][6]. ∎

### 4.4 RDMA for Disaggregated Storage and Far Memory

Disaggregation separates compute from memory and storage at rack scale, and RDMA is its interconnect of choice for three reasons: (i) one-sided access matches the *remote memory* abstraction exactly; (ii) microsecond latency keeps the far-memory penalty within a tolerable factor of local DRAM (~100 ns → ~2 µs, vs. ~80 µs for NVMe SSD); (iii) zero-copy semantics preserve the page-cache abstraction across the network.

**NVMe over Fabrics (NVMe-oF)** standardizes remote block access over RDMA, allowing a host to address remote SSDs through the same submission/completion queue pair abstraction as local NVMe, with the fabric (RDMA, Fibre Channel, or TCP) abstracted beneath [9]. Production measurements show end-to-end 4 KB read latencies in the tens of microseconds over RoCEv2 — competitive with local SSDs once queueing is accounted for.

**Memory disaggregation** goes further: systems like LegoOS [7] split the OS itself, running a *monitor* on memory nodes that services one-sided RDMA requests for virtual-memory paging, effectively making remote DRAM a slower tier in the page hierarchy. The research frontier — CXL-attached memory pools and RDMA-backed far-memory allocators — inherits RDMA's unresolved problems: protection (rkeys as capabilities are coarse), failure semantics (what does a one-sided READ observe during a remote crash?), and congestion under memory-pressure incast.

## 5. Empirical Results / Proofs

The empirical case for RDMA rests on a small number of widely reproduced measurements:

1. **Latency.** On 40/56 Gbps fabrics, one-sided READ/WRITE complete in ~1.7 µs user-to-user for 2 KB messages, versus ~25.4 µs for TCP and ~2.8 µs for two-sided SEND [1]. The gap persists across generations: at 100/200 Gbps, one-sided small-message latency remains in the 1–3 µs band while kernel-stack latency is dominated by software overhead that does not shrink with link rate.
2. **Throughput and CPU efficiency.** A single RC QP saturates 100+ Gbps with negligible sender/receiver CPU; the same throughput over TCP consumes multiple cores. FaRM reports 11 M lookups/s per machine with one-sided reads [2].
3. **DCQCN convergence.** In dumbbell experiments with two elephant flows, DCQCN converges to fair rates within hundreds of microseconds with queue occupancy near *K_min*; under 3-to-1 incast, DCQCN exhibits persistent rate oscillation while telemetry-based HPCC converges smoothly [5]. Beyond hundreds of concurrent incast flows, DCQCN fails to prevent PFC triggering, motivating DCQCN+ [6].
4. **Incast collapse threshold.** Measurements show DCQCN's control loop stable for tens of flows but degrading superlinearly past ~100 synchronized senders, where aggregate burst exceeds the *K_max* − *K_min* absorption window before CNP feedback can react [6].
5. **Disaggregation overhead.** NVMe-oF over RoCEv2 adds single-digit microseconds over local NVMe for 4 KB random reads in uncongested fabrics [9]; LegoOS reports remote page-fault service within ~10 µs over RDMA versus ~100+ µs for disk-backed swap [7].

*Proof sketch (one-sided read linearizability).* Consider a register implemented as a single 8-byte cell accessed via RDMA READ/WRITE on an RC QP. RC guarantees per-QP ordering and at-most-once delivery; the NIC executes each verb atomically on the same cell. Hence every READ observes the latest preceding WRITE in RC order — i.e., linearizable. Multi-word registers require versioning (§4.2) since the NIC provides no multi-word atomicity. ∎

## 6. Limitations

RDMA's advantages are purchased with significant costs, and several are structural rather than transient:

- **Lossless fabric fragility.** RoCEv2's dependence on PFC creates *congestion spreading*: a pause frame halts an entire priority class on a link, punishing innocent flows (head-of-line blocking) and, in pathological topologies, causing PFC deadlock. IRN's loss-tolerant approach [5] suggests the lossless requirement itself may be the wrong invariant.
- **Security and isolation.** The rkey capability model is coarse: any holder can read/write the entire region, and rkeys have historically been guessable or leaked. Multi-tenant RDMA demands memory protection keys, QP-level isolation, and encryption that remain inconsistently deployed.
- **CPU-bypass programmability tax.** One-sided designs push concurrency control into application code over weak memory models; debugging a torn read across a one-sided WRITE is strictly harder than debugging an RPC handler. The ecosystem lacks mature formal tooling for verbs-level concurrency.
- **Connection scalability.** RC QPs carry per-connection state on the NIC; all-to-all RC meshes scale as *O(n²)* in NIC memory, motivating shared receive queues, DCT (dynamic connected transport), and UD-based designs at warehouse scale.
- **Congestion control heterogeneity.** DCQCN, TIMELY, and HPCC make mutually incompatible assumptions (ECN vs. RTT vs. INT); a fabric mixing NIC generations cannot run a single optimal scheme, and fallback interactions are poorly understood.
- **Failure semantics.** A one-sided READ to a crashed peer returns a transport error, not a clean exception; exactly-once and fencing semantics for RDMA-based replication remain active research.

## 7. Conclusion

RDMA has evolved from a high-performance computing interconnect into the foundational primitive of datacenter distributed systems. The verbs model — queue pairs, completion queues, and memory registration — provides a hardware-executed transport with single-digit microsecond latency and zero CPU involvement on the data path. One-sided READ, WRITE, and atomic operations have restructured distributed protocol design, enabling CPU-bypassing key-value stores, replication, and disaggregated memory whose performance was previously unattainable. The migration to RoCEv2 exchanged InfiniBand's lossless link layer for routability, elevating congestion control — DCQCN and its successors — to a central architectural concern with well-characterized dynamics and well-documented failure modes under incast.

The trajectory is clear: as memory disaggregation, GPU-centric collectives, and far-memory computing mature, RDMA's one-sided primitives will increasingly serve as the *narrow waist* of distributed systems — the minimal mechanism over which storage, memory, and coordination are built. The open problems are no longer primarily about raw performance but about the *systems properties* of a CPU-bypassing world: protection, isolation, failure semantics, and congestion behavior at warehouse scale. Solving them will determine whether RDMA remains a fast network or becomes, as the evidence increasingly suggests, the memory bus of the datacenter.
