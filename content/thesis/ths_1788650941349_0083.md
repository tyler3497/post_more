# Zero-Copy Serialization Frameworks: Cap'n Proto, FlatBuffers, and rkyv with Arena Allocation and Schema Evolution

## Abstract

Zero-copy deserialization removes the parse-and-allocate phase of traditional serialization pipelines by making the wire format identical to the in-memory representation, so that "deserialization" collapses to a pointer cast plus bounds validation. This thesis develops a rigorous comparative treatment of three production-grade zero-copy frameworks—Cap'n Proto [1][2], FlatBuffers [3], and rkyv [4][5]—unifying their designs under a common formal model of *memory-isomorphic encoding*. We analyze Cap'n Proto's segmented message layout and capability-based RPC with promise pipelining; FlatBuffers' vtable-indirected tables and forward offset arithmetic; and rkyv's archived types with relative pointers and bytecheck validation. We give a precise account of schema evolution as a monotone compatibility lattice, characterize the role of arena (bump) allocation in achieving deterministic zero-copy construction, and report empirical comparisons against Protocol Buffers showing an order-of-magnitude reduction in deserialization latency at comparable or smaller wire sizes. The treatment closes with a candid discussion of limitations: alignment waste, untrusted-buffer validation costs, and the fundamental tension between maximal evolution freedom and layout canonicity.

---

## 1 Introduction

Serialization mediates between the structured, pointer-rich world of in-memory data and the flat, sequential world of storage and networks. Traditional frameworks—Protocol Buffers, JSON, MessagePack—adopt a *parse-then-materialize* architecture: a buffer is traversed once to build an object graph of freshly allocated nodes, and a second phase copies those nodes into application structures. The cost is dominated not by bytes on the wire but by **allocation, cache misses, and pointer chasing** during decode [9].

Zero-copy frameworks invert this design. They constrain the in-memory layout *at construction time* so that the serialized byte stream is already a valid, traversable in-memory object. Decoding then requires no allocation at all: the application simply validates the buffer (optionally) and follows the pointers embedded in it. Three systems exemplify three distinct points in this design space:

1. **Cap'n Proto** [1] — segmented messages, a unified pointer vocabulary (struct, list, far, capability pointers), explicit schema evolution numbering, and a capability-secure RPC layer with promise pipelining.
2. **FlatBuffers** [3] — reverse-order construction, tables indirected through shared virtual tables (vtables), offset-relative addressing, and aggressive support for forward-compatible field addition.
3. **rkyv** [4][5] — a Rust-native framework in which every type `T` has an *archived* counterpart `Archived<T>` with identical layout; archived values are produced by serializing into an aligned arena and validated by the `bytecheck` derive.

These systems share one deep principle—*the wire format must be a subset of valid machine-addressable memory*—but differ sharply in how they handle pointer relocation, schema evolution, and validation. This thesis gives the first side-by-side formalization of all three, grounded in verified documentation and benchmark evidence [2][3][4][6].

## 2 Background

### 2.1 The cost model of classical deserialization

In a parse-based decoder, deserializing a message of $n$ fields costs $\Theta(n)$ allocations in the worst case, each an independent trip to the allocator, plus $\Theta(n)$ cache misses as the newly built graph is scattered across the heap. For large messages this dominates end-to-end latency. A now-standard back-of-the-envelope comparison for one million graph nodes reports Cap'n Proto at ~0 µs of decode time versus 380 ms for Protocol Buffers and 980 ms for JSON—figures reported in independent engineering evaluations of the two designs [9]. The gap is not an artifact of implementation polish; it is structural, and it motivates the memory-isomorphic encodings studied here.

### 2.2 Pointer relocation and the zero-copy contract

A zero-copy buffer cannot contain raw machine pointers, which are meaningless outside the process that created them. Each framework therefore defines a **relativization**: a rule for rewriting pointers into buffer-relative offsets that can be resolved with a single addition at read time.

- Cap'n Proto segments each message into independently addressable 8-byte-word arrays; intra-segment pointers are word offsets, and cross-segment references use *far pointers* [8].
- FlatBuffers builds the buffer backwards from a single root offset, so every reference is a forward `uoffset_t` (unsigned 32-bit) relative to the referrer, with vtables excepted as the one explicitly backwards offset (`soffset_t`) [3].
- rkyv places archived data in a single aligned allocation and stores all pointers as relative offsets resolved by adding the stored delta to the field's own address [4].

> **Lemma (Relativization soundness):** If every reference stored in a buffer is a buffer-relative offset $\delta$ such that $\text{target} = \text{referrer} + \delta$ and $\text{target}$ lies within the validated extent of the buffer, then traversal of the buffer terminates and never escapes the buffer. Each of the three frameworks enforces a variant of this invariant at construction time; rkyv additionally enforces it at *read* time via bytecheck validation [5].

### 2.3 Arena (bump) allocation

All three frameworks rely, at least optionally, on **arena allocation**: a large contiguous region from which construction requests are satisfied by advancing a bump pointer, with no per-object bookkeeping and a single bulk free. This yields three properties essential to zero-copy construction:

1. *Contiguity* — the final buffer is one extent, so a single `mmap` or `sendfile` moves it.
2. *Alignment control* — the arena allocator enforces the maximum alignment required by the format (8-byte words for Cap'n Proto, per-scalar alignment for FlatBuffers, type alignment for rkyv).
3. *Deterministic cost* — allocation is $O(1)$ amortized pointer arithmetic.

```rust
// Conceptual bump arena: allocation is pointer arithmetic, not a search.
pub struct BumpArena {
    base: *mut u8,
    cursor: usize,
    capacity: usize,
}

impl BumpArena {
    pub fn alloc(&mut self, size: usize, align: usize) -> *mut u8 {
        let aligned = (self.cursor + align - 1) & !(align - 1);
        assert!(aligned + size <= self.capacity, "arena exhausted");
        let ptr = unsafe { self.base.add(aligned) };
        self.cursor = aligned + size;
        ptr
    }
    pub fn reset(&mut self) { self.cursor = 0; } // single bulk free
}
```

FlatBuffers' `FlatBufferBuilder` is internally a backwards-growing arena [3]; Cap'n Proto builders allocate from growable *segment arenas* [8]; rkyv serializes directly into any `&mut [MaybeUninit<u8>]` arena and records the final aligned extent as the archive.

## 3 Methodology

Our analysis proceeds in three stages, designed for reproducibility:

1. **Specification mining.** We ground every claimed format property in primary documentation: the Cap'n Proto schema-language reference for evolution numbering [2], the FlatBuffers internals document for vtable layout and offset semantics [3], and the rkyv book and API documentation for archived-type guarantees [4][5]. Secondary corroboration comes from the Rust serialization benchmark suite [6], which contains dedicated zero-copy shootouts, and from independent engineering write-ups [7][8][9][10].
2. **Formal modeling.** We express wire layouts as transition systems over byte extents and prove (in prose, with the key invariants stated as theorems) that (a) construction preserves the buffer-containment invariant, (b) evolution rules are monotone with respect to reader compatibility, and (c) validation is decidable in linear time in the buffer size.
3. **Empirical comparison.** We synthesize published benchmark evidence [6][9] into a unified table of serialize size, decode latency, and allocation counts, comparing each framework against a Protocol Buffers baseline on equivalent message shapes.

Scope is deliberately restricted to *in-process, same-machine* zero-copy semantics and schema evolution; we do not evaluate network transport layers except where Cap'n Proto's RPC is integral to the design [1][7].

## 4 Deep Dive

### 4.1 Cap'n Proto: segments, pointers, and capability RPC

A Cap'n Proto message is a sequence of **segments**, each a flat array of 8-byte words. The message begins with a segment table (a count followed by per-segment word lengths); the root pointer follows. Every value is addressed through a uniform 64-bit pointer vocabulary: struct pointers (offset + data/pointer section sizes), list pointers (offset + element size + count, with composite lists for structs), far pointers (landing pad + segment id + offset for cross-segment references), and capability pointers (indices into a per-message capability table) [8].

Structs split into a **data section** (scalars packed by size, defaulted fields omitted) and a **pointer section** (lists, blobs, nested structs, capabilities). Because data-section fields live at schema-computed fixed offsets, reading a scalar is one indexed load—no parse, no branch:

```python
# Logical model of a Cap'n Proto struct read (illustrative).
def read_struct_field(segment: bytes, struct_offset: int, field_word_offset: int) -> int:
    # struct pointer -> (data_offset, data_words); field is words[data_offset + field_word_offset]
    lo = struct_offset + 8 * field_word_offset
    return int.from_bytes(segment[lo:lo + 8], 'little')
```

Cap'n Proto's distinguishing feature among the three is its **capability-based RPC** [1][7]. Interfaces are first-class schema types; object references cross the network as *capabilities*—unforgeable references that carry both designation and authority. The protocol supports **promise pipelining**: a client may issue a call on the *result* of a previous call before the first call returns, collapsing dependent round trips into one. This is not mere serialization; it is a distributed object system in which the wire format's zero-copy property makes message construction and dispatch nearly free [7][8].

### 4.2 FlatBuffers: vtables and offset arithmetic

FlatBuffers takes the opposite construction strategy: the buffer is built **backwards**, from the highest address downward, so that when any object is written, everything it refers to already exists at a known, higher address. Every reference is then a forward unsigned 32-bit offset (`uoffset_t`)—the format is binary-compatible between 32- and 64-bit hosts by construction [3].

The signature mechanism is the **vtable**. Each table begins with a signed offset (`soffset_t`) that is *subtracted* from the table start to locate its vtable—the one deliberately backwards offset in the format. The vtable's first two `voffset_t` (uint16) entries are the vtable byte size and the inline object size; the remaining entries map schema field ordinals to byte offsets within the table, or 0 for absent fields [3]:

| vtable entry | type | meaning |
|---|---|---|
| 0 | `voffset_t` | vtable size in bytes |
| 1 | `voffset_t` | table inline size in bytes |
| 2…N+1 | `voffset_t` | field offsets (0 = absent → use default) |

Generated accessors embed the field's vtable index as a compile-time constant and bounds-check it against the vtable size, which is exactly the mechanism that makes **newer code reading older data** safe: an out-of-range index or a zero entry yields the schema default [3]. Vtables are deduplicated across tables with identical layouts, so the per-object overhead collapses toward the shared table in homogeneous collections.

A subtle consequence of reverse construction is that *structs* (as opposed to tables) are stored inline with a fixed, compiler-independent layout, and are the right choice for small, version-stable data such as 3D vectors—while *tables* pay the vtable indirection for evolution freedom [3].

### 4.3 rkyv: archived types, relative pointers, and bytecheck

rkyv's insight is to make zero-copy a **type-level** property. For every serializable type `T: Archive`, the derive macro generates `Archived<T>`—a `#[repr(C)]` type whose layout is a valid in-memory representation of the value. Serializing `T` into an aligned arena produces bytes that *are* an `&Archived<T>`; deserialization is a cast. Pointers inside the archive are relative: a field stores a signed offset that, added to the field's own address, yields the target [4].

```rust
use rkyv::{Archive, Serialize, Deserialize, to_bytes, archived_root};

// The derive generates ArchivedPoint: { x: Archived<i32>, y: Archived<i32> }
// with layout-identical, pointer-free representation.
#[derive(Archive, Serialize, Deserialize, Debug, PartialEq)]
struct Point { x: i32, y: i32 }

fn roundtrip() {
    let value = Point { x: 3, y: 4 };
    let bytes = to_bytes::<rkyv::rancor::Error>(&value).unwrap();
    // Zero-copy access: no allocation, just a validated cast.
    let archived = rkyv::access::<ArchivedPoint, rkyv::rancor::Error>(&bytes).unwrap();
    assert_eq!(archived.x, 3);
}
```

Because a cast is *unsafe* on untrusted bytes, rkyv pairs archiving with **bytecheck**: a derived validator that walks the buffer once, confirming that every offset lands inside the buffer, every discriminant is valid, and every archived invariant holds—linear time, zero allocation [5]. The ecosystem splits concerns into focused crates: `rend` for endian-agnostic primitives, `bytecheck` for validation, `rancor` for error handling, and `ptr_meta` for pointer manipulation [4].

### 4.4 Schema evolution as a monotone compatibility lattice

All three frameworks define evolution rules that old readers can apply to new data and new readers to old data. The rules differ in strictness, but they share a monotone structure:

**Cap'n Proto** requires fields to be numbered consecutively from zero *in the order added*; numbers may never be skipped or reused. Reads past a struct's data section return schema defaults, and the reference implementation supports upgrading primitive lists to struct views [2][8]. This yields the strongest guarantee of the three: a total order on field introduction that the compiler can verify.

**FlatBuffers** identifies fields by vtable slot; adding a field appends a vtable entry, and old readers simply never index it. Fields may not be removed (their slot must remain, or the vtable layout shifts); changing a field's type is permitted only when the wire representation is identical [3].

**rkyv** is the least schema-oriented: archived layout follows the Rust type definition, so evolution is governed by type-level versioning (explicit versioned enums/structs) rather than field ordinals. This trades automatic compatibility for zero overhead and full type-system integration [4].

> **Theorem (Evolution monotonicity):** Let $R_v$ be a reader compiled against schema version $v$ and $D_w$ data written under version $w \ge v$. If every change from $v$ to $w$ is an *additive* change (new numbered fields with defaults, new vtable slots, new enum variants appended), then $R_v(D_w)$ terminates and agrees with $R_w(D_w)$ on all fields of version $v$. *Proof sketch:* additive changes only extend the readable extent (larger data sections, longer vtables, wider archives); readers compiled at $v$ index a prefix of the extended layout, and all newly addressable regions are guarded by explicit bounds/default checks in each framework's accessor contract [2][3][5].

The practical corollary is the compatibility matrix:

| change | Cap'n Proto | FlatBuffers | rkyv |
|---|---|---|---|
| add field with default | ✅ safe | ✅ safe | ⚠️ manual versioning |
| remove field | ❌ (reserve number) | ❌ (keep slot) | ⚠️ manual |
| change field type | ❌ unless layout-identical | ❌ unless wire-identical | ❌ layout changes |
| add enum variant | ✅ appended | ✅ appended | ⚠️ manual |
| rename field | ✅ (names not on wire) | ✅ | ✅ |

### 4.5 Arena allocation strategies compared

Construction-side allocation policy determines whether the zero-copy promise survives contact with a real allocator:

- **Cap'n Proto** builders allocate from *segment arenas* that grow by appending new segments; far pointers stitch segments together. This bounds copying on growth to the current segment and keeps the common single-segment case a single extent [8].
- **FlatBuffers'** `FlatBufferBuilder` grows a single backwards buffer with exponential reallocation; because construction proceeds from leaves to root, reallocation never invalidates already-written data—it only changes the base address, and all stored offsets are relative, so they survive the move [3].
- **rkyv** serializes into a caller-provided aligned buffer (or a `Vec` used as an arena) and supports `to_bytes` with scratch reuse across messages, amortizing allocation to zero in steady state [4][5].

```haskell
-- The arena discipline, expressed as a state transition (illustrative).
-- Allocating n bytes at alignment a in state (base, cursor) is pure arithmetic:
--
--   alloc (base, cursor) n a = let c' = alignUp cursor a
--                             in ((base, c' + n), base + c')
--
-- No search, no free-list, no fragmentation: the invariant "cursor is monotone"
-- is the entire allocator. Reset is O(1).
```

> **Lemma (Arena contiguity):** A message constructed entirely within one arena reset epoch occupies a single contiguous extent iff the arena never reallocates mid-message or all references are base-relative. FlatBuffers' backwards growth and rkyv's caller-provided buffers satisfy this directly; Cap'n Proto satisfies it per segment, with far pointers as the explicit escape hatch [3][4][8].

## 5 Empirical Results and Proofs

### 5.1 Benchmark evidence

The Rust serialization benchmark suite runs dedicated zero-copy shootouts including rkyv, measuring serialize throughput, deserialize latency, and output size across shared message shapes [6]. Independent engineering evaluations of Cap'n Proto against Protocol Buffers report the following representative figures for a one-million-node graph workload [9]:

| operation (1M nodes) | Cap'n Proto | Protocol Buffers | JSON |
|---|---|---|---|
| serialize | ~0 ms (build in place) | ~450 ms | ~1200 ms |
| deserialize | ~0 ms (pointer cast) | ~380 ms | ~980 ms |
| wire size | ~85 MB | ~65 MB | ~180 MB |

Three observations follow. First, decode latency is not merely reduced but *eliminated as a distinct phase*: it is $O(1)$ to obtain the root reader plus $O(1)$ per accessed field. Second, the wire-size penalty of alignment and metadata is modest—Cap'n Proto is larger than protobuf here but less than half the size of JSON. Third, these numbers are workload-sensitive: for tiny messages, fixed overheads (segment tables, vtables) can dominate, and packed/compact encodings may win [10].

### 5.2 Formal properties established

We collect the proven invariants:

1. **Traversal safety.** Under each framework's construction discipline, every stored reference resolves inside the buffer extent (Lemma, §2.2); rkyv additionally checks this on untrusted input in linear time [5].
2. **Evolution monotonicity.** Additive schema changes preserve reader compatibility across versions (Theorem, §4.4), with Cap'n Proto's consecutive-numbering rule giving the strongest static guarantee [2].
3. **Allocation complexity.** Construction is amortized $O(1)$ per allocation unit under arena discipline; steady-state rkyv serialization performs zero allocator calls [4].
4. **Validation decidability.** bytecheck validation is linear in buffer size with constant auxiliary space [5]; Cap'n Proto's traversal bounds-checking and FlatBuffers' vtable bounds-checking are likewise linear with small constants [2][3].

A TLA+-style sketch of the core safety argument makes the shared structure explicit:

```tla
---- MODULE ZeroCopy ----
EXTENDS Integers, Sequences
VARIABLES buf        \* the byte extent, a sequence of bytes
VARIABLES refs       \* stored references as (referrer, delta) pairs

InBounds(r) == LET t == r.referrer + r.delta
               IN t \in 1..Len(buf)

TypeInvariant == \A r \in refs : InBounds(r)

\* Construction preserves the invariant: every emitted reference
\* is computed as (target - referrer) with target inside the extent.
Init == TypeInvariant
Next == TypeInvariant'   \* no step may introduce an out-of-bounds ref
====
```

## 6 Limitations

No zero-copy design is free; the constraints that enable memory-isomorphism are also its costs.

1. **Alignment and metadata overhead.** Fixed alignments (8-byte words in Cap'n Proto, per-scalar alignment in FlatBuffers) waste bytes for small or oddly-sized fields, and vtables/segment tables add fixed per-message costs that dominate tiny payloads [3][8][10].
2. **Untrusted-buffer validation.** Zero-copy traversal of adversarial bytes is unsafe without validation; bytecheck pays a linear pre-pass [5], and Cap'n Proto/FlatBuffers readers must bounds-check every access—costs that partially erode the "0 µs" ideal on hostile input.
3. **Immutability and in-place update.** Zero-copy buffers are effectively read-only views; mutation requires either copy-on-write builders or full rebuilds, and FlatBuffers' reverse construction makes incremental appends awkward [3].
4. **Evolution ceilings.** None of the three supports *removing* a field without reservation overhead; rkyv offers no automatic evolution at all, pushing versioning into user types [4]. Cap'n Proto's no-skipped-numbers rule, while principled, forbids reserving ranges the way protobuf does [2].
5. **Endianness and portability.** FlatBuffers mandates little-endian with byte-swap shims on big-endian hosts [3]; rkyv's `rend` types provide endian-agnostic primitives at a small access cost [4].
6. **Ecosystem and codegen weight.** Cap'n Proto's RPC and plugin-based codegen are powerful but heavyweight for simple use cases [7]; rkyv is Rust-only, limiting polyglot deployments [4][5].

## 7 Conclusion

Cap'n Proto, FlatBuffers, and rkyv converge on a single architectural thesis: *make the wire format a valid memory image, and deserialization disappears*. They diverge instructively on the hard problems—pointer relocation (segments and far pointers vs. backwards offsets vs. relative archived pointers), schema evolution (consecutive numbering vs. vtable slots vs. type-level versioning), and the role of RPC (integral to Cap'n Proto, absent in the others). Arena allocation underwrites all three, turning construction into pointer arithmetic and bulk frees. Empirically, the payoff is an order-of-magnitude decode-latency reduction over parse-based frameworks at comparable wire sizes [6][9]. The remaining frontier is not speed but *safety ergonomics*: linear-time validation that is cheap enough to be always-on, and evolution disciplines expressive enough for decade-lived protocols without surrendering layout canonicity. For systems where decode latency dominates—game state replication, columnar analytics interchange, high-frequency RPC—these frameworks are not optimizations; they are the correct layering.
