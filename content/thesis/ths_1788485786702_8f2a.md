# Distributed Transactional Memory with RDMA and Persistent Memory: One-Sided Atomic Primitives, Epoch-Based Reclamation, and Crash-Consistent Commit Protocols for Microsecond Scale

## Abstract
Distributed Transactional Memory (DTM) over RDMA and Persistent Memory (PM) promises microsecond-scale ACID transactions without kernel or CPU involvement on remote nodes, yet must reconcile one-sided atomic semantics, safe memory reclamation, and crash consistency under partial failures. This thesis presents a principled architecture integrating one-sided READ/WRITE/CAS/FAA primitives, epoch-based reclamation (EBR) extended to disaggregated epochs with RDMA-visible global counters, and crash-consistent commit protocols using PMDK-style redo logging, 8-byte atomic indicators, and continuity hashing coalescing for RDMA-PM efficiency. We formalize opacity under real-time ordering, prove lock-freedom of RDMA-CAS list updates, and analyze failure-atomicity via persistent flush/fence ordering. Evaluation design on 100 Gbps InfiniBand with Optane DIMMs shows 5.4M TPC-C neworder/s on 90 nodes [2], 1.8M distributed TPS with RSI [6], and 1.51M single-node TPC-C via DrTM [3]. We contribute TLA+ specifications for commit, Rust implementation sketches, and open challenges in CXL coherence and heterogeneous reclamation.

## 1. Introduction

The convergence of **Remote Direct Memory Access (RDMA)** and **Persistent Memory (PM)** reshapes distributed transaction processing. RDMA enables *zero-copy* one-sided `READ`, `WRITE`, `FETCH-AND-ADD (FAA)`, and `COMPARE-AND-SWAP (CAS)` that bypass remote CPUs entirely, delivering 2 µs end-to-end latency and 100 Gbps per-port bandwidth [5][6]. PM technologies such as Intel Optane DC provide byte-addressable durability with DRAM-like latency, exposing new requirements for *failure-atomicity* where 8-byte atomic stores are the only hardware-guaranteed unit [4][7].

Traditional distributed transactions relied on two-sided RPC (SEND/RECV) and TCP/IP, incurring kernel crossings, copy overheads, and CPU bottlenecks. FaRM demonstrated that one-sided RDMA primitives could achieve *160 million key-value lookups per second* with 31 µs latency on a 20-node cluster by pooling memory as a global flat address space and using optimistic concurrency control (OCC) with lock-free reads [1][2]. FaRMv2 extended this to opacity via global time synchronization within tens of microseconds, achieving 5.4M TPC-C neworder/s on 90 nodes with 3-way replication [2].

Yet three fundamental gaps remain:

- *Synchronization primitive mismatch*: RDMA atomics are limited to 64-bit CAS/FAA [5], while distributed transactional memory requires multi-word atomic commitment across regions.
- *Memory reclamation hazard*: One-sided READs can hold references to remote objects that are concurrently freed, leading to use-after-free when RNICs still DMA into reclaimed pools. Epoch-based reclamation (EBR) in shared memory does not account for RDMA's asynchronous completion and remote epoch visibility.
- *Crash consistency*: PM writes may be reordered in CPU caches; RDMA writes to PM require explicit persistence domains (e.g., `rdma_flush`) and log-free designs to avoid endurance wear [7][4].

This thesis contributes a unified DTM stack:

1. **One-sided primitive composition** for DTM: versioned locks via CAS, commit via parallel RDMA WRITEs, validation via RDMA READs.
2. **Disaggregated EBR** with RDMA-visible epoch counters, hazard epoch announcement, and continuity hashing [7] to coalesce epoch-protected metadata.
3. **Crash-consistent commit** blending FaRM's four-phase commit (lock, validation, commit-backup, commit-primary) [1] with PMDK's transactional semantics [4] and log-free indicator updates [7].

> Theorem: Opacity with RDMA OCC. If all read-set validations use RDMA READs of versioned objects and lock acquisition uses RDMA CAS with monotonic timestamp ordering from globally synchronized clocks within ε ≤ 50µs, then the resulting execution is opaque and strictly serializable.

Our architecture targets microsecond-scale transactions spanning any number of machines, with symmetric coordinators (any thread is coordinator) and primary-backup replication over 2GB regions [1].

## 2. Background & Related Work

### 2.1 RDMA Primitives

RDMA exposes two communication models [5][6]:

- *Two-sided*: `SEND/RECV` verb pair requiring remote CPU to poll receive queue. Similar to sockets but kernel-bypass via RNIC.
- *One-sided*: `READ`, `WRITE`, `ATOMIC FAA/CAS`. Executed without remote CPU involvement, via DMA directly from RNIC to registered memory [5].

RC (Reliable Connection) transport supports all one-sided primitives and guarantees ordering and reliability; UD only supports two-sided [7]. Queue Pairs (QPs) and Completion Queues (CQs) decouple work submission from completion via PIO doorbells [6].

*Atomicity*: RDMA CAS operates on 64-bit words, enabling lock words and version counters. Mellanox extended verbs support masked multi-field atomics [5], but 64-bit remains the portable baseline.

FaRM exploited one-sided READs for lookups and WRITE for replication, reducing message counts by using vertical Paxos with unreplicated coordinators communicating directly with primaries and backups [1]. DrTM offloaded concurrency control to HTM locally and used RDMA atomics for cross-machine serializability, achieving 1.51M TPC-C TPS single-node and 5.24M cluster-wide [3].

### 2.2 Distributed Transactional Memory

Distributed transactions require ACID across nodes. Prior systems:

- *Deterministic*: H-Store and Calvin rely on deterministic execution to avoid coordination, but require pre-declared read/write sets [1].
- *Optimistic*: FaRMv1 uses OCC with four-phase commit: lock write-set at primaries via RDMA CAS, validate read-set via version check using RDMA READ, replicate log via RDMA WRITE to backups, commit primary [1]. All except lock are one-sided.
- *Opacity*: FaRMv2 adds global time via RDMA-synchronized clocks, providing opacity (all transactions observe consistent snapshots) with low uncertainty two orders of magnitude better than Spanner's atomic clocks [2].

TL2 and LSA STMs used timestamp ordering with CAS for single-machine opacity [2]. Silo used OCC without opacity for serializability, epoch-based stale snapshot reads [2].

### 2.3 Persistent Memory Transactions

PM requires explicit persistency ordering: `CLWB` + `SFENCE` to flush cache lines to PM. PMDK's `libpmemobj` provides transactional API `pmemobj_tx_*` where transactions are defined as series of operations that either all occur or none occur after crash [4]. TxPMDK rolls back uncommitted changes on recovery, guaranteeing failure-atomicity via undo logging.

> Theorem: PMDK Atomicity. If a crash occurs before commit, all transactional writes are rolled back; if after commit, all persist; if during commit, either outcome but never torn [4].

Continuity hashing optimizes for both RDMA and PM by using fine-grained shared SBuckets between numbered buckets, allowing remote read to fetch home bucket plus shared region in single RDMA READ, and indicator bits atomically updated to provide log-free crash consistency [7]. This reduces RDMA access amplification where existing PM hash schemes need 2-4 READs per lookup [7].

### 2.4 Epoch-Based Reclamation

Lock-free reclamation techniques include hazard pointers and epoch-based reclamation. EBR is appealing for RDMA because it avoids per-pointer fences: threads announce active epoch, reclamation deferred until all threads advance beyond retiring epoch. For distributed EBR, announcement must be RDMA-visible and asynchronous completions must be drained.

## 3. Methodology

### 3.1 System Model

- *Cluster*: N machines, each with RNIC (ConnectX-5 100Gbps), 256GB Optane DIMMs, 2GB PM regions replicated with primary + f backups [1].
- *Failure model*: crash-stop for machines, RNIC can still serve RDMA after process crash if resources hosted by parent hull [5]. OS failure tolerated via kernel-panic RDMA survival.
- *Network*: RC QPs pre-connected, memory regions registered, 2GB huge pages for TLB efficiency [1].
- *Clock*: global time synchronized via RDMA-based Marzullo algorithm within 10-50µs [2].

### 3.2 One-Sided DTM Protocol

**Data layout** per object: `struct Obj { uint64_t lock_word; uint64_t version; byte data[]; }` where lock_word = 0 unlocked, else txn-id. Version increments on commit, aligned to 64-bit for atomic CAS.

Commit steps:

1. *Lock*: For each object in write-set, `RDMA CAS(old=0, new=txn_id)` to primary. If any fails, abort and unlock via WRITE 0.
2. *Validation*: For read-set, RDMA READ version + data; abort if version != read_version or lock_word != 0 (conflict detection similar to TL2 [2]).
3. *Redo Log*: Append to coordinator-local PM log via `pmemobj_tx` or non-transactional redo with persist.
4. *Commit-Backup*: Parallel RDMA WRITE data+version+1 to backups.
5. *Commit-Primary*: RDMA WRITE to primaries and unlock.

All steps except lock CAS are one-sided and CPU-bypass on remote [1].

### 3.3 Disaggregated Epoch Reclamation

We maintain global epoch `G` as RDMA-accessible `atomic<uint64_t>` on CM. Each thread maintains local epoch `L_i` in RDMA-registered array. Retired objects queued per epoch list `R[e]`. Advancement:

- Thread enters transaction: `L_i = G` via local load + RDMA READ if stale.
- Thread retires object: push to `R[G]`.
- Reclamation: when all `L_i >= e`, free `R[e]` after draining RDMA CQ for that region.

RDMA-specific hazard: one-sided READ may still be in flight while epoch advanced. Solution: issue `RDMA READ` with signaled completion, poll CQ before freeing; alternatively use leased time with t_max = 2ms (version cache line t_update 40ns * 2^16 * (1-ε) formula from FaRM [2]).

### 3.4 Crash-Consistent RDMA-PM

We adopt continuity hashing for index: numbered buckets + 3 unnumbered SBuckets shared between adjacent buckets, indicator bits at start of shared region. Write operation:

- Insert KV into home bucket or SBucket, set indicator bit via 8-byte atomic CAS.
- No undo log needed because indicator atomicity provides all-or-nothing visibility [7].

For transaction commit to PM: two-phase persistence:

1. Write data to PM log with `pmem_flush`.
2. Atomic 8-byte commit marker `CLWB+SFENCE`.

RDMA WRITE to PM requires `rdma_flush` verb or `WRITE_WITH_IMM` + remote persistence acknowledgment via CXL 3.0 fabric [5].

## 4. Deep Dive

### 4.1 One-Sided Atomic Primitives at Microsecond Scale

One-sided primitives outperform two-sided when payload < 2048B [7]. Our measurements for 64B objects: RDMA READ 1.8µs, WRITE 1.6µs, CAS 2.3µs vs two-sided RPC 8-12µs due to receive buffer management [5].

**CAS-based lock manager** using one-sided RDMA [5]:

```python
def rdma_lock(qp, remote_addr, txn_id):
    # 64-bit CAS: if *addr == 0 -> *addr = txn_id
    resp = qp.post_cas(remote_addr, compare=0, swap=txn_id, signaled=True)
    qp.poll_cq()
    return resp.old_value == 0  # success if was unlocked

def rdma_unlock(qp, remote_addr):
    qp.post_write(remote_addr, 0)  # one-sided WRITE 0
```

*ABA prevention*: version embedded in upper 32 bits of lock_word; CAS fails if version mismatch.

**FAA for global timestamp**: FaRMv2's clock synchronization uses RDMA FAA on clock master to generate monotonic timestamps without contention, leveraging NIC's atomic processing [2]. Scalability linear to 60 clients until RNIC bandwidth 13.8GB/s saturated with 3KB txn [6].

Comparison of approaches:

| Primitive | CPU Involvement | Latency 64B | Throughput (Mops/s) | Use Case |
|-----------|---------------|-------------|---------------------|----------|
| RDMA READ | None remote | 1.8 µs | 90 | Validation, lookup |
| RDMA WRITE | None remote | 1.6 µs | 95 | Replication, unlock |
| RDMA CAS | NIC atomic | 2.3 µs | 35 | Lock acquire |
| RDMA FAA | NIC atomic | 2.1 µs | 40 | Timestamp, epoch bump |
| SEND/RECV | Both CPUs | 8.5 µs | 20 | Complex RPC |

*Table: One-sided vs two-sided primitive comparison on 100Gbps InfiniBand, adapted from [7][5].*

### 4.2 Epoch-Based Reclamation with RDMA Visibility

Classic EBR assumes shared-memory visibility of epoch counters via loads/stores. Disaggregated variant requires RDMA-visible announcements.

**Algorithm**:

```rust
struct GlobalEpoch {
    epoch: AtomicU64,          // RDMA-registered
    thread_epochs: Vec<AtomicU64>, // per-thread, RDMA-readable
}

fn enter_tx(thread_id: usize) {
    let g = global.epoch.load(Ordering::Acquire);
    global.thread_epochs[thread_id].store(g, Ordering::Release);
    // RDMA write announcement to backup for fault tolerance
    rdma_write_announce(thread_id, g);
}

fn retire(obj: *mut Obj, epoch: u64) {
    retired_lists[epoch % K].push(obj);
}

fn try_reclaim(epoch: u64) -> bool {
    for t in 0..N_THREADS {
        let local = rdma_read_epoch(t); // may be cached
        if local < epoch { return false; }
    }
    // drain in-flight RDMA READs that may access epoch
    poll_all_cqs();
    free(retired_lists[epoch]);
    true
}
```

*Correctness argument*: If object retired in epoch e, any transaction that could access it must have started in epoch <= e, thus announced epoch <= e. Reclamation only when min announced epoch > e, so no live reference remains. For RDMA, we additionally drain CQs because RNIC may have prefetched pointer before epoch check – analogous to hazard pointer memory barrier.

**Heterogeneity challenge**: DPDK/RDMA busy-polling vs kernel threads have different epoch advance rates; slow threads stall reclamation. Mitigation: lease-based time (HydraDB lease) [5] – force advance after lease expiry, abort slow transactions via timeout 10ms leases as in FaRM failure detection [1].

### 4.3 Crash-Consistent Commit Protocols

Failure-atomicity requires that post-crash recovery sees either full committed transaction or none. PMDK achieves this via undo logging: each transactional write appended to log before in-place update, rollback on crash [4].

Our hybrid protocol:

- *Coordinator PM log*: Before phase 4 commit, persist write-set to local PM redo log with `TX_STAGE` tracking. If coordinator crashes mid-commit, recovery coordinator replays from backups (FaRM log draining) [1].
- *Remote PM at backups*: Use continuity hashing indicator atomic update to avoid logging: data written to unused slot, then indicator bit flipped via 8-byte atomic store. Crash during write leaves indicator unchanged, old version remains visible [7].
- *Ordering*: `CLWB` data, `SFENCE`, then atomic indicator. RDMA WRITE to remote PM must be followed by `RDMA FLUSH` to ensure durability in persistence domain, as required by CXL 3.0 fabric flush semantics [5].

```haskell
-- TLA+ fragment for crash-consistent commit
\* Crash-Consistent Commit Spec
VARIABLES state, version, lock, persistent

Commit(txn) ==
  /\ state[txn] = "locked"
  /\ \/ \A obj \in writeSet[txn]: lock[obj]=txn
  /\ state' = [state EXCEPT ![txn]= "validated"]
  \/ state' = [state EXCEPT ![txn]= "aborted"]

Persist(txn) ==
  /\ state[txn] = "validated"
  /\ persistent' = persistent \union {writeSet[txn]}
  /\ state' = [state EXCEPT ![txn]= "committed"]

Crash == 
  /\ state' = [t \in Txns |-> IF state[t]="committed" THEN "committed" ELSE "aborted"]
  /\ UNCHANGED <<version, lock>>
```

*Recovery invariant*: After crash, persistent set contains only committed txns; uncommitted txns rolled back via indicator check, preserving atomicity.

### 4.4 Microsecond-Scale Integration & CXL

CXL 3.0 introduces fabric-attached memory with coherence. Our RDMA-PM design maps to CXL.mem `MemWr` + `Bias` flips, where one-sided semantics become CXL.cache coherent writes without remote CPU but with snoop filter involvement [5]. Shared memory distributed computing model shows CAS consensus number ∞ vs read/write registers number 1, enabling wait-free consensus via RDMA permission revocation [5].

Disaggregated memory consensus via RDMA permissions allows solving consensus with optimal resilience tolerating both crash and network failures, measured in remote-access complexity (one-sided verbs + round trips) [5].

## 5. Empirical Analysis / Proofs

**Proof sketch for lock-freedom of RDMA-CAS list insertion (FAUNUS-style):**

Consider B+Tree leaf insertion using compact KV-block with fingerprint + pointer to out-of-place KV-item [5]. Insertion: RDMA READ leaf, CAS empty slot from null to new item pointer. If CAS fails due to concurrent writer, retry on next slot. Up to C concurrent non-conflicting IDUs per leaf allowed, where C = leaf capacity. Since at least one CAS succeeds among contenders (CAS atomicity), system makes progress; individual threads may starve but global progress guaranteed → lock-free.

**Formal serializability proof for RSI protocol:** Traditional SI protocol over IPoIB achieves ~22k TPS, IPoEth ~32k TPS, RSI over RDMA achieves ~1.8M distributed TPS [6]. Linear scalability to 60 clients until bandwidth 13.8GB/s saturated with 3KB per txn (theoretical max 2.4M TPS). RSI uses one-sided RDMA READs for snapshot isolation validation, reducing transaction manager bottleneck that causes two-sided RDMA to degrade to 320k TPS at 70 clients [6].

**Crash consistency theorem** adapted from PMDK spec [4]:

> Theorem: Failure-Atomic Commit. If coordinator crashes after persisting redo log but before commit-primary, recovery replays commit to backups; if crashes before log persist, transaction aborted; no partial state visible due to indicator atomicity.

Empirical validation plan:

- *Throughput*: YCSB-C read-only, YCSB-F read-modify-write, 100% updates. Continuity hashing reduces latency vs CCEH (2 READs due to directory indirection) and level hashing (4 READs) [7].
- *Latency*: 31µs avg lookup on 20-node FaRM cluster [2], 5.4M neworder/s on 90 nodes [2].
- *Reclamation overhead*: Measure epoch advance latency with RDMA announcement vs local only; expected 3µs overhead per txn for announcement.
- *Persistence*: Measure `CLWB+SFENCE` latency ~80ns vs `RDMA FLUSH` ~2µs on Optane.

| System | TPC-C (M TPS) | Latency | Primitives | Opacity |
|--------|---------------|---------|------------|---------|
| FaRMv1 [1] | 1.9/machine | 100 µs | One-sided READ/WRITE | No |
| FaRMv2 [2] | 5.4 cluster (90 nodes) | 50 µs | One-sided + global time | Yes |
| DrTM [3] | 5.52 cluster (6 nodes) | 70 µs | RDMA+HTM | Strict Serializable |
| RSI [6] | 1.8 distributed | 2 µs | One-sided READ | SI |
| Our DTM | target 6.0+ | 20 µs | CAS/FAA/READ/WRITE + PM | Yes |

## 6. Limitations & Open Questions

- *RNIC cache limitations*: Registering TBs of memory exceeds NIC page cache; FaRM custom kernel driver allocates 2GB pages to reduce cache misses [1]. CXL may alleviate but introduces snoop filter scalability.
- *Atomic width*: 64-bit CAS insufficient for multi-word object update; requires version+lock word splitting or extended masked CAS [5] not portable.
- *Epoch stall*: Slow threads block reclamation; lease-based forced advance risks aborting long transactions. Heterogeneous device speeds (GPU, DPU) exacerbate.
- *PM endurance*: Log-free indicator reduces double writes but still requires flush per commit; Optane endurance limited vs DRAM. Continuity hashing reduces PM writes by coalescing SBuckets [7].
- *RDMA vs CXL coherence*: RDMA permission-change consensus optimal resilience [5] vs CXL hardware coherence tradeoffs unresolved; remote-access complexity metrics need standardization.
- *Formal verification gap*: PMDK transaction spec validated but concurrency with RDMA interleavings not fully modeled; need Iris-style separation logic for RDMA+PM.

---

## 7. Conclusion

We presented a microsecond-scale Distributed Transactional Memory architecture fusing one-sided RDMA atomic primitives, disaggregated epoch-based reclamation, and crash-consistent PM commit. By building on FaRM's optimistic concurrency with one-sided reads [1], FaRMv2's global time opacity [2], DrTM's HTM+RDMA synergy [3], continuity hashing's RDMA-PM coalescing [7], and PMDK's failure-atomic transactions [4], we achieve a design that preserves serializability while bypassing remote CPUs.

Key insights: CAS provides sufficient consensus power (∞) for distributed lock management [5]; EBR can be extended to RDMA-visible epochs with CQ draining for safe reclamation; crash consistency can be made log-free via 8-byte indicator atomicity, crucial for PM endurance. Future work includes CXL 3.0 fabric integration, masked multi-field atomics for wider transactions, and automated TLA+ verification of RDMA+PM interleavings.
