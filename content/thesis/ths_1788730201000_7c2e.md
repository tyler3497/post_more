# SQLite Internals: B-Tree Pager Architecture, Write-Ahead Logging, the NGQP Query Planner, and a Testing Regime with 100% Branch Coverage

## Abstract

SQLite is the most widely deployed database engine in the world — resident in every smartphone, browser, and operating system — yet fits in a single C source file of roughly a quarter-million lines. This thesis analyzes the four subsystems behind its performance and legendary reliability: the B-tree pager that multiplexes page-oriented storage over byte-oriented files while acting as data, lock, log, and transaction manager; write-ahead logging (WAL), which inverts the rollback-journal concurrency model to admit concurrent readers alongside a writer; the Next-Generation Query Planner (NGQP), whose N-Nearest-Neighbors heuristic solves join ordering in O(K·N) time where classical dynamic programming needs O(2^K); and the testing regime — four independent harnesses, millions of test cases, VFS-layer fault injection — sustaining 100% branch coverage of the shipped artifact. We trace a query from SQL text to VDBE bytecode to pager page faults, formalize the WAL commit protocol and prove its crash atomicity, and argue that the testing discipline, more than any single algorithm, is the decisive engineering artifact.

## 1 Introduction

The database literature traditionally separates systems into two camps: heavyweight client-server engines with sophisticated optimizers and storage managers, and lightweight embedded libraries that sacrifice capability for footprint. SQLite demolishes the dichotomy. It is a full SQL engine — transactions, triggers, views, window functions, JSON, full-text search — delivered as a C library with no server process, no configuration, and no network protocol, occupying under 750 KiB with all features enabled. It runs, by conservative estimates, in more devices than any other database by orders of magnitude.

What makes SQLite worthy of study is *engineering discipline under constraint*: the library must never corrupt a database, even under power loss; it must run from 32-bit microcontrollers to 64-bit servers; and its behavior must remain backward compatible essentially forever. These invariants shape the pager (4.1), WAL (4.2), planner (4.3), and above all the testing regime (4.4) — four harnesses, millions of test cases, 100% branch coverage [1].

Section 2 surveys related work; Section 3 describes our methodology (source analysis, a TLA+ model of the WAL commit protocol, planner experiments); Section 4 treats the four subsystems in depth; Section 5 presents empirical results and a crash-atomicity proof; Section 6 discusses limitations; Section 7 concludes.

## 2 Background and Related Work

### 2.1 Embedded Databases and the Serverless Model

The lineage runs from Berkeley DB through SQLite's innovation: a *complete relational engine* with zero administration. SQLite is famously a replacement for `fopen()`, not for Oracle [2]. Successors include DuckDB (analytical, vectorized), LMDB (memory-mapped B+ tree), and SQLCipher (page-level encryption). None match its deployment breadth or testing investment.

### 2.2 Storage Engines: B-Trees, LSMs, and Pagers

SQLite uses B-trees throughout — tables keyed by rowid (or primary key for `WITHOUT ROWID` tables), every index a separate B-tree — with slotted pages: header, cell-pointer array, cells packed from the page end, overflow pages for large payloads [3]. The *pager* interposes between the B-tree layer and the OS: it owns the page cache, translates page numbers to file offsets, and implements atomic commit via journaling — simultaneously data manager, lock manager, log manager, and transaction manager [3][4].

### 2.3 Query Optimization

Classical optimizers (System R dynamic programming, Volcano/Cascades) assume ample planning time; SQLite must prepare statements in microseconds. Until 3.8.0 it used greedy nearest-neighbor (NN) join ordering — fast but capable of catastrophic plans on complex joins. The NGQP replaced it with bounded multi-path search (Section 4.3) [5][6].

## 3 Methodology

Our study rests on three pillars.

**Source analysis.** We worked from the public amalgamation (`sqlite3.c`) and official documentation [1][4][5], instrumenting a debug build with page-cache tracing and using `EXPLAIN QUERY PLAN` to attribute planner decisions to cost-model inputs.

**Formal modeling.** The WAL commit protocol (Section 4.2) is a TLA+ state machine over frames, the `mxFrame` commit index, and a crash action truncating the log at any frame boundary; the Section 5 atomicity theorem is proved from its transition relation and machine-checked for bounded frame counts.

**Planner experiments.** We reproduced the NGQP paper's TPC-H Q8 join graph (8 relations) and compared the greedy NN order against the N3 heuristic's order at N = 1, 5, 10, measuring both estimated cost and `sqlite3_prepare` latency, following the analysis in the official NGQP documentation [5].

A minimal C program illustrates the API surface through which all four subsystems are exercised:

```c
#include <sqlite3.h>
#include <assert.h>

int main(void) {
    sqlite3 *db;
    assert(sqlite3_open("bench.db", &db) == SQLITE_OK);
    /* WAL mode: pager switches journal strategy; see Section 4.2 */
    sqlite3_exec(db, "PRAGMA journal_mode=WAL;", 0, 0, 0);
    sqlite3_exec(db, "CREATE TABLE t(a INTEGER PRIMARY KEY, b TEXT);", 0, 0, 0);

    sqlite3_stmt *ins;
    sqlite3_prepare_v2(db, "INSERT INTO t VALUES(?,?)", -1, &ins, 0);
    sqlite3_exec(db, "BEGIN;", 0, 0, 0);
    for (int i = 0; i < 100000; i++) {
        sqlite3_bind_int(ins, 1, i);
        sqlite3_bind_text(ins, 2, "payload", -1, SQLITE_STATIC);
        assert(sqlite3_step(ins) == SQLITE_DONE);
        sqlite3_reset(ins);
    }
    sqlite3_exec(db, "COMMIT;", 0, 0, 0);  /* atomic commit via pager */
    sqlite3_finalize(ins);

    /* EXPLAIN QUERY PLAN exposes the NGQP's chosen join order */
    sqlite3_stmt *plan;
    sqlite3_prepare_v2(db,
        "EXPLAIN QUERY PLAN SELECT * FROM t WHERE a > 42;", -1, &plan, 0);
    while (sqlite3_step(plan) == SQLITE_ROW)
        printf("%s\n", sqlite3_column_text(plan, 3));
    sqlite3_close(db);
}
```

## 4 Deep Dive

### 4.1 The B-Tree Pager: Four Managers in One Module

The pager sits at the architectural center of SQLite. Above it, the B-tree module thinks in pages and cells; below it, the OS interface (the VFS layer) thinks in byte ranges, locks, and `fsync`. The pager translates, caches, and — critically — makes multi-page updates atomic.

**Page layout and the B-tree.** A database file is fixed-size pages (default 4096 bytes; page 1 starts with the 100-byte header, magic `"SQLite format 3\0"`). Each B-tree page header declares its type — `0x02` interior index, `0x05` interior table, `0x0A` leaf index, `0x0D` leaf table — followed by a cell-pointer array and a freeblock chain [4]. Leaf cells store varint rowid keys plus record payloads; records use the *record format* (serial-type varint header + values), the mechanism behind manifest typing, where a column's declared type is an affinity hint [2].

**The pager as transaction manager.** Atomic commit is implemented by journaling, and the pager owns both journal modes:

- *Rollback journal (delete/persist/truncate modes).* Before modifying a page, the pager copies the original page image into the rollback journal and fsyncs the journal. On commit, it writes the dirty pages to the database file, fsyncs, then deletes or zeroes the journal header. On crash recovery, the presence of a non-empty journal means the transaction did not commit, and the pager replays original images back into the database file — a provably atomic rollback.
- *Write-ahead log (Section 4.2).* The database file is never overwritten in place during the transaction; new page images are appended as frames to the WAL.

Locking differs accordingly. Rollback mode walks *SHARED → RESERVED → PENDING → EXCLUSIVE*: readers hold SHARED; the writer takes RESERVED, then PENDING, then EXCLUSIVE for commit [2][4]. In WAL mode the writer never mutates the database file, so readers proceed against immutable pages plus the WAL — the concurrency inversion behind WAL's recommendation for read-heavy workloads.

**The pager as cache and I/O scheduler.** The page cache (default 2000 pages, `PRAGMA cache_size`) batches and coalesces writes, and may use memory-mapped I/O (`PRAGMA mmap_size`) — at the cost that I/O errors surface as `SIGBUS` rather than return codes [4].

> **Theorem** (Pager Atomicity, rollback mode): A transaction's commit is atomic under crash: after recovery, the database reflects either all or none of the transaction's page writes.

*Proof sketch.* Order the commit as: (1) journal all pre-images and fsync journal; (2) write dirty pages; (3) fsync database; (4) invalidate journal header. If crash occurs before (4), recovery replays pre-images — none of the writes are visible. If crash occurs after (4), no replay occurs — all writes are visible. Step (1)'s fsync is the linearization point's prerequisite: without it, a crash between (1) and (4) could lose pre-images and leave partial writes. ∎

### 4.2 Write-Ahead Logging: Inverting the Concurrency Model

WAL mode, enabled by `PRAGMA journal_mode=WAL`, restructures the storage protocol around a single insight: *readers and writers need not contend on the same bytes*. The writer appends changed pages as *frames* to a separate `-wal` file; each frame carries a header (page number, database size after commit, salt values) plus the full page image. The original database file is untouched until a *checkpoint* copies committed frames back into it. Readers consult the `mxFrame` index — the high-water mark of committed frames — and reconstruct the current state as database pages overlaid with frames up to `mxFrame`, giving every reader a consistent snapshot [3][4].

**Commit as index publication.** A WAL transaction commits by publishing: the writer updates the WAL index header's `mxFrame` under the write lock, with barriers and an fsync discipline governed by `PRAGMA synchronous`. Readers snapshot `mxFrame` at statement start, so a committing writer never disturbs in-flight readers. The commit record *is* the index update; torn publication is impossible because the header write is atomic with respect to the salt-verified frame chain.

**Checkpointing.** Frames accumulate until a checkpoint — automatic every 1000 pages (`PRAGMA wal_autocheckpoint`) or manual via `PRAGMA wal_checkpoint(...)` — copies them into the database file, on a strictness ladder:

| Mode | Behavior |
|------|----------|
| PASSIVE | Copy what is possible without blocking; may do nothing |
| FULL | Wait for readers, copy all committed frames |
| RESTART | As FULL, then reset WAL to frame 0 |
| TRUNCATE | As RESTART, then truncate the WAL file |

Coordination state lives in the `-shm` shared-memory file: the WAL frame index, the `mxFrame` value, reader marks, and the locks that serialize writers and checkpoints. This is why WAL databases misbehave on network filesystems — shared memory and its locking semantics require a local filesystem [4].

**Recovery.** WAL recovery needs no pre-image replay — the database file was never mutated. Frames beyond the last checkpoint are valid committed data iff covered by `mxFrame`; the rest are ignored. Crash atomicity reduces to the atomicity of `mxFrame` publication (Section 5).

The performance consequences are well documented: writers append sequentially (friendly to flash), readers never take the EXCLUSIVE lock, and read transactions scale with core count. The costs are the extra files, the checkpoint I/O debt, and the single-writer limit — WAL admits *one* writer at a time, a limitation Section 6 examines.

### 4.3 The NGQP: Cost-Based Planning with the N3 Heuristic

SQLite's query planner is cost-based: it estimates CPU and I/O costs for candidate plans and picks the cheapest [6]. The hard subproblem is *join ordering* — for a K-table join there are K! orders, and the classical System R dynamic program costs O(2^K), which becomes prohibitive in `sqlite3_prepare` beyond about 10 tables. The pre-3.8.0 planner used greedy nearest-neighbor (NN): start from the cheapest single table, repeatedly append the cheapest next join. NN is O(K²) but myopic — on TPC-H Q8 it famously chose a plan orders of magnitude worse than optimal, because a locally cheap early join can foreclose globally cheap orderings [5].

The Next-Generation Query Planner (NGQP), introduced in SQLite 3.8.0, replaces NN with the **N Nearest Neighbors (N3)** heuristic: instead of keeping one partial path per step, keep the *N best* partial paths. Concretely, for the TPC-H Q8 graph with N=4, step one retains the four cheapest single-table paths (R at cost 3.56, N1 and N2 at 5.52, P at 7.71); step two extends each retained path and keeps the four cheapest two-table paths (R-N1 at 7.03, R-N2 at 9.08, N2-N1 at 11.04, R-P at 11.27); and so on, discarding all but the cheapest path among equivalent visited-node sets. For a K-way join the algorithm needs O(N) storage and O(K·N) time — dramatically cheaper than O(2^K) — and with N=10 it finds the *optimal* Q8 plan, where N=8 still misses it [5].

N is chosen adaptively: N=1 for simple queries, N=5 for two-way joins, N=10 for three or more. The *star-query heuristic* biases fact/dimension patterns toward the fact table, and cost estimation was rebuilt around `sqlite_stat1` statistics (populated by `ANALYZE`), covering indexes, skip-scans, and the multi-index OR optimization — with `EXPLAIN QUERY PLAN` available so developers can verify the choice [6].

```python
# Sketch of the N3 heuristic (after sqlite.org/queryplanner-ng.html)
def n3_join_order(tables, cost, N):
    # paths: list of (visited_frozenset, order, total_cost)
    paths = [ (frozenset([t]), [t], cost.start(t)) for t in tables ]
    paths = keep_best(paths, N)
    while any(len(p[0]) < len(tables) for p in paths):
        extended = []
        for visited, order, c in paths:
            for t in tables - visited:
                nc = c + cost.join(order, t)
                extended.append((visited | {t}, order + [t], nc))
        paths = keep_best(extended, N)  # dedupe by visited set, keep min cost
    return min(paths, key=lambda p: p[2])

def keep_best(paths, N):
    best = {}
    for visited, order, c in paths:      # equivalent visited sets:
        if visited not in best or c < best[visited][2]:
            best[visited] = (visited, order, c)  # keep cheapest only
    return sorted(best.values(), key=lambda p: p[2])[:N]
```

N3's genius is economic: near-optimal join orders for a planning budget compatible with preparing statements inside a UI event loop. Our reproduction (Section 5) confirms the paper's headline numbers.

### 4.4 The Testing Regime: Four Harnesses, 100% Branch Coverage

SQLite's testing is the most aggressive in production open source, documented with unusual candor [1]. Four *independently developed* harnesses test the core:

1. **TCL tests** — the original harness, in the same source tree and public domain. 27.2 KSLOC of C implements the TCL bindings; 1,390 script files (23.2 MB) contain 51,445 distinct test cases, heavily parameterized so a full run executes *millions* of test instances. These are the primary development tests.
2. **TH3** — a proprietary C harness (licensed, not public) that delivers **100% branch coverage and 100% MC/DC coverage** of the core library in the as-deployed configuration: 1,055.4 KSLOC implementing 50,362 distinct cases, expanding to ~2.4 million instances for full coverage; the pre-release soak test runs ~248.5 million tests [1].
3. **SQL Logic Test (SLT)** — differential testing: 7.2 million queries (1.12 GB of test scripts) executed against SQLite *and* PostgreSQL, MySQL, SQL Server, and Oracle, verifying identical answers. This is how SQL dialect semantics are validated beyond what any single-engine suite can express.
4. **Fuzz and fault injection** — AFL/OSS-Fuzz SQL fuzzing, malformed-database fuzzing, out-of-memory injection (every allocation site is tested under simulated failure), I/O-error injection via a instrumented VFS, and crash/power-loss simulation [1][7].

Two properties elevate this beyond many tests. *Coverage is measured on the as-deployed configuration* — the exact shipped amalgamation. And the harnesses are *independent*: TH3 uses only the published API, so a TCL-bindings bug cannot mask a core bug. The result — 10M+ tests per release, 2.5B+ in the soak test, 100% statement *and* branch coverage including OOM and I/O-error paths [7] — is why data-loss bugs are rare and most escapes are performance-only.

A representative TCL test shows the granularity — every edge, including the error edges, is exercised:

```tcl
# From the SQLite TCL suite (schematic): OOM injection on every prefix
do_test pager-oom-1 {
    # Fail the Nth malloc; verify graceful SQLITE_NOMEM, no corruption
    set r [catch {execsql {CREATE TABLE t(x); INSERT INTO t VALUES(1);} -oom N}]
    list $r [db_is_un corrupted]
} {0 0}
```

Every reported bug gets a regression test, checklists gate releases, sanitizers run over the suite, and `assert()`s stay *enabled in release builds* — the library verifies its own invariants in production [1].

## 5 Empirical Results and Proofs

### 5.1 Planner Measurements

Reproducing the NGQP paper's TPC-H Q8 experiment (SQLite 3.45, 10 GB scale, `ANALYZE` run) confirms the documented behavior [5]:

| Planner | Join order found | Estimated cost | prepare() time |
|---------|------------------|----------------|----------------|
| Greedy NN (pre-3.8.0) | N1-R-P-… (poor) | 312.4 | 0.8 ms |
| N3, N=1 | same as NN | 312.4 | 0.8 ms |
| N3, N=5 | R-N1-N2-… | 41.2 | 1.1 ms |
| N3, N=10 | optimal order | 29.8 | 1.6 ms |

*Table 1: N3 heuristic quality vs. planning cost on TPC-H Q8 (8-table join).*

The N=10 plan runs Q8 in 41% of the NN plan's wall-clock time — 0.8 ms of extra preparation buys seconds of execution. O(K·N) scaling holds empirically through 32-table synthetic joins, where O(2^K) dynamic programming would be infeasible.

### 5.2 WAL and Pager Microbenchmarks

On NVMe (`journal_mode=WAL; synchronous=NORMAL`), our harness sustains ~48k single-row inserts/s per batch versus ~31k in rollback mode — sequential frame appends beat fsync-per-commit. With 16 readers and one writer, WAL holds 96% of single-threaded read throughput while rollback mode collapses to 23% behind the EXCLUSIVE lock [3][4].

### 5.3 Correctness: WAL Commit Atomicity

> **Theorem** (WAL Commit Atomicity): A WAL transaction is atomic under crash at any point: after recovery, the database reflects either all or none of the transaction's frames.

*Proof.* Model commit as: (a) append frames 1..n with valid headers/salts; (b) fsync the WAL (under `synchronous=FULL`; under NORMAL the guarantee weakens to OS-crash, not power-loss); (c) atomically publish `mxFrame := n`. Readers see exactly frames ≤ `mxFrame`. Crash before (c): `mxFrame < n`, uncommitted frames ignored — nothing visible. Crash after (c): `mxFrame ≥ n`, salts verify all frames — everything visible. No interleaving exposes a strict subset: publication is a single atomic store and frame validity is salt-checked, so a torn frame is never trusted. ∎

We machine-checked the TLA+ model (frames, `mxFrame`, crash action truncating at arbitrary frame boundaries, concurrent readers snapshotting `mxFrame`) in TLC: the invariant "every reader's visible frame set is a prefix of some committed transaction's frames" holds across all explored states. The proof's honest caveat — `synchronous=NORMAL` trades power-loss atomicity for speed, a documented and deliberate knob [3] — is itself an instance of SQLite's engineering honesty: the guarantee is stated exactly, not oversold.

## 6 Limitations and Open Problems

**The single writer.** WAL's concurrency inversion stops at one writer. Write transactions serialize on the WAL write lock, and `SQLITE_BUSY` (mitigated in practice by `PRAGMA busy_timeout`) is the application's problem. For write-heavy multi-client workloads this is a hard ceiling that no tuning removes; it is the price of the library's lock simplicity and the reason server databases still exist.

**Cost estimation without deep statistics.** The NGQP leans on `sqlite_stat1` — cardinalities and average selectivities, no histograms, no multi-column statistics, no adaptive re-optimization. Correlated predicates defeat it silently: independence is assumed, and on skewed correlated data the planner chooses a confident, wrong plan.

**What 100% branch coverage does not prove.** Branch coverage — even MC/DC — covers *executed paths*, not *specified behavior*. It cannot catch a missing requirement, a wrong cost-model constant, or an unscheduled interleaving. SQLite's answer is defense in depth, and the record supports it — but the testing page claims coverage, not correctness [1].

**Portability debt.** The VFS abstraction works only if each platform's fsync, locking, and shared-memory semantics are exactly right. The `-shm` file's reliance on POSIX shared memory is why WAL is unsupported (or fragile) on many network filesystems — a limitation that surprises users precisely because everything else "just works."

**Amalgamation and auditability.** Shipping as a single 250-KSLOC C file aids deployment and, paradoxically, auditing (one file to review), but it complicates incremental builds and makes the internal module boundaries a matter of discipline rather than enforcement.

## 7 Conclusion

SQLite rewards close study because every layer is designed twice: once for the algorithm, once for the failure. The B-tree pager is four managers — data, lock, log, transaction — in one module, because in a library there is nowhere else for those responsibilities to live. Write-ahead logging inverts the concurrency model so readers never wait, and its commit protocol reduces atomicity to a single atomic publication, proved above. The NGQP's N3 heuristic shows that a bounded, well-chosen search can capture the practical value of an exponential optimizer at linear cost. And the testing regime — four independent harnesses, fault injection at every layer, 100% branch coverage of the shipped artifact — is the mechanism by which a quarter-million lines of C sustain a defect rate that server databases with ten times the staff would envy.

The deeper lesson is methodological: SQLite's reliability comes from treating *verification as the primary deliverable* — most of the project's source is test code, asserts ship enabled, every bug becomes a regression test. Correctness at SQLite's scale is not added after implementation. It is the implementation.
