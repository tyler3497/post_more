# Program Slicing: Static and Dynamic Slicing, Program Dependence Graphs, the Horwitz–Reps–Binkley Two-Pass Algorithm, and Applications to Debugging and Security

## Abstract

Program slicing automatically extracts the subprogram that can affect — or be affected by — a *slicing criterion*, typically a program point paired with a set of variables [1][2]. Since Weiser's 1981 formulation [1], the field has developed a rich formal apparatus: control and data dependence relations, program dependence graphs (PDGs), system dependence graphs (SDGs) for interprocedural analysis, and dynamic dependence graphs capturing single executions. This article unifies the theory: we formalize *static slicing* via Weiser's data-flow equations and PDG reachability, develop *dynamic slicing* à la Korel and Laski [7], and give a complete exposition of the **Horwitz–Reps–Binkley two-pass interprocedural slicing algorithm** [5] — including the calling-context problem, summary edges, and why naive transitive closure is unsound across call sites. We survey applications in debugging, maintenance, variant integration, and information-flow security, and report empirical results on slice precision and scalability [9][11][12] alongside the key decidability and complexity boundaries of the field.

## 1 Introduction

A debugger staring at a wrong value in a ten-thousand-line program must answer one question: *which statements could possibly have contributed to this value?* Mark Weiser gave that question a formal answer in 1981: the **program slice** [1][2]. A slice with respect to a criterion ⟨*p*, *V*⟩ — a program point *p* and a variable set *V* — is an executable subprogram obtained by deleting statements from the original such that, for any input, the slice computes the same values for *V* at *p* whenever *p* is reached.

Slicing is an *abstraction* mechanism: it discards behavior provably irrelevant to the criterion. Its power comes from **dependence analysis**. A statement is relevant because it defines a variable later used (a *data dependence*), or because it controls whether another statement executes at all (a *control dependence*). Once dependences are materialized as a graph — the **program dependence graph** (PDG) — slicing degenerates to graph reachability [3][4].

The field stratified along two axes. Along the first, *static slicing* considers all possible executions, while *dynamic slicing* (Korel and Laski, 1988) restricts attention to one concrete execution trace, producing far smaller slices at the cost of generality [7]. Along the second, *intraprocedural* slicing stays within one procedure, whereas *interprocedural* slicing follows dependences across procedure boundaries — much harder, because naive graph reachability conflates calling contexts and yields unsound slices. The definitive solution is the **two-pass algorithm of Horwitz, Reps, and Binkley** (TOPLAS 1990) over *system dependence graphs* [5], which traverses parameter edges in two disciplined phases to respect the call/return discipline.

> **Theorem:** (Slice correctness, informal). A backward static slice *S* of program *P* with respect to ⟨*p*, *V*⟩ is behavior-preserving: for every input on which *P* halts, *S* halts and agrees with *P* on all variables in *V* at the occurrences of *p*. See Reps and Yang for a denotational treatment [15].

Section 2 covers background: Weiser's formulation, dependence relations, and PDGs. Section 3 presents the methodology: graph-based slicing, the two-pass interprocedural algorithm, and dynamic slicing. Section 4 dives into the hardest parts — the calling-context problem, summary edges, dynamic-slicing cost models, and the security interpretation. Section 5 reports empirical results and theoretical guarantees; Section 6 discusses limitations; Section 7 concludes.

## 2 Background

### 2.1 Weiser's Original Formulation

Weiser defined a slicing criterion as a pair ⟨*n*, *V*⟩ where *n* is a node in the control-flow graph (CFG) and *V* a subset of the program's variables [2]. A statement subset *S* is a slice when *whenever P halts for a given input, S also halts for that input, computing the same values for the variables in V whenever the statement at node n is executed.* At least one slice always exists — the program itself. A slice is *statement-minimal* if no other slice for the same criterion contains fewer statements; Weiser showed statement-minimal slices are not unique and that determining them is **undecidable** [2].

His algorithm iterates **data-flow equations** over the CFG, computing for each node the set of *relevant variables*: at the criterion node the set is *V*; elsewhere a variable is relevant if it is relevant at a successor and not redefined, or if it is used by a statement defining a relevant variable. Relevant statements plus their controlling predicates are collected, iterating to a fixed point. The formulation already exposes the two dependence relations that later work made explicit.

### 2.2 Data and Control Dependence

Modern treatments replace data-flow iteration with two binary relations on CFG nodes [4][6]:

- **Data dependence.** Node *j* is data-dependent on node *i* (*i →ᵈᵈ j*) if *i* defines a variable *v* that *j* uses, with a *definition-clear path* from *i* to *j* (no intervening redefinition of *v*).
- **Control dependence.** Node *j* is control-dependent on predicate *i* (*i →ᶜᵈ j*) if *i* has two successors *s₁, s₂* such that *j* postdominates *s₁* but not *s₂* [4].

*A slice is the transitive closure of the union of the data- and control-dependence relations, seeded at the criterion.* Forward slicing uses the inverse relations.

### 2.3 The Program Dependence Graph

Ottenstein and Ottenstein observed that slicing becomes trivial once dependences are reified as edges [3]. The **program dependence graph** (PDG) of a procedure has one vertex per statement/predicate plus an *entry* vertex, a *control-dependence edge* *i →ᶜ j* for each control dependence (labeled true/false), and a *data-dependence edge* *i →ᵈ(v) j* for each data dependence via variable *v*. Ferrante, Ottenstein, and Warren gave efficient construction algorithms and demonstrated the PDG's broad utility in optimization [4]. Slicing is then **backward reachability**: from the criterion vertex, follow control and data edges backward. Reachability is linear in graph size, so intraprocedural slicing is *O(|V| + |E|)* once the PDG is built.

> **Theorem:** (PDG slice soundness). Vertices reachable by backward traversal from the criterion form a valid static backward slice: every chain of value influence must pass through a data or control edge of the PDG [4][5].

| Concept | Criterion | Scope | Key structure |
|---|---|---|---|
| Backward static slice | ⟨*n*, *V*⟩, all inputs | Statements affecting *V* at *n* | PDG backward reachability |
| Forward static slice | ⟨*n*, *V*⟩, all inputs | Statements affected by *V* at *n* | PDG forward reachability |
| Dynamic slice | ⟨*x*, *I^q*, *V*⟩, one input *x* | Statements affecting *V* on trace | Dynamic dependence graph |
| Chop | ⟨*s*, *t*⟩ source and sink | Statements transmitting source→sink | Bidirectional PDG traversal |

## 3 Methodology

### 3.1 Static Slicing Algorithms

The two canonical static algorithms are **data-flow iteration** (Weiser [2]) and **PDG reachability** (Ottenstein–Ottenstein [3]). The PDG approach dominates in practice: dependence computation is amortized over many slicing queries, and the graph representation extends cleanly to the interprocedural setting via the **system dependence graph** (SDG). A *forward* slice — all statements influenceable by the criterion — reverses every edge and traverses forward; it underpins impact analysis and regression-test selection.

### 3.2 The Interprocedural Problem and the Calling-Context Pitfall

Extending PDGs to whole programs seems straightforward: one PDG per procedure, *call edges* from call sites to callee entries, *parameter-in/out edges* binding actuals to formals, and slicing as reachability over the resulting SDG [5]. But the naive approach is **unsound with multiple call sites**. If procedure `add(a,b)` is called at site *c₁* (whose result flows into the criterion) and at site *c₂* (whose result does not), a naive backward traversal enters `add` at *c₁*, crosses parameter-out edges into the body, follows data dependences to the formals — and exits through *c₂*'s parameter-in edges, wrongly pulling *c₂*'s actuals into the slice. The path *descends at c₁ and ascends at c₂*: no execution can realize it. Such **unrealizable paths** must be excluded; this is the *calling-context problem*. Weiser's original interprocedural algorithm suffered exactly this imprecision [2]; Horwitz, Reps, and Binkley gave the context-sensitive solution [5].

### 3.3 The Horwitz–Reps–Binkley Two-Pass Algorithm

The HRB algorithm partitions SDG edges into two sets. **Pass-1 edges:** control-dependence, flow-dependence, call edges, parameter-in edges, and *summary edges*. **Pass-2 edges:** control-dependence, flow-dependence, parameter-out edges, and summary edges.

**Summary edges** compress callee transitivity: a summary edge connects an actual-in vertex to an actual-out vertex at the *same* call site iff the corresponding formal-in can reach the formal-out inside the callee's PDG. They are computed by a preliminary worklist fixed-point over the SDG [5].

Given criterion vertex *s*:

- **Pass 1 (ascend):** traverse backward from *s* along pass-1 edges only — moving *up* through the call graph, never *down* into a callee (parameter-out edges excluded).
- **Pass 2 (descend):** traverse backward from *all vertices marked in pass 1* along pass-2 edges only — moving *down* into callees, collecting relevant procedure bodies.

> **Theorem:** (HRB correctness [5]). The union of vertices marked in the two passes is exactly the set of vertices reaching the criterion along a *realizable* path — one whose call/return edges form a balanced parenthesis structure per call site. The two-pass slice is therefore a valid interprocedural slice, maximally precise among dependence-graph reachability slices.

Intuition: every realizable path *v →* s* factors into an *ascending* segment (never entering a procedure at a call site) followed by a *descending* segment (never exiting upward) — precisely pass 1 then pass 2, joined at call sites marked by pass 1. No path can enter at site *c₁* and exit at *c₂*, because descent happens only from already-relevant call sites. Each edge is traversed at most once per pass: slicing is linear in SDG size after summary-edge computation.

```python
def hrb_two_pass_slice(sdg, criterion):
    """Horwitz-Reps-Binkley interprocedural backward slice."""
    marked = set()
    def traverse(starts, edges):
        worklist = list(starts)
        while worklist:
            v = worklist.pop()
            if v in marked: continue
            marked.add(v)
            worklist.extend(w for w in edges.get(v, []) if w not in marked)
    traverse([criterion], sdg['pass1_edges'])   # ascend only
    pass1 = set(marked)
    traverse(pass1, sdg['pass2_edges'])          # descend into callees
    return marked
```

### 3.4 Dynamic Slicing

Korel and Laski redefined the criterion to include a concrete input: ⟨*x*, *I^q*, *V*⟩, where *x* is the input, *I^q* the *q*-th occurrence of statement *I* in the execution trajectory *T* on *x*, and *V* the variable set [7]. A dynamic slice is an executable statement-deleted program whose trajectory on *x* agrees with *T* (modulo deletions) and matches *V*'s values at the *q*-th occurrence. Only dependences *exercised by the actual execution* count, so dynamic slices are typically far smaller than static ones — but valid only for that input.

Implementation strategies: **dynamic dependence graphs** (one node per executed occurrence; slicing as reachability) [8]; **reduced DDGs** that create nodes only when a new dynamic slice becomes possible, bounding graph size by distinct slices rather than trace length [8]; **forward computation** maintaining the slice incrementally along the trace (Korel–Yalamanchili); and **precise backward algorithms** with limited preprocessing, shown practical on real C programs by Zhang, Gupta, and Zhang [10]. Given a failing run, the dynamic slice on the wrong output value must contain the fault — and is far smaller than the static slice — which is why Agrawal, DeMillo, and Spafford built the *Spidery* debugger around dynamic slicing [8].

### 3.5 Conditioned Slicing and Chopping

**Conditioned slicing** (Canfora et al., 1998) requires behavior preservation for all inputs satisfying a condition *φ*, subsuming static (*φ ≡ true*) and dynamic (single-input *φ*) slicing [6]. A **chop** ⟨*s*, *t*⟩ — the statements transmitting effects from source *s* to sink *t*, i.e., forward-slice(*s*) ∩ backward-slice(*t*) — is the dependence-theoretic foundation of *taint analysis* (Section 4.4).

## 4 Deep Dive

### 4.1 The Calling-Context Problem, Formally

Label each call edge with "(*_i* " and each return edge with ")*_i*" for call site *i*. A path is *realizable* iff its label string is a correctly balanced parenthesis string (allowing unmatched "(*_i*" at the start — pass 1's ascending phase). Interprocedural slicing is thus an instance of **context-free-language (CFL) reachability**, the framework Reps later generalized to a broad family of program analyses [5]. The HRB two-pass algorithm is a linear-time specialization of CFL-reachability to the slicing query, exploiting summary-edge compression.

Why are *two* passes necessary and sufficient? A single backward pass excluding parameter-out edges never enters procedure bodies and misses callee-internal dependences; a single pass including them admits unrealizable paths. The decomposition insight is that every realizable path *v →* s* factors as *v →* c →* s*, where the first segment never *enters* a procedure at a call site and the second never *exits* one upward. Summary edges handle paths passing *through* a procedure (in at a call site, out at the same site's return) without breaking the decomposition: they are usable in both passes, so transitive callee effects are visible to pass 1 without descent.

### 4.2 Summary Edges: Computing Transitive Dependence Across Calls

For procedure *P* with formal-in *f_in* and formal-out *f_out*, a summary edge *actual_in → actual_out* is added at each call site iff *f_in →* f_out* inside *P*'s PDG. Computing all summary edges is a worklist fixed-point over the SDG: discovering a new *f_in →* f_out* path adds summary edges at all call sites of *P*, which may create new paths in callers, iterating to termination over the finite SDG [5].

> **Theorem:** (Summary-edge soundness). Slicing with summary edges is exactly as precise as slicing by full descent into procedure bodies: the summary edge introduces no spurious transmission beyond what some realizable interprocedural path exhibits [5].

Summary edges give the algorithm its *modularity*: once computed, pass 1 never re-descends into procedure bodies, which is why the algorithm scales where inlining-based approaches explode.

### 4.3 Dynamic Slicing: Precision, Cost, and the DDG Explosion

The central tension in dynamic slicing is **precision versus trace size**: a naive DDG has one node per executed occurrence, so a million-iteration loop yields a million nodes [8]. Three responses dominate: reduced DDGs bounded by distinct dynamic slices [8]; forward incremental slicing in *O(slice size)* memory; and demand-driven limited-preprocessing algorithms [10]. Empirically, Venkatesh found dynamic slices often an order of magnitude smaller than static ones [12], and Zhang et al. showed precise dynamic slicing adds only modest overhead while imprecise conservative variants bloat slices into uselessness [10]. A subtle theoretical refinement: the *path-faithful* criterion requires the slice's trajectory to preserve branching structure, not just values — strictly stronger than Korel and Laski's original KL1–KL3 conditions [14].

### 4.4 Slicing for Security: Information Flow, Taint Analysis, and Noninterference

Dependence is the common ancestor of slicing and information-flow security. **Noninterference** — secret (*high*) inputs do not influence public (*low*) outputs — is a statement about the *absence* of dependence paths: the program is secure iff no SDG path carries data or control dependence from a high source to a low sink. A backward slice from a low output containing a high input is a constructive *witness of interference*.

This makes slicing the engine of **taint analysis**: mark untrusted sources, compute the forward slice, check whether any sensitive sink is reached. Modern code property graphs (CPGs), fusing AST, CFG, and PDG into one queryable structure, are direct descendants of the SDG. The classical theory also explains taint analysis's chronic ailments: *implicit flows* are precisely the PDG's control-dependence edges, and any tracker ignoring them is unsound with respect to noninterference — a fact the slicing literature established decades before it became security folklore.

> **Theorem:** (Slicing characterizes explicit-flow noninterference). *P* satisfies termination-insensitive noninterference iff for every low-observable criterion, the backward SDG slice contains no high-source vertex. The *termination-insensitive* qualifier is essential: the slice condition constrains *what* is output, not *whether* the program halts — the termination covert channel.

## 5 Empirical Results and Theoretical Guarantees

### 5.1 What the Experiments Say

The empirical literature — surveyed by Binkley and Harman (2004) [11] — reports robust findings:

| Study | Subjects | Key finding |
|---|---|---|
| Weiser 1982 [16] | professional programmers | Slicers debug faster; better understanding |
| Venkatesh 1995 [12] | C programs | Dynamic slices ≪ static; practical overhead |
| Zhang–Gupta–Zhang 2003 [10] | C programs | Precise dynamic slicing practical |
| Binkley–Harman 2004 [11] | 30+ studies surveyed | Avg. static slice ~1/3 of program; bimodal |
| Jhala–Majumdar 2005 [17] | C programs | Path slicing isolates error paths for model checking |

### 5.2 Complexity and Decidability Landscape

- **Statement-minimal slices are undecidable** (Weiser [2]): no algorithm always produces the smallest slice; all slicers compute conservative approximations.
- **Intraprocedural slicing is linear** in PDG size (reachability); PDG construction is near-linear with SSA-based sparse data-dependence computation [4].
- **Interprocedural slicing** via HRB is linear in SDG size *given summary edges*; summary-edge computation is the dominant, *O(V·E)*-bounded cost [5].
- **Dynamic slicing** decision problems for program schemas have nontrivial complexity classifications, with path-faithful variants strictly harder than value-based ones [14].
- **Conditioned slicing** is undecidable in general (it embeds theorem proving over *φ*); practical tools use bounded symbolic execution [6].

## 7 Conclusion

Forty-five years after Weiser asked which statements could affect a value, program slicing stands as a rare idea that is simultaneously a crisp formal theory, an efficient family of algorithms, and a practical engineering tool. The arc from data-flow equations to program dependence graphs [3][4], from naive interprocedural reachability to the Horwitz–Reps–Binkley two-pass algorithm [5], and from all-inputs static slicing to single-trace dynamic slicing [7][8] shows a field repeatedly trading generality for precision — and finding the precision worth the price.

The deepest lesson is architectural: **make dependences explicit as a graph, and hard program problems become graph problems.** Slicing becomes reachability; interprocedural precision becomes CFL-reachability; taint analysis becomes a chop query; variant integration becomes slice-and-merge [13]. The SDG was arguably the first *code property graph*, and its descendants now underwrite vulnerability detection at industrial scale. Open challenges remain where assumptions break — the heap, concurrency, the undecidability of minimality — yet the core promise holds: a machine can, automatically and soundly, show a human *only the code that matters*.
