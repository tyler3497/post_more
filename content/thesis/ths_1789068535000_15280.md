# Certified Compilation: CompCert, Verified C Semantics, and the Preservation of Observable Behavior

## Abstract

CompCert is the first realistic, optimizing C compiler accompanied by a complete, mechanically checked proof that it preserves the observable behavior of its source programs. Developed primarily in the Coq proof assistant, CompCert translates a large subset of C99 (CompCert C, formerly Clight) into assembly for PowerPC, ARM, RISC-V, x86, and x86-64 targets through roughly a dozen intermediate languages, with each translation pass verified by a forward-simulation argument between small-step operational semantics [1][2]. This dissertation-style study reconstructs the architecture of CompCert: its layered language pipeline, its block-structured memory model, the simulation relations that constitute its soundness proof, and the engineering discipline — the *trusted computing base* — that keeps the proof meaningful. We examine the proof mechanics of individual passes (front-end translation, RTL optimizations, register allocation, instruction scheduling), quantify the empirical performance and defect-detection record of the compiler, and assess its limits: unverified parsing and assembly, compiler bugs in the Coq kernel's trusted base, and the semantic gaps between ISO C and the CompCert C model. The result is a portrait of what compiler verification buys, what it cannot buy,

## 1 Introduction

Can you trust your compiler? Compilers are, by convention, treated as semantically transparent: the machine code they emit is expected to behave exactly as prescribed by the semantics of the source program. Yet production compilers are among the most complicated symbolic-transformation systems in existence, and despite enormous testing effort, miscompilation bugs — where an *optimizing* pass silently changes program meaning — occur with distressing regularity. For critical software in avionics, automotive control, or medical devices, such bugs are not merely embarrassing; they invalidate the safety arguments constructed at the source level, since a proof of `P` about source code means nothing if the compiler maps the program to executable code that violates `P`.

The radical response is to *prove the compiler correct*. Xavier Leroy's CompCert project, begun in 2005 at INRIA, did exactly that: it is a compiler from a substantial subset of the C language to PowerPC assembly (later extended to ARM, RISC-V, and x86 targets), written predominantly inside the specification language of the Coq proof assistant, with a machine-checked proof that every compilation phase preserves program semantics [1]. A high-level account of the full system was given by Leroy in 2009, describing a compiler mature enough for industrial use in safety-critical embedded systems [2].

> **Theorem (Semantic preservation, informal).** *For any CompCert C source program `S`, if `compile(S) = Some(T)` then the target program `T` exhibits only behaviors that are also behaviors of `S`, modulo the refinement of observable events.*

This thesis unpacks that theorem: what "behavior" means formally, how twenty-odd intermediate passes compose into one end-to-end guarantee, what the proof trusts but does not verify, and where the approach falls short. Section 2 surveys the verification landscape; Section 3 describes the method — forward simulation over small-step semantics and the memory model that makes it tractable; Section 4 dissects the language pipeline, the simulation proof technique, the memory model, and the trusted computing base; Section 5 presents empirical evidence of CompCert's effectiveness; Section 6 catalogues its limitations; Section 7 concludes.

## 2 Background

### Compiler correctness: the problem space

Formally, compiler verification means establishing a property `Prop(S, C)` relating a source program `S` and compiled code `C` — for example, that the observable behaviors of `C` refine those of `S`. Three broad strategies have been pursued [1]:

1. **Certified compilers.** The compiler is proved correct once and for all; every run is then covered by the theorem. CompCert is the canonical example.
2. **Certifying compilers (translation validation).** Each compilation is accompanied by a *verifier* that checks `Prop(S, C)` per run; only the verifier (or its certificate) needs trust.
3. **Proof-carrying / independent checking.** The compiler emits a proof that a checker can verify independently, so neither the compiler nor its producer needs trust.

CompCert follows strategy (1), but — unusually — the compiler itself is *programmed* in Coq, extracted to executable OCaml, so the code that is proved is essentially the code that runs. The proof development spans well over 100,000 lines of Coq, making it one of the largest mechanically checked correctness proofs of a production-scale software artifact.

### Small-step semantics and observable events

Every CompCert language is given an operational semantics in the *small-step* style: configurations `σ` (register state, memory, program point) reduce by single transitions `σ → σ'`. The sequence of transitions, together with externally observable events (calls to external functions, volatile accesses, I/O), defines the *behavior* of a program: it may terminate with an exit code, diverge (loop forever, possibly producing an infinite event trace), or go wrong (encounter undefined behavior, e.g. a stuck configuration) [2].

The correctness theorem is stated in terms of behavior refinement:

> **Theorem (Behavior refinement).** *If `compile(S)` succeeds producing `T`, then `Behaviors(T) ⊆ Behaviors(S)` modulo event-trace refinement: every observable trace of `T` — including termination and divergence — is a legal trace of `S`, except that `T` may define strictly more behaviors when `S` goes wrong (the compiler may exploit undefined behavior).*

The "goes wrong" clause is the standard license taken by all C compilers: after undefined behavior, anything is permitted. CompCert is allowed, like GCC, to optimize aggressively under this clause, but it cannot *introduce* wrongness into a program that has none.

### The intermediate-language pipeline

CompCert is not verified monolithically. It is decomposed into roughly a dozen compilation passes through a ladder of intermediate languages — Clight, Cminor, RTL, LTL, LTLin, Linear, Mach, and Asm, among others — each equipped with its own formal semantics [2]. Each pass is proved correct *locally*: given a source program in language `L₁` and its translation to `L₂`, a simulation relation connects their executions. The global theorem then follows by *composition* of simulations, a compositionality property that is the architectural key to the entire project.

The front end — from CompCert C through Clight to Cminor — was itself a substantial verification effort, documented separately by Blazy, Dargaye, and Leroy [3], while the optimizing back end from Cminor to PowerPC assembly is covered in Leroy's journal-length treatment [4].

### Prior and parallel efforts

Compiler verification has a long prehistory (McCarthy and Painter's 1967 sketch; the Verifix and CLI-stack projects), but none produced an optimizing compiler for a realistic language at CompCert's scale. CompCert's success catalyzed a field: CakeML (a verified ML compiler) adopted its simulation-based methodology, and verified separate compilation [7] and verified static analyzers built on CompCert's memory model followed. The 2021 ACM Software System Award recognized CompCert as "the first practically useful optimizing compiler targeting multiple commercial architectures that has a complete, mechanically checked proof of its correctness" [8].

## 3 Methodology

### The simulation proof technique

The core proof obligation for each pass is a **forward simulation** (also called a refinement proof). Suppose pass `P` maps programs in language `L₁` to programs in `L₂`. We define a *matching relation* `~` between states of the two languages' small-step semantics and prove:

> **Theorem (Forward simulation).** *If `P(S) = T` and `σ₁ ~ σ₂` where `σ₁` is a state of `S` and `σ₂` a state of `T`, then every step `σ₁ →₁ σ₁'` can be matched by zero or more steps `σ₂ →₂* σ₂'` with `σ₁' ~ σ₂'`, and observable events are preserved in order.*

The "zero or more steps" clause is essential: optimizations may delete code (dead-code elimination), fold constants, or reorder instructions, so one source step may correspond to several target steps — or none at all. The special case of *lock-step* simulation (one-to-one) applies to passes like instruction selection; the general form handles optimizing transformations. From forward simulation plus determinism-ish conditions on the target semantics, the behavior-refinement theorem follows: every target trace is a source trace [4].

Proving one simulation per pass is feasible precisely because the intermediate languages are *close*: each pass changes little (e.g., RTL → LTL is mostly register allocation), so the matching relation is simple and the proof small relative to the pass itself. This "climbing the ladder one rung at a time" design is what made a 100,000-line proof tractable at all.

### The block-structured memory model

C's memory model is notoriously subtle: pointer arithmetic, casts between pointers and integers, `malloc`/`free`, and partially overlapping objects. CompCert abstracts memory as a **collection of disjoint blocks**, each block a finite array of bytes with a unique identifier `b`, and a pointer is a pair `(b, ofs)` of block and byte offset [5]. Operations include:

| Operation | Semantics |
|---|---|
| `alloc(m, lo, hi)` | Fresh block `b` with valid offsets `[lo, hi)` |
| `free(m, b)` | Block `b` becomes invalid |
| `load(m, κ, b, ofs)` | Read memory chunk `κ` at `(b, ofs)` |
| `store(m, κ, b, ofs, v)` | Write chunk `κ`, value `v` |

Loads and stores are defined only when the access is in-bounds and the chunk type matches the stored value — otherwise the semantics *goes wrong*, modelling undefined behavior.

### Correctness-relevant versus performance-relevant code

A recurring engineering insight of the project is the separation of *correctness-relevant* from *performance-relevant* aspects of an algorithm [1].

### The trusted computing base (TCB)

No verification is absolute; every proof rests on axioms and unverified infrastructure.

1. **The Coq kernel** (type checker) — assumed sound.
2. **The formal semantics** of CompCert C and of the target assembly — assumed to faithfully model reality. A bug in the semantics is a bug in the theorem's *meaning*, not its proof.
3. **The parser** from C text to CompCert C abstract syntax — unverified OCaml [2].
4. **The assembler and linker** — unverified; CompCert emits assembly text.
5. **Coq's extraction** to OCaml and the OCaml runtime.
6. **Axioms** used in the development (functional extensionality, classical logic fragments).

Items 3–5 are shared with any compiler workflow; the verification *shrinks* the TCB from "the entire compiler" to "specifications plus front/back plumbing," a qualitatively different and far smaller attack surface.

## 4 Deep Dive

### 4.1 The language ladder: Clight to Asm

The pipeline descends from a high-level C-like language to machine code in carefully graded steps.

```haskell
-- Conceptual view of the CompCert language ladder (simplified)
data Stage = Clight        -- structured C: loops, switches, block exprs
           | Cminor         -- structured control only; explicit stack frames
           | RTL            -- control-flow graphs, pseudo-registers, 3-addr code
           | LTL            -- RTL + physical registers after allocation
           | LTLin          -- linearized basic blocks
           | Linear         -- explicit stack slots, no pseudo-registers
           | Mach           -- activation records, spilling, frame layout
           | Asm            -- target assembly (PowerPC/ARM/RISC-V/x86)
```

Passes between adjacent stages are individually verified.

- **Clight → Cminor** (front end): eliminates C's expression evaluation order subtleties and block-scoped variables, producing a simpler imperative core [3].
- **Cminor → RTL**: translation to a control-flow-graph representation with infinite pseudo-registers — the substrate for most optimizations.
- **RTL optimizations**: constant propagation, common-subexpression elimination, dead-code elimination, function inlining, tail-call optimization — each verified by simulation against unoptimized RTL semantics.
- **RTL → LTL**: register allocation via graph coloring with a verified validator, as described above.
- **LTLin → Linear → Mach**: branch tunneling, linearization, stack-slot assignment, spilling, and construction of activation records — the "calling convention" layer where the simulation relation must handle stack frames [4].
- **Mach → Asm**: pretty-printing to assembly text; verified down to a formal model of the target ISA.

The architecture is deliberately *linear*: no pass needs global knowledge of any other, and the end-to-end theorem is the transitive closure of per-pass simulations.

### 4.3 The memory model and its refinements

The block model of Section 3 is not static across the pipeline: it is *refined* as compilation descends.

> **Theorem (Injection composition).** *If `μ₁` injects memory `m₁` into `m₂` and `μ₂` injects `m₂` into `m₃`, then `μ₂ ∘ μ₁` injects `m₁` into `m₃`, preserving the values of all defined loads.*

Stack-frame construction is the hardest injection proof: locals of several source blocks are packed into one target block at computed offsets, and the proof must show no overlap and no out-of-bounds escape.

### 4.4 The trusted computing base, precisely

The TCB deserves a second, sharper look, because it determines what "verified" actually guarantees:

1. **Specifications.** The ~15,000 lines defining the semantics of CompCert C and the target ISAs are *assumed*, not proved. If the PowerPC semantics mis-models a carry flag, the theorem is vacuous for real hardware.
2. **Parsing.** The C parser (an unverified Menhir/OCaml front end) is outside the proof; a parser bug means the proved property applies to a *different program* than the user wrote [2].
3. **Assembly and linking.** CompCert emits assembly *text*; the assembler, linker, and loader are trusted.
4. **Extraction.** Coq extraction to OCaml is unverified; the OCaml compiler and runtime are trusted. (The extracted compiler is, however, *tested* against the Coq-evaluated reference.)
5. **The Coq kernel itself** — a few thousand lines of OCaml implementing dependent type checking. Bugs here are rare but not inconceivable.

The net guarantee is therefore: *modulo the fidelity of the C and assembly specifications, the parser, assembler, linker, extraction, and the Coq kernel, the generated machine code refines the source semantics.* This is enormously stronger than "we tested the compiler," but it is not — and never claimed to be — absolute.

## 5 Empirical Results and Proofs

### The end-to-end theorem, stated

The composition of all per-pass simulations yields the headline result, proved in Coq and checked by the kernel:

> **Theorem (CompCert correctness).** *For every CompCert C source program `S` and target assembly `T`, if `compcert(S) = OK(T)` then `Behaviors(T) ⊆ Behaviors(S)` up to trace refinement, where behaviors are defined by the small-step semantics of [2] and the ISA models of [4].*

```tla+
---- MODULE CompCertCorrectness ----
EXTENDS Naturals, Sequences
CONSTANTS SourceProg, TargetProg
VARIABLES ok
CompileOK == ok = TRUE
\* The proved property, in TLA+ flavor:
BehaviorRefinement ==
    CompileOK => \A t \in Behaviors(TargetProg) :
                     \E s \in Behaviors(SourceProg) : Refines(t, s)
====
```

### Industrial adoption and performance

CompCert has been deployed in safety-critical contexts — notably avionics software — where compiler qualification under standards like DO-178C otherwise forces developers to *disable optimizations* and manually review generated assembly, a costly process [2]. Because the optimizations are inside the verified perimeter, CompCert can optimize aggressively while remaining qualifiable.

Performance measurements consistently place CompCert-generated code at roughly **twice the speed of GCC `-O0`** and within about **20% of GCC `-O1`/`-O2`** on typical embedded benchmarks — far better than the unoptimized code that qualification regimes previously mandated, though below a fully optimizing GCC or Clang [6].

### Defect record

The strongest empirical evidence for the methodology is negative: in over a decade of industrial and research use, **no miscompilation bug has ever been found in the verified passes** of CompCert — every confirmed miscompilation traced to the TCB (parser, assembler) or to the formal semantics themselves. By contrast, differential testing campaigns (e.g., Csmith-style random program generation) routinely find hundreds of miscompilation bugs in GCC and LLVM over comparable periods, and a 2011 study on a development version of CompCert confirmed the verified core's resilience to the bug classes that plague conventional compilers [6].

### Verified separate compilation and linking

A significant extension, CompCertELF, proved correct the separate compilation of C translation units into ELF object files and their linking — closing a gap in the original theorem, which covered whole programs only [7]. The proof introduces a notion of *semantic linking* of behaviors across compilation units, showing that the methodology scales beyond closed programs to realistic build workflows.

### Recognition

In 2021, Xavier Leroy, Sandrine Blazy, Zaynah Dargaye, Jacques-Henri Jourdan, Michael Schmidt, Bernhard Schommer, and Jean-Baptiste Tristan received the **ACM Software System Award** for CompCert, cited as "the first practically useful optimizing compiler targeting multiple commercial architectures that has a complete, mechanically checked proof of its correctness" [8]. The compiler is maintained both as a research artifact at Inria and as a commercial product by AbsInt, which provides industrial support and qualification kits [6].

## 6 Limitations

1. **The semantics gap.** CompCert C is a *large subset* of C99, not all of it: `long double`, variable-length arrays, `setjmp`/`longjmp`, unstructured `goto` into blocks, and most of the C library's semantics are unsupported or restricted. Programs outside the subset are rejected — sound, but limiting. More subtly, where ISO C leaves behavior *unspecified* (e.g., evaluation order), CompCert C *fixes* a choice; the theorem is relative to CompCert's semantics, not the standard's [2][4].

2. **Unverified plumbing.** As detailed in §4.4, the parser, assembler, and linker are outside the proof. A miscompilation through any of them is entirely possible; only the middle is verified [2].

3. **Specification trust.** The C and ISA semantics are large, human-written specifications. A specification bug does not break the proof — it breaks the *meaning* of the theorem. Validating specifications against real hardware and against the C standard remains manual, expert work.

4. **Performance ceiling.** The oracle-plus-validator architecture buys proof tractability at the cost of optimization sophistication: CompCert performs classical optimizations but lacks loop nest optimization, vectorization, profile-guided optimization, and the aggressive inlining of modern compilers. The ~20% gap to GCC `-O1` is structural, not incidental [6].

5. **Separate compilation and concurrency.** The original theorem addressed whole, sequential programs; verified separate compilation [7] is recent and still maturing, and CompCert's semantics for concurrency (the C11 memory model, atomics, threads) is essentially absent — a frontier for the field, not a solved problem.

6. **Proof maintenance.** The 100,000+ lines of Coq are a living artifact: every new optimization or target architecture is a multi-person-year proof effort. Verification scales with *proof engineering*, and the project's velocity is bounded by the supply of experts fluent in both compiler internals and dependent type theory.

## 7 Conclusion

CompCert demonstrated, against decades of skepticism, that a realistic optimizing compiler can be *proved* correct — not tested into confidence, not argued informally, but checked by machine down to the last simulation diagram. Its technical contributions are architectural as much as logical: the ladder of intermediate languages that makes per-pass simulation feasible, the block-structured memory model with composable injections, the oracle-plus-validator pattern that admits sophisticated heuristics into a verified pipeline, and the honest accounting of a trusted computing base that keeps the theorem meaningful rather than absolute [1][2][4].

The project's legacy is a changed default: where once "verified compiler" meant a toy language compiled by a verified-but-useless prototype, it now means a compiler you can buy, qualify for avionics, and run at 80% of GCC's speed with a machine-checked guarantee that your source-level safety arguments survive compilation [6][8]. The remaining frontiers — concurrency, richer C coverage, verified linking at scale [7], and closing the optimization gap — define the research program CompCert inaugurated. The deepest lesson may be methodological: verification succeeded not by proving a big thing all at once, but by designing the compiler *so that* it could be proved — a discipline of proof-aware engineering that generalizes far beyond compilation.
