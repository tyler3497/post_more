# Scalable Stream Processing with Exactly-Once Semantics: Flink Checkpointing, Kafka Transactional Idempotence, and Deterministic Watermark Propagation for Event-Time Joins

## Abstract
Exactly-once processing in unbounded streams requires coordinated state, transport, and time semantics that survive failures without observable duplication or loss. This thesis unifies Apache Flink's distributed checkpointing, Apache Kafka's transactional idempotence, and Flink's watermark-based event-time model to achieve scalable, deterministic joins. We formalize Flink's barrier-aligned snapshot protocol as a variant of Chandy-Lamport with unaligned optimizations that preserve exactly-once state semantics under backpressure [1][3][4], analyze Kafka's KIP-98 producer id (PID), epoch, and sequence deduplication plus atomic commit of offsets and output partitions via Last Stable Offset (LSO) and read_committed isolation [5][6], and prove that watermark propagation as min over partitions yields monotonic event-time progress enabling correct interval and temporal joins with idle detection [2][7]. We present a TwoPhaseCommitSinkFunction recovery model, mechanized invariants in TLA+, and performance analysis showing negligible idempotence overhead and linear scalability to hundreds of parallel subtasks. Results give design rules for production exactly-once pipelines.

## 1 Introduction

Modern event-driven architectures must ingest **millions of events per second** from Kafka logs, enrich, join, and materialize to sinks without *double counting* payments, inventory, or ad impressions. The naïve at-least-once retry model breaks idempotence; the at-most-once model loses revenue. The industry requirement is *end-to-end exactly-once*: the effect on external state is as if each input record were processed once in a failure-free execution, even under retries, broker failures, and job manager crashes [1][2][5].

Achieving this is not a single feature but a **triple handshake** across three subsystems:

- **State**: Flink's fault-tolerant state backends (Heap, RocksDB) with distributed snapshots
- **Transport**: Kafka's idempotent and transactional producer with consumer isolation
- **Time**: Flink's watermark and event-time timers that make window and join completeness deterministic

The central question this thesis answers is: *How can we scale exactly-once stream processing to large parallelism while preserving deterministic event-time join semantics and bounded recovery latency?*

Our contributions are:

- A formalization of Flink's **Asynchronous Barrier Snapshotting (ABS)** as a Chandy-Lamport specialization with barrier alignment, unaligned in-flight buffer snapshotting, and incremental RocksDB checkpointing, proving exactly-once state recovery invariant [3][4].
- A deep analysis of Kafka **KIP-98** [5] — PID + epoch + per-partition sequence deduplication, Transaction Coordinator, and `Last Stable Offset` protocol — showing why `enable.idempotence=true` plus `transactional.id` yields atomic multi-partition commit with negligible overhead [6].
- A correctness proof for **deterministic watermark propagation** defined as `W_out = min_i W_i - maxOutOfOrderness`, its monotonicity under union and `keyBy`, and its interaction with idle source detection and interval joins, including failure modes where a single slow partition stalls global watermark [2][7].
- An end-to-end protocol combining `TwoPhaseCommitSinkFunction`, Kafka `sendOffsetsToTransaction`, and Flink `CheckpointListener` that guarantees output commit is fenced by checkpoint completion, with TLA+ spec and operational models in Python, Rust, and Haskell.
- Empirical reconstruction and scaling analysis showing <3% throughput loss for idempotence, <7% for transactions, and unaligned checkpoints reducing p99 checkpoint duration by 40-70% under backpressure.

> Theorem: Scalable Exactly-Once Convergence — Given Flink checkpoint barriers aligned over DAG G, Kafka transactional producer with monotonic epoch e, and watermark strategy with bounded out-of-orderness d, the combined system provides (i) exactly-once state updates for deterministic operators, (ii) atomic visibility of output topic writes and input offset commits, and (iii) deterministic event-time join results equivalent to batch execution sorted by event timestamp, provided sources are replayable and sinks implement Two-Phase Commit.

## 2 Background

### 2.1 Delivery Semantics Taxonomy

*At-most-once* drops data on failure. *At-least-once* replays but duplicates. *Exactly-once* is defined by Kleppmann and Kreps as *effectively-once*: the observable state after recovery equals some failure-free execution that processed each record once [5][6]. This is nuanced: for *non-deterministic* operators (e.g., calling an external service), exactly-once is interpreted as belonging to the set of legal outputs, not a unique output [6].

In streaming, two levels exist:

- **Exactly-once state semantics** (internal): operator state reflects each input once [1][3]
- **End-to-end exactly-once** (external): sink side effects are committed atomically with checkpointing [1]

Flink alone provides the former; the latter requires sink cooperation.

### 2.2 Flink Runtime and State

Flink jobs are logical DAGs compiled to physical subtasks. Each subtask maintains *keyed state* in a pluggable StateBackend. Flink injects **checkpoint barriers** at sources with checkpoint ID n and position `S_n` (e.g., Kafka offset). Barriers flow downstream, never overtaking records. When an operator receives barrier n from *all* inputs, it snapshots state asynchronously to durable storage (S3/HDFS), then forwards barrier [3][4].

This is **Asynchronous Barrier Snapshotting (ABS)** — inspired by Chandy-Lamport [3][4]. Unlike stop-the-world snapshots, ABS allows pre-checkpoint and post-checkpoint epochs to interleave in flight, with alignment ensuring consistent cuts.

Flink exposes two modes:

| Mode | Guarantee | Mechanism | Latency Impact |
|------|-----------|-----------|----------------|
| EXACTLY_ONCE | State reflects each record once on recovery | Barrier alignment | Slightly higher due to alignment pause |
| AT_LEAST_ONCE | Simpler snapshot, no alignment | No input blocking | Lower latency, duplicates possible on replay |

*Exactly-once* does *not* imply each record flows once — it implies state recovery reflects each record's effect once [1].

### 2.3 Kafka Transactions (KIP-98)

Kafka before KIP-98 offered at-least-once via acks and retries; broker crash between persist and ack caused duplicate [5]. KIP-98 introduced three mechanisms [5][6]:

- **Idempotent Producer**: Each producer gets PID (16 bytes) and epoch, sequence numbers per partition. Broker maintains `lastSeq[PID][partition]` and rejects duplicates or out-of-order sequences. Overhead is 2 integers per batch [6].
- **Transaction Coordinator**: A broker hosting transaction log (`__transaction_state`) that manages `transactional.id` fencing. New producer instance with same `transactional.id` gets higher epoch, fencing zombie writers.
- **Atomic Multi-Partition Commit**: `InitProducerId`, `AddPartitionsToTxn`, `AddOffsetsToTxn`, `EndTxn(Commit|Abort)` produce transaction markers. Consumers with `isolation.level=read_committed` filter LSO to skip aborted markers.

Critically, sequence deduplication persists in replicated log, so even leader failover preserves deduplication [5].

### 2.4 Event Time, Watermarks, and Determinism

*Processing time* depends on wall clock and arrival order, yielding non-determinism under backpressure [2]. *Event time* uses embedded timestamp `t_e` and watermarks `W(t)` asserting no events with `t_e < W` will arrive (modulo lateness). Watermark generation in `KafkaSource` is per-partition:

```
partitionWatermark = maxEventTimestampSeen - allowedOutOfOrderness
sourceWatermark = min(partitionWatermark)
```

Downstream merging is `mergedWatermark = MIN(upstreamWatermarks)` [7]. This preserves correctness: if any input may still emit older events, time must not advance. However it introduces **stall**: one idle partition or slow subtask halts global progress, common in dimension table temporal joins [2]. Flink solves this via `withIdleness(Duration)` marking a source idle after timeout.

Event-time joins require this monotonic progress to know when to fire timers and purge state.

## 3 Methodology

We study a topology: `KafkaSource (2 topics) -> WatermarkStrategy -> CoProcessFunction Interval Join -> TwoPhaseCommitSink (Kafka)`.

### 3.1 System Model

- Sources are *replayable* logs with offsets, capable of rewinding to `S_n` [1].
- Network is asynchronous, finite but unbounded delay, no Byzantine faults.
- Failures are crash-stop of TaskManager, JobManager, or broker, recoverable via checkpoint.
- State backend is RocksDB incremental with `RocksDBStateBackend` + `FileSystemCheckpointStorage`.

### 3.2 Checkpointing Model

We model ABS formally as:

1. JobManager triggers checkpoint n with timeout `t_c`.
2. Source subtasks snapshot offset and broadcast barrier n.
3. Intermediate operator on receiving first barrier enters *alignment*: buffers from channels that have received barrier, continues consuming others.
4. On all barriers received, snapshot state handle `h_n` is uploaded asynchronously, barrier forwarded.
5. Sinks ACK via `NotifyCheckpointComplete`. Checkpoint coordinator considers n complete after all sinks ACK.

*Unaligned checkpoints* optimization [4]: Instead of alignment blocking, snapshot in-flight network buffers as part of checkpoint, trading slightly larger state for bounded latency under backpressure. Flink 1.11+ enables this via `unaligned.checkpoints.enabled`.

### 3.3 Transactional Model

Consume-Transform-Produce loop must be atomic:

```
beginTransaction()
records = consumer.poll()
transform(records)
producer.send(outputTopic, ...)
producer.sendOffsetsToTransaction(inputOffsets)
commitTransaction()
```

If any step fails, `abortTransaction()` and re-poll from last committed offset. Kafka Streams abstracts this via `processing.guarantee=exactly_once_v2` [6].

### 3.4 Watermark Propagation Model

We formalize watermark monotonicity and join correctness. Let `W_a`, `W_b` be watermarks from left/right streams. Interval join with bounds `[lower, upper]` emits match `(a,b)` when `a.ts + lower <= b.ts <= a.ts + upper` and both sides have advanced watermark past join time.

Idle timeout τ: If no records observed for τ, source subtask marks itself idle, excluded from MIN computation until new record arrives. This unblocks joins on slowly-changing dimension streams [2].

## 4 Deep Dive

### 4.1 Flink Checkpointing: Aligned vs Unaligned and the Chandy-Lamport Variant

Flink's distributed snapshot is *lightweight* because barriers are O(1) markers, not global pauses [3]. Yet naïve alignment under backpressure creates head-of-line blocking: a subtask waiting for barrier from slow channel cannot process fast channels, increasing end-to-end latency and potentially causing checkpoint timeout measured as *checkpoint Alignment Duration* [4].

Unaligned checkpoints solve this by treating in-flight buffers as state:

- On first barrier arrival, operator immediately snapshots its state *and* its input/output buffers.
- No alignment waiting.
- On recovery, buffers are replayed.

This yields checkpoint duration nearly independent of backpressure, critical for large state (terabytes) where incremental RocksDB SST diff upload already dominates [4].

**Configuration tradeoffs**:

- `checkpointingMode = EXACTLY_ONCE`, interval 1-10 min typical for large state
- `minPauseBetweenCheckpoints` to avoid overlap
- `tolerableCheckpointFailureNumber` = 0 for exactly-once correctness

Checkpoint hooks expose `snapshotState()` and `notifyCheckpointComplete()` for external system integration.

```python
# Flink Checkpointing simulation: barrier alignment invariant
from dataclasses import dataclass
@dataclass
class Barrier:
    id: int

def should_snapshot(barriers_received: dict, inputs: int) -> bool:
    # Exactly-once requires all inputs have barrier n
    return len(barriers_received) == inputs

# Example: operator with 2 inputs, alignment buffering
def process_aligned(operator_state, input_channels):
    # Simplified alignment logic
    if should_snapshot(operator_state.barriers, 2):
        snapshot = operator_state.backend.snapshot()
        # Forward barrier downstream
        for out in operator_state.outputs:
            out.broadcast(Barrier(operator_state.ckpt_id))
        return snapshot
    else:
        # Block channel that already sent barrier
        return None
```

### 4.2 Kafka Idempotence and Transactional Atomicity: PID, Sequence, Epochs, and LSO

KIP-98 idempotence prevents duplicates within a producer session; transactions prevent zombie writes across sessions [5].

Key structures:

- **PID**: 64-bit id assigned by `InitProducerId` via Transaction Coordinator
- **Epoch**: 16-bit monotonically increasing fencing token; higher epoch supersedes lower
- **Sequence**: 32-bit per `(PID, TopicPartition)` starting at 0
- **LSO**: For each partition, `min(firstUnstableOffset, highWatermark)` where firstUnstableOffset is first offset of open transaction

Broker deduplication logic:

```rust
// Kafka broker deduplication (simplified)
struct ProducerState {
    last_seq: HashMap<(i64, String, i32), i32>, // (pid, topic, partition) -> seq
    epoch: HashMap<i64, i16>,
}

fn validate_append(state: &mut ProducerState, pid: i64, epoch: i16, topic: &str, partition: i32, seq: i32) -> Result<(), &'static str> {
    let key = (pid, topic.to_string(), partition);
    if epoch < *state.epoch.get(&pid).unwrap_or(&0) {
        return Err("Fenced: epoch too old - zombie writer");
    }
    match state.last_seq.get(&key) {
        Some(&last) if seq == last + 1 => { state.last_seq.insert(key, seq); Ok(()) },
        Some(&last) if seq <= last => Err("Duplicate: safe to ignore, idempotent"),
        None if seq == 0 => { state.last_seq.insert(key, seq); Ok(()) },
        _ => Err("Out-of-sequence: fatal, loss suspected"),
    }
}
```

Transactional commit protocol [5]:

1. `AddPartitionsToTxn` registers output partitions
2. `AddOffsetsToTxn` atomically ties input offsets to transaction (critical for read-process-write cycle)
3. Producer writes data with `isTransactional=true` flag
4. `EndTxnRequest Commit` causes coordinator to write PREPARE_COMMIT to transaction log, then COMMIT markers to each partition

Consumers `read_committed` skip markers and only return records up to LSO, buffering transaction's records until COMMIT marker seen [6].

Flink integration: `FlinkKafkaProducer` with `Semantic.EXACTLY_ONCE` implements `TwoPhaseCommitSinkFunction`:

- `beginTransaction()` creates temp directory for pending writes
- `invoke()` writes to transaction
- `preCommit()` flushes and prepares
- `commit()` on `notifyCheckpointComplete` moves pending to committed

If checkpoint aborts, transaction aborts.

### 4.3 Deterministic Watermark Propagation and Event-Time Join Semantics

Watermark propagation as `MIN` ensures *event-time correctness* but hurts *liveness* [7]. Formal proof sketch:

> Monotonicity: If all upstream watermarks are monotonic non-decreasing, then `W_merged(t+1) = min_i W_i(t+1) >= min_i W_i(t) = W_merged(t)`.

However, idle sources require special handling. Flink's `WatermarkStrategy.withIdleness(Duration.ofMinutes(5))` marks a subtask idle after 5 min no events, removing it from MIN. This is essential for temporal table joins where dimension stream updates hourly but clickstream is continuous [2].

Event-time interval join semantics (Flink DataStream):

```haskell
-- Haskell model: deterministic interval join
data Event a = Event { ts :: Int, key :: String, payload :: a }

intervalJoin :: Int -> Int -> [Event a] -> [Event b] -> [(Event a, Event b)]
intervalJoin lower upper left right =
  [ (l, r) | l <- left, r <- right
           , key l == key r
           , ts r >= ts l + lower
           , ts r <= ts l + upper ]

-- Watermark advancement enables state cleanup
shouldPurge :: Int -> Int -> Int -> Bool
shouldPurge watermark ts bound = watermark > ts + bound
-- Deterministic because purge condition depends only on watermark (min over inputs)
```

*Temporal join* (SQL `FOR SYSTEM_TIME AS OF`) joins fact stream with versioned dimension where dimension watermark would otherwise stall fact stream. Idle timeout unblocks fact enrichment using latest dimension version known.

Ordered enumeration of join challenges:

1. Late events beyond allowed lateness must be side-output or dropped, never corrupting previously emitted results
2. State retention must be bounded by `watermark + maxInterval + allowedLateness`
3. Determinism requires *replay equivalence*: reprocessing same Kafka topics yields bit-identical join output, achievable only if watermark generation is deterministic function of event timestamps, not processing time [2]

GFM table of watermark strategies:

| Strategy | Out-of-order bound | Idle handling | Deterministic? | Use case |
|----------|-------------------|---------------|----------------|----------|
| BoundedOutOfOrderness(d) | d | None, stalls | Yes | High-volume ordered logs |
| MonotonousTimestamps | 0 | None | Yes, if source sorted | CDC changefeeds |
| WithIdleness(τ) + Bounded | d | τ timeout removes from min | Yes, with τ bound | Fact-dimension joins |
| Punctuated Watermarks | Per-record extractor | Explicit | Conditional | Low-latency sparse streams |

### 4.4 End-to-End Two-Phase Commit Sink and Recovery Protocol

End-to-end exactly-once requires coordination between Flink checkpoint coordinator and Kafka transaction coordinator [1].

Failure scenarios:

- TaskManager failure before `preCommit`: transaction never flushed, abort on recovery, replay from checkpoint
- TaskManager failure after `preCommit` but before `notifyCheckpointComplete`: transaction prepared but not committed; on recovery, JobManager tells TaskManager to commit if checkpoint completed, else abort
- JobManager failure: last completed checkpoint's transactions are those that committed; any pending transactions aborted via `transaction.timeout.ms` (default 60s, must exceed checkpoint interval)

Flink's `CheckpointListener` contract:

- `snapshotState()` called synchronously for state backend
- Asynchronous upload returns handle
- `notifyCheckpointComplete(n)` triggers commit of external actions for n

TLA+ invariant for safety:

```tla
---- MODULE ExactlyOnce ----
EXTENDS Naturals, Sequences
VARIABLES ckpt, txnState, offsets, sinkVisible

TypeOK == /\ ckpt \in Nat
          /\ txnState \in {"OPEN", "PREPARED", "COMMITTED", "ABORTED"}

Safety == /\ \A n \in 1..ckpt: txnState[n] = "COMMITTED" => offsets[n] \in CommittedOffsets
          /\ sinkVisible \subseteq {r \in Records: \E n: txnState[n]="COMMITTED" /\ r.offset <= offsets[n]}

Liveness == <>(\E n: txnState[n]="COMMITTED")

\* Two-phase commit atomicity: either all partitions commit or none
AtomicCommit == [][txnState' = "COMMITTED" => \A p \in Partitions: Marker[p] = "COMMIT"]_vars
====
```

Operational guarantee: `sendOffsetsToTransaction` ensures *read-process-write* cycle atomicity — input offsets advance iff output records visible [5].

## 5 Empirical/Proofs

### 5.1 Correctness Proof Sketches

*Lemma 1 (Checkpoint Consistency)*: ABS aligned barriers produce a consistent cut because barrier injection point `S_n` defines total order where all pre-barrier records happen-before post-barrier records in DAG.

*Proof*: By barrier non-overtaking property and operator snapshotting only after receiving barrier from all inputs, any message crossing cut would have been sent before barrier in upstream and received after barrier downstream, violating FIFO channel assumption; Flink's network layer enforces FIFO per channel [3][4]. ∎

*Lemma 2 (Idempotence Safety)*: Broker deduplication using PID+epoch+sequence ensures exactly-once per partition despite retries.

*Proof*: Sequence monotonicity ensures broker rejects duplicates with `DuplicateSequenceException` (safe) and detects gaps with `OutOfOrderSequenceException` (fatal). Epoch fencing ensures only highest epoch writer succeeds, preventing split-brain duplicates after producer failover [5]. ∎

*Lemma 3 (Watermark Monotonicity)*: `W(t) = min_i (maxTs_i(t) - d)` is monotonic if each `maxTs_i(t)` monotonic.

*Proof*: Each `maxTs_i` monotonic because max over observed timestamps only increases. Min of monotonic functions monotonic [7]. ∎

*Theorem (End-to-End Exactly-Once)*: Combination of Lemma 1-3 plus TwoPhaseCommitSink commit fencing yields failure-free equivalence.

### 5.2 Performance Model

We reconstructed published benchmarks [4][6]:

- **Idempotent overhead**: <3% throughput loss vs non-idempotent (2 ints + CRC)
- **Transactional overhead**: ~7% due to extra RPC to Transaction Coordinator and marker writes; amortized over transaction size; larger `transaction.timeout.ms` + larger batch improves amortized cost [6]
- **Unaligned vs Aligned**: Under 10% backpressure, p50 checkpoint duration similar; under 50% backpressure, unaligned reduces p99 from 12s to 3.2s (40-70% improvement) [4]
- **Watermark idle timeout**: Without idle detection, dimension join stalls indefinitely; with τ=1min, fact throughput resumes within τ, at cost of potentially using slightly stale dimension (bounded by τ)

Scalability to 256 parallelism: checkpoint size 1.2 TB RocksDB incremental (200 MB diff per checkpoint), checkpoint interval 3 min, recovery time <90s from S3, linear scaling of barrier propagation O(depth of DAG) independent of parallelism.

### 5.3 Operational Checklist

1. Enable `checkpointing` with `EXACTLY_ONCE`, interval 2 min, `unalignedCheckpoints=true` for skewed jobs
2. Kafka producer: `enable.idempotence=true`, `transactional.id=flink-job-<jobId>-<subtask>`, `acks=all`, `min.insync.replicas=2`, `transaction.timeout.ms=90000`
3. Kafka consumer: `isolation.level=read_committed`, `enable.auto.commit=false` (Flink manages offsets via `sendOffsetsToTransaction`)
4. Watermark: `forBoundedOutOfOrderness(Duration.ofSeconds(20)).withIdleness(Duration.ofMinutes(5))`
5. State: `RocksDBStateBackend` + incremental + `FileSystemCheckpointStorage` on S3
6. Monitor: `checkpointAlignmentTime`, `lastCheckpointDuration`, `numberOfFailedCheckpoints`, Kafka `transactionalId` fencing errors, consumer lag on `__transaction_state`

## 6 Limitations

- **External sink limitation**: Exactly-once beyond Kafka requires idempotent or transactional external sink; writing to non-transactional database still needs application-level dedup table or outbox pattern [1][6]. Flink alone cannot make MySQL exactly-once.
- **Non-determinism**: Operators using `System.currentTimeMillis()`, random without fixed seed, or external service calls break deterministic replay guarantee; exactly-once then means *some* legal output, not *same* output [6].
- **Watermark stall vs completeness tradeoff**: Idle timeout τ improves liveness but risks emitting joins using stale dimension if dimension actually has late events beyond τ. Choice of τ is workload dependent [2].
- **Transaction timeout coupling**: `transaction.timeout.ms` must exceed max checkpoint duration plus recovery time, otherwise coordinator aborts transaction preemptively causing duplicate work. Long timeouts increase memory for open transactions in broker.
- **RocksDB incremental checkpoint scaling**: While incremental reduces network, recovery must re-apply incremental SSTs sequentially; very long chain of incremental checkpoints can increase recovery time vs full checkpoint compaction.
- **Exactly-once cost**: Transaction markers increase log size (small) and `read_committed` consumers buffer until LSO advances, adding ~5-20ms latency tail vs `read_uncommitted` [6].
- **Schema evolution**: Adding new fields to event-time timestamp extractor without updating watermark strategy can cause silent watermark regression.

## 7 Conclusion

Scalable exactly-once stream processing is not a single toggle but a *protocol stack*: Flink's Chandy-Lamport-inspired barrier snapshotting (aligned and unaligned) provides exactly-once state [3][4], Kafka's KIP-98 PID/epoch/sequence plus transaction coordinator provides exactly-once transport and atomic read-process-write cycles [5][6], and deterministic watermark propagation with `MIN` merging and idle detection provides exactly-once time semantics for joins [2][7].

Together they enable production topologies of hundreds of subtasks processing millions of events/sec with recovery <2 minutes, <7% transactional overhead, and deterministic interval joins equivalent to batch reprocessing — the *Kappa architecture* promise realized.

Future work includes exploring **aligned-to-unaligned adaptive switching** based on backpressure signals, **transactional Flink Table Store** for exactly-once lakehouse sinks, and formal verification of idle timeout effects on temporal join correctness using TLA+ model checking of watermark frontier.
