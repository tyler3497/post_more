# CompCert Verified Compilation and Kripke Logical Relations for C Semantics: Memory Injections, Compositional Correctness, and End-to-End Preservation Proofs

## Abstract

We present a comprehensive analysis of CompCert, the first industrially deployed verified optimizing compiler for C, through the lens of Kripke logical relations (CKLR) and memory injections that enable compositional correctness. CompCert's theorem — that compiled assembly preserves observable behavior of source C up to undefined behavior refinement — rests on ~20 intermediate languages each equipped with mechanized operational semantics in Coq. We formalize its memory model as block-based allocation with permissions, and show how forward and backward simulations parameterized by memory injections yield transitive preservation. The central difficulty of open modules and separate compilation is resolved by lifting simulations to Kripke worlds indexed by memory injections ordered by inclusion, with monotonicity ensuring pointer validity across world extension. We explain CKLR's role as uniform semantic interface [5] for heterogeneous module linking and direct refinement, following CompCertO [4] and recent fully composable results [6]. Our synthesis covers correctness proofs of register allocation, constant propagation, and tail-call elimination via memory extensions [7], demonstrates linking adequacy for mutual recursion, and situates CompCert within the verified software toolchain. The treatment is intentionally PhD-level dense, bridging programming languages, separation logic, and compiler verification.

## 1 Introduction

Can you trust your compiler? For *critical software certified by formal methods*, the answer determines whether source-level proofs survive compilation. CompCert, led by Xavier Leroy [1] since 2005, answers affirmatively: a Coq-verified optimizing compiler from **Clight** (large subset of ISO C99) to **PowerPC / ARM / RISC-V / x86-64** assembly, with machine-checked proof that *if the compiler succeeds*, the generated assembly's observable trace set refines source's trace set.

Observable behavior includes **termination mode** (normal, divergence, stuck due to undefined behavior), and **I/O events** (`trace = list Event`, where Event = volatile load/store, external call, annotation). Preservation is not bisimulation but *refinement*:

$$\forall S, C, \text{CompCert}(S)=C \implies \forall b \in \text{Behaviors}(C), b \notin \text{Wrong} \implies \exists b' \in \text{Behaviors}(S), b' \preceq b$$

where $b' \preceq b$ denotes $b'$ has same events but may be *more defined* — compiler may narrow nondeterminism and may replace undefined behavior by arbitrary defined behavior.

CompCert's scale: **~100k lines of Coq**, **~14k lines OCaml**, **19 intermediate languages**, **20 passes**. Yet original theorem assumes *closed-world*: program = single translation unit with `main`. Real software is *modular*, linking heterogeneous objects.

*Compositional CompCert* closes gap via **Kripke logical relations** indexed by worlds representing memory evolution [4][5][6].

> **Theorem 1 (End-to-End Correctness):** For all Clight programs $S$ free of undefined behavior, if `CompCert(S) = Asm`, then $S$ and $Asm$ have identical observable traces; if $S$ has UB, $Asm$ may have any behavior *after* UB point. Formally, $Beh(Asm) \subseteq Beh(S) \cup (Pref(Beh(S)) \cdot Wrong)$.

## 2 Background / Preliminaries

### 2.1 Memory Model

CompCert memory is *not flat*; addresses are $(b, ofs)$ where $b \in Block$, $ofs \in \mathbb{Z}$. Each cell carries permission $perm: Mem\to Block\to Z\to Perm$, $Perm = \{ \bot, Freeable, Writable, Readable, Nonempty \}$. Allocator `alloc(M, lo, hi) = (M', b)` picks fresh $b$ notin $M$ and sets $perm[b][ofs]=Freeable$ for $ofs\in[lo,hi)$. Load/store check permissions.

Crucially, **pointer arithmetic stays within block** unless via `undef` escape; ISO C forbids inter-block arithmetic, enabling injections.

### 2.2 Languages and Passes

Pipeline:

| Source / IR | Description | Verified property |
|-------------|-------------|-------------------|
| **CompCertC** | Full C | Elab to Clight |
| **Clight** | Simplified C | Nondet eval order (big/small-step) |
| **Cminor** | Explicit stack | Match via injection |
| **RTL** | CFG, infinite regs | Dataflow via Kildall |
| **LTL / LTLin** | Finite locations | Register allocation (graph coloring validator) |
| **Mach** | Abstract asm | Linearization |
| **Asm** | Concrete asm | Encoding |

Pass categories:

- **Translation:** Clight → Cminor → RTL — change memory structure, need *injection*.
- **Optimization:** RTL → RTL (CSE, inlining, tailcall) — need *extension* or *injection*.
- **Lowering:** RTL → LTL → Mach — finite mapping.

### 2.3 Forward vs Backward Simulation

Standard simulation:

$$S \vdash s \to^t s' \land s \sim_f t \implies \exists t', f', t \vdash t \to^{t}^* t' \land s' \sim_{f'} t' \land f \subseteq f' $$

- **Identity:** $f=id$.
- **Extension:** $M \le_{ext} M'$: target has *more blocks* but agrees on old.
- **Injection:** $f : Block \rightharpoonup  \lfloor Block' \times \mathbb{Z} \rfloor$: may map source block to sub-block at offset, drop unused blocks.

Monotonicity: $f \subseteq f'$ means injection only *grows* — key to Kripke.

## 3 Methodology / Formalism

### 3.1 Kripke World Construction

Define world $w = (f, M_s, M_t)$ with $f \in MemInj$. World order $w \le w'$ iff $f \subseteq f'$. CKLR:

```coq
Record CKLR := {
  W : Type;
  le : W -> W -> Prop;
  R_mem : W -> Mem -> Mem -> Prop;
  R_val : W -> Val -> Val -> Prop;
  monotonic : forall w w' v v', le w w' -> R_val w v v' -> R_val w' v v'
}.
```

Validity of pointers persists under future worlds.

### 3.2 Compositional Correctness

For open module $p : L$, interaction semantics $L(p)$ denotes trace of external calls. CKLR-based open simulation:

$$p \le_R^{comp} q := \forall w, w\vdash R \to (p \text{ asks } q \text{ on } w \implies q \text{ answers compatibly})$$

**Vertical:** If $p \le_{R1} r$ and $r \le_{R2} q$ with $R1,R2 \in CKLR$, then $p \le_{R1\circ R2} q$ because CKLRs share same world structure.

**Horizontal:** For modules $p1,p2$, if $p1 \le_R q1$ and $p2 \le_R q2$, then $p1 \oplus p2 \le_R q1 \oplus q2$ — relies on $R$ protection.


## 4 Deep Dive

### 4.1 Memory Injections Unifying All Passes

Most passes fit into one CKLR using world = `MemInj`. Why?

- **SimplLocals**: source memory block for local with no counterpart — injection partial, domain excludes, requiring proof external calls never touch it.
- **Stacking**: target has extra stack frame blocks; injection maps source same, extension allows extra.
- **Tailrec**: injection offset-shifts argument block to reuse frame.
- **Inlining:** caller and callee memories merged; injection merges two source spaces into one target.

This yields uniform interface $\forall R\in CKLR, L(p) \le_{R\to R} L(p')$ — same $R$ works for all languages, enabling vertical composition $O(n)$ vs $O(n^2)$.

| Pass | Old Relation | CKLR Mapping | Memory Effect |
|------|--------------|--------------|---------------|
| SimplLocals | Partial env | Partial Inj | Drop block |
| Csharpminor → Cminor | Inj + ext | Inj grows | Alloc globals same |
| Inlining | Inject caller+callee | Disjoint union | Merge |
| Tailcall | Offset | Inj(b)=Some(b',ofs) | Reuse frame |
| Stacking | Ext | Ext | Add frames |

### 4.2 From Closed to Open: Structured Simulations

Closed simulation considers whole program $main$. Open simulation considers **game** where module $M$ interleaves internal steps and external calls. Interaction semantics $\mathcal{I}(M)$ L TS labels = `Call(f, args, mem)` and `Return(v, mem)`.

CKLR provides *both* rely and guarantee encoded as same relation $R$ — reminiscent of **rely-guarantee** but semantic. Key lemma (Theorem 4.3 [5]):

> **Theorem 2 (Preservation of CKLR):** For each CompCert language $L$, $\forall R\in CKLR, L(p) \le_R^{comp} L(p)$. I.e., any program respects *any* CKLR — it never fabricates dangling pointers.

Thus external call correctness piggybacks on self-preservation: external module also preserves $R$ if it is itself CompCert language (heterogeneous $Clight\oplus Asm$ allowed).

**Direct refinement** [6]: $p \le_{direct} q$ if $\forall$ behaviors $b$ of $q$, either $b$ behavior of $p$, or $b$ goes Wrong after prefix also reachable by $p$. Avoids exposing intermediate traces — essential for adequacy.

### 4.3 Memory Extensions, Security Features, and Optimizations

- **Stack Canaries [7]:** Insert secret canary on entry, check on exit, abort on corruption. Proof uses **memory extension**: target Mach has extra slot, source not, but extension keeps canary outside source-observable region, permissions prevent overwriting unless already overflow (UB). Hence canary invisible; if overflow in source (UB), refinement allows abort.
- **Pointer Authentication (ARMv8.3 PAC) [7]:** Sign return address, authenticate before ret. Proof: extension with shadow authenticated copy; auth failure → refined to UB.
- **Tail Recursion Elimination:** Need liveness proving tail position; injection offset but also measure decreasing to show divergence preserved.

Each extension follows template `MemExt` parameterized by CKLR, maintaining *protection*.

### 4.4 Heterogeneous Linking and Mutual Recursion

Consider three modules: `crypto.c` compiled via CompCert, `handwritten.S` untrusted asm manually proved to respect $R$, `driver.c` calling both.

Horizontal composition guarantees linking `crypto ⊕ driver ⊕ hand_assembly` preserves refinement irrespective of heterogeneity, provided each respects same $R$.

Mutual recursion: `A.c` calls `B.c` vice versa. World extension allows *interleaved* growth during cross-module calls: when $A$ calls $B$, world $w$ evolves to $w'$ where $B$'s private blocks added to protection set; upon return, $A$'s locals still enforced due to monotonicity. Requires **Transitive** CKLR composition — $R\circ R \subseteq R$ — which holds because $MemInj$ inclusion transitive.

Empirical verification: teams verified **2kLOC** heterogeneous program with proof effort 60% reduction vs per-pass $R_i$ [5].

## 5 Empirical Evaluation or Proofs

**Proof 1 — Injection Monotonicity:** If $f \vdash M_s \triangleright M_t$ and $f \subseteq f'$, $M_s \le M'_s$, $M_t \le M'_t$ compatibly, then $f' \vdash M'_s \triangleright M'_t$. Induction on `valid_block` and permission lattice.

**Proof 2 — Forward to Backward via Determinism:** For deterministic target $Asm$ (single successor), forward + progress + receptiveness ⇒ backward. Sketch uses receptiveness: if target can receive event e, source can too.

**Proof 3 — Stack Canary Security Extension:** Construct $M_t = M_s \oplus [canary]$. Define $s \sim_{ext} t$ iff $M_s$ injects into $M_t \setminus canary$ and canary holds magic. Store respects extension because canary block disjoint (proved via layout invariant). Check on exit: if corrupted, target aborts, allowed as refinement because source same overflow already had UB.

**Empirical numbers** (from [4][5][6]):

- Whole-program theorem proof time ~30 min on 32-core.
- Compositional overhead +15% lines vs +200% for per-pass $R_i$.
- Linking 10 modules: $O(n)$ unified vs $O(n^2)$ heterogeneous.
- Runtime overhead canary/pac <2% vs gcc -O2.

## 6 Limitations

- **Unverified front-end:** CompCert's parser, typechecker, preprocessor, assembler (GAS), linker are *unverified*; only Elab → Clight to Asm chain verified. Trust base includes OCaml extraction and Coq kernel.
- **Memory model gaps:** Model forbids *byte-level pointer casts* that break block abstraction (XOR lists, pointer laundering via `intptr_t` roundtrip not faithful). Provenance-aware models more faithful may break some injections.
- **Concurrency absent:** Original sequential only; CompCertTSO and CompCertMMM add relaxed memory but compositional $R$ more complex, still open for full DRF preservation.
- **Separate compilation assumptions:** Requires all modules share same $CKLR$ interface; linking with arbitrary unverified asm that violates $R$ cannot be proven safe.
- **UB permissiveness:** Refinement allows compiler to *eliminate* UB by giving arbitrary defined behavior; while sound per ISO, may surprise security-minded developers expecting fail-stop.
- **Proof engineering cost:** Even with unified CKLR, adding new optimization requires proving simulation *uniform* w.r.t $CKLR$, imposing strong monotonicity conditions some speculative optimizations violate.

---

## 7 Conclusion

CompCert remains **gold standard** for verified compilation, not because it handles all C, but because it *practically balances* language coverage, optimization power, and proof tractability via **systematic use of memory injections as Kripke worlds**. Evolution from whole-program to compositional demonstrates profound shift: Early CompCert forward simulation sufficient but not modular; CompCertO interaction semantics indexed by per-pass Kripke relations yields separate compilation but heavy interfaces; Unified CKLR [5][6] single frame $\langle MemInj, \subseteq \rangle$ abstracts *all* passes; passes become endomorphisms on same category of worlds, enabling **both** vertical and horizontal composition in one theorem; Direct refinements speak *only* source Clight vs target Asm, hiding 19 middles — true adequacy.

Memory injection viewpoint reusable beyond CompCert: Iris, VST, CertiKOS kernels adopt similar block offset injections to reason about **substructural memory protection** and **capability safety**. Future directions: **CompCert + concurrency** (TSO-preserving Kripke worlds with protocol invariants), **provenance-aware memory** (C2x `P(n)` provenance using colored blocks), and **verified linking with Rust / CHERI** where $R$ becomes richer (capability derivation relation monotone under extension).

Philosophically, *verified compilation is not one theorem, but a **algebra of relations*** closed under composition, parameterized by world evolution; Kripke monotonicity is semantic analogue of “private state stays private,” i.e., **robust safety**.
