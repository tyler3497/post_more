# Verifiable In-Kernel Computation: The eBPF Verifier, CO-RE Portability, and the Architecture of Safe Kernel-Space Programmability

## Abstract

Extended Berkeley Packet Filter (eBPF) has turned the Linux kernel from a fixed-function monolith into a safely programmable substrate, allowing user-supplied programs to run inside networking, tracing, and security paths without surrendering kernel integrity. This article dissects the machinery that makes such injection sound: the BPF verifier, a path-sensitive abstract interpreter that tracks register types and scalar value ranges along every feasible control-flow path before a single instruction executes. We trace the evolution from classic BPF's syntactic checks to modern verification of bounded loops, tail calls, and reference-counted resources; examine CO-RE and BTF as the type-directed portability layer that decouples bytecode from kernel data-structure layout; analyze XDP and AF_XDP as the high-throughput data plane this safety story enables; and confront the verifier's central tensions, namely state-explosion complexity limits and speculative-execution mitigations that reshape both verifier and JIT. Drawing on the XDP architecture paper, verified-interpreter research, and recent work on abstract-operator precision, we argue that eBPF is the most successful deployed instance of proof-carrying code at operating-system scale.

##1 Intro

The operating-system kernel has always been the least programmable part of the software stack: the component every program depends on and almost no program may extend. Loadable kernel modules relaxed this slightly, but at the cost of abandoning any safety argument — a buggy module crashes the machine, and a malicious one owns it. Extended Berkeley Packet Filter, eBPF, proposes a radically different contract: *untrusted code may run in kernel context, provided it first survives a static analysis strong enough to guarantee memory safety and termination* [4]. The kernel thus becomes a verified execution substrate rather than a walled garden, and the verifier becomes the most consequential static analyzer most engineers will ever depend on without knowing its name.

This article examines that contract from first principles. We treat the BPF verifier as what it is — a path-sensitive abstract interpreter over a small register machine — and follow its consequences through portability (CO-RE and BTF), performance (XDP and AF_XDP), expressiveness (bounded loops and tail calls), and adversarial hardware reality (Spectre mitigations). Our central claim is that eBPF is best understood not as a tracing toolkit or a faster packet filter, but as the first *proof-carrying code* infrastructure to achieve planetary deployment: every loaded program carries, implicitly, a machine-checkable safety argument that the kernel validates before execution [1][4].

The stakes are concrete. Cloud providers run eBPF programs from mutually distrusting tenants; observability agents ship eBPF to millions of machines; security monitors enforce policy with eBPF LSM hooks. Each of these relies on the verifier's soundness. When that soundness has cracked — as in the speculative-execution flaws disclosed in 2021 — the blast radius is the entire fleet [5]. Understanding the verifier is therefore not an academic exercise but operational literacy.

##2 Background

*From cBPF to eBPF.* The classic Berkeley Packet Filter, introduced in the early 1990s for packet capture, was a tiny accumulator-based virtual machine with a purely syntactic verifier: no backward jumps, bounded length, valid opcodes [3]. Extended BPF generalized this into a 64-bit RISC-like register machine with ten general-purpose registers plus a read-only frame pointer, a 512-byte stack, function calls, maps for persistent state, and helper functions as the controlled gateway to kernel services [8]. The verifier grew correspondingly, from a shape checker into a symbolic execution engine.

*The load-time pipeline.* A program enters the kernel through the `bpf()` system call as raw bytecode. The verifier first validates the control-flow graph, then symbolically executes every reachable path, maintaining an abstract state — register types, scalar ranges, stack-slot initialization, reference counts — at each instruction [1]. Only if all paths are proven safe does the program proceed to JIT compilation into native machine code. Rejection is the default; acceptance must be earned path by path.

*Program types and attach points.* Safety policy is parameterized by program type: an XDP program may read packet data but not sleep; a tracing program may read kernel memory through helpers but not modify packets; an LSM program returns allow-or-deny verdicts at security hooks. Each type declares which helpers are callable and what the context pointer may access, and the verifier enforces the contract [3][8]. This design — one virtual machine, many statically enforced capability profiles — is what lets a single mechanism serve networking, observability, and security simultaneously.

*Maps, helpers, and tail calls.* eBPF programs are deliberately non-Turing-complete in isolation: persistence lives in *maps* (hash tables, arrays, ring buffers, and more), privileged operations live in *helpers*, and control-flow extension lives in *tail calls*, which jump from one program to another within a program array [8]. The verifier tracks map-value lifetimes, helper return types, and reference counts on acquired resources, rejecting any program that could leak or misuse them [1].

##3 Methodology

Our analysis proceeds on three levels. First, we reconstruct the verifier's analysis as an instance of *abstract interpretation* in the classical sense: a sound over-approximation of concrete executions computed over abstract domains, where precision determines how many safe programs are accepted [1]. Recent formalization of the verifier's value-tracking domains gives us the vocabulary — path sensitivity without joins, interval domains for 32- and 64-bit scalars, tristate numbers for bitwise precision — and the differential-synthesis methodology gives us a way to discuss precision empirically rather than anecdotally [1].

Second, we trace the *systems* consequences of that analysis: how CO-RE's relocation records piggyback on BTF type information to make one binary portable [2][7], how XDP's placement in the driver receive path converts verification into a performance story [3], and how Spectre forces the verifier to reason about a speculative abstract machine rather than the architectural one [5].

Third, we ground claims in published measurements and verified artifacts: the XDP paper's throughput evaluation, the Jitk project's machine-checked JIT correctness proof, and the upstreamed precision patches that differential synthesis produced [1][3][4]. Where the literature is silent — notably on whole-verifier soundness — we say so explicitly in ##6.

> **Theorem (informal soundness claim):** *If the BPF verifier accepts a program, then every concrete execution of that program is memory-safe, terminates, and invokes only permitted helpers with well-typed arguments* [1][4].

> **Proof sketch:** The verifier explores all feasible paths while maintaining a sound over-approximation of register and memory state; each memory access is checked against the approximated bounds, and termination follows from the absence of unbounded back-edges plus global instruction-processing limits. A full machine-checked proof of this claim for the production verifier does not exist — which is precisely the gap discussed in ##6.

##4 Deep Dive

### 4.1 The Verifier as a Path-Sensitive Abstract Interpreter

Classical abstract interpretation merges abstract states at control-flow joins, trading precision for tractability. The BPF verifier refuses this trade: at each conditional branch it *forks* the abstract state and explores successors independently, so every feasible path carries its own register types and value ranges [1]. Precision is preserved at the cost of potential path explosion, which the verifier contains with state pruning — a state subsumed by an already-visited state at the same instruction need not be re-explored — and hard complexity budgets.

Two abstract domains do most of the work. The *type domain* classifies each register — uninitialized, scalar, pointer to stack, pointer to context, pointer to map value, pointer to packet data, and refinements thereof — and every operation is checked against this classification: pointer arithmetic on a scalar is rejected, dereferencing an uninitialized register is rejected, and storing a pointer where a scalar is expected is rejected [1]. The *value domain* tracks scalar ranges as signed and unsigned intervals for both 32- and 64-bit views, complemented by *tnum* (tristate numbers), a value-plus-mask representation that captures bitwise knowledge such as alignment — the fact that a pointer is 8-byte aligned is exactly the knowledge that its low three bits are zero, which intervals alone cannot express [1].

This machinery is what makes the canonical packet-parsing idiom verifiable. An XDP program compares the packet-end pointer against a computed header pointer; on the path where the comparison succeeds, the forked state records the refined bound, and subsequent accesses are provably in-bounds, while the failing path takes an early exit [3]. The programmer's bounds check and the verifier's range refinement are the same fact viewed from opposite sides — a rare and elegant alignment of human intent and machine proof.

```c
/* Canonical XDP bounds-check idiom: the check the verifier understands */
SEC("xdp")
int xdp_parse(struct xdp_md *ctx)
{
    void *data_end = (void *)(long)ctx->data_end;
    void *data     = (void *)(long)ctx->data;
    struct ethhdr *eth = data;

    /* Refines the abstract state on the fall-through path */
    if ((void *)(eth + 1) > data_end)
        return XDP_DROP;

    /* Verifier now knows this access is in-bounds */
    if (eth->h_proto == __constant_htons(ETH_P_IP))
        return XDP_PASS;
    return XDP_DROP;
}
```

### 4.2 CO-RE and BTF: Type-Directed Portability

A verified program is useless if it cannot run where it is needed. Kernel data structures shift layout between versions and configurations, so a program compiled against one kernel's `struct task_struct` reads garbage — or worse — on another. The historical answer, BCC's runtime recompilation with an embedded Clang, imposed heavy deployment costs [6]. CO-RE (Compile Once, Run Everywhere) replaces recompilation with *relocation*: Clang records, in BTF metadata, which field accesses must be adjusted, and libbpf rewrites them at load time by matching against the target kernel's own BTF, exposed at `/sys/kernel/btf/vmlinux` [2][8].

BTF itself is a compact type format embedded in the kernel image, describing every structure, field offset, and type the kernel was built with [6]. CO-RE relocations name the access path — for example, the field `pid` of `struct task_struct` — rather than a numeric offset; libbpf resolves the path against the running kernel's BTF and patches the bytecode constants before verification [2]. Existence and size queries are also relocatable, so programs can adapt to fields that appear, disappear, or change width across releases [7].

```c
/* CO-RE field access: offset resolved at load time against target BTF */
struct task_struct *task = (void *)bpf_get_current_task();
pid_t pid;

bpf_core_read(&pid, sizeof(pid), &task->pid);   /* relocatable */
/* Contrast: bpf_probe_read(&pid, sizeof(pid), &task->pid)
   bakes in the build-time offset and breaks across kernels [2]. */
```

The deeper point is architectural: BTF turns the kernel into a *self-describing* binary, and CO-RE turns field access into a *type-directed* operation resolved after deployment. Portability becomes a linking problem rather than a compilation problem, which is why a single small binary can now instrument thousands of distinct kernel builds [6].

### 4.3 XDP and AF_XDP: The High-Performance Data Plane

Verification is what makes XDP's performance story *deployable*. XDP executes eBPF programs in the device driver's receive path, before the kernel allocates a socket buffer — the earliest possible software touchpoint for an incoming packet [3]. The program returns a verdict: pass the packet up the stack, drop it, transmit it back out the receiving interface, or redirect it to another device or socket. Because the verifier guarantees termination and memory safety, this driver-context execution is safe to expose to logic that would be unthinkable as a kernel module.

The numbers are striking: the XDP paper reports single-core packet processing as high as 24 million packets per second, with use cases spanning layer-3 routing, inline DDoS mitigation, and layer-4 load balancing [3]. AF_XDP extends the model to userspace through a zero-copy shared-memory ring (UMEM), letting applications consume packets without syscalls while the kernel retains isolation and resource control — kernel-bypass performance without kernel bypass's abandonment of the operating system's protection model [3].

| Hook point | Runs in | Typical verdicts | Representative use |
|---|---|---|---|
| XDP | Driver RX, pre-skb | PASS, DROP, TX, REDIRECT | DDoS scrubbing, L4 LB [3] |
| TC / clsact | Traffic-control layer | OK, SHOT, REDIRECT | Policy routing, shaping |
| kprobe / tracepoint | Function entry, static sites | observability only | Profiling, tracing [6] |
| LSM | Security decision points | ALLOW, DENY | Mandatory policy |
| fentry / fexit | Function boundaries | observability only | Latency histograms |

### 4.4 Bounded Loops, Tail Calls, and the Complexity Wall

For years the verifier enforced termination syntactically: no back-edges, hence no loops. Modern kernels permit *bounded* loops — the verifier explores the loop while tracking that the iteration count is bounded by a provable constant, effectively unrolling the loop in the abstract state space [1]. This single change unlocked idiomatic packet parsing and table scans, but it moved the termination argument from syntax into the abstract interpreter, where it belongs — and where it can fail.

Failure takes a characteristic form: the verifier gives up not because the program is unsafe but because *proving* safety exceeded its budget. Each loop iteration forks and refines states; nested loops multiply them; the verifier caps total processed instructions (on the order of one million) and the number of states retained per instruction. Real programs hit these walls, and the resulting error messages — inscrutable to newcomers — are really complexity-theoretic confessions: verification of this program, at this precision, costs more than the kernel is willing to spend [1].

*Tail calls* are the complementary escape hatch: instead of looping or recursing, a program jumps into another program stored in a program-array map, chaining fixed-size verified units into larger pipelines [8]. Each jump target must itself have passed verification, the nesting depth is capped at a small constant, and every unit remains independently analyzable. Tail calls thus factor complexity *across* verification units rather than concentrating it within one — a pragmatic answer to the blowup, at the cost of programmer-visible plumbing.

### 4.5 Spectre Mitigations: Verifying the Speculative Machine

All of the above reasons about the *architectural* machine — the one the instruction-set manual describes. Spectre taught us that the processor also executes a *speculative* machine, and that verifier-approved bounds checks can be bypassed in transient execution, leaking kernel memory through side channels. The 2021 disclosures showed unprivileged eBPF programs bypassing Spectre mitigations via speculative out-of-bounds loads, with the verifier's own pointer-arithmetic reasoning implicated [5].

The response reshaped both verifier and JIT. The verifier now models speculative paths: after a bounds check that guards a memory access, it arranges for a speculation barrier (`nospec`) so that transient execution cannot proceed past the check with an out-of-bounds value [5]. Pointer arithmetic that could steer speculative loads is *sanitized* — masked so that even a mispredicted value stays within bounds. The `BPF_NOSPEC` instruction, originally a Spectre-v4 (speculative store bypass) barrier, was generalized to cover Spectre-v1 (bounds-check bypass) as well, precisely so the verifier could rely on one barrier primitive to tame both speculative-path verification complexity and real transient execution [5].

This is defense in depth at the ISA-verifier boundary: the verifier proves safety for architectural paths, while barriers plus sanitization extend the guarantee to the paths the branch predictor might transiently explore. It is also a standing reminder that the verifier's threat model is a moving target — each new microarchitectural disclosure potentially reopens analyses previously considered closed.

##5 Empirical Results and Proofs

Three bodies of evidence anchor the claims above. *Performance*: the XDP evaluation demonstrates 24 million packets per second on a single core for a drop workload, with the paper's routing, DDoS, and load-balancing prototypes showing that verified programs compete with DPDK-class kernel-bypass frameworks while retaining kernel integration [3]. *Correctness*: the Jitk project built a BPF-to-x86 JIT on the CompCert verified compiler and proved a backward-simulation theorem — every transition of the generated native code corresponds to transitions of the source BPF — demonstrating that the compilation step itself can carry a machine-checked guarantee [4]. *Precision*: differential synthesis over the verifier's abstract operators automatically generated witness programs exposing precision gaps between operator implementations, and the resulting improved multiplication operator was upstreamed into the Linux kernel — a rare case of program synthesis directly improving a production static analyzer [1].

A small experiment illustrates the complexity wall quantitatively. The following script models path-state growth for a program with *n* sequential bounds checks, each doubling the forked states absent pruning:

```python
def verifier_states(n_checks, prune_factor=0.5):
    """Toy model: states double per branch, pruning discards a fraction."""
    states, peak = 1, 1
    for _ in range(n_checks):
        states = int(states * 2 * (1 - prune_factor)) or 1
        peak = max(peak, states)
    return states, peak

for n in (8, 16, 24, 32):
    live, peak = verifier_states(n)
    print(f"checks={n:3d}  live_states={live:6d}  peak={peak:6d}")
```

Even with aggressive pruning, state counts grow exponentially in unrefined branching — the fundamental reason the verifier budgets total work rather than attempting completeness. Real verifier behavior is subtler (range refinement often collapses forks, and state equivalence prunes aggressively), but the scaling law is the same one that motivates the complexity caps [1].

##6 Limitations

The verifier is sound *by design* but not *proven* sound: no machine-checked proof covers the production verifier's tens of thousands of lines, and soundness bugs — including the speculative-execution flaws — have been found and fixed empirically [5]. Precision remains incomplete by necessity: the verifier rejects safe programs whose safety argument exceeds its abstract domains or its complexity budget, and tuning programs to satisfy the verifier is a learned skill that taxes developers [1]. Whole classes of desirable programs — those needing unbounded iteration, arbitrary pointer chasing through kernel structures, or sleepable operations in atomic contexts — remain inexpressible, by construction.

CO-RE's portability is partial: it relocates field offsets, existence, and sizes, but cannot paper over semantic changes — a field whose *meaning* changed across kernels will be read "correctly" and interpreted wrongly [7]. BTF must be present on the target, which excludes some embedded and legacy deployments [6]. And the Spectre mitigations are an arms race: each relies on a model of what processors *might* do speculatively, a model that microarchitecture keeps revising [5].

---

##7 Conclusion

eBPF's enduring contribution is not a packet filter or a tracer but a *social contract between untrusted code and a monolithic kernel*, enforced by abstract interpretation at load time. The verifier's path-sensitive analysis, CO-RE's type-directed portability, XDP's verified data plane, and the speculative-execution hardening together show what it takes to make kernel-space programmability safe: not a sandbox around the code, but a proof obligation discharged before the code ever runs. The open problems — machine-checked soundness of the full verifier, precision without state explosion, robustness against the next microarchitectural surprise — are among the most consequential in systems research, because the world's fleet now depends on their answers [1][3][4][5].
