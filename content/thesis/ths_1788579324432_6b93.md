# In-Network Computation with Programmable Data Planes: The P4 Language, the PISA Architecture, and the Economics of Stateful Processing at Line Rate

## Abstract

The programmable data plane represents a fundamental reallocation of computational responsibility within the network: rather than treating switches as fixed-function packet forwarders, the *P4* language and the *Protocol-Independent Switch Architecture (PISA)* permit operators to define packet-processing behavior down to the wire while preserving line-rate throughput [1]. This paper develops a doctoral-level treatment of in-network computing on programmable data planes. We formalize the match-action pipeline model and its hardware realization in reconfigurable match tables, programmable parsers, and stateful arithmetic logic units; we analyze three landmark systems — **SwitchML** [2], which performs distributed machine-learning gradient aggregation in the switch fabric; **NetCache** [3], which implements line-rate in-network key-value caching for rack-scale storage; and **In-Band Network Telemetry (INT)** [4], which embeds per-hop measurement state into production packets — and we evaluate the control-plane coupling provided by the *P4Runtime* API [5]. Our empirical analysis shows training speedups of up to **5.5×** for distributed ML workloads and order-of-magnitude throughput gains for cached key-value reads under skewed workloads. We conclude with a critical treatment of the limits of stateful line-rate processing: bounded per-packet memory access, weak consistency of data-plane state, and the expressiveness ceiling imposed by feed-forward pipeline stages.

## 1 Introduction

For three decades, the forwarding plane of the Internet was defined by a closed bargain: vendors shipped fixed-function application-specific integrated circuits (ASICs) implementing a standardized protocol stack, and operators configured them through narrow management interfaces. Software-Defined Networking (SDN) separated control from forwarding [1], but in its first incarnation — exemplified by OpenFlow — the data plane remained *protocol-dependent*: the OpenFlow specification enumerated every header field a switch could match on, growing from 12 to 41 fields in a few years, yet still unable to accommodate new protocols without a specification revision [1].

The *P4* language, introduced by Bosshart et al. in 2014 [1], broke this bargain by making the data plane itself programmable. P4 is a domain-specific language in which the programmer declares *headers*, a *parser* (a finite-state machine extracting those headers), *match-action tables*, and a *control flow* composing those tables — and the compiler lowers this program onto a target device, whether a high-speed ASIC such as the Barefoot Tofino family, a network processor, an FPGA, or the software reference switch *bmv2*. The companion abstract machine, PISA (Protocol-Independent Switch Architecture), decomposes the switch into a programmable parser, a sequence of match-action stages with local stateful memory, and a programmable deparser, all operating at terabits per second [1].

Programmability at this level unlocked a qualitatively new class of applications: **in-network computing**. If the switch can parse, compute on, and rewrite arbitrary headers at line rate, then it can also *participate in application logic* — aggregating machine-learning gradients [2], caching key-value pairs [3], and recording per-hop telemetry [4] — without leaving the fast path. This paper studies that phenomenon rigorously: its language and architecture foundations (§2–§4.1), its flagship applications (§4.2–§4.4), its measured benefits (§5), and its hard limits (§6).

## 2 Background

### 2.1 From OpenFlow to Protocol Independence

OpenFlow's match-action abstraction was the right idea with the wrong closure: the set of matchable fields was fixed by the standard. P4 inverts the dependency. In P4, the programmer *defines* the headers; the compiler generates the parser state machine and the table key formats. This yields three properties emphasized in the original paper [1]:

1. **Reconfigurability in the field** — the packet-processing behavior can change after deployment.
2. **Protocol independence** — the switch is not tied to any fixed protocol stack.
3. **Target independence** — the same program compiles to diverse targets via architecture definitions.

### 2.2 The RMT / PISA Hardware Model

The hardware counterpart of P4 is the *Reconfigurable Match-Table* (RMT) design [1], generalized as PISA. A PISA pipeline consists of:

| Stage | Function | Programmability |
|---|---|---|
| Parser | Extract headers via FSM | Fully programmable |
| Ingress match-action units (MAUs) | TCAM/SRAM table lookups + ALU actions | Tables configured; actions from P4 |
| Stateful memory | Registers, counters, meters | Atomic read-modify-write per stage |
| Traffic manager | Queuing, scheduling, replication | Largely fixed-function |
| Egress MAUs | Post-queue match-action | Programmable |
| Deparser | Re-emit headers | Programmable |

Crucially, each MAU stage must complete its work within a fixed *packet budget* — on a 12.8 Tbps-class device, a 64-byte packet arrives roughly every **nanosecond-scale** interval per pipeline, so per-stage logic is bounded to a handful of ALU operations and a bounded number of SRAM accesses [1]. This budget is the central constraint of everything that follows: it is what makes line rate possible, and it is what makes in-network computing hard.

### 2.3 P4_14 to P4_16: Language Evolution

The original P4_14 was tightly coupled to a specific switch model. **P4_16** (2016–2017, maintained at p4.org [6]) redesigned the language around *architectures*: a P4_16 program is written against an architecture model (e.g., `v1model`, the Portable Switch Architecture *PSA*, or the Tofino Native Architecture *TNA*) that declares the programmable blocks, their interfaces, and the available *externs* (target-specific functions such as checksum units, meters, and stateful ALUs). This separation is what lets the SwitchML P4 program target TNA while remaining expressible, in principle, against other architectures [2].

## 3 Methodology

Our treatment proceeds in three methodological steps.

**Formal model.** We treat a P4 program as a function over *packet header vectors* (PHVs): the parser maps the byte stream to a PHV; each match-action stage applies a guarded transformation `stage_i : PHV × S_i → PHV × S_i` where `S_i` is the stage-local state (registers); the deparser maps the final PHV back to bytes. Feed-forward structure (no backward edges, bounded iteration) guarantees that the pipeline sustains one packet per clock per port — *line rate* — by construction.

**System case studies.** We analyze three production-grade systems built on this model: SwitchML (in-network aggregation for ML training) [2], NetCache (in-network key-value caching) [3], and INT (in-band telemetry) [4]. For each, we identify the *co-design* between switch processing and end-host protocols that makes the application feasible within the per-stage budget.

**Control-plane coupling.** We examine P4Runtime [5], the protobuf/gRPC-based control-plane API that makes P4 programs manageable: it exposes table entries, action profiles, counters, and digests through a target-independent *P4Info* description generated by the compiler, closing the loop between the programmable data plane and SDN controllers.

> **Theorem (Line-rate preservation):** *A P4 program whose every match-action stage performs O(1) table lookups, O(1) stateful ALU operations, and no data-dependent looping sustains deterministic per-packet latency and therefore line-rate throughput on a PISA pipeline, independent of traffic mix.*

*Proof sketch.* Each MAU stage is a fixed-latency combinational-plus-SRAM datapath; the pipeline accepts one PHV per clock cycle per port by construction. Since no stage's latency depends on packet content (bounded operations, no unbounded iteration), the pipeline never stalls on data-dependent control flow, and throughput equals the clock rate times the PHV width — i.e., the device's rated line rate. ∎

## 4 Deep Dive

### 4.1 The P4_16 Language and the PISA Pipeline

A P4_16 program has four principal components. Consider a minimal L3-forwarding sketch:

```p4
/* P4_16 (v1model): header definitions and parser */
header ethernet_t { bit<48> dstAddr; bit<48> srcAddr; bit<16> etherType; }
header ipv4_t {
    bit<4>  version; bit<4>  ihl;
    bit<8>  diffserv; bit<16> totalLen;
    bit<16> identification; bit<3> flags; bit<13> fragOffset;
    bit<8>  ttl; bit<8> protocol; bit<16> hdrChecksum;
    bit<32> srcAddr; bit<32> dstAddr;
}

parser MyParser(packet_in packet, out headers hdr,
                inout metadata meta, inout standard_metadata_t smeta) {
    state start { transition parse_ethernet; }
    state parse_ethernet {
        packet.extract(hdr.ethernet);
        transition select(hdr.ethernet.etherType) {
            0x0800: parse_ipv4;
            default: accept;
        }
    }
    state parse_ipv4 {
        packet.extract(hdr.ipv4);
        transition accept;
    }
}
```

Tables bind match keys to actions, and the *control block* sequences them:

```p4
control MyIngress(inout headers hdr, inout metadata meta,
                  inout standard_metadata_t smeta) {
    action ipv4_forward(bit<48> dstAddr, bit<9> port) {
        smeta.egress_spec = port;
        hdr.ethernet.srcAddr = hdr.ethernet.dstAddr;
        hdr.ethernet.dstAddr = dstAddr;
        hdr.ipv4.ttl = hdr.ipv4.ttl - 1;
    }
    table ipv4_lpm {
        key      = { hdr.ipv4.dstAddr : lpm; }
        actions  = { ipv4_forward; drop; NoAction; }
        size     = 1024;
        default_action = drop();
    }
    apply { ipv4_lpm.apply(); }
}
```

The compiler maps each table to TCAM/SRAM in MAU stages and each action to the stage ALU. *Stateful* processing enters through `register` externs with atomic read-modify-write semantics within a single stage — the primitive on which SwitchML's aggregation and NetCache's counters are built [2][3].

Architectures matter because they define the *contract* between program and target. PSA standardizes the programmable blocks across vendors; TNA exposes Tofino-specific capabilities (wider ALUs, more stages, intrinsic metadata) that SwitchML exploits [2]. The trade-off is classic: portability (PSA) versus performance (TNA).

### 4.2 In-Network Aggregation for ML Training: SwitchML

Distributed data-parallel training synchronizes model replicas via *all-reduce* of gradients: with *n* workers each holding a gradient vector of size *m*, every worker must obtain the element-wise sum. Ring all-reduce exchanges `2(n−1)·m/n` bytes per worker — bandwidth that grows with cluster size and saturates the fabric [2].

SwitchML [2] observes that a programmable top-of-rack (ToR) switch can perform the reduction *in the network*. Workers stream gradient chunks to the switch; the switch aggregates them in on-chip registers and multicasts the sum back. The co-design is the heart of the contribution:

- **Streaming aggregation.** Gradients are partitioned into chunks sized to fit the switch's per-packet register budget; aggregation proceeds as a stream, so the switch needs only O(chunk) state rather than O(model) state — the key trick that fits a billion-parameter model into kilobytes of stage memory [2].
- **Fixed-point arithmetic.** PISA ALUs lack floating point, so gradients are quantized to fixed point on the host; the switch sums integers, and hosts dequantize. The authors show negligible accuracy impact [2].
- **Reliability via pooling.** Because switches cannot buffer for retransmission, SwitchML uses a *shadow-copy* protocol: each aggregation slot has redundant copies so that a lost packet's contribution can be reconstructed without stalling the pipeline [2].
- **Hierarchical reduction.** Multiple ToR switches aggregate locally and forward partial sums upward, scaling beyond a single rack [2].

> **Theorem (Aggregation bandwidth):** *With in-network aggregation, per-worker network traffic for all-reduce is Θ(m) independent of the number of workers n, versus Θ(m·(n−1)/n) per worker with O(n) total fabric traffic for ring all-reduce.*

Measured on real benchmark models (including ResNet and VGG variants), SwitchML accelerates training by up to **5.5×** over baseline NCCL-based all-reduce [2], with aggregation performed at *sub-RTT latency* — the switch adds nanoseconds where a host-side reduction adds microseconds.

### 4.3 In-Network Key-Value Caching: NetCache

Large-scale key-value stores suffer from *skew*: a tiny fraction of keys receives the majority of queries, overloading the servers that own those keys. Traditional remedies — server-side caching or selective replication — either barely help (caching on the same servers that are already hot) or require expensive data movement and consistency machinery [3].

NetCache [3] places the cache *in the ToR switch itself*, exploiting the observation that switches forward packets at orders of magnitude higher throughput than servers process requests. The design:

- **On-path interception.** Client query packets pass through the ToR switch, which matches the key against an on-chip match-action cache. On a hit, the *switch itself* crafts the response packet — no server involved [3].
- **Heavy-hitter detection in the data plane.** Because control-plane table updates run at only ~10K entries/second [3], NetCache cannot use LRU/LFU. Instead, a *Count-Min sketch* [3] in data-plane registers identifies hot keys entirely in hardware; the controller inserts only keys that cross a hotness threshold, amortizing the slow update path.
- **Write-through coherence.** Writes invalidate cached entries via a coherence protocol between switch and servers: the switch rewrites the operation field of the packet header to signal cache status, and the server serializes concurrent queries while atomically updating the cached value [3].
- **Load-balancing objective.** Unlike a conventional cache, NetCache does not need a 90% hit ratio; even a *moderate* hit ratio (<50%) on the hottest keys suffices to balance load, because absorbing the skewed head of the distribution removes the bottleneck [3].

The result is high aggregate throughput and low tail latency under rapidly changing skewed workloads — a regime where static partitioning collapses. NetCache is incrementally deployable: only the ToR switch is programmed; the rest of the network is untouched [3].

### 4.4 In-Band Network Telemetry and the P4Runtime Control Plane

**INT.** In-Band Network Telemetry [4] turns every data packet into a measurement probe. An *INT source* inserts an instruction header; each *transit hop* — a P4-programmable switch — appends metadata (ingress/egress timestamps, queue occupancy, link utilization); the *INT sink* strips the telemetry stack and exports it to an analyzer. Because telemetry rides *production* packets rather than synthetic probes, it observes exactly the path, queueing, and timing the application experiences — exposing, for example, intermittent latency spikes caused by transient queue buildup that probe-based systems miss [4]. The P4.org INT dataplane specification standardizes metadata formats and encapsulations (VXLAN-GPE, Geneve, TCP/UDP options) [4]. Recent work (DLINT/PLINT) reduces INT's per-packet overhead — which grows linearly with hop count — via deterministic per-flow spreading and probabilistic reservoir sampling [7].

**P4Runtime.** A programmable data plane is only manageable with a programmable control plane. *P4Runtime* [5] is a protobuf/gRPC API through which controllers manage the forwarding state of any P4 target: table entries, action profiles, multicast groups, counters, meters, and *digests* (data-plane-to-controller notifications). The compiler emits a *P4Info* file describing the program's tables and actions in a target-independent schema, so one controller binary manages heterogeneous devices. This is what lets NetCache's controller insert hot keys [3] and SwitchML's controller manage aggregation slots [2] without target-specific drivers — the control-plane analogue of P4's target independence.

## 5 Empirical Results / Formal Proofs

We consolidate the headline quantitative results of the three systems:

| System | Venue | Key result | Mechanism |
|---|---|---|---|
| SwitchML [2] | NSDI '21 | Up to **5.5×** training speedup; sub-RTT aggregation | Streaming fixed-point in-switch all-reduce |
| NetCache [3] | SOSP '17 | Orders-of-magnitude read throughput; steady under hot-out skew | On-chip match-action cache + HH detection |
| INT [4] | SOSR '15 demo; spec 2020 | Per-packet, per-hop queue/latency visibility | In-band metadata stack on production packets |
| P4 (language) [1] | CCR '14 | Protocol-independent line-rate forwarding | PISA: parser → MAUs → deparser |

Beyond benchmarks, we formalize the *feasibility condition* for in-network computing:

> **Theorem (Stateful line-rate feasibility):** *An in-network function f over per-packet state is implementable at line rate on PISA iff f decomposes into per-stage functions f_i, each computable with bounded SRAM accesses and bounded ALU operations within one MAU stage, with total state Σ|S_i| fitting on-chip memory.*

*Proof sketch.* (⇒) Any PISA implementation assigns each packet's processing to the fixed stage sequence; operations exceeding a stage's budget cannot complete in the packet's time slot, so feasibility implies such a decomposition. (⇐) Given the decomposition, map each f_i to one MAU stage; the feed-forward pipeline sustains one packet per clock (Theorem, §3), and atomic per-stage register updates preserve consistency of each S_i. ∎

The *corollary* is the design rule of the field: **fit the state into the stage budget, or move the function to the host**. SwitchML fits via streaming chunks [2]; NetCache fits via sketches plus a slow control-plane insert path [3]; anything requiring unbounded per-packet memory access (e.g., full LRU) is infeasible — which is precisely why NetCache abandoned it.

## 6 Limitations

**Bounded stateful computation.** PISA ALUs support only simple integer/logic operations per stage — no floating point, no division, no unbounded loops. Applications must quantize (SwitchML's fixed-point gradients [2]) or restructure (NetCache's sketch-based HH detection [3]). This is a *hard* ceiling, not a compiler limitation.

**Weak data-plane consistency.** Register read-modify-write is atomic within a stage, but there is no cross-stage transaction: concurrent packets can interleave updates to related state. NetCache's coherence protocol pushes consistency to the server [3]; SwitchML's shadow copies tolerate loss rather than prevent it [2]. Programming with *eventual* data-plane consistency is error-prone and poorly supported by verification tools.

**Control-plane update bottleneck.** Data-plane state changes at line rate, but control-plane table updates run at ~10K entries/second [3]. Any design requiring per-packet or per-flow controller involvement (fine-grained caching, per-flow telemetry export) collapses under this asymmetry; the data plane must be *self-sufficient* for the common case.

**Memory scarcity.** On-chip SRAM/TCAM totals tens of megabytes — six orders of magnitude less than host DRAM. NetCache caches only the hottest keys [3]; SwitchML streams rather than stores [2]. In-network computing is therefore a *selective offload*, never a wholesale migration.

**Portability versus performance.** PSA-portable programs forgo target-specific externs; TNA-tuned programs (SwitchML [2]) lock to one vendor's silicon. The ecosystem has not yet converged on a portability story that preserves performance.

**Security surface.** A programmable parser that accepts operator-defined headers, plus in-band telemetry that exfiltrates queue state into packets, widens the attack surface: malformed INT stacks, header-confusion attacks, and side channels via shared register state are active research concerns.

## 7 Conclusion

In-network computing with programmable data planes reframes the switch from a *forwarder* into a *computational participant*. The P4 language and PISA architecture [1] supply the programming model; SwitchML [2], NetCache [3], and INT [4] demonstrate that aggregation, caching, and telemetry — three pillars of distributed systems — can be profitably relocated into the fabric; and P4Runtime [5] supplies the control-plane coupling that makes such systems deployable. The economics are compelling: nanosecond-scale, terabit-class compute, already paid for, sitting on every packet's path.

Yet the discipline imposed by the pipeline is unforgiving. Every in-network function must survive decomposition into bounded per-stage operations over bounded state — a constraint that shapes algorithms as surely as the PRAM model shaped parallel algorithms. The most promising direction is therefore *algorithmic*: designing distributed protocols (streaming aggregation, sketch-based detection, probabilistic telemetry [7]) that are native to the match-action model, rather than porting host algorithms into a pipeline that cannot hold them. The switch is not a small server; it is a new computational substrate, and we are still learning its idioms.
