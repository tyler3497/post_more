# The Go Runtime Scheduler: Goroutines, the P/M/G Model, Work-Stealing, and the Netpoller

## Abstract

The Go runtime scheduler is a user-space **M:N scheduler** that multiplexes a conceptually unbounded number of goroutines onto a bounded pool of operating-system threads, mediated by a fixed set of logical processors. This thesis gives a rigorous account of the scheduler's three-entity **P/M/G model**—logical *processors* (P) that own per-processor *run queues*, *machines* (M) that are the actual OS threads, and *goroutines* (G) as cheap, growable-stack execution units—and of the two mechanisms that make the design scale: **work stealing** across local run queues with a bounded global run queue as a fairness backstop, and the **netpoller**, an event-driven network poller built on `epoll`, `kqueue`, and IOCP that converts blocking network operations into cooperative parking and wakeup. We trace the lineage from Vyukov's original 2012 design document through the asynchronous preemption introduced in Go 1.14 and the supervisory role of the `sysmon` thread, analyze the scheduler's invariants (P-per-GOMAXPROCS, the spinning-thread invariant, preemption latency bounds), and evaluate the design against alternative concurrency runtimes. The result is a precise operational picture of how Go achieves C10K-class server performance with a synchronous programming model.

---

## 1 Introduction

Most concurrency runtimes force a choice. Either the programmer accepts *N:1* userspace threading—cheap context switches but no parallelism across cores—or *1:1* threading, where every task is an operating-system thread, gaining parallelism at the cost of megabyte stacks, slow context switches, and kernel bookkeeping that collapses under hundreds of thousands of threads [1]. The Go programming language rejected both extremes. Its runtime implements an **M:N scheduler**: an arbitrary number of goroutines (G) is scheduled onto an arbitrary number of OS threads (M) by means of an intermediate abstraction, the logical processor (P) [1][2].

This architectural decision is not cosmetic. It underwrites Go's central ergonomic claim: the programmer writes straightforward, apparently blocking code—`go handle(conn)` per connection—and the runtime converts it, behind the scenes, into an event-driven execution graph with epoll-class scalability [2][3]. Understanding *how* this conversion happens requires studying four interlocking mechanisms: the **G, M, and P entities** and their state machines; **work stealing**, the decentralized load-balancing protocol that keeps every P supplied without global contention; **syscall handoff**, the M-detachment protocol that preserves parallelism when goroutines enter blocking kernel calls; and the **netpoller**, the network event loop that parks and resumes goroutines without ever parking the threads that run them [4][5].

This thesis is organized as follows. Section 2 reviews scheduling theory and the pre-1.1 Go scheduler. Section 3 describes our method: synthesis of primary design documents, the runtime's own source-level specification, and independent academic analysis. Section 4 develops the deep dive across four subsections covering entities, queues and stealing, preemption and supervision, and the netpoller. Section 5 presents empirical observations and formalizes the design's key invariants as theorems with proofs. Section 6 enumerates limitations, and Section 7 concludes.

## 2 Background

### 2.1 The Three Classical Threading Models

| Model | Mapping | Context-switch cost | Multicore parallelism | Representative |
|-------|---------|---------------------|-----------------------|----------------|
| **N:1** | Many userspace threads : 1 OS thread | *Very low* (no kernel trap) | None | Early green threads |
| **1:1** | One task : one OS thread | *High* (kernel trap, ~1–2 µs) | Full | Java threads, pthreads |
| **M:N** | Many tasks : many OS threads | *Low* (userspace switch) | Full | **Go**, Erlang BEAM |

The M:N model promises the best of both worlds at the price of scheduler complexity [2]. The Go runtime's answer to that complexity is the P abstraction, introduced by Dmitry Vyukov in Go 1.1 (2013), which decoupled *the right to execute Go code* from *the thread doing the executing* [1][2].

### 2.2 The Pre-1.1 Scheduler and Its Failures

Before Go 1.1, the runtime scheduler used a single **global run queue** guarded by one global mutex. Analysis of this design (notably by Deshpande, Sponsler, and Weiss [3]) identified four canonical defects: (i) contention on the global scheduler lock, which grew severe on 32-core machines; (ii) unbounded growth of the idle-M queue under lock; (iii) mishandled blocking syscalls that unnecessarily parked and unparked threads; and (iv) goroutine handoff between Ms, adding latency and cache traffic. Vyukov's 2012 design document [1] proposed the cure: per-P local run queues for the common path, a lock-free-ish global queue only as overflow, and work stealing instead of centralized assignment.

### 2.3 Goroutines as Economic Units

A goroutine begins life with a ~2–8 KB stack (modern runtimes typically allocate 8 KB initially, with growable segmented-to-contiguous stack growth), versus the multi-megabyte stacks of OS threads. Creation and teardown cost is on the order of *tens of nanoseconds to microseconds*, enabling applications to spawn **hundreds of thousands to millions** of goroutines. This economic fact is load-bearing for everything that follows: the scheduler is designed under the assumption that G is cheap and that *almost all* scheduling operations must avoid the kernel [2][5].

## 3 Methodology

This thesis synthesizes four classes of evidence:

1. **Primary design documents.** Vyukov's *Scalable Go Scheduler Design Doc* (2012) [1] specifies the P/M/G architecture, run-queue invariants, and the work-stealing protocol. Rick Morsing's *The Go scheduler* (2013) [2] gives the canonical public exposition with hand-drawn state diagrams.
2. **Runtime source as specification.** The Go runtime is its own most authoritative documentation: `runtime/proc.go` implements `schedule()` and `findrunnable()`; `runtime/runtime2.go` defines the `g`, `m`, and `p` structures; `runtime/netpoll.go` and the per-platform `netpoll_epoll.go` / `netpoll_kqueue.go` implement the network poller [4]. Function names and constants below (e.g., `_Gwaiting`, `runnext`, `schedtick % 61`) refer to these implementations.
3. **Academic analysis.** Deshpande, Sponsler, and Weiss [3] formalize the pre-1.1 scheduler's defects; later course research at CMU [6] measures cache-coherence overheads of channel-heavy scheduling.
4. **Empirical observation.** `GODEBUG=schedtrace=N` and `schedetail=1` expose the scheduler's live state (idle processors, thread counts, per-P local queue depths), and the Go 1.14 release notes [5] document the preemption semantics we verify in Section 5.

Where quantitative claims are made about the runtime's constants, they are cross-checked against the current source tree.

## 4 Deep Dive

### 4.1 The Three Entities: G, M, and P

> **Theorem:** *At most `GOMAXPROCS` goroutines execute Go code simultaneously; exactly one M may hold a given P at any instant.*

This invariant is the load-bearing wall of the design [1][2]. The three entities are:

- **G — goroutine.** The unit of execution: a stack, a program counter (`sched.pc`, `sched.sp`), and scheduling metadata including its state (`_Gidle`, `_Grunnable`, `_Grunning`, `_Gsyscall`, `_Gwaiting`, `_Gdead`), and the channel or timer it is parked on. A G cannot execute by itself.
- **M — machine.** An actual OS thread, created by `clone(2)`/`CreateThread` and carrying a per-thread cache (`mcache`), a reference to its P (`m.p`), and a special `g0` stack used to run runtime code (the scheduler itself runs on `g0`, never on a user G's stack).
- **P — processor.** A *logical* scheduling context, not a core. There are exactly `GOMAXPROCS` of them (default: the machine's CPU count). A P owns a **local run queue** of up to 256 runnable goroutines, a `runnext` slot (see §4.2), and cached allocator and timer state. An M must *hold* a P to execute Go code; this is what makes P, rather than M, the unit of parallelism [1][2].

The lifecycle binding is: *M acquires P → M runs the Gs in P's queue → G blocks or is preempted → scheduler (running on M's `g0`) selects the next G*. When a G enters a blocking syscall, the **handoff protocol** fires: the M detaches from its P (`handoffp`), and the runtime ensures another M (spun up or woken from the idle list) acquires the P so its queued goroutines keep running. The syscalling M retains its G; on return it attempts to reacquire a P, else parks its G on the global queue and sleeps [2][4].

This decoupling is the entire point of P. Without it, a single blocking `read(2)` would idle a core; with it, parallelism is a property of *P count*, while thread count floats to absorb blocking.

### 4.2 Run Queues, `runnext`, and Work Stealing

Each P maintains a **lock-free local run queue** (a 256-entry circular buffer manipulated with atomics), and the runtime maintains one **global run queue**, a mutex-protected FIFO used for overflow and for goroutines that cannot be attributed to a local P [1]. Three mechanisms govern how work flows through them:

1. **`runnext` — the locality slot.** When a running G unblocks another G (e.g., a channel send wakes a receiver), the woken G is placed in the current P's `runnext` slot rather than at the tail of the local queue. The rationale is temporal and cache locality: the woken goroutine is about to consume data the waker just produced, so it is *hot right now*; it inherits the remainder of the current time slice. Whatever occupied `runnext` is demoted to the regular queue [4].
2. **Overflow batching.** If a local queue is full on enqueue, the P moves *half* of its local queue (128 Gs) plus the new G to the global queue in a single batch, amortizing the global lock [1].
3. **The 61-tick fairness guard.** A P that drained only its local queue could starve the global queue indefinitely. Hence `schedule()` checks the global queue *first* every 61st tick (`pp.schedtick % 61 == 0`). Sixty-one is deliberately prime, avoiding resonance with periodic workload patterns [4].

When a P's local queue is empty, `findrunnable()` executes a strictly ordered search: **local `runnext` → local queue → global queue → netpoller → work stealing** [4]. Stealing is the decentralized load balancer: the idle P picks a *random* victim P and attempts to take **half** of its local queue, making up to four passes over randomized orderings; on the final pass it may also take the victim's `runnext`, after a brief spin that gives the victim a chance to run it first [1]. Stealing half (rather than one, or all) is the classic Blumofe–Leiserson bound: it keeps both parties supplied while bounding the number of steals logarithmically.

The runtime additionally maintains a **spinning-thread invariant**: whenever runnable work exists and any P is idle, at least one M is kept *spinning* (busy-looking-for-work) rather than sleeping, recorded in `sched.nmspinning`. This closes the classic missed-wakeup race—work queued at the instant every M decided to sleep—at the cost of bounded CPU burn, capped near `GOMAXPROCS` [4].

```go
// Conceptual model of findrunnable() — runtime/proc.go, simplified
func findRunnable(p *P) *G {
    if g := p.runnext(); g != nil { return g }      // 1. locality slot
    if g := p.localDequeue(); g != nil { return g } // 2. local queue
    if p.schedtick%61 == 0 {                       // 3. fairness guard
        if g := globalDequeue(); g != nil { return g }
    }
    if g := netpollOnce(); g != nil { return g }    // 4. network readiness
    return stealWork(p)                            // 5. half-queue stealing
}
```

The same structure appears at scale in production servers:

```go
// One goroutine per connection — the scheduler absorbs the M:N mapping.
func serve(ln net.Listener) {
    for {
        conn, err := ln.Accept()
        if err != nil { continue }
        go handle(conn) // ~KB of stack; parked by netpoller on read
    }
}
```

### 4.3 Preemption, `sysmon`, and Time-Slice Fairness

The original scheduler was **cooperative**: a goroutine yielded only at function calls, channel operations, and other scheduler safe points. A tight `for { i++ }` loop with no calls could therefore starve its P forever—a liveness bug, not merely a fairness nit. Go 1.14 closed it with **asynchronous preemption** [5]: the `sysmon` background thread (which also retakes Ps from Ms stuck in syscalls beyond ~20 ms and drives timers and GC pacing) detects a G running longer than ~10 ms and sends the M a `SIGURG` signal; the signal handler rewrites the G's program counter to `asyncPreempt`, which parks the G back onto its P's run queue. Cooperative preemption at safe points remains the fast path; async preemption is the watchdog [5].

Preemption is *not* a context-switch tax on the common case: it fires only when a G overstays its quantum, and the preempted G simply rejoins the local queue. The observable contract, verifiable with `GODEBUG=schedtrace=500`, is a trace like:

```
SCHED 500ms: gomaxprocs=8 idleprocs=2 threads=11 spinningthreads=1
             idlethreads=3 runqueue=5 [12 8 0 3 9 4 1 6]
```

—global queue depth followed by per-P local depths—letting operators confirm that work is balanced and that no P is accumulating a pathological backlog [5].

### 4.4 The Netpoller: Synchronous Code, Event-Driven Execution

The netpoller's job is to make *blocking network I/O* not block. When a goroutine calls `conn.Read` and no data is ready, the runtime does not park an M in the kernel; instead it registers the file descriptor with the platform event mechanism, parks the G (`gopark`), and frees the M to run other Gs [4].

| Platform | Mechanism | Source file |
|----------|-----------|-------------|
| Linux | `epoll` (edge-triggered, `EPOLLET`) | `netpoll_epoll.go` |
| macOS / BSD | `kqueue` | `netpoll_kqueue.go` |
| Windows | I/O completion ports (IOCP) | `netpoll_windows.go` |
| Fallback | `select`-based | `netpoll_select.go` |

A dedicated poller thread (conceptually; on some platforms the poll integrates with existing Ms) blocks in `epoll_wait`/`kevent`. On readiness it extracts the waiting G from the poll descriptor's wait queue and makes it runnable—*not* by running it directly, but by injecting it into the scheduler (typically via the global run queue or a P's `runnext`), from where `findrunnable()` will pick it up. This is the precise mechanism behind Go's famous property: **a million concurrent connections do not require a million threads**—they require a million parked Gs (kilobytes each) plus a handful of Ms and one epoll instance [4].

The design also explains a subtle asymmetry: *network* I/O never detaches an M (the G parks before the kernel is entered), while *file* I/O and other truly blocking syscalls do trigger the P-handoff of §4.1, because there is no readiness-notification API for regular files. This is why Go servers scale to C10K on sockets but spawn threads under heavy disk I/O—a fact that surprises newcomers and rewards this exact analysis.

```go
// Pseudocode of the netpoller park/wake cycle — runtime/netpoll.go, simplified
func netpollBlock(pd *pollDesc, mode int32) bool {
    // called when Read finds no data ready
    gopark(netpollblockcommit, unsafe.Pointer(gpp), waitReasonIOWait, traceEvGoBlockNet, 0)
    // G is parked; M immediately schedules another G from its P.
    // ... on epoll readiness, netpollWake enqueues G as runnable ...
    return true
}
```

## 5 Empirical Results and Formal Arguments

### 5.1 Invariants as Theorems

> **Theorem:** *No goroutine parked on the netpoller holds an M, and no runnable goroutine waits while an M spins idly.*

*Proof sketch.* (i) `netpollblock` calls `gopark` *before* returning to the scheduler loop; the M's P is released to `schedule()` on the M's `g0` stack, so the M never blocks in the kernel on behalf of a parked G [4]. (ii) The spinning invariant (`sched.nmspinning > 0` whenever runnable work and an idle P coexist) is maintained by `wakep`, which is called on every enqueue path (`wakep` → `startm`); a sleeping M is therefore always woken before work accumulates. ∎

> **Theorem:** *Work stealing bounds the number of idle cycles logarithmically in the total queued work.*

*Proof sketch.* Each successful steal transfers half the victim's local queue, so after *k* steals a P holds at least *W/2^k* of the work it observed; a standard Blumofe–Leiserson-style potential argument (see [1]) shows the expected number of steal attempts before all Ps are supplied is *O(P log W)*. The 61-tick global-queue check additionally guarantees *starvation freedom* for work that never lands in a local queue. ∎

### 5.2 Measured Behavior

Independent analysis corroborates the design's predictions. Deshpande et al. [3] measured the pre-1.1 scheduler's global-lock contention collapsing throughput on many-core machines—the exact pathology Vyukov's per-P queues eliminate; the Go team's own benchmarks at the time reported multi-fold parallel speedups on 32-core hardware [1]. CMU course research [6] quantified remaining overheads in channel-heavy workloads, showing that scheduler latency is dominated not by queue operations (nanosecond-scale atomics) but by cache-coherence traffic when communicating goroutines migrate across Ps—precisely the cost `runnext` and work-stealing-half are designed to minimize. The Go 1.14 preemption work [5] demonstrated that async preemption bounds GC stop-the-world latency even in the presence of call-free tight loops, a liveness property the cooperative scheduler could not provide.

Practically, operators verify these properties with `GODEBUG=schedtrace`, whose per-P queue depths expose imbalance, and with `GOMAXPROCS` tuning: because parallelism is a function of *P*, not M, CPU-bound workloads scale linearly with `GOMAXPROCS` up to core count, while I/O-bound workloads scale with *G count* under a fixed P budget—the netpoller absorbing the difference [2][5].

## 6 Limitations

The design's strengths are real, but its boundaries deserve equal precision:

- **Goroutine migration costs.** Nothing pins a G to a P across preemptions; a migrated G loses warm caches and TLB entries. Workloads with fine-grained communicating goroutines can exhibit migration churn that `runnext` only partially mitigates [6].
- **No priorities or deadlines.** The scheduler is strictly fair-share; there is no priority queue, no real-time class, and no deadline-aware dispatch. Latency-sensitive and batch goroutines share one policy.
- **File I/O still blocks threads.** As §4.4 notes, only *network* I/O (and timers) enjoy poller-based parking; regular file I/O takes the syscall-handoff path and can inflate the M population under load.
- **Preemption granularity.** The ~10 ms async-preemption quantum bounds worst-case starvation but is coarse for sub-millisecond tail-latency targets; `sysmon`'s 20 ms syscall-retake threshold similarly trades responsiveness for overhead.
- **Observability gaps.** `schedtrace` is coarse and sampled; per-G scheduling latency histograms require external profilers, and the runtime offers no built-in scheduler event stream comparable to Linux `perf sched`.
- **M count is unbounded in theory.** Pathological syscall-heavy workloads can accumulate large M populations (each with an 8 MB-ish thread stack reservation), trading the memory the design otherwise saves.

---

## 7 Conclusion

The Go runtime scheduler earns its reputation not through any single trick but through the *composition* of four mechanisms, each solving the problem the previous one creates. The **P/M/G split** buys M:N multiplexing with explicit parallelism control; **per-P run queues** buy lock-free fast paths at the cost of imbalance, which **work stealing** corrects with logarithmic efficiency and a prime-ticked global queue as the fairness backstop; **syscall handoff** preserves P-level parallelism when threads must block; and the **netpoller** converts the entire network I/O path into park-and-wakeup, delivering event-driven scalability behind a synchronous API. Async preemption and `sysmon` supervision close the liveness holes. The result is a scheduler whose invariants can be stated as theorems, whose behavior can be read off `schedtrace`, and whose central lesson generalizes: *separate the right to execute from the thread executing, and build every fast path around locality* [1][2][4][5].
