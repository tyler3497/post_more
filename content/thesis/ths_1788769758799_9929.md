# NVMe over Fabrics: RDMA Transports, Discovery Subsystems, Multipath Failover, and Zero-Copy Data Paths

## Abstract

This thesis presents a rigorous treatment of **NVM Express over Fabrics (NVMe-oF)** with an RDMA-centric emphasis: the queue-pair transport model that maps NVMe submission and completion queues onto RDMA work requests, the discovery subsystem and its Discovery Log Page mechanics, Asymmetric Namespace Access (ANA) multipath failover, and the zero-copy data paths that distinguish RDMA transports from message-only alternatives. We derive a latency model decomposing the end-to-end I/O completion time into queueing, fabric, and target components, prove a zero-copy invariant under inline SGL and RDMA WRITE/READ mappings, and formalize failover correctness as a liveness property over ANA group state transitions. Empirical grounding draws on SNIA's cross-transport performance evaluation and representative SPDK/Linux host-side configuration [1][7]. We close with limits — RoCE congestion sensitivity, security implications of unauthenticated RDMA memory keys [8], and the scaling constraints of queue-pair resource consumption — and directions for hardware-offloaded target design.

---

## 1 Introduction

NVM Express was conceived for *local* PCI Express-attached storage: a register-mapped interface with deep queues and a driver stack that dispenses with the SCSI translation layer. NVMe over Fabrics generalizes the queue-pair abstraction across a network, preserving the command set while substituting the PCIe transport with RDMA, TCP, or Fibre Channel [2]. Among these, **RDMA transports** — InfiniBand, RoCEv2, and iWARP — are the most latency-sensitive and analytically rich, because they transform the NVMe *memory/memory* transport model into direct hardware-mediated memory transfers that bypass the host CPU and kernel on the data path [3].

The engineering problem is deceptively simple: move NVMe queue entries and data buffers across a fabric without eroding the sub-10-microsecond latency budgets that make flash media useful. The solution rests on four pillars. First, the **RDMA transport binding** maps each NVMe queue pair (one submission queue, one completion queue) to an RDMA queue pair of send/receive work requests [3]. Second, the **discovery subsystem** — itself an NVMe-oF NVM subsystem exposing only a discovery controller — provides the mechanism by which hosts learn which subsystems, controllers, and namespaces are reachable through which transport addresses [2]. Third, **multipath failover** via ANA states lets hosts route I/O to *optimized* paths and survive path failure with kernel-native rerouting rather than multipath daemons [5]. Fourth, the **zero-copy data path** uses RDMA WRITE/READ and inline capsule placement so that payloads traverse the fabric at most once between host and target memory [1].

This thesis formalizes each pillar, develops a performance model, and proves the key correctness invariants. Our contributions: (i) a complete RDMA queue-pair data path decomposition with a latency model; (ii) a state-machine treatment of discovery and ANA failover with a liveness theorem; (iii) a zero-copy invariant proof; and (iv) quantitative grounding from published evaluations.

## 2 Background

### 2.1 NVMe over Fabrics Architecture

NVMe-oF extends the NVMe Base Specification's queue-pair model to fabrics [1][2]. A host and an **NVM subsystem** (an NVMe-oF target) establish communication through *controllers*; each controller owns one admin queue pair and zero or more I/O queue pairs. The host issues Fabrics commands (Connect, Property Set/Get, Authentication Send/Receive), Admin commands (Identify, Get Log Page, Namespace Attachment), and I/O commands (Read, Write, Flush) over these queues. NVMe-oF mandates **scatter/gather lists (SGLs)** for all commands, and the transport binding defines whether data travels *within capsules* (message model) or *via transport-specific memory transfers* (memory model) [1].

### 2.2 RDMA Primitives

RDMA provides *verbs*: queue pairs (QPs) of send and receive queues, completion queues (CQs), memory regions (MRs) registered with remote and local keys (rkey/lkey), and one-sided operations — RDMA WRITE and RDMA READ — that move data between memories without involving the remote CPU [3][8]. Two-sided SEND/RECEIVE operations carry control messages. The NVMe/RDMA binding (Revision 1.2, ratified 2025) requires the RDMA IP Connection Management service for establishment and assigns IANA ports: UDP 4420 for RoCEv2, TCP 4420 for iWARP [3].

### 2.3 Discovery and ANA

The **discovery subsystem** exposes a *discovery controller* whose only function is to serve the Discovery Log Page (log page identifier 70h): a list of Discovery Log Page Entries, each naming a subsystem NQN, transport type, address family, transport address, service ID, and controller ID [2]. Separately, the **ANA log page** (Asymmetric Namespace Access) reports per-namespace-group access states — *Optimized*, *Non-Optimized*, *Inaccessible*, *Persistent Loss*, *Change* — enabling hosts to prefer and fail over paths [1][5].

> Theorem: (Scope of this work). We treat NVMe-oF as the composition of (a) an RDMA transport binding realizing reliable ordered delivery of capsules and one-sided data transfers, (b) a discovery protocol converging to a complete reachable-subsystem view, and (c) an ANA-driven path selection policy. Each is analyzed independently and then composed.

## 3 Methodology

Our method combines specification analysis, operational modeling, and empirical grounding:

1. **Specification analysis.** We extract the normative requirements of the NVMe Base Specification 2.0c [1], NVMe over Fabrics 1.1a [2], and the RDMA transport bindings [3][4], in particular queue-pair mapping, capsule formats, SGL descriptor types (RDMA keyed data blocks), and discovery log semantics.
2. **Operational modeling.** We model the host–target interaction as a labeled transition system over queue-pair states (idle, connected, failed-over), and ANA group states as a lattice with a designated optimal element. Latency is decomposed additively and each component bounded.
3. **Configuration-as-evidence.** Representative host and target configurations (Linux `nvme-cli`, kernel `nvmet`, SPDK `nvmf_tgt`) are used as constructive witnesses that the modeled behaviors are realizable in production software [6].
4. **Empirical grounding.** We cite SNIA's 100 GbE study comparing RDMA (iWARP, RoCEv2) against TCP transports across workloads, MTU sizes, and backing media [7], and the NeVerMore security analysis of RDMA in NVMe-oF for the threat model [8].

## 4 Deep Dive

### 4.1 The RDMA Queue-Pair Data Path

Each NVMe queue pair maps to one RDMA queue pair [3]. The host posts the 64-byte NVMe command as an RDMA SEND; the target's pre-posted RECEIVE buffers catch it. Data transfer then proceeds by one of two mechanisms:

- **In-capsule data**: small transfers ride inside the command/response capsule as an SGL *data block* descriptor — a single SEND, no extra round trips.
- **RDMA-mapped SGL**: the command carries an SGL *RDMA* descriptor (rkey, remote address, length). The target issues RDMA WRITE (for host reads, pushing data to host memory) or RDMA READ (for host writes, pulling data from host memory) directly against the host's registered buffers, then returns the completion capsule via SEND [3].

This design yields the zero-copy property: the payload crosses the fabric exactly once, DMA'd by the RNIC into pinned host memory without kernel involvement. Contrast NVMe/TCP, where every byte traverses the host TCP/IP stack and is copied at least once [7].

The latency decomposition for a 4 KiB read over an RDMA-mapped SGL is:

$$T_{\text{total}} = T_{\text{post}} + T_{\text{SEND}} + T_{\text{tgt}} + T_{\text{RDMA-WRITE}} + T_{\text{cqe}} + T_{\text{poll}}$$

where $T_{\text{post}}$ is doorbell/verbs posting, $T_{\text{SEND}}$ the command capsule flight, $T_{\text{tgt}}$ the target-side media or cache service time, $T_{\text{RDMA-WRITE}}$ the one-sided data movement, $T_{\text{cqe}}$ the completion capsule flight, and $T_{\text{poll}}$ host completion polling. On modern RNICs $T_{\text{post}} + T_{\text{poll}} \approx 1$–$2\,\mu s$, and the fabric terms add roughly $1$–$3\,\mu s$ per hop at 100 GbE [7].

| Component | NVMe/RDMA (typical) | NVMe/TCP (typical) | Dominant cost |
|---|---|---|---|
| Command submission | ~0.5 µs (verbs post) | ~1–2 µs (socket + stack) | Kernel crossings |
| Data movement | 0-copy RDMA WRITE/READ | ≥1 copy in TCP stack | Memory bandwidth |
| Completion | ~0.5 µs (CQ poll) | ~1–2 µs (socket poll) | Interrupt/poll overhead |
| CPU per I/O (host) | < 1 core per MIOPS | several cores per MIOPS | Copy + stack processing |
| Congestion behavior | PFC/ECN dependent | Standard TCP CC | Loss sensitivity |

### 4.2 Discovery Subsystems and the Discovery Log Page

Discovery is itself an NVMe-oF subsystem whose NQN is the well-known `nqn.2014-08.org.nvmexpress.discovery`. The host connects a *discovery controller* (a controller that supports only Fabrics commands plus Get Log Page) and issues Get Log Page with LID 70h [2]. Each returned entry carries:

| Field | Width | Semantics |
|---|---|---|
| TRTYPE | 1 B | Transport: 1=RDMA, 2=FC, 3=TCP, 254=intra-host |
| ADRFAM | 1 B | IPv4, IPv6, InfiniBand (GUID), Fibre Channel |
| TRADDR | 256 B | Transport address (ASCII) |
| TRSVCID | 32 B | Service ID; for RDMA IP CM, a TCP port as ASCII decimal [3] |
| SUBNQN | 256 B | Subsystem NQN of the reachable controller |
| CNTLID | 2 B | Controller ID (dynamic controllers use FFFFh) |

The host then issues Connect commands to each advertised subsystem. Referral entries (SUBTYPE=1) chain discovery across subsystems, supporting *centralized* and *direct* discovery topologies [2]. A complete discovery round is:

```bash
# 1. Persist the discovery controller: connect to the discovery subsystem
nvme discover -t rdma -a 192.168.10.1 -s 4420

# 2. Connect to a discovered subsystem NQN over RDMA
nvme connect -t rdma -n nqn.2016-06.io.spdk:cnode1 \
  -a 192.168.10.1 -s 4420 -i 8 -l 3600

# 3. Inspect the resulting subsystem, controllers, and ANA states
nvme list-subsys /dev/nvme2n1
nvme ana-log /dev/nvme2 --output-format=json | jq '.ANA_Groups'
```

The `-i 8` sets I/O queue pairs per controller and `-l 3600` the controller loss timeout — the failover time budget discussed in §4.3.

### 4.3 Multipath Failover via ANA

The Linux kernel implements **native NVMe multipath**: multiple controllers (paths) to the same subsystem collapse into one namespace device, with an I/O policy (default `numa`, or `round-robin`) selecting among *live* paths [5]. ANA refines this: each ANA group reports a state, and the host prefers paths in the *Optimized* group, using *Non-Optimized* paths only when no optimized path is live.

```c
/* Simplified ANA-driven path selection (per I/O dispatch) */
enum ana_state { ANA_OPTIMIZED, ANA_NON_OPTIMIZED, ANA_INACCESSIBLE,
                 ANA_PERSISTENT_LOSS, ANA_CHANGE };

struct nvme_path *nvme_select_path(struct nvme_subsys *s)
{
    struct nvme_path *best = NULL, *fallback = NULL;
    list_for_each_entry(p, &s->paths, entry) {
        if (p->state != PATH_LIVE)
            continue;
        if (p->ana == ANA_OPTIMIZED && !best)
            best = p;                       /* preferred: zero penalty */
        else if (p->ana == ANA_NON_OPTIMIZED && !fallback)
            fallback = p;                   /* standby: usable on failover */
        /* INACCESSIBLE / PERSISTENT_LOSS paths are never selected */
    }
    return best ? best : fallback;           /* NULL => I/O error / retry */
}
```

Failover sequence on path loss: (1) the RDMA connection breaks and the controller enters reconnecting state; (2) after the keep-alive timeout (default 10 s) and controller-loss timeout, the path is marked dead; (3) the multipath layer re-routes in-flight and new I/O to surviving paths, typically completing failover in seconds with no application involvement [5]. SPDK's user-space NVMe bdev multipath mirrors this with per-thread I/O channels and ANA-aware path policies [6].

> Theorem: (Failover liveness). Let $P$ be the set of paths to a namespace, $L \subseteq P$ the live paths, and $A(p)$ the ANA state of $p$. If $\exists p \in L : A(p) \in \{\text{OPTIMIZED}, \text{NON\_OPTIMIZED}\}$, then every submitted I/O eventually completes or the controller-loss timeout expires — i.e., the multipath layer never wedges while a usable path exists. *Proof sketch.* Path selection scans $L$ in finite time and returns the first usable path or NULL. If NULL, no usable path exists, contradicting the premise. Retried I/O is re-dispatched on ANA change notifications (asynchronous events), which the target issues on every group transition [1], so the selection set tracks ground truth within one notification round.

### 4.4 Zero-Copy Data Paths and Memory Registration

Zero-copy rests on **memory registration**: host data buffers are pinned and registered with the RNIC, yielding rkeys the target uses in one-sided operations. The NVMe/RDMA binding defines the SGL *Keyed SGL Data Block* descriptor carrying exactly this (address, length, key) triple [3][4].

The invariant is:

> Theorem: (Zero-copy invariant). For any I/O whose SGL resolves to RDMA keyed descriptors or in-capsule data blocks, the payload traverses the fabric exactly once and is copied zero times by host or target CPUs. *Proof.* In-capsule data is DMA'd by the RNIC from the posted send buffer into the pre-posted receive buffer — one fabric traversal, no CPU copy. RDMA WRITE/READ moves data RNIC-to-RNIC between registered regions — one traversal, with the remote CPU uninvolved by the semantics of one-sided verbs [3][8]. No other copy step exists on the path.

Registration cost is amortized via fast memory registration (FRMR) or on-demand paging; SPDK pre-registers its huge-page DMA buffers once at startup, eliminating per-I/O registration from the hot path [6].

### 4.5 Target-Side Architecture: Kernel nvmet vs. SPDK

Two production target architectures realize the spec:

```ini
# SPDK nvmf_tgt: RDMA transport + subsystem + namespace (construct via RPC)
# scripts/rpc.py nvmf_create_transport -t RDMA -u 131072 -i 8192
# scripts/rpc.py nvmf_create_subsystem nqn.2016-06.io.spdk:cnode1 -a -s SPDK0001
# scripts/rpc.py nvmf_subsystem_add_ns nqn.2016-06.io.spdk:cnode1 Malloc0
# scripts/rpc.py nvmf_subsystem_add_listener nqn.2016-06.io.spdk:cnode1 \
#     -t RDMA -a 192.168.10.1 -s 4420
```

- **Linux `nvmet`** (in-kernel): `nvmet-rdma` offloads queue-pair handling to the RDMA stack; configuration via configfs. Simple, robust, interrupt-driven.
- **SPDK `nvmf_tgt`** (user-space, polled-mode): one reactor thread per core polls QPs and CQs; zero interrupts, zero context switches on the data path. This is the architecture behind most published million-IOPS NVMe-oF results [6][7].

The polled model trades a full CPU core for deterministic single-digit-microsecond tail latency — the right trade precisely when media latency (tens of microseconds for NAND, single digits for Optane-class) dominates.

## 5 Empirical Results and Formal Arguments

### Published performance evidence

SNIA's 2021 NVMe-oF study at 100 GbE compared iWARP, RoCEv2, and TCP transports across MTU sizes, workloads, and backing media (3D NAND vs. 3D XPoint) [7]. Key findings:

- RDMA transports outperform non-offloaded TCP across nearly all workloads; corner-case single-stream iWARP reads show round-trip spikes, implicating transport-level retransmission behavior rather than the NVMe-oF layer itself.
- MTU (1500 B vs. 9000 B jumbo) has surprisingly little effect on NVMe-oF performance — the capsule/SGL structure, not frame size, dominates.
- Backing-media differences are partly masked by target-side RAM caching: writes absorbed in cache show faster relative response than reads hitting media directly.

These observations validate the §4.1 model: when the fabric term $T_{\text{SEND}} + T_{\text{cqe}}$ is minimized by RDMA, the residual $T_{\text{tgt}}$ (media/cache) becomes the binding constraint, exactly as Amdahl-style reasoning predicts.

### Formal arguments

Beyond the two theorems above, we note a **safety property** of discovery: because discovery controllers accept no I/O commands and each entry is self-describing (TRTYPE/ADRFAM-gated address parsing [3]), a malformed entry cannot induce the host to issue I/O to an unintended endpoint — it can at worst cause a failed Connect. And an **ordering argument**: RDMA RC queue pairs provide reliable in-order delivery, so per-queue-pair NVMe command ordering is inherited from the transport without additional sequencing [3].

## 6 Limitations

1. **Queue-pair scalability.** Each NVMe queue pair consumes an RDMA QP, CQ entries, and registered receive buffers. Thousands of hosts × dozens of I/O queues exhaust RNIC resources; shared receive queues and dynamic queue scaling remain active engineering areas [3].
2. **RoCE congestion sensitivity.** RoCEv2 relies on Priority Flow Control and ECN; misconfigured lossless fabrics produce head-of-line blocking and the latency spikes SNIA observed [7]. iWARP's TCP-based congestion control is more robust but adds processing.
3. **Security.** RDMA's one-sided semantics bypass the OS: NeVerMore demonstrated packet injection into RDMA connections by unprivileged users, yielding unauthorized block access to NVMe-oF devices [8]. NVMe-oF authentication (DH-HMAC-CHAP, TLS 1.3 secure channels [1]) mitigates but is not universally deployed.
4. **Failover latency vs. timeout tuning.** Aggressive keep-alive timeouts speed failover but risk false positives on congested fabrics; the controller-loss timeout is a blunt instrument [5].
5. **In-capsule data limits.** Capsule sizes bound inline transfers; large I/O must use RDMA-mapped SGLs, reintroducing registration and an extra protocol phase.

---

## 7 Conclusion

NVMe over Fabrics on RDMA achieves its design goal — remote storage at near-local latency — through a coherent composition: queue pairs mapped to RDMA verbs, a self-describing discovery protocol, ANA-driven multipath with provable failover liveness, and a zero-copy invariant enforced by one-sided data movement. The empirical record [7] confirms that the fabric overhead can be driven to a few microseconds, leaving media and target software as the residual bottlenecks. The remaining challenges are operational rather than architectural: congestion-correct fabrics, scalable QP management, and closing the RDMA security gap [8]. As hardware-offloaded targets (RNIC-driven I/O with no target CPU [4]) mature, the host-side verbs-posting and polling costs analyzed here will define the final latency floor.
