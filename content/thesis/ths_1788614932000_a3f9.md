# Beyond Bloom Filters: Xor Filters, Ribbon Filters, and Morton Filters — Space-Optimal Approximate Membership Queries via Peelable Hypergraphs and Linear-System Solving

## Abstract

Approximate membership for a set *S* of *n* keys with false positive rate ε is dominated by the Bloom filter at 1.44·log₂(1/ε) bits per key — 44% above the information-theoretic lower bound log₂(1/ε) [1][7]. This thesis surveys the three leading post-Bloom designs — **xor**, **ribbon**, and **Morton filters**. Xor filters (Graf and Lemire, 2020) solve *B[h₀(x)] ⊕ B[h₁(x)] ⊕ B[h₂(x)] = f(x)* over a peelable 3-uniform hypergraph — 9.84 bits per key at ε ≈ 0.4%, within 23% of the bound, querying faster than Bloom and cuckoo filters [2]. Ribbon filters (Dillinger and Walzer, 2021) use banded linear systems over GF(2) with an on-the-fly solver: sub-10% overhead, and via bumped ribbon retrieval (BuRR), below 1% [3][4]. Morton filters (Breslow and Jayasena, 2018) compress cuckoo-filter structure into bandwidth-efficient blocks, with up to 15.5× higher insertion and 2.5× higher lookup throughput than cuckoo filters [5]. We develop the shared substrate — peelability thresholds [6], spatial coupling, banded elimination — and argue one convergence: *approximate membership is best solved as static-function retrieval reduced to sparse linear algebra over GF(2)*.

## 1. Introduction

The approximate membership query problem is among the most widely deployed interfaces in computer systems. From the SSTable filters guarding LSM-tree reads in RocksDB and Cassandra [3] to cache synchronization, network packet processing, and database join pruning, the contract is simple: given a static set *S* of *n* keys drawn from a universe *U*, build a compact data structure such that every *x ∈ S* is reported present (no false negatives) and every *x ∉ S* is reported absent with probability at least 1 − ε (false positive rate bounded by ε). Because the structure may return an arbitrary answer for *x ∉ S*, it can be dramatically smaller than any exact dictionary, which would require Ω(n·log|U|) bits [1][7].

For half a century the Bloom filter has been the default realization [1]. A Bloom filter stores *m* bits and *k* hash functions; each key sets *k* bits, and a query checks them. With *m/n = 1.44·log₂(1/ε)* bits per key, the false positive rate is ε — but the 1.44× overhead above the lower bound *n·log₂(1/ε)* is inherent to the bit-array design [1][7]. Cuckoo filters, quotient filters, and Golomb-compressed sequences chipped at the constant but never below ~20–30% overhead in practice [2][3].

A breakthrough, seeded by Dietzfelbinger and Pagh's observation that static-set AMQ is a special case of static-function retrieval [2], reframed the problem: store for each key *x* an *r*-bit fingerprint *f(x)* as the right-hand side of a linear equation over GF(2),

> **Theorem:** Let *h* map each *x ∈ S* to a sparse row vector *h(x) ∈ {0,1}^m*, and let *Z ∈ {0,1}^{m×r}* satisfy *h(x)·Z = f(x)* for all *x ∈ S* over GF(2). Then querying *h(y)·Z ≟ f(y)* has no false negatives and false positive rate *2⁻ʳ* for *y ∉ S* [2][4].

The engineering problem collapses to: choose row patterns *h(x)* so the *n × m* system is (a) solvable in linear time with *m ≈ n*, and (b) queryable with minimal memory traffic. Xor filters choose random 3-sparse rows solved by hypergraph peeling [2]; ribbon filters choose banded rows solved by banded elimination on the fly [3]; Morton filters take a hardware-driven route, compressing the cuckoo layout into blocks that trade computation for off-chip bandwidth [5].

This thesis develops each construction, states the key theorems, reproduces the core algorithms, and compares them on space, query throughput, construction cost, and mutability — then identifies each filter's efficient frontier and the gaps toward optimality.

## 2. Background

### 2.1 The information-theoretic floor

Consider any data structure that encodes the *n*-subsets of a universe *U* so that membership queries err with false positive rate at most ε. A counting argument shows that at least *n·log₂(1/ε)* bits are necessary (for ε|U| ≫ n), because each of the *(1−ε)*-fraction distinguishable negatives must be encoded somewhere [7]. Bloom filters need *1.44·n·log₂(1/ε)* bits — a factor 1.44 (≈ *1/ln 2*) above optimal — because their bit array treats set and unset bits symmetrically in the worst case [1][7]. Closing this gap is the central objective of the entire line of work surveyed here.

### 2.2 Static-function retrieval

A *retrieval data structure* represents *f : S → {0,1}^r* for a known static set *S* of *n* keys [4]. Queries on *x ∈ S* must return *f(x)*; queries on *x ∉ S* may return anything. The lower bound is exactly *n·r* bits — no key storage is needed [4]. Dietzfelbinger and Pagh showed that AMQ with false positive rate *2⁻ʳ* reduces to retrieval: store random *r*-bit fingerprints *f(x)* and compare on query [2]. The retrieval formulation strictly dominates the Bloom formulation, because the *n·r* bound is *tight*.

### 2.3 Peelable random hypergraphs

The xor filter's system has one row per key and three 1s per row — the incidence structure of a random 3-uniform hypergraph. It is solvable in linear time *iff* the hypergraph is *peelable*: repeatedly deleting degree-1 vertices (with their incident edge) must delete every edge [6]. A non-peelable hypergraph contains a non-empty 2-core, and its system may be inconsistent.

Fully random *k*-uniform hypergraphs have sharp peelability thresholds: for *k = 3*, density *c = n/m* must satisfy *c < c₃ ≈ 0.818*, whence *m ≥ 1.22·n* — the origin of xor's 1.23 overhead factor [2][6]. Dietzfelbinger and Walzer's *segmented* (spatially coupled) hypergraphs partition vertices into linearly arranged segments with each edge spanning *k* consecutive segments; these peel "from the outside in," with thresholds *f₃ ≈ 0.918, f₄ ≈ 0.977, f₅ ≈ 0.992* — the engine behind binary fuse filters, which approach *1.08n* storage [6].

## 3. Methodology

Our methodology is analytic and comparative. We treat each filter as an instantiation of the linear-system schema of §1, and we compare them along five axes:

1. **Space**: bits per key at fixed false positive rate, and overhead relative to *log₂(1/ε)*.
2. **Query cost**: number and locality of memory accesses, and arithmetic per query.
3. **Construction cost**: time, memory, and failure probability (retries).
4. **Functionality**: static vs. dynamic (insert/delete), counting, self-resizing.
5. **Tunable range**: which (ε, space) trade-offs are reachable.

For empirical figures we report the numbers measured by the original authors — on comparable hardware and uniform random 64-bit keys — and mark them as such [2][3][5]. We do not re-benchmark; the cited works share the FastFilter benchmarking harness [2][5], making their figures directly comparable.

## 4. Deep Dive

### 4.1 Xor Filters: Membership as Hypergraph Peeling

The xor filter (Graf and Lemire, 2020) is the cleanest realization of the retrieval-to-AMQ reduction [2].

**Construction.** For *n* keys and fingerprint length *r* ("Xor8": *r = 8*), allocate three blocks *B₀, B₁, B₂*, each an array of *r*-bit words of length *ℓ ≈ 1.23·n/3*. Each key *x* hashes to *h₀(x) ∈ [0,ℓ)*, *h₁(x) ∈ [ℓ,2ℓ)*, *h₂(x) ∈ [2ℓ,3ℓ)* — a hyperedge *{h₀(x), h₁(x), h₂(x)}* — with fingerprint *f(x) ∈ {0,1}^r*.

Peeling: queue degree-1 vertices; repeatedly remove such a vertex *v* and its unique edge *e = {v, u, w}*, pushing *(e, v)* onto a stack. If every edge is removed, assign in reverse (stack-pop) order:

> **Theorem (Xor assignment):** When edge *e = {v,u,w}* with fingerprint *fp* is popped, *v* was degree-1 when *e* was peeled, so *B[v] := fp ⊕ B[u] ⊕ B[w]* determines *B[v]* uniquely while *B[u], B[w]* are already fixed (or zero). Afterward, *B[h₀(x)] ⊕ B[h₁(x)] ⊕ B[h₂(x)] = f(x)* for every *x ∈ S* [2].

If a 2-core remains, peeling stalls and construction retries with a fresh seed. At density *1/1.23 < 0.818*, failure is rare and retry cheap [2][6].

**Query.** For *y*: report present iff *B[h₀(y)] ⊕ B[h₁(y)] ⊕ B[h₂(y)] = f(y)*. Three random reads, three XORs, one comparison. No false negatives; false positive rate *2⁻ʳ* [2].

**Performance.** Xor8 uses ≈ 9.84 bits/key at ε ≈ 0.39% — within 23% of the 8-bit bound — and queries *faster* than Bloom and cuckoo filters, because three cache-line reads with XOR reduction beat Bloom's *k ≈ 8* scattered reads [2]. The **xor+** variant bit-packs the final block with rank/select structures, undercutting even Golomb-compressed sequences in space [2].

**Binary fuse filters** (Graf and Lemire, 2022) replace the fully random hypergraph with Dietzfelbinger–Walzer's *segmented* construction [6]: keys map to *k* consecutive segments, peeling outside-in at densities up to *f₃ ≈ 0.918* (3-wise) and *f₄ ≈ 0.977* (4-wise). Result: **3-wise binary fuse** within **13%** of the bound, **4-wise** within **8%**, with construction 2× faster than xor thanks to better cache locality during peeling [8].

```python
def build_xor(keys, r=8, c=1.23):
    """Simplified xor-filter construction (peeling + reverse assignment)."""
    import math
    n = len(keys)
    L = math.ceil(c * n / 3)          # block length; 3 blocks total
    B = [0] * (3 * L)                # r-bit fingerprint array
    # hypergraph: vertex -> set of edge indices
    adj = [set() for _ in range(3 * L)]
    edges = []
    for x in keys:
        h = (h0(x) % L, L + h1(x) % L, 2 * L + h2(x) % L)
        e = len(edges)
        edges.append((h, fingerprint(x, r)))
        for v in h:
            adj[v].add(e)
    from collections import deque
    q = deque(v for v in range(3 * L) if len(adj[v]) == 1)
    stack = []
    while q:
        v = q.popleft()
        if len(adj[v]) != 1:
            continue
        e = next(iter(adj[v]))
        (a, b, d), fp = edges[e]
        stack.append((e, v, fp))
        for u in (a, b, d):
            adj[u].discard(e)
            if len(adj[u]) == 1:
                q.append(u)
    assert len(stack) == n, "2-core nonempty: retry with new seed"
    while stack:                     # reverse assignment
        e, v, fp = stack.pop()
        (a, b, d), _ = edges[e]
        others = [u for u in (a, b, d) if u != v]
        B[v] = fp ^ B[others[0]] ^ B[others[1]]
    return B, L

def contains(B, L, y, r=8):
    h = (h0(y) % L, L + h1(y) % L, 2 * L + h2(y) % L)
    return (B[h[0]] ^ B[h[1]] ^ B[h[2]]) == fingerprint(y, r)
```

### 4.2 Ribbon Filters: Banded Linear Systems and On-the-Fly Solving

Ribbon filters (Dillinger and Walzer, 2021) keep the linear-system schema but change row geometry: each row is a *band* — *w* consecutive ones starting at random position *s(x) ∈ [m − w + 1]* — plus an *r*-bit right-hand side *f(x)* [3]. The banded system *M·Z = y* is solved by Gaussian elimination touching only *O(w)* entries per row, and queries read *w* *contiguous* words — far better cache behavior than xor's scattered triple.

The key contribution is **RIBBON**, "Rapid Incremental Boolean Banding ON the fly" [3]:

> **Theorem (RIBBON solver):** Maintain a table *T* of at most one pivot row per start position, in row-echelon form. To insert key *x* with row *c(x)* and rhs *f(x)*: while *c(x)* is nonzero, let *i* be its first 1; if *T[i]* is empty, store it and succeed; else XOR the stored row in and continue. Insertion fails iff a zero row with nonzero rhs appears. Inserting rows in order of increasing *s(x)* makes the whole construction expected *O(n)* time [3][4].

This is incremental Gaussian elimination resembling hash-table insertion — each row is reduced against stored pivots until it finds an empty slot, and back substitution then comes from a single reverse pass. With *m = n/(1−ε)* rows, failures are negligible, and ribbon filters achieve **overhead below 10%** with xor-competitive queries — strongest at larger false positive rates *f ≥ 2⁻⁷*, where xor's fixed 23% overhead cannot shrink [3].

```rust
/// RIBBON on-the-fly insertion of one row (banded Gaussian elimination).
/// table[i]: optional (w-bit row, r-bit rhs) pivot starting at position i.
fn ribbon_insert(table: &mut [Option<(u64, u64)>], start: usize,
                 mut row: u64, mut rhs: u64, w: usize) -> bool {
    let mut i = start;
    loop {
        // find first set bit of row
        let b = row.trailing_zeros() as usize;
        if b >= w { return rhs == 0; }      // zero row: consistent iff rhs == 0
        let pos = i + b;
        match table[pos] {
            None => { table[pos] = Some((row, rhs)); return true; }
            Some((prow, prhs)) => {
                // eliminate: row ^= pivot shifted to align first ones
                row ^= prow << b;   // (pivot's first 1 is at bit 0)
                rhs ^= prhs;
                i = pos;            // continue reduction
            }
        }
    }
}
```

### 4.3 Homogeneous Ribbon and Bumped Ribbon Retrieval (BuRR)

**Homogeneous ribbon.** Drop the right-hand side: solve *M·Z = 0* and fill the free variables *randomly*. A query for *y ∉ S* computes *c(y)·Z* over its window — a nearly uniform *r*-bit value, equal to the expected *0^r* with probability *2⁻ʳ* [4].

> **Theorem (Homogeneous ribbon):** With ribbon width *w = Θ(max(r, log w)/ε)*, the homogeneous ribbon filter has false positive rate *φ ≈ 2⁻ʳ* and space overhead *O(ε)*, expected construction time *O(n/ε)*, query time *O(r)*. No retries are needed — insertion *cannot fail* since the homogeneous system is always consistent [4].

The filter stores *no per-key data at all* — fingerprints emerge from randomizing the solution space.

**Bumped ribbon retrieval (BuRR).** The band structure leaves the last *w − 1* rows underloaded; BuRR reclaims them by *bumping* tail keys into a recursively constructed second layer [4]. Layers shrink geometrically, so total overhead drops **below 1%** — the first practical filter to essentially attain the lower bound — with *O(r)* queries and fast construction [4]. A 2024 brief announcement gives a *parallel* BuRR construction with 14× speedup on 32 cores at 105 bytes/thread extra space [9].

### 4.4 Morton Filters: Compressed Sparse Cuckoo Filtering for Bandwidth-Bound Hardware

Morton filters (Breslow and Jayasena, 2018) attack a different bottleneck: *off-chip memory bandwidth* [5]. A cuckoo filter's lookups touch two random buckets — two cache lines / DRAM rows. On bandwidth-constrained accelerators, those random accesses dominate.

The Morton filter reorganizes the cuckoo table into **blocks** of *B* buckets with three mechanisms [5]:

1. **Block Selection Algorithm (BSA):** insertions scan for the first block with a free slot, *biasing* occupancy toward early blocks — the filter is *logically sparse* even at high load.
2. **Compressed format:** empty late blocks are elided from the memory-resident image.
3. **Overflow Tracking Array (OTA):** succinct embedded metadata records which blocks overflowed, letting lookups *prune* probes without touching DRAM — computation traded for avoided memory traffic.

Morton filters keep full dynamic functionality — **insert, delete, lookup, counting** — while improving insertion throughput by **0.9–15.5×**, lookup by **1.3–2.5×**, and deletion by **1.3–1.6×** over cuckoo filters, using *less* memory than a Bloom filter at false positive rates below ~1–3% [5]. They also **self-resize**: logical capacity can double using only the internal representation (at increased FPR), unlike vanilla cuckoo filters which need the backing key set [5].

Where xor and ribbon are *static* (rebuild on any change), Morton is *dynamic* — mutability costs a higher space constant than ribbon's <1%, but the functionality is incomparable: SSTable filters want ribbon; flow tables want Morton.

## 5. Empirical Results and Proofs

**The peeling threshold theorem** (Dietzfelbinger–Walzer [6]) is the load-bearing result for xor-family filters: for the segmented *k*-uniform model, peelability holds w.h.p. up to *f₃ ≈ 0.918* (vs. *0.818* fully random). This single theorem explains why binary fuse filters beat xor filters by 10 points of overhead with identical query paths [8].

**The RIBBON solver analysis** [3] shows inserting rows in *s(x)*-order keeps the pivot table in echelon form with *O(w)*-bit rows, so each insertion costs *O(w)* word operations; the overload parameter ε trades a *1/(1−ε)* row multiplier against failure probability, bounded and validated empirically.

**The BuRR theorem** [4] establishes overhead *O(ε)* with *φ ≈ 2⁻ʳ* and expected construction *O(n/ε)* — the lower bound approached by a *practical, implemented* structure. The accompanying C++ implementation (fastfilter_cpp) is the community benchmark artifact [5].

**Empirical head-to-heads** (FastFilter harness, uniform 64-bit keys) [2][5][8]: xor filters query at ~40–60 ns/key, ~2× faster than Bloom, because the query is three dependency-free loads plus XORs; ribbon matches xor at equal overhead and wins decisively below 15% overhead (a regime xor cannot reach); Morton filters win where the metric is bytes moved, not cycles spent [3][5].

> **Theorem (Lower bound):** Any AMQ structure with false positive rate ε (ε|U| ≫ n) needs ≥ *n·log₂(1/ε) − O(n)* bits. Bloom filters need *1.44·n·log₂(1/ε)*. The gap between 1.0 and 1.44 is the entire game — and ribbon/BuRR have, for practical purposes, closed it [4][7].

## 6. Limitations

1. **Static vs. dynamic is a hard split.** Xor, ribbon, and binary fuse filters are *immutable*: any change requires a full rebuild from the retained key set [2][3]. Morton filters are dynamic but pay a cuckoo-like space constant [5]. No known construction is simultaneously <5%-overhead *and* fully dynamic — the field's central open problem.
2. **Construction memory.** Peeling and RIBBON need auxiliary structures ~*n* during the build; a filter *storing* 9 bits/key may need 50+ bytes/key transiently to *construct* [2]. Partially addressed by sharding and parallel BuRR [9].
3. **Failure handling.** Xor construction can hit a 2-core and retry with a new seed — a rare latency tail; homogeneous ribbon eliminates this [2][4].
4. **Adversarial inputs.** False-positive analyses assume random hashes and non-adaptive queries. An adversary observing positives can adaptively extract members at rate *2⁻ʳ* per query — quantify before adversarial deployment [2].
5. **Small-*n* overhead.** Asymptotic figures assume large *n*; seeds and block rounding dominate below ~10⁴ keys [3].
6. **Morton complexity.** BSA tuning, OTA sizing, and the compressed format make Morton filters far harder to implement than xor filters — justified only where bandwidth is the binding constraint [5].

---

## 7. Conclusion

The decade since the retrieval reduction has turned approximate membership from a bit-array craft into *sparse linear algebra over GF(2)*. Xor filters showed hypergraph peeling beats Bloom in size and speed [2]; binary fuse showed spatial coupling pushes the peeling threshold — and overhead — far lower [6][8]; ribbon showed banded systems with on-the-fly elimination buy locality and tunable sub-10% overhead [3]; homogeneous ribbon and BuRR showed the lower bound is *practically reachable* at <1% overhead [4]; Morton showed that where bandwidth binds, compressing the dynamic cuckoo layout is the right trade [5].

The guidance is crisp. For **static sets** — SSTable filters, immutable snapshots — use **BuRR/homogeneous ribbon** when space is paramount, **binary fuse (3-wise)** when latency dominates. For **dynamic sets**, **Morton filters** dominate on bandwidth-constrained hardware, cuckoo filters elsewhere. Bloom remains the pedagogical baseline.

Open problems: a *dynamic* filter with <5% overhead; spatial coupling for *k = 2* geometries; GPU-native parallel ribbon construction; tight adaptive-adversary leakage bounds for fingerprint AMQs. The lower bound is in sight; the engineering is not finished.
