# Zoned Namespace SSDs: Host-Managed Garbage Collection, Copyback Semantics, and LSM-Tree Integration

## Abstract

The Zoned Namespace (ZNS) command set for NVMe SSDs redraws the division of labor between host software and flash firmware by exposing erase-block-aligned zones that must be written sequentially and explicitly reset. This thesis presents a systematic treatment of ZNS as a storage interface: it formalizes the zone model and its write-pointer invariant, derives the Zone Append primitive as the mechanism for concurrent intra-zone writers, and develops the theory of **copyback semantics** — the data-relocation discipline that replaces device-side garbage collection when the host assumes ownership of reclamation. We analyze host-managed garbage collection policies over zones, prove bounds on write amplification under lifetime-segregated placement, and examine the concrete integration of log-structured merge (LSM) trees through the ZenFS storage backend for RocksDB. Drawing on published characterizations of first-generation ZNS hardware, we show that zone-specialized stacks achieve **2× write throughput** and **2–4× lower 99.9th-percentile read latency** versus block-interface SSDs built on identical media [2]. We conclude with its limitations — open-zone limits, append-latency penalties, and metadata fragility — and argue that ZNS converts the flash "unwritten contract" into an explicit, auditable one.

## 1 Introduction

For three decades the block interface has hidden the physics of NAND flash behind a fiction: fixed-size sectors that can be overwritten in place. Inside every conventional SSD, a Flash Translation Layer (FTL) sustains this fiction through an LBA-to-physical page map, background garbage collection (GC), wear leveling, and write buffering. The cost of the fiction is well documented: device DRAM for the mapping table is the largest bill of materials after NAND itself, garbage collection steals bandwidth and injects tail latency, and over-provisioning — typically 7–28% of raw capacity — is capacity the customer buys but cannot use [8].

The Zoned Namespace (ZNS) command set, standardized by NVM Express beginning with revision 1.1 in 2021 and extended in revision 1.2 (2024), proposes a different bargain [1]. A ZNS namespace is divided into *zones*, each an erase-block-sized, sequentially-written region with a device-maintained write pointer. The host may only write at the write pointer; a zone is reclaimed by an explicit host-issued *reset*, after which the host is responsible for having relocated any live data. Reads remain fully random. By aligning the interface with the underlying erase-before-write physics, ZNS **eliminates the device-side FTL's garbage collector**, reduces mapping DRAM by orders of magnitude, and reclaims most over-provisioning as usable capacity — reported gains exceed **20% additional capacity** on identical hardware [3].

This reallocation of responsibility is not free. The host must now implement the placement and reclamation policies the FTL used to hide: sequential write discipline, zone-state management, lifetime-aware data grouping, and crash-consistent metadata. The purpose of this thesis is to make that burden precise. Our contributions are fourfold:

1. **A formal model of the zone abstraction**, including the write-pointer invariant, zone capacity versus zone size, and the full zone state machine defined by the Zone Management Send command [1].
2. **A theory of copyback semantics** distinguishing host-initiated copy (read–rewrite) from device-internal relocation, with a derived write-amplification bound for host-managed GC.
3. **An analysis of Zone Append** as the concurrency primitive that removes the single-writer-per-zone bottleneck [3].
4. **A case study of LSM-tree integration** via ZenFS, the RocksDB filesystem plugin that maps SST files onto zones and eliminates background GC by construction [6].

## 2 Background

### 2.1 From Open-Channel SSDs to Zoned Namespaces

The road to ZNS passes through open-channel SSDs, which exposed raw NAND channels, dies, and planes to the host and demanded that the host implement the entire FTL. Open-channel designs proved the principle — host control enables better tail latency and lower write amplification — but failed the ecosystem test: every flash generation required host rewrites, and reliability mechanisms (bad-block management, read-disturb handling, retention) leaked across the boundary [8].

ZNS is the pragmatic middle ground. The device retains responsibility for media reliability (error correction, bad-block remapping, refresh), while the host takes ownership of *data placement and garbage collection* — precisely the decisions that determine write amplification and tail latency [2]. The zone is the unit of both parallelism and reclamation: I/O to different zones is isolated and parallel, and a zone reset reclaims an entire erase unit in one operation.

### 2.2 The Zone Abstraction

A zone is a contiguous range of logical blocks of *zone size* (a power of two for cheap LBA↔zone arithmetic), of which *zone capacity* LBAs are writable; capacity ≤ size, with the difference aligned to the erase unit of the media [2]. Each zone carries a **write pointer (WP)**: the LBA at which the next write must land. Sequential-write-required zones enforce the invariant

> **Theorem (Write-Pointer Invariant):** For any sequential-write-required zone in the *Open* or *Full* state, every accepted write command's starting LBA equals the current write pointer, and on completion the write pointer advances by the transfer length. Any write whose starting LBA differs is rejected with an unaligned-write error.

The Zone Management Send command provides the control plane: **Open**, **Close**, **Finish**, **Reset**, **Offline**, and (in revision 1.2) descriptor-extension operations [1]. Reset returns a zone to the *Empty* state and the write pointer to the zone start; Finish advances a partially written zone directly to *Full* so it can be reset without padding. A small number of zones may be *randomly writable* (conventionally writable) for metadata, but this area is typically a tiny fraction of capacity [2].

### 2.3 The Zone Append Command

The classical zone model admits only one outstanding writer per zone, since two writers cannot both target the write pointer without racing. The **Zone Append** command (opcode 7Dh) solves this: the host supplies a zone start LBA and data, and the *device assigns* the actual placement, returning the assigned LBA in the completion [3]. Append therefore offloads fine-grained placement to the SSD, enables multiple concurrent writers per zone, and allows clients in distributed filesystems to write directly to shared zones. Measurements on early hardware show append latency slightly *higher* than positioned writes at equal transfer size, so the choice between Write and Zone Append is a latency-versus-concurrency tradeoff that filesystems must expose as a first-class decision [4].

## 3 Methodology

Our analysis follows three complementary methods:

1. **Specification analysis.** We derive the zone state machine, command semantics, and management operations directly from the ratified NVM Express ZNS command-set specifications (revisions 1.1 through 1.2) [1].
2. **Analytical modeling.** We formalize host-managed garbage collection as a zone-selection and relocation problem, derive write-amplification bounds under segregated placement, and contrast host copy paths with device-side copyback.
3. **Empirical grounding.** We anchor quantitative claims in published measurements of first-generation ZNS devices and zone-specialized software (RocksDB/ZenFS, F2FS), notably the characterization by Bjørling et al. [2] and the CLUSTER 2023 performance study [4], supplemented by the znstools "written contract" analysis [5] and the USENIX Vault 2020 zone-append presentation [3].

The LSM-tree integration discussion is grounded in the design and documented behavior of ZenFS [6] and the key-value-separation study built atop it [7].

## 4 Deep Dive

### 4.1 The Zone State Machine and the Cost of a Reset

A zone's lifecycle is a finite-state machine driven entirely by host commands and write completions. The principal states are:

| State | Write pointer | Writable? | Meaning |
|---|---|---|---|
| **Empty** | = ZSLBA | Yes | Fresh; accepts writes from the start |
| **Implicitly Open** | > ZSLBA | Yes | First write arrived without explicit Open |
| **Explicitly Open** | > ZSLBA | Yes | Host issued Open; resources reserved |
| **Closed** | frozen | No | Quiesced; cheap to re-open |
| **Full** | = ZSLBA + capacity | No | No space remains |
| **Read Only** | frozen | No | Media-driven; host cannot write |
| **Offline** | — | No | Defective; excluded from use |

*ZSLBA = Zone Start LBA. Adapted from the state-transition rules of the ZNS specification [1].*

The transitions that matter for GC design are *Finish → Full* and *Full → Reset → Empty*. A crucial subtlety: **reset is the only reclamation primitive, and it discards everything**. Unlike a TRIM on a conventional SSD — a hint the FTL may act on lazily — a ZNS reset is an immediate, irrevocable erasure of the zone's contents from the host's perspective. Consequently, the host GC must guarantee, before issuing reset, that every live byte has been relocated elsewhere. This is the *copyback obligation*, and it makes host metadata — the zone-to-liveness accounting — the single most reliability-critical structure in the stack.

The device also caps the number of concurrently open zones (*maximum open zones*, a few tens on early hardware). Because each open zone holds controller resources, a host stack that fans writes across many zones can be throttled by this limit; ZenFS and similar systems therefore multiplex file streams onto a bounded pool of open zones [6].

### 4.2 Copyback Semantics: Host Copy versus Device Relocation

In a conventional SSD, garbage collection is a *device-internal copyback*: the FTL reads live pages from a victim erase block into controller buffers and rewrites them elsewhere, invisible to the host. The host pays in stolen bandwidth, unpredictable tail latency, and write amplification it cannot observe or control.

ZNS inverts the visibility. All relocation is *host-initiated copy*: the host reads live data from a victim zone and rewrites it into a fresh zone, then resets the victim. We call this the **copyback semantics** of ZNS — not because the device performs copyback, but because the *semantic obligation* of copyback (preserve live data across erasure) is transferred to the host. This yields three structural differences:

1. **Observability.** Every relocated byte traverses the host's I/O path; write amplification becomes a measurable, attributable quantity rather than a firmware secret.
2. **Scheduling control.** The host decides *when* relocation happens (idle-time, low-water-mark, or on-demand), eliminating the GC-induced tail-latency spikes that plague conventional SSDs under mixed workloads [2].
3. **Policy expressiveness.** The host can group data by *lifetime*: short-lived and long-lived data placed in different zones die together, so victim zones reset nearly empty.

The relocation cost can be bounded. Consider zones of capacity *C* pages, a steady-state workload with average live fraction *f* per victim zone, and lifetime-segregated placement such that victim zones are selected at live fraction *f_v*:

> **Theorem (Host-Managed GC Write Amplification):** Under greedy victim selection with lifetime segregation, the steady-state write amplification *WA* satisfies *WA ≤ 1 + f_v / (1 − f_v)*, and with perfect lifetime grouping *f_v → 0* so *WA → 1*.

*Proof sketch.* Each user page written eventually dies or is relocated once per GC cycle. In a victim zone with live fraction *f_v*, reclaiming *C(1 − f_v)* dead pages requires relocating *C·f_v* live pages. Amortized over the dead pages freed, each GC cycle contributes *f_v/(1 − f_v)* extra writes per user write. Adding the original write gives the bound. With perfect segregation, victims are entirely dead (*f_v = 0*) and no relocation occurs — the theoretical optimum that motivates lifetime hints in ZenFS [6]. ∎

Contrast this with device-side GC, where the FTL's victim selection is blind to application lifetimes and *f_v* is typically much larger, yielding the familiar 2–4× write amplification of conventional SSDs under random-write workloads.

The price of host copyback is bandwidth: relocation consumes host PCIe and CPU cycles. The Zone Append command partially offsets this by allowing multiple relocation threads to append concurrently into one destination zone without write-pointer coordination [3].

### 4.3 Zone Append: Breaking the Single-Writer Bottleneck

Without Append, each zone admits exactly one outstanding positioned write — a severe constraint for both foreground ingestion and GC relocation parallelism. Zone Append changes the protocol from *positioned* to *device-assigned*:

```c
/* Simplified Zone Append submission (NVMe opcode 0x7D) */
struct nvme_zns_append {
    __u8  opcode;      /* 0x7D: Zone Append */
    __u8  flags;
    __u16 command_id;
    __le32 nsid;
    __le64 zslba;      /* zone start LBA: placement domain */
    __le32 nlb;        /* number of logical blocks */
    /* ... */
};
/* On completion, CQE DW0 returns the LBA actually assigned. */
```

The device serializes appends internally at the write pointer and reports each assigned LBA, so *N* threads can share one zone with no host-side locking. This unlocks three patterns [3]:

- **Direct client writes** in distributed filesystems: clients append to a shared zone; the returned LBAs become the placement record.
- **Parallel GC relocation**: multiple GC threads append live data into the same destination zone.
- **Offloaded data placement**: fine-grained packing decisions move into the controller, which knows the exact write-pointer state.

The measured cost is modest but real: append latency exceeds positioned-write latency at the same transfer size on characterized hardware, because the device must serialize at the pointer and report the assignment [4]. Filesystems therefore treat Write and Append as dual primitives and select per stream — a design point formalized in the 2024 LSF/MM zoned-storage discussions.

### 4.4 LSM-Tree Integration: ZenFS and Zone-Aligned SSTs

Log-structured merge trees are the natural client of ZNS: SST files are immutable, sequentially written, and deleted wholesale at compaction — precisely the lifetime profile that zones reward. ZenFS, a RocksDB `FileSystem` plugin, maps this affinity onto raw zoned block devices (ZNS SSDs and SMR HDDs) [6].

**Architecture.** ZenFS partitions the device's zones among *extents* belonging to files. Each SST file is assigned to one or more zones according to its **write lifetime hint** (short/medium/long/extreme), which RocksDB derives from the LSM level: L0 and WAL data are short-lived, deep-level SSTs long-lived. The mapping is direct:

```python
# Conceptual ZenFS placement (simplified)
def place_sst(sst_file):
    hint = sst_file.lifetime_hint        # from LSM level
    zone = zone_pool.acquire(hint)       # lifetime-segregated zone
    for extent in sst_file.extents:      # sequential write
        zone.append(extent.data)         # positioned write or Zone Append
    journal.record(sst_file.id, zone.id, extent.lbas)  # metadata journal
```

**No background GC — by construction.** When compaction deletes an SST, ZenFS decrements the zone's live accounting; when a zone's live fraction reaches zero, the zone is *reset* — no data is ever relocated. GC only occurs when zones mix lifetimes imperfectly, and the lifetime hints make this rare. ZenFS therefore "ensures that there is no background garbage collection in the file system or on the disk" [6], which is exactly why the 99.9th-percentile read latency drops 2–4× versus the same RocksDB on a block SSD: there is no firmware GC to inject multi-millisecond stalls into the read path [2].

**Crash consistency.** The Achilles' heel of host-managed placement is metadata: the zone→file mapping must survive power loss. ZenFS maintains a superblock plus a metadata journal in a small set of *randomly writable* zones, replayed at mount. This mirrors the FTL's own mapping-table journaling — but the journal is now host-visible, host-tunable, and tiny relative to a full LBA map.

**Extensions.** The ZSKV study builds key-value separation atop ZenFS: values above a size threshold are routed to dedicated zones with their own GC thresholds (`zone_gc_low_threshold`, `zone_gc_high_threshold`), demonstrating that zone-granular policy knobs compose with higher-level LSM optimizations [7].

## 5 Empirical Analysis and Proofs

### 5.1 Published Measurements

The most complete public characterization of first-generation ZNS hardware and zone-specialized software is Bjørling et al.'s study [2], which compares modified F2FS and RocksDB/ZenFS on a ZNS SSD against the identical physical hardware presenting a block interface:

| Metric | Block SSD | ZNS SSD (specialized stack) | Improvement |
|---|---|---|---|
| Write throughput (RocksDB) | baseline | ~2× | 2× [2] |
| 99.9th-pct random-read latency | baseline | 2–4× lower | 2–4× [2] |
| Usable capacity | baseline | +20% | over-provisioning reclaimed [3] |
| Device DRAM for mapping | full LBA map | ~order of magnitude less | zone-granular map [3] |

The CLUSTER 2023 performance study adds microarchitectural detail: write latency is *lower* than append latency at equal request size, open-zone limits and queue-depth interactions dominate tail behavior, and the mq-deadline scheduler's serialization of zoned writes becomes a bottleneck above ~200K IOPS — motivating first-class kernel support for both Write and Append paths [4].

The znstools "unwritten contracts" analysis [5] empirically validates the written contract itself: zone reset latency, append-vs-write ordering, and write-pointer error behavior match the specification on tested devices, confirming that host stacks can rely on the state machine rather than reverse-engineering firmware quirks.

### 5.2 Analytical Results

Beyond the write-amplification bound of §4.2, two further results structure host GC design:

> **Theorem (Reset Optimality):** For a zone with live fraction *f*, resetting after relocating live data is strictly cheaper (in total bytes moved) than any scheme that relocates at finer granularity, provided relocation cost is linear in bytes moved. The zone is the optimal atomic unit of reclamation.

> **Theorem (Lifetime Segregation Gain):** If a workload's data lifetimes are bimodal with hot fraction *h* and the host segregates hot and cold data into disjoint zone sets, then host-managed GC achieves *WA_hot → 1* on the hot set while the cold set approaches *WA_cold = 1 + ε* with infrequent resets, versus *WA ≈ 1 + f̄/(1 − f̄)* for mixed placement, where *f̄* is the blended live fraction.

These results formalize the intuition behind ZenFS's lifetime hints: segregation converts GC from a continuous tax into an occasional, cheap operation [6].

## 6 Limitations

ZNS is a sharper tool, not a free one:

1. **Open-zone limits.** Controllers support only tens of concurrent open zones. Write fan-out — across LSM levels, WAL streams, and GC destinations — must be budgeted against this cap, or the device serializes opens and throughput collapses [4].
2. **Append latency penalty.** Zone Append costs more per operation than positioned writes at equal size [4]. High-IOPS paths may prefer positioned writes with host-side write-pointer tracking, reintroducing coordination complexity.
3. **Metadata fragility.** The host's zone map and liveness accounting are now on the critical path for *all* data, not just performance. A corrupted zone journal can strand or orphan entire zones; backup and replication of this metadata is mandatory, not optional.
4. **No in-place update.** Any random-write workload (OLTP indexes, small-file metadata) must be log-structured above the zone layer. ZNS punishes stacks that cannot sequentialize.
5. **Ecosystem immaturity.** Kernel zoned-block-device support, I/O schedulers, and filesystems are still catching up: the mq-deadline serialization bottleneck above 200K IOPS and the ongoing LSF/MM work on first-class Append support show the software stack is mid-transition [4].
6. **Variable zone capacity.** Some devices change zone capacity on reset, complicating the LBA↔zone arithmetic the power-of-two zone size was meant to simplify [1].
7. **Wear visibility.** The device still owns wear leveling *within* a zone's erase blocks, but zone-level wear (hot zones reset far more often) is host-visible only through reset counters — the host must implement zone-level wear leveling itself for skewed workloads.

## 7 Conclusion

Zoned Namespace SSDs replace the flash translation layer's hidden garbage collector with an explicit contract: the host writes sequentially within zones, tracks liveness, relocates live data under its own copyback discipline, and resets zones to reclaim them. We have formalized the zone state machine and write-pointer invariant from the NVMe specifications [1], derived write-amplification bounds showing that lifetime-segregated host GC approaches the *WA → 1* optimum, analyzed Zone Append as the concurrency primitive that dissolves the single-writer bottleneck [3], and examined ZenFS as the existence proof that LSM-tree storage engines map cleanly onto zones — eliminating background GC and cutting tail latency by multiples [2][6].

The deeper lesson is architectural. The conventional SSD's "unwritten contract" — the set of workload behaviors that avoid pathological FTL behavior — was reverse-engineered at great cost [5]. ZNS writes the contract down: zone capacities, state transitions, append semantics, and reset obligations are specified, testable, and host-observable. The host pays for this clarity with new responsibilities — placement policy, GC scheduling, crash-consistent zone metadata, and wear management — but these are precisely the responsibilities that determine performance, and they are now programmable rather than inscrutable. As the kernel and filesystem ecosystem completes its transition to first-class zoned I/O [4], the zone is poised to become what the erase block always was: the true atom of flash storage, finally visible to software.
