# io_uring vs epoll for High-Throughput NVMe: Userspace Page Cache Bypass, SQ Polling, and Zero-Copy Storage Stacks in Linux 6.8+

## Abstract
This thesis analyzes the architectural transition from ***readiness-based epoll*** to ***completion-based io_uring*** for high-throughput NVMe storage on Linux 6.8+. We examine why epoll, while optimal for socket readiness multiplexing, fails to scale for sub-10µs NVMe devices due to per-I/O syscall, VFS indirection, and page-cache copy amplification. We dissect io_uring's shared-memory SQ/CQ ring design, *IORING_SETUP_SQPOLL*, *IORING_SETUP_IOPOLL*, fixed files, fixed buffers, and *io_uring_cmd* passthrough for NVMe-native submission. We formalize a zero-copy storage stack that bypasses the page cache via `O_DIRECT`, registered buffers, and DMA remapping, eliminating three copies on the critical path. Empirical models derived from FAST '24 and DBMS 2024 benchmarks show *850K–950K IOPS* per core with io_uring interrupt/SQPOLL versus ~600K with libaio, and *3.3M aggregate IOPS* across 8× PCIe 5.0 drives at 80% of SPDK while retaining POSIX, cgroups, and filesystem visibility. We prove syscall-amortization lemmas and discuss security isolation post Google's 2023 disablement. 152 words.

## 1 Introduction
**NVMe over PCIe 5.0** has exposed a structural mismatch: device latency *<10 µs* and per-device IOPS *2.45M* at 4 KiB now undercut kernel I/O stack overhead. Traditional Linux storage stacks were optimized for *millisecond* HDDs where syscall cost was negligible.

*epoll* arrived in Linux 2.5.44 as a scalable replacement for `select`/`poll`, providing `O(1)` readiness notification for `O(N)` descriptors. Its model is *reactor*: notify when fd is ready, then application invokes `read()`/`write()`. Each operation remains a syscall, each completion requires a second wakeup via interrupt, and regular files are always reported ready — making epoll unusable for asynchronous disk I/O. Databases bolted `libaio` for storage and `epoll` for networking — two disjoint, non-composable paths.

**io_uring**, introduced in 5.1 by Jens Axboe and matured through Linux 6.8+, introduces a *proactor* model: enqueue operation descriptors (SQEs) into memory-mapped Submission Queue (SQ), reap completions (CQEs) from Completion Queue (CQ). Queues are shared between kernel and userspace, coalescing *N* operations into one `io_uring_enter`. With `IORING_SETUP_SQPOLL`, even that syscall disappears: a kernel thread polls SQ shared memory. With `IORING_SETUP_IOPOLL`, the NVMe driver exposes poll queues via `poll_queues` module parameter, eliminating interrupts entirely.

This thesis contributes:

* A formal cost model of epoll vs io_uring submission/completion paths, quantifying syscall, context-switch, refcount, and copy overheads in Linux 6.8+.
* Design of a zero-copy NVMe stack: `O_DIRECT` page-cache bypass, `IORING_REGISTER_BUFFERS`, `IORING_REGISTER_FILES`, and `IORING_OP_URING_CMD` for block-layer bypass.
* Analysis of SQPOLL scheduling policy, idle timeout, and CPU-core reservation tradeoffs versus SPDK pollers.
* Empirical synthesis from arXiv 2512.04859, FAST '24, SNIA SDC '19, and KIT 2024 libuseruring bypass thesis.
* Security and operational analysis of privilege requirements for SQPOLL/IOPOLL under systemd and container cgroups v2.

> **Thesis Statement:** *For high-throughput NVMe arrays in Linux 6.8+, io_uring with SQPOLL + registered buffers + io_uring_cmd passthrough achieves SPDK-class IOPS while preserving kernel filesystem integrity; epoll is architecturally precluded from this regime due to readiness semantics and non-batched syscall topology.*

## 2 Background / Preliminaries

### 2.1 Linux Storage I/O Taxonomy

Linux provides four generations:

1.  **Synchronous `read`/`write`**: thread blocks in `TASK_UNINTERRUPTIBLE`, ~15K IOPS at QD1.
2.  **posix-aio (glibc threadpool)**: userspace threads emulate async, massive context-switch storm (64M ctx switches / 433K IOPS per SNIA).
3.  **libaio (`io_submit`)**: true kernel AIO but restricted to `O_DIRECT`, no buffered I/O, no sockets/pipes, 2 syscalls per batch (submit + getevents).
4.  **io_uring**: unified, supports network and storage, buffered and direct, fixed and dynamic.

*Page cache* is Linux's DRAM cache for file data; for NVMe throughput tests, it masks device characteristics but introduces double copy and coherency `inode->i_rwsem` contention.

### 2.2 epoll Model and Limits

epoll workflow:

```c
int efd = epoll_create1(0);
epoll_ctl(efd, EPOLL_CTL_ADD, fd, &ev);
int n = epoll_wait(efd, events, 128, -1);
for (i=0..n-1) { read(events[i].data.fd, buf, len); }
```

Key costs per I/O: `epoll_wait` wakeup → `read` syscall → `copy_to_user` → completion. For 4K random reads, 320K syscalls/sec at 100K ops/sec baseline. Spectre/Meltdown KPTI adds ~150 cycles per syscall on vulnerable x86_64, doubling indirect cost.

> epoll cannot efficiently signal NVMe completion because NVMe devices complete out-of-order via submission/completion queue pairs invisible to VFS poll semantics.

### 2.3 io_uring Fundamentals

Architecture comprises:

* **SQ ring** — `io_uring_params.sq_entries` power-of-2, `SQE` 64 bytes, user writes tail, kernel reads.
* **CQ ring** — `CQE` 16 bytes `{user_data, res, flags}`.
* **SQPOLL kernel thread** — `io_sq_thread`, configurable CPU affinity `sq_thread_cpu`, idle `sq_thread_idle` ms, `IORING_SQ_NEED_WAKEUP` flag.

Memory barrier protocol uses `acquire/release` semantics on head/tail indices to avoid cache-line ping-pong.

In kernel 6.8, >60 opcodes: `IORING_OP_READ`, `WRITE`, `READV`, `SEND_ZC`, `RECV_ZC`, `URING_CMD`, `FIXED_BUF`, `PROVIDED_BUFFERS`.

#### Registered optimizations:

| Optimization | Flag | Benefit |
|--------------|------|---------|
| Fixed files | `IORING_REGISTER_FILES` | Eliminate `fget/fput` per I/O, 5-10% IOPS |
| Fixed buffers | `IORING_REGISTER_BUFFERS` | Pre-pin user pages for DMA, avoid `gup`, ~11% |
| Huge page SQ/CQ | `IORING_SETUP_CLONE_RING` | Reduce TLB miss |
| IOPOLL | `IORING_SETUP_IOPOLL` | Bypass `irq` and `softirq`, busy-poll NVMe CQ |

## 3 Methodology / Formalism

### Cost Model

Define per-I/O cost `C`:

```
C_epoll = s + w + k_copy + k_vfs + k_poll_wake
C_uring = (t + s)/n_batch + c_fixed + m_barrier + (1-hit)*c_dma_map
C_sqpoll = c_fixed + m_barrier + p_poll_spin
```

where `s` = syscall entry/exit including KPTI/Mitigation, `t` = `io_uring_enter` when batched, `n_batch` = average SQE batch depth, `c_fixed` = registered buffer fastpath, `p_poll_spin` = CPU spin cost of dedicated poller, `w` = wakeup latency.

*Lemma:* As `n_batch → 64`, `C_uring → C_epoll / k` for `k ≈ 2·(s/w)` ignoring copy.

### Formal Assumption Set

* **A1** NVMe driver loaded with `poll_queues >= n_cores` for IOPOLL.
* **A2** Buffers page-aligned 4K and size 512 aligned for `O_DIRECT`.
* **A3** `CAP_SYS_NICE` or `CAP_SYS_ADMIN` available for SQPOLL unprivileged since 5.11 with `IORING_SETUP_SQPOLL | IORING_SETUP_NO_SQARRAY`.
* **A4** IOMMU disabled or in `passthrough` mode, otherwise `max_hw_sectors_kb` truncates large I/O triggering async workers (128 KiB limit).
* **A5** Linux ≥ 6.8 includes `IORING_OP_SEND_ZC` v6.0+, `IORING_OP_URING_CMD` for ublk/NVMe passthrough.

### Measurement Methodology

We synthesize results from:

* **Qdrant 768d vector search**: mmap vs io_uring with `O_DIRECT` + scalar quantization; `iostat` IOPS sampling.
* **KIT libuseruring bypass**: `cat_liburing` with `drop_caches`, 128 KiB–32 MiB range, mean over 100 runs.
* **SNIA SDC 2019 submission/completion latency**: TSC capture before/after submit/complete, Intel Optane 4K QD1.
* **DBMS shuffle benchmark (arXiv 2512.04859)**: tuple-shuffle 100 GiB, 1 MiB chunks, zero-copy send/recv variants.

## 4 Deep Dive

### 4.1 Submission Path Amalgamation: From Syscalls to Shared Memory

epoll requires **2 syscalls per I/O cycle**: `epoll_wait` + `read/write`. io_uring collapses to **0.02 syscalls per I/O** at batch=64 or zero with SQPOLL. The ring-based protocol avoids `fdget`/`fput` when `fixed files` pre-installed via `io_uring_register_files`, shaving ~80 cycles.

In SQPOLL mode, kernel creates `io_sq_thread` which busy-spins checking `sq_ring->tail`. The application sequence guarded by need-wakeup flag:

```c
// liburing SQPOLL wake sequence (simplified)
void submit_sqe(struct io_uring *ring, struct io_uring_sqe *sqe) {
    memcpy(&ring->sq.sqes[tail & mask], sqe, sizeof(*sqe));
    atomic_store_explicit(&ring->sq.tail, tail+1, memory_order_release);
    if (atomic_load_explicit(&ring->sq.flags, memory_order_acquire) & IORING_SQ_NEED_WAKEUP)
        io_uring_enter(ring->ring_fd, 0, 0, IORING_ENTER_SQ_WAKEUP);
}
```

CPU cost is `1 core × 100%` for poller — same as SPDK, but kernel retains scheduling, cgroups, and `smartctl` visibility.

> **Theorem 4.1 (Zero-Syscall Sufficiency):** Under SQPOLL with non-full SQ and non-overflow CQ, steady-state I/O submission and completion can be sustained indefinitely without privileged transition, provided memory ordering respects `smp_load_acquire` / `smp_store_release` on head/tail indices.

*Proof Sketch:* Rings provide single-producer single-consumer lock-free semantics; kernel poller acts as consumer `head`, application as producer `tail`. CQ dual. Since `io_uring_enter` only needed on `NEED_WAKEUP`, quiescent busywait avoids trap.

### 4.2 Userspace Page Cache Bypass and Zero-Copy Stack

Default `buffered I/O` path: `NVMe DMA → page cache (kernel) → copy_to_user → application buffer`. Three copies and `memcpy` bandwidth bottleneck at 90 GiB/s read saturation ( PCIe 5.0 ×16 ≈ 56 GiB/s per device).

Zero-copy stack layers:

1.  **O_DIRECT**: bypass page cache, requires aligned buffers.
2.  **Registered buffers**: `IORING_REGISTER_BUFFERS` pins pages once via `pin_user_pages()`, DMA mapping reused.
3.  **`io_uring_cmd`**: NVMe passthrough bypasses block layer `bio`/`request` allocation entirely, building NVMe command directly (`nvme_uring_cmd_pdu`).

KIT libuseruring implementation measured *3.37× speedup* at 8 MiB reads with premapped pages versus native `io_uring` without cache, and crossover at 1 MiB where bypass wins.

Rust example of fixed-buffer registration:

```rust
use io_uring::{IoUring, opcode, types};

fn zero_copy_read(ring: &mut IoUring, fd: types::Fd, buf_index: u16) -> std::io::Result<()> {
    let sqe = opcode::Read::new(fd, std::ptr::null_mut(), 4096)
        .buf_group(buf_index)
        .build()
        .flags(io_uring::squeue::Flags::FIXED_BUF);
    unsafe { ring.submission().push(&sqe).expect("SQ full"); }
    ring.submit_and_wait(1)?;
    Ok(())
}
```

For network spillover, `IORING_OP_SEND_ZC` and `RECV_ZC` with provided buffer rings removed last copy, yielding 2.5× shuffle speedup in arXiv 2512.04859.

### 4.3 Completion Model: Interrupts vs IOPOLL vs Hybrid

*Interrupt-driven*: NVMe IRQ → softirq → `blk_mq_complete_request` → wake io_uring task.

*IOPOLL*: driver creates dedicated `poll_queues` (module param `nvme_core.poll_queues=N`). `IOPOLL` requires `IORING_SETUP_IOPOLL` and only compatible with `O_DIRECT`. The `io_iopoll_check` polls hardware Completion Queue in kernel thread context, achieving 60% lower submission latency vs libaio (`704 ns vs 1526 ns` SNIA) and 155 ns completion.

*Hybrid IOPOLL*: introduced 6.10 via `IORING_SETUP_HYBRID_IOPOLL` — delays busy polling by `~15 µs` to conserve CPU, then spins. Balance between power and tail latency.

Tradeoff table:

| Mode | Avg Lat QD1 4K | CPU @ 950K IOPS | Need Root | Power |
|------|----------------|----------------|-----------|-------|
| IRQ | ~12 µs | 1.2 core | No | Low |
| IOPOLL | ~6.8 µs | 1 core poll + app | Yes (poll_queues) | High |
| SQPOLL+IOPOLL+Passthru | ~5.2 µs | 2 cores | Yes | Highest |
| SPDK | ~4.5 µs | 1-2 dedicated | Yes + hugepages | Highest |

### 4.4 NVMe Multi-Queue Sharing and NUMA Affinity

Modern Kioxia CM7-R exposes 128 hardware SQ/CQ per device. Linux `blk-mq` maps software queues to cores. `poll_queues` share strategy: if `poll_queues < n_cpu`, round-robin sharing. For 8-drive aggregate 19.6M IOPS theoretical, bottleneck shifts to PCIe fabric and `max_hw_sectors_kb`. Disabling IOMMU raises sector limit from 128 KiB to 1024 KiB, avoiding async worker thread punt described in DBMS paper; such punt occurs when single request exceeds DMA max, spawning `io_wq` worker and fallback to slow path.

NUMA placement critical: allocate SQ/CQ rings on same NUMA node as NVMe RC, pin SQPOLL thread to isolated core via `sq_thread_cpu`, set `isolcpus` and `nohz_full`.

Python orchestration benchmark harness:

```python
import os, subprocess, json, time
from pathlib import Path

def run_fio(engine, iodepth, numjobs, bs='4k', direct=1):
    cmd = f"fio --name=randread --filename=/dev/nvme0n1 --ioengine={engine} \
            --iodepth={iodepth} --numjobs={numjobs} --bs={bs} --direct={direct} --runtime=10 --output-format=json"
    out = subprocess.check_output(cmd, shell=True)
    data = json.loads(out)
    return data['jobs'][0]['read']['iops'], data['jobs'][0]['read']['lat_ns']['mean']

for cfg in [('io_uring',16,2),('io_uring',64,1),('io_uring',128,8)]:
    iops, lat = run_fio(*cfg)
    print(f"{cfg} -> {iops:.0f} IOPS lat {lat/1000:.1f} us")
```

Multi-tenant isolation via cgroups v2 `io.latency` and `io.weight` still functional with io_uring unlike SPDK, which requires full device VFIO pass-through.

## 5 Empirical / Proofs

### 5.1 Single-Device IOPS Envelope

Compiled from FAST '24, SNIA, and DBMS 2024:

| Configuration | IOPS 4K RR | Cycles / IO | Syscall Amplification |
|---------------|------------|-------------|----------------------|
| sync `read()` | 15K QD1 | 240K | 1 |
| libaio | 600K | 3.1K | 2 |
| io_uring IRQ | 850K | 1.8K | 0.04 |
| io_uring SQPOLL | 950K | 1.5K | 0 |
| io_uring_cmd + IOPOLL | 1.3M | 0.9K | 0 |
| SPDK polling | 1.5M | 0.7K | 0 |

*Derivation:* submission sw latency drop 1526 ns → 704 ns → 647 ns → 150 ns shows 60% and additional 8% improvement from fixed buffers, aligning with lemma `C_uring`.

### 5.2 DBMS Network + Storage Shuffle

Figure 13 of arXiv 2512.04859 shows epoll zero-copy vs io_uring zero-copy send/recv: without zero-copy, epoll only marginally slower (chunk 1 MiB amortizes syscall). With zero-copy `SEND_ZC`, io_uring 1.6× epoll at 16 workers; with zero-copy recv, 2.5×. Effective memory bandwidth halved (both directions) as expected when dma-buf eliminates `memcpy`.

### 5.3 Cycle-Based Transaction Throughput

Model from §3.3.1 DBMS: `c_tx=8264` cycles, `c_io=15900` cycles, `r_pf=0.70`. Throughput `f_clk/(c_tx+r_pf·c_io) = 3.7e9/19394 ≈ 190.8k tx/s` measured 183k tx/s. Adaptive batched read submission reduces `c_io` by amortizing `io_uring_enter` across waiting fibers, improving throughput 18% to 216k tx/s.

### 5.4 Large Blocks CPU Cost Per Byte

Figure 8 of same paper: increasing block 4K→128K→256K reduces CPU cycles/byte by 90% as PCIe saturates at 90 GiB/s reads, 50 GiB/s writes. Past 128 KiB with IOMMU enabled, `io_wq` fallback triggers — measured latency spike 30%.

> **Theorem 5.1 (Scalability Condition):** Under block size `b ≥ 128 KiB`, thread count `p ≥ 6` with `+Passthru+IOPOLL`, aggregate bandwidth reaches hardware limit `min(BW_pcie, BW_nand)`. For `b < 16 KiB`, IOPS bound by syscall amortized core cycles, not media.

### 5.5 Qdrant Remote Disk Case

Network-attached NVMe over TCP (Hetzner volume): `io_uring` ~max 4000 IOPS CPU 200% vs mmap 2000 IOPS CPU 93% time 43s→12s (3.6×) due to overlapping rescore compute and I/O without page-fault stalls.

## 6 Limitations

* **Security:** io_uring attack surface spans ~40% of kernel CVEs 2022-2024 via `SQPOLL` and `PROVIDED_BUFFERS`; Google Container-Optimized OS disables io_uring by default (`CONFIG_IO_URING=n`), Kubernetes requires `seccompProfile.allow: io_uring`. Mitigation in 6.6+ restricts unprivileged zero-copy via `IORING_REGISTER_RESTRICTIONS`.

* **CPU reservation:** SQPOLL consumes a full core spin; heterogeneous workloads with <100K IOPS see negative ROI vs IRQ. `sq_thread_idle` tunable 0→500 ms trades wake latency vs power: idle wake adds ~30 µs.

* **Filesystem compatibility:** `IORING_SETUP_IOPOLL` currently only `O_DIRECT` block devices; btrfs/XFS buffered content still requires `io_wq` thread offload for metadata journaling, breaking zero-syscall promise.

* **IOMMU / DMA size:** `max_hw_sectors_kb` 128 KiB with IOMMU on causes fallback; must boot `intel_iommu=off` or `iommu.passthrough=1` or adjust `sysfs /sys/block/nvme0n1/queue/max_hw_sectors_kb`.

* **Latency variance:** IOPOLL reduces mean latency but increases P99.9 jitter under thermal throttling — NVMe CQ poll shares SMT core contention.

* **Tooling:** `strace` misses SQPOLL traffic, `blktrace` required; debug builds need `CONFIG_IO_URING_DEBUG`.

## 7 Conclusion
We established that **epoll is fundamentally mismatched** for NVMe high-throughput due to readiness abstraction, separate storage path, and per-I/O syscall tax amplified by KPTI. **io_uring** converts storage to shared-memory queueing, optional kernel pollers, and zero-copy extensible opcodes.

The design stack in Linux 6.8+ distilled:

1. Use `IORING_SETUP_SQPOLL | IORING_SETUP_IOPOLL` for <10 µs paths; otherwise IRQ with `adaptive batch`.
2. Register files and buffers; pin `HUGEMEM` DMA mappings; use `io_uring_cmd` for NVMe PT.
3. Bypass page cache with `O_DIRECT`, leveraging `posix_memalign`, reclaim via `MADV_DONTNEED` rather than cache eviction.
4. Pin rings to NVMe NUMA node, configure `poll_queues`, isolate SQPOLL thread, disable IOMMU for large blocks.

Empirically, this stack reaches ~80% SPDK IOPS (3.3M vs 4.2M on 8× PCIe 5.0) while preserving `fstrim`, `S.M.A.R.T.`, `cgroup` accounting, and filesystem tools — a pragmatic **kernel-integrated bypass** rather than full bypass. Future work explores `io_uring bundle` (6.10) to cut cycles/byte 3× further, CXL-attached memory tiering with `memmap` zero-copy, and eBPF-guided adaptive polling that adjusts `sq_thread_idle` via BPF program on `cq_overflow`.

In PostMore-scale thesis ingestion where KV file cardinality grows indefinite via `zcard` logs, overlapping embedding generation with storage reclamation using `io_uring` batch reads suggests 14% throughput lift free — meaningful, not revolutionary, but aligned with DB guidance.
