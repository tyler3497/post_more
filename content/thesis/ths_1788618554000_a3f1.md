# GraalVM Native Image and Project Panama: Closed-World Ahead-of-Time Compilation Meets Foreign Memory Access

## Abstract

This thesis examines GraalVM Native Image and Project Panama's Foreign Function & Memory (FFM) API, and the friction and synergy at their intersection. Native Image converts Java bytecode into self-contained machine code under a *closed-world assumption*, using iterative *points-to analysis* to compute the exact reachable set of classes, methods, and fields, and bundling a stripped-down *SubstrateVM* in place of the HotSpot runtime. Panama's FFM API (finalized in JDK 22 as JEP 454) re-opens the door to the outside world: safe, idiomatic Java access to off-heap memory through `MemorySegment` and `Arena`, structured layouts, and direct downcalls via `Linker` and `SymbolLookup`—eliminating the boilerplate that made JNI notoriously brittle. We formalize points-to analysis as an abstract interpretation, compare AOT against JIT compilation across startup latency, peak throughput, footprint, and devirtualization power, and show how Panama's method-handle design composes with Graal's partial evaluation while clashing with the closed-world assumption for upcall stubs and `jextract`-generated bindings. We conclude with the open problems: Vector API SIMD specialization in AOT images, restricted-native-access enforcement (JEP 472), and the experimental status of FFM support in Native Image.

## 1 Introduction

The Java platform has long traded *startup cost* for *steady-state performance*. The HotSpot virtual machine loads classes lazily, profiles method executions at runtime, and lets the just-in-time (JIT) compiler speculate aggressively—devirtualizing call sites, inlining monomorphic dispatches, and eliminating bounds checks—on the basis of observed behavior. This speculative model is extraordinarily powerful for long-running servers, but it exacts a price: warmup time, memory footprint (the JIT compiler and its code cache), and unpredictable first-request latency. Two parallel engineering programs inside OpenJDK and the GraalVM project have attacked this trade-off from opposite ends, and their convergence defines the modern Java native story.

The first program, **GraalVM Native Image**, asks: what if we performed the analysis *once, before deployment*? Rather than speculating at runtime, Native Image assumes a *closed world*—every class, method, and field that can ever execute is visible at build time—and computes the exact reachable subset via *points-to analysis*. Everything reachable is ahead-of-time (AOT) compiled; everything else is discarded. The result is a native binary that starts in milliseconds and carries its own minimal runtime, *SubstrateVM*. The second program, **Project Panama**, asks the dual question: what if the boundary between Java and the native world were not a hand-written, error-prone bridge (JNI) but a first-class, type-safe programming model? The Foreign Function & Memory API gives Java programs deterministic, GC-independent control over off-heap memory and zero-boilerplate downcalls into C libraries, while `jextract` mechanically generates bindings from C headers.

> **Theorem:** Under the closed-world assumption, the points-to analysis computes a *sound over-approximation* of runtime reachability: every method that can execute at runtime is present in the compiled image, though some included methods may never execute. The proof is by induction over the call graph construction, where each invocation instruction resolves its possible targets within the fixed class universe known at build time [1].

This thesis makes three contributions. First, it gives a rigorous treatment of the points-to analysis at the heart of Native Image, its relationship to the closed-world assumption, and the build-time-initialization machinery (`--initialize-at-build-time`) that snapshots a pre-warmed heap into the image. Second, it provides a systematic account of Panama's FFM API—`MemorySegment`, `Arena`, `Linker`, `SymbolLookup`, upcall stubs—and of `jextract`, grounded in the finalized JEP 454 semantics. Third, it analyzes the *interaction*: where Panama's dynamism threatens closed-world soundness (upcalls, `loaderLookup`, restricted native access), where it composes beautifully (method-handle constant folding under partial evaluation), and what the performance data actually show versus JNI. The reader is assumed to be comfortable with program analysis, JIT compilation, and systems-level Java.

## 2 Background

### 2.1 From HotSpot's Open World to SubstrateVM's Closed World

A conventional JVM operates under an *open-world assumption*: classes can be loaded at any time via `Class.forName`, custom class loaders, agents, or reflection, so the set of executable code is unknowable until the program runs. The JIT compiler copes by *speculation*: it compiles hot methods under optimistic assumptions (e.g., "this call site is monomorphic") guarded by deoptimization traps that fall back to the interpreter when assumptions break.

Native Image inverts this design. The `native-image` builder runs a whole-program static analysis starting from entry points (`main`, or `--shared` library entry points) and iteratively discovers reachable code until a fixed point is reached. Because the analysis "needs to see all bytecode," the *closed-world assumption* requires that all classes and bytecodes reachable at runtime be known at build time—no new code may be loaded at runtime [1]. The analysis is a *points-to analysis*: a flow-insensitive, context-sensitive abstract interpretation that tracks, for each allocation site and variable, the set of types whose instances may flow there. Virtual call resolution then becomes precise: if the points-to set at a receiver contains exactly one concrete type, the call is devirtualized at build time.

The output binary embeds **SubstrateVM**, a stripped-down VM containing only the components required to execute the image—thread scheduling, garbage collection (Serial GC by default, with G1 available), and exception handling—without a class loader, bytecode interpreter, or JIT compiler [2]. Build-time initialization extends the model further: classes listed via `--initialize-at-build-time` have their static initializers executed *during image construction*, and the resulting heap objects are snapshotted into the *image heap*, so execution at runtime begins from an already-initialized state [3].

### 2.2 The Native Boundary Problem: JNI

The Java Native Interface (JNI), unchanged in essence since JDK 1.1, is the historical answer to "Java needs to call C." It is also widely regarded as one of the platform's most dangerous APIs: every crossing requires hand-written C glue (`JNIEXPORT`/`JNICALL` functions), manual reference management (`GetStringUTFChars`/`ReleaseStringUTFChars`, local/global refs), per-platform compilation, and offers *no* memory safety—a mistake crashes the JVM with no stack trace. JEP 472 now proposes restricting JNI by default as part of the integrity-by-default initiative, precisely because JNI's unsafety is un-auditable [6].

### 2.3 Project Panama: A Principled Foreign Interface

Project Panama's answer is the **Foreign Function & Memory API**, finalized in JDK 22 via JEP 454 [4]. Its design rests on four pillars:

- **MemorySegment**: a typed, bounds-checked view over a contiguous region of memory, on-heap or off-heap, with spatial and temporal safety enforced by the runtime.
- **Arena**: a deterministic lifetime scope (`Arena.ofConfined()`, `ofShared()`, `ofAuto()`, `global()`) that frees all associated native memory on `close()`, replacing `malloc`/`free` discipline with try-with-resources [7].
- **MemoryLayout / VarHandle**: declarative descriptions of C structs, unions, and sequences, from which the JDK derives correctly-aligned field accessors—no manual offset arithmetic, portable across platforms [8].
- **Linker / SymbolLookup / MethodHandle**: downcalls modeled as ordinary `MethodHandle` invocations (`linker.downcallHandle(address, FunctionDescriptor)`), and upcalls (Java callbacks passed to C) modeled as `linker.upcallStub(handle, descriptor, arena)` [9].

The companion tool **jextract** parses C headers and mechanically generates these bindings in pure Java, scaling the approach from a handful of hand-written descriptors to entire libraries such as OpenSSL or libpng [8].

## 3 Methodology

Our method is threefold. *Analytically*, we reconstruct the Native Image build pipeline and the FFM API semantics from primary sources—the GraalVM reference manuals, the OpenJDK JEPs, and the Panama design documents—and formalize the points-to analysis as an abstract interpretation, stating its soundness theorem and characterizing where configuration files (reflection, JNI, proxy, resource) inject externally-declared reachability edges. *Comparatively*, we construct side-by-side models of AOT vs. JIT compilation and of FFM vs. JNI across the dimensions of call overhead, memory management, build complexity, and failure modes, using published measurements and the architectural properties of method-handle intrinsification. *Empirically*, we report a microbenchmark design for downcall latency and vectorized kernels, distinguishing intrinsic call cost from marshalling cost, and we document the *experimental* status of FFM support inside Native Image (`-H:+ForeignAPISupport`), which constrains what can currently be claimed about the combined stack [5].

We take care to distinguish *finalized* APIs (FFM, JEP 454) from *incubating/preview* ones: the Vector API remains in preview (JEP 508 in recent JDKs; seventh preview in JDK 22 [10]), and FFM-in-Native-Image support is explicitly experimental [5]. Claims about production readiness are calibrated accordingly.

## 4 Deep Dive

### 4.1 Points-To Analysis and the Closed-World Assumption

The Native Image builder's static analysis is a monotone dataflow analysis over the lattice of type sets: for each variable *v* it computes *pts(v)*, the set of runtime types that may flow into *v*. An allocation `new C()` adds *C*; assignments propagate sets; a virtual call `v.m(...)` resolves to the union of `m` implementations over all *C ∈ pts(v)*. The analysis is *flow-insensitive* but *context-sensitive*, precise enough to devirtualize the overwhelmingly monomorphic call sites in real programs yet cheap enough to run over the entire JDK.

The closed-world assumption is what makes this *sound*. In an open world, *pts(v)* could grow at runtime when a new class is loaded, invalidating every devirtualization decision. In the closed world, the class universe is fixed, so the fixed point is final. The price is that every *dynamic* feature of Java must be made statically visible through configuration:

| Dynamic feature | Configuration artifact | Effect on analysis |
|---|---|---|
| Reflection (`Class.forName`, `getMethod`) | `reflect-config.json` | Declares reflective targets reachable |
| JNI (`RegisterNatives`, field access) | `jni-config.json` | Declares native-accessible members |
| Dynamic proxies | `proxy-config.json` | Declares generated proxy interfaces |
| Resources (`getResource`) | `resource-config.json` | Embeds resources in image |
| Serialization | `serialization-config.json` | Registers serializable classes |

The **tracing agent** (`-agentlib:native-image-agent`) automates the production of these files by observing a trial run on a regular JVM and recording every dynamic access, with `config-merge-dir` supporting multi-run coverage accumulation [11]. Frameworks such as Quarkus and Micronaut go further, generating configuration at compile time from their bean metadata.

> **Theorem:** *Configuration completeness implies image correctness.* If every dynamic access performed at runtime is covered by the build-time configuration, the native image behaves identically to the JVM execution. The contrapositive is the practitioner's rule: an undeclared reflective access fails at runtime (typically with `ClassNotFoundException` or `NoSuchMethodException`) rather than degrading gracefully [1].

### 4.2 Ahead-of-Time vs. Just-in-Time: A Systematic Comparison

| Dimension | JIT (HotSpot) | AOT (Native Image) |
|---|---|---|
| Startup latency | 100s of ms – seconds (class loading, interpretation, warmup) | Milliseconds (pre-initialized heap, no interpretation) |
| Peak throughput | Highest: profile-guided speculation, aggressive inlining | Near-JIT for static shapes; cannot speculate on unseen profiles |
| Memory footprint | Large: JIT compiler, code cache, class metadata retained | Small: dead code eliminated, minimal SubstrateVM |
| Devirtualization | Runtime: guarded by deoptimization | Build time: exact, from points-to sets |
| Dynamic features | Full: reflection, agents, class loading | Restricted: require build-time configuration |
| Platform specificity | Bytecode is portable | Binary is OS/architecture-specific |

The comparison is not a verdict but a *workload classification*. Long-running services with stable profiles favor the JIT; short-lived processes (serverless functions, CLIs), memory-constrained containers, and fast-scaling microservices favor Native Image. Notably, GraalVM's AOT compiler shares the Graal JIT's optimization machinery—both are the same compiler—so the performance gap is attributable to the *information available* (profiles vs. closed-world analysis), not to compiler quality [2].

### 4.3 SubstrateVM and Build-Time Initialization

SubstrateVM is frequently misunderstood as "a JVM inside the binary." It is not: there is no interpreter, no class loader, and no JIT. What remains is a *runtime substrate*: thread management, safepoints, exception unwinding tables, and a garbage collector (Serial GC by default, G1 available for larger heaps).

Build-time initialization (`--initialize-at-build-time`) executes static initializers *during image construction*, converting runtime work into build-time work: locale data, charset tables, and framework metadata are computed once and snapshotted into the image heap's data section, which the running process memory-maps directly [3]. The discipline is real—initializers must be deterministic and side-effect-free with respect to the deployment environment—but the dividend is large: published case studies routinely report 50–100× faster startup and 3–5× lower RSS versus JVM execution [2].

### 4.4 The Foreign Function & Memory API: MemorySegment, Arena, Linker, SymbolLookup

The FFM API's central insight is that *native interop is a memory-management problem first and a calling-convention problem second*. JNI conflates the two; Panama separates them.

**Memory access.** A `MemorySegment` is an immutable, bounds-checked handle to a contiguous memory region. Dereference operations go through `MemoryLayout`-derived `VarHandle`s, so struct field access is both type-safe and alignment-correct on every platform—`MemoryLayout.structLayout(JAVA_DOUBLE.withName("x"), JAVA_DOUBLE.withName("y"))` handles padding automatically, a notorious source of JNI bugs [8]. Out-of-bounds and use-after-free accesses raise Java exceptions instead of corrupting memory: *temporal* safety comes from the segment's liveness being tied to its arena.

**Lifetimes.** The `Arena` API offers four lifetime disciplines, and choosing correctly is the API's main design decision [7]:

1. `Arena.ofConfined()` — single-threaded, explicit `close()`; the workhorse for request-scoped native calls.
2. `Arena.ofShared()` — thread-safe, explicit `close()`; required when segments cross threads (e.g., `MemorySegment::elements` parallel streams).
3. `Arena.ofAuto()` — GC-managed lifetime; convenient but sacrifices determinism.
4. `Arena.global()` — immortal; for library handles and process-lifetime data.

**Foreign calls.** A downcall requires three ingredients: the function's address (via `SymbolLookup`, e.g., `linker.defaultLookup().find("strlen")`), its signature as a `FunctionDescriptor`, and a `MethodHandle` from `linker.downcallHandle(address, descriptor)` [9]. Because downcalls *are* method handles, they participate in all of HotSpot's method-handle intrinsification and inlining machinery—this is the architectural reason FFM can approach JNI's raw speed while remaining pure Java. Upcalls invert the direction: `linker.upcallStub(handle, descriptor, arena)` produces a native function pointer that C code can invoke, with the arena bounding the stub's lifetime [9].

**jextract.** For large C APIs, hand-written descriptors do not scale. `jextract` (distributed separately from the JDK, built on the finalized FFM API) parses headers and emits complete Java bindings—`MethodHandle` constants, layouts, and struct accessors—so calling `qsort` with a Java comparator becomes a few lines of ordinary Java [8].

```java
import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;

public class PanamaStrlen {
    public static void main(String[] args) throws Throwable {
        Linker linker = Linker.nativeLinker();
        MemorySegment strlenAddr = linker.defaultLookup()
            .find("strlen").orElseThrow();

        FunctionDescriptor desc = FunctionDescriptor.of(
            ValueLayout.JAVA_LONG,   // size_t return
            ValueLayout.ADDRESS);    // const char* parameter
        MethodHandle strlen = linker.downcallHandle(strlenAddr, desc);

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment cString = arena.allocateFrom("Hello, Panama!");
            long len = (long) strlen.invoke(cString);
            System.out.println(len); // 14
        } // native memory freed deterministically here
    }
}
```

Compare with the JNI equivalent: a `native` method declaration, a `javac -h` generated header, a hand-written C file with `GetStringUTFChars`/`ReleaseStringUTFChars`, and a per-platform build. The FFM version has *zero* native code and *zero* manual memory management.

### 4.5 The Vector API and SIMD in AOT Images

Panama's third pillar, the **Vector API** (JEP 508; preview through at least JDK 22's seventh iteration [10]), exposes data-parallel hardware to Java in a portable way. A `FloatVector` of species `SPECIES_256` maps to one AVX2 register; the JIT compiles vector operations to single SIMD instructions when the hardware supports them, falling back to scalar loops otherwise. Recent GraalVM releases explicitly improved AOT compilation of Vector API idioms—mask operations, masked loads/stores, rearranges, and vector loads/stores to and from memory segments—so SIMD code survives the closed-world translation [12].

The conceptual link to Native Image is *lane-count specialization*: because the target CPU is known at image build time, an AOT compiler can commit to the widest available species without runtime dispatch. The practical caveat is portability—an image compiled for AVX-512 will not run on older hardware—so production builds typically target a baseline (e.g., AVX2) and let cloud fleets standardize on it.

### 4.6 Where the Two Worlds Collide: FFM Inside Native Image

The intersection is where the thesis gets interesting, because Panama's dynamism strains the closed-world assumption in three places:

1. **Upcall stubs are runtime code generation.** `linker.upcallStub` synthesizes a native trampoline at runtime—precisely the kind of "new code" the closed world forbids. Native Image's experimental FFM support (`-H:+ForeignAPISupport` plus `--enable-native-access`) handles this by pre-registering stub shapes discovered during analysis, but coverage is incomplete: as documented, foreign calls in Native Image are supported on x64, with upcalls historically limited to Linux [5].
2. **`SymbolLookup` is dynamic linking.** Looking up `"strlen"` by name at runtime is a stringly-typed dynamic access, the native analog of `Class.forName`. Native Image currently supports `SymbolLookup.loaderLookup()` and requires the accessed libraries to be declared, mirroring the reflection-configuration discipline [5].
3. **Restricted native access (JEP 472).** The integrity-by-default program requires modules performing restricted operations—creating downcall handles, upcall stubs—to be granted `--enable-native-access`. In a native image, this grant must be resolved at build time, folding a *security policy* into the closed world.

Where they compose well is in *partial evaluation*: because FFM downcalls are method handles with constant descriptors, Graal's partial evaluator can inline through the call setup, constant-fold layouts, and eliminate bounds checks it can prove redundant—recovering, at build time, much of what the JIT would have done with profiles.

## 5 Empirical Results

We report a benchmark *design* and the architectural expectations it tests, calibrated against published FFM-vs-JNI experience reports [7][8].

**Experiment 1 — Downcall latency.** A nullary native call invoked in a tight loop, comparing (a) JNI, (b) FFM via `invokeExact`, (c) FFM via `invoke`. Hypothesis: JNI and FFM converge within noise on hot paths—both reduce to a direct call instruction—and published experience supports near-parity, with FFM sometimes *faster* due to the absence of JNI's thread-state transitions [7].

**Experiment 2 — Bulk memory transfer.** 1 MB Java→native→Java copies via (a) JNI critical arrays, (b) `MemorySegment::copy`, (c) Vector API comparison kernels. Hypothesis: FFM matches or beats JNI (no pinning; vectorized copy intrinsic), and the Vector API kernel shows 4–8× over scalar Java on AVX2 hardware.

**Experiment 3 — Binding authoring cost.** Time-to-first-working-call for a 50-function C API: hand-written JNI vs. `jextract`-generated FFM bindings. Qualitative but decisive: reports consistently show *hours-to-minutes* reductions and the elimination of an entire class of memory-safety defects [8].

**Threats to validity.** Microbenchmarks overstate call overhead where native work dominates; FFM-in-Native-Image numbers remain experimental [5]; SIMD results are ISA-sensitive.

## 6 Limitations

1. **FFM in Native Image is experimental.** Support must be explicitly enabled, shared arenas are unsupported, and platform coverage (x64-focused, upcall limitations) lags the JVM implementation [5]. Production deployments combining both should be considered early-adopter territory.
2. **The Vector API is still in preview.** Its API surface may change across JDK releases, which interacts poorly with AOT images that bake in a specific JDK's intrinsics [10][12].
3. **Configuration burden is real.** The tracing agent mitigates but does not eliminate the closed-world tax; applications with heavy dynamic behavior (scripting engines, runtime bytecode generation) remain poor Native Image candidates [1][11].
4. **Restricted native access changes the contract.** JEP 472's direction—JNI and FFM restricted by default—means existing native code will require explicit `--enable-native-access` grants, a migration cost for legacy libraries [6].
5. **AOT SIMD specialization trades portability for speed.** Targeting the widest vector ISA at build time produces binaries that fail on older CPUs; fleet homogeneity becomes a deployment prerequisite.

---

## 7 Conclusion

GraalVM Native Image and Project Panama represent complementary answers to Java's oldest tensions: *when* to pay for compilation, and *how* to talk to the world outside the heap. The closed-world assumption, enforced through points-to analysis and paid for with configuration discipline, buys millisecond startup and minimal footprint by moving whole-program reasoning to build time. The Foreign Function & Memory API, finalized in JEP 454, buys back the native boundary—deterministic arenas instead of `malloc`/`free` roulette, method-handle downcalls instead of C glue, `jextract` instead of hand-maintained headers—without surrendering safety.

Their intersection is genuinely new territory: a Java program that is *both* ahead-of-time compiled to a closed world *and* fluent in native interop, with upcall stubs and symbol lookups as the remaining soundness frontiers. The open problems are well-defined—maturing FFM support in Native Image past experimental status, stabilizing the Vector API so AOT SIMD specialization is a safe default, and completing the integrity-by-default migration. If the last decade of Java was about making the JIT smarter, the next will be about making the *build* smarter. The closed world and the foreign frontier are converging, and the meeting point is a Java that starts instantly, speaks C fluently, and still refuses to corrupt memory.
