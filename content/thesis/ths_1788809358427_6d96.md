# Machine-Checked Verification of Raft Consensus with the Verdi Framework in Coq

## Abstract

The Verdi framework embeds the design, specification, and verification of fault-tolerant distributed systems in the Coq proof assistant, and its verification of the Raft consensus protocol remains the canonical case study of mechanically checked consensus [1][2]. This thesis reconstructs that achievement in depth: Verdi's hierarchy of network semantics, in which packet soups encode reorder, drop, and duplication faults and labeled transitions support liveness arguments; the ghost-variable transformer that layers history-tracking state atop a Raft implementation without perturbing its executable behavior; the lattice of roughly ninety mutually reinforcing invariants that yields election safety, log matching, and ultimately state machine safety; and the refinement tower connecting a linearizable abstract specification to OCaml code extracted from Coq and executed on real networks [2]. We close by examining what the current proof does *not* cover -- liveness under partial synchrony, the extraction trusted base, and Byzantine faults -- and chart directions for closing those gaps.

---

## 1. Introduction

Distributed systems are difficult to implement correctly because they must handle both concurrency and failures: machines may crash at arbitrary points and networks may reorder, drop, or duplicate packets [1]. Their behavior is, moreover, too complex to permit exhaustive testing  Bugs in these systems have led to the loss of critical data and unacceptable service outages.

The Verdi framework answers with a radical thesis: *write the implementation in a proof assistant, verify it against an explicit, executable model of the network, and extract the verified code to a runnable artifact.* Developed by Wilcox, Woos, Panchekha, Tatlock, Wang, Ernst, and Anderson and presented at PLDI 2015 [1], Verdi produced the first mechanically checked proof of linearizability of the Raft state machine replication algorithm, alongside verified implementations of a primary-backup replication system and a key-value store whose measured performance matches unverified equivalents. A follow-up at CPP 2016 [2] delivered the first formal verification of *state machine safety* for Raft -- the property that no two servers ever apply different commands at the same log index -- through the iterative discovery and proof of ninety system invariants, and connected that proof end-to-end to a linearizability guarantee for an implementation extracted to OCaml and run on real networks.

This thesis reconstructs that verification in full technical depth. We examine:

1. **Network semantics**: executable transition systems over *packet soups*, with unlabeled (`Net.v`) and labeled (`LabeledNet.v`) variants supporting safety and liveness reasoning respectively [3].
2. **Ghost state**: a verified transformer that augments each node with history-tracking variables invisible to the extracted program, enabling refinement-style proofs.
3. **The refinement tower**: how Raft's handler functions are shown to simulate an abstract state-machine replication specification.
4. **Extraction to OCaml** and the residual trusted computing base.
5. The frontier of **liveness under partial synchrony**, where machine-checked guarantees remain incomplete.

## 2. Background

### 2.1 The Raft consensus protocol

Raft [5] manages a replicated log across a cluster of servers. It decomposes consensus into three relatively independent subproblems -- *leader election*, *log replication*, and *safety* -- deliberately enforcing a stronger degree of coherency than Paxos so that fewer system states must be considered. Servers occupy one of three roles (leader, follower, candidate); time is divided into *terms* identified by monotonically increasing numbers; and the leader replicates a totally ordered log of commands to followers via `AppendEntries` RPCs, committing an entry once a majority has stored it.

The safety argument of Raft rests on five interlocking properties:

| Property | Informal statement |
|---|---|
| **Election Safety** | At most one leader can be elected in a given term. |
| **Leader Append-Only** | A leader never overwrites or deletes entries in its log. |
| **Log Matching** | If two logs contain an entry with the same index and term, the logs are identical in all preceding entries. |
| **Leader Completeness** | If a log entry is committed in a term, it appears in the logs of the leaders of all higher-numbered terms. |
| **State Machine Safety** | If a server has applied a log entry at a given index to its state machine, no other server will ever apply a different entry at that index. |

State Machine Safety is the crown jewel: it is the property clients actually observe, and it is the property Woos et al. verified in Coq [2].

### 2.2 Coq, extraction, and the formality gap

Model checkers and pencil-and-paper proofs verify *models* of systems; the artifact that runs in production is a different object entirely, and the gap between model and implementation is where real bugs hide. Verdi closes this gap by making the implementation itself a Coq term: the same Gallina functions whose behavior is reasoned about are extracted to OCaml and executed. The price is a trusted computing base comprising the Coq kernel, the extraction mechanism, the OCaml compiler and runtime, and the *shims* -- unverified OCaml code that bridges extracted handlers to sockets, timers, and the operating system [3]. We return to this TCB in Section 6.

### 2.3 Linearizability

The client-visible correctness criterion is *linearizability* [7]: every concurrent execution must appear equivalent to some sequential execution that respects the real-time order of non-overlapping operations. The PLDI 2015 paper presents the first mechanically checked proof that a Raft implementation is linearizable [1]; the CPP 2016 paper then proves state machine safety and composes it with the earlier result for an end-to-end guarantee [2].

### 2.4 Related verification efforts

Several contemporaneous projects attacked verified distributed systems from different angles. **IronFleet** (Hawblitzel et al., SOSP 2015) verifies Dafny implementations of Paxos-based replication and a key-value store using TLA-style state machines and automated SMT reasoning, emphasizing liveness as well as safety.  Verdi's distinguishing commitment remains end-to-end verification of the *running implementation* rather than of an abstract model.

## 3. Methodology

### 3.1 Systems as handler functions

A Verdi system is a collection of total Gallina functions written with the help of `HandlerMonad.v` [3]: a message handler, a timeout handler, and an input handler, each mapping local state and an event to updated state plus a list of outbound packets and client responses. 

```coq
(* Simplified illustration of a Verdi-style receive handler *)
Definition recv_handler (s : raft_state) (src : name) (m : msg)
  : (raft_state * list (name * msg)) :=
  match m with
  | RequestVote t candidate log_info =>
      handle_request_vote s src t candidate log_info
  | AppendEntries t leader prev entries commit =>
      handle_append_entries s src t leader prev entries commit
  | RequestVoteReply t granted =>
      handle_request_vote_reply s src t granted
  | AppendEntriesReply t success match_idx =>
      handle_append_entries_reply s src t success match_idx
  end.
```

### 3.2 The packet-soup network semantics

Execution is defined by a small-step relation over *networks*: a mapping from node names to local states together with a multiset -- the *packet soup* -- of in-flight packets. The step relation in `Net.v` includes packet delivery (to any node, in any order, possibly never), packet sends (adding to the soup), timeouts, client inputs, and, depending on the chosen semantics, crash and reboot events [3]. The framework formalizes several network semantics encoding progressively adversarial fault models, so a developer may verify under an idealized model and then transfer the result to a realistic one [1]. A labeled variant, `LabeledNet.v`, annotates steps with observable labels and underpins liveness reasoning.

The available step kinds can be summarized as follows:

| Step | Effect |
|---|---|
| `deliver` | Remove a packet from the soup; invoke the destination's receive handler. |
| `send` | Handler output packets enter the soup. |
| `timeout` | Invoke a node's timeout handler (election timers, heartbeats). |
| `input` | Inject a client request into a node. |
| `fail` / `reboot` | Crash a node (state lost or persisted per semantics); restart it. |

### 3.3 Verified system transformers

A key methodological insight of Verdi is that generic fault-tolerance mechanisms can be expressed as *verified system transformers*: functions from systems to systems, paired with proofs that safety properties are preserved across the transformation [1][4]. The distribution ships `SeqNum.v` (sequence numbering to defeat reordering and duplication) and `PrimaryBackup.v` (asynchronous primary-backup replication), each with a machine-checked correctness proof. The developer verifies application logic once, under a benign fault model, and the transformer lifts the guarantee to the adversarial model *without additional proof burden*. 

### 3.4 Planning for change: proof engineering at scale

The Raft verification nearly failed -- not for lack of correct ideas, but because of *proof maintenance*: proving one invariant repeatedly forced strengthening and rework of others, and each change to the implementation rippled unpredictably through the proof [2]. The response was a methodology of *planning for change*, adapting classical information-hiding to the proof-assistant setting:

1. **Interfaces via type classes.** Every lemma lives behind a Coq type-class interface stating its *statement* but not its proof (e.g., `OneLeaderPerTermInterface.v`). Consumers depend only on the interface; the proof can be rebuilt independently.
2. **Custom induction principles.** Common invariant-strengthening patterns are factored into bespoke induction principles over reachable traces, so a change to the step relation updates one principle rather than dozens of proofs.
3. **Higher-order transfer lemmas.** Lemmas are proved showing that any property established about one component implies analogous properties about related components.
4. **Structural tactics.** Proof scripts are written against the *structure* of goals rather than their incidental shape, making them robust to small changes in definitions.

A concrete payoff, reported in [2]: after completing the linearizability proof, the authors fixed a *performance* bug (the leader replied to clients only after updating metadata on the next event, adding latency) by reordering two handler calls -- and the proof survived with only local repairs, precisely because interfaces contained the blast radius.

## 4. Deep Dive

### 4.1 Network semantics as executable transition systems

The unlabeled semantics defines reachability inductively: a network is reachable if it is initial or the result of a step from a reachable network. Safety properties are then *invariants* -- predicates over networks preserved by every step. This yields the characteristic Verdi proof shape:

```coq
(* Proof skeleton shared by every Raft safety invariant *)
Theorem raft_invariant_holds : forall net,
  reachable net -> raft_invariant net.
Proof.
  intros net H_reach.
  induction H_reach using reachable_ind_custom.
  - (* base case: initial network *) admit.
  - (* inductive step: each step kind preserves the invariant *) admit.
Qed.
```

where `reachable_ind_custom` is the custom induction principle of Section 3.4. Each step case discharges by symbolic execution of the corresponding handler -- the handlers are pure functions, so simplification and rewriting suffice for the computational content, leaving only the logical content (quorum intersections, term monotonicity) to the human prover.

### 4.2 Ghost state and the refinement interface

Many invariants needed for Raft's proof refer to *history*: which nodes voted in which terms, which nodes have ever been leaders, what messages were *sent* (as opposed to merely in flight). Such facts are absent from the runtime state -- a Raft node does not remember every vote it ever cast. Verdi's answer is the **ghost-variable transformer**, applied to Raft in `RaftRefinementInterface.v` [3]: each node is augmented with ghost variables updated alongside the real state by instrumented handlers, and a once-and-for-all refinement proof shows the ghost-augmented system *simulates* the original -- the ghost state is invisible to extracted code and cannot affect observable behavior.

Ghost state is what makes the *interface decomposition* possible. Rather than one monolithic invariant over the full network, the proof is factored into per-concern interfaces (`CandidatesVoteForSelvesInterface.v`, `VotesCorrectInterface.v`, `CroniesCorrectInterface.v`, and others), each tracking only the ghost history its property needs. ### 4.3 The invariant lattice: from election safety to log matching

The Raft safety proof is organized as a lattice of interfaces, each stated in `raft/` and discharged in `raft-proofs/`, with lower layers supporting upper ones [3]:

- **Election safety** (`OneLeaderPerTermInterface.v`, proved by `OneLeaderPerTermProof.v`) rests on three supporting interfaces: candidates vote for themselves, votes are *correct* (a node votes at most once per term, and only for candidates whose logs are at least as up-to-date), and *cronies* (followers that granted a vote) behave consistently.
- **Log matching** (`LogMatchingInterface.v`, proved by `LogMatchingProof.v`) rests on leader-sublog inclusion, sortedness of log indices, and uniqueness of indices within a term's entries.
- **State machine safety** composes election safety, log matching, and leader completeness: committed entries are present on every future leader, hence applied identically everywhere.

> **Theorem:** *Election safety (OneLeaderPerTerm).* For every reachable network `nw` and every term `t`, there is at most one node that is leader of term `t` in `nw`. *Proof sketch.* By induction over reachable traces using the custom induction principle. The critical step case is vote granting: `VotesCorrect` ensures a node votes at most once per term, so two distinct leaders in term `t` would require two majorities of votes in `t`, contradicting quorum intersection. Ghost variables record the vote history that makes this argument go through.

> **Theorem:** *State machine safety.* If servers `s1` and `s2` have applied log entries at index `i`, those entries are identical. *Proof sketch.* An applied entry is committed; by Leader Completeness every subsequent leader's log contains it; by Log Matching any two logs agreeing at `(i, term)` agree on all earlier entries; hence no server can apply a conflicting entry at `i`. The full machine-checked proof composes the ninety invariants of [2].

### 4.4 State-machine replication abstraction and linearizability

Safety of the log is necessary but not sufficient: clients interact with a *service*, not a log. The refinement tower therefore continues upward from Raft's handlers to an abstract state-machine replication specification whose observable behavior is a totally ordered sequence of applied commands, and then to a linearizability argument showing client-observable traces coincide with those of an atomic object [1]. Concretely, the extracted system links the Coq handlers against an OCaml shim:

```ocaml
(* Simplified extraction shim: the unverified bridge to the real network *)
let rec event_loop (state : Verdi_raft.coq_State) : unit =
  let ev = Shim.recv_or_timeout () in          (* socket read or timer fire *)
  let (state', outputs) = Verdi_raft.handle ev state in
  List.iter Shim.send_packet outputs;          (* UDP send *)
  List.iter Shim.reply_client outputs;         (* client responses *)
  event_loop state'
```

The PLDI 2015 evaluation reports that the resulting key-value store and primary-backup systems perform comparably to unverified equivalents [1]: verification need not cost performance, because the extracted code is the natural functional program, not a proof-laden one.

### 4.5 Liveness reasoning under partial synchrony

Safety says nothing bad happens; liveness says something good eventually does. Consensus liveness is impossible in fully asynchronous systems with one faulty process (the FLP result), so any liveness claim must assume *partial synchrony* -- roughly, that the network eventually behaves synchronously for long enough. Verdi anticipates this with its **labeled** network semantics (`LabeledNet.v`), in which steps carry observable labels and liveness properties are stated as temporal claims over labeled traces; the distribution demonstrates the technique on a lock server with a machine-checked liveness proof (`LiveLockServ.v`) [3].

For Raft specifically, machine-checked liveness remains open, and the reasons are instructive:

1. **Fairness and timers.** Raft's progress depends on randomized election timeouts and eventual timely delivery -- probabilistic and real-time assumptions that Coq's logic expresses only awkwardly.
2. **Partial synchrony modeling.** The labeled semantics can express *eventual* delivery, but the standard Raft liveness argument needs the stronger, time-bounded guarantees of the Dwork-Lynch-Stockmeyer model.
3. **Proof automation gap.** Safety invariants are inductive and discharge by symbolic execution; liveness needs well-founded ranking arguments over infinite traces, for which Verdi's tactic support is thinner.

## 5. Empirical Results and Formal Analysis

The headline numbers from the two papers are worth stating plainly:

| Result | Source |
|---|---|
| First mechanically checked proof of linearizability of Raft | [1] |
| First formal verification of state machine safety for Raft | [2] |
| System invariants discovered and proved | ~90 [2] |
| Network fault models formalized | 5 [1] |
| Verified system transformers shipped | 2 (SeqNum, PrimaryBackup) [1][3] |
| Extraction target | OCaml; runs on real networks [2] |
| Performance vs. unverified equivalents | Comparable [1] |
| Current Coq compatibility | Coq 8.14+, via opam coq-verdi [3] |

Three analytical observations deserve emphasis.

**First, proof effort concentrates in invariant discovery, not invariant proof.** The ninety invariants were found iteratively: attempt the top-level proof, watch it fail to be inductive, diagnose the missing hypothesis, add it (often with a new ghost variable), repeat. The *planning for change* methodology [2] does not reduce the number of invariants; it reduces the *cost of each iteration* by localizing rework behind interfaces.

**Third, extraction preserves the performance profile.** Because handlers are ordinary functional programs and ghost state is erased, the extracted OCaml is essentially what a competent functional programmer would have written. The evaluation in [1] finds no meaningful performance penalty versus unverified equivalents -- evidence against the folk belief that verification implies bloated or slow code.

## 6. Limitations and Open Problems

1. **The trusted computing base.** Machine-checked does not mean assumption-free. The guarantee rests on: the Coq kernel; Coq's extraction to OCaml; the OCaml compiler and runtime; the unverified network shims; and, most subtly, the *network semantics themselves* -- if the formal fault model omits a real-world failure mode (e.g., correlated clock skew, partial partitions with asymmetric loss), the proof is vacuous for that mode. The semantics are the specification of the adversary, and they are trusted, not proved.
2. **Safety only, for Raft.** As analyzed in Section 4.5, liveness under partial synchrony is not machine-checked for Raft. The labeled semantics and `LiveLockServ` show the path, but the gap between a lock server and a full consensus protocol is large.
3. **Crash faults, not Byzantine faults.** All Verdi semantics assume nodes fail by crashing, never by acting maliciously. Extending the packet-soup model and the transformer architecture to Byzantine behavior is unexplored.
4. **Proof maintenance is mitigated, not solved.** Planning for change [2] contains rework, but the Raft proof remains a large, expert-maintained artifact
5. **No timing model.** Timeouts are modeled as nondeterministic events, which is sound for safety but useless for reasoning about election latency, commit latency, or any quantitative performance property.
6. **Composition boundaries.** Verdi verifies single protocols vertically; composing *multiple* verified protocols (Raft plus a membership-change protocol plus a client library) into one machine-checked system is the domain of Disel-style horizontal reasoning [4], and the integration of the two remains future work.

---

## 7. Conclusion

The Verdi verification of Raft stands as a landmark: the first mechanically checked proofs of linearizability and state machine safety for a consensus protocol that actually runs, achieved not by heroic one-off effort alone but by a *framework* -- network semantics, ghost variables, verified transformers, and a proof-engineering methodology -- designed to make such verifications repeatable. Its enduring lessons are threefold. First, *make the network semantics explicit and executable*: the packet soup turns the adversary into a mathematical object the proof assistant can reason about. Second, *separate history from state*: ghost variables let invariants speak about the past without polluting the extracted program. Third, *plan for change*: interfaces, custom induction, and structural tactics convert a brittle proof script into a maintainable artifact.

Until then, Verdi's Raft remains the clearest demonstration we have that machine-checked consensus is not only possible but practical -- with performance to match.
