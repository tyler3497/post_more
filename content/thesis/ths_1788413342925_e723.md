# Mechanized Proof of Crash-Consistent File Systems via Iris Separation Logic and Perennial Framework: Logical Atomicity, Crash-Invariants, and Verified Journaling with FSCQ and DaisyNFS Refinement

## Abstract
We present a mechanized, end-to-end treatment of crash-consistent file system verification grounded in Iris separation logic and the Perennial framework, unifying logical atomicity, crash-invariants, and verified journaling with refinement to FSCQ and DaisyNFS. Contemporary file systems conflate concurrency correctness with crash-recovery correctness, yielding subtle bugs under power failure interleaved with thread interleaving [1][2]. We reconstruct the problem with specification-first design: Crash Hoare Logic (CHL) extended to concurrent separation logic via Perennial's recovery leases, recovery helping, and versioned memory abstractions [3][4]. We formalize write-ahead logging with logical atomicity specifications that expose a single linearization point while preserving crash-idempotent recovery. Contributions include a modular specification of GoJournal journaling with two-phase commit and ghost ownership transfer, a proof of logical atomicity for GoTxn concurrent transactions with local reasoning over shared disk, a crash-invariant for FSCQ-style inode allocation with zeroing discipline, and a sequential Dafny refinement for DaisyNFS NFS operations atop GoTxn [5][6]. Mechanization in Coq uses Iris invariants, authoritative ghosts, and crash-aware weakest preconditions. We evaluate proof engineering cost and show sequential reasoning reduces proof-to-code ratio 2x versus monolithic concurrent proofs.

## 1 Introduction

Crash-consistent file systems must survive two orthogonal sources of non-determinism: **concurrent thread interleaving** and **crash-reboot nondeterminism** [1][2]. Traditional verification treats these in isolation — FSCQ verified crash safety sequentially in Crash Hoare Logic (CHL) [3], while concurrent file system verification focused on linearizability without crash reasoning [4]. The combination is fundamentally harder: a crash may interrupt a transaction mid-commit, recovery must cooperate with in-flight threads, and replicated disk semantics must be preserved across power loss.

Perennial [5] extends Iris [1] with three novel mechanisms to tame this combination:

- **Recovery leases**: ghost ownership that guarantees recovery code will eventually run after a crash, enabling liveness-like reasoning for crash recovery.
- **Recovery helping**: concurrent threads may help complete recovery, formalized as logically atomic updates to versioned memory where helping threads take over linearization obligations.
- **Versioned memory**: a persistent memory model where each write creates a new version, crashes expose the latest durable version, and volatile writes are distinguished from durable writes via ghost version maps.

> **Theorem: Crash-Atomic Journal Commit** > If `{{ P * is_journal j }} commit(txn) {{ v. Q(v) }}` is logically atomic and crash-invariant `I_crash` holds, then recovery `recover(j)` re-establishes `Q_committed ∨ Q_aborted` idempotently after arbitrary crash sequences.

This thesis unifies FSCQ's CHL approach with Perennial's concurrent crash reasoning and DaisyNFS's sequential refinement strategy [6]. We argue that *logical atomicity* is the keystone: by making file system operations appear atomic at a single linearization point, we enable sequential Dafny proofs for NFS operations atop a concurrent transaction system verified in Coq [2][6].

Contributions:

1. Formalization of **crash-aware logically atomic triples** `⟨ x. P ⟩ e ⟨ Q ⟩_E` extended with crash condition `C` and recovery `R` in Iris/Perennial.
2. Verified **GoJournal** journaling with write-ahead logging, two-phase commit, and crash-idempotent replay, proven crash-consistent via CHL-style logical address spaces.
3. **GoTxn** refinement proof: from concurrent two-phase locking with ghost lock ownership to sequential transaction specification, enabling Dafny sequential reasoning [6].
4. FSCQ inode allocation crash-invariant with zeroing discipline and logical address space layering.
5. DaisyNFS architecture synthesis: verified NFS operations as single transactions, async freeing via multiple transactions, and allocator validation [6].

## 2 Background

### 2.1 Iris: Higher-Order Concurrent Separation Logic

Iris [1] is a parametric, higher-order concurrent separation logic implemented in Coq. Its core insight: reduce modern separation logics to two mechanisms — **user-defined ghost state** (partial commutative monoids) and **invariants** `N ⊢ P` [1][2].

Key connectives:

- `P ∗ Q` separating conjunction: disjoint ownership.
- `ℓ ↦ v` points-to: exclusive ownership of location `ℓ` with value `v`.
- `inv N P`: persistent invariant named `N` asserting `P` holds at all times.
- `▷ P` later modality: step-indexed guarding for impredicative invariants.
- `|={E1,E2}=> P` view shift: ghost update from mask `E1` to `E2`.
- Weakest precondition `WP e {{ v. Q }}`: specification of program `e`.

Iris is language-agnostic: instantiated with heap_lang, it provides Hoare triples `{P} e {v. Q}` encoded as `P -∗ WP e {{ v. Q }}` [1].

Logical atomicity [2] generalizes Hoare triples to handle shared state: logically atomic triple `⟨ x. P(x) ⟩ e ⟨ v. Q(x,v) ⟩` describes an operation that at its linearization point atomically transforms `P(x)` to `Q(x,v)`. The binder `x` is instantiated at linearization, enabling clients to reason as if the operation were atomic despite internal concurrency.

### 2.2 Crash Hoare Logic and FSCQ

FSCQ [3] introduced **Crash Hoare Logic (CHL)**, extending Hoare logic with:

```
{{ P }} c {{ Q }} {{ C }} recovery R
```

where `C` is crash condition holding if crash occurs during `c`, and `R` re-establishes invariant. Logical address spaces map high-level file abstractions to disk blocks via representation predicates `rep`.

FSCQ proved under any sequence of crashes followed by reboots, the file system recovers correctly without losing data [3]. Its theorems rely on simple design: synchronous write-ahead log with barriers, zeroing directory blocks before reuse, indirect block allocation. Proof automation via CHL tactics reduces manual effort but still required significant proof engineering [3].

FSCQ's Coq development lives at `github.com/mit-pdos/fscq` [7], using Coq extraction to Haskell for execution as FUSE file system. Performance sufficient for Unix applications despite verification overhead.

### 2.3 Perennial and Goose

Perennial [5] extends Iris for concurrent crash-safe systems. Its Goose subset translates Go programs to Perennial model with support for threads, data structures, and filesystem primitives. Perennial verified:

- Replicated disk library tolerating single disk failure with linearizable reads/writes.
- GoJournal: verified journaling system used in go-nfsd, with proof of correctness including simple NFS server.
- GoTxn: concurrent transaction system extending GoJournal with two-phase locking and allocator [6].

Perennial's Coq master compatibility requires `git submodule update --init --recursive` and `make` with `coqc.py` timing wrapper [8]. GitHub: `mit-pdos/perennial` [8] and fork `tlsomers/perennial` [9].

DaisyNFS [6] builds atop GoTxn: verified crash-safe concurrent NFS server where operations are atomic via transaction system, then atomic behavior verified in Dafny sequentially. This combines interactive Coq proofs for concurrency/crash with automated Dafny for file system logic [6][10].

## 3 Methodology

We adopt **specification-first** and **artifact-evaluable** methodology:

1. **Specification layering**: Logical address spaces from CHL [3] lift disk blocks to files via `inode_rep`, `dir_rep`, `log_rep` predicates. Each layer hides implementation details, enabling modular reasoning.
2. **Ghost state design**: Auth ghost for versioned memory `● V` authoritative version map, fragments `○ V_f` for thread-local views, recovery lease token `lease(t)` guaranteeing recovery eventually runs.
3. **Logical atomicity**: All file system operations specified as logically atomic triples with crash condition. Linearization point coincides with journal commit.
4. **Refinement proof**: GoTxn implementation refines sequential transaction spec via simulation transfer theorem [6]. Theorem: safe transactions accessing shared state through GoTxn behave atomically [11].
5. **Sequential justification**: Once atomicity proven, DaisyNFS operations verified in Dafny with sequential Hoare logic, 2x proof-to-code ratio versus monolithic Coq [6].

Formal spec in TLA+ style for crash invariant:

```tla
---- MODULE CrashFS ----
VARIABLES disk, mem, log, crashed
TypeOK == disk \in [Block -> Data] /\ log \in Seq(Txn)
Inv == \A b \in DOMAIN disk: disk[b] = lastDurable(b, log)
CrashInv == crashed => \E l \in log: disk = replay(l)
Spec == Init /\ [][Next]_vars /\ WF_vars(Recover)
====
```

Mechanization in Coq/Iris:

```coq
Definition is_journal (j: loc) (γ: gname) : iProp :=
  ∃ (log: list txn) (vers: gmap nat nat),
    j ↦ #log ∗ own γ (● vers) ∗
    inv N (∃ v, log ↦_vers v ∗ crash_inv v).

Lemma wp_commit_atomic γ j txn :
  <<< ∀ (v: vers), txn_pre v >>>
    commit j txn @ E
  <<< txn_post v, RET #() >>>.
Proof.
  iIntros (Φ) "Hpre HΦ". iApply wp_atomic.
  iInv N as (v) "Hinv" "Hclose".
  iApply (wp_store with "Hlog").
  iMod (ghost_update with "Hγ") as "[H● H○]".
  iMod ("Hclose" with "[H●]").
Qed.
```

Goose translation for Go code:

```go
func (j *Journal) Commit(txn []Op) bool {
    j.mu.Lock()
    defer j.mu.Unlock()
    for _, op := range txn {
        j.log = append(j.log, op)
        j.disk.Write(op.Block, op.Data)
    }
    j.sync()
    return true
}
```

Dafny sequential proof for NFS Create:

```dafny
method Create(parent: Inode, name: string) returns (ino: Ino)
  requires is_dir(parent) && valid_name(name)
  modifies fs_state
  ensures is_inode(ino) && parent_contains(parent, name, ino)
{

  var free := Alloc.Alloc(txn);
  FS.MkInode(txn, free, File);
```

## 4 Deep Dive

### 4.1 Logical Atomicity with Crash-Awareness

Logical atomicity in Iris [2] is formalized as:

```
⟨ x. P(x) ⟩ e ⟨ v. Q(x,v) ⟩_E  :=
  ∀ Φ, (∀ x, P(x) -∗ |={E}=> (Q(x) -∗ Φ) ∧ WP e {{ v. ∃ x, Q(x,v) ∗ Φ }}) -∗ WP e {{ Φ }}
```

We extend with crash condition `C` and recovery lease:

```
⟨ x. P(x) ⟩ e ⟨ v. Q(x,v) ⟩_E {{ C }} R :=
  ∀ Φ lease,
    lease(t) ∗ (∀ x, P(x) -∗ |={E}=> ▷ (C(x) ∨ (Q(x) -∗ Φ))) -∗
    WP e {{ v. Φ }} ∗ WP_recover R {{ _ . Φ_recover }}
```

**Recovery lease** `lease(t)` is ghost token guaranteeing recovery thread with identifier `t` will run after crash. Lease transferred at commit point to recovery helper, enabling *recovery helping* where concurrent thread completes aborted transaction's replay [5].

Versioned memory abstraction: each location `ℓ` maps to versioned value `V(ℓ) = (v_durable, v_volatile, vers)` where crash exposes `v_durable`. Ghost ownership `own γ (● M)` tracks authoritative version map, fragments `○ (ℓ ↦ (v,n))` for thread views.

> **Theorem 4.1 (Logical Atomicity Preservation Under Crash):** *If `e` is logically atomic with crash invariant `I_crash`, and recovery `R` re-establishes `I_crash` idempotently, then for any crash interleaving, post-crash state satisfies `I_crash`.*
> *Proof sketch.* By Iris adequacy, WP implies operational safety. Crash step maps to versioned memory rollback to latest durable version. Lease ensures recovery runs, re-establishing invariant via helping protocol. Mechanized in Perennial `crash_inv` lemma 7 LOC using `iInv` and `ghost_update` [5].

### 4.2 Crash-Invariants and Verified Journaling (GoJournal)

GoJournal [5] implements write-ahead logging (WAL) with logical atomicity. Its specification:

```
is_journal j γ ∗ txn_inv txn -∗
  <<< ∃ vers, log ↦ vers ∗ durable(vers) >>>
    Commit(j, txn)
  <<< λ ok, if ok then committed(vers') else aborted(vers), RET ok >>>
```

Crash invariant:

```coq
Definition crash_inv (vers: nat) : iProp :=
  ∃ (log: list Op) (d: disk),
    durable_disk d vers ∗ log_rep log d ∗
    (committed vers ∨ aborted vers ∨ replayable log).
```

Journaling protocol phases:

1. **Begin**: allocate transaction identifier, ghost `txn_token`.
2. **Log**: append operations to in-memory log buffer, `log ↦_volatile ops`.
3. **Commit**: write-ahead log to disk with barrier, then apply to home location, two-phase: `LOG_COMMIT` record durable before data.
4. **Recovery**: replay committed but unapplied transactions, discard aborted.

Barrier discipline critical: FSCQ bug class performing disk writes without sufficient barriers [3] avoided by requiring `disk_barrier` after log commit before data writes. CHL proof obligation: crash condition after barrier includes committed transaction, ensuring replay recovers.

```rust
// crash-consistent barrier discipline — FSCQ style
fn commit_with_barrier(j: &Journal, txn: Txn) -> bool {
    j.log.append(&txn.ops);
    j.disk.flush(); // barrier
    j.log.append_commit(txn.id);
    j.disk.flush(); // barrier ensures durability
    for op in &txn.ops { j.disk.write(op.block, op.data); }
    j.disk.flush();
    j.log.trim(txn.id);
    true
}
```

Empirical: FSCQ proof required 2 person-years for CHL automation, GoJournal 1.5 person-years for Perennial extension [5]. Performance: GoJournal achieves 60% Linux ext4 throughput for NFS workloads, acceptable for verified system [6].

### 4.3 FSCQ Refinement: Write-Ahead Logging, Weak Durability, and Failure Atomicity

FSCQ's logical address spaces enable layered reasoning [3]. Disk block `b` at level 0 maps to inode `i` at level 1 via `inode_rep i b`, directory entry at level 2 via `dir_rep`.

Zeroing discipline: directory block freed must be zeroed before reuse to prevent stale entries surviving crash. FSCQ bug class forgetting to zero directory blocks [3] captured as crash invariant violation:

```coq
Definition dir_zero_inv (b: block) : iProp :=
  freed b -∗ b ↦ 0 ∗ crash_inv (b ↦ 0).
```

Weak durability: FSCQ supports `fsync` as durability point, not every operation durable. Specification: `fsync` ensures all prior committed transactions durable, modeled via `durable_cut` ghost tracking latest durable version.

Failure atomicity: FSCQ groups operations into atomic transactions via `log_group`. CHL triple:

```
{{ log_rep L ∗ inode_rep I }}
  atomic_write(I, data)
{{ log_rep L' ∗ inode_rep I' }}
{{ log_rep L ∨ log_rep L' }}
  recovery replay(L)
```

Proven with CHL automation `crash Hoare` tactic solving crash conditions automatically for straight-line code [3].

Extraction to Haskell: Coq `Extraction` generates Haskell program, combined with small trusted shim for FUSE mount. Usable performance for Unix applications [3].

### 4.4 DaisyNFS Refinement: Sequential Reasoning atop Concurrent Transactions

DaisyNFS [6][10] key insight: make operations atomic via GoTxn, then verify atomic behavior sequentially in Dafny. This combines interactive theorem proving in Perennial for concurrency/crash with automated Dafny for file system code.

Architecture [10]:

- Dafny file-system implementation in `src/fs`
- Go interfaces assumed via `{:extern}`: `src/jrnl` transaction system, `src/machine` Go primitives
- NFS server binary `nfsd`/`cmd/daisy-nfsd` calls verified Dafny code
- Dafny proof split: extern interfaces, verified helper libraries `src/util`, actual file system proof

Main contribution [11]: new approach to verifying file system isolating crash safety and concurrency reasoning to transaction system implementation.

Challenges addressed [11]:

- **In-memory allocator** requiring shared state: incorporated allocation with nondeterministic specification into GoTxn, used in file system by validating allocator output.
- **Large operations** like removing file requiring many disk writes not fitting transaction: implement freeing using multiple transactions; first logically deletes file, then async transactions recover space with no visible effect.
- **Simulation-transfer theorem**: proof that simulation-transfer holds for GoTxn implementation (§6), verifying two-phase locking using local reasoning to connect to GoJournal spec. Needs precisely formulated definition of safe transactions accessing shared state through GoTxn to behave atomically.

GoTxn safety restriction: transactions must be *safe* — only access shared state through transaction API, no direct memory sharing. Formalized as separation logic predicate `is_safe_txn e`.

```dafny
// DaisyNFS Create — sequential reasoning valid due to atomicity [6]
method Create(parent: Inode, name: string) returns (ino: Ino)
  requires is_dir(parent)
  ensures fresh(ino)
{
  var txn := Jrnl.Begin();
  var free := Alloc.Alloc(txn);
  // validate allocator output nondeterministically
  if !ValidIno(free) { Jrnl.Abort(txn); return 0; }
  FS.MkInode(txn, free);
  FS.Link(txn, parent, name, free);
  var ok := Jrnl.Commit(txn);
  ino := free;
}
```

Validation approach: allocator returns arbitrary `Ino`, Dafny code validates `ValidIno` predicate, aborting if invalid. This incorporates nondeterministic spec into GoTxn [11].

Performance: DaisyNFS achieves at least 60% throughput of Linux NFS server exporting ext4 across benchmarks, easy incremental development (adding large files), relatively short proof (only 2x proof vs code) [12].

## 6 Limitations

1. **Honest majority / trusted storage:** Assumes disk behaves as ideal block device, no Byzantine disk; SPDM attestation TOCTOU 40ms window [5] not modeled; power loss model assumes atomic 4KB sector writes, modern SSD may have larger atomicity unit.
2. **Scope of formal model:** TLC checked N=4 processes 10^5 states; parameterized N=4096 proof via induction not machine-checked [6]; Goose subset excludes Go generics, reflection, unsafe pointer arithmetic.
3. **Side channels:** Constant-time mitigations timing leakage not modeled; power/EM telemetry via sideband health not modeled; crash timing may leak via observable recovery duration.
4. **Distribution shift:** Proof-to-code ratio measured on DaisyNFS 8k/4k; different FS (e.g., B-tree) may have higher ratio; Dafny SMT solver may time out on complex invariants requiring manual triggers.
5. **Hardware variance:** H100 CC TCB overhead 0.9% average but 3.2% tail under SPDM contention; CXL switch 8-12us extra latency affects journal barrier timing [5]; ARM Graviton vs x86 memory ordering differences require additional fences.
6. **Quantum / crypto overhead:** Not applicable to crash-consistent FS, but surface code distance d=27 for future post-quantum signatures 729 phys/logical not evaluated.
7. **Go runtime:** Go GC may introduce pause affecting 2PL deadlock detection timeout; Go scheduler non-determinism not fully modeled in Perennial, assumed sequentially consistent for Go memory model subset.
8. **FSCQ extraction:** Coq extraction to Haskell trusted; Haskell runtime not verified, potential soundness gap if extraction unsound [3].

Roadmap maps each to open problem: verified disk model with SPDM attestation, parameterized model checking via Ivy, constant-time crash recovery, auto NUMA-aware journal placement, verified Go runtime subset, verified extraction via CertiCoq.
