The RISC-V Vector extension (RVV 1.0, ratified December 2021) replaces fixed-width SIMD with vector-length agnostic computing: software discovers the hardware vector length at run time via the vsetvli instruction, and a single binary runs correctly on any conforming VLEN. This thesis gives a comprehensive account of RVV 1.0: the vsetvli configuration model and its selection law, LMUL register grouping that trades register count against effective vector length, masked predication through the v0 mask register with tail-agnostic and mask-agnostic execution policies, the riscv_vector.h C intrinsic interface, and compiler auto-vectorization in GCC and LLVM across vector-length-specific and vector-length-agnostic code-generation modes. We prove the strip-mining coverage invariant that guarantees every application element is processed exactly once on any implementation, and we synthesize published empirical results — 151 TSVC loops and real applications on RVV silicon, LLVM tail-folding advances, and differential fuzzing of intrinsic compilers — to map where auto-vectorization succeeds and where hand-tuned intrinsics remain essential.

# Vector-Length Agnostic Computing: The RISC-V Vector Extension (RVV 1.0) — VSETVLI Configuration, LMUL Register Grouping, Masked and Tail-Agnostic Execution, Vector Intrinsics, and Compiler Auto-Vectorization

## Abstract

The RISC-V Vector extension ("V", RVV 1.0) rethinks data-level parallelism for an era of heterogeneous silicon. This thesis presents a comprehensive treatment of RVV 1.0: its vector-length agnostic (VLA) programming model, the `vsetvli` configuration mechanism, LMUL register grouping, masked predication with tail- and mask-agnostic policies, the C vector intrinsic interface, and compiler auto-vectorization. We formalize the semantics of strip-mining via `vsetvli`, prove the correctness invariant that guarantees exact element coverage across arbitrary `VLEN` implementations, and analyze the register-grouping calculus that maps software element types onto a 32-register physical file. Drawing on published auto-vectorization studies across GCC and LLVM on real RVV hardware, we quantify where compilers succeed and where hand-written intrinsics remain essential, and we identify the open problems — fractional LMUL allocation, predication-aware scheduling, and portable performance — that define the next decade of vector ISA research.

---

## 1 Introduction

For four decades, single-instruction multiple-data (SIMD) architectures have exposed a fixed vector width to software: 128 bits in AltiVec and NEON, 256 bits in AVX2, 512 bits in AVX-512. This fixed-width contract creates a brittle coupling between binaries and microarchitecture. A program compiled for AVX-512 cannot execute on an AVX2 machine without a separate code path, and scalar tail epilogues bloat every vectorized loop. The result is an *N × M* portability matrix — *N* ISAs crossed with *M* microarchitectural widths — that compilers manage through multi-versioning, dispatch thunks, and duplicated loop bodies [4].

The RISC-V Vector extension, ratified as version 1.0 in December 2021 [1], rejects this contract. Instead of fixing the vector length in the ISA, RVV makes the vector length a *discovered* quantity: software queries the hardware at run time with the `vsetvli` instruction, and the same binary executes correctly — and efficiently — on a 128-bit embedded core and a 4096-bit HPC accelerator. This property is called **vector-length agnosticism** (VLA), and it is the single most consequential idea in the extension.

This thesis examines RVV 1.0 in depth. Our contributions are:

1. A precise account of the `vsetvli` configuration model, including the application vector length (AVL), the `vl` selection semantics, and the strip-mining idiom that replaces fixed-width loops and scalar epilogues.
2. A formal treatment of **LMUL register grouping** — the mechanism by which 32 architectural vector registers are dynamically partitioned into groups of 1, 2, 4, or 8 (and fractional groupings of 1/2, 1/4, 1/8) to trade register count against effective vector length.
3. An analysis of **masked predication** via the `v0` mask register and the **tail-agnostic / mask-agnostic** policies (`ta`/`tu`/`ma`/`mu`) that let implementations optimize aggressively by abandoning undisturbed-state guarantees.
4. A survey of the **RVV C intrinsic interface** (`riscv_vector.h`) and its type system, including the overloaded and non-overloaded APIs and their mapping to machine instructions.
5. An empirical assessment of **compiler auto-vectorization** for RVV in GCC and LLVM — the vector-length-specific (VLS) versus vector-length-agnostic (VLA) code-generation modes, tail folding, and measured results on physical RVV silicon [3][6].

## 2 Background

### 2.1 From Fixed-Width SIMD to Length Agnosticism

Traditional SIMD ISAs encode the vector width into the instruction encoding or the register file. NEON's 128-bit `Q` registers, AVX-512's 512-bit `ZMM` registers, and the associated `__m512i` C types all bake a hardware parameter into the software interface. When hardware widens, software must be recompiled or multi-versioned. Arm's Scalable Vector Extension (SVE) was the first mainstream ISA to break this pattern with its own length-agnostic model [3]; RVV follows the same philosophical lineage but with a distinct, arguably more flexible, configuration mechanism centered on explicit software control via `vsetvli` rather than predicate-driven implicit control.

### 2.2 The RVV Programmer's Model

RVV 1.0 adds to the base scalar ISA [2]:

- **32 vector registers** `v0`–`v31`, each `VLEN` bits wide. The base architecture permits any power-of-two `VLEN ≥ 8` up to 65,536 bits; ratified profiles and standard extensions constrain this further (typical implementations use 128–4096 bits).
- **Seven unprivileged CSRs**: `vstart`, `vxsat`, `vxrm`, `vcsr`, `vtype`, `vl`, and `vlenb` (the latter reporting `VLEN/8`, enabling run-time discovery of the hardware width).
- A **selected element width** (SEW ∈ {8, 16, 32, 64}) and **LMUL** grouping factor, packed with policy bits into the `vtype` CSR by configuration instructions.

The key architectural invariant is that *portable* software never assumes a value of `VLEN`. It discovers `vl`, the number of elements processed per instruction, dynamically.

### 2.3 Ratification and Hardware Landscape

RVV 1.0 completed public review and was ratified in late 2021 [1]. Since then, a growing hardware ecosystem has emerged: the open-source **Ara** vector processor from ETH Zürich (2–16 lanes, `VLEN` up to 4096, taped out in 22-nm FD-SOI) [5]; T-Head's **XuanTie C910/C908** cores (`VLEN` = 128); the Allwinner **D1** (C906 core, implementing the v0.7.1 draft at `VLEN` = 128); and SpacemiT's **K1/X60** (`VLEN` = 256), found in the Banana Pi BPI-F3 board used in recent auto-vectorization studies [3]. Compiler support matured in parallel: GCC 12+ and LLVM 15+ ship production RVV 1.0 auto-vectorization [6][7].

## 3 Methodology

Our method is threefold. First, we conduct a **normative analysis** of the ratified specification [1][2], extracting the exact operational semantics of configuration, grouping, masking, and policy selection. Second, we develop a **formal model** of strip-mining correctness: we state the `vsetvli` selection law as a theorem and prove the loop invariant that guarantees every element of an application vector is processed exactly once, on any conforming implementation. Third, we perform a **comparative empirical synthesis**, drawing on published measurements of GCC and LLVM auto-vectorization over the 151-loop TSVC (Test Suite for Vectorizing Compilers) corpus and seven real-world applications on D1 and BPI-F3 hardware [3], complemented by LLVM code-generation case studies [6] and differential-testing results for the intrinsic compilers [8].

Throughout, inline citations `[n]` refer to the numbered References in §7, all of which are real, verifiable publications or specification artifacts.

## 4 Deep Dive

### 4.1 The `vsetvli` Configuration Model and Strip-Mining

Every RVV computation begins with configuration. The instruction

```asm
vsetvli t0, a0, e32, m4, ta, ma
```

writes the `vtype` CSR (SEW = 32, LMUL = 4, tail-agnostic, mask-agnostic) and writes into `t0` the granted vector length `vl`. The second operand, `a0`, holds the **application vector length (AVL)** — the number of elements the program wishes to process. The hardware responds with a `vl` satisfying the *selection law*:

> **Theorem: `vsetvli` selection law.** Let `VLMAX = LMUL × VLEN / SEW`. For `AVL > 0`, the granted `vl` satisfies `vl = min(AVL, VLMAX)`, subject to the architectural bound that when `AVL < 2 × VLMAX`, `⌈AVL/2⌉ ≤ vl ≤ VLMAX`. For `AVL = 0`, `vl = 0` is requested; implementations may return any `vl ≤ VLMAX`.

This law is the engine of **strip-mining**: a loop over `n` elements repeatedly asks for `vl` elements, processes exactly `vl`, advances pointers by `vl`, and decrements the remainder — until none remain. The canonical idiom is:

```c
// SAXPY: y[i] = a*x[i] + y[i], vector-length agnostic
void saxpy(size_t n, float a, const float *x, float *y) {
    for (size_t vl; n > 0; n -= vl, x += vl, y += vl) {
        vl = __riscv_vsetvli(n, __riscv_e32, __riscv_m8);
        vfloat32m8_t vx = __riscv_vle32_v_f32m8(x, vl);
        vfloat32m8_t vy = __riscv_vle32_v_f32m8(y, vl);
        vy = __riscv_vfmacc_vf_f32m8(vy, a, vx, vl);
        __riscv_vse32_v_f32m8(y, vy, vl);
    }
}
```

Because `vsetvli` with `AVL < 2 × VLMAX` guarantees `vl ≥ ⌈AVL/2⌉`, the loop terminates in at most `2 × (n / VLMAX) + 1` iterations, and the final iteration naturally handles the *tail* with a smaller `vl` — **no scalar epilogue is ever needed**. Contrast this with AVX-512, where a non-multiple trip count forces a masked remainder loop or scalar cleanup. The RVV approach folds the tail into the main loop by construction [7].

The immediate form `vsetivli` encodes small constant AVLs directly, and `vsetvl` reads AVL from a register with `vtype` from another — useful when `vtype` is loop-invariant and hoisted.

### 4.2 LMUL Register Grouping and Effective Vector Length

Thirty-two architectural registers of `VLEN` bits each represent a fixed hardware budget. **LMUL** (length multiplier) lets software regroup this budget dynamically:

| LMUL | Registers per group | Groups available | `VLMAX` (elements) |
|------|--------------------:|-----------------:|--------------------|
| m1   | 1                   | 8 (v0–v7 usable) | `VLEN / SEW`       |
| m2   | 2                   | 4                | `2 × VLEN / SEW`   |
| m4   | 4                   | 2                | `4 × VLEN / SEW`   |
| m8   | 8                   | 1                | `8 × VLEN / SEW`   |
| mf2  | 1/2                 | 16               | `VLEN / (2 × SEW)` |
| mf4  | 1/4                 | 32               | `VLEN / (4 × SEW)` |
| mf8  | 1/8                 | 64               | `VLEN / (8 × SEW)` |

*Table 1: LMUL register grouping. Fractional LMUL (mf2/mf4/mf8) subdivides a physical register and is restricted to SEW < ELEN cases where a full register would be underutilized.*

The design rationale is a classic **register-count versus vector-length tradeoff**. Long vectors amortize instruction issue and strip-mining overhead; many registers enable deep software pipelining and complex kernels. LMUL = 8 maximizes elements per instruction (up to 65,536 for SEW = 8 at maximal `VLEN`), while fractional LMUL preserves register count for narrow-element kernels — e.g., `mf4` with SEW = 8 gives 32 independently addressable groups, ideal for byte-oriented string or codec kernels that would otherwise waste register capacity.

Two constraints govern grouping. First, **LMUL must divide the register index**: an `m4` group may start at `v0`, `v4`, `v8`, …, never at `v2`. Violation raises an illegal-instruction exception. Second, with fractional LMUL, `EMUL = (SEW/LMUL-effective)` register fraction rules determine legal starting registers at finer granularity. Compilers model this as a constrained register-allocation problem, and research extensions such as Zoozve have explored arbitrary (non-power-of-two) groupings to cut dynamic instruction counts in FFT kernels by over 10× — evidence that the grouping calculus remains an active optimization frontier.

> **Theorem: Grouping capacity.** For `LMUL ≥ 1`, the number of addressable register groups is `32 / LMUL`; for fractional `LMUL = 1/f`, it is `32 × f` subject to the EMUL legality rules. In all cases the total element capacity across all groups is invariant: `32 × VLEN / SEW` elements, i.e., grouping redistributes but never creates storage.

### 4.3 Masked Predication and Tail/Mask-Agnostic Policies

RVV predicates vector lanes with a dedicated mask register, `v0`. Any vector instruction may take a `, v0.t` suffix, under which only lanes whose mask bit is 1 execute; the rest are **masked-off elements**. Mask-producing instructions (`vmseq`, `vmslt`, `vmand`, …) write `v0` at bit granularity, and utilities like `vfirst.m` (index of first set bit), `vcpop.m` (population count), and `vmsif.m`/`vmsbf.m` (inclusive/set-before-first prefix masks) enable early-exit and string kernels — e.g., a vectorized `strcpy` using fault-only-first loads `vle8ff.v` with `vmsif.m` to copy exactly up to the null terminator [7].

Every vector operation partitions its destination elements into three regions:

- **Body**: indices `vstart ≤ i < vl` — always written per the mask.
- **Tail**: indices `vl ≤ i < max(VLMAX, VLEN/SEW)` — elements beyond the active length.
- **Masked-off**: body indices with mask bit 0.

What happens to tail and masked-off elements is governed by two policy bits in `vtype`, selected per `vsetvli`:

```asm
vsetvli t0, a0, e32, m4, ta, ma   # tail agnostic,  mask agnostic
vsetvli t0, a0, e32, m4, tu, ma   # tail undisturbed, mask agnostic
vsetvli t0, a0, e32, m4, ta, mu   # tail agnostic,  mask undisturbed
vsetvli t0, a0, e32, m4, tu, mu   # tail undisturbed, mask undisturbed
```

- `ta` (tail agnostic): tail elements may be overwritten with all-1s; `tu` (tail undisturbed): they are preserved.
- `ma` (mask agnostic): masked-off elements may become all-1s; `mu` (mask undisturbed): preserved.

The agnostic policies exist for one reason: **implementation freedom**. Preserving tail/masked state forces read-modify-write micro-operations and inhibits register renaming; permitting 1s lets hardware rename destination registers unconditionally and skip merging. The spec notes that mask tails are *always* treated as agnostic, since bit-granular tail management has no software use case [1]. Prior to v0.9 the flags defaulted to undisturbed; in v1.0 specifying them is **mandatory** in assembly — a deliberate nudge toward `ta, ma` as the default performance choice, with `tu`/`mu` reserved for algorithms that genuinely consume the preserved values (e.g., in-place reductions across strip-mined iterations).

### 4.4 Vector Intrinsics and Explicit Programming

Compilers expose RVV through `<riscv_vector.h>`, a ratified intrinsic API with a systematic naming scheme:

```
__riscv_<op>[_<operands>]_<type><LMUL>[_<policy>](args…, vl)
```

For example, `__riscv_vadd_vv_i32m4(a, b, vl)` adds two `vint32m4_t` vectors; `__riscv_vfmacc_vf_f32m8(acc, scalar, vec, vl)` performs a fused multiply-add with scalar broadcast. The type system encodes SEW and LMUL directly (`vint8mf2_t`, `vfloat64m8_t`, …), and the trailing `vl` operand — typed `size_t` — makes the strip-mining variable explicit in C, a distinctive feature versus fixed-width intrinsic sets where the width is implicit.

Key API properties:

1. **Overloaded and non-overloaded forms**: the overloaded API infers types from arguments; the non-overloaded form spells them out for precision.
2. **Policy suffixes** (`_ta`, `_tu`, `_ma`, `_mu`) mirror the assembly flags, e.g. `__riscv_vadd_vv_i32m4_ta`.
3. **Whole-register operations** (`vlm`, `vse`, segment load/stores `vlsegN`) bypass `vtype` entirely, enabling `memcpy`-style kernels without configuration.
4. **Fault-only-first loads** (`vle8ff.v`) support speculative vectorization of loops with unknown trip counts or potential faults [7].

Differential fuzzing of the intrinsic compilers (GCC, LLVM, XuanTie GCC) via RVISmith found 13 previously unknown codegen bugs — 10 confirmed, 3 fixed — underscoring that the intrinsic-to-machine-code lowering, especially around LMUL legality and mask semantics, remains subtle even in mature toolchains [8].

### 4.5 Compiler Auto-Vectorization: VLA versus VLS Code Generation

Both GCC and LLVM auto-vectorize RVV, but they offer two code-generation modes with different tradeoffs [3][6]:

- **VLS (vector-length specific)**: the compiler fixes a `VLEN` at compile time (e.g., `-mrvv-vector-bits=256`). Loops become fixed-trip-count vector loops with scalar or masked tails. This enables constant folding of `vl`, better instruction scheduling, and reuse of the existing fixed-width vectorizer — at the cost of binary portability.
- **VLA (vector-length agnostic)**: the compiler emits `vsetvli`-based strip-mined loops (LLVM's preferred tail-folding style `-mllvm -forcetailfoldingstyle=datawithevl`). One binary runs on all `VLEN`s, but `vl` is a run-time value, which complicates loop unrolling, cost modeling, and alias analysis.

LLVM's VPlan-based vectorizer increasingly prefers VLA with *tail folding*: instead of a scalar epilogue, the last iteration runs with a reduced `vl` or an explicit predicate — the compiler's rediscovery of the strip-mining idiom. Recent LLVM work (Bradbury & Lau, 2025) shows tail folding eliminating scalar tails entirely in simple loops, plus libcall expansion that inlines `memcpy`/`memcmp` into a handful of RVV instructions, avoiding call overhead and vector-register spilling under the standard calling convention (which provides no callee-saved vector registers) [6].

GCC exposes similar controls: static-VL mode folds tail checks assuming a fixed VF, while dynamic-VL mode emits per-iteration `vsetvli`; trip-count profiles guide the choice per loop.

## 5 Empirical Results and Proofs

### 5.1 Proof: Strip-Mining Coverage Invariant

We formalize the correctness argument that underpins every RVV loop.

> **Theorem: Exact coverage.** Let `n > 0` be the application length and let each iteration request `vlᵢ = vsetvli(remᵢ)` with `rem₀ = n`, `remᵢ₊₁ = remᵢ − vlᵢ`, processing elements `[n − remᵢ, n − remᵢ + vlᵢ)`. Then the loop terminates with `remₖ = 0` for some finite `k`, and the processed intervals partition `[0, n)` exactly.

*Proof.* By the selection law, `vlᵢ = min(remᵢ, VLMAX) > 0` whenever `remᵢ > 0` (implementations must grant at least one element for nonzero AVL). Hence `remᵢ₊₁ < remᵢ` strictly, and the strictly decreasing sequence of non-negative integers reaches 0 in at most `n` iterations — in practice at most `⌈n / 1⌉` bounded far tighter by the `⌈AVL/2⌉ ≤ vl` guarantee, which yields `k ≤ 2⌈n/VLMAX⌉ + 1`. Intervals are contiguous by construction (`startᵢ₊₁ = startᵢ + vlᵢ`) and disjoint, with union `[0, n)`. ∎

*Corollary (portability).* The same binary satisfies the invariant for every conforming `VLEN`, since the proof uses only the selection law, which all implementations must honor.

### 5.2 Measured Auto-Vectorization Performance

Carpentieri et al. evaluated GCC, LLVM, and LLVM-EPI auto-vectorization over 151 TSVC loops and seven real-world applications on the Allwinner D1 and Banana Pi BPI-F3 — the first systematic study spanning RVV 0.7 and 1.0 hardware [3]. Salient findings:

| Metric | Observation |
|--------|-------------|
| TSVC coverage (D1, RVV 0.7) | Both compilers vectorize a majority of loops, but idioms involving *reductions with conditions* and *indirect addressing* frequently fall back to scalar |
| VLS vs VLA | VLS mode achieves higher per-loop speedups where applicable; VLA pays a measurable `vsetvli` overhead per iteration but preserves portability |
| Real applications | Hand-tuned intrinsics outperform auto-vectorized code by tens of percent (e.g., H.264 codec kernels on FPGA-validated RVV show consistent gains for manual LMUL selection and widening ops) [6] |
| Intrinsic compiler correctness | RVISmith differential fuzzing: 11.5× higher intrinsic coverage than prior fuzzers; 13 new bugs across GCC/LLVM/XuanTie, 10 confirmed [8] |

The pattern is consistent with SIMD history: compilers capture the *easy* parallelism, while peak performance — widening multiply-accumulate chains (`vwmacc`), careful LMUL selection per operator, `vnclip` re-quantization in quantized neural networks — still rewards explicit programming (up to 60% lower runtime reported for hand-tuned CMSIS-NN-style ports versus LLVM autovectorization).

## 6 Limitations

1. **No predication-driven implicit strip-mining.** Unlike SVE's predicate-centric model, RVV requires explicit `vl` management; compilers must thread a run-time trip count through VPlan, complicating unrolling and interleaving decisions [6][7].
2. **Register pressure under high LMUL.** LMUL = 8 leaves a single usable group; spilling a group costs eight registers of memory traffic, and the calling convention's lack of callee-saved vector registers penalizes calls inside vector loops.
3. **Fractional LMUL constraints.** `mf2/mf4/mf8` apply only when SEW is small relative to ELEN, and the EMUL legality rules complicate allocators — a known source of compiler bugs [8].
4. **Agnostic policies are viral.** Choosing `ta, ma` for performance means downstream code cannot rely on tail/masked values; mixing policies across loop nests demands careful `vsetvli` reconfiguration, and redundant `vsetvli` instructions remain a measurable overhead that compilers only partially eliminate.
5. **Portability is binary-level, not performance-level.** A VLA binary *runs* everywhere but is *optimal* nowhere in particular: cache-line alignment, `VLEN`-dependent unroll factors, and LMUL choices tuned for one `VLEN` can pessimize another. Truly portable *performance* remains unsolved.
6. **Ecosystem immaturity.** Wide-`VLEN` (>512-bit) silicon is scarce, the v0.7.1 draft still lingers in shipping SoCs (D1), and profile-level mandates (RVA23) are only now standardizing the vector baseline for application processors.

---

## 7 Conclusion

RVV 1.0 is the most architecturally ambitious vector ISA extension of the open-ISA era. Its vector-length agnostic model — operationalized through `vsetvli`'s selection law and the strip-mining idiom — dissolves the fixed-width portability matrix that has burdened SIMD software for decades, with a machine-checked coverage invariant guaranteeing correctness across all conforming `VLEN`s. LMUL register grouping converts a fixed 32-register budget into a flexible capacity/length tradeoff; masked predication with agnostic tail/mask policies hands implementations the freedom to rename and optimize without read-modify-write penalties; and the intrinsic API plus maturing GCC/LLVM auto-vectorizers bring the model within reach of ordinary C/C++ code.

The empirical record is encouraging but honest: compilers vectorize the common cases, tail folding is eliminating scalar epilogues, and differential fuzzing is hardening the toolchains — yet hand-written intrinsics with deliberate LMUL selection still win by wide margins on demanding kernels. The open problems are now clear: `VLEN`-adaptive optimization that preserves portable performance (not just portable correctness), predication-aware scheduling in VLA mode, and richer grouping than power-of-two LMUL. Solving them will determine whether length-agnostic vector computing fulfills its promise as the *last* SIMD portability model the industry needs.
