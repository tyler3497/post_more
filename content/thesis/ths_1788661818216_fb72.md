# NewSQL Without Compromise: Spanner TrueTime External Consistency, CockroachDB Parallel Commits, and Calvin Deterministic Transaction Scheduling

## Abstract

The tension between strong consistency and global scalability has long been treated as an iron law of distributed databases. Three landmark systems — Google Spanner, CockroachDB, and Calvin — each demonstrate that the law admits narrow, principled exceptions. Spanner achieves externally consistent distributed transactions at planetary scale by exposing bounded clock uncertainty through the TrueTime API and pairing timestamp assignment with commit wait, so real-time order is reflected in commit order [1]. CockroachDB, targeting Spanner's semantics without TrueTime, layers a hybrid logical clock over consensus-driven intents and introduces parallel commits, cutting distributed commit from two sequential consensus rounds to one while preserving serializable isolation [5]. Calvin eliminates distributed agreement altogether: a deterministic scheduling layer orders transaction inputs before execution, so replicas converge without two-phase commit or Paxos in the transaction path [3]. This thesis formalizes all three commit protocols, compares their latency models analytically and against published benchmarks, proves the key correctness properties, identifies the workload regimes where each design dominates, and maps the open problems: clock-free external consistency, deterministic interactive transactions, and hybrid architectures.

---

## 1. Introduction

For decades, the distributed database community accepted a working folk theorem: systems could provide either *strong consistency* or *horizontal, geographic scalability*, but not both [1][6]. Into this landscape arrived the NewSQL movement — relational semantics, ACID transactions, and SQL, rebuilt on architectures capable of spanning datacenters and continents. Three designs from this movement have proven especially durable as ideas, not merely as products: Google Spanner [1], CockroachDB [5], and Calvin [3].

Each system confronts the same fundamental problem. A transaction spanning multiple partitions must be ordered consistently everywhere despite failures, clocks that drift, and networks whose latencies vary by orders of magnitude. Classical solutions — two-phase locking (2PL) with two-phase commit (2PC), Paxos-backed transaction managers — impose contention costs that explode under geographic distribution. The three systems diverge on *where they pay for agreement*:

1. **Spanner** pays in clock infrastructure: GPS receivers, atomic clocks, and an uncertainty-aware time API (TrueTime) that makes real-time ordering cheap enough to use as the serialization order [1][2].
2. **CockroachDB** pays in consensus round trips but refuses special hardware: it layers a *hybrid logical clock* (HLC) over Raft-replicated key ranges and pipelines commit phases so that two sequential consensus rounds collapse into one [5].
3. **Calvin** pays in *pre-execution ordering*: a deterministic scheduling layer assigns every transaction a position in a global input sequence before any lock is acquired, eliminating distributed agreement from the transaction path entirely [3].

Our contribution is a unified formal treatment of these three commit protocols, a comparative latency model that explains their measured behavior, and a decision framework grounded in workload characteristics. 

> **Definition 1 (External Consistency).** A system is *externally consistent* if for any two transactions $T_1$ and $T_2$, whenever $T_1$ commits before $T_2$ begins in real time, the serialization order places $T_1$ before $T_2$. This is strictly stronger than serializability and equivalent to strict serializability for transactional systems [1][7].

External consistency is the gold standard because it composes with reasoning *outside* the database: if a client observes a committed write and then phones a colleague who starts a new transaction, the colleague's transaction is serialized after the write. No weaker isolation property supports this composition.

## 2. Background and Related Work

### 2.1 The Transaction Ordering Problem

Distributed transactions classically combine *concurrency control* (which concurrent operations may proceed) with an *atomic commit protocol* (all-or-nothing across partitions). Two-phase locking acquires locks during execution and releases them after 2PC; optimistic concurrency control validates read sets before commit; multiversion concurrency control (MVCC) keeps immutable old versions so that reads never block writes.



### 2.2 Linearizability, Strict Serializability, and the TrueTime Insight

Spanner generalizes this from single operations to transactions: *external consistency* is linearizability's transactional sibling. The Spanner authors note the equivalence explicitly [1].

TrueTime's insight is that *uncertainty bounds*, not accuracy, are what commit protocols need: the API returns an interval $[earliest, latest]$ guaranteed to contain the true time, and protocols wait out the uncertainty rather than hoping it does not exist [1][2].

### 2.3 Hybrid Logical Clocks and Consensus Without Clocks

CockroachDB cannot assume atomic clocks in its deployment targets, so it replaces physical timestamps with *hybrid logical clocks*: each timestamp pairs wall-clock time with a logical counter, updated as $HLC := max(now, received + 1)$ [5]. The result preserves causality — if event $a$ happened-before $b$, then $HLC(a) < HLC(b)$ — without any bound on clock skew. The price is that ordering no longer implies real-time order, so CockroachDB must enforce external consistency by other means.

### 2.4 Deterministic Databases

Early deterministic systems (e.g., VoltDB) required that transactions never block and fit a single partition; Calvin generalizes determinism to partitioned, disk-backed, replicated systems with multi-partition transactions.

## 3. Methodology

Our analysis proceeds in three stages. First, we *formalize* each system's commit protocol as a sequence of rounds with precise timestamp assignment rules, drawing on the primary publications [1][3], the CockroachDB architecture documentation [5], and Google's technical explanations of TrueTime semantics [2]. Second, we *derive latency models* parameterized by uncertainty bound $epsilon$, consensus round latency $L_c$, and one-way inter-region latency $L_r$, and we instantiate these models with published figures. Third, we *compare* the designs on a common workload taxonomy and state correctness claims as theorems with proof sketches grounded in the original arguments.

We evaluate the systems along five dimensions:

- **Correctness property**: external consistency (Spanner), serializability with bounded staleness and follower reads (CockroachDB), deterministic serializability (Calvin).
- **Hardware assumptions**: atomic clocks and GPS (Spanner), none (CockroachDB), none (Calvin).
- **Commit latency** as a function of network and uncertainty parameters.
- **Availability during partitions**: Spanner's Paxos groups continue on majority quorum; CockroachDB likewise via Raft; Calvin's sequencer is the availability bottleneck of its epoch.
- **Workload fit**: interactive vs. stored-procedure transactions, single-partition vs. multi-partition mix, read-heavy vs. write-heavy balance.

## 4. Deep Dive

### 4.1 Spanner: TrueTime, Timestamp Assignment, and Commit Wait

Spanner organizes data into *tablets* served by Paxos groups. Read-write transactions execute under wound-wait 2PL: reads acquire shared locks, writes are buffered client-side, and at commit the client drives a *modified two-phase commit* across participant Paxos leaders [1].

The protocol's beating heart is timestamp assignment. When the commit begins, the coordinator selects a commit timestamp $s$ satisfying two rules:

1. $s >$ every timestamp used by reads in the transaction (preserving internal consistency).
2. $s >= TT.now().latest$ at the moment of commit.

Then comes *commit wait*: before logging the commit record through Paxos, the coordinator waits until $TT.now().earliest > s$ — that is, until the chosen timestamp is *provably in the past* [1][2]. The elegance is that this wait overlaps with the Paxos proposal round, so it rarely adds latency: as the Google Cloud documentation notes, the wait proceeds in parallel with sending Paxos messages [2].

> **Theorem 1 (Spanner External Consistency).** If transaction $T_1$ commits before $T_2$ starts in real time, then $TS(T_1) < TS(T_2)$.
>
> *Proof sketch.* Commit wait guarantees $T_1$'s commit record is durable only after true time has passed $TS(T_1)$; otherwise the coordinator would still be waiting. $T_2$ begins after $T_1$'s commit, so any call $TT.now()$ made by $T_2$'s coordinator returns an interval with $earliest$ greater than the true time at $T_1$'s commit completion, which exceeds $TS(T_1)$. Rule 2 sets $TS(T_2) >= TT.now().latest >= TT.now().earliest > TS(T_1)$. Q.E.D.

TrueTime's implementation keeps the uncertainty window $epsilon$ small — typically under 10 ms, often microseconds — using GPS and atomic clock references, with clock daemons that widen the interval when references degrade [1]. The commit-wait duration is bounded by $2\epsilon$, which is negligible against inter-datacenter latencies of 30–100 ms [2]. Read-only transactions and snapshot reads need no locks at all: they simply read at $TT.now().latest$, and the start rule guarantees they observe every transaction that committed before they began.

```python
# TrueTime API: uncertainty is first-class
class TrueTime:
    def now(self):
        """Returns (earliest, latest) bounding true time."""
        t = self._reference_time()
        return (t - self.epsilon, t + self.epsilon)

def commit_wait(tt, s):
    """Spanner commit wait: block until s is provably past."""
    while True:
        earliest, _ = tt.now()
        if earliest > s:
            return  # Theorem 1's key invariant now holds
```

### 4.2 CockroachDB: Intents, HLC, and Parallel Commits

CockroachDB partitions the keyspace into *ranges*, each replicated by Raft. A write does not immediately modify a key; it leaves a *write intent* — a provisional record carrying the transaction's HLC timestamp — replicated via Raft [5]. Reads encountering an intent either wait, push the intent's timestamp forward, or resolve it, depending on priority and isolation requirements. This is MVCC with physically distributed, consensus-backed uncommitted state.

The original commit protocol required *two* sequential consensus rounds: first the transaction record transitions `PENDING` to `COMMITTED`, then intents are resolved asynchronously. The insight of **parallel commits** (introduced in CockroachDB 19.2) is that the coordinator can write intents in a `STAGING` state that already names the transaction's commit timestamp, return success to the client after a *single* consensus write of the transaction record, and resolve the intents asynchronously [5]. A reader encountering a `STAGING` intent consults the transaction record; if it is `COMMITTED`, the intent is treated as committed at the staged timestamp.

The latency win is concrete. Where the old protocol paid $2L_c$ for commit, parallel commits pay approximately $L_c$, with intent cleanup off the critical path. For a geo-distributed deployment with $L_c \approx 40$ ms, that is a halving of commit latency for multi-range transactions — the dominant cost in write-heavy workloads.

Correctness rests on the staged timestamp. Because the transaction record (a single Raft-replicated key) is the *single source of truth* for the commit decision, and because it is written exactly once via consensus, there is a unique linearization point: all intents atomically become visible at the staged commit timestamp. CockroachDB guarantees serializable isolation; external consistency holds for clients that observe commit acknowledgments, since the HLC assigned at commit is monotonic with respect to causally prior observed commits — though without TrueTime it cannot offer Spanner's real-time guarantee for *uncoordinated* external observers [5].

```sql
-- CockroachDB exposes the mechanics to the user:
-- follower reads bound staleness, trading recency for latency.
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN;
SELECT balance FROM accounts WHERE id = 42
  AS OF SYSTEM TIME follower_read_timestamp();
COMMIT;
```

### 4.3 Calvin: Deterministic Scheduling and Replication of Inputs

Calvin inverts the problem. Instead of ordering transactions by agreement *during* execution, it orders *transaction inputs* before execution begins [3]. The architecture has three layers:

1. **Sequencing layer.** One or more sequencers collect client requests into *batches* (epochs, typically 10 ms). Sequencers agree on a global order — a deterministic function of per-sequencer batches — producing the *global input sequence*.
2. **Scheduling layer.** Schedulers at each node take the global sequence, perform read/write set analysis for transactions touching local partitions, and acquire *all* locks for a transaction's lifetime *before* handing it to a worker thread. Because lock acquisition order is identical at every replica, deadlocks are structurally impossible and execution is deterministic.
3. **Storage layer.** Calvin is storage-agnostic; the original paper demonstrates a disk-backed engine.

The masterstroke is *replicating inputs, not effects*. Replicas of a partition receive the same ordered input sequence and deterministically produce the same state transitions, so Calvin supports multiple consistency levels — including Paxos-backed strong consistency across regions — *at no cost to transactional throughput*, since replication rides on the already-ordered inputs [3]. Atomic commit needs no 2PC: either all participants received the transaction in the batch (commit) or the deterministic protocol aborts it identically everywhere.

> **Theorem 2 (Calvin Deterministic Serializability).** All non-faulty replicas of every partition execute conflicting transactions in the identical global order, hence converge to identical states and the execution is serializable in global-sequence order.
>
> *Proof sketch.* The sequencing layer delivers the same global input sequence to all schedulers (by construction of the deterministic merge). Each scheduler acquires locks for transactions strictly in sequence order before execution, so at every replica the lock acquisition order — and therefore the execution order of conflicting transactions — equals the global sequence order. Identical inputs in identical order through deterministic transaction logic yield identical outputs. Q.E.D.

Calvin's measured results are striking: near-linear scale-out on TPC-C across a cluster of commodity machines, with the sequencing layer's throughput — not distributed coordination — as the ceiling [3]. The cost is expressiveness: Calvin transactions are *stored procedures* whose read/write sets must be knowable ahead of execution. Interactive transactions, where a client reads a value mid-transaction and decides what to do next, fundamentally violate the pre-ordering assumption.

### 4.4 Comparative Latency Models

We now derive per-commit latency under a simple model. Let $L_c$ be one consensus round-trip within a region, $L_r$ the cross-region round trip, and $epsilon$ the TrueTime uncertainty bound.

| System | Commit critical path | Dominant term (geo) | Hardware needed |
|---|---|---|---|
| Spanner | timestamp assign + 2PC prepare/commit + commit wait ($\leq 2\epsilon$, overlapped) | $2L_r$ (2PC across regions) | GPS + atomic clocks |
| CockroachDB | intent writes + 1 consensus round (parallel commits) | $L_r$ + intent replication | none |
| Calvin | epoch batching ($\sim$10 ms) + deterministic execution | epoch delay + local execution | none |

Several observations follow. First, Spanner's commit wait is *not* the latency bottleneck: $2\epsilon < 20$ ms hides inside the $2L_r$ of cross-region 2PC. The folk claim that TrueTime "slows down" Spanner misreads the paper; uncertainty only bites when references degrade [1][2]. Second, CockroachDB's parallel commits strictly dominate its old protocol by one consensus round on the critical path, and dominate Spanner's 2PC when TrueTime hardware is unavailable. Third, Calvin's epoch batching imposes a *latency floor* — no transaction commits faster than the batch window — but its throughput ceiling is the highest of the three for partitionable workloads, since no per-transaction agreement occurs at all.

Throughput tells the complementary story:

| System | Throughput limiter | TPC-C scale-out (reported) |
|---|---|---|
| Spanner | Paxos leader per group; 2PL contention on hot keys | linear to 100s of nodes (F1 workload) [1] |
| CockroachDB | Raft leader per range; intent conflict rate | near-linear on TPC-C [5] |
| Calvin | Sequencer batch assembly | near-linear; 12x vs. single node on 24 cores [3] |

## 5. Empirical Evaluation and Theoretical Analysis

### 5.1 What the Papers Report

TrueTime's $epsilon$ is "generally less than 10 ms" and frequently in the microsecond range, The F1 advertising backend — Spanner's motivating production workload — demonstrated global replication with externally consistent reads across five US datacenters.

Calvin's evaluation is the most classically database-like: on a cluster of commodity machines, Calvin scales TPC-C throughput near-linearly with node count, and on a 24-core machine it achieves roughly 12x the single-threaded throughput, with four cores dedicated to sequencing and scheduling [3]. ### 5.2 Theoretical Comparison: Where Each Design Is Optimal

We can now state the decision rule precisely. Let $p$ be the fraction of multi-partition transactions, $i$ the fraction of interactive (non-stored-procedure) transactions, and $h$ a boolean for TrueTime-capable hardware:

1. If $h$ and strong external consistency is required for *uncoordinated* observers (e.g., auditing, global secondary indexes consumed by external systems), Spanner's design is uniquely sufficient: it is the only one of the three whose guarantee holds without client cooperation [1][2].
2. If not $h$ and $i > 0$, CockroachDB dominates: parallel commits minimize the consensus tax while supporting fully interactive SQL [5].
3. If $i$ is approximately 0 (stored procedures with analyzable read/write sets) and $p$ is high, Calvin dominates on throughput: it removes agreement from the transaction path entirely, and its batching cost is amortized over the epoch [3].
4. Read-heavy workloads with relaxed recency (seconds) favor all three systems' snapshot and follower-read paths, which bypass locking and consensus on the read path entirely.

> **Theorem 3 (Optimality boundary).** No system among the three strictly dominates another across the $(p, i, h)$ parameter space; each is Pareto-optimal on a non-empty region.
>
> *Proof sketch.* Spanner alone provides external consistency without client coordination (region $h$ and strong-audit). CockroachDB alone supports interactive transactions without special hardware (region not-$h$ and $i > 0$). Calvin alone achieves per-transaction agreement-free commit for multi-partition stored procedures (region $i \approx 0$ and high $p$), since its commit path contains zero consensus rounds while both competitors contain at least one. Q.E.D.

## 6. Limitations and Open Problems

**Clock-free external consistency.** The SSS protocol and related work attempt external consistency without TrueTime using vector and scalar clocks, but at the cost of blocking read-only transactions or delaying commit acknowledgments [6]. Whether Spanner-grade external consistency is achievable with *zero* special hardware and *zero* added commit latency remains open.

**Determinism for interactive transactions.** Calvin's pre-declaration requirement excludes the interactive transactions that dominate OLTP practice. Optimistic determinism — execute speculatively, then deterministically order — recovers some ground but reintroduces aborts. A deterministic system supporting fully general interactive transactions with Calvin-level throughput is an unsolved problem [3][4].

**The sequencer bottleneck.** Calvin's sequencing layer is a throughput ceiling and an availability hinge. **Hybrid logical clocks and real-time anomalies.** CockroachDB's HLC can assign commit timestamps that violate real-time order for uncoordinated external observers — the precise gap TrueTime closes. **Hybrid architectures.** The most promising direction borrows from all three: deterministic scheduling within a region (Calvin-style), HLC or TrueTime ordering across regions, and staged parallel commits to collapse consensus rounds. ---

## 7. Conclusion

Spanner, CockroachDB, and Calvin each refute a different clause of the folk theorem that strong consistency cannot scale. Spanner shows that *bounded uncertainty* is a sufficient substitute for perfect clocks, and that external consistency at global scale costs less than the network already charges [1][2]. CockroachDB shows that careful protocol engineering — staging commit decisions in consensus-backed intents — can halve the price of serializable commit without exotic hardware [5]. Calvin shows that the price can be eliminated rather than merely reduced, if transactions are ordered before they execute [3].

For the practitioner, the choice among them reduces to workload parameters $(p, i, h)$ and the strength of consistency the application genuinely needs. ---
