# Oblivious RAM: Path ORAM, Circuit ORAM, and the Asymptotics of Access-Pattern Privacy

## Abstract

Oblivious RAM (ORAM) hides the memory access pattern of a program running over data held by an untrusted party. Introduced by Goldreich and Ostrovsky [1], ORAM compilers transform arbitrary RAM computations into ones whose physical address trace reveals nothing about logical inputs. This thesis develops ORAM theory from its definitional foundations through the modern tree-based constructions that made it practical. We present Path ORAM [2] — a binary bucket-tree with a client-side position map, stash, and greedy single-path eviction. We analyze Circuit ORAM [3], which replaces probabilistic eviction with two metadata scans plus one data scan to achieve near-optimal circuit complexity with constant client memory, and Ring ORAM [4], whose bucket-size-independent bandwidth improves on Path ORAM by 2.3–4×. We study Onion ORAM [5], which trades polylogarithmic server-side homomorphic computation for constant bandwidth, and survey the lower-bound landscape: the Goldreich–Ostrovsky Ω(log *n*) bound and its caveats, and the Larsen–Nielsen [6] and Hubáček et al. [7] online bounds that close them. We also cover secure-processor definitions [8], oblivious parallel RAM [9], bandwidth metrics, applications, and open problems.

## 1 Introduction

Encryption hides the *content* of outsourced data, but not the *pattern* of access: a database of ciphertexts still reveals which records are read, how often, and in what order — enough to infer keywords, control flow, even keys. Goldreich and Ostrovsky formalized this threat and introduced Oblivious RAM [1]: a compiler that takes any RAM program and produces an equivalent program whose sequence of physical memory addresses is statistically (or computationally) independent of the program's logical behavior.

For two decades ORAM remained a theoretical curiosity: the original hierarchical construction achieved amortized *O*(log³ *n*) overhead, and successors kept constants and client-storage requirements far beyond practicality. The field changed in 2013 with Path ORAM [2]: an "extremely simple" tree-based protocol with small client storage, provably *O*(log *n*) bandwidth for blocks of size *B* = Ω(log² *n*), adopted in secure-processor designs within months of publication.

> **Theorem:** (Goldreich–Ostrovsky lower bound, informal [1]) Any statistically secure, online ORAM compiler in the balls-and-bins model with *O*(1) client blocks and *O*(log *n*)-bit blocks incurs Ω(log *n*) amortized bandwidth overhead per access.

The sections that follow trace the arc from this impossibility result to constructions that meet it.

## 2 Background

### 2.1 The ORAM definition

An ORAM scheme is a pair of algorithms (in the simplest client–server model) implementing the interface of a random-access memory. Let the logical memory hold *n* blocks. A *request sequence* is a sequence of operations `Read(a)` / `Write(a, v)` on logical addresses *a* ∈ [*n*]. The ORAM compiler produces, for each request, a sequence of *physical* accesses to server storage. Security is defined by an experiment: the adversary observes the full transcript of physical accesses and must be unable to distinguish which of two equal-length request sequences was executed [1, 8].

Two security notions matter. *Statistical* security requires the access-pattern distributions to be statistically close for any two request sequences — no computational assumption on the adversary. *Computational* security requires only that no polynomial-time adversary can distinguish them; this admits encryption-based encodings and is the notion achieved by all deployed tree-based schemes. *Perfect* security (zero distinguishing advantage) is strictly stronger and an active frontier.

### 2.2 The Goldreich–Ostrovsky lower bound and its caveats

Goldreich and Ostrovsky proved that any ORAM in the *balls-and-bins* model — where the client may only move opaque blocks between memory cells, never re-encode their contents — with constant client storage and *O*(log *n*)-bit blocks has amortized bandwidth overhead Ω(log *n*) [1]. The bound is remarkably strong: it holds even if the ORAM knows the entire request sequence offline.

Boyle and Naor (ITCS 2016) identified two caveats [surveyed in 6, 7]:

1. **Balls-and-bins only.** If the ORAM may apply arbitrary encodings (e.g., homomorphic encryption), the bound's proof breaks: removing the assumption would imply super-linear lower bounds for sorting circuits, a long-standing open problem in circuit complexity.
2. **Statistical security only.** The original bound assumes the adversary is unbounded. A computationally bounded adversary might permit asymptotically better schemes.

Both caveats were subsequently addressed for the *online* setting — where requests arrive one at a time and must be served before future requests are known, the setting in which essentially all real ORAMs operate. Larsen and Nielsen [6] proved an Ω(log *n*) lower bound for any online ORAM with *computational* security and arbitrary data representation; Hubáček et al. [7] strengthened this to hold even when the adversary cannot tell which physical accesses correspond to which logical operation ("blurred boundaries"). Together, these results establish that logarithmic overhead is essentially unavoidable for online ORAM — so the interesting question is not *whether* to pay it, but *which constant factors* and *which side constraints* (client storage, circuit complexity, server computation) the payment takes.

### 2.3 Bandwidth, client storage, and server storage

ORAMs are evaluated on three metrics, all as functions of *n*, the number of logical blocks [4]:

| Metric | Definition | Typical target |
|---|---|---|
| **Bandwidth overhead** | Physical blocks transferred per logical access (multiplicative blowup) | *O*(log *n*) |
| **Client storage** | Trusted local memory at the client / ORAM controller | *O*(1) blocks or *O*(λ) |
| **Server storage** | Untrusted memory at the server | *O*(*n*) blocks |

Bandwidth is further distinguished as *amortized* versus *worst-case*: Path ORAM's worst-case and amortized costs coincide up to constants, which is one reason it displaced hierarchical schemes with expensive periodic reshuffles.

A subtle but crucial parameter is the **block size** *B*. All tree-based schemes pack auxiliary metadata (position-map entries) into blocks; recursion multiplies bandwidth by a factor depending on how many entries fit in one block. For the Ω(log *n*) bound to be *tight*, block sizes of *B* = Ω(log² *n*) bits are needed, so that the recursion costs only a constant factor [2, 3].

## 3 Methodology

### 3.1 The tree-based ORAM framework

Nearly all practical ORAMs follow the tree paradigm introduced by Shi et al. and perfected by Path ORAM [2]. The server stores a complete binary tree of height *L* = ⌈log₂ *n*⌉. Each node of the tree is a *bucket* holding up to *Z* encrypted blocks (real or dummy). The client holds two structures:

- **Position map:** a table mapping each logical address *a* to a uniformly random leaf label *s* ∈ {0, 1}^*L*. This is the secret that randomizes access: every block *a* is *assigned* to leaf *s*, meaning it may legally reside anywhere on the root-to-leaf path *P*(*s*).
- **Stash:** a small client-side buffer holding blocks transiently during accesses.

The framework maintains one invariant:

> **Path invariant:** If block *a* is mapped to leaf *s*, then *a* is stored either in some bucket on path *P*(*s*) or in the stash — nowhere else.

An access to address *a* proceeds in three phases:

1. **Read path.** Look up *s* = pos[*a*]; read and decrypt all *Z*·(*L*+1) blocks on *P*(*s*) into the stash.
2. **Remap.** Assign *a* a fresh uniform leaf *s*′; update pos[*a*] ← *s*′. (This is the step that guarantees unlinkability: the next access to *a* will touch an independent random path.)
3. **Evict.** Write back along *P*(*s*), greedily placing stash blocks as deep as possible subject to the path invariant, padding with encrypted dummies.

Every access reads and writes exactly one uniformly random path, so the physical transcript is independent of the request sequence. Security reduces to one probabilistic claim: the stash does not overflow except with negligible probability.

### 3.2 Recursion: shrinking client storage

A naive position map stores *n* leaf labels: *O*(*n* log *n*) bits of client storage, far too much for a secure processor's on-chip memory. The standard fix is *recursion* [1, 2]: store the position map itself in a smaller ORAM, whose position map is stored in an even smaller ORAM, and so on, until the top-level map fits in *O*(1) client blocks. If each block holds χ position-map entries, recursion depth is log_χ *n*, and each logical access triggers that many recursive ORAM accesses — a multiplicative bandwidth factor. For *B* = Ω(log² *n*), χ is large enough that the factor is a small constant, preserving asymptotic optimality [2].

### 3.3 Stash analysis via stochastic coupling

The technical heart of tree-based ORAM is bounding the stash. Path ORAM's original analysis uses a coupling argument [2]: the real process is coupled to an idealized "infinite" ORAM with non-overflowing buckets, and the stash is shown to equal the ideal overflow, which behaves like a well-understood queueing system. For bucket size *Z* ≥ 4, the stash exceeds *R* blocks with probability negligible in *R* — a few dozen slots suffice for failure probability 2⁻⁸⁰. Circuit ORAM [3] gives a tighter post-processing argument that works with *Z* = 2.

## 4 Deep Dive

### 4.1 Path ORAM: the canonical construction

Path ORAM [2] is the reference design against which all tree-based ORAMs are measured. Its pseudocode fits on half a page:

```python
def access(a, op, v=None):
    s = pos[a]                      # 1. leaf currently assigned to a
    for bucket in path(s):          # 2. read entire path into stash
        stash |= decrypt(bucket)
    if op == READ:
        out = find(a, stash)
    else:
        update(a, v, stash); out = ACK
    pos[a] = random_leaf()           # 3. remap to fresh random leaf
    for bucket in reversed(path(s)):# 4. greedy evict back along path
        writeable = [b for b in stash if b.leaf in subtree(bucket)]
        bucket[:] = encrypt(writeable[:Z] + dummies(Z))
        stash -= set(bucket)
    return out
```

Three properties make it practical. First, *bandwidth is deterministic*: exactly 2·*Z*·(*L*+1) blocks per access (read path + write path), so there are no expensive reshuffle phases and no timing side channel from variable-length operations. Second, *eviction is local and greedy*: blocks are pushed as deep as the invariant allows, requiring no global coordination. Third, *security is conceptually trivial*: each access touches a uniformly random path, and remapping makes successive accesses to the same block unlinkable; the only nontrivial proof obligation is the stash bound.

Concretely, with *n* = 2²⁰ blocks, *Z* = 4, and 4 KB blocks, one access moves roughly 168 blocks before recursion — large constants, but the asymptotics are right: *O*(log *n*) blocks per access with *O*(1)-block client storage after recursion, matching the Goldreich–Ostrovsky bound for *B* = Ω(log² *n*) [2].

### 4.2 Circuit ORAM: optimal circuit complexity via deterministic eviction

Path ORAM is bandwidth-optimal, but it is not *circuit*-optimal. When ORAM is used inside secure computation — garbled circuits, or the control logic of a secure processor — the cost metric is the number of gates (especially non-XOR/AND gates) needed to implement one access. Path ORAM's eviction requires obliviously sorting the stash along the path, costing *O*(*Z* log *n*) comparisons per level and a naive circuit of *O*((*D* + log² *n*) log² *n*) gates for *D*-bit blocks [3].

Circuit ORAM [3] restructures eviction into a form with tiny, constant-memory circuits:

1. **Two metadata scans.** Scan the *headers* (leaf labels and occupancy bits) of all buckets on the eviction path — twice, not the data. The first scan identifies, for each level, the block that can be pushed deepest; the second scan resolves conflicts. Metadata is *O*(log *n*) bits per block, so these scans are cheap.
2. **One data scan.** A single linear pass moves at most one block per level into place, using only oblivious multiplexers.

The eviction is *deterministic* given the metadata and uses *O*(1) client memory. The result is a circuit of *O*((*D* + log² *n*) log *n*)·ω(1) gates — concretely about 0.97M AND gates at the 8 KB breakeven point with failure probability 2⁻⁸⁰, a 1000× improvement over the prior art [3]. This is *near-optimal*: the Goldreich–Ostrovsky logarithmic lower bound applies to the circuit-size metric as well, so Circuit ORAM is tight up to the ω(1) factor for *D* = Ω(log² *n*) [3].

### 4.3 Ring ORAM: bandwidth independent of bucket size

Path and Circuit ORAM read *entire buckets* (*Z* blocks per level) on every access, so bandwidth scales with *Z*. Ring ORAM [4] breaks this coupling. Its key observation: on a read path, only *one* block per bucket is ever the target — the rest are dummies or blocks destined for other paths. Ring ORAM therefore reads exactly one block per bucket per access, using two mechanisms:

- **XOR technique.** When the target block is not the one read, the server can XOR-combine blocks so the client still learns its block while the server learns nothing about *which* block was wanted. This moves work from bandwidth to (untrusted) server computation.
- **Early reshuffle.** Buckets are reshuffled after *S* accesses (*S* < *Z*·something) rather than on every access, amortizing the reshuffle cost.

The payoff is twofold. First, Ring ORAM's bandwidth is *independent of the bucket size Z*, so *Z* can be tuned purely for stash-overflow probability without bandwidth penalty — the first tree-based ORAM with this property [4]. Second, measured end-to-end bandwidth is 2.3–4× better than Path ORAM in the small-client-storage setting, and with the XOR technique (simple untrusted server computation) the *online* bandwidth becomes *constant* — roughly a 60× improvement over Path ORAM for the latency-critical portion of an access [4]. By tuning parameters, Ring ORAM also matches the best *large*-client-storage schemes, "closing the gap" of its title.

### 4.4 Beyond the logarithmic barrier: Onion ORAM and the lower-bound landscape

The Ω(log *n*) lower bounds of [1, 6, 7] assume the server is *passive storage*. If the server may compute, the bound's proof fails — and Onion ORAM [5] exploits exactly this. Using *additively* homomorphic encryption (the Damgård–Jurik cryptosystem, avoiding the ciphertext expansion of FHE), the server performs the eviction's linear operations on encrypted data itself. The client's bandwidth per access becomes *constant*; the server does polylogarithmic homomorphic work. Onion ORAM was the first concrete constant-bandwidth ORAM under standard assumptions (even semi-honest), with a novel malicious-server variant that avoids SNARKs [5].

Where does this leave optimality? The picture is now sharp:

| Setting | Lower bound | Tight construction |
|---|---|---|
| Statistical, balls-and-bins, online | Ω(log *n*) [1] | Path ORAM [2] |
| Computational, arbitrary encoding, online | Ω(log *n*) [6, 7] | Circuit ORAM [3] (circuit metric) |
| Server computation allowed | none (barrier broken) | Onion ORAM [5]: *O*(1) bandwidth |
| Perfect security | open | Logarithmic overhead achievable [recent] |

The statistical-vs-computational distinction thus turned out to be less decisive than Boyle and Naor feared: Larsen–Nielsen and Hubáček et al. recovered the logarithmic bound for computational online ORAM anyway [6, 7]. The decisive relaxation is *server computation* — which is why modern confidential-computing deployments pair ORAM with trusted or semi-trusted compute [8].

Oblivious *parallel* RAM (OPRAM) extends the story to *m* CPUs accessing memory concurrently: Circuit OPRAM [9] unifies the statistically and computationally secure regimes, showing that Circuit ORAM's deterministic eviction composes cleanly with parallel recursion.

### 4.5 Applications

Tree-based ORAMs are deployed wherever the access pattern itself is sensitive. In **secure processors**, the ORAM controller sits between the last-level cache and DRAM, holding the position map and stash on chip; Path ORAM was adopted in such designs within months of publication [2], and Fletcher et al. [8] formalize the security definitions for adversaries observing the DRAM bus (including the need for constant-time padding). **Oblivious databases** (e.g., oblivious OLTP engines) layer transactional stores over Path ORAM with Merkle-tree integrity over the buckets. In **secure computation**, garbled-RAM compilers use ORAM as a subroutine, where Circuit ORAM's gate-optimal eviction [3] and Circuit OPRAM's parallel variant [9] are the designs of choice because every AND gate is paid for in the protocol. **Confidential cloud storage** — private information retrieval with writes, encrypted search indexes — uses tree-based ORAM as the default access-pattern compiler.

## 5 Empirical Results and Proofs

We summarize the concrete asymptotic and experimental results established in the cited works.

**Bandwidth.** Path ORAM: 2*Z*(*L*+1) blocks per access worst-case [2]. Ring ORAM: 2.3–4× lower total bandwidth; constant online bandwidth with XOR-technique server computation [4]. Onion ORAM: *O*(1) blocks per access with *O*(log² *n*) homomorphic server work [5].

**Circuit complexity.** Circuit ORAM: *O*((*D* + log² *n*) log *n*)·ω(1) gates per access vs. Path ORAM's naive *O*((*D* + log² *n*) log² *n*); 0.97M AND gates at the 8 KB breakeven point, 1000× better than prior work at 2⁻⁸⁰ failure probability [3].

**Lower bounds.** Goldreich–Ostrovsky [1]: Ω(log *n*) amortized, statistical, balls-and-bins, offline. Larsen–Nielsen [6]: Ω(log *n*) for online ORAM with computational security and arbitrary data representation. Hubáček et al. [7]: the bound persists even when operation boundaries are hidden. All three match the tree-based upper bounds up to the block-size condition *B* = Ω(log² *n*), where position-map recursion contributes only a constant factor [2, 3].

**Stash bounds (proof sketch).** The modern argument [2, 3] couples the real process to an idealized ORAM with infinite buckets. In the ideal process, each block's leaf is uniform and independent, so the number of blocks competing for the top *k* levels is a sum of (near-)independent indicators; a Chernoff bound shows it exceeds capacity only with probability exp(−Ω(*k*)). The coupling lemma shows the real stash equals the ideal overflow pathwise, transferring the tail bound. Circuit ORAM refines this with a post-processing argument that avoids the union bound over paths and yields the *Z* = 2 result [3].

## 6 Limitations

**The stash tail is not zero.** Path ORAM's overflow probability is negligible but nonzero; deployments choose parameters for a target failure probability (typically 2⁻⁸⁰) and provision an *O*(λ)-block stash [2]. The analysis is worst-case over request sequences, but implementers who shrink *Z* to save bandwidth without redoing the analysis do observe overflows.

**Small blocks break tightness.** The recursion factor log_χ *n* is constant only when many position-map entries fit in one block. For cache-line-sized blocks and large *n*, recursion adds a genuine multiplicative factor; the Ω(log *n*) bound is met asymptotically only for *B* = Ω(log² *n*) [2, 3].

**Timing and termination channels.** ORAM hides *which* addresses are touched, not *when* or *how long* accesses take. Variable-time operations (e.g., background evictions in hierarchical schemes, or data-dependent crypto) leak through timing; secure-processor deployments must pad to constant time [8].

**Malicious servers need more.** The basic tree-based schemes assume a semi-honest server. Integrity against an actively malicious server requires authenticated data structures (Merkle trees over buckets, root in client storage) plus freshness — at additional bandwidth cost [4, 5].

**Server computation is not free.** Onion ORAM's constant bandwidth [5] moves the logarithmic factor into homomorphic operations on the server — concretely expensive with Damgård–Jurik ciphertexts — and changes the trust model.

**Perfect security remains open at the bound.** Whether a perfectly secure (zero-error) single-server ORAM can achieve *O*(log *n*) worst-case bandwidth is unknown; the best known perfectly secure schemes pay more, though recent work narrows the gap.

---

## 7 Conclusion

The asymptotics of access-pattern privacy are essentially settled for the online setting: logarithmic bandwidth overhead is both necessary [1, 6, 7] and sufficient [2, 3], with the bound tight for block sizes *B* = Ω(log² *n*). The frontier has moved from *whether* to *how*: Path ORAM made the optimal scheme simple enough to deploy; Circuit ORAM made it gate-optimal for secure computation; Ring ORAM decoupled bandwidth from bucket sizing and pushed online cost toward constant; Onion ORAM showed that server-side homomorphic computation dissolves the logarithmic barrier entirely. The remaining open problems — perfectly secure logarithmic ORAM, malicious-server integrity at low cost, and taming the constants for cache-line blocks — will decide how widely access-pattern privacy can be deployed.
