# Crash-Consistent Programming for Persistent Memory in the CXL Era: Failure-Atomic Transactions, Persist Barriers, and the Durability Semantics of Disaggregated Memory

## Abstract

Byte-addressable persistent memory collapses the boundary between memory and storage, but imports storage's hardest problem — *crash consistency* — into ordinary loads and stores. This thesis develops a unified treatment of crash-consistent programming as the industry migrates from DIMM-attached non-volatile memory to CXL-attached, fabric-disaggregated memory pools. We formalize the failure-atomic transaction, characterize undo and redo logging as dual strategies for all-or-nothing durability, and dissect the persist barrier — the store/fence/flush choreography that moves the durability frontier from volatile caches into the persistence domain. We analyze how *extended Asynchronous DRAM Refresh* (eADR) enlarges the persist domain to include processor caches, and why CXL-attached memory re-opens settled durability questions: whose power domain owns a flush, how Global Persist Flush propagates across a fabric, and what recovery means when memory outlives every host. Drawing on the lineage from NV-Heaps, Mnemosyne, and Atlas to DudeTM and RECIPE, we derive engineering principles, a cost model of logging overheads, and a research agenda for durability in disaggregated systems.

## 1 Introduction

For fifty years, systems programming rested on a clean dichotomy: memory was fast, volatile, and byte-addressable; storage was slow, durable, and block-addressable. Byte-addressable non-volatile memory — from phase-change memory and STT-RAM prototypes to Intel Optane DC Persistent Memory — shattered it: a program can `mmap` a DAX file, issue ordinary loads and stores, and have those stores survive power failure [1][2].

The consequence is severe. Where block storage mediates durability through `fsync` with block granularity, PM makes the *cache line* the durability unit, governed by a subtle contract between memory ordering, coherence, and power-fail handling. A retired store is *not* durable — it may sit in a store buffer, L1 cache, or controller queue. Durability requires explicit action — `clwb`/`clflushopt`, non-temporal stores, `sfence` ordering — collectively *persist barriers*. Worse, durable order need not match program order: a crash can expose a persisted pointer to an unpersisted object. This is the crash-consistency problem.

Just as the community converged on transactional libraries and failure-atomic sections, the ground shifted: Compute Express Link (CXL) standardizes cache-coherent load/store access to fabric-attached memory, enabling pooled, composable memory at rack scale, with CXL 3.0 adding fabric topologies and cross-host sharing [3]. But CXL durability is murkier than DIMM durability: a host's flush traverses a fabric, the persistence domain spans independent power domains, and memory may be shared by hosts that crash independently. The intellectual core of PM programming — failure-atomic transactions over explicit persist barriers — transfers to the CXL era, provided we generalize the *persistence domain* from a platform property to a fabric-wide, negotiated contract.

Our contributions: (1) a unified model of failure-atomic transactions over an abstract persistence domain; (2) a duality analysis of undo vs. redo logging with a cost theorem; (3) a persist-domain taxonomy from ADR through eADR to CXL Global Persist Flush; (4) a recovery-correctness argument and cost model grounded in published measurements [4][5][6]; (5) a research agenda for disaggregated-memory crash consistency.

## 2 Background and Related Work

### 2.1 The first wave: persistent objects and lightweight transactions

The modern PM literature begins with two ASPLOS 2011 systems. **NV-Heaps** (Coburn et al.) introduced *persistent objects*: a C++ framework guarding against dangling pointers, double frees, and persistence-specific hazards where a bug's corruption is permanent [1], with transactions over persistent objects via undo logging.

**Mnemosyne** (Volos, Tack, Swift) offered compiler-assisted, word-granular persistent variables (`pstatic`) and dynamic allocation [2], reporting 20–280% gains over disk-oriented persistence. Together they established the enduring pattern: *transactions + logging + explicit persist barriers* as the price of crash consistency.

### 2.2 Failure-atomic sections from existing synchronization

Must programmers rewrite code around transactions, or can durability be grafted onto existing synchronization? **Atlas** (Chakrabarti and Boehm, OOPSLA 2014) derived failure-atomic sections from existing *critical sections*: lock-protected regions become implicit transactions recovered by a log-based implementation [4]. It flagged cache flushing as the core bottleneck and, crucially, decoupled the *durability mechanism* from *concurrency control* — a separation DudeTM later made explicit [5].

### 2.3 High-performance durable transactions and converted indexes

**DudeTM** (Liu et al., ASPLOS 2017) decoupled the TM core from the persistency engine: transactions execute on *shadow memory*, flushing only the write set as a redo log tagged with serialization order [5]. Removing persist barriers from the fast path yielded up to 1.7× speedup on write-heavy workloads [5].

**RECIPE** (Lee et al., SOSP 2019) gave three precise *conditions* under which a concurrent DRAM index converts to a crash-consistent PM index with 30–200 lines of mechanical changes [6] — translating *concurrency* invariants into *crash-consistency* invariants. Converted indexes outperformed hand-crafted PM indexes on Optane DC PMM: a portability insight for crossing the durability boundary [6].

### 2.4 Platform support: ADR, eADR, and the persistence domain

Software barriers are half the story; the other half is the platform's *persistence domain* — the components whose contents survive power failure. **ADR** guarantees stores reaching the memory controller's write pending queue are flushed to PM on power loss. **eADR** (3rd-gen Intel Xeon Scalable) enlarges the domain to the full cache hierarchy: power-fail circuitry flushes caches automatically, so software keeps fences but drops flushes [7]. This single change collapses much of the barrier cost model — and previews the CXL question: *who owns the flush when memory is across a fabric?*

| System | Venue | Logging | Key idea |
|---|---|---|---|
| NV-Heaps [1] | ASPLOS 2011 | Undo | Persistent objects + transactions; pointer safety |
| Mnemosyne [2] | ASPLOS 2011 | Undo | Word-granular persistent variables; compiler support |
| Atlas [4] | OOPSLA 2014 | Undo | Failure-atomic sections from lock critical sections |
| DudeTM [5] | ASPLOS 2017 | Redo (shadow) | Decoupled TM core and persistency engine |
| RECIPE [6] | SOSP 2019 | Converted | Mechanical DRAM-index → PM-index conversion |

## 3 Methodology

Our method is *analytic and constructive*: distill a formal model of failure-atomic transactions from the surveyed systems, prove its core invariant, derive a cost model for each logging discipline's barrier traffic, and stress-test the model against CXL disaggregation.

### 3.1 System model

A machine comprises *cores*, a *cache hierarchy*, and a *memory controller* draining into a *persistence domain* 𝒟 — the hardware guaranteed to survive power failure. A **persist barrier** moves data from outside 𝒟 into 𝒟 (flush, non-temporal store, power-fail flush) or orders such movements (fence). A **crash** discards all state outside 𝒟; **recovery** deterministically inspects only 𝒟.

We assume the standard PM hardware contract: (1) aligned ≤8-byte stores are *failure-atomic*; (2) `clwb` moves a line into 𝒟 asynchronously, with `sfence` ordering it before later persists; (3) under ADR the WPQ is inside 𝒟, under eADR the whole cache hierarchy is [7]; (4) crashes are fail-stop per power domain.

### 3.2 The failure-atomic transaction protocol

A transaction *T* is reads/writes bracketed by *begin*, *commit*, *abort*. The undo-logging variant in TLA⁺-style pseudocode:

```tla
------------------------------ MODULE UndoLog ------------------------------
VARIABLES mem, log, status
(* mem: persistent map; log: sequence of (addr, oldval); status \in
   {"active", "committed", "aborted"} *)

Write(a, v) ==
  /\ status = "active"
  /\ log' = Append(log, [addr |-> a, old |-> mem[a]])
  /\ PersistBarrier(log')          \* log durable BEFORE in-place update
  /\ mem' = [mem EXCEPT ![a] = v]
  /\ status' = status

Commit ==
  /\ status = "active"
  /\ PersistBarrier(<<COMMIT, Len(log)>>)  \* commit record durable
  /\ status' = "committed"

Recover ==
  /\ status # "committed"
  /\ mem' = Foldl(ApplyUndo, mem, Reverse(log))
  /\ status' = "aborted"
=============================================================================
```

The *golden rule* in `Write` is **log-before-data**: the undo record must be durable before the in-place update it protects. Every PM bug taxonomy catalogs violations of it: data persisted before its log, a missing fence between them, a commit record before its redo log.

### 3.3 Analytical approach

We derive (i) a duality theorem for undo vs. redo logging, (ii) a persist-domain taxonomy for ADR/eADR/CXL, and (iii) a cost model parameterized by flush latency, fence cost, and log size, instantiated with published measurements [5][6].

## 4 Deep Dive

### 4.1 The Anatomy of a Persist Barrier

A persist barrier is a *choreography* of **movement** (dirty data out of volatile caches), **ordering** (constraining durable sequence), and **completion** (knowing durability holds). On x86-64 with ADR:

```rust
// Failure-atomic 8-byte update of a persistent counter (ADR domain)
unsafe fn pm_add(counter: *mut u64, delta: u64, log: &mut UndoLog) {
    let old = *counter;
    log.append(UndoRecord { addr: counter, old }); // (1) log record
    clwb(log.tail_cacheline());                    // (2) move log to WPQ
    sfence();                                      // (3) ORDER: log before data
    *counter = old.wrapping_add(delta);            // (4) in-place update
    clwb(counter as *const u8);                     // (5) move data to WPQ
    sfence();                                      // (6) ORDER: data before commit
}
```

`clwb` is *movement* (asynchronous); `sfence` is *ordering*, draining prior `clwb`s before later persists — a common error is treating `sfence` as durability itself. Under eADR, steps (2) and (5) vanish since caches are inside 𝒟, but (3) and (6) remain: *eADR removes flushes, not ordering* [7].

With flush latency *F*, fence cost *S*, and *n* updated lines, undo pays ≈ *2nF + 2S* (log + data, each fenced); redo pays *nF + S* plus deferred application — the seed of the undo/redo duality.

> **Lemma 1 (Barrier minimality).** *Any failure-atomic transaction updating n distinct cache lines in place needs at least n ordered persist barriers between its log records and data updates.*
>
> *Proof sketch.* Suppose some line ℓ's data is persisted with no barrier ordering it after its log record. A crash interleaving can then place ℓ's data in 𝒟 without its log record; recovery cannot restore ℓ's pre-transaction value, violating failure atomicity. The argument applies per line. ∎

### 4.2 Undo versus Redo Logging: A Formal Duality

Undo and redo logging are better understood as *duals* than as a mere engineering tradeoff:

- **Undo logging** [1][2][4]: log the *old* value, update in place, commit. Reads see the latest value with no indirection — ideal for read-heavy workloads — but every write pays a log-before-data barrier pair, and recovery *rolls back* uncommitted transactions by reverse replay.
- **Redo logging** [5]: execute against shadow copies, log the *new* value, persist the log, commit, then apply in place. Writes pay only log barriers; reads may need shadow indirection; recovery *rolls forward* committed transactions and discards the rest.

> **Theorem 1 (Logging duality).** *For a transaction with read set R and write set W, let Cᵤ, Cᵣ be the persist-barrier costs of undo and redo logging. Then Cᵤ − Cᵣ = |W|·(F + S) − |R ∩ W|·I, with flush cost F, fence cost S, and shadow-read indirection cost I. Redo strictly dominates when |W| is large relative to read-write overlap; undo dominates for read-heavy transactions with small write sets.*
>
> *Proof sketch.* Undo pays one log-barrier pair per written line (Lemma 1), zero read indirection. Redo pays one barrier per logged write but no log-before-data pair, saving |W|·(F+S); it pays I per read consulting shadow state. Subtracting yields the identity. ∎

This explains the empirical landscape: Atlas's small critical-section writes favor undo [4]; DudeTM's write-heavy transactions favor redo, measuring the predicted 1.7× gain [5]. Recovery cost mirrors commit cost: undo recovery scales with *uncommitted* write volume at crash time; redo recovery with *committed-but-unapplied* volume.

| Dimension | Undo logging | Redo logging |
|---|---|---|
| Log content | Before-images | After-images |
| Golden rule | Log durable *before* data update | Log durable *before* commit record |
| Read path | Direct | May consult shadows |
| Write barriers | Log + data, fenced apart | Log only; deferred apply |
| Recovery | Roll back uncommitted | Roll forward committed |
| Exemplars | NV-Heaps [1], Atlas [4] | DudeTM [5] |

### 4.3 Persist Domains: ADR, eADR, and the CXL Problem

The persistence domain 𝒟 is the most consequential, least standardized concept in PM programming. Under **ADR**, 𝒟 = {PM media, controller WPQ}: software flushes every dirty line. Under **eADR**, 𝒟 includes the cache hierarchy with automatic power-fail flush; software keeps fences, drops flushes [7].

CXL-attached memory breaks both models' assumptions:

1. **Whose power domain?** A CXL Type 3 expander may sit in a different power domain than the host. ADR's residual-energy flush is a bilateral controller–DIMM contract; across a fabric the flush must be *requested* (Global Persist Flush) and *acknowledged* — a distributed commit inside a formerly local guarantee.
2. **Ordering across the fabric.** `sfence` orders persists within the issuing core's coherence domain. When 𝒟 spans a CXL switch and device caches, the primitive must be fabric-aware: a host `sfence` does not order a device's internal writeback. CXL 3.0 provides the transport, but durability *ordering semantics* remain a software-visible gap [3].
3. **Multi-host sharing.** CXL 3.0 pools memory across hosts [3]. If host A crashes mid-transaction while B continues, whose recovery runs, against which log? We need *per-host failure-atomicity* composed over shared 𝒟 — distributed transactions at cache-line granularity.
4. **The eADR mirage.** Even if a CXL device implements eADR-like semantics internally, the host cannot observe them: 𝒟's boundary is wherever the GPF handshake says it is. Persist domains must be *negotiated and discoverable* (e.g., NFIT extensions), not fixed platform properties.

> **Lemma 2 (Fabric persist barrier).** *In a CXL-attached persistence domain, a host-issued persist barrier completes only when every fabric component on the path has acknowledged durability. Its latency is lower-bounded by the fabric round-trip time, not local flush latency.*
>
> *Proof sketch.* Data is durable only inside 𝒟. If any on-path component (switch buffer, device cache) is outside the guaranteed-flush set, unacknowledged data may be lost on that component's power failure. Completion requires end-to-end acknowledgment, including the full fabric round trip. ∎

Corollary: re-parameterize Section 4.1 with fabric-aware flush latency *F꜀ₓₗ* ≫ *F*. Barrier-*count*-minimizing disciplines — redo logging, batched group commit — gain systematically as *F* grows: a quantitative case for redo-style designs in disaggregated PM.

### 4.4 Recovery Protocols and Log Reclamation

Recovery has three phases: (i) **log scan** — classify transactions via commit records from the last checkpoint; (ii) **replay** — roll back (undo) or roll forward (redo); (iii) **reclamation** — truncate/checkpoint so the log stays bounded.

Two subtleties: *torn commit records* — the commit record must itself be failure-atomic (8-byte store or checksummed record), else recovery cannot classify the transaction; and *idempotent replay* — recovery may itself crash, so replay must be restartable. Before-image restoration is naturally idempotent; redo of non-idempotent updates needs care.

RECIPE is a recovery argument in disguise: its conditions are exactly when *no recovery is needed* — crashes leave the index consistent by construction or repairable by a concurrent helper [6]. This *recovery-free crash consistency* is the gold standard: prefer structures whose invariants are closed under arbitrary crash interleavings, reserving logging for the residue.

## 5 Empirical Evaluation / Formal Proofs

### 5.1 Correctness: the crash-consistency invariant

> **Theorem 2 (Crash consistency of the undo protocol).** *Every reachable post-recovery state of the Section 3.2 protocol equals the result of executing some prefix of committed transactions — i.e., the system is failure-atomic.*
>
> *Proof sketch.* Invariant: 𝒟 always holds (a) every active transaction's log records, each durable before its protected update (golden rule in `Write`), and (b) a commit record for *T* only if *T*'s full log is durable (barrier in `Commit`). On crash, recovery rolls back all transactions lacking commit records — by (a) their before-images are present, restoring pre-transaction state exactly. Committed transactions are left in place: by (b) their updates are fully logged and were issued, so the state reflects precisely the committed prefix. 8-byte atomicity rules out torn single-word updates; multi-word updates are covered by undo records. ∎

The redo variant admits a dual theorem: "log before data" becomes "log before commit record," "roll back uncommitted" becomes "roll forward committed." Identical proof structure — the duality of Theorem 1 holds at the correctness level too.

### 5.2 Analytical cost model

DudeTM's decoupling reports up to 1.7× speedup on write-heavy workloads, consistent with Theorem 1's prediction that savings scale with |W| [5]. RECIPE's 30–200 lines per index yields competitive PM indexes, validating "convert, don't rebuild" [6]. Mnemosyne's 20–280% gains bound the upside of byte granularity [2].

Projecting to CXL via Lemma 2: if *F꜀ₓₗ* ≈ 3–5× local *F*, barrier traffic dominates and Theorem 1's crossover shifts toward redo logging and batched commits. Disaggregation does not merely add latency — it *changes the optimal logging discipline*:

```python
def crossover(n_writes, n_reads, F, S, I, fabric_penalty=1.0):
    """Positive favors redo: barriers saved minus extra read indirection."""
    F_eff = F * fabric_penalty
    return n_writes * (F_eff + S) - n_reads * I

print(crossover(100, 900, F=90, S=25, I=15))                 # local ADR domain
print(crossover(100, 900, F=90, S=25, I=15, fabric_penalty=4.0))  # CXL-attached
```

The model omits reclamation amortization and NUMA effects, but captures the first-order pressure fabric latency exerts.

## 6 Limitations and Open Problems

**Single-host model.** One crash domain, one recovery agent. CXL multi-host sharing needs a compositional theory of per-host failure atomicity over shared 𝒟; interaction with back-invalidate coherence flows is open [3].

**No partial-media failures.** Fail-stop crashes, intact media assumed. Real PM suffers media errors and silent corruption; checksums and replication are essential but outside our model.

**Underspecified fabric barrier.** GPF handshake semantics, timeouts, and switch failure modes are platform-specific. A portable model needs a *discoverable* persist-domain description — today's firmware tables are a start, not a solution.

**Verification gap.** Theorem 2 is a proof sketch; machine-checked verification of PM transaction libraries remains rare, and crash-interleaving model checkers cover only small configurations.

**Endurance.** Our model counts latency, not wear. Undo logging doubles PM write traffic; on finite-endurance media the discipline is also a *lifetime* decision — barely quantified.

**Usability.** Atlas grafted durability onto locks [4], RECIPE made conversion mechanical [6], but no general-purpose type-safe PM language exists. Rust's ownership fits persistent-object safety (cf. NV-Heaps [1]); a borrow-checked PM framework remains open.

## 7 Conclusion

Crash-consistent PM programming rests on three ideas: the *failure-atomic transaction* as the unit of durability, the *persist barrier* moving the durability frontier, and the *persistence domain* defining "durable." Undo and redo logging are dual strategies governed by a cost identity (Theorem 1); correctness reduces to small ordering invariants (Theorem 2); and the ADR → eADR [7] → CXL [3] migration is a sequence of *expansions and redistributions* of the persistence domain — each removing software barriers while adding fabric-scale ordering obligations (Lemma 2).

The moral is twofold. First, the DIMM era's lessons — log before data, fence what you flush, make recovery idempotent, prefer crash-closed structures [1][2][4][5][6] — transfer to disaggregated memory: they are statements about *ordering*, which no fabric provides for free. Second, disaggregation changes the *optimum*: as barrier latency grows, barrier-count-minimizing designs gain a systematic edge. The frontier is a *compositional durability theory* for shared, fabric-attached PM: per-host failure atomicity, discoverable persist domains, verified recovery at rack scale. The memory will outlive the hosts; our abstractions must survive them too.
