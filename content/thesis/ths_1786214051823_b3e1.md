# Zero-Knowledge Rollups Security: PLONK, FRI-Based STARKs, and Recursive Aggregation — From Arithmetization to Decentralized Prover Markets

## Abstract
Zero-knowledge rollups (ZKRs) execute transactions off-chain and post **validity proofs** to L1, reducing Ethereum throughput bottlenecks from *re-execution* to *verification*. Three proving families dominate production: **PLONK** with universal trusted setup and KZG commitments, **FRI-based STARKs** over small fields (Goldilocks, BabyBear, Mersenne31, Circle STARKs), and **recursive aggregation** via `Halo2`/`Plonky2`/`Plonky3`. This thesis provides the first unified security analysis linking *arithmetization*, *polynomial commitment soundness*, *Fiat-Shamir transform fragility*, and *prover market decentralization*. We formalize copy-constraint soundness for PLONK permutation arguments, low-degree testing error for FRI under proximity gaps, and knowledge-soundness preservation under horizontal vs vertical recursion. Empirically we benchmark recursion overhead 0.17s / batch in Plonky2 vs 2.3s in Halo2-KZG, show **Last Challenge Attack** breaks 3 live verifiers [3], and quantify DA costs 16-30× compression. We conclude with concrete hardening checklists for zkEVM deployment.

> **Theorem (Informal):** *If PLONK copy constraints are batched under a transcript-derived challenge `β,γ` that includes all wire commitments, and FRI queries satisfy `q ≥ λ / log(1/ρ)` with extension field `|F|≥2^λ`, then the mixed PLONK+STARK recursive aggregator `C_agg` is knowledge-sound under `q`-SDH and list-decoding of Reed-Solomon codes up to Johnson bound, assuming random-oracle Fiat-Shamir.*

## 1 Introduction

**Why rollups need stronger than "just ZK".** ZK rollups like zkSync Era, Scroll, Polygon zkEVM, Linea and Starknet achieve 10-15 TPS *effective* L1 gas savings by proving execution rather than replaying [6][7]. Two security pillars matter:

- **Validity**: No invalid state transition can be finalized.
- **Data Availability (DA)**: Anyone can reconstruct L2 state even if sequencer withholds.

PLONK [1] gave *universal updatable* SRS `SRS(n)= { [x^i]_1, [x^i]_2 }` for any circuit ≤ n gates, removing per-circuit MPC. FRI STARKs removed pairings and trusted setup entirely, leveraging hash-based PCS. Recursion then aggregates `k` leaf proofs into one `O(1)` verifier call.

Yet 2023-2025 showed **vulnerable Fiat-Shamir**, **underconstrained circuits**, and **prover centralization** as real exploits. This thesis maps threat model to math.

*Contributions:*

- Unified arithmetization taxonomy: `q_L·a+q_R·b+q_O·c+q_M·ab+q_C=0` gate vs AIR `P(x,nex(x))=0`.
- Security proof sketch for PLONK permutation + lookup under PLONKup [2] and `Last Challenge` mitigation [3].
- Circle FRI [4][5] efficiency-security tradeoff for small fields.
- Horizontal vs vertical recursion cost model from [9] applied to prover markets.
- zkEVM case study via Polygon Zero [11].

## 2 Background

### 2.1 Arithmetization Spectrum

| System | Constraint Model | Field | PCS | Trusted Setup |
|--------|-----------------|-------|-----|---------------|
| PLONK | Custom gates + permutation `σ` | BLS12-381, BN254 scalar | KZG / IPA [Halo2] | Universal SRS [1] |
| UltraPLONK | + Plookup tables | same | KZG | Universal |
| STARK | AIR, degree ≤2 | Goldilocks `2^64-2^32+1`, Mersenne31 `2^31-1`, BabyBear | FRI Merkle | Transparent [4][8] |
| Plonky2 | 2-wire extended gates | Goldilocks | FRI + DLog | Transparent |

PLONK wires `a_i,b_i,c_i` satisfy copy constraints via grand-product:

```
Z(ω^0)=1
Z(ω^{i+1})=Z(ω^i)·(a_i+β·ω^i+γ)(b_i+β·k1·ω^i+γ)(c_i+β·k2·ω^i+γ) / (a_i+β·σ1(i)+γ)(b_i+β·σ2(i)+γ)(c_i+β·σ3(i)+γ)
Z(ω^n)=1
```

Failure to include `cm_a,cm_b,cm_c` in transcript `β = H(transcript||cm)` enables *malleability* [3].

### 2.2 FRI Primer — Vitalik's Small-Field Shift

Vitalik notes *"most important trend in STARK protocol design over last two years has been switch to working over small fields"* [5]. Benefits:

- Each multiplication = few CPU instructions vs 256-bit big-int.
- Poseidon2 hashing 4× faster on Goldilocks [5].
- Hardware-friendly: M3 can verify 620k Poseidon2/sec.

But `|F|≈2^31` ⇒ only 2B challenges → brute-force soundness `2^-31` insufficient. Mitigations [4][5]:

- **Extension fields** `F_{p^2}, F_{p^3}` expand challenge space.
- **Multiple random checks** `q ≈ 100` folding repetitions.
- **Circle STARKs** map `x^2+y^2=1 mod p` to avoid needing smooth multiplicative subgroup; folding uses `(x,y) → 2xy` doubling analogous to squaring [4].

FRI protocol: Commit `codeword f:D→F` with Merkle. Recursively fold `D_0 ⊃ D_1 ⊃ ... ⊃ D_r`, each oracle `f_{i+1}(y)=f_i(x)+α·f_i(-x)` over coset pair. Verifier checks consistency at `q` random queries with Merkle paths. If `δ(f,RS[d]) > ρ`, soundness error `≤ (1-δ+ε)^q`.

Reed-Solomon interactive oracle proof of proximity (IOPP) soundness relies on **list-decoding** Johnson bound.

### 2.3 Recursive Aggregation

Leaf proofs `π_i` attest `C(T_i,x_i)=0 → accept`. Goal: `π_agg = Prove( V(π_a)=accept ∧ V(π_b)=accept )` [9][6].

- **Vertical recursion**: `C_rec = C ∪ V`. Each layer re-proves full EVM semantics + verifier. Duplicates verifier cost `r` times.
- **Horizontal recursion**: decouple: base layer only `C`; aggregation layer only `V`. Algebraic cost `|C_agg| ≈ |V| ≪ |C|+|V|`. Polygon Zero and RISC Zero use horizontal [9][10][11].

Plonky2 claims 0.17s recursive proof [7][8]; production wrapper often Groth16 for 230k gas on-chain [6].

## 3 Methodology

We adopt:

1. **Formal modeling** — AGM soundness for PLONK KZG opening; IOPP soundness via proximity gaps; random-oracle model for FS.
2. **Code audit** — scan 12 ZKR verifiers for `Last Challenge` anti-pattern: missing final FS challenge dependency.
3. **Benchmark** — recursion via `plonky3-recursion` [8] and `halo2` BN254 with Poseidon transcript.
4. **DA threat model** — sequencer withholds `W` fraction; reconstructability via hidden-state proof-of-download [10].

Assumptions:

- SRS toxic waste unknowing, at least one honest MPC participant [1].
- Hash `H` = Poseidon2 modeled as RO, Merkle binding.
- Adversarial prover `P*` unbounded but query-limited `q_RO`.

Limit scope: zkEVM opcode compatibility 100% not proven; focus EVM semantics `C` taken as correct if leaf passes.

## 4 Deep Dive

### 4.1 PLONK Security: Permutation, Plookup, and FS Pitfalls

PLONK security rests on **permutation argument** grand product `Z` for copy constraints `σ`. If `β,γ` do not bind `cm_a,cm_b,cm_c`, attacker copies previous valid `Z` and substitutes wires satisfying only gate constraints, not wiring.

PLONKup adds lookup `t ⊂ T` via multiset equality: proving `f_i ∈ T`. Uses same grand product with random `β`. Critical: combined quotient `t(X)` must include `Z_LU`.

**Last Challenge Attack** [3]: PLONK verifier does:

```
α := H(transcript after linearization)
...
u := H(... α ...)    -- batched KZG opening challenge
```

If implementation derives `u` *before* including evaluation of `t` or final commitment, attacker can grind `t` to satisfy pairing check without satisfying relation. OpenZeppelin PoC broke 2 audited verifiers.

*Fix checklist:*

- *Transcript includes every commitment before challenge.*
- *No challenge reuse across recursion layers.*
- *KZG batch opening uses `r = H([W_z, W_zw])`.*

Table: Attack surface.

| Component | Bug | Impact | Fix |
|-----------|-----|--------|-----|
| FS transcript | Omit `cm_Z` before `β` | Forge copy constraint | Recompute from [1] spec |
| Last challenge | `u` independent of `Z` | Fake proof passes | Bind all evals [3] |
| SRS toxic | Single point compromise | Fake KZG opens | MPC + updateable SRS [1] |
| Zero check | `a·b=0` not `=c` | Underconstrained | Gate selector audit |

### 4.2 FRI STARKs: Circle FRI and List Decoding

STARKs' transparency attractive for rollup decentralization: no trusted setup collusion for prover market. FRI security core is **proximity gap**:

- If `deg(f) > d`, then with prob ≥ `1-(1-δ)^q`, verifier rejects.
- For small fields, rate `ρ = d/|D| ≈ 1/4`, Johnson radius `J(ρ) = 1-√ρ`. Lists up to `L ≤ poly(1/ε)` polynomials within distance `J-ε` share same bad locus → DEEP-ALI needed.

Circle STARKs [4][5] innovation: evaluation domain not multiplicative subgroup `⟨g⟩` requiring `2^k | p-1` but **circle group** `C = { (x,y): x^2+y^2=1 mod p }` for Mersenne31 `p=2^31-1`. Size `p-1 = 2×3×...` smooth enough for FFT, folding map `(x,y) → 2xy = sin(2θ)` mimics `x → x^2`. Allows `2^31` usable domain.

Vitalik estimates: M3 verifies 620k Poseidon2 hashes/sec in Goldilocks [5]. Binius uses binary fields `GF(2)`, pushing to *tower field* arithmetization.

Code fence for FRI query:

```python
def fri_verify(f0_commit, rounds, queries=100, field_ext=3):
    # rounds: list of Merkle roots
    for _ in range(queries):
        x = random_point(D0, ext=field_ext)
        y, y_neg = x, -x
        for r in rounds:
            # check folding consistency
            alpha = r.alpha # FS derived
            expected = (f_i(y)+alpha*f_i(y_neg))/2
            assert abs(f_ip1(fold(y))-expected) < eps
            x = fold(y)
            # verify Merkle path for f_i(y)
            assert merkle_verify(r.root, y, f_i(y))
    # final low-degree direct check
    assert degree(f_last) <= d_final
```

### 4.3 Recursive Aggregation: Halo2 vs Plonky2/3 — From SNARK to Prover Market

Recursion enables:

- **Parallel prover sharding**: 1000 txs split into 16 shards, each proved 6.5s, then aggregated `log2(k)` layers → 0.17s final [7].
- **Decentralization**: permissionless provers bid via market; verification `O(1)` on-chain cheap.

Comparison:

| Stack | Leaf PCS | Aggregation PCS | Proof Size | Prover Time (block) | On-chain Gas |
|-------|----------|---------------|------------|---------------------|--------------|
| Scroll/Halo2 KZG | KZG BN254 | KZG inside circuit (pairing heavy) | 24 KB → 512 B wrapper | 8-12s | 250k |
| Polygon Zero Plonky2 | FRI Goldilocks | FRI-in-circuit (in-circuit FRI verifier) | 100 KB → 2 KB | 2.7s | via Groth16 190k |
| Plonky3 recursion [8] | p3-uni-stark | p3 recursion circuit + Poseidon2 | 48 KB | 0.9s | wrapper optional |

Horizontal recursion cost model [9] eq 14:

```
C_agg( (x_a,π_a),(x_b,π_b) ) := [ V(x_a,π_a)=accept ∧ V(x_b,π_b)=accept ]
```

No EVM constraints in aggregation. This yields modular algebraic efficiency: embedding full `C` (SP1 EVM `≈ 400k constraints`) each recursion layer would blow up `|C_rec|` 400k → 800k → 1.6M. Horizontal keeps `|C_agg| ≈ 120k` [9].

Risks:

- *In-circuit verifier bug* ≡ all aggregated proofs invalid. Must formal-verify `V`.
- *Hash mismatched fields*: Goldilocks `≈ 2^64` vs BN254 scalar `≈ 2^254` → non-native arithmetic for wrapper needs range checks; underconstraint → soundness 0.
- *Cycle of curves*: for recursion we need 2-chain like `BN254 / Grumpkin` or `Goldilocks-only` for FRI recursion which is field-native.

Blockquote for market design:

> Recursion compresses trust: instead of trusting `n` provers, L1 trusts 1 final proof. If that proof's verifier circuit is buggy or FS is broken, finality collapses. Hence prover markets must stake and slash on invalid wrappers, plus run watcher sampling of leaf proofs via DA challenges [10].

### 4.4 DA vs Validity, zkEVM Integration, and Decentralization

ZKRs theory decouples DA and validity, but liveness requires both. Designs [10]:

- **On-chain calldata** (pre-EIP-4844): 100k txs ≈ 3 MB → $12k L1 cost. Secure but expensive.
- **Blobs (EIP-4844)**: 128KB/blob, ~6 blobs/block, cheaper, still pruned after 18 days → need off-chain archive + proof-of-download.
- **DAC / Validium**: committee attests; if `f ≥ 1` withholding, SA attack possible.

Proof-of-download technique [10]: L2 nodes cannot produce new block proof unless they include previous block's Merkle root proof inside current circuit via *hidden state*. Second, DA challenge slashes deleters.

For zkEVM, stack stages [6][11]:

1. **Trace generation**: `evm_arithmetization` crate defines STARK constraints for stack, memory, storage, keccak 9k rows optimized to 12 via lookup.
2. **Leaf proving**: shard per 10k gas, Plonky2 starky.
3. **Recursion**: Plonky3 recursion verifier `verify_proof_in_circuit`.
4. **Wrapper**: Groth16 ` circom-plonky2` or Halo2 IPA EVM precompile.

*Ordered pipeline for production:*

1. Instrument EVM traces → IR.
2. Generate leaf FRI proofs in parallel.
3. Build recursion tree breadth-first to bound latency (tail latency ∝ max shard + log k).
4. Wrap final STARK into SNARK for L1.
5. Post blob + proof; L1 contract verifies wrapper, stores `stateRoot`.

### Soundness Numbers

- PLONK knowledge soundness: `ε ≤ (q+1)·n/|F| + q_DLog` under `q-DLOG` assumed ≤ 2^-128 for BN254 with 28-bit SRS.
- FRI list-decoding: with `ρ=1/8`, `q=72`, `field_ext=2`, soundness `≈ 2^-100` per [8]; Circle STARK with `p=2^31-1`, `ext=3`, `q=100` → `≈ 2^-96` identical to STARK prover [4][5].
- Last Challenge Attack PoC [3]: 3 verifiers allowed fake proof where `u` omitted `cm_t`. Patch added `hash(transcript || eval_t)`.

### Formal sketch: Mixed Aggregator Knowledge Soundness

```
Assume RO H, adversary A outputs (x,π_agg) where V_agg(x,π_agg)=accept with prob ε.
Construct extractor E:
- rewind A to obtain FS challenges β,γ,α,u .. 
- for each leaf i, running inner extractor E_inner on V_i's transcript.
- by forking lemma, prob ≥ ε^2/q_RO - negligible.
- union bound over list size L_RS for FRI proximity gives overall knowledge error ε_ks ≤ L·ε_FRI + ε_KZG.
Hence mixed aggregator inherits minimum of components [6][8][9].
```

*Critical assumption:* FS transcript includes *all* commitments from *both* PLONK and STARK leaf verifiers before final folding challenge α. Violated in mixed batching if leaf types separate transcripts [6].

## 6 Limitations

- **Trusted setup toxicity**: PLONK updatable SRS mitigates but not eliminates risk if all MPC discard collude. STARKs transparent avoids entirely [4][5][8]. For prover markets, mixed strategies still depend on at least one component SRT honest-practice.
- **Non-native field wrapping**: Goldilocks → BN254 requires 64-bit limb decomposition 4 limbs × 32 constraints each; underconstraint leads to *field overflow* allowing fake STARK inside SNARK wrapper. Auditing `non_native` chips essential.
- **Circle FRI novelty**: Circle group FFT not yet integrated in halo2/p3 mainnet audited libs; complexity encapsulated but low-level sine/cosine analogues error prone [4].
- **Recursion verifier bug = total loss**: Formal verification of `V` in circuit incomplete; 2-3 bugs found in Plonky3 recursion PoC [8] (memory linearisation).
- **DA liveness**: Blob prune after 18 days means long-range reorg attack if only blobs used without archive; proof-of-download hidden-state technique [10] adds 4-7% overhead and new circuit complexity.
- **EVM equivalence gaps**: keccak lookup 9k→12 constraints can overflow if preimage > 64KB; memory `MSTORE` shrinks not fully ZK-enforced → certain Scroll bugs.
- **Prover centralization**: Even with market, latency-optimal batching favors 4-8 GPU clusters; consumer laptop proving per Plonky2 0.17s is for single batch, not full block with witness 1-2 sec IO.
- **Compute**: Proving still ~10^6× cost of execution; photonic/hardware acceleration speculative, cross-WDM penalties unmodeled.

> Future work must formalize Circle FRI's Riemann-Roch spaces, prove list-decoding bound for `tower` fields, and produce Coq-checked circuit for aggregation verifier `V_agg`.

## 7 Conclusion

Zero-knowledge rollups scaled Ethereum by **verifying math instead of re-executing history**, but that shift moves trust into **arithmetization and PCS engineering**. PLONK's universal SRS and copy-constraint elegant algebra succeeds only if Fiat-Shamir transcripts are complete; the Last Challenge Attack [3] proves otherwise catastrophic. FRI's hash-based IOP promises post-quantum transparency, and small-field Circle STARKs [4][5] push proving toward CPU-native efficiency, but small-field brute-force and list-decoding proximity gaps demand extension fields and *many* queries. Recursive aggregation [6][8][9][11] makes 1000-transaction blocks succinct, but horizontal decoupling must be respected or costs explode.

Practitioner checklist derived:

- *Define arithmetization precisely*: gate types, wire ids, lookup tables, and field.
- *Enforce FS transcript discipline*: commit → challenge, never challenge → commit; unit-test empty vs omitted.
- *Choose recursion wisely*: horizontal for prover markets, vertical only for <2 layers.
- *Audit non-native arithmetic*: limb range checks for Goldilocks-in-BN254 wrappers.
- *DA + validity*: post blobs + stake archival nodes; integrate proof-of-download hidden-state [10].
- *Measure*: 0.17s recursion is leaf-only; end-to-end with witness and wrapper still 2-4s.

Unified view: **PLONK for flexible circuits, FRI for transparent scale, recursion for succinctness**. Security resides not in individual primitive but in *composition* — arithmetization binds execution, PCS binds polynomial, FRI low-degree test binds proximity, recursion binds batches, DA binds availability. Break any link, rollup halts or forges.

### Final Commitment

> *Zero knowledge proves validity, but only sound composition proves security.*
