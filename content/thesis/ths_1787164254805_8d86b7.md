# Encrypted Search via Oblivious RAM and Structured Encryption: Path ORAM Recursion, FuturORAM Parallelization, Three-Choice Allocation for Searchable Symmetric Encryption, and Forward-Secure Conjunctive Queries

## Abstract
We present a unified treatment of encrypted search primitives that hide access patterns at both block and query level. Beginning from Goldreich–Ostrovsky Oblivious RAM lower bounds and the optimal logarithmic bandwidth of Path ORAM [1][2], we dissect recursive position-map compression, stash analysis via Chernoff occupancy, and the Maples attack mitigations. We then extend to parallel obliviousness via FuturORAM and recent OptORAMa constructions [4][7] that reduce depth to doubly-logarithmic by hierarchical reshuffling and deterministic cuckoo hashing. The second arc bridges ORAM to Structured Encryption: we analyze single-keyword SSE leakage profiles L1–L3, Cash et al. OXT conjunctive cross-tags [5], and three-choice allocation variants of Kamara-Papamanthou-Roeder [6] that achieve O(1) locality with o(N) server storage. Finally we synthesize forward-secure dynamic SSE via Bost et al. Σoφoς [8], puncturable PRFs, and backward-privacy types, showing how ORAM can encapsulate TSet for volume-hiding conjunctive search with sublinear worst-case overhead.

## 1 Introduction

> **Theorem 1 (Goldreich-Ostrovsky Lower Bound):** Any oblivious simulation of RAM with $n$ blocks and client storage $m \le n^{1-\epsilon}$ requires $\Omega(\log n)$ bandwidth overhead in the balls-and-bins model.

Encrypted search must hide *what* is accessed and *how* it is accessed. Two traditions have evolved largely independently: **Oblivious RAM (ORAM)** hides block addresses for general-purpose RAM computation [1][3], while **Searchable Symmetric Encryption (SSE)** hides keyword-document relationships for inverted indexes [6][5]. Recent cloud deployments observe that naive SSE leaks access and volume patterns sufficient for full recovery attacks via injection or co-occurrence [10], compelling a convergence of the two lines.

Path ORAM [1][2] remains the most deployed ORAM due to extreme simplicity: server stores a binary tree of encrypted buckets, client holds a position map and small stash. This paper revisits Path ORAM's correctness proof and recursion trick that reduces $O(N)$ client map to $O(1)$ at cost of $O(\log N)$ multiplicative overhead, then examines parallel generalizations—Circuit ORAM, RingORAM, and most recently **FuturORAM** [4]—that decouple eviction scheduling from request parallelism.

In parallel, SSE advanced from Curtmola et al. single-keyword index to OXT (Oblivious Cross-Tags) [5] supporting conjunctive queries $w_1 \wedge \dots \wedge w_q$ with cost $O(|DB(w_1)|)$. To achieve sublinear worst-case for arbitrary Boolean queries, Kamara-Moataz IEX and Cash-Jutla-Patranabis JXT introduced bin-packing allocations and three-choice hashing reminiscent of BOSCH. Forward privacy—defined by Stefanov et al. and formalized by Bost, Minaud, Ohrimenko [8]—prevents linking updates to prior search tokens, critical for defeating file-injection attacks. We show how combining ORAM-wrapped TSet, puncturable PRFs, and per-keyword state counters yields forward-secure conjunctive SSE with Type-II backward privacy.

**Contributions:**
- Unified bandwidth and client-storage analysis for recursive Path ORAM with $Z=4$, stash bound $O(\log N)\cdot \omega(1)$ [2].
- Deconstruction of FuturORAM's two-phase leveling and dependency-graph scheduler enabling $c$-parallel clients with $O(\log N + c \log c)$ overhead [4].
- Three-choice allocation analysis for SSE locality: reduces read efficiency from $O(\log N)$ to $O(1)$ with $(1+\epsilon)N$ storage [6][9].
- Construction FSQ-Conj: forward-secure OXT with ORAM-hidden XSet, achieving $O(a_{w_1} + \sum r_i)$ conjunctive search where $a_{w_1}$ is update count for s-term.
- Empirical leakage evaluation on Enron (500k emails): quantifies keyword-pair result pattern (KPRP) reduction from $O(|DB(w_1)\cap DB(w_2)|)$ to statistical $negl(\lambda)$ via volume-hiding padding.

## 2 Background

### 2.1 ORAM Definition
An ORAM consists of $(Setup, Access)$ where $Setup(1^\lambda, N)$ outputs server state $\mathsf{ST}_S$ and client state $\mathsf{ST}_C$. $Access(op, addr, data)$ obliviously reads/writes $addr$. Security: for any two equal-length logical access sequences $\vec{y_1}, \vec{y_2}$, their physical access patterns $A(\vec{y_1}), A(\vec{y_2})$ are computationally indistinguishable.

Goldreich-Ostrovsky [3] introduced hierarchical ORAM with $O(\log^3 N)$ overhead: levels $0..L$, each level $2^i$ times larger, reshuffled via oblivious sort. Larsen-Nielsen [7] proved $\Omega(\log N)$ lower bound for online ORAM with $poly\log$ client memory.

### 2.2 Searchable Symmetric Encryption
SSE [6] encrypts an inverted index $EDB = \{{DB(w)\}}_{w\in W}$. Setup generates $K$, encrypted database $EDB$. Search token $\tau_w \leftarrow Token(K,w)$ enables server to return $DB(w)$ without learning $w$ beyond leakage $\mathcal{L} = (\mathcal{L}_1(DB), \mathcal{L}_2(q))$ where $\mathcal{L}_1$ is number of docs/keys, $\mathcal{L}_2$ search/access pattern.

Cash et al. OXT [5] extends to conjunctive: TSet stores $(w, id)$ tuples, XSet stores $xtag = g^{F(K_X,w)\cdot xind}$. Search for $w_1 \wedge w_2$ retrieves candidates for least-frequent $w_1$ then filters via DDH checks in XSet without learning which survive, except KPRP leakage $|DB(w_1)\cap DB(w_j)|$.

### 2.3 Forward-Security

Bost [8] defines forward privacy: $Update(op, w, id)$ leakage must not leak $w$. Backward privacy types:

- **Type I:** leaks when deletions happened but not what was deleted.
- **Type II:** leaks number of deletes per keyword.
- **Type III:** leaks deletion time for deleted entries.

Achieved via stateful $ST_c$ counter and trapdoor permutation $ST_{c+1} = \pi^{-1}(ST_c)$.

## 3 Methodology

### 3.1 Path ORAM Construction Re-Derived

We implement Path ORAM with $N=2^L$ blocks, bucket size $Z=4$, tree height $L=\lceil \log_2 N \rceil$. Position map $pos: [N] \to \{{0,1\}}^L$.

```
Access(a, op, data*):
  x ← pos[a];  pos[a] ←$ {{0,1}}^L
  S ← ReadPath(x)          // Z(L+1) blocks
  tmp ← S ∪ Stash
  if op==write: tmp[a]=data*
  S' ← GreedyEvict(tmp, x) // push blocks as deep as possible
  WritePath(x, S')
  return tmp[a] to client
```

**Recursion:** Store $pos$ in smaller ORAM $ORAM_1$ of $N_1 = N/\chi$ blocks where $\chi = B/(2(L+1))$. Repeating $O(\log_{\chi} N)$ times yields client storage $O(1)$. Bandwidth $O(BZ\log N / \beta)$ where $\beta$ is recursion factor.

> **Lemma:** For $B = \Omega(\log^2 N)$, recursive Path ORAM bandwidth is $8Z B \log N$ bits per access, stash overflow probability $N^{-\omega(1)}$ for stash size $2\omega(1)\log N$.

Proof follows Chernoff bound on bucket occupancy plus overflow queue.

### 3.2 FuturORAM and Parallel ORAM

FuturORAM [4] observes hierarchical ORAM reshuffles dominate cost. It splits $\log N$ levels into $c$ epochs and pre-computes permutation seeds for future accesses. Key innovation: *levels compete for eviction bandwidth via lazy write-back*.

We model $c$ clients issuing parallel accesses $\vec{op}$. Dependency graph $G$ has node per bucket read; edge $u\to v$ if $v$'s eviction needs $u$'s path. FuturORAM scheduler topologically sorts epochs:

```python
def parallel_access(batch: List[Op]):
    paths = [pos_map[op.addr] for op in batch]
    # Phase 1: read in parallel
    blocks = par_read(paths)  # O(Z log N) per op, no locks
    # Phase 2: assign fresh random leaves
    new_leaves = prf_batch(batch)
    # Phase 3: oblivious merge into stash levels
    stash = merge_sort(blocks, Stash)
    # Phase 4: concurrent write-back with level locks
    par_evict(stash, new_leaves, levels_available=c)
```

Bandwidth reduces from $O(c \log^2 N)$ to $O(c \log N \log\log N)$ for $B = O(\log N)$ via three-way cuckoo hashing inside each level.

### 3.3 Three-Choice Allocation for SSE

To avoid ORAM $\log N$ factor per keyword lookup, BOSCH framework uses allocation. For each keyword $w$, list $DB(w)$ is split into chunks of size $p=O(\log N)$. Allocator chooses $3$ bins $h_1(w), h_2(w||1), h_2(w||2)$ via PRF, places each chunk in least-loaded bin. Theorem from Mitzenmacher:

> Max load $\le \lceil m/n \rceil + O(\log\log n)$ w.h.p. for 2-choice, and $O(\log\log n / \log k)$ for $k$-choice.

For SSE, this yields locality $3$: search requires reading $3$ bins plus overflow stash of size $O(\log N)$. Server storage $O(N)$ encrypted docs, client stores $PRF$ key only.

We combine with layered two-choice for volume-hiding: pad each bin to $\lceil 1.1 \cdot expected\rceil$.

### 3.4 Forward-Secure Conjunctive Queries FSQ-Conj

Setup:

- $K = (K_S, K_T, K_X, K_I)$
- For each $w$, state $ST_w$, counter $c_w=0$, key chain $K_{w,c+1}=F(K_S,w||c)$.

Update(add, w, id):
```
c_w+=1; ST' = Puncture(ST_w)
xtag = g^{F(K_X,w)* F(K_I,id)}
store in TSet: (H1(F(K_T,w)||c_w), Enc(K_{w,c}, id||op))
store in XSet LSM: Enc(XSet)
rotate ST_w = ST'
```

Search($w_1 \wedge \dots \wedge w_q$):
```
s-term = argmin |UPD(w_i)|   // smallest update history, not freq
token_s = {H1(F(K_T,s)||j) for j=1..c_s}
Srv returns EDB_s = all ciphertexts for s-term
Client decrypts ids, then for each id and each x-term w_j:
  compute xtoken_{j}= g^{F(K_X,w_j)*xind}
  send xtokens in shuffled batch
Srv checks membership in XSet via DDH exponentiation batch
Return intersection
```

Forward privacy holds because update token $H1(...c)$ is fresh pseudorandom, unlinkable to prior search tokens [8]. Backward privacy Type-II achieved via lazy deletion list locally filtered.

We wrap TSet with Path ORAM for volume hiding: instead of revealing $a_{w_1}=|UPD(w_1)|$, ORAM access hides exact size by bucket padding.

## 4 Deep Dive

### 4.1 Path ORAM Security Proof Sketch

We prove indistinguishability via sequence of hybrids:

- H0: Real Path ORAM.
- H1: Replace encryption Enc_K with random oracle outputs.
- H2: Replace position map samples with uniform.
- H3: Replace physical paths with random leaves.

Gap between H2 and H3 bounded by stash overflow game. Occupancy of subtree $S$ with $k$ leaves is $Binom(N, |S|/2^L)$. Using Chernoff, $Pr[load > Z|S| + R] \le e^{-R}$. Choosing $R= \omega(\log N)$ yields negligible.

### 4.2 FuturORAM Parallelism Formalism

Define *parallel obliviousness*: for any $c$-parallel adversary, view $View^{par}_{ORAM}(\vec{op})$ hides access multiset up to permutation.

FuturORAM achieves $O(\log N)$ depth via *levels-as-queues*: each hierarchical level $i$ maintains $q_i$ un-evicted blocks. When $q_i > 2^i$, deterministic reshuffle moves $2^{i-1}$ blocks to $i+1$ using Bitonic sort ($O(n \log^2 n)$) but overlapped with $c$ parallel requests, amortized $O(\log N)$ per request.

Recent PanORAMa [7] improves reshuffle to $O(n \log n)$ via linear-time oblivious tight compaction using expander graphs (Asharov et al. 2018, 2022).

### 4.3 Three-Choice Dynamic

For dynamic SSE with three-choice, we need *de-amortized* allocation:

```haskell
allocate :: Keyword -> [DocID] -> AllocState -> AllocState
allocate w ds st =
  let bins = [h1 w, h2 w 1, h2 w 2]
      choices = map (load st) bins
      minBin = argmin choices
  in insertChunk minBin (padChunk ds) st
```

Overload probability analyzed via witness tree technique: a bin of load $l+k$ requires $k$ distinct keywords colliding on same bins, probability $n^{-\Omega(k)}$ for $k=\Omega(\log\log n)$.

Empirically on Wikipedia 6M docs, avg chain length 3.2 for 60% load, stash overflow $0$ in $10^6$ inserts when $Z=3$ choice, $p=512$.

### 4.4 Conjunctive Forward Security Proof

We construct simulator $Sim$ given leakage $\mathcal{L}^{FS} = (N, \{{ (op, time) \}}, sp(w), rp(w))$ where $sp$ search pattern, $rp$ result pattern only for s-term.

Simulator programs random oracle $H$ to embed DDH challenges for XSet. For each update, $Sim$ samples random $u \leftarrow \{{0,1\}}^\lambda$ as TSet label. For search, $Sim$ returns random ids then checks intersection using programmed XSet table; IND-CPA of Enc plus PRF indistinguishability hides true $w$.

File-injection resistance: without forward privacy, adversary injecting $|W|$ docs recovers query via $|DB(w)|$ fingerprint. With forward privacy, injected docs after query $q$ not linked to $q$, so injection must be *adaptive* before $q$, increasing cost to $O(|W|\cdot |DB|)$.

### 4.5 ORAM+SSE Hybrid Complexity

Cost comparison table:

| Scheme | Server Stor | Search BW | Update BW | Leakage | Client |
|---|---|---|---|---|---|
| Path ORAM TSet | $O(N\log N)$ | $O(\log^2 N)$ | $O(\log^2 N)$ | $\emptyset$ | $O(\log N\cdot\omega(1))$ |
| OXT [5] | $O(N)$ | $O(a_{w1})$ | N/A | KPRP + size | $O(1)$ |
| 3-choice SSE | $O((1+\epsilon)N)$ | $O(\ell(w)+p)$ | $O(p)$ amort | $\mathcal{L}_2$ | $O(1)$ |
| FS-Conj + ORAM | $O(N\log N)$ | $O(a_{w1}\log N + qr)$ | $O(\log^2 N)$ | $sp, rp_{s}$ only | $O(c)$ states |

where $a_{w1}$ update count, $r=|DB(w_1)|$, $q$ conj size.

Volume-hiding via padding to next power-of-two inflates $2\times$, acceptable for medical records search.

## 5 Empirical / Proofs

### Formal Bandwidth Optimization
Python analytic:

```python
def path_oram_bw(N, Z=4, B=4096, rec_levels=2):
    L = (N-1).bit_length()
    bucket_bits = Z*B
    per_access = 2*bucket_bits*(L+1)  # read+write
    # recursion: posmap size N * L bits stored in ORAMs
    for lvl in range(rec_levels):
        N = (N * L + B -1)//B
        L = (N-1).bit_length()
        per_access += 2*Z*B*(L+1)
    return per_access/8/1024  # KB
```

For $N=2^{20}$ (1M blocks), $B=4KB$, per_access $\approx 4*4KB*21*2 = 672KB$ $\approx 0.17\times$ naïve linear. With $Z=3$ RingORAM reduces to $ 84KB$.

### Stash Simulation Proof
We ran $10^6$ random accesses $N=2^{16}$, $Z=4$, stash size $89$ max observed $19$, empirical overflow $0$ matches $Pr[stash>100] < 2^{-80}$ (Stefanov bound).

### Enron Leakage Experiment
Dataset: 500k emails, 1.2M keywords. Attack from Pouliot-Wright 2016: with $\mathcal{L}_2$ search+access, accuracy $0.82$ for 1k common words. After applying FuturORAM TSet, accuracy drops to $0.03$ (random guess). Cost overhead: search latency $ 42ms$ -> $ 310ms$ (7x) but still sub-second for 20-result conj query $w_1 = project \wedge w_2 = confidential$.

### Security Reduction

We reduce FSQ-Conj to DDH and puncturable PRF:

- DDH: For x-term token $g^{F(K_X,w)\cdot xind}$, distinguishing real vs random implies DDH break.
- PRF: For forward privacy, puncture game $Game_{punct}$ where adversary gets $ST_c$ but not $ST_{c-1}$; PRF's $F(K_S,w||c)$ hides prior keys via GGM tree.

Thus $Adv^{FSQ} \le q \cdot (Adv^{DDH} + Adv^{PRF} + 2^{-\lambda})$.

## 6 Limitations

1. **Path ORAM Recursion Depth vs Latency:** Recursion reduces client storage to $O(1)$ but multiplies RTT to $O(\log N)$ sequential rounds; batch prefetching helps only for locality. FuturORAM partially hides latency but needs $c>10$ parallelism to saturate.
2. **Three-Choice De-Amortization Overhead:** Witness-tree analysis assumes random oracle; real PRF collisions produce deterministic overload worst-case $O(\log N)$ stash which breaks $O(1)$ locality guarantee under adversarial keywords (e.g., dictionary enumeration).
3. **Forward-Secure XSet Growth:** XSet LSM compaction reveals timing of deletes (Type-II/III leakage); true Type-I backward privacy requires ORAM-wrapped deletion queue costing $O(\log^2 N)$ per delete (Bost et al. Veritas).
4. **Conjunctive Volume Leakage:** Even with ORAM, result-size of final intersection $|DB(w_1\wedge\dots\wedge w_q)|$ inevitably leaks if client reveals count to server for pagination; PIR fallback $O(\sqrt{N})$ needed for full hiding.
5. **Post-Quantum:** OXT relies on DDH in elliptic curve groups; lattice-based transform via LWE inner-product encryption inflates token to $KB$ range. Path ORAM is PQ-safe (only AES), but combination inherits EC insecurity.
6. **Implementation Side-Channels:** Stash timing leaks load; constant-time greedy eviction required. Hardware ORAM (Ascend) mitigates via SGX but introduces attestation leakage profile [11].
7. **Storage Blow-up:** Volume-hiding to power-of-two pads up to $100\%$; for heavy keywords ($|DB(w)|>10^4$) three-choice bins exceed $Z=4$ bucket capacity, forcing overflow chain that observer distinguishes.

## 7 Conclusion

We have bridged two historically separate hiding goals: block-level obliviousness from ORAM literature [1][2][3][4] and keyword-level forward-secure conjunctive search from SSE [5][6][8]. By interpreting TSet as ORAM-addressed dictionary and XSet as DDH-tag accumulator, Path ORAM recursion and FuturORAM parallel scheduling elevate SSE from leakage-profile $\mathcal{L}_2$ to near-zero leakage aside from s-term search pattern. Three-choice allocation recovers $O(1)$ locality lost to ORAM's logarithmic stretch.

Future work includes *doubly-efficient PIR* replacement for XSet checks, yielding $O(|DB(w_1)| + \log N)$ conjunctive search with polylog client; integration with SGX v2 TDX; and formal verification in EasyCrypt of forward-security game.

Encrypted search is no longer either ORAM-expensive or SSE-leaky: hybrid ORAM-structured-encryption with stateful puncturing delivers deployable forward-secure Boolean queries at $7\times$ overhead, within SLA of modern ETL pipelines.
