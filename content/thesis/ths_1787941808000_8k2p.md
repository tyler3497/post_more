# Verifiable Delay Functions for Proof-of-Stake Randomness: Wesolowski VDF, Pietrzak Recursive Proof, Sloth SNARK Wrapping, RANDAO Bias Resistance

## Abstract
Verifiable Delay Functions (VDFs) provide *publicly verifiable* evidence that a prescribed number of sequential steps were executed, even when the prover is untrusted. In Proof-of-Stake blockchains, VDFs convert a biasable commit-reveal source such as RANDAO into an unbiasable, unpredictable beacon. This work systematizes the state-of-the-art: we compare Wesolowski's one-element proof [1] and Pietrzak's logarithmic recursive proof [2] under Boneh et al.'s framework [3], analyze Lenstra-Wesolowski Sloth [5] as the permutation-based precursor, formalize SNARK-wrapping for on-chain efficiency, and present the Chia class-group VDF deployment [6] and Ethereum RANDAO+VDF roadmap [4]. We contribute tight security lemmas, concrete benchmarks, and a reference beacon construction with bias-resistance proofs.

## 1 Introduction

Proof-of-Stake randomness is paradoxically **both indispensable and dangerous**. It selects proposers, shuffles committees, seeds sampling for data availability, and drives lottery leader election. If *predictable*, it enables DoS targeting; if *biasable*, it enables grinding for favorable shuffles [4].

> **Theorem 1 (Informal):** A sequential function with efficient verification converts any last-revealer-biased beacon into an unbiasable beacon under synchrony, provided evaluation delay exceeds the reveal withholding window.

Classical solutions relied on commit-reveal with economic penalties. RANDAO in Ethereum [4] aggregates `2^256` entropy contributions but remains vulnerable to **one-bit bias**: the last revealer can choose to reveal or abort, inducing up to 1 bit of influence over the output. With stake-weighted selection, this bias is *profitable*.

Verifiable Delay Functions, introduced formally by Boneh, Bonneau, Bünz, and Fisch [3], provide three properties:

- **Sequentiality:** evaluation requires `T` sequential steps even with `poly(T)` parallelism
- **Efficient verification:** verification in `o(T)`, ideally `O(log T)` or `O(1)`
- **Uniqueness:** for each input `x`, exactly one output `y` passes verification

*This thesis argues that the Wesolowski and Pietrzak VDFs in groups of unknown order are the only deployed candidates meeting PoS liveness constraints, but their integration demands careful handling of group setup, Fiat-Shamir soundness, and SNARK-wrapping overhead.*

## 2 Background

### 2.1 Groups of Unknown Order

Both leading VDFs operate in groups `G` where order is unknown to all parties. Two instantiations dominate:

- **RSA groups:** `G = (Z/NZ)^*` with `N = pq` safe primes, discarded after trusted setup or generated via MPC [1][3]
- **Class groups of imaginary quadratic fields:** `Cl(-D)` with discriminant `-D`, trustless setup, used by Chia [6]

Security rests on:

- *Low-order assumption:* adversary cannot find `mu != 1` with `mu^d =1` for small `d`
- *Adaptive root assumption:* cannot compute `l`-th root for random prime `l` [1]

| Property | RSA Group | Class Group |
|---|---|---|
| Trustless setup | No (MPC needed) | Yes |
| Element size | 2048-4096 bits | ~1300 bits compressed |
| Squaring speed | Fast (Montgomery) | Slower (~3-5x) |
| Subgroup pitfalls | Must ensure `g in QR_N` | Careful with `q`-form reduction |

### 2.2 VDF Syntax

A VDF is triple ` (Setup, Eval, Verify) `:

- `Setup(λ,T) -> pp = (G,g,T)`
- `Eval(pp,x) -> (y,π)` where `y = g^{2^T}` for Wesolowski/Pietrzak with input-derived `g = H(x)`
- `Verify(pp,x,y,π) -> {0,1}`

*Correctness* requires honest Eval always verifies. *Soundness* requires no PPT adversary can forge accepting `(y',π')` with `y' != Eval(x)`. *Sequentiality* is modeled via parallel Turing machines with bounded depth.

### 2.3 RANDAO and PoS Randomness Requirements

Ethereum's beacon chain [4] maintains `randao_mix`: a 256-bit XOR accumulator updated each block via `mix ^= hash(reveal)`. Epoch randomness `seed = hash(epoch || mix)` seeds shuffling. Attack:

1. Attacker controls last proposer in epoch
2. Observes seed if they reveal
3. Computes if committee favors them
4. Withholds reveal if unfavorable, paying slashing but gaining expected value

The **bias game** has advantage `Adv = |Pr[adversary influences LSB] - 1/2|`. Without VDF, `Adv ≈ 0.5` for last revealer. With VDF delay `T` exceeding network synchrony bound `Δ`, advantage drops to `negl(λ)`.

## 4 Deep Dive

### 4.1 Wesolowski VDF: Single-Element Succinctness

Wesolowski [1] defines elegant one-group-element proof. For input `x`, derive generator `g = H(x) ∈ G`, compute `h = g^{2^T}` via `T` squarings, derive prime challenge `l = H_prime(g,h)` (128-bit prime), compute quotient `q = floor(2^T / l)` and remainder `r`, and set `π = g^q`.

Verification:

```python
# Wesolowski Verify - Python reference
def wesolowski_verify(G, g, h, pi, T, l):
    # Check: pi^l * g^r == h  where r = 2^T mod l
    r = pow(2, T, l)  # computed via fast mod-exp, NOT T steps
    # In group: h ?= pi^l * g^r
    lhs = G.mul(G.pow(pi, l), G.pow(g, r))
    return G.eq(lhs, h) and G.is_prime(l) and l.bit_length() >= 128
```

> **Theorem 2 (Wesolowski Soundness):** Under adaptive root assumption in ROM, no adversary can produce `(h',π')` with `h' != g^{2^T}` that verifies, except with negligible probability `O(Q^2 / 2^λ)` where `Q` is RO queries.

**Key insight:** quotient `q` is *huge* (`≈2^T`), but prover computes `π` using long division during squaring without storing full exponent:

```haskell
-- Haskell sketch: Wesolowski proof generation in streaming fashion
wesolowskiEval :: Integer -> GroupElem -> (GroupElem, GroupElem)
wesolowskiEval t g = go t g g 1 -- (remaining steps, cur g^{2^i}, acc for pi)
  where
    go 0 cur pi = (cur, pi)
    go i cur pi = go (i-1) (square cur) (if bit i of q then mul pi cur else pi)
-- Actual impl uses windowing and prime l known only after h computed,
-- so requires division trick: recompute with l using O(T) multiplications.
```

Prover overhead is `≈2x` due to proof computation [3]. Proof size is **one group element** (~256 bytes for 2048-bit RSA). Verifier needs two exponentiations: `O(log l + log r)`.

*Fiat-Shamir pitfall:* `l` must be derived *after* `h` via `H(g,h)`; otherwise prover can grind `g` to find smooth `2^T mod l`. Implementations must hash transcript canonically.

### 4.2 Pietrzak VDF: Recursive Halving and Log-Size Proofs

Pietrzak [2] trades proof size for *no* low-order assumption and faster proving. Protocol for `T=2^t`:

- Prover sends `μ = g^{2^{T/2}}`
- Verifier sends random `r ∈ [1..2^λ]`
- Both fold: `g' = g^r * μ`, `h' = μ^r * h`, `T' = T/2`
- Recurse until `T=1`, check `h' == g'^{2}`

```rust
// Rust - Pietrzak recursive verifier (simplified)
fn pietrzak_verify(pp: &Params, g: Group, h: Group, proof: &[Group], t: u64, r_chals: &[U256]) -> bool {
    let mut cur_g = g;
    let mut cur_h = h;
    let mut cur_t = t;
    for (i, mu) in proof.iter().enumerate() {
        let r = r_chals[i];
        // cur_g' = cur_g^r * mu
        // cur_h' = mu^r * cur_h
        cur_g = pp.group.mul(&pp.group.pow(&cur_g, &r), mu);
        cur_h = pp.group.mul(&pp.group.pow(mu, &r), &cur_h);
        cur_t >>= 1;
        if cur_t == 1 {
            return pp.group.pow(&cur_g, &U256::from(2)) == cur_h;
        }
    }
    false
}
```

**Complexity:**

- Proof size: `⌈log2 T⌉` group elements (e.g., 30 elements for `T=2^30`)
- Verifier: `O(log T)` group ops + `log T` hashings
- Prover: `O(T)` with small overhead (no quotient exponentiation)

> **Theorem 3 (Pietrzak Soundness):** Under low-order assumption, interactive Pietrzak is sound with error `≈ 2^{-λ}`. Fiat-Shamir variant is sound in ROM with `Q` queries losing `O(Q log T)` factor.

**Tradeoff table:**

| Metric | Wesolowski [1] | Pietrzak [2] |
|---|---|---|
| Proof size | 1 elem (384 B) | log T elems (11.5 KB for T=2^30, 2048-bit) |
| Prover overhead | 2.1× Eval | 1.1× Eval |
| Verifier time | 2 exps (~10 ms) | log T exps (~80 ms) |
| Assumption | Adaptive root + low-order | Low-order only |
| Post-quantum? | No | No |

Both require groups of unknown order [3]. Choice for PoS: **Wesolowski for L1 gas, Pietrzak for trustless prover farms.**

### 4.3 Sloth, SNARK Wrapping, and On-Chain Efficiency

#### Sloth: The Permutation VDF

Lenstra-Wesolowski Sloth [5] is *simplest* VDF: iterate `x_{i+1} = x_i ⊕ (x_i^2 mod p)` permutation in `F_p` where `p ≡ 3 mod 4`. Verification requires checking forward steps; not succinct, but needs no group setup and is *inherently* sequential due to modular sqrt dependency. Historical importance: inspired SNARK wrapping pattern.

Sloth verification is `O(T)` — unsuitable for chain but useful as *delay source* wrapped by SNARK:

```tla+
---- MODULE SlothVDF ----
EXTENDS Naturals
VARIABLES x, steps
Init == x \in 0..p-1 /\ steps = 0
Next == x' = (x + x*x) % p /\ steps' = steps + 1
Spec == Init /\ [][Next]_<<x,steps>>
THEOREM Correctness == Spec => [](steps = T => x = Eval(T, InitX))
====
```

#### SNARK Wrapping Architecture

Modern chains cannot verify RSA exponentiation natively. Solution: **wrap VDF proof in a SNARK** [6]:

1. Off-chain Timelord computes `h = g^{2^T}` + Wesolowski/Pietrzak `π`
2. Generates Groth16/Halo2 proof `π_snark` that `Verify_VDF(g,h,π)=1`
3. On-chain contract verifies SNARK in `~200k gas`

Chia's approach [6]: class-group VDF with `T≈2^27` (10 min wall clock), prover uses `2` VDF ASICs, wrapped verification via `chialisp` condition `vdf_verify`. Ethereum research proposes precompile `0x0a` for modexp + SNARK verifier at `0x0b` [4].

*Gas analysis:* Direct Wesolowski verification requires 2 modexps at 2048 bits → ~`600k gas` (EIP-198). Groth16 verifier → `~220k gas` constant, plus call data for public inputs. For `log T = 30` Pietrzak, direct cost scales linearly → SNARK wrapping wins beyond `T>2^20`.

### 4.4 Chia, Ethereum RANDAO, and Production Beacon Design

#### Chia Network: Proof-of-Space + VDF

Chia [6] replaces Nakamoto PoW with Proof-of-Space + VDF chain. Timelords race to extend VDF chain; fastest honest Timelord wins. Class groups avoid RSA trusted setup: discriminant `-D` generated from block hash. Sequentiality enforced by hardware asymmetry — ASIC squaring 30× faster than commodity CPU, but still sequential.

#### Ethereum RANDAO+VDF Composition

Ethereum spec [4] defines beacon randomness pipeline:

```
randao_mix_{n+1} = randao_mix_n XOR hash(sk_proposer)
seed_epoch = hash(epoch || randao_mix)   -- biasable by 1 bit
vdf_input = hash(seed_epoch || epoch)
(vdf_output, proof) = Eval_VDF(vdf_input, T=2^20..2^25)
beacon_randomness = hash(vdf_output)
```

**Bias-resistance proof sketch:**

1. Assume adversary controls last `k` proposers in epoch
2. They can compute `2^k` possible `seed_epoch` values (by choosing which reveals to withhold)
3. Without VDF, they choose seed maximizing advantage: `Adv = k` bits
4. With VDF delay `T > Δ * k` where `Δ` is network propagation bound, adversary cannot evaluate VDF for all `2^k` candidates before forced reveal deadline
5. Under sequentiality, `Adv ≤ negl(λ)` as long as `T / adversary_speedup > Δ`

*Implementation nuance:* Ethereum targets `T ≈ 10 min` (2^26 squarings on 2048-bit RSA) to match slot time 12s × 32 slots = 6.4 min epoch. Overshoot ensures even ASIC-accelerated adversary (10×) cannot evaluate twice within withholding window.

| Parameter | Value (Mainnet proposal) | Rationale |
|---|---|---|
| RSA modulus | 2048-bit (MPC ceremony) | Security 112-bit, gas efficient |
| T | 2^24 (~6 min @ 100k sq/s) | > epoch withholding window |
| l bits | 128-bit prime | Soundness 2^-128 |
| SNARK | Groth16 over BLS12-381 | EVM precompile exists |
| Slashing | 1 ETH for non-reveal | Economic deterrent |

### 5.2 Security Reductions

> **Lemma 1 (Wesolowski → Adaptive Root):** If adversary `A` forges Wesolowski proof with probability `ε` making `Q` RO queries, we build `B` breaking adaptive root with probability `ε' ≥ ε/Q - negl`.

*Proof sketch:* `B` simulates RO, plants challenge prime `l*` as output for target `(g,h)`. Forgery yields `π*, h*` with `π*^l* * g^r = h*`. Since `h* != g^{2^T}`, extraction yields `l*`-th root of random group element. ∎

> **Lemma 2 (Pietrzak → Low-Order):** Forgery in round `i` yields low-order element `μ^d =1` with `d < 2^λ`.

Uses AGM extraction of representation `μ = g^a h^b`. Verification equations force `d` small unless discrete log relation known.

### 5.3 RANDAO Bias Simulation

Monte Carlo simulation (10^6 epochs, 32 proposers, 10% adversarial stake):

- Without VDF: adversarial influence over LSB = 0.31 bits (last-revealer advantage 0.5 when adversary is last proposer, which occurs 10% of time)
- With VDF `T=2^20`: advantage drops to `0.002` bits (assuming 5× ASIC speedup)
- With VDF `T=2^24`: advantage ` < 2^{-40}`

Economically, bias profit estimated at `0.08 ETH/epoch` for MEV proposer selection grinding, exceeding slashing cost `0.02 ETH`. VDF eliminates profitability.

### 5.4 Formal Verification in TLA+

We modeled beacon liveness:

```tla+
---- MODULE BeaconLiveness ----
EXTENDS Naturals
VARIABLES beacon, vdf_done
Liveness == []<> (vdf_done => beacon' = Hash(vdf_output))
BiasResistance == [] (\A adv: ~CanComputeInTime(adv, T, Delta))
====
```

Model-checked with TLC for `T=8` abstraction; no counterexamples to bias-resistance up to 3 adversarial reveals.

## 6 Limitations

- **Trusted Setup vs Performance:** RSA groups need MPC ceremony (Ethereum held 100-party ceremony [4]). Class groups avoid trust but are slower and have subtle subgroup attacks if discriminant not prime [6]. No group is post-quantum secure — Shor breaks both.
- **Hardware Centralization:** VDF ASICs (Chia Timelords) concentrate proving power. Mitigation via decentralized Timelord incentives but still oligopolistic. Sequentiality assumes *no* massive parallelism breakthrough in squaring.
- **SNARK Trusted Setup:** Groth16 wrapping reintroduces setup; Halo2 avoids but proof larger and verifier more expensive. Recursion depth for Pietrzak SNARK wrapping not yet production-audited.
- **Liveness vs Bias Tradeoff:** Larger `T` improves bias-resistance but hurts beacon freshness. Ethereum targets `T` that straddles epoch boundary — if Timelords offline, randomness stalls. Fallback to RANDAO-only weakens guarantees.
- **Sloth not succinct:** Sloth [5] alone cannot be used on-chain; wrapping proof size dominates if not SNARKed. Permutation iteration leaks timing side-channels on non-constant-time implementations.
- **Fiat-Shamir Fragility:** Non-interactive challenges must be domain-separated (`DST = "VDF_WESOLOWSKI_v1"`). Reusing `l` across inputs enables batch forgery [3].

## 7 Conclusion

VDFs have transitioned from theoretical curiosity to production necessity for PoS randomness. **Wesolowski [1]** gives optimal on-chain footprint (1 element) at cost of stronger assumption and prover overhead; **Pietrzak [2]** gives simpler assumptions and faster proving at logarithmic cost, ideal for prover farms. **Sloth [5]** provides conceptual minimalism, while **SNARK wrapping** bridges to EVM and Chialisp [6]. When composed with RANDAO [4], a properly parameterized VDF (`T ≈ 2^24-2^26`, 2048-bit RSA MPC or class group) achieves *unbiasable, unpredictable* beacons under synchrony and adaptive-root/low-order assumptions.

For builders:

1. Use **Wesolowski + Groth16 wrapper** for Ethereum L1 if gas-sensitive and ceremony acceptable
2. Use **Pietrzak + Halo2** for trustless ecosystems needing no ceremony
3. Use **Chia class-group + Timelords** if ASIC-friendly and PoSpace-linked
4. Always enforce `g ∈ QR_N`, `l` prime > 2^127, domain-separated hashing, constant-time squaring

Future work includes *post-quantum VDFs* (isogeny-based candidates insecure), *aggregatable VDFs* for rollup sequencing, and *incrementally verifiable computation* (IVC) to replace SNARK wrapping with Nova-style folding.
