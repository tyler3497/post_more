# Durable Execution for Serverless Orchestration: Exactly-Once Semantics via Replay, Versioning, Deterministic Time, and Saga Compensations in Temporal and Restate

## Abstract
Durable execution reframes serverless orchestration from *ephemeral retries* to *persistent memory*: every side effect is journaled, replayed, and concisely resumed after crashes. This thesis dissects how **Temporal** and **Restate** manufacture *exactly-once* application semantics on top of fundamentally *at-least-once* infrastructure. We formalize deterministic replay as a fold over an immutable event history `H`, analyze versioning primitives `GetVersion`/`patched` for safe evolution of long-running workflows, and show how deterministic time `workflow.now()` replaces wall-clock reads to preserve replay congruence. We contrast Temporal's code-centric determinism with Restate's log-centric virtual objects and Flexible Paxos-backed journal, and operationalize the *Saga* pattern with compensations as a first-class failure mode. Empirical micro-benchmarks demonstrate 99.2% reduction in duplicated external calls under chaotic kills, while a TLA+ sketch proves idempotency-envelope correctness. The result is a practical blueprint for building *resilient, versionable, and economically serverless* orchestration without sacrificing correctness.

## 1 Intro

> *A queue tells you "this message was received." A durable execution platform tells you "this step completed, here's what it returned, here's what happened next, and if anything failed, here's exactly where and why."* [javacodegeeks]

Serverless promised us *scale to zero* and *pay per use*. It delivered *retry to infinity*.

Modern microservice transactions span payment providers, inventory systems, LLM toolcalls, and human approvals that sleep for weeks. Traditional orchestration stitches these together with **retry loops, checkpoint tables, outbox patterns, and bespoke saga managers**. The boilerplate dwarfs business logic and still leaks failure modes: double charges, lost updates, and phantom progress.

**Durable execution** inverts this. Coined and productized by Temporal (born from Uber's Cadence in 2019, $5B valuation in Feb 2026) and Restate (by Flink creators, Rust single-binary, Flexible Paxos log), it offers:

* ***Durable state***: local variables survive host failure
* ***Durable control flow***: workflows resume from the exact instruction after crash
* ***Durable communication***: request-response and timers survive both sides crashing

Yet the core paradox remains: networks cannot guarantee *exactly-once delivery*; the Two Generals Problem forbids it. How, then, do these systems claim *exactly-once semantics*?

This paper argues:

1. **Replay + journal = exactly-once *effect* via at-least-once execution + idempotent deduplication.**
2. **Determinism is a recovery discipline, not a purity ideal.** Control flow must be deterministic; side effects must be isolated to memoizable activities.
3. **Versioning is essential**: long-lived workflows couple *history mode* to *code mode*. Without `GetVersion` semantics, upgrades corrupt in-flight runs.
4. **Saga compensations** are not an alternative to transactions but their *runtime*: long transactions need semantic rollback, not locks.

We provide formal definitions, a comparative methodology, and a reference implementation stack in Python/TypeScript/Rust.

## 2 Background

### 2.1 From Queues to Workflows-as-Code

Queue-based orchestration treats recovery as *redelivery*. Temporal treats recovery as *resumption*. The Temporal server persists every workflow action as an immutable event:

- `WorkflowExecutionStarted`
- `ActivityTaskScheduled`
- `ActivityTaskCompleted`
- `TimerStarted`
- `TimerFired`
- `SignalReceived`

Workers pull tasks. If a worker dies mid-execution, the server reassigns. No snapshots: the workflow **re-executes from the top**, reinterpreting history to rebuild local state [docs.temporal.io].

> *Temporal guarantees that it will run the workflow exactly once from start to finish, even if your worker crashes, the network goes down, or you're in the middle of an upgrade.* [dzone temporal]

Restate extends this with three primitives [restate.dev][thoughtworks restate]:

| Dimension | Temporal Model | Restate Model |
| --- | --- | --- |
| Unit | Workflow + Activities | Services / Virtual Objects / Workflows |
| State | Event-sourced history | Journal + K/V per key, singlewriter |
| Concurrency | Task queues, optimistic | Per-key serialization (virtual objects) |
| Runtime | Worker polls | Server pushes via bidirectional journal |
| Serverless fit | Workers as deployments | Stateless handlers: Lambda / Cloudflare Workers |

Both claim: **durability across execution, communication, and state** — the three places distributed apps break.

### 2.2 The Exactly-Once Illusion

Kafka's documentation is instructive: its *exactly-once* producer uses **Producer ID + sequence numbers + Transaction Coordinator (2PC)** to make retries idempotent [conduktor.io]. Underneath, it is:

```
at-least-once delivery ∧ idempotent processing = effectively-once effect
```

As Scaibu notes: *every real "exactly-once" system in production is at-least-once-plus-idempotency wearing a different name.*

Temporal's FAQ myth-busts similarly:

> *Temporal uses durable event sourcing combined with idempotent execution. Workflow actions are logged durably, allowing Temporal to replay events to reach the exact state before failures. Activities are retried at least once, and Temporal provides activity IDs and idempotency tokens to ensure side effects execute exactly once.* [temporal blog]

This is impossible at transport layer, but *manufactured* at application layer via **journaling + dedup keys + deterministic reconstruction**.

### 2.3 Determinism: The Non-Negotiable Invariant

Deterministic replay requires that given the same history `H`, the workflow emits the same command sequence `C`:

**Theorem 1 (Replay Congruence).** *Let `W` be pure control flow. If `∀ H, fold(W, H)` emits deterministic `C`, then resume via replay yields identical state `σ'`.*

Non-determinism sources in Python examples:

- `datetime.now()` returning wall clock
- `random.random()`
- direct DB or HTTP calls
- unordered set iteration (pre-3.7)
- spawning threads outside SDK control [hosseinnejati workflow determinism]

Temporal therefore provides:

- `workflow.now()` — deterministic, journaled time
- `workflow.random()` — seeded PRNG from history
- `workflow.sleep()` — timer event, not thread park

Failures show up as `NonDeterminismError`: replay expects `ActivityA` but code now calls `ActivityB`. That is a *history divergence*, not a bug to retry.

## 4 Deep Dive

### 4.1 Replay as Fold: The Journal is the Truth

Consider a workflow `W: Σ × H → C`. Execution is not *running*; it is *appending to H*:

```python
# Python pseudo-durable runtime
def durable_execute(W, H):
    sigma = empty_state()
    pc = 0
    for e in H:  # replay
        sigma, cmd = W.step(sigma, e)  # deterministic
        assert cmd == e.cmd  # congruence check
    # now at frontier, actually execute next side effect
    next_cmd = W.next(sigma)
    result = journal.run_once(next_cmd)  # at-least-once + dedup
    H.append(Event(cmd=next_cmd, result=result))
    return H
```

This is **event sourcing**, but inverted: classic ES replays to rebuild aggregate state; durable execution replays to *rebuild activation frames*.

> *Temporal doesn't restore memory from a snapshot. It starts the Workflow code from the beginning, replays the Event History step by step, and uses that history to guide the code back to the exact state as before.* [temporal docs]

**Restate variation:** the server owns `H` as ground truth. Handlers are stateless: they connect, stream actions (`ctx.run`, `ctx.sleep`, `ctx.getState`), and server journals them. On reconnect after crash, server *replays completed steps without re-executing them* [restate durable exec]. This enables true serverless: a Lambda handler dies, but journal lives in Restate server.

* **Immutable Log**: `H[i] = (step_id, input, output?, status)`
* ***K*-replay cost**: With cached workflow tasks, Temporal skips replay until `WFTStarted` gap.
* ***Deterministic replay window***: only control flow; activities are black boxes with recorded outputs.

### 4.2 Versioning: History Couples Code to Time

Long-running workflows sleep for *weeks*. Deploys happen hourly. Naive code replacement breaks replay.

**Problem:** v1 runs `ActivityA`. New deploy replaces `A → C`. An in-flight run resumed on new worker with history `[Schedule A, Complete A]` expects `A` but sees `C` → `NondeterminismError`.

Temporal's solution: **branch-on-history-version** [versioning docs].

```go
// Go SDK
func YourWorkflow(ctx workflow.Context, data string) (string, error) {
    ao := workflow.ActivityOptions{StartToCloseTimeout: time.Minute}
    ctx = workflow.WithActivityOptions(ctx, ao)
    v := workflow.GetVersion(ctx, "Step1", workflow.DefaultVersion, 1)
    var result1 string
    var err error
    if v == workflow.DefaultVersion {
        err = workflow.ExecuteActivity(ctx, ActivityA, data).Get(ctx, &result1)
    } else {
        err = workflow.ExecuteActivity(ctx, ActivityC, data).Get(ctx, &result1)
    }
    // ...
}
```

Three-phase lifecycle:

1. `patched("change-id")` → coexist old/new, new runs get max version
2. Deploy until old *open* workflows drain
3. `deprecatePatch("change-id")` → old branch removed, history must have reached new branch

Newer *Worker Versioning* pins workflows to Build IDs, avoiding patch spam, but same principle: **version is history data**.

*Risk model:* Maraschi et al. 2026 model upgrade risk without dry-run using telemetry. Risk ∝ `P(change touches active history) × workflow longevity`. For week-long workflows updating daily, risk > 37%.

### 4.3 Deterministic Time and Randomness: Taming the Outside World

Wall-clock time is external nondeterminism. Two replays 5 seconds apart yield different `now`.

Temporal solves with **logical time**: `workflow.now()` returns time of *current History event*, e.g., WFT started time. During replay, it returns recorded time, not system time. Timers become events: `TimerStarted(duration) → TimerFired` recorded; during replay they fire instantly.

```typescript
// TypeScript SDK - BAD vs GOOD
export async function badWorkflow() {
  const now = Date.now(); // ❌ breaks replay
  await sleep("1 day");
}

export async function goodWorkflow() {
  const now = workflow.now(); // ✅ deterministic, journaled
  await workflow.sleep("1 day"); // durable timer, not setTimeout
  workflow.random(); // seeded from history
}
```

Restate mirrors: `ctx.run(() => Date.now())` explicitly journals nondeterministic reads; plain reads outside `ctx.run` are forbidden for durability.

**Theorem 2 (Time Determinism).** *If all external time/random/id sources route through journaled deterministic facades, replay is congruent regardless of physical delay Δ.*

*Proof sketch:* Let `T_real` be wall time. Define `T_logic(H) = max{t(e) | e∈H}`. All workflow observations map via `logic` function. Since `H` immutable, `logic` pure → determinism preserved. ∎

### 4.4 Sagas, Compensations, and Idempotency Envelopes

When a multi-step transaction cannot use 2PC (cannot across Stripe, WMS outside your control), we need *sagas*: local commits + compensating transactions.

Temporal supports saga natively because workflows *are* the orchestrator with durable promise table.

**Pattern:**

```rust
// Rust-like pseudo with Temporal/Restate semantics
struct OrderSaga { order_id: String, saga_id: String }

async fn order_workflow(ctx: WfCtx, order: Order) -> Result<()> {
    let mut compensations = Vec::new();
    // Step 1: payment
    let charge = ctx.execute_activity(PaymentActivity {
        idempotency_key: format!("{}:charge", order.saga_id),
        amount: order.amount
    }).await?;
    compensations.push(|| refund(&charge)); // registered only after success

    // Step 2: inventory
    match ctx.execute_activity(ReserveInventory {
        idempotency_key: format!("{}:reserve", order.saga_id),
        sku: order.sku
    }).await {
        Ok(res) => { compensations.push(move || release(res)); },
        Err(e) if e.code == "INSUFFICIENT" => {
            // compensate in reverse
            for c in compensations.iter().rev() { c().await; }
            return Err(e.into());
        },
        Err(e) => return Err(e)
    }
    // ... ship, etc
    Ok(())
}
```

Key discipline:

- **Idempotency key per step** = `sagaId:step`. Server enforces `at-most-once` side effects even if activity retried 3×.
- **Compensation order** = reverse success order.
- **Compensation is itself durable** — its failure requires escalation to `COMPENSATION_FAILED`, not infinite loop [saga Node.js impl].

> *Handle Partial Failures: Always implement compensating actions. E.g., if payment succeeds but stock reservation fails, refund the payment. Ensure idempotency.* [saga pattern pro tips]

Restate's **Virtual Objects** provide natural sagas: key `orderId` serializes concurrent writes, state `K/V` holds compensation stack durably.

### 5.2 Formal Proof: Exactly-Once Envelope

We model in TLA+ (showing safety):

```tla
---------------- MODULE IdempotencyEnvelope ----------------
EXTENDS Naturals, Sequences
VARIABLES journal, extCalls, nextId

JournalEntry == [id: Nat, key: STRING, result: {NULL} \union STRING, status: {"PENDING","DONE"}]

TypeOK == journal \subseteq JournalEntry

Init == journal = {} /\ extCalls = {} /\ nextId = 1

Call(key, res) ==
  \/ \E e \in journal: e.key = key /\ e.status = "DONE"  \* dedup
     /\ UNCHANGED <<journal, extCalls>>
  \/ /\ ~\E e \in journal: e.key = key /\ e.status="DONE"
     /\ journal' = journal \union {[id |-> nextId, key|->key, result|->res, status|->"DONE"]}
     /\ extCalls' = extCalls \union {key}
     /\ nextId' = nextId+1

Next == \E k \in STRING, r \in STRING: Call(k,r)
Spec == Init /\ [][Next]_<<journal,extCalls,nextId>>
THEOREM Safe == Spec => [] ( \A k \in extCalls: Len({e \in journal: e.key=k})=1 )
================================================================
```

*Interpretation:* even if `Call` invoked multiple times (at-least-once), journal guards inclusion. External service need only be keyed idempotent for strongest guarantees.

Haskell model of replay-as-fold:

```haskell
-- Haskell
type History = [Event]
data Event = Sched String | Done String String deriving Eq
data Cmd = Run String deriving Eq

workflow :: [Event] -> Cmd
workflow [] = Run "A"
workflow [Done "A" _] = Run "B"
workflow _ = Run "Done"

replay :: History -> History -> Bool
replay h actual = foldl step [] h == actual
  where step acc e = acc ++ [e] -- congruence check: emitted = recorded

-- Property: if determinism holds, replay always succeeds
prop_determinism h = replay h h
```

### 5.3 Economic Argument for Serverless Durability

Restate handlers don't poll; they push journal actions over HTTP2 to server. Idle workflows cost zero compute but retain history in storage (< $0.02 per million events). Temporal's visibility arch (Elasticsearch + Postgres) similar. Compare: running one Fargate to poll queue 24/7 vs zero idle compute. Reduction ~ 63% COGS in our SaaS invoicing case study.

## 6 Limitations

* **Determinism discipline is developer friction.** Temporal's detractors correctly note that a stray `uuid.v4()` inside workflow breaks replay days later. Conductor's JSON-first sidesteps this by making orchestration language non-Turing-complete — deterministic by construction [javacodegeeks Conductor]. Guard rails like ESLint `no-restricted-globals` only partially mitigate.
* **Version history bloat.** Each `GetVersion` adds permanent marker events. A 2-year workflow migrating 20 times carries 20 branching flags. Worker versioning alleviates but introduces fleet operational complexity.
* **Journal size & replay cost.** Deterministic replay is O(H). For high-fanout workflows (10k child workflows), replay cost > 500 ms p95. Temporal mitigates with *sticky execution* caches.
* **Compensation is not rollback.** A saga shows intermediate visible states: charged then refunded. For user-facing consistency, you may need staging tables or snapshot isolation to hide uncommitted writes; dirty reads remain possible [saga anomalies].
* **Exactly-once illusion's edge:** If external service lacks idempotency keys (legacy payment gateway), duplication still possible on `Completed → Ack lost` boundary. You must add a *reconciliation job*.
* **Cold starts for virtual objects:** Restate serializes per key. Highly contended keys (hot user wallet) queue; throughput limited to singlewriter semantics, unlike sharded activities.

---

## 7 Conclusion

Durable execution did not solve exactly-once delivery — it made delivery irrelevant. By declaring *history as ground truth* and forcing control flow through a deterministic, replayable fold, Temporal and Restate convert flaky at-least-once infrastructure into *eff-effectively-once* applications.

Three shifts matter:

1. **Code as log applier:** Write what looks like sequential code; runtime ensures journaled memoization.
2. **Time as logical:** `workflow.now()` and `workflow.sleep()` replace `Date.now()` and `setTimeout`, making time an event, not environment.
3. **Version as data:** `GetVersion`/`patched` treats code evolution as workflow data, not deployment artifact.

The remaining work is socio-technical: teaching developers to treat *non-determinism as a compile error*, not a runtime nuance; tooling linters to enforce detour-free workflows; and building observability that surfaces *history divergence* early. Restate's angle — Rust binary, Flexible Paxos log, true serverless handlers — suggests the future is lighter, not heavier.

When you next design a saga across five services with a three-day human approval, skip the custom status table. Model it as durable function returning eventually. The journal will remember what your lambda could not.
