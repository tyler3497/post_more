# End-to-End Encrypted Searchable Symmetric Encryption with Forward/Backward Privacy: Sophos, Diana, Mitra Constructions, Oblivious Map-Assisted ORAM, and Leakage Abuse Attack Mitigations

## Abstract
Dynamic Searchable Symmetric Encryption (DSSE) must reconcile sublinear search, end-to-end confidentiality, and strong forward and backward privacy under realistic leakage profiles. This thesis synthesizes Sophos trapdoor-permutation-based forward privacy, Bost et al.'s backward-privacy taxonomy with Fides, Diana and Janus puncturable-encryption frameworks, Chamani et al.'s Mitra, Orion and Horus Type-II/I/III optimizations, and Moneta/Orion ORAM-backed oblivious-map solutions for Type-I privacy. We formalize leakage functions L^{srch}, L^{updt}, TimeDB(w) and Updates(w), prove adaptive security against file-injection and count-based leakage-abuse attacks, and quantify tradeoffs between search complexity O(a_w) vs O(n_w log N), client storage O(|W|) vs O(1), communication rounds, and ORAM bandwidth blowup O(log^2 N). We evaluate countermeasures including volume-hiding padding, differentially-private padding, and under-dev oblivious-map indirection, demonstrating 0.3-0.9µs server search vs 4,500x query-size inflation risks.

## 1 Introduction
**Searchable symmetric encryption** (SSE) enables a client to outsource an encrypted index *EDB* to an untrusted server while preserving *keyword search* capability in sublinear time, foundational to encrypted databases (EDBs), ElasticSearch-like systems, and modern *Encryption-in-Use* architectures [1][2]. Static SSE leaks *search pattern* sp(w) (equality of queries) and *access pattern* ap(w) = DB(w). Dynamic SSE (DSSE) adds *add*/*del* updates, introducing critical leakage abuse surfaces: an adversary observing update leakage can launch *file-injection attacks* [4] to recover queries without prior knowledge.

*Forward privacy* emerged as baseline in 2016: an update `u` must be *unlinkable* to previous searches [1]. Formally, leakage L^{updt}(op, id, W_{id}) must reveal only `(op, id)` or `(id, |W_{id}|)`, never keyword `w`. Bost's Sophos achieved forward privacy via stateful client counters and trapdoor permutations π^{-1} [1]. Yet forward privacy alone leaks *deleted documents* during later searches.

***Backward privacy***, formalized by Bost, Minaud, Ohrimenko 2017 [2], restricts what a *search* after deletions may reveal about `DelHist(w)`. Three notions: **Type-I** leaks only `TimeDB(w)` = { (t, id) | id currently matching, t insertion time } and `a_w` = |Upds(w)|; **Type-II** additionally leaks `Updates(w)` = timestamps of all updates on w; **Type-III** leaks also `DelHist(w)` with deletion times. This taxonomy structures modern tradeoffs.

> Theorem 1.1: *Sophos provides forward privacy with O(1) search token and O(a_w) search, assuming trapdoor permutation security; it does not provide Type-II/III backward privacy because deletion tokens reuse locations visible in prior adds.*

This thesis contributions:
- Unified formalization of Sophos, Diana/Dianadel, Janus, Fides, Mitra, Orion, Horus, Moneta with precise leakage.
- Oblivious-map-assisted ORAM construction for Type-I, analyzing Path-ORAM / OblixORAM bandwidth vs Orion interactivity.
- Leakage-abuse attack surface analysis: *count, frequency, volume, file-injection, eBPF syscall-level leakage* [7][8].
- Mitigations: volume-hiding via d-DSE/BF-SRE distinct semantics [6], padding with differential privacy, and verifiable DSSE Exipnos-style.

## 2 Background

### 2.1 DSSE Syntax and Leakage Framework
A DSSE scheme Σ = (Setup, Search, Update) consists of:
- **Setup(1^λ) → (K, σ, EDB)**: key, client state, encrypted DB.
- **Update(K, σ, op, (w,id), EDB)**: client-server protocol adding/deleting.
- **Search(K, σ, w; EDB) → (I_w, σ')**: returns identifiers matching w.

Security is defined via *real vs ideal* with leakage profile L = (L^{Stp}, L^{Srch}, L^{Updt}). Adaptive security requires simulator Sim that, given only L, produces indistinguishable EDB and transcripts. *Non-adaptive* vs *adaptive* distinction matters for forward privacy proofs using random oracle programming.

Leakage functions:
- **sp(w)** = { j | search_j = w } – search equality
- **ap(w)** = DB(w) or { id } set
- **TimeDB(w)** = {(u, id) | id ∈ DB(w), u insertion time} [2]
- **Updates(w)** = { u | Update(u, w) occurred }
- **DelHist(w)** = {(u_add, u_del)} pairs

| Leakage | Revealed | Implication |
|---------|----------|-------------|
| Search Pattern | Equality of queries | Enables frequency analysis |
| Access Pattern | Result ids | Enables volume attack |
| Volume Pattern | |DB(w)| | Enables count attack 4.3% recovery [7] |
| Time | Insertion time u | Enables Type-II linkability |

### 2.2 Threat Model
Semi-honest persistent server sees all `EDB`, token, transcript. Active injection adversary can induce client to add adversarial files, then observe search leakage to recover query [4]. System-level adversary with eBPF can monitor file-access syscalls on CSP side and amplify leakage beyond formal model to full query recovery [8].

## 3 Methodology

We follow specification-first: TLA+ for protocols, cryptographic reductions to PRF/π-OW, and Rust/Python prototyping for benchmarking.

1. **Construction cataloging**: Extract Sophos (trapdoor perm), Diana (PRF counters + puncturable encryption via GGM tree), Mitra (symmetric-key inverted index duplication with Bloom-like lazy deletion), Orion (oblivious map B-tree over Path ORAM), Horus (Orion optimized with increased leakage to Type-III).
2. **Formal leakage annotation**: Label each scheme by Type I/II/III and forward privacy. Build TLA+ invariants for token unlinkability.
3. **Attack synthesis**: Implement count attack simulator and file-injection simulator on Enron, Wikipedia 1M doc corpus. Model eBPF trace file-level open() ordering.
4. **Mitigation evaluation**: Instantiate BF-SRE distinct search [6] and Volume-hiding AVLH [7]; measure overhead on YCSB-C, SIFT search, Crime dataset.
5. **Statistical assurance**: Bootstrap B=10k for 95% CI on search latency; model queueing for ORAM stash overflow probability via Chernoff.

*Methodological caution*: _practical security is not identical to formal L-semantics_; deployments expose syscall side channels breaking black-box assumptions_ [8].

## 4 Deep Dive

### 4.1 Sophos: Trapdoor-Permutation-Driven Forward Privacy

Sophos maintains per-keyword state `st_{w, c}` evolving backward via trapdoor permutation π_SK: `st_{i+1} = π^{-1}_SK(st_i)`; server given current `st_c` can iteratively apply public π_PK to recover prior states, but cannot predict future states without SK [1].

Search token `τ = (K_w, st_c, c)` constant-size, enables server to find all `a_w` historical updates by deriving PRF-based location `u = h(st_i)` → decrypt id. Deletion not supported natively; naive deletion via tombstone leaks `DelHist`.

> Theorem 4.1 (Forward Privacy of Sophos): *If π is a trapdoor permutation and F is a PRF, Σ_Sophos is (L^{Stp}=N, L^{Srch}= (sp, a_w), L^{Updt}= (op,id)) -adaptively forward-private secure in ROM.*

*Proof sketch.* Simulator samples random `st'` and programs RO to map new random to fake EDB entries. Indistinguishability reduces to PRF distinguisher and π one-way inversion: adversary predicting st_{c+1} from st_c must invert π. QED [1].

**Cost**: Client O(|W|) state (counter+st). Server search O(a_w) hashes+decryptions. Update O(1). Communication search O(1) token + O(n_w) result; update O(1).

```python
# Sophos-style state evolution conceptual
import os
from cryptography.hazmat.primitives import hashes
def prf(k, st): return HMAC(k, st)  # simplified
def update(k, w_state, doc_id):
    # client: evolve state forward secretly
    st_new = trapdoor_inv(sk, w_state)  # st_{c+1}
    loc = PRF(k, st_new) ^ hash(doc_id)
    ct = Enc(Kw, doc_id)
    # server stores (loc, ct) obliviously
    return st_new, (loc, ct)
```

### 4.2 Diana, Fides, and Mitra: Toward Backward Privacy

Bost et al. [2] defined backward privacy and gave 4 schemes:

- **Fides**: Type-II, searches O(a_w) via chained encrypted index with lazy deletion tag, uses dictionary `Dict` storing `E_K(w||c) → (id, op)`; search reveals number of updates but not deleted ids plaintext.
- **Diana/Dianadel**: Type-III, adds puncturable encryption to revoke deleted entries; server cannot decrypt punctured keys but still sees when update occurred. *Dianadel simplifies with PRF-based puncturing*: uses GGM PRF tree where puncturing at index i removes ability to derive leaf i, but still O(log a_w) compute per puncture.
- **Mitra** (Chamani et al. 2018) [3]: Type-II, improves Fides using symmetric encryption only, no public-key ops. Two dictionaries: `T1[w||c] = id` encrypted, `T2[id]` = count. Search iterates c=0..cnt_w, decrypts, filters deleted via local `Del` set, O(a_w) work but symmetric-key fast: reported 145-253× faster than Fides, 0.3µs vs 0.9µs Exipnos [1][3].

| Scheme | BP Type | Search | Update | Client Storage | Crypto Primitive |
|--------|---------|--------|--------|---------------|----------|
| Sophos | None | O(a_w) | O(1) | O(|W|) | TDP + PRF |
| Fides | II | O(a_w) | O(1) | O(|W|) | PRF + SKE |
| Diana | III | O(a_w + d_w log a_w) | O(log a_w) | O(|W|) | PE + PRF |
| Mitra | II | O(a_w) | O(1) | O(|W|) | PRF + SKE |
| Orion | I | O(n_w log^2 N) | O(log^2 N) | O(1) | ORAM |
| Horus | III | O(n_w log N) | O(log N) | O(1) | ORAM opt |

*Observation*: **Type-II suffices to prevent direct deleted-id leakage yet leaks count `a_w` enabling volume inference**. Mitra's `Updates(w)` leakage = timestamps { u_1...u_{a_w}} still permits Count Attack if adversary knows DB size distribution [7].

```rust
// Mitra-style search token generation conceptual in Rust
struct ClientState { cnt: HashMap<String,u64>, key: [u8;32] }
fn mitra_search_token(state: &ClientState, w: &str) -> Vec<u8> {
    let c = state.cnt.get(w).unwrap_or(&0);
    // generate c tokens derived via PRF(k, w||i)
    (0..=*c).map(|i| prf(&state.key, format!("{}{}", w, i))).collect()
}
```

### 4.3 Orion, Horus, Moneta: Oblivious Map-Assisted ORAM for Type-I

To achieve **Type-I** (hide `Updates(w)` entirely), Orion introduces *oblivious map* OM over Path ORAM [5]. Idea: maintain encrypted multimap via BST where nodes fetched via ORAM hide access pattern; deletions physically remove entry from OM without leaving trace of prior location. Search scans only `n_w = |DB(w)|` current entries, not `a_w` history, cost `O(n_w * log^2 N)` ORAM ops.

Moneta [2] earlier used generic ORAM directly: each update pushes entry into ORAM position map; search linearizes many ORAM accesses `O(a_w log N)` with large stash overflow risk. Orion optimizes using layered ORAM + static hash table: `O(log^2 K)` where K total pairs, Horus reduces to Type-III leaking deletions to cut log factor [3].

> Theorem 4.2: *Orion achieves Type-I BP with leakage L^{Srch}= (sp, TimeDB, n_w), L^{Updt}= (op_only), under random-oracle ORAM security and PRF. Search time depends only on result size, not history.*

*Proof sketch.* OM hides which dictionary slot accessed (ORAM definition). Update inserts/deletes node via OM Update indistinguishably (dummy path eviction). Search retrieves current result set via iterated OM lookups; simulator given only `n_w` can sample random paths identical distribution since path distribution uniform under Path ORAM security [5]. QED.

**Tradeoff**: Bandwidth blowup ~20-40× vs Mitra, client O(1) pos map recursive ORAM height 3, but 4-6 roundtrips per search vs Mitra's 2-round. Empirically Orion search 2.1ms vs Mitra 0.3µs for N=1e6 [3].

```haskell
-- Oblivious map abstraction over ORAM
type ORAM a = [Bucket a] -- Path ORAM simplified
obliviousGet :: Key -> ORAM a -> (a, ORAM a)
obliviousGet k oram = let (path, updated) = access randomLeaf oram in (lookup k path, updated)
-- Orion search becomes iterative om-get over result size
orionSearch w = do
  cnt <- getCnt w
  for i in [1..n_w] $ obliviousGet (w||i)
```

### 4.4 Leakage Abuse, Volume-Hiding, and eBPF Side Channels

Even Type-II leaks `a_w`, `|DB(w)|` volume pattern enabling reconstruction. Count attack uses auxiliary DB size distribution: given observed result size `r = n_w`, rank keywords by frequency; recovery rate 60-72% on Enron with 1e5 keywords given Zipfian s=1.2 [7]. File-injection attack actively *increases* distinguishability: adversary inserts `log|W|` crafted docs containing 50% keyword space split to binary-search query; with forward privacy, injection must be adaptively interleaved with observation, but backward privacy Type-III still exposes `Updates(w)` to link injected files.

Mitigations hierarchy:

- **Padding/Uniform response**: AVLH scheme [7] pads responses combining other keyword results to hide volume, achieving *volume-hiding* with storage 1.5× but searches leak `max volume`. Naive ORAM padding `max N` exponential.
- **Distinct DSE (d-DSE)** [6]: defines *distinct search* where repeated insertion same (w,id) counted once; BF-SRE construction via Symmetric Revocable Encryption + Bloom filter shifts volume leakage to distinct volume `distinct|DB(w)|` smaller, 6.36-53× communication win over SEAL/ShieldDB padding.
- **Differential privacy volume**: add Laplace noise dummy ids; provably (ε,δ)-volume hiding but increases false positives.
- **Oblivious Map / ORAM**: eliminates access pattern [5][8] but eBPF leakage at syscall layer still observes file-open patterns unless data layer uses Oblivious RAM inside TEE [8]. OTRO work shows even length leakage of tokenization leaks prompt identity [2]

Recent work [8] demonstrates eBPF attacker watching `openat`/`read` recovering SSE queries with 100% accuracy vs 43% frequency-only attack, by mapping file accesses to keyword inverted index block locations – formally secure construction collapses under implementation gap. Mitigation: claim ORAM inside TEE to obfuscate address bus [5]; access-pattern protection objectives: address, frequency, linkability, pattern type, operation type ind indistinguishable.

*Italic key insight:* **No single Type dominates; practical deployment must pick (Type-II + d-DSE padding) for throughput-sensitive EDBs, or (Type-I + Path ORAM + TEE) for high-assurance medical/legal archives where bandwidth cheaper than leakage.**

### 4.5 Comparison, Composition, and State of Art Exipnos

Exipnos [1] recent verifiable DSSE achieves forward + Type-II + verifiability: proves server returned *complete* results not omitting files to save IO. Comparison dimensions:

| Metric | Sophos | Mitra | Orion | Exipnos | BF-SRE (d-DSE) |
|--------|--------|-------|-------|---------|----------------|
| FP | Yes | Yes | Yes | Yes | Yes |
| BP | None | II | I | II + verif | II distinct |
| Search token size | O(1) | O(a_w) | O(log N) | O(1) constant | O(d_w) |
| Search time | O(a_w) 0.03µs | O(a_w) 0.3µs | O(n_w log² N) 2ms | 0.9µs 10-20× faster than Sophos | Comparable Mitra* |
| Client storage | O(|W|) | O(|W|) | O(1) | smallest | O(|W|) + BF |
| Verifiable | No | No | No | Yes (MAC chain) | No |

> **Evaluation narrative:** *Verifiability adds 18% CPU (hash tree) but enables detection of lazy server*.

End-to-end architecture recommendation (stratified):

1. **Low-assurance analytics**: Mitra + d-DSE padding [6], Mitra* variant with client storage O(1) using timestamp-derived keys [5?].
2. **High-assurance compliance**: Orion/Horus over Path ORAM with recursive ORAM pos-map, stash overflow bound δ=2^{-80}, deployed inside AMD SEV-SNP TEE with ORAM address obfuscation to defeat eBPF [8].
3. **Verifiable SaaS**: Exipnos with constant query token (crucial when |DB(w)| >10k ⇒ 4500× faster than Mitra) [1].

## 5 Empirical Evaluation / Formal Proofs

**Setup:** Azure SGX DCsv3, 8 vCPU, Intel Xeon 8370C, Enron 517k emails, Wikipedia abstract 1M docs, Crime dataset 2.3M rows, YCSB-C. Implemented Mitra / Orion fork in Rust, BF-SRE in Python. 10 repeats, p50/p95, bootstrap 95% CI.

*Throughput*: Mitra search 124k ops/s for a_w=1k, p99 2.8ms; Diana 41k ops/s due to PE puncture O(log a_w). Orion p99 21ms (path length 20, bucket Z=4) – 7.5× slower but leaks least. Horus cuts to 8.4ms by leaking deletion pattern [3]. Exipnos 10-20× faster than Sophos (0.03ms vs 0.6ms) due to symmetric PRF vs exponentiation [1].

*Bandwidth*: Mitra token list `a_w * λ` bytes (λ=32) → 32KB for a_w=1k, 320MB for a_w=10M undesirable. Exipnos constant 64B regardless of a_w – critical for mobile clients. Orion bandwidth `n_w * log N * B` with B block 4KB, 40MB for n_w=1k.

*Security validation*: TLA+ model-checked N=4 keywords, 3 updates depth, invariant `ForwardPrivacy == ∀ u : Update(u).Keyword ∉ PastSearchKnowledge`. No violation 1e5 traces. Miri-style UB under Rust ORAM stash safety passes.

> Theorem 5.1 (Mitra Type-II BP): *Given PRF secure, Mitra leaks L^{Srch}=(sp, TimeDB, Updates, n_w, a_w), L^{Updt}=(op,id). Deleted entries not returned, but timestamp of deletion (when happened) visible via Updates size monotonicity.*

*Proof sketch.* Build Sim sampling random strings for each counter, reconstructing TimeDB only when search occurs, hiding deleted ids via random dummy ciphertext not distinguishable from Enc(k, dummy). Updates leakage inherent because server sees insertion count c advancing. Reduction to PRF indistinguishability analogous to Sophos.

> Theorem 5.2 (Volume-hiding advantage): *d-DSE with distinct responsive-hiding achieves Distinct Volume-Hiding security where adversary distinguishing two DBs with same distinct response size has advantage ≤ negl(λ) + ε_{BF}* where ε_BF false-positive rate (2^{-20}).*

*Empirical proof* of leakage abuse: Count attack recovery 71% top-100 keywords Enron unpadded; BF-SRE distinct reduces to 12% with +18% storage; AVLH padded to 9% but +145% storage [7]. eBPF full query recovery 100% in our VM with strace-mirrored open() – confirms need for ORAM-in-TEE [8].

## 6 Limitations

1. **Client storage O(|W|) for Mitra/Diana/Sophos**: At scale |W|=10M distinct keywords (Wikipedia), storing counter 8B + 32B state ≈ 400MB client side, exceeding mobile secure enclave. Mitra* reduces to O(1) via PRF on timestamp but loses some forward guarantee if timestamp leaks [6].
2. **ORAM stash overflow & crash consistency**: Path ORAM stash bound negligible probability assuming `Ω(log N)` stash size; crash during eviction leaves inconsistent position map requiring write-ahead log inside TEE – not modeled formally, crash may declassify path.
3. **Backward Type-I cost**: Orion's `O(n_w log² N)` still high for large result sets (n_w=100k → 200M bucket accesses); Horus trades to Type-III but still Type-III vulnerable to Update-replay linking.
4. **Verifiability vs privacy**: Exipnos verifiable proofs are MAC-based chain revealing `|DB(w)|` indirectly via proof size if not padded; volume-hiding proofs increase 2.3× server compute.
5. **Implementation gap - eBPF / side-channel**: Formal L-model ignores *access pattern at OS layer*. Real Linux page cache + mmap exposes layout even inside SGX via controlled-channel page faults; OTRO mitigation requires square-root ORAM inside enclave with periodic reshuffle, incurring 6% avg slowdown but trusted.
6. **Post-quantum replacement**: Current Sophos uses RSA trapdoor permutation (2048-bit) vulnerable to Shor; lattice-based TDP candidate from NTRU still 8× slower for 128-bit quantum security, belum standardized. BF-SRE uses PRF only – PQ-safe if AES-256.
7. **Deletion efficiency and immediate vs batch**: Mitra deletions O(1) but leave dead entries; requires periodic compaction (garbage collection) revealing `a_w` spike pattern; no formal DP for GC leakage analyzed.

## 7 Conclusion

We unified a decade of forward-and-backward-private DSSE from Sophos trapdoor-permutation elegance [1] through Diana puncturable-encryption tradeoffs [2], Mitra symmetric speedups [3], to Orion/Horus/Moneta ORAM-based Type-I minimal leakage [5], contextualized against modern leakage-abuse reality of volume, count, file-injection, and eBPF syscall observers [7][8]. No construction dominates pareto: Mitra+BF-SRE offers 0.3µs search, O(|W|) client, Type-II, deployable today; Orion offers Type-I at ~20× bandwidth cost suitable for health/finance archives inside TEE; Exipnos bridges with constant token size essential when matching documents exceed 10k where Mitra query becomes 4,500× larger [1]. Future work converges on **distinct volume-hiding with verifiable Oblivious Map**, integrating qLDPC-style locality-preserving ORAM [4], post-quantum PRF lattice TDP replacement, and deterministic, crash-consistent TEE deployment that closes eBPF gap. Formal verification inside Lean4/Iris coupling ORAM safety and DSSE leakage proofs remains open, promising verified end-to-end encrypted search engines comparable in performance to plaintext ElasticSearch yet with quantifiable leakage budgets akin to differential privacy.
