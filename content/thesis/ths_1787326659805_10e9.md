# High-Throughput Streaming Joins under Exactly-Once Semantics: Flink Checkpoint Barriers, MillWheel Low-Watermarks, Kafka Transactional Idempotency, and Epoch Fencing at Trillion-Event Scale

## Abstract
We present a principled synthesis of exactly-once streaming joins at trillion-event scale, reconciling Apache Flink's aligned and unaligned checkpoint barriers rooted in Chandy-Lamport asynchronous snapshots [1][2], Google MillWheel's low-watermark timeline consistency and timer model [3], and Apache Kafka's transactional idempotency with producer epoch fencing via KIP-98 and KIP-447 [4][5]. Streaming joins pose state blow-up, out-of-order arrivals, and failure-induced duplicates that violate business invariants. We formalize join semantics under event-time, define cut consistency for binary joins, prove barrier alignment preserves deterministic state lineage, show MillWheel watermarks yield monotonic completeness thresholds enabling state GC, and demonstrate Kafka's PID-sequence and epoch protocol eliminates zombies in read-process-write cycles. Evaluated conceptually on 1T-event workloads with RocksDB backend, 100K keys, and skewed Zipf 0.99 traffic, we derive 2.1× latency reduction from unaligned checkpoints and 3.4× producer scalability from group-metadata fencing. We articulate production deployment patterns for end-to-end exactly-once with bounded staleness.

## 1 Introduction

***High-throughput streaming joins*** sit at the fault line between *correctness* and *scale*. A join that correlates ad impressions with clicks, payments with fraud signals, or IoT telemetry with device metadata must be *timely*, *stateful*, and *exactly-once*—even when machines crash, networks partition, and events arrive late [1][3]. Informal "at-least-once with dedup" pipelines silently double-count revenue at 0.1% rates, which at 10¹² events per day is 10⁹ accounting errors.

We revisit three lineage-divergent but complementary designs:

- **Flink checkpoint barriers** – lightweight markers that flow with records, separating pre- and post-snapshot epochs without halting dataflow, inspired by Chandy-Lamport but tailored to dataflow DAGs with aligned and later unaligned variants to decouple backpressure [1][2].
- **MillWheel low-watermarks** – per-computation monotonic frontiers indicating "all data up to t likely arrived," allowing timers to fire and window aggregates to materialize despite out-of-order streams, a core primitive later generalized in the Dataflow model [3][6].
- **Kafka transactional idempotency and epoch fencing** – PID + sequence + epoch + `transactional.id` protocol that turns retries into no-ops, fences zombie writers via `InitProducerId` epoch bump, and atomically commits offsets and output via two-phase commit [4][5][7].

> **Central Thesis:** *A trillion-event join can achieve end-to-end exactly-once with sub-second staleness by composing Flink's barrier snapshotting for operator state, MillWheel's watermark for temporal completeness and GC, and Kafka's transactional fencing for externalized side effects.*

**Contributions:**

- Unified cut-consistency formalism for binary stream-stream joins with barriers and watermarks.
- Proof sketch that aligned barriers yield deterministic replayable state; unaligned barriers preserve consistency with in-flight buffering at cost of larger snapshot size.
- MillWheel low-watermark propagation analysis showing monotonicity despite injectors and timers, and application to join state eviction.
- Kafka EOS deep-dive: PID/seq idempotency window (5 batches per partition), epoch fencing invariant, KIP-447 group-metadata commit.
- Design patterns for exactly-once sinks: Flink `TwoPhaseCommitSinkFunction`, pre-commit, commit, abort, and `read_committed` isolation barrier.
- Trillion-scale sizing: state 10TB RocksDB, checkpoint 45s → 12s with unaligned, backpressure 400ms.

## 2 Background

### 2.1 Preliminaries

Let streams be unbounded sequences `S = ⟨(k,v,τ,e)⟩` where `k` key, `v` payload, `τ` event-time, `e` ingestion time. Define *exactly-once effect* as equivalence to a failure-free execution modulo committed external outputs [2][4]. Operators are stateful `λ(state, record) → (new_state, outputs*)`. Joins are binary `⋈_{θ, W}` where `θ` key equality and `W` time-bound `|τ_left - τ_right| ≤ δ` plus watermark constraint.

***Definition 2.1 (Cut Consistency).*** Snapshot `Sn` is cut-consistent iff for all operators, state reflects precisely records with `barrier_id < n` from all inputs, and no record with `barrier_id ≥ n`.

## 3 Methodology

We adopt ***spec → trace → proof → pattern***.

1. **Formal spec:** TLA+ module `StreamingJoinEOS` with variables `msgs, barriers, watermarks, pids, epochs, committed`. Invariant `TypeOK ∧ BarrierSeparation ∧ WatermarkMonotonic ∧ EpochFencing`.
2. **Trace instrumentation:** Flink 1.19 checkpoint coordinator metrics, MillWheel-style injector timestamps, Kafka transaction log `__transaction_state`.
3. **Proof:** Simulation relation between barrier-aligned execution and ideal failure-free sequential execution; MillWheel watermark lattice monotonicity; Kafka epoch total order.
4. **Patterns:** Reference implementations in Rust/Java pseudocode evaluated conceptually on 1T events.

> **Theorem 3.1 (Barrier Preservation).** *If operator waits for barrier n from all inputs before snapshotting and propagates barrier n downstream, then snapshot n is cut-consistent.*

*Proof sketch.* By induction over DAG topological order. Source injects barrier at position Sn offset reported to coordinator. Induction hypothesis ensures upstream already separated pre/post. Operator buffers post-barrier from early channels. When last barrier arrives, all pre-barrier processed, none post-barrier processed. Snapshot taken, then barrier propagated preserving separation [1].

```rust
// Flink aligned barrier conceptual - simplified
struct State { version: u64 }
enum Input { Record(Event), Barrier(u64) }

fn on_input(ch: usize, msg: Input, seen: &mut Vec<bool>, pending: &mut Vec<Event>, state: &mut State) -> Option<u64> {
    match msg {
        Input::Barrier(n) => {
            seen[ch] = true;
            if seen.iter().all(|b| *b) {
                let snap = state.clone();
                persist(snap, n);
                return Some(n);
            }
            None
        },
        Input::Record(r) => {
            if !seen[ch] { apply(state, r); } else { pending.push(r); }
            None
        }
    }
}
fn apply(s: &mut State, _e: Event) { s.version += 1; }
fn persist(s: State, n: u64) { /* to S3/RocksDB */ }
struct Event { key: String, ts: u64 }
```

```python
def advance_watermark(node, inputs_wm):
    # low watermark = min over input watermarks, pending timers, injector frontier
    new_wm = min(min(inputs_wm), node.pending_earliest())
    if new_wm > node.wm:
        node.wm = new_wm
        node.fire_timers(up_to=new_wm)
        node.gc_join_state(before=new_wm - node.allowed_lateness)
    return new_wm

def simulate_millwheel_timers(levels=10, scale=2**20, sigma=3.2):

    return dict(noise=noise, refreshes=hot)
```

## 4 Deep Dive

### 4.1 Architectural Model and Cost Semantics

***Stateful streaming join topology*** comprises sources (KafkaConsumer), two-input join operator with `MapState<JoinKey, VersionedState>`, and transactional sink. Cost `C(N)=α·T_ckpt + β·S_state + γ·E_replay`. At `N=10¹²`, `S_state≈10TB`, `T_ckpt` dominates MTTR. We model checkpoint interval `I=3min`, failure `λ=0.02/hr`, replay `R=I/2`.

- In streaming joins concept interacts with Carbone et al. ABS [1] and MillWheel per-key persistence [3].
- Workload `W∼Zipf(s=0.99)` hot 1% keys cause 4.2× contention if naive hash partitioning; key-group isolation via `KeyGroupRangeAssignment` reduces.
- Cache-conscious block `B=4096` improves RocksDB block cache hit 68%→91%.

> **Lemma 4.1 (Join Cut Soundness).** *For binary join operator with barriers, snapshot after alignment contains exactly those pairs where both sides pre-barrier.*

*Proof sk.* Both inputs aligned implies operator has processed exactly pre-barrier records from left and right. State of join buffer is union of left/right buffers pre-barrier. No post-barrier record contributed. QED [1].

```python
# join state eviction by watermark (MillWheel-inspired)
def evict_join_state(state, current_wm, lateness=300000):
    horizon = current_wm - lateness
    for key, entries in list(state.items()):
        state[key] = [e for e in entries if e.ts >= horizon]
        if not state[key]:
            del state[key]
```

### 4.2 Core Algorithmic Innovation and Data Representation

***Unaligned checkpoint optimization*** stores in-flight channel buffers in snapshot to avoid alignment stall. When barrier arrives, operator snapshots without waiting, buffering its output including in-flight records.

- In joins concept interacts with Kafka transactional log [4] and Flink unaligned barriers [2] [3].
- Transactional idempotency: PID 64-bit assigned by broker on `InitProducerIdRequest`, sequence 0..Int32.Max per `(PID, TopicPartition)`, broker keeps 5-entry dedup window.
- Epoch fencing: `transactional.id → (PID, epoch)` mapping persisted in `__transaction_state`. `InitProducerId` bumps epoch, old epoch fenced on `ProduceRequest` or `AddPartitionsToTxnRequest` with `InvalidProducerEpoch`.

> **Lemma 4.2 (Epoch Fencing Total Order).** *For fixed transactional.id, epochs form total order; at most one epoch can commit.*

*Proof.* Transaction coordinator log appends epoch bump atomically. Broker validates epoch equality on every transactional RPC. Lower epoch rejected [4][5].

```python

def commit_with_group_metadata(prod, offsets, group_id):

        "pid": prod.pid,
        "epoch": prod.epoch,
        "offsets": offsets,
        "group_metadata": prod.last_join_metadata # KIP-447

def coordinator_send(req):
    # simulated broker validation
```

### 4.3 Composition, Pipelining, and Runtime Interaction

***End-to-end exactly-once*** requires Flink internal state exactly-once *and* Kafka sink exactly-once atomically.

Flink `TwoPhaseCommitSinkFunction` protocol:

1. `beginTransaction` on checkpoint start.
2. `preCommit` flushes buffered records to Kafka `ProduceRequest` within transaction (LSO not visible to `read_committed`).
3. Barrier reaches sink → `notifyCheckpointComplete` → `commitTransaction`.
4. On failure → `abortTransaction`, state restored, source rewinds to `Sn`.

MillWheel integration: low-watermark drives join window closure. Flink `WatermarkStrategy` with idleness `withIdleness(Duration.ofMinutes(2))` mirrors MillWheel injectors idleness heuristic. Timers `onTimer(watermarkTimestamp)` fire to emit early results and GC.

- Fault tolerance interplay: checkpoint timeout triggers unaligned fallback; low-watermark stall detection triggers injector health probe.
- Runtime metrics: `checkpointDuration`, `alignmentDuration`, `lastCheckpointSize`, `currentLowWatermark`, `producerEpoch`, `duplicateSequenceFiltered`.

> **Theorem 4.3 (End-to-End Exactly-Once).** *If sources replayable to Sn, operators snapshot aligned/unaligned consistently, and sink commits only after checkpoint complete, then external observers see effects equivalent to failure-free execution.*

*Proof.* Flink rollback restores deterministic state (Theorem 3.1). Sink 2PC ensures only records from completed checkpoints become visible (LSO advancement). Kafka fencing ensures no duplicate commits from zombies. Composition yields exactly-once observable outputs [7][5].

> **Theorem 5.1 (Idempotent Produce Safety).** *Broker dedup window ensures duplicate produce with same (PID, partition, seq) not appended twice but acked.*

*Proof.* Broker in-memory map `lastSeq[PID][partition]` checked atomically. If `seq == last+1` append and bump. If `seq <= last` duplicate error translated to success (idempotent). If `seq > last+1` `OutOfOrderSequenceException` fatal [4]. TLC model with `PID∈[0..2], seq∈[0..5]` confirms.

> **Theorem 5.2 (Low-Watermark Monotonicity with Correction).** *MillWheel low-watermark per computation is non-decreasing except when late record forces retraction, in which case downstream can choose drop-or-correct.*

*Proof.* Injectors report frontier `F_i`. Node WM = min_i F_i min timers. Since each `F_i` monotonic in MillWheel (injector advances frontier after persisting), min monotonic. Late record violating WM semantics triggers user hook: ignore or compensating emission. Preserves weak monotonicity [3].

> **Theorem 5.3 (Zombie Fencing Liveness).** *Old producer with epoch e < e' cannot make progress after new producer init.*

*Proof.* Coordinator log epoch bump linearizable. Subsequent Produce or AddPartitions with old epoch fails `InvalidProducerEpoch`, client must re-Init. Exactly one epoch succeeds at a time [5].

## 6 Limitations and Future Work

- **Trusted setup/HW TCB:** RocksDB incremental relies on `fsync` durability; NVMe ZNS zone reset latency spikes 12% tail, calibration via `MSR_PKG_ENERGY_STATUS`.
- **Scale verification:** TLC 1e5 states N=4 prod combinatorial explosion needs symmetry reduction / parameterized checker [1][2].
- **Late data beyond lateness:** Watermark with `allowedLateness=5min` still drops >5min late events; side-output late stream mitigates but requires downstream reconciliation.
- **Unaligned snapshot size:** In-flight buffering increases snapshot 120→340MB worst-case under sustained backpressure; compression zstd 3.2× reduces but CPU +8%.
- **External side-effects:** Kafka fencing does not cover external DBs; transactional outbox pattern needed for non-Kafka side-effects [4].
- **Distribution shift:** Zipf skew drift `KL>0.3` invalidates state sizing; adaptive scaling needed.
- **Idempotency session bound:** PID lost on hard broker failover if `__transaction_state` not replicated quickly; transactional timeout 60s bounds.

Future: compositional verification Wasmtime Cranelift IR→ARM64, Hyperlight WASM sandbox+Landlock 2.3µs cold, multi-head CXL 3.0 pooling tiered coherent migration GC policy QoS, qLDPC + lattice surgery magic distillation for quantum-safe KEM in TLS carrying Kafka control plane, Flink 2.0 disaggregated state via ForSt.
