# NVMe over Fabrics and SPDK: User-Space Polling, I/O Uring Integration, and Zero-Copy RDMA Transport for Million-IOPS Storage

## Abstract

This thesis dissects the architectural convergence enabling million-IOPS disaggregated storage: NVMe over Fabrics (NVMe-oF), the Storage Performance Development Kit (SPDK), and Linux io_uring. We analyze how zero-copy RDMA transports (RoCEv2, InfiniBand, iWARP) eliminate kernel TCP/IP overhead via memory-to-memory verbs and HCA offload, how SPDKs user-space poll-mode NVMe driver achieves linear scalability to 80-120M IOPS via lockless queue pairs, hugepage DMA, NUMA-aware reactor pinning and batch doorbell coalescing, and how io_uring narrows the gap through SQ/CQ shared rings, SQPOLL zero-syscall submission, fixed buffer registration, and NVMe passthrough URING_CMD. We present formal transport models, end-to-end latency breakdowns, and micro-architectural bottleneck analysis across PCIe 5.0 SSDs and 200/400GbE fabrics, deriving design guidelines for hybrid polling, CQ coalescing, and memory registration strategies for production NVMe/TCP and NVMe/RDMA deployments.

---

## 1. Introduction

The renaissance of storage performance driven by 3D TLC NAND, Intel Optane limitations, and PCIe 5.0 has brutally exposed the **software inefficiency** of the traditional Linux block stack. Modern devices such as the Kioxia CM7-R advertise **2.45M random 4KiB IOPS** per drive [8], while 400GbE NICs like NVIDIA ConnectX-7 push **400 Gbit/s** line rates. Yet production database engines still struggle to saturate a single device with kernel interfaces, consuming a majority of CPU cycles in system-call dispatch, interrupt handling, and copy-heavy TCP/IP processing [2][6].

NVMe over Fabrics (NVMe-oF) emerged as the architectural answer to disaggregation: preserving the NVMe queue semantics over a network fabric while permitting *multiple transports* [1]. Among those, **RDMA-based transports dominate latency-critical AI training and HPC domains** due to their zero-copy and kernel-bypass capabilities [1]. However, the software endpoint remains decisive. Intel's **SPDK** re-architected the entire storage data plane in user space, with a polled-mode NVMe driver that eschews interrupts entirely, delivering **80M IOPS on a 2U Xeon system** in 2021 and **120M IOPS** on similar hardware in 2023 with scalability locked to core count [3][4].

Linux's response, **io_uring**, introduced in kernel 5.1, reimagines the syscall boundary via shared memory submission and completion rings (SQ/CQ), SQPOLL, and registered buffers. Early systematic studies in *SYSTOR'22* demonstrated that with correct polling configuration, **io_uring can approach SPDK performance given enough cores**, but scalability and fio self-bottlenecks remain nontrivial [6][7].

> **Theorem: Zero-Copy Transport Dominance.** For NVMe-oF over a lossless fabric with RTT $R$, MR registration cost $C_{reg}$ amortized over transfer size $S$, and CPU cycles per byte $c_{tcp}$ vs $c_{rdma}$, RDMA outperforms TCP iff $S > \frac{C_{reg} \cdot B}{c_{tcp}-c_{rdma}}$ where $B$ is effective bandwidth. Empirically $c_{tcp}\approx 2.3\times c_{rdma}$ under 100GbE+ at QD128 [1][7].

This work contributes:

- A unified model of NVMe-oF transport bindings: NVMe/RDMA, NVMe/TCP, FC-NVMe [1][2]
- Deep dissection of SPDK reactor, lockless queue, and memory subsystems [5]
- io_uring integration paths: passthrough, bdev, and xNVMe shim [7]
- Empirical latency breakdown for million-IOPS stacks and design heuristics for hybrid polling

## 2. Background

### 2.1 NVMe over Fabrics Specification and Transport Bindings

The NVM Express organization published NVMe-oF 1.0 on **June 5, 2016**, building on NVMe 1.2 [2]. NVMe-oF defines a layered architecture: a common NVMe queue and command set encapsulated in *Fabrics capsules*, then mapped to a transport. Version 1.1 (2019) added TCP binding, asynchronous discovery, end-to-end flow control, and finer-grain I/O queue management [1].

*Key transports in 2026:*

- **NVMe over RDMA (RoCEv2, InfiniBand, iWARP):** Memory-to-memory semantics, WRITE/READ verbs bypass the remote CPU, kernel bypass, sub-5µs added latency. Dominant in HPC but requires lossless Ethernet with PFC/ECN, raising operational complexity [1][2].
- **NVMe/TCP:** Standard sockets, per-core SQ/CQ pairs to avoid lock contention, PDUs for Command/Data/Response. Superior universality and commodity NIC support, but host-side packet processing becomes the bottleneck at 100GbE+ [1]. Kernel implementation added in Linux 5.x [6].
- **FC-NVMe (NVMe/FC):** Mapping via INCITS T11, coexistence with SCSI via same LWBAs, firmware-upgradable FC switches at 32/64Gbps.

The protocol retains **90% similarity** to local PCIe NVMe, allowing existing drivers to be ported [2].

### 2.2 Linux Block I/O Evolution: libaio, SPDK, io_uring

Three eras coexist:

| API | Execution Model | Syscalls/IO | Copies | Core Affinity |
|-----|----------------|-------------|--------|---------------|
| POSIX `psync` | synchronous, one thread per IO | 1+ | 1-2 | kernel migrated |
| `libaio` | kernel AIO, interrupt-driven | 1 submit + 1 reap | 1 | kthread |
| `io_uring` default | shared rings + io_uring_enter | amortized ~0.1-0.5 | 0-1 with fixed buffers | configurable |
| `io_uring` SQPOLL | kernel SQ poll thread | zero in steady state | 0-1 | pinned poll thread |
| **SPDK** | user-space polled NVMe | zero | zero | reactor pinned |

Micro-architectural studies by Didona et al. *SYSTOR'22* reveal that **polling design impacts performance more than interface choice** [6]. At low QD=1, psync achieves 81-95 KIOPS competitive with SPDK due to low setup cost, while iou (io_uring default) regresses 17-72% due to ring overhead [7]. At high load scale-out, SPDK exceeds io_uring by >10× unless hybrid polling and careful CPU partitioning are applied [7].

### 2.3 Zero-Copy RDMA Primer

RDMA eliminates the network bottleneck by permitting a NIC to *directly place* payload into remote application memory via memory keys (RKEY), bypassing remote CPU [2]. The NIC offloads segmentation, CRC (RoCEv2 employs ICRC), and transport ACK. **Zero-copy** implies application buffer → HCA DMA → wire → remote HCA → target NVMe PRP without intermediate `memcpy`.

*Critical fabric tuning:* RoCEv2 requires Priority Flow Control to avoid drops, else Go-Back-N retransmission collapses throughput. [1].

## 3. Methodology

Our analysis triangulates three sources: **(i)** SPDK 23.x tree inspection [5], **(ii)** fio-based reproductions guided by *Performance Characterization of Modern Storage Stacks* [7], and **(iii)** production traces from NVMe/TCP and NVMe/RDMA Cloud deployments [1].

We instrument:

- **Latency breakdown:** `bpftrace` + `perf c2c` for CQ miss rates, using SPDK `bdev_nvme` with JSON-RPC latency histograms (p50, p99, p99.9).
- **Instruction-level:** `perf stat` cycles/op, branch misses, DTLB MPKI.
- **Network:** RNIC counters `rx_pause_duration`, `roce_adaptive_retrans`.

Assumptions: Intel Xeon Ice Lake/Sapphire Rapids, 2× NUMA, 512GB DDR5, 24× NVMe Gen4 SSDs, 2× 200GbE ConnectX-6 Dx, Linux 6.6, DPDK 23.11.

### 3.1 Formal Model for SPDK Reactor Scalability

Let \(N_{cores}\) be reactors, each polling \(Q\) NVMe queue pairs with no locks. Ideal IOPS:

$$IOPS_{ideal} = \frac{N_{cores} \cdot 10^9}{L_{media} + L_{pcie} + L_{poll}}$$

Where \(L_{poll}\) approaches **200-300ns** per CQ peek in SPDK [5], versus **2-3µs** for interrupt path including MSI-X and softirq.

> **Theorem: Linear SPDK Scalability Condition.** SPDK scaling is linear iff (1) each NVMe SQ is accessed by at most one reactor (no `pthread_mutex`), (2) hugepage DMA pool does not cross NUMA, (3) CQIs are dense (no hole-skipping). Violating (1) induces MESI bouncing $O(Q^2)$.

## 4. Deep Dive

### 4.1 SPDK User-Space Polled-Mode Architecture

SPDK moves **all necessary drivers into user space** and operates polled-mode instead of interrupt-driven [5]. Core components:

- **NVMe Driver:** A C library (`spdk/nvme.h`) directly mapping BAR0 doorbells via `uio/vfio`. QP creation uses DMA-coherent hugepages (2MiB). Submission: `spdk_nvme_qpair_submit_request()` enqueues to shared host-controller queue but does *not* ring doorbell until batch flush.
- **Reactor:** Event-driven executor, one per lcore, polling subsystems: `bdev`, `nvmf`, `accel`. No preemptive scheduling; long-completions must yield.
- **Bdev Layer:** Virtual block stack (`bdev_malloc`, `bdev_nvme`, `bdev_lvol`) performing similar to kernel bio but lock-free via message passing.
- **Transport Targets:** `nvmf_tgt` supporting RDMA and TCP. CPU efficiency **10× vs Linux kernel** for NVMe-oF targets [4][9].

**Why Polling Wins:** Interrupts coalesce but cause tail-latency jitter (99.9% >> p50). Polling keeps data in L1/L2 cache by pinning. Intel blog exposed that SPDK saturates **8× P3700 SSDs with ONE core** where kernel requires 4+ [4].

```python
# Conceptual SPDK reactor polling loop (Python pseudocode illustrating lockless polling)
import spdk_bdev as bdev
from collections import deque

class Reactor:
    def __init__(self, lcore_id, qpairs):
        self.lcore = lcore_id
        self.qpairs = qpairs  # list of (ns, qpair) pinned to this core
        self.pollers = []
        self.completions = deque()
    
    def register_poller(self, fn, period_us=0):
        self.pollers.append((fn, period_us))
    
    def run(self):
        while True:
            for ns, qp in self.qpairs:
                # SPDK-style zero-copy polling - no syscall
                wc = qp.process_completions(max_completions=32)  # spdk_nvme_qpair_process_completions()
                if wc:
                    self.completions.extend(wc)
                    # Direct callback without kcontext switch
                    for c in wc:
                        c.cb_fn(c.ctx, c.status)
            for poll_fn, _ in self.pollers:
                poll_fn()
```

*Analogous Rust reactor:* Tokio cannot replace reactor because its I/O source is SPDK DMA, not epoll.

```rust
// Rust conceptual: polling NVMe completion queue via VFIO mmap
use std::ptr::NonNull;
use std::sync::atomic::{AtomicU32, Ordering};

struct NvmeCq {
    doorbell: NonNull<AtomicU32>,
    cq: Vec<CompletionEntry>, // DMA coherent
    head: usize,
}

impl NvmeCq {
    #[inline(always)]
    fn poll(&mut self) -> Option<CompletionEntry> {
        let cqe = &self.cq[self.head % self.cq.len()];
        // phase bit check - no lock
        if (cqe.status & 0x1) == expected_phase {
            let entry = *cqe;
            self.head += 1;
            unsafe { self.doorbell.as_ref().store(self.head as u32, Ordering::Release); }
            Some(entry)
        } else { None }
    }
}
```

SPDK caveats: **core burning** (100% CPU even idle), hugepage fragmentation, no fork-safety. Latter mitigated by `_reactor` isolation and DPDK EAL.

### 4.2 Zero-Copy RDMA Transport for NVMe-oF

In NVMe/RDMA, the capsule is mapped to RDMA verbs:

1. **NVMe COMMAND** → RDMA SEND with immediate data containing SQE capsule (64B + inline SGL).
2. **Data Transfer** → Target RDMA WRITE/READ directly into initiator MR. No intermediate bounce buffer: PRP entry points to MR VA/RKEY.
3. **Response** → RDMA SEND containing CQE.

This eliminates two kernel copies of traditional TCP stack. In NVMe/TCP, each PDU requires `tcp_sendmsg()` + `skb` allocation + `copy_from_iter` → **30-50% driver overhead** exposed in literature [4].

Registering memory for RDMA remains costly: `ibv_reg_mr()` 5-20µs. SPDK amortizes via **memory domains** and `spdk_mem_register()` caching with LRU invalidation on `munmap` hazards [4]. For small IO (4KiB), registration overhead dominates unless using *inline* transfer (<= 4KiB inline) or *fixed buffers* analogous to io_uring.

> **Theorem: Memory Registration Amortization.** Let registration cost $C_R$, IO size $S$, pipeline depth $QD$. Effective cost per IO $C_{eff}=C_R/(QD\cdot r)$ where $r$ is reuse factor. Million-IOPS requires $C_{eff}<0.5µs$ ⇒ $r>40$ at $QD=128$ for $S=4KiB$.

SPDK's target path uses `rdma_cm` to establish RC QPs with *shared receive queue (SRQ)* to reduce memory. Flow control relies on host managing I/O queue depth via fabricated SQ tail pointer, **not** TCP congestion.

### 4.3 io_uring Integration and the xNVMe Bridge

io_uring provides three integration tiers for NVMe-oF:

1. **Block Layer via `io_uring`** – e.g., PostgreSQL 16+ registers files with `IORING_REGISTER_FILES` and issues `IORING_OP_READ` through filesystem. Preserves VFS, but limited to block size aligned IO [8].
2. **Passthrough `IORING_OP_URING_CMD` with NVMe passthrough** – Linux 5.17+ permits `NVME_IOCTL_IO_CMD` via io_uring without mapping through bio. This is fastest but breaks FS abstractions.
3. **xNVMe Shim** – Samsung's xNVMe library abstracts `libaio`, `SPDK`, `io_uring passthrough` under a unified `xnvme` handle, allowing runtime selection [7]. SNIA SDC 2023 reported early perf **parity within 15% of SPDK when using fixed buffers + SQPOLL** [7].

The salient io_uring primitives for million-IOPS:

- `IORING_SETUP_SQPOLL` – Spawns kernel thread polling SQ, **eliminating `io_uring_enter`** syscall. Cost: that thread burns core (~ SPDK).
- `IORING_REGISTER_BUFFERS` – Pre-register iovecs, avoid `iovec` copy per IO.
- `IORING_FEAT_FAST_POLL` + multishot – For NVMe/TCP socket accept loops.

```c
// C: io_uring SQPOLL with registered NVMe passthrough (Linux 6.x)
struct io_uring ring;
io_uring_queue_init(512, &ring, IORING_SETUP_SQPOLL | IORING_SETUP_SQ_AFF);
// Register fixed buffers to avoid MR re-registration
struct iovec iovs[128]; // hugepage-backed
io_uring_register_buffers(&ring, iovs, 128);

struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_uring_cmd(sqe, IORING_OP_URING_CMD, -1);
sqe->uring_cmd_flags = IORING_URING_CMD_FIXED;
struct nvme_passthru_cmd *cmd = (void*)sqe->cmd;
cmd->opcode = nvme_cmd_read;
cmd->nsid = 1;
cmd->addr = (__u64)iovs[0].iov_base;
cmd->data_len = 4096;
io_uring_submit(&ring);
```

The IBM-VU benchmark underscored **fio self bottleneck at high scale**: once fio spawns 16+ jobs to saturate Optane, userspace `fio` thread accounting dominates cycles, masking API differences [8]. Direct IO engines under-test must bypass fio via `io_uring` fixed files to observe true device limits.

### 4.4 Million-IOPS System Design

Achieving 10M+ IOPS per socket demands disciplined integration:

- **Queue Depth Math**: Per SSD 2.45M IOPS at QD128 implies **52K IOPS per QD**. To hit 120M IOPS requires ~24 SSD × 128 QD ≈ 3072 inflight. SPDK reactor processes 32 completions per poll loop to amortize doorbell writes (write coalescing).
- **Affinity:** Pin reactors to NUMA-local SSDs. Crossing NUMA doubles tail p99 due to QPI hop (Home Agent contention).
- **Interrupt vs Polling Hybrid:** Use `NAPI`-like adaptive: poll 50µs after IO burst, then sleep. DPDK/SPDK now ships `spdk_thread_poll` with backoff threshold.
- **RDMA Congestion:** Fine-tune `ecn_low`, `ecn_high`, `cnp_dscp`. Without Tuning, PFC storms collapse RoCEv2 to 12% line rate [1].

| Configuration | Single-core IOPS (4KiB Rand Read) | p99 Latency | CPU Efficiency |
|---------------|-------------------|-------------|----------------|
| Linux NVMe kernel + irq | 400K | 120 µs | baseline |
| io_uring default (iou) | 280K (-30%) | 95 µs | 1.1× |
| io_uring SQPOLL + fixed | 1.8M (+350%) | 55 µs | 2.3× |
| SPDK polled-mode | 3.3M (+725%) | 18 µs | 6.8× |
| SPDK + NVMe/RDMA SRQ | 3.1M (RDMA) | 22 µs E2E | 8× vs kernel NVMe-oF |

*Numbers derived from [3][4][6] and Xeon E5-2695v4 baseline; newer Sapphire Rapids 2-3×.*

## 5. Empirical Analysis / Proofs

### 5.1 Proofs Sketch

We sketch correctness for zero-copy MR validation:

**Lemma 1 (No UAF during RDMA WRITE).** If initiator MR is registered with `IOVA=VA` and reference-counted to completion CQE using `spdk_mem_map`, and target respects RDMA RKey validity check, then payload cannot be overwritten before completion because initiator's CQ handler defers `spdk_free` until `cqe->phase` flips.

*Proof:* MPKI-based hazard detection: If `munmap` occurs inflight, SPDK's notifier fires `spdk_mem_unregister` invalidating MR before NIC DMA → RDMA error → retry path distinguishes from data corruption ∎

**Lemma 2 (Poll Liveness).** Reactor with at least one poller polling QP pair infinitely often guarantees completion visibility within bounded cycles if device obeys NVMe SQ/CQ forward progress (spec 1.4b clause 3.3.5.3) [1].

### 5.2 Performance Analysis Methodology

Reproducing Didona et al. setup but with PCIe5 devices: Use fio `ioengine=spdk` vs `io_uring` with `hipri`.

**Observation A – Polling CPU Instruction Bloat:** Polling libraries `ious`, `iouc`, `spdk` consume **2.3× instructions** vs non-polling but improve IOPS 1.7× at QD1 [7]. Tradeoff justified only when `IOPS per Watt` metric dominates.

**Observation B – fio Bottleneck Partitioning:** At 8 devices QD128, fio's own `io_u` completion processing consumes 18% cycles for io_uring vs 4% for SPDK because SPDK completions are directly C callbacks while io_uring requires CQE ring parsing and `io_uring_cqe_seen()` [7].

**Observation C – Scheduler Antagonism:** CFQ/BFQ/mq-deadline introduce up to **50% overhead** attributed to global `sbitmap` lock [7]; SPDK bypasses OS schedulers wholesale. For NVMe-oF disaggregated stacks, use `none` scheduler.

*End-to-end SE.* Real deployment Simple: simplyblock powered storage reports achieving NVMe speed without building SPDK infra from scratch while claiming microsecond latencies attributed to user-space polled-mode [9].

## 6. Limitations

- **Core Tax:** Pure polling burns 100% core regardless of load. In cloud tenancy where $/vCPU high, kernel interrupt path may be cheaper at <200K IOPS per volume. Hybrid interrupt+polling mitigable but naïve hints cause 3× tail regression [6].
- **Security Isolation:** User-space driver exposes NVMe BAR to unprivileged process via `/dev/uio` or VFIO IOMMU. CVE-2022-46146 type DMA attacks feasible unless IOMMU strict-mode enabled incurring IOTLB miss penalty 6-12%. Future directions: Intel TDX/AMD SEV IO isolation.
- **Filesystem Inefficacy:** SPDK offers blobstoreFS (`spdk_blob`) but lacks POSIX features: unlink semantics, permission ACL, journaling, extended attrs. Production systems on ext4/xfs cannot adopt SPDK transparently, necessitating io_uring path [8].
- **RoCE Operational Complexity:** PFC/ECN misconfigurations induce head-of-line blocking persisting seconds [1]. NVMe/TCP mitigates but loses 25-40% tail vs RoCE.
- **Memory Pinning Limits:** Registered MR memory cap (`ulimit -l`) and IOMMU page table size limit large working sets > 1TB; registration churn top source of tail at scale.

---

## 7. Conclusion

Disaggregated storage at million-IOPS scale mandates shedding kernel abstractions selectively, not recklessly. NVMe over Fabrics defines the control wire format, RDMA zero-copy reduces CPU per IO metric by up to **2.3×** while avoiding copies, SPDK's user-space poll-mode achieves order-of-magnitude IOPS-per-core gains through lockless reactors, hunched hugepages, and direct BAR doorbells, and io_uring offers credible middle-ground preserving FS abstractions via SQPOLL, fixed buffers, and passthrough commands.

The future is neither *pure kernel* nor *pure userspace* but **negotiated heterogeneity**: storage daemon polling RDMA QPs via SPDK reactor, exposing block services to compute via NVMe/TCP with io_uring front-ends, transparent to PostgreSQL buffer managers using multishot io_uring network shuffle that recent VLDB guidelines improved by 14% [8]. Administrative tactics such as Global lock avoidance, NUMA-aware reactor placement, and adaptive polling substantiate the path from 80M to 120M IOPS [3][4] and impending 200M+ on PCIe6.

For practitioners: start with `none` scheduler, enforce vfio-iommu strict, amortize MR; deploy SPDK `nvmf_tgt` for performance domain but permit Linux NVMe/TCP initiators for breadth; employ io_uring SQPOLL fixed files for metadata-heavy workloads paying p99.
