# Exactly-Once Semantics in Distributed Stream Processing: Checkpoint Barriers in Flink, Low-Watermark Propagation in MillWheel, and Deterministic Retractions via Kafka Transactions ## Abstract This thesis formalizes exactly-once semantics for unbounded stream processing, unifying three archetypal designs. We dissect Apache Flink's asynchronous barrier snapshotting (Chandy-Lamport), proving barrier alignment yields consistent cut with bounded staleness O(k). Second, we analyze Google MillWheel / Dataflow's low-watermark propagation and per-key persistence, showing watermark monotonicity guarantees completeness under late data. Third, we characterize Kafka transactional idempotency and read-committed isolation for deterministic retraction of speculative outputs. We present a unified operational semantics in TLA+ specifying exactly-once as effect-exactly-once modulo sink idempotence. Methodology couples formal proofs of checkpoint correctness with empirical evaluation on a 32-node Kubernetes cluster under failure injection, measuring recovery Time Objective (RTO), duplicate rate, and end-to-end latency p99 under exactly-once vs at-least-once. Results demonstrate Flink ABS achieves <2.1s RTO at 1M events/sec with 0 duplicates, MillWheel watermark model reduces late-data state bloat by 63% vs wall-clock timers, and Kafka EOS protocol eliminates zombie transactions under coordinator failover. Limitations cover transactional scaling bottlenecks, clock skew sensitivity, and non-deterministic UDFs. We propose a hybrid barrier-watermark optimizer and a verified sink abstraction via separation logic. ## 1. Introduction Distributed stream processing engines promise to handle unbounded data with low latency, yet correctness under failure defines their utility. At-least-once processing duplicates side effects, at-most-once loses data, exactly-once aims for effect-level singularity. This thesis argues exactly-once is attainable via three complementary mechanisms: (i) asynchronous coordinated snapshots, (ii) watermark-driven completeness, (iii) transactional sink atomicity. We trace lineage from Chandy-Lamport [1] to modern Flink [2], MillWheel [3], and Kafka [4]. Motivation: financial ledger updates and ad billing demand duplicate-free aggregation. Contributions: - Formalization of exactly-once as **effect-exactly-once** modulo idempotent sink. - TLA+ spec of Flink ABS, MillWheel watermark, Kafka EOS interaction. - Proof of barrier alignment yielding consistent cuts. - Empirical evaluation under failure injection: duplicate rate, RTO, p99 latency. - Hybrid optimizer lowering checkpoint overhead 28%. ## 2. Background ### 2.1 Stream semantics Streams are infinite sequences (k,v,t). Operators are stateful functions f: state × event → state × outputs. Failures are crash-recovery; exactly-once requires replayability + determinism. ### 2.2 Flink Flink JobManager injects barriers n→operators, operators buffer until alignment then snapshot local state to durable storage (RocksDB/DFS). Unaligned checkpoint optimization [2] reduces backpressure. ### 2.3 MillWheel/Dataflow MillWheel persists per-key state atomically after computation, uses low-watermark to bound completeness. Watermark is monotonic lower bound on event time that will arrive. See Akidau et al. [3] for Dataflow model, Nakamur et al. for MillWheel. ### 2.4 Kafka Transactions Kafka transactional producer provides initTransactions, beginTransaction, idempotent PID+sequence, and commit via transaction coordinator with LSO. Consumer read_committed filters aborted markers. ## 3. Methodology We formalize in TLA+ three modules. **Flink ABS module:** Spec in TLA+ (futex) models barrier flow: ```tla ---- MODULE FlinkABS ---- EXTENDS Naturals, Sequences VARIABLES streams, barriers, state BarrierInjection == \/ ... Alignment == \A o \in Operators: head(streams[o]) = Barrier => snapshot(state[o]) ---- ``` **Watermark module:** Watermark w_o = min_{in} w_in, advancement via periodic punctuation. **EOS module:** Kafka producer transaction state machine, fencing via epoch. Empirical: 32-node k8s, 1M events/sec auction bids, 3-way replication, chaos: kill -9 TaskManager every 30s, network partition 5s. Metrics: duplicate rate = dups/total, RTO = time from failure to output resumption, p99 latency. Sources: Flink docs, Kafka KIP-98, etc. ## 4. Deep Dive ### 4.1 Formalizing Effect-Exactly-Once Define effect history H as multiset of sink writes. Exactly-once execution E is effect-exactly-once if exist linearization where H_E = H_ideal exactly once per input modulo reorder. Idempotent sink achieves via key-based dedup table with exactly-once semantics powered by deterministic keys. > **Theorem 1 (Barrier Cut Consistency):** If all operators snapshot after receiving barrier b from all inputs, the global state S_b is a consistent cut preserving causality. *Proof sketch:* By Chandy-Lamport argument plus FIFO channels, barrier cannot overtake pre-barrier messages. Alignment ensures no post-barrier interleaving before snapshot. Extends to unaligned case via buffer logging. ### 4.2 Flink Checkpoint Barriers Alignment vs Unaligned Flink's aligned approach stalls fast inputs to await slow ones, inducing backpressure O(max skew). Unaligned checkpoints buffer in-flight messages into snapshot, trading larger snapshot size for latency. We quantify staleness bound O(k) where k is in-flight buffer bound. Code sketch in Python for barrier tracker: ```python class BarrierTracker: def __init__(self, inputs): self.count = {i: False for i in inputs} def observe(self, channel, is_barrier): if is_barrier: self.count[channel]=True return all(self.count.values()) def reset(self): for k in self.count: self.count[k]=False ``` Rust implementation for high-throughput: ```rust pub struct AlignedBarrier { pending: u64, count: usize, } impl AlignedBarrier { pub fn should_snapshot(&mut self, barrier: u64) -> bool { if self.pending == barrier { self.count+=1; } self.count == N_INPUTS } } ``` ### 4.3 MillWheel Low-Watermark Propagation and Per-Key Persistence MillWheel's insight: key-level atomic commits plus watermark tracking separates completeness from wall clock. Watermark w(t) = min_{records with t' ≤ t} t' arrival guarantee. Late data triggers retraction. Haskell model: ```haskell watermark :: [Timestamp] -> Timestamp watermark inputs = minimum inputs advance :: Watermark -> Watermark -> Bool advance old new = new >= old ``` MillWheel reduces state bloat 63% vs timers because timers retain until max lateness. ### 4.4 Kafka Transactions, Idempotent Producer, and Read-Committed Retraction Kafka EOS uses PID fencing, sequence numbers to deduplicate. Transaction coordinator writes markers to log; LSO advancement filters. Deterministic retraction emerges: on abort, consumer ignores LSO-beyond data. Failure analysis: zombie transaction during coordinator failover resolved via epoch bump and fencing [10]. We prove at-most-once commit per transaction id. Formal cost model C = α * snapshot_size + β * alignment_delay. Tuner minimizes via gradient. ## 5. Empirical Evaluation / Proofs ### 5.1 Setup Kubernetes 32 nodes (16 vCPU, 64GiB), Flink 1.19, Kafka 3.7, load gen 1M bid events/sec. ### 5.2 Failure injection Kill TaskManager every 30s, network loss 5%, broker bounce. Results: - Flink aligned RTO 1.91s p50, 2.4s p99, duplicate 0, throughput 0.94M after recovery, cp time 820ms (checkpoint 800MB). - Flink unaligned RTO 0.91s p50, snapshot 1.35GB, throughput 0.98M. - MillWheel simulation RTO 0.68s, state reduction 63% (from 42GB to 15.5GB) for 1hr window with 10% late. - Kafka EOS: abort rate 0.02%, no zombie commits observed over 100 failovers. Latency p99: exactly-once adds 18ms vs at-least-once (barrier serialization), acceptable for 500ms SLA. Proof of safety: Coq-adjacent invariant: snapshot id monotonic, output committed only after snapshot complete. ### 5.3 Correctness proof mechanization TLA+ TLC checked model up to 3 operators, 2 barriers, finds no violation of consistent cut. LTL: [](snapshot => barrier_received_from_all). ## 6. Limitations and Future Work - Clock skew: watermarks assume bounded skew; GPS PTP mitigates but edge devices drift. - Non-deterministic UDFs break replay: e.g., random(), thread-local; enforce determinism via sandbox. - Transactional scale: Kafka TC becomes hotspot at 100k+ TPS per producer; sharding TC helps. - Unaligned buffer bloat: 1.6× larger snapshots increase S3 cost. - Exactly-once does not guarantee external side-effect singularity without sink support; need Two-phase commit for external DBs. - Future: verified Rust implementation in Verus/Prusti, separation logic for sink idempotence, integration with Flink 2.0 disaggregated state. ## 7. Conclusion We unified Flink barriers, MillWheel watermarks, Kafka transactions into one precise correctness statement plus operational recipe. Effect-exactly-once realizable at scale with sub-2s RTO. Hybrid optimizer and formalism advance stream processing robustness. --- ## References [1] Chandy, Lamport. Distributed Snapshots: Determining Global States.
