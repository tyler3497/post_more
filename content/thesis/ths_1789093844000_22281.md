# The DOT Calculus: Path-Dependent Types and the Sound Foundations of Scala 3

## Abstract

The Dependent Object Types (DOT) calculus is the first core calculus to formalize Scala's path-dependent types — types of the form `x.T` that refer to abstract type members through term-level paths — on a provably sound footing. Its distinguishing features, abstract type members with lower and upper bounds, type selections, intersection and union types, and recursive object types, capture precisely the constructs that make Scala's type system expressive and that for years resisted a soundness proof: type refinement, mixin composition, and a lattice-structured subtyping relation all break classical metatheoretic properties such as environment narrowing and subtyping transitivity. This essay reconstructs the decade-long arc from the first DOT formulation to its soundness argument via definitional interpreters, analyzes the "bad bounds" phenomenon and why runtime values keep the lattice consistent, surveys extensions such as pDOT and ιDOT, and contrasts DOT with System F-sub and Featherweight Java. We explain how DOT now serves as the theoretical core of Scala 3's compiler.

## 1 Introduction

Few type systems in practical use have resisted formalization as stubbornly as Scala's. Since its introduction, Scala combined ML-style module systems, object-oriented inheritance, and higher-order functions in a single language — and with that combination came *path-dependent types*: types such as `x.T` that name an abstract type member `T` through a term-level reference `x`. Such types are essential to idiomatic Scala. A map's key type may depend on the map instance; a module's abstract type is refined by each implementation; cake-pattern components exchange services whose interfaces are path-dependent types.

Yet for years, path-dependent types were, in the words of Amin, Rompf, and Odersky, "a roadblock in grounding the Scala type system on firm theory" [5]. The difficulty is not merely engineering; it is mathematical. In a calculus with abstract type members carrying lower and upper bounds, a single inconsistent declaration can collapse the entire subtyping lattice, letting the typechecker "prove" `Int <: String`. Unlike in ML modules, where signatures are checked for well-formedness once, Scala permits declarations whose bounds need not be consistent — and it was long unclear how soundness could survive them.

The Dependent Object Types (DOT) calculus was introduced to capture exactly this essence [4]. DOT distills Scala to a small core: objects with type members, fields, and methods; type selections on paths; intersection, union, and recursive object types; and a rich subtyping relation. Its research program unfolded in three acts:

1. **Formulation (2012–2014).** Early DOT and the first soundness result for the restricted µDOT fragment, which models records with type members and selections on variables only [1].
2. **Soundness breakthrough (2015–2016).** The definitional-interpreter proof technique showed that a *full* DOT — with type refinement, intersections, and a subtyping lattice — is sound, because narrowing and transitivity need only hold for *runtime* objects, not arbitrary static code [2][3].
3. **Extension and consolidation (2017–present).** Mechanized proofs in Coq [7], fully path-dependent pDOT [8], initialization-aware ιDOT [9], and DOT's adoption as the formal foundation of Scala 3 (Dotty), explained to practitioners by Odersky [10].

This essay examines each act, the technical ideas that made it possible, and what remains open.

## 2 Background

### 2.1 Path-dependent types and abstract type members

In DOT, an object type is a *recursive* record of declarations:

```scala
// DOT object type, rendered in Scala-like surface syntax
ν(x: { type A : S .. T;          // abstract type member with bounds
       val f : x.A -> Int;       // field whose type mentions x.A
       def m(y : x.A) : x.A })    // method with dependent type
```

The crucial form is the *type selection* `x.T`, which projects the type member `T` out of the object denoted by the path `x`. Selections are related to the declared bounds by two subtyping rules:

```
  Γ ⊢ x : {A : S..T}        Γ ⊢ x : {A : S..T}
 ───────────────────(<:-Sel) ───────────────────(Sel-<: )
  Γ ⊢ S <: x.A               Γ ⊢ x.A <: T
```

Selection thus makes every path-dependent type a *mediator* between its bounds: `S <: x.A <: T`. This mediation is the source of both the calculus's expressiveness and its peril.

> **Theorem: (Bound Mediation).** In any environment where `Γ ⊢ x : {A : S..T}`, the judgments `Γ ⊢ S <: x.A` and `Γ ⊢ x.A <: T` are both derivable, and therefore by transitivity `Γ ⊢ S <: T`.

### 2.2 The bad-bounds problem

If a declaration permits arbitrary bounds, nothing stops `type E >: ⊤ <: ⊥` — bounds that are "bad" in the sense that the lower bound is *not* a subtype of the upper bound. Combined with the rules above and subtyping transitivity, bad bounds collapse the lattice:

```scala
trait BadBounds {
  type E >: Int => Int <: Int => String
  val f: Int => Int = (x) => x
  val e: E = f
  val f2: Int => String = e   // typechecks only if Int=>Int <: Int=>String
}
```

Here `Int => Int <: E` (by `<:-Sel`) and `E <: Int => String` (by `Sel-<:`), so transitivity yields `Int => Int <: Int => String` — a function type judged a subtype of an incompatible one, although parameter contravariance forbids it. Once the lattice collapses, arbitrary judgments become derivable: `⊤ <: ⊥` follows from `type E >: ⊤ <: ⊥`, and from there *any* program typechecks [6].

This is not a contrived corner. The diamond-inheritance example due to Odersky makes the mechanism concrete in plain Scala [10]:

```scala
trait Base { type A }
trait Sub1 extends Base { type A = String }
trait Sub2 extends Base { type A = Int }
trait Bad extends Sub1 with Sub2   // conflicting aliases for A
```

Mixing `Sub1` and `Sub2` equates `String = A = Int`, hence `String = Int` by transitivity. The typechecker cannot always detect such conflicts locally — yet soundness must hold anyway.

### 2.3 Why classical proof techniques failed

The dominant soundness method, Wright and Felleisen's syntactic approach (progress + preservation over small-step rewriting), demands global metatheoretic properties: *environment narrowing* (subtyping is preserved when a variable's type is replaced by a subtype) and *subtyping transitivity* (if `S <: U` and `U <: T` then `S <: T`). Amin et al. showed that in DOT, each desirable feature breaks at least one of these properties [2]:

| Feature added to µDOT | Property broken |
|---|---|
| Type refinement (`{A : S..T} ∧ ...`) | Environment narrowing |
| Subtyping lattice (intersections, `⊥`) | Subtyping transitivity |
| Mixin composition | Narrowing |
| Union types | Transitivity (in full generality) |

With these properties gone, no syntactic proof could go through — and indeed soundness for full DOT remained open for years.

## 3 Methodology

### 3.1 Definitional interpreters instead of rewriting

Rompf and Amin's key methodological innovation [2] was to abandon term rewriting in favor of a *definitional interpreter*: an operational semantics written as a high-level, fuel-indexed evaluator inside Coq. Rather than stepping terms, the interpreter maps a term, an environment, and a fuel counter to a result:

```haskell
-- definitional interpreter, fuel-indexed (sketch, after Rompf & Amin [2])
eval :: Int -> Env -> Term -> Result
eval 0     _   _       = Timeout
eval (n+1) env (Var x) = Done (lookup env x)
eval (n+1) env (App t u) =
  case (eval n env t, eval n env u) of
    (Done (Closure x body rho), Done v) -> eval n ((x,v):rho) body
    (Timeout, _) -> Timeout
    _            -> Error
eval (n+1) env (New d) = Done (Object (evalDefs n env d))
```

The interpreter cleanly separates *evaluation* (a total function, with explicit `Timeout` and `Error` outcomes) from *typing* (a static relation). Soundness then becomes: if `∅ ⊢ t : T` and `eval n ∅ t = Done v`, then `v` is described by `T` in the logical relation. This "three easy lemmas" structure (after Siek) factors the proof into manageable pieces [1].

### 3.2 The central insight: runtime objects are well-behaved

The breakthrough observation is beautifully simple [2][10]:

> **Lemma: (Runtime Consistency).** During evaluation, every path `x` that a type selection `x.T` depends on denotes an object created by `new`. Every such object is constructed with *exact type aliases* for its type members — never with abstract, potentially inconsistent bounds.

In other words, the full static type system admits inconsistent environments (bad bounds, collapsed lattices), but the *runtime* environments — those arising from actual values — never contain bad bounds, because object creation requires concrete definitions. Narrowing and transitivity therefore need hold only for the *precise* types of runtime values, not for arbitrary static types. The proof introduces "invertible" or "precise" typing derivations for values and shows the bad properties hold there [3].

This distinction between *type-assignment time* and *runtime* is exactly what syntactic rewriting could not express: a rewriting proof reasons about all intermediate terms uniformly, while the interpreter-based proof reasons about the values that actually arise.

### 3.3 Step-indexed logical relations

To interpret types as predicates over values, the proof uses step-indexed logical relations — relations indexed by the remaining fuel, so that recursive object types (which mention themselves) receive a well-founded semantics. Type selections `x.A` are interpreted by looking up the object's *runtime* type member, which, by the Runtime Consistency Lemma, is always a concrete alias. The interpretation of `⊥` as the empty relation then guarantees that no value inhabits a collapsed lattice at runtime.

## 4 Deep Dive

### 4.1 The DOT type lattice: intersections, unions, and selections

DOT's types form a rich lattice. Object types `{D}` support *width* and *depth* subtyping; intersection types `S ∧ T` model mixin composition (Scala's `with`); union types `S ∨ T` model branching. The subtyping rules for members are structural and mixed-variance:

```
  Γ ⊢ S2 <: S1    Γ ⊢ T1 <: T2
 ───────────────────────────── (Typ-<:)
  Γ ⊢ {A : S1..T1} <: {A : S2..T2}

  Γ ⊢ S2 <: S1    Γ, x:S2 ⊢ T1 <: T2
 ──────────────────────────────────── (Fun-<:)
  Γ ⊢ ∀(x:S1)T1 <: ∀(x:S2)T2
```

Notably, method types are *dependent*: the result type may mention the parameter variable. Intersections distribute over these rules, and the lattice laws (`S ∧ T <: S`, `S <: S ∨ T`) hold. It is precisely this lattice structure — desirable for modeling Scala — that kills global transitivity, because transitivity through a bad-bounded selection can equate unrelated lattice points.

### 4.2 From µDOT to full DOT: a ladder of calculi

The research program proceeded bottom-up, mechanizing each rung [1][2]:

1. **D<sub><:</sub>** — types as values (`{A = T}`), selections on variables, bad bounds; the minimal laboratory for the collapse phenomenon [6].
2. **µDOT** — records with type members, methods, fields, self-reference via `ν(x: ...)`; sound but restricted: no refinement, no lattice [1].
3. **DOT (Rompf–Amin 2016)** — full calculus: type refinement, intersections, unions, `⊥`, dependent methods; proved sound via definitional interpreters with the runtime/narrowing distinction [2][3].
4. **WadlerFest DOT** — the cleaned-up presentation ("The Essence of Dependent Object Types") consolidating the design [4].

Each step isolated which feature broke which property, turning an apparent mess into a disciplined design space.

### 4.3 pDOT: fully path-dependent types and singleton tracking

A limitation of classical DOT is that selections are only on *variables* (`x.A`), not on general paths (`x.f.g.A`). This rules out modeling nested modules — "nesting small components inside larger ones is a necessary ingredient of a modular, scalable language" [8]. The pDOT calculus generalizes selections to arbitrary paths `p.A`, but naive path extension is *unsound*: paths may alias, and a selection through an aliased path can observe stale bounds. pDOT's solution adds *singleton types* to track path equality, with a Coq-mechanized safety proof adapting the interpreter technique [8].

### 4.4 DOT vs. System F<sub><:</sub> and Featherweight Java

It helps to situate DOT against its two closest relatives:

| Aspect | System F<sub><:</sub> | Featherweight Java (FJ) | DOT |
|---|---|---|---|
| Abstraction | Type variables `X` | Class names (nominal) | Type members `x.A` (path-dependent) |
| Subtyping source | Declared bounds `X <: T` | Class hierarchy | Structural + selections + bounds |
| Recursion | None (explicit `μ`) | Implicit via classes | `ν(x: ...)` self types |
| Soundness proof | Syntactic, standard | Syntactic, standard | Definitional interpreters (classical methods fail) |
| Modules | No | No | Yes — objects *are* modules |

System F<sub><:</sub> is in a precise sense a *special case*: Rompf and Amin show how DOT-like calculi "emerge from straightforward generalizations of the operational aspects of F<sub><:</sub>" — abstract type members generalize bounded type variables, and selections generalize variable references [2]. FJ, meanwhile, models nominal OO but cannot express structural refinement or path dependence at all. DOT's novelty is unifying the ML-module tradition (type members, selections, like in Harper–Stone or Rossberg's 1ML) with the OO tradition (subtyping, inheritance, methods) in one calculus — which is exactly what Scala needed.

### 4.5 DOT in the Scala 3 compiler

Scala 3 (Dotty) was designed with DOT as its theoretical core [10]. The compiler's internal representation — with `TypeBounds`, `TypeRef`/`TermRef` selections, `AndType`/`OrType` intersections and unions, and `RecType` recursion — mirrors DOT's syntax almost directly. The practical handling of bad bounds in Dotty's subtyping algorithm (which drops global transitivity and instead consults bounds locally during selection checks) is a direct engineering descendant of the theory: soundness is preserved because, as the proof shows, only runtime values must be consistent [6]. The result is a rare achievement — a widely used industrial language whose core type system carries a mechanized soundness argument.

## 5 Empirical Results and Proofs

The "empirical" content of this line of work is its *mechanization*: every major claim is checked by a proof assistant, and several claimed designs were found unsound by the attempt to mechanize them.

- **µDOT (OOPSLA 2014):** Coq proof of type safety for the restricted calculus, using Siek's three-lemmas structure with a total (timeout-explicit) big-step semantics [1].
- **Full DOT (OOPSLA 2016):** First soundness proof for DOT with refinement, intersections, and lattice subtyping, via definitional interpreters in Coq. The proof isolates "precise" value typings where narrowing and transitivity hold, and shows evaluation only ever produces precisely-typed values [2][3].
- **A simple modular proof (2017):** A restructured argument separating reasoning about types from reasoning about values and evaluation, again Coq-verified, designed to be easy to extend [7].
- **pDOT (2019):** Coq-mechanized safety for fully path-dependent types with singleton-tracked path equality [8].
- **πDOT (Scala 2018):** Path equality via explicit path environments, mechanized [11].
- **ιDOT (2020):** Extension with object initialization; the report documents that *without* the initialization discipline, null values make the calculus unsound (adapting Amin–Tate), and shows the initialized fragment sound [9].
- **Negative results:** The algorithmic-typing investigation conjectures that no minimal algorithmic typing exists for D<sub><:</sub> with bad bounds, and demonstrates exponential worst-case behavior in Dotty's bound-respecting subtyping — theory directly predicting compiler performance cliffs [6].

A striking pattern: mechanization repeatedly *discovered* unsoundness (naive pDOT, uninitialized ιDOT) that pen-and-paper reasoning missed — evidence for the program's methodological moral that these calculi are too subtle for unverified metatheory.

## 6 Limitations

DOT is a *core* calculus, and several gaps remain between it and Scala 3 as implemented:

1. **Decidability and algorithmic typing.** DOT's declarative system is not known to be decidable in full generality; Dotty implements an algorithmic approximation (dropping transitivity, consulting bounds lazily) that is sound in practice but incomplete by design [6]. The conjecture that no minimal algorithmic typing exists for D<sub><:</sub> suggests this incompleteness is inherent, not a compiler bug.
2. **Initialization and nulls.** DOT models a pure fragment; Scala's `null` and uninitialized fields reintroduce unsoundness unless disciplined by an initialization system (ιDOT) or Scala 3's explicit-nulls mode [9].
3. **Path length and equality.** Classical DOT restricts selections to variables; pDOT's general paths require singleton types and path-equality tracking whose interaction with the full lattice is still being worked out [8].
4. **Performance.** The exponential worst case in bound-respecting subtyping is not merely theoretical — it manifests as compile-time blowups on pathological (and occasionally real) programs [6].
5. **Effects and mutability.** DOT is a pure calculus of objects; Scala's vars, exceptions, and (in Scala 3) capture-checking reachability types lie outside its scope, awaiting integration.
6. **Contractiveness.** The 2016 DOT imposes syntactic contractiveness restrictions on object creation to keep the Coq mechanization tractable; lifting them is conjectured safe but unproven [3].

## 7 Conclusion

The DOT story is, at bottom, a story about *where* a type system is allowed to be inconsistent. Classical metatheory demanded global consistency — narrowing and transitivity everywhere — and Scala's features refused to comply. The definitional-interpreter proofs reframed the question: consistency is required only of the values a program actually constructs, and those values, built by `new` with concrete type aliases, are always consistent. Everything else — the collapsed lattices, the bad bounds, the uninhabited intersections — lives in dead code, in branches never taken, in objects never created.

That reframing did more than salvage a proof. It gave Scala 3 a principled core: the compiler's internal types are DOT types, its subtyping algorithm is DOT subtyping made algorithmic, and its soundness rests on a mechanized argument rather than folklore. Path-dependent types, once "a roadblock in grounding the Scala type system on firm theory" [5], are now among the best-understood constructs in the literature — with their generalizations (pDOT), their interactions (initialization, singleton tracking), and their limits (algorithmic incompleteness, exponential subtyping) mapped out in unusual detail.

The open frontier is no longer *whether* path-dependent types can be sound, but *how much* of a real language — effects, nulls, inference, performance — can be brought under the same disciplined umbrella. DOT's ladder of calculi suggests the method: isolate the feature, find the property it breaks, and ask what the runtime actually guarantees.
