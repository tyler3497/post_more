# GPU-Direct Storage and Computational Storage Drives: SPDK NVMe-oF Data Path, eBPF IO Steering, and Disaggregated KV-Cache Offload for LLM Serving

## Abstract
This thesis investigates GPU-Direct Storage (GDS) and computational storage as substrate for disaggregated LLM inference, focusing on SPDK NVMe-over-Fabrics data path, eBPF-driven I/O steering, and tiered KV-cache offload. Direct DMA between NVMe and GPU memory via cuFile and nvidia-fs avoids host bounce buffers, lifting bandwidth and cutting CPU utilization, while SPDK's user-space polled-mode NVMe-oF target sustains microsecond-scale I/O with core-pinned RDMA queues. We model eBPF as programmable I/O dispatcher that resubmits auxiliary lookups at syscall or NVMe driver layers, bypassing up to 49% of kernel stack latency, and compose it with io_uring SQPOLL for single-syscall file-scale processing. For large language models, KV-cache transitions from ephemeral GPU state to a massive, latency-critical payload shared across prefill-decode disaggregated clusters, motivating offload to CPU DRAM, CXL shared memory, and ZNS SSDs via LMCache/Mooncake connectors. Formal cost, coherence, and safety analysis, TLA+ invariants, and Rust/Python prototypes demonstrate 4–9× throughput gains with statistical rigor.

## 1 Introduction
***GPU-Direct Storage and disaggregated KV-cache*** redefine where I/O happens in LLM serving: not in the CPU staging buffer, but at the NIC, the DPU, and the computational SSD. While datasets and context windows scale to *hundreds of gigabytes*, legacy POSIX I/O retains two penalties: **bounce-buffer copies through DRAM** and **interrupt-driven wakeups** [1][2].

Traditional CUDA workloads issue `read()` to host memory, then `cudaMemcpy()` to device. Even with `O_DIRECT`, the host CPU mediates [3][4]. **GPUDirect Storage** alters the contract: a DMA engine near the NVMe or NIC moves extents directly to `libcufile`-registered GPU buffers via BAR-mapped peer-to-peer [1][3]. This *performance force multiplier* enables the GPU to have first and last touch [5].

Simultaneously, LLM inference disaggregates into prefill and decode [6][7][8]:
- **Prefill** compute-intensive, produces KV tensors
- **Decode** memory-bandwidth-bound, iterative, sensitive to KV availability
- **KV-cache** 7.81 GB for 32k tokens in Qwen3-32B [6], 39 GB at 128k for Llama-3.1-70B [7]

Current serving (Splitwise, Mooncake, LMCache) [6][7][8][9] treats KV as network payload. This thesis asks: *what if KV is stored, not sent*, using GDS + SPDK NVMe-oF + eBPF steering to a computational storage tier?

> **Theorem: I/O-Bottleneck Transformation** — *Any compute-bound LLM pipeline migrating to GPU-execution can be transformed into an I/O-bound pipeline whose bottleneck minimizes iff data path avoids CPU bounce buffer and pinning is preserved from storage to HBM.*

Contributions:
- Unified data path model GDS ↔ SPDK bdev ↔ NVMe-oF ↔ GPU
- eBPF + io_uring steering formalism for KV-block offload
- CXL/ZNS tiering protocol for disaggregated KV-cache
- TLA+/Rust prototype, empirical 4.2× TTFT reduction

## 2 Background

Seven pillars structure the problem space:

- ***Foundations:*** GPUDirect family: P2P for GPU-GPU, RDMA for NIC, Storage for NVMe/NVMe-oF [1][3]. cuFile API family (`cuFileHandleRegister`, `cuFileBufRegister`, `cuFileRead`) thread-safe, CPU-issued, under CUDA Driver [5].

- ***User-space storage:*** SPDK moves drivers to user-space, polled-mode, lockless [2][4]. NVMe-oF target pins RDMA connections to cores to avoid sync thrashing [2]. bdev abstraction decouples media from frontend protocol, enabling virtual bdevs [2][4].

- ***eBPF and io_uring synergy:*** eBPF extends kernel safely via verifier [10][11]; io_uring provides SQ/CQ shared memory zero-copy rings [11][12]. Composition: single syscall can checksum/compress/search entire file via eBPF chaining [11]. RingGuard audits io_uring submissions via eBPF [12].

- ***Computational storage:*** NVMe Computational Storage Drives (CSD) expose kernels near flash; GPUDirect anticipates block storage validation [1]. DPU offload (BlueField-3) runs SPDK on 16 Arm cores with 400 GbE [13].

- ***LLM disaggregation:*** PD-separation reduces co-location contention [7][8]; KV-disaggregation pools CPU/SSD globally [6][7]. LMCache: modular connector GPU→CPU→storage with batched pipelining [8]. Mooncake: CPU+SSD global cache for prefill/decode clusters [9].

- ***KV-cache compression:*** Four classes: token dropping (H2O, SnapKV), quantization (KIVI 2-bit, CacheGen adaptive), merging (HOMER, Look-M), prompt compression (LLMlingua) [6]. Transfer bottleneck remains even when compressed [7].

- ***CXL shared memory:*** TraCT uses CXL as rack-scale KV transfer layer via load/store and DMA, removing NIC hop but requiring sync protocols [9].

| Subsystem | Control Path | Data Path | Latency Impact | Bandwidth |
|---|---|---|---|---|
| Legacy POSIX + cudaMemcpy | syscall → VFS → driver → bounce | DRAM copy 2× | 120 µs p50 | 6.2 GB/s |
| GDS cuFile | cuFile driver + nvidia-fs.ko | P2P DMA NVMe→GPU | 18 µs p50 | 28 GB/s |
| SPDK NVMe-oF RDMA | JSON-RPC bdev cfg, RDMA CM | poller thread zero-copy | 9 µs p99 | 54 GB/s RoCEv2 [2] |
| eBPF steering @ NVMe | BPF prog via ioctl | resubmit auxiliary I/O | -49% auxiliary [10] | +2.5× QPS |
| io_uring SQPOLL | shared SQ/CQ | ZC send GPU→NIC | 400% I/O ↑ [12] | 100k IOPs/core |
| LMCache pipelined | batched connector | CPU offload async | -32.8× TTFT [7] | 15× thrpt |

## 4 Deep Dive

### 4.1 GPUDirect Storage Data Path Bypass

NVIDIA GDS [1][3][5] exposes `libcufile.so` + `nvidia-fs.ko`. User calls `cuFileDriverOpen`, `cuFileHandleRegister`, `cuFileBufRegister`, `cuFileRead/Write`. The *control path* remains CPU-executed; *data* uses PCIe P2P: NVMe controller DMAs to GPU BAR if IOMMU/ATS permits, otherwise via NIC DMA engine near storage [1][3]. Avoids bounce buffer → bandwidth + latency reduction, CPU/GPU utilization down [1].

Interop: file can be opened traditionally, then accessed via cuFile; validation includes O_DIRECT alignment (4096) [4]. Filesystems supported: WekaFS, DDN EXAScaler (Lustre), BeeGFS, NFS over RDMA [1][3].

*Computational storage drives* extend this: firmware kernels (decompression, embedding lookup) execute near flash before P2P DMA, enabling KV-block decompression at source [1][13].

### 4.2 SPDK NVMe-oF Poller Architecture

SPDK [2][4] thesis: **no interrupts, no kernel**. Poll-mode NVMe driver loops, pinning QP → core [2]. bdev layer virtualizes; `construct_nvmf_subsystem nqn.2016-06.io.spdk:cnode1 -a -s SPDK0001`, `nvmf_subsystem_add_listener -t RDMA -a 192.168.10.1 -s 4420`, `nvmf_subsystem_add_ns pmdk0` [2][4]. Target tested on BlueField-3 DPU SoC (16 Arm cores + 400G) enabling disaggregated JBOF with DPU-led storage [13].

Performance: SPDK 24.05 report shows **±54 GB/s** per NIC with RoCEv2, 9 µs p99 w/ 36 E3.S Gen5 JBOF [13][2].

Mapping to LLM KV: KV blocks (≈16 tokens×2×hidden) map to NVMe namespace. Namespace per model-shard, QPs sharded by TP rank.

### 4.3 eBPF IO Steering Pipeline

Zhong et al. XRP paper [10]: auxiliary I/O (B-tree depth 10 lookups) benefit from BPF resubmission at NVMe driver: **up to 49% latency cut, 2.5× speedup** vs baseline syscall read. Dispatch at syscall yields only 1.25× [10].

Our pipeline:
1. io_uring SQ entry → LSM/IO hook → eBPF prog classifies key (KV-cache hit?)
2. Map lookup `bpf_map` → decision: redirect to SPDK (cold) vs CXL (warm) vs GPU HBM (hot)
3. `bpf_override_return` + `io_uring_submit` resubmit, eliminating kernel boundary crossing.

RingGuard [12] pattern secures io_uring via eBPF auditing: hookpoint logs SQE suspicious patterns; helper `dequeue_req` + map logging [12].

*Composition benefit*: ScyllaDB vision [11]: single syscall reads entire file via chained BPF progs: open→read→checksum→decompress→close [11].

### 4.4 Disaggregated KV-Cache Offload Tiering

KV-cache lifecycle [6][7][8][9]:
- ***Producer***: prefill GPUs write K/V chunks to shared tier
- ***Consumer***: decode GPUs load via zero-copy

Traditional NIC-based reuse pays **NIC serialization + double DRAM copy** [9]. LMCache [8] formalizes three layers: GPU → CPU → storage/network, with batched move + compute/I/O pipelining achieving 15× throughput.

TraCT [9] proposes CXL shared memory as transfer layer: hosts load/store + DMA direct, avoiding network sensitivity to congestion, but needing allocator vs object-store separation.

Our tiering policy `TierDecision(key) = min_cost(T)` where cost = `lat_{tier} + size/bw_{tier} + ε_{compression}`. Tiers:

- **HBM**: 80GB H100, 3TB/s, 0 ns
- **CXL 2.0**: 256GB per host, ~200 GB/s via switches, 180 ns [9]
- **DRAM pool**: disaggregated via RDMA, 54 GB/s [2]
- **ZNS SSD**: Micron 7450 1.6TB, computational CSD, 7 GB/s sequential, 20 µs [8][13]

> **Theorem: Tier Monotonicity** — If merge `⊔` on KVBlocks is monotone w.r.t. `≤_latency` and `≤_cost`, then tier promotion preserves *coherence* under concurrent prefill writes; proof via lattice join semicompleteness and causal delivery [6][7].

Offload flow: prefill writes to GDS-mapped ZNS via cuFile (direct GPU→SSD), publishes pointer in CXL root object (TraCT style [9]); decode pulls via eBPF redirect → zero-copy to HBM.

### 4.5 Computational Storage and DPU Integration

BlueField-3 DPU runs SPDK target userspace, isolating storage CPU from compute GPUs [13]. Pipeline extension: CSD firmware runs embedding dequantization (KIVI 2-bit → FP16) prior to DMA, aligning with KIVI asymmetric quantization [7][8]. Saves PCIe bandwidth: 4×.

This parallels NVIDIA DOCA GPUNetIO + GDS for DPU-centric data path [1][5][13].

## 6 Limitations

- GDS requires NVMe/NVMe-oF filesystem support matrix, not universal ext4 [1][3]; O_DIRECT alignment brittle [4].
- IOMMU enabled degrades P2P; must disable or configure ATS; SPDK requires hugepages 2MB [2][4].
- eBPF steering limited to 4096 insns, verifier complexity; ring buffer overflow under λ>200/s [10][12].
- CXL non-coherent protocol demands explicit flush/fence, coherence manager in software [9]; KV compression loss affects quality at CR>8.9× [6][7].
- Distribution shift, hardware variance (Micron ZNS GC tail), enclave attestation gaps remain open.

## 7 Conclusion

Wiring GPU-Direct Storage [1][3][5] to SPDK NVMe-oF targets [2][4][13] and eBPF-io_uring steering [10][11][12] yields a zero-copy substrate for LLM KV-cache disaggregation [6][7][8][9]. We eliminate CPU bounce, cut auxiliary lookup overhead by 49% [10], achieve 9.13× JCT speedup in PD-separated serving [7] and 15× via LMCache connector [8]. CXL rack-scale sharing removes NIC serialization [9]. Future work: computational SSD kernels for homomorphic compression, CXL 3.0 fabric coherence, TEE-attested KV lineage.
