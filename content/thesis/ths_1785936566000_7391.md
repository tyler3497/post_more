# Verified Superoptimization via Equality Saturation: Synthesizing Optimal LLVM Peephole Rewrites with E-Graphs, Souper Enumeration, and Alive2 SMT Oracles

## Abstract
We present a unified framework for verified superoptimization that combines equality saturation over e-graphs with SMT-based translation validation. Superoptimizers such as Souper enumerate LLVM IR candidates and discharge equivalence via solvers, while verifiers like Alive and Alive2 establish refinement under LLVM's undefined behavior, poison, and memory model. We show how equality saturation, as realized in egg and egglog, provides a non-destructive substrate for organizing this search, avoiding phase-ordering and enabling optimal extraction under composable cost models. The integration yields a certified peephole synthesis loop where each learned rewrite is both optimal w.r.t. size or latency and provably sound via an Alive2 oracle. We evaluate design tradeoffs, solver encodings with Z3, and scalability limits on real LLVM InstCombine patterns.

> **Contribution Claim:** *A superoptimizer without a verifier is a bug generator; a verifier without a saturating search is a peephole checker. Equality saturation provides the mediation: a compact congruence closure over exponentially many programs, interrogable by SMT.*

## 1. Introduction

Modern optimizing compilers are structured as **pass pipelines** applying *local, heuristic, and largely syntactic* rewrites. This architecture suffers from the **phase-ordering problem**: the profitability of one transformation depends on prior transformations, yet the compiler must commit to an order *a priori* [2][3]. Peephole optimizations, which replace a small window of intermediate representation (IR) with a cheaper equivalent sequence, are emblematic: LLVM's `InstCombine` contains >20k lines of hand-written C++ pattern matching, historically the single buggiest file in LLVM under Csmith fuzzing [4].

*Superoptimization* [1] promises to sidestep manual enumeration by searching the space of programs for semantics-preserving, cost-improving replacements. Massalin's original approach exhaustively enumerated instruction sequences and validated equivalence via probabilistic testing. Contemporary llvm-level approaches — notably **Souper** [1] — recast synthesis as *SMT-guided enumeration*: extract a pure SSA data-flow fragment from LLVM IR, infer its input-output specification, enumerate smaller or cheaper RHS candidates up to a bound, and dispatch equivalence to an SMT solver.

Yet soundness remains fragile. LLVM IR is not a simple bit-vector language; its semantics include `undef`, `poison`, `unreachable`, *non-deterministic* allocation, and a highly subtle memory model where `!dereferenceable` and aliasing attributes constrain transformations validly missed by naive equivalence [3][5]. **Alive** [4] and **Alive2** [3] address this by formalizing LLVM IR transformation validity as *refinement* rather than equivalence: the target must have *no more* observable behavior than the source, must not introduce new undefined behavior, and must respect `poison` propagation.

In this thesis we argue that **e-graphs** as implemented in `egg` [2] provides the right intermediate structure to unite these two lines. Rather than committing to a single best RHS per LHS, we saturate a *space* of equivalent IR fragments under algebraic axioms, Souper-synthesized rules, and Alive2-verified rewrites, then extract a globally optimal term under a learned cost model.

***Thesis structure.*** We review LLVM IR refinement (section 2), e-graphs and equality saturation (section 3), Souper enumeration (section 4), Alive2 SMT encoding (section 5), propose an integrated verified saturation loop (section 6), evaluate tradeoffs (section 7), and contrast with related work (section 8).

## 2. Preliminaries: LLVM IR and Peephole Refinement

LLVM IR is a typed, SSA, three-address IR with infinite virtual registers. Its complexity stems from underdefined values:

- **`undef`:** an *unconstrained* bit pattern, chosen arbitrarily per use. `undef` enables dead-code-driven folding but breaks equational reasoning: `x xor undef` is not `undef`, it is *any* `i32` [4].
- **`poison`:** deferred undefined behavior arising from e.g., `nsw` overflow, `inbounds` GEP violation, or `exact` division failure. Poison propagates strictly: any instruction with a poison operand yields poison, except `freeze` [3].
- **`nuw/nsw/exact` attributes:** create *conditional poison* that verification must model precisely.
- **Memory:** LLVM's memory model is block-based with typed pointers, `alloca`, `getelementptr`, and explicit lifetime. Translation validation that ignores memory unsoundly validates load-store forwarding [5].

> Formally, Alive2 defines: `src` refines to `tgt` iff for all states, if `src` is well-defined (no UB) then `tgt` is well-defined, and if both defined, their observable values are equal, where poison refines to any value via `freeze` semantics. Equivalence is insufficient; refinement is required.

This is captured via SMT: LLVM values are encoded as pair `(value, poison, undef, UB)` where UB is a boolean flag. A rewrite `src => tgt` is sound iff:

```
forall inputs. not UB_src and (src_poison -> tgt_poison?) actually: refinement condition
   src_UB -> not tgt_UB_must_not_introduce
```

More precisely, Lopes et al. [4] encode counterexamples as:

```
exists inputs. IsCounterexample =  ( not src_ub and tgt_ub ) or
                                   ( not src_ub and not tgt_ub and not poison_implies and src_val != tgt_val )
```

If UNSAT, the rewrite is valid.

### 2.1 Peephole Optimizers

InstCombine performs *syntactic* rewrites like:

```llvm
%1 = shl i32 %x, 29
%2 = lshr i32 %1, 29
=> 
%2 = and i32 %x, 7
```

The optimization is valid for 32-bit ints, removes a use, reduces cost. Alive expressed it as:

```
Pre: true
%1 = shl i32 %x, 29
%2 = lshr %1, 29
=>
%2 = and %x, 7
```

Alive automatically proved correctness via Z3. Alive2 extended this to loops (bounded unrolling) and memory.

## 3. Equality Saturation and E-Graphs

### 3.1 E-Graphs as Compact Congruence Closure

An **e-graph** [2] compactly represents an equivalence relation over ground terms.

> **Definition 3.1 (E-Graph).** An e-graph `G = (N, C, M)` consists of e-nodes `N`, e-classes `C`, and membership `M: N -> C`. Each e-node is `f(c1,...,ck)` where `f` is a function symbol and `ci` in `C`. The congruence invariant asserts: if `f(c1...)` in `c` and `f(c1...)` in `c'` then `c = c'` (hash-consing), and if `ci = cj` under equivalence, then uses are congruent.

Unlike destructive rewriting, equality saturation never discards information: rules *add* equalities.

- **E-class analysis:** `egg` generalizes e-graphs with domain-specific data attached to e-classes, e.g., constant folding, range analysis, free-variable set, cost. This enables conditional rewrites like `x + 0 -> x` when `x` is analyzed as non-poison.
- **Rebuilding:** The key algorithmic contribution of `egg` is *deferred rebuilding*. After merges, invariants (congruence, analysis) are restored amortized, yielding asymptotic speedups of 10-100x over naive saturation [2].

**Theorem 3.2 (Monotonicity of Saturation).** *Let E0 be initial e-graph and R a set of sound rewrites. Let Ei+1 = Ei union (rhs | lhs in Ei, lhs -> rhs in R ). Then: (i) Ei subset Ei+1 (monotonic), (ii) If t1,t2 are merged in Ei they remain in all Ej, j>=i, (iii) If saturation reaches fixpoint E*, then E* contains all terms reachable by R* from E0 modulo congruence.*

*Proof Sketch:* By construction e-graph insertion is monotonic and merge never splits classes. Congruence closure is monotone.

This property is critical for superoptimization: we can safely compose thousands of candidate rewrites without losing alternatives.

### 3.2 Extraction

Given a saturated e-graph, extraction selects a minimal representative per e-class under cost function `cost: N -> Nat`. For DAG cost (common subexpression sharing), extraction is NP-hard; egg uses heuristic with integer linear programming via `egg_lp` or greedy bottom-up.

In compiler terms this corresponds to solving phase-ordering globally.

| Workload | E-graph Size | Rebuilding Speedup | Domain |
|----------|--------------|--------------------|--------|
| `egg` math simpl | 10k e-nodes, 2k e-classes | 5.1x vs naive | Floating-point |
| Tensor | 50k e-nodes | 12x | MLIR/rewriting |

## 4. Souper: Synthesizing Superoptimizer for LLVM

Souper [1] is a *synthesizing* superoptimizer, in contrast to enumerative assembly searchers like STOKE [6]. Its workflow:

1. **Harvesting:** Profile/instrument LLVM to extract SSA DAGs (data-flow slices without memory or control) from `InstCombine`-style code. Slices are converted to Souper IR: bitvector operations with width, `undef`, `poison` flags.
2. **Inference:** Given input registers `%0..%n`, Souper infers their concrete types/widths and builds a specification `exists RHS. forall inputs. LHS == RHS`.
3. **Enumeration:** Enumeratively generate RHS candidates in increasing cost: constants, inputs, unary ops, binary ops, etc., pruned by type. Typically up to 3-4 instructions.
4. **SMT Verification:** For each RHS, query Z3/CVC4: is there an input distinguishing LHS,RHS? Encoding uses QF_BV. If UNSAT and RHS cheaper under cost model (e.g., `llvm-mca` latency or LLVM `TargetTransformInfo`), cache as winning replacement.
5. **Generalization:** Replace concrete constants with symbolic `C` via `const` inference.

Souper discovered optimizations that ship in LLVM and MSVC, e.g., `(x ^ y) ^ y -> x`, `((x << C1) >> C2) variant -> and/select` [1]. When run as a pass over Clang's own IR, Souper reduces binary size by about 3 MB (4.4%) [1].

```python
# Souper-like candidate verification (Python/Z3 sketch)
import z3
def check_refinement(lhs_fn, rhs_fn, width=32):
    x = z3.BitVec('x', width)
    y = z3.BitVec('y', width)
    lhs_val, lhs_poison, lhs_ub = lhs_fn(x,y)
    rhs_val, rhs_poison, rhs_ub = rhs_fn(x,y)
    s = z3.Solver()
    # refinement violation
    s.add(z3.Not(lhs_ub))        # src defined
    s.add(rhs_ub)                # tgt UB introduced
    if s.check() == z3.sat:
        return False, "UB introduction"
    s.reset()
    s.add(z3.Not(lhs_ub))
    s.add(z3.Not(rhs_ub))
    s.add(z3.Not(lhs_poison)) # src not poison nuance
    # value inequality
    s.add(lhs_val != rhs_val)
    return s.check() == z3.unsat
```

> **Limitation Note:** Souper's IR deliberately *abstracts memory* and assumes total, side-effect-free DAGs. This is why Alive2 verification is essential post-hoc: Souper alone would unsoundly hoist `undef`-creating ops.

Souper also addresses engineering: **caching**. Synthesis results are keyed by LHS hash and stored in Redis-like store, so expensive SMT queries amortize across builds.

## 5. Alive2: Bounded Translation Validation with a Precise SMT Oracle

Alive2 [3] is the contemporary reference for automatic LLVM IR refinement checking. It extends Alive [4] from peephole-only to bounded intraprocedural verification including loops (unrolled k-times) and memory.

### 5.1 Memory Encoding

The key contribution of Lee et al. [5] is a first SMT encoding of LLVM's memory model precise enough to validate all intraprocedural memory optimizations. Encoding challenges include:

- Block identifiers: each `alloca` and `malloc` yields fresh block id.
- Pointer as `(bid, offset)`, with bounds checks for `inbounds`.
- `undef` pointer = non-deterministic `bid,offset` per use.
- Alias analysis modeling: `may-alias` approximated via `block` overlap constraints; Souper ignores this, Alive2 models it [5].

This encoding allowed Alive2 to uncover **21 previously unknown bugs in LLVM memory optimizations** (GVN, DSE, etc.), 10 fixed immediately [5]. By running over LLVM's unit test suite, Alive2 overall reported **47 new bugs, 28 fixed**, and led to **8 patches to LLVM LangRef** clarifying semantics [3].

### 5.2 SMT Formulation

Alive2 encodes each LLVM instruction as pure functions over `(val, poison, defined)`. Example `add nsw`:

```haskell
-- Haskell-like encoding of nsw add semantics
add_nsw :: (BV, Bool) -> (BV, Bool) -> (BV, Bool, Bool)
add_nsw (a, pa) (b, pb) =
  let res = a + b
      poison = pa || pb || overflow_s res a b
      ub     = False -- add itself never UB, but poison flag set
  in (res, poison, ub)
```

Verification query:

```
exists inputs, mem. not src_ub and (tgt_ub or (not tgt_poison and src_poison? no) or src_val != tgt_val)
```

If SAT, solver provides model = counterexample.

Souper uses *equivalence*; Alive2 uses *refinement* which is strictly more expressive. Soundness: if Alive2 says UNSAT, then `src` refines `tgt` holds up to bound (loops unrolled k). This is **bounded translation validation**: incomplete (misses bugs requiring >k iterations) but *sound* in that no false alarms [3][footnote].

Performance: Alive2 uses Z3 [6] with `qf_bv` + arrays + quantified block IDs. Approximations (e.g., limited block count, `forall` -> concrete) improve scalability to 100kLOC programs [5].

### 5.3 Refinement Table

| Case | src | tgt | Valid? |
|------|-----|-----|--------|
| `undef` refinement | `undef` | `0` | Yes |
| Opposite | `0` | `undef` | No |
| Poison conv | `poison` | `0` via `freeze` | Only if `freeze` |
| UB intro | `%x / 0` UB | `0` | If tgt introduces UB when src not UB -> invalid |
| `nsw` elimination | `add nsw a,b` | `add a,b` | Yes: removes poison |

## 6. Integrated Architecture: Verified E-Graph Superoptimization

We now define the *verified saturation loop* combining these.

### 6.1 Pipeline

```
LLVM IR Function
    | extract pure DAGs (Souper frontend)
E-Graph Initialize (egg)
    | saturate with:
      - algebraic axioms (commutativity, De Morgan, bitwise identities)
      - Souper-enumerated candidates (cost-ordered)
      - Alive-peephole database (InstCombine patterns proved via Alive2)
    | at each merge, query Alive2 oracle for *new* equalities:
         if unsat -> merge e-classes
         if sat   -> discard rewrite + emit counterexample to pruner
Extraction (minimize LLVM cost: instruction count, critical latency)
    |
Alive2 final bounded validation of extracted function vs original
    |
LLVM backend lowering
```

Key insight: *e-graph serves as a cache of Alive2-proved equivalences*. Souper's Redis cache is syntactic; e-graph cache is semantic modulo congruence.

> ***Theorem 6.1 (Soundness of Saturated Extraction).*** *If all rewrites added to e-graph are verified by Alive2 refinement oracle (refinement UNSAT), and extraction returns term `t` from e-class of source `s`, then `s` refines to `t`. Therefore extracted program refines original.*

*Proof:* By monotonic merging preserves inclusion. Each merge preserves refinement (oracle). Refinement is transitive. Extraction picks reachable element.

### 6.2 Cost Models and Extraction

We use composite cost:

```
cost(instr) = w1*Latency_TTI + w2*Size + w3*RegisterPressure
cost(e-node) = instr_cost + sum child_costs
```

`egg` extraction via `lp` can optimize for size; we extend via e-class analysis storing `post-verified` flag, so extraction prefers verified lowers-cost options.

```rust
// Rust egg snippet: defining LLVM BV language with poison analysis
use egg::{define_language, Analysis, EGraph, Id};

define_language! {
    enum LlvmLang {
        "bvadd" = Add([Id; 2]),
        "bvand" = And([Id; 2]),
        "bvxor" = Xor([Id; 2]),
        "freeze" = Freeze(Id),
        "const" = Const(i64),
        Symbol(egg::Symbol),
    }
}

#[derive(Clone)]
struct PoisonAnalysis;
impl Analysis<LlvmLang> for PoisonAnalysis {
    type Data = Option<bool>; // Some(poison_free)
    fn merge(&self, a:&Self::Data, b:&Self::Data)->Self::Data { a.or(*b) }
    fn make(egraph:&EGraph<LlvmLang,_>, enode:&LlvmLang)->Self::Data {
        match enode {
            LlvmLang::Const(_) => Some(false),
            _ => None,
        }
    }
}
```

### 6.3 Poison and Freeze Handling

Critical subtlety: `poison` *does not distribute* over some rewrites. Example: `add nsw x,1` poison on overflow cannot be replaced by `add x,1` unless `freeze` inserted. Our pipeline forces Souper to synthesize with poison tags preserved; Alive2 oracle rejects merges where poison lost.

This mirrors PrediPrune [7] observation: ML pruner reduces verification overhead by 51%, but must preserve safety.

Additional language example for completeness:

```tla
---- MODULE Alive2Refinement ----
EXTENDS Naturals, TLC
VARIABLES src_ub, tgt_ub, src_val, tgt_val, src_poison
RefinementOK == 
    /\ src_ub = FALSE => tgt_ub = FALSE
    /\ (src_ub = FALSE /\ tgt_ub = FALSE /\ src_poison = FALSE) => src_val = tgt_val
====
```

## 7. Evaluation Considerations and Limitations

**Scalability.** Souper enumeration explodes: RHS candidates up to size 3 over 4 opcodes approx 1e5 queries, each Z3 call 10-100ms. Equality saturation *amplifies* this unless e-matching filters candidates. Strategy: use `egg` *e-matching* to generate only candidates that fit e-classes with matching types; use *PrediPrune*-style ML classifier to skip unlikely candidates (original Souper baseline -> 51% faster with pruning [7]).

**Memory.** Current e-graph approaches to LLVM IR translation via `eqsat` MLIR dialect [8] represent e-graphs *natively* in MLIR, avoiding translation overhead between egg and MLIR. Yet memory remains bottleneck: 100k e-nodes requires incremental GC.

**Soundness gaps.** Alive2 is bounded for loops; unbounded loops require loop-invariant synthesis or bi-abduction. Also, Souper's harvesting excludes `call`, `volatile`, and concurrency. Full-function verification remains open.

| Superoptimizer | IR | Verification | Search Strategy | Memory Model |
|----------------|----|--------------|-----------------|--------------|
| Massalin87 | x86 asm | exhaustive bool | enum assembly | none |
| STOKE13 [6] | x86_64 | test + SMT | stochastic MCMC | none |
| Denali02 | alpha | SAT | equality sat early | none |
| Souper17 [1] | LLVM IR BV | SMT Z3 | enum DST | abstracted |
| Souper+Alive2 (this) | LLVM IR+BV+Mem | Alive2 refinement | equality saturation | full [5] |

*Table 3: Evolution towards verified saturation.*

## 8. Related Work

**Alive family:** Lopes et al. [4] introduced Alive DSL and proved approx 400 InstCombine patterns, finding mismatches between LangRef and implementation. Alive2 [3] generalized to bounded translation validation, receiving distinguished paper award at PLDI21. Memory encoding [5] is fundamental to our oracle.

**E-graph libraries:** The classic `eqsat` technique from Tate et al. and `egg` [2] revitalized interest. Recent work on **semantic foundations of EqSat** [9] formalizes saturation as chase over tree automata, linking to conjunctive query evaluation complexity. Contextual EqSat [10] shows how to reason about equivalences that hold only under path conditions — essential for `guarded` LLVM transforms like `i+1>n` under `i<=n`.

**MLIR integration:** `eqsat` dialect [8] demonstrates maintaining e-graph state through compilation flow in MLIR, enabling constructive passes. This suggests future where LLVM `PassManager` itself is e-graph aware.

**Translation frameworks:** `mlir-tv` [3 extended], Halide validation [4] rely on similar Z3 refinement. Common theme: over-approximate FP, bound tensors, hash-based reduction encoding [11].

## 9. Conclusion

We have shown how the three strands — *enumerative superoptimization* (Souper), *e-graph non-destructive rewriting* (egg), and *bounded refinement verification* (Alive2) — compose into a verified superoptimization stack that addresses phase-ordering, search explosion, and soundness simultaneously. Key takeaways:

- **Do not destroy:** E-graphs retain exponentially many programs succinctly; rebuilding enables asymptotics that make saturation feasible.
- **Synthesize, then verify:** Souper's synthesis strategy pruned by cost remains powerful, but its outputs must pass Alive2's refinement, especially for `poison`, `undef`, and memory.
- **Oracle as merge condition:** Treating SMT validity as condition for e-class merge converts verification from post-pass filter to saturation driver.
- **Refinement not equivalence:** LLVM semantics demand refinement not equality. Masking this distinction yields miscompilations detectable only after deployment.

Future work includes unbounded loop validation via invariants, contextual e-graphs tracking path-sensitive facts, and incorporation of `freeze` placement synthesis as cost-aware choice during extraction.
