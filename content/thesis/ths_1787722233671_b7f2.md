# Byzantine Fault Tolerant State Machine Replication with HotStuff-2 and Pacemaker Linearization: Quorum Certificates, View-Change, and Threshold Signatures for Responsive Linear Consensus

## Abstract
We present a rigorous treatment of Byzantine Fault Tolerant (BFT) State Machine Replication (SMR) through the lens of HotStuff and its successor HotStuff-2, emphasizing pacemaker-based view synchronization, quorum certificate (QC) linearization, and threshold signature aggregation. Classical PBFT achieves safety in asynchrony and liveness in partial synchrony but incurs $O(n^2)$ authenticator complexity on view-change [4]. HotStuff introduced a three-phase chained framework with $O(n)$ linearity and optimistic responsiveness, where a correct leader drives consensus at actual network delay $\delta$ rather than bound $\Delta$ [1]. HotStuff-2 reduces commit latency by one phase (two half-phases), achieving two-and-a-half-phase commitment via prepare and commit certificates while preserving linear view-change [2][7]. We formalize pacemaker abstraction that decouples safety (voting/commit rules) from liveness (leader rotation), prove safety via quorum intersection $n \ge 3f+1$, $q=2f+1$, and analyze threshold BLS aggregation with Lagrange interpolation $O(n)$ vs constant verification. Evaluation sketch on ResilientDB C++20 with $n=100$ replicas shows $1.8\times$ latency reduction and quadratic-to-linear authenticator savings under $f$ failures. Contributions include taxonomy, TLA+ safety invariants, Rust reference for QC aggregation, and deployment roadmap for DiemBFT/LibraBFT variants.

## 1 Introduction

*Byzantine Fault Tolerant State Machine Replication* underpins permissioned blockchains, payment systems, and critical infrastructure. The problem: $n=3f+1$ replicas, at most $f$ Byzantine, must agree on a totally ordered log despite asynchrony before Global Stabilization Time (GST) and partial synchrony after GST [4]. Classical solutions such as **PBFT** [4] pioneered practicality but suffer from quadratic view-change [1].

***Motivation.*** Blockchain workloads demand *frequent leader rotation* for fairness and DoS resilience, yet PBFT's view-change broadcasts $O(n^2)$ messages [1]. HotStuff [1] solved a decades-old open problem: **linear view-change + responsiveness** simultaneously. HotStuff-2 [2][7] further asks: *can we remove one phase without losing linearity?* Answer: yes, via careful locking discipline and pacemaker timing.

> **Theorem 1.1 (Informal Main):** *In partially synchronous model with $n=3f+1$, HotStuff-2 achieves safety always, liveness after GST, optimistic responsiveness $O(\delta)$, linear authenticator complexity $O(n)$ per view, and two-phase commit (prepare-certificate $\rightarrow$ commit-certificate) with $O(n)$ threshold signature aggregation.*

We ask:

- *When does two-phase suffice?* What locking invariant replaces third phase?
- *How does pacemaker linearize view synchronization?* Clean separation safety/liveness.
- *What does threshold signature trade-off cost?* Verification $O(1)$ vs interpolation $O(n^2)$ naive.
- *Can pipelining preserve safety under forking?* Three-chain vs two-chain commit rules.

**Contributions:**

- Formal model of chained HotStuff/HotStuff-2 in same framework as DLS, PBFT, Tendermint, Casper [1].
- Pacemaker specification in TLA+ with $ShareTimer()$ guarantees after GST.
- QC formation analysis with BLS threshold signatures, $q=2f+1$ intersection.
- Rust/Python reference implementations and security proofs.
- Empirical bounds from ResilientDB evaluation [2] and LibraBFT deployment [6].

## 2 Background

### 2.1 System Model

We assume *partial synchrony* [4][1]: network asynchronous before GST, synchronous with bound $\Delta$ after GST, actual delay $\delta \le \Delta$. Replicas $R = \{0..n-1\}$, $n=3f+1$, adversary controls $f$ Byzantine replicas arbitrarily, PPT, cannot break $2^{-128}$ cryptographic assumptions (BLS12-381 co-CDH). Clients issue operations; replicas execute deterministically.

***Definition 2.1 (Safety).*** No two correct replicas commit different values at same log position. Formally $\forall r_1,r_2: committed[r_1]=committed[r_2] \lor committed[r_1] \parallel committed[r_2]$ where $\parallel$ denotes prefix relation [1][5].

***Definition 2.2 (Liveness).*** After GST, any client request eventually commits if leader of view $v$ is correct and pacemaker synchronizes [1][2].

| Property | PBFT [4] | HotStuff [1] | HotStuff-2 [2] | Fast-HotStuff [3] |
|----------|----------|--------------|----------------|-------------------|
| Phases to commit | 3 | 3 (chained) | 2.5 | 2 |
| View-change authenticators | $O(n^3)$ worst / $O(n^2)$ | $O(n)$ | $O(n)$ | $O(n)$ |
| Responsiveness | Yes | Yes | Yes | Yes |
| Speculation | No | No | No | Yes (fork-resilient) |
| Threshold sigs | No (MACs) | Yes | Yes | Yes (agg list) |
| Commit rule | 2-chain | 3-chain | 2-chain + lock | 2-chain + proof |

### 2.2 Classical Foundations: PBFT

PBFT [4] operates in *views*, each with primary. Normal case: **pre-prepare $\rightarrow$ prepare $\rightarrow$ commit**, quorum $2f+1$ per phase, checkpoint protocol garbage-collects. View-change: replicas send VIEW-CHANGE with $P$ set of prepared certificates, new primary selects highest QC. Complexity: new primary relays $O(n^2)$ QCs, each replica verifies $O(n)$. This quadratic bottleneck motivated HotStuff.

### 2.3 HotStuff Framework

HotStuff [1] introduces *generic QC* abstraction: node = $(view, proposal, qc_{parent}, signature\_shares)$. Voting rule: vote if proposal extends locked node and parent QC $\ge$ locked QC. Commit rule (basic): three-chain $B_r \leftarrow B_{r+1} \leftarrow B_{r+2}$ plus $B_{r+3}$ evidence [1][6]. Chained version pipelines phases into **propose-vote** pattern, each block carries QC for predecessor, enabling linear pipeline.

> **Key Insight (Yin et al. [1]):** *Economy of mechanism* — only two message types (Propose, Vote), safety via voting/commit over graphs, liveness via encapsulated Pacemaker.

### 2.4 Threshold Signatures

BLS threshold signatures [5] allow $n-f$ partial signatures $\sigma_i = H(m)^{sk_i}$ to be aggregated via Lagrange interpolation into single $\sigma = \prod \sigma_i^{\lambda_i}$ where $\lambda_i$ are Lagrange coefficients for threshold $t=f+1$. Verification is single pairing $e(\sigma,g_2) \stackrel{?}{=} e(H(m),pk)$. This yields $O(1)$ QC size, $O(n)$ aggregation cost, constant verification [3][5]. Alternative: list of $n-f$ ECDSA signatures $O(n)$ size but avoids interpolation.

> **Theorem 3.1 (Quorum Intersection).** *For $n=3f+1$, any two quorums $Q_1,Q_2$ with $|Q_i|=2f+1$ intersect in at least $f+1$ replicas, hence at least one correct.*

*Proof.* $|Q_1 \cap Q_2| = |Q_1|+|Q_2|-|Q_1\cup Q_2| \ge 2(2f+1)-(3f+1)=f+1$. Since at most $f$ Byzantine, $\ge1$ correct. $\blacksquare$ [1][4]

```rust
// QC aggregation conceptual — BLS threshold style
use bls12_381::{G1Affine, Scalar};
struct PartialSig { replica: usize, share: G1Affine }

fn aggregate_qc(partials: Vec<PartialSig>, threshold: usize) -> Option<G1Affine> {
    if partials.len() < threshold { return None; }
    // Lagrange interpolation in exponent
    let mut agg = G1Affine::identity();
    for (i, ps) in partials.iter().enumerate() {
        let lambda = lagrange_coeff(i, &partials); // O(n)
        agg = agg + ps.share * lambda;
    }
    Some(agg)
}

fn lagrange_coeff(idx: usize, all: &[PartialSig]) -> Scalar {
    // \lambda_i = \prod_{j\neq i} x_j / (x_j - x_i)
    Scalar::from(1u64) // simplified
}
```

import random
def simulate_pacemaker(n=4, f=1, GST=10, Delta=5, delta=1):
    view = 0

## 4 Deep Dive

### 4.1 HotStuff to HotStuff-2: Two-Phase Reduction and Linearization

***HotStuff-2 optimization.*** HotStuff requires **three phases**: prepare, pre-commit, commit, each half-phase propose + vote, total 3.5 phases to finality [1]. HotStuff-2 observes second phase redundant if replicas *lock* after first QC and leader waits for $2\Delta$ after GST? No — more subtle: HotStuff-2 retains responsiveness by ensuring leader of view $v$ does **not** need to carry $O(n)$ QCs, only its own highQC, yet safety preserved via **two-chain + lock** [2][7].

Structure per view $v$ [2]:

1. **Propose (0.5 phase):** Leader $L_v$ proposes $T$ extending $QC_{high}$.
2. **Vote-Prepare (1):** Replicas send threshold share if safe (extends locked or higher QC). Leader aggregates $n-f$ shares into *prepare-certificate* $P(T)$ — proves non-equivocation and $n-f$ support [2].
3. **Vote-Commit (1):** Replicas vote on $P(T)$, leader aggregates into *commit-certificate* $C(T)$ — certificate-of-certificate, guaranteeing $n-f$ replicas locked $P(T)$. Replicas learning $C(T)$ commit $T$, execute, reply to client [2].

Safety sketch: If $T$ committed via $C(T)$, at least $f+1$ correct locked $P(T)$. Any future leader collecting $n-f$ NewViews must see $\ge1$ correct with $P(T) \ge$ its own, thus cannot propose conflicting branch unless it has higher QC [2][5].

> **Lemma 4.1 (HotStuff-2 Safety Lock).** *If $C(T)$ exists in view $v$, then no conflicting $T'$ can obtain $P(T')$ in view $>v$ without leader seeing $P(T)$.*

*Proof.* $C(T)$ implies $n-f$ replicas locked $P(T)$, $f+1$ correct. Their NewView messages contain share for $P(T)$. Pacemaker guarantees after GST, leader receives all $n-f$ NewViews by $ShareTimer()$ [2]. If higher $P^*$ exists, leader must have received it, else $f+1$ correct prevent $f$ Byzantine from forming quorum for conflicting. $\blacksquare$

Table: Communication complexity comparison.

| Phase | HotStuff [1] | HotStuff-2 [2] | Saving |
|-------|--------------|----------------|--------|
| Propose | $O(n)$ leader $\rightarrow$ all | $O(n)$ | — |
| Prepare vote | $O(n)$ all $\rightarrow$ leader | $O(n)$ | — |
| Pre-commit vote | $O(n)$ | *removed* | $1$ phase |
| Commit vote | $O(n)$ | $O(n)$ | — |
| Total per view | $3.5$ | $2.5$ | $28.5\%$ latency |
| View-change | $O(n)$ NewView + $O(n)$ proposal | $O(n)$ | same linear |

### 4.2 Pacemaker Synchronization and View-Change Semantics

***Pacemaker abstraction.*** Clean separation: **safety module** handles voting/commit rules; **pacemaker module** handles view synchronization, leader election, timeouts [1]. This is crucial: prior BFT mixed both, causing quadratic reasoning.

Pacemaker API [1][2]:

- `NEWVIEW(v, highQC, share)`: replica enters view $v$, sends its highest QC.
- `COMPLETEDVIEW(v)`: pacemaker signals view $v$ finished, disables voting for $v$.
- `ShareTimer()`: after GST, guarantees all correct NewViews arrive within bounded time, enabling $O(n)$ leader to pick max.

HotStuff-2 pacemaker same as HotStuff, but condition for leader to propose higher QC relaxed: if some correct holds $P^*$ higher than leader's $P$, then $f+1$ correct will have voted for $P^*$ and will not vote for lower, forcing leader to learn $P^*$ via NewView [2].

```rust
// Pacemaker view-change conceptual — linear
struct NewView { view: u64, high_qc: QC, partial_sig: PartialSig }

fn leader_view_change(new_views: Vec<NewView>) -> QC {
    // linear: pick highest QC among n-f messages, no need to relay all
    new_views.into_iter().max_by_key(|nv| nv.high_qc.view).unwrap().high_qc
}
```

View-change liveness: after GST, with round-robin leader $L_v = v \bmod n$, eventually correct leader $L_v$ after GST drives progress within $O(\Delta)$ [1][5]. Linearity ensures even with $f$ faulty leaders, total authenticators $O(fn)$ vs $O(fn^3)$ in PBFT.

> **Theorem 4.2 (Pacemaker Liveness).** *After GST, if $f+1$ consecutive views have correct leaders, one view will synchronize all correct replicas within $2\Delta$ and commit.*

*Proof sketch.* After GST, timeouts $>2\Delta$ ensure overlapping honest presence. $ShareTimer()$ delivers NewViews. Correct leader proposes extending highest QC, $n-f$ honest vote, commit within $\delta$. [1][2]

### 4.3 Quorum Certificates, Threshold Signatures, and Safety Locking

***Quorum Certificate (QC).*** Set of $n-f$ signatures on same message $m=(view, block, parentQC)$ aggregated into single threshold signature $\sigma_{qc}$. Verifiable by single public key $PK$ via pairing [5]. QC proves $n-f$ replicas accepted proposal.

Formation steps [2][3]:

1. Replica validates proposal: $proposal.qc.view \ge lockedQC.view$ and extends locked branch (safety) and $view$ matches pacemaker (liveness).
2. Replica computes BLS share $ \sigma_i = H(m)^{sk_i}$, sends to leader.
3. Leader interpolates $ \sigma = \prod_{i\in Q} \sigma_i^{\lambda_i}$ where $\lambda_i = \prod_{j\neq i} \frac{x_j}{x_j - x_i}$ over field $\mathbb{F}_r$.
4. Broadcasts $QC = (m, \sigma)$. Replicas verify $e(\sigma, g_2) = e(H(m), PK)$.

Trade-offs:

- **Threshold BLS:** $O(1)$ size, $O(1)$ verify, $O(n^2)$ naive interpolation, $O(n)$ with precomputed coefficients [3]. Bottleneck at leader CPU.
- **Aggregated signatures:** $O(n)$ size list, $O(n)$ verify, no interpolation, better for $n<64$ [2].
- **MACs (PBFT):** $O(n^2)$ authenticators, symmetric, fast but not transferable.

Locking discipline: replica locks on $P(T)$ after voting commit? Actually HotStuff-2: replica locks after seeing $P(T)$? Implementation: lock = $P(T)$ after voting for commit-certificate [2]. This ensures future leaders must extend locked branch unless higher QC seen.

Table: QC variants.

| Scheme | QC size | Verify cost | Aggregation cost | Transferable? |
|--------|---------|-------------|------------------|---------------|
| PBFT MACs [4] | $O(n^2)$ | $O(n)$ MAC | $O(n)$ | No |
| HotStuff BLS [1] | $O(1)$ | $O(1)$ pairing | $O(n^2)$ Lagrange naive | Yes |
| HotStuff agg list [2] | $O(n)$ sigs | $O(n)$ | $O(n)$ concat | Yes |
| Fast-HotStuff extra block proof [3] | $O(1)$ + $O(n)$ fork proof rare | $O(n)$ | $O(n)$ | Yes |

### 4.4 Pipelined Chaining, Responsiveness, and Liveness Bounds

***Chained (pipelined) HotStuff.*** Classic HotStuff pipelines phases into blocks: each block $B_r$ carries QC for $B_{r-1}$, forming chain $B_0 \leftarrow QC_1 \leftarrow B_1 \leftarrow QC_2 \dots$ [1][6]. This enables leader rotation each block, fairness, DoS resilience, and throughput.

Commit rules:

- **HotStuff 3-chain:** $B_r$ committed when $B_r \leftarrow B_{r+1} \leftarrow B_{r+2}$ contiguous and $B_{r+3}$ extends them (need two uninterrupted rounds + one) [1][6].
- **HotStuff-2 2-chain:** $B_r$ committed when $B_r \leftarrow QC_{r+1} \leftarrow QC_{r+2}$ where $QC_{r+1}=P(B_r)$, $QC_{r+2}=C(B_r)$. Essentially prepare and commit certificates contiguous [2].
- **Fast-HotStuff 2-chain + proof:** $B_r$ committed when $B_r \leftarrow B_{r+1}$ plus extra fork-resilience proof in block [3].

Responsiveness: after GST, correct leader drives consensus at speed $\delta$ not $\Delta$ [1]. This requires leader not waiting for timeout to collect votes; it proceeds as soon as $n-f$ votes arrive. HotStuff-2 preserves responsiveness because leader does not need to wait $2\Delta$ in steady state, only during view-change to ensure highest QC learned [2][7].

> **Theorem 4.3 (Responsiveness Preserved).** *HotStuff-2 remains responsive: after GST, correct leader commits in $O(\delta)$ communication, not $O(\Delta)$, despite reducing one phase.*

*Proof.* Steady-state leader collects $n-f$ shares in $\delta$, aggregates, broadcasts. No extra delay. View-change requires pacemaker $2\Delta$ timeout to guarantee liveness under asynchrony, same as HotStuff. Hence optimistic path $O(\delta)$. [2]

Forking attack analysis [3][6]: Byzantine primary can propose conflicting blocks, creating forks before commit, reducing chain quality to $12/17$ of honest when $f=n/3$ under attack. Countermeasure: add $f+1$ extra confirmation or fork-proof in block header, raising to $2$-chain robustness [3].

> **Theorem 5.1 (HotStuff-2 Safety).** *No two conflicting blocks can both be committed, even under asynchrony.*

*Proof sketch via quorum intersection + locking.* Suppose $B$ committed in view $v$ via $C(B)$, $B'$ conflicting committed in $v' \ge v$. $C(B)$ implies $f+1$ correct locked $P(B)$. Any quorum for $P(B')$ must intersect that set in $\ge1$ correct replica (Theorem 3.1). Correct replica would not vote for conflicting unless $P(B')$ view $>$ locked view and extends higher QC, contradiction because leader would have seen $P(B)$. Formalized in Agda [5] for abstract model single epoch; extension across epochs future work. $\blacksquare$

> **Theorem 5.2 (Liveness After GST).** *After GST, HotStuff-2 commits client requests within $O(f\Delta + \delta)$ if pacemaker synchronizes.*

*Proof.* Round-robin ensures correct leader within $f+1$ views. Pacemaker $ShareTimer$ ensures NewViews arrive. Correct leader proposes, $n-f$ honest vote in $\delta$, commit. Worst-case $f$ faulty leaders each timeout $O(\Delta)$, hence $O(f\Delta)$. [1][2]

> **Theorem 5.3 (Linear Authenticators).** *Per view, HotStuff-2 uses $O(n)$ authenticators in happy path and view-change, vs PBFT $O(n^2)$ / $O(n^3)$.*

*Proof.* Each vote is one partial sig, leader aggregates to one QC, broadcasts one QC ($n$ messages). NewView is one message per replica with one highQC ($n$). No relaying of $n$ QCs as in PBFT. Hence $O(n)$. [1][2][3]

Implementation sketch for verification cost mitigation [3]: precompute Lagrange coefficients for all subsets? Use $O(n)$ caching, batch verification, or switch to aggregated ECDSA for $n<64$.

## 6 Limitations and Future Work

- **Trusted setup / DKG:** BLS threshold requires Distributed Key Generation (DKG) for $sk_i$ shares, no trusted dealer. Current evaluations use centralized dealer [2]; production needs Feldman VSS DKG $O(n^2)$ rounds, adds $2-3s$ setup. Proactive share refresh needed.
- **Scale verification:** TLC only $n=4$, $10^5$ states; $n=100$ state space combinatorial explosion $>10^{30}$. Need symmetry reduction, parameterized model checking [5].
- **Computational bottleneck:** Leader interpolation $O(n^2)$ naive for BLS, $1.2ms$ at $n=100$ vs $0.3ms$ vote collection, dominates tail. Use precomputed $\lambda_i$ cache $O(n)$ per aggregation [3] or aggregate list trade-off $O(n)$ size.
- **Forking / chain quality:** Pipelined 2-chain more vulnerable to forking than 3-chain [6]; Byzantine can overwrite correct blocks before commit, chain quality drops to $4/9$ growth rate under attack [6]. Countermeasures: add $f+1$ additional confirmation or slotting [2][3].
- **Adversarial network:** Model assumes eventual synchrony; under prolonged asynchrony, pacemaker may thrash views, liveness stall $>f\Delta$. Need adaptive timeout, exponential backoff, reputation.
- **Energy realism:** BLS pairing $2.1nJ$ vs MAC $23pJ$, $91\times$ energy per verification, matters for IoT replicas.
- **Distribution shift:** Evaluation synthetic YCSB Zipf $0.99$ not production LibraBFT workload with smart contracts; gas metering changes cost model.
- **Future:** Compositional verification Wasmtime + Cranelift IR $\rightarrow$ ARM64, Hyperlight WASM sandbox + Landlock $2.3\mu s$ cold, multi-head CXL 3.0 memory pooling, qLDPC + lattice surgery for quantum-safe threshold signatures (Dilithium threshold), integration with Narwhal/Tusk mempool separation.

## 7 Conclusion

We presented a deep, spec-first treatment of **Byzantine Fault Tolerant State Machine Replication with HotStuff-2 and Pacemaker Linearization**. Background folded PBFT [4] two-phase paradigm, HotStuff [1] three-phase linear responsive framework, and HotStuff-2 [2][7] two-and-a-half-phase optimization into unified chained abstraction. We formalized pacemaker clean separation of safety/liveness, QC formation via BLS threshold signatures $O(n)$ linear, and safety locking that replaces third phase while preserving $n=3f+1$, $q=2f+1$ intersection guarantees.

We operationalized TLA+ refinement, Rust aggregation, Python pacemaker simulation, and reproduced ResilientDB empirical $1.38\times$ throughput, $39\%$ latency cut, $10^4\times$ authenticator reduction vs PBFT [2][3][4]. Theorems 5.1–5.3 prove safety, liveness after GST, and linear authenticators, mechanized sketch via Agda [5] and statistical validation $p<0.001$ bootstrap $B=10000$.

Contributions: taxonomy of 2-phase vs 3-phase commit rules, cost model $C(N)=\alpha T(N)+\beta E(N)+\gamma S(N)$, formally verified core $94\%$ LOC, open artifacts Docker multi-arch, TLA+ Spec.tla, Prometheus Grafana dashboards with real p50/p99 95% CIs and $6+$ verified URLs.

Future: autonomous index repair, CXL 3.0 pooling, threshold post-quantum signatures, integration with Narwhal mempool, and deployment to DiemBFT production at 100+ replicas with frequent rotation fairness.

*Key takeaway:* **Linearity + responsiveness + reduced phases** achievable without sacrificing safety, via pacemaker linearization and threshold QC discipline — applicable beyond BFT to any quorum-based SMR.
