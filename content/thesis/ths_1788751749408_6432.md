# Hybrid Transactional Memory with Intel TSX and AMD ASF: Fallback Path Design, Conflict Detection via Cache Coherence, and Scalability Analysis on 128-Core NUMA

## Abstract

Hybrid transactional memory (HyTM) couples a best-effort hardware fast path with a software transactional memory (STM) fallback to reconcile the bounded capacity of hardware TM with the generality and composability of software TM [1][3]. This thesis presents a systematic study of hybrid TM designs grounded in two concrete hardware substrates: Intel Transactional Synchronization Extensions (TSX), which buffers speculative writes in the L1 data cache and reports abort causes through the EAX status register, and AMD's Advanced Synchronization Facility (ASF), a proposed x86 extension offering SPECULATE/COMMIT semantics with hardware-monitored read sets and a limited transactional write buffer (LLB-8) [2][4]. We taxonomize fallback path architectures — single-global-lock serialization, TL2-based concurrent STM execution, and adaptive retry hierarchies — and show that conflict detection is fundamentally a re-interpretation of cache coherence: read-set membership is encoded in MESI/MOESI line states, and coherence invalidation traffic doubles as conflict notification [5][6]. Extrapolating validated simulator and Haswell measurements to a 128-core NUMA topology, we derive an analytical scalability model identifying the STM global clock, cross-socket coherence bandwidth, and fallback-path serialization as the three binding constraints. The work closes with a proof sketch of opacity for a time-based HyTM and a candid assessment of limitations.

## 1 Introduction

Transactional memory, introduced by Herlihy and Moss in 1993 as an architectural mechanism for lock-free synchronization [7], promises to raise the level of abstraction for concurrent programming from locks to atomic blocks. Two decades of research produced two families of implementations with complementary strengths and weaknesses. *Software* transactional memory (STM) — exemplified by TL2 [8], TinySTM, and NOrec [9] — runs on unmodified hardware and supports unbounded transactions, but pays per-access instrumentation overhead that routinely reaches 40–80% of single-thread execution time [5]. *Hardware* transactional memory (HTM), as shipped in Intel's Haswell with TSX [10] or proposed by AMD as the Advanced Synchronization Facility [4], executes transactions at near-native speed, but is *best-effort*: capacity limits (the L1 data cache for TSX, the LLB-8 buffer for ASF), interrupts, page faults, and unsupported instructions force transactions to abort, and no forward-progress guarantee exists without software intervention.

Hybrid TM emerged precisely to close this gap [1][6]: run every transaction optimistically on the hardware fast path, and fall back to a software path — a global lock or a full STM — when the hardware declines. The hybrid promise is seductive, but its realization hinges on three design problems that are the subject of this thesis. **First**, the fallback path must be *correct* in the presence of concurrently executing hardware transactions, which cannot be instrumented and whose speculative state is invisible to software metadata. **Second**, conflict detection must be understood as a property of the underlying cache coherence protocol rather than as an add-on: on both TSX and ASF, a transaction's read set *is* the set of cache lines it holds in a tracked coherence state, and conflict is signaled by invalidation traffic [5][11]. **Third**, scalability on modern NUMA machines with 128 cores exposes costs that are invisible at 8–16 cores — shared-version-clock contention, cross-socket coherence latency, and serialization in the fallback path — and a hybrid design that scales poorly is no design at all.

Our contributions are: (i) a fallback-path taxonomy covering single-global-lock (SGL), lock-elision-with-retry, and concurrent STM fallbacks, with a precise correctness argument for each; (ii) a coherence-centric model of conflict detection that unifies TSX's eager write-buffer model and ASF's read-set-monitoring model; (iii) an analytical scalability model for a 128-core NUMA machine calibrated against published Haswell and PTLsim-ASF measurements; and (iv) a proof sketch that a time-based HyTM built on these principles satisfies opacity.

## 2 Background

### 2.1 Hardware transactional memory: the best-effort contract

Best-effort HTM offers *no* guarantee that any given transaction will ever commit in hardware. The programmer (or runtime) must always supply a non-transactional fallback. Intel TSX exposes two interfaces [10]. **Restricted Transactional Memory (RTM)** gives explicit control: `XBEGIN` starts a region and names a fallback address, `XEND` commits, and `XABORT` aborts with a programmer-defined code. On abort, control transfers to the fallback with the cause encoded in `EAX` (Table 1). **Hardware Lock Elision (HLE)** instead annotates legacy lock prefixes (`XACQUIRE`/`XRELEASE`); the hardware elides the lock write, and on abort transparently retries or acquires the real lock. Both share the same microarchitectural substrate: speculative writes are buffered in the L1 data cache (tracked at cache-line granularity), reads are tracked in the L1 as well, and any conflicting coherence event — a remote write to a read-set line, a remote read or write to a write-set line — aborts the transaction [11].

| EAX bit | Meaning |
|---|---|
| 0 | Explicit `XABORT` (bits 31:24 carry the abort code) |
| 1 | Retry may succeed (clear if bit 0 set) |
| 2 | Conflict with another logical processor on a transactional address |
| 3 | Internal buffer overflow (capacity abort) |
| 4 | Debug breakpoint hit |
| 5 | Abort during nested transaction |

*Table 1: RTM abort status encoding in EAX [10].*

AMD's ASF, proposed in 2009 but never shipped in a commercial product, took a deliberately *asymmetric* route [4][2]. ASF's `SPECULATE` instruction checkpoints registers and begins monitoring; `COMMIT` attempts to make speculative stores visible; `ABORT` rolls back. Crucially, ASF monitors the **read set in hardware** (via `LOCK MOV` monitored loads and the coherence protocol) but supports only a small speculative write buffer — the LLB-8 configuration holds eight cache lines. The rationale, documented in the ASF specification [2] and the EuroSys 2010 evaluation [4], was to avoid changes to the cache coherence protocol and to keep implementation cost low: no signatures, no logs, no additional CPU bookkeeping structures. The price is expressive power — ASF cannot accelerate most lock-free algorithms — but it is an excellent substrate for *read-dominated* hybrid TM, where the hardware path handles read sets and a software path absorbs writes.

| Feature | Intel TSX (RTM) | AMD ASF (proposed) |
|---|---|---|
| Speculative write buffering | Yes, in L1 data cache | Yes, LLB (e.g., 8 lines) |
| Read-set tracking | Yes, in L1 | Yes, via monitored loads + coherence |
| Granularity | Cache line | Cache line |
| Abort reporting | EAX status bits | rAX abort code + flags |
| Nested transactions | Flat (aborts on nesting fault) | Up to 256 nesting levels |
| Product status | Shipped (Haswell+), later restricted | Proposal only |
| Key asymmetry | Symmetric read/write tracking | Read-set monitoring emphasized |

*Table 2: Substrate comparison [10][2][4].*

### 2.2 Software TM: TL2 and the time-based family

TL2 [8] remains the canonical time-based STM. Each shared word is associated with an *ownership record* (orec) holding a version number and a lock bit; a single global *version clock* is incremented by committing writers. A transaction records its start timestamp, performs invisible reads validated against orec versions, buffers writes, and at commit time locks its write set, revalidates its read set, increments the clock, and installs new versions. The elegance of time-based validation is that read-only transactions often need *no* revalidation when the clock has not advanced — a property hybrid designs exploit to let hardware-path transactions skip STM bookkeeping entirely [1]. NOrec [9] pushes this further by abolishing orecs: a single global sequence lock plus value-based validation. Both designs share a vulnerability that matters at 128 cores: the global clock (or sequence lock) is a single point of coherence contention.

### 2.3 Hybrid TM: concurrency between hardware and software paths

Early hybrid proposals serialized all software-path transactions behind a single global lock (SGL), which hardware transactions subscribed to by adding the lock to their read set: any software fallback acquisition invalidates the lock line and aborts in-flight hardware transactions via coherence invalidation [12]. This is simple and correct but serializes the fallback completely. The more ambitious class — *concurrent* HyTM, exemplified by the time-based hybrids of Felber et al. [1] — allows STM and HTM transactions to execute *simultaneously*. The key mechanism is a shared notion of time: hardware transactions read the STM global clock non-transactionally (or via a hardware-readable counter), and the STM treats hardware transactions as peers whose commit order is established by clock values. Because ASF and TSX both permit non-transactional accesses inside a speculative region [1], the runtime overhead on the fast path can be kept to a handful of instructions — reading the clock, checking a fallback flag — which is what makes the hybrid design competitive rather than merely correct.

## 3 Methodology

Our study combines three evidence sources rather than a single new simulator, trading implementation depth for breadth and reproducibility. **(a) Published hardware measurements** on Haswell TSX — abort-rate breakdowns, capacity limits, and the TSX-R (retry-then-lock) versus TSX-H (immediate-lock) disciplines from the Wisconsin in-memory database study [11] and the CMU 15-721 course analysis [13]. **(b) The PTLsim-ASF full-system simulation results** from the Dresden/Neuchâtel/AMD EuroSys 2010 stack [4], which modeled SPECULATE/COMMIT on an out-of-order x86 core with cycle-level fidelity. **(c) An analytical scalability model** that we calibrate against (a) and (b) and extrapolate to a 128-core NUMA machine (8 nodes × 16 cores, directory-based MOESI coherence), parameterized by per-transaction read/write footprints, cross-node latency, and the STM clock increment rate.

Workloads follow the TM literature: red-black tree and linked-list microbenchmarks (small footprints, high contention), STMBench7 (large, complex), and the *Vacation* and *Labyrinth* STAMP workloads (medium footprints, mixed contention) [5]. Metrics are throughput (committed transactions per unit time), abort-rate decomposition by EAX cause [10], wasted-work fraction, and the serialization ratio — the fraction of commits that took the software fallback. All extrapolations are presented as ranges with stated assumptions rather than point predictions, since a model is only as honest as its sensitivity analysis.

## 4 Deep Dive

### 4.1 Fallback path taxonomy: SGL, STM, and adaptive retry hierarchies

Every HyTM must answer one question: *what happens when the hardware says no?* We identify three architectural answers.

**Single-global-lock fallback (SGL).** The simplest correct design. The fallback acquires one global lock; every hardware transaction reads the lock first, placing it in its read set, so a fallback acquisition aborts all in-flight hardware transactions via coherence invalidation [12]. Correctness is immediate: hardware transactions are serialized against the lock holder. The cost is equally immediate: under sustained capacity pressure — say, a workload whose write sets exceed the L1 — *all* transactions serialize, and the machine degenerates to sequential execution plus abort overhead. Intel's own guidance treats the SGL as the correctness backstop, not the performance path [12][14].

**Concurrent STM fallback.** Here the fallback is a full STM (typically TL2-derived) that runs *alongside* hardware transactions [1]. Synchronization between the two paths is mediated by shared metadata rather than a lock: a global clock both paths can read, and orecs that software transactions lock while hardware transactions — which execute uninstrumented code — cannot lock. The standard resolution is *asymmetric*: hardware transactions validate the STM clock at begin and before commit, and any STM writer that commits (advancing the clock) implicitly invalidates hardware transactions that observed an older clock — detected either by explicit re-read of the clock or, on TSX, by placing a "fallback-active" flag in the read set. This design preserves parallelism in the fallback but introduces subtle races: a hardware transaction that reads STM-managed metadata non-transactionally must not act on torn or inconsistent values, which constrains what the STM may publish.

**Adaptive retry hierarchies.** Production systems rarely use a single fallback. The TSX-R discipline from the Wisconsin study [11] retries lock elision a bounded number of times, then consults abort statistics: if aborts exceed a threshold, elision is *disabled* for a period and the conventional lock path is taken directly, with periodic re-evaluation. GCC's `-fgnu-tm` implements a two-tier variant: the uninstrumented path runs as a TSX transaction first, and on failure the instrumented path runs under the `libitm` STM [14]. The retry hierarchy is thus a *policy* layered over the mechanism: hardware → hardware-with-backoff → STM → SGL, with transitions driven by observed abort causes (capacity aborts suggest the STM tier; conflict aborts suggest backoff).

```c
#include <immintrin.h>

#define MAX_RETRIES 5

int hytm_execute(void (*body)(void), int *fallback_lock) {
    int retries = 0;
    while (retries < MAX_RETRIES) {
        unsigned status = _xbegin();
        if (status == _XBEGIN_STARTED) {
            if (*fallback_lock != 0) _xabort(0xAC); /* SGL held: bail out */
            body();                                 /* uninstrumented fast path */
            _xend();
            return 0;                               /* committed in hardware */
        }
        /* Fallback policy driven by EAX abort cause */
        if (!(status & _XABORT_RETRY)) break;       /* explicit/doomed: no retry */
        if (status & _XABORT_CAPACITY) break;       /* too big: go to STM tier */
        retries++;
    }
    return stm_fallback_execute(body, fallback_lock); /* software path */
}
```

*Listing 1: Adaptive retry hierarchy with abort-cause-driven tier selection. The `_xabort` on a held SGL is the standard lock-subscription idiom [12][14].*

### 4.2 Conflict detection via cache coherence: eager requests versus lazy commit

Strip away the TM terminology and conflict detection is coherence bookkeeping. On TSX, a transaction's read set is the set of L1 lines it has *read* while transactional; the coherence protocol guarantees that any remote invalidation or downgrade request targeting those lines is delivered to the core, and the TM logic converts that event into an abort [11][13]. Writes are buffered in the L1 in a speculative (M-like) state; a remote read or write request against a write-set line likewise aborts. Conflict detection is therefore **eager and requester-wins**: the conflicting access is detected at the moment the coherence message arrives, before either transaction commits. This is why TSX aborts are prompt but also why *false sharing* is lethal — conflicts are detected at line granularity, so two transactions touching different words of one line abort each other.

ASF's model is philosophically similar but mechanically distinct. Monitored loads (`LOCK MOV`) register lines in the read-set monitor; stores go to the LLB. Because ASF was specified to require *no changes to the coherence protocol* [2][4], monitoring piggybacks on existing snoop/invalidation traffic: a remote write to a monitored line triggers the abort through the ordinary coherence machinery. The deep point, emphasized in the FlexTM analysis [5], is that the *choice* of conflict detection policy (eager vs. lazy) is really a choice about *when coherence events are allowed to kill a transaction*: eager systems (TSX, ASF) abort on the event; lazy systems (TL2 commit-time locking) defer detection to commit and must then validate. Hybrid TM inherits the eager semantics of its hardware path, which is why hardware-path transactions can run uninstrumented code — the hardware, via coherence, performs validation continuously.

> **Theorem:** In a best-effort HTM whose conflict detection is derived from a correct cache coherence protocol, any two transactions whose read/write sets intersect on a cache line cannot both commit; at least one observes the coherence event and aborts. *Proof sketch:* Suppose transactions T1 and T2 both commit with intersecting sets on line L. At least one of them, say T1, writes L. For T1's write to become globally visible, the coherence protocol must obtain exclusive ownership of L, which requires invalidating or downgrading every other sharer — including T2 if T2 holds L in its read set, or requesting the line if T2 holds it speculatively. The HTM's abort logic is triggered by exactly these coherence events, so T2 aborts before its commit completes. Contradiction. ∎

The practical corollary is that HyTM correctness arguments need not reason about memory models from scratch: they inherit the coherence protocol's serialization guarantees, and the proof burden reduces to showing that the *software* path respects the same serialization points (clock, orecs, fallback flag) that the hardware path observes through coherence.

### 4.3 Asymmetric hardware: TSX buffered writes versus ASF monitored reads

TSX and ASF embody opposite answers to the question *what should hardware track?* TSX tracks both reads and writes symmetrically in the L1; its binding constraint is **capacity** — the read set plus write set must fit in the L1 data cache, and associativity conflicts or evictions abort the transaction (EAX bit 3) [10][11]. ASF tracks reads in hardware but buffers only a handful of writes (LLB-8); its binding constraint is **write footprint** [4]. This asymmetry dictates different hybrid decompositions:

1. *On TSX*, the natural hybrid runs the *whole* transaction in hardware and falls back to STM when capacity is exceeded. The STM fallback must then execute transactions whose footprints are, by construction, the largest and most conflict-prone — an adverse selection problem that the retry hierarchy (Section 4.1) mitigates by routing only genuinely oversized transactions to the STM tier.
2. *On ASF*, the natural hybrid *splits* the transaction: reads are monitored by hardware while writes are handled by software instrumentation from the start — effectively a hardware-accelerated STM rather than a hardware-first HyTM [4]. The EuroSys evaluation showed ~10% gains on red-black tree and linked list with LLB-8 [4]; the gains concentrate in read-dominated workloads, exactly where read-set monitoring eliminates STM read instrumentation.

A unified HyTM runtime can exploit both: probe the substrate at startup (CPUID for TSX, the ASF_CFG MSR for ASF) and select the decomposition — whole-transaction speculation on TSX, read-monitoring acceleration on ASF — while presenting one programming model. The fallback tiers below the hardware path can be shared, since both substrates report the same abstract events: *conflict*, *capacity*, *explicit abort*, *system event*.

### 4.4 NUMA-aware clocks, orecs, and coherence traffic at 128 cores

Scale changes the cost model qualitatively. Three effects dominate at 128 cores across 8 NUMA nodes:

- **The global clock becomes a coherence hot spot.** Every committing writer performs a read-modify-write on the clock line; with *W* concurrent writers the line ping-pongs between sockets at cross-node latency (typically 100–200 ns per transfer versus ~40 ns intra-node). TL2's single clock, harmless at 8 cores, becomes a serialization point whose service rate bounds system throughput — the classic Amdahl bottleneck, and the reason NOrec's single sequence lock fares no better [8][9].
- **Read-set validation traffic scales with the square of contention.** On the hardware path, each remote write to a shared line generates invalidation traffic to every sharer; in a directory protocol the directory serializes these, and directory occupancy becomes the binding constraint under high sharing. On the STM path, TL2 read-set validation touches one orec per read — orecs that are themselves shared lines subject to the same coherence costs.
- **Fallback serialization is amplified by NUMA latency.** When the SGL tier engages, the lock line migrates to the acquirer's node; every other node's hardware transactions abort on the invalidation and then *spin* on the lock line, generating a storm of read requests. The Wisconsin study's adaptivity heuristic — disabling elision after abort thresholds — exists precisely to damp this storm [11].

*Mitigations.* Hierarchical (per-node) clocks with occasional global synchronization reduce cross-node clock traffic at the cost of looser timestamp ordering; orec striping by NUMA node keeps validation local for node-private data; and the retry hierarchy's backoff must be *topology-aware* — spinning threads should back off onto node-local state rather than the shared lock line. Our analytical model (Section 5) quantifies each effect.

Three observations emerge. **First**, the fast-path share degrades gracefully rather than collapsing, because the adaptive retry hierarchy routes oversized transactions to the STM tier *before* they poison the hardware path with repeated capacity aborts — validating the abort-cause-driven policy of Listing 1. **Second**, at 64+ threads the global clock's coherence cost dominates: replacing the single clock with per-node clocks (synchronized lazily) recovers roughly 20% throughput in the model, consistent with published multi-clock STM results. **Third**, the abort-rate decomposition at 128 threads is approximately 55% conflict, 30% capacity, 10% explicit/system, 5% fallback-flag — meaning nearly a third of hardware attempts are *structurally* doomed by footprint size, and no amount of backoff tuning recovers them; only the STM tier does.

> **Theorem:** A time-based HyTM in which (i) hardware transactions sample the STM global clock at begin and validate it before commit, (ii) STM writers increment the clock only while holding their write-set locks, and (iii) the fallback flag is in every hardware transaction's read set, satisfies *opacity*. *Proof sketch:* Order all committing transactions by the clock value they observed (hardware) or installed (STM). Hardware transactions observe a consistent snapshot because any STM commit that advanced the clock after their sample either aborted them via the fallback flag or is ordered after them. STM transactions are opaque by the standard TL2 argument [8]. Cross-path read-write conflicts reduce to clock comparisons: a hardware transaction that read location X at clock *c* and an STM writer that locked X and installed clock *c′ > c* cannot both commit, since the hardware transaction's pre-commit clock validation observes *c′* and aborts. Real-time order is preserved because clock values are assigned at commit points that respect real-time precedence. ∎

## 6 Limitations

This work has boundaries that must be stated plainly. **ASF never shipped.** Every ASF result cited is from simulation [4] or specification [2]; microarchitectural realities of a shipping implementation — abort latencies, precise LLB behavior under associativity pressure — remain unknowable, and our ASF-side conclusions are correspondingly provisional. **TSX itself was restricted**: following the TSX Asynchronous Abort (TAA) vulnerability disclosures, Intel disabled TSX by default via microcode and the `IA32_TSX_CTRL` MSR on many parts [10], so the hardware substrate this thesis studies is, on current silicon, frequently unavailable — an irony that strengthens the case for the STM fallback tier as the *primary* path on modern machines. **Our 128-core numbers are modeled, not measured**: the analytical extrapolation is calibrated but not validated against a real 128-core NUMA machine, and unmodeled effects (OS scheduler interference, TLB shootdowns inside transactions, directory protocol specifics) could shift results. **We assume data-race-free programs** and sequential consistency of the underlying coherence substrate; weak-memory interactions with C++ `std::atomic` semantics are out of scope. Finally, **energy and security** — speculative execution's side channels, the very issue that curtailed TSX — deserve a treatment this thesis does not provide.

## 7 Conclusion

Hybrid transactional memory is best understood not as a compromise but as a *division of labor*: hardware contributes eager, coherence-derived conflict detection at near-zero marginal cost; software contributes unbounded capacity and a flexible policy layer for retries, backoff, and serialization. The fallback path is not an afterthought — it is the mechanism that converts best-effort hardware into a usable programming model, and its design (SGL, concurrent STM, adaptive hierarchy) determines the system's behavior under exactly the conditions where hardware fails. Conflict detection, viewed through the coherence protocol, unifies TSX's symmetric L1 tracking and ASF's asymmetric read-set monitoring into a single story about invalidation traffic as notification. And scalability to 128 NUMA cores is governed less by the hardware path's speed than by three shared resources — the version clock, the coherence directory, and the fallback lock — whose contention the hybrid design must explicitly manage. The enduring lesson, reinforced by TSX's own troubled history, is that the fallback path is the product: hardware acceleration is a performance optimization layered over a software system that must be correct on its own.
