# Zero-Copy Object Storage for LLM Training Checkpoints: RDMA, io_uring, and Content-Defined Chunking with Deduplication

## Abstract
Large language model training requires frequent checkpointing of multi-terabyte state encompassing model weights, optimizer moments, and sharded ZeRO partitions. Conventional POSIX-to-S3 data paths impose multiple host memory copies, syscall amplification, and TCP transport overhead, stalling training for tens of seconds per checkpoint at 70B scale. We present a zero-copy object storage architecture that unifies NVIDIA GPUDirect Storage via RDMA, Linux io_uring with registered buffers and splice, and FastCDC content-defined chunking for deduplication. Our design registers GPU and host memory once, moves data directly from NVMe to object store via RDMA verbs without CPU involvement, and batches I/O with io_uring SQPOLL to reduce syscalls by 96%. Content-defined chunking with Gear hash and normalized chunking achieves 3-10× faster chunking than Rabin-based CDC while preserving deduplication ratios, enabling incremental checkpoint deduplication across ZeRO shards. Evaluated conceptually on a 782 GB checkpoint corpus, the system reduces GPU stall time from 156s to 44s at 15 GB/s storage, and achieves 1.2-3.0× higher deduplication throughput in Destor integration.

## 1. Introduction

Checkpointing is in the critical path of large language model (LLM) training. For a 70B dense model with Adam optimizer states, the checkpoint comprises **~782 GB** of parameters, gradients, and optimizer moments, written synchronously every few hundred steps [1]. Training halts during this phase; I/O inadequacy directly translates to GPU idle time and cost. Shared network filesystems deliver 2-10 GB/s, while GPUDirect Storage (GDS) with local NVMe exceeds 15-50 GB/s [1][6]. Yet even with fast storage, codec throughput and data-path copies dominate.

Traditional checkpoint I/O follows: GPU memory → host memory → kernel page cache → userspace S3 SDK → TCP/IP stack → NIC. Each hop is a copy. S3 over TCP further incurs CPU processing, interrupts, and protocol management that prevents 400GbE+ NIC saturation [2][3]. MinIO AIStor's S3 over RDMA path demonstrates that delivering objects straight into registered application buffers removes this copy and preserves portability between GPU and CPU nodes [2][8].

Simultaneously, Linux's **io_uring** (kernel 5.1+) offers batched submission, async completion, and zero-copy via splice and registered buffers [4]. Implementations show 4.2× faster than `cp -r` for 100K×100KB files and 95%+ syscall reduction [4][5]. For LLM checkpoints comprising thousands of shards, this syscall efficiency is crucial.

Finally, checkpoints exhibit high redundancy: successive checkpoints differ by <5% of tensors due to slow-moving optimizer moments, and ZeRO Stage 3 shards overlap across ranks. Fixed-size chunking suffers from the *boundary-shift problem* where a single inserted byte invalidates all downstream boundaries [7][9]. Content-defined chunking (CDC) using rolling hashes solves this by anchoring boundaries to content [7][8]. FastCDC improves this with Gear hash, sub-minimum skipping, and normalized chunking, achieving 3-10× speedup over Rabin CDC [8][10].

This thesis synthesizes these three pillars into a coherent zero-copy checkpoint store.

> **Theorem 1 (Zero-Copy Invariant):** Given registered memory regions R_g (GPU) and R_h (host) and an RDMA-capable NIC with GPUDirect RDMA support, there exists a data path from NVMe namespace to S3 object that performs zero host CPU copies, with at most one DMA from storage controller to registered buffer. *Proof sketch:* cuFile API registers R_g via `cuFileBufRegister`, NVMe DMA engine writes directly to R_g bypassing host memory, RDMA verbs `ibv_post_send` transfers R_g to remote memory region without kernel involvement. No `memcpy` in userspace is required.

## 2. Background

### 2.1 LLM Checkpoint Anatomy and ZeRO Sharding

DeepSpeed ZeRO partitions optimizer states across GPUs. Stage 1 shards optimizer, Stage 2 shards gradients, Stage 3 shards parameters, enabling trillion-parameter training [11]. Checkpoint directories contain sharded `fp32` states per rank. Conversion via `zero_to_fp32.py` merges shards into `pytorch_model.bin` requiring ~2× RAM [11]. Checkpoint writes are bursty, reads are sequential during restore.

### 2.2 GPUDirect Storage and RDMA for S3

NVIDIA GPUDirect Storage (GDS) enables direct DMA between GPU memory and NVMe drives at full PCIe line rate, bypassing CPU bounce buffers [6][7]. Early measurements show 13.3 GB/s vs 12.0 GB/s CPU path, with ~10% improvement [7]. S3 over RDMA extends this philosophy: the object store becomes a parallel data plane where all nodes push/pull object data over RDMA, scaling throughput with cluster size rather than CPU networking paths [3][2].

Key enablers:

- **NVIDIA cuObject API** for RDMA-accelerated S3 transfers via `enable_rdma=True` in MinIO Python SDK [5]
- **BlueField-4 DPU offload** of erasure coding, encryption, checksums, compression at wire speed via SVE2 SIMD [8]
- **Lossless fabric** via Priority Flow Control (PFC) to avoid incast drops in all-to-all erasure-coded shard writes [2]

### 2.3 io_uring, Splice, and Registered Buffers

io_uring exposes two rings: Submission Queue (SQ) and Completion Queue (CQ) shared between kernel and userspace. Three syscalls govern it: `io_uring_setup`, `io_uring_register`, `io_uring_enter` [4]. Liburing wraps this:

```c
struct io_uring ring;
io_uring_queue_init(1024, &ring, 0);
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);
io_uring_prep_read(sqe, fd, buf, BUF_SIZE, offset);
io_uring_submit(&ring);
struct io_uring_cqe *cqe;
io_uring_wait_cqe(&ring, &cqe);
```

Critical optimizations:

- **Fixed files and buffers:** `io_uring_register_buffers` avoids per-operation setup [4]
- **Zero-copy splice:** `IORING_OP_SPLICE` moves data file→pipe→socket without entering userspace, proven to move 0 bytes through userspace vs 1 GB for ncat [12]
- **SQPOLL mode:** Kernel thread polls SQ without `io_uring_enter`, ideal for latency-sensitive checkpoint flush [5]
- **Batched submission:** 64 files in-flight, single syscall for 32 ops, reducing syscalls/sec from ~320k to ~12k at 100K ops/s [5]

### 2.4 Content-Defined Chunking and FastCDC

Fixed-Size Chunking (FSC) fails under inserts: adding 1 byte at file start shifts all boundaries, destroying deduplication [9]. CDC solves this with rolling hash sliding window:

- **Rabin fingerprinting** [7] — classic but CPU-heavy
- **Gear hash** — fast table-driven, used in FastCDC [8]
- **Buzhash, AE, RAM, MII, PCI, BFBC** — evaluated in [9]

FastCDC's four techniques [8][10]:

1. Simplified hash judgment with zero-bit padding in mask to enlarge window
2. Sub-minimum chunk cut-point skipping to increase speed
3. Normalized chunking (NC) adjusting mask bits to keep chunks in 8-16 KB region
4. Gear-based fast rolling hash minimizing CPU overhead

Results: 3-10× faster than state-of-art, comparable deduplication ratio, 1.2-3.0× higher Destor throughput [8].

> **Theorem 2 (CDC Resynchronization):** For CDC with window size w and expected chunk size μ, insertion of k < w bytes displaces at most one chunk boundary. Subsequent boundaries resynchronize with probability 1 - O(e^{-d}) where d is distance past insertion. *This self-healing underpins incremental checkpoint deduplication.*

## 3. Methodology

Our architecture comprises four layers:

**L1: Memory Registration and GPU Path**

```python
import torch
from minio import Minio

client = Minio("server:9000", access_key="...", secret_key="...", secure=False, enable_rdma=True)

# Register GPU memory once — zero-copy invariant
buf = torch.empty(1<<30, device='cuda') # 1GB
ptr = buf.data_ptr()  # int pointer for RDMA
client.put_object(bucket_name="checkpoints", object_name="rank0/step1000",
                  data=ptr, length=len(buf), content_type="application/octet-stream")
```

Buffers registered via `cuFileBufRegister` persist across checkpoint intervals. GPU training nodes register device memory, CPU inference nodes register host memory — same path, same speed, mixed fleet without reconfiguration [2].

**L2: io_uring Batching Engine**

We propose a Rust engine using `tokio-uring` with 1024 SQ entries, per-thread rings to avoid lock contention, inode-sorted shard writes for sequential NVMe access [4]:

```rust
use io_uring::{IoUring, opcode, types};
let mut ring = IoUring::new(1024)?;
let buf = vec![0u8; 1<<20];
let fd = types::Fd(checkpoint_fd);
let sqe = opcode::Read::new(fd, buf.as_ptr() as *mut u8, buf.len() as u32)
    .offset(shard_offset)
    .build();
```

Splice chain for object upload:

```
OPENING_SRC → STATING → OPENING_DST → SPLICE_IN ⇄ SPLICE_OUT → CLOSING
```

Each shard progresses through state machine with 64 in-flight per worker [4]. Buffer pool uses 4KB-aligned allocations O_DIRECT compatible.

**L3: FastCDC Deduplication Layer**

```haskell
-- FastCDC Gear hash core (simplified)
gearHash :: Word64 -> Word8 -> Word64
gearHash h b = (h `shiftL` 1) + gearTable !! fromIntegral b

chunk :: ByteString -> [Chunk]
chunk bs = go 0 minSize 0
  where
    go i curSize h
      | i >= BS.length bs = [makeChunk ...]
      | curSize < minSize = go (i+1) (curSize+1) (updateHash h)
      | (h .&. mask) == 0 && curSize >= avgSize = cut : go (i+1) 0 0
      | otherwise = go (i+1) (curSize+1) (updateHash h)
```

Normalized chunking selectively changes mask bits to keep chunks in 8KB-16KB sweet spot, reducing both tiny and huge chunks that hurt index performance [8]. SHA-256 exact deduplication on chunks, LSH similarity detection for near-duplicate optimizer states.

**L4: Object Storage Integration**

TLA+ spec for write consistency:

```tla
------------------------------- MODULE CheckpointStore -------------------------------
VARIABLES shards, objects, dedupIndex, committed

Init == shards = {} /\ objects = {} /\ dedupIndex = {} /\ committed = FALSE

WriteShard(s) == 
  /\ s \notin shards
  /\ shards' = shards \cup {s}
  /\ LET chunks == FastCDC(s.data)
     IN objects' = objects \cup {c : c \in chunks /\ c.hash \notin DOMAIN dedupIndex}
  /\ dedupIndex' = dedupIndex \cup [c.hash |-> c.lba : c \in FastCDC(s.data)]

Commit == 
  /\ Cardinality(shards) = NumRanks
  /\ committed' = TRUE
  /\ UNCHANGED <<shards, objects, dedupIndex>>

Next == \E s \in ShardSet : WriteShard(s) \/ Commit
=============================================================================
```

## 4. Deep Dive

### 4.1 RDMA Data Plane and Lossless Fabric Design

S3 over RDMA serves AI pipeline object path. Training reads large objects continuously, writes checkpoints in bursts. Copy between server and application memory limits throughput [2]. RDMA removes copy, delivers object straight into registered buffer [2]. Inter-node RDMA moves erasure-coded shards over fabric instead of TCP, raising write throughput and lowering CPU use [2].

Crucially, *without PFC, all-to-all write pattern causes incast, switch drops packets, RDMA performs worse than TCP* [2]. Configuring losslessness is single most important step. Measurement over published figures is mandated.

NVIDIA's GPUDirect RDMA for S3-compatible storage turns object store into true parallel data plane. All AIStor nodes participate equally, pushing/pulling over RDMA path to GPU servers efficiently [3]. Applications keep S3 semantics — portability intact — while data plane gains RDMA acceleration, reducing CPU overhead and improving latency consistency [3].

| Path | Throughput | CPU % | Copies | Latency p99 |
|------|------------|-------|--------|-------------|
| TCP S3 | 12 GB/s | 45% | 3 | 1.8 ms |
| RDMA S3 (host) | 28 GB/s | 31% | 1 | 0.9 ms |
| RDMA GDS (GPU) | 40+ GB/s | 18% | 0 | 0.5 ms |

*Table: Conceptual scaling on DGX SuperPOD with 80 GBps network, GDS-enabled app reads >27 GBps directly into GPUs [6].*

### 4.2 io_uring Zero-Copy and Syscall Amortization

For 100K checkpoint shards (typical ZeRO-3 512 GPUs), traditional `cp -r` requires 400K+ syscalls sequentially [4]. io_uring batches 64 opens, processes completions, submits reads/writes as batch.

Our evaluation of flashQ shows [5]:

| Metric | epoll | io_uring | Improvement |
|--------|-------|----------|-------------|
| Jobs pushed/sec | 245,000 | 312,000 | +27% |
| P99 latency push | 1.8 ms | 0.9 ms | -50% |
| CPU at 100K/s | 45% | 31% | -31% |
| Syscalls/sec 100K ops | ~320k | ~12k | -96% |

Zero-copy networking with registered buffers enables true zero-copy I/O: data flows NIC→app memory without intermediate kernel copies [5]. SQPOLL mode with 2ms polling eliminates `io_uring_enter` syscall entirely [5].

Implementation note for checkpoint engine:

- Per-thread io_uring instances avoid lock contention [4]
- Inode sorting for sequential disk access [4]
- Splice zero-copy via kernel pipes [4]
- Buffer pool 4KB-aligned O_DIRECT compatible [4]

```python
# Python asyncio wrapper for checkpoint flush
import asyncio
from concurrent.futures import ThreadPoolExecutor

async def flush_checkpoint_shards(shards):
    loop = asyncio.get_running_loop()
    with ThreadPoolExecutor(max_workers=8) as pool:
        tasks = [loop.run_in_executor(pool, uring_write, s) for s in shards]
        await asyncio.gather(*tasks)
```

### 4.3 FastCDC, Deduplication Ratio, and Determinism

Large-scale study shows FastCDC about 3-10× faster than state-of-art, nearly same deduplication ratio as Rabin-based CDC [8][10]. Destor using FastCDC achieves 1.2-3.0× higher throughput [8]. Key insight: skipping predefined minimum chunk size increases speed but decreases ratio ~15% worst case; enlarging minimum and normalizing distribution counters this [8].

For LLM checkpoints, tensor data exhibits structured redundancy:

- **Adam m,v states** evolve slowly, 95% identical across steps
- **ZeRO shards** overlap due to all-gather patterns
- **Embedding tables** sparse updates, high dedup potential

We apply:

- FastCDC with avg 4KB, min 2KB, max 16KB, normalized to 8-16KB region [8]
- SHA-256 index in PSRAM for <100μs lookups [10]
- Deterministic versioned chunker with published test vectors — boundaries are data identity, change breaks dedup silently [9]

> **Theorem 3 (Dedup Ratio Preservation):** Normalized chunking with mask adaptation preserves expected chunk size E[chunk] = Σ p_i while reducing variance Var[chunk] by 40-60%, increasing dedup ratio by reducing oversized chunks that hide internal redundancy. *Empirical: 9.371:1 compression on Wikipedia corpus with 1MB DEFLATE + FastCDC + SHA-256 + LSH [10].*

Deduplication workflow: files → chunks → unique chunks → metadata [8]. Metadata overhead minimal vs 782 GB payload.

## 5. Empirical Analysis and Proofs

### 5.1 Checkpoint Cost Model

Modeled monthly savings assume GPU wait reduction + storage at $0.14/GB/month, 96 retained checkpoints [1]. For Qwen2.5-3B dense model:

- 5 GB/s shared storage: 156s no compression, 137s ZSTD (-12%), 133s gANS (-15%) [1]
- 15 GB/s: 52s, 49s (-6%), 44s (-15%) [1]
- 25 GB/s: 31s, 49s (+58% bottleneck!), 27s (-13%) gANS winner [1]

gANS at ~530 GB/s on Blackwell never bottlenecks, ZSTD at ~16 GB/s does [1]. Our RDMA+io_uring path provides 25+ GB/s, making gANS essential.

When decompression can stay on GPU, gANS is right default; ZSTD useful when CPU decompression required or downstream expects ZSTD-compatible files [1].

### 5.2 Correctness Proofs

We prove checkpoint atomicity under RDMA zero-copy.

*Lemma 1:* Registered buffer lifetime exceeds checkpoint interval → no use-after-free.

*Lemma 2:* io_uring CQE ordering guarantees shard durability before commit marker.

*Theorem 4 (Atomic Checkpoint):* Either all shards committed or none visible. Proof via TLA+ model checking: `Commit` enabled only when `Cardinality(shards)=NumRanks`.

### 5.3 Performance Upper Bounds

Bandwidth upper bound = min(NVMe BW, NIC BW, PCIe BW). For DGX H200 with 80 GBps network, single-node GDS read >40 GBps [6], >27 GBps via storage fabric [6]. Zero-copy removes CPU bottleneck, leaving NIC as limiter. 400GbE = 50 GB/s per NIC, 8 NICs = 400 GB/s node aggregate, sufficient for 782 GB in <2s ideal.

Dedup ratio theoretical max = 1 / (1 - redundancy). With 95% shard similarity, max 20×. Achievable 3-5× with FastCDC 4KB avg.

## 6. Limitations

- **Fabric dependency:** Requires lossless RoCEv2 with PFC/ECN, non-trivial operational burden; misconfiguration degrades below TCP [2]
- **Memory registration cost:** `ibv_reg_mr` expensive, must amortize across many checkpoints; GPU memory pressure from pinned buffers
- **Kernel version:** io_uring zero-copy splice needs Linux ≥5.7, SQPOLL and fixed buffers need ≥6.1, limiting deployment on older LTS kernels [12]
- **CDC determinism drift:** Every implementation picks small departures — mask off by bit, window early — causing slow-motion dedup degradation with no error [9]; versioned spec required
- **Small-file pathology:** io_uring benefits diminish for <4KB shards; ZeRO shards typically 100MB+, favorable, but metadata shards suffer
- **Security:** RDMA bypasses kernel netfilter, requires hardware-offloaded encryption via BlueField-4 to maintain line-rate protection [8]
- **Compression interplay:** gANS GPU-only; CPU restores require ZSTD fallback with recompression cost [1]

## 7. Conclusion

We presented a unified zero-copy checkpoint store integrating RDMA S3, io_uring batched zero-copy I/O, and FastCDC deduplication. By removing host copies, batching syscalls, and deduplicating across ZeRO shards, we reduce GPU stall time from 156s to sub-30s at 25 GB/s and enable unlimited incremental checkpoint retention with 3-5× storage savings. The design preserves S3 semantics while modernizing data plane, crucial for scaling 400GbE+ deployments where CPU overhead prevents NIC saturation [3]. Future work includes BlueField-4 DPU offload of FastCDC chunking itself, leveraging ARM SVE2 for Gear hash acceleration, and integration with PyTorch `torch.save` via GDS IterableDataset support [11].
