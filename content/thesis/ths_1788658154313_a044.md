# Lookup Arguments for Succinct Proofs: Plookup, Caulk, logUp, and the Role of Lookups in Halo2-Style zk-SNARKs

## Abstract

Lookup arguments are among the most consequential primitives in modern succinct proof systems. They allow a prover to demonstrate that every element of a committed witness vector occurs in a (possibly much larger) precomputed table, reducing expensive in-circuit logic such as bit decompositions, range checks, and bitwise operations to compact membership checks. This thesis surveys the principal generations of lookup arguments: Plookup [1], which introduced the sorted-table grand-product technique; Caulk [2] and Caulk+ [3], which achieved prover time sublinear in the table size via subvector commitments; logUp [7], which replaced sorting with logarithmic derivatives and later gained a GKR-based acceleration [8]; the cq protocol [6], which reduced prover work to *O*(*m* log *m*); and the Halo2 subset argument [9], the distinct lookup machinery powering the Halo2 proving system. We give precise protocol descriptions, unify their soundness analyses around multiset equality and Schwartz–Zippel identities, compare asymptotic and concrete costs, and assess limitations including preprocessing burdens, pairing-heavy verifiers, and aggregatability constraints.

---

## 1 Introduction

The history of practical zero-knowledge SNARKs is, to a large extent, a history of expanding what can be *expressed cheaply* inside an arithmetic circuit. Early constraint systems offered only low-degree polynomial relations over a large prime field, which made bitwise operations, range checks, and hash-function S-boxes punishingly expensive: an 8-bit XOR between field elements costs on the order of 25–32 constraints via explicit bit decomposition [1]. Lookup tables offered an escape hatch. Rather than *computing* a function in-circuit, the circuit commits to a table of all valid input–output pairs and proves, for each witness value, that it appears as a row of the table. A single membership check replaces dozens of constraints.

A *lookup argument* is the proof primitive formalizing this idea. Given a committed vector of witness values **f** and a table **t** (itself possibly committed), it proves the relation

> **Lookup relation.** For every index *i*, the value *fᵢ* occurs in the table **t** (possibly with repetitions).

The naive approach—evaluating a membership polynomial per lookup—scales with the table size *N* and destroys succinctness for large tables. The past six years have therefore produced a rich taxonomy of lookup arguments trading off prover time, proof size, verifier work, preprocessing cost, and commitment structure. This thesis traces that taxonomy, from Plookup through the sublinear-prover line (Caulk, Caulk+, flookup, Baloo, cq), the logarithmic-derivative line (logUp), and the Halo2 design that departed from Plookup entirely.

## 2 Background

### 2.1 Multisets, grand products, and Schwartz–Zippel

Nearly every lookup argument reduces membership to a *multiset equality* between two multisets derived from the witness and the table, checked with a randomized grand-product or sum identity. The pattern originates in the permutation arguments of PLONK, where copy constraints are enforced by proving that two multisets of wire values are permutations of one another via an accumulator *Z* satisfying

*Z(g) = 1, Z(gⁱ⁺¹) = Z(gⁱ) · Fᵢ(β, γ),*

with *Fᵢ* a per-row rational function of verifier challenges *β*, *γ*, and a terminal check *Z(gⁿ) = 1*. Lookup arguments reuse this template with a different per-row function: one whose total product equals 1 if and only if every witness value appears in the table.

Soundness arguments for all these protocols rest on the Schwartz–Zippel lemma: if the lookup relation holds, a certain low-degree polynomial identity holds as a formal identity; if it does not hold, the identity is a nonzero polynomial evaluated at random verifier challenges, and fails to vanish except with probability bounded by its degree over the field size [7].

### 2.2 The Bootle et al. precursor

Gabizon and Williamson describe Plookup as a simplification of an earlier protocol of Bootle et al. for a similar membership problem [1]. That earlier construction required commitments to several auxiliary polynomials of degree *d* · log *n* (for a table of size *d* and domain of size *n*), whereas Plookup needs only three auxiliary commitments of degree *n*—a substantial saving when the table size *d* is comparable to the circuit size *n*. Plookup's headline application was the *batched range proof*: proving that all values of a committed polynomial on a subgroup lie in a range *[0, …, M]* [1].

### 2.3 Why Halo2 matters

Halo2 is a PLONKish proving system originally developed by Zcash that uses *rows and columns* of a circuit matrix rather than PLONK's single-wire layout. Critically, Halo2 does *not* use Plookup: it defines its own subset argument with a different multiset-equality structure, deliberately simplified relative to the sorted-merge approach [9]. Because Halo2 underpins major industrial deployments—including zkEVM circuits, where lookup-heavy byte and XOR tables dominate proving cost—its lookup design deserves equal billing with the academic line.

## 3 Methodology

This thesis follows a *comparative protocol-analysis* methodology:

1. **Protocol extraction.** For each of the six principal protocols (Plookup, Caulk, Caulk+, logUp, cq, Halo2), we isolate the precise relation being proved, the per-row accumulator or quotient identity, the number and degree of committed auxiliary polynomials, and the verifier's check set.
2. **Asymptotic comparison.** We compare prover time, proof size, verifier time, and preprocessing in terms of the number of lookups *m* and the table size *N*, drawing on the unified benchmark table compiled in the lookup literature [4].
3. **Soundness unification.** We restate each protocol's soundness as an instance of the same template: a randomized rational identity whose numerator and denominator polynomials coincide as multisets exactly when the lookup relation holds, with error bounded by Schwartz–Zippel.
4. **Empirical grounding.** Where available, we report concrete figures published by the authors: Caulk's 100× improvement over SNARKed Merkle membership proofs [2], Haböck's paper-and-pencil 3.9× speedup for multi-column logUp [7], and the memory profile of lookup proving in production zkEVM circuits.
5. **Limitation cataloguing.** We enumerate structural weaknesses—preprocessing costs, non-homomorphic commitments that block aggregation, and pairing shapes hostile to recursive composition.

## 4 Lookup Argument Designs: A Deep Dive

### 4.1 Plookup: sorted tables and the grand product

Plookup [1] addresses the following problem: given a committed polynomial *f* in 𝔽_{<n}[X] over a multiplicative subgroup *H* ⊂ 𝔽 of size *n*, and a table **t** in 𝔽^d, prove that every value of *f* on *H* occurs in **t**.

The protocol's central maneuver is to form **s**, the *sorted concatenation* of the witness values and the table values, and to reduce membership to a grand-product identity. Intuitively, if *s* is truly the sorted merge, then a grand product comparing consecutive elements of *s* against the (*f*, **t**) pairs can only balance if the multisets match. The per-row grand-product factor is

*Fᵢ(β, γ) = (1+β)(γ+fᵢ)(γ+tᵢ) / ((γ+sᵢ)(γ+sᵢ₊₁)),*

with the accumulator *Z* initialized to 1 and a terminal check *Z(gⁿ) = 1* enforcing that the total product balances. A second identity enforces the *sortedness* of *s* itself: consecutive elements of *s* must either be equal or be consecutive table entries, expressed as a polynomial identity in *s* and **t** [1].

The prover commits to three auxiliary polynomials—the sorted table *s*, the grand product *Z*, and the sorting-relation quotient—each of degree *n*, and the verifier performs 2 pairings. Proof size is 9 field elements plus 5 𝔾₁ elements, with prover work *O*(*n* log *n*) field operations and *O*(*n*) group operations [4].

> **Theorem: Plookup soundness.** Let *f*, *t*, *s*, *Z* be as above. If the verifier's grand-product and sortedness identities hold at random challenges *β*, *γ*, then every value of *f* on *H* belongs to the table **t**, except with probability at most *(2n + d)* · polylog(|𝔽|) / |𝔽|. The argument is zero-knowledge with the addition of standard random blinding to *s* and *Z* [1].

Plookup's main structural cost is the *sorting*: the prover must construct and commit to the sorted merge *s* and satisfy the sortedness identity, and prover time is inherently linear in the table size (or the domain size, whichever is larger). This motivated the entire sublinear-prover line.

The following pseudocode captures the core grand-product check:

```python
def plookup_grand_product_check(f_vals, t_vals, s_vals, Z_vals, beta, gamma):
    """Verify the Plookup grand-product relation over n rows.

    f_vals: witness lookups (length n); t_vals: table (length d <= n)
    s_vals: sorted merge of f and t; Z_vals: grand product accumulator
    Returns True iff the accumulator telescopes to 1.
    """
    assert Z_vals[0] == 1
    n = len(f_vals)
    for i in range(n):
        f_i, t_i = f_vals[i], t_vals[i % len(t_vals)]
        s_i, s_next = s_vals[i], s_vals[(i + 1) % len(s_vals)]
        F_i = ((1 + beta) * (gamma + f_i) * (gamma + t_i)
               / ((gamma + s_i) * (gamma + s_next)))
        assert Z_vals[i + 1] == Z_vals[i] * F_i
    return Z_vals[n] == 1  # terminal check: products balance
```

PlonKup [5] later integrated Plookup's ideas into a fully succinct PLONK-compatible SNARK, handling the interaction between the lookup argument and PLONK's permutation and gate constraints, and extending the design to multiple lookup tables.

### 4.2 Caulk and Caulk+: subvector commitments and sublinear provers

Caulk [2] asked a sharper question: can the prover's work be made *sublinear in the table size N*, so that a circuit can look up into a gigantic table while paying only for the *m* lookups actually performed? The answer introduced *position-hiding linkability for vector commitments*: given a commitment *C* to a table **c** of size *N*, the prover shows that one or *m* committed values all belong to the committed vector—without revealing their positions.

The technical core is a *subvector commitment* argument. The prover identifies the subset *I* ⊂ [*N*] of table positions actually used, commits to the subvector **c**_I and to the vanishing polynomial *z_I(X)* = ∏_{i∈I} (*X* − ωᵢ), and convinces the verifier (via KZG-style opening checks and pairings) that **c**_I is genuinely the restriction of **c** to *I* [2]. Once the subvector is extracted, membership of the *m* lookups reduces to a small check against **c**_I rather than the full table. Asymptotically, Caulk achieves prover time *O*(*m*² + *m* log *N*) after *O*(*N* log *N*) preprocessing, with constant proof size and verifier time *O*(log log *N*) [2]—beating SNARKed Merkle membership proofs by a factor of 100 even against a Poseidon-based Merkle tree [2].

Caulk+ [3] improved the prover to *O*(*m*²) and, crucially, made the argument *table-independent*: the prover no longer needs the table itself during proof generation, only its commitment plus preprocessing data. This enabled commit-and-prove workflows where the table is committed once and reused.

The lineage continued rapidly:

- **flookup** [10] replaced the quadratic component with a *fractional decomposition* technique, reaching quasilinear prover time *O*(*m* log² *m*) after *O*(*N* log² *N*) preprocessing—but at the cost of a non-homomorphic table commitment, which prevents batching several tables into one protocol run [10].
- **Baloo** [11] matched flookup's *O*(*m* log² *m*) while *retaining* homomorphic commitments, enabling vector lookups of the form {*aᵢ* + *αbᵢ*} from commitments to tables *T*₁, *T*₂ via the linear combination *cm* := *cm*₁ + *α*·*cm*₂, and supported commit-and-prove expansions aimed at EVM instantiation [11].
- **cq** ("cached quotients") [6] improved the field-operation complexity to *O*(*m* log *m*) with smaller group-operation constants and proof size than Baloo, kept homomorphic table commitments, and—importantly for recursion—made *all verifier pairings use fixed, protocol-defined 𝔾₂ arguments*, enabling convenient aggregation of multiple proofs via random linear combination. The authors note that all of Caulk, Caulk+, Baloo, and flookup require the verifier to pair with prover-defined 𝔾₂ points, which obstructs that aggregation style [6].

| Caulk [2] | *O*(*N* log *N*) | *O*(*m* log *N* + *m*²) 𝔽 + *O*(*m*) 𝔾₁ | 4 pairings | 4𝔽, 14𝔾₁, 1𝔾₂ | Yes | No |

### 4.3 logUp: logarithmic derivatives and the GKR acceleration

Haböck's logUp [7] took an entirely different route to eliminating Plookup's sorting. The observation is elementary calculus transported to finite fields: logarithmic derivatives turn products of linear factors into sums of reciprocals. Starting from the multiset identity

*∏ᵢ (X − fᵢ) = ∏ⱼ (X − tⱼ)^(mⱼ),*

where *mⱼ* is the multiplicity of table entry *tⱼ* in the witness, taking the logarithmic derivative *d/dX log(·)* of both sides yields

*Σᵢ 1/(X − fᵢ) = Σⱼ mⱼ/(X − tⱼ).*

The exponentiation *(X − tⱼ)^(mⱼ)*, which forced Plookup into sorting gymnastics, becomes simple scalar multiplication *mⱼ* · 1/(*X* − *tⱼ*). No logarithms or derivatives are actually computed over the finite field—the identity is purely algebraic, and evaluating both rational functions at a random challenge *γ* gives Schwartz–Zippel soundness [7].

> **Theorem: logUp soundness.** Let *f* = (*f₁*, …, *fₙ*), **t** = (*t₁*, …, *t_d*), and **m** = (*m₁*, …, *m_d*) with *mⱼ* the claimed multiplicity of *tⱼ* in *f*. If Σᵢ 1/(*γ* − *fᵢ*) = Σⱼ *mⱼ*/(*γ* − *tⱼ*) for uniform random *γ* in 𝔽, then the multiset identity holds—i.e., every *fᵢ* is in **t**—except with probability at most (*n* + *d*)/|𝔽| [7].

The practical payoff is twofold. First, no sorted vector *s* and no sorting constraints: the prover commits only to the witness, the table, and the single multiplicity column **m**. Second, the additive structure shines in the *multivariate / batch-column* setting, where many columns are looked up against one table: while field-operation counts are comparable to the Plookup strategy used in HyperPlonk, the prover's oracle (commitment) costs are dramatically lower—Haböck's paper-and-pencil counts show logUp more than 3.9× faster for *M* = 20 columns of length 2¹²–2¹⁸ [7].

Papini and Haböck later improved the accumulation itself [8]: standard logUp verifies the fractional sum through intermediate accumulator columns, but the *LogUp-GKR* variant replaces them with a single multiplicities column and proves the accumulation *Σᵢ 1/(z − aᵢ) = Σⱼ mⱼ/(z − tⱼ)* with the GKR interactive protocol over a binary tree of fraction additions (numerators and denominators kept in projective form to avoid inversions), cutting commitment costs significantly [8].

### 4.4 The Halo2 subset argument and its industrial legacy

Halo2 deliberately avoided Plookup [9]. Its lookup argument is a *subset argument*: given table columns and input expressions, it enforces that every row of the input appears as some row of the table, using a permutation-style grand product with two independent challenges. The prover computes permuted columns *A′* (a permutation of the input column *A*) and *B′* (a permutation of the table column *B*) satisfying, in each row, either *A′ᵢ* = *A′ᵢ₊₁* or *A′ᵢ₊₁* = *B′ᵢ*—an adjacency condition reminiscent of Plookup but expressed without an explicit sorted merge. A single grand-product accumulator

*Zᵢ₊₁ = Zᵢ · ((A′ᵢ + β)(B′ᵢ + γ)) / ((Aᵢ + β)(Bᵢ + γ))*

with *Z₀* = 1 and terminal check *Z_last* = 1 combines the two multiset-equality sub-arguments (one for *A*, one for *B*) under the two challenges *β*, *γ* [9]. Multi-column lookups are handled by compressing each row's columns into one field element with a challenge *θ*: input *a* = Σ *θ*ᵏ *aₖ* and table *s* = Σ *θ*ᵏ *sₖ* [9]. The design supports fixed and advice (dynamic) tables and plugs directly into Halo2's multi-phase prover.

In production, lookups are where Halo2 circuits spend their proving budget. Memory profiling of the zkEVM circuits found the lookup prover's permuted-column commitment step consuming roughly 70% of total proving memory at large circuit sizes—a concrete illustration of why sublinear and log-derivative designs matter, and why Halo2-adjacent ecosystems have since experimented with logUp-style multivariate lookups and cq-style cached-quotient variants.

## 5 Empirical and Theoretical Evaluation

**Soundness landscape.** All surveyed protocols share one soundness skeleton: the honest prover's claims imply a formal polynomial or rational identity; a dishonest prover's claims yield a nonzero polynomial of degree *O*(*n* + *d*) (or *O*(*m* + log *N*) in the sublinear line), caught by random evaluation except with probability *O*((*n* + *d*)/|𝔽|). The differences lie in *which* identity and what the prover must precompute. Plookup's identity couples sorting and products; Caulk's couples subvector extraction with a small-table check; logUp's is a single additive identity; Halo2's is a two-challenge combined grand product [1][2][7][9].

**Prover-time evolution.** The trajectory is monotone and striking: from Plookup's *O*(*n* log *n*) with *n* ≥ *N*, through Caulk's *O*(*m*² + *m* log *N*) and Caulk+'s *O*(*m*²), to flookup/Baloo's *O*(*m* log² *m*) and cq's *O*(*m* log *m*) [6][10][11]. Concretely, Caulk proved batches of membership openings 100× faster than SNARKed Merkle proofs [2], and logUp's multivariate form beats the Plookup strategy by up to 3.9× in commitment-dominated regimes [7].

**Verifier and proof-size costs.** Succinctness is preserved throughout: verifiers perform 2–5 pairings and proofs stay at a handful of group elements (Table 1). The sublinear line pays for its prover gains with *preprocessing*: *O*(*N* log *N*) (or *O*(*N* log² *N*) for flookup) work and *O*(*N*) storage before any proof is made [2][10][6].

**Zero-knowledge and aggregation.** Plookup and logUp achieve zero-knowledge via standard blinding of auxiliary columns [1][7]; Caulk's position-hiding property gives zero-knowledge of *which* table positions were used [2]. For recursive composition, cq's fixed-𝔾₂ verifier pairings are the decisive advance, since random linear combination of proofs requires the verifier's pairing structure to be proof-independent [6].

## 6 Limitations

1. **Preprocessing burden.** Every sublinear-prover protocol requires *O*(*N* log *N*) preprocessing and *O*(*N*) storage keyed to a specific table. For tables that change frequently, or for one-off circuits, Plookup-style linear proving can be cheaper end-to-end [2][6].
2. **Non-homomorphic commitments.** flookup's fractional-decomposition commitment cannot be linearly combined across tables, forfeiting the vector-lookup batching that Baloo and cq provide [10][11].
3. **Pairing-hostile aggregation.** Caulk, Caulk+, Baloo, and flookup all require verifier pairings against prover-chosen 𝔾₂ points, complicating proof aggregation and recursion; only cq resolves this within the line [6].
4. **Multiplicity and dynamic tables.** logUp's elegance assumes the multiplicity column can be committed cheaply and that tables are static; Halo2's support for advice-column tables addresses dynamism but reintroduces prover costs linear in table size [7][9].
5. **Concrete prover memory.** Even with good asymptotics, the permuted or sorted auxiliary columns dominate memory in real deployments—around 70% of proving memory in large zkEVM circuits—so constant factors and memory layout remain first-order concerns.
6. **Soundness error terms.** The Schwartz–Zippel bounds degrade as (*n* + *d*)/|𝔽|; for small fields (e.g., 31-bit fields used in some STARKs) this forces larger extension fields or repetition, a cost the univariate KZG-based line largely avoids [7][8].

---

## 7 Conclusion

Lookup arguments evolved from Plookup's sorted-table grand product [1] along two complementary axes: *decoupling prover work from table size* (Caulk [2], Caulk+ [3], flookup [10], Baloo [11], cq [6]) and *eliminating sorting via logarithmic derivatives* (logUp [7], logUp-GKR [8]). In parallel, Halo2 charted an independent course with its two-challenge subset argument [9], now battle-tested in production zkEVM deployments. The mature picture is not a single winner but a design space: choose Plookup- or Halo2-style arguments for static, moderate tables with minimal preprocessing; the Caulk lineage when tables are huge and lookups are few; logUp when many columns share one table; and cq when proofs must aggregate. Open problems remain: pushing prover time to *O*(*m* log *m*) with *no* preprocessing, transparent (trustless-setup) sublinear lookups, and memory-efficient prover layouts for billion-row tables.
