# Formally Verified Smart Contracts: EVM Semantics, Symbolic Execution, and Certified Compilation for On-Chain Correctness

## Abstract

Smart contracts secure digital assets exceeding one hundred billion dollars in aggregate value, yet they execute in an adversarial, immutable environment where a single flaw is irrevocably exploitable. This thesis develops an end-to-end methodology for establishing on-chain correctness of Ethereum smart contracts. We formalize the Ethereum Virtual Machine as a small-step operational semantics with explicit gas accounting and cross-contract call structure; we characterize reentrancy, access-control failure, and arithmetic error as violations of precise safety properties; we show how symbolic execution with SMT solving enumerates feasible attack traces while deductive techniques discharge absence of entire bug classes; and we close the trust gap between source and bytecode via certified compilation grounded in mechanized simulation lemmas. Across the toolchain — KEVM [1], Dafny EVM [2], Oyente [3], Slither [4], Manticore [5], solc-verify [6], MAIAN [7], VeriSol [8] — we compare audit, testing, and proof, quantifying what each technique can and cannot guarantee.

---

## 1 Introduction

A smart contract is a program whose execution is *consensus*: every full node replays its bytecode against replicated state, and the result is binding and irreversible. There is no hotfix channel; the 2017 Parity library self-destruct froze hundreds of millions of dollars permanently, and the 2016 The DAO reentrancy exploit drained tens of millions through recursive calls that exploited the interaction between external calls and deferred state updates [3]. These failures share a structural feature: the vulnerability is a *semantic* mismatch between the programmer's mental model and the actual EVM semantics.

The EVM is a 256-bit-word stack machine with byte-addressable volatile memory, persistent word-addressed storage, and a resource model — *gas* — metering every opcode [1]. Formal verification here must solve three coupled problems. First, the platform semantics must be pinned down mathematically, because properties are meaningless without a definition of what a program *does*; the Yellow Paper's ambiguities were only exposed by mechanized semantics [1]. Second, analysis must handle path explosion across contract boundaries: any public function can be invoked in any order by any caller, and symbolic execution addresses this by treating inputs as logical variables and accumulating path conditions discharged by SMT solvers [3][5]. Third, source-level assurance must survive compilation — verified Solidity is worthless if the bytecode differs from the model — which is why certified compilation, with machine-checked proofs of semantics preservation, closes the loop [6].

We define a core EVM calculus with small-step semantics (§4.1); formalize symbolic execution with path conditions and SMT feasibility (§4.2); encode vulnerability patterns as negated safety properties (§4.3); develop certified compilation via forward simulation (§4.4); and present a Hoare-style contract logic (§4.5). Empirics ground the theory (§5); limits close the work (§6).

## 2 Background

**The EVM execution model.** A *world state* σ maps addresses to accounts holding nonce, balance, code, and persistent storage. A machine state is ⟨pc, stack, mem, σ, gas, calldata, depth⟩: a 1024-deep word stack, linear byte memory charged quadratically on expansion, gas consumed per opcode [1][2]. Transactions are the reflexive-transitive closure of small steps until halt, exceptional halt, or a nested call.

**Calls and reentry.** The `CALL` family transfers control to another account's code with value and a gas stipend, pushing a new frame — and the callee may call back into the caller before its frame completes: *reentrancy*. The EVM imposes no reentry discipline; the 63/64 gas-forwarding rule only bounds recursion indirectly. Sound verification must therefore model the caller as an *adversarial environment*: unknown code at an arbitrary address can reenter any public entry point [3].

**The assurance ladder.** Conventional assurance ascends in rigor: manual audit (expert, informal), static analysis (Slither's SlithIR detectors run pattern rules over SSA IR [4]), symbolic execution (Oyente and Manticore enumerate feasible paths, querying SMT solvers for violations [3][5]), and deductive verification (reachability-logic proofs over KEVM [1], Boogie-based modular verification in solc-verify [6] and VeriSol [8], machine-checked semantics in Dafny [2]). Each rung trades soundness against automation: pattern detectors are fast but incomplete; symbolic execution is sound only for bounded depths; deductive verification is complete relative to the specification but demands human proof effort.

**Symbolic execution.** A *symbolic state* replaces concrete inputs with symbols; each symbolic branch splits the state, conjoining the guard to the *path condition* π. Feasibility is SMT satisfiability over bitvectors, arrays, and uninterpreted functions; a violation φ is reachable iff π ∧ φ is satisfiable, and the solver's model yields a concrete attack trace [5]. Oyente pioneered EVM symbolic execution, flagging 8,833 of 19,336 contracts on the first 1.46 million blocks [3].

**Hoare-style contract logics.** Contracts are open systems, so modular reasoning needs boundary specifications: {P} f {Q} means every terminating execution of f from P ends in Q [6]. Loop and contract-level invariants reduce global reasoning to local verification conditions discharged by SMT [6][8].

## 3 Methodology

Our methodology is *semantics-first*: define the machine precisely, state properties as logical formulas over its traces, then choose the analysis whose soundness theorem matches the required guarantee.

**Step 1 — Mechanized operational semantics.** We formalize the EVM core as a deterministic labeled transition system in the KEVM style [1]: each opcode is a rewrite rule over machine states, gas is an explicit premise, exceptional halts are distinguished outcomes. Determinism is proved by opcode case analysis, ruling out the "specification gap" where analyzers disagree with clients.

**Step 2 — Property specification.** Vulnerability classes become negated trace properties: reentrancy forbids a second entry before the first entry's state effects commit across an external call; access control requires `msg.sender` in an authorized set at every state-modifying entry; arithmetic requires each 256-bit result to equal its mathematical value or carry an explicit check [6].

**Step 3 — Symbolic exploration with SMT.** Symbolic execution over the semantics: branch conditions become path constraints; at each `CALL` the callee is modeled as a nondeterministic environment capable of arbitrary gas-bounded reentry; solver queries decide feasibility and violation [3][5]. Unsatisfiable paths are pruned; satisfiable violations yield concrete counterexamples.

**Step 4 — Deductive closure.** Where symbolic execution is bounded, reachability-logic proofs [1] or Boogie VCs [6][8] close the gap: validity of all VCs implies the property for *all* executions.

**Step 5 — Certified compilation.** We prove forward simulation: every bytecode behavior is permitted by the source semantics, so source proofs transfer to deployed artifacts; the mechanized proof emits proof objects alongside bytecode [6].

**Evaluation.** Three axes: *fidelity* (does the semantics pass the 40,683-test Ethereum conformance suite [1]?), *recall on known bugs* (The DAO pattern, BEC overflow, frozen-library patterns [3][7]?), and *proof coverage* (functional correctness of ERC-20 end-to-end [1]?).

## 4 Deep Dive

### 4.1 Operational Semantics of the EVM: A Small-Step Machine

We define a core calculus, λ-EVM, capturing the safety-relevant fragment: stack, memory, storage, control flow, and the call family. A machine state is:

```haskell
data Machine = Machine
  { pc      :: Int                  -- program counter
  , stack   :: [Word256]            -- operand stack, depth <= 1024
  , mem     :: Mem                  -- byte array, word-aligned expansion
  , stor    :: Map Word256 Word256  -- persistent account storage
  , gas     :: Integer              -- remaining gas
  , world   :: WorldState            -- global account map
  , frames  :: [Frame]              -- call stack
  }
```

Single-step transitions are inference rules. The arithmetic rule shows gas accounting and modular semantics together:

```tla+
\* TLA+ sketch of the ADD transition
ADD(mu, sigma) ==
  /\ Len(mu.stack) >= 2
  /\ mu.gas >= G_verylow
  /\ LET x == Head(mu.stack)
         y == Head(Tail(mu.stack))
     IN  /\ mu' = [mu EXCEPT !.stack = <<(x + y) % 2^256>> \o Tail(Tail(mu.stack)),
                          !.pc = mu.pc + 1,
                          !.gas = mu.gas - G_verylow]
         /\ UNCHANGED sigma
```

The call rule is where verification gets hard: `CALL` invokes *arbitrary bytes* from the world state. KEVM handles this via reachability-logic abstraction over a code-map-parametric semantics [1]; the Dafny formalization machine-checks the same case analysis functionally [2]. Both exposed Yellow Paper ambiguities, including the exact forwarded gas stipend and `RETURNDATACOPY` on empty return data [1].

Gas is itself a verification target: the semantics yields a deterministic *gas function* over traces, and proving upper bounds is essential for liveness. The 63/64th rule makes recursion depth a function of initial gas, which symbolic executors exploit to bound reentry depth [3][5].

### 4.2 Symbolic Execution: Path Conditions and SMT Solving

Symbolic execution lifts the concrete relation to symbolic states ⟨μ̂, σ̂, π⟩ — values as terms over symbolic variables, π the path condition. The symbolic `JUMPI` forks:

```python
def sym_jumpi(state, dest, cond):
    """Fork on a symbolic branch; query SMT for feasibility."""
    for branch, guard in [(dest, cond), (state.pc + 1, Not(cond))]:
        pi = And(state.pi, guard)
        if solver.is_sat(pi):                      # bitvector + array theories
            yield state._replace(pc=branch, pi=pi)
        # else: infeasible path pruned — sound by solver soundness
```

Three engineering decisions dominate EVM symbolic execution [3][5]:

1. **Memory and storage as SMT arrays.** The array theory models `MLOAD`/`SSTORE` precisely, but the 256-bit index space forces concretization of almost-concrete addresses, keeping symbolic only attacker-dependent ones.
2. **Hashing as uninterpreted functions.** `KECCAK256` is solver-opaque, so `keccak256(key . slot)` becomes an uninterpreted *f* with *x ≠ y → f(x) ≠ f(y)* — sound absent collisions [5].
3. **Environment as adversary.** `CALL` to an unknown address havocs reachable state and assumes arbitrary return data; Manticore adds state merging and concretization policies against fork explosion [5].

Path explosion is the fundamental barrier: *n* symbolic branches yield up to 2ⁿ paths, and each 256-bit bitvector query is NP-complete in the worst case. Small programs and gas-bounded loops keep this tractable — Oyente completed thousands of contracts — but symbolically-bounded loops remain the incompleteness frontier, addressed by invariant-based deduction (§4.5) [3][6].

### 4.3 Reentrancy and Access Control as Safety Properties

Vulnerability taxonomies — Oyente's four classes [3], Slither's 80+ detectors [4], MAIAN's greedy/prodigal/suicidal trichotomy [7] — are best understood as *patterns*, syntactic witnesses of semantic property violations. We formalize the two most consequential.

**Reentrancy.** The canonical vulnerable pattern:

```rust
// VULNERABLE (Solidity sketched in Rust-like pseudocode)
fn withdraw(&mut self, amount: U256) {
    require(self.balances[msg_sender] >= amount);
    msg_sender.call{value: amount}("");      // (A) external call FIRST
    self.balances[msg_sender] -= amount;    // (B) state update AFTER
}
```

The attacker's fallback reenters at (A); the balance check still passes since (B) has not executed; recursion drains the contract. The fix — *checks-effects-interactions* — moves (B) before (A); a reentrancy guard makes reentry revert.

> **Definition (Reentrancy safety).** A contract is reentrancy-safe iff in every trace, for every external call *c* in function *f*, no segment *c … reentry(f) … return(c)* contains a storage write that precedes in program order a write to the same slot ordered after *c* in *f*.

Symbolic executors detect the violation via the query of §4.2 [3][5]; Slither detects the *pattern* (state write after external call) syntactically with taint tracking [4]. The semantic property is strictly stronger: it admits safe patterns that syntactic detectors flag as false positives — the audit-vs-proof gap in miniature.

**Access control.**

| Vulnerability class | Formal property | Detection technique | Canonical tool |
|---|---|---|---|
| Reentrancy | No reentrant write-before-commit | Symbolic path query | Oyente [3], Manticore [5] |
| Unprotected privileged ops | `msg.sender ∈ Owners` at every privileged entry | Taint + pattern | Slither [4], MAIAN [7] |
| Integer overflow | Math result = modular result ∨ explicit check | SMT bitvector query | solc-verify [6] |
| Greedy / prodigal | ∃ trace locking funds / leaking to arbitrary caller | Inter-procedural symbolic search | MAIAN [7] |
| Tx-order dependence | Outcome independent of interleaving | Path-condition comparison | Oyente [3] |

MAIAN instead *searches for exploit primitives* — contracts that can be forced to lock ether forever, leak it to an arbitrary address, or be killed by anyone — finding thousands at scale [7].

### 4.4 Certified Compilation: Verified Solidity/Yul Pipelines

Source-level assurance is void if compilation is untrusted. A *certified compiler* is a pair (compile, proof) with:

> **Theorem 2 (Forward simulation / semantics preservation).** For every source program *S* and *T = compile(S)*, every terminating execution of *T* from σ₀ corresponds to an execution of *S* from σ₀ with identical observable behavior (return data, storage effects, balance transfers, logs).

The proof uses *simulation diagrams*: a relation R between source and target states preserved as each target step is matched by source steps, concluding by coinduction over traces. The solc-verify pipeline implements the practical half: annotated Solidity → Boogie IVL, the Boogie verifier discharges VCs with SMT solvers, and results map back to source lines [6]. Its modular-arithmetic mode is instructive — mathematical integers *with* range assertions capturing exact 256-bit wraparound, giving solver scalability plus bit-precise overflow detection and discharging all SimpleBank VCs in seconds [6].

The full stack is layered: **source → Yul** (the translation must preserve checked- vs. wrapping-arithmetic semantics, a notorious analyzer unsoundness when the wrong mode is assumed); **IR → IR optimizations** (peephole rules proved as denotational equalities in the Dafny EVM semantics [2]); **IR → bytecode** (the simulation relation must account for gas exactly, since out-of-gas is observable). The economic argument is decisive: a compiler bug is *systemic*, affecting every contract it compiles — certified compilation amortizes proof effort across all compilations.

### 4.5 Hoare-Style Contract Logics and Modular Verification

Symbolic execution reasons about *traces*; Hoare logic reasons about *programs*:

```haskell
-- Hoare triple for a token transfer
-- { balanceOf[from] >= amt /\ to /= 0 }
--   transfer(from, to, amt)
-- { balanceOf[from] = old(balanceOf[from]) - amt
--   /\ balanceOf[to] = old(balanceOf[to]) + amt
--   /\ sum(balanceOf) = old(sum(balanceOf)) }
```

> **Theorem 3 (Soundness of the contract logic).** If every function of contract *C* satisfies its {P} f {Q} against the λ-EVM semantics, every loop carries a valid invariant, and every contract-level invariant *I* is established by the constructor and preserved by each public function, then *I* holds in every reachable state of *C* under arbitrary adversarial callers.

*Proof sketch.* Induction on traces: the constructor establishes the base; the inductive step applies the frame rule — reentry can only invoke public functions, each preserving *I* by its verified triple; adversary code never executes in the contract's frame. ∎

This is the architecture of VeriSol and solc-verify [6][8]: Solidity → Boogie; annotations become VCs; Z3/CVC4 discharge them; failures map back to source. VeriSol adds *semantic conformance* — the contract must refine a finite-state workflow policy — and *infers* invariants via predicate abstraction [8]. Where symbolic execution finds bugs, this logic proves their absence: solc-verify's evaluation shows each catches what the other misses [6].

## 5 Empirical Results and Proofs

**Semantics fidelity.** KEVM passes all 40,683 tests of the official Ethereum VM conformance suite — the first formal semantics to do so — and its reachability-logic verifier, derived correct-by-construction from the same semantics, has verified ERC-20 transfers, the Ethereum 2.0 deposit contract, and MakerDAO components [1]. The Dafny formalization provides a complementary human-readable, machine-checked interpreter with proved gas-reasoning invariants and a methodology for synthesizing verified bytecode from verified Dafny code [2].

**Bug-finding recall.** The empirical record is unambiguous [3][4][5][7]:

| Tool | Technique | Scale | Key result |
|---|---|---|---|
| Oyente [3] | Symbolic execution on bytecode | 19,336 contracts | 8,833 flagged; The DAO pattern detected |
| MAIAN [7] | Inter-procedural exploit search | 970k+ contracts | Thousands greedy/prodigal/suicidal |
| Manticore [5] | Dynamic symbolic execution | Commercial audit corpus | Bugs found + correctness proofs in production |
| Slither [4] | SlithIR static analysis | 1,000 top contracts, manual review | Best speed/false-positive balance |
| solc-verify [6] | Boogie VCs + SMT | Annotated benchmarks | All VCs discharged in seconds |
| VeriSol [8] | Boogie + predicate abstraction | Azure Blockchain samples | Unknown conformance bugs found |

Two results deserve emphasis: solc-verify's SimpleBank experiment shows only VC-based reasoning discharges reentrancy *and* overflow with zero false alarms [6], and MAIAN's solver found killable-by-anyone contracts absent from 2016-era taxonomies [7].

**Proofs of absence.** Reachability-logic verification over KEVM proves functional correctness — not just bug absence — of token contracts against full specifications including gas bounds [1]. VeriSol's conformance proofs guarantee implementation traces refine workflow policies for *all* interleavings of public calls, which no bounded symbolic executor can establish [8] — genuine *proofs*, composable with the simulation theorem of §4.4.

**The layered stack.** Manual audit remains unmatched at *specification discovery* — auditors find missing requirements no formal property states. The mature stack is therefore layered: Slither-class analyzers in CI [4], symbolic executors for pre-deployment exploit search [3][5][7], deductive verification for invariants that must hold forever [1][6][8] — with the compiler verified so the layers agree on what the code *means*.

## 6 Limitations

**Decidability and the solver ceiling.** Symbolic execution reduces security to SMT satisfiability, but 256-bit bitvector formulas with arrays and uninterpreted functions sit at the edge of solver capacity. Path explosion is exponential; symbolically-bounded loops force unsound bounding or expensive invariant inference. Every symbolic tool is *bounded-complete at best*: no counterexample within the bound is not absence of a bug [3][5].

**The specification bottleneck.** Deductive verification proves exactly what is specified — written by humans, at a cost comparable to the code. The DAO's flaw was arguably a *missing requirement* (no reentrant withdrawal), not a failed proof; no verifier discovers requirements. Invariant inference (VeriSol's predicate abstraction [8]) mitigates but does not eliminate this.

**Semantic drift.** The EVM is a moving target: gas schedules change at hard forks (EIP-150, EIP-1884, EIP-2929 repriced opcodes), and analyzers parameterized by stale schedules are unsound against the live network. KEVM makes the semantics parametric in the fee schedule [1], but downstream tools must track the parameterization or silently diverge.

**Environment modeling.** Reentry analysis assumes an *arbitrary* adversary, but gas stipends, the 63/64 rule, and callee whitelists constrain it. Over-approximation yields false positives; under-approximation misses exploits via trusted-but-compromised callees. The `delegatecall` proxy pattern — the "callee" executing in the *caller's* storage context — defeats most modular analyses and remains the sharpest open problem.

**Certified compilation coverage.** Today's verified pipelines cover subsets: solc-verify handles most of Solidity but not inline assembly or ABI-encoding edge cases [6]; Dafny-to-EVM synthesis is a research methodology, not a production compiler [2]. Until solc itself carries proof objects, the trust gap is narrowed, not closed.

**Economic properties are out of scope.** Formal methods verify *code* properties. Oracle manipulation, governance attacks, and MEV extraction are *mechanism* properties; a provably correct lending contract can still be drained through a price-feed exploit. Verification is necessary but not sufficient for on-chain safety.

---

## 7 Conclusion

On-chain correctness is achievable — not by any single technique, but by a semantics-grounded stack in which each layer's guarantee is stated as a theorem. Mechanized EVM semantics [1][2] fix the meaning of execution; symbolic execution with SMT solving [3][5][7] hunts feasible attacks and produces replayable counterexamples; static analysis [4] gives fast approximate feedback; Hoare-style modular logics [6][8] prove invariants for all executions and all adversaries; certified compilation carries those proofs to the bytecode that executes.

The central lesson is the *audit-vs-proof* distinction: audits discover requirements; proofs establish, with machine-checked certainty, that stated requirements hold of the deployed artifact. The DAO hack, the Parity freeze, and MAIAN's greedy contracts were failures of *guarantee* — properties believed but never proved. Assurance must move up the ladder: from testing what we can think of, to proving what we must guarantee, over a semantics we can trust.
