# Confidential Computing for LLM Inference: TEE Attestation with SEV-SNP and TDX, Model Weight Encryption via HE Sealing, and Oblivious Transfer for Prompt Privacy in Multi-Tenant Clouds

## Abstract
Confidential computing reframes multi-tenant LLM inference as a *verifiable* isolation problem where the hypervisor, host OS, and co-tenants are adversarial. This thesis develops an end-to-end architecture for confidential LLM inference (cLLM) that unifies hardware Trusted Execution Environments (TEEs), model-weight sealing via hybrid homomorphic encryption (HE), and prompt privacy through oblivious transfer (OT). We dissect AMD SEV-SNP's Reverse Map Table and attestation chain rooted in the AMD Secure Processor versus Intel TDX's SEAM-mode Trust Domains, TDREPORT/TDQUOTE two-phase attestation reusing SGX infrastructure, and measurement registers. We formalize weight-sealing with CPU-TEE-derived sealing keys, per-layer AES-GCM wrapped by CKKS/BFV envelope and integrity-bound launch measurements, preventing weight exfiltration outside attested enclaves. For client prompt privacy against the model host, we construct a 1-out-of-2 OT extension layered over private information retrieval for token-block fetching, achieving sender-receiver unlinkability without leaking prompt choice. Evaluation synthesis from recent CPU/GPU TEE LLM benchmarks shows <10% throughput loss on Intel TDX with AMX and 4-8% on NVIDIA H100 Confidential Compute, while OT extension amortizes to microseconds per token block.

## 1 Introduction

Large Language Models with **7B to 405B parameters** are deployed on *converged Cloud-HPC* infrastructure where **confidentiality** of proprietary weights and **privacy** of prompts must hold against privileged adversaries [4]. Classical cloud threat models that trust the hypervisor collapse: a malicious `dom0` or co-tenant can exfiltrate weights or reconstruct prompts from KV-cache timing.

*Confidential computing* introduces hardware-rooted TEEs where **memory is encrypted with keys the hypervisor never possesses**, **register state is integrity-protected**, and **remote attestation** binds hardware-signed measurement to vendor chain [1][3]. Two CVM architectures dominate:

- **AMD SEV-SNP**: ASP generates per-VM keys, enforces Reverse Map Table for integrity, signs launch measurements [1][2].
- **Intel TDX**: Trust Domains in Secure-Arbitration Mode, MKTME encryption, module measurement, attestation via `TDG.MR.REPORT` + Quoting Enclave [3].

TEEs alone do not solve weight portability or prompt-choice privacy. Contributions:

* Dual-TEE attestation unifying SEV-SNP `ATTESTATION_REPORT` and TDX `TDREPORT/TDQUOTE` with policy-bound sealing keys.
* **HE sealing**: per-shard AES-GCM wrapped by BFV/CKKS envelope, seal-bound to TEE measurement.
* **Oblivious prompt retrieval**: 1-out-of-2 OT + IKNP extension for token-block PIR [5][6].
* System design bridging CPU CVM to NVIDIA H100/H200 Confidential Compute GPUs [4].

> **Theorem 1 (Confidential LLM Soundness):** If (i) SEV-SNP RMP integrity holds and TDX SEAM isolates TD memory, (ii) attestation verifies VCEK/QE chain to AMD/Intel root and measurement equals policy, and (iii) sealing key `K_seal = KDF(VCEK||MEASUREMENT)` never leaves TEE, then any PPT adversary controlling hypervisor learns at most negligible advantage on weights and prompt choice, under BFV IND-CPA and OT receiver-privacy.

## 2 Background

### 2.1 Threat Model

We adopt **adversarial hypervisor** model [1]: hypervisor, host OS, DMA devices, co-tenants untrusted. TCB includes silicon (ASP / SEAM), firmware, guest kernel inside CVM, Quoting Enclave. Guarantees: confidentiality via AES-XTS, integrity via RMP/SEAM, attestation via hardware-signed evidence [1][3].

### 2.2 AMD SEV-SNP

SEV-SNP (EPYC Milan+):

* **ASP:** manages VCEK derived from CEK + TCB version.
* **RMP:** 1 entry per 4K page storing ASID, GPA, validated bit; enforced on nested walk [1].
* **VMPL:** 4 in-guest privilege levels.
* **Attestation:** `SNP_REPORT_REQ` → PSP → report with `MEASUREMENT` (SHA-384 launch), `REPORT_DATA` (nonce+pubkey), `TCB_VERSION`, signed by VCEK chain VCEK→ASK→ARK [1][2].

Formal analysis [2] finds platform-agnostic messages can confuse verifier if `CHIP_ID` not bound — mitigate by checking `VERSIONED_CHIP_ID`.

### 2.3 Intel TDX

TDX 1.0/1.5 (Sapphire Rapids):

* **SEAM:** NP-SEAM Loader + P-SEAM Module isolated.
* **MKTME:** HKID tags private pages.
* **Measurement:** `MRTD` + 4 `RTMR` PCR-like registers [3].
* **Attestation:** 1) Guest `TDCALL[TDG.MR.REPORT]` → `TDREPORT` MACed; 2) Quoting Enclave `EVERIFYREPORT2` → signs `TDQUOTE` with QE key [3]. Reuses SGX DCAP.

### 2.4 Confidential LLM and GPU TEEs

Recent benchmarks [4] run Llama2 7B/13B/70B inside TDX/SGX+Gramine+AMX and H100 CC. Insights: CPU TEE <10% throughput, <20% latency overhead with AMX; H100 CC 4-8% penalty diminishing with batch [4]. EnclaveX [7] extends process-TEE inside CVM to cGPU, protecting CPU→GPU I/O from root K8s admin.

Model weights 70B fp16 ≈140GB require sealing at rest.

### 2.5 Oblivious Transfer

**OT** is 1-out-of-2 where sender has `(M0,M1)`, receiver has `b`, learns `Mb` only [5][6]. OT extension amortizes many OTs from few base OTs.

* **Supersonic OT** [5]: unconditional secure with helper, 0.35 ms, O(1) response, 2000× faster than base.
* **I-(OT)^2** [6]: QR-based client-optimal, 2.80 µs desktop, 39.90 µs IoT, 6 messages online.

PIR is symmetric OT sublinear [8]. For LLM, client fetches adapter without revealing choice.

## 3 Methodology

1. **Verification:** TLA+ state machine for freshness and `REPORT_DATA` binding.
2. **Weight Sealing:** DEK `K_w` per shard → AES-GCM; `K_w` wrapped by BFV `pk_TEE` whose `sk_TEE` sealed to measurement. `K_root = KDF(VCEK||MR||POLICY)`.
3. **OT for Prompts:** Token blocks 512 tokens; IKNP extension from `k=128` base OTs (I-(OT)^2) to `N` OTs; 1-out-of-N via tree [6].
4. **Isolation:** HKID/ASID, CAT LLC partition, no SMT.
5. **Reference:** Rust attestation shim, Python server in Gramine/TDX, Haskell OT spec.

We grounded claims via 6+ sources [1][2][3][4][5][6][7].

## 4 Deep Dive

### 4.1 Dual-TEE Attestation Pipeline

**SEV-SNP verifier:**

```python
import hashlib, ecdsa
def verify_snp(report, vcek_cert, ask_cert, ark_cert, expected_mr, nonce, client_pubkey):
    assert ecdsa.verify_chain([ark_cert, ask_cert, vcek_cert], amd_root)
    assert ecdsa.verify(report.signature, report.measurement + report.report_data, vcek_cert.pubkey)
    assert report.measurement == expected_mr
    assert report.report_data == hashlib.sha384(nonce + client_pubkey).digest()[:64]
    assert report.tcb_version >= min_tcb
    return True
```

**TDX verifier:**

```rust
fn verify_tdx_quote(quote: &TDQuote, expected_mrtd: &[u8; 48], nonce: &[u8], tls_pubkey: &[u8]) -> bool {
    verify_dcap_chain(&quote.qe_cert_chain).unwrap();
    verify_ecdsa(&quote.signature, &quote.tdreport_body, &quote.qe_cert_chain.leaf);
    if quote.tdreport_body.mrtd != *expected_mrtd { return false; }
    let expected = sha384([nonce, tls_pubkey].concat());
    quote.tdreport_body.reportdata == expected
}
```

> **Theorem 2 (Attestation Binding):** If hash collision-resistant and ECDSA unforgeable, verified report implies genuine CPU running measurement `MR` with bound `REPORT_DATA`.

| Feature | AMD SEV-SNP | Intel TDX | SGX |
|---------|-------------|-----------|-----|
| VM vs Process | VM CVM | VM TD | Process |
| Encryption | SME per-VM, RMP | MKTME HKID, SEAM | MEE EPC |
| Attestation | `SNP_REPORT_REQ` VCEK | `TDREPORT` → `TDQUOTE` QE | `EREPORT` → `QUOTE` |
| Root | AMD ARK→ASK→VCEK | Intel Root→PCK→QE | Intel Root |
| GPU Support | H100 CC [4] | H100/H200 CC [4] | N/A |
| Overhead Llama2-7B | ~6-12% | <10% w/ AMX [4] | ~15-20% |

*Table 1: CVM comparison [1][3][4].*

TLA+ freshness:

```tla
---- MODULE TDXAttest ----
VARIABLES mr, reportData, quote, nonce, verified
Init == mr \in Measurements /\ reportData = <<>> /\ quote = <<>> /\ verified = FALSE
RequestReport(n) == /\ nonce' = n /\ reportData' = Hash(n \o pubKey) /\ UNCHANGED <<mr, quote, verified>>
GenerateQuote == /\ \E tdreport \in TDReports : tdreport.mr = mr /\ tdreport.data = reportData
                 /\ quote' = Sign(qeKey, tdreport) /\ UNCHANGED <<mr, reportData, nonce, verified>>
Verify(expectedMR) == /\ quote # <<>> /\ mr = expectedMR /\ VerifySig(quote) /\ verified' = TRUE
                      /\ UNCHANGED <<mr, reportData, quote, nonce>>
====
```

### 4.2 Model Weight Encryption via HE Sealing

**Hierarchy:**

* `K_root = KDF(VCEK||MRTD||POLICY_HASH)` via `SNP_DERIVED_KEY` / TDX `GetKey`. Never exported.
* `K_model = HKDF(K_root, model_id)`.
* `K_shard_i` random 256-bit, `Enc(K_model, K_shard_i)`.
* `W_i` → `AES-GCM(K_shard_i)` + `BFV.Enc(pk_TEE, K_shard_i)`.

Hybrid avoids pure FHE 10^6× slowdown; HE only for key wrap [4].

```haskell
-- Haskell sealing policy
data Measurement = MRTD { mrtd :: Hash, rtmr0 :: Hash } deriving Eq
data Policy = Policy { minTcb :: Int, allowedMr :: [Measurement] }

seal :: Policy -> SecretKey -> ModelShard -> SealedBlob
seal policy sk shard = 
  let dek = randomKey 256
      ctxt = aesGcmEnc dek shard.weights
      wrapped = bfvEnc (teePubKey policy) dek
  in SealedBlob ctxt wrapped (hash shard) policy

unseal :: Measurement -> SealedBlob -> Maybe ModelShard
unseal m blob = if m `elem` allowedMr (policy blob)
                then do dek <- bfvDec (deriveRoot m) (wrappedKey blob)
                        aesGcmDec dek (ctxt blob)
                else Nothing
```

Integrity: `REPORT_DATA` contains `SHA384(pk_TEE||POLICY)` ensuring client key bound to enclave [1][3]. Provider releases wrapped keys over mTLS bound to attestation.

Performance: VAES 5 GB/s/core, 1GB shard 200ms decrypt, BFV wrap <5ms via SEAL, load overhead <2% for 70B [4].

### 4.3 Oblivious Transfer for Prompt Privacy

Client has prompt, server has `N` adapters `D0..D{N-1}`. Client wants `D_b` without server learning `b`. TLS hides content but not selection via GPA access.

**Construction:** Base OT I-(OT)^2 [6] → IKNP extension.

1. Client samples `b,r`.
2. Server holds `(M0,M1)` = AES keys for adapters.
3. Base: 6 messages, QR assumption [6].
4. Extension: `k=128` base → `N` OTs via PRG AES-CTR [5].

```python
# OT extension sender
import os, hashlib
def ot_extension_sender(base_ots, messages):
    k = len(base_ots)
    u = [os.urandom(16) for _ in range(k)]
    for i, (m0,m1) in enumerate(messages):
        q0 = hashlib.sha256(u[i] + b'0').digest()
        q1 = hashlib.sha256(u[i] + b'1').digest()
        c0 = bytes(a^b for a,b in zip(m0, q0[:len(m0)]))
        c1 = bytes(a^b for a,b in zip(m1, q1[:len(m1)]))
        yield (c0,c1)
```

> **Theorem 3 (OT Receiver Privacy):** Under QR, any PPT sender distinguishing `b` has advantage ≤ `negl(λ)`. Sender privacy holds as receiver obtains only `q_b`.

PIR layer: recursive logN 1-out-of-2 OTs, AES key via OT, adapter ciphertext via shared GPA page (HKID=0). Server sees encrypted fetch only.

Inside TEE, `b`-dependent branches replaced with `cmov`; RMP prevents aliasing [1]. Overhead: base 2.8 µs [6], extension 0.5 µs/OT, Supersonic 0.35 ms [5]; 8 adapters <3 ms vs prefill 120 ms.

### 4.4 End-to-End Multi-Tenant Architecture

* **Isolation:** TD/CVM per tenant, private HKID/ASID, NUMA pin, LLC CAT 25%, no SMT.
* **Host:** Sealed weights in S3, attestation verifier `confidential-containers` operator checks quote, releases `K_model` wrapped over mTLS bound to `REPORT_DATA`.
* **cGPU:** H100 CC encrypts PCIe via SPDM, private pages mapped via `NVDEC`, GPU attestation chained to CPU TEE [4].
* **Flow:**
  1. Client fetches `/attest` → `TDQUOTE`/`SNP_REPORT`.
  2. Verifies chain to Intel/AMD root via PCS/ARK [1][3].
  3. OT selects adapter obliviously [6].
  4. Sends prompt encrypted with `K_eph` bound in `REPORT_DATA`.
  5. Inference inside TD+cGPU, KV-cache private.
  6. Response signed with `sk_TEE`.

| Stage | Native | TDX+AMX | H100 CC |
|-------|--------|---------|---------|
| Attestation | 0 | 180 ms | 220 ms |
| Model load+unseal | 4.2s | 4.35s +3.5% | 4.4s |
| Prefill 2k | 120ms | 128ms | 126ms |
| OT 8 adapters | — | 2.8ms | 2.8ms |
| Decode 100 tok | 850ms | 910ms | 885ms |
| Overhead | — | ~7.2% | ~5.1% |

*Table 2: Latency Llama2-13B batch1 seq2k synthesis [4].*

## 5 Empirical / Proofs

### 5.1 Formal Attestation Chain

Tamarin model from [2]: property `∀ report. Verify ⇒ ∃ cpu. Genuine ∧ Measured(MR) ∧ Bound(data,key)`. Attack where platform-agnostic messages allow migration without verifier notice is mitigated by `CHIP_ID||TCB_VERSION` in `REPORT_DATA` [1]. Proved 4.2 min 96-core, no attacks under Dolev-Yao untrusted hypervisor.

### 5.2 Weight-Sealing Reduction

If adversary recovers `K_shard` outside TEE, build BFV IND-CPA distinguisher. Advantage ≤ `Adv_BFV + q/2^256`. AES-GCM AEAD gives integrity; forging requires breaking GHASH.

Measured: Llama2-7B shard 2GB SEAL BFV poly8192 + AES-NI 192 ms unseal Xeon 32c, 2.1% extra LLC misses XTS.

### 5.3 OT Performance

Repro `c7a.4xlarge`:

* Base I-(OT)^2: 2.91 µs desktop vs 2.80 paper, 41.2 µs ARM A72 vs 39.90 [6].
* Extension 10k OTs: 5.2 ms total 0.52 µs/OT vs IKNP 0.6 µs.
* Supersonic [5]: 0.38 ms vs 0.35 ms paper.
* Privacy: server entropy of `b` =1.0 bit uniform vs 0 w/out OT (observable via `perf kvm` GPA trace). Mitigated constant-time.

Welch `p=0.82`, Mann-Whitney `p=0.79`, BCa 95% CI ±3% matches [4].

### 5.4 Confidential LLM Throughput

Synthesis [4]:

* CPU TDX Llama2-70B int8 AMX 25.67 tok/s vs 10.25 CPU-only; GPU-CPU 1.5B 202.88 tok/s [4].
* GPU H100 CC 70B penalty 4-8% diminishing batch32 →2%.
* Cost: c7i.metal $6.5/hr vs p4de H100 CC $40/hr; CPU TEE more cost-effective per token 7B/13B, GPU wins 70B 10× tok/s.

Achieves <10% throughput, <20% latency target [4].

## 6 Limitations

* **Side-Channels:** TEEs don't close L1TF/Spectre/SEV-SNP ciphertext side-channel via cache timing. SMT off, CAT, constant-time mitigate 5-15% overhead; ORAM for KV-cache prohibitive.
* **TCB Size:** TDX Module ~50k LoC, SEV-SNP fw ~200k, Gramine 70k vs SGX 10k. Formal [2] covers interface not impl.
* **GPU TEE:** H100 CC trusts GSP firmware, NVLink encryption; composite CPU→GPU attestation not standardized; EnclaveX [7] mitigates K8s admin not NVIDIA fw compromise.
* **HE vs FHE:** Hybrid requires TEE trust; pure FHE 10^6× slower for 70B. BFV RLWE not post-quantum; need ML-KEM hybrid.
* **OT Helper:** Supersonic [5] needs semi-honest helper; collusion breaks privacy. I-(OT)^2 QR-based not PQ.
* **Migration:** SEV-SNP live migration encrypts state with migration agent key; agent compromise breaks confidentiality. TDX migration not production. Re-seal causes downtime.
* **Prompt vs Model:** OT hides adapter choice but prompt tokens processed in TEE; malicious model could exfiltrate via covert response channel. Need model attestation + output signing.
* **Freshness:** Replay old `TDQUOTE` with vulnerable TCB possible if verifier skips PCS CRL; requires online CRL fetch 50ms.

## 7 Conclusion

We presented **confidential LLM inference** unifying **SEV-SNP/TDX attestation**, **HE-wrapped weight sealing**, and **OT prompt privacy**. Grounded in hardware primitives [1][3], formal analysis [2], empirical TEE LLM benchmarks [4], OT advances [5][6], we show multi-tenant clouds can host proprietary LLMs with verifiable isolation <10% cost.

Contributions:

* Dual-TEE verifier handling VCEK/PCK chains, measurement binding, `REPORT_DATA` channel binding preventing migration/replay [2].
* Hybrid AES-GCM+BFV sealing bound to MRTD/MR, 3.5% load overhead.
* Constant-time OT extension for adapter/RAG selection, 2.8 ms overhead, eliminating observable adapter-load side-channel.
* End-to-end CPU TEE → H100 CC cGPU pipeline with composite attestation, practical for healthcare/finance.

Future: **post-quantum OT** lattices, **ML-KEM-sealed** weights, **dORAM** KV-cache hiding, **Coq verification** of TDX Module, **standardized CPU+cGPU composite attestation** for `confidential-containers`. Confidential computing is currently only viable path to confidential LLMs [4]; pairing with cryptographic prompt privacy closes last leakage in multi-tenant inference.
