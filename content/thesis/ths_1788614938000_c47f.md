# CHERI Capabilities and Hardware-Enforced Memory Safety: 128-Bit Fat Pointers, Provenance and Monotonicity, Compartmentalization with Domain Transitions, and Morello Prototype Evaluation

## Abstract

Memory-safety vulnerabilities dominate exploited software defects: Microsoft's Security Response Center estimates roughly seventy percent of its CVEs over the last decade stem from memory-unsafety, most of which CHERI-style architectural enforcement would mitigate [4]. This thesis analyzes the **Capability Hardware Enhanced RISC Instructions (CHERI)** architecture, a hybrid capability model from SRI International and the University of Cambridge developed since 2010 under DARPA programs [1]. We dissect the 128-bit CHERI fat pointer — a 64-bit cursor fused with 64-bit metadata (compressed bounds, permissions, object type) and a single out-of-band validity tag — and CHERI Concentrate, the floating-point-like bounds compression that shrinks 256-bit capabilities to 128 bits with exact representation for small allocations and guaranteed monotonicity [2]. We formalize the twin invariants of *provenance validity* and *monotonicity*, examine compartmentalization via sealed capabilities and the `CInvoke` domain-transition primitive underpinning CheriBSD's object-capability model [1][6], and review the Arm Morello Neoverse-N1 prototype evaluation on SPECint across hybrid and pure-capability code-generation models [3]. We conclude that CHERI, standardizing toward CHERI-RISC-V in ISA version 9 [5], is the most industrially mature deterministic memory-safety architecture demonstrated to date.

## 1. Introduction

For half a century, the C and C++ memory model has entrusted the compiler, the programmer, and good fortune with the integrity of every pointer. The price of that trust is measurable: buffer overflows, use-after-free, and type confusion continue to dominate vulnerability taxonomies decades after their exploitation was first systematized. Software-only mitigations — sanitizers, control-flow integrity, probabilistic schemes such as multi-variant execution — either exact punishing runtime costs or provide only probabilistic guarantees that sophisticated adversaries routinely defeat. CHERI takes the opposing, architectural route: it revises the hardware-software contract so that *pointers themselves* carry the metadata required for their own validation, and the microarchitecture enforces that validation on every memory access at near-zero marginal cost [1][4].

CHERI is best understood as a *hybrid* capability architecture [4]. Unlike historical capability machines, which replaced virtual memory wholesale and demanded ground-up software ecosystems, CHERI extends commodity ISAs (MIPS, RISC-V, and Arm's Morello) and blends architectural capabilities with conventional MMU-based virtual memory and C/C++ software stacks [1]. This hybrid character is the central design bet: memory safety becomes incrementally adoptable, with "hybrid" compilation models that protect selected pointers and "pure-capability" models that reinterpret every pointer as a capability, all within existing operating systems such as CheriBSD [8].

## 2. Background

### Capability systems and the hybrid turn

Capability-based addressing descends from the 1960s–1970s work on capability machines (e.g., the Cambridge CAP computer, Hydra, the Intel iAPX 432): references to objects are unforgeable tokens combining *designation* (which object) with *authority* (what may be done to it). Classical systems failed commercially because capabilities were coarse-grained, incompatible with existing software, and expensive to enforce. CHERI's insight — articulated most completely in the 2015 IEEE Symposium on Security and Privacy paper that later received a Test-of-Time award — is that capabilities can be *hybridized* with contemporary ISAs, retaining the MMU, the virtual address space, and the C abstract machine while gaining deterministic spatial safety and scalable compartmentalization [4][9].

### The memory-safety problem space

Spatial safety (every dereference within the referent's bounds) and temporal safety (no dereference after deallocation) together constitute memory safety. CHERI's architectural mechanisms directly provide *spatial* safety and pointer integrity; temporal safety is addressed through revocation, quarantine, and capability-aware allocators built on the capability substrate — recent work shows allocators must trace reference graphs *through* sealed capabilities to avoid leaks [7]. CHERI's philosophy explicitly prefers "robust deterministic protection, not probabilistic debugging" [1].

### Related enforcement strategies

Software fat pointers (e.g., Cyclone, CCured) demonstrated the concept but incurred 2–3× overheads. Tagged-memory schemes and Intel MPX showed that coarse hardware support is insufficient without an integrity story for the metadata itself — MPX's bounds tables could be corrupted because the metadata lacked protection. CHERI's out-of-band *tag bit*, which hardware clears on any non-capability write, closes precisely this gap: metadata integrity is enforced by the same mechanism that enforces the bounds [1][2].

## 3. Methodology

This thesis is an analytical synthesis. Our evidence base comprises the primary architectural specifications — CHERI ISA versions 8 (UCAM-CL-TR-951) and 9 [1][5] — the CHERI Concentrate compression paper (Woodruff et al., *IEEE Transactions on Computers*, 2019) [2], the Arm Morello early-performance technical report (UCAM-CL-TR-986) [3], the IEEE Security & Privacy retrospective on the CHERI software ecosystem (Watson et al., 2024) [4], the CheriRTOS embedded capability-model study [6], and the CAPSTONE capability foundation paper which builds directly on CHERI's compression scheme [10]. Our analysis proceeds by (i) decomposing the 128-bit capability encoding, (ii) formalizing provenance and monotonicity as inductive invariants over capability derivation, (iii) modeling the sealed-capability domain-transition protocol, and (iv) reviewing the Morello SPECint evaluation design and its reported outcomes.

## 4. Deep Dive

### 4.1 The 128-Bit Fat Pointer: Anatomy of a CHERI Capability

A CHERI capability is a *fat pointer*: an integer address extended with metadata that the hardware interprets as authority. In the original CHERI-MIPS design, capabilities were 256 bits wide — base, cursor, limit, and permissions each held at full precision. The production direction, adopted by Morello and CHERI-RISC-V, is a **compressed 128-bit in-memory representation**: 64 bits for the pointer value (the *cursor*) and 64 bits of metadata, plus a single **validity tag bit** stored out of band [1][2].

The logical fields of a capability are: a **tag** (1 out-of-band bit; set only by legitimate capability operations, cleared by any non-capability write); an **address cursor** (64 bits, full precision — kept distinct from the bounds so C idioms like `*p++` in `strcpy` need no second register, and the pointer may transiently wander *out of bounds*, with dereference, not arithmetic, being the checked operation [2]); **bounds** (base and top, compressed); **permissions** (hardware bits — load, store, execute, seal, system-register access — plus software-defined bits); and an **object type** (*otype*, 18 bits) used as the sealing discriminator for compartmentalization.

Capability-sized, capability-aligned memory locations each carry one tag bit (Morello maintains tags at 16-byte granularity), and capability registers carry tags alongside their contents. Every load and store of a capability preserves or clears the tag atomically with the data: writing a capability with a byte-granular store, or overwriting it with an integer, clears the tag, rendering the value unusable as authority [1].

> **Theorem (Non-forgeability):** No sequence of instructions can produce a tagged capability except by deriving it from an existing tagged capability through a monotonic transformation, or from the architectural root capabilities established at reset. Consequently, unprivileged software cannot fabricate authority.

Memory accesses via capabilities are checked in hardware on every dereference: the cursor must lie within `[base, top)`, and the required permission must be present, or the processor raises a capability exception. Crucially, CHERI capabilities carry a *cursor* distinct from the bounds precisely for C compatibility — idioms like `*p++` in `strcpy` move the address without a second register, and the pointer may transiently wander *out of bounds* (a requirement identified from analysis of widely used C programs), with dereference — not arithmetic — being the checked operation [2].

### 4.2 CHERI Concentrate: Compressed Bounds as Floating-Point Intervals

The compression problem is stark: representing base, top, and a 64-bit address in 64 bits of metadata. CHERI Concentrate (Woodruff et al.) observes that base, length, and cursor are *frequently redundant* — the cursor is usually within bounds and the allocation small, so the high bits of all three values coincide [2]. The scheme encodes bounds as a floating-point-like representation of the *distances* from the cursor to the base and top, with an exponent field `E` controlling precision:

- For small objects (below a few KiB), bounds are represented **exactly**, with no additional alignment imposed beyond the natural granularity — stack allocations and small heap objects suffer no representability penalty [2].
- For larger objects, increasing the exponent trades precision for range, requiring stronger bounds *alignment*; the allocator rounds requested bounds outward to a representable envelope. This is the price of compression, and it is paid at allocation time, not on every access.
- A fast **representability check** permits pointer arithmetic directly on compressed capabilities without decompressing them in the register file — avoiding both an enlarged register file and additional load-to-use latency. This optimization is grounded in an instruction-frequency study of compiled capability programs [2].

The encoding retains full monotonicity by construction: narrowing bounds or adjusting the cursor can never *expand* the authorized range. When a pointer is moved substantially out of bounds such that the bounds become unrepresentable relative to the new cursor, the hardware clears the tag rather than permitting a rights-expanding re-encoding — a deliberate choice, hardened in ISA version 9, which prefers clearing tags over raising exceptions for non-monotonic manipulation [1][5].

```c
/* Hybrid C: malloc returns a bounded capability narrowed to the allocation. */
char *buf = malloc(504);          /* capability: base=&buf[0], top=&buf[504] */
buf[600] = 'x';                   /* hardware trap: cursor outside [base, top) */
char *narrow = buf;
__builtin_cheri_bounds_set(narrow, 128);  /* monotonic narrowing; tag preserved */
```

> **Theorem (Monotonicity):** For every capability-manipulation instruction, the set of rights (addressable range × permissions) of each output capability is a subset of the rights of its input. Rights are a *partial order* that hardware enforces to be non-increasing along every derivation edge.

### 4.3 Provenance, Monotonicity, and the Tag Hierarchy

CHERI's security rests on two interlocking invariants [1]:

1. **Provenance validity.** Every valid (tagged) capability has a *provenance chain*: a derivation history rooted in the architectural capabilities the hardware provides at boot — the Default Data Capability (DDC), which authorizes the ambient address space, and the Program Counter Capability (PCC), which authorizes instruction fetch. Capabilities are never "looked up" from ambient authority the way an MMU transparently translates addresses; instead, *instructions always accept capability operands, and never derive them automatically*. This is the **principle of intentional use**: software operates exactly the way the programmer intended, not the way an attacker tricked it into operating [1].
2. **Monotonicity.** Guarded manipulation instructions — `CSetBounds` (narrow bounds), `CAndPerm` (clear permission bits), `CSetOffset`/`CIncOffset` (adjust cursor) — may only *reduce* rights. Permission bits can be cleared but never set; bounds can be shrunk but never grown; sealing and unsealing are mediated by explicit authority. Formal models of the ISA in L3 and subsequently in Sail (a ~2000-line executable specification running at hundreds of KIPS) have been used to prove these properties about compressed capabilities and the architecture as a whole, and serve as the golden reference against which hardware implementations are tested [1][9].

The tag hierarchy makes these invariants *compositional*. Because tags are stored out of band and cleared by any non-capability write, capabilities can be spilled to the stack, passed through memory, and copied between compartments without ever becoming forgeable: integrity travels with the value at the granularity of the memory system itself. Dedicated tag caches keep tag-lookup overhead small in practice [2][3].

```rust
// Conceptual Rust model of the monotonicity invariant enforced in hardware.
struct Capability { tag: bool, base: usize, top: usize, perms: u32 }

fn narrow_bounds(c: &Capability, new_base: usize, new_top: usize) -> Capability {
    assert!(c.tag, "cannot derive from untagged value");
    // Hardware checks: new range must be a subset of the old range.
    assert!(new_base >= c.base && new_top <= c.top, "non-monotonic: trap, tag cleared");
    Capability { tag: true, base: new_base, top: new_top, perms: c.perms }
}
```

### 4.4 Compartmentalization: Sealed Capabilities and `CInvoke` Domain Transitions

Memory safety confines *accidents*; compartmentalization confines *adversaries*. CHERI scales compartmentalization down to the intra-address-space level using **sealed capabilities**: capabilities marked immutable and non-dereferenceable, which raise exceptions if modified, dereferenced, or jumped to [1]. There are two forms:

- **Sealed pairs.** A code capability and a data capability sealed with a common *object type* (*otype*) form an unforgeable token pair. The `CInvoke` instruction takes such a pair and, *iff* the otypes match, **atomically unseals both and transfers control** to the code capability — installing the data capability as the callee's ambient authority. This atomic unseal-and-branch is the domain-transition primitive: the caller cannot intercept the unsealed capabilities mid-flight, and the callee receives exactly the authority the sealer delegated, no more.
- **Sentry capabilities.** A single sealed code capability that can be jumped to with automatic unsealing; Morello-family designs use these pervasively to harden control flow *within* a domain (return addresses become sealed sentries, defeating ROP-style manipulation of saved return pointers) [1].

This mechanism is the foundation of the CheriBSD object-capability model for **in-address-space compartmentalization**: compartments are closed graphs of capabilities, and cross-compartment calls pass through `CInvoke`-mediated object references that switch protection domains without kernel involvement or page-table surgery [1]. The design generalizes beyond processes: CheriRTOS applies the same capability model to embedded devices, using sealed capabilities and capability calls for fast, MPU-free task isolation where the number of simultaneous protection contexts would otherwise be bounded by scarce MPU regions [6].

> **Theorem (Domain-transition integrity):** A `CInvoke` on a sealed pair transfers control to the sealed code capability with exactly the authority named by the sealed data capability if and only if (i) both capabilities are tagged, (ii) both are sealed, and (iii) their object types are equal. No other instruction sequence can unseal a capability without the corresponding sealing authority.

A compartment call sequence in the CHERI assembly idiom is therefore:

1. The caller holds `sealed_code` (otype *T*, executable) and `sealed_data` (otype *T*, non-executable) — opaque tokens it can neither inspect nor modify.
2. `CInvoke sealed_code, sealed_data` atomically unseals both, sets PCC to the code capability, and installs the data capability as the new domain's DDC.
3. The callee executes with least privilege; return passes through a sealed sentry that restores the caller's domain.

Because transitions avoid TLB flushes, page-table walks, and kernel crossings, CHERI compartmentalization is *orders of magnitude* cheaper than process-based isolation — the performance argument that makes fine-grained decomposition (per-library, per-connection compartments) economically viable [4][6].

## 5. Empirical Results: The Morello Prototype Evaluation

Arm's **Morello** is the first industrially credible CHERI implementation: a CHERI-extended Arm Neoverse N1 — a multi-GHz, multi-core, out-of-order superscalar design — taped out as a prototype SoC and evaluation board under the UKRI Digital Security by Design programme, shipping to researchers in January 2022 [3][8]. Morello implements 129-bit capabilities (128-bit value plus tag), the full sealed-capability and sentry machinery, and the hybrid/pure-capability execution modes, composed with a contemporary high-performance microarchitecture and a full CheriBSD/LLVM software stack at a scale unreachable by ISA emulators or FPGA soft cores [3].

The Cambridge performance study (UCAM-CL-TR-986, a living technical report) evaluates Morello against its own baseline microarchitecture on the **SPECint** suite under multiple code-generation models [3]:

| Code-generation model | Pointer representation | Expected overhead source |
|---|---|---|
| Baseline (AArch64) | 64-bit integers | None (reference) |
| Hybrid | Selected pointers as capabilities | Bounds checks on annotated pointers; modest register-pressure increase |
| Pure-capability | Every pointer a 128-bit capability | Doubled pointer footprint; tag-cache traffic; spilling of 16-byte values |

The study's methodology is notable: rather than reporting a single headline number, it explores the *design space* — FPGA variants with modified tag handling alongside the fixed silicon — to attribute overhead to specific mechanisms. Early published snapshots report that **hybrid-mode overheads are small** (bounds checking folds into the existing load/store pipeline), while **pure-capability overheads are dominated by memory-system effects** — the doubled pointer size increases cache footprint and DRAM traffic, with tag costs kept low by dedicated tag caches — rather than by the per-access checks themselves [3]. This validates CHERI Concentrate's central claim: the representability check and in-register compressed arithmetic remove the capability unit from the critical path, leaving overhead proportional to pointer *density* rather than check *complexity* [2].

Complementary evidence comes from the broader ecosystem. The IEEE Security & Privacy retrospective documents the maturation of the CHERI software stack — CHERI Clang/LLVM, CheriBSD, and demonstration ports of nginx, OpenSSH, and WebKit — and the emergence of second-generation industrial cores (Microsoft's CHERIoT on Ibex for embedded targets), arguing that CHERI now offers the fastest credible path to widely deployed memory safety [4]. Microsoft's vulnerability analysis, cited in the Cambridge announcement of the Morello programme, found that roughly 70% of MSRC CVEs over a decade were memory-safety bugs, over two-thirds of which CHERI-style enforcement would have mitigated [8]. Formal-methods evidence rounds out the picture: the Sail ISA model provides an executable, testable specification of provenance and monotonicity, and has been used to verify compressed-capability theorems mechanically [9].

## 6. Limitations

CHERI's guarantees are strong but bounded, and intellectual honesty requires enumerating the boundaries:

1. **Temporal safety is not architectural.** CHERI provides spatial safety deterministically; use-after-free requires complementary mechanisms — revocation sweeps, quarantining allocators, or the emerging allocator/sealing co-design of [7]. The architecture gives revocation a foundation (tags can be swept), not a policy.
2. **Compression imprecision.** Very large allocations receive slightly enlarged bounds; software must tolerate over-approximation at the top of the size spectrum, and tag-clearing on far-out-of-bounds pointers, while safe, can surprise code doing extreme pointer arithmetic [2].
3. **Adoption and ABI surface.** Pure-capability mode doubles pointer size, changing ABIs and struct layouts; hybrid mode requires annotation and recompilation discipline. The ecosystem bet — that Morello-class prototypes de-risk industrial adoption — remains in evaluation [3][4].
4. **Side channels and transient execution.** CHERI enforces *architectural* safety; transient-execution attacks (Spectre/Meltdown-class) operate below the architectural contract. Dedicated analyses have begun mapping CHERI's interaction with speculative execution, but speculative bounds-bypass remains an active research front [11].
5. **Compartmentalization is mechanism, not policy.** Sealed capabilities and `CInvoke` provide fast domain transitions; deciding *where* compartment boundaries lie, and auditing the authority each compartment holds, remains a software-engineering and verification challenge [1][6].

## 7. Conclusion

CHERI reframes memory safety from a software-discipline problem into a hardware-enforced invariant problem. Its 128-bit fat pointer — a full-precision cursor fused with compressed bounds, permissions, and an object type, all guarded by an out-of-band tag — makes every pointer self-describing and self-policing. CHERI Concentrate shows this need not cost 256 bits per pointer; provenance validity and monotonicity, rooted in boot-time capabilities and enforced by formally modeled hardware, make the resulting authority unforgeable and non-amplifiable. Sealed capabilities and `CInvoke` extend the same machinery from *safety* to *least privilege*, enabling in-address-space compartmentalization cheap enough to apply pervasively. The Morello prototype demonstrates that these ideas compose with a modern superscalar pipeline and a real software stack at industrially relevant performance. With ISA version 9 standardizing CHERI-RISC-V, the remaining questions are no longer whether hardware capabilities *can* work, but how quickly software ecosystems will demand that they *must*.
