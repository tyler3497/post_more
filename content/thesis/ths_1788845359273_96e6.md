# Pause-Free Garbage Collection at Scale: Colored Pointers in ZGC, Brooks Forwarding in Shenandoah, and LXR Reference Counting with SATB Barriers for Sub-Millisecond Pauses on 16TB Heaps

## Abstract

Stop-the-world garbage collection pauses have long been the dominant source of tail-latency outliers in managed-language server systems. This thesis dissects three production-grade architectures that each deliver near pause-free collection on heaps up to 16 terabytes: OpenJDK's Z Garbage Collector (ZGC), which embeds GC metadata into 64-bit pointers as *colored pointers* and intercepts stale references with *load barriers* [1][2]; Shenandoah, Red Hat's concurrent compacting collector, which routes every object through a *Brooks forwarding pointer* so relocation never invalidates a mutator-held reference [5][6]; and LXR (Zhao, Blackburn & McKinley, PLDI'22), implemented in MMTk, which combines coalescing reference counting on a hierarchical Immix heap with an infrequent concurrent SATB backup trace, eliminating the read barrier entirely [7][8]. We formalize the Snapshot-At-The-Beginning invariant [4], prove the correctness of self-healing remapping, analyze the cost model of each barrier design, and present empirical evidence that sub-millisecond pauses are achievable independently of heap size with mutator overhead between 1.6% and 15%. We close with open problems: read-barrier cost on wide vector loads, safe elimination of the Brooks word, and colored-pointer multi-mapping on huge-page and CXL memory tiers.

## 1. Introduction

In a managed runtime, garbage collection is the silent tax every allocation eventually pays. For latency-sensitive systems — payment authorizers, ad exchanges, real-time bidding — that tax cannot be paid all at once: a single multi-second stop-the-world (STW) pause violates service-level agreements measured in *milliseconds*.

> **How can a collector guarantee pause times that are independent of heap size, live-set size, and root-set size, while sustaining mutator throughput within a few percent of an unmanaged baseline?**

Three independent designs answer this question along three distinct axes of the barrier-placement design space. ZGC *pays on loads*: every heap read passes through a load barrier that repairs stale colored pointers, so that no global "stop and fix the world" phase is ever needed [1]. Shenandoah *pays on writes*: it reserves one extra word per object — the Brooks forwarding pointer — and uses SATB write barriers plus a load-reference barrier to evacuate objects while mutators run [6]. LXR *pays on stores but never on loads*: coalescing reference counting reclaims the overwhelmingly common acyclic garbage promptly, while an infrequent concurrent SATB trace sweeps up reference cycles [7].

Our contributions are a unified analytic framework treating all three collectors as *barrier-interception strategies* over the same object graph; correctness proof sketches for SATB marking and ZGC's self-healing remap; a comparative empirical analysis of max pause, tail latency, throughput overhead, and heap scalability to 16TB; and an honest inventory of each design's limitations and open problems.

## 2. Background and Related Work

### 2.1 The pause-time problem

A garbage collector must periodically answer two questions: *which objects are live?* and *where can memory be reclaimed?* In stop-the-world collectors these questions are answered while all mutator threads are suspended, so pause duration grows with the work performed — typically proportional to the live set or the whole heap. G1 mitigates this with region-based incremental collection, but its evacuation pause remains proportional to the collection-set size [3].

The three collectors studied here push all remaining work onto concurrent GC threads and the *mutators themselves* via compiler-inserted barriers.

### 2.2 Barriers: a taxonomy

A *barrier* is a small fragment of code the JIT executes around a heap access to maintain collector invariants:

| Barrier type | Interception point | Cost driver | Used by |
|---|---|---|---|
| Load barrier | every object-reference *load* | load rate (~64/µs per core in published profiles) | ZGC |
| Load-reference barrier | loads only | load rate | Shenandoah |
| Pre-write (SATB) barrier | every reference *store*, logs the *old* value | store rate (~4.3/µs per core) | G1, Shenandoah, LXR backup trace |
| Post-write / field-logging barrier | stores, logs the *field* (not value) once | distinct mutated fields | LXR RC phase |
| CAS / acmp / clone barriers | atomic ops, comparisons, cloning | rare | Shenandoah (auxiliary) |

> **Theorem (Barrier-cost asymmetry):** *On typical server workloads, stores are roughly an order of magnitude less frequent than loads. A write-side barrier therefore has a fundamentally lower cost ceiling than a read-side barrier.*

LXR's design is an explicit bet on this theorem: its field-logging write barrier costs ≈1.6% mutator overhead, while ZGC's load barrier, which fires on every reference load, costs ≈5–15% depending on workload [7][1]. The asymmetry is not a law of nature — allocation-heavy, store-heavy workloads can invert it — but it structures the entire design space.

### 2.3 Brooks (1984) and the forwarding-pointer lineage

The Brooks forwarding pointer, introduced in Brooks' 1984 thesis on the Treadmill collector, reserves one word in every object header that always contains *the current address of the object*. When the collector moves an object, it CAS-installs the new address into the forwarding word; every access dereferences through it, so mutators can never observe a stale address. This idea — "never touch a mutator-visible pointer without an indirection the collector controls" — is the direct ancestor of Shenandoah's protocol [5][6] and, in mutated form, of ZGC's colored pointers and C4's load-value barriers.

### 2.4 SATB: Snapshot-At-The-Beginning

Snapshot-At-The-Beginning marking, developed in the context of the G1 collector, defines correctness as *marking the transitive closure of the heap as it existed when marking began* [4]. Any object reachable at snapshot time must be marked, even if the mutator severs the last reference during concurrent marking. The mechanism is a *pre-write barrier*: before overwriting a reference field, the mutator records the field's *old* value into a SATB queue, guaranteeing that no object that was live at the snapshot escapes the marking wavefront. The price is floating garbage — objects that die during marking are conservatively retained until the next cycle — typically a few percent of heap.

## 4. Deep Dive

### 4.1 Colored Pointers and Load Barriers in ZGC

ZGC's core insight is that a 64-bit virtual address space is vastly larger than any physical heap, so the *unused high bits of a pointer are free metadata storage*. On x86-64, ZGC uses 44–48 bits for the object address (supporting up to 16TB heaps) and hijacks 4 of the unused bits as *color bits*: `Marked0`, `Marked1`, and `Remapped` (plus combinations), encoding the known GC state of the referenced object [1][3].

```java
// Conceptual model of ZGC's colored pointer (x86-64, simplified)
//
//  63        46 45 44 43 42 41                         0
// +------------+--+--+--+--+----------------------------+
// | unused     |M1|M0|R |  | object address (42-46 bits)|
// +------------+--+--+--+--+----------------------------+
//                Marked1 Marked0 Remapped
Object o = obj.field;   // JIT inserts, on x86-64 roughly:
                        //   test  ptr, BAD_COLOR_MASK
                        //   jnz   slow_path_remap_or_mark
```

The decisive mechanism is *heap multi-mapping*. ZGC `mmap`s the same physical memory at several virtual addresses — a *Marked0 view*, a *Marked1 view*, and a *Remapped view* [3]. A pointer's color therefore selects *which view* of the same object the mutator sees. During relocation, ZGC copies an object to a new region and records the old→new mapping in a global *forwarding table* (off-heap, so old copies carry no forwarding data and their memory is immediately reusable) [3]. When a mutator later loads a stale (non-`Remapped`) pointer, the load barrier takes a slow path: it looks up the forwarding table and *writes the corrected pointer back into the field it was loaded from* ("self-healing"). Over time the heap converges to a fully remapped state with zero further slow-path hits.

```
 Mutator load path (ZGC): load ptr → color == Remapped? yes → use directly (fast path);
 no → slow path: look up forwarding table, self-heal *field_slot, mark/relocate as needed.
```

Generational ZGC (default since JDK 21/23) adds a young/old split with *store barriers* tracking inter-generational references, keeping the same sub-millisecond pause target [1][2]. Measured load-barrier overhead is ≈4% on SPECjbb2015 [3].

### 4.2 Brooks Forwarding Pointers in Shenandoah

Shenandoah takes the opposite structural bet: instead of stealing pointer bits (which excludes 32-bit and compressed-oop platforms), it pays *one extra word per object* — the Brooks forwarding pointer — plus bits in the object's `markWord` [5][6].

> **Theorem (Brooks invariant):** *At every instant, dereferencing an object's forwarding pointer yields the object's current (to-space) address. A mutator that always accesses objects through the forwarding pointer can never observe a stale copy.*

The evacuation protocol works as follows. Each object starts with its forwarding pointer pointing to *itself*. To evacuate an object, the collector (or a mutator via the write barrier) copies it to a to-space region, then CAS-installs the copy's address into the from-space object's forwarding word [6]. The CAS arbitrates races between concurrent GC threads and mutators: exactly one copy wins; losers discard their copy and use the winner's address. Shenandoah's phases are: STW *init mark*, *concurrent mark* (with SATB), STW *final mark*, *concurrent evacuation*, *concurrent update-references*, and *concurrent cleanup* [6].

Access is mediated by a *load-reference barrier* (LRB): on loading a reference, the barrier checks whether the object lies in a region being evacuated; if so, it resolves the forwarding pointer [6]. SATB write barriers keep the concurrent mark correct, exactly as in G1 [4][5].

The Brooks word is Shenandoah's most controversial tax: every object grows by 8 bytes, increasing allocation pressure and cache footprint. Red Hat's JDK 13 work eliminated the dedicated word by *folding the forwarding pointer into unused mark-word bits* [5]. Reported pauses are typically 1–5ms for young and 1–20ms for mixed phases, sub-linear in heap size, with ≈5–10% throughput overhead [6].

### 4.3 SATB Barriers: the Correctness Core

Both Shenandoah's mark phase and LXR's backup trace rest on SATB. We formalize the invariant.

> **Theorem (SATB correctness):** *Let G₀ be the object graph at the instant concurrent marking begins. If every mutator store of a reference field enqueues the field's pre-store value into the SATB buffer (when marking is in progress), then the concurrent marking wavefront marks every object reachable in G₀, regardless of concurrent mutation.*

*Proof sketch.* Consider any path *r → … → o* in G₀. The wavefront traverses edges forward from roots. A mutator can only hide *o* by overwriting some edge *(u,v)* on every remaining un-traversed path — but the pre-write barrier enqueues *v* before the overwrite commits, and the marker drains SATB buffers as additional roots. Hence every severed edge's target remains reachable from the augmented root set, and *o* is still discovered. ∎

The standard fast-path pseudocode (from the G1 design [4]):

```c
// SATB pre-write barrier: obj.field = new_val
void satb_write_barrier(Object* obj, size_t offset, Object* new_val) {
    if (!marking_in_progress) return;            // filtered: most stores skip
    Object* old = obj->field[offset];            // load pre-store value
    if (old != null) satb_enqueue(old);          // preserve the snapshot edge
    obj->field[offset] = new_val;                // the actual store
}
```

Two refinements matter at scale. First, the `marking_in_progress` check filters the large majority of dynamically executed barriers [4]. Second, Yuasa-style *incremental-update* barriers log the *new* value instead — a different, generally less safe conservatism; SATB's choice to log the old value is what makes the proof above go through without a final re-scan.

The price of SATB is *floating garbage*: objects that become unreachable during marking are treated as live until the next cycle — the accepted tax for never stopping the world to mark.

### 4.4 LXR: Coalescing Reference Counting with a SATB Backup Trace in MMTk

LXR (Zhao, Blackburn & McKinley, *Low-Latency, High-Throughput Garbage Collection*, PLDI'22; extended version arXiv:2210.17175) is built in the MMTk framework over a *hierarchical Immix* heap [7][8]. Its architecture inverts the usual concurrent-collector wisdom: instead of making *tracing* concurrent and paying a read barrier, it makes *reference counting* the primary reclamation mechanism and uses tracing only as an infrequent, concurrent backup.

**Coalescing RC.** Classic reference counting is too expensive per-store for a high-performance runtime. LXR uses *coalescing* RC: a cheap *field-logging* write barrier records each mutated *field* at most once per RC epoch (tracked with per-field "unlogged" bits in MMTk's metadata [8]). At the next short STW pause, the collector processes the logged fields in bulk — repeated stores to the same field within an epoch cost one log entry. Measured mutator overhead is ≈1.6% [7].

**Why no read barrier?** LXR's central economic argument: on measured workloads, stores occur at ≈4.3/µs per core while loads occur at ≈64/µs, making a read barrier ~5× more expensive than the store-side barrier [7]. ZGC and Shenandoah pay the load-side tax to support *concurrent evacuation*; LXR avoids concurrent evacuation entirely. Its Immix heap defragments with *bounded* evacuation inside short STW pauses, and the backup trace is *non-moving*, so no barrier ever needs to intercept a stale reference.

**The SATB backup trace.** Reference counting cannot reclaim cyclic garbage and is conservative under races. LXR therefore runs an *infrequent concurrent backup trace* using SATB marking [7]. Because the trace is non-moving and runs rarely, its cost is amortized; meanwhile the RC fast path reclaims acyclic garbage *promptly* — often within one epoch of death — which is what gives LXR its low-latency profile. Reported results: in a tight heap, 7.8× throughput and 10× better 99.99% tail latency versus Shenandoah; in a moderate heap, +4% throughput over G1 and +43% over Shenandoah [7]. A simplified LXR plan is being upstreamed into mmtk-core with `Pause::RefCount` and field-unlogged-bits metadata [8].

```
 LXR epoch: mutator logs mutated fields via field-logging barrier (once per field per epoch);
 STW pause processes logs in bulk (inc/dec, sweep zero-count objects); rarely, a concurrent
 non-moving SATB backup trace reclaims cycles plus bounded Immix defrag. No read barrier.
```

### 4.5 Scaling to 16TB: Multi-Mapping, Regions, and NUMA

All three designs are *region-based*: the heap is divided into regions (ZGC) or blocks/lines (Immix), so collection work is proportional to the *chosen collection set* — which decouples pause time from heap size.

ZGC's 16TB ceiling comes from the colored-pointer encoding: 4 color bits plus 42–46 address bits fit in 64 bits, and multi-mapping means color changes require no data movement — the same physical page is addressed through a different virtual view [3]. NUMA awareness keeps the concurrent phases from saturating interconnects on large machines [2].

Shenandoah scales to ~2TB heaps; its pause profile is sub-linear rather than flat because the STW *final mark* must drain SATB buffers whose size grows with mutation volume. LXR's scalability argument is different: RC reclamation is *incremental by construction* (work is proportional to mutated fields, not heap size), so its pause bound is a function of the *epoch's mutation volume*, which the collector controls by sizing epochs.

| Design | Pause scaling | Heap ceiling | Barrier tax | Moving? |
|---|---|---|---|---|
| ZGC (gen) | flat (sub-ms) | 16TB | load barrier ~5–15% | yes, concurrent |
| Shenandoah | sub-linear (1–20ms) | ~2TB | LRB + SATB ~5–10% | yes, concurrent |
| LXR | bounded by epoch | Immix-limited | field-logging ~1.6% | bounded STW defrag only |

## 5. Empirical Evaluation / Formal Proofs

### 5.1 Normalized comparison

All numbers are reported *as published*, not re-measured.

| Axis | ZGC | Shenandoah | LXR |
|---|---|---|---|
| Max pause | < 1ms, heap-independent [2] | 1–20ms, sub-linear [6] | short STW pauses, bounded by epoch [7] |
| p99.99 tail | sub-ms [2] | low ms [6] | 10× better than Shenandoah (tight heap) [7] |
| Throughput vs baseline | −4% (SPECjbb2015) [3] | −5–10% [6] | +7.8× vs Shenandoah (tight heap); +4% vs G1 [7] |
| Memory overhead | colored pointers + metadata ~10–20% | Brooks word ~8% (pre-elimination) [5] | RC counts + Immix metadata |

### 5.2 Proof: self-healing remap converges

> **Theorem (Remap convergence):** *In ZGC, after relocation of a region completes, the number of stale (non-Remapped) pointers to that region is monotonically non-increasing, and reaches zero without any stop-the-world phase.*

*Proof sketch.* Stale pointers are repaired exactly when loaded: the slow path rewrites the field slot with the remapped pointer (self-healing), and new stores always install `Remapped`-colored pointers. A stale pointer can therefore only disappear and never be created; roots are remapped during the sub-millisecond root pauses, so repeated mutator execution heals everything and the forwarding-table entry can be freed. ∎

### 5.3 Proof: Brooks CAS evacuation is race-free

> **Theorem:** *Under the Brooks protocol, concurrent evacuation by GC threads and mutator-assisted evacuation can never produce two live copies of the same object.*

*Proof sketch.* Installation of the forwarding pointer is a single CAS from the from-space address to the copy address. Exactly one CAS succeeds; losers observe the winner's address and discard their copies. All subsequent accesses resolve through the single, stable forwarding pointer. ∎

### 5.4 Threats to validity

Published numbers come from different benchmarks (SPECjbb2015, DaCapo, Renaissance), different JDK versions, and different hardware; the "tight heap" regime that flatters LXR punishes collectors tuned for headroom. Treat the table above as *existence evidence* for the claimed regimes, not as a head-to-head ranking.

## 6. Limitations and Open Problems

1. **Read-barrier amortization on wide loads.** ZGC's load barrier fires per reference load; vectorized or bulk-copy paths that move many references per instruction remain a code-generation challenge. Whether hardware memory-tagging extensions can absorb color checks is an open question.
2. **The Brooks word is not free.** Even after mark-word folding [5], the forwarding protocol adds a dependent load to object access during evacuation windows.
3. **SATB floating garbage under high mutation.** All three designs' concurrent traces retain garbage that dies mid-cycle; allocation storms can force premature cycles.
4. **LXR's cycle latency.** Cyclic garbage waits for the infrequent backup trace; workloads dominated by cyclic structures see reclamation latency far above the RC fast path.
5. **Epoch sizing vs. pause bound.** LXR's pause bound is only as good as its epoch-size controller; adversarial mutation bursts can inflate a single epoch's log-processing pause.
6. **CXL and tiered memory.** Colored-pointer multi-mapping assumes cheap virtual aliasing of physical pages; on CXL-attached tiered memory, the cost model of multi-mapped views versus explicit copy is uncharted.
7. **Root scanning.** All designs scan thread stacks in STW pauses; with tens of thousands of threads, root scanning — not heap size — becomes the pause floor [2].

---

## 7. Conclusion

ZGC, Shenandoah, and LXR are three coherent answers to the pause-free collection problem, differing along a single axis: *where the barrier intercepts the mutator*. ZGC intercepts loads with colored pointers and self-healing remaps, buying heap-size-independent sub-millisecond pauses at a 5–15% throughput tax. Shenandoah intercepts through a Brooks forwarding word with SATB-correct concurrent evacuation, trading a per-object word (since folded away) for portability to platforms without pointer-bit headroom. LXR refuses the read barrier altogether, betting — correctly, on measured store/load ratios — that coalescing reference counting plus an infrequent SATB backup trace delivers lower tail latency at 1.6% barrier overhead.

The deeper lesson is architectural: *pause-freedom is not a property of a tracing algorithm but of an interception strategy*. Once the mutator repairs, forwards, or logs every dangerous access, the collector can move the entire heap concurrently. Future work will decide which interception point survives contact with new hardware — tagged memory, CXL tiers, and thousand-core NUMA machines — but the barrier taxonomy developed here will describe those designs too.
