# Erasure Coding at Exabyte Scale: MSR and MBR Regenerating Codes, Clay Codes, and Locally Recoverable Codes for Repair-Optimal Distributed Storage

## Abstract

Modern hyperscale object stores hold exabytes of data across millions of individually unreliable disks, where a single percent of annual drive failures translates into a continuous stream of reconstruction work. Classical Reed–Solomon codes achieve storage-optimal redundancy but repair a single lost fragment by downloading an entire file's worth of data, squandering network bandwidth, the data center's scarcest resource. This thesis develops the theory and practice of *regenerating codes*: the information-flow-graph cut-set bound of Dimakis et al. [1] that lower-bounds every repair, the MSR and MBR corner points and their exact-repair constructions — product-matrix codes [2] and interference-alignment codes [8] — the Clay code's coupled-layer MSR construction with optimal repair access and its Ceph deployment [3], and the production counterpoint of Locally Recoverable Codes in Windows Azure Storage [4, 5], RS policies in HDFS-EC [6], and Partial-MDS codes for sector-plus-disk failures [7]. Quantitative bandwidth comparisons show MSR repair cutting traffic by roughly 3× over Reed–Solomon at identical storage overhead, while Clay codes deliver those savings with practical sub-packetization, closing the gap between information-theoretic optimality and deployed systems.

## 1 Introduction

A storage cluster that holds an exabyte ($10^{18}$ bytes) across 12 TB drives contains on the order of $10^5$ disks. At a conservative annualized failure rate of 2%, such a cluster loses roughly five drives *per day*, every day, forever [4]. In this regime, *repair* — reconstructing the data that lived on failed hardware — is not an exceptional event but the steady-state workload of the system. The question is not whether redundancy is needed, but how much network traffic, disk I/O, and time each repair consumes.

Maximum Distance Separable (MDS) codes, and Reed–Solomon (RS) codes in particular [9], are the workhorse answer to the storage question: an $(n,k)$ RS code spreads a file of size $M$ across $n$ nodes, stores $\alpha = M/k$ symbols per node, tolerates any $n-k$ failures, and is provably storage-optimal. But MDS codes are profoundly *repair-pessimal*. To rebuild a single lost fragment of an RS$(10,4)$ stripe, the canonical procedure downloads any $10$ surviving fragments — the full file $M$ — decodes, and re-encodes. The repair bandwidth $\gamma$ therefore equals the file size, regardless of the fragment's tiny $\alpha = M/10$ footprint. When five drives fail daily, that inefficiency compounds into petabytes of avoidable cross-rack traffic per year.

This inefficiency motivated a decade-long research program. Dimakis, Godfrey, Wu, Wainwright, and Ramchandran reframed repair as a *multicast problem on an information flow graph* and derived a fundamental tradeoff between per-node storage $\alpha$ and repair bandwidth $\gamma = d\beta$ [1]. The two extreme points of that tradeoff — the Minimum Storage Regenerating (MSR) point, which keeps MDS-level storage efficiency while minimizing repair traffic, and the Minimum Bandwidth Regenerating (MBR) point, which minimizes traffic first — became targets for explicit code constructions: product-matrix codes [2], interference-alignment codes [8], and eventually Clay codes, the first MSR construction practical enough for production Ceph clusters [3]. In parallel, systems builders pursued orthogonal objectives: Locally Recoverable Codes (LRCs) in Windows Azure Storage sacrifice a sliver of storage efficiency to repair from a *handful* of nodes [4, 5], HDFS standardized RS erasure-coding policies [6], and Partial-MDS (PMDS) codes addressed the mixed disk-plus-sector failure modes of real RAID arrays [7].

This thesis unifies these threads: the bound, the optimal points, the constructions, the deployments, and the limits.

## 2 Background

### 2.1 The Distributed Storage Model

A file of $M$ symbols over a finite field $\mathbb{F}_q$ is encoded into $n\alpha$ symbols and dispersed so that each of $n$ storage nodes holds $\alpha$ symbols. The code must satisfy two properties:

- **Data collection:** the file is recoverable from *any* $k \le n$ nodes.
- **Repair:** when a node fails, a replacement (*newcomer*) node contacts any $d \ge k$ surviving *helper* nodes, downloads $\beta$ symbols from each, and reconstructs exactly (or functionally) the $\alpha$ symbols the failed node held. The *repair bandwidth* is $\gamma = d\beta$.

Classical MDS codes correspond to $\alpha = M/k$, $d = k$, $\beta = \alpha$, $\gamma = M$.

> **Theorem (naive RS repair):** For a systematic $(n,k)$ Reed–Solomon code, exact repair of one failed node by the decode-and-re-encode procedure requires downloading $k\alpha = M$ symbols — the entire file — irrespective of $d \ge k$.

This is the baseline every subsequent construction must beat.

### 2.2 The Information Flow Graph

Dimakis et al. model the evolution of a storage system as a directed acyclic *information flow graph* [1]: a source $S$ injects the file; each storage node is split into an input vertex $x_{\text{in}}^i$ and output vertex $x_{\text{out}}^i$ joined by an edge of capacity $\alpha$; when node $j$ fails, a newcomer $x^{j'}$ connects to $d$ helpers with edges of capacity $\beta$ and joins the graph with its own $\alpha$-capacity internal edge. A *data collector* connects to any $k$ active nodes with infinite-capacity edges and must recover the file. Since the file flows from $S$ to every data collector, the file size $M$ cannot exceed the minimum $S$–collector cut. Minimizing the cut over all failure histories yields the fundamental bound:

> **Theorem (Dimakis et al. cut-set bound [1]):** For any $(n,k,d)$ regenerating code,
>
> $$M \le \sum_{i=0}^{k-1} \min\{\alpha, (d-i)\beta\}.$$

The bound is tight: random linear network codes achieve it *functionally* (the newcomer need not store exactly what was lost, only something preserving the code's properties) for every point on the tradeoff curve.

### 2.3 Production Context

Three deployments anchor the theory:

- **Windows Azure Storage (WAS):** faced with approaching an exabyte, Microsoft replaced 3× replication with Local Reconstruction Codes — an LRC$(12,2,2)$ with overhead $\approx 1.29\times$ versus $1.5\times$ for RS$(6,3)$ — cutting both storage cost and repair traffic, a design that won Best Paper at USENIX ATC 2012 [4, 5].
- **HDFS Erasure Coding:** Apache Hadoop 3 standardized EC policies RS$(6,3)$ (default), RS$(10,4)$, RS$(3,2)$, RS-LEGACY$(6,3)$, and XOR$(2,1)$, with a 1024 KiB striping cell, bringing RS to data-warehouse scale [6].
- **Ceph:** integrated vector-code (sub-packetized) erasure-code plugins into its master codebase, enabling the first production MSR deployment via Clay codes [3].

## 3 Methodology

Our method is threefold: (i) derive the optimal tradeoff from the cut-set bound and identify the MSR and MBR corner points analytically; (ii) survey exact-repair constructions — product-matrix [2], interference alignment [8], zigzag, and Clay [3] — comparing sub-packetization $\alpha$, field size, and repair access; (iii) contrast with the locality and sector-failure axes via LRCs [4, 5] and PMDS/SD codes [7], and quantify all schemes on common $(n,k,d)$ parameters with a uniform bandwidth model.

### 3.1 The Storage–Bandwidth Tradeoff

Normalizing the bound with $B = M$, the admissible region in the $(\alpha, \gamma)$ plane is piecewise: the curve's two distinguished endpoints are [1]:

- **MSR point** (minimum storage first): $\alpha = \frac{M}{k}$, $\beta = \frac{M}{k(d-k+1)}$, $\gamma_{\text{MSR}} = \frac{Md}{k(d-k+1)}.$
- **MBR point** (minimum bandwidth first, $\gamma = \alpha$): $\alpha = \gamma_{\text{MBR}} = \frac{2Md}{k(2d-k+1)}$, $\beta = \frac{2M}{k(2d-k+1)}.$

*Example.* For $(n,k,d) = (14,10,13)$ and file size $M$: RS repair downloads $M$; MSR downloads $\frac{13}{40}M \approx 0.325M$ (a $3.1\times$ saving at identical storage); MBR downloads $\frac{13}{85}M \approx 0.153M$ (a $6.5\times$ saving at $1.53\times$ the storage per node).

The interior of the curve is achievable only functionally in general; *exact* repair of interior points remains largely open, which is why the literature concentrates on the two corners.

### 3.2 Exact versus Functional Repair

*Functional* repair preserves only the code's abstract properties, requiring the system to track ever-changing coding coefficients. *Exact* repair regenerates bit-identical content, so coefficients are static, the code can be systematic (raw data readable without decoding), and implementations stay sane. Rashmi, Shah, and Kumar proved that exact repair costs nothing extra at the MBR point for all parameters and at the MSR point for $d \ge 2k-2$ [2] — the foundation on which practical codes were built.

## 4 Deep Dive

### 4.1 The Dimakis Bound, Sharpened

The cut-set bound's power lies in its universality: it constrains *every* linear or nonlinear scheme, exact or functional. The minimizing failure history in the proof is adversarial — each of the $k$ nodes a data collector touches is imagined to have been repaired using the *previous* $i$ nodes among the $k$ as helpers, so the $i$-th node contributes only $\min\{\alpha, (d-i)\beta\}$ of *fresh* information. Two corollaries deserve emphasis:

1. **RS is maximally wasteful on the curve.** At the MSR storage level $\alpha = M/k$, the bound permits $\beta = M/(k(d-k+1)) \ll \alpha$; RS's $\beta = \alpha$ overshoots by the factor $d-k+1$ — the number of "extra" helpers beyond the $k$ needed for decoding.
2. **Helpers beat decoders.** The optimal strategy never reconstructs the file during repair; it downloads *projections* ($\beta < \alpha$ symbols) that cancel interference among the unknowns, a principle that interference-alignment constructions [8] later made explicit.

### 4.2 Product-Matrix Codes: Exact Repair Made Explicit

Rashmi, Shah, and Kumar's product-matrix framework [2] gives the cleanest exact-regenerating codes known. Each node $i$ stores the row $\psi_i^{\top} M$, where $\Psi$ is an $n \times d$ encoding matrix (any $d$ rows independent, any $k$ of the first-type rows independent) and $M$ is a $d \times \alpha$ *message matrix* whose structure encodes the operating point:

- **MBR:** $M$ is $d \times d$ *symmetric*, $B = kd - \binom{k}{2}$ message symbols, $\alpha = d$, $\beta = 1$. Repair of node $f$: each helper $h$ sends the single scalar $\psi_h^{\top} M \psi_f$; the newcomer collects $d$ such scalars $= \Psi_{\text{helpers}} M \psi_f$ and inverts to recover $M\psi_f$, then symmetrizes. Elegant, small field, zero repair-coding cost.
- **MSR:** $M = \begin{bmatrix} S_1 \ S_2 \end{bmatrix}$ stacks two $\alpha \times \alpha$ symmetric matrices with $\alpha = d-k+1$, $B = k\alpha$, valid for $d \ge 2k-2$. Each helper sends one symbol; the newcomer's $d$ equations separate the wanted symmetric block from interference.

The framework's real gift is *operational*: repair is a fixed linear recipe with globally known coefficients, independent of failure history — precisely what a storage daemon needs.

### 4.3 Interference Alignment and Zigzag: Exact MSR at $d = n-1$

The product-matrix MSR construction requires $d \ge 2k-2$. Suh and Ramchandran closed the practically crucial case $d = n-1$ (use *all* survivors as helpers) via *interference alignment* [8]: during repair, each helper transmits linear combinations engineered so that all *unwanted* message symbols (interference) collapse into a low-dimensional subspace while the *wanted* symbols remain resolvable. Exact repair of *all* nodes — systematic and parity alike — was shown to cost nothing over the functional bound for $d \ge 2k-1$. The price is sub-packetization $\alpha$ exponential in $k$: theoretically profound, operationally forbidding.

Tamo, Wang, and Bruck's *zigzag codes* offered a combinatorial alternative at the MSR point with $\alpha = r^{k-1}$ ($r = n-k$) and optimal *rebuilding ratio* — the fraction of each helper's content touched during repair — minimizing disk I/O rather than just network bytes. Together, these results mapped the exact-MSR landscape but left a chasm: no construction was simultaneously optimal in bandwidth, sub-packetization, and I/O *and* implementable.

### 4.4 Clay Codes: Coupled Layers with Optimal Access

Clay codes (Coupled-Layer codes) by Vajha et al. [3] bridged that chasm with a construction of disarming simplicity:

1. **Stack:** take $\alpha$ independent codewords of *any* $(n,k)$ MDS code and lay them as $\alpha$ layers.
2. **Couple:** pair symbols from different layers and apply a fixed $2 \times 2$ invertible *pairing transform* to each pair.

The result is an MSR code with $d = n-1$ that is simultaneously optimal in three metrics: *repair bandwidth* (meets the Dimakis bound), *sub-packetization level* (the smallest known among practical MSR codes), and *disk I/O* — it achieves *optimal access*, meaning the number of symbols *read* from each helper equals the number *transmitted* ($\beta$), with no wasted reads. Data and parity nodes repair uniformly, and a variant handles multiple erasures.

Crucially, Clay codes made the leap from theory to practice. Because all MSR codes are *vector* codes (each "symbol" is itself a vector of sub-symbols), the authors modified Ceph to support arbitrary vector codes — a contribution merged into Ceph's master codebase [3]. Evaluated on EC2 with parameters matched to real deployments, a Clay code with $1.25\times$ storage overhead reduced repair network traffic by **2.9×**, disk reads by **3.4×**, and repair time by **3×** relative to its RS counterpart.

### 4.5 The Other Axes: Locality and Sector Failures

Bandwidth is not the only repair cost. *Locality* counts how many *nodes* a repair touches:

- **LRCs:** Gopalan et al. proved a Singleton-type bound for codes with information locality $r$: $d_{\min} \le n - k - \lceil k/r \rceil + 2$, so locality costs distance or storage [5]. Microsoft's WAS LRC$(12,2,2)$ — 12 data fragments, 2 local parities (each covering 6 fragments), 2 global parities — repairs any single fragment from just 6 others, at overhead $\approx 1.29\times$ versus $1.5\times$ for RS$(6,3)$, with *better* durability than triple replication [4].
- **PMDS / SD codes:** real arrays suffer *mixed* failures — whole disks plus latent sector errors. A PMDS$(m,s)$ code tolerates $m$ disk failures *plus* $s$ additional sector failures anywhere in the stripe; e.g., PMDS$(1,2)$ survives one dead disk and two bad sectors, a pattern that defeats RAID-6 despite its two full parity disks. Blaum, Plank, Schwartz, and Yaakobi gave explicit constructions with modest field sizes, generalizing RAID-5/6 [7].

The design space is thus three-dimensional: **bandwidth** (MSR/MBR/Clay), **fan-in** (LRC), and **failure granularity** (PMDS). Production systems increasingly combine them — e.g., LRCs with regenerating-style local repair.

## 5 Empirical Evaluation and Proofs

### 5.1 Bandwidth Comparison on Common Parameters

The following table fixes $(n,k,d) = (14,10,13)$ (HDFS's RS$(10,4)$ footprint with all-survivor repair) and normalizes by file size $M$:

| Scheme | Storage/node $\alpha$ | Total overhead | Repair download $\gamma$ | $\gamma / M$ | Helpers touched |
|---|---|---|---|---|---|
| RS$(10,4)$ (HDFS default class [6]) | $M/10$ | $1.40\times$ | $M$ | 1.000 | 10 |
| MSR point [1] | $M/10$ | $1.40\times$ | $13M/40$ | 0.325 | 13 |
| MBR point [1] | $13M/85$ | $2.13\times$ | $13M/85$ | 0.153 | 13 |
| Product-matrix MSR [2] ($d \ge 2k-2$) | $M/10$ | $1.40\times$ | $0.325M$ | 0.325 | 13 |
| Clay code [3] ($d = n-1$) | $M/10$ | $1.40\times$ | $0.325M$ | 0.325 | 13 |
| LRC (Azure-style, $r \approx 6$) [4] | $\approx M/12$ | $\approx 1.29\times$ | $\approx 0.5M$ | $\approx 0.50$ | 6 |
| PMDS$(1,2)$ over RAID-6-like stripe [7] | $\approx M/10$ | $\approx 1.40\times$ | $M$ | 1.000 | 10 |

*Reading:* MSR/Clay cut repair traffic by $\approx 3.1\times$ at *identical* storage overhead to RS; MBR cuts it by $6.5\times$ at higher storage; LRC optimizes the orthogonal axis (fewest nodes contacted); PMDS pays full-bandwidth repair but survives failure patterns that kill RAID-6.

### 5.2 Reproducible Bandwidth Model

```python
def repair_bandwidth(M, k, d, scheme="msr"):
    """Normalized repair bandwidth gamma for a file of size M."""
    if scheme == "rs":                       # decode-and-re-encode
        return M
    if scheme == "msr":                      # Dimakis bound, storage-optimal corner
        return M * d / (k * (d - k + 1))
    if scheme == "mbr":                      # bandwidth-optimal corner, gamma == alpha
        return 2 * M * d / (k * (2 * d - k + 1))
    raise ValueError(scheme)

for name in ("rs", "msr", "mbr"):
    print(name, round(repair_bandwidth(1.0, 10, 13, name), 4))
# rs 1.0 | msr 0.325 | mbr 0.1529  — matches the table above
```

### 5.3 Proof Sketch: Optimality of the MSR $\beta$

*Claim.* At storage $\alpha = M/k$, no code can repair with $\beta < M/(k(d-k+1))$.

*Proof.* In the information flow graph [1], consider a data collector contacting $k$ nodes whose failure history is nested: node $i$ ($0$-indexed) was repaired using the $i$ previous nodes among the $k$ as helpers. Node $0$ contributes at most $\alpha$ fresh symbols; node $i \ge 1$ shares at least $i\beta$ of its repair data with the previous $i$ nodes, contributing at most $(d-i)\beta$ fresh symbols beyond them. Hence $M \le \alpha + \sum_{i=1}^{k-1}\min\{\alpha,(d-i)\beta\}$. With $\alpha = M/k$ fixed, the sum is maximized (and the bound tightest) when $(d-k+1)\beta \le \alpha \le (d-k+2)\beta$, i.e., $\beta \ge M/(k(d-k+1))$. ∎

Interference-alignment constructions [8] show the bound is *achievable* with exact repair for $d \ge 2k-1$; product-matrix codes [2] achieve it for $d \ge 2k-2$ with far smaller sub-packetization; Clay codes [3] achieve it at $d = n-1$ with additionally optimal access.

## 6 Limitations

1. **Sub-packetization explosion.** Exact-MSR constructions need $\alpha$ growing exponentially (IA codes) or as $(n-k)^t$ (Clay) in the worst case; tiny sub-symbols inflate metadata and CPU costs, and repair parallelism has diminishing returns below stripe granularity.
2. **The exact-repair interior.** Functional codes achieve every interior $(\alpha,\gamma)$ point, but exact-repair constructions for interior points are essentially unknown; systems must pick a corner.
3. **Field size and update complexity.** Large fields slow Galois arithmetic; zigzag-style I/O-optimal codes trade update complexity (each data update rewrites many parities) for read efficiency.
4. **Correlated failures.** All bounds assume independent failures; rack power events and bad firmware batches violate this, which is why operators pair codes with placement constraints (CRUSH failure domains) rather than trusting the math alone.
5. **LRC distance penalty.** Locality provably costs minimum distance or storage [5]; LRCs are tuned for the *common* single-failure case and lean on global parities for the rare multi-failure case.
6. **PMDS practicality.** General PMDS constructions need careful field-size management, and several SD-code parameters were found only by Monte-Carlo search [7].
7. **Degraded reads.** Repair-optimized codes shine when rebuilding lost redundancy; a *client read* that hits a failed node (degraded read) still needs low-latency reconstruction, a workload where systematic codes and LRCs outperform pure regenerating designs.
8. **Adoption friction.** Vector-code support had to be engineered into Ceph from scratch [3]; HDFS-EC's RS policies [6] remain scalar, so MSR's $3\times$ bandwidth dividend is still largely unharvested in the Hadoop ecosystem.

---

## 7 Conclusion

The arc from Dimakis et al.'s cut-set bound [1] to Clay codes running in Ceph [3] is one of information theory's cleanest transfers into production: a multicast bound on an abstract flow graph became, within a decade, a merged kernel of storage infrastructure cutting repair traffic threefold at exabyte scale. The MSR point captures the sweet spot for most operators — MDS-grade storage efficiency with near-minimal repair bandwidth — while MBR, LRC [4, 5], and PMDS [7] cover the bandwidth-extreme, fan-in-extreme, and failure-granularity-extreme corners of the design space. The open frontier is exact repair of interior tradeoff points and taming sub-packetization, problems whose resolution will decide how much of the remaining $3\times$ stays on the table as clusters grow from exabytes toward zettabytes.
