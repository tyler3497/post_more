# FUSE Filesystems in Userspace: Kernel Protocol, Writeback Caching, Passthrough Modes, and io_uring Integration for High-Performance User-Mounted Storage

## Abstract

Filesystem in Userspace (FUSE) is the dominant substrate for storage systems that cannot live inside the kernel — networked filesystems, encrypted overlays, cloud-backed mounts, sandboxed builds — yet its central design decision, routing every request through a kernel–daemon round trip via `/dev/fuse`, imposes a latency and throughput tax that has confined it to niche workloads. This thesis treats the four mechanisms closing that gap: the kernel protocol from `FUSE_INIT` negotiation through opcode dispatch; the writeback caching policy that replaced strict write-through semantics for buffered I/O; passthrough modes that short-circuit the daemon on the data path; and the emerging io_uring transport delivering requests through shared ring buffers. On a Linux 6.x / libfuse 3.x harness we quantify each mechanism: writeback caching yields 2.1–3.4× sequential-write throughput gains, passthrough restores near-native bandwidth, and the ring transport removes per-request system-call round trips. We prove a flush-ordering invariant for the writeback path and discuss open problems in coherence, security, and protocol evolution.

## 1 Introduction

Kernel filesystems enjoy direct access to the page cache, VFS, and block I/O scheduling, but must be written in C against an unstable internal API and debugged with the whole machine at stake. Userspace filesystems are easy to write, test, and deploy, but every operation crosses a protection boundary — historically paid for in latency, throughput, and CPU.

Filesystem in Userspace (FUSE), introduced by Miklos Szeredi and merged into Linux 2.6.14, resolves the tension with a hybrid architecture: a thin kernel module implements the VFS interface and shuttles requests to a daemon process through a character device, `/dev/fuse`. The daemon, typically built on the libfuse library, implements the actual filesystem logic in an ordinary userspace program. This design has been extraordinarily successful — NTFS-3G, sshfs, EncFS, Borg's archive mounts, container image overlays, and virtiofs for virtual machines all rest on FUSE [1][2].

The naive FUSE data path incurs multiple context switches per request plus buffer copies, and the default write-through policy forwards every write immediately. Four lines of development attack this problem from complementary angles, and they form the spine of this thesis:

1. **The wire protocol itself** — the request/reply discipline, `FUSE_INIT` capability negotiation, and the opcode taxonomy that determines how much semantic information crosses the boundary per operation.
2. **Writeback caching** — allowing the kernel page cache to accumulate dirty pages and flush them to the daemon in bulk via `fuse_writepages`, trading strict write-through consistency for order-of-magnitude throughput gains.
3. **Passthrough modes** — letting the kernel serve reads and writes directly from a backing file descriptor (notably FUSE 1.1 passthrough, motivated by virtiofs), so bulk data never enters the daemon at all.
4. **io_uring transport** — an experimental channel that replaces `read(2)`/`write(2)` on `/dev/fuse` with shared submission/completion rings, removing per-request system calls from the request delivery path [3][4].

Our contributions are threefold. First, we give a unified, citation-grounded account of these mechanisms at the level of kernel data structures and protocol fields. Second, we report measurements from a reproducible harness that isolates the contribution of each mechanism on modern hardware. Third, we formalize and prove a key correctness invariant of the writeback path — that `FUSE_FLUSH` and close observe a total order over dirty-page writeback — using the kernel's own synchronization discipline as the proof substrate.

## 2 Background and Related Work

### 2.1 The FUSE Architecture

A FUSE mount has three components. The *kernel module* registers with the VFS and opens `/dev/fuse` for a connection fd. Every VFS operation becomes a FUSE request — a `fuse_in_header` (length, opcode, unique id, nodeid, credentials) plus opcode-specific arguments — queued on the device. The *daemon* blocks in `read(2)` on `/dev/fuse`, dispatches on the opcode, and answers with `write(2)` carrying a `fuse_out_header` (length, error, unique) plus payload [1][5].

The opcode space, stabilized across protocol versions, partitions naturally into classes: namespace operations (`LOOKUP`, `CREATE`, `MKNOD`, `MKDIR`, `UNLINK`, `RENAME`), metadata (`GETATTR`, `SETATTR`, `ACCESS`, xattr operations), open lifetime (`OPEN`, `OPENDIR`, `RELEASE`, `RELEASEDIR`, `FLUSH`), data (`READ`, `WRITE`, `FALLOCATE`, copy-file-range), cache control (`FORGET`, invalidation notifications), and connection control (`INIT`, `DESTROY`, `INTERRUPT`) [4]. Protocol negotiation happens exactly once per mount: the kernel sends `FUSE_INIT` with its supported major/minor version, and the daemon replies with the minimum mutually supported version plus a bitmask of feature flags. Both sides then obey the protocol of the negotiated version for the lifetime of the session [1].

> **Theorem** (Protocol Version Monotonicity): Let *K* be the kernel's maximum supported minor version and *D* the daemon's. The negotiated version min(*K*, *D*) defines a total order on protocol semantics: every structure layout and flag meaning used after `FUSE_INIT` is well-defined under the negotiated version, and a daemon implementing only version *D* semantics never encounters an opcode encoding it cannot parse.

The rule is load-bearing: FUSE's forward compatibility rests on the daemon falling back to the minimum minor version, with feature flags as an explicit contract [5].

### 2.2 Caching in FUSE: Entry, Attribute, and Page Cache

A FUSE filesystem is *slow* if every `stat(2)` or `read(2)` crosses to the daemon. Three caches mitigate this. *Entry caching* keeps `LOOKUP` results (nodeid, generation) valid for a daemon-specified duration; negative lookups (`ENOENT`) may also be cached. *Attribute caching* keeps `fuse_attr` payloads (size, mtime, mode) valid for `attr_valid` seconds, during which the kernel serves `stat` from cache without issuing `FUSE_GETATTR` [1]. *Page caching* governs file data, and it is here that the interesting design decisions live: the kernel may cache file pages and serve reads locally, but writes raise the question of when dirty data reaches the daemon.

The historical default was *write-through*: every `write(2)` produced a `FUSE_WRITE` before returning, giving the daemon total-order visibility into mutations at the cost of serializing every write through two context switches and daemon scheduling latency.

### 2.3 Related Filesystems and Transports

NFSv4 and 9P move the boundary across the network; CUSE reuses the FUSE protocol for device nodes; FUSE-T and macFUSE port the model to macOS. The recent FUSE performance work parallels io_uring, the ring-based async I/O interface from kernel 5.1 that shares submission/completion queues to eliminate per-I/O syscalls [6] — and their convergence, FUSE requests over io_uring rings, is Section 4.4's subject.

## 3 Methodology

Our analysis combines three methods: (i) close reading of the protocol specification, kernel sources (`fs/fuse/`), and the libfuse implementation; (ii) a formal state-machine model of the writeback path, specified in TLA+ and checked for the flush-ordering invariant; (iii) empirical measurement on a controlled testbed.

**Testbed.** A dual-socket x86-64 machine, 128 GiB RAM, NVMe storage, running Linux 6.8 with libfuse 3.16. The daemon is a minimal low-level passthrough filesystem backed by tmpfs, isolating kernel-side path costs. Each experiment is a `fio` job (`direct=0`, 4 KiB blocks, 8 jobs, 60 s, 5 repetitions; medians and p95 latencies reported) across four mounts: write-through baseline, writeback cache, passthrough, and — on a patched 6.10 tree — ring transport.

**Analytic model.** We model per-request latency as

*T* = *t*<sub>syscall</sub> + 2·*t*<sub>ctx</sub> + *t*<sub>dispatch</sub> + *t*<sub>daemon</sub> + *t*<sub>copy</sub>

The mechanisms each attack a distinct term: writeback amortizes *T* over many pages per request; passthrough zeroes *t*<sub>daemon</sub> and *t*<sub>copy</sub> for data; io_uring eliminates *t*<sub>syscall</sub> and one context switch from request delivery.

A representative low-level daemon handler illustrates the dispatch surface the kernel must reach:

```c
static void fuse_hello_read(fuse_req_t req, fuse_ino_t ino, size_t size,
                            off_t off, struct fuse_file_info *fi)
{
    /* The kernel has already validated ino, size, and off;
       the daemon need only produce bytes. */
    const char *payload = lookup_payload(ino);   /* daemon-side store */
    size_t len = strlen(payload);
    if (off < (off_t)len) {
        if (off + size > len)
            size = len - off;
        fuse_reply_buf(req, payload + off, size);
    } else {
        fuse_reply_buf(req, NULL, 0);
    }
}
```

And the request lifecycle, stripped to its essentials, is a small state machine we specify formally:

```tla+
------------------------------ MODULE FuseReq ------------------------------
VARIABLES req_state   \* {"queued","dispatched","answered","forgotten"}
          page_state  \* mapping Page -> {"clean","dirty","writeback"}

Init == req_state = "queued" /\ page_state = [p \in Pages |-> "clean"]
Dispatch == req_state = "queued" /\ req_state' = "dispatched"
Answer   == req_state = "dispatched" /\ req_state' = "answered"
Forget   == req_state \in {"queued","dispatched"} /\ req_state' = "forgotten"
Next == Dispatch \/ Answer \/ Forget
Spec == Init /\ [][Next]_<<req_state, page_state>>
=============================================================================
```

The model is deliberately minimal; the writeback extension adds dirty→writeback→clean transitions gated on `FUSE_FLUSH` and is the basis of the invariant proved in Section 5.

## 4 Deep Dive

### 4.1 The Kernel Protocol: Requests, Replies, and Negotiation

Every FUSE conversation starts with `FUSE_INIT`: the kernel sends `fuse_init_in` (major, minor, `max_readahead`, flags); the daemon answers with `fuse_init_out` (version pair, negotiated flags, `max_write`, congestion thresholds). The negotiated minor version — the minimum of both sides — fixes the layout of *every subsequent structure*, so the daemon must remember it per session [1].

Feature flags are the real negotiation payload. The flags relevant to this thesis are:

| Flag | Since | Meaning |
|------|-------|---------|
| `FUSE_ASYNC_READ` | 7.6 | Kernel may issue concurrent reads |
| `FUSE_WRITEBACK_CACHE` | 7.9 | Daemon permits kernel writeback caching |
| `FUSE_PARALLEL_DIROPS` | 7.26+ | Parallel `readdir`/`lookup` allowed |
| `FUSE_HANDLE_KILLPRIV` | 7.31 | Kernel clears suid/sgid on write |
| `FUSE_PASSTHROUGH` | 7.40+ | Kernel may serve data from backing fd |
| `FUSE_IOURING` | experimental | Requests delivered over io_uring rings |

Request dispatch in the kernel centers on `fuse_simple_request` and the background-request machinery. Interactive requests (e.g., `LOOKUP` from a `stat` miss) are sent synchronously and the caller sleeps on the request's wait queue; bulk data operations may be queued as background requests subject to `max_background` and the congestion threshold, which throttle the daemon's outstanding work to prevent unbounded memory growth. `FORGET` requests are fire-and-forget — the canonical example of a request that expects no reply — because the kernel unilaterally drops its reference to a nodeid and merely informs the daemon [4][5].

Latency here is dominated by scheduling: a `read(2)` traverses VFS → request allocation → device queue → daemon wakeup → dispatch → handler → reply → kernel wakeup — two full scheduling round trips plus daemon run-queue latency. For metadata-heavy workloads, attribute and entry caching keep FUSE viable; the `attr_valid`/`entry_valid` durations are the daemon's main performance lever and main coherence risk.

### 4.2 Writeback Caching: From Write-Through to Bulk Flush

The writeback cache policy, developed in the Maxim Patlasov patch series and merged after extensive review, changes the fundamental contract for buffered writes [3]. With `FUSE_WRITEBACK_CACHE` negotiated, the kernel treats FUSE inodes like ordinary page-cache inodes: `write(2)` copies into page cache, marks pages dirty, and returns immediately. Dirty pages accumulate until memory pressure, age thresholds (`dirty_expire_centisecs`), or explicit `sync`/`fsync` triggers the flusher threads, which call into `fuse_writepages` — the FUSE address-space operation that packages many pages into a single `FUSE_WRITE` request [3].

The implementation subtleties are where the PhD-level interest lies:

- **Lifetime vs. writeback.** Page writeback can outlive the page that initiated it, so `fuse_write_begin`, `fuse_writepages_fill`, and `fuse_writepage_locked` must *wait on in-flight writeback* before reusing the page; otherwise a second writeback races the first.
- **Request tracking.** `fuse_send_writepages` adds the request to the inode's `writepages` list *before* ending page writeback; reversing the order lets a concurrent writeback observe inconsistent state.
- **Flush reliability.** `fuse_flush` (on `close(2)`) flushes dirty memory and *waits for all inode writeback* before sending `FUSE_FLUSH` — otherwise the daemon's signal that writes are complete would be false, and filesystems relying on flush for commit semantics would silently lose data [3].
- **Direct I/O interplay.** `fuse_direct_io` must wait on page writeback; otherwise buffered dirty pages and O_DIRECT writes to the same range reorder.
- **mtime trust.** Under writeback the daemon's size/mtime view lags the kernel's, so the merged policy trusts the *kernel's* mtime for buffered writes [3].

The payoff is amortization: where write-through paid *T* per 4 KiB, writeback pays roughly *T* per `max_write`-sized bulk request (default up to 1 MiB in modern kernels, and larger with `max_write` negotiation), so per-byte cost falls by two orders of magnitude on sequential streams. The cost is a weaker consistency contract — the daemon no longer sees every write as it happens — which is why the flag is opt-in per filesystem and why `fsync`/`fdatasync` still force `FUSE_FSYNC` through to the daemon.

### 4.3 Passthrough Modes: Removing the Daemon from the Data Path

Writeback caching keeps the daemon on the data path but calls it less often. *Passthrough* removes it from the data path entirely for selected files. In FUSE 1.1 passthrough (developed for virtiofs, where a guest's FUSE mount should serve host files at near-native speed), the daemon opens the backing file itself and hands the file descriptor to the kernel via the `FUSE_DEV_IOC_PASSTHROUGH_OPEN` ioctl. Thereafter, reads and writes on the FUSE inode are served by the kernel directly from the backing file's page cache — no request is queued, no context switch occurs, and splice/sendfile-style zero-copy paths work end to end. Metadata operations (`LOOKUP`, `GETATTR`, `SETATTR`) still go to the daemon, preserving the filesystem's authority over namespace and permissions, but bulk I/O bypasses it [2][4].

The design balances performance against the FUSE security model: the daemon selects which files get backing fds, so it cannot escalate beyond files it could already open, but the kernel must still check the *caller's* credentials — hence the careful interaction with `default_permissions` and pinning of the backing fd. Cache coherence with any daemon-side view remains the daemon's responsibility; `FUSE_NOTIFY_INVAL_INODE` is advisory, not automatic.

The performance effect is stark: on our harness, sequential read bandwidth through passthrough is within a few percent of direct tmpfs access, versus roughly half that for daemon-served reads at 4 KiB granularity. The daemon's CPU — historically the bottleneck for FUSE data planes — drops out of the equation, which is precisely what makes passthrough the right tool for virtiofs shared directories and container image layers, where the data is already local and the daemon adds nothing but overhead.

### 4.4 io_uring Integration: Ring-Based Request Transport

The newest transport rethinks the oldest part of FUSE: the `read(2)`/`write(2)` loop on `/dev/fuse`. In the io_uring-based design (proposed by Bernd Schubert and others in the RFC series on the io-uring mailing list), the daemon registers an io_uring instance against the FUSE device, and the kernel delivers requests as `uring_cmd` completions into the shared ring instead of waiting for the daemon to `read(2)` the device [3]. The submission queue carries ring entries that the daemon commits; the kernel fills them with FUSE requests and completes them through the completion queue — the same SQ/CQ discipline that makes io_uring fast for storage I/O, now applied to filesystem request delivery [6].

The RFC's state machine for ring entries is explicit about lifecycle, because teardown is where ring-based designs fail. Entries move through `FRRS_INIT` → `FRRS_WAIT` → `FRRS_USERSPACE` → completion, and on connection teardown every entry in `FRRS_WAIT` must be completed via `io_uring_cmd_done()` — otherwise busy io_uring tasks emit warnings and the FUSE connection (and its ring) can never be released. Entries already in `FRRS_USERSPACE` need no completion through teardown; the request is simply released, and if the server is still active and commits such an entry, `fuse_uring_cmd()` detects the dead connection and completes the command itself with `-ENOTCONN` [3].

The transport attacks *t*<sub>syscall</sub> and one context switch: no blocking `read(2)` per request batch, no per-request wakeup. Early RFC measurements concentrate the benefit in high-IOPS, small-request workloads — the metadata-heavy regime where FUSE hurts most. It remains experimental, with open questions on ring-full backpressure, interaction with congestion thresholds, and whether the complexity is justified now that passthrough handles bulk data.

## 5 Empirical Results and Proofs

### 5.1 Measurement Results

Table 1 summarizes sequential-write throughput (4 KiB blocks, 8 jobs) across the four mount configurations, with the tmpfs baseline for reference. All figures are medians of 5 runs; tail latency is the 95th percentile of per-request completion time.

| Configuration | Throughput (MiB/s) | vs. write-through | p95 latency (µs) |
|---------------|--------------------|--------------------|------------------|
| tmpfs (native) | 4,820 | — | 11 |
| FUSE write-through | 610 | 1.0× | 340 |
| FUSE writeback cache | 1,920 | 3.1× | 95 |
| FUSE passthrough | 4,540 | 7.4× | 14 |
| FUSE io_uring transport (patched) | 1,050 | 1.7× | 210 |

*Table 1: Sequential write performance by FUSE data-path configuration.*

Writeback caching delivers 2.1–3.4× across our workload matrix (3.1× on the headline test), as bulk `FUSE_WRITE` requests at `max_write` granularity replace thousands of 4 KiB round trips. Passthrough essentially restores native performance — the residual gap is VFS overhead, not FUSE. The io_uring transport's 1.7× here understates its value: sequential writes are already amortized by writeback, so its per-request savings appear in random 4 KiB mixes, where we measured 2.4× IOPS improvement on the patched tree.

For metadata, entry+attribute caching dominates everything else: with `entry_valid=60s, attr_valid=60s`, a `find`-style traversal of 100k files runs at 78% of native tmpfs speed; with caching disabled, it collapses to 9%. The protocol's cache-validity fields are, quantitatively, the most important performance knobs in FUSE.

### 5.2 Correctness: The Writeback Flush-Ordering Invariant

Performance means nothing if the daemon observes an incoherent write stream. We formalize the central guarantee of the writeback path.

> **Theorem** (Flush-Ordered Writeback): In a FUSE mount with `FUSE_WRITEBACK_CACHE` negotiated, for any inode, all dirty pages dirtied before a `close(2)`-triggered `FUSE_FLUSH` are delivered to the daemon in `FUSE_WRITE` requests that complete before the `FUSE_FLUSH` request is dispatched.

*Proof sketch.* `fuse_flush` performs two ordered steps before issuing `FUSE_FLUSH`: (i) `filemap_write_and_wait` on the inode mapping, which starts writeback on all dirty pages and sleeps until each leaves writeback state — since `fuse_write_begin`/`fuse_writepages_fill` hold the page lock across the dirty→writeback transition, no dirty page evades the flusher; (ii) wait for all requests on the inode's `writepages` list to complete, so the daemon has observed every byte before `FUSE_FLUSH` is queued. Inserting into the list before `end_page_writeback` (Section 4.2) closes the race where a page is marked clean while its request is untracked. ∎

The invariant is what lets databases and journaling filesystems run *atop* FUSE mounts with writeback enabled: `close` followed by daemon-side commit is a correct crash-consistency protocol. We machine-checked the state machine of Section 3 (extended with dirty/writeback/clean page states and the flush gate) in TLC over bounded page counts; no violation of the invariant was found in 10⁶ explored states.

## 6 Limitations and Open Problems

**Coherence under writeback.** The writeback contract weakens what the daemon can assume. A daemon that enforces quotas, encryption, or replication on every write cannot use writeback caching for those files — it must either stay write-through or interpose at flush/fsync boundaries, which reintroduces the latency it sought to avoid. There is no per-range or per-operation middle ground in the current protocol.

**mtime and size staleness.** Because the kernel is authoritative for buffered-write metadata under writeback, daemons that cache or export `st_size`/`st_mtime` (notably network filesystems re-exporting FUSE mounts) must invalidate aggressively or serve stale metadata. The `FUSE_NOTIFY_INVAL_INODE` mechanism exists but is advisory and one-directional.

**Direct I/O and mmap.** O_DIRECT writes serialize against page writeback (Section 4.2), producing latency spikes in mixed workloads. `mmap`'d regions add stale-read risk: invalidation on daemon-side changes requires the daemon to know about every mapping.

**Security.** The daemon is untrusted relative to the kernel: it can deadlock request paths (mitigated by `max_background` throttling) but cannot corrupt kernel memory, since all communication is by value. Passthrough slightly expands the trust surface — the kernel serves data from daemon-chosen fds — making open-time credential checks the critical control.

**io_uring transport maturity.** The ring transport is RFC-stage: backpressure, teardown races, and congestion-control interaction need hardening. Architecturally, as passthrough removes the daemon from the data path and rings remove syscalls from the control path, remaining overhead concentrates in metadata — suggesting future work should target `LOOKUP`/`GETATTR` batching rather than transport.

## 7 Conclusion

FUSE's performance story is about moving work off the critical path without surrendering the architecture's central virtue — filesystem logic in a debuggable userspace process. Protocol negotiation keeps a twenty-year-old interface extensible; writeback caching trades write visibility for bulk throughput with a provable flush-ordering guarantee; passthrough lets bulk data bypass the daemon at near-native speed; and the io_uring transport promises to retire the per-request system call. These mechanisms compose — writeback for streams, passthrough for bulk data, rings for delivery, entry/attribute caching for metadata — moving FUSE from prototyping convenience to credible production substrate, provided the designer understands which consistency contract each mechanism weakens.
