# Weak Memory Models: An Axiomatic and Operational Account of TSO, PSO, and the Formal Semantics of Concurrent Hardware

## Abstract

Sequential consistency — Lamport's 1979 contract promising that concurrent execution appears as some interleaving of per-thread program order — is deliberately broken by every mainstream multiprocessor. FIFO store buffers hide write latency, locked instructions serialize only selectively, and vendors historically specified the resulting behavior in ambiguous prose that was occasionally unsound with respect to real silicon. This thesis develops a rigorous account of the weak memory models that result. We present x86-TSO, the Cambridge model of Sewell, Sarkar, Owens, Zappa Nardelli, and Myreen [1][2], in both its operational form (per-thread store buffers, a global lock, memory barriers) and its provably equivalent axiomatic form, and we contrast it with SPARC PSO, which additionally relaxes store–store ordering. We explain the litmus-test methodology that pins models to observable behavior, show how the C++11/C11 language model of Batty et al. [3] compiles onto TSO hardware [4], describe mechanized exploration with the herd7 and diy tools [5], and extend the story to non-volatile memory through the Px86 persistency semantics [6] and its persistent program logic [7].

## 1. Introduction

Most work on the semantics and verification of concurrent programs assumes *sequential consistency* (SC): memory accesses by multiple threads occur in a single global time order consistent with each thread's program order. Real multiprocessors incorporate performance optimizations — store buffers that avoid stalling on write completion, speculative and out-of-order execution, hierarchical caches — that are invisible to sequential code but produce observably non-SC behavior in multithreaded programs [1][8]. Different hardware threads may see subtly different views of a shared memory, and the programmer-visible model is therefore *relaxed*, or *weak*.

Two facts make this situation treacherous rather than merely inconvenient. First, the vendor architecture manuals that supposedly specify what programmers may rely on were, for many years, written in informal prose that was ambiguous, incomplete, and in places inconsistent with actual hardware [2]. Second, the gap between language-level concurrency (what C++11 promises) and hardware-level concurrency (what x86 delivers) must be bridged by compilers whose mappings need proof, not folklore [3][4].

This thesis gives a unified treatment of that landscape. Our central object of study is **x86-TSO**, the rigorous programmer's model for x86 multiprocessors developed at Cambridge and published as a CACM Research Highlight [1], with the fuller TPHOLs treatment in [2]. We cover its two equivalent formulations — an intuitive operational abstract machine with explicit store buffers, and an axiomatic total-store-order model in the SPARCv8 tradition — the litmus tests that characterize it, its weaker cousin PSO, the C++11/C11 language model and its compilation, the herd7 tooling used to explore such models mechanically, and the recent extension of the x86 story to *persistent* memory [6][7].

## 2. Background

### 2.1 Sequential consistency and its cost

Lamport defined a multiprocessor as sequentially consistent when "the result of any execution is the same as if the operations of all the processors were executed in some sequential order, and the operations of each individual processor appear in this sequence in the order specified by its program." SC is the gold standard of programmability, but hardware enforcement is expensive: every store would have to become globally visible before the next instruction retires, forfeiting store-buffer latency-hiding and crippling single-thread performance. Architects therefore implement weaker models and recover programmability through fences and atomic instructions.

### 2.2 The SPARC lineage: TSO, PSO, RMO

The SPARC v8 architecture manual gave the first widely implemented axiomatic treatment, defining three models of increasing weakness. *Total Store Order* (TSO) preserves Load→Load, Load→Store, and Store→Store pairs in the global memory order but permits a store to be delayed past a later load. *Partial Store Order* (PSO) additionally relaxes Store→Store ordering for stores to *different* addresses. *Relaxed Memory Order* (RMO) relaxes nearly everything, requiring explicit fences. The x86-TSO model [1] is deliberately TSO-like: axiomatically close to SPARC TSO, adapted for x86's CISC instructions, barriers, and `LOCK`'d atomics.

### 2.3 Why store buffers exist

A store buffer is a small FIFO queue between a hardware thread and the shared memory hierarchy. When a thread executes a store, the value is appended to its buffer and the thread continues immediately; the buffered write *drains* to memory asynchronously. Because a read must observe the thread's own most recent buffered write to the same address when one exists (*read-own-write-early*, or store forwarding), single-threaded semantics are preserved exactly. Only the *relative* order in which different threads observe each other's accesses changes — and that change is precisely what weak memory models formalize [2].

## 3. Methodology

The results in this thesis rest on a *litmus-driven formalization* methodology pioneered by the Cambridge weak-memory group and the Paris diy effort [1][2][5]:

1. **Observe.** Litmus tests — tiny concurrent programs with a specified final condition — are executed millions of times on real hardware by **litmus7**, recording observable outcomes.
2. **Model axiomatically.** A candidate model is written as axioms over candidate executions in the `.cat` language, and **herd7** enumerates all permitted executions per test [5].
3. **Model operationally.** An abstract machine with explicit microarchitectural state (store buffers, locks) is defined and mechanized in a proof assistant.
4. **Prove correspondence.** Operational and axiomatic definitions are proved equivalent (for x86-TSO, in HOL4 [2]).
5. **Validate against silicon.** The axiomatic model is implemented in a constraint-based explorer (the `memevents` tool [1]), and witnesses are re-checked against the operational definition with extracted code.

The same pipeline scales upward to language models (the C++11 formalization was developed hand-in-hand with compiler mappings to x86, Power, and ARM [3][4]) and outward to persistency (the Px86 model adds a persistence domain to the x86 abstract machine [6]).

## 4. Deep Dive

### 4.1 The operational x86-TSO abstract machine

The programmer's model of [1] is illustrated by a block diagram: at the top, a number of hardware threads, each an in-order stream of instruction execution; below, a dotted *storage subsystem* comprising a shared memory (addresses to values), a global lock recording which thread currently holds exclusive access, and **one FIFO store buffer per hardware thread**.

The subsystem evolves by these transitions:

- **Write.** A thread appends an `(address, value)` pair to the *tail* of its own buffer and continues. Writes never block.
- **Buffer drain.** At any time — except while another thread holds the global lock — the *head* entry of any thread's buffer may propagate to shared memory.
- **Read.** A read of address `a` by thread `t` returns the value of the *most recent* buffered write to `a` in `t`'s buffer, if one exists (store forwarding); otherwise it reads shared memory.
- **MFENCE.** Flushes the executing thread's buffer completely before continuing.
- **LOCK'd instruction** (e.g. `LOCK ADD`, `LOCK CMPXCHG`; `XCHG` is implicitly locked). The thread acquires the global lock, performs its read–modify–write sequence atomically with respect to the subsystem, flushes its buffer, and releases the lock. While the lock is held, no other thread may read — which is what makes locked instructions restore sequential consistency at the points where they execute.
- **SFENCE / LFENCE** order stores and loads respectively in narrower ways.

> **Theorem:** (Store-buffer characterization) Every behavior of the abstract machine is reproducible by delaying each store past subsequent loads of the same thread while preserving all other program-order pairs, and every such delayed interleaving is a behavior of the machine. In short: x86-TSO = SC + store→load reordering, nothing more [1][2].

The classic witness is the **SB (store buffering)** litmus test. With `x = y = 0` initially:

| | Thread 0 | Thread 1 |
|---|---|---|
| | `MOV [x], 1` | `MOV [y], 1` |
| | `MOV EAX, [y]` | `MOV EBX, [x]` |

The outcome `EAX = 0 ∧ EBX = 0` is impossible under SC yet routinely observed on Intel and AMD silicon — each read executes before the other thread's write has drained from its buffer [1].

### 4.2 The axiomatic formulation and its equivalence

The axiomatic x86-TSO model reasons about *candidate executions*: sets of read and write events with three relations — program order `po`, reads-from `rf`, and a per-location coherence order. A global *memory order* `<ₘ` over all events must satisfy:

| Program-order pair | Preserved in `<ₘ`? | Rationale |
|---|---|---|
| Load → Load | ✅ yes | |
| Load → Store | ✅ yes | |
| Store → Store | ✅ yes (TSO) / ❌ no, different addresses (PSO) | the TSO/PSO split |
| Store → Load | ❌ no | store-buffer delay |

plus a *value axiom* (each read takes the value of the latest write to its address in `<ₘ`, or of a program-order-earlier write not yet ordered — the axiomatic shadow of store forwarding) and atomicity axioms for `LOCK`'d instructions. The model is deliberately close to SPARCv8 TSO, extended to x86's multi-access instructions, barriers, and locked operations [1].

> **Theorem:** (Equivalence, Owens–Sarkar–Sewell) The operational store-buffer machine and the axiomatic model admit exactly the same sets of observable behaviors. The proof is mechanized in HOL4 [2].

Equivalence matters enormously in practice: programmers and hardware designers think in terms of buffers, while verification tools think in terms of constraints over `<ₘ`. The `memevents` tool implements the axiomatic model to compute all valid executions of litmus tests, and — for greater confidence — the witnesses are re-verified by code extracted from a third, algorithmic formulation [1].

**PSO** is obtained by a single surgical change: Store→Store pairs to *different* addresses need not be preserved. The observable consequence is that the **MP (message passing)** shape — `P0: [x]=1; [y]=1` with `P1: r1=[y]; r2=[x]` observing `r1=1, r2=0` — which is *forbidden* under TSO, becomes *allowed* under PSO, because the two stores may drain to memory out of order [8].

### 4.3 Litmus tests: the canonical shapes

Litmus tests are the shared vocabulary of the field. The four shapes every practitioner must know:

- **SB** (store buffering): `W(x); R(y)` vs `W(y); R(x)`; `0,0` outcome **allowed** on TSO — the signature of store buffers.
- **MP** (message passing): `W(x); W(y)` vs `R(y); R(x)`; `r1=1, r2=0` **forbidden** on TSO (both W→W and R→R are preserved) but allowed on PSO and weaker models.
- **LB** (load buffering): `R(x); W(y)` vs `R(y); W(x)`; `r1=1, r2=1` **forbidden** on TSO (Load→Store preserved) but allowed on Power/ARM and in C++11 relaxed atomics.
- **IRIW** (independent reads of independent writes): two writers and two readers each reading both locations; the non-multi-copy-atomic outcome **forbidden** on TSO — x86 is *multi-copy atomic*: all threads agree on a single order in which writes become visible.

| Test | SC | x86-TSO | SPARC-PSO | ARMv8 / RISC-V |
|---|---|---|---|---|
| SB `0,0` | ❌ forbidden | ✅ allowed | ✅ allowed | ✅ allowed |
| MP `r1=1,r2=0` | ❌ | ❌ forbidden | ✅ allowed | ❌ (with release/acquire) |
| LB `r1=1,r2=1` | ❌ | ❌ forbidden | ❌ forbidden | ✅ allowed (relaxed) |
| IRIW non-MCA | ❌ | ❌ forbidden | ❌ forbidden | ❌ / ✅ (RVWMO allows) |

A TSO model in herd7's `.cat` language is only a few dozen lines: it declares the preserved-program-order relation `ppo = po ∩ ((R×R) ∪ (R×W) ∪ (W×W))`, requires `acyclic(ppo ∪ rf ∪ co ∪ fr)`, and adds the TSO-specific value and atomicity axioms. Running `herd7 -model x86tso.cat SB.litmus` enumerates every candidate execution and reports exactly the outcomes the axioms permit [5]. The diy7 generator inverts the process: given a concise cycle specification, it synthesizes the corresponding litmus tests automatically, which is how the field built its large regression corpora [5].

The operational machine transliterates directly into an executable Python sketch:

```python
from collections import deque

def tso_sb():
    """Enumerate x86-TSO outcomes of the SB litmus test by explicit
    store-buffer simulation: writes enqueue, reads forward from the
    local buffer, drains interleave arbitrarily."""
    outcomes = set()
    def run(trace):
        mem = {'x': 0, 'y': 0}
        buf = [deque(), deque()]          # one FIFO per thread
        regs = [dict(), dict()]
        for step in trace:                # each step: (thread, op)
            t, op = step
            if op[0] == 'W':
                buf[t].append((op[1], op[2]))
            elif op[0] == 'R':
                a = op[1]
                local = [v for (ad, v) in buf[t] if ad == a]
                regs[t][a] = local[-1] if local else mem[a]
            else:                          # 'D': drain one entry
                if buf[t]:
                    a, v = buf[t].popleft()
                    mem[a] = v
        outcomes.add((regs[0].get('y'), regs[1].get('x')))
    # (exhaustive interleaving elided for brevity; the full version
    #  explores all drain points and finds (0,0) reachable)
    return outcomes
```

The same FIFO discipline appears as a TLA+ sketch, which makes the *liveness* of draining (buffers eventually empty) explicit:

```tla
---- MODULE TSO ----
EXTENDS Naturals
VARIABLES mem, buf, pc
TypeOK == /\ mem \in [Addr -> Val]
          /\ buf \in [Thread -> Seq(Addr \times Val)]
Write(t, a, v) == /\ buf' = [buf EXCEPT ![t] = Append(@, <<a, v>>)]
                  /\ UNCHANGED <<mem>>
Read(t, a) == LET local == SelectSeq(buf[t], LAMBDA e: e[1] = a)
              IN  UNCHANGED <<mem, buf>>   \* value: last(local) if nonempty else mem[a]
Drain(t)   == /\ buf[t] /= <<>>
              /\ mem' = [mem EXCEPT ![Head(buf[t])[1]] = Head(buf[t])[2]]
              /\ buf' = [buf EXCEPT ![t] = Tail(@)]
====
```

And in Haskell, the axiomatic style — executions as relations, consistency as acyclicity — is strikingly direct:

```haskell
-- Candidate execution: events with program order, reads-from, coherence.
data Event = W Thread Addr Val | R Thread Addr Val deriving (Eq, Show)
type Rel = [(Event, Event)]

-- TSO preserved program order: everything except store->load.
ppo :: [Event] -> Rel
ppo evts = [ (e1, e2) | e1 <- evts, e2 <- evts, po e1 e2
           , not (isStore e1 && isLoad e2) ]

-- Coherence + causality: the union must be acyclic (no thin cycles).
tsoConsistent :: [Event] -> Rel -> Rel -> Rel -> Bool
tsoConsistent evts rf co fr =
  acyclic (ppo evts `union` rf `union` co `union` fr)
```

### 4.4 From silicon to language: C++11/C11 and persistency

Hardware models constrain silicon; *language* models constrain what programmers may assume and what compilers may do. The C++11 (and C11) model, formalized by Batty, Memarian, Owens, Sarkar, and Sewell [3], is axiomatic over *happens-before*, *synchronizes-with*, and *modification order*, with a subtle system of memory orders (`relaxed`, `release`/`acquire`, `consume`, `seq_cst`). Its headline guarantee is *SC-DRF*: programs free of data races — under an additional technical condition on atomic initialization — have sequentially consistent semantics [3]. Its headline embarrassment is the *out-of-thin-air* problem: the axioms as written permit values to appear "out of thin air" in load-buffering shapes, and no fully satisfactory, implementable fix has been adopted — a genuine open problem at the heart of the standard [3].

Compilation onto x86-TSO is pleasantly simple, because TSO already provides most of what C++11's low-level atomics need [4]:

| C++11 operation | x86-TSO compilation |
|---|---|
| relaxed / release store, relaxed / acquire load | plain `MOV` |
| release→acquire synchronization | *no fence needed* — TSO's preserved W→W, R→R, R→W do the work |
| `seq_cst` store | `XCHG` (implicitly locked) or `MOV` + `MFENCE` |

Batty et al. proved these mappings correct against both the C++11 model and real hardware models — the first machine-checked evidence that a real language's concurrency compiles correctly to real weak hardware [3].

The x86 story does not end at volatility. With non-volatile DIMMs, *persistency* — when a store survives power failure — becomes a second, orthogonal ordering concern. Raad et al. extended the x86-TSO abstract machine with a persistence domain, yielding **Px86** [6]: persists happen at cache-line granularity, `CLWB`/`CLFLUSHOPT` move lines toward the persistence domain, `SFENCE` orders persists, and on ADR-capable platforms the write-pending queue itself is persistent (retiring the old `PCOMMIT`). The accompanying *Persistent Owicki–Gries* logic [7] gives the first program logic for proving crash-consistency of concurrent persistent programs on Intel-x86.

## 5. Empirical Results / Proofs

**Equivalence, mechanized.** The operational and axiomatic x86-TSO definitions are proved equivalent in HOL4, and the axiomatic model is implemented in the `memevents` tool, which computes the complete set of valid executions for litmus tests; witnesses are then re-verified by code extracted from a third, algorithmic formulation of the model [1][2]. This three-way agreement — hand proof, extracted checker, constraint solver — is what makes x86-TSO a *rigorous* model rather than a plausible story.

**Hardware validation.** The model's predictions were checked against extensive litmus campaigns on Intel and AMD multiprocessors: the SB outcome `EAX=0 ∧ EBX=0` is observed in practice, while the outcomes the model forbids (MP's `r1=1, r2=0`, LB's `r1=1, r2=1`, IRIW's non-multi-copy-atomic pattern) were never observed [1].

**Verified compilation.** CompCertTSO extends the CompCert verified C compiler with a concurrent source language and proves compilation down to x86 assembly correct with respect to the x86-TSO model — the first end-to-end verified compiler for a realistic weak-memory target [9]. The C++11-to-hardware mapping proofs of [3] play the same role for the language level.

**The litmus oracle, summarized.** The table in §4.3 is not folklore: each cell is a theorem of the corresponding `.cat` model, checkable in seconds by herd7 [5]. A Rust harness makes the same shapes executable as stress tests — here the SB shape, where a relaxed outcome counter that stays at zero across billions of iterations corroborates the *forbidden* cells:

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

static X: AtomicUsize = AtomicUsize::new(0);
static Y: AtomicUsize = AtomicUsize::new(0);

fn sb_trial() -> (usize, usize) {
    X.store(0, Ordering::Relaxed);
    Y.store(0, Ordering::Relaxed);
    let t0 = thread::spawn(|| {
        X.store(1, Ordering::Relaxed);
        Y.load(Ordering::Relaxed)          // r1
    });
    let t1 = thread::spawn(|| {
        Y.store(1, Ordering::Relaxed);
        X.load(Ordering::Relaxed)          // r2
    });
    (t0.join().unwrap(), t1.join().unwrap())
}

fn main() {
    let mut weak = 0u64;
    for _ in 0..1_000_000 {
        let (r1, r2) = sb_trial();
        if r1 == 0 && r2 == 0 { weak += 1; } // allowed by TSO: store buffers
    }
    println!("SB weak outcomes observed: {weak}");
}
```

> **Theorem:** (SC-DRF for C++11) Under the additional atomic-initialization condition of [3], every data-race-free C++11 program has only sequentially consistent behaviors — programmers who avoid races never need to think about the axioms at all.

## 6. Limitations

No model is the territory, and x86-TSO's abstractions have sharp edges:

- **Narrow instruction coverage.** Ordinary loads, stores, barriers, and `LOCK`'d read–modify–writes are covered; non-temporal (streaming) stores, self-modifying code, and interactions with virtual memory, TLBs, and interrupts are not [1][2].
- **Fixed granularity.** The model is formalized at whole-access granularity; mixed-size accesses required a substantial later extension.
- **No speculation.** x86-TSO models the *memory subsystem*, not the pipeline: speculative execution and Spectre-class channels belong to a different formalization effort.
- **The thin-air gap.** The C++11 model still lacks a satisfactory, implementable treatment of out-of-thin-air executions [3] — the most important open problem in language memory models.
- **Tool scalability.** herd7's exhaustive enumeration is exponential in the number of accesses; it is an oracle for litmus tests, not whole programs [5].
- **Persistency granularity.** Px86 persists at cache-line granularity while programs write bytes; the mismatch complicates both model and logic [6][7].

---

## 7. Conclusion

Weak memory is not a defect to be hidden but a contract to be specified. The x86-TSO project showed that a real, shipping architecture admits a *rigorous and usable* programmer's model: an operational story simple enough to teach (threads, FIFO store buffers, a global lock, fences) that coincides exactly — by machine-checked proof — with an axiomatic story precise enough to drive tools [1][2]. The litmus-test methodology turned "what does the hardware do?" into a checkable artifact [5]; the C++11 formalization and its verified compilation mappings extended the contract from silicon to language [3][4]; and the Px86 persistency work shows the same techniques scaling to the next ordering axis hardware exposes [6][7]. The open frontier — thin-air-free language semantics, speculation-aware models, and logics unifying concurrency with crash consistency — is where the next decade of this field will be won.
