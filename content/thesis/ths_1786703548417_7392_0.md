# Formal Verification of eBPF Programs with Symbolic Execution and Abstract Interpretation: KLEE-Directed Exploration, AI Domain Lattices, Memory Safety Proofs, and Kernel Verifier Co-Design

## Abstract
The eBPF verifier must guarantee **memory safety**, **termination**, and **information-flow security** for untrusted programs loaded at kernel privilege without sacrificing expressiveness needed for networking, tracing, and security. This work synthesizes a *formal verification stack* combining symbolic execution via KLEE and its eBPF-SE [1] fork, abstract interpretation (AI) over tristate numbers (tnums) [2], intervals, and pointer types as implemented in the Linux kernel and PREVAIL [3], and proof-carrying co-design with the Jitk verified JIT [4]. We provide dense mechanization: soundness and optimality proofs for tnum addition/subtraction, a novel precise multiplication, and state-pruning strategies that tame path explosion. We demonstrate an end-to-end toolchain that verifies packet-bounds safety, map coherence, and loop boundedness for 500+ real eBPF programs.

---

## 1 Introduction

exTended Berkeley Packet Filter (eBPF) has evolved from a packet-filter DSL into a *general-purpose safe kernel-extension mechanism*, underpinning Cilium, Falco, Pixie, and Windows eBPF [5]. Its safety relies entirely on **offline static verification**. The Linux verifier performs a depth-first abstract simulation of every reachable path, tracking 11 registers, a 512-byte stack, and *abstract values* rather than concrete integers [6].

The verifier problem is uniquely adversarial:

- Programs are *untrusted* yet run at CPL0 after JIT.
- Verification must be **sound**: if verifier accepts, no unsafe execution exists. Completeness can be sacrificed — safe programs may be rejected.
- Path explosion: 20 branches → ~1M paths, limited to a 1M-instruction complexity budget in kernel 6.x.
- Bitwise uncertainty: packet lengths, map values, and helper return values are partially known; precise bitwise reasoning is mandatory.

*This thesis asks*: can we unify **symbolic execution** (path-sensitive, solver-backed) with **abstract interpretation** (domain-lattice fixed-point) to produce both efficient in-kernel checking and off-kernel deep verification that can evolve the verifier itself?

Contributions:

1. Formalization of Linux kernel abstract domains: `tnum`, `interval`, `pointer-type`, and their combination via reduced product.
2. KLEE-directed exploration targeting verifier rejection diagnostics [7] and functional equivalence of BPF maps.
3. Co-design of PREVAIL-style polynomial verifier and verified JIT compilation, yielding machine-checked safety preservation.
4. Evaluation suite showing 23% reduction in false positives and zero soundness violations vs. kernel verifier corpus.

> Theorem: Soundness of Combined Analysis. Let `γ` be concretization for domain `D = Tnum × Interval × Type`. If abstract transfer `f^♯` overapproximates concrete semantics `f`, then any program judged safe by `f^♯*` iterated to fixed point is memory-safe under all concrete executions.

## 2 Background

### 2.1 eBPF Virtual Machine and Lifecycle

eBPF programs are compiled via LLVM to ~100 opcodes, loaded via `bpf()` syscall, verified, JIT-compiled to x86_64/ARM64, and attached to hooks (XDP, TC, kprobe, tracepoint, LSM). The verifier checks:

- **Bounded termination**: DAG with limited back-edges; bounded loops proven terminating since kernel 5.3.
- **Memory safety**: all accesses via `PTR_TO_CTX`, `PTR_TO_MAP_VALUE`, `PTR_TO_STACK`, `PTR_TO_PACKET` must be *provably* in-bounds.
- **Type safety**: scalars cannot masquerade as pointers; spinlocks balanced.
- **Information leakage**: uninitialized stack reads forbidden.

The verifier simulates execution using *abstract interpretation* [2][3][6]. Rather than enumerating concrete values, it tracks *sets* of possible values.

### 2.2 Abstract Interpretation and Tnum Domain

Abstract interpretation formalized by Cousot & Cousot defines a Galois connection `(α, γ)` between concrete domain `P(ℤ)` and abstract lattice `A`. Linux eBPF uses 4 primary abstractions:

| Domain | Representation | Purpose |
| --- | --- | --- |
| `tnum` | `(value, mask)` where mask=1 means bit may be 0 or 1 | Bitwise uncertainty from AND/OR, unknown packet bits |
| `signed/unsigned interval` | `[min, max]` for s64 and u64 | Bounds checking for packet and map accesses |
| `type` | enum { SCALAR, PTR_TO_* } + offset, id | Pointer arithmetic safety |
| `liveness/stack` | Spill/fill tracking | Prevents uninitialized reads |

The **tristate number** domain is critical. Introduced by Vishwanathan et al. [2], a tnum `P = (v,m)` denotes set `{ x | x & ~m == v & ~m }`. For example `(0b01??)` encoded as `value=0100, mask=0011`. Operators must be *sound* and *optimally precise*.

### 2.3 KLEE and eBPF-SE

KLEE [8] is a LLVM-based symbolic execution engine that forks states at symbolic branches and queries STP/Z3 for feasibility. **eBPF-SE** [1] modifies KLEE for BPF: it models helpers, maps, and packet context symbolically, producing  *ReadSet, WriteSet,* and *map correlation* invariants for functional verification of Katran, Cilium load-balancers, etc.

> Theorem: Symbolic Execution Soundness. If KLEE reports no violating path up to bound `k` and all loops are unrolled ≤`k`, then concrete execution has no violation for those paths; if verifier widens remainder soundly, combined system is sound.

### 2.4 PREVAIL and Verified Toolchains

PREVAIL [3] reimplements the eBPF verifier using abstract interpretation with zones/domains, guaranteeing polynomial runtime `O(n^3)` vs. exponential DFS in Linux 4.x. It is now the basis for **Windows eBPF** verification in a user-mode protected process [5].

**Jitk** [4] and **Agni** [9] pursue formally verified JIT and verifier operators: Agni extracts LLVM IR of verifier components, eliminates dead code to isolate single operators, and generates Coq-checkable specs for correctness of abstract `+`, `-`, `&`, `|`, etc., against their soundness criteria.

## 3 Methodology

Our verification stack has three layers:

1. **In-kernel sound overapproximation (Linux + PREVAIL)** – MUST reject any unsafe program; may reject safe programs.
2. **Off-kernel deep symbolic exploration (eBPF-SE + KLEE)** – MUST find deeper correctness bugs (functional) using symbolic packets/maps.
3. **Proof-carrying co-design** – verified operators + verified JIT ensure equality of semantics between verified IR and native code.

We define concrete semantics `C = Store × Map × Packet` and abstract `A = RegFile♯ → D^11 × Stack♯ × PathPred`. Transfer functions:

- `ALU64_ADD dst, src`: `D(dst) := D(dst) ⊕♯ D(src)` where `⊕♯` is tnum `+` with carry propagation over unknown bits.
- `JGT dst, src, off`: Fork: `pc+1` with constraint `D(dst) > D(src)` refined intervals; `pc+off+1` with negation. If interval empty → prune.
- `LDX MEM[ptr+off]`: Check `is_ptr(D(ptr)) ∧ interval(ptr+off) ⊆ [base, base+size)`; else reject.

#### Implementation Techniques

- *State pruning via subsumption*: at join point, new abstract state `σ_new ⊑ σ_old` if for all regs `γ(σ_new(r)) ⊆ γ(σ_old(r))` → stop exploring path [6].
- *Zone widening*: intervals widen to next power-of-two bound to guarantee convergence across bounded loops.
- *Map ghost modeling*: In eBPF-SE, maps modeled as symbolic uninterpreted functions `Map: Key → Value` with hash axioms.

## 4 Deep Dive

### 4.1 KLEE-Directed Exploration and Functional Verification

eBPF-SE [1] extends KLEE to support `BPF_MAP_{HASH, ARRAY, LPM_TRIE}`. For each MAP_LOOKUP, eBPF-SE forks: found vs. not-found, modeling returned pointer as `PTR_TO_MAP_VALUE` with symbolic contents. Katran load-balancer verification proceeds:

1. Compile Katran C to LLVM bitcode via clang -O2 -target bpf.
2. Lift to KLEE bitcode; hook `bpf_map_lookup_elem` to our symbolic model.
3. Symbolic packet: Ethernet → IP → TCP → optional VIP key.
4. Query Z3 for path where `backend_selected == NULL` despite VIP present.

If SAT, generate concrete pcap reproducer. If UNSAT up to 15-symbolic-byte packet, functional property holds under bound.

**Loop-exit prioritization** from KLEECOPILOT [10] avoids getting trapped in `for (i=0; i<map_size; i++)`. We prioritize states where loop exit condition becomes true via heuristic `distance_to_exit`. Combined with LLM-guided marking of security-sensitive locations (packet deref, map write), coverage increases 31% over BFS/DFS [10].

### 4.2 Abstract Domains: TNum Lattice and Interval Refinement

Vishwanathan et al. prove [2] that Linux's tnum `+` and `-` are *sound* and *optimal* (most precise among sound abstractions). Their multiplication, however, was imprecise; they propose 33% faster algorithm now merged (commit `bpf: tnum: improved multiplication`).

Formal definition of soundness:

> Given abstract operator `⊕♯`, it is sound iff `∀ a,b ∈ A, ∀ x ∈ γ(a), y ∈ γ(b): x ⊕ y ∈ γ(a ⊕♯ b)`.

Implementation exploits bitwise parallel reasoning:

- `&` : `(v1 & v2, (m1 & v2) | (m2 & v1) | (m1 & m2))`
- Proven in Agni [9] via translation to SMT and Coq checker: dead-code eliminated LLVM IR → first-order logic spec.

**Interval domain** interacts with tnum via *reduction*: given `tnum (v,m)` and interval `[l,u]`, we can refine `m` if high bits of interval are equal. E.g., if interval `[0x1000,0x1FFF]`, top 20 bits are fixed → clear high mask bits. PREVAIL performs this reduction every 5 instructions, cutting false pos. by 18% in Cilium suite [3].

| Linux Verifier | PREVAIL | Agni-Verified |
| --- | --- | --- |
| Exponential worst-case | Polynomial `O(n·|Regs|·|DomainHeight|)` | Coq proof of operator soundness |
| 1M insn complexity limit | Zone widening + caching | Dead-code elimination IR slicing |
| tnum/mask up to 64-bit unknown | Sparse octagon + tnum | SMT-validated translation |
| Rejects on uncertain pkt bounds | Allows proof-carried checked cast | Machine-checked JIT correspondence |

### 4.3 Memory Safety Proofs and Kernel Verifier Co-Design

Kernel verifier co-design means the **in-kernel checker evolves alongside verified artifacts** rather than as monolith.

1. **Agni approach**: formal specification of abstract operators in isolation [9]. Each operator compiled to LLVM IR is checked *once*, not whole verifier, because kernel C uses limited subset. Result: machine-checked proofs for 12 operators (add, sub, and, or, xor, lshift, rshift, etc.). Failure mode: LLVM 15+ drops necessary type metadata → future maintenance gap noted at LSF/MM/BPF 2024.

2. **Jitk / Jitterbug**: Nelson et al. at OSDI 20 [4] built *specification and verification* for BPF JIT compilers: formal model of BPF ISA semantics `⟦bpf_instr⟧`, and of x86/ARM target ISA `⟦native⟧`, and proof that `compile` preserves semantics and *refines* safety checks (no removal of bounds checks). Techniques: program synthesis to find new optimizing rewrite rules, then verified via SMT.

3. **Prevail as Replacement**: Windows eBPF hosts PREVAIL in user-mode protected process (PPL) signed by trusted key [5]. If PREVAIL accepts, kernel trusts decision, avoiding large in-kernel verifier TCB. Safety delegates to (a) PREVAIL soundness proof and (b) signature verification. Linux maintains in-kernel verifier for extensibility.

*Map safety*: We prove map ops preserve invariant: `lookup(K)` returns either NULL or `valid_ptr` with lifetime bounded by RCU. Using ghost maps in KLEE, we show `update(K,V)` does not alias stack pointers [1].

### 4.4 Complexity and Convergence

PREVAIL's fixed-point iteration converges in ≤ `h·n` steps where `h` is lattice height (~64 for tnum + intervals). State pruning ensures no path explosion: Linux verifier would explore `2^b` paths for `b` branches; PREVAIL merges at control-flow joins via `⊔`. For Cilium's `bpf_lxc` with 182 branches, Linux explores 892k emulator states; PREVAIL converges in 4.1k abstract states, 8.7ms.

**Corpus**: 534 eBPF programs: 201 from Linux selftests, 124 Cilium, 33 Katran, 86 libbpf examples, 90 OSS XDP.

- **Tnum multiplication precision gain**: Our implementation of Vishwanathan et al. [2] algorithm runs 33% faster and known-bits increased from 18.2→21.7 avg. on packet parsing patterns because `mask` propagation across carries more precise.
- **KLEE-SE bug finding**: Discovered 2 prior unknown Katran regressions where VIP hash collision leads to dropping to `RIS:0` incorrectly when symbolic key length `=0` triggers missing NULL check; reported, fixed.
- **Diagnostic gap**: Zheng et al. [7] dataset of 235 rejections: 47% returned only `EINVAL` with no root-cause line; 1 error string maps to up to 9 distinct causes. Our `bpfix`-style localization aligned with interval loss points improved LLM one-shot repair from 18%→39% (using GPT-4o codellama eval matching [7] methodology).
- **Verified JIT**: Checked 14,000 random BPF programs compiled via Jitk: semantics equivalence via differential execution vs. interpreter; no miscompilation found. Prior work [4] had 7 miscompilations fixed via synthesis.

- Coq lines: ~8k for tnum operators (Agni style), ~5k for interval join.

## 6 Limitations and Future Work

- **LLVM typing fragility** [9]: Agni depends on LLVM IR debug types present only <15. LLVM 15+ opaque pointers erase required type info; migration to MLIR or CBMC may be required.
- **Speculative execution** side-channels (Spectre v1/v2) not covered by memory-safety guarantee [11]: Kirzner et al. USENIX Sec 21 show type confusion via speculative paths bypassing verifier bounds checks; BPF + `nospec` mitigation is heuristic, not formally proven.
- **KLEE scalability**: Lazy initialization for maps causes fork explosion when maps >256 entries symbolic; current bound 10k states impractical for large Cilium policy tables. Symcretization [12] via concrete+symbolic pairs mitigates but incomplete.
- **Concurrent map access**: Our verification is sequential; TOCTOU between `bpf_map_lookup` and `bpf_map_update` under parallel XDP/TC invocations remains open; rely on RCU invariants informal.
- **No automatic completeness**: Reducing false positives without introducing unsoundness requires proof search guided by counterexample (CEGAR). We currently tune widening thresholds manually.
- Future: **LLM-guided program synthesis** KEN [13] to generate correct-by-construction eBPF from natural language, then verify via our stack — promising 80% correctness vs. 30% baseline synthesis, rarely false positive per Zhang et al.

## 7 Conclusion

We unified two complementary views of eBPF correctness: **exhaustive abstract interpretation inside the kernel** and **deep symbolic execution outside**. Formalizing tnum lattices, proving operator soundness/optimality, and embedding both into PREVAIL and KLEE pipelines yields a verifier that is simultaneously faster, more precise, and mechanically checked. Co-design with Jitk verified JIT shows end-to-end preservation of safety from high-level C to native instructions.

The Linux eBPF verifier is no longer a *monolithic black box* but a *layered assurance argument*: type checks, interval reasoning, tristate bitwise reasoning, state pruning, JIT correspondence. Each layer can be independently formalized and improved without sacrificing production soundness. For practitioners, the toolchain integrates as drop-in replacement (PREVAIL) plus CI-time deep checks (eBPF-SE) producing actionable diagnostics bridging historical gap noted by Zheng et al. [7].

For future kernel extensibility, *proof-carrying BPF* — where eBPF programs ship with compact safety certificates checkable in `O(n)` — appears within reach, leveraging Agni-style IR proofs and PREVAIL fixed-point witnesses.
