# Stacked Borrows and Tree Borrows: Formal Aliasing Models for Unsafe Rust

## Abstract

Rust's ownership system guarantees memory safety for safe code, but `unsafe` blocks manipulate raw pointers beyond the borrow checker — while the optimizer still exploits aliasing assumptions through LLVM `noalias` attributes. A sound optimizer therefore needs an operational definition of which unsafe pointer accesses are legitimate, with violations classified as undefined behavior. This thesis compares the two formal aliasing models built to answer that question: **Stacked Borrows**, which equips each memory location with a *stack* of tagged borrow items governed by retagging and protector semantics, and **Tree Borrows**, which replaces the stack with a *tree* of permissions distinguishing foreign from local accesses. We reconstruct both models' mechanics — tags, validity invariants, protectors, permission lattices — alongside their mechanized soundness proofs in Coq and Rocq, and trace their empirical validation in Miri over the standard library and 30,000 crates. We explain why Tree Borrows rejects 54% fewer real-world tests while preserving nearly all proven optimizations and enabling read–read reordering, and situate both models within the Unsafe Code Guidelines effort and the MiniRust semantics.

## 1 Introduction

Rust's ownership and borrowing discipline is among the most consequential ideas in modern language design: affine types and borrow-checked references deliver memory safety and data-race freedom *without* a garbage collector. For safe code the guarantees are enforced statically, and the compiler is entitled to exploit them aggressively. Mutable references `&mut T` are unique; shared references `&T` are immutable. An optimizer that hoists a read of `*x` above a call to an opaque function `f()` is justified by the mere type of `x`: no aliasing write can exist, because the type system would have rejected it.

The difficulty begins at `unsafe`. Raw pointers, unchecked casts, and arbitrary address arithmetic all escape the borrow checker — yet the optimizer keeps going, deriving LLVM `noalias` and `dereferenceable` attributes from reference types regardless. For these optimizations to be *sound*, violations of the aliasing discipline must be classified as **undefined behavior** (UB): the compiler then need only preserve the semantics of UB-free programs [1].

Stacked Borrows, by Jung, Dang, Kang, and Dreyer (POPL 2020) [1], answers with an *operational semantics* for memory accesses: an executable aliasing discipline, implemented in the Miri interpreter, that declares certain pointer-access patterns UB. Mechanized Coq proofs show the discipline justifies the reorderings compilers actually perform, and runs of large parts of the standard library test suite under Miri validate that it admits real-world unsafe code [1]. Jung's dissertation extends the retagging and protector machinery [2]; the "Stacked Borrows 2" notes pin down the precise stack invariants [3].

But Stacked Borrows proved too strict: idiomatic patterns — two-phase borrows, `container_of` pointer arithmetic, interior mutability through raw pointers, certain raw-pointer casts — were flagged as UB, eroding trust in Miri as an arbiter [4]. **Tree Borrows** (Villani, Hostert, Dreyer, Jung; PLDI 2025 [5]) replaces the per-location *stack* with a *tree* of permissions, distinguishes *foreign* from *local* accesses, and rethinks retagging, protectors, and initialization. Over the 30,000 most widely used crates it rejects 54% fewer test cases while retaining most proven optimizations and enabling read–read reordering; it earned a Distinguished Paper Award at PLDI'25 [6], with the full development in Villani's thesis [7].

This thesis reconstructs both models from first principles, compares their mechanics and metatheory, surveys their empirical validation, and situates them in the standardization effort — the Unsafe Code Guidelines working group [8] and the MiniRust semantics — that will decide which rules become *the* definition of Rust.

> **Theorem (Informal, SB soundness):** *Under the Stacked Borrows operational semantics, hoisting a read (resp. write) through a reference across an unknown function call is semantics-preserving for all programs that do not themselves exhibit Stacked Borrows UB [1].*

The remainder of this thesis is organized as follows. Section 2 reviews the background: Rust's aliasing guarantees, the role of UB as an optimization license, Miri as executable semantics, and the Unsafe Code Guidelines process. Section 3 describes our methodology: a comparative reconstruction of the two models from the primary sources, grounded in the published mechanizations and evaluation data. Section 4 is the deep dive — retagging and tags, the borrow stack versus the permission tree, protectors and two-phase borrows, validity invariants, and interior mutability. Section 5 presents the empirical and formal results: what each model proves, what each model rejects, and the 54% figure. Section 6 discusses limitations and open questions, and Section 7 concludes.

## 2 Background

### 2.1 Aliasing, optimization, and the meaning of UB

In C, `restrict` and the effective-type rules try to tell the compiler which pointers may alias, but the rules are so subtle that programmers and compiler writers routinely disagree. Rust enforces aliasing discipline *statically* for safe code, so the optimizer's assumptions hold by construction. The open question — occupying the Unsafe Code Guidelines (UCG) working group for years — is what the optimizer may assume about *unsafe* code [8].

The community's answer is operational: define an abstract machine in which certain executions get *stuck* with a UB error, and justify optimizations as refinements preserving the observable behavior of UB-free executions. This "UB as license" reading makes the aliasing model the most load-bearing definition in unsafe Rust — simultaneously a bug-finding oracle, a contract for unsafe authors, and the optimizer's proof obligation.

### 2.2 Miri: executable semantics

The Stacked Borrows project implemented its semantics in **Miri**, an interpreter for Rust MIR that tracks per-location borrow state and reports UB the moment it occurs [9]. Miri runs in the CI of the standard library and many major crates, and a recent POPL paper validates it as "the first tool that can find all de-facto undefined behavior in deterministic Rust programs" [9]. Crucially, Miri supports both models — Stacked Borrows by default, Tree Borrows via `-Zmiri-tree-borrows` [6] — making it the shared experimental apparatus: claims like "54% fewer rejections" are measured by running both instrumented interpreters over the same corpus.

### 2.3 The Unsafe Code Guidelines and MiniRust

The UCG working group maintains the long-running design discussion of what unsafe Rust *means*, including the validity invariants — alignment, non-nullness, initialization — every reference must satisfy at creation [8]. In parallel, **MiniRust** develops a small, precise formal semantics for a Rust fragment, intended as the eventual normative core. The aliasing models slot into MiniRust as the memory-access layer, deliberately separated from evaluation: validity is checked at reference creation while borrow state evolves per access, so the two concerns can be specified and proved about independently [2].

| Concern | Checked when | Owned by |
|---|---|---|
| Validity invariants (aligned, non-null, initialized) | Reference creation / retag | UCG validity discussion [8] |
| Aliasing discipline (stack/tree transitions) | Every memory access | Stacked/Tree Borrows [1][5] |
| Protectors (no invalidation during call) | Function entry/exit | Both models [1][5] |
| Data-race freedom | Concurrent accesses | Borrow checker + model [2] |

### 2.4 What the models must achieve

Any candidate model faces three demands: **strong enough** to justify rustc's actual optimizations, **permissive enough** to accept the unsafe code the ecosystem writes, and **precise enough** for a dynamic checker with comprehensible errors. Stacked Borrows maximized the first and learned, through Miri deployment, that it had sacrificed too much of the second. Tree Borrows rebalances — recovering permissiveness without surrendering the optimizations that matter [4][5].

## 3 Methodology

This thesis is a comparative reconstruction, not a new experiment: the empirical results we report are those published by the model authors, and our contribution is to systematize them, verify the internal consistency of the claims across sources, and draw out the implications for unsafe-code authors and for the standardization process.

Our method has four parts. **First**, reconstruct Stacked Borrows' operational rules from the POPL 2020 paper [1], Jung's dissertation [2], and the Stacked Borrows 2 notes [3], cross-checking informal presentations against the mechanized definitions. **Second**, reconstruct Tree Borrows from the PLDI 2025 paper [5], Jung's 2023 announcement [4], the ETH summary [6], and Villani's thesis [7], attending to deliberate divergences (raw-pointer retagging, lazy initialization, the conflicted flag). **Third**, compare along fixed axes — state representation, access checking, function boundaries, two-phase borrows, interior mutability, proven optimizations, measured false-positive rates. **Fourth**, situate both within the UCG validity discussion [8] and Miri validation literature [9], separating answered questions from open ones.

We take the published mechanizations and evaluation corpora at face value but verify every quantitative claim against at least two independent sources.

## 4 Deep Dive

### 4.1 Tags and retagging: how permissions are born

Both models share a foundation: every pointer value carries an opaque **tag** naming its borrow, and creating a reference performs a **retag** — conceptually `x = &mut *x` — minting a fresh tag and installing the permission in the model's state [1][3]. The compiler inserts retagging automatically: reference-typed arguments are retagged on entry, every explicit reborrow retags [2]. The tag travels with the pointer *value* in memory; the permission state lives *per location*; the two evolve independently [3][10].

In Stacked Borrows, retagging pushes `(tag, permission)` onto each affected location's stack, popping incompatible items above [3]. In Tree Borrows, it creates a *child node* under the parent's node with a type-determined initial permission [5]. The stack is a total order — every new borrow invalidates everything above; the tree is a partial order whose sibling subtrees evolve independently.

```rust
fn demo() {
    let mut x: i32 = 0;
    let r1: &mut i32 = &mut x;   // retag: fresh tag t1, permission Unique
    let p: *mut i32 = r1 as *mut i32; // raw cast: retagging differs by model!
    let r2: &i32 = &*r1;          // retag: fresh tag t2, SharedReadOnly (SB)
    unsafe { *p = 42; }           // legal? the models disagree — see §4.2
}
```

### 4.2 The borrow stack versus the permission tree

**Stacked Borrows.** Each location owns a stack of items granting `Unique`, `SharedReadWrite`, `SharedReadOnly`, or `Disabled` [3], with strict invariants: above `SharedReadOnly` only more `SharedReadOnly`, and no tag twice [10]. An access is legal only if the pointer's item remains in the stack with compatible permission. Conflicting accesses pop: writing through `Unique` pops `SharedReadOnly` items above it, and touching a popped item is UB. Borrows nest LIFO — using a borrow after a conflicting borrow is an error [1][3].

The stack's elegance is also its brittleness. Consider two-phase borrows — the borrow checker's mechanism for method-call receivers like `vec.push(vec.len())`, where the mutable borrow is created but not *activated* until the call. Stacked Borrows has no notion of an unactivated borrow: every `&mut` retag immediately installs `Unique` and invalidates everything above [4]. Real code that the borrow checker accepts is therefore rejected by Miri. Similarly, casting `&mut T` to `*mut T` downgrades the permission to `SharedReadWrite`, and casting to `*const T` makes the pointer *read-only even if the reference was mutable* — a constant source of confusion, since programmers reasonably expect `*const` vs `*mut` not to affect aliasing [4]. Pointer arithmetic across array elements or struct fields after a field-level retag is likewise UB, because the raw pointer is confined to the type and range it was created with [4].

**Tree Borrows.** Each location keeps a *tree* of permission nodes — `Reserved`, `Active`, `Frozen`, `Disabled` — and accesses are **local** (through the node or its descendants, ↓) or **foreign** (outside its subtree, ↑) [5]. Local accesses strengthen toward `Active`; a foreign write disables; a foreign *read* merely freezes to `Frozen`. Sibling subtrees evolve independently, so a foreign read no longer destroys a mutable borrow — which is exactly what enables the read–read reordering Stacked Borrows cannot justify [5].

Three further design decisions widen the gap:

1. **No retagging on reference-to-raw-pointer casts.** Under TB, a raw pointer simply inherits its parent reference's tag, mutability, and address range. The `*const`-from-`&mut` read-only trap disappears [4].
2. **Lazy initialization of access ranges.** A new reference records an initial range from its type, but accessing outside that range is permitted if the *parent* pointer could access it — checked recursively up to the root. This makes `container_of`-style arithmetic and `extern` types legal [4].
3. **Foreign/local distinction for protectors.** Protectors (see §4.3) are expressed naturally as constraints on foreign accesses rather than stack pops.

| Aspect | Stacked Borrows [1][3] | Tree Borrows [4][5] |
|---|---|---|
| State per location | Stack of `(tag, perm)` items | Tree of permission nodes |
| Permissions | Unique, SharedReadWrite, SharedReadOnly, Disabled | Reserved, Active, Frozen, Disabled |
| Access classification | Granting-item lookup + pops | Foreign (↑) vs local (↓) transitions |
| Foreign read vs `&mut` | Pops / UB | Freezes to `Frozen` |
| Raw-pointer cast | Retagged, range-confined | Inherits parent tag and range |
| Two-phase borrows | Not modeled (UB) | `Reserved` until activation |
| Out-of-range access | UB | Lazy initialization via parent |

> **Theorem (Informal, TB read–read reordering):** *Starting from an arbitrary permission state, executing two consecutive reads through distinct mutable references in either order reaches the same final state; hence the reordering is semantics-preserving [5]. Stacked Borrows admits no such theorem.*

### 4.3 Protectors, two-phase borrows, and the conflicted flag

Retagging alone cannot justify optimizations across *unknown* code: an opaque `f()` might write through a smuggled alias. **Protectors** close the gap — each reference argument is retagged *and protected* on entry, so any access invalidating the protected item (a stack pop, a tree-node disable) is UB for the call's duration [1][2]:

```rust
fn caller(x: &mut i32, f: impl FnOnce()) {
    // retag[fn] x  — x is retagged AND protected on entry
    *x = 42;
    f();        // opaque call: cannot touch x (protector)
    *x = 13;    // optimizer may keep only this write — or only the first
}
```

Since `f` cannot legally invalidate `x`'s item, the compiler may move writes across the call freely — observable behavior of UB-free programs is unchanged [2]. Protectors are the mechanism behind LLVM's `noalias` on reference parameters.

Tree Borrows refines protectors twice. First, a *protected* `&mut` always starts `Reserved`, regardless of interior mutability — activation is deferred until a local write, faithfully modeling two-phase borrows [5]. Second, TB adds the **conflicted** flag: a *foreign read* before the activating local write marks the node conflicted, making the later write UB [5]. Net rule: *for a protected mutable reference, a foreign read plus a local write — in either order — is UB.* This justifies hoisting a write above an unknown call even for never-written references, closing the hole naive "mutable implies writable" reasoning would open [5].

### 4.4 Validity invariants and interior mutability

Aliasing is half the story. The UCG validity discussion separates *bit-level* reference properties — non-null, aligned, initialized — from the access discipline [8]. Subtly, *dereferenceability* is asserted by `Retag`, not by the validity check at assignment: this keeps validity independent of memory state, at the cost of making retag the operation that fails on dangling references [8].

Under Stacked Borrows, `&Cell<T>` retags as `SharedReadOnly`; mutation must flow through the raw-pointer `SharedReadWrite` item derived from the `UnsafeCell`, demanding careful protector handling since protected shared references otherwise forbid writes [2]. Under Tree Borrows, the uniform `Reserved` start extends to interior-mutable types, and the foreign/local distinction lets shared references tolerate exactly the writes `UnsafeCell` exists to permit [5]. The upshot, confirmed in §5: Tree Borrows accepts substantially more interior-mutability idioms.

## 5 Empirical Results / Formal Analysis

### What is proven

Stacked Borrows was mechanized in **Coq**: the POPL 2020 paper proves the model justifies moving reads and writes across unknown calls via purely intraprocedural reasoning [1]. Tree Borrows was mechanized in **Rocq**, retains most SB optimizations, and adds read–read reordering [5][6]. One asymmetry: Stacked Borrows justifies inserting and reordering writes *without regard for the activating write* — a consequence of treating every `&mut` as immediately `Unique`. Tree Borrows is deliberately conservative: a reference counts as writable only once written, so collapsing a conditional increment loop into one addition is not generally valid [5]. Neither model is a pure relaxation of the other.

### What is rejected: the 54% figure

The headline result is a differential evaluation over the test suites of the **30,000 most widely used crates** under Miri: Tree Borrows rejects **54% fewer test cases** than Stacked Borrows [5][6]. The eliminated rejections cluster exactly on the §4.2 patterns: two-phase borrows, raw-pointer casts with arithmetic, `container_of` idioms, interior mutability through shared references [4][5]. Stacked Borrows' original validation ran large parts of the standard library suite and found only six violations in the architecture-independent portion — all fixed — suggesting it fit the standard library but not the wider ecosystem [1].

### Miri as the ongoing experiment

Miri remains the shared laboratory — SB by default, TB via `-Zmiri-tree-borrows` — so each new dispute about an unsafe idiom is adjudicated by running both [6]. The POPL 2026 Miri paper calls it the first tool capturing all de-facto UB of deterministic Rust programs [9]. Every model change is thus immediately falsifiable against the corpus — which is how Tree Borrows earned adoption: not by authority, but by rejecting fewer real programs while keeping the optimizer's proof obligations.

## 6 Limitations

**Neither model is final.** Both are *proposals* awaiting UCG and MiniRust; data races are largely out of scope — the TB proofs never needed to reason about them since protectors already induce enough UB [5] — and atomics, inline assembly, and FFI boundaries (where LLVM's own aliasing rules apply) are unaddressed.

**Tree Borrows gives up real optimizations.** The write-insertion/reordering family SB justifies is unsound under TB's lazy `Reserved` semantics [5]. Whether performance-critical code depends on them is an open empirical question; a "strong mode" recovering them at the cost of new UB is already being explored [5].

**The corpora are test suites, not proofs.** "54% fewer rejections" counts Miri test executions: untested paths are invisible and Miri's determinism under-samples concurrency [9][5]. The long tail of crates was never exhaustively adjudicated under SB — which is why the TB evaluation mattered.

**Validity is unresolved.** Whether references must always point to *valid* data, how uninitialized bits interact with retagging, and the exact dereferenceability contract remain open UCG design questions [8].

---

## 7 Conclusion

Stacked Borrows and Tree Borrows answer the same question — *what may unsafe Rust do with a pointer?* — separated by five years of deployment experience. SB established the methodology: an operational, executable discipline with mechanized optimization proofs and standard-library validation [1][2][3]. TB kept the methodology and replaced the central data structure, trading LIFO elegance for a tree distinguishing foreign from local accesses, modeling two-phase borrows, and tolerating the ecosystem's raw-pointer idioms [4][5][7] — rejecting 54% fewer test cases, preserving nearly all proven optimizations, adding read–read reordering, and earning a Distinguished Paper Award at PLDI'25 [6].

The deeper lesson is institutional: there is no *correct* rule set to be proved, only a design to validate against proof obligations and real code [1]. The models are instruments in an ongoing negotiation between compiler writers, unsafe authors, and the UCG working group [8] — conducted empirically, in Miri, one rejected test case at a time [9]. Until MiniRust converges on a normative semantics, the responsible position is conservative: write code *both* models accept, run Miri in CI with both flags, and treat each new rejection as data about where the language is heading.
