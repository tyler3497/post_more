# Composing Sandboxed Universes: The WebAssembly Component Model, WASI 0.3, and the Formal Foundations of Portable Polyglot Modules

## Abstract

The WebAssembly Component Model, paired with the WASI 0.3 release of June 2026, is the most consequential reformulation of portable software composition since the dynamic linker. This thesis treats the model's four interlocking pillars: **interface types** — a value-level type algebra for cross-language data; the **canonical ABI**, a total function from interface types to core WebAssembly value sequences with provable memory-safety invariants; **WIT bindings generation**, whereby one interface description mechanically yields idiomatic Rust, Python, Go, and JavaScript bindings; and **capability-based sandboxing**, in which unforgeable resource handles instantiate deny-by-default authority. We trace the shift from WASI 0.2's polling ceremony to WASI 0.3's native async primitives — `async` functions, `stream<T>`, `future<T>` — which relocate event-loop ownership from guests to the host and render cross-component async composition tractable [1][3][4]. We formalize the lift/lower calculus, exhibit representative WIT specifications and generated bindings, and survey the ecosystem, including Wasmtime 46's default 0.3 support [4].

---

## 1. Introduction

Software composition has long been an accident of shared toolchains. A Python program invoking a Rust library crosses a foreign-function interface negotiated in C, with manual lifetime discipline, incompatible string encodings, and *ad hoc* error conventions. A Go microservice talking to a JavaScript handler marshals through serialized JSON over HTTP, paying a latency and allocation tax at every boundary. In each case the *module boundary* is a site of incidental complexity rather than a locus of semantic design.

The WebAssembly Component Model proposes instead that the module boundary be given a first-class, mathematically grounded semantics. Building on the WebAssembly core specification — a typed, stack-based virtual machine with formally specified validation and execution [2] — the Component Model adds a *component layer*: modules declare typed imports and exports drawn from a rich **interface-type algebra** (records, variants, options, results, lists, tuples, flags, enums, opaque *resources*) rather than the core module's meager numeric signatures. Components link through a **canonical ABI** defining byte-for-byte how high-level values flatten into linear memory and reconstruct on the other side. Interfaces are authored once in **WIT** (Wasm Interface Types) and compiled to language bindings by generators such as `wit-bindgen` and `jco`. Because components touch the outside world only through explicitly granted **capability handles**, the model instantiates a capability-security discipline: authority is deny-by-default, unforgeable, and attenuatable [5].

WASI is the flagship consumer. WASI 0.1 exposed POSIX-flavored imports to core modules; WASI 0.2 (January 2024) rebased WASI onto the Component Model with WIT interfaces and cross-language composition [6]; WASI 0.3, ratified **June 11, 2026**, completes the asynchronous turn — `async` functions, `stream<T>`, and `future<T>` as canonical-ABI primitives, removal of `wasi:io`, restructuring of `wasi:http`, and relocation of the event loop from each guest into the host runtime [3][4]. Each layer exists to make the next implementable.

> **Theorem:** *The Component Model's four pillars — interface types, the canonical ABI, WIT binding generation, and capability-based sandboxing — are mutually necessary: removing any one collapses portability, expressiveness, usability, or security.*

## 2. Background

### 2.1 From core modules to components

A core module exposing a string-typed function must encode it as an `(i32, i32)` pointer-length pair, leaving allocation convention, encoding, and deallocation to out-of-band documentation — the *convention problem*. The Component Model stratifies the binary format: components embed core modules and describe interface types in a dedicated component type section. The canonical ABI then defines, for every interface type `t`, two directions of translation:

- **Lowering** `↓ₜ : t → (i32 | i64 | f32 | f64)*` — flatten a high-level value into core values (or linear memory, when the flattened size exceeds the calling convention's capacity).
- **Lifting** `↑ₜ : (i32 | i64 | f32 | f64)* → t` — reconstruct the value, with validation (UTF-8 checks, discriminant bounds, handle-table lookups).

Both are specified as total functions over validated inputs, so a Rust component and a Python component exchange `list<record{name: string, score: f64}>` with neither knowing the other's representation [2].

### 2.2 WIT: the interface description language

WIT declares *packages* (`namespace:package@version`, e.g. `wasi:clocks@0.3.0`), *interfaces* (types plus functions), and *worlds* (a component's complete import/export contract) [1]. Beyond primitives and constructors (`record`, `variant`, `enum`, `flags`, `tuple`, `list`, `option`, `result`), WIT provides **resources**: opaque handles with owned (`own<T>`) and borrowed (`borrow<T>`) semantics. Resources are capabilities-as-types — a WASI 0.3 file descriptor is not an integer into a process-global table but an unforgeable `own<descriptor>` whose possession constitutes authority [5].

### 2.3 A brief history of WASI

| Release | Date | Model | Defining characteristic |
|---|---|---|---|
| WASI 0.1 (P1) | 2020–2023 | Core module imports | POSIX-like syscalls; broad runtime support |
| WASI 0.2 (P2) | Jan 2024 | Component Model + WIT | `wasi:io` with `pollable` and streams; per-component event loops; `start`/`finish`/`subscribe` async ceremony |
| WASI 0.3 (P3) | Jun 2026 | Native async ABI | `async func`, `stream<T>`, `future<T>`; `wasi:io` removed; `wasi:http` 11 → 5 resources; host-owned single event loop [3][4] |
| WASI 0.3.1 | Aug 2026 | 0.3 + extensions | `map<K, V>` type; `implements` and `external-id` annotations [4] |

The 0.2 → 0.3 migration is conceptually clean: `pollable` → `future<T>`, `input-stream`/`output-stream` → `stream<u8>`, `subscribe()` → returning a `future`, `start`/`finish` → `async func` [3]. Migration is optional: Wasmtime's `wasmtime serve` dispatches 0.2 and 0.3 components from one binary, and 0.3 runtimes may polyfill 0.2 imports at the host boundary [5].

## 3. Methodology

This thesis is analytic and constructive. We reconstruct the design from primary sources — the Component Model specification (`design/mvp/WIT.md`, `design/mvp/CanonicalABI.md`, the Concurrency explainer), Bytecode Alliance documentation, WASI 0.3 release notes, and contemporary engineering analyses [1][2][3][4][7] — and validate the reconstruction three ways:

1. **Formal exposition.** The lift/lower calculus as a definitional translation, with the memory-safety and determinism invariants it must preserve stated as checkable theorems.
2. **Constructive demonstration.** Representative WIT interfaces with schematic `wit-bindgen` (Rust) and `jco` (JavaScript) output, showing one description yields *idiomatic* code per language.
3. **Empirical survey.** Ecosystem state as of late 2026: Wasmtime 46's default 0.3 support, `wit-bindgen` async Rust bindings, `jco`'s experimental Node.js shim, Rust's Tier 3 `wasm32-wasip3` target, and shared `wasi-testsuite` conformance [4].

We do not claim mechanized verification of the full specification; that remains an open research program (§6).

## 4. Deep Dive

### 4.1 Interface types: a value algebra for the module boundary

Interface types form a first-order algebraic data language closed under constructors chosen to be (a) expressive enough for real system interfaces, (b) simple enough that every guest language can implement lift/lower, and (c) total, so boundary validation is decidable:

- **Records** — flattened field-wise with C-like alignment via the standard `align_up` recurrence.
- **Variants** — discriminant plus payload union; lifting validates the discriminant, converting memory-safety violations into *traps*.
- **`option<T>` / `result<T, E>`** — variant specializations; `result` is the canonical error channel, with WASI 0.3 standardizing `error-context` [3].
- **`list<T>`** — pointer-length pair into canonical linear memory; the primary bulk-transfer mechanism.
- **`flags` / `enum`** — bitfields and constants with bounds-checked lifting.
- **Resources** — the *capability* constructor. `own<T>` handles transfer ownership across boundaries; `borrow<T>` handles are call-scoped. The runtime keeps a per-instance handle table (free-list allocator, bounded at 2²⁸ − 1 entries) and guarantees borrows never outlive their lender [1].

The payoff appears in WASI 0.3's own interfaces, where asynchrony moved from explicit `pollable` resources into the type system itself:

```wit
package wasi:http@0.3.0;

interface handler {
  use types.{request, response};
  /// The host drives scheduling; the body arrives as a byte stream
  /// and trailers resolve through a future.
  handle: async func(req: request, body: stream<u8>)
    -> tuple<response, stream<u8>, future<result<option<trailers>>>>;
}
```

`async`, `stream<u8>`, `future<…>` are *canonical-ABI primitives*, not library types [2][3]: the type system grew exactly the constructors needed to make the host, rather than each guest, the owner of concurrency.

### 4.2 The canonical ABI: lifting, lowering, and the memory-safety contract

The canonical ABI's core judgments are *flattening* (interface type → core value list), *size/alignment computation*, and the *lift*/*lower* translations, organized around three invariants:

1. **Determinism.** Lower-then-lift is the identity on well-typed values (up to handle renaming).
2. **Memory safety.** Lifting validates discriminants, UTF-8 sequences, handle-table indices, and list bounds before constructing values; invalid encodings trap. The guest can never be tricked into misinterpreting memory because the translation — performed by the host or importing side — is the trusted computing base of the boundary.
3. **Isolation.** Components are *shared-nothing* by default: disjoint linear memories, values crossing only through canonical translation. This is the foundation of §4.4's sandboxing.

A schematic Rust lowering for `record point { x: f64, y: f64 }` with `distance: func(a: point, b: point) -> f64`:

```rust
#[repr(C)]
struct Point { x: f64, y: f64 } // layout matches canonical ABI

unsafe extern "C" fn __lower_distance(a: Point, b: Point) -> f64 {
    // flatten: (f64, f64, f64, f64) fits core params — no memory pass
    let r = distance(a, b);              // idiomatic Rust call
    core::ptr::write(RET_AREA as *mut f64, r);
    r
}
```

Oversized signatures switch to the *indirect* convention (caller-allocated buffer, address passed instead); strings lower as `(ptr, len)` with a specified encoding, negotiated through the ABI's *realloc* protocol so neither side trusts the other's allocator blindly [2].

> **Theorem:** *Canonical-ABI lifting is a total, decidable validation function: for every interface type `t` and core sequence `v` of the flattened shape of `t`, `↑ₜ(v)` yields a well-typed value of `t` or traps. No ill-typed value is ever constructed.*

Interface validation is therefore not the guest's job: a malicious component cannot smuggle a malformed string or forged handle past the boundary, because the boundary is a verified translator.

### 4.3 WIT bindings generation: one interface, idiomatic everywhere

Generators — `wit-bindgen` (Rust, C, Go), `jco` (JavaScript/TypeScript), community backends for Python, Java, C# — consume one WIT package and emit code that calls the canonical ABI's `canon.lift`/`canon.lower` builtins while wrapping raw values in idiomatic constructs. From:

```wit
package example:geometry@1.0.0;
interface shapes {
  record point { x: f64, y: f64 }
  distance: func(a: point, b: point) -> f64;
}
world app { import shapes; export run: func() -> result<_, string>; }
```

a Python generator produces code that never exposes linear memory:

```python
from example.geometry import shapes

def run() -> None:
    a = shapes.Point(x=0.0, y=0.0)
    b = shapes.Point(x=3.0, y=4.0)
    d = shapes.distance(a, b)   # crosses into the Rust component
    assert abs(d - 5.0) < 1e-9
```

Generated `distance` lowers two records (flattened to four `f64` params), invokes the imported canonical function, and lifts the result; error paths use each language's idiom — Rust `Result`, Python exceptions, JavaScript rejected promises for `async` functions [7].

WASI 0.3 raises the bar: generators must emit *idiomatic async*. `wit-bindgen` maps `async func` to Rust `async fn` driven by the host executor, `stream<u8>` to an async byte-stream, `future<T>` to an awaitable handle — absorbing the impedance mismatch between the component task model and the host language's async runtime so the programmer never sees it [3][4]. Composition then follows from canonical world names (`wasi:http/handler@0.3.0`): a Rust router, Python middleware, and Go service link by matching exports to imports, with the ABI translating at every edge [1].

### 4.4 Capability-based sandboxing: authority as unforgeable handles

The Component Model realizes the **object-capability** paradigm (Dennis and Van Horn; KeyKOS, EROS, seL4) in a practical artifact: authority is designated by unforgeable references, and subjects may perform only operations their references authorize. The references are resource handles; the subjects are component instances. Three properties make the discipline airtight where POSIX sandboxing never was:

1. **Deny by default.** An instance starts with authority over nothing but its own memory and its world's declared imports — no ambient filesystem, network, or global fd table. WASI 0.3's removal of `wasi:io` shrinks ambient surface further: former resources are now ABI-native values whose transfer the ABI tracks [3].
2. **Unforgeability.** Handles are per-instance table indices managed by the runtime; guessing an integer fails because lifting validates every handle operand and traps on unknown entries (§4.2, Theorem). `own<T>` moves the entry; `borrow<T>` creates a scoped alias invalidated at call return.
3. **Attenuation by construction.** A component holding `own<descriptor>` for a directory can derive only what the host's interface permits — e.g., opening files *beneath* it — never amplifying to the parent. WASI's filesystem signatures make authority requirements explicit, so attenuation is *visible in the type signature* and auditable by inspection [5].

Contrast WASI 0.1: integer fds inherit the confused-deputy hazards of the POSIX tradition. The Component Model replaces integer authority with *typed* authority, with the canonical ABI's total validation as the runtime mechanism keeping the typing honest.

### 4.5 WASI 0.3's async turn: one event loop to rule the composition

WASI 0.2's asynchrony was *component-local*: each component ran its own event loop behind `wasi:io/poll` readiness interfaces. That composed poorly — two components' loops could not coordinate, and a stream produced by one could not be awaited by another without out-of-band polling protocols [3]. WASI 0.3 inverts responsibility with three canonical-ABI primitives:

- **`async func`** — receives both synchronous and non-blocking core signatures, so sync callers invoke async callees (and vice versa) with no convention adoption [2].
- **`stream<T>` / `future<T>`** — owned, resource-like, non-borrowable handles; ownership transfers across boundaries. Stdin/stdout/stderr become `stream<u8>`; completion signals become `future<T>`.
- **Host-driven, completion-based scheduling** — the runtime owns the single event loop; delivering a value to a `future` schedules its awaiter even across component boundaries. Completion-based (in the spirit of `io_uring`/IOCP), with readiness polling emulatable atop for compatibility [3].

The consequences are immediate: `wasi:http` collapses 11 resources to 5, request handling becoming one `async func` whose body is a `stream<u8>` and whose trailers resolve via `future`; the per-component executor tax disappears; and backpressure becomes a first-class, cross-component phenomenon mediated by the runtime's flow control rather than ad-hoc guest protocols [2][5].

### 5.2 Proof sketches

> **Theorem (Boundary integrity):** *If every cross-component transfer passes through canonical-ABI lifting, no component can observe or mutate another's linear memory, regardless of source language.*

*Sketch.* Instances receive disjoint linear memories; core semantics offers no instruction naming another instance's memory. The sole cross-instance flow is lift/lower, which copies *values* — never references — into freshly validated representations. Lifting validates all bounds, discriminants, encodings, and handle indices, trapping on violation; no malformed encoding can induce type confusion aliasing foreign memory. ∎

> **Theorem (Capability confinement):** *An instance's authority at any step is a subset of the transitive closure of capabilities granted by its world's imports and subsequently received through calls.*

*Sketch.* Authority is exercised only through resource handles — unforgeable (table validation, §4.2) and transferred solely by explicit `own` moves or scoped `borrow`s across typed boundaries. Initial authority is exactly the world's imports; each transfer is runtime-recorded, so reachable authority evolves only by the two permitted operations, both preserving the subset property. ∎

These are sketches, not mechanized proofs — but they are sketches *of the right theorems*, itself evidence of the design's coherence: the enforced invariants are the ones one would write down first.

## 6. Limitations

1. **Streaming error semantics.** Mid-transfer `stream<u8>` failure must propagate to readers, writers, and every component the stream traversed; the compositional ordering of partial-stream failure remains under-specified relative to the synchronous ABI's totality [3].
2. **Resource cycles.** Cross-component `own<T>` cycles have no specified collection discipline; reclamation depends on runtime-specific tracing.
3. **Generator verification.** The security argument rests on generated bindings faithfully implementing lift/lower. A bounds-check bug in `wit-bindgen` would puncture boundary integrity for every component built with it. A verified-compiler treatment of the canonical-ABI translation (à la CompCert) is the field's most important open engineering problem.
4. **Async cancellation.** Abandoning a task awaiting a `future` must deterministically reclaim its streams, borrows, and buffers; host implementations diverge on edge cases [2].
5. **Performance transparency.** Deeply nested `list<record<…>>` values pay per-element validation and copying — a deliberate throughput-for-isolation trade whose magnitude needs systematic benchmarking.
6. **Linking maturity.** Canonical names promise cross-version linking, but version-aware composition tooling lags; practitioners still pin toolchains manually [4].

---

## 7. Conclusion

The Component Model with WASI 0.3 reads as one argument in four movements. **Interface types** give the module boundary a semantics worth having. The **canonical ABI** makes it executable with total, validated translations. **WIT bindings generation** makes it programmable idiomatically in every major language. **Capability-based sandboxing** makes the composition trustworthy — the only authority is explicitly granted and mechanically unforgeable. WASI 0.3's async turn removes the last structural obstacle to composing asynchronous components: with scheduling unified under the host, the component graph becomes a *single concurrent program* rather than a federation of mutually suspicious event loops [3][4].

The frontier is clear: mechanize the metatheory, verify the generators, specify streaming failure compositionally, and measure the isolation tax honestly. Executed well, the Component Model will do for software composition what WebAssembly did for portable execution — replace convention with specification, and folklore with proof.
