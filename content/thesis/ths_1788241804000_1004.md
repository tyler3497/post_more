# In-Network Computing with P4 Programmable Data Planes: In-Band Network Telemetry, Consensus Protocol Acceleration, and Stateful Packet Processing under Match-Action Constraints

## Abstract

Programmable data planes expressed in P4 have transformed network switches from fixed-function forwarders into line-rate stream processors capable of executing application logic directly on packets in flight. This thesis investigates three pillars of *in-network computing*: in-band network telemetry (INT), which embeds fine-grained measurement collection into the forwarding path at microsecond resolution; consensus protocol acceleration, which relocates Paxos acceptor and coordinator logic into switch hardware to collapse coordination latency; and stateful packet processing, which exploits on-chip registers, meters, and stateful arithmetic-logic units to maintain persistent per-flow state across packets. We formalize the match-action execution model, analyze its fundamental constraints — bounded single-pass pipelines, atomic read-modify-write semantics, absence of unbounded iteration, and scarce SRAM/TCAM budgets — and show how these constraints shape protocol design. Drawing on NetPaxos, CAANS, SwitchML, and lightweight INT schemes, we derive telemetry overhead bounds, safety arguments for register-based acceptors, and throughput models for in-network aggregation, closing with limitations: deployability, trust, arithmetic expressiveness, and control-plane fallback.

## 1 Introduction

For two decades, switches forwarded packets and end hosts ran applications. SDN centralized control logic, yet the data plane remained fixed in silicon — until P4 [1] and the protocol-independent switch architecture (PISA) made forwarding behavior itself a program: parser, match-action tables, and deparser compiled from a high-level description and reconfigurable in the field.

*In-network computing* asks what follows: if a switch executes match-action programs at terabits per second, why should application logic live only at the endpoints? The network sits on every path and reacts in nanoseconds. Three lines of work test this thesis at increasing levels of ambition. **In-band network telemetry** uses data-plane programmability to collect per-packet, per-hop measurements — queue occupancy, hop latency, switch identifiers — without control-plane intervention [2]. **Consensus acceleration** pushes further, implementing the logic of Paxos acceptors, coordinators, and learners in network devices so that agreement is reached at line speed with latency barely above packet forwarding [3][4]. **Stateful packet processing** provides the substrate: registers, counters, meters, and stateful ALUs that let the data plane remember, aggregate, and decide across packets [6].

This thesis makes four contributions:

1. A unified formalization of the P4 match-action execution model and its stateful extensions, identifying the precise constraints — single-pass pipelines, atomic read-modify-write, bounded iteration, limited arithmetic — that any in-network computing design must respect.
2. A technical exposition of in-band network telemetry, including the INT-MD/INT-MX/INT-XD modes, header overhead analysis, and modern lightweight schemes (DLINT, PLINT) that compress telemetry state with Bloom filters and reservoir sampling [2].
3. A rigorous treatment of consensus on switches, covering the optimistic NetPaxos protocol, the full P4-based Paxos acceptor of *Paxos Made Switch-y*, and the CAANS hardware consensus service, with safety arguments for register-based ballot state [3][4].
4. Empirical grounding: throughput, latency, and overhead figures from published hardware evaluations, including SwitchML's in-network gradient aggregation [5], organized into comparative tables and accompanied by proof sketches.

> **Thesis:** Programmable data planes can execute telemetry, consensus, and aggregation logic at line rate with strong correctness guarantees, provided protocol designs are co-shaped with the match-action constraint envelope; outside that envelope, the control plane remains indispensable.

## 2 Background

### 2.1 The P4 Abstract Forwarding Model

P4 [1] describes packet processing through an *abstract forwarding model*: a programmable **parser** extracts headers into typed fields; a sequence of **match-action tables** matches on those fields and executes actions; an optional **deparser** reassembles the packet. In P4-16 [6], this model is refined by target architectures — the v1model, the Portable Switch Architecture (PSA), and the Portable NIC Architecture (PNA) — which define fixed-function blocks (traffic manager, packet replication engine) surrounding programmable ingress and egress pipelines.

Each match-action stage is a match-action unit (MAU) — TCAM/SRAM lookup feeding an action ALU — traversed in fixed feed-forward order with a bounded packet header vector (PHV). The model imposes three structural constraints:

- **Single pass.** A packet visits each stage at most once per traversal; there are no data-dependent loops. Recirculation is possible but costs a full additional pipeline pass.
- **Bounded computation per stage.** Actions are straight-line sequences of primitive operations; division, floating point, and unbounded iteration are unavailable.
- **Atomic state access.** On-chip state (registers, meters, counters) is accessed through stateful ALUs that guarantee atomic read-modify-write within a stage, serializing concurrent packet accesses to the same cell.

These constraints are not incidental: they are what make terabit line-rate execution possible. Every in-network computing design is, at bottom, a negotiation with this envelope.

### 2.2 In-Band Network Telemetry

Conventional monitoring (SNMP, NetFlow, sFlow) samples coarsely and cannot resolve microsecond-scale phenomena such as microbursts. In-band network telemetry [2] instead instruments the data packets themselves. The INT specification defines three roles — *source*, *transit hop*, *sink* — and three modes: **INT-MD** (metadata accumulates in the packet), **INT-MX** (transit hops export metadata directly), and **INT-XD** (no packet modification).

The telemetry items defined by the specification include switch ID, ingress and egress port IDs, hop latency, queue occupancy and congestion status, and ingress/egress timestamps. Because collection is performed entirely in the data plane, INT achieves per-packet visibility at line rate — but at a cost: header overhead grows linearly with path length and the number of telemetry values, motivating the lightweight schemes analyzed in Section 4.1.

### 2.3 Consensus and the Case for the Network

Consensus protocols such as Paxos underpin replicated state machines, configuration services, and distributed locks. In software, a Paxos round costs multiple network round trips plus host-stack processing — typically tens to hundreds of microseconds. Yet the *logic* of an acceptor is remarkably simple: compare a ballot number, conditionally update three registers (`rnd`, `vrnd`, `val`), and reply. Dang et al. [3] observed that this logic maps almost perfectly onto match-action tables with register state, and that placing acceptors *inside* the network collapses consensus latency to little more than forwarding delay. This observation launched a line of work — NetPaxos, Paxos Made Switch-y, CAANS [4] — that treats consensus as a network service rather than an endpoint library.

### 2.4 Stateful Processing Primitives

P4-16 exposes persistent state through several constructs [6]:

| Primitive | Semantics | Typical use |
|---|---|---|
| `register<T>` | Indexed array of state cells; atomic RMW via stateful ALU | Per-flow counters, ballot numbers, sketches |
| `counter` | Packet/byte counts, direct or static | Flow statistics |
| `meter` | Token-bucket rate measurement (RFC 2697/2698) | Policing, congestion signals |
| `digest` | Asynchronous message to control plane | Exception reporting, learning |
| `extern` | Target-specific function (hash, checksum, timestamp) | Checksums, random sampling |

Registers are the workhorse of in-network computing: atomic read-modify-write per packet gives the data plane a sequentially consistent scratchpad, provided the programmer respects the one-access-per-stage discipline.

## 3 Methodology

Our investigation follows a design-science methodology with three interlocking phases: **formalization**, **construction**, and **evaluation**.

*Formalization.* We model the match-action pipeline as a synchronous dataflow machine: a packet is a tuple of header fields *h* ∈ *H* and metadata *m* ∈ *M*; each stage *i* computes *(h, m, σᵢ) → (h′, m′, σᵢ′)* where *σᵢ* is the stage-local state, with the constraint that *σᵢ′* differs from *σᵢ* only through an atomic read-modify-write function drawn from a restricted ALU instruction set. Protocol correctness is then stated as invariants over the sequence of state transitions — e.g., ballot monotonicity for acceptors — and discharged by a combination of manual proof sketches and bounded model checking in the style of p4v.

*Construction.* We decompose each application into per-packet match-action programs plus a minimal host shim, following **constraint-first design**: protocols are re-derived under the match-action envelope rather than ported verbatim — Paxos as register comparisons and table dispatches, telemetry as per-packet sketch updates.

*Evaluation.* We ground claims in published hardware measurements — Tofino-class pipelines, FPGA prototypes, BMv2 experiments [2][3][4][5] — tying each analytical bound to a concrete parameter regime so the analysis stays falsifiable.

## 4 Deep Dive

### 4.1 In-Band Network Telemetry at Line Rate

The INT-MD data plane program is conceptually simple. The INT source matches on a flow selector (or samples probabilistically), inserts an INT shim header carrying an instruction bitmap, and each transit hop executes an action that appends its local metadata to a growing stack:

```p4
action int_transit(switch_id_t swid) {
    hdr.int_md.push_front(1);
    hdr.int_md[0].switch_id  = swid;
    hdr.int_md[0].hop_latency = (bit<32>)(standard_metadata.egress_global_timestamp
                                        - standard_metadata.ingress_global_timestamp);
    hdr.int_md[0].queue_occ  = (bit<16>)standard_metadata.enq_qdepth;
    hdr.int_md[0].setValid();
}
```

The sink strips the stack and clones a report to the collector — but header overhead grows as **O(h·k·w)** per packet, exceeding 100 bytes on a 5-hop path with 8 fields [2].

Two families of lightweight INT address this. **DLINT** (deterministic) spreads telemetry values across the packets of a flow: per-flow telemetry state is maintained in switch registers so that consecutive packets carry *different* subsets of metadata, and the collector reassembles the full path trace. To compress the per-flow state tables, DLINT employs **Bloom filters**, trading a tunable false-positive rate for a dramatic reduction in SRAM. **PLINT** (probabilistic) instead uses *reservoir sampling*: every INT node inserts its telemetry values into each packet with equal probability, so the collector observes an unbiased sample of the path without any per-flow state at all. Papadopoulos et al. [2] show both schemes alleviate transmission overhead while preserving monitoring accuracy, with DLINT superior at conveying complete path traces and PLINT faster at detecting path updates thanks to more efficient header-space utilization.

> **Theorem (INT overhead bound):** For INT-MD over a path of *h* hops collecting *k* fixed-width metadata fields of width *w* bits, per-packet header overhead is exactly *h·k·w* bits plus shim overhead. DLINT reduces expected per-packet overhead to *O((k·w·h)/n)* amortized over *n* packets of a flow, at the cost of *O(f)* register state per tracked flow where *f* is the Bloom filter size in bits.

### 4.2 Consensus Protocol Acceleration on Switch Hardware

Paxos decomposes into three roles — *proposer*, *acceptor*, *learner* — communicating in two phases. Phase 1 (prepare/promise) establishes a ballot; Phase 2 (accept/accepted) commits a value. The acceptor's logic is the critical kernel:

```rust
// Acceptor logic, expressed as a match-action program
fn acceptor_step(pkt: PaxosMsg, regs: &mut AcceptorRegs) -> Option<PaxosMsg> {
    match pkt.kind {
        Msg::Prepare { rnd } if rnd > regs.rnd => {
            regs.rnd = rnd;
            Some(Msg::Promise { rnd, vrnd: regs.vrnd, vval: regs.vval })
        }
        Msg::Accept { rnd, val } if rnd >= regs.rnd => {
            regs.rnd = rnd; regs.vrnd = rnd; regs.vval = val;
            Some(Msg::Accepted { rnd, val })
        }
        _ => None, // stale ballot: drop silently
    }
}
```

Each branch is a register compare followed by conditional updates — precisely what a stateful ALU provides atomically. **NetPaxos** [3] explored two designs: a full Paxos implementation requiring modest OpenFlow extensions, and an *optimistic* protocol that needs no switch changes at all, instead exploiting the network's natural packet ordering (a single top-of-rack switch acting as serializer over fixed-length topologies, in the spirit of speculative Paxos). The optimistic variant trades generality for deployability: it is correct only when the network delivers messages in order, an assumption that holds in benign data-center conditions but fails under reordering.

**Paxos Made Switch-y** made the mapping concrete in P4: acceptor tables dispatch on message type to `handle_1a` and `handle_2a` actions that read and write `rnd`, `vrnd`, and `value` registers, with learners counting Phase 2B messages per interface toward a majority quorum of *f*+1. **CAANS** [4] completed the arc: a full Paxos protocol implemented in a high-level data-plane language, portable across targets, exposed as a drop-in network service. Consensus executes at line speed — hardware transmits consensus messages as fast as it forwards packets, with latency only marginally above plain forwarding.

```tla
---- MODULE PaxosAcceptor ----
EXTENDS Naturals
VARIABLES rnd, vrnd, vval
Prepare(r) == /\ r > rnd
              /\ rnd' = r /\ UNCHANGED <<vrnd, vval>>
Accept(r, v) == /\ r >= rnd
                /\ rnd' = r /\ vrnd' = r /\ vval' = v
Safety == [](vrnd <= rnd)   \* ballot monotonicity invariant
====
```

> **Theorem (Acceptor safety):** If each acceptor's register updates are atomic and ballot comparisons use the stored `rnd`, then no two different values can be chosen in the same instance: any value chosen at ballot *b* is the value proposed at the highest ballot < *b* accepted by a quorum. The proof follows Lamport's original argument, with atomic register RMW substituting for the atomic step of a software acceptor.

### 4.3 Stateful Packet Processing under Match-Action Constraints

Statefulness is what elevates P4 from a fancy classifier to a computing substrate — and the constraints are severe. Consider implementing a per-flow heavy-hitter detector with a Count-Min sketch:

```python
# Control-plane view of a data-plane Count-Min sketch update
def sketch_update(regs, flow_key, d=4, w=1024):
    for i in range(d):                       # d hash rows...
        idx = hash_i(flow_key) % w           # ...but the data plane
        regs[i][idx] += 1                    # has no loops: unroll!
```

The data plane cannot loop; the *d* rows must be unrolled into *d* stages or parallel stateful ALUs, each performing exactly one hash and one atomic increment. This illustrates the general discipline:

1. **Unroll iteration into pipeline depth.** Every loop becomes spatial replication across stages; sketch width is bounded by the stage budget (typically ≤ 20).
2. **One state access per packet per cell.** Concurrent packets serialize on the stateful ALU; throughput is preserved but per-packet work is capped at a single RMW per register array.
3. **Approximate when exact is unaffordable.** Without division or floating point, algorithms must be re-expressed with integer arithmetic, fixed-point scaling, and probabilistic data structures (Bloom filters, HyperLogLog, Count-Min) — all of which fit naturally in registers [2].
4. **Recirculate sparingly.** Multi-pass algorithms (e.g., iterative graph propagation) pay a full pipeline traversal per pass, halving effective throughput per recirculation.
5. **Export exceptions, not streams.** The `digest` mechanism ships rare events to the control plane; bulk export belongs to INT-style collection, not the fast path.

### 4.4 Case Study: In-Network Aggregation and Caching

**SwitchML** [5] moves all-reduce aggregation into a programmable switch: workers stream gradient chunks; the switch sums them in on-chip registers and multicasts the result back. The co-design is essential — the end-host protocol handles reliability (packet loss, stragglers) with chunk-level retransmission and shadow copies, because the switch cannot buffer arbitrarily. The result: up to **5.5× speedup** in training throughput on real benchmarks, with aggregation latency below a round-trip time [5].

| System | In-network function | State primitive | Reported gain |
|---|---|---|---|
| INT / DLINT / PLINT [2] | Per-hop metadata append; sampling | Registers + Bloom filters | Overhead cut vs. baseline INT-MD |
| NetPaxos [3] | Acceptor/coordinator logic | Registers (`rnd`/`vrnd`/`val`) | ~µs-scale rounds vs. ~100s µs software |
| CAANS [4] | Full Paxos as network service | FPGA/hardware registers | Line-rate consensus messaging |
| SwitchML [5] | Gradient all-reduce aggregation | On-chip accumulator registers | Up to 5.5× training speedup |
| NetCache | Hot-key read caching | Match-action + SRAM cache | Load balancing under skew |

## 5 Empirical Results and Proofs

### 5.1 Latency and Throughput Landscape

Published hardware evaluations establish a consistent quantitative picture. We consolidate the headline figures:

| Metric | Software baseline | In-network design | Source |
|---|---|---|---|
| Paxos round latency | 50–200 µs (host stack + RTTs) | Single-digit µs; ≈ forwarding + ALU | [3][4] |
| Consensus throughput | 10⁴–10⁵ rounds/s per coordinator | 10⁶–10⁷+ msgs/s at line rate (FPGA/Tofino class) | [4] |
| INT overhead (5 hops, 8 fields) | N/A (no equivalent) | >100 B/pkt baseline; DLINT/PLINT reduce substantially | [2] |
| All-reduce aggregation | Host/NCCL ring | Sub-RTT in-switch aggregation; ≤5.5× end-to-end speedup | [5] |
| Telemetry resolution | ms (SNMP/NetFlow) | Per-packet, sub-µs timestamps | [2] |

> **Theorem (Consensus latency lower bound):** Any acceptor implemented as a single match-action stage with atomic register RMW completes a Phase 2B response in *T_fwd + T_alu*, where *T_fwd* is the pipeline forwarding latency and *T_alu* the stateful ALU latency (single-digit nanoseconds on Tofino-class hardware). No software acceptor can respond faster than *T_nic + T_stack + T_sched*, bounded below by PCIe and kernel scheduling delays — typically three orders of magnitude larger.

*Proof sketch.* The acceptor's critical path is: parse Paxos header → table match on message type → one register read-compare-write → construct reply → deparse. Each step is a fixed pipeline stage; the total is deterministic and independent of system load. The software path additionally traverses NIC DMA, interrupt handling, kernel network stack, and userspace scheduling, each contributing variable delay. ∎

### 5.2 Correctness Arguments for Stateful Designs

**Ballot monotonicity**: because register RMW is atomic per packet, the sequence of `rnd` values observed at any acceptor is totally ordered, and the guard `rnd > regs.rnd` ensures only strictly increasing ballots update state — the standard Paxos safety argument carries over unchanged [3][4]. **Telemetry consistency**: DLINT's per-flow state machine guarantees that the union of metadata subsets carried across a flow's packets reconstructs the full path trace, provided the Bloom filter's false-positive rate *ε* satisfies *ε < 1/(f·h)* for *f* flows and *h* hops — otherwise state aliasing corrupts reassembly. PLINT sidesteps this entirely: reservoir sampling gives each hop equal inclusion probability *1/h* per packet, yielding unbiased path samples with no switch state at all [2].

### 5.3 Resource Footprint Analysis

The binding constraint is on-chip memory: tens of MB of SRAM and a few MB of TCAM shared across all tables and registers. A Paxos acceptor needs three registers per instance — negligible. A DLINT Bloom filter tracking 10⁵ flows at 1% false-positive rate needs ~1 MB — feasible. A Count-Min sketch with *d*=4, *w*=2¹⁶ needs 4 stages × 256 KB. SwitchML's accumulators are hungriest, which is why it pages gradient chunks through the switch rather than holding full tensors [5]. The lesson: *in-network computing scales when state is small, commutative, or streamable*.

## 6 Limitations

Intellectual honesty demands we catalog where the paradigm breaks down.

**Expressiveness.** The match-action envelope excludes floating point, division, unbounded loops, and general recursion. Algorithms that need them — most of numerical computing, graph analytics beyond one hop, cryptographic verification — cannot be faithfully relocated. Fixed-point and sketch-based approximations recover *some* ground, but approximation error must be analyzed per application, and silent precision loss is a real hazard.

**Deployability.** P4 is portable in principle [6] but target-specific in practice — stage counts, PHV widths, and ALU semantics differ across targets — and programmable switches remain a small fraction of deployed fleets, so designs must degrade gracefully on legacy paths.

**Trust and security.** INT assumes trusted sources, hops, and sinks; a compromised switch can forge telemetry, and INT headers leak topology to observers. A malicious acceptor with register access can equivocate in ways far harder to audit than a software process — and data-plane attestation remains immature.

**Failure semantics.** Switches reboot and lose register state; an acceptor that forgets its `rnd` can violate safety without persistent ballots or recovery extensions. Production designs therefore keep a host-based fallback — the "pure" in-network protocol is really a fast path with a slow path behind it.

## 7 Conclusion

In-network computing with P4 data planes is no longer speculative: INT delivers per-packet, microsecond-resolution visibility from the data plane [2]; Paxos acceptors execute consensus logic at line speed [3][4]; in-network aggregation accelerates distributed training by up to 5.5× [5]. The unifying mechanism is stateful packet processing — registers, meters, and stateful ALUs accessed through atomic read-modify-write within a single-pass match-action pipeline [6].

The deeper lesson is methodological. Successful designs do not port protocols to switches; they *re-derive* protocols under the match-action constraint envelope: unroll loops into pipeline depth, replace exact computation with sketches and fixed-point arithmetic, trade per-flow state for sampling when memory binds, and co-design a host-side shim for everything the envelope excludes. The failures — and there will be failures as the field matures — will come from designs that treat the switch as a small server rather than as what it is: a synchronous, feed-forward, line-rate stream processor with a tiny, precious scratchpad.
