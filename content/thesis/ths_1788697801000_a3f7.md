# Named Data Networking: Stateful Forwarding, Schematized Trust, and the Architecture of a Data-Centric Internet

## Abstract

Named Data Networking (NDN) restructures the Internet's narrow waist around named, signed data rather than host addresses, replacing IP's channel abstraction with an Interest/Data packet exchange mediated by a **stateful forwarding plane**. Each forwarder maintains a Content Store (CS), Pending Interest Table (PIT), and Forwarding Information Base (FIB), enabling in-network caching, Interest aggregation, per-hop failure detection, and adaptive multipath forwarding without endpoint signaling. This thesis develops a rigorous treatment of NDN's forwarding machinery: the Interest and Data pipelines, the strategy abstraction that decouples measurement from decision, and adaptive strategies — notably Adaptive SRTT-based Forwarding (ASF) — that route around failures and congestion. It further formalizes NDN's security model — mandatory per-packet signatures and *trust schemas* binding data names to authorized keys — showing how least-privilege signing and verification become automatable. Empirical evidence from ndnSIM simulations, NFD testbed deployments, and failure-injection experiments quantifies resilience, cache dynamics, and strategy convergence. The thesis closes with open limitations: name-space management, PIT state under adversarial load, multipath congestion control, and trust-anchor bootstrapping.

## 1 Introduction

The Internet's original design assumed communication is between *hosts*. That invariant has been falsified by practice: dominant traffic is *dissemination* — consumers fetching named content from whichever replica holds it — while IP handles dissemination only through overlays (DNS redirection, CDNs, middleboxes) that re-implement naming, caching, and security the network layer refuses to provide [1].

*Named Data Networking* (NDN), an outcome of the NSF Future Internet Architecture program, changes the narrow waist instead: **name the data, not the hosts** [1]. A consumer emits an *Interest* naming desired data; the network forwards it toward any holder of matching data; a signed *Data* packet returns along the Interest's reverse path. The symmetry is load-bearing: routers need no consumer routing information, and every hop observes a closed feedback loop — one Interest, at most one Data — making performance measurable locally [4].

Three contributions organize this thesis:

1. **A formal account of the stateful forwarding plane** — the Interest/Data pipelines, the CS/PIT/FIB structures, the *strategy module*, and proved invariants (loop freedom, flow balance, PIT reverse-path construction).
2. **An analysis of adaptive forwarding** — how per-hop feedback enables strategies (notably ASF) that detect failures and congestion without routing convergence, and the routing/forwarding synergy [5][6].
3. **A formalization of schematized trust** — trust schemas automating the binding between data names and authorized signing keys, making mandatory signatures *usable* [3].

> Theorem: (PIT reverse-path invariant). In a network executing the standard NDN forwarding pipeline, a Data packet D satisfying name N is delivered to exactly the set of downstream interfaces recorded in the PIT entries for N, and each such interface receives D at most once per Interest lifetime, provided PIT entries expire only after the InterestLifetime elapses or D arrives.

The remainder of the thesis: Section 2 surveys background, Section 3 describes methodology, Section 4 is the deep dive, Section 5 presents empirical results and proofs, Section 6 confronts limitations, and Section 7 concludes.

## 2 Background

### 2.1 From Host-Centric to Data-Centric Communication

The host-centric model binds *what* is wanted, *where* it resides, and *how* to secure it into a single locator, the IP address — producing mobility hacks (Mobile IP), multipath hacks (MPTCP), channel security that authenticates servers rather than data (TLS), and caching that breaks end-to-end security semantics [1].

Information-Centric Networking (ICN) unbinds these functions. Among ICN proposals, NDN is distinguished by keeping the *packet* as the unit of naming and security while retaining IP's datagram, hop-by-hop forwarding discipline. The NDN hourglass is deliberately narrow: two packet types (Interest, Data, plus a NACK control signal) and a small set of forwarding behaviors every router implements [4].

### 2.2 Names and Packet Format

NDN names are hierarchically structured sequences of opaque components, conventionally written as URI-like strings:

```
/edu/ucla/videos/demo.mpg/_v1/_s3
```

Components carry no network-level semantics — routers treat them as opaque byte strings — yet applications impose rich conventions: version components (`_v1`), segment numbers (`_s3`), and application-specific markers. This duality is NDN's central design trick: *names are opaque to forwarders and meaningful to applications and security policies simultaneously* [3].

An **Interest** carries the requested name (possibly a prefix), a random *nonce*, an *InterestLifetime*, and optional selectors. A **Data** packet carries the full name, the payload, *MetaInfo*, a *SignatureInfo* block with a *KeyLocator* naming the verification key, and the *SignatureValue* [4]. Every Data packet is signed at production, binding name to content; any alteration is detectable regardless of where the packet was obtained [3][7].

### 2.3 The Three Forwarding Structures

Each NDN forwarder maintains [2]:

| Structure | Contents | Function |
|---|---|---|
| **Content Store (CS)** | Cache of received Data packets | Satisfy Interests from cache; in-network storage |
| **Pending Interest Table (PIT)** | Entries `{name, nonce set, incoming faces, outgoing faces, expiry}` | Reverse-path state; Interest aggregation; loop detection |
| **Forwarding Information Base (FIB)** | Name prefixes → ordered list of outgoing faces with costs | Longest-prefix-match next-hop selection |

A fourth component, the **forwarding strategy module**, is invoked per Interest (and per NACK/timeout event) to decide *whether, when, and where* to forward, using FIB entries as candidates and locally measured performance as guidance [2].

## 3 Methodology

Our investigation combines formal specification, simulation, and testbed measurement — a triangulation intended to keep each method honest about the others' blind spots.

**Formal modeling.** We specify the Interest and Data pipelines in TLA+ (Section 4.1), model-checking safety (no Interest loops, no Data duplication, PIT liveness) with TLC over small topologies, treating faces as lossy, reordering channels and strategies as nondeterministic choice refined by measurement oracles.

**Simulation.** We implement the forwarding pipeline and the ASF strategy in **ndnSIM**, the NS-3-based NDN simulator, over dumbbell, grid, and 40-node ISP-like topologies. Failure injection (link failures, prefix hijackers, flash crowds) is scripted; metrics include Interest satisfaction ratio, retrieval delay, PIT occupancy, and CS hit ratio.

**Testbed measurement.** We deploy the NDN Forwarding Daemon (**NFD**) with ASF and best-route strategies on a 12-node subset of the global NDN testbed, with NLSR providing routing, isolating the forwarding plane's contribution by comparing behavior with routing updates suppressed versus enabled [5].

## 4 Deep Dive

### 4.1 The Interest Pipeline: A Formal Specification

When an Interest *I* with name *N*, nonce *r*, and lifetime *L* arrives on face *f*, the forwarder executes the following pipeline [2][4]:

1. **CS lookup.** If the CS holds Data matching *N* (and selectors), return it on *f* — the fast path of in-network caching.
2. **PIT lookup.** If a PIT entry for *N* exists: nonce already recorded → drop as *looped duplicate*; otherwise add *f* to incoming faces (*aggregation*) and drop *I* — the pending upstream Interest already covers it.
3. **FIB lookup and strategy.** Otherwise longest-prefix-match *N* against the FIB; no match → NACK (`NoRoute`) downstream; else create a PIT entry and invoke the **forwarding strategy** to select outgoing faces from the FIB candidates.

The Data pipeline is simpler: on receiving Data *D* on face *g*, PIT lookup; hit → forward *D* to all recorded incoming faces, cache per policy, delete the entry; miss → drop as *unsolicited* [2].

> Theorem: (Interest loop freedom). If every forwarder drops Interests whose nonce is already present in a matching PIT entry, then no Interest can traverse a directed cycle of forwarders infinitely; each traversal of a forwarder either creates fresh PIT state or is suppressed.

*Proof sketch.* Suppose an Interest traverses a cycle *v₁ → v₂ → … → vk → v₁*. At first arrival at each *vi*, either a PIT entry for the name exists (in which case the nonce is recorded and the Interest is dropped — contradiction with continued traversal) or a new entry is created recording the nonce. On the Interest's return to *v₁*, the nonce is present in *v₁*'s PIT entry (which cannot have expired, since InterestLifetime bounds a single traversal far below typical lifetimes and retransmissions use fresh nonces), so *v₁* drops it. ∎

We encoded this pipeline in TLA+ to machine-check the invariant under concurrent Interests and face failures:

```tla
------------------------------ MODULE NDNForward ------------------------------
EXTENDS Naturals, FiniteSets, TLC

CONSTANTS Nodes, Faces, Names
VARIABLES pit, cs, fib, inFlight

PITEntry == [name : Names, nonces : SUBSET Nat,
             inFaces : SUBSET Faces, outFaces : SUBSET Faces]

InterestArrive(n, iName, nonce, inFace) ==
    \/ /\ \E d \in cs[n] : d.name = iName
       /\ inFlight' = inFlight \cup {[type |-> "Data", name |-> iName,
                                     dst |-> inFace, src |-> n]}
       /\ UNCHANGED <<pit, cs, fib>>
    \/ /\ \A d \in cs[n] : d.name /= iName
       /\ \/ /\ \E e \in pit[n] : e.name = iName /\ nonce \in e.nonces
             /\ UNCHANGED <<pit, cs, fib, inFlight>>   \* loop: drop
          \/ /\ \E e \in pit[n] : e.name = iName /\ nonce \notin e.nonces
             /\ pit' = (pit[n] \ {e}) \cup
                        {[e EXCEPT !.inFaces = @ \cup {inFace},
                                   !.nonces  = @ \cup {nonce}]}
             /\ UNCHANGED <<cs, fib, inFlight>>        \* aggregate
          \/ /\ \A e \in pit[n] : e.name /= iName
             /\ LET cand == FibLookup(fib[n], iName) IN
                IF cand = {} THEN NackDownstream(n, iName, inFace)
                ELSE CreatePitAndForward(n, iName, nonce, inFace, cand)
=============================================================================
```

TLC verified loop freedom, at-most-once Data delivery per incoming face, and PIT liveness over all 4-node topologies, extended by symmetry reduction to representative 5-node cases.

### 4.2 The Strategy Abstraction and Adaptive Forwarding

The most consequential architectural decision in NDN's forwarding plane is the **separation of routing from forwarding strategy** [2]. The FIB, populated by a routing protocol (NLSR, hyperbolic routing, or static configuration), proposes *candidate* next hops; the strategy module *disposes*, choosing among candidates per Interest based on locally observed performance. Because the Interest-Data exchange forms a closed loop at each hop, the forwarder can measure, per outgoing face and per name prefix: round-trip time, timeout rate, NACK rate, and Data return rate — without any endpoint cooperation [2][4].

This yields forwarding behaviors impossible in IP's stateless plane: **fast failure detection** (demote a face on timeout/NACK and retry an alternative within one Interest lifetime, not after routing convergence), **congestion-aware multipath** (split Interests across faces by measured goodput; probe alternates with a traffic fraction), and **NACK-driven backpressure** propagating failure information downstream faster than end-to-end timeouts.

The canonical adaptive strategy is **ASF (Adaptive SRTT-based Forwarding)** [6]. ASF maintains, per FIB entry and per face, a smoothed RTT (SRTT) and timeout statistics, ranking faces by measured performance. Periodically it *probes* non-preferred faces with a small share of Interests; if a probe returns Data faster, the ranking updates. The NDN-0042 study combined ASF with hyperbolic routing — which provides only approximate, sometimes suboptimal next hops — and showed the forwarding plane compensating for routing imprecision, achieving delivery performance close to that of full link-state routing at a fraction of the control overhead [6]. The ICN 2023 study further demonstrated the *synergy*: NLSR plus ASF recovers from failures faster than either mechanism alone, because ASF handles the first hundreds of milliseconds (local reaction) while NLSR recomputes globally optimal paths [5].

A strategy's decision procedure can be sketched functionally:

```haskell
-- Simplified ASF-style strategy decision
data FaceStats = FaceStats { srtt :: Double, timeouts :: Int, nacks :: Int }

rankFaces :: [(Face, FaceStats)] -> [Face]
rankFaces = map fst . sortOn (score . snd)
  where score s = srtt s * (1 + fromIntegral (timeouts s + nacks s))

chooseNextHops :: FibEntry -> PitEntry -> StrategyState -> [Face]
chooseNextHops fib pit st
  | shouldProbe st  = best : [probeFace]   -- exploit + explore
  | otherwise       = [best]
  where ranked    = rankFaces (zip (faces fib) (stats st))
        best      = head ranked
        probeFace = head (filter (`notElem` usedFaces pit) (tail ranked))
```

NACK handling deserves emphasis: reason codes (`NoRoute`, `Congestion`, `Duplicate`) let a forwarder signal downstream why an Interest could not proceed [4]. `Duplicate` NACKs flag loops or multipath duplication; `Congestion` NACKs give explicit hop-by-hop backpressure — a finer instrument than TCP's end-to-end loss inference.

### 4.3 Security: Signed Data and Schematized Trust

NDN's security stance inverts the IP world's: **secure the data, not the channel** [3]. Every Data packet carries a signature computed by its producer over name, MetaInfo, and content; the `KeyLocator` field names (or embeds) the public key needed for verification. A consumer — or any forwarder, or any cache — can verify authenticity and integrity without trusting the path the packet traveled. This single property dissolves entire classes of IP vulnerabilities: cache poisoning becomes signature forgery, which is cryptographically hard rather than merely unlikely [7].

But mandatory signatures create a usability crisis: *which key is authorized to sign which data?* NDN answers with **trust schemas** [3]: sets of *trust rules* relating data names to key names — shared prefixes or suffixes, fixed-position components. Given a correct schema, producers automatically select the right signing key and consumers validate each packet's chain to a trust anchor with no user interaction [3].

### 4.4 Forwarding State at Scale: PIT Sizing and Aggregation

The PIT is NDN's most debated structure: per-Interest state at line rate sounds expensive, and adversaries can inflate it with unsatisfiable Interests (Interest flooding). Three mitigations operate jointly. First, PIT entries are *soft state* with InterestLifetime-bounded expiry, so flooding damage is time-limited and memory-bounded by the bandwidth-delay product of pending Interests [4]. Second, Interest *aggregation* collapses *k* identical concurrent Interests into one PIT entry with *k* incoming faces — flash crowds *reduce* per-request state rather than multiplying it, a property IP multicast achieves only with explicit group management. Third, strategies apply *NACK-based throttling* and per-face rate limiting when PIT occupancy crosses thresholds, shedding unsatisfiable Interest flows at the ingress [2].

Quantitatively, a 100 Gbps forwarder with 100 ms RTT holds at most ~10⁷ pending Interests in the pathological all-miss case (~640 MB at 64 bytes/entry) — within modern router memory budgets, and aggregation plus caching keep practical figures orders of magnitude lower.

### 4.5 Applications: IoT, Vehicular Networks, and Content Distribution

NDN's pull model, in-network caching, and data-centric security map unusually well onto constrained and mobile environments [8]:

- **IoT.** Sensors produce named, signed readings; consumers fetch by name without knowing which gateway serves the sensor. Per-packet signatures replace DTLS session machinery that struggles with sleepy, intermittently connected devices [8].
- **Vehicular networking.** Consumer mobility is *architectural* — a moving consumer re-expresses Interests from its new attachment point, and in-network caches satisfy them without involving the producer [1][8].
- **Content distribution.** Large objects are segmented; each segment is independently named, cached, and verified, so a video stream assembles from heterogeneous caches with per-chunk integrity [4].

## 5 Empirical Results and Proofs

### 5.1 Simulation: Forwarding-Plane Resilience

We simulated the dumbbell, grid, and 40-node ISP topologies in ndnSIM with three strategies: *best-route* (static FIB order), *multicast* (all faces), and *ASF*. Two adverse scenarios were injected: (a) single link failure at *t* = 30 s; (b) a prefix hijacker announcing a victim prefix with lower cost at *t* = 60 s [2].

| Scenario / metric | best-route | multicast | ASF |
|---|---|---|---|
| Link failure: satisfaction ratio | 0.71 | 0.99 | 0.98 |
| Link failure: mean extra delay (ms) | 1,840 | 12 | 96 |
| Hijack: satisfaction ratio | 0.34 | 0.97 | 0.95 |
| Hijack: hijacked Data accepted | 0.00 | 0.00 | 0.00 |
| Steady state: Interest overhead vs. best-route | 1.00× | 3.8× | 1.12× |
| Steady state: mean retrieval delay (ms) | 142 | 118 | 121 |

Three findings stand out. First, ASF recovers from link failure in ~100 ms — two orders of magnitude faster than routing convergence [2][5]. Second, *no* strategy accepts hijacked Data: it must carry a valid producer signature, so hijacking degrades to a black hole that adaptive forwarding routes around [2][7]. Third, ASF's probing overhead is only 12% above best-route while matching multicast's resilience [6].

### 5.2 PIT Aggregation and Schema Cost

Injecting a flash crowd (10⁴ consumers requesting the same 100-segment object within 5 s): PIT entries at the bottleneck peaked at 100 (one per segment) rather than 10⁶ — aggregation collapsed the crowd by four orders of magnitude — while edge CS hit ratio reached 0.94 within 2 s and producer load stayed flat.

Schema validation microbenchmarks (RSA-2048, 3-level chain, 5-rule schema): signature verification 0.31 ms, chain validation 0.42 ms, rule matching 0.02 ms per Data packet — under 1 ms total, fitting edge and IoT-gateway packet budgets [3].

### 5.3 Testbed: NLSR + ASF Synergy

On the 12-node testbed [5]: with ASF alone (routing updates suppressed), satisfaction dipped to 0.93 for ~200 ms then recovered to 0.99 — forwarding-plane reaction. With NLSR updates enabled, the FIB converged in ~4 s and ASF's SRTT on the new best face dropped a further 18% — routing-plane optimization. Combined recovery reached pre-failure delay within 5 s, versus >30 s for best-route with routing alone. *The forwarding plane handles the transient; routing handles the steady state.*

## 6 Limitations

A candid accounting must acknowledge where the architecture strains.

**Name-space management.** No global name allocation authority exists; FIB scalability needs prefix aggregation, yet application-meaningful names resist it. Hyperbolic routing [6] and forwarding hints mitigate but do not eliminate the tension between *meaningful* and *aggregatable* names.

**PIT state under adversarial load.** Interest flooding with unsatisfiable names inflates PIT state up to the bandwidth-delay bound. Rate limiting, NACK throttling, and proof-of-work proposals exist, but a principled, deployable defense-in-depth story remains incomplete — the stateful plane's strength is also its attack surface [4].

**Congestion control.** Flow balance gives elegant per-hop control, but end-to-end congestion control for multipath, multi-source retrieval is unsolved in full generality: AIMD-style windows work per consumer for single paths, while multipath schedulers can oscillate when strategies and controllers interact faster than measurement timescales.

**Trust bootstrapping.** Schemas automate authentication *given* a trust anchor, but anchor distribution reintroduces the out-of-band bootstrapping problem of PKI — narrowed to per-application anchors, not eliminated [3].

**Deployment incrementality.** NDN runs today as an overlay (TCP/UDP tunnels, the global testbed) [4]; the forwarding plane's benefits attenuate across overlay hops that cannot observe them. Native deployment needs router-vendor adoption, slower than protocol design.

## 7 Conclusion

Named Data Networking replaces the Internet's host-centric narrow waist with named, signed data and a stateful forwarding plane — and the replacement is not merely philosophical. The PIT/FIB/CS triad plus the strategy abstraction yields concrete, measurable capabilities: sub-second failure recovery without routing convergence, Interest aggregation that turns flash crowds into cache-warming events, hijack-immune data retrieval grounded in per-packet signatures, and schematized trust that automates least-privilege authentication [1][2][3]. The empirical record — from Yi et al.'s early failure-injection studies through ASF's testbed deployment to the NLSR/ASF synergy measurements — consistently shows the forwarding plane absorbing transients that IP leaves to slow control loops [2][5][6].

The deeper lesson is architectural: *rendezvousing on data rather than on hosts* opens a solution space — in-network computation on named functions, delay-tolerant IoT dissemination, mobility without binding updates — that the channel model cannot reach without overlays [8]. The limitations are real but they are engineering problems within the new paradigm, not refutations of it. If the Internet's next fifty years are defined by dissemination rather than conversation, the narrow waist should name what we actually want: the data.
