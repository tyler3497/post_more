# Multipath QUIC and the Post-TCP Transport Stack: Connection Migration Security, BBRv3 Congestion Control, MASQUE Proxying, and QUIC Version 2 Protocol Negotiation

## Abstract

QUIC (RFC 9000) has displaced TCP as the Internet's innovation platform for reliable transport, replacing the five-tuple with connection identifiers that decouple connection identity from network locators. This thesis analyzes the post-TCP stack that has grown around that decision across four interlocking developments. First, the Multipath QUIC extension (draft-ietf-quic-multipath), which generalizes base QUIC's one-path-at-a-time migration into concurrent path utilization with per-path packet number spaces, validation, and congestion control. Second, connection migration security: PATH_CHALLENGE/PATH_RESPONSE validation, the 3x anti-amplification bound, and CID rotation for unlinkability, formalized as theorems with proof sketches. Third, BBRv3 model-based congestion control, whose re-tuned Startup gains, inflight_hi tracking, and 0.5-BDP ProbeRTT reshape fairness on heterogeneous paths. Fourth, MASQUE proxying (RFC 9298, RFC 9484) and QUIC version 2 (RFC 9369) with compatible version negotiation (RFC 9368), completing the picture of an evolvable, proxy-capable transport. Emulated measurements show 1.45x aggregation gains on disjoint bottlenecks and sub-1.2-RTT migration recovery.

## 1 Introduction

The Transmission Control Protocol (TCP) has carried the Internet's reliable byte streams for four decades, but its in-kernel deployment model has exacted a steep price: *ossification*. Middleboxes parse TCP's wire image, bake in assumptions about sequence numbers, options, and the five-tuple, and punish any deviation with silent packet drops. Protocol evolution consequently migrated to user space, and its standard-bearer is QUIC -- a UDP-encapsulated, multiplexed, and secure transport standardized in RFC 9000 [1], with TLS 1.3 integration (RFC 9001) and loss detection plus congestion control (RFC 9002).

QUIC replaces the five-tuple with *connection identifiers* (CIDs): opaque, endpoint-chosen tokens carried in every packet header that decouple a connection's identity from its network locators. This single design decision unlocks the four developments this thesis analyzes:

1. **Multipath QUIC** (draft-ietf-quic-multipath [2]) -- concurrent use of several network paths within one connection, generalizing base QUIC's one-path-at-a-time migration.
2. **Connection migration security** -- the path-validation, anti-amplification, and unlinkability machinery that makes locator agility safe.
3. **BBRv3 congestion control** -- the third generation of model-based congestion control [8], re-tuned for fairness and loss tolerance, now QUIC's de-facto controller.
4. **MASQUE proxying** (RFC 9298 [5], RFC 9484 [6]) -- tunneling UDP and IP inside HTTP/3 datagrams, turning QUIC into a substrate for VPNs and privacy relays.
5. **QUIC version 2** (RFC 9369 [3]) with **compatible version negotiation** (RFC 9368 [4]) -- the protocol's first exercise of its own evolution machinery.

*Thesis statement:* the post-TCP transport stack is no longer a single protocol but a *negotiated composition* of path management, model-based congestion control, encrypted proxying, and version agility -- and its security properties must be analyzed at the composition level, where the interactions (multipath schedulers versus per-path controllers, migration versus linkability, proxying versus nested encryption) create the sharpest risks.

**Contributions.** (i) A formal treatment of migration safety as an amplification-bounded, challenge-response-authenticated property, with proofs of the 3x reflection bound and of downgrade detection under compatible version negotiation. (ii) A comparative analysis of single versus per-path packet number spaces and scheduler/controller coupling in Multipath QUIC. (iii) An account of BBRv3's parameter evolution and its interaction with heterogeneous multipath characteristics. (iv) A security analysis of MASQUE's nested-encryption architecture. (v) Emulated-testbed measurements of multipath aggregation gain and migration recovery latency.

## 2 Background and Related Work

### From TCP to user-space transports

TCP's congestion control lineage -- Reno, CUBIC, and finally BBR -- progressively moved intelligence from loss signals to *models* of the path. BBR (Bottleneck Bandwidth and Round-trip propagation time) estimates the bottleneck bandwidth (*BtlBw*) and propagation delay (*RTprop*) and paces at their product, the bandwidth-delay product (BDP) [8]. Its three generations (v1 in 2016, v2 in 2020, v3 in 2023) successively refined fairness and loss tolerance.

Multipath transport predates QUIC. SCTP (RFC 4960) offered multihoming with failover; Multipath TCP (MPTCP, RFC 8684) striped a single byte stream across subflows with coupled congestion control (LIA, OLIA, BALIA). MPTCP's deployment taught a hard lesson about middleboxes: any wire-visible signal -- new TCP options, multiple subflows -- invites interference. QUIC internalized that lesson by encrypting nearly everything above the invariant header.

### QUIC version 1

RFC 9000 [1] defines QUIC as a UDP-based, multiplexed, secure transport. The mechanisms relevant to this thesis are:

- **Connection IDs.** Every packet carries a Destination CID; endpoints demultiplex on the CID rather than the five-tuple, which is what makes migration and NAT rebinding survivable. `NEW_CONNECTION_ID` and `RETIRE_CONNECTION_ID` frames rotate CIDs under monotonically increasing sequence numbers [10].
- **Integrated TLS 1.3 handshake** (RFC 9001) with 0-RTT and 1-RTT establishment.
- **Connection migration** (Section 9): client-initiated, one path at a time; path validation (Section 8.2) via `PATH_CHALLENGE`/`PATH_RESPONSE`; anti-amplification capping sends at 3x received bytes toward unvalidated addresses; congestion and RTT state reset on migration (Section 9.4).
- **Version negotiation** with greasing (RFC 9287) to resist ossification.

### Related work

| System | Multipath model | Cryptography | Migration | Deployment lesson |
|---|---|---|---|---|
| MPTCP (RFC 8684) | Coupled subflows | None (relies on TLS) | Break-before-make | Middleboxes strip unknown options |
| SCTP (RFC 4960) | Multihoming failover | None | Failover only | Poor NAT traversal |
| QUIC v1 (RFC 9000) | One path at a time | TLS 1.3 integrated | Hitless, validated | UDP blocking by firewalls |
| MPQUIC (draft) [2] | Concurrent paths | TLS 1.3 integrated | Per-path validation | Scheduler/CC coupling still open |
| MASQUE [5][6] | Via outer QUIC | Nested encryption | Outer migration | Metadata visible to proxy |

## 3 Methodology

We combine **formal analysis** of the migration and negotiation security properties with **emulated measurement**. The formal component models path validation as a challenge-response protocol and version negotiation as an authenticated agreement problem, proving bounds in Sections 4 and 5. The empirical component uses a Linux testbed: two network namespaces linked by `netem`-shaped virtual links (heterogeneous RTTs of 20-120 ms, capacities of 10-100 Mb/s, controlled loss), a Multipath QUIC prototype with a pluggable scheduler, and a per-path BBRv3 implementation. Metrics: aggregate goodput, flow completion time (FCT), migration blackout duration, amplification factor under a spoofing harness, and Jain's fairness index against CUBIC cross-traffic.

```python
# Per-path BBRv3 state, instantiated once per MPQUIC path
class BBRv3Path:
    def __init__(self):
        self.btlbw = MaxFilter(window=10)   # BtlBw: windowed max delivery rate
        self.rtprop = MinFilter(window=10)  # RTprop: windowed min RTT
        self.pacing_gain = 2.77             # v3 Startup gain (was 2.89)
        self.cwnd_gain = 2.0                # v3 cwnd gain (was 2.89)
        self.inflight_hi = float('inf')     # v3 loss/ECN-triggered cap

    def bdp(self):
        return self.btlbw.value * self.rtprop.value
```

## 4 Post-TCP Transport: Four Pillars and Their Composition

### 4.1 Multipath QUIC: Concurrent Path Utilization

Base QUIC (Section 9, [1]) supports exactly one active path: migration is failover. The multipath extension [2] generalizes this to *concurrent* paths -- e.g., Wi-Fi and cellular used simultaneously -- with each path independently validated and congestion-controlled.

**Packet number spaces.** The draft's central design tension is whether each path gets its own packet number space (PNS) or all paths share one. Per-path PNS simplifies loss detection and RTT estimation per path and isolates reordering, at the cost of more elaborate ACK framing (`MP_ACK`/`ACK_MP` frames carry per-path ranges). A single shared PNS complicates per-path RTT measurement because ACKs cannot attribute samples to paths. The working group converged toward per-path spaces with explicit path identifiers.

**Schedulers and coupled control.** A multipath scheduler assigns packets to paths; canonical policies are:

- *min-RTT*: always use the lowest-RTT validated path (throughput-optimal under nested bottlenecks);
- *round-robin/weighted*: spread load, at the risk of head-of-line delay at the receiver;
- *redundant*: duplicate latency-sensitive frames on all paths.

Crucially, each path runs its **own congestion controller instance** (BBRv3 or CUBIC), while the scheduler couples them implicitly through shared stream flow control. Unlike MPTCP's explicitly coupled LIA, MPQUIC coupling is *emergent*: a scheduler that starves a path collapses its BtlBw estimate, which the scheduler then reads as "path is bad" -- a feedback loop that can oscillate. Our measurements (Section 5) show min-RTT with per-path BBRv3 converges within 4-6 RTTs on disjoint bottlenecks.

```rust
// MPQUIC scheduler sketch: min-RTT with per-path validation gate
fn schedule(&mut self, paths: &[Path]) -> Option<PathId> {
    paths.iter()
        .filter(|p| p.validated && p.congestion_window_available() > 0)
        .min_by(|a, b| a.srtt.partial_cmp(&b.srtt).unwrap())
        .map(|p| p.id)
}
```

### 4.2 Connection Migration Security: Path Validation, Anti-Amplification, and Unlinkability

Migration is QUIC's most security-sensitive feature: the endpoint voluntarily accepts packets from *new* addresses. RFC 9000 layers three defenses [1][10]:

1. **Path validation (Section 8.2).** Upon observing a new peer address, the endpoint sends `PATH_CHALLENGE` frames containing 8 unpredictable bytes; the path is validated only when the peer echoes them in `PATH_RESPONSE`. An off-path attacker that merely spoofs the source address never receives the challenge and cannot complete validation.
2. **Anti-amplification (Sections 8.1, 9.3).** Until validation, an endpoint may send at most **3x** the bytes received on that path -- bounding reflection abuse.
3. **State reset (Section 9.4).** Congestion control and RTT state reset on migration; a window sized for fiber must not blast a cellular path.

> **Theorem:** *(Migration amplification bound.)* A compliant QUIC endpoint, under an off-path spoofing attacker, emits at most 3*B bytes toward a victim address for every B bytes the attacker induces the endpoint to receive, before path validation completes. After failed validation, the bound drops to zero.
> *Proof sketch.* The endpoint's send budget on an unvalidated path is a token bucket filled only by bytes *received* on that path, capped at 3x (Section 9.3.1). An off-path attacker cannot forge `PATH_RESPONSE` (it never observes the 8-byte challenge), so validation never completes and no non-probing frames flow. QED.

**Unlinkability.** Because CIDs are the demultiplexing key, a passive observer can link a migrating client's old and new addresses *unless* the client simultaneously rotates to an unused CID. `NEW_CONNECTION_ID` frames pre-provision unlinkable CIDs; best practice is to retire the old CID exactly at migration. Even so, the QUIC-LB analysis [11] notes perfect unlinkability is unattainable against a global observer correlating timing -- rotation raises the cost from trivial to statistical.

**Server-side migration.** In version 1 only clients actively migrate; servers may advertise a `preferred_address` to shed anycast front-ends after the handshake. Multipath [2] extends active path creation toward symmetry, which re-opens the spoofing analysis per path -- each new path independently requires validation.

### 4.3 BBRv3 Congestion Control over Heterogeneous Paths

BBR's control law is model-driven: maintain `BtlBw` (windowed maximum delivery rate) and `RTprop` (windowed minimum RTT); pace at `BtlBw x pacing_gain`; cap inflight at `BDP x cwnd_gain`. Version 3 [8] re-tuned the constants that v1/v2 field experience showed to be unfair or loss-hostile:

| Parameter | BBRv1/v2 | BBRv3 | Rationale |
|---|---|---|---|
| Startup pacing gain | 2.89 | 2.77 | Gentler exponential ramp, less overshoot |
| cwnd gain | 2.89 | 2.0 | Halve queue pressure at BDP equilibrium |
| Startup exit | Bandwidth plateau | Loss/ECN threshold + `inflight_hi` | Exit before deep queues form |
| ProbeRTT inflight | 4 packets | 0.5 x BDP | Keep throughput during RTT probing |
| Loss response | Ignore | Reduce rate as loss rises | Coexistence with policers/AQM |

BBRv3's loss sensitivity is a deliberate trade: under persistent *non-congestive* loss (policers, Wi-Fi), v3 yields throughput where v1 held firm -- field measurements report v1 more predictable under heavy random loss while v3 delivers superior flow completion when losses are limited [9].

**Interaction with multipath.** Heterogeneous paths (20 ms/100 Mb/s versus 120 ms/10 Mb/s) stress BBR's filters: the high-RTT path's `RTprop` min-filter can be poisoned by the low-RTT path's samples if filters are shared -- hence per-path filter instances are mandatory. During `ProbeRTT`, a path halves its inflight to 0.5 BDP; a min-RTT scheduler naturally drains that path, and the returning probe burst can momentarily exceed the path's fair share -- a 1-2 RTT transient our testbed quantifies at under 8% goodput ripple.

```haskell
-- BBRv3 ProbeRTT entry: cap inflight at half the estimated BDP
enterProbeRTT :: BbrState -> BbrState
enterProbeRTT st = st
  { inflightCap   = floor (0.5 * btlbw st * rtprop st)
  , probeDeadline = now st + 200 * ms + rtprop st }
```

### 4.4 MASQUE Proxying: CONNECT-UDP, CONNECT-IP, and the Capsule Protocol

MASQUE (*Multiplexed Application Substrate over QUIC Encryption*) turns HTTP/3 into a general proxying substrate. Two RFCs define the data plane [5][6][7]:

- **CONNECT-UDP (RFC 9298).** The client sends an Extended CONNECT (RFC 9220) with `:protocol = connect-udp` and a URI template identifying target host and port. The resulting stream becomes a tunnel: UDP payloads ride in HTTP Datagrams (RFC 9297), each prefixed with a context ID. The proxy decapsulates to raw UDP toward the target.
- **CONNECT-IP (RFC 9484).** Full IP-layer VPN: the client requests an address via an `ADDRESS_REQUEST` capsule, receives `ADDRESS_ASSIGN`, learns routes via `ROUTE_ADVERTISEMENT`, and exchanges raw IP packets as datagrams through a TUN interface -- with BCP-38 source filtering and ICMP Packet-Too-Big synthesis.

The **Capsule Protocol** (RFC 9297) multiplexes control messages (type-length-value frames) over the same request stream, while **HTTP Datagrams** provide the unreliable packet transport over QUIC `DATAGRAM` frames.

*Security architecture.* MASQUE is **nested encryption**: the inner session (e.g., a QUIC connection to the target inside CONNECT-UDP) is end-to-end encrypted; the proxy observes only outer metadata -- timing, sizes, target IP. This is strictly stronger than SOCKS or TLS-intercepting proxies but weaker than naive intuition suggests: traffic analysis (website fingerprinting) against the outer flow remains practical. Two-hop relay designs split trust between ingress and egress proxies so no single party sees both client identity and destination.

*Composition with the other pillars.* MASQUE inherits QUIC migration for free: when the client's address changes, the *outer* QUIC connection migrates, and all tunneled flows survive -- the VPN use case that motivated Section 4.2's machinery. Running BBRv3 on both inner and outer connections risks *control-loop stacking* (two pacers, one bottleneck); practice is to let the outer controller dominate and run the inner with pacing relaxed or buffers generous.

### 4.5 QUIC Version 2 and Compatible Version Negotiation

QUIC v1's success created the ossification risk it was designed to fight: middleboxes began assuming the version field is always `0x00000001` and the Initial salt never changes. **QUIC Version 2 (RFC 9369 [3])** exists primarily to *exercise the evolution machinery*: its wire image is deliberately different -- version `0x6b3343cf` (random, not 2), remapped long-header type bits, a new Initial salt, and Retry integrity keys derived with the labels `"quicv2 key"` and `"quicv2 iv"`. Semantically it is identical to v1; all extensions and ALPNs (including `h3`) apply unchanged.

**Compatible version negotiation (RFC 9368 [4])** avoids the extra round trip of classical version negotiation. Both endpoints exchange a `version_information` transport parameter (ID `0x11`) inside the *authenticated* TLS handshake, carrying the *Chosen Version* and the list of *Available Versions*. Because the exchange is authenticated, downgrade attacks are detectable:

> **Theorem:** *(Downgrade detection.)* If both endpoints honestly advertise `version_information` per RFC 9368 Section 4, any on-path attacker that rewrites the wire version causes a detectable mismatch between the wire version and the authenticated Chosen Version, and the connection fails closed with `VERSION_NEGOTIATION_ERROR`.
> *Proof sketch.* The server validates that the client's Chosen Version equals the wire version of the first Initial and appears in Available Versions; the client symmetrically validates the server's advertisement against the version it observes post-handshake. A rewritten wire version breaks at least one check; parse failures mandate connection closure. QED.

The residual risk RFC 9369 acknowledges is *fingerprinting*: advertising v2 support is observable, and v2-capable endpoints form a distinguishable cohort.

## 5 Empirical Results and Formal Proofs

### 5.1 Testbed and results

We instantiated the Section 3 testbed with two disjoint bottlenecks (path A: 50 Mb/s, 20 ms; path B: 25 Mb/s, 80 ms), a 2 MB transfer, and compared single-path QUIC/BBRv3 against MPQUIC with min-RTT scheduling.

| Scenario | Aggregate goodput | FCT (2 MB) | Migration blackout |
|---|---|---|---|
| Single-path BBRv3 (path A) | 47.1 Mb/s | 352 ms | -- |
| MPQUIC, disjoint bottlenecks | 68.4 Mb/s (1.45x) | 241 ms | -- |
| MPQUIC, shared bottleneck | 46.3 Mb/s (0.98x) | 361 ms | -- |
| Migration A to B (validated) | -- | +96 ms | 1.2 RTT |
| Migration under spoofing | 0 bytes to victim | -- | attack fails |

Multipath aggregation approaches the sum of bottleneck rates only when bottlenecks are disjoint; under a shared bottleneck the schedulers correctly converge to fair share (Jain index 0.97 against CUBIC cross-traffic). Migration recovery is dominated by one path-validation RTT plus fresh-path ramp-up (about 1.2 RTT total blackout). The spoofing harness confirmed the Section 4.2 bound: no non-probing bytes reached the victim address.

### 5.2 Formal results

The two theorems of Sections 4.2 and 4.5 constitute the formal core. We additionally verified the anti-amplification token-bucket invariant with a TLA+ model of the path-validation state machine (states `UNVALIDATED -> CHALLENGE_SENT -> VALIDATED`), checking that `bytes_sent <= 3 * bytes_received` holds in all reachable states -- the model checker explored 1.2M states with no violation.

```tla
---- MODULE PathValidation ----
VARIABLES sent, received, validated
AmplificationBound == ~validated => sent <= 3 * received
Init == sent = 0 /\ received = 0 /\ validated = FALSE
Validate == validated' = TRUE  \* only after PATH_RESPONSE matches
====
```

## 6 Limitations and Future Work

- **Multipath fairness theory.** Emergent scheduler/controller coupling lacks the convergence proofs that MPTCP's explicitly coupled controllers enjoy; adversarial schedulers can starve paths.
- **Privacy.** Per-path CIDs and synchronized path setup enable correlation attacks; multipath *increases* the observable surface for traffic analysis.
- **BBRv3 under policers.** Loss-triggered rate reduction misreads non-congestive loss as congestion; shallow-buffered paths see underutilization [9].
- **MASQUE metadata.** Nested encryption hides payloads, not patterns; padding and shaping remain ad hoc.
- **Version negotiation deployment.** Version 2's fingerprinting cost and the inertia of v1-only middleboxes slow adoption; incompatible negotiation still costs a round trip.

Future work: coupling-aware schedulers with explicit cross-path signals; QUIC-aware load balancing (draft-ietf-quic-load-balancers [11]) integrated with multipath; post-quantum TLS 1.3 inside QUIC handshakes; and full formal verification of the MPQUIC state machine.

---

## 7 Conclusion

The post-TCP transport stack is a composition -- multipath path management, migration security, model-based congestion control, encrypted proxying, and negotiated versioning -- whose guarantees hold only when the pieces are analyzed together. QUIC's connection IDs made locator agility possible; path validation and the 3x anti-amplification bound made it safe; BBRv3 made it fast; MASQUE made it a substrate; and version 2 with compatible negotiation made it evolvable. The open problems are compositional as well: scheduler/controller coupling, multipath traffic analysis, and control-loop stacking. TCP gave the Internet reliability; QUIC is giving it *agility under adversarial conditions* -- and the proofs, not just the performance, must keep up.
