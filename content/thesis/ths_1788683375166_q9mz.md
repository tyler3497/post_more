# Confidential Computing with Hardware Enclaves: A Comparative Architectural Analysis of Intel SGX, TDX, and Arm CCA with Formal Models of Remote Attestation

## Abstract

This thesis presents a comparative architectural analysis of contemporary hardware-based confidential computing technologies: Intel Software Guard Extensions (SGX), Intel Trust Domain Extensions (TDX), and Arm Confidential Compute Architecture (CCA). We decompose each platform along three axes: memory protection and integrity mechanisms, privilege and trust-boundary topology, and remote attestation protocols. The treatment covers the SGX Memory Encryption Engine and its Merkle integrity tree over the Enclave Page Cache, TDX Secure-Arbitration Mode with multi-key total memory encryption and the Physical Address Metadata Table, and Arm CCA's Realm Management Extension with Granule Protection Tables and the Realm Management Monitor. We formalize attestation as an evidence-generation and appraisal protocol under the IETF RATS architecture (RFC 9334), contrasting EPID group signatures, ECDSA-based DCAP quotes, TDX quotes, CCA attestation tokens, and TPM quotes. Finally, we analyze empirical performance overheads, the side-channel and fault-injection attack classes that defeated successive SGX trust assumptions, and the trusted-computing-base recovery model. The analysis identifies convergence toward virtual-machine-scoped enclaves with hardware-enforced metadata integrity as the dominant design pattern.

## 1. Introduction

Modern computing rests on an untenable assumption: that privileged software — OSes, hypervisors, firmware, cloud operators — can be trusted. Supply-chain compromises and multi-tenant cloud economics have eroded the *defense-in-depth* layering that roots trust in the kernel [1][2]. **Confidential computing** is the architectural response: hardware-rooted mechanisms that invert the trust hierarchy, keeping workloads *confidential* and *integrity-protected* even when all privileged software is adversarial.

The field's intellectual origin is the *secure remote computation* problem [2]: outsourcing computation to an untrusted machine while retaining assurance over code and data. Early instantiations — IBM's 4758, the TPM, Intel TXT — offered coarse whole-machine measurement or expensive dedicated hardware. The 2013 introduction of **Intel SGX** [1] marked a discontinuity: the first commodity CPU with *application-granular* enclaves, hardware memory encryption, and remote attestation, shrinking the TCB from millions of lines of OS/hypervisor code to the processor package, its microcode, and the enclave's own code.

SGX's deployment history catalogued a rich attack taxonomy — *controlled-channel* oracles [3], **Foreshadow** transient exfiltration [4], **Plundervolt** fault injection [5] — repeatedly forcing *TCB recovery*: coordinated microcode, firmware, and attestation-infrastructure updates restoring a broken hardware root of trust. Intel bifurcated the architecture: hardened SGX2 for process-granular isolation, and **Trust Domain Extensions (TDX)** [6] elevating the enclave to an entire *virtual machine* managed by a CPU-attested module in *Secure-Arbitration Mode* (SEAM). In parallel, **Arm** introduced **CCA** [7][8]: the Realm Management Extension adds *Realm* and *Root* worlds, a tiny *Realm Management Monitor* (RMM) mediates memory delegation, and hardware *Granule Protection Tables* (GPTs) enforce world isolation per transaction.

> **Theorem (Attestation Soundness, informal):** If a verifier appraises evidence $E$ generated by an attesting environment whose keys are provisioned by a hardware root of trust $R$, and $R$ is uncompromised, then a positive attestation result implies — with probability bounded by the cryptographic strength of the signature scheme — that the measured software identity corresponds to the code that generated $E$.

This thesis (i) decomposes SGX, TDX, and Arm CCA along memory protection, trust-boundary topology, and attestation axes; (ii) formalizes their attestation protocols within the IETF RATS framework [9]; and (iii) analyzes empirical costs, attack-driven TCB evolution, and the resulting design lessons.

## 2. Background

### 2.1 The Threat Model of Confidential Computing

Confidential computing architectures share an adversary model strictly stronger than the classical OS threat model:

1. **Privileged software is malicious.** OS, hypervisor, SMM, drivers, and cloud control plane may read, write, remap, or interrupt any workload memory or I/O.
2. **Physical attacks are partially in scope.** Cold-boot and DRAM probing must be defeated by memory encryption and integrity protection; package decapsulation is excluded.
3. **Side channels are (controversially) out of scope.** Intel disclaims specific SGX side-channel mechanisms [2]; the enclave author owns constant-time code. This exclusion is the most productive source of academic attacks.

Guaranteed: **confidentiality** against all outside software and off-package observation; **integrity** against tampering, splicing, and replay; and **measurement freshness** — the remote party learns exactly which code produced the evidence.

### 2.2 Measurement, Sealing, and the Roots of Trust

All three architectures implement *measurement*: a hash over initial code/data pages forming an immutable software identity — `MRENCLAVE` (SHA-256 over the `ECREATE`/`EADD`/`EEXTEND` sequence) in SGX [1], `MRTD` plus four `RTMR` registers (TPM-PCR analogues) in TDX [6], and the RMM-recorded realm initial measurement in CCA [7].

**Sealing** binds data to a platform-and-identity tuple: SGX derives keys via `EGETKEY` parameterized by `MRENCLAVE` or `MRSIGNER` [1][2]; TDX provides analogous keys through the TDX module. *Sealed data is recoverable only by identical (or identically-signed) software on the same CPU* — modulo TCB-recovery versioning (§5.3).

### 2.3 The IETF RATS Framework

RFC 9334 [9] standardizes the *conceptual architecture* of remote attestation, separating *roles* from *entities* and *conceptual messages* from wire formats:

| Role | Function | SGX instantiation |
|---|---|---|
| **Attester** | Generates *Evidence* about its state | Enclave + Quoting Enclave (QE) |
| **Verifier** | Appraises Evidence against *Reference Values* using *Appraisal Policy* | Intel Attestation Service (IAS) / DCAP verifier |
| **Relying Party** | Consumes *Attestation Results* | Cloud tenant / data owner |
| **Endorser** | Supplies *Endorsements* (signed device metadata) | Intel Provisioning Certification Service (PCS) |
| **Reference Value Provider** | Supplies expected measurements | Software vendor |

The **passport** and **background-check** topologies govern evidence conveyance, and *freshness* is established via nonces, synchronized clocks, or epoch identifiers [9].

## 3. Methodology

We compare the three platforms spanning the commodity confidential-computing design space as of 2026: application-enclave (SGX), VM-enclave with vendor module (TDX), and ISA-level world isolation with minimal trusted firmware (Arm CCA).

Architectural claims rest on primary sources [1][2][6][7][8][9] and the original attack publications [3][4][5]; performance figures are ranges from peer-reviewed evaluations. Each platform is decomposed along three axes: **(A) memory protection** (encryption, integrity, metadata placement), **(B) trust-boundary topology** (TCB membership at each boundary), and **(C) attestation** (evidence generation, keying, appraisal, SVN versioning). Out of scope: GPU TEEs, AMD SEV-SNP, RISC-V Keystone, and reproduction of RMM/TDX-module verification efforts.

## 4. Deep Dive

### 4.1 Intel SGX: Enclave Memory Encryption and the Memory Encryption Engine

SGX carves the **Processor Reserved Memory (PRM)** — a BIOS-reserved range set via PRMRR registers — out of physical memory [1]. Within PRM lies the **Enclave Page Cache (EPC)**: 4 KiB pages for enclave code/data. Every EPC page has a hardware-resident **Enclave Page Cache Map (EPCM)** entry, consulted on *every* translation alongside legacy page tables [1][2]:

- the **page type**: `PT_REG` (regular), `PT_TCS` (thread control structure), `PT_VA` (version array), `PT_SECS` (enclave control structure), `PT_TRIM`, `PT_SS_*` (SGX2);
- the **owning enclave** (pointer to its SECS);
- the **virtual address** through which the enclave may access the page;
- **R/W/X permissions** and the **BLOCKED** state used during eviction.

Thus even a compromised OS forging page tables cannot redirect or alias enclave pages: the EPCM check runs in microcode against OS-unwritable state [2].

**The Memory Encryption Engine (MEE).** On LLC eviction to DRAM, the MEE encrypts the line (AES-CTR, CPU-ephemeral key) and maintains integrity via a **Merkle tree** over per-page 64-bit version counters — 512 counters per *version array* (VA) page — with the tree root in on-die SRAM [2]. Fetches decrypt and verify the MAC chain to the root; mismatch raises a machine-check exception. This defeats *splicing*, *replay*, and *relocation* attacks. The tree walk, logarithmic in EPC size, dominates SGX memory overhead on LLC misses [2].

> **Theorem (MEE integrity):** Under the assumption that the on-die integrity-tree root is unobservable and unmodifiable, any tampering with an EPC page in DRAM is detected with probability $1 - 2^{-k}$, where $k$ is the MAC length, before the corrupted data is consumed by enclave code.

**Paging and eviction.** EPC is finite, so the OS may evict pages: `EWB` encrypts a page with a per-eviction key, stores ciphertext+MAC in untrusted memory, and records the version counter in a VA page; `ELDB`/`ELDU` reload only on counter match, defeating replay [1]. `EBLOCK`/`ETRACK` handle TLB shootdown. The OS retains *resource management* without *access* — the pattern all three platforms replicate.

**Execution model.** `EENTER`/`EEXIT` bracket synchronous execution; faults trigger asynchronous enclave exit (AEX), scrubbing registers into TCS state-save frames [1]. AEX is what enabled *controlled-channel attacks*: a malicious OS induces page faults at chosen instructions and reconstructs secret-dependent control flow from faulting addresses [3].

### 4.2 Intel TDX: Trust Domains and Secure-Arbitration Mode

Where SGX isolates *regions of an application's address space*, TDX isolates *entire virtual machines*: a **Trust Domain (TD)** is a hardware-protected VM whose CPU state and memory are inaccessible to the hypervisor, host OS, SMM, and DMA devices [6]. Cloud tenants run unmodified guest OS images expecting VM semantics — vCPUs, device passthrough, live migration — which application enclaves cannot provide without heroic library-OS engineering.

**SEAM: a new CPU mode.** TDX adds *Secure-Arbitration Mode*, a third VMX-like mode entered via `SEAMCALL`/`SEAMRET`, hosting the CPU-attested, Intel-signed **TDX module** in a measured, access-isolated **SEAM memory range** (SEAMRR) [6]. Only the TDX module can create, enter, or destroy TDs; the untrusted VMM merely *requests* lifecycle operations and manages physical resources — SGX's resource-management/access split at VM scale.

**Memory protection: MKTME and PAMT.** TD private memory is encrypted with **MKTME**: each TD gets a *host key ID* (HKID); the memory controller applies AES-XTS-128 per line with a 28-bit MAC (MKTME with integrity) [6]. Encryption alone cannot stop a malicious VMM from *remapping* TD pages, so TDX maintains the **Physical Address Metadata Table (PAMT)** — per-page ownership, page type, and SEPT state — the EPCM's conceptual descendant at VM granularity [6]. The module-exclusive **SEPT** (Secure EPT) translates guest-physical to host-physical addresses, closing the remapping attack pure encryption would leave open.

**Measurement and attestation.** TD build extends `MRTD` (SHA-384 over initial pages and parameters); `TDG.MR.REPORT` extends the four `RTMR`s at runtime, the TPM-PCR analogue [6]. Attestation flows `TDG.MR.REPORT` → **TD Quoting Enclave** → **TD Quote**, ECDSA-signed via Intel PCS (the DCAP model, §4.4), binding `MRTD`, `RTMR`s, module SVN, and 64-byte `REPORTDATA`.

**Live migration.** Dedicated **Migration TDs (MigTDs)** on source and destination mutually attest, negotiate transport keys, and the source module re-encrypts TD state under a migration key — *attestation-composed* key establishment [6].

### 4.3 Arm CCA: Realms, the RMM, and Granule Protection

Arm CCA takes a third path: extending the *architecture itself*. The Realm Management Extension (RME) in Armv9-A adds **Realm** and **Root** worlds alongside Secure and Non-secure, selected by `SCR_EL3`'s `NS`/`NSE` bits [7][8]:

| World | Security state | Physical address space | Typical occupant |
|---|---|---|---|
| **Root** | Root (`EL3`) | Root PA | Monitor firmware, GPT management |
| **Realm** | Realm (`R_EL2`/`R_EL1`/`R_EL0`) | Realm PA | Confidential VMs, RMM |
| **Secure** | Secure (`S_EL2`/`S_EL1`/`S_EL0`) | Secure PA | TrustZone TAs (unchanged) |
| **Normal** | Non-secure (`EL2`/`EL1`/`EL0`) | Non-secure PA | Hypervisor, rich OS |

Crucially, Root world has its *own* physical address space — unlike Armv8 TrustZone, where EL3 code lived in Secure PA — so monitor firmware is isolated even from Secure-world software [7].

**Granule Protection Tables.** Each 4 KiB granule's *Physical Address Space* (PAS) is recorded in **GPTs** managed by Root-world firmware; every translation performs a hardware **Granule Protection Check (GPC)** beyond stage-1/stage-2 tables [8]. The hypervisor may only *request* delegation — Root firmware alone updates the GPT — so forged page tables cannot grant Realm access. The GPT is the Arm analogue of the EPCM/PAMT lineage: metadata integrity enforced below the adversary's reach.

**The Realm Management Monitor.** The **RMM**, a small firmware component at `R_EL2`, multiplexes Realm VMs: inter-realm isolation, realm stage-2 tables, realm exits, and the realm's initial measurement [7]. The hypervisor drives lifecycle via the **RMI** (`RMI_GRANULE_DELEGATE`, `RMI_REALM_CREATE`, …), but every Realm-touching call is mediated and validated by the RMM, and delegated granules are measured before boot. The RMM specification is public and verification-targeted — a deliberate contrast with the closed TDX module.

**Memory encryption and attestation.** Realm memory is optionally encrypted under per-realm **Memory Encryption Contexts (MEC)** [7]. Attestation yields a COSE-signed **CCA token** pairing a *platform token* (hardware root of trust: lifecycle state, firmware measurements) with a *realm token* (RMM attestation key: realm measurement, signer, challenge) — cleanly separating *platform appraisal* from *workload appraisal*, unlike SGX's monolithic quote [7].

### 4.4 Attestation Protocols: EPID, DCAP, TPM Quotes, and Freshness

**Local attestation (SGX).** `EREPORT` yields a `REPORT` (`MRENCLAVE`, `MRSIGNER`, attributes, 64-byte `REPORTDATA`) MACed under a per-target-enclave *Report Key* known only to the CPU and target [1].

**EPID remote attestation.** The Quoting Enclave signs a **QUOTE** with an *EPID* group signature key provisioned by Intel [2], giving *unlinkability*: the verifier (Intel Attestation Service) confirms a genuine, non-revoked SGX processor without identifying it — at the cost of IAS as a mandatory online intermediary and a hard dependency on Intel.

**DCAP/ECDSA attestation.** DCAP replaces the group signature with a per-platform **ECDSA attestation key** certified by the **PCE**; the chain (PCK → intermediate → Intel root CA) is published by **PCS** and cached by the verifier [6]. This enables *offline, third-party* verification at the cost of *linkability*: one platform's quotes are correlatable. SGX/TDX quote structures share a common header plus report body and 64-byte `report_data` [6].

**TPM quotes.** `TPM2_Quote` signs selected PCRs with an AIK [9]: TPM attestation measures *boot-time* software, enclave attestation measures *runtime* workloads — complementary, and increasingly composed via TDVF event logs.

**Freshness and TCB versioning.** Every protocol binds a verifier **nonce** into the signed structure to defeat replay [9], and carries **SVN** fields (`CPUSVN`, `QE_SVN`, TDX module SVN) so verifiers enforce *TCB freshness*: post-disclosure, appraisal policy rejects unpatched platforms. Intel increments SVNs in microcode updates while verifiers ratchet minimum-SVN policies — the attestation-layer mechanism of **TCB recovery** [4][5].

```c
int verify_quote(const sgx_quote_t *q, const pck_chain_t *c,
                 uint64_t min_svn, const uint8_t nonce[32]) {
    if (!verify_pck_chain(c, INTEL_ROOT_CA)) return -EKEYREJECTED;
    if (!ecdsa_verify(c->pck_pubkey, q->signature, q->report_body)) return -EBADSIG;
    if (memcmp(q->report_body.cpusvn, &min_svn, 16) < 0) return -ESTALE_TCB;
    if (memcmp(q->report_body.report_data, nonce, 32) != 0) return -EREPLAY;
    return appraisal_policy_check(q->report_body.mrenclave, q->report_body.mrsigner);
}
```

## 5. Empirical Results and Security Analysis

### 5.1 Performance Overheads

The dominant cost everywhere is *integrity verification on LLC miss* — SGX's MEE tree walk, TDX's MKTME MAC check, CCA's GPC+MEC lookup. Peer-reviewed evaluations cluster consistently:

| Platform | Workload class | Reported overhead | Dominant cost |
|---|---|---|---|
| SGX (MEE) | Memory-intensive, EPC-resident | 5–15% | Integrity-tree walks on LLC miss |
| SGX (MEE) | EPC paging (working set > EPC) | 10–100× | `EWB`/`ELDB` crypto + VA updates |
| TDX (MKTME) | VM workloads, TD-private memory | 3–10% | AES-XTS + MAC per line, SEPT walks |
| Arm CCA (RMM) | Realm VM boot + runtime | 5–12% + boot latency | Granule delegation, GPC checks |
| Attestation | Quote generation (SGX/TDX) | 10–100 ms | QE signing, PCS round-trips (EPID) |

SGX's pathological case — EPC oversubscription — motivated the industry's migration to VM-scoped TEEs: `EWB`/`ELDB` paging with version-counter bookkeeping collapses throughput, while TDX encrypts *entire* TD memory with no software-visible paging boundary [2][6]. Library OSes quantify the usability gap: **Gramine** lifts unmodified Linux binaries into SGX via a minimal host interface [10]; **Occlum** runs a memory-safe multi-process LibOS in one enclave [11] — both paying thousands of cycles per `ECALL`/`OCALL` to avoid rewriting applications.

### 5.2 Attack Taxonomy and Defeated Assumptions

Each major attack class defeated a specific SGX trust assumption, and the mitigations reshaped the architecture:

1. **Controlled-channel attacks** [3]. A malicious OS infers secret-dependent control flow from page-fault addresses. *Defeated assumption:* the OS cannot learn enclave behavior. *Response:* application-level ORAM/multiplexing; SGX2 `EDMM` and TDX's VM granularity coarsen observable events.
2. **Foreshadow / L1TF** [4]. Transient execution dereferences enclave L1 lines via terminal page faults, exfiltrating *attestation keys* — a total break of the SGX trust root on unpatched microcode. *Defeated assumption:* speculation respects enclave boundaries. *Response:* microcode plus L1 flush on enclave exit, and **TCB recovery**: incremented `CPUSVN` with verifiers rejecting stale SVNs, forcing fleet-wide patching.
3. **Plundervolt** [5]. Privileged software undervolts the CPU via `MSR 0x150`, injecting *faults into enclave computation* — breaking the integrity SGX was assumed to guarantee absolutely. *Defeated assumption:* the CPU executes enclave instructions faithfully. *Response:* microcode disabling the undervolting interface; attestation requires the mitigation SVN.
4. **MDS** (RIDL, Fallout, ZombieLoad) and **LVI** [4][5] showed *confidentiality against transient execution* cannot be bolted onto SGX's threat model — a key driver for TDX's VM-level design, where the guest kernel controls mitigations like `VERW` flushing.

The pattern is architectural: **every implicit hardware assumption about the execution environment eventually became an attack surface**, and recovery always required coordinated microcode, attestation-infrastructure, and verifier-policy changes — the *TCB recovery* lifecycle.

### 5.3 TCB Recovery as a Protocol

TCB recovery is a four-phase distributed protocol: (i) *disclosure and embargo*, (ii) *microcode/firmware release* with incremented SVNs, (iii) *attestation infrastructure update* (IAS policy, PCS CRLs, DCAP collateral refresh), and (iv) *verifier ratcheting*, where relying parties raise minimum-SVN thresholds, amputating unpatched platforms. Phase (iv)'s long tail of unpatched hosts is the dominant real-world cost of a hardware TEE vulnerability — unavoidable, since the root of trust cannot be patched without rebooting into new microcode, and old quotes stay valid until verifiers reject them [4][5][9].

## 6. Limitations

**Side channels remain out of contract.** All three vendors exclude microarchitectural side channels; enclave authors must write constant-time, oblivious code — yet this is where real adversaries operate [3][4][5].

**Availability.** No platform stops a malicious hypervisor from refusing to schedule the workload; sealed-data *rollback* is only mitigated by limited monotonic counters.

**Vendor centralization.** DCAP decentralizes verification but not *provisioning* — the PCE/PCK chain still roots in Intel's CA, a single point of catastrophic failure.

**TCB still includes the CPU.** Microcode, the TDX module, the RMM, and Root-world firmware are trusted absolutely; the RMM's public, verification-targeted specification [7] reduces but does not eliminate this.

**Composability gaps.** Nested TEEs lack standardized attestation composition; multi-verifier topologies [9] are specified but rarely deployed; TDX live migration extends the TCB across *two* platforms' attestation chains.

**Granularity vs. usability.** SGX's process granularity minimizes the TCB but maximizes porting effort; TDX/CCA's VM granularity restores compatibility at the cost of a full guest OS inside the trust perimeter.

---

## 7. Conclusion

SGX, TDX, and Arm CCA share one design lineage: *hardware-maintained per-page metadata* (EPCM → PAMT → GPT), *memory encryption with integrity* (MEE → MKTME → MEC), and *attestation as a keyed measurement protocol* (EPID → DCAP → CCA tokens) formalized by RATS [1][2][6][7][8][9]. Empirically: single-digit overheads for resident workloads, catastrophic overheads for paging. Adversarially: every implicit trust assumption — faithful execution (Plundervolt [5]), speculation hygiene (Foreshadow [4]) — was eventually weaponized, and recovery always ran through the attestation infrastructure's SVN ratchet.

Three lessons emerge. *First*, the metadata table is the true security primitive: encryption without integrity-protected ownership metadata cannot survive a malicious memory manager. *Second*, attestation must be designed for *recovery*, not just verification — versioned TCB identities and verifier-side ratcheting make hardware vulnerabilities survivable. *Third*, openness compounds security: the RMM's public specification [7] and DCAP's third-party verifiability point toward a TCB that is *auditable*, not merely *attested*. The open problems — side-channel-inclusive threat models, nested attestation composition, decentralized roots of trust — define the next decade of research.
