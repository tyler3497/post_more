# Static Single-Assignment Form and Modern Register Allocation: Graph-Coloring Allocation, Linear Scan, and the Partitioned Boolean Quadratic Problem

## Abstract

Register allocation maps an unbounded set of virtual values onto a finite register file while minimizing spill traffic, and Static Single-Assignment (SSA) form is the dominant intermediate representation in which this mapping is analyzed. This thesis unifies the two subjects: the dominance-frontier construction of SSA — phi-function placement and renaming [1] — with the subtleties of SSA destruction, including the lost-copy and swap problems of phi sequentialization. We then develop three allocation paradigms: Chaitin-style graph-coloring allocation with Briggs' optimistic spilling and iterated register coalescing [2][3][4][6]; Poletto and Sarkar's linear-scan allocation with second-chance binpacking refinements [5]; and the Partitioned Boolean Quadratic Programming (PBQP) formulation of Scholz and Eckstein for irregular architectures [7][8]. Worked examples quantify register pressure and spill decisions; benchmark data from the literature compare allocator quality against compile-time cost; and we close by appraising NP-hardness barriers, coalescing phase-ordering dilemmas, and PBQP solver scalability.

##1 Introduction

*Register allocation* assigns the unbounded virtual values of optimized code to a small, fixed set of physical registers; every value that does not fit must be *spilled* to memory, and the resulting traffic can dominate running time. The problem is NP-complete in its graph-coloring formulation [2], so production compilers live with heuristics — and heuristic quality separates adequate code generators from excellent ones.

In *Static Single-Assignment form*, every variable is defined exactly once, and a *phi-function* (φ) selects among incoming values wherever control flow merges definitions [1]. Developed at IBM and published in 1991 by Cytron, Ferrante, Rosen, Wegman, and Zadeck, SSA is now the core IR of LLVM, GCC, HotSpot, and V8 — and its single-definition discipline makes data flow explicit and interference structure well-behaved, which is exactly what allocators need.

This thesis treats SSA construction and register allocation as one continuous subject. Our contributions are:

1. SSA construction via *dominance frontiers*: phi placement, renaming, pruning [1].
2. SSA *destruction*: the lost-copy and swap problems of naive phi elimination.
3. Three allocation families: **graph coloring** with optimistic spilling and iterated coalescing [2][3][4][6]; **linear scan** with second-chance binpacking [5]; **PBQP** for irregular architectures [7][8].
4. Worked examples, literature benchmark comparisons, and correctness sketches.

Section 2 fixes terminology; Section 3 presents SSA construction and destruction; Section 4 develops the three allocation paradigms; Section 5 gives worked examples and proof sketches; Section 6 states the limitations; Section 7 concludes.

##2 Background

### 2.1 Control-flow graphs and dominance



> **Definition (Dominance).** A block *A* *dominates* a block *B* if every path from the entry block to *B* passes through *A*. *A* *strictly dominates* *B* if *A* dominates *B* and *A* is not *B*.



### 2.3 The allocation sub-problems

| Sub-problem | Question it answers |
|---|---|
| **Spilling** | Which live ranges to evict to memory when *k* colors do not suffice, and where to place spill code |
| **Coalescing** | Which copy-related live ranges to merge so copies can be eliminated |
| **Splitting** | Where to cut a long live range into pieces to reduce peak register pressure |
| **Rematerialization** | Which values are cheaper to recompute than to spill and reload |
| **Assignment** | The final mapping of live ranges (or live-range fragments) to physical registers |

##3 Methodology

## 3.1 The dominance frontier

The key question of SSA construction is *where phi-functions are required*. A phi is needed exactly where definitions of the same variable from different control paths converge. Cytron et al. captured "convergence" with a new concept [1]:

> **Definition (Dominance frontier).** The *dominance frontier* DF(*n*) of a block *n* is the set of blocks *z* such that *n* dominates some predecessor of *z* but does *not* strictly dominate *z*.

Intuitively, DF(*n*) is where *n*'s control-flow influence ends. If *n* defines *v*, any join where *n*'s definition meets another definition of *v* lies in DF(*n*) — so a phi for *v* belongs at the head of each block in DF(*n*).

### 3.2 Phi-function placement

Placement is an iterated fixed-point computation. Let Defs(*v*) be the set of blocks containing a definition of *v*:

```
for each variable v:
    worklist W = Defs(v);  placed = empty set
    while W is nonempty:
        remove a block n from W
        for each block z in DF(n):
            if z not in placed:
                insert "v = φ(v, v, ...)" at the head of z
                placed = placed ∪ {z}
                if z not in Defs(v):      # the φ is itself a new definition
                    Defs(v) = Defs(v) ∪ {z}
                    add z to W
```

Iteration is necessary because each phi is a *new definition* of *v* with its own frontier; the finite fixed point is the *iterated dominance frontier* DF⁺(Defs(*v*)) [1].

Naive placement inserts useless phis too. Three disciplines control this:

- **Maximal SSA**: place everywhere the criterion demands; simple but bloated.
- **Semi-pruned SSA**: skip single-definition variables — they need no phis.
- **Pruned SSA**: also suppress phis with dead results; needs liveness, yields the minimal practical form.

### 3.3 Renaming

Renaming walks the *dominator tree* in preorder, maintaining a stack of current versions per variable [1]:

```
rename(block b):
    for each instruction i in b (in order):
        rewrite each use with the version on top of stack[var]
        assign a fresh version v_k to the definition; push v_k
    for each successor s of b:
        for each φ in s: set the operand corresponding to edge b→s
            to the version on top of stack[var]
    for each child c of b in the dominator tree:
        rename(c)
    pop the versions pushed in b
```

By the dominator-tree walk, the stack top is always the *unique reaching definition* — the invariant all SSA optimization rests on. The algorithm is linear in program size plus inserted phis.

### 3.4 Worked construction example

Consider:

```c
x = 1;                 // block B0
if (p)  x = 2;         // block B1
else    x = 3;         // block B2
y = x + 1;             // block B3 (join)
```

DF(B1) = DF(B2) = {B3}: each branch block dominates its own exit edge but not the join. Placement inserts `x_3 = φ(x_1, x_2)` at B3, and renaming yields `y_0 = x_3 + 1` — the phi makes explicit *which* value of `x` reaches the join.

### 3.5 SSA destruction: the lost-copy and swap problems

Code generation cannot execute phis — a phi is a *notational* "select by incoming edge." The standard translation replaces each phi `v = φ(a_1, ..., a_n)` in *B* with copies `v = a_i` at the end of each predecessor *B_i*, splitting *critical edges* so each copy executes exactly when its edge is taken.

Two classic hazards make naive copy insertion wrong:

- **The lost-copy problem.** With phis `x = φ(a, ...)` and `y = φ(x, ...)` in one block, naive edge copies `x = a; y = x` destroy the incoming `x` the second phi needed — the first copy is "lost" to the second phi.
- **The swap problem.** Phis `x = φ(y, ...)` and `y = φ(x, ...)` form a pure exchange; sequential copies `x = y; y = x` leave both holding the old `y` — a temporary is required.

The robust fix treats a block's phis as a *parallel copy* — conceptually simultaneous — then *sequentializes* it, breaking permutation cycles with one temporary [1]. LLVM keeps phis late in the IR and lowers them with a parallel-copy pass handling both hazards uniformly:

```llvm
join:                                     ; preds = %left, %right
  %x = phi i32 [ %a, %left ], [ %b, %right ]
  ret i32 %x
; after out-of-SSA, on edge left->join:  %x = %a
; after out-of-SSA, on edge right->join: %x = %b
```

##4 Deep Dive

### 4.1 Chaitin-style graph-coloring allocation

Chaitin et al. framed register allocation as graph coloring for a PL/I compiler targeting the IBM System/370 [2], adding principled spilling in 1982 [3]. Four phases:

1. **Build.** Compute liveness and build the interference graph — one node per live range (per SSA version in modern variants).
2. **Simplify.** Repeatedly remove a node of degree below *k*, pushing it on a stack — it is guaranteed colorable later, since at most *k*−1 neighbors can be colored when it is popped.
3. **Spill.** If all remaining nodes have degree at least *k*, remove a *spill candidate* of minimum spill-cost-over-degree [3], and continue.
4. **Select.** Pop nodes, coloring each differently from its colored neighbors; uncolorable spill candidates get spill code and the process repeats.

**Briggs' optimistic improvement.** Chaitin's spill phase commits too early: a removed *potential* spill might have been colorable once high-degree neighbors are gone. Briggs, Cooper, and Torczon [4] *defer* the decision to select: nodes are pushed even when all have degree at least *k*, and only during select — with true colored-neighbor sets known — is a node actually spilled. This *optimistic coloring* strictly dominates Chaitin's in code quality and underlies most production allocators.

**Iterated register coalescing.** Copies `x = y` vanish if `x` and `y` share a register — but merging live ranges can uncolor a colorable graph. George and Appel's *iterated* scheme [6] interleaves coalescing with simplification using four worklists:

| Worklist | Holds nodes that are... |
|---|---|
| *simplify* | degree < *k*, not move-related |
| *freeze* | degree < *k*, move-related |
| *spill* | degree ≥ *k* |
| *worklistMoves* | copy instructions available for coalescing |



> **Theorem (Simplify safety).** *If a node n has degree strictly less than k at the moment it is removed during simplification, then n can always be colored in the select phase regardless of the colors assigned to its neighbors.*

*Proof sketch.* When *n* is popped, only neighbors still on the stack below it are colored — at most degree(*n*) < *k* of them. Hence at least one of the *k* colors is free. ∎

### 4.2 Linear scan and second-chance binpacking

Graph coloring builds a quadratic interference graph and iterates to a fixed point — too slow for JIT compilers, where compile time is user-visible. Poletto and Sarkar [5] approximate each live range by one *live interval* (first definition to last use) and sweep intervals in start order over an *active* set, expiring finished intervals and recycling their registers:

```
active = empty set
for each interval i in order of increasing start:
    expire intervals in active ending before start(i)
    if active is full: spill the interval with the farthest end
    else: assign i a free register; add i to active
```

No interference graph is ever built: *O(n log n)* time, linear memory. The price is precision — intervals are convex over-approximations causing false interferences — yet measured code lands within 12% of aggressive coloring on all but two benchmarks while compiling several times faster [5]. **Second-chance binpacking** [5] recovers precision with *lifetime holes* (dead stretches inside intervals, tracked via an *inactive* set) and interval splitting around hot regions — the middle ground between minimal scan and full coloring.

**Second-chance binpacking.** Traub, Holloway, and Smith observed that much of linear scan's imprecision comes from *lifetime holes* — stretches inside an interval where the value is provably dead — and from spilling entire intervals when only a fragment is problematic [5]. Their *second-chance binpacking* keeps intervals with holes in an *inactive* set (register freed during the hole, reclaimed after), splits intervals around high-pressure regions, and gives each interval a second chance at a register after spilling decisions. It invests more compile time for measurably better code — the middle ground between Poletto's minimal scan and full coloring.



### 4.3 The PBQP formulation of register allocation

Graph coloring assumes registers are interchangeable colors — adequate for uniform RISC files, poor for DSPs and irregular CISC targets. Scholz and Eckstein recast allocation as *Partitioned Boolean Quadratic Programming* [7], which models such irregularities exactly.

**The model.** For each virtual value *vᵢ*, introduce a Boolean decision vector *xᵢ* over the register options (one-hot: exactly one entry is 1). Costs come in two parts:

- **Cost vectors** *cᵢ*: *cᵢ(r)* prices *vᵢ* ↦ *r* — infinite for forbidden registers, spill cost for the spill option.
- **Cost matrices** *Cᵢⱼ*: *Cᵢⱼ(r, s)* prices the joint assignment — infinite for *r* = *s* on interfering values, discounted when a copy is coalesced by *r* = *s*.

The objective is the quadratic pseudo-Boolean function

> minimize  Σᵢ *xᵢᵀcᵢ*  +  Σᵢ<ⱼ *xᵢᵀCᵢⱼxⱼ*  subject to each *xᵢ* one-hot.

The NP-complete problem is attacked with optimality-preserving reductions, plus branch and bound as fallback:

| Reduction | Applies when | Action |
|---|---|---|
| **R0** | node independent (no edges) | assign its minimum-cost option, delete |
| **R1** | node has exactly one neighbor | fold its costs into the neighbor's vector, delete |
| **R2** | node has exactly two neighbors | fold its costs into the edge between them, delete |
| **RN** | none of the above apply | branch: fix the minimum-cost option, recurse (branch and bound) |



**Impact.** On the Infineon Carmel DSP compiler, the PBQP allocator beat traditional coloring on irregular code [7]. With branch-and-bound search, Hames and Scholz solved 97.4% of SPEC2000 functions *to proven optimality* [8] — nearly exact on real code. LLVM shipped a PBQP allocator built on this work, later reused for instruction selection and DNN primitive selection.



### 4.4 SSA-based allocation and out-of-SSA translation

In strict SSA form, interference graphs are chordal — every cycle of length four or more has a chord — and chordal graphs admit greedy optimal coloring in linear time: the NP-hard core of coloring evaporates. Production compilers exploit this asymmetrically, optimizing on SSA and translating *out of* SSA around allocation. The translation must preserve parallel-copy semantics:

1. **Insert parallel copies** for each phi-block on incoming edges (splitting critical edges).
2. **Sequentialize** each parallel copy: decompose into cycles and chains; break each cycle with one temporary.
3. **Coalesce afterward**: most inserted copies join values the allocator assigns to the same register, so a post-allocation pass removes them — why iterated coalescing [6] and out-of-SSA translation are deeply intertwined.

##5 Empirical Results and Proof Sketches

### 5.1 Worked example: register pressure and the spill decision

Consider this fragment for a machine with *k* = 2 registers:

```c
a = ...;          // def a
b = ...;          // def b
c = ...;          // def c
d = a + b;        // use a, b; def d
e = c + d;        // use c, d
```

After the three definitions, *a*, *b*, *c* are simultaneously live — pressure 3 over *k* = 2. The interference graph is the triangle *K3* (chromatic number 3), so one range must spill; with costs 100, 100, 10, Chaitin's cost-over-degree metric [3] selects *c*.





- **Chaitin 1981/82 [2][3]**: *c* is removed as a definite spill; *a*, *b* simplify and take R0, R1; spill code is inserted for *c* and allocation iterates.
- **Briggs optimistic [4]**: *c* is pushed as a *potential* spill but finds no free color during select — same outcome here, though Briggs avoids spills whenever the candidate would fit.
- **Linear scan [5]**: *a* ↦ R0, *b* ↦ R1 in start order; *c* finds the active set full and, having the farthest end, is spilled.
- **PBQP [7]**: infinite conflict entries make spilling *c* at cost 10 the minimum — all four paradigms agree on this forced decision, via very different machinery.

### 5.2 Benchmark comparisons from the literature

| Allocator | Compile-time cost | Code quality (reported) | Source |
|---|---|---|---|
| Chaitin-style coloring | Interference graph + iterate to fixed point; slowest | Baseline for quality comparisons | [2][3] |
| Briggs optimistic + iterated coalescing | Graph + worklists; moderate | *Aggressive* reference: best code among heuristics | [4][6] |
| Linear scan (Poletto–Sarkar) | *O(n log n)*, no graph; several × faster than fast coloring | Within 12% of aggressive coloring on all but two benchmarks | [5] |
| Second-chance binpacking | Between linear scan and coloring | Better than plain linear scan; costs more compile time | [5] |
| PBQP heuristic | Nearly linear via reductions | Optimal on 97.4% of SPEC2000 functions (with branch and bound) | [7][8] |

Two patterns emerge: compile time buys quality with sharply diminishing returns, while exact modeling buys the last few percent.

### 5.3 Correctness sketch: minimal phi placement

> **Theorem (Cytron et al. [1]).** *Placing phi-functions for a variable v exactly at the iterated dominance frontier DF⁺(Defs(v)) yields a correct SSA form: every use of v is reached by exactly one definition, and no join point lacking a phi can merge two distinct definitions of v.*

*Proof sketch.* If two definitions *d₁*, *d₂* of *v* both reach a join *z* with no phi, follow a path from *d₁* avoiding *d₂*'s block; the last block on it dominated by *d₁*'s block has a successor in the frontier of *d₁*'s region — iterating, *z* lies in DF⁺(Defs(*v*)), contradiction. Renaming then gives each use its unique reaching definition. ∎



### 5.4 Correctness sketch: parallel-copy sequentialization

> **Claim.** *Any parallel copy {x₁ = y₁, ..., xₙ = yₙ} can be sequentialized using at most one temporary register.*

*Proof sketch.* The copy relation decomposes into disjoint chains and cycles. Chains emit directly in reverse topological order. Each cycle *x₁ = x₂, x₂ = x₃, ..., xₘ = x₁* is broken by `t = x₁` followed by the chain — one temporary suffices, and cycles are independent. ∎

##6 Limitations

**NP-hardness is fundamental.** *k*-coloring is NP-complete [2], and *coalescing* is NP-hard even for *k*-colorable graphs — so production allocators layer heuristics [4][6] whose failure modes are known only empirically.

**Phase ordering plagues the pipeline.** Aggressive coalescing can uncolor a graph; early spilling destroys coalescing opportunities; splitting inserts copies for later passes. No optimal pass ordering is known, though iterated coalescing [6] mitigates one interaction.

**Splitting has hidden costs.** Cutting a live range around hot regions inserts copies at every split and can raise pressure elsewhere; the spill-vs-split choice is heuristic, and bad splits pessimize code that spilling would have handled.

**PBQP solvers do not scale uniformly.** R0–R2 collapse typical graphs nearly linearly [7], but adversarial functions hit exponential RN branching; production solvers cap effort with timeouts. The basic model also *excludes live-range splitting* — phase ordering through the back door [8].

**SSA destruction is not free.** Out-of-SSA translation inserts copies on critical edges and relies on the allocator to remove them; where coalescing fails, the "zero-cost abstraction" of phis becomes a real tax, especially with few registers.

**Irregular architectures resist uniform models.** Register classes, aliased pairs, and calling conventions fracture the coloring abstraction. PBQP models them exactly [7] at solver cost; coloring allocators approximate them with ad hoc constraints that interact poorly with coalescing.

##7 Conclusion

Static Single-Assignment form and register allocation are two halves of one idea: SSA makes the *values* of a program explicit, and allocation decides where those values *live*. The dominance-frontier construction of Cytron et al. [1] remains the definitive method for building SSA, and its destruction demands the same care — parallel-copy semantics that defeat the lost-copy and swap hazards.

Three paradigms span the design space: **graph coloring** [2][3] with optimistic spilling [4] and iterated coalescing [6] remains the quality reference; **linear scan** [5] trades some quality for JIT-grade compile speed; **PBQP** [7][8] unifies spilling, coalescing, and irregular constraints in one exact optimization.

Open problems endure: taming phase ordering, scaling exact methods to whole programs, and learning better spill-cost models. What is settled is the representation: the SSA discipline of precise, single-definition values is the foundation every allocator stands on.
