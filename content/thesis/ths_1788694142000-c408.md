# Compositional Sandboxing: The WebAssembly Component Model, WIT, and WASI as a Portable, Capability-Secure Compute Fabric

## Abstract

WebAssembly's core modules exchange only scalars, vectors, and references; every richer interaction is a host-specific import negotiated by private convention. The **WebAssembly Component Model**, developed by the WebAssembly Community Group and the Bytecode Alliance, inverts this arrangement: core modules are wrapped into *components* whose boundaries speak **interface types** — strings, records, variants, lists, and resource handles — declared in the **WIT** IDL and translated by the **canonical ABI**'s lifting and lowering. **WASI 0.2** (January 2024) rebases the system interface on this foundation, replacing a flat POSIX-like API with versioned, virtualizable, *capability-based* interface packages. This thesis argues that the component model is the first operating-system-independent, capability-secure application binary interface for portable compute. We expound its mechanisms — canonical lifting and lowering, own/borrow resource handles, worlds as import/export contracts, deny-by-default capability grants — prove round-trip fidelity and a handle-confinement theorem, derive the asymptotic cost of cross-component calls, and assess the remaining frontiers: async execution, threading, garbage collection, and versioning.

## 1 Introduction

Core WebAssembly [9] is, by design, a *closed* computational universe. A core module's imports and exports admit only numeric types, vector types, and opaque references — no strings, no lists, no files. Everything beyond arithmetic and linear-memory manipulation is *imported* from the host under whatever convention the host and toolchain privately agree upon. The 2017 MVP brought near-native speed to the browser; WASI (2019) then standardized a POSIX-flavored import set, `wasi_snapshot_preview1`, for use beyond it [8].

The flat-import convention has three structural weaknesses. First, it is *untyped where it matters*: a file descriptor is an `i32`, indistinguishable from an integer, so no tooling can reason about it. Second, composition is *shared-memory by convention*: cooperating modules must agree on linear-memory layouts that are fragile and invisible. Third, the security model is *ambient*: once a module can call `path_open`, the authority it wields is whatever the host granted, with no language in the binary to circumscribe it.

The **Component Model** [1] reframes what a WebAssembly binary *is*. A **component** wraps core modules (and nested components) in *typed* imports and exports expressed in **interface types** [5]: strings, records, variants, lists, tuples, enums, flags, options, results, and *resources* — opaque handles with ownership semantics. The **canonical ABI** [2] specifies, as pseudocode over an abstract machine, exactly how these values are *lowered* to core values and memory buffers and *lifted* back, covering alignment, flattening, string encodings, and the `realloc`/`post-return` discipline. **WIT** [3] is the human-authorable IDL for interfaces, packages, and **worlds** — named import/export contracts describing what a component needs and provides.

**WASI 0.2** (January 2024) [4] is the first full realization: the system interface is now versioned WIT packages (`wasi:filesystem@0.2.x`, `wasi:http@0.2.x`, …), importable piecemeal and *virtualizable* — a host may interpose on any interface. This thesis contributes: (1) a precise exposition of interface types, the canonical ABI, resources, and worlds from the primary specifications; (2) a characterization of WASI 0.2's capability-based security against Preview 1's ambient model; (3) an analytic cost model of cross-component calls plus two formal results — *round-trip fidelity* of lifting/lowering and a *confinement theorem* for resource handles; and (4) a critical assessment of the unfinished frontiers: async, threading, GC, and versioning.

## 2 Background and Related Work

### 2.1 From modules to components

Core WebAssembly became a W3C Recommendation in 2019 [9] with a deliberately minimal value domain. The **Interface Types** proposal (2019–2021) sought to define high-level types in the binary format; it was subsumed into the broader **Component Model**, which added *module linking* — components linking to components without host mediation — and the canonical ABI. The component format is a separate *layer*: like core modules it begins with the `\0asm` magic, but carries layer byte `0x01` and version `0x0d00` (pre-standardization) versus `0x00` for core modules [1].

### 2.2 WASI: Preview 1 to 0.2

WASI Preview 1 exposed roughly forty POSIX-like functions over a flat namespace (`fd_read`, `path_open`, `clock_time_get`). Its security was *capability-flavored but ambient in practice*: file access flowed through preopened directory descriptors, yet the surface was monolithic — importing the interface imported all of it. WASI 0.2 [4] decomposes it into seven versioned proposals (Table 1), each independently importable and virtualizable. Two canonical **worlds** ship with 0.2: `wasi:cli/command` (a traditional command-line process) and `wasi:http/proxy` (edge platforms serving streaming HTTP) [4]. Rust's `wasm32-wasip2` target reached tier-2 support in Rust 1.82 (October 2024), letting mainstream toolchains target the new interfaces directly [7].

| Proposal | Version in 0.2 | Provides |
|---|---|---|
| `wasi:io` | 0.2.x | Streams, pollables (async-shaped I/O) |
| `wasi:clocks` | 0.2.x | Wall clock, monotonic clock |
| `wasi:random` | 0.2.x | Cryptographic randomness |
| `wasi:filesystem` | 0.2.x | Capability-scoped files and directories |
| `wasi:sockets` | 0.2.x | TCP/UDP sockets, IP name lookup |
| `wasi:cli` | 0.2.x | stdio, args, environment, exit, terminal |
| `wasi:http` | 0.2.x | HTTP client/server types and handlers |

*Table 1: The seven WASI proposals stabilized in WASI 0.2, each an independently versioned WIT package [4][8].*

### 2.3 Related work

The design space has deep roots. **Capability-based systems** — KeyKOS, EROS, seL4, the E language, Capsicum, CloudABI — established that unforgeable, delegable references compose into least-privilege systems; WASI 0.2's resource handles are direct descendants, a `wasi:filesystem` *descriptor* being a capability in the classic sense: unforgeable, attenuated by construction, carrying no ambient authority [6]. Among IDLs (CORBA, Protobuf, Thrift, Smithy), WIT's distinguishing feature is a *formally specified binary lowering* — the canonical ABI — rather than ad hoc per-language code generation. **Fuchsia's component framework** and **Erlang/OTP** explore hierarchical isolated components; the component model differs in making isolation *language-agnostic and binary-level*, so Rust, Go, and Python components link with no shared runtime.

## 3 Methodology

This is a specification-grounded analytic study. First, **primary-source analysis**: we work from the component-model design documents — the explainer, `WIT.md` [3], `CanonicalABI.md` [2] — plus the WASI 0.2 release materials [4] and per-proposal WIT sources [8]. Second, **constructive modeling**: a minimal formal calculus of resources and lifting/lowering in which to state and prove the Section 5 results, kept small so the proofs track the specification rather than implementation choices. Third, **analytic cost modeling**: asymptotic cross-call costs derived from the canonical ABI's flattening and copy rules, with a Python harness computing the model's predictions for representative signatures. 

Terminology: to **lower** is to convert an interface value to core values plus linear-memory writes; to **lift** is the inverse. **Flattening** statically maps an interface type to core value types. A **world** is a named import/export contract; an **instance** is a component instantiated against satisfied imports. A **resource** is manipulated only via `own<T>` and `borrow<T>` handles.

## 4 The Component Model, Deconstructed: From Interface Types to Worlds
### 4.1 Interface types and WIT: a typed boundary language

Interface types give component boundaries a *rich static type system* where core WebAssembly has scalars. Primitives (`u8`…`u64`, `s8`…`s64`, `f32`, `f64`, `char`, `bool`, `string`) join algebraic constructors — `record`, `variant`, `enum`, `flags`, `tuple`, `list`, `option`, `result` — plus `future`/`stream` for the in-progress async story [3][5]:

```wit
package acme:geometry@1.3.0;

interface shapes {
    record point { x: f64, y: f64 }
    variant shape {
        circle(point, f64),
        polygon(list<point>),
    }
    resource canvas {
        constructor(width: u32, height: u32);
        draw: func(s: shape) -> result<_, string>;
    }
    area: func(s: shape) -> f64;
}

world renderer {
    import shapes;
    export render: func(s: shape, c: borrow<canvas>) -> list<u8>;
}
```

Three properties matter. First, *structural contracts with nominal anchors*: a `world` names exactly the imports a component needs and the exports it provides, so hosts check compatibility before instantiation. Second, **semantic versioning** (`namespace:name@x.y.z`): compatibility rules respect semver — adding an enum case or optional record field is a minor change old consumers still bind [1]. Third, *virtualizability*: imports are typed instances, not host intrinsics, so a host or intermediate component can interpose logging, policy, or emulation without the guest's cooperation.

### 4.2 The canonical ABI: lifting, lowering, and flattening

The **canonical ABI** [2] is the enforcement mechanism: a deterministic translation between interface values and the core machine, specified as pseudocode. Each boundary call compiles to two adapters: the caller *lowers* arguments to core values (and memory buffers when needed); the callee *lifts* them back.

The static core is **flattening**: each interface type maps to core value types (`u32`→`i32`; `record{a:u8,b:u16}`→`[i32,i32]`; `string`→`[i32,i32]` as pointer+length). Caps then apply: at most `MAX_FLAT_PARAMS = 16` core values pass in registers, at most `MAX_FLAT_RESULTS = 1` return that way [2]. Fitting signatures travel *by value in registers* — zero memory traffic; the rest go *by pointer*, the caller allocating via the callee's `realloc` (`cabi_realloc`) and the callee cleaning up through `post-return`. Strings admit UTF-8, UTF-16, and latin1+UTF-16, chosen per `canon lift`/`canon lower`, and every crossing string is validated — a whole class of memory-safety bugs dies at the boundary.

The consequence is a *two-regime* cost structure (Section 5): small signatures cross at register speed; heap-allocated values pay linear copies. And the two sides *never share linear memory*: every instance owns its memory, and all cross-boundary movement is a canonical-ABI copy. That is the shared-nothing half of isolation — a compromised callee cannot name an address in the caller's memory.


### 4.3 Resources, handles, and lexical confinement

The second half of the isolation story is the **resource type**: how components share *stateful* things — files, sockets, streams — without sharing memory. A resource declares methods plus an implicit destructor; values are manipulated only through two handle flavors [1][2]:

- `own<T>` — an *owning* handle. Dropping the last `own` handle runs the destructor. Transfer is explicit and linear: exactly one owner at a time.
- `borrow<T>` — a *borrowed* handle, valid only for the call or scope that created it. A borrow can never outlive its `own`, enforced *dynamically* by per-instance resource tables tracking borrow depth.

Handles cross boundaries as `i32` indices into per-instance **resource tables** (free-list structures capped at 2²⁸−1 entries); the canonical ABI defines the lowering/lifting of `own`/`borrow`, including traps for use-after-drop and borrow escape [2]. The payoff is *confinement by construction*: a component can name only resources it was explicitly given — as imports, as call arguments or returns, or as call-scoped borrows. There is no ambient namespace to reach for and no integer-forging attack, since a handle is meaningful only inside the issuing instance's table. In WASI 0.2 this is concrete: a `wasi:filesystem` *descriptor* is an `own<descriptor>` resource, and the `openat`-relative discipline of classic capability systems falls out of the type system rather than host convention [4][6].

In Rust, `wit-bindgen` renders `own<canvas>` as an owned struct whose `Drop` runs the destructor, and `borrow<canvas>` as a lifetime-parameterized reference:

```rust
// generated by wit-bindgen (simplified)
pub struct Canvas { handle: u32 }
impl Drop for Canvas {
    fn drop(&mut self) {
        unsafe { _rt::resource_drop(self.handle) } // canonical resource-drop
    }
}
pub fn area(s: &Shape) -> f64 { /* ... */ }
```

### 4.4 Worlds, instances, and language-agnostic composition

A **world** is the component's complete import/export contract — the unit against which hosts advertise capability and tools check compatibility. `wasi:cli/command` imports filesystem, clocks, random, sockets, stdio and exports one `run` function; any component targeting it runs on any implementing host — Linux, macOS, Windows, a browser shim — without recompilation [4]. Composition is *linking at the interface level*: tooling wires exports to imports, checking WIT type equality (modulo semver-compatible evolution) at link time [1].

Because the canonical ABI is language-neutral, composition is language-agnostic in the strong sense: a Rust component exporting `area: func(shape) -> f64` links against a Python component importing it, each toolchain generating its own adapters against the *same* WIT. Components nest hierarchically, each with isolated state, and **adapters** — themselves components — translate between worlds, as the `wasi_snapshot_preview1` adapter does when lifting Preview 1 modules into Preview 2 hosts [4].

### 4.5 WASI as the component ecosystem: capabilities, not syscalls

WASI 0.2 is best read as the first large-scale *application* of the component model to systems design. Three shifts matter. First, **granularity**: interfaces are independently importable WIT packages — a component needing only clocks and randomness imports just `wasi:clocks` and `wasi:random`. Second, **virtualizability**: WASI interfaces are ordinary component imports, so hosts interpose freely — in-memory filesystem overlays for tests, edge-native `wasi:http` backends, per-component policy attenuation. Third, **capability discipline by default**: 0.2 keeps Preview 1's deny-by-default posture (no filesystem, network, or environment unless granted) and strengthens it with resource handles — preopened directories arrive as `own<descriptor>` handles, sockets come from explicit constructors, and `wasi:cli` exposes only host-chosen environment variables [4][6].

In a Unix process, `open("/etc/passwd")` succeeds by ambient identity; the *program's* authority is the *user's*. In a WASI 0.2 component there is no absolute-path `open` at all — only operations *relative to* directory handles already held, and only handles the host granted at instantiation are held. Confused-deputy attacks get structurally harder: authority travels in unforgeable handles, not ambient identity, so a deputy cannot be induced past the handles it was given [6][10].

## 5 Empirical Results and Formal Proofs

### 5.1 An analytic cost model of cross-boundary calls

The canonical ABI is specified as an algorithm, so its costs derive *statically* from a signature. Let parameters and results flatten to *p* and *r* core values, *m* be heap-allocated bytes copied through linear memory, *h* the handles crossing, and *s* the string bytes validated:

```
T_boundary = c_reg * (p + r) + c_copy * m + c_valid * s
             + c_handle * h + c_call
```

The flattening caps yield two regimes (`MAX_FLAT_PARAMS = 16`, `MAX_FLAT_RESULTS = 1`):

| Signature shape | Example | Regime | Dominant term |
|---|---|---|---|
| Small scalar | `area(shape) -> f64`, flat ≤ 16 | Register | `c_reg*(p+r)`, no memory traffic |
| String in/out | `greet(string) -> string` | Mixed | `c_copy*m` for string bodies |
| Large record | 20-field record | Pointer | `c_copy*m` over record image |
| Handle passing | `draw` with `borrow<canvas>` | Handle | `c_handle*h`, O(1) per handle |
| Bulk data | `render(...) -> list<u8>` (1 MB) | Copy-bound | `c_copy*m`, linear in payload |

*Table 2: Boundary-cost regimes derived from the canonical ABI's flattening rules [2].*

This harness computes the model's prediction per signature, encoding the flattening rules of [2]:

```python
MAX_FLAT_PARAMS, MAX_FLAT_RESULTS = 16, 1

def flatten(ty):
    """Simplified flattening -> (core_vals, heap_involved)."""
    scalars = {"u8","u16","u32","s8","s16","s32","bool","char",
               "f32","u64","s64","f64"}
    if ty in scalars:                       return (1, False)
    if ty == "string":                      return (2, True)
    if ty.startswith("list<"):              return (2, True)
    if ty.startswith(("own<", "borrow<")):  return (1, False)
    if ty.startswith("record{"):
        return (ty.count(";") + 1, False)   # scalar fields assumed
    raise ValueError(ty)

def regime(params, results):
    p = sum(flatten(t)[0] for t in params)
    r = sum(flatten(t)[0] for t in results)
    heap = any(flatten(t)[1] for t in params + results)
    return "register" if (p <= MAX_FLAT_PARAMS
                          and r <= MAX_FLAT_RESULTS
                          and not heap) else "pointer+copy"

for sig in [(["u32","u32"],["f64"]), (["string"],["string"]),
            (["borrow<canvas>","string"],["u32"])]:
    print(sig, "->", regime(*sig))
```

Qualitative predictions: (a) boundary cost is *linear in payload bytes* with a small per-handle constant — no format negotiation, no JSON parsing, no dynamic dispatch; (b) the register regime covers scalar and small-record RPC, making fine-grained decomposition affordable; (c) handles are *O(1)*, which is what makes capability-passing composition cheap. 

### 5.2 Round-trip fidelity

Lifting and lowering are *verified inverses* — by construction in the specification's pseudocode, not by testing:

> **Theorem:** *(Round-trip fidelity.)* For every interface value *v* of type *t* admitted by the canonical ABI's validation rules, `lift(lower(v, t), t) = v`; and for every core representation *c* produced by lowering, `lower(lift(c, t), t)` is observationally equivalent to *c*.

*Proof sketch.* Structural induction on *t* per `CanonicalABI.md` [2]. Base cases are direct: `lower_flat`/`lift_flat` are mutual inverses, with range checks (`bool`∈{0,1}, `char` a valid scalar) trapping invalid inputs so only valid values round-trip. Inductive cases reuse identical `alignment`/`elem_size` computations in `store`/`load`; strings are validated on lift against the declared encoding while lowering emits exactly that encoding, making validation the identity on lowered output. Handles lower to table indices and lift by lookup in the *same* instance's table — a bijection on live entries. The `realloc`/`post-return` discipline guarantees the lifted memory image is exactly the lowered one. ∎



### 5.3 A confinement theorem for resource handles

> **Theorem:** *(Handle confinement.)* A component instance *I* can invoke a resource method on resource *R* only if *I*'s resource table holds a live `own`/`borrow` handle for *R* obtained (i) as an import, (ii) as a call argument or return, or (iii) by creating *R* itself. *I* can never name a resource held exclusively by another instance.

*Proof sketch.* Invocation in the canonical ABI [2] is defined only over handles: the callee lifts an `i32` by lookup in *its own* per-instance table, trapping on absent or dead entries. Indices are runtime-allocated; guest code cannot mint them because the table is runtime state outside linear memory. Handles enter a table only via the three listed channels: instantiation imports, argument/return lifting, and `resource.new` (allocating in the constructor's table). No rule references another instance's table, and `borrow` handles carry scope bounds via borrow-depth tracking, so they cannot escape their call. Induction over the execution trace completes the proof. ∎



## 6 Limitations and Future Work

Six frontiers bound the current claim.

1. **Async execution.** The MVP canonical ABI is *synchronous*: a lifted import cannot reenter the component mid-call. The *async* proposal (`future`/`stream`, waitable sets, tasks) is in active design, with WASI 0.3 expected to reshape `wasi:io` around it; until then, async-heavy workloads (the `wasi:http/proxy` world's core use) rely on host polling shims.
2. **Threading.** Components are shared-nothing, but the threads proposal's interaction with the ABI — concurrent lifting, borrow tracking under races — remains open design.
3. **Garbage collection.** WIT maps cleanly to Rust, C, and Go; GC'd languages (Java, Kotlin, C#) need Wasm GC integrated with resources — a hard problem at the managed-heap/linear-memory boundary.
4. **Versioning.** Semver-typed packages are a start, but compatible-evolution rules (is adding a variant case safe? what if only `wasi:filesystem@0.2.3` exists for a `0.2.1` component?) are still being worked out.
5. **Tooling.** Cross-boundary debugging are nascent.
6. **The copy tax.** Linear copy cost is fundamental, not incidental. Bulk-data pipelines (media, ML inference) will need zero-copy extensions with preserved isolation or will compose *inside* components rather than across them.

None is fatal — async, threads, and GC have active proposals with Wasmtime prototypes — but they bound today's claim: the component model is the best *specification* of portable capability-secure compute, not yet a finished *platform* for every workload.

## 7 Conclusion

The Component Model, WIT, and WASI 0.2 propose a new narrow waist for portable computation. Historical answers — the Unix process with ambient file descriptors, the JVM with classloader boundaries, the container with a namespaced kernel — couple *portability* to a *particular host's* authority. The component model decouples them. Portability comes from the canonical ABI: a deterministic, formally specified translation with provable round-trip fidelity. Authority comes from resource handles: unforgeable, scoped capabilities whose confinement is a theorem about the abstract machine, not a host policy. Composition comes from worlds and typed linking: components in any language snap together at WIT-typed boundaries with no shared memory, runtime, or trust.

WASI 0.2 is the existence proof that this stack carries a real systems interface — files, clocks, sockets, HTTP — and Rust 1.82's tier-2 `wasm32-wasip2` target [7] shows the ecosystem taking it seriously as a compilation target. Ambient authority was a historical accident, a consequence of bolting security *around* interfaces designed without it. The component model builds the interface *from* the security property, and that inversion makes it the most promising foundation for portable compute since WebAssembly itself.
