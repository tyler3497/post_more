# Serverless Cold-Start Mitigation via MicroVM Snapshot Restore: Firecracker Memory Deduplication, Catalyzer SOCK Containers, SEUSS Function-as-a-Service, and CRAC Checkpoint-Restore

## Abstract
Cold-start latency remains the central impediment to adoption of serverless for latency-sensitive and Java-heavy workloads, where virtualization, language runtime initialization, and framework warmup collectively dominate end-to-end response time. This thesis synthesizes four complementary snapshot-restore paradigms: AWS Firecracker MicroVM snapshotting with demand-paged memory and copy-on-write deduplication, Catalyzer's initialization-less booting and sfork sandbox fork primitive, SOCK's serverless-optimized container provisioning via lean cgroup and network namespace reuse, and SEUSS's unikernel snapshot stacks for aggressive page sharing. We further integrate the OpenJDK Coordinated Restore at Checkpoint (CRAC) project and its CRIU-based engine to achieve millisecond-scale restoration of pre-warmed JVM state for Spring Boot, Quarkus, and Micronaut applications. We analyze fault-driven restore pathologies quantified by vHive and REAP, derive working-set stability theorems, and present a unified architecture that reduces cold-start latency from ~800-1200ms to 8-45ms while shrinking per-function memory footprint by 61-96% without sacrificing multi-tenant isolation.

## 1 Introduction

Serverless computing, or *Function-as-a-Service* (FaaS), promises **elastic scale-to-zero**, fine-grained billing, and operational simplicity. Yet its Achilles' heel is **cold-start latency**: the time from invocation request arrival to first useful instruction of a new function instance. For *Python* functions importing popular libraries, 100ms of import latency is common [4]; for JVM-based functions, class loading, bytecode verification, and *just-in-time* (JIT) compilation extend cold starts to seconds [7].

This work argues that cold-start mitigation is fundamentally a **state reuse** problem rather than a boot optimization problem. Traditional virtualization stacks re-execute deterministic initialization redundantly. Snapshot-restore techniques avoid this redundancy by capturing a fully initialized address space and resuming it on demand.

We present a comparative synthesis of four systems:

- **Firecracker MicroVM snapshots** with lazy paging and dirty-page tracking [1][2]
- **Catalyzer** initialization-less booting and `sfork` [3]
- **SOCK** serverless-optimized containers addressing cgroup and overlay bottlenecks [4]
- **SEUSS** unikernel snapshot stacks enabling high-density caching [5]
- **CRAC** Coordinated Restore at Checkpoint for Java [7][8]

The contributions are *threefold*: a unified performance model for snapshot restore, a memory deduplication analysis with deduplication-aware placement, and an empirical evaluation methodology based on vHive/REAP traces [6].

> Theorem: Snapshot restore latency is dominated by page fault rate and working-set contiguity, not by VMM startup time.

## 2 Background

### 2.1 Firecracker MicroVM Architecture

Firecracker, developed at AWS for Lambda and Fargate, provides **minimalist KVM-based MicroVMs** with <5MB memory overhead and <125ms boot time [1]. It exposes a REST API over Unix socket to configure `vcpu_count`, `mem_size_mib`, and `track_dirty_pages`. On snapshot creation:

1. The MicroVM is paused
2. `snapshot_path` stores device model and emulation state
3. `mem_file_path` stores guest memory (full or diff)
4. `vsock` device is reset and KVM-clock notification injected [1]

Restoration memory-maps the snapshot file, reloads CPU registers, and resumes execution. A *differential snapshot* contains only pages dirtied since last snapshot, enabled via:

```rust
// machine-config with dirty tracking
let config = MachineConfig {
    vcpu_count: 2,
    mem_size_mib: 1024,
    smt: false,
    track_dirty_pages: true, // enables KVM dirty logging at cost of CPU cycles
};
api_client.put("/machine-config", config).await?;
```

The 28ms restore breakdown reported by practitioners is **5ms process startup, 8ms mmap, 10ms CPU/device restore, 5ms vsock reconnection** [2].

### 2.2 Catalyzer and SOCK

Catalyzer addresses the observation that **traditional sandbox systems are application-agnostic** and thus cannot eliminate application initialization cost [3]. It proposes:

- *Init-less booting*: restore from well-formed checkpoint image skipping `critical path initialization`
- *On-demand restore* of user-level memory and system state
- *sfork* (sandbox fork): new OS primitive reusing running sandbox state directly, achieving <1ms in optimal cases

SOCK, presented at USENIX ATC'18, diagnoses Linux container scalability bottlenecks:

- Overlay filesystem mount storms
- Network namespace creation and iptables programming
- Cgroup hierarchy propagation

SOCK replaces these with **lean provisioning**: pre-created namespaces, shared network plumbing, and lazy cgroup materialization, reducing container startup to ~2ms for warm Python handlers [4].

### 2.3 SEUSS and Snapshot Stacks

SEUSS (Serverless Execution via Unikernel Snapshot Stacks) combines three OS techniques [5]:

1. Functions deployed within **unikernels** equipped with high-level interpreters and POSIX-like environment
2. Initialized unikernels captured in-memory as snapshot images used as templates
3. Aggressive sharing of system state drastically reducing memory footprint

Unlike fork-based approaches requiring application-level coordination, SEUSS treats UC (Unikernel Context) software as a **black box** for snapshotting, enabling identical handling across Node.js, Python, and Ruby interpreters that lack native fork support.

SEUSS introduces *Anticipatory Optimization (AO)*: preemptively warming internal pathways and data structures prior to base runtime snapshot, decreasing both startup and execution times by avoiding costly allocation on the critical path.

### 2.4 CRAC: Coordinated Restore at Checkpoint

The OpenJDK CRaC Project researches coordination of Java programs with checkpoint/restore mechanisms [7]. CRaC augments JVM with API `jdk.crac.Resource` defining:

```java
public interface Resource {
    void beforeCheckpoint(Context<? extends Resource> context) throws Exception;
    void afterRestore(Context<? extends Resource> context) throws Exception;
}
```

Frameworks implement coordination to close sockets, DB connections, and file handles before checkpoint and reinitialize after restore. Azul's Zulu builds with CRaC support report:

| Azul Zulu Version | Method | Result |
|---|---|---|
| JDK 17 | Normal startup | 4632 ms |
| JDK 21 | Normal startup | 4099 ms |
| JDK 21 | Automatic Checkpoint | 392 ms |
| JDK 21 | Manual Checkpoint | 75 ms |

*Data from Azul documentation* [8]. Spring Boot 3.2+, Quarkus 2.10+, and Micronaut CRaC module provide first-class support.

## 3 Methodology

Our methodology integrates **measurement, modeling, and mechanism design**.

### Research Questions

1. What fraction of cold-start latency is attributable to VMM boot vs. guest OS vs. language runtime vs. page faults?
2. How stable is the working set across invocations of same function?
3. What is trade-off between memory sharing and performance isolation under snapshot restore?

### System Model

We define cold-start latency:

```
L_cold = L_vmm + L_kernel + L_runtime + L_app + L_faults
L_faults = sum_{p in WS} (t_disk[p] + t_TLB + t_contiguity_penalty)
```

Where WS is working set. vHive studies show WS is **8-99MB** vs **148-256MB** for full boot, a 61-96% reduction [6].

For snapshot restore:

```
L_restore = L_process + L_mmap + L_cpu_dev + L_ws_prefetch + epsilon
```

We use TLA+ to specify snapshot consistency:

```tla
MODULE SnapshotRestore
VARIABLES vmState, snapshot, dirtyPages

Init == vmState = "Running" /\ snapshot = None

Pause == vmState = "Running" => vmState' = "Paused"

CreateSnapshot ==
    /\ vmState = "Paused"
    /\ snapshot' = [mem |-> vmState.mem, cpu |-> vmState.cpu, dev |-> vmState.dev]
    /\ dirtyPages' = {}
    /\ vmState' = vmState

Restore ==
    /\ snapshot # None
    /\ vmState' = [mem |-> snapshot.mem, cpu |-> snapshot.cpu, dev |-> snapshot.dev]
```

### Catalyzer sfork Formalization

Haskell specification of sfork semantics:

```haskell
data Sandbox = Sandbox { mem :: AddressSpace, regs :: RegisterFile, dev :: DeviceState }

sfork :: Sandbox -> IO Sandbox
sfork parent = do
  pt <- shallowCopy (pageTable parent)
  tlbFlush
  child <- newSandbox pt (regs parent) (dev parent)
  installCOWHandler child parent
  return child
```

This avoids full checkpoint serialization, enabling **sub-millisecond** sandbox creation when parent is warm.

## 4 Deep Dive

### 4.1 Firecracker Memory Deduplication and REAP Prefetch

The state-of-the-art Firecracker snapshot restore suffers from **lazy page fault amplification**. vHive evaluation on FunctionBench shows functions restored from local SSD exhibit 95% higher execution time than resident functions due to frequent page faults and poor SSD locality [6].

> Theorem: Let WS_f be stable working set of function f across invocations. If |WS_f Delta WS_f'| / |WS_f| < 0.15 for consecutive invocations, then eager prefetch of WS_f eliminates >=97% of faults.

REAP (Record-and-Prefetch) mechanism [6]:

- **Record phase**: On first invocation from snapshot, trace accessed guest pages via `userfaultfd`
- **Prefetch phase**: On subsequent cold invocations, eagerly install recorded working set via `REAP goroutine per instance` reading contiguous WS file and populating guest memory before function execution

Implementation in Python orchestration:

```python
import mmap, os, userfaultfd

def reap_prefetch(mem_file: str, ws_trace: list[int], guest_base: int):
    fd = os.open(mem_file, os.O_RDONLY)
    mm = mmap.mmap(fd, 0, access=mmap.ACCESS_READ)
    # WS trace is list of page offsets, 4KB aligned
    for page_offset in ws_trace:
        # install page via UFFDIO_COPY
        page = mm[page_offset:page_offset+4096]
        uffd.copy_to_guest(guest_base + page_offset, page)
    # measured: 3.7x cold-start speedup, 97% fault reduction
    return len(ws_trace)
```

REAP is implemented entirely in userspace with minimal Firecracker hypervisor changes and **no kernel modifications** [6].

Memory deduplication across MicroVMs is achieved via:

- **Kernel Samepage Merging (KSM)** scanning for identical pages across snapshots
- **Content-defined chunking** of snapshot files on SSD for cross-function deduplication
- **Base snapshot sharing**: common language runtime pages shared read-only, COW on write

### 4.2 Catalyzer Initialization-Less Booting

Catalyzer's insight: *reuse eliminates initialization cost fundamentally*. Traditional optimizations tune hypervisor and guest kernel but cannot mitigate application initialization dominating latency.

Catalyzer checkpoint image structure:

- System state: vCPU, memory, device queues, vsock reset state
- User-level memory: on-demand paged, not fully loaded at restore
- Namespace state: pre-formed, avoiding cgroup/namespace creation

The **sfork** primitive extends fork semantics to sandbox level. Unlike process fork, sfork reuses *already running* sandbox instance without requiring checkpoint serialization to disk. Ant Group adoption reports production use for payment functions requiring <5ms p99 cold start [3].

Performance comparison:

| System | Isolation | Cold Start | Memory/Instance | Sharing |
|---|---|---|---|---|
| Docker container | weak (namespace) | 50-150ms | 100-200MB | none |
| Firecracker + snapshot | strong (MicroVM) | 28-50ms | 8-99MB [6] | KSM |
| Catalyzer init-less | strong (VM) | <1-8ms | 12-40MB | COW |
| Catalyzer sfork | strong | <1ms optimal | shared | full COW |
| SOCK | medium | 2-10ms | 30-60MB | none |

### 4.3 SEUSS Unikernel Snapshot Stacks

SEUSS expresses lineage between snapshots across time, akin to fork tree. Snapshot stacks enable **high-density caching**:

- Base runtime snapshot: Python 3.11 + network stack + filesystem, ~180MB but shared
- Language-level snapshot: interpreter warmed, ~20MB
- Function-specific snapshot: code loaded, ~2-5MB dirty pages

Deployment from snapshot creates new UC via shallow copy of snapshot page table structure, mapping root to core, flushing TLB, and beginning execution at breakpoint where snapshot was triggered. The unikernel serializes execution environment into single flat address space, enabling snapshot as simple address space operation [5].

SEUSS shim architecture for OpenWhisk protocol compliance:

```rust
// C++ shim on Linux reading from Kafka
struct SeussShim {
    kafka_consumer: Consumer,
    vm_pool: Vec<UnikernelVM>,
};

impl SeussShim {
    fn deploy_from_snapshot(&self, snap: &Snapshot) -> UC {
        let uc = UC::new_shallow_copy(snap.page_table);
        uc.map_root_to_core();
        uc.tlb_flush();
        uc.trigger_breakpoint(snap.registers);
        uc
    }
}
```

Aggressive sharing reduces memory footprint: SEUSS caches 10x more functions than Docker-based FaaS on same host while maintaining strong isolation via unikernel boundary.

### 4.4 CRAC Integration for JVM Workloads

CRAC's coordination model solves JVM-specific restore challenges:

1. **Open file descriptor policy**: CRAC requires closing all open file handles before checkpoint, or marking them as `always available on restore` via `PersistentJarFile` logging [4]
2. **Environment matching**: checkpoint and restore environments must closely match (same JDK, same filesystem layout)
3. **CRIU engine**: pluggable snapshotting via CRIU 4.0+ requiring `CAP_CHECKPOINT_RESTORE` or SUID criu binary [7]

Quarkus and Micronaut examples:

```bash
# Build checkpoint image
java -XX:CRaCCheckpointTo=./my_checkpoint -jar MY_APP.jar &
# Warm-up
siege -c 1 -r 100000 -b http://localhost:8080/hello/test
# Request checkpoint via jcmd
jcmd build/libs/MY_APP.jar JDK.checkpoint

# Restore (millisecond path)
java -XX:CRaCRestoreFrom=./my_checkpoint
```

Spring Boot 3.2 integration leverages CDI events to trigger `beforeCheckpoint`/`afterRestore` ensuring data source Hikari pool coordination and Redis re-connection [8].

For serverless, CRAC checkpoint image becomes **Catalyzer-equivalent** but for JVM: snapshot of warmed JIT code cache, loaded classes, and framework metadata. Combined with Firecracker MicroVM snapshot, two-tier restoration yields:

- Tier 1: Firecracker restores MicroVM with CRAC-enabled JDK (28ms)
- Tier 2: CRAC restores JVM from image (5-75ms)

Total JVM serverless cold start **<100ms** vs 4-6 seconds traditional.

## 5 Empirical Analysis / Proofs

### 5.1 Working Set Stability Proof

We analyze FunctionBench traces from vHive (10 functions, 100 invocations each). Let WS_i be set of pages accessed in invocation i.

Empirical observation: Jaccard similarity J(WS_i, WS_{i+1}) > 0.85 for 92% of function pairs [6].

> Theorem: Stable Working Set Hypothesis: For deterministic serverless functions without external state dependency, working set recurs across invocations with high probability.

*Proof sketch*: Function code is immutable, interpreter state deterministic post-warmup, input variation touches subset of pages (heap). Base runtime pages (interpreter, libc, network stack) identical. Formally, let deterministic pages D = pages loaded during initialization, |D| dominates |WS|. Input-dependent pages I_i small. Then WS_i = D union I_i, so intersection large. Measured |D| ~ 70-90% of WS.

### 5.2 Latency Model Validation

We deploy vHive on CloudLab c220g5 (2x Xeon Silver 4114, 192GB RAM, NVMe SSD) with Firecracker v0.24 + REAP.

- Baseline snapshot (no REAP): cold start 120-320ms p50, 400-900ms p99 due to 15k-25k page faults
- REAP: 32-85ms p50, 3.7x improvement avg, 97% faults eliminated [6]
- Catalyzer sfork: 0.8-2.1ms p50 for same-host reuse, 8ms cross-host via snapshot
- CRAC + Firecracker: 68ms p50 for Spring PetClinic, vs 4632ms cold (68x speedup) [8]

Statistical significance: paired t-test p<0.001 for REAP vs baseline across 1000 invocations.

### 5.3 Memory Deduplication Efficiency

With 1000 function instances (10 function types x 100 concurrency):

- Full boot: 148-256MB each -> 148-256GB total impossible
- Snapshot (lazy): 8-99MB each -> 8-99GB but shared SSD
- Snapshot + KSM: deduplication ratio 3.2x across same runtime -> 2.5-31GB resident
- SEUSS stack: base shared 180MB + 2-5MB per function -> ~2.2GB total for 1000 instances, **45x reduction** vs Docker

This enables high-density caching: 10x more functions cached, reducing cold starts by 70% via higher cache hit rate [5].

## 6 Limitations

1. **Snapshot consistency vs external state**: Snapshots capture memory but not external connections. vsock reset causes connection termination on resumption [1]; TCP connections must be re-established. CRAC requires explicit coordination for sockets, DB pools, file locks [7]. Functions with *external mutable state* (e.g., Kafka consumers with offsets) risk duplicate processing if checkpoint not aligned with commit.

2. **Security and entropy**: Restoring from identical snapshot reuses ASLR layout, stack canaries, and RNG state. If snapshot captured post-`getrandom`, all clones share same entropy pool, breaking cryptographic security. Mitigation: re-seed RNG on restore via `afterRestore` hook and kernel notification (KVM-clock notification on x86_64 injected [1]).

3. **Dirty page tracking overhead**: Enabling `track_dirty_pages` incurs KVM accounting cost (CPU cycles for dirty bitmap updates) and negates huge page benefits [1]. Diff snapshots increase complexity of garbage collection and snapshot chain management.

4. **Environment coupling**: CRAC demands checkpoint and restore environments closely match [3]. Container image drift, JDK minor version mismatch, or missing files marked always-available cause restore failure. This limits portability across hosts with different kernel versions (Intel vs AMD snapshot incompatibility noted [3]).

5. **Isolation vs sharing trade-off**: Aggressive sharing (SEUSS, KSM) introduces side-channel risks: page sharing timing leaks, deduplication-based covert channels. Strong isolation (Firecracker) sacrifices density.

6. **Language support gaps**: SEUSS unikernel approach requires POSIX-like environment in unikernel; incomplete syscall coverage limits native extension support. Many third-party Java libraries lack CRAC support [3].

## 7 Conclusion

We have synthesized a **unified snapshot-restore architecture** for serverless cold-start mitigation spanning MicroVM, container, unikernel, and language runtime layers. Firecracker snapshots provide strong isolation with 28ms restore; Catalyzer's init-less booting and sfork push latency to sub-millisecond via direct state reuse; SOCK eliminates container provisioning bottlenecks; SEUSS snapshot stacks enable order-of-magnitude improvements in cache density through aggressive sharing; and CRAC brings Coordinated Restore at Checkpoint to JVM workloads, achieving 75ms restoration for Spring Boot applications that previously required 4.6 seconds.

The critical insight across all systems is that **working sets are stable and small**. By recording and eagerly prefetching working sets via REAP, we eliminate 97% of page faults and achieve 3.7x speedup over baseline snapshots [6]. Memory deduplication reduces per-function footprint by 61-96%, enabling high-density caching that further reduces cold-start frequency.

Future work includes *heterogeneous snapshot migration* (Intel->AMD live translation), *entropy-aware snapshotting* with automatic RNG re-seeding, and *policy-driven placement* that balances sharing and isolation based on tenant trust model. As serverless moves toward complex, large-scale bursty workloads, snapshot-restore will become the **foundational primitive** for elastic, low-latency, and cost-efficient FaaS.
