# CompCert Verified Compilation: Semantic Preservation Theorems, the Clight Memory Model, Verified Register Allocation and Scheduling, and Mechanized Correctness Proofs in Coq

## Abstract

CompCert is the first realistic, industrially usable compiler for a substantial subset of C whose *semantic preservation* has been mechanically verified end to end in the Coq proof assistant [1]. This thesis dissects the methodology that makes CompCert possible: a global correctness theorem phrased as *backward simulation* between Clight source semantics and generated assembly; a layered decomposition into roughly a dozen compiler passes, each justified by its own *forward simulation* with a machine-checked Coq proof; the abstract block-based **memory model** of Leroy and Blazy [2], which makes pointer-heavy C semantics tractable and supports *memory injections* for reasoning about spilling and stack-frame layout; a mechanized proof of a **George-Appel graph-coloring register allocator** together with the Rideau-Leroy verified-validation alternative [5]; and the treatment of scheduling-like optimizations through verified translation validation [6]. We reconstruct the proof-engineering discipline of determinacy, receptiveness, and well-founded measures that enables composition of per-pass simulations, examine the trusted computing base [8], and assess CompCert's empirical record in safety-critical domains including avionics tool qualification.

## 1. Introduction

Every compiler ever written contains bugs, and miscompilation is uniquely dangerous: the defect lies in the trusted infrastructure itself, silent and nearly undetectable by testing. Test suites, differential testing, and fuzzing can find bugs but never establish their absence — a gap that matters in avionics and automotive control, where standards like DO-178C demand extraordinary assurance.

**Formally verified compilation** offers a radical answer: prove, with mathematical rigor checked by machine, that the compiler never miscompiles. That is, prove a *semantic preservation theorem*: every observable behavior of the generated assembly code is also a behavior admitted by the source program under the source language semantics. The CompCert project, led by Xavier Leroy at Inria, is the landmark realization of this idea — a realistic optimizing compiler for a large subset of ISO C99 targeting ARM, PowerPC, RISC-V, and x86, whose semantic preservation is *proved in Coq*, end to end, from Clight source to assembly [1][3].

This thesis addresses five interlocking questions:

1. **What does the correctness theorem say, exactly?** We formalize backward simulation and explain why CompCert proves per-pass *forward* simulations, flipping them into backward simulations using determinacy and receptiveness of the target semantics.
2. **How is C memory formalized?** We present the Leroy-Blazy block-based memory model [2] — the abstract `mem` type, its four operations, memory chunks, and the injection/extension relations that make transformation proofs possible.
3. **Can register allocation be proved correct?** We analyze the mechanized George-Appel coloring allocator of the CompCert back end and the verified validator of Rideau and Leroy [5] that checks an untrusted allocator's output.
4. **What about scheduling?** We examine verified translation validation of scheduling-like optimizations — lazy code motion and trace scheduling experiments [6] — and the validator architecture that makes aggressive optimizations provable.
5. **Does it work in practice?** We review proof size, compiler performance (~85-90% of GCC -O1), industrial qualification experience, and differential-testing campaigns [8].

> **Theorem (CompCert semantic preservation, informal):** If `transf_c_program p = OK tp`, every behavior of the assembly `tp` is a behavior of the source `p` (or a refinement). Compilation may turn undefined behavior into arbitrary code, but never turns well-defined source behavior into something else.

The methodology is *proof-co-design* rather than post-hoc verification [1]: the compiler is written from scratch in Coq's specification language (Gallina) alongside its proof, with algorithms chosen to be both efficient and provable. This thesis reconstructs that design.

## 2. Background and Related Work

### 2.1 A short history of compiler verification

The dream of a proved-correct compiler predates Coq by decades. Early milestones include McCarthy's 1963 abstract, the Pitman and Polak correctness proofs for Algol subsets, and Morris's 1973 proof for a small language. The 1980s saw Hoare-style proofs of realistic compilers (e.g., the *ProCoS* project and the CLI stack). These efforts were heroic but paper-based: proofs ran to hundreds of pages, were error-prone, and could not be maintained as the compiler evolved.

The proof-assistant era changed the economics. Notable predecessors and contemporaries of CompCert include:

- **Proof-carrying code (Necula):** the compiler emits checkable safety proofs with the code — properties, not full semantic preservation.
- **Translation validation (Pnueli et al.):** per-run equivalence checking of input/output. CompCert uses the *verified* form: the validator itself is proved correct in Coq [5][6].
- **CakeML (Kumar et al., POPL 2014):** verified compilation of Standard ML down to machine code — the functional counterpart to CompCert's imperative focus.
- **CompCertTSO (Sewell et al.):** extends CompCert's result to the x86-TSO relaxed memory model for concurrent programs.
- **Vellvm / Alive (Lopes et al.):** formalization of LLVM IR and bounded translation validation for LLVM optimizations — the industrial-strength cousin of CompCert's validators.

### 2.2 The Coq proof assistant

Coq implements the *Calculus of Inductive Constructions*, where programs and proofs are the same syntactic objects (Curry-Howard). CompCert exploits this twice: passes are Gallina functions extracted to OCaml, and their correctness is proved as Coq propositions. The trusted core is Coq's small kernel; tactics, extraction, and libraries are untrusted but checked [8].

## 3. Methodology

### 3.1 Small-step semantics and simulations

Every intermediate language in CompCert is given a **small-step operational semantics**: a transition relation `step : state -> trace -> state -> Prop` over program states, producing observable *traces* of external events (system calls, volatile accesses). Program *behaviors* are the maximal traces of complete executions: termination with a result, divergence, or going wrong (undefined behavior).

Per-pass correctness is a **simulation** between transition systems; CompCert's workhorse is *forward simulation*:

> **Definition (Lock-step forward simulation):** A relation `match_states` between L1-states and L2-states such that: (i) initial states match; (ii) whenever `s1` matches `s2` and `s1 --t--> s1'` is a step of L1, there exists `s2'` with `s2 --t--> s2'` a step of L2 and `s1'` matching `s2'`; (iii) matching is preserved by final states.

Variants (`star`, `plus`, `option`) let the target take zero, one, or several steps per source step — for optimizations that delete or duplicate code. The global theorem, however, is a **backward simulation** (target behaviors are source behaviors), because only backward simulation directly implies preservation of all behaviors including divergence. CompCert's pivotal lemma: a forward simulation *plus* **determinacy** of the target semantics (each state has at most one successor per trace) *plus* **receptiveness** (the target can always accept the next event of any source trace) implies backward simulation [3]. Prove the easy direction per pass, flip globally — the methodological heart of the project.

### 3.2 Proof engineering at scale

Key proof-engineering techniques:

1. **Modular decomposition:** each pass proves its own simulation; composition of simulations yields the end-to-end theorem. A change to one pass requires re-proving only that pass.
2. **Executable specifications:** passes are pure functions; Coq's extraction produces the actual OCaml compiler binary. The *same* artifact is executed and verified — no model/implementation gap.
3. **Tactic automation:** Ltac scripts, decision procedures (`omega`/`lia`), and reflection discharge routine proof obligations; human effort concentrates on invariants.
4. **Semantic test oracles:** each language's semantics is executable on small programs, enabling differential testing of the semantics against the extracted compiler [8].

## 4. Deep Technical Dive

### 4.1 The semantic preservation theorem, precisely

In `Compiler.v`, roughly:

```coq
Theorem transf_c_program_correct:
  forall p tp,
    transf_c_program p = OK tp ->
    backward_simulation (Csem.semantics p) (Asm.semantics tp).
```

where `transf_c_program` chains every pass and `Csem`/`Asm` give the small-step semantics of Clight and of the target assembly. Unfolding `backward_simulation`: if the assembly can produce trace `t` (terminating, diverging, or crashing), the source can produce a trace that *improves* on `t` — identical except the source may go wrong where the target does something defined. In particular, **miscompilation is impossible**: a source program with fully defined behavior compiles to assembly with exactly the same observable behavior.

The proof composes ~15 per-pass forward simulations, all agreeing on the shared trace/event model. Passes where one source step maps to zero target steps (e.g., dead-code elimination) use *measured* relations: a well-founded measure must strictly decrease on stuttering steps, ruling out infinite stuttering and preserving divergence behavior.

| Pass (source -> target) | Simulation style | Key invariant |
|---|---|---|
| Clight -> Cminor (SimplExpr) | lock-step | expression evaluation correspondence |
| Cminor -> CminorSel (SelectOp) | lock-step | operator/addressing-mode matching |
| CminorSel -> RTL (RTLgen) | lock-step | CFG construction preserves evaluation |
| RTL -> RTL (Constprop, CSE, DCE) | lock-step / star | dataflow analysis soundness |
| RTL -> LTL (Allocation) | lock-step | location agreement under liveness |
| LTL -> Linear (Linearize) | star | CFG linearization preserves order |
| Linear -> Mach (Stacking) | lock-step + injection | frame layout via memory injection |
| Mach -> Asm (Asmgen) | lock-step | instruction encoding correctness |

### 4.2 The Clight memory model: blocks, chunks, and injections

C memory is hostile to formalization: pointer arithmetic, pointer-integer casts, unions, uninitialized reads, and out-of-bounds accesses that are *undefined behavior* rather than errors. The Leroy-Blazy model [2][7] tames this with an elegant abstraction.

**States as collections of blocks.** A memory state `m : mem` is a finite collection of disjoint *blocks*, each an array of bytes indexed by integer offsets. `alloc m lo hi` returns a fresh block `b` (never reused) with bounds `[lo, hi)`; `free m b` invalidates it. A pointer is a pair `(b, ofs)` — never a raw integer — so pointer arithmetic stays within its block.

**Typed access via chunks.** Loads and stores are parameterized by a *memory chunk* `κ` describing size, signedness, and float/integer kind:

```coq
Inductive chunk : Type :=
  | Mint8signed | Mint8unsigned
  | Mint16signed | Mint16unsigned
  | Mint32 | Mfloat32 | Mfloat64
  | Many32 | Many64.
```

`load κ m b ofs` and `store κ m b ofs v` operate on byte sequences, with defined decode/encode between values and bytes. Reading uninitialized or freed memory yields `Vundef` (undefined value), which propagates poisonously through arithmetic — the model's mechanism for *delaying* the consequences of undefined behavior until it becomes observable, matching the C standard's latitude.

**The good-variable laws.** The model is axiomatized by algebraic properties proved once in Coq: *load-after-store-same*, *load-after-store-other* (disjoint locations unaffected), and *load-after-alloc/free* characterizations. Pass proofs use these laws rather than any concrete representation, so the model could be reimplemented without invalidating them [2].

**Memory injections: the masterstroke.** Many transformations *relocate* data: spilling moves a pseudo-register into a stack slot; the Linear-to-Mach pass lays out the entire stack frame, merging abstract blocks. A **memory injection** `f : block -> option (block * Z)` maps source blocks to target blocks plus an offset delta, with the crucial property that distinct source blocks map to *non-overlapping* target ranges. Pass correctness is then stated as simulation *up to injection*: related states have memories related by `f`, values related by `f` (pointers translated, integers preserved). The Stacking pass proof — widely considered one of the hardest in CompCert — is essentially a careful construction of such an injection for the frame layout [3][7].

> **Theorem (Injection composition):** Correctness up to `f` followed by correctness up to `g` gives correctness up to `g ∘ f`. The whole back end thus threads one evolving injection from abstract stack blocks down to machine addresses.

### 4.3 Verified register allocation: mechanizing George-Appel coloring

The CompCert back end's register allocator (RTL to LTL) is a verified implementation of the **George-Appel iterated register coalescing** graph-coloring algorithm [3]. The problem: map an unbounded set of RTL pseudo-registers onto a finite set of machine registers (plus stack slots for spills), respecting interference (two live-at-once temporaries cannot share a register), calling conventions, and architectural constraints (e.g., two-address instructions).

The correctness argument is a lock-step forward simulation whose `match_states` relation says: at every program point, the LTL *location state* (registers + stack slots) **agrees** with the RTL *register state* on all pseudo-registers that are *live* at that point. The proof's crux is showing the coloring respects interference, which reduces to the soundness of the liveness analysis — a classic dataflow fixpoint, itself proved correct in Coq.

Two sub-proofs deserve special mention:

- **Parallel-move lowering.** Calling conventions produce *parallel* register moves (possibly cyclic); sequentializing them with at most one temporary per kind is folklore-correct but proof-hostile — the Rideau-Serpette mechanized proof [3] is among the project's most intricate.
- **Naive spilling.** The directly-verified allocator spills after every definition and reloads before every use of uncolorable temporaries — adequate for register-rich targets (PowerPC, ARM), motivating the validated approach below.

### 4.4 Verified validation: allocators and scheduling you don't have to prove

Proving an *advanced* allocator directly is daunting: complex algorithms, fragile invariants. Rideau and Leroy's answer [5] is **verified translation validation**: an *unverified* OCaml allocator (free to use any heuristic) paired with a **validator** — a Coq-verified checker accepting only correct input/output pairs. The theorem covers the composition: bad outputs fail compilation safely; only provably-correct ones are accepted.

The allocation validator runs a **backward dataflow analysis refining liveness**, checking the allocator's mapping in a single pass — handling splitting, reloading, coalescing, and calling conventions. Its Coq soundness proof shows acceptance implies the location-agreement invariant, hence lock-step simulation. The payoff: experiment freely with heuristics; the proof never changes [5].

The same architecture scales to **scheduling-like optimizations**. Tristan and Leroy applied verified validation to **lazy code motion** (PLDI 2009) [6]: an untrusted LCM implementation plus a verified validator based on available-expression analysis, with a machine-checked semantic-preservation proof. Trace-scheduling experiments follow the identical pattern — the validator checks that the scheduled trace is a semantics-preserving permutation. The lesson: *translation validation is the path of least resistance for aggressive optimizations*, since the validator reasons about one concrete transformation instance, not all executions of a complex algorithm.

```coq
(* Shape of a verified validator: untrusted oracle + proved checker *)
Record validator_result := { trans_ok : bool; (* checker verdict *) }.

Theorem validator_sound:
  forall (f f' : function) (v : validator_result),
    validate f f' = OK v -> trans_ok v = true ->
    forward_simulation (semantics f) (semantics f').
(* The oracle producing f' from f is entirely untrusted. *)
```

### 4.5 Mechanized proofs in Coq: discipline and scale

Recurring disciplines across the Coq development, worth naming as reusable methodology:

1. **Determinacy + receptiveness flipping.** Per-pass forward simulations compose and flip to a global backward simulation — but only because every language's semantics was *designed* deterministic and receptive. Semantics design is proof design.
2. **Well-founded stuttering measures.** Step-erasing/inserting optimizations use `star`/`plus` simulations with explicit measures; divergence preservation follows from well-foundedness.
3. **Untrusted oracles, verified checkers.** The parser is verified *a posteriori* (a validator checks the AST against the grammar); constant propagation uses abstract interpretation with widening checked, not proved.
4. **Axiom hygiene.** The development avoids classical axioms; the trusted base is Coq's kernel, extraction, the (validated) parser and pretty-printer, and the external assembler/linker [8].

## 5. Empirical Results and Formal Arguments

### 5.1 Scale of the formalization

The Coq development spans the compiler (tens of thousands of lines of Gallina) and proofs several times larger, maintained over more than a decade. Proof *maintenance* is a first-class result: per-pass modularity means new architectures (RISC-V) and optimizations are added by proving new simulations, not revisiting old ones.

### 5.2 Compiler quality: performance and compile time

Verified does not mean slow: CompCert delivers roughly **85-90% of GCC -O1 performance** on embedded benchmarks [1] — the price of provability (no loop optimizations, modest inlining) is bounded and adequate for control-dominated safety-critical software. Compilation is slower than GCC, but that cost is amortized over a certified product's lifetime.

### 5.3 Industrial adoption and qualification

CompCert is deployed in avionics and other critical industries with a commercial **qualification kit** for DO-178C / EN 50128 objectives. Kästner et al. (ERTS 2018) report that qualification effort *decreases* relative to GCC, because the proof discharges entire classes of verification objectives that testing otherwise must cover.

### 5.4 Testing a proved compiler

Paradoxically, the CompCert team also *tests* aggressively — bugs can hide in the trusted base (semantics definitions, extraction, validator oracles) that the theorem does not cover. Monniaux et al. (TAP 2023) describe randomized differential testing against GCC/Clang, which has uncovered *specification* bugs and TCB issues rather than proof bugs — proof eliminates exactly the defect class it targets; testing guards the perimeter [8].

| Assurance activity | Defect class eliminated | Residual risk |
|---|---|---|
| Coq proof of passes | miscompilation in verified passes | none (modulo kernel soundness) |
| Verified validators | unsound optimization instances | oracle bugs (caught: compile fails safe) |
| Differential testing | semantics/TCB mismatches | incomplete coverage |
| Qualification kit | process objectives (DO-178C) | external assembler/linker |

## 6. Limitations and Open Problems

1. **The trusted computing base.** The theorem assumes: the Coq kernel and extraction; the Clight semantics (does it *mean* C?); unverified front-end elaboration; the assembler, linker, and hardware [8]. A bug in the Clight semantics is a bug in the theorem's statement, invisible to Coq.
2. **Concurrency.** The main theorem is sequential. CompCertTSO extends the result to x86-TSO, but a general verified compiler for the C11 memory model with data-race semantics remains open; the block-based memory model [2] was not designed for concurrent access and its extension is nontrivial.
3. **Optimization ceiling.** Loop optimizations (LICM beyond LCM, vectorization, software pipelining), SSA-based middle ends, and link-time optimization are absent or experimental. Each requires new simulation arguments; verified validation [5][6] is the favored vehicle, but scaling validators to loop nests with polyhedral transformations is an open proof-engineering challenge.
4. **Proof maintenance economics.** The development is a large, specialized codebase; evolving it requires rare expertise at the intersection of compiler engineering and interactive theorem proving. Better proof automation and more modular semantics frameworks (e.g., interaction trees) are needed to lower the entry barrier.
5. **Undefined behavior refinement.** The theorem permits the compiler to *refine* undefined behavior arbitrarily — the standard's license, but a source of subtle security-relevant surprises (e.g., `Vundef` propagation enabling surprising optimizations). Formally characterizing which refinements are security-preserving is open.

## 7. Conclusion

CompCert turned verified compilation from aspiration into engineering discipline. Its contributions are methodological as much as technical: **semantic preservation as backward simulation**; **per-pass forward simulation** with determinacy/receptiveness flipping; the **block-based memory model with injections** [2][7]; **verified translation validation** [5][6] for aggressive optimization; and **proof-co-design**. The mechanized allocator and validated scheduling experiments show even the most intricate back-end algorithms submit to machine-checked proof when untrusted heuristics are separated from verified checkers. The open problems — concurrency, the optimization ceiling, TCB minimization [8] — define the frontier. The central result stands: a realistic C compiler that *cannot miscompile*, known not by testing, but by proof.
