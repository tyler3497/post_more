# Program Synthesis from Specification: SyGuS Grammars, CEGIS Loops, Sketch-Guided Search, and LLM-Guided Synthesis with Verification Feedback

## Abstract

Program synthesis seeks the automatic construction of programs from specifications, trading programmer labor for computational search. This article surveys the dominant formal frameworks that have shaped the field: **Syntax-Guided Synthesis (SyGuS)**, which constrains the search space by a context-free grammar and states correctness as a quantified formula; **Counterexample-Guided Inductive Synthesis (CEGIS)**, which alternates an inductive synthesizer that generalizes from examples with a verification oracle that refutes candidates with counterexamples; **sketch-guided synthesis**, in which the programmer supplies a partial program whose holes the synthesizer completes; and the recent **neuro-symbolic hybrids**, where large language models propose candidates inside a CEGIS-style loop closed by formal verification feedback. We develop the formal foundations, work through the classic `max` example in full, analyze the relative power and termination behavior of CEGIS variants (including minimal and history-bounded counterexamples), sketch the reduction of deductive synthesis to proof extraction, and evaluate empirical progress from the SyGuS competitions and SMT-embedded synthesis engines. The article closes with an assessment of the open limitations: theory dependence, scalability of the synthesize-verify loop, distribution shift in neural guidance, and the soundness risks of LLM feedback loops.

## 1. Introduction

Few aspirations in computer science are as old or as resilient as *automatic programming*: given a description of *what* a program should do, produce a program that does it. Early deductive work in the 1980s treated synthesis as constructive proof — extract a program from a proof of a ∀∃ specification. The approach was principled but brittle: the user had to guide the proof through an unfamiliar interactive theorem prover, and the resulting systems demanded formalisms far removed from ordinary programming practice [1].

The modern synthesis renaissance took a different route. Rather than demanding complete formal specifications and expert-guided proofs, it accepts three compromises that make synthesis tractable in practice:

1. **Search-space restriction.** The synthesizer explores only programs expressible in a restricted language — a grammar (SyGuS), a template, or a *sketch*: a partial program with *holes* marking the details to be filled in [1][2].
2. **Example-driven induction plus verification.** A *CEGIS loop* learns a candidate from a finite set of input-output examples and then calls a verification oracle to prove correctness or to extract a counterexample refuting the candidate [3][7].
3. **Specification by behavior.** Correctness is stated as a logical formula — often `∃f. ∀x. P(f, x)` — where `P` is expressed in a decidable SMT theory such as linear integer arithmetic or bitvectors [6].

More recently, a fourth element has arrived: **neural guidance**. Large language models trained on code act as powerful prior distributions over program space, proposing plausible candidates that a verifier then accepts or refutes, closing the loop with counterexample feedback [4]. This article develops each of these threads, their interactions, and their formal guarantees.

## 2. Background

### 2.1 The synthesis problem

We fix a domain of values *D* and a class of programs *P*. A *specification* is a relation σ ⊆ *D* × *P* — or, in logical form, a formula φ(*f*, *x*) relating a program *f* and its inputs *x*. The **synthesis problem** is:

> **Synthesis:** Find *f* ∈ *P* such that ∀*x* ∈ *D*. φ(*f*, *x*), or report that no such program exists.

This is the standard *∀∃-quantified* formulation that underlies both SyGuS and CEGIS [7]. The universal quantifier over inputs is what makes the problem hard: it demands that *f* be correct on *all* inputs, while any tractable search procedure can only ever inspect *finitely* many of them.

### 2.2 Deductive synthesis

The classical deductive approach (Manna and Waldinger) treats synthesis as theorem proving: prove `∃f. ∀x. φ(f, x)` in a constructive logic and extract the witness *f* from the proof. This yields a powerful guarantee — the program is correct *by construction* — but pushes the search problem into proof search, which is generally undecidable and in practice requires extensive user guidance [1]. Modern descendants include synthesis inside proof assistants, where tactics generate both the program and its correctness proof simultaneously.

### 2.3 Inductive synthesis and the CEGIS architecture

**Counterexample-Guided Inductive Synthesis (CEGIS)** reconciles the finite with the infinite through an oracle-guided loop [2][3][7]:

1. **Synthesize.** Given a finite set *E* of input-output examples, an inductive synthesizer produces a candidate program *f* consistent with *E*.
2. **Verify.** A verification oracle checks `∀x. φ(f, x)`. If valid, return *f*.
3. **Refine.** If invalid, the oracle extracts a *counterexample* input *c* with ¬φ(*f*, *c*), adds it to *E*, and repeats.

The loop is a synthesis analogue of the counterexample-guided abstraction refinement (CEGAR) loop in model checking: each iteration eliminates at least one wrong candidate (or one class of wrong candidates), and for a *finite* candidate space the loop is guaranteed to terminate with a correct program or a proof of unrealizability [7].

> **Theorem (CEGIS termination, finite spaces):** If the candidate space *P* is finite, the CEGIS loop terminates: it returns *f* ∈ *P* with ∀*x*. φ(*f*, *x*), or it concludes that no such program exists. This follows because every iteration that does not terminate adds a counterexample ruling out at least the current candidate.

For *infinite* spaces — grammars of unbounded term size — termination is no longer guaranteed in general, and the *quality* of the counterexamples matters. Jha et al. analyze whether *minimal* counterexamples (MinCEGIS) or *history-bounded* counterexamples (HCEGIS) change the synthesis power of the loop [7]. Their results are subtle: MinCEGIS has the *same* power as plain CEGIS, while HCEGIS has *different* power — strictly incomparable, neither dominating the other. There are, in a formal sense, "good mistakes": the choice of which counterexample the oracle returns can determine whether synthesis succeeds at all.

### 2.4 Syntax-guided synthesis

**SyGuS** (Syntax-Guided Synthesis) provides a unified logical framework that separates the *semantic* specification from the *syntactic* specification [5][6]. A SyGuS problem is a pair:

- a **semantic specification**: a quantified formula `∃f. ∀x. P(f, x)` in an SMT theory;
- a **syntactic specification**: a context-free grammar *G* constraining the body of *f*.

For example, the classic `max` benchmark states [6]:

```
∃f. ∀x, y. (f(x,y) ≥ x) ∧ (f(x,y) ≥ y) ∧ (f(x,y) = x ∨ f(x,y) = y)
```

with grammar:

```
A → A + A | -A | x | y | 0 | 1 | ite(B, A, A)
B → B ∧ B | ¬B | A = A | A ≥ A | ⊥
```

The standardized SyGuS input format and the annual **SyGuS competition** turned synthesis into an empirical science: dozens of solvers compete on tracks (LIA, bitvectors, PBE strings), and the grammar-per-track design lets benchmark authors calibrate problem difficulty to the frontier of solver capability [6].

### 2.5 Sketch-guided synthesis

**Sketching** (Solar-Lezama) takes a different route to constraining the search space: the programmer writes a *sketch* — an ordinary program with *holes* (`??`) in place of low-level details — and the synthesizer completes the holes so the result satisfies a separate specification [1][2]. For example:

```c
int max_sketch(int x, int y) {
    if (??) return x; else return y;
}
```

The holes are compiled into Boolean/integer control variables, and a SAT-based inductive synthesis procedure searches assignments to those variables. Sketching was the original home of CEGIS: the thesis introduces the algorithm as the synthesis core of the SKETCH language [1]. The key insight is sociological as much as technical — sketches let programmers communicate high-level insight in a formalism they already know, while the machine fills in the tedious detail.

### 2.6 Semantics-guided synthesis

**SemGuS** generalizes SyGuS by adding a third component: the *semantics* of the grammar constructs, given as inference rules [5]. This closes an expressiveness gap: SyGuS semantics are limited to fixed SMT theories, while solver-aided languages like Rosette can express imperative programs with loops but cannot state SyGuS problems with infinite search spaces. SemGuS encompasses both by letting the user define meaning explicitly, yielding a single framework for synthesis across theories, languages, and paradigms.

## 3. Methodology

### 3.1 The CEGIS loop, formally

Following the oracle-based formulation of [7], we define the components precisely.

**Definition (CEGIS oracle interface).** Let ℒ be a class of candidate languages, *D* the example domain, and *L*φ ⊆ *D* the target behavior set. The oracle interface 𝒪 = 𝒬 × ℛ offers:

- `q_wit⁺`: returns a *positive witness* — an example *i* ∈ *L*φ;
- `q_corr(L)`: given a candidate *L* ∈ ℒ, returns a counterexample *i* ∈ *L* \ *L*φ, or ⊥ if *L* ⊆ *L*φ.

The CEGIS engine iterates:

```
E := ∅
loop:
    f := Synthesize(E)          # inductive step: consistent with E
    if f = NONE: return UNREALIZABLE
    cex := Verify(f)            # deductive step: ∀x. φ(f,x)?
    if cex = ⊥: return f
    E := E ∪ {cex}
```

The **synthesizer** is an *inductive* learner: it only ever sees finitely many examples. The **verifier** is *deductive*: it reasons about the whole input domain. This division of labor is what makes CEGIS practical — the expensive all-inputs check happens once per candidate, while the synthesizer works in the much smaller world of accumulated counterexamples.

### 3.2 Learning strategies

Three families of inductive learners dominate the literature [3]:

| Strategy | Mechanism | Strengths |
|---|---|---|
| **Enumerative** | Enumerate grammar terms by increasing size; prune by equivalence on examples | Simple, complete for finite spaces; dominates SyGuS competitions [4][6] |
| **Symbolic / constraint-based** | Encode "∃ program consistent with *E*" as SAT/SMT; solve | Handles holes and templates; core of SKETCH [1][2] |
| **Stochastic** | Random walk (MCMC) over program space, e.g. STOKE superoptimization | Scales to low-level code; escapes local minima |

The enumerative approach deserves emphasis because of an empirical surprise noted across the field: *enumerative synthesis with good heuristics remains the dominant SyGuS technique* [4]. Exhaustive enumeration guided by equivalence pruning on examples is hard to beat when the grammar is small, which motivates machine-learned heuristics to bias the enumeration order [4].

### 3.3 The verifier's role

The verifier must decide `∃x. ¬φ(f, x)` — a satisfiability query in the theory. For decidable theories this is routine SMT. The **CEGIS(T)** architecture generalizes the loop so that synthesis and verification communicate through *theory solvers*, with the candidate's skeleton generalized by constant removal and deduction propagating constraints back to the synthesizer [8]. When the verification query is unsatisfiable, the candidate is a final solution; when satisfiable, the model yields a concrete counterexample.

### 3.4 Sketching as constraint solving

In SKETCH, holes `??` become *control variables* **c**. The synthesis problem "find **c** such that ∀*x*. Spec(sketch(**c**), *x*)" is solved by a SAT-based procedure: the bounded checker encodes the sketch, the specification, and a bounded input domain into a Boolean formula, and the solver's model assigns the holes [1][2]. Finite programs — cryptographic kernels, bit-manipulation routines, stencil computations — fall squarely in this regime: Solar-Lezama reports a DES cipher synthesized from a sketch in an afternoon, matching hand-tuned performance [2].

## 4. Deep Dive

### 4.1 Worked example: synthesizing `max` by CEGIS

Consider the specification `x ≤ f(x,y) ∧ y ≤ f(x,y)` over the grammar of `ite`, comparisons, `+`, and constants. We trace the CEGIS loop [3]:

**Iteration 1.** Examples *E* = {(0, 1)}. The synthesizer proposes the smallest consistent candidate, `f(x,y) = y`. The verifier checks `∀x,y. x ≤ y ∧ y ≤ y` — satisfiable to refute: counterexample (1, 0).

**Iteration 2.** *E* = {(0,1), (1,0)}. Candidates consistent with both: any `f` with `f(0,1) ≥ 0 ∧ f(0,1) ≥ 1` and `f(1,0) ≥ 1 ∧ f(1,0) ≥ 0`. The synthesizer might propose `f(x,y) = x + y`. Verifier refutes with (0, 0): `0 ≤ 0` holds but the full spec (with the `f = x ∨ f = y` clause) fails since `0 + 0 = 0`... under the tighter spec the counterexample stands for the ≥ clauses trivially — concretely, (1,1) gives `f = 2 ≠ 1,2`'s required disjunct. Add (1, 1).

**Iteration 3.** *E* = {(0,1), (1,0), (1,1)}. Now `f(x,y) = ite(x ≤ y, y, x)` is consistent with all examples, and the verifier proves `∀x,y` validity. **Success.**

Each counterexample eliminated a *class* of wrong programs (all programs wrong on that input), not just the single candidate — this is why CEGIS converges quickly in practice despite its worst case.

### 4.2 SyGuS as ∃∀ solving

SyGuS problems are *syntax-guided ∃∀ conjectures modulo theories*: `∃f. ∀x. P(f, x)` where `f`'s body ranges over a grammar [6]. The "syntax-guided" qualifier matters because the same semantic specification with a larger grammar is a *different*, harder problem — the grammar is not an implementation detail but part of the problem statement. This is why the SyGuS competition varies grammars across tracks and even within tracks [6]: the grammar calibrates difficulty.

Two solver architectures dominate [6]:

1. **Enumerative CEGIS.** An enumerator generates grammar terms in heuristic order; each candidate is checked against the accumulated examples and then the full quantified spec by the SMT solver's own CEGIS-for-quantifiers machinery.
2. **CEGIST with refutation-based synthesis.** The SMT solver's quantifier-instantiation engine is adapted so that instantiations *are* candidate programs, turning the solver itself into the synthesizer.

Both live inside the SMT solver in modern systems (e.g. cvc5), blurring the line between "synthesizer" and "solver" [6].

### 4.3 Deductive synthesis and proof extraction

Deductive synthesis inverts the inductive direction: instead of learning from examples and verifying after the fact, it *constructs* the program during proof search. The sequent-calculus approach of Manna and Waldinger applies non-clausal resolution to a specification `∀x. ∃z. φ(x, z)`; each resolution step simultaneously refines a conditional program term, and the extracted term is correct by the soundness of the calculus. The guarantee is absolute — no verifier loop needed — but automation is the bottleneck: proof search in expressive logics is undecidable, so practical deductive synthesizers restrict to decidable fragments or demand interactive guidance [1]. In the modern landscape, deductive synthesis survives principally as *type-directed* synthesis (programs from refinement types) and as verified compilation, where the "proof" is a machine-checked certificate.

### 4.4 Neuro-symbolic hybrids: LLM-guided synthesis with verification feedback

The most active recent development pairs a **large language model** with a **formal verifier** in a CEGIS-shaped loop [4]:

```
loop:
    candidates := LLM(spec, feedback)     # neural proposal
    for f in candidates:
        cex := Verify(f)                  # symbolic check
        if cex = ⊥: return f
        feedback := feedback ∪ {cex}      # counterexample in context
```

The LLM acts as a *learned prior* over program space, replacing or augmenting the enumerative heuristic; the verifier supplies *ground-truth* feedback that the LLM cannot hallucinate away. Reinforcement-learning approaches train the proposal policy directly on synthesis rewards: Parser and Polgreen show that an RL loop can *learn its own search heuristics* for SyGuS with relatively little training data, addressing the hypothesis that ML has underperformed in logical-specification SyGuS precisely because training data was scarce [4].

Two guarantees distinguish this architecture from "ask the LLM and hope":

- **Soundness is inherited from the verifier.** Whatever the LLM proposes, only a machine-checked candidate is returned. The neural component affects *efficiency*, never *correctness*.
- **Counterexamples are the feedback currency.** Feeding refutations back into the model's context (or into its training reward) mirrors the CEGIS refinement step exactly — the LLM is an inductive learner that happens to be differentiable and pretrained on code.

The failure modes are correspondingly CEGIS-like: if the verifier's theory cannot express the property, the loop certifies nothing; if the LLM's distribution never proposes the needed construct, the loop spins. Distribution shift — specifications unlike anything in training — remains the central empirical risk.

## 5. Empirical Evaluation / Proofs

### 5.1 Proof sketches

We collect the key formal results referenced above:

> **Theorem (CEGIS soundness):** Any program returned by the CEGIS loop satisfies ∀*x*. φ(*f*, *x*). *Proof.* The loop returns *f* only when `Verify(f)` reports ⊥, i.e. `∃x. ¬φ(f,x)` is unsatisfiable, which is exactly ∀*x*. φ(*f*,*x*). ∎

> **Theorem (Jha et al. [7]):** MinCEGIS (minimal counterexamples) has the same synthesis power as CEGIS; HCEGIS (history-bounded counterexamples) has incomparable power — neither dominates the other. *Significance:* the oracle's *choice* of counterexample is semantically load-bearing, not an implementation detail.

> **Theorem (Sketching decidability [1]):** For finite programs (bounded loops, bounded integers), the SKETCH completion problem reduces to SAT and is therefore decidable; the CEGIS core terminates.

### 5.2 Empirical landscape

- **SyGuS competitions** (2014–present): enumerative solvers with aggressive equivalence pruning dominate the PBE and LIA tracks; grammar size is the strongest predictor of difficulty, which motivated grammar-filtering research [6].
- **Sketching case studies** [2]: DES cipher from a one-afternoon sketch at near hand-tuned performance; cipher kernels 2× faster than reference C — evidence that sketching captures *algorithmic* insight while automating *optimization* detail.
- **RL-guided SyGuS** [4]: learned heuristics adapt to unseen tasks with reported speedups of 2×–100× over uninformed enumeration in the meta-solver setting.
- **CEGIS(T)** [8]: lifting the loop into theory solvers extends synthesis to programs with interpreted constants, with the skeleton-generalization step propagating learned constraints back to the synthesizer.

## 6. Limitations

1. **Theory dependence.** SyGuS and SMT-embedded CEGIS inherit the limits of their theories: linear arithmetic and bitvectors are well supported; non-linear arithmetic, strings with length, and heap reasoning remain frontier territory [5][6]. SemGuS relaxes this by user-defined semantics, at the cost of automation.
2. **The loop's scalability ceiling.** Each CEGIS iteration pays a full verification query; for deep programs the number of iterations — and the size of the accumulated example set — can explode. Unrealizability detection (proving *no* program exists) is especially costly.
3. **Specification burden.** Writing a correct, complete formal specification is often as hard as writing the program. Under-specification yields programs that are "correct" yet useless; this is the practical ceiling on deployment outside verified domains.
4. **Neural guidance risks.** LLM proposers bring distribution shift, prompt brittleness, and a subtle soundness-adjacent risk: *feedback leakage*, where the loop overfits to verifier quirks rather than the specification. The verifier remains the trust anchor — but only if it is itself sound and complete for the property at hand.
5. **Sketching's expertise requirement.** Sketching trades specification effort for *insight* effort: a bad sketch (holes in the wrong places) yields slow or failed synthesis, and writing good sketches is a skill [1].

## 7. Conclusion

Program synthesis has converged on a small set of durable ideas. **SyGuS** gave the field a common language — grammar plus quantified formula — and a competitive empirical culture. **CEGIS** gave it the central algorithm: learn from examples, refute by verification, repeat, with termination guaranteed over finite spaces and a subtle, counterexample-sensitive power hierarchy over infinite ones. **Sketching** showed that human insight and machine search compose best through partial programs rather than through proofs. And **LLM-guided synthesis with verification feedback** is now showing that a learned prior over programs can accelerate the loop by orders of magnitude *without surrendering the verifier's guarantee* — the neural network proposes, the solver disposes.

The open frontier is synthesis that is *both* general and trustworthy at scale: richer theories, cheaper verification, specifications that are easier to write than the programs they describe, and neuro-symbolic loops whose feedback cannot be gamed. Until then, the discipline's central lesson stands: **search proposes, proof disposes** — and the architecture that keeps those two roles honest is the loop.
