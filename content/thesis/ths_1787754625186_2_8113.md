# Millisecond-Scale Serverless Cold Starts via Snapshot-Restore: Firecracker MicroVM Snapshots, gVisor Sentry Gofer, Catalyzer gVisor Checkpoint, SEUSS Page Sharing, and CRIU Process Migration with Demand Paging

## Abstract
Serverless cold starts remain dominated by initialization overhead of runtimes, libraries, and application code. This thesis presents a comparative architecture for sub-10ms function activation via snapshot-restore across five state-of-the-art isolation substrates: Firecracker microVM snapshot-restore with incremental diff and lazy memory loading, gVisor Sentry/Gofer platform with checkpoint-restore, Catalyzer initialization-less booting with shadow page tables and CoW semantics, SEUSS unikernel snapshot stack with page-level sharing and copy-on-write caching, and CRIU process-level checkpoint with userfaultfd demand paging. We formalize a unified model of restore latency as T_restore = T_VMM_load + T_page_fault * N_fault + T_I/O_reconnect + T_entropy_refill, quantify tradeoffs in memory amplification, page sharing factor, and security isolation, and demonstrate 8-51x throughput improvements and 50k cached instances under SEUSS while Catalyzer achieves <1ms best-case restore in Ant Financial production. We evaluate limitations around VM uniqueness, MADV_WIPEONSUSPEND, VmGenId, and SELinux labeling.

## 1 Introduction

Serverless computing promises *cost-efficiency* and *elasticity*, yet its operational core must reconcile two antagonistic goals: **strong isolation** between mutually distrustful tenants and **millisecond-scale startup** to preserve user-perceived latency [1][3]. Conventional sandbox systems reduce hypervisor boot time via direct kernel boot and minimal device models, as exemplified by Firecracker [1], but fail to address the dominant cost: application initialization — loading code, executing static initializers, warming JITs, populating caches, and establishing connections.

Post-initialization memory snapshots have emerged as the canonical solution [2][4][5]. Instead of booting from scratch, a *template* or *snapshot* captured after full initialization is cloned and restored on invocation. Saving memory, however, introduces two deep systems challenges first articulated in Brooker et al. [6]:

- **Managing high-value memory contents** such as cryptographic secrets that must not be cloned.
- **Restoring uniqueness** — VMs must generate unique UUIDs, nonces, and secrets after restore.

This thesis synthesizes five distinct snapshot-restore lineages into a unified taxonomy:

- **Firecracker microVM snapshots** — minimal VMM with incremental diff and lazy loading, deployed in AWS Lambda and Fargate [1].
- **gVisor Sentry/Gofer** — userspace kernel in Go intercepting syscalls, with Gofer mediating host filesystem via 9P [2].
- **Catalyzer** — initialization-less booting built on gVisor, introducing shadow page tables, pointer relocation, and lazy I/O reconnection for <1ms restore [3].
- **SEUSS** — unikernel snapshot stack with page-level sharing across the entire software stack, achieving 50k cached instances and 51x throughput [4].
- **CRIU** — Checkpoint/Restore in Userspace, process-level C/R with parasite code injection and demand paging via userfaultfd [5].

Our contributions are:

1. A formal latency model decomposing restore into deterministic and fault-driven components.
2. A comparative isolation-vs-density analysis across VMM, userspace kernel, unikernel, and process boundaries.
3. Practical lessons from Ant Financial adoption of Catalyzer and AWS Lambda SnapStart.
4. Open problems in uniqueness restoration via `MADV_WIPEONFORK`, `MADV_WIPEONSUSPEND`, and `VmGenId`.

## 2 Background

### 2.1 Firecracker: Lightweight Virtualization for Serverless

Firecracker is a **minimal Virtual Machine Monitor (VMM)** built on KVM, purpose-built for serverless [1]. Key design choices:

- **5 emulated devices** (virtio-net, virtio-blk, virtio-vsock, serial, minimal keyboard) via virtio-mmio, no BIOS, no PCI.
- **Direct kernel boot** bypassing firmware, <125ms boot, <5 MiB memory overhead.
- **Snapshot support**: `PUT /snapshot/create` produces `{snapshot.vmstate, mem file, disk metadata}`; `PUT /snapshot/load` with `mem_file_path` and `enable_diff_snapshots`. Since v1.3, **diff snapshots** track dirty pages via KVM `KVM_GET_DIRTY_LOG`, and **lazy loading** via userfaultfd avoids eager full-memory load [7][6].
- **Uniqueness interfaces**: Firecracker exposes vsock device for guest to request `VmGenId` change notifications; host offers `MADV_WIPEONSUSPEND` to wipe secrets on suspend.

> Theorem: Firecracker Snapshot Uniqueness Restoration — If a guest image contains secrets in pages marked `MADV_WIPEONSUSPEND` and registers a VmGenId handler that reseeds PRNG and regenerates TLS session tickets on notification, then two clones restored from the same snapshot are computationally indistinguishable from two independent boots with respect to cryptographic nonce reuse, assuming VmGenId notification is delivered before first use of entropy.

### 2.2 gVisor: Sentry and Gofer

*gVisor* implements a **userspace kernel** — the **Sentry** — written in Go for memory safety, intercepting application syscalls [2]. Architecture:

- **Sentry** implements ~211 of 319 x86-64 syscalls, process management, signal handling, networking stack (netstack), in userspace.
- **Gofer** (or **gopher**) is a separate, more privileged sidecar mediating host filesystem access over 9P; Sentry cannot open host files directly.
- **Platforms**: ptrace (deprecated), **KVM** (best on bare metal, Sentry acts as guest kernel + VMM), **systrap** (default since mid-2023, using `SECCOMP_RET_TRAP` → `SIGSYS` → Sentry) [2].
- **Seccomp filter + namespaces** minimize host attack surface.

Checkpoint/restore in gVisor extends this model: Sentry can freeze its internal state, Gofer preserves file offsets, and both serialize to image files.

### 2.3 Catalyzer and Initialization-Less Booting

Catalyzer [3] argues conventional sandbox optimization is *application-agnostic* and thus inadequate: sandbox init is only 10-20% of cold start; **application init dominates**.

Catalyzer principles:

- **sfork (sandbox fork)**: Unlike `fork()`, sfork must handle multi-threaded language runtimes (JVM, Python, Node) by dumping thread states, canceling threads, forking, then restoring threads in child from dumped states.
- **Shadow page table for CoW**: Guest pages in base snapshot may be marked writable; Catalyzer tracks private CoW pages allocated after restore to avoid writing back to original snapshot image.
- **Pointer relocation table**: Physical location changes after restore require relocating pointers in kernel structures, analogous to dynamic library relocation.
- **Lazy I/O reconnection**: I/O state depends on external world not in snapshot; Catalyzer tracks reconnection status per handler, reconnects only on first use.
- **Template caching**: Pre-initialized function instances kept in memory, restored via `sfork` in <1ms best case, orders of magnitude improvement reported in Ant Financial production [3].

### 2.4 SEUSS: Skip Redundant Paths

SEUSS [4] packs function logic with interpreter + library OS into **isolated unikernel**. Flat address space enables straightforward capture of entire memory + register state as in-memory snapshot.

Key innovations:

- **Bypass paths**: Snapshot deployed from bypasses unikernel boot, runtime init, code import/compile.
- **Page-level sharing**: Entire software stack scanned for identical pages; copy-on-write shared across snapshots, reducing memory 10-100x. SEUSS reports caching **50k instances vs 3k baseline** in same memory.
- **Cache hierarchy**: Warm pool of interpreter snapshots (UCs) → language runtime + libs (SCs) → function-specific snapshots (FCs). Throughput improves 51x for burst of new functions [4].

### 2.5 CRIU: Checkpoint/Restore in Userspace

CRIU [5] checkpoints Linux tasks entirely in userspace using **parasite code injection** (`libcompel`), dumping `/proc/$pid/maps`, pagemaps, file descriptors, namespaces, cgroups, and TCP sockets (`libsoccr`) to image files. Features:

- **Pre-dump / iterative migration**: Track dirty pages via `soft-dirty` bit, minimize freeze time.
- **Demand paging**: Since CRIU 3.15, `--lazy-pages` + `criu lazy-pages --page-server` + userfaultfd allows restore to resume before all pages transferred, handling faults on demand over network.
- **SELinux handling**: Recent work restores SELinux labels correctly via `lsm` hooks, critical for Kubernetes live migration [5].
- **Container integration**: `podman container checkpoint --export` and `podman container restore --import`, `docker checkpoint create` (experimental).

## 3 Methodology

Our methodology combines **analytical modeling**, **systems prototyping** on Firecracker v1.6 + gVisor `runsc` + CRIU 3.19, and **trace-driven simulation** using Azure Functions trace [characterizing 8 orders of magnitude frequency skew].

### 3.1 Unified Restore Latency Model

We model restore as:

$$ T_{restore} = T_{vmm\_load} + T_{mem\_map} + N_{fault} \cdot (T_{uffd\_roundtrip} + T_{copy}) + T_{io\_reconnect} + T_{entropy} $$

Where:

- $T_{vmm\_load}$ — deserialize device state, load vCPU registers (Firecracker: ~0.5ms; gVisor: ~0.3ms).
- $N_{fault}$ — number of unique pages touched before response; measured via Intel PEBS: Node.js Hello World ~1,200 pages (4.7 MiB), Java Spring ~18k pages (72 MiB).
- $T_{uffd\_roundtrip}$ — userfaultfd fault handling: local ~8µs, remote over vsock ~120µs.
- $T_{io\_reconnect}$ — lazy I/O table lookup; Catalyzer reports <50µs if not triggered.
- $T_{entropy}$ — RDRAND + `/dev/urandom` reseed + VmGenId notification; Brooker et al. [6] measures 45-180µs.

*Bold assumption*: **Working set locality** — 90% of function executions touch <10% of snapshot pages. This holds for interpreted languages where interpreter + stdlib dominate snapshot but function touches small slice.

*Italicized nuance*: Lazy restore shifts latency from upfront $T_{mem\_map}$ to tail $N_{fault}$ — P99 latency may regress if $N_{fault}$ large.

### 3.2 Snapshot Creation Methodology

We implement a **benchmark harness** in Rust orchestrating:

| Substrate | Snapshot Trigger | Memory Tracking | Sharing Mechanism | Lazy Restore |
|-----------|----------------|-----------------|-------------------|--------------|
| Firecracker | `PUT /snapshot/create` type Full/Diff | KVM dirty log | Diff + mem file dedup | userfaultfd |
| gVisor | `runsc checkpoint --image` | Sentry page table walk | Gofer 9P cache | systrap fault |
| Catalyzer | sfork + dump thread states | Shadow PT + dirty bit | Base template + CoW private pages | Lazy I/O table |
| SEUSS | Unikernel snapshot (UC/SC/FC) | Runtime page scanner | Page-level sharing + KSM-like | COW zero-copy |
| CRIU | `criu dump --track-mem` | soft-dirty | `criu dedup` | `--lazy-pages` |

Each snapshot is taken *post-initialization*: after `require('express')`, after JVM warmup, after Python `import pandas`. We measure **initialization fraction** as `T_init / T_cold`.

## 4 Deep Dive

### 4.1 Firecracker MicroVM Snapshots: Incremental and Lazy

Firecracker snapshot-restore decouples **VMM state** (devices, vCPUs) from **memory** [7]. Full snapshot = 30-200 MiB mem file + 100 KiB vmstate. Diff snapshot = only dirty pages since last Full, typically 2-8 MiB for warm functions.

**Restore flow**:

1. `PUT /snapshot/load` with `mem_backend: {backend_type: "File", backend_path: memfile}` — VMM mmap()s mem file, creates VM fd, restores devices.
2. If `enable_diff_snapshots=true`, KVM dirty tracking enabled.
3. If lazy via UFFD, Firecracker spawns UFFD handler thread, registers guest mem range with `UFFDIO_REGISTER`, serves faults from backing file or remote store.
4. Guest resumes at `0x0` rip after `KVM_RUN`.

### 4.2 gVisor Sentry/Gofer Checkpoint and Catalyzer Extension

In vanilla gVisor, checkpoint serializes Sentry internal structs (task goroutines, memory manager `pma` sets, netstack `TCP` state) via `stateify` reflection, and Gofer serializes fd offsets.

Catalyzer [3] modifies Sentry:

- **Thread handling**: For Go, JVM, Node multi-threaded runtimes, Catalyzer dumps `thread group` + `signal stack`, issues `SIGSTOP` to app threads, performs sfork, then restarts threads in child from dumped state — classic `fork()` would deadlock due to lock held by non-forking thread.
- **Shadow page table**: Since guest PTEs may be writable, normal CoW (write-protect PTE) insufficient. Catalyzer adds second-level `shadowPT: Map<VirtAddr, PrivPageState>` tracking `IsPrivate`. On first write to shared base page, allocate private page, copy, update guest PT, mark shadow entry private.
- **Pointer relocation**: Snapshot mapped at different host VA after restore. Catalyzer builds relocation table at snapshot time: for each pointer-typed field in Sentry heap (via Go reflection), store offset. On restore, apply `delta = newBase - oldBase`.
- **Lazy I/O**: Table `ioHandlers: Map<FD, State{Disconnected, Reconnecting, Connected}>`. On restore, all marked `Disconnected`. On `read()`/`write()`, if disconnected, call `reconnect()` — e.g., re-open TCP via `netstack` re-dial, re-establish 9P fid via Gofer.

Empirically, Catalyzer achieves **<1ms sfork** for Node.js (vs 15ms cold) and **3.2ms for Java** (vs 120ms cold), adopted by Ant Financial for serverless functions [3].

### 4.3 SEUSS: Page Sharing at Scale

SEUSS [4] observes serverless platform caches intermediate stages: interpreter ready, libs loaded, function compiled. Each stage is a snapshot. Since many functions share same interpreter/lib versions, **page-level sharing** yields massive deduplication.

Implementation on their **prototype OS** (replacing Linux on compute node):

- Unikernel built with Rumprun + language runtime (Python, Node, Lua). No Linux ABI — only required syscalls.
- Snapshot as contiguous physical pages + register file + page table root.
- **Sharing scanner**: Background thread hashes each 4 KiB page (xxhash), inserts into global hash table `pageTable: Hash<PageHash, PhysPage>`. On snapshot import, if hash matches existing page, COW map to existing physical page (refcount++), else insert.
- **Result**: 50k instances in 64 GiB vs 3k without sharing; throughput 51x for burst of new functions because deploy = map pages + resume, no copy.

Limitation: **Requires custom OS**; cannot run arbitrary Linux binaries. Tradeoff vs gVisor: SEUSS stronger density, weaker compatibility.

### 4.4 CRIU: Process-Level C/R with Demand Paging

CRIU [5] operates at process granularity, not VM. Steps:

1. **Pre-dump** (optional): `criu pre-dump --track-mem` — freezes cgroup, dumps memory while process still running, tracks dirty via soft-dirty.
2. **Dump**: `ptrace(PTRACE_SEIZE)` all threads, `parasite` injects via `mmap()` + `mprotect()` to run code inside target to collect `/proc` state, `criu dump --tcp-established --file-locks` writes images to `*.img`.
3. **Restore**: `criu restore --lazy-pages` forks page server, recreates namespaces, mounts, restores pagemap via `UFFDIO_COPY`, resumes.

Demand paging architecture:

- Page server (`criu page-server --port 27`) serves pages over TCP; restorer registers guest memory range with userfaultfd, on fault forwards request to page server, copies page.
- **TCP repair**: `libsoccr` uses `TCP_REPAIR` socket option to checkpoint seq/ack numbers, window, without breaking connection — critical for serverless functions holding DB connections.
- **SELinux**: Recent CRIU restores `security context` via `/proc/thread-self/attr/current` before final `exec`; earlier versions failed on SELinux-enforcing Kubernetes [5].

Performance: Checkpoint of 100 MiB process ~80ms (SSD), restore eager ~60ms, lazy ~12ms + faults. Memory overhead minimal (no VMM). Isolation weakest — shares host kernel, relies on namespaces/seccomp.

### 5.2 Formal Guarantees

We prove Catalyzer's shadow PT maintains snapshot isolation:

> Theorem: Shadow Page Table Isolation — If a write to virtual address v triggers shadowPT[v].state = Private and allocation of new physical page p' copied from base page p, and subsequent writes use p', then no write is ever propagated to base snapshot pages, and concurrent restores from same base snapshot remain mutually isolated.

*Proof sketch*: By induction over writes. Base pages mapped read-only in host PT; first write traps to userfaultfd handler, handler checks shadowPT, allocates private, copies, updates guest PT to writable private. Since base pages never made writable, invariant holds. ∎

Similarly, Firecracker diff snapshot correctness relies on KVM dirty log being cleared after snapshot: `KVM_CLEAR_DIRTY_LOG` ensures next diff only includes pages dirtied after snapshot, no lost dirty.

### 5.3 Density and Memory Amplification

Define **memory amplification** $A = \frac{\text{Total Host Mem}}{\text{Unique Guest Mem}}$.

- No sharing: $A=1$ per instance.
- SEUSS page sharing: $A = 0.12$ for 10k Node.js functions (shared interpreter + libs 40 MiB, private 3 MiB avg). Measured via `smem` PSS.
- Catalyzer CoW: $A=0.34$ for 1k functions sharing base template (base 80 MiB, private avg 12 MiB).
- Firecracker diff: $A=0.58$ (base mem file shared via `MAP_PRIVATE`, diff private).
- CRIU: $A=0.91$ (little sharing, but no VMM overhead).

**Burst throughput** (Azure trace simulation, 10k new functions / 100ms, 64-core node):

- Cold boot (containers): 12 functions/s, 98% cold starts.
- Firecracker snapshot: 420 functions/s.
- SEUSS: 612 functions/s (51x vs cold) [4].
- Catalyzer: 580 functions/s, p50 2.1ms.

## 6 Limitations

### 6.1 Uniqueness and Security

Cloning breaks **cryptographic uniqueness**. Solutions and gaps:

- `MADV_WIPEONFORK`/`MADV_WIPEONSUSPEND` requires application annotation; legacy code unaware will leak secrets. Brooker et al. [6] shows OpenSSL 1.1.1 does not mark its key buffer, requiring wrapper.
- `VmGenId` — guest must poll or receive interrupt; if function generates UUID before handler runs, collision risk remains. Firecracker exposes via MMIO, but guest kernel must expose to userspace via `sysfs`.
- **Time**: Cloned VMs share `CLOCK_MONOTONIC`; SEUSS resets TSC via `kvm_set_tsc_khz` but `gettimeofday` may go backwards if snapshot older than current time. NTP not feasible in 1ms.

### 6.2 Compatibility and Isolation Spectrum

| Isolation | Substrate | Startup | Compatibility | Density | CVEs (2023) |
|-----------|-----------|---------|---------------|---------|-------------|
| Hardware (KVM) | Firecracker | 4 ms | OCI, any kernel | Medium | 2 (guest->host) |
| Userspace kernel | gVisor/Catalyzer | 0.8-5 ms | ~211 syscalls, 9P FS | High | 1 |
| Library OS | SEUSS | 0.2-2 ms | Rumprun + interpreters only | Very High | 0 (custom) |
| Process | CRIU | 1-8 ms | Linux only, needs `CAP_CHECKPOINT_RESTORE` | Highest | Host kernel vulns |

Choosing substrate is policy: **regulated workloads** require Firecracker/gVisor; **internal bursty Python** may tolerate SEUSS/CRIU for density.

### 6.3 Snapshot Aging and Staleness

Snapshot taken at $T_0$, restored at $T_0 + \Delta$. If $\Delta$ large (hours), snapshot may contain stale CA bundle, timezone DB, or ML model. Catalyzer's **lazy I/O reconnection** mitigates but does not solve semantic staleness. Ant Financial rebuilds templates every 15min via CI/CD [3].

### 6.4 SELinux and Seccomp Restoration

CRIU struggles with **SELinux labeling** — restore must set `security context` before file creation, otherwise labels default to `unlabeled_t` and subsequent `execve` fails. Kubernetes PSP/OPA policies may forbid `CAP_SYS_PTRACE` needed for parasite injection. gVisor's seccomp filter must be re-applied after checkpoint, losing JIT-generated seccomp BPF if not serialized.

## 7 Conclusion

Snapshot-restore has become the *de facto* substrate for millisecond-scale serverless. We unified five lineages — **Firecracker**, **gVisor**, **Catalyzer**, **SEUSS**, and **CRIU** — under a single latency model and demonstrated sub-10ms p50 restore across substrates, with SEUSS achieving 50k cached instances and Catalyzer <1ms in production.

Serverless is no longer about *cold* vs *warm*; it is about *how cold* your snapshot is, and how fast you can *demand-page* your way to warm.
