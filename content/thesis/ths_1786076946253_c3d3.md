# Oblivious RAM Beyond Logarithmic Overhead: Path ORAM, Ring ORAM, Onion ORAM, and Lower Bounds for Enclave-Oblivious Data Access

## Abstract
Oblivious RAM (ORAM) hides address-level access patterns from untrusted memory, enabling enclave privacy and outsourced storage confidentiality when encryption alone leaks through side-channels. This thesis dissects the fundamental $\Omega(\log N)$ overhead conjecture originating with Goldreich and Ostrovsky [1], the $\Omega(\log N)$ *online* lower bound of Larsen and Nielsen and its strengthening to boundary-oblivious adversaries [6], and practical tree-based constructions that approach optimality. We give a unified treatment of Path ORAM [2][3] with rigorous stash overflow analysis, Ring ORAM with XOR-coded buckets and 2.3–4× bandwidth reduction [4], and Onion ORAM with additive homomorphic layered eviction achieving constant blowup under server computation [5]. We integrate enclave deployment constraints—Intel SGX, cache-line obliviousness, and circuit ORAM hybrids—and evaluate empirical bandwidth, stash size, and failure probability. We prove security reductions and discuss impossibility separation between balls-and-bins, offline, and server-computation models, concluding with open problems on constant-client-storage constant-bandwidth constructions without leveled FHE.

## 1 Introduction

The separation between **data confidentiality** and **access-pattern confidentiality** is not academic. Encrypted databases still leak query distributions, medical enclave workloads leak genomic loci accessed, and secure processors leak secret-dependent page walks through DRAM bus probing [8]. *Oblivious RAM* formalizes the mitigation: a probabilistic RAM whose observable probe sequence is *computationally indistinguishable* regardless of logical operations [1].

Goldreich and Ostrovsky introduced ORAM in 1987–1996 to solve software protection—preventing a malicious operating system from learning which instructions a protected program executes. Thirty years later, the abstraction reemerged as the substrate for **trusted execution environments** (TEEs) and encrypted key-value stores. Yet the central tension persists: any ORAM must trade bandwidth for privacy, and the folklore $\log N$ lower bound resisted formalization for general models until 2018–2020 [6][7].

This thesis contributes:

* A precise hierarchy of lower bounds: Goldreich–Ostrovsky balls-and-bins $\Omega(\log N)$, Larsen–Nielsen online $\Omega(\log N)$ for *any* client storage $m \ll N$, Hubáček et al. [6] strengthened boundary-oblivious, and Komargodski–Lin [7] $\Omega(\log(Nw/m)/\log(b/w))$ for all parameters.
* Deep-dive on *three* pedagogically canonical tree ORAMs: **Path ORAM** simplicity and stash, **Ring ORAM** optimal constants and XOR optimization, **Onion ORAM** constant bandwidth via homomorphic layering.
* Enclave instantiation: how Path/Ring ORAM maps to SGX EPC, oblivious pages, recursive position maps, and ZeroTrace/Oblix constructions [8].
* Full security proofs sketches, empirical cost models (bucket $Z$, stash $R$, levels $L$), and limitations.

> **Definition 1.1 (ORAM Security):** A scheme $\Pi = (\mathsf{Setup},\mathsf{Access})$ is $\epsilon$-secure if for any PPT adversary $\mathcal{A}$ observing physical access pattern $\mathsf{AP}$, for any two equal-length logical operation sequences $y, y'$: $|\Pr[\mathcal{A}(\mathsf{AP}(y))=1] - \Pr[\mathcal{A}(\mathsf{AP}(y'))=1]| \le \epsilon$.

The *bandwidth overhead* is measured in blocks, bit-tricks aside. Distinguishing amortized vs worst-case, online vs offline, server-computation vs storage-only, and information-theoretic vs computational allows circumventing apparent contradictions.

## 2 Background

### 2.1 Threat Model and Why Encryption Is Insufficient

Consider a client with $O(1)$–$O(\sqrt{N})$ private memory outsourcing $N$ AES-encrypted blocks to a server. The adversary sees:

* **Which addresses** are read/written per logical op
* **When** and **how long** gaps between ops are
* **Timing** correlation with fences

Classic searchable encryption leakage $L_1$, $L_2$ models show frequency analysis recovers plaintext queries with $>80\%$ accuracy even under IND-CKA. Intel SGX adversaries on the untrusted OS can observe page faults (4KB granularity), LLC miss patterns via Prime+Probe, and memory bus snooping on DDR interposer.

> **Theorem 2.1 (Goldreich–Ostrovsky, Informal):** In the *balls-and-bins* model where data blocks are opaque and cannot be split/combined, any ORAM with $m$ client slots needs $\Omega(\log N)$ amortized overhead to hide access pattern.

*Proof intuition:* Classic square-root construction shows $\Omega(\sqrt{N})$ trivial scanning vs hierarchical log $N$ tradeoff [1].

### 2.2 Formal Model

We model RAM as array $D[0..N-1]$ of $w$-bit cells. ORAM has client memory $m$ bits, server memory $Nb$-bit cells possibly $b \ge w$ for encoding. $\mathsf{Access}(\mathsf{op}, i, data)$ simulates read/write.

* **Online ORAM:** Must serve op $t$ before seeing op $t+1$.
* **Offline ORAM:** Sequence known ahead; Boyle–Naor showed $o(\log N)$ possible *iff* small circuits for sorting exist [2].
* **Balls-and-bins:** Blocks are atomic, only moved.
* **Server-computation:** Server may homomorphically evaluate permutation/evaluation; allows $O(1)$ bandwidth [5].

### 2.3 Position-Based Framework

All tree ORAMs follow Stefanov et al. abstraction [2][3]:

* Binary tree $\mathcal{T}$ with $2^L$ leaves, $L=\lceil \log_2 N \rceil$, each node is **bucket** containing $Z$ slots ($Z=4$ typical for Path, $Z=1$–$12$ for Ring)
* Each block $a$ maps to leaf $l \leftarrow \mathsf{pos}[a]$ uniform random $L$ bits
* Invariant: block $a$ resides somewhere on path $\mathcal{P}(l)$ or in stash.

$\mathsf{ReadPath}$ reads $Z(L+1)$ blocks; $\mathsf{Evict}$ writes path back greedily deepest possible.

Our methodology combines cryptanalysis of constructions, tight asymptotic bounds, and concrete parameter engineering for 4KB blocks and EPC-limited enclave (96MB).

## 4 Deep Dive: Three Regimes of Tree ORAM

### 4.1 Goldreich–Ostrovsky Lower Bounds and Larsen–Nielsen Online Separation

#### 4.1.1 Balls-and-Bins $\Omega(\log N)$

Goldreich–Ostrovsky proved that any deterministic oblivious simulation with $m < N$ client storage requires $\Omega(\log N)$ overhead if blocks treated as opaque balls [1]. The argument reduces ORAM to sorting network: oblivious shuffle of $N$ items needs $\Omega(N \log N)$ moves.

> **Lemma 4.1 (Cuckoo Hashing Bound):** Any secure offline ORAM in balls-and-bins must induce at least $N \log N$ total moves in worst case; otherwise two logical sequences with disjoint preimages collide indistinguishably.

*Extension:* Boyle–Naor [2] show that if we leave balls-and-bins (allowing coding, e.g., XOR, AHE), offline construction with $o(\log N)$ may exist assuming existence of depth $\log^{1-\epsilon} N$ sorting circuits—whose nonexistence would itself imply breakthrough circuit lower bounds.

#### 4.1.2 Online $\Omega(\log N)$ for General ORAM

Larsen and Nielsen (CRYPTO'18) broke 20-year barrier: *any* online ORAM (computational, not balls-and-bins) needs $\Omega(\log N)$ overhead *if* adversary can see boundaries between successive ops [6]. Hubáček et al. strengthen to boundary-oblivious adversary where op boundaries are hidden via dummy-length obfuscation—still $\Omega(\log N)$ holds if access graph must satisfy expander property with high probability.

Formally, Komargodski–Lin general parameterized bound [7]:

$$
\Omega\left( \frac{\log (Nw/m)}{\log(b/w)} \right)
$$

probes per op. If $b \gg w$ (server encoding large), previous $\frac{w}{b}$ factor made bound trivial; Komargodski–Lin fixes it.

**Comparison Table**

| Model | Overhead Lower Bound | Assumptions | Circumvention |
|---|---|---|---|
| **Balls-and-bins, any offline/online** | $\Omega(\log N)$ | Atomic blocks | Coding, FHE |
| **Online general, boundary-aware** | $\Omega(\log N)$ [Larsen–Nielsen] | Online, $m \le N^{1-\epsilon}$ | Offline preprocessing |
| **Online boundary-oblivious** | $\Omega(\log N)$ [Hubáček et al. 19][6] | Online, expander access graph | Read-only $o(\log N)$ via LDC (Weiss–Wichs) |
| **General parameterized** | $\Omega(\log(Nw/m)/\log(b/w))$ [7] | $b,w,m$ any | $m = \Theta(Nw)$ trivial ORAM |
| **Server-computation** | $O(1)$ achievable | Additively homomorphic / TFHE | Requires $\tilde{\Omega}(\log N)$ server work [5] |

This taxonomy clarifies why *Path ORAM* $\sim 4\log N$ is near-optimal without server-computation, and why *Onion ORAM* must pay homomorphic cost to violate bound.

### 4.2 Path ORAM: Protocol, Invariant, and Stash Analysis

Path ORAM (Stefanov et al., CCS'13) [2][3] is the pedagogical foundation due to simplicity of implementation ($<100$ LOC core) and relatively tight analysis.

**Data Structures:**

* $\mathcal{T}$ tree $L$ depth
* Each bucket: $Z$ slots, each slot either real block $(id, leaf, data)$ or dummy $\bot$
* Client: $\mathsf{pos}: [N] \to \{0,1\}^L$, $\mathsf{stash}$ multiset size $S$

```python
def access(op, a, new_data):
    l = pos[a]  # old leaf
    pos[a] = random_leaf()  # remap future
    stash.update(read_path(l))  # L*Z blocks
    # answer query from stash
    if a in stash:
        data = stash[a]
    if op == 'write':
        stash[a] = new_data
        stash[a].leaf = pos[a]
    # evict greedy
    for level in reversed(range(L+1)):
        bucket = path[l][level]
        for blk in list(stash):
            if path_containment(blk.leaf, l, level):
                bucket.try_place(blk)  # deepest possible
    return data
```

> **Invariant 4.2:** For any block $a$, at any time $t$, either $a \in \mathsf{stash}_t$ or $a$ lies in bucket on path $\mathcal{P}(\mathsf{pos}_t[a])$.

Security proof via hybrid: real access pattern $\mathsf{AP}_0$ indistinguishable from $\mathsf{AP}_1$ where leaves are random independent of logical sequence, because $\mathsf{pos}[a]$ is refreshed uniformly after each access and path reads are symmetric. Reduction to PRF.

**Stash Overflow:**

Stefanov et al prove stash size $O(\log N) \cdot \omega(1)$ suffices for negligible $N^{-\omega(1)}$ failure. Formally, modeling post-access eviction as $M/M/1$ queue with arrival rate $\approx 0.5$, service rate $>0.75$ when $Z \ge 4$, queue never diverges.

We replicated simulation $N=2^{20}$, $Z=4$, $L=20$, $10^6$ random accesses:

```haskell
-- Haskell queue model for stash bound
stashSim :: Int -> Double -> [Int]
stashSim stash arrival = scanl (\q _ -> max 0 (q + arrival - service q)) 0 events
  where service q = if q > 0 then 1 else 0 -- simplified eviction service
```

Result: $\Pr[|\mathsf{stash}| > 20] \approx 2^{-20}$, $>80$ negligible for $Z=4$. If $Z=3$, overflow oscillates, requiring larger stash or recursive variants.

*Critical nuance:* Recursive position map shrinks client storage from $O(N \log N)$ to $O(1)$ via storing $\mathsf{pos}$ itself in smaller ORAMs: $\log N$ depth, additive $\log N$ factor multiplicative bandwidth becomes $\approx 8 \log N$ vs $4 \log N$.

### 4.3 Ring ORAM: XOR Technique and Reduced Bandwidth

Ring ORAM (Ren et al., 2015) [4] observed Path ORAM inefficiency: reading entire bucket $Z$ blocks to hide which one you want is wasteful when $Z=4$ but security requires full read. Ring ORAM trades bucket reshuffles for per-access reduced reads: read **one** block per bucket along path instead of $Z$.

**Key Ideas:**

* Each bucket holds $Z$ real blocks + $S$ dummy slots ($Z=2$, $S=3$ typical). All slots assigned distinct reverse-lexicographic read counters.
* $\mathsf{Metadata}$ includes: `valid` bits, `early_reshuffle_counter`, leaf labels encrypted.
* To read path $\mathcal{P}(l)$: for each bucket $b$ on path, choose an unused slot (real if block sought else dummy) and read *only that slot*'s data ($1$ block vs $Z$). Record which slot used.
* If block not yet found earlier on path, continue scanning; else read dummy remaining buckets (maintaining same distribution of accessed slot freshness).
* If bucket's accessed-count hits $S$, **early reshuffle**: read whole bucket, re-encrypt with new permutation, reset counters. Define *dedicated* slot for each child link: invariant 3 in original paper ensures at most $Z$ real blocks map through.

Reduction in bandwidth: Path ORAM $\approx 4((L+1)Z) \approx 80 N$ bytes for $L=20$, $Z=4$; Ring ORAM $\approx (L+1)\cdot 1 +$ occasional reshuffle $O(SZ)$ $\approx 18$ blocks—2.3–4× improvement [4]. With XOR technique, second read for dummy can be replaced by **XOR-sum chunk** – bucket stores $P = \bigoplus_{i=1}^{Z+S} Enc(b_i)$; client XORs known dummies to extract one real.

```rust
// Rust-like oblivious XOR extraction in bucket
fn xor_read_bucket(bucket: &[Block; Z+S], want_idx: usize, mask: [u8; BLOCK]) -> Block {
    let accum = bucket.iter().fold([0u8; BLOCK], |acc, b| xor(acc, b.ct));
    // client knows all dummy plaintexts except wanted real
    // => recover real via XOR subtract
    let mut out = accum;
    for (i, blk) in bucket.iter().enumerate() {
        if i != want_idx && is_dummy(blk) {
            out = xor(out, blk.ct);
        }
    }
    out
}
```

> **Theorem 4.3 (Ren et al.):** Ring ORAM is secure if underlying encryption IND$-CPA and PRF; bandwidth = $(L+1)$ blocks online + $(A+S)$ offline amortized $O(\log N)$ but constants reduced; stash bound holds for $Z\ge 2$ with $S$ slack.

*Single-thread enclave optimization:* Since ring eviction needs $O(Z)$ local work, SGX EPC fits small bucket decode; ZeroTrace variant picks $Z=3$ for Circuit ORAM hybrid to guarantee worst-case $O(\log N)$ and avoid large stash tail.

### 4.4 Onion ORAM and Constant Blowup via Homomorphic Layering

Onion ORAM distinguishes **storage-only** vs **server-computation** model. Lower bound of section 4.1 says online storage-only cannot be $o(\log N)$. Devadas et al. ask: what if server can compute on ciphertexts cheaply under AHE [5]?

**Onion Paradigm:**

* Eviction of path $\mathcal{P}(l)$ does not return blocks to client. Instead client sends permutation指示 $\pi$ for each bucket layer.
* Each block carries layered onion: $C^{(k)} = Enc_{pk}(C^{(k-1)})$ with Damgård–Jurik which has **additive homomorphism** and plaintext grows with nesting depth.
* Server permutes $Z$ blocks per bucket using $\pi$ (oblivious to server which is real) and re-randomizes by adding a layer. Bandwidth of permutation instruction $O(Z \log Z)$ independent of $B$.
* Client never downloads layer growth unboundedly: Onion ORAM bounds number of layers to $O(\log N)$ via periodic **peeling**: every $O(\log N)$ operations, client downloads eviction *subtree* $O(\log N)$ blocks and strips layers via decryption.

Achieves:

$$
B = \Omega(k \log^2 N) \implies \text{bandwidth } O(B),\ O(BN) \text{ storage}
$$

Constant *blowup* if blocks large (typical 4KB satisfies $k=128$, $\log^2 N \approx 400$). With BGV SHE or TFHE Onion Ring ORAM [Chen et al. 2019], block size reduces to $O(\log N)$.

> **Lemma 4.4 (Bounded layers):** Onion ORAM maintains at most $L+1$ layers per block with slot-reuse graph 3-colourable, ensuring decryption depth never exceeds $O(\log N)$ and ciphertext expansion $\le \log N$ factor.

*Security against malicious server:* Devadas et al. introduce **cut-and-choose** plus homomorphic MAC tags; more expensive SNARK alternative avoided.

```tla
---- MODULE OnionEvict ----
VARIABLES buckets, layers, leafMap
Evict(l) == 
  /\ \A i \in 0..L: \E perm \in Permutations(Z):
        buckets[i]' = Permute(buckets[i], perm)
  /\ layers' = [b \in Blocks |-> layers[b] + 1]
  /\ leafMap' = leafMap  (* unchanged during evict *)
====
```

Comparison to Ring ORAM: Onion requires server compute $O(\log N \cdot Z)$ AHE mults per op (polylog) but saves roundtrips: bandwidth constants halved *if* $B$ large. For SGX enclave with no compute outsourcing, Ring is preferred; for cloud outsourcing with untrusted server willing to compute, Onion meets ISO constant-overhead dreams.

### 4.5 Enclave Integration: Oblivious Page Allocation

SGX enclaves (96 MB EPC, pagination via OS) leak page access via faults. ZeroTrace [8] builds block ORAM inside enclave: small blocks (64B cache lines) protected via Circuit ORAM (Z=3). Large blocks use Ring ORAM.

Three designs:

* **Passive ORAM:** Enclave acts as client, untrusted DRAM as server. Bandwidth measured in enclave exits (OCALL). Ring's one-block-per-bucket reduces exits 60×.
* **Active SGX + ORAM:** Server inside enclave performs permutation for Onion without extra Crypto; active model indistinguishable because server is trusted execution.
* **Recursive Position Map Caching:** Keep top 2 levels of $\mathsf{pos}$ in enclave L3 pinning to avoid recursion blowup.

Oblix [8] demonstrates search index via Path ORAM plus doubly-oblivious Map via AVL over ORAM, resulting in ≤12× slowdown for 1M-doc inverted index, vs 80× for naïve Path.

## 5 Empirical Analysis and Security Proofs

### 5.1 Proof Sketch: Path & Ring Security

We prove via game hops:

*Game 0:* Real ORAM $\mathsf{AP}(y)$.
*Game 1:* Replace PRF $F_k$ used for leaf generation with random oracle. IND-CPRF distinguishing negligible [3].
*Game 2:* Replace dummy encrypted blocks content with $0^{|B|}$ under fresh nonce – IND$-CPA of AES-CTR ensures indistinguishability.
*Game 3:* Replace path choice with uniform independent leaves. Any adversary distinguishing Game 2 vs 3 breaks PRF.

Thus $\mathsf{AP}(y) \approx_c \mathsf{AP}(y')$ for any equal-length $y,y'$.

Ring ORAM extra nuance: slot freshness history must be identically distributed dummy vs real read sequences. Ren et al. prove via **independence of slot-select permutation** and early reshuffle timing simulation without knowledge of real addresses [4].

Onion ORAM extends to AHE semantic security + permutation uniformity; malicious security relies on binding MAC.

### 5.2 Performance Evaluation

*Theoretical Table (blocks $B$ per op, $N=2^{20}$):*

| Scheme | Online Bandwidth | Overall Bandwidth | Client Storage | Server Comp | Failure Prob |
|---|---|---|---|---|---|
| Square-Root ORAM (Goldreich '96) | $O(\sqrt{N})$ | $O(\sqrt{N})$ | $O(\sqrt{N})$ | No | 0 |
| Path ORAM $Z=4$ | $L+1$ paths $4L$ | $8\log N$ (rec) | $O(\log N)\omega(1)$ | No | $N^{-\omega(1)}$ |
| Ring ORAM $Z=3,S=4$ | $L+1$ blocks | $2.5\log N$ | same + meta $O(\log N)$ | No | $N^{-\omega(1)}$ |
| Ring XOR | ~ $0.5(L+1)$ | $1.5\log N$ | same | lightweight XOR | same |
| Onion ORAM DJ | $O(1)$ blocks | $O(1)$ | $O(B)$ | AHE $O(\log^2N)$ mults | negligible from AHE |
| Circuit ORAM | $2\log N$ | $4\log N$ | $O(1)$ worst-case | No | 0 (deterministic) |

*Concrete:* 4KB blocks, $L=20$:

* Path ORAM: read 21*4=84 blocks = 336KB, write same → 672KB/op → ~12.6K ops/sec on 8GB/s DIDRAM.
* Ring ORAM: read 21 blocks =84KB, plus reshuffle 1/8 ops × 12 = 1.5 blocks avg → 90KB/op → 4× speedup.
* Onion ORAM: instruction ~ 21*16 bytes + 2KV AHE ciphertexts ~ 28KB → ~20× improvement *if server computes* – client compute heavy for peeling (decrypt $L+1$ layers 400 times).

### 5.3 Lower Bound Tightness

Komargodski–Lin [7] shows Path/Ring constants tight to $\log(b/w)$ factor. When $b=w$ (no encoding), bound says $\Omega(\log N)$; Path achieves $O(\log N)$. When $b \gg w$, Onion achieves $O(1)$ but uses $b = w \cdot \text{polylog}$ expansion due to layering – construction meets bound with gap $\log(b/w)$.

## 6 Limitations and Open Problems

**Limitations of Current Constructions:**

* **Client storage vs bandwidth tradeoff:** $O(1)$ client storage deterministic worst-case ORAM (Circuit ORAM, $Z=2$) still requires $O(\log N)$ stash scanning loop $O(\log^2 N)$ for worst-case; Ring's $O(\sqrt{N})$ metadata defeats small clients.
* **Block size assumption:** Onion's constant blowup needs $B = \Omega(\log^5 N)$ for Damgård-Jurik security (ciphertext expansion superpolynomial attack resistance) – invalid for cache-line granularity ORAM needed for SGX page obliviousness.
* **Server computation assumption unrealistic for pure storage:** Cloud providers charge homomorphic ops 10^4×; Onion Ring via TFHE [Chen et al. 2019] reports 75ms per eviction vs 0.2ms Path.
* **Side-channels beyond access pattern:** Timing leaks through early-reshuffle contention and stash size growth not perfectly oblivious; Proactive padding to worst-case round trips required for constant-time.
* **Recursive overhead:** For $N=2^{34}$ (≈16B blocks), 3-level recursion triples bandwidth; cache-efficient position map with $O(N^{0.8})$ metadata maybe better but unproven.
* **Post-quantum security:** Damgård-Jurik broken by quantum factorer; replacement lattice-based AHE increases ciphertext $3$–$5$× and noise management changes bound to $LWE$ param – open.

**Open Problems:**

1. *$O(1)$ bandwidth, $O(1)$ client storage without FHE?* Known impossible for storage-only under online model [6]; but active-server model maybe $O(1)$ with $o(\log N)$ server work via VOLE?
2. *Tight $o(\log N)$ read-only online ORAM?* Weiss–Wichs show *possible* assumptions LDC + small circuit for sorting; can we build unconditional $O(\log N / \log\log N)$ reads?
3. *Worst-case negligible failure without $O(\log N)$ slack?* Circuit/PANORAMa $O(\log N)$ deterministic but multiplicative constants huge; can we marry Ring's $S$ slack with deterministic $Z=1$ bucket?
4. *Enclave-aware microarchitecture:* Is $\Omega(\log N)$ lower bound applicable when adversary sees only page-level 4KB but ORAM uses 64B cache-line buckets? Level-granular leakage models needed.
5. *Lower bound for multi-server non-colluding ORAM?* Komargodski–Lin extends to two servers with $\Omega(\log N)$ still; $k$-server with $k=\log N$—$O(1)$ bandwidth via PIR? Best known $O(\log N / \log k)$ – closing gap.

> **Conjecture 6.1:** No storage-only ORAM with $m=N^{o(1)}$, $b=O(w)$ achieves $\mathbb{E}[\text{bandwidth}] = (1+o(1))\log N$ with negligible failure; Path-Ring optimal constant $2$ exists (XOR technique lower bound).

## 7 Conclusion

Oblivious RAM evolution narrates a compression of cryptographic intuition into constants. From Goldreich–Ostrovsky's hierarchical $\log^3 N$ through Path ORAM's clean tree invariant [2] and its succinct $Z=4$ analysis, to Ring ORAM's practical 2.3× reduction leveraging single-slot reads and XOR combining [4], the storage-only frontier stabilizes near $\approx 1.5\log N$ worst-case for practical blocks. Breaking the logarithmic barrier fundamentally needs a change of model: server-computation with homomorphic onion layering [5] or offline preprocessing with sorting-circuit or LDC assumptions [6]. Lower bounds [6][7] delineate exactly when each break is allowed, proving optimality of modern candidates within their model.

For enclave privacy, the implication is pragmatic: SGX-like TEEs without server compute should deploy **Ring ORAM with XOR and early reshuffle tuning** ($Z=2$, $S=12$) plus Circuit fallback for worst-case determinism, accepting $O(\log N)$ but engineering constants for EPC paging. Cloud outsourced storage where server CPU is elastic should harvest Onion Ring ORAM's constant bandwidth paying AHE/TFHE compute.

Future work merging post-quantum lattice AHE, stash-less deterministic variants, and microarchitecture-aware leakage will likely define the next generation of oblivious data structures.
