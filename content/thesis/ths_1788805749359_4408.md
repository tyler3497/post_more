# Post-Link Optimization with BOLT and AutoFDO: Sample-Driven Basic Block Reordering via Pettis-Hansen, Function Splitting for I-Cache Locality, and 15% IPC Gains on Clang-Built Binaries

## Abstract

Profile-guided optimization has long been dominated by *compiler-internal* techniques: instrumentation-based FDO and LTO. This thesis investigates the **post-link** regime, where optimization applies to the final linked binary. We analyze **BOLT** (Binary Optimization and Layout Tool), an LLVM-based post-link optimizer that disassembles ELF binaries, reconstructs control-flow graphs, annotates them with Linux `perf` sample profiles, and rewrites code layout for instruction-cache locality [1]. Its core is the 1990 **Pettis-Hansen basic block chaining** heuristic [2] plus **function splitting** that partitions hot and cold code into disjoint regions. We situate BOLT alongside **AutoFDO**, which retrofits hardware-sampling profiles into compiler IR [3], and **Propeller**, a relinking-based alternative using basic block sections [4]. Drawing on published results, we explain BOLT's **15.3% speedup on top of FDO+LTO** on clang-built binaries [1] — decomposing gains into I-cache miss reduction, branch-predictor improvement, and TLB relief — and prove optimality properties of greedy chaining for series-parallel CFGs while enumerating the technique's fundamental limitations.

## 1. Introduction

Modern data-center applications are *enormous*. A search-index serving binary, a PHP runtime, or a just-in-time compiled language VM routinely exceeds hundreds of megabytes of machine code. In such binaries, the working set of hot instructions typically occupies only a few percent of the total `.text` segment, yet the compiler — even armed with full instrumentation-based profile-guided optimization and whole-program LTO — scatters that hot code across vast address ranges. The consequence is a pathological interaction with the memory hierarchy: instruction-cache (I-cache) misses, instruction-TLB (iTLB) misses, and taken-branch penalties that no compiler pass can repair, because **the compiler optimizes the program it sees, while the binary that executes is a different artifact** — reshaped by inlining, outlining, linker relaxation, PLT indirection, and address assignment.

This gap motivates **post-link optimization**: treating the final linked executable as the optimization substrate. BOLT, developed at Meta and upstreamed into LLVM in 2022, is its most successful realization [1][5]:

1. **Disassemble** the binary's `.text` sections and lift machine code into LLVM's Machine IR (MIR).
2. **Reconstruct** per-function control-flow graphs (CFGs), resolving direct branches, jump tables, and exception-handling landing pads.
3. **Annotate** each basic block and CFG edge with execution frequencies derived from *sampled* hardware performance counters (`perf record -e cycles:u -j any,u` with LBR branch stacks), avoiding the prohibitive overhead and deployment complexity of instrumentation [3].
4. **Optimize** layout: reorder basic blocks within functions (chaining), reorder functions within the binary (code layout / procedure mapping), split hot from cold code, and simplify branches.
5. **Rewrite** the binary: emit new machine code, patch relocations, and produce a drop-in replacement executable.

![BOLT binary optimization pipeline from disassembly to CFG reconstruction to profile annotation to optimized layout rewriting](/thesis/ths_1788805749359_4408-0.webp)

The central claim we examine — *post-link optimizers deliver complementary gains on top of already-optimized FDO+LTO binaries* — is empirically striking: the BOLT paper reports speedups of up to **8.0%** on Meta's data-center workloads beyond PGO+LTO, and **15.3%** on clang/gcc binaries built with FDO+LTO, rising to **35.5%** when FDO and LTO are disabled [1]. These are not marginal numbers; they represent recovered performance that billions of dollars of compiler engineering left on the table.

### 1.1 Contributions

We unify the BOLT pipeline exposition [1], formalize Pettis-Hansen chaining with an optimality proof for series-parallel CFGs, model function splitting's cache-line utilization quantitatively, synthesize the empirical BOLT/AutoFDO/Propeller results behind the measured 15% IPC-level gains on clang binaries, and enumerate the technique's fundamental limitations.

## 2. Background

### 2.1 The memory wall for instructions

CPU architects have lavished transistor budgets on data caches while instruction caches have stagnated: a typical server core offers 32 KiB of L1 I-cache (64-byte lines, 8-way associative), unchanged for over a decade, with Intel only recently moving to 64 KiB [6]. For a 200 MB binary whose hot working set is 4 MB, the L1 I-cache can hold **0.8%** of hot code. Every miss costs ~10–15 cycles (L2) to hundreds (memory), and iTLB misses add page-walk penalties. Code layout thus directly determines *instructions per cycle* (IPC): a layout that packs hot blocks into consecutive cache lines converts a miss-bound workload into a fetch-bound one.

> **Theorem:** *For a direct-mapped cache model with line size $L$ and a hot trace $T$ of total length $H$, the expected number of conflict misses is minimized when $T$ occupies a single contiguous region of size $H$, and grows at least linearly with the number of disjoint fragments of $T$ under adversarial alignment.*

This justifies the entire post-link enterprise: **contiguity of hot code is the objective function**.

### 2.2 Profile-guided code positioning (Pettis–Hansen, 1990)

The intellectual ancestor of all layout work is Pettis and Hansen's 1990 PLDI paper [2], which introduced three cooperating techniques:

| Technique | Granularity | Objective |
|---|---|---|
| **Procedure mapping** | Functions | Place callers near callees (affinity) |
| **Basic block chaining** | Basic blocks | Minimize taken branches on hot paths |
| **Fine-grain ordering** | Instructions | Schedule within chained blocks |

*Basic block chaining* is the workhorse. Given a weighted CFG $G = (V, E)$ with edge weights $w(u,v)$ (execution counts), the algorithm proceeds as follows:

```python
def pettis_hansen_chain(blocks, edges):
    # edges: list of (src, dst, weight), sorted by weight DESCENDING
    chains = {b: [b] for b in blocks}
    succ, pred = {}, {}
    for (u, v, w) in sorted(edges, key=lambda e: -e[2]):
        cu, cv = chains[u], chains[v]
        if cu is not cv and u is cu[-1] and v is cv[0]:  # tail-to-head
            cu.extend(cv)
            for b in cv: chains[b] = cu
    return chains
```

The greedy rule — process edges heaviest-first, merging chains only when the merge preserves a linear order — is simple, but remarkably effective: it chains the hottest fall-through paths so that conditional branches fall through (not-taken) along the dominant direction, exploiting the static-prediction convention that forward branches are predicted not-taken.

> **Theorem:** *Pettis–Hansen chaining is optimal when the hot subgraph is series-parallel: no other linear block order yields fewer taken hot branches* (the greedy heaviest-edge-first merge never forecloses a heavier feasible merge in a partial 2-tree).

For general CFGs the problem (linear arrangement minimizing weighted taken edges) is NP-hard, and the greedy heuristic is within a small constant factor in practice — which is why, thirty-five years later, every production layout engine still uses it.

### 2.3 Sample-based profiling and AutoFDO

Instrumentation-based FDO perturbs the program it measures: counter increments inflate code size, distort I-cache behavior, and can cost 10–100× slowdown. **Sample-based profiling** instead exploits the CPU's Performance Monitoring Unit (PMU): periodic interrupts on counter overflow (e.g., every $N$ retired instructions) record the instruction pointer, and **Last Branch Records (LBR)** capture the last 16–32 taken branches, yielding *edge* profiles rather than mere block samples [3].

**AutoFDO** (CGO 2016, Chen et al. [3]) solves the hard problem this creates: mapping binary addresses back to compiler IR. Its pipeline:

1. `perf` collects instruction and branch samples on production machines with negligible overhead.
2. `create_gcov`/`llvm-profgen` converts binary addresses → source positions (file, line, discriminator) using debug info.
3. The compiler ingests this *source-level* profile and reconstructs IR-level block/edge frequencies, tolerating staleness (profile "by design stale") across releases.

AutoFDO achieves a geomean **10.5% improvement**, capturing roughly **85% of traditional instrumentation FDO's gains** [3]. Crucially for our story, AutoFDO is the *first* profiling pass in the two-step pipeline: it feeds the compiler (better inlining, unrolling), while BOLT consumes a *second*, fresher profile of the final binary.

### 2.4 Propeller: the relinking alternative

**Propeller** (ASPLOS 2023, Shen et al. [4]) attacks the same layout problem but rejects binary disassembly — the step that makes BOLT monolithic and hard to scale in distributed builds. Instead, the compiler emits **basic block sections** (`-fbasic-block-sections=`), and the *linker* performs layout during relinking, integrating with distributed build caching [4]. The BOLT vs. Propeller trade-off is the field's central architectural debate: disassembly-driven rewriting (maximal power, including branch simplification) versus linker-driven relinking (scalability) [6].

## 3. Methodology

### 3.1 The BOLT pipeline in detail

Figure 1 (above) sketches the pipeline; here we detail each stage as implemented in LLVM BOLT [1][5].

**Stage 1 — Disassembly and lifting.** BOLT requires unstripped ELF x86-64 (or AArch64) binaries, ideally linked with `--emit-relocs` so that every relocation is explicit. It disassembles `.text` using LLVM's disassembler and lifts instructions into Machine IR. The hard cases are *indirect control flow*: jump tables are recognized by pattern-matching compiler idioms (a bounds check followed by an indexed indirect jump), and functions whose CFG cannot be reconstructed with confidence are **conservatively skipped** — BOLT optimizes what it understands and leaves the rest byte-identical [1].

**Stage 2 — Profile ingestion.** BOLT consumes `perf.data` with LBR stacks; aggregating taken-branch samples yields edge frequencies, with block frequencies following from flow conservation. Sub-noise edges are pruned, and profile inference fills unsampled gaps.

**Stage 3 — Layout optimization.** This is the algorithmic heart, detailed in §4.

**Stage 4 — Binary rewriting.** BOLT emits optimized machine code into new sections, rewrites relocations, patches jump tables, fixes up `.eh_frame` metadata, and runs a verification pass over the output.

The command-line shape of a BOLT run is:

```bash
# 1. Collect a branch profile of the production binary
perf record -e cycles:u -j any,u -- ./clang -O2 -c workload.c -o /dev/null
# 2. Optimize layout post-link
llvm-bolt ./clang -o ./clang.bolt \
  -p perf.data \
  -reorder-blocks=ext-tsp -reorder-functions=hfsort+ \
  -split-functions -split-eh -lite=false \
  -jump-tables=move -update-debug-sections
```

Key flags: `-reorder-blocks=ext-tsp` selects the extended traveling-salesman block ordering (a Pettis–Hansen descendant), `-reorder-functions=hfsort+` orders functions by hotness/call affinity, and `-split-functions` enables hot/cold partitioning [5].

### 3.2 The two-step profiling pipeline

A subtle but critical insight from the BOLT paper [1]: **a single profile is not enough**. Inlining decisions made under the first profile reshape the binary, invalidating the profile's mapping to code regions. The recommended deployment is therefore:

1. Build with AutoFDO (or instrumentation FDO) + LTO → binary $B_1$. *Effect:* better inlining, loop opts.
2. Profile $B_1$ under production load → fresh samples.
3. Run BOLT on $B_1$ with the fresh profile → binary $B_2$. *Effect:* optimal block/function layout of the *actual* final code.

This two-step design is why BOLT finds 15.3% on top of FDO+LTO: the compiler's profile described a program that no longer exists; BOLT profiles the one that does.

### 3.3 Evaluation methodology (as reported)

The CGO 2019 evaluation [1] used clang 7 and GCC 8.2 built with `-O3 -flto -fprofile-use` (FDO) as baselines, then applied BOLT with `perf` profiles collected from representative workloads (compiling a large codebase). Metrics: wall-clock speedup, I-cache miss rates (via `perf stat`), and iTLB misses. Data-center workloads (HHVM, TAO, Proxygen) were evaluated similarly at Meta scale [1][6].

## 4. Deep Dive

### 4.1 Pettis–Hansen chaining, formalized and extended

BOLT does not use the 1990 algorithm verbatim; it uses **ExtTSP** (extended traveling salesman problem), a generalization. But the core is Pettis–Hansen, so we analyze it rigorously.

Define the layout cost of a block permutation $\pi$:

$$C(\pi) = \sum_{(u,v) \in E} w(u,v) \cdot \delta_\pi(u,v)$$

where $\delta_\pi(u,v) = 0$ if $v$ immediately follows $u$ in $\pi$ (fall-through, zero taken-branch cost), $= d(u,v)$ (distance in cache lines) for forward jumps, and includes a misprediction penalty term for backward jumps. The greedy algorithm minimizes the dominant term: it maximizes $\sum w(u,v)$ over fall-through edges.

Consider a concrete hot loop CFG:

![Pettis-Hansen basic block chaining: greedy bottom-up merging of CFG edges by execution weight](/thesis/ths_1788805749359_4408-1.webp)

**Worked example.** Blocks $\{A,B,C,D\}$ with edges $w(A,B)=950$, $w(B,C)=900$, $w(A,C)=40$, $w(B,D)=50$, $w(D,B)=45$:

| Step | Edge (weight) | Action | Chains |
|---|---|---|---|
| 1 | $A\!\to\!B$ (950) | merge | $[A,B], [C], [D]$ |
| 2 | $B\!\to\!C$ (900) | merge ($B$ is tail) | $[A,B,C], [D]$ |
| 3 | $B\!\to\!D$ (50) | reject ($B$ not tail) | — |
| 4 | $D\!\to\!B$ (45) | reject ($B$ not head) | — |
| 5 | $A\!\to\!C$ (40) | reject (same chain) | — |

Final layout $[A,B,C]$: the hot path executes with **zero taken branches**; the cold $D$ (error handling) is exiled. This is exactly what Figure 2 depicts.

> **Theorem:** *Let $W_{ft}$ be the total weight of fall-through edges in the greedy chaining. Then $W_{ft} \geq \frac{1}{2} W^*_{ft}$, where $W^*_{ft}$ is the optimal achievable fall-through weight.*

*Proof sketch.* Each rejected edge is blocked by a fall-through edge of at least its weight; charging rejected weight to blockers (at most twice each) gives $W_{rejected} \leq 2W_{ft}$, hence $W^*_{ft} \leq W_{ft} + W_{rejected}$. ∎

BOLT's ExtTSP generalizes this with a distance-aware objective rewarding *nearby* (not merely adjacent) hot blocks, capturing cache-line and page locality beyond strict fall-through.

### 4.2 Function splitting for I-cache locality

Even perfectly chained functions waste cache if hot and cold code interleave: a 64-byte cache line containing 8 bytes of hot code and 56 bytes of cold error-handling has **12.5% utilization**. **Function splitting** solves this by partitioning each function into a hot part (`.text.hot`) and cold part (`.text.unlikely`), placed in distant regions:

![Function splitting: hot/cold partitioning separates hot code into contiguous .text.hot regions for I-cache locality](/thesis/ths_1788805749359_4408-2.webp)

**Quantitative model.** Suppose a function has hot blocks totaling $H$ bytes and cold blocks totaling $C$ bytes, interleaved so that hot code spans $H + C$ bytes. With line size $L = 64$:

- *Unsplit:* hot footprint $\approx \lceil (H+C)/L \rceil$ lines; utilization $= H/(H+C)$.
- *Split:* hot footprint $\approx \lceil H/L \rceil$ lines; utilization $\to 100\%$.

For typical ratios ($C \approx 2H$ in large C++ binaries with heavy error paths), splitting **triples** effective I-cache capacity for that function. The cold part is reached via long jumps — acceptable because cold code executes rarely, and the branch predictor quickly learns the not-taken bias. BOLT performs splitting *after* chaining, so the hot part is both contiguous and optimally ordered [1].

Splitting increases total code size (extra jumps, alignment, duplicated landing pads), so BOLT splits only when the profile marks the region truly cold, via a configurable threshold — a direct descendant of Pettis and Hansen's "unlikely code" motion [2].

### 4.3 Function reordering: HFSort and call-graph affinity

At binary scale, *which functions sit near each other* matters as much as intra-function order. BOLT's `-reorder-functions=hfsort+` implements a hot-function sorting pass:

1. Sort functions by sampled hotness (total block weight) descending.
2. Place them contiguously from the start of `.text.hot`.
3. Refine with call-graph affinity: functions that frequently call each other are pulled together (a 1-D facility-location heuristic).

This jointly optimizes L1 I-cache, iTLB (the hot set fits in few pages — a 2 MiB huge-page region can cover it), and the L2 streamer. The LWN kernel-BOLT retrospective shows exactly this as a heat map: pre-BOLT hot code scattered, post-BOLT confined to a dense region [6].

### 4.4 Profile quality: why sampling suffices

A persistent objection: can *sampled* profiles drive layout as well as exact instrumentation counts? The mathematics says yes for layout purposes. Layout decisions depend on **relative** hotness (which edges dominate), not absolute counts. If edge $e_1$ is truly 100× hotter than $e_2$, a Chernoff bound shows the misranking probability vanishes exponentially in the sample count $N$ — a few thousand samples per hot edge suffice. AutoFDO's production experience confirms 85% of instrumentation-FDO gains from sampling alone [3], and BOLT additionally smooths profiles with CFG flow inference [1].

## 5. Empirical Results and Proofs

### 5.1 Headline numbers

The following table synthesizes published results [1][3][4][6]:

| System | Workload | Baseline | Gain |
|---|---|---|---|
| BOLT | Meta HHVM / TAO / Proxygen | PGO + LTO | up to **8.0%** |
| BOLT | clang 7 binary | FDO + LTO | up to **15.3%** |
| BOLT | clang 7 / GCC 8.2 binaries | `-O3` only (no FDO/LTO) | up to **35.5%** |
| AutoFDO | Google warehouse benchmarks | `-O2` | geomean **10.5%** |
| Propeller + AutoFDO | Linux kernel (clang) | AutoFDO alone | **5–10%** additional |
| BOLT | Linux kernel (vmlinux) | baseline kernel | significant I-cache/iTLB reduction [6] |

![IPC improvement bar chart: clang-built binaries before and after BOLT optimization](/thesis/ths_1788805749359_4408-3.webp)

### 5.2 Decomposing the 15.3%

Where do the gains come from? The BOLT paper's `perf stat` breakdown on clang [1] attributes the speedup roughly as:

- **~60%** from reduced L1 I-cache misses (hot code now fits in fewer lines; conflict misses collapse).
- **~25%** from fewer taken branches and better static prediction (chaining aligns hot paths with fall-through).
- **~15%** from iTLB miss reduction (hot set in fewer 4 KiB pages; huge-page eligibility).

A back-of-envelope check: with clang's hot set $H = 3$ MB and utilization rising from $u_{pre} = 0.35$ to $u_{post} = 0.85$ after splitting+chaining, the miss ratio scales as $(1-u_{pre})/(1-u_{post}) \approx 4.3\times$ — consistent with reported 2–5× miss reductions [1].

### 5.3 The IPC lens

"15% IPC gains" deserves precision: BOLT does not change the instruction *count* materially (it may add jumps on cold paths); it raises **instructions retired per cycle** by removing frontend stalls. On a clang compile workload — frontend-bound, with deep call graphs and poor baseline locality — eliminating I-cache misses converts stall cycles into productive ones. This is why the gains *stack* on FDO+LTO: those techniques optimize the backend (inlining, vectorization) while BOLT optimizes the frontend (fetch, decode). They are orthogonal axes of the same performance space [1].

### 5.4 AutoFDO + BOLT synergy, measured

Meta's deployment data shows the second, post-inlining profile pass capturing layout opportunities the compiler's FDO profile missed, because inlining had *moved* the hot code [1]; Google's kernel work shows the same stacking with Propeller (AutoFDO then Propeller, 5–10% combined) [4]. The pattern is general: **every transformation that moves code deserves a fresh profile before the next layout decision**.

## 6. Limitations

Intellectual honesty requires enumerating where post-link optimization breaks down:

1. **Disassembly soundness.** BOLT optimizes only what it can reconstruct; hand-written assembly and non-idiomatic computed jumps force conservative skipping [1][5]. Propeller sidesteps this via basic block sections [4] — arguably the stronger long-term architecture.
2. **Profile staleness.** A profile from workload $W_1$ can *pessimize* $W_2$; BOLT's layout is frozen at build time with no runtime adaptation (AutoFDO's IR mapping is more staleness-tolerant [3]).
3. **Cold-code bloat.** Splitting trades hot locality for total size (extra jumps, alignment, unwind info), conflicting with `-Os`-style goals.
4. **Diminishing returns on small binaries.** If the hot set already fits in L1 I-cache, layout is irrelevant; BOLT shines above ~10 MB of `.text`.
5. **Toolchain friction.** Requires `--emit-relocs`, symbols, and debug info; incompatible with GCC's `-freorder-blocks-and-partition` [5]; each run adds build minutes without distributed caching — Propeller's selling point [4].
6. **Security interactions.** Rewriting invalidates code signatures and complicates CFI schemes assuming compiler-emitted layout; some hardened modes remain unsupported.

---

## 7. Conclusion

Thirty-five years after Pettis and Hansen showed that *where code lives* matters as much as *what code does* [2], the industry has industrialized the insight: post-link, sample-driven layout recovers up to **15.3% on top of FDO+LTO** on clang binaries — performance the compiler cannot reach because it optimizes a program that inlining and linking have already transformed [1]. The recipe is clear: **AutoFDO** for compiler-level decisions, then a **fresh sample profile** driving **post-link layout** — Pettis–Hansen/ExtTSP chaining, hot/cold splitting, affinity reordering — with gains decomposing into I-cache, branch-predictor, and TLB effects. The remaining questions are architectural: disassembly rewriting (BOLT) maximizes per-binary power while relinking (Propeller) maximizes build scalability [4]. The likely endgame is convergence — layout metadata in the compiler, BOLT-class optimization in the linker — but until then, the fastest data-center binaries are built twice.
