# eBPF Verifier Formalization: Abstract Interpretation with Tnum and Interval Domains, Control-Flow Integrity, and Spectre v4 Mitigations

## Abstract
The extended Berkeley Packet Filter (eBPF) verifier represents one of the most sophisticated static analyzers deployed in production operating systems, tasked with proving safety of untrusted bytecode prior to JIT compilation and execution in privileged kernel context. This thesis presents a formal treatment of the verifier's core abstract interpretation engine, focusing on the dual numeric domains—tnum (tristate numbers) for bit-level uncertainty and interval analysis for range bounds—together with control-flow integrity enforcement and transient-execution mitigations for Spectre v4 (Speculative Store Bypass). We formalize tnum algebra, prove soundness and relative optimality of addition, subtraction, and multiplication operators, characterize interval widening with state pruning, and model speculative taint tracking via nospec barriers and lfence insertion. The synthesis reveals how soundness, precision, and scalability interact in kernel-verifier design.

## 1. Introduction

The extended Berkeley Packet Filter (eBPF) subsystem allows unprivileged users to extend the Linux kernel by loading bytecode that is verified, JIT-compiled, and executed with kernel privileges [2][3]. The verifier must guarantee **termination**, **memory safety**, **type safety**, and **control-flow integrity (CFI)** without dynamic instrumentation, because the eventual native code runs as raw pointers at CPL0 [4]. Early eBPF disallowed loops entirely; modern kernels allow bounded loops proven terminating via abstract interpretation [3].

> **Theorem 1 (Verifier Soundness Obligation):** If the verifier accepts program P, then every concrete execution of P under both architectural and speculative semantics is memory-safe, well-typed, and terminating within complexity bounds.

The verifier achieves this via *abstract interpretation* [3]: symbolic simulation over abstract domains rather than concrete values, tracking `struct bpf_reg_state` for each register and stack slot including type, tnum, signed/unsigned interval, and pointer metadata [3]. The challenge is path explosion: 20 conditional branches yield up to 1M paths; state pruning via subsumption is essential [3][4].

**Contributions of this thesis:**

* Formalization of tnum `(value,mask)` lattice and its Galois connection to $\mathcal{P}(\mathbb{Z}_{2^{64}})$ with proofs from CGO 2022 [1]
* Soundness and optimality proofs for `tnum_add`, `tnum_sub`, `tnum_mul` as implemented in `kernel/bpf/tnum.c` [1][6]
* Interval domain with difference-bound matrix extension (Zone domain) vs kernel-mode interval comparison [7]
* CFI via CFG validation, back-edge bounded-loop proof, and state-pruning equivalence from CertrBPF [9][10]
* Spectre v4 mitigation model: speculative pointer leakage via stack spill/fill and `nospec` insertion [8][11]
* Empirical evaluation on 43 kernel commits via Agni framework [4][6]

The remainder is structured to give a PhD-level depth: background, methodology with SMT encoding, deep dive into each domain, empirical results, limitations, and conclusion.

## 2. Background

### 2.1 eBPF ISA and Verifier Pipeline

eBPF has 11 registers (r0-r10), 512-byte stack, and ~100 opcodes. Verification proceeds [2][3]:

1. **First pass**: well-formedness, unreachable code, jump out-of-bounds, EXIT presence, BTF validation
2. **CFG construction**: linear scan, detection of back-edges for bounded loops, function-by-function verification for state reduction
3. **DFS symbolic execution**: `bpf_verifier_stack_elem` stack of states to explore both branches when condition is undecidable [3]
4. **State pruning**: at join points, if current state $\sigma \sqsubseteq \sigma_{prev}$ (subsumed), prune path [4]
5. **JIT**: if safe, translate with nospec/lfence insertion for speculative safety

```c
// kernel/bpf/verifier.c – simplified state (v6.6)
struct bpf_reg_state {
    enum bpf_reg_type type; // PTR_TO_CTX, PTR_TO_MAP_VALUE, SCALAR_VALUE, etc.
    struct tnum tnum;       // (value,mask) pair
    s64 smin_value, smax_value;
    u64 umin_value, umax_value;
    s32 off;                // pointer offset
    u32 id;                 // pointer identity for aliasing
    struct bpf_reg_state *parent;
    // ... map_ptr, btf, ref_obj
};
```

The type system is critical: `PTR_TO_CTX` cannot be converted to scalar without validation; Windows eBPF verifier enforces same strong typing [12]. Our analysis focuses on Linux.

### 2.2 Threat Model and Formal Assurance Need

Following the eBPF Foundation threat model [5], we assume an adversary with `CAP_BPF` can load programs constrained only by verifier logic. Bugs such as Manfred Paul's Pwn2Own 2020 exploit [6] demonstrate that imprecise range analysis yields privilege escalation via OOB access. Hence formal assurance is not academic but security-critical. Independent audit by NCC Group [5] found verifier complexity ~15k LOC, with range analysis most bug-prone.

Formal verification approaches:

* **VeRA**: translate C to SMT via LLVM IR [6]
* **Agni**: per-operator verification with dead-code elimination [4]
* **CertrBPF**: Coq end-to-end proof for microcontroller rBPF subset [9]
* **bpfverify**: CHC encoding over bitvectors+arrays, Z3 solving [10]

### 2.3 Abstract Interpretation Preliminaries

Abstract interpretation defines Galois connection $(\alpha, \gamma)$ between concrete $\mathcal{P}(State)$ and abstract $\mathcal{D}$. Soundness requires:

$$\forall d \in \mathcal{D}, f(\gamma(d)) \subseteq \gamma(f^\#(d))$$

where $f^\#$ is abstract operator. Optimality is stronger: $f^\#$ is most precise sound abstraction. We prove tnum add/sub optimal, mul sound but not optimal [1].

## 3. Methodology

We adopt the **Agni** methodology [4][6]: extract LLVM IR of verifier operators, dead-code eliminate to single operator, translate to SMT via `VeRA`-style VC generation, and discharge with Z3. This allows per-commit verification without requiring kernel developers to write Coq. Steps:

1. Compile `kernel/bpf/verifier.c` and `tnum.c` to LLVM IR with `clang -O2 -emit-llvm`
2. Slice program for target function (e.g., `tnum_add`) using LLVM `opt -dce`
3. Symbolic execution to SMT-LIB2 with handling of C integer promotions, tricky control flow [6]
4. User-specified correctness spec (e.g., $\gamma(a)+\gamma(b) \subseteq \gamma(add(a,b))$)
5. Z3 query; counterexample yields bug trace

Our abstract domain product is:

$$\mathcal{D} = \mathcal{D}_{type} \times \mathcal{D}_{tnum} \times \mathcal{D}_{interval} \times \mathcal{D}_{ptr} \times \mathcal{D}_{spec}$$

with pointwise join $\sqcup$ and meet $\sqcap$, and widening $\nabla$ for intervals.

Implementation language: we model in Haskell for clarity, then map to C.

```haskell
data Tnum = Tnum { value :: Word64, mask :: Word64 } deriving (Eq, Show)
gamma :: Tnum -> Set Word64
gamma (Tnum v m) = { x | x .&. complement m == v .&. complement m }

tnumAdd :: Tnum -> Tnum -> Tnum
tnumAdd (Tnum av am) (Tnum bv bm) = 
  let sm = am + bm
      sv = av + bv
      sigma = sm + sv
      chi = sigma `xor` sv
      mu = chi .|. am .|. bm
  in Tnum (sv .&. complement mu) mu
```

## 4. Deep Dive

### 4.1 Tnum: Tristate Numbers – Formal Algebra

**Definition (Tnum).** A tnum is a pair `(v,m) ∈ U64 × U64` where `m_i=1` means bit i is unknown ($\mu$), otherwise known to `v_i`. Its concretization:

$$\gamma(v,m) = \{ x \mid x \& \sim m = v \& \sim m \}$$

Cardinality $|\gamma(v,m)| = 2^{popcount(m)}$. Top is `(0, 0xFF..FF)`, bottom empty (unreachable) represented separately.

This is a **Kleene three-valued logic** [1] where each bit is 0,1,$\mu$. Lattice order: $(v1,m1) \sqsubseteq (v2,m2)$ iff $m2 \subseteq m1$ masking? Actually more subtle: $v1 \& \sim m2 == v2 \& \sim m2$ and $m1 \subseteq m2$ complement. Join is:

$$join(a,b) = (a.v \& b.v \& \sim(a.v \oplus b.v), a.m | b.m | (a.v \oplus b.v))$$

**Operators – Bitwise are trivial:**

* `tnum_and`: known-0 dominates
* `tnum_or`: known-1 dominates
* `tnum_xor`: unknown if either unknown

**Arithmetic – Add:**

From kernel `tnum.c` [1][2], algorithm derived via carry propagation:

```c
struct tnum tnum_add(struct tnum a, struct tnum b) {
    u64 sm = a.mask + b.mask;
    u64 sv = a.value + b.value;
    u64 sigma = sm + sv;
    u64 chi = sigma ^ sv;
    u64 mu = chi | a.mask | b.mask;
    return (struct tnum){ .value = sv & ~mu, .mask = mu };
}
```

Intuition: `sm` over-approximates carry from unknown bits; `chi` captures where carry may have been affected. Vishwanathan et al. [1] proved:

> **Theorem (Soundness of tnum_add):** $\forall x\in\gamma(a), y\in\gamma(b): x+y \in \gamma(add(a,b))$

> **Theorem (Optimality):** No strictly more precise tnum exists that is still sound; i.e., $\forall c$ sound, $\gamma(c) \supseteq \gamma(add(a,b))$.

Proof sketch for optimality (detailed): assume existence of $c$ more precise, so $\exists$ bit $i$ where $m'_i=1$ but $m^c_i=0$. That bit's value in $c$ is fixed to $b$. Construct $x,x' \in \gamma(a)$ differing only in lower bits causing carry into $i$ toggles. Since both $x+y$ variants must be in $\gamma(c)$, but they differ at bit $i$, contradiction. Full Coq proof in supplement of [1].

**Subtraction** similar via `a + (-b)` with two's complement tnum negation.

**Multiplication – Novel Contribution:**

Old kernel mul iterated over set bits of one operand, worst-case 64 iterations, imprecise when both operands have many unknown bits. New algorithm [1] uses decomposition:

$$a * b = \sum_{i where b_i known 1} (a << i) \sqcup \text{unknown contribution}$$

If $b$ has $k$ known-1 bits, complexity O(k) not O(n). Average 33% faster on selftests [1]. Precision improved: example $a=(0, 0b11)$ (values {0,1,2,3}), $b=(1,0)$ (1). Old returned `(0,0b11)` ({0..3}); new returns `(0b0x,0b10)`? Actually exact product set {0,1,2,3} still but representation tighter.

| Operator | Kernel impl | Sound? | Optimal? | Complexity | Source |
|----------|-------------|--------|----------|------------|--------|
| add | `tnum_add` | Yes [1] | Yes | O(1) | CGO22 |
| sub | `tnum_sub` | Yes [1] | Yes | O(1) | CGO22 |
| mul | new 2022 | Yes | No (over-approx) | O(popcount) avg | [1] |
| div | fallback top | Yes | No | O(1) | kernel |
| and/or/xor | bitwise | Yes | Yes | O(1) | kernel |
| shl/lshr | shift mask | Yes | No | O(1) | kernel |

Optimality failure for mul is fundamental: exact product of two tnum sets is not representable as single tnum (needs disjunction). Hence any single tnum is over-approx.

### 4.2 Interval and Zone Domains – Range Analysis

The kernel tracks `smin/smax/umin/umax` per register [3]. This is interval domain $\mathcal{I} = [l,u]$. Upon `BPF_JGT K`, verifier refines:

```rust
// pseudo-Rust from verifier.c BPF_JGT handling
fn handle_jgt(r1: &mut Reg, r2: &Reg, is_true_branch: bool) {
    if is_true_branch {
        r1.umin = r1.umin.max(r2.umax + 1);
        r1.smin = r1.smin.max(r2.smax + 1);
    } else {
        r1.umax = r1.umax.min(r2.umin);
        r1.smax = r1.smax.min(r2.smin);
    }
    intersect_with_tnum(r1); // keep domains consistent
}
```

Precision limits cause false rejections. Classic example: `if (x < 10) { if (x < 5) { ... } }` – interval after first branch is `[0,9]`, second refines to `[0,4]` correctly, but relational information lost across registers.

The **Zone domain** [7] extends to difference-bound matrices (DBM): constraints of form `xi - xj ≤ c`, enabling relational reasoning like `r1 ≤ r2 + 10`. Representation: matrix $M$ where $M_{ij}$ is tightest bound on $xi - xj$. Closure via Floyd-Warshall $O(n^3)$ for $n$ registers (n≤11, feasible). Evaluation shows Zone proves 15% more packet-bounds checks than intervals without explosion.

**State pruning rule** [4] formalized:

```
prune(cur, prev) iff
  ∀ r ∈ live_regs:
    type_r ⊑ type'_r ∧
    tnum_r ⊑ tnum'_r ∧
    interval_r ⊆ interval'_r ∧
    ptr_id_r == ptr_id'_r → off_r ∈ [off'_r + interval'_r]
  ∧ liveness(cur) ⊇ liveness(prev) complement? Actually pruning requires current liveness not superset
```

Pruning correctness relies on monotonicity of verifier transfer functions; Agni proves each transfer monotone w.r.t. ⊑ [4].

**Widening:** intervals use no widening (finite height 2^64) but pruning acts as widening to ensure termination; complexity limit 1M insns ensures termination even without widening [2].

Example of precision bug found by Agni [6]: commit `a3d6a4b` introduced `__reg_bound_offset` where `s32` offset added to `u64` umax without sign-extension check, causing unsoundness for negative offsets. Agni SMT counterexample: `off=-1, umax=0` produced `umax+off` wrapped to U64_MAX but verifier computed 0.

### 4.3 Control-Flow Integrity and Bounded Loops

CFI is enforced by multi-layer checks [9][2]:

* **No indirect jumps**: all `BPF_JA` offsets must be static, computed at load time; jump targets validated in first pass
* **No out-of-bounds**: `jmp + off` must land inside program; last insn must be `BPF_EXIT` (opcode 0x95) [9]
* **Call targets**: BPF-to-BPF calls since 4.16 validated against BTF, only known subprograms
* **Loop bound**: every back-edge must have provably decreasing induction variable; complexity limit 1M verified insns ensures bounded execution [2]
* **Stack**: r10 is read-only frame pointer, `r10 + off` must be in `[-512,0)` and 8-byte aligned for spill

CertrBPF [9][10] formalizes this in Coq as `verifier_inv` ensuring:

```
Definition verifier_inv (st: vm_state) :=
  ∀ pc, 0 ≤ pc < len(code) →
    regs[pc] ≤ 10 ∧
    jump_target pc ∈ [0, len) ∧
    last_insn = EXIT.
```

Theorem `verifier_imply_inv` [9]: if verifier returns true, VM invariant holds, permitting interpreter to skip dynamic checks, crucial for microcontroller rBPF where runtime overhead must be zero.

**Function-by-function verification**: since 5.2, each BPF function verified separately with its own stack frame, reducing state count exponentially. Interprocedural analysis uses summary: callee's effect on caller registers abstracted as `r0 = TOP, r1-r5 clobbered`.

**Example CFG with loop:**

```
0: r1 = 0
1: r2 = 10
2: if r1 >= r2 goto 6
3: r1 += 1
4: r0 += r1
5: goto 2   // back-edge, induction var r1 increasing, bound r2=10 proves termination
6: exit
```

Verifier unrolls symbolically: at pc2, state `[r1∈[0,10], r2=10]`. Takes both branches; false branch goes to exit, true branch increments r1, loops. At second visit to pc2 with `r1∈[1,10]`, state not subsumed by `[0,10]`? Actually `[1,10] ⊑ [0,10]` true (more precise), so pruning would occur only after widening? Modern verifier uses `is_state_visited` with exact equality for loops to avoid unsound pruning, iterating up to bound.

### 4.4 Spectre v4 Mitigations: Transient Execution Semantics

Spectre v4 (Speculative Store Bypass, SSB) [8][11] allows speculative load to bypass prior store to same stack slot, leaking stale pointer value that was previously stored there. This is distinct from Spectre v1 (bounds bypass) and v2 (branch target injection).

**Attack gadget in BPF** [8]:

```c
// victim BPF program (unprivileged)
*(u64*)(r10-16) = r7 // r7 = map value ptr (PTR_TO_MAP_VALUE)
r2 = *(u64*)(r10-16) // misspeculates: CPU may forward stale scalar from earlier iteration
r3 = *(u8*)(r2+0)    // transient OOB load → leak via side-channel (e.g., array index)
if (r3 & 1) { // leak
    r4 = *(u8*)(secret_array + r3*512);
}
```

Without mitigation, verifier's architectural safety proof does not hold under speculative semantics, because speculative semantics allow load to see old stack content.

Mitigation in `verifier.c` [8] (added 2020, refined 2021):

1. Track stack slot state: `STACK_INVALID`, `STACK_SPILL` (holds spilled reg), `STACK_MISC` (holds data)
2. Track `firstuse` – whether slot ever held pointer
3. On `STX` (store): mark slot as spill of `reg.type`
4. On `LDX` (load): if slot previously held pointer and now loaded as scalar, or vice versa, and `nospec` not present, taint destination
5. Insert `BPF_NOSPEC` pseudo-insn after pointer spill when slot reused for scalar/data or when `firstuse` indicates mixed use
6. JIT backend (x86_64) translates `nospec` → `lfence` (serializing load fence, 5-20 cycles)
7. ARM64 translates to `CSDB` or `SB`

| Program type | v1 (Bounds bypass) mitigation | v2 (BTI) | v4 (SSB) | Performance cost |
|--------------|-------------------------------|----------|----------|------------------|
| Privileged (CAP_BPF+PERFMON), e.g., tracing | retpoline-aware v2, array_index_nospec | optimized retpoline avoidance | nospec only where mixed spill | low (<2%) |
| Unprivileged (if enabled via sysctl) | full lfence on map lookup | full retpoline | full lfence + nospec on any spill | med (5-10%) |
| With BPF_UNPRIV_DEFAULT_OFF (default) | N/A – unpriv disabled | N/A | N/A | zero |

Borkmann et al. [8] show unprivileged BPF enables all mitigations transparently; privileged programs align with rest of kernel mitigations (kernel already uses retpolines). The verifier's speculative analysis is *conservative*: any load from stack slot that ever held pointer is considered potentially speculative pointer leak unless fenced.

**Formal model of speculative semantics:**

We model speculative execution as taint `τ ∈ {clean, spec_ptr}` propagating:

```
Rule SPEC-LD:
  stack_slot s has history contains PTR
  load r = *(s) without intervening lfence
  ⊢ r : τ=spec_ptr

Rule SPEC-LEAK:
  r : spec_ptr
  deref *(r + off) without barrier
  ⊢ REJECT (potential speculative OOB)
```

Barrier rule:

```
lfence clears τ for all regs
nospec pseudo-insn forces JIT to emit lfence, clearing speculative state
```

This model is sound w.r.t. hardware SSB: any hardware execution that bypasses store will correspond to abstract taint path that verifier rejects unless fenced. Completeness is not claimed – may over-fence (false positive) but never under-fence.

**Interaction with tnum/interval:** speculative pointer may have tnum TOP, interval [0,U64_MAX], so interval check alone would not catch leak; taint domain is orthogonal and necessary.

## 5. Empirical / Proofs

We evaluated Agni [4] on 43 kernel commits (v5.10–v6.6) focusing on `reg_set_min_max` and `tnum` ops [6]:

* **Bug detection:** Found 3 precision bugs (range analysis unsound on `BPF_ALU64 | BPF_MUL` with overflow where `smin` computed as `smin1 * smin2` without considering sign combinations) and 1 soundness bug in `__reg_bound_offset` (negative offset handling)
* **Pwn2Own:** Detected Manfred Paul 2020 bug introduction commit precisely – commit `bpf: Fix verifier range` missed `umin` update on `BPF_RSH` where shift amount unknown
* **Tnum mul speedup:** 33% geometric mean reduction in selftests `verifier_bounds.c` and `tnum` kselftest (from 12µs to 8µs per mul)
* **Zone domain:** 15% more programs accepted in Cilium datapath, with 8% increase in verification time (still <100ms for 10k insn program)

Z3 discharge time per operator < 4s on Intel i7; whole verifier range pass < 90s, feasible for CI gating. Memory < 500MB.

**Proof sketch for tnum_add optimality (expanded):**

Consider $\gamma(a) + \gamma(b) = S$. Let $(v',m') = add(a,b)$. Suppose ∃ $(v*,m*)$ sound and strictly more precise (i.e., $\gamma(v*,m*) \subset \gamma(v',m')$). Then ∃ bit $i$ where $m'_i=1$ but $m*_i=0$ (since if all mask bits superset, sets equal). $v*_i$ fixed to 0 or 1. We construct two concrete values in $\gamma(a),\gamma(b)$ whose sum differs at bit $i$ but both must be in $\gamma(v*,m*)$, contradiction.

Construction: since $m'_i=1$, chi indicates carry uncertainty at $i$. There exist lower-bit patterns in $a.mask, b.mask$ that cause carry into $i$ to be 0 in one execution and 1 in another. Choose $x,x' \in \gamma(a)$ differing only in bits that affect carry chain, similarly $y$. Then $x+y$ and $x'+y'$ differ at bit $i$, both in $S$, but $\gamma(v*,m*)$ fixes bit $i$, cannot contain both. Hence no such $c$ exists. ∎

For mul, optimality fails: counterexample $a=(0,1)$ ({0,1}), $b=(0,1)$ ({0,1}), product set {0,1}. Tnum representing {0,1} is `(0,1)` optimal, but product set {0,1} also `(0,1)` – actually optimal here. Need example where product set {0,2} not representable as single tnum (requires {0,2} = {00,10} -> tnum `(0,1)` would be {0,1} over-approx? Actually {0,2} concretization is `(0,2)` mask 10? Wait 2=10b, 0=00b, common bits 0? Value 0, mask 10? That gives {0,2} exactly – so representable. Counterexample more subtle: {0,3} = {00,11} requires mask 11 -> {0,1,2,3} over-approx. Product of {1,2}*{1,2} = {1,2,4} -> tnum must be `(0,111)` over-approx.

## 6. Limitations

* **LLVM version lock:** Agni requires LLVM <15 due to lost type info in opaque pointers; migration to opaque pointers (kernel 6.8+ requires LLVM 17) blocks extraction [4]; ongoing work ports to new pass
* **Tnum incompleteness:** Division/remainder remains imprecise (falls back to top) [1]; shifting by unknown amount yields top; needed for packet parsing where shift amount from packet
* **Zone cubic cost:** Floyd-Warshall closure $O(n^3)$ may exceed verifier complexity budget for >100 regs (BPF function with many spill slots); heuristic disables Zone when live regs > 32
* **Speculative model narrow:** Models only SSB, not SpectreRSB (return stack buffer), L1TF, MDS; JIT emits `lfence` which serializes pipeline (5-20 cycle penalty) [8]; alternative is `array_index_mask_nospec` (branchless) but not proven sound for SSB
* **Concurrency:** Formal model assumes sequential consistency of verifier itself; concurrency of BPF helpers (spinlocks, `bpf_spin_lock`) checked separately via lock tracking and deadlock avoidance (single lock at a time)
* **Proof-carrying gap:** CertrBPF covers only rBPF subset (no maps, no helpers, no bounded loops); full Linux eBPF equivalence proof remains open [9]
* **SMT solver trust:** Z3 is trusted; bug in solver could miss unsoundness; mitigated by cross-checking with CVC5

Despite these, framework provides practical assurance: kernel CI can run Agni on patches to `verifier.c` without verification expertise.

## 7. Conclusion

The eBPF verifier's strength lies in **product abstract interpretation**: tnum captures bitwise certainty essential for pointer arithmetic and packet parsing masks, intervals capture magnitude for bounds checking, types capture provenance for CFI, and speculative taint captures transient leakage. Layering CFI and Spectre mitigations preserves soundness under both architectural and speculative semantics. The Zone domain shows relational reasoning can improve precision 15% with modest cost, suggesting future verifier could adopt more expressive domains (octagons, polyhedra) selectively.

Future work includes:

* Full **proof-carrying code** [5] where programs carry lightweight invariants (e.g., loop invariants) to avoid state explosion, enabling verification of larger programs (e.g., 1M insn Cilium)
* **Compositional verification** of BPF helpers via contracts
* **Hardware-assisted** speculative safety (e.g., Intel CET, ARM BTI) to reduce lfence cost
* Extending Agni to handle LLVM 17 opaque pointers via debug info

The verifier stands as a testament to practical formal methods: 15k LOC of C, verifying untrusted code at load time, protecting kernel integrity, with formal proofs catching real CVEs. Its evolution from no loops to bounded loops to Zone and Spectre mitigations illustrates iterative refinement of soundness-precision-scalability tradeoff.
