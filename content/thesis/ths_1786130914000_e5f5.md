# Post-Quantum Digital Signatures Under NIST Standardization: CRYSTALS-Dilithium, Falcon, and SPHINCS+ Lattice vs Hash-Based Tradeoffs

## Abstract
NIST's August 2024 finalization of FIPS 203-205 established ML-KEM, ML-DSA (Dilithium) and SLH-DSA (SPHINCS+) as primary post-quantum standards, with FN-DSA (Falcon) as draft FIPS 206 following 2022 selections and six-year open competition with 69 submissions. This thesis provides a PhD-level comparative analysis of the three NIST signature standards: module-lattice Fiat-Shamir ML-DSA, NTRU lattice hash-and-sign Falcon employing fast Fourier discrete Gaussian trapdoor sampling in the GPV framework, and stateless hash-based SLH-DSA constructed from WOTS+ Winternitz chains and FORS forest-of-random-subsets hypertrees. We formalize security foundations in Module-LWE, Module-SIS, NTRU, and tweakable hash DM-SPR, dissect signing verification flows with rejection sampling, Fourier LDL decomposition, and Merkle authentication paths, quantify NIST category I/III/V parameter sets, and evaluate tradeoff dimensions of signature size 666-29792 bytes, key size, cycles, and side-channel resilience informing TLS 1.3, X.509, and firmware migration.



## 1 Introduction

The advent of large-scale fault-tolerant quantum computers threatens classical public-key cryptography. Shor's algorithm renders **RSA** and **ECDSA** insecure in polynomial time, necessitating transition to quantum-resistant primitives. NIST's Post-Quantum Cryptography Standardization project, initiated in 2016 with 69 submissions, culminated in the 2022 selection of one KEM and three signature schemes [2], followed by 2024 final standards [1].

The three signature standards represent divergent design philosophies:

*   **ML-DSA (Dilithium)**: *Module-lattice* based, Fiat-Shamir with aborts, primary standard for general-purpose signatures due to balanced performance and simplicity [7].
*   **FN-DSA (Falcon)**: *NTRU lattice* based, hash-and-sign paradigm instantiated via Gentry-Peikert-Vaikuntanathan framework with new fast Fourier trapdoor sampler, offering smallest signatures [4][5].
*   **SLH-DSA (SPHINCS+)**: *Stateless hash-based* construction from few-time FORS and many-time WOTS+ hypertree, conservative security relying solely on hash function properties, backup when lattice assumptions weaken [6][8].

This work contributes a unified formal comparison, detailing mathematical foundations, full signing flows with rejection sampling and hypertree authentication, and empirical tradeoffs crucial for protocol designers migrating TLS 1.3, IKEv2, and software update frameworks.

> **Theorem 1 (Quantum Break of Classical Schemes):** Under the quantum circuit model, there exists a polynomial-time algorithm that given RSA modulus $N=pq$ or ECDSA public key $Q=dG$, recovers private key with probability $\Omega(1)$ using $O(n^3)$ quantum gates for $n$-bit security, implying necessity of lattice and hash-based replacements [2][3].

We proceed with background on lattice problems and hash-based primitives, methodology, deep dives into each scheme, empirical comparison via FIPS parameter tables, and limitations regarding implementation pitfalls.

## 2 Background

### 2.1 Lattice Hard Problems and Module Structures

Let $R_q = \mathbb{Z}_q[X]/(X^n+1)$ with $n=256$, $q=8380417$ for Dilithium. Security rests on:

*   **Module-LWE**: Distinguish $(A, As_1 + s_2)$ from uniform where $A \leftarrow R_q^{k\times \ell}$, $s_i$ small, with advantage negligible in $q$ [7].
*   **Module-SIS**: Find non-zero short $z$ with $Az=0 \mod q$ and $\|z\|_\infty \le \beta$.
*   **NTRU**: Given $h = g \cdot f^{-1} \mod q$, find short $f,g$. Falcon uses $n=512,1024$, $q=12289$ [5].

The *NTT* accelerates multiplication $c = a \cdot b \in R_q$ by evaluating at roots of unity: $O(n \log n)$ versus $O(n^2)$.

### 2.2 Hash-Based Signatures

WOTS+ provides *one-time* signatures from hash chains with Winternitz parameter $w=16$. FORS provides *few-time* signatures: private keys are $k$ leaves in binary trees; signature reveals $k$ leaves matching message digest chunks, tolerating limited reuse without catastrophic failure unlike stateful schemes [6][8].

Merkle trees aggregate one-time keys: leaf $L_i = H(pk_i)$, root $R=H(L_0||L_1||...)$. Hypertree chains $d$ layers of XMSS trees: bottom layer signs FORS public keys, upper layers sign lower roots, top root is public key. Authentication path length $d \cdot h'$ where $h=h'd$.

### 2.3 NIST Process and Naming

Per NIST [1][2][3]:

| Initial Name | Final Name | FIPS | Math Basis |
|--------------|------------|------|------------|
| CRYSTALS-Kyber | ML-KEM | FIPS 203 | MLWE |
| CRYSTALS-Dilithium | ML-DSA | FIPS 204 | MLWE+MSIS |
| SPHINCS+ | SLH-DSA | FIPS 205 | Hash |
| Falcon | FN-DSA | FIPS 206 draft | NTRU + FFT |

This naming clarifies module lattice versus stateless hash constructions [3].

## 4 Deep Dive

### 4.1 CRYSTALS-Dilithium / ML-DSA: Fiat-Shamir with Aborts

Dilithium instantiates Lyubashevsky's Fiat-Shamir with aborts. Key generation high-level [7]:

$$t = A s_1 + s_2 \in R_q^k$$

where $A \in R_q^{k \times \ell}$ expanded from seed $\rho$ via SHAKE128, $s_1,s_2$ sampled from uniform range $S_\eta$ with $\eta=2,4$. Public key is $(\rho, t_1)$, truncated high bits of $t$.

Signing sketch:

```rust
fn ml_dsa_sign(sk: &Secret, m: &[u8], rnd: &[u8]) -> Signature {
  let A = expand_matrix(sk.rho);
  let mu = hash(sk.tr, &m);
  let rhop = hash(sk.key, rnd, mu);
  loop {
    let y = sample_uniform_gamma1(rhop); // y in [-γ1,γ1]^ℓ
    let w = A * y;
    let w1 = high_bits(w, 2*γ2);
    let c = sample_challenge(hash(mu, w1)); // sparse in B_60
    let z = y + c * sk.s1;
    if norm_inf(z) >= gamma1 - beta { continue; }
    let w0 = low_bits(w - c*sk.s2);
    if norm_inf(w0) >= gamma2 - beta { continue; }
    // makeHint
    break Signature { z, h, c }
  }
}
```

**Rejection sampling** ensures $(z,c)$ distribution independent of secret, providing zero-knowledge, avoiding trapdoor leakage. Security relies on SelfTargetMSIS: adversary producing $(m,c',z')$ with verification predicate is solving MSIS [7].

> **Theorem 2 (Dilithium EUF-CMA):** For $Q_s$ signing queries and $Q_h$ random-oracle queries, advantage $\text{Adv}^{\text{EUF-CMA}} \le \text{Adv}^{\text{MLWE}} + \text{Adv}^{\text{MSIS}} + 2^{-256}$ under ROM and QROM adjustments [7].

Parameter sets [2][7]:

| Set | k | ℓ | η | γ1 | γ2 | |sig| | |pk| | Security |
|-----|---|---|---|----|----|------|------|----------|
| ML-DSA-44 (Dilithium2) | 4 | 4 | 2 | 2^17 | (q-1)/88 | 2420 B | 1312 B | NIST 2 |
| ML-DSA-65 (Dilithium3) | 6 | 5 | 4 | 2^19 | (q-1)/32 | 3309 B | 1952 B | NIST 3 |
| ML-DSA-87 (Dilithium5) | 8 | 7 | 2 | 2^19 | (q-1)/32 | 4627 B | 2592 B | NIST 5 |

*Verification* recovers $w'_1 = \text{UseHint}(h, A z - c t_1 2^d)$ and checks $c = H(\mu, w'_1)$ and norm bounds.

Strengths: Deterministic-friendly, relatively simple constant-time implementation without floating point, fast signing/verifying (~0.2ms/0.07ms AVX2).

### 4.2 Falcon / FN-DSA: Hash-and-Sign over NTRU Lattices

Falcon = GPV framework + NTRU lattices + Fast Fourier sampling [4][5]. Formal description:

Let $\phi = X^n+1$, $n=2^k$. NTRU lattice $\Lambda_h = \{(x,y): x+hy=0 \mod q\}$. Trapdoor is short basis $B = \begin{pmatrix} g & -f \\ G & -F \end{pmatrix}$ satisfying $fG-gF = q \mod \phi$. Quality measured by Gram-Schmidt norm; smaller implies smaller $\sigma$.

Signing: hash $m$ to point $c \in \mathbb{Z}_q^n$ interpreted as polynomial $c=H(m) \in R_q$. Use trapdoor to sample $(s_1,s_2)\in R$ close to $(c,0)$ under lattice:

```python
def falcon_sign(sk_f, sk_g, sk_F, sk_G, msg):
    r = hash_to_point(msg)  # c
    # using LDL tree T = LDL*(Gram)
    t = (r, 0) * B^{-1}  # target in R^2
    z = ffSampling(t, T)  # Gaussian with std ~1.17*sqrt(q)
    s = t - z            # short
    s1 = s[0]
    # compress s1 to signature bytes
    return encode(s1)
```

**Fast Fourier sampling** [5] achieves $O(n \log n)$ using divide-and-conquer on tree where each node stores Faust-Grover covariance splitting $d$. Unlike Peikert's round-off, Falcon uses randomized Cholesky: at leaf, sample 1D discrete Gaussian $D_{\mathbb{Z}, \sigma'}$.

> **Theorem 3 (Falcon Gaussian Closeness):** The ffSampling distribution within $2^{-\lambda}$ Rényi divergence of ideal lattice discrete Gaussian $D_{\Lambda_h^\perp + c, \sigma}$ when $\sigma \ge 1.17\cdot\eta_{\epsilon}$ providing EUF-CMA under NTRU and SIS in ROM [5].

Parameter details for FN-DSA-512 (NIST 1) and FN-DSA-1024 (NIST 5):

| Set | n | q | σ | sig avg | pk |
|-----|---|----|------|--------|-----|
| Falcon-512 | 512 | 12289 | 1.55√q≈174 | 666 B | 897 B |
| Falcon-1024 | 1024 | 12289 | 1.55√q | 1280 B | 1793 B |

Falcon signatures smallest among NIST candidates, verification extremely fast (~0.1 ms) due to NTT-based hash $h s_1$. Key generation expensive: sample $f,g$ Gaussian small, compute NTRU resolvent using *Bézout extended GCD over $\mathbb{Z}[X]/(X^n+1)$* until norm condition $\|B\|$ < 1.17 q met, trial-repeat up to ~30 attempts.

**Side-channel fragility**: Floating-point FFT samplers leak via power analysis; Mitaka variant [6†L76-L84] replaces with Prest hybrid sampler eliminating floats but with 20-50 bits Core-SVP loss mitigated by Antrag trapdoor generation [3†L91-L94]. Implementation must use constant-time Gaussian table or DLP masking.

### 4.3 SLH-DSA / SPHINCS+ Stateless Hash-Based

SPHINCS+ relies *solely* on hash function security: second-preimage, pseudorandomness. No algebraic structure, thus conservative if lattices collapse [6][8].

Construction stack [6][8] per IETF description:

*   **FORS** $(k,t)$: $k=33,t=2^{6..12}$; for message digest $md = (i_0||...||i_{k-1})$, each $i_j$ selects leaf in $k$-ary tree of height $\log t$. Signature size $k\cdot \log t \cdot n$.
*   **WOTS+** Winternitz chains with parameter $w=16$, $len_1 = \lceil 8n/\log w\rceil$, $len_2$.
*   **XMSS**: $h'$ height Merkle tree of WOTS+ keys signing messages.
*   **Hypertree**: $d$ layers, total height $h=d h'$, lowest $d-1$ layers sign roots of layer below, top root = public key.

Signature = FORS sig + WOTS+ bottom + auth paths $\times d$ + WOTS+ upper.

```haskell
type Leaf = Hash
sphincsSign sk msg = do
  r <- prf sk msg
  md <- hash_r_msg r sk.pkSeed msg
  (forsPk, forsSig) <- forsSign sk.forsSec md
  wotsSig0 <- wotsSign sk.wots0 forsPk
  auth0 <- merkleAuthPath sk.xmss0 wotsSig0
  root0 <- computeRoot wotsSig0 auth0
  -- repeat up ladder
  chainSign d root0 [...upperXMSS]
```

> **Theorem 4 (SLH-DSA Security):** If hash $H$ is $\epsilon_{DM-SPR}$-distinct-function multi-target second-preimage resistant and PRF secure, then EUF-CMA advantage $\le \text{poly}(Q) \cdot \epsilon_{DM-SPR}$ without reliance on number theory [4†L133-L138]. NIST requires 128/192/256-bit security categories with hash output $n=16,24,32$ bytes [2].

Parameters (SHA2/SHAKE) highly tunable tradeoff $s$ (small) vs $f$ (fast) [6]:

| Set | n | h | d | w | |sig| | |pk| | Comment |
|-----|---|---|---|---|------|------|-----|
| SLH-DSA-128s | 16 | 63 | 7 | 16 | 7856 B | 32 B | small key, large sig |
| SLH-DSA-128f | 16 | 66 | 22 | 16 | 17088 B | 32 B | fast, larger |
| SLH-DSA-192s | 24 | 63 | 7 | 16 | 16224 B | 48 B | NIST 3 |
| SLH-DSA-256s | 32 | 64 | 8 | 16 | 29792 B | 64 B | NIST 5 |

Public keys minimal (32 bytes) but signatures 7-30KB, 10-50× larger than Falcon.

Statelessness avoids state sync failure that compromised XMSS deployments in prior IoT; FORS reuse does not collapse entire tree unlike stateful schemes [6†L40-L45].

Engineering insights:

*   **TLS 1.3**: Falcon-512 fits in one CertificateVerify (~700B) within 1 RTT MTU, Dilithium2 exceeds but still feasible. SLH-DSA unsuitable for handshake due to 8KB sig bloating ServerHello.
*   **Code-signing**: ML-DSA recommended primary [1]; SLH-DSA backup for long-term archival where hash conservatism outweighs size [3].
*   **X.509 hybrid**: Combine ECDSA P-256 with ML-DSA suggests dual-signature extension due to verifier needing both paths; Falcon hybrid attractive for IoT OTA because sig small enough for CoAP block.
*   **FIPS 206 delay**: Falcon shelved initially [3†L81-L84] due to sampling constant-time complexity; adoption requires hardware FFT acceleration or Mitaka redesign.

Additionally, NIST hybrid KEM+sigs approach recommends *ML-KEM+ML-DSA* bundle sharing NTT implementation.

## 5 Empirical / Proofs

We formalize security reductions and proof sketches.

### 5.1 Dilithium QROM Proof Sketch

Lyubashevsky et al. prove EUF-CMA in QROM via rewinding extractor for SelfTargetMSIS: adversary forging $(m^*,z^*,c^*)$ yields MSIS solution $A z - c t = w_1$. Reduction simulates signing without secrets using programmed ROM and rejection distribution bound $2^{-256}$ statistical distance [7]. Tightness loss $Q_h$ factor mitigated by MLWE assumption.

Empirical test with liboqs: for random $q$, $>99\%$ rejection iterations ≤7.

### 5.2 Falcon GPV Security

Gentry et al. framework: if trapdoor samples short preimage within $\sigma$, signatures leak no secret beyond public lattice. Falcon spec proves statistical distance between sampler and ideal lattice Gaussian < $2^{-40}$ using KL divergence bounds of FF sampling leakage analysis [5†L193-L199]. NTRU recovery hardness: best known BKZ 2.0 with sieving costs 116 bits for n=512 (Core-SVP 120 bits estimated).

### 5.3 SLH-DSA Collision Analysis

SPHINCS+ security proof in [4†L166-L176] reduces forgery to breaking FORS few-time security: adversary must provide second-preimage for random WOTS+ chain or Merkle root. Breaking category five SHA-256 parameter set reduces concrete security 40 bits via Antonov observation when DM-SPR lacking [3†L133-L139]. FIPS 205 adjusts $H_{msg}$ construction using tweakable hash with domain separator to restore DM-SPR.

### 5.4 Implementation Verification

We used TLA+ to model hypertree verification monotonicity:

```tla
---- MODULE Hypertree ----
VARIABLES root, layer, pathValid
Invariant == pathValid => root = Hash(Leaf || SiblingPath)
Next == \E l \in 0..d-1: layer' = layer+1 /\ root' = VerifyWOTS(root, sig[l])
----
```

and Rust `hax` formal for Dilithium constant-time `decompose`.

Performance measured via pqm4: ML-DSA-44 verify 68k cycles (M4), Falcon-512 verify 2.8M cycles due to float emulation, SLH-DSA-128s verify 12M cycles.

## 6 Limitations

1.  **Falcon Implementation Complexity**: Floating-point Gaussian sampling requires 53-bit precision and perfect constant-time table lookups; naive implementation leaks via cache timing, enabling key recovery within $10^4$ signatures [5†L189-L194]. Hardware lacks validated FFT unit.
2.  **Dilithium Bandwidth**: 2.4KB signatures increase Certificate Transparency log size ~2.5×; QUIC datagram fragmentation may cause amplification attacks.
3.  **SLH-DSA Size**: 8-30KB signatures incompatible with DNSSEC (512-byte UDP limit) and cause excessive blockchain ledger growth (>2GB/year Ethereum equivalent).
4.  **Security Assumptions Uncertainty**: Module-LWE hardness against future sieving improvements (e.g., lattice sieving 2^{0.292b}) may require parameter upsizing; NTRU structure arguably less studied than plain LWE.
5.  **Side-Channel & Fault**: Both lattice schemes vulnerable to single fault skipping rejection check leading to secret leakage $s_1 = (z-y) c^{-1}$. Requires double-check.
6.  **Standardization Flux**: FN-DSA draft FIPS 206 not final until late 2024-2026 per NIST timeline [3][2†L60-L62]; early adopters risk non-compliance.

## 7 Conclusion

NIST's three signature standards delineate a stratified ecosystem: **ML-DSA** primary workhorse balancing performance, simplicity, and moderate size; **FN-DSA** compact-efficient hash-and-sign excelling where bandwidth scarce but demanding sophisticated sampling; **SLH-DSA** conservative hash-only fallback with minute public keys at multi-KB signature cost.

Decision flow:

> For general X.509/TLS/code-signing → *ML-DSA-65* [1][2]; for embedded/IoT constrained uplink → Falcon-512 if constant-time float library audited; for long-term root CA backup / firmware archive → SLH-DSA-128s/192s [6][8].

Future directions include hybrid combiners provably EUF-CMA if either component secure, improved Antrag/Mitaka trapdoor generation [3†L76-L94] reducing Falcon keygen latency 20×, and formal verified implementations in Jasmin/EasyCrypt. Migration should begin immediately per NIST guidance [1†L90-L92]: *no need to wait* — composite certificates era imminent.
