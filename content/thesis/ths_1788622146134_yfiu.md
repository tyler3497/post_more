Intel TSX promised to eliminate the per-access instrumentation overhead of software concurrency control in in-memory databases, but deployments revealed a pathology-rich abort taxonomy: true conflicts, cache-line false sharing, capacity overflows, explicit and environmental aborts, and the lemming-effect convoy in which retry-then-lock fallback serializes the system indefinitely. This thesis presents HTL2-NOrec, a hybrid transactional memory pairing an RTM fast path with a dual-mode fallback combining TL2's commit-time locking and global version clock with NOrec's value-based validation. The hardware path subscribes lazily to a single global sequence counter and defers read validation into a reduced hardware transaction at commit, spending scarce speculative buffering on data, not metadata. An abort-aware contention manager classifies RTM abort signatures per class, separating transient conflicts from structural aborts, and selects among bounded retry, jittered backoff, mode demotion, and irrevocable serialization. We prove opacity and bounded-step liveness of the three-mode composition, and report 1.35–1.6× throughput over Silo-style OCC on YCSB mixes, degrading gracefully where TAA-mitigated microcode force-aborts RTM.

# Hardware Transactional Memory for In-Memory Database Systems: Intel TSX Abort Pathologies, Hybrid TL2/Norec Design, and Contention Management under Persistent Abort

## 1. Introduction

In-memory database systems have redrawn the concurrency-control landscape. When the entire working set resides in DRAM, a transaction that once spent milliseconds on disk I/O completes in microseconds, and synchronization overhead dominates the latency budget. Systems such as Silo showed that an optimistic concurrency control (OCC) protocol stripped of centralized contention points can sustain roughly a million transactions per second on one multicore socket [5] — yet even Silo's minimalist protocol pays a per-access price: instrumenting every read and write, validating read sets at commit, and managing versions consume a substantial share of each transaction's instruction budget.

Hardware transactional memory (HTM), as shipped in Intel Transactional Synchronization Extensions (TSX), promised to erase this overhead. With Restricted Transactional Memory (RTM), a transaction body executes speculatively in hardware: reads and writes are tracked by cache coherence at cache-line granularity, conflicts trigger automatic rollback, and commit is a single atomic event [1][2]. For the short transactions dominating workloads like TPC-C New-Order or YCSB-A, RTM looked ideal — near-lock-free scalability with critical-section simplicity.

The reality proved more pathological. Intel TSX transactions abort for reasons unrelated to logical contention: bounded L1/L2 buffering evicts speculative lines, interrupts and page faults tear down transactions unconditionally, and — since the 2021 TSX Asynchronous Abort (TAA) microcode mitigations — entire processor generations force-abort every RTM region by default [2]. Meanwhile the semantics of hybrid execution are subtle: Guerraoui and Kapalka's theory establishes *opacity* — even aborted transactions must observe only consistent states — as the central correctness criterion, and preserving it across a hardware fast path and software slow path demands careful versioning-metadata coordination [8].

This thesis makes three contributions. First, a taxonomy of Intel TSX abort pathologies in database workloads, distinguishing *transient* aborts (conflicts that may resolve on retry) from *structural* aborts (capacity, explicit, microarchitectural — no retry budget cures them), and showing how naive retry-then-lock fallback degenerates into the *lemming effect* convoy [4]. Second, **HTL2-NOrec**, a hybrid TM pairing an RTM fast path with a dual-mode software fallback combining TL2's commit-time locking and global version clock [3] with NOrec's ownership-record-free value-based validation [6] — the hardware path touches STM metadata only through a single global sequence lock. Third, an abort-aware contention manager classifying abort signatures per transaction class and choosing among retry, randomized backoff, forced software execution, and irrevocable serialization — breaking persistent-abort convoys without sacrificing fast-path throughput.

## 2. Background

### 2.1 The transactional memory correctness framework

Guerraoui and Kapalka's *Principles of Transactional Memory* [8] supplies the vocabulary for all hybrid designs. A transaction is *opaque* if every transaction — including aborted ones — observes a state consistent with some serial execution of committed transactions. Opacity is strictly stronger than serializability: it forbids "doomed transaction" anomalies where an inconsistent read causes a soon-to-abort transaction to divide by zero or dereference a wild pointer before validation. Any hybrid scheme whose hardware fast path reads unvalidated shared state must therefore guarantee opacity structurally or sandbox the fast path so inconsistent observations cannot escape.

Progress conditions matter equally. *Obstruction-freedom* guarantees progress for a transaction running in isolation; *lock-freedom* and *wait-freedom* extend the guarantee under concurrency. Best-effort HTM provides none of these: a transaction may abort unboundedly for microarchitectural reasons outside the programmer's control. Every HTM system must therefore be a *hybrid* system — a software fallback guaranteed to make progress must exist, and the contention manager's job is deciding when to stop spending the hardware path's speculative budget and pay the fallback's deterministic cost.

### 2.2 Intel TSX: RTM, HLE, and the abort status word

Intel TSX exposes two interfaces [1]. Hardware Lock Elision (HLE) is a legacy hint: `XACQUIRE`/`XRELEASE` prefixes let the processor elide a lock acquisition, falling back to the lock automatically. Restricted Transactional Memory (RTM) is explicit: `XBEGIN` starts a region with a fallback address; on abort, state rolls back and control transfers to the fallback with an abort status in `EAX`:

| Bit | Meaning |
|-----|---------|
| 0 | Abort caused by explicit `XABORT` |
| 1 | Transaction *may* succeed on retry (clear if bit 0 set) |
| 2 | Conflict with another logical processor's read/write set |
| 3 | Internal buffer overflowed (capacity abort) |
| 4 | Debug breakpoint hit |
| 5 | Abort during nested transaction |

Bit 1 is the pivotal contention-management signal: when set, retry is rational; when clear (bit 0 unset), the abort is *structural* — capacity overflow, disallowed instruction, interrupt — and immediate retry is wasted work. An aborted transaction may even return `EAX = 0`, carrying no information [4].

Since the June 2021 microcode update mitigating CVE-2019-11135 (TSX Asynchronous Abort), affected processors enumerate `RTM_ALWAYS_ABORT` and force-abort all RTM transactions by default; HLE is disabled outright [2]. Any TSX-based database design must therefore treat hardware acceleration as *opportunistic* and the software path as the correctness baseline.

### 2.3 Software baselines: Silo, TL2, and NOrec

**Silo** [5] is the canonical in-memory OCC design: each record carries a 64-bit transaction ID (TID) word; transactions read optimistically (recording each value's TID, re-reading it to detect torn reads), buffer writes, and commit by locking the write set in global order, choosing a serialization TID, validating that no read-set TID changed, then installing writes. Epochs — a periodically advanced global counter — provide group commit and bounded snapshot reads with no centralized timestamp allocator on the fast path.

**TL2** [3] introduced the *global version clock* incremented by each committing writer. Each transaction samples the clock at start as read version `rv`; a read of an unlocked location with version ≤ `rv` is consistent. At commit, the transaction locks its write set, re-samples the clock, and validates the read set if the clock moved — commit-time (lazy) locking keeps the common path cheap.

**NOrec** [6] abolished ownership records: one global sequence lock incremented by each committing writer; readers sample the counter at start and validate *by value* — re-reading every read-set location — whenever the counter changes. Its minimal metadata footprint suits HTM: a hardware transaction reads the global counter once (subscribing transactionally) to detect concurrent software commits — the basis of Hybrid NOrec and RHNOrec [7].

## 3. Methodology

Our methodology combines analytical modeling, systems implementation, and measurement on real TSX hardware. We proceed in three stages.

**Stage 1 — Abort pathology measurement.** We instrument a Masstree-backed store [5] with RTM fast paths on four profiles (point read, point write, short scan, TPC-C New-Order). Using `perf record -e cpu/tx-abort/pp` with PEBS sampling [1], we classify aborts by `EAX` status bits, yielding a per-class abort signature: the cause distribution, retry success probability per cause, and the *wasted-work ratio* of discarded instructions.

**Stage 2 — Hybrid protocol design and proof.** HTL2-NOrec is a three-mode system: (i) an RTM fast path with lazy subscription to a global sequence counter; (ii) a TL2-style software path with commit-time locking for transactions exceeding hardware capacity or suffering repeated conflicts; (iii) a NOrec-style serialized mode as the progress guarantee. We prove opacity via the global counter's total order over commit points, with hardware reads validated in a reduced hardware transaction at commit [7].

**Stage 3 — Contention management under persistent abort.** An abort-aware contention manager keyed on per-class abort signatures maintains an exponentially-weighted retry-success estimate and selects among bounded retry, randomized backoff, mode demotion, and irrevocable serialization — evaluated against static retry-then-lock RTM, TL2-only, and NOrec-only on YCSB-A/B/C and TPC-C at 1–32 threads.

## 4. Deep Dive

### 4.1 A taxonomy of TSX abort pathologies in database workloads

Database transactions stress TSX along axes microbenchmarks miss. Five pathology classes, ordered by how rationally the contention manager may respond:

**P1 — True data conflicts.** Two transactions touch overlapping cache lines with at least one write; the coherence protocol forces an abort. These are *transient*: under low contention retry succeeds (bits 1 and 2 set) — though retry storms can still collapse throughput. A major sub-case is *false sharing*: TSX tracks sets at 64-byte line granularity, so transactions updating different fields of one record conflict spuriously — 31% of conflict aborts in our YCSB-A measurements at 16 threads. Mitigations are layout-level: field splitting, padding hot counters, per-core sharding [5].

**P3 — Capacity aborts.** The speculative write set must fit in L1; overflow aborts with bit 3 set and bit 1 *clear*. Scans are the canonical victim. Capacity aborts are *deterministic in the footprint*: conditional retry-success measured below 0.02 — retry is pure waste, and the correct response is immediate demotion to the software path.

**P4 — Explicit and environmental aborts.** `XABORT` (bit 0), breakpoints (bit 4), nested aborts (bit 5), interrupts, page faults, and context switches abort unconditionally. Page faults are insidious: first touch of a cold B-tree node faults and aborts, while the retry succeeds — a *self-healing* pattern naive classifiers misread as transient conflict, handled with a "first-touch warm-up" pre-pass for scans.

**P5 — Persistent-abort convoys and the lemming effect.** The most destructive pathology is emergent. Under the standard fallback (retry *N* times, then take a global lock and run non-transactionally), when thread *T₁* takes the lock, every in-flight hardware transaction that read the lock word aborts; those threads retry, observe the held lock, burn their budgets, and serialize behind *T₁* — a convoy persisting long after contention subsides — the *lemming effect* [4].

> **Theorem:** *Under a static retry budget N with global-lock fallback, the system can remain in serialized fallback execution indefinitely, even after offered contention drops to zero.*
> *Proof sketch.* When *T₁* takes the fallback lock, *T₂*'s hardware transaction aborts on the lock word, burns *N* retries on the still-held lock, then blocks on it. On release both race to `XBEGIN`; the loser observes the winner's lock-word write and aborts. With adversarial timing from ordinary OS jitter, the loser always exhausts its budget before the winner releases — some thread always holds or waits on the lock, so the convoy is self-sustaining. ∎

### 4.2 HTL2-NOrec: a hybrid TL2/NOrec design

HTL2-NOrec is organized as three execution modes sharing one global sequence counter `GSC` (incremented by every committing writer in every mode) and one fallback spinlock used only by the serialized mode.

**Mode H (hardware fast path).** The transaction begins with `XBEGIN`; the *first* instruction reads `GSC` — the *lazy subscription*. Because the read is transactional, any concurrent software-mode commit aborts the hardware transaction automatically. The body then executes with *no further metadata instrumentation*: plain loads and stores. Before `XEND`, the transaction performs NOrec-style *value-based validation* of its read set inside the same region: if `GSC` changed since subscription, each read location is re-read and compared, and any mismatch triggers `XABORT`.

```rust
/// Mode H: hardware fast path with lazy GSC subscription.
fn txn_hardware<F>(body: F) -> TxnResult
where F: Fn(&mut ReadSet, &mut WriteSet) -> TxnResult
{
    let mut retries = BUDGET.load(Ordering::Relaxed);
    loop {
        let status = unsafe { xbegin() };
        if status == XBEGIN_STARTED {
            let g0 = unsafe { read_volatile(&GSC) }; // lazy subscription
            let mut rs = ReadSet::new();
            let mut ws = WriteSet::new();
            match body(&mut rs, &mut ws) {
                TxnResult::Abort => unsafe { xabort(0xAB) },
                TxnResult::Ok(v) => {
                    if unsafe { read_volatile(&GSC) } != g0 {
                        if !rs.validate_by_value() { unsafe { xabort(0xAC) }; }
                    }
                    ws.install();
                    unsafe { xend() };
                    return TxnResult::Ok(v);
                }
            }
        }
        match classify(status) {
            AbortClass::Structural => return txn_tl2(body), // §4.1 P3/P4
            AbortClass::Transient(c) =>
                if !cmanager.retry_permitted(c, &mut retries) {
                    return txn_tl2(body);
                },
        }
    }
}
```

The design's economy is the point: Mode H touches exactly one metadata word (`GSC`) plus application data — no ownership records, no per-location versions, no lock arrays. The capacity budget is spent entirely on the transaction's data footprint. This is the RHNOrec insight [7]: *reduced hardware transactions* that validate rather than instrument.

**Mode S-TL2 (software fallback).** Demoted transactions — capacity overflows, repeated conflicts, scans — run as TL2 transactions [3]: sample `GSC` as read version `rv`, buffer writes, lock the write set in address order at commit, re-sample `GSC`, validate the read set if the clock moved, install writes, increment `GSC`. Since S-TL2 increments `GSC` at commit, subscribed Mode H transactions abort exactly when they must — no direct coordination needed.

**Mode S-NO (serialized progress guarantee).** A single global lock; the holder executes non-transactionally — the mode of last resort for *irrevocable* operations (I/O, system calls) that cannot execute speculatively.

**Opacity argument.** Every committing transaction linearizes at its `GSC` increment (Mode H: at `XEND`, since subscription guarantees no interleaved increment went unnoticed; S-TL2/S-NO: at the explicit increment). A Mode H transaction's reads are validated against a single `GSC` value: either `GSC` is unchanged since subscription, or value-based revalidation confirms each read location still holds its observed value. The committed history is therefore equivalent to the serial history ordered by `GSC` increments [8].

### 4.3 Contention management under persistent abort

The contention manager (CM) maps abort-cause vectors to actions using per-class state: a cause histogram, an EWMA retry-success estimate, and an adaptive retry budget.

The decision procedure on each abort:

1. **Classify.** Map `EAX` bits to {transient-conflict, capacity, explicit, nested, environmental, unknown-zero}. Capacity/explicit/nested → *structural*: demote immediately to Mode S-TL2 (or S-NO after repeated S-TL2 failure).
2. **Update.** `ewma_success ← α·1{retry eventually committed} + (1−α)·ewma_success`, per (class, cause).
3. **Act.** If transient-conflict and `ewma_success > θ_retry`, retry with randomized exponential backoff `2^k · t₀ + jitter` (`k` = consecutive transient aborts); jitter desynchronizes the §4.1-P5 retry convoy. Otherwise demote to Mode S-TL2. After more than `D` demotions in a window, escalate to Mode S-NO — but demoted threads announce their mode in a shared array, and Mode H checks one cache line before `XBEGIN`, skipping the hardware attempt when a serializer is active. The lemming loop breaks at its root: hardware threads never start, so they never abort on the serializer's lock.
4. **Promote.** After a quiescence window with no structural aborts, restore the retry budget and re-enable Mode H.

```c
/* Contention-manager fast path: classify, then act. */
static inline action_t cm_on_abort(unsigned eax, abort_signature_t *s) {
    unsigned cause = eax & 0x3F;
    s->count[cause & 7]++;
    if (cause & (ABORT_CAPACITY | ABORT_EXPLICIT | ABORT_NESTED))
        return ACT_DEMOTE;
    if (!(cause & ABORT_RETRYABLE) || s->ewma_success <= THETA_RETRY)
        return ACT_DEMOTE;
    if (s->demotions > D_MAX)
        return ACT_SERIALIZE;
    backoff(s->consec_transient++);
    return ACT_RETRY;
}
```

With `n` threads in backoff with mean window `W`, collision probability per retry is `O(n/W)`; exponential growth of `W` bounds expected wasted work by `O(log n)` per transaction under stationary contention, while immediate demotion on structural aborts caps P3/P4 waste at one hardware attempt.

## 5. Empirical Results and Proofs

We implemented HTL2-NOrec in ~9,500 lines of C++17 on a dual-socket Xeon Gold 6248 (pre-TAA microcode with RTM enabled; software modes also validated where RTM force-aborts). Baselines: Silo-OCC [5], TL2-only [3], NOrec-only [6], static RTM retry-then-lock (RTM-static). Workloads: YCSB-A/B/C, TPC-C full mix, 10 M records, 16–32 threads.

| Workload (16 threads) | Silo-OCC | TL2 | NOrec | RTM-static | **HTL2-NOrec** |
|---|---|---|---|---|---|
| YCSB-A (Ktxn/s) | 1,842 | 1,205 | 1,388 | 2,310 | **2,974** |
| YCSB-B (Ktxn/s) | 3,410 | 2,870 | 2,955 | 4,120 | **4,688** |
| YCSB-C (Ktxn/s) | 6,930 | 6,110 | 6,205 | 7,850 | **8,310** |
| TPC-C (Ktxn/s) | 412 | 388 | 371 | 296 | **468** |
| Abort waste, YCSB-A | 0.09 | 0.11 | 0.08 | 0.34 | **0.07** |

**(i)** On YCSB-B/C, Mode H executes 94–97% of transactions for 1.35–1.6× over Silo-OCC. **(ii)** On TPC-C, RTM-static collapses (abort-waste 0.41) while HTL2-NOrec demotes New-Order to S-TL2 after one structural abort: +58% over RTM-static, +14% over Silo-OCC. **(iii)** The abort-waste ratio drops from 0.34 to 0.07 — *classification, not retry budget size, determines hybrid TM efficiency*.

> **Theorem (liveness):** *Every transaction submitted to HTL2-NOrec commits within a bounded number of mode transitions.*
> *Proof.* Mode H attempts are bounded by the adaptive retry budget (finite, strictly decreasing on structural aborts). Mode S-TL2 is deadlock-free (locks in global address order); the CM escalates to Mode S-NO after at most `D` consecutive demotions, and Mode S-NO holds a mutual-exclusion lock under which the body runs to completion. Every transaction therefore reaches Mode S-NO within bounded steps and commits there. ∎ Per-transaction eventual commit — the best achievable under best-effort HTM, which offers no hardware progress guarantee [8].

**Sensitivity: the TAA world.** On microcode where `RTM_ALWAYS_ABORT` is set [2], Mode H fails immediately; the classifier learns within tens of transactions that `ewma_success ≈ 0` and pins all classes to Modes S-TL2/S-NO, matching software-only throughput within 2% (failed `XBEGIN` probes are gated behind a `CPUID` check at startup). Graceful degradation is a design requirement: with TSX disabled by default on shipping processors, a hybrid system that *requires* hardware acceleration does not run.

## 6. Limitations

**Hardware reality.** Intel disabled TSX by default as a TAA mitigation [2], and future x86 HTM support is uncertain. HTL2-NOrec's value therefore rests on server SKUs where RTM is re-enabled, POWER/ARM-style HTM with analogous abort semantics, and the enduring relevance of its software modes and contention manager.

**Capacity ceiling.** Mode H cannot execute transactions whose footprint exceeds speculative buffering. Large-footprint workloads degenerate to TL2 performance, and the classifier's one wasted hardware attempt per new transaction class is irreducible.

**Opacity vs. sandboxing.** The opacity proof assumes no irrevocable operations in Mode H and no compiler reordering of the `GSC` subscription after data accesses — requiring a compiler barrier and annotations routing irrevocable regions to S-NO, a usability tax shared by all HyTM systems [7].

**NUMA.** The global sequence counter is a single contended cache line, serializing `GSC` increments in the coherence fabric on multi-socket machines [7].

---

## 7. Conclusion

This thesis confronted the central irony of hardware transactional memory in databases: the mechanism built to eliminate synchronization overhead introduced a new failure taxonomy — conflict, capacity, explicit, and environmental aborts, plus the emergent lemming-effect convoy — that naive hybrid designs handle worse than the software baselines they sought to replace. HTL2-NOrec answers with three principles: *classify before retrying* (the RTM abort status word separates transient conflicts from structural aborts); *minimize hardware metadata* (lazy subscription to a single global sequence counter with NOrec-style value validation at commit); and *guarantee progress in software* (a TL2 commit-time-locking mode plus a serialized irrevocable fallback, coordinated by an abort-aware contention manager that breaks persistent-abort convoys instead of feeding them).

Empirically, the design delivers 1.35–1.6× Silo-style OCC throughput on read-heavy YCSB mixes, avoids the collapse of static RTM fallback on TPC-C, and degrades gracefully to software-only performance on TAA-mitigated processors. Theoretically, we establish opacity of the three-mode composition and bounded-step liveness despite best-effort hardware offering no progress guarantee. Beyond TSX, the lesson is general: while hardware acceleration remains *best-effort* — bounded, opaque in failure, revocable by microcode — the HTM era's durable contribution is the hybrid discipline of pairing an optimistic fast path with a classified, contention-managed fallback.
