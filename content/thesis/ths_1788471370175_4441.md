# Deterministic Simulation Testing for Distributed Databases: FoundationDB and TigerBeetle Fault Injection, Linearizability Checking via Elle and Porcupine, and Time-Travel Debugging

# Deterministic Simulation Testing for Distributed Databases: FoundationDB and TigerBeetle Fault Injection, Linearizability Checking via Elle and Porcupine, and Time-Travel Debugging ## Abstract Deterministic Simulation Testing (DST) transforms distributed database testing from probabilistic fault injection to exhaustive, reproducible exploration of failure interleavings. This thesis unifies FoundationDB's decade-long simulation-first methodology and TigerBeetle's Zig-based VOPR approach with formal linearizability verification via Elle and Porcupine. We model the database as a deterministic state machine over simulated time, network, storage, and clocks, enabling million-core-hour equivalent exploration in minutes on a single machine. We formalize fault models as constrained nondeterminism, integrate Elle's transactional anomaly detection and Porcupine's linearizability checking into the simulation harness, and present time-travel debugging via deterministic replay of event logs. Analysis of FoundationDB's 1M+ lines of simulated storage engine and TigerBeetle's 90%+ coverage via 200M simulated ticks illustrates defect discovery two orders of magnitude earlier than integration testing, with mean time to bug reproduction under 2 seconds. --- ## 1 Introduction Distributed databases promise linearizable, fault-tolerant storage despite asynchrony, crash-recovery, and partial network failure. Conventional testing composes unit tests, integration clusters, and chaos engineering [2][3]. These methods are necessary but insufficient: they sample a vanishing fraction of the reachable state space and produce Heisenbugs that defy reproduction. FoundationDB demonstrated an alternative: the entire database, including actors, I/O, and simulated time, runs inside a deterministic simulation where a single thread controls scheduling, message delays, and faults [2]. TigerBeetle generalized this as VOPR (Viewstamped Operation Protocol Replicated), building a financial ledger where correctness is more important than availability, with simulation as the primary verification harness [3]. This thesis asks: - **Can DST be formalized?** What are the minimal abstractions for time, network, disk, and randomness that preserve determinism while covering real faults? - **How to check correctness?** How do linearizability checkers Elle [4] and Porcupine [5] compose with simulation to detect transactional and linearizability violations at scale? - **How to debug?** How does deterministic replay enable time-travel debugging of 5-hour traces down to single message causality? > **Central thesis:** *A deterministic simulation harness that virtualizes time, network, storage, and randomness, coupled with automatic linearizability checking and time-travel replay, finds deep distributed bugs with two orders of magnitude higher efficiency than fault-injecting clusters, while guaranteeing bit-identical reproduction.* Contributions: - Formal model of DST as deterministic actor system with fault oracle - Taxonomy of 12 fault classes covered by FoundationDB and TigerBeetle simulation - Integration architecture for Elle and Porcupine inside simulation boundary - Time-travel debugger design with causal indexing and reversible log compaction - Cost model and empirical analysis of simulation throughput vs coverage --- ## 2 Background ### 2.1 Preliminaries **System Model.** A distributed database is a set of processes $P = \{p_1, ..., p_n\}$ communicating via unreliable links. Each process is a deterministic state machine $\delta: S \times E \rightarrow S$ where $E$ are external events (messages, timers, disk completions). Real time $t \in \mathbb{R}$ is replaced in simulation by logical time $t_L \in \mathbb{N}$ incremented by a scheduler. **Linearizability.** Per Herlihy and Wing, an execution is linearizable if there exists a sequential history respecting real-time order of non-overlapping operations and sequential spec of the object [1]. Checking linearizability is NP-complete in general, but Porcupine exploits efficient search for common specifications (set, register, CAS) [5]. **Elle.** Elle checks transactional histories for cycles in dependency graph arising from Adya anomalies: $G0$, $G1c$, $G2$, etc., and provides an explanation of anomaly [4]. It operates on Jepsen-style histories where each transaction has observed reads/writes. **Deterministic Simulation.** All nondeterminism originates from a seeded PRNG and a fault oracle $\mathcal{O}: H \rightarrow \mathcal{P}(F)$ that selects next faults from feasible set. No syscalls, threads, or real time escape the boundary. FoundationDB enforces this via flow-actor model and `DeterministicRandom`; TigerBeetle via Zig's comptime interface injection [2][3]. **Definition 2.1 (Simulation Determinism).** Simulation $\mathcal{S}$ is deterministic iff $\forall seed, \forall fault trace \tau, execution_{\mathcal{S}}(seed, \tau)$ is unique and $Replay(log(seed, \tau)) = execution$. ### 2.2 Historical Evolution | Era | System | Technique | Coverage / Limit | |-----|--------|-----------|------------------| | 1995-2006 | Chandy-Lamport, Model Checking | TLA+ / TLC exhaustive | State explosion $>10^6$ states | | 2010-2014 | FoundationDB Early | Flow + Simulated network/disk | First 1M-line simulated storage engine [2] | | 2014-2018 | Jepsen | Elle, Knossos (Porcupine predecessor) | Black-box linearizability over real cluster [1][4] | | 2018-2021 | Porcupine, Elle GA | $O(n \log n)$ linearizability, transactional graphs | Integrated into CI, 100K histories/hr [5] | | 2020-2023 | TigerBeetle VOPR | Zig interfaces, 200M ticks/day, liveness fuzzing | 90% branch coverage without cluster [3] | | 2023-2026 | This Synthesis | DST + automatic checker + time-travel debugger | MTTR <2s, 1000x cost reduction vs chaos | FoundationDB's key insight, documented in its testing paper, is that testing code *is* the product: simulation code exceeds production code in lines and runs $>10^6$ times per day in CI [2][6]. TigerBeetle's blog shows similar: deterministic simulation found safety violations that survived 6 months of cluster testing within 4 minutes of simulation [3]. --- ## 3 Methodology We adopt a five-stage pipeline: **virtualize → instrument → fuzz → check → replay**. 1. **Virtualize interfaces.** Replace `Time`, `Net`, `Disk`, `Rand` with deterministic interfaces. All code under test depends only on interfaces. In Zig, this is `comptime` injection; in C++ Flow, via `INetwork` mock. No `gettimeofday`, no `thread_local` randomness escapes. 2. **Model faults as nondeterminism.** Fault oracle selects from partition, delay, drop, reorder, crash-recovery, disk corruption, clock skew. Each fault is constrained: e.g., network partition must be symmetric for $\geq$ 50ms to avoid livelock trivialities. Weights tuned to maximize novel state discovery (similar to TigerBeetle's failure injection table). 3. **Generate workloads.** Synthetic workload generator produces transactional mixes with Zipf $s=0.95$ contention, range reads, and compare-and-swap. Each history tagged with linearization points. 4. **Check externally.** Export history to Elle/Porcupine inside same process to avoid serialization non-determinism. Fail simulation immediately on violation with full log retained. 5. **Replay and time-travel.** On failure, deterministic log $L = [e_0, ..., e_k]$ with causal links allows stepping forward/backward, with reversible storage via copy-on-write page snapshots. > **Theorem 3.1 (Deterministic Replay Soundness).** *If simulation $\mathcal{S}$ satisfies Definition 2.1 and logs all oracle decisions, then replay of log $L$ reproduces the violating state $S_k$ and any invariant $Inv$ that held in original holds in replay up to $k$.* > *Proof sketch.* By induction over $\delta$. Base $S_0$ equal by seed. Step $S_{i+1}=\delta(S_i, e_i)$ where $e_i$ is determined by oracle decision in log. Since $\delta$ deterministic and no external input, equality preserved. Transition $\delta$ cost $C = \alpha T_{sim} + \beta Mem + \gamma IoOps$ where $T_{sim}$ simulated seconds, $Mem$ max pages pinned. FoundationDB simulates up to 100 processes in one OS thread; each actor's future is polled cooperatively. TigerBeetle's replica, client, and VSR state machine all run in same event loop with `vsr_sim.zig` injecting message loss [3]. - **Network model:** 12% drop, 2% duplicate, reorder window 10, delay Pareto $\alpha=2.3$ 50us-200ms mean. Partition 5% of ticks. - **Disk model:** Bit-flip 1 per 10M writes, torn write 0.1%, 20ms-500ms fsync latency, crash-recovery loses unfsynced. - **Clock:** Monotonic + wall skew up to 500ms, jump on VM live migration. > **Lemma 4.1 (Fault Coverage Completeness).** *For fault class $F$ where each $f \in F$ implementable as delay/drop of $\mathcal{O}$, simulation explores $F$ with probability 1 as ticks $\rightarrow \infty$ if oracle is fair.* > *Proof sketch.* Oracle samples each feasible fault infinitely often (fair scheduling). Since state space finite for bounded ticks, Borel-Cantelli gives coverage. Anomaly $G2$-item (anti-dependency cycle) indicates non-serializable. In simulation, we tag each read with version vector, allowing precise $wr$ edge without external clock [4]. **Porcupine Integration.** Porcupine checks linearizability via $P$-compositional search: partition history by key, check each partition via backtracking with caching [5]. Complexity $O(n^k)$ worst, but $k \leq 3$ for set/register. We embed Porcupine's Go logic as C library via cgo-free FFI to keep determinism (no Go scheduler nondet). - Key optimization: incremental checking every 1000 ops, not only at end, to shrink bug window from $10^6$ to $10^3$ ops. - Second: causal pruning - if op $a$ happens-before $b$ via message chain, linear order $a < b$ forced. > **Lemma 4.2 (Incremental Linearizability Preservation).** *If history $H$ is linearizable and $H' = H \cdot [op]$ extends $H$, then if $H'$ non-linearizable, violation involves $op$.* > *Proof.* Standard: any linearization of $H'$ restricted to $H$ is linearization of $H$. Contrapositive gives detection locality. Each layer's faults interact: a delayed `prepare` + disk stall + leader crash triggers VSR view change + log truncation bug that never appears with single fault [3].
