# RDMA One-Sided Distributed Transactions at Scale: FaRM-Style Two-Phase Commit over RDMA Verbs, Coroutine Request Multiplexing, Membership-Lease Failure Detection, and Timestamp Ordering vs Two-Phase Locking

## Abstract

This thesis presents a unified analysis of distributed transaction processing on RDMA fabrics, centered on the design space opened by FaRM's one-sided two-phase commit and the counter-designs it provoked. We dissect how one-sided RDMA verbs — READ, WRITE, and compare-and-swap — eliminate remote-CPU involvement from the commit path, reducing a distributed commit to a small constant number of network round trips, and how coroutine-per-request multiplexing over completion queues lets a single thread drive millions of transactions per second. We formalize FaRM-style optimistic commit as a four-phase protocol (lock via CAS, validate read set, replicate commit log, apply and unlock) and prove its serializability, then contrast timestamp ordering against two-phase locking with NoWait deadlock avoidance as realized in DrTM's HTM/RDMA hybrid. Empirical evidence is drawn from published results: FaSST's 3.55M transactions/s per machine on a 50-node cluster versus FaRM's 1.9M, DrTM's 0.93M on SmallBank, and HERD's 26M operations/s key-value ceiling. We conclude that one-sided verbs dominate when round-trip counts are minimal, two-sided datagram RPC dominates when protocol logic is CPU-bound, and the frontier lies in hybrid per-phase verb selection.

## 1 Introduction

Distributed transaction processing has long been bottlenecked by coordination cost: every commit historically required multiple message exchanges, kernel stack traversals, and remote-CPU participation. Three hardware trends — abundant DRAM, microsecond-scale RDMA networks, and reliable one-sided verbs — jointly removed the storage and networking bottlenecks, leaving CPU efficiency as the dominant optimization target [1][2]. This thesis studies the systems that exploited this shift, with FaRM [1] as the canonical design: a shared-address-space computing platform exposing transactional access to cluster memory, built entirely over one-sided RDMA.

FaRM's central insight is that a distributed transaction can be executed without ever involving the remote CPU. Reads become one-sided RDMA READs of versioned objects; locking becomes one-sided RDMA compare-and-swap on lock bits embedded in object headers; and log replication becomes one-sided RDMA WRITEs into the memory of backup replicas [2]. The result is a commit protocol whose latency is measured in a handful of RDMA round trips — single-digit microseconds on InfiniBand — rather than in message-passing round trips that each pay kernel and scheduling overhead.

This design did not go unchallenged. HERD [5] demonstrated that pure one-sided access pays a "price of CPU bypass": index indirection forces multiple RDMA READs per lookup, and a write-based request/response design with server-side polling achieves 26M operations/s at roughly 5µs latency on 187 nodes. FaSST [3] pushed the argument further for transactions: two-sided unreliable-datagram RPCs, multiplexed through coroutines on a single thread, reach 3.55M transactions/s per machine on a 50-node cluster, nearly twice FaRM's 1.9M on identical hardware. DrTM [4] took a third path, combining hardware transactional memory (Intel RTM) with RDMA-based two-phase locking.

Our contribution is a single coherent treatment of these systems along four axes that prior work treats separately:

1. **Commit protocol structure**: the FaRM-style four-phase one-sided two-phase commit, formalized and proved serializable.
2. **Request multiplexing**: coroutine-per-request execution over shared completion queues, which converts microsecond network latency into throughput rather than idle time.
3. **Failure detection and membership**: lease-based configuration management in the ZooKeeper tradition [6], and how it interacts with one-sided recovery.
4. **Concurrency control**: a precise comparison of timestamp ordering against two-phase locking (including NoWait variants), quantifying the abort/blocking trade-off under microsecond coordination.

## 2 Background

### 2.1 RDMA verbs and the one-sided/two-sided divide

RDMA exposes queue pairs (QPs) over which applications post *verbs* directly to the NIC, bypassing the kernel. The verbs divide into two families. **One-sided verbs** — `READ`, `WRITE`, and atomics (`fetch_and_add`, `compare_and_swap`) — operate on remote memory without involving the remote CPU: the responder's NIC executes the DMA and returns a completion [3]. **Two-sided verbs** — `SEND` and `RECV` — require a pre-posted receive buffer and remote-CPU participation to consume the message.

Transports compound the choice. Reliable Connected (RC) provides one-to-one reliable connections supporting all verbs but scales poorly: NICs cache limited QP state, and thousands of QPs cause cache thrashing [3]. Unreliable Datagram (UD) scales to large clusters and supports only `SEND`/`RECV`, which is precisely why FaSST builds its RPC layer on UD [3].

A critical performance asymmetry shapes every design: RDMA WRITEs are typically faster than RDMA READs, because a WRITE completes as a PCIe DMA write at the responder while a READ requires a PCIe DMA read followed by a response [5]. HERD's entire architecture — clients WRITE requests into server memory, servers reply via `SEND` — is an exploitation of this asymmetry.

### 2.2 Distributed commit: the classical baseline

Classical two-phase commit (2PC) proceeds in a voting phase (coordinator sends `prepare`, participants vote ready/abort) and a decision phase (coordinator broadcasts commit/abort, participants acknowledge). In a kernel-networking world each phase costs millisecond-scale latency and CPU on both endpoints, making the protocol the throughput bottleneck and motivating decades of optimization (presumed abort, Paxos commit, etc.). On RDMA, the calculus inverts: a one-sided CAS or WRITE costs ~1–3µs and zero remote CPU, so protocol designers minimize *round trips* and *remote-CPU involvement* rather than message count per se [2].

## 3 Methodology

Our method is architectural reconstruction with formal verification of the critical protocol. We (i) extract the commit, multiplexing, membership, and concurrency-control mechanisms from the primary papers and their published artifacts [1][2][3][4][5]; (ii) restate the FaRM-style commit protocol in TLA+ and state its serializability as a theorem with a proof sketch; (iii) compare concurrency-control disciplines analytically, deriving abort-probability and blocking-time expressions as functions of RDMA round-trip latency; and (iv) report empirical results strictly from published evaluations, attributing each number to its source rather than re-measuring. Where the literature disagrees — notably the one-sided versus two-sided dispute between [1] and [3] — we identify the workload condition that decides the winner (round-trip count versus per-request CPU work) instead of declaring a victor.

## 4 Deep Dive

### 4.1 FaRM-Style One-Sided Two-Phase Commit

In FaRM, every object in the shared address space carries a header with a version number and a lock bit. A transaction executes optimistically at a coordinator: reads are performed with one-sided RDMA READs that fetch object data plus headers, recording `(address, version)` pairs in a read set; writes are buffered locally in a write set. Commit is a four-phase protocol executed by the coordinator using only one-sided verbs [2]:

1. **Lock.** For each object in the write set, issue an RDMA `compare_and_swap` on the header, attempting to transition the lock bit from free to locked while checking the expected version. Any CAS failure aborts the transaction immediately.
2. **Validate.** Re-read the headers of all objects in the read set with one-sided READs. If any version differs from the recorded version, abort (some concurrent transaction committed a write to a read object).
3. **Replicate.** Append the transaction's commit record — containing the full write set — to the commit logs of the object's backup replicas using one-sided RDMA WRITEs. This is the point of durability: once all backups acknowledge, the transaction is committed regardless of coordinator failure, because any recovery process can replay the log.
4. **Apply and unlock.** WRITE the new object versions (incremented) and clear the lock bits with one-sided WRITEs, then release.

Note the inversion of the classical design: there is no `prepare` message and no remote participant logic. "Voting" is replaced by atomic CAS on memory; "decision" is replaced by log replication into passive backup memory. The remote CPU is never scheduled during a commit.

```tla
---- MODULE FarmCommit ----
EXTENDS Naturals, FiniteSets
CONSTANTS Objects, Txns
VARIABLES ver, locked, log, committed

Lock(t, o) == /\ ~locked[o]
              /\ locked' = [locked EXCEPT ![o] = t]
              /\ UNCHANGED <<ver, log, committed>>

Validate(t, readset) == \A o \in readset : ver[o] = t.readver[o]

Replicate(t) == log' = [log EXCEPT ![t.backup] = log[t.backup] \cup {t.writeset}]

Commit(t) == /\ Validate(t, t.readset)
             /\ \A o \in t.writeset : locked[o] = t
             /\ Replicate(t)
             /\ committed' = committed \cup {t}
====
```

> **Theorem:** *Serializability of FaRM-style commit.* Any two transactions that both reach phase 3 are serializable: there exists a total order of committed transactions consistent with all observed reads.

*Proof sketch.* Lock acquisition (phase 1) guarantees that the write sets of concurrently committing transactions are disjoint — a CAS on an already-locked header fails, so at most one committer holds each object's lock. Validation (phase 2) guarantees that each committer's read set reflects versions that were current at a point when its write locks were held: any concurrent writer that committed a change to a read object must have held that object's lock, contradicting the reader's successful validation unless the writer committed strictly before the reader's validation point. Hence the serialization point of each transaction can be placed at its validation instant, and conflicting operations are ordered by lock acquisition. Log replication (phase 3) makes the decision durable before it is externally visible in phase 4, so failures cannot expose partial effects. ∎

The protocol's cost is dominated by round trips: one RTT for the CAS batch, one for validation reads, one for log replication, one for apply — a constant independent of cluster size, with all operations within a phase issued in parallel across objects.

### 4.2 Coroutine Request Multiplexing over Completion Queues

Microsecond RDMA latency creates a utilization paradox: a thread that blocks on each round trip wastes thousands of cycles per request, but spawning an OS thread per outstanding request wastes memory and scheduling overhead. The resolution adopted by FaSST — and increasingly by the whole RDMA transaction literature — is *coroutine-per-request* multiplexing [3].

A single worker thread runs an event loop over a shared completion queue (CQ). Each incoming transaction is assigned a lightweight coroutine with its own stack (tens of kilobytes). When the coroutine posts an RDMA verb and must wait, it *yields* rather than blocks; the event loop polls the CQ, matches completions to suspended coroutines by work-request ID, and resumes them. Thousands of transactions are thus in flight on one thread, and the thread never idles while any request has pending work.

### 4.3 Membership, Leases, and Failure Detection

One-sided protocols create a failure-detection problem: if no remote CPU participates in the commit path, a failed machine cannot be detected by its silence in protocol messages — there are no protocol messages. FaRM therefore separates the data plane (one-sided, CPU-bypass) from a control plane built on ZooKeeper-style coordination [6].

A configuration manager (CM), itself replicated via ZooKeeper, maintains the authoritative cluster membership and issues *leases* to every machine. Each machine must periodically renew its lease; if a lease expires without renewal, the CM declares the machine failed and drives reconfiguration: regions owned by the failed machine are reassigned, and backup replicas are promoted. Leases — rather than heartbeats with timeouts in the data path — give a clean failure detector: any machine holding a valid lease is by definition a member, and the CM's decisions are linearizable through ZooKeeper's Zab protocol [6].

Recovery exploits the commit protocol's structure. Because phase 3 replicates the commit log to backups with one-sided WRITEs *before* the decision is applied, a coordinator that fails mid-commit leaves its intent in backup memory. During reconfiguration, the new primary for each affected region scans the replicated logs and replays any committed-but-unapplied transactions, then clears stale locks held by the dead coordinator. New transactions can proceed during recovery because lock ownership is recorded in object headers, not in coordinator-local state [2].

### 4.4 Concurrency Control: Timestamp Ordering versus Two-Phase Locking

With coordination reduced to microseconds, the choice of concurrency control becomes the decisive performance variable. The literature offers three answers.

**Timestamp ordering (TO).** Each transaction receives a timestamp from a cluster-wide synchronized clock — FaRM implements clock synchronization by broadcasting local clocks with one-sided RDMA WRITEs and applying a Marzullo-style interval intersection [1]. Each object carries read and write timestamps. A read with timestamp *ts* succeeds iff *ts* ≥ write-ts(object); a write succeeds iff *ts* ≥ read-ts(object) and *ts* ≥ write-ts(object), with the Thomas write rule allowing stale writes to be silently ignored. TO never blocks and never deadlocks, but aborts on any timestamp-order violation, and clock skew directly converts into spurious aborts.

**Two-phase locking with NoWait (DrTM).** DrTM uses RDMA CAS to lock *and fetch* remote records before entering an Intel RTM hardware transaction; no I/O is permitted inside the HTM region, so all remote data must be locked and copied locally first [4]. Locking uses NoWait: if a CAS fails, the transaction aborts immediately rather than waiting. This eliminates deadlock by construction (no waiter ever holds a lock while waiting), at the cost of aborting under contention that a waiting protocol might have ridden out.

**Optimistic validation (FaRM).** As formalized in §4.1: reads are lock-free, writes lock only at commit, and validation replaces deadlock-prone waiting with abort-and-retry. This is timestamp ordering's optimistic cousin — ordering is established by validation instants rather than assigned timestamps.

| Discipline | Blocks? | Deadlock? | Abort condition | Best workload |
|---|---|---|---|---|
| Timestamp ordering | Never | Impossible | ts-order violation (incl. clock skew) | Read-heavy, low skew |
| 2PL NoWait (DrTM) | Never | Impossible | Lock contention | Partitionable OLTP |
| Optimistic validation (FaRM) | Never | Impossible | Read-set invalidation | Low contention, multi-object |
| Classical 2PL | Yes | Possible | Deadlock timeout | High contention (rare on RDMA) |

The striking pattern: on microsecond fabrics, *every* competitive design refuses to block. Blocking for even tens of microseconds wastes the throughput that RDMA bought; all three disciplines convert would-be waiting into aborts, betting that retry at microsecond latency is cheaper than coordination to avoid the retry. Under low contention, FaRM's optimistic validation aborts least, because reads never conflict. Under partitionable OLTP with good locality, DrTM's NoWait locking wins by colocating execution with data via HTM.

## 5 Empirical Results and Correctness Arguments

**Correctness.** The serializability theorem of §4.1 covers the FaRM-style protocol. Two further properties are argued from the design. *Durability:* a transaction is decided at the instant its commit record is replicated to all backups (phase 3); any later failure is masked by log replay during lease-driven reconfiguration (§4.3). *Liveness:* because no phase ever blocks on a remote CPU — every wait is on a NIC completion with a bounded timeout — a transaction either commits, aborts on a failed CAS or validation, or is aborted by lease expiry of a participant, after which recovery replays or discards it.

**Performance.** Published head-to-head numbers define the envelope (all from the primary evaluations, cited to source):

- **HERD** [5]: 26M operations/s at ~5µs average latency on 187 nodes for key-value GET/PUT — the ceiling for single-key RDMA access, and the number that bounds any transaction built atop KV primitives.
- **FaSST** [3]: 3.55M transactions/s *per machine* on a 50-node cluster (ConnectX-3, TATP benchmark), rising to 8.7M on a faster Connect-IB cluster; the same paper reports FaRM at 1.9M and DrTM at 0.93M (SmallBank) on equivalent hardware — a 1.9× and 3.8× margin for two-sided datagram RPC over one-sided designs on that workload.
- **FaRM** [1]: order-of-magnitude latency and throughput improvements over TCP/IP-based main-memory systems, with RDMA READ latency of 1–3µs; transactions add the four-phase commit at a small constant multiple of this base.
- **DrTM** [4]: demonstrates that HTM offload makes single-partition transactions nearly free in CPU terms, but distributed locking via RDMA CAS remains the bottleneck — consistent with the analysis that remote atomic throughput, not local execution, bounds 2PL designs.

The *interpretation* matters more than the ranking. FaSST beats FaRM not because two-sided verbs are intrinsically faster — per-verb, one-sided is faster — but because FaSST's transactions need fewer *round trips*: a UD RPC carries an entire multi-key request and response in one RTT, while FaRM's one-sided design pays one RTT per dependent pointer chase [3][5]. The decision rule that emerges is quantitative: one-sided wins when the protocol needs ≤ 2 sequential round trips per transaction; two-sided RPC wins when request logic is CPU-bound or when indirection would multiply one-sided RTTs. This is why DrTM's successors [7] are hybrids, selecting the verb family per phase.

## 6 Limitations

**Atomic scope.** One-sided atomics operate on 8-byte words; any lock or version scheme must fit in a CAS-able header, which constrains object metadata design and rules out multi-word atomic updates without heavier protocols.

**Connection scalability.** RC QPs carry per-connection NIC state; at hundreds of nodes with thread-per-connection designs, QP cache thrashing collapses throughput [3]. UD-based designs (FaSST, HERD's reply path) sidestep this but sacrifice one-sided verbs and reliability, pushing retransmission logic into software.

**False failure detection.** Lease-based membership trades detection latency against false positives; a stop-the-world GC pause exceeding the lease timeout triggers full reconfiguration and log replay — expensive and, under load, potentially cascading.

**Optimistic abort storms.** FaRM-style validation degrades sharply under write contention: the abort probability grows with the product of read-set size and commit rate, and unlike 2PL there is no queueing to serialize hot spots. High-contention workloads (e.g., TPC-C warehouse rows) remain the worst case for every non-blocking discipline surveyed.

**Hardware specificity.** DrTM depends on Intel RTM, whose availability and abort behavior vary across CPU generations [4]; HERD-class designs assume lossless RDMA fabrics (InfiniBand or RoCE with PFC/ECN), and performance collapses on lossy Ethernet without datacenter bridging.

**Evaluation comparability.** The headline numbers above come from different clusters, benchmarks, and years; they bound the design space but do not constitute a controlled experiment.

## 7 Conclusion

RDMA one-sided distributed transactions reorganized the field around a single question: *what is the cheapest set of network round trips that still guarantees serializability and durability?* FaRM's answer — optimistic reads, CAS-based locking, validation, and one-sided log replication, all without remote-CPU involvement — reduced the commit to a constant handful of microsecond round trips and proved the design serializable. The counter-designs sharpened rather than refuted it: HERD showed when CPU bypass costs more than it saves, FaSST showed that coroutine-multiplexed two-sided RPC wins when per-transaction logic exceeds a couple of round trips, and DrTM showed that HTM can absorb local execution entirely while leaving RDMA CAS as the distributed primitive. Lease-based membership in the ZooKeeper tradition supplies the failure detection that CPU-bypass designs cannot provide themselves, and the universal refusal to block — in timestamp ordering, NoWait locking, and optimistic validation alike — is the deepest lesson: at microsecond coordination cost, abort-and-retry dominates wait-and-coordinate. The open frontier is per-phase verb selection — hybrids in the DrTM+H lineage [7] — and carrying these protocols onto CXL-attached memory pools, where the NIC disappears but the one-sided/two-sided trade-off survives in new form.
