# Oblivious RAM for Encrypted Cloud Storage: Path ORAM Tree Access with Recursive Position Maps, Circuit ORAM Deterministic Eviction, Stash Overflow Bounds, and Onion ORAM Bandwidth

## Abstract

Oblivious RAM (ORAM) hides *which* data a client accesses on an untrusted cloud server, closing the metadata leakage encryption leaves exposed. This thesis unifies four pillars of tree-based ORAM: (i) **Path ORAM**, where each access reads and rewrites one randomly assigned root-to-leaf path; (ii) **recursive position maps**, shrinking client storage from *O(N)* to *O(1)* via auxiliary ORAM trees; (iii) **Circuit ORAM**, replacing randomized eviction with deterministic reverse-lexicographic two-pass eviction for near-optimal circuit size *O((D + log² N) log N)·ω(1)*; and (iv) **Onion ORAM**, escaping the Goldreich–Ostrovsky Ω(log *N*) bandwidth bound with server-side homomorphic computation for *constant* bandwidth. We derive the **Chernoff tail bound** on stash overflow, compare concrete bandwidth figures, and connect theory to systems like ZeroTrace and Signal's private contact discovery.

## 1. Introduction

Cloud storage separates the *custodian* of bits from the *owner* of bits. Symmetric encryption hides content but not *access*: the server still observes the sequence of read and write addresses, and this pattern is extraordinarily informative — query frequency, block correlations, and, in encrypted databases, full record reconstruction attacks [1][2].

Oblivious RAM, introduced by Goldreich and Ostrovsky in 1987/1996 [3][4], is the formal answer to this problem. An ORAM is a compiler that transforms any RAM program into one whose physical memory probes are statistically or computationally independent of the logical access pattern. The central cost metric is the **bandwidth blowup**: the multiplicative overhead in the number of memory blocks transferred per logical access. Goldreich and Ostrovsky proved that any ORAM in the balls-and-bins model incurs Ω(log *N*) overhead [3], a lower bound subsequently sharpened and generalized to arbitrary parameters by Komargodski and Lin [5], and to statistical versus computational security by Weiss and Wichs [6].

The modern era of ORAM is the era of the *tree-based* paradigm. Path ORAM (Stefanov et al., CCS 2013 [7]; JACM 2018 [8]) distilled the construction to sixteen lines of pseudocode and demonstrated that simplicity and practicality are compatible with provable security. Yet Path ORAM leaves three engineering problems unresolved, each of which this thesis treats in depth:

1. **Client storage.** The position map requires *O(N)* client memory. Recursion fixes this but multiplies bandwidth.
2. **Eviction randomness.** Greedy randomized eviction complicates circuit evaluation for secure computation; Circuit ORAM (Wang, Chan, Shi, CCS 2015 [9]) supplies a deterministic alternative with tight circuit complexity.
3. **The logarithmic barrier itself.** Onion ORAM (Devadas et al. [10]) shows that when the server performs homomorphic computation, constant bandwidth is achievable — the lower bound is a property of the *passive-server* model, not of obliviousness per se.

Our contributions are expository and analytic: full protocol detail, a first-principles Chernoff derivation of the stash tail bound, a quantified bandwidth hierarchy, and connections to deployed systems. The intended reader has graduate background in cryptography and probability.

## 2. Background

### 2.1 The ORAM Security Definition

We consider a client with small trusted local storage interacting with an untrusted server hosting *N* logical blocks of *B* bits each. Let *y⃗ = (op₁, …, opₘ)* be a sequence of logical operations. An ORAM compiler *C* maps *y⃗* to a physical access sequence *A(C(y⃗))*. Security requires that for any two equal-length logical sequences *y⃗, z⃗*, the distributions of physical access patterns be indistinguishable:

> **Definition (ORAM security):** For all PPT adversaries *𝒜*, |Pr[𝒜(A(C(y⃗))) = 1] − Pr[𝒜(A(C(z⃗))) = 1]| ≤ negl(λ).



### 2.2 The Goldreich–Ostrovsky Lower Bound

Goldreich and Ostrovsky [3][4] proved **Ω(log *N*)** amortized overhead for ORAMs in the balls-and-bins model; Komargodski and Lin [5] extended the bound to all parameter regimes, and Path ORAM and Circuit ORAM show it is *tight*. Crucially, the bound **assumes a passive server** — with server-side homomorphic computation, it evaporates [10]. This model sensitivity is the central conceptual point of this thesis.

### 2.3 Tree-Based ORAM: Common Structure

All tree-based ORAMs share the following skeleton:

- The server stores a **binary tree** of height *L = ⌈log₂ N⌉*, each node a *bucket* of *Z* blocks (real or dummy), all encrypted under a semantically secure scheme.
- Each block *a* is assigned a uniform random leaf label *pos[a] ∈ {0,1}^L* (the **position map**).
- **Invariant:** block *a* resides either in the client stash or in some bucket on the root-to-leaf path *𝒫(pos[a])* [7][8].

An access reads the entire path, remaps the block to a fresh random leaf, and writes the path back, greedily pushing stash blocks as deep as their leaf labels permit.

| Construction | Year | Bandwidth | Client storage | Server compute | Key idea |
|---|---|---|---|---|---|
| Goldreich–Ostrovsky [3][4] | 1996 | *O(log³ N)* | *O(1)* | None | Hierarchical levels, periodic reshuffle |
| Path ORAM [7][8] | 2013 | *O(log N)* | *O(N)* pos. map | None | Single-path access, stash |
| Recursive Path ORAM [8] | 2013 | *O(log² N)* | *O(1)* | None | Position map in smaller ORAMs |
| Circuit ORAM [9] | 2015 | *O(log N)* | *O(1)* | None | Deterministic eviction, tight circuit |
| Onion ORAM [10] | 2016 | *O(1)* | *O(1)* | Polylog (AHE) | Server-side homomorphic eviction |
| ZeroTrace (impl.) | 2017 | *O(log N)* | — | None (SGX) | Path ORAM in enclaves |

## 3. Methodology

Our methodology is analytic and comparative. We (i) formalize the Path ORAM access protocol and its recursive variant following Stefanov et al. [8] and the lecture treatment of Chan ; (ii) reconstruct the stash-overflow tail bound using the infinite-tree coupling argument and a Chernoff bound, as in the original analysis; (iii) specify Circuit ORAM's deterministic two-pass eviction and its circuit-size accounting [9]; (iv) describe Onion ORAM's homomorphic eviction and its malicious-server defenses [10]; and (v) compare bandwidth, client storage, and failure probability across constructions, grounded in the concrete parameterization *Z = 4* buckets and 4 KB blocks commonly used in implementations.

We adopt the standard notation: *N* blocks, tree height *L*, bucket size *Z*, stash *𝒮*, position map *pos*, block size *B* bits, security parameter *λ*.
## 4. Deep Dive

### 4.1 Path ORAM Access Protocol and the Position Map

The Path ORAM access procedure, `Access(op, a, data*)`, is famously compact. We reproduce its structure in pseudocode:

```python
def access(op, a, data_star=None):
  x = position[a]       # 1. look up leaf label
  position[a] = random_leaf() # 2. remap to fresh random leaf
  stash |= read_path(x)    # 3. read entire path P(x) into stash
  if op == 'write':
    stash.update(a, data_star)
  data = stash.find(a)     # 4. linear scan of stash
  write_path(x, stash)     # 5. greedy eviction back along P(x)
  return data
```

Step 5 is the heart of the construction. Buckets are processed from leaf to root; a block *b* in the stash is evicted into the deepest bucket on *𝒫(x)* that (i) lies on *𝒫(pos[b])* and (ii) has free space. Because *x* is uniformly random and independent of *a* (the remap in step 2 happens *before* the read), the observed path *𝒫(x)* is a uniform random root-to-leaf path, perfectly hiding *a*. The stale path read at the old label and the fresh label stored for the next access together guarantee that no two accesses to the same block ever touch the same path — the standard "no linkability" argument [7][8].

> **Theorem:** Path ORAM is a secure ORAM with *O(log N)* bandwidth blowup for block size *B = Ω(log² N)*, client storage *O(N)* (position map) plus an *O(log N)·ω(1)* stash, and failure probability negligible in the security parameter [8].

Bandwidth is one path of *L + 1* buckets × *Z* blocks per access: *O(log N)* blocks with *Z = 4*. The subtlety is entirely in the stash analysis of §4.3.

### 4.2 Recursive Position Maps: From O(N) to O(1) Client Storage

The position map stores *N* leaf labels of *L* bits each: *O(N log N)* bits of client storage — unacceptable for a thin client or a hardware enclave with kilobytes of trusted memory. The recursive construction [8][11] stores the position map itself in a *smaller* ORAM on the server:

- ORam₀ holds data; the position map of ORamᵢ is stored in ORamᵢ₊₁, a factor *χ ≥ 2* smaller.
- After *X = ⌈log N / log χ⌉* levels, the final position map has constant size and lives on the client.

An access to block *a₀* in ORam₀ recursively accesses block *⌊a₀/χ⌋* in ORam₁ (a *write*, updating the entry to the fresh random leaf), which recursively accesses ORam₂, and so on [8]. Each recursion level multiplies bandwidth by the cost of one ORAM access, so with *χ = Θ(log N)* the total bandwidth becomes *O(log² N)* blocks and the number of round trips grows linearly in recursion depth.

The trade-off is sharp and worth stating precisely:

- *Non-recursive*: *O(N log N)* bits client-side, *O(log N)* bandwidth.
- *Recursive, uniform block size B*: bandwidth *O(log² N)* blocks; client storage *O(1)* blocks [8].
- *Recursive, non-uniform*: position-map blocks of *χ log N* bits with *B = Ω(log² N)* data blocks yields bandwidth *O(B log N + log³ N)* bits, i.e., blowup *O(log N)* — recursion need not asymptotically worsen bandwidth if block sizes are tuned [8].

In practice, implementations such as ZeroTrace keep a non-recursive map inside SGX enclave memory for moderate *N*, switching to recursion only when the map exceeds the enclave page cache .

### 4.3 Stash Overflow Bounds via Chernoff Analysis

The stash is Path ORAM's safety valve: blocks that cannot be placed on the accessed path accumulate client-side. If the stash ever exceeds its provisioned capacity, the construction fails catastrophically (blocks must be dropped). The central probabilistic result of [8] is:

> **Theorem:** For bucket size *Z ≥ 4* and any stash size *R = ω(log N)*, the probability that the stash exceeds *R* blocks after polynomially many accesses is negligible in *N*.

*Proof sketch (infinite-tree coupling + Chernoff).* Couple the real ORAM with an *infinite* tree of unbounded-capacity buckets. For any subtree *T*, a block competes for *T*'s buckets only if its uniform random leaf label falls in *T*'s leaf set, so the competing count *X_T* is dominated by Binomial*(n, p)* with *p = |leaves(T)|/N* and mean *μ = n·p*. Post-processing pushes excess blocks upward and the stash absorbs the root's overflow [8, §5]. For a subtree of *s* leaves, capacity *Z·s* exceeds *E[X_T] = s·(n/N)·c* for load constant *c < Z*; the overflow event *{X_T ≥ Z·s}* is a large deviation, and Chernoff gives:

```
Pr[X_T ≥ (1+δ)·μ] ≤ exp(−μ·δ²/(2+δ))
```

Choosing *δ* with *(1+δ)μ = Z·s* gives an exponentially small tail in *s*; a union bound over all subtrees and time steps yields failure probability *N^{-ω(1)}* for *R = ω(log N)*. Concretely, *Z = 5* gives failure below *2^{-80}* with stash ≈ 100 blocks at *N = 2²⁰* [9]. ∎

Two consequences follow. First, the bound is *why* Path ORAM is deployable: a ~100-block stash makes overflow a cryptographic failure event. Second, the analysis leans entirely on fresh uniform leaf labels, so deterministic schemes like Circuit ORAM must reprove stash bounds under their own dynamics [9].

In TLA⁺, the core safety invariant checked by model-based testers is:

```tla
StashInvariant == Cardinality(Stash) <= MaxStash
PathInvariant == \A b \in Blocks :
  b \in Stash \/ (\E n \in Path(Pos[b]) : b \in Bucket[n])
```

### 4.4 Circuit ORAM: Deterministic Two-Pass Eviction

Path ORAM's greedy eviction is randomized (leaf labels are random) and, more importantly, its *circuit complexity* — the size of a boolean circuit evaluating one access, the metric that matters for garbled-circuit MPC and FHE — is *O((D + log² N)·log² N)* naively, because eviction requires oblivious sorting of the stash. Circuit ORAM [9] restructures eviction to be **deterministic** and sorting-free:

1. **Eviction order.** Paths are evicted in deterministic *reverse lexicographic* order of leaf labels: consecutive evictions touch paths that are maximally "different," guaranteeing every bucket is visited regularly regardless of the (adversarially chosen) access pattern.
2. **Two passes.** Each eviction performs a *read pass* down the path (identifying, for each bucket, the deepest block that can legally move down) followed by a *write pass* that performs the moves. Both passes are straight-line, data-oblivious scans — no sorting network, no randomness beyond the initial leaf assignment.
3. **Metadata/data separation.** Buckets store tiny metadata blocks (leaf labels, occupancy) separately from large data blocks, so the circuit touches only *O(log N)*-bit metadata during eviction decisions.

> **Theorem:** For block size *D = Ω(log² N)*, Circuit ORAM achieves circuit size *O((D + log² N)·log N)·ω(1)* with negligible failure probability — nearly matching the Ω(*D log N*) circuit lower bound inherited from Goldreich–Ostrovsky [9].

Concretely, at *N = 2²⁰*, 4 KB blocks, and failure probability *2^{-80}*, Circuit ORAM's access circuit uses roughly **0.97M AND gates** versus ~56.6M for naive Path ORAM — a ~58× reduction [9]. Bandwidth remains *O(log N)*, and a combinatorial stash analysis yields an *O(log N)* stash with overwhelming probability. Circuit ORAM thus settles the 27-year-old question of the Goldreich–Ostrovsky bound's tightness under the circuit metric, and is the construction of choice for ORAM inside secure computation.

### 4.5 Onion ORAM: Escaping the Logarithmic Lower Bound

The Goldreich–Ostrovsky bound assumes the server is a *passive* store. Onion ORAM [10] changes the model: the server performs **polylogarithmic homomorphic computation** per access, and bandwidth collapses to a constant.

The construction layers additively homomorphic encryption (Damgård–Jurik or BGV without bootstrapping) like onion skins, so:

- Buckets hold *homomorphically encrypted* blocks; the client sends small encrypted *select vectors* and the server homomorphically computes the permuted buckets itself, so client communication per access is *O(1)* blocks.
- Security against a *malicious* server is achieved without SNARKs via verifiable structure (permuted writes with MAC-like checks under the homomorphic layer) so deviations are detected [10].

> **Theorem:** Onion ORAM achieves *O(1)* worst-case bandwidth blowup with *polylog(N)* server computation per access, under standard assumptions (Decisional Composite Residuosity / RLWE), in the semi-honest and malicious server models [10].

The conceptual moral is crisp: **the logarithmic lower bound is a statement about passive storage, not about obliviousness**. The price of constant bandwidth is computational: the server must evaluate homomorphic additions over the path, which in practice (Damgård–Jurik ciphertext expansion ~2–3×, BGV noise management) makes Onion ORAM a theoretical landmark rather than a deployed system. Its descendants — Constant-overhead ORAM via somewhat homomorphic encryption with tighter parameters — remain an active research frontier.

## 5. Empirical Results and Proofs

### 5.1 Bandwidth Comparison at Concrete Parameters

Fix *N = 2²⁰* blocks (1M records), *B = 4 KB*, *Z = 4*, *L = 20*. The following table gives per-access concrete costs:

| Construction | Blocks transferred | Bytes on wire | Client state | Failure prob. |
|---|---|---|---|---|
| Insecure baseline | 1 | 4 KB | 0 | 0 |
| Path ORAM [8] | ~84 (path) | ~336 KB | pos. map ~2.5 MB + stash | negl. |
| Recursive Path ORAM [8] | ~84 × 3 levels | ~1 MB | *O(1)* | negl. |
| Circuit ORAM [9] | ~84 | ~336 KB | *O(1)* + stash | ≤ 2^{-80} |
| Onion ORAM [10] | *O(1)* (~4–8) | ~32 KB (incl. HE expansion) | *O(1)* | negl. |
| GO96 hierarchical [4] | *O(log³ N)* ~8000 | ~32 MB | *O(1)* | negl. |

The engineering reality is plain: Path ORAM pays ~84× bandwidth for simplicity; Circuit ORAM matches it with far smaller circuits; Onion ORAM pays in server CPU instead — attractive in principle, but homomorphic evaluation latency currently dominates.

### 5.2 Stash Occupancy: Theory vs. Simulation

The Chernoff analysis of §4.3 predicts rapidly decaying tails. Empirical validation from the literature:

- At *Z = 4*, *N = 2²⁰*: simulated maximum stash occupancy over 2²⁰ accesses stays below **~30 blocks** with overwhelming observed frequency; the proven bound requires *R = ω(log N)* asymptotically but concrete constants are far kinder [8][9].
- At *Z = 5*: failure probability below *2^{-80}* with stash ≈ 100 blocks [9] — the standard deployment parameterization.
- Increasing *Z* from 4 to 5 roughly *squares* the tail decay rate, since the Chernoff exponent scales with the gap *(Z − c)* between bucket capacity and expected load.

### 5.3 Deployed Systems

Theory has met practice in three notable deployments:

1. **ZeroTrace** — Path ORAM inside Intel SGX enclaves for oblivious data structures; the stash and position map fit enclave memory for moderate *N*.
2. **Signal's private contact discovery** — ORAM-flavored oblivious structures inside SGX so clients can check contact registration without revealing their address book.
3. **Obladi** — an oblivious OLTP database layering serializable transactions over ORAM.

These systems uniformly choose **Path ORAM**: implementation simplicity and auditability outweigh asymptotic refinements against honest-but-curious providers.

## 6. Limitations

1. **Semi-honest server assumption.** Path ORAM and Circuit ORAM assume the server follows the protocol (returning correct ciphertexts). A malicious server can fork the tree, roll back writes, or return stale paths undetectably. Malicious-secure variants (Onion ORAM [10], authenticated tree ORAMs with Merkle proofs) close this gap at significant cost.
2. **Timing and volume leakage.** ORAM hides *which* blocks are accessed, not *how many* accesses occur or their timing. Padding to constant rate is required against traffic-analysis adversaries — an often-ignored deployment cost.
3. **Client storage vs. bandwidth tension.** Non-recursive Path ORAM needs *O(N)* client memory; recursion recovers *O(1)* client storage but multiplies bandwidth by recursion depth (§4.2). There is no free lunch within the passive-server model — the lower bound [5] forbids it.
4. **Onion ORAM's practicality gap.** Constant bandwidth is purchased with homomorphic computation whose concrete cost (ciphertext expansion, noise growth, malicious-server verification) remains prohibitive for interactive cloud storage [10].
5. **Stash bounds are asymptotic.** The Chernoff argument guarantees *negligible* failure, but concrete deployments must pick *(Z, R)* from simulations; a mis-parameterized stash is a silent catastrophic failure mode, not a graceful degradation.
6. **Concurrency.** The analyses above are single-client. Concurrent ORAM (multiple mutually distrusting clients, e.g., TaoStore/Obladi-style proxies) introduces synchronization that can reintroduce leakage channels through contention.

## 7. Conclusion

Oblivious RAM for encrypted cloud storage has matured from Goldreich and Ostrovsky's hierarchical constructions [3][4] into a small family of tree-based schemes whose trade-offs are precisely understood. **Path ORAM** [7][8] provides the practical baseline: one random path per access, a Chernoff-bounded stash, and *O(log N)* bandwidth. **Recursive position maps** [8][11] trade bandwidth for client storage along a clean, tunable curve. **Circuit ORAM** [9] shows the Goldreich–Ostrovsky bound is tight under the circuit metric, replacing randomness with deterministic reverse-lexicographic eviction and shrinking access circuits by nearly two orders of magnitude. **Onion ORAM** [10] demonstrates that the logarithmic barrier is model-relative: give the server homomorphic computation and bandwidth becomes constant.

The through-line is one design question: *where does the work go?* To the wire (Path ORAM), to recursion depth (recursive Path ORAM), into the circuit (Circuit ORAM), or onto the server's CPU (Onion ORAM). For today's encrypted cloud storage — passive object stores, honest-but-curious providers — Path ORAM with *Z ≥ 4* and a ~100-block stash remains the rational choice, as ZeroTrace and Signal attest. The frontier is narrowing Onion ORAM's practicality gap and cheap malicious-secure tree ORAMs. Until then, the logarithm stands — exactly where Goldreich and Ostrovsky said it would.
