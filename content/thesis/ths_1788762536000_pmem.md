# Failure-Atomic Programming for Persistent Memory: From ADR Persistence Domains to CXL-Attached Non-Volatile Memory

## Abstract

The arrival of byte-addressable non-volatile memory collapsed the long-standing boundary between memory and storage, forcing programmers to reason about *concurrency* and *crash consistency*. This thesis develops a unified account of failure-atomic persistent memory programming, from the Intel Optane DC Persistent Memory Module (DCPMM) and the Persistent Memory Development Kit (PMDK) to the emerging Compute Express Link (CXL) persistent-memory fabric. We formalize the x86 persistency model — cache-line write-back primitives, store fences, and the ADR/eADR persistence domains — and show how PMDK's `libpmemobj` builds multi-object failure-atomic transactions from hardware's meager guarantee of aligned 8-byte atomic stores, using undo logging for snapshots and redo logging for allocation metadata. We analyze DAX filesystems that bypass the page cache for direct load/store access, and CXL 3.0's Global Persistent Flush protocol that extends persistence domains across a fabric. Finally, we survey crash-consistency verification, from dynamic checkers (PMTest, Yat) and symbolic execution (AGAMOTTO) to machine-checked program logics (Spirea, Perennial), and argue that durable linearizability is the right correctness criterion for persistent concurrent data structures.

## 1 Introduction

For five decades, systems software rested on a clean dichotomy: *memory* was fast, byte-addressable, and volatile; *storage* was slow, block-addressable, and durable. The Intel Optane DC Persistent Memory Module (DCPMM), built on 3D XPoint, destroyed it [2]: a DIMM on the memory bus holding terabytes of data that survived power loss, accessible with ordinary loads and stores at near-DRAM latency. Every store instruction became a potential durability event, and every data-structure update a candidate for corruption by an untimely crash.

The central problem is **failure atomicity**: a group of persistent stores must either all survive a crash or none do [1]. Hardware offers almost nothing: on x86 the only failure-atomic primitive is an *aligned 8-byte store* [2], so anything larger — a pointer pair, a B-tree node split, a list splice — can be *torn* by power failure. Worse, stores are unordered with respect to persistence: a later store may reach media before an earlier one because caches evict lines arbitrarily. The programmer must therefore master two orderings — *visibility* (the consistency model) and *persistence* (explicit flush and fence instructions) [9].

This thesis makes three contributions. First, a precise account of the x86 persistence domain — ADR, eADR, and the roles of `CLFLUSH`, `CLFLUSHOPT`, `CLWB`, and `SFENCE` [9]. Second, a dissection of the PMDK programming model showing how undo and redo logging lift 8-byte atomicity to transactional failure atomicity, and how the protocol was formally specified and model-checked [3][4]. Third, a forward look: with Optane discontinued, the ideas migrate to CXL-attached persistent memory, where Global Persistent Flush (GPF) re-creates persistence domains at fabric scale, and to a verification ecosystem — PMTest, Yat, AGAMOTTO, Spirea — learning to *prove* crash consistency rather than merely test for it [5][7][8].

The remainder of this thesis is organized as follows. Section 2 reviews the hardware and software background. Section 3 describes our methodology. Section 4 contains the deep technical dive across five subsections. Section 5 presents empirical results and formal proofs. Section 6 discusses limitations, and Section 7 concludes.

## 2 Background

### 2.1 The x86 persistency model

On modern x86 processors, a store instruction writes to the L1 cache; the cache line may sit dirty in the cache hierarchy for an unbounded time before eviction. Persistence — arrival in the *persistence domain* — is therefore decoupled from execution. Three instructions move data toward persistence [9]:

| Instruction | Semantics | Ordering |
|---|---|---|
| `CLFLUSH` | Flush line, invalidate | Serializing (strongly ordered) |
| `CLFLUSHOPT` | Flush line, invalidate | Weakly ordered; needs `SFENCE` |
| `CLWB` | Write back line, *retain* in cache | Weakly ordered; needs `SFENCE` |

The canonical persist pattern is: `store; CLWB(addr); SFENCE;`. The `SFENCE` guarantees that all prior flushes are *globally ordered before* any subsequent store, establishing a **persist-before** edge that programmers use to build ordering protocols [9]. Crucially, `CLWB` is preferred over `CLFLUSHOPT` in hot paths because the line remains cached for subsequent reads.

Only an aligned 8-byte store is failure-atomic on Intel processors [2]. If power fails mid-store of a larger object, the persistent contents may mix old and new bytes arbitrarily. `CMPXCHG16B` does *not* extend this guarantee. All larger failure-atomic updates must be synthesized in software.

### 2.2 Persistence domains: ADR and eADR

**Asynchronous DRAM Refresh (ADR)** uses residual power-fail energy to flush the memory controller's write-pending queue (WPQ) into the DIMMs. The persistence domain thus begins at the memory controller; CPU caches lie *outside* it, which is why explicit `CLWB`/`SFENCE` sequences are mandatory [2]. **Extended ADR (eADR)** enlarges the domain to include the caches: on power loss the platform flushes dirty lines automatically, so `SFENCE` alone orders persistence (eADR shipped with 3rd-gen Xeon Scalable plus Optane PMem 200 series) [2].

### 2.3 The PMDK library stack

The Persistent Memory Development Kit (PMDK) is Intel's open-source library collection for persistent memory programming [1][2]:

- **`libpmem`**: low-level primitives — `pmem_persist()` (flush + drain), `pmem_flush()`/`pmem_drain()`, `pmem_memcpy_persist()`, `pmem_map_file()` for DAX mappings.
- **`libpmemobj`**: transactional object store. Pools, a root object, typed persistent pointers (`PMEMoid`, `persistent_ptr<T>`), and `TX_BEGIN`/`TX_END` transactions with undo/redo logging [4].
- **`libpmemblk`**: arrays of fixed-size blocks with block-atomic writes.
- **`libpmemlog`**: append-mostly persistent logs.

PMDK transactions provide *atomicity* and *durability*, but not full ACID: consistency holds only for PMDK metadata, and isolation requires application-level locking [4].

### 2.4 DAX filesystems

Direct Access (DAX) removes the page cache from the I/O path: files are `mmap`'d directly onto persistent memory, so loads and stores hit the media. Linux ext4 and XFS support DAX; `MAP_SYNC` further guarantees that metadata is synchronously durable on `msync`/`fsync`. Research filesystems such as NOVA (log-structured for PM) push further, optimizing specifically for PM's byte-addressability [8]. Userspace PM libraries typically sit atop DAX-mapped files.

### 2.5 Correctness criteria

The accepted correctness criterion for persistent concurrent objects is **durable linearizability**: every operation appears to take effect atomically at some point between invocation and response, *and* the state that survives a crash corresponds to a prefix of the linearization — i.e., recovery never exposes effects of operations that never "happened" before the crash. Testing tools check approximations of this; proof frameworks target it directly.

## 3 Methodology

Our investigation proceeds in four stages. **(i) Hardware semantics:** reconstructing the x86 persistency model to identify which orderings the ISA guarantees and which must be synthesized [2][9]. **(ii) Library archaeology:** tracing PMDK's transactions through published internals — undo/redo logging, the commit protocol, type-safe persistent pointers — and cross-checking against the formal CSP specification validated with FDR4 [3][4]. **(iii) Fabric extrapolation:** mapping DCPMM-era concepts onto CXL 3.x, where Type-2/3 devices and Global Persistent Flush generalize ADR to a switched fabric. **(iv) Verification survey:** comparing dynamic, symbolic, and deductive techniques by crash-state coverage and whether they certify *absence* of bugs [5][7][8].

> **Theorem (Persist-ordering synthesis):** On x86 with ADR, any desired persist-before partial order over stores can be realized using only `CLWB`/`CLFLUSHOPT` and `SFENCE`, by flushing each store's line and fencing before the dependent store executes [9].

Throughout, we distinguish *ordering* (which persists first), *atomicity* (all-or-nothing), and *durability* (survives the crash) — three properties PM programming must separate.

## 4 Deep Dive

### 4.1 The x86 Persistence Domain: ADR, eADR, and Ordering Primitives

The persistence domain is the hardware state guaranteed to survive power loss, and its boundary is the programming contract. Under ADR it contains the WPQ and DIMMs; the caches are outside. Programs therefore follow a two-level discipline: make data *visible* (ordinary stores under TSO), then *persistent* (flush + fence), and finally *ordered* where the algorithm requires it.

Consider the classic ordered pair: a persistent linked-list insertion that writes a new node `N` and then swings the predecessor's `next` pointer to `N`. If `next` persists before `N`'s payload, a crash yields a dangling pointer. The correct protocol is:

```c
/* N freshly allocated in PM; payload stores first */
N->key = k;  N->val = v;  N->next = head;
pmem_persist(N, sizeof(*N));   /* CLWB each line + SFENCE */
head->next = N;               /* now safe: payload already durable */
pmem_persist(&head->next, sizeof(head->next));
```

`pmem_persist` expands to a `CLWB` loop over the range followed by `SFENCE` (the *drain*), and is a no-op beyond the fence on eADR platforms where caches are inside the domain [9]. The performance art of PM programming is minimizing these fences: batching flushes, using non-temporal stores (`MOVNT`) that bypass caches and enter the WPQ directly, and overlapping persist barriers with useful work.

**Persistence is not linearizable with respect to visibility:** thread A may *read* B's store from cache while it is not yet *persistent*, so a crash can lose an update some thread already observed — legal under durable linearizability only if the observing operation had not returned. This visibility/persistence gap causes most PM concurrency bugs and motivates the persist-aware models of Section 4.5.

### 4.2 The PMDK Programming Model: libpmemobj Transactions via Undo/Redo Logging

`libpmemobj` turns a DAX-mapped file into a *pool* with a distinguished root object — the anchor from which all persistent state is reachable after a restart [1]. Because virtual addresses change across mappings, pointers are stored as `PMEMoid` (pool UUID + offset) or, in the C++ bindings, as `persistent_ptr<T>`, which prevents mixing volatile and persistent pointers at the type level [4]. Plain persistent fields use the `p<T>` template, whose overloaded assignment operators automatically enlist the field in the ambient transaction.

Transactions are the heart of the library. The C interface exposes them as macros:

```c
TX_BEGIN(pop) {
    /* allocate inside the transaction: redo-logged */
    TOID(struct node) n = TX_NEW(struct node);
    /* snapshot before modify: undo-logged */
    TX_ADD_FIELD(root, head);
    D_RW(n)->next = D_RO(root)->head;
    D_RW(root)->head = D_RW(n);
} TX_ONCOMMIT {
    /* ... */
} TX_ONABORT {
    /* ... */
} TX_END
```

Two logging disciplines cooperate to guarantee failure atomicity [3]:

1. **Undo logging (snapshots).** `TX_ADD` copies *old* contents of each modified range into a persistent undo log, flushed before in-place modification; recovery replays it to restore the pre-transaction state. Uncommitted changes are invisible to recovery but *visible* to concurrent threads — hence external locking is required [4].
2. **Redo logging (allocations and commit).** Allocation metadata is staged in a redo log; the commit is a redo-logged sequence ending in a single 8-byte failure-atomic commit record. Recovery replays complete redo logs and discards incomplete ones — write-ahead logging miniaturized to cache-line granularity [3].

The txPMDK formal specification models transactions as a concurrent object with crash events, validated against an abstract durable specification (ddTMS) via FDR4 refinement checking — including combination of the PMDK redo log with software TM (TML/NOrec) [4]. It is a rare case of an industrial PM library carrying a machine-checked concurrency-plus-crash specification.

Undo logging roughly doubles write traffic for modified ranges; PMDK batches log flushes to amortize the two `SFENCE` barriers per transaction the protocol requires [3].

### 4.3 DAX Filesystems and the Kernel Interface

DAX-capable filesystems (ext4, XFS) map file pages directly to persistent memory, eliminating the page cache and the `read`/`write` path [8]. With `mmap(MAP_SHARED)` plus `MAP_SYNC`, `msync(MS_SYNC)` gives failure atomicity at page granularity — the substrate for `libpmem`'s `pmem_map_file`.

**NOVA** is a log-structured PM filesystem keeping per-inode logs in PM for fast crash recovery and atomic metadata operations. **SquirrelFS** encodes Synchronous Soft Updates' ordering rules in Rust's type system via the *typestate pattern*, making illegal orderings *compile-time errors* [8]. Its evaluation on real Optane DCPMM hardware shows performance competitive with NOVA and WineFS. And **PMOs** (persistent memory objects) propose an OS primitive — `psync` — with explicit state machines (Detached, Read, Write, Persisting, Copying) and shadow paging, so crash-consistent updates need no userspace logging at all [7].

The lesson: the kernel/userspace boundary for PM is still being negotiated, with designs ranging from "filesystem does everything" (NOVA) to "compiler checks everything" (SquirrelFS) to "userspace libraries do everything" (PMDK).

### 4.4 CXL Persistent and Type-2 Memory: A Fabric-Scale Persistence Domain

With Intel's Optane exit, the industry's persistent-memory bet moved to **Compute Express Link (CXL)**, a PCIe-based coherent interconnect. CXL defines three device classes:

| Type | CXL.cache | CXL.mem | Role |
|---|---|---|---|
| Type 1 | ✓ | ✗ | Smart NICs; coherent caching, no host-managed memory |
| Type 2 | ✓ | ✓ | Accelerators (GPUs) with device memory coherent to host |
| Type 3 | ✗ | ✓ | Memory expanders/pooling; host-managed device memory (HDM) |

Memory can be exposed as ordinary volatile HDM or, with appropriate device support, as *persistent* capacity. The key addition is **Global Persistent Flush (GPF)** in CXL 3.0: Phase 1 flushes all caches and buffers in the domain down to the persistent device; Phase 2 signals completion — a fabric-wide `SFENCE`. GPF is ADR generalized from one socket's WPQ to a switched fabric, making the persistence domain a *distributed* property negotiated between host, switches, and endpoints.

Latency to CXL memory is higher and less uniform than local DCPMM was, and fabric-wide GPF makes naive `CLWB`-per-line porting expensive. The emerging consensus mirrors the DCPMM endgame: coarse-grained failure-atomic primitives (transactions, `psync`-like syscalls, automatic cache flush) over hand-rolled flush/fence sequences. The PMDK-era lesson — target *libraries with specified crash semantics*, not raw persistency primitives — transfers directly.

### 4.5 Crash-Consistency Verification: PMTest, Yat, and Formal Methods

Because crashes can interleave with *every* persistency event, the crash-state space is enormous: any subset of unpersisted stores may be lost, in any order consistent with the persistency model. Verification tools differ in how they tame this space.

**Dynamic checkers.** **PMTest** (ASPLOS 2019, Liu et al.) records traces of PM operations and checks them against assertions: low-level `isPersist(addr)` and `isOrderedBefore(A, B)`, plus high-level wrappers such as transaction checkers verifying all modified objects were written back at commit [5]. The checking engine encodes x86 persistency rules (and alternatives like HOPS) and, on real code, found 3 new bugs in PMFS and PMDK-based applications while running 7.1× faster than the prior state of the art [5]. **Yat** (Lantz et al.) provides a similar validation framework oriented at PM software stacks. **XFDetector** targets cross-failure bugs spanning crash and failover.

**Symbolic execution.** **AGAMOTTO** (OSDI 2020) applies symbolic execution to explore crash states systematically, while **Witcher** and **Jaaru** extend the approach to PM *libraries* and concurrent programs. These tools find deep bugs but, being testing-based, cannot certify absence.

**Deductive verification.** The frontier is machine-checked proof. **Spirea** (Vindum & Birkedal) is a higher-order separation logic embedded in Iris/Coq for crash-safe PM programs under a release/acquire persistency model; **Perennial** extends crash separation logic to persistency; **Pierogi** and the PArmv8/Px86 logics (Raad, Vafeiadis et al.) give program logics for weak persistency architectures. These have verified durable-linearizable queues, stacks, and maps — but full-featured, heavily optimized PM indexes with torn-write reasoning remain at the edge of feasibility.

> **Theorem (Durable linearizability, informal):** A concurrent object is durably linearizable iff every crash-recovery cycle leaves the persistent state equal to the state produced by *some* linearization prefix of the operations invoked before the crash — no operation that "took effect" after the last persisted prefix may be visible post-recovery.

The trajectory is clear: from ad-hoc flush/fence reasoning, to assertion-based dynamic checking, to proof. The cost of proof (10–20× the code size) confines it to critical structures today, but the crash-consistency bugs that PMTest-class tools keep finding in production PMDK code suggest the investment is warranted.

## 5 Empirical Results and Proofs

PMTest's evaluation remains the landmark dynamic-verification result: beyond injected bugs, it discovered **3 previously unknown crash-consistency bugs** in PMFS and PMDK-based applications at **7.1× lower overhead** than the prior state of the art [5]. The bug classes were exactly those theory predicts — missing persist barriers (`isOrderedBefore`) and missing write-backs (`isPersist`) — confirming that even experts misjudge the visibility/persistence gap.

On the formal side, the txPMDK specification effort validated the library's transaction protocol — redo-logged allocation, undo-logged snapshots, 8-byte-atomic commit record — against a durable transactional specification using FDR4 refinement checks over a most-general client model with nondeterministic crashes [4]. This is a *proof of protocol correctness* modulo the hardware model: it certifies that, assuming the persistency primitives behave as specified, no crash interleaving corrupts transactional state.

For application-level structures, the strongest available results are the machine-checked durable-linearizability proofs in Iris-family logics (Spirea, Perennial extensions) for moderately complex lock-free structures — persistent queues, Treiber-style stacks, durable maps — including idempotent recovery that tolerates crash-during-recovery via well-founded measures. Proof effort remains high, but the artifacts exist and check in Coq.

Hardware measurements from the Optane era ground the theory: `CLWB`+`SFENCE` sequences cost tens of nanoseconds per line when pipelined but serialize persist ordering; eADR removes explicit flushes at the cost of platform support; SquirrelFS's evaluation on physical Optane DCPMM shows a verified-ordering filesystem matching or beating unverified competitors [8]. The numbers say the same thing as the logic: crash consistency is affordable when it is *designed in*, and punishing when bolted on.

## 6 Limitations

This account has several honest boundaries. **First, the hardware moved.** Intel discontinued Optane in 2022; DCPMM-specific results (e.g., ADR capacitor hold-up times, 3D XPoint write endurance) do not transfer verbatim to CXL-attached or battery-backed-DRAM persistent memory, whose latency, granularity, and failure modes differ. **Second, the 8-byte atomicity ceiling.** Everything above — transactions, filesystems, proofs — is scaffolding around hardware's refusal to provide multi-word failure atomicity; a future ISA primitive (failure-atomic cache-line write, say) would obsolete large parts of this machinery. **Third, verification is incomplete.** Dynamic tools (PMTest, Yat, AGAMOTTO) find bugs but prove nothing about absence; deductive tools prove absence but only for small, carefully modeled programs under idealized persistency models that may not capture real platform quirks (partial cache-line writes, firmware-level reordering). **Fourth, the concurrency story is thin.** PMDK transactions deliberately punt on isolation [4]; composing failure atomicity with high-performance concurrency (lock-free PM indexes under durable linearizability) remains the hardest open engineering problem. **Finally, CXL persistent memory is nascent**: GPF semantics, heterogeneous persistence domains, and disaggregated failure handling are specified but barely deployed, so the fabric-scale claims of Section 4.4 are architectural projections, not measured results.

## 7 Conclusion

Persistent memory programming is the discipline of making *persistence* as principled as *concurrency*. The x86 platform taught the vocabulary: domains bounded by ADR/eADR, ordering from `CLWB` and `SFENCE`, failure atomicity bootstrapped from one 8-byte atomic store into full transactions via undo and redo logging [2][3][9]. PMDK industrialized it into pools, persistent pointers, and crash-safe transactions — then submitted the protocol to model checking [4]. DAX filesystems and OS primitives (NOVA, SquirrelFS, PMOs) redistributed responsibility across kernel, compiler, and library [7][8]; verification grew from assertions (PMTest) through symbolic execution (AGAMOTTO) to machine-checked separation logics (Spirea, Perennial) [5]. As the substrate shifts to CXL fabrics with Global Persistent Flush, specifics change but invariants do not: separate ordering from atomicity from durability, distrust any store you have not fenced, and — where correctness matters — *prove* the recovery argument rather than merely testing it. The crash is not an edge case in persistent memory programming. It is the specification.
