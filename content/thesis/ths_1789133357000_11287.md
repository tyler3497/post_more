# Certified Compilation with CompCert: Semantic Preservation, Simulation Diagrams, and the Proof Engineering of a Verified C Compiler

## Abstract

CompCert is the first realistic, optimizing C compiler accompanied by a machine-checked proof of semantic preservation end to end. This thesis develops the theory and proof engineering of certified compilation: a compiler from Clight, a large subset of C, through about fifteen intermediate languages to assembly for PowerPC, ARM, x86, RISC-V, and AArch64 targets [1]. The central device is the *simulation diagram* — a commuting relation between source and target executions that decomposes whole-compiler correctness into per-pass lemmas, composed by transitivity into a global preservation result [2]. We formalize the behavioral semantics underlying the correctness statement, the forward-versus-backward simulation bridge via target determinacy, and the *memory injections* relating source and target memory states [3]. We analyze the extension to floating-point arithmetic via the Flocq formalization of IEEE-754 [4], compositional refinements repairing whole-program-only correctness [7], the secure-compilation extension SECOMP containing undefined behavior [6], and the trusted-computing-base analysis enumerating what the proof does *not* guarantee [8], closing with a comparison against CakeML [5] and open problems.

## 1. Introduction

Every safety argument about software rests, at its foundation, on a silent assumption: that the compiler is semantically transparent. Source-level verification, static analysis, and testing all reason about *programs as written*; the artifact that actually executes is the output of a compiler — a large, complex, aggressively optimizing program that performs intricate symbolic transformations. Compiler bugs are not hypothetical: miscompilations of safety-critical code have been observed in production compilers, and the very act of turning optimizations on or off can change the computed value of a floating-point program [4]. The question *"Can you trust your compiler?"* is therefore not rhetorical but foundational [2].

CompCert answers this question with a radically stronger guarantee than testing can provide. Developed by Xavier Leroy and collaborators starting in 2005, CompCert is a compiler from Clight — a large subset of the C99 standard — to assembly code for several mainstream architectures, and it carries a *machine-checked proof*, developed in the Coq proof assistant, that the generated assembly behaves as prescribed by the formal semantics of the source program [1]. The verification is not an afterthought or a model of the compiler: the compiler itself is *written* in Coq (in a purely functional style, extracted to OCaml), and the proof is about the actual compiler code.

Three design decisions make this achievement possible, and each is the subject of a deep technical literature:

1. **Semantics as contract.** Each intermediate language in the compilation chain has a formal operational semantics mechanized in Coq. Correctness is a *relation between behaviors* defined by these semantics, not a property of any particular execution.
2. **Decomposition by simulation.** Rather than proving whole-compiler correctness monolithically, each compiler pass is proved correct by a *simulation diagram*: if the source program takes a step and the states are related by an invariant, the target program takes matching steps and the invariant is re-established. Per-pass simulations compose, so the global theorem follows by transitivity of behavior refinement [2].
3. **Engineering discipline.** Verified passes coexist with *verified validators*: for hard optimizations (notably register allocation), CompCert runs an unverified optimizer and then checks its output with a proved-correct validator, falling back to unoptimized code if validation fails [1]. This hybrid tactic keeps the trusted proof effort tractable.

> **Theorem (CompCert semantic preservation, informal):** For every Clight source program `S` and assembly program `T` such that `compile(S) = T` (compilation succeeds), every observable behavior of `T` — termination with an exit code, divergence, or going wrong — is also an observable behavior of `S`, modulo the elimination of undefined behavior. In particular, if `S` has no undefined behavior, then `T` behaves exactly as `S` prescribes [1].

This thesis unpacks that theorem: what it means, what it costs, and what it leaves out.

## 2. Background

### 2.1 Verified compilers before CompCert

Formally verified compilers predate CompCert by decades — McCarthy and Painter verified a compiler for arithmetic expressions in 1967 — but all earlier efforts targeted *toy languages* or were verified only on paper [1]. The gap between a toy expression compiler and a realistic C compiler is enormous: real C has a subtle memory model, unspecified evaluation order, unstructured control flow (`goto`, `switch`), and a preprocessor-scale feature set. CompCert's breakthrough was to show that the verification of a *realistic* compiler — one that could compile actual embedded avionics software — was feasible with roughly the same effort as developing the compiler itself: about six person-years for the initial PowerPC backend [1].

### 2.2 The three classical approaches to compiler trust

The literature distinguishes three strategies for obtaining trustworthy compilation, and CompCert deliberately combines two of them:

| Approach | Guarantee | Proof burden | Example |
|---|---|---|---|
| **Verified compiler** | Universal: *for all* inputs, compilation is correct | Prove the compiler correct once | CompCert [1], CakeML [5] |
| **Translation validation** | Existential: *this run's* output is correct | Validate each compilation; no compiler proof | Necula's GCC validator; Alive2 for LLVM |
| **Verified validator** | Universal *validator* + arbitrary optimizer | Prove the checker, not the optimizer | CompCert's register allocator [1] |

Leroy observed that a verified validator composed with an unverified compiler yields a guarantee as strong as a verified compiler — *provided the validator is smaller and simpler than the compiler* — and CompCert exploits this for its most algorithmically delicate pass [2]. This hybrid design is arguably CompCert's most important proof-engineering contribution: it converts hard algorithmic verification problems into easier *checking* problems.

### 2.3 Coq as implementation language and proof medium

CompCert is written in Coq's Gallina language — a purely functional, total language — and extracted to OCaml for execution. This has a double consequence. First, the compiler code *is* the object of verification: there is no gap between the verified artifact and the running artifact (modulo extraction and the OCaml runtime). Second, the parts of a real compiler that are inherently imperative or effectful — parsing, pretty-printing, assembly emission — are kept *outside* the verified core and implemented directly in OCaml, which shrinks the proof burden but enlarges the trusted computing base [8].

## 3. Methodology

Our methodology is a close technical reconstruction of CompCert's proof architecture, organized around three questions: *what is the correctness statement*, *how is it decomposed*, and *how do the pieces compose*.

### 3.1 Observable behavior as the correctness criterion

CompCert defines program behavior as a trace of observable events: system calls, volatile accesses, and annotations, culminating in one of three outcomes — *termination* with an exit code, *divergence* (infinite execution producing a possibly infinite trace), or *going wrong* (undefined behavior, e.g., an illegal memory access) [1]. Correctness is *behavior refinement*: the set of behaviors of the compiled program is included in the set of behaviors of the source program, where "going wrong" in the source licenses arbitrary target behavior (the standard treatment of undefined behavior in C). This is a *backward* refinement statement — target behaviors refine source behaviors — and it is the property a user of the compiler actually wants: every safety property proved of the source (absence of wrong behaviors) transfers to the executable.

### 3.2 Forward vs. backward simulation

The subtlety is that compiler passes are proved correct via *forward* simulation (source steps are matched by target steps), while the desired end-to-end property is *backward* refinement (target behaviors are explained by source behaviors). The bridge between them is a classical result:

> **Theorem (Forward-to-backward):** If the target language is *determinate* — each state has at most one successor behavior — then forward simulation implies backward simulation, and hence behavior refinement [2].

CompCert therefore proves that every *target* intermediate language is determinate, while source languages are permitted nondeterminism (C's unspecified evaluation order is modeled by a *reduction strategy* that picks one behavior). This asymmetric treatment is the key technical device that makes per-pass forward proofs compose into a global backward theorem [2]. In the Haskell model below, `fwd` captures the local diagram and `det` the determinacy hypothesis:

```haskell
-- States of the source and target languages, related by invariant R
data Sim s t = Sim
  { rel  :: s -> t -> Bool          -- simulation invariant R
  , fwd  :: s -> s -> t -> Maybe t  -- diagram: source step matched by target steps
  , det  :: t -> t -> Bool          -- target determinacy (at most one successor)
  }

-- The global property the diagram buys: every target trace is a source trace.
refinement :: Sim s t -> [t] -> Bool
refinement sim targetTrace =
  det sim `implies` all (`explainedBy` sim) targetTrace
  where implies p q = not p || q
        explainedBy _ _ = True  -- proved in Coq: forward + determinate => backward
```

### 3.3 Memory injections

Compiler passes transform the memory layout: spilling moves locals to stack slots, inlining merges activation records, and the backend concretizes abstract blocks into machine addresses. The *memory injection* is the relational device that tracks this: a partial function from source blocks to target blocks plus offsets, together with validity and permission conditions [3]. If pointer `p = (b, δ)` is valid in source memory `M` and the injection maps `b ↦ (b', δ')`, then the corresponding target pointer `(b', δ + δ')` must be valid in the target memory `M'` and hold a related value. Injections compose across passes, so a whole-compiler memory relation is built incrementally — at the cost of substantial proof bureaucracy, which later work (notably CompCertM and the denotational framework of [7]) seeks to algebraize.

## 4. Deep Dive

### 4.1 The intermediate-language tower

CompCert compiles through roughly fifteen intermediate languages, each with a mechanized semantics. The major strata are:

1. **Clight** — a large subset of C99 with structured control flow; the verification starts here rather than at full C because the C preprocessor, `goto`-heavy idioms, and some dark corners of the standard are excluded [1].
2. **Cminor** — a minimal imperative language; the Clight→Cminor front end (verified in [3]) performs the bulk of C-specific elaboration: expression evaluation order is fixed, block-scoped variables become explicit stack blocks, and the memory model is simplified.
3. **RTL** (register transfer language) — a control-flow-graph language with pseudo-registers; most optimizations (constant propagation, CSE, dead-code elimination, inlining) operate here.
4. **LTL / Linear / Mach** — progressively concretized: register allocation produces LTL, linearization flattens CFGs, and Mach introduces the machine-specific stack frame layout.
5. **Asm** — the target assembly language with a formal operational semantics per architecture.

*Why so many languages?* Each pass's simulation proof is tractable only if the semantic gap between its input and output languages is small. The tower is proof engineering: many small, provable steps instead of one unprovable leap. The price is that every language needs a semantics, a determinacy proof, and often a memory-model adaptation — the fixed cost that makes verified compilation expensive [1].

### 4.2 The anatomy of a simulation diagram

Consider an optimization pass `transf : RTL → RTL`. Its correctness lemma has the following shape, proved once per pass:

> **Theorem (Per-pass forward simulation):** There exists a relation `R` between source states `S` and target states `T` such that: (i) initial states are related; (ii) whenever `S —e→ S'` is a source step producing observable event `e` and `R(S, T)` holds, there exist target steps `T —e→* T'` (zero or more steps, permitting *stuttering*) with `R(S', T')`; (iii) related states agree on observable behavior [2].

Two refinements handle real-world complexity. *Stuttering* (`→*` rather than `→`) allows passes that eliminate instructions: several source steps may map to zero target steps, as long as an ordinal *measure* decreases to rule out infinite stuttering. *Option simulation* handles passes that may fail or that change the set of behaviors in controlled ways. The diagram below (conceptually) shows the commuting square with the invariant as horizontal edges, the source step on the left, and the matching target steps on the right:

```tla+
---- MODULE SimDiagram ----
EXTENDS Naturals
VARIABLES S, Sp, T, Tp       \* source/target states before and after
CONSTANT R                   \* simulation invariant, a relation on states
Diagram ==
  /\ R[S, T]                 \* invariant holds before
  /\ S -> Sp                  \* one source step (labeled transition)
  => \E Tp : T ->* Tp /\ R[Sp, Tp]   \* matching target steps restore R
THEOREM FwdImpliesRefinement ==
  ASSUME Determinate(T) PROVE \A trace \in Behaviors(T) : trace \in Behaviors(S)
====
```

### 4.3 Verified validators: the register-allocation case study

Register allocation — mapping infinitely many pseudo-registers onto finitely many machine registers with spilling — is the most algorithmically intricate pass in CompCert, using iterated register coalescing in the style of George and Appel. Proving such an algorithm correct directly would be formidable. CompCert instead runs the *unverified* allocator and then validates its result with a small, proved-correct checker that verifies the coloring is a valid interference-graph coloring and that the rewritten code respects it; on validation failure, compilation falls back to unoptimized code [1]. The correctness theorem then depends only on the validator. This pattern — *unverified oracle + verified checker* — recurs in verified systems (cf. verified SAT checkers) and is arguably CompCert's most transferable engineering lesson: it decouples algorithmic sophistication from proof burden.

### 4.4 Floating point: Flocq and the limits of the model

Until 2013, CompCert did not verify floating-point compilation. Boldo, Jourdan, Leroy, and Melquiond closed the gap by formalizing IEEE-754 in Coq (the Flocq library) and proving CompCert's FP passes correct — yielding, at the time, the first formally verified compiler that provably preserves the semantics of floating-point programs [4]. Their work exposed how much of "the semantics of C" lives *outside* the compiler proof: the notorious example in [4] shows the same program computing three different results under GCC at different optimization levels (`-O0`, `-O1/2/3`, `-Ofast`) on 32-bit x86, due to excess-precision (x87 80-bit registers) and reassociation — behaviors CompCert's semantics must pin down precisely. The lesson: a verified compiler is only as trustworthy as its formal semantics of the *hardware*, and hardware semantics are where the trusted base gets thinnest [8].

## 5. Empirical Results / Proofs

CompCert's "empirical results" are its proofs and their measured costs — verification produces theorems, not benchmarks. The quantitative record, drawn from [1], [2], and [8], is as follows:

| Metric | Value | Source |
|---|---|---|
| Initial development effort | ~6 person-years (compiler + proof) | [1] |
| Lines of Coq (compiler + proof, circa 2009) | ~42,000 (proof ≈ 60% of total) | [1] |
| Supported source | Large subset of C99 (Clight) | [1] |
| Target architectures | PowerPC, ARM, x86, RISC-V, AArch64, KVX | [1], [8] |
| Performance of generated code | Within ~7–12% of GCC `-O1` on embedded benchmarks | [1] |
| Proof-to-code ratio | Roughly 2:1 in the hardest passes | [2] |

The performance row deserves emphasis: CompCert performs *moderate* optimizations (the verified middle end) and deliberately forgoes the aggressive loop transformations of GCC/LLVM, trading ~10% runtime for a machine-checked guarantee [1]. For safety-critical embedded software — CompCert's original target domain, including avionics — this is the right trade.

Beyond the core artifact, the *proof* results include: the front-end simulation proof for Clight→Cminor with memory injections [3]; the IEEE-754 preservation proof [4]; and, in subsequent work, compositional extensions. CompCertM reframes the simulation theory around *interaction semantics* so that separately compiled modules can be linked with a correctness guarantee — repairing CompCert's original whole-program-only theorem [7]. SECOMP goes further, proving a *secure compilation* criterion (robust preservation of safety properties against adversarial contexts) for compartmentalized C, restricting undefined behavior's blast radius to the compromised compartment [6]. CakeML provides the instructive contrast: a verified compiler for a *functional* language (ML), whose correctness proof must handle garbage collection and closures rather than C's memory model [5] — evidence that the simulation-diagram methodology generalizes across paradigms.

## 6. Limitations

A candid assessment of CompCert must enumerate what the machine-checked proof does *not* establish. The trusted-computing-base analysis of [8] is the authoritative source here:

1. **The semantics gap.** CompCert proves preservation between *its formal semantics* of Clight and *its formal semantics* of assembly. Neither C99-as-written nor the physical processor has a formal semantics; the proof assumes the mechanized models faithfully capture the real artifacts. Bugs have been found in CompCert's own semantics (e.g., the KVX speculative-load modeling issue documented in [8], where a load's defined value was incorrectly fixed to 0 rather than left undefined).
2. **The unverified perimeter.** Parsing, elaboration of full C into Clight, assembly emission (pretty-printing), the linker, the assembler, and the Coq extraction pipeline plus the OCaml runtime are all outside the proof [8]. A bug in the pretty-printer can silently invalidate the guarantee.
3. **Whole-program compositionality.** The original CompCert theorem applies to *whole programs*; separate compilation and linking were initially unverified. Compositional frameworks [7] and CompCertM address this, but at the cost of reworking the simulation theory around open modules.
4. **Language coverage.** Clight excludes `goto` into complex shapes, variable-length arrays, `long double` subtleties, and much of the C standard library; concurrency was addressed only later (CompCertTSO) and remains partial.
5. **Optimization ceiling.** Only optimizations with tractable simulation proofs (or validators) are included; CompCert cannot match GCC/LLVM on floating-point reassociation, vectorization, or polyhedral loop optimization — and for FP, some "optimizations" are unsound under strict IEEE-754 anyway [4].
6. **Proof maintenance.** Each new architecture backend and each new optimization requires new simulation proofs; the proof-to-code ratio means the compiler evolves at a fraction of the speed of GCC/LLVM.

None of these limitations diminishes the result; they *scope* it. A verified compiler moves trust from an unexamined 10-million-line optimizer to an explicitly enumerated trusted base — which is precisely what [8] makes auditable.

## 7. Conclusion

CompCert established that a realistic, optimizing compiler can carry a machine-checked proof of semantic preservation, and in doing so it created the proof-engineering discipline of certified compilation [1]. Its durable technical contributions are the *simulation diagram* as a compositional proof device [2], the *memory injection* as a relational treatment of layout-changing passes [3], the *verified validator* pattern that decouples optimization sophistication from proof burden [1], and the demonstration — via Flocq — that even IEEE-754 floating point can be brought inside the verified perimeter [4]. The research frontier has moved outward from this core: to compositional and denotational reframings that support separate compilation [7], to secure-compilation criteria that contain undefined behavior [6], and to systematic audits of what the proof assumes rather than proves [8].

The deeper lesson is methodological. CompCert succeeded not by verifying an existing compiler but by *co-designing* the compiler with its proof: the intermediate-language tower, the validator pattern, and the forward-to-backward simulation bridge are all design decisions whose primary justification is proof tractability. For any future verified system — verified hypervisors, verified cryptographic implementations, verified ML compilers — the CompCert playbook remains the template: fix the semantics first, decompose by simulation, check what you cannot prove, and write down exactly what you trust.
