# The eBPF Verifier: Abstract Interpretation, Bounded Loops, and Sound Static Analysis for In-Kernel Programs

## Abstract

The Linux kernel's extended Berkeley Packet Filter (eBPF) verifier is arguably the most consequential static analyzer ever deployed: an abstract interpreter that must decide, for every untrusted program before it may execute inside the kernel, whether that program is safe. This thesis formalizes the verifier as an instance of abstract interpretation over a product abstract domain comprising register types, tristate numbers (tnums), signed and unsigned interval bounds, and liveness information. It explains the verifier's state-exploration algorithm — a depth-first symbolic execution of the control-flow graph with subsumption-based state pruning at designated prune points — and analyzes the bounded-loop discipline introduced in kernel 5.3, which replaced the blanket prohibition on back-edges with a provable-termination argument enforced by a one-million-instruction complexity budget. We further examine precision tracking and register liveness as performance refinements that preserve soundness, and evaluate the verifier's speculative-execution discipline — Spectre v1/v2/v4 mitigations — as a second, transient-execution semantics layered over the architectural one. The thesis closes with the verifier's known limitations: false rejections, the compiler–verifier gap, and incompleteness under path explosion.

## 1. Introduction

The extended Berkeley Packet Filter (eBPF) lets untrusted code execute inside the operating system kernel [2][3]. The only thing standing between an arbitrary byte sequence supplied by a user and ring-0 execution is the eBPF verifier, a static analyzer in `kernel/bpf/verifier.c` that must *prove* a program safe before the kernel will JIT-compile and run it. This thesis argues that the verifier is best understood not as an ad hoc collection of checks, but as a large-scale, industrially deployed instance of **abstract interpretation**: it executes the program symbolically over an abstract domain that over-approximates all concrete behaviors, and rejects the program if any abstract state violates the safety policy.

The stakes are unusual. Most static analyzers trade soundness for usability; the verifier cannot, because an unsound acceptance is a kernel vulnerability [5]. At the same time it must be *complete enough* in practice to admit real programs — packet filters, load balancers, tracers — and *fast enough* to verify them at load time. The remainder of this thesis dissects how the verifier navigates this trilemma: the abstract domains it tracks (§4.1–4.2), the state-space exploration and pruning that keep path explosion tractable (§3, §4.3), the bounded-loop discipline that recovers termination arguments (§4.4), precision and liveness refinements (§4.5), and the speculative-execution semantics layered on top for Spectre (§4.5).

## 2. Background

### The eBPF execution model

An eBPF program is a sequence of 64-bit instructions executed by a register machine with eleven 64-bit registers (`r0`–`r10`), where `r10` is a read-only frame pointer, and a fixed 512-byte stack [2][3]. There are no floating-point operations and no direct access to arbitrary kernel memory: programs interact with the kernel through a fixed set of *helper functions* and *maps* (key/value stores), and they run at designated *hooks* — network packet paths (XDP, tc), system-call tracepoints, LSM hooks, and others. A program is loaded with the `bpf(BPF_PROG_LOAD)` system call, verified, JIT-compiled to native machine code, and attached to its hook [2].

### The safety policy

The verifier enforces a conjunctive safety policy [2][3][8]:

- **Memory safety.** Every load and store must target memory the program is entitled to touch: its stack, packet data within `[data, data_end)`, map values, or context fields declared readable by the program type.
- **Type safety.** Pointers and scalars must not be confused; e.g., a program may not return a kernel pointer in `r0`, which would leak addresses to userspace [3].
- **Termination.** The program must provably halt; infinite loops and unbounded recursion are forbidden.
- **No uninitialized reads, no leaks, no deadlocks.** Registers and stack slots must be initialized before use; reference-counted objects must not leak; at most one spinlock may be held at a time.

### Why abstract interpretation

Checking these properties is undecidable in general — the halting problem forbids a perfect decision procedure for termination alone [1]. The verifier therefore *over-approximates*: it computes, for every program point, a set of abstract states guaranteed to include every state reachable by any concrete execution. If no abstract state violates the policy, no concrete execution can either. This is precisely the framework of abstract interpretation. The verifier's originality lies in its domain engineering and its scale: tens of thousands of lines of C deciding safety for untrusted code at load time, on every eBPF load, on production machines [2][5].

## 3. Methodology

Verification proceeds in two broad phases [8][2]:

1. **CFG construction and validation.** The verifier builds the program's control-flow graph: it checks that every jump target lies within the program, that there is no unreachable code, that calls target known helpers or BPF-to-BPF callees, and it records *back-edges* (jumps to earlier instructions) for the loop analysis of §4.4.
2. **Symbolic execution.** Starting from an initial abstract state — `r1` holding a context pointer of the program type's shape, all other registers uninitialized — the verifier simulates each instruction's effect on the abstract state, following both successors of every conditional branch.

Branch exploration is organized as an explicit worklist: at a conditional jump the verifier pushes a copy of the current abstract state onto a stack and continues down one path; when a path reaches `BPF_EXIT` or is pruned, the saved state is popped and the other path explored [8]. Each instruction is interpreted by a *transfer function* — `check_alu_op` for arithmetic, `check_mem_access` for loads and stores, and so on — which either refines the abstract state (e.g., recording that a register now holds a non-NULL map-value pointer) or rejects the program.

Because symbolic execution can explode, the verifier counts every simulated instruction against a budget, `BPF_COMPLEXITY_LIMIT_INSNS`, currently one million [3][8]. Exceeding the budget rejects the program. This bound is load-bearing: it converts the undecidable termination question into a decidable, budgeted one, as §4.4 explains.

> **Theorem: Soundness of the abstract exploration.** *Let α be the abstraction mapping concrete states to abstract states, and let each transfer function be a sound over-approximation (post♯ ⊇ α ∘ post ∘ γ). If exploration of all paths terminates with no policy violation, then every concrete execution of the program satisfies the safety policy.*

The proof obligation is discharged per transfer function: each must over-approximate the concrete semantics of its instruction. Bugs here are soundness bugs — and have historically been CVEs [5].

## 4. Deep Dive

### 4.1 The Tnum abstract domain

The workhorse of the verifier's value analysis is the *tristate number* (`struct tnum`), implemented in `kernel/bpf/tnum.c` [7]:

```c
struct tnum {
    u64 value; /* bits known to be 1 */
    u64 mask;  /* bits whose value is unknown */
};
```

Each bit of an abstracted 64-bit word is in one of three states — known-0, known-1, or unknown (`?`) — so a tnum denotes a set of up to 2^popcount(mask) concrete values. A freshly loaded byte is `(0x00; 0xff)`: the top 56 bits known zero, the low 8 unknown [7]. The domain supports sound abstract arithmetic — `tnum_add`, `tnum_sub`, `tnum_mul`, `tnum_and`, `tnum_or`, `tnum_xor`, shifts — each computing the tightest tnum covering all concrete results. Tnums are *precise* for bitwise operations, where interval domains are hopelessly coarse, and deliberately coarse for multiplication: a pragmatic trade-off.

| Concrete knowledge | tnum `(value; mask)` | Denotation |
|---|---|---|
| constant `0x3` | `(0x3; 0x0)` | `{3}` |
| a byte just loaded | `(0x0; 0xff)` | `{0, …, 255}` |
| any even number | `(0x0; 0xfff…fe)` | `{2k}` |
| fully unknown | `(0x0; 0xfff…ff)` | all 2⁶⁴ values |

Alongside tnums, each scalar register carries *interval* bounds — unsigned (`umin_value`, `umax_value`) and signed (`smin_value`, `smax_value`) — refined by comparisons: after `if r2 < 10 goto`, the taken branch records `umax_value = 9` [7]. The product of the tnum domain and the interval domains is the verifier's value abstraction: tnums for bit-level reasoning, intervals for range checks, each compensating for the other's weakness.

### 4.2 Register state and the type lattice

Values alone do not imply safety; the verifier must also know *what kind of thing* each register holds. Every register is described by `struct bpf_reg_state` [7]:

```c
struct bpf_reg_state {
    enum bpf_reg_type type; /* SCALAR, PTR_TO_CTX, PTR_TO_MAP_VALUE, ... */
    struct tnum var_off;    /* value abstraction */
    s64 smin_value, smax_value;
    u64 umin_value, umax_value;
    s32 off;                /* constant offset from pointer base */
    int ref_obj_id;         /* reference tracking */
    /* ... liveness, precision, spill info ... */
};
```

The `type` field lives in a lattice. `NOT_INIT` sits at the bottom — any read is rejected; scalars and the pointer types (`PTR_TO_CTX`, `PTR_TO_MAP_VALUE`, `PTR_TO_PACKET`, `PTR_TO_STACK`, …) form the middle; joins of incompatible types collapse toward rejection. Transfer functions enforce the lattice discipline: pointer arithmetic on `PTR_TO_MAP_VALUE` is allowed only with bounded scalar offsets, keeping the pointer type with updated `off` and bounds; arithmetic between two pointers is rejected outright. A `bpf_map_lookup_elem` call transitions `r0` to `PTR_TO_MAP_VALUE_OR_NULL`, forcing the program to test for NULL before dereference — the verifier *learns* the refinement on each branch [8]. Returning a pointer-typed `r0` at `BPF_EXIT` is rejected, closing the address-leak channel [3].

### 4.3 State pruning by subsumption

Naive path enumeration is exponential in the number of branches. The verifier's answer is *state pruning*: at designated prune points in the CFG it records the abstract state; when it later arrives at the same point with a state *subsumed* by a recorded one, the current path is abandoned — every continuation was already proven safe [4][8].

State A subsumes state B when A describes a superset of B's possible concrete behaviors: for each live register, A's type is compatible, A's interval bounds contain B's, and A's tnum mask covers B's unknown bits — equivalently, B's tnum refines A's [7]. Two refinements make this practical. First, *register liveness* (`regalive.c`): only registers that are live — possibly read before being overwritten — participate in the comparison, so irrelevant divergence no longer defeats pruning [4]. Second, prune points are placed *periodically* rather than at every jump, because early designs that recorded state at every branch stored mostly useless entries [8]. The decade-long evolution of this mechanism — from a simple optimization to the sophisticated, liveness-aware subsumption engine of today — is chronicled by Chaignon and Tardy [4].

### 4.4 Bounded loops and provable termination

Until kernel 5.3, the verifier simply rejected any back-edge: loops were forbidden, and programmers emulated them with compiler unrolling (`#pragma unroll`) [1][3]. In 2019, bounded-loop support landed: the verifier now follows back-edges, symbolically unrolling loop iterations, and accepts the program when exploration demonstrates that every loop terminates *before the complexity budget is exhausted* [1][3]. Termination is thus proved by construction — the verifier only accepts executions it has fully simulated — with the one-million-instruction budget as the backstop: a loop whose bound the verifier cannot pin down explodes the budget and is rejected [8].

The discipline has sharp edges. Loops must be *single-entry* — the analysis relies on dominator information, so jumping into the middle of a loop body is rejected [7]. And some programs are safe yet unverifiable: the verifier may fail to prove termination of a correct loop, a textbook instance of incompleteness [1]. For such cases the kernel offers an escape hatch, `bpf_loop()` (kernel 5.17): the loop mechanics move into the helper, so the verifier knows *by construction* that the iteration count is bounded, and verification of loop-heavy programs collapses from tens of seconds to fractions of a second [1].

> **Theorem: Termination.** *Every program accepted by the verifier terminates after at most BPF_COMPLEXITY_LIMIT_INSNS abstract steps, because acceptance requires the complete symbolic exploration of all paths, and exploration halts at the budget.*

### 4.5 Precision tracking and the Spectre discipline

Two further mechanisms deserve attention. *Precision tracking* marks registers whose exact abstract value must be preserved for sound pruning; on-demand *precision backtracking* propagates precision requirements backward through the instruction stream when a check — such as a memory access — demands it [7]. This keeps the common case cheap, with imprecise registers comparing loosely, while guaranteeing that safety-critical values are never over-approximated away at prune points.

The second mechanism addresses a different adversary: *transient execution*. The verifier's abstract semantics models the architectural behavior of the CPU, but speculative execution can transiently violate it — the Spectre class of attacks. For unprivileged programs on x86-64, the verifier therefore enforces a second, speculative safety discipline [3][6]:

| Attack | Verifier / JIT mitigation |
|---|---|
| Spectre v1 (bounds-check bypass) | branchless bounds enforcement (index masking) plus verification of speculative paths |
| Spectre v2 (branch-target injection) | retpoline, or speculation barriers where retpoline is unavailable |
| Spectre v4 (speculative store bypass) | `nospec` barriers (lowered to `lfence`) inserted after stores the verifier identifies as bypassable [6] |

The insertion pass (`sanitize_speculation`) rewrites the program after analysis, placing barriers where the verifier observed attacker-influenced speculation windows — for example, after pointer spills to the stack that a subsequent load might speculatively bypass [6]. These mitigations are explicitly scoped: they protect *kernel* secrets from *malicious* programs, not a program's own secrets from itself, and unprivileged eBPF is disabled by default on most distributions precisely because the transient-execution attack surface keeps evolving [3].

## 5. Empirical Results and Soundness Arguments

What evidence supports the claim that this machinery works? First, *scale*: the verifier routinely admits production programs — XDP packet processors, load-balancer datapaths — spanning thousands of instructions, and the first comprehensive account of the runtime (through kernel 6.7) characterizes its safety properties as exhaustively enforced across four verification passes [2]. Second, *measured performance engineering*: the `bpf_loop()` case study shows verification time for a loop-heavy program falling from nearly 30 seconds to 0.15 seconds — roughly a 200× improvement — achieved purely by giving the verifier a termination argument it can check syntactically [1].

Third, *adversarial review*. The 2024 Linux Foundation security audit subjected the verifier to expert manual review and found genuine soundness-relevant defects — for instance in scalar bound tracking across 32-bit versus 64-bit addition — which were subsequently fixed upstream [5]. This is the expected lifecycle of a soundness-critical analyzer: the *design* is sound by over-approximation, while the *implementation* is hardened by continuous scrutiny and CVE-driven fixes. The audit's lesson is methodological as much as technical: a verifier of this complexity cannot be validated by testing alone; it requires the same adversarial attention as the attack surface it guards [5].

Formally, the guarantee is a *relative* soundness claim: modulo implementation bugs, acceptance implies that every concrete execution — architectural and, for the mitigated classes, speculative — respects the policy. No stronger claim is possible for an undecidable property; the verifier's achievement is making the "modulo bugs" caveat small enough, and the accepted language rich enough, to underpin an industry [2][5].

## 6. Limitations

The verifier is sound but *incomplete*: it rejects programs that are in fact safe. False rejections arise from precision loss at control-flow joins, from loops whose bounds the verifier cannot reconstruct out of low-level bytecode, and from the blunt complexity budget [1][8]. Programmers experience this as the verifier being "a well-meaning but rule-bound and picky bureaucracy" [1].

A second limitation is the *compiler–verifier gap*: the verifier analyzes LLVM's output, not the programmer's C, and the two tools' models of legal code drift apart — constructs the compiler emits routinely can baffle the verifier [4][5]. Third, verification *cost*: large programs can take seconds to verify at load time, and pathological ones are rejected only after burning the full budget [1][8]. Fourth, the Spectre mitigations are architecture- and privilege-scoped, and unprivileged eBPF remains disabled by default — a concession that the transient-execution problem is managed, not solved [3][6]. Finally, soundness is an implementation property, not a proven theorem: the audit history shows that the gap between the abstract-interpretation design and its tens-of-thousands-of-lines C embodiment is where vulnerabilities live [5].

---

## 7. Conclusion

The eBPF verifier is a landmark in applied program analysis: an abstract interpreter — over tnums, intervals, types, liveness, and precision — that performs sound static analysis of untrusted code at kernel load time, proves termination of bounded loops by exhaustive symbolic exploration under a complexity budget, prunes the resulting state space by subsumption, and even reasons about speculative execution to blunt Spectre. Its limitations — incompleteness, the compiler gap, verification cost, and the ever-present risk of implementation bugs — are the honest price of decidability in an undecidable domain. Future work points toward machine-checked soundness proofs of the transfer functions, richer abstract domains that shrink the false-rejection rate, and formal models of the speculative semantics. Whatever form it takes, the verifier's core insight will endure: when untrusted code must run in the kernel, *proof* must precede execution.
