# Verified Cryptography at Scale: HACL*, EverCrypt, and Vale — Machine-Checked Memory Safety, Constant-Time Discipline, and Verified Assembly for Cryptographic Primitives

## Abstract

We examine Project Everest's program of end-to-end verified cryptography: HACL*, a verified modern cryptographic library written in the Low* subset of F* and extracted to C via KreMLin; Vale, a verified DSL for high-performance assembly carrying machine-checked Hoare-logic proofs; and EverCrypt, a cross-platform cryptographic provider unifying both under an agile API. We analyze the verification methodology — dependent types, refinement types, and SMT-backed proof automation in F* — the memory-safety model of Low*, the leakage-based constant-time security model guarding against timing side channels, and the embedding of assembly semantics that enables Vale to prove register- and memory-level properties. We quantify the empirical results: over 124,000 lines of verified specifications, code, and proofs producing 29,000 lines of C and 14,000 lines of assembly, with performance matching or exceeding the best unverified implementations and deployment in production systems including the Windows kernel, Firefox, and Python. We conclude with honest limitations: trusted computing bases, compiler soundness assumptions, and the boundary of the verified fragment.

## 1 Introduction

Cryptographic libraries are among the most security-critical software artifacts in existence, and historically among the most bug-prone. The *Heartbleed* vulnerability in OpenSSL (2014), the *Lucky13* padding-oracle attack against TLS's CBC mode, and *goto fail* in Apple's TLS stack all share a common structure: subtle implementation defects in code whose correctness is extraordinarily difficult to audit by inspection or conventional testing [1][2][3]. In response, Project Everest (2016–2021) — a collaboration between Microsoft Research, Carnegie Mellon University, INRIA, and the MSR-INRIA joint center — set out to build a verified HTTPS stack in which the cryptographic components carry **machine-checked proofs** of functional correctness, memory safety, and side-channel resistance [4].

The effort rests on three pillars, each addressed in this work:

1. **HACL\*** — a verified cryptographic library of modern primitives (NaCl-style APIs, AES-GCM, SHA-2/3, ChaCha20-Poly1305, Ed25519, Curve25519, HMAC, HKDF), written in Low\*, a memory-safe imperative subset of the F\* dependently-typed language, and extracted to portable, auditable C by the KreMLin compiler [1].
2. **Vale** — a verified assembly language: a domain-specific language for writing hand-tuned assembly whose programs carry machine-checked proofs of correctness, first on a Dafny backend (USENIX Security 2017, Distinguished Paper Award) [5] and later re-embedded in F\* (POPL 2019) [6].
3. **EverCrypt** — a cross-platform cryptographic *provider* that composes HACL\* and Vale implementations behind an agile API, proving that the choice of algorithm and the choice of implementation are both safe, multiplexed at zero cost [2].

The central intellectual contribution of this program is not any single primitive, but the **methodological thesis** that high-performance cryptographic code — the kind of code that has historically been written in inscrutable, hand-optimized assembly — can be developed *and* proven correct within a single coherent verification infrastructure, and that the resulting code can be fast enough to ship in production. EverCrypt's measured performance matches or exceeds the best unverified implementations; its code is deployed in the Windows kernel, Hyper-V, Firefox, and Python, software used by billions of people every day [4].

> **Theorem (informal, motivating):** *Every HACL\*/EverCrypt primitive satisfies three properties simultaneously: (i) memory safety — no buffer overflows, use-after-free, or spatial violations; (ii) functional correctness — the implementation's observable behavior equals a high-level mathematical specification; and (iii) secret independence — observable leakage (addresses accessed, branches taken) is a function of public data only.*

The remainder of this paper decomposes how this theorem is made formal, how it is proven at scale, and where its boundaries lie.

## 2 Background

### 2.1 The verification substrate: F\*

F\* is a general-purpose functional programming language with **dependent types**, **refinement types**, and **SMT-backed proof automation** [7]. A refinement type `{x: t | p x}` denotes values `x` of type `t` satisfying predicate `p`; verification conditions are discharged largely automatically by the Z3 SMT solver, with manual proofs expressed as ordinary programs (in F\*, *proofs are programs*). F\* supports layered effects, and its computation types capture pre- and postconditions in the style of Hoare logic:

```fsharp
// F*: a refinement-typed stack computation (ST effect) with pre/postconditions
let fmul (output a b: felem) : Stack unit
  (requires fun h0 -> {output,a,b} in h0 /\ (a == b \/ disjoint a b))
  (ensures  fun h0 _ h1 -> modifies (loc output) h0 h1 /\
                            sel h1 output == Spec.fmul (sel h0 a) (sel h0 b))
```

Here `requires`/`ensures` are the pre- and postcondition, `modifies` frames the set of locations the function may touch, and `sel h0 a` reads buffer `a` in the pre-state heap `h0`. Crucially, `Spec.fmul` is a *pure mathematical specification*; the refinement states that the imperative code's result equals the specification. The SMT solver proves these facts automatically in the common case; when it cannot, the programmer supplies lemmas.

### 2.2 The problem landscape: why crypto code resists verification

Cryptographic code presents a uniquely hostile combination of verification challenges:

- **Bit-level arithmetic with carries.** Field arithmetic for elliptic curves (e.g., Curve25519's 2²⁵⁵−19) involves long-limb multiplication with carry chains. A single dropped carry is exploitable and virtually untestable [2].
- **Memory discipline at the metal.** Buffers are raw, aliasing is pervasive, and bounds errors are silent.
- **Constant-time discipline.** Secrets must not influence branches, memory addresses, or variable-time instructions. The *leakage model* must be made formal and enforced.
- **Performance.** Assembly-level optimization (AES-NI, carry-less multiplication, vectorized SHA) is often mandatory for line-rate protocols. Verification must not sacrifice the last 10% of performance that determines adoption.

### 2.3 Lineage and scope

HACL\* was presented at CCS 2017 [1]; Vale at USENIX Security 2017 [5]; its F\*-embedded successor at POPL 2019 [6]; EverCrypt at IEEE Symposium on Security and Privacy 2020 [2]. The Everest perspective paper [4] surveys the full effort. This paper synthesizes the technical content of these works into a single account of *how* the proofs are constructed.

## 3 Methodology

Our methodology follows the Everest decomposition: **specify once at high level, implement twice (C-like and assembly-like), verify against shared specifications, extract to auditable artifacts.**

| Phase | Artifact | Tool | Guarantee obtained |
|---|---|---|---|
| Specification | Pure F\* functions (e.g., `Spec.fmul`) | F\* typechecker | Definitional truth |
| Implementation | Low\* (C-like) code | F\* + Z3 | Memory safety + functional correctness |
| Extraction | Readable C | KreMLin | Faithful translation (trusted) |
| Assembly | Vale DSL programs | Dafny/F\* + trusted printer | Correctness + constant-time at instruction level |
| Composition | EverCrypt provider | F\* zero-cost generics | Agility + multiplexing safety |
| Deployment | Compiled binaries | C compiler / assembler | **Trusted:** compiler correctness assumed |

Three methodological commitments structure the work:

1. **Single-language verification.** Everything — specifications, implementations, assembly semantics, and proofs — is expressed in F\* (after the 2019 Vale re-embedding), so that C and assembly implementations can be verified *against shared specifications* [2]. This compositionality is what makes the EverCrypt provider provable.
2. **Separation of specification and implementation.** Cryptographic *math* (what the algorithm computes) is specified in pure F\*; *memory behavior* (how buffers are mutated) is verified in Low\*'s effectful fragment. Functional correctness is then the statement that the two coincide.
3. **Leakage as a first-class observable.** Constant-time security is formalized as a property of the program's *leakage trace* — the sequence of addresses read/written and branches taken — proving it independent of secrets.

## 4 Deep Dive

### 4.1 Low\* and KreMLin: a memory-safe C embedded in F\*

Low\* is a **first-order, effectful subset of F\*** designed so that every well-typed Low\* program can be compiled to C with a predictable, direct correspondence [1]. Its memory model is explicit: a heap maps references to values, buffers are sequences of machine words, and the `Stack`/`ST` effects track the set of live allocations. The key innovation is that Low\*'s types are *refined with spatial properties*:

```fsharp
// Low*: buffer type refined with liveness and disjointness
let live (h:mem) (b:buffer t) = ...     // b is allocated in heap h
let disjoint (b1 b2: buffer t) = ...    // regions do not overlap
let modifies (s:loc) (h0 h1:mem) = ...  // only locations in s changed
```

The typechecker rejects, *at compile time*, any program that might read a dead buffer, write out of bounds, or violate the frame condition. This is **memory safety by construction** — not checked at runtime, but proven from the typing derivation, with Z3 discharging the separation-logic-style obligations.

**KreMLin** then extracts Low\* to C. Unlike extraction pipelines that produce unreadable code, KreMLin is engineered to emit **source-like C** that independent cryptographers can audit — a deliberate design choice, since the extracted C must be reviewable by experts outside the F\* community [1]. The extraction is *trusted*: its correctness is argued by construction and auditing, not machine-checked. This is an explicit, documented point in the trusted computing base (see §6).

### 4.2 HACL\*: verified primitives and the constant-time discipline

HACL\* implements a modern suite — ChaCha20, Poly1305, AES-GCM (including AES-NI paths), SHA-2/3, HMAC, HKDF, Ed25519, X25519, and more — each carrying a proof of **(a)** memory safety, **(b)** functional correctness against a pure specification, and **(c)** *secret independence* [1].

The constant-time property is formalized over a **leakage model**. Concretely, the instrumented semantics of Low\* records, for each execution, a leakage trace:

$$\mathrm{leak}(\pi, s_{\mathrm{pub}}, s_{\mathrm{sec}}) \in (\text{addresses} \times \text{branches})^*$$

**Secret independence** is the property that for all secret inputs $s_{\mathrm{sec}}, s'_{\mathrm{sec}}$,

$$\mathrm{leak}(\pi, s_{\mathrm{pub}}, s_{\mathrm{sec}}) = \mathrm{leak}(\pi, s_{\mathrm{pub}}, s'_{\mathrm{sec}}).$$

In HACL\*, this is enforced *structurally*: the Low\* fragment used for secret-dependent code is restricted so that (i) secret values never flow into branch conditions, and (ii) secret values never flow into memory addresses or variable-time instructions (e.g., division). The verification checks *taint*: every value is classified public or secret, and the type system tracks propagation.

```fsharp
// BAD: secret-dependent branch — rejected by the discipline
if secret_bit = 1 then fast_path () else slow_path ()

// GOOD: constant-time select — both operands computed, branch-free
let mask  = secret_bit_to_mask secret_bit in
let res   = (mask &&& a) ||| (~~~mask &&& b) in
res   // leakage identical regardless of secret_bit
```

> **Theorem (Secret independence, Zinzindohoué et al. [1]):** *Any HACL\* implementation typed in the constant-time Low\* fragment exhibits leakage traces independent of secret inputs; hence a passive observer of the program's control flow and memory-access pattern learns nothing about secrets.*

The practical payoff is substantial: HACL\* was audited and has been integrated into Mozilla's NSS (Firefox), Python's `hashlib` backend, and the Linux kernel — deployments where a timing side channel would be catastrophic [4].

### 4.3 Vale: verified assembly with machine-checked Hoare triples

Some primitives cannot reach peak performance in C: the compiler may spill registers at the wrong moment, fail to use AES-NI's `aesenc` rounds efficiently, or refuse to emit carry-less multiplication (`pclmulqdq`). HACL\* handles this by dropping to **Vale**, a DSL in which assembly is written *together with* its correctness proof [5].

A Vale procedure is assembly annotated with preconditions, postconditions, and loop invariants — essentially, **inline Hoare logic**. The Vale *tool* then: (1) verifies the procedure against an **operational semantics of the target ISA** (x86-64, ARM) using Dafny [5] or, in the re-engineered version, a deep embedding in F\* [6]; and (2) passes the result through a **small trusted printer** that emits MASM and GNU assembly. The trusted printer is the only assembly-specific component — deliberately tiny, so it can be audited exhaustively.

A subtlety worth emphasizing: in the 2017 Dafny version, Vale and Low\* lived in *different* verification worlds, and composing them required care. The 2019 POPL re-embedding [6] expresses Vale's machine-state semantics as F\* datatypes — registers as functions from names to values, memory as a partial map from addresses to bytes, and a validity flag `ok` that becomes `false` on any invalid access:

```fsharp
// F*: Vale's machine state (Fromherz et al., POPL 2019) [6]
type reg   = Rax | Rbx | Rcx | Rdx | ...
type state = { regs: reg -> nat; xmm: xmmreg -> seq nat;
               flags: nat; mem: addr -> option byte; ok: bool }
```

With both C-like and assembly-like code verified *in the same logic*, EverCrypt can prove deep integration properties — e.g., that an AES-GCM implementation using Vale assembly for the AES rounds and Low\* C for the GHASH loop satisfies a single shared specification [2].

### 4.4 EverCrypt: the agile provider

EverCrypt's central abstraction contribution is a **provably agile API** [2]. Cryptographic agility means a caller can select among algorithms (e.g., SHA-256 vs. SHA-3) for the same functionality; *multiplexing* means selecting among implementations of the same algorithm (e.g., C vs. AES-NI assembly). EverCrypt proves, once, that:

1. Every implementation satisfies the functionality's specification (so swapping is behavior-preserving).
2. The dispatch logic itself (including runtime CPU-feature detection) is verified — a caller cannot be silently routed to a weaker or incorrect implementation.
3. Agility is achieved through **zero-cost generic programming**: the F\* functors that instantiate implementations for algorithms and platforms *erase* during extraction, so the generated C pays no abstraction penalty [2].

This composition is validated by case studies at scale: a verified secure network protocol achieving **line-rate performance**, and a verified Merkle-tree library used in a production blockchain sustaining **2.7 million insertions/second** [2].

### 4.5 The leakage model, precisely

To close the loop on §3's methodological claim, it is worth stating what the verified fragment *does not* cover. The leakage model assumes a **passive, local observer**: one who sees the program's addresses and branches but not its data values. It excludes:

- *Speculative-execution leakage* (Spectre-class): the model is defined over the architectural, in-order semantics [6].
- *Power/EM analysis*: physical emanations are outside the model.
- *Compiler-introduced leakage*: verified at the C/Vale source level; the C compiler and assembler are trusted (§6).

Within these bounds, however, the guarantee is total: *no* input — however adversarial — can cause a verified primitive to branch on a secret or address memory by a secret, because the property is proven over the program's semantics, not sampled by tests [1][2].

## 5 Empirical Evidence

The Everest program is distinguished by the *scale* of its verification and the *reality* of its deployment. The headline numbers from the EverCrypt paper [2]:

| Metric | Value |
|---|---|
| Verified lines (specs + code + proofs) | **> 124,000** |
| Generated C | ~29,000 lines |
| Generated assembly | ~14,000 lines |
| AES-GCM vs. OpenSSL | Matches or exceeds |
| Curve25519 vs. best unverified | Matches or exceeds |
| Merkle-tree case study | 2.7M insertions/sec (production blockchain) |
| Secure protocol case study | Line-rate performance |

Performance parity deserves emphasis, because it falsifies the common objection that verification necessarily costs speed. EverCrypt's AES-GCM (Vale assembly with AES-NI) and Curve25519 match or beat the best hand-tuned unverified implementations [2]. HACL\*'s primitives were benchmarked against OpenSSL and the formally-verified-but-slower alternatives of the era (e.g., Fiat-Crypto-generated C, which lagged hand-tuned assembly by 0.25–2×); the Vale path exists precisely to close that gap [2][5].

Deployment evidence is equally concrete. Project Everest's software shipped in the **Windows kernel** (verified crypto in the kernel's TLS stack), **Hyper-V**, **Linux**, **Firefox** (via NSS), and **Python** — "improving the security and reliability of software used by *billions* of people every day" [4]. HACL\* is maintained as an open library at [8], and the Vale toolchain at [9].

The verification effort is also *reusable*: the F\* standard libraries, Low\* memory model, and Vale embeddings are infrastructure, so each new primitive costs less proof effort than the last — the 124K-line figure includes this shared substrate [2].

## 6 Limitations

Intellectual honesty requires stating what the proofs do **not** buy.

1. **Trusted computing base.** The proofs assume: (a) the F\* typechecker and Z3 are sound; (b) KreMLin extraction preserves semantics; (c) the Vale printer faithfully emits the verified instruction sequence; (d) the C compiler and assembler produce correct machine code. A bug in any of these silently voids guarantees. Notably, *the C compiler is the largest unverified component* — CompCert-style verified compilation was not used.
2. **Specification completeness.** Proofs show the implementation matches the *specification*; a wrong specification (e.g., an incorrect statement of the AES standard) yields verified-but-wrong code. Specifications are audited but not themselves proven against standards documents.
3. **Side-channel scope.** As noted in §4.5, speculative execution, power analysis, and fault injection are outside the leakage model. The proofs cover timing and cache-observation channels under the in-order architectural semantics only.
4. **Cryptographic (not just implementation) security.** HACL\*/EverCrypt prove *implementation* correctness — the code computes the right function safely. They do not prove that AES or Curve25519 are *cryptographically secure* against mathematical cryptanalysis; that rests on the standard assumptions of the field.
5. **Incomplete Everest goals.** The TLS *handshake* proof in miTLS/F\* was left incomplete, and the 2025 perspectives paper [4] documents this openly; the verified fragment covers primitives, the record layer, and providers — not the full handshake negotiation state machine.
6. **Proof maintenance cost.** Verification at this scale is brittle under change: modifying an algorithm often requires repairing thousands of lines of proof. The zero-cost-generic infrastructure [2] mitigates but does not eliminate this.

## 7 Conclusion

Project Everest demonstrated a thesis that was, in 2016, widely considered implausible: that production cryptographic software — including hand-optimized assembly — can carry **machine-checked proofs of memory safety, functional correctness, and constant-time discipline**, at performance competitive with the best unverified code, and can ship to billions of users [4]. HACL\* showed how to structure C-like crypto in Low\* so that KreMLin extracts auditable C [1]; Vale showed how to verify assembly at the instruction level within a tiny trusted printer [5][6]; EverCrypt showed how to compose both under a provably agile, multiplexing provider API with zero-cost abstraction [2].

The open problems are now sharper for this success: shrinking the trusted computing base (verified compilation, verified extraction), extending the leakage model to speculative semantics, completing the protocol-layer proofs Everest left unfinished, and reducing the proof-maintenance tax so verified crypto can evolve at the pace of the field. The 124,000 verified lines are not an endpoint but a foundation — and, as the Everest perspectives paper notes, its offshoots (Pulse, EverParse, Verus, Aeneas) are already carrying the methodology into parsers, concurrency, and Rust [4].
