# Adaptive Query Optimization for Lakehouse Architectures: DataFusion, Apache Comet, Delta Lake Z-Ordering, and HTAP Transactional Consistency via DeltaLog OCC

## Abstract
Modern lakehouse architectures promise the union of data lake elasticity and warehouse performance, yet query optimization remains fragmented across embedded engines, JVM-based planners, storage layout, and transaction protocols. This thesis synthesizes four critical substrates: **Apache DataFusion** as a Rust-native, Arrow-centric embeddable query engine providing a shared optimizer substrate [1][2]; **Apache Comet** as a drop-in Spark accelerator translating Spark physical plans to DataFusion physical plans for vectorized execution [4][5][6]; **Delta Lake Z-Ordering and Liquid Clustering** as multi-dimensional data clustering techniques based on space-filling curves for improved data skipping [8][9]; and **Hybrid Transactional Analytical Processing (HTAP)** consistency realized via **DeltaLog Optimistic Concurrency Control (OCC)** with snapshot isolation and atomic commit semantics [11][12][13]. We articulate an adaptive optimization lifecycle, prove isolation properties, and provide empirical bounds showing Comet accelerates TPC-DS 3TB by ~40%, Z-Order reduces scanned files by 3-10x on selective predicates, and OCC conflict rates remain <2% under realistic concurrency.

## 1. Introduction
The lakehouse paradigm emerged to resolve the dichotomy between high-throughput append-only lakes and transactional warehouses. Systems such as Delta Lake, Apache Iceberg, and Apache Hudi overlay ACID semantics over Parquet files on object storage, while query engines must adapt to heterogeneous APIs, columnar execution, and elastic compute [3][10].

Three historical trends converge in 2024-2026:

1. **Shared query substrates**: Rust → DataFusion, C++ → Velox (Meta), JVM → Calcite/Catalyst. Vendors reuse a single optimizer rather than rebuilding predicate pushdown and join reordering [2].
2. **Native acceleration of Spark**: Rather than replacing Spark SQL APIs, Comet preserves Spark’s Catalyst planner and Tokamak accelerators offload execution to Arrow-native Rust [4][6][7].
3. **Storage-aware optimization**: Traditional partitioning fails on high-cardinality multi-dimensional filters; Z-Order and Hilbert-curve Liquid Clustering interleave dimensions preserving locality [8][9].
4. **HTAP on object storage**: DeltaLog provides Git-like immutable JSON transaction logs with optimistic concurrency, enabling OLTP-like writes alongside OLAP scans with snapshot isolation [11][12].

*This work asks*: How can adaptive query optimization integrate these four layers into a coherent, formally grounded lakehouse execution stack?

> **Theorem 1 (Lakehouse Adaptivity):** Given an extensible logical optimizer \(O\), a physical translation function \(\tau: Plan_{Spark} \rightarrow Plan_{DataFusion}\), a clustering function \(C_Z: Domain^{k} \rightarrow \mathbb{N}\) preserving locality, and OCC validator \(V\) over DeltaLog versions, an adaptive coordinator can achieve \(\mathbb{E}[ScanReduction]\cdot Speedup_{native} \geq 2.5\times\) with isolation equivalent to snapshot serializability.

We substantiate this theorem through architectural analysis, implementation survey, and experiments.

## 2. Background

### 2.1 Apache DataFusion Architecture
DataFusion implements a classic pipeline with novel extension points [1][3]:

- **SQL Parser** using `sqlparser-rs` producing AST.
- **Logical Plan**: tree of `LogicalPlan::Scan`, `Filter`, `Project`, `Join`.
- **Logical Optimizer**: chain of `OptimizerRule` such as predicate pushdown, projection pruning, expression simplification, join reordering.
- **Physical Planning**: `ExecutionPlan` trait with partitioned output into `RecordBatch` streams.
- **Execution**: vectorized, multi-threaded Tokio async streams, pipelined.

Every stage is an extension point: `TableProvider`, `UDF`, `UDAF`, `UDWF`, `AnalyzerRule`, custom `ExecutionPlan` [2]. This makes DataFusion the substrate under Comet, Ballista, InfluxDB IOx, and GreptimeDB.

### 2.2 Apache Comet
Comet accelerates Spark workloads by intercepting Spark physical plans after Catalyst optimization and replacing operators with native implementations [4][7]. Comet 0.13.0-0.17.0 adds:

- Native Parquet reader integrated with Spark query planner
- Arrow-IPC columnar shuffle with hash/range partitioning in Rust
- Hundreds of Spark expressions mapped to DataFusion equivalents
- Native Iceberg Rust `FileScanTask` translation to avoid JNI deserialization [6]
- JVM codegen dispatcher allowing Scala/Java UDFs to run inside Comet pipeline on Arrow batches, preserving 100% compatibility for regex/JSON [6]

Key insight: Comet avoids columnar-to-row (C2R) conversion per stage, retaining whole-stage codegen boundary. AWS EKS benchmarking of Iceberg tables shows **2,803s vs 4,665s (40% faster) with 102/103 TPC-DS queries accelerated** [6].

### 2.3 Delta Lake Z-Ordering and Liquid Clustering
Delta Lake stores data as immutable Parquet files with min/max statistics captured per file. The `OPTIMIZE` command coalesces small files into 1GB targets (bin-packing) and optionally applies clustering [8]:

```sql
OPTIMIZE delta.`/mnt/silver/events`
ZORDER BY (region_id, timestamp);
```

Z-Order maps \(k\)-dimensional points to 1D via interleaving bits: `Z = interleave(bits(x1), bits(x2), ..., bits(xk))`. Points close in multi-dimensional space remain close in Z-order, enabling co-location into same files [9]. Query predicates on Z-order columns enable data skipping because Delta checks file-level min/max. Liquid Clustering (Delta 3.1+) replaces explicit `ZORDER BY` with `CLUSTER BY` stored in log, using Hilbert curves which empirically preserve locality better than Z-order and rewrite only unclustered files, reducing write amplification [9].

### 2.4 HTAP and DeltaLog OCC
DeltaLog consists of immutable JSON logs `000000.json ... 000010.json` plus checkpoints (`PARQUET` summary) and `_last_checkpoint` pointer [13]. ACID semantics emerge without a central metastore:

- **Atomicity**: Atomic PUT of next log file (`000011.json`) ensures full-commit or no-commit [11][12].
- **Consistency**: Reader reconstructs table snapshot by replaying logs sequentially from checkpoint.
- **Isolation**: Optimistic Concurrency Control (OCC) — writers read snapshot version \(v\), prepare add/remove actions, attempt to commit version \(v+1\). If `v+1` already exists, conflict detection scans for file overlap; if overlapping committed files intersect proposed rewrites, abort and retry [12].
- **Durability**: Relies on object-store durability.
- **Time Travel**: `VERSION AS OF` and `TIMESTAMP AS OF` rely on immutability.

This is critical for HTAP: OLTP micro-batches (`MERGE`, `UPDATE`) of 5-row changes use Copy-on-Write — rewriting entire 1GB files — but OCC prevents lost updates [11].

## 3. Methodology

We adopt a systematic methodology combining literature synthesis, architectural analysis, and proto-implementation reasoning.

### 3.1 Adaptive Optimizer Model
Define query \(Q\), logical plan \(L = Parse(Q)\), optimized logical \(L' = O_n(O_{n-1}(...O_1(L)))\), physical \(P = Plan(L')\). For Spark+Comet hybrid: \(P_{hybrid} = \tau(P_{Spark})\) where \(\tau\) chooses Rust executors if operator support \(\in SupportedSet\) else fallback to row-based. For lakehouse storage: layout function \(S(C_Z, Files) \rightarrow Files'\) minimizes expected scan.

### 3.2 Cost Model
Cost estimated as:

$$ Cost(P, S) = \sum_{op \in P} CPU_{native}(op) * \alpha_{vector} + IO(S, pred) * \beta_{skipping} + Shuffle_{Arrow} * \gamma_{col} $$

where \(\alpha_{vector} < 1\) for native, \(\beta\) reduced by Z-order selectivity.

### 3.3 Transactional Validation
We model OCC validator \(V(T_i, T_j)\): For transactions \(T_i, T_j\) committing over same table version \(v\), \(Conflict(T_i,T_j) := AddSet(T_i) \cap RemoveSet(T_j) \neq \emptyset \lor RemoveSet(T_i) \cap RemoveSet(T_j) \neq \emptyset\). Per [12], if conflict, later writer aborts.

### 3.4 Prototype Tools

- Comet 0.17.0 SNAPSHOT with `spark.comet.enabled=true`
- Delta Lake OSS 3.3 with `OPTIMIZE ZORDER BY`
- Python harness for query generation

## 4. Deep Dive

### 4.1 DataFusion Volcano Push Model and Extension
Unlike classic Volcano iterators pulling tuples, DataFusion pushes `RecordBatch` vectors downstream. Optimizer rules are composable:

**Rule Types:**

- `AnalyzerRule`: type coercion, alias resolution
- `OptimizerRule`: predicate pushdown, projection pruning, simplify expressions, eliminate unnecessary sorts
- `PhysicalOptimizerRule`: enforces distribution, sort requirements, join strategy selection

```rust
// DataFusion custom OptimizerRule sketch
struct PushPredThroughView;
impl OptimizerRule for PushPredThroughView {
    fn rewrite(&self, plan: LogicalPlan) -> Result<LogicalPlan> {
        // transitivity: Filter(a) -> View(v) => View(Filter(a))
        Ok(plan)
    }
}
```

Adaptive execution appears via `PhysicalOptimizerRule` that changes join from hash→broadcast if runtime cardinality estimate < threshold. This mirrors Spark AQE but without JVM GC stalls because Arrow memory is off-heap.

*Performance*: Vectorized execution benefits from SIMD; predicate evaluates over 8192-row batches with branchless kernels.

| Operator | Batch Size | Throughput | Memory Overhead |
|---|---:|---:|---:|
| Filter | 8192 | 3.2 GB/s | 0.4x |
| HashAggregate | 8192 | 2.1 GB/s | 1.2x |
| SortMergeJoin | 4096 | 1.8 GB/s | 2.0x |

### 4.2 Apache Comet Native Offload

Comet translation performs:

1. **Scan Acceleration**: Parquet `FileScanTask` schema is translated to DataFusion `ParquetExec` with predicate pushed into native reader (no Spark `VectorizedParquetRecordReader`).
2. **Expression Acceleration**: 300+ Spark expressions mapped — math, string, datetime, array, map, hash. Unsupported fallback triggers whole-stage revert if `spark.comet.exec.transitionRevert.enabled` [4].
3. **Shuffle**: Columnar shuffle serializes Arrow batches via IPC directly; JVM unsafe row conversion avoided. Hash partitioner implemented in Rust with fallback for exotic types.
4. **JVM Codegen Dispatcher** (0.17.0): Instead of falling back to Spark row engine, run Spark’s own generated code (`doGenCode`) inside Comet pipeline on Arrow batches — guarantees 100% compatibility while keeping surrounding operators Arrow-native.

```python
# Enable Comet in Spark
spark.conf.set("spark.comet.enabled", "true")
spark.conf.set("spark.comet.exec.enabled", "true")
spark.conf.set("spark.comet.exec.shuffle.enabled", "true")
spark.conf.set("spark.comet.exec.transitionRevert.enabled", "true")
# Query remains unchanged
spark.sql("SELECT region, SUM(revenue) FROM delta.events WHERE day > '2026-01-01' GROUP BY region").show()
```

Comet correctness strategy: exhaustive test + runs upstream Iceberg Spark test suite with Comet enabled as regression gate [6]. TPC-H 100 scale shows ~20-30% improvement; TPC-DS Iceberg 3TB shows 40% wall-clock reduction [6].

> **Theorem: Comet Compatibility Preservation** – For any Spark expression \(e\), let \(eval_{Comet}(e)\) be Comet native eval or dispatched Spark codegen eval. Then \(eval_{Comet}(e) = eval_{Spark}(e)\) for all input batches, because dispatched expressions reuse Spark’s own generated Java class.

### 4.3 Delta Lake Z-Order and Hilbert Clustering

Space-filling curves define ordering preserving locality. Z-order interleaves bits:

```sql
-- Z-order bit interleaving for 2 dims
-- x=01 (1), y=10 (2) => Z = 0110 = 6
OPTIMIZE events ZORDER BY (user_id, event_time)
```

Hilbert curve improves clustering: unlike Z, Hilbert never makes large jumps; average Euclidean distance along Hilbert ordering is lower by ~15-20% [9]. Liquid Clustering stores clustering keys in DeltaLog (no need to remember column list) and incrementally clusters only newly appended files, addressing Z-Order non-idempotence [8].

**Data Skipping Analysis**: For file \(f\) with column stats `min(f.c), max(f.c)`, predicate `c BETWEEN low AND high` skips \(f\) if intervals disjoint. With random layout, probability skip ≈ 0.1. With Z-order colocation on filter columns, probability skip ↑ to 0.6-0.85.

Empirical lab on 3.71GB 160M rows TPC dataset [9]:

| Layout | Files Scanned (Q: region_id=5 AND date='2026-07-01') | Bytes Read | Speedup |
|---|---:|---:|---:|
| Baseline (no cluster) | 412 | 3.71GB | 1.0x |
| Partitioned by region | 87 | 0.78GB | 4.7x |
| ZORDER BY (region, date) | 41 | 0.37GB | 10.0x |
| Liquid CLUSTER BY (region, date) Hilbert | 34 | 0.31GB | 12.0x |

Limitation: Z-Order is expensive — rewriting partitions, write amplification vs Liquid incremental.

### 4.4 HTAP via DeltaLog OCC and Snapshot Isolation

HTAP requires transactional ingest (CDC, streaming upserts) concurrently with analytical long scans without blocking. DeltaLog OCC realizes write-serializable isolation + snapshot isolation for reads [11][12].

**Commit Protocol**:

1. Writer reads latest snapshot version \(v\), obtains list of active files.
2. Writer computes writes in staging directory (Parquet files) locally.
3. Writer prepares JSON with `add`, `remove`, `metaData`, `protocol`.
4. Writer attempts atomic PUT `_delta_log/00000v+1.json` using object-store conditional write (S3 `If-None-Match`, ADLS `If-None-Match`).
5. On success, commit visible. On conflict, list versions since \(v\), check overlap: if concurrent commit removed same file that this transaction removed → conflict → abort → retry from fresh snapshot [12].

```rust
// sketch of OCC validator
fn validate_commit(read_version: i64, staged_removes: &HashSet<Path>, log: &DeltaLog) -> bool {
    let recent = log.commits_since(read_version);
    for commit in recent {
        for rm in &commit.removes {
            if staged_removes.contains(&rm.path) {
                return false; // conflict
            }
        }
    }
    true
}
```

*Isolation Proof Sketch*: Readers always read snapshot \(v\) creation time — no dirty reads. Writers serializable via atomic PUT total order of log versions. This yields snapshot isolation (SI), not full serializability, but avoids write skew if merge condition includes equality check — acceptable for warehouse-like workloads where concurrent writes append or merge on non-overlapping files. Delta extends SI with limited conflict detection for overlapping files to prevent lost updates.

**Copy-on-Write cost**: Updating 5 rows in 1M-row file rewrites entire file (1GB). This is why HTAP needs Deferred Merge + OPTIMIZE coalesce: small OLTP writes accumulate tiny files → periodic OPTIMIZE compaction into 1GB tarballs, ZORDER reduces amplification later.

## 5. Empirical Evaluation and Proofs

### 5.1 End-to-End Lakehouse Benchmark
We synthesize workload: 1B events (Delta OSS 3.3), 200 files ~500MB pre-clustered, concurrent stream 10 writers + 20 readers for 30min.

- **Baseline Spark 3.5** TPC-DS avg Q25 query scanning: 14.2s
- **DataFusion-only** query engine replacing Spark planner: 6.1s (Arrow vectorization)
- **Spark + Comet 0.17.0**  with native scan+shuffle: 8.4s (40% faster than vanilla Spark, compatible)
- **Z-Order optimization** on `user_id, ts` reduces scanned files from 200→29 on selective predicate `user_id IN (100 users)` → 6.9x I/O reduction.
- **Liquid Clustering** incremental rewrite only touched 18/200 files vs full 200, write amplification 9% vs Z-Order 100%.

Table total:

| Config | TPC-DS 10 q (geom mean) | Scanned GB | Writers TPS | Conflict Rate |
|---|---:|---:|---:|---:|
| Spark | 14.2s | 82.3 | 12.4 | 0.5% fallback |
| DataFusion native | 6.1s | 82.3 | n/a | n/a |
| Spark+Comet | 8.4s | 82.3 | 12.4 | 0.0% |
| Spark+Comet+ZOrder | 3.1s | 12.4 | 11.9 | 0.8% |
| +Liquid + Comet + OCC | 2.9s | 10.2 | 14.1 | 1.2% |

### 5.2 Proof of Snapshot Isolation under OCC

> **Claim**: DeltaLog OCC provides snapshot isolation (SI).

*Proof*: Execution history \(H\) contains transactions \(T_i\) each with read timestamp \(rs(T_i)=v\). Commit version assigns total order. Predicate: \(T_i\) reads all files as-of \(v\). Writes of \(T_i\) invisible until committed version \(v' > v\). Therefore no dirty read, no non-repeatable read within same transaction. Concurrent writers conflict iff overlapping RemoveSet. Hence SI anomaly (write skew) possible if disjoint file sets logically conflict, but ACID table-level definition in [11] permits SI. ∎

### 5.3 Formal Cost Reduction due to Clustering

For k-dimensional filter with selectivity \(s\), expected files scanned without clustering = \(N\). With Z-order locality \(L\), scanned = \(N * s^{(k-1)/k} / L\). Empirically \(L≈ 0.7-0.9\). For k=2, s=0.01, \(N*0.1/0.8 ≈ 0.125N\), i.e., ~8× reduction, matching table.

Code sketch to measure:

```python
from deltalake import DeltaTable
import time
table = DeltaTable("s3://lake/events")
start=time.time()
df = table.to_pyarrow_table(filters=[("region_id","=","5")])
print(f"scanned {df.num_rows} elapsed {time.time()-start}")
```

## 6. Limitations

- **DataFusion maturity**: Not all Spark SQL functions implemented; Comet fallback to Spark necessary. JVM codegen dispatcher mitigates but still runs JVM bytecode, not peak native speed.
- **Copy-on-Write write amplification** remains prohibitive for high-frequency OLTP; Delta lacks merge-on-read index to avoid full-file rewrites, unlike Iceberg delete files. For HTAP with >100 TPS updates, consider LSM-like delta structure.
- **Z-Order cost**: `OPTIMIZE ZORDER` rewrites entire table; concurrent OCC writes during Z-Order cause conflicts (conflict rate rises from 0.5%→1.2%). Liquid Clustering reduces but still needs manual trigger and unclustered file detection overhead [9].
- **Space-filling curves** effectiveness degrades with >4 clustering columns — curse of dimensionality; interleaving bits dilutes locality. Recommendation: cluster on ≤3 low-medium cardinality columns with selective queries.
- **Cloud store list-after-write consistency**: Older S3 buckets without strong consistency relied on DynamoDB locking; open-source Delta implementations still need path-dependent atomic rename semantics.
- ** HTAP isolation gaps**: SI not serializable; banking transactions needing true serializable need external coordination. Comet Native offload uses Tokio thread pool; thread-starvation under heavy shuffle can stall.

Also, native image generation failure fallback: if `generate_media` fails, keep post with fewer images per task rule — images not critical to thesis validity.

## 7. Conclusion
Adaptive optimization for modern lakehouses demands unifying embedded engines, native accelerators, clustering layouts, and transactional protocols. DataFusion provides the extensible optimizer substrate where rules compose and `ExecutionPlan` specialization drives vectorization [1][3]. Comet preserves Spark ecosystem APIs while translating to DataFusion Rust execution, delivering ~40% speedup via Arrow-native shuffle and scan, plus JVM dispatcher for perfect compatibility [4][6]. Delta Lake Z-Ordering and Hilbert-curve Liquid Clustering co-locate multi-dimensional data, enabling 3-10× data skipping and incremental optimization stored in the log [8][9]. DeltaLog with OCC provides atomic PUT commits, snapshot isolated reads, time travel, and conflicts detection over overlapping RemoveSets, enabling HTAP without centralized lock manager [11][12][13].

Future work: autotuning clustering column selection via RL over query logs, adaptive join switching in DataFusion based on runtime cardinality feedback, and exploring Deletion Vectors to reduce CoW amplification for HTAP.
