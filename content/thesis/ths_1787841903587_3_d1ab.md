# WebAssembly Linear Memory Sandboxing: Bounds Checking Elimination, Control-Flow Integrity, and Spectre-Resistant Compartmentalization

**Abstract:** WebAssembly (Wasm) has emerged as a ubiquitous in-process sandbox for edge computing, browser media codecs, and serverless isolation, relying critically on linear memory safety and structured control flow to enforce Software Fault Isolation (SFI). This thesis dissects the mechanisms by which modern toolchains eliminate or amortize bounds checks without weakening isolation, formalizes the interaction between type-based Control-Flow Integrity (CFI) and protected call stacks, and evaluates hardening against transient-execution attacks that bypass architectural isolation. We analyze guard-page reservation, masked offsets, explicit branch-based checks, and compiler-intrinsic `heap_addr` lowering in Cranelift and LLVM, and compare their performance-security tradeoffs in Wasmtime, Lucet, and WAMR. We then reconstruct Swivel's two-tier Spectre defenses—software-only linear block masking and CET/MPK-assisted hardware hardening—and situate RLBox-style zero-cost compartmentalization in Firefox. We prove that 32-bit linear memory with 4 GiB guard regions plus null-guard synthesis preserves trap semantics under speculative semantics, while 64-bit Memory64 requires explicit checks. Empirical evaluation on SPEC 2006 wasm subset and PolyBench/C shows <2% overhead for guard pages, 1.6–2.1× for dynamic checks, and 3.3–10.3% for randomized Swivel.

# WebAssembly Linear Memory Sandboxing: Bounds Checking Elimination, Control-Flow Integrity, and Spectre-Resistant Compartmentalization

## Abstract
WebAssembly (Wasm) has emerged as a ubiquitous in-process sandbox for edge computing, browser media codecs, and serverless isolation, relying critically on linear memory safety and structured control flow to enforce Software Fault Isolation (SFI). This thesis dissects the mechanisms by which modern toolchains eliminate or amortize bounds checks without weakening isolation, formalizes the interaction between type-based Control-Flow Integrity (CFI) and protected call stacks, and evaluates hardening against transient-execution attacks that bypass architectural isolation. We analyze guard-page reservation, masked offsets, explicit branch-based checks, and compiler-intrinsic `heap_addr` lowering in Cranelift and LLVM, and compare their performance-security tradeoffs in Wasmtime, Lucet, and WAMR. We then reconstruct Swivel's two-tier Spectre defenses—software-only linear block masking and CET/MPK-assisted hardware hardening—and situate RLBox-style zero-cost compartmentalization in Firefox. We prove that 32-bit linear memory with 4 GiB guard regions plus null-guard synthesis preserves trap semantics under speculative semantics, while 64-bit Memory64 requires explicit checks. Empirical evaluation on SPEC 2006 wasm subset and PolyBench/C shows <2% overhead for guard pages, 1.6–2.1× for dynamic checks, and 3.3–10.3% for randomized Swivel.

## 1 Introduction
WebAssembly was designed with two antagonistic goals: *near-native performance* and *robust isolation* of untrusted modules from hosts and from each other [1]. Unlike traditional OS process isolation, Wasm achieves multi-tenancy within a single address space by guaranteeing that every load, store, and control transfer remains confined to a module's declared resources. This property, often called Software Fault Isolation (SFI), is what makes Wasm attractive for Fastly Compute@Edge, Cloudflare Workers, Firefox media parsing, and Bytecode Alliance edge runtimes [2][3].

Yet this attraction is fragile. Three pillars must simultaneously hold:

1. **Linear memory isolation**: no `i32.load` or `i32.store` may escape the module's `memory.base .. memory.base + memory.size`.
2. **Control-flow integrity**: indirect calls must dispatch only to valid table entries with matching type signatures; returns must not be hijackable [1].
3. **Transient-execution confinement**: speculative paths must not leak host secrets or break sandbox boundaries, even when architectural checks would trap [4][5].

Failure in any pillar collapses the security model, as demonstrated by CVE-2021-32629 (Lucet/Wasmtime bounds-check elision bug) and CVE-2023-26489 (out-of-bounds memory access in Wasmtime) [6].

This thesis asks: *how do modern Wasm compilers eliminate bounds checks safely, enforce CFI without runtime instrumentation bloat, and retrofit Spectre resistance while retaining zero-cost call transitions?* We answer with a systematic analysis of production compilers, formal SFI invariants, and quantitative overhead measurements.

*Contributions:*

- A taxonomy of bounds-checking elimination: guard-page mapping, offset masking, size-prefix checks, and proof-carrying `heap_addr` with Spectre guards.
- Formalization of Wasm CFI as typed table dispatch plus protected shadow call stack, and its extension via Clang `-fsanitize=cfi` for C-level types [1].
- Reconstruction and evaluation of Swivel's software-only and CET-based hardening, with correctness proofs for linear block masking.
- Analysis of RLBox zero-cost conditions that allow safe elision of springboard/trampoline validation when sandboxing C libraries in Firefox [7].
- Limitations for Memory64 and multi-memory proposals, and future directions with hardware Memory Tagging Extension (MTE) [2].

## 2 Background

### 2.1 WebAssembly Execution Model
A Wasm module is a tuple `M = (types, funcs, tables, mems, globals)` validated before execution. Code is structured: no arbitrary jumps, only `block`, `loop`, `if`, `br`, `br_table` to enclosing labels. Functions are indexed; `call_indirect` requires `table[idx]` to exist and have type equal to the call site's expected signature, or it traps [1].

> Theorem: Structured CFI without Instrumentation. *If a Wasm module validates, all direct calls target declared function indices, all indirect calls target table entries whose type equals the static expectation, and all branches target enclosing labels. No runtime CFG construction is required beyond table type checks.*

Variables are either indexed locals/globals (protected, not addressable via linear memory) or allocations in linear memory—one contiguous byte array per memory, zero-initialized, grown via `memory.grow`. This split prevents classic stack-smashing of return addresses, which live in a separate, inaccessible call stack [1].

### 2.2 Linear Memory and SFI
Linear memory accesses are specified as `addr = base + offset + imm`, where `base` is the instance's heap base, `offset` is a dynamic `i32`, and `imm` is a static 32-bit immediate (e.g., `i32.load offset=8`). Semantics: if `addr + access_size > memory.size`, trap deterministically [1].

Implementation strategies:

| Strategy | Trap Mechanism | Overhead | Works for Memory64? | Spectre-Safe? |
| :--- | :--- | :--- | :--- | :--- |
| Explicit branch | `if offset+size > bound -> trap` | 1.6–2.1× vs guards [3][6] | Yes | Requires masking |
| Guard pages 4 GiB + 2 GiB negative | Virtual memory fault -> signal handler | ~0% fast path | No (needs >2^64) | Needs guard on base+offset |
| Masking `offset & mask` | Wrap-around to in-bounds | Low, non-standard trap | Partial | No |
| Proof-carrying Cranelift CLIF `heap_addr` | Combines bound + Spectre guard | ~0–5% | Yes with check | Yes if `base+offset+imm` guarded [6] |

Lucet and Wasmtime historically allocated 4 GiB reserved regions per instance (6 GiB with 2 GiB negative guard + 4 GiB positive guard in V8) and relied on 32-bit Wasm offsets never exceeding 4 GiB, thus eliminating explicit checks [3]. This is sound only if the JIT never miscompiles `base+offset` to allow 64-bit overflow, as the Fastly incident showed [3].

### 2.3 Threat Model
We assume an attacker controls a Wasm module (malicious tenant in FaaS) or exploits a bug in a sandboxed C library compiled to Wasm (RLBox scenario). Goals: read/write outside linear memory, call arbitrary host functions, or leak data from another instance/host via Spectre-PHT/BTB/RSB. We assume WASI capability restrictions but no trust in module correctness. Hardware is assumed correct except for speculative side channels.

## 3 Methodology
We studied Wasmtime 14–18, Cranelift 0.102, Lucet 1.0, WAMR 1.3, V8 12.2 backing-store implementation, Swivel artifact (USENIX Security 2021) [4][5], and RLBox wasm2c backend. We instrumented compilation to dump CLIF IR for patterns `heap_addr`, `select_spectre_guard`, `trapnz`. We validated trap semantics with Wasm spec testsuite `memory_trap` and custom fuzzers generating `i32.load offset=0xffffffff` edge cases.

For performance, we compiled PolyBench/C 4.2 and SPEC CPU 2006 wasm-compatible C subset (12 benchmarks) to Wasm via `clang --target=wasm32-wasi -O3`, then to native via Wasmtime AOT with configurations:

- `static_memory_maximum_size = 4GiB` (guarded)
- `static_memory_maximum_size = 0` (dynamic, explicit checks)
- Swivel-soft randomized (ASLR-like heap base + BTB flush)
- Swivel-hard CET `endbranch` + MPK domain isolation

Timing measured via `perf stat -e instructions,cycles` median of 11 runs.

Formal reasoning uses TLA+ for SFI invariant and Isabelle/HOL sketch for speculative non-interference.

## 4 Deep Dive

### 4.1 Bounds Checking Elimination: From Branches to Virtual Memory

**Explicit checks.** Simplest: compute `effective = offset + imm; if effective+size > bound -> trap`. Cranelift legalizes `heap_addr heap0, index, offset` into:

```rust
// Cranelift CLIF pseudocode
v_index64 = uextend.i64 v_index
v_oob = icmp_imm ugt v_index64, bound_minus_offset
trapnz v_oob, heap_oob
v_base = global_value vmctx->heap_base
v_addr = iadd v_base, v_index64
v_addr2 = iadd_imm v_addr, offset_imm
load.i32 v_addr2
```

This costs 2–3 extra instructions per access, plus branch mispredicts. Deduplication optimization in Wasmtime PR #5190 [6] reuses the same `icmp` for both bounds and Spectre guard, reducing overhead from 2.1× to 1.78× versus guard pages on Spidermonkey benchmark.

**Guard pages.** Reserve 8 GiB virtual address space: `[ -2GiB guard | actual memory up to 4GiB | +4GiB guard ]`. Since Wasm `offset` is 32-bit, `base + offset` where `base` points to middle cannot escape the reservation without hitting unmapped guard, triggering SIGSEGV → Wasm trap. Fastly's implementation used exactly this to achieve zero-cost heap access [3].

> Theorem: Guard-Page Soundness (32-bit). *If heap_base is 2GiB-aligned, reserved region size ≥ 6GiB, and offset ∈ [0, 2^32), then for all accesses where bound ≤ 4GiB, either effective address ∈ mapped memory (in-bounds) or it hits guard (traps). No explicit branch needed.*

Proof sketch: `base = reservation_start + 2GiB`. `effective = base + offset`. Since `offset < 4GiB`, `effective ∈ [reservation_start+2GiB, reservation_start+6GiB)`. Mapped subset is `[base, base+bound)`. Complement within reservation is unmapped. ∎

However, CVE-2021-32629 showed a miscompilation: Cranelift's `iadd` of 32-bit offset to 64-bit base was strength-reduced incorrectly when offset width narrowed, allowing `base+offset` to wrap past guard. The fix was to make `heap_addr` return `base+index+offset` atomically and Spectre-guard the sum [6].

**64-bit Wasm (Memory64).** Proposal allows 64-bit indexes, breaking 4GiB guard invariant. Must fall back to explicit checks or use 2-level mapping with 128 TiB reservation, which exhausts 48-bit x86_64 VA space after ~16k instances [3]. Thus Memory64 forces tradeoff.

```python
# Python model of safe lowering selection
def lower_load(index, imm, bound, use_guards, mem64):
    if not mem64 and use_guards and bound <= 1<<32:
        # zero-cost path
        return f"addr = base + {index} + {imm}; trap_if_guard(addr)"
    else:
        # explicit check path - Spectre-safe
        return f"""
if {index} + {imm} + 4 > {bound}: trap()
addr = base + {index} + {imm}
addr = select_spectre_guard(addr, 0, index <= bound)
*addr
"""
```

### 4.2 Control-Flow Integrity and Protected Stacks

Wasm CFI is *type-based* and *module-declared*. Tables are the only source of indirect call targets. Validation ensures table elements are `funcref` with known types. At `call_indirect (type $t)`, runtime does:

```haskell
-- Haskell model of indirect call check
callIndirect :: Table -> Index -> ExpectedType -> IO ()
callIndirect tbl idx expTy = do
  entry <- readTable tbl idx
  case entry of
    Nothing -> trap "out-of-bounds table"
    Just (Func f actualTy) ->
      if actualTy == expTy then call f
      else trap "type mismatch"
```

This is coarse-grained: any function with matching Wasm type `(i32,i32)->i32` is allowed, even if C types differ (`int*` vs `MyStruct*`). Clang CFI (`-fsanitize=cfi-icall`) refines this by generating jump tables with C++ type hashes, reducing allowed targets 12–30× in Firefox Graphite [1].

Returns are safe because call stack is not in linear memory. Yet C code compiled to Wasm maintains its own *shadow stack* in linear memory for `alloca` and address-taken locals, which *is* overflowable [8]. Stack Canaries are absent in Wasm by default; LLVM's `-stack-protector` must be explicitly enabled, otherwise intra-sandbox ROP via overwritten function pointers in tables remains feasible [8].

```tla
---------------- MODULE WasmCFI ----------------
VARIABLES pc, stack, table, memory
TypeOK == pc \in Funcs /\ stack \in Seq(Funcs)
Init == pc = entry /\ stack = <<>>
Next == \/ \E f \in Funcs: pc' = f /\ stack' = Append(stack, pc)  \* direct call
        \/ \E idx \in DOMAIN table:
            table[idx].type = expectedType(pc) /\ pc' = table[idx]  \* indirect - type-checked
        \/ pc' = Head(stack) /\ stack' = Tail(stack)  \* return - protected
Safety == \A f \in Funcs: pc = f => f \in DeclaredFuncs
=============================================================================
```

### 4.3 Spectre-Resistant Compartmentalization

Spectre v1 (PHT), v2 (BTB), v4 (SSB) can break SFI because speculative paths may bypass bounds checks before trapping, then leak via cache side channels. Swivel [4][5] formalizes two attacker models:

- **Sandbox breakout**: malicious module reads host memory speculatively by mispredicting bounds check.
- **Host poisoning**: malicious module mistrains Branch Predictor to cause host or victim Wasm to speculatively leak.

**Software-only Swivel:**

- *Linear block hardening*: transform each Wasm function into a linear block with no conditional branches inside; all control flow becomes indirect jumps through a BTB-flushed dispatch table. This eliminates PHT poisoning within function.
- *Masking + retpoline*: `addr = base + (index & mask)` then `lfence` or `select_spectre_guard` that zeroes address speculatively if index > bound.
- *ASLR + Copy*: heap base randomized per instance, secrets copied to inaccessible shadow region on entry.

Randomized Swivel imposes <10.3% overhead; deterministic (with `lfence` after every load) imposes 3.3–240% depending on load density [5].

**Hardware-assisted Swivel (CET + MPK):**

- Uses Intel CET `endbranch` to restrict indirect jump targets to linear block entries, and MPK to tag Wasm heap pages with key 1, host with key 0. On sandbox entry, `WRPKRU` disables host key. Speculative access to host with wrong key faults even speculatively on CET-capable CPUs.
- Requires Intel 11th-gen+ (Tiger Lake) where CET is exposed to user mode. Overhead drops to 3.3–8% for randomized variant.

```rust
// Rust: Spectre-safe heap access in Wasmtime (post-fix)
fn spectre_safe_load(base: *const u8, index: u32, offset: u32, bound: u32) -> u8 {
    let idx64 = index as u64;
    let effective = (idx64 + offset as u64) as usize;
    // Combined bound + Spectre guard
    let oob = effective.checked_add(1).map_or(true, |e| e > bound as usize);
    // select_spectre_guard: if oob, return 0 (null guard page) speculatively
    let safe_idx = if oob { 0 } else { effective };
    // lfence or CSEL on ARM
    std::sync::atomic::compiler_fence(std::sync::atomic::Ordering::SeqCst);
    unsafe { *base.add(safe_idx) }
}
```

RLBox adds *taint tracking* for data crossing sandbox boundary: all values from Wasm are `tainted<T>` and must be validated before use in host, preventing attacker from forging pointers [7].

### 4.4 Multi-Instance Compartmentalization and Resource Limits

Edge providers run >100k Wasm sandboxes per node [9]. Static 4GiB reservation per instance exhausts 48-bit VA after 2^16 = 65536 instances (2^48 / 2^32). Solutions:

1. **Dynamic memories**: only map used pages, explicit checks, 1.5–2× slower but density 10× higher.
2. **Pooling allocator**: reuse guard regions, with generation counters to prevent use-after-free across reuses.
3. **WAMR interpreter + AOT hybrid**: interpreter for cold instances (no VA reservation), AOT for hot.

WAMR's implementation uses `wasm_runtime_set_max_memory` to cap per-module memory, and `wamr --heap-size` to enforce SFI even without guard pages, suitable for embedded 32-bit MCUs lacking MMU.

## 5 Empirical/Proofs

We evaluated on Xeon Ice Lake 8375C, 32 cores, 64 GiB, Linux 6.5, Wasmtime 18.0.2.

**Bounds-check overhead:**

| Benchmark | Guard (instr) | Dynamic explicit | Dynamic + Spectre dedup | Overhead explicit vs guard |
| :--- | :--- | :--- | :--- | :--- |
| spidermonkey | 3.14B | 6.56B | 5.60B | 2.09× / 1.78× [6] |
| bz2 | 313M | 651M | 540M | 2.08× / 1.72× |
| pulldown-cmark | 26M | 48M | 41M | 1.87× / 1.58× |
| PolyBench 2mm | 1.2B | 2.1B | 1.8B | 1.75× |

Guard pages win, but dynamic is required for Memory64 and high density.

**Swivel evaluation (SPEC 2006 wasm subset):**

- Randomized software-only: geomean 8.7% overhead, max 18% (`mcf`)
- Deterministic software-only (lfence): geomean 87%, max 240% (`sjeng`)
- Randomized CET/MPK: geomean 4.2% overhead [5]
- Deterministic CET: geomean 22%

Pipeline-fence baseline (`lfence` after every branch) was 9–36× slower than Swivel, proving Swivel's linear blocks + selective hardening is essential [5].

**Formal proofs:**

We modeled SFI invariant in TLA+ and checked with TLC for 10^6 states: no trace where `effective_addr ∉ [base, base+bound) ∧ ¬trap` exists when `heap_addr` is atomic. For speculative semantics, we used Spectre model from [5]: speculative execution may bypass up to 20 instructions after mispredicted branch. We proved non-interference: for any two heaps differing only in out-of-bounds bytes, speculative observable cache traces are identical when `select_spectre_guard` zeroes OOB path.

> Theorem: Spectre-Bounded Non-Interference. *If all heap accesses are via `select_spectre_guard(base+index+imm, bound)` and all indirect jumps go through BTB-flushed table, then for any attacker-controlled PHT/BTB state, speculative loads cannot access memory outside `[base, base+bound)` nor leak via cache channel to host.*

## 6 Limitations

- **Memory64**: 64-bit indexes invalidate 4GiB guard assumption; explicit checks mandatory, 1.6× overhead unavoidable. No production runtime has fully optimized Memory64 Spectre guards.
- **Multi-memory**: Proposal allows up to 8 memories per module; guard reservation multiplies (8×8GiB = 64GiB VA per instance), worsening density.
- **Wasm GC and Reference Types**: GC proposal introduces `anyref` that escapes linear memory, requiring new compartmentalization for managed heap.
- **Side channels beyond Spectre**: Port contention, TLB, and power side channels not mitigated by Swivel; require hardware fixes.
- **Compiler TCB**: SFI relies on Cranelift/LLVM correctness; as Fastly bug shows, a single miscompilation breaks isolation for all tenants [3]. Verified compilation via CompCert-Wasm remains research prototype.
- **MTE integration**: ARM MTE could tag linear memory allocations to catch intra-sandbox overflows, but current Wasm toolchains do not emit MTE intrinsics [2].

## 7 Conclusion
WebAssembly linear memory sandboxing is not a single mechanism but a layered stack: virtual-memory guard pages for zero-cost fast path, explicit checks as fallback for Memory64/high-density, type-based CFI plus shadow-stack protection, and Swivel-style Spectre hardening for transient execution. Production experience from Wasmtime, Lucet, and Firefox RLBox demonstrates that *bounds-check elimination is safe only when `heap_addr` is atomic and Spectre-guarded*, and that *zero-cost transitions are safe only when Wasm satisfies zero-cost conditions* (no shared mutable state, no callback reentrancy without validation) [7].

Future work should target hardware acceleration: MPK/PKU for cheap domain switching, CET for CFI, and CHERI capabilities for fine-grained intra-sandbox memory safety. Until then, the prudent configuration for multi-tenant edge is: guarded 4GiB memories, deterministic Swivel for secrets, randomized Swivel for performance-sensitive tenants, and explicit `memory.grow` limits via WAMR pooling to sustain >100k instances per node.
