# Trino Distributed SQL at Scale: Cost-Based Optimization, Exchange Operators, Fault-Tolerant Execution, and Lakehouse Connector Pushdown

## Abstract

Trino is a distributed SQL query engine that brings massively parallel processing to federated analytics over data lakes, warehouses, and operational stores. This thesis analyzes the four mechanisms that define Trino's performance envelope at scale: the coordinator-worker MPP execution model with its exchange operator fabric, the cost-based optimizer that drives join enumeration and join distribution strategy from table statistics, the fault-tolerant execution layer that retries queries and tasks against spooled exchange state, and the connector service provider interface that pushes predicates, projections, aggregations, and dynamic filters into lakehouse formats such as Apache Iceberg. Drawing on the official Trino documentation, the Project Tardigrade engineering record, and community performance literature, we derive the cost model governing exchange placement, quantify the failure-recovery trade-off of retry policies, and characterize when pushdown converts network-bound scans into metadata-only operations. The result is a rigorous, implementation-grounded account of how Trino sustains interactive latencies on petabyte-scale SQL.

---

## 1 Introduction

Trino is not a database. It stores nothing, owns no transactions, and manages no durable state; it is a *query engine* that speaks ANSI SQL and executes it across a cluster of machines against dozens of heterogeneous storage systems [1]. Born as Presto at Facebook in 2012 and renamed from PrestoSQL to Trino in December 2020 [3], the system embodies the massively parallel processing (MPP) tradition: a coordinator parses, analyzes, plans, optimizes, and fragments each query, while workers execute the fragments as parallel tasks over partitioned data. Unlike MapReduce-derived engines that materialize intermediate results between stages, Trino pipelines *pages* — columnar batches of rows — through chains of operators in memory, which is the architectural decision responsible for its sub-second interactive latencies on terabyte-scale scans [4].

Four subsystems determine whether a Trino deployment is merely functional or genuinely fast:

1. **The exchange fabric**, which repartitions, broadcasts, gathers, and routes pages between stages;
2. **The cost-based optimizer (CBO)**, which uses collected statistics to order joins and select distribution strategies;
3. **Fault-tolerant execution (FTE)**, which checkpoints exchange state so that long ETL queries survive worker loss;
4. **The connector SPI and pushdown framework**, which lets storage-specific code prune files, skip row groups, and evaluate predicates before data ever reaches the network.

This thesis treats each mechanism with engineering precision: how it works, what it costs, when it fails, and how the four interact. Wherever possible we ground claims in the Trino 483 documentation, the Project Tardigrade launch record, and the performance-tuning literature [1][2][3][5].

> **Thesis claim:** Trino's performance is governed less by raw per-node throughput than by *data movement decisions* — where exchanges are placed, how joins are distributed, and how much work is pushed below the scan boundary. Every major subsystem in the engine exists to minimize, parallelize, or survive that movement.

## 2 Background and Related Work

### 2.1 Lineage: from Presto to Trino

Presto was created at Facebook in 2012 by Martin Traverso, Dain Sundstrom, David Phillips, and Eric Hwang to answer a concrete pain point: Hive-on-MapReduce jobs took minutes to hours, and analysts needed interactive SQL over the same HDFS data. The founding insight was that an in-memory, pipelined, MPP execution model could deliver interactive latencies on data that was never going to fit in any single machine [3][6]. The creators later left Facebook, continued the project as PrestoSQL, and in December 2020 renamed it Trino to resolve the trademark dispute with the PrestoDB fork — an event announced on the Trino blog [3].

### 2.2 The MPP design space

Trino sits in a crowded lineage of distributed analytic engines, and its design choices are best understood comparatively:

| Engine | Execution model | Intermediate materialization | Primary target |
|---|---|---|---|
| **Trino** | MPP, pipelined pages | In-memory streaming | Interactive federated SQL |
| Apache Spark SQL | DAG, stage materialization | Disk/memory shuffle | Batch + streaming ETL |
| Apache Hive (Tez) | DAG containers | Disk | Batch warehousing |
| ClickHouse | MPP, vectorized | In-memory | Single-node-biased OLAP |
| Apache Drill | MPP, columnar | In-memory | Schema-on-read SQL |

The decisive contrast is with Spark: Trino streams pages between operators within a stage and between stages through exchanges, avoiding the stage-barrier materialization that gives Spark its fault tolerance but costs it latency [4][5]. That choice explains both Trino's speed and the historical absence of mid-query fault tolerance — the gap Project Tardigrade closed [3].

### 2.3 Columnar storage and the lakehouse

Trino's scan performance depends on columnar formats — ORC, Parquet, and the Facebook-originated DWRF — whose stripe/row-group statistics let the engine skip irrelevant data. The lakehouse table formats (Apache Iceberg, Delta Lake, Hudi) add a metadata layer of manifests, manifest lists, and partition specs that Trino's connectors exploit for file pruning before any object-store read occurs [5]. The *connector* abstraction is what keeps the engine generic: every data source implements the Connector SPI, and the engine's optimizer negotiates pushdown through it.

## 3 Methodology

This thesis is an *architecture-analytic* study rather than a benchmark paper. Our method has three parts:

1. **Source reconstruction.** We reconstruct the execution pipeline from the Trino 483 administration and installation documentation [1][2], the definitive architecture chapter of *Trino: The Definitive Guide* [4], and community curricula that instrument the planner with `EXPLAIN` and `EXPLAIN ANALYZE` [5].
2. **Cost modeling.** We formalize the exchange-placement and join-distribution decisions as cost equations parameterized by relation cardinalities, selectivities, and network bandwidth, and derive the decision boundaries the CBO approximates from statistics.
3. **Failure and trade-off analysis.** We characterize fault-tolerant execution through the retry-policy taxonomy (`NONE`, `TASK`, `QUERY`) and the exchange-manager spooling design, quantifying the checkpoint overhead against the recomputation cost it avoids [1][2][3].

All quantitative claims are either directly cited or explicitly labeled as modeled estimates derived from the documented architecture.

## 4 Deep Dive

### 4.1 The Coordinator-Worker MPP Model and Execution Primitives

A Trino cluster has exactly two roles. The **coordinator** accepts SQL over HTTP, parses it with an ANTLR grammar into an AST, analyzes it (name resolution, type checking, scope analysis), builds a logical plan, optimizes it, fragments it into stages, and schedules those stages onto workers [4]. **Workers** execute tasks: each task processes one or more *splits* — the unit of parallelism assigned by the connector, typically one file stripe or a partition range — using *drivers*, each of which runs a pipeline of operators over a split [4][5].

The data currency is the **page**: a columnar batch of rows, on the order of a megabyte, that flows from operator to operator without serialization overhead inside a stage. A driver's pipeline might be `TableScan → Filter → Project → PartialAggregation`, and pages stream through it in a tight loop. Between stages sit **exchange operators**, the subject of the next section.

```sql
-- EXPLAIN reveals the logical plan; EXPLAIN ANALYZE instruments it
EXPLAIN ANALYZE
SELECT l_orderkey, sum(l_extendedprice)
FROM lineitem
WHERE l_shipdate >= DATE '1994-01-01'
GROUP BY l_orderkey;
```

`EXPLAIN ANALYZE` reports estimated versus actual row counts at every plan node — the single most important diagnostic in Trino performance work, because a large estimate/actual divergence indicts the statistics the CBO consumed [5].

### 4.2 The Exchange Fabric: Repartition, Broadcast, Gather

When a stage's output must be redistributed to feed the next stage, Trino inserts an exchange. The distributed plan uses three exchange types:

| Exchange | Semantics | Typical use |
|---|---|---|
| **REPARTITION** | Hash-partition pages by key across downstream tasks | Shuffle for partitioned joins and aggregations |
| **REPLICATE** | Broadcast every page to every downstream task | Small build side of a broadcast join |
| **GATHER** | Collect all pages onto a single task | Final aggregation, `ORDER BY`, output |

Exchanges operate in two modes. **Streaming exchanges** forward pages as they arrive, preserving pipelining; **materialized exchanges** buffer pages at the producer before consumers read them, which is required for fault-tolerant execution because spooled pages become the checkpoint [1][2].

The join distribution decision is the highest-leverage call the optimizer makes. For a join of relations R (probe) and S (build) with cardinalities |R|, |S| over N workers with per-byte network cost β:

- *Partitioned join cost* ≈ β · (|R| + |S|) — both sides shuffled on the join key;
- *Broadcast join cost* ≈ β · |S| · N — the build side replicated to every worker.

> **Theorem (Broadcast threshold):** A broadcast join dominates a partitioned join iff |S| · N < |R| + |S|, i.e. when the build side is smaller than the probe side by roughly the worker factor. The CBO evaluates exactly this inequality — with |S| estimated from statistics — to choose `REPLICATE` versus `REPARTITION` [4][5].

This is why stale or missing statistics are a performance emergency: with no estimate of |S|, the optimizer cannot place the exchange correctly, and a multi-terabyte accidental broadcast is the canonical Trino outage [5].

### 4.3 Cost-Based Optimization: Statistics, Join Enumeration, Dynamic Filtering

Trino's optimizer is rule-based at its core, but the rules that matter are *cost-driven*. The CBO consumes statistics gathered by `ANALYZE` — row counts, null fractions, distinct-value counts (via HyperLogLog sketches), and low/high bounds per column — and propagates them through the plan to estimate intermediate cardinalities [4][5].

Three CBO behaviors deserve close attention:

1. **Join enumeration and reordering.** For multi-way joins the optimizer explores orderings with dynamic programming over subsets, bounded by `optimizer.max-reordered-joins`, pruning the exponential space with the cost model. The `optimizer.join-reordering-strategy` session property (`AUTOMATIC`, `ELIMINATE_CROSS_JOINS`, `NONE`) controls aggressiveness [5].
2. **Join distribution selection.** As derived in §4.2, estimated build-side size selects broadcast versus partitioned execution — automatically, per query, per join [4].
3. **Dynamic filtering.** At runtime, the build side of a join collects a filter — typically min/max ranges or a Bloom filter over the join keys — and ships it to the probe-side scan *before the scan completes*, letting the connector skip files and row groups that cannot join [5]. Dynamic filtering is the bridge between the optimizer's static plan and runtime data: it converts join selectivity discovered mid-query into scan pruning.

```sql
-- Statistics are the CBO's eyes; collect them after large writes
ANALYZE hive.warehouse.lineitem;
-- Then verify estimates against reality
EXPLAIN ANALYZE SELECT ... ;  -- compare "estimated" vs "actual" rows
```

A healthy Trino deployment treats `ANALYZE` freshness as a production concern, not a tuning nicety [5].

### 4.4 The Connector SPI and Lakehouse Pushdown

The Connector SPI is the contract between the generic engine and the specific storage. A connector provides metadata operations (list tables, get splits, provide partition layouts) and data operations (read pages, apply pushed-down operations). The optimizer negotiates pushdown through this interface, and the taxonomy of what can be pushed is precise [5][7]:

- **Predicate pushdown:** `WHERE` clauses become file/row-group filters at the source (e.g., Parquet min/max statistics, Iceberg manifest evaluation).
- **Projection pushdown:** only referenced columns are read — critical for wide tables where a query touches 3 of 200 columns.
- **Aggregation pushdown:** partial aggregates computed in the storage engine.
- **Limit and TopN pushdown:** early termination of scans.
- **Dynamic filtering:** runtime join-key filters injected into scans, as described in §4.3.

The Iceberg connector is the showcase. Because Iceberg maintains manifest files recording per-file partition values and column bounds, the connector can prune the file set from metadata alone — turning a petabyte-scale logical scan into a few hundred file reads when the query is selective [5]. This is the mechanism by which pushdown converts network-bound queries into *metadata-only* queries: the engine never asks the object store for data it can prove irrelevant.

> **Design principle:** engine behavior and connector behavior must be reasoned about separately. "Trino does not support X" is usually sloppy; the precise statement names whether planning (engine), pushdown (connector), or file layout (format) is the limiting factor [5].

### 4.5 Fault-Tolerant Execution: Retries Against Spooled Exchanges

Classic Trino had a hard failure semantic: lose a worker mid-query and the query fails. Project Tardigrade (announced 2022) introduced fault-tolerant execution by *materializing* exchanges: intermediate pages are spooled to durable storage through an **exchange manager** (filesystem, S3, Azure Blob, GCS, or HDFS), so a failed task can be retried from the last completed stage boundary instead of restarting the query [1][2][3].

Configuration is explicit and cluster-wide [1][2]:

```properties
# config.properties — retry policy for the whole cluster
retry-policy=TASK

# exchange-manager.properties — where spooled pages live
exchange-manager.name=filesystem
exchange.base-directories=s3://exchange-spooling-bucket
```

The retry policy taxonomy matters [1]:

| Policy | Granularity | Best fit |
|---|---|---|
| `NONE` (default) | No retries | Interactive ad-hoc queries |
| `TASK` | Retry failed tasks from spooled state | ETL on preemptible/spot workers |
| `QUERY` | Retry the whole query | Small queries where task overhead dominates |

Fault tolerance is not free: materializing exchanges adds write/read round-trips to durable storage and checkpoint coordination, which measurably increases latency for short interactive queries — the documented reason it is disabled by default and why practitioners split ETL and interactive workloads onto separate clusters [3][8]. The AWS EMR experience report demonstrates the intended use case: Trino on EC2 Spot instances, where worker preemption is routine, becomes viable because `TASK` retries absorb the interruptions [8].

## 5 Empirical Results and Proofs

We consolidate the documented evidence into three quantitative statements.

**Result 1 — Exchange placement dominates join cost.** From the cost equations of §4.2, misplacing a single exchange on a 10 TB probe / 50 GB build join over 100 workers converts an ~50 GB broadcast into a ~10 TB shuffle — a *200×* inflation of network traffic from one wrong decision. This is the analytic justification for the community guidance that statistics freshness is the highest-leverage tuning action in Trino [5].

**Result 2 — Dynamic filtering compounds scan pruning.** When the build side is selective, dynamic filters propagate join selectivity into the probe scan *before* full data movement. In the federated-analytics curriculum, combining partition pruning, Parquet row-group statistics, and dynamic filters reduces scanned bytes by one to two orders of magnitude on selective TPC-H-style queries relative to naive full scans [5]. The mechanism is multiplicative: each pruning layer operates on the residue of the previous one.

**Result 3 — Fault tolerance trades latency for completion.** The Tardigrade launch report documents long-running ETL suites that failed intermittently on non-resilient clusters completing reliably with fault-tolerant execution enabled; the price is checkpoint overhead that makes short interactive queries slower, motivating workload separation [3][8].

> **Theorem (FTE break-even):** Let p be the per-stage failure probability, R the recomputation cost of restarting a query, and C the checkpoint overhead per stage over s stages. Fault-tolerant execution reduces expected cost iff s·C < p·R·(expected restarts). For long ETL (large R, non-trivial p on spot infrastructure) the inequality favors FTE; for short ad-hoc queries (small R) it does not — matching the documented operational guidance [1][3][8].

## 6 Limitations and Open Problems

1. **Statistics dependence.** The CBO is only as good as its inputs. Stale statistics after bulk loads, skewed distributions that defeat distinct-value sketches, and correlated predicates (which the independence assumption mishandles) all produce misestimated cardinalities and therefore misplaced exchanges [5]. Automatic statistics collection remains an open operational problem.
2. **Fault tolerance is opt-in and coarse.** FTE is disabled by default, configured per cluster rather than per query, and its checkpoint overhead penalizes the interactive workloads Trino is famous for — forcing the two-cluster split [1][3].
3. **Connector heterogeneity.** Pushdown capability varies by connector; a query plan that is optimal against Iceberg may be pessimal against a JDBC source that cannot evaluate predicates. The engine cannot push down what the connector does not implement [5][7].
4. **Memory management.** Trino is an in-memory engine with spill-to-disk as a safety valve, not a design center; queries with large build sides or explosive intermediate cardinalities hit `EXCEEDED_MEMORY_LIMIT` unless carefully provisioned with memory limits, spill paths, and resource groups [5].
5. **Coordinator scaling.** Parsing, analysis, optimization, and scheduling are centralized; extremely high query concurrency or enormous plan shapes stress the coordinator before workers saturate.
6. **No storage, no transactions.** Trino deliberately owns no durable state, so exactly-once ETL semantics must be constructed above it (e.g., Iceberg snapshot isolation), not within it.

---

## 7 Conclusion

Trino's architecture is a study in the economics of data movement. The MPP engine pipelines pages through operators; the exchange fabric decides how those pages cross the network; the cost-based optimizer decides where the exchanges go using statistics as its price signals; the connector SPI pushes work below the scan boundary so movement never happens; and fault-tolerant execution checkpoints the movement so failures cost retries instead of restarts. Each subsystem is individually well-engineered, but the system's true behavior emerges from their interaction — a stale statistic misplaces an exchange, a missing pushdown multiplies a scan, an absent retry policy turns a spot preemption into a failed ETL run. Practitioners who internalize this interaction model — *read EXPLAIN ANALYZE, keep statistics fresh, know your connector's pushdown surface, and match retry policy to workload* — will extract the order-of-magnitude performance Trino was built to deliver [1][4][5][8].
