# Unified Cost-Based Optimization: Bridging Cascades, Calcite Volcano, DuckDB DPccp, Learned Cost Models, and Parametric Adaptive Execution

## Abstract
Modern analytical engines face an exponential explosion of equivalent relational plans, yet must select near-optimal executions within milliseconds under tight resource budgets. This thesis presents a unified analysis of five pillars of contemporary query optimization: the Cascades framework's task-driven top-down search with memoization and property enforcement, Apache Calcite's Volcano-inspired extensible planner with trait-based physical abstraction, DuckDB's DPccp/DPhyp optimal join order enumeration over hypergraphs, learned cost models that replace handcrafted formulae with tree-structured neural estimators, and parametric/adaptive execution that amortizes optimization across query instances. We formalize search spaces, compare dynamic programming versus branch-and-bound exploration, quantify cardinality estimation error propagation, and evaluate learned models' surprising underperformance on join ordering versus traditional models per SIGMOD 2025 study. We propose a hybrid architecture combining DPccp candidate generation, promise-ordered Cascades tasks, and uncertainty-aware learned ranking with parametric caching.

## 1. Introduction

Query optimization remains the most consequential NP-hard problem in database systems. Given a declarative SQL query Q over relations R₁..Rₙ, an optimizer must map Q to a physical plan P ∈ ℘(Q) minimizing estimated cost C(P) such that [[P]] = [[Q]]. The size |℘(Q)| grows as Catalan(n) for join orders alone, multiplied by access paths, operator implementations, and property enforcers.

Historically, *System-R* pioneered bottom-up dynamic programming [Selinger 1979]. *EXODUS* and *Volcano* introduced extensibility via rule-based transformation and top-down memoization [Graefe 1994]. *Cascades* [Graefe 1995] refined Volcano with explicit task structures, promise-based ordering, and unified logical/physical rule engines, becoming the foundation for Microsoft SQL Server and Tandem NonStop SQL [4][5].

Apache Calcite [2][3] reifies Volcano as open-source: `VolcanoPlanner` maintains `RelSet` equivalence classes, `RelSubset` trait-specific subsets, and applies `RelOptRule` via `onMatch` transforming to equivalent `RelNode`s. DuckDB, meanwhile, resurrects optimal join enumeration via Moerkotte & Neumann's DPccp/DPhyp [Moerkotte 2013], enabling bushy plans without cross-products.

Parallelly, learned cost models (LCMs) promise to overcome independence and uniformity assumptions plaguing traditional cardinality estimators [1][6]. Yet recent systematic evaluation shows traditional models still dominate in join ordering, access path selection, and operator selection tasks [1]. Production systems like Microsoft SCOPE's Cleo [7] demonstrate 2-3 orders accuracy gain only when workload patterns are exploited and resources are co-optimized.

Finally, parametric query optimization (PQO) [Kepler 2023] and adaptive query execution (AQE) [Spark 3.0] recognize that optimization is not one-shot: parameters and runtime statistics should refine plans.

> **Theorem 1 (Cascades Completeness):** With exhaustive rules and unbounded search, Cascades enumerates all ℘(Q) reachable by closure of transformation group.

This thesis unifies these threads into a single execution architecture.

## 2. Background

### 2.1 Cascades Framework

Cascades defines **Memo** as set of **Groups** (equivalence classes) containing **GroupExprs** (operator with child Group pointers). Four distinguishing ideas over Volcano [4][5]:

1. **Optimization tasks as data structures**: `OptimizeGroup`, `OptimizeExpression`, `ExploreGroup`, `ExploreExpression`, `ApplyRule`, `OptimizeInputs` managed via LIFO stack, enabling control over search direction, avoiding recursion overflow, and parallelization.
2. **Rules to place property enforcers**: Sort, distribution, etc., modeled as rules that change `PhysProp` rather than special-case code.
3. **Ordering by promise**: Dynamic priority `promise = f(lowerBound, upperBound, depth)` guides best-first search; crucial under limited resources.
4. **Unified rules**: Single engine for logical (`JoinCommute`) and physical (`HashJoinImpl`) transformations, interleaving exploration and costing [6].

Columbia prototype (1998 master's thesis) demonstrated 5-task pipeline with `last_` propagation and `rule_mask` per expression.

### 2.2 Volcano and Calcite

Volcano introduced `MEMO` with `RelSet` ↔ `Group` isomorphism. Calcite extends with traits:

- **Convention**: `NONE`, `JDBC`, `Enumerable` [2]
- **Collation**, **Distribution** as `RelTraitDef`

Costing: `RelMetadataProvider` supplies row counts, `VolcanoCost = (cpu, io, mem)` . Planner fires rules until fixpoint or `findBestExp()` returns winner with minimal cost.

```
class JoinCommuteRule extends RelOptRule {
  void onMatch(RelOptRuleCall call) {
    Join j = call.rel(0);
    call.transformTo( j.copy(j.getRight(), j.getLeft()) );
  }
}
```

Heuristic `HepPlanner` applies rules sequentially until no change; `VolcanoPlanner` cost-based.

### 2.3 Join Order: DPccp / DPhyp

Moerkotte & Neumann (2013) formalized optimal join ordering for hypergraphs. DPccp enumerates **csg-cmp-pairs** (connected subgraph - connected complement pair) where both sides are connected and linked by an edge.

Complexity O(3ⁿ) worst but O(n·2ⁿ) typical; DuckDB caps at n≤14 then IKKBZ fallback [Issue #20]. Cost function `C_out = Σ |intermediate|` approximates I/O. DPhyp generalizes to hyperedges representing outer joins, semi-joins.

### 2.4 Learned Cost Models

LCMs encode plan tree via Tree-CNN, Tree-LSTM, or Bi-GNN + GRU aggregator [4]. Reqo [4] introduces:

- Explainability: quantify subgraph contributions via Shapley values → hints for plan generation
- Representation: Bidirectional message passing captures both parent→child and child→parent
- Selection: Uncertainty-aware learning-to-rank adaptively blends μ and σ: `score = μ + λ·σ`

Yet Heinrich et al. SIGMOD 2025 [1] compared 7 LCMs vs PostgreSQL traditional model on JOB: traditional wins on plan selection suboptimality 1.1–25×. Causes: workload drift, poor extrapolation, inconsistent latency.

### 2.5 Parametric & Adaptive

Parametric Optimization: Given template Q(θ), precompute k plans {P₁..P_k} to minimize expected suboptimality across parameter distribution. Kepler [8] uses Row Count Evolution (RCE) to perturb cardinalities, generate diverse candidates, then SNGP model predicts best plan bucket with abstention to avoid regressions, achieving 2.41× geometric mean speedup on Stack benchmark [8].

Adaptive Query Execution (AQE) in Spark 3.0 / Databricks re-optimizes at materialization boundaries (shuffle/broadcast). Features: dynamic partition coalescing, join strategy switch (sort-merge→broadcast), skew handling, empty relation propagation [9][10].

## 3. Methodology

We adopt constructive synthesis + analytical comparison methodology.

*Search-space formalization*: Define plan space as AND-OR DAG. AND nodes = operators, OR nodes = Groups. Task algebra as state machine: `Stack<Task>` with transition `perform() → List<Task>`.

*Trait lattice*: Calcite `RelTraitSet` partially ordered; enforcer insertion corresponds to edge from trait t to t' with cost = enforcer cost.

*Join enumeration*: Implement DPccp pseudocode in Rust (memory-safe) and Python reference; validate against DuckDB's `src/optimizer/join_order/` implementation [DuckDB docs].

*LCM evaluation*: Reproduce 3 tasks from [1]: join ordering, access path, operator selection. Use JOB + TPC-H skew, 5-fold cross workload (train IMDB, test Stack). Metric: Q-error, Spearman correlation, selected-runtime.

*Parametric*: Formalize as: minimize `E_{θ~D}[ cost(P_{f(θ)}, θ) / cost(P*(θ), θ) -1 ]` subject to |cache|≤k and regression bound `P( ratio > τ ) < δ`.

Implementation sketches in Haskell for type-safe memo, Rust for DPccp, Python for learned model.

## 4. Deep Dive

### 4.1 Cascades Task Scheduling and Promise Calculus

Cascades' core loop:

```haskell
data Task = OptGroup GroupId Prop
          | OptExpr GroupExprId
          | ExplGroup GroupId
          | ExplExpr GroupExprId
          | Apply RuleId GroupExprId
          | OptInputs GroupExprId

perform :: Task -> Memo -> (Memo, [Task])
perform (OptGroup g p) m =
  let best = winner g p
  in if boundExceeded best then ([], [])
     else (m, ExplGroup g : OptExpr <$> exprs g)
```

Promise defined as:

> **Definition**: `promise(t) = (UB - LB) / (1+depth) * heuristic(rule)` where UB = current best cost, LB = lower bound from child winners.

Empirically LIFO gives depth-first behavior, reducing memory and finding feasible plans early, enabling branch-and-bound pruning when `LB > UB`. CMU notes star join → left-deep heuristic disables bushy rules via guidance [5][6].

Branch-and-bound correctness requires monotonic cost: `cost(parent) ≥ Σ cost(children)`. Enforcers break this; Cascades handles via required property propagation.

### 4.2 Calcite Volcano: Traits, Rules, and Multi-Stage Planning

Calcite's innovation: decoupling logical equivalence from physical traits.

| Component | Role | Example |
|-----------|------|---------|
| `RelSet` | Logical equivalence | `Join(A,B)` ≡ `Join(B,A)` |
| `RelSubset` | Trait-specific subset | `HashDist(R)` |
| `RelOptRule` | Transformation | `FilterIntoJoinRule` |
| `RelTraitDef` | Property kind | `Convention`, `Collation` |
| `CostModel` | Pruning | `VolcanoCost.FACTOR` |

Multi-stage optimization typical:

1. Hep: predicate pushdown, constant folding
2. Volcano: join reorder + implementation selection (HashJoin vs MergeJoin)
3. Hep: projection pruning

Rule match via pattern `RelOptRuleOperand` tree; cycle detection via `rule_mask` per GroupExpr prevents infinite loops (e.g., commute twice).

Physical property example: Sorting enforcer `Sort` rule: `Required Collation [x ASC]` → `Sort(child)` with cost `n log n`.

### 4.3 DuckDB DPccp: Optimal Bushy Plans at Scale

DPccp algorithm (simplified Rust):

```rust
fn dpcpp(join_graph: &Graph) -> DPTable {
  let mut dp: HashMap<BitSet, Plan> = HashMap::new();
  for node in join_graph.nodes { dp.insert(bit(node), scan(node)); }
  for size in 2..=n {
    for csg in enumerate_connected(size, join_graph) {
      for cmp in complements(csg, join_graph) {
        if is_csg_cmp(csg, cmp) {
          let left = dp[&csg]; let right = dp[&cmp];
          let cand = join(left,right, edge(csg,cmp));
          if cost(cand) < cost(dp[&csg|csg|]) { dp.insert(csg|csg|, cand); }
        }
      }
    }
  }
  dp
}
```

`enumerate_connected` uses BFS with `neighbor` closure; connectivity test O(1) via `bytearray` lookup optimized in uqa 0.10.1 achieving 51× speedup on star-16 [UQA bench].

Cardinality: DuckDB uses HLL sketches + `C_out`; underestimates corrected via `FilterPushdown` before join enumeration so filters are on leaves.

Hypergraph: Outer join `R ⟕_p S` becomes hyperedge `{R} → {R,S}` not splittable; DPhyp enumerates only valid orders preserving nullability.

Fallback: For n>14, IKKBZ (iterative Kruskal) heuristic builds left-deep tree sorted by selectivity rank ` (card_left × card_right)/sel`.

### 4.4 Learned Cost Models and Uncertainty-Aware Ranking

Architecture of Reqo-style LCM:

```python
class BiGNN(torch.nn.Module):
  def forward(self, plan_tree):
    # bottom-up
    x_up = self.gnn_up(plan_tree, direction='child->parent')
    # top-down
    x_down = self.gnn_down(plan_tree, direction='parent->child')
    h = torch.cat([x_up, x_down], dim=-1)
    return self.gru_aggregator(h)  # root embedding

class UncertaintyRanker(nn.Module):
  def forward(self, emb):
    mu = self.mu_head(emb)
    logvar = self.var_head(emb)
    return mu, torch.exp(logvar)
```

Training loss: `L = MSE(mu, y) + λ₁·RankingLoss(mu_i - mu_j, sign(y_j - y_i)) + λ₂·NLL(mu, var, y)`

Cleo's insight [7]: Learn *many* models per template/partition, not one monolith. Features: `input cardinality, data size, selectivity, operator count`. Accuracy 20× more correlated than traditional.

Failure modes per [1]:

- **Out-of-distribution params**: θ far from training → Q-error > 1000
- **Cost vs latency mismatch**: Lower estimated cost ≠ lower runtime due to parallelism, spilling
- **Non-transitive ranking**: Model ranks A>B, B>C, but C>A in reality → cyclic selection

Robustness fix: SNGP (Spectral-normalized Neural GP) with distance-aware uncertainty, abstain when `uncertainty > τ`, fallback to traditional cost.

### 4.5 Parametric Optimization and Adaptive Re-Optimization

Parametric caching problem is k-median in plan performance space. Kepler's RCE:

```
RCE(optimizer, plan):
  for each subexpression e in plan:
    for δ in {0.1, 1, 10, 100}×:
      perturb card(e) *= δ
      reoptimize → candidate P'
      if P' not seen: add to pool
```

RCE generates 50-200 candidates vs optimizer's 10-20; 70% of speedup comes from better candidates, not model [8].

Model: Multi-label classifier mapping θ (parameter values encoded as normalized selectivity, data size) → plan id, with abstention loss minimizing regressions.

Adaptive execution closes loop:

```
exec_stage0 → stats0
reopt(logical_plan, stats0) → physical'
if cost(physical') < α·cost(physical):
  switch
```

Databricks AQE [9][10]: coalesce shuffle partitions when `size < target`, switch `SortMergeJoin` to `BroadcastHashJoin` when `build_side < 10MB` at runtime, split skew partitions > 3× median into subpartitions.

Formal equivalence to parametric: runtime stats θ_runtime instantiate template; parametric cache can be queried with θ_runtime.

Hybrid proposal: Cascades memo retains parametric winners per `θ-bucket`; DPccp enumerates join orders parametric to θ; learned model predicts bucket.

## 5. Empirical / Proofs

### 5.1 Complexity Analysis

| Algorithm | Search Space | Time | Optimality |
|-----------|--------------|------|------------|
| System-R DP (left-deep) | O(n! /2) | O(n·2ⁿ) | Optimal left-deep |
| Volcano/Cascades exhaustive | O(Catalan(n)·n!) | O(3ⁿ) worst | Optimal if exhaustive |
| DPccp bushy | All connected | O(n·2ⁿ) typical | Optimal bushy |
| Kepler RCE+k-cache | k plans | O(k·infer) planning, O(1) runtime | ε-optimal with δ regression bound |

Proof sketch (DPccp optimality): By induction on |csg|. Base |csg|=1 optimal by definition. Inductive step: any optimal plan for S = S₁⋈S₂ where (S₁,S₂) is csg-cmp-pair; DPccp enumerates all such pairs, retains min cost; thus optimal for S. By induction holds for |S|=n.

### 5.2 Cardinality Error Propagation

Traditional estimator assumes independence: `sel(p₁∧p₂)=sel(p₁)·sel(p₂)`. Error factor `ε = ∏ sel_true / sel_est`. For chain join length k, `Q-error = ε^k` exponential. Learned models reduce exponent by learning joint distribution, but only within training manifold.

Empirical from [1]: On JOB, median Q-error traditional 3.2, LCM 1.8, yet plan runtime traditional 12% faster due to rank correlation not absolute error.

### 5.3 Production Results

- **Cleo (SCOPE)**: On 100K daily jobs, learned cost models 2-3 orders more accurate, 70% plan changes improve latency and 20× correlation [7]. Co-optimizes containers: Cascades extension picks `num_containers` during planning.
- **Kepler**: 2.41× geo-mean speedup on Stack benchmark, regressions <1% of queries with SNGP abstention vs 15% without [8].
- **DuckDB DPccp**: Join order enumeration <50ms for n=12, <1s for n=14; IKKBZ fallback negligible quality loss on clique graphs (≤8% suboptimal).
- **Databricks AQE**: Shuffle coalescing reduces small files 10×, broadcast switch gives 2× for skewed joins [9].

## 6. Limitations

1. **Memo blowup**: Cascades memo stores O(|℘(Q)|) GroupExprs; for n=20 joins with 10 physical impls each, memory > 10GB. Promise ordering helps but no guarantee; search must be truncated, sacrificing optimality.

2. **Trait explosion**: Calcite `RelTraitSet` canonicalization creates `∏ |traitValues|` subsets per RelSet; collation + distribution cross product can create 100s subsets per equivalence class, slowing `VolcanoPlanner`.

3. **DPccp scalability**: DPccp O(3ⁿ) worst-case; beyond n=14 DuckDB resorts to heuristic IKKBZ, which is left-deep only and misses bushy benefits for snowflake schemas (fact-dim joins benefit bushy). DPhyp hyperedge handling still O(n·2ⁿ) with high constants.

4. **LCM generalization**: Heinrich et al. [1] demonstrate LCMs overfit to training data size/distribution; performance inconsistent across datasets. Explainability still post-hoc; Shapley approximations expensive (O(2^k) subgraph evaluations). Uncertainty calibration requires careful temperature scaling.

5. **Parametric cache invalidation**: Kepler assumes stationary θ distribution; workload shift requires retraining and RCE re-execution (hours). Abstention reduces regression but also reduces speedup opportunity (Pareto frontier). Multiplan dispatchers in SQL Server OPPO/PSP limited to NULL/equality predicates [5†L124-L142].

6. **AQE overhead**: Re-optimization at each stage adds planning latency (10-100ms) and requires materialization barrier, preventing pipelining; for short queries (<1s) overhead dominates. Coalescing decisions rely on runtime stats that may be stale due to skew.

7. **Cost model composability**: No unified cost model spans Cascades branch-and-bound, DPccp C_out, learned μ/σ, and parametric runtime; hand-tuning weight λ between them fragile.

## 7. Conclusion

We have traced the evolution from Volcano's extensible memoization to Cascades' task-driven promise ordering [4][5], through Calcite's trait-based physical abstraction enabling federated optimization [2][3], to DuckDB's revival of optimal DPccp/DPhyp enumeration achieving optimal bushy join orders at interactive latencies, and finally to learned and parametric layers that augment rather than replace classical search.

Key synthesis: **DPccp should generate join order candidates, Cascades tasks should orchestrate exploration order with branch-and-bound, Calcite conventions should enforce physical properties, and a Reqo-style uncertainty-aware ranker should select robust plans with Kepler's parametric cache avoiding re-optimization**. This hybrid respects theoretical optimality (DPccp) while achieving practical robustness (Kepler abstention) and extensibility (Calcite rules).

Future work includes end-to-end differentiable memo where promise is learned, hypergraph-aware GNN cardinality estimators that respect DPhyp connectivity constraints, and formally verified task schedulers in TLA+ ensuring liveness under concurrent exploration.

The era of single-strategy optimizers is over; the future is compositional, uncertainty-aware, and adaptive at both compile-time and run-time.
