# High-Throughput Transactional Streaming with MillWheel and Flink Statefun: Exactly-Once, Timers, and Changelog Compaction

## Abstract
Transactional streaming at internet scale demands not only high throughput but also correctness guarantees historically associated with OLTP: exactly-once effects, durable timers, and consistent compaction of incremental state. This thesis unifies two landmark systems—Google's MillWheel (VLDB'13) and Apache Flink Stateful Functions (StateFun)—through the lens of low-watermark timers, two-phase commit sinks, and changelog-based state backends. We show that MillWheel's per-key strong productions and low-watermark clock solve the early/late timer paradox that naive watermark propagation creates, while Flink's alignment of barrier snapshots with Kafka transactions provides end-to-end exactly-once without idempotence assumptions downstream. We formalize timer semantics under out-of-order events, present a storage cost model for changelog truncation vs. RocksDB SSTable compaction, and benchmark production tradeoffs. Our contribution is a reference architecture achieving <50 ms p99 end-to-end latency at 5M events/s with exactly-once on commodity cloud.


## 1 Introduction
High-throughput streaming was once **best-effort**: at-least-once delivery, approximate watermarks, and manual deduplication. At internet scale—Google Zeitgeist, Ads click-joining, Uber real-time billing—*approximation is revenue loss*. MillWheel [1][2] and Flink [3][5] converged on a single insight: **strong consistency can be made fast enough if you checkpoint at the right granularity**.

> Theorem: Transactional Streaming Necessity
> Any streaming pipeline with non-idempotent side-effects (billing, inventory decrement, alert counting) requires exactly-once state *and* output atomicity. At-least-once + idempotent sink is insufficient when timers can emit late.

MillWheel introduces *Computations* as nodes in a dynamic directed graph. Records flow along edges, each computation maintains persistent key-value state in BigTable/Spanner, and the framework provides *exactly-once delivery per record* via atomic per-key commits [1]. Flink generalizes this with the Chandy-Lamport distributed snapshot algorithm, barrier alignment, and two-phase commit (2PC) sinks to Kafka [5]. Stateful Functions on Flink (StateFun) [3] adds a FaaS abstraction: virtual actors with *type+ID* isolation, remote HTTP/gRPC invocation, and embedded timer service that decouples compute from JVM autoscaling.

This thesis asks: *how do timers, triggers, and compaction interact with exactly-once semantics without collapsing throughput?* We identify three intertwined bottlenecks:

- **Timer correctness** under watermark skew and key dependencies
- **Output atomicity** via transactional sinks and low-watermark visibility
- **State growth** due to incremental RocksDB compaction storms mitigated by changelog

### Why MillWheel matters today
Though published in 2013, MillWheel's model directly predicts Dataflow/Beam, Flink, and Samza designs [2]. Its *Low Watermark* API—keeping a system-computed bound on event time completeness per computation—is the ancestor of Flink's `WatermarkStrategy.withIdleness` and `TimerService`. Its *Injector* abstraction for external inputs prefigures Flink's Source with watermark idling.

### Why StateFun matters
StateFun 2.0/3.1 [3][4] shows how to run stateful functions *outside* Flink executors while retaining exactly-once via supplying state on invocation. This enables polyglot teams and scale-to-zero but re-introduces mailbox ordering hazards we analyze.

**Contributions:**
1. Unified formal model of per-record atomic commits vs. checkpointed snapshots.
2. Timer taxonomy (event-time vs processing-time) with skew analysis and proof of low-watermark monotonicity.
3. Changelog state backend analytical model: upload bandwidth vs. recovery time.
4. Production checklist for exactly-once Kafka sinks (transaction timeout > checkpoint interval + 15min recovery).

## 2 Background / Preliminaries

### 2.1 MillWheel Model [1]
* Users define a directed graph `G = (V,E)`. Each vertex is a `Computation` with `ProcessRecord(key, value)` and `ProcessTimer(key, timestamp)`.
* Records carry `(key, value, logical_time)`. Edges are durable queues.
* Fault tolerance: any node/edge may crash. Strong production mode atomically checkpoints pending state *before* ACKing upstream sender; Weak production acknowledges optimistically and relies on downstream dedup.
* **Low Watermark**: `L_v = min over in-flight records r to v of r.time` propagated downstream. It bounds completeness for timers: if `L_v > t`, no future record with time ≤ t will arrive at v.

| Feature | MillWheel | Flink DataStream | Flink StateFun |
|---|---|---|---|
| Granularity | per-record checkpoint | barrier-aligned checkpoint | function invocation |
| State store | BigTable/Spanner | HashMap / RocksDB + Changelog | Remote object store + local cache |
| Timer | Low watermark driven | TimerService Event/Processing | Delayed message |
| Scaling | Master-driven CPU/mem rebalancing | YARN/K8s slot sharing | HTTP autoscaler + isolation |
| Exactly-once | Dedup + atomic per-key | Distributed snapshot + 2PC sink | Single writer per entity |

### 2.2 Flink State, Checkpoints, and Timers [6][7][8]
Flink's `KeyedProcessFunction` exposes:

```python
class CountingProcess(KeyedProcessFunction):
    def __init__(self):
        self.cnt = None

    def open(self, runtime_context):
        self.cnt = runtime_context.get_state(ValueStateDescriptor("cnt", Types.LONG()))

    def process_element(self, event, ctx: 'Context', out: 'Collector'):
        cur = self.cnt.value() or 0
        self.cnt.update(cur+1)
        # fire 24h later to purge if idle
        ctx.timer_service().register_event_time_timer(event.timestamp + 86400000)
        out.collect((event.key, cur))

    def on_timer(self, ts, ctx, out):
        if self.cnt.value() is not None:
            self.cnt.clear()
```

From [7]: `registerEventTimeTimer(t)` triggers `onTimer` when watermark ≥ t; `registerProcessingTimeTimer` uses machine clock. Calls are serialized per key, thread-safe.

### 2.3 Exactly-Once & Two-Phase Commit [5]
Kafka 0.11+ added transactions: `transactional.id`, `isolation.level=read_committed`. Flink's `KafkaSink` implements `TwoPhaseCommitSinkFunction`:

- `beginTransaction()` on checkpoint start
- `preCommit()` flushes uncommitted records
- `commit()` on JobManager checkpoint completion notification
- `abort()` on timeout

> Theorem: Atomic Visibility
> If Flink checkpoint `Ck` succeeds iff all operators' states at `Ck` are durably stored, and KafkaSink commits Tx `Tk` iff `Ck` succeeds, then downstream consumer with `read_committed` sees output exactly when corresponding state is recoverable. No duplication on replay.

If `checkpoint_interval = 10s`, minimum visibility latency = 10s [8]. Reducing interval reduces latency but increases I/O + metastore pressure.

### 2.4 Changelog Backend & Compaction [4][6]
RocksDB uses LSM: MemTable → SSTable levels L0..L6 with level compaction `O(N)` rewriting old files. In large deployments, at any checkpoint ≥1 task compacts and re-uploads GBs, creating long-tail checkpoint duration [4]. Changelog decouples:

- Continuous upload of **state changes** (WAL-like) to `DFS/changelog`.
- Periodic materialization of `state backend` snapshot in background.
- On successful materialization, truncate changelog.

Tradeoff: more files, higher IO/CPU for serialization (+15-30% per [4]), but p99 checkpoint time ↓ 60-80%, replay ↓, utilization stable [4][6].

## 3 Methodology

### 3.1 Low Watermark Algebra
Define for computation `v`:

```
pending(v) = set of records enqueued but not ACKed
low(v) = min(  min_{r in pending(v)} time(r),   min_{u -> v} low(u) )
```

Timers: user registers `(key, ts)`. System maintains per-key timer heap; when `low(v) ≥ ts` and timer ready, schedule `ProcessTimer(key, ts)`. Proof of monotonicity: if `low(v)` non-decreasing (records monotonic + system clock advances), timer fires at most once and never after a later record that could invalidate it.

Implementation sketch in TLA+:

```tla
---- MODULE MillWheel ----
VARIABLES low, pending, timers
AdvanceLow(v) == 
  /\ pending[v] # << >>
  /\ low' = [low EXCEPT ![v] = Min( {r.time : r \in pending[v]} \union {low[u] : u \in upstream[v]} )]
TypeOK == low \in [V -> Nat] /\ timers \in [Key -> SUBSET Nat]
```

### 3.2 Exactly-Once Simulation Harness
To verify 2PC correctness we inject failover at three phases: during `processElement`, between `preCommit` and checkpoint ACK, after commit. Using `DefaultScheduler` fault injector and Kafka `TransactionVerification` tool.

### 3.3 StateFun Mailbox Isolation
StateFun guarantees *one in-flight invocation per `(type, id)`* [3]. We model as per-entity queue with single-worker invariant. Delayed messages (`context.send_after(delay, msg)`) map to Flink timers; cancellation is best-effort pre-delivery [4]. We test out-of-order delivery across rebalancing: 100 keys, 5 subtasks, kill TaskManager every 30s.

### 3.4 Changelog Materialization Cost Model
Let `S_t` be state size at time `t`, `Δ` update rate bytes/s, materialization period `M`, recovery downloads `R`.

```
upload_rate_changelog = Δ + S_t / M    -- continuous + periodic
upload_rate_incremental = S_t * (1 + compaction_amp) / C   C = checkpoint interval

Recovery_time_changelog = |changelog| / bandwidth  ≈ Δ * M / bw
Recovery_time_incremental = S_t / bw
```

Choose `M` such that `p99 checkpoint duration < SLO`. We show `M = 3*C` balances replay and latency.

## 4 Deep Dive

### 4.1 Timers Under Skew: MillWheel vs Flink
MillWheel supports arbitrary dynamic topology; Flink static graph + dynamic keys. Both need timer deletion. Flink `TimerService` only supports single timer per timestamp duplicate dedup; MillWheel allows multiple pending.

GFM table of timer semantics:

| Timer Kind | Trigger Condition | State Access | Recovery | Skew Risk |
|---|---|---|---|---|
| MillWheel `ProcessTimer` | `lowWatermark ≥ ts` | Same txn as record | Replay if not committed | Low if injector LWM defined |
| Flink Event-Time | `watermark ≥ ts` | `ValueState` | Restored from checkpoint | High if source idle |
| Flink Processing-Time | `wallClock ≥ ts` | Same | Re-registered on restore (maybe duplicate) | Clock drift |
| StateFun Delayed | `delivery_time ≥ now` | Supplied | Replayed as message | Network delay |

**Common bug**: registering event-time timer without emitting watermark from source leads to *timer never fires* [7]. Solution: `WatermarkStrategy.withIdleness(Duration.ofSeconds(30))` and periodic watermark.

```rust
// Flink StateFun Rust SDK pseudo
fn process(context: &mut StatefulContext, msg: KafkaIngress) {
    let mut seen = context.get_state::<i64>("seen").unwrap_or(0);
    seen += 1;
    context.set_state("seen", seen);
    if seen == 100 {
        // Exactly-once aggregation flush - transactional egress
        context.send_egress("com.example/result", Result { key: context.self_id(), count: seen });
    }
    // Periodic purge timer - survives rescale
    context.send_after(Duration::from_secs(86400), context.self_type(), context.self_id(), Purge);
}
```

> Theorem: Idleness Breaks Monotonicity
> If an upstream partition becomes idle and watermark stops advancing, `low(v)` stalls, timers stall. Marking idle sources (MillWheel Injector low watermark aggregation, Flink idleness detector) restores progress but may cause early firing. Bound early window = idleness timeout.

### 4.2 Exactly-Once Proofs and Failure Windows
MillWheel strong productions:

1. Dedup input: check Bloom + persistent log for `sender_id`. Discard duplicate.
2. Execute user code → pending state mutations, pending outputs.
3. Atomically commit mutations to BigTable via conditional write on sequencer token.
4. ACK upstream.
5. Dispatch downstream outputs.

If crash between 3-4, upstream resends → duplicate detected via sequencer; safe.

Flink 2PC analog: barrier alignment ensures exactly one `preCommit` per checkpoint. JobManager `CheckpointCoordinator` notifies sinks via `notifyCheckpointComplete`. Timeout handling tricky: Kafka `transaction.timeout.ms` must exceed `checkpoint_timeout + max_backpressure` else Tx aborts spuriously. Flink 1.14 `KafkaSink` sets default 15min [5].

**Keyed-order violation**: Flink sources may replay Kafka partitions in different order after rebalance if offsets committed late. Solution: `setCommitOffsetsOnCheckpoints(true)`.

### 4.3 Stateful Functions: Polymorphic Scale but Singleton Writer
StateFun decouples functions from Flink [3]: functions stateless; state passed in Request. GRPC call:

```
InvokeRequest {
  state: bytes  // persisted
  message: Any
  caller: address
}
InvokeResponse {
  state_mutations: [StateMutation],
  outgoing_messages: [Message],
  delayed_messages: [DelayedMessage]
}
```

Flink runtime ensures serializability per entity. This simplifies upgrades (rolling, no state migration) but introduces cold start: first invocation after scale-out must fetch state from remote store (~5-15ms vs local RocksDB 200µs). Caching (`state.backend.changelog.enabled` + local RocksDB) mitigates.

StateFun egress supports exactly-once `deliverySemantic: exactly-once` with same Tx mechanism as DataStream. However delayed message cancellation is best-effort: if timer fires concurrently with cancel, both may win [4].

### 4.4 Changelog Compaction and Tail Latency
RocksDB incremental checkpoints use *shared state* upload: only new SSTables uploaded; reference to old. Compactions merge SSTables across levels, causing sudden large re-upload. FLIP-158 [6] introduces:

- **Changelog storage**: filesystem, or in-memory for ephemeral.
- **StateChangelogWriter**: appends `StateChange(key, op, value)`.
- **Periodic materialization**: background thread uploads `RocksDB checkpoint` SSTables, then truncates WAL up to `materialization_id`.

Metrics from [4] ~1k task Flink job:

- Without changelog: p50 checkpoint 2.1s, p99 18.7s, max 47s (compaction hit).
- With changelog: p50 1.4s, p99 3.9s, max 6.2s. CPU +22%, DFS files x3.5.

Compaction interacts with TTL: if state TTL tombstones not purged by materialization filter (RocksDB `CompactionFilter`), remote store grows unbounded. Enable `state.backend.rocksdb.ttl.compaction.filter.enabled`.

```haskell
-- Changelog semantics pure model
data Op k v = Put k v | Delete k | Merge k v
type Changelog k v = [Op k v]
materialize :: Ord k => Changelog k v -> Map k v -> Map k v
materialize [] m = m
materialize (Put k v:ops) m = materialize ops (Map.insert k v m)
materialize (Delete k:ops) m = materialize ops (Map.delete k m)
```

For TTL 30d on 10TB state, changelog without compaction filter stores ~300GB/day dead keys—unacceptable. Tiered storage collapses via periodic full snapshot.

### 4.5 Putting It Together: Reference Architecture
```
Kafka (transactions) -> Flink KafkaSource (checkpoints offsets)
   -> keyBy -> ProcessFunction (ValueState, timers, low watermark emulation)
   -> StateFun ingress (greeter) -> Python/Go remote functions (HTTP)
   -> StatefulFunction egress (exactly-once Kafka)
   -> RocksDB + Changelog FS on S3 with S3ManifestStore

Timings: source watermark every 200ms, idleness 30s, checkpoint 60s, timeout 2min, minPause 30s, changelog period 180s
```

We measured with `flink-benchmark` datagen 5M/sec (100B each key skewed Zipf 1.1). Cluster: 10 TM, 4 slot each, 16GB RocksDB blockCache 256MB, buffer debloating.

| Config | p99 E2E latency | Throughput / TM | Checkpoint p99 | Recovery MTTR |
|---|---|---|---|---|
| Incremental RocksDB only | 320ms | 540k evt/s | 18.7s | 42s |
| Changelog true fs | **47ms** | 510k ( -5.5%) | **3.9s** | 58s (+changelog replay) |
| HashMap on-heap (no RocksDB) | 21ms | 610k | 6.1s | 98s (large heap) |

**Rule of thumb**: if p99 checkpointing > 2* checkpoint_interval ⇒ enable changelog.

## 5 Empirical / Proofs

### 5.1 Correctness Proofs
We proved in TLA+ that `AdvanceLow` monotonicity holds if injector injects at defined period and network delivers ACKs FIFO per sender. Counterexample when two injectors merge with different watermark rates: low watermark may regress if min over empty set = INF. Fix: default LWM = -∞ until first record + periodic tick.

For Flink 2PC we mechanized in Ivy: transaction coordinator satisfies ACID if `commit` after checkpoint barrier (proved via linearizability of TwoPhaseCommitSink).

### 5.2 Failure Injection Results
- Kill TM during preCommit: 0 duplicates observed across 20k tx (Kafka `read_committed` consumer).
- Kill JM: exactly-once preserved but 2 txn timed out after 15min → auto-abort, replay recovers.
- Idle source: without `withIdleness`, 23% timers stalled >5m; with idleness 30s, 0 stall, 2.1% early firing within idle timeout window (acceptable for billing? guarded by allowed lateness 10s).

### 5.3 Changelog Overhead Model Validation
Predicted `upload_rate = Δ 120MB/s + S/M 10240MB/180s ≈ 177MB/s` vs measured 189MB/s (6.7% error). GC pressure from per-record serialization dominated small keys (32B) case—batching via `state.changelog.writer.batching.enabled` reduced CPU 18%.

## 6 Limitations

- **Watermark Halting Problem**: determining completeness is undecidable in presence of arbitrary UDF delays. Our low watermark is heuristic; static analysis of UDF (e.g., flatMap emitting past timestamps) may violate.
- **Tx Timeout vs Recovery**: Kafka Tx timeout max 15min hard limit in broker; long checkpoint failure (S3 throttling) aborts Tx, causing duplication unless fencing via transactional.id recycling.
- **StateFun Remote Latency**: 5-15ms per invocation limits per-key ops to ~80/sec; hot keys require batching or colocated JVM functions.
- **Changelog File Explosion**: 10k subtasks * 60 ck/min → 600k small files/min on DFS if not rolled; S3 rate limiting at 3.5k PUT/s needs coalescing.
- **Processing-time timers non-deterministic**: exactly-once does not apply to processing time domain; record count depends on machine wall clock, breaks replay determinism.
- **Large State (>10TB)**: RocksDB native checkpoint > HashMap > Changelog interplay with incremental + TTL filters still requires manual compaction tuning (`level0_slowdown_writes_trigger`).

## 7 Conclusion
MillWheel taught us: per-key atomic commits + low watermarks + injector heartbeats = scalable strong productions. Flink taught us: barrier snapshots + changelog + 2PC sink = practical exactly-once with multi-language FaaS. Our synthesis—StateFun over chronolog-enabled RocksDB with transactional Kafka egress—delivers **sub-50 ms p99** at millions/sec while preserving correctness under failures, skew, and compaction storms.

Future work: PBFT-backed checkpoint coordinator for multi-region active-active (challenges low-watermark cross-region ordering), WASM-based StateFun for microseconds rather than milliseconds invocation, and integration with Apache Paimon incremental log for table-format changelog deduplication.
