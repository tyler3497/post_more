# Multi-Stage Programming and the Futamura Projections: Staging, Partial Evaluation, and Generative Metaprogramming in LMS

## Abstract

---

## 1 Introduction

The tension between *generality* and *performance* is arguably the oldest in software engineering. We write general programs — interpreters, generic libraries, query planners parameterized by schemas — because generality is maintainable; we then pay for that generality at runtime, once per input, in interpretive overhead. Compilation is the traditional escape hatch, but compilers are expensive to build and maintain, and each new domain-specific language (DSL) demands another.

In 1971, Yoshihiko Futamura observed that compilation need not be built at all: it can be *computed*. Given a partial evaluator — a program `mix` that specializes a two-input program with respect to its first input — and an interpreter `int` for a language *S*, the equation `target = mix(int, p)` produces a program that runs `p` without re-interpreting it; it is, in every behaviorally relevant sense, a compiled version of `p`. Feed `mix` *itself* to `mix`, and the result is a compiler: `comp = mix(mix, int)`. Feed `mix` to itself twice, and the result is a compiler generator — a program that manufactures compilers from interpreters. These are the **Futamura projections** [1][2].

The projections are beautiful, and for decades they were nearly unusable in practice: specializing a specializer requires binding-time analyses subtle enough that only a handful of systems (notably Jones's *mix* and its descendants) ever achieved genuine self-application. The field responded by changing the contract. Rather than *inferring* which computations can be performed early, multi-stage programming languages ask the programmer to *declare* the staging structure explicitly, using quotation and escape annotations [3]. This trades automation for control and predictability. Lightweight Modular Staging [4] pushes the idea further still: binding times are distinguished not by syntax but by **types** — `Rep[T]` marks values computed at a later stage — so that staging becomes an ordinary library feature of a host language, complete with a graph-based intermediate representation, common subexpression elimination, and code motion.

## 2 Background

### 2.1 Partial evaluation and the *mix* equation

Partial evaluation, or *program specialization*, is the execution of a program with only some of its inputs available. Let a source program `p` take a static input `s` (known early) and a dynamic input `d` (known late). A partial evaluator `mix` satisfies the defining equation [2][5]:

> **Definition (The *mix* equation).** For all programs `p`, static data `s`, and dynamic data `d`:
> `⟦mix⟧(p, s)(d) = ⟦p⟧(s, d)`
> where `⟦·⟧` denotes the semantic evaluation function. The residual program `p_s = mix(p, s)` is *behaviorally equivalent* to `p` with `s` fixed, but specialized.

In computability theory this is Kleene's *s-m-n* theorem: every acceptable numbering of the partial computable functions admits a total computable function *s* with `φ_{s(e,x)}(y) = φ_e(x,y)`. Futamura's contribution was to read the theorem as an *engineering* principle [1].

Two architectures dominate implementations. **Online** partial evaluators make specialization decisions during specialization, using the actual static values; **offline** partial evaluators first run a *binding-time analysis* (BTA) — an abstract interpretation over the two-point domain `{static, dynamic}` — that annotates every subexpression, and then follow the annotations mechanically [2]. Offline specialization is faster and more predictable; online specialization is more powerful. Jones's group at DIKU demonstrated both, culminating in self-applicable systems where `mix` could specialize `mix` [2][5].

### 2.2 From automatic specialization to explicit staging

Automatic partial evaluation has an Achilles' heel: the programmer cannot easily predict or control *what* gets specialized, and termination is fragile — an unfolding loop at specialization time diverges the specializer. The multi-stage programming tradition, launched by Taha and Sheard [3], inverts the design: the programmer writes **staging annotations** that say explicitly which code runs at which stage. The three canonical constructs, inherited from Lisp's quasiquotation and refined in MetaML and MetaOCaml, are:

| Construct | Syntax | Meaning |
|---|---|---|
| Brackets (quotation) | `.<e>.` | Build a code value representing `e`, to run at a later stage |
| Escape (splice) | `.~e` | Evaluate `e` now and splice the resulting code into the enclosing bracket |
| Run | `run e` | Compile and execute a closed code value now |

A staged power function illustrates the style:

```haskell
-- MetaOCaml-style staging: the exponent is static, the base dynamic
pow : int -> .<int -> int>.
pow n = if n = 0 then .<fun x -> 1>.
        else .<fun x -> x * .~(pow (n-1)) x>.
```

Evaluating `pow 3` at staging time yields the residual code `.<fun x -> x * (x * (x * 1))>.` — the loop is gone, unrolled by the generator. No binding-time analysis was needed; the *types* (`int` vs `.<int>.`) enforce the phase distinction, and scope extrusion (a bound variable escaping its bracket) is rejected statically [3].

### 2.3 Binding times as a design space

Whether inferred by BTA or declared by annotation, every staging system partitions computation along a single axis: **binding time**. Static computations happen at generation time and vanish from the residual program; dynamic computations are residualized into generated code. The following table summarizes the design space:

| System | Binding times decided by | Notation | Self-applicable? |
|---|---|---|---|
| Jones's *mix* (offline PE) | Binding-time analysis | Annotations from BTA | Yes (the hard way) |
| MetaML / MetaOCaml | Programmer annotations | `.<·>.`, `.~`, `run` | Not required |
| Template Haskell | Programmer annotations | `[|·|]`, `$(·)` | No |
| LMS | Types | `Rep[T]` vs `T` | By construction (library) |

LMS's row is the distinctive one: because staging is expressed entirely through the type system of the host language, no new syntax, parser, or type checker is required — staging is a library, and the "compiler" it embeds is an ordinary, composable program [4][6].

## 3 Methodology

Our methodology is *equational and constructive*. We take the *mix* equation as axiomatic, derive the three Futamura projections as theorems, and then examine the two mechanisms — automatic binding-time analysis and explicit staging annotations — by which the equations are made operational. We then dissect the LMS architecture: a staged library in which the generator is written in direct style against `Rep[T]`-typed operations, and an extensible compiler pipeline lowers the resulting IR graph to target code.

Concretely, the article **derives** each projection from the *mix* equation with proof sketches (§4.1–§4.3); **contrasts** automatic partial evaluation with annotation-driven staging (§4.4); **dissects** the LMS design — type-based binding times, the graph IR, and the optimization pipeline (§4.5); **surveys** the empirical record, including production incarnations of the first projection in tracing JITs (§5); and **catalogues** the limits: termination, code duplication, cross-stage effects, and error reporting (§6).

All code examples are illustrative of the cited systems' documented semantics [2][3][4]; the Scala snippets follow the LMS embedding as published [4].

## 4 Deep Dive

### 4.1 The First Projection: Specializing an Interpreter Is Compilation

Let `int` be an interpreter for a source language *S*, written in a language *L*. It satisfies `⟦int⟧(p, d) = ⟦p⟧_S(d)`: running the interpreter on source text `p` and input `d` equals the meaning of `p` in *S*. Instantiate the *mix* equation with `p := int` and static input `s := p`:

> **Theorem (First Futamura projection).** `target = mix(int, p)` satisfies `⟦target⟧(d) = ⟦p⟧_S(d)` for all `d`. The residual program is a compiled version of `p`: interpretive dispatch on the syntax of `p` has been performed at specialization time and no longer occurs at runtime [1][2].

*Proof sketch.* By the *mix* equation, `⟦mix(int, p)⟧(d) = ⟦int⟧(p, d)`, and by the definition of an interpreter the right-hand side equals `⟦p⟧_S(d)`. ∎

The practical content is that the *dispatch loop* of the interpreter — the case analysis over AST nodes, the environment lookups, the tag checks — is static with respect to `p` and therefore evaluated away. What remains is straight-line code in *L* computing exactly what `p` computes. Jones's group measured speedups of roughly 4–10× for the first projection on untyped interpreters [2], and the idea is alive in production: PyPy's RPython toolchain and GraalVM's Truffle framework are industrial realizations of the first projection [1].

```python
# A miniature illustration of the mix equation (pseudocode)
def mix(program, static_input):
    """Return residual program p_s with static_input baked in."""
    residual = specialize(program.body, env={"s": static_input})
    return residual  # takes only the dynamic input d

# First projection: interpreter + source -> compiled program
# target = mix(int, p);  target(d) == run_interpreter(int, p, d)
```

### 4.2 The Second Projection: Specializing the Specializer Yields a Compiler

Apply the first projection not to a user program but to `mix` itself. Let the static input to the outer `mix` be the interpreter `int`, and consider what the residual program *does* when later given a source program `p`:

> **Theorem (Second Futamura projection).** `comp = mix(mix, int)` satisfies `⟦comp⟧(p) = mix(int, p)`, i.e., `comp` maps every source program `p` to its compiled version. `comp` *is* a compiler from *S* to *L*, obtained without writing one [1][2].

*Proof sketch.* By the *mix* equation, `⟦mix(mix, int)⟧(p) = ⟦mix⟧(int, p) = mix(int, p)`. By the first projection, `mix(int, p)` is a compiled version of `p`; hence `mix(mix, int)` maps source programs to compiled programs, which is the definition of a compiler. ∎

This is the projection that made the DIKU group's work famous and infamous in equal measure: *famous*, because a compiler appears "for free" from an interpreter plus a self-applicable specializer; *infamous*, because making `mix` efficient enough to specialize *itself* required a binding-time analysis of exquisite precision. The static/dynamic division must now classify the *specializer's* operations: the parts of `mix` that manipulate the interpreter's syntax are static; the parts that manipulate the interpreter's *input data* are dynamic [2][5].

### 4.3 The Third Projection: The Compiler Generator

Specialize `mix` with respect to itself:

> **Theorem (Third Futamura projection).** `cogen = mix(mix, mix)` satisfies `⟦cogen⟧(int) = mix(mix, int)`: given *any* interpreter, it produces a compiler for that interpreter's language. `cogen` is a compiler generator [1][2].

*Proof sketch.* Immediate from the *mix* equation: `⟦mix(mix, mix)⟧(int) = ⟦mix⟧(mix, int) = mix(mix, int)`, which is a compiler by the second projection. ∎

In practice nobody runs the third projection for production use — the generated compiler generator is typically slower than a hand-written one — but its *existence* is a deep fact: it shows that the entire tower (interpreter → compiler → compiler generator) is already implicit in a single self-applicable specializer. Jones called this the vindication of the "language triplet" view: semantics given once, as an interpreter, mechanically yields the whole toolchain [2].

The three projections are summarized below:

| Projection | Equation | Static input | Dynamic input | Result |
|---|---|---|---|---|
| First | `target = mix(int, p)` | source program `p` | runtime data `d` | Compiled program |
| Second | `comp = mix(mix, int)` | interpreter `int` | source programs `p` | Compiler *S → L* |
| Third | `cogen = mix(mix, mix)` | specializer `mix` | interpreters `int` | Compiler generator |

### 4.4 Staging Annotations: Binding Times by Declaration

The classical projections demand *automatic* binding-time analysis, and self-application demands it twice over. Taha and Sheard's insight [3] was to *give up inference* and let the programmer annotate. The resulting discipline is simpler to specify, simpler to implement, and far more predictable — at the cost of requiring the programmer to think in stages.

The annotation discipline rests on a modal reading of types: `.<t>.` is the type of *code* that will compute a `t` at a later stage. The typing rules enforce two critical invariants:

1. **No scope extrusion.** A variable bound at one stage may not be referenced inside brackets belonging to a later stage unless explicitly passed; the type system rejects `.<fun x -> .~(y)>.`-style escapes of unbound variables.
2. **Phase separation.** `run` requires a *closed* code value, so generated code can be compiled and executed without dangling references.

```haskell
-- Staged dot product: the vector length n is static, elements dynamic
dot : int -> .<float array -> float array -> float>.
dot n = .<fun a b ->
  let acc = ref 0.0 in
  .~(unroll n) ;  -- staging-time loop unrolling spliced in
  !acc>.
```

Environment classifiers (Taha–Nielsen, POPL 2003) later generalized the system to *open* code, tracking the free variables a code fragment may mention — the theoretical basis for typed cross-stage persistence [3]. The price of explicitness is verbosity and a new class of programmer errors (staging a computation at the wrong level), but the payoff is total control: what runs when is visible in the source.

### 4.5 Lightweight Modular Staging: Binding Times by Type

LMS [4] keeps the explicitness of staging annotations but removes the *syntax*. Instead of brackets, the single marker is a type constructor: `Rep[T]`. A value of type `T` is computed *now* (staging time); a value of type `Rep[T]` is computed *later* (runtime) and denotes a node in the generated program's IR graph. Ordinary host-language code — functions, objects, higher-order combinators — runs at staging time for free; only operations on `Rep` values generate code.

```scala
// LMS-style staged power: n is static (Int), x is dynamic (Rep[Double])
def pow(n: Int, x: Rep[Double]): Rep[Double] =
  if (n == 0) 1.0
  else x * pow(n - 1, x)   // recursion happens at staging time; * builds IR nodes

val f: Rep[Double] => Rep[Double] = (x: Rep[Double]) => pow(3, x)
// generates: (x: Double) => x * (x * (x * 1.0))
```

Three architectural decisions make LMS more than a notational variant of MetaOCaml:

Where the Futamura projections *derive* compilers from interpreters automatically, LMS *constructs* them deliberately: the programmer writes what is effectively the generating extension (the compiler) by hand, in the host language, with types guaranteeing that staging-time and runtime computations do not mix.

## 5 Empirical Results and Proof Sketches

### 5.1 Correctness: what the equations guarantee

The *mix* equation is not merely definitional: the substantive proof obligation is *showing that a given implementation satisfies it*. For offline partial evaluation this decomposes into two lemmas [2]:

> **Theorem (Correctness of offline specialization).** If the binding-time analysis is *congruent* (static computations never depend on dynamic values) and the specializer follows the annotations, then `⟦mix(p, s)⟧(d) = ⟦p⟧(s, d)`.

*Proof sketch.* By induction on the annotated syntax: static constructs are evaluated by the specializer (sound by congruence), and dynamic constructs are residualized homomorphically, preserving the original semantics under substitution of the static values. ∎

A stronger property, *Jones optimality*, asks that specializing a *self-interpreter* remove all interpretive overhead: `mix(sint, p)` should be textually identical to `p` modulo renaming. Early Mix-style systems achieved it for untyped interpreters; typed interpreters initially left residual tag manipulations, spurring the development of tagless staged interpreters and type specialization techniques [2][5].

### 5.2 Measured speedups

The empirical record supports the theory's promise when the staging structure is right:

- **First projection (classical PE):** Jones's group reported 4–10× speedups specializing untyped interpreters, with residual programs competitive with hand-written compiled code on small benchmarks [2].
- **Tracing JITs (industrial first projection):** PyPy and GraalVM/Truffle specialize language interpreters at *runtime*, routinely achieving order-of-magnitude speedups over pure interpretation on dynamic-language workloads [1].
- **LMS-based DSLs:** the LMS paper's case studies — a staged parser-combinator library and a linear-algebra DSL — document multi-fold to order-of-magnitude speedups over unstaged baselines, with generated code comparable to hand-optimized low-level implementations [4]. The Delite framework built on LMS showed a single staged DSL program targeting multicore CPUs and GPUs competitively with hand-written kernels [6].

### 5.3 Why self-application stayed rare

The second and third projections have essentially one successful family of implementations (the DIKU *mix* lineage) [2][5]. The reason is now well understood: self-application requires the binding-time analysis to be *uniformly* precise across two very different programs (the interpreter and the specializer), and the specializer's own binding times form a fixed point that is easy to get subtly wrong — producing a "compiler" that is correct but performs no useful staging. This practical difficulty is precisely what motivated the annotation-based and type-based staging traditions: rather than inferring the tower, *declare* it.

## 6 Limitations

**Termination.** Partial evaluation inherits the halting problem: unfolding a recursive function with static arguments that never shrink diverges the specializer. Offline systems mitigate this with memoization and generalization (widening static values to dynamic when recursion is detected), but these heuristics can silently *lose* specialization. Staging annotations move the burden to the programmer — an infinite staging-time loop is just an ordinary infinite loop — which is more honest but no more decidable.

**Code explosion.** Specialization duplicates code: unrolling a loop over static bounds, or inlining a function at many static call sites, can make the residual program exponentially larger than the source. Classical PE counters this with *let-insertion* and sharing heuristics; LMS's graph IR shares subexpressions by construction, since common subexpression elimination is a core pass [4].

**Effects across stages.** Staging a language with mutable state, exceptions, or I/O raises the question of *when* an effect executes. Naive residualization can duplicate or reorder effects; sound systems must track effect ordering through the staging barrier (LMS models effects explicitly in its IR [4]). This remains an active research area, particularly for delimited control and algebraic effects.

**Error reporting and debuggability.** A bug in a staged program can manifest at staging time (generator crash), at code-generation time (malformed IR), or at runtime (wrong residual behavior) — and the generated code bears little resemblance to the source. LMS mitigates this by keeping generators in direct host-language style, so ordinary debuggers apply to the staging computation.

**The annotation burden.** Explicit staging demands that the programmer decide binding times up front; a wrong decision either loses optimization or breaks phase separation. BTA-based systems automate this but are unpredictable. No existing system gives both full automation and full predictability.

---

## 7 Conclusion

The Futamura projections compress an entire philosophy of language implementation into three equations: *specialization is compilation; applied twice it is compiler generation; applied thrice it is the generator of compiler generators* [1][2]. Their practical history is a study in the gap between a beautiful equation and a usable tool. Automatic partial evaluation closed the gap partially, at the cost of heroic binding-time analyses; explicit staging annotations closed it pragmatically, at the cost of programmer effort; and Lightweight Modular Staging reframed the problem so that staging is not a language feature at all but a *type discipline* inside an ordinary library — with an optimizing compiler framework riding along [3][4].

For the working language implementer, the lesson is concrete. If you can write an interpreter, the first projection — in its modern tracing-JIT form — can compile it. If you need a family of high-performance DSLs, the LMS discipline lets you write the generator in a high-level host language and still ship first-order, optimized target code. Futamura's 1971 paper promised compilers "for free"; half a century later, the price is finally legible, and for many domains, worth paying.
