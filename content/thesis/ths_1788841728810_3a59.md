# PagedAttention and the Memory Management of Large Language Model Inference: From Fragmented KV Caches to Disaggregated Serving

## Abstract

Serving large language models is dominated not by arithmetic intensity but by memory: the key-value (KV) cache generated during autoregressive decoding grows linearly with sequence length and batch size, and naive reservation-based allocators waste the majority of GPU DRAM through internal and external fragmentation [1]. This thesis unifies modern LLM inference memory management, centered on **PagedAttention** — the virtual-memory-inspired technique that partitions the KV cache into fixed-size blocks and translates logical token positions through a per-sequence block table [1]. We formalize the allocation problem, derive memory-footprint equations, and analyze the copy-on-write sharing mechanism that makes beam search, parallel sampling, and prefix reuse nearly free. We then situate PagedAttention within the broader serving stack: iteration-level (continuous) batching schedulers [4][7], chunked-prefill policies [7], radix-tree prefix caching [5], disaggregated prefill–decode architectures [6][8][10], and IO-aware attention kernels with KV compression [2][3]. Through analytical models and reported empirical results, we show how these layers compose to raise serving throughput by an order of magnitude while bounding tail latency, and we identify open problems in heterogeneous memory hierarchies, SLO-aware goodput optimization, and hardware–software co-design.

## 1. Introduction

The Transformer decoder generates text one token at a time. At step $t$, the model attends over all $t-1$ previously generated tokens, and recomputing their key and value projections at every step would cost $O(t^2)$ work per sequence. The standard remedy — the **KV cache** — stores the key and value tensors of every processed token so that each decoding step costs only $O(t)$ attention work over cached entries [1]. The KV cache is thus the central data structure of LLM inference, and its management determines the economics of serving.

Consider a concrete footprint. For a model with $L$ layers, $h_{kv}$ KV heads per layer, head dimension $d$, and $b$ bytes per element, the cache for one token occupies

$$M_{\text{tok}} = 2 \cdot L \cdot h_{kv} \cdot d \cdot b \quad \text{bytes},$$

the factor of two accounting for keys and values. For LLaMA-2-13B ($L=40$, $h_{kv}=40$, $d=128$) in FP16 ($b=2$), $M_{\text{tok}} \approx 1.6$ MB per token; a single 2,048-token sequence then pins roughly 3.3 GB of HBM. On an 80 GB A100, a few dozen concurrent sequences exhaust memory — not because of the model weights, but because of the cache.

> **Thesis claim:** The KV cache should be managed like virtual memory. Fixed-size paging with per-sequence block tables eliminates the dominant sources of fragmentation, enables zero-copy sharing across requests, and provides the substrate on which modern scheduling, prefix caching, and disaggregated serving are built.

Early serving systems sidestepped the problem by *reserving* the maximum possible sequence length for every request: a contiguous slab of $M_{\text{tok}} \cdot L_{\max}$ bytes per sequence, allocated up front [4]. This is simple but catastrophically wasteful. A request that generates 50 tokens on a 2,048-token reservation wastes over 97% of its slab — **internal fragmentation**. Variable-length sequences packed into fixed slabs additionally suffer **external fragmentation**, and the inability to share memory between requests with common prefixes (system prompts, few-shot examples) forfeits further savings.

This thesis proceeds as follows. §2 reviews autoregressive decoding and quantifies the memory wall. §3 formalizes the allocation problem as an online bin-packing variant. §4 — the deep dive — develops PagedAttention's block-table design and copy-on-write sharing, iteration-level scheduling, RadixAttention prefix caching, disaggregated prefill/decode, and IO-aware kernels with KV compression. §5 presents analytical and empirical results. §6 discusses limitations, and §7 concludes.

## 2. Background

### 2.1 Autoregressive Decoding and the KV Cache

A decoder-only Transformer computes, per layer, multi-head attention

$$\text{Attn}(Q, K, V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d}}\right) V,$$

where queries $Q \in \mathbb{R}^{1 \times d}$ (during decoding) attend over cached keys $K \in \mathbb{R}^{t \times d}$ and values $V \in \mathbb{R}^{t \times d}$. Inference has two phases with sharply different profiles:

| Phase | Work per token | Arithmetic intensity | Bottleneck |
|---|---|---|---|
| **Prefill** (prompt processing) | $O(t^2)$ over prompt | High (GEMM-bound) | Compute |
| **Decode** (token generation) | $O(t)$ over cache | Low (memory-bound) | HBM bandwidth |

*Table 1: The two phases of LLM inference. Decode is memory-bandwidth bound, which is why KV-cache layout and locality dominate serving performance.*

During prefill, the prompt of length $p$ is processed in parallel, populating the cache with $p$ entries. During decode, each new token appends one entry. The cache is therefore *append-only* with a known access pattern — a property PagedAttention exploits.

### 2.2 The Memory Wall and Fragmentation Taxonomy

Let requests arrive with prompt lengths $p_i$ and (unknown) output lengths $o_i \le L_{\max} - p_i$. A reservation allocator assigns each request a contiguous region of size $M_{\text{tok}} \cdot L_{\max}$. Define utilization $U = \sum_i (p_i + o_i) / (n \cdot L_{\max})$. In production traces, output lengths are heavy-tailed and unpredictable; reported average utilization under reservation is frequently below 30%, and the maximum batch size is bounded by $\lfloor M_{\text{GPU}} / (M_{\text{tok}} L_{\max}) \rfloor$ regardless of actual demand [1][4].

We distinguish three waste categories:

- **Internal fragmentation:** reserved-but-unused tail slots within each slab.
- **External fragmentation:** free memory scattered in unusable gaps between slabs (less severe under reservation, dominant in naive dynamic allocators).
- **Sharing foregone:** duplicated storage of identical prefixes across requests — e.g., a 4K-token system prompt replicated across thousands of concurrent sessions.

PagedAttention attacks all three simultaneously.

## 3. Methodology: The Allocation Problem Formalized

We model serving as an *online* resource allocation problem. At any time, a set of active sequences $\mathcal{S}$ each holds a logical KV cache of length $\ell_i(t)$ tokens, growing by at most one per decoding iteration. Physical memory is partitioned into blocks of $B$ token slots ($B=16$ in vLLM [1]). The allocator maintains, per sequence $i$, a **block table** $T_i : \{0, \dots, \lceil \ell_i/B \rceil - 1\} \to \mathcal{P}$, mapping logical block indices to physical block IDs in a global pool $\mathcal{P}$.

> **Theorem (Fragmentation bound):** Under block-granular allocation with block size $B$, the internal fragmentation per sequence is at most $(B-1) \cdot M_{\text{tok}}$ bytes, independent of $L_{\max}$. Hence total waste is $O(nB)$ rather than $O(nL_{\max})$.

*Proof sketch.* Only the final logical block of each sequence may be partially filled; all earlier blocks are full. Each sequence therefore wastes fewer than $B$ token slots. ∎

This is the virtual-memory analogy made precise: logical blocks are pages, the block table is a page table, and $B$ is the page size. Small $B$ minimizes waste but increases table size and kernel launch metadata; large $B$ amortizes overhead but reintroduces waste. Empirically, $B \in [8, 32]$ is the sweet spot [1].

The online aspect — unknown $\ell_i(t)$ growth — is handled by *demand allocation*: when a sequence's last block fills, the scheduler allocates one fresh physical block and appends it to $T_i$. No reservation, no over-provisioning. If the pool is exhausted, the scheduler **preempts**: it either *swaps* blocks to CPU memory or *recomputes* by discarding and later re-prefilling — a policy choice trading PCIe bandwidth against FLOPs [1][7].

## 4. Deep Dive

### 4.1 PagedAttention: Block Tables and Copy-on-Write Sharing

The second key idea is that attention itself can be computed over non-contiguous blocks. Standard attention kernels assume $K, V$ are contiguous in sequence order; PagedAttention rewrites the kernel to iterate over a sequence's block table:

```python
# PagedAttention kernel sketch (one query token, one head)
# q: [d], block_table: [num_blocks] -> physical ids, B: block size
num_blocks = ceil(seq_len / B)
acc, denom = zeros(d), 0.0
for j in range(num_blocks):
    phys = block_table[j]                      # address translation
    Kb = K_pool[phys]  # [B, d]                # gather, not necessarily contiguous
    Vb = V_pool[phys]
    n = B if j < num_blocks - 1 else seq_len - j * B
    s = (q @ Kb[:n].T) / sqrt(d)                # [n] scores
    m_new = max(m_old, s.max())
    alpha = exp(m_old - m_new)
    acc = acc * alpha + exp(s - m_new) @ Vb[:n] # online softmax update
    denom = denom * alpha + exp(s - m_new).sum()
    m_old = m_new
out = acc / denom
```

The per-block online softmax rescaling (in the spirit of FlashAttention [2]) keeps the reduction numerically stable while never materializing the full $t \times t$ score matrix.

**Sharing via reference counting and copy-on-write.** Because blocks are addressed indirectly, multiple sequences can reference the *same* physical block: the block table entries simply alias. A reference count per physical block tracks sharers. When a sequence must write into a shared block (i.e., append to a full shared block), the kernel performs **copy-on-write**: it allocates a fresh block, copies the shared content, and remaps only that sequence's table entry [1]. This makes several previously expensive patterns nearly free:

- *Parallel sampling* ($n$ completions per prompt): the prompt's blocks are shared across all $n$ sequences; only divergent suffixes consume new memory.
- *Beam search*: hypotheses share prefixes until they diverge, with CoW handling divergence lazily.
- *Shared system prompts*: thousands of sessions alias the same physical blocks for a common prefix, with reference counts in the thousands.

The memory saving is dramatic: for $n$ parallel samples sharing a prompt of length $p$ and generating $o$ tokens each, contiguous allocation costs $n(p+o)M_{\text{tok}}$ while paged sharing costs $(p + n \cdot o)M_{\text{tok}}$ plus table overhead — a reduction approaching $n\times$ for long shared prompts.

### 4.2 Iteration-Level Scheduling: Orca, vLLM, and Sarathi-Serve

Paging solves *where* memory lives; scheduling solves *when* sequences run. **Orca** introduced **iteration-level (continuous) batching**: instead of waiting for an entire batch to finish, the scheduler forms a new batch at every decoding iteration, admitting newly arrived requests and retiring finished ones immediately [4]. This eliminates the "straggler" problem of request-level batching, where a batch's latency is dictated by its longest sequence.

vLLM couples iteration-level scheduling with PagedAttention and a simple FCFS policy with preemption [1]. **Sarathi-Serve** refines this with two insights [7]:

1. **Chunked prefills:** a long prompt's prefill is split into token chunks (e.g., 512 tokens) that are fused with decode steps in the same iteration. This bounds the latency spike a large prefill would otherwise inflict on in-flight decodes, achieving *stall-free* scheduling.
2. **Decode-maximal batching:** the scheduler packs as many decode tokens as memory allows each iteration, maximizing the memory-bandwidth-bound throughput.

> **Theorem (informal, Sarathi-Serve):** Under chunked prefills with chunk size $C$, the worst-case added latency to an in-flight decode batch from admitting a prompt of length $p$ is $O(C)$ rather than $O(p)$, at the cost of $O(p/C)$ extra iterations of attention recomputation over chunk boundaries.

Together, these schedulers convert the paged substrate into a serving system whose throughput scales with memory bandwidth utilization rather than with the longest request in the batch.

### 4.3 Prefix Sharing at Scale: RadixAttention

PagedAttention enables sharing, but *discovering* shareable prefixes across independent requests requires an index. **RadixAttention** (SGLang) maintains a **radix tree** over token sequences: each tree node corresponds to a token subsequence resident in the KV pool, with edges labeled by tokens [5]. Insertion walks the tree matching the request's tokens; the longest matched prefix's cached KV blocks are reused directly, and only the unmatched suffix is prefilled.

Each cached node carries a reference count and a last-access timestamp. Eviction follows LRU among zero-reference nodes, so hot prefixes (system prompts, few-shot templates, common document chunks in RAG) persist while cold ones are reclaimed [5]. This generalizes PagedAttention's intra-request sharing to *inter-request* sharing, and is particularly potent for agentic workloads where many requests share long tool-use histories.

| Mechanism | Sharing scope | Index structure | Typical saving |
|---|---|---|---|
| PagedAttention CoW | Within request group (beam, samples) | Block table + refcounts | Up to $n\times$ on shared prompts |
| RadixAttention | Across all requests | Radix tree + LRU | 30–60% prefill elimination in chat/RAG traces [5] |

*Table 2: Two complementary layers of KV reuse.*

### 4.4 Disaggregated Prefill and Decode

Prefill is compute-bound; decode is memory-bandwidth-bound. Co-locating them on the same GPUs forces a compromise: chunked prefills (§4.2) mitigate interference but cannot eliminate it. **Disaggregation** splits the two phases onto separate GPU pools [6][8][10]:

- *Prefill workers* optimize for FLOPs: large prompt batches, tensor/pipeline parallelism, high SM occupancy.
- *Decode workers* optimize for HBM capacity and bandwidth: many concurrent sequences, paged KV pools sized for maximum residency.

The phases are joined by a **KV cache transfer**: after prefill, the prompt's KV blocks are shipped to the decode worker (over NVLink/InfiniBand or, in Mooncake's design, via a dedicated transfer plane with RDMA) [10]. DistServe formalizes the objective as **goodput** — throughput subject to per-request TTFT (time-to-first-token) and TPOT (time-per-output-token) SLOs — and shows that phase-specialized placement with SLO-aware scheduling strictly dominates co-location on goodput [6]. Splitwise independently demonstrated the same principle on heterogeneous clusters, placing prefill on compute-rich and decode on memory-rich hardware [8].

Disaggregation interacts cleanly with paging: because KV data is already block-structured, transfer units are whole blocks, and the decode worker simply installs received blocks into its own pool and block tables.

### 4.5 IO-Aware Kernels and KV Compression

Even with perfect allocation, each decode step must *read* the entire KV cache from HBM — the fundamental bandwidth tax. Two complementary directions reduce it:

**IO-aware exact attention.** FlashAttention tiles $Q, K, V$ in SRAM and computes attention with an online softmax, avoiding materialization of the $N \times N$ score matrix and reducing HBM accesses from $\Theta(N^2)$ to $\Theta(N^2 d^2 / M_{\text{SRAM}})$ [2]. FlashAttention-2 improves work partitioning and parallelism across thread blocks and sequence length [3]. PagedAttention kernels adopt the same tiling discipline, adding the block-table gather as the outer loop (§4.1).

**Reducing KV heads and rank.** Multi-Query Attention (MQA) shares a single KV head across all query heads, cutting $h_{kv}$ to 1 [12]; Grouped-Query Attention (GQA) interpolates with $g$ KV groups [13]. Multi-head Latent Attention (MLA) goes further, compressing the KV cache into a low-rank latent vector cached per token and reconstructed on the fly [14]. These are *orthogonal* to paging: a GQA model with 8 KV groups simply has a smaller $M_{\text{tok}}$, and paged block tables work unchanged.

**Alternative substrates.** vAttention observes that OS virtual memory (via CUDA's low-level VMM APIs) can provide demand paging without a custom kernel gather loop, mapping logical contiguity onto physical discontiguity in the driver [15]. This trades kernel complexity for reliance on driver support — a reminder that PagedAttention's block table is one point in a design space whose axes are *who translates addresses* (kernel vs. driver vs. MMU) and *when* (per-block vs. per-page-fault).

## 5. Empirical Results and Analytical Models

**Throughput.** vLLM reports up to **24×** higher throughput than reservation-based baselines (HuggingFace Transformers) on ShareGPT traces, with the gain decomposing into ~2–4× from larger effective batch sizes (fragmentation elimination) and the remainder from continuous batching and sharing [1]. Orca demonstrated 3–5× throughput gains over request-level batching at matched tail latency [4].

**Latency.** Sarathi-Serve's chunked-prefill scheduler reduces P99 token latency by up to 5× versus vLLM's FCFS on mixed workloads, by capping prefill-induced stalls [7]. DistServe's goodput-aware placement meets strict TTFT/TPOT SLOs at 2–4× the request rate of co-located serving [6].

**Prefix caching.** SGLang's RadixAttention eliminates 30–60% of prefill computation on multi-turn chat and RAG benchmarks, translating directly to TTFT reductions since prefill dominates first-token latency [5].

**Analytical model.** Let $M$ be pool memory, $B$ block size, and active sequences have mean length $\bar\ell$. The maximum concurrency under paging is approximately

$$n_{\max} \approx \frac{M}{M_{\text{tok}} \cdot (\bar\ell + B)},$$

versus $M / (M_{\text{tok}} L_{\max})$ under reservation — a gain factor of $L_{\max}/(\bar\ell + B)$, often 5–20× in practice. The $+B$ term is the residual fragmentation from §3's theorem, and shrinking $B$ trades metadata overhead (block-table size $O(\ell/B)$ per sequence) against this term.

## 6. Limitations

1. **Preemption cost.** When the block pool exhausts, swapping to CPU costs PCIe round-trips and recomputation costs FLOPs; under bursty overload, either policy can induce latency spikes that paging alone cannot prevent [1][7].
2. **Metadata and kernel overhead.** Block tables add per-sequence metadata and the gather loop adds indirection; for very short sequences or tiny $B$, overhead can outweigh fragmentation savings.
3. **Disaggregation transfer tax.** KV transfer between pools consumes interconnect bandwidth and adds a pipeline bubble; on bandwidth-constrained clusters the transfer can dominate, favoring co-location [10].
4. **Prefix-cache staleness.** RadixAttention reuses KV blocks across requests, which is unsound if model weights or sampling-affecting state change; cache invalidation on weight updates must be total and immediate [5].
5. **Heterogeneous memory.** Emerging hierarchies (HBM + LPDDR + CXL-attached memory) break the two-level pool abstraction; optimal block placement across tiers with different bandwidth/latency is open [15].
6. **SLO heterogeneity.** Goodput formulations assume known TTFT/TPOT SLOs; interactive, agentic, and batch workloads with conflicting SLOs remain hard to co-schedule optimally [6].

---

## 7. Conclusion

PagedAttention reframed KV-cache management as virtual memory management, and the serving stack reorganized itself around that reframing: demand-paged blocks with copy-on-write sharing (§4.1), iteration-level schedulers that exploit the resulting elasticity (§4.2), radix-tree indexes that extend sharing across requests (§4.3), disaggregated phase-specialized pools that transfer whole blocks (§4.4), and IO-aware kernels plus KV compression that attack the residual bandwidth tax (§4.5). The composition is multiplicative — each layer's savings multiply rather than add — which explains the order-of-magnitude throughput gains reported across these systems.

The deeper lesson is architectural: inference serving is a *memory-systems* problem wearing a machine-learning costume. The techniques that won — paging, copy-on-write, LRU eviction, phase disaggregation — are operating-systems ideas rediscovered at the granularity of attention blocks. As context lengths grow toward millions of tokens and agentic workloads multiply shared prefixes, we expect this convergence to deepen: the inference engine of the future will look less like a batch job scheduler and more like a virtual memory manager with a softmax unit attached.
