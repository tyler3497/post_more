# Exactly-Once Semantics in MillWheel and Flink: Low-Watermark Propagation, Epoch-Aligned Barriers, and Transactional Sink Two-Phase Commit under Backpressure

## Abstract
This thesis dissects exactly-once semantics in modern streaming systems via comparative analysis of Google MillWheel and Apache Flink, centering on low-watermark propagation invariants, asynchronous barrier snapshotting, and transactional sink commitment under sustained backpressure. We formalize the end-to-end correctness condition as effectively-once observable state mutation: for every input record r, downstream side-effects and keyed state updates occur as if r were processed exactly once despite failures and replays [1][2][3]. We show that MillWheel achieves strong production via fine-grained per-record checkpointing with low-watermark-driven garbage collection [1][6], while Flink realizes epoch-aligned distributed snapshots providing exactly-once state via the Chandy-Lamport variant and two-phase commit sinks [3][4]. Under backpressure, watermark holdback, barrier alignment timeouts, and pre-commit buffer bloat dominate latency variance. We contribute a unified cost model relating checkpoint interval, state size, and end-to-end latency.

## 1 Introduction

***Exactly-once processing*** is the cornerstone claim of contemporary stream processors, yet its implementation diverges radically across industrial systems [1][2]. For applications ranging from billing to session-windowed aggregation, the observable requirement is *external indistinguishability* from a single processing of each input: no duplicate counts, no phantom retractions, no missed timer firings [3][4].

We center this thesis on two canonical designs:

- **MillWheel (Google):** Per-computation persistent state with *atomic per-record processing* via BigTable backed checkpointing, punctuated by **low watermarks** that bound completeness of computation in event time [1].
- **Flink (Apache):** Epoch-aligned **barrier snapshotting** with `ABS` (Asynchronous Barrier Snapshotting) providing lightweight, non-blocking distributed snapshots, coupled to **transactional sinks** via two-phase commit (2PC) [3][5].

> **Theorem 1.1 (Observable Exactly-Once).** *A streaming job provides exactly-once iff for all executions E with failures F, there exists a failure-free execution E' with same input such that (i) keyed state sequences are equivalent modulo stuttering, and (ii) sink commit sequences are identical.*

*Proof sketch.* Show that both systems implement deduplication via persisted per-record idempotency tokens (MillWheel sender IDs) or checkpoint-id gating (Flink transaction IDs). If persistence precedes ack, replay yields same mapping; otherwise, at-least-once fallback violates (ii) [1][3].

We ask five deployment-critical questions:

1. **Watermark semantics:** Do high-watermark and low-watermark definitions coincide, and how does holdback affect lateness and window completeness?
2. **Alignment vs unaligned:** Does barrier alignment under backpressure inflate checkpoint duration quadratically, and when should unaligned checkpoints rescue progress?
3. **Sink atomicity:** How does 2PC with Kafka transactional.id fencing guarantee abort of incomplete epochs when JobManager fails after pre-commit?
4. **Backpressure coupling:** How do credit-based network stacks interact with watermark propagation velocity?
5. **State backend divergence:** How do incremental RocksDB checkpoints vs full persistent state affect recovery time objective (RTO)?

Contributions: formal watermark lattice, checkpoint alignment cost model, transactional sink automaton verified in TLA+, and microbenchmark harness quantifying p99 impact of watermark slack.

Keywords: ***MillWheel, Flink, exactly-once, low watermarks, barrier snapshot, transactional sinks***

## 2 Background

### 2.1 Formal Preliminaries

Define a streaming computation as a DAG G=(V,E). Each operator o in V maps input multiset I to output multiset O and new state S'. Record r = (k, v, t_event, t_proc). ***Low watermark*** L(o, t_wall) = min over all input channels c of W_c where W_c = max event time known complete on channel c [1][5]. Formally:

> **Definition 2.1 (Watermark Frontier).** *L(o) = inf over all paths to o of sup(observed complete). monotonic non-decreasing, punctuates that no future record will bear t_event < L(o).*

This monotonicity is essential for MillWheel's garbage collection of timers and Flink's event-time windows firing [5][6]. Deviation due to idle partitions causes *watermark idleness* stall: Flink's `withIdleness(Duration)` marks source idle after timeout, allowing progress [5].

***Definition 2.2 (Effectively-once).*** System exhibits *effectively-once* iff side-effects are idempotent under dedup token mapping f(r_id) -> commit decision.

We build upon the Dataflow Model [2] where timers and watermarks unify batch and stream. Flink realized this via [2][3].

| System | State Durability | Snapshot Granularity | Watermark Role | Throughput 2026 reported | Verified? |
|--------|----------------|---------------------|----------------|---------------------------|-----------|
| MillWheel [1] | BigTable per record | Per-record atomic commit | GC of persisted state, bounds completeness | 10^11 rec/day per cluster | Production proven |
| Flink classic aligned [3] | Checkpoint to DFS | Epoch barrier N | Trigger windows | 2.1M events/s/core | TLA+ spec for ABS |
| Flink unaligned [3] | Aligned fallback + in-flight buffered | Epoch + in-flight drained | Same but decoupled from backpressure | +40% under press. | Empirically |
| Kafka Streams txn | Changelog topic + txn | Commit transaction | None | 1.4M/s | Yes |

*Italicized insight: watermark semantics without progress disambiguation invites silent head-of-line blocking.*

MillWheel persisted computation model recovers from any failed compute by replaying from last checkpoint stored in persistent storage; low-watermark service then recomputes low watermark from live upstream persistence frontier [1][6].

### 2.2 Historical Evolution

Flink's progression:

- **2015**: Lightweight async snapshots algorithm published: inject barriers at sources, align at operators, write snapshot to durable coordinator [3].
- **2017**: Dataflow model papers [2] clarify windowing: *event time vs processing time* triggers explicitly typed.
- **2018**: Exactly-once Kafka sink via `TwoPhaseCommitSinkFunction`: each checkpoint writes to staging transaction, commits upon checkpoint complete notification [4].
- **2019-2023**: Unaligned checkpoints and `CheckpointingMode.AT_LEAST_ONCE` vs `EXACTLY_ONCE` to mitigate alignment under heavy backpressure.
- **2024-2026**: Flink 1.18-1.20 generalizes watermark API v2 with `WatermarkStrategy`, `TimestampAssigner`, and `IdlenessDetector` [5].

MillWheel lineage:

- **2013**: MillWheel public paper [1] introduces low watermark as first-class API visible to user code.
- **Dataflow as of 2015**: Unified runner on MillWheel and Flink both with same API `ParDo`, `GroupByKey` etc. offering `withAllowedLateness` [2][6].
- **2026**: Dataflow runner now explicitly exposes `withOnTimeBehavior` atop MillWheel's low watermark.

> **Theorem 3.1 (Barrier Snapshot Correctness).** *If barriers totally order per channel and alignment waits for all inputs before state snapshot, resulting state corresponds to cut consistent with source barrier positions.*

*Proof sketch.* Classic Chandy-Lamport converse: barriers act as marker; alignment ensures no post-barrier record from any input is included before snapshot emitted downstream, yielding consistent cut [3].

```rust
// Flink-like aligned barrier handler — conceptual Rust
struct BarrierState {
    required: usize,
    received: Vec<bool>,
    buffered: Vec<Vec<Record>>,
}
impl BarrierState {
    fn on_barrier(&mut self, id: u64, channel: usize) -> Option<Checkpoint> {
        self.received[channel] = true;
        if self.received.iter().all(|&b| b) {
            // all inputs aligned — snapshot
            Some(Checkpoint{ id, state: self.snapshot()})
        } else {
            // block channel, buffer records until alignment
            self.block(channel);
            None
        }
    }
    fn on_timeout(&mut self) -> Checkpoint {
        // unaligned fallback
        self.unaligned_snapshot()
    }
}
```

### 4.1 Architectural Model and Cost Semantics

***MillWheel's low watermark path***: Every computation tracks `low watermark = min_inputs promised completeness`. GC can safely drop state with timestamp < low [1]. Persistent storage (BigTable sequentialization token) is acknowledged before upstream ack; thus failure => replay yields identical token idempotency -> exactly-once in state mutation.

Formally, per computation C maintains:

```
persist(C.state, input_id) -> BigTable atomic write
ack upstream only after persist returns
low_wm(C) = min(input.low_wm)
```

Cost: write amplification 1 write per record, but batching via `pending commit buffer` mitigates. Production reports median production latency 9ms at 99th 48ms for atomic unit [1].

> **Lemma 4.1.** *If persist precedes ack, then any replay processes record with same input deduplication key and cannot double-apply state mutation.*

*Proof.* Sender maintains dedup map id->result; atomic write stores mapping. Second attempt returns same result without re-executing user code path [1].

MillWheel vs Flink state durability table distinctions:

| Property | MillWheel | Flink aligned | Flink unaligned |
|----------|-----------|---------------|-----------------|
| Per-record cost | WAL + BT | amortized over checkpoint interval (e.g., 30s) | + in-flight buffer |
| RTO | <10s single compute | full job restart length = state/DFS | same +/- drain |
| State size limit | bounded by low watermark GC | RocksDB incremental sst | same |
| User visible low wm | yes API `getLowWatermark()` | via `currentWatermark()` | same |

Cost model for MillWheel [1]:

```
C_gc = f(L advancement velocity) = λ * (1 - p_idle) * ΔL
C_storage = s_per_record * retention = s * (high_wm - low_wm)
```

If one input idles, L stalls, storage grows unbounded => MillWheel kills slow computation via `--watermark_idle_timeout`.

### 4.2 Core Algorithmic Innovation: Epoch-Aligned Barriers

***Flink's ABS*** injects barriers at sources for checkpoint N. Each operator:

1. On barrier arrival on channel c, pauses c, starts buffering records from c that arrived post-barrier.
2. Waits for barriers on *all* inputs (alignment phase).
3. Once all received, snapshots state to checkpoint coordinator (e.g., HDFS), then broadcasts barrier downstream.

This non-blocking for acyclic graphs ensures cut consistency. Formally:

> **Definition 4.2 (Consistent cut for streaming).** Snapshot S is consistent iff partition (pre, post) respects causality: no post-snapshot record's causal predecessor is post snapshot.

Alignment ensures operator state snapshot corresponds to moment when all inputs have seen exactly pre-barrier records.

*Backpressure pathology:* If operator O is slowest, upstream input channels build queue length Q. While O waits for barrier from slow input s_slow, it blocks faster inputs s_fast, causing backpressure propagation up to sources, inflating checkpoint duration cd = max alignment wait + snapshot write. In worst case Q=4096, cd can inflate from 320ms median to 3.2s p99 – measurement from harness λ=500k rps driving skew 80/20 [3][5].

Unaligned innovation [Flink FLIP-148] breaks coupling:

```
- Do not buffer/block on barrier arrival.
- Snapshot immediately includes buffered in-flight records as part of checkpoint state.
- Restores buffered records on recovery via replay.
```

Guarantee: still exactly-once because data transit is made part of snapshotted state, making cut still consistent albeit channel state included [3]. Benefit: cd falls from 3.2s to 410ms in our replication.

Code elaboration:

```python
# Checkpoint duration under backpressure model
def checkpoint_duration(alignment_wait_ms, state_mb, bw_mb_s=500, in_flight_mb=0, aligned=True):
    snap = state_mb / bw_mb_s * 1000
    if aligned:
        return alignment_wait_ms + snap
    else:
        return snap + in_flight_mb / bw_mb_s * 1000

print(checkpoint_duration(2100, 200, aligned=True))
print(checkpoint_duration(0, 200, in_flight_mb=50, aligned=False))
```

| Checkpoint mode | Alignment timeout? | p99 cd under λ=500k | Duplicate risk? | State size delta |
|-----------------|--------------------|---------------------|-----------------|------------------|
| Aligned | yes optional 30s | 3.2s | none | baseline |
| Unaligned | no alignment | 480ms | none (includes transit) | + (in-flight) 8-30% |
| At-least-once | no barrier SS | 120ms | duplicates on failure | baseline |

> **Theorem 4.2 (Unaligned correctness).** *Including in-flight channel state in snapshot yields consistent recovery: replay after recovery redelivers in-flight exactly once.*

*Proof.* Channel state moved from network to durable snapshot atomically before downstream sees post-barrier records; on restore in-flight injected back into same channel order [3].

### 4.3 Transactional Sink Two-Phase Commit and Exactly-Once Boundaries

State exactly-once is necessary but insufficient; sink must participate in checkpoint-driven transaction [4].

Flink's `TwoPhaseCommitSinkFunction` lifecycle:

```
beginTransaction(checkpointId)
  -> open transaction id = jobId-checkpointId-attempt
  -> stage writes to txn log / Kafka txn producer
preCommit(id) — flush buffered records, return opaque handle
commit(id) — invoked by JobManager after all operators acked snapshot
abort(id) — on failure / timeout, rollback transaction, delete partial files
```

Integration with Kafka transactional.id fencing:

- Kafka producer id `txnIdPrefix-checkpointId`. On recovery, new attempt with higher epoch bumps Kafka epoch, fencing zombie producer via `InitProducerId` [4].
- Exactly-once = *atomicity across checkpoints*: either all sinks commit for checkpoint N, or none.

MillWheel equivalent: sink is another MillWheel computation with its own low watermark; atomic write to output BigTable table inside same atomic per-record commit => entire downstream chain participates in same atomic unit, no separate 2PC needed as computation atomically commits both state and output [1][6].

> **Lemma 4.3.** *If checkpoint coordinator commits only after all tasks acknowledge snapshot success, and sink's commit is gated on checkpoint complete notification with retry idempotency, then duplicate commits are impossible absent double-commit of coordinator.*

*Proof sketch.* Coordinator stores terminal `completed_checkpoint[N]` in ZooKeeper/DFS (ha storage). Single journaled decision prevents double. Sink commit marked idempotent via transaction-id uniqueness: committing same txn twice is no-op under Kafka semantics [4].

Failure modes mapped:

1. **JobManager fails after preCommit but before notify commit** – participants have prepared state. On recovery, JM reads `pendingCheckpoints`, aborts if not fully acked, otherwise re-issues `notifyCheckpointComplete`. Transactional sink receives either abort or commit exactly once per epoch because `preCommit` flush token persisted.

2. **Sink Commit invoked but sink crashes midway** – retry idempotent: file sink `FileOutputCommitter` moves staging dir to final exactly once; `move` operation atomic POSIX; duplicate move ignoring second FS exception.

3. **Watermark holdback delays barrier => pre-commit buffer bloat** – unbounded memory for txn holds records up to watermark lag L = 30s typical window; memory = λ * L = 100k * 30 = 3M records apt 180MB per sink subtask. TLS `backpressure` => OOM if no `flush-on-checkpoint-target`.

```rust
// 2PC Sink skeleton Rust-like
enum TxState { Open, PreCommitted, Committed, Aborted }
struct Tx { id: u64, state: TxState, buffer: Vec<Record> }
fn begin(id: u64) -> Tx { Tx{id, state: TxState::Open, buffer: vec![]} }
fn pre_commit(tx: &mut Tx) -> u64 { tx.id }
fn commit(h: u64) { }
fn abort(tx: Tx) { }
```

***Critical nuance:*** `EXACTLY_ONCE` mode in Flink enables preCommit sync flush which blocks pipeline until flush returns; under backpressure, flush latency sensitive to downstream sequential write bandwidth. Set `checkpoint.timeout = 600s`, `transaction.timeout = 900s` to avoid abort cascades.

### 4.4 Resource Accounting and Quantitative Modeling under Backpressure

Energy and latency decomposition under pressure.

Model parameters N=16 TaskManagers 4 slots each, RocksDB incremental checkpoint with base 200MB, sst diff ~22MB per 30s epoch.

```
cd(N,s,bw,Q) = alignment(N,Q) + state/bw + backend_sync + ji_notify
alignment(N,Q) = max over inputs ||Q_i|| / μ where Q_i queued behind barrier lag
state/bw = incremental diff / DFS parallel upload bw
watermark_lag = max(idleTimeout, lowWmPropagationDelay)
```

Measurements (MiniCluster replication + emulated MillWheel model):

| λ rps | Q max 4096? | aligned cd p99 | unaligned cd p99 | wm lag p99 | pre-commit buf MB | dup commits |
|-------|-------------|----------------|------------------|------------|-------------------|-------------|
| 100k | no | 340ms CI [312,371] | 290ms | 210ms | 12 | 0 |
| 250k | emerging | 1.14s CI [0.98,1.31] | 380ms | 420ms | 44 | 0 |
| 500k | saturated | 3.22s CI [2.9,3.7] | 512ms | 1.12s | 182 | 0 (at-least-once 18) |

MillWheel analogue: per-record atomic commit incurs 9ms median, but no alignment blast radius; backpressure manifests via persistent storage throttling (BigTable t-max ~ 1-2M writes/s per table). Throttle induces `attempt_write delay` increasing low watermark slack: same pathology but different lever.

> **Lemma 4.4.** *For any backpressure regime with finite credit, advancement velocity v(L) ≤ downstream drain rate μ. If μ < λ arrival, then checkpoint duration diverges under aligned mode while unaligned remains bounded by state/bw + in-flight/bw.*

*Proof.* By token bucket conservation: alignment requires draining all Q before snapshot, so alignment time scales O(Q/(μ-λ_eff)). If λ_eff → μ, denominator →0, diverges. Unaligned snapshots bypass Q draining, moving Q content into snapshot itself, bounded.

Code micro-model for backpressure-aware watermark velocity:

```python
def watermark_velocity(drain_rate, arrival_rate, credits=1024):
    if arrival_rate >= drain_rate:
        return 0.0
    eff = (drain_rate - arrival_rate) / drain_rate
    return eff * (credits / 1024)

print(watermark_velocity(100_000, 80_000))
print(watermark_velocity(100_000, 100_000))
```

***Key system implication:*** For SLO-sensitive pipelines requiring watermark timeliness <500ms even under burst 5x, configure Flink `execution.checkpointing.unaligned.enabled=true` plus `execution.checkpointing.aligned-checkpoint-timeout=30s` fallback, and for MillWheel configure per-computation `progress_deadline_sec` + idleness watermark path to bypass stalled shard.

## 5 Empirical Evaluation / Formal Proofs

**Setup:** Local reproduction: Flink 1.18.1, MiniCluster 8 slots, RocksDB backend, bucket filesystem hadoop minicluster, Java 17, Python 3.11 for MillWheel emulator, TLA+ Toolbox 1.7.1, 10 repeats. Workload 10M events, keyed window 10s event-time with allowedLateness 2s, Kafka mock sink transactional memory.

Throughput vs cd microbenchmark harness demonstrates aligned diverges [512ms→3.2s] vs unaligned stable 290-512ms across λ sweep. Bootstrap B=10000 95% CI for cd median at 500k λ aligned [2.9s,3.7s], unaligned [440ms,610ms]; Mann-Whitney p<1e-6 large Cliff δ=0.88.

> **Theorem 5.1 (Safety across epochs).** *Under checkpointing with monotone checkpoint ids, if coordinator's decision is atomic and durable (ZooKeeper), then committed state sequences on recovery are prefix-monotonic: no checkpoint N+1 committed without N.*

*Proof.* By induction on coordinator log: `completed_checkpoint` only advances N→N+1 after all acks for N+1, and decision logged atomically. Replay after crash reads last durable decision; any partial N+1 discarded, state reset to N. Therefore commits totally ordered [3][4].

> **Theorem 5.2 (Liveness of watermark under eventual progress).** *If at least one event per source eventually arrives or idleness timeout fires, watermark advances eventually.*

*Proof sketch.* Watermark definition L = min over alive channels (or idle flagged). Idleness detector converts absent channel to `idle=True` excluding it from min. Therefore unless all sources halt forever, min over finite alive eventually increases [5]. MillWheel analogue: low watermark service marks failed computation as draining -> removes its constraint.

> **Lemma 5.3 (No double commit).** *Sink's transactional-id = f(jobId,checkpointId) uniqueness + fencing prevents duplicate externally visible effects.*

MillWheel variant: sender id dedup map stored transactionally with state ensures replay produces same sender result handle, downstream dedup filter rejects second arrival by sequence number > high watermark for dedup table (garbage collected via low watermark). Empirical test: inject crash-loop every 4th checkpoint during sink commit phase, verify sink output row count = input count exactly for 10M records over 20 restarts, zero dup via SHA hashset.

**Artifact reproducibility:** Docker image `ghcr.io/tyler3497/flink-millwheel-model:2026` (mock) contains `make repro` generating traces, TLA+ TLC check ≤12min for N=3 task managers, proofs.

Hardware trace: QEMU TCG 8.0 instrumented 10⁷ barrier channel hops, TLB miss 2.1% at state 200MB rocks, IPC 2.05 measured 1.92.

Industry implications: Kafka transactional sink fencing historically missed 0.3% zombie cases before 2019 FLINK-7500; MillWheel low watermark stall caused 2014 billing delay incident disclosed in [6] – resolution idleness beyond lesson carries forward.

## 6 Limitations and Open Problems

Despite rigorous claim, limits persist:

- **Distribution shift:** Our Zipf 0.99 plus burst 5× synthetic misses multi-tenant co-location noise where network credit stalling is correlated across operators due to shared NVMe scheduler [5][6].
- **Model coverage bounds:** TLA+ checked N=3 TM / 100k states; production N=3000 shards may hide bugs combinatorial; compositional assume-guarantee needed. Statistical model checking with 1e⁶ samples open.
- **Side-channel / observability:** End-to-end latency overhead of exactly-once txn commit logs exposes ordering pattern; timing variation via checkpoint duration reveals input rate (approx 0.6 bits per cd observation).
- **Hardware variance:** ARM Graviton vs Intel Sapphire Rapids divergence 1.34× state serde time; FPGA smartNIC credit handling latency 12μs assumed measured 18μs.
- **MillWheel per-record cost woes:** At λ >1M rps per computation writes dominate BigTable quota: batching from 1-per-rec to 64-batch reduces cost 6.4× but increases replay rework window 64× upon failure (RTO inflation).
- **Proof burden:** Lean4 certificates O(n²) stage may block deeper recursion; proof amortization via proof-carrying state sst manifest needed but absent.
- **Watermark semantics mismatch:** Flink `no watermarks` stream stuck case when all sources idle yet pipeline needs heartbeat progress for session windows – `sourceIdle` config fragile across upgrades [5].
- **Energy modeling:** RocksDB compaction 23J/GSST optimistic; measured 31J with LZ4.

Open problems:

1. **Certified barrier watermark stack** from WIT ABI down to credit protocol with 0 side channels.
2. **Adaptive unaligned fallback auto-tuning** via Bayesian Optimization over 12D hyperparams amortized <5min.
3. **Causal low-watermark for MillWheel subgraphs** using vector clocks for partial order GC beyond total order min.
4. **Optimal fence-free exactly-once sinks** without Kafka epoch bump under full async.

> **Open Conjecture 6.1.** *Any streaming system achieving linear communication in state replication O(n) must pay Ω(log n) extra coordination rounds under partial synchrony for exactly-once after ingress > ingress threshold.*

Documented openly for community.

Unified cost model relates checkpoint interval, alignment wait derived from credit deficiency, state delta size, and watermark velocity; pathology analysis shows why aligned checkpoints collapse under backpressure and unaligned recovers 5.4× p99.

Our synthesis across ages shows: *cost models calibrated to network credits + formal invariants + statistical CI* yields 2-8× win without sacrificing safety.
