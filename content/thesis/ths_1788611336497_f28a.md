# io_uring and the Redesign of Kernel Asynchronous I/O: Shared Ring Buffers, SQPOLL, and Zero-Copy Submission at Ten Million IOPS

## Abstract

The Linux kernel's asynchronous I/O story was, for nearly two decades, a catalogue of compromises: Linux AIO restricted to `O_DIRECT` and burdened by per-operation system calls; POSIX AIO emulated in user space with thread pools; and `epoll` offering only readiness notification, never completion semantics. *io_uring*, merged in Linux 5.1 by Jens Axboe, redesigns the interface around two lock-free ring buffers shared between user space and the kernel, batched submission through `io_uring_enter`, a kernel polling thread (SQPOLL) that eliminates submission syscalls, and registered buffers plus fixed files that remove per-request page pinning and descriptor lookup. This thesis develops a cost model of the submission and completion paths, analyzes the twin rings' memory-ordering protocol, examines multishot networking as a replacement for `epoll` loops, and evaluated benchmarks: io_uring exceeding 1.4M 4 KiB random-read IOPS per saturated core against 1.32M for Linux AIO [6], io_uring polling matching SPDK NVMe throughput at 1.49M IOPS on a single core [4], and database-engine studies quantifying registered-buffer, NVMe-passthrough, and completion-polling gains [5]. We close with the interface's remaining limits and its trajectory toward a universal asynchronous syscall substrate.

---

## 1. Introduction

Modern storage hardware broke the operating system's I/O contract. An NVMe device exposes up to 65,535 command queues each 65,535 entries deep, capable of saturating a PCIe link with millions of small operations per second. The classical Linux system call, however, was designed for an era of millisecond disks: one call, one operation, one context switch, one trip through the page cache and the block layer. Even the kernel's own asynchronous interface, Linux AIO (`io_submit`/`io_getevents`), was widely regarded as difficult to use and inefficient [2]. It supported only direct I/O, required one system call per batch of operations, and delivered completions through a kernel-managed ring that the application could not share efficiently.

The performance consequences became acute after the Meltdown and Spectre mitigations, which dramatically increased system-call entry cost [6]. When each operation costs a few microseconds of kernel entry overhead and the device can absorb millions of operations per second, the interface — not the hardware — is the bottleneck. Jens Axboe's answer, proposed in early 2019 and merged for Linux 5.1, was **io_uring**: a completion-oriented asynchronous I/O interface built on shared memory [1][2].

The design rests on four interlocking ideas. First, *shared ring buffers*: the submission queue (SQ) and completion queue (CQ) live in memory mapped into both user space and the kernel, so posting a request or harvesting a completion is a memory access, not a system call. Second, *batched submission*: a single `io_uring_enter` call hands the kernel hundreds of operations at once, amortizing the remaining syscall cost toward zero. Third, *SQPOLL*: an optional kernel thread polls the submission queue, achieving zero system calls in the steady state. Fourth, *registered resources*: buffers and file descriptors pinned once at setup, eliminating per-request page pinning and file-table lookups.

## 2. Background

### 2.1 Linux AIO: the flawed predecessor

Linux AIO, introduced in the 2.5 development cycle, was the kernel's first serious asynchronous block I/O interface. Applications submit `iocb` structures via `io_submit` and reap completions via `io_getevents`. Three defects proved fatal at scale. It supported only direct I/O, excluding buffered I/O, networking, and filesystem metadata entirely. Submission still required a system call per batch, and the submission path performed copies and indirections passing requests between user space and the kernel [2]. Finally, the interface never generalized: sockets were unsupported, forcing every network application onto `epoll` plus thread pools.

### 2.2 POSIX AIO and the thread-pool tax

POSIX AIO (`aio_read`/`aio_write`) is implemented in glibc as a pool of worker threads performing synchronous I/O. The fio comparison in [6] is damning: on NVMe hardware capable of 3.5M IOPS, POSIX AIO delivered only **433,000 IOPS** while burning **64 million context switches** — against 814,000 IOPS for plain synchronous reads. The thread pool adds scheduling latency, stack memory, and thundering-herd wakeups without removing a single kernel crossing.

### 2.3 epoll: readiness is not completion

`epoll` scales readiness notification to millions of file descriptors, but it answers the wrong question. It reports that a socket *may* be readable; the application must still issue `recv`, paying a syscall per operation, and must manage the readiness/completion impedance mismatch (notably `EPOLLONESHOT` re-arming and edge-triggered starvation). The result is the familiar reactor pattern: an event loop, a thread pool, and per-connection state machines — all of which io_uring's completion model and multishot operations collapse into a single queue [5].

### 2.4 The io_uring proposal

Axboe's design paper [1] and the accompanying LWN coverage [2] framed io_uring as a *completion-based* interface: the application describes operations in submission queue entries (SQEs); the kernel executes them and posts results in completion queue entries (CQEs). Crucially, the queues are shared memory, so the steady-state fast path involves no system call at all when SQPOLL is enabled, and at most one amortized call per batch otherwise. The interface was designed from the start to cover nearly every syscall — reads, writes, sends, receives, accepts, connects, opens, closes, `fsync`, `fallocate`, `poll`, timeouts — rather than the storage-only ghetto of Linux AIO [3].

## 3. Methodology

Our analysis combines an analytical cost model with published third-party measurements, following the principle that interface overhead must be decomposed before it can be optimized.

**Analytical model.** We decompose per-operation latency into submission cost (SQE preparation, memory barriers, optional syscall), execution cost (device or network service time), and completion cost (CQE harvesting, wakeups, interrupts). The model predicts that syscall amortization and copy elimination dominate at small operation sizes — precisely the 4 KiB random-I/O regime where NVMe excels.

**Empirical sources.** We rely on three independent measurement programs rather than single-vendor claims:

1. **fio interface comparison** [6]: synchronous, POSIX AIO (thread pool), Linux AIO, and io_uring (basic and enhanced) driving NVMe storage rated at 3.5M IOPS, with 8 CPUs running 72 fio jobs at iodepth 8 so that CPUs saturate and the *interface* is the limiting factor.
2. **SPDK NVMe bdev 23.01 performance report** [4]: single-core, single-SSD, 4 KiB random read/write with queue depth swept from 1 to 512, comparing SPDK's user-space NVMe driver against kernel `libaio` and io_uring polling. This is the critical head-to-head because SPDK bypasses the kernel entirely.
3. **Database-engine tuning study** [5]: an arXiv paper instrumenting a storage engine with io_uring's registered buffers, NVMe passthrough (`IORING_OP_URING_CMD`), and completion polling, reporting per-feature throughput deltas on YCSB.

We additionally reference the `io_uring_setup(2)` manual [7] and the liburing project [3] for API semantics, and Axboe's "what's new" deck [8] for the evolution of multishot and provided-buffer features.

## 4. Deep Dive

### 4.1 The twin-ring protocol: SQ, CQ, and memory ordering

An io_uring instance is created by `io_uring_setup(entries, &params)`, which returns a file descriptor [7]. The application then performs three `mmap` calls to map (a) the SQ ring, (b) the CQ ring, and (c) the array of SQEs. The `params` structure returns the ring sizes and the byte offsets of the head/tail indices within the mapped regions:

```c
struct io_uring_params {
    __u32 sq_entries;
    __u32 cq_entries;
    __u32 flags;
    __u32 sq_thread_cpu;
    __u32 sq_thread_idle;
    __u32 features;
    __u32 wq_fd;
    __u32 resv[3];
    struct io_sqring_offsets sq_off;
    struct io_cqring_offsets cq_off;
};
```

The protocol is a pair of **single-producer, single-consumer** lock-free rings. On the submission queue the application is the sole producer: it writes an SQE (64 bytes, or 128 with `IORING_SETUP_SQE128`), advances the SQ tail with the appropriate write barrier, and — in the default mode — calls `io_uring_enter` to notify the kernel. The kernel is the sole consumer. On the completion queue the roles reverse: the kernel posts CQEs (16 bytes: `user_data`, `res`, `flags`) and advances the CQ tail; the application consumes. Because each ring has exactly one writer, no atomic compare-and-swap is needed on the fast path — only ordered head/tail updates with acquire/release barriers. This is the fundamental reason the per-operation overhead collapses: posting work is a few cache-line touches in memory the application already owns.

> **Theorem (Submission amortization).** *Let `C_enter` be the cost of one `io_uring_enter` syscall and `C_sqe` the per-SQE preparation cost in shared memory. Submitting a batch of `N` SQEs costs `C_enter + N · C_sqe`, so the amortized per-operation submission cost is `C_sqe + C_enter/N`, which tends to `C_sqe` — pure memory traffic — as `N` grows. In SQPOLL mode `C_enter = 0` identically.*

The `user_data` field deserves emphasis: it is an opaque 64-bit token echoed back in the CQE, letting applications correlate completions without any kernel-side lookup table — typically a pointer to the request context. This removes the completion-demultiplexing data structure that `epoll` servers maintain separately.

### 4.2 `io_uring_enter` and batched submission semantics

```c
int io_uring_enter(unsigned int fd, unsigned int to_submit,
                   unsigned int min_complete, unsigned int flags,
                   sigset_t *sig);
```

The call's contract is richer than "submit work." `to_submit` tells the kernel how many new SQEs are visible; `min_complete` requests blocking until at least that many completions arrive; and `flags` selects behavior — notably `IORING_ENTER_GETEVENTS`, which folds submission *and* completion waiting into one syscall. An event loop can therefore submit a batch of reads, wait for completions, harvest CQEs, and re-arm — all with a single kernel crossing per iteration. The linked-SQE mechanism (`IOSQE_IO_LINK`) goes further, expressing dependent chains (e.g., `openat` → `read` → `close`) as one submission whose elements execute in order, with failure short-circuiting the chain.

Batching interacts favorably with the block layer: a single `io_uring_enter` carrying dozens of reads lets the kernel build a deep hardware queue instantly, which is exactly what NVMe needs to exploit internal parallelism. The measured consequence appears in Section 5: fio's io_uring backend sustains 1.417M IOPS where synchronous I/O manages 814K on identical hardware [6] — the gap is almost entirely submission-path efficiency.

### 4.3 SQPOLL: zero-syscall I/O

Setting `IORING_SETUP_SQPOLL` at ring creation spawns a kernel thread that polls the submission queue [7]. The application posts SQEs and updates the tail; the polling thread observes them (after the application's barrier), dispatches the operations, and posts CQEs. The application harvests completions by reading shared memory. **No system call occurs in the steady state** — submission, execution notification, and completion are all memory operations.

The tuning surface is real. `sq_thread_cpu` pins the polling thread; `sq_thread_idle` (milliseconds) controls how long it spins before sleeping, trading CPU burn for wakeup latency; the `IORING_SQ_NEED_WAKEUP` flag tells the application when the thread has slept and one `io_uring_enter` is needed to revive it. Sharing polling threads across rings is possible via `IORING_SETUP_ATTACH_WQ` [3].

The cost is one CPU core (or a share of one) dedicated to polling. The benefit is the removal of *all* submission syscall latency and, critically, of syscall-induced jitter: completion latency becomes a function of device service time plus a bounded poll interval. For latency-sensitive stores this determinism matters as much as throughput [5].

### 4.4 Zero-copy: registered buffers and fixed files

Two per-request costs survive ring sharing: pinning user pages (`get_user_pages`) so DMA can target them, and resolving file descriptors through the file table. io_uring eliminates both by registration.

`io_uring_register_buffers` pins an array of `iovec`s once at setup; subsequent `read_fixed`/`write_fixed` operations reference them by index (`buf_index` in the SQE), and the kernel performs DMA directly into already-pinned memory [5][8]. `io_uring_register_files` similarly installs file descriptors into a fixed table, replacing per-request `fget`/`fput` with an array index. The database-engine study in [5] measured registered buffers alone at **+11% throughput** on a YCSB workload — pure data-movement overhead removed.

The mechanism generalizes. `IORING_OP_URING_CMD` passes NVMe commands straight to the device driver, bypassing the block layer; combined with fixed buffers (`IORING_URING_CMD_FIXED`), applications drive native NVMe queues through the ring with no intermediate copies. The same study measured passthrough at an additional **+20%** [5].

```rust
// liburing-style flow (conceptual): register once, reference by index forever
ring.register_buffers(&iovecs)?;      // pages pinned a single time
ring.register_files(&fds)?;           // descriptors installed in fixed table
let sqe = ring.next_sqe();
sqe.prep_read_fixed(fd_index, buf_index, len, offset); // no pin, no fget
sqe.set_user_data(ctx_id);            // echoed back in the CQE
ring.submit();                        // one io_uring_enter for the whole batch
```

### 4.5 Multishot operations and the network path

Storage was the beachhead; networking is the larger prize. Traditional `epoll` servers pay per-event: `epoll_wait` returns readiness, then `accept`/`recv` syscalls execute the work, then re-arming (`EPOLLONESHOT`) or edge-triggered bookkeeping repeats. io_uring's **multishot** operations collapse this into one submission per *listener*, not per *event*.

`IORING_ACCEPT_MULTISHOT` arms an accept that, on each new connection, posts a CQE with `IORING_CQE_F_MORE` set — the flag meaning "this operation remains armed; more completions will follow" — and immediately accepts the next connection without application involvement. `IORING_RECV_MULTISHOT` does the same for reads, ideally paired with **provided buffers** (`IORING_OP_PROVIDE_BUFFERS`): the application donates a ring of buffers to the kernel, and each multishot completion arrives with the buffer index already selected, eliminating the guess-the-datagram-size dance. A multishot echo server in liburing's examples demonstrates the pattern: a handful of SQEs sustain tens of thousands of connections, with the event loop reduced to harvesting CQEs and recycling buffers [3].

The theoretical payoff is the removal of the readiness/completion impedance mismatch. `epoll` tells you work *might* be available; multishot io_uring *does* the work and reports the result. The per-event cost falls from (wakeup + readiness scan + syscall + re-arm) to (CQE harvest + buffer recycle) — both pure user-space memory operations in the SQPOLL configuration.

## 5. Empirical Results and Proofs

### 5.1 Interface efficiency at saturation (fio)

The thenewstack study [6] saturated 8 CPUs with 72 fio jobs (iodepth 8) against NVMe storage rated at 3.5M IOPS, so the measured limit is the software interface, not the device:

| backend | IOPS | context switches | Δ vs io_uring |
|---|---|---|---|
| synchronous reads | 814,000 | 27,625,004 | −42.6% |
| POSIX AIO (thread pool) | 433,000 | 64,112,335 | −69.4% |
| Linux AIO | 1,322,000 | 10,114,149 | −6.7% |
| **io_uring (basic)** | **1,417,000** | 11,309,574 | — |
| **io_uring (enhanced)** | **1,486,000** | 11,483,468 | **+4.9%** |

Two observations matter. First, io_uring beats Linux AIO by 7–12% on Linux AIO's home turf (direct random reads), with the "enhanced" configuration (registered buffers/files, polling) adding another 5%. Second, the context-switch counts show *why* POSIX AIO collapses: 64M switches for 433K IOPS — 148 switches per operation — versus ~8 for io_uring. The ring does not merely reduce syscalls; it removes the scheduling churn that thread-pool emulation introduces.

### 5.2 Against the kernel bypass: io_uring vs SPDK

SPDK moves the NVMe driver into user space, eliminating the kernel from the data path entirely — the strongest possible competitor. SPDK's own 23.01 NVMe bdev report [4] benchmarks SPDK against kernel `libaio` and io_uring polling on one core and one SSD, sweeping queue depth from 1 to 512 (4 KiB random reads):

| QD | SPDK IOPS (avg lat) | libaio IOPS (avg lat) | io_uring poll IOPS (avg lat) |
|---|---|---|---|
| 1 | 13,587 (73 µs) | 12,946 (77 µs) | 13,409 (74 µs) |
| 64 | 725,692 (88 µs) | 493,829 (129 µs) | 699,578 (91 µs) |
| 128 | 1,172,164 (109 µs) | 492,440 (260 µs) | 1,056,231 (121 µs) |
| 512 | 1,399,856 (366 µs) | 493,311 (1,038 µs) | **1,486,734 (344 µs)** |

At QD 512, io_uring polling **exceeds SPDK** — 1.487M vs 1.400M IOPS at lower average latency (344 vs 366 µs) — while `libaio` plateaus at 493K IOPS with latency exploding past a millisecond. The philosophical result is striking: a kernel interface with shared rings and polling matches a full kernel-bypass stack, because both have converged on the same design (user-space-accessible queues, no syscalls, no interrupts). The practical result is stronger: applications get SPDK-class performance *without* surrendering the kernel's driver ecosystem and multi-tenancy.

### 5.3 Feature-by-feature decomposition (database engine)

The arXiv study [5] tuned a storage engine incrementally, isolating each mechanism's contribution on YCSB:

1. **Registered buffers** (zero-copy DMA into pre-pinned memory): **+11%**, to 238K tx/s.
2. **NVMe passthrough** (`IORING_OP_URING_CMD`, skipping the block layer): **+20%**, to 300K tx/s.
3. **Completion polling** (IOPOLL, replacing interrupt signaling): **+21%**, to **376K tx/s single-threaded**.

The compound gain is roughly 1.75× from interface tuning alone — no hardware change, no algorithmic change. It validates the cost model of Section 3: data movement, storage-stack depth, and completion signaling are independent, additive overheads, and io_uring addresses each with a dedicated mechanism.

### 5.4 The ten-million-IOPS argument

No single core in these studies crosses 1.5M 4 KiB IOPS — the per-core ceiling is set by cache-line traffic on the rings and device submission latency. The path to 10M IOPS is horizontal: io_uring instances are cheap (a few mapped pages and a file descriptor) and SQPOLL threads can be affined per core. Eight saturated cores at ~1.4M IOPS each yield **≈11M IOPS**, and Axboe's Kernel Recipes measurements demonstrated multi-million-IOPS regimes with exactly this fan-out [8].

> **Theorem (Linear ring fan-out).** *Given `k` io_uring instances on disjoint cores, each sustaining `R` IOPS with no shared mutable state on the submission/completion fast paths, aggregate throughput is `k·R` minus only the application's sharding overhead. The interface contributes no superlinear term because SQ/CQ pairs are strictly per-instance and single-producer/single-consumer.*

## 6. Limitations

**Interrupt-mode gaps.** `IORING_SETUP_IOPOLL` requires `O_DIRECT` and explicit filesystem/device support; most non-polled operations are forbidden on such rings, and mixing socket I/O with polled storage I/O in one ring is disallowed [7]. Applications needing both must run two rings — an architectural wart, though a minor one.

**Polling cost.** SQPOLL burns a core to save syscalls. At low load this is pure waste; the `sq_thread_idle` timeout mitigates it by sleeping the thread, but the sleep/wake transition reintroduces the very syscall the mode exists to avoid. The break-even point is workload-dependent and must be measured, not assumed [3].

**Security surface.** Shared rings that let user space direct kernel execution are a large attack surface. The kernel security community has repeatedly flagged missing LSM and audit hooks in io_uring code paths, including the `uring_cmd` passthrough mechanism [9]. Privileged features (notably SQPOLL, which historically required elevated privileges) and the interface's rapid feature growth demand careful sandboxing — seccomp filters for the ring's file descriptor are now standard practice.

**Correctness hazards.** The SPSC protocol is lock-free, not foolproof: missing barriers between SQE writes and tail updates, CQ ring overflow, and `user_data` lifetime management are the classic bug sources. liburing exists largely to encapsulate these [3]. And io_uring is Linux-only — portable applications must abstract it behind a portability layer.

**Benchmark caveats.** The SPDK comparison [4] uses one SSD and one core; multi-device NUMA topologies introduce cross-socket costs neither side escapes. The fio study [6] predates multishot networking, so its network conclusions are extrapolated, not measured. All cited numbers are from specific kernels and hardware — io_uring's behavior changes materially across kernel versions, and minimum-version gating is mandatory [3].

---

## 7. Conclusion

io_uring is not an optimization of Linux AIO; it is a repudiation of its architecture. By moving the submission and completion queues into shared memory, it reduces the per-operation kernel interaction from a system call to a cache-line transfer, and with SQPOLL to nothing at all. By registering buffers and files once, it removes the per-request pinning and lookup taxes. By adding multishot operations and provided buffers, it extends the completion model from storage to networking, absorbing the `epoll` reactor into the ring. The measured results — 1.49M polled IOPS per core exceeding SPDK's kernel-bypass stack [4], 1.75× compound gains from feature-by-feature tuning [5], and a clean linear fan-out argument to ten million IOPS — confirm that the interface, not the hardware, was the binding constraint.

The deeper significance is the trajectory. Each kernel release extends the ring's opcode coverage; `uring_cmd` turns it into a generic device-command multiplexer [9]; and proposals for fully asynchronous system calls suggest a future in which *every* syscall has a ring-based form. If that future arrives, io_uring will be remembered not as a faster AIO but as the prototype of the post-syscall operating system interface.
