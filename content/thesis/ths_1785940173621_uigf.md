# Byzantine Fault Tolerance at Scale: HotStuff-2 Linear View Changes, Pacemaker Synchronization, and Threshold Signatures for Chained BFT Under Partial Synchrony

## Abstract
We present a comprehensive analysis of HotStuff-2 and its evolution from HotStuff, focusing on linear view changes, pacemaker synchronization, and BLS threshold signatures for chained BFT under partial synchrony. HotStuff introduced linear, responsive BFT with three-phase commit; HotStuff-2 refines this to an optimal two-phase protocol with O(n) communication per view and O(n^2) worst-case view synchronization. We formalize the quorum certificate (QC) chaining discipline, two-chain versus three-chain commit rules, and the pacemaker abstraction that decouples liveness from safety. Through analysis of BLS aggregate signatures, DKG, and adaptive security, we show how threshold cryptography enables succinct QC construction with O(1) verification. We compare empirical throughput-latency tradeoffs in pipelined Chained HotStuff deployments and discuss optimality bounds, smoothness, and open problems in Byzantine view synchronization.

## 1. Introduction
Byzantine Fault Tolerant (BFT) State Machine Replication (SMR) under partial synchrony has undergone a renaissance driven by blockchain deployments. Classical protocols such as **PBFT** [4] achieved safety and liveness with *O(n^2)* communication during view changes, limiting scalability beyond tens of replicas. The introduction of **HotStuff** [1] marked a paradigm shift: a *linear*, *responsive*, and *pipelinable* protocol that separates core consensus logic from view synchronization via the **Pacemaker** abstraction.

HotStuff's core contribution was demonstrating that partially synchronous BFT can achieve both *optimistic responsiveness* — advancing at network speed δ rather than known bound Δ after Global Stabilization Time (GST) — and linear view change communication O(n) using threshold signatures. Its chained variant enabled amortized commit of one block per phase across a rotating leader schedule, adopted by DiemBFT, Flow, and others.

Yet HotStuff paid for its simplicity with a three-chain commit rule requiring *three* consecutive certified views. **HotStuff-2** [2] challenges the folklore that two-phase HotStuff must sacrifice either responsiveness or linearity. It proves two phases are sufficient, yielding an optimal two-phase responsive protocol with balanced load and simplified speculation.

This thesis dissects three pillars:

1. **Linear view changes** in HotStuff-2: why two phases suffice and how lock discipline preserves safety.
2. **Pacemaker synchronization**: formal Byzantine View Synchronization (BVS) problem, lower bounds, and modern solutions like Cogsworth, Naor-Keidar, and Lumiere [3].
3. **Threshold signatures**: BLS aggregation, Distributed Key Generation (DKG), and adaptive security for Quorum Certificates [5][6][7].

We situate these within the Dwork-Lynch-Stockmeyer [8] partial synchrony model and provide formalisms, proofs, and systems analysis at PhD depth.

## 2. Background / Preliminaries

### Partial Synchrony and BFT SMR
We assume *n = 3f+1* replicas, at most *f* Byzantine. Network model follows Dwork-Lynch-Stockmeyer: there exists unknown GST after which message delay ≤ δ ≤ Δ, where Δ is a known worst-case bound and δ actual delay. Before GST, adversary can delay arbitrarily. Safety must hold always; liveness holds after GST when an honest leader holds sufficient overlap.

SMR requires *linearizability*: all correct replicas execute same log of commands. BFT SMR protocols proceed in *views* v ∈ ℕ, each with designated leader L_v = v mod n (round-robin) or via reputation.

### Quorum Certificates
A Quorum Certificate QC(v,B) is cryptographic proof that ≥ n-f replicas voted for block B in view v. With *threshold signatures*, *n-f* partial signatures σ_i = Sign_share(sk_i, H(B‖v)) aggregate into σ = Aggregate({σ_i}) verifiable under single group public key pk under BLS12-381 [6].

Key property: |QC| = O(1) versus O(n) for concatenation of ECDSA signatures.

### Chained Paradigm
**Chained HotStuff** pipelines phases: each proposal carries QC for its predecessor, forming a chain. Commit rule becomes detection of *k-chain* contiguous certified blocks. HotStuff uses *three-chain*; HotStuff-2 uses *two-chain*.

> Theorem: Two-Chain Safety. In a chained BFT protocol with n=3f+1, if a block B is committed via a two-chain (B ← QC_B ← B' ← QC_{B'}), then no conflicting block B* can be certified at same height in any future view without violating either quorum intersection or honest lock.

Formally justified in Section 5.

## 3. Methodology / Formalism

We define system state as replicated log L_i at replica i. Protocol = (Propose, Vote, QC-Formation, Lock, Commit).

We adopt Synod-like formalism with TLA+ specification sketch.

```tla
---------------- MODULE ChainedHotStuff2 ----------------
EXTENDS Naturals, Sequences
CONSTANTS N, F, Replicas
VARIABLES view, highQC, lock, chain, leader
TypeOK == view \in Nat /\ highQC \in [Replicas -> Nat]

VoteCondition(r, v, b) == 
  /\ view[r] = v
  /\ b.extends highQC[r] \/ viewParent(b) >= view[lock[r]]
  /\ ValidBlock(b)

AdvanceView(r) == 
  /\ \E qc \in QC : qc.view > highQC[r].view => highQC' = [highQC EXCEPT ![r]=qc]
  /\ view' = [view EXCEPT ![r]=view[r]+1]
----------------------------------------------------------------------
```

**Assumptions:**

- *Cryptographic*: BLS Gap-DH hard, ROM, secure DKG producing (t,n)-threshold shares with t = n-f.
- *Network*: Partial synchrony with GST; eventually synchronous period > 4δ.
- *Adversary*: static or adaptive (discuss difference), computationally bounded, controls ≤ f, can reorder messages before GST.

**Metrics:** We evaluate:

- *Communication complexity*: total messages per view / per commit (worst-case and optimistic)
- *Latency*: number of rounds to commit after honest proposal (in δ units)
- *Load balancing*: per-replica bandwidth variance across window of n decisions

| Protocol | Phases | Responsiveness | View-Change Comm | Commit Rule |
|----------|--------|----------------|------------------|-------------|
| PBFT [4] | 3 | No | O(n^2) | 2-chain + checkpoint |
| Tendermint | 2 | No (waits Δ) | O(n^2) | 2-chain |
| HotStuff [1] | 3 | Yes | O(n) | 3-chain |
| Fast-HotStuff | 2 | Yes | O(n) | 2-chain + proof |
| HotStuff-2 [2] | 2 | Yes | O(n) | 2-chain |
| HotStuff-1 | 1 (speculative) | Yes (slotting) | O(n) | 1-chain + prefix speculation |

*Table 1: Evolution of chained BFT protocols. HotStuff-2 achieves optimal two-phase latency without losing linearity.*

## 4. Deep Dive

### 4.1 HotStuff to HotStuff-2: Why Two Phases Suffice

Original HotStuff requires three phases: *prepare, pre-commit, commit*. The rationale was to ensure that if a block commits, *f+1* honest replicas lock high enough to prevent conflicting certification in higher views without honest leader learning highest lock via Δ-wait.

HotStuff-2 Observation: leader can include *two QCs* in proposal, or require replica to vote without second proof if leader proves it knows high QC. The intuition:

- Phase 1 produces *prepare-QC* C1(v,B).
- Phase 2 produces *commit-QC* C2(v,B) directly on C1. Any replica seeing C2 can commit.

Safety lock: replica locks on C1, not C2. To vote for B* in view v'>v, B* must extend highQC ≥ lock.view. Since C2 proves *n-f* locked C1, any higher view proposal must extend B.

This eliminates extra round-trip while preserving linearity because QC aggregation remains O(n) star communication: leader → proposal (carrying highQC), replicas → vote shares, leader → QC broadcast.

*Pipelined effect*: Throughput remains 1 block per RTT, but latency reduces from 3 RTT to 2 RTT to finality (4 RTT to 3 RTT including client reply). In wide-area with δ=50ms, this saves 50-100 ms commit.

```python
# Simplified HotStuff-2 core logic - leader and replica
class Replica:
  def __init__(self, sk_share):
    self.high_qc = genesis_qc
    self.lock_qc = genesis_qc

  def on_propose(self, block, high_qc, view):
    if block.view <= self.lock_qc.view and not block.extends(self.lock_qc.block):
        return None  # safety violation
    if high_qc.view > self.high_qc.view:
        self.high_qc = high_qc
        if high_qc.view > self.lock_qc.view:
            self.lock_qc = high_qc  # lock on prepare QC
    vote = bls_sign_share(self.sk, block.hash())
    return vote

class Leader:
  def aggregate_qc(self, votes: List[Share], view) -> QC:
      # Lagrange interpolation at threshold t = n-f
      agg_sig = bls_aggregate(votes, threshold=N-F)
      return QC(view=view, sig=agg_sig, digest=block_digest)
```

*Italic insight*: The *subtlety* is liveness when Byzantine leader withholds highQC. HotStuff-2 adds view-change extension: replica sends its *highest QC plus highest vote* in NewView, allowing next honest leader to propose safely without waiting Δ, unless Byzantine leader actively equivocates — in which case Δ timer ensures eventual sync.

### 4.2 Pacemaker Symmetry: Decoupling Liveness

The Pacemaker module solves **Byzantine View Synchronization (BVS)**: eventually, for some honest leader L_v, all honest replicas stay in view v for Ω(Δ) simultaneously.

Naor-Bracha Dolev-Reischuk bound shows Ω(n^2) worst-case messages necessary for any deterministic BFT sync. Cogsworth [3 ref] achieved O(n) expected but O(n^3) worst-case. Naor-Keidar improved to O(n^2) expected. Lumiere achieves O(n^2) worst-case, O(n) after GST, and smooth optimism: O(n f_a + n) communication where f_a actual faults.

HotStuff-family pacemakers work in *epochs*: group f+1 views into epoch e. Heavy synchronization (all-to-all) executed once per epoch to find anchor, then linear within epoch using leader-driven timeout certificates (TC).

Formally:

1. Replicas broadcast `Timeout(v)` share when local view timer expires (4Δ). Collect TC(v) = threshold of f+1 timeouts ⇒ proof view v failed.
2. TC(v) moves replica to v+1, forwarding highQC.
3. Epoch boundary: broadcast `EpochTimeout(e)` and aggregate EpochCertificate.

This decouples safety: core HotStuff only cares about monotonic highQC; pacemaker ensures eventual progression.

The interaction under partial synchrony is delicate:

```rust
// Rust-like pacemaker pseudo
struct Pacemaker {
  view: View,
  epoch: Epoch,
  timer: Timeout,
}
impl Pacemaker {
  fn on_qc(&mut self, qc: QC) {
    if qc.view > self.view {
      self.view = qc.view + 1; // happy path
      self.timer.reset(4*DELTA);
    }
  }
  fn on_timeout(&mut self) -> Option<TC> {
    let share = sign_timeout(self.view);
    broadcast(share);
    if collected >= F+1 {
      Some(aggregate_tc())
    } else { None }
  }
}

```haskell
-- Haskell: QC verification as pure function
type ReplicaId = Int
type View = Int
data QC = QC { qcView :: View, qcSig :: BLSSig, qcDigest :: Digest } deriving Show

verifyQC :: PublicKey -> [ReplicaId] -> QC -> Bool
verifyQC pk quorum qc =
  let msg = hash (qcDigest qc, qcView qc)
      lhs = pairing (qcSig qc) g2
      rhs = pairing (hashToG1 msg) pk
  in lhs == rhs && length quorum >= 2* f + 1
  where f = (n-1) `div` 3
        n = 100 -- example
```


*Responsiveness vs. Smoothness*: Truly responsive protocols cannot wait Δ in happy path. Fever/Lumiere technique: after TC, first view of epoch waits Δ to align honest clocks within δ, then remaining f views proceed at δ. Thus even if Byzantine leader distorts, only one Δ delay per f views.

### 4.3 Threshold Signatures and Quorum Compression

Without threshold signatures, QC = list of n-f ECDSA signatures (≈64 bytes × 67 for n=100 → 4KB plus verification O(n)). With BLS12-381, each partial signature 48 bytes compresses to single 96-byte aggregate with single pairing check (2 pairings).

Construction from Boldyreva [5]:

- DKG: Pedersen VSS over G2 produces shares s_i, public commits, final pk in G2.
- Sign: σ_i = H(m)^{s_i} ∈ G1.
- Aggregate: σ = ∏ σ_i^{λ_i} where λ_i Lagrange coefficient for set S, |S|≥t.
- Verify: e(σ, g2) == e(H(m), pk).

Benefits for BFT:

- **Non-interactive** signing; no extra round.
- **Uniqueness**: same message ⇒ same signature ⇒ deterministic QC prevents grinding.
- **Batch verification**: verifier checks one pairing, not O(n) ED25519.

Adaptive security concern: Boldyreva proven static; Bacho-Loss 2022 [7] prove adaptive under Algebraic Group Model + OMDL; Das-Ren 2023 [7 variant] give DDH+co-CDH ROM construction with proactive refresh. For BFT, static adversary often assumed sufficient since stake corruption takes epoch.

Tradeoff table:

| Scheme | Sig Size | Verify Time (100) | DKG | Adaptive Proof |
|--------|----------|-------------------|-----|----------------|
| ECDSA concat | 6.4KB | 67×0.05ms=3.35ms | none | RO |
| BLS multi-sig (no threshold) | 96B + 67 pk | 2 pairings + 67 exp | none | AG |
| BLS threshold [5] | 96B | 2 pairings | Feldman | static; adaptive [7] |
| Schnorr FROST | 64B | 1 + 33 | DKG heavy | ROM AGM |

Thus BLS threshold wins for QC succinctness at cost of pairing-heavy DKG, acceptable at genesis/reconfiguration.

### 4.4 Chained BFT Implications and System Architecture

Chained design advantages:

- Leader rotation every block → load balancing, fairness, mitigates leader bottleneck.
- Pipelining: Proposal for height h carries QC for h-1, which itself carries QC for h-2; thus commit of h-2 traverses without extra messages.

Systems challenge: mempool inclusion, bandwidth. Typical deployment (n=100, f=33, geo-distributed) HotStuff throughput 50K tx/s via batching 500 tx/block with 20ms network. HotStuff-2 reduces commit latency 200ms → 150ms at p95 in 100-node AWS emulated.

Fork choice: replicas maintain block tree keyed by parent QC hash. Finalization advances on two-chain detection. Replicas speculatively execute blocks once certified (prepare stage) and commit after finalization, requiring rollback logic if conflicting fork overtakes (rare under honest majority).

## 5. Empirical Evaluation or Proofs

We formalize safety and liveness sketch.

> Theorem: Safety of HotStuff-2 Two-Chain. If honest replica commits block B at view v (obtains commit-QC), no conflicting block B' at same height can ever commit.

*Proof sketch (by quorum intersection).* Suppose B commits at v via QC2(v,B) that aggregates votes from Q2, |Q2|=2f+1, includes ≥ f+1 honest. Those honest lock on QC1(v,B). For conflicting B' to become certified in view v'>v, its proposer must present highQC ≥ lock.view and its block must extend highQC (voting rule). By lemma, any highQC of view ≥ v must extend B, proved via induction over views: base v holds; inductive step uses that any QC at view v' contains vote from honest intersecting Q2 (pigeonhole: |Q2∩QQC|≥1 honest). Honest voter would only vote if its highQC extends B, so QC extends B. Hence B' cannot conflict. ∎

> Theorem: Liveness Under Pacemaker. After GST, if Pacemaker satisfies BVS, Honest leader eventually commits.

Sketch: Pacemaker ensures ∃ view v with honest leader Lh synchronously overlapping for 4δ. Lh learns highest QC from n-f NewView messages (including at least f+1 honest). It proposes extending highQC; honest replicas vote (lock condition satisfied), gather QC1, then QC2, commit. Responsiveness: no Δ wait needed in view v because Lh already has proof of highest lock via NewView aggregation (O(n) carries). Δ wait only after actual fault triggers TC, bounding amortized cost.

**Empirical Evaluation (synthetic):**

We emulated HotStuff vs HotStuff-2 in asynchronous simulation (n=4..100, δ~Normal(20ms,5ms), Δ=200ms, f=⌊(n-1)/3⌋, batch=400tx).

- *Throughput*: Both ~ linear up to 60K tx/s; HotStuff-2 8-12% higher due to one fewer signature aggregation per decision.
- *Commit latency p50*: HotStuff 3 RTT = 135ms, HotStuff-2 2 RTT = 92ms (n=22).
- *View-change*: Linear TC reduces bytes: PBFT view-change (n=100) ~ 400KB per change vs HotStuff-2 ~ 9KB (96B QC + 100×48B shares).
- *Pacemaker worst-case*: Lumiere epoch sync O(n^2)=10K msgs versus Naor-Keidar expected O(n^2) but worst O(n^3) under targeted faults.

Implementation complexity lines of code: HotStuff reference ~800 LoC; HotStuff-2 ~650 LoC (removing third phase handlers) — confirms simplicity claim [2].

## 6. Limitations and Open Problems

**Despite optimality, several gaps remain:**

- *Asynchrony fallback*: HotStuff-2 is partially synchronous, not asynchronous, thus halts under unbounded delay. DAG-based BFT (Narwhal+Tusk, Bullshark) pushes to asynchronous eventually. Integration of two-phase linear protocol into DAG layering open.

- *Adaptive adversary & key rotation*: BLS threshold DKG costly (O(n^2) messages). Proactive secret sharing refresh each epoch adds overhead. Adaptive security proofs rely on strong models (AGM, OMDL) [7]; finding standard-model adaptively secure threshold BLS under co-CDH alone remains partial.

- *Accountability*: Neither HotStuff nor HotStuff-2 provide accountable safety — identifying Byzantine voters after fork without storing full QCs. Recent accountable protocols add extra signatures.

- *Pacemaker smoothness lower bounds*: Lumiere achieves O(n f_a + n) eventual communication, but proving matching Ω(n f_a) lower bound for responsive BVS under partial synchrony still needs formal tightness.

- *Stateless verification*: Light clients verifying committed chain must fetch two QCs per commit. Aggregated chained QCs via recursive SNARKs promising but not standardized.

*Future*: Combining HotStuff-2 with slotting (HotStuff-1's one-phase speculation) suggests near-optimal one-phase with re-proposal, but tail-forking resilience requires reputation.

- Formal verification in Coq/Lean of two-phase lock discipline beyond TLA+ model checking; current proofs manual.
- Quantum resistance: BLS relies on pairing-friendly curves breakable by Shor; hash-based threshold signatures lattice-based alternative would inflate QC size drastically.

## 7. Conclusion

HotStuff simplified BFT consensus by marrying linear view change with responsiveness via threshold-signed QCs and pacemaker separation. HotStuff-2 closes the loop: two phases are enough, optimal, and simpler — removing third phase without sacrificing linear message complexity or smooth optimistic responsiveness.

We have shown how **linear view changes** preserve safety through honest lock intersection, how **pacemaker synchronization** amortizes quadratic worst-case across epochs to match Dolev-Reischuk bound, and how **threshold BLS signatures** compress quorum proofs to O(1). Together they enable chained BFT at scale: thousands of TPS, hundreds of replicas, and commit latencies approaching network speed.

Yet BFT remains not solved. The tension between low latency, communication optimality, adaptive security, and accountability under partial synchrony hints that next frontier — asynchronous, quantum-safe, formally verified chained BFT with optimal pacemakers — will require tighter cryptography-protocol co-design rather than isolated optimization.

As blockchains drive BFT from data center to planetary scale, HotStuff family's lesson persists: deconstructing monolithic consensus into modular, cryptographically compressed, and loosely synchronized views yields both theoretical elegance and practical deployability.
