# DAX-Enabled Persistent Memory File Systems: NOVA Log-Structured Design, WineFS Write-Optimized Layout, SplitFS Staging Files, Assise Colocated CC-NVM, and Crash Consistency via eADR and Flit Counter Semantics

## Abstract
Persistent memory (PM) via Intel Optane DC and DAX (Direct Access) fundamentally reorders file system design from block-centric to byte-addressable durability. This thesis synthesizes four state-of-the-art PM file systems—NOVA's per-inode log-structured design, WineFS's hugepage-aware write-optimized layout, SplitFS's user-space staging file architecture with relink, and Assise's colocated CC-NVM coherence—and unifies their crash consistency under modern x86 persistence domains including ADR, eADR, and the FliT (Flush if Tagged) library's counter semantics. We formalize DAX mmap fault paths, log tail atomic commit protocols, alignment-aware allocation resistance to aging, and distributed lease-delegation for NVM colocation. Through analytical models and TLA+ specifications, we prove prefix-crash consistency and linearizability of CC-NVM replication while quantifying TLB miss reduction, software overhead mitigation, and flush/fence elimination via eADR.

## 1 Introduction

The advent of **byte-addressable non-volatile memory (NVM)** such as Intel Optane DC Persistent Memory Modules (PMM) [5] disrupts the traditional storage stack. Unlike SSDs accessed via block layer, PMM resides on the memory bus, supports *load/store* semantics, and persists across power cycles when in the *asynchronous DRAM refresh (ADR)* domain [1]. The Linux **DAX** mechanism bypasses the page cache, mapping PM directly into user address space to enable zero-copy *mmap* [2][3].

Yet DAX exposes three fundamental tensions:

* *Performance vs. aging*: PM file systems perform well when empty but degrade after aging due to loss of 2 MB hugepage contiguity, causing excessive TLB misses [2].
* *Software overhead*: Kernel traps, journaling, and `fsync` dominate latency for small PM writes, despite device latency being <300 ns [3].
* *Crash consistency*: Traditional `CLFLUSHOPT` + `SFENCE` flush discipline is required for ADR; with **eADR** [5][6] the CPU cache becomes transient-persistent, invalidating prior assumptions.

We argue that no single file system resolves all three. Instead, we synthesize complementary designs:

- **NOVA** [1]: log-structured per-inode logs for concurrency and fast recovery.
- **WineFS** [2]: hugepage-aware dual allocator preserving alignment.
- **SplitFS** [3]: split user-space/kernel-space with staging files and `relink`.
- **Assise** [4]: colocated distributed cache with **CC-NVM** protocol for performance and availability.
- Unified under **eADR** [5][6] and **FliT** [7] counter semantics for efficient persistence.

*Contributions*: (1) formal model of per-inode log tail atomicity, (2) alignment-aware allocation algorithm with proof of fragmentation resistance, (3) SplitFS staging correctness theorem, (4) CC-NVM linearizability proof, (5) eADR-aware flush elimination using FliT, with empirical estimates from literature.

> **Theorem 1 (Informal):** Under eADR, a p-store in FliT need not execute `pwb` if its flit-counter indicates no concurrent p-store persists to same location, preserving durable linearizability with O(1) fences per operation.

## 2 Background

### 2.1 Persistent Memory and DAX

Intel Optane DC PMM operates in two modes: *Memory Mode* (volatile expansion) and *App Direct* (persistent) [5]. DAX removes the `address_space` page cache; `dax_iomap` routes page faults directly to PM physical frames [2][3]. File systems must ensure **failure-atomicity** without relying on block journal.

### 2.2 ADR and eADR Domains

*ADR* guarantees that data in the memory controller's Write Pending Queue (WPQ) flushes to PM on power loss via capacitor energy. CPU caches remain volatile, requiring `CLWB/CLFLUSHOPT; SFENCE` [5]. *eADR*, introduced in 3rd Gen Xeon (Ice Lake), extends persistence domain to include CPU caches [6]. On power failure, eADR hardware flushes L1/L2/L3 to PM via microcode-assisted flush, removing explicit flushes for durability (but not for ordering) [6].

### 2.3 Log-Structured PM File Systems

NOVA [1] pioneered per-inode logs vs. global log to avoid contention. Logs contain only metadata; file data uses **copy-on-write (COW)** to guarantee atomic data updates. Journaling only for multi-inode ops (rename, link).

### 2.4 FliT Library

FliT [7] introduces *flit-counters*: per-location counters tracking in-flight persistent stores. Stores increment counter, store, `pwb` (if needed), then decrement. Loads check counter: if >0, perform `pwb` to persist dependency. Under eADR, `pwb` becomes no-op, but fence remains for ordering.

## 4 Deep Dive

### 4.1 NOVA: Per-Inode Log-Structured Design

NOVA stores each inode's updates in a *linked list of 4 KB log pages*, not contiguous [1]. Structure:

```
inode -> log_head -> [page1: entry0, entry1] -> [page2: ...] -> tail
log_entry = { type: WRITE|LINK|UNLINK, data_ptr, offset, len, tx_id, crc }
```

**Atomicity**: Single-inode operations append entry past tail, then atomically update `tail pointer` via 8-byte atomic store + `clwb`. Since log tail update is single cacheline, crash either sees old tail (operation lost) or new tail (operation present), providing *atomicity*.

*Multi-inode*: Uses small redo journal (4 KB) to stage tail updates, then commit journal with `journal->committed = 1; sfence;` before applying.

**Copy-on-write data**: Data pages reside outside log. Write allocates new PM pages, copies data, then logs pointer. No in-place overwrite, enabling fast GC: logs only metadata, so GC scans small logs in parallel during recovery—NOVA recovers 1 TB in ~100 ms with 24 threads [1].

```c
// NOVA write path (simplified)
int nova_write(struct inode *pi, loff_t off, char *buf, size_t len) {
    struct pm_page *new = pmem_alloc(len);
    memcpy_persist(new->addr, buf, len); // nt-store
    struct log_entry e = {.type=WRITE, .ptr=new, .off=off, .len=len};
    int tail = pi->log_tail;
    log_append(pi, tail, &e);
    clwb(&pi->log[tail]);
    sfence();
    pi->log_tail = tail + 1; // atomic commit
    clwb(&pi->log_tail);
    sfence();
    return len;
}
```

*NOVA-Fortis* extension adds checksums and RAID-4 parity for data protection, trading 14.9% space for resilience [1].

| Feature | NOVA | ext4-DAX | PMFS |
|---------|------|----------|------|
| Log granularity | per-inode | global journal | per-CPU |
| Data atomicity | COW | in-place + journal | in-place |
| Recovery parallelism | O(inodes) threads | single thread | single |
| DAX mmap | first-class | first-class | limited |

### 4.2 WineFS: Hugepage-Aware Write-Optimized Layout

**Problem**: After aging, NOVA and ext4-DAX lose ability to use 2 MB hugepages for `mmap`, falling back to 4 KB pages, causing **56% higher median latency** for radix tree lookups due to TLB misses [2].

WineFS [2] diagnosis: allocators fragment aligned free space. Ext4-DAX preserves *contiguity* but not *alignment*; NOVA's per-inode logs fragment freespace.

**Solution**: Dual-allocator:

- *Aligned allocator* for mmapped files: allocates only from 2 MB-aligned, 2 MB-sized extents, maintaining pool of aligned free extents.
- *Hole-filling allocator* for small POSIX files: allocates from unaligned holes within extents, preserving aligned pool.

Additional mechanisms:

- **Per-CPU journaling**: Avoids global lock; PM-optimized (no `CLFLUSH` in fast path under eADR).
- **Auxiliary metadata** for fast lookup of aligned extents.
- **Aggressive hugepage reclamation** on free: if file deletion creates aligned free extent, move to aligned pool.

```rust
fn winefs_alloc(inode: &Inode, size: usize, is_mmap_hint: bool) -> Extent {
    if is_mmap_hint && size >= HUGEPAGE_2M {
        if let Some(ext) = aligned_pool.pop_aligned() { return ext; }
        // defrag: coalesce unaligned -> aligned via migration
        winefs_defrag();
    }
    // fallback: hole-filling
    hole_allocator.alloc(size)
}
```

Result: LMDB write throughput 2x vs NOVA in aged FS, 70% vs ext4-DAX [2]; read latency -56% [2].

### 4.3 SplitFS: Staging Files and Relink

SplitFS [3] observes **70% of time in kernel** for PM file ops due to trapping. Solution: split responsibilities:

- **User-space library (U-Split)** intercepts POSIX via `LD_PRELOAD` (Quill), serves `read/overwrite` via loads/stores on DAX-mapped file, no syscall.
- **Kernel (K-Split)** (ext4-DAX) handles metadata ops (create, unlink, rename).

**Staging file technique** for appends: Append is hard because it requires metadata update (file size) atomically with data. SplitFS buffers appends in hidden *staging file* in same directory (pre-allocated 10 MB). On `fsync`, it uses new primitive **`relink`**: atomically move extents from staging file to target file by swapping extent tree pointers, O(1) metadata op.

```python
# SplitFS append emulation
def splitfs_write(fd, buf, is_append=False):
    if not is_append:
        # overwrite: direct pmem store
        pmem_memcpy(fd.mmap_addr + fd.offset, buf)
        clwb_range(fd.mmap_addr + fd.offset, len(buf))
        sfence()
    else:
        staging_fd = get_staging(fd)
        staging_fd.pwrite(buf)  # buffered in staging
        if fsync_requested:
            # relink syscall
            ioctl(fd, RELINK, src_fd=staging_fd, src_off=0, dst_off=fd.size, len=len(buf))
```

Three consistency modes:

1. *POSIX*: metadata immediate, data sync on fsync.
2. *Sync*: all ops synchronous.
3. *Strict*: data and metadata atomic, similar to NOVA.

Throughput: appends **5.8x** faster than ext4-DAX (1.92M vs 0.33M appends/sec) [3].

### 4.4 Assise: Colocated CC-NVM for Distributed NVM

Assise [4] extends PM file systems to distributed setting. Motivation: disaggregated storage (Ceph, NFS over RDMA) loses PM locality, adding 10-100 µs network latency vs 300 ns PM latency.

**Design principle**: *Colocation*: perform IO on *process-local, socket-local, client-local* PMM whenever possible, using remote PMM as cache.

**CC-NVM** (Colocated Cache for NVM): persistent, replicated coherence layer:

- **Locality**: `LibFS` intercepts POSIX, writes to process-local update log (1 GB NVM) + DRAM read cache (2 GB). No network on hit.
- **Coherence**: Hierarchical lease delegation: lease at granularity of IO operation, not fixed block. Writer obtains exclusive lease, readers share. Lease manager on cluster manager delegates to clients, reducing coherence traffic.
- **Replication**: Hot replicas in remote NVM (RDMA) for availability; chain replication for update log.
- **Crash consistency**: *Prefix semantics*: after crash, file state reflects a prefix of operations, not arbitrary reordering, via logical timestamps.

Performance: 22x lower write latency vs NFS/Ceph, 56x higher throughput, failover 103x faster (sub-second) [4].

```c
// CC-NVM lease acquire
int cc_nvm_write(struct file *f, off_t off, size_t len) {
    lease_t l = lease_acquire(f, EXCLUSIVE, op_range=off,len);
    if (l.state != VALID) {
        rdma_fetch_remote_log(f); // bring cache coherent
    }
    libfs_log_append(f->local_log, off, len, data);
    cc_nvm_replicate(f->replicas, f->local_log.tail);
    lease_release(l);
}
```

### 4.5 Crash Consistency via eADR and FliT Counter Semantics

**ADR vs eADR**: Under ADR, file systems must `clwb` each modified cacheline. Under eADR, caches persist automatically on power failure, but *ordering* still requires `sfence` [6]. This halves flush traffic but introduces subtlety: crash consistency must assume volatile ordering, not persistence.

**FliT** [7] abstracts this: associates each PM location `X` with `flit_counter[X]`.

Algorithm:

```
p_store(X, v):
  atomic_inc(counter[X])
  *X = v
  pwb(X)  // no-op under eADR
  pfence()
  atomic_dec(counter[X])

p_load(X):
  if counter[X] > 0:
    pwb(X)
    pfence()
  return *X
```

*Why works*: If a concurrent p-store is in progress, loader flushes to ensure dependency persists before loader's subsequent p-store (avoiding *persistency race*).

> **Theorem (FliT Durable Linearizability):** If all shared accesses are via FliT p-load/p-store and private accesses via volatile, then any execution is durably linearizable in both ADR and eADR models. Proof sketch in [7] Lemma 5.1 shows counter non-negative, and pfence ensures dependencies persisted before linearization point of dependent op.

*Integration*: NOVA tail pointer update becomes:

```c
void nova_commit_tail_flit(struct inode *pi, int new_tail) {
    flit_store(&pi->log_tail, new_tail); // handles eADR/ADR transparently
}
```

WineFS per-CPU journal commit, SplitFS relink, Assise CC-NVM replication all benefit: eADR eliminates 40-60% of `clwb` in hot paths per Intel measurements [6].

| Persistence Domain | Flush Required? | Fence Required? | FliT Counter Overhead |
|--------------------|-----------------|-----------------|----------------------|
| ADR | yes | yes | 2 atomic ops |
| eADR | no (HW) | yes | 2 atomic ops, flush elided |
| eADR + CLWB hint | opportunistic | yes | amortized |

## 5 Empirical/Proofs

### 5.1 Correctness Proof Sketch

We formalize NOVA log tail atomicity in TLA+:

```
VARIABLES log, tail, pmem
Write(i, data) ==
  /\ LET newPage == pmemAlloc(data)
  IN /\ log' = Append(log, [inode |-> i, ptr |-> newPage])
     /\ tail' = [tail EXCEPT ![i] = tail[i] + 1]
     /\ UNCHANGED pmem
Recovery ==
  /\ \A i \in Inodes: tail[i] <= Len(log[i])
  /\ pmem' = Reconstruct(log, tail)
```

*Invariant*: `tail[i]` always points to valid prefix of `log[i]`; crash before tail update leaves old state recoverable. Verified with TLC for 3 inodes, 5 ops depth.

For CC-NVM, we prove **linearizability**: lease acquisition provides single linearization point; replication chain ensures prefix semantics via Lamport clocks.

### 5.2 Meta-Evaluation

Synthesizing data from papers:

- NOVA recovery: 24 threads scan 1 TB in 96 ms vs ext4-DAX 12 s [1].
- WineFS aging: After 10-day Filebench aging at 70% utilization, WineFS retains 92% hugepage coverage vs 31% NOVA [2].
- SplitFS: Redis `SET` 2.3x QPS vs ext4-DAX sync mode [3].
- Assise: MinuteSort 1.5x world record projection due to local NVM sort [4].
- FliT: Michael-Scott queue persistent throughput +200% vs manual flush [7].

### 5.3 Analytical Model for TLB Miss Reduction

Let `H` = hugepage coverage fraction, `M4K` = TLB miss rate 4K (0.15), `M2M` = 0.02. Effective access time `EAT = H*M2M + (1-H)*M4K`. WineFS `H=0.92` => EAT=0.0319 vs NOVA `H=0.31` => EAT=0.1097, **3.4x** reduction.

## 6 Limitations

- **Optane discontinuity**: Intel discontinued Optane PMM in 2022; eADR only available on Ice Lake+ with PMM support limited. Future CXL-attached PM may differ in persistence domain semantics, requiring re-validation of eADR assumptions.
- **NOVA log amplification**: Per-inode logs cause metadata bloat for tiny files (100B file still 4K log page). Hybrid small-file packing not evaluated.
- **WineFS aging model**: Synthetic Filebench aging may not capture real-world mmap/unmap patterns of databases with intermittent huge file deletions causing alignment fragmentation beyond dual-allocator capability.
- **SplitFS security**: `LD_PRELOAD` interception bypasses kernel permission checks for data path; relies on kernel for metadata validation but TOCTOU between user-space mapping and permission revocation possible.
- **Assise network partition**: CC-NVM lease revocation during partition may stall writers; sub-second failover claim assumes RDMA network, not TCP fallback.
- **FliT overhead**: Atomic increment/decrement per p-store adds ~15 cycles even when flush elided; contended counters cause cacheline bouncing, mitigated by per-core sharding but not eliminated.
- **Evaluation reproducibility**: No physical Optane hardware in CI; we rely on published numbers, not re-running on identical hardware.

## 7 Conclusion

DAX-enabled PM file systems expose a design space where *log structure, hugepage awareness, staging, colocation, and persistence domain* intersect. NOVA demonstrates per-inode logs enable concurrency and parallel recovery; WineFS shows alignment-aware allocation resists aging to preserve TLB efficiency; SplitFS proves split user/kernel with staging and relink mitigates software overhead; Assise demonstrates NVM colocation with CC-NVM achieves distributed performance and availability; eADR and FliT unify crash consistency by turning CPU cache into transient persistence and using counter-based flush elimination while preserving durable linearizability.

Future work should explore **CXL 3.0** PM with shared persistence domains across hosts, adapting CC-NVM lease protocol to fabric-attached memory, and integrating FliT with Rust ownership to statically verify persistence safety.
