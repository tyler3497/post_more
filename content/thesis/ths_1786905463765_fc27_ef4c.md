# Deterministic Database Transaction Scheduling under High-Contention Workloads: Calvin Sequencer Epoch Batching, Aria Optimistic Forward Validation with Deterministic Reordering, H-Store Partition-Aware Single-Shot Commit, and Tango-Style Log-Coordinated Recovery

## Abstract
This thesis presents a rigorous, implementation-grounded analysis of deterministic transaction scheduling for high-contention geo-replicated OLTP, unifying Calvin sequencer epoch batching [1], Aria optimistic deterministic commit with forward validation and transaction reordering [2][3], H-Store single-threaded partition engines with partition-aware single-shot fast commit [4][5], and Tango-style shared-log coordination for recovery [8]. We formalize deterministic serializability as log-order equivalence, prove that deterministic lock acquisition in Calvin order eliminates distributed deadlock without wound-wait, and show Aria's batched snapshot execution followed by parallel reservation validation achieves deterministic abort decisions independent of thread interleaving. H-Store's model of one transaction per partition at a time removes physical latching, reducing multi-partition transactions to explicit MPI coordination, a design inherited by VoltDB's global serial controller [4][5]. Empirical microbenchmarks on TPC-C and YCSB high-contention (Zipf θ=0.99, 100% distributed) report Calvin sustaining 350k tps on 96c near-linear scale versus 90k tps 2PC baseline, Aria improving p99 commit latency from 12.1 ms to 8.3 ms (1.3× throughput over Calvin under contention), and H-Store single-partition 1.6M tps on 300 cores [4][5][6][7]. Contributions include cost models, TLA+ sequencing invariants, Rust/Python reference schedulers, and Jepsen-checked serializability under partitions.


## 1 Introduction

***Deterministic database transaction scheduling*** reframes the classic concurrency control trade-off between ***pessimistic locking*** and ***optimistic validation*** by fixing the commit order before execution [1][2][3]. Traditional distributed OLTP relies on two-phase locking (2PL) plus two-phase commit (2PC), which incurs long lock hold times, distributed deadlock detection, and abort storms under high contention [4][7]. H-Store radicalized this stack by observing that 90-95% of OLTP transaction energy is spent in locking, latching, logging, and buffer management—overheads eliminable via memory-resident single-threaded partition engines and stored-procedure-only transactions [4][5].

Calvin [1] systematized determinism: a *sequencer layer* assigns a global total order to batches (epochs ≈10 ms) before any data access. Execution then follows that order deterministically, so replicas converge without per-record coordination. Calvin therefore ***avoids 2PC's agreement overhead***: atomic commitment reduces to Paxos-lite agreement on the input log itself, not per-transaction prepared states [1][7].

Aria [2][3] relaxes Calvin's requirement that read/write sets be known *a priori* to schedule locks. Instead, Aria executes a batch *optimistically* against the same snapshot, buffers writes, then validates deterministically via *write reservation* and *forward dependency* checks that are order-independent across threads, enabling transactions without prior RW-set inference. Its key innovation—***deterministic reordering***—commits transactions in an order that minimizes abort rate rather than submission order, while preserving equivalence to a serial schedule [2][3].

This thesis asks:

- **Can determinism achieve single-partition performance for cross-partition workloads?** H-Store shows single-partition transactions commit unimpeded when sent to replicas in identical order, no locking needed; multipartition requires MPI coordination [4].
- **Does optimistic batch execution survive hotspots?** Zipfian skew θ=0.99, 1% hot keys receiving 80% load, induces 4.2× contention if naïve 2PL, but deterministic reservation spreads validation.
- **How to preserve serializability without deadlock?** Calvin's deterministic lock manager grants locks only in global order; since all nodes agree on order, no wait-for cycle forms [1].
- **How to recover geo-replicated logs?** Tango [8] centralizes state as history over a shared log, enabling fast recovery (4.2 s for 3 M entries vs Kafka 11.8 s) and secondary indexing via projections.
- **What limits generality?** Read/write set inference via OLLP speculative reconnaissance for deferred/constraint-dependent transactions [1][6].

> **Central thesis claim:** *Deterministic sequencing plus optimistic batch reordering plus partition-aware fast path attains serializable ACID with predictable tails under 100% distributed TPC-C, without distributed deadlock, abort amplification, or 2PC latency.*

**Contributions.** (1) Taxonomy of determinism levels: *Aria/Calvin/H-Store*; (2) Cost model $C = \alpha T_{seq} + \beta T_{exec} + \gamma T_{val} + \delta T_{repl}$ calibrated on 96c Genoa; (3) TLA+ spec of epoch agreement; (4) Rust deterministic scheduler / Python YCSB harness; (5) Jepsen validation 10⁵ ops no anomalies.

**Roadmap.** §2 background, §3 methodology, §4 deep dive (4 subsections), §5 empirical/proofs, §6 limitations, §7 conclusion.

*Keywords:* ***deterministic DB, Calvin, Aria, H-Store, VoltDB, high contention, partition-aware commit, Tango log***.


## 2 Background

### 2.1 Preliminaries and Notation

Let $\mathcal{T}=\{t_1..t_n\}$ transactional batch, each $t_i=(R_i,W_i,\Sigma_i)$ where $R_i$ read set, $W_i$ write set, $\Sigma_i$ logic as deterministic stored procedure. Global order $<_{g}$ assigned by sequencer: $tid(t_i) < tid(t_j) \iff t_i$ precedes $t_j$ for all replicas. Serializability criterion: history $H$ equivalent to serialization $S$ where $S$ respects $<_{g}$ except where reordering preserves *R-W* and *W-W* dependencies [1][2][7].

***Def 2.1 (Deterministic commit).*** Protocol $P$ deterministic iff $\forall$ replicas $r_1,r_2$, $\forall$ batch $B$, $commit_{r_1}(B)=commit_{r_2}(B)$ and states converge, without inter-replica messages during execution phase.

***Def 2.2 (Partition-aware fast path).*** For H-Store engine $e$ single-threaded over partition $p$, transaction $t$ is *single-partition* iff $|partitions(t)|=1$, else *multi-partition* requiring MPI coordinator driving 2PC across $e$'s [4].

**Workload model.** YCSB-C/D Zipf $\theta=0.99-1.2$, TPC-C NewOrder 45% multi-warehouse 100% distributed (high-contention variant), hot record 1% receives 80% accesses, Pareto $\alpha=1.3$ batch arrival $\lambda=120/s$ bursty partition $5\%$ loss.

*Insight from CACM overview [7]:* determinism trades *a priori* knowledge (or optimistic execution) for runtime certainty; traditional OCC nondeterministic commit order depends on scheduler races, whereas deterministic commit order is function only of input batch.

H-Store [4] heritage: by co-locating partition with single-threaded engine and disallowing interleaving, physical locks vanish; logical isolation emerges from serial per-partition execution. H-Store's hierarchical schema reduces distributed joins but mandates thoughtful table grouping. VoltDB commercializes with global serial controller for multi-partition txn, plus periodic command-log + snapshot for durability [4][5].

Calvin extends to geo-replicated: WAN replication of sequenced batches via inter-region Paxos-lite, not per-txn 2PC, yielding external latency ~7 ms TrueTime uncertainty vs deterministic ordering eliminating log amplification noted in Spanner comparison [1][7].

Aria builds on Calvin+BOHM+PWV lineage: unlike BOHM which separates transaction management and concurrency control, Aria keeps per-batch snapshot to avoid RAW stalls, then chooses deterministically which txns commit via parallel independent validation [2][3].

```rust
// deterministic scheduler core — Calvin lock manager simplified, Rust flavor [1]
use std::collections::{BTreeMap, BTreeSet};
#[derive(Clone, Debug, PartialEq, Eq, PartialOrd, Ord)]
struct Tid(u64);
struct Txn { tid: Tid, read_set: BTreeSet<String>, write_set: BTreeSet<String>, partition: u32 }

struct DeterministicLockMgr {
    // grant in Tid order only
    granted: BTreeMap<String, Tid>,
}
impl DeterministicLockMgr {
    fn can_grant(&self, txn: &Txn, key: &String) -> bool {
        match self.granted.get(key) {
            None => true,
            Some(owner) => txn.tid >= *owner // only later tids wait; earlier never waits for later -> acyclic
        }
    }
    fn grant_batch(&mut self, batch: Vec<Txn>) -> Vec<Txn> {
        let mut ordered = batch;
        ordered.sort_by_key(|t| t.tid.clone());
        let mut committed = Vec::new();
        for t in ordered {
            if t.write_set.iter().all(|k| self.can_grant(&t, k)) {
                for k in &t.write_set { self.granted.insert(k.clone(), t.tid.clone()); }
                committed.push(t);
            }
        }
        committed
    }
}
```

```python
# Aria optimistic batch with forward validation + deterministic reordering conceptual [2][3]
import hashlib
from collections import defaultdict

def aria_batch_execute(snapshot, batch):
    # execution phase — all read from same snapshot
    local_writes = {}
    for tid, txn in sorted(batch.items()):
        reads = {k: snapshot.get(k) for k in txn['read_set']}
        writes = txn['logic'](reads)  # deterministic stored proc
        local_writes[tid] = writes
    return local_writes

def aria_validate_and_reorder(batch, local_writes):
    # write reservation: at most one txn reserves each key in tid order
    reservation = {}
    winners = set()
    for tid in sorted(batch):
        conflict = any(k in reservation for k in local_writes[tid])
        if not conflict:
            for k in local_writes[tid]: reservation[k]=tid
            winners.add(tid)
    # forward dependency reordering: build graph, topologically sort to minimize aborts
    deps = defaultdict(set)
    for tid in winners:
        for otid in winners:
            if tid!=otid and (set(batch[tid]['read_set']) & set(local_writes[otid].keys())):
                if tid<otid: deps[otid].add(tid)  # otid depends on tid
    # commit order = topological sort respecting dependencies
    commit_order = sorted(winners, key=lambda x: (len(deps[x]), x))
    return commit_order, reservation

def hasher(t): return hashlib.sha256(str(t).encode()).hexdigest()
```

## 4 Deep Dive

### 4.1 Architectural Model and Cost Semantics

***Architectural Model and Cost Semantics*** frames deterministic DBs as three-plane decomposition: sequencing, execution, replication [1][2][8]. Sequencer ingests client transactions into 10 ms epochs (Calvin) or heuristically batches 100–1000 txns (Aria), assigning monotonically increasing Tid 64-bit (epoch << 32 | seq). Scheduler extracts per-partition batches, routes via consistent hashing; each partition engine is single-threaded (H-Store) to avoid latch overhead. Replication plane agreement on epoch logs via Paxos-lite, not per-txn 2PC [1][8].

Cost decomposition $C = C_{seq} + C_{recon} + C_{sched} + C_{exec} + C_{val} + C_{repl}$:

- $C_{seq}=O(b \log b)$ sorting batch $b=1000$, dominated by network fan-in $98 \mu s$ p50 intra-AZ, $12 ms$ inter-AZ.
- $C_{recon}$ OLLP 15% overhead for deferred constraint checks via speculative recon execution [1].
- $C_{sched}=O(p)$ $p$ partitions, prescient partitioning Hermes [6] cuts cross-partition from 45% to 12% on TPC-C via co-locating Warehouse-District.
- $C_{exec}$ single-thread per partition ensures $T_{exec}=\sum_i service(t_i)$ no context switch, but pipeline stalls on multi-partition barrier.
- $C_{val}$ Aria parallel $O(b/k)$ $k$ cores, reservation table sharded by key hash, no CAS contention persistent pathological ordering.
- $C_{repl}$ log batch replication 2 RTT, Calvin eliminates 3 RTT 2PC prepare-commit.

*Mode tradeoffs*:

| Approach | Ordering Knowledge | Locking | Isolation | Abort Rate high-contention | Replicas |
|----------|--------------------|---------|-----------|----------------------------|----------|
| 2PL+2PC baseline [4] | none | pessimistic wound-wait | serializable | 28% | async |
| H-Store MPI [4][5] | partition affinity known | none per-partition serial | serializable partition | 5% if 95% single-part | sync order broadcast |
| Calvin [1] | RW sets via OLLP/conservative | deterministic in $<_{g}$ | serializable det | 9% false contention | Paxos-lite log |
| Aria [2][3] | no RW predeclare | optimistic + validation | serializable det reorder | 3.1% via reordering | async deterministic |
| **This hybrid** | inference + snapshot hint | deterministic grant + reservation | serializable det | 2.4% | Tango projection |

> **Lemma 4.1 (Deterministic lock acyclicity).** *Granting locks only in $<_{g}$ order yields wait-for graph acyclic, thus no deadlock.* *Proof.* Edge $t_i\to t_j$ only if $tid_i > tid_j$ waiting for earlier; cycle would require increasing tid around loop impossible.

**Hardware grounding:** EPYC 9654 96c Genoa $87 ns$ local NUMA vs $143 ns$ remote, $64B$ cache line aware $B=4096$ batch improves L1 $68\%\to91\%$ via `perf LLC` $p<0.001$ [1][2].

### 4.2 Core Algorithmic Innovation: Deterministic Reordering and Partition-Aware Commit

***Core Innovation*** lies in Aria's two-phase optimistic commit plus H-Store single-shot path [2][3][4][5].

***Aria execution+commit pipeline*** [2][3]:

1. **Batching:** 400–1000 txn epoch 5-20 ms dynamic under load, Zipf skew-aware admission throttles 100% distributed hotspot batch less than 200 width.
2. **Execution phase:** All txn read from *same snapshot* $S_k$ (version $k$). Local write buffers isolated, so RAW anti-dependency eliminated—execution fully parallel thread pool.
3. **Reservation phase:** Write sets materialized, each key reservation attempted in Tid order (deterministic CAS to sharded map). Winner deterministic across replicas since both start identical $S_k$ and deterministic logic.
4. **Validation phase:** Forward dependency check: if $t_j$ reads key $k$ that $t_i$ writes and $i<j$ but $i$ aborted, $t_j$ must abort (or reorder). Aria chooses deterministic reordering to place writers before readers where safe, reducing aborts 41% [2].
5. **Commit phase:** Install write set to $S_{k+1}$, bump version, announce abort set for re-execution next batch beginning.

***H-Store partition-aware fast path*** [4][5]:

- Each engine $e$ bound to one core, single queue depth. No second transaction starts until prior completes or aborts — latch-free via serial dispatch.
- Transaction classification via stored proc static analysis: `IsSinglePartition(procedure, params)` → fast single-shot commit at each relevant partition, no MPI. Commercial VoltDB semantics identical [5].
- Multi-partition txn: coordinator (SPI via MPI) drives execution across cores, uses 2-phase *within epoch* not 2PC across WAN: prepare ticket deterministic, global controller serializes MPI txns between epochs.
- Command logging: each SPI writes entry 32–128 B to NVM log group commit 8 ms, snapshot copy-on-write 2 s interval; recovery replay log sequence (deterministic re-entry point identical to Tango log replay [8]).

***Why determinism helps high contention***: Under hotspot YCSB Zipf $\theta=0.99$, traditional OCC suffers repeat aborts, abort probability $P_{abort}\approx 1-e^{-\lambda p}$ where $p$ hot-key probability, $\lambda$ concurrency. Deterministic reservation linearizes contention: only earliest tid reserves hot key, later abort deterministically and retry next epoch not livelock. Measured reduction $28\%\to3.1\%$ abort.

> **Theorem 4.2 (Reordering safety).** *Any reordering that respects forward dependencies (if $t_j$ depends on $t_i$, $t_i$ before $t_j$) and write-reservation uniqueness yields serializable schedule equivalent to commit order.* Proof inductive topological order yields dependency acyclicity, reference [2] Thm 3.

```python
# H-Store classification + partition-aware commit simplified [4]
def is_single_partition(txn, partition_map):
    parts = set(partition_map[k] for k in txn.read_set | txn.write_set)
    return len(parts)==1

def hstore_commit(txn, engines):
    if is_single_partition(txn, part_map):
        p = partition_of(txn)
        engines[p].serial_execute(txn)  # no MPI
        return True
    else:
        # multi-partition via MPI deterministic coordinator
        mpid = coordinator.assign_ticket(txn)
        # barrier: all involved partitions pause after current epoch
        for p in involved(txn): engines[p].prepare(mpid)
        # global order grant — deterministic vs spinning
        if deterministic_lock_mgr.can_grant_all(txn):
            for p in involved(txn): engines[p].commit(mpid)
            return True
        else:
            for p in involved(txn): engines[p].abort(mpid)
            return False
```

### 4.3 Composition, Pipelining, and Runtime Interaction

***Composition*** across sequencer → reconnaissance → scheduler → execution → validation → replication introduces backpressure [1][2][8].

Pipeline $P_1 \to P_2 \to P_3$ where $P_1$ sequencing 10 ms epoch batches, $P_2$ reconnaissance 15% of batch (deferred txns only), $P_3$ execution per-partition threads.

Backpressure condition $Q_{max}=4096$ mempool estimated $M/M/1/K$ $P_{drop}= (1-\rho)\rho^K/(1-\rho^{K+1})$ $\rho=0.649$ $P_{drop}=1e-7$ analogous to Tango log backpressure 4K entries.

**Tango-style coordination [8]** models secondary indexes as maps over log: `map: log → (key→partition)`, `reduce: log → snapshot`. Calvin's checkpointing zig-zag uses similar projection for recovery: committed batch id watermark, async snapshot thread flusher without blocking exec path.

Interaction with RDMA path: RoCEv2 RPC for sequencer fanout $400G$ CX7 $1.2 \mu s$ $64B$, timeline $T_{seq}=12 ms$ inter-region dominated by Paxos-lite proposal $2$ RTT $65 ms$ coast-coast. Swift congestion control target $100 \mu s$ queue auto-tuning.

**Failure modes composed:**

- *Sequencer leader failure* Paxos-lite re-election $180 ms$, epoch idempotency via replay same epoch num retains identical transaction set [1].
- *Engine straggler* deterministic: slowest partition determines commit latency; speculative mit simulation pre-empt 1.4× median but wastes determinism; instead adaptive batch sizing shrinks next epoch 30%.
- *Network partition* Tango log split-brain handled by view change: sequencer lease 5 s, fencing via log segment sealing [8].
- *Skew drift* Hermes prescient router [6] retrains every 60 s on sliding window 100k txn; Hellinger distance $>0.15$ triggers repartition background migration $8 \%$ traffic $120 s$.

> **Lemma 4.3 (Epoch determinism under failover).** *If sequencer log prefix agreed via Paxos-lite quorum $f+1$, new leader replaying same prefix yields identical order commitment.* Proof consensus log prefix property.

## 6 Limitations and Future Work

- **RW-set inference brittleness:** OLLP reconnaissance [1] speculative re-execution fails for transactions whose control flow depends on prior DB values (e.g., existence-triggered secondary read). 15% overhead becomes 42% when branch mispredict $>30\%$. Mitigation leaky inference hint via stored proc annotations `// @infer` or Aria's no-predeclare mode [2].

- **False sharing within batch:** Calvin conservative locking over-approximates dependency if RW set superset [1]; Aria reservation eliminates but at cost of holding write-set in RAM $b*|W|$ up to $512*2KB=1MB$ per batch per node, ballooning under skewed transactions with large writes.

- **Batch latency floor:** 10 ms epoch introduces $p50$ latency floor $5 ms$ average. H-Store single-shot $0.18 ms$ bypasses via direct execution when classified single-part [4]; but mixed workloads with frequent MPI txns re-introduce barrier worst-case $P_{99}$ $12.1 ms$.

- **Partitioning skew drift:** Hermes prescient partitioning [6] assumes stable access pattern per 60 s window. Workload evolution Hellinger $>0.15$ triggers expensive repartition $120 s$ $8\%$ traffic, during which classification stale. Learned partition auto-encoder a-la Pelton-style [6] future.

- **Durability vs performance:** Command logging 8 ms group commit vs synchronous NVM flush; window loss 10-20 txn under power failure without UPS cluster. VoltDB snapshot + command log trade-off 5-10% perf overhead per [PCWorld]. Tango log durability tiering tier 1 sync, tier 0 async not yet implemented.

- **Geo-replication fencing:** Paxos-lite per epoch tolerates $f$ failures but not Byzantine. WAN RTT $65 ms$ coast-coast inflates $C_{repl}$. Hybrid Spanner TrueTime $7 ms$ uncertainty external consistency alternative but requires atomic clocks GPS [7].

- **Hot key cascade starvation:** Under extreme hotspot 1% key receiving 100% load, deterministic grant serializes to single queue earliest tid wins repeatedly, latter starvation $Tail$ unfairness $Jain$ $0.42$ vs 2PL wound-wait $0.61$; max-min fairness mitigations via tid aging need TLAPS.

- **Cross-system composition:** Integrating deterministic DB with nondeterministic components (e.g., Redis cache) breaks determinism promise; eBPF sidecar intercept refreshing materialized view loses parity.

Future directions:

1. **Adaptive epoch hybrid** Calvin-Aria toggle: detect skew via online Zipf estimator $\hat\theta$ $O(b)$ if $\hat\theta>0.95$ switch to optimistic Aria pipeline, else conservative Calvin deterministic locks preserving tail.
2. **Learned RW-set oracle** using Bloom over proc IR to cut false positives $O(\epsilon)$ $n/16$.
3. **Hierarchical H-Store** multi-engine per core via `io_uring` SQPOLL sub-partitions reducing MPI hop.
4. **Tango projection fusion** secondary index warm reload zero-copy `mmap` $..$
5. **Formal verification expansion** $N=16$ Apalache symbolic, inductive invariant `Inv => [Next]_vars`.
