# Weak Memory Models from x86-TSO to RC11: Store Buffers, Release–Acquire Synchronization, Operational and Axiomatic Semantics, and the Verification of Relaxed-Concurrency Programs

## Abstract

Modern multiprocessors and optimizing compilers refuse the fiction of sequential consistency: store buffers, speculative issue, and code motion admit executions that no interleaving of thread instructions can produce. This thesis surveys weak memory models from the hardware contract of x86-TSO — simultaneously an operational store-buffer machine and an equivalent axiomatic total-store-order model [1] — through the C++11 release–acquire discipline and its out-of-thin-air pathologies, to the RC11 repair that restored sound compilation to Power [2]. We contrast the two great definitional styles: operational abstract machines, including per-thread promise buffers [3] and point-to-point communication for release–acquire [4], against axiomatic execution-graph semantics over program order, reads-from, modification order, and happens-before. We examine the equivalence bridges between them, and finally survey verification practice: GenMC's optimal dynamic partial-order-reduction model checking over axiomatic models [5][6] and the program logics — RSL [10], Owicki–Gries for RA [7], iGPS in Iris [8] — that make relaxed-concurrency programs provable rather than merely executable.

##1 Introduction

For four decades, programmers reasoned about shared-memory concurrency through Leslie Lamport's *sequential consistency* (SC): every execution is equivalent to some interleaving of the threads' instructions that respects each thread's program order. SC is the natural mental model, and it is also, on real machines, a lie. The store-buffering (SB) litmus test tells the story in four instructions:

```cpp
// x = y = 0 initially; both locations atomic with seq_cst or plain x86 stores
// Thread 0               // Thread 1
x.store(1);               y.store(1);
r1 = y.load();            r2 = x.load();
```

On every modern x86 processor, the outcome `r1 == 0 && r2 == 0` is *observable*: each thread's store sits in its own FIFO store buffer, draining to coherent shared memory later, while each load reads the still-stale memory. No interleaving explains this outcome. The program is not sequentially consistent, and neither is the machine it runs on.

Two forces relax memory. **Hardware**: store buffers hide write latency, speculative issue hides load latency, and non-multi-copy-atomic interconnects (Power, pre-v8 Arm) let cores observe writes in different orders. **Compiler**: reordering independent accesses, load-after-store elimination, and value-range propagation are invisible single-threaded but observable the moment a second thread watches. A language model must therefore do two contradictory jobs: free the compiler to transform code aggressively, and give the programmer a contract strong enough to reason about.

C++11 was the first serious attempt at such a contract — mechanized by Batty et al. [9], with access modes *relaxed*, *release/acquire*, *acq_rel*, *seq_cst*, and a *data-race freedom* (DRF) promise of SC to race-free programs. But it contained genuine defects: its `seq_cst` treatment admitted behaviors no sound Power compilation could reproduce while forbidding optimizations compilers needed — the "too strong" and "too weak" problems of [2]. Deeper still, its *relaxed* axiomatics permits **out-of-thin-air (OOTA)** executions: reads returning values no thread ever wrote, justified by circular self-fulfilling prophecies in the candidate-execution graph [3].

This thesis is organized around three questions. First, what do the canonical hardware and language models actually say — x86-TSO's dual operational/axiomatic presentation, the release–acquire fragment, and the RC11 repair? Second, how do the two definitional styles — *operational* abstract machines versus *axiomatic* predicates over execution graphs — compare, and where do equivalence theorems bridge them? Third, how do we *verify* programs against these models: with optimal model checkers like GenMC, and with program logics from RSL to iGPS?

##2 Background

### 2.1 Sequential consistency and its discontents

Lamport's SC demands a single global order of all memory operations consistent with each thread's program order — the mental model behind Owicki–Gries, rely/guarantee, and separation logic. The trouble is physical: a store globally visible before the next instruction issues would stall the pipeline on every write. A *store buffer* amortizes this by letting the thread proceed while the write drains to the cache hierarchy, and *store forwarding* lets a thread read its own still-buffered write — preserving single-thread semantics while breaking the global interleaving story.

Litmus catalogs organize behaviors by which program-order pairs may reorder: x86 permits only store→load (to distinct addresses); Power and Arm add load→load, load→store, store→store, and independent reads of independent writes (IRIW) via non-multi-copy-atomic propagation. Architecture litmus suites — thousands of `diy`-generated tests executed on silicon via `litmus7` — pin down the observable envelope every faithful model must enclose [1].

### 2.2 The C++11 atomics taxonomy

C++11 stratifies atomic accesses by strength:

| Mode | Ordering guarantee | Typical use |
|---|---|---|
| `memory_order_relaxed` | Per-location coherence only | Counters, statistics |
| `memory_order_release` / `acquire` | Synchronizes-with edges, transitive hb | Message passing, flags |
| `memory_order_acq_rel` | Both directions | Read-modify-write |
| `memory_order_seq_cst` | Single total order S over all SC ops | Locks, default |

A *release* store *synchronizes-with* an *acquire* load that reads from it (or from its release sequence), and *happens-before* (hb) is the transitive closure of program order (sb) with synchronizes-with (sw). The canonical idiom is **message passing (MP)**:

```cpp
std::atomic<int> x{0}, f{0}; int data = 0; // data is non-atomic payload
// Thread 0 (publisher)            // Thread 1 (subscriber)
data = 42;                         while (!f.load(memory_order_acquire)) {}
x.store(1, memory_order_relaxed);   r = x.load(memory_order_relaxed);
f.store(1, memory_order_release);   // r == 1 guaranteed; data == 42 safe
```

The release store of `f` synchronizes with the acquire load that observes it, so the prior relaxed store to `x` — and the non-atomic write to `data`, by the DRF guarantee — happens-before the subscriber's reads. The outcome `r == 0` after observing `f == 1` is forbidden: this is the *causality* that release–acquire buys without a single fence instruction on x86 or Armv8.

**Data-race freedom** is the model's social contract: a program whose every execution is free of races on non-atomic locations (and on atomics, races are permitted but ordered) behaves as if sequentially consistent. Compilers exploit the contrapositive: non-atomic accesses may be compiled to plain machine instructions and subjected to all standard sequential optimizations, because any race is the programmer's undefined behavior [2].

### 2.3 The out-of-thin-air problem

The relaxed fragment's axiomatics admits executions in which a value appears from nowhere. The classic shape is *load buffering with control dependency* (LB+ctrl):

```
Thread 0:  r1 = x; if (r1 == 42) y = 42;     Thread 1:  r2 = y; if (r2 == 42) x = 42;
```

C++11 deems `r1 == r2 == 42` *consistent* though no thread ever wrote 42: reads justify writes and writes justify reads in a closed causal loop. OOTA executions are unobserved on hardware and catastrophic for reasoning — they break DRF's promise and make allowed outcomes non-computable in the worst case. The promising semantics [3] and Promising 2.0 [10] attack the problem operationally, requiring every speculatively-introduced write to be *certifiable*.

> **Theorem: DRF-SC for release–acquire (Lahav et al. [4]).** Every data-race-free program executed under the (strengthened) release–acquire semantics exhibits only sequentially consistent behaviors.

### 2.4 Compilation as the ground truth

A language model is implementable only if each mode maps to real instructions — release/acquire to plain x86 loads/stores plus compiler barriers, `seq_cst` stores to `XCHG` or `MOV`+`MFENCE`, Power mappings with `lwsync`/`sync` — and the mapping is *sound*: every hardware behavior of compiled code must be source-allowed. Lahav et al. [2] showed both proposed Power schemes for C++11's SC atomics were unsound, because the source was simultaneously too strong (forbidding the schemes) and too weak (admitting the IRIW-acqsc litmus that trailing-sync compilation exhibits on real Power hardware). Compilation soundness is the empirical anchor of memory-model research.

##3 Methodology

We compare models along two orthogonal axes: **definitional style** and **verification technology**.

**Definitional style.** *Operational* semantics: an abstract machine (thread states, buffers, memory or message pools) with small-step rules; executions are traces, reasoning by step induction — the home of simulations and compiler-correctness proofs. *Axiomatic* semantics: a *candidate execution* — events with program order (po), reads-from (rf), modification order (mo), and happens-before (hb) — declared *consistent* when global axioms hold ("hb acyclic", "rf respects mo", "SC reads see the latest SC write in S"). Axiomatic models suit model checkers and litmus oracles (`herd7`), because consistency is a decidable graph property.

**Bridges.** The styles are complementary projections. Owens et al. [1] proved their store-buffer machine equivalent to an axiomatic total-store-order model; the promising semantics [3] coincides with declarative C11 on promise-free programs; and Taming RA [4] gives release–acquire an operational point-to-point semantics equivalent to its axiomatics.

**Verification technology.** We survey two families. *Model checkers* (notably GenMC [5][6]) enumerate a program's axiomatic executions with dynamic partial-order reduction — exploring each consistent execution graph exactly once — and report assertion violations, data races, and memory-safety errors under models like RC11 and IMM. *Program logics* internalize the model into proof rules: RSL's release/acquire assertions, Owicki–Gries adapted to RA with strengthened non-interference [7], GPS's ghost protocols, and iGPS mechanized in Iris [8], which scales separation logic to weak memory with machine-checked soundness, and RSL's value-indexed release/acquire assertions [10].

##4 Deep Dive

### 4.1 x86-TSO: the store-buffer machine and its axiomatic twin

The x86-TSO model of Owens, Sarkar, and Sewell [1] is the gold standard of hardware memory models, formalized in HOL4 with two provably equivalent presentations.

**Operationally**, each hardware thread owns a FIFO *store buffer*. A store appends `(address, value)` to the local buffer; a load first consults its own buffer (most recent buffered write to that address wins — *store forwarding*), falling back to shared memory only on a miss; a nondeterministic *drain* step moves the oldest buffered write into shared memory; `MFENCE` and locked instructions (`XCHG`, `LOCK`-prefixed RMWs) drain the buffer completely before proceeding. The SB litmus from §1 is explained: both stores sit in buffers while both loads read stale memory.

```python
# Sketch of the x86-TSO abstract machine (single step)
def step(thread, buffers, mem):
    instr = thread.next()
    if instr.is_store(x, v):
        buffers[thread].append((x, v))          # never blocks
    elif instr.is_load(x):
        buf = [v for (a, v) in buffers[thread] if a == x]
        thread.reg = buf[-1] if buf else mem[x] # forwarding, else memory
    elif instr.is_mfence():
        assert not buffers[thread]              # drain first
    # nondeterministic: any thread may drain its oldest write
    t = choose_thread()
    if buffers[t]:
        x, v = buffers[t].pop(0); mem[x] = v
```

**Axiomatically**, TSO is a *total store order*: a total order over all stores (drain order); loads read from the thread-local most recent po-previous store (forwarding) or from the latest store in the total order; program order holds except for store→load pairs. Forbidden: load buffering, IRIW (multicopy atomicity holds), and any store→store or load→load reordering — the face `memevents` and `cppmem` implement for litmus adjudication.

**Two definitions, one machine-checked equivalence**: the operational face serves programmers (drain-order intuition, DRF theorems), the axiomatic face serves tools (decidable consistency, exhaustive litmus evaluation). Practically, the model settled that restoring SC on x86 requires fencing store→load pairs — nothing more.

### 4.2 Release–acquire and the RC11 repair

The release–acquire (RA) fragment — all accesses release/acquire — is the sweet spot isolated in [4]. RA forbids C11's dubious behaviors (in particular OOTA), admits an intuitive **operational semantics of point-to-point communication** (threads exchange messages carrying *views*: per-location timestamps of observed writes), supports SC-restoring fences, and compiles to x86-TSO and Power with *exactly the same* schemes as C11's release/acquire. It satisfies monotonicity (adding synchronization never introduces behaviors) and a DRF theorem, which is why RSL, GPS, and OGRA all target RA.

RC11 [2] repairs the *full* model, including SC atomics. The diagnosis had four parts, each with a surgical fix:

1. **Release sequences too strong.** C11's baroque definition of release sequences forbade removing a `po;rf`-final segment — an optimization compilers wanted. RC11 *strengthens the definition* in a way that permits the optimization while preserving synchronization.
2. **SC reads axiom too weak/strong.** The original axiom both forbade valid Power compilations (correctness problem) and admitted the IRIW-acqsc behavior that trailing-sync Power compilation exhibits (soundness problem). RC11 replaces it with a **total order S over SC events** plus acyclicity constraints coupling S with hb and mo — the "SC-fix."
3. **SC fences too weak.** Fences were supposed to restore SC; the cumulative-order fix makes them actually do so.
4. **The hb characterization of synchronization** was simplified: RC11's *coherence* condition is equivalent to the conjunction of C11's coherence axioms, in a more concise axiomatization that drops the problematic `rf;hb` condition for non-atomics.

Formally, consistency requires acyclic hb, coherence (`rf⁻¹;mo;rf` patterns forbidden), and the SC order S with its strengthened constraints. The centerpiece is a **verified compilation theorem**: the standard RC11 mappings to x86-TSO and Power are sound [2].

> **Theorem: RC11 compilation soundness (Lahav et al. [2]).** The standard compilation schemes from RC11 to x86-TSO and to Power map every source-consistent behavior to target-consistent behaviors; i.e., no compiled program exhibits a behavior the source model forbids.

### 4.3 Operational versus axiomatic: the promise machinery

The deepest definitional tension is the *relaxed* fragment, where axiomatic consistency is too permissive (OOTA) and naive operational machines are too restrictive (they forbid load buffering, which compilers and Arm hardware require). The **promising semantics** [3] resolves it with a radical operational idea: threads may *promise* future writes — inserting a write into shared memory before executing the instruction that produces it — provided the promise can later be *certified*, i.e., the thread can execute from its current state to the promised write without contradiction, with all outstanding promises fulfilled at thread end.

```
Thread 0:  r1 = x_rlx; y_rlx = r1        Thread 1:  r2 = y_rlx; x_rlx = r2
```

Load buffering is allowed — each thread promises its write, reads the other's, then fulfills its own — but OOTA fabrications (`r1 == r2 == 42`) are forbidden: a promise of 42 can never be certified, since no execution step produces 42 from the initial state. The promise mechanism draws the line axiomatic models could not: *speculation about control and data flow is allowed; invention of values is not.*

Promising 2.0 [10] redesigned the certification machinery to support *global* optimizations — value-range analysis and register promotion, which the original PS forbade — while preserving thread-local optimizations, hardware mappings, and DRF theorems. The lesson for our methodology: operational semantics is not merely an alternative presentation but an *enabling technology* — the promise machine validates compiler transformations (by simulation) that no axiomatic predicate could justify, and its promise-free fragment provably coincides with C11's declarative model, bridging the styles.

### 4.4 Verification of relaxed-concurrency programs

**Model checking.** GenMC [5][6] is a stateless, model-parametric checker: it enumerates execution graphs rather than interleavings, and its TruSt algorithm implements optimal dynamic partial-order reduction — each consistent execution explored exactly once, in polynomial memory. Given a program and a model (RC11, IMM, LKMM), it incrementally builds graphs event by event, checking consistency and flagging assertion violations, data races, and memory-safety errors; the PLDI 2019 predecessor [6] extended the technique to *weakly consistent libraries* as first-class graph events.

**Program logics.** Where model checking is bounded, logics are unbounded. The lineage begins with **RSL** (Vafeiadis & Narayan [10]): assertions `R(ℓ, Q)` and `W(ℓ, Q)` grant permission to perform acquire loads and release stores on `ℓ`, with `Q` mapping values to the invariant transferred — the first separation logic for C11 release–acquire, used to verify MP and a spinlock. **GPS** added ghost protocols for ownership transfer; **OGRA** (Lahav & Vafeiadis [7]) showed classical Owicki–Gries is *unsound* for weak memory and repaired it with a strengthened non-interference condition plus ghost "view" variables, sound for RA with automation potential. **iGPS** (Kaiser et al. [8]) rebuilt GPS inside the Iris framework in Coq: subjective views, escrows, and protocols become Iris ghost state, yielding machine-checked soundness for RA reasoning at a scale paper proofs could not sustain. Ridge's rely/guarantee for TSO and iCAP-TSO round out the hardware side.

```tla
---- MODULE ReleaseAcquire ----
EXTENDS Naturals
VARIABLES mem, views  \* mem: Loc -> Val, views: Thread -> (Loc -> Nat timestamps)
Init == mem = [l \in Loc |-> 0] /\ views = [t \in Thread |-> [l \in Loc |-> 0]]
ReleaseWrite(t, l, v) ==
    /\ mem' = [mem EXCEPT ![l] = v]
    /\ views' = [views EXCEPT ![t] = [@ EXCEPT ![l] = @ + 1]]
AcquireRead(t, l) ==
    /\ views' = [views EXCEPT ![t][l] = Max(views[t][l], TimestampOf(mem[l]))]
    \* reader's view advances past the write it observes: synchronization
====
```

The TLA+ sketch above captures the *operational intuition* of [4]: synchronization is view advancement — an acquire that observes a release adopts the releaser's knowledge, and happens-before becomes reachability in the view lattice.

##5 Empirical Results / Formal Proofs

Three kinds of evidence anchor the theory. **Hardware litmus testing** — the `diy`/`litmus7`/`herd7` toolchain on real silicon — confirmed x86 conforms to x86-TSO (forbidden outcomes like LB and IRIW are never observed) and mapped the Power and Armv7/v8 envelopes, including the non-multicopy-atomic behaviors behind IMM. **Mechanized metatheory** includes x86-TSO's HOL4 operational/axiomatic equivalence [1], RC11's Coq compilation-correctness proofs [2], iGPS's Iris/Coq soundness [8], and KATER (POPL 2023), which *derives* consistency checkers from declarative model definitions. **Tool case studies**: GenMC has verified the absence of assertion violations and races in Treiber stacks, Michael–Scott queues, and epoch-based reclamation under RC11 [5]; the OGRA logic discharged message-passing and a lock-free stack automatically [7]; and the promising semantics validated the soundness of common LLVM transformations (load→load reordering, roach-motel reorderings) that the C11 axiomatics could not justify [3][10].

> **Theorem: Promise-free correspondence (Kang et al. [3]).** On programs without outstanding promises, the promising semantics coincides with the declarative C11 model: every promised execution has a matching consistent candidate execution and vice versa.

Quantitatively, the trajectory is one of shrinking gaps: each successive model — C11, RA, RC11, Promising 2.0 — forbids more unobservable behaviors while permitting more real optimizations, and each successive tool — cppmem's exhaustive enumeration, herd7's analytic adjudication, GenMC's optimal DPOR — explores the remaining space faster.

##6 Limitations

The edifice is incomplete, and the gaps are instructive.

*OOTA for relaxed atomics remains unsolved.* Promising 2.0 permits load buffering only when a compiler transformation justifies it — yet no current model admits all observed hardware behaviors, forbids all OOTA fabrications, and stays efficiently checkable. The "right" relaxed semantics is contested territory.

*No operational semantics matches full RC11.* The promising semantics covers a large fragment, and point-to-point communication covers RA [4], but the complete RC11 model — SC atomics, fences, non-atomics with their race detector — has no equivalent abstract machine. Compiler-correctness proofs for the full model therefore still pass through declarative simulations, which are harder to compose.

*Scope restrictions.* `memory_order_consume` was effectively deprecated (compilers promote it to acquire) because dependency tracking proved unimplementable; mixed-size accesses (overlapping writes of different widths) break the per-location mo abstraction and are handled only by specialized models; the Linux kernel memory model (LKMM) diverges from C++ in its treatment of address dependencies and control dependencies, so kernel code needs its own verification stack (GenMC's LKMM backend [5] is a start, not a finish); and persistency (crash consistency under NVRAM) adds a second dimension — the persists-before order — that PerSeVerE only begins to explore.

*Automation limits.* GenMC is stateless and optimal per execution, but the number of executions still explodes on programs with many independent rf choices; program logics remain expert tools — iGPS proofs are large Coq developments, and OGRA's automation covers only small litmus-style programs. Push-button verification of a full RCU implementation under RC11 is still beyond reach.

---

##7 Conclusion

Weak memory models trace an arc from hardware honesty to programmer usability. x86-TSO [1] showed a hardware contract can be rigorous and intuitive with two equivalent faces — a store-buffer machine for humans, a total-store-order axiomatics for tools. Release–acquire [4] showed a useful fragment can be tamed: point-to-point operationalization, DRF, monotonicity, zero-fence compilation. RC11 [2] repaired full C++11 without breaking compilation, re-axiomatizing SC atomics around a total order S. The promising semantics [3][10] showed operational creativity — promises with certification — can draw the OOTA line axiomatics alone could not. And the verification stack — GenMC's optimal exploration [5][6], RSL through iGPS [7][8][10] — proves relaxed concurrency need not be folklore: its programs can be model-checked and proved against mechanized models. The open frontier is the relaxed fragment's final semantics and push-button verification of real concurrent systems — where the operational and axiomatic views must again advance together.
