# Affine Loop-Nest Optimization in the Polyhedral Model: Parametric ILP Scheduling after Feautrier, Pluto's Tiling and Fusion Heuristics, isl Set Manipulation, and CLooG Code Generation

# Affine Loop-Nest Optimization in the Polyhedral Model: Parametric ILP Scheduling after Feautrier, Pluto's Tiling and Fusion Heuristics, isl Set Manipulation, and CLooG Code Generation

## Abstract

The polyhedral model represents loop nests as integer points in parametric polyhedra, exposing dependence structure to exact integer-linear reasoning and enabling provably semantics-preserving transformations — interchange, skewing, tiling, and fusion — that elude syntax-directed optimizers. This article develops the model end-to-end: from the *SCoP* (static control part) abstraction and exact dependence analysis via integer linear programming, through Feautrier's parametric scheduling with the affine Farkas lemma and multidimensional time, to Pluto's ILP-driven tiling and fusion heuristics for parallelism and locality, Polly's integration into the LLVM pipeline, and the isl library's modern representation of Presburger sets and schedule trees. Code generation via the CLooG algorithm — projecting scheduled polyhedra back to efficient imperative loops with minimal control overhead — closes the loop from analysis to executable. We give correctness arguments for the scheduling constraints, quantify tiling's asymptotic locality improvement, and discuss the model's boundary: quasi-affine extensions, parametric tiling, and the recent rise of equality-saturation approaches in modern compilers.

## 1. Introduction

Scientific and machine-learning workloads are dominated by *affine loop nests*: loop bounds and array subscripts that are affine functions of enclosing loop indices and symbolic constants [2]. Classical compilers treat these nests syntactically, applying *ad hoc* pattern-based transforms — loop interchange, blocking, unrolling — that rarely compose and never carry proof. The **polyhedral model** abandons syntax in favor of geometry: each dynamic statement instance becomes an integer point in a parametric polyhedron; each data dependence becomes an affine relation between such points. Once programs live in this geometric universe, transformation becomes *scheduling* — choosing, for every statement instance, a new logical execution time — and legality becomes a *theorem* about preserved dependence order rather than a heuristic about matched patterns [1][6].

> **Theorem (Schedule validity):** Let *D* be the union of all dependence relations of a static control part, and let *θ* be an affine schedule assigning each statement instance a multidimensional timestamp. If for every dependence edge *(x → y) ∈ D*, *θ(y) − θ(x) ≽ 1* lexicographically, then the transformed program preserves the original program's semantics.

The consequence is that loop optimizations — tiling for cache locality, wavefront skewing for parallelism, loop fusion for temporal locality — are *instances* of a single mathematical problem: find an affine schedule satisfying the validity constraints while minimizing an objective (latency, communication, distance). The remainder of this article constructs this problem precisely, solves it by the methods of Feautrier [1], Pluto [2], and modern LLVM infrastructure [3][4][5], and measures what it buys.

## 2. Background

### 2.1 Static Control Parts

A **static control part (SCoP)** is a maximal program region in which control flow and data access are *affine* [4]:

- Loop bounds are affine combinations of outer indices and *parameters* (symbolic constants fixed for the region, e.g., problem size *N*).
- Array subscripts are affine functions of the same quantities.
- Conditionals have affine predicates; the code contains no function calls with side effects.

For a statement *S* nested in loops with index vector **i**, the **iteration domain** is the set

> D_S = { **i** ∈ ℤ^d | A_S **i** + B_S **p** + c_S ≥ 0 }

where **p** is the parameter vector. Each element of D_S is a *statement instance* — the smallest unit the polyhedral model schedules.

### 2.2 Dependences as Affine Relations

Two instances conflict if they touch the same memory cell and at least one is a write. Exact dependence analysis computes, for each pair of statements *(R, S)*, a **dependence polyhedron** — the set of *(i_R, i_S)* pairs where the instances access the same location in conflicting ways. This is an integer linear programming problem solved by Fourier–Motzkin elimination or, in modern practice, by the isl library [3]. The **dependence distance** *δ = i_S − i_R* along each dependence edge is the raw material of all legality reasoning: a loop at depth *k* is parallelizable iff no dependence has a zero distance at level *k* before all outer levels are zero.

| Analysis concept | Geometric object | Computed by |
|---|---|---|
| Iteration domain | Parametric integer polyhedron | Fourier–Motzkin / isl |
| Read-after-write dependence | Affine relation *D ⊆ D_R × D_S* | Exact dataflow analysis |
| Validity of a transform | Lexicographic positivity constraints | Affine Farkas lemma |
| Optimal schedule | Lexicographically minimal piecewise-affine map | Parametric ILP (Pip) |

### 2.3 The Affine Farkas Lemma

The bridge from universal quantifiers ("for all iteration vectors, dependences are respected") to finite linear constraints is the **affine form of Farkas' lemma** [1]: an affine function *f*(**x**) = a·**x** + b is nonnegatIVE over a polyhedron *P* = {**x** | C**x** + d ≥ 0} iff *f* is a nonnegative affine combination of the constraints of *P*. This lets a scheduler express "schedule *θ* is nonnegatIVE over the dependence polyhedron" as a finite system of linear inequalities over the *unknown coefficients* of *θ* — the masterstroke that makes scheduling a linear program over schedule coefficients rather than over iterations.

## 3. Methodology

### 3.1 Scheduling Problem Formulation

Following Feautrier [1][7], we seek a schedule *θ_S*(**i**, **p**) = **X**_S·**i** + **Y**_S·**p** + ρ_S for each statement *S*. For every dependence edge *e* from instance *x ∈ D_R* to *y ∈ D_S*, validity demands

> **θ**_S(**y**) − **θ**_R(**x**) ≥ 1,   ∀ (**x**, **y**) ∈ *D_e*.

By the affine Farkas lemma, this infinite family of constraints becomes a finite LP over the entries of **X**_S, **Y**_S, ρ_S. A second objective then minimizes schedule *latency*: the lexicographically smallest feasible schedule maximizes parallelism. When no one-dimensional affine schedule exists, Feautrier's algorithm proceeds to **multidimensional time** — finding the maximal set of statements that *can* share a time dimension, then recursing on the remainder [7]. Each schedule dimension corresponds, after code generation, to a sequential loop level; dimensions carrying no dependence are parallel loops.

### 3.2 Pluto's Tiling and Fusion Heuristics

Pluto reframes the problem around **tiling**: rather than merely exposing parallelism, it seeks affine hyperplanes whose normal vectors *simultaneously* minimize communication and maximize locality [2][6]. For each dependence edge, Pluto introduces a *bounding function* on the dependence distance under the schedule:

> *φ_e(θ) = u_e·(θ(y) − θ(x)) ≥ 0*,

and solves an ILP that (a) finds as many *tilable* (permutable, dependence-free) hyperplanes as possible, (b) minimizes a weighted sum of dependence distances to improve locality, and (c) fuses loops aggressively at outer levels while distributing at inner levels to keep tiles atomic. The result is a schedule whose outer dimensions are coarse-grained parallel and whose inner permutable band is tiled into cache-sized blocks.

```python
# Conceptual sketch: Pluto-style objective over schedule hyperplanes
from itertools import product

def pluto_objective(dependence_edges, schedule_hyperplanes):
    # (a) maximize number of tilable hyperplanes
    tilable = sum(1 for h in schedule_hyperplanes
                  if all(e.satisfied_by(h) for e in dependence_edges))
    # (b) minimize weighted dependence distances (locality)
    locality_cost = sum(e.weight * e.distance(h) 
                        for e in dependence_edges for h in schedule_hyperplanes)
    # (c) fusion: penalize distributing statements to different bands
    return tilable - 0.01 * locality_cost
```

### 3.3 isl and Schedule Trees

The **isl** library [3] is the modern substrate: a thread-safe C library manipulating sets and relations of integer tuples bounded by affine constraints, with exact GMP arithmetic. Crucially, isl represents schedules as **schedule trees** — hierarchical structures where *band* nodes carry partial schedules, *sequence*/*set* nodes order statements, and *filter* nodes restrict domains. Transformations become tree rewrites: Pluto's algorithm, reimplemented on isl, computes a schedule tree whose bands directly encode the tilable/permutable structure [8]:

```haskell
-- Sketch of a schedule tree (isl-style), in Haskell notation
data ScheduleTree
  = DomainNode  Domain                 -- iteration domain filter
  | BandNode    [AffineMap] ScheduleTree  -- partial schedule: one band
  | SequenceNode [ScheduleTree]        -- ordered execution
  | SetNode     [ScheduleTree]        -- unordered (parallel) execution
  deriving Show

-- Tiling legality: a band is tilable iff it carries no dependence
isTilable :: [Dependence] -> [AffineMap] -> Bool
isTilable deps band =
  all (\d -> all (\m -> dot m (dist d) >= 0) band) deps
```

Polly [5] lifts this machinery into LLVM: it detects SCoPs in LLVM IR, builds the isl model, applies the isl scheduler (a Pluto-descendant), and regenerates optimized IR — making polyhedral optimization available to every LLVM frontend language.

## 4. Deep Dive

### 4.1 Parametric Integer Programming and the QUAST

Feautrier's scheduler needs more than a rational LP optimum: schedules must be *integral* and *parametric* in the symbolic constants. **Parametric integer programming (PIP)** [1] solves min{**c**·**x** | A**x** + B**p** + d ≥ 0, **x** ∈ ℤⁿ} as a function of **p**, returning a **QUAST** (quasi-affine selection tree): a decision tree whose leaves are affine expressions in **p**. This is what allows a compiler to emit *one* transformed program valid for all problem sizes *N*, with size-dependent cases (e.g., "if N < 32 use the scalar path") appearing as explicit branches in the QUAST.

### 4.2 Tiling: From Dependence Geometry to Cache Behavior

Consider the canonical double loop with a diagonal dependence:

```rust
// Jacobi-style stencil: dependence distance (1, -1)
for i in 1..n {
    for j in 1..n {
        a[i][j] = (a[i-1][j] + a[i][j-1]) / 2.0;
    }
}
```

The dependence vectors {(1,0), (0,1)} span a cone; skewing by *(i+j, j)* makes the outer loop carry all dependences and the inner loop parallel. Rectangular tiling then partitions the skewed space into *T×T* blocks. Asymptotically, for an *n×n* iteration space with working set exceeding cache capacity *C*, naive execution incurs Θ(n³) misses (each of *n* sweeps reloads the *n²* array), while *T×T* tiling with *T² = Θ(C)* reduces this to Θ(n³/(B√C)) misses for block size *B* — the classic cache-complexity improvement that Pluto's ILP objective targets directly [2][6].

> **Theorem (Tiling legality):** A rectangular tiling of a loop band with tile sizes *t₁…t_d* is semantics-preserving iff the band is *fully permutable*: every dependence distance vector, projected onto the band's dimensions, is lexicographically nonnegative.

### 4.3 Fusion, Distribution, and the Pluto Cost Model

Fusion merges distinct loop nests into one; distribution splits them. Pluto's key insight [2] is that the fusion decision should be driven by the same ILP as the schedule: statements whose dependences are *satisfied at outer levels* fuse freely (improving temporal locality), while statements linked by *fine-grained* dependences distribute (preserving tilability). The Pluto cost model therefore:

1. **Maximizes** the number of outer parallel hyperplanes (coarse-grained OpenMP parallelism).
2. **Minimizes** the parametric upper bound on inter-tile communication volume.
3. **Fuses** at outer levels, **distributes** at inner levels — the *"fuse outer, distribute inner"* heuristic validated across PolyBench [2].

Empirically on PolyBench, this yields geometric-mean speedups of **2–5×** over Intel ICC *-O3* on stencil and linear-algebra kernels, with the largest gains on codes where ICC's syntactic blocking fails to compose [2].

### 4.4 Code Generation: CLooG and the AST Problem

A schedule is not code. **CLooG** (Chunky Loop Generator) [4] solves the *code generation problem*: given a union of polyhedra in the transformed (schedule) space, emit imperative loop nests scanning exactly those integer points, with minimal control overhead. The algorithm recursively projects the polyhedron onto its outer dimensions, separating the projection into disjoint chambers and emitting one loop nest per chamber; *control overhead* (guards inside inner loops) is minimized by a simplification pass that removes redundant constraints. Measured on SPECfp2000 and PerfectClub SCoPs, CLooG-generated code is **4.05× smaller** than the naive Omega CodeGen output and **2.57× smaller** than LoopGen, at comparable generation time [4] — the quantitative reason every modern pipeline (Pluto, Polly, PPCG) routes through CLooG or its isl-based successor.

### 4.5 Polly: Polyhedral Optimization Inside LLVM

Polly [5] closes the practicality gap. Its pipeline:

1. **SCoP detection** on LLVM IR (canonicalized, scalar-evolution-analyzed regions).
2. **Model construction** in isl: domains, access relations, schedules.
3. **Scheduling** with the isl scheduler (Pluto-style objectives on schedule trees).
4. **AST generation** via isl's code generator, lowering back to LLVM IR with OpenMP annotations for parallel loops.

Because Polly operates at IR level, transformations are *language-agnostic* and *syntactically transparent*: the optimized IR remains ordinary LLVM IR that downstream vectorizers and register allocators consume unchanged [5].

## 5. Empirical Results and Proofs

### 5.1 Correctness Argument

We sketch the standard correctness proof for the affine scheduling pipeline [1][7]:

> **Lemma 1 (Farkas reduction):** The validity constraints *θ_S(y) − θ_R(x) ≥ 1* over all *(x,y) ∈ D_e* hold iff the finitely many Farkas-coefficient constraints on *θ*'s coefficients hold.
> **Lemma 2 (Lexicographic execution):** Executing statement instances in lexicographic order of their multidimensional timestamps respects every dependence edge, since each edge's endpoints differ by at least *1* at the first nonzero schedule dimension.
> **Theorem (End-to-end correctness):** If CLooG generates loop nests that scan each statement's domain in lexicographic schedule order, the generated program is semantically equivalent to the source SCoP.

The proof's force is that *legality is checked once, geometrically* — downstream code generation cannot introduce a dependence violation that the schedule forbids.

### 5.2 Measured Impact

| System | Benchmark suite | Reported result |
|---|---|---|
| Pluto [2] | PolyBench, NAS | 2–5× geomean over ICC -O3; near-linear OpenMP scaling on stencils |
| CLooG [4] | SPECfp2000, PerfectClub SCoPs | 4.05× smaller code than Omega CodeGen |
| Polly [5] | LLVM test suite, PolyBench | Consistent wins on unblocked linear algebra; transparent to downstream passes |
| isl scheduler [3][8] | PolyBench | Matches or exceeds Pluto on tilable codes; schedule-tree form enables GPU mapping (PPCG) |

The dominant cost is compile time: the ILP formulation grows with the number of dependence edges, and pathological SCoPs (deep nests, many statements) can push Pluto's scheduler into minutes — the price of exactness.

## 6. Limitations

- **The SCoP restriction is severe.** Real programs contain while loops, pointer-chasing, indirection arrays (*a[b[i]]*), and dynamic control flow. Extensions to *quasi-affine* forms (floordiv/modulo in subscripts, handled natively by isl [3][8]) widen the net, but irregular codes remain out of reach.
- **Parametric tiling is hard.** Fixed tile sizes chosen at compile time misfire when *N* varies; parametric tiling requires runtime tile-size selection and *nonlinear* control overhead that CLooG's chamber decomposition handles poorly.
- **The model is memory-model-blind.** The polyhedral model reasons about *values*, not about caches, NUMA, or prefetchers; Pluto's locality objective is a proxy (dependence distance), not a machine model. Auto-tuning frameworks (ATLAS-style empirical search over tile sizes) remain necessary [2].
- **Compile-time scalability.** Exact ILP scheduling is NP-hard in the worst case; production use (Polly in LLVM) therefore restricts SCoP size and falls back to syntactic transforms when the model is too expensive [5].
- **Emerging competition.** Equality-saturation and sketch-guided superoptimization now compete on the same loop-nest territory with weaker legality guarantees but broader applicability — an active research frontier.

## 7. Conclusion

The polyhedral model is the rare compiler technology that is simultaneously a *mathematical theory* and an *engineering artifact*. From Feautrier's parametric ILP [1] through Pluto's tiling ILP [2][6], isl's exact set library [3][8], CLooG's chamber-based code generation [4], and Polly's LLVM integration [5], the pipeline converts geometric truth — points, polyhedra, Farkas certificates — into machine code that is faster *by proof* rather than by pattern. Its boundary is sharply drawn: where control and access are affine, no syntactic optimizer competes; where they are not, the model is silent. The next decade's work — parametric tiling, machine-model-aware objectives, and fusion with learning-guided search — will determine how much of real software eventually falls inside the polyhedron.
