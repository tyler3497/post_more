# User-Space TCP Stacks for Microsecond Networking: mTCP Batch Processing, TAS Fast-Path Separation, and Demikernel Kernel-Bypass with DPDK

## Abstract

Kernel TCP stacks were designed for generality, not for microsecond-scale datacenter workloads: even state-of-the-art designs spend 70-80% of CPU cycles inside TCP processing, leaving little headroom for application logic. This thesis analyzes three architecturally distinct user-space TCP stacks that relocate protocol processing out of the kernel: **mTCP**, a highly scalable batch-oriented user-level TCP stack for multicore systems; **TAS**, which recasts TCP acceleration as an OS service by splitting a DPDK-driven fast-path data plane from a kernel slow-path control plane; and **Demikernel**, a Rust-based LibOS that unifies kernel-bypass I/O frameworks under a safe, run-to-completion asynchronous API. We formalize a latency decomposition model, compare the systems on throughput, tail latency, connection scalability, and porting cost, and prove batch-amortization bounds that explain why per-packet overheads collapse under batched processing. Empirical evidence from the primary papers shows mTCP improving applications by 33-320% over Linux TCP, while TAS and Demikernel each trade programmability against protection and generality. We close with limitations and a decision framework for choosing among them.

## 1 Introduction

The Transmission Control Protocol remains the dominant transport for datacenter and wide-area communication, yet the software substrate that implements it — the kernel TCP stack — has become the principal bottleneck for short-lived, high-fan-in workloads. Measurements reported in the mTCP work show Linux TCP transaction rates peaking at roughly *0.3 million transactions per second*, while raw packet I/O frameworks such as DPDK, netmap, and PF_RING scale to *tens of millions of packets per second* on the same hardware [1][2]. The two-order-of-magnitude gap between packet movement and TCP processing is the central anomaly this thesis explains: packet I/O is a solved mechanical problem, but the kernel's protocol path — system calls, interrupt handling, socket indirection, global connection-table locks, and per-packet timer and congestion-control bookkeeping — does not scale with core count or NIC bandwidth [6].

Three research systems attack this gap from orthogonal directions, and together they map the design space of user-space TCP:

1. **mTCP (NSDI '14)** [1][2] pursues *batch-oriented, per-core specialization*: a complete user-level TCP stack following RFC 793 with NewReno congestion control, organized around per-core threads, RSS-aligned flow dispatch, batched packet I/O, lock-free data structures, and an event-notification model (``mtcp_epoll``) that ports existing applications with fewer than 100 lines of code change [3].
2. **TAS (TCP Acceleration as an OS Service)** [4] pursues *fast-path/slow-path separation*: it replaces only the TCP *datapath* with dedicated user-space threads doing DPDK packet I/O and protocol processing, while connection setup, teardown, and policy remain in the kernel — delivering acceleration without abandoning OS services or socket semantics.
3. **Demikernel** [5] pursues *language-level, LibOS kernel bypass*: a Rust-based library operating system that augments kernel-bypass frameworks (DPDK, RDMA) with memory safety, lightweight coroutines, and a run-to-completion asynchronous I/O API, targeting *microsecond-scale* latency for latency-critical applications.

The thesis makes four contributions: (i) a unified latency/throughput decomposition model applicable to all three systems; (ii) a detailed architectural exposition of each design, grounded in the primary sources; (iii) analytic bounds — including a batch-amortization theorem — that quantify when user-space TCP wins; and (iv) an evidence-backed comparison with explicit limitations and a selection guide. The treatment is unapologetically technical: we assume fluency with TCP state machines, congestion control, DMA-based packet I/O, and multicore synchronization.

## 2 Background

### 2.1 Where kernel TCP time goes

A packet's journey through the Linux stack crosses four cost centers: **packet I/O** (interrupt or NAPI poll, SKB allocation, DMA unmap), **protocol processing** (header parsing, sequence validation, SACK scoring, congestion control, timer management), **socket/API** (system-call entry, copy to user buffer, wakeup), and **synchronization** (per-socket locks, the global ``inet_ehash`` table). Under high connection churn the synchronization center dominates: profiling of connection setup storms shows four CPUs spending over 70% of time in ``__inet_check_established``, ``_raw_spin_lock_bh``, and ``__inet_hash_connect`` [6]. The SO_REUSEPORT feature (Linux 3.9) alleviates listener contention but leaves the stack far from fully parallel.

Two structural facts compound the problem. First, CPU clock frequencies have stagnated near 4 GHz while NIC speeds marched from 10 GbE (2002) to multi-100 GbE (2020); the *cycle budget per byte* shrinks every generation [5]. Second, the kernel TCP implementation keeps growing — 5-25% of lines of code churn annually — so a clean-slate stack can be dramatically smaller: Seastar's entire TCP implementation is under 3,000 lines, VPP's TCP roughly 14,000 lines, while Linux's stack is an order of magnitude larger and entangled with decades of extensions, some without RFCs [6][5].

### 2.2 Kernel-bypass packet I/O

Kernel-bypass frameworks (DPDK, netmap, PF_RING, PacketShader I/O) eliminate interrupts and system calls on the data path through *poll-mode drivers*, *hugepage-backed descriptor rings*, and *zero-copy DMA*. Packets arrive in batches; the application polls rather than sleeps. This converts packet I/O from an interrupt-driven, copy-heavy pipeline into a tight polling loop whose per-packet cost is dominated by PCIe descriptor management — a cost that, crucially, is *amortizable* by batching.

The design spectrum for stacks atop such frameworks spans:

- **Full clean-slate stacks** (mTCP, Seastar, Demikernel): protocol reimplemented from scratch in user space, maximum optimization freedom, maximum engineering cost.
- **Ported stacks** (F-Stack on FreeBSD TCP, lwIP): mature protocol logic transplanted to user space, still paying copy and API overheads, and inheriting kernel-era locking.
- **Split datapaths** (TAS): keep control in the kernel, accelerate only the hot path.

### 2.3 Analytical framework

We decompose per-request latency as

$$L = L_{pio} + L_{proto} + L_{api} + L_{sched}$$

where $L_{pio}$ is packet I/O (DMA, descriptor handling), $L_{proto}$ protocol processing, $L_{api}$ the application interface (syscall/copy/wakeup), and $L_{sched}$ scheduling and synchronization delay. Kernel bypass attacks $L_{pio}$ and $L_{api}$ directly; batching attacks the fixed-cost components of $L_{pio}$; per-core specialization attacks $L_{sched}$; and lean protocol implementations attack $L_{proto}$. Throughput follows from Little's law applied to the bottleneck stage: $X_{max} = N_{core} / \bar{S}_{bottleneck}$ for the relevant parallelism width.

## 3 Methodology

This is a *comparative systems analysis* built on primary sources rather than new measurement. Our method has three parts:

1. **Source-grounded architecture reconstruction.** For mTCP we use the NSDI '14 paper, full PDF, and presentation slides [1][2][3]; for TAS the presentation and design materials [4]; for Demikernel the ASPLOS '21 paper as summarized in the recent comparative survey [5]; and for ecosystem context the Tempesta Technologies analysis of user-space TCP stacks and the mTCP project documentation [6][7].
2. **Analytic modeling.** We derive batch-amortization bounds and a fast-path/slow-path cost model, then instantiate them with published numbers (Linux ~0.3M txn/s baseline, mTCP's 33-320% application speedups [1]).
3. **Design-matrix comparison.** We score the three systems on packet-I/O substrate, concurrency model, language/safety, connection scalability, porting effort, and workload fit, and we stress-test each against its documented limitations.

Citations are inline and mapped to the References; quoted performance claims are attributed to their original evaluations, not re-measured here.

## 4 Deep Dive

### 4.1 mTCP: batch-oriented user-level TCP for multicore systems

mTCP's thesis is that *multicore scalability is a data-structure and batching problem*, not a protocol problem. Its architecture has five pillars [1][2][3]:

- **Per-core thread affinity with RSS-aligned dispatch.** mTCP spawns one TCP thread per core; the NIC's Receive-Side Scaling steers each flow's packets to the same core, so a connection's state is *never* touched by two threads. Synchronization cost $L_{sched}$ for established flows drops to zero by construction.
- **Batched packet I/O.** Both receive and transmit paths operate on bursts. A single poll retrieves up to dozens of packets; TCP processing runs over the whole batch; a single doorbell releases transmit descriptors. This amortizes PCIe and driver fixed costs across packets.
- **Lock-free, cache-friendly data structures.** Connection tables use per-core partitions; hugepages prevent TLB misses on hot tables.
- **Efficient TCP timer management.** Rather than per-connection timer wheels scanned globally, mTCP uses lightweight, batched timer handling aligned to the polling loop.
- **Event notification and a familiar API.** ``mtcp_epoll`` mirrors ``epoll()`` semantics with a readiness model, and ``ps_select()`` extends the PacketShader I/O engine — so Lighttpd ports with 65 changed lines, ApacheBench with 29, an SSL proxy with 43 [3]. The whole implementation is 11,473 lines of C, follows RFC 793, implements NewRingo... *NewReno* congestion control, and passes correctness and stress tests against the Linux stack.

The canonical mTCP event loop illustrates the batching philosophy:

```c
/* mTCP-style batched event loop (illustrative, after [1][3]) */
struct mtcp_context *mctx = mtcp_create_context(cpu_id);
mtcp_epoll_create(mctx, MAX_EVENTS);

for (;;) {
    /* One syscall-equivalent retrieves a BATCH of events */
    int nevents = mtcp_epoll_wait(mctx, events, MAX_EVENTS, -1);
    for (int i = 0; i < nevents; i++) {
        if (events[i].events & MTCP_EPOLLIN)
            handle_rx_ready(mctx, events[i].data.sockid);
        if (events[i].events & MTCP_EPOLLOUT)
            handle_tx_ready(mctx, events[i].data.sockid);
    }
    mtcp_process_timeouts(mctx);   /* batched timer handling */
}
```

and the receive path consumes packets in bursts:

```c
/* Batched receive: amortize descriptor and DMA costs */
#define BATCH_SZ 32
struct rte_mbuf *pkts[BATCH_SZ];

for (;;) {
    uint16_t n = dpdk_rx_burst(port, queue, pkts, BATCH_SZ);
    for (uint16_t i = 0; i < n; i++)
        tcp_input(mctx, pkts[i]);          /* per-packet protocol work */
    rte_pktmbuf_free_bulk(pkts, n);        /* one release, amortized */
}
```

> **Theorem (Batch amortization).** Let $c_d$ be the fixed per-doorbell/per-poll cost and $c_p$ the per-packet protocol cost. Processing packets in batches of size $B$ reduces amortized I/O overhead per packet to $c_d/B + c_p$. Hence $\lim_{B \to \infty}$ overhead $= c_p$, bounded below by protocol processing — batching eliminates *mechanical* overhead but never *algorithmic* overhead.

*Proof sketch.* Each poll/doorbell pair costs $c_d$ regardless of batch size; total cost per batch is $c_d + B c_p$; divide by $B$. The bound is tight when the NIC can sustain full bursts, which DPDK poll-mode drivers achieve under load. ∎

### 4.2 TAS: TCP acceleration as an OS service

TAS starts from a different premise: *most TCP complexity lives in the control plane, most CPU cycles in the data plane* — so split them [4]. In TAS:

- The **slow path** (connection setup/teardown, socket options, policy, congestion-control *parameters*) remains in the kernel, preserving the mature control logic, security policy enforcement, and the standard socket API that applications and operators rely on (iptables, tcpdump, and friends keep working on the control path).
- The **fast path** — per-packet send/receive, ACK processing, congestion-control *execution*, loss recovery, packet filtering — runs in dedicated user-space threads using DPDK for packet I/O. Application threads communicate with fast-path threads through shared-memory queues, so the hot path never enters the kernel.

This split resolves the classic kernel-bypass dilemma. *Unprotected* bypass lets applications emit arbitrary packets — fast, but congestion control and fairness policies evaporate. *Protected* bypass reintroduces kernel crossings to enforce policy — safe, but slow. TAS's insight is that policy enforcement is a *control-plane* concern occurring at connection granularity, while byte movement is a *data-plane* concern at packet granularity; enforcing policy once per connection and executing the datapath in user space gets both.

The cost model makes the trade-off precise. Let $f$ be the fraction of per-connection work on the fast path and $S$ its speedup versus the kernel. Effective speedup $\approx 1/((1-f) + f/S)$. For bulk and RPC-heavy datacenter traffic $f \to 0.95+$, so even modest $S$ yields large wins — while control operations (rare, complex, security-sensitive) pay kernel costs only when they occur. The price is *dedicated cores*: fast-path threads poll continuously, sacrificing a core per datapath pipeline — efficient only under sustained network-heavy load [4].

### 4.3 Demikernel: LibOS kernel-bypass with DPDK

Demikernel pushes the pendulum to the opposite extreme from TAS: instead of *splitting* the stack, it *rebuilds* it as a library operating system in a memory-safe language [5]:

- **LibOS architecture.** Demikernel links directly into the application as a library; there is no kernel on the data path at all. It augments kernel-bypass I/O frameworks (DPDK, and RDMA transports) with its own from-scratch TCP/IP implementation, like mTCP and TAS in protocol terms but unlike both in structure.
- **Rust for safety.** Because stack and application share an address space (necessary for zero-copy), memory safety cannot come from hardware protection domains. Rust's ownership model provides it instead — protecting the stack *from* the application and vice versa without page-table or context-switch overhead. This removes the protection tax that made earlier library OSes (e.g., Dune/IX-style protected domains) expensive [5].
- **Coroutines and run-to-completion.** Demikernel generates lightweight Rust coroutines instead of POSIX threads, and exposes a new asynchronous I/O API executed run-to-completion: no scheduler preemption on the hot path, no thread-context-switch cost, minimal cache pollution.
- **Target: microsecond latency.** The design goal is explicitly ultra-low latency for latency-sensitive datacenter applications — single-digit-microsecond-scale request processing where even a kernel crossing is prohibitive.

The documented caveat is scale of validation: Demikernel has been tested with only small numbers of concurrent connections — up to 16 by the original authors, 64 by others — and porting existing applications to its new async API is difficult [5]. It is a *latency* instrument, not (yet) a *throughput-at-scale* instrument.

### 4.4 Comparative design analysis

| Dimension | mTCP [1][2] | TAS [4] | Demikernel [5] |
|---|---|---|---|
| Packet I/O substrate | DPDK / netmap / PSIO | DPDK | DPDK, RDMA |
| Concurrency model | Per-core threads, RSS pinning | Dedicated fast-path threads + app threads | Rust coroutines, run-to-completion |
| Protocol source | Clean-slate C (RFC 793, NewReno) | Clean-slate datapath, kernel control | Clean-slate Rust TCP/IP |
| Protection model | Process isolation | Kernel retains control plane | Language-level (Rust ownership) |
| API / porting | ``mtcp_epoll``; <100 LoC ports [3] | Socket-compatible service | New async API; porting difficult |
| Validated connection scale | High (multicore, memcached/SSL proxy) | Datacenter scale | 16-64 connections |
| Primary optimization target | Throughput & txn/s on multicore | Datapath CPU efficiency as OS service | Microsecond tail latency |
| Dedicated cores required | Polling threads | Yes (fast-path polling) | Yes (polling) |

Three conclusions follow: the systems agree on DPDK-style polling but disagree on *where the protection boundary goes* (process, kernel/user split, or language); porting cost is inversely related to architectural ambition (65 lines for mTCP [3] versus a rewrite for Demikernel [5]); and the three ideas are *composable* — later industry systems (e.g., Meta's Luna userspace TCP at cloud scale [5]) recombine exactly these ingredients.

## 5 Empirical Results and Proofs

**mTCP: the headline numbers.** The NSDI '14 evaluation reports [1][2]:

| Metric | Linux kernel stack | mTCP | Delta |
|---|---|---|---|
| Short-connection txn/s (8 cores) | ~0.3M | >1M-class | 3-25x class |
| Application speedup (lighttpd, ab, SSL proxy) | baseline | — | +33% to +320% |
| Packet I/O ceiling (DPDK-class) | — | tens of Mpps | 2 orders of magnitude |
| Porting cost | — | 29-81 LoC | <100 lines [3] |

These numbers instantiate the latency decomposition of §2.3: $L_{api}$ and interrupt-driven $L_{pio}$ dominate the kernel baseline; mTCP deletes both, batching amortizes descriptor costs per the Theorem, and RSS pinning deletes $L_{sched}$ for flows. The residual $c_p$ — protocol work per packet — is where mTCP's lean 11 KLoC implementation and cache-friendly structures matter.

**TAS: fast-path economics.** TAS's results show the fast path cutting per-packet CPU substantially versus the kernel while preserving socket semantics; as a shared OS service, multiple applications amortize its dedicated polling cores, addressing the "sacrifices an entire core" criticism of naive dedicated-stack designs [4].

**Demikernel: latency at small scale.** Demikernel's evaluation targets microsecond-scale RPC latency with minimal jitter, enabled by run-to-completion coroutines (no preemption, no lock contention on the hot path) and Rust's zero-cost safety. The honest bound on these claims is the connection count: 16-64 validated connections [5] means Demikernel's *scalability* curve is unproven where mTCP's is the headline.

**A proof of the separation principle.** Consider per-packet work $w = w_{pol} + w_{mech}}$, policy work plus mechanical work. Kernel bypass moves $w_{mech}$ to user space at cost $w'_{mech} \ll w_{mech}$ (no syscalls/interrupts) but must also relocate $w_{pol}$ at cost $w'_{pol} \geq w_{pol}$ (reimplementation risk). TAS's claim is the inequality $w'_{pol} \approx 0$ *on the datapath* — policy stays in the kernel, executed once per connection — so total per-packet cost $\approx w'_{mech}$, achieving bypass performance with kernel policy. The inequality holds exactly when policy decisions are connection-granular, which is true for congestion-control parameters, firewall rules, and socket options, but *fails* for per-packet policies (e.g., per-packet filtering must be reimplemented in the fast path — which TAS does [4]).

## 6 Limitations

Each system pays for its strengths, and the literature is candid about the bills:

- **mTCP: fixed resource provisioning.** mTCP uses fixed memory pools: TCP send/receive buffer sizes are fixed at startup and do not grow dynamically, which can limit large long-lived connections; operators must size buffers for the workload [7]. It also inherits the maintenance burden of a clean-slate stack — every TCP extension the kernel gains must be reimplemented by hand.
- **Clean-slate completeness gaps.** User-space stacks routinely lag kernel TCP on extensions. The Tempesta analysis notes, for example, that mTCP has *zero* mentions of delayed ACK handling in its tree, and Seastar's TCP — under 3,000 lines — carries explicit TODOs for TIME_WAIT timers, URG handling, and retransmission-queue cleanup [6]. For general Internet-facing deployment, these gaps are disqualifying; for controlled datacenter fabrics, they are acceptable.
- **TAS: dedicated cores and deployment coupling.** Fast-path threads poll continuously, burning cores even at low load; the OS-service model requires kernel modifications and coordinated deployment, raising the adoption bar versus a pure library.
- **Demikernel: scale and porting.** Validated only to 16-64 concurrent connections [5], with a new async API that makes porting existing applications difficult — the classic LibOS adoption trap.
- **Ecosystem loss.** Kernel bypass forfeits the kernel's tooling: iptables, tc, LVS, tcpdump, and two decades of operational knowledge do not transfer to user-space datapaths [6]. TAS mitigates this by keeping the control plane in the kernel; mTCP and Demikernel do not.
- **A moving target.** The kernel stack is not standing still — 5-25% of its code changes yearly [5] — and newer kernel interfaces (notably ``io_uring``) have closed part of the syscall-cost gap that motivated bypass in the first place; the Tempesta analysis argues ``io_uring`` can beat some user-space stacks on small connection counts [6].

## 7 Conclusion

mTCP, TAS, and Demikernel are three answers to one question — *where should TCP live when microseconds matter* — and their answers compose a coherent design theory. **mTCP** proves that batching plus per-core specialization can take a complete, RFC-faithful TCP stack past a million transactions per second on commodity multicore hardware, with application ports measured in dozens of lines [1][2][3]. **TAS** proves that the protection-versus-performance dilemma of kernel bypass dissolves once policy (slow path, kernel) is separated from mechanism (fast path, DPDK user space), yielding TCP acceleration *as an OS service* rather than as an application burden [4]. **Demikernel** proves that language-level safety can replace hardware protection domains, enabling a LibOS whose coroutines and run-to-completion scheduling target single-digit-microsecond latency [5].

The decision framework for practitioners is correspondingly crisp:

1. *Throughput on multicore with minimal porting* → mTCP-style batch-oriented user stack; size the fixed buffer pools [7] and confine deployment to fabrics where missing TCP extensions are tolerable [6].
2. *Datacenter-wide TCP acceleration preserving OS tooling and socket semantics* → TAS-style fast-path/slow-path separation; budget dedicated polling cores.
3. *Microsecond tail latency for latency-critical RPCs at modest connection counts* → Demikernel-style Rust LibOS; accept the new async API and validate scale yourself.

Open directions include *composing* the three ideas (batched Rust fast paths as OS services), pushing bypass into SmartNICs and programmable pipelines, and re-examining the boundary as ``io_uring`` and XDP shrink the kernel's overhead from below. The deeper lesson endures: the kernel TCP stack's costs are not protocol costs but *systems* costs — syscalls, interrupts, locks, copies — and systems costs yield to systems redesign.
