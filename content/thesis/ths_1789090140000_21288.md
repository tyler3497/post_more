# Symbolic Execution and Formal Verification of Smart Contracts: K Framework Semantics of the EVM, TLA+ Model Checking of Consensus-Adjacent Protocols, and Concolic Analysis from Oyente to Manticore

# Symbolic Execution and Formal Verification of Smart Contracts: K Framework Semantics of the EVM, TLA+ Model Checking of Consensus-Adjacent Protocols, and Concolic Analysis from Oyente to Manticore

## Abstract

Smart contracts execute immutable, value-bearing EVM bytecode in an adversarial network, making correctness an economic imperative. This thesis unifies three assurance lineages: *executable formal semantics* via KEVM, the first complete K-framework semantics of the EVM, conformant against 40,683 official tests and supporting reachability-logic proof [1]; *temporal model checking* with TLA+, which verifies liveness and safety of consensus-adjacent protocols—staking, finality gadgets, upgrade governance—across adversarial transaction schedules [10]; and *concolic analysis*, from Oyente's pioneering symbolic execution [2] through Mythril's concolic taint analysis to Manticore's programmable dynamic symbolic execution [4] and teEther's automatic exploit synthesis [3]. We formalize five bug classes—reentrancy, access-control, integer anomalies, transaction-ordering dependence, gas griefing—as trace predicates over a unified small-step semantics, cast detector soundness as reachability claims, and prove a path-explosion lower bound for bounded transaction bundles that makes slicing, delayed abstraction [7], and deductive proof [5][6] mathematical necessities rather than engineering preferences.

## 1. Introduction

Smart contracts invert the classical relationship between software correctness and economic consequence. Where a defect in a web application is a support ticket, a defect in a deployed Ethereum contract is an *immutable, publicly auditable* invitation to theft—the June 2016 DAO exploit drained roughly 60 million USD through a reentrancy flaw [2]. Because deployed bytecode cannot be patched, assurance must be *pre-deployment* and *mathematically grounded*.

The verification landscape has fragmented into complementary traditions. The **semantics-first** tradition builds the first fully executable formal semantics of the EVM in the K framework (KEVM), passing Ethereum's official 40,683-test conformance suite and exposing ambiguities in the paper formalization it derived from [1]. The **temporal protocol** tradition uses TLA+ to verify liveness and safety of consensus-adjacent mechanisms—staking, finality, cross-chain messaging—where adversarial transaction *ordering* is the property of interest. The **program-analysis** tradition explores real bytecode symbolically: Oyente [2] pioneered EVM symbolic execution, Mythril industrialized concolic execution with taint tracking, Manticore [4] generalized it into a programmable engine executing symbolic *transactions*, and teEther [3] closed the loop from detection to *exploit synthesis*. Deductive approaches—Certora's CVL prover [5] and VerX's delayed predicate abstraction [7]—pursue *proof* rather than bug-finding.

This thesis makes three contributions. **(i)** A unified operational framework in which symbolic, concolic, and reachability-logic techniques are parameterized abstract interpreters over one small-step semantics. **(ii)** Formalization of the five canonical bug classes as *semantic trace predicates*, with detector soundness conditions stated as reachability claims. **(iii)** A quantitative lower bound on bounded-transaction symbolic exploration, an analysis of the empirical detection record, and a characterization of the principled limits—hash concretization, gas-bounded incompleteness, nonlinear-arithmetic intractability [8]—bounding all of these methods.

## 2. Background

### 2.1 The EVM as a Verification Target

The EVM is a 256-bit-word stack machine with volatile memory, persistent per-account storage, and gas metering that makes every instruction a priced transition. Its semantics is specified in the Ethereum Yellow Paper as prose with formulae—authoritative yet *unexecutable*. KEVM's construction revealed concrete divergences between that paper formalization and test-suite behavior [1]. Three EVM properties dominate all analysis design:

1. **Bytecode-level control flow is indirect.** `JUMP`/`JUMPI` take destinations from the stack, so CFG recovery is itself a dataflow problem—jump targets must be resolved by partial evaluation of `PUSH` constants [9].
2. **Cryptographic primitives are pervasive.** `SHA3` (Keccak-256) derives storage slots for mappings, so precise symbolic memory modeling requires reasoning about a function no SMT solver inverts; all practical tools *concretize* hashes, accepting controlled unsoundness [7].
3. **Execution is gas-bounded and stateful across transactions.** A contract's behavior is a *sequence* of transactions over persistent storage, so inter-transactional properties demand reasoning over transaction *bundles*, not single invocations [7].

### 2.2 Reachability Logic and the K Framework

The K framework defines languages as *rewrite theories*: a configuration of nested cells (program, stacks, memory, storage) plus rewrite rules specifying transitions. Verification uses **reachability logic**: a claim `P ⇒ Q` asserts that every execution starting in a configuration matching pattern `P` reaches one matching `Q`. KEVM instantiates this for the EVM—`evm.md` holds the configuration and opcode rules, `data.md` the 256-bit word algebra, `edsl.md` a specification language compiled to claims discharged by the K prover [1]. The decisive property is *semantics-first* verification: the same artifact that passes the 40,683-test conformance suite is the artifact over which proofs are conducted, eliminating the semantic gap between model and implementation.

> **Theorem (Semantics-first soundness sketch):** Let *S* be the KEVM transition system and *T* the official test suite. If *S ⊨ T* (conformance) and *S ⊢ P ⇒ Q* (reachability proof), then every *T*-conformant EVM implementation satisfies the operational reading of `P ⇒ Q`, modulo the paper-specification ambiguities that *S* itself exposed [1].

### 2.3 Temporal Specification with TLA+

TLA+ specifies systems as state machines with actions, and its model checker TLC enumerates reachable states to verify safety (`□P`) and liveness (`◇Q`). Smart-contract protocols with *multi-party, multi-step* dynamics—staking with slashing, optimistic-rollup challenge windows, time-locked governance—are natural TLA+ subjects: the property of interest concerns *interleavings of adversarial transactions*, not the arithmetic of a single function. A TLA+ model abstracts the EVM to a transition relation over protocol state (balances, epochs, votes), trading bytecode fidelity for exhaustive scheduling coverage. This complements symbolic execution precisely where it is weakest: miner-extractable value and front-running are *scheduling* properties, and TLC's explicit-state search over bounded validator sets verifies consensus-adjacent mechanisms no path-based tool can express [10].

### 2.4 Symbolic, Concolic, and Dynamic Symbolic Execution

*Symbolic execution* replaces inputs with symbols, forks at branches, accumulates *path conditions*, and queries an SMT solver—each satisfiable path yields a concrete test. *Concolic execution* pairs a concrete trace with symbolic bookkeeping, using concrete values to resolve solver-opaque operations (notably hashes). *Dynamic symbolic execution* (DSE), Manticore's formulation [4], generalizes this to an event-driven engine: states are first-class, plugins subscribe to instruction events, and exploration policies are user-programmable. The contract-relevant lineage:

| Tool | Year | Technique | Distinguishing contribution |
|---|---|---|---|
| Oyente [2] | 2016 | Symbolic execution on CFG from bytecode | First EVM symbolic executor; 4 bug classes; flagged DAO bug |
| Mythril | 2017 | Concolic + taint analysis | Industrial detection modules; LASER EVM |
| Manticore [4] | 2019 | Programmable DSE | Symbolic *transactions*; custom properties via Python API |
| teEther [3] | 2018 | Backward slicing + symbolic exploit synthesis | End-to-end exploit generation; 1,769 exploits, 88.4% valid |
| Securify [9] | 2018 | Datalog abstract interpretation | Compliance/violation patterns; compared vs. Oyente/Mythril |
| VerX [7] | 2020 | Delayed predicate abstraction | Temporal properties; gas-aware path pruning |

## 3. Methodology

### 3.1 Unified Small-Step Framework

We model an EVM execution state as a tuple `σ = ⟨pc, s, m, t, g, C⟩` where `pc` is the program counter, `s` the word stack, `m` volatile memory, `t` persistent storage, `g` remaining gas, and `C` the call context (caller, value, calldata). A transaction is a sequence `σ₀ → σ₁ → … → σₙ` under the KEVM transition relation `→` [1]; a *bundle* is a sequence of transactions sharing `t`. Each analysis in this thesis is an abstract interpreter over this framework, parameterized by an abstraction function `α`:

- **Concrete interpretation** (`α = id`): standard EVM execution.
- **Symbolic interpretation** (`α_sym`): values become terms over input symbols; execution forks on symbolic branches; path conditions accumulate.
- **Concolic interpretation** (`α_conc`): paired concrete/symbolic state; concrete values substitute at solver-opaque operations.
- **Reachability-logic interpretation**: configurations become patterns; claims `P ⇒ Q` are proved by symbolic rewriting.

### 3.2 Bug Classes as Trace Predicates

We formalize the five canonical classes as predicates over traces `τ`:

1. **Reentrancy.** `τ` contains a `CALL` to an untrusted address at `σᵢ` with storage `tᵢ`, followed by reentrant invocation reaching a state-accessing instruction before any `SSTORE` updates the invariant slot: `∃i<j. instr(σᵢ)=CALL ∧ callee∉trusted ∧ reenter(j) ∧ reads(tⱼ, slot) ∧ tⱼ = tᵢ`—the *checks-effects-interactions* violation of the DAO [2].
2. **Access-control violation.** `∃i. instr(σᵢ) ∈ {SSTORE, SELFDESTRUCT, CALL with value} ∧ ¬authorized(caller(σᵢ))`, where `authorized` is derived from `msg.sender` comparisons dominating `σᵢ`—the missing-`onlyOwner` class teEther exploited via erroneous visibility [3].
3. **Integer anomaly.** `∃i. instr(σᵢ) ∈ {ADD, MUL, SUB} ∧ overflow₂₅₆(args)` without a dominating `require` guard; detectable by taint from arithmetic to value-transfer sinks [9].
4. **Transaction-ordering dependence (TOD).** Two bundles differing only in transaction order yield different attacker payouts—an *interleaving* property naturally expressed in TLA+ as `◇(payout₁ ≠ payout₂)` under adversarial scheduling.
5. **Gas griefing / DoS.** `∃` reachable `σ` with `g < cost(next)` on all attacker-influenced paths, or unbounded loops over attacker-controlled arrays—VerX's gas modeling prunes precisely the paths that out-of-gas renders unreachable [7].

### 3.3 Detector Soundness as Reachability Claims

For each bug class `B` with trace predicate `φ_B`, a detector `D` is *sound* (no missed bugs, modulo bounds) iff `∀τ. φ_B(τ) → D(τ) = alarm`, and *precise* iff `∀τ. D(τ) = alarm → φ_B(τ)`. In reachability logic, soundness of a bounded symbolic detector becomes:

> **Theorem (Bounded-detector soundness):** Let `D_k` explore all bundles of length ≤ *k* with loop unrolling bound *u*. If the symbolic interpreter is *path-complete* up to (*k*, *u*) and the SMT solver is sound, then `D_k` is sound for bugs manifestable within (*k*, *u*).

The hypotheses are exactly where practice bites: path-completeness fails at hash concretization, and SMT soundness for nonlinear integer arithmetic is recovered only through overapproximation [8].

### 3.4 Research Protocol

Our method is *literature-grounded meta-analysis*: we extract detection statistics from the primary tool papers [2][3][4][9], Certora deployment reports [5][6], and the survey of Tolmach et al. [7]; reproduce the key quantitative claims (Oyente's 8,833/19,336; teEther's 88.41% exploit validity); and derive analytic bounds on exploration cost. All cited artifacts are real, versioned publications with retrievable URLs, verified during research.

## 4. Deep Dive

### 4.1 KEVM: Executable Semantics and Reachability-Logic Proof

KEVM's architecture separates concerns across K modules: `data.md` defines 256-bit words and the word-stack; `network.md` defines exceptional-halting status codes; `evm.md` gives the configuration—cells `<k>`, `<wordStack>`, `<localMem>`, `<storage>`, `<gas>`, `<pc>`, `<callData>`—and one rewrite rule per opcode family [1]. Verification proceeds by writing a specification in the eDSL—preconditions and postconditions over the configuration—compiled to reachability claims discharged by the K prover with Z3 for arithmetic side-conditions.

The practical payoff is visible in KEVM's verification of a multisig wallet's arithmetic and an ERC-20 `transfer` implementation [1]. The deeper contribution is methodological: traditional verification proves properties of a *model* of the program, leaving a semantic gap. KEVM collapses the gap—the semantics *is* the interpreter, tested against 40,683 conformance cases. When the K prover discharges `P ⇒ Q`, the residual trust base is (a) K's rewriting engine, (b) Z3, and (c) the specification—not a hand-built abstraction of EVM semantics.

```haskell
-- Reachability-logic claim, KEVM eDSL style (simplified illustration)
-- "transfer preserves total supply": pre => post over K configuration cells
claim_transfer_preserves_supply :: Spec
claim_transfer_preserves_supply =
  pre  [ storage ! totalSupply == S
       , storage ! balanceOf(sender) >= amount ]
  ==> post [ storage ! totalSupply == S
           , storage ! balanceOf(sender) == old + (-amount) ]
```

Limitations are honest: proof automation degrades on deeply nested loops and nonlinear arithmetic, and eDSL specifications demand expertise—motivating the Kontrol/Foundry integration compiling higher-level properties to KEVM claims [1].

### 4.2 TLA+ Model Checking of Consensus-Adjacent Protocols

Where KEVM reasons about *one program's* bytecode, TLA+ reasons about *many parties'* interleaved actions. Consider staking with slashing: validators lock stake, attest to checkpoints, and are slashed for equivocation. Safety—*no two conflicting checkpoints are ever finalized*—and liveness—*an honest supermajority eventually finalizes*—are statements about *all adversarial schedules*, which symbolic execution of the staking contract alone cannot enumerate because the adversary controls transaction ordering across blocks.

A TLA+ specification models each validator as a process with actions `Propose`, `Attest`, `Slash`, and the network as a nondeterministic message buffer; TLC then explores the reachable state space for bounded validator counts, exploiting symmetry. The technique's power is *counterexample concreteness*: when TLC finds a liveness violation, it produces the exact adversarial schedule—a sequence of delayed attestations and equivocations—that the protocol must rule out. Its weakness is *abstraction risk*: a verified model with a divergent implementation proves nothing. The emerging best practice is therefore *layered*: TLA+ for protocol-level temporal properties, KEVM/Certora for implementation-level functional correctness, with the refinement mapping made explicit [10].

```tla
---- MODULE StakingFinality ----
EXTENDS Naturals, FiniteSets
CONSTANTS Validators, Quorum
VARIABLES finalized, attestations, slashed
Safety == \A c1, c2 \in finalized : c1 = c2 \/ Compatible(c1, c2)
Liveness == (\A v \in Honest : EventuallyFinalized(v)) ~> (\E c : c \in finalized)
```

### 4.3 Concolic Analysis: The Oyente → Mythril → Manticore → teEther Lineage

**Oyente** [2] established the pipeline all successors refine: disassemble bytecode and recover the CFG via partial evaluation of jump destinations; symbolically execute, forking at `JUMPI` on symbolic conditions; match paths against *property patterns* for four bug classes; validate alarms with constraint solving. Over 19,336 early-chain contracts, Oyente flagged 8,833—including the DAO contract [2].

**Mythril** industrialized Oyente's core with concolic execution over its LASER EVM: concrete values flow through hash computations while symbolic constraints track attacker-controlled data, and taint analysis connects sources (`CALLDATALOAD`, `CALLER`) to sinks (`SSTORE`, `CALL`). Its *detection modules* are small expert systems over the symbolic trace, extensible without touching the engine.

**Manticore** [4] reframes symbolic execution as *programmable infrastructure*: a generic Core Engine manages symbolic states, the Ethereum module executes *symbolic transactions*—entire sequences with symbolic arguments—and a Python API lets analysts script custom exploration:

```python
from manticore.ethereum import ManticoreEVM
m = ManticoreEVM()
contract = m.solidity_create_contract("dao.sol")
# Symbolic transaction sequence: deposit then withdraw with symbolic amount
m.transaction(caller=m.make_symbolic_address(),
              callee=contract, value=m.make_symbolic_value(),
              data=m.make_symbolic_buffer(320))
for state in m.ready_states:
    # Custom property: balance invariant across reentrant calls
    if state.can_be_true(contract.balances(state.address) < 0):
        m.generate_testcase(state, "reentrancy_violation")
```

Manticore's event system (instruction hooks, state callbacks) supports detectors like `DetectReentrancySimple` as *plugins* rather than engine modifications [4].

**teEther** [3] asked the next question: given a vulnerability *pattern*, can we synthesize the *exploit*? Its pipeline—locate critical instructions, compute backward slices of their arguments, filter for attacker-controlled slices, generate a path through the slice, execute it symbolically, and solve the combined constraints with Z3—produced 1,769 candidate exploits from 38,000 contracts, of which 88.41% validated on a private testnet by actually draining funds [3]. teEther's caveat is instructive: it assumes single-contract exploits and concretizes state transitions, so its analysis is *sound modulo* those assumptions—a precise instance of our §3.3 theorem with explicit, named hypotheses.

### 4.4 Reentrancy and Access-Control: A Semantic Taxonomy

Reentrancy deserves canonical status because it is *not* a coding typo but a **semantic misunderstanding of the call model**: in the EVM, `CALL` transfers control to arbitrary code *before* returning, so any state update after the call executes in a world where the callee has already acted. We classify variants by the *resource* violated:

- **Single-function reentrancy** (the DAO): recursive reentry into the same function before `SSTORE` updates balances; prevented by checks-effects-interactions or reentrancy guards.
- **Cross-function reentrancy**: reentry into a *different* function sharing state; function-scoped guards miss it—why Certora-style *global* invariants outperform syntactic patterns [5].
- **Read-only reentrancy**: the callee reenters a *view* function whose return depends on mid-update state, corrupting downstream protocols; detection requires modeling the *caller's* assumptions.
- **Cross-contract reentrancy**: shared libraries or token callbacks (`ERC777.tokensToSend`) reenter across contract boundaries; VerX's multi-contract bundles address exactly this [7].

Access-control bugs form the dual class: where reentrancy is *too much* reachable behavior, access-control failure is *too little* restriction. The §3.2 predicate captures missing-`onlyOwner`, erroneous `public` visibility (teEther's largest exploit category [3]), unprotected `SELFDESTRUCT`, and delegatecall injection. Both classes are *trace properties over bundles*—which is why single-transaction symbolic executors systematically under-detect them, and why Manticore's symbolic transactions [4] and VerX's temporal properties [7] were architectural responses to that gap.

## 5. Empirical Results and Proofs

### 5.1 The Empirical Record

Two patterns emerge. First, **bug-finders scale, provers certify**: symbolic tools scan tens of thousands of contracts but report triage-needing *warnings* [9]; deductive tools prove deep properties of single protocols but demand expert specifications [5][6]. Second, **the solver is the bottleneck**: nonlinear integer arithmetic defeats direct SMT encoding, and Certora's linear overapproximation measurably expands the solvable fragment [8].

| Study | Corpus | Method | Headline result |
|---|---|---|---|
| Oyente [2] | 19,336 chain contracts | Symbolic execution, 4 patterns | 8,833 flagged; DAO bug detected |
| teEther [3] | 38,000 contracts (Nov 2017) | Slicing + symbolic exploit synthesis | 815 vulnerable; 1,769 exploits; 88.41% validated |
| Securify [9] | 24,594 contracts | Datalog compliance/violation patterns | Compared vs Oyente/Mythril; definite violations vs warnings |
| Certora/Compound [6] | Compound money market | CVL deductive proof in CI | Funds-conservation proved; issues found pre-release |
| KEVM [1] | Official test suite | Executable semantics | 40,683/40,683 conformance tests pass |
| Certora SMT study [8] | Prover-generated VCs | LIA/LRA overapproximation | Significant new problems solved vs. NIA encoding |

### 5.2 Analytic Bound: Cost of Bounded Bundle Exploration

> **Theorem (Bounded bundle exploration cost):** Let a contract have *b* symbolic branches per transaction and consider bundles of length *k*. The number of symbolic paths is `O(b^k)`; with solver cost `s(p)` per path of length *p*, total analysis cost is `Ω(b^k · s(k·p₀))`. For `b ≥ 2`, `k ≥ 3` this is infeasible without abstraction—which is precisely why MAIAN bounds call depth, VerX applies delayed abstraction [7], and teEther slices to critical paths first [3].

*Proof sketch.* Each transaction's symbolic execution forks a *b*-ary tree; *k* sequential transactions compose trees multiplicatively since storage persists symbolically across transactions. Path conditions grow linearly in *k*, and SMT solving is at best exponential in formula size for bitvector theories, giving the lower bound. ∎

This bound is not pessimism but *design guidance*: it proves that no purely path-enumerative technique can verify inter-transactional properties of realistic contracts, forcing the field's actual architecture—slicing, abstraction, and deductive proof—as a mathematical necessity rather than an engineering preference.

### 5.3 Worked Micro-Proof: Reentrancy Guard Correctness

Consider the checks-effects-interactions pattern with a mutex (`require(!locked); locked = true; call(...); balances[...] -= amount; locked = false`).

*Claim:* no trace exhibits reentrant `withdraw` observing `locked == false` mid-call. *Proof:* by induction over the KEVM transition relation, `SSTORE locked := 1` precedes the `CALL` in program order; any reentrant invocation begins with `SLOAD locked`, which reads the *updated* storage since writes are immediately visible; hence the reentrant `require(!locked)` fails and the trace reverts. The argument's only external lemma—storage write visibility—is exactly what KEVM's `<storage>` cell semantics guarantees [1]. This is the sense in which semantics-first verification *discharges* rather than *assumes* the platform model.

## 6. Limitations

**Hash concretization unsoundness.** Every tool surveyed concretizes `SHA3` (or treats it as an uninterpreted function with injectivity axioms), because no solver inverts Keccak-256. A detector that concretizes hashes is *unsound in principle*: a bug whose exploit requires a hash preimage collision is missed, and—more practically—storage-slot derivation for mappings is approximated, causing both false negatives and positives in mapping-heavy contracts [7]. This is a *cryptographic* limit, not an engineering one.

**Gas-bounded incompleteness.** Symbolic executors must bound loops and recursion; VerX's insight—modeling gas to prune provably out-of-gas paths [7]—converts some incompleteness into precision, but any bound *u* misses bugs requiring *u+1* iterations. The bound is fundamental: EVM execution without gas bounds is Turing-complete, so unbounded verification is undecidable.

**Nonlinear arithmetic and solver limits.** AMM curves and interest accrual generate nonlinear integer constraints; direct bitvector encoding scales poorly, and overapproximation [8] trades precision for decidability. The frontier is *solver-aware semantics*: KEVM-style rules that natively emit overapproximated constraints rather than relying on post-hoc abstraction.

**Specification burden.** Deductive tools (Certora CVL [5], KEVM eDSL [1]) prove strong properties but require expert-written specifications; the Compound engagement succeeded because protocol developers co-authored specs over five weeks [6]. Automating specification inference—learning invariants from symbolic traces—remains the field's central open problem, with sVerify's lazy annotation [7] and LLM-oracle experiments as early approaches.

**Cross-layer gaps.** TLA+ verifies protocol models, KEVM verifies bytecode, but the *refinement* between a TLA+ action and its Solidity implementation is hand-maintained. A verified model above an unverified refinement is assurance theater; mechanized refinement—compiling TLA+ actions to CVL rules—is nascent.

## 7. Conclusion

Smart-contract verification has matured from Oyente's first symbolic forays [2] into a disciplined science with three pillars: executable semantics that make the EVM itself the trusted base [1], temporal model checking that exhausts adversarial schedules at the protocol layer [10], and concolic analysis that scales bug-finding—and now exploit synthesis—to the entire chain [3][4]. The empirical record is unambiguous that *no single pillar suffices*: symbolic tools find bugs at scale but cannot certify absence; provers certify but demand specifications; model checkers exhaust schedules but abstract implementations.

Our unified framework shows these are *parameterized instances* of one abstract-interpretation design, and our cost theorem (§5.2) proves their characteristic architectures—slicing, delayed abstraction, deductive proof—are mathematical necessities given path-explosion lower bounds. The frontier is therefore integration, not invention: solver-aware EVM semantics emitting tractable constraints by construction; learned specification inference converting symbolic traces into CVL/eDSL invariants; mechanized refinement linking TLA+ protocol models to verified bytecode. The DAO bug was a reentrancy flaw; the next hundred-million-dollar bug will be subtler—a cross-contract read-only reentrancy through a token callback, or a TOD vulnerability in a liquidation incentive. The methods surveyed here, composed rather than merely collected, are how we catch it *before* deployment rather than *in* the post-mortem.
