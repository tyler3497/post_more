# The RISC-V Vector Extension for Machine Learning: RVV 1.0 LMUL and SEW Configuration, Segmented Memory Operations, and Autovectorization in LLVM for GEMM Kernels

## Abstract

The RISC-V Vector Extension (RVV) 1.0, ratified by RISC-V International, is the first widely adopted *length-agnostic* vector ISA: a single binary executes correctly on implementations whose hardware vector length (*VLEN*) ranges from 128 to over 2048 bits without recompilation. For machine learning, where general matrix multiply (GEMM) kernels dominate compute, RVV's distinguishing features — dynamic configuration of element width (*SEW*) and register grouping (*LMUL*) via `vsetvli`, unit-stride/strided/indexed memory operations, *segmented* loads and stores for structure deinterleaving, and explicit tail/mask agnosticism policies — create a programming model with no direct analogue in fixed-width SIMD. This thesis develops a rigorous account of RVV 1.0's configuration machinery, formalizes the economics of *LMUL* register grouping for GEMM microkernels, analyzes segmented memory operations as hardware-supported array-of-structures to structure-of-arrays transposition, and evaluates LLVM's autovectorization pipeline — LoopVectorizer, VPlan, and the RISC-V backend — for production ML code. Synthesizing the specification, recent empirical studies of compiler-generated RVV code on RVV 1.0 silicon, and commercial vector core designs from SiFive and Andes, we derive concrete GEMM kernel design rules: optimal *LMUL*=4–8 with *SEW*=16 on 512-bit implementations, fused multiply-add chaining across register groups, and tail-agnostic strip mining to eliminate remainder-loop overhead. We close with an honest accounting of autovectorizer gaps — reductions, mixed precision, and gather/scatter — that still require intrinsic-level intervention for peak ML throughput.

## 1 Introduction

Machine learning workloads are vector workloads. The *general matrix multiply* (GEMM) at the heart of dense layers, attention projections, and convolutional lowering typically accounts for 80–95% of floating-point operations in inference and training [8]. For two decades, the industry response has been fixed-width SIMD: Intel AVX-512 (512-bit), ARM NEON (128-bit), and SVE (scalable but masked). Fixed-width SIMD couples the software's vectorization strategy to the hardware's vector width at compile time, forcing *remainder loops* for sizes not divisible by the lane count and recompilation for each new width.

The RISC-V Vector Extension (RVV) 1.0 breaks this coupling. Ratified in late 2021 after an extended public review, RVV 1.0 defines a *vector-length-agnostic* programming model [1]: software configures the *application vector length* `vl` at runtime with the `vsetvli` instruction, and the identical instruction stream executes on any conforming implementation. This single design decision reverberates through the entire ML software stack:

- **Portability of kernels.** A GEMM microkernel written once runs on the 128-bit SpacemiT K1, the 256-bit implementations, and the 512/1024-bit SiFive Intelligence X280 and Andes AX45MPV vector cores [4][5][6].
- **Elimination of tail loops.** Because `vsetvli` returns the *granted* vector length (the minimum of the requested application length and the hardware maximum), strip-mined loops handle remainders *in the main loop*, not in scalar epilogues [2].
- **Dynamic precision control.** *SEW* (selected element width) can change at instruction granularity, enabling mixed-precision kernels — e.g., FP16 multiply with FP32 accumulate — without separate code paths.

Yet these advantages come with genuine complexity. The configuration space (`vsetvli` operands, `vtype` encoding, `vta`/`vma` policies), the register-grouping economics of *LMUL*, and the subtle semantics of segmented and masked operations demand careful analysis. Compiler autovectorization, which must bridge the gap between scalar source code and this configuration machinery, is a research frontier: recent studies show measurable gaps between hand-written RVV assembly and compiler-generated code on real RVV 1.0 silicon [2].

This thesis makes four contributions. **First**, we present a complete, specification-grounded account of RVV 1.0's configuration model (Section 4.1). **Second**, we formalize *LMUL* register grouping as a resource-allocation problem for GEMM and derive optimal groupings (Section 4.2). **Third**, we analyze segmented memory operations as hardware-supported AoS→SoA transposition with direct ML applications (Section 4.3). **Fourth**, we dissect LLVM's RVV autovectorization pipeline and quantify where it falls short of intrinsic-level kernels for GEMM (Sections 4.5, 5). Throughout, we ground claims in the ratified specification and verifiable primary sources [1][2][3][4][5][6][7][8].

## 2 Background

### 2.1 Vector architectures before RVV

Vector computing predates modern ML by decades. Seymour Cray's Cray-1 (1976) introduced vector registers with a *vector length register* — the direct ancestor of RVV's `vl`. The academic lineage runs through Asanović's doctoral work on vector microprocessors [8], which established that decoupled vector execution tolerates memory latency better than scalar or fixed-SIMD designs, a property ML's streaming access patterns exploit.

### 2.2 RVV 1.0 at a glance

RVV 1.0 adds 32 architectural vector registers `v0`–`v31`, each `VLEN` bits wide, plus two CSRs: `vtype` (configuration) and `vl` (active length) [1]. The extension is *polymorphic*: most instructions do not encode element width; width comes from the dynamic `vtype` state. Implementations choose `VLEN` (≥128 bits for the full V extension; the Zve* sub-extensions permit 32), `ELEN` (maximum element width, ≥ `SEW` max), and the datapath width `DLEN`.

> **Theorem (Length-agnostic portability):** Any RVV 1.0 program that (a) sets `vl` exclusively via `vsetvli`/`vsetivli`/`vsetvl`, (b) never assumes a value of `VLEN` beyond the `Zvl*b` minimum it targets, and (c) respects the `EMUL·NFIELDS ≤ 8` constraint on segmented operations, executes with identical *functional* results on all conforming implementations. *Proof sketch:* the specification defines all data-dependent behavior (element counts, tail/mask policy, register grouping) as functions of `vl`, `SEW`, and `LMUL`, which are themselves functions of implementation parameters only through the granted `vl`; no instruction's semantics reference `VLEN` directly [1].

The commercial landscape has matured rapidly since ratification: the SpacemiT Keystone K1 shipped 256-bit RVV 1.0 (one of the first, enabling OpenCV's `riscv-rvv` HAL backend [4]); SiFive's Intelligence X280 offers 512-bit `VLEN` with register ganging to effective 4096-bit vectors and bfloat16 support for AI [6]; Andes' AX45MPV scales to 1024-bit with dual-issue vector execution [5].

## 3 Methodology

This thesis is a *synthesis and analysis* work. We combine:

1. **Specification analysis.** Primary reading of the ratified RVV 1.0 specification (the standalone vector extension document and its incorporation into the RISC-V ISA manual) [1], with exact instruction semantics, encoding constraints, and configuration rules.
2. **Compiler literature.** The LLVM project's RVV development record, including the RVV dialect RFC and the intrinsic specification exposed via `<riscv_vector.h>` [7], plus the OpenCV project's production RVV 1.0 backend experience [4].
3. **Empirical studies.** "Closer in the Gap" (2026), which compares hand-written RVV 1.0 assembly microbenchmarks against GCC 15 and Clang 21 autovectorized code on two RVV 1.0 testbeds [2]; "SEAM-V" (2026), a hybrid-decoupled vector microarchitecture study with GEMM among its kernels [3].
4. **Analytical modeling.** We construct a first-order performance model of an RVV GEMM microkernel (Section 5) parameterized by `VLEN`, `SEW`, `LMUL`, and memory bandwidth, deriving optimal configurations and comparing against published measurements.

## 4 Deep Dive

### 4.1 The configuration model: `vtype`, `vl`, and `vsetvli`

| Field | Bits | Meaning |
|---|---|---|
| `vsew[2:0]` | 2:0 | Selected element width: 8, 16, 32, 64, 128, 1024 (encodings 0–2, 5, 7 valid in 1.0) |
| `vlmul[2:0]` | 4:2 | *LMUL*: 1/8, 1/4, 1/2, 1, 2, 4, 8 |
| `vta`, `vma` | 7:6 | Tail-agnostic / mask-agnostic policy bits |

$$\mathrm{VLMAX} = \frac{\mathrm{VLEN} \times \mathrm{LMUL}}{\mathrm{SEW}}$$

is the maximum elements per instruction for the current configuration [1]. The canonical strip-mined loop is therefore:

```riscv-asm
loop:
    vsetvli t0, a0, e32, m4, ta, ma   # t0 = min(a0, VLMAX); SEW=32, LMUL=4
    vle32.v v4, (a1)                  # load t0 elements
    # ... compute on v4 ...
    vse32.v v4, (a2)                  # store t0 elements
    sub a0, a0, t0                    # remaining -= granted
    add a1, a1, t0, ...               # advance pointers (scaled)
    bnez a0, loop
```

Three properties make this loop remarkable. **First**, it is *portable*: on a 128-bit machine with `LMUL=4`, `VLMAX = 128·4/32 = 16`; on a 1024-bit machine, `VLMAX = 128` — the same binary, different strip sizes. **Second**, there is *no remainder loop*: the final iteration naturally receives a short `vl`. **Third**, the mandatory `ta`/`ma` (tail-agnostic, mask-agnostic) flags in the 1.0 assembly syntax license implementations to skip writing tail and masked-off elements, removing false dependencies and enabling register renaming to treat those elements as don't-cares [1][2]. The undisturbed variants (`tu`/`mu`) preserve elements but cost hardware complexity; performance-sensitive ML code should default to `ta, ma` wherever semantics permit.

The `vsetvli` instruction is cheap but not free: it serializes on the `vtype`/`vl` state. A central finding of recent empirical work is that *redundant* `vsetvli` instructions — emitted when the compiler cannot prove configuration invariance across loop nests — measurably degrade autovectorized GEMM performance [2]. Kernel authors hoist `vsetvli` out of inner loops by fixing `SEW`/`LMUL` for the whole kernel and strip-mining only on `vl`.

### 4.2 LMUL register grouping: the economics of vector registers for GEMM

*LMUL* (length multiplier) groups `LMUL` physical vector registers into one logical register group, multiplying `VLMAX` by `LMUL` at the cost of consuming `LMUL` architectural registers per operand. With 32 vector registers and `LMUL=8`, only 4 independent groups exist — a severe constraint that shapes GEMM microkernel design.

- `SEW=32`, `LMUL=8`: `VLMAX = 512·8/32 = 128` elements per group. An $8 \times 128$ tile of C occupies 8 register groups = all 32 registers. No registers remain for A/B operands — *infeasible without spilling*.
- `SEW=32`, `LMUL=4`: `VLMAX = 64`. A $12 \times 64$ tile needs 12 groups (48 registers) — infeasible; $6 \times 64$ needs 24 registers, leaving 8 (two groups of 4) for A/B streaming — *feasible and typical*.
- `SEW=16` (FP16/BF16), `LMUL=8`: `VLMAX = 256`. An $8 \times 256$ tile in 16-bit elements occupies 8 groups; A/B operands stream in additional groups — attractive for inference, and precisely why SiFive's X280 emphasizes BF16 with 4096-bit effective vectors [6].

The general optimization is:

> **Design rule (LMUL selection):** Choose the largest `LMUL` such that (i) the C tile plus streaming operands fit in 32 registers, (ii) `EMUL·NFIELDS ≤ 8` holds for any segmented access, and (iii) the inner-loop instruction count hides the FMA latency. In practice: `LMUL=4` for FP32, `LMUL=8` for FP16/BF16 on `VLEN ≥ 512`; `LMUL=8` FP32 is viable only with small $M_r$ and aggressive software pipelining.

FMA chaining interacts with `LMUL`: `vfmacc.vv` has a true dependency on its accumulator operand, so back-to-back `vfmacc` instructions targeting the *same* register group stall for the FMA latency (typically 4–6 cycles). With a $6 \times 64$ tile, six independent accumulators rotate, providing enough independent work to hide latency — the same register-blocking argument as in GotoBLAS, but with the block dimensions now *functions of LMUL and VLEN* rather than compile-time constants [3].

### 4.3 Segmented memory operations: hardware AoS→SoA transposition

Among RVV's most distinctive features are the *segmented* (formerly "strided-segment") load/store instructions `vlseg<NFIELDS>e<EEW>.v` / `vsseg<NFIELDS>e<EEW>.v`, with `NFIELDS` from 2 to 8. A single `vlseg8e32.v` loads eight interleaved 32-bit fields from memory into eight consecutive vector register groups — deinterleaving, in hardware, what would otherwise require a shuffle network in software [1].

```c
// Intrinsics: deinterleave RGB with one segmented load
#include <riscv_vector.h>
size_t vl = __riscv_vsetvli(n, __riscv_e8, __riscv_m1);
vuint8m1x3_t rgb = __riscv_vlseg3e8_v_u8m1x3(ptr, vl);
vuint8m1_t r = __riscv_vget_v_u8m1x3_u8m1(rgb, 0);
vuint8m1_t g = __riscv_vget_v_u8m1x3_u8m1(rgb, 1);
vuint8m1_t b = __riscv_vget_v_u8m1x3_u8m1(rgb, 2);
```

The constraint `EMUL·NFIELDS ≤ 8` bounds the total register footprint to one quarter of the register file [1]: with `LMUL=2` (`EMUL=2`), at most 4 fields per segment. For GEMM, segmented operations accelerate *complex-valued* kernels (`NFIELDS=2`: real/imaginary pairs in FFT-based convolution and complex attention variants), *multi-channel* feature maps in NHWC layouts, and *quantized* packed formats where scale/zero-point metadata interleaves with int8 payloads. Andes' AX45MPV product material explicitly calls out segment instructions for video/audio/complex-number processing as a differentiator of its 1024-bit VPU [5].

### 4.4 Tail and mask policies: `ta`/`tu`, `ma`/`mu`

RVV 1.0 requires every `vsetvli` to declare its policy for two element classes: *tail* elements (indices `≥ vl`) and *masked-off* elements (where the mask register `v0` is clear) [1]. The agnostic policies (`ta`, `ma`) permit the implementation to write any value — commonly all-ones, which simplifies hardware by allowing "overwrite everything" datapaths. The undisturbed policies (`tu`, `mu`) preserve prior values, requiring read-modify-write semantics in the vector unit.

For ML kernels the choice is nearly always `ta, ma`, with one critical exception: **reductions across strip-mined iterations**. A dot product accumulated across `vsetvli` iterations must preserve the running sum, so the accumulator update uses undisturbed tail semantics or, more commonly, restructures to reduce *within* each strip (`vfredsum`) and accumulate scalars across strips. LLVM's RVV backend models these policies explicitly: its intrinsics carry tail/mask policy operands, and the instruction selector prefers agnostic forms when dataflow analysis proves undisturbedness unobservable [7]. The "Closer in the Gap" study found that forcing agnostic policies in hand-written microbenchmarks was necessary to reach peak issue throughput, confirming that policy selection is a first-order performance concern, not a semantic nicety [2].

### 4.5 Autovectorization in LLVM: from C loops to RVV

1. **LoopVectorizer + VPlan.** The loop vectorizer builds a VPlan modeling the vectorized loop nest; for RISC-V it must use *scalable* vector types (`<vscale x N x float>`) because `VLEN` is unknown at compile time. VPlan's cost model queries the RISC-V target for per-instruction costs parameterized by `vscale`.
2. **Intrinsic lowering.** Scalable-vector IR lowers to RISC-V-specific intrinsics (`llvm.riscv.vle`, `llvm.riscv.vfmacc`, …), each carrying explicit `vl`, `vtype`, and policy operands — the IR-level reification of the configuration model.
3. **`vsetvli` insertion and configuration optimization.** A dedicated MachineIR pass inserts `vsetvli` instructions and attempts to prove configuration invariance, hoisting and merging them. Redundant `vsetvli`s that survive this pass are a known code-quality issue [2].
4. **Register allocation under LMUL constraints.** The register allocator must respect group alignment: an `LMUL=4` group must start at a register number divisible by 4. Fragmentation from mixed-`LMUL` code is a real hazard the backend mitigates by coalescing `LMUL` usage per loop.

Programmers can bypass autovectorization uncertainty with `<riscv_vector.h>` intrinsics (the *RISC-V V C intrinsic API*), which expose configuration, segmented operations, and policies directly — the interface used by OpenCV's production `riscv-rvv` HAL, where universal intrinsics map to RVV 1.0 with length-agnostic dispatch [4][7]. The MLIR RVV dialect RFC further shows the community converging on `vsetvli`-as-strip-mining as the canonical lowering for tensor programs [7].

## 5 Empirical Evaluation / Proofs

### 5.1 Analytical performance model of an RVV GEMM microkernel

$$I = \frac{768\ \mathrm{FLOP}}{280\ \mathrm{B}} \approx 2.74\ \mathrm{FLOP/B}$$

Repeating with `LMUL=8` FP16 (`SEW=16`, `VLMAX=256`, tile $8 \times 256$): per-iteration FLOP $= 8 \times 256 \times 2 = 4096$; traffic $= 16 + 512 = 528$ B; $I \approx 7.75$ FLOP/B — deeply compute-bound, exploiting the 2× element density that motivates BF16/FP16 inference on X280-class cores [6].

### 5.2 The autovectorization gap

"Closer in the Gap" provides the closest available empirical anchor: hand-written RVV 1.0 assembly microbenchmarks (10⁸-iteration inner loops, dependency-broken, `ta`/`ma` policies) establish throughput ceilings on two RVV 1.0 testbeds, against which GCC 15 and Clang 21 autovectorized proxy applications from HPC and ML domains are measured [2]. Their findings, corroborated by the OpenCV team's production experience [4], decompose the gap into:

| Gap source | Mechanism | Mitigation |
|---|---|---|
| Redundant `vsetvli` | Compiler cannot prove config invariance; re-emits per inner iteration | Hoist manually; single `SEW`/`LMUL` per kernel |
| Conservative `LMUL` | Cost model underestimates benefit of `LMUL=4/8` grouping | `#pragma clang loop vectorize` hints; intrinsics |
| Tail policy pessimization | `tu`/`mu` defaults where `ta`/`ma` provable | Explicit policy intrinsics |
| Remainder handling | Scalar epilogues instead of `vsetvli` strip mining | Trust strip mining; verify assembly |
| Reduction serialization | `vfredsum` ordered reduction not recognized | Manual reduction trees |

The SEAM-V study adds a microarchitectural dimension: even with ideal code, tightly-coupled vector integration leaves throughput on the table for GEMM (their PF mechanism targets exactly GEMM's prefetch behavior), achieving ~32% cycle reduction via hybrid decoupling [3]. The lesson is twofold: *software* must configure aggressively (large `LMUL`, agnostic policies, hoisted `vsetvli`), and *hardware* continues to evolve around RVV's decoupled model.

### 5.3 Proof: strip mining dominates remainder loops

> **Theorem (Strip-mining optimality):** For a loop of trip count $N$ on a machine with $\mathrm{VLMAX} = V$, `vsetvli`-based strip mining executes exactly $\lceil N/V \rceil$ vector iterations with zero scalar remainder code, versus $\lfloor N/V \rfloor$ vector plus up to $V-1$ scalar iterations for fixed-width SIMD. The dynamic instruction-count saving is $\Theta(V)$ in the worst case.
>
> *Proof:* `vsetvli` grants $\min(\mathrm{AVL}, V)$; the loop maintains the invariant $\sum \mathrm{vl}_i = N$ by decrementing `AVL` by the granted amount each iteration, terminating when `AVL = 0`. The final iteration processes $N \bmod V$ elements (or $V$ if divisible) with full vector instructions. No scalar path exists. ∎

## 6 Limitations

1. **Autovectorizer immaturity for reductions and mixed precision.** Ordered floating-point reductions (`vfredsum`) and widening/narrowing mixed-precision patterns — the bread and butter of quantized inference — are the weakest points of current LLVM/GCC RVV codegen; intrinsic-level code remains necessary for peak throughput [2][7].
2. **Gather/scatter performance.** Indexed loads/stores (`vluxei`/`vsuxei`) exist but are microarchitecturally expensive on most implementations; sparse ML (pruned weights, embedding lookups) cannot rely on them for performance. Embedding-bag style access remains scalar- or DMA-bound.
3. **VLEN fragmentation.** The ecosystem spans 128-bit (embedded) to 1024-bit (AX45MPV) `VLEN` [5]; while binaries are portable, *performance* portability is not automatic — `LMUL` choices optimal at 512 bits may spill at 128. Libraries must ship multiple microkernel variants or accept suboptimal configurations.
4. **Profiling and debug tooling.** Vector-aware profiling (`perf` vector counters) is nascent compared to x86/ARM; the "Closer in the Gap" authors had to *validate* `perf` counters with hand-written microbenchmarks before trusting measurements [2].
5. **No native matrix-multiply in base RVV 1.0.** Unlike ARM SME or Intel AMX, base RVV 1.0 lacks 2-D matrix instructions; outer-product GEMM must be synthesized from `vfmacc` chains. Vendors fill the gap with custom extensions (SiFive Intelligence extensions add native matmul; Andes adds AI datatypes [5][6]), fragmenting the "standard" performance story.
6. **Memory subsystem dependence.** RVV's decoupled model tolerates latency but still demands bandwidth; vector load/store throughput on current cores is typically well below the FMA peak, making the Section 5.1 compute-bound regime contingent on high L1/streaming bandwidth.

## 7 Conclusion

RVV 1.0's length-agnostic model — `vsetvli`-driven strip mining, `SEW`/`LMUL` configuration, segmented memory operations, and explicit tail/mask policies — is the most significant vector ISA development for machine learning since the introduction of FMA. We have shown that its configuration machinery is precisely analyzable: `VLMAX = VLEN·LMUL/SEW` governs strip size; `LMUL` selection is a register-allocation optimization with clean solutions (`LMUL=4` FP32, `LMUL=8` FP16/BF16 at 512-bit `VLEN`); segmented operations provide hardware AoS→SoA transposition at memory bandwidth; and strip mining provably eliminates remainder loops. Our analytical GEMM model demonstrates compute-bound microkernels are achievable with disciplined configuration, while the empirical literature confirms that current compilers leave measurable performance on the table — redundant `vsetvli`s, conservative `LMUL`, and weak reduction support — making intrinsic-level kernel engineering still necessary for peak ML throughput [2][4].

The trajectory is clear: commercial cores (SiFive X280, Andes AX45MPV) are shipping RVV 1.0 with ML-oriented datatypes and extensions [5][6]; LLVM's RVV backend advances with each release [2][7]; and production libraries (OpenCV) already dispatch length-agnostic RVV kernels [4]. The open research problems — performance-portable `LMUL` selection across fragmented `VLEN`s, autovectorization of mixed-precision reductions, and a standardized matrix-multiply story — define the next phase of RISC-V for machine learning. RVV 1.0 provides the architectural substrate; the software stack is now racing to exploit it fully.
