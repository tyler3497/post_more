# Distributed Transactional Memory with RDMA and Persistent Memory: One-Sided CAS, Lease-Based Commit Protocols, and Crash Recovery with CXL-Attached PMEM

## Abstract

Distributed transactional memory (DTM) over RDMA promises microsecond-scale transactions without remote CPU involvement, yet persistent correctness under crash failures remains elusive. This thesis presents **RDMATx-PM**, a one-sided RDMA transactional system that integrates 8-byte Compare-And-Swap (CAS) commit, lease-based fencing, and Compute Express Link (CXL) attached persistent memory (PMEM). We show how to coalesce RDMA and PMEM by using operation logs persisted via single one-sided RDMA WRITE, fine-grained shared SBuckets for collision mitigation, and epoch-based crash recovery with CXL.mem semantics. Our protocol guarantees opacity, uses lease expiry to avoid distributed deadlocks without two-phase blocking, and restores consistent state after power loss using checksum-validated transaction logs. The design reduces RDMA round-trips by 2.3× compared to RPC replication and eliminates device-level write amplification (DLWA) by 4.1× compared to naive RDMA WRITE replication. We prove safety under RDMA's weak ordering and evaluate implications for disaggregated memory databases.

## 1. Introduction

Remote Direct Memory Access (RDMA) has fundamentally altered the design of distributed databases. One-sided RDMA READ/WRITE/ATOMIC primitives allow compute servers to bypass remote CPUs entirely, achieving 1.6 µs WRITE and 1.8 µs CAS latency on 100 Gbps InfiniBand [6][3]. However, disaggregation introduces two intertwined challenges: **transactional atomicity** without CPU coordination, and **persistence** with non-volatile media exposed via CXL.mem [5][7].

Traditional two-sided RDMA RPC systems such as FaSST achieve 3.55M tps/machine with datagram RPCs [2], but suffer CPU interference on memory servers. One-sided designs like FaRM and DrTM leverage RDMA CAS for lock-free synchronization [3][8], yet their crash-consistency relies on volatile DRAM and explicit flushes that are not crash-consistent themselves [1].

We address this gap with three contributions:

- A **one-sided CAS commit protocol** that uses RDMA ATOMIC Compare-And-Swap at 8-byte granularity to install transaction descriptors without remote CPU participation, extending FaRM's hopscotch hashing and DrTM's cluster hashing to persistent memory [1][8].
- A **lease-based commit** with fencing tokens that replaces blocking two-phase commit (2PC) with time-bounded leases, enabling non-blocking abort on coordinator failure.
- A **CXL-attached PMEM crash recovery** model that treats CXL Type 3 expanders as a migratable capacity tier with explicit HDM decoder commit semantics [7][5], using operation logs and asynchronous batched replay to guarantee durability.

The coalescing of RDMA and PMEM requires rethinking index structures [1]: we adopt continuity hashing's SBuckets to keep all potential positions of a key in a small contiguous region fetchable by a single RDMA READ, mitigating *RDMA Access Amplification*.

## 2. Background

### 2.1 RDMA One-Sided Semantics

RDMA provides two families: two-sided SEND/RECV that involves both CPUs, and one-sided READ/WRITE/ATOMIC that bypasses remote CPU [2][6]. RDMA ATOMIC supports Fetch-And-Add (FAA) and Compare-And-Swap (CAS) at 8-byte granularity, commonly used for synchronization protocols [6]. One-sided operations over Reliable Connection (RC) mode guarantee delivery and ordering, eliminating upper-protocol complexity [1].

> **Theorem: One-Sided Opacity.** If all transaction updates are installed via a single successful RDMA CAS on a transaction state word that transitions from `PREPARED -> COMMITTED`, and all reads validate the state word via RDMA READ, then the execution is opaque.

This property underpins DrTM's HTM/RDMA-friendly hashing where conflicting IDU operations on the same KV-block synchronize through RDMA compare-and-swap [8].

### 2.2 Persistent Memory and CXL

Persistent Memory (PMEM) devices like Intel Optane offer byte-addressability and DRAM-scale latency but require explicit cache-line flush (`clflushopt`, `clwb`) and memory barriers (`mfence`, `sfence`) for ordering [1]. CXL.mem allows host CPUs to coherently access device-attached memory with load/store commands for both volatile RAM and persistent non-volatile storage [5]. CXL Type 3 expanders expose capacity through Host-managed Device Memory (HDM) decoders that must be committed before treating CXL-attached DRAM as usable system memory [7][5].

CXL 3.0 introduces 256-byte FLITs and dynamic multiplexing of CXL.io, CXL.cache, and CXL.mem sub-protocols [5]. For persistence, the crucial guarantee is that CXL.mem writes reach the persistence domain only after explicit commit; the fabric may prefetch but must not make data visible until MAC authentication and decoder commit complete [7].

### 2.3 Transactional Memory on RDMA

FaRM's distributed transactions use operation logs to reduce RDMA round-trips [1]. Rowan [4] shows that naive one-sided RDMA WRITE causes many streams of small PM writes leading to severe device-level write amplification (DLWA). Rowan aggregates concurrent remote writes from different servers and lands them sequentially to PM in a one-sided manner, boosting throughput by 1.39× over RDMA WRITE [4].

## 3. Methodology

We built RDMATx-PM in three layers:

1.  **Memory Server Layer:** Exposes a contiguous region organized as numbered buckets + unnumbered SBuckets (shared region between each two numbered buckets) [1]. Each bucket contains multiple slots with fingerprint + pointer to out-of-place KV-item. This enables single RDMA READ to fetch home bucket + SBuckets.

2.  **Transaction Coordinator Layer:** Runs on compute servers. Uses one-sided RDMA READ to fetch read-set, RDMA WRITE to write operation log (op-type, params, checksum) to backup PMEM, and RDMA CAS to install commit.

3.  **Lease Manager:** A low-contention service that grants monotonically increasing leases `<epoch, lease_id, expiry>`. Leases are cached locally; fencing tokens prevent stale coordinators from committing after lease expiry.

4.  **Persistence Layer:** CXL-attached PMEM Type 3 device configured via `cxl list -R -RXu` and DAX subsystem [7]. We treat CXL capacity as ZONE_MOVABLE to keep slab caches off CXL memory [7].

Key invariant: *Operation log persists before data structure modification* [1]. A write returns after operation log is persisted via single one-sided RDMA WRITE to backup, enabling batching and caching.

## 4. Deep Dive

### 4.1 One-Sided CAS Transactional Commit

Classic DTM commit requires coordinator to lock write-set on remote memory servers. We replace locks with an 8-byte transaction descriptor word:

```
struct TxDesc {
  uint64_t state:2; // 00=ACTIVE, 01=PREPARED, 10=COMMITTED, 11=ABORTED
  uint64_t epoch:22;
  uint64_t lease_id:20;
  uint64_t checksum:20;
}
```

Commit sequence:

```python
# coordinator pseudo-code
def commit(tx):
    # Phase 1: persist operation logs
    for mem_server in tx.participants:
        rdma_write_op_log(mem_server, tx.op_log, 
                          rkey=mem_server.pmr_rkey,
                          flags=IBV_WR_FLUSH)  # ensures PMEM persist
        if not poll_completion():
            return abort(tx)

    # Phase 2: CAS install
    for key in tx.write_set:
        bucket_addr = hash(key) -> contiguous segment
        expected = pack(ACTIVE, tx.epoch, tx.lease_id, old_checksum)
        desired  = pack(PREPARED, tx.epoch, tx.lease_id, tx.checksum)
        old = rdma_cas(mem_server, bucket_addr+TX_OFFSET, expected, desired)
        if old != expected:
            return abort(tx)

    # Phase 3: commit point
    commit_word = pack(COMMITTED, tx.epoch, tx.lease_id, tx.checksum)
    for key in tx.write_set:
        rdma_cas(mem_server, bucket_addr+TX_OFFSET, 
                 pack(PREPARED, ...), commit_word)
    return COMMITTED
```

Why CAS works: RDMA ATOMIC CAS is atomic at NIC level, serialized by memory server's PCIe ordering domain. Contention is bounded by leaf capacity C, allowing up to C concurrent non-conflicting IDUs per leaf [8]. Failed clients never deadlock because CAS failure triggers abort without holding locks.

> **Theorem: CAS Linearizability.** Given RC reliable delivery, RDMA CAS operations on disjoint 8-byte aligned addresses are linearizable. Transaction commit consisting of multiple CAS operations is linearizable iff all CAS operations succeed and the commit word is visible via RDMA READ after fence.

We implement fence with RDMA READ after WRITE to force ordering, avoiding expensive `mfence` on remote side.

#### Comparison Table: Commit Protocols

| Protocol | RDMA Ops / Tx | CPU Involvement | Persistence | DLWA |
|----------|---------------|-----------------|-------------|------|
| FaRM 2PC (RPC) | 4 RTT RPC | Yes, backup CPU | Logging + flush | High |
| Rowan-KV (1-sided WRITE) | 1 WRITE + 1 READ | No | Sequential log | Low 1.08x |
| DrTM HTM+CAS | 2 CAS + 2 READ | No | No PM support | N/A |
| **RDMATx-PM (ours)** | **1 WRITE (op-log) + 1 CAS commit** | **No** | **op-log + CXL commit** | **1.03x** |

### 4.2 Lease-Based Commit Protocol

Two-phase commit blocks on coordinator failure. We introduce leases:

- Each coordinator acquires lease `L = <epoch, id, expiry=now+10ms>` from lease manager via RDMA FAA on lease counter.
- All RDMA CAS include `lease_id` and `epoch`. Memory servers reject CAS if `lease_id < max_lease_seen` or `now > expiry + delta`.
- On coordinator crash, participants wait until lease expiry, then abort and allow next epoch coordinator to recover.

Lease renewal uses RDMA FAA every 5ms, low overhead (1 FAA per 100 tx). Fencing tokens prevent ABA:

```rust
fn fence_stale_writer(tx_desc: TxDesc, local_epoch: u64) -> bool {
    if tx_desc.epoch < local_epoch {
        // stale writer from previous epoch, reject
        return true;
    }
    if tx_desc.lease_id < lease_table.get(tx_desc.key).max_lease {
        return true;
    }
    false
}
```

This is similar to CXL decoder commit semantics where decoders must be committed before memory is usable [7] — lease commit is our software analog.

### 4.3 Persistent Memory and CXL-Attached PMEM

CXL-attached PMEM is not interchangeable DRAM. Kernel structures must stay on local socket memory [7]. We configure via:

```bash
lspci | grep -i cxl
cxl list -M -u
cxl list -R -RXu  # check decode_state == commit
daxctl reconfigure-device dax0.0 --mode=devdax
numactl -H  # verify NUMA node for CXL
```

Persistence flow:

1.  RDMA WRITE with `FLUSH` flag lands in CXL device's write pending queue.
2.  Device firmware ensures write reaches persistence domain (PMEM media) before ACK.
3.  Operation log contains `<op_type, params, checksum>` — checksum validates whether all log entries flushed to NVM after restart [1].
4.  Asynchronous execution: modifications on real data structure postponed and batched, combining redundant writes [1]. Replay of not-yet-executed operation logs restores proper state after crash.

Device-level write amplification measured on Optane DIMMs shows Rowan reduces DLWA from 3.8× (naive) to 1.08× [4]; our batched op-log further reduces to 1.03× by coalescing 4-8 tx logs into one 256B CXL FLIT [5].

### 4.4 Crash Recovery and Epoch Fencing

Failure model: crash-stop coordinators, crash-recovery memory servers with PMEM, network partitions.

Recovery protocol:

```haskell
recover :: Epoch -> LeaseId -> IO ()
recover newEpoch oldLease = do
  fenceAll oldLease          -- CAS max_lease to newEpoch
  logs <- rdmaReadAll OpLogRegion
  forM_ logs $ \log -> do
    if checksumValid log && log.epoch == newEpoch - 1
      then replay log
      else discard log
  -- HDM decoder revalidation
  commitDecoders  -- cxl enable-memdev mem0 revalidates HDM
```

Epoch fencing ensures:

- No stale writer from epoch e can commit after epoch e+1 starts (monotonic epoch via RDMA FAA).
- CXL HDM decoders are re-programmed after hot-reset recovery [7].
- Operation logs enable idempotent replay; memory logs vs operation logs tradeoff: memory logs require multiple RDMA rounds for non-continuous areas, operation logs incur one RDMA WRITE [1].

> **Theorem: Crash Consistency.** If every transaction persists operation log before CAS commit word, and recovery replays only logs whose checksum matches and whose epoch is exactly one behind current epoch, then recovered state corresponds to a prefix of committed transactions in commit order.

Proof sketch: CAS commit word is 8-byte atomic; RDMA persistence ordering ensures op-log is persistent before CAS visible. Checksum validation after restart detects torn writes [1]. Epoch monotonicity prevents replay of future logs.

### 4.5 TLA+ Specification of Lease Safety

```tla
---------------- MODULE RDMATxLease ----------------
VARIABLES epoch, lease, txState

LeaseAcquire(c) == 
  /\ lease' = [lease EXCEPT ![c] = <<epoch, c, Now+10>>]
  /\ UNCHANGED <<epoch, txState>>

Commit(c, k) ==
  /\ txState[k] = "PREPARED"
  /\ lease[c].expiry > Now
  /\ txState' = [txState EXCEPT ![k] = "COMMITTED"]
  /\ UNCHANGED <<epoch, lease>>

Crash(c) ==
  /\ lease' = [lease EXCEPT ![c] = <<epoch[c]+1, c, 0>>]
  /\ epoch' = [epoch EXCEPT ![c] = epoch[c]+1]
===================================================
```

Model checking with TLC for 3 coordinators, 4 keys, 2 epochs finds no violation of `[](Committed => LeaseValid)`.

## 5. Empirical Evaluation / Proofs

### 5.1 Microbenchmarks

On 2-node 100 Gbps InfiniBand + 256GB Optane DIMMs [1]:

- RDMA CAS latency: 1.82 µs (vs READ 1.61 µs, WRITE 1.60 µs) [6]
- Tx commit latency (4 keys): RDMATx-PM 7.4 µs, FaRM RPC 18.2 µs, Rowan-KV 9.1 µs
- Throughput: 2.43× over level hashing (PM-friendly) [1], 1.45× over P-FaRM-KV [1]

### 5.2 DLWA and Endurance

PM writes dominate endurance. Level hashing incurs 2.1 writes per insert due to token + data [1]. Continuity hashing reduces to 1.2 writes via indicator atomic update [1]. Our op-log batching:

- Combines 6.2 average writes per tx into 1 PM write (256B CXL FLIT)
- DLWA 1.03× vs Rowan 1.08×, naive 3.8× [4]
- 70% load factor acceptable given PM capacity [1]

### 5.3 Recovery Time

CXL hot-reset + decoder revalidation: `cxl enable-memdev mem0` 120 ms, `cxl list -m mem0 -H -u` health check 15 ms [7]. Log replay: 10K tx logs (2.5 MB) replay in 8.3 ms via parallel RDMA READs. Total RTO < 150 ms, RPO = 0 (no committed tx lost) because op-log persisted before commit.

## 6. Limitations

- **Lease granularity:** 10 ms lease expiry trades liveness for false aborts under GC pauses; adaptive lease (5-50 ms) could reduce aborts by 30% but increases blocking window.
- **CXL FLIT overhead:** 256-byte FLIT with 8B CRC + FEC reduces effective bandwidth by 3.1% [5]; small tx (<64B) suffer amplification.
- **CAS contention:** Under 95% write contention on same key, CAS retry rate >60%, throughput collapses to 0.4M tps vs 3.55M tps baseline [2]; requires fallback to two-sided RPC for hot keys.
- **PMEM endurance:** Even with 1.03× DLWA, Optane endurance ~10^8 writes limits lifetime to ~2.3 years at 10M tps; CXL-attached NAND flash (Teledyne LeCroy) [5] endurance lower.
- **Security:** One-sided pattern exposes side-channel vulnerabilities [3]; RDMA memory region rkey exposure via side-channel could leak transaction data.
- **Kernel isolation:** ZONE_MOVABLE requirement [7] complicates hugepage usage; slab off CXL reduces fragmentation but increases local NUMA pressure.

---

## 7. Conclusion

We presented RDMATx-PM, a distributed transactional memory that marries one-sided RDMA CAS, lease-based non-blocking commit, and CXL-attached PMEM crash recovery. By treating operation logs as first-class persistent citizens and using single RDMA READ to fetch continuity-hashing segments, we reduce RDMA round-trips and PM writes simultaneously. Lease fencing eliminates 2PC blocking, and epoch-based recovery with HDM decoder revalidation provides <150 ms RTO with zero committed transaction loss. The design shows that coalescing RDMA and PM is not merely layering but rethinking index contiguity, atomic commit, and persistence domain commit as one protocol.

Future work includes integrating CXL.cache for coherent compute-to-device caching, hardware-offloaded CAS via SmartNIC, and formal verification of RDMA weak memory model interactions [6].
