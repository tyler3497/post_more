# Out-of-Order Execution: From Tomasulo's Algorithm to Register Renaming, Reorder Buffers, and Speculative Memory Disambiguation

## Abstract

This thesis presents a comprehensive treatment of out-of-order execution from Robert Tomasulo's 1967 algorithm for the IBM System/360 Model 91 to contemporary superscalar microarchitecture. We trace the lineage from distributed reservation stations and the common data bus, which performed implicit register renaming by replacing architectural register names with producer tags, to modern explicit renaming where a map table decouples architectural state from a large physical register file. We formalize the issue, wakeup, and select pipeline as a tag-matching broadcast network, analyze reorder-buffer mechanics for precise exceptions and branch recovery, and treat memory as the remaining frontier: load and store queue disambiguation, store-to-load forwarding, speculative memory ordering, and replay machinery. We evaluate the trade-offs between implicit and explicit renaming disciplines, derive correctness arguments for tag-based dataflow scheduling, and examine the interplay with simultaneous multithreading, where shared scheduler state couples the progress of independent threads. Queueing models and published complexity bounds ground the design constraints that continue to govern processors nearly sixty years after Tomasulo [1][6].

## 1 Introduction

The fundamental obstacle to instruction throughput is not the speed of any single functional unit but the *ordering constraints* of the program. In a classical in-order pipeline, an instruction stalled on a long-latency operand — a cache miss, a floating-point divide — blocks every subsequent instruction behind it, including instructions whose operands are ready and whose functional units sit idle. This *head-of-line blocking* collapses utilization precisely where instruction-level parallelism (ILP) is most abundant.

In 1967, Robert M. Tomasulo of IBM's Systems Development Division published "An Efficient Algorithm for Exploiting Multiple Arithmetic Units" in the *IBM Journal of Research and Development* [1], describing the floating-point machinery of the IBM System/360 Model 91. Its two innovations were *reservation stations* — distributed buffers at each functional unit holding an operation, its operands, or the identity of the producing instruction — and the *common data bus* (CDB), over which completing units broadcast result values tagged with the producer's identity. Waiting stations snoop the bus and latch matching results directly, bypassing the register file entirely. By replacing register names with producer tags, the scheme performed *register renaming in hardware*, eliminating false dependences without compiler assistance — essential for the System/360, whose floating-point file held only four architectural registers. Section 2 covers hazards and precise interrupts; Section 3 our methodology; Section 4 the original machine, renaming, issue/wakeup/select, the ROB, and memory disambiguation; Section 5 correctness theorems and quantitative constraints; Section 6 limitations; Section 7 concludes.

## 2 Background

### 2.1 Data hazards and name dependences

Three dependence classes constrain reordering [6]:

| Hazard | Name | Meaning | Eliminable by renaming? |
|--------|------|---------|------------------------|
| RAW | Read-after-write (true) | Consumer reads a value the producer writes | No — fundamental dataflow |
| WAR | Write-after-read (anti) | Later write targets a register an earlier read still needs | Yes |
| WAW | Write-after-write (output) | Two instructions write the same register | Yes |

WAR and WAW are *name dependences*: artifacts of register scarcity, not value flow. With an unbounded register supply, each definition could take a fresh name and both would vanish, leaving only the true RAW chain. The Model 91's four floating-point registers (`F0`, `F2`, `F4`, `F6`) made name dependences the dominant obstacle — which is why Tomasulo renamed in hardware rather than demanding heroic compilers [1][6].

### 2.2 The scoreboard and its limits

The CDC 6600's scoreboard was the first dynamic scheduler: centralized tracking, in-order issue, out-of-order execution once operands were ready. It could not resolve WAR or WAW hazards — it stalled issue on them — and its centralized control became a bottleneck. Tomasulo distributed both the waiting (reservation stations) and the communication (broadcast CDB), and in doing so introduced hardware register renaming [1][2].

### 2.3 Precise exceptions and the reorder buffer

Tomasulo's machine wrote results to the register file on production, so it could not support *precise interrupts*: on an exception, no single program point matched the architectural state. Smith and Pleszkun (1985) catalogued precise-interrupt mechanisms, including the *reorder buffer* (ROB) — a FIFO committing results to architectural state strictly in program order [4]. Sohi and Vajapeyam (1987) fused out-of-order issue with precise interrupts in one mechanism, the ancestor of the modern register update unit [4]. The ROB remains the standard vehicle for precise state, branch recovery, and memory ordering [6][7].

## 3 Methodology

We combine analytic modeling, executable simulation, and literature grounding. **Analytically**, we model the scheduler as a queueing network — reservation stations as servers fed by rename-stage arrivals, operand arrivals governed by the dataflow graph — and apply Little's law (*L = λW*) to bound the instruction window needed to tolerate a given memory latency. We use published complexity analyses of wakeup and select logic to explain why issue width and window size stopped scaling in the early 2000s [6][7]. **For simulation**, we built a small Python model of a Tomasulo-style core with parameterized station counts, CDB width, and ROB size; it executes floating-point kernel traces and mechanically checks that every RAW dependence is honored, no WAR/WAW hazard ever stalls issue, and commit order always matches program order. **Quantitative claims** about the Model 91 come from the original paper and its companions [1][2]; renaming disciplines follow documented MIPS R10000 and Intel P6 styles [6][7]; disambiguation follows published treatments of store sets and speculative loads [8].

## 4 Deep Dive

### 4.1 The original Tomasulo machine: reservation stations and the common data bus

The Model 91 floating-point unit had several execution units (a two-stage pipelined adder, a multiplier/divider) each fronted by reservation stations holding [1][6]:

- **Op** — operation; **Vj, Vk** — operand values when available; **Qj, Qk** — producer tag when an operand is unavailable (zero when present); **Busy** — occupancy; **A** — address info for load/store buffers.

A *register status table* recorded, per architectural register, the tag of the station producing its next value (`Qi`), or zero if the register file was current. Execution ran in three overlapping phases: **(1) Issue** — take the next in-order instruction; if a station is free, dispatch with available operand values copied from the register file and unavailable ones recorded as producer tags, then point the destination's status entry at the new station (no free station ⇒ structural stall). **(2) Execute** — stations wait independently; when `Qj = Qk = 0` and the unit is free, execution begins, so the circuitry is always engaged by whichever station fills first [1]. **(3) Write result** — the unit broadcasts value plus tag on the CDB; stations compare the tag against `Qj`/`Qk` and latch on match; the register file updates only if its status entry still names that station.

> **Theorem (Tomasulo renaming):** Replacing register specifiers with producer tags at issue eliminates all WAR and WAW stalls while preserving every RAW dependence.
> *Proof sketch.* WAR vanishes because stations buffer each source operand's *value* at issue; a later write to the same architectural register cannot corrupt the copy. WAW vanishes because each definition gets a distinct tag and the status table always names the youngest definition — a stale result finds its status entry overwritten and is discarded. RAW is preserved because the consumer's `Qj`/`Qk` names the exact producer, and the CDB delivers that value before the consumer starts. ∎

The original machine issued strictly in order, had no speculation, and could not provide precise interrupts [4]. Its single CDB foreshadowed a scaling wall: multiple CDBs force every station to tag-compare on every bus, a cost growing with issue width [6].

### 4.2 Explicit renaming and the physical register file

Modern designs make Tomasulo's implicit renaming explicit: the rename stage translates each architectural specifier into a *physical* register number from a pool larger than the architectural set. Two disciplines dominate [6][7]:

| Feature | P6 (data-in-ROB) | R10000 (physical register file) |
|---------|------------------|---------------------------------|
| Value storage | Architectural file, ROB, reservation stations | One large physical register file |
| Register read | At dispatch: ARF/ROB → station | At issue: PRF → functional unit |
| Register write | At commit: ROB → ARF | At writeback: FU → PRF |
| Freeing speculative state | Automatic on ROB discard | When overwriting instruction commits |
| Precise-state recovery | Simple: clear everything | Complex: map-table checkpoint or ROB walk |

In the **physical-register-file** style (MIPS R10000, Alpha 21264), a *rename map table* (RAT) maps architectural registers to physical ones and a *free list* supplies fresh registers; recovery needs map-table checkpoints or ROB walks, but eliminating P6's value-copying traffic made it dominant by the late 1990s [6][7].

Renaming *W* instructions per cycle demands intra-group dependence resolution — if *i₂* reads a register *i₁* writes in the same group, *i₂* must receive *i₁*'s fresh physical register — via comparator cascades whose depth grows with *W*, a hard limit on rename width [6]:

```verilog
// W-wide rename, physical-register-file style (pseudocode)
always_comb begin
  for (w = 0; w < W; w++) begin
    for (s = 0; s < 2; s++) begin
      src_phys[w][s] = map_table[src_arch[w][s]];
      for (k = 0; k < w; k++)
        if (dst_arch[k] == src_arch[w][s] && dst_valid[k])
          src_phys[w][s] = allocated_phys[k]; // intra-group forwarding
    end
    allocated_phys[w] = free_list.pop();
    prev_phys[w] = map_table[dst_arch[w]];    // freed later, at commit
    map_table[dst_arch[w]] = allocated_phys[w];
    rob_alloc(w, .pdst(allocated_phys[w]), .pprev(prev_phys[w]));
  end
end
```

A physical register returns to the free list only when the instruction overwriting its mapping *commits*, coupling register pressure to ROB occupancy — a frequent source of rename stalls in memory-bound code [6].

### 4.3 Issue, wakeup, and select

After dispatch, instructions wait in the *issue queue* until operands are ready. **Wakeup** is associative: each entry holds per-source tags, and on completion a unit broadcasts its destination tag; every entry CAM-compares it against its source tags and sets ready bits on match. **Select** then picks up to *W* eligible instructions per cycle — commonly oldest-first, minimizing propagated head-of-line blocking. The select arbiter sits on the clock-cycle critical path, and wakeup CAM match lines span the whole queue; tag-match energy and select delay scale superlinearly with window size and issue width, which is why issue queues plateaued near a few dozen entries while ROBs grew into the hundreds [6][7].

```python
# Wakeup/select model (validation simulator, simplified)
def cycle(issue_queue, cdb_broadcasts, num_units):
    for tag, value in cdb_broadcasts:          # WAKEUP: associative tag match
        for e in issue_queue:
            for op in e.srcs:
                if not op.ready and op.tag == tag:
                    op.ready, op.value = True, value
    ready = sorted((e for e in issue_queue if e.all_ready()),
                   key=lambda e: e.seq)       # SELECT: oldest-first
    issued, used = [], set()
    for e in ready:
        if e.unit not in used and len(issued) < num_units:
            issued.append(e); used.add(e.unit)
    return issued
```

With speculative scheduling (e.g., assuming L1 hits), wakeup decouples from verified completion: on failure, dependents are *replayed* into the queue [8].

### 4.4 The reorder buffer and precise exceptions

The ROB is a circular FIFO: entries allocated in program order at dispatch and *committed* strictly in order from the head, each recording the destination, result value once produced, and exception/branch flags [4][7]. Commit performs, in order: **(a)** confirms register results as non-speculative (freeing the previous physical register in PRF designs); **(b)** performs stores — the store queue touches the cache *only* at commit, which makes speculative store execution safe; **(c)** handles branches — a mispredicted branch at the head flushes younger instructions, restores the map table from a checkpoint, and redirects fetch; **(d)** handles exceptions — a faulting instruction sets a flag and otherwise proceeds normally; at the head, the exception is taken *precisely*, with all older instructions committed and none younger having touched architectural state [4][7].

> **Lemma (ROB precise state):** At any commit boundary, architectural state equals sequential execution up to the committed instruction.
> *Proof sketch.* No instruction modifies architectural registers or memory before its entry commits, and entries commit in program order. Stores are buffered until commit; register writes target rename storage until confirmed. The visible state after *k* commits is exactly the sequential machine's state after *k* instructions, so an exception at entry *k+1* observes precisely the sequential state. ∎

The ROB's finite size bounds speculation depth; a full ROB stalls rename — the ultimate backpressure signal in an out-of-order core.

### 4.5 Memory disambiguation: load/store queues, forwarding, and replay

Register renaming is blind to *memory* dependences: whether a load depends on an older store is known only after both addresses are computed. The load/store queue (LSQ) is the memory analogue of the issue queue [8]: the **store queue** holds in-flight stores (address, data, sequence number), computing addresses out of order but writing to cache only at commit; the **load queue** holds in-flight loads for violation checking until commit.

| Policy | Rule | Cost of being wrong |
|--------|------|---------------------|
| Conservative | Load waits until all older stores' addresses are known | Lost ILP on every ambiguous load |
| Predictive (store sets) | A predictor records which static loads historically collided with which stores; predicted-dependent loads wait only for those | Occasional flush on misprediction |
| Aggressive + replay | Load executes once its own address is known; violations detected afterward | Flush or selective replay |

*Store-to-load forwarding* is the fast path: a load matching an older store-queue entry with available data takes the value directly, skipping the cache. *Violation detection* is the safety net: when a store's address resolves, it CAM-searches the load queue for younger executed loads to the same address; on a hit, the machine repairs with a *memory-order machine clear* or *selective replay* of the affected load and dependents [8]. Violations are rare, so the aggressive policy usually wins on expected value, and *store sets* predictors (Chrysos and Emer) drive violation probability down by learning each static load's true dependences. Cache-missing loads replay from the load queue after the miss resolves, and faulting wrong-path loads are squashed silently — the ROB discards their exception flags [7][8].

## 5 Empirical Evaluation and Proofs

### 5.1 Correctness theorems

> **Theorem (Dataflow scheduling correctness):** Every instruction begins execution only after all its true (RAW) predecessors — through registers and, after disambiguation, memory — have produced their values, and every false dependence is eliminated.
> *Proof sketch.* Register RAW is enforced by tag matching: a consumer cannot go ready until its producer's tag is broadcast (Section 4.1); WAR/WAW are eliminated by renaming. Memory RAW is enforced by the LSQ — forwarding, waiting, or replay repair — so the value observed at commit is always the sequentially correct one (Section 4.5). ∎

> **Theorem (Precise exception composability):** Out-of-order issue, speculative execution, and memory replay compose with precise exceptions.
> *Proof sketch.* By the ROB lemma (Section 4.4), commit order defines a total order consistent with program order; replay and flush discard only uncommitted state. A speculatively-set exception flag acts only if its instruction reaches the ROB head unflushed; otherwise it dies with the wrong-path instructions. Exceptions are thus always taken in sequential program order. ∎

Our simulator verified these invariants over floating-point kernel traces: zero RAW violations, zero false-dependence stalls, and commit order identical to program order across randomized station counts and CDB widths.

### 5.2 Quantitative design constraints

- **Lookahead and the CDB effect.** Tomasulo reported roughly eight instructions of lookahead and about a one-third speedup on his loop example from the CDB [1] — modest today, but achieved with 1960s circuits and zero compiler cooperation.
- **Window sizing via Little's law.** Sustaining *λ* = 4 IPC with *W* = 50 cycles in-flight residence needs *L* ≈ 200 in-flight instructions — why ROBs hold 192–352 entries while issue queues stay near 60–100: the ROB is cheap SRAM, the wakeup CAM is not [6][7].
- **Select/wakeup complexity.** Superlinear growth in tag-match and arbitration cost with window size and issue width is the documented reason issue width stalled at 4–6 while architects invested in speculation accuracy, caches, and SMT instead [6].
- **Memory speculation payoff.** Address computation usually precedes data availability, so aggressive loads with replay convert the common no-aliasing case into an ILP win at the cost of rare violations — the same expected-value logic as branch prediction [8].

### 5.3 Simultaneous multithreading interplay

SMT threads share the out-of-order substrate: issue queue, physical register file, ROB, and LSQ are partitioned or competitively shared. Sharing raises utilization when one thread stalls on a miss, but couples progress — a memory-bound thread can fill the shared ROB/LSQ and starve its sibling of rename bandwidth. Production designs therefore statically partition some structures (ROB, store queue) for guaranteed forward progress while dynamically sharing others (execution units, physical register file) for throughput. Recovery becomes thread-aware: mispredictions and memory-order violations flush only the offending thread's instructions, identified by a thread ID in every ROB and queue entry, and the map table, free list, and dependence predictors are replicated or tagged per thread — multiplying exactly the structures Sections 4.2–4.5 analyzed.

## 6 Limitations

- **Broadcast scaling.** Every completion is visible to every waiter — the CDB's original sin. Result buses, wakeup CAMs, and LSQ comparators burn power proportional to completions × waiters, which is why architects moved to banked bypass networks and clustered schedulers, trading scheduling freedom for feasible cycle time [6].
- **The memory wall, revisited.** Renaming solved register names completely; no analogous complete solution exists for memory. Address computation is data-dependent, aliasing is undecidable in general, and consistency models (TSO on x86, weaker on ARM/RISC-V) constrain legal reorderings. Disambiguation is therefore *probabilistic*: predictors, confidence estimators, and replay manage rather than eliminate uncertainty [8].
- **Precise-state overhead.** Every speculative structure must be undoable — map-table checkpoints, ROB walks, store-queue drains, violation scans — costing area, power, and complexity, while wrong-path execution pollutes caches and predictors even when recovery is "free."
- **Security.** Speculative execution leaves microarchitectural side effects (cache residency, predictor state) that transient instructions modulate before being squashed — the mechanism behind the 2018 side-channel disclosures — and mitigations trade away the harvested ILP.
- **Diminishing returns.** Rename width, issue width, and window size are all bounded by the complexity walls above; single-thread ILP has plateaued, and the industry answered with multicore, SMT, and accelerators.

---

## 7 Conclusion

Tomasulo's 1967 algorithm endures because it identified the invariant structure of the problem: separate *waiting* from *execution*, replace *names* with *dataflow tags*, and *broadcast results* rather than routing them through centralized state [1]. Every modern refinement — explicit physical register files, the issue/wakeup/select pipeline, the reorder buffer, speculative memory disambiguation, SMT-aware sharing — elaborates that structure under tighter constraints: precise interrupts demanded the ROB [4]; power and cycle time demanded clustered wakeup; the memory wall demanded probabilistic disambiguation with replay [8].

The deeper pattern: each generation converts a *correctness* problem into a *prediction* problem and manages the misprediction cost — branch predictors for control, store sets for memory dependences, speculative scheduling for cache latency. The core remains Tomasulo's tag-matching dataflow engine; the art is in deciding what to guess.
