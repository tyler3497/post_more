# Confidential GPU Computing with NVIDIA H100 Confidential Computing Mode: Attestation of GPU TEE, Encrypted PCIe, In-Transit AES-GCM, and CPU-GPU Secure Channel via SPDM

## Abstract
NVIDIA H100 Tensor Core GPU introduces the first production-grade GPU Trusted Execution Environment (TEE) with Confidential Computing (CC) mode, enabling data-in-use protection for AI workloads. This thesis analyzes the end-to-end architecture spanning on-die Hardware Root of Trust (RoT), dual micro-controller trust chain (FSP/GSP), Compute Protected Region (CPR) isolated by hardware firewalls, BAR0 Decoupler, and CPU-GPU secure channel negotiated via DMTF Security Protocol and Data Model (SPDM). We formalize attestation flow: device-unique ECC-384 identity fused at manufacturing, certificate chain to NVIDIA Root CA, OCSP revocation, measurement of firmware, microcode, and configuration registers into signed attestation report verified by NVIDIA Remote Attestation Service (NRAS) and Intel Trust Authority. We dissect encrypted PCIe transport: bounce buffers in untrusted shared memory, AES-256-GCM per-copy-engine encryption with integrity tags, anti-replay, and command-buffer signing. Evaluation synthesizes published benchmarks: 0-30% latency overhead model-dependent, ~4 GB/s CPU encryption bottleneck, 99.78% BAR0 register zeroization in CC-On. We prove security properties via TLA+ and discuss limitations: single-tenant GPU exclusivity, NVLink encryption removal in Protected PCIe mode, side-channel mitigations disabling perf counters, and multi-GPU topology attestation complexity.

## 1 Introduction

Confidential Computing redefines cloud security by protecting *data in use* within a hardware-rooted Trusted Execution Environment (TEE), where even privileged hypervisor, host OS, and physical attacker cannot inspect or tamper with computation [1][2]. While CPU TEEs such as Intel Trust Domain Extensions (TDX) and AMD Secure Encrypted Virtualization-Secure Nested Paging (SEV-SNP) matured to VM-level isolation, accelerators remained a gaping hole: models and PII traversing PCIe in plaintext, GPU memory accessible via BAR mappings, and no remote verifiability [3].

NVIDIA H100, built on Hopper architecture with 80 GB HBM3 co-packaged, closes this gap. It is the *first GPU to support confidential computing* [4], anchoring trust in on-die RoT, establishing measured boot, and exposing three modes: **CC-Off** (standard), **CC-On** (full isolation, firewalls active, perf counters disabled), and **CC-DevTools** (functional emulation with security disabled for NSys profiling) [4].

The central technical challenge: extend a CPU Confidential VM (CVM) TEE to include PCIe-attached GPUs without violating CPU TEE's memory isolation, which blocks direct device access to CVM private pages. NVIDIA's solution comprises:

- **Hardware firewalls** partitioning GPU memory into public and **Compute Protected Region (CPR)** — ~90% of HBM3, accessible only by internal compute/DMA engines [5]
- **BAR0 Decoupler** returning zeros for 99.78% of control registers in CC-On vs 80.25% errors in CC-Off [6]
- **SPDM session** between CPU TEE driver (Requester) and GPU System Processor (GSP) (Responder) for authentication, measurement retrieval, and ephemeral session key derivation [7][8]
- **Encrypted PCIe** via bounce buffers: all UVA, command buffers, CUDA kernels, and UVM transfers encrypted with AES-256-GCM, signed, anti-replay protected [4][9]
- **Attestation**: device identity certificate with ECC P-384 fused key, chain to NVIDIA CA, measurements of FSP/GSP firmware, VBIOS, configuration registers, and CC mode status, verifiable via NRAS or locally with OCSP [10][11]

This thesis contributes a unified formalization of H100 CC, linking DMTF SPDM 1.1+ to NVIDIA's implementation, and evaluates performance-security trade-offs.

## 2 Background

### 2.1 TEE Taxonomy

*Traditional CPU TEEs* isolate at process (SGX) or VM (TDX/SEV-SNP/CCA) granularity, encrypting memory with hardware-managed keys and excluding hypervisor [12]. *Accelerator TEEs* must additionally protect:

- Device memory confidentiality/integrity against host BAR access
- PCIe transport against physical interposer and hypervisor packet capture
- Device identity authenticity against counterfeit or tampered firmware
- Multi-device topology integrity (NVSwitches in HGX)

H100 satisfies these via *physically isolated TEE* created during boot: firmware scrubs state, configures firewall, then enables PCIe [4].

### 2.2 Hopper Security Lineage

Since Volta V100, NVIDIA authenticated firmware via AES signatures. Turing/Ampere added encrypted firmware, revocation, fault-injection countermeasures. Hopper adds on-die RoT, measured/attested boot, and micro-controller isolation [4]:

- **FSP (Foundation Security Processor)**: root of trust, secure boot, CC mode fuse management, attestation report generation
- **GSP (GPU System Processor)**: RM offload, SPDM responder, copy-engine key programming, firewall policy enforcement

Each H100 provisioned at manufacturing with unique device key pair (ECC-384) burned into fuses; public key certified into device certificate [10].

### 2.3 DMTF SPDM

SPDM (DSP0274) defines generic request-response for capability discovery, authentication, measurement, and secure session establishment over any transport (PCIe DOE, MCTP) [7]. Core exchanges:

- `GET_VERSION` / `VERSION` : version negotiation
- `GET_CAPABILITIES` / `CAPABILITIES` : flag negotiation (CERT_CAP, CHAL_CAP, MEAS_CAP, KEY_EX_CAP, ENCRYPT_CAP, MAC_CAP)
- `NEGOTIATE_ALGORITHMS` / `ALGORITHMS` : select hash (SHA-256/384/512), signature (ECDSA P-256/384), DHE (secp256r1/secp384r1, FFDHE), AEAD (AES-128/256-GCM, ChaCha20-Poly1305)
- `GET_DIGESTS` / `DIGESTS` , `GET_CERTIFICATE` / `CERTIFICATE` : certificate chain retrieval
- `CHALLENGE` / `CHALLENGE_AUTH` : proof of private key possession, transcript `M1/M2` signing
- `GET_MEASUREMENTS` / `MEASUREMENTS` : DMTF-defined measurement blocks (firmware version, SVN, config)
- `KEY_EXCHANGE` / `KEY_EXCHANGE_RSP`, `FINISH` / `FINISH_RSP` : ECDHE session, `TH1/TH2` transcript hash, derivation of handshake secrets and data secrets for AEAD [13]

SPDM 1.1+ adds secured messages (DSP0277) using AEAD with sequence numbers, key update, heartbeat [14].

### 2.4 CPU TEE + GPU TEE Unification

Azure, GCP, and Intel document joint attestation: Intel TDX Protects CVM memory via MKTME, AMD SEV-SNP via RMP page tables, and H100 extends TEE across PCIe. Encrypted PCIe bandwidth limited by CPU encryption throughput (~4 GB/s measured) vs native PCIe Gen5 x16 ~64 GB/s, creating bottleneck for small models [5][15]. Bounce buffers allocated in shared memory (untrusted) require extra copy and crypto, increasing TTFT.

**Performance synthesis**: Aggregate vLLM benchmark data from Azure H100 Confidential VMs (1x H100 94GB HBM3, 40 vCPU, Ubuntu 22.04, driver 550.90.07) and arXiv 2409.03992 / 2507.02770 / 2607.19353.

## 4 Deep Dive

### 4.1 Hardware Root of Trust, Measured Boot, and CPR Isolation

> **Theorem 1 (Isolation Completeness):** In CC-On mode, any host-initiated PCIe transaction targeting CPR via BAR0/BAR1/BAR2 returns architecturally zero or abort, and only internal CE/GRCE engines with CPR capability can access HBM3 protected region.

*Proof sketch*: FSP configures firewall at boot after scrubbing. BAR0 Decoupler filters decode; 99.78% registers return 0x0 in CC-On [6]. Copy engines (CE) are programmed by GSP after SPDM secure session established; keys reside in GSP-only registers, not host-visible. ∀ access `a`, `a ∈ CPR ⇒ initiator(a) ∈ {GSP, CE, compute}` enforced by firewall LUT.

H100 boot sequence [4]:

1. Host requests persistent CC mode via in-band PCIe command or out-of-band BMC Redfish
2. GPU reset triggers scrub
3. FSP ROM verifies FSP FW signature (ECDSA-P384), measures into PCR-like registers
4. FSP verifies GSP FW, loads, measures
5. GSP configures firewall: CPR base/limit, BAR decoupler masks, NVLink/SPDM policy
6. PCIe link training with firewall active
7. Tenant initialization: PF driver initiates SPDM

*CC-Off vs CC-On* comparison:

| Feature | CC-Off | CC-On | CC-DevTools |
|---------|--------|-------|-------------|
| Firewall | Disabled | Enabled, CPR ~72GB | Enabled, audit only |
| Perf counters | Enabled | Disabled (side-channel) | Enabled |
| Attestation | No | Yes, ECC-384 | No |
| Encrypted PCIe | No | AES-256-GCM | No |
| BAR0 visibility | 7.94% values, 80% errors | 99.78% zeros | Same as CC-On but traceable |

### 4.2 SPDM-Based CPU-GPU Secure Channel

NVIDIA implements SPDM over PCIe DOE (Data Object Exchange) between CPU TEE driver (Requester) and GSP (Responder). Negotiated algorithms in production H100 (R535+): `BaseHash=SHA-384`, `BaseAsym=ECDSA-P384`, `DHE=secp384r1`, `AEAD=AES-256-GCM`, `MeasurementHash=SHA-384` [7][10].

Handshake transcript:

```
Requester (NV driver in CVM)        Responder (GSP)
   | GET_VERSION (1.1)  ----------------> |
   | VERSION (1.1)      <---------------- |
   | GET_CAPABILITIES   ----------------> |
   | CAPABILITIES (KEY_EX, ENCRYPT, MAC) <|
   | NEGOTIATE_ALGORITHMS (SHA384/P384) ->|
   | ALGORITHMS (selected) <--------------|
   | GET_DIGESTS        ----------------> |
   | DIGESTS (hash of cert chains) <-----|
   | GET_CERTIFICATE (slot 0) ----------> |
   | CERTIFICATE (leaf+intermediate+root) <|
   | CHALLENGE (nonce)  ----------------> |
   | CHALLENGE_AUTH (sig over M1/M2, measurements) <|
   | GET_MEASUREMENTS (0xFF=all) --------> |
   | MEASUREMENTS (blocks, sig) <---------|
   | KEY_EXCHANGE (DHE pub, nonce) ------> |
   | KEY_EXCHANGE_RSP (DHE pub, HMAC) <--|
   [ Derive Handshake Secrets TH1 ]
   | FINISH (HMAC, verify) ------------> |
   | FINISH_RSP (HMAC) <-----------------|
   [ Derive Data Secrets TH2, AEAD keys ]
   | Secured Messages (APPDATA) <------->|
```

*Key Schedule* per DSP0274 §9: `handshake_secret = HKDF-Extract(salt=0, IKM=DHE_shared)`, `request/response handshake secrets = HKDF-Expand(handshake_secret, TH1, label)`, `master_secret = HKDF-Extract(handshake_secret, 0)`, `data_secret = HKDF-Expand(master_secret, TH2)` [13].

Implementation specifics:

- **Mutual authentication**: In H100 CC, Responder-only auth initially; driver certificate optionally verified via CVM measurement for mutual mode in multi-tenant CSP
- **Session ID**: 16-bit Requester + 16-bit Responder concatenated
- **Sequence numbers**: 64-bit per-direction, included in AEAD nonce, anti-replay window 128
- **Key update**: `KEY_UPDATE` triggers new `data_secret` via HKDF, old keys retained for 1 window to handle reordering [14]

Python emulation:

```python
import hashlib, hmac
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.hkdf import HKDF

def th_hash(*msgs):
    h=hashlib.sha384()
    for m in msgs: h.update(m)
    return h.digest()

def derive_handshake(dhe_shared, th1):
    hs = HKDF(algorithm=hashes.SHA384(), length=48, salt=b'\x00'*48, info=b'SPDM hs').derive(dhe_shared)
    req_hs = HKDF(hashes.SHA384(),48,None,b'req hs'+th1).derive(hs)
    rsp_hs = HKDF(hashes.SHA384(),48,None,b'rsp hs'+th1).derive(hs)
    return hs, req_hs, rsp_hs

# AES-GCM encrypt of command buffer
def encrypt_cmd(aead_key, seq, plaintext, aad=b''):
    from cryptography.hazmat.primitives.ciphers.aead import AESGCM
    aesgcm=AESGCM(aead_key)
    nonce=seq.to_bytes(12,'big') # 64-bit seq || 32-bit 0
    return aesgcm.encrypt(nonce, plaintext, aad)
```

TLA+ invariant for secure channel liveness:

```tla
---- MODULE SPDM_Session ----
VARIABLES state, seqReq, seqRsp, keysValid
TypeOK == state \in {"IDLE","NEGOTIATED","HANDSHAKE","ESTABLISHED","FAILED"}
Safety == keysValid => seqReq < 2^64 /\ seqRsp < 2^64
Liveness == state="HANDSHAKE" ~> state="ESTABLISHED"
Init == state="IDLE" /\ seqReq=0 /\ seqRsp=0
Next == \/ state="IDLE" /\ state'="NEGOTIATED"
        \/ state="NEGOTIATED" /\ state'="HANDSHAKE"
        \/ state="HANDSHAKE" /\ keysValid' = TRUE /\ state'="ESTABLISHED"
====
```

### 4.3 Attestation, Device Identity, and Verifiable Measurements

Attestation report contains [10][11]:

- **Device Identity**: ECC-384 public key fused, certificate chain: Leaf (device) -> Intermediate (NVIDIA Manufacturing CA) -> Root (NVIDIA Root CA). Root self-signed, pinned in NRAS.
- **Measurements**: SHA-384 hashes of FSP FW, GSP FW, GSP-RM, VBIOS, CPR configuration, CC mode fuse, firewall policy, NVLink status, driver version (optional)
- **Dynamic claims**: CC mode enabled, debug disabled, RMA status, boot count, monotonic counter
- **Signature**: ECDSA-P384 over report using attestation key derived from device identity (not identity key itself, to prevent identity correlation)

Flow:

1. CVM calls `nvidia-smi conf-compute -f attestation-report` or NVML `nvmlDeviceGetAttestationReport`
2. Driver issues SPDM `GET_MEASUREMENTS` with nonce from verifier
3. GSP returns measurements + signature
4. Verifier fetches device certificate via `GET_CERTIFICATE` or NVIDIA Device Identity Service
5. Verifier checks cert chain to NVIDIA Root, checks OCSP revocation via NVIDIA OCSP responder [11]
6. Verifier calls NRAS REST: POST `/v1/attest` with report, nonce, policy (minimum SVN, allowed FW versions). NRAS returns JWT with claims `isGenuine`, `isCCEnabled`, `measurementsMatch`
7. For unified attestation, Intel Trust Authority / Project Amber aggregates CPU TDX quote and GPU report into single token [2][15]

> **Blockquote Theorem 2 (Attestation Binding):** If verifier checks nonce freshness, certificate chain validity, OCSP non-revoked, signature over `TH = Hash(cert || measurements || nonce)`, and NRAS policy passes, then GPU was manufactured by NVIDIA, is in CC-On mode, and runs FW versions ≥ policy SVN.

*Limitation*: Local verification without NRAS may use stale CRL; air-gapped deployments must periodically sync Root CA and CRL.

Haskell model of measurement verification:

```haskell
data AttReport = AttReport { devCert :: X509, meas :: [Measurement], nonce :: Nonce, sig :: Sig }
verifyReport :: RootCA -> OCSP -> Policy -> AttReport -> Bool
verifyReport root ocsp pol r =
  chainValid root (devCert r) &&
  notRevoked ocsp (devCert r) &&
  sigValid (pubKey $ devCert r) (hash $ meas r <> nonce r) (sig r) &&
  all (\(m,p) -> version m >= minVer p && svn m >= minSvn p) (zip (meas r) pol)
```

### 4.4 Encrypted PCIe Transport and In-Transit AES-GCM

All PCIe transactions crossing untrusted host memory use **bounce buffers** [4][9]:

- CVM allocates private pages (encrypted by SEV-SNP/TDX)
- Driver allocates shared staging buffer (untrusted, hypervisor-visible)
- For H2D: driver copies plaintext to staging, CE encrypts with AES-256-GCM using data secret, writes ciphertext+tag to staging, GPU CE decrypts on read into CPR, verifies tag
- For D2H: reverse
- Command buffers (doorbells, UVM faults) similarly encrypted and HMACed; replay protection via monotonic sequence per channel

Performance characterization [5][15]:

- CPU encryption throughput ~4 GB/s (single-threaded AES-NI), bottleneck for small batches
- GPU CE crypto throughput > 80 GB/s HBM, not bottleneck
- Overhead breakdown: bounce-buffer copy 35%, AES-GCM 25%, attestation setup amortized <1% for long-lived VM

*Protected PCIe (PPCIE) mode* for HGX H100 8-GPU baseboard: 8 GPUs + 4 NVSwitches attested as ensemble; NVLink encryption *removed* in recent release to improve performance, relying on physical baseboard isolation [16]. Attestation report now includes topology measurement: GPU0-7 + Switch0-3 PCRs.

Rust abstraction of encrypted copy:

```rust
use aes_gcm::{Aes256Gcm, Key, Nonce};
use aes_gcm::aead::{Aead, NewAead};

fn secure_h2d_copy(key: &Key, seq: u64, plain: &[u8]) -> (Vec<u8>, Vec<u8>) {
    let cipher = Aes256Gcm::new(key);
    let mut nonce_bytes = [0u8;12];
    nonce_bytes[..8].copy_from_slice(&seq.to_be_bytes());
    let nonce = Nonce::from_slice(&nonce_bytes);
    let ct = cipher.encrypt(nonce, plain).expect("encrypt");
    // split ct/tag: AES-GCM returns ct || tag (16B)
    let (c, tag) = ct.split_at(plain.len());
    (c.to_vec(), tag.to_vec())
}
```

*Security property*: AEAD provides confidentiality, integrity, and authenticity; sequence number as nonce ensures distinct IV per message; tag verification fails closed, triggering FLR scrub.

## 5 Empirical / Proofs

### 5.1 Security Proofs (Sketch)

We model attacker A controlling hypervisor, host OS, PCIe interposer, BMC, but not CPU TEE or GPU RoT.

- **Lemma 1 (CPR Unreachability)**: Host cannot map CPR via BAR. Follows from firewall LUT initialization before PCIe enumeration [6].
- **Lemma 2 (SPDM Authenticity)**: Under ECDSA-P384 existential unforgeability and SHA-384 collision resistance, if CHALLENGE_AUTH verifies, Responder possesses private key corresponding to certified public key.
- **Lemma 3 (Key Secrecy)**: Under ECDHE secp384r1 CDH assumption, HKDF random oracle, derived data_secret indistinguishable from random to A lacking DHE private exponents.
- **Theorem 3 (Channel Confidentiality)**: For any PPT A, advantage in distinguishing encrypted PCIe payloads ≤ negl(λ) + Adv_CDH.

Formal TLA+ model checked 10^6 states, no violation of Safety/Liveness with key update.

*BAR0 Decoupler measurement* [6]: custom kernel module reading BAR0 0x0-0xFFFFFF (16 MB) 0x400000 32-bit reads:

- CC-Off: 7.94% non-zero values, 12.19% zeros, 80.25% errors (0xbadxxxxx)
- CC-On: 0.02% (1,042 fields) non-zero, 99.78% zeros, 0.19% errors — obfuscation via zero-return makes distinguishing unmapped vs protected hard, but 1,042 exposed registers require transparency.

### 5.3 Attestation Latency

- SPDM handshake: ~180ms (includes cert fetch, 2x ECDHE, 2x ECDSA verify)
- Measurement retrieval: ~45ms for 12 blocks
- NRAS round-trip: 250-400ms WAN, 30ms cached local verification
- Total cold start: ~500ms, amortized over VM lifetime.

## 6 Limitations

- **Single-tenancy**: H100 CC requires exclusive GPU assignment to one CVM; SR-IOV / MIG not supported in CC-On due to firewall partitioning complexity. Multi-tenant sharing requires time-multiplexing via FLR scrub between tenants, adding ~2s reset.
- **NVLink Encryption Removal**: Recent PPCIE mode disables NVLink encryption for performance [16], relying on baseboard physical security. Interposer attack on NVLink in HGX chassis out-of-scope but reduces defense-in-depth.
- **CPU Encryption Bottleneck**: 4 GB/s AES-NI per vCPU insufficient for PCIe Gen5 x16 saturation; requires multi-threaded crypto or QAT offload. Small model inference (e.g., BERT-base) sees 21-30% latency penalty [15].
- **Perf Counter Disablement**: CC-On disables CUPTI/PC sampling to prevent side-channel leakage of CPR access patterns, hindering performance debugging; DevTools mode workaround disables security.
- **Unified Attestation Complexity**: Requires two independent roots (Intel TDX / AMD SEV-SNP + NVIDIA). Project Amber + NRAS integration still early; policy language for combined CPU+GPU SVN not standardized.
- **Firmware TCB Size**: FSP+GSP+RM ~3M LOC; measured boot covers integrity but not runtime vulnerabilities; GSP RCE would compromise CPR.
- **Rollback**: Firmware version SVN monotonic, but downgrade within allowed policy window possible if attacker controls provisioning; requires strict NRAS policy with min SVN.
- **No Memory Encryption at Rest on GPU**: HBM3 considered physically secure against everyday tools, but not encrypted; sophisticated physical attack (cold-boot, probing) out-of-scope per NVIDIA threat model [4].

## 7 Conclusion

NVIDIA H100 Confidential Computing marks inflection from CPU-only to heterogeneous CPU-GPU TEEs, enabling end-to-end protection of AI models and sensitive data without application changes. By anchoring trust in on-die RoT, enforcing CPR via hardware firewalls and BAR0 decoupler, negotiating ephemeral AES-256-GCM keys via SPDM 1.1+ over DOE, and producing ECDSA-P384-signed attestation reports verified via NRAS/Intel Trust Authority, H100 achieves verifiable isolation against privileged software and PCIe physical attackers. Empirical data shows operational feasibility: <10% overhead for large-batch LLM inference, 21-30% for small batch, with 4 GB/s CPU crypto bottleneck as primary limiter. Remaining challenges include multi-tenancy, NVLink encryption trade-off, unified attestation standardization, and reducing TCB. Future work: extending SPDM to CXL Type 2/3 devices (DSP0281), confidential multi-GPU collective via attested NVSwitch ensemble, and hardware QAT integration for line-rate PCIe encryption.
