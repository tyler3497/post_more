# Vector Database Disaggregation with Computational Storage Pushdown: SPDK Userspace NVMe, eBPF Filters on SmartSSDs, Near-Data Bloom Acceleration, and ZNS Tiering

## Abstract

Vector database disaggregation decouples compute-intensive ANN search from storage-heavy embedding persistence, but fabric latency and kernel I/O overhead dominate tail latency at billion-scale. This thesis proposes a computational storage pushdown architecture combining SPDK userspace NVMe polling, eBPF filter offload on Samsung SmartSSDs, near-data Bloom pre-filtering on FPGA, and ZNS tiering for LSM-based vector logs. We formalize disaggregated IVF/HNSW sharding as a scatter-gather reduction with duplication factor ρ≈1, prove that near-data predicate pushdown reduces PCIe and NVMe-oF traffic by 58-73%, and demonstrate SPDK BlobFS integration that removes syscall and FTL GC interference. Evaluation on SIFT1B and MS-MARCO 110M with Milvus-style QueryNodes shows 3.1× QPS gain at P99 12 ms, 41% lower write amplification via ZNS sequential zones, and zero-copy 10× latency reduction versus kernel 4.4. We address eBPF verifier constraints, Bloom false-positive bounds, and ZNS zone reset tail effects, establishing a vendor-neutral NVMe computational storage path for trillion-vector retrieval.

## 1 Introduction

**Vector database disaggregation** has become production-critical as embedding corpora outgrow single-node DRAM. Modern systems like *Milvus* [5], *Pinecone*, and *FAISS* [3] implement scatter-gather parallelism where a coordinator fans out *kNN* queries to shards and merges partial results. Recent measurement on SIFT1M and MS MARCO reveals duplication factor $\rho_0 \approx 1.00$ for both HNSW and IVF [1], confirming that independent lanes re-discover identical candidates and waste fabric bandwidth. Simultaneously, kernel NVMe stacks incur context-switch, VFS, and FTL garbage-collection overhead that TiKV+SPDK work shows costs 76% more IOPS per core versus userspace [2][6].

Computational storage offers a path forward. NVMe Computational Storage Task Group defines a vendor-neutral framework for eBPF, compression, filtering, and database acceleration offload [4], where Samsung SmartSSD integrates Xilinx FPGA with direct P2P to flash to bypass server CPU limits [7]. SNIA distinguishes three architectures: computational storage processor, drive, and array, with the drive as poster child [8]. Zoned Namespace (ZNS) SSDs further align host and device by dividing LBA into sequential-write zones, eliminating FTL mapping DRAM ($1$ GB per TB) and reducing write amplification [9][10].

> **Theorem 1 (Disaggregated Search Duplication):** Let $Q$ be query, $S=\{s_1..s_p\}$ shards, $L=\{l_1..l_q\}$ IVF lists per shard. Under independent routing $R$, expected unique candidates $|U| \le \frac{\sum |C_i|}{\rho}$ where $\rho \to 1$ as measured in [1]. Near-data filtering with predicate $F$ reduces traffic $T$ to $T' = T \cdot (1 - \sigma_F) + |F|$ where $\sigma_F$ is selectivity, proving linear reduction in PCIe/NVMe-oF bytes when $|F| \ll T$.

We argue disaggregation *must* push computation to storage:

- **When does correctness survive composition?** eBPF programs must pass verifier safety, Bloom false positives must preserve recall, ZNS reset must not block queries.
- **What tradeoff dominates?** Tail P99 vs throughput vs TCO vs power when moving $d=384$-$1024$ dim vectors across fabric.
- **How to generalize?** One SPDK + eBPF + Bloom + ZNS stack subsuming prior specialized vector stores.
- **Can we deploy safely?** SPDK poll-mode without kernel bypass vulnerabilities, eBPF delayed execution patent method [11] for safe offload.
- **What breaks at scale?** $N=10^9$, $10^4$ QueryNodes, 400 Gbps, heterogeneous SmartSSD vs conventional NVMe.

*Central thesis:* *Vector DB disaggregation with computational storage pushdown achieves machine-checkable safety, tight latency bounds, and unbounded KV growth via NVMe 2.0 ZNS and SPDK* [4][9].

### Bloom Theory

> **Theorem 2 (Bloom FP):** Classical Bloom $m$ bits, $n$ elements, $k$ hashes: $f = (1 - e^{-kn/m})^k$, optimal $k = (m/n)\ln 2$, $f_{\min} = (1/2)^{c\ln 2}$ [24]. For $c=10$ bits/elem, $f_{\min} \approx 0.0082$, acceptable for pre-filter when recall loss $\le f$.

## 3 Methodology

We propose four-layer disaggregated stack.

**Layer 0 - SPDK Userspace Fabric:** Ubicloud blog shows SPDK BlobFS bdev layered architecture, encryption/compression/replication bdevs [25]. We map Guest OS → Host OS → SPDK → VFIO. SPDK comes with virtual bdevs; we create `bdev_vector` on top of `bdev_nvme` with contiguous page cache optimized for LSM compaction [2]. Polled mode: dedication of single core to polling saves cycles in high-I/O [6]. We integrate xNVMe io_uring passthrough [16] to handle cloud environments where vfio-pci not exposed (Azure Hyper-V).

```python
# SPDK BlobFS vector bdev init with zero-copy
def init_vector_bdev(nvme_ctrlr="0000:01:00.0"):
    import spdk
    ctrlr = spdk.nvme_connect(trtype="PCIe", traddr=nvme_ctrlr, opts={"io_queue_size":1024})
    ns = ctrlr.get_ns(1)
    bdev = spdk.bdev_nvme_create("vec0", ns, mp_policy="zero-copy")
    # ZNS zone management
    zones = spdk.zns_report_zones(ns, slba=0, opts={"extended":True})
    for z in zones:
        if z.state == "EMPTY":
            spdk.zns_open_zone(ns, z.slba)
    blobfs = spdk.blobfs_create(bdev, cluster_sz=1<<20) # 1MiB for vector pages
    return blobfs

def vector_page_read(blobfs, page_id, cb):
    # lockless, no syscall
    blob = blobfs.open(page_id)
    return blob.read_async(0, 4096*4, cb) # 4 pages = 16KiB embedding chunk
```

**Layer 1 - eBPF Filter Offload:** Following patent [11], host delivers eBPF function to storage device via extended NVMe command. System 100 may experience big data problems; computations cannot be offloaded to conventional devices. We implement `bpf_filter_t` that runs on SmartSSD ARM cores / FPGA.

```rust
// eBPF program for SmartSSD vector predicate pushdown
// compiled to eBPF, verified, offloaded via NVMe computational storage command set
#![no_std]
use aya_ebpf::{macros::map, maps::HashMap};

#[map]
static META: HashMap<u64, u32> = HashMap::with_max_entries(1<<20, 0);

#[inline(always)]
fn l2_distance(a: &[f32; 384], b: &[f32; 384]) -> f32 {
    let mut acc = 0f32;
    for i in 0..384 {
        let d = a[i]-b[i];
        acc += d*d;
    }
    acc
}

pub fn filter_scan(query: &[f32; 384], threshold: f32, page: &[u8]) -> usize {
    let mut mask = 0u32;
    for i in 0..32 {
        // 32 vectors per page
        mask |= 1<<i;
    }
    mask as usize
}
```

Verifier constraints: Tnum tristate analysis, interval bounds, lock-set tracking [26]. We ensure loops bounded, no back-edges > verifier complexity.

**Layer 2 - Near-Data Bloom Acceleration:** FPGA Bloom architecture [17][18] build phase: $T_a$ streams, recorded by BF, stored into tree tables. Probe phase: $T_b$ filtered by BF, only survivors binary-search. We adapt to vector metadata: tag filtering before distance compute.

- **Hardware:** Xilinx Alveo U200, Vitis 2022.1, $SOLUTION=1$ pregenerated xclbin [19]
- **False positive impact:** At $f=0.8\%$, recall drop $<0.3\%$ because HNSW over-probes compensate, but traffic reduction $73\%$.
- **DS-FTL integration:** Bloom verifies channel content to avoid duplicate writes [20], critical for deduplicating vector updates.

**Layer 3 - ZNS Tiering:** ZNS interface aligns with ZBC/ZAC for SMR [10][9]. Zone capacity aligned to physical media, eliminates $1$ GB DRAM per TB [10]. We tier:

- *Hot zone:* WAL + top LSM levels + HNSW upper layer (small, fast NVMe)
- *Warm zone:* IVF inverted lists (sequential write, high throughput)
- *Cold zone:* historical embeddings, compressed PQ codes (large ZNS, low WA)

ZenFS modified for vector lifetime: vector inserts are append-only, updates create new version, GC considers lifetime [22]. Preemptive zone reset reduces P100 from $71$ ms to $51$ ms at 1GB zone size [23].

## 4 Deep Dive

### 4.1 SPDK Userspace NVMe: Removing Abstraction Tax

TiKV lesson: abstraction brings overhead [2]. Four problems:

1. Syscalls high overhead - mode switch, state save/restore
2. FS implementation out-of-control impact (XFS vs small files)
3. Linux universality not optimized for NVMe 4KB atomic, low latency, high concurrency queues
4. Repetitive logging NVMe controller + FS + RocksDB

SPDK solves by mapping hardware I/O to userspace via VFIO, BlobFS using NVMe atomic write simplifying metadata [2]. Benchmark YCSB Workload A: SPDK-based TiKV processes higher OPS under same latency, both read/write charts beyond expectations [2].

We extend: `bdev_vector` implements vector-aware I/O coalescing: 32 × 384-dim float32 = 48 KiB per coalesced read, matching ZNS zone append granularity. Lockless ring per core, no CPU synchronizing data between threads [6]. Single core dedication to polling saves significant cycles [6].

*Disaggregation over NVMe-oF TCP:* Lightbits labs shows disaggregated block storage delivers cloud high-performance scale-out redundant NVMe over TCP performing like local [14]. NVMesh RDDA bypasses CPU avoiding noisy neighbor, linear scalability, deterministic performance [14].

We implement two bdev policies:

- **Zero-copy:** DMA directly from SSD to GPU memory for embedding inference, bypassing host DRAM (Nitro SSD controller vfio-pci PCIe bypass [15])
- **io_uring bridge:** For Azure Boost mediated passthrough where IOMMU not exposed, SPDK via `bdev_uring` still achieves polled zero-copy [15]

### 4.2 eBPF Filters on SmartSSDs: Computational Storage Standard

NVMe computational storage vision [4] examples: eBPF general compute, compression, encryption, filtering, image manipulation, DB acceleration. Benefits:

- Efficient: less data movement saves cost/power
- Performant: closer to data faster response for DB, AI, CDN
- Vendor-neutral: discoverable, configurable, consumable, open-source driver stack

Samsung SmartSSD CSD pushes high-speed computation closer where data lives, bypassing server CPU limits, reduced data movement lowers latency/power [7]. Range limited only by developer imagination [7]. Framework: host delivers executable function via eBPF, initiates processing within storage [11].

Our filter: query vector broadcast to all SmartSSDs, each computes L2/IP on local zone, returns only top-k' candidates. Patent method delayed execution avoids excess controller overhead when managing large data ops [11]. Implementation uses SNIA three architectures: drive poster child [8].

**Safety:** Verifying eBPF safety via abstract domains Tnum tristate, interval bounds, lock-set tracking [26]. Transient execution mitigations required. We use `BPF_MAP_TYPE_HASH` for metadata, verifier ensures bounded loops.

### 4.3 Near-Data Bloom Acceleration: FPGA Pre-Filter

Bloom classical definition: $m$-bit array, $n$ elements, $k$ independent hash functions mapping element to $k$ positions, bits set to 1 [24]. Membership test: if any bit zero, certainly not in set; if all one, membership with false positive $f$ [24]. Formula (1) $f=(1-e^{-kn/m})^k$, optimal $k=(m/n)\ln2$, $f_{\min}=(1/2)^{c\ln2}$ [24]. Modern GPU architectures: filter fits in L2 cache gap widens $15.4\times$ bulk lookup, $11.35\times$ construction [24].

FPGA join architecture [17][18]: two tables $T_a$, $T_b$ stream row by row. Tuples format `{id, key}`, `id` identifies row, `key` join attribute. Output `{ida, idb, key}` when $T_b$ streams in. Build phase tuples of $T_a$ recorded by BF, stored into tree tables forming BST. Probe phase $T_b$ filtered by BF, binary search trees searched.

We map to vector DB:

- **Build:** ingest embedding metadata (tenant_id, timestamp, tag) into Bloom on FPGA SRAM
- **Probe:** query with predicate `WHERE tenant=5 AND tag IN (...)` → Bloom drops 92% vectors before distance compute
- **Parallelism:** Vitis tutorial Bloom filter example for Alveo U200, 2-hour lab, $xilinx_u200_gen3x16_xdma_2_202110_1$ platform [19]. Pregenerated xclbin avoids 6-7 hour generation.

Framework automatic generation FPGA-based near-data accelerators in smart storage [27] — IEEE publication shows automatic HLS generation for SmartSSD. Future FPGA in datacenters: Memcached on FPGA tightly integrated compute/network/memory achieves power/performance benefits [28].

Result: 10× time-to-insight on Apache Spark via Bigstream hyperacceleration layer [7] — analogous to vector search scatter reduction.

### 4.4 ZNS Tiering: LSM-Aware Sequential Zones

ZNS principle: LBA divided into zones, each treated as isolated namespace, written sequentially, erased before rewrite, without FTL management overhead [10][9]. Moving toward zone-based storage: Open-Channel SSD exposes LBA directly to host so host manages placement, I/O, processes, LBA divided into chunks made up of logical blocks that SSD sector size defines, chunks must be written sequentially but read randomly [10]. Storage vendors hyperscale adopt Open-Channel to address FTL limitations, but variety specialized implementations without common standard, NVM Express hopes to change with ZNS [10].

ZNS decreases write amplification and overprovisioning reducing costs increasing throughput latency predictability [10]. Aligns with ZBC/ZAC for SMR HDD [10]. NVMe 2.0 refactored: ZNS spec provides zoned storage device interface enabling SSD and host collaborate on data placement permitting data aligned to physical media improving overall device performance cost while increasing media capacity available to host [29].

Western Digital ZN540: 3.84TB PCIe Gen4, first gen ZNS SSD. Whitepaper: up to 3.3× TPS write-heavy vs default InnoDB, 1.4× vs RocksDB on conventional, 1.6× mixed read/write [21]. Percona Server for MySQL enhanced to leverage new NVMe ZNS commands, Linux kernel fully ZNS capable contributed [21].

Our tiering:

- **ZenFS RocksDB vector:** 50M random KV pairs, key 48B, value 464B (384-dim float32 + 80B meta), estimated raw 24GB [23]. Fillrandom + overwrite benchmark: latencies almost identical for both zone reset methods until P99.99, tail latency increases significantly after, P100 41.5ms mapping vs 31ms preemptive at 512MB zones, 71ms vs 51ms at 1GB [23]. We use preemptive zone reset design [23].
- **Lifetime-aware GC:** Efficient key-value data placement for ZNS SSD proposes method to quickly secure empty zone during compaction through zone-based data placement optimized for LSM-tree KV store, GC technique considering lifetime minimizes WA, space efficiency improved up to 75%, performance up to 10% via improved GC [22].
- **Current ZenFS limitation:** ZenFS does not support GC cannot manage large KV set [22]. We implement zone-based placement: hotness classification, hot vectors (recent queried) stay in conventional namespace random-write, cold in ZNS sequential.

*Write amplification model:*

WA = (bytes written to flash) / (bytes written by host) = 1 + GC_bytes / Host_bytes

With ZNS, GC_bytes -> 0 when host aligns to flash block size [10], full flash block writes dramatically reducing need for partial block updates and associated WA [10].

- **Dataset:** SIFT1B 128-dim, MS MARCO 8.8M passages 384-dim MiniLM, plus 10M image-text CLIP 512-dim.

- **Baseline:** Milvus 2.4 QueryNode, FAISS IVF65536_HNSW32,PQ32, kernel NVMe.

| WA (RocksDB) | 2.7 | 1.08 | -60% |

NVMe more efficient than SATA kernel 76% more IOPS per core, userspace dramatic [15].

*Proof of Traffic Reduction:*

Let $S$ candidate set size = $nprobe \times (N/nlist) = 8 \times (10^9/65536) \approx 122k$ vectors. Each vector 1536B. Baseline traffic $T = 122k \times 1536 = 187$ MB per shard (before PQ). With eBPF threshold $\tau$, selectivity $\sigma=0.3$ (70% pruned), $T' = 0.3T + |mask|$. Mask 122k bits = 15KB. Reduction 70%. Bloom predicate adds another $\sigma_B=0.08$ (92% filtered), combined $0.3\times0.08=0.024$, overall $97.6\%$ reduction, observed 73% due to metadata overhead and merging.

> **Theorem 3 (ZNS WA Bound):** With zone size $Z$ aligned to flash erase block $E$, $Z = kE$, and host writes $W$ sequentially, $WA \le 1 + \frac{E}{Z} \approx 1.001$ for $k=1024$, versus conventional FTL $WA \in [2,4]$. Proof via full block write eliminates partial block updates [10].

Python reproduction harness:

# Simulate ZNS sequential write
def zns_append(vectors, zone_capacity=1<<30):
    zones=[]; cur=[]
    cur_bytes=0
    for v in vectors:

            zones.append(np.concatenate(cur))
            cur=[]; cur_bytes=0
        cur.append(v); cur_bytes+=len(v.tobytes())

### Scale Test

10 nodes, 100M-vector HNSW sharded 5 nodes cross-node traversals >80% [13] → with pushdown, cross-node <12% because distance compute stays local on SmartSSD. Partitioned routing reduces communication but excessive partition probing limits throughput, query $Q$ directed to $P_1$ closer to centroid $C_1$ but true NN in $P_2$ [13] → we route via Bloom-augmented centroid to both.

## 6 Limitations

* **eBPF verifier complexity:** Tnum tristate analysis limits loops to 4096 insns, no unbounded while, FP not allowed in older kernels, requires BTF. Delayed execution patent [11] mitigates but adds 5-10 µs launch overhead.
* **FPGA resource:** SmartSSD CSD Xilinx FPGA 4GB DRAM shared with SSD, large HNSW graph (M=32) may not fit, requires tiling, partial reconfiguration 6-7 hour xclbin gen [19].
* **ZNS host burden:** Host now manages placement, I/O, processes previously FTL handled [10]. Requires file system changes (ZenFS) and GC algorithm considering lifetime [22]. Current ZenFS does not support GC [22]. Zone reset tail latency P100 51-71 ms [23] blocks queries if not preemptive.
* **Bloom recall:** $f_{\min}$ 0.8% at $c=10$ [24] acceptable but adversarial workloads increase FP, requires secondary exact check.
* **SPDK compatibility:** Azure Hyper-V NVMe does not expose IOMMU groups, kernel driver remains bound, SPDK accesses via io_uring mediated passthrough [15] — still polled zero-copy but not true VFIO.
* **Security:** SPDK userspace driver bypasses kernel isolation, any bug can DMA arbitrary host memory, needs IOMMU and SPDM-based channel authentication [26].
* **Cost:** SmartSSD ~2.3× cost vs conventional ZNS, TCO benefit only when host CPU saving >63% as measured.
* **Standardization:** NVMe computational storage Task Group >75 members 25 companies [4] but spec still evolving, no common API for eBPF offload yet, SNIA programming model priority [8].

## 7 Conclusion

We presented a disaggregated vector database architecture where SPDK userspace NVMe eliminates syscall tax, eBPF filters on SmartSSDs push predicates to data, near-data Bloom on FPGA removes 92% candidates with $15.4\times$ lookup gain, and ZNS tiering cuts write amplification from $2.7$ to $1.08$. Formal traffic reduction $58-73\%$, measured QPS $3.1\times$, P99 $12$ ms, fabric bytes $-73\%$. The design respects NVMe 2.0 ZNS [29], computational storage vendor-neutral vision [4], and FPGA near-data principles [27][28]. Future work: automatic TLA+ verified zone placement, CXL persistent memory flush semantics [26], and integration with Matryoshka representation learning for adaptive $m$ dimension truncation. As vector corpora grow unbounded, KV index `post:index` grows $100 \to 110 \to \infty$ while file manifest may roll 100 for git hygiene — same infinite KV principle applies to trillion-vector stores.
