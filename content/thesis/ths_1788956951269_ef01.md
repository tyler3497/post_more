# The Polyhedral Compilation Model: Affine Scheduling via the Farkas Lemma, Dependence Analysis, and Code Generation from Pluto to ISL for Loop-Nest Optimization

## Abstract

The polyhedral compilation model recasts loop-nest execution as geometry: each dynamic statement instance becomes an integer point in a parametric polytope, each data dependence an affine map between polytopes, and each legal transformation an affine schedule respecting lexicographic positivity. This thesis reconstructs the full pipeline, from Paul Feautrier's affine scheduling theory [1] — which reduces the search for valid multidimensional schedules to linear programming over the Farkas image of dependence polyhedra — through Uday Bondhugula's Pluto system [2], which made polyhedral optimization practical by formulating tiling, fusion, and parallelization as one integer linear program, to Sven Verdoolaege's integer set library (isl) [3], supplying exact integer arithmetic, schedule trees, and AST generation used by LLVM's Polly and GCC's Graphite. We derive the affine Farkas lemma, present Pluto's cost model, detail isl schedule-tree code generation, and evaluate against the PolyBench/C suite [4], where end-to-end systems report multi-fold multicore speedups [2], closing with the model's expressive limits.

## 1 Introduction

Optimizing compilers have long treated the loop nest as the decisive battlefield of program performance. Between 50% and 90% of execution time in scientific, signal-processing, and increasingly machine-learning workloads is consumed by regular loop nests whose control flow is *static* — loop bounds and array subscripts are affine functions of enclosing iterators and symbolic constants. For such *static control parts* (SCoPs), the polyhedral model offers something no peephole or pattern-based optimizer can: a mathematically complete characterization of *all* semantics-preserving re-executions of the loop nest as affine functions over integer points.

The intellectual spine of the model is Paul Feautrier's affine scheduling theory, developed across two landmark 1992 papers on one-dimensional and multidimensional affine schedules [1]. Feautrier's decisive insight was that the validity condition for a candidate schedule — that every dependence is carried forward in time — is an affine implication over a dependence polyhedron, and that the *affine form of Farkas' lemma* converts such universal implications over parametric polyhedra into finitely many linear constraints on the schedule coefficients. Scheduling thereby becomes linear programming: exact, decidable, and optimal with respect to any linear objective.

For fifteen years this theory remained largely academic, because three gaps blocked practice: (i) dependence polyhedra must be computed *exactly* (an approximation forfeits the precision the theory buys); (ii) the schedule space must be searched with a cost model that simultaneously serves locality, parallelism, and fusion; and (iii) the computed schedule must be turned back into executable code — the *code generation* problem, itself nontrivial. Uday Bondhugula's Pluto system closed these gaps in a single end-to-end framework [2], winning the 2018 ACM SIGPLAN Most Influential Paper Award: an integer-linear-programming formulation that finds tilings for locality and parallelism together, implemented as a source-to-source tool emitting OpenMP code. In parallel, Sven Verdoolaege's integer set library (isl) [3] supplied the exact integer-arithmetic substrate — sets and relations of integer points bounded by affine constraints, manipulated in exact arithmetic via GMP — that underpins LLVM's Polly, GCC's Graphite, and the PPCG GPU compiler. Louis-Noël Pouchet's PolyBench/C suite [4] finally gave the community a shared empirical yardstick.

This thesis reconstructs the entire arc — theory, dependence analysis, scheduling algorithm, and code generation — as one coherent mathematical narrative, and evaluates it against published empirical evidence.

## 2 Background

### 2.1 Static control parts and iteration domains

A *static control part* (SCoP) is a maximal program region in which control flow depends only on affine conditions over loop iterators and symbolic parameters (structure parameters such as `N`, `M`), and in which all array accesses are affine functions of those quantities. Within a SCoP, each syntactic statement `S` is executed once per point of its *iteration domain*:

$$\mathcal{D}_S = \{\, (i_1, \dots, i_d) \in \mathbb{Z}^d \mid A_S \cdot \vec{\imath} + B_S \cdot \vec{p} + \vec{c}_S \ge \vec{0} \,\}$$

a parametric (rational) polytope — the intersection of half-spaces defined by the loop bounds. For the canonical doubly-nested loop `for (i=0; i<N; i++) for (j=0; j<N; j++) S(i,j)`, the domain is the integer points of the triangle $0 \le j \le i < N$. Every dynamic instance of `S` is thus an *integer point*; the whole execution is a finite set of such points. This geometrization is the model's founding move: control flow becomes convex geometry, and program transformations become affine maps.

Dependences are captured equally geometrically. A *dependence polyhedron* $\mathcal{P}_{S \to T}$ relates source instances $\vec{\imath} \in \mathcal{D}_S$ to sink instances $\vec{\jmath} \in \mathcal{D}_T$ via affine access functions $F_S, F_T$ and an equality $F_S(\vec{\imath}) = F_T(\vec{\jmath})$ over a shared memory cell, conjoined with the domains and (for exactness) the *last-write* condition that no intermediate instance overwrites the cell [5]. Computing these polyhedra exactly is the business of *affine dependence analysis*, surveyed in the compiler literature alongside the scheduling theory it feeds [6].

### 2.2 Schedules, legality, and multidimensional time

An *affine schedule* assigns to every statement $S$ a function $\Theta_S : \mathcal{D}_S \to \mathbb{Z}^m$ of the form

$$\Theta_S(\vec{\imath}, \vec{p}) = X_S \cdot \vec{\imath} + Y_S \cdot \vec{p} + \vec{\rho}_S$$

with rational coefficient matrices $X_S, Y_S$ and offset $\vec{\rho}_S$. Executing instances in increasing lexicographic order of their timestamps reproduces a valid program *iff* every dependence is respected: for every dependence edge $e : S \to T$ and every $(\vec{\imath}, \vec{\jmath}) \in \mathcal{P}_e$,

$$\Theta_T(\vec{\jmath}) \succ_{\text{lex}} \Theta_S(\vec{\imath}).$$

Multidimensional time is essential: when no one-dimensional schedule satisfies all dependences (a *strongly connected* dependence graph, e.g. imperfectly nested recurrences), Feautrier showed that a lexicographic schedule always exists for the maximal strongly connected components, by scheduling each SCC with successively finer time dimensions [1]. The outermost constant dimensions expose *parallelism* (instances sharing a timestamp execute concurrently); inner dimensions expose *sequentiality*. Loop interchange, skewing, reversal, fusion, distribution, and tiling all emerge as special choices of the matrices $X_S$ — the model *unifies* the classical loop transformations in a single algebraic language.

## 3 Methodology

Our reconstruction follows the historical pipeline in four stages, each treated as a mathematical object with explicit inputs, outputs, and correctness obligations.

1. **Extraction.** Parse the SCoP into iteration domains $\mathcal{D}_S$ and affine access functions, using exact integer arithmetic (isl) [3].
2. **Dependence analysis.** Compute exact dependence polyhedra $\mathcal{P}_e$ (RAW, WAR, WAW) via array dataflow analysis [5].
3. **Scheduling.** Formulate the legality constraints as affine implications over the $\mathcal{P}_e$; apply the affine Farkas lemma to obtain linear constraints on schedule coefficients; solve a (integer) linear program whose objective encodes the optimization goal — minimal latency (Feautrier [1]), or Pluto's joint locality/parallelism/fusion objective [2].
4. **Code generation.** Scan the scheduled polytopes to emit loop nests: either by the classic *polyhedron scanning* approach of CLooG, or by constructing isl *schedule trees* and generating an AST [7]. Verify semantic preservation by checking that the generated schedule satisfies the legality condition on every dependence polyhedron.

> **Theorem (Feautrier legality via Farkas).** *Let $\Theta_S(\vec{x}) = X_S\vec{x} + \vec{\rho}_S$ be affine schedules with rational coefficients. Then $\Theta_T \succ_{\text{lex}} \Theta_S$ holds for all $(\vec{\imath},\vec{\jmath}) \in \mathcal{P}_e$ iff the lexicographic difference $\Delta_e(\vec{\imath},\vec{\jmath}) = \Theta_T(\vec{\jmath}) - \Theta_S(\vec{\imath})$ is lexicographically positive over the polyhedron $\mathcal{P}_e$; by the affine form of Farkas' lemma, each positivity condition is equivalent to a finite system of linear inequalities in the entries of $X_S, X_T, \vec{\rho}_S, \vec{\rho}_T$.*

The force of the theorem is that an *infinite* family of constraints (one per dependence instance, parameterized by symbolic $N$) collapses to a *finite* linear system — the Farkas multipliers $\lambda \ge 0$ become the new decision variables alongside the schedule coefficients.

## 4 Deep Dive

### 4.1 The Affine Farkas Lemma and the Feautrier Formulation

Farkas' lemma, in its affine form, states that an affine function $f(\vec{x}) = \vec{a}\cdot\vec{x} + b$ is nonnegative over a nonempty polyhedron $\mathcal{P} = \{\vec{x} \mid C\vec{x} + \vec{d} \ge 0\}$ *iff* it is a nonnegative affine combination of the defining constraints:

$$f(\vec{x}) = \lambda_0 + \sum_k \lambda_k (C_k \vec{x} + d_k), \qquad \lambda_k \ge 0.$$

Feautrier's masterstroke [1] was to apply this to the *schedule validity* implication. For a one-dimensional schedule and a dependence $e$, legality requires

$$(\vec{\imath},\vec{\jmath}) \in \mathcal{P}_e \;\Rightarrow\; \Theta_T(\vec{\jmath}) - \Theta_S(\vec{\imath}) \ge 1$$

(the "$\ge 1$" reflecting integrality of time). Both sides are affine in $(\vec{\imath}, \vec{\jmath}, \vec{p})$; by Farkas, there exist multipliers $\lambda \ge 0$ such that the difference *identically equals* a nonnegative combination of the constraints defining $\mathcal{P}_e$. Equating coefficients of $\vec{\imath}, \vec{\jmath}, \vec{p}$ and the constant term yields a linear system in $(X_S, X_T, \rho_S, \rho_T, \lambda)$. Any linear objective may then be optimized — Feautrier minimizes total latency by minimizing the *makespan* variables, computing one schedule per statement in a greedy loop over the dependence graph's SCC condensation, which he proved optimal for the chosen objective [1][5].

For multidimensional time, the construction is applied hierarchically: find the first time dimension satisfying as many dependences as possible (those it satisfies *strongly*, i.e. with strict inequality, are removed); recurse on the remainder. Each level corresponds to one loop level in the generated code, and the number of levels is bounded by the nesting depth. This greedy decomposition is the precise sense in which the polyhedral model "discovers" loop structure from dataflow alone.

### 4.2 Dependence Polyhedra and Exact Array Dataflow Analysis

Dependence analysis in the polyhedral model is not the conservative distance-vector analysis of classical vectorizing compilers; it is *exact*. For a read instance $\vec{\jmath}$ of statement $T$ accessing cell $F_T(\vec{\jmath})$, the *source* is the lexicographically maximal write instance $\vec{\imath}$ of any statement $S$ with $F_S(\vec{\imath}) = F_T(\vec{\jmath})$ preceding $\vec{\jmath}$ in the original sequential order $\prec$:

$$\text{src}(\vec{\jmath}) = \max_{\prec} \{\, \vec{\imath} \in \mathcal{D}_S \mid F_S(\vec{\imath}) = F_T(\vec{\jmath}) \,\}.$$

Feautrier's *array dataflow analysis* computes this maximum parametrically as a piecewise-affine (quasi-affine) function using parametric integer programming — exactly the operation isl implements as "lexicographic optimization" [3]. The lecture notes of Pouchet develop the same computation as the bridge between Farkas-based scheduling and practical implementation [5]. The key subtlety is the *last-write* condition: $\mathcal{P}_e$ must exclude pairs $(\vec{\imath}, \vec{\jmath})$ for which some intervening write kills the value, otherwise the schedule is constrained by phantom dependences and valid transformations are lost. Exactness here is what separates polyhedral compilers from the conservative dependence tests (GCD, Banerjee) of the 1980s [6].


### 4.3 Pluto's Cost Model: Fusion, Tiling, and Parallelism in One ILP

Feautrier's scheduler optimizes latency; Pluto [2] optimizes the *memory hierarchy*. Its central artifact is a single integer linear program whose decision variables are the schedule coefficients of every statement, and whose constraints and objective jointly encode three goals historically handled by separate passes:

- **Fusion / distribution.** Statements fused at a loop level share schedule coefficients at that level; the ILP decides fusion structure automatically by allowing or forbidding coefficient sharing, guided by a *fusion conflict graph*. Pluto's key modeling device is the *dependence distance* bound: for each dependence $e$, it introduces a variable $\phi_e$ bounding the schedule distance, $\Theta_T(\vec{\jmath}) - \Theta_S(\vec{\imath}) \le \phi_e \cdot \vec{u} + \vec{v}$, and minimizes $\sum_e \phi_e$ — small distances mean producer and consumer execute near each other in time, i.e. good temporal locality.
- **Tiling for locality and parallelism.** After the "communication-free" schedule dimensions are found, Pluto tiles the *band* of permutable loops: it computes tiling hyperplanes (linear combinations of the band's schedule dimensions) such that dependences within a band are forward and bounded, making rectangular (or diamond) tiles atomic units. Tiling is thus not a post-pass but a direct consequence of the schedule's band structure.
- **Parallelism detection.** A schedule dimension carrying no dependence (all $\Delta_e$ strictly positive along it, or vacuous) marks a *parallel loop*; Pluto emits it as an OpenMP `parallel for`. Coarse-grained parallelism falls out of the same ILP.

Concretely, Pluto minimizes a lexicographic objective: first the number of *scalar* (synchronization-carrying) dimensions, then total dependence distances $\sum_e \phi_e$, then the number of unfused statements. Solved with an off-the-shelf ILP solver (PIP), the formulation typically contains thousands of variables for real kernels yet solves in seconds — because the Farkas-derived constraint matrix is totally structured, and because Pluto prunes aggressively using the SCC condensation. The result, demonstrated on the PolyBench suite [4], was a fully automatic source-to-source tool whose output rivaled hand-tiled code [2].

### 4.4 Schedule Trees and isl: The Modern Substrate

The isl library [3] re-founded the entire stack on exact integer arithmetic and a richer intermediate representation: the *schedule tree*. A schedule tree is a tree whose leaves are statement instances (domains) and whose internal nodes are schedule operations — *domain*, *filter*, *sequence/set*, *band* (a partial schedule with coincidence and permutability annotations), *extension*, and *mark* nodes. Pluto-style scheduling maps naturally onto bands; the tree makes the schedule *compositional* and *inspectable*, and it is the representation consumed by isl's AST generator [7].

Code generation from a schedule tree proceeds in two phases [7]:

1. **Separation into atomic pieces.** Each band node is split so that every piece carries a *single* affine schedule; filters separate statements.
2. **AST construction.** For each piece, isl generates loop nests by projecting the scheduled domain onto the time dimensions — a generalization of the Quilleré–Rajopadhye–Wilde *polyhedron scanning* algorithm that avoids the exponential blowup of naive Fourier–Motzkin elimination by generating *guard-free* code where the schedule is injective, and inserting conditionals only where disjunctions are unavoidable. The output is an AST with `for`, `if`, and user nodes that backends (Polly, PPCG) lower to LLVM IR or CUDA.

A minimal illustration of the isl textual format, as consumed by the interactive `iscc` calculator, shows how naturally programs become sets:

```python
# isl-style description of a 2-D iteration domain with a dependence map
domain = "[N] -> { S[i,j] : 0 <= i < N and 0 <= j <= i }"
dep    = "[N] -> { S[i,j] -> S[i+1,j] : 0 <= i+1 < N and 0 <= j <= i }"
# a skewing schedule: t0 = i, t1 = i + j  (carries the dependence forward)
sched  = "[N] -> { S[i,j] -> [i, i+j] }"
```
## 5 Empirical Analysis and Formal Guarantees

**Correctness.** The end-to-end correctness argument composes three lemmas: (i) dependence polyhedra computed by exact array dataflow analysis contain *exactly* the true dependences (Feautrier [1], Pouchet [5]); (ii) any schedule satisfying the Farkas-derived linear system respects every dependence (Theorem, §3); (iii) polyhedron-scanning code generators emit code whose execution order coincides with the schedule's lexicographic order (Quilleré–Rajopadhye–Wilde; Grosser–Verdoolaege–Cohen [7]). Chaining them: the generated program computes the same values as the source on all inputs. This is a genuine *verified pipeline* in the mathematical sense, even though the implementations themselves are not machine-checked.

**Performance.** Bondhugula et al. evaluated Pluto on a suite of kernels drawn from dense linear algebra, stencils, and dynamic programming — the workloads that became PolyBench/C [2][4]. On an 8-core SMP of the era, Pluto-generated OpenMP code achieved speedups of **2×–10×** over Intel's ICC `-fast` and **1.5×–5×** over the best prior automatic parallelizers, with the largest gains on imperfectly nested codes (e.g. LU decomposition, Floyd–Warshall) that classical loop-nest optimizers could not restructure at all. Grosser et al.'s Polly — LLVM's isl-based polyhedral optimizer [3][7] — later reproduced comparable automatic speedups on the full PolyBench 2.0 suite, validating that the isl substrate preserved Pluto's optimization power inside a production compiler [7].

**Complexity.** Scheduling is polynomial: the Farkas formulation is an LP over $O(|E| \cdot d)$ variables, and the greedy multidimensional decomposition adds only a factor of the nesting depth [1]. Pluto's ILP is NP-hard in the worst case, but instances are small and structured; practical compile times remain in seconds [2]. Code generation is worst-case exponential in the number of disjuncts (Fourier–Motzkin projection), but the schedule-tree/AST approach of [7] is effectively linear on real codes because schedules are "close to injective."

| System | Scheduling objective | Dependence analysis | Code generation | Reported PolyBench-class speedup |
|---|---|---|---|---|
| Feautrier [1] | Minimize latency (LP) | Exact array dataflow | Sequential loop nests | Theory (optimality proof) |
| Pluto [2] | Locality + parallelism + fusion (ILP) | Exact, PolyLib-based | CLooG + OpenMP | 2×–10× vs ICC on 8 cores |
| Polly / isl [3][7] | pluto-like / isl scheduler | isl exact analysis | isl AST → LLVM IR | Significant automatic speedups [7] |

## 6 Limitations

The model's power is fenced by the *affine* restriction, and the fences are load-bearing.

1. **Non-affine control and access.** `while` loops, data-dependent branches, indirect accesses (`A[B[i]]`), and pointer-chasing structures are not SCoPs; they are invisible to the analysis. Production systems (Polly) handle them by *SCoP detection* — optimizing only the affine regions and bailing out elsewhere — which fragments optimization and can pessimize boundary code [7].
2. **Parametric complexity.** Every symbolic constant multiplies the dimension of every polyhedron; deeply parametric codes (e.g. `A[f(N,M,K)]` bounds) blow up the Farkas system and the ILP. Compile times degrade from seconds to minutes on pathological inputs [2].
3. **Objective mismatch.** Pluto's distance-minimization is a *proxy* for cache behavior, not a cache model; on architectures with hardware prefetchers or scratchpads, the ILP-optimal schedule can underperform simpler tilings. The model knows nothing of vectorization legality beyond dependence distances, and nothing of energy.
4. **Code explosion.** Generated loop nests for imperfectly nested, multi-statement SCoPs can be an order of magnitude larger than the source, stressing instruction caches and downstream compiler passes — the "code bloat" problem that isl's AST generation mitigates but does not eliminate [7].
5. **Reductions and associativity.** Reductions (`sum += A[i]`) carry loop-carried dependences that forbid parallelization unless the compiler *knows* the operator is associative/commutative — semantic knowledge outside the polyhedral abstraction. Extensions exist (e.g. reduction-aware scheduling in Polly) but remain heuristic [7].
6. **Integer vs. rational gap.** Schedules are computed over $\mathbb{Q}$ and must be integralized; the $\ge 1$ strengthening in §4.1 is sound but can exclude schedules that are valid only with rational timestamps subsequently scaled — a known, if rarely binding, incompleteness [1].

## 7 Conclusion

The polyhedral compilation model is one of the rare ideas in computer science that is simultaneously a *theorem* and a *tool*. As a theorem, Feautrier's reduction of scheduling to linear programming over Farkas images [1] gives a complete, decidable account of which re-executions of a loop nest preserve semantics — a result of genuine mathematical beauty, turning compiler correctness into convex geometry. As a tool, Pluto [2] proved that this mathematics could be made to *run*: a single ILP capturing fusion, tiling, and parallelism, emitting OpenMP code that beat production compilers on the PolyBench kernels [4] that the community still uses to measure progress. And as infrastructure, isl [3] and its schedule-tree AST generation [7] carried the model into LLVM and GCC, where it optimizes real code today.

The arc from Farkas' lemma to `isl_ast_build` is thus a case study in how deep mathematics becomes engineering: the affine implication becomes a linear constraint, the linear constraint becomes an ILP row, the ILP solution becomes a schedule tree, and the schedule tree becomes machine code — each step preserving the legality invariant established by the first. Its limitations are honest ones, drawn exactly along the boundary of what affine geometry can express. For the vast territory inside that boundary — the dense linear algebra, stencils, and tensor contractions at the heart of scientific computing and deep learning — the polyhedral model remains the most principled optimization framework compilers possess.
