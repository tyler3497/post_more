# Hardware-Enforced Control-Flow Integrity for RISC-V: Shadow Stacks, Pointer Authentication, and Compartmentalization via CHERI

## Abstract

RISC-V's open ISA has become the substrate for security experimentation, yet control-flow hijacking via Return-Oriented Programming (ROP) and Jump-Oriented Programming (JOP) remains viable in C/C++ firmware. This thesis synthesizes *three* hardware primitives ratified or prototyped for RISC-V into a unified control-flow integrity (CFI) architecture: **Zicfilp** landing pads for forward-edge protection, **Zicfiss** shadow stacks for backward-edge integrity [1][2], and **CHERI** capabilities for fine-grained compartmentalization and pointer provenance [4][5]. We analyze CVA6-CFI integration reporting 1.0% area overhead in 22 nm FDX and up to 15.6% performance overhead on MiBench automotive [1], Linux kernel enablement via `menvcfg.LPE/SSE` and software-check exception cause 18 [3], and CHERI-RISC-V capability compression and monotonicity guarantees [5]. We formalize a pointer-authentication extension using RoCC-coupled QARMA/GIFT ciphers with 1.3–5.8% SPEC CPU2017 overhead [6][7] and prove backward-edge soundness under an attacker controlling writable memory but not shadow-stack pages. The result is a layered defense that blocks ROP/JOP, limits lateral movement via compartments, and remains incrementally deployable from bare-metal Ibex to application-class CVA6 and Codasip A730 cores [4].

## 1 Introduction

Control-flow integrity aims to ensure that runtime control transfers follow the static control-flow graph (CFG). On x86, Intel CET provides a hardware shadow stack and indirect branch tracking (`endbr64`); ARMv8.3-A adds Pointer Authentication (PAC) and Branch Target Identification (BTI) [10]. RISC-V, lacking a single vendor driver, has ratified analogous primitives in 2024–2026:

- **Zicfilp** (`landing pad`): `lpad` instruction with 20-bit label checked against `x7`, ELP state machine, software-check trap on mismatch [2][3].
- **Zicfiss** (`shadow stack`): `sspush`, `sspopchk`, `ssrdp`, `ssamoswap`, SSP register, PTE encodings `W=1,R=0,X=0` for shadow pages [2][3].
- **CHERI-RISC-V**: 128-bit capabilities with tag, bounds, permissions, otype, and sentry sealing for compartment entry [4][5][6].

This thesis contributes a *unified* view: how to compose these mechanisms, what their TCB and OS requirements are, and where pointer authentication (PA) fits as a lightweight alternative to full shadow stacks on resource-constrained Ibex-class cores [6][7][8].

> **Theorem 1.1 (Backward-Edge Soundness).** Given a thread-private shadow stack with W⊕R pages writable only via `sspush`/`ssamoswap`, and `sspopchk` atomically comparing `*sp` vs `*ssp`, an attacker who can arbitrarily write normal memory cannot cause a `ret` to target an address not previously pushed by a matching `call` without raising a software-check exception (`xtval=3`).

We evaluate practical deployment paths from bare-metal to Linux, including picolibc CRT variants for `-fcf-protection=full` [3].

## 2 Background

### 2.1 Threat Model

We assume C/C++ code compiled with `-fcf-protection`, attacker with arbitrary read/write to non-shadow memory via spatial/temporal safety bug, DEP enforced (`W⊕X`), ASLR enabled, but no arbitrary code injection. Attacker goals: ROP chain via overwritten return address on stack, or JOP via corrupted function pointer.

### 2.2 RISC-V CFI Extensions

**Zicfilp** forward-edge: At indirect `jalr`, core enters ELP state; next retired instruction must be `lpad label` with label in `x7` matching `lpad` immediate, else `#3 software-check` with `tval=2` [1][2][3]. LPE bit in `menvcfg/senvcfg/henvcfg` enables the extension [3].

**Zicfiss** backward-edge: Dedicated SSP. `sspush x1` pushes `ra` onto shadow stack. `sspopchk x1` pops and checks. `ssrdp` reads SSP, `ssamoswap` atomically swaps for signal handling [2]. Linux shadows are discontiguous, marked via page-table extension, writable only via shadow instructions. Non-leaf functions save `ra` to both stacks; mismatch on `ret` raises `xtval=3` [3].

**Intel CET / ARM Comparison**: Intel CET uses a single `SSP` and transparent push/pop on `CALL/RET` [9]. ARM PAC signs pointers with QARMA in upper bits, BTI requires `bti` landing pad [10]. RISC-V's design is explicit, requiring compiler cooperation, which enables finer control but increases code size [1].

### 2.3 CHERI and Pointer Authentication

CHERI extends each 64-bit pointer to 128-bit capability with 1-bit validity tag stored out-of-band, compressed bounds, permissions, and object type [5]. Capabilities are *unforgeable*: integer-to-capability casts clear tag, monotonicity prevents privilege escalation. CHERI-RISC-V on Codasip A730 shows hybrid deployment where only TCB is pure-capability, rest hybrid [4].

Pointer Authentication for RISC-V prototypes use RoCC or Ibex custom extension: `PTR_SEAL` / `PTR_UNSEAL` or `pac`/`aut` with 128-bit key in CSRs, GIFT cipher requiring 5.6kGE vs QARMA 8.9kGE in 65 nm [6][7]. Vt prototype reports 1.3–5.8% overhead on SPEC CPU2017 and SPLASH-2 on VCU118 FPGA [6].

## 3 Methodology

We combine architectural analysis, microarchitectural integration patterns from CVA6-CFI and Ibex, and software stack analysis from Linux and picolibc.

1. **Spec Extraction**: Zicfilp/Zicfiss v1.0 ratified spec, LLVM `experimental-zicfilp/zicfiss` [8], binutils `GNU_PROPERTY_RISCV_FEATURE_1_AND` bits `CFI_LP_UNLABELED` and `CFI_SS` [3].
2. **Hardware Model**: CVA6 6-stage in-order, scoreboard/ROB, separate CFI units for forward/backward edges, 1.0% area in GF 22FDX [1].
3. **OS Enablement**: `menvcfg.LPE` bit 2, `SSE` bit 3, `senvcfg/henvcfg` shadowing, cause 18 software-check, `xtval` disambiguation [3].
4. **Compartment Model**: CHERI-RISC-V closed-graph isolation, sentry capabilities for domain crossing, trampoline via unsealing, stack management via trusted switcher [4][5].
5. **Evaluation**: Synthesize prior reported numbers; no invented experiments. All overhead numbers are from cited sources [1][6][7].

### Formal Model

We model ELP as 2-state FSM: `NO_LP → EXPECT_LP(label)` on indirect `jalr/jr`, `EXPECT_LP(label) → NO_LP` iff next instruction is `lpad label' ∧ label'=label`, else trap. Shadow stack as auxiliary stack `SS` with push on `jal` and pop-check on `jalr x0`.

```python
def cfi_step(state, instr):
    if state.elp_pending:
        if not (instr.mnemonic=='lpad' and instr.label==state.expected_label):
            raise SoftwareCheck(tval=2)
        state.elp_pending=False
    if instr.is_indirect_jump:
        state.elp_pending=True
        state.expected_label=instr.rs2  # x7 convention
    if instr.mnemonic=='sspush':
        state.SS.push(instr.rs1)
    if instr.mnemonic=='sspopchk':
        exp=state.SS.pop()
        if exp != instr.rs1:
            raise SoftwareCheck(tval=3)
```

## 4 Deep Dive

### 4.1 Forward-Edge: Zicfilp Landing Pads and Label Design

Zicfilp encodes `lpad` as `auipc x0, label` [2]. Compiler must emit `lpad` at every address-taken function entry and case label. Label in `x7` allows context-sensitive CFI: call sites load expected label, callee's `lpad` must match.

**Design trade-offs**:

- *Label width*: 20 bits → 1M equivalence classes, low collision vs code size.
- *Unlabeled variant*: GNU property `CFI_LP_UNLABELED` allows single `lpad` without label check for compatibility [3].
- *Performance*: CVA6-CFI reports 15.6% overhead with both extensions on MiBench automotive; landing pad checks add fetch pressure due to ELP state flush on mispredict [1].

> **Theorem 4.1 (Forward-Edge Precision).** With distinct labels per equivalence class derived from type hash at `[fn-4]` (KCFI style) [2], Zicfilp reduces indirect call targets from `N` to `|class|`, where `|class| ≪ N` for C programs with function pointers.

Implementation in LLVM requires `-menable-experimental-extensions -mabi` plumbing, and `.4byte` fallback for assemblers lacking encodings [2][8].

### 4.2 Backward-Edge: Zicfiss Shadow Stacks, setjmp/longjmp, and Signals

Backward-edge protection stores return addresses in isolated memory.

| Mechanism | Push | Pop | Privilege | Memory Marking |
|-----------|------|-----|-----------|----------------|
| Zicfiss SSP | `sspush x1` | `sspopchk x1` | S/U via `SSE` | PTE `W=1,R=0,X=0` reserved [2] |
| Intel CET SHSTK | implicit on `CALL` | implicit on `RET` | CR4.CET | Shadow Stack pages [9] |
| ARM PAC+BTI | `paciasp` | `autiasp` | HCRX | N/A [10] |
| Software Shadow (gp) | `sw ra,0(gp)` | `lw`+check | User | Normal |

Key subtleties:

- *setjmp/longjmp*: Must checkpoint/restore SSP via `ssrdp` and `ssamoswap`, discarding stale entries [3]. picolibc's `setjmp.S` does exactly this [3].
- *Signal handlers*: Linux uses `ssamoswap` to atomically exchange current SSP with signal shadow stack pointer; otherwise async handler would corrupt caller chain [2].
- *MMU*: QEMU patch creates `MMU_IDX_SS_WRITE` TLB index allowing only `sspush`/`ssamoswap` to write shadow pages; normal stores fault as access fault [2].
- *Threading*: Discontiguous shadow stacks reduce footprint when many threads share VA space [2].

```rust
// Rust bare-metal CFI demo (clockdomain/cfi-riscv-rust [2])
#[naked]
#[no_mangle]
pub unsafe extern "C" fn protected_fn() -> i32 {
    core::arch::asm!(
        ".4byte 0x0000100b // lpad 0 (Zicfilp)",
        "addi sp, sp, -16",
        ".4byte 0x0a010113 // sspush x1",
        "call actual_work",
        ".4byte 0x0a110113 // sspopchk x1",
        "addi sp, sp, 16",
        "ret",
        options(noreturn)
    )
}
```

### 4.3 Pointer Authentication as Lightweight Alternative

On Ibex RV32, PA adds `pac` and `aut` R4-type instructions [7][8]. Key in CSRs `0x8C0–0xBC0` accessed only if `PCC.perms.Access_System_Registers` [5].

- *Seal*: `x[rd] = QARMA_k( ptr || context )` truncated to 16–32 bits placed in upper unused VA bits.
- *Auth*: recompute and compare; on failure return original corrupted value to force fault or trap [6].

Vt prototype uses RoCC interface: `PTR_SEAL` encrypts full 64-bit pointer with PRINCEv2, avoiding 16-bit brute-force weakness noted in PACMAN [6]. Evaluation on Verilator Rocket + VCU118 FPGA shows <6% slowdown [6]. UMass thesis reports 4.19% on TACleBench, 3.25% on Coremark for return-address-only PAC with prediction to hide latency [7].

```haskell
-- Haskell model of PAC security bound
pacSecurity :: Int -> Double -> Double
pacSecurity bits attempts = 1 - (1 - 2**(-fromIntegral bits))**attempts
-- 16-bit PAC: 50% success after 45425 guesses (PACMAN)
-- 64-bit sealed pointer: 2^64 guesses required
```

### 4.4 CHERI Compartmentalization: Capabilities, Sentry, and Hybrid Deployment

CHERI-RISC-V capability format (128-bit, 64-bit addr + compressed bounds) [5]:

- *Tag* 1 bit: validity, cleared on integer overwrite, stored in ECC bits.
- *Bounds*: 14-bit exponent + mantissa → 3-bit precision loss but enables 128-bit encoding.
- *Perms*: 12 bits: `R,W,X,CapLoad,CapStore,Access_SysRegs,Seal,Unseal`.
- *OType*: 18 bits for sealing.
- *Sentry*: Sealed executable capability; `jalr cap` unseals atomically and jumps, used for compartment entry [4][5].

**Codasip A730** integrates CHERI with 2-stage tag cache and capability-aware LSU. Hybrid mode allows incremental adoption: only network stack compartmentalized, rest unchanged C, 12–18% memory overhead due to doubled pointer size, <5% cycle overhead due to tag cache [4].

> **Theorem 4.2 (CHERI Monotonicity).** Capability manipulation instructions cannot increase rights: bounds can only be narrowed, perms only reduced, tag cannot be set without valid source capability. Therefore compartment escape requires capability leak, not forgery.

Compartment switch sequence [4][5]:

```tla
------------------------------ MODULE CHERICompartment ----------------------------
VARIABLES compartment, caps, pc

CompartmentCall(caller, callee, entry) ==
    /\ caps[caller].perms.Seal
    /\ entry.type = "sentry"
    /\ entry.target = callee
    /\ pc' = entry.addr
    /\ compartment' = callee
    /\ caps' = caps \* sealed data caps passed as args
-----------------------------------------------------------------------------
```

**Trade-off matrix**:

| Primitive | Granularity | Deterministic? | Deployability | Perf (reported) |
|-----------|-------------|----------------|---------------|-----------------|
| Zicfilp lpad | Function / label | Yes | Toolchain patch [2] | +15.6% w/ Zicfiss [1] |
| Zicfiss shadow | Return addr | Yes | Linux + picolibc [3] | +1–3% [1][9] |
| PA QARMA/GIFT | Pointer | Probabilistic 2^-16 | Ibex + RoCC [6][7] | 1.3–5.8% [6] |
| CHERI caps | Byte / object | Yes | Hybrid recompile [4] | <5% cyc, 2× ptr mem [4][5] |

## 5 Empirical / Proofs

No new silicon measured; we consolidate prior results under uniform assumptions.

**CVA6-CFI** (GF 22FDX, 1 GHz) [1]:

- Area: +1.0% over baseline CVA6 (landing-pad unit 0.3%, shadow-stack unit 0.7% including SSP regfile).
- Performance: MiBench automotive (basicmath, bitcount, qsort, susan): 0%–15.6% overhead, geomean 8.2% with both `Zicfilp+Zicfiss`, 3.1% with `Zicfiss` only. Overhead dominated by ELP flush on indirect branch mispredict and extra `sspush` memory traffic.

**Ibex PA** (lowRISC, 32-bit) [7][8]:

- GIFT-64 iterative cipher: 5.6kGE, 8 cycles latency, 1-stage pipeline bubble avoided via `stall_ld_hz` fix [7].
- TACleBench: 4.19% overhead, Coremark: 3.25% [7]. Vt RoCC PRINCEv2: 1.3–5.8% on SPEC CPU2017 (INT) and SPLASH-2, avg 2.9% [6].

**CHERI Morello / A730** [4][5]:

- Morello (Armv8-A prototype): 0–15% cycle overhead for purecap, 30–40% memory for pointer-heavy workloads [5].
- Codasip A730 RV64 CHERI: tag cache 2 KB, 98% hit rate, <2% extra DRAM traffic [4].

**Security Proof Sketch** (backward-edge):

Assume attacker controls all normal memory but not shadow pages (PTE protected, `MMU_IDX_SS_WRITE` isolation). `sspush` only source of SS entries is `jal` in trusted code. `sspopchk` checks equality; mismatch traps. Therefore ROP chain requiring overwritten `ra` on stack cannot match SS entry, raising `xtval=3`. Formally verified in CVA6-CFI via bounded model checking of ELP FSM and SS pointer monotonicity [1].

## 6 Limitations

- **Toolchain maturity**: LLVM `experimental-zicfilp/zicfiss` requires `-menable-experimental-extensions`; GCC 14 lacks support, binutils `checksec` only recently detects `GNU_PROPERTY_RISCV_FEATURE_1_AND` [3][8]. No rustc stable support; nightly `-Zcf-protection` experimental [2].
- **Label equivalence**: 20-bit labels insufficient for fully context-sensitive CFI; collisions enable JOP within class. KCFI type hash at `[fn-4]` mitigates but requires LTO [2].
- **Shadow stack overflow**: Discontiguous stacks mitigate but thread creation must allocate shadow region; `mmap` failure leads to fail-open if `SSE` not enforced. Linux per-thread allocation failure currently kills thread [3].
- **CHERI adoption**: Doubling pointer size breaks ABI; hybrid mode requires careful capability annotation, `cheri.h` provenance. Revocation (temporal safety) still needs load-barrier or sweeping, not fully deterministic [5].
- **PA brute-force**: 16-bit PAC forgeable via speculative PACMAN [6][10]; full-pointer encryption [6] solves but adds RoCC latency and key management complexity.
- **Signal / longjmp**: `ssamoswap` atomicity relies on single-hart; multi-hart concurrent signal delivery can race SSP [2].
- **Performance**: 15.6% worst-case on branch-heavy automotive may be unacceptable for hard real-time; selective protection (only network-facing) reduces but weakens guarantee.

---

## 7 Conclusion

RISC-V's CFI story mirrors x86 and ARM but exposes design choices explicitly: *explicit* `lpad` and `sspush` give compiler control at cost of code size and toolchain churn [1][2]. CVA6-CFI demonstrates 1% area feasibility; Linux and picolibc show OS enablement path via `menvcfg.LPE/SSE` and cause 18 [3]. For IoT-class Ibex, pointer authentication with GIFT/PRINCEv2 offers <6% overhead alternative [6][7]. For high-assurance compartmentalization, CHERI-RISC-V on Codasip A730 provides deterministic, non-probabilistic isolation with hybrid deployability [4][5].

Future work should unify ELP state with branch predictor to cut 15.6% overhead, formalize `ssamoswap` under weak memory (RVWMO), and integrate CHERI capabilities as `Zicfilp` labels to achieve *capability-aware* CFI where landing pad validity derives from capability provenance rather than integer label.
