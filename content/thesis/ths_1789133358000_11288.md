# Completion-Based Asynchrony at Million-IOPS Scale: io_uring's Shared-Ring Interface, eBPF In-Kernel Programmability, and the XDP Packet Path

## Abstract

For four decades, the POSIX system-call interface has mediated every interaction between applications and the devices they drive, and its cost — a privilege-level transition and argument validation per operation — has become the dominant term in the latency budget of I/O-intensive workloads. This thesis examines the two mechanisms that have dismantled that bottleneck: io_uring, a pair of lock-free shared-memory rings that decouple I/O submission from completion and amortize syscall cost to near zero [1][3]; and eBPF, a verified in-kernel virtual machine that relocates programmable logic from user space into the kernel's packet and storage paths [5]. We analyze the ring protocol's memory-ordering discipline, the verifier's static safety argument, and the XDP driver-level hook that processes packets before sk_buff allocation, achieving 24 million packets per second on a single core [4]. We then study their convergence — BPF-driven io_uring submission, multishot network operations, and coroutine-based multisyscall interfaces — and argue that the post-POSIX I/O stack is not a faster syscall layer but the removal of the syscall from the steady state entirely.

## 1. Introduction

The system call is the narrowest waist of the modern operating system. Every byte read from disk and every datagram received from the network crosses the user–kernel boundary, and each crossing exacts a toll: a privilege-level transition, Spectre/Meltdown mitigations through page-table isolation, argument validation, and often a scheduler interaction. Recent work documents that these mitigations have slowed system calls by up to a factor of five relative to the pre-Spectre era [6]. When an NVMe device services 4 KiB random reads in tens of microseconds and a 100-gigabit NIC delivers a small packet every sixty-seven nanoseconds, a per-operation tax of hundreds of nanoseconds is not noise — it is the bottleneck.

Two decades of application-side engineering could not remove it. Non-blocking sockets with `epoll` still cost a syscall to learn readiness and another to act on it, and readiness is a hint, not a guarantee. POSIX AIO bifurcated into the glibc thread-pool implementation and kernel AIO (`libaio`), which was confined in practice to `O_DIRECT` access, performed extra copies, and burned 72 bytes per submission plus 32 per completion [1].

The last decade produced two architectural answers. **io_uring**, merged in Linux 5.1, replaces the syscall-per-operation model with two lock-free rings shared between application and kernel — a submission queue (SQ) and a completion queue (CQ) — through which requests flow as 64-byte descriptors and return as 16-byte completion records [1][2]. **eBPF** is an in-kernel virtual machine whose programs are statically verified for safety and JIT-compiled to native code, so untrusted logic can execute at the earliest point in the packet and I/O paths [5]. Their intersection, the eXpress Data Path (XDP), runs eBPF programs inside the device driver before any `sk_buff` allocation, sustaining 24 million packets per second on a single core [4] — proof that the kernel need not be bypassed to be fast; it can be *programmed*.

This thesis contributes: (i) a precise account of the io_uring ring protocol, its memory-ordering discipline, SQPOLL/IOPOLL execution models, and the multishot and linked-submission extensions that made it a general event engine [3]; (ii) an analysis of the eBPF verifier as a static safety argument enabling the XDP hook; and (iii) a study of their convergence — BPF-driven io_uring submission [7], multishot networking, and coroutine multisyscall interfaces [6].

## 2. Background

### 2.1 The async I/O lineage

| Mechanism | Model | Syscalls per op | Buffered files | Batching |
|---|---|---|---|---|
| `read(2)` / `write(2)` | Synchronous | 1 | yes | no |
| `epoll` + non-blocking | Readiness | 2+ | partial | no |
| POSIX AIO (glibc) | Thread pool | 1 (amortized) | yes | no |
| Kernel AIO (`libaio`) | Completion | 1 | no (`O_DIRECT` only) | limited |
| **io_uring** | Completion, shared rings | ≈ 0 | yes | yes |

The readiness model's flaw is structural: between notification and action, state can change, and each action still costs a syscall. The completion model is strictly more expressive — describe the transfer, be told when it finishes — but kernel AIO's implementation crippled it. io_uring's insight is that the completion model wins only if the *submission channel itself* is cheap, which is what the shared rings provide [1].

### 2.2 From packet filters to a general in-kernel VM

The Berkeley Packet Filter (1993) paired a tiny VM with a static safety checker, so untrusted filter bytecode could run in kernel context without crashing it. Extended BPF (2014) generalized the machine — 64-bit registers, a 512-byte stack, function calls, persistent maps, hundreds of attach points — while the checker grew into a full abstract interpreter that simulates every execution path, tracking each register's type and value range at each instruction [5].

> **Theorem (Verifier soundness, informal):** Any eBPF program accepted by the kernel verifier terminates within a bounded instruction count, accesses only memory it provably owns, and cannot leak uninitialized kernel memory to user space.

The consequence: the kernel hosts arbitrary user-supplied logic — load balancers, DDoS filters, tracers — without a process boundary's isolation cost or kernel bypass's integration cost [4].

## 3. Methodology

This thesis is an analytical synthesis. We treat the primary design documents as first-class evidence: Axboe's *Efficient IO with io_uring* [1], the *What's new* series [2], and the io_uring networking survey [3] trace the interface from a storage API (5.1) to a general async substrate. For eBPF we rely on the XDP architectural paper [4] and the Vieira et al. survey [5].

We construct analytical cost models of the submission path — counting syscalls, memory barriers, and cache-line transfers per operation under interrupt-driven, SQPOLL, and IOPOLL execution. Reported throughput figures (1.7M 4 KiB IOPS with polling, the 608K `libaio` cliff, 12–20M messages/s on the no-op path [1]; 24 Mpps for XDP [4]) are cited as published measurements. Finally, we evaluate the convergence designs — io_uring-BPF [7] and coroutine-to-eBPF lowering [6] — against one question: how much application logic can migrate across the user–kernel boundary before the boundary becomes vestigial?

## 4. Deep Dive

### 4.1 The shared-ring protocol: submission without syscalls

`io_uring_setup(2)` creates an instance; the application `mmap(2)`s two ring buffers. The SQ ring holds indices plus head/tail counters; the 64-byte SQEs live in a directly writable array. The CQ ring is symmetric: the kernel writes 16-byte CQEs (`user_data`, result code) and advances the CQ tail. Both directions are single-producer/single-consumer, so synchronization reduces to ordered publication of the tail index — a store barrier for the producer, an acquire load for the consumer.

```c
struct io_uring_sqe {
    __u8  opcode;      /* IORING_OP_READV, ... */
    __u8  flags;       /* IOSQE_FIXED_FILE, IOSQE_IO_LINK, ... */
    __u16 ioprio;
    __s32 fd;
    __u64 off;
    __u64 addr;        /* buffer or iovec pointer */
    __u32 len;
    __u32 rw_flags;    /* opcode-specific */
    __u64 user_data;   /* opaque, echoed in the CQE */
    /* ... 64 bytes total */
};
```

Submission has two modes. By default, the application fills SQEs, advances the SQ tail, and calls `io_uring_enter(2)` — which can simultaneously wait for completions, so an event loop's steady state is *one* syscall per iteration regardless of batch size [1]. In **SQPOLL** mode (`IORING_SETUP_SQPOLL`), a kernel thread polls the SQ tail and submission costs *zero* syscalls; in **IOPOLL** mode, completions are reaped by polling rather than interrupts, removing interrupt latency for NVMe-class devices.

> **Theorem (Syscall amortization):** In SQPOLL mode the steady-state syscall count per I/O operation is zero; in default mode it is *O(1/N)* for *N* operations batched per `io_uring_enter`. The ring protocol is not a faster syscall — it removes the syscall from the data path.

Two extensions generalized the interface. **Linked SQEs** (`IOSQE_IO_LINK`) express dependencies — a write that must not start until its read completes — so the kernel executes read→write chains without round-tripping to user space [2]. **Multishot** operations (5.19+, for `accept`/`recv`) post a completion *every time* the event fires: a server submits one accept SQE and receives a CQE per connection, eliminating submission housekeeping from the accept loop [3]. Fixed files and registered buffers pre-resolve descriptors and pin pages, removing per-operation lookup costs. The opcode space now spans sockets, timers, filesystem metadata, and `IORING_OP_URING_CMD`, a driver-defined escape hatch [3].

### 4.2 The eBPF verifier: a proof checked at load time

A program written in restricted C is compiled by clang/LLVM to bytecode and loaded via `bpf(2)`. Before JIT translation, the **verifier** runs the most consequential static analysis in production operating systems:

1. **Control-flow validation.** The program must be a DAG once bounded loops are accounted for; since 5.3 bounded loops are permitted but total verified instructions are capped (~1M), preserving termination.
2. **Abstract interpretation.** The verifier simulates execution over an abstract domain: each register is a scalar with known ranges, a pointer to a specific region (stack, map value, packet data, context), or unknown. Any unprovable operation — out-of-bounds access, pointer leak, uninitialized read — rejects the program.
3. **Helper gating.** Only whitelisted helpers for the program type may be called (an XDP program may redirect packets but may not sleep), with argument types checked against abstract register states.

This is proof-carrying code in the Necula–Lee sense, with the proof reconstructed by the verifier rather than shipped. The kernel can therefore execute untrusted logic at driver interrupt priority with a formal safety argument, and the JIT reduces steady-state cost to a direct call [5]. State persists through **maps** — hash tables, arrays, LRU caches, ring buffers shared with user space — yielding the canonical split: *fast path in the kernel, control plane in user space*, e.g., an XDP blocklist enforced at line rate while a daemon updates the map [4][5].

### 4.3 XDP: programmability at the earliest hook

XDP attaches eBPF programs inside the driver's receive routine, before `sk_buff` allocation or protocol processing [4]. The program receives raw packet pointers and returns a verdict:

| Verdict | Semantics |
|---|---|
| `XDP_ABORTED` | Error; drop, raise tracepoint |
| `XDP_DROP` | Drop silently |
| `XDP_PASS` | Continue up the normal stack |
| `XDP_TX` | Transmit back out the ingress interface |
| `XDP_REDIRECT` | Forward to another device, CPU, or `AF_XDP` socket |

The anchoring result is **24 million packets per second on a single core** [4], demonstrated for L3 routing, inline DDoS mitigation, and L4 load balancing (Facebook's Katran). The argument against kernel bypass (DPDK) is integration: the program composes with the existing stack — routing tables, namespaces, tooling — instead of reimplementing it, while `AF_XDP` sockets hand selected packets to user space at near-bypass speed [4][5].

### 4.4 Convergence: when the ring programs itself

**io_uring-BPF.** A 2021 prototype lets eBPF programs drive io_uring rings from kernel context: BPF helpers submit SQEs, reap CQEs, and emit synthetic completions [7]. The target is the *dependent I/O chain* — read metadata, parse, issue the data read at the discovered offset — which today round-trips through user space twice per step. With io_uring-BPF, a verified program performs the parse-and-resubmit transition in-kernel, collapsing the chain into one submission. The verifier is what makes this thinkable; unverified kernel callbacks would be a reliability catastrophe.

**Multishot networking.** Multishot accept/recv [3] plus zero-copy socket operations (`IORING_OP_SEND_ZC`/`RECV_ZC`) recast io_uring as a complete network event engine: one ring pair replaces `epoll`, non-blocking sockets, and the thread pool, with fewer syscalls and no readiness race.

**Coroutine multisyscalls.** Sieck lowers C++20 coroutine suspension points, via an alternative compilation path, into eBPF programs, so logic *between* two io_uring operations executes in the kernel [6]. The author writes sequential code; the compiler partitions it into a kernel-resident fast path and a user-space control plane, absorbing the porting cost that has historically blocked new I/O interfaces.

```rust
// Sketch: multishot accept loop. One SQE submitted once;
// the runtime reaps one CQE per connection, zero syscalls in SQPOLL mode.
async fn serve(listener: &UringSocket) {
    let mut stream = listener.multishot_accept().await;
    while let Some(conn) = stream.next().await {
        // IOSQE_LINK chains read -> parse -> write as one linked
        // submission, executed entirely by the kernel.
        spawn(conn.pipeline().read_fixed(hdr).then_parse().respond());
    }
}
```

The pattern is uniform: *describe the whole workflow once, let verified in-kernel logic handle the transitions*. The syscall is being removed from the control flow, not just the data path.

## 5. Empirical Results and Analytical Arguments

### 5.1 Reported measurements

| Workload | Interface | Reported result | Source |
|---|---|---|---|
| 4 KiB random read, NVMe | io_uring + polling | ~1.7M IOPS | [1] |
| 4 KiB random read, NVMe | `libaio` | ~608K IOPS (cliff) | [1] |
| 4 KiB random read, NVMe | io_uring, no polling | ~1.2M IOPS | [1] |
| Raw `IORING_OP_NOP` | io_uring | 12–20M msgs/s | [1] |
| L3 routing / DDoS / L4 LB | XDP, single core | 24 Mpps | [4] |

Two observations outweigh the absolutes. First, the `libaio` cliff at 608K versus 1.7M on identical hardware isolates the *interface* as the bottleneck — the device had headroom only the cheaper submission channel could exploit [1]. Second, 12–20M messages/s on the no-op path shows the ring machinery is memory-bandwidth bound: the protocol adds essentially no per-operation work beyond descriptor cache-line transfers [1].

### 5.2 Analytical arguments

> **Theorem (Ring linearizability, sketch):** Each ring is single-producer/single-consumer over a power-of-two buffer with monotonic head/tail indices. Release publication of the tail paired with acquire loads suffices for exactly-once visibility of every SQE and CQE without locks, since the producer never overwrites unconsumed entries (enforced by the queue-full check against head).

> **Theorem (Verifier-mediated safety, sketch):** The verifier explores all abstract states reachable under its interpretation and rejects any program with an unprovable access; the JIT is semantics-preserving. Hence no accepted program can access out-of-bounds memory, leak uninitialized memory, or diverge — *for any input*. Safety is checked per load, not per execution.

Together they explain the convergence: the ring is a lock-free, exactly-once transport, and the verifier is a per-load proof that in-kernel request logic cannot violate kernel invariants [5][7].

## 6. Limitations

**The verifier is conservative.** Abstract interpretation over-approximates: safe programs whose safety the domain cannot express are rejected, sometimes after minutes of verification; bounded-loop rules and the instruction cap are engineering compromises, and large programs must be split across tail calls [5].

**Mitigations cut both ways.** The Spectre defenses that inflated syscall cost [6] also apply inside eBPF — speculation barriers in JITed code are a measurable overhead. In-kernel programmability inherits the kernel's threat model.

**io_uring's attack surface is real.** Years of ring-implementation CVEs led distributions and container runtimes to restrict unprivileged io_uring via seccomp. SQPOLL burns a core polling, trading power for latency; and some opcodes silently fall back to worker-thread emulation on filesystems or drivers lacking true async support, reintroducing the costs the interface was built to remove [1][2].

**XDP's reach is driver-bounded.** The hook lives in the driver, so unsupported NICs cannot deliver headline rates, and the instruction set remains awkward for stateful connection-oriented logic — which is why `AF_XDP` and user-space stacks handle the complex cases [4].

**Debuggability lags capability.** Verifier rejection logs are cryptic, ring-buffered telemetry is the primary observability channel, and a pipeline split across coroutines, descriptors, and in-kernel BPF demands tooling that is still maturing [6].

## 7. Conclusion

The arc runs from the system call as unavoidable tax, through two mechanisms attacking it from opposite sides — io_uring amortizing the crossing to zero with shared rings, eBPF relocating logic across the boundary under a machine-checked safety argument — to their convergence in 24-Mpps XDP processing, BPF-driven ring submission, and coroutine-to-kernel lowering [1][4][6][7]. The expensive operation was never the I/O itself but the *negotiation* between protection domains about each I/O. Rings eliminate the negotiation per operation; the verifier eliminates the need for it to be conservative. The emerging model has applications describing workflows, the kernel executing them, and the boundary crossed at configuration time rather than in the steady state. The post-POSIX I/O stack is not a faster way to ask the kernel for things — it is a way to stop asking.
