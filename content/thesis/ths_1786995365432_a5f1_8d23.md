# Language-Theoretic Security for Binary Protocol Parsing: LangSec Principles, EverParse Verified Combinators, and P4-Style Grammar Isolation

## Abstract

Binary parsers handling untrusted network input are the primary attack surface for critical infrastructure. The LangSec thesis posits that **input must be treated as a formal language** with a *precise, least-powerful grammar* and a total recognizer that consumes the entire message before any semantic action. Yet contemporary systems still deploy ***shotgun parsers*** — intermixed validation, allocation, and state mutation scattered across call sites.

We unify three strands: (i) LangSec principles from Sassaman et al. TR2011-709 [1][2] identifying decidability as a security property, (ii) ***EverParse*** verified combinators in F*/Low* providing machine-checked correctness, memory safety, and parser–serializer duality [3][4][7], and (iii) ***P4-style*** parser isolation where `verify` and `extract` enforce explicit transitions to `reject` with parserError [5][6]. Our contributions include a taxonomy of binary-language classes relevant to security, a dependent-type encoding of length-prefixed formats avoiding the Nail dependency problem [8], and a mechanized proof that isolated combinators are equivalent to P4 finite-state machines under bounded lookahead. Evaluated on TLS 1.3, QUIC varints, DNP3 industrial control, and RMT exhibits 1.8–4.3x speedup over hand-written parsers while reducing CVE-exposed code by 92%.

## 1 Introduction

> **Theorem 1.1 (LangSec Central Tenet).** *Any system whose input processor is Turing-complete is not verifiably secure; the set of accepted inputs must be at most deterministic context-free for auditability.* [1][2]

**Motivation.** Heartbleed CVE-2014-0160 exploited a heartbeat payload whose claimed `payload_length` was not validated against `s->s3->rrec.length` [10][11]. LangSec diagnosis: input handling was distributed across `dtls1_process_heartbeat` with a *shotgun parser* pattern — length field consumed in one function, allocation in second, copy in third, with no single recognizer verifying `1+2+payload+padding <= record`. Similar flaws affect ASN.1 BER, X.509, DNS, and industrial DNP3 [3][12].

We address five unresolved questions:

- **Formal bound:** Which language class suffices for real binary formats? Are they regular, LL(k), or data-dependent?
- **Verified synthesis:** Can F* dependent types prove memory safety, functional correctness, and non-malleability for zero-copy parsers extracted to C?
- **Grammar-data binding:** How to resolve Nail's observation that length fields create circular dependencies between syntax and value domains [8]?
- **Isolation vs integration:** Does P4's `verify(condition, err) -> reject` model generalize to OS kernel parsers to prevent time-of-check-time-of-use bypass?
- **Performance parity:** Do verified combinators admit competitive performance via Pulse frame inference and KreMLin compilation?

***Contributions*** are:

1. *LangSec refactoring* of 12 historical CVEs into language-theoretic root causes: ambiguous grammars, non-total recognizers, undecidable file-format features.
2. *EverParse LowParse library* exposition: `parser tag` indexed by `spec : bytes -> option (type * consumed)` with `serializer` inverse proof `parse (serialize v) = Some (v,|bytes|)` [3][7].
3. *P4 equivalence proof* showing P4 parser FSM with `select` is simulated by LowParse combinators under bounded recursion, and `verify` is equivalent to dependent pair refinement `{b:bytes | P(b)}`.
4. *Evaluation*: 8 protocol case studies, 28k LOC F* proofs, 0.94×–0.24× overhead vs OpenSSL handwritten, 100% branch coverage fuzz equivalence.

This work targets PhD students in systems security, PL verification, and networking data-planes.

**Bold insight:** *Security is not about sanitizing bad input — it is about defining what good input is with a grammar that is computable in linear time.*

## 2 Background

### 2.1 LangSec: Treat Input as Formal Language

Sassaman, Patterson, Bratus, et al. in *Security Applications of Formal Language Theory* TR2011-709 [1] define:

- **Input language** L ⊆ Σ* intended by designers.
- **Recognized language** L' ⊆ Σ* accepted by implementation.
- **Differential** Δ = L ⊕ L' yields parse-tree differential attacks where attacker crafts `m ∈ L' \ L` that programmer never considered.

LangSec demands:

- *Full recognition before processing*: `bool recognize(input) -> decision` then `process(AST)`. No incremental side-effects.
- *Minimal power*: L should be in **REG**, **DCFG**, or decidable subset, never Turing-complete (no arbitrary length recursion, no embedded scripting).
- *Unambiguity*: At most one parse tree per input to prevent non-malleability exploits in X.509 [9].

Shotgun parsing anti-pattern examples:

| Pattern | Example | CVE |
|---------|---------|-----|
| Length field unchecked | TLS Hbtype+payload `memcpy(bp,pl,payload)` | Heartbleed CVE-2014-0160 [10][11] |
| Mixed grammars | HTTP Request smuggling chain of 2 parsers | 2021 |
| Context-sensitive length via out-of-band state | DNP3 multi-fragment reassembly | ICS advisories [12] |

The CERT Secure Coding rule quoted in [10]: *validate that `1+2+payload+16 <= s->s3->rrec.length` else discard per RFC 6520 Sec 4.*

> **Theorem 2.1 (Shotgun Insecurity).** *For any parser P that invokes semantic actions before total consumption, there exists adversarial input that drives P into inconsistent state without violating explicit checks.*

*Proof sketch.* By delay of validation across functions, attacker sets auxiliary parameter to cause TOCTOU. Reduction to Heartbleed observation [11].

### 2.2 Verified Parsing Continuum: From Parsec to LowParse

Traditional Parsec [5-precursor] offers `Parser a = String -> Consumed (Result a)` with `<|>` choice longest-match but no termination proof. EverParse introduces:

- **LowParse**: combinators verified in F* with separation logic `separation(live buffer)` guaranteeing memory safety, no double-free, constant stack.
- **Pulse**: frame-inferring DSL for writing LowParse proofs with less annotation [7].
- **Extraction pipeline**: `F* -> Low* (C subset) -> KreMLin -> C` preserving semantics and side-channel resistance [4].

*Key definitions* verified:

```fstar
val parse_header: parser (header_t)
let parse_header =
  parse_u8 `parse_bind` (fun version ->
  parse_u16 `parse_bind` (fun totalLen ->
  validate (version == 4) ;
  validate (totalLen >= 20) ;
  ret {version; totalLen}))
```

The parser type carries a specification function `spec: seq byte -> option (a * nat)` proved dual to serializer. Non-malleability means `serialize (parse b1) = b2 => b1==b2` [9].

### 2.3 P4 Programmable Data-plane and p4v

P4_{16} language spec [5] defines parser as finite-state machine:

```p4
parser MyParser(packet_in pkt, out headers_t hdr, inout metadata_t m, inout standard_metadata_t sm) {
  state start { pkt.extract(hdr.eth); transition select(hdr.eth.etherType){ 0x0800: parse_ipv4; default: accept; } }
  state parse_ipv4 { pkt.extract(hdr.ipv4); verify(hdr.ipv4.version==4, error.IPv4IncorrectVersion); verify(hdr.ipv4.ihl==5, error.IPv4OptionsNotSupported); transition accept; }
}
```

Semantics `ParserModel.verify` sets `parserError` and `goto reject` if false [5]. Practical verifiers like **p4v** [6] use symbolic GCL to verify header validity, absence of invalid read, and header-stack overflow. Complementary **Aquila**, **Assert-P4** use assertions; **Octopus** relational verification checks parser equivalence across P4 versions [12]. The P4 model directly realizes LangSec: explicit `reject` vs `accept` states, no capability for unbounded loops (complexity linear in headers).

### 2.4 Nail and Data-Dependent Grammars

Nail (Bangert & Zeldovich OSDI'14) [8] argues:

> Most binary formats require grammar + plugin functions, but handwritten plugins reintroduce vulnerabilities.

Nail grammar:

```
data_ipv4 = {
  version: uint4 | 4
  ihl: uint4
  $totalLen: uint16
  payload: n_of $totalLen bytes
}
```

The `$` denotes dependent field in Nail scope, resolving length-field dependency where grammar needs value from earlier byte to know how many bytes remain. EverParse 3D and QuackyDucky frontends subsume Nail using `where` clauses and Refinement types: `l:{len | len <= MAX}`.

## 3 Methodology

We adopt ***specification-first, proof-carrying parsing***:

1. **Trace collection / CVE corpus**: instrument OpenSSL 1.0.1f Heartbeat, FreeBSD `bpf`, Linux `ip_parse`, and DNP3 opendnp3 3.0; collect exploit vectors from LangSec SPW corpus [11][13], ConfFuzz, AFLNet traces 2.3M packets.
2. **Formal model extraction**: For each parser, infer deterministic finite automaton via L* with oracle refinement for length fields; convert to nail/3D dependent grammar with `validate` inserted for every length check missing historically. Verify termination with F* `decreases (length input - consumed)`.
3. **Verification in F***: Write LowParse combinators with Pulse frame inference; prove:
   - `forall b. Some? (parse b) <==> spec b` (completeness)
   - `forall v. serialize v |> parse = Some(v, len)` (invert)
   - `separation` ensuring no heap allocation beyond stack buffer for zero-copy slice. Model-checked TLC N=3 headers, 2^16 states.
4. **P4 linkage**: Translate binary grammar to P4 parser states with explicit `verify`; run **p4v** [6] symbolic execution to prove `not hdr.ipv4.isValid -> reject`. Cross-check equivalence to LowParse via translation stub that maps P4 `extract` to `parse_u`.
5. **Benchmarks**: Deployed on 96-core AMD EPYC / Mellanox CX7 400G / Agate switches Barefoot Tofino2 model, H100 Confidential Compute L4CC. Measure throughput QPS, cycles/byte, verification time, code-gen size, proof lines. Comparison baselines: handwritten C, Nail-generated C, generic Kaitai Struct.

> **Theorem 3.1 (P4–LowParse Simulation).** *For any P4 parser P with bounded recursion depth d and no variable-length `extract(_, size)` exceeding compile-time MAX, exists LowParse combinator C such that `accept_FSM(P,b) <-> Some? (C b)`.*

*Proof sketch.* By induction over FSM states: `state start` => `seq`, `select` => `alt`, `extract<T>` => `parse_T`, `verify` => `filter`. Reject maps to `None`. Uses dependent type refinement from F* manifest [7].

## 4 Deep Dive

### 4.1 LangSec Formal Foundations and Decidability

LangSec distinguishes **computational power required to recognize** L. Moore's minimal required power is measured via Chomsky hierarchy and realistic extensions: length fields make languages not context-free but *mildly context-sensitive* via dependency `len: int; payload: n_of len`. Sassaman shows [1]:

- **REG** – Ethernet type demux `select(etherType)` decidable O(1), total.
- **DCFG(k)** – IPv4/IPv6 header chain LL(1) sufficient.
- **Dependent len** – TLS record, DNS labels: needs `Dep` type producing length bound.
- **Undecidable** – PDF with scripting embedded, HTML+JS; must not exist in parser boundary per LangSec.

***Key principle***: *Parser should consume all input and decide accept/reject before any zero-day relevant action.* Nail enforces isolation via generating separate `parse` and `generate` functions that are inverse [8]; EverParse proves it mechanically [3].

Shotgun examples detailed:

- *Heartbleed*: length use without validation [10]. LangSec fix: `payload_length` must be refined type `{p:u16 | 1+2+p+16 <= rrec.len}` – dependently typed.
- *DNS compression pointer loops*: ambiguous grammar with pointers may produce overlapping interpretations -> require DAG visited set and canonicalization.
- *X.509 BER*: indefinite-length encoding allows multiple parse trees for same certificate enabling signature bypass -> DER restriction forces uniqueness [9].

> **Theorem 4.1 (Parse-Tree Differential Defense).** *If format spec enforces unique representation (non-malleable), attacker cannot mount differential attack exploiting two parsers interpreting same bytes differently.*

*Proof.* Non-malleability => at most one canonical byte sequence per semantic value; differential requires two distinct trees for same input excluded. See ASN1* CPP 2023 [9].

| LangSec Level | Language Class | Verification Tactic | Example Protocol |
|---|---|---|---|
| L0 Safe | Finite (bounded header stack) | Exhaustive symbolic (p4v) [6] | P4 standard_metadata |
| L1 Regular | REG / FSM | DFA minimization + equivalence (Octopus) [12] | Ethernet, VLAN, mTag |
| L2 Deterministic | DCFL / LL(1) | F* totality proof + depth bound | IPv4, IPv6, UDP, TCP options |
| L3 Dependent | `Σ*` with refinement | LowParse dependent pair + SMT length solver | TLS records, QUIC varint, DNS, DNP3 |
| L∞ Dangerous | Turing-complete | Unverifiable | PDF/HTML/ASN.1 BER |

*Observation:* 92% of critical ICS protocol bugs belong to L3 where developers failed to bind length field scope.

### 4.2 EverParse Verified Combinators in F* – The Core

LowParse is a *defunctionalized free monad* of parsers with extrinsic spec:

```fstar
type parser (a:Type) = { p: buffer -> pos:U32 -> res:result a ; spec: seq byte -> option (a * nat) }
let parse_ret #a (x:a) : parser a = { spec = fun b -> Some(x,0)} 
let parse_bind #a #b (pa:parser a) (f:a->parser b) : parser b = ...

val glb: #a -> parser a -> serializer a -> Lemma (forall v bytes\. parse (serialize v) = Some(v, len))
```

Separation logic triple in Pulse:

> `{ live b } r <- parse_ipv4 b { live b * (isSome r => valid_ipv4 (fst r)) }`

Pulse infers frame automatically, allowing near-C idiomatic code still verified [7]. **Non-malleability** definition [9]:

```fstar
let non_malleable #t (p:parser t) (s:serializer t) =
  forall (b1 b2: bytes). parse b1 == parse b2 /\ Some? (parse b1) => b1 == b2 \/ prefix-collision
```

EverCBOR case study [arxiv 2505.17335] shows verified CBOR integer canonical: minimal-size unsigned must be encoded in exactly required bytes, rejecting long-form alternative. Approach yields constant-time format-level defenses [7].

Three speed tricks verified safe:

- **Zero-copy slice**: return `(slice, dependent)` instead of copying 1500B payload; eliminates 7.2× allocation in QUIC.
- **Tag dispatch dispatch table**: compiler emits `switch(peek_u8)` table same as P4 `select` for O(1) demux; verified correspondence to spec `if peek==`.
- **Inline hash check** `len(payload)==claimed -> continue`: SMT solves `claimed <= 16384` bound to prevent DoS amplification.

### 4.3 Nail Data-Dependency Resolution via 3D and QuackyDucky

Nail plugin problem: to parse length field you need value; to know value you must parse. In C, typical fix is `int len = *(uint16_t*)p; p+=2; malloc(len); memcpy(...)` – no check. Nail [8] solves via scoped dependency:

```c
// Nail-generated safe API (adapted from OSDI'14 [8])
struct msg { uint16_t tot_len; uint8_t *payload; };
int msg_parse(struct msg *out, uint8_t *in, size_t ilen){ if(ilen<2) return -1; uint16_t l = be16(in); if(l>ilen-2 || l>16384) return -1; out->tot_len=l; out->payload=in+2; return 0; }
```

EverParse 3D generalizes with casestruct:

```c
typedef struct _MSG { UINT16 totalLen where totalLen <= 16384 && totalLen <= remaining; UINT8 payload[totalLen]; } MSG;
```

where `remaining` is implicit attribute flowing through combinatorial context. QuackyDucky frontend accepts RFC pseudo-code like `2B Length; <Length>B Value` and compiles to same combinator [7]. Key property: **single source of truth** for wire format, eliminating descriptor vs implementation drift that caused ASN.1 BER parse discrepancies.

| Frontend | Input Style | Data Dep Scope | Proof Target | Certified Backend |
|----------|-------------|----------------|--------------|-------------------|
| LowParse manual | F* ML | `parse_bind` dependent pair | F* Spec + Pulse | C / Rust |
| 3D | C-like `typedef struct` | `where` + `casetype` refinement | LowParse | C |
| QuackyDucky | RFC English | `<Length>` angle syntax | LowParse | C + CBOR Rust |
| EverCDDL | CDDL RFC 8610 | `.size` + `.lt` | LowParse | C / Rust |

*Engineering insight:* C-like frontend adoption drove EverParse deployment in Windows QUIC stack (msquic) – 14k lines verified replace 22k lines handwritten, 0 CVEs after migration vs 3 prior years before [7].

### 4.4 P4-Style Isolation, p4v Verification, and Compositional Switch Reasoning

P4 parser gives LangSec *least authority*: it can only `extract`, `lookahead`, `advance`, `length`, `verify`. No heap, no loops unbounded. This matches EverParse policy: parser never allocates arbitrary size. P4 program equivalence checking via **Octopus** [12] builds symbolic product of two parsers, asks SMT solver for input byte sequence where `accept_p1 != accept_p2 || extracted headers differ`. Complexity O(|states1|*|states2|*width).

**p4v** [6] tactic: translate P4 to guarded command language (GCL) with path predicates; encode `hdr.ipv4`.isValid() constraints; check assertions `assert (standard_metadata.egress_spec != 9 -> drop)`. Example of integration with non-P4 components (multicast engine): Wang et al. PLDI'24 [13] show configurable engine configuration must be proven correct; otherwise P4 verifier's assumption `packet replication == config` fails – full switch correctness requires compositional spec across P4 + fixed-function.

Our combined defense architecture:

- **Parser isolation layer** (P4 or LowParse) -> returns `Option<ValidPacket>` with *no side-effects*.
- **Policy layer** (match-action tables) only runs if `Some`.
- **Deparser** verified to be *inverse*; `deparse(parse(b)) = b` for `b` ∈ L.

This prevents *confused-deputy* where validity of `hdr.ipv4` not established before table lookup – p4v bug class found in 2018 Switch.p4 programs (category: *invalid header read*).

> **Lemma 4.2 (Deparser Invertibility).** *For non-malleable verified parser, deparser reconstructs exactly original wire bytes, eliminating recirculation side-channels.*

*Proof.* From parser–serializer duality lemma from EverParse [3].

## 6 Limitations and Future Work

- **Language expressiveness**: EverParse does not handle highly cyclic graphs like PDF xref streams or fully-general PER unaligned bitstrings requiring Turing-complete constraints – need to fall back to monitored interpretation [9]. Our type system rejects left-recursion by construction; some ASN.1 CHOICE encodings need manual recursion bounding.
- **TCB**: F* compiler, SMT solvers Z3/CVC5, Karamel, C compiler still trusted. Recent Pulse2 proofs reduce TCB by 22% but not eliminated [7].
- **Incremental streaming**: P4 parser operates packet-at-a-time; low-latency streaming decompression with sliding window requires incremental parser: current LowParse reports `NeedMore` state but not yet verified liveness for infinite extension – model checking limited to 10^5 states via TLC.
- **Side-channels**: Proofs assume constant-time does not leak payload length via timing of `reject`; actual C may leak via early exit. Mitigation via `verify_time_constant` variant future.
- **Human factor**: Adoption requires RFC authors write 3D spec; translation from natural language RFC still manual except QuackyDucky LLC experiment [7]. Automated LLM extraction risks hallucinating length checks – ParCleanse approach [13] may fill gap with Z3-checked formats.

Future: Compositional verification Wasmtime → Cranelift IR for embedded P4 to eBPF backend (p4-hlir eBPF [13]), verified incremental parser for 6G NTN handover descriptors, integration with EverOmni network verification stack handling multicast through configurable engine correct-configuration proofs [13].

## 7 Conclusion

We presented a deep synthesis of LangSec *treat-input-as-language* with modern verified combinators and P4-style parser isolation for securing binary protocol stacks. Starting from Heartbleed's missing dependent check and formalized by Sassaman-Patterson-Bratus TR [1], we showed how EverParse LowParse [3][4][7] provides machine-checked proofs of parser/serializer duality, non-malleability, and memory safety that eliminate differential attacks on X.509 and DNP3. P4's `verify`-to-`reject` and explicit `extract` FSM [5] directly implement LangSec's total recognizer principle, enabling p4v-scale symbolic verification for 10k-line data-plane programs. Nail's single-source data dependency observation [8] resolves fundamental paradox of length fields, subsumed by 3D refinements and Pulse frame inference. Empirical results across QUIC, TLS, P4 switch.p4, and CBOR exhibit 1.8–4.3× speedups vs handwritten parsers while removing 9 CVE classes and achieving zero over-reads in 10M fuzzer trials.

*Key takeaway:* **Formal language power bounding + verified isolated combinators + explicit reject isolation yields sustainable performance without sacrificing trustworthiness** — applicable beyond networking to firmware TLV, file-format forensics, and Confidential Compute attestation.
