# Verified Just-in-Time Compilation: Meta-Tracing Interpreters, Deoptimization Guards, and the Formal Semantics of Speculative Optimization

## Abstract

Just-in-time compilers interleave interpretation with native code generation, specialize code under runtime assumptions that may later be invalidated, and recover from broken speculation through deoptimization. This thesis develops a unified, formally grounded account of these mechanisms. We begin with *meta-tracing* interpreters, in which a tracing JIT records the execution of an interpreter written in a restricted language and optimizes the resulting linear traces under guard assumptions. We then analyze *deoptimization guards* and on-stack replacement as the semantic backstop of speculation: the machinery that reconstructs interpreter state from optimized frames when an assumption fails. The centerpiece is the *formal semantics of speculative optimization*: an intermediate representation in which speculation is explicit through an `Assume` instruction carrying deoptimization metadata, enabling machine-checked proofs that optimizations such as predicate hoisting, assume composition, and unrestricted deoptimization preserve program behavior. Finally, we examine FM-JIT, a Coq-verified JIT reusing the CompCert backend for dynamic native code generation via an effectful, free-monadic modeling discipline. Together these lines chart a credible path from today's unverified production JITs toward compilers whose speculative optimizations carry machine-checked correctness guarantees.

## 1 Introduction

A modern just-in-time compiler is a study in controlled risk. Unlike a static compiler, which commits to a translation before any input is observed, a JIT observes program behavior *at runtime* and then bets on it: it assumes a polymorphic call site will keep seeing the same receiver type, that a loop counter will not overflow a machine word, that a class hierarchy will not gain a new subclass. Under these assumptions it generates aggressively specialized native code — unboxed arithmetic, devirtualized calls, elided bounds checks — and plants *guards*: cheap dynamic checks verifying the assumptions still hold. When a guard fails, the system *deoptimizes*: it abandons the optimized frame, reconstructs the state an interpreter would have had, and resumes in a less speculative tier [1][2].

This architecture delivers remarkable performance — and is a verification nightmare. The compiler's output is no longer a pure function of its input; it depends on profiling data, compilation timing, and which speculative versions happen to be installed. The semantics of "the compiled program" is entangled with the *monitor*: the runtime component deciding when to compile, what to speculate on, and how to transfer control between tiers, including *on-stack replacement* (OSR).

Three research threads have made this territory tractable to formal methods:

1. **Meta-tracing interpreters** (the PyPy/RPython lineage [3][4]): write the *interpreter* in a restricted language and let a meta-tracing engine derive the JIT automatically. Tracing makes speculation concrete — every guard in a compiled trace corresponds to a recorded interpreter decision — and yields a small linear IR to reason about.
2. **Explicit speculation IRs** (sourir [5], CoreIR [1]): make assumptions first-class via an `Assume` instruction pairing a dynamic check with *deoptimization metadata*. Once speculation is explicit, ordinary optimizations — and speculation-specific ones — admit clean machine-checked correctness proofs.
3. **Effectful verified JITs** (FM-JIT [2]): extend the CompCert methodology to a JIT that genuinely generates native code at runtime, using a free-monadic discipline to delimit the impure primitives (code allocation, execution transfer) that cannot be written in the proof assistant.

This thesis synthesizes these threads: what it means, formally, for a speculative optimization to be correct, and how that meaning can be mechanized end to end.

## 2 Background

### 2.1 The anatomy of a speculative JIT

A production JIT (HotSpot's C2, V8's TurboFan, PyPy's meta-tracer) is organized in *tiers*. Execution begins in an interpreter that doubles as a profiler: it counts loop back-edges, records receiver types, and notes branch biases. Past a threshold, a hot unit — method, loop, trace — is compiled under profile-derived assumptions. The compiled code contains guards; guard failure triggers deoptimization to a baseline, where execution continues with semantically equivalent but unoptimized code.

Formally, view the system as an abstract machine whose state includes a *code heap* (functions mapped to versioned artifacts annotated with assumption sets), *interpreter state* , and a *monitor* implementing the compilation policy. A speculation is a predicate *P* over future states (e.g., "register *r* holds a tagged integer"). Compiled code *C* is correct *relative to P*: on executions where *P* holds at every guard, *C* refines the source semantics. Deoptimization is the total function mapping a machine state at a failed guard to an interpreter state whose subsequent behavior coincides with the source program's. Whole-JIT correctness is then a *simulation* property: every observable behavior of JIT-executed code is a behavior of the source program — speculation may change performance, never semantics [1][5].

### 2.2 Why verification lagged

Verified compilation à la CompCert matured around *static* compilation: fixed pass pipelines, each proved semantics-preserving via forward or backward simulation diagrams [6]. JITs resist this treatment for three reasons. First, *self-modifying code*: the compiler's output becomes the machine's input mid-execution; early verified JITs performed no optimizations and resembled no realistic dynamic compiler [7]. Second, *impurity*: code generation, installation, and OSR are inherently effectful and inexpressible in a pure proof assistant without a modeling discipline. Third, *speculation*: correctness must account for assumptions true now and false later, which static simulation diagrams do not naturally express.

The breakthrough was representational: **make speculation explicit in the IR**, so the proof assistant reasons about assumptions as data rather than about the JIT's implicit global invariants [1][5]. Meta-tracing reached the same insight from the engineering side: a trace is a linear program in which every speculative decision is already reified as a guard with a well-defined failure continuation [3][4].

## 3 Methodology

Our methodology is *representational and mechanized*. Rather than verifying a production JIT line by line — whose trusted computing base would swallow the entire runtime — we follow the literature's strategy:

1. **Define a model IR** with first-class speculation (CoreIR, after [1]): an RTL-like language extended with `Assume r f.l [(r ← e)*] l'`, which checks a guard and, on failure, *deoptimizes* to function *f* at label *l* using the metadata environment.
2. **Give the IR a small-step operational semantics** in which deoptimization is an ordinary transition, so simulation arguments apply uniformly to speculative and non-speculative code.
3. **Prove speculative optimizations correct** as Coq simulation diagrams — including optimizations with no static analogue: *unrestricted deoptimization*, *predicate hoisting*, and *assume composition* [1][5].
4. **Connect the model to native code** through the FM-JIT discipline [2]: specify impure primitives (code allocation, monitor transitions) as a free monad, prove the Coq model correct against those specifications, then extract and link trusted OCaml/C implementations.
5. **Ground the design in meta-tracing practice** [3][4]: use the trace IR — linear, single-path, guard-terminated — as the bridge between interpreter-level speculation and the verified IR.

## 4 Deep Dive

### 4.1 Meta-tracing interpreters: compiling the compiler

The meta-tracing insight, pioneered by PyPy, inverts the traditional JIT construction problem [4]. Rather than writing a tracing JIT for a *language* — deciding what a "hot loop" means for every guest language — one writes a tracing JIT for an *interpreter*, obtaining a JIT for every language with an interpreter in the meta-language (RPython, a statically typeable Python subset). The tracer records the *interpreter's* operations as it executes the guest program; the interpreter's dispatch loop is unrolled by the tracer, so the resulting trace corresponds, after optimization, to the guest program's own hot loop.

Two interpreter-author hints make this work [4]: `jit_merge_point()` marks the dispatch-loop header, `can_enter_jit()` marks guest-level backward jumps where tracing begins, and variables are classified *green* (loop-invariant position keys, constant-foldable during tracing) or *red* (genuinely varying values):

### 4.2 Deoptimization guards and on-stack replacement

The essential data structure is the **deoptimization metadata** attached to each guard: a mapping from the optimized frame's physical state to the logical interpreter state of the target. In CoreIR it is the `[(r ← e)*]` environment carried by `Assume` [1]; the metadata expressions are evaluated *in the failing frame's state*, making the metadata itself a small program — and part of the trusted computing base.

Proving this requires *synchronization points* — program points where interpreter state is well-defined — to be explicit in the IR. Barrière et al. introduce exactly this: the `Anchor` instruction marks points where speculation may be inserted, and every `Assume` carries the full reconstruction recipe [1]. Without explicit synchronization points, the argument degenerates into a global invariant over the JIT's code heap — the entanglement that stalled verification for a decade.

Guards are not free, so production JITs invest in *guard quality* and in *deoptless* techniques: Flückiger et al.'s dispatched OSR with specialized continuations replaces the fallback interpreter frame with a freshly specialized native continuation [8]. Formally, deoptless *refines* the transparency theorem: a guard failure's target need not be the interpreter — only something bisimilar to it.

### 4.3 The Assume instruction: a formal semantics of speculation

The representational breakthrough shared by sourir [5] and CoreIR [1] is to treat speculation as *syntax*. In a machine state *(F, l, ρ, μ)*, executing `Assume r f.l [(r ← e)*] l'` evaluates the guard on *ρ(r)*; if it holds, execution continues at *l'*; if it fails, the machine **deoptimizes**: it constructs *(f, l, ρ', μ)* with *ρ'* mapping each metadata register to its expression evaluated in *ρ*, and transfers control to the monitor.

Flückiger et al.'s earlier sourir work [5] established the same program for a higher-level IR , proving classical optimizations correct *in the presence of* explicit assumptions, plus the three deoptimization-specific transformations. The difficulty was never in the optimizations — it was in the *absence of a semantics for the thing being optimized*.

### 4.4 FM-JIT: effectful verification with the CompCert backend

The methodological key is a **free-monadic specification of impure primitives**. The parts of a JIT unwritable in Coq — executable-memory allocation, invoking the assembler, jumping into generated code — sit behind a small primitive interface, with abstract Coq specifications. The JIT is written in Coq against this interface; extraction produces OCaml code linked against hand-written primitive implementations trusted to match their specifications [2].

The deep result: the `Assume` instruction — proved sound for optimizations in [1] — is now also proved to **compile correctly to native code** through the CompCert backend. The simulation spans the whole stack: source semantics → CoreIR with speculation → CompCert passes → assembly, . The TCB grows only by the primitive implementations and extraction.

### 4.5 Type feedback, tiering, and the speculative pipeline

- **guarded devirtualization**: `guard_class(r, C); call C.foo` instead of vtable dispatch;
- **unboxed arithmetic**: `guard_int(a); guard_int(b); add` on machine words;
- **shape-specialized property access**: `guard_shape(obj, S); load obj+offset(S.p)` instead of hash lookup;
- **bounds-check elimination**: `guard (i < len)` hoisted out of loops via predicate hoisting [1][5].

Each speculation site is exactly an `Assume` in the verified IR — the formal semantics gives a precise meaning to every profile-driven bet. *Tiering* organizes bets by confidence: the interpreter collects feedback without speculating; a baseline JIT speculates cheaply and deoptimizes eagerly; an optimizing tier speculates aggressively with the baseline as its deoptimization target. Deoptless continuations [8] add a lateral tier: specialized native fallbacks.

## 5 Empirical Evaluation and Mechanized Results

Verified JIT research evaluates itself on two axes: the *strength of the mechanized guarantee* and the *fidelity of the model to production practice* (does the artifact run, and does speculation pay?).

### 5.1 What the proofs cover

The proofs are *foundational*: they reason directly about small-step operational semantics, and FM-JIT reuses the *same verified* CompCert backend passes — register allocation, instruction selection, linearization — applied dynamically. Both developments ship as Coq artifacts with machine-checked proofs [1][2].

> **Theorem (FM-JIT end-to-end correctness [2]).** *Against an abstract JIT memory model and abstract specifications of the impure primitives, executing a program with FM-JIT produces exactly the behaviors assigned by the program's source semantics — covering dynamic native code generation, interpreter/native interoperability, speculative Assume instructions, and on-stack replacement.*

### 5.2 Does speculation pay? End-to-end evidence

Barrière et al. [1] complement their Coq proofs with an end-to-end experiment: the verified speculative optimizations are extracted and applied in a realistic pipeline, demonstrating *significant speedups* — the proved-correct optimizations are the same ones (predicate hoisting, assume composition) production JITs rely on.

## 6 Limitations

1. **No inlining across the speculation boundary (FM-JIT).** FM-JIT compiles functions one at a time; its `Assume` synthesizes a single stackframe on deoptimization [2]. Production deoptimizers rebuild *chains* of inlined frames; CoreIR's multi-frame metadata models this [1], but its compilation to native code is unverified.
2. **Speculation insertion is unverified.** Both [1] and [2] verify optimizations *given* speculation and the compilation *of* speculation — but the profiling-driven decision of *where* to speculate is outside the proved artifact. A misguided profiler can only hurt performance, not soundness.
3. **Concurrency and the code heap.** The models are single-threaded; real JITs compile on background threads while mutating a shared code heap and invalidating speculative code when class hierarchies change. Verified reasoning about *code invalidation* — assumptions dying globally rather than locally — is largely unexplored.
4. **Meta-tracing remains unverified.** PyPy's tracer, optimizer, and backend are tested, not proved [3][4][9]; tracing also carries high recording overhead (reported at 100–200× in surveys of the area [10]) and degenerative workload cases.
5. **TCB boundaries.** FM-JIT trusts its primitive implementations (executable-memory allocation, control transfer into generated code) and the Coq extraction chain [2]; bugs in the hand-written deoptimization stub would escape the proof.
6. **Garbage collector interaction.** Deoptimization metadata pins object layouts across tiers; a moving GC must update derived pointers in optimized frames and metadata. The verified models assume a simple non-moving heap [1][2].

## 7 Conclusion

Fifteen years ago, a *verified* just-in-time compiler sounded like a category error: JITs were too dynamic, too effectful, too speculative for simulation proofs. The work surveyed here shows the error was in the framing. Meta-tracing interpreters demonstrated that speculation can be *reified* — every optimistic decision recorded as a guard with an explicit failure continuation [3][4]. Sourir and CoreIR turned that operational insight into *semantics*: an `Assume` instruction whose small-step meaning includes deoptimization, making speculative optimizations amenable to the same simulation-diagram proofs that certified static compilation [1][5]. And FM-JIT showed the verified IR can actually *run*: dynamic native code generation through the CompCert backend, with irreducible impurity disciplined by free-monadic specifications [2].

The through-line is a single design principle: **make the assumption explicit, and the proof becomes possible**. A guard carrying its own deoptimization metadata needs no global invariant; a primitive with a formal specification needs no leap of faith; a trace whose guards enumerate its assumptions needs no oracle to explain when it is valid.

Open problems remain: multi-frame deoptimization to native code, verified speculation *insertion*, concurrent code invalidation, a proved-correct meta-tracing engine, and GC integration. But the trajectory is clear — from "can we verify a static compiler?" to "can we verify a compiler that rewrites its own output at runtime under assumptions that expire?" The emerging answer is *yes, and the proofs get shorter as the representations get better*.
