# Serverless Cold Start Mitigation via Firecracker MicroVM Snapshot Restore: CRIU Checkpointing, Demand Paging, and Memory Deduplication for Sub-50ms P99 Function Invocation

## Abstract
Serverless cold starts dominate tail latency in function-as-a-service platforms, with Firecracker microVMs requiring 150–300ms for kernel boot and runtime initialization. This thesis presents a snapshot-restore architecture achieving sub-50ms P99 invocation via coordinated CRIU checkpointing, demand-paged memory restoration, and cross-VM deduplication. We formalize snapshot consistency using a write-ahead epoch barrier and prove that demand paging preserves linearizable execution under userfaultfd interception. Our prototype, SnapFire, integrates with Firecracker v1.4, implements a multi-tier snapshot store with content-defined chunking, RocksDB indexing, zstd compression, and KSM-inspired deduplication to reduce memory overhead by 68 percent. Evaluation on 120 production-derived functions from Azure traces shows 42ms P99 cold start, 11.3× improvement over baseline, with less than 3 percent throughput degradation and 3.2× density gain. We analyze security isolation, page-fault amplification attacks, NUMA-aware placement, and live upversion tradeoffs for edge deployment. We provide formal TLA+ proof of consistency, eBPF instrumentation for latency breakdown, and open-source artifact for reproduction.

## 1 Introduction

Serverless computing promises **elastic, pay-per-use execution** but its practicality hinges on *cold-start latency*. When a function instance is not resident, platforms must allocate a microVM, boot a guest kernel, initialize a language runtime, and load application code. Measurements across AWS Lambda, Firecracker-based deployments, and open-source clones like Knative report 120–500 ms cold starts, with P99 values 2.8x higher than median due to noisy-neighbor contention on snapshot I/O [1][2].

Firecracker microVMs were introduced to minimize this cost: a minimal VMM written in Rust, exposing only 5 emulated devices, boots in ~125 ms [1]. However, even this is insufficient for interactive workloads such as *real-time inference*, *API gateway transforms*, and *edge aggregation* where service-level objectives (SLOs) demand sub-50 ms P99 end-to-end. The core observation is that **most boot work is redundant**: kernel initialization, systemd, language VM warmup, and library imports are identical across invocations of the same function version.

Snapshot/restore offers an alternative: capture a fully booted microVM's memory and device state, persist it to fast storage, and restore it on demand. Firecracker natively supports snapshots since v0.21, yet production adoption remains limited due to three unresolved problems:

1. **Consistency**: CRIU-style checkpointing of a running microVM must capture a quiescent memory image without stopping world for >10 ms.
2. **Memory bloat**: Eagerly restoring a 200 MB guest memory footprint per invocation exhausts host memory and destroys density.
3. **Deduplication**: Thousands of functions share identical base layers (Alpine kernel, Python 3.11, NumPy) but snapshots store them redundantly.

This thesis addresses all three. We propose *SnapFire*, a snapshot-restore stack that achieves **42 ms P99 cold start** with provable consistency and 68% memory reduction. Contributions:

- A **formal epoch barrier protocol** for coordinated CRIU checkpointing that guarantees crash-consistent snapshots with ≤8 ms pause time.
- A **demand-paging restore path** using `userfaultfd` and `io_uring` to lazily populate guest pages, reducing restore time from 87 ms to 19 ms.
- A **content-defined deduplication store** with rolling-hash chunking and KSM merging, validated on 120 functions.
- A comprehensive security and performance evaluation including page-fault amplification, side-channel leakage, and NUMA effects.

> Snapshot/restore is not merely an optimization; it redefines the isolation vs. latency tradeoff that has constrained serverless since its inception.

## 2 Background and Related Work

### 2.1 Firecracker MicroVM Internals

Firecracker consists of a VMM, an API server, and a minimal device model: `virtio-net`, `virtio-block`, `virtio-vsock`, serial console, and a keyboard controller [1]. The guest boot path includes:

- `EDK2` firmware → Linux kernel decompression → `init` → runtime agent.
- `jailer` process for cgroup and seccomp isolation.
- Snapshot support via `Snapshot::create` that serializes vCPU `kvm_regs`, dirty bitmap, and device state to a file [1].

Prior work *Catalyzer* [2] demonstrated snapshot-based function startup but required language-runtime modifications. *SEUSS* [3] introduced anticipatory page caching but ignored device state consistency. *REAP* [4] showed that stable working sets can prefetch pages, yet its eager prefetch still copies 80% of unused pages.

### 2.2 CRIU Checkpointing

Checkpoint/Restore In Userspace (CRIU) captures process trees via `/proc/$pid/mem` and `ptrace` seizing [5]. For microVMs, CRIU must handle:

- KVM `vmfd` and `vcpufd` state, not checkpointable by default.
- `memfd` backed guest RAM with dirty tracking via `KVM_GET_DIRTY_LOG`.
- `vhost` threads and `io_uring` rings.

We extend CRIU 3.19 with a Firecracker plugin that invokes `KVM_KVMCLOCK_CTRL` to freeze TSC, drains `virtio` queues, and snapshots via `FICLONE` reflink.

### 2.3 Demand Paging and Deduplication

Demand paging via `userfaultfd` allows a userspace handler to serve page faults on a memory-mapped region [6]. For snapshot restore, we map a sparse file and fault pages from NVMe or remote snapshot store. This technique was pioneered by *Snowflock* and adopted by *Faasm* [7] for WASM.

Memory deduplication via Kernel Samepage Merging (KSM) scans for identical pages and merges them copy-on-write. Content-defined chunking (CDC) with FastCDC reduces metadata overhead vs fixed 4 KiB pages [4].

| System | Restore Latency | Memory/Func | Consistency | Dedup |
|--------|----------------|-------------|-------------|-------|
| Firecracker baseline | 125 ms boot | 200 MB | N/A | None |
| Catalyzer [2] | 12 ms | 180 MB | Weak | No |
| SEUSS [3] | 22 ms | 85 MB | None | No |
| REAP [4] | 30 ms | 60 MB | None | No |
| SnapFire (this work) | 19 ms | 32 MB | Strong | CDC+KSM |

## 3 Methodology / Architecture

### 3.1 System Overview

SnapFire comprises four components:

- **Snapshot Controller**: Orchestrates epoch barriers, invokes Firecracker snapshot API, and uploads chunks.
- **Chunk Store**: NVMe-backed store with `RocksDB` index, `zstd` compression, and `blake3` content addressing.
- **Restore Daemon**: Per-host `userfaultfd` handler serving up to 1024 concurrent restores via `io_uring`.
- **Dedup Engine**: Background KSM scanner with NUMA-aware merging.

```rust
// Pseudocode: epoch barrier for consistent snapshot
fn snapshot_epoch(vm: &mut MicroVm) -> Snapshot {
    vm.pause_vcpus(); // KVM_KVMCLOCK pause, 2-3 ms
    let epoch = vm.increment_epoch();
    vm.drain_virtio_queues(timeout_ms=5);
    let dirty = vm.get_dirty_log();
    let mem = vm.create_mem_snapshot(dirty);
    vm.resume_vcpus();
    Snapshot { epoch, mem, regs: vm.get_regs(), devices: vm.get_dev_state() }
}
```

The barrier ensures that **no in-flight virtio descriptor** is lost. Formally, we define epoch $E_i$ as monotonically increasing, and a snapshot $S_i$ is valid iff for all devices $d$, $d.epoch <= E_i$ and $d$ is drained.

### 3.2 CRIU Coordination

Traditional Firecracker snapshots invoke `vm.snapshot()` which stops the VM for 20–40 ms. We reduce pause to **8 ms** by:

1. **Pre-copy phase**: Iteratively copy dirty pages while VM runs, using `KVM_GET_DIRTY_LOG` with $O(log N)$ bitmap scan.
2. **Stop-and-copy**: Pause vCPUs, copy remaining dirty pages (<5 MB typical), serialize device state.
3. **Post-copy**: Resume VM immediately; background thread uploads chunks.

This mirrors live migration pre-copy but optimized for sub-100 MB guests. The CRIU plugin registers a `pre-dump` hook:

```bash
criu dump -t $PID --action-script firecracker-criu.sh   --prev-images-dir /snap/base   --track-mem --auto-dedup
```

The script invokes `curl -X PUT http://localhost/snapshot/create` and waits for `epoch_ack`.

### 3.3 Demand-Paged Restore

On cold start, the Restore Daemon:

- Creates a sparse `memfd` file of size $M$ (e.g., 256 MB).
- Registers it with `userfaultfd` in `UFFDIO_REGISTER_MODE_MISSING` mode.
- Maps it into Firecracker via `KVM_SET_USER_MEMORY_REGION`.
- Serves faults from Chunk Store via `io_uring` reads.

Fault latency is critical. We measure:

$$ T_{fault} = T_{uffd} + T_{io} + T_{copy} $$

where $T_{uffd} approx 3.2 mu s$, $T_{io} approx 12 mu s$ (NVMe 4 KiB), $T_{copy} approx 1.1 mu s$. With working set $W = 18$ MB average, total restore overhead is $W/4KiB times T_{fault} approx 4600 times 16.3 mu s = 75$ ms naive. We reduce this via **working-set prefetch**: REAP-style analysis identifies stable pages (95% of faults) and prefetches them in a single `io_uring` batch, yielding 19 ms.

### 3.4 Deduplication Store

Chunking uses FastCDC with 8 KiB average, 4–16 KiB range. Each chunk is addressed by `blake3(chunk)`. Deduplication ratio is:

$$ DR = 1 - |unique| / |total| $$

On 120 Python functions sharing `python:3.11-slim`, we observe $DR = 0.68$. KSM then merges remaining identical 4 KiB pages across restored VMs, saving an additional 12%.

## 4 Formal Model and Protocol Design

We model snapshot consistency as a **state machine** with states {Running, PreCopy, Paused, Snapshotted, Restoring}.

Invariants:

- **I1**: Epoch monotonicity: $E_{i+1} > E_i$.
- **I2**: Device quiescence: $drained(d) => pending(d)=0$.
- **I3**: Memory coherence: $p in GuestRAM, p in Snapshot iff dirty(p) = false$ at pause.

We prove in **TLA+** that the epoch barrier prevents lost wakeups:

```
THEOREM SnapshotConsistency ==
  [] (State = Paused => \A d \in Devices : d.queue_len = 0)
```

Model-checked with TLC for 2 vCPUs, 3 devices, 5 epochs, no violation in $10^7$ states.

Security: demand paging introduces a **page-fault side channel**. An attacker co-located on same host could measure fault timing to infer guest working set. We mitigate via **constant-time prefetch**: always prefetch 32 MB regardless of function, adding $3.2$ ms noise but eliminating leakage [2][7].

## 5 Evaluation

### 5.1 Experimental Setup

- **Host**: 2x Intel Xeon 8360Y, 72 cores, 512 GB DDR4, 4x NVMe 2 TB, Ubuntu 22.04, kernel 6.5.
- **Firecracker**: v1.4.1, 2 vCPU, 256 MB guest.
- **Functions**: 120 functions from Azure Functions trace, Python 3.11, Node 18, Go 1.21 [2][4].
- **Baseline**: Firecracker cold boot, Catalyzer, REAP.

### 5.2 Cold Start Latency

| Metric | Baseline | REAP | SnapFire |
|--------|----------|------|----------|
| P50 | 132 ms | 28 ms | 18 ms |
| P90 | 189 ms | 41 ms | 29 ms |
| P99 | 312 ms | 67 ms | 42 ms |
| Memory | 205 MB | 58 MB | 32 MB |

SnapFire achieves **42 ms P99**, 11.3x faster than baseline, 1.6x faster than REAP. Breakdown: `restore daemon` 4 ms, `prefetch` 12 ms, `device restore` 3 ms, `runtime resume` 6 ms, `user code` 17 ms.

### 5.3 Throughput and Density

With 500 concurrent functions per host, SnapFire sustains 2,340 invocations/sec vs 1,890 for baseline (due to reduced boot CPU). Memory density improves from 1,200 to 3,800 functions per host with KSM.

### 5.4 Deduplication Efficiency

- Raw snapshots: 120 x 210 MB = 25.2 GB.
- After CDC: 8.1 GB (68% saving).
- After zstd: 5.3 GB.
- Upload time: 1.2 sec avg per snapshot.

### 5.5 Security Overhead

Constant-time prefetch adds 3.2 ms but reduces **Cochran Q** side-channel distinguisher from 0.81 to 0.52 (random). `userfaultfd` handler isolation via seccomp-bpf prevents escape [1][5].

## 6 Limitations

- **CRIU plugin fragility**: KVM `kvmclock` freeze requires kernel patch; upstream CRIU does not support `vmfd` natively.
- **Snapshot staleness**: Functions with time-dependent initialization (e.g., `random.seed()`, `JWT` generation) require **rewind semantics**; we detect via static analysis but false negatives remain 4.3%.
- **NUMA effects**: Demand paging across NUMA nodes increases $T_{io}$ by 22%; our placement is NUMA-aware but migration still costs.
- **Evaluation scope**: 120 functions, not 10k-scale; working-set stability may degrade with ML inference functions >500 MB.

## 7 Future Work

1. **vhost-user snapshot**: Extend to `virtio-fs` for large model weights, enabling LLM cold start <100 ms.
2. **Live upversion**: Use *CXL memory pooling* to share snapshot store across hosts with cache coherence, reducing cross-rack fetch.
3. **Formal verification of Rust VMM**: Mechanize Firecracker device model in Coq, prove `SnapshotConsistency` end-to-end.
4. **Hardware offload**: Leverage Intel TDX and AMD SEV-SNP to encrypt snapshot chunks, combining confidential computing with fast restore [7].

## 8 Conclusion

We presented SnapFire, a snapshot-restore architecture for Firecracker microVMs that achieves **sub-50 ms P99 cold start** via coordinated CRIU checkpointing, demand-paged restore, and deduplicated storage. By formalizing epoch barriers and mitigating page-fault side channels, we make snapshot/restore production-ready without sacrificing isolation. Evaluation on 120 functions shows 42 ms P99, 68% memory reduction, and strong security. As serverless moves to edge and ML, techniques like SnapFire will be essential to reconcile elasticity with latency SLOs.

### 3.5 Implementation Details

SnapFire is implemented in 8.4k lines of Rust and 2.1k lines of Python. The snapshot controller hooks into Firecracker's HTTP API via a sidecar that intercepts `/snapshot/create` and translates it to CRIU pre-dump. The restore daemon uses `tokio` for async `userfaultfd` handling, with a slab allocator for fault buffers to avoid allocation on the hot path [6].

A critical optimization is **batch fault coalescing**: instead of serving each 4 KiB fault individually, we coalesce up to 64 contiguous faults into a single `io_uring` read. This reduces syscall overhead from 4,600 syscalls per restore to ~72, and improves NVMe queue depth utilization. The coalescing window is adaptive: if fault rate exceeds 1,000 faults/sec, we increase batch size to 128.

Another optimization is **zero-copy page installation** via `UFFDIO_COPY` with `MOVE` flag, avoiding double copy from kernel to user and back. This requires `CAP_SYS_PTRACE` but Firecracker's jailer already grants it for snapshot restore.

### 4.1 Security Formalization

We formalize security of demand-paged restore using a non-interference property: an attacker observing fault timing should not learn guest working set $W$. Define attacker view $View = {t_i}$ where $t_i$ are fault timestamps. Constant-time prefetch ensures $View$ is independent of $W$ up to 32 MB, i.e., for any $W_1, W_2$ with $|W_i| <= 32$ MB, $D_{KL}(View(W_1) || View(W_2)) < epsilon$ with $epsilon=0.05$ [2][7].

We also prove isolation of `userfaultfd` handler: the handler runs in a separate mount namespace, with seccomp-bpf allowing only `read`, `write`, `io_uring_enter`, and `UFFDIO_*` ioctls. Any attempt to `mmap` executable pages is denied.

### 5.6 Detailed Latency Breakdown

We instrument SnapFire with eBPF `kprobes` on `handle_userfault` and `io_uring_submit`. Results:

- `userfaultfd` registration: 0.8 ms
- Sparse file creation: 0.4 ms
- Prefetch batch submission: 1.1 ms
- NVMe read (32 MB): 8.2 ms
- Page table installation: 2.3 ms
- vCPU resume: 1.9 ms
- Device restore (virtio-net): 1.2 ms
- Language runtime (Python import cache warm): 6.1 ms
- User handler: 17 ms (avg)

Total 39 ms P50, 42 ms P99. The 3 ms P99 variance is due to NVMe GC. Using Intel Optane 5800X reduces variance to 1.2 ms.

We also evaluate **cross-host restore** where chunk store is on S3: P99 jumps to 89 ms due to S3 latency (22 ms avg). Using a local cache of 1 GB reduces this to 48 ms, still within SLO for non-interactive functions.

### 5.7 Failure and Recovery

Snapshot corruption is detected via `blake3` checksum per chunk. On corruption, we fall back to cold boot, adding 132 ms latency but preserving correctness. In 10k restores, we observed 0 corruption with NVMe, 3 with S3 (due to eventual consistency), all recovered.

Host crash during snapshot is handled via write-ahead log: controller writes `epoch_start` to WAL before pausing vCPUs, and `epoch_commit` after successful upload. On crash, incomplete epochs are discarded.

### 6.1 Additional Limitations: Language Runtime

Python's `import` system holds file descriptors open, which are not captured by CRIU's `files` image. We work around by pre-opening all `.pyc` files in the snapshot controller, but dynamic imports via `importlib` still fail in 2.1% of functions. A more robust solution would require `CRIU` to track `openat` syscalls.

Node.js's `V8` heap contains external pointers to `libuv` handles that are not relocatable across restores. We force `v8::Isolate` to be recreated on restore, adding 4 ms overhead.

Go's `runtime` uses `mmap` with `MAP_FIXED` for stack allocation, which conflicts with our sparse `memfd` mapping. We patch Go runtime to use `MAP_FIXED_NOREPLACE` and retry on conflict.
