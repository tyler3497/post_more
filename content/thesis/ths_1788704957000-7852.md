# CHERI Capability Hardware for Deterministic Memory Safety: Capability Derivation, Monotonicity Enforcement, Morello Prototype Evaluation, and C/C++ Compartmentalization

## Abstract

Memory-unsafe code in C and C++ remains the dominant source of exploitable vulnerabilities in commodity software, with spatial and temporal safety violations underpinning the majority of CVEs in systems software [1][4]. CHERI (Capability Hardware Enhanced RISC Instructions) reframes the pointer as an unforgeable, hardware-enforced capability carrying bounds, permissions, and an object type, with a single-bit tag distinguishing valid capabilities from ordinary data and a monotonicity invariant guaranteeing that derived capabilities can never exceed the authority of their parents [1]. This thesis formalizes the CHERI capability model — 128-bit compressed capabilities with floating-point-encoded bounds, tagged memory, and the complete instruction-level derivation algebra — proves the monotonicity property through the Isabelle/HOL verification of the Morello specification [3], and evaluates the first-generation Arm Morello prototype built on the Neoverse N1 microarchitecture across the SPECint suite under multiple code-generation models [5]. We analyze capability-aware compilation for C/C++ (hybrid versus pure-capability ABIs), quantify the performance overhead of fine-grained memory protection, and demonstrate scalable software compartmentalization as the mechanism that converts deterministic memory safety into principled least-privilege decomposition [6]. Evaluation shows that CHERI eliminates entire classes of memory-safety vulnerabilities with low single-digit to low double-digit overhead on Morello, while formal verification establishes capability monotonicity as a machine-checked architectural invariant [3][5]. Limitations include the trust placed in privileged capability-creation instructions, concurrency modeling gaps in the verified specification, and the engineering cost of porting legacy software to pure-capability ABIs [6].

## 1 Introduction

The persistence of memory-safety vulnerabilities is one of the most expensive open problems in computer systems. Despite decades of mitigations — stack canaries, ASLR, DEP, control-flow integrity, sanitizers — the fundamental defect remains: the C and C++ abstract machine treats pointers as integers, and the hardware provides no mechanism to distinguish a pointer from data or to constrain the memory a pointer may address. CHERI attacks this root cause architecturally rather than probabilistically [1].

The CHERI program, developed by SRI International and the University of Cambridge with DARPA support, introduces an architecture-neutral capability-based protection model instantiated in commodity base architectures: CHERI-MIPS, CHERI-RISC-V, Arm's Morello prototype, and a sketched CHERI-x86-64 [1]. Every pointer becomes a *capability*: an unforgeable token of authority bundling the address with its valid bounds, its permissions, and an object type, protected by a hardware tag bit that is cleared by any non-capability-aware manipulation [1]. Crucially, capabilities obey **monotonicity** — every operation that derives a new capability from an existing one can only narrow its authority — which the CHERI team has verified formally in Isabelle/HOL against the Morello architectural specification [3].

This thesis makes four contributions:

1. A complete exposition of the CHERI capability model: compressed 128-bit capability encoding, tagged memory, the derivation instruction algebra, and the sealing mechanism for encapsulation.
2. A proof sketch of capability monotonicity grounded in the machine-checked verification of the Morello specification, with explicit treatment of the proof's assumptions and limitations [3].
3. A performance and compatibility evaluation of the Morello prototype — a first-generation CHERI-enabled CPU based on Arm's Neoverse N1 — across SPECint under hybrid and pure-capability code-generation models [5].
4. An analysis of CHERI compartmentalization as the architectural primitive for scalable software decomposition, contrasted with process and software-fault-isolation alternatives [6].

## 2 Background

### 2.1 The memory-safety crisis

Memory-safety violations — buffer overflows, use-after-free, type confusion, uninitialized reads — account for roughly 70% of serious vulnerabilities in large C/C++ codebases. Probabilistic mitigations raise the bar for attackers but do not eliminate the vulnerability class; CHERI's design goal is *deterministic* safety: violations trap in hardware rather than succeeding with some probability [1].

> **Theorem: Deterministic protection.** Under the CHERI capability model, any load, store, or instruction fetch through a capability is checked against the capability's bounds and permissions in hardware; a violation raises a synchronous exception. No probabilistic assumption is required [1].

### 2.2 Capability systems lineage

CHERI descends from a long lineage of capability systems — Dennis and Van Horn's supervisor, Hydra, the Intel iAPX 432, EROS/KeyKOS — but departs from them in a critical respect: rather than replacing the virtual-memory protection model, CHERI *composes* with it, extending the existing ISA with capability registers and instructions so that conventional software stacks (UNIX, C/C++, MMU-based isolation) continue to work with incremental adoption [1]. This design-for-adoptability is what distinguishes CHERI from clean-slate capability machines.

### 2.3 The Morello prototype

Arm's Morello is a first-generation CHERI-enabled prototype CPU based on Arm's Neoverse N1, as found in the N1SDP evaluation board, created under UKRI sponsorship through the Digital Security by Design programme [5][6]. It provides a research platform to evaluate CHERI at industrial scale — a rich, contemporary, high-performance microarchitecture with a full software stack — at a scale unobtainable via ISA emulators or FPGA soft cores alone [5]. The Morello programme documents both its architectural security goals and its known limitations, acknowledging explicitly where the prototype falls short of the full CHERI vision [6].

## 3 Methodology

Our methodology combines formal, architectural, and empirical analysis:

1. **Formal exposition**: We reconstruct the capability derivation algebra from the CHERI ISA specification (versions 6 through 9) [1][2], with emphasis on the compressed 128-bit encoding and its floating-point bounds representation.
2. **Verification analysis**: We examine the Isabelle/HOL formalization of the Morello specification — generated from Arm's ASL via Sail — and its machine-checked proof of capability monotonicity, carefully enumerating the proof's assumptions [3].
3. **Empirical evaluation**: We report and analyze the early performance results from the Morello microarchitecture on SPECint, comparing hybrid-capability and pure-capability compilation models [5].
4. **Compartmentalization case studies**: We analyze the software compartmentalization idioms enabled by CHERI — sealed capabilities, compartment switching, and the resulting performance improvements over process-based isolation [6].

## 4 Deep Dive

### 4.1 The 128-bit compressed capability format

The original CHERI design used 256-bit capabilities; the production target is 128 bits — the next natural power-of-two pointer size above 64-bit pointers — with roughly one-third the overhead of the full scheme [1]. The 128-bit format packs:

| Field | Purpose |
|---|---|
| *Address* (64 bits) | The pointer value itself |
| *Bounds* (compressed) | Base and top, encoded as floating-point distances from the address |
| *Permissions* | Read, write, execute, and capability-manipulation rights |
| *Object type* | 18-bit sealed type for encapsulation |
| *Tag* (1 bit, out-of-band) | Validity: cleared by any non-capability-aware write |

The bounds compression is the format's most subtle feature. It uses a floating-point representation of the distances between the pointer and the base/top, exploiting redundancy between the three values. This yields **fully precise bounds for small allocations** (below ~1–4 MiB, depending on version) — covering the stack frames and small heap objects that dominate C programs — with graceful imprecision for larger regions [1][2]. Imprecision is *safe by construction*: representable bounds always cover at least the requested region, so imprecision can only over-approximate authority within limits the monotonicity proof accounts for.

A deliberate C-compatibility decision: pointers may go "out of bounds" — the address can wander outside `[base, top)` during arithmetic, as real C programs routinely do (e.g., computing one-past-the-end or sentinel pointers), and only *dereference* is checked [1]. Substantially out-of-bounds movement may clear the tag, an intentional hardening behavior.

```c
// Hybrid ABI: annotated pointers become capabilities
void * __capability buf = malloc(128);
// buf carries (base, top=base+128, perms=RW); hardware checks every access
buf[200] = 0;  // synchronous CHERI exception: bounds violation
```

### 4.2 Tagged memory and provenance

Every capability-sized, capability-aligned word in memory carries a tag bit indicating whether it holds a valid capability. The tag is stored out-of-band (in Morello, transported through the entire memory hierarchy — including the CMN-Skeena coherent interconnect with its 129th data-path bit — and stored as a special ECC encoding in DRAM) [5]. Ordinary stores clear the tag; only capability-aware instructions (`SC`, `CLC`) set it, and only when storing through a capability with sufficient permission [1].

This gives CHERI its *provenance* property: valid capabilities can only originate from legitimate derivation — from the root capabilities installed at boot (`PCC`, `DDC`), from `CBuildCap` on privileged memory, or from narrowing existing capabilities. Forgery is impossible because no instruction sequence can set a tag bit from arbitrary data.

### 4.3 The derivation algebra and monotonicity

The heart of CHERI is its instruction-level algebra. The principal derivation instructions are:

- `CSetBounds` / `CSetBoundsExact` — narrow bounds (never widen)
- `CAndPerm` — clear permission bits (never set)
- `CSeal` / `CUnseal` — seal a capability with an object type, or unseal with the matching authority
- `CSetOffset` / `CIncOffset` — adjust the address within bounds

> **Theorem: Capability monotonicity.** For every CHERI instruction that produces a capability output from capability inputs, the output's authority (bounds × permissions × object type) is a subset of the inputs' authority. No instruction can expand bounds, add permissions, or forge a tag [1][3].

Monotonicity is what makes CHERI *composable*: a callee receiving a narrowed capability cannot escalate, regardless of its behavior. The Isabelle/HOL verification of the Morello specification proves this property across the full instruction set, generated from Arm's authoritative ASL via the Sail toolchain [3]. The proof's assumptions are explicit and important:

1. Only the sequential architecture is modeled; concurrency effects require integrating a whole-system memory model, though capability properties are expected to be largely orthogonal provided capability body and tag writes appear atomic [3].
2. The translation mapping is arbitrary but fixed; system software managing translations must be trusted or verified, since CHERI capabilities are expressed in virtual addresses [3].
3. Privileged capability-creation instructions are assumed disabled and no external debugger active, as these can circumvent protections [3].
4. One lemma depends on an SMT solver as an oracle; the ASL→Sail→Isabelle translation itself is unverified, though validated against the Sail-generated C emulator [3].

These caveats do not weaken the result — they scope it precisely, which is exactly what a verification should do [3].

### 4.4 Sealing, compartments, and the object-type space

Sealing converts a capability into an *opaque* token bound to an 18-bit object type: the sealed capability cannot be dereferenced, only passed around and eventually unsealed by code holding the matching unseal authority [1]. This is the primitive for encapsulation — sealed code/data capabilities implement protected subsystems, exception handlers, and, critically, **software compartments**.

CHERI compartmentalization replaces process boundaries (with their TLB-flush and kernel-crossing costs) with in-address-space domain transitions via sealed capability invocation — measured in tens of cycles rather than microseconds [6]. Compartments receive only the capabilities they need (least privilege), and a compromised compartment cannot forge capabilities outside its grant because of monotonicity. This yields *significant performance improvements for software compartmentalization* as an explicit design goal of the architecture [1].

```rust
// Conceptual compartment entry: sealed pair (code, data)
let entry: Sealed<CompartmentEntry> = seal(code_cap, data_cap, COMPARTMENT_T);
// Invoke: hardware unseals, switches PCC/DDC, enters compartment
invoke_compartment(entry, args);  // ~tens of cycles, no kernel crossing
```

### 4.5 Compilation models: hybrid versus pure-capability

Adoptability demands a migration path, so CHERI C/C++ supports two ABIs [1]:

- **Hybrid**: `int *` remains a 64-bit integer offset; only annotated pointers (`void * __capability`) become capabilities, interpreted relative to `DDC`. Recompile libraries with annotations for spatial safety where it matters most.
- **Pure-capability**: every pointer is a capability; `sizeof(void *)` is 16 bytes. Full spatial and temporal safety (with appropriate allocator support for temporal safety via revocation or quarantining), at the cost of ABI change and porting effort.

The Morello evaluation explores both, measuring the overhead of each on real workloads [5].

## 5 Empirical Results and Proofs

### 5.1 Formal result: machine-checked monotonicity

The verified-security effort for Morello establishes capability monotonicity as a theorem in Isabelle/HOL over the Sail-generated specification of the Morello architecture, covering the complete instruction set [3]. This is, to our knowledge, the largest-scale machine-checked proof of a security property over a contemporary commercial ISA specification. The proof composes with the ISA specification versions (v8/v9) that document the compressed-capability semantics [1][2].

### 5.2 Morello performance: SPECint

The early performance investigation runs SPECint on Morello under multiple code-generation models — baseline AArch64, hybrid-capability, and pure-capability — providing a first look at the overhead of hardware-enforced memory protection on a contemporary out-of-order microarchitecture [5]. Key findings from the living performance document:

- **Pointer footprint doubles** in pure-capability mode (16-byte pointers), increasing cache pressure and memory bandwidth — the dominant cost, not the bounds checks themselves, which the pipeline absorbs with minimal added latency [5].
- **Bounds checks are cheap**: the capability checks fold into the existing load/store pipeline with low single-digit overhead on most benchmarks; outliers correlate with pointer-heavy data structures and increased cache misses [5].
- **Hybrid mode** shows near-baseline performance for unannotated code, with safety proportional to annotation coverage — the intended incremental-adoption tradeoff [5].

These results validate CHERI's central performance thesis: *low performance overhead for memory protection* is achievable because the checks ride on existing pipeline structures rather than requiring software instrumentation [1][5].

### 5.3 Security goals and residual risk

The Morello programme's security-goals document is unusually candid: it enumerates what the prototype guarantees and what fell out of scope — side channels, concurrency subtleties, and the trusted role of privileged software are all explicitly discussed [6]. This candor is itself a contribution: it defines the *threat model* precisely rather than implying total security.

## 6 Limitations

1. **Trusted privileged software**: CHERI capabilities are virtual-address capabilities; the OS/hypervisor managing page tables can remap memory beneath capabilities and must be trusted or verified [3][6].
2. **Temporal safety is not free**: CHERI provides deterministic *spatial* safety and capability *integrity*; use-after-free requires additional mechanisms (revocation via sweeping, quarantine in allocators), which carry their own costs [1].
3. **Side channels**: the verified properties are functional, not non-interference; timing and microarchitectural side channels are out of scope for both the ISA proof and the Morello security goals [3][6].
4. **Porting cost**: pure-capability ABIs change pointer size and break assumptions baked into decades of C code (pointer-integer casts, custom allocators, JITs); hybrid mode eases this but provides only partial protection [1][5].
5. **Capability compression imprecision**: large bounds lose precision; software must use `CSetBoundsExact` where exactness is required, and the semantics of imprecision must be understood by systems programmers [1][2].

## 7 Conclusion

CHERI reframes memory safety from a probabilistic software property into a deterministic architectural invariant. Its three interlocking mechanisms — compressed capabilities with bounds and permissions, tagged memory enforcing provenance, and a monotonicity invariant verified in Isabelle/HOL against the Morello specification — eliminate the confused-deputy structure of memory-safety vulnerabilities at the hardware level [1][3]. The Morello prototype demonstrates that this protection is achievable on a contemporary high-performance microarchitecture with modest overhead, and that compartmentalization can be restructured from a microsecond-scale OS primitive into a tens-of-cycles hardware primitive [5][6]. The remaining work is engineering and ecosystem: completing temporal-safety mechanisms, hardening the privileged software base, and carrying legacy software across the ABI boundary. The formal and empirical evidence together suggest that the decades-long memory-safety crisis has, for the first time, an architecturally complete answer.
