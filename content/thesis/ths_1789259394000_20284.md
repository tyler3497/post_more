# The Polyhedral Model of Loop Optimization: Dependence Analysis, Affine Scheduling, and Code Generation

## Abstract

The polyhedral model recasts the execution instances of a static-control loop nest as integer points inside rational polyhedra, turning loop optimization into a problem of geometry and linear algebra. This thesis develops the model end to end: iteration domains and access relations as parametric integer sets; dependence analysis via dependence polyhedra and the affine Farkas lemma; valid affine scheduling with Feautrier's algorithm and its greedy optimality analysis; the Pluto heuristic for tiling hyperplanes that jointly optimize coarse-grain parallelism and locality; and AST code generation through CLooG and the isl integer-set library. We state the dependence-validity condition as a Farkas certificate, derive Feautrier's linear constraints for multidimensional schedules, and present Pluto's cost model for communication-minimized tiling. A formal proof sketch establishes schedule validity, and empirical evidence from the PolyBench suite is reviewed, showing polyhedral transformations competitive with hand-optimized codes on modern multicores.

## 1 Introduction

High-performance computing lives and dies by the loop. Dense linear algebra, stencil computations, image processing, and deep learning kernels all spend their time inside nested loops whose bounds and memory references are affine functions of the enclosing iterators and a handful of symbolic parameters. For this class of programs — the *static control parts* (SCoPs) — the polyhedral model provides an exact, closed-form representation of every dynamic execution instance, every data dependence, and every legal reordering of the computation [1][4].

Where classical dependence analysis works with direction and distance vectors [5], the polyhedral model works with *sets*: the set of statement instances is a parametric polyhedron, the set of memory locations read or written is the image of that polyhedron under an affine access map, and the set of all producer-consumer pairs is a polyhedron in the product space [7]. Because every object of interest is a polyhedron or a Presburger formula, every analysis is a polyhedral operation — intersection, projection, image, preimage, transitive closure — and every optimization is the choice of a single object: the **schedule**, a multidimensional affine relation mapping each statement instance to a logical time stamp [1][2].

This thesis gives a self-contained account of the classical pipeline: representation, dependence analysis via the affine Farkas lemma, Feautrier's scheduling algorithm [1][5], the Pluto tiling heuristic [2][3], and polyhedral code generation with CLooG and isl [4][8][10]. The presentation is mathematical but implementation-aware: every construction corresponds to an algorithm that runs inside production compilers such as Polly/LLVM, PPCG, and Pluto itself.

## 2 Background

### 2.1 Static control parts

A *static control part* is a maximal region of the program in which all control flow — loop bounds and conditionals — is an affine function of the surrounding loop iterators and of *structural parameters* (symbolic constants such as array sizes that are fixed for the duration of the region) [4]. Statements inside a SCoP execute according to the *original schedule*, the lexicographic order of iteration vectors. Typical SCoP kernels include matrix multiplication, LU decomposition, Jacobi and Gauss-Seidel stencils, and the FDTD kernels of the PolyBench/C suite [6].

The model's expressiveness boundary is sharp: while loops with data-dependent trip counts, dynamic data structures, recursion, and non-affine subscripts (e.g., `A[B[i]]`) are excluded, everything affine is captured exactly, including imperfectly nested loops, conditionals, and statement sequences. This exactness is the model's central virtue: unlike vector-based analyses that over-approximate, polyhedral dependence analysis is *exact* for affine programs, and the transformations it licenses are provably semantics-preserving [1][7].

### 2.2 Polyhedral machinery

We recall the essential operations. A **rational polyhedron** is a set `P = { x in Q^n | A x + b >= 0 }`; intersecting with `Z^n` yields an **integer polyhedron**. Key operations include:

- **Projection** onto a subset of dimensions (Fourier-Motzkin elimination).
- **Image and preimage** under affine maps `f(x) = M x + v`.
- **Emptiness testing** via linear programming (Farkas certificates of infeasibility).
- **Parametric integer programming**, as provided by the PIP library of Feautrier and the Omega library of Pugh [8].

Libraries such as **isl** [4] represent these sets with GMP-based arbitrary precision arithmetic, internally using integer divisions inspired by PipLib's output format, and support unions of polyhedra, schedule trees, transitive closure, and AST generation [8]. The older **Omega** and **Polylib** libraries provided the same services with different internal representations; isl has become the de facto standard inside LLVM/Polly, PPCG, and modern Pluto [4][9][10].

> **Definition:** An *iteration domain* `D_S` of a statement `S` nested in `n` loops with parameter vector `p in Z^q` is the integer polyhedron `D_S = { x in Z^n | A x + B p + c >= 0 }`, the set of all iteration vectors for which `S` executes.

## 3 Methodology

Our methodology follows the standard polyhedral compilation pipeline, and the thesis is organized to mirror it. First, a SCoP is extracted from C source (by tools such as Clan or PET) into iteration domains, access relations, and the original schedule [10]. Second, dependence analysis computes, for every ordered pair of statements and every pair of a write and a read/write reference, the **dependence polyhedron**: the set of instance pairs that touch the same memory location with at least one write, ordered by the original schedule [5][7]. Third, a **scheduler** computes an affine schedule satisfying all dependences while optimizing an objective — minimum latency (Feautrier [1]), or parallelism plus locality (Pluto [2]). Fourth, the schedule is materialized: tiling hyperplanes may be introduced to obtain cache-blocked or parallel loop nests [2][3], and finally a **code generator** (CLooG, or isl's AST builder) scans the transformed polyhedra to emit loop nests with exact, non-redundant bounds [8][10].

Correctness is carried by a single invariant: every dependence polyhedron must be *respected* by the final schedule, i.e., every producer instance must be mapped to a logical time strictly before its consumer. The affine Farkas lemma turns this infinite family of ordering constraints into a finite linear program over the schedule coefficients [1][5].

## 4 Deep Dive

### 4.1 Iteration Domains and Access Relations as Integer Polyhedra

Consider the canonical example:

```c
for (i = 0; i < N; i++)
  for (j = i; j < N; j++)
    S: A[i][j] = A[i][j-1] + B[i];
```

The iteration domain of `S` is the triangle

```
D_S = { (i,j) in Z^2 | 0 <= i <= N-1, i <= j <= N-1 }.
```

Each array reference induces an **access relation**, an affine map from the iteration domain to the array index space. Here the write access is `W(i,j) = (i,j)` and the read accesses are `R_1(i,j) = (i,j-1)` and `R_2(i,j) = (i)` (into `B`). In isl notation these are maps such as `{ S[i,j] -> A[i,j] }` [4][8]. Composing the access relation with the statement domain yields, for every reference, the exact set of memory cells touched — no may/must approximation is needed for affine programs [7].

Imperfect nesting is handled uniformly: each statement carries its own domain and its own dimensionality, and statement order is disambiguated by constant schedule dimensions interleaved between the loop dimensions [8]. The union of all domains, with the original schedule, is a complete and exact model of the SCoP's dynamic behavior.

### 4.2 Dependence Analysis and the Affine Farkas Lemma

A dependence exists between a write instance `x` of statement `S` and a read (or write) instance `y` of statement `T` whenever both access the same location and `x` precedes `y` in the original order. For a write-write or write-read pair with access maps `f` and `g`, the **dependence polyhedron** is

```
D_{S->T} = { (x, y) in D_S x D_T | f(x) = g(y), x <<_orig y },
```

where `<<_orig` is the original execution order (a lexicographic constraint on the schedule dimensions). Emptiness of this polyhedron means no dependence; a nonempty polyhedron describes *exactly* the set of conflicting instance pairs [5][7]. Distance and direction vectors are merely the projections of this polyhedron — the polyhedron itself carries strictly more information, including non-uniform and non-constant dependences that vector methods cannot express.

The validity condition for a schedule `Theta` is that every pair in every dependence polyhedron be ordered in time. The infinite constraint family

```
(x, y) in D_e  ==>  Theta_T(y) - Theta_S(x) >= 1
```

is converted to a finite linear program by the **affine Farkas lemma** [1][5]:

> **Theorem:** (Affine Farkas lemma) Let `P = { x | A x + b >= 0 }` be a nonempty polyhedron and `psi(x) = u . x + c` an affine form. Then `psi(x) >= 0` for all `x in P` if and only if there exist multipliers `lambda_k >= 0` with `psi(x) = lambda_0 + sum_k lambda_k (a_k . x + b_k)` for all `x`.

Identifying coefficients on both sides yields linear constraints over the unknowns `(u, c, lambda)`. Hence dependence satisfaction becomes linear programming over schedule coefficients, solvable parametrically by PIP [1][5][8]. This is the technical hinge of the entire model: *legality of a transformation is equivalent to feasibility of a linear program*.

### 4.3 Affine Scheduling and Feautrier's Algorithm

A **schedule** assigns to each statement `S` an affine timestamp

```
Theta_S(x) = X_S . x + Y_S . p + rho_S,
```

possibly multidimensional: `Theta_S : D_S -> Z^d`. Validity requires `Theta_T(y) - Theta_S(x) >= delta_e` (with `delta_e >= 1` in the first dimension that separates the pair) for every dependence polyhedron `D_e` [1][5]. A one-dimensional schedule suffices when the dependence graph is acyclic in the projected sense; **multidimensional time** is needed in general, and Feautrier's Part II algorithm computes it [1].

Feautrier's algorithm is greedy and dimension-recursive [1][5]:

1. Using the Farkas-derived linear constraints, find a one-dimensional schedule that satisfies (strongly, i.e., with `>= 1`) a *maximal* subset of dependence polyhedra.
2. Remove the satisfied dependences and recurse on the remainder for the next schedule dimension.
3. Dependences that can never be strongly satisfied are *weakly* satisfied (`>= 0`) in all dimensions — they correspond to loop-carried dependences preserved by the transformation.

The algorithm minimizes the latency of the schedule and, in the multidimensional form, is optimal with respect to asymptotic parallelism extraction [1][5]. Vivien's analysis shows that Feautrier's greedy choice — maximizing the number of *dependence relations* satisfied per dimension — can be refined to a greedier variant maximizing the number of *operation-to-operation* dependences satisfied, using the vertices of the dependence polyhedra [5]. The price of this precision is compile time: each level solves a parametric integer linear program, exponential in the worst case, which is why production compilers bound the recursion and the problem sizes [2][6].

| Scheduler | Objective | Method | Optimality |
|---|---|---|---|
| Feautrier 1-D | minimum latency | Farkas LP + PIP, greedy | optimal latency |
| Feautrier multi-D | max parallelism | recursive greedy | asymptotically optimal parallelism [5] |
| Pluto | parallelism + locality | ILP cost model | heuristic, practical [2][3] |
| isl scheduler | locality/parallelism | ILP over schedule trees | heuristic [8] |

### 4.4 The Pluto Tiling Heuristic

Feautrier's schedules minimize time but ignore the memory hierarchy. The **Pluto algorithm** [2][3] revisits the affine scheduling problem with a different objective: find a set of *tiling hyperplanes* — linear forms `phi` such that dependences have non-negative components along `phi` — that simultaneously expose coarse-grain parallelism and optimize temporal locality.

Pluto formulates, for each statement, the search for transformation rows as an integer linear program. For a dependence `e` with distance polyhedron projected to a dependence vector `d`, the legality constraint is `phi . d >= 0`; the cost model then minimizes a weighted sum of dependence distances `sum_e w_e (phi . d_e)`, pushing the hyperplanes to carry as little communication as possible, while maximizing the number of outer parallel (communication-free, `phi . d = 0` for all `d`) dimensions [2]. Key design decisions of Pluto include:

- **Hyperplane-based tiling**: a set of `n` linearly independent valid hyperplanes tiles an `n`-deep loop nest into atomic tiles that can execute atomically, enabling cache blocking and parallel wavefronts [2][3].
- **Communication minimization**: the objective bounds inter-tile communication, yielding one line of near-neighbor communication per tile in the canonical examples [2].
- **Fusion/distribution structure**: Pluto decides which loops to fuse across statements by minimizing the same cost function over the shared transformation space [3].
- **Iterative refinement**: Pluto+ extends the model with a more precise cost function and a post-transformation pass, improving execution time at a modest compile-time cost (about 2.04x in cases where it helps significantly) [3].

The Pluto source-to-source chain is: C code → polyhedral extraction (Clan/PET) → dependence analysis (isl/candl) → Pluto transformer → CLooG code generation → OpenMP C [10]. This pipeline has been validated extensively on PolyBench/C, where Pluto-generated tiled and parallel code routinely matches or approaches hand-optimized performance on multicores [2][3][6].

### 4.5 AST Code Generation: CLooG and isl

A schedule is an abstract mapping; **code generation** materializes it as loop nests. Given transformed polyhedra `{ (t, x) | t = Theta_S(x), x in D_S }`, the generator must emit loops that visit each integer point exactly once, with loop bounds that are as tight and as cheap as possible. **CLooG** (Chunky Loop Generator) solves this by recursive projection: it projects the polyhedron onto the outermost time dimension, generates a loop over that projection, and recurses into the resulting slices, producing an abstract syntax tree of loops and guards [10]. The Quilleré–Rajopadhye–Wonnacott separation of *polyhedral scanning* from *transformation* made CLooG a reusable backend for LooPo, Pluto, Graphite, and others [10].

Modern flows increasingly use **isl's AST generator** [8], which operates on *schedule trees* — a structured representation of the schedule as nested bands (sequence, set, band nodes) — and generates code with better control over separation, atomicity annotations, and parallelism markings. The isl manual documents the full chain: Presburger formulas for sets and relations, the scheduler, schedule trees, and the AST builder, all in one coherent library [8]. LLVM's MLIR affine dialect adopts the same conceptual split, debating explicitly whether schedules and domains should live in the IR or be materialized eagerly by transformations [9].

Tiled code generation illustrates the machinery at its most demanding. For a tile schedule `(T_i, T_j)` with tile sizes `(B_i, B_j)`, the generator emits:

```c
for (T_i = 0; T_i <= (N-1)/B_i; T_i++)
  for (T_j = 0; T_j <= (N-1)/B_j; T_j++)
    for (i = max(T_i*B_i, ...); i <= min((T_i+1)*B_i - 1, ...); i++)
      for (j = ...; j <= ...; j++)
        S(i, j);
```

where the inner bounds are the exact projections of the tiled polyhedron — no over-approximation, no redundant guards when the projection is exact [8][10].

## 5 Empirical Results / Formal Proofs

### 5.1 Validity theorem (proof sketch)

> **Theorem:** Let `Theta = { Theta_S }` be affine schedules such that for every dependence polyhedron `D_e` from `S` to `T`, the Farkas-derived linear constraints imply `Theta_T(y) - Theta_S(x) >= 1` for all `(x,y) in D_e` in the first schedule dimension where the two instances differ, and `>= 0` in earlier dimensions. Then any execution order consistent with `Theta` preserves program semantics.

*Proof sketch.* By the affine Farkas lemma, the linear constraints certify the implication over the whole (possibly parametric, infinite) polyhedron `D_e`; no instance pair is missed [1][5]. If `(x,y) in D_e`, then `x` writes a location that `y` reads or writes, and the constraint forces `Theta_S(x)` lexicographically before `Theta_T(y)`. Hence every read sees the same last write as in the original order, and every write-write pair keeps its order: the observable memory behavior is unchanged. Multidimensional schedules recurse on the residual dependences, so the argument applies dimension by dimension [1]. ∎

### 5.2 Empirical evidence

The Pluto framework was evaluated on the PolyBench/C suite against then-current parallelizers, demonstrating that automatic tiling plus OpenMP parallelization from a single affine model yields large speedups on multicores without manual tuning [2]. Pluto+ further improved locality modeling with only a moderate increase in optimization time [3]. An independent line of work builds a *performance vocabulary* of ILP constraints and objectives — stride optimization, parallelism/reuse trade-offs, unroll-and-jam cost models — and shows, on a 10-core Intel Core-i9 (Skylake-X), performance comparable or superior to Pluto across most PolyBench kernels, without source-level tiling or autotuning [6]. The FDTD-2D case study in that work is instructive: 567 Pluto tile configurations produce a wide performance distribution, motivating richer cost models that capture cache-line usage and vector-register width [6]. Recent work unifies the temporal and spatial locality models in a single framework, showing that restrictions to linearly independent schedule dimensions miss profitable schedules that decouple locality from parallelization [7].

## 6 Limitations

1. **SCoP restriction.** Non-affine control flow, while loops, pointer-chasing data structures, and indirect subscripts fall outside the model. Real programs require hybrid analyses, and SCoP detection failures silently disable optimization [4][9].
2. **Compile-time complexity.** Fourier-Motzkin elimination, vertex enumeration (Chernikova), and parametric integer programming are exponential in the worst case. Feautrier's scheduler and Pluto's ILP can dominate compile time on deep nests, which is why production compilers cap dimensions and time out gracefully [1][2][6].
3. **Cost-model fidelity.** The polyhedral model is exact about *legality* but approximate about *profitability*: cache associativity, prefetchers, SIMD widths, and NUMA effects are not polyhedral concepts. Bridging this gap requires external cost models and ILP objectives [6][7].
4. **Code bloat and control overhead.** Generated loop nests carry `min`/`max` bounds and guards whose overhead can erase gains on small trip counts; separation and simplification passes mitigate but do not eliminate this [8][10].
5. **Parametric undecidability edges.** Dependence analysis with arbitrary symbolic parameters and Presburger arithmetic with multiplication by parameters leaves the decidable fragment; tools restrict themselves to affine forms to stay decidable [4][5].

---

## 7 Conclusion

The polyhedral model remains the most principled framework for loop optimization: it replaces heuristic pattern-matching on loop nests with exact geometry. Iteration domains and access relations give a complete static description of dynamic behavior; dependence polyhedra capture every producer-consumer pair exactly; the affine Farkas lemma reduces legality to linear programming; Feautrier's algorithm extracts optimal multidimensional schedules; Pluto's cost model turns those schedules into tiled, parallel, locality-optimized code; and CLooG/isl materialize the mathematics as efficient loop nests [1][2][3][4][8][10]. Its limits — the SCoP boundary, compile-time cost, and the legality/profitability gap — define the active research frontier, from performance vocabularies [6] to unified locality models [7] and MLIR's rethinking of how polyhedral concepts should live inside a compiler IR [9]. For the affine programs that dominate scientific computing, the lesson of four decades stands: *geometry first, heuristics second*.
