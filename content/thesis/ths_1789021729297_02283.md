# Learned Index Structures: Recursive Model Indexes, ALEX, and the PGM-Index — Replacing B-Trees with Learned Models

## Abstract

The 2018 proposal by Kraska et al. that *indexes are models* — a B-tree maps keys to positions, a hash index maps keys to slots, a Bloom filter classifies membership — founded learned index structures, in which the empirical CDF of the key set is approximated by a learned function and queries are answered by *predict-then-correct*: evaluate the model, then run a bounded local search inside its error interval. This post treats the three pillars of the field. The **Recursive Model Index (RMI)** arranges simple models in a two-stage hierarchy: a root model routes each key to a leaf model that predicts its position with measured error bounds, beating cache-optimized B-trees by up to 70% at an order of magnitude less memory. **ALEX** makes learned indexes updatable through gapped arrays, model-based inserts, and cost-model-driven node splits. The **PGM-index** reduces learned indexing to optimal piecewise-linear ε-approximation of the CDF, adding provable worst-case bounds and a dynamic logarithmic-method variant. We also cover learned Bloom filters with sandwiching, RadixSpline, SOSD benchmark results, and limitations: distribution shift, retraining costs, and the last-mile search tax.

## 1 Introduction

For half a century the B-tree and its variants have been the default answer to the question *"given a key, where is its record?"* Their dominance rests on a powerful generality: they assume nothing about the data and guarantee O(log_B n) I/Os regardless of distribution. The learned-index hypothesis, introduced by Kraska, Beutel, Chi, Dean, and Polyzotis at SIGMOD 2018, is that this generality is exactly the inefficiency: *knowing the exact data distribution enables highly optimizing almost any index structure* [1]. If keys are the integers 1…100M, no one would build a B-tree — the key itself is the offset, an O(1) lookup with O(1) memory. A learned index generalizes this observation: fit a model F̂ to the empirical CDF of the key set, so that

> *Theorem:* Let sorted keys k_0 < k_1 < … < k_{n−1} have rank function rank(k) = |{i : k_i ≤ k}|. If a learned index h: U → [0, n] satisfies |h(q) − rank(q)| ≤ ε for all queries q, then lookup reduces to evaluating h plus a correction search over at most 2ε + 1 array positions [3][5].

The formulation converts pointer-chasing tree traversal into constant-time function evaluation, makes the error budget explicit and tunable, and exposes indexing as statistical learning over a smooth, monotone, one-dimensional CDF target.

## 2 Background

### 2.1 The sorted-array model and the CDF view

Consider n key–payload pairs stored in a sorted dense array A. The fundamental lookup primitive is *rank*: given a query key x, return the number of stored keys ≤ x; membership, predecessor, and range queries all reduce to it [3]. If P(A ≤ x) denotes the proportion of elements no larger than x, then pos(x) = ⌊n · P(A ≤ x)⌋ — the position is a scaled CDF [6]. The CDF of a fixed key set is a deterministic, monotone, stepwise function; any model that approximates it well is an index. This is the insight the RMI reference implementation distills to a single sentence: *a learned index is a function mapping a key to an approximate index, used as the starting point for a linear, exponential, or binary search* [1].

Three classical structures are recovered as special cases of the model view [1]:

- **B-tree (range index):** a model mapping a key to the *page* (or position) of the first record in a range, with min/max error bounds — page boundaries.
- **Hash index:** a model mapping a key to a position in an *unsorted* array, with collision resolution as the correction step.
- **Bitmap/Bloom index:** a model (binary classifier) predicting key *existence*, with false positives as its error and a backup structure for the residual.

### 2.2 Predict-then-correct and the last-mile search

Because a learned model is approximate, every learned-index lookup has two phases: (1) *model evaluation* (constant-time arithmetic), and (2) *last-mile correction search* inside the error window. The choice of correction algorithm matters enormously:

1. **Bounded binary search** over [p̂ − ε_lo, p̂ + ε_hi]: O(log ε) comparisons, deterministic, cache-unfriendly for large ε.
2. **Exponential (galloping) search** from the predicted position p̂: doubling strides outward until bracketing the target, then binary search within the bracket. When the model is accurate, this finds the key in O(log |p̂ − rank(x)|) steps and *always beats binary search* [2]; it is the default correction in ALEX and in most SOSD contestants.
3. **Linear scan** when ε is tiny (a few positions) — the RMI often lands within a cache line.

A recent micro-architectural study of correction routines on the SOSD platform confirms that for datasets larger than cache, data-cache-miss stalls dominate, and the *quality of the prediction interval* — not the model evaluation — decides the race [7]. This foreshadows Section 5's finding: in the PGM-index, internal error-bounded search consumes 69–81% of total lookup overhead, versus only 19–27% in an optimized RMI, which explains much of RMI's practical lead [6].

### 2.3 Error-bounded approximation

The quality of a learned index is governed by its *maximum prediction error* ε. Two families of approximators dominate:

- **Linear regression models:** f(x) = a·x + b fit by least squares or by min-max-error linear fits. Cheap to evaluate (one multiply-add), surprisingly accurate on locally smooth CDFs.
- **Piecewise-linear approximation (PLA):** partition the sorted keys into segments, fit one line per segment, guarantee |F̂(x) − rank(x)| ≤ ε for all x. The number of segments m controls space; the classic greedy "shrinking cone" streaming algorithm builds a *minimum-cardinality* ε-PLA in O(n) time and O(1) space [3][5].

The streaming optimal PLA is the mathematical core of the PGM-index, and it is worth stating precisely:

> *Theorem (Optimal ε-PLA):* Given n points (k_i, rank(k_i)) with strictly increasing keys, there exists a streaming algorithm that computes a piecewise-linear function with the minimum possible number of segments such that every point is approximated within vertical error ε, in O(n) time and O(m) space, where m is the number of segments produced [3].

## 3 Methodology

Our treatment follows a uniform analytical framework across all structures, so that claims are comparable.

**Definitions.** A *static learned index* is a data structure built once over a fixed sorted key set S, |S| = n, supporting rank queries with worst-case or empirical error ε. A *dynamic learned index* additionally supports insert/delete with amortized update cost. The *space* of an index is measured in bytes of model parameters plus auxiliary structures (excluding the payload array itself, shared by all contestants).

**Cost decomposition.** We decompose expected lookup time as

T_lookup = T_descend + T_eval + T_correct

where T_descend is internal navigation (zero for one-level models; segment lookup for multi-level ones), T_eval is model arithmetic, and T_correct is the last-mile search as a function of ε. This decomposition is not merely expository: the "Why Are Learned Indexes So Effective" study shows T_descend + T_correct (internal search) accounts for up to 81% of PGM-index lookup time, so minimizing ε and the number of levels is the decisive design pressure [6].

**Evaluation discipline.** Reported numbers follow the SOSD (Search on Sorted Data) methodology [7]: 200M-key real datasets (amzn book popularity, face Facebook IDs, osm OpenStreetMap locations, wiki Wikipedia timestamps), uniform random lookups, dense sorted packed arrays, in-memory. The companion benchmark by Marcus et al. compares tuned learned indexes against state-of-the-art traditional baselines (B+tree, ART, FAST, binary/interpolation search) and studies caching, pipelining, key size, and build time [6]. We adopt their headline results and add the update workloads from the ALEX paper (read-only, read-heavy 95/5, write-heavy 50/50) [2].

**Retraining and dynamics.** For updatable structures we model updates as *distribution drift*: an index is accurate only while the learned CDF matches the stored CDF.

## 4 Deep Dive

### 4.1 The Recursive Model Index: learning the CDF hierarchically

The Recursive Model Index (RMI), the prototype learned index of Kraska et al. [1], addresses a basic tension: a single global model cannot fit a complex CDF (think of the heavy-tailed osm dataset), while a separate model per key region needs a routing mechanism. The RMI's answer is a *hierarchy of simple models* trained bottom-up.

**Architecture.** A typical RMI has two stages. The *root model* f_0 takes a key and outputs (a scaled version of) the index j of the *leaf model* responsible for that key's region. Each *leaf model* f_{1,j} maps the key to a predicted position p̂ in the sorted array. During training, every key is assigned to the leaf its root prediction selects, each leaf is fit (e.g., linear regression) on its assigned keys, and — critically — each leaf records its *maximum positive and negative prediction errors* on the training set. At query time:

```python
def rmi_lookup(key):
    leaf = int(root_model.predict(key) * num_leaves)   # route
    pos  = leaf_models[leaf].predict(key)              # predict
    lo, hi = pos - max_neg_err[leaf], pos + max_pos_err[leaf]
    return bounded_search(array, key, lo, hi)           # correct
```

The root model need not be accurate — it only routes — so a coarse linear model suffices; the leaves do the precise work [1]. Because leaf error bounds are *measured*, not assumed, correctness is unconditional: the true position is guaranteed inside [lo, hi]. Neural-network leaf models (a staged "zero → hidden → output" design) delivered the paper's headline: up to **70% faster than cache-optimized B-trees while saving an order of magnitude in memory** across real datasets [1].

The hierarchy's elegance is that model prediction *directly serves as the index into the next level*, bypassing any internal error-bounded search — the structural difference that lets an optimized RMI beat the PGM-index in practice despite weaker theory [6].

### 4.2 ALEX: updatable learned indexes via gapped arrays and model-based inserts

Static RMIs cannot absorb inserts without retraining — a fatal flaw for OLTP. ALEX (Ding et al., SIGMOD 2020) is the first learned index engineered for updates, and its design is a masterclass in co-designing data layout with the model [2].

**Gapped arrays.** ALEX stores records in each leaf *data node* in a **gapped array**: an array with empty slots interspersed, kept at a target density. Inserts go to *model-predicted positions* ("model-based inserts"): the leaf's linear model predicts where the key belongs, and the key is placed at or near that slot. Because insertions land near their predictions, the model stays accurate without retraining — the structure's central trick. Gaps are filled with copies of adjacent keys so that exponential search operates over a dense logical array; when the predicted slot is occupied, keys shift locally (amortized O(1) thanks to gaps) or the node splits/expands.

**Adaptive structure with cost models.** Like a B+tree, ALEX grows and shrinks nodes at different rates, but its decisions are learned-index-aware: each data node tracks its empirical cost (expected lookup + insert cost under the current model), and *expansion* (grow the gapped array, keep the model), *split* (partition the key space, retrain children), or *merge* is triggered by cost-model thresholds rather than fixed fill factors. This eliminates manual tuning and keeps performance robust under skewed or drifting distributions [2].

Reported results (200M keys, YCSB-like workloads): read-only throughput matches or beats B+trees and stays within ~2× of a static RMI; the 95/5 read-heavy workload is faster and smaller than a B+tree; the 50/50 write-heavy workload reaches parity with B+trees at smaller size [2]. The caveat is *adversarial* updates that break the learned CDF: then ALEX splits frequently and the B-tree catches up — the price of betting on distribution stability.

### 4.3 The PGM-index: optimal piecewise-linear approximation with provable bounds

If the RMI is the practitioner's learned index and ALEX the dynamic one, the PGM-index (Ferragina & Vinciguerra, PVLDB 2020) is the *theorist's* — it gives learned indexing worst-case guarantees competitive with B-trees [3].

**The geometric reduction.** Building a learned index is recast as a computational-geometry problem: approximate the point set {(k_i, rank(k_i))} by the fewest ε-bounded line segments. The streaming OptimalPLA algorithm produces the *minimum-complexity* piecewise-linear ε-approximation in O(n) time [3]. Each segment stores its slope, intercept, and first key; the index is then built *recursively*: level ℓ+1 indexes the first keys of level ℓ's segments, until one segment remains at the top. Querying descends the levels — each step a segment evaluation plus a bounded search of width 2ε over the next level's segment array — and finishes with the last-mile search over the data.

**Complexity.** With m segments at the bottom level and error bound ε:

| Operation | PGM-index | B-tree (fanout B) |
|---|---|---|
| Space | Θ(m) segments — *independent of n* beyond m | Θ(n) pointers/keys |
| Static query | O(log m · log ε) worst case | O(log_B n) |
| Build | O(n) streaming | O(n log n) typical |

Because m shrinks as ε grows, the PGM-index trades a tunable knob (ε) directly against space and time — something B-trees cannot do. Empirically, the static PGM-index *matches the query performance of a cache-optimized static B-tree within two orders of magnitude (83×) less space* [3].

**Fully-dynamic variant.** The dynamic PGM-index applies the *logarithmic method*: maintain O(log n) static PGM-indexes of geometrically growing capacities, insert into the smallest, and merge on overflow — yielding amortized O(log² n) updates with provable worst-case query bounds. In the dynamic setting it improves B-tree query *and* update time by up to 71% within three orders of magnitude (1140×) less space [3].

### 4.4 Learned Bloom filters and the sandwiching optimization

Kraska et al. observed that a Bloom filter is a binary classifier: train f: U → [0,1] to predict membership, pick a threshold τ, and answer "yes" when f(y) ≥ τ [1]. The catch is *false negatives* — the model may score a true member below τ — which are eliminated by a classical **backup Bloom filter** holding exactly {z ∈ K : f(z) < τ}. The learned filter's false-positive rate then combines the model's FPR with the backup's.

Mitzenmacher (NeurIPS 2018) put this construction on firm analytical footing and proposed the **sandwiching** optimization: place the learned oracle *between two* classical Bloom filters — an initial filter first, then the model, then the backup filter [4]. The analysis yields a closed-form optimal split of the bit budget between the two filters. The headline insight: sandwiching *always* improves on the naive learned Bloom filter for the same total space, because the initial filter cheaply discards the bulk of negatives before the model is even evaluated [4].

## 5 Empirical Results and Complexity Analysis

### 5.1 Head-to-head: learned vs. traditional

The SOSD benchmark [7] and the Marcus et al. study [6] provide the most careful comparisons. Key findings on 200M-key real datasets:

- **Read-only in-memory lookups over dense arrays:** tuned learned indexes (RMI, PGM, RadixSpline) *consistently outperform* state-of-the-art traditional indexes (B+tree, ART, FAST, binary search) on lookup time *and* index size; they lose only on build time [6].
- **Why RMI wins in practice:** the internal-search decomposition shows PGM spends 69–81% of lookup time in error-bounded internal search across levels, while RMI — whose predictions index the next level directly — spends only 19–27% [6]. Fewer levels and tighter ε dominate raw model sophistication.

### 5.2 The update dimension

| Index | Insert support | Update cost | Space | Worst-case guarantees |
|---|---|---|---|---|
| RMI [1] | No (rebuild) | O(n) rebuild | O(#models), tiny | None (empirical ε) |
| RadixSpline [5] | No | — | O(#spline points) | ε-bounded lookup |
| ALEX [2] | Yes (in-place) | Amortized O(1) typical | Gapped arrays + models | Cost-model driven, no hard bounds |
| PGM-index [3] | Yes (logarithmic) | Amortized O(log² n) | O(m) segments | Provable bounds |
| B+tree | Yes | O(log_B n) | O(n) | Full |

Lan et al.'s external-memory study is the sobering counterpoint: once inner nodes fit in memory and I/O dominates, *none* of the updatable learned indexes are competitive with B-trees on disk (Lan et al., 2023). The learned-index advantage is, at present, an **in-memory** phenomenon.

### 5.3 Space: the order-of-magnitude story

The most robust claim in the literature is not speed but *size*. Kraska et al. reported an order of magnitude less memory than B-trees [1]; the PGM-index makes it quantitative — 83× less space at equal static query speed, 1140× less in the dynamic setting [3].

## 6 Limitations

A PhD-level treatment must be candid about where the paradigm strains.

1. **Distribution shift and adversarial updates.** Every learned index bets that the future resembles the training set. ALEX degrades under CDF-breaking insert patterns, splitting frequently until it resembles the B-tree it sought to replace [2]. Static RMIs require full rebuilds; choosing *when* to retrain is an unsolved policy problem in general.
2. **The last-mile tax.** The model is only half the lookup. As ε grows — on hard distributions like osm, where RMI's predicted interval averages 5.26M positions — correction search dominates and the advantage evaporates [7]. LIPP (VLDB 2021) attacks exactly this by placing keys at *exact* predicted positions, removing last-mile search at the cost of memory.
3. **Build time and tunability.** Learned indexes lose to B-trees on build time [6]; RMI hyperparameters (depth, leaf count, model class) interact non-trivially with accuracy, and misconfiguration silently inflates ε (Maltry & Dittrich's critical analysis). RadixSpline and PLEX reduce this to one or two knobs [5], but the "it just works" bar of B-trees remains unmet.
4. **Weak guarantees for the popular designs.** RMI and ALEX offer empirical error bounds, not worst-case ones; only the PGM-index provides provable bounds [3]. Systems builders who need latency SLOs under adversarial workloads still reach for B-trees.
5. **The memory-hierarchy boundary.** Learned indexes win in RAM, where model evaluation is nearly free and cache misses are the currency. On disk, where one random I/O dwarfs all computation, the calculus flips and B-trees remain unbeaten [Lan et al.].
6. **Learned Bloom filter fragility.** The sandwiching analysis assumes the query distribution matches training; under distribution shift the model's FPR estimates — and the backup filter's sizing — become unreliable, while classical Bloom filters guarantee their FPR for *any* subset [4].

## 7 Conclusion

Learned index structures replaced a fifty-year-old assumption — that an index must be distribution-agnostic — with a better one: that data has learnable structure worth exploiting. The RMI showed that a hierarchy of tiny models can beat a cache-optimized B-tree by 70% at a tenth of the memory [1]; ALEX showed that model-based inserts into gapped arrays make learned indexes updatable without surrendering the win [2]; the PGM-index showed that the whole enterprise reduces to optimal piecewise-linear approximation with provable bounds [3]; and learned Bloom filters with sandwiching showed the idea extends beyond ordered indexes to approximate membership [4].

The honest assessment, a decade into the program, is bifurcated. For *read-heavy, in-memory, dense-array* workloads, learned indexes are the state of the art — smaller and faster than anything classical, as the SOSD line of benchmarks has repeatedly confirmed [6][7]. The most promising direction is therefore *hybridization*: PGM's guarantees, ALEX's adaptivity, and classical fallbacks where worst-case discipline matters. Kraska et al.'s deeper thesis — that learned components will permeate query optimizers, sorters, schedulers, and caches — is well on its way: learned sorting already runs 1.49–5× faster than state-of-the-art sorters on integer keys (Lan et al., 2023), and close to a hundred learned index variants have been proposed. The B-tree is not dead. But it is no longer the only answer.
