# Columnar Query Engines: Apache Arrow, Vectorized Execution, and Push-Based Design in DataFusion

## Abstract

The convergence of columnar in-memory representations, vectorized (batch-at-a-time) execution, and push-based operator scheduling has redefined analytical query-engine performance. This thesis unifies these pillars through Apache DataFusion, a modular, embeddable engine built directly on Apache Arrow [1][3]. We formalize Arrow's buffer triples — validity bitmaps, offset vectors, densely packed value regions — and derive the cache-traffic equations governing selective scans, including a scan-cost dominance theorem. We reconstruct the vectorized model of MonetDB/X100 [2], showing analytically why cache-sized vectors escape both the interpretation overhead of the tuple-at-a-time Volcano iterator [4] and the memory-bandwidth blowup of full-column materialization, and prove a cache-residency lemma for vectorized pipelines. We formalize push-based, morsel-driven scheduling [5] as a labeled transition system and prove a skew-robustness bound for work-stealing dispatch. We then map each formal element onto DataFusion's design — RecordBatches as the unit of exchange and scheduling, vectorized kernels, partition-level parallelism — and its trajectory toward morsel-granular execution. A roofline-style model predicts the regimes in which each pillar dominates. We close with open problems in byte-adaptive batch sizing, late-materialization joins, backpressured push scheduling, and zero-copy UDF boundaries.

## 1 Introduction

Analytical database engines have undergone a fundamental architectural migration over the past two decades. The row-oriented, tuple-at-a-time Volcano iterator model that dominated systems of the 1990s [4] has been displaced, for scan-heavy analytical workloads, by three mutually reinforcing ideas: columnar in-memory layouts, vectorized execution, and push-based scheduling. While these ideas originated in different systems — C-Store and MonetDB for columnar storage, MonetDB/X100 for vectorization [2], and HyPer for morsel-driven push execution [5] — they have recently converged in a single open ecosystem: Apache Arrow [1] supplies the standardized columnar substrate, and Apache DataFusion [3] builds a full SQL engine upon it in Rust.

This thesis treats that convergence as its object of study. Our contributions are:

1. **A memory-hierarchy-first account of Arrow's columnar layout**, formalizing the buffer triples (validity, offsets, data) and deriving the cache-traffic equations that govern scan cost under selectivity.
2. **An analytical comparison of three processing models** — tuple-at-a-time, vectorized, and compiled data-centric — using an explicit cost model with instruction-cache, data-cache, and branch-prediction terms, grounded in the X100 design rationale [2].
3. **A push-based execution semantics for morsel-driven engines** with a proved skew-robustness theorem for work-stealing dispatch.
4. **A detailed reading of DataFusion's architecture** [3]: how Arrow RecordBatches become the unit of both data exchange and scheduling, where vectorization lives in its kernels, and where its parallelism model sits relative to morsel-driven scheduling.
5. **A quantitative regime analysis** identifying when each design choice dominates, plus a candid discussion of limitations.

## 2 Background

### 2.1 From tuples to columns

Row-oriented (NSM) storage lays out each record contiguously; column-oriented (DSM) storage lays out each attribute contiguously. For analytical queries that touch few columns of wide tables, columnar layouts reduce I/O and memory traffic by the ratio of projected to total columns — the classic projection argument. Apache Arrow [1] standardizes this idea as a *language-agnostic in-memory* specification: arrays are sequences of slots decomposed into physical buffers. A primitive array, for instance, is the triple

- a **validity bitmap** (1 bit per slot, null tracking),
- a **values buffer** (densely packed fixed-width values),

while a variable-width binary array adds an **offsets buffer** of int32/int64 boundaries. Buffers are padded to 64-byte alignment, the format is relocatable without pointer swizzling, and random access is O(1). These properties make the format SIMD-friendly and zero-copy across process and language boundaries via the Arrow IPC protocol, whose primitive message unit is the **RecordBatch** — an ordered collection of equally-long arrays sharing one schema [1].

### 2.2 The Volcano model and its costs

Graefe's Volcano model [4] composes query operators as iterators exposing `open()`, `next()`, and `close()`. Control flows top-down: the consumer calls `next()` on its child, which recursively calls `next()` on *its* child, until a single tuple bubbles to the top. The model is supremely composable and makes operators like `LIMIT` trivially efficient, but every tuple pays a virtual-function dispatch chain through the whole operator stack. On modern superscalar CPUs this manifests as low instructions-per-cycle (IPC): branch mispredictions and instruction-cache misses dominate, and Boncz et al. measured MySQL 4.1 achieving an IPC of only 0.7 on TPC-H Q1, spending under 10% of its time in actual arithmetic [2].

### 2.3 Vectorization: the X100 middle ground

MonetDB/X100 [2] rejected both extremes — tuple-at-a-time interpretation and MonetDB/MIL's full-column materialization (which saturates memory bandwidth) — in favor of *hyper-pipelining*: process vectors of roughly 1000 values, sized so that intermediate results stay resident in CPU caches. Each vector carries a selection vector recording which positions survived filtering, so selection need not materialize. Operators are written as tight loops over dense arrays, exposing auto-vectorization to the compiler and explicit SIMD to the programmer. Their measured result on TPC-H Q1 at scale factor 1: 0.50s for X100 versus 26.6s for MySQL and 3.7s for MonetDB/MIL [2].

### 2.4 Push versus pull: morsel-driven execution

Leis et al. [5] introduced morsel-driven parallelism for HyPer: split the input into fixed-size morsels (on the order of 10^5 tuples), dispatch them via a lock-free queue to worker threads pinned to NUMA nodes, and have each worker push its morsel through the *entire* operator pipeline to the next pipeline breaker. This inverts Volcano's control flow: data flows bottom-up, pushed by producers, rather than being pulled top-down by consumers. The degree of parallelism becomes a runtime property of data availability rather than a plan-time constant, and work stealing absorbs skew. HyPer reported speedups above 30x on 32 cores on TPC-H [5], compared with under 10x for statically partitioned exchange-operator parallelism.

### 2.5 DataFusion in one paragraph

Apache DataFusion [3] is an extensible, embeddable analytical query engine written in Rust, built natively on Apache Arrow. Its physical plans are executed as streams of `RecordBatch` (each typically 8192 rows), its expression evaluation and kernels are vectorized over Arrow arrays, and intra-query parallelism is achieved by partitioning input streams across Tokio tasks. The SIGMOD Companion paper [3] presents it as evidence that a modular, community-built engine can reach state-of-the-art performance without a monolithic rewrite — precisely because Arrow, Parquet, and the Rust ecosystem commoditize the hard substrate.

## 3 Methodology

Our method is *architectural reconstruction with quantitative teeth*. Rather than benchmarking (which would measure one snapshot of a moving codebase), we:

1. **Formalize.** We give the Arrow array layout and the three processing models as small mathematical objects: buffer triples, cost recurrences, and a labeled transition system for push pipelines.
2. **Derive.** From these we derive closed-form cost expressions parameterized by selectivity σ, vector size V, column width w, cache line size L, and morsel size M.
3. **Prove.** We state and prove (proof sketches) a skew-robustness theorem for morsel scheduling and a cache-residency lemma for vectorized pipelines.
4. **Map.** We map each formal element to its concrete realization in DataFusion [3], citing the engine's actual abstractions (RecordBatch streams, physical operators, partition dispatch).
5. **Bound.** We identify, via a roofline-style argument, the workload regimes in which each pillar is load-bearing and where it ceases to matter.

Where concrete numbers appear (e.g., X100's TPC-H Q1 figures [2], HyPer's 30x [5]), they are reported measurements from the cited papers, not our own.

## 4 Deep Dive

### 4.1 The Arrow buffer algebra: why columnar wins the memory hierarchy

Consider a scan with a filter of selectivity σ over a table with C columns of width w bytes each, projecting P columns. In a row store, touching N rows moves roughly N·C·w bytes (modulo compression). In a columnar store, the scan moves N·P·w bytes plus the validity bitmaps, a factor-C/P reduction in the streaming term. Arrow strengthens this with two subtler properties [1]:

- **Validity as bitmap, not sentinel.** Null tracking costs 1 bit per value instead of widening every value to a nullable representation, keeping values buffers dense and SIMD-lane-aligned.
- **Offsets enable slicing without copying.** A filter producing a selection vector, or a `LIMIT k`, can be represented as offset arithmetic on the same buffers — Arrow's zero-copy slicing. Only materializing operators (sort, hash build) must copy.

> **Theorem:** *(Scan-cost dominance.)* Let a columnar scan over N rows project P of C fixed-width columns, each w bytes, with filter selectivity σ applied before projection, and let δ be the validity-bitmap overhead per row. Then the streaming memory traffic satisfies T_col ≤ N·(P·w + δ) bytes, while a row store with the same filter pays T_row ≥ N·σ⁻¹·(C·w) in the worst case when filtering cannot be pushed below the row fetch, i.e., the columnar advantage is at least (C·w)/(σ·(P·w + δ)).

*Proof sketch.* The columnar scan streams each projected column once, sequentially, touching exactly N·(P·w + δ) bytes; validity bits are streamed at 1 bit/value. The row store must fetch entire rows to evaluate the predicate before filtering can discard them, so it moves N·C·w bytes to retain σN rows. The ratio follows by division. ∎

The theorem's real content is not the inequality but its *assumption*: the columnar engine must evaluate the predicate from the projected columns alone and must not re-materialize rows. This is exactly what vectorized selection vectors accomplish.

### 4.2 Vectorized execution: amortizing interpretation over cache-sized batches

X100's core quantitative argument [2] can be reconstructed as follows. Let c_interp be the per-tuple interpretation overhead (virtual dispatch, branch misprediction) of the Volcano model, c_kernel the per-tuple cost of a tight compiled loop over a dense array, and c_mem the per-byte memory cost. Then:

| Model | Per-tuple interpretation | Intermediate materialization |
|---|---|---|
| Volcano tuple-at-a-time [4] | c_interp (per tuple, full operator chain) | none (pipelined) |
| Full-column materialization | c_interp / N (amortized) | N·w bytes per operator boundary |
| Vectorized (V ≈ 1024) [2] | c_interp / V (amortized) | V·w bytes (cache-resident) |

The vectorized row pays interpretation once per vector, not once per tuple, recovering a factor ~V on the dominant cost term, while its intermediates live in L1/L2 rather than DRAM. The compiler can now auto-vectorize the inner loop because it sees a counted loop over a flat array — the "hyper-pipelining" of the paper's title [2].

> **Theorem:** *(Cache-residency lemma.)* Let a pipeline of k vectorized operators each maintain O(1) state per vector plus input/output vectors of size V·w bytes. If k·V·w ≤ L_cache (the usable L1/L2 capacity), then the steady-state data-cache traffic per output tuple is O(w) regardless of k.

*Proof sketch.* By induction over the pipeline: operator i reads its input vector and writes its output vector, both resident from the previous step; with k·V·w ≤ L_cache no vector is evicted between production and consumption, so each tuple's bytes cross the cache hierarchy boundary exactly once on load and once on final store. ∎

This lemma is the formal shadow of X100's design rule that vectors hold "ca. 1000 entries" [2].

A Rust-flavored sketch of the pattern:

```rust
// Vectorized filter kernel: predicate evaluated once per batch,
// selection vector avoids materializing rejected rows.
fn filter_batch(batch: &RecordBatch, pred: &BooleanArray) -> RecordBatch {
    let indices: Vec<u32> = (0..batch.num_rows() as u32)
        .filter(|&i| pred.value(i as usize))
        .collect();
    let idx = UInt32Array::from(indices);
    batch.columns().iter()
        .map(|c| take(c.as_ref(), &idx, None).unwrap())
        .collect::<Vec<_>>()
        .into() // new RecordBatch sharing buffers where untouched
}
```

Note the `take` with an index array: this is late materialization at the batch level, and where columns are merely passed through, Arrow's reference-counted buffers make the "copy" free [1].

### 4.3 Push-based execution: inverting the iterator

The Volcano iterator is *pull*: `next()` requests flow down, tuples flow up. Push-based execution reverses the arrows: a source operator *produces* a morsel and *pushes* it into its parent, which transforms it and pushes it onward, until a pipeline breaker (hash-table build, sort, aggregation) materializes it. Control is data-driven rather than demand-driven.

We model a pipeline as a labeled transition system over morsel states:

```tla
---- MODULE PushPipeline ----
EXTENDS Naturals, Sequences
CONSTANTS Workers, MorselSize
VARIABLES queue,         \* sequence of unprocessed morsels
          active,        \* worker -> morsel-or-None
          sinks          \* breaker-local partial results

Dispatch(w) == /\ queue /= <<>>
               /\ active[w] = None
               /\ LET m == Head(queue) IN
                  /\ queue' = Tail(queue)
                  /\ active' = [active EXCEPT ![w] = m]
                  /\ UNCHANGED sinks
```

Each worker then applies the full operator chain to its morsel — a *vertical* slice of the plan — before returning for another morsel. The scheduler's only shared state is the morsel queue, so coordination cost is O(1) per morsel rather than O(1) per tuple as in Volcano's per-tuple dispatch chain [4][5].

Why does this matter for parallelism? In the exchange-operator model, the degree of parallelism is baked into the plan: each exchange partitions data among a fixed set of threads, and skew in the partitioning becomes skew in completion time. In the morsel model, the degree of parallelism is *elastic*: it equals the number of live morsels, and work stealing rebalances dynamically.

> **Theorem:** *(Skew robustness of morsel scheduling.)* Let W be total work divided into morsels of size M, executed by p workers with work stealing, where each morsel's processing time lies in [t_min, t_max] with ratio ρ = t_max/t_min. Then the makespan T satisfies T ≤ (W/p)·ρ + O(p·t_max), i.e., the skew penalty is bounded by the morsel granularity rather than by any static partition.

*Proof sketch.* Standard work-stealing analysis: each worker processes morsels from its local deque and steals from others when empty. The total idle time is bounded by O(p) steal attempts each costing O(t_max); every unit of work is processed exactly once, giving W/p ideal time, and the slowest morsel delays termination by at most a factor ρ relative to uniform morsels. No term depends on data skew across partitions, because partitions do not exist. ∎

DuckDB's adoption of this model [6] — pull-based *within* a pipeline (vectors flow operator to operator) but morsel-driven *across* threads — shows the two ideas compose: vectorization governs the inner loop, morsel scheduling governs the thread pool.

### 4.4 DataFusion's synthesis: Arrow as the unit of everything

DataFusion [3] is the existence proof that the three pillars compose in a modular, embeddable engine:

1. **Arrow as substrate.** Every operator consumes and produces `RecordBatch` streams. Because Arrow arrays are reference-counted buffer triples, operators like projection and slicing are zero-copy; only genuinely transformative operators allocate [1][3].
2. **Vectorized kernels.** Expression evaluation compiles to Arrow compute kernels over whole columns. DataFusion's physical expression layer evaluates a batch at a time, and its aggregate and join implementations operate on columnar inputs with selection-vector-style filtering.
3. **Push-flavored streaming execution.** DataFusion's `ExecutionPlan` is a tree of `RecordBatchStream`s: each stream is polled (pulled) by its parent, but the *unit* being pulled is an 8192-row batch, and independent partitions are executed concurrently across Tokio tasks. This is pull at the API level, push at the granularity level — a pragmatic hybrid. Notably, the DataFusion community's roadmap has explicitly discussed moving toward finer-grained, morsel-like task splitting for scan parallelism (dynamic file-group splitting), acknowledging the static-partitioning limitation the theorem in §4.3 formalizes [5].

The engine's optimizer stack (logical planning, physical planning, rule-based rewrites such as filter pushdown and projection pushdown) sits above all this unchanged in shape from classical systems — which is precisely the modularity argument of [3]: columnar vectorized push execution does not require a new optimizer, only a new runtime contract.

### 4.5 Operator fusion: erasing the boundaries vectorization leaves behind

Vectorization still pays one function call per operator per batch, and each operator boundary is a pass over V·w bytes. *Operator fusion* — compiling a pipeline of simple operators (filter, project, map) into a single loop — removes even that. This is the data-centric compilation of Neumann [7]: instead of materializing vectors between operators, generate one tight loop per pipeline that keeps tuples in registers. DataFusion approaches fusion pragmatically through its expression compiler (whole-expression evaluation as fused kernels) rather than full LLVM codegen, trading the last 10–20% of peak throughput for debuggability and compile latency — a defensible point on the engineering Pareto frontier [3][7].

## 5 Empirical Results and Analytical Predictions

We summarize the key reported measurements from the literature and derive regime predictions from our cost model.

| System / claim | Reported result | Source |
|---|---|---|
| MonetDB/X100 TPC-H Q1 (SF=1, Itanium2) | 0.50 s vs 26.6 s (MySQL), 3.7 s (MonetDB/MIL) | [2] |
| X100 IPC on TPC-H | near-optimal IPC vs MySQL's 0.7 | [2] |
| HyPer morsel-driven speedup (32 cores, TPC-H/SSB SF100) | >30x average | [5] |
| VectorWise (static exchange) speedup (same setup) | <10x | [5] |
| DataFusion vs Spark/DuckDB-class engines | competitive TPC-H performance as embeddable library | [3] |

From the cost model of §4.2, we predict three regimes:

1. **Selectivity-dominated scans (σ < 0.01).** Columnar projection and selection vectors dominate; vectorization's amortization matters less than skipping bytes. Arrow's validity bitmaps and late materialization are load-bearing [1].
2. **Compute-dominated pipelines (σ ≈ 1, arithmetic-heavy).** The V-fold amortization of interpretation and SIMD utilization dominate; this is where X100's 50x over MySQL came from [2].
3. **Skewed parallel joins/aggregations.** Static partitioning collapses; morsel-driven push scheduling's skew bound (§4.3) dominates. This is DataFusion's known weak regime under fixed `target_partitions`, and the active area of its executor evolution [3][5].

A roofline sketch: let B be memory bandwidth and F peak SIMD flop rate. A vectorized pipeline is memory-bound when (bytes/tuple)/(flops/tuple) > B/F. Columnar projection *reduces* bytes/tuple (pushing the workload right, toward compute-bound), while vectorization *raises* effective F — the two pillars cooperate to keep the engine at the roofline knee rather than bandwidth-starved.

## 6 Limitations

Honesty requires stating where the edifice cracks.

- **Mutation and updates.** Arrow's immutability-by-convention (copy-on-write buffers, expensive in-place updates [1]) makes the substrate hostile to OLTP. Columnar vectorized engines are analytical engines; the unified HTAP dream remains unsolved at this layer.
- **Batch-size brittleness.** The cache-residency lemma (§4.2) assumes V·w fits in cache; wide rows or deep pipelines violate it silently, and variable-width data (strings) makes V a poor proxy for bytes. Adaptive batch sizing by *bytes* rather than *rows* is still rare.
- **Push scheduling and backpressure.** Pure push needs flow control: an unbounded producer (fast scan) can OOM a slow consumer (spilling sort). Pull-based streams give backpressure for free; DataFusion's hybrid pull-of-batches inherits this safety, which partly explains the industry's reluctance to go fully push.
- **Compilation latency vs. peak throughput.** Full data-centric codegen [7] wins benchmarks but adds milliseconds of LLVM time per query — fatal for interactive, short-query workloads where DataFusion and DuckDB compete [6].
- **Skew inside a morsel.** The skew-robustness theorem bounds *across*-morsel imbalance; a single pathological morsel (e.g., one giant string group in an aggregation) still serializes. Finer morsels help but raise dispatch overhead — the eternal granularity tradeoff [5].
- **Zero-copy boundaries leak.** Arrow IPC is zero-copy only when producer and consumer agree on alignment and ownership; crossing into UDFs, Python (via the C data interface), or GPUs routinely forces copies that the architecture diagrams omit [1].

## 7 Conclusion

Three ideas — columnar memory layout, vectorized execution, and push-based scheduling — each attack a different bottleneck: memory traffic, interpretation overhead, and parallel skew. Apache Arrow [1] commoditized the first into a cross-language standard; MonetDB/X100 [2] proved the second could recover an order of magnitude on real CPUs; HyPer's morsel-driven model [5] showed the third could make parallelism elastic. Apache DataFusion [3] is the contemporary synthesis: a modular, embeddable engine whose every operator speaks Arrow, whose kernels are vectorized, and whose scheduler is evolving from static partitions toward the morsel granularity this thesis formalizes.

The deeper lesson is architectural: none of these ideas required abandoning relational algebra or cost-based optimization. They changed the *runtime contract* — the unit of data (batch, not tuple), the unit of work (vector, not operator call), and the direction of control flow (push, not pull) — while the optimizer above remained recognizably classical. Future work lies at the seams: byte-adaptive batch sizing, morsel-granular scheduling with backpressure, and join algorithms that preserve late materialization end to end. The columnar engine is no longer a research prototype; it is infrastructure. The interesting questions now are about its rough edges.
