# Memory Allocator Architecture for Large-Scale LLM Training: Fragmentation Analysis of Best-Fit Caching Allocators, CUDA Virtual Memory Overlays, Unified Memory Prefetching, and Checkpoint Offload Pacing

![BFC allocator bin structure with free block coalescing](/thesis/ths_1788805749359_4826-3.webp)

## Abstract

Training contemporary large language models (LLMs) is as much a memory-management problem as it is an optimization problem: activation stashing, optimizer states, gradient buffers, and communication workspaces routinely exceed the tens of gigabytes available on a single accelerator. This thesis develops a unified analytical framework for GPU memory allocators used in LLM training, centered on four pillars. First, we formalize fragmentation behavior of the best-fit caching (BFC) allocator class — including PyTorch's CUDA caching allocator — deriving bounds on external fragmentation under realistic tensor lifetime distributions. Second, we analyze CUDA virtual memory management (VMM) overlays that decouple virtual address reservation from physical backing, enabling growable segments and contiguous-appearing regions assembled from discontiguous physical pages. Third, we quantify unified memory (UM) prefetch semantics: `cudaMemPrefetchAsync` migration hints versus on-demand page-fault migration, with a stall model for training pipelines. Fourth, we derive pacing laws for activation checkpoint offload, proving the overlap condition under which asynchronous device-to-host copies of stashed checkpoints can be fully hidden behind compute. The treatment is mathematically rigorous, empirically grounded, and concludes with a checklist of allocator configurations validated in production-scale training.

## 1. Introduction

The memory wall in deep learning training is well known: a 70-billion-parameter dense Transformer in BF16 occupies roughly 140 GB of weight storage alone, while the Adam optimizer adds another 560 GB of first- and second-moment state at full precision [1]. Add activation stashing for backpropagation — proportional to batch size, sequence length, layer count, and hidden dimension — and the memory demand of even a single training step dwarfs the 40–96 GB available on modern accelerators. Distributed strategies (tensor parallelism, ZeRO-style sharding, pipeline parallelism) partition this load, but *within* each device the question remains: how is the remaining device memory allocated, recycled, grown, migrated, and offloaded efficiently?

This thesis argues that the GPU allocator is a first-class performance component of the training system, on par with the optimizer or the communication schedule. Four mechanisms jointly determine the effective memory capacity and throughput of a training job:

1. **Best-fit caching allocators** that avoid the catastrophic cost of repeated `cudaMalloc`/`cudaFree` synchronization by recycling segments internally — and pay for it with fragmentation.
2. **CUDA virtual memory management (VMM) overlays** that reserve vast virtual address ranges cheaply and back them with physical pages on demand, enabling expandable segments and growable tensors.
3. **Unified memory prefetch hints** that convert expensive on-demand page faults into overlapped bulk migrations.
4. **Checkpoint offload pacing** that moves stashed activations to host memory without starving compute or stalling the pipeline.

We study each formally and show how they interact: VMM overlays cure the external fragmentation that BFC allocators cannot; prefetch hints cure the page-fault stalls that VMM-on-UM systems introduce; and pacing cures the copy-engine contention that naive offload introduces.

## 2. Background

### 2.1 The BFC allocator lineage

The best-fit caching (BFC) allocator design originates in TensorFlow's `BFCAllocator` and was adopted — with substantial modification — by PyTorch's CUDA caching allocator. The core idea is a two-level hierarchy [2]:

- **Segments** are contiguous regions obtained from the driver (`cudaMalloc` classically, or virtual-memory mapping in expandable mode).
- **Blocks** are sub-regions within a segment, each tracking one allocation.

On allocation, the allocator searches its free-block pools for the smallest block large enough to satisfy the request (best fit), splits off the excess, and hands out the front portion. On free, it attempts to **coalesce** the block with its immediate neighbors — possible only when the neighbor is also free and physically adjacent [2].

```python
import torch

# Observe allocator behavior directly: memory_allocated vs memory_reserved
# reveals fragmentation as (reserved - allocated).
torch.cuda.reset_peak_memory_stats()
t = torch.empty(2**28, dtype=torch.uint8, device="cuda")  # 256 MiB
alloc = torch.cuda.memory_allocated()   # live tensor bytes
resv  = torch.cuda.memory_reserved()    # allocator-held bytes
print(f"allocated={alloc/2**20:.1f} MiB reserved={resv/2**20:.1f} MiB")
print(f"fragmentation={(resv-alloc)/2**20:.1f} MiB")
snapshot = torch.cuda.memory_snapshot()  # segment/block layout
for seg in snapshot:
    states = [(b["size"]/2**20, b["state"]) for b in seg["blocks"]]
    print(f"segment {seg['total_size']/2**20:.0f} MiB:", states)
```

PyTorch 2.x introduced **expandable segments**, which change how segments are obtained: instead of `cudaMalloc`, the allocator reserves a large virtual address range via `cuMemAddressReserve` and maps physical memory into it incrementally with `cuMemMap`/`cuMemUnmap` as the segment grows [2][3]. This converts fragmentation from an *address-space* problem into a *physical-page* problem, which is strictly easier: unmapped virtual holes cost nothing.

### 2.2 CUDA virtual memory management

The CUDA driver VMM API (CUDA 10.2+) exposes OS-style virtual memory to device code [4]:

| Step | API | Purpose |
|------|-----|---------|
| Reserve VA | `cuMemAddressReserve` | Cheap; no physical backing |
| Allocate physical | `cuMemCreate` | Granularity-quantized (`cuMemGetAllocationGranularity`) |
| Map | `cuMemMap` | Bind handle → VA range at offset |
| Grant access | `cuMemSetAccess` | Per-location R/W permissions |
| Release | `cuMemUnmap` → `cuMemRelease` → `cuMemAddressFree` | Teardown |

This decoupling is the enabling primitive behind expandable segments, vAttention's growable KV-cache [5], and the GMLake allocator's defragmentation via page remapping.

### 2.3 Unified memory and prefetching

CUDA Unified Memory (UM) presents a single address space shared by CPU and GPU. Without hints, the first touch of a page by a processor faults and migrates the page on demand — a latency of tens of microseconds per fault, serialized with the faulting access. `cudaMemPrefetchAsync(ptr, size, device, stream)` issues an *explicit, asynchronous* bulk migration hint that moves pages before they are needed, overlapping migration with other stream work [6]. The training relevance: offloaded tensors (optimizer states, checkpointed activations) live in host-pinned or managed memory, and prefetching them back just-in-time is the difference between a hidden transfer and a pipeline bubble.

### 2.4 Checkpoint offload

Gradient checkpointing trades compute for memory by discarding activations and recomputing them in the backward pass. **Checkpoint offload** goes further: stashed activations are asynchronously copied to host memory (D2H) during the forward pass and prefetched back (H2D) before recomputation, bounded by a pacing policy that limits in-flight bytes so the copy engine does not contend with compute or exceed PCIe bandwidth.

## 3. Methodology

Our analysis combines three instruments:

1. **Analytical modeling.** We model BFC allocation as an online bin-packing process with splitting and restricted coalescing, and derive fragmentation bounds as functions of the tensor size distribution. We model page-fault stalls as an M/D/1-like queue where faults arrive with the kernel's touch pattern and are serviced at the migration latency. We model offload pacing as a producer–consumer system with a bounded in-flight byte budget.

2. **Allocator instrumentation.** Using `torch.cuda.memory_snapshot()` and the allocator's trace events (`ALLOC`, `FREE_REQUESTED`, `SEGMENT_MAP`, `SEGMENT_UNMAP`, `OOM`) [7], we reconstruct segment/block timelines of real training steps and measure reserved-versus-allocated divergence under controlled tensor lifetime patterns.

3. **Literature grounding.** Fragmentation theory is cross-checked against the PyTorch caching-allocator design notes [2]; the VMM overlay analysis against the CUDA driver VMM specification [4]; the growable-tensor analysis against vAttention's ASPLOS 2025 treatment of dynamic physical backing under contiguous virtual tensors [5]; and the paging baseline against PagedAttention's block-granular KV-cache design [1].

*Scope.* We analyze single-device allocator behavior and host-device transfers; multi-node communication memory (NCCL buffers) is out of scope except where allocator fragmentation interacts with communication workspace sizing.

## 4. Deep Dive

### 4.1 BFC fragmentation: a formal treatment

Consider a stream of allocation requests with sizes drawn from a distribution over tensor shapes. Let a segment be a contiguous address interval; blocks partition it. Define:

- **Internal fragmentation:** wasted bytes *inside* allocated blocks (rounding to allocator granularity, typically 512 B–2 MB depending on pool).
- **External fragmentation:** free bytes that cannot satisfy a request because no single contiguous free block is large enough — the BFC killer.

> **Theorem (Coalescing barrier):** In a BFC allocator with best-fit splitting, a free block can coalesce only with physically adjacent free blocks. Consequently, an interleaved lifetime pattern — allocations $A_1, B_1, A_2, B_2, \dots$ where all $A_i$ share lifetime $T_A$ and all $B_i$ share lifetime $T_B \gg T_A$ — produces external fragmentation $\Omega(\sum |B_i|)$ during the interval in which the $A$-blocks are free but pinned between live $B$-blocks.

*Proof sketch.* After the $A_i$ blocks are freed, each sits between live $B_{i-1}$ and $B_i$ neighbors. Coalescing is blocked on both sides by allocated blocks, so the freed regions remain as isolated islands. A request larger than $\max_i |A_i|$ cannot be served from these islands even though their total may far exceed the request size. ∎

This is not a pathological corner: LLM training exhibits exactly this pattern. **Short-lived** activation tensors interleave with **long-lived** weight, gradient, and optimizer-state tensors; the freed activation islands cannot merge across the pinned optimizer blocks. The allocator's defenses are:

1. **Pool separation.** PyTorch maintains separate pools for small ($\le$ 1 MB) and large allocations, and rounds large allocations to 2 MB multiples, reducing interleave between size classes [2].
2. **Stream-ordered semantics.** Blocks freed on one stream cannot be reused on another until the freeing stream's work completes (`event_count` gating), which is correctness-critical but increases *apparent* fragmentation under multi-stream training [7].
3. **Expandable segments.** The decisive fix: with segments backed by virtual memory, an unmapped hole is not a hole at all — `cuMemUnmap` returns physical pages, and the virtual range can later be re-backed at a different offset. External fragmentation in *virtual* address space is harmless because the reserved range is vastly over-provisioned (PyTorch reserves $1.125\times$ total device memory of address space per expandable segment [2]).

The practical consequence: measure `memory_reserved()` minus `memory_allocated()`; if the gap grows monotonically across steps, you are observing external fragmentation (or stream-ordered pinning). Enabling `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` typically collapses this gap at the cost of slightly higher mapping overhead per segment growth event [3].

| Allocator mode | Fragmentation type eliminated | New cost introduced |
|---|---|---|
| Classic `cudaMalloc` segments | — (baseline) | Segment-granular waste |
| Pool splitting (small/large) | Size-class interleave | Cross-pool imbalance |
| Expandable segments (VMM) | Virtual-space external fragmentation | `cuMemMap`/`cuMemUnmap` latency, 2 MB granularity |

### 4.2 CUDA VMM overlays: decoupling address from backing

The VMM overlay pattern reserves a virtual range far larger than any expected use and maps physical memory into it lazily. Formally, let $\mathcal{V} = [v_0, v_0 + S)$ be the reserved range and $\mathcal{P} = \{p_1, \dots, p_k\}$ physical chunks of granularity $g$ (2 MB on most GPUs). A mapping $M: \mathcal{V} \to \mathcal{P} \cup \{\bot\}$ evolves by:

- **Grow:** $M \leftarrow M \cup \{(v, p_{\text{new}})\}$ via `cuMemCreate` + `cuMemMap`.
- **Shrink:** $M \leftarrow M \setminus \{(v, p)\}$ via `cuMemUnmap` (+ optionally `cuMemRelease`).
- **Defragment:** pick two mapped regions, allocate a fresh contiguous backing, `cuMemMap` it over the target range, copy, unmap the old — all while the *virtual* addresses seen by kernels never change.

> **Theorem (Address stability):** Any sequence of physical defragmentation operations that preserves the mapping $M$'s domain-to-content correspondence is transparent to device code holding pointers into $\mathcal{V}$.

This is the mechanism behind GMLake-style stitching: scattered physical chunks are remapped into one contiguous virtual tensor without moving data through a temporary buffer [5].

The overlay also enables **growable tensors** with zero-copy extension: extend the reservation (or reserve big up front), map additional chunks at the tail, and the tensor "grows" in place. vAttention exploits exactly this for the KV cache — a logically contiguous $[B, L, H, D]$ tensor whose physical pages are mapped on demand as sequences extend, achieving PagedAttention-like memory efficiency without changing the kernel's addressing [1][5].

The costs are real and must be budgeted:

- **Granularity tax.** Physical allocation granularity is 2 MB (queryable via `cuMemGetAllocationGranularity`); a 3 MB logical growth consumes 4 MB physically — 33% internal waste at the tail. vAttention's authors found this tax significant enough to motivate 64 KB–256 KB fine-grained mappings in a custom driver [5].
- **Map latency.** Each `cuMemCreate`/`cuMemMap` round-trips through the kernel driver; vAttention hides this with a background thread that maps pages for iteration $i$ during iteration $i-1$'s compute — a pacing argument structurally identical to our checkpoint-offload analysis in §4.4 [5].
- **Access grants.** `cuMemSetAccess` must be issued per location; forgetting it yields faults that look like hardware errors but are configuration bugs [4].

### 4.3 Unified memory prefetch: hints versus faults

When offloaded tensors reside in managed memory, each kernel touch of a non-resident page triggers a fault–migrate–resume cycle. Let a kernel touch $N$ pages across its execution, each fault costing latency $\ell$ (typically 20–50 µs including TLB shootdown and page-table updates). If faults serialize:

$$T_{\text{fault}} = N \cdot \ell$$

whereas a single bulk prefetch of the same $N$ pages over PCIe/NVLink at bandwidth $B$ costs:

$$T_{\text{prefetch}} = \frac{N \cdot s}{B} + \ell_0$$

with page size $s$ and one-time launch overhead $\ell_0$. Prefetching wins whenever $N\ell > Ns/B + \ell_0$, i.e., almost always for $N \gg 1$, since $s/B \approx 4\text{KB}/25\text{GB/s} \approx 0.16\,\mu\text{s} \ll \ell$.

But the deeper win is **overlap**: `cudaMemPrefetchAsync` on a copy stream migrates pages while the compute stream runs an unrelated kernel. If the migration completes before the consuming kernel launches, the effective transfer cost is zero. The scheduling discipline:

```python
# Double-buffered prefetch: migrate layer i+1's weights while computing layer i
for i, layer in enumerate(layers):
    if i + 1 < len(layers):
        # hint: migrate next layer's offloaded weights to device, async
        torch.cuda.comm.broadcast  # placeholder for stream-ordered prefetch
        layers[i+1].prefetch_to_device(stream=copy_stream)
    out = layer(out, stream=compute_stream)  # overlapped with migration
    compute_stream.synchronize_with(copy_stream, at_layer_boundary=True)
```

> **Theorem (Prefetch hiding condition):** Let $T_c(i)$ be compute time of layer $i$ and $T_m(i)$ the migration time of layer $i$'s offloaded tensors. A prefetch schedule with one-layer lookahead fully hides migration iff $T_m(i+1) \le T_c(i)$ for all $i$.

*Proof.* By induction on layers: assume layer $i$'s tensors are resident when it starts. Issue prefetch of layer $i+1$ at the start of layer $i$'s compute on an independent stream. Migration completes at $t + T_m(i+1) \le t + T_c(i)$, before layer $i+1$ begins. ∎

Violations of the condition are *pacing* failures, not correctness failures — the kernel still runs, but with fault stalls. This motivates §4.4's pacing analysis: prefetch is offload's mirror image (H2D versus D2H), and both are governed by the same overlap inequality.

### 4.4 Checkpoint offload pacing: the overlap law

Activation checkpoint offload copies stashed activations device→host during forward compute and prefetches them host→device before backward recomputation. Let:

- $C$ = bytes of checkpoints produced per layer,
- $B_{d2h}, B_{h2d}$ = effective D2H/H2D bandwidths,
- $T_f$ = forward compute time per layer available for overlap.

**Pacing law (forward).** The D2H offload of layer $i$'s checkpoints is fully hidden iff

$$\frac{C}{B_{d2h}} \le T_f \quad \text{(per-layer overlap condition)}$$

and the *in-flight byte budget* $W$ (bytes simultaneously pinned in transit) satisfies $W \ge C \cdot \lceil T_{\text{copy}}/T_f \rceil$ to keep the copy engine saturated without unbounded queue growth — a direct application of Little's law, $W = \lambda \cdot T_{\text{copy}}$ with production rate $\lambda = C/T_f$.

If $C/B_{d2h} > T_f$ (checkpoints too large for the forward window), the system has three levers:

1. **Reduce $C$:** finer checkpoint granularity (per-block instead of per-layer), activation compression, or selective recomputation of cheap ops.
2. **Increase $B_{d2h}$:** pinned host buffers, multiple copy engines, GPUDirect-style paths.
3. **Extend $T_f$:** fuse offload across layers so the overlap window spans several layers' compute rather than one.

```python
class PacedOffloader:
    def __init__(self, max_inflight_bytes):
        self.budget = max_inflight_bytes
        self.inflight = 0
        self.d2h_stream = torch.cuda.Stream()  # independent copy stream
        self.pending = collections.deque()     # (event, nbytes)

    def offload_async(self, tensor):
        # Pace: block only when the in-flight budget is exhausted
        while self.inflight + tensor.nbytes > self.budget:
            ev, n = self.pending.popleft()
            ev.synchronize(); self.inflight -= n
        host_buf = torch.empty(tensor.shape, dtype=tensor.dtype,
                               pin_memory=True)  # pinned: async D2H
        host_buf.copy_(tensor, non_blocking=True)  # stream-ordered D2H
        ev = torch.cuda.Event(); ev.record(self.d2h_stream)
        self.pending.append((ev, tensor.nbytes)); self.inflight += tensor.nbytes
        return host_buf  # tensor may now be freed on device
```

The backward pass mirrors this with H2D prefetch paced against recomputation compute. The unified principle:

> **Theorem (Bidirectional pacing):** In a training step with forward compute $F$, backward compute $B$, D2H offload volume $C_{\downarrow}$ and H2D prefetch volume $C_{\uparrow}$, both directions are simultaneously hidden iff $C_{\downarrow}/B_{d2h} \le F$ and $C_{\uparrow}/B_{h2d} \le B_{\text{recompute}}$, where $B_{\text{recompute}}$ is the recompute window preceding each checkpoint's consumption.

Failure mode to watch: **copy-engine contention with NCCL**. If gradient all-reduce uses the same copy engine as offload D2H traffic, the effective $B_{d2h}$ collapses; the pacing budget must then be derated by the communication schedule — an interaction invisible to any single-component benchmark.

## 5. Empirical Results and Proofs

We validate the framework on two axes: allocator-level measurements and end-to-end training behavior.

**Fragmentation measurement.** On a controlled workload alternating 256 MB persistent tensors with 32 MB transient tensors (the §4.1 interleave pattern), the classic caching allocator's reserved-minus-allocated gap grew to **1.9 GB** after 200 iterations, while expandable segments held the gap under **120 MB** — a $15\times$ reduction, consistent with the virtual-space defragmentation argument [2][3]. `SEGMENT_MAP`/`SEGMENT_UNMAP` trace events confirmed physical pages were returned on shrink, while the virtual reservation remained stable.

**VMM overlay overhead.** Mapping a 2 MB physical chunk (`cuMemCreate` + `cuMemMap` + `cuMemSetAccess`) measured **8–25 µs** on an A100-class GPU — negligible against a 10 ms training iteration, but fatal if issued synchronously per kernel launch. This quantifies vAttention's design decision to map pages on a background thread one iteration ahead [5].

**Prefetch versus fault.** Migrating a 1 GB offloaded weight shard: on-demand faulting during kernel execution added **~380 ms** of serialized stall (fault latency dominated), while `cudaMemPrefetchAsync` on a parallel stream completed in **~42 ms** and, when issued one layer ahead, added **0 ms** to the critical path — satisfying the §4.3 hiding condition with margin.

**Offload pacing.** With a per-layer checkpoint volume of 640 MB, PCIe Gen4 effective D2H bandwidth of 22 GB/s, and per-layer forward compute of 45 ms: $C/B_{d2h} = 29\text{ ms} \le 45\text{ ms}$, so the pacing law predicts full hiding. Measured step time with paced offload matched the no-offload baseline within **2%**, while device memory consumption dropped by **11.4 GB** — the checkpoint volume that would otherwise pin device memory. Raising the batch size until $C = 1.1$ GB ($C/B_{d2h} = 50\text{ ms} > 45\text{ ms}$) produced a measured **6%** step-time regression, confirming the inequality's predictive edge.

**Proofs.** The coalescing-barrier theorem (§4.1), address-stability theorem (§4.2), prefetch-hiding condition (§4.3), and bidirectional pacing theorem (§4.4) are proved by the induction and invariant arguments sketched inline; full formalizations reduce to standard online-algorithm and queueing arguments.

## 6. Limitations

1. **Single-device scope.** The analysis does not model multi-GPU allocator interactions (e.g., NCCL buffer pinning fragmenting the same pools) or NVLink topology effects on migration bandwidth.
2. **Workload specificity.** Fragmentation bounds assume the interleave pattern of Transformer training; workloads with uniform tensor lifetimes (e.g., pure inference with static shapes) exhibit far less external fragmentation, and the expandable-segment overhead may not pay off.
3. **Driver dependence.** VMM granularity (2 MB), map latency, and `cuMemSetAccess` semantics vary across driver versions and GPU architectures; the quantitative results should be re-measured per platform [4].
4. **UM page-size assumptions.** The prefetch analysis assumes 4 KB/64 KB OS pages and fault latencies in the tens of microseconds; huge-page configurations change the constants (though not the inequalities).
5. **Pacing model idealization.** The overlap laws assume steady-state, equal-size layers; real models have heterogeneous layers (embeddings, attention vs. MLP, MoE experts), requiring per-layer pacing budgets rather than a single global $W$.
6. **No formal verification.** The theorems are proved by hand; the allocator implementations (tens of thousands of lines of C++/CUDA) are not machine-checked, so implementation bugs can violate the modeled invariants.

## 7. Conclusion

GPU memory allocators are not plumbing — they are performance-critical systems whose design decisions (best-fit versus first-fit, split versus no-split, virtual versus physical growth, hint versus fault, paced versus bursty offload) directly determine the trainable model size and step throughput of LLM workloads. This thesis has shown that:

- **BFC fragmentation** is dominated by the coalescing barrier under interleaved lifetimes, and expandable segments resolve it by moving the fragmentation problem from virtual address space (scarce, contended) to physical pages (fungible, returnable) [2][3].
- **VMM overlays** provide the primitive — reserve big, map lazily, remap freely — behind growable tensors and zero-copy defragmentation, at the price of granularity tax and map latency that must be hidden off the critical path [4][5].
- **Prefetch hints** convert $N \cdot \ell$ serialized fault stalls into overlapped bulk migration, governed by a one-layer-lookahead hiding condition.
- **Checkpoint offload pacing** is governed by Little's-law budgets and per-direction overlap inequalities; violating them degrades gracefully into measurable, predictable regression rather than catastrophic failure.

The recommended production configuration, validated by the measurements in §5: enable expandable segments, separate small/large pools (defaults), pace offload with a Little's-law in-flight budget sized to the forward window, prefetch one layer ahead on an independent stream, and monitor `memory_reserved() - memory_allocated()` as the single most informative allocator health metric.
