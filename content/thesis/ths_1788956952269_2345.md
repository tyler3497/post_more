# CompCert and the Verified Compilation Stack: Simulation Diagrams, Verified Register Allocation, and Translation Validation for C Semantics Preservation

## Abstract

The CompCert project demonstrates that a realistic, optimizing C compiler can be developed together with a machine-checked proof of semantic preservation, all within the Coq proof assistant [1]. Rather than proving a monolithic translation, CompCert decomposes compilation into some twenty passes over nine intermediate languages, each justified by a *simulation diagram* relating source and target executions, and composes these local arguments into an end-to-end theorem: every observable behavior of the generated assembly is admitted by the source program [2]. This thesis dissects that architecture. We reconstruct the four simulation schemata — lock-step, plus, star, and option — and show how target determinacy turns forward simulation into observable-behavior preservation [4]. We examine the register allocation pass, first as a directly verified George–Appel graph-coloring allocator and later as an untrusted OCaml allocator guarded by a verified dataflow-based validator [3]. Placing CompCert on a spectrum from translation validation to the bootstrapped CakeML compiler [5][7] and binary-level refinement of the seL4 kernel [6], we argue verified compilation is a discipline for allocating proof effort where it buys the most trust.

## 1 Introduction

The question *"can you trust your compiler?"* is sharper than it first appears. A program may be exhaustively reviewed, model-checked, and proved correct against its specification, yet all of that assurance evaporates if the compiler silently mistranslates it: safety properties established at the source level need not hold of the executable. Historically the response has been testing — differential fuzzing campaigns such as Csmith uncovered hundreds of miscompilation bugs in production compilers — but testing can only sample a vanishingly small corner of the input space. The CompCert project, led by Xavier Leroy and collaborators since 2005, takes the complementary route of *software–proof codesign*: the compiler and its correctness proof are written together, in Coq, so that the artifact delivered to the user carries a machine-checked guarantee of semantic preservation [1].

Three design decisions make CompCert's verification tractable, and each is the subject of this thesis. **First**, the compiler is factored into roughly twenty passes over nine intermediate languages, from Clight (a large, precisely specified subset of C) down to assembly; each pass is proved correct independently, and correctness composes [2]. **Second**, every pass proof takes the shape of a *simulation diagram* relating source and target executions, which — the target language being deterministic — flips into a backward simulation and hence into preservation of all observable behaviors [4]. **Third**, where an algorithm is heuristic or painful to verify, CompCert uses *translation validation*: an unverified oracle computes the result and a small verified checker certifies each output [3].

We develop these ideas in depth. Section 2 reviews the landscape from proof-carrying code to Csmith-era mistrust. Section 3 presents the simulation-based methodology. Section 4 dives into the simulation schemata, the pass pipeline, register allocation, translation validation, and the memory model. Section 5 evaluates the empirical evidence. Section 6 states the limitations honestly, and §7 concludes by situating CompCert between direct verification and binary-level validation, drawing lessons for CakeML [5][7] and the seL4 refinement stack [6].

## 2 Background

### 2.1 From trusted translators to verified translators

The dream of a compiler whose output is guaranteed correct predates modern proof assistants. In *proof-carrying code* (PCC), a code producer attaches a proof of a safety policy that the consumer checks — but each program must carry its own argument [1]. Translation validation, introduced by Pnueli, Siegel, and Singerman in the late 1990s, moved the check to the compiler: an independent validator establishes per compilation that the output refines the input. Leroy's insight in CompCert was that these ideas compose with direct verification: verify the passes whose algorithms are stable and elegant, and validate the passes whose algorithms are heuristic or in flux [2].

### 2.2 The empirical motivation: miscompilation is common

Before CompCert, the best evidence about compiler trustworthiness came from *testing*. Yang et al.'s Csmith campaign reported 325 previously unknown defects across eleven C compilers — and CompCert, the only formally verified compiler in the study, was the only one with no middle-end or back-end defect; the five defects found all lived in the *unverified* front end, sharply delineating what the proof covers [1]. This demonstrates that the boundary between the verified and unverified parts of a compiler is itself an empirical fact. It also motivates *formally verified defensive programming* (FVDP): complex oracles are left untrusted while only their *results* are checked by verified decision procedures, converting would-be miscompilations into clean compiler failures [6].

### 2.3 Related verified compilers

CompCert is not alone. **CakeML** is an end-to-end verified compiler for Standard ML developed in HOL4, notable for being *bootstrapped* inside the logic — the correctness theorem is instantiated to the compiler's own implementation, yielding a verified binary — and for a lightweight clock-based technique for divergence preservation so that all proofs proceed by induction on the big-step semantics [5]. The CakeML back end was later re-engineered and re-verified with substantially improved generated code [7]. Where CompCert proves forward simulations between small-step semantics of many intermediate languages, CakeML proves refinement between big-step functional semantics of fewer, larger phases — two legitimate points in a design space whose trade-offs we explore in §4.4.

## 3 Methodology

The technical core of CompCert is a single reusable proof pattern applied roughly twenty times. For a pass from language *L₁* to *L₂*, one defines a **matching relation** *R* between states of the two languages and proves a **simulation diagram**: whenever a source state *s₁* related to a target state *s₁′* takes an execution step, the target can take steps reaching a state *s₂′* related to the resulting source state *s₂*. Schematically:

```haskell
-- Forward simulation: source steps are matched by target steps
forwardSim :: (s -> s -> Bool)      -- source step relation
           -> (t -> t -> Bool)      -- target step relation
           -> (s -> t -> Bool)      -- matching relation R
           -> Bool
forwardSim stepS stepT match =
  forall s1 s1' s2. match s1 s1' && stepS s1 s2
    ==> exists s2'. stepsT s1' s2' && match s2 s2'
```

Because every CompCert target language has a *deterministic* small-step semantics, a forward simulation can be inverted into a **backward simulation**: every target behavior is matched by a source behavior. The observable behavior of a program is its *trace* — the sequence of external events it performs — plus its termination or divergence status. Backward simulation therefore yields the headline theorem [4]:

> **Theorem: (Semantic preservation, CompCert back end).** Let *C* be a Clight program and let *A* be the assembly produced by successful compilation. Then every observable behavior of *A* — terminating with trace *t* and exit code *v*, diverging with trace *t*, or going wrong only where *C* could also go wrong — is an observable behavior admitted by the source semantics of *C*. In particular, if *C* is safe (never goes wrong), then *A* is safe and exhibits only behaviors of *C*.

The proof obligation decomposes per pass, and per-pass theorems compose by transitivity of the preservation relation [1]. The methodology therefore has three moving parts, examined in §4: the simulation schemata that handle stuttering and silent steps, the pipeline of intermediate languages that keeps each simulation local, and the verified/validated treatment of heuristic passes such as register allocation.

## 4 Deep Dive

### 4.1 The Four Simulation Schemata

Real compiler passes do not translate one source step into exactly one target step. CompCert therefore proves four increasingly permissive variants of the forward diagram, choosing per pass the weakest schema the transformation requires [2]:

| Schema | Source steps | Target steps | Used for |
|---|---|---|---|
| Lock-step | 1 | exactly 1 | Simple local rewrites (e.g., tunneling) |
| Plus | 1 | ≥ 1 | Passes that expand code (e.g., stack frame layout) |
| Star | ≥ 1 | ≥ 0 | Passes that may delete or duplicate steps |
| Option | 1 | 0 or ≥ 1 | Passes with administrative silent steps |

The *star* simulation is the workhorse: it permits the target to take zero steps for a source step (stuttering, as in dead-code elimination) provided a well-founded measure on source states decreases whenever the target stutters, ruling out infinite stuttering. The *option* simulation handles the opposite mismatch by exploiting a syntactic characterization of administrative steps. These schemata are proved once as meta-theorems in Coq, so each pass proof instantiates the general machinery rather than re-deriving it. Determinacy of the target then upgrades any forward simulation to a backward simulation, and backward simulations compose across passes into the end-to-end observable-behavior theorem [4].

In TLA⁺-style pseudocode, the star simulation's stuttering discipline is:

```tla
------------------------------ MODULE StarSim ------------------------------
\* s \in Source, t \in Target, R the matching relation, mu a measure
\* into the naturals, <_S the source step, <_T the target step.
\* Diagram: s -R-> t /\ s ->_S s' ==>
\*   \/ \E t' : t ->*_T t' /\ R(s', t')            \* target catches up
\*   \/ R(s', t) /\ mu(s') < mu(s)                 \* silent target stutter
=============================================================================
```

The measure condition is the liveness argument: the target cannot stutter forever because each stutter strictly decreases a natural number. This is how CompCert handles optimizations that remove code while still guaranteeing that divergence is preserved — a point to which we return in §4.5.

### 4.2 The Pass Pipeline: Nine Languages, Twenty Proofs

CompCert's front end (C parsing, type-checking, elaboration into Clight) is written in OCaml and *unverified* — outside the proof [1]. Everything from Clight downward is written and proved in Coq. The pipeline is:

| Stage | Languages | Character of the pass |
|---|---|---|
| Simplification | Clight → C#minor → Cminor | Remove side effects from expressions; make control flow explicit |
| Instruction selection | Cminor → CminorSel → RTL | Match operators to machine idioms; build control-flow graphs |
| Middle end | RTL → RTL (several) | Tail calls, inlining, constant propagation, CSE, dead code |
| Register allocation | RTL → LTL | Graph coloring with spilling (see §4.3) |
| Linearization | LTL → LTLin → Linear | Resolve control flow to linear code; branch tunneling |
| Code generation | Linear → Mach → Asm | Stack frame layout; emit assembly with a verified pretty-printer |

Each arrow is a proved simulation, and the composition theorem states that the *error-propagating* composition of verified passes is itself a verified compiler [2]. Two engineering idioms recur. First, *monadic translation*: passes such as RTL generation build control-flow graphs inside a state monad whose invariant — nodes are only ever added — is what the simulation proofs lean on. Second, *bounded iteration*: dataflow fixpoints run under an explicit iteration budget and return an `option` type, so non-convergence produces a clean compiler error rather than an unprovable obligation; the bound is never hit in practice but keeps the logic total [1].

The intermediate languages are the methodology's central artifact. Each is given a complete formal operational semantics — Clight's semantics alone is a substantial formalization of C's evaluation order and memory model — so that the *statement* of each pass's correctness is mathematically precise. A verified compiler, in this view, is less a program with a proof than a tower of precisely specified languages with proved refinements between adjacent levels [4].

### 4.3 Verified Register Allocation: Coloring, Spilling, Validation

Register allocation is where CompCert's methodology shows its full range. The task — map the unbounded pseudo-registers of RTL onto the finite machine registers and stack slots of LTL, inserting spills and reloads — is NP-hard in its coloring formulation and traditionally implemented with intricate heuristics. CompCert has used *two* architectures for this pass.

**Generation 1: the directly verified allocator.** The original back end verified a George–Appel iterated-coalescing graph-coloring allocator written directly in Coq: build the interference graph, simplify, coalesce, freeze, spill, select; repeat until colorable [2]. Spilling was deliberately naive — spill after every definition, reload before every use, with dedicated scratch registers — adequate for the register-rich PowerPC but hopeless for x86. Proving the coloring algorithm correct was feasible but painful, and every heuristic improvement would have required re-proof.

**Generation 2: the validated allocator.** Rideau and Leroy replaced the verified allocator with a *translation-validation* architecture: an arbitrary, unverified OCaml program performs iterated register coalescing with sophisticated splitting and spilling, and a small Coq-verified *validator* checks each allocation it produces [3]. The validator uses a backward dataflow analysis refining standard liveness: it verifies that the LTL code mirrors the RTL instruction-for-instruction in shape, and that the register assignment satisfies equations guaranteeing every value is available where needed. Because the validator reasons only about the *output*, it handles overlapping registers, aggressive coalescing, and arbitrary spill strategies the original proof could not touch:

> **Theorem: (Soundness of the allocation validator, Rideau–Leroy).** If the validator accepts a pair of RTL and LTL functions, then every execution of the LTL function is simulated by an execution of the RTL function; hence the allocation preserves observable behavior. The OCaml allocator itself need satisfy no property whatsoever — a buggy allocator can only cause the validator to reject its output, i.e., a compile-time failure, never a miscompilation [3].

This is the *proof-effort spectrum* in miniature: verifying the heuristic costs thousands of lines of proof and freezes the algorithm; verifying the checker costs hundreds and leaves the algorithm free to evolve. CompCert applies the same pattern to linearization (OCaml trace-picker unchecked; Coq verifies only that every reachable node appears exactly once), switch compilation, inlining, and if-conversion — in each case a `Parameter` in the Coq development marks the untrusted oracle, realized at extraction by OCaml code [1].

```python
# Sketch of the validator's core idea (cf. Rideau & Leroy, CC 2010)
def validate_allocation(rtl_fn, ltl_fn, assignment):
    # 1. Structural check: LTL must mirror RTL instruction-for-instruction
    assert same_shape(rtl_fn.cfg, ltl_fn.cfg)
    # 2. Backward dataflow: compute, for each program point, the set of
    #    RTL pseudo-registers that must hold values, and check that the
    #    assigned LTL locations actually provide them (refined liveness).
    live = backward_liveness(rtl_fn)
    for node in rtl_fn.nodes:
        for r in live[node]:
            assert location_holds(assignment[r], node, ltl_fn)
    return True   # accepted: simulation holds; rejected: compile error
```

## 5 Empirical Analysis and Formal Guarantees

What does this machinery cost, and what does it buy? The numbers, as reported across the CompCert publications [1][2][4], are striking:

| Metric | CompCert (circa CACM 2009) | Typical production compiler |
|---|---|---|
| Trusted proof size | ~42,000 lines of Coq (+ OCaml oracles) | 0 lines of proof |
| Front end | Unverified (OCaml, outside proof) | Unverified |
| Miscompilation defects found by Csmith | 0 in verified parts; 5 in unverified front end | 325 across 11 compilers |
| Generated code performance | Within ~10–20% of `gcc -O1` on benchmarks | Baseline |
| Compilation speed | Slower than gcc, acceptable for embedded targets | Fast |

Several conclusions follow. **First**, the proof is large but *amortized*: written once, it checks every compilation thereafter, unlike testing, whose cost recurs per release. **Second**, the Csmith result empirically validates the methodology's boundary-drawing: defects clustered exactly where the proof did not reach [1]. **Third**, the defensive-programming discipline has a measurable payoff: the register allocator was substantially improved *without touching the proof*, because the proof constrains only the validator [3]. **Fourth**, performance is competitive: generated code trails `gcc -O1` modestly, and CompCert performs *proved* optimizations — constant propagation, CSE, dead-code elimination, inlining, tail calls — refuting the folk belief that verification forces `-O0` [4].

The guarantee itself deserves precise statement, because it is weaker than "the compiler has no bugs" and stronger than "the compiler passes its test suite":

> **Theorem: (End-to-end, observable behavior).** For every source program *P* in the supported Clight subset, either compilation fails (with a clean error), or the produced assembly *A* satisfies: every trace of *A* — terminating, diverging, or going wrong — is a trace admitted by the formal semantics of *P*. Safety properties proved of *P* therefore transfer to *A* [1][4].

Note the *failure* disjunct: it is what makes the validator architecture sound. A rejected allocation, a fixpoint that exhausts its iteration budget, an unrecognized construct — all become compile-time errors, never silent miscompilations.

## 6 Limitations

Intellectual honesty requires stating what the theorem does *not* cover — the residual trusted computing base is real and must be managed, not wished away.

1. **The unverified front end.** C parsing, elaboration, and type-checking are OCaml code outside the proof; the Csmith defects found in CompCert lived here [1]. A front-end bug can produce well-formed but *wrong* Clight, which the verified back end then faithfully mistranslates.
2. **Assembler, linker, and hardware.** The theorem is about assembly *text*; assembling, linking, and executing are trusted. Binary-level validation [6] closes part of this gap, but the hardware model remains axiomatized.
3. **Language subset.** The verified semantics covers a large but incomplete fragment of C: `long long` and `long double` were historically unsupported, unstructured `switch` (Duff's device), `setjmp`/`longjmp`, and variadic functions are excluded, and several constructs are supported only through unverified desugaring [1]. Programs outside the subset are rejected — safe, but limiting.
4. **Concurrency.** The original correctness theorem assumes sequential execution; the memory model does not specify data-race semantics, and the CompCertTSO extension for x86-TSO relaxed memory is a separate, substantial development rather than part of the mainline guarantee.
5. **Proof maintenance.** The ~42k lines of Coq are a living cost: every Coq version upgrade, every new target architecture, and every language extension demands proof engineering. The validator pattern [3] mitigates this for heuristic passes but not for the semantic core.
6. **No liveness or security properties.** Semantic preservation transfers *safety* properties and observable traces; it says nothing about timing, side channels, or constant-time behavior, which compilation can and does alter.

## 7 Conclusion

CompCert's enduring contribution is methodological. The artifact — a usable, optimizing, verified C compiler — is impressive, but the method is the transferable asset: *decompose* the compiler into passes over formally specified intermediate languages; *prove* each pass by the weakest simulation schema its transformation requires; *verify* the stable algorithms and *validate* the heuristic ones; and *compose* the per-pass theorems into an end-to-end observable-behavior guarantee [1][2][4]. The register allocation story — from a directly verified George–Appel colorer to an untrusted allocator behind a verified dataflow checker [3] — shows the method adapting to engineering reality without surrendering assurance. The wider landscape confirms the pattern's generality: CakeML's bootstrapped HOL4 development [5][7] makes different but equally principled trade-offs, and binary-level translation validation for seL4 [6] shows validation can extend *below* the compiler's output, not just within it.

The open frontier is compositional verification *across* toolchains: a verified compiler whose output is binary-validated against a verified kernel, running on a verified ISA model, with the front end finally brought inside the proof. Each of those steps is now a demonstrated technique rather than a research gamble.
