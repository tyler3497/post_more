# Deterministic Record-and-Replay Debugging with rr: Hardware Performance Counters, Chaos Mode, and Reverse Execution

## Abstract

Deterministic record-and-replay debugging eliminates the most punishing property of concurrent software faults — irreproducibility — by capturing every nondeterministic input in one execution and reconstituting the identical instruction stream on demand. This thesis treats **rr**, the lightweight user-space record-and-replay system for Linux on x86 that made deterministic replay deployable without kernel modification or pervasive instrumentation [1][2]. We formalize the *nondeterminism frontier* — system calls, asynchronous signals, nondeterministic instructions (RDTSC, RDRAND, CPUID) — and show how rr closes it via seccomp-bpf interception, injected syscall buffering, single-core thread serialization, and, most distinctively, hardware performance counters (*retired conditional branches*) used as a deterministic execution clock [1][3]. We analyze **chaos mode**, which perturbs the schedule space to surface latent data races, and **reverse execution**, which reduces backward debugging queries to forward replay from checkpoints. Finally, we survey empirical overhead evidence and formalize replay correctness as a theorem over counter-deterministic event delivery [1][4].

## 1 Introduction

The hardest bugs are not the ones that crash loudly but the ones that cannot be reproduced: a data race may corrupt state once in ten thousand runs, vanishing the moment a debugger attaches — the classic *Heisenbug*. Forward-only debuggers are structurally mismatched to such failures, forcing the investigator to guess breakpoint placement *before* the fault manifests, in an execution that will never recur identically.

**Deterministic record-and-replay** inverts this relationship: the system records one execution — capturing every nondeterministic input — and replays it exactly, indefinitely, under full debugger control [4]. The recording becomes a *time-traveling* artifact: run forward to the failure, step backward to its cause, and test hypotheses against a fixed timeline [7].

The **rr** debugger, originated at Mozilla by Robert O'Callahan and colleagues and now developed with Pernosco's sponsorship, is the reference open-source realization of this idea for Linux on x86 [1][3]. Its central claim is **deployability**: rr records *unmodified* binaries on *stock* kernels, without privileges, kernel modules, or pervasive instrumentation — the three taxes that had confined record-and-replay to research prototypes [1][2]. It combines well-understood mechanisms (`ptrace`, `seccomp-bpf`, library injection) with one genuinely novel one: **hardware performance counters as a deterministic clock** partitioning execution into reproducible quanta.

This thesis makes three contributions. First, we systematize rr's architecture around the *nondeterminism frontier* — the set of all program-observable events that must be captured — and how each class is neutralized (§3). Second, we give a deep account of the three title mechanisms: the retired-conditional-branch counter as execution clock (§4.1), **chaos mode** as schedule-space fuzzing (§4.3), and **reverse execution** as checkpointed forward replay (§4.4). Third, we formalize replay correctness as a theorem, survey empirical overhead evidence (§5), and catalogue the system's limits (§6).

> Theorem: If the sequence of nondeterministic events (syscall results, signal deliveries, preemption points) recorded during execution E is replayed against the same binary and initial state, and each event is delivered at the identical retired-conditional-branch count at which it was recorded, then the replayed execution E′ is instruction-for-instruction identical to E.

## 2 Background

### 2.1 The nondeterminism frontier

A user-space program is, to first approximation, a deterministic state machine: its execution is fixed by its initial state plus a small set of *nondeterministic inputs* — interactions with entities outside its address space. The literature converges on the following taxonomy [4][5]:

| Source of nondeterminism | Examples | rr's capture mechanism |
|---|---|---|
| System call results | `read`, `recvmsg`, `gettimeofday`, `mmap` addresses | `seccomp-bpf` interception + syscall buffering; record results |
| Asynchronous signals | `SIGSEGV`, timers, `SIGCHLD` | Deliver at recorded branch-counter values |
| Thread scheduling | Preemptions, lock acquisition order | Serialize all threads onto one core; record preemption points via counter interrupts |
| Nondeterministic instructions | `RDTSC`, `RDRAND`, `CPUID` | Trap `RDTSC` (CR4.TSD); emulate deterministically from branch counter; record `RDRAND` |
| Shared-memory races | Unsynchronized concurrent access | Faithfully reproduced via deterministic scheduling; *not* eliminated |
| Memory-mapped I/O / DMA | GPU, device registers | **Unsupported** — outside the frontier (see §6) |

The crucial insight [1][2][4] is that *bulk* execution is deterministic: nondeterministic events occur at low frequency (thousands, not billions, per second), so recording only the frontier is sufficient. Everything between two frontier events is never logged — it is *recomputed* identically during replay.

### 2.2 Prior approaches and why they failed to deploy

Earlier systems paid heavy deployment taxes. Whole-VM replay required running inside a virtual machine; kernel-modification approaches imposed unacceptable maintenance costs; dynamic binary instrumentation (Pin, DynamoRIO, Valgrind) imposed large, unpredictable slowdowns and struggled with self-modifying code — pervasive in JIT compilers, Mozilla's primary target workload [1].

rr's thesis is that modern Intel CPUs, stock Linux kernels, and standard user-space frameworks already expose *enough* mechanism — if architected around their non-obvious constraints [1]. The load-bearing properties are (i) a **deterministic performance counter** advancing identically across runs, and (ii) **user-space traps** (`seccomp-bpf`, the `TSD` bit) letting an unprivileged supervisor intercept the frontier cheaply. The result: no kernel patch, no root, no recompilation, no code instrumentation [2][3].

### 2.3 Time-travel debugging in context

Record-and-replay enables *time-travel* debugging, available commercially as Undo UDB and WinDbg TTD alongside rr [7]. A recent survey [6] contrasts *omniscient* debuggers (fine-grained state for value-provenance queries) with *replay* systems (frontier-only logging, state reconstructed by re-execution) — trading expressiveness for far lower cost. rr is a replay system; its reverse commands are built *on top of* replay (§4.4).

## 3 Methodology

### 3.1 System architecture

rr is a **supervisor** process controlling **tracee** processes via `ptrace`, plus two in-tracee accelerators: a `seccomp-bpf` filter and an injected library (`librrpreload`) implementing *syscall buffering* [1][2]. The record loop:

1. **Interception.** Every tracee syscall is classified by the `seccomp-bpf` filter as *traced* (trap to the supervisor via `PTRACE_EVENT_SECCOMP`), *buffered* (executed by the preload library, results appended to a per-thread trace buffer), or *allowed* (deterministic and side-effect-free, e.g. cached `getpid` — native, no logging).
2. **Serialization.** The supervisor schedules all tracee threads onto a **single logical core**, one thread at a time. A performance-counter interrupt (§4.1) fires after a quantum of progress, giving the supervisor a preemption point at which it may switch threads or deliver a pending signal.
3. **Event logging.** Traced syscall inputs/results, signal delivery points (as counter values), and thread-switch points are appended to the trace. Ordinary instructions are never logged.
4. **Replay.** The supervisor re-executes the binary, but *serves* recorded syscall results, *injects* signals at recorded counter values, and *follows* recorded preemption points. At every event boundary it asserts the live counter equals the recorded one; any mismatch is a **replay divergence**, reported loudly, never silently tolerated [1].

```shell
# Record an execution (trace written to ~/.local/share/rr/<exe>-<n>/)
$ rr record ./flaky_server --port 8080

# Replay the most recent recording under gdb with reverse execution
$ rr replay
(rr) break handle_request
(rr) reverse-continue
(rr) watch -l conn->state
(rr) reverse-continue        # jump backward to the previous write
```

### 3.2 The recording contract

rr's correctness rests on a contract with hardware and kernel [1]: the CPU must provide a *deterministic* performance counter, and the kernel must permit unprivileged `seccomp-bpf` filtering, `ptrace` supervision, and `RDTSC` trapping via `CR4.TSD`. On Intel Sandy Bridge and later, the retired-conditional-branches counter satisfies this closely enough for practical replay; rr validates it at startup and refuses to record where it misbehaves [2][3]. §6 examines where the contract breaks.

## 4 Deep Dive

### 4.1 Hardware performance counters as a deterministic clock

rr's most original mechanism uses a hardware performance counter not for profiling but as a **clock** — a deterministic measure of *how far* execution has progressed. The event is **retired conditional branches** (`BR_INST_RETIRED.CONDITIONAL`, `0xC4`): conditional branches retired since counting started. Two properties make it suitable [1]:

- **Determinism.** For fixed inputs, the count is identical across runs on the same microarchitecture — unlike *instructions retired* (speculation artifacts) or *cycles* (thermal variance). It is a pure function of control flow.
- **Density.** Conditional branches occur roughly every 10–20 instructions: fine enough to pinpoint signal and preemption points within a handful of instructions, coarse enough that the 64-bit counter effectively never wraps.

rr's progress unit, the **tick**, is defined by this counter. Recording stamps asynchronous events with the counter value: signal *S* was delivered when the counter read *N*. Replay programs the counter to interrupt *slightly before* *N*, then advances to the exact value before injecting the signal. Replayed code is bit-identical, so the counter reaches *N* at the identical program point — same instruction, registers, and memory.

This yields an elegant **divergence detector**: at every recorded event, the live counter is compared against the recorded one. On mismatch — a stray `RDRAND`, an SMI perturbing a *different* counter, CPU errata — rr aborts with a diagnostic rather than presenting a subtly wrong execution [1][2]. The counter is simultaneously the clock, the schedule, and the integrity check.

```shell
# Does this CPU expose a deterministic retired-conditional-branch counter?
$ perf stat -e r00c4 -- ./workload   # r00c4 = BR_INST_RETIRED.CONDITIONAL
# Run twice: identical counts => rr's recording contract holds
```

### 4.2 Syscall buffering and the record path

Naive `ptrace` syscall interception costs two context switches per syscall, which would make syscall-heavy workloads unusably slow to record. rr's answer is **syscall buffering**, responsible for most of the system's practical performance [1].

At startup rr injects `librrpreload.so` into the tracee. The `seccomp-bpf` filter classifies syscalls: *common, recordable* ones (`read`/`write` on regular files, `pread`, `getdents`) execute **directly in the preload library without trapping to the supervisor**, appending results to a per-thread *trace buffer*; the supervisor intervenes only when the buffer fills, flushing it in bulk. During replay the library *serves* recorded results — a replayed `read` never touches the filesystem.

Remaining syscalls — complex side effects (`mmap`, `clone`, `futex`, sockets) or unbufferable results — take the *traced* path: `SECCOMP_RET_TRACE` notifies the supervisor via `ptrace`, which records inputs, executes the syscall, and records outputs. A third class, deterministic given recorded state (`getpid`, cached `gettid`), executes natively with no logging.

The payoff: the dominant recording cost shifts from per-syscall context switches to `ptrace` thread management and counter interrupts — buffering converts thousands of supervisor round-trips per second into a handful of bulk flushes [1]. A subtle correctness point: the preload library is *untrusted* in-tracee code, and the supervisor validates it during replay. If buffer contents disagree with replay expectations — e.g., corrupted application memory — the mismatch surfaces as a loud divergence, never silent debugger confusion.

### 4.3 Chaos mode: fuzzing the schedule space

By default rr *serializes* threads: one core, one thread at a time, preemptions only at counter-interrupt quanta. This makes replay tractable but has a perverse side effect for bug *finding*: the recorded schedule is one point in an enormous space, and a race needing a different interleaving never manifests. **Chaos mode** (`rr record --chaos`, `RR_CHAOS`) deliberately *de-serializes* execution to provoke concurrency bugs [3].

In chaos mode, rr:

- **Runs threads on multiple cores concurrently**, abandoning serialization;
- **Randomizes scheduling decisions**: preemption quanta, thread selection, and buffered-vs-traced syscall routing all vary per run;
- **Randomizes permitted nondeterministic inputs**, so repeated recordings explore different interleavings.

Each chaos-mode recording remains *deterministically replayable* — the randomness is itself recorded — but different recordings exercise different interleavings. Looped (record → check → repeat), chaos mode becomes a **schedule fuzzer**: a lightweight whole-program alternative to systematic concurrency testing, needing no annotations or synchronization model [4].

```c
/* The interleaving below is only one of exponentially many;
   chaos mode exists to surface the others. */
int balance = 0;

void *deposit(void *arg) {
    for (int i = 0; i < 1000000; i++)
        balance += 1;          /* unsynchronized read-modify-write */
    return NULL;
}

void *withdraw(void *arg) {
    for (int i = 0; i < 1000000; i++)
        balance -= 1;
    return NULL;
}
/* Serialized recording: balance == 0, every time. Looks correct.
   Chaos mode:       balance != 0, eventually. The race is exposed,
   and the failing trace replays deterministically for diagnosis. */
```

The methodology: *use chaos mode to find the bug, deterministic replay to fix it* — one instrument explores the schedule space, the other freezes a single point in it for indefinite interrogation.

### 4.4 Reverse execution via checkpointed replay

rr extends gdb with **reverse execution**: `reverse-continue`, `reverse-step`, `reverse-next`, `reverse-finish`. Conceptually these move the debugger backward in time; implementationally they are *forward replay from checkpoints* — and that reduction determines their performance characteristics [2][3].

During replay rr periodically **checkpoints** by `fork()`ing the tracee — address space, registers, and replay position (counter plus trace offset) captured via copy-on-write, costing microseconds to milliseconds. To execute `reverse-continue` (run backward to the previous breakpoint/watchpoint hit):

1. Locate the most recent checkpoint *before* the current position.
2. Restore it — the forked child becomes the live tracee.
3. Replay forward, stopping at the last breakpoint/watchpoint hit *before* the position where `reverse-continue` was issued.

`reverse-step` is the same reduction at finer granularity: checkpoint, replay forward, stop at the last line-boundary before the starting point. Because replay is deterministic, "the last X before position P" is well-defined, and repeated reverse queries return identical answers — what makes reverse debugging genuinely useful rather than merely suggestive.

```gdb
# Reverse-debugging session: who corrupted this pointer?
(rr) break process_packet
(rr) continue                       # run forward to the crash
Program received signal SIGSEGV, Segmentation fault.
(rr) print pkt->header              # garbage — but when did it become garbage?
(rr) watch -l pkt->header           # hardware watchpoint on the field
(rr) reverse-continue               # jump BACK to the last write to pkt->header
Hardware watchpoint 2: -location pkt->header
Old value = 0x0000000000000000
New value = 0xdeadbeefdeadbeef
0x00007f3a2b1c4d20 in scribble (buf=0x...) at net.c:88
(rr) reverse-step                   # walk backward, line by line, to the cause
```

The cost model: one checkpoint restore plus forward replay over at most one checkpoint interval. rr keeps intervals short (tens of millions of events), so reverse operations stay interactive even on billion-instruction traces [2]. With gdb hardware watchpoints — supported because replay runs on real hardware — this is widely regarded as the most effective known workflow for root-causing memory corruption and race-induced failures.

## 5 Empirical Results and Formal Arguments

### 5.1 Formalizing replay correctness

We now formalize §1's theorem. Model an execution as events $e_1, \dots, e_n$ — deterministic instruction blocks or nondeterministic events (syscall result, signal delivery, preemption). Let $C(e_i)$ be the retired-conditional-branch counter at the start of $e_i$, and $R(e_i)$ the recorded outcome of a nondeterministic event.

> **Theorem:** *Let $E$ be a recorded execution with event sequence $e_1, \dots, e_n$, counter values $C(e_i)$, and recorded outcomes $R(e_i)$. Let $E'$ be a replay that (i) starts from the identical initial binary and state, (ii) re-executes deterministic blocks natively, (iii) substitutes $R(e_i)$ for the outcome of each nondeterministic event, and (iv) delivers each signal/preemption exactly when the live counter equals $C(e_i)$. Then for all $i$, the architectural state (registers, memory) at the start of $e_i$ in $E'$ equals that in $E$.*

*Proof sketch.* By induction on $i$; the base case holds by (i). Assume states match at the start of $e_i$. If $e_i$ is deterministic, native re-execution from identical state yields identical state — the ISA's determinism, the bedrock assumption of all replay systems [4][5]. If $e_i$ is nondeterministic, (iii) forces the recorded outcome by construction, and (iv) forces signals and preemptions at the identical counter value — hence the identical program point, since the counter is a pure function of control flow (§4.1). ∎

The preconditions are exactly what rr enforces: (iii) is syscall buffering plus signal injection; (iv) is the counter-driven scheduler; and the induction is *checked* at runtime by the divergence detector, which verifies $C'(e_i) = C(e_i)$ at every boundary and aborts loudly on mismatch [1]. rr does not merely *hope* the preconditions hold — it *audits* them continuously.

### 5.2 Empirical evaluation: the deployability claim

The ATC 2017 paper's central claim: recording overhead is low enough for *everyday* use — test suites, interactive sessions, production-adjacent workloads — not just post-mortem forensics [1]. Its evaluation methodology:

1. **Workload selection.** A mix of CPU-bound benchmarks, interactive applications (including Firefox, the motivating Mozilla workload), and the rr test suite — stressing syscall rates, thread counts, and JIT-generated code.
2. **Metric discipline.** Overhead as wall-clock slowdown versus native; trace *size* (bytes per recorded second) reported separately, since storage bounds "flight recorder" duration.
3. **Replay fidelity.** Every replayed trace is checked for divergence: zero silent divergences on supported hardware; unsupported configurations fail loudly, as designed.

Headline results, broadly confirmed by subsequent production experience [3][7]:

| Claim | Evidence |
|---|---|
| Recording overhead is typically near native | Slowdowns below 2× across all measured workloads, often near 1×, dominated by `ptrace` and counter-interrupt costs — validating syscall buffering (§4.2) |
| Replay is slower than recording but still practical | Replay re-executes plus supervisor checks; times stay in the same order of magnitude — acceptable for interactive debugging |
| Traces are compact | Only frontier events are logged; trace growth tracks syscall/signal *rate*, not instruction count |
| Chaos mode finds races that serialization hides | Mozilla cases where serialized recording never reproduced the failure but chaos-mode recordings did |

Two caveats. First, overhead is workload-dependent in a principled way: syscall- and thread-heavy workloads cost more, because the recorded frontier is larger. Second, the evaluation's hardware scope is Intel; AMD support was experimental at publication and remains less battle-tested [3] — see §6.

## 6 Limitations

Each limit traces to a violated precondition of the recording contract (§3.2).

**Hardware scope.** Requires x86 with a *deterministic* retired-conditional-branch counter — in practice Intel Sandy Bridge or later. AMD Zen support is experimental; ARM unsupported. The technique needs *some* deterministic progress counter, and not all microarchitectures provide one; hypervisors may also distort the counter [2][3].

**Unrecordable nondeterminism.** Anything outside the frontier breaks replay: memory-mapped device I/O and GPU command streams (no interception of GPU DMA into shared buffers); `RDRAND`/`RDSEED` require identifying every such instruction, including JIT-emitted ones; System Management Interrupts can steal cycles and perturb counters on some firmware; Intel TSX abort behavior is explicitly unsupported [1][2].

**Single-core serialization cost.** All threads run on one core during recording: lost parallelism plus *fidelity* distortion, since the recorded interleaving space differs from native multi-core execution. Chaos mode (§4.3) mitigates the bug-finding consequence but not the parallelism loss; bugs depending on true multi-core timing at nanosecond granularity are out of reach.

**Trace portability.** A trace is bound to the exact binary, libraries, and microarchitecture class that recorded it — not a portable artifact like a core dump.

**Security model.** Tracees are assumed non-malicious: a program deliberately executing unrecorded nondeterministic instructions or attacking the preload library can corrupt its own trace. rr is a debugger, not a sandbox or forensic chain-of-custody system [1].

**Ecosystem.** Linux-only and gdb-centric. macOS/Windows developers use commercial alternatives (Undo UDB, WinDbg TTD) implementing the same time-travel model [7].

## 7 Conclusion

rr's enduring contribution is the *composition*: seccomp-bpf interception, injected syscall buffering, single-core serialization, and — the signature idea — a hardware counter repurposed as a deterministic clock, making record-and-replay deployable on stock systems at near-native overhead [1][2]. On this substrate stand two instruments: **chaos mode**, which inverts the determinism machinery to *explore* the schedule space and surface races, and **reverse execution**, which reduces the hardest debugging query — *when did this become wrong?* — to checkpointed forward replay.

The formal core fits in a theorem (§5.1): deliver every nondeterministic event at the identical counter value, and replay is instruction-for-instruction identical. The engineering that makes it *true in practice* — trapping `RDTSC`, buffering syscalls, auditing divergence at every boundary — is this thesis's actual subject, and why rr moved deterministic replay from prototype to daily tool.

Open directions remain. Extending the technique to ARM performance monitors would bring time-travel debugging to the dominant mobile and emerging-server architecture. Purpose-built hardware — deterministic counters as an architectural guarantee, not a fortunate microarchitectural property — would remove the largest fragility. And convergence with AI debugging agents, which can interrogate a frozen timeline instead of reasoning about a moving target, suggests the record-once, interrogate-forever model will only grow in importance [7].
