# ThinLTO and the Engineering of Whole-Program Optimization: Summary-Based Analysis, Import Heuristics, and Distributed Thin Linking

## Abstract

Link-time optimization (LTO) is the compiler's strongest weapon for optimizing across translation-unit boundaries, yet the classical monolithic implementation — merging every input module into a single intermediate representation before analysis and code generation — collapses on industrial-scale code bases: memory grows with the whole program, serial passes bottleneck the build, and incremental builds become impossible. ThinLTO, developed by Johnson, Amini, and Li and deployed in LLVM since 2016, restructures whole-program optimization into a summary-driven, data-parallel pipeline: each translation unit is compiled to bitcode augmented with a compact *module summary* (function GUIDs, instruction counts, call graphs, reference edges, linkage properties); a fast serial *thin link* merges summaries into a combined index and records all whole-program decisions; and fully parallel, lazily-loading backends then optimize each module independently using summary-directed function importing. This thesis dissects the architecture — summary encoding and GUID identity, the heuristic machinery of cross-module importing, index-recorded global decisions, and the distributed thin-link protocol for cluster-scale builds — and examines the empirical evidence that ThinLTO delivers near-monolithic-LTO performance at near-non-LTO build cost.

## 1. Introduction

Whole-program analysis has an irresistible premise: the optimizer's view should match the program's reality. In languages built on separate compilation — C, C++, Rust, Swift — the most consequential optimization opportunities routinely span module boundaries. A small accessor defined in one translation unit and hotly called from dozens of others; a virtual call whose receiver type is pinned down only by whole-program class-hierarchy analysis; a static initializer whose constant propagation demands visibility into every initializer in the program. *Link-time optimization* exists to bring these edges back inside the optimizer's field of view.

The original LLVM implementation of LTO embodies the most literal interpretation of this premise. At compile time, the frontend emits LLVM bitcode; at link time, the linker plugin feeds every bitcode file into LLVM, which merges them all into one giant `Module` and runs the full interprocedural pipeline serially on it [2]. Conceptually clean, and brutally unscalable: peak memory grows with total program size plus debug information, optimization passes see no parallelism, and a single source change invalidates everything downstream. For large applications — Google's monorepos, the Linux kernel, mobile operating systems — monolithic LTO is often simply unavailable [1].

ThinLTO's central insight is that whole-program *decisions* and whole-program *transformations* need not be colocated. Almost everything the thin-link phase must decide — which functions to import into which modules, which symbols can be internalized, how weak/ODR symbols resolve — can be decided from a lossy, compact summary of each module rather than from its full IR. Transformations, which require full IR, can then execute in embarrassingly parallel backends that consult the recorded decisions. The serial, monolithic portion of the build shrinks to a summary-merge and planning problem whose working set is orders of magnitude smaller than the program's IR. This thesis presents the design in depth: how summaries are encoded and globally addressed (§4.1), how the import planner weighs size against expected inlining benefit (§4.2), how index-driven whole-program decisions coordinate parallel backends without further communication (§4.3), and how the protocol extends to distributed and incremental builds (§4.4).

> **Theorem (Import soundness):** Let *I* be the combined summary index and *D(m)* the set of whole-program decisions recorded for module *m* during the thin link. If every backend applies exactly the import, internalization, and renaming actions prescribed by *D(m)*, and imported functions are renamed to globally unique names, then the linked program is semantically equivalent to the program produced by serial monolithic optimization of the same modules.

*Proof sketch.* Each imported definition is a verbatim copy of its canonical definition, promoted to a unique global name, with references resolved through *I*. Because *D(m)* records the unique-linkage resolution of every weak/ODR symbol, and promotion of locals is bijective on GUIDs, no two definitions of the same symbol survive with conflicting values, and every call site binds to a definition semantically identical to the one monolithic LTO would have chosen. ∎

## 2. Background

### 2.1 The monolithic LTO pipeline

Classical LTO proceeds in two phases. First, every translation unit is compiled to an object containing LLVM bitcode. Second, the link step loads all bitcode, merges it into a single module, and runs the full optimization pipeline — interprocedural constant propagation, function inlining, dead-code elimination, devirtualization — followed by code generation, all serially. The merged module is the analysis scope, which is precisely why the approach scales so poorly: peak memory is proportional to the sum of all IR (dramatically worse with `-g` debug info), wall-clock time cannot exploit multicore machines, and the merged module is a build artifact that cannot be reused incrementally [2].

### 2.2 Earlier attempts at scalability

Two classical mitigations predate ThinLTO. *Partitioned* approaches (e.g., GCC's WHOPR mode) split the merged module for parallel code generation, but the expensive IPA/IPO phases remain serial and the merge step itself stays a memory bottleneck. *Incremental* frameworks require dependency checksums and binary-equivalent code generation to be trustworthy [6]. ThinLTO's contribution is a clean architectural decomposition instead: shrink the serial whole-program phase to operate on summaries, and make everything else per-module parallel [1].

### 2.3 What ThinLTO reuses

ThinLTO does not reimplement LLVM's optimization passes. The inliner, function-attrs, GVN, indirect-call promotion, and the code generator are identical; what changes is the *schedule* and the *scope* of information available when each runs — a deliberate decision guaranteeing ThinLTO's output quality can converge to monolithic LTO's without duplicating the compiler's most intricate parts [2].

## 3. Methodology

The ThinLTO pipeline decomposes into three stages with sharply separated concerns:

1. **Thin compile (parallel, per translation unit).** The frontend compiles each TU to LLVM bitcode exactly as in a non-LTO build, then runs a *module summary* analysis that appends a compact summary block to the bitcode. For every function the summary records: a globally unique identifier (GUID), instruction count, function attributes relevant to IPO (e.g., `norecurse`, memory behavior), the set of called functions (with per-callsite hotness when profile data is available), and the set of referenced global values. Module-level metadata — target triple, source file name, hash of the IR — accompanies the block. Importantly, the bitcode remains fully loadable on its own; the summary is auxiliary data.

2. **Thin link (serial, fast).** The linker plugin reads *only the summary blocks* from every input and merges them into a single `ModuleSummaryIndex`. All whole-program analysis runs on this index: function importing is planned, symbols are resolved (ODR/weak uniquing, internalization of provably-local symbols), and per-module decision records are written out. The index is the sole communication channel between the thin link and the backends — no later synchronization exists [3].

3. **Parallel backends (parallel, per module).** Each module is optimized independently. Guided by its decision record, a backend lazily loads the exporting modules' IR, *imports* the planned function definitions (renaming them to unique names and promoting their linkage), runs the standard optimization pipeline — where imported functions make cross-module inlining and IPO possible — and emits a native object file. Because import decisions were already fixed, backends never communicate; they are embarrassingly parallel and trivially distributable.

The remainder of this thesis examines each mechanism: summary encoding and GUID identity (§4.1), the import planner's budget/benefit machinery (§4.2), index-recorded whole-program decisions (§4.3), and distribution and incrementality (§4.4).

## 4. Deep Dive

### 4.1 Module summaries and GUID-based global identity

A whole-program planner operating without IR faces a fundamental naming problem: the same source-level entity may appear as different `llvm::GlobalValue`s in different modules, and internal-linkage entities in different modules may share a name without sharing an identity. ThinLTO's answer is the **GUID** — a 64-bit identifier computed as the MD5 hash of the entity's name, with a crucial refinement for locals: for `static` functions and other internal-linkage values, the GUID is hashed from *module path + name*, so that two translation units each defining `static void helper()` receive distinct GUIDs, while a `linkonce_odr` template instantiation receives the same GUID in every module that emits it.

The per-module summary block uses dedicated bitcode record types and is deliberately minimal:

- **Function summaries**: GUID, linkage type, instruction count, function flags (e.g., not eligible for inlining, has inline assembly), list of called-value GUIDs with call-edge hotness, list of referenced global GUIDs.
- **Global variable and alias summaries**: GUID, linkage, and (for aliases) aliasee GUID.
- **Module path string table**: maps each module to a stable path used for GUID computation and backend file location.

For large programs the index is typically a few percent of the size of the object files [3] — which is what makes the serial thin-link phase fast and what makes transmitting the index to distributed workers cheap.

```python
# Simplified model of GUID computation (conceptual; LLVM uses MD5 of the
# qualified name, truncated to 64 bits).
import hashlib

def global_value_guid(name: str, linkage: str, module_path: str) -> int:
    if linkage in ("internal", "private"):
        # Locals are disambiguated by their defining module.
        qualified = f"{module_path}:{name}"
    else:
        # Externals, weak/ODR, linkonce: identity is name-based so that
        # duplicate definitions across modules share one GUID.
        qualified = name
    digest = hashlib.md5(qualified.encode()).digest()
    return int.from_bytes(digest[:8], "little")
```

Two design subtleties deserve emphasis. First, the GUID scheme makes *symbol resolution* a pure index operation: ODR uniquing reduces to "summaries sharing a GUID denote one entity; keep the prevailing definition," and internalization reduces to "a GUID referenced only within one module may be marked internal." Second, importing renames copies with a module-unique suffix, so the GUID namespace also underpins *renaming on import*: an imported `static` function keeps its GUID-derived identity for analysis while acquiring a backend-unique symbol name, so later passes and the final link never confuse copies with originals.

### 4.2 Cross-module function importing: heuristics and thresholds

Function importing is ThinLTO's principal cross-module optimization enabler: a callee defined in module *E* is physically copied into module *M* (as a uniquely-renamed, promoted definition) so that *M*'s inliner and IPO passes can optimize across the call edge. But importing is not free — every imported copy grows the importing module's IR, slows its backend, and (if not inlined) grows the final binary. The import planner therefore solves, heuristically, a knapsack-like problem per module: *which callees are worth their bytes?*

The planner's core is a budget-driven, benefit-ordered walk over the call graph recorded in the combined index [4]:

1. **Candidate enumeration.** From each function defined in *M*, the planner follows call edges in the combined index transitively, collecting callees defined in other modules.
2. **Size gate.** A candidate is importable only if its summary instruction count is below a threshold. The default is **100 instructions** (`-import-instr-limit`), mirroring the inliner's own notion of "cheap enough to inline." Larger functions are skipped: they are unlikely to inline, so importing them buys nothing while costing IR size.
3. **Benefit ordering and decay.** Candidates are considered in expected-benefit order. To prevent exponential blowup along deep call chains, each level of transitive importing multiplies the remaining budget by a decay factor below 1, progressively starving distant, speculative imports.
4. **Whole-program pruning.** Functions proven dead by the index-level analysis are never imported; linkonce/weak definitions that lost ODR resolution are skipped in favor of the prevailing copy.

The following Rust-flavored pseudocode captures the planner's shape:

```rust
/// Summary-driven import planning for one module.
fn plan_imports(
    module: &ModuleId,
    index: &CombinedIndex,
    budget: &mut ImportBudget,
) -> Vec<ImportAction> {
    let mut worklist: Vec<(Guid, f64)> = seed_with_local_callsites(module, index);
    let mut plan = Vec::new();
    while let Some((callee, benefit)) = worklist.pop() {
        let summary = index.function_summary(callee);
        // Size gate: only import what the inliner might plausibly inline.
        let limit = budget.limit_for(benefit, summary.hotness);
        if summary.instruction_count > limit { continue; }
        if plan.contains(&callee) || summary.is_dead { continue; }
        plan.push(ImportAction::import(callee, rename_unique(callee)));
        budget.consume(summary.instruction_count, benefit);
        // Transitive callees enter with decayed benefit.
        for next in summary.callees() {
            worklist.push((next, benefit * DECAY_FACTOR));
        }
    }
    plan
}
```

Several refinements sharpen this picture. With profile data, hot call edges are prioritized and the effective size budget scales with hotness: a hot callee may be imported above the nominal threshold (via `-import-hot-multiplier`), while cold callees face a stricter limit — a major reason ThinLTO's binary-size impact stays modest. The `-import-constants` logic imports globals referenced by imported functions. And because the planner runs on summaries, it can afford to be *globally* greedy: it sees every call edge in the program, so its benefit estimates approximate the monolithic inliner's view without ever loading IR [2].

### 4.3 Index-recorded whole-program decisions

The thin link does more than plan imports; it is the *only* phase with a global view, so every decision requiring one is recorded into the index for the backends to obey blindly. The principal decisions are:

| Decision | Index mechanism | Backend effect |
|---|---|---|
| **Import set** | Per-module import list (GUID → source module) | Backend lazily loads exporting IR, copies and renames definitions |
| **ODR / weak resolution** | Prevailing-copy election per GUID | Non-prevailing copies dropped or converted to available_externally |
| **Internalization** | GUIDs referenced by exactly one module marked local | Symbol made `internal`, enabling aggressive IPO |
| **Dead stripping** | GUIDs unreachable in the combined call/reference graph | Definitions omitted from backend IR entirely |
| **Renaming on import** | Unique suffix recorded per (importer, GUID) | Imported copies never collide at final link |

This "decide once, obey everywhere" protocol is what eliminates cross-module synchronization during the parallel phase [5]. Each backend receives the combined index (or, in the distributed case, the slice relevant to its module plus its import sources) and its own decision record; it then proceeds deterministically. The protocol also composes with extensions: indirect-call promotion records value-profile targets in the index; whole-program devirtualization records vtable resolutions; function *specialization* proposals record per-callsite constant arguments and globally-unique suffixes so specialized clones can be coordinated across modules without backend-to-backend communication [5].

### 4.4 Distributed thin linking and incremental builds

Because backends are independent given the index and decision records, ThinLTO parallelizes *across machines*. The **distributed ThinLTO** (DTLTO) protocol splits the pipeline: the thin link runs once on a coordinator, then each backend is dispatched as an independent job carrying its module's bitcode, the combined index (or a pruned slice), and the list of exporting modules whose definitions it must import; a final ordinary native link produces the binary. The constraints are logistical, not algorithmic: the build system must materialize the thin-link artifacts and route IR files to workers, which is why first-class DTLTO support arrived in Bazel and Buck2 before generic integrations such as the "Integrated Distributed ThinLTO" effort aimed at make/ninja/CMake-style builds [7]. A Linux-kernel DTLTO RFC applies the same architecture to one of the most build-sensitive code bases in existence, motivated by objtool and livepatch integration [6].

Incrementality falls out of the same decomposition. Backends depend only on their own module's bitcode plus the index slice relevant to their imports, so a source change to module *M* requires re-running only the thin compile of *M*, the (cheap, summary-only) thin link, and the backends of modules importing from *M*. Modules that neither changed nor import from *M* reuse cached objects — the property monolithic LTO fundamentally lacks [2].

## 5. Empirical Results and Proofs

The canonical evaluation remains the CGO 2017 paper [1], whose headline results on large C++ workloads (Google-internal applications, SPEC CPU2006) established ThinLTO's position:

- **Build time.** ThinLTO's total link-time cost approaches that of a *non-LTO* build: the serial thin link is a small fraction of the pipeline, and the parallel backends scale with available cores. Monolithic LTO, by contrast, is dominated by its serial whole-program phase.
- **Memory.** Peak memory during the thin link is bounded by the summary index — dramatically below the merged-module IR (plus debug info) that monolithic LTO holds. Each backend's memory is bounded by a single module plus its imports.
- **Runtime performance.** Across the reported benchmarks, ThinLTO recovers the large majority of monolithic LTO's runtime gains — in many cases matching them — because the import planner restores the cross-module inlining opportunities that dominate LTO's benefit [2].

Subsequent engineering has sharpened both sides of the trade-off. Profile-guided import tuning (hotness-scaled thresholds) concentrates the import budget where inlining actually fires; size-optimization work for `-Oz` mobile targets has exposed cases where ThinLTO's importer was tuned for speed rather than size, e.g., by making the import planner aware of the downstream size costs of speculative imports [8]. The DTLTO integration efforts [6][7] extend the scalability claim from multicore to multi-machine — the thin-link artifacts (index plus per-module plans) are small enough to distribute cheaply, the same compactness property that makes the single-machine thin link fast.

On the formal side, the import-soundness argument of §1 rests on two properties verifiable from the index: (i) renaming on import is injective over (module, GUID) pairs, so no imported copy aliases an unrelated symbol; (ii) ODR resolution elects exactly one prevailing definition per GUID, so `available_externally` conversions cannot resurrect a second live definition. Together they imply the parallel backends, despite never communicating, collectively realize a single consistent whole-program symbol table — the invariant that makes ThinLTO's parallelism *embarrassingly* parallel rather than merely concurrent.

## 6. Limitations

ThinLTO's architecture buys scalability at the cost of several genuine constraints, and an honest account must name them:

1. **The serial thin link.** The thin link is the one monolithic phase that remains, and while it is fast (summary-only), it is serial and its cost grows with program size. Index bloat — e.g., from recording per-argument constant information for specialization [5] — directly taxes this phase; measurements on SPEC2017 intrate show roughly a 2.8% object-size increase from enriched summaries, a cost paid on every build [5].
2. **Indirect calls.** Without profile data, indirect call edges are invisible to the summary call graph, so virtual and function-pointer calls across modules are not imported and not devirtualized. ThinLTO leans on PGO/indirect-call promotion and whole-program devirtualization metadata to recover these cases, but cold or unprofiled indirect calls remain a gap relative to monolithic LTO's IR-level visibility.
3. **Debug information.** Imported functions carry their debug info into importing modules, and the duplication interacts poorly with already-heavy `-g` builds; this remains an active tuning area.
4. **Distributed logistics.** DTLTO's algorithm is simple; its deployment is not — the build system must orchestrate index distribution, IR staging, and plan routing, which is why adoption outside Bazel/Buck2-style systems needed dedicated integration work [7].
5. **Heuristic fragility.** The import planner's thresholds (instruction limit, decay factors, hotness multipliers) are tuned empirically. Pathological programs — deep chains of just-under-threshold functions, or hot code hidden behind unprofiled indirect calls — can defeat the heuristics, yielding import bloat or missed inlining: the standard price of summary-based approximation, where the planner sees the call graph but not the IR the inliner will face.

## 7. Conclusion

ThinLTO reframes whole-program optimization as a *planning* problem separable from the *transformation* problem. By compressing each translation unit to a summary of GUIDs, sizes, call edges, and linkage facts, it reduces the serial whole-program phase to an index merge and a heuristic import plan; by recording every global decision in that index, it frees the backends to optimize in complete isolation, lazily materializing only the IR they were told to import. The result is an architecture that is simultaneously scalable (serial work proportional to summaries, not IR), parallel (backends share nothing), distributable (the index and plans are small artifacts), and incremental (changes invalidate only affected modules and their importers) — while recovering, empirically, the large majority of monolithic LTO's runtime performance [1][2].

The deeper lesson generalizes beyond LLVM. Any whole-program analysis whose decisions depend only on *relational* facts — who calls whom, who references what, which definitions are equivalent — can be factored into a summary phase and an action phase, with the summary phase engineered for compactness and the action phase for parallelism. ThinLTO is the existence proof that this factoring need not sacrifice optimization quality: with careful heuristic design, a planner that never sees IR can make nearly the same inlining decisions as one that sees everything. Future work — richer summaries for specialization and devirtualization, tighter size-aware import budgets, and frictionless distributed deployment [6][7][8] — continues to narrow the residual gap between what the summary planner can see and what the whole program contains.
