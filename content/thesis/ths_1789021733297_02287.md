# Control-Flow Integrity: Forward-Edge Enforcement, Shadow Stacks, and Hardware-Assisted Defenses from CET to Pointer Authentication

## Abstract

Control-flow integrity (CFI) is the foundational defense against code-reuse attacks, constraining every indirect control transfer to a statically sanctioned target set. This thesis unifies the two halves of CFI — forward-edge enforcement of indirect calls and jumps, and backward-edge protection of return addresses — with the hardware assists that make them practical: Intel Control-flow Enforcement Technology (CET), Arm Pointer Authentication (PAC) and Branch Target Identification (BTI), and compiler schemes such as LLVM's CFI, KCFI, and Microsoft's Control Flow Guard (CFG) and Xtended Flow Guard (XFG). We trace the lineage from Abadi et al.'s 2005 formalization through the bypass era of return- and jump-oriented programming and control-flow bending to today's hybrid software-hardware stacks, compare precision-versus-performance tradeoffs across label-based, type-based, and cryptographic designs, and evaluate production deployments in the Linux kernel, Windows, and Android. We conclude that durable protection requires exact backward-edge enforcement, precise forward-edge policy, hardware roots of trust, and information-flow hygiene against disclosure-assisted forgery.

## 1 Introduction

The vulnerability behind all control-hijacking attacks is deceptively simple: a von Neumann machine cannot reliably distinguish code pointers from data. Corrupt a return address, a function pointer, or a C++ vtable pointer, and the processor transfers control wherever the corrupted pointer directs. Data Execution Prevention closed the easiest avenue — injected shellcode — but attackers adapted by *reusing* code already resident in the address space. Shacham's 2007 demonstration that Turing-complete computation is achievable by chaining fragments ("gadgets") of existing libc code [5] inaugurated the modern era of code-reuse exploitation.

The principled defense arrived in 2005, when Abadi, Budiu, Erlingsson, and Ligatti introduced **control-flow integrity**: every *computed* transfer (indirect calls, indirect jumps, returns) is checked at runtime against the legal destinations of a precomputed control-flow graph [1]. CFI is a *stateless, prevent-the-exploit* defense — it permits the corruption but blocks its weaponization — and its guarantees can be stated formally even against an adversary with arbitrary read and write access to data memory.

Two decades later CFI has fragmented into a constellation of mechanisms. The first division is between the **forward edge** (calls and jumps, where the legal target set must be over-approximated) and the **backward edge** (returns, where the correct target is known exactly). Our central claim: the trajectory — from coarse-grained software CFI, through the bypass era, to hardware-rooted cryptographic enforcement — converges on one conclusion: **fine-grained forward-edge CFI is necessary but insufficient; only precise forward-edge checks combined with exact backward-edge protection and hardware enforcement constitute a durable defense.**

> **Theorem:** *Soundness of CFI.* Given a control-flow graph \(G = (V, E)\) over-approximating all legitimate transfers of program \(P\), a mechanism that aborts whenever an indirect transfer \((u, v) \notin E\) is attempted guarantees every executed transfer is a member of \(E\) — under non-writable code, non-executable data, and unforgeable labels [1].

## 2 Background

### 2.1 The Attack Lineage

Control hijacking proceeds in three phases: (i) a memory-safety bug grants a write primitive; (ii) the write corrupts control data — a return address, function pointer, or vtable pointer; (iii) control is redirected. Early defenses addressed each phase partially: **stack canaries** detect (i→ii) but fall to information disclosure; **ASLR** collapses once a single pointer leaks; **DEP** defeats (iii) for injected code but not reused code.

The watershed was *return-oriented programming*: x86's dense encoding yields gadgets — short sequences ending in `ret` — chainable via corrupted return addresses into arbitrary computation [5]. **Jump-oriented programming** generalized the technique to indirect jumps via a *dispatcher gadget*, and *counterfeit object-oriented programming* (COOP) chained legitimate C++ virtual calls through attacker-crafted objects, showing that even sophisticated policies leave residual surface.

### 2.2 The CFI Abstraction

Abadi et al. formalized CFI as a runtime monitor over a labeled control-flow graph [1]: each indirect-branch source and each legal destination carries matching *labels*, and instrumentation checks label equality before every indirect transfer, aborting on mismatch. Soundness rests on non-writable code (\(W\oplus X\)), non-executable data, and label unforgeability — labels must occur nowhere else in code memory. The original binary-rewriting implementation reported ~16% mean overhead on SPEC CPU2000, a cost profile that motivated two decades of refinement.

### 2.3 Forward Edge versus Backward Edge

- **Forward-edge CFI** guards indirect calls and jumps. The legal set must be over-approximated by static analysis — typically type-based: a call through a pointer of type \(\tau\) may target any address-taken function of type \(\tau\). The resulting *equivalence classes* are the central security metric.
- **Backward-edge CFI** guards returns, where the correct target is *exactly* known: the address pushed by the matching call, enabling exact enforcement via a **shadow stack**.

Carlini et al.'s *control-flow bending* (2015) showed why the distinction matters: even *fully precise* static forward-edge CFI remains exploitable, because attackers bend execution along *legal* paths [2]. Crucially, adding shadow stacks removed arbitrary code execution in three of six evaluated binaries. **Forward-edge precision has a ceiling; the backward edge must be exact.**

## 3 Methodology

We reconstruct the Abadi et al. label-based model and its soundness argument [1], trace the attack literature (ROP [5], JOP, COOP, control-flow bending [2]) as a sequence of precision defeats, classify forward-edge schemes by granularity, binding mechanism, and trust anchor, derive the operational semantics of Intel CET [6] and Arm PAC/BTI [7][8], and synthesize published evaluations [9] with production deployments (Linux KCFI [10][11], Windows CFG/XFG [12][13][14], Android, iOS).

## 4 Deep Dive

### 4.1 Forward-Edge Enforcement: From Labels to Type Signatures to Hashes

The Abadi scheme is *label-based*: every indirect call site and function entry carries a 32-bit ID, and the check is one comparison [1]. Labels are coarse — all functions sharing a label are mutually reachable — but need no whole-program type information.

**LLVM's CFI** refines this to *type-based* enforcement [3]. At link time (requiring LTO in the classic design), the compiler builds one **jump table** per observed function prototype, and every indirect call is checked against the jump table for the call site's expected type. The residual weakness is the **equivalence class problem**: hundreds of functions may share a signature (e.g., `void (*)(void *)` callbacks), and any one — including dangerous ones — remains reachable; such type collisions are abundant and exploitable in nested fashion [4].

**Microsoft's Control Flow Guard (CFG)** verifies only that the target is a *valid function entry point* (a bitmap check), ignoring the call-site type [12]. **Xtended Flow Guard (XFG)** answers with 55-bit hashes of the full prototype embedded before each indirect call and compared against a hash at the target [13][14] — type-based precision without LTO's whole-program requirement.

**KCFI**, merged for Linux 6.1, keeps type-based checks but eliminates jump tables and LTO: the compiler emits a 32-bit type hash before each function, and each indirect call site traps on hash mismatch [10][11] — the modern pattern of *software precision layered over hardware enforcement*.

| Scheme | Granularity | Needs LTO | Hardware assist | Typical overhead |
|---|---|---|---|---|
| Abadi 2005 labels [1] | Coarse label sets | No | None | ~16% avg (SPEC2k) |
| LLVM CFI [3] | Type-signature jump tables | Yes | None | 1–5% |
| KCFI [10][11] | 32-bit type hash + trap | No | CET IBT | <2% |
| MS CFG [12] | Valid-entry bitmap only | No | None | ~2% |
| MS XFG [13][14] | 55-bit prototype hash | No | None | ~2–4% |
| CET IBT [6] | ENDBRANCH landing pads | No | **Yes** | <1% |

### 4.2 Backward-Edge Protection: Shadow Stacks

The backward edge admits an *exact* solution because the legitimate target is determined by the dynamic call history. A **shadow stack** is a parallel stack recording return addresses at `call` time and verifying them at `ret` time; any mismatch aborts execution. Security reduces entirely to the integrity of the shadow stack itself.

Software shadow stacks (e.g., LLVM's **ShadowCallStack** for AArch64/RISC-V [9]) dedicate a callee-saved register (x18) as the shadow-stack pointer — a fragile convention broken by third-party code or disclosure attacks revealing its location.

**Intel CET** solves the integrity problem in hardware [6]. The shadow stack lives in pages where ordinary stores fault — only `call`/`ret` micro-operations may modify them. On `call`, the return address is pushed to both stacks; on `ret`, the processor pops both and compares, raising `#CP` on mismatch, and refuses to execute, even speculatively, at a target disagreeing with the shadow stack.

```nasm
; x86-64 with CET (shadow-stack operations are implicit in call/ret)
foo:
    endbr64                 ; IBT landing pad (forward edge)
    call bar                ; pushes ret addr to data stack AND shadow stack
    ret
bar:
    endbr64
    ret                     ; pops both stacks; #CP on mismatch (backward edge)
```

The shadow stack converts the backward edge from a *policy* problem (which targets are allowed?) into an *integrity* problem (is this the address the matching call pushed?) — and hardware page protections make the integrity problem tractable.

### 4.3 Hardware Forward-Edge Enforcement: CET IBT and Arm BTI

**Intel CET Indirect Branch Tracking (IBT)** implements a two-state machine per privilege level [6]: when an indirect `call`/`jmp` retires, the tracker enters `WAIT_FOR_ENDBRANCH`, and the next retired instruction *must* be `ENDBR32`/`ENDBR64`, else a `#CP(ENDBRANCH)` fault fires. Compilers emit `ENDBR64` at every function entry (a NOP on legacy silicon, so CET binaries degrade gracefully), and the `notrack` (`3Eh`) prefix permits deliberate opt-outs. IBT confines the gadget universe from "any executable byte" to "function entries and address-taken labels," defeating classic mid-function ROP/JOP gadgets at near-zero cost; its speculative window past a missing ENDBRANCH is limited to two instructions [6].

**Arm Branch Target Identification (BTI)** (Armv8.5-A) is the architectural twin: indirect branches may only target instructions beginning with a `BTI` landing pad, with variants distinguishing call-only, jump-only, or either-class targets [7][8]. ELF `GNU_PROPERTY` notes let the loader enforce BTI permissions only when every mapped object opts in — a deployability lesson: partial adoption must not break unprotected libraries.

Both are *coarse-grained by design*. Their thesis is defense in depth: not substitutes for type-based forward-edge CFI, but a hardware floor beneath it, eliminating the cheapest gadget classes at negligible cost.

### 4.4 Cryptographic Pointer Integrity: Arm Pointer Authentication

**Pointer Authentication (PAC)** (Armv8.3-A) authenticates the pointer itself rather than checking targets against a set [7][8]. A keyed MAC (QARMA) is computed over the pointer value and a 64-bit *context* modifier, truncated into the pointer's unused upper bits; any corruption invalidates the MAC with overwhelming probability. The canonical deployment signs **return addresses**:

```c
// AArch64, -mbranch-protection=pac-ret (GCC/Clang) [8]
foo:
    PACIASP            // sign LR with SP as modifier; spill signed LR
    stp x29, x30, [sp, #-16]!
    ...
    ldp x29, x30, [sp], #16
    RETAA              // authenticate x30 against SP; trap on failure; return
```

`PACIASP` signs the link register using the stack pointer as modifier, defeating *replay* of a signed address from another frame; `RETAA` authenticates before use, trapping on failure. The key lives in hardware registers inaccessible to EL0, so even an attacker with arbitrary memory read/write cannot forge a PAC. The residual attack is **forgery via signing gadgets** — PAC authenticates pointers, not control flow, and must be paired with forward-edge policy.

PAC generalizes beyond returns: **code pointers** (function pointers, vtable pointers) can be signed at creation with type- or site-specific modifiers and authenticated before indirect calls — *cryptographically enforced* forward-edge CFI with per-pointer precision no static equivalence class can match. Apple's arm64e ABI deploys PAC pervasively across kernel and userspace [8].

> **Theorem:** *PAC unforgeability.* Under the QARMA pseudorandom-permutation assumption with the key confined to privileged registers, the probability that an adversary with arbitrary memory access forges a valid PAC for an attacker-chosen pointer without a signing oracle is negligible in the PAC width. Corruption is thus *detected* at use; residual risk is confined to oracle-driven forgery, which forward-edge policy must independently constrain.

### 4.5 The Precision–Performance–Compatibility Trilemma

Burow et al. formalized the three-way tension governing every CFI design [9]:

1. **Precision** — the size of the allowed target set per indirect branch. Type-based schemes achieve 10–100× reduction; landing-pad schemes only entry-point granularity; PAC achieves per-pointer granularity.
2. **Performance** — cycles per indirect branch. Software checks cost 5–30 cycles per site; CET IBT costs ~0; shadow-stack push/pop costs one extra store/load per call; PAC costs one QARMA evaluation in dedicated hardware.
3. **Compatibility** — tolerance of JITs, `dlopen`'d plugins, hand-written assembly, and cross-module boundaries. LTO-dependent schemes struggle with dynamic loading; KCFI and XFG avoid whole-program visibility; CET's NOP-compatible ENDBRANCH and Arm's NOP-space PAC instructions let mixed binaries interoperate [6][7][8].

No design dominates all three axes — the trilemma is fundamental, because precision demands whole-program knowledge, performance demands hardware, and compatibility demands locality. The industry's revealed preference is *layered*: coarse hardware floors (IBT/BTI), exact hardware backward edges (shadow stacks/PAC-signed returns), and increasingly precise software forward edges (KCFI/XFG).

## 5 Empirical Results and Complexity Analysis

### 5.1 Security: What the Bypasses Taught Us

- **Coarse-grained bypasses (2013–2014).** Davi et al. showed that CFG-class policies — any policy whose equivalence classes contain Turing-complete gadget sets — fall to ROP/JOP built entirely from *allowed* targets. COOP extended this to C++ virtual dispatch through attacker-crafted counterfeit objects.
- **Fine-grained limits (2015).** Carlini et al. evaluated *fully precise static CFI* and still achieved Turing-complete computation via control-flow bending on five of six real binaries [2]. The decisive secondary finding: shadow stacks removed arbitrary code execution in three of six cases, isolating the backward edge as the load-bearing wall.

Each increase in forward-edge precision raised the bar from "gadget stitching" to "bending along legal paths" to "oracle-driven forgery," while the backward edge — once exactly enforced — proved the most robust single investment.

### 5.2 Performance Complexity

Software forward-edge checks cost \(O(1)\) per branch — roughly one load, one compare, one predictable branch. Shadow stacks add one store per `call` and one load-plus-compare per `ret`. CET IBT is \(O(1)\) with a near-zero constant: ENDBRANCH retires as a NOP. PAC signing costs a few cycles per pointer in dedicated hardware.

Published end-to-end overheads cluster instructively: classic LLVM CFI 1–5% on SPEC CPU2006 [3]; KCFI under 2% on kernel workloads [11]; CET shadow stack plus IBT under 2% combined on SPEC CPU2017; PAC return-address signing ~1–3% on AArch64 server workloads [7]. **Hardware assistance moved strong CFI from "research overhead" to "deployable default"** — which is why Android, Windows, and iOS now ship layered CFI to billions of devices.

### 5.3 Deployment Case Studies

- **Linux kernel (KCFI + CET/PAC).** After the LTO-bound CFI of 5.13 proved operationally painful, 6.1 replaced it with KCFI: no LTO, no jump tables, trap-based type-hash checks, composable with x86 CET-IBT and arm64 PAC/BTI [10][11].
- **Windows (CFG → XFG → CET).** CFG shipped as the coarse bitmap baseline [12]; XFG added 55-bit prototype hashes for call-site-sensitive precision [13][14]; on CET-capable silicon the OS additionally enables hardware shadow stacks.
- **Android / iOS.** Android has shipped LLVM CFI plus ShadowCallStack in userspace and the kernel since 2018 [9]; Apple's arm64e ABI applies PAC to return addresses, code pointers, and data pointers across the OS [8].

## 6 Limitations

1. **Non-control-data attacks.** CFI constrains *where* the program goes, not *what* it computes. Corrupting a UID or an `is_admin` flag achieves the attacker's goal without diverting control flow; CFI is orthogonal to data-flow integrity, not a substitute.
2. **Control-flow bending residual.** Even fully precise static forward-edge CFI permits attacker-directed computation along legal paths [2]. PAC-precise signing narrows but does not eliminate this: any policy admitting attacker-influenced-but-legal calls retains bending surface.
3. **Signing oracles and key exposure.** PAC's unforgeability assumes no signing oracle and key confidentiality. A gadget that signs attacker-chosen pointers, or a disclosure leaking the key, collapses the guarantee to that of a software check.
4. **Just-in-time compilation.** JITs generate code at runtime, violating the non-writable-code assumption; CFI coverage of JIT'd code remains partial.
5. **TOCTOU in software checks.** A software check that loads a pointer, validates it, then calls it is racy under concurrent attacker writes; only atomic authenticate-and-branch sequences (RETAA, CET-paired instructions) close the window.
6. **Coverage gaps.** Hand-written assembly, setjmp/longjmp, C++ exception unwinding, and signal handlers resist clean CFG modeling; each requires carve-outs (landing pads, `notrack` prefixes, unwinder annotations) that are themselves attack surface.

## 7 Conclusion

Control-flow integrity has traveled from a binary-rewriting prototype with 16% overhead to a hardware-rooted, OS-deployed baseline protecting billions of devices — yet its core is unchanged since 2005: *execution must follow the control-flow graph, and every computed transfer must be justified* [1]. Three lessons endure. **First, the backward edge is the priority.** Return addresses admit exact enforcement, and the record — from control-flow bending's shadow-stack findings [2] to CET's hardware shadow stack [6] and PAC-signed returns [7] — shows exact backward-edge protection is the highest-leverage investment. **Second, forward-edge precision has diminishing returns without cryptographic binding.** Type-based equivalence classes shrink the target set but leave bending surface; per-pointer MACs or hardware state machines change the attacker's problem from "find a permitted gadget" to "forge an authentication." **Third, hardware is the trust anchor.** Page-protected shadow stacks, privileged PAC keys, and microarchitectural branch trackers remove whole bypass classes by construction.

The frontier is *compositional*: KCFI type hashes verified under CET-IBT [11], XFG prototype hashes atop CFG bitmaps [14], PAC-signed code pointers beneath BTI landing pads [8]. No single mechanism ends code reuse; but the layered stack — precise software policy, exact hardware backward edge, cryptographic pointer integrity, coarse hardware forward floor — has made control-flow hijacking expensive, unreliable, and increasingly impractical. The open problems are data-only attacks, JIT'd code, and the formal verification of the composition itself.
