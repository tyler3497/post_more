# Vectorized Query Execution at Scale: A Principled Analysis of Apache DataFusion, Morsel-Driven Parallelism, SIMD Hash Joins, Dictionary Encoding, and Adaptive Reoptimization

## Abstract

Vectorized query execution has become the dominant paradigm for analytical query processing, replacing tuple-at-a-time interpretation with tight loops over columnar batches. This thesis presents a principled analysis of the execution architecture underpinning Apache DataFusion, an extensible vectorized engine built on Apache Arrow, and examines five interlocking mechanisms that determine its performance: columnar vectorized operator pipelines, morsel-driven parallelism as a NUMA-aware scheduling discipline, SIMD-accelerated hash joins with cache-conscious partitioning, dictionary encoding as a late-materialization compression strategy, and adaptive reoptimization driven by runtime statistics. Drawing on four decades of literature from MonetDB/X100 through contemporary adaptive optimizers, we derive quantitative cost models, state formal theorems characterizing morsel scheduling and vectorized probe complexity, and specify empirical microbenchmark methodology for validating each claim. We argue these techniques compose multiplicatively rather than additively: vectorization amortizes interpretation overhead, morsel scheduling balances skew, SIMD widens per-cycle throughput, dictionary encoding reduces memory traffic, and runtime reoptimization corrects cardinality errors that static planning cannot foresee.

---

## 1 Introduction

Analytical query engines face a fundamental tension: they must evaluate declarative SQL over billions of rows with sub-second latency while running on hardware whose peak throughput is gated by memory bandwidth, instruction-level parallelism, and cache residency. For two decades the community has converged on a coherent answer. First, *columnar storage* with *vectorized execution* keeps tight inner loops fed from L1 cache, amortizing the interpretation overhead that cripples tuple-at-a-time engines [6]. Second, *morsel-driven parallelism* dispatches small fragments of data to worker threads dynamically, achieving automatic load balancing and NUMA locality without a static partitioning plan [3]. Third, *SIMD-accelerated operators* widen per-cycle throughput by evaluating predicates and hash probes on multiple values simultaneously [4], while cache-conscious partitioning keeps hash tables resident in the fastest levels of the hierarchy [5]. Fourth, *dictionary encoding* compresses repetitive string data into integer codes, converting expensive string comparisons into cheap integer arithmetic. Fifth, *adaptive reoptimization* revises the physical plan mid-execution using statistics that only exist at runtime, correcting the cardinality misestimates that plague static optimizers [7].

Apache DataFusion is a *columnar, streaming, multi-threaded, vectorized execution engine* in Rust on Apache Arrow [1]; Ballista scales it across a cluster via scheduler/executor processes exchanging Arrow data over Flight [2]. The pair is an ideal case study: all five mechanisms are visible in, or directly applicable to, this architecture.

The contributions of this thesis are: (1) a unified analytical cost framework relating batch size, cache residency, and selectivity; (2) formal theorems on morsel scheduling bounds and vectorized probe complexity; (3) a detailed mapping of these abstractions onto DataFusion's `RecordBatch` streams, `ExecutionPlan` nodes, and Ballista's stage graph; and (4) empirical methodology with modeled projections, plus an honest accounting of limitations.

## 2 Background and Related Work

The lineage begins with MonetDB/X100 (2005), which showed that processing vertical *vectors* of values through tight operator loops keeps instruction and data caches hot [6]. DataFusion inherits this: physical operators consume and produce Arrow `RecordBatch` values, turning filters into simple loops over contiguous arrays [1].

The classical *Volcano* model encapsulates parallelism in exchange operators with static thread assignment, which suffers under skew [3]. Leis et al. answered with *morsel-driven parallelism* (2014): small fragments (*morsels*, 10K–100K rows) are pulled from a shared dispatcher by worker threads, each pushing its morsel through an entire pipeline — a discipline modern engines such as DuckDB adopt [3].

Balkesen et al. redesigned hash joins for multi-core hardware: radix partitioning into cache-sized fragments plus parallel build-probe achieves near-linear scaling, with hardware-conscious tuning (fan-out matched to TLB/cache) deciding between implementations [5]. Polychroniou et al. took the orthogonal axis — *rethinking SIMD vectorization* — showing vertical, branch-free kernels for selection, aggregation, and probing beat scalar code on x86 [4], later generalized into the VIP vectorized engine [10].

Finally, static cardinality estimation is the Achilles' heel of physical planning. Spark's *Adaptive Query Execution* (AQE, since 3.0) re-optimizes mid-execution using runtime statistics: coalescing small shuffle partitions, converting sort-merge joins to broadcast/hash joins when runtime sizes permit, and splitting skewed partitions [7]. Later work added fine-grained multi-objective parameter tuning [8] and learned optimizers that improve across executions [9].

The following table positions the major execution models discussed in this thesis:

| Execution model | Unit of work | Parallelism discipline | Interpretation overhead | Representative systems |
|---|---|---|---|---|
| Tuple-at-a-time (Volcano) | single row | static exchange operators | one virtual call / row | PostgreSQL, early MySQL |
| Vectorized (X100-style) | columnar batch | morsel-driven, dynamic | amortized over batch | DataFusion, DuckDB, Velox |
| Data-centric codegen | tight loop over morsel | morsel-driven + compiled | none (compiled) | HyPer, Umbra |
| Distributed vectorized | stage of batch partitions | scheduler + task graph | amortized over batch | Ballista, Spark AQE |

## 3 Methodology

Our methodology is analytical and constructive. For each mechanism we:

1. Define a parametric cost model grounded in hardware parameters (cache sizes, SIMD width, memory bandwidth, thread count).
2. Instantiate the model for the DataFusion/Ballista architecture.
3. Derive asymptotic and constant-factor predictions.
4. Specify a microbenchmark design to test each prediction.

Cost models and scaling laws transfer across hardware; absolute benchmark numbers do not.

We adopt the following notational conventions throughout. Let $B$ denote the vector (batch) size in rows, $W$ the SIMD lane width in elements, $C_k$ the capacity of cache level $k$ in bytes, $P$ the number of worker threads, $M$ the morsel size in rows, and $\sigma$ an operator's selectivity. Memory traffic is measured in bytes moved through the slowest crossed level of the hierarchy; compute cost in CPU cycles.

The canonical vectorized scan-filter-project pipeline cost is modeled as:

$$T(B, \sigma) = \frac{N}{B}\left(c_{\text{dispatch}} + B \cdot (c_{\text{scan}} + \sigma \cdot c_{\text{proj}})\right) + T_{\text{mem}}(N \cdot w)$$

where $N$ is input cardinality, $w$ row width, $c_{\text{dispatch}}$ per-batch overhead, and $T_{\text{mem}}$ memory-transfer time. The key insight: $c_{\text{dispatch}}$ amortizes over $B$ rows ($c_{\text{dispatch}}/B \to 0$), but $B \cdot w$ must stay cache-resident or $T_{\text{mem}}$ dominates — the central tension of Section 4.

For empirical validation we specify microbenchmarks on a dual-socket $P=64$ machine with AVX-512 ($W=8$ for 64-bit elements), TPC-H scale factors 10 and 100, geometric means over five runs with cache flushes between iterations, reporting wall-clock time and hardware counters (L1/L2/LLC misses, SIMD retired-µop fraction).

## 4 Architectural Deep Dive: The Five Pillars of Modern Vectorized Execution

### 4.1 Columnar Vectorized Execution in Apache DataFusion

DataFusion's execution model is built on two primitives: the Apache Arrow `RecordBatch`, a columnar container of $B$ rows (default target batch size 8192), and the `ExecutionPlan` trait, whose physical operators transform streams of batches. Execution is pull-based and streaming: a parent operator polls its children for the next batch, applies a tight loop over contiguous column arrays, and emits the result. Because Arrow is also the network protocol (via Arrow Flight), Ballista can ship intermediate results between executors without serialization cost, decomposing a physical plan into stages connected by shuffle boundaries [2].

The vectorized filter illustrates the paradigm: given a boolean mask, the operator compacts surviving rows via selection vectors — no per-tuple branching, no virtual dispatch in the inner loop. With $B=8192$ and ~100 cycles of dispatch cost, per-row overhead is $≈ 0.01$ cycles against 1–5 cycles of data touching — the X100 argument [6], now in a memory-safe language with a full SQL planner [1].

A minimal physical operator in DataFusion's style can be sketched in Rust as follows:

```rust
use arrow::array::{ArrayRef, BooleanArray};
use arrow::compute::filter;
use arrow::record_batch::RecordBatch;
use datafusion::physical_plan::SendableRecordBatchStream;

/// Vectorized selection: one tight loop over a whole batch,
/// amortizing dispatch cost over B rows instead of paying it per tuple.
fn vectorized_select(batch: &RecordBatch, mask: &BooleanArray) -> RecordBatch {
    let projected: Vec<ArrayRef> = batch
        .columns()
        .iter()
        .map(|col| filter(col.as_ref(), mask).expect("filter"))
        .collect();
    RecordBatch::try_new(batch.schema(), projected).expect("schema")
}
```

Streaming keeps memory bounded: operators never materialize full intermediates; only *pipeline breakers* — hash-join builds, sorts, aggregations — materialize.

### 4.2 Morsel-Driven Parallelism and NUMA-Aware Scheduling

Vectorization answers *how* a thread processes data; morsel-driven parallelism answers *which* data and *when*. Inputs are divided into morsels; $P$ workers race to claim them from a dispatcher, each pushing its morsel through an entire pipeline [3]. DataFusion realizes this via *partitioned* execution: sources expose multiple partitions whose streams are assigned to worker threads, each running a full operator pipeline.

Three properties make the discipline powerful: *dynamic load balancing* (a thread finishing a morsel claims another, so skew never idles cores); *NUMA awareness* (dispatch prefers node-local morsels, cutting cross-socket traffic [3]); and *lock-free hot paths* (global state built once, per-morsel state thread-local, merged only at pipeline boundaries).

> **Theorem 1 (Morsel scheduling bound).** *Let $T_1$ be the single-threaded execution time of a pipeline over $N$ rows divided into morsels of size $M$, scheduled work-conservingly over $P$ identical workers with per-morsel dispatch cost $d$. Then the parallel makespan satisfies*
>
> $$T_P \le \frac{T_1}{P} + \frac{N}{M} \cdot \frac{d}{P} + M \cdot c_{\max}$$
>
> *where $c_{\max}$ is the maximum per-row processing cost. In particular, as $M \to \sqrt{N d / (P c_{\max})}$, the overhead terms are balanced.*

*Proof sketch.* The first term is ideal speedup; the second spreads total dispatch work $(N/M) \cdot d$ over $P$ workers; the third bounds the tail by one morsel's processing time on the critical path. Minimizing the overhead terms in $M$ yields the optimum. ∎

The theorem quantifies the central tuning trade-off: morsels too small drown in dispatch overhead; morsels too large reintroduce skew at the tail. A Python simulation of the dispatch dynamics makes the trade-off concrete:

```python
import heapq

def morsel_makespan(row_costs, M, P, d):
    """Work-conserving morsel schedule; row_costs = per-row costs (skew-aware)."""
    morsels = [sum(row_costs[i:i+M]) + d
               for i in range(0, len(row_costs), M)]
    workers = [0.0] * P          # each worker's current load
    heapq.heapify(workers)
    for m in sorted(morsels, reverse=True):  # LPT: largest morsel first
        t = heapq.heappop(workers)
        heapq.heappush(workers, t + m)
    return max(workers)

# Skewed input: 5% of rows cost 20x. Fine morsels absorb the skew.
import random
random.seed(7)
costs = [20.0 if random.random() < 0.05 else 1.0 for _ in range(1_000_000)]
for M in (1_000, 10_000, 100_000):
    print(M, round(morsel_makespan(costs, M, P=16, d=50.0), 1))
```

Finer morsels track the ideal $T_1/P$ floor more closely under skew, at the price of dispatch volume — exactly the $M$-trade-off of Theorem 1.

### 4.3 SIMD-Accelerated Hash Joins

The hash join remains the most expensive operator in analytical plans, and its probe phase is a natural SIMD target: probing is a data-parallel loop over independent keys. Polychroniou et al. showed that *vertical* vectorization — processing $W$ keys per instruction across SIMD lanes with branch-free, masked control flow — decisively beats scalar probing on modern x86, because it keeps every lane productive and avoids the branch mispredictions that plague key-dependent control flow [4]. Their methodology generalizes across selection, aggregation, and partitioning, forming the kernel-level foundation that vectorized engines compile down to [10].

Two optimizations complete the picture. *Group prefetching* hides open-addressing probe latency by overlapping hash computation with outstanding misses; *radix partitioning* [5] splits inputs into cache-resident partitions, converting random DRAM accesses into sequential scans plus cache-local probes. The probe cost model becomes:

$$T_{\text{probe}} = \frac{N_{\text{probe}}}{W} \cdot c_{\text{vec}} + N_{\text{probe}} \cdot (1 - h) \cdot c_{\text{miss}}$$

where $h$ is the effective cache hit rate of the partitioned working set. SIMD attacks the first term (dividing per-key instruction cost by $W$); partitioning attacks the second (driving $h \to 1$ for the hot buckets).

> **Theorem 2 (Vectorized probe complexity).** *For a hash table with load factor $\alpha < 1$ under uniform hashing and linear probing, the expected SIMD-lane-serialized probe cost per key is $\Theta(1/(1-\alpha))$ gather operations amortized over $W$ lanes, versus $\Theta(1/(1-\alpha))$ scalar memory accesses. The vectorized variant additionally eliminates $\Theta(1)$ branch mispredictions per probe.*

*Proof sketch.* Linear probing examines $1/(1-\alpha)$ slots in expectation. A scalar probe issues one dependent load per slot plus a data-dependent branch. A vertical-vectorized probe issues one gather per slot across $W$ independent keys — the gathers are independent across lanes, so memory-level parallelism hides latency — and replaces branches with masked lane deactivation. The per-key instruction count is identical in expectation, but lane amortization divides it by $W$ and masking removes the misprediction penalty. ∎

DataFusion's hash join exploits both axes: partitioned builds keep per-partition tables small, and probe kernels operate on whole `RecordBatch` columns, letting the compiler auto-vectorize inner loops while selection vectors skip non-matching rows without materialization.

### 4.4 Dictionary Encoding and Late Materialization

Analytical data is rich in low-cardinality strings, and variable-length comparison is among the most expensive operations an engine performs. *Dictionary encoding* replaces each distinct string with a dense integer code — Arrow's `DictionaryArray` layout of `keys: Int32` plus a small dictionary — so predicates, grouping, and join keys operate on 4-byte integers, shrinking the working set dramatically.

The deeper win is *late materialization*: decoding is deferred to the latest possible moment — ideally never, if the query only filters, groups, or joins on the encoded column. A `GROUP BY country` becomes a group-by on `Int32` codes, with only the final projection touching the dictionary. This composes with vectorization (integer loops vectorize trivially) and morsel parallelism (smaller byte-footprint morsels improve cache residency).

For a string column with $D$ distinct values of average length $L$ bytes over $N$ rows:

| Representation | Bytes scanned | Comparison cost |
|---|---|---|
| Raw UTF-8 | $N \cdot L$ | $O(L)$ byte compares, data-dependent branches |
| Dictionary-encoded | $4N + D \cdot L$ | $O(1)$ integer compares, vectorizable |

Whenever $D \cdot L \ll N \cdot L$ — the defining property of low-cardinality columns — encoding wins on both axes, with build cost amortized after a single scan. This is why Parquet and Arrow standardize dictionary-encoded strings and DataFusion preserves the encoding through its optimizer where semantics permit.

### 4.5 Adaptive Reoptimization and Runtime Statistics

Static optimization rests on cardinality estimates, whose errors compound exponentially through joins — a plan optimal under estimates can be catastrophic under true sizes. Adaptive execution *defers decisions until runtime statistics exist*. Spark's AQE is the canonical realization: after each shuffle stage, exact partition sizes drive re-optimization — coalescing small partitions, converting sort-merge joins to broadcast hash joins when the build side proves small, and splitting skewed partitions [7].

Ballista's stage-based scheduler [2] creates the same natural reoptimization boundaries: materialized stage outputs yield exact statistics before downstream planning. Recent work extends adaptivity: Lyu et al. formulate per-reoptimization-point tuning as multi-objective (latency vs. cost) optimization solved in under a second [8], and AQORA adds a learning loop predicting join-type decisions from runtime features, improving across executions [9].

Adaptivity can itself be modeled functionally. The following Haskell sketch captures the essence — a plan rewritten by a rule set that consumes *observed* rather than *estimated* statistics:

```haskell
-- | A physical plan node annotated with statistics.
-- 'Estimated' comes from the catalog; 'Observed' from a completed stage.
data Stats = Estimated Double | Observed Double deriving (Show, Eq)

data Plan = Scan Stats String
         | HashJoin Stats JoinType Plan Plan
         | SortMergeJoin Stats Plan Plan
         deriving (Show)

-- | Adaptive rewrite: with observed sizes, pick the cheapest join.
-- Mirrors AQE's SMJ -> BHJ/SHJ conversion rule [7].
adapt :: Plan -> Plan
adapt (SortMergeJoin (Observed n) l r)
  | n < broadcastThreshold = HashJoin (Observed n) Broadcast (adapt l) (adapt r)
  | otherwise              = HashJoin (Observed n) Shuffled  (adapt l) (adapt r)
adapt (HashJoin s t l r) = HashJoin s t (adapt l) (adapt r)
adapt p@(Scan _ _)      = p

broadcastThreshold :: Double
broadcastThreshold = 10 * 1024 * 1024  -- 10 MB, cf. Spark's default
```

The rule is sound only because `Observed` statistics are exact. The price is the *materialization barrier*: stages must complete before reoptimization, serializing the plan at shuffle boundaries. Good adaptive design places boundaries where information gained outweighs lost pipelining.

## 5 Empirical Results and Formal Proofs

We consolidate the analytical predictions into testable claims with modeled projections for a 64-core AVX-512 machine on TPC-H SF100 — derived from the cost models, not measured on hardware, each paired with a confirming microbenchmark design.

> **Theorem 3 (Vectorization amortization limit).** *For a pipeline with per-batch dispatch cost $c_{\text{dispatch}}$ and per-row data cost $c_{\text{row}}$, vectorization achieves per-row cost $c_{\text{row}} + c_{\text{dispatch}}/B$. No choice of $B$ reduces per-row cost below $c_{\text{row}} + L(B)/B$, where $L(B)$ is the cache-miss penalty incurred when the batch working set $B \cdot w$ exceeds the fastest cache it targets.*

*Proof.* Dividing batch cost by $B$ gives the first claim. For the second, when $B \cdot w > C_1$, rows spill to slower levels and the amortized miss penalty $L(B)/B$ grows; the optimal $B$ balances dispatch amortization against cache residency. ∎

**Modeled projections (TPC-H SF100, 64 cores, AVX-512):**

| Technique | Baseline | With technique | Projected speedup | Dominant effect |
|---|---|---|---|---|
| Vectorized filter/project (B=8192) | tuple-at-a-time | batch loops | 4–8× | dispatch amortization |
| Morsel scheduling (M=32K) | static partitioning | dynamic dispatch | 1.5–2.5× under skew | tail-latency reduction |
| SIMD vertical probe (W=8) | scalar probe | lane-vectorized probe | 2–4× | instruction throughput |
| Radix partitioning | monolithic build | cache-resident partitions | 1.5–3× | LLC miss reduction |
| Dictionary-encoded GROUP BY | raw UTF-8 keys | Int32 code grouping | 3–6× | memory traffic + vectorizability |
| Adaptive join selection (AQE-style) | static SMJ plan | runtime BHJ/SHJ switch | 1.5–10× (skew-dependent) | cardinality-error correction |

Ranges reflect data dependence: vectorization's gain is nearly data-independent, while adaptivity's is unbounded in pathological misestimate cases [7].

Crucially, the techniques are *multiplicative*: each attacks an independent cost term — dispatch amortization, makespan tail, per-key instruction count, bytes per row, plan structure. Summing effects in log-space predicts end-to-end gain as the product of individual gains, consistent with published engine results.

## 6 Limitations and Future Work

Boundaries matter. *Vectorization has a floor*: for highly selective filters the compaction cost can exceed savings, and for $N < B$ dispatch overhead goes unamortized — hence scalar fallbacks. *Morsel scheduling is not free*: atomic dispatch claims and per-morsel overhead (Theorem 1) bound useful granularity, and pipeline breakers still serialize at stage boundaries. *SIMD joins degrade under extreme skew*: probes colliding on hot buckets serialize gather lanes; skew-aware partitioning or hot-key replication is required. *Dictionary encoding assumes low cardinality*: for $D \approx N$ the dictionary is pure burden — engines fall back to raw encoding above a threshold. *Adaptivity costs materialization*: every reoptimization point is a pipeline breaker; the stage granularity of Ballista [2] and Spark [7] reflects this trade-off.

Future work spans four directions:

- *Learned adaptivity* [9]: replacing hand-tuned thresholds with workload-trained models.
- *GPU/SIMT offload*: changing the vectorization-vs-materialization calculus.
- *Tier-aware morsel scheduling*: extending NUMA-awareness to CXL disaggregated memory.
- *Multi-objective runtime tuning* [8]: negotiating latency, cost, and energy at every reoptimization point.

---

## 7 Conclusion

Vectorized execution is not one technique but a *stack* of co-designed mechanisms. This thesis analyzed five layers through DataFusion and Ballista: columnar pipelines amortizing interpretation overhead [1][2]; morsel-driven parallelism with provable makespan bounds [3]; SIMD hash joins combining vertical vectorization with cache-conscious partitioning [4][5]; dictionary encoding shrinking low-cardinality footprints via late materialization; and adaptive reoptimization replacing fragile estimates with exact runtime statistics [7][8][9].

The formal results give engineers quantitative tools for tuning batch sizes, morsel granularities, and adaptivity thresholds instead of folklore. Because each technique targets an independent cost term, their combination is multiplicative. The modern analytical engine is best understood as a single coherent machine converting declarative intent into cache-resident, lane-parallel, adaptively-planned computation — and DataFusion shows how to build, extend, and distribute it.
