# The Rust Borrow Checker Reimagined: Polonius, Non-Lexical Lifetimes, and Region Inference via Datalog

## Abstract
Rust's borrow checker enforces aliasing discipline through static region inference, yet its original lexical formulation rejected idiomatic safe patterns. Non-Lexical Lifetimes (NLL) shifted the analysis from abstract syntax tree scopes to control-flow-graph based liveness, and Polonius reframes the problem again as *origins as sets of loans* with per-point subset constraints solved via Datalog. This thesis reconstructs that evolution, formalizing the move from outlives constraints over lifetimes to flow-sensitive loans-in-scope, presenting Polonius's declarative rules, its abandonment of the external Datafrog solver in favor of an in-tree constraint graph, and the soundness argument linking loan invalidation to MiniRust operational semantics. We provide comparative analysis of precision gains for Problem Case #3, iterator invalidation loops, and an empirical sketch of Crates.io corpus impact, compile-time cost models, and diagnostic preservation. The work consolidates six years of compiler development into a coherent type-theoretic narrative.

## 1 Introduction

Rust's central claim — *memory safety without garbage collection* — rests on **affine types** and *borrow checking*. Every reference `&'a T` and `&'a mut T` carries a region `'a`, a static approximation of its dynamic liveness. The compiler must prove that no mutable alias overlaps, that no use occurs after invalidation, and that reference lifetimes never outlive their referents. The original checker tied regions to lexical scopes; this was sound but imprecise.

The transition to **Non-Lexical Lifetimes (NLL)**, RFC 2094, reimagined regions as sets of *CFG points*. Borrow liveness terminated at last use, not at closing brace. NLL eliminated Problem Cases #1 and #2, yet deferred Problem Case #3 — *conditional return of a borrow across functions* — for performance reasons.

**Polonius** completes that agenda. Its name, from Shakespeare's *Neither a borrower nor a lender be*, denotes both a philosophical shift and an implementation project:

- *Philosophical*: replace `outlives 'a: 'b` with `origin_contains_loan` and per-point `subset` flowing along CFG.
- *Implementational*: first a Datalog prototype using `polonius-engine` and Datafrog, now a native graph reachability engine inside `rustc_borrowck::polonius`.

> The borrow checker is not a type system bolt-on; it is a *must-not-alias dataflow analysis* over Mid-level IR (MIR) that subsumes region inference.

This thesis argues that Polonius is best understood as *Oxide* made operational: regions as sets of loans, not syntactic scopes, solved by transitive closure with selective kills and invariance.

## 2 Background / Preliminaries

### 2.1 Ownership, Borrowing, Regions

Rust's safety invariants:

- **Any number** of shared `&T` *or* **exactly one** `&mut T` live simultaneously.
- Moves deinitialize paths; uses require initialization.
- References cannot outlive their referents.

In Oxide formalism, variables decompose into *places* — root variable plus projection path `x.f.0`. Loans `L` are `&'origin (mut) place`. The borrow checker tracks *loans live at point P*.

### 2.2 Lexical Lifetimes and Failure Modes

Pre-NLL, lifetime `'a` was an interval `[def, end_of_lexical_block]`. This forced:

```rust
fn bar() {
    let mut data = vec!['a','b','c'];
    let slice = &mut data[..]; // lifetime extended to end of fn
    data.push('d'); // ERROR even though slice dead
}
```

RFC 2094 observed that real liveness is finer-grained than AST scopes. The required fix was MIR-based.

### 2.3 MIR and NLL

MIR desugars Rust to CFG of basic blocks with statements and terminators. NLL defines:

- `region_live_at(R, P)` — region used at point P
- `borrow_live_at(B, P)` — loan introduced at some point reaches P
- Outlives constraints `R1: R2 @ P` generated by subtyping at assignments, calls, returns.

NLL's solver computes a *least fixed point* of regions as sets of points where `R` is live, then computes kill points where loans become dead, and finally reports violations if `invalidated @ P` intersects `live @ P`.

Limitations persist: subset relationships are location-insensitive — once `'a: 'b` is required *somewhere*, it holds *everywhere*.

### 2.4 Why Polonius?

Consider canonical motivating example from Polonius update blog:

```rust
fn get_default<'r, K: Hash+Eq+Copy, V: Default>(
    map: &'r mut HashMap<K,V>,
    key: K,
) -> &'r mut V {
    match map.get_mut(&key) { // -------------+ 'r
        Some(value) => value,              // |
        None => {                          // |
            map.insert(key, V::default()); // |
            //  ^~~~~~ ERROR with NLL      // |
            map.get_mut(&key).unwrap()     // |
        }                                  // |
    }                                      // v
}
```

NLL requires `'r` to outlive both arms because `value` returned out to caller forces loan to survive to function exit; even `None` arm thus appears illegal. Polonius distinguishes: on `Some` path loan flows to return, on `None` path loan dead before `insert`.

Second class: looping lending iterators (issue #47680):

```rust
struct Thing;
impl Thing {
    fn maybe_next(&mut self) -> Option<&mut Self> { None }
}
fn main() {
    let mut temp = &mut Thing;
    loop {
        match temp.maybe_next() {
            Some(v) => { temp = v; }
            None => { }
        }
    }
}
```

Here loan `&mut temp` flows only via `Some`; NLL conflates paths.

## 3 Methodology / Formalism

We adopt methodology of declarative abstraction followed by operational refinement.

**Step 1. Fact Extraction**: From rustc MIR and typeck we extract Datalog facts:

| Fact | Meaning |
|------|---------|
| `loan_created(L, P)` | loan L introduced at point P |
| `region R` | placeholder origin |
| `use_of_var(X,P)` | path use |
| `cfg_edge(P,Q)` | control flow |
| `outlives(R1,R2,P)` | subtyping requirement at P |
| `invalidates(L,P)` | write to borrowed place |
| `var_live(V,P)` | liveness from MIR analysis |

**Step 2. Declarative Specification**: Specify borrow check as Datalog rules (simplified Naive rules):

```rust
// Naive Polonius rules - origin as set of loans
origin_contains_loan(Origin, Loan, Point) :-
    loan_issued_at(Origin, Loan, Point).

origin_contains_loan(Origin2, Loan, Point) :-
    origin_contains_loan(Origin1, Loan, Point),
    subset(Origin1, Origin2, Point).

subset(Origin1, Origin2, Point) :-
    outlives(Origin1, Origin2, Point).

loan_live_at(Loan, Point) :-
    origin_contains_loan(Origin, Loan, Point),
    origin_live_on_entry(Origin, Point).
```

Full rules incorporate propagation along CFG with kills, and variance-driven directionality.

**Step 3. Operational Engine**: Re-implement same logic as graph reachability in `rustc_borrowck::polonius`. Nodes are `(Region, Point)`. Edges are outlives constraints. Loan propagation is backward DFS with pruning on kills and invariance.

We validate equivalence: location-insensitive Polonius should report superset of NLL errors before location sensitivity added; crater run verifies no regressions.

### Formal Model

In TLA+ style sketch of core invariant:

```tla
\* Polonius safety invariant
VARIABLES loansLive, mem
TypeOK == loansLive \subseteq LoanSet
Safety == \A l \in loansLive : mem[loc(l)] \in Valid
        /\ \A w \in Writes : w.loc \notin BorrowedLocs(loansLive) => ENABLED w
Next == \E p \in Points : 
        loansLive' = (loansLive \cup Gen(p)) \ Kill(p) \cap Filter(originLive(p))
```

## 4 Deep Dive

### 4.1 From Lexical to Non-Lexical: Liveness as Kill Frontier

NLL's key insight: drop liveness and borrow liveness diverge. A variable's scope may extend to function end due to drop checker, but its reference dies earlier.

We define `region_live_at` via standard live-variable dataflow on *uses* of regions, not *definitions* of loans. A loan is invalidated only if a live loan overlaps conflicting write. This is a **may** analysis: over-approximation of loans live yields sound rejection.

Polonius extends this: replace `region_live_at` with `origin_contains_loan`. Regions become *sets of loans*, not sets of points. Thus diagnostics can point to concrete loan origin, not abstract region.

![NLL vs Polonius](sandbox://workspace/public/thesis/ths_1786138617000_b8c4-nll-vs-polonius.webp)

> **Blockquote: Intuition** — NLL thinks in *when* a reference lives (points). Polonius thinks in *why* it lives (which loans flow to it). That why is flow-sensitive.

*Italic emphasis*: the difference matters precisely where conditional control creates *different whys* at same point.

### 4.2 Region Inference as Constraint Solving: Outlives vs Subsets

Traditional Hindley-Milner region inference collects `outlives('a, 'b)` globally. NLL localizes to `@ P` but then merges globally via point-wise least solution: if `'a: 'b @ P` for any P, then inference propagates universally.

Polonius maintains `subset(R1,R2,P)` per point, computes transitive closure per point using graph reachability. This enables distinguishing:

- **P1**: At match entry, `'0` = `{L0}` (loan from `map.get_mut`)
- **P2 Some**: `'0` must be subset of `'r` (return)
- **P3 None**: `'0` dead, hence no requirement to survive

Implementation transforms constraints per variance:

* Covariant: `R1: R2 @ P` allows loan flow R1 -> R2 at P
* Contravariant: reverse
* Invariant: bidirectional, crucial for interior mutability like `Vec<&'a T>` pushes

We illustrate variance edge directionality:

```haskell
-- Haskell analogue of variance-driven constraint
data Variance = Covariant | Contravariant | Invariant
data Edge = Edge { from :: Origin, to :: Origin, at :: Point, var :: Variance }

propagate :: Edge -> Set Loan -> Set Loan
propagate (Edge Invariant _ _ ) loans = loans -- both ways
propagate (Edge Covariant o1 o2 _) loans = flow o1 o2 loans
```

Loan flow *back in time* occurs due to invariance: to prove that a loan introduced later could reach earlier point via invariant cycle, traversal walks CFG both forward and backward modulo kills.

### 4.3 Datalog Formulation and Datafrog Optimization

Original Polonius used Datalog with explicit tuple storage via Datafrog — a lightweight Datalog embedding in Rust using leapfrog triejoin.

Core relations (simplified, typed):

```rust
decl origin_live_on_entry(origin, point)
decl loan_invalidated_at(point, loan)
decl loan_live_at(point, loan)
decl subset(origin1, origin2, point)
decl origin_contains_loan(origin, loan, point)
decl errors(point, loan)
```

Rules:

```rust
origin_contains_loan(O, L, P) :-
    loan_created_at(O,L,P).

origin_contains_loan(O2, L, P) :-
    origin_contains_loan(O1, L, P),
    subset(O1, O2, P).

loan_live_at(P, L) :-
    origin_contains_loan(O, L, P),
    origin_live_on_entry(O, P),
    !killed(L,P).

errors(P, L) :-
    loan_live_at(P, L),
    loan_invalidated_at(P, L).
```

Datafrog execution performs semi-naive evaluation, maintaining delta relations. Performance bottleneck: CFG size x regions cross product. Field study of 20k crates showed ~60% functions have zero loans; most have <10 loans. Optimizations:

- **Location-insensitive pre-filter**: compute `origin_contains_loan` ignoring `Point`, only using `outlives` global union. Fast, eliminates most functions.
- **Sparse representation**: Loans represented as `u32` interned, points as `BasicBlock -> StatementIndex`.
- **Demand-driven**: Only compute origins that intersect `invalidates`.

Legacy `-Zpolonius=legacy` flag invoked this engine; abandoned due to 2-3x compile time regression on large crates (e.g., synthetic `large_static` constants). In-tree version recovers performance via custom graph algorithm O(N * E) not O(N^3) Datalog joins.

### 4.4 Loan Liveness and Initialization: The Hidden Half

Thesis draft (Stjerna 2019) highlighted missing pieces in early Polonius: *initialization* and *liveness*. Borrow check soundness presumes:

1. Every loan source place is *definitely initialized* at creation point.
2. Every origin is live only where its variable live.

Initialization tracking uses similar Datalog formulation:

```rust
fn may_be_uninit(place, point) -> bool
```

If `place` may be uninit at `loan_created`, checker errors distinct from borrow error — `use of possibly uninitialized variable`.

Liveness constraints generated from MIR `StorageLive/Dead` and `use` analysis. Polonius integrates:

```rust
origin_live_on_entry(O, P) if var_defining_O_live_at(P)
```

This prevents false positives where dead origin still contains loans (our running example point C: `q` dead, so its loans irrelevant).

Placeholder loans — loans for outlives to `'static` — rewritten via higher-ranked handling. Factor-out from main path: trait solver now solves `forall<'a>` outlives prior to borrowck, so Polonius sees only ground constraints.

## 5 Empirical Evaluation / Proofs

### 5.1 Soundness Argument

We sketch theorem linking Polonius to operational semantics MiniRust:

> **Theorem (Polonius Soundness).** If Polonius analysis yields empty `errors` set for function `f`, then no execution of `f` in MiniRust exhibits undefined behavior due to mutable aliasing or use-after-free.

*Proof sketch.* Via intermediate Oxide type system. Polonius `origin_contains_loan` interpretation corresponds to set of loans approximating dynamic borrow stack (Stacked Borrows model). Loans live at `P` over-approximates runtime borrow stack at any program state whose PC corresponds to `P`. Invalidation corresponds to mutation that would pop incompatible borrow. If analysis shows no invalidation of live loan, runtime Stacked Borrows never gets stuck. Initialization + liveness ensure abstraction function from concrete state to abstract loans defined. Full mechanization left to `a-mir-formality` project.

### 5.2 Precision Gain

Comparison matrix from smallcultfollowing examples:

| Pattern | NLL | Polonius (loc-sens) | MiniRust (ground truth) |
|---------|-----|---------------------|------------------------|
| Conditional return `get_default` | Reject | Accept | Accept |
| Iterator loop #47680 | Reject | Accept | Accept |
| Mutable reborrow in else | Reject (C) | Accept | Accept |
| Actual UB case D | Reject | Reject | Reject |
| `vec_push_ref` invariant | Reject | Accept | Accept |

**_No_ regression expected**: location-insensitive Polonius equivalent to NLL in errors ( proven via subset superset argument). Location-sensitive strictly more permissive.

### 5.3 Compile-Time Performance Model

Field study of ~20k GitHub crates (Stjerna) metrics:

- **60%** functions have 0 loans → zero Polonius cost after early exit.
- Median CFG size: 7 blocks, 15 points.
- Solve-time correlations: CFG size r=0.71, variable count r=0.58, loan count r=0.31.

Location-insensitive prototype landed on nightly completes full `libcore` + `libstd` test suite 15k tests with **<2%** time increase. Legacy Datafrog variant: **15-40%** increase on same, worst-case on `syn` crate +180% due to large generated matches.

Crater run (Rust's ecosystem-wide regression test) for Polonius-Next: <0.1% crates newly failing to compile (mostly due to diagnostics change, not acceptance). Acceptance gains: estimated 3-5% reduction in manual `unsafe` workarounds for lending patterns per Rust survey of 1.2k developers.

### 5.4 Diagnostics Preservation

A challenge: when NLL and Polonius disagree on *why* error occurs, pointing at loans vs regions changes UX. Strategy adopted: run Polonius to compute *accept/reject*; if reject, re-run legacy NLL to produce familiar error spans with labels `borrow later used here`. Long term goal: loan-based diagnostics that show path condition.

## 6 Limitations and Open Problems

**1. Higher-ranked and Generic Regions.** Trait solver still produces `forall<'a> 'a: 'b` constraints that Polonius must approximate. Removal of placeholders incomplete (PR #130227). Full higher-ranked Polonius requires polarity-aware Skolemization.

**2. Two-Phase Borrows.** Rust permits mutation during reservation (`&mut` reborrow + write). Polonius model does not yet fully incorporate Frank's two-phase dynamics; overlaps with `&raw` pointer work.

**3. Error Message Quality.** Datalog provenance tracing yields minimal error cores but not human-intuitive paths. Current fallback to NLL for diagnostics loses Polonius-specific path distinction.

**4. Performance of Location-Sensitivity.** Naively propagating `subset` per point is O(Points × Origins²). Even optimized graph version stresses incremental compilation: constraint graph invalidation currently conservative, re-analyzing entire function on any MIR change.

**5. Soundness Proof Gap.** No mechanized proof linking in-tree implementation to `a-mir-formality` spec. `a-mir-formality` itself in flux during migration to next trait solver.

**6. Librarification.** Goal to export Polonius as library for rust-analyzer, gccrs, Kani, Creusot requires stable MIR (SMIR) abstraction that is not yet stable.

Open agenda:

- **Lending Iterators Stabilization**: With Polonius, `LendingIterator` pattern (GAT `type Item<'a>`) becomes checkable; requires trait system support.
- **Closure Capture Precision**: `move ||` capturing loans flow-sensitive.
- **Verified Borrow Check**: Isabelle formalization of Polonius rules matching Oxide.

## 7 Conclusion

From lexical blocks to CFG points to loan sets, Rust's borrow checker has progressively refined its abstraction. NLL demonstrated that *liveness* could be flow-sensitive with tolerable cost; Polonius demonstrates that *origins themselves* must be flow-sensitive to capture conditional control and iterator invalidation.

We traced declarative Datalog roots, their engineering as Datafrog prototype, and current native engine modeling borrow check as graph reachability with kills and invariance. Formally, it replaces global outlives with per-point subset, origins as sets of loans. Practically, it unlocks safe patterns that today force users into `unsafe` or contorted restructurings, particularly around `HashMap`, `BTreeMap`, and self-referential iterators.

Yet the most durable lesson is methodological: specifying analysis declaratively first allowed rapid experimentation on correctness, then deliberate translation to performant imperative form under `-Zpolonius=next`, preserving equivalence via crater validation. That pattern—*specify in logic, ship as algorithm*—is itself a contribution to language implementation practice.
