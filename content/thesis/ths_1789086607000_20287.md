# GPU Microarchitecture: SIMT Execution, Memory Coalescing, and the Roofline Model

## Abstract

The modern graphics processing unit derives its staggering throughput not from single-thread speed but from an execution model that marries thousands of hardware-resident threads to explicitly managed memory hierarchies. This thesis develops a unified treatment of three pillars of GPU performance engineering: the Single-Instruction, Multiple-Thread (SIMT) execution model with its warp scheduler and divergence mechanics; the memory subsystem's coalescing rules, shared-memory bank organization, and occupancy-driven latency hiding; and the roofline performance model that binds arithmetic intensity to attainable throughput. We trace the evolution from pre-Volta lockstep warps with a single shared program counter to Volta's independent thread scheduling, quantify how memory access patterns collapse or multiply DRAM transactions, and show how the roofline's two ceilings — bandwidth-bound slope and compute-bound flat top — predict kernel performance and expose optimization headroom. Analytical derivations are grounded in published microbenchmarking studies and vendor architecture whitepapers, culminating in worked roofline analyses of memory-bound SAXPY and compute-bound dense matrix multiplication.

## 1. Introduction

The GPU occupies a singular position in the computing landscape: a device whose peak floating-point throughput exceeds that of contemporary multicore CPUs by one to two orders of magnitude, yet which demands an entirely different performance discipline from the programmer [1]. Where CPU performance engineering leans on out-of-order execution, branch prediction, and deep cache hierarchies, GPU performance engineering is fundamentally an exercise in *orchestrating parallelism* — keeping tens of thousands of threads in flight, ensuring their memory accesses combine into efficient transactions, and matching the kernel's arithmetic intensity to the hardware's balance point [2].

Three ideas form the analytical core of this thesis. First, **SIMT execution**: threads are grouped into warps of 32 that share instruction issue, and divergence within a warp serializes execution, converting a logical parallel operation into sequential replay. Second, **memory coalescing and bank structure**: global memory transactions are issued per warp in fixed-size segments, so that the mapping from per-thread addresses to transaction count determines effective bandwidth, while shared memory is partitioned into banks whose conflicts serialize accesses. Third, the **roofline model**: the achievable performance of any kernel is bounded above by the minimum of peak compute and bandwidth times arithmetic intensity, yielding a visual diagnostic that classifies kernels as memory-bound or compute-bound and quantifies the remaining optimization headroom [2].

> **Thesis:** Attainable GPU kernel performance is jointly determined by warp-level execution efficiency (divergence, scheduling), memory-transaction efficiency (coalescing, bank conflicts, occupancy), and the arithmetic-intensity ceiling of the roofline model; no kernel can be optimized without measuring and addressing all three.

The remainder of this work proceeds as follows. Section 2 reviews the streaming multiprocessor, memory hierarchy, and tensor-core datapath. Section 3 describes a measurement methodology combining controlled microbenchmarks with roofline construction. Section 4 provides a deep dive into the three pillars. Section 5 presents empirical results and formal derivations. Section 6 discusses limitations, and Section 7 concludes.

## 2. Background

### 2.1 The Streaming Multiprocessor and the SIMT Model

A CUDA-capable GPU is organized as a scalable array of streaming multiprocessors (SMs). When a kernel grid launches, thread blocks are distributed across SMs with available capacity; all threads of a block execute on a single SM, and multiple blocks may share an SM concurrently [1]. Each SM manages hundreds of resident threads through the SIMT (Single-Instruction, Multiple-Thread) architecture: threads are grouped into *warps* of 32 consecutive thread IDs, and a warp executes one common instruction at a time. Full efficiency is realized only when all 32 threads agree on their execution path; when threads diverge through a data-dependent conditional branch, the warp serially executes each taken path with inactive threads masked off, reconverging afterward [1].

SIMT resembles SIMD vector organizations in that one instruction controls many processing elements, but it differs in the programming contract: SIMD widths are exposed to software, whereas SIMT specifies the branching behavior of a single scalar thread. Early microbenchmarking studies confirmed and extended the documented behavior, measuring undocumented characteristics of the processing elements, TLB hierarchies, and barrier mechanisms on the GT200 generation [4].

### 2.2 The Memory Hierarchy

The GPU memory hierarchy is explicitly tiered and programmer-visible:

- **Global memory (DRAM):** large capacity (tens of GB), high aggregate bandwidth (hundreds of GB/s to TB/s on HBM devices), but latency of several hundred cycles.
- **L2 cache:** shared across SMs, typically several MB (e.g., 6 MB on GA102), caching global traffic [6].
- **L1 data cache / shared memory:** per-SM unified partition (e.g., up to 128 KB configurable on Ampere), with shared memory explicitly managed by the programmer and L1 caching read traffic [3][6].
- **Registers:** per-thread register file, the fastest storage; register pressure limits occupancy.

Because arithmetic units are cheap relative to DRAM, the central performance problem is *feeding* the units: overlapping memory latency with computation via massive multithreading (occupancy), and minimizing the number of DRAM transactions per useful byte via coalescing [3].

### 2.3 Tensor Cores and Specialized Datapaths

Since Volta, SMs include tensor cores — matrix-multiply-accumulate units that execute small dense matrix operations (e.g., 16×16×16 FP16 multiply-accumulate) per instruction. Ampere's third-generation tensor cores add BF16, TF32, FP64, INT8/INT4, and fine-grained 2:4 structured sparsity, doubling effective throughput by skipping zeros [6]. These units create a *second, higher compute ceiling*: kernels recast as dense matrix multiplication access an order-of-magnitude higher peak than the FP32 datapath.

### 2.4 The Roofline Model

Williams, Waterman, and Patterson introduced the roofline model as a visual performance bound for multicore architectures [2]. For a kernel with arithmetic intensity $I$ (FLOP per byte of memory traffic), peak compute $\pi$ (FLOP/s), and peak bandwidth $\beta$ (B/s), attainable performance $P$ satisfies

$$P(I) \le \min(\pi,\ \beta \cdot I).$$

Plotted on log-log axes, this yields a "roof": a bandwidth-bound slope rising with $I$ until the *ridge point* $I^* = \pi/\beta$, beyond which performance is compute-bound and flat. Kernels left of the ridge point are memory-bound; kernels right of it are compute-bound [2].

## 3. Methodology

Our analysis combines three methodological strands.

**Analytical modeling.** We derive attainable-performance bounds from first principles: divergence efficiency as a function of active-thread fraction, transaction counts from address-mapping analysis, occupancy from the register/shared-memory/thread-block constraints published by NVIDIA [1][3], and roofline ceilings from device specifications [6]. Each derivation states its assumptions explicitly (Section 6).

**Microbenchmark-based measurement.** Following Wong et al., who exposed undocumented GT200 characteristics such as branch-divergence sequences and barrier behavior [4], and Jia et al., who systematically dissected Volta's instruction latencies, cache geometries, and warp-scheduling behavior [5], we advocate microbenchmarks that isolate each effect: pointer-chase for latency, strided versus contiguous copies for coalescing efficiency, and active-mask sweeps for divergence cost. These techniques remain the empirical backbone of GPU performance analysis because vendors document performance rules rather than the microarchitectural mechanisms behind them [4].

**Roofline construction.** We construct rooflines from measured stream bandwidth $\beta$ and vendor peak $\pi$ (with separate FP32 and tensor-core ceilings), then place representative kernels — SAXPY, tiled dense matrix multiplication, and a reduction — by their arithmetic intensities. Kernel intensity is computed analytically from the algorithm's FLOP and byte counts, counting only compulsory traffic under an ideal-cache assumption, and then corrected for measured cache effects [2].

## 4. Deep Dive

### 4.1 SIMT Execution, Warp Scheduling, and Divergence

The warp is the fundamental scheduling unit of the GPU. On pre-Volta architectures, all 32 threads of a warp shared a single program counter and an active mask; divergent branches were handled by pushing the taken path and its mask onto a reconvergence stack, executing each path serially [1]. This design had a subtle consequence: threads of a warp in divergent regions could not exchange data or signal each other through locks, and certain producer-consumer patterns could deadlock depending on which warp the contending threads belonged to — a behavior Wong et al. characterized empirically [4].

Volta introduced **independent thread scheduling**: each thread maintains its own program counter and call stack, with the scheduler tracking per-thread state. This preserves SIMT throughput while permitting forward progress guarantees the old model could not provide, such as spin-waiting on a flag set by another thread in the same warp [1][5]. Volta's microbenchmarking study confirmed per-thread PCs and measured the resulting changes in synchronization granularity and shuffle-instruction semantics [5].

Divergence efficiency can be quantified. If a warp executes $k$ distinct branch paths with active fractions $f_1, \dots, f_k$ of the warp's threads, the warp issues the full instruction stream of every taken path, so the *divergence efficiency* is

$$\eta_{\text{div}} = \frac{\sum_j f_j \cdot W_j}{\sum_j W_j},$$

where $W_j$ is the dynamic instruction count on path $j$. In the worst case — each thread taking a distinct path of equal length — $\eta_{\text{div}} = 1/32$: a **32× slowdown**. Best-practice guidance therefore treats warp-uniform branching as high priority, recommending that divergent work be restructured or segregated into separate kernels [3].

Warp scheduling itself is a second axis. Each SM hosts multiple warp schedulers that select among eligible warps each cycle, hiding latency through zero-overhead context switching. The scheduler can only pick warps whose next instruction's operands are ready; long-latency operations (global loads, ~400–800 cycles) therefore require enough *other* eligible warps to fill the gap. This is the mechanism behind occupancy: the ratio of resident warps to the architectural maximum determines the scheduler's freedom to hide latency [1][3].

```cuda
// Branch on a warp-uniform predicate: no divergence
if (blockIdx.x < numTiles) {
    processTile(blockIdx.x);
}
// Branch on a per-thread predicate: warp diverges, both paths serialized
if (laneValue > threshold) {
    expensivePathA();
} else {
    expensivePathB();
}
```

### 4.2 Memory Coalescing and Shared-Memory Bank Conflicts

Global memory accesses by the threads of a warp are *coalesced* by the hardware into as few transactions as possible. On compute capability 6.0 and later, the number of transactions equals the number of 32-byte aligned segments touched by the warp's addresses [3]. Consequences are immediate and quantitative:

- **Fully coalesced 4-byte access:** 32 threads touch 128 contiguous bytes → 4 segments → 4 transactions of 32 bytes; 100% of transferred bytes are useful.
- **Strided access with stride $s$ words:** the warp touches 32 addresses spread over $32 \cdot s$ words; transaction count grows linearly with $s$ until every access needs its own segment, at which point useful-bytes-per-transaction collapses to 4/32 = 12.5% and effective bandwidth falls by up to 8× [3].

> **Theorem (Coalescing bound):** For a warp issuing one load instruction with per-thread byte addresses $a_t$, let $S$ be the set of 32-byte aligned segments intersecting $\{a_t\}$. The access completes in at least $|S|$ DRAM transactions. The *coalescing efficiency* $\eta_c = (\text{useful bytes})/(32 \cdot |S|)$ upper-bounds the fraction of peak bandwidth the access pattern can achieve.

Shared memory, the programmer-managed on-chip scratchpad, is organized into **32 banks** (4-byte-wide on most architectures), with successive 4-byte words mapped to successive banks. When two threads of a warp access different addresses in the same bank, a *bank conflict* serializes the accesses into multiple waves; an $n$-way conflict costs $n$ times the single-access latency. The classic remedy is *padding*: adding one column of padding to a 2D tile changes the access stride from 32 to 33 words, mapping each thread's element to a distinct bank [3].

### 4.3 Occupancy and Latency Hiding

*Occupancy* — resident warps per SM divided by the architectural maximum — is the GPU's primary latency-hiding dial. It is constrained by three per-block resources: threads, registers, and shared memory. If a kernel uses $R$ registers per thread and $B$ threads per block, an SM with 65,536 registers can host at most $\lfloor 65536 / (R \cdot B) \rford$ blocks by the register constraint alone; the binding constraint among the three determines occupancy [3].

Higher occupancy is not unconditionally better. The CUDA Best Practices Guide emphasizes that *increasing per-thread work (instruction-level parallelism) can compensate for lower occupancy*: a kernel doing substantial independent arithmetic per thread needs fewer warps to hide latency [3]. This is the insight behind persistent-kernel and grid-stride-loop designs, and it explains why many tuned kernels peak well below 100% occupancy.

Little's-law reasoning makes the requirement precise: to sustain bandwidth $\beta$ with per-transaction latency $L$ and transaction size $T$, the SM needs $\beta \cdot L / T$ transactions in flight. With too few resident warps, the schedulers drain their eligible pool during a memory stall and the DRAM interface idles — the kernel becomes *latency-bound* rather than bandwidth-bound, falling below even the roofline's slope [2][3].

### 4.4 Tensor Cores and the Two-Ceiling Roofline

Tensor cores reshape the roofline by raising the compute ceiling selectively. A kernel expressible as dense matrix multiplication can target the tensor datapath, whose peak (e.g., 142 FP16 TFLOP/s dense, 284 sparse on GA102) dwarfs the FP32 ceiling [6]. The ridge point moves right, meaning many kernels that were comfortably compute-bound on the FP32 ceiling become memory-bound against the tensor ceiling.

This has a sharp practical consequence: **tensor-core kernels are almost always memory-bound**, and their optimization reduces to maximizing arithmetic intensity — kernel fusion, larger tiles, epilogue fusion to keep operands on chip. Conversely, a kernel that cannot use tensor cores is capped by the lower FP32 ceiling regardless of its intensity. The honest roofline for a modern GPU therefore has *two flat tops* (FP32 and tensor) sharing one bandwidth slope [2][6].

> **Definition (Effective ridge point):** For a kernel able to utilize datapath $d$ with peak $\pi_d$, the effective ridge point is $I^*_d = \pi_d / \beta$. The kernel is memory-bound iff its operational intensity $I < \min_d I^*_d$ over reachable datapaths $d$.

## 5. Empirical Results and Proofs

### 5.1 Roofline Placement of Canonical Kernels

We now place three canonical kernels on the GA102 roofline ($\beta = 936$ GB/s, $\pi_{\text{FP32}} = 35.6$ TFLOP/s, $\pi_{\text{tensor}} = 142$ TFLOP/s dense FP16).

| Kernel | FLOPs | Bytes (compulsory) | Intensity $I$ (FLOP/B) | Regime (FP32) | Roofline bound |
|---|---|---|---|---|---|
| SAXPY $y = ax + y$ (FP32) | $2N$ | $12N$ | $1/6 \approx 0.167$ | Memory-bound | $936 \times 0.167 \approx 156$ GFLOP/s |
| Dot product reduction (FP32) | $2N$ | $8N$ | $0.25$ | Memory-bound | $\approx 234$ GFLOP/s |
| Dense GEMM, $n \times n$ (FP32) | $2n^3$ | $12n^2$ (tiled, ideal) | $n/6$ | Compute-bound for $n > 228$ | $35.6$ TFLOP/s |
| Dense GEMM (FP16 tensor) | $2n^3$ | $8n^2$ | $n/4$ | Compute-bound for $n > 606$ | $142$ TFLOP/s |

The table makes the roofline's diagnostic power concrete: SAXPY can never exceed ~156 GFLOP/s on this device — 0.4% of FP32 peak — no matter how cleverly it is scheduled, because its intensity sits far left of the ridge point $I^* \approx 38$ FLOP/B. Optimization effort on SAXPY should target *bandwidth utilization* (coalescing, vectorized 128-bit loads), never instruction throughput [2][3]. GEMM, by contrast, crosses into the compute-bound region and justifies tensor-core targeting and deep software pipelining.

### 5.2 Proof Sketch: The Attainable-Performance Bound

We sketch why $P \le \min(\pi, \beta I)$ is tight as an upper bound and what closes the gap.

> **Theorem (Roofline bound):** Let a kernel perform $W$ FLOPs and transfer $Q$ bytes between processor and DRAM. Then its execution time $T$ satisfies $T \ge \max(W/\pi,\ Q/\beta)$, i.e., $P = W/T \le \min(\pi,\ \beta \cdot W/Q)$.

*Proof sketch.* The kernel cannot complete faster than the time to execute its FLOPs on a $\pi$-FLOP/s datapath, giving $T \ge W/\pi$. Nor can it complete faster than the time to move $Q$ bytes through a $\beta$-B/s interface, giving $T \ge Q/\beta$. Both must hold simultaneously, so $T \ge \max(W/\pi, Q/\beta)$, and dividing $W$ by this lower bound on $T$ yields the stated inequality. ∎

The bound is approachable but rarely tight: divergence multiplies dynamic instructions without raising $W$ (lowering effective $\pi$), uncoalesced accesses inflate $Q$ beyond compulsory traffic (lowering effective $\beta$), bank conflicts add shared-memory stall cycles, and insufficient occupancy leaves both resources idle [1][3]. Microbenchmarking studies quantify each gap: Jia et al. measured Volta's instruction latencies and cache bandwidths [5], while Wong et al. showed how undocumented scheduling behavior creates performance cliffs invisible to the model [4].

### 5.3 Divergence and Coalescing: Measured Costs

Controlled experiments reported in the literature align with the analytical model of Sections 4.1–4.2. A predicated branch with $k$ taken paths of equal cost runs approximately $k$ times slower than the uniform case — the serialization predicted by the active-mask mechanism [1][4]. For memory, a unit-stride FP32 copy kernel sustains near-peak bandwidth, while a stride-32 variant issues 32× the transactions and collapses to roughly one-eighth of peak, matching the segment analysis; the Best Practices Guide documents this 32-byte transaction granularity as the governing rule on modern architectures [3].

Shared-memory bank conflicts exhibit the predicted step function: a 32×32 FP32 tile transposed without padding incurs a 32-way conflict on the column read, while the padded tile (one extra column) eliminates conflicts entirely, recovering full shared-memory bandwidth — a textbook instance of address-mapping analysis guiding a one-line fix [3].

## 6. Limitations

The analysis carries several limitations that the honest performance engineer must keep in view.

1. **Ideal-cache intensity.** Operational intensity is computed from compulsory traffic; real caches (with finite capacity, line size, and associativity) admit capacity and conflict misses that inflate $Q$. Cache-aware roofline extensions exist but require per-kernel miss modeling [2].
2. **Static ceilings.** Peak $\pi$ and $\beta$ are steady-state maxima; thermal throttling, clock boosting, and power caps (e.g., TGP limits on GA102 [6]) modulate them dynamically. A kernel measured at 90% of roofline on a cool GPU may exceed it nominally under boost — or fall short under throttling.
3. **Vendor opacity.** Key scheduling parameters — warp scheduler arbitration policy, exact DRAM controller behavior, tensor-core pipeline depth — remain undocumented and are known only through microbenchmarking [4][5]. Models built on them can silently break across driver or architecture revisions.
4. **Single-kernel scope.** The roofline bounds one kernel's steady state; it says nothing about launch overhead, inter-kernel dependencies, multi-GPU communication, or the host-device transfer bottleneck that dominates many real pipelines.
5. **Divergence model granularity.** The active-mask cost model assumes reconvergence at the immediate post-dominator; unstructured control flow and Volta's independent scheduling admit interleavings whose cost the simple $k$-path model underestimates [1][5].
6. **Tensor-core reachability.** The two-ceiling roofline assumes the kernel's arithmetic maps cleanly onto matrix-multiply-accumulate shapes; padding, masking, and layout-transform overheads for "almost-GEMM" kernels erode the effective tensor ceiling substantially [6].

## 7. Conclusion

GPU performance rests on three interlocking foundations. SIMT execution delivers throughput through warp-wide instruction issue but punishes intra-warp divergence with serialized replay — a cost that independent thread scheduling (Volta and later) made more flexible but did not eliminate [1][5]. The memory subsystem converts per-thread addresses into a countable number of fixed-size transactions, so coalescing discipline and bank-conflict avoidance directly determine the fraction of peak bandwidth a kernel can harvest [3]. And the roofline model binds these microarchitectural facts to a single diagnostic: plot the kernel's arithmetic intensity, read off which ceiling binds, and spend optimization effort only where the bound permits improvement [2].

The practical workflow is therefore: compute the kernel's intensity and place it on the device roofline; if memory-bound, audit coalescing, bank conflicts, and occupancy; if compute-bound, audit divergence, instruction mix, and datapath selection (FP32 versus tensor cores); when the kernel sits at the roofline, only algorithmic changes to intensity — fusion, tiling, precision, sparsity — move the bound [2][3][6]. Microbenchmarking remains the indispensable empirical complement, exposing the undocumented behaviors that separate the model from the machine [4][5].
