# Hybrid Logical Clocks and TrueTime: Physical–Logical Time Fusion for Externally Consistent Distributed Transactions

## Abstract

Globally distributed transaction processing demands an ordering of events faithful to physical reality yet immune to its imperfections. Physical clocks drift; logical clocks float free of wall-clock meaning; each deficiency breaks external consistency — the guarantee that if T1 commits before T2 begins, T1 serializes first. This thesis develops a unified treatment of two responses: Hybrid Logical Clocks (HLCs), which fuse physical and logical time into an O(1)-sized timestamp preserving the Lamport clock condition while staying boundedly close to physical time, and Google TrueTime, which exposes clock uncertainty as an explicit [earliest, latest] interval and purchases external consistency via commit wait. We formalize the HLC (l, c) update rules, prove one-way causality and the skew bound, derive the commit-wait rule TT.after(s) from the TrueTime bracketing theorem, and trace Spanner's two-phase-locked write pipeline. Empirical evidence from Spanner, CockroachDB closed timestamps, TiKV resolved timestamps, and Calvin deterministic scheduling quantifies each fusion's cost, and we close with the limits of time fusion and uncertainty-aware scheduling as future work.

## 1 Introduction

Distributed databases that span continents must answer a question that is deceptively simple: *in what order did things happen?* The answer determines which write wins a conflict, which snapshot a reader observes, and whether a causal chain of transactions — write, read, respond, write again — remains coherent when its links land in datacenters thousands of kilometers apart. The strongest classical answer is **external consistency** [2]: if transaction T1 commits before transaction T2 begins (in real time), then the serialization order must place T1 before T2. External consistency implies linearizability for single-key operations [8], and Spanner demonstrated it is achievable at planetary scale.

Physical clocks drift — NTP holds only tens of milliseconds over the public Internet [1] — so ordering by physical timestamps is undefined when uncertainty intervals overlap. **Logical clocks** [8] guarantee the clock condition — if e happens-before f, then C(e) < C(f) — but are divorced from physical time entirely, making debugging, auditing, and cross-system correlation impossible, and providing no basis for *external* consistency, which is defined over real time rather than causality.

This thesis analyzes two engineering fusions that take the problem from opposite directions. **Hybrid Logical Clocks (HLCs)** [1] start from physical time and repair it with a logical counter, producing a constant-sized timestamp that *never diverges from physical time by more than a bounded skew* while still capturing causality. **TrueTime** [2] starts from physical time as well but attacks the uncertainty itself: GPS and atomic-clock hardware tighten the error bound ε, and the API exposes the residual uncertainty as an explicit interval [earliest, latest], so the database can *wait out* uncertainty (commit wait) rather than risk violating external consistency.

§2 reviews foundations; §3 states the formal model; §4 presents HLC update rules and the one-way causality theorem, TrueTime's interval API and commit wait, Spanner's transaction pipeline, and two counterpoints (closed timestamps, Calvin deterministic scheduling); §5 states the theorems and surveys evidence; §6 catalogues limits; §7 concludes.

## 2 Background

The intellectual lineage begins with Lamport [8]. His *happens-before* relation (→) is defined by three rules: (i) events on one process are ordered; (ii) send(m) → receive(m); (iii) transitivity. A logical clock C satisfies the *clock condition*: e → f ⇒ C(e) < C(f). Lamport's algorithm is almost trivial — each process keeps a counter, timestamps events, and on receive advances to max(local, message) + 1 — but it guarantees only *potential* causality detection: C(e) < C(f) does not imply e → f. **Vector clocks** strengthen this to exact causality detection at O(n) cost per timestamp, a price that does not scale to thousand-node clusters.

The Spanner project [2] asked whether physical time could be made trustworthy enough to serialize transactions. TrueTime uses "multiple modern clock references (GPS and atomic clocks)" to keep uncertainty "generally less than 10ms", and crucially the API *exposes* that uncertainty. Three primitives suffice for everything downstream:

- `TT.now()` — returns `[earliest, latest]` with `earliest ≤ t_abs ≤ latest`
- `TT.before(t)` — true when t has definitely *not* arrived: `TT.now().latest < t`
- `TT.after(t)` — true when t has definitely *passed*: `TT.now().earliest > t`

On top of this, Spanner assigns every read–write transaction a globally meaningful commit timestamp s satisfying external consistency: if T1 commits before T2 starts, then s1 < s2. Read-write transactions use two-phase locking; read-only transactions are lock-free snapshot reads at an assigned timestamp [2].

HLCs [1] were motivated by precisely the question TrueTime answers with hardware: *what if special clocks are infeasible?* The HLC timestamp is a pair (l, c): l tracks the maximum physical time seen (local or learned from messages), and c is a logical counter used only to break ties when l values coincide. The design goals are explicit: (1) e → f ⇒ hlc(e) < hlc(f); (2) each timestamp is O(1) integers; (3) bounded space; (4) |l.e − pt.e| is bounded — timestamps stay close to the physical clock. Demirbas and Kulkarni later showed that this "AugmentedTime" could replace or complement TrueTime inside Spanner itself [6].

On the systems side, three deployments matter. **CockroachDB** [4] uses HLCs everywhere and introduces **closed timestamps**: a follower replica that has observed all writes up to T_closed can serve consistent reads at any timestamp ≤ T_closed without contacting the leaseholder — "closed timestamps typically trail current time by ~2 seconds". **TiKV/TiDB** [7] uses *resolved timestamps* on the same principle: the minimum over in-flight transactions' lower-bound commit timestamps. **Calvin** [5] takes the opposite pole: instead of fusing time into transactions, it sequences transactions deterministically through epochs (advanced every 10 ms), executes them with deterministic locking, and thereby eliminates distributed commit protocols altogether.

## 3 Methodology

We model a distributed database as a set of processes P = {p1, …, pn} with physical clocks pt.i(t) subject to bounded drift. Absolute time is denoted t_abs. An event e at process i has timestamp hlc(e) = (l.e, c.e) ordered lexicographically. Transactions are partially ordered programs with read and write sets; their serialization order is a total order consistent with real-time precedence: T1 commits (client-observable) before T2 begins ⇒ s(T1) < s(T2).

Our analysis proceeds in three passes — algorithmic (HLC rules and the commit-wait invariant [1,2]), proof-theoretic (the core theorems and their sketches), and empirical (published measurements from [2,4,5,6]).

Notation summary:

| Symbol | Meaning |
|---|---|
| (l.e, c.e) | HLC timestamp of event e: physical component, logical counter |
| pt.i | Physical clock reading at process i |
| t_abs(e) | Absolute (Newtonian) time of event e |
| ε | TrueTime uncertainty half-width; TT.now() = [now−ε, now+ε] |
| s(T) | Commit timestamp assigned to transaction T |
| T_closed | Closed timestamp: all writes ≤ T_closed are durable and visible |

## 4 Deep Dive

### 4.1 The HLC Mechanism: Tuple Dynamics and the One-Way Causality Theorem

The naive hybrid idea — max of physical time seen so far, plus a counter when it collides — fails because the single scalar l is forced to serve two masters: it must track the maximum physical time *and* absorb logical increments. Kulkarni et al. [1] split the responsibilities into the tuple (l, c). The algorithm:

```python
# HLC update at process i. State: l_i, c_i (initially 0, 0).
def hlc_local_or_send(i):
    l_prime = l_i
    l_i = max(l_prime, pt_i())          # track max physical time
    if l_i == l_prime:
        c_i += 1                        # causality: new event, same l
    else:
        c_i = 0
    return (l_i, c_i)                   # stamp event (and message)

def hlc_receive(i, msg):
    l_prime = l_i
    l_m, c_m = msg.ts                   # sender's HLC timestamp
    l_i = max(l_prime, l_m, pt_i())
    if l_i == l_prime == l_m:
        c_i = max(c_i, c_m) + 1
    elif l_i == l_prime:
        c_i += 1
    elif l_i == l_m:
        c_i = c_m + 1
    else:
        c_i = 0
    return (l_i, c_i)
```

The receive rule's four cases are the heart of the design: when the incoming l exceeds both local state and physical time, causality is preserved by adopting the message's counter; when local time dominates, the local counter absorbs the event; only when physical time advances does the counter reset to zero, keeping (l, c) glued to the wall clock [1,3].

> Theorem: *One-way causality.* For any two events e, f, if e happens-before f (e → f), then hlc(e) < hlc(f) in lexicographic order. The converse does not hold: hlc(e) < hlc(f) does not imply e → f.

The proof is by induction on the construction of →. Local events strictly increase (l, c) lexicographically: either l advances (c resets to 0, but the pair is larger because l dominates), or l stays and c increments. Send(m) carries (l, c); on receive, the max-construction guarantees the receiver's new l is ≥ l_m, and in every case where equality holds the counter is strictly larger than c_m. Transitivity closes the argument. The boundedness claim — |l.e − pt.e| bounded — follows because l.e exceeds pt.e only when a message from the future (a fast clock) arrives, and the excess is at most the maximum clock skew; crucially, *c* absorbs the rapid-fire events so l never needs to run ahead [1].

### 4.2 TrueTime and the Commit-Wait Invariant

TrueTime inverts HLC's bargain: instead of absorbing skew into a counter, it *measures* the skew and makes it visible. The API contract is a single invariant [2,6]:

> Theorem: *TrueTime bracketing.* For any invocation enow of TT.now() returning [earliest, latest], t_abs(enow) ∈ [earliest, latest].

The implementation combines GPS receivers and atomic clocks in each datacenter with Marzullo-style interval intersection across time masters; when masters disagree beyond threshold, ε grows and the system slows down rather than lie. Reported typical values: ε ≈ 2–7 ms, so intervals are roughly 4–14 ms wide [2].

Commit wait is the mechanism that converts bracketing into external consistency. The read–write transaction protocol [2]:

1. The coordinator leader picks a commit timestamp s ≥ TT.now().latest (after prepare).
2. The coordinator **commit-waits**: it does not expose the commit until TT.after(s), i.e., until TT.now().earliest > s.
3. Only then does it send the commit timestamp to the client and participant leaders, who log the outcome through Paxos and apply at s.

> Theorem: *External consistency via commit wait.* If transaction T1 commits (becomes client-visible) at real time r1 and T2 begins at real time r2 > r1, then s1 < s2.

*Proof sketch.* T1's commit becomes visible only after TT.after(s1), hence the absolute time of visibility exceeds s1. T2's coordinator chooses s2 ≥ TT.now().latest evaluated at T2's prepare, which brackets an absolute time ≥ r2 > r1 ≥ the visibility time of T1's commit; chaining the bracketing invariant yields s1 < s2 [2]. As Google's engineering notes emphasize, "if a write transaction t2 is dependent on the outcome of a write transaction t1 (causal relationship), then t2's commit timestamp is guaranteed to be greater than t1's commit timestamp," and because timestamp selection precedes the wait while Paxos messaging proceeds *during* it, "the vast majority of the time, Spanner's commit wait step involves no waiting."

### 4.3 Spanner's Read–Write Transaction Pipeline

With commit wait established, the full write path is a study in layered mechanisms [2]:

1. **Client buffering.** The client drives reads (served at a chosen timestamp, possibly stale) and buffers writes client-side; locks are acquired lazily at commit.
2. **Participant prepare.** The coordinator sends prepare to each participant Paxos group's leader. Each acquires write locks and chooses a prepare timestamp ≥ TT.now().latest.
3. **Timestamp selection.** The coordinator sets s = max over participants' prepare timestamps (monotonic across the transaction).
4. **Commit wait.** As in §4.2: wait until TT.after(s). Paxos commit records are dispatched *during* the wait, overlapping communication with the uncertainty window.
5. **Apply and release.** Each participant leader logs the commit through Paxos, applies at s, releases locks, and the coordinator notifies the client.

Read-only transactions avoid all of this: a single-site read takes s_read = LastTS(); a multi-group read takes s_read = TT.now().latest and executes as a lock-free snapshot read on any sufficiently fresh replica.

The invariant chain is worth stating plainly: *Paxos provides per-group total order; 2PL provides isolation within and across groups; TrueTime timestamps make the cross-group order externally consistent.* Remove any one layer and the guarantee collapses — without Paxos, participants disagree; without 2PL, concurrent writes interleave invisibly; without TrueTime, timestamps cannot respect real time.

### 4.4 Closed Timestamps and Deterministic Scheduling: Two Counterpoints

**Closed timestamps (CockroachDB, TiKV).** A closed timestamp T_closed for a range is a promise: *no write with commit timestamp ≤ T_closed will ever appear in the future.* The advancement rule is T_closed ≤ min over in-flight writers' lower-bound commit_ts; once a follower learns T_closed, it serves reads at any t ≤ T_closed locally — no leaseholder round trip, no lock. The catch is physical clock skew: if T_closed is computed on the leader's clock but consumed on a follower's, a skew δ breaks the promise unless a margin δ is subtracted or — CockroachDB's solution — timestamps are HLC pairs, in which case the logical component absorbs the skew and the margin shrinks to zero [4]. CockroachDB's HLC uses 64-bit physical and 32-bit logical components; *synthetic* timestamps (a reserved high bit) are used for future-dated writes that must never contaminate real HLC clocks [4].

**Deterministic scheduling (Calvin).** Calvin [5] rejects the entire timestamp-assignment problem. Client requests are batched into epochs (every 10 ms); a sequencer layer totally orders the epoch's transactions identically at every replica; each partition then executes its slice under deterministic locking, so no distributed commit protocol is needed at all — atomicity follows from the shared input order. The price is input latency (requests wait for epoch boundaries) and the loss of interactive transactions (all read/write sets must be known upfront, or handled via reconnaissance queries). Where Spanner buys external consistency with hardware and waiting, Calvin buys it with *agreement on order before execution*.

The three designs form a clean taxonomy:

| Design | Time source | External consistency mechanism | Latency tax | Hardware need |
|---|---|---|---|---|
| Spanner [2] | TrueTime (GPS/atomic) | Commit wait on TT.after(s) | ~2ε on writes | Specialized |
| CockroachDB [4] | HLC over NTP | HLC causality + closed timestamps | ~2 s staleness for follower reads | Commodity |
| Calvin [5] | Epoch sequencing | Deterministic lock order | Epoch batching (~10 ms), no interactive txns | Commodity |

## 5 Empirical Results and Proofs

**Measurement summary.** Spanner's TrueTime holds ε to a few milliseconds (~2–7 ms reported), so commit wait adds single-digit milliseconds to write latency in the common case and frequently zero, since the wait overlaps Paxos messaging [2]. The HLC counter c was observed at values up to 10 in the original experiments — nowhere near overflow of even 16-bit compact encodings [1]. CockroachDB's closed timestamps "typically trail current time by ~2 seconds," trading ~2 s of follower-read staleness for locality [4]; TiKV's resolved timestamps follow the same pattern, enabling TiDB's Stale Read feature to nearly double read throughput for read-heavy workloads [7]. Calvin's TPC-C evaluation showed near-linear scaling on partitioned workloads because deterministic scheduling removes the distributed commit from the hot path, though cross-partition transactions pay the full epoch-plus-execution cost [5].

**Proof: HLC bounded skew.** We sketch the argument from [1]. Let σ be the maximum skew between any two physical clocks. Claim: for every event e, l.e − pt.e ≤ σ. Suppose not; let e be the first event (in causal order) violating the bound. e cannot be a local/send event (those set l.e = max(l′, pt.e), and l′ satisfied the bound by minimality, while pt.e − pt.e = 0). So e is a receive of message m with l.m − pt.e > σ; but l.m ≤ pt at the send event + σ (induction hypothesis at the sender), and message delay is non-negative, so pt(send) ≤ pt.e, giving l.m − pt.e ≤ σ — contradiction. Thus l never leads the local physical clock by more than the skew, and c only grows when l is stationary, so timestamps track physical time within σ *by construction* [1].

**Proof: commit-wait correctness** was sketched in §4.2; its corollary is that *write latency is bounded below by the uncertainty interval*: halving ε halves the worst-case commit wait.

## 6 Limitations

1. **Hardware fragility (TrueTime).** TrueTime's guarantees are only as good as its references. GPS jamming or spoofing, atomic-clock failures, or datacenter network partitions that isolate time masters all inflate ε; Spanner's response — slowing every write — is correct but converts a clock fault into a global latency event. Systems that cannot provision such hardware simply cannot use this design [2].
2. **Skew amplification (HLC).** HLC bounds l − pt by the maximum skew σ, but σ itself can grow large under NTP failure or VM clock-step events; a single misbehaving node's fast clock drags every HLC it touches into the future, and c-counters, while absorbing ordering, cannot prevent timestamps from becoming *meaningless as wall-clock values*. Raw physical clocks are not even monotonic — the Cloudflare leap-second incident is the canonical reminder — and HLC repairs monotonicity but not accuracy.
3. **Counter width under adversarial rates.** Compact 64-bit HLC encodings (48-bit physical + 16-bit logical) overflow the counter if 65,536 events occur within one physical tick at a single process — pathological but not inconceivable for in-memory transaction coordinators. CockroachDB's 64+32-bit split mitigates this at the cost of wider timestamps on every key and log record [4].
4. **Causality ≠ real time.** HLC preserves the clock condition but cannot provide external consistency on its own: causally unrelated transactions can be stamped in an order contradicting real-time precedence, so linearizable reads need commit wait or an equivalent barrier [1,2].
5. **Determinism's straitjacket (Calvin).** Epoch batching imposes a floor on latency, and the requirement that read/write sets be known before execution excludes interactive, data-dependent transactions. High-contention cross-partition workloads serialize through the deterministic lock order with limited parallelism [5].
6. **Staleness floors (closed/resolved timestamps).** Follower reads at T_closed trail the present by seconds; applications requiring read-your-writes across regions must still contact the leaseholder, recovering the latency the mechanism was built to avoid [4].

## 7 Conclusion

Hybrid Logical Clocks and TrueTime are answers to the same question from opposite ends of the cost spectrum: *how do we order events in a way that is both causally sound and anchored to real time?* HLCs answer with software — an (l, c) tuple, four receive-case rules, and a theorem that causality is never inverted, all within O(1) space and commodity NTP. TrueTime answers with physics — GPS and atomic clocks, an API that refuses to hide uncertainty, and a commit-wait protocol that converts the bracketing invariant into external consistency at planetary scale.

The systems built on these fusions reveal the underlying unity. Spanner's globally meaningful commit timestamps, CockroachDB's closed timestamps, TiKV's resolved timestamps, and Calvin's deterministic epochs are all mechanisms for producing *one total order that every replica agrees on and that respects real time*. The choice among them is a choice of which resource to spend: specialized hardware, logical compensation, read staleness, or scheduling latency.

Two directions stand out. First, *uncertainty-aware scheduling*: expose ε to schedulers so latency-sensitive transactions ride low-uncertainty windows. Second, *adaptive fusion*: HLC layers that widen counters under detected skew, and TrueTime layers that fall back to logical compensation during reference outages, yielding graceful degradation instead of a binary choice between correctness and availability.
