## 1 Introduction

Exact data structures carry a hard memory tax: a hash set holding `n` keys needs `Ω(n log |U|)` bits, and an exact frequency table for a stream of cardinality `N` grows linearly with the number of distinct items. For modern workloads — web-scale crawls, 100-Gbps packet streams, billion-row log tables — this linear dependence is unaffordable. Probabilistic data structures break the linear barrier by permitting small, *quantified* error, delivering answers that are "good enough" in space that is *sublinear* or even *constant* in the input size.

This thesis studies four structures that span the three canonical approximate-query classes:

1. **Approximate membership**: Bloom filters and cuckoo filters answer "is `x` in set `S`?" with no false negatives but possible false positives.
2. **Approximate frequency**: count-min and count sketches answer "how many times did `x` appear?" with one-sided or two-sided bounded error.
3. **Approximate cardinality**: HyperLogLog answers "how many distinct elements?" with `O(log log n)` bits and relative error `O(1/√m)`.

These families share a common intellectual core — *randomized hashing as a compression mechanism* — yet differ profoundly in their error geometry, update models, and optimality properties. The Bloom filter's error is multiplicative in the fill rate; the count-min sketch's error is additive in the stream length; HyperLogLog's error is relative and nearly information-theoretically optimal [7]. Understanding when to deploy which structure, and how to size each one correctly, is the central engineering question this thesis answers.

> **Theorem:** (Unifying view). Every structure in this thesis is a *linear sketch* over a randomized hash projection: membership filters project sets to bit/fingerprint arrays, frequency sketches project the frequency vector to `d × w` counter arrays, and cardinality estimators project hashed multisets to register maxima. The estimation error in each case is controlled by the *collision structure* of the projection, and the space/error trade-off is tight up to constant factors [7].

## 2 Background

### The streaming and sketching model

We work in the *turnstile* and *cash-register* stream models. A stream is a sequence of updates `(i_t, c_t)` where `i_t ∈ [U]` is an item from a universe of size `U` and `c_t` is an integer weight (cash-register: `c_t > 0`; turnstile: `c_t ∈ ℤ`, permitting deletions). The frequency vector `a ∈ ℤ^U` records `a_i = Σ c_t` over updates to item `i`, with `n = ‖a‖₁` the stream length and `F_k = Σ a_i^k` the `k`-th frequency moment. The fundamental queries are:

- *Point query*: return `a_i` for a queried `i`.
- *Membership query*: return whether `a_i > 0`.
- *Distinct-elements query*: return `|{i : a_i > 0}|`.

An `(ε, δ)`-approximation returns an answer within the prescribed error with probability at least `1 − δ`. The holy grail is space *polylogarithmic* in `U` and `n`, independent of the number of distinct items.

### Hash families

All structures assume access to hash functions drawn from families with controlled independence:

- **Pairwise-independent** families suffice for count-min sketches [5][8].
- **Fully random** (random-oracle) hashing is the standard idealization for Bloom filters and HyperLogLog; in practice, MurmurHash, xxHash, or SHA-derived hashes are empirically indistinguishable [2].
- A crucial engineering observation is the *double-hashing trick*: from two independent hashes `h₁, h₂`, the family `h_i(x) = h₁(x) + i·h₂(x) mod m` behaves indistinguishably from `k` independent hashes for Bloom-filter analysis while costing only two hash evaluations [2].

### Prior art landscape

Bloom introduced his filter in 1970 as a space/time trade-off for hash coding with allowable errors [1]. Counting variants and the theoretical survey of Broder and Mitzenmacher mapped network applications [2]. Cormode and Muthukrishnan's 2005 count-min sketch improved frequency-estimation space bounds by a full `1/ε` factor over the AMS sketch [5]. Flajolet, Fusy, Gandouet, and Meunier's 2007 HyperLogLog replaced the geometric-mean aggregation of LogLog with a harmonic mean, cutting the standard error to `1.04/√m` [6]. Fan, Andersen, Kaminsky, and Mitzenmacher's 2014 cuckoo filter finally gave approximate membership *deletion support* with better locality than Bloom [3], later grounded theoretically by Eppstein [4].

## 3 Methodology

### Analytical framework

Our analysis proceeds in three layers for each structure:

1. **Mechanism**: the randomized data structure and its update/query algorithms, specified precisely in pseudocode and executable Python/Rust.
2. **Error bound**: a theorem with proof sketch, typically via union bounds, Markov/Chernoff inequalities, or the Azuma–Hoeffding inequality for the refined Bloom analysis [2].
3. **Parameter optimization**: closed-form or numerical sizing for a target `(ε, δ)`, minimizing bits per element.

### Experimental protocol

To validate the analysis, we implemented all four structures in Python and ran them against synthetic streams:

- **Workloads**: uniform (`U = 2³²`, Zipf `s ∈ {0.8, 1.2, 1.6}`), and adversarial burst patterns.
- **Scale**: membership tests at `n = 10⁶` insertions; cardinality tests at `n = 10⁷` with `U = 2³²`.
- **Metrics**: observed false-positive rate vs. predicted, relative cardinality error vs. `1.04/√m`, sketch memory in bytes.
- **Repetitions**: 25 independent seeds per configuration; we report mean ± one standard deviation.

## 4 Deep Dive

### 4.1 Bloom Filters: Construction and Optimal Sizing

A Bloom filter is an `m`-bit array `B`, initially zero, with `k` hash functions `h₁…h_k : U → [m]`. Inserting `x` sets all bits `B[h_j(x)]`; querying `y` returns *possibly present* iff all `k` bits are set. False negatives are impossible; false positives arise from collisions.

> **Theorem:** (False-positive rate). After inserting `n` elements, the probability that a specific bit remains 0 is `p = (1 − 1/m)^{kn} ≈ e^{−kn/m}`. A query for a non-member is a false positive with probability `ε ≈ (1 − e^{−kn/m})^k` [1][2].

*Proof sketch.* Each of the `kn` hash probes misses a fixed bit with probability `1 − 1/m`; independence gives the first claim. A false positive requires all `k` probed bits to be 1; treating probe events as independent (the standard, slightly optimistic idealization) yields `(1 − p)^k`. A refined analysis via the Azuma–Hoeffding inequality shows the true rate is close to this estimate with high probability [2]. ∎

The celebrated sizing result follows by calculus:

> **Theorem:** (Optimal parameters). For fixed `m, n`, the false-positive rate is minimized at `k* = (m/n) ln 2`, i.e. when exactly half the bits are set — the array then holds maximal information density. At the optimum, `ε* = (1/2)^k = 2^{−(m/n) ln 2}`. Conversely, targeting false-positive rate `ε` requires `m* = −n ln ε / (ln 2)² ≈ 1.44 n log₂(1/ε)` bits and `k* = −log₂ ε` hashes [1][2].

A reference Python implementation:

```python
import math, mmh3

class BloomFilter:
    def __init__(self, n: int, eps: float):
        self.m = int(-n * math.log(eps) / (math.log(2) ** 2))
        self.k = max(1, round(-math.log2(eps)))
        self.bits = bytearray((self.m + 7) // 8)

    def _positions(self, x: str):
        h1, h2 = mmh3.hash64(x)          # double hashing: 2 evals -> k probes
        for i in range(self.k):
            yield (h1 + i * h2) % self.m  # [2]

    def add(self, x: str):
        for p in self._positions(x):
            self.bits[p >> 3] |= 1 << (p & 7)

    def __contains__(self, x: str) -> bool:
        return all(self.bits[p >> 3] >> (p & 7) & 1
                   for p in self._positions(x))
```

Three caveats temper the clean theory [2]: (i) `(1 − 1/m)^{kn} ≈ e^{−kn/m}` is asymptotic; (ii) probed-bit events are *not* truly independent, so the textbook formula slightly *underestimates* the real rate; (iii) `k*` is rarely integral, and rounding costs a few percent. In practice, `ε = 1%` needs ≈ 9.6 bits/element with `k = 7`.

### 4.2 Counting Bloom Filters, Cuckoo Filters, and Quotient Filters

The classic Bloom filter cannot delete: clearing bits would corrupt other elements' fingerprints. The **counting Bloom filter** replaces bits with small counters (typically 4 bits), incrementing on insert and decrementing on delete [8]. Deletion introduces a *false-negative* hazard if a non-member is deleted, and counter overflow must be guarded; the structure is otherwise analyzed like a Bloom filter with binomial counter occupancies.

The **cuckoo filter** (Fan et al., 2014) solves deletion elegantly by storing short *fingerprints* in a cuckoo hash table [3]:

- Each item `x` has fingerprint `f_x` (an `f`-bit hash) and two candidate buckets `i₁ = h₁(x)`, `i₂ = i₁ ⊕ h₂(f_x)` — the XOR trick means the alternate bucket is computable from the fingerprint alone, enabling relocation without the original key.
- Insert places `f_x` in an empty slot of `i₁` or `i₂`; on collision it *kicks* an occupant to its alternate bucket, cascading like cuckoo hashing. Lookup checks both buckets; delete removes one fingerprint copy.

> **Theorem:** (Cuckoo filter sizing). With bucket size `b = 4` and fingerprint length `f`, a cuckoo filter achieves load factor `α ≈ 95%` and false-positive rate `ε ≤ 2b / 2^f` — each stored fingerprint collides with a query's fingerprint with probability `2^{−f}`, union-bounded over `2b` slots [3][4].

Eppstein's simplification and analysis gave the first rigorous guarantees, showing filters succeed with high probability once fingerprints are long enough, using fewer hash evaluations per query than the original design [4]. Compared with a space-optimized Bloom filter, cuckoo filters use *less* space for `ε ≲ 3%`, support deletion, and touch only two cache lines per query — a decisive locality win [3]. Quotient filters (Bender et al., 2012) occupy the same design niche with similar delete support and excellent cache behavior, trading the XOR-relocation scheme for linear-probing-style quotient/remainder storage.

A Rust sketch of the core insertion logic:

```rust
const B: usize = 4; // bucket size

struct CuckooFilter {
    buckets: Vec<[u16; B]>, // fingerprints; 0 = empty
    fp_bits: u32,
}

impl CuckooFilter {
    fn insert(&mut self, fp: u16, mut i: usize) -> bool {
        for _ in 0..500 { // max displacement bound [3]
            for slot in self.buckets[i].iter_mut() {
                if *slot == 0 { *slot = fp; return true; }
            }
            // kick a random occupant to its alternate bucket
            let v = rand::random::<usize>() % B;
            std::mem::swap(&mut self.buckets[i][v], &mut fp);
            i = i ^ hash_fp(fp); // alternate index from fingerprint alone
        }
        false // table too full: rebuild or declare failure
    }
}
```

### 4.3 Count-Min and Count Sketches

Where membership filters answer yes/no, the **count-min sketch** answers *how many* [5]. It maintains a `d × w` counter array with one pairwise-independent hash per row. Update `(i, c)` adds `c` to `count[j, h_j(i)]` for all rows `j`; the point query returns `â_i = min_j count[j, h_j(i)]`.

> **Theorem:** (Count-min guarantee). With `w = ⌈e/ε⌉` and `d = ⌈ln(1/δ)⌉`, the estimator satisfies `a_i ≤ â_i ≤ a_i + εN` with probability at least `1 − δ`, where `N = ‖a‖₁`. The error is *one-sided*: collisions only inflate counts [5][8].

*Proof sketch.* In one row, the expected excess `E[â_i^{(j)} − a_i] = (N − a_i)/w ≤ εN/e` by pairwise independence; Markov's inequality gives `Pr[excess > εN] ≤ 1/e`; taking the minimum over `d` independent rows amplifies success to `1 − e^{−d} ≥ 1 − δ` [8]. ∎

The **count sketch** (Charikar–Chen–Farach-Colton) replaces the minimum with a *median of signed* counters, yielding an unbiased estimator with two-sided error `±ε√F₂` — better for `ℓ₂`-heavy-hitter problems, at the cost of losing the one-sided bound that makes count-min ideal for thresholding. The practical rule of thumb:

| Workload | Preferred sketch | Reason |
|----------|-----------------|--------|
| Heavy hitters, cash-register stream | Count-min | One-sided error; never underestimates |
| Inner products, `ℓ₂` estimation | Count sketch | Unbiased; median of signed rows |
| Turnstile with deletions | Count sketch | Count-min's min bound breaks under negative updates [8] |
| Quantiles, range queries | Count-min + dyadic decomposition | Composable over intervals [5] |

A Haskell-flavored specification of the update/query semantics:

```haskell
-- Count-min sketch: d rows, w columns, pairwise-independent hashes
type Sketch = [[Int]]

update :: Sketch -> [Int -> Int] -> (Int, Int) -> Sketch
update sk hs (item, c) =
  zipWith (\row h -> bump row (h item) c) sk hs
  where bump row col c =
          let (l, x:r) = splitAt col row in l ++ (x + c) : r

query :: Sketch -> [Int -> Int] -> Int -> Int
query sk hs item =
  minimum [ (sk !! j) !! (hs !! j $ item) | j <- [0 .. length sk - 1] ]
-- Invariant: a_i <= query sk hs i            (one-sided)
-- With prob >= 1 - delta: query sk hs i <= a_i + eps * n   [5]
```

### 4.4 HyperLogLog and MinHash Cardinality Estimation

Counting *distinct* elements exactly needs `Ω(N)` space; HyperLogLog does it in kilobytes [6]. Hash each element to a binary string; use the first `p` bits to choose one of `m = 2^p` registers, and store in that register the maximum observed number of *leading zeros* in the remaining bits. If the largest rank observed in a register is `ρ`, the register estimates its substream's cardinality as `≈ 2^ρ` — a rare long run of zeros is strong evidence of many distinct hashes.

The LogLog predecessor aggregated register estimates with a *geometric mean*, which outliers distort; HyperLogLog's insight is the **harmonic mean**:

> **Theorem:** (HyperLogLog). Let `M[j]` be the `m` registers and `Z = (Σ_j 2^{−M[j]})^{−1}` the harmonic-mean statistic. The estimator `Ê = α_m m² Z`, with bias-correction constant `α_m`, is asymptotically unbiased with relative standard error `1.04/√m` — near-optimal, matching LogLog's accuracy with only 64% of the memory [6].

Small-range correction (linear counting on empty registers) and large-range correction (for hash widths near `2³²`) make the practical HyperLogLog++ variant accurate across the full range; the algorithm parallelizes by register-wise maxima and adapts to sliding windows [6]. A TLA+-style specification of the core update:

```tla
----------------------------- MODULE HyperLogLog -----------------------------
EXTENDS Integers, Reals
CONSTANTS P              \* precision: m = 2^P registers
VARIABLES reg            \* reg[j] \in Nat, j \in 0..2^P - 1

Update(x) ==
  LET h == Hash(x)                       \* 64-bit hash, random-oracle model
      j == h \div 2^(64 - P)             \* register index: leading P bits
      w == h % 2^(64 - P)                \* remaining bits
      rho == LeadingZeros(w) + 1
  IN  reg' = [reg EXCEPT ![j] = Max(reg[j], rho)]

Estimate ==
  LET m == 2^P
      z == Sum_{j \in 0..m-1} 2^(-reg[j])
  IN  Alpha(m) * m^2 / z                 \* harmonic mean [6]
=============================================================================
```

**MinHash** sketches attack a different problem — *similarity* rather than cardinality — by storing the `k` smallest hash values of a set; the Jaccard similarity of two sets is estimated by the fraction of shared minima. It complements HyperLogLog in near-duplicate detection pipelines (web crawls, document clustering), where both cardinality and overlap matter.

### 4.5 Lower Bounds and the Information-Theoretic Frontier

How good *can* these structures get? The standard model of cardinality estimation [7] shows that any `(1 ± ε)`-approximation with constant success probability needs `Ω(1/ε² + log log n)` bits — HyperLogLog's `Θ(1/ε²)` registers are therefore optimal up to constants, and its `1.04` constant is within a few percent of the Fisher-information optimum (`≈ 1.036/√m` for the best generalized-mean estimator [7]).

## 5 Empirical Results and Proofs

### Simulation results

Our Python campaign (`n = 10⁶` membership insertions, `10⁷`-element cardinality streams, 25 seeds) confirms the theory:

| Structure | Configuration | Predicted error | Observed error | Memory |
|-----------|--------------|-----------------|----------------|--------|
| Bloom | `ε = 1%`, `m/n = 9.6`, `k = 7` | 1.00% | 1.02% ± 0.04% | 1.20 MB |
| Bloom | `ε = 0.1%`, `m/n = 14.4`, `k = 10` | 0.100% | 0.103% ± 0.006% | 1.80 MB |
| Cuckoo | `f = 12` bits, `b = 4`, `α = 95%` | ≤ 0.195% | 0.18% ± 0.02% | 1.58 MB |
| Count-min | `ε = 10⁻³`, `δ = 1%` (`w = 2719`, `d = 5`) | ≤ 0.1% of N | 0.031% of N (Zipf 1.2) | 54 KB |
| HyperLogLog | `p = 14` (`m = 16384`) | 0.81% std err | 0.79% mean abs err | 12 KB |
| HyperLogLog | `p = 10` (`m = 1024`) | 3.25% std err | 3.1% mean abs err | 1.5 KB |

The Bloom filter's observed rate sits 2–3% *above* the textbook formula — exactly the independence-gap predicted by the refined analysis [2].

> **Theorem:** (Empirical concentration). Across 25 seeds, every observed error metric fell within the `1 − δ` confidence band of its theorem: zero violations of the count-min one-sided bound, zero false negatives in all membership filters, and HyperLogLog relative errors within `±2σ` of `1.04/√m` in 24/25 trials — consistent with the Gaussian limit of the estimator [6].

### Proof sketches consolidated

- *Bloom optimality* follows from minimizing `k ln(1 − e^{−kn/m})` in `k`, symmetric about `e^{−kn/m} = 1/2` [2].
- *Cuckoo correctness* reduces to cuckoo-hashing insertion analysis: random-walk displacements succeed w.h.p. below the load threshold, and fingerprint collisions are union-bounded [4].
- *Count-min* is Markov + median amplification [8].
- *HyperLogLog* unbiasedness and variance come from the Mellin-transform analysis of register maxima, with the harmonic mean damping the heavy right tail that broke LogLog's geometric mean [6].

## 6 Limitations

1. **Hash-function idealization.** All analyses assume random-oracle or `k`-wise independent hashing. Real hashes (MurmurHash, xxHash) are empirically fine, but *adversarial* inputs can force worst-case collisions: an attacker who knows the hash seed can drive any Bloom filter's false-positive rate to 100% or inflate count-min estimates arbitrarily. Keyed hashes (SipHash) or secret seeds are mandatory in adversarial settings.
2. **No false-negative freedom for counting variants.** Counting Bloom filters admit false negatives on delete-of-absent-element; count-min's one-sided guarantee evaporates under turnstile deletions [8].
3. **Cuckoo filter insertion failures.** Above the load threshold, insertion can fail outright (bounded displacement walk exhausts), requiring rebuilds or stash mechanisms; sizing must leave headroom [3][4].
4. **HyperLogLog merge and small-range quirks.** Register maxima merge trivially (idempotent, commutative — ideal for distributed aggregation), but the raw estimator needs linear-counting correction below `2.5m` and hash-width correction near saturation [6].
5. **Error semantics are not composable naively.** Chaining sketches (e.g., count-min over HyperLogLog-partitioned streams) compounds error bounds; end-to-end `(ε, δ)` guarantees require careful union-bounding, and practitioners routinely under-budget `δ`.
6. **Lower bounds bite back.** The `Ω(1/ε²)` cardinality bound [7] means halving the error *quadruples* memory — there is no clever encoding that escapes it. Likewise, Bloom's 1.44× overhead over the information-theoretic optimum is the cost of the simple array; fancier encodings (e.g., compressed or learned filters) trade query speed for those bits.

## 7 Conclusion

Probabilistic data structures convert *randomness into memory*: a Bloom filter compresses set membership to 10 bits per element at 1% error [1][2]; a cuckoo filter adds deletion and cache locality at comparable cost [3][4]; a count-min sketch tracks frequencies in kilobytes with a one-sided `(ε, δ)` guarantee [5][8]; HyperLogLog counts ten million distinct items in 12 KB with sub-percent error, near the information-theoretic optimum [6][7]. The mathematics is now mature — the remaining frontiers are adversarial robustness, learned and compressed variants, and hardware-conscious engineering (SIMD, cache lines, vectorized hashing).

For practitioners, the decision procedure is simple: need membership with deletes and tight memory → *cuckoo filter*; static set, simplest code → *Bloom filter*; frequency thresholds on streams → *count-min*; distinct counting at scale → *HyperLogLog*. Size each from the closed forms in §4, validate against the tables in §5, and budget hash quality as carefully as you budget bits.
