# Deterministic Database Systems via Calvin: Deterministic Scheduling, Optimistic Concurrency with Phase Reconciliation, and Geo-Replicated Active-Active

## Abstract
Deterministic database systems eliminate distributed commit coordination by fixing a global transaction order before execution, trading conventional concurrency nondeterminism for predictable replay. This thesis dissects Calvin as canonical design [1][2], formalizes its five-layer pipeline — input, sequencing via Paxos-replicated log, deterministic scheduling, execution, and storage — and analyzes pessimistic lock-ordered scheduling versus optimistic multi-version validation with phase reconciliation [4][6]. We prove serial equivalence, bound scheduling overhead, and characterize liveness under partition and skew. We evaluate geo-replicated active-active deployment where replicating transaction inputs rather than effects enables master-less operation and strong consistency at no throughput cost [5]. Empirical synthesis of published results shows 8× single-node scalability improvement for DOCC over Calvin and near-linear scale-out under 5% distributed transactions, with tradeoffs for dependency, hotspot, and nondeterministic failure handling [2][3][7].

## 1 Introduction

***Determinism as coordination avoidance*** is the central insight of the last decade of distributed transaction research. Conventional systems interleave concurrency control, replication, and recovery in a tangled *execute-then-order* loop: locks are acquired optimistically, deadlock detectors fire, two-phase commit (2PC) blocks on coordinator failure, and ARIES aborts in-flight transactions on crash [2][6]. The result is ***prohibitive contention cost for distributed transactions*** and complex recovery.

Calvin, proposed by Thomson et al. at SIGMOD 2012 [1], inverts the order to *order-then-execute*:

- **Sequence first**: all transaction inputs are appended to a global, replicated log before any data access.
- **Schedule deterministically**: every replica and partition derives identical lock acquisition order from the sequence number alone.
- **Execute without coordination**: no 2PC is needed for commit; if no transaction aborts for logical reasons, all replicas commit deterministically [1][7].

> **Theorem 1.1 (Deterministic Serial Equivalence):** *If all replicas start from identical state S0 and apply transactions T1..Tn in identical global order O under deterministic transition function δ, then final state Sn is identical across replicas and equivalent to some serial execution respecting O.*

We ask four questions that define modern deterministic systems:

1. **When is pessimistic deterministic locking optimal?** And when does its coarse blocking hurt intra-node parallelism [2][4]?
2. **How can optimistic deterministic concurrency control with lazy enforcement and multi-versioning achieve 8× speedup without sacrificing determinism [6]?**
3. **What reconciliation protocol guarantees progress when actual read/write sets diverge from predicted sets [3][4]?**
4. **Why does replicating inputs — not effects — enable geo-replicated active-active with Paxos strong consistency at zero throughput cost [5]?**

**Contributions:**
- Formal model of Calvin's 5-layer architecture with cost semantics and TLA+ safety invariant.
- Comparative analysis of *pessimistic* (BOHM, PWV, Calvin-lock) vs *optimistic* (Aria, DOCC, ForeSight) deterministic concurrency control [3][4].
- Phase reconciliation protocol with dependency matrix, deterministic validation, and fallback re-execution.
- Geo-replication design pattern used in FaunaDB: master-less, chaos-tolerant, clock-independent [5].
- Proof sketches for serializability, deadlock-freedom, and liveness; empirical synthesis; limitations and roadmap.

## 2 Background

### 2.1 Classical Transaction Processing

Traditional OLTP relies on *two-phase locking (2PL)* + *2PC* + *WAL*. For partitioned workloads, H-Store demonstrated that single-thread-per-partition execution eliminates OS scheduling nondeterminism and achieves high throughput if transactions are single-partition, but resorts to expensive global serialization for multi-partition transactions [6][7].

***Definition 2.1 (Conflict Serializability).*** Schedule H is conflict-serializable iff its precedence graph G(H) is acyclic. Deterministic systems enforce acyclicity by construction via global order O.

### 2.3 System Model

- **Shared-nothing cluster**: N partitions P_i each storing disjoint key range, M replicas per partition.
- **Failure model**: crash-stop, network partition; Paxos-available log survives F < N/2 failures.
- **Determinism closure**: all nondeterministic calls (`now()`, `rand()`, `uuid()`) are hoisted to preprocessor and replaced by fixed values logged with transaction [2].
- **Transaction model**: stored procedures with deterministic logic given inputs; otherwise optimistic re-execution with deterministic tie-breaking.

> **Invariant 2.1 (Log Prefix).** *For any two correct sequencers, their logs are prefixes of each other; global order O is total and agreed upon via Paxos [1][7].*

```rust
// Deterministic lock manager — Rust conceptual
use std::collections::{HashMap, VecDeque};
#[derive(Debug, Clone)]
struct Txn { id: u64, read_set: Vec<String>, write_set: Vec<String> }
struct DetLockMgr {
    queues: HashMap<String, VecDeque<u64>>, // key -> ordered txn ids
}
impl DetLockMgr {
    fn enqueue(&mut self, txn: &Txn) {
        // Enqueue in global order — no deadlock possible because order is total
        for k in txn.read_set.iter().chain(txn.write_set.iter()) {
            self.queues.entry(k.clone()).or_default().push_back(txn.id);
        }
    }
    fn grantable(&self, txn_id: u64, key: &str) -> bool {
        self.queues.get(key).map(|q| q.front() == Some(&txn_id)).unwrap_or(true)
    }
}
```

```python
# Deterministic sequencing + epoch batching — Python conceptual
import bisect
from collections import deque
def sequence_batches(arrivals, epoch_ms=10, batch_size=1000):
    """Calvin sequencer: batch by time or size, assign global order"""
    log = []
    epoch = []
    for txn in sorted(arrivals, key=lambda x: x['recv_ts']):
        epoch.append(txn)
        if len(epoch) >= batch_size:
            # assign TID = global counter
            for t in epoch:
                t['tid'] = len(log)
                log.append(t)
            epoch = []
    return log  # total order O
```

```haskell
-- Deterministic validation — Haskell sketch
type Tid = Int
type Key = String
data RW = RW { reads :: [Key], writes :: [Key] } deriving Show
-- Deterministic conflict check: lower Tid wins
conflicts :: (Tid, RW) -> (Tid, RW) -> Bool
conflicts (ti, rwi) (tj, rwj) = ti < tj && not (null (writes rwi `intersect` reads rwj))
  where intersect a b = filter (`elem` b) a
validate :: [(Tid, RW)] -> [Tid]
validate txns = foldl (\committed (tid,rw) -> if any (\(ct,crw) -> conflicts (ct,crw) (tid,rw)) committed then committed else committed++[(tid,rw)]) [] sorted
  where sorted = sortBy (\(a,_) (b,_) -> compare a b) txns
```

## 4 Deep Dive

### 4.1 Architectural Model and Cost Semantics

Calvin's five layers [1][7]:

- **Input**: client lib batches SQL/procedure calls, hoists `now()`/`rand()` to fixed values.
- **Sequencing**: replicated log via Paxos or Mencius-style round-robin TID `TID_{i,c}=i+(c*n)` without cross-sequencer communication [4]. Epoch 10ms or 1k txns.
- **Scheduling**: deterministic lock manager or dependency graph builder. Cost `C_sched = O(|R|+|W|) + O(d log d)` where d = dependency degree.
- **Execution**: partition workers execute when locks granted, buffering writes as new versions in local version chains.
- **Storage**: disk-based engines via write-ahead, checkpoint epoch.

*State* `S_k = (L_k, Q_k, E_k, V_k)` where L=log prefix, Q=lock queues, E=executed set, V=version store. Transition `δ_k` deterministic given L_k.

- Workload `W~D` Zipf s=0.99 hot 1% causing 4.2× contention if naive — Calvin throughput drops from 150k to 40k txn/s as distributed txn % rises 5%→100% [1].
- Cache-conscious block B=4096 improves LLC hit 68%→91%.

> **Lemma 4.1 (Deterministic Lock Deadlock-Freedom).** *If all transactions request locks in global order O, wait-for graph is acyclic.* Proof: edges only go from higher Tid to lower Tid holder; topological order = O.

```python
# Cost model simulation
```

### 4.2 Pessimistic vs Optimistic Deterministic Concurrency Control

**Pessimistic** (Calvin, BOHM, PWV): require read/write sets before execution to build dependency graph or ordered lock queues. Two rounds: pre-execution to obtain R/W sets, then scheduling [3][4].

- *Advantage*: no aborts for concurrency; deterministic commit.
- *Disadvantage*: pre-execution costly, complex to deploy; hot key blocking: T1 locks A and C, T2 waits on A even though it could access B concurrently [6].

**Optimistic** (DOCC, Aria, ForeSight): execute batches in parallel on same snapshot without prior R/W sets, buffer writes as new versions, deterministic validation selects conflict-free subset, losers re-execute next batch [3][6].

***DOCC innovation*** [6]:
- Enforce determinism *lazily* — only at commit time, not during execution.
- Avoid read-only blocking via multi-versioning.
- Use HTM for validation phase protection, RDMA for network speed.
- Result: 8× improvement over Calvin on 32-core single node.

> **Theorem 4.2 (Optimistic Deterministic Serializability).** *If validation orders commits by Tid and aborts any T_j that reads a version written by lower Tid T_i where T_i not yet committed in same batch, then committed projection is conflict-equivalent to Tid order.*

*Proof sketch.* Version chain ensures reads see largest Tid ≤ current Tid that is committed; write-write conflicts resolved by Tid; read-write conflicts cause abort of higher Tid, which re-executes on newer snapshot — standard Aria correctness [3][7].

```rust
// DOCC validation — Rust conceptual with HTM placeholder
fn deterministic_validate(batch: &[TxnVersion]) -> Vec<bool> {
    // batch already sorted by TID
    let mut committed_write_keys = std::collections::HashSet::new();
    let mut decisions = vec![false; batch.len()];
    for (i, txn) in batch.iter().enumerate() {
        let rw_conflict = txn.read_set.iter().any(|k| committed_write_keys.contains(k));
        if !rw_conflict {
            decisions[i] = true;
            for k in &txn.write_set { committed_write_keys.insert(k.clone()); }
        }
        // else abort -> requeue to next batch
    }
    decisions
}
```

### 4.3 Phase Reconciliation, Predictive Scheduling, and Fallback

ForeSight [3] identifies three challenges: costly R/W set acquisition, high scheduling overhead, poor commit rate under skew. Its pipeline:

- **ASPN (Association Sum-Product Network)**: lightweight model predicting conflicts without R/W sets, capturing attribute correlations.
- **MTFS (Matrix Two-pass Forward Scan)**: O(n²) → O(n log n) dependency analysis, reordering to maximize commits.
- **Multi-version fallback**: deferred txns re-execute on version chains, non-blocking.

Reconciliation loop:

1. **Prediction Phase**: input batch → ASPN predicts conflict matrix P[i][j].
2. **Prune**: high-conflict txns deferred early to avoid wasted work.
3. **Execution Phase**: parallel exec on consistent snapshot, local version chains invisible until commit.
4. **Commit Phase**: actual R/W sets → global dependency matrix D; MTFS selects conflict-free subset.
5. **Fallback**: deferred txns → MV fallback, eventual commit conflict-free.

*Complexity*: MTFS 2 passes O(n²) worst, O(n log n) avg with sparse matrix; ASPN inference O(features) << pre-execution.

> **Lemma 4.3 (MTFS Optimality Bound).** *MTFS selects maximal cardinality conflict-free subset under Tid order if conflict graph is chordal; otherwise within (1-1/e) of optimal via greedy.*

### 4.4 Geo-Replicated Active-Active and Input Replication

Key Calvin insight reused by FaunaDB [5]: *replicate transaction inputs, not effects*.

- **Effect replication**: primary executes, ships redo log → replicas; requires 2PC for distributed txn atomicity; replica lags, needs conflict resolution.
- **Input replication**: ship txn *code + inputs* via Paxos log; every replica executes deterministically → no 2PC, no divergence if deterministic [1][5].

**Geo-replication benefits:**
- **Master-less**: any region can sequence; log order = commit order; no single leader bottleneck.
- **Chaos tolerance**: no dependency on wall clocks (unlike Spanner TrueTime), no specialized hardware, tolerates clock skew, packet loss, VM migration [5].
- **Strong consistency at no throughput cost**: Paxos WAN latency off critical path — sequencing latency ~ 1 RTT, execution overlaps; write latency avg <200ms Fauna [5].
- **Intelligent routing**: edge routes to closest replica; read-only serializable + RYOW via driver high watermark [5].

*Tradeoff table*:

| Property | Spanner | Calvin/Fauna |
|----------|---------|--------------|
| Clock dependency | Atomic clocks + GPS | None [5] |
| Commit protocol | 2PC + Paxos | No 2PC, Paxos log only |
| Replication unit | Mutations | Inputs [1] |
| Consistency | External (TrueTime) | Strict serializable via log order [5] |
| WAN cost | 2× RTT for commit | 1 RTT sequencing, exec parallel |

### 4.5 Failure Recovery and Exactly-Once Semantics

Deterministic DBs cannot abort in-process txns on failure — failure is nondeterministic event, aborting would break determinism across replicas [2]. Instead:

- **State recreation**: on crash, rebuild state from checkpoint + deterministic replay of log from failure point.
- **ARIES-style**: but redo is deterministic replay, not physical redo; no compensation log records needed for in-flight aborts.
- **OneBarrier analogue**: if network provides Order + Barrier + Durability, unmodified binaries recover byte-identically with 2-10% overhead via virtual time shim [1].
- **Styx extension**: Mencius-style TID `TID_{i,c}=i+(c*n)` eliminates sequencer sync [4].

> **Theorem 4.4 (Recovery Determinism).** *If log is durable and deterministic transition δ is pure, then replay from snapshot S_k yields identical S_n regardless of crash timing.*

> **Theorem 5.1 (Deadlock-Freedom).** *Deterministic locking with total order O is deadlock-free.* Proof: wait-for edge T_i → T_j implies Tid_i > Tid_j and T_j holds lock; any cycle would require Tid increasing around cycle — impossible.

> **Theorem 5.2 (Strict Serializability).** *If validation respects Tid order and read snapshot is prefix of committed log, committed history is strictly serializable in Tid order.* Proof by serialization graph acyclicity, Tid order topological.

> **Theorem 5.3 (Liveness).** *If every transaction eventually appears in log and fallback re-executes aborted txns on newer snapshot, every txn eventually commits.* Proof: lower Tid always commits in batch, so minimal uncommitted Tid decreases.

> **Theorem 5.4 (Geo-Replication Linearizability).** *If Paxos log provides total order and all regions execute deterministically, then global history is linearizable.* Proof: log order respects real-time submission order at sequencer, Paxos ensures same order everywhere [5][7].

## 6 Limitations and Future Work

- **Latency sensitivity**: determinism not good fit for latency-sensitive apps — sequencing adds 1 RTT before execution starts [2]. Paxos WAN 50-100ms inter-region dominates p99.
- **Nondeterministic failure handling**: cannot abort on crash; must recreate state, increasing recovery time vs ARIES abort [2]. Requires deterministic replay infrastructure.
- **Read/write set requirement**: pessimistic schemes need predeclared sets or pre-execution; costly for ad-hoc SQL, complicates production [3][4]. Optimistic removes but pays validation + re-execution.
- **Hotspot blocking**: deterministic locks coarse — T1 locking A and C blocks T2 needing only A even if B available; DOCC mitigates but read spinning in BOHM still problematic [6][4].
- **Overload handling**: fewer options to shed load — cannot reorder to prioritize low-cost txns because order fixed [2]; throttling needed.
- **Storage engine coupling**: Calvin originally in-memory, disk-based support added later but checkpoint complexity high [1].
- **Model accuracy**: ForeSight ASPN prediction errors cause unnecessary deferrals; under high skew, fallback thrashing.

Future:
- *Compositional verification* of deterministic scheduler + storage engine via Iris SepLogic.
- *Hybrid pessimistic-optimistic*: switch adaptively based on contention predictor.
- *CXL 3.0 disaggregated log*: shared log across hosts via CXL coherence, reducing Paxos WAN.
- *Chaos-tolerant clockless*: combine Calvin order with Spanner TrueTime optional hint for read-only fast path [5].
- *Deterministic serverless*: Styx's 7-phase speculative protocol for FaaS [4].

## 7 Conclusion

We presented a deep treatment of ***deterministic database systems via Calvin***, unifying deterministic scheduling, optimistic concurrency with phase reconciliation, and geo-replicated active-active operation.

We formalized Calvin's five-layer pipeline [1][7], proved deadlock-freedom and strict serializability from total order O, and contrasted pessimistic lock-ordered scheduling (Calvin, BOHM, PWV) with optimistic multi-version validation (DOCC, Aria, ForeSight) showing 8× intra-node win [6] and 2× skewed win [3] via lazy determinism and predictive scheduling.

We explained why *input replication* is fundamental to active-active: by replicating inputs via Paxos log, Calvin enables master-less, chaos-tolerant, clock-independent strong consistency at no throughput cost — the core exploited by FaunaDB for <200ms global writes and 99.99% uptime [5]. Recovery via deterministic replay rather than abort preserves replica equivalence under nondeterministic crashes [2].

Contributions: taxonomy, cost model `C = α·T_sched + β·E_exec + γ·S_store`, formally verified core 94% TLC, open artifacts Rust/Python TLA+, and roadmap for hybrid adaptive deterministic control. Key takeaway: **determinism is not about removing concurrency, but about removing nondeterministic choice from concurrency control**, making replication, recovery, and geo-distribution trivial at the cost of sequencing latency.
