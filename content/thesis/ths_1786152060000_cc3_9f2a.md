# Causal Consistency in Geo-Replicated Stores: Hybrid Logical Clocks, COPS, Eiger, and AntidoteDB CRDT Integration

## Abstract
Geo-replication demands *always-on* low-latency reads and writes even under partition, a requirement that forces systems away from linearizability. Causal consistency emerges as the **strongest achievable** consistency without sacrificing availability. This thesis unifies four pillars of modern causal systems: *Hybrid Logical Clocks (HLC)* that blend physical time with Lamport causality in 64 bits, *COPS* which scales causal+ via explicit dependency checking across partitioned clusters, *Eiger* which adds low-latency read-only and write-only transactions without locks, and *AntidoteDB* which layers the Cure protocol and *CRDTs* for transactional causal+ with convergence. We formalize causal+, compare explicit vs implicit dependency tracking, prove HLC monotonicity preserves happens-before, and analyze why latency-optimal ROTs impose write overhead. Through tables and protocol sketches we show how AntidoteDB synthesizes Cure's atomic transaction cache with operation-based CRDT merge, achieving high availability with principled conflict resolution. We close with limits around clock skew, dependency bloat, and CRDT semantic tension.

## 1 Introduction

> *If process A tells process B about an update, B must never see the past — but C, uninformed, may.*

Modern social networks, shopping carts, and collaborative editors replicate data across continents. Users expect local-latency *GET* and *PUT* even when transatlantic links are partitioned. The **CAP theorem** says you cannot have linearizability, availability, and partition tolerance simultaneously. Industry chose AP: Dynamo, Cassandra, PNUTS embraced eventual consistency to survive.

Yet *eventual* is too weak. Consider Alice uploads `photo2.jpg`, Bob's comment `x = "Nice!"` causally after seeing photo. Under eventual, Carol could see comment before photo — a causality violation that breaks UX. Application developers then reinvent causal tracking ad-hoc, with complex compensating logic.

**Causal consistency** formalizes intuition: all processes agree on causal order, but concurrent writes may be seen in different orders. **Causal+** augments with *convergent conflict handling*: all replicas converge deterministically via last-writer-wins or CRDT merge. Lloyd et al. proved causal+ is the strongest achievable under low-latency always-available constraints [1].

Four breakthroughs shape this space:

1. **COPS (SOSP'11)** — first scalable geo-replicated causal+ store enforcing dependencies across an entire cluster, not just per-server, via *dependency checking* and introducing **get-transactions** for multi-key consistent reads without blocking [1].
2. **Eiger (NSDI'13)** — strengthens COPS to provide both **read-only transactions** and **write-only transactions** (atomic multi-write), with validity-interval metadata enabling at most two-round, non-blocking reads [2].
3. **Hybrid Logical Clocks (Kulkarni et al., OPODIS'14)** — replaces heavy vector clocks or brittle NTP with 64-bit `<l, c>` timestamps that are *close to physical time* yet preserve Lamport's `e hb f => hlc.e < hlc.f`, enabling snapshot queries and **CausalSpartanX** robustness to NTP anomalies [3][4].
4. **AntidoteDB / Cure** — planetary-scale transactional CRDT store implementing *Transactional Causal+ Consistency (TCC+)*: snapshot atomic transactions + highly-available CRDTs + real-time causality via commit vectors [5][7].

This thesis argues synthesis is necessary: HLC solves timestamping, COPS/Eiger solve dependency and transaction scope, AntidoteDB solves datatype convergence. Together they define modern causal store architecture.

*Contributions*: formal definition of causal+ and ROT semantics, comparative taxonomy of explicit vs timestamp-based causality, HLC algorithm proof, detailed reconstruction of COPS/Eiger two-round ROT protocol, Cure protocol with CRDT integration analysis, and empirical trade-off table of latency vs metadata size.

## 2 Background

### 2.1 Consistency Spectrum

| Model | Guarantee | ALPS? | Requires |
|-------|-----------|-------|----------|
| **Linearizable** | Real-time total order | No | Consensus |
| **Sequential** | Process order total | No | Consensus |
| **Causal+** | Preserves hb + convergence | **Yes** | Causality tracking only |
| **Causal** | Preserves hb, concurrent may diverge | Yes | Causality tracking |
| **Eventual** | If no new writes, eventually converge | Yes | Anti-entropy only |

*ALPS*: Always available, Low-latency, Partition-tolerant, Scalable. Bailis [8] shows causal+ provides read-your-writes, monotonic reads, writes-follow-reads automatically.

Definition: Let `e1 -> e2` denote Lamport happens-before (same client session, read->write, or transitive). System is causally consistent if for any client, if it observes version `v1` of key `x`, and `v1 -> v2` (v2 depends on v1), then it never later sees version older than `v2` for keys depending on `v1`.

Causal+ adds: if two clients concurrently write `x1`, `x2`, all replicas converge via deterministic function `f(x1,x2)` — typically LWW by timestamp.

### 2.2 Why Not Vector Clocks Everywhere?

Vector clocks precisely capture causality with O(N) size N = #nodes. At Facebook-scale N=1000s, per-value vector = KBs, unacceptable for value <100 bytes. Dependency bloat kills throughput.

Two mitigations evolved:

- **Explicitdeps (COPS/Eiger)**: store small set of immediate dependencies `{(key, version-id)}` per write, assume transitivity covers rest; worst-case still large for popular keys, but practical compression via nearest dependencies.
- **Implicit (timestamp) deps**: single scalar timestamp `t` per version; if `t1 < t2`, causality possible but not exact. Physical clocks need tight synchronization; with skew, visibility delay increases. **HLC** bridges gap.

### 2.3 CRDTs and Transactional Causal+

CRDTs are data types where concurrent updates commute via math: operation-based (`effect` must commute for concurrent ops) and state-based (`merge = join` semi-lattice). In causal stores, CRDT is natural convergence mechanism replacing crude LWW, preserving intent for counters, sets, maps.

**Transactional Causal+ (TCC+)** defined by Cure [5]: adds **all-or-nothing** writes (atomic multi-key) + snapshots (all reads from same causal cut) + causal consistency. This prevents anomaly: Bob sees Alice's `photo` and `wall` update atomically or neither.

We modelled protocols in TLA+-like sketch, evaluated conceptual complexities, not live cluster (no physical deployment), but validated via theorem reduction.

Unified notation:

- `dc_id`, `node_id`, `hlc = <l, c>` where `l = max(phy, ...)` physical component, `c = logical`
- `dep(v) = { (k, ver_id) }` dependency set for version v
- `EVT, LVT` Earliest/Latest Valid Time for validity-period scheme in Eiger
- `commit VC`, `snapshot VC` vectors for Cure

```python
# HLC send/receive (Kulkarni et al. simplification)
def hlc_send(local_hlc, phy_clock):
    l, c = local_hlc
    l_prime = max(l, phy_clock)
    if l_prime == l:
        c_prime = c + 1
    else:
        c_prime = 0
    local_hlc = (l_prime, c_prime)
    return local_hlc  # piggyback on msg

def hlc_recv(local_hlc, msg_hlc, phy_clock):
    l, c = local_hlc
    lm, cm = msg_hlc
    l_prime = max(l, lm, phy_clock)
    if l_prime == l == lm:
        c_prime = max(c, cm) + 1
    elif l_prime == l:
        c_prime = c + 1
    elif l_prime == lm:
        c_prime = cm + 1
    else:
        c_prime = 0
    if l_prime > (1<<48): # boundedness check
        raise BoundedOverflow()
    return (l_prime, c_prime)
```

*Key property*: HLC fits in 64-bit NTP format: 48 bits for physical ms, 16 bits for logical offset allows 65536 concurrent events per ms, sufficient per [3].

## 4 Deep Dive

### 4.1 Hybrid Logical Clocks – Physical Time Meets Causality

Pure physical clocks (PT, TrueTime) offer intuitive ordering but suffer **non-monotonic kinks** during NTP step corrections and require tight synchronization (Spanner's TT waits out uncertainty `2*epsilon` ~7ms). Pure logical clocks (LC, VC) capture `hb` perfectly but have no relation to wall-clock, breaking *external causality*: asking for snapshot at wall time `t`.

HLC invariants:

- `hlc.e = < l.e, c.e >`
- Lexicographic order total
- `e hb f => hlc.e < hlc.f` (one-way, not converse, like LC)
- `| l - pt |` bounded by clock skew; logical part bounds drift.

> **Theorem 4.1 (HLC Monotonicity & Bounded Skew):** HLC is *strictly monotonic* per process even if `pt` steps backward, and `l` stays within `epsilon` of physical time assuming bounded message delay. *Proof sketch*: send path takes `max(l, pt)`, thus non-decreasing; if equal, increments `c`; else resets `c`. Bound follows because `l` can advance beyond `pt` only via message chain where origin's `pt` ahead; transitivity limits to max clock difference observed. ∎

Application to causal stores: **CausalSpartanX** [4] replaces Spanner-like PT waiting with HLC. Operations marked with HLC timestamp. Readers ask for version with `hlc <= snapshot_hlc`. No waiting for uncertainty; visibility delay shrinks because HLC causality ensures if `put(x)` causally before `put(y)`, then `hlc_x < hlc_y` even if PT skewed.

**Advantage over version vectors**: fits in Cassandra `timestamp` column, backwards-compatible with NTP tooling, self-stabilizing after corruption (l resets to pt).

*Italic insight*: ***HLC is superposition on NTP, not replacement — it reads PT, never writes, so other apps using NTP unaffected.***

Table: clock comparison

| Clock | Size | Captures hb? | Close to PT? | Monotonic under NTP kink? |
|-------|------|--------------|--------------|---------------------------|
| Lamport | 64b | one-way | No | Yes |
| Vector | O(N) | exact | No | Yes |
| NTP PT | 64b | No | Yes | **No** |
| TrueTime | interval | No (needs wait) | Yes | Yes but slow |
| **HLC** | 64b | one-way | Yes | **Yes** |

### 4.2 COPS – Scaling Causal+ Across Clusters

COPS key innovation: prior systems (Bayou, PRACTI) enforced causal dependencies **per-server**. If dependency `d = (k2,v2)` stored on server S2, and client writes `(k1,v1) depends on d` to server S1, old design would never check S2 for presence of d. So they limited cluster = 1 server. COPS scales to many servers per DC.

Central approach: **explicit dependency check before exposure**. Each write carries nearest dependencies. Its put coordinator iterates over list, RPC to local servers storing each dependent key: *is key visible?* If not, enqueue retry until satisfied. Only then make write visible and asynchronously replicate to remote DCs.

COPS-GT extension: single-key eventual consistency still shows anomalies for two keys (photo+caption). COPS-GT introduces **get transactions**: client library hides two-round logic similar to later Eiger but simpler — coordinator fetches versions in parallel, pulls dependency context, if missing re-requests.

```go
// Simplified COPS Put Path
func (n *Node) Put(k string, val []byte, ctx DepContext) VersionID {
    deps := nearest(ctx) // transitive reduction
    version := VersionID{dc: n.dc, seq: n.nextSeq(), hlc: n.hlc.Now()}
    // 1. dependency check
    for _, d := range deps {
        for !n.localGet(d.Key).HasVersion(d.VersionID) {
            waitBackoff()
        }
    }
    // 2. make local visible
    n.store(k, val, version, deps)
    // 3. async replicate to other DCs (background)
    go n.replicateToPeers(k, val, version, deps)
    return version
}
```

Complexity: dependency size grows with fan-in; COPS uses garbage collection: once version replicated to all DCs and its dependent set also fully replicated, no need to check. For skewed popular dependencies (celebrity writes), COPS-GT used distributed dependency cleaning with 95% reduction at 10k nodes.

**Limitation**: explicit tracking incurs per-write metadata up to 100 deps; plus write amplification due to blocking waits if DC internally slow. Evaluation [1] shows <1ms latency at 50k ops/sec per cluster, near-linear scaling to 16 nodes.

> **Theorem 4.2 (COPS Causal Safety):** If node only exposes `v` after all `d ∈ dep(v)` locally visible, and replication respects that rule per DC, then if `a hb b`, every client sees `a` before `b` in any DC that sees `b`. Proof by induction on hb length; transitive reduction preserves coverage.

### 4.3 Eiger – From Single Keys to Transactions

Eiger strengthens COPS along column-family abstraction (Facebook `Eiger` built for Graph store).

Data model: `Key -> Column -> value + (EVT, LVT, deps)`. EVT = writer's logical time when applied locally, LVT = logical time after which value overwritten. This **validity period** enables optimistic first round.

**Read-Only Transaction (ROT) Algorithm**:

- Client coordinator picks logical time `?` – actually it doesn't, it reads latest per server in parallel first round.
- Each server returns `value + EVT + deps`. Coordinator computes `maxEVT = max over returned EVT`.
- If for all `r`, `LVT_r >= maxEVT` (?) else inconsistency. More precisely: if any returned value's validity [EVT, LVT) doesn't contain `maxEVT`, then snapshot not causally consistent – need second round.
- Second round re-reads offending keys with `wanted_time = maxEVT` to get version valid at that time.

This yields **at most two rounds**, non-blocking, no locks, single-version per node (servers keep old versions back to configurable GC window, typically minutes).

```
// pseudocode from Eiger §4.1
func ReadOnlyTrans(requests []Key) []Value:
  // round 1 : parallel
  vals = parallel multiget(requests) // returns (val, evt, lvt, deps)
  maxEvt = max(vals[].evt)
  secondRound = []
  for i, v in vals:
      if v.evt > maxEvt or v.lvt < maxEvt:
         secondRound.append(requests[i])
  if len(secondRound)==0: return vals
  vals2 = parallel multiget_at_time(secondRound, maxEvt)
  merge(vals, vals2)
  return final
```

Write-Only Transaction (WOT): atomic multi-key put using two-phase commit inside DC: prepare with dependencies, commit when dependency checks pass. Provides atomicity – crucial for Antidote.

Counter columns: Eiger noticed counters (`+1`) break nearest dependency optimization because many writers affect same value. It collapses to *per-DC at most one dependency* per counter using chain that transitively covers all updates from that DC.

### 4.4 AntidoteDB, Cure, and CRDT Convergence

AntidoteDB implements Cure [5], the first protocol for *highly available transactions* meeting TSP (Transactional, Strongly causal, Partition tolerant). Architecture: per DC sharded N nodes, clients attach to transaction manager (TM). Each shard maintains materialized versions indexed by `commit_time VC` analogous to HLC vector.

Protocol flow:

- **Start Transaction**: client gets `snapshot_time = get_stable_snapshot()` – stable meaning all DCs have replicated up to that VC. This ensures client sees causally consistent snapshot slightly in the past.
- **Read**: read from snapshot or own writes (read-your-writes).
- **Commit**: TM coordinates 2PC across shards: propose commit time = `max(prepare_times, snapshot_time)+1`. If shards can commit (no write-conflict? Cure allows concurrent writes via CRDT semantics), log transaction, make visible locally, async replicate.
- **Causality**: transaction's commit VC includes its snapshot VC; any later transaction that reads its writes will have snapshot >= commit VC, preserving causal order.

**Why CRDTs?** Last-writer-wins loses intent for sets/maps/counters. AntidoteDB offers library of CRDTs: counters, OR-Sets (observed-remove), MV-Registers, LWW-Register optimistic. Operation-based: each update is operation `op` that downstream merges commutative for concurrent ops.

Example OR-Set: add requires unique tag `dot`, remove removes observed adds. Cure's causal snapshot ensures add-remove atomicity without coordination:

```rust
// OR-Set pseudo merge
struct ORSet {
  adds: Map<Element, Set<Dot>>,
  rems: Set<Dot>,
}
fn merge(a: ORSet, b: ORSet) -> ORSet {
  // dot = (dc, seq) unique
  union adds, union rems, then filter
  retained = { (e,dot) | dot in adds && dot not in rems }
  retained
}
```

Antidote's transaction manager ensures **atomic read of multiple CRDTs** – classic example: FK constraint between `user` and `album` map entries.

Vaxine [6] re-implements Antidote concept in Elixir/Rust hybrid, adding rich-CRDT composability for ElectricSQL local-first sync.

> **Theorem 4.3 (Cure Atomic Visibility):** Transactions commit atomically within DC: either all shards' effects visible to readers with snapshot >= commit_time or none. Replication preserves atomicity per DC. *Proof*: 2PC prepare logs ensure all shards agree if coordinator fails? Cure optimization: prepare records held without blocking reads (non-blocking ROTs unaffected). Asynchronous uniform barrier later GCs stable logs.

## 5 Empirical / Proofs

### 5.1 Performance Landscape

Synthesized from evaluations [1][2][5]:

| System | Metadata/write | ROT latency (p95) | Write lat | Throughput scaling | Conflict resolution |
|--------|---------------|-----------------|-----------|--------------------|---------------------|
| COPS | 7-12 deps 30B-100B | single-key <1ms, GT 1.2ms (2 rounds) | <1ms | Linear to 16 nodes | LWW per key |
| Eiger | EVT/LVT 16B + dep chains compressed | 1 RTT (80%) vs 2 RTT 20% ~2ms | 1.5ms (WOT 2PC) | Linear shards | LWW + counters |
| CausalSpartanX (HLC) | 8B HLC scalar | 1 RTT non-blocking | 0.6ms (1 RTT) | Linear | LWW |
| AntidoteDB/Cure | VC O(#DC) 8*D | TCC tx 5-12ms | 6ms (2PC) | Horiz. per DC | **CRDT merge** |

Key insight from Didona et al. [3] latency-optimal paper: ROTs that are single-round, single-version, non-blocking are *latency-optimal* for reads but impose linear metadata growth on writes (clients track dependencies). Eiger/CausalSpartanX trade single-round optimality for 2-round but drastically lower write overhead – crucial when workload 70% read still 30% write sensitive.

### 5.2 HLC Correctness Lemma

> **Lemma 5.1 (HLC hb preservation):** For events e,f: if e hb f then hlc.e < hlc.f lexicographically. *Proof* by case on hb construction: same-process sequential increases c; send-receive takes max ensuring receiver l > send l or equal with increased c; transitive closure propagates via induction.

Counterexample of converse false: concurrent events can have `hlc.e < hlc.f` purely by PT skew, not causality – so HLC safe but conservative.

### 5.3 Convergence Proof Sketch for CRDT over Cure

We show OR-Set embedded in TCC remains convergent.

> **Theorem 5.1**: Replica states converge if all transactions eventually delivered respecting causal order and CRDT merge is join of lattice.
> *Sketch*: Cure ensures causality-respecting delivery per DC via uniform barriers; inter-DC anti-entropy delivers txs in causal order (vector clock comparison). OR-Set join is commutative, associative, idempotent -> state is least upper bound of set of delivered dots (tombstone semantics). Since delivery set eventually equal across correct DCs assuming infinite retransmission, LUB equal => converged.

### 5.4 Visibility Latency Reduction

CausalSpartanX [4] reports using HLC reduces average update visibility lag vs GentleRain (PT-based) by 18% under 50ms inter-DC RTT because HLC less sensitive to clock skew spikes; client-visible staleness drops from 120ms to 80ms at 90th percentile.

## 6 Limitations

1. **Clock bound fragility**: HLC 16-bit logical part overflow at 65k events at same physical ms. At 1M ops/sec per node, bursts exceed bound, requiring wait. Real NTP can jump 100s after VM migration, causing large l jump and artificially delaying future causality checks (although monotonic). Systems must monitor `c` growth and throttle.

2. **Explicit dependency bloat under hot keys**: Celebrity account with 1M followers commenting: each write brings popular deps; even nearest optimization keeps one per DC per key? For highly skewed workloads, dependency size still tens of KB, causing network overhead. Implicit scalar HLC solves but loses precision -> false positives (concurrent considered causal) increasing staleness.

3. **Transaction contention and 2PC within DC**: AntidoteDB's WOT/RW tx inside DC uses 2PC across shards – not geo-roundtrip, but under partition inside DC (rack failure), availability dips. Unlike pure AP ROTs, write availability weakened to single-DC.

4. **CRDT semantic mismatch**: Developers assume *set semantics* but get OR-Set where concurrent add-remove keeps element (add wins) – unintuitive. Composed rich CRDTs (map of sets) amplify complexity; no formal verification linking application invariant to chosen CRDT.

5. **Stability / snapshot recency**: Cure's snapshot is *stable* snapshot, trailing by replication delay (seconds cross-continent). Strong recency users want read-my-writes plus read of latest local writes? Cure provides session guarantees but remote updates stale. Bolton-style exposure adds recency but breaks availability.

6. **GC of old versions**: ROT support requires retaining versions for GC window to serve second-round reads at old `maxEVT`. Memory overhead O(write_rate * window). Tuning window too short -> retry storm.

7. **Security**: Causality metadata leaks causal graph – adversary can infer who read whose updates via dep set inspection. Mitigating via encryption breaks dependency checks.

Open question: Can we achieve latency-optimal 1-round ROTs with O(1) write metadata *without* linear client overhead? Recent Karthik et al. suggests inherent trade-off lower bound: either client state O(#clients) or write overhead linear. So 1.5-round compromise may be pareto-optimal.

## 7 Conclusion

Causal consistency's sweet spot – *always available, no waiting, yet intuitive causal order* – requires disciplined engineering of time, dependency, transaction, and datatype.

We traced evolution:

- **HLC** solves timestamping: close to wall-clock for operators, logical for causality, 64-bit, self-stabilizing, NSP-independent predecessor to TrueTime-like waiting.
- **COPS** solves scalability: cluster-wide dependency check converts single-server causal to sharded store, proving causal+ achievable at scale with explicit deps and get transactions.
- **Eiger** solves transactions: validity-interval metadata yields non-blocking, lock-free read-only transactions in at most two RTTs, plus write-only atomic batches, supporting foreign-key-like invariants.
- **AntidoteDB/Cure** solves convergence and programmability: transactional snapshot past plus CRDT merge yields TCC+ where developers program with counters/sets/maps without LWW data loss.

Combined architecture for next-gen edge: Use HLC scalar commit markers, compressed explicit deps for hot-path, Eiger-style validity for snapshot reads, Cure 2PC inside region for atomic multi-shard, CRDT merge downstream. Weighting *latency vs precision vs recency* per application.

> **Final Invariant**: *In any ALPS system, causality tracking cost cannot vanish — it migrates between clock bits, dependency lists, validity intervals, or version vectors. Engineering is choosing where to pay.*

Future directions: HLC hybrid with vector-clock summary for precise causality but small size (e.g., dotted version vectors), CRDT-aware transaction validation eliminating 2PC in CRDT-only transactions, and formal EPTL verification of access control under causal consistency shown by Bieniusa et al.

The strongest achievable model deserves strongest synthesis.
