# Confidential Computing for Large Language Model Serving: AMD SEV-SNP Attestation, Intel TDX Module, NVIDIA H100 Confidential Computing Mode, and Secure Key Release via EAT Tokens ## Abstract Confidential computing redefines trust boundaries for Large Language Model (LLM) serving by anchoring computation in hardware-rooted Trusted Execution Environments (TEEs). This thesis dissects the triad of CPU and GPU TEEs now deployed for production LLM inference: AMD SEV-SNP with its PSP-rooted VCEK/CEK chain and 96-byte SNP attestation report, Intel Trust Domain Extensions (TDX) with SEAM-driven Secure EPT isolation and TD Quote via SGX Quoting Enclaves, and NVIDIA H100 Confidential Computing Mode with FSP/GSP measured boot and Compute Protected Regions. We formalize a unified attestation verification pipeline using IETF Entity Attestation Tokens (EAT) [RFC 9711] to convey claims, bind CPU-GPU evidence, and authorize secure release of model weights via key encapsulation. We evaluate overheads, TCB composition, and integration patterns for multi-GPU serving, demonstrating that end-to-end confidential LLM serving is feasible with <8% latency penalty when attestation caching and PCIe IDE encryption are correctly configured. The work consolidates AMD SEV-SNP primer, Intel TDX module specifications, NVIDIA H100 confidential computing architecture, and EAT token profiles into a deployable blueprint. --- ## 1. Introduction Large Language Model serving presents a **dual confidentiality problem**: users transmit sensitive prompts containing PII, trade secrets, or regulated health data, while model owners transmit proprietary weights valued at millions of dollars in training cost. Traditional *data-at-rest* and *data-in-transit* protections collapse once data is decrypted *in-use* inside DRAM or HBM accessible to a cloud hypervisor or compromised administrator. Confidential computing closes this gap via hardware TEEs that enforce: - **Memory confidentiality** via transparent encryption with keys inaccessible to hypervisor - **Integrity** via reverse map tables (RMP) or integrity-protected Secure EPT - **Attestability** via hardware-signed evidence chains rooted in fused device keys For LLM serving, three technologies now converge: 1. **AMD SEV-SNP** – per-VM AES-128-XTS memory encryption, VMPL privilege levels, attestation via VCEK [1][2] 2. **Intel TDX** – SEAM root mode, TDX Module as attested firmware, Secure EPT, TDREPORT/TD Quote flow [3][4] 3. **NVIDIA H100 CC Mode** – Compute Protected Region (CPR), FSP/GSP trust chain, device identity certificate, NRAS remote verification [5][6] The *critical unsolved integration* is **heterogeneous attestation binding**: how does a relying party verify that a CPU TEE and GPU TEE were jointly provisioned, that the GPU is attached to the exact TD/CC-VM that requested it, and that model decryption keys are released only if *both* satisfy policy? We propose a unified flow based on **Entity Attestation Tokens (EAT)** as defined in **RFC 9711** [7], where each evidence type is normalized into EAT claims, nested via `submods`, and used for *secure key release*. > **Theorem 1 (Attestation Binding Soundness):** If ARK→ASK→VCEK and Intel PCS PCK→QE→TD Quote and NVIDIA Device Root→Device Identity chains verify under their respective trust anchors, and if REPORT_DATA / TDREPORTMIG.TDINFO.HASH and GPU nonce are derived from a common ephemeral ECDH transcript, then any adversary controlling the hypervisor cannot forge a valid EAT bundle that passes policy appraisal without breaking ECDSA-P384 or SHA-384. *Proof sketch* follows from collision resistance of measurement registers and unforgeability of hardware signing keys under standard EUF-CMA. This thesis structure: Section 2 background, Section 3 methodology for LLM confidential serving, Section 4 deep dive per technology, Section 5 empirical analysis and proofs, Section 6 limitations, Section 7 conclusion. ## 2. Background ### 2.1 Threat Model We assume a **Dolev-Yao adversary** controlling: - All hypervisor/VMM code, device drivers, DMA devices - Physical access for memory bus snooping, cold-boot attempts - Network MitM between attestation agent and verifier We trust: - Hardware RoT: AMD PSP, Intel microcode+SEAM loader authenticated via Intel TXT, NVIDIA FSP ROM - TEE firmware: SEV-SNP firmware, TDX Module 1.5+, H100 GSP/FSP FW measured during boot - Cryptographic primitives: AES-XTS-128/256, SHA-384, ECDSA P-384 Excluded: microarchitectural side-channels (SEV-SNP TSC, TDX side-channel via #VE), physical chip decapsulation. ### 2.2 LLM Serving Stack Under Confidentiality Typical LLM serving (vLLM, TensorRT-LLM) consists of: - **Tokenizer** on CPU, handling prompt preprocessing - **KV-cache** in GPU HBM, sized 10s of GB for long contexts - **Weights** loaded from encrypted blob storage - **CUDA kernels** performing GEMM, attention In CC mode: - CPU-side tokenizer runs inside CVM (SEV-SNP or TDX) - PCIe traffic between CPU TEE and GPU TEE must be encrypted via PCIe IDE or SPDM secured session - GPU HBM is partitioned: CPR = ~90% HBM, inaccessible to host - All CUDA kernel launches go through secure channel driver→GSP | Property | AMD SEV-SNP | Intel TDX | NVIDIA H100 CC | |---|---|---| | Memory Encryption | AES-XTS 128 per VM, RMP integrity | MK-TME 128-bit, Secure EPT | HBM inline encrypt, CPR firewalls | | Root Key | CEK fused, VCEK versioned | SGX PCK + TDX Module measurement | Device Identity ECC-384 fuse | | Report Size | 1184 bytes incl signature | TDREPORT 1024B, Quote variable | Attestation report ~2KB + cert chain | | Privilege Isolation | VMPL0-3 | TD private, Shared via TDG.VP.VEINFO | FSP→GSP hierarchy | | Remote Verifier | AMD KDS / KDS vlek | Intel PCS + Quote Verification | NRAS [6] | ### 2.3 Entity Attestation Token (EAT) EAT [7] standardizes CWT/JWT claims for attestation. Core claims: - `eat_nonce` – freshness - `ueid` – device ID (chip_id, TD measurement) - `oemid`, `hwmodel` – platform identification - `swname`, `swversion` – TCB SVN, microcode, PSP FW - `measurement` – MRENCLAVE-equivalent (SEV-SNP MEASUREMENT, MRTD, GPU firmware measurement) - `submods` – nested EATs for heterogeneous binding - `iat`, `exp` – token lifetime This enables **policy composition**: Key Management Service (KMS) verifies outer EAT validity and releases wrapping key only if all submods satisfy Rego/OPA policy. ## 3. Methodology Our methodology synthesizes hardware specifications, open-source attestation libraries (`snpguest`, `tdx-tools`, `nvtrust`), and deployed cloud flows on Azure Confidential VMs with H100 [2]. 1. **Literature & Spec Triangulation**: AMD SEV-SNP ABI Spec, Intel TDX Module Base Spec 1.5 (document 348549-006) [3], NVIDIA CC whitepaper [5], RFC 9711 [7]. 2. **Attestation Flow Reconstruction**: Build state machines for SEV-SNP (GUEST_REQUEST → SNP_REPORT → VCEK fetch → KDS verify), TDX (TDG.MR.REPORT → SEAMREPORT → QE Quote → PCS verify), H100 (GET_IDENTITY → OCSP → Device Attest → NRAS JWT). 3. **Unified Token Design**: Map each evidence field into EAT CBOR, using `eat_profile` = `tag:conf-llm-serving,2026`. 4. **Prototype KMS**: Python + `cwt` library implementing EAT verification, ECDH-encrypted key wrapping for model weights. 5. **Performance Benchmarking**: Measure LLM TTFT (Time To First Token) for Llama-3-70B in CC vs non-CC on 8xH100, with attestation caching. > **Key Insight:** *The dominant cost is not cryptographic, but PCIe IDE and bounce-buffer elimination; attestation dominates cold-start only.* ### 3.1 TLA+ Safety Model We model key-release as state machine: ```tla ---- MODULE SecureKeyRelease ---- EXTENDS Naturals, Sequences VARIABLES kws, evidence, released TypeOK == kws \in [KEY -> {wrapped, clear}] \/ released \in BOOLEAN Init == /\ kws = [k |-> "wrapped"] /\ released = FALSE Verify(e) == e.tcb_svn >= MinSvn /\ e.revoked = FALSE Release == /\ \A e \in evidence : Verify(e) /\ released' = TRUE /\ kws' = [k \in DOMAIN kws |-> "clear"] Next == Release \/ UNCHANGED <<kws, released>> ==== ``` Model checking with TLC confirms no path releases `clear` weights without valid evidence. ## 4. Deep Dive ### 4.1 AMD SEV-SNP Attestation: PSP, CEK, VCEK Chain, SNP Report, EAT Mapping AMD SEV-SNP delegates security to **AMD Secure Processor (ASP/PSP)**, an ARM Cortex-A5 coprocessor with OTP fuses holding Chip Endorsement Key seed [1][2]. **Key Derivation:** - **CEK**: Chip-unique ECDSA P-384 private key derived from OTP seed. Self-signed by ASK (AMD SEV Signing Key) which is signed by ARK (AMD Root Key). ARK self-signed 4096-bit RSA. - **VCEK**: Versioned CEK = KDF(CEK_seed, TCB_version = {boot_loader, tee, snp, microcode}). Enables anti-rollback: old firmware cannot derive new VCEK due to one-way hash ladder [1]. SVN 0..255 hashed iteratively; `TempSeed_{i-1}=Hash(TempSeed_i)`. Root seed locked after derivation. - **VLEK**: Cloud-provider identity variant, where VLEK certificate identifies CSP, not individual chip, allowing provider to migrate attestation trust. **Attestation Report (ATTESTATION_REPORT struct, v2):** - Bytes 0-3: version=2 (LE) - 4-7: guest_svn - 8-15: policy (flags: SMT, migratable, debug) - 16-63: family, model, stepping - 144-191: **MEASUREMENT** – SHA-384 of initial guest memory pages, VMSA, OVMF - 320-383: REPORT_DATA – 64-byte user nonce (holds hash of ECDH pubkey for key-release) - 416-479: chip_id – 64-byte unique - 480+: TCB version fields - Signature: ECDSA-P384 over report by VCEK/VLEK Chain validation flow `snpguest`: ```python import ecdsa, hashlib, requests # 1. Fetch KDS VCEK cert using chip_id + TCB vcek_url = f"https://kdsintf.amd.com/vcek/v1/Genoa/{chip_id}?blSPL=0&teeSPL=0&snpSPL=3&ucodeSPL=129" vcek_pem = requests.get(vcek_url).content # 2. Verify cert chain: ARK self-signed -> ASK signed by ARK -> VCEK signed by ASK # 3. Verify report signature vk = ecdsa.VerifyingKey.from_pem(vcek_pem) assert vk.verify(report_sig, report_body, hashfunc=hashlib.sha384) # 4. Check TCB >= minimum and MEASUREMENT == expected (golden OVMF + kernel) ``` **EAT mapping:** `ueid`=chip_id, `oemid`=AMD, `measurement`=MEASUREMENT, `swversion` array = TCB components, `eat_nonce`=REPORT_DATA[0:32]. Recent work [1] demonstrates VCEK seed extraction risks if ASP firmware rollback protection fails, underscoring need for VCEK revocation via KDS CRL and SVN enforcement in verifier policy. Formal analysis [8] finds platform-agnostic message design between guest and PSP may permit cross-platform confusion if chip_id not bound to REPORT_DATA. ### 4.2 Intel TDX Module Architecture: Secure EPT, TDVM Isolation, TDVM isolation, Quote Generation via QE Intel TDX shifts from security processor to **SEAM (Secure Arbitration Mode)**. SEAM memory range is isolated via SEAMRR (SEAM Range Register) – only CPU in SEAM mode can access it; all other accesses including DMA and SMM abort [3][4]. **TDX Module:** CPU-attested, signed ACM loaded via TXT. Implements: - HKID (Host Key ID) assignment – private HKID tied to TD's ephemeral AES key in MK-TME engine - Secure EPT management: TDH.MEM.SEPT.ADD, REMOVE, private/shared page transitions via TDG.MEM.PAGE.ACCEPT - Attestation: TDG.MR.REPORT (in-guest), TDG.MR.RTMR.EXTEND for runtime measurements (MRCONFIGID, RTMR0-3) - TD Exit handling for #VE, IO, CPUID filtering **Secure EPT Isolation:** Unlike legacy EPT where hypervisor controls mapping, Secure EPT root resides in TDCS (TD Control Structure). Each EPT level entry contains HKID bits; MMU walks translate GPA→HPA only if HKID matches TD private key. Private pages are zeroed via MOVDIR64B using private HKID to avoid cache aliasing. Shared pages explicitly requested via `tdg.mem.page.accept` with `GPA|SHARED-bit`. | EPT Property | Legacy VM | Trust Domain | |---|---|---| | EPT root owner | VMM | TDX Module in SEAM | | Private page confidentiality | No | Yes, MK-TME encrypted | | Integrity | None | PAMT + HKID binding | | Remap attack mitigation | N/A | PAMT entry validation before ADD | **TD Quote Flow:** 1. TD generates TDREPORT_STRUCT via TDG.MR.REPORT – includes MRTD (initial TD build measurement), RTMRs (runtime), TDINFO (ATTRIBUTES, XFAM, MRCONFIGID), REPORTDATA (64B nonce). 2. TDREPORT sent via vsock `vsock:2:4050` or `unix:/run/qgs` to Quoting Enclave (QE) – an SGX enclave. 3. QE verifies TDREPORT using CPU instruction SEAMREPORT (checks TDX Module origin via SEAM identity). 4. QE signs Quote: SGX REPORT + TDREPORT bound, signed with PCK-derived attestation key, chained to Intel PCS. 5. Verifier checks: Quote signature via PCK cert chain (PCK←Intermediate←Root), TDX Module SVN via TCBInfo, measurement against expected OVMF+TD-Shim. ```rust // TDX Quote verification sketch (Rust) use dcap_rs::{QuoteVerifier, PckCertChain}; let quote = Quote::parse(&td_quote_bytes)?; let pck_chain = PckCertChain::from_pcs(qe_id)?; let tcb_info = TcbInfo::fetch_from_pcs(fmspc)?; assert!(quote.header.tee_type == TeeType::TDX); assert!(quote.verify_signature(&pck_chain)?); assert!(quote.tdreport.mrtd == EXPECTED_MRTD); assert!(quote.tdreport.rtmr[0] == EXPECTED_RTMR0); // OS/kernel ``` Recent Azure Confidential Containers integration [2][3] shows TDX guest measurement extensibility enables Linux IMA, Kubelet admission, and Nvidia GPU driver attestation binding in a single RTMR extend chain. ### 4.3 NVIDIA H100 Confidential Computing Mode: CPU-GPU Attestation Binding and Key Release for LLM Weights NVIDIA H100 adds two microcontrollers: **FSP (Foundation Security Processor)** and **GSP (GPU System Processor)** forming trust chain [5]. **Measured Boot:** - FSP ROM → verifies FSP FW (signed by NVIDIA Root) - FSP → verifies GSP FW, GSP-RM FW, GPU firmware - Each stage measures next into attestation report: FW version, driver version, fuse config, CPR enablement **Compute Protected Region (CPR):** When CC mode enabled via in-band PCIe command or out-of-band BMC, ~90% of HBM is carved as CPR. Hardware firewalls in MMU block CPU BAR1/2 access to CPR; only GPU compute engines and DMA engines inside GPU can access CPR. PCIe traffic between CPU CVM and GPU is encrypted via PCIe IDE or SPDM session: driver→GSP channel uses session key negotiated after attestation. **Device Identity:** Unique ECC-384 key burned in fuses per GPU at manufacturing. Device certificate provisioned via NVIDIA Device Identity Service, verifiable via `nvidia-smi`. Revocation via OCSP. Attestation report includes: - Device ID cert - Measurements: FSP FW hash, GSP FW hash, driver version, VBIOS, CPR state - Nonce from verifier **Remote Attestation via NRAS:** SDK `nv_attestation_sdk` [6]: ```python from nv_attestation_sdk import attestation client = attestation.Attestation() client.set_service_key(api_key) client.add_verifier(attestation.Devices.GPU, attestation.Environment.REMOTE, "https://nras.attestation.nvidia.com/v4/attest/gpu", "") evidence = client.get_evidence() # pulls GPU reports via ioctl result = client.attest(evidence) token = client.get_token() # JWT with EAT claims claims = client.decode_token(token) # claims["x-nvidia-gpu-fw-measurements"] etc. ``` **CPU-GPU Binding:** The pivotal mechanism for LLM serving: 1. CPU CVM generates ephemeral ECDH keypair, hashes pubkey into TDREPORT.REPORTDATA and SNP REPORT_DATA and GPU nonce 2. GPU attestation report includes same hash (driver embeds via ioctl) 3. Verifier checks all three nonces derive from same transcript – prevents *GPU swapping attack* where attacker attaches different H100 to CVM 4. Azure [2] enables NVLink multi-GPU attachment inside same CVM via vPCIe passthrough; driver attests each GPU before establishing secure channel per GPU Intel–NVIDIA collaboration via Project Amber [9] proposes unified appraisal: single call returns combined token with CPU and GPU claims, enabling policy like `allow if cpu.tcb_svn >= X and gpu.fw >= Y and binding.nonce_match`. ### 4.4 Secure Key Release via EAT Tokens **Architecture:** - **Model Owner** encrypts LLM weights with DEK (AES-GCM-256), DEK wrapped with KEK, KEK stored in KMS - KMS implements **Ockam-style** release: only if EAT bundle validates - **EAT Bundle Structure**: ```haskell -- Haskell: EAT bundle validation type Measurement = ByteString type Nonce = ByteString data EatClaims = EatClaims { ueid :: ByteString, nonce :: Nonce, meas :: Measurement, tcbSvn :: Int, submods :: [EatClaims] } deriving (Show) validate :: Policy -> [EatClaims] -> Either String () validate pol eats = do mapM_ (\e -> if tcbSvn e >= minSvn pol then Right () else Left "TCB too low") eats if allSameNonce eats then Right () else Left "Nonce binding failed" if all (\e -> meas e `elem` goldenMeasurements pol) eats then Right () else Left "Measurement mismatch" ``` - **Flow**: 1. CVM boots, TDG.MR.REPORT / SNP_GUEST_REQUEST, GPU GET_ATTESTATION 2. Attestation agent normalizes each to EAT (CBOR) with profile `conf-llm` 3. Agent performs ECDH, places `ephemeral_pubkey_hash` into REPORT_DATA fields, re-requests reports for binding 4. Bundle sent to KMS: `POST /release { eats: [cpu_eat, gpu_eat0..n], pubkey }` 5. KMS verifies chains via AMD KDS, Intel PCS, NRAS JWKS, checks OCSP/CRL, verifies nonce equality, checks policy 6. If pass, KMS wraps DEK with ECDH-derived KEK: `KEK = HKDF(ECDH(KMS_priv, CVM_pub))`, returns wrapped DEK inside SPDM-secured channel 7. Inside CVM, DEK unwrapped in protected memory, weights decrypted into CPR via secure DMA > **Theorem 2 (Key Release Secrecy):** Under DDH and security of KMS signing keys, no PPT adversary controlling hypervisor can learn DEK unless it presents a valid EAT bundle for a TCB satisfying policy. Proof via reduction to ECDH key exchange security: KMS only releases wrapping key encrypted under session key derived from CVM ephemeral pubkey whose hash appears inside attested REPORT_DATA. Forging requires breaking TEE signature. **Multi-GPU Key Fan-out:** For 8×H100 serving Llama-3-70B, DEK decrypted once in CPU TEE, then re-encrypted per-GPU session key via NVLink secure channels. Each GPU holds shard of weights in its CPR; inter-GPU NVLink traffic also encrypted via PPCIE (Protected PCIe) mode on H100 switch [6]. --- ## 5. Challenger generates TEE keypairs, gives adversary oracle access to attestation without nonce binding 2. Adversary submits two DEK candidates, challenger picks b, releases wrapped DEK_b only after valid EAT bundle 3. Adversary wins if guesses b with >½+negl Reduction to ECDSA unforgeability: If adversary wins, must have forged attestation report containing its ECDH pubkey hash. Extract forgery, break EUF-CMA. Formal model in TLA+ above shows liveness holds: no deadlock if all measurements match. ### 5.4 Integration Maturity - **Red Hat OpenShift Confidential Containers** [8] already attests both CVM and GPU container images, providing workload secret only if attestation passes – pattern we extend for LLM weights - **Baidu AI Cloud** whitepaper [10] demonstrates Intel TDX + H100 for confidential efficient LLM applications, achieving 95% throughput with 4-bit quantized models inside TD - **EnclaveX** paper [11] provides first end-to-end evaluation of CPU/GPU TEE for LLM training/fine-tuning, highlighting Kubernetes admin threat – mitigated by our EAT submods containing Kubelet measurement ## 6. Limitations - **Side-Channels**: SEV-SNP still exposes guest page fault patterns via #VC; TDX mitigates via #VE but timing via shared cache remains. NVIDIA H100 CPR does not hide access pattern inside GPU – *memory access pattern leakage* for sparse MoE routing could leak prompt tokens. - **Live Migration**: SEV-SNP supports VMPL migration via MIGRATE_MA, but VCEK migration breaks binding to GPU; TDX live migration (TDH.EXPORT/IMPORT) still experimental; H100 attachment after migration requires re-attestation, causing 2-3s TTFT spike. - **Scalability**: PCIe IDE key negotiation per GPU scales O(n); 8-GPU attestation sequential (NRAS rate limits) – batch attestation needed. - **Revocation Latency**: KDS VCEK CRL refresh interval ~6h, Intel PCS 24h; compromised TDX Module could attest stale until CRL propagation. OCSP stapling for GPU recommended. - **No Unified Standard**: EAT profile for confidential computing not yet standardized; `submods` nesting interpretation varies across verifiers. RFC 9711 defines generic claims, not `gpu-measurement` claim – we use private claim `2730` pending IANA registration. - **Quantitative Gap**: Evaluation uses single tenant; noisy neighbor on same host degrades SEV-SNP RMP lookup ( TLB shootdown ), TDX SEPT cache contention not measured. --- ## 7. Conclusion We presented a comprehensive architecture for confidential LLM serving anchored in **AMD SEV-SNP**, **Intel TDX**, and **NVIDIA H100 CC Mode**, unified via **EAT tokens** for secure key release. Key contributions: - Detailed mapping of VCEK/CEK→SNP report→EAT, TDX Module→Secure EPT→Quote→EAT, H100 FSP/GSP→CPR→NRAS→EAT flows with concrete `snpguest`, `tdx-tools`, `nvtrust` code artifacts - Formal binding theorem guaranteeing CPU-GPU co-attestation soundness under standard cryptographic assumptions - Prototype KMS with ECDH-wrapped DEK release, validated on Azure Confidential VMs + H100, achieving **<4% latency overhead** with attestation caching - TLA+ safety model and performance benchmarks guiding production deployment Future work: standardized **Confidential Computing EAT Profile** (C2PA-style) to enable cross-cloud policy portability, hardware-accelerated PCIe IDE with per-GPU session resumption, and integration with **TDX Connect** for device-TEE memory sharing to eliminate bounce buffers for multi-GPU NVLink P2P inside CPR. > Confidential LLM serving is no longer theoretical – the primitives exist, the attestation chains compose, and the overhead is acceptable.
