# Ownership Types and Memory Safety: Linear Logic, Borrow Checking, and the Formal Semantics of Rust

## Abstract

Rust's ownership and borrow discipline constitutes the most ambitious deployment of substructural type theory in a production programming language: memory safety and data-race freedom are guaranteed statically, without garbage collection, by treating every value as an *affine resource* that is owned, moved, or borrowed under compiler-checked rules. This article traces the intellectual lineage of that discipline from Girard's linear logic (1987) — where the structural rules of weakening and contraction are made explicit and controlled — through ownership-type research to the three modern formal accounts of Rust: Oxide's syntactic type system with progress and preservation, RustBelt's semantic typing in Iris over the λRust calculus, and the operational aliasing models of Stacked Borrows and Tree Borrows. We formalize the alias-XOR-mutability invariant, explain non-lexical lifetimes as liveness-driven region inference, analyze reborrowing and interior mutability as principled relaxations of affinity, and survey the machine-checked verification of standard-library abstractions that encapsulate `unsafe` code. We conclude with the open problems — the undecided aliasing model, borrow-checker incompleteness, and foreign-function boundaries — that delimit the frontier of ownership-based memory safety.

##1 Introduction

Memory-unsafe behavior — use-after-free, double-free, buffer overruns, data races — has driven a majority of severe software vulnerabilities for decades. The conventional cures are garbage collection (automatic reclamation at the cost of runtime overhead and weak resource reasoning) and manual management (control at the cost of exactly the bugs collection was invented to prevent). Rust proposes a third way: the compiler tracks the *ownership* of every value, enforces that each value has exactly one owner, and permits temporary access through *borrows* whose lifetimes are statically verified — memory safety and thread safety without a garbage collector [6].

What makes this remarkable from a programming-languages perspective is that Rust's discipline is not an ad-hoc lint but a rediscovery — at industrial scale — of ideas from *substructural logic*. In classical logic, a hypothesis may be used zero times (weakening) or duplicated arbitrarily (contraction). Linear logic, introduced by Jean-Yves Girard in 1987, removes these structural rules by default and reintroduces them only under the explicit exponential modality `!`, so that a proof literally consumes its premises [1]. Under the Curry–Howard correspondence, linear logic is a type system in which values cannot be silently discarded or copied: they must be *used exactly once*. Rust's ownership system is, in essence, an *affine* variant of this idea — weakening is permitted (a value may be dropped), contraction is not (a value may not be implicitly duplicated) — extended with a rich theory of *borrowing* that has no direct linear-logic antecedent and which required genuine new research to formalize [2][3]. First, to make the linear-logic foundations of ownership precise: affine types, the `!` modality as the logical content of `Copy`, and lifetimes as regions. Second, to explain how the borrow checker works as an algorithm — liveness analysis over the Mid-level Intermediate Representation (MIR), non-lexical lifetimes, and the constraint systems of Polonius. Third, to survey the *semantic* side of the story: because Rust contains `unsafe` escape hatches, the safety of the ecosystem rests on formal models — RustBelt's logical-relations proof in Iris, Oxide's syntactic soundness, and the Stacked Borrows / Tree Borrows operational models of aliasing — that pin down what "memory safe" means when unsafe code is in play [2][4][5].

##2 Background

**From linear logic to affine ownership.**

Girard's linear logic decomposes the intuitionistic implication `A → B` into `!A ⊸ B`, separating the *reusable* (modal) from the *consumable* (linear) [1]. A linear function `A ⊸ B` consumes its argument exactly once; `!A` marks a value that may be duplicated or discarded at will. The proof theory is resource-conscious: the context is a multiset, and the rules of weakening and contraction are available only for formulas under `!`.

Rust's type system is the programming-language shadow of this proof theory. Every type is *affine* by default: a value may be used at most once — it is *moved* — and may also be silently dropped (weakening without contraction). The `Copy` trait is the programmer-visible face of Girard's `!`: only `Copy` types may be duplicated, and the compiler inserts the duplication explicitly rather than permitting ambient contraction. The slogan "values are resources" is enforced operationally: moving a value out of a variable *invalidates* the source binding, and the borrow checker rejects any subsequent use.

```rust
let s: String = String::from("linear");
let t: String = s;        // move: ownership of the heap buffer transfers
// println!("{}", s);     // ERROR: use of moved value — contraction denied
println!("{}", t);        // fine: the resource was consumed exactly once
```

Ownership types predate Rust — notably Clarke, Potter, and Noble's work on alias protection — but Rust made ownership the *memory-management* discipline itself and added *borrowing*: temporary, scoped, compiler-tracked aliases under a strict invariant.

**The borrowing rules.**

The borrow checker enforces two interlocking rules, often summarized as *alias-XOR-mutability*:

> **Theorem:** (Alias-XOR-Mutability, informal). At any program point, for every live memory location, either there is exactly one live mutable borrow and no other borrows, or there are zero mutable borrows and any number of live shared borrows. Well-typed safe Rust programs preserve this invariant at every step.

Shared borrows (`&T`) permit aliasing but forbid mutation; mutable borrows (`&mut T`) permit mutation but must be unique. This invariant is what licenses the compiler's alias analysis and what the formal models must reconstruct in the presence of `unsafe` [4].

**Lifetimes as regions.**

Every borrow carries a *lifetime* — an abstraction of the program region during which the borrow may be used. The borrow checker assigns lifetimes by solving constraints: a borrow `&'a x` is valid only if `'a` is contained in the region where `x` is live and every use of the borrow falls inside `'a`. Oxide recasts this idea elegantly, viewing lifetimes as *approximate provenances* — sets of memory locations a reference may point to — computed by a flow-sensitive substructural typing judgment [3].

Since Rust 2018, lifetimes are *non-lexical* (NLL): a borrow's region ends at its last use, not at the end of its enclosing block, which the compiler computes via liveness analysis over MIR [6]. This removed a large class of false rejections and brought the implementation closer to the semantic ideal of "a borrow is live exactly where it is used."

| System | Duplication | Discard | Aliasing | Mutation | GC |
|---|---|---|---|---|---|
| Classical types (Java/C#) | unrestricted | unrestricted | unrestricted | unrestricted | required |
| Linear types (affine) | denied | allowed (affine) / denied (linear) | restricted | — | unnecessary |
| Rust ownership | `Copy` only | allowed (drop) | alias-XOR-mutability | via `&mut` uniqueness | unnecessary |
| C++ RAII / move semantics | opt-in (`=delete`) | destructors | unrestricted | unrestricted | optional |

##3 Methodology

Studying Rust's ownership discipline requires three complementary methods, because no single formalism captures the whole language: the *surface* borrow checker (what the compiler accepts), the *semantic* model (what unsafe code must respect), and the *operational* aliasing model (what optimizations may assume).

**Syntactic type safety (Oxide).** Weiss, Patterson, Matsakis, and Ahmed's Oxide is a formalized core language close to source-level Rust with fully annotated types [3]. Rather than embedding the semantics in a program logic, Oxide proves type safety the classical way — *progress and preservation* — over a small-step operational semantics, with lifetimes as *regions* (sets of locations) and a novel region-based alias-management judgment that computes provenances automatically. Because the metatheory uses conventional tools rather than separation logic, Oxide is the most approachable foundation for source-level reasoning about borrow checking, and it was the first to give a syntactic account including non-lexical lifetimes.

**Semantic typing (RustBelt).** Jung et al.'s RustBelt defines what types *mean* — a semantic interpretation of Rust types as predicates in the Iris higher-order concurrent separation logic — over λRust, a core calculus in continuation-passing style close to MIR [2]. A library is "well-typed" if its operations satisfy the semantic interpretation of their types; this yields an extensible *soundness criterion for unsafe code*: any library whose unsafe implementation meets the semantic model is a safe extension of the language. The RustBelt project page maintains the Coq development and the list of verified libraries [8].

**Operational aliasing models (Stacked Borrows, Tree Borrows).** Where RustBelt says what types mean, Stacked Borrows says what *pointer accesses* mean at runtime: every memory location carries a *stack* of borrow items tagged `Unique` or `SharedReadOnly`, each access must find its tag on the stack and pops incompatible items above it, and violations are *undefined behavior* [4]. The model is implemented in Miri, the Rust interpreter, so it is executable: running a test suite under Miri dynamically checks conformance. Tree Borrows, its successor, replaces the stack with a *tree* of permissions (`Reserved`, `Active`, `Frozen`, `Disabled`), accepting strictly more real-world unsafe code while retaining the optimizations the model exists to justify [5].

Our exposition proceeds by aligning these three views on the same phenomena — moves, borrows, reborrows, and interior mutability — and noting where they disagree, since the disagreements mark genuine open problems.

##4 Deep Dive

###4.1 Affine Types as Linear Logic Without Contraction

The Curry–Howard reading of ownership is sharpest for the fragment without borrowing. Consider the linear λ-calculus typing rules:

```
Γ ⊢ e : A        x ∉ dom(Γ)
───────────────────────────── (lin-var, use-once)
Γ, x:A ⊢ x : A

Γ, x:A ⊢ e : B
──────────────── (⊸-intro)
Γ ⊢ λx. e : A ⊸ B
```

Rust's move semantics is the affine relaxation: the variable rule permits *dropping* (weakening) but the application rule still forbids *duplication* (contraction). In Haskell's linear-types extension this is written explicitly:

```haskell
-- Linear Haskell (GHC): the multiplicity annotation 1 enforces use-once
consume :: String %1 -> IO ()
consume s = putStrLn s   -- s cannot be used again after this

-- The unrestricted arrow is recovered with the ! modality:
dup :: String %Many -> (String, String)   -- %Many ≈ Girard's !
```

Rust's `Copy` is precisely `%Many`/`!A`: `i32: Copy` means the value may be duplicated freely, while `String` (affine) may not. `Clone` is the *explicit*, potentially expensive duplication that linear logic would write as a function `!A ⊸ A ⊗ A` — duplication as an operation, never as an ambient structural rule. This correspondence explains why the borrow checker feels alien to programmers raised on classical type systems: it enforces a *resource* discipline, and resources obey conservation laws.

*Drop order* is the dynamic face of affinity. Because an affine value is consumed exactly once — by move or by drop — the compiler schedules destructors deterministically at the end of the owner's lifetime. RAII falls out of affinity for free: `Drop::drop` is the elimination rule for the affine resource, guaranteed to run exactly once.

###4.2 The Borrow Checker as a Constraint Solver

The modern borrow checker (NLL, and its successor-in-development Polonius) does not "check scopes"; it solves constraints over a control-flow graph. For each program point `P` in MIR, the analysis computes:

1. **Loans**: the set of borrows created, each `&'a mut x` or `&'a x` introducing a *loan* on the borrowed place.
2. **Liveness**: the set of loans *live* at `P` — created on some path to `P` and used on some path from `P`.
3. **Conflicts**: a mutable loan conflicts with any other loan on overlapping places; the borrow checker reports an error if two conflicting loans are simultaneously live.

In Polonius's Datalog formulation, these become relations over `Origin` (region variables), `Loan`, and `Point`:

```
live_at(Origin, Point) :- loan_issued_at(Loan, Point),
                          origin_contains_loan(Origin, Loan),
                          loan_live_at(Loan, Point).
error(Point) :- loan_live_at(L1, Point), loan_live_at(L2, Point),
                conflicts(L1, L2).
```

Non-lexical lifetimes are the observation that `loan_live_at` should be driven by *dataflow liveness* rather than lexical scope: a borrow dies at its last use. This single change — shipped in Rust 1.31 alongside the 2018 edition [6] — accepted a large class of previously rejected programs, such as conditional reborrowing and early-release patterns, without weakening any guarantee.

**Two-phase borrows** are the subtlest algorithmic feature: in `v.push(v.len())`, the mutable borrow of `v` for `push` must not conflict with the shared borrow of `v` for `len()`. The checker splits the mutable borrow into a *reservation* phase (which permits shared reads) and an *activation* phase (beginning at the call). Tree Borrows later gave this a semantic counterpart: every mutable reference starts `Reserved` and claims `Active` status only on its first write [5].

###4.3 Reborrowing, Variance, and the Alias-XOR-Mutability Invariant

*Reborrowing* is the mechanism by which `&mut` references compose: passing `&mut *x` to a function that expects `&mut T` creates a new borrow derived from the original, and the original is *frozen* until the reborrow expires. Semantically, reborrowing is what Stacked Borrows models with its push/pop discipline: creating `let y = &mut *x` pushes a new `Unique` item tagged for `y`; using `x` again requires popping `y`'s item, which is legal only if `y` is dead [4][7].

```rust
fn main() {
    let mut x: i32 = 0;
    let a: &mut i32 = &mut x;   // borrow #1: x frozen
    let b: &mut i32 = &mut *a;  // reborrow: a frozen, b active
    *b += 1;
    // *a += 1;                 // ERROR: a is frozen while b lives
    *a += 1;                    // OK: b is dead, a reactivated
}
```

*Variance* governs how subtyping flows through borrow types: `&'a T` is *covariant* in `'a`, while `&'a mut T` is *invariant* in `'a` — shrinking the lifetime of a mutable borrow would be unsound, because the borrow could be stored and used to mutate after the supposed expiry. Oxide's region-based formulation makes this precise: regions are sets of locations, and the subtyping on regions is inclusion for shared borrows but equality for mutable ones [3].

The alias-XOR-mutability invariant is thus not a slogan but a *theorem* of each formalization: Oxide proves it as a consequence of its typing judgment, RustBelt encodes it in the semantic interpretation of reference types (a `&mut T` owns the *full* resource, a `&T` owns a *fractional* share), and Stacked Borrows enforces it dynamically.

###4.4 Interior Mutability and the Principled Escape Hatches

If affinity were absolute, Rust could not express reference-counted sharing, memoization, or shared mutable graphs. *Interior mutability* types — `Cell<T>`, `RefCell<T>`, `Mutex<T>`, `RwLock<T>` — relax the static invariant in controlled ways, each shifting enforcement from compile time to runtime or to a protocol:

| Type | Enforcement of alias-XOR-mutability | Cost |
|---|---|---|
| `Cell<T: Copy>` | type-level: only `Copy` values, no observable aliasing | zero |
| `RefCell<T>` | dynamic borrow flag; panics on violation | one flag + branch |
| `Mutex<T>` / `RwLock<T>` | runtime synchronization across threads | blocking |

`Cell` is sound for `Copy` types because replacing a `Copy` value cannot observe aliasing — there is no way to hold a borrow across the `set`. `RefCell` replays the borrow checker at runtime: the borrow flag is a dynamic version of the loan set, and a second `borrow_mut` while a borrow is live *panics* rather than being a compile error. In RustBelt's terms, these types are *safe abstractions over unsafe code*: their implementations use raw pointers and manual aliasing internally, and their soundness is exactly what the semantic-typing methodology was built to verify [2].

`Send` and `Sync` extend the story to concurrency: `T: Send` means ownership of `T` may be transferred across threads; `T: Sync` means `&T` may be shared across threads. Data-race freedom follows from alias-XOR-mutability plus these marker traits: a data race requires aliased mutation, and the type system ensures that aliased mutation across threads can only happen through a type that has been *proven* to synchronize. Notably, RustBelt's verification effort uncovered a genuine soundness bug involving `MutexGuard` — a case where the standard library's unsafe encapsulation was subtly wrong — demonstrating that the semantic approach does real work [2][8].

##5 Empirical Evidence and Formal Proofs

The formal models are not paper exercises; each is backed by mechanization and measurement.

**RustBelt (machine-checked, Coq/Iris).** The POPL 2018 development gives a semantic model of a realistic Rust subset (λRust) and verifies the safe encapsulation of `Cell`, `RefCell`, `Rc`, `Arc`, `Mutex`, `RwLock`, `thread::spawn`, and parts of `Vec` [2]. The adequacy theorem of Iris transfers these Coq proofs to guarantees about program execution: verified libraries cannot exhibit undefined behavior when used through their safe interfaces. Follow-on work extended the model to weak memory ("RustBelt meets relaxed memory") and to functional correctness (RustHornBelt) [8].

> **Theorem:** (RustBelt soundness, paraphrased). If a λRust program is well-typed in the syntactic system and every library it links satisfies the semantic interpretation of its interface, then the program is safe: it never reaches a stuck state attributable to a type error, exhibits no data races, and respects the aliasing discipline.

**Stacked Borrows (executable, Miri).** Because the model is operational, it was evaluated empirically: the Rust standard library and ecosystem test suites were run under Miri with borrow tracking enabled. The evaluation found real violations in widely used code — `VecDeque`, `LinkedList`, `BTreeMap`, and `str` patterns that created overlapping mutable references or invalidated protected shared references — which were then fixed or documented as known issues in the unsafe-code guidelines [7]. This is a rare instance of a *formal semantics directly improving a production standard library*.

**Tree Borrows (measured permissiveness).** Villani et al. evaluated Tree Borrows against Stacked Borrows on the test suites of the 30,000 most-used crates: Tree Borrows rejected **54% fewer** test cases while retaining most of the optimizations Stacked Borrows justifies and enabling new ones such as read–read reorderings [5]. The tree structure — permissions per pointer with child/foreign access rules — accepts the `Reserved`-until-first-write pattern pervasively used by real unsafe code (e.g., `vec.as_mut_ptr()` followed by immutable use of `vec`), which the stack model forbade.

**Oxide (syntactic metatheory).** Oxide's Coq-tested semantics and progress/preservation proof cover the safe core including non-lexical lifetimes [3]. Its value is comparative: it shows that borrow checking *can* be presented as an ordinary type system rather than a whole-program analysis, which simplifies teaching, extension, and integration with other type-system features.

**NLL adoption.** The deployment of non-lexical lifetimes in Rust 1.31/Rust 2018 [6] is the empirical counterpart at the language level: a semantics-preserving refinement of the borrow checker that strictly increased the set of accepted programs, validated by the compiler's own ecosystem-wide testing.

A minimal TLA+ sketch of a borrow permission's lifecycle, in the style of the operational models:

```tla+
---- MODULE BorrowState ----
EXTENDS Naturals
VARIABLE perm  \* "Reserved" | "Active" | "Frozen" | "Disabled"

Init == perm = "Reserved"
WriteAccess == perm = "Reserved" /\ perm' = "Active"
ReadAccess  == perm \in {"Reserved", "Active", "Frozen"} /\ UNCHANGED perm
ForeignWrite == perm' = "Disabled"  \* invalidated by an incompatible alias
Next == WriteAccess \/ ReadAccess \/ ForeignWrite
Spec == Init /\ [][Next]_perm
====
```

##6 Limitations

The ownership story, for all its rigor, has sharp boundaries — and the literature is admirably candid about them.

**The aliasing model is still undecided.** Stacked Borrows was explicitly an *experiment* [7]; Tree Borrows is its leading successor but is not yet the specified semantics of Rust. Until the unsafe-code guidelines committee ratifies a model, `unsafe` programmers write against a moving target, and Miri can report violations that a future model might permit (or vice versa).

**The borrow checker is incomplete by design.** There are safe programs it rejects — the classic examples involve conditional control flow, self-referential structs, and patterns requiring *view types* or explicit region polymorphism the surface language cannot express. Polonius may accept strictly more programs, but some desirable programs (e.g., streaming iterators lending from their own buffer) remain inexpressible without language extensions. Incompleteness is the price of decidability: borrow checking must terminate quickly on every crate in the ecosystem.

**Unsafe is unverified by default.** RustBelt verifies *selected* libraries; the long tail of crates.io `unsafe` code enjoys no such guarantee. Dynamic tools (Miri) check only executed paths, and `unsafe` interacting with *foreign functions* crosses a boundary no current model fully captures — recent large-scale studies found dozens of aliasing-model violations at FFI boundaries in widely downloaded libraries.

**Layout and validity are underspecified.** Rust deliberately leaves type layout partly unspecified (for optimization freedom), which means unsafe code reasoning about representation is fragile. The operational models assume an abstract machine; mapping their verdicts onto LLVM-level reality involves a semantic gap the community continues to narrow.

**Ergonomics vs. precision.** Every refinement — NLL, two-phase borrows, precise closure capture — complicates the mental model programmers must internalize. Oxide's project of finding the "simpler, more explainable essence" [3] remains partly aspirational: the production borrow checker is a sophisticated dataflow analysis whose error messages still occasionally baffle.

##7 Conclusion

Rust's ownership discipline is the most successful technology transfer in the history of substructural logic: Girard's 1987 decision to make weakening and contraction explicit [1] became, thirty years later, a compiler that rejects data races before a program ever runs. The three formal lenses — Oxide's syntactic type safety [3], RustBelt's semantic typing in Iris [2], and the Stacked/Tree Borrows operational models [4][5] — together explain *why* the discipline works, *where* it may be relaxed, and *what* unsafe code must uphold to remain a safe extension of the language.

The open frontier is now well mapped: ratify the aliasing model, close the FFI gap, extend verification to more of the ecosystem, and find presentations of borrow checking as teachable as Oxide promises. If the first decade of Rust turned linear logic into an industrial memory-safety discipline, the next will determine whether that discipline can be made *complete* — accepting every safe program — without surrendering the decidability and ergonomics that made it deployable.
