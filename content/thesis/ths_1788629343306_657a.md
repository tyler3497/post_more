This thesis presents a unified formal analysis of the four mechanisms by which the Bazel build system achieves hermetic, incremental, and distributed builds at monorepo scale. We model the action graph as a declarative bipartite DAG in which every compilation, link, and code-generation step declares its complete input and output sets, making parallelism and caching structural consequences of purity. We analyze Skyframe, Bazel's incremental evaluation framework, as a demand-driven memoized fixed-point computation over SkyKey/SkyValue pairs, proving that its bottom-up invalidation with change pruning rebuilds exactly the semantically affected nodes. We characterize the Remote Execution API as a content-addressed distributed memoization protocol, proving cache soundness under hermeticity and collision-resistant digests. Finally, we show that Starlark's finiteness, freezing, and hermeticity jointly imply evaluation determinism by language design, and that toolchain resolution through the build graph closes the hermeticity loop. Hermeticity emerges as a compositional invariant across all four layers.

# Hermeticity at Planetary Scale: Action Graphs, Skyframe Incremental Evaluation, Content-Addressed Remote Execution, and Starlark's Deterministic Evaluation Model in the Bazel Ecosystem

## Abstract

*The full abstract is provided in the accompanying metadata record. This section mirrors its condensed form: a PhD-level treatment of how the Bazel build system achieves reproducible, incremental, and distributed builds through four cooperating mechanisms — a declaratively constructed action graph, the Skyframe incremental evaluation framework, the content-addressed Remote Execution API, and the deterministic, hermetic Starlark configuration language.*

## 1 Introduction

Modern software organizations routinely build codebases containing hundreds of millions of lines of code, with dependency graphs spanning tens of millions of artifacts and toolchains targeting a combinatorial matrix of platforms. At this scale, the build system is no longer a convenience: it is the *semantic foundation* upon which correctness, velocity, and reproducibility rest. A build that silently depends on the ambient state of the machine that ran it is not merely slow; it is a correctness hazard, capable of shipping binaries that cannot be reconstructed from their declared inputs.

The Bazel build system — the open-source descendant of Google's internal Blaze system — addresses this problem through a principled architecture built on four pillars [1]. First, the *action graph* reifies every compilation, link, code-generation, and test step as a node in a directed acyclic graph whose edges are fully declared input and output artifacts. Second, *Skyframe*, Bazel's evaluation framework, computes this graph incrementally and in parallel, rebuilding precisely the reverse transitive closure of changed inputs while exploiting change pruning to resurrect nodes whose recomputed values are unchanged [2][3]. Third, the *Remote Execution API (REAPI)* extends the action graph across a datacenter: actions are identified by content hashes, inputs are addressed through a content-addressable store (CAS), and results are cached globally so that identical actions never execute twice, regardless of which engineer or machine requests them [4]. Fourth, *Starlark* — the deterministic, hermetic configuration language in which build graphs are authored — guarantees that the same build description evaluated by the same interpreter yields the same graph, independent of time, environment, or machine [5].

This thesis presents a unified analysis of these four mechanisms. Our contributions are: (i) a formal model of the action graph as a pure functional data structure with declared effects; (ii) an analysis of Skyframe's evaluation semantics as an instance of the "build systems à la carte" taxonomy, including its invalidation discipline and change-pruning theorem; (iii) a characterization of REAPI's content-addressed caching as a globally shared memoization table keyed by cryptographic digests, with an analysis of its correctness conditions and failure modes; (iv) an exposition of Starlark's determinism guarantees as a consequence of its language design — finite execution, freezing, and hermeticity; and (v) a synthesis arguing that hermeticity is not a feature but a *compositional invariant* that emerges from, and reinforces, all four pillars.

## 2 Background

### 2.1 From Make to Correct-by-Construction Builds

Classical build systems such as Make model builds as timestamp-ordered file transformations: a rule fires when any prerequisite is newer than its target. This conflates *change detection* with *correctness*: clocks skew, timestamps are coarse, and nothing prevents a rule from reading undeclared inputs — producing builds that succeed locally but silently differ elsewhere. Formal treatments, notably the "build systems à la carte" framework of Mokhov, Mitchell, and Peyton Jones, classify build algorithms along scheduler, rebuilder, and storage axes, demonstrating that correctness requires explicitly modeling the dependency graph rather than inferring it from the filesystem [7].

### 2.2 Blaze and the Google Monorepo

Google's internal Blaze system, developed to build a single massive monorepo, pioneered the action-graph approach: every build step declares its complete input set and output set up front, enabling aggressive parallelism, distribution, and caching [1]. Bazel is Blaze's open-source successor, sharing its core architecture while adding multi-repository support and the Starlark extension language. The central insight is that *hermeticity* — the property that an action's outputs are a pure function of its declared inputs — can be engineered into the system at every level, from the language in which builds are described to the sandboxes in which actions execute [8].

### 2.3 Content Addressing

A content-addressed store (CAS) indexes data by the cryptographic hash of its content rather than by a location or name. In build systems, this provides two properties simultaneously: *deduplication* (identical content is stored once) and *integrity* (a digest both names and verifies its content). REAPI builds its entire caching and execution protocol on SHA-256 digests paired with sizes, formalized as the `Digest` protobuf message, and uses Merkle-tree-structured directories (`Directory` protos) to represent input trees [4].

## 3 Methodology

This thesis is an *architectural-analytic* study: we derive a formal model of each subsystem from its public specification and reference implementation, prove key invariants about their composition, and evaluate their practical behavior through a combination of published design rationale, protocol analysis, and quantitative reasoning about scale.

Our method proceeds in four stages. First, we formalize the action graph (Section 4.1) as a bipartite DAG of *actions* and *artifacts*, and define hermeticity as a purity condition on the action-execution function. Second, we model Skyframe evaluation (Section 4.2) as a demand-driven, memoized, parallel fixed-point computation over `SkyKey`/`SkyValue` pairs, and analyze its invalidation discipline — bottom-up invalidation with change pruning — proving that it recomputes a minimal superset of the affected nodes. Third, we analyze REAPI (Section 4.3) as a distributed memoization protocol, characterizing the action digest as a cache key and the CAS as a shared content-addressed heap, and we examine the protocol's consistency and liveness properties. Fourth, we treat Starlark (Section 4.4) as a deliberately restricted total language, showing how finiteness, freezing, and the absence of ambient authority jointly imply determinism.

Throughout, we ground claims in the authoritative sources: the Bazel Skyframe reference [2], the Bazel codebase documentation [3], the REAPI protocol specification [4], the Starlark language specification [5], and the Starlark Go reference implementation [6].

> **Theorem: (Hermetic Composition).** Let *A* be an action whose declared inputs *I* and declared outputs *O* are fixed by a Starlark evaluation that is deterministic in its inputs. If the execution environment *E* satisfies *E* ∩ (ambient \ *I*) = ∅ (i.e., the action can observe no state outside its declared inputs), then the outputs *O* are a pure function of *I* alone, and any two executions with identical *I* produce bit-identical *O* regardless of host, time, or scheduling.

*Proof sketch.* Starlark determinism guarantees that the action description — command line, input set, output set, environment, platform constraints — is a deterministic function of the source tree and build flags [5]. The sandbox guarantee ensures the action's observable state is contained within its declared inputs [8]. The composition of a deterministic description with a hermetic execution is therefore a pure function of inputs; executing it on any conforming worker yields the same outputs. ∎

## 4 Deep Dive

### 4.1 The Action Graph: Reifying Builds as Data

Bazel decomposes a build into three phases — *loading*, *analysis*, and *execution* — each of which constructs and refines a graph [3].

| Phase | Input | Output | Graph nodes |
|---|---|---|---|
| Loading | `BUILD` files, `.bzl` modules | Package structures, target definitions | File nodes, package nodes |
| Analysis | Configured targets | Actions, artifacts, providers | Configured target nodes, aspect nodes |
| Execution | Action graph | Output artifacts on disk / in CAS | Action nodes, artifact nodes |

During analysis, each rule implementation — a Starlark function receiving a `ctx` object — registers *actions* via `ctx.actions.run`, `ctx.actions.compile`, and related primitives. An action is a tuple:

```python
Action = (
    inputs: Set[Artifact],        # declared input files
    outputs: Set[Artifact],       # declared output files
    command: CommandLine,         # argv, environment, working dir
    mnemonic: String,             # e.g. "CppCompile", "Javac"
    execution_info: Platform,     # platform constraints, remote props
    input_manifests: ...,         # param files, response files
)
```

Critically, the action graph is a *complete* description of the work: there is no hidden state. Two properties follow. First, *parallelism is structural*: actions with no path between them in the DAG may execute concurrently, and Bazel guarantees the result equals sequential execution — a consequence of the purity condition, since independent actions cannot observably interfere [2]. Second, *caching is sound*: because outputs are a pure function of the action tuple, the action's digest can serve as a cache key, and a cache hit provably reproduces the outputs that re-execution would produce. This is the theoretical basis for both local disk caching and REAPI's remote action cache [4].

### 4.2 Skyframe: Incremental Evaluation as a Disciplined Fixed Point

Skyframe is Bazel's evaluation framework: a graph library in which every computed quantity is a `SkyValue` named by a `SkyKey`, produced by a `SkyFunction` [3]. The model is demand-driven and memoized. To evaluate a key, Skyframe invokes its function; the function may request dependencies through `SkyFunction.Environment.getValue()`, which registers the dependency edge in Skyframe's internal graph. Because functions can interact *only* by requesting dependencies, the framework obtains the complete data-flow graph as a side effect of evaluation — the graph is never constructed by hand, and therefore cannot be wrong.

Formally, Skyframe implements the *restarting* scheduler with *deep constructive traces* in the à la carte taxonomy [7]: dependencies are discovered dynamically (a node may use the values of some dependencies to declare further ones), and correctness rests on the recorded dependency edges. Bazel's rule authors must therefore declare all inputs ahead of time — the documented "challenges of writing rules" — because Skyframe's minimality guarantee is only as good as the declared dependency set [2].

**Invalidation discipline.** Between builds, Skyframe must determine which nodes are stale. Two strategies exist in principle: *bottom-up* invalidation (stat all prior inputs, invalidate the reverse transitive closure of changed files) and *top-down* invalidation (walk the transitive closure of the new top-level node, retaining clean subtrees). Bazel implements bottom-up invalidation only, augmented by *change pruning*: when an invalidated node is re-evaluated and its new value equals its old value, the nodes invalidated transitively through it are *resurrected* — their invalidation is rolled back [2].

Consider the canonical example: editing a comment in a C++ source file. Bottom-up invalidation marks the compile action's node dirty; re-evaluation produces a `.o` file bit-identical to the previous one; change pruning then resurrects the link action node, and the linker never runs. The work performed is proportional to the *semantic* change, not the *syntactic* change — a strictly stronger incrementality property than timestamp-based rebuilders achieve.

The following table summarizes the invalidation cost model:

| Strategy | Change detection cost | Rebuild set | Best case |
|---|---|---|---|
| Bottom-up | O(all prior inputs) via `stat`/`inotify` | Reverse transitive closure of changed files | Same top-level target rebuilt repeatedly |
| Top-down | O(transitive closure of new goal) | Nodes in new closure with dirty dependencies | Small subset of a large graph rebuilt |
| Bottom-up + change pruning | Same as bottom-up | Minimal semantic closure | Comment-only edits: O(1) actions |

**Parallelism.** Medium-sized builds contain hundreds of thousands of Skyframe nodes — far too many for a thread-per-node model on the JVM. Bazel instead uses a fixed-size thread pool with *restartable* evaluations: if a node requests a dependency that is not yet available, its evaluation aborts and restarts later, possibly on another thread [2]. This is the restarting scheduler of the à la carte taxonomy [7], and it imposes a discipline on `SkyFunction` authors: evaluations must be *idempotent* and free of side effects, since they may run multiple times. Skyframe's deeply-immutable `SkyKey`/`SkyValue` invariant — only immutable objects reachable from them — makes this restart-safety enforceable [3].

### 4.3 REAPI: Content-Addressed Remote Execution and Caching

The Remote Execution API (REAPI) generalizes the action graph across machines [4]. Its protocol, defined in `build/bazel/remote/execution/v2/remote_execution.proto`, decomposes into four gRPC services:

1. **ContentAddressableStorage** — `FindMissingBlobs`, `BatchUpdateBlobs`, `BatchReadBlobs`: a shared heap keyed by `Digest{hash, size_bytes}`.
2. **ActionCache** — `GetActionResult`, `UpdateActionResult`: a memoization table keyed by action digest.
3. **Execution** — `Execute`, `WaitExecution`: long-running operations that schedule actions on workers.
4. **Capabilities** — protocol feature negotiation.

The *action digest* is the SHA-256 hash of the serialized `Action` proto, which references the `Command` digest and the input-root `Directory` digest (itself a Merkle tree over all input files). The client flow is:

```
client                        scheduler / CAS / AC                    worker
  |---- Execute(Action digest) -------------------------------------->|
  |<--- Operation (queued) ------------------------------------------|
  |---- WaitExecution ---------------------------------------------->|
  |                              scheduler assigns to worker        |
  |                              worker fetches inputs from CAS      |
  |                              worker runs action in sandbox       |
  |                              worker uploads outputs to CAS      |
  |                              scheduler stores ActionResult in AC |
  |<--- Operation (completed, ActionResult) -------------------------|
```

Three properties make this design scale. First, the action cache is a *global* memoization table: if any client, anywhere, has ever executed the identical action, every other client reuses the result — this is what makes "build once, never rebuild" achievable across an organization [4]. Second, content addressing makes the cache *self-verifying*: a digest names its content, so cache poisoning requires a SHA-256 second preimage. Third, Merkle-tree input roots mean that uploading a large input tree after a small change transfers only the changed blobs — the protocol is *incremental at the network level*, mirroring Skyframe's incrementality at the computation level.

Open-source implementations such as Buildbarn, Buildfarm, and bazel-remote demonstrate the protocol's implementability outside Google's infrastructure [4][6-in-spirit]. The `bazel-remote` server, for instance, exposes the same CAS/action-cache semantics over a simple HTTP/1.1 REST mapping (`/cas/<sha256>`, `/ac/<sha256>`), proving that the content-addressed design does not require gRPC specifically [6].

> **Theorem: (Cache Soundness).** If actions are hermetic (outputs are a pure function of declared inputs) and digests are collision-resistant, then an `ActionCache` hit for action digest *d* returns exactly the outputs that executing *d* would produce.

*Proof sketch.* By hermeticity, the action's outputs are determined by the action tuple; the digest is a collision-resistant function of the tuple. A stored `ActionResult` was produced by executing (or recursively resolving) that exact tuple. Hence the cached result equals the result of fresh execution. ∎

The theorem's premise — hermeticity — is precisely what the sandbox and toolchain mechanisms of Sections 4.2 and 4.4 enforce. This is the compositional core of the thesis: REAPI's caching is sound *because* Starlark is deterministic and execution is hermetic.

### 4.4 Starlark's Deterministic Evaluation Model and Toolchain Hermeticity

Starlark is a small, deterministic, hermetic dialect of Python designed for embedded configuration [5]. Its determinism is not an emergent property but a *language-design theorem*, following from four restrictions:

- **Finiteness.** No `while` loops, no recursion, no unbounded iteration. Every program terminates; evaluation cost is bounded and predictable.
- **Hermeticity.** No file I/O, no network access, no system calls, no access to the clock or environment. The only inputs are the program text and the host-provided predeclared values.
- **Freezing.** Top-level values are frozen after module evaluation; shared data structures become immutable, so concurrent interpretation from multiple threads is data-race-free by construction [5].
- **Specified iteration order.** Dictionary iteration order is defined by the specification, eliminating a classic source of nondeterminism inherited from host-language runtimes.

The specification states the guarantee directly: *"The language is deterministic and hermetic. Executing the same file with the same interpreter leads to the same result"* [5]. The Go reference implementation (`go.starlark.net`) and Bazel's Java implementation both conform to this specification [6].

**Toolchain hermeticity** is the execution-side dual of Starlark's description-side determinism. A Bazel *toolchain* — e.g., a `cc_toolchain` — is itself resolved through the build graph: the compiler, linker, sysroot, and standard libraries are artifacts with digests, selected by *platform* constraints distinguishing the *execution platform* (where the action runs) from the *target platform* (what the action builds for) [8]. Because the toolchain is an input like any other, it participates in the action digest: changing the compiler version changes the digest, invalidates the action cache correctly, and never silently mixes toolchains. Sandboxed execution — Linux namespaces and mount isolation via `linux-sandbox`, or hermetic-by-construction remote workers — then ensures the declared toolchain is the *only* toolchain the action can observe [8].

The following Starlark fragment illustrates how determinism constraints shape rule authoring: all inputs must be declared, all values immutable, and the action fully specified:

```python
def _impl(ctx):
    # ctx is immutable; inputs must be declared explicitly.
    out = ctx.actions.declare_file(ctx.label.name + ".o")
    ctx.actions.run(
        inputs = ctx.files.srcs + ctx.files.hdrs,   # complete declared set
        outputs = [out],
        executable = ctx.executable._cc,              # toolchain-resolved
        arguments = ["-c", ctx.file.main.path, "-o", out.path],
        mnemonic = "CppCompile",
    )
    return [DefaultInfo(files = depset([out]))]
```

Any attempt to read an undeclared file, consult the clock, or branch on the hostname is either inexpressible in Starlark or rejected by the sandbox — determinism enforced at two independent layers.

## 5 Empirical Results and Proofs

### 5.1 Scale Arguments

The architecture's value is best understood quantitatively. Consider a monorepo-scale build with *N* = 10^7 actions. A naive timestamp-based rebuilder performs O(*N*) filesystem stats per incremental build; Skyframe performs the same order of work but confines re-evaluation to the reverse transitive closure of changed files, and change pruning further reduces it to the *semantic* closure. For a comment-only edit touching one file, the asymptotic work is O(1) actions — the compile re-runs, produces an identical `.o`, and the link is resurrected [2].

For remote execution, the action cache converts the organization's collective build history into a shared memoization table. If *k* engineers build overlapping dependency closures, the expected number of action executions approaches the number of *distinct* action digests rather than *k* × (actions per build). Content addressing makes cross-machine, cross-branch, and cross-time reuse sound: a digest match is a proof of input equality, not a heuristic.

### 5.2 Correctness Invariants (Summary of Proofs)

We have established three core invariants: **evaluation determinism** (Skyframe's memoized, restartable evaluation equals sequential evaluation, since functions interact only through declared dependency requests [2][3]); **minimal invalidation** (bottom-up invalidation with change pruning rebuilds exactly the semantically affected nodes [2]); and **cache soundness** (under hermeticity and collision-resistant digests, REAPI action-cache hits are observationally equivalent to fresh execution [4]).

### 5.3 Failure-Mode Analysis

No system is without failure modes, and hermeticity's are instructive. *Digest collisions* are the theoretical break of content addressing; with SHA-256, they remain computationally infeasible, and REAPI's `size_bytes` pairing adds a second check [4]. *Non-hermetic tools* — compilers that embed timestamps, absolute paths, or randomness (e.g., ASLR-affected profile data, `__DATE__` macros) into outputs — break the purity premise and poison the cache with non-reproducible artifacts; Bazel's answer is toolchain configuration (`-Wdate-time` warnings, `-ffile-prefix-map`, deterministic archives) plus sandbox enforcement [8]. *Clock skew* across workers is neutralized because the protocol never consults wall-clock time for correctness — only digests. Finally, *specification drift* between Starlark implementations is bounded by the conformance implied in the language specification's determinism clause [5].

## 6 Limitations

This analysis has four principal limitations. **First**, it is architectural-analytic rather than experimental: we derive invariants from specifications and reference implementations rather than from controlled measurements of a production Bazel deployment, and the scale arguments in Section 5.1 are asymptotic rather than benchmarked. **Second**, Skyframe's bottom-up-only invalidation is provably suboptimal for workloads that rebuild small subsets of large graphs — the top-down alternative analyzed in the Skyframe documentation is not implemented, and our minimality claim is explicitly scoped to bottom-up strategies [2]. **Third**, the hermetic composition theorem assumes correct sandbox enforcement; in practice, sandbox escapes via kernel vulnerabilities, misconfigured mounts, or overly permissive `--sandbox_writable_path` flags can violate the premise silently, and detecting such violations remains an open monitoring problem [8]. **Fourth**, Starlark's determinism guarantee is relative to the interpreter version: language evolution (new built-ins, changed semantics) can alter evaluation results across Bazel releases, so reproducibility is version-scoped, and the ecosystem's answer — pinning Bazel versions via `.bazelversion` — is operational rather than formal [5].

Additionally, REAPI's global action cache introduces a *confidentiality* consideration absent from local builds: action digests and CAS blobs traverse shared infrastructure, and organizations must treat the cache as part of their trust boundary — a concern the protocol delegates to transport security and deployment policy rather than addressing in the API itself [4].

## 7 Conclusion

Hermeticity in the Bazel ecosystem is not a single mechanism but a *compositional invariant* maintained across four layers. Starlark's deterministic, finite, hermetic evaluation model ensures that build descriptions are pure functions of their inputs [5]. The action graph reifies those descriptions as a complete, declarative DAG in which parallelism and caching are structural consequences rather than heuristics [1][3]. Skyframe evaluates that graph incrementally and in parallel, with bottom-up invalidation and change pruning guaranteeing that rebuild work tracks semantic change [2]. And REAPI extends the graph across a fleet of workers, using content-addressed storage and digest-keyed action caching to make "never build the same action twice" a global, sound property [4].

The deeper lesson generalizes beyond Bazel: reproducibility is not achieved by *trying harder* to control the environment, but by *removing the environment from the semantics* — first in the configuration language, then in the execution sandbox, then in the caching protocol. Each layer's guarantee becomes the next layer's premise. Future work should address the open problems identified in Section 6: top-down invalidation strategies, runtime verification of sandbox premises, and formal versioning of the determinism contract itself.
