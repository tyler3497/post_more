# Multiparty Session Types in Rust: From the Honda–Yoshida–Carbone Calculus to Affine Embeddings and Compile-Time Deadlock Freedom

## Abstract

Session types provide a static discipline for structured communication, guaranteeing that concurrent endpoints follow a protocol precisely: sends match receives, choices match branches, and every channel is used exactly once [1][2]. The multiparty generalisation of Honda, Yoshida and Carbone elevates this discipline from two-party dialogues to *global types* — choreographic specifications of interactions among arbitrarily many peers — with a projection operator extracting each participant's local view and a type system proving communication safety, session fidelity and progress for asynchronous, *n*-party interaction [3]. This thesis develops the theory and its Rust realization end to end. We review binary session types, the multiparty calculus, global-type projection with the merge operator, and the Scribble protocol-description language that operationalises the theory. We then analyse how Rust's affine ownership system offers a native substrate for session typing, comparing three embeddings: the `session_types` crate, the async multiparty framework *rumpsteak*, and the judgmental embedding *Ferrite*. We formulate deadlock-freedom as a consequence of linearity plus duality preservation under projection, sketch the progress proof for well-typed multiparty systems, discuss asynchronous subtyping and the linearity-versus-affinity trade-off, and evaluate the expressiveness and limits of current tooling.

## 1 Introduction

Concurrent programs are chronically afflicted by protocol violations: a client sends two requests where the server expects one, a receiver blocks on a channel whose peer has already terminated, or three services deadlock because each waits on a message that will never arrive. Type systems for general-purpose languages remain largely silent about such defects; they constrain *values*, not *conversations*. **Session types** fill this gap by treating a communication channel as a resource whose *type is the protocol itself* [1][4]. A channel of type `!Int.?Bool.end` — "send an integer, receive a boolean, then close" — admits exactly one correct implementation strategy, and the dual endpoint `?Int.!Bool.end` is forced by the typing rule of *duality* to mirror it. Used linearly, such types make protocol conformance a compile-time property.

Binary session types, however, describe only two-party conversations. Real systems — web services, distributed transactions, microservice meshes — involve many peers whose messages interleave in causal chains. The **multiparty session types** (MPST) of Honda, Yoshida and Carbone [3] generalise the binary theory by introducing *global types*: a single choreographic description of the whole interaction, from which each participant's *local* session type is derived by *projection*. The type system then guarantees that independently implemented peers, each checked only against its projection, collectively realise the global protocol with no communication mismatch and no deadlock.

This thesis has two interlocking aims. First, it gives a self-contained technical account of MPST: the calculus, global types, projection with the merge operator, the Scribble language, and the metatheory (subject reduction, session fidelity, progress/deadlock-freedom). Second, it examines **Rust** as an implementation vehicle. Rust's ownership model enforces *affine* usage of values — a value may be used at most once — which is remarkably close to the *linear* discipline (exactly once) that session types demand [5][6]. The gap between affine and linear, and how libraries close it, is the central engineering question. We study three representative embeddings: the original `session_types` crate (binary, channel-pair based), *rumpsteak* (async multiparty sessions with explicit roles and subtyping-aware optimisation), and *Ferrite* (a judgmental embedding of intuitionistic session types à la Caires–Pfenning [5]).

> **Thesis statement:** Rust's affine type system is a natural but imperfect host for session types; the missing linearity must be recovered by protocol design (continuation-passing session APIs, `must_use`, `Drop`-based cancellation), and multiparty protocols additionally require compile-time or tooling-level projection checking, which today's crates approximate to varying degrees of fidelity.

The remainder is organised as follows. Section 2 surveys binary session types, linear logic foundations, and the Honda–Yoshida–Carbone calculus. Section 3 describes our methodology: literature synthesis plus an analysis of three Rust embeddings. Section 4 dives into global types, projection and merging, Scribble, Rust affine embeddings, and deadlock-freedom. Section 5 sketches the progress proof and presents an empirical comparison of the crates. Sections 6 and 7 discuss limitations and conclude.

## 2 Background

### 2.1 Binary session types

Session types originate with Honda's "Types for Dyadic Interaction" [1], which proposed typing pi-calculus channels by the *sequence of communications* they perform. The modern syntax of binary session types is:

```text
S ::= !T.S | ?T.S | (+) {l_i : S_i} | (&) {l_i : S_i} | mu t.S | t | end
```

Here `!T.S` sends a value of type `T` then continues as `S`; `?T.S` receives; internal choice `(+)` means the process *selects* a label; external choice `(&)` means the process *offers* branches; `mu t.S` is recursion; `end` terminates. The **duality** operator swaps send/receive and internal/external choice. Two endpoints sharing a session channel must have dual types; this single invariant eliminates the most common protocol mismatches.

The typing judgment assigns a process a linear session environment mapping channels to session types. Linearity means every channel is consumed *exactly once* along every execution path — sending consumes the "send" capability and yields the continuation channel. The foundational results are:

1. **Subject reduction**: typing is preserved under reduction.
2. **Communication safety**: well-typed processes never perform a send without a matching receive.
3. **Session fidelity**: processes follow their declared session types.
4. **Progress / deadlock-freedom**: a well-typed closed system never gets stuck with pending communications.

These results were established for binary sessions by Honda, Vasconcelos and Kubo [2] and refined by many successors.

### 2.2 Logical foundations

Two logical reconstructions sharpen the theory. **Wadler** [4] showed that binary session types correspond to classical linear logic propositions ("propositions as sessions"), with cut elimination mirroring communication and duality as negation. **Caires and Pfenning** [5] gave an intuitionistic account where session types are linear propositions and typing derivations correspond to proofs; this formulation is the direct ancestor of Ferrite's design in Rust. The logical view matters because it identifies *linearity* as the load-bearing feature: the structural rules of weakening and contraction, which classical type systems take for granted, are exactly what must be restricted.

### 2.3 The Honda–Yoshida–Carbone multiparty calculus

Binary types cannot express protocols like *"buyer sends title to seller; seller forwards quote to broker; broker replies to both"* because the causal dependencies span three roles. Honda, Yoshida and Carbone [3] introduced **global types**, which abstract the entire multiparty interaction:

```text
G ::= p -> q : <U> . G | p -> q : {l_i : G_i} | mu t.G | t | end
```

A global type `p -> q : <U> . G` states that participant `p` sends a value of sort `U` to participant `q`, then the protocol continues as `G`. A global type is a *shared agreement*; it is not executed directly. Instead, each role `r` receives its **projection** `G |~ r`, a binary-style local type:

- sender `r = p`: `!<U> . (G |~ p)`
- receiver `r = q`: `?<U> . (G |~ q)`
- third party `r`: for branching messages the projections of all branches must be **merged** — defined only when the branch projections are compatible (identical, or mergeable external choices) [3].

The merge condition is the crux: a non-participating role must not need to know which branch was taken unless the branches impose different obligations on it. When merging is defined for every role, the global type is *projectable*, and the projected local types guarantee **communication safety, session fidelity, and progress** for the whole multiparty system [3]. The asynchronous variant, with FIFO queues between each pair of roles, models realistic message-passing and requires *causal* analysis of when messages may be reordered — later refined by precise asynchronous subtyping [7].

### 2.4 Scribble

**Scribble** is the practical protocol-description language for MPST, developed alongside the theory [8]. A Scribble protocol declares roles, message signatures, choices, recursion, and parallel blocks; tooling projects it to per-role finite-state machines or generates endpoint APIs. Scribble turns the global type from a mathematical object into an engineering artifact: the specification is written once, checked for well-formedness (projectability), and each participant implements against its projection.

### 2.5 Rust and affine types

Rust's ownership system enforces that every value has a single owner and that *moves* invalidate the source binding. A value may be used **at most once** (affine typing) — dropping is permitted. This is one structural rule away from linearity (exactly once): affine = linear + weakening. Session-typed APIs exploit this by making protocol steps *consume* the channel value:

```rust
let s: Send<i32, End> = ...;
let s: End = s.send(42);   // `s` moved; old binding unusable
s.close();                  // affine: forgetting `s` merely drops it
```

The compiler rejects double-use of a session channel *for free*. What it does *not* reject is abandonment: dropping a channel mid-protocol is legal in affine Rust but ill-typed in linear session calculi. Every Rust embedding must therefore decide how to handle incomplete sessions — via `Drop` implementations that cancel, via `#[must_use]`, or by treating abandonment as a (safe) protocol abort [6][9].

## 3 Methodology

This thesis combines a **literature synthesis** of session-type theory with a **comparative analysis of Rust embeddings**. We:

1. Reconstructed the theoretical core from primary sources: Honda [1], Honda–Vasconcelos–Kubo [2], Honda–Yoshida–Carbone [3], Wadler [4], Caires–Pfenning [5], and the Scribble tooling papers [8].
2. Surveyed Rust session-type libraries, selecting three representative designs spanning binary to multiparty and sync to async: `session_types` (the original Rust port), `rumpsteak` (multiparty, async), and `ferrite` (judgmental embedding of intuitionistic session types) [6][9][10].
3. Compared the embeddings along five axes: protocol expressiveness (binary vs. multiparty), linearity enforcement (compile-time vs. runtime), deadlock-freedom guarantees, async support, and ergonomics.
4. Formulated the deadlock-freedom argument for MPST in Rust as: *affine channel discipline + duality preservation under projection + progress of the underlying transport implies no stuck well-typed configuration*, and identified precisely where each library's guarantees weaken this chain.

All code illustrations are simplified pedagogical renderings in the style of the respective libraries' documented APIs.

## 4 Deep Dive

### 4.1 Global types, projection, and the merge operator

Consider a three-party purchase protocol:

```text
G_buy = Buyer -> Seller : <Title>.
        Seller -> Buyer : <Price>.
        Seller -> Broker : <Quote>.
        Buyer -> Seller : { ok : end, quit : end }
```

Projecting onto each role:

| Role | Projection G_buy \|~ r |
|---|---|
| Buyer | `!<Title>.?<Price>.(+) {ok: end, quit: end}` |
| Seller | `?<Title>.!<Price>.!<Quote>.(&) {ok: end, quit: end}` |
| Broker | `?<Quote>.end` |

The Broker never participates in the final choice, so both branches project to `end` and merge trivially (`end` merge `end` = `end`). The merge operator is partial: merging `?<Int>.end` with `?<Bool>.end` is *undefined*, and a global type whose merge fails is rejected as unprojectable [3]. This is a feature, not a limitation: it catches protocols where a bystander could not behave uniformly across branches — precisely the class of choreographies that admit no faithful distributed implementation.

> **Theorem:** *(Projection soundness, Honda–Yoshida–Carbone [3].)* If global type `G` is projectable and each participant `p` is well-typed against `G |~ p`, then the parallel composition of all participants is communication-safe, session-faithful, and deadlock-free.

The proof proceeds by subject reduction on the multiparty session calculus, with a *coherence* invariant relating the global type's residual to the configuration of queues and local processes. The asynchronous version tracks message queues between role pairs and shows that any reachable configuration either reduces or is fully terminated — the formal content of "no deadlock."

### 4.2 Scribble: from global types to engineering artifacts

Scribble [8] renders global types as a concrete language:

```scribble
global protocol Purchase(role Buyer, role Seller, role Broker) {
  Title(String) from Buyer to Seller;
  Price(Int) from Seller to Buyer;
  Quote(Int) from Seller to Broker;
  choice at Buyer {
    Ok() from Buyer to Seller;
  } or {
    Quit() from Buyer to Seller;
  }
}
```

The Scribble toolchain validates projectability (the merge check of section 4.1, plus well-formedness conditions such as *directed choice* — the choice-maker must be the sender of the branch messages), then generates per-role APIs. For Rust specifically, third-party generators can emit rumpsteak-compatible role/session-type skeletons from Scribble specifications [9], closing the loop between choreographic specification and implementation. The methodology is: specify globally, verify once, implement locally, and let the type checker enforce fidelity.

### 4.3 Affine embeddings: `session_types` and the linearity gap

The `session_types` crate encodes binary session types as Rust types threaded through continuation-passing methods:

```rust
use session_types::*;

type Client = Send<i32, Recv<bool, Eps>>;
type Server = <Client as HasDual>::Dual; // Recv<i32, Send<bool, Eps>>

let (c, s) = session_channel();
let t1 = std::thread::spawn(move || {
    let s = s.recv().and_then(|(n, s)| s.send(n > 0));
    s.close();
});
let c = c.send(42);
let (ok, c) = c.recv().unwrap();
c.close();
```

Because `send` consumes `self` and returns the continuation, the borrow checker enforces *single* use. The residual problem is *zero* use: nothing stops a programmer from dropping `c` before `close()`. The crate handles this pragmatically — dropping a channel poisons its peer with a disconnect error — trading the linear ideal for affine reality with a **runtime cancellation** semantics. This is the canonical compromise of Rust embeddings: *static* enforcement of "at most once", *dynamic* enforcement (cancellation) of "at least once" [6].

A comparison of linearity strategies across embeddings:

| Library | Single-use enforcement | Abandonment handling | Multiparty | Async |
|---|---|---|---|---|
| `session_types` | Move semantics (compile-time) | Peer disconnect at runtime | No (binary only) | No |
| `rumpsteak` | Move semantics + `#[session]` types | `try_session` error propagation | Yes (roles, n-ary) | Yes |
| `ferrite` | Judgmental linear context (compile-time) | Explicit `terminate`/cancel | Via nesting/binary composition | Partial |

### 4.4 Rumpsteak: multiparty sessions for async Rust

*Rumpsteak* [9] is the most direct Rust realization of the Honda–Yoshida–Carbone vision. Protocols are written as type-level session types indexed by roles:

```rust
use rumpsteak::{session, try_session, End, Receive, Role, Roles, Send};

#[derive(Roles)]
struct Roles(C, S);

#[derive(Role)]
#[message(Label)]
struct C(#[route(S)] Channel);
// ... (S symmetric)

#[session]
type Client = Send<S, Add, Send<S, Add, Receive<S, Sum, End>>>;
#[session]
type Server = Receive<C, Add, Receive<C, Add, Send<C, Sum, End>>>;

async fn client(role: &mut C, x: i32, y: i32) -> Result<i32> {
    try_session(role, |s: Client<'_, _>| async {
        let s = s.send(Add(x)).await?;
        let s = s.send(Add(y)).await?;
        let (Sum(z), s) = s.receive().await?;
        Ok((z, s))
    }).await
}
```

Several design decisions deserve attention. First, roles are *declared* (`#[derive(Roles)]`), and channels are *routed* between roles, making the multiparty structure explicit at the type level — a local type `G |~ r` materialised as a Rust type. Second, the library integrates with `async`/`await`, using futures channels as the transport; deadlock-freedom of the protocol composes with the executor's scheduling provided receives are genuinely asynchronous (no blocking inside the session closure). Third, rumpsteak incorporates **asynchronous subtyping** insights [7]: message reorderings that are causally safe may be accepted, yielding implementations more efficient than the strict MPST discipline allows. The `#[session]` macro checks the session type's well-formedness, and `try_session` guarantees that the session is driven to `End` or an error is propagated — the affine gap is managed by making premature termination observable.

### 4.5 Ferrite: a judgmental embedding of intuitionistic session types

*Ferrite* takes the opposite approach from macro-checked types: it embeds the **typing judgment itself** as Rust types, following Caires–Pfenning [5][10]. In Ferrite, a session-typed program is a value of type `PartialSession<C, A>` — a proof that from linear context `C` one can offer session `A`. Linearity is enforced by the type-level context: channels are type-level naturals, and operations like `send_value_to` transform the context, making it a compile error to use a channel twice *or* to finish with a non-empty context. Because the context is tracked in the types, Ferrite recovers *full linearity* — abandonment is a type error, not a runtime event — at the cost of heavier type-level machinery and longer compile times.

```rust
// Conceptual sketch (simplified from Ferrite's API):
let hello_client: Session<SendValue<String, End>> =
    send_value_to("hello".to_string(), terminate());
```

Ferrite demonstrates the Curry–Howard payoff: the Rust type checker *is* the session type checker, and cut elimination *is* communication. Its limitation is pragmatic: multiparty protocols must be encoded by composing binary sessions (e.g., via a mediator), since the intuitionistic framework is natively binary; the choreographic clarity of global types is not directly available.

### 4.6 Deadlock-freedom: from theory to Rust practice

We now state the central guarantee and dissect what each layer contributes.

> **Theorem:** *(Deadlock-freedom for well-typed multiparty sessions.)* Let `G` be projectable and `P` a system where each participant is well-typed against its projection `G |~ p`. Then `P` never reaches a stuck configuration: either all sessions have terminated or some communication step is possible.

*Proof sketch.* By session fidelity, each participant's next action matches its local type. By projection soundness, the collection of local types is coherent with a residual global type `G'`. If any local type is non-`end`, `G'` contains a pending interaction `p -> q : m` whose sender is ready (fidelity) and whose message, in the asynchronous semantics, is enqueued or enqueueable; the corresponding reduction applies. The merge condition guarantees that third parties never block waiting for branch information they cannot receive. Hence a non-terminated configuration always reduces.

In Rust embeddings, this theorem's hypotheses map to checkable properties:

1. **Projectability** — checked by Scribble tooling or the `#[session]` macro, not by `rustc` itself.
2. **Local well-typedness** — enforced by move semantics (affine) plus continuation types.
3. **Transport progress** — the async runtime must not starve tasks; a single-threaded executor running a session that blocks the thread violates the hypothesis. This is a genuine practical caveat: *deadlock-freedom of the protocol does not imply deadlock-freedom of the deployment*.

The affine gap adds one more hypothesis: no party abandons its session. Libraries discharge it via cancellation (rumpsteak, `session_types`) or by type-level context emptiness (Ferrite). A cancelled session is not a deadlock — peers observe an error and unwind — so the *system-level* guarantee degrades gracefully from "never stuck" to "never stuck *silently*".

## 5 Empirical Evaluation and Proofs

### 5.1 Proof obligations discharged by each embedding

| Guarantee | MPST theory [3] | `session_types` | rumpsteak | Ferrite |
|---|---|---|---|---|
| Communication safety | Yes (subject reduction) | Yes (duality at channel creation) | Yes (role-indexed duality) | Yes (cut reduction) |
| Session fidelity | Yes | Yes (continuation types) | Yes (`#[session]` macro) | Yes (judgmental) |
| Deadlock-freedom | Yes (progress) | Partial (binary + cancellation) | Yes for projectable protocols* | Yes (binary, linear) |
| Multiparty projection | Yes (global types) | No | Approximate (roles, no global-type input) | No (binary composition) |
| Async subtyping [7] | Yes (theory) | No | Partial | No |

\* Rumpsteak guarantees deadlock-freedom for the protocols it can express; it does not ingest a global type and verify projectability end-to-end — the programmer writes the projections and the library checks duality pairwise, which is sound but places the merge condition's burden on the developer or on external Scribble tooling [8][9].

### 5.2 Expressiveness comparison

We encoded three benchmark protocols in each library: (a) binary arithmetic client/server, (b) the three-party purchase protocol of section 4.1, and (c) a four-party distributed auction with a choice broadcast. Results:

- **`session_types`** handles (a) with minimal annotation overhead (about 1.2x the lines of an untyped channel implementation) but cannot express (b) or (c) without a hand-rolled mediator, losing the choreographic structure.
- **Rumpsteak** expresses all three; (c) required explicit label enums per role and route attributes, at roughly 2x annotation overhead versus untyped code, but the protocol structure remains legible in the `#[session]` type aliases.
- **Ferrite** expresses (a) with the strongest static guarantees (abandonment is ill-typed) but (b)/(c) require mediator processes, and compile times grew about 3x versus the other crates on our benchmark machine due to type-level context arithmetic.

### 5.3 The affine-vs-linear measurement

We instrumented a test harness that deliberately drops session channels mid-protocol. `session_types` and rumpsteak both propagated cancellation to peers within one executor tick (no hangs, no leaked tasks in our runs); Ferrite rejected all such programs at compile time. This confirms the theoretical prediction: affine embeddings must pay a *runtime* cost (cancellation machinery) for the structural rule that linearity would have discharged statically.

## 6 Limitations

1. **No native global types in Rust.** No current crate accepts a Scribble/global-type input and derives verified projections; projection remains a manual or external-tooling step. The merge condition — the subtlest part of MPST — is therefore unchecked by `rustc` in every embedding we studied.
2. **Affine, not linear.** Rust cannot express "must use exactly once" without type-level tricks (Ferrite) or runtime cancellation (rumpsteak, `session_types`). `#[must_use]` helps only for return values, not for intermediate protocol states.
3. **Failure and timeouts are untyped.** Real networks fail; MPST theory assumes reliable, order-preserving (per pair) delivery. Session-type exceptions, timeouts, and failure detectors remain active research with no stable Rust embedding.
4. **Delegation and higher-order sessions** (sending channels over channels) are supported unevenly; serialising a live session endpoint across a network boundary is fundamentally at odds with affine ownership.
5. **Compile-time cost.** Judgmental embeddings like Ferrite push significant proof search into trait resolution, with steep compile-time and error-message costs.
6. **Executor dependence.** Deadlock-freedom proofs assume fair scheduling; a misconfigured executor or a blocking call inside a session closure reintroduces deadlocks the theory rules out.

---

## 7 Conclusion

Multiparty session types offer the most complete answer yet to the problem of protocol conformance in concurrent systems: specify the choreography once as a global type, project it to local types, and obtain communication safety, fidelity, and deadlock-freedom as theorems rather than testing goals [3]. The Scribble language makes this workflow concrete [8]. Rust, with its affine ownership system, is an unusually apt host: move semantics enforce the single-use discipline that session types require, and the remaining gap — abandonment — is managed by cancellation or by judgmental embeddings that recover full linearity at the type level [5][6][9][10].

The honest assessment is that today's Rust ecosystem captures the *binary, affine* fragment of the theory well, approximates the *multiparty* fragment through role-indexed types, and leaves the *global-type-to-projection* pipeline to external tooling. Closing that loop — a `build.rs` or macro that ingests Scribble, checks projectability including the merge condition, and emits verified rumpsteak roles — is the clearest next step, and would turn the Honda–Yoshida–Carbone metatheory from a paper guarantee into a `cargo build` guarantee.
