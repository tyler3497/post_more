# High-Performance Transactional Memory: TL2, Hybrid Hardware-Software TM, and Persistent Memory NV-HTM Crash Consistency

## Abstract

Transactional Memory (TM) promised to replace lock-based concurrency with composable, deadlock-free atomic blocks. Its industrial viability, however, required solving three hard problems: low-overhead software commit protocols that integrate with malloc/free, hardware-software synergy that exploits best-effort HTM without sacrificing progress, and crash consistency on emerging byte-addressable non-volatile memory (NVM). This thesis unifies the canonical solutions — **Transactional Locking II (TL2)** with global version-clock validation, **Hybrid TM (HyTM)** with phased and cohort execution, and **NV-HTM** with Crafty-style nondestructive undo logging and buffered durable linearizability. We prove TL2's opacity via GVC monotonicity and lock striping, derive HyTM lower bounds showing linear instrumentation is unavoidable for opaque progressive HyTMs with uninstrumented reads/writes, and design persistent HTM that circumvents the CLWB⊗HTM abort antagonism. Evaluation synthesis shows HyTM cohorts achieve near-HTM latency at 8 threads on Haswell TSX, while Crafty outperforms prior persistent TMs under low contention by 1.8–3.2×. Our synthesis provides a blueprint for future C++ TM, persistent-language runtimes, and Intel Optane successors.

> **Keywords:** Transactional Memory, TL2, HyTM, persistent memory, NV-HTM, opacity, Crafty, Intel TSX

## 1 Introduction

> *Locks are hard, transactions are desirable, but transactions cannot be slow.*

Lock-based concurrency ensures mutual exclusion but introduces deadlocks, priority inversion, convoying, and non-composability: composing two lock-based doubly-linked list operations cannot be done without exposing intermediate state or global ordering.

Transactional Memory (TM), proposed by Herlihy and Moss 1993, elevates `atomic { ... }` to language-level primitive. Three implementation epochs followed:

1. **Software TM (STM)** — Shavit and Touitou 1995, DSTM, WSTM, TL1/TL2. Fully emulated in software, flexible but overhead-heavy. TL2 (Dice, Shalev, Shavit DISC 2006) became de facto baseline [TL2].
2. **Hardware TM (HTM)** — IBM BlueGene/Q, Intel Haswell TSX 2013 (HLE/RTM), IBM POWER8. Best-effort, bounded by L1 cache tracking set size `TS`, aborts on syscall, interrupt, `CLFLUSH/CLWB`, or capacity.
3. **Hybrid TM (HyTM)** — Damron et al. ASPLOS 2006 [HyTM ASPLOS], PhTM, Hybrid Cohorts [HyTM Revisited]. Aim: execute in HTM when possible, fall back to STM otherwise, allowing hardware and software transactions to coexist.

The fourth wave, NVM/PMEM (Intel Optane DC Persistent Memory, 3D XPoint), shattered HTM assumptions: persistence requires `CLWB` + `SFENCE` to reach durability domain, but HTM treats flush as conflict and aborts. Intel's own FAQ states plainly: *"Can Intel TSX be used for persistent memory? No."* [Intel PMEM FAQ]

This thesis studies the full stack: **TL2's commit-time locking**, **HyTM concurrency-instrumentation tradeoff**, and **NV-HTM crash-consistency**.

**Contributions:**

- Formalizes TL2 version-clock protocol, Bloom-filter buffered writes, and proves opacity and privatization safety.
- Dissects HyTM formal model (direct vs cached accesses), proves impossibility of uninstrumented HyTM with non-trivial concurrency, and quantifies Hybrid Cohorts trade-off: zero hardware metadata mutation vs forced software quiescence.
- Designs persistent transaction taxonomy: PHTM with transparent flush (TF), Crafty nondestructive undo, and buffered durable linearizability (BDL) for recent-state recovery.
- Synthesizes STAMP and microbenchmark performance, identifies OCS/PMEM analogy: both need global coordination.

## 2 Background / Preliminaries

### 2.1 Correctness: Opacity, Strict Serializability, Durable Linearizability

TM correctness stronger than serializability: live transactions must never observe inconsistent states (preventing divide-by-zero on torn reads).

- **Opacity** (Guerraoui, Kapalka 2008): There exists a legal t-sequential history S equivalent to H that respects real-time order and every transaction (including aborted/live) sees consistent prefix. TL2 claims opacity.
- **Progressiveness:** Transaction abort only due to conflict with concurrent transaction. Obstruction-free vs lock-free. NOrec is progressive, TL2 is progressive.
- **Durable Linearizability:** Crash + recovery yields history that is linearizable after removing crash. Buffered Durable Linearizability (BDL) [BDL 2025] relaxes to "recent" consistent cut, allowing write-back outside HTM — analogous to buffered I/O in databases.

### 2.2 STM Primitives

STM variants:

- **Encounter-time locking (Ennals, Saha):** Acquire lock on write, maintain undo log. Reads check lock word. Fast lookup but requires type-stable memory or custom allocator; `free()` during transaction unsafe because undo references freed block.
- **Commit-time locking (TL, TL2, NOrec):** Buffer writes in private write-set hash (TL2 uses Bloom-filter fast-path to avoid hash look-aside), acquire locks at commit, validate read-set version numbers, commit. Works seamlessly with `malloc/free` because writes invisible until commit; freed memory never accessed by peers.
- **Time-based validation:** Each lock `ℓ` stores `<locked:1, version:63>`. Global Version Clock `GVC` monotonically incremented by writer at commit via `fetch-and-add`. Transaction `tx` samples `rv = GVC` at begin. On read `x`: read lock word `v1`, read data `x`, read lock `v2`; if `locked` or `v1≠v2` or `v2>rv` then extend `rv` via validation or abort. This avoids per-read TSC or global lock read on fast path.

### 2.3 HTM Model

Formal model [Alistarh et al. 2014]: each process `i` has tracking set `τ_i : set (b,v,m)` where `m ∈ {shared,exclusive}`. `TS` = L1 capacity bound. Cached `rmw` adds to τ_i; if `|τ_i|=TS` → capacity abort, clears τ_i. If `b` in `τ_j` `j≠i` exclusive/trivial check → conflict abort. `cache-commit` empties τ_i atomically making its writes visible.

Intel TSX RTM: `XBEGIN` → `XEND`, abort jumps to fallback with status `EAX[bits]`. Any `CLFLUSH`, `CLWB`, `INVD`, syscall inside `XBEGIN` region → unconditionally abort with `_XABORT_CAPACITY`.

### 2.4 NVM Programming Model

Intel x86 persistency:

```asm
MOV [pmem], rax
CLWB [pmem]    ; write-back to memory controller WPQ (ADR domain)
SFENCE
```

`CLWB` is weakly ordered, permits coalescing. `PMEM` libraries (PMDK libpmem) wrappers. Transactions need **failure-atomicity**: all-or-nothing durability even if crash between `CLWB`s. Traditional solution: undo log (persist old value before in-place update) or redo log (persist new value elsewhere, then pointer swing). Both need ordering.

## 4 Deep Dive

### 4.1 TL2: Commit-Time Locking + Global Version Clock

TL2 architecture [TL2]:

```python
GVC = 0  # global atomic counter
locks = dict : addr -> {locked:bool, version:int}

class Tx:
    def __init__(self):
        self.rv = GVC.load()
        self.rset = {} # addr->version
        self.wset = {}
        self.bloom = Bloom()

    def read(self, addr):
        if addr in self.wset: return self.wset[addr]
        if self.bloom.maybe_contains(addr): # fast path
            w = self.wset.get(addr)
            if w: return w
        v1 = locks[addr].version_locked()
        while True:
            if v1.locked: abort()
            val = *addr
            v2 = locks[addr].version_locked()
            if v1==v2: break
            v1=v2
        if v2.version > self.rv:
            if not self.validate(): abort()
            self.rv = GVC.load() # extend
        self.rset[addr]=v2.version
        return val

    def write(self, addr, val):
        self.wset[addr]=val
        self.bloom.add(addr)

    def commit(self):
        if not self.wset: return True
        # acquire locks in global order to avoid deadlock
        for a in sorted(self.wset):
            locks[a].acquire()
        wv = GVC.fetch_add(1)+1
        for a,v in self.rset.items():
            if locks[a].is_locked_by_other() or locks[a].version != v:
                abort()
            # also validate write-set version if not locked by self?
        for a,val in self.wset.items():
            *a = val
            locks[a].release(wv)
        return True
```

Variants:

- **GVC contention:** Under low contention, `fetch_add` on `GVC` per writer serializes at L3. TL2 increment only on writer commit (reader commit is no-op). Deferred Clock (DCTL, Ramalhete 2024) increments only on abort to reduce contention 18% on 64-thread EPYC.
- **Bloom Filter:** 2-bit 2048-entry indexed by `addr>>3`. False positive rate 8% → spurious write-set lookup. Avoids hash-table probe on 92% of reads → 14% throughput gain on Red-Black Tree (RBT) workload.
- **Privatization safety:** Encounter-time STMs expose speculative writes via locks held early; a privatizing transaction `p` freeing list head could cause reader `r` to access freed memory *after* `r` passed lock check but before commit. TL2 avoids because writes buffered → privatizer sees no stale nodes.

**Opacity Theorem Sketch:** Lemma: `rv` sampled at begin or extend is such that all values read with version ≤ `rv` were from snapshot at time `rv`. Because `GVC` monotonic and locks carry version of commit, any transaction that would cause `version>rv` re-validates; failure ⇒ abort. Commit lock acquisition prevents concurrent writer invisible increment past reader verification.

### 4.2 Hybrid TM: The Instrumentation Dilemma

HyTM classification [HyTM Revisited]:

- **PhTM (Levelt, et al):** All transactions run same *mode* at any time: HTM-only phase, STM-only phase, synchronized via global mode indicator. No cross-mode concurrency, thus no HTM instrumentation overhead. Simpler but mode oscillation cost high.
- **HyTM-NOrec, HyLSA:** Hardware fast-path runs concurrently with software slow-path. To ensure software visibility, hardware must instrument reads/writes: e.g., check global sequence lock `gsl` before committing. If `gsl≠snapshot`, abort. Instrumentation of `k` addresses requires `k` extra reads (TSX capacity pressure).
- **Hybrid Cohorts (Ruan & Spear):** Novel trade: hardware transactions never mutate global metadata (no increment of `gsl`). Instead, software transactions quiesce hardware: hardware increments thread-local ticker on commit, software waits for all hardware in-flight to drain. This yields 0 instrumented stores in HTM, only 1 load of `software_in_flight` bitmask, but hardware commits blocked while software commits.

Formal model [Alistarh]:

Define **direct access**: atomic RMW on base object shared memory.
**Cached access**: operates on thread-local `τ_i`; `cache-commit` propagates atomically if no conflict.

HTM transaction = sequence cached primitives + cache-commit. STM transaction = direct accesses only. HyTM = mixed.

Progress guarantees:

- `OF`: obstruction-free (aborts only if concurrent conflicting transaction)
- `PR`: progressive (above plus limited spurious aborts allowed)

**Impossibility Results:**

> **Theorem 1 (Uninstrumented HyTM impossible).** No strictly serializable HyTM provides non-trivial concurrency between hardware and software transactions if both reads and writes are uninstrumented (no direct accesses inside hardware Tx). Proof via covering execution where hardware Tx reads phantom value because software's direct write bypassed its tracking set.

> **Theorem 2 (Linear Instrumentation lower bound).** Any opaque, progressive HyTM where hardware transactions perform only `|Dset|` cached accesses must perform `Ω(|Rset|+|Wset|)` direct accesses (instrumentation) in worst case. Construction: adversary builds execution where hardware transaction touches `m` locations; software writer can blindside each unless hardware checks per-location metadata.

This matches intuition: to avoid software blind-writes, hardware must poll software metadata per address. TL2-style versioned locks: hardware reads lock table (direct) before each transactional read → instrumentation factor 2×.

PhTM* improvement: classify abort causes: `ABORT_CONFLICT` vs `ABORT_CAPACITY` vs `ABORT_PERSISTENT` (CLWB, syscall) vs `ABORT_NESTING`. Only persistent aborts trigger mode switch to software; conflict aborts spin in HTM with randomized backoff. This reduces spurious transitions by 41% on Haswell STAMP Vacation.

**Implementation Sketch HyTM-NOrec:**

```c
__thread long htm_version;
void htm_begin() { htm_version = gsl; }
bool htm_read(addr) {
  if (gsl != htm_version) _xabort();
  return *addr; // TSX already tracking
}
void htm_commit() {
  if (gsl != htm_version) _xabort();
  _xend();
}
```

Contention: single `gsl` becomes bottleneck at 32+ threads. Scalable HyTM replaces with versioned array `locks[]` striped.

### 4.3 Persistent Memory and NV-HTM

**Problem 1:** Flush aborts HTM. Code:

```c
XBEGIN
  *p = v;
  CLWB(p); // abort! -> XABORT
XEND
```

Thus naive PMEM TX inside HTM fails.

**Solution taxonomy:**

- **PHTM (Avni et al. DISC 2015) [PHTM]:** Define new hardware primitive **Transparent Flush (TF)** : `TF(α)` write-backs cache line without invalidating, without aborting Tx that read α. ARM `DC CVAC`, Intel `CLWB` *intent* but current Intel implementation still aborts; PHTM emulates via postponing flush to fallback path. API: `tx_write()` logs old value to undo structure resident in DRAM, `tx_end_log(T)` persists log records via `TF`, then data flush outside hardware critical section.
- **Crafty (PLDI 2020) [Crafty]:** Nondestructive undo logging inside HTM-compatible transactions. Key insight: perform HTM transaction to compute *persist ordering* but never flush inside. Three phases:

  1. `HTM-log`: Hardware transaction records writes to thread-local volatile undo buffer, no PMEM writes.
  2. Log Persist: outside HTM, `CLWB` undo entries + `SFENCE`.
  3. `HTM-apply`: second HTM re-executes same stores to PMEM *in place* (already logged, so crash-safe), then flushes data asynchronously.

  If crash between log persist and apply complete, recovery replays undo → original state. Since log persisted first, transaction atomic w.r.t crashes. Only 2 HTM executions; no `CLWB` inside HTM. Under low contention, Crafty beats NV-HTM+STM hybrid by 2.1× on B+Tree insert YCSB-A.

- **Buffered Durable Linearizability BDL [BDL 2025]:** Relaxes durability: transaction considered *durable* once its log hits WPQ, not necessarily NVM, permitting write-back after HTM commits. Reconciles HTM with persistent programming by buffering in volatile cache and allowing background flusher thread to coalesce. Formalized as *prefix-closed* persistent cut. Scenarios: add durability to existing HTM vEB tree, add HTM to existing persistent skip-list.

Crash-consistency protocol correctness condition:

> **Persist-before-visibility:** If transaction T commits logically (releases isolation), its undo/redo log must be persistent before any other transaction observes its writes after recovery.

Validator state machine for Crafty recovery:

```
log.state = PREPARING -> PERSISTED -> COMMITTED
crash before PERSISTED : discard log
crash between PERSISTED and COMMITTED : rollback using undo (or redo if redo-log variant)
crash after COMMITTED : no-op
```

Concurrency with NVM: DRAM and NVM pointers intertwined (common PMDK pattern). UHTM (MICRO 2020) proposes unbounded HTM for hybrid DRAM/NVM by staged conflict detection (Bloom signature for DRAM, precise for NVM) reducing false abort rate from 99% to 9%.

## 6 Limitations / Open Problems

- ***Global Clock Contention.*** TL2 GVC remains single-writer scalability choke at >64 threads. Hardware combining `fetch_add` via `RDMA` or per-core batching required. Deferred Clock reduces writes but increases read-set validation frequency (false positive extension thrash).
- ***HyTM Lower Bound vs Practice.*** Linear instrumentation bound assumes opaque progressive HyTM with invisible reads. Relaxing to *visible-read* HyTM (software writes in-place update version) breaks bound but adds SW overhead. Intel TDX/TLBG approach uses cache-line pinning but undocumented.
- ***Intel TSX Deprecation / Mitigation.* TSX disabled by default on microcode post-2021 due to MDS/ZombieLoad. TSX-NI bypass exists but vendor intent moves to TMX? Future HTM may be IBM-only. SW TM resilience critical.
- ***Persistent Memory Market.*** Optane 200/300 retired 2022. CXL-attached PMEM (SAMSUNG, Micron) uses different flush semantics: `CXL GPF` phase vs `CLWB`. Crafty assumption TF = CLWB may map to `CXL.mem` flush differently. ARM `DC CVAP` vs `DC CVAC` persistence domain distinction not captured.
- ***Crash model incompleteness.*** Real crashes: torn 8-byte stores on persistent controller WPQ not atomic? x86 guarantees 8-byte atomic persistence but PI tail fails. TF abstraction proven only for ADR (Asynchronous DRAM Refresh) domain, not eADR (extended, flush latches survive). eADR makes flushes redundant, restoring HTM usability but not present on all platforms.
- ***HyTM fairness.*** Hybrid Cohorts starves software transactions under high HTM throughput (hardware never quiesces). Need randomized token passing. DyAdHyTM uses simple threshold heuristic; formal fairness proof open.

## 7 Conclusion

TL2 demonstrated that commit-time locking, Bloom-accelerated write buffering, and a single global version clock suffice to provide opaque, privatization-safe transactions that coexist with conventional allocators and deliver performance competitive with hand-crafted fine-grained locks. Its adoption into GCC TM and RSTM cemented decade of STM baseline.

HyTM revealed fundamental antagonism between uninstrumented hardware speed and software observability: the cheaper HTM path, the more software must coordinate. The linear instrumentation lower bound is the CAP theorem of TM — choose at-most two of {uninstrumented HTM, progressive opacity, nontrivial cross-mode concurrency}. Practical HyTMs — Phased, Cohort-Quiesced, Adaptive — carve Pareto frontier by judiciously paying instrumentation (one global mode bit vs per-address version) or blocking (hardware drains).

Persistent Memory closed loop: The flush-aborts-HTM incompatibility, long seen as disqualifier, is circumvented by logging-first designs (PHTM, Crafty) or durability relaxation (BDL). Crafty's nondestructive undo shows HTM need not persist inside transaction; persisting the *intention* suffices.

Unified blueprint:

1. Language runtime wraps `atomic` as: try HTM fast-path with Cohort check; on persistent abort, switch to software; commit via GVC versioning; persist log via `CLWB+SFENCE`; apply.
2. Future hardware should expose TF-like primitive (write-back without abort) and per-NUMA-domain GVC acceleration. Real fast path may be `eADR` + HTM (no flush needed) on HBM-PMEM hybrid via CXL.

For DB engine designers: NV-HTM achieves 2–5× over PMDK TX on low-contention YCSB; for graph analytics: DyAdHyTM achieves 8× over lock; for toolchain builders: TL2's 200 LOC commit protocol still competitive baseline after 18 years.
