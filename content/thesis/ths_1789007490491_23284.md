# CompCert and Compositional Certified Compilation: Simulation Proofs, the Block-Based Memory Model, and Verified Compilation of Open Modules

## Abstract

*CompCert* is a formally verified optimizing C compiler, implemented and proved correct in the Coq proof assistant. This thesis presents the machinery that makes it trustworthy: semantic preservation as refinement over observable behaviors; per-pass forward simulation diagrams composing vertically into an end-to-end correctness theorem; a block-based memory model with byte offsets and permissions grounding every intermediate language; and verified frontends and backends spanning parsing, register allocation, and assembly emission. We then trace the frontier beyond whole-program verification — CompCertO's open-module semantics and simulation conventions, CompCertM's heterogeneous modules, and direct-refinement frameworks — yielding horizontal and vertical compositionality: separately compiled, possibly unverified components linked with machine-checked guarantees. We evaluate the evidence: ~100,000 lines of Coq, six person-years, performance roughly 10% behind GCC at `-O1`, and differential testing that found hundreds of bugs in unverified compilers but none in CompCert's verified core. We close with limitations: the trusted computing base, performance and language-subset tradeoffs, and the open challenge of verified concurrency-aware compilation.

## 1. Introduction

Compilers are the most trusted — and among the least scrutinized — components of the software toolchain. A single miscompilation silently invalidates every program it translates: Csmith-style testing campaigns found hundreds of miscompilation bugs in mature compilers like GCC and LLVM [1]. Testing, review, and certification reduce but cannot eliminate this risk: testing samples an effectively infinite execution space.

*Certified compilation* attacks the problem at its root. A certified compiler is accompanied by a machine-checked proof of a semantic preservation property: the generated machine code behaves as prescribed by the semantics of the source program. The CompCert project, initiated by Xavier Leroy in 2005, realized this vision for a realistic compiler, translating a large subset of the C language (Clight) to assembly for PowerPC, ARM, x86, and RISC-V targets [1][2]. At approximately 100,000 lines of Coq and six person-years of effort, CompCert's proof is among the largest ever performed with a proof assistant [2].

CompCert's central contribution is its proof architecture: formal semantics for each of its ~20 languages, and a per-pass *simulation diagram* relating target transitions to source transitions. These diagrams compose — fifteen independently proved simulations yield whole-compiler semantic preservation by construction. This thesis examines that architecture: semantic preservation as behavioral refinement, forward simulation diagrams and their variants, the shared block-based memory model, the verified frontend and backend, and the compositional extensions (CompCertO, CompCertM, direct refinement) that bring machine-checked guarantees to separately compiled, linked, partially unverified components.

## 2. Background

### 2.1 What "correct compilation" means

To a first approximation, a compiler preserves semantics if the generated code exhibits exactly the same set of observable behaviors as the source code: the same termination properties and the same input/output actions. CompCert makes this precise through two refinements of the naive statement [2]:

1. **Source nondeterminism.** C permits several evaluation orders; the compiler may legitimately *reduce* nondeterminism by selecting one — the target need only exhibit behaviors the source *could* exhibit.
2. **Undefined behavior.** C programs can "go wrong" (null dereference, signed overflow, aliasing violations). CompCert may replace source undefined behavior with more defined target behavior, but must *never* introduce undefined behavior where the source was well-defined.

Formally:

> **Theorem: (Semantic Preservation).** If the compiler produces compiled code *C* from source code *S* without reporting compile-time errors, then every observable behavior of *C* is either identical to an allowed behavior of *S*, or improves over such an allowed behavior of *S* by replacing undefined behaviors with more defined behaviors. [2]

Behaviors are traces of observable events — system calls and volatile-memory accesses — plus an outcome: termination, divergence, or going wrong. Semantic preservation is thus a *refinement*: any safety property proved of the source transfers to the executable [1].

### 2.2 Three approaches to verified compilers

Leroy distinguishes three strategies [1]:

| Approach | Mechanism | Strength | Weakness |
|---|---|---|---|
| Proof-carrying code | Compiler emits checkable proof per compilation | Flexible | Proof burden; checker trusted |
| Translation validation | Independent verifier checks each compilation | Works on existing compilers | Verifier complexity; per-run cost |
| Verified compiler (CompCert) | Compiler itself proved correct once | One proof covers all compilations | Enormous proof effort; prover-friendly code required |

CompCert takes the third path: passes are written in Coq, extracted to OCaml, each carrying a proof; unverified components (notably the parser) are validated by other means. The trusted base shrinks to the Coq kernel, extraction, frontend glue, assembler/linker, and hardware — far smaller than "the entire optimizing compiler."

### 2.3 The pass structure

CompCert compiles through a tower of intermediate languages: C → Clight → C#minor → Cminor → CminorSel (frontend), then RTL → LTL → Linear → Mach → Asm (backend) [1][2]. Each language has a formal operational semantics — big-step for high-level languages, small-step for the backend — and each pass is proved correct against both. The original presentation lists 15 simulation diagrams, one per pass; current CompCert has more passes but the same architecture.

## 3. Methodology

### 3.1 Coq as programming language and logic

The compiler's core passes are written as pure Gallina functions, *extracted* to OCaml; correctness properties are Coq propositions proved interactively and rechecked mechanically. **The proof checker, not the proof author, is the final authority** — Coq's kernel re-verifies every inference step, so confidence rests on the small kernel rather than human review of a 100,000-line argument [2]. This imposes discipline: passes must be total, structurally recursive functions. Heuristics resisting that formulation — notably graph-coloring register allocation — required careful engineering, including a machine-checked termination proof [1].

### 3.2 Simulation diagrams

The workhorse of the CompCert proof is the *simulation diagram*. Suppose a source language *L₁* and target language *L₂* with small-step transition relations →₁ and →₂, and a relation *R* between source and target states. A **forward simulation** states: whenever *s₁ R s₂* and the source steps *s₁ →₁ s₁′* emitting trace *t*, the target takes zero or more steps *s₂ →₂\* s₂′* emitting *t*, with *s₁′ R s₂′* — the target "keeps up" up to stuttering.

CompCert needs four flavors of forward simulation to handle the realities of compilation [1]:

- **Lock-step:** one source step maps to exactly one target step (e.g., simple translations).
- **Plus:** one source step maps to one *or more* target steps (e.g., expansion of a complex operation into several instructions).
- **Star:** one source step maps to zero or more target steps, with a measure to rule out infinite stuttering (e.g., passes that eliminate no-ops).
- **Option:** like star, but the measure may also decrease on "silent" target steps.

Each pass proves the flavor it needs; a composition theorem chains them into a whole-compiler forward simulation, from which semantic preservation follows. **Backward simulations** — every target behavior is covered by a source behavior — are derived from forward simulations under target-determinacy conditions [1].

### 3.3 Research method for this thesis

This thesis synthesizes the primary literature: Leroy on CompCert [1][2], Blazy and Leroy on Clight semantics [3], Besson, Blazy, and Wilke on the concrete memory model [4], Koenig and Shao's CompCertO [5][6], and Zhang et al.'s direct-refinement framework [7]. Performance and proof-size figures come from the projects' published evaluations; limitations are assessed against each artifact's stated scope.

## 4. Deep Dive

### 4.1 The block-based memory model

Nearly every language in CompCert shares a single, elegant abstraction of memory: memory is a finite collection of disjoint **blocks**, each block an array of bytes indexed by integer offsets [1][4]. A pointer is a pair *(b, o)* of a block identifier *b* and a byte offset *o* within that block. Pointer arithmetic is defined only within a block; comparing or subtracting pointers from different blocks is undefined. This captures the essence of the C object model — distinct allocations never alias — while remaining abstract enough to admit many implementations.

Each byte carries a **permission** — *Freeable*, *Writable*, *Readable*, *Nonempty* — forming a lattice governing access. Allocation creates a fresh block; `free` invalidates one; loads and stores check permissions and alignment. Crucially, the model supports *memory injections* — mappings from source blocks to target blocks plus offsets — by which simulation relations track layout transformations such as spilling a variable to a stack slot [1].

```python
# Illustrative sketch of the CompCert block-based memory model
from enum import IntEnum

class Perm(IntEnum):
    NONEMPTY = 0
    READABLE = 1
    WRITABLE = 2
    FREEABLE = 3  # top of the permission lattice

class Block:
    def __init__(self, size: int):
        self.cells = bytearray(size)
        self.perms = [Perm.FREEABLE] * size

class Memory:
    def __init__(self):
        self.blocks: dict[int, Block] = {}
        self.nextblock = 0
    def alloc(self, size: int) -> int:
        b = self.nextblock; self.nextblock += 1
        self.blocks[b] = Block(size)
        return b
    def load(self, b: int, ofs: int, nbytes: int) -> bytes:
        blk = self.blocks[b]  # KeyError models a dangling pointer: "going wrong"
        assert all(p >= Perm.READABLE for p in blk.perms[ofs:ofs+nbytes])
        return bytes(blk.cells[ofs:ofs+nbytes])
    def free(self, b: int) -> None:
        del self.blocks[b]  # subsequent accesses are undefined
```

> **Theorem: (Memory injection preservation).** If `mem_inject f m1 m2` relates a source memory `m1` to a target memory `m2` via injection `f`, then every load, store, allocation, and free performed in `m1` is mirrored by a corresponding operation in `m2` preserving the values of all injected pointers. Compilation passes that rearrange memory (stack layout, spilling) are correct *because* they preserve a suitable injection. [1]

Besson, Blazy, and Wilke proved an **enhanced, concrete memory model** mapping abstract pointers to concrete 32-bit integers, making memory finite and the binary encoding of pointers reason-about-able — validating the abstract semantics as a sound abstraction of machine reality [4].

### 4.2 Simulation relations, injections, and the "option" diagram

The subtlety lies in the simulation relations. In register allocation, the source has infinitely many pseudo-registers; the target has finitely many machine registers plus stack slots. The relation *R* maps each live pseudo-register to its location, and every source step must be matched — including steps where the target inserts spill code (*plus* simulation) or deletes dead moves (*star* simulation with a decreasing measure) [1].

The recurring **memory injection diagram** carries an injection `f` between source and target memories; each source step is matched by target steps preserving `f`, possibly extended with fresh blocks. Passes need not preserve layout, only the injection — arguably CompCert's deepest methodological contribution, reappearing in CompCertO as the *simulation convention* mediating C-level and assembly-level interactions [5].

```haskell
-- Sketch of a forward simulation in a dependently-typed metalanguage
data Sim : State S -> State T -> Trace -> Type where
  LockStep :: (s1 ~>1 s1') -> (s2 ~>2 s2')   -- same trace t
           -> Sim s1 s2 t -> Sim s1' s2' t
  Stutter  :: (s2 ~>2 s2')                   -- silent target step
           -> Sim s1 s2 t -> (measure s2' < measure s2)
           -> Sim s1 s2' t
-- The measure rules out infinite stuttering: liveness is preserved.
```

### 4.3 Verified frontends: from C to Clight

The frontend begins where trust is thinnest: parsing real C. The parser, elaborator, and type checker are written in OCaml and **not** verified; validation comes from proving the elaborated-AST-to-Clight translation preserves semantics [1]. Clight is a designed subset — structured control flow, explicit operators. The C-to-Clight pass is among the largest proofs, handling sequence points, CompCert's committed right-to-left evaluation order, and bit-level operator semantics over the memory model.

CompCert's C semantics is **deterministic by construction** for evaluation order, resolving C's nondeterminism toward one legal order; the simulation framework shows this is a valid refinement — e.g., `f() + g()` evaluates `g` first and prints `gf`, one of the standard's two permitted behaviors [2].

### 4.4 Verified backends: RTL to Asm

The backend is where CompCert earns its "optimizing" qualifier. Key verified passes include:

- **Instruction selection** (CminorSel → RTL): matches complex expressions onto target instruction idioms.
- **Constant propagation, CSE, and dead-code elimination** over RTL, each proved via forward simulations whose dataflow analyses are themselves verified.
- **Register allocation** (RTL → LTL): a verified graph-coloring allocator with iterated coalescing, proved via the injection-carrying simulation of §4.2 — historically the most delicate backend proof [1].
- **Spilling, stack layout, and calling conventions** (LTL → Linear → Mach): lowers the abstract machine to concrete stack frames, proved against the memory model.
- **Assembly emission** (Mach → Asm): the Asm language has a formal semantics over registers, memory, and a program counter; the final theorem connects Clight execution to Asm execution [1].

Backend languages use **small-step semantics** so non-terminating programs — the norm in reactive, embedded software — get the same guarantees. Big-step/small-step equivalence for terminating programs is itself proved, bridging the two styles [3].

```rust
// Sketch: permissions as a lattice, in the style of the verified model
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
enum Perm { Nonempty, Readable, Writable, Freeable }

struct MemByte { val: u8, perm: Perm }

fn checked_load(mem: &[MemByte], ofs: usize, n: usize) -> Option<Vec<u8>> {
    let slice = mem.get(ofs..ofs + n)?;
    if slice.iter().all(|b| b.perm >= Perm::Readable) {
        Some(slice.iter().map(|b| b.val).collect())
    } else {
        None // models "going wrong": stuck execution, not a crash
    }
}
```

### 4.5 CompCertO, CompCertM, and compositional correctness

Classic CompCert verifies *whole programs*: `main` is compiled and the theorem speaks of closed execution. Real software is built from separately compiled modules linked against libraries, some of them unverified. **CompCertO** (Koenig and Shao, PLDI 2021) extends CompCert to *open modules* [5][6]. Its innovations:

1. **Interaction semantics.** Each language's semantics becomes a labeled transition system over *interactions* (calls to/returns from the environment), defining module behavior relative to an arbitrary context.
2. **Simulation conventions.** A convention `C : C ⇔ A` relates C-level to assembly-level interactions — the memory injection's role for closed programs — absorbing the calling-convention representation gap.
3. **Horizontal and vertical composition.** Open forward simulations compose *vertically* (pass to pass) and *horizontally* (module to module, modeling linking via a `⊕` operator). The main result:

> **Theorem: (Compositional correctness of CompCertO).** For a Clight program *M* and an Asm program *M′* with `CompCert(M) = M′`, the open simulation `Clight(M) ≤C↠C Asm(M′)` holds. Consequently, separately compiled modules can be linked — `Clight(M₁.c) ⊕ ⋯ ⊕ Clight(Mₙ.c) ≤C↠C Asm(M.s)` — with the guarantee that the linked assembly refines the composed source semantics [5].

**CompCertM** and successors tackle *heterogeneous* modules: components compiled through different chains, or hand-written assembly linked against compiled C [7]. The POPL 2024 framework of Zhang et al. unifies these strands with **direct refinements between open modules**, achieving fully composable and *adequate* verified compilation — adequacy meaning the refinement transfers end-to-end behavioral guarantees to the linked target, closing a gap in earlier accounts [7]. A three-dimensional refinement algebra (POPL 2025) further unifies compositional verification and certified compilation in one algebraic structure.

```tla
---- MODULE CompCertSim ----
EXTENDS Naturals, Sequences
CONSTANTS SrcStates, TgtStates, Events
VARIABLES s, t, trace
R(s_, t_) == (* simulation relation: source state s_ related to target state t_ *)
Init == s \in SrcStates /\ t \in TgtStates /\ R(s, t) /\ trace = <<>>
SrcStep == \E s2 \in SrcStates, e \in Events :
             /\ Step1(s, s2, e) /\ trace' = Append(trace, e) /\ s' = s2
             /\ \E t2 \in TgtStates : Step2Star(t, t2, e) /\ R(s2, t2) /\ t' = t2
Next == SrcStep
Spec == Init /\ [][Next]_<<s,t,trace>>
====
```

The TLA+ sketch captures the star-simulation of §3.2 as a temporal property: every source step with event `e` is matched by target steps emitting `e`, re-establishing `R`.

## 5. Empirical Evaluation and Proofs

### 5.1 Scale of the formalization

| Artifact | Scale |
|---|---|
| Coq source | ~100,000 lines (2008 figure; the current development is substantially larger) [2] |
| Effort | ~6 person-years for the initial verified compiler [2] |
| Passes with simulation proofs | 15 in the original presentation; more in current CompCert [2] |
| Target architectures | PowerPC, ARM, x86 (IA-32), RISC-V, AArch64 in current releases [1] |
| CompCertO proof delta | ~3% additional proof relative to CompCert for compositional correctness [5] |

Notably, compositional correctness — arguably the most conceptually demanding extension — cost only ~3% more proof, because simulation conventions slot cleanly into the per-pass architecture [5].

### 5.2 Performance: the cost of certainty

On PowerPC and ARM, CompCert-generated code runs **at least twice as fast as GCC unoptimized**, and roughly **10% slower than GCC `-O1`**, 15% slower at `-O2`, 20% at `-O3** [2]; on register-starved IA-32 the gap to `-O1` is ~20%. The deficit concentrates in dense-matrix HPC codes needing aggressive loop optimization [2]. For safety-critical embedded software — where `-O1`-level performance with absolute correctness beats `-O3` with miscompilation risk — the tradeoff is practical.

### 5.3 Differential testing: the dog that didn't bark

The strongest empirical evidence is negative: Csmith-style differential testing found **hundreds of miscompilation bugs in GCC and LLVM** but essentially none in CompCert's verified passes [1]. Bugs surfaced in *unverified* components (parser, elaboration edge cases) — exactly what the trusted-base analysis predicts: verification pushes defects to the artifact's boundary, where each is fixed or motivates extending the verified portion.

### 5.4 What the proofs actually guarantee — and are checked to guarantee

Every claim above is a kernel-rechecked Coq theorem. The end-to-end theorem (original PowerPC backend):

```
Theorem transf_c_program_correct:
  forall prog tprog trace n,
    transf_c_program prog = Some tprog ->
    Csem.exec_program prog trace (Vint n) ->
    PPCsem.exec_program tprog trace (Vint n).
```

Small-step variants extend this to diverging programs; CompCertO's compositional theorem and the POPL 2024 adequacy results are likewise fully mechanized [5][7].

## 6. Limitations

**The trusted computing base.** Verification concentrates trust rather than eliminating it: the Coq kernel, extraction and the OCaml compiler, the unverified parser/elaborator/type checker, the assembler and linker, and the hardware [1]. Bugs *have* been found in the unverified frontend; the verified core is exactly as strong as its boundary, and extending verification outward (verified parsing remains future work) is the honest direction of improvement.

**Language subset.** CompCert compiles Clight, not all of C — early versions excluded computed `goto`, VLAs, and variadics; current versions cover a large but incomplete C11/C17 fragment. Out-of-subset programs are rejected, not miscompiled — safe, but an adoption barrier for legacy code.

**Performance ceiling.** The ~10–20% gap to GCC `-O2`/`-O3` reflects missing loop optimizations (unrolling, vectorization, polyhedral transforms), each demanding its own simulation proof — an active but expensive research area.

**Concurrency.** Classic CompCert is sequential; its memory model knows no data races or weak memory. CompCertO models environment interaction, not true shared-memory concurrency. CompCertTS adds thread-safe semantics and CompCertOC (PLDI 2025) handles multi-threaded programs with shared stacks — but verified compilation of racy, weak-memory C11 concurrency remains an open frontier [5][7].

**Specification risk.** CompCert proves the compiler respects its *formal semantics* of C — but if that semantics mis-models intent or hardware, the proof guarantees the wrong thing. The concrete memory model work [4] attacks exactly this risk, validating the abstract semantics against a more machine-faithful one.

## 7. Conclusion

CompCert turned "verified compiler" from aspiration into engineering discipline. Its enduring contributions are architectural: semantic preservation as behavioral refinement, per-pass simulation diagrams in four flavors composed into whole-compiler correctness, a block-based memory model whose injections absorb layout transformations, and a clean split between verified core and explicit trusted base. The compositional turn — CompCertO's open modules and simulation conventions, CompCertM's heterogeneous linking, adequate direct refinements — extends these guarantees to how software is actually built: separately compiled, partially unverified, linked components. The empirical record shows machine-checked proof is a practical tool for compiler correctness, not merely a theoretical one.

Open problems: verified parsing to close the trusted base's largest hole; verified loop optimization and vectorization; and weak-memory concurrency — where "observable behavior" itself must be renegotiated — as the grand challenge. The methodology, however, is the field's template: state the semantics, prove the simulation, let the kernel check your work. Twenty years on, CompCert remains the standard.
