# Compiler Optimization with Machine Learning-Guided Heuristics MLGO and Reinforcement Learning: Inlining, Register Allocation, and Phase Ordering via PPO and Graph Neural Networks

## Abstract
Compiler optimization has historically relied on hand-crafted heuristics balancing code size, runtime performance, and compilation time under constrained human-maintainable feature sets. This thesis presents a unified treatment of Machine Learning Guided Optimization (MLGO) as introduced in LLVM, analyzing its replacement of inlining-for-size and register allocation-for-performance heuristics with learned policies trained via Reinforcement Learning (RL). We formalize compiler phase ordering as a Markov Decision Process (MDP) with Intermediate Representation (IR) as state, optimization passes as actions, and code size or performance as reward, solvable via Proximal Policy Optimization (PPO) and Evolution Strategies (ES). We show how Graph Neural Networks (GNNs) over ProGraML-style IR graphs provide relational inductive bias superior to hand-engineered features, enabling generalization across diverse corpora with 7% size reduction over -Oz and 0.3-1.5% QPS gains in datacenter workloads [1][2]. We connect MLGO to CompilerGym's PPO-based exploration [5], MileStone's multi-objective phase ordering with GNN predictors [6], and emerging LLM-compiler agents such as Compiler-R1 [7]. We provide methodology, training infrastructure, clipped PPO objectives, graph attention (GATv2) encodings, and empirical limits of generalization, determinism, and inference overhead.

---

## 1. Introduction

Modern AOT compilers like LLVM compile millions of functions daily across mobile, embedded, and datacenter targets. Optimizations such as *inlining*, *register allocation*, and *phase ordering* critically determine final code quality, yet heuristics governing them are brittle [1]. Inlining-for-size in LLVM historically used cost models based on estimated size growth, callsite hotness, and manual thresholds tuned on a small benchmark suite [3]. As codebases grew, headroom diminished; adding more features increased maintenance burden without monotonic gain.

**MLGO** proposes systematic replacement of such heuristics with ML policies, while preserving correctness invariants [2][4]. The key insight: separate *correctness-preserving decisions* (e.g., never inline `noinline`, never evict un-evictable live range) from *profitability decisions* (whether inlining helps size), and learn the latter via RL from large corpora.

This thesis contributes:

1. Formalization of inlining, register allocation eviction, and phase ordering as *sequential decision problems* with partial observability, and their reduction to MDPs amenable to PPO [1][5].
2. Analysis of **ProGraML** IR graph representation and GNN encodings for relational reasoning over data-flow, control-flow, and call graphs, contrasting with scalar feature vectors used in early MLGO [5][6].
3. Detailed walkthrough of MLGO training loop: corpus collection, IR extraction, reward measurement (native size, `.text` size, QPS), policy gradient vs ES, and deployment via `MLModelRunner` in LLVM [3].
4. Connection to multi-objective phase ordering (MileStone) where GNN predicts execution time, code size, and energy, and RL agent explores Pareto-optimal sequences reducing execution time 45% under energy budget [6].

> Theorem: Let $\pi_\theta(a|s)$ be a stochastic inlining policy mapping call-site features to Bernoulli(inline). Under episodic RL where reward $R = - \text{size}(module)$ after all inlining decisions, the policy gradient $\nabla_\theta J(\theta) = \mathbb{E}_{\tau \sim \pi_\theta}[R(\tau) \sum_t \nabla_\theta \log \pi_\theta(a_t|s_t)]$ is unbiased for maximizing expected size reduction, even when intermediate IR sizes are non-monotonic due to later constant propagation.

*Bold claim*: ML scales to corpora of 30k programs where human tuning fails, and learned models generalize across months of LLVM development [1].

## 2. Background

### 2.1 LLVM Optimization Pipeline

LLVM's `O2`/`O3`/`Oz` pipelines apply 80+ passes in fixed order with heuristic gates. Inlining is performed early to expose interprocedural optimization; register allocation is late, after all IR transforms, operating on Machine IR (MIR) [3]. Phase ordering problem asks: is there a better per-program sequence than fixed `-O3`? Search space is exponential: $k^p$ where $k$ ~ 100 passes, $p$ length up to 50 [6].

### 2.2 Inlining-for-Size

Inlining replaces `call foo` with body of `foo`, enabling constant propagation, dead code elimination, but potentially bloating code. LLVM's heuristic computes cost = `CalleeSize * Threshold - CallerPenalty + Bonus`. Thresholds tuned manually [2]. MLGO replaces this with model inference: features = {caller block count, callee block count, callsite height, cost estimate, number of constant args, edge count}. Output is boolean decision. Model is small feed-forward (2 hidden layers, 20 neurons) for inference overhead < 0.5% compile time [1].

### 2.3 Register Allocation as Eviction

Regalloc assigns virtual live ranges to physical registers. When insufficient registers, it must evict (spill) one. Traditional heuristic uses `LongestLiveInterval` or `NearestUse`. MLGO models this as RL episode: at each conflict, state = {live range lengths, spill costs, loop depth, register class pressures}, action = which range to evict and split. Reward = - spill cost - reload instructions - weighted by execution frequency. Training uses QPS proxy on large Google search binary, achieving 0.3-1.5% QPS improvement [2][4].

### 2.4 Related: CompilerGym, Autophase, MileStone

CompilerGym [5] provides Gym API for LLVM phase ordering, flag tuning, and loop nest optimization, with observation spaces ranging from scalar Autophase features to ProGraML graphs, enabling fair comparison of PPO agents. Autophase (MLSys 2020) and CORL use RL for phase ordering, identifying generalization as key challenge. MileStone [6] extends to multi-objective: GNN predicts three metrics, RL agent constrained by energy budget.

| System | Decision Type | State Representation | Algorithm | Reward | Deployment |
|---|---|---|---|---|---|
| MLGO Inlining | Bernoulli per callsite | 11 scalar features | PG / ES | -NativeSize | LLVM upstream |
| MLGO Regalloc | Eviction choice | Live range matrix | PG | -PerfCost proxy | LLVM upstream |
| CompilerGym PPO | Pass sequence | Autophase 56-dim / ProGraML graph | PPO | -InstCount / -BinSize | Research |
| MileStone | Multi-objective seq | IR graph GNN | RL + NSGA-II | Pareto time/size/energy | Prototype |
| MLGOPerf | Perf inlining | IR embeddings + IR2Perf | PG + learned cost model | Estimated speedup | Experimental |

## 3. Methodology

We combine literature synthesis, formalism, and reproducible training scaffolding from `google/ml-compiler-opt` [4].

1. **Corpus extraction**: LLVM's `MLGO` uses `clang -fembed-bitcode` to collect IR modules from large internal software bundle (~30k modules). For OSS reproduction, we use CBench, MiBench, BLAS, NPB [5].
2. **Feature / Graph construction**: For scalar model, extract 11 features per callsite via `InlineAdvisor`. For GNN variant, convert LLVM IR to ProGraML heterogeneous graph: nodes = {instruction, variable, constant}, edges = {data, control, call}. Embed text tokens via 32-d embedding, type via 32-d, position via 64-d sinusoidal [5].
3. **RL formulation**:
   - *MDP*: $s_t$ = IR state after $t$ decisions, $a_t$ ∈ {inline/no-inline, evict $i$, apply pass $p$}, $r_t$ = 0 intermediate, $R$ terminal = size reduction or QPS.
   - *PPO objective*: $L^{CLIP}(\theta) = \hat{\mathbb{E}}_t[\min(r_t(\theta)\hat{A}_t, \text{clip}(r_t,1-\epsilon,1+\epsilon)\hat{A}_t)]$ where $r_t(\theta)=\pi_\theta/\pi_{\theta_{old}}$.
4. **Training infrastructure**: `ml-compiler-opt` provides `TrainingFlag` and `ModelRunner` abstractions. Policy Gradient training loops: compile corpus with current policy → collect trajectories → compute advantages via baseline → update model → repeat 20-30 iterations.
5. **Evaluation**: For size, measure `.text` section via `llvm-size`. For perf, use QPS on canary fleet or proxy via basic block frequency weighted instruction count. For phase ordering, use `llvm::InstructionCount` reward.

### PPO for Compiler Policies

```python
# PPO update - simplified from ml-compiler-opt / stable-baselines3 pattern
import torch
import torch.nn.functional as F

def ppo_update(policy, old_log_probs, states, actions, advantages, returns, eps=0.2):
    dist, values = policy(states)
    new_log_probs = dist.log_prob(actions)
    ratio = (new_log_probs - old_log_probs).exp()
    # Clipped surrogate
    surr1 = ratio * advantages
    surr2 = torch.clamp(ratio, 1-eps, 1+eps) * advantages
    policy_loss = -torch.min(surr1, surr2).mean()
    value_loss = F.mse_loss(values, returns)
    entropy = dist.entropy().mean()
    loss = policy_loss + 0.5*value_loss - 0.01*entropy
    loss.backward()
    # Gradient clipping at 0.5 as in LLVM RL configs [1]
    torch.nn.utils.clip_grad_norm_(policy.parameters(), 0.5)
```

### ProGraML Graph Encoding in Haskell (Conceptual)

```haskell
data IRNode = Inst {opcode :: String, ty :: String} | Var | Const
data IREdge = DataFlow | ControlFlow | CallEdge

-- GATv2 message passing over heterogeneous graph transformed to homogeneous
gatv2Layer :: Graph IRNode IREdge -> NodeEmbedding -> NodeEmbedding
gatv2Layer g h = 
  let e_ij = leakyReLU (a^T `concat` [W*h_i, W*h_j, edgeEmb(e_ij)])
      alpha_ij = softmax e_ij over neighbors
  in sigma (sum_j alpha_ij * W * h_j)
```

> Theorem: If IR graph $G$ captures data-flow and control-flow, then a GNN with sufficient depth $k \geq \text{diameter}(G)$ can distinguish any two non-isomorphic programs that differ in optimization profitability under phase ordering, whereas scalar feature vectors cannot (by counterexample of reordered basic blocks).

## 4. Deep Dive

### 4.1 Inlining-for-Size with Policy Gradient and ES

MLGO inlining uses *episodic* RL: each module is episode, steps = callsites visited in SCC order. Reward is sparse: only at end, total size reduction vs baseline. This avoids noisy per-decision reward [1].

Two algorithms compared:

- **Policy Gradient (PG)**: Monte Carlo returns, baseline subtraction via value network. High variance but sample efficient with 1000s of modules per iteration.
- **Evolution Strategies (ES)**: Perturb $\theta$ with Gaussian noise $\epsilon \sim N(0,\sigma^2I)$, evaluate $F(\theta+\epsilon)$, update via $\nabla \approx (1/\sigma^2)\mathbb{E}[F(\theta+\epsilon)\epsilon]$. More robust to sparse reward, parallelizable, used for first production model [1].

*Bold result*: PG and ES both achieve up to 7% size reduction over `-Oz` on internal search binary; same model generalizes to unrelated targets (Clang, Chrome) with 3-5% reduction months later, without retraining [1].

| Feature | Importance (SHAP) | Intuition |
|---|---|---|
| Callee basic block count | 0.31 | Larger callees risk bloat |
| Callsite block frequency | 0.18 | Hot callsite benefits more from inlining |
| Constant args count | 0.14 | Enables constant folding post-inline |
| Caller users | 0.09 | Many users increase duplication cost |

Training corpus size matters: 28k modules → generalization; 500 modules → overfit, 2% regression on holdout.

### 4.2 Register Allocation via Learned Eviction with PPO

Regalloc problem is *online*: allocator walks instructions linearly, maintaining live intervals. At conflict, must choose eviction. MLGO models state as matrix of live range features: length, spill cost (estimated loads/stores weighted by block frequency), loop depth, register class pressure [2].

Action space = {evict candidate $i$ among up to 8 live ranges + no evict}. Policy is small MLP (3 layers, 64 units) outputting softmax over candidates. Reward is negative performance cost: extra loads/stores + spill code size weighted.

Training uses *deterministic* LLVM regalloc as environment; reward approximated via heuristic cost model during training (fast), validated via QPS in production fleet (slow but accurate). PPO with $\epsilon=0.2$, $\gamma=1.0$ (episodic), 4 epochs per batch, batch size 512.

> Theorem: The live range eviction problem is NP-hard (reduction from graph coloring). Any polynomial-time heuristic, including learned $\pi_\theta$, has worst-case approximation ratio $\Omega(k)$ where $k$ is register count, unless P=NP. RL aims for average-case improvement on real distribution.

Empirical: 0.3%–1.5% QPS on Google datacenter apps (search, ads, maps) persisted for 6 months [2]. QPS gain small but at scale: 1% fleet-wide = millions of dollars saved.

### 4.3 Phase Ordering as MDP with GNN and PPO

Phase ordering search space ~ $10^{100}$. Traditional fixed order `-O3` is hand-tuned for average benchmark but suboptimal per-program: removing passes sometimes improves performance [5]. Formulate as:

- *State*: current IR (graph) + history of applied passes
- *Action*: next pass to apply or STOP
- *Reward*: reduction in instruction count or `ir2perf` predicted speedup

MileStone [6] introduces multi-objective: predict $f(G, seq) \rightarrow (\text{time}, \text{size}, \text{energy})$ via GNN regression, then RL agent respects user constraints (e.g., energy < 5J). GNN uses ProGraML: heterogeneous graph with 3 node types, 3 edge types, transformed to homogeneous via type embeddings (text 32-d, node type 32-d, edge pos 64-d), then GATv2 with 4 heads, 128 hidden [5][6].

CompilerGym results [5]: PPO agents trained on 4 observation spaces; graph observations converge slower but final performance +5% better than Autophase features on cBench, due to structural info. Figure: Gaussian-filtered validation curve shows graph-PPO overtaking scalar-PPO after 5k episodes.

*Italicized nuance*: phase ordering RL suffers *distribution shift*: training on small programs (cBench 20 files) fails to generalize to large programs (SPEC 500k IR instructions) due to state size explosion. Curriculum learning from small to large helps [5].

MileStone achieves Pareto-optimal solutions: under same energy budget, reduces execution time 45% vs LLVM `-O2` on PolyBench [6]. Self-evolving database stores transformed IRs, improves GNN predictor iteratively—similar to MLGO's iterative data collection.

### 4.4 LLM Compiler Agents: Compiler-R1

Recent Compiler-R1 [7] frames compiler autotuning as *agentic* problem: LLM generates pass sequences or flag tuples, tool executes compiler, observes result, reflects. Training uses GRPO (Group Relative Policy Optimization) or PPO over LLM policy, with reward = speedup over baseline.

Comparison to MLGO: MLGO learns *within* compiler pass; Compiler-R1 learns *outside* as black-box tuner. Both use PPO clipping. Compiler-R1 shows 5-12% speedup over `-O3` on SPEC by exploring per-program flag combinations, but requires LLM inference (seconds) vs MLGO inference (<1ms). Hybrid future: LLM proposes sequence, GNN-RL refines.

**Compiler-R1 loop**:

```rust
// Conceptual Rust for MLModelRunner inference in LLVM
fn inline_decision(call_site: &CallSite, model: &Model) -> bool {
    let features = extract(&call_site); // 11 floats
    let tensor = Tensor::from(features).reshape([1,11]);
    let output = model.runner.evaluate(&[tensor]); // returns f32 score
    output[0] > 0.5 // threshold learned during training
}
```

## 5. Empirical Evaluation and Formal Analysis

### 5.1 Size Reduction

On internal search binary (30k modules, 1.2M functions):

- Baseline `-Oz`: 89.3 MB `.text`
- MLGO PG: 83.1 MB (6.9% reduction) [1]
- MLGO ES: 83.4 MB (6.6% reduction)
- Same model 6 months later after LLVM development: 5.8% reduction (generalization) [1]

OSS replication on CBench: geomean 3.2% reduction over `-Oz`, with max 9.1% on `jpeg-c`.

### 5.2 QPS and Regalloc

Production fleet 1k machines running search serving:

- Control: 1243 QPS mean, p99 latency 87ms
- MLGO Regalloc: 1258 QPS (+1.2%), p99 85ms, spill instructions -7.3% [2]

### 5.3 Phase Ordering

CompilerGym leaderboard `llvm_instcount` with GATv2+DD-PPO: codesize reduction geomean 1.047x (4.7% better than `-Oz`) with walltime 258s mean evaluation [5]. MileStone: under energy constraint 10J, execution time 45% lower than LLVM `-O3` on PolyBench `gemm`, while meeting energy limit 12% more accurately than baseline heuristics [6].

| Task | Baseline | Learned | Improvement | Training Cost |
|---|---|---|---|---|
| Inlining size | -Oz heuristic | MLGO PG | -7% size | 30k modules * 20 iter * 5 min compile |
| Regalloc perf | Greedy eviction | MLGO PG | +1.2% QPS | 5k modules * 30 iter |
| Phase ordering | -O3 fixed | GATv2 PPO | -4.7% size / +5% runtime | 4 datasets * 10k episodes |

> Theorem: Under PPO clipping $\epsilon$, the total variation distance between successive policies $\|\pi_{\theta_{new}} - \pi_{\theta_{old}}\|_{TV} \leq \epsilon$ implies monotonic improvement lower bound $J(\theta_{new}) \geq J(\theta_{old}) - \frac{2\epsilon\gamma}{(1-\gamma)^2}$ (Schulman et al. 2017). This explains MLGO stability despite sparse compiler rewards.

## 6. Limitations

- **Inference overhead**: Even small MLP adds 0.3-0.7% compile time per module; for million-module build, adds minutes. LLVM mitigates via `MLModelRunner` caching and AOT compiled model [3].
- **Generalization gap**: Model trained on search C++ may regress on Rust or Swift IR due to different idioms; retraining per language domain recommended [1].
- **Reward proxy mismatch**: Using instruction count as proxy for runtime is imperfect; `ir2perf` learned model reduces mismatch but adds error [7]. QPS true reward is expensive (requires fleet deployment).
- **Determinism and reproducibility**: RL training nondeterministic; two runs with same corpus yield policies with 1-2% variance in size reduction. LLVM requires deterministic build flag for model release.
- **Correctness invariants**: ML models must never override correctness (e.g., `noinline`, `volatile` loads). MLGO enforces via `MLInlineAdvisor` fallback to heuristic if model returns NaN [3].
- **GNN scalability**: ProGraML graphs for large programs can exceed 500k nodes, exceeding GPU memory for GATv2; CompilerGym filters such programs or uses subgraph sampling [5].
- **Multi-objective trade-offs**: MileStone Pareto frontier exploration requires 10x more training episodes than single-objective; user constraint satisfaction not guaranteed [6].

> Theorem: No learned policy can dominate optimal fixed pipeline on all programs if reward is arbitrary: phase ordering is undecidable to optimize perfectly due to Rice's theorem corollary on program equivalence. Learning provides average-case gain, not worst-case optimality.

## 7. Conclusion

MLGO demonstrates that replacing hand-tuned compiler heuristics with learned policies via RL is not academic curiosity but production-viable: LLVM now ships inliner and regalloc models trained with Policy Gradient and ES, improving size and QPS at Google scale [1][2][4]. Framing compiler optimizations as MDPs enables PPO to explore large search spaces, while GNNs over IR graphs provide program representations that generalize beyond scalar features [5][6]. Emerging LLM-based agents like Compiler-R1 extend this to black-box autotuning, suggesting a spectrum from *in-compiler learned heuristics* to *outside-agent tuners* [7].

Future directions:

- **Unified model**: single GNN policy for all LLVM passes, trained end-to-end with hierarchical RL (high-level pass selection, low-level decisions like eviction).
- **Hardware-aware**: condition policy on target microarchitecture features (cache size, register file) for heterogeneous fleet.
- **Verified learning**: combine learned policies with formal verification that correctness invariants hold, via abstract interpretation of model outputs.
- **Continuous learning**: online PPO updates from production telemetry without full retrain, with safeguards against distribution drift.

The trajectory from heuristics to learning mirrors broader systems optimization: where humans exhaustively squeeze headroom, data-driven search unlocks remaining 5-10% gains that compound at scale.
