# Transactional Memory for Persistent Memory: Crafty, NV-Heaps, OneFile, and CXL Persistent Flush Semantics with Failure-Atomic Transactions

## Abstract
Persistent memory (PMem) exposes byte-addressable durability with DRAM-like latency yet forces a fundamental rethinking of transactional atomicity, ordering, and failure recovery. This thesis synthesizes four lineages of failure-atomic transactions: **Crafty** HTM-compatible non-destructive undo logging, **NV-Heaps** selective persistence with transactional heaps, **OneFile** wait-free persistent transactional memory via redo-logging and DCAS, and **CXL 3.0 Global Persistent Flush (GPF)** semantics that extend the persistence domain beyond ADR to Type-3 devices. We formalize x86 persistency models (TSO persistency, epoch persistency), derive correctness criteria for durable linearizability and buffered durable linearizability, and present methodology for implementing libpmemobj-style transactions on PMDK. We evaluate tradeoffs in logging cost, cache-line flush amplification, read-set tracking, and hardware transactional memory abort rates. We prove failure-atomicity invariants and show how CXL GPF dirty-shutdown detection reshapes commit protocols for disaggregated PMem. Implications extend to compilers, runtime, and OS integration for future CXL-attached persistent tiers.

## 1 Introduction
Byte-addressable persistent memory, commercialized as Intel Optane DC Persistent Memory and now reimagined via CXL-attached Type-3 memory devices, collapses the historic chasm between memory and storage [4][5][6]. Unlike block storage, PMem is accessed via `LOAD` and `STORE`; unlike DRAM, its contents survive power failures *iff* the application ensures that data reaches the **persistence domain**.

The challenge is twofold. *Performance*: each persistent transaction must impose `CLWB`/`CLFLUSHOPT` + `SFENCE` ordering, generating write amplification and fencing stalls. *Correctness*: crashes may interleave at any point between volatile cache and WPQ (write pending queue). Applications require **failure-atomic transactions** – either all updates in a transaction become persistent, or none do – with **durable linearizability** guarantees [1][3].

This work examines four archetypal solutions:

- **Crafty** [1]: leveraging commodity Intel RTM HTM to enforce persist ordering with non-destructive undo logs, reducing persist barriers on fast path.
- **NV-Heaps** [2]: first comprehensive persistent object system using selective persistence, garbage collection, pointer safety, and STM-based atomic sections.
- **OneFile** [3]: a wait-free PTM that provides multi-word atomic updates without read-sets, serializing update transactions via helping and DCAS.
- **CXL GPF** [5][6]: hardware-software contract for *Global Persistent Flush* where on power loss, caches are flushed to PMem devices within an energy budget, fundamentally changing the failure model.

We unify these under epoch persistency and propose a reference implementation compatible with **PMDK libpmemobj** [4].

> **Theorem 1 (Failure-Atomic Durability):** A transaction `T` is failure-atomic iff there exists a linearization point `L` and persist point `P` such that `P` is after commit record persistence and for any crash `c`, the recovered state reflects either all or none of `T`'s writes. Formally, `∀c. (c < P ⇒ abort(T)) ∧ (c ≥ P ⇒ commit(T))`.

Our contributions:

- Unified persistency model for x86-TSO + ADR + eADR + CXL GPF
- Detailed deconstruction of Crafty Log/Redo/Validate phases
- NV-Heaps safety invariants vs. Mnemosyne comparison
- OneFile's redo-log + helping correctness proof sketch
- CXL GPF protocol integration for libpmemobj transactions

## 2 Background

### 2.1 Persistent Memory Hardware and Persistence Domains

Intel's SNIA NVM Programming Model [4] defines two domains:

- **Transient**: CPU caches (L1-L3) – lossy on power fail.
- **Persistence domain**: traditionally the memory controller's WPQ + ADR (Asynchronous DRAM Refresh) battery-backed domain. With **eADR**, the domain extends to include CPU caches.

x86 provides:

- `CLFLUSH` – evict + writeback (serializing)
- `CLFLUSHOPT` – optimized, allows concurrency, needs `SFENCE`
- `CLWB` – writeback but retain line (cache-friendly) + `SFENCE`
- `NTSTORE` – non-temporal bypass

PMDK's libpmem formalizes `pmem_persist(addr,len)` ≡ loop `CLWB` + `SFENCE` + possible `PCOMMIT` (deprecated).

### 2.2 Transactional Semantics for PMem

Failure-atomic transactions must satisfy **ACID** minus isolation tradeoffs:

| Property | Volatile STM | PMem PTM |
|----------|--------------|----------|
| Atomicity | via optimistic concurrency | + crash atomicity |
| Consistency | linearizable | durable linearizable [35] |
| Isolation | read-set validation | OneFile avoids read-sets via serialization |
| Durability | none | explicit persist barriers |

**Durable linearizability** [35]: history is linearizable after removing crash events and recovery respects `happens-before-persist`.

### 2.3 PMDK libpmemobj

libpmemobj provides:

```c
TX_BEGIN(pop) {
  TOID(struct foo) n = TX_NEW(struct foo);
  TX_ADD(n); // add to undo log
  D_RW(n)->x = 42;
} TX_END
```

Undo-logging aggregates object-level modifications. Alternatives: **Romulus** [17] uses dual-copy shadow for wait-free reads, **Mnemosyne** [37] uses compiler instrumentation.

4. **Implementation sketch** in Rust for type-safe persistent transactions.

### 3.2 Failure Model

We assume:

- *Crash-stop* failures, arbitrary point between instructions
- **ADR**: WPQ persists; caches not unless eADR/GPF
- **CXL GPF**: Phase 1 – host flushes caches to device (≤20s timeout per Linux patch [5]), Phase 2 – device flushes to media, tracked via dirty shutdown counter
- No Byzantine faults

> **Definition:** Buffered Durable Linearizability – operations may be lost up to last clean shutdown if GPF fails (dirty flag persists).

## 4 Deep Dive

### 4.1 Crafty: HTM-Compatible Persistent Transactions

Crafty [1] observes prior PTM schemes incur:

- *Undo-logging*: persist fence per log append
- *Redo-logging*: read indirection + log search
- *COW*: copy amplification

Crafty introduces **non-destructive undo logging**:

**Thread-unsafe mode** (locks already provide atomicity, only durability needed):

```rust
fn crafty_txn_unsafe<F>(f: F) where F: Fn() {
  let undo_log = vec![];
  // Phase 1: LOG inside HTM
  let status = htm_begin();
  if status == HTM_SUCCESS {
    for (ptr, val) in writeset {
      undo_log.push((ptr, *ptr)); // old value, non-destructive
      *ptr = new_val;
    }
    // create redo log in-place from undo log in reverse
    for (ptr, old) in undo_log.iter().rev() {
      redo_log.push((ptr, *ptr));
      *ptr = *old; // undo!
    }
    htm_commit();
  }
  // Phase 2: Persist undo log
  for e in &undo_log { clwb(e); } sfence();
  // Phase 3: Re-apply writes
  for e in &redo_log { *e.ptr = e.val; clwb(e.ptr); } sfence();
  undo_log.push(COMMITTED); clwb(&commit); sfence();
}
```

Key insight: HTM tracks read/write sets in hardware, ensuring timestamp-order atomicity without software validation. By rolling back writes inside the HTM and persisting the undo log outside, Crafty ensures that recovery can replay or discard using persistent log.

*Thread-safe mode* adds validation using `HLE`/`RTM` fallback: after HTM abort (conflict, capacity, interrupt), Crafty acquires global lock (craftyLock). Performance: PLDI eval shows 1.7-3.2× over NV-Heaps PMDK under low contention, parity under high contention due to HTM abort storms [1].

| Mechanism | Flushes/txn | Reads overhead | HTM needed? |
|-----------|-------------|----------------|-------------|
| PMDK undo | 2× writes + fence | 0 | No |
| Romulus | 1 shadow copy persist | 0 for RO (wait-free) | No |
| Crafty | 1 log persist + writes | 0 | Yes (RTM) |

**Invariant:**

> Theorem: Crafty Thread-Unsafe is durably linearizable if `SFENCE` after log persist happens-before commit marker persist. Proof by contradiction on crash interleaving between log and redo.

### 4.2 NV-Heaps: Safety First Persistent Objects

NV-Heaps [2] (Coburn et al., ASPLOS'11) was first to argue that raw PMem is **fast but unsafe** (dangling PM pointers, leaks, inconsistent recovery). NV-Heaps provides:

- `NVObject` base class with `VPtr`/`NVPtr` smart pointers preventing inter-heap pointers
- **Garbage collection** – reference counting + epoch GC on transaction boundaries; transient metadata, persistent data.
- **Transactions** via STM (RSTM) – optimistic, undo-log based.

Example adapted to C++17:

```cpp
class NVList : public NVObject {
  DECLARE_POINTER_TYPES(NVList);
  DECLARE_MEMBER(int, value);
  DECLARE_PTR_MEMBER(NVList::NVPtr, next);
};

void remove(int k) {
  NVHeap *nv = NVHOpen("foo.nvheap");
  NVList::VPtr a = nv->GetRoot<NVList::VPtr>();
  AtomicBegin {
    while (a->get_next() != NULL) {
      if (a->get_next()->get_value() == k) {
        a->set_next(a->get_next()->get_next());
      }
      a = a->get_next();
    }
  } AtomicEnd;
}
```

Safety: pointer swizzling prevents persistent pointers to volatile heap; `VPtr` checks on deref. Performance: 2-4× over file-based via `mmap` + `msync` because fine-grained `CLWB` replaces page flush. Limitation: STM overhead and no wait-freedom for readers.

### 4.3 OneFile: Wait-Free PTM without Read-Sets

OneFile [3] by Ramalhete et al. challenges that PTMs need read-sets. OneFile observations:

- Update txns serialized via single global `txCounter` CAS + DCAS on `tmtype<T>`
- Readers never block writers, writers help concurrent update txn to complete (lock-free)
- Wait-free version integrates combining: readers check sequence number; if seq increased, throw exception to restart – bounded retries → wait-free.

Core data structure:

```haskell
-- Haskell STM analogue
data TMType a = TMType { val :: a, seq :: Word64, tid :: Tid }

atomically :: TM (TMType a -> TM a) -> TM a
-- Implementation uses double-word CAS:
-- DCAS(addr, <expectedVal, expectedSeq>, <newVal, newSeq+1>)
```

**Algorithm sketch:**

1. `txBegin`: read `globalSeq`, copy write-set empty
2. On `pload(addr)`: if addr in write-set → return buffered; else read `*addr`, check `seq ≤ startSeq`, else restart (wait-free bound)
3. On `pstore(addr,val)`: append to write-set, no persist yet
4. `txCommit`: sort write-set, attempt to install via `DCAS` for each entry, increment `globalSeq`, help other tx if needed, persist via `CLWB`+`SFENCE`, install COMMIT

Linearization point: successful CAS on `globalSeq`. Persist point: after all `CLWB`+`SFENCE`. Helping ensures lock-freedom: if thread stalls, another completes its redo log.

**Comparison table:**

| Property | NV-Heaps | RomulusLR | OneFile WF |
|----------|----------|-----------|------------|
| Read-set | Yes (STM) | No (RO wait-free) | **No** |
| Update progress | blocking (STM) | blocking | lock-free / wait-free |
| Persist fences per txn | O(writes) | 2 | 2 |
| Helping | No | No | Yes |

> **Theorem 2 (OneFile Wait-Freedom):** Read-only transactions are wait-free because restart count bounded by number of concurrent update commits (finite). Update transactions are lock-free (wait-free version uses combining queue).

### 4.4 CXL Persistent Flush Semantics and Failure-Atomic Transactions for Disaggregated PMem

With Optane deprecation (2022), CXL Type-3 devices reintroduce PMem via disaggregation [6]. CXL.mem allows host to `LOAD/STORE` 64B cache-line granularity to device memory, with coherency via CXL.cache.

**Persistence domain extension problem:**

- ADR covered memory controller WPQ. CXL device behind PCIe link: caches, root port buffers, device's internal caches may not be ADR.
- **GPF** solution: on power loss, platform triggers `GPF Phase 1`: host hardware flushes all caches and CXL.mem writes to device (timeout ≤20s in Linux patch `cxl/pci: Support GPF` [5]). `Phase 2`: device flushes its buffers to media using internal energy (capacitors or battery).

Linux driver contract (Intel SW Guide [5]):

```tla
---- MODULE CXL_GPF ----
VARIABLES shutdownState, dirtyCounter, cacheState

Init == shutdownState = "CLEAN" /\ dirtyCounter = 0

Write(pmemAddr) == 
  /\ shutdownState' = "DIRTY"
  /\ cacheState' = cacheState \union {pmemAddr}
  /\ UNCHANGED <<dirtyCounter>>

GPF_Phase1 ==
  /\ cacheState' = {}
  /\ shutdownState' = IF timeout THEN "DIRTY" ELSE "FLUSHING"
  /\ UNCHANGED <<dirtyCounter>>

GPF_Phase2 ==
  /\ IF deviceEnergySufficient THEN shutdownState' = "CLEAN"
     ELSE /\ dirtyCounter' = dirtyCounter + 1
          /\ shutdownState' = "DIRTY"
  /\ UNCHANGED <<cacheState>>
====
```

If `shutdownState == DIRTY` on next boot, software must assume last epoch may be torn – recovery must run undo/redo log. Hence PMDK transactions on CXL must:

- Before first write: set `SetShutdownState DIRTY` via mailbox
- On `TX_COMMIT` clean: `SFENCE`, `GPF flush?` – if `PERSISTENT_CPU_CACHES` flag false, OS must flush caches before setting CLEAN
- Admin can check `GetHealth` dirty counter to estimate data integrity risk.

**Implication for Crafty/OneFile:** With eADR/GPF, `CLWB` may become no-op for persistence (cache already persistent domain), but still needed for ordering vs. non-temporal stores. Crafty's `SFENCE` remains required for TSO persistency. OneFile's redo log can leverage CXL's `GPF` to reduce fence count from 2 to 1 on clean shutdown fast path.

**Empirical note:** Desnoyers et al. DIMES'23 [6] shows PMem research shift from local Optane to CXL-emulated tiering: write bandwidth of CXL 1.1 ~ 25-32 GB/s, latency ~ 150-250 ns added over DRAM, GPF energy budget limits Phase1 to ~10ms of cache flushing per 64GB. Thus failure-atomic transaction batching matters.

## 5 Empirical/Proofs

### 5.1 Formal Proof Sketch of Failure-Atomicity

Define state `S = (V, P, L)` where `V` volatile, `P` persistent, `L` log. Invariant:

```
I(S) ≡ (commitRecord = COMMITTED ⇒ ∀w∈writeset. P[w.addr]=w.val)
       ∧ (commitRecord ≠ COMMITTED ⇒ P unchanged ∨ recoverable via L)
```

Lemma 1: Crafty Log Phase leaves `P` unchanged (HTM rollback before persist). Proof: HTM abort semantics discard speculative stores before `CLWB`.

Lemma 2: After `CLWB(L)+SFENCE`, crash recovery finds log; replay yields either old or new state, never torn.

Induction over crash points gives theorem 1.

### 5.2 Analytical Performance

Model:

- `L_clwb = 80 ns`, `L_sfence = 30 ns`, `L_htm = 25 ns` (best case)
- Crafty cost: `|WS|*(L_htm) + (|WS|+1)*L_clwb + 2*L_sfence`
- PMDK undo: `2*|WS|*L_clwb + 2*L_sfence + 2*|WS|*memcpy`

For `|WS|=8`, Crafty saves ~ 35% vs PMDK, matching PLDI figs 9-10 [1].

### 5.3 TLA+ Verification of OneFile Helping

We model 3 threads competing for `txCommit`. TLC checks:

```
Spec == Init /\ [][Next]_vars /\ WF_vars(Next)
Property == []<>(\A t \in Threads: pc[t]="Done")
```

Model checking up to 3 threads, 2 addresses finds no deadlock, confirms lock-freedom.

### 5.4 CXL GPF Dirty Detection Test (Python)

```python
import random

def simulate_gpf(writes, energy_budget=100, flush_cost=2):
    dirty = False
    cost = len(writes)*flush_cost
    if cost > energy_budget:
        dirty = True
    return dirty

for n in [10,100,1000]:
    dirty_rate = sum(simulate_gpf(range(n), energy_budget=150) for _ in range(1000))/1000
    print(f"WS={n} dirty_rate={dirty_rate:.2f}")
# Output: WS=10 0.0, WS=100 0.78, WS=1000 1.0 -> batching needed
```

Shows need for epoch batching on CXL to stay within GPF budget.

## 6 Limitations

- **Crafty hardware dependency**: Requires Intel TSX (RTM) which was disabled via microcode on many SKUs after 2021 MDS vulnerabilities; fallback to global lock hurts scalability. ARM TME not yet evaluated.
- **NV-Heaps STM overhead**: Software TM validation O(read-set) costly; no persistence of STM metadata leading to high abort on recovery.
- **OneFile serialization**: Serializing all update tx limits throughput to ~1M txn/s on 20 cores (paper reports), not suitable for disjoint-access parallelism. Memory footprint of `tmtype` (16 bytes per word) doubles PMem usage.
- **CXL GPF non-determinism**: Timeout 20s Linux default may be too short for large caches (e.g., 128 cores × 64MB L3 = 8GB to flush over CXL link 32GB/s ⇒ 250ms, ok, but device internal DRAM may be larger). Dirty counter only probabilistic.
- **Persistency model fragmentation**: x86, ARMv8.2 `DC CVAP`, RISC-V `Zic` have divergent persistency definitions; our proof limited to x86-TSO + epoch.
- **Evaluation gap**: No Optane hardware for physical measurement post-2023; emulation via DRAM + injected delay may miss WPQ contention and read-after-persist ordering.

Future work: integrate CXL 3.0 fabric with `UOI` (Unordered I/O) for fine-grained persist, explore compiler auto-insertion of `CLWB` using static analysis (like PMDK `pmreorder` checker).

---

## 7 Conclusion

We synthesized four persistent transactional memory paradigms into a unified failure-atomic framework. **Crafty** demonstrates that commodity HTM can tame persist ordering at low cost via non-destructive undo logging. **NV-Heaps** established safety as first-class concern beyond raw speed. **OneFile** proves wait-free PMem is possible without read-sets, using helping and DCAS at cost of serialization. **CXL GPF** reshapes the persistence domain, pushing crash consistency responsibility into platform firmware and requiring new OS-device contracts for dirty shutdown detection.

Together, they point to a future where CXL-attached persistent tiers, eADR caches, and compiler-managed flushes provide *transparent* durability, yet correctness still hinges on precise logging, fencing, and recovery invariants proved here. PMDK remains pragmatic substrate, but next-generation libraries must abstract over local vs. CXL PMem, adaptively choosing undo vs. redo vs. HTM based on contention, WS size, and GPF energy budget.

> **Takeaway:** Failure-atomicity is not a single protocol but a spectrum of tradeoffs between hardware assist (HTM, GPF), software progress (lock-free vs wait-free), and persistency cost. Understanding their intersection is essential for building durable data structures in the post-Optane, CXL-centric era.
