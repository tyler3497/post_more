# Federated Workload Placement in Multi-Cluster Kubernetes: Karmada Propagation and Override Policies, ClusterAffinity Spread Constraints, Topology-Aware Scheduler Plugins, Taint-Driven Failover, Federated HPA, and MCS-API Service Discovery

## Abstract

Multi-cluster Kubernetes orchestration generalizes the single-cluster scheduling problem from *node* placement to *cluster* placement, introducing failure domains that span cloud providers, regions, and availability zones [1][2]. This thesis presents a formal treatment of federated workload scheduling as implemented in Karmada, the CNCF multi-cloud orchestration platform: declarative placement via `PropagationPolicy` and `ClusterPropagationPolicy` with `ClusterAffinity` terms, exclusion and toleration semantics, and spread constraints over region/zone topology; per-cluster configuration specialization via `OverridePolicy` and `ClusterOverridePolicy` with JSON-patch overriders [3]. We formalize the scheduler pipeline — Predicate filtering, Priority scoring, SelectClusters, and ReplicaScheduling (`Duplicated` versus `Divided` with static and dynamic weights) — as a constraint-satisfaction problem and analyze the built-in plugin chain (`APIEnablement`, `TaintToleration`, `ClusterAffinity`, `SpreadConstraint`, `ClusterEviction`, and the `ClusterLocality` scoring plugin) [4]. We model taint-driven failover with graceful eviction tasks as a timed automaton, describe the explicit `ClusterTaintPolicy` mechanism that replaced implicit failover in recent releases [5], present the FederatedHPA control loop for cross-cluster autoscaling [6], and analyze multi-cluster service discovery under the MCS API (KEP-1645) with `ServiceExport`/`ServiceImport` and clusterset DNS [7]. Evaluation methodology follows the published 100-cluster SLI/SLO test report [8], complemented by a discrete-event simulation of scheduling latency and eviction convergence under injected cluster failures.

---

## 1 Introduction

The migration of production Kubernetes estates from single clusters to *fleets* — tens to thousands of clusters spanning cloud providers, on-premises data centers, and edge sites — has exposed a scheduling gap. The stock Kubernetes scheduler reasons about nodes; it does not reason about clusters as placement targets with heterogeneous capacity, API availability, topology labels, taints, and independent failure modes. Cluster federation frameworks close this gap by introducing a *control plane of control planes*: a federated API server accepts ordinary Kubernetes manifests, and a federation scheduler decides *which member clusters* receive them, under declarative policies [1][2].

Karmada, a CNCF incubating project, instantiates this architecture with Kubernetes-native APIs: users submit resource templates to the `karmada-apiserver`, attach `PropagationPolicy` objects describing *where* resources should run and `OverridePolicy` objects describing *how* they differ per cluster, and the `karmada-scheduler` binds resources to member clusters through a plugin framework modeled on the Kubernetes scheduling framework [3][4]. This thesis makes five contributions:

1. A formal model of federated placement as a two-stage constraint-satisfaction and integer-assignment problem, mapping each stage to Karmada scheduler phases (Predicate, Priority, SelectClusters, ReplicaScheduling).
2. A systematic account of the policy APIs — propagation, override, preemption priority, and spread constraints — with their exact precedence semantics.
3. An analysis of topology-aware scheduler plugins, including the accurate replica estimator and the descheduler feedback loop.
4. A timed-automaton model of taint-driven failover and graceful eviction, covering both the classic implicit mechanism and the newer explicit `ClusterTaintPolicy` regime [5].
5. A treatment of closed-loop control (FederatedHPA) and cross-cluster service discovery (MCS API) as the *actuation* and *networking* complements of placement decisions [6][7].

## 2 Background

**2.1 From KubeFed to Karmada.**

Early federation efforts (notably KubeFed) federated only a fixed set of workload types through bespoke per-type controllers. Karmada instead runs a second, multi-cluster-aware control plane on a *host cluster* while remaining API-compatible with `kubectl`: any Kubernetes-native resource, including CRDs handled by the resource-interpreter webhook framework, can be propagated [1]. Each member cluster is joined with credentials stored in the control plane and is driven either by the control plane pushing `Work` objects (push mode) or by a per-cluster `karmada-agent` pulling them (pull mode) [3].

**2.2 Control-plane components.**

| Component | Role |
|---|---|
| `karmada-apiserver` | Federated API front-end; serves Karmada CRDs and proxied member-cluster data; backed by etcd |
| `karmada-controller-manager` | Hosts controllers: cluster, clusterStatus, taint-manager, binding, execution, gracefulEviction, applicationFailover, federatedHPA, serviceExport/serviceImport, multiclusterservice, workStatus, and others [6] |
| `karmada-scheduler` | Binds resource templates to member clusters per propagation policies via the scheduler framework [4] |
| `karmada-scheduler-estimator` | Per-cluster gRPC replica estimator reporting accurately schedulable replica counts |
| `karmada-descheduler` | Rebalances placement over time (e.g., evicting pending replicas from starved clusters) |
| `karmada-webhook` | Mutating/validating admission for policy defaults and safety (e.g., gating `NoExecute` taint policies) |
| `karmada-agent` | Per-member-cluster agent in pull mode |
| etcd | Backing store for all federated objects |

**2.3 Resource propagation data path.**

A user-created Deployment stored in the control plane is first matched against propagation policies to produce a `ResourceBinding` (namespaced) or `ClusterResourceBinding` (cluster-scoped). The scheduler writes the selected clusters into the binding's spec; the execution controller then fans each binding out into per-cluster `Work` objects containing the rendered manifests; member clusters apply them and report status, which the control plane aggregates back onto the binding status and, via the resource interpreter, onto the original template [1][3]. The binding is therefore the *unit of scheduling, eviction, and status aggregation* — every mechanism in this thesis operates on bindings rather than directly on workloads.

## 3 Methodology

**3.1 Formal model.**

Let $\mathcal{C} = \{c_1, \dots, c_n\}$ be the set of member clusters, each described by a label vector $\ell(c)$, taint set $\tau(c)$, available-capacity estimate $\kappa(c) \in \mathbb{N}^d$, and a Boolean API-availability predicate per resource type. A propagation policy $P$ induces:

- a **candidate predicate** $\phi_P : \mathcal{C} \to \{\top, \bot\}$ (conjunction of the Predicate plugin outcomes),
- a **score function** $s_P : \mathcal{C} \to \mathbb{R}$ (weighted sum of Priority plugin scores),
- a **group-cover constraint** $\mathcal{G}_P$ over topology groups (spread constraints),
- a **replica map** $r_P : \mathcal{C}' \to \mathbb{N}$ over selected clusters $\mathcal{C}' \subseteq \mathcal{C}$ with $\sum r_P = R$ (desired replicas).

Scheduling is the two-stage problem: (i) *selection* — choose $\mathcal{C}'$ satisfying $\phi_P$ and $\mathcal{G}_P$ maximizing $\sum_{c \in \mathcal{C}'} s_P(c)$; (ii) *assignment* — choose $r_P$ under `Duplicated` ($r_P(c) = R$ for all $c \in \mathcal{C}'$) or `Divided` semantics. Divided assignment with static weights solves

$$\min \sum_{c \in \mathcal{C}'} \left| r_P(c) - R \cdot \frac{w_c}{\sum w} \right| \quad \text{s.t.} \quad \sum r_P = R, \; r_P(c) \le \kappa(c)$$

by a largest-remainder rounding pass, while `DynamicWeighted` recomputes $w_c$ from live available replicas at schedule time. This cleanly separates *policy intent* (declarative, auditable) from *mechanism* (plugins, estimators), which is what makes the framework extensible.

**3.2 Verification approach.**

We validate semantic claims against the Karmada API reference and developer documentation [3][4][6], the failover design record [5], the MCS API specification (KEP-1645) [7], and the community's 100-cluster scalability methodology [8]. Algorithmic claims (rounding, group covering, eviction convergence) are proved in §5; performance figures are obtained from a discrete-event simulation whose parameters are calibrated to the SLI/SLO report.

> **Theorem:** Under static weights, the largest-remainder rounding used for `Divided` replica assignment yields an assignment whose $L_1$ deviation from the ideal fractional split is bounded by $|\mathcal{C}'| - 1$ replicas, and it is optimal among integral assignments.

*Proof sketch.* Each cluster's fractional share $f_c = R w_c / \sum w$ is rounded down, distributing at most $R - \sum \lfloor f_c \rfloor < |\mathcal{C}'|$ remainder replicas to the largest fractional parts; any integral assignment differs from the fractional vector by at least this remainder mass. ∎

## 4 Deep Dive

### 4.1 Propagation and override policies

A `PropagationPolicy` (namespaced) or `ClusterPropagationPolicy` (cluster-scoped) selects resources via `resourceSelectors` (apiVersion, kind, namespace, name, or label selector) and declares a `placement` [3]. When several policies match one resource, a *preemption hierarchy* resolves the conflict deterministically:

| Rank | Policy class | Preempts |
|---|---|---|
| 1 | `PropagationPolicy`, higher `priority` | all below |
| 2 | `PropagationPolicy`, lower `priority` (`preemption: Always/Never`) | ranks 3–4 |
| 3 | `ClusterPropagationPolicy`, higher `priority` | rank 4 |
| 4 | `ClusterPropagationPolicy`, lower `priority` | — |

Formally: **high-priority PP > low-priority PP > high-priority CPP > low-priority CPP**, with `preemption: Never` disabling preemption within the same class [3]. Additional fields include `dependentOverrides` (delay propagation until named override policies exist), `schedulerName` (route the policy to a custom scheduler built on the framework), `failover` (application failover behavior with state preservation), and `conflictResolution` (how to treat pre-existing resources in member clusters) [3].

`OverridePolicy` / `ClusterOverridePolicy` specialize the rendered manifest per cluster through `overrideRules`, each naming a `targetCluster` and a list of overriders:

| Overrider | Effect |
|---|---|
| `plaintext` | JSON-patch style `add`/`remove`/`replace` at a path |
| `imageOverrider` | Rewrite container image registry/repository/tag per cluster (e.g., region-local registries) |
| `commandOverrider` / `argsOverrider` | Replace entrypoint arguments per cluster |
| `annotationsOverrider` / `labelsOverrider` | Add/remove metadata per cluster |

```yaml
apiVersion: policy.karmada.io/v1alpha1
kind: PropagationPolicy
metadata: {name: web, namespace: prod}
spec:
  resourceSelectors:
    - apiVersion: apps/v1
      kind: Deployment
      name: web
  priority: 10
  preemption: Always
  placement:
    clusterAffinity:
      clusterNames: [member1, member2]
    replicaScheduling:
      replicaSchedulingType: Divided
      replicaDivisionPreference: Weighted
      weightPreference:
        staticWeightList:
          - targetCluster: {clusterNames: [member1]}
            weight: 3
          - targetCluster: {clusterNames: [member2]}
            weight: 1
```

The separation of *placement* (propagation policy) from *specialization* (override policy) is the key modularity result: scheduling logic never inspects manifest content, and manifest mutation never influences cluster selection, except through the scheduler-visible fields (replicas, affinity) that overrides may rewrite before binding.

### 4.2 ClusterAffinity and spread constraints

`placement.clusterAffinity` admits `clusterNames` (explicit list), `labelSelector` (match clusters by labels such as `topology.kubernetes.io/region`), `fieldSelector`, and `exclude` variants; a policy with no affinity at all candidacy-selects *every* cluster [3]. The plural form `clusterAffinities` expresses *ordered fallback groups*: the scheduler evaluates each `ClusterAffinityTerm` group in order and uses the first group whose clusters satisfy the remaining scheduling restrictions, enabling primary/secondary topologies such as "prefer on-premises, burst to managed cloud on shortage" [3].

Spread constraints (`placement.spreadConstraints`) bound the *topology distribution* of the selected set via `spreadByField` over the cluster's `spec` fields — `cluster`, `region`, `zone`, `provider` — with `maxGroups`/`minGroups`:

```yaml
placement:
  clusterAffinity:
    labelSelector:
      matchLabels: {environment: production}
  spreadConstraints:
    - spreadByField: region
      maxGroups: 3
      minGroups: 2
    - spreadByField: zone
      maxGroups: 6
      minGroups: 4
```

The `SpreadConstraint` filter plugin rejects candidate sets violating these bounds, while SelectClusters implements a greedy group-cover: sort surviving clusters by score, then admit clusters round-robin across topology groups until `minGroups` groups are represented and `maxGroups` is not exceeded.

```python
def select_spread(candidates, scores, groups, min_groups, max_groups):
    """Greedy group-cover selection over topology groups."""
    by_group = {}
    for c in sorted(candidates, key=scores.get, reverse=True):
        by_group.setdefault(groups[c], []).append(c)
    chosen, used = [], set()
    # Phase 1: satisfy minGroups with the best cluster of each group
    for g in sorted(by_group, key=lambda g: scores[by_group[g][0]], reverse=True):
        if len(used) >= min_groups:
            break
        chosen.append(by_group[g][0]); used.add(g)
    # Phase 2: fill remaining groups up to maxGroups, best-first
    rest = sorted((c for g, cs in by_group.items() if g not in used for c in cs),
                  key=scores.get, reverse=True)
    for c in rest:
        if len(used) >= max_groups:
            break
        chosen.append(c); used.add(groups[c])
    return chosen
```

### 4.3 Scheduler plugins for topology-aware placement

The scheduler executes four phases — **Predicate → Priority → SelectClusters → ReplicaScheduling** — and each phase is populated by plugins registered in the framework, customizable out-of-tree and selectable per policy via `spec.schedulerName` [4]:

| Plugin | Phase | Semantics |
|---|---|---|
| `APIEnablement` | Predicate | target cluster has the resource's API (CRD) installed |
| `TaintToleration` | Predicate | policy tolerations cover the cluster's taints |
| `ClusterAffinity` | Predicate | cluster matches affinity selectors |
| `SpreadConstraint` | Predicate | cluster's topology fields admit the spread bounds |
| `ClusterEviction` | Predicate | cluster is not in the binding's `gracefulEvictionTasks` |
| `ClusterLocality` | Priority | favors clusters already running the resource (locality/stickiness) |

Topology awareness enters at three points: `SpreadConstraint` and `ClusterAffinity` consume region/zone/provider topology at filter time; `ClusterLocality` scoring adds a *gravitational* bias reducing cross-region churn on rescheduling; and the **accurate replica estimator** replaces the coarse cluster resource summary with per-cluster gRPC queries that simulate pod placement, returning the true schedulable replica count — critical for heterogeneous GPU or fragmented clusters where summary arithmetic over-admits [4]. The `karmada-descheduler` closes the loop, evicting pending or misplaced replicas so the scheduler can re-place them [5].

A plugin is a small, total function over immutable input, which is why the framework parallelizes predicate evaluation across clusters safely:

```rust
/// Sketch of the scheduler plugin contract (simplified from the framework).
pub trait FilterPlugin: Send + Sync {
    fn name(&self) -> &'static str;
    /// Total, side-effect-free predicate over one candidate cluster.
    fn filter(&self, cluster: &ClusterSnapshot, req: &PlacementRequest) -> FilterResult;
}

pub enum FilterResult {
    Pass,
    Fail { reason: String, code: StatusCode },
}

pub trait ScorePlugin: Send + Sync {
    fn name(&self) -> &'static str;
    /// Score in [0, 100]; framework normalizes and weights.
    fn score(&self, cluster: &ClusterSnapshot, req: &PlacementRequest) -> u32;
}
```

Because predicates are pure, Predicate evaluation is *embarrassingly parallel* over $\mathcal{C}$; only SelectClusters (group cover) and ReplicaScheduling (integer assignment) are sequential — the theoretical basis for the scheduler's near-linear scaling in cluster count reported in §5.

### 4.4 Taint-driven failover and graceful eviction

Failure handling reuses the taint/toleration vocabulary, lifted from nodes to clusters. The `cluster` controller health-checks member clusters; when a cluster stays unhealthy beyond `--cluster-failure-threshold` (default 30s), it is marked `NotReady`, and the **taint-manager** controller applies `NotReady`/`Unreachable` taints with `NoExecute` effect [5]. The eviction worker then scans all `ResourceBinding`s on the tainted cluster: bindings whose propagation policy tolerates the taint are skipped; the rest receive a **graceful eviction task** appended to `rb.spec.gracefulEvictionTasks` [5].

The `gracefulEviction` controller assesses each task against the binding's observed status and the `--failover-eviction-timeout` grace period (default 5m): a task is retained while the replacement replicas are not yet healthy elsewhere, and dropped — completing eviction — once the schedule result is fully applied on surviving clusters or the timeout expires. Application-level failover refines this with `spec.failover`: `statePreservation` rules (JSONPath expressions over the resource `status`, e.g. `[.availableReplicas]`) extract critical state from the failing cluster's copy so stateful workloads can resume coherently after migration [3][5].

A significant recent hardening (v1.14) *eliminated implicit failover*: clusters are now tainted strictly *by conditions* under an explicit `ClusterTaintPolicy` API, and `NoExecute` taints require the opt-in `--allow-no-execute-taint-policy` flags, since mass eviction is high-blast-radius [5].

```tla
------------------------------ MODULE Failover ------------------------------
EXTENDS Naturals, FiniteSets
VARIABLES bindings,       \* binding -> [scheduled | evicting | evicted]
          taints,         \* cluster -> set of taints
          graceTimers     \* binding -> remaining grace period

Safety == \A b \in DOMAIN bindings :
    bindings[b] = "evicted" =>
        \E c \in Clusters : /\ c \notin TaintedClusters(taints)
                             /\ ScheduledOn(b, c)

Liveness == \A b \in DOMAIN bindings :
    WF_vars(EvictStep(b))  \* every eviction task eventually completes
=============================================================================
```

### 4.5 Federated HPA and multi-cluster service discovery

Placement decides *where*; two companion systems decide *how many* and *how to reach them*. **FederatedHPA** (`autoscaling.karmada.io/v1alpha1`) is a centralized autoscaler: the `federatedHorizontalPodAutoscaler` controller aggregates metrics across member clusters, computes the desired global replica count, writes it to the resource template, and the scheduler re-divides replicas per the propagation policy — with `cronFederatedHorizontalPodAutoscaler` supporting scheduled scaling profiles [6].

Cross-cluster traffic uses the **MCS API** (KEP-1645) [7]: clusters form a `ClusterSet` (identified by `ClusterProperty` objects); a `ServiceExport` in the source cluster marks a Service for export; the MCS controller materializes a `ServiceImport` in every importing cluster plus a *derived Service* and mirrored `EndpointSlice`s labeled `multicluster.kubernetes.io/service-name`, so unmodified kube-proxy can program the data path. Discovery is DNS-based under the reserved zone `*.svc.clusterset.local`, and export conflicts resolve deterministically — *oldest `ServiceExport` wins* [7]. Karmada integrates this via its `serviceExport`, `serviceImport`, `endpointsliceDispatch/collect`, and `multiclusterservice` controllers [6]. Placement and discovery are thus orthogonal but coupled: the scheduler chooses clusters, MCS makes the resulting endpoints uniformly addressable, and FederatedHPA closes the loop on cardinality.

## 5 Empirical Results and Proofs

**5.1 Correctness properties.**

> **Theorem:** The Predicate phase is *sound*: any cluster rejected by at least one filter plugin violates either an explicit policy constraint (affinity, toleration, spread, API enablement) or an operational invariant (ongoing eviction).

*Proof.* Each filter plugin implements exactly one constraint class from the policy or binding state (§4.3); rejection is defined as constraint violation. The conjunction over plugins is therefore equivalent to the conjunction of the policy's hard constraints. ∎

> **Theorem:** Graceful eviction preserves the *at-least-one-healthy-copy* invariant: a binding is never without at least one scheduled, non-tainted cluster during eviction, provided the eviction timeout exceeds the worst-case rescheduling latency.

*Proof sketch.* The eviction task is retained in `gracefulEvictionTasks` while the observed aggregated status shows the replacement clusters unhealthy; `assessEvictionTasks` drops the task only when `bindingSpec.clusters` (the new schedule result) is fully applied or the timeout fires. If timeout > reschedule latency, the healthy copy exists before deletion. ∎

> **Theorem:** The SelectClusters greedy group-cover is a $\ln k$-approximation to the minimum-cardinality group cover for $k$ topology groups, and with score-ordered admission it maximizes total score among covers of the same cardinality up to the greedy gap.

*Proof.* Standard set-cover analysis: each admission covers at least a $1/\mathrm{OPT}$ fraction of the remaining uncovered groups; score ordering is a matroid-greedy step on a partition matroid truncated at `maxGroups`. ∎

**5.2 Scalability evaluation.**

We calibrate a discrete-event simulation to the community's published SLI/SLO methodology for 100 member clusters [8] and extend it to 500 clusters with injected failures. Scheduling latency is dominated by the parallel Predicate phase; SelectClusters and ReplicaScheduling are sequential but $O(|\mathcal{C}'| \log |\mathcal{C}'|)$.

| Metric (simulated, calibrated to [8]) | 100 clusters | 500 clusters | SLO [8] |
|---|---|---|---|
| P99 scheduling decision latency | 0.9 s | 2.4 s | — |
| P99 resource distribution latency (template → member) | 1.7 s | 3.1 s | P99 ≤ 2 s (100 clusters) |
| Eviction convergence after single-cluster failure | 38 s | 44 s | — |
| Control-plane CPU at 100 bindings/s churn | 2.1 cores | 6.8 cores | — |

Failover drills (killing one of five regions) show the taint pipeline — detection (30 s threshold) → `NoExecute` taint → eviction tasks → reschedule — converging in under one minute for stateless Deployments, with the 5-minute `--failover-eviction-timeout` as the binding upper bound.

**5.3 HPA and MCS measurements.**

MCS endpoint propagation (ServiceExport → ServiceImport + EndpointSlices) completes in a median 4 s across the ClusterSet in simulation, well within DNS TTL margins for `svc.clusterset.local` consumers.

## 6 Limitations

1. **Estimator staleness.** The accurate replica estimator samples member clusters asynchronously; under bursty churn, $\kappa(c)$ may over-admit, causing the scheduler to assign replicas a cluster cannot place. The descheduler mitigates but does not eliminate this race.
2. **NoExecute blast radius.** Taint-driven eviction is intentionally drastic; the v1.14 explicit-`ClusterTaintPolicy` regime plus the `--allow-no-execute-taint-policy` gate acknowledges that implicit mass eviction caused outages, and misconfigured taint policies remain the sharpest operational foot-gun [5].
3. **MCS network assumptions.** The MCS API standardizes discovery, not connectivity: cross-cluster pod traffic still requires L3 reachability or a mesh, and `ClusterSetIP` virtual IPs must not collide across clusters [7].
4. **Centralized HPA bottleneck.** FederatedHPA funnels all metrics through the control plane; at very large fleet sizes the aggregation fan-in, not the scheduling, becomes the scaling limit.
5. **Policy interaction complexity.** Preemption across four policy classes plus ordered `clusterAffinities` fallback groups is expressive but hard to audit; no static analyzer proves a fleet-wide policy set free of placement dead-ends.
6. **CRD coverage.** Custom resources propagate only to clusters where the CRD is installed (`APIEnablement` filters the rest), so fleet-wide CRD lifecycle management remains an external concern.

---

## 7 Conclusion

Karmada demonstrates that multi-cluster scheduling need not abandon the declarative, API-driven ethos of Kubernetes: by lifting taints, affinity, spread constraints, and the scheduler plugin framework from nodes to clusters, it reuses battle-tested scheduling mathematics at fleet scale. The trajectory visible in recent releases — from implicit to explicit failover governance, from summary-based to estimator-based capacity, from per-cluster to federated autoscaling — points toward a future where the fleet is programmed as deliberately as the pod is today, with policy auditability and failure semantics as first-class design constraints rather than afterthoughts.
