# Homomorphic Encryption for Private Vector Search: CKKS Approximate Arithmetic, Ring-LWE Bootstrapping, and GPU-Accelerated NTT Pipelines

## Abstract
Encrypted similarity search must preserve both privacy and utility: the server must compute $\langle q, d_i \rangle$ for a private query $q$ and private or public database vectors $d_i$ without learning either, while the client learns only top-k identities. We survey the CKKS scheme [1][2], its RNS variant [3], bootstrapping improvements [4][7], and GPU NTT acceleration [5][6][8]. We propose a concrete pipeline for private vector search and analyze correctness, precision, and performance.

---

## 1 Introduction

Vector search underpins retrieval-augmented generation, biometric identification, and recommendation. In outsourced settings, both query and database are sensitive. Fully Homomorphic Encryption (FHE) allows the server to evaluate arithmetic circuits directly on ciphertexts [7].

*CKKS is unique among FHE schemes*: unlike BFV/BGV which operate over exact integer rings $\mathbb{Z}_t$, CKKS operates over $\mathbb{C}^{n/2}$ approximately, embedding real numbers via the canonical embedding $\sigma: \mathbb{R}[X]/(X^n+1) \to \mathbb{C}^{n/2}$ and tolerating small decryption error as inherent to floating-point workloads [1][3].

Private vector search reduces to:

1. **Encode** $q, d_i \in \mathbb{R}^d$ into plaintext polynomials $m_q, m_d$
2. **Encrypt** to $ct_q = Enc(pk, m_q)$
3. **Evaluate** $ct_{score,i} = Eval(\langle \cdot, \cdot \rangle, ct_q, pt_{d_i})$ or fully encrypted dot-product
4. **Threshold** / argmax without revealing scores

This work makes three contributions:

- A rigorous exposition of CKKS approximate arithmetic with RNS/NTT optimizations
- A bootstrapping-aware analysis for unbounded-depth vector search with composition of SlotToCoeff and CoeffToSlot
- A GPU pipeline design achieving 63–141× speedups over CPU baselines [5][6]

> **Theorem 1 (CKKS Approximate Correctness):** For message $m \in \mathbb{C}^{n/2}$ with scale $\Delta$, encoding then encryption then decryption yields $m' = m + e_{enc} + e_{scale}$ where $\|e_{enc}\|_\infty = O(\sqrt{n} \sigma)$ and $\|e_{scale}\|_\infty = O(\Delta^{-1})$. [1][3]

## 2 Background

### 2.1 Ring-LWE and RLWE Hardness

Security of CKKS, BFV, BGV rests on **Ring Learning With Errors (RLWE)** over cyclotomic ring $R = \mathbb{Z}[X]/(X^n+1)$ where $n=2^k$. Given samples $(a, b = a\cdot s + e) \in R_q \times R_q$, distinguishing from uniform is hard under worst-case ideal lattice problems [2][8]. For $q$ a product of distinct primes $q_i$ in RNS, each residue lives in $\mathbb{Z}_{q_i}$ enabling word-sized arithmetic [3].

Public key: $pk = (b = -a\cdot s + e, a)$
Secret key: $s \leftarrow \chi_{key}$, sparse ternary $\{-1,0,1\}^n$ with Hamming weight $h=64$ typical in OpenFHE [8].

### 2.2 FHE Taxonomy

| Scheme | Plaintext Domain | Exact? | Bootstrapping Cost | Vector Search Suitability |
|--------|------------------|--------|-------------------|--------------------------|
| BFV | $\mathbb{Z}_t^{n}$ | Yes | High (digit extraction) | Low — requires quantization |
| BGV | $\mathbb{Z}_t^{n}$ | Yes | Moderate | Medium |
| CKKS | $\mathbb{C}^{n/2}$ approximate | No | Moderate — approximate mod reduction | **High** — native real vectors |
| TFHE/FHEW | Bits | Yes | Gate bootstrapping <0.1s [7] | Low — bit-wise dot product inefficient |

### 2.3 Number Theoretic Transform

Polynomial multiplication in $R_q$ naive is $O(n^2)$. NTT is the finite-field analogue of DFT, enabling $O(n \log n)$ multiplication:

$$ c = a \cdot b \in R_q \iff NTT^{-1}(NTT(a) \odot NTT(b)) $$

For $n=2^{16}=65536$ and $\log q \approx 1500$ bits (decomposed into 30+ 50-bit limbs), NTT dominates 70–80% of runtime in CKKS key switching and rescaling [5][6]. Hence GPU acceleration is pivotal.

## 3 Methodology

### 3.1 CKKS Encoding and Encryption

Encoding: Given $z \in \mathbb{C}^{n/2}$, compute $\pi^{-1}(z) \in R$ via inverse canonical embedding then scale by $\Delta$ and round:

```python
def ckks_encode(z: np.ndarray, Delta: int, n: int) -> Poly:
    # z: complex vector length n/2
    # Embed to polynomial via FFT-style inverse
    slots = np.fft.ifft(z, n) # simplified; actual uses complex roots of unity
    scaled = np.round(slots * Delta).astype(np.int64)
    return Poly(scaled) % (X**n + 1)
```

Encryption (RLWE):

```rust
// RLWE encryption, simplified RNS form
fn encrypt(pk: &(Poly, Poly), m: Poly, sigma: f64) -> (Poly, Poly) {
    let u = sample_ternary();
    let e0 = sample_gaussian(sigma);
    let e1 = sample_gaussian(sigma);
    let c0 = &pk.0 * &u + e0 + m;
    let c1 = &pk.1 * &u + e1;
    (c0, c1)
}
```

Ciphertext: $ct = (c_0, c_1) \in R_{Q_l}^2$, level $l$ with modulus $Q_l = \prod_{i=0}^l q_i$.

Homomorphic ops:

- **HAdd**: $ct_1 + ct_2 = (c_{0,1}+c_{0,2}, c_{1,1}+c_{1,2})$
- **HMult**: $ct_{mult} = (d_0, d_1, d_2)$ where $d_0=c_{0,1}c_{0,2}$, $d_1=c_{0,1}c_{1,2}+c_{1,1}c_{0,2}$, $d_2=c_{1,1}c_{1,2}$ then relinearize $d_2$ via $evk$
- **Rescale**: $ct' = \lfloor Q_{l-1}/Q_l \cdot ct \rceil$, scale $\Delta^2 \to \Delta$, critical for precision [3]

### 3.2 Private Cosine Similarity Circuit

Given normalized query $\hat{q}=q/\|q\|$, database $\hat{d}_i$, cosine $= \langle \hat{q}, \hat{d}_i \rangle$. Encrypted circuit:

1. If database plaintext (server holds vectors in clear but query private): $score_i = \langle Dec? Actually Enc dot pt \rangle = \sum_j q_j \cdot d_{i,j}$ via multiply-plain and rotate-sum

```haskell
-- CKKS rotate-and-sum for dot product, n/2 slots
encryptedDot :: Ctxt -> [Ptxt] -> Ctxt
encryptedDot ctQ dbVecs =
  let prods = zipWith cmulPlain dbVecs (repeat ctQ) -- SIMD mul
      summed = foldl1 hadd prods
  in rotateSum summed -- log d rotations
  where rotateSum c = if slots==1 then c else rotateSum (hadd c (rotate c (slots`div`2)))
```

2. If both encrypted (two-tower private): use $ct_q \cdot ct_{d_i}$ then relinearize.

Inner product requires $d$ multiplications + $\log d$ rotations. Rotations need Galois keys, each a key-switch with NTT-heavy automorphism.

> **Theorem 2 (Dot Product Noise Growth):** After dot product of dimension $d$ with scale $\Delta$, noise variance $\sigma_{dot}^2 = d \cdot (\sigma_{mult}^2 + \sigma_{rot}^2 \cdot \log d) + \sigma_{rescale}^2$. For $d=768$, $\Delta=2^{40}$, $\log q_i=50$, variance stays $<2^{-30}$ before bootstrapping, yielding $\approx 20$ bits precision [4].

### 3.3 RNS Decomposition and NTT

Full RNS variant [3] avoids multi-precision integers: $Q_l$ limbs $q_i$ are NTT-friendly primes $q_i \equiv 1 \mod 2n$ enabling NTT per limb. Key switching decomposes $c_1$ into digits base $P$.

NTT butterfly (Cooley-Tukey):

$$ \begin{aligned}
U &= a_j \\
V &= a_{j+k} \cdot \omega^{bitrev} \\
a_j &= U+V \mod q_i \\
a_{j+k} &= U-V \mod q_i
\end{aligned} $$

GPU mapping: Each limb independent; $n=65536$ threads per NTT. Prior work [5][6] achieves 9.93× NTT speedup via kernel fusion, and 141.95× BFV keygen via full GPU offload on V100 vs i9-7900X.

## 4 Deep Dive

### 4.1 CKKS Bootstrapping for Unbounded Search

Leveled depth $L \approx 10-15$ for $n=2^{16}$; dot product of 768 dims consumes ~2 levels (mult + rescale + rotations). Without bootstrapping, only ~5 queries possible before exhaustion. Bootstrapping refreshes ciphertext to level $L$ by homomorphically decrypting.

CKKS bootstrapping steps [4][8]:

1. **ModRaise**: $ct_{Q} \to ct_{Q'}$ lifting to larger modulus $Q' >> Q$
2. **CoeffToSlot**: homomorphic decode, moving coefficients to slots via linear transform $U_{CtS}$ (DFT matrix)
3. **EvalMod**: approximate modular reduction $x \mod q_0$ via high-degree polynomial $f(x) \approx x - q_0 \cdot round(x/q_0)$
4. **SlotToCoeff**: inverse transform

EvalMod is core: approximate $mod$ via Chebyshev / sine approximation: $\cos(2\pi x / q_0)$ compositions [4]. Depth-10 polynomials achieve 93-bit precision [4] vs depth 11-12 prior.

Lazy BSGS reduces complexity from $O(\sqrt{d})$ to $O(\sqrt{d}/2)$ by deferring relinearization [4].

*Precision constraint*: For vector search, bootstrapping error $e_{boot} \approx 2^{-20}$ to $2^{-14}$ must be << inter-vector distance margin $\gamma$. For normalized embeddings, margin typical $0.02-0.05$, so 14-bit bootstrapping suffices.

### 4.2 GPU-Accelerated NTT Pipelines

Profile on RTX 3060Ti [8]: 128 NTTs for $n=2^{14}$ in $176.1 \mu s$ vs CPU $11.2 ms$ — **63.4×** for one multiplication. Pipeline design:

- **TLMOP**: Thread-Level Memory Optimization: inner NTT in registers via `__shfl_sync`, avoiding shared memory stalls [6]
- **TransOP**: Implicit transpose via TensorCore MMA layout, avoiding explicit transpose
- **TFOP**: Twiddle factor pre-arrangement for coalesced access; separate pools for negacyclic vs standard
- **OT (On-the-fly Twiddling)**: Generate $\omega^{k}$ on fly from generator $g$, saving 50% bandwidth on large $Q$ [5]

```rust
// Pseudocode CUDA kernel launch for batched RNS NTT
fn gpu_ntt_batch(polys: Vec<RnsPoly>, stream: CudaStream) -> Vec<RnsPoly> {
    // polys: [batch=32][limbs=20][n=65536]
    for limb in 0..nlimbs {
        // 1. Global -> shared coalesced
        // 2. Inner NTT radix-8 in registers
        // 3. Transpose via shared mem bank-conflict-free
        // 4. Outer NTT
        launch_kernel!(ntt_radix8_kernel, grid=n/256, block=256, args=(polys_ptr, twiddles[limb], q[limb]));
    }
    // Fused Hadamard multiply for BFV/CKKS base conversion
}
```

Roofline analysis on Intel Gen11 GPUs [5] shows optimized NTT reaches 79.8–85.7% peak bandwidth, 9.93× over naive.

### 4.3 Security and Parameter Selection

128-bit security per HE standard: $n=2^{16}$, $\log Q \le 1750$, ternary secret, $\sigma=3.2$ [8][2]. OpenFHE automatically selects $n$ given $Q$ [8]. For private search with bootstrapping depth 11, we need $L=22$ levels, $Q \approx 1100$ bits after bootstrapping, fits $n=65536$.

| Parameter Set | $n$ | $\log Q$ | Levels $L$ | Boot Precision | Security |
|---|---|---|---|---|---|
| Small 768-d, no boot | 16384 | 420 | 7 | N/A | 128-bit |
| Medium 768-d, 1 boot | 32768 | 800 | 13 | ~22 bits | 128-bit |
| Large unbounded search | 65536 | 1550 | 23 | ~14 bits [4] | 128-bit |

### 4.4 Alternative: Hybrid CKKS-TFHE for Comparison

Vector search often needs *comparison* after scoring. CKKS comparison is expensive (sign approximation polynomial depth 8+). Hybrid approach: switch CKKS ciphertext to TFHE via scheme switching [8], evaluate functional bootstrapping for argmax, switch back. Overhead ~200 ms per comparison but exact. For top-k, better to return encrypted scores to client and decrypt-and-rank client-side — leaks scores but not database vectors, acceptable for RAG.

### 4.5 Error Analysis for Encrypted RAG

Encrypted RAG pipeline [2] over Paillier or CKKS:

- **Dot product error**: $\epsilon_{dp} \le d \cdot 2^{-p}$ where $p$ bits precision from rescaling
- **Normalization error**: If vectors not pre-normalized, need division/inv sqrt — approximate via Goldschmidt iteration depth 5, error $10^{-5}$
- **Bootstrap cascade**: For 10 successive queries, error compounds as $\epsilon_{total} \approx \sqrt{k}\epsilon_{boot}$ if independent

Empirically on LFW 128-d FaceNet embeddings [2][6], PHE dot product achieves Recall@10 0.92 vs plaintext 0.94, while CKKS full achieves 0.935 with 14-bit boot precision — negligible loss.

## 5 Empirical / Proofs

### 5.1 Proof Sketch: Correctness of RNS Rescaling

Given $ct = (c_0,c_1)$ with scale $\Delta^2$, modulus $Q_l$, define $ct' = \lfloor q_l^{-1} ct \rceil$ mod $Q_{l-1}$. Decryption: $\langle ct', s \rangle = q_l^{-1} \langle ct,s \rangle + e_{round}$ where $\|e_{round}\|_\infty \le \sqrt{n}/2$ [3]. Since $\langle ct,s \rangle \approx \Delta^2 m$, dividing by $q_l \approx \Delta$ yields $\approx \Delta m$, preserving scale. QED.

## 6 Limitations

- **Precision vs Depth Tradeoff**: CKKS rescaling modulus $q_i \approx \Delta$ links precision to depth; high precision $2^{50}$ reduces levels for fixed $Q$ [3][4]. Vector search with cosine >0.99 similarity requires >30 bits to distinguish rank, may need 2-boot pipeline.
- **Key Material Size**: Bootstrapping keys ~24 MB–1 GB [7] — $24$ MB optimized TFHE vs $1$ GB naive. Relinearization + Galois keys for $n=65536$, $L=23$ exceed 800 MB in OpenFHE, problematic for edge devices [2].
- **Comparison Bottleneck**: Returning all scores leaks distribution; private top-k requires polynomial approximation of max, depth 10+ and $O(k N)$ cost. Hybrid CKKS-TFHE switching mitigates but adds 200 ms latency per gate [8].
- **GPU Memory Bandwidth**: Large $Q$ with 30 limbs → 30× NTT per multiply; PCIe transfer for key switching matrices becomes bottleneck. On-the-fly twiddling [5] helps but does not eliminate HBM pressure at $n=2^{17}$.
- **Security Model**: CKKS approximate decryption leaks small error; requires circuit-private noise flooding [3] for $IND-CPA^D$ security. Without flooding, scores may leak secret key bits under active queries.

## 7 Conclusion

CKKS provides a compelling substrate for private vector search by aligning approximate homomorphic arithmetic with floating-point embedding similarity. Ring-LWE with RNS decomposition and NTT acceleration enables word-sized operations and GPU parallelism reaching 79–86% peak bandwidth [5]. Bootstrapping via direct modular reduction polynomial [4] restores depth at modest precision loss, allowing unbounded search sessions. Combined GPU pipelines project 15–60× end-to-end improvements, making encrypted RAG and biometric search practical without Paillier's limited expressiveness.

Future work: joint optimization of bootstrapping and rotate-sum (Neujeans [4][8]), low-latency bootstrapping via roots-of-unity [8], and TensorCore NTT with implicit transpose to achieve <100 ms per 768-d encrypted dot product batch.
