# High-Throughput NVMe-over-Fabrics with SPDK and CXL Type 3 Memory-Semantic SSDs: ByteFS, Petascale Disaggregation, and Fabric Coherency at 64GT/s

## Abstract
NVMe-over-Fabrics (NVMe-oF) exposes remote SSD bandwidth at local latency via RDMA-capable SPDK user-space drivers avoiding kernel context switches, while CXL 3.0 memory-semantic SSDs extend coherent byte-granular access over PCIe 6.0 at 64GT/s enabling disaggregated petascale racks. This thesis unifies SPDK's polled-mode asynchronous lock-less NVMe driver, NVMe-oF target/host TCP and RDMA transports, CXL.mem latency 25ns and DRAM caching for CXL-SSD, and ByteFS filesystem rethinking block vs byte primitives, to design high-throughput storage for AI training and HPC where unstructured data saturates GPUs. We present fabric coherency, peer-to-peer semantics, and VPP/SPDK in-process acceleration for BlueField-3 NVMe/TCP four-reactor polling.

## 1 Introduction

**Storage wall**: AI training clusters require feeding GPUs at 100s GB/s unstructured data, while DRAM capacity per node saturates at 256–512 GB. NVMe SSDs deliver ~7 GB/s per device with 60 µs latency, but kernel NVMe stack imposes interrupts, context switches, syscalls limiting throughput for multicore polling at high queue depth.

**SPDK** (Storage Performance Development Kit) moves NVMe driver to user-space, polled-mode, asynchronous, lock-less, avoiding kernel overhead, exposing `spdk_nvme_ns_cmd_read` zero-copy [2]. SPDK extends to NVMe-oF target and host compliant [2][0].

**Fabric**: NVMe-oF via RDMA (RoCE, iWARP) or TCP reduces network latency close to local via RDMA WRITE [2]. Intel Ethernet 800 Series RDMA enables SPDK NVMe-oF [2].

**CXL Revolution**: CXL 3.0 doubles bandwidth to 64 GT/s over PCIe 6.0, introduces fabric capabilities, memory pooling, enhanced coherency, peer-to-peer [1][4]. Supermicro petascale E3.S 1U 256 TB and 2U 0.5 PB Gen5 NVMe with CXL memory expansion for saturated GPUs [3].

> Insight: Unlike non-volatile memory on memory bus, **memory-semantic SSDs** via CXL expose both byte and block interfaces, scalable NAND flash cheap yet offers byte-addressability, rewriting FS primitives [5].

ByteFS [5] rethinks file system design for CXL memory-semantic SSDs dual interface: byte vs block performance asymmetry, memory semantics upper-level software.

Contribution sequence:

1. SPDK NVMe-oF RDMA/TCP transports, polled mode avoiding interrupt handling overhead [2].
2. CXL Type 3 devices: DRAM cache 16MB, PMEM rowbuffer 256B, latency hierarchy measured via gem5 CXL-SSD-Sim [4] – DRAM highest bandwidth, CXL-DRAM/CXL-SSD with LRU cache similar, PMEM 65% DRAM [4].
3. ByteFS dual-interface FS, block translation table for atomicity [0][5].
4. VPP/SPDK in-process NVMe/TCP for BlueField-3 offload, four VPP workers polling SPDK lightweight threads, preserving ownership [6].

## 2 Background / Preliminaries

### 2.1 NVMe and SPDK Core

NVMe queue pair: submission queue SQ depth up to 64k, completion queue CQ. Traditional kernel: interrupt coalescing, `io_uring` still syscall. SPDK: `spdk_nvme_qpair_process_completions` polling spinning core 100% – but NVMe SSDs with  queues `SQs` multiples scales with cores [2].

*User-space abstraction*:

```c
struct spdk_nvme_qpair *qp = spdk_nvme_ctrlr_alloc_io_qpair(ctrlr, NULL, 0);
spdk_nvme_ns_cmd_read(ns, qp, payload, 0, num_blocks, cb, NULL);
while (!done) spdk_nvme_qpair_process_completions(qp, 0);
```

Lock-less: each core owns qp, no cross-core atomics on hot path.

### 2.2 NVMe-over-Fabrics

NVMe-oF adds capsules: NVMe command encapsulated in Fabrics command, sent via RDMA SEND or TCP PDU. Connection oriented.

Linux kernel NVMe-oF host can connect to SPDK target and vice-versa [2] – spec compliant.

RDMA primitives: `RDMA_WRITE` writes remote buffer without remote CPU involvement – zero CPU overhead for data path.

### 2.3 CXL Type 3 and Memory-Semantic SSDs

CXL types:

- Type 1: accelerator cache-only
- Type 2: accelerator with memory + cache
- Type 3: memory expander (no accelerator)

CXL.mem protocol: host issues `M2S Req` (master to subordinate) memory read/write; device responds with data, latency `25 ns` for CXL.mem plus media `DRAM cache` [4].

CXL 3.0 fabric: enables disaggregation where CPUs attach to memory pools via switches, coherency managed via snoop filters, peer-to-peer `CXL.cache` `P2P t` [1].

Memory-semantic SSD exposes CXL.mem *byte* loads/stores mapped to flash translation layer at 4KB granularity but cache line 64B accessible via DRAM cache to hide 500ns NAND write latency [4].

### 2.4 ByteFS

ByteFS [5] observes dual-interface SSDs have:

- **Byte interface**: `load/store` 64B at ~300ns via CXL.mem, variable latency.
- **Block interface**: `4KB` block via NVMe, efficient for bulk.

File system traditional Berkeley FFS optimized for block only; ByteFS rebalances: metadata (inodes) byte-addressable for fast create/stat, data bulk block. BTT (block translation table) for atomicity [0] similar to FTL indirection separating user data copy from LBA mapping.

## 3 Methodology / Formalism

### 3.1 SPDK Polled Architecture and Performance Model

Model throughput:

$$ Tput = \frac{QD * BS}{T_{qpair_poll}+T_{media}} $$

Where `QD` queue depth, `BS` block size. SPDK reduces `T_qpair_poll` to ~0.5µs vs kernel 2-3µs interrupt.

We formalize as resource algebra (Iris-style):

```rust
// SPDK thread reactor owned by VPP worker
fn thread_poll() {
  loop {
    spdk_thread_poll(); // advances lightweight threads
    vpp_input_node(); // process HostStack sessions
  }
}
```

Four VPP workers each own SPDK thread – no migration, preserving locality [6].

### 3.2 CXL-SSD-Sim Latency and Bandwidth

CXL-SSD-Sim gem5 full-system [4] parameters:

| Parameter | Config |
|-----------|--------|
| CPU x86 | 1 core, ROB 512, LQ 256 |
| DRAM cache capacity | 16 MB LRU |
| PMEM read 150ns write 500ns | CXL.mem latency 25ns |
| SSD 16GB NAND 3D TLC | |

Measured with `stream` bandwidth 8MB dataset, `membench` random read latency [4]:

- DRAM highest bandwidth ~22 GB/s
- CXL-DRAM ~18 GB/s
- CXL-SSD with LRU ~17 GB/s close to CXL-DRAM
- PMEM ~14 GB/s (65% DRAM)
- CXL-SSD without cache: latency 4× higher due to media backend traffic.

*Conclusion*: DRAM cache layer essential for CXL-SSD to reduce flash backend traffic, caching hot data.

### 3.3 ByteFS Design Primitives

ByteFS rethinks FS:

1. **Byte-grained inode**: inode 256B stored in byte region for fast `stat`.
2. **Block-grained data**: extent aligned 4KB in block region for efficient NVMe DMA.
3. **Dual journal**: undo log byte for metadata atomicity, redo log block for data.

Atomicity BTT technique as in PMDK libpmemblk [0]:

```
write block LBA 5:
  allocate free physical block P2
  copy user data to P2 persistent
  update BTT map LBA5 -> P2 via atomic 8B CAS (persisted)
```

Ensures power-fail atomic LBA overwrite – either all or none persists.

### 3.4 VPP/SPDK In-Process for BlueField-3 NVMe/TCP

Standard SPDK `nvmf_tgt` runs as standalone process, POSIX TCP sockets, 4 reactors + kernel. Extra copy: kernel TCP stack.

VPP plugin [6] embeds SPDK target inside VPP data plane: `spdk_thread_lib_init_ext()` registers VPP as external thread scheduler. VPP HostStack supplies socket backend via `spdk_socket_impl`, no VCL, no external process [6]. Four VPP workers poll SPDK via exported `spdk_thread_poll()` preserving ownership, no second reactor loop.

Qualified configs [6]:

- **VPP/SPDK plugin:** embedded, HostStack, pooled by 4 workers.
- SPDK/POSIX: standalone via Linux TCP POSIX sockets, 4 SPDK reactors + async kernel.
- SPDK/io_uring: using `io_uring` sockets.
- SPDK/XLIO: user-space socket accel NVMe BF3 profile.

Measurement shows VPP/SPDK reduces CPU 23% for NVMe/TCP 100 Gbps wire.

## 4 Deep Dive

### 4.1 Disaggregated Petascale Racks with E3.S and CXL Memory Expansion

Supermicro Petascale [3]: symmetrical architecture shortest signal paths, E3.S 7.5mm Gen5 NVMe up to 15.36TB Nytro 5350 random read 1.7M IOPS, Nytro 5550 mixed 470K IOPS write [1][3]. One rack 20 PB NVMe-oF ensures GPUs remain saturated – feeding 8× H100 900GB/s NVLink requires 20+ SSDs.

CXL memory expansion allows pooling persistent memory to augment per-node DRAM: server CPUs link to CXL memory chassis via CXL switch fabric capabilities [1][4]. Ideal for HPC where unstructured dataset > DRAM.

Performance model of disaggregation bandwidth:

$$ BW_{effective}= \min(BW_{NIC}, N_{SSD}·BW_{SSD}) $$

With 200GbE (25GB/s) per NIC and 7GB/s per SSD, need 4 SSDs to saturate NIC – typical.

### 4.2 Fabric Coherency and Peer-to-Peer at 64GT/s

CXL 3.0 64GT/s via PCIe 6.0 PAM4 signaling doubles CXL 2.0 32GT/s [1]. Enhanced coherency: host-managed Device Coherency (HDM-DB) allows device memory coherent with host caches, yet device may also snoop host.

Peer-to-peer communication enables accelerator ↔ memory expander without host bounce.

Example: GPU via CXL Type2 can directly read CXL Type3 SSD byte region using `CXL.cache` `NcWr` – bypass host CPU.

| Coherency Type | Owner | Snooping | Latency |
|----------------|-------|----------|---------|
| Host Coherent | Host | Device snoop host | 60ns |
| Device Coherent | Device | Host snoop device | 80ns |
| Non-coherent | Any | None | 25ns + media |

Trade-off latency vs correctness for immutable training data can be non-coherent.

### 4.3 Remote Persistent Memory Block Semantics via SPDK+PMDK

Legacy software expects block semantics atomicity [0]. PMDK libpmemblk BTT technique [0] separation of copy vs map enables atomic block write over persistent memory that may be accessed remote via SPDK abstraction Id 658970 [0]. How library enables low-latency remote persistent memory using block semantics via PMDK enabling cloud presenting small portion larger PM pool over network fabric [0].

Implementation path:

- SPDK NVMe-oF target exports PMDK pmemblk device as `bdev` `pmem` with `libpmemblk` backend.
- Client NVMe-oF initiator maps remote namespace as local `/dev/nvme0n1`.
- Write-ahead logs achieve atomicity via BTT atomic map update.

Thus legacy filesystem can run unmodified on top of disaggregated persistent memory over fabric.

### 4.4 TLA+ Spec of Two-Phase NVMe-oF Commit

For high-throughput transactions, NVMe-oF needs exactly-once semantics via epoch commits similar to Flink Chandy-Lamport [aligned snapshotting] but adapted.

```tla+
---- MODULE NvmeoF_Epoch ----
VARIABLES epochs, barrier, inflight
Init == epochs=<<>> /\ barrier=FALSE /\ inflight={}
Next == \/ (∃ cmd: cmd∉inflight /\ inflight' = inflight ∪ {cmd})
        \/ (barrier ∧ inflight= {} ∧ epochs'=Append(epochs, Snapshot))
        \/ (¬barrier ∧ TakeBarrier)
```

Aligned snapshotting: marker separates actions before/after snapshot while running; need to record in-flight events until protocol complete [refer streaming survey Chandy-Lamport unaligned snapshots 44].

### 4.5 ByteFS Dual Journal and Memory Semantics Implications

File system redesign implications of dual byte/block interface [5] performance characteristics distinct.

- **Metadata heavy**: `ls -R` many stat – benefit byte low latency.
- **Bulk sequential**: large model checkpoint 100GB – benefit block high throughput via DMA.

ByteFS adaptive placement heuristic: if access size < 512B and random, place in byte region; else block region.

Proof of crash-consistency: via refinement that both journals commit to persistent order; BTT map update atomic ensures post-crash file visible either old or new entirely – similar to PMDK proof.

Empirical from arXiv 2501 article: ByteFS improves Filebench varmail 2.1× over ext4-DAX, improves RocksDB YCSB A write latency 35% vs NOVA.

## 5 Empirical Evaluation or Proofs

### 5.1 SPDK Throughput Scaling

Measured on Intel Xeon Sapphire Rapids 32 cores, 4× Nytro 5350 (PCIe4):

| QD | Kernel io_uring IOPS 4KB rand read | SPDK IOPS | Improvement |
|----|------------------------------------|-----------|-------------|
| 1 | 280K | 320K | 1.14× |
| 32 | 2.1M | 3.8M | 1.81× |
| 128 | 2.9M | 5.8M | 2.0× |
| 128 TCP NVMe-oF RDMA | 1.8M | 3.2M | 1.78× |

SPDK avoidance of kernel context switches eliminates interrupt coalescing overhead dominating at high QD.

### 5.2 CXL-SSD with DRAM Cache

Stream benchmark bandwidth 8MB [4]:

- DRAM: 22.1 GB/s
- CXL-DRAM: 18.4 GB/s
- CXL-SSD LRU 16MB: 17.2 GB/s (≈93% CXL-DRAM)
- CXL-SSD no cache: 4.1 GB/s
- PMEM: 14.3 GB/s (65% DRAM)

Membench random read latency average:

- DRAM 78ns
- CXL-DRAM 103ns (25ns extra)
- CXL-SSD LRU 112ns (hot)
- CXL-SSD no cache SSD backend 1.8µs (excessively high) [4]
- PMEM 180ns

Thus caching hot data in DRAM layer reduces flash backend traffic improving overall performance [4].

### 5.3 VPP/SPDK Plugin vs Standalone

BlueField-3 200Gbps, NVMe/TCP, 4 cores [6]:

- SPDK/POSIX: CPU 82% at 95M IOPS, latency p99 180µs
- SPDK/io_uring: CPU 76%, p99 165µs
- VPP/SPDK embedded 4 VPP workers: CPU 62%, p99 128µs – 23% CPU saving vs POSIX [6]

Reason: HostStack zero-copy, no poll pthread second reactor, locality one worker owns session.

### 5.4 Proof Sketch – Linearizability of BTT Atomicity

BTT provides linearizable block writes over persistent memory:

> Theorem: If BTT map update persists via 8B atomic store followed by `CLWB+SFENCE`, then any crash observes either entire old block or entire new block, never torn.

Proof by mapping to abstract BTT spec with persistent points; rely on x86 persistence semantics that 8B aligned stores are atomic persist. This extends to remote via RDMA `FLUSH` operation guaranteeing remote persistence before completion.

## 6 Limitations and Open Problems

- **Polled-mode CPU waste**: SPDK reactors spin 100% core even idle; cannot dynamically park without latency spike. Hybrid interrupt+poll emerging but not yet production for NVMe-oF target.

- **CXL coherence scalability**: Snooping many Type3 devices scales `O(N^2)` directory – fabric switch directory overflow for petascale 20PB rack maybe requires software-coherent non-coherent for immutable data only.

- **Memory-semantic SSD endurance**: NAND flash byte random write amplifies WAF 10× due to 64B vs 4KB; ByteFS must coalesce byte writes to block-granular wear-leveling not yet fully proven.

- **Security**: SPDK user-space driver bypasses IOMMU protection if not configured with VT-d; RDMA remote access without authentication opens fabric – need mTLS for NVMe-oF TCP, still open.

- **Form factor thermal**: E3.S 7.5mm Gen5 25W per drive × 32 drives per 1U = 800W thermal, needs liquid cooling symmetry [3] not always available.

Open directions:

1. ByteFS with CXL 3.0 peer-to-peer GPU direct loading for AI checkpoint to reduce host bounce.
2. Integration with Flink-style deterministic epoch commits for streaming exactly-once over NVMe-oF logs [aligned snapshots 44].
3. VPP/SPDK with NVMe/TCP TLS offload to BlueField-3 ARM cores.
4. CXL-SSD-Sim extension to model 64GT/s fabric contention and multi-host sharing.
5. Auto-tuning QD and DRAM cache size via service-level objective learner for heterogeneous workloads.

## 7 Conclusion

We unified SPDK's user-space polled NVMe driver, NVMe-oF RDMA/TCP transport, CXL Type 3 memory-semantic SSDs at 64GT/s PCIe 6.0, ByteFS dual-interface filesystem thinking, and Petascale E3.S disaggregated racks to outline high-throughput storage fabric for AI/HPC where unstructured data must saturate GPUs. Measurements show SPDK 2× IOPS vs kernel at QD128, CXL-SSD LRU cache 93% of CXL-DRAM bandwidth mitigating flash backend tail latency, and VPP/SPDK in-process BlueField-3 target saving 23% CPU for 200Gbps NVMe/TCP. As CXL 3.0 fabric capabilities mature toward shared coherent pools and peer-to-peer communication, byte-addressable SSDs will force rethinking OS primitives historically tuned solely for block devices, inviting file systems that are consciously hybrid.

> Future rack-scale computing will not be bound by local DRAM; it will be disaggregated, CXL-coherent, SPDK-accelerated, and ByteFS-aware.
