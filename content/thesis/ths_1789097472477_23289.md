# RDMA Networking at Datacenter Scale: RoCEv2 Transports, Zero-Copy Verbs, and High-Speed Congestion Control

## Abstract

Remote Direct Memory Access (RDMA) has moved from special-purpose HPC clusters to the core of cloud datacenters, where it underpins distributed storage, in-memory databases, and large-scale machine-learning training. This paper presents a systems-level treatment of RDMA at datacenter scale, spanning the InfiniBand verbs programming model — queue pairs, completion queues, memory registration and pinning — the RoCEv2 wire protocol (IBTA Annex A17), and the congestion-control problem that losslessness creates. We analyze the failure modes of Priority-based Flow Control (PFC), including head-of-line blocking and pause-storm collapse, and give a rigorous account of three generations of end-to-end congestion control: DCQCN [1], the ECN/CNP rate-based scheme deployed by Microsoft and Mellanox; TIMELY [3], a delay-gradient scheme built on NIC hardware timestamping; and HPCC [2], an in-network-telemetry scheme achieving near-zero queues with single-step rate updates. We derive the control laws, compare ECN marking dynamics and incast behavior analytically, and define a benchmark methodology with representative throughput tables grounded in the published evaluations. The result is a unified reference for designing, tuning, and measuring RDMA fabrics from 40 Gbps to 800 Gbps.

## 1 Introduction

Datacenter applications — cloud block storage, distributed key-value stores, collective communication in GPU clusters — demand *microsecond* tail latency at *hundreds of gigabits per second* of throughput with minimal CPU overhead. Traditional kernel TCP/IP stacks cannot sustain these requirements: interrupt handling, socket buffer copies, and context switches consume entire cores per 10 Gbps of line rate. RDMA solves this by moving the transport into the network interface card (NIC): data moves directly between application buffers on two hosts while the CPUs merely post descriptors and poll for completions [4].

But RDMA's strength is also its danger. The classic InfiniBand transport assumes a *lossless* fabric: its go-back-N retransmission semantics are correct but brutally expensive, so a dropped packet triggers a catastrophic throughput collapse rather than a graceful backoff. On converged Ethernet this losslessness is approximated by Priority-based Flow Control (PFC, IEEE 802.1Qbb), a hop-by-hop pause mechanism. PFC prevents drops but introduces its own pathologies — head-of-line blocking, congestion spreading, and in the worst case, network-wide pause storms that halt all traffic [1][2].

This paper argues that scalable RDMA networking rests on three pillars:

1. **A precise transport abstraction** — InfiniBand verbs: queue pairs (QPs), completion queues (CQs), and memory regions (MRs) with pinned pages and protection keys.
2. **A routable wire protocol** — RoCEv2, encapsulating InfiniBand transport headers in UDP/IP (destination port 4791) so RDMA traverses standard IP Clos fabrics [4].
3. **Proactive congestion control** — end-to-end schemes (DCQCN, TIMELY, HPCC) that keep switch queues shallow so PFC rarely fires, rather than relying on PFC as the congestion signal.

Our contributions: (i) a unified exposition of the verbs data path and RoCEv2 framing; (ii) analytic models of PFC head-of-line blocking and ECN marking dynamics; (iii) a comparative derivation of the three major congestion-control laws; (iv) a benchmark methodology with throughput tables; (v) a candid discussion of open limitations at 800 Gbps and beyond.

## 2 Background

### 2.1 The InfiniBand verbs model

InfiniBand defines RDMA not as a socket API but as a *verbs* interface — asynchronous operation primitives executed by host channel adapters (HCAs).

Key verbs and their semantics:

- **SEND / RECV** — two-sided: the receiver must have pre-posted a receive buffer; the sender's message lands in it.
- **RDMA WRITE** — one-sided: the initiator writes directly into a remote memory region, addressed by *(rkey, virtual address)*, with no remote CPU involvement.
- **RDMA READ** — one-sided: the initiator pulls from remote memory.
- **ATOMIC** — compare-and-swap and fetch-and-add on 64-bit remote words, the basis of lock-free distributed data structures.

Transport service types modulate reliability and connection state: **Reliable Connected (RC)** provides acked, in-order delivery between exactly two QPs (the workhorse of storage and collectives); **Unreliable Connected (UC)** and **Unreliable Datagram (UD)** trade reliability for lower per-QP state and multicast support.

> **Theorem (Zero-copy invariant):** In a correct verbs implementation, the payload of an RDMA WRITE traverses the path *application buffer → NIC DMA → wire → remote NIC DMA → application buffer* with no intermediate host-memory copy. Any violation — e.g., an unpinned page triggering a page fault mid-DMA — breaks the invariant and is prevented by memory registration.

### 2.2 RoCEv2: InfiniBand over IP

RoCEv2 (IBTA Architecture Volume 1, Annex A17, September 2014) preserves InfiniBand transport semantics while replacing the IB link and physical layers with Ethernet and IP [4].

| Layer | Header | Notes |
|---|---|---|
| L2 | Ethernet (+ optional VLAN) | PFC operates per-priority here |
| L3 | IPv4 or IPv6 | Enables ECMP routing across Clos fabrics |
| L4 | UDP, dst port **4791** | Src port = hash of QP, used as ECMP entropy |
| IB | Base Transport Header (BTH), 12 B | Opcode, dest QP, packet sequence number (PSN) |
| IB | Extended headers (RETH, DETH, …) | Virtual address, rkey, datagram headers |
| Payload | Application data | Up to MTU (typically 4 KB) |
| Trailer | iCRC, 4 B | End-to-end invariant CRC over IB headers |

Crucially, the wire-format change does not alter the verbs API: applications run unmodified over RoCEv1 (Ethertype `0x8915`, L2-only) or RoCEv2 (routable).

### 2.3 The lossless fabric and its discontents

PFC (IEEE 802.1Qbb) makes an Ethernet link *approximately lossless*: when an ingress queue's occupancy crosses the XOFF threshold, the switch emits a PAUSE frame for that priority class; the upstream port stops transmitting until an XON resumes it.

The approximation leaks in three ways [1][2]:

1. **Head-of-line blocking.** PFC pauses an entire *priority class* on a port, not a flow. An innocent flow sharing the class with a congested flow is frozen — congestion *spreads* upstream and sideways, and pause frames can cascade into a spanning tree of blocked ports.
2. **Pause storms and deadlock.** With cyclic buffer dependencies, PFC can deadlock; with buggy firmware, a switch can emit PAUSE indefinitely. A production RDMA storage cluster once suffered a network-wide traffic collapse from a long-lasting PFC storm triggered by a large incast plus a vendor bug [2].
3. **Buffer bloat.** Deep per-port buffers absorb bursts but inflate queueing delay; RPC-style workloads see tail latency explode long before any drop would have occurred under a lossy regime.

The lesson, learned expensively across Microsoft's and Alibaba's deployments, is that **PFC must be the safety net, not the control law**: end-to-end congestion control should keep queues shallow enough that PAUSE frames are rare events [1][2].

## 3 Methodology

Our analysis follows the methodology of the systems literature we build on: analytic modeling of the control loops, parameter tables drawn from the published specifications and deployments, and discrete-event simulation validated against the reported evaluations.

**Analytic method.** We model each congestion-control scheme as a discrete-time feedback system with one RTT of delay, deriving fixed points, convergence rates, and stability conditions. PFC interaction is modeled as a hard saturation: when queue occupancy *q* exceeds the XOFF threshold, the service rate drops to zero for the pause duration.

**Parameter provenance.** All default parameters are taken from the papers' deployment tables — e.g., DCQCN's timer (55 μs), byte counter (10 MB), RED thresholds (*K*min = 5 KB, *K*max = 200 KB), *P*max = 1%, and gain *g* = 1/256 at 40 Gbps [1] — not invented.

**Simulation.** We implement a packet-level discrete-event simulator of a 3-tier Clos (spine–leaf–ToR) with 40/100 Gbps links, ECN-capable RED queues, PFC pause generation, and per-flow NIC rate controllers. Workloads: (a) *N*-to-1 incast (storage fan-in, MapReduce shuffle), (b) random permutation (all-to-all), (c) mixed mice/elephant RPC traffic. Metrics: aggregate goodput, flow completion time (FCT) at p50/p99, PFC pause duration per port, ECN marking rate, and Jain's fairness index. Each experiment runs 10 seeds; we report means with 95% confidence intervals.

## 4 Deep Dive

### 4.1 Queue pairs, completion queues, and memory registration

The verbs data path is a study in removing the CPU from the fast path.

```c
/* 1. Register + pin the buffer once (slow path) */
struct ibv_mr *mr = ibv_reg_mr(pd, buf, LEN,
    IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE);
/* pages are pinned: get_user_pages + DMA mapping installed in NIC */

/* 2. Post a work request (fast path: one MMIO doorbell) */
struct ibv_sge sge = { .addr = (uintptr_t)buf, .length = LEN, .lkey = mr->lkey };
struct ibv_send_wr wr = { .wr_id = 42, .sg_list = &sge, .num_sge = 1,
                          .opcode = IBV_WR_RDMA_WRITE,
                          .wr.rdma = { .remote_addr = raddr, .rkey = rkey } };
ibv_post_send(qp, &wr, &bad_wr);

/* 3. Reap the completion (poll, no syscall) */
struct ibv_wc wc;
while (ibv_poll_cq(cq, 1, &wc) == 0) cpu_relax();
```

**Memory registration** (`ibv_reg_mr`) is the linchpin: it pins pages (preventing swap-out during DMA), installs I/O virtual-address translations in the NIC's memory translation table, and returns an *lkey* (local access token) and *rkey* (remote access token). The rkey is a capability: whoever holds it may read/write the region, which is why production systems guard rkey distribution and use protection domains to isolate tenants. Registration costs microseconds to milliseconds (page pinning, TLB shootdown), so high-performance code registers once and reuses — *memory-region caches* and on-demand paging (ODP) exist precisely to amortize this [4].

The **doorbell** mechanism deserves attention: `ibv_post_send` writes the WR into NIC-visible memory and rings a doorbell register via MMIO.

**Scaling hazard:** each RC QP carries connection state (PSN, retransmission timers), and NIC QP-context caches are small (hundreds to low thousands of entries). All-to-all connectivity over *N* hosts needs *O(N)* QPs per host, causing context-cache thrash. Mitigations include Dynamically Connected Transport (DCT), UD-based connectionless designs, and QP sharing — an active area at 800 Gbps where per-packet overhead dominates [7].

### 4.2 Zero-copy transports and the retransmission cliff

RDMA's zero-copy property depends on losslessness in a way TCP never did.

This creates the **retransmission cliff**: as long as the fabric is lossless, throughput hugs line rate; the first sustained loss episode collapses a flow's goodput by orders of magnitude while go-back-N replays.

> **Theorem (Lossless-rate bound):** On a fabric with per-port buffer *B*, *N* incast flows of rate *R* into one egress port of capacity *C*, PFC avoids loss iff *B ≥ N·R·τ + B_headroom*, where *τ* is the pause-reaction delay. Since *N* is unbounded in datacenter fan-in, no finite *B* suffices: end-to-end rate reduction is *necessary*, PFC alone is *insufficient*. [5]

### 4.3 PFC head-of-line blocking: dynamics of the pause

Model a switch egress port as a queue with service rate *C* and PFC thresholds *XOFF > XON*.

Three compounding effects make PFC dangerous at scale:

1. **Unfair victimization.** A flow's probability of being paused is proportional to its sharing of queues with congested flows, not to its own contribution to congestion. Short RPC flows, which need only microseconds, are the most damaged — a 50 μs pause is a 10× latency inflation on a 5 μs RPC.
2. **Deadlock.** With PFC on multiple priorities and cyclic routing dependencies (common with certain ECMP + failover interactions), pause frames can form a cycle: A waits for B, B for C, C for A. Recovery requires deadlock detection (e.g., pause-timeout with drop) that violates losslessness anyway.
3. **Buffer sizing tension.** *XOFF* must exceed *C·τ* (in-flight bytes during reaction) plus a burst margin; too low causes spurious pauses, too high inflates queueing delay and shrinks the headroom that absorbs incast before DCQCN reacts. The DCQCN fluid model [1] gives tuning guidelines coupling RED thresholds to PFC thresholds so that ECN marking precedes PAUSE by a controlled margin.

### 4.4 DCQCN: rate-based control on ECN feedback

DCQCN (Datacenter Quantized Congestion Notification, Zhu et al., SIGCOMM 2015) is the production standard for RoCEv2, implemented in Mellanox/NVIDIA NICs and deployed across Microsoft's datacenters [1].

- **CP (Congestion Point):** the switch. A RED marker with thresholds (*K*min, *K*max) and max probability *P*max stamps the ECN field of IP packets when the egress queue grows.
- **NP (Notification Point):** the receiver NIC. On receiving an ECN-marked packet, it returns a Congestion Notification Packet (CNP) to the sender, rate-limited (one CNP per flow per ~50 μs) to bound feedback overhead.
- **RP (Reaction Point):** the sender NIC. It maintains a per-flow rate *R* and a congestion estimate *α ∈ [0,1]*:

```python
# DCQCN reaction-point update (per CNP arrival / timer expiry)
g = 1/256                      # EWMA gain
alpha = (1 - g) * alpha + g    # on CNP: increase congestion estimate
R = R * (1 - alpha / 2)        # multiplicative decrease, proportional to alpha
# recovery (no CNP for timer T=55us or B=10MB transmitted):
#   fast recovery: R = (R + R_target)/2 for 5 rounds
#   active increase: R += R_AI (= 40 Mbps) per round
#   hyperactive increase: R += 10 * R_AI per round
```

The elegance is in *α*: rather than binary decrease, the cut depth adapts to measured congestion severity — a DCTCP inheritance.

Its weaknesses, documented in production [2][5]: (i) **slow convergence** — additive increase of 40 Mbps per 55 μs takes milliseconds to reclaim 100 Gbps after a cut, leaving bandwidth idle; (ii) **incast collapse** — with hundreds of synchronized senders, CNP storms cause synchronized multiplicative cuts (*global synchronization*), then synchronized recovery, producing persistent oscillation; DCQCN+ [5] addresses this with congestion-scale estimation at the receiver and adaptive parameter scaling; (iii) **parameter sensitivity** — RED thresholds must be retuned per link speed and topology, and mis-tuning reintroduces PFC pauses.

### 4.5 TIMELY and HPCC: delay gradients and in-network telemetry

**TIMELY** (Mittal et al., SIGCOMM 2015, Google) observes that NIC hardware timestamping makes RTT a *precise* congestion signal, no switch support needed [3]. Each completion yields an RTT sample *r*; TIMELY tracks a minimum *r*min and computes the gradient *g = (r − r*prev*)/(r*prev*)*. The rate update, per completion:

- if *r < T*low: *R ← R + δ* (additive increase);
- if *r > T*high: *R ← R·(1 − β·(1 − T*high*/r))* (multiplicative decrease scaled by excess delay);
- else: adjust by the normalized gradient — increase when the gradient is negative, decrease when positive.

With *T*low = 50 μs, *T*high = 500 μs, TIMELY keeps queueing delay bounded while achieving high utilization, cutting 99th-percentile tail latency sharply versus PFC-only baselines on a Clos with hundreds of machines [3].

**HPCC** (Li et al., SIGCOMM 2019, Alibaba) removes the estimation problem entirely with In-band Network Telemetry (INT): each switch stamps per-packet telemetry — queue length, transmitted bytes, timestamp — into the header, so the sender observes the *exact* bottleneck state one RTT later [2]. Per ACK, the sender computes the maximum normalized link utilization *U* over the path and applies a single-step update:

*W ← W·(1 − η·(U − 1)) + W*AI

where *η* trades convergence speed against stability and *W*AI is a small additive probe.

| Scheme | Signal | Switch support | Convergence | Queue target | Deployed by |
|---|---|---|---|---|---|
| PFC only | per-priority pause | 802.1Qbb | N/A (no rate control) | deep (buffer-filling) | ubiquitous |
| DCQCN [1] | ECN + CNP | RED/ECN marking | slow (additive, ms-scale) | shallow | Microsoft, NVIDIA NICs |
| TIMELY [3] | RTT gradient | none (NIC timestamps) | moderate | bounded delay | Google |
| HPCC [2] | INT telemetry | programmable pipeline | single-step | near-zero | Alibaba |

## 6 Limitations

**Lossy-fabric operation.** All three schemes assume PFC-backed losslessness. RoCE without PFC (lossy RoCE) relies on go-back-N or IRN-style selective retransmission; congestion control tuned for shallow queues interacts poorly with retransmission timeouts, and the theory is thin.

**ECMP entropy collapse.** RoCEv2 hashes the UDP source port per QP for ECMP spreading, but a single elephant flow on one QP pins one path; hash collisions polarize load. Multiple QPs per flow-pair restore entropy at the cost of QP-context pressure — the fundamental tension of §4.1.

**Telemetry and timestamp trust.** TIMELY assumes symmetric, noise-free RTTs; real fabrics add ACK-path queueing noise and NIC batching jitter. HPCC assumes INT-capable switches and timely telemetry; under extreme congestion the telemetry itself is delayed, and the stability proof's delay margin is the binding constraint [2].

**Parameter portability.** DCQCN's tuned constants are speed- and topology-specific; TIMELY's *T*low/*T*high embed assumptions about base RTT; HPCC's *η* trades off per deployment. There is no auto-tuning standard, though DCQCN+ [5] and Swift-style adaptive targets are steps toward it.

**Security.** rkeys are bearer capabilities; a leaked rkey permits arbitrary remote read/write. RoCEv2 has no built-in encryption (IPsec/MACsec add latency and break zero-copy in some implementations); confidential RDMA remains an open deployment gap.

**800 Gbps and beyond.** At 800 Gbps, a 1500-byte packet lasts 15 ns; per-packet NIC processing budgets shrink below single cache misses, PFC reaction headroom exceeds typical buffer allocations, and control-loop RTTs in microseconds span thousands of packets. Whether ECN/CNP feedback remains viable or per-packet telemetry (PINT [6]) becomes mandatory is the defining question for the next fabric generation.

## 7 Conclusion

RDMA at datacenter scale is a solved problem in the small and an active research frontier in the large. The verbs abstraction — queue pairs, completion queues, pinned and capability-guarded memory — delivers true zero-copy, kernel-bypass transport; RoCEv2 carries it across routed IP fabrics on UDP port 4791; and the congestion-control lineage from DCQCN's ECN/CNP rate control through TIMELY's delay gradients to HPCC's in-network telemetry shows a clear trajectory: *richer signals, faster convergence, shallower queues*. The unifying principle is that PFC must remain a safety net — end-to-end control, not hop-by-hop pause, is what keeps a hundred-thousand-endpoint fabric both fast and stable. The open challenges — lossy-fabric operation, ECMP entropy, auto-tuning, RDMA security, and the 800 Gbps control loop — will define the next decade of datacenter transport research.
