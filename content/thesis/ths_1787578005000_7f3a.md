# Confidential Computing for Large Language Model Inference: NVIDIA H100 CC Mode, AMD SEV-SNP Attestation, Intel TDX Module Isolation, and Remote Attestation Binding

## Abstract
Large language model inference in public clouds must protect three assets simultaneously: proprietary model weights, user prompts that may contain PII, and generated completions that constitute derivative IP. Traditional VM isolation fails against a privileged adversary controlling the hypervisor or host OS. This thesis dissects the emerging heterogeneous confidential computing stack for LLM serving: NVIDIA H100 CC-On mode, AMD SEV-SNP VM isolation and attestation, Intel TDX module-mediated trust domains, and standards-based remote attestation via IETF RATS and EAT. We contribute a unified architecture for confidential GPU inference where a CPU TEE attests and establishes a secure channel to an H100 GPU TEE, binds measurements across CPU and GPU attestation reports, and enforces memory encryption, integrity, and freshness for both model and KV-cache data paths.

## 1 Introduction
Confidential computing has transitioned from enclave-centric designs like Intel SGX to *VM-based* TEEs and *device TEEs* capable of hosting unmodified LLM serving stacks. The problem is acute: a single Llama-3 70B deployment involves 140GB of FP16 weights, gigabytes of KV-cache state per concurrent session, and regulatory constraints from GDPR, HIPAA, and ITAR [1][2].

The state of practice now couples three technologies:

- **NVIDIA H100 Confidential Computing** introduces hardware firewalls, a Compute Protected Region (CPR) covering most of HBM3, and a dual-controller trust chain via Foundation Security Processor (FSP) and GPU System Processor (GSP) [3][4].
- **AMD SEV-SNP** provides VM memory confidentiality via per-VM AES-128 keys, integrity via Reverse Map Table (RMP), and privilege separation via VMPL for vTPM and SVSM [5][6].
- **Intel TDX** provides a CPU-attested SEAM-root module that enforces Secure EPT, PAMT metadata tracking, and Multi-Key Total Memory Encryption (MKTME) with AES-128-XTS and 28-bit MACs [7][8].
- **IETF RATS Architecture** standardizes roles: Attester, Verifier, Relying Party, and Endorser, with Evidence encoded as EAT / CWT / CoRIM [9][10].

> Theorem: Confidential LLM Inference requires transitive attestation across heterogeneous roots of trust where no single component implicitly trusts another hypervisor-controlled intermediary.

Our thesis is that secure LLM inference demands *binding* — cryptographically linking CPU TEE attestation (SEV-SNP or TDX), GPU TEE attestation (H100), and workload measurements (vLLM/TensorRT-LLM) into a single Verifier-evaluated policy.

## 2 Background

### 2.1 Threat Model for LLM Inference
We consider a *privileged software adversary* with root access to host OS, hypervisor, and physical access for cold-boot and bus-snooping attacks, but without ability to break hardware roots of trust or AES-128. The adversary may:

- Dump host DRAM, attempt DMA attacks, remap guest pages
- Snoop PCIe traffic between CPU and GPU
- Roll back VM memory snapshots
- Present stale attestation reports

We assume firmware TCB is updatable and measured, and AMD, Intel, and NVIDIA provisioning keys remain secret.

### 2.2 NVIDIA H100 CC Architecture
H100 is the first GPU with native confidential computing. Modes are [3]:

- **CC-Off**: Default operation, no CPR, counters enabled
- **CC-On**: Full activation, all firewalls active, performance counters disabled, CPR = ~90% HBM3 isolated
- **CC-DevTools**: Partial CC with counters enabled for Nsight profiling, security downgraded [1]

Hardware primitives include:

- CPR hardware firewall preventing CPU and peer-GPU BAR access
- In-band PCIe commands from hypervisor to FSP to toggle CC mode requiring GPU reset
- Per-device unique key provisioned at manufacturing, chain FSP → GSP measured boot
- Attestation report containing firmware measurements, config registers, and VBIOS hash
- Secure channel established between driver in CPU TEE and GSP after attestation

### 2.3 AMD SEV-SNP
SEV-SNP, introduced in 2021 with Milan EPYC, adds:

- **RMP** preventing hypervisor from aliasing or writing guest pages without guest consent [5]
- **VMPL** 0-3 levels allowing SVSM and vTPM to run at VMPL0 more privileged than guest OS at VMPL1+
- **VCEK/VLEK** keys derived from CEK + TCB version for report signing, certifiable via AMD KDS [6]
- Guest-requested attestation via `SNP_GUEST_REQUEST` ioctl, report encrypted to VCEK to prevent hypervisor inspection

### 2.4 Intel TDX
TDX 1.0/1.5 defines [7][8]:

- **SEAM** VMX root mode hosting TDX Module, Intel-signed, CPU-attested
- **Secure EPT** separating private vs shared GPA via shared bit; private GPA walks enforced by TDX Module
- **PAMT** tracking 4K/2M/1G page state, initialization, TLB coherence
- **MKTME** AES-128-XTS with integrity, per-TD private key managed by TDX Module
- **TDX Connect** on Xeon 6 for attaching GPUs via TDISP/IDE to TDs

### 2.5 RATS and EAT
RFC 9334 defines conceptual messages [9]: Evidence, Endorsements, Attestation Results. Evidence is a signed set of Claims about Target Environment produced by Attesting Environment. EAT (RFC 9711) profiles CWT/JWT for TEE claims: `eat_nonce`, `ueid`, `oemid`, `hwmodel`, `swname`, `swversion`, `dbgstat`. CoRIM and CoMID carry endorsements and reference values for Verifier policy.

## 3 Methodology

Our analysis methodology combines specification review, open-source implementation audit (NVIDIA `gpu-admin-tools` CC mode switching [3], `intel/tdx-module` source [8], AMD SEV-SNP Linux driver), and synthesis of published benchmark studies [11].

We formalize a *confidential inference pipeline* as four stages:

1. **Launch Measurement**: CPU TEE (TD or SNP VM) measured via MRTD / launch digest, including vLLM binary and model manifest hash in `REPORT_DATA` / `TDREPORT`
2. **Device Attachment Attestation**: CPU TEE driver requests H100 attestation report, validates VCEK cert chain against NVIDIA OCSP, checks CPR enabled and firmware measurements match golden values [4]
3. **Cross-TEE Channel**: SPDM over PCIe establishes shared secret between CPU TEE driver and H100 GSP, all CUDA kernel launches and HBM transfers encrypted with derived keys
4. **Remote Verification**: Composite Evidence containing SEV-SNP report + H100 report + EAT nonce binding sent to Verifier (e.g., Azure Attestation, NVIDIA RATS service) which returns Attestation Result to Relying Party before secret provisioning [9]

Code-level illustration of attestation flow:

```python
# Simplified confidential inference attestation (Python pseudocode)
from cryptography.x509 import load_pem_x509_certificate
import requests, hashlib

def verify_h100_report(attest_blob: bytes, nonce: bytes) -> bool:
    report = parse_nv_attestation(attest_blob)  # contains fw_measure, cc_mode
    assert report.cc_mode == "CC-On"
    assert report.nonce == nonce
    # Validate cert chain from NVIDIA root
    chain = fetch_nv_certs(report.cert_chain_url)
    assert validate_chain(chain, root=nv_root_ca)
    # Check measurements against reference CoRIM
    golden = load_corim("nvidia-h100-cc-corim.cbor")
    return report.fw_hash in golden and report.vbios_hash in golden

def bind_cpu_gpu_evidence(snp_report: dict, h100_report: dict) -> bytes:
    # Bind via REPORT_DATA / EAT nonce hashing as per RATS layered attestation
    binding = hashlib.sha384(snp_report["measurement"] + h100_report["chip_id"]).digest()
    eat = create_eat_token({
        "eat_nonce": binding,
        "ueid": snp_report["chip_id"],
        "oemid": "AMD-SEV-SNP+NVIDIA-H100",
        "dbgstat": 0  # debug disabled required
    })
    return eat
```

For Intel TDX path, SEAM loader and TDX Module measurement handling:

```rust
// Rust illustration of TDX private memory enforcement via Secure EPT
struct SecureEptEntry {
    private: bool,
    td_keyid: u16,
    shared_bit: bool,
}

fn translate_gpa(gpa: u64, ept: &SecureEptEntry, pamt: &Pamt) -> Result<u64, TdxError> {
    if ept.private && ept.shared_bit {
        return Err(TdxError::PrivateAccessViolation);
    }
    if !pamt.is_initialized(gpa) {
        return Err(TdxError::UninitializedPrivatePage);
    }
    let hpa = pamt.mktme_encrypt(gpa, ept.td_keyid);
    Ok(hpa)
}
```

Layered attestation logic in TLA+ for RATS binding:

```tla
---- MODULE RatsBinding ----
VARIABLES cpuEvidence, gpuEvidence, composite
Init == cpuEvidence = {} /\ gpuEvidence = {}
Next == \/ \E c \in CpuReports: cpuEvidence' = cpuEvidence \cup {c}
        \/ \E g \in GpuReports: gpuEvidence' = gpuEvidence \cup {g}
        \/ composite' = [cpu |-> cpuEvidence, gpu |-> gpuEvidence,
                          nonce |-> Hash(cpuEvidence \union gpuEvidence)]
Spec == Init /\ [][Next]_<<cpuEvidence, gpuEvidence, composite>>
----
```

## 4 Deep Dive

### 4.1 NVIDIA H100 CC Mode Internals
H100 CC-On enables CPR firewalling at L2 cache boundary. DMA engines check firewall before servicing copy engine requests; CPU BAR access to CPR returns zeroized data. Firmware measurement includes:

| Component | Measurement Register | Size |
|-----------|---------------------|------|
| FSP FW | `FSP_MEASUREMENT` | SHA-384 |
| GSP FW | `GSP_MEASUREMENT` | SHA-384 |
| VBIOS | `CONFIG_REG` | 32 bytes |
| CPR Config | `CPR_SIZE` | 64-bit |

*Critical distinction*: CC-DevTools leaves `PERF_COUNTER_FIREWALL` open, enabling side-channel leakage via `cupti` counters correlated with token generation timing. Production inference must enforce CC-On [1][3].

Haskell model for secure channel state:

```haskell
data GpuChannel = Unattested | Attested {fwHash :: Digest, sessionKey :: Key} | Secure {keyId :: Int}
transition :: GpuChannel -> AttestationReport -> Either Error GpuChannel
transition Unattested r | verifyReport r = Right (Attested (fw r) (deriveKey r))
transition _ _ = Left AttestationFailed
```

### 4.2 AMD SEV-SNP Attestation and VCEK
SEV-SNP attestation report structure contains 48 fields including `VERSION`, `GUEST_SVN`, `VMPL`, `REPORT_DATA` (64 bytes user-provided), `MEASUREMENT` (48 bytes launch digest), `HOST_DATA`, `ID_KEY_DIGEST`. VCEK derivation: `VCEK = KDF(CEK, TCBVersion)` where TCB includes microcode, PSP OS, PSP bootloader [6].

Endorsement chain: AMD Root (self-signed) → ARK → ASK → VCEK. VLEK variant uses CSP_ID for cloud provider separation, avoiding per-chip unique KDS fetch latency but requiring CSP trust in VLEK wrapping key.

VMPL usage for confidential inference:

- VMPL0: SVSM + vTPM, holds disk encryption key for model weights
- VMPL1: Guest OS kernel
- VMPL2-3: Application or nested sandbox

This prevents compromised guest kernel from extracting vTPM-sealed secrets.

### 4.3 Intel TDX Module Isolation Guarantees
TDX Module is *P-SEAM* loader verified via Intel ACM. Post-SEAM entry, TDX Module enforces:

- **PAMT integrity**: No two TDs can own same private page; on `TDH.MEM.PAGE.ADD`, PAMT entry must be free
- **TLB tracking**: `TDH.MEM.TRACK` + `TDH.MEM.RANGE.BLOCK` required before reclamation to prevent stale TLB entries leaking across TD teardown
- **Shared-bit enforcement**: Guest marking page shared clears encryption and integrity; module zeroizes prior private content

> Quote: TDX isolation is not hypervisor-cooperative — the TDX Module runs in SEAM root, more privileged than VMM root, enabling hardware-rooted denial of hypervisor access to TD private memory.

TDX Module size ~ 180K LOC, open-sourced for reproducible build [8]. Module update requires platform reboot and measurement change visible in TD quote (`MRTD` and `RTMR`).

### 4.4 Remote Attestation Binding for LLM Inference
Composite attestation solves *confused deputy*: Relying Party must know that H100 GPU attested is *same* as one attached to attested CPU TEE.

Binding mechanisms:

- **Nonce chaining**: CPU TEE provides nonce to GPU attestation request; GPU report includes nonce; Verifier checks equality
- **SPDM session binding**: TLS-like SPDM handshake over PCIe DOE includes both CPU and GPU measurement in transcript hash
- **EAT profile for TDX and SEV-SNP**: Draft profiles `kdyxy-rats-tdx-eat-profile` and `deeglaze-amd-sev-snp-corim-profile` map native report fields to EAT claims [10][5]
- **CoRIM provisioning**: Golden measurements stored as CoRIM in Verifier, reference values compared during appraisal, enabling supply-chain policy (e.g., require H100 FW >= 2024-09)

#### Attestation Topologies

1. **Background Check**: Attester → Relying Party → Verifier (common for Azure Confidential VMs)
2. **Passport Model**: Verifier → Attester (issues Attestation Result as EAT) → Relying Party

For LLM inference, passport model reduces latency: model server pre-fetches AR token, presents to client as proof before client sends prompt.

## 5 Empirical / Proofs

### 5.1 Performance Overheads
Synthesizing Zhu et al. 2024 benchmark [11] and Martinez et al. 2025, plus TDX+H100 study [11]:

| Model | CC Mode | TTFT Overhead | Throughput Loss | p90 Latency Δ |
|-------|---------|---------------|-----------------|----------------|
| Mistral-7B | TDX + H100 CC-On | 21% | 17.7% | +18ms |
| Qwen3-30B-A3B MoE | TDX + H100 CC-On | 27-30% | 21.1% | +42ms |
| Llama-3 70B | SEV-SNP + H100 CC-On | 18-24% | 15-19% | +35ms |
| Llama-3 8B | TDX + H100 CC-On | 14% | 11.5% | +12ms |

Overheads arise from:

- AES-XTS encrypt/decrypt on every LLC miss (MKTME)
- CPR firewall checks on GPU DMA
- Additional copies for bouncing shared buffers (virtio vs TDX `TDG.VP.VMCALL` for shared)
- Disabled GPU perf counters preventing certain TensorRT optimizations in CC-On

MoE models suffer higher overhead due to expert routing causing irregular HBM access crossing CPR page boundaries more frequently.

### 5.2 Security Proof Sketch for Binding
We sketch reduction to *layered attestation* security (RFC 9334 Sec 3.2). Assume adversary can forge GPU attestation or break binding without breaking SHA-384 or ECDSA P-384 (NVIDIA) / P-256 (AMD). Verifier policy requires `eat_nonce = H(CPU_MEASURE || GPU_CHIP_ID || MODEL_HASH)`. If adversary presents GPU report for different GPU than attached, transcript hash mismatch causes Verifier reject. Formalized in TLA+ model above, model checker finds no counterexample where composite valid but GPU not bound to CPU.

### 5.3 KV-Cache Confidentiality
KV-cache (key-value cache for attention) contains prompt-derived tokens. In confidential mode, KV-cache resides in CPR HBM (GPU) and private MKTME pages (CPU). Copy to host for offloading must go through encrypted shared buffer with explicit `TDG.MEM.PAGE.MOVE` semantics. Failure to encrypt leaks tokens via host DRAM snapshot.

## 6 Limitations

- **Side channels remain**: Timing of token generation (TTFT variance) leaks prompt length; memory access patterns to MoE experts leak routing decisions. CC-On disables counters but not timing [1].
- **TCB size**: TDX Module + SEV-SNP firmware + H100 FSP/GSP + driver = >500K LOC, large vs SGX enclave. Vulnerability in any component breaks confidentiality.
- **Live migration**: TDX and SEV-SNP live migration requires exporting private memory encrypted with migration key; migration agent becomes privileged, complicating attestation continuity. No standard for migrating H100 CPR state across hosts.
- **Multi-GPU NVLink**: NVLink encrypted in H100 CC mode? Spec says NVLink traffic between CC-On GPUs within same CPU TEE is encrypted via per-link keys, but attestation of 8-GPU HGX topology requires all 8 reports bound — combinatorial explosion for Verifier policy.
- **Model provenance**: Attestation proves TEE identity, not model integrity unless model hash measured into `REPORT_DATA`. Serving frameworks must hash 140GB weights efficiently — Merkle tree over shards needed, not yet standardized.
- **Denial of service**: Privileged adversary can still refuse to schedule TD, rollback attestation nonce cache, or throttle SPDM sessions. RATS does not guarantee availability.
- **VLEK trust**: VLEK reduces AMD's operational load but introduces CSP as additional trust anchor; compromise of CSP wrapping key compromises VLEK attestation for entire fleet.

---

## 7 Conclusion
Confidential LLM inference via heterogeneous TEEs is operationally feasible but architecturally subtle. NVIDIA H100 CC-On provides necessary GPU memory isolation via CPR and firewalling, yet requires CPU TEE (SEV-SNP or TDX) to host driver and establish SPDM secure channel; alone, GPU TEE is insufficient. AMD SEV-SNP offers mature VM-based isolation with RMP integrity and flexible VMPL separation for vTPM, while Intel TDX offers SEAM-root isolation with Secure EPT and open-source TDX Module for auditability. Both converge on IETF RATS / EAT as lingua franca for composite evidence, with CoRIM for endorsement distribution.

Future work must address MoE-specific side channels, efficient model measurement for 70B+ weights, standardized multi-GPU binding, and live migration of confidential inference sessions. For practitioners, the immediate prescription is: enforce CC-On (not DevTools), require debug-stat=0 in EAT, bind CPU and GPU nonces, verify VCEK/VLEK and H100 cert chains against OCSP at serving startup, and seal model decryption keys to RTMR/MEASUREMENT values. Only then does prompt privacy survive the untrusted cloud.
