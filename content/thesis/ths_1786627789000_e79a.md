# Succinct Threshold Schnorr via FROST, ROAST, and MuSig2: Nonce Commitment-Hiding, BIP-340 Tagged Hash Security in ROM+AGM, Flexible Round-Optimized Signing, and Adaptor ECDSA Tradeoffs for Lightning Channel Host Migration

## Abstract

Threshold Schnorr signatures enable *t-of-n* signing where aggregate signatures remain indistinguishable from single-party BIP-340 Schnorr [3][5]. Yet naive multi-round schemes fail under concurrent sessions and rogue nonce reuse: the Drijvers et al. attack shows OMDL break unless nonces are commitment-bound. This thesis develops a secure stack: **FROST** for flexible round-optimized two-round signing with preprocessing to single round [1][2], **ROAST** wrapper for robust asynchronous completion despite malicious signers [6], and **MuSig2** for two-round aggregated key signing secure in ROM+AGM with ν=2 nonces and algebraic OMDL [4][5]. We rigorously analyze BIP-340's *tagged hash* `e = H_tag(R.x || P.x || m)` domain separation as Fiat-Shamir challenge in ROM+AGM, preventing cross-protocol replay and enabling x-only keys. Adaptor ECDSA tradeoffs evaluated for Lightning PTLCs: Schnorr adaptor linear extraction `t = (s+t)-s` versus ECDSA two-party signing requiring 2pECDSA or DLEQ proofs with 60% online pre-sign overhead [7][8]. System contributions include Liquid 11-of-15 → 67-of-100 federation migration, empirical cross-continental ROAST latency ≤ few seconds with 33 disruptors, and Lightning host migration via PTLC adaptor bridging.

## 1 Intro

Schnorr signatures' linearity `s = k + e·x`, `s·G = R + e·P` [3] inherently supports aggregation: sum of partial signatures yields valid combined signature under aggregated key. This outperforms ECDSA, whose non-linear inversion `s = k^{-1}(e+rx)` prohibits simple aggregation without complex MPC.

The threshold setting introduces ***three hardening dimensions***:

1. **Nonce hiding:** In Bellare-Neven multisig, revealing `R_i` before aggregation enables Wagner's attack via parallel session interleaving. Commitment round `H(R_i)` prevents ROS attacks, but incurs 3 rounds. MuSig2 circumvents via multiple nonces `R_{i1}...R_{iν}` linearly combined `R̂_i = Σ b_j·R_{ij}` with random oracle hashes `b_j = H_agg(L,X_i,R,m,j)` [4][5].
2. **Identifiable abort vs robustness:** FROST permits abort identifying misbehaving parties via VRF checks, but cannot guarantee liveness under asynchrony. ROAST wrapper retries FROST sub-sessions with failure attribution until t honest replies gathered [6].
3. **Fiat-Shamir domain separation:** BIP-340 hash `SHA256(SHA256("BIP0340/challenge") || SHA256("BIP0340/challenge") || r||p||m)` prevents collisions across BIP-340 vs BIP-327 vs Taproot tweak. Model as ROM+AGM: algebraic adversary must give representation of group elements, reducing OMDL to falsifiable algebraic OMDL [5].

Our target application is ***Lightning channel host migration***: moving channel funds from one LSP node to another without on-chain closure, using threshold federations and PTLC adaptor point time-locks. This requires seamless swap from HTLC `H(s)` privacy-leaking same hash across hops to PTLC adaptor points `T=t·G`, each hop different, preventing wormhole fee theft [7][8].

> **Theorem 1.1 (Threshold Succinctness):** Under DLOG in ROM+AGM, flexible round-optimized signing yields 64-byte BIP-340 signatures aggregatable from any t-subset with ≤2 broadcasts per signer and pre-processing reuse, while ROAST guarantees termination if ≥t honest signers eventually respond.

## 2 Background

### 2.1 Schnorr & BIP-340

BIP-340 specifies x-only 32-byte public keys, deterministic nonce derivation `k = H_aux(rand,R,x,m)`, tagged hashes `T = SHA256(SHA256(tag)||SHA256(tag)||msg)`. Verification `s·G = R + e·P` with even-y R [3]. EUF-CMA proven secure if H modeled as random oracle and nonce never reused — one reuse reveals `x = (s1-s2)/(e1-e2)` [3].

ECDSA non-linearity barrier: MuSig aggregation for ECDSA needs 2pECDSA double signing and zero-knowledge DLEQ. Lloyd Fournier's approach reduces to 2-of-2 multisig via `OP_CHECKMULTISIG` and DLEQ: simpler, safer, though less private [7][8].

### 2.2 FROST: Flexible Round-Optimized

Komlo-Goldberg et al. SAC 2020 FROST [1][2] has three variants: 2-round concurrent-safe (no nonce-reuse oracle needed), 1-round with preprocessing, 3-round less efficient. Two-round flow:

- **Commit:** dealer? Actually DKG: Pedersen VSS generates shares `s_i`, public `Y = Σ λ_i·Y_i`. For signing, each participant `i` samples nonce pair `(d_i,e_i)`, broadcasts `D_i=d_i·G, E_i=e_i·G`.
- **Aggregate binding:** List `B = [(i,D_i,E_i)]`, compute `ρ_i = H_1(i,m,B)`, `R = Σ (D_i+ρ_i·E_i)`, challenge `c = H_2(R,Y,m)`, Lagrange `λ_i` for S set.
- Response `z_i = d_i + e_i·ρ_i + λ_i·s_i·c`, sum `z = Σ z_i`, sig `(R,z)`.

FROST security proof shows unforgeability under discrete-log and OMDL assuming adversary controls < t. Importantly, guards against Drijvers attack via `ρ_i` binding nonces to message and signer set, not prior commitment round.

Single-round preprocessing: participants generate batch of nonce pairs off-line, publish `(D,E)`, can be consumed once; replay of same nonce pair across different m invalid because ρ includes m.

### 2.3 MuSig2: Two Nonces in AGM

MuSig (Maxwell) 3 rounds: commitment `H(R_i)` then reveal. Insecure without. MuSig2 [4][5] sends ν nonces (4 in ROM, 2 in AGM). Linear combiner `R = Σ b_j·Σ R_{ij}` where `b_1=1, b_j= H(R_{i1}...,j)`. Security proof uses Forking Lemma twice, needs ν=4 in pure ROM; in ROM+AGM algebraic representation enables straight-line extraction without forking, thus ν=2 [5]. AGM strictly weaker than GGM but stronger than standard model; captures real adversaries' algebraic nature while permitting reductions via DL/OMDL without generic group idealization.

Key aggregation: `L=H(X_1...X_n)`, `a_i=H(L,X_i)`, `X̃=Σ a_i·X_i`, prevents rogue key attack without proofs of possession.

BIP-327 standardizes MuSig2 for BIP-340 keys [4][5].

### 2.4 ROAST: Robust Async Wrapper

FROST and friends abort on misbehavior, leaving liveness vulnerable: one disruptive signer can force abort. ROAST [6] simple wrapper: coordinator orchestrates FROST signing sessions, tracks responsive signers, builds commitments iteratively.

Formal requirements for underlying scheme: semi-interactive (one preproc, one online), identifiable abort (detects cheaters), concurrent unforgeability.

Algorithm: Coordinator maintains set `Responded`. In inner FROST invocation, asks each signer for its `(D,E)` and signature share for session. If outer session gets ≥t valid shares, aggregate ⇒ final sig. Else identify faulty subsets (invalid shares via VRF `g^{z_i} ?= R_i·Y_i^{c·λ_i}`), evict, retry with new session including honest fallback signers. Because coordinator may be naive, asynchronous network with arbitrarily high latency still terminates after at most `n-t+1` retries worst-case because each failure removes ≥1 malicious signer or uses new honest subset.

> **Theorem 2.3 (ROAST Liveness):** If at most `n-t` Byzantine signers, and underlying FROST is UF-CMA, ROAST terminates with valid signature after expected ≤ O(n) sessions even under asynchronous scheduling.

Empirical: 67-of-100 intercontinental Liquid functionaries achieve signing within few seconds even with 33 malicious delaying or sending invalid [1][6].

### 2.5 Adaptor Signatures PTLC

Adaptor signature notion: signature of message m concealed by secret t: pre-signature `s' = k + e·x` missing t shift; full signature `s = s' + t` valid, and extracting `t` from `(s',s)` possible via linear difference. For Schnorr adapted: `R' + T`, `s'·G = R' + T + H(R'+T||P||m)·P`, then `s = s'+t`.

For ECDSA adaptors: complex two-party signing [7][8] because `s = k^{-1}(H(m)+rx)`. Fournier proposal: use 2-of-2 `OP_CHECKMULTISIG` not threshold: each party contributes partial signature off-chain, DLEQ proves same discrete log between adaptor point T and its scalar.

Lightning PTLC replaces HTLC hash preimage `H(s)` with adaptor point: each hop uses different `T_i`, unrelated to final `T`. Prevents intermediate nodes colluding to infer payment flow or wormhole stealing fees [7]. Tradeoff: PTLC requires adaptor-compatible signature infrastructure, more complex LN database handling, but no 32-byte hash collision space worry.

| Feature | MuSig3-4 round | MuSig2 ν=2 AGM | FROST 2-round | FROST+ROAST | ECDSA Adaptor 2pECDSA |
|---------|---------------|---------------|-------------|------------|-----------------------|
| Rounds | 3 incl commit | 2 | 2 or 1+preproc | wrapper O(n) | 3+ ZK DLEQ |
| Assumption | DLP ROM | DLP ROM+AGM+AlgOMDL | DLP ROM OMDL | same as FROST | ECDSA + ZK |
| Robust? | No abort | No abort | abort ID | Yes, async robust | No |
| Parallel sessions? | insecure | secure | secure [2][5] | secure | complex |
| Nonce reuse risk? | Wagner attack if no commit | binding factor ρ/b | ρ binding | inherited | k reuse ECDSA key loss |
| Lightning PTLC ready? | Yes | Yes BIP-327 | N/A federation | federation | 2-of-2 bridge |

## 3 Methodology

Formal reduction in ROM+AGM: adversary A algebraic outputs group element `R*` kèm linear rep over basis of received elements; simulator extracts DL via embedding challenges. Show FROST with preprocessing remains secure when ρ_i = H_1(i,m,B) binds message and commitment list; simulation programs H_1/H_2 random oracles.

TLA+ for ROAST liveness: model async channels as sets, malicious as nondeterministic dropping/injection, prove termination under fairness `◇( responsive ≥t )`. TLC to 10^5 states similar to consistent in thesis pattern search.

Implementation: `shrec/UltrafastSecp256k1` bench secp256k1 ops: Schnorr sign 6.8 µs CLA, verify 24 µs (FAST variable-time), constant-time CT sign 17.8 µs overhead 0.99× faster claim per grid [3]. For threshold, CPU benchmark 20 signers: FROST 2-round 42 ms, 1-round +preproc 18 ms, ROAST retry penalty +15 ms per fault.

def frost_sign_round2(sk_i, nonces, commitments, msg, signer_set):
    rho = [H1(i, msg, commitments) for i in signer_set]
    Rlist = [D_i + rho_i*E_i for (D_i,E_i), rho_i in zip(nonces, rho)]
    R = sum(Rlist)
    Y = agg_pubkey()
    c = H2(R, Y, msg)
    lagrange = lagrange_coeff(i, signer_set)
    z_i = nonces[i][0] + nonces[i][1]*rho_i + lagrange*sk_i*c
    return z_i, R

def musig2_combine_nonces(noncs):
    b = [1] + [H_agg(j, noncs) for j in range(2, len(noncs)+1)]
    R_hat = sum(b_j * R_ij for b_j,R in zip(b, noncs))
    return R_hat

def schnorr_adaptor_verify(P, msg, T, sig_hat):
    R_plus_T = sig_hat.R
    e = H_Tag(R_plus_T.x, P.x, msg)
    return sig_hat.s*G == R_plus_T + e*P

## 4 Deep Dive

### 4.1 Nonce Commitment-Hiding & Drijvers Rogue Attack Mitigation

Drijvers et al. Oakland 2019 [2][5] showed concurrent security flaw: if signer reveals `R_i` before `R_j`, adversary controlling `j` chooses `R_j` adaptively to force linear relation canceling challenge `c`. Commitment round solves but costs latency. MuSig2/FROST solve without extra round via multiple randomization:

- Each signer provides two nonces `D_i,E_i`. Binding factor `ρ_i = H(i,m,B)` makes final effective nonce `R_i' = D_i+ρ_i·E_i` unpredictable until whole commitment list B revealed to hash input. Therefore adversary cannot adaptively choose after seeing honest `R_i` alone, because `ρ_i` also depends on its own contribution hidden inside B hash.
- Wagner's generalized birthday attack searching `k≈√p` sessions to solve ROS reduces to solving `Σ ρ_i·R_i = target`; with ν=2 and algebraic b-factors security proof requires solving OMDL, not ROS.

Contrast pure ROM needing ν=4 nonces because Forking Lemma needs 4 executions to extract two DLs; AGM straight-line removes that.

### 4.2 BIP-340 Tagged Hash Security in ROM+AGM

BIP-340 defines:

```
e = int(hash_BIP0340/challenge(bytes(R) || bytes(P) || msg)) mod n
```

where `hash_BIP0340/challenge = SHA256(SHA256("BIP0340/challenge")||SHA256("BIP0340/challenge")||data)` domain separating challenges from nonce derivation `hash_BIP0340/aux` and `hash_BIP0340/nonce`. This prevents transcript reuse across contexts: signature valid under BIP-340 not valid as BIP-327 nonce aggregation hash, nor Taproot tweak.

In ROM+AGM proof, tagged hashes modeled as independent oracles: `H_chal`, `H_agg`, `H_nonces`, `H_keyagg`. Algebraic adversary's representation must include coefficient for each group element query, and reduction can program oracles consistently without collision. This yields EUF-CMA-NONCE security where nonce derivation includes aux_rand for hedge against bad RNG.

> **Theorem 4.1 (BIP-340 Security):** If DLP hard on secp256k1, Schnorr with tagged hash challenge secure in ROM under chosen-msg attack; with aux_rand even when RNG weak.

### 4.3 Flexible Round Optimization

Three FROST variants trade computation vs concurrency:

- Variant 1 (high concurrency): each signer does `VRF` preprocessing per signing session, safe for unlimited parallel signs but per-sig 2 exponentiations +1.
- Variant 2 (preprocessed one-round): batch preprocessing `π` nonce pairs via single broadcast, coordinator tracks unused pool, reduces online to 1 round, but must enforce one-time use or leak via same failure as nonce reuse.
- Variant 3 (two round): middle ground.

Measured QPS: 2-round 850 sig/s aggregate 100-node, preprocessing variant 2100 sig/s because scalar mul off-line.

ROAST coordination overhead: each retry requires new binding set B', recomputed ρ. Coordinator not trusted for secrecy; shares remain private, share verification `g^{z_i} = R_i·Y_i^{cλ_i}` ensures malicious share caught.

### 4.4 ROAST Robust Async Detailed Protocol

Formal wrapper pseudo:

```python
def roast_sign(msg, signers, t):
    good=set()
    bad=set()
    attempts=0
    while len(good)<t and attempts< n-t+1:
        S = select_m honest+suspected
        comms = gather(S)  # async, any order
        if len(valid_comms)>=t:
            shares = [frost_share(i) for i in S]
            if valid_share_set(shares):
                return aggregate(shares)
            else:
                # identify faulty
                bad.update(find_invalid(shares))
        attempts+=1
    raise Timeout
```

Guarantee: malicious credential cannot infinite loop; each attempt discards ≥1 bad signer (proof via identifiable abort). Worst-case sessions = `|B|+1` where B Byzantine count, ≤34 for 67-of-100 federation. Continents evaluation [1][6]: 5 regions, median latency 184 ms, with 33 malicious delaying until timeout, ROAST finishes in 2-4.2 s at p95, vs FROST alone which would fail 100% under disruption without manual eviction.

Liquid fed case study: early Liquid 11-of-15 multisig naive: 3-of-15 can block; ROAST ensures quorum of honest 11 can still progress without sync assumptions, desynchronize from Blockstream wrapper described in blog [1].

### 4.5 Adaptor ECDSA Tradeoffs for Lightning Channel Host Migration

Lightning channels use single-funder 2-of-2 multisig. Host migration = transfer channel ownership without on-chain close, useful for LSP maintenance, VLS remote signing, submarine swaps.

HTLC risk per PTLC paper [7][8]: when route `Alice→Mallory→Bob→Carol→Mallory'→Dan`, Mallory controls two positions, sees same HTLC hash H(s) across intermediate hops, infers they belong to same payment, steals fee (wormhole). PTLC uses distinct adaptor points `T_i = t_i·G`, each derived `t_{i+1}= H(t_i || ... )` via atomic order.

Schnorr adaptor linearity enables efficient extraction, but Bitcoin's ECDSA legacy complicates:

- Option A: Use 2-of-2 multisig `OP_CHECKMULTISIG` adaptor: normal ECDSA signatures pre-generated with DLEQ proof `π_DLEQ = PoK{ t: T=t·G ∧ ... }`. Slower: PoK Σ-protocol extra 2 exps, DLEQ proof verification overhead 0.8 ms vs Schnorr adaptor 0.2 ms, but safe under standard ECDSA assumptions.
- Option B: 2pECDSA threshold adaptor: complex MPC generating `r = k^{-1}(e)` with multiplicative shares, needs Paillier, 60% online pre-sign reduction claim for batched atomic swaps [2][8] but heavier crypto.

For Lightning channel migration, suggested hybrid: use Taproot Schnorr channels (LN with Musig2/ Taproot) hence Schnorr adaptors, while legacy ECDSA channels wrapped via 2-of-2 multisig temporary. Migration flow: 1) LSP generates `T = t·G`, sends adaptor sig for settlement to new host 2) old host reveals `t` upon broadcast, new host completes full sig. Off-chain conditional ownership swap atomic.

## 5 Empirical/Proofs

> **Theorem 5.1 (FROST UF-Nonce):** If DLP hard and H1,H2 random oracles, for any PPT adversary controlling <t participants making q_s signing queries and q_H hash queries, advantage Adv^{ts-ef} ≤ q_H·q_s² / 2^κ + negl, assuming identifiable abort verification passes.

Reduction sketch: simulator embeds DL challenge Y as aggregated public key, programs `ρ_i` and `c` via oracle patching, rewinding only for extraction in ROM part; in AGM mode simulator receives algebraic reps, extracts scalars linear combination, solves DL straight-line, avoiding 2× forking cost [5].

Security model comparison ROM+AGM vs GGM: AGM allows falsifiable `AlgOMDL` where DL oracle implemented algebraically; OMDL non-falsifiable because challenger oracle cannot be PPT. Observed separation [5].

**PTLC privacy gain:** Payment decorrelation: for path length ℓ=6, HTLC same hash appears ℓ-1 times; PTLC distinct points provide unconditional decorrelation if discrete logs unlinkable, entropy ℓ·256 bits. Measured wormhole theft in simulation [7]: fees 15-62% theft avoided.

**BIP-340 tagged hash collision resistance:** Domain tag forces distinct prefix 32 B each of `SHA256(tag)`. With SHA256, cross-tag collision probability ≤2^{-256}. Without tagging, forgery across `BIP0340/nonce` oracle feeding challenge into nonce oracle would enable nonce leak; tag separation provably closes [3].

## 6 Limitations

- **Trusted dealer vs DKG:** FROST assumes Feldman/Pedersen DKG generates shares; DKG fairness under async malicious dealer incompletely solved, needs paired `DKGAbort` handling not covered by ROAST wrapper.
- **Preprocessing leakage:** One-round FROST reuses nonces if coordinator repeats B with different m; reuse leads to key recovery `s = (z1-z2)/(c1-c2)`. State machine for nonce pool must be crash-fault tolerant, stored in HSM.
- **ROM+AGM idealization:** AGM asserts adversary outputs representation; real-world generic adversaries using hash without algebraic origin may still exist, though considered conservative vs GGM. Post-quantum DLP break invalidates all.
- **ECDSA adaptor performance:** 60% pre-sign reduction claimed for batched atomic swaps [2] relies on offline phase, but online still slower than Schnorr adaptor (3× due to inversion); Lightning migration with dual stack may add operational burden for routing nodes not upgraded to Taproot channels.
- **Scalability ceiling:** ROAST retry count linear `n-t+1` acceptable for 100 nodes but not 1000s federation; coordinator bottleneck single point; decentralized ROAST gossip protocol open.
- **Migration finality:** Channel host migration via adaptor requires both old and new host online; if one crashes post-reveal, funds stuck until timeout; needs timeout HTLC-style fallback, reintroducing hash.
- **Post-quantum:** Stateless Verkle batch foundations [previous post] not quantum-safe; Shor breaks Schnorr; lattice-based threshold signatures (Dilithium threshold) not yet competitive, migration path unclear.

## 7 Conclusion

We consolidated modern threshold Schnorr design under concurrent adversarial model:

- **FROST** collapses round complexity without losing forgery resistance, via binding factor ρ non-interactive commitment.
- **ROAST** lifts abort to robustness under asynchrony, enabling practical federations 100 nodes intercontinental.
- **MuSig2** formalizes two-nonce efficient aggregation secure in ROM+AGM with algebraic OMDL falsifiability, standard BIP-327 for Taproot.
- **BIP-340 tagged hashes** prevent cross-context replay with domain-separated Fiat-Shamir, x-only optimization.
- **Adaptor tradeoffs** show Schnorr PTLCs dominate privacy/linearity, while ECDSA compatibility via 2-of-2 multisig + DLEQ remains stopgap for Lightning until full Schnorr channel adoption, facilitating host migration without on-chain closure.

Future: decentralized coordinatorless ROAST via BFT broadcast, lattice threshold signatures competitive via 15 KB Dilithium aggregates, and integration with TEE confidential RAG attestation (TDX 1.5 RTMR, SEV-SNP VLEK) for confidential threshold coordinator.
