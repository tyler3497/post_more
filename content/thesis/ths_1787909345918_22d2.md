# Hyperscale Feature Store Temporal Correctness: TARDIS Point-in-Time Joins, Feast On-Demand Transformations, Temporal Interval Versioned Storage, and Proof of Time Consistency via TLA+ Trace Refinement

## Abstract
Feature stores promise training-serving consistency by decoupling feature definition from physical storage, yet temporal correctness remains their hardest invariant. This thesis formalizes point-in-time (PIT) joins, on-demand transformation semantics, and versioned offline storage under bi-temporal intervals. We define PIT correctness as selecting the latest feature whose event timestamp ≤ label event timestamp per entity, preventing future leakage. We contrast Feast's offline/online dual stores and Tecton's event-driven validity intervals, then model Delta Lake time travel as versioned snapshot semantics for auditability. Using a TLA+ trace refinement lens, we specify safety: any materialized training row must be reproducible from historical feature and entity timelines. We present design patterns, failure modes, and operational checks for skew, TTL expiry, and late arrivals. The result is a practitioner-oriented correctness model that aligns implementation (Feast SDK, DuckDB ASOF JOIN, valid_from/valid_to) with specification, enabling leakage-free training without overstating unverified performance claims.

## 1 Introduction

Training a model on future information is a classic form of leakage. In batch ML it appears as using today's aggregated feature to predict yesterday's label. In production it appears as online serving returning a different value than training saw for the same logical time. Feature stores exist to close that gap [1][3].

A feature store provides three logical components: an offline store for historical features used in training, an online store for low-latency serving, and a registry for definitions [1]. The critical operator is `get_historical_features(entity_df, features)` which must perform a temporal join, not a snapshot join. For each row in the entity/label dataframe with timestamp `t_event`, the system must return the feature value valid at `t_event` [2][5].

This thesis reconstructs temporal correctness from first principles:

- **When does PIT matter?** Every training row has its own event time. Using `NOW()` instead of `t_event` inflates AUC and collapses online [2].
- **What are the semantics?** Latest record with `feature_timestamp <= event_timestamp`, bounded by TTL, plus on-demand transformations computed deterministically from base columns [1][2].
- **How to version?** Delta Lake `TIMESTAMP AS OF` and `VERSION AS OF` give snapshot isolation over the offline store, enabling reproducibility and rollback [5][6].
- **Can we specify it?** TLA+ style invariants: `TypeOK`, `TimeCorrect`, `NoFutureLeak`.

We deliberately avoid fabricated benchmarks. Our contribution is definitional, architectural, and operational: a clear model for PIT correctness, its implementation in Feast and Tecton, its storage substrate in Delta Lake, and its formal specification sketch.

## 2 Background

### 2.1 Feature Stores: Feast and Tecton

Feast defines entities, feature views, and sources [1]. A `FeatureView` groups features with shared entity, TTL, and source. The SDK's `get_historical_features` takes an entity dataframe containing `event_timestamp` and returns PIT-correct features by joining against offline storage (Parquet, BigQuery, Snowflake) using interval semantics [1][4].

Tecton makes point-in-time correctness explicit: training data generation requires a timestamp per sample, and features are valid over `[valid_from, valid_to)` intervals that never overlap for the same join keys [2][3]. For non-aggregate views, validity ends on overwrite or TTL expiry; for aggregate views, on window entry/exit [3]. This interval model enables both online serving ("what would the online store have returned at time t?") and offline audit.

### 2.2 Temporal Databases and Time Travel

Point-in-time joins have roots in temporal databases: bi-temporal tables track valid time and transaction time. Modern lakehouses approximate this with versioned Parquet: Delta Lake maintains a transaction log, supporting `TIMESTAMP AS OF` and `VERSION AS OF` to query prior snapshots [5][6]. `DESCRIBE HISTORY` shows operations, enabling debugging of data quality issues that affect feature freshness [6].

Point-in-time correctness for feature data can be formalized as: given label set `L(e, t_event)` and feature history `F(e, t_feature, v)`, the correct value is `v` where `t_feature = max{ t | t <= t_event and entity=F.entity }` [7]. SDKs abstract this asof-join complexity; users provide spine and features list [1].

### 2.3 Why Not Naive Joins

A naive join `SELECT ... FROM labels JOIN features_today ON user_id` uses current feature values for historical labels, a leakage pattern [1][7]. Example: churn label on Feb 1st should use features computed before Feb 1st, not aggregates that include post-churn behavior [7]. Feast's documentation shows training dataset construction where zipcode and credit history features are joined in PIT-correct way by only including features available at loan active time [4].

## 3 Methodology

We use specification → pattern → validation methodology, not benchmark chasing.

1. **Trace definition:** Entity timeline `E = {(entity, t_event)}`, feature timeline `F = {(entity, t_feature, v, created_at)}`. Both are append-only logs partitioned by date for offline efficiency [1].

2. **PIT Join Specification:** Formal operator:

```
PIT(E, F) = { (e, t_event, v) | (e, t_event) in E, 
              v = F(e, t*), 
              t* = max{ t_feature | t_feature <= t_event and entity=e 
                       and t_event - t_feature <= TTL } }
```

Strict `<=` not `<` ensures same-millisecond features included; TTL window prevents stale features [2].

3. **On-Demand Transformations:** Feast 0.30+ supports on-demand feature views: Python UDF transforms base features at retrieval time for both offline and online paths, guaranteeing single-definition reuse [1]. This prevents skew where training computes `avg_30d` in Spark SQL but serving recomputes in Python differently.

4. **Versioned Storage:** Delta Lake time travel gives snapshot isolation: `SELECT * FROM table TIMESTAMP AS OF '2026-01-15'` returns exactly the files valid at that log version [5][6]. For feature stores, this enables reproducible `feast materialize` runs and point-in-time debugging when freshness SLOs fail.

5. **Formal Sketch:** TLA+ module `FeatureStore` with variables `offlineLog`, `onlineStore`, `entityRequests`. Actions `IngestFeature`, `Materialize`, `GetHistorical`, `GetOnline`. Invariants:

- `TypeOK == offlineLog \in Seq(FeatureRow) /\ onlineStore \in [Entity -> Feature]`
- `TimeCorrect == \A r \in trainingRows: r.featureTimestamp <= r.eventTimestamp`
- `NoLeak == \A r: ~\E f \in offlineLog: f.entity=r.entity /\ f.timestamp > r.eventTimestamp /\ f.value = r.value /\ f.created > r.eventTimestamp`

TLC can check these on finite traces (N=4 entities, 3 timestamps) to catch off-by-one errors in TTL handling. This is a design aid, not a proof of production scale.

## 4 Deep Dive

### 4.1 Architectural Model and Cost Semantics

State `S = (Registry, Offline, Online, MaterializationWatermark)`. Transitions:

- `Ingest`: append to Offline, no immediate Online change.
- `Materialize(t_start, t_end)`: copy latest per entity from Offline where `event_timestamp in [t_start, t_end]` to Online [1]. Incremental materialization uses high-water mark.
- `RetrieveHistorical(E)`: asof join against Offline, not Online, to avoid serving-induced staleness.
- `RetrieveOnline(entity)`: point lookup in Redis/SQLite.

Cost is not throughput but correctness debt: leakage causes inflated offline metrics that do not transfer online [2]. Tecton's tutorial shows why per-sample timestamps matter: ad click-through prediction must use features available at impression time, which differs per sample [2].

Block size considerations: offline partitioning by `event_timestamp` date enables efficient range scans for PIT joins; online store sharding by entity key enables horizontal scaling [1]. Feast supports this via `FileSource` with `timestamp_field` and `created_timestamp_column` to disambiguate event vs ingestion time [1].

### 4.2 Core Algorithmic Innovation - PIT Join Patterns

**Pattern: Standard PIT Join (SQL)**

```sql
-- From feature store SKILL [1] - canonical form
SELECT l.user_id, l.event_timestamp, l.label, f.feature_value
FROM labels l
LEFT JOIN features f
  ON l.user_id = f.user_id
 AND f.feature_timestamp <= l.event_timestamp
 AND f.feature_timestamp > l.event_timestamp - INTERVAL '30 days'
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY l.user_id, l.event_timestamp 
  ORDER BY f.feature_timestamp DESC
) = 1
```

Feast's implementation pushes this into data warehouse engines (BigQuery, Snowflake) or DuckDB for local testing [1]. DuckDB `ASOF JOIN` is syntactically cleaner: `FROM labels ASOF JOIN features ON user_id AND feature_timestamp <= event_timestamp` [2].

**Pattern: Entity DataFrame (Feast Python)**

```python
from feast import FeatureStore
import pandas as pd

store = FeatureStore(repo_path="feature_repo/")

entity_df = pd.DataFrame({
  "user_id": ["u001", "u002"],
  "event_timestamp": pd.to_datetime(["2024-05-01", "2024-06-15"]),
})

training_df = store.get_historical_features(
  entity_df=entity_df,
  features=["user_stats:tenure_days", "user_stats:amount_30d"],
).to_df()
# Feast picks LATEST feature row whose event_timestamp <= entity event_timestamp [1]
```

This prevents future leakage [1]. Bad pattern is `get_online_features` + merge to historical events, which contaminates training with today's values [1].

**Interval Validity (Tecton)**

Tecton's `get_features_in_range` returns `_valid_from`, `_valid_to` per row, non-overlapping per join key [3]. Definition: feature valid if online store would have returned it if queried at that moment [3]. For aggregate views, validity changes when event enters/exits sliding window [3].

### 4.3 Composition, Pipelining, and Runtime Interaction

Feast pipeline: `feature_store.yaml` declares provider (local, GCP, AWS), registry path, online/offline store types [1]. Example local:

```yaml
project: my_project
registry: data/registry.db
provider: local
online_store:
  type: sqlite
  path: data/online.db
offline_store:
  type: file
```

Feature views registered via `feast apply`, then `feast materialize` copies offline to online for serving [1]. Feature server `feast serve` provides REST API on port 6566; `feast ui` on 8888 for discovery [1].

Materialization frequency trades freshness vs cost. Streaming feature views via Rift or Spark Structured Streaming achieve <1s freshness [3][5]. Batch materialization hourly/daily is simpler but risks stale online features; monitoring freshness age, null ratio, and PSI drift is required [1].

On-demand transformations: Python UDF `def transform(df: pd.DataFrame) -> pd.DataFrame` runs inside both `get_historical_features` and `get_online_features` paths, ensuring train/serve symmetry. This is critical for derived features like `avg / count` that should not be pre-materialized.

Pipelining backpressure: `Q_max=4096` queue for materialization prevents OOM when offline store has millions of rows; credit-based batching amortizes driver calls.

### 4.4 Resource Accounting and Versioned Storage

Delta Lake time travel is the versioned substrate [5][6]. Syntax:

```sql
SELECT * FROM sales TIMESTAMP AS OF '2026-01-15 14:30:00';
SELECT * FROM sales VERSION AS OF 42;
DESCRIBE HISTORY sales;
```

Python:

```python
df = spark.read.option('versionAsOf', 0).table("people_10k")
df = spark.read.option('timestampAsOf', '2026-01-05T23:09:47').table("people_10k")
```

Retention `delta.deletedFileRetentionDuration` (default 7 days) and `logRetentionDuration` (30 days) bound how far back you can travel [6]. For feature stores, setting longer retention (e.g., 90 days) enables audit of training datasets that used older feature values.

Offline store partitioning by date enables efficient time-range queries for PIT joins [1]. Online store memory utilization (Redis) and serving latency p50/p95/p99 are monitored [1].

Carbon/cost awareness: while not central to temporal correctness, placing offline store in columnar cheap storage (S3) and online in memory (Redis cluster) balances $/query. Materialization parallelized by feature view partitions [1].

## 5 Empirical Validation Sketch (Not Benchmarks)

We do not claim 2-10x wins. Instead we describe validation approach consistent with docs:

- **Leakage demonstration:** Train two models on same labels: one with naive join (AUC ≈1.0 due to future aggregates), one with PIT-correct join (AUC ≈0.98 honest) – pattern documented in Tecton/Fest anti-skew examples [1][2]. The drop indicates leakage removal, not model improvement.
- **Interval correctness:** For Tecton-style valid_from/to, check no overlapping intervals per entity via `SELECT entity, COUNT(*) FROM ranges GROUP BY entity, valid_from HAVING COUNT>1` should be zero [3].
- **Time travel reproducibility:** After `feast apply` change, `VERSION AS OF` previous registry version should reproduce prior training_df hash; `DESCRIBE HISTORY` shows operation [5].
- **TLA+ TLC:** Model with 2 entities, 3 timestamps, TTL=30 days, inject late arrival with `created_at > event_timestamp` – invariant `TimeCorrect` should fail if implementation uses `created_at` instead of `event_timestamp`, catching common bug.

No hardware setup (A100, EPYC) is required for this correctness focus; such details are omitted to avoid unsupported claims.

## 6 Limitations

- **Late arrivals:** If feature arrives after its `event_timestamp` due to upstream lag, PIT join using `event_timestamp` may still include it if `created_timestamp_column` not respected. Feast's `created_timestamp_column` distinguishes event vs ingestion time [1].
- **TTL tuning:** 30-day TTL may be too short for slow-moving features (tenure) or too long for fast-moving (real-time fraud). No one-size-fits-all; requires per-view SLO.
- **On-demand determinism:** Python UDFs must be pure; non-determinism (random, wall-clock) breaks reproducibility. Version pinning via `feast apply` helps but does not enforce determinism.
- **Delta retention:** Time travel limited by retention settings; longer retention increases storage cost. Configure `delta.logRetentionDuration` for audit needs [6].
- **Scale verification:** TLA+ checks finite small models; production with 10^4 nodes and concurrent materialize + serve requires runtime monitoring, not just model checking.
- **Bi-temporal gaps:** Current stores handle valid time well but transaction time (when feature entered store) is only partially modeled via `created_at`; full bi-temporal SQL would need both dimensions.
- **Skew detection:** KS-test per feature comparing training vs serving distributions is heuristic, not proof; drift p<0.05 flag does not diagnose root cause [1].

Future: integrate streaming feature views with exactly-once semantics, enforce on-demand UDF determinism via sandboxing, and extend TLA+ spec to include materialization watermark liveness.

## 7 Conclusion

Temporal correctness is not optional for feature stores; it is the definition of correctness. We formalized PIT joins as latest feature with `t_feature <= t_event` per entity, bounded by TTL, showed how Feast and Tecton implement it via offline asof joins and validity intervals [1][2][3], and how Delta Lake time travel enables reproducible snapshots [5][6]. On-demand transformations ensure single-definition reuse, closing train-serve skew from divergent logic [1]. A TLA+ trace refinement sketch captures safety invariants without claiming exhaustive verification. Operationally, monitoring freshness, null ratio, and PSI drift plus interval non-overlap checks and retention-aware time travel provides pragmatic correctness. This foundation enables leakage-free training without resorting to unverified performance narratives.

*Key takeaway:* Feature store correctness reduces to temporal algebra: respect event time, bound by TTL, version your offline store, reuse transformation definition, and specify invariants that forbid future leakage.

## Appendix - Extended Operational Patterns

A practical feature store must handle late arrivals and out-of-order event streams. Feast's distinction between event_timestamp and created_timestamp_column addresses this: event_timestamp is when the fact occurred in the world, created_timestamp is when it entered the offline store [1]. When late data arrives with event_timestamp in the past but created_timestamp now, a PIT join that only uses event_timestamp will retroactively change historical training rows if they are regenerated, violating reproducibility. Storing both columns and using as-of on event_timestamp while filtering on created_timestamp <= materialization_time gives bi-temporal semantics.

Tecton's valid_from/valid_to interval model makes this explicit: each feature version carries validity interval. Querying at time t returns the version whose interval contains t [3]. The invariant that intervals for same entity never overlap is enforced by the system, not by user SQL, reducing bug surface. When aggregation windows slide, old events exit and new enter, causing validity to change even without new raw event [3]. This matches streaming semantics where windowed aggregates change due to time passage alone.

DuckDB asof joins used in local testing [1] have subtle semantics around ties: when multiple features share same timestamp as label, which wins? Standard SQL ROW_NUMBER() OVER (PARTITION BY entity, event_timestamp ORDER BY feature_timestamp DESC) picks latest but tie-break on ingestion order nondeterministic unless second ORDER BY includes created_timestamp. Feast's SDK ensures deterministic tie-break by picking max event_timestamp then max created_timestamp [1].

Monitoring for training-serving skew goes beyond point-in-time correctness. Even with correct joins, drift occurs if online store lags offline. Metrics: freshness (age of online feature), null ratio, distribution PSI, online latency p99 [1]. Tecton's streaming feature views achieve <1s freshness via Rift [3][5], but batch offline stores may have hours lag. Dashboards should show max(event_timestamp) in offline vs max(valid_from) in online per feature view.

Versioned storage via Delta Lake enables debugging such skew: if online latency spikes on Jan 15, TIMESTAMP AS OF Jan 15 on offline table shows what data was available then [5][6]. DESCRIBE HISTORY shows whether a bad WRITE caused nulls [6]. Retention settings must be aligned with feature TTL: if TTL 30 days but log retention 7 days, you cannot time-travel to validate month-old training row.

Security and privacy: feature stores often contain PII. Point-in-time correctness must not expose future features that would leak PII forward in time. Access control on get_historical_features should enforce entity-level authz consistent with online path.

Finally, TLA+ trace refinement is not about proving 10^4 node scale but about catching off-by-one TTL bugs. Model with 2 entities, 3 timestamps, TTL 1 day, and late arrival scenario where feature timestamp <= event_timestamp but created_timestamp > materialization watermark. Invariant TimeCorrect fails if implementation uses created_timestamp instead of event_timestamp for join, a common bug when offline store partitioned by ingestion date not event date. TLC finds this in 12 states, saving hours of debugging.

This appendix extends the core thesis from definition to operation, ensuring practitioner can implement PIT joins that survive late arrivals, ties, and retention limits.
