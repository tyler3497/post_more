# Deterministic Simulation and Layered Transaction Processing in FoundationDB: An Ordered Key-Value Store Architecture for Strict Serializability at Scale

## Abstract

FoundationDB is an ordered, distributed key-value store that combines the scalability of NoSQL systems with full ACID transactions and strict serializability. Its distinguishing design decisions are twofold: an *unbundled architecture* that decomposes transaction processing into a control plane, a stateless distributed transaction system, a write-ahead log system, and a storage system — each scaled independently — and a *deterministic simulation testing framework* that collapses an entire multi-machine cluster into a single-threaded process with virtual time, a seeded pseudorandom number generator, and pervasive fault injection. This thesis provides a systematic treatment of both. We trace the end-to-end transaction protocol from read-version acquisition through optimistic conflict detection over multi-versioned state, formalize the serializability argument in terms of commit-version ordering, dissect the Flow actor-model framework that makes simulation possible, and analyze the economics of the BUGGIFY fault-injection discipline that allowed the project to find and fix concurrency defects that would otherwise have required years of production exposure to manifest [1][2][5].

## 1. Introduction

The distributed systems literature of the past two decades documents a persistent tension between *scalability* and *correctness*. NoSQL systems achieved horizontal scale by relaxing transactional guarantees, exposing application developers to anomalies — lost updates, phantom reads, write skew — that are notoriously difficult to reason about. Traditional relational engines preserved strict serializability but resisted distribution, or distributed it only with quorum protocols whose resource cost (replicating data to *2f + 1* nodes to tolerate *f* failures) and operational complexity limited adoption.

FoundationDB, developed originally at FoundationDB Inc., acquired by Apple in 2015, and later open-sourced under the Apache 2.0 license, occupies a distinctive point in this design space. It is an *ordered* key-value store — keys are byte strings totally ordered lexicographically, supporting efficient range scans — with a transactional API offering strict serializable ACID transactions [1][4][7]. The system is described in "FoundationDB: A Distributed Unbundled Transactional Key Value Store" (Zhou et al., SIGMOD 2021), which makes three primary contributions: the open-source system itself, combining NoSQL and ACID and used in production at Apple, Snowflake, and other organizations; an integrated deterministic simulation framework that makes the system among the most stable of its kind; and the architectural lessons distilled from building it [1][5].

This thesis examines FoundationDB through two lenses mirroring the paper's contributions: the *layered transaction architecture* — how versioning, conflict detection, durability, and storage are decomposed into independently scalable roles, with OCC over MVCC yielding strict serializability without distributed locking — and *deterministic simulation testing* — how Flow's complete mediation of I/O lets an entire cluster run deterministically in one thread, and how BUGGIFY fault injection converts rare edge cases into routinely exercised code paths.

> **Theorem (Transaction total order):** Every committed FoundationDB transaction is serializable in the total order of its assigned commit versions, and that order is consistent with real time (strict serializability). A transaction reading at read version *r* observes exactly the writes of all transactions with commit version ≤ *r*.

The remainder of this thesis is organized as follows. Section 2 situates FoundationDB among related concurrency-control and testing techniques. Section 3 describes our analytical methodology. Section 4 presents the deep technical analysis: the unbundled architecture, OCC/MVCC transaction processing, the Flow actor model, and deterministic simulation. Section 5 develops the serializability argument and summarizes reported empirical behavior. Section 6 discusses limitations and open questions. Section 7 concludes.

## 2. Background

### 2.1 The NoSQL–ACID Divide

Early distributed key-value stores (e.g., Dynamo, Cassandra, Bigtable) scaled by weakening consistency: last-writer-wins, eventual convergence, or single-key atomicity. These designs are operationally simple but push correctness burdens onto application developers, who must implement compensation logic for anomalies the database cannot prevent. FoundationDB's central bet is that a carefully decomposed architecture can deliver both scale *and* strict serializability [1].

### 2.2 Optimistic vs. Pessimistic Concurrency Control

Concurrency control schemes divide broadly into pessimistic approaches (two-phase locking, which blocks transactions to prevent conflicts) and optimistic approaches, which allow transactions to proceed without locks and validate them at commit time, aborting on conflict [1]. OCC suits low-contention OLTP workloads — FoundationDB's target domain of small read/write sets — because the common case proceeds with no coordination overhead and aborts are rare [1]. FoundationDB couples OCC with MVCC so read-only transactions never abort or block writers: reads observe a consistent snapshot at a read version, while conflict detection guards only read-write transactions [1][5].

### 2.3 Actor Models for Concurrent Systems

The actor model structures concurrent computation as isolated entities communicating exclusively through asynchronous messages. FoundationDB's **Flow** framework is an actor-based asynchronous programming framework for C++ in which long-running computations are expressed as `ACTOR` functions that `wait()` on futures, yielding control to a cooperative scheduler [3][6]. Flow is not merely a stylistic choice: it is the mechanism that makes deterministic simulation possible, because every blocking point in the system — network I/O, disk I/O, timers — is mediated by the Flow runtime and can therefore be replaced by a simulated implementation [2][3][6].

### 2.4 Testing Distributed Systems

Conventional testing of distributed systems relies on integration clusters, chaos experiments, and luck: rare interleavings of failures may require years of production traffic to manifest. *Deterministic simulation testing* (DST) addresses this by collapsing the entire distributed system into a single-threaded simulation where all sources of nondeterminism — network, disk, time, randomness — are controlled by a seeded PRNG, so that the same seed reproduces the identical execution and any discovered bug is perfectly replayable [2][6][8]. FoundationDB pioneered this technique for databases; its founding team later generalized it commercially as Antithesis [4][8].

## 3. Methodology

Our analysis follows a protocol-tracing methodology:

1. **Architectural decomposition.** We enumerate the process roles of the control and data planes from the SIGMOD 2021 paper and the project's design documentation, and assign each responsibility (versioning, routing, conflict detection, durability, serving reads) to its owning role [1][7].
2. **Transaction lifecycle trace.** We walk a transaction end-to-end — read-version acquisition, snapshot reads, client-side write buffering, commit submission, version assignment, conflict checking, log replication, and storage application — identifying the invariant maintained at each step [1][5].
3. **Concurrency-control formalization.** We reconstruct the serializability argument from the conflict-detection algorithm's specification: read-set/write-set range comparison against a bounded history of committed transactions indexed by commit version [1].
4. **Framework analysis.** We examine the Flow actor model's scheduling discipline and the Sim2 deterministic simulator's mediation of I/O, timers, and randomness, together with the BUGGIFY fault-injection design, drawing on project documentation and secondary technical analyses [2][3][6].
5. **Source triangulation.** Every substantive claim is cross-checked against the peer-reviewed paper, official project documentation, or independent technical write-ups [1][2][3][4][5][6][7][8].

## 4. Deep Dive

### 4.1 The Unbundled Architecture: Control Plane and Data Plane

FoundationDB's guiding principle is *divide and conquer*, also described as separation of concerns: the transaction management system (write path) is decoupled from distributed storage (read path), and each is scaled independently by adding processes of the appropriate role [1][5]. The cluster is organized into a **control plane** and a **data plane**.

**Control plane.** The control plane persists cluster metadata and performs orchestration. *Coordinators* form a disk Paxos group (Active Disk Paxos) and elect a singleton *ClusterController*, which recruits three singletons: the **Sequencer** (assigns read/commit versions), the **DataDistributor** (failure monitoring and rebalancing), and the **Ratekeeper** (overload protection) [1][5]. Coordinators do not participate in transaction processing [7].

**Data plane.** The data plane contains the transaction system (TS), the log system (LS), and the storage system (SS):

| Role | System | Responsibility |
|---|---|---|
| Sequencer | TS | Assigns read versions and commit versions; recruits proxies, resolvers, log servers |
| Proxies | TS | Serve MVCC read versions to clients; orchestrate commits |
| Resolvers | TS | Detect conflicts between transactions using recent commit history |
| LogServers | LS | Replicated, sharded persistent queues storing write-ahead log data per storage server |
| StorageServers | SS | Store key-range shards; serve reads; form a distributed B-tree |

The TS processes — Sequencer, Proxies, Resolvers — are *stateless*, performing all transaction processing in memory. The LS stores the write-ahead log durably, and the SS stores data and serves reads [1][5]. This unbundling is what makes failure handling economical: rather than masking failures with quorums, FoundationDB eagerly detects failures and recovers by reconfiguring the system, achieving *f*-failure tolerance with only *f + 1* replicas instead of the *2f + 1* required by quorum schemes [1].

> **Theorem (Resource-efficient fault tolerance):** Because transaction-system state is either stateless (TS) or recoverable from the log (LS/SS), FoundationDB reconfigures around failed processes instead of voting through them, tolerating *f* failures with *f + 1* replicas — strictly fewer resources than quorum-based designs requiring *2f + 1* [1].

Each StorageServer owns a set of contiguous key-range shards, and together the storage servers form a distributed B-tree. The per-server storage engine is a modified SQLite enhanced for faster range clears, deferred background deletion, and asynchronous programming — chosen partly because simulation requires every component to run in a single thread, precluding engines needing thread pools for synchronous I/O [5]. A multi-version B-tree engine, **Redwood**, is the successor design, with RocksDB support in later releases [7].

### 4.2 OCC over MVCC: The Transaction Protocol

FoundationDB achieves strict serializability through a combination of optimistic concurrency control and multi-version concurrency control [1]. The end-to-end transaction lifecycle proceeds as follows:

1. **Read-version acquisition.** The client contacts a Proxy, which asks the Sequencer for a read version guaranteed to be no less than any previously issued commit version. Proxies batch these requests to amortize cost [1][5].
2. **Snapshot reads.** The client reads from StorageServers *at that specific read version*. Multi-versioned storage means reads never block and read-only transactions never abort; recent versions (under ~5 seconds old) are kept in memory, older ones on disk [1][7].
3. **Client-side write buffering.** Writes are buffered locally in the client without contacting the cluster [1][5].
4. **Commit submission.** At commit time the client sends the transaction's *read set* and *write set* — expressed as key ranges, with a single key converted to a degenerate range — to a Proxy [1].
5. **Commit-version assignment.** The Proxy obtains a commit version from the Sequencer. Crucially, unlike write-snapshot isolation, FoundationDB assigns the commit version *before* conflict detection, which permits efficient batch processing of both version assignment and conflict checking [1].
6. **Conflict detection.** Resolvers check the transaction's read set against write sets of recently committed transactions. Each Resolver keeps a history of recently modified key ranges — the last five seconds of commits — indexed by commit version in a version-augmented probabilistic skip list [1][7]. Read-write conflicts abort; snapshot reads are excluded from the read set and never cause conflicts [1].
7. **Durable logging.** Admitted transactions are sent to LogServers, which persist the write-ahead log to disk. Each log queue is sharded per storage server [1][5].
8. **Storage application.** StorageServers pull log data from LogServers in increasing log sequence numbers and apply committed mutations, advancing the versioned state that serves reads [1].

The following pseudocode sketches the resolver's conflict-detection core (after Algorithm 1 of the paper [1]):

```python
# Resolver state: version-augmented history of committed write ranges
# history: SkipList keyed by (commit_version), values = modified key ranges

def check_commit(txn, commit_version, history, window):
    # 1-5: check read set against concurrent committed writes
    for r in txn.read_ranges:                       # snapshot reads excluded
        for (cv, w) in history.since(txn.read_version):
            if cv <= commit_version and overlaps(r, w):
                return ABORT                       # read-write conflict
    # 6-7: admit and record the write set
    history.insert(commit_version, txn.write_ranges)
    history.evict_older_than(commit_version - window)
    return COMMIT
```

Because the read version lower-bounds all previously committed transactions and the resolver rejects any transaction whose reads overlap a concurrent committed write, committed transactions are equivalent to execution in commit-version order — the classic OCC argument, strengthened to *strict* serializability by the real-time-consistent sequencer [1].

### 4.3 The Flow Actor Model

All of FoundationDB's server and client logic is written in **Flow**, an actor-based asynchronous framework embedded in C++. An actor is a function that returns a `Future` and uses `wait()` to suspend until an asynchronous result is ready, at which point the cooperative scheduler resumes it [3][6]:

```cpp
ACTOR Future<Optional<Value>> readWithRetry(Database db, Key key) {
    state Transaction tr(db);
    loop {
        try {
            // Every wait() is a scheduling point the simulator can intercept
            wait(tr.onError(success()));       // placeholder: begin txn
            Optional<Value> v = wait(tr.get(key));
            wait(tr.commit());
            return v;
        } catch (Error& e) {
            wait(tr.onError(e));               // retry with backoff
        }
    }
}
```

Three properties make Flow load-bearing for correctness:

- **Total mediation of blocking.** Every network send, disk read, timer, and random draw passes through the Flow runtime's `INetwork` interface: the same source code runs in production against `Net2` (real sockets, real clock) and in testing against `Sim2` [2][6].
- **Cooperative, single-threaded scheduling.** Actors run until their next `wait()`; the entire simulated cluster executes in one OS thread, eliminating thread races by construction within the simulation boundary [2][6].
- **Deterministic randomness.** All randomness flows from a seeded PRNG: same seed and binary produce identical interleavings, fault timings, and outcomes [2][6].

The Flow discipline also explains a stark engineering decision: components that cannot live inside the determinism boundary must be *replaced*, not mocked. Fault injection found two independent ZooKeeper bugs circa 2010, after which ZooKeeper was deleted and coordination reimplemented as a de novo Paxos in Flow — a component outside the determinism boundary cannot be tested [8].

### 4.4 Deterministic Simulation, BUGGIFY, and the Economics of Bug-Finding

The Sim2 simulator (`fdbrpc/sim2.cpp`) replaces the network layer during tests. It instantiates a full virtual cluster — machines, datacenters, processes — in a single thread with a virtual clock: time advances through task scheduling rather than wall-clock waiting, timers fire deterministically, and a seeded PRNG drives network latency, clogging, partitions, disk I/O errors, process crashes, machine and datacenter failures [2][6]. Test workloads (~51K lines, 60+ workload types, TOML-configured) run against this simulated cluster, with thousands of seeded runs executing continuously [2].

**BUGGIFY** is the mechanism that converts rare paths into common ones. `BUGGIFY` / `BUGGIFY_WITH_PROB(p)` macros mark code sites that take unusual branches — short timeouts, extra delays, shrunk buffers, early returns, knob randomizations — and the simulator enables them probabilistically per run, with calibrated tiers (roughly 5–10% for common edge cases, ~1% for standard scenarios, down to 0.01% for rare critical failures), gated so they can never fire in production builds [2][3][6]. Each site's enablement is itself seed-deterministic, so a failing seed replays the exact fault combination [2][6]. Client libraries expose the same machinery with `client_buggify_section_activated_probability` and a default 25% firing probability for enabled sections [3].

The economic argument is stark: traditional testing samples only anticipated interleavings, while simulation with buggification *manufactures* adversarial ones continuously, and every failure ships with a reproducing seed — collapsing debugging from weeks of log archaeology to deterministic replay [4][6][8]. The FoundationDB team commercialized this generalization as **Antithesis**, which raised $47M in 2024 with customers including MongoDB, Palantir, and the Ethereum Foundation [4].

## 5. Empirical Results / Proofs

### 5.1 The Serializability Argument

We now formalize the claim sketched in Section 4.2. Let each transaction *T* carry a read version *r(T)* and, if admitted, a commit version *c(T)*, with *r(T) < c(T)* and both drawn from the Sequencer's monotonically increasing version counter.

> **Theorem (Strict serializability):** Let *H* be the history of transactions admitted by the resolvers. Then *H* is equivalent to the serial history ordered by commit version, and that order respects real-time precedence.

*Proof sketch.* Consider two committed transactions *T₁, T₂* with *c(T₁) < c(T₂)*, where *T₂*'s execution overlaps *T₁*'s commit. If *T₂* read any key written by *T₁*, then *T₁*'s write range intersects *T₂*'s read range. Since *r(T₂) < c(T₁)* (otherwise *T₂* would observe *T₁*'s write and no anomaly arises) and the resolver checks *T₂*'s read set against all committed write ranges with commit versions in *(r(T₂), c(T₂)]* — a window the five-second history is sized to cover for all in-flight transactions — the intersection is detected and *T₂* aborts. Hence every committed transaction's reads are consistent with the snapshot of all transactions committed before its read version, i.e., the history is conflict-equivalent to commit-version order. Real-time order follows because the Sequencer never issues a read version smaller than any previously issued commit version: a transaction beginning after another commits necessarily reads at a version ≥ that commit. ∎ [1]

The batching-friendly variant — assigning *c(T)* *before* conflict detection — preserves this argument because detection still ranges over *(r(T), c(T)]*, and it allows the proxy to pipeline version assignment with resolver checks [1].

### 5.2 Reported System Behavior

The SIGMOD paper's evaluation focuses on the scalability and efficiency of the unbundled components: transaction throughput scales with the number of proxies and storage servers independently, and the resolver's skip-list-based conflict detection sustains the commit path without becoming the bottleneck, validating the decision to assign commit versions ahead of conflict checks so both can be batch-processed [1]. On the testing side, the project's long-standing claim is that deterministic simulation "found all of the bugs in the database" — given weight by thousands of continuously running seeded simulations and by downstream evidence: MongoDB reported 75+ severe bugs found via Antithesis that all other testing had missed [4][8]. One caveat: the paper's simulation section (§4) is qualitative — no bug counts or coverage percentages — so quantitative efficacy claims properly cite engineering reports and adopters, not the paper itself [8].

### 5.3 The Five-Second Window as a Correctness Parameter

The resolver's five-second history window is not arbitrary: it must exceed the maximum possible duration of an in-flight transaction's commit protocol, so that every potentially conflicting committed write is still present when a late-arriving commit is checked [1][7]. This couples a performance parameter (history size, skip-list memory) to a commit-path liveness property — correctness arguments in distributed systems are quantitative, not merely logical [1].

## 6. Limitations

**Simulation measures correctness, not performance.** Virtual time severs the link to wall-clock behavior; passing simulations say nothing about throughput or tail latency, which still require physical clusters [2][6].

**The determinism boundary is porous at the edges.** Anything outside Flow's mediation — third-party libraries, kernel behavior, thread pools — cannot be simulated. Engines needing synchronous I/O thread pools were excluded for violating the single-threaded discipline, constraining storage-engine choice until coroutine support matured [5][7].

**Bounded history bounds transaction duration.** The five-second resolver window assumes no commit protocol exceeds it; long client pauses risk aborts or pressure to enlarge the window and its memory cost [1][7].

**Optimistic concurrency punishes contention.** Under high contention, abort rates climb; with no pessimistic fallback, hot-key workloads must be restructured at the application layer [1].

**Recovery is fast but not free.** Eager detection plus reconfiguration avoids quorum costs but introduces windows where the transaction system is unavailable during re-recruitment; tail latency during reconfiguration remains a deployment concern [1][5].

**Single-writer metadata paths.** The Sequencer, ClusterController, DataDistributor, and Ratekeeper are singletons: lightweight and re-recruitable, but centralized coordination points that complicate multi-region active-active topologies [1][7].

---

## 7. Conclusion

FoundationDB shows the NoSQL–ACID divide was a failure of architecture, not a law of nature. *Unbundling* transaction processing into stateless versioning, conflict detection, durable logging, and storage — each scaled independently — with OCC over multi-versioned storage and commit-version-ordered conflict detection, it delivers strict serializable transactions at NoSQL scale with *f + 1* rather than *2f + 1* replication [1]. Equally important is *how* it earned its stability reputation: Flow's total mediation of I/O makes the whole cluster simulatable in one thread with virtual time, and BUGGIFY turns rare faults into routine test events, with seed-deterministic replay collapsing debugging cost [2][3][6]. The broader lesson, commercialized in Antithesis: where correctness matters, the highest-leverage investment may be a better *world in which to break the protocol* [4][8].
