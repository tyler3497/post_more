# Time-Series Storage Engines: LSM-Tree and B-Tree Adaptations for Time-Partitioned Data, from Gorilla Compression to Out-of-Order Ingestion

## Abstract

Time-series databases sustain the densest sustained-write workload in operational computing: billions of immutable, append-mostly points that must be ingested at wire speed and scanned over arbitrary time ranges. This thesis gives a systems-level account of how modern engines reconcile write amplification, compression, index bloat, and late-arriving data. We formalize the **time-partitioned LSM** and the **chunk-bounded B-tree** as the two canonical adaptations of classical storage structures to near-monotonic time, and derive an amortized **one-bit-per-timestamp** bound for delta-of-delta encoding under constant-rate sampling. We reconstruct Facebook's Gorilla codec — delta-of-delta timestamps with variable-length prefixes and XOR-framed IEEE-754 values — and its successors Chimp and Elf, tracing how InfluxDB's Time-Structured Merge Tree, InfluxDB IOx's Arrow/Parquet redesign, TimescaleDB's hypertable chunks, ClickHouse's MergeTree parts, and Prometheus's head-block TSDB instantiate the same write path with different tradeoffs. Finally, we analyze out-of-order ingestion via bounded lateness windows, rollup and downsampling hierarchies, and retention policies as a unified lifecycle, proving that bounded-disorder buffering keeps late-data merge cost proportional to the disorder, not the dataset.

##1 Introduction

Few database workloads are as structurally exploitable as time-series telemetry. Writes arrive in near-monotonic timestamp order, are never updated in the relational sense, and are read back as **range scans over recent intervals grouped by series identity** [10]. A B-tree designed for random OLTP access spends its write bandwidth rebalancing a monolithic index; a columnar warehouse compresses well but ingests poorly. The time-series storage engine is the joint optimization of *write throughput, per-sample storage cost, and windowed read latency* that no general engine achieves.

This thesis argues that every production time-series engine varies two themes. First, the **write-optimized frontier**: an LSM-tree derivative with memtable, WAL, and leveled compactions aligned to the time axis — InfluxDB's Time-Structured Merge Tree (TSM) [4], Prometheus's WAL/head-block/compaction pipeline [9], and InfluxDB IOx's Arrow-native object-store engine [5]. Second, the **read-optimized frontier**: classical B-tree or sorted-part machinery, *time-partitioned* so each index's working set fits in memory — TimescaleDB's hypertable chunks [6][7] and ClickHouse's MergeTree parts with sparse primary indexes [8].

On top of these substrates sits a compression layer that has converged on one family of ideas. Facebook's Gorilla (Pelkonen et al., VLDB 2015) [1] showed that physical sensors and software counters carry two exploitable regularities: timestamps advance at near-constant deltas, and consecutive IEEE-754 values share most of their bits. Gorilla's **delta-of-delta** timestamp encoding and **XOR-framed** float encoding reach roughly **1.37 bytes per sample — a ~12× reduction over the naive 16-byte (timestamp, double) layout** — with 96% of timestamp deltas collapsing to a single bit [2]. Its successors, Chimp [3] and Elf, refine the same bit budget.

The remaining challenge is the *lifecycle*: data arrives late, queries need pre-aggregated rollups, and old data must expire. We examine **out-of-order ingestion** under bounded lateness (Prometheus's `out_of_order_time_window` [11], Mimir, InfluxDB's active-shard tolerance, TimescaleDB's chunk-local late writes with continuous-aggregate invalidation), **rollup/downsampling hierarchies** (Thanos-style 5-minute/1-hour blocks, TimescaleDB continuous aggregates, ClickHouse materialized views), and **retention policies** implemented as *partition drops* rather than row deletes — because in a time-partitioned engine, deletion should be metadata work, not I/O work.

##2 Background

### 2.1 The workload shape

A time-series database stores a set of *series*, each identified by a unique key — a string in Gorilla [1], a measurement-plus-tag-set in InfluxDB, a `(metric, label-set)` hash in Prometheus — as $(t_i, v_i)$ sequences. Four properties dominate engine design:

1. **Append-mostly, monotone-time arrival.** Points are written once; corrections and late points are the exception.
2. **Time-ordered reads.** Queries request windows $[t_a, t_b]$ far more often than point lookups.
3. **High write rate, moderate read rate.** Single nodes sustain millions of samples per second [9].
4. **Cardinality as the scaling ceiling.** The number of distinct series bounds memory more tightly than raw point volume — the per-series index is engineered before the byte-per-point budget.

### 2.2 The classical structures: LSM-tree and B-tree

The **log-structured merge-tree** (O'Neil, Cheng, Gawlick, O'Neil, 1996) [12] converts random writes into sequential ones: inserts land in an in-memory memtable, are persisted to a write-ahead log, and flush as immutable sorted files; background **compactions** merge files across levels. Its virtue is *burst absorption*: write amplification bounded by the level fan-out.

The **B-tree** instead offers read-efficient in-place updates, but its pages fragment under append-heavy, high-cardinality insertion: every series' points scatter across the tree and each insertion touches a random leaf. This "B-tree index bloat" under telemetry rates is the explicit motivation TimescaleDB cites for chunking [6].

The time-series insight is that *time itself is a partitioning function*: splitting either structure along the time axis confines the hot working set to one small, recent, memory-resident partition while cold partitions stay immutable and compressible.

### 2.3 Partitioning as a primitive

Time partitioning appears in every engine under different names — InfluxDB **shards**, TimescaleDB **chunks**, ClickHouse **parts/partitions**, Prometheus **blocks** — with three obligations:

- **Exclusion**: a range query skips partitions whose time bounds cannot intersect it (chunk exclusion [7], partition pruning [8], block min/max filtering [9]).
- **Immutable cold storage**: sealed partitions never change, enabling aggressive compression and trivial retention.
- **Bounded hot index**: only the active partition's index grows during ingestion, so B-tree thrashing is confined (TimescaleDB's rule: active chunks' indexes within ~25% of RAM [7]).

##3 Methodology

Our analysis proceeds along three axes. **First**, the codecs — delta-of-delta, XOR framing, successors — and their asymptotic bit costs. **Second**, five engines (InfluxDB TSM, IOx, TimescaleDB, ClickHouse, Prometheus) on a common grid: write path, index, partitioning, codec, out-of-order policy, rollup, retention. **Third**, the lifecycle — late data, downsampling, expiry — as a scheduling problem on the partitioned substrate, with write-amplification bounds for bounded-disorder ingestion.

> **Theorem:** (Single-bit amortized timestamps.) For a series with perfectly regular sampling $t_{i+1} - t_i = \Delta$ for all $i$, Gorilla's delta-of-delta timestamp encoding stores each timestamp for $i \ge 3$ in exactly one bit. The amortized cost is $1 + 64/n$ bits per timestamp over $n$ samples.

*Proof sketch.* With $t_1$ as the 64-bit block header and $t_2$ as a full delta, all subsequent delta-of-deltas are $0$, encoded as the single bit `0` [1]: $64 + 64 + (n-2)$ bits over $n$ points, i.e. $1 + 64/n$ amortized. ∎

The theorem explains Gorilla's empirical 96%-of-deltas-at-one-bit result [2]: the farther sampling deviates from regularity, the wider the prefix buckets and the higher the per-point cost.

##4 Deep Dive

### 4.1 Gorilla and its descendants: the bit budget of a time series

Facebook's Gorilla (Pelkonen et al., VLDB 2015) [1] exploits two regularities of physical telemetry: timestamps advance at near-constant deltas, and consecutive IEEE-754 values share most bits. Its encoding splits the stream into two bitstreams. **Timestamps** use delta-of-delta against the previous delta with the prefix table above. **Values** XOR each double with its predecessor: all-zero costs one `0` bit; otherwise `1` plus the meaningful middle bits — reusing the previous leading/trailing-zero window when they fit, else emitting a new 6-bit leading-zero count and 6-bit length:

| `dod` range | Prefix | Payload | Total bits |
|---|---|---|---|
| `0` | `0` | — | 1 |
| `[-63, 64]` | `10` | 7 bits | 9 |
| `[-255, 256]` | `110` | 9 bits | 12 |
| `[-2047, 2048]` | `1110` | 12 bits | 16 |
| else | `1111` | 64 bits | 68 |

A walkthrough (ten timestamps and values, 48 bytes raw → 21 bytes) shows how aggressively the scheme exploits regularity [13].

Two successors refine the XOR half. **Chimp** (Liakos et al., PVLDB 2022) [3] keeps a 128-value history ring, hashed by trailing bits, so each point XORs against the most similar candidate — better ratio than Gorilla, still single-pass with $O(1)$ state. **Elf** (Li et al., PVLDB 2023) erases insignificant mantissa bits of monitoring floats to manufacture trailing-zero runs for XOR encoding to devour.

Reference implementation of both halves:

```python
import struct

def _bits(x: int, n: int) -> str:                      # n-bit two's-complement field
    return format(x & ((1 << n) - 1), f'0{n}b')

def encode_timestamps(ts: list[int]) -> str:           # Gorilla delta-of-delta
    out = _bits(ts[0], 64) + _bits(ts[1] - ts[0], 64)  # header + first delta
    prev_delta = ts[1] - ts[0]
    for i in range(2, len(ts)):
        delta = ts[i] - ts[i - 1]
        dod = delta - prev_delta
        prev_delta = delta
        if dod == 0:            out += '0'
        elif -63 <= dod <= 64:  out += '10' + _bits(dod, 7)
        elif -255 <= dod <= 256: out += '110' + _bits(dod, 9)
        elif -2047 <= dod <= 2048: out += '1110' + _bits(dod, 12)
        else:                   out += '1111' + _bits(dod, 64)
    return out

def encode_values(vals: list[float]) -> str:          # Gorilla XOR floats
    def as_u64(f): return struct.unpack('>Q', struct.pack('>d', f))[0]
    prev, out = as_u64(vals[0]), _bits(as_u64(vals[0]), 64)
    lz = tz = 0
    for v in vals[1:]:
        cur, xor = as_u64(v), prev ^ as_u64(v)
        prev = cur
        if xor == 0:
            out += '0'; continue
        nlz, ntz = 64 - xor.bit_length(), (xor & -xor).bit_length() - 1
        mean = 64 - nlz - ntz
        if lz <= nlz and tz <= ntz and mean <= 64 - lz - tz:
            out += '10' + _bits(xor >> tz, 64 - lz - tz)      # reuse window
        else:
            lz, tz = nlz, ntz
            out += '11' + _bits(nlz, 6) + _bits(mean, 6) + _bits(xor >> ntz, mean)
    return out
```

Decoding mirrors encoding: maintain the running delta and reconstruct each value as `prev ^ bits` [1]. The encoder is *causal* — no lookahead — so mid-stream inserts break the chain, which is why Section 4.5's out-of-order machinery exists.

### 4.2 InfluxDB: the Time-Structured Merge Tree and the IOx rewrite

InfluxDB's original engine is the **Time-Structured Merge Tree (TSM)**, an LSM-tree keyed on `(series, time)` [4]:

1. Writes append to the current WAL segment and enter an in-memory **Cache**; on pressure, the **Compactor** snapshots it into an immutable **TSM file** — all points of a series contiguous — after `fsync`.
2. Compaction runs through levels up to **Full (level 4)** compactions when a shard goes cold.

Updates shadow at query time (newer wins); deletes write **tombstone files** per TSM file, purged by compaction [4]. The **TSI index** is itself an LSM index over series keys: WAL-backed LogFile compacts into leveled IndexFiles, with a global SeriesFile assigning series IDs [14]. Data is time-partitioned into **shards**, the unit of compaction and retention.

**InfluxDB IOx** is the successor: a Rust engine on **Apache Arrow** (in-memory columnar), **DataFusion** (query), and **Parquet in object storage** [5]. IOx keeps the LSM control plane — buffering, immutable files, compaction — but separates storage from compute. The lesson: the LSM *control plane* survives the columnar transition; only the file format and durability layer change.

### 4.3 TimescaleDB: B-trees, right-sized by time

TimescaleDB takes the opposite starting point — full PostgreSQL with its B-tree heap — and partitions it. A **hypertable** is transparently split into **chunks**, each an ordinary PostgreSQL child table over a disjoint time interval (default 7 days) plus optional hash space partitioning [6][7]:

- **Ingest stays memory-resident.** Appends to "now" touch only hot pages of the active chunk; no global index thrashes.
- **Queries prune by exclusion.** The planner eliminates chunks whose time bounds cannot match — `O(1)` in window size regardless of total history [6].
- **Retention is DDL.** Expiring data drops whole chunk tables instead of deleting rows, sidestepping vacuuming [6].

For the cold side, TimescaleDB folds row-oriented chunks into **columnar compressed form**: wide rows become single rows whose columns hold ordered arrays, with `segmentby`/`orderby` controlling the grouping that makes per-column codecs effective; compression and retention run as background policies [7].

### 4.4 ClickHouse MergeTree and Prometheus TSDB: sorted parts at the extremes

**ClickHouse**'s `MergeTree` family stores each insert batch as an immutable **part**: per-column compressed `.bin` files, a sparse `primary.idx` recording the sorting key every `index_granularity` (default 8192) rows, and `.mrk2` marks mapping index entries to file offsets [8]. With `PARTITION BY toYYYYMM(t)` and `ORDER BY (t, ...)`, range queries touch only matching partitions and binary-search the tiny in-memory sparse index — the same exclusion/immutability contract as TSM and hypertables, over sorted columnar files with background same-partition merges. Retention is expressed as `TTL` expressions; ClickHouse even ships **DoubleDelta** and **Gorilla** column codecs.

**Prometheus**'s TSDB is the minimalist endpoint: samples accumulate in an in-memory **head block** as Gorilla-derived XOR chunks (default 120 samples, with a delta-varint fast path for integers [9]), the head flushes to immutable **2-hour blocks**, and background compaction merges them upward. Retention is block-granular (`--storage.tsdb.retention.time`) [9]. At ~1.3 bytes/sample, a million 15-second series costs ~7.5 GB/day — the arithmetic that makes 15-day single-node retention on an SSD plausible [9].

| Engine | Write path | Index | Partition unit | Retention |
|---|---|---|---|---|
| InfluxDB TSM | WAL → cache → TSM files | TSI (LSM) | Shard (time) | Drop shards |
| InfluxDB IOx | Buffer → Parquet in object store | DataFusion/Arrow | Parquet file sets | Object lifecycle |
| TimescaleDB | B-tree inserts per chunk | Per-chunk B-trees | Chunk (time × hash) | `drop_chunks` |
| ClickHouse | Insert → part | Sparse primary.idx | Partition (e.g. month) | TTL on parts |
| Prometheus | WAL → head chunks → blocks | In-block inverted index | Block (2h) | Block deletion |

### 4.5 Out-of-order ingestion: bounded disorder

Real pipelines reorder data — retries, batched collectors, clock skew — and every codec in Section 4.1 assumes monotone time. Engines therefore isolate disorder in a bounded buffer and reconcile it at compaction.

- **Prometheus** (v2.39+) accepts samples within `out_of_order_time_window` (30 minutes is the documented sweet spot [11]) into a separate **OOO head** with its own Write-Behind Log, merged with ordered chunks at compaction; older samples are rejected.
- **Mimir / Cortex** expose the same per-tenant window to multi-tenant remote-write [15].
- **InfluxDB's TSM** absorbs out-of-order writes *within the active shard* via the cache merge; only cold compacted shards pay [4].
- **TimescaleDB** writes late points into the chunk owning their timestamp, but repairs invalidated continuous aggregates from an **invalidation log** instead of recomputing wholesale [15].
- **VictoriaMetrics** deduplicates HA collector pairs at ingest with `-dedup.minScrapeInterval` [16].

> **Theorem:** (Bounded-disorder merge cost.) With lateness bound $\tau$, buffering late points in an isolated OOO head and merging at compaction costs $O(\tau \cdot r)$ buffer memory ($r$ = per-series arrival rate) and merge work touching only the blocks the window overlaps — independent of total dataset size $N$.

*Proof sketch.* The buffer holds only points in $(t_{\max} - \tau, t_{\max}]$ — at most $\tau \cdot r$ per series — and merge touches exactly the blocks intersecting the window, a constant for fixed $\tau$; no block outside the window is read or rewritten. ∎

The theorem justifies the industry-wide convergence on *explicit lateness windows*: disorder costs bounded memory and localized rewrites, never a full re-sort.

### 4.6 Rollups, downsampling, and retention: the lifecycle algebra

Raw resolution is unaffordable forever, so engines build **rollup hierarchies**: pre-aggregated series at coarser granularity. *Eager materialization* (Thanos 5-minute/1-hour downsampled blocks; TimescaleDB continuous aggregates; ClickHouse materialized views) pays write amplification once to make long-range queries cheap. *Lazy computation* (Prometheus recording rules, IOx's DataFusion pushdown) pays at query time but stores no second copy. The subtle case is continuous aggregates: late data arriving after a bucket was materialized forces recomputation, so TimescaleDB keeps an **invalidation log** and recomputes only dirty buckets — $O(\text{dirty buckets})$, not $O(\text{history})$ [15].

**Retention** closes the lifecycle and is uniformly *partition metadata work*: drop expired shards/chunks/blocks, never delete rows [4][6][8][9]. If the partition function aligns with the retention predicate, expiry is $O(1)$ I/O; otherwise it degenerates into a rewrite. The lifecycle algebra in Haskell:

```haskell
-- retention: partition-level, never row-level.
data Partition p = Partition { timeRange :: (Int, Int), payload :: p }

expire :: Int -> [Partition p] -> ([Partition p], [Partition p])
expire cutoff = partition (\p -> snd (timeRange p) < cutoff)
-- dropping is O(#partitions) metadata work.

-- rollup: monotone aggregation over aligned buckets.
rollup :: (a -> a -> a) -> Int -> [(Int, a)] -> [(Int, a)]
rollup f width pts = map aggregate (buckets pts)
  where bucket (t, _) = t `div` width
        buckets = groupBy (\a b -> bucket a == bucket b) . sortOn bucket
        aggregate g = (bucket (head g) * width, foldl1 f (map snd g))
```

##5 Empirical Results / Formal Proofs

Quantitative claims, each traceable to its source.

| Codec / system | Reported density | Reduction vs 16 B raw | Notes |
|---|---|---|---|
| Gorilla (Facebook production) | **~1.37 B/sample** | ~12× | 96% of timestamp DoDs = 1 bit [2] |
| Gorilla (pedagogical trace) | 2.1 B/sample | ~7.6× | 48 B raw → 21 B over 10 points [13] |
| Prometheus XOR chunks | **~1.3 B/sample** | ~12× | 7.5 GB/day per 1M series @15s [9] |
| Chimp / Elf | strictly better than Gorilla | — | 128-value history ring; mantissa erasure [3] |

*Worked example — retention sizing.* The Prometheus figure gives $10^6$ series $\times$ 1 sample/15 s $\times$ 1.3 B/sample $\times$ 86400 s/day $\approx$ 7.5 GB/day [9]; fifteen days is $\approx$ 112 GB — a single SSD — versus $\approx$ 1.3 TB uncompressed. *Compression is what makes retention a policy choice rather than a hardware constraint.*

The `Accept` predicate admits exactly the lateness window; `Compact` merges the buffer into overlapping blocks without ever mutating a sealed one:

```tla
---- MODULE OOOIngest ----
EXTENDS Naturals
CONSTANTS Tau
VARIABLES head, oooHead, blocks, tmax   \* ordered chunks, OOO buffer, sealed blocks

Accept(t) == t >= tmax - Tau            \* bounded lateness admission

Ingest(t, v) ==
  \/ /\ t >= tmax                       \* in-order: append to head
     /\ head' = Append(head, <<t, v>>)
     /\ tmax' = t /\ UNCHANGED <<oooHead, blocks>>
  \/ /\ Accept(t) /\ t < tmax           \* late but admissible: OOO buffer
     /\ oooHead' = Append(oooHead, <<t, v>>)
     /\ UNCHANGED <<head, blocks, tmax>>

Compact ==  \* merge buffer into overlapping blocks; sealed blocks never mutated
  /\ blocks' = Merge(head, oooHead, blocks)
  /\ oooHead' = <<>> /\ head' = <<>>
  /\ UNCHANGED tmax
====
```

##6 Limitations

1. **Gorilla's causality is its cage.** The forward-chained bitstream needs decoding from the block start for random access, and mid-stream inserts invalidate the tail — the root cause of the OOO machinery in Section 4.5. Chimp inherits this.
2. **Elf is lossy in spirit.** Erasing mantissa bits is only "lossless" under a declared precision contract; for billing-grade or scientific data the erased bits may be the signal.
3. **Time partitioning assumes temporal locality of queries.** Ad-hoc full-history scans defeat exclusion and degenerate into full scans — where columnar warehouses still win.
4. **Continuous aggregates trade correctness labor for speed.** Every rollup hierarchy must solve late-data invalidation; the invalidation log is a second write path.
5. **Cardinality remains the hard ceiling.** No codec compresses the per-series index entry; million-series workloads are bounded by index memory long before the point stream becomes the bottleneck [14].

##7 Conclusion

The time-series storage engine is the joint solution to a specific optimization problem — *absorb monotone writes at wire speed, compress each point to a few bits, answer windowed queries by touching only the partitions they name, and expire the past with metadata operations.* The field has converged: an LSM-style write path (WAL, in-memory head, immutable time-partitioned files, background compaction); Gorilla-family codecs inside the chunks; bounded lateness windows isolating disorder; rollup hierarchies with invalidation logs; retention as partition drops. Whether the substrate is InfluxDB's TSM, IOx's Arrow/Parquet object store, TimescaleDB's chunked B-trees, ClickHouse's sparse-indexed parts, or Prometheus's head-block TSDB, the invariants are identical — only the file format and index flavor change.
