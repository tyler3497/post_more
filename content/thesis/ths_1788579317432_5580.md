# CHERI Hardware Capabilities and Deterministic Memory Safety: A Deep Analysis of Fat-Pointer Architectures, Monotonicity, Compartmentalization, and Temporal Revocation from Morello to CHERIoT

## Abstract

Capability Hardware Enhanced RISC Instructions (CHERI) replaces integer addresses with unforgeable fat-pointer capabilities carrying bounds, permissions, and object types in hardware, enforcing spatial memory safety and fine-grained compartmentalization with single-digit percentage overhead. This thesis presents a rigorous analysis of the CHERI design space: the capability data model and its 128-bit compressed representation, the monotonicity principle governing capability derivation, sealed capabilities and hybrid versus pure-capability compartment models, and temporal safety via capability revocation (CHERIvoke, Cornucopia, and the deterministic epoch model of CHERIoT). We trace the lineage from CHERI-MIPS through CHERI-RISC-V and Arm Morello — the first industrial-scale CHERI prototype — to the 32-bit CHERIoT architecture for microcontrollers, examining software adaptations (CheriABI, CheriBSD, the CHERIoT RTOS) and the empirical performance evidence from SPECint on Morello silicon. We analyze what CHERI does and does not guarantee, including its interaction with speculative execution, concurrent revocation, and legacy software, and conclude with open problems in formal verification and adoption economics.

---

## 1 Introduction

Memory safety failures in C and C++ — spatial violations (out-of-bounds reads and writes) and temporal violations (use-after-free, use-after-reallocation) — remain the dominant source of exploitable vulnerabilities in deployed systems, with industry security teams consistently attributing the majority of serious bugs in large C/C++ codebases to memory unsafety. For five decades, the industry's response has been layered software mitigation: guard pages, stack canaries, ASLR, control-flow integrity, and sanitizer tooling. Each raises attacker costs incrementally; none eliminates the underlying unsafety of the C abstract machine.

CHERI proposes a different bargain: change the hardware-software contract so that *every* pointer dereference is checked, cheaply, in silicon. A CHERI pointer is not an integer but a **capability** — an unforgeable token of authority that carries its own bounds and permissions, checked on every load, store, and fetch [1]. Because capabilities cannot be forged — they are protected by a one-bit **tag** in memory that software cannot set directly — the hardware enforces that a program can only access memory it has been granted, at exactly the granularity the software intended. This yields **spatial safety by default** and a principled foundation for **compartmentalization**: breaking a process into mutually distrusting components whose interactions are mediated by capabilities rather than ambient authority.

This thesis analyzes CHERI end-to-end:

- The **capability data model**: fields, compressed encoding, tags, and the monotonicity theorem that makes revocation-free safety arguments possible (§4.1).
- **Pointer provenance and the C abstract machine** (CheriABI), and why recompiling the world is neither necessary nor sufficient (§4.2).
- **Compartmentalization models**: hybrid-capability, pure-capability, sealed entry, and object-capability invocation (§4.3).
- **Temporal safety**: from the architectural insight of CHERIvoke to production-grade Cornucopia revocation and CHERIoT's deterministic epoch model (§4.4).
- **Hardware realizations**: CHERI-RISC-V, Arm Morello, and the CHERIoT microcontroller profile (§4.5).

> **Theorem (CHERI spatial safety, informal):** In a pure-capability CHERI system, any memory access outside the bounds of a valid capability, or lacking the required permission, raises a hardware exception. Forgery of a capability requires hardware-controlled tag manipulation, inaccessible to ordinary instructions. Hence spatial memory-safety violations are eliminated *architecturally*.

This guarantee is precisely as strong as its assumptions — which §6 examines unsparingly.

## 2 Background

### 2.1 Capabilities: from operating-system kernels to hardware

The capability concept originates in the 1960s–70s: Dennis and Van Horn's segmented addressing, the Plessey 250, IBM System/38, and later software capability systems such as EROS, KeyKOS, seL4, and Capsicum. In all these systems, a *capability* is an unforgeable reference that bundles a designator (what it names) with rights (what it permits). The historical lesson was discouraging: **software-enforced** capabilities imposed unacceptable overhead on contemporary hardware, and fine-grained designs demanded whole-system rewrites [1].

CHERI's insight is that the *granularity mismatch* can be fixed in hardware. Rather than capabilities as coarse kernel objects, CHERI makes capabilities the **pointers themselves** — 128-bit architectural values manipulated by dedicated instructions alongside, and then replacing, conventional integer addresses.

### 2.2 The tagged-memory model

CHERI protects capabilities from forgery with **tagged memory**: every capability-sized, capability-aligned word in physical memory carries a one-bit tag indicating whether it holds a valid capability. Tags are manipulated only by capability-aware instructions:

- Storing a capability via a capability store preserves its tag.
- Storing via an ordinary data store *clears* the tag, rendering the bits mere data.
- Byte-level or misaligned writes clear tags.

This is the mechanism that makes capabilities **unforgeable**: no sequence of ordinary integer arithmetic can produce a tagged capability, since tags are not addressable as data [1].

### 2.3 The C problem: provenance, integers, and the hybrid model

C's abstract machine treats pointers as integers: pointer-integer casts, `uintptr_t` arithmetic, custom allocators, and serialization of pointers through files and networks are all idiomatic. Early CHERI prototypes showed that naïvely recompiling C programs against capabilities broke large amounts of real code — particularly programs that *manufacture* pointers from integers or compare pointers across allocations [2].

CHERI's answer is the **hybrid capability model**: the architecture supports both capability registers and ordinary integer-addressed memory. A hybrid ABI runs legacy code with integer pointers (bounds-checked against a coarse **default data capability**, DDC) while capability-aware code uses fine-grained capabilities.

## 4 Deep Dive

### 4.1 The Capability Data Model: Fields, Compression, and Monotonicity

A CHERI capability is an architectural fat pointer with the following logical fields [1]:

| Field | Purpose |
|---|---|
| **Address** | The 64-bit (or 32-bit in CHERIoT) virtual address used by the dereference |
| **Bounds** (base, top) | The contiguous range the capability authorizes |
| **Permissions** | Read, write, execute, capability-load/store, seal/unseal, system-register access, etc. |
| **Object type** | When *sealed*, the type governing unsealing; otherwise unset |
| **Tag** | 1-bit validity bit held in tagged memory, not in the capability value itself |

Naïvely, base + top + address + permissions exceeds 256 bits — too large to be a drop-in pointer. CHERI's key hardware trick is the **compressed bounds encoding** (the "CHERI Concentrate" format): bounds are stored relative to the address with a floating-point-like exponent, so that precisely representable regions are aligned to their size. A 128-bit capability (64-bit address + 64 bits of metadata, on 64-bit CHERI) fits the two-pointer-word budget; on 32-bit CHERIoT, capabilities compress to 64 bits [1][7].

The semantic heart of CHERI is **monotonicity**:

> **Theorem (Capability monotonicity):** Every capability-manipulation instruction produces a result whose authority (bounds × permissions) is a subset of its source's authority. The only exceptions are controlled: sealing/unsealing via authorized sealing capabilities, and invocation of sealed entry capabilities, which transfer control without expanding ambient authority.

Monotonicity is what makes CHERI's safety story *compositional*: if a compartment holds only capabilities bounded to its own objects, no sequence of its instructions can manufacture access to anything else [1]. This is a property amenable to formal proof — the CHERI semantics have been specified in Sail and subjected to mechanized reasoning about reachable-authority invariants [1].

Permissions are worth enumerating because they show how much policy lives in the architecture. Beyond read/write/execute, CHERI defines permissions governing *whether a capability loaded through this capability is itself usable as a capability* (load/store-capability permissions — the basis of "non-capability" memory for secrets), *sealing* authority, *system register* access, and branch-and-link behavior.

### 4.2 CheriABI and the Pure-Capability C Abstract Machine

Making capabilities the *default pointer representation* required rethinking the C abstract machine. Chisnall et al. (ASPLOS 2015) defined the CHERI C memory model: every C pointer becomes a capability, `malloc` returns a capability bounded precisely to the allocation, and pointer arithmetic is constrained so that out-of-bounds *intermediate* values clear the tag (preventing the classic "compute an out-of-bounds pointer, then bring it back" idiom that sanitizers also reject) [2].

Davis et al. (ASPLOS 2019, CheriABI) scaled this to a complete operating system: a pure-capability FreeBSD (CheriBSD) userspace running PostgreSQL, demonstrating **complete spatial and referential safety** for a large, unmodified application with overhead in the low single-digit percents [3].

1. **Pointer provenance tracking** in the compiler (LLVM/Clang): every pointer value carries provenance from its allocation; integer-to-pointer casts synthesize provenance from a privileged root (the DDC) rather than from thin air.
2. **ABI changes**: capabilities passed in capability registers, doubling register pressure on argument passing — the dominant source of measured overhead.
4. **Linker and loader** support for capability relocation and sealed imports.

The hybrid model — capability-aware libraries linked against legacy integer-pointer code, with the DDC bounding the legacy portion — proved essential for incremental deployment: Morello ran hybrid Android and Linux stacks alongside pure-capability experiments [4].

```c
/* Illustrative: what changes in the C abstract machine under CheriABI.
 * Pointers are capabilities; provenance is part of the value. */
#include <stdint.h>
#include <stdlib.h>

void example(void) {
    char *buf = malloc(64);          /* capability: bounds [buf, buf+64) */
    char *p = buf + 128;             /* OUT-OF-BOUNDS: tag cleared -> trap on use */
    uintptr_t u = (uintptr_t)buf;    /* provenance stripped; cast back */
    char *q = (char *)u;             /* derives from DDC, NOT from buf's bounds */
    /* q has ambient authority, not buf's precise bounds: */
    /* spatial safety holds, but precision is lost at the cast. */
    free(buf);
}
```

```rust
// The same discipline expressed in a safe language's terms:
// CHERI gives C programmers a hardware-checked borrow-like discipline.
fn bounded_copy(dst: &mut [u8], src: &[u8]) {
    // In CheriABI C, `dst` and `src` are capabilities whose bounds the
    // hardware checks on every access — no length parameter to get wrong.
    let n = dst.len().min(src.len());
    dst[..n].copy_from_slice(&src[..n]);
}
```

### 4.3 Compartmentalization: Hybrid, Pure, Sealed, and Object-Capability Models

Spatial safety stops a bug from corrupting arbitrary memory, but it does not stop a compromised component from misusing the authority it legitimately holds. **Compartmentalization** — decomposing software into mutually distrusting components with least-privilege interfaces — is CHERI's second pillar, and arguably its more transformative one [1][3].

CHERI supports a spectrum of compartment models:

- **Library compartmentalization (hybrid):** legacy code compiled with integer pointers is sandboxed by restricting its DDC; calls into it pass only the capabilities it needs.
- **Pure-capability compartments:** each compartment holds capabilities only for its own state; cross-compartment calls go through **sealed capabilities**.
- **Sealed entry capabilities:** a sealed code/data capability pair can be *invoked* (like a protected procedure call) but not dereferenced or forged. Sealing uses an **object type**; unsealing requires the corresponding sealing capability. This is the hardware primitive for domain crossing, with semantics resembling a hardware call gate [1].
- **Full object-capability discipline:** in the CHERIoT model, compartments communicate only by passing capabilities as arguments; there is no ambient authority at all, and the RTOS switcher mediates cross-compartment calls with complete register clearing [7].

The **CompartOS** project demonstrated automatic, linkage-based compartmentalization of FreeRTOS on CHERI-RISC-V: every object file becomes a compartment, with trampolines mediating calls, achieving fine-grained isolation of embedded software with modest overhead versus MPU-based schemes [8]. This matters because embedded systems historically relied on the MPU — a handful of coarse regions — and CHERI offers *unbounded* compartments at capability granularity.

A subtle point: compartmentalization without **temporal safety** is fragile. If compartment A frees an object and compartment B retains a dangling capability, B's use-after-free can corrupt A's reallocated memory *within* B's legitimately held bounds. Hence revocation (§4.4) is not an optional extra but a load-bearing part of the compartmentalization story.

### 4.4 Temporal Safety: CHERIvoke, Cornucopia, and Deterministic Epochs

Spatial safety is CHERI's headline; **temporal safety** — ensuring freed memory cannot be accessed through stale pointers — is its hardest problem. Capabilities make the problem *tractable* (stale pointers are identifiable by their tags and bounds) but not free: finding every dangling capability to freed memory requires a sweep reminiscent of garbage collection.

**CHERIvoke** (MICRO-52, 2019) established feasibility: by quarantining freed heap regions and then sweeping memory for capabilities pointing into quarantine (identified efficiently via tags, which distinguish capabilities from data), a system can deterministically revoke dangling pointers with modeled overhead of a few percent [5]. The key architectural enabler is the **tag bit**: a sweeper need only examine tagged words, skipping the vast majority of memory that contains no capabilities.

**Cornucopia** (IEEE S&P 2020) turned the feasibility study into a production-oriented system: a concurrent, kernel-resident revocation service in CheriBSD with a shadow bitmap tracking quarantined regions, demonstrating **<2% average overhead** (8.9% worst case) on SPEC CPU2006 on multi-core CHERI FPGA hardware, validated against the Juliet temporal-safety corpus [6].

**CHERIoT** took a different, stronger position appropriate to microcontrollers: *deterministic* use-after-free protection without sweeping. Capabilities are tied to heap allocation epochs; on free, the epoch advances and stale capabilities fault deterministically on next use — no sweep, no quarantine tuning, no probabilistic window [7]. Combined with a co-designed RTOS allocator, CHERIoT achieves temporal safety as a *local* property rather than a global sweep. This is only affordable because the heap is small and the allocator is co-designed with the hardware — a vindication of CHERI's hardware-software co-design philosophy.

> **Theorem (Revocation completeness):** If (a) every capability to a freed region is identifiable via tags, (b) the sweeper visits all tagged memory locations before the region is reallocated, and (c) no new capabilities to the region can be manufactured (monotonicity), then use-after-reallocation is impossible. CHERIvoke/Cornucopia satisfy (a)–(c) by construction; CHERIoT satisfies them via deterministic epochs.

### 4.5 Hardware Realizations: CHERI-RISC-V, Morello, and CHERIoT

| Platform | Base ISA | Capability width | Status |
|---|---|---|---|
| CHERI-MIPS (BERI) | MIPS64 | 256-bit (early) → 128-bit | Research prototype, FPGA |
| CHERI-RISC-V | RV64 | 128-bit | Research, QEMU + FPGA (Toooba) |
| **Arm Morello** | AArch64 (Neoverse N1) | 128-bit | Industrial prototype SoC, 2022 |
| **CHERIoT** (Ibex/Sonata) | RV32 | 64-bit | Microcontroller RTOS platform |
| Codasip X730 | RISC-V | 128-bit | Commercial IP (2024) |

**Arm Morello** is the landmark: a CHERI-enabled superset of AArch64 based on the Neoverse N1, taped out as a real SoC and distributed on development boards under the UKRI Digital Security by Design programme [4]. Early performance results (UCAM-CL-TR-986) ran SPECint 2006/2017 on Morello silicon across hybrid and pure-capability code models, finding overheads consistent with the FPGA literature — roughly **0–10%** depending on workload and code model, dominated by increased pointer size (cache pressure) and ABI register pressure rather than the bounds checks themselves, which the pipeline absorbs [4].

**CHERIoT** scales CHERI *down* three orders of magnitude: a 32-bit RISC-V microcontroller profile with 64-bit capabilities, a clean-slate RTOS, and a compartment model supporting *large numbers* of mutually distrusting compartments in under 256 KiB of SRAM, with a silicon area overhead around **3%** over the baseline Ibex core [7]. The lowRISC Sonata board provides an open FPGA platform for CHERIoT experimentation. Where Morello asks "can CHERI protect a phone or server?", CHERIoT asks "can CHERI protect a light bulb?" — and answers affirmatively.

## 5 Empirical Results / Formal Proofs

### 5.1 Performance evidence

Three independent measurement campaigns tell a consistent story:

1. **CheriABI on CHERI-MIPS/CHERI-RISC-V (FPGA):** pure-capability FreeBSD + PostgreSQL within a few percent of the baseline; overhead dominated by pointer-size effects [3].
2. **Morello (silicon, SPECint):** hybrid and pure-capability builds of SPEC CPU2006/2017 show geometric-mean overheads in the low single digits to ~10%, workload-dependent; bounds-check latency is absorbed by the out-of-order pipeline [4].
3. **Cornucopia revocation (FPGA, SPEC CPU2006):** <2% mean, 8.9% worst-case for concurrent always-on temporal safety [6].



### 5.2 Formal results

- **Monotonicity and reachable-authority invariants** have been formalized in the Sail ISA semantics and subjected to mechanized proof, giving high assurance that the hardware model itself cannot be subverted by instruction sequences [1].
- **Compartment isolation theorems**: given sealed entry discipline and correct switcher code, the authority reachable from a compartment is bounded by its initial capabilities — the basis of the CHERIoT security argument [7].
- **Temporal-safety models**: work on CHERI C memory models formalizes how revocation mechanisms interact with C semantics, proving that swept revocation restores temporal safety for the defined language subset.

## 6 Limitations

An honest accounting must bound the claims:

1. **CHERI is not a bug fix; it is exploit mitigation with teeth.** Spatial safety converts buffer overflows from control-flow hijacks into deterministic traps
2. **Speculative execution.** CHERI checks are architectural; transient-execution attacks (Spectre-class) that exfiltrate via microarchitectural channels are *not* prevented by capabilities alone. Capability-aware speculation defenses are active research.
3. **Revocation costs and complexity.** Always-on sweeping revocation (Cornucopia) adds a kernel service, quarantine memory overhead, and load barriers; CHERIoT's deterministic epochs avoid this only by co-designing the allocator and restricting the heap model. There is no free temporal safety at application-processor scale yet.
4. **Software ecosystem inertia.** Pure-capability operation requires recompilation with a CHERI-aware toolchain and adaptation of code that plays fast and loose with pointer provenance (custom allocators, JITs, garbage collectors). The hybrid model eases adoption but dilutes guarantees at the boundary.
5. **Compressed-bounds imprecision.** Representability rounding means bounds are *conservative over-approximations*; fine-grained sub-object safety (e.g., per-field bounds within a struct) requires instrumentation beyond raw CHERI, and very large objects demand aligned allocation.
6. **Side channels and physical attacks.** Tags protect against software forgery, not against an attacker with physical memory access or fault injection; CHERI is not a substitute for memory encryption or attestation.
7. **Formal verification gaps.** The ISA semantics are formalized, but full-stack proofs (compiler correctness for provenance, RTOS switcher correctness, compartment composition) remain partial.

---

## 7 Conclusion

CHERI represents the most serious attempt in decades to move memory safety from probabilistic software mitigation into the architectural contract. Its contributions are threefold: a **capability data model** with compressed bounds and hardware tags that makes per-pointer enforcement affordable; a **monotonicity discipline** that yields compositional, formally tractable safety arguments; and a **compartmentalization substrate** — sealed capabilities, hybrid and pure models, deterministic revocation — that makes least privilege the default rather than the exception.

The empirical record, from CheriBSD/PostgreSQL through Morello SPECint to the 3%-area-overhead CHERIoT microcontroller, supports a striking claim: *deterministic spatial safety costs about as much as today's best-effort mitigations, and temporal safety is achievable at low single-digit overhead.*

If memory unsafety indeed underpins the majority of serious systems vulnerabilities, then an architecture that *architecturally eliminates* spatial violations — and confines the rest within compartments — is not an incremental improvement but a phase change in systems security. Morello proved it can be built at industrial scale; CHERIoT proved it can be built at microcontroller scale. The open question is no longer *whether* capabilities work, but *how fast* the software world will adopt them.
