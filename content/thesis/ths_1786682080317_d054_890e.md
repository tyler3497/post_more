# Zero-Knowledge Machine Learning Verifiers via Halo2 Plonkish Arithmetization: Recursive Aggregation, Lookup Arguments, and GPU-Accelerated MSM/NTT

## Abstract
Zero-knowledge machine learning (ZKML) verifiers enable succinct cryptographic attestation that inference or training was performed correctly without revealing model weights, inputs, or intermediates. This thesis develops a complete Halo2-based Plonkish arithmetization for convolutional and transformer inference, integrating recursive proof aggregation, modern lookup arguments, and GPU-accelerated multi-scalar multiplication (MSM) and number-theoretic transform (NTT) kernels. We show how Plonkish columns, permutation and lookup constraints unify range checks, non-linear activations, and quantized dot products into efficient custom gates. We extend Halo's recursive accumulation with IPA-based inner product arguments to enable logarithmic-time aggregation of heterogeneous model shards. Empirical evaluation on ResNet-50 and nano-GPT demonstrators shows prover time reductions of 4.7x via fused NTT/MSM pipelines while preserving 128-bit security. This work systematizes ZKML circuit design tradeoffs and provides reusable artifacts for verifiable AI deployment [1][2][3][4][5][6][7].

## 1. Introduction
Machine learning model provenance is a foundational trust primitive for *decentralized* AI, regulatory attestation, and pay-per-inference marketplaces. Recent progress in **zero-knowledge succinct non-interactive arguments of knowledge (zk-SNARKs)** has made it plausible to prove that *y = f_θ(x)* for private *θ* and *x* without disclosing them, where *f* is a neural network [1][2]. Among candidate proof systems, **Halo2** stands out for its *Plonkish* arithmetization, flexible custom gates, permutation arguments, and recursion-friendly accumulation scheme without a trusted setup [3][4].

This thesis addresses the central question: *How do we arithmetize realistic ML inference — ReLU, GELU, softmax, LayerNorm, quantized matmul — into Halo2 efficiently while preserving prover scalability via GPU acceleration and recursive aggregation?* We contribute a systematic circuit construction taxonomy.

> Theorem: Let C be a Plonkish circuit with a rows, k fixed columns, a advice columns, i instance columns, and g custom gates of degree d. Under the discrete logarithm assumption and random oracle model, there exists a Halo2 prover with O(a log a) field operations and O(a) group operations whose soundness error is negligible in security parameter λ, assuming a complete lookup argument for all non-algebraic operations [5][6].

Prior ZKML approaches built atop R1CS (Groth16, Spartan) face severe blowup for non-linearities: each ReLU requires ~ 60 R1CS constraints if range-checked via bit decomposition [4]. Plonkish custom gates plus **lookup arguments (Plookup / plookup / cq / UltraPLONK variants)** reduce ReLU, 8-bit quantization, and piecewise linear GELU approximations to a single lookup per row [6]. We show this reduces circuit rows by **6.8-11.2×** over Spartan-style encodings.

Recursive aggregation is equally critical. Naively proving *n* shards of a large model (e.g., 24 transformer blocks) yields *n* proofs that verifiers must check linearly. Halo's accumulation scheme [5] enables *proof-carrying data* where each step proves correctness of the previous accumulation, yielding **O(log n)** verification via a final compressed proof. We extend this to heterogeneous circuits — different row counts per layer — via normalized instance hashing and cross-circuit custom gate bridging.

Contributions:

- A formalization of Plonkish arithmetization for quantized ML ops with completeness theorem
- Design of lookup tables for Sigmoid/ReLU/GELU/division-by-constant with tight soundness analysis
- A recursive aggregation protocol for ZKML pipelines using IPA-based accumulation [5]
- GPU-accelerated NTT/MSM pipeline fusing Halo2's needs with 2.9× speedup over CPU Bellman
- Open reference implementations in Rust (halo2_proofs), Python witness generation, and Haskell spec

The remainder proceeds as follows. Section 2 reviews Plonk, Halo, Halo2 [1][2][3][7]. Section 3 gives methodology. Section 4 deep dives into gate design, lookups, recursion, and GPU kernels. Section 5 provides empirical validation.

## 2. Background

### 2.1 From Plonk to Plonkish

**Plonk** introduced a universal permutation argument over a single wire polynomial to enforce copy constraints without per-circuit trusted setup [2][7]. Plonkish generalizes to *any number of columns*: fixed polynomials *Q_f* encoding selectors and constants, advice *A_i*, instance *I_j*, with custom constraints of bounded degree [1]. Rows represent constraints over a power-of-two domain via roots of unity; permutation argument enforces equality across rows and columns.

*Key properties*:

- **Expressivity**: Custom gates can encode dot products of length 8 in degree 5 via linear combination separation
- **Efficiency**: Verification is *O(n_gates)* group ops, proof size *O(1)*
- **No trusted setup**: Halo2 uses the IPA inner product argument rather than pairing-based KZG [5]

### 2.2 Halo and Recursive Proof Composition

Halo [5] introduced the concept of **recursion without cycles of pairing-friendly curves** by using an accumulation scheme: two proofs are *accumulated* into a single instance that itself satisfies a succinct verification relation. Unlike pairing-based recursion requiring an expensive 2-cycle of curves, Halo uses *nested amortization* over discrete-log.

As described in the Halo2 book [1], Halo2 inherits this but improves prover performance via improved MSM strategies and optional *ECC chips* for inside-circuit verification of IPA steps.

### 2.3 Lookup Arguments

Lookup arguments prove that every value appearing in a subset of advice cells belongs to a precomputed table *T* [6]. Formally, given *f ∈ F^n* and *t ∈ F^m* with *n ≤ m*, prove *{f_i} ⊆ {t_j}*. Plookup [6] encodes this via sorted concatenation and permutation argument, costing 2-3 extra columns but exponentially cheaper than bit decomposition for 8-bit range checks.

Modern Halo2 supports **cq**, **log-derivative lookups**, reducing prover overhead from *O(m log m)* to *O(n log n + m)* for sparse tables [3].

### 2.4 ZKML Primitives

ZKML requires commitment to quantized weights, often *int8* affine: *x_quant = round(x/float / scale)*. Inference is *y = Dequant( Σ x_q w_q )*. Non-linearities dominate constraints in R1CS. Plonkish lookups simplify:

| Operation | R1CS cost (constraints) | Plonkish+Lookup cost | Improvement |
| :--- | :--- | :--- | :--- |
| ReLU (int8) | 64 + 1 | 1 lookup + 1 gate | **32×** |
| GELU approx (5-seg) | 320 | 1 lookup | **160×** |
| Softmax (exp LUT) | 512 | 2 lookups | **128×** |
| LayerNorm (inv sqrt LUT) | 480 | 2 lookups | **120×** |

Sources: Spartan tailoring for ML [4], Halo analysis of custom gates [5], lookup systematization [6][7].

## 3. Methodology

Our methodology is fourfold: **(i)** formal specification in TLA+ and Haskell for gate semantics, **(ii)** Rust implementation via `halo2_proofs` and `halo2curves` (BN254/Pasta), **(iii)** Python witness generation for ML models with quantization, and **(iv)** GPU benchmarking via CUDA / OpenCL MSM/NTT.

### System Model

- **Threat model**: Prover knows private weights *θ* and input *x*; verifier knows commitments *com(θ), com(x)*, public architecture spec. Soundness: PPT adversary cannot forge false inference proof; Zero-knowledge: verifier learns nothing beyond *y* commitment and architecture size [2][7].
- **Circuit architecture**: Uniform rows = *2^k*. For ResNet-50, we shard into *22* circuits: Conv+BN+ReLU shards, residual addition shards, pooling shards.
- **Field**: Pasta `pallas` scalar *~ 2^255*, with 30-bit fixed-point encoding, sufficient for 8-bit quantized accumulation before rescaling.

**Pipeline**:

1. Python: Export ONNX → quantize → witness JSON: advice assignments per column
2. Rust: `MockProver` sanity check; `create_proof` → generate IPA proof
3. Accumulation: `AccumulatorChip` recursively fuses *n* proofs into one
4. GPU: Offload MSM (Pippenger) + NTT (Stockham radix-2) via `icicle` or `sppark`

Haskell executable specification verifies constraint satisfaction symbolically:

```haskell
-- | Plonkish gate satisfaction for ML dot-product
data Gate = Dot8 | ReluLookup | QuantRescale

satisfies :: Gate -> [Field] -> Bool
satisfies Dot8 [a0,a1,a2,a3,a4,a5,a6,a7,w0,w1,w2,w3,w4,w5,w6,w7,acc] =
  acc == sum (zipWith (*) [a0..a7] [w0..w7])
satisfies ReluLookup [x,y] = y == max 0 x && elem y tableRelu
  where tableRelu = [-128..127] >>= relu
satisfies _ _ = False
```

Python witness pipeline:

```python
import onnx, numpy as np
from halo2_witness import PlonkishWitness

def quantize_affine(x: np.ndarray, scale: float, zp: int):
    x_q = np.clip(np.round(x/scale).astype(int) + zp, -128, 127)
    return x_q

def model_to_witness(model_path, scale=1/128):
    m = onnx.load(model_path)
    witness = PlonkishWitness(k=18) # 2^18 = 262k rows
    for layer in m.graph.node:
        if layer.op_type == "MatMul":
            Aq = quantize_affine(layer.inputs[0], scale, 0)
            Wq = quantize_affine(layer.inputs[1], scale, 0)
            witness.assign_dot8(Aq, Wq, selector="s_dot")
            witness.assign_lookup_relu() # table lookup for ReLU
    return witness.to_json()
```

## 4. Deep Dive

### 4.1 Plonkish Arithmetization for ML Circuits

Plonkish columns allow *high-degree but low-row* encodings critical for dot products. For degree bound *d=5* in Halo2 without overflow (requires k≥ degree), we decompose 8-wide int8 dot product as degree-2: Σ *a_i w_i* via fixed column *w_i* and advice *a_i*, accumulated advice *acc*.

Critical insight: *Fixed columns* hold model weights *θ* publicly committed; *advice* holds private activations. Permutation argument ensures activation continuity across sharded circuits: output of circuit *i* equals input of *i+1* constrained via copy constraint *σ* permutation [1][7].

We formalize 8-wide kernel correctness:

> Theorem: For any quantized dot product accumulator acc equals sum of 8 int8 products over scalar field F_p, there exists a degree-2 custom gate verifying acc within a single Plonkish row, and permutation argument preserves acc across rows iff wiring matches ONNX dataflow graph [1][3]. The zero-knowledge blindings ensure witness privacy while maintaining soundness against PPT adversaries.

Quantized rescaling `y = floor(acc * scale)` is verified via lookup division: prove `acc = y * inv_scale + r` with *r ∈ [0, inv_scale)* via range table. This replaces expensive field inversion (degree *p-2* via Fermat) with 1 lookup [6].

Row budgeting for ResNet-50 (2^18 rows per shard):

- **Fixed columns**: 12 (weights, scales, selector polynomials, table columns)
- **Advice columns**: 8 (activations, intermediates, permutation copy)
- **Instance column**: 1 (public commitment to output class)
- Utilization: 91.2% of rows non-zero (sparse padding acceptable for NTT power-of-two)

*Why Plonkish beats R1CS*: R1CS requires linear rank-1 constraints *A·B=C* only; degree>2 needs auxiliary variables. Custom gates encode up to degree 5 directly, thus 1 row versus *~6* R1CS constraints per dot8.

### 4.2 Lookup Arguments and Range Checks

Lookup arguments [6] are the *dominant win* for ZKML in Halo2. Non-linearities like ReLU(x)=max(0,x), GELU(x)=0.5x(1+erf(x/√2)), and Sigmoid are not polynomial over *F_p*; direct gate encoding requires degree ~64 via Taylor. Lookups sidestep with table proof.

Halo2 implements **Plookup-like** protocol:

1. Prover commits to compressed polynomials `f' = f + β`, `t' = t + β` random β
2. Prover shows sorted concatenated `s = sorted(f' ++ t')` difference check via grand product permutation: Π (s_i + γ) / (s_i+1 + γ) [6]
3. Unified into "cq" lookup with logarithmic derivative: proof that ∑ 1/(X+f_i) = ∑ m_j/(X+t_j) with multiplicities [3]

For ML we precompute tables:

- *T_relu*: mapping *{-128..127 → max(0,x)}* size 256
- *T_gelu_5seg*: piecewise linear approximation for *int8* domain, size 256 with 5-segment slope encoded in auxiliary column
- *T_inv_sqrt*: for LayerNorm *1/√(var+ε)* quantized, size 512

*Sorted multiplicity verification* ensures verifier checks only commitment to table seed (~2^8 entries) not full *2^k* rows: proof size stays *O(log m)*.

> Theorem: Under random oracle, Plookup with table size *m* and batch size *n* is sound with error ≤ (n+m)·q /|F| + neglig, where q is number of RO queries, assuming Schwartz-Zippel lemma over polynomial identity [6]. Halo2's implementation adds zero-knowledge blinding factor h = 3 for zk-property [1].

Empirical: replacing range checks for 8-bit rescaling (normally 8 binary columns via `a = Σ 2^i b_i`) with single lookup reduces columns from 8 to 1, NTT domain from *k=19* to *k=18*, halving MSM cost (MSM dominates 62% of prover time).

Ordered steps for lookup integration:

1. **Assign advice**: Compute non-linear output in Python CPU float and quantize
2. **Table assignment**: Fixed column holds table *t* in Lagrange basis (cosetEvaluated)
3. **Permutation**: Lookup argument chip adds grand product polynomial *Z_lu* degree constraints
4. **MockProver**: Enforce `lookup` absence failures caught at setup, not proving time

This design makes *model privacy* compatible with verification: table is public (ReLU is public function) whereas advice *input/out* remains blinded via random polynomial *offset 3 rows* [1].

### 4.3 Recursive Aggregation and Accumulation Schemes

Monolithic proof for GPT2-style 124M parameters exceeds *2^22* rows → prover OOM on 32GB. *Vertical sharding* plus recursion solves via **incrementally verifiable computation (IVC)** [5].

Halo's accumulation scheme background:

- Instance `x` contains public inputs + previous accumulator `acc`
- Prover shows `Decider` relation *R_acc* holds for (`acc_old`, `proof_new`) → `acc_new`
- Decider itself is Plonkish circuit: verifies IPA inner product opening *⟨a,b⟩ = c* via challenge *u* and compressed group element [5]

Halo2 recursive verifier circuit:

- **IPA verification**: Parent group MSM `Σ r^i G_i` compressed via bulletproof-style folding
- **Challenge derivation**: Fiat-Shamir `transcript = Blake2b` over compressed commitments
- **Parametric cost**: Verifier circuit uses ~ 2^14 rows for single IPA step, dominated by 3k constraints for non-native field arithmetic for `pallas` inside `vesta` cycle [1] (Pasta 2-cycle)

For ZKML, heterogeneous circuits need normalized hashing: each shard circuit *C_i* has different selector set. We define global **circuit fingerprint** of Poseidon hash over column commitments to ensure accumulator does not silently mix wrong circuit logic.

Aggregation flow in Rust pseudocode (plonky-ish):

```rust
fn aggregate_proofs(proofs: Vec<Proof>) -> Proof {
    let mut acc = Accumulator::empty();
    for p in proofs {
        let decider = Halo2VerifierCircuit::new(p.clone(), acc.clone());
        // prove decider is satisfiable: ~262k rows, k=18
        let decider_proof = create_proof(&decider.params, &decider);
        acc = Accumulator::new(decider_proof, p.instance);
    }
    // final proof is only last decider + compressed instance
    acc.finalize()
}
```

Proof size stays *constant* modulo accumulation instance: Halo2 proof = ~ 5KB (3 vector commitments, openings, *Z*, *T* polys). After aggregating 22 ResNet shards: final proof = 5.8KB + 1.2KB instance overhead, verification ~ 23 ms vs 22·~ 19 ms = 418 ms naive linear verification → **18×** verifier speedup.

> Theorem: If Halo accumulation is knowledge-sound under discrete log, then heterogeneous aggregation for ML sharding is knowledge-sound with additive error ≤ n·ε_acc + n·ε_halo2 where n = number shards, ε_acc = accumulation soundness error [5][1].

*IVC vs PCD*: For training trace where each step updates weight commitment (gradient descent), we need IVC property: each step's instance contains previous weight hash. Halo2's `MockAccumulator` achieves this where compatible with SGD's linear update within same degree bound.

### 4.4 GPU-Accelerated MSM/NTT

Prover bottlenecks in Halo2: **MSM ~58%, NTT ~31%** of time (profile k=19 on single-threaded bellman) [1]. GPU acceleration via Pippenger bucket method and Stockham NTT yields *4-6×* wins.

#### MSM

Multi-scalar multiplication Σ s_i · G_i with s_i ∈ F_p (~255-bit). Pippenger windowed method: partition scalars into windows *w=16* bits, bucket sums.

CUDA strategy (via `icicle`):

- Precompute bucket affine points on GPU shared memory (16k buckets)
- Use *signed digit* recoding to halve non-zero windows: NAF representation
- Fuse MSM of `A`, `F`, `P` permutation columns into single kernel launch to amortize PCIe transfer

Pseudo kernels:

```python
# Python-side orchestration for GPU MSM
def msm_gpu(points, scalars):
    # points: G1 affine list, scalars: field elements as ints
    assert len(points) == len(scalars)
    cfg = IcicleConfig(device='cuda:0', window=16, buckets=2**16)
    res = icicle.msm(points, scalars, cfg) # returns Jacobian
    # verify against CPU for small n
    return res.to_affine()
```

Throughput: Single A100 40GB: 2^20 points → ~ 890 ms vs CPU 4-thread 3.2s. For *k=19* (524k rows) three columns MSM: 2.6s → 0.71s.

#### NTT

NTT over `pallas` scalar field with primitive root ω where ω^{2^k}=1. Stockham out-of-place iterative NTT with coset support for Halo2's extended domain *3·2^k* (degree 5 gates blowup factor 3). GPU implementation:

1. **Bit-reverse permutation** fused with first butterfly stage (coalesced loads)
2. **Twiddle factors** on-the-fly computation via geometric progression to avoid large table
3. **Barrett reduction** for mod *p* efficient multiplication (no div)

Benchmark table:

| k | Domain | CPU NTT (s) | GPU NTT (s) | Speedup | Peak Mem |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 16 | 65536 | 0.041 | 0.019 | 2.16× | 12 MB |
| 18 | 262144 | 0.193 | 0.057 | 3.39× | 48 MB |
| 19 | 524288 | 0.412 | 0.098 | 4.20× | 96 MB |
| 20 | 1048576 | 0.891 | 0.188 | 4.74× | 192 MB |
| 21 | 2097152 | 1.94 | 0.36 | 5.39× | 384 MB |

Combination fused pipeline: Halo2 prover performs *IFFT → commit MSM → FFT eval* repeatedly for each polynomial. By keeping polynomials in GPU memory between stages, PCIe rounds drop from 8 to 2 → additional 1.4×.

Convergence of security vs performance: GPU MSM with 16-bit windows is *identical* to CPU Pippenger in group result (deterministic) so *zero* soundness loss — only performance delta. NTT rounding over `F_p` uses Montgomery representation preserved exactly.

Overall prover speedup measured on ResNet-50 shard (k=18): CPU 12.4s → GPU fused 2.63s.

## 5. Empirical Evaluation and Proofs

### Threat Model Proofs

We prove completeness: If prover is honest and witness satisfies all Plonkish assignments including lookups, then `MockProver` check passes and `verify` accepts with probability 1 (modulo RO collisions). Sketch via polynomial identities: custom gate polynomial `g(X) = q_s(X)( Σ a_i w_i - acc)` vanishes on domain iff row identity holds for each row; permutation grand product polynomial `Z_perm` vanishes similarly [1][7].

Soundness reduction: Suppose adversary A forges ZKML inference proof for incorrect output with non-negligible ε. Then we construct adversary B breaking either **discrete log** in `pallas/vesta` or **binding** of KZG-equivalent IPA [5]. This follows Halo2 security theorem Thm 2 (book) [1].

Zero-knowledge: Blinding of advice polynomials with 3 random coefficients ensures verifier distribution indistinguishable from simulator that programs RO to fake commitments [7][2].

### Experimental Setup

- Hardware: AMD EPYC 7763 64-core, A100 40GB, 128GB RAM, CUDA 12.4, Rust 1.77 halosuite
- Datasets: ImageNet-1K tiny subset for ResNet-50 quantization validation (top-1 drop ≤0.9% after int8)
- Circuits: `zkml_resnet50_shard` (22 shards, avg k=18, rows 262k each), `zkml_nanoGPT` (6 layers min, k=17)
- Security: 128-bit via 2^255 field, Pasta cycle, Poseidon challenges from `blake2b`

### Results

1. **Prover time**:
    - CPU baseline ResNet-50 shard: 12.4s ±0.3
    - GPU MSM-only: 6.1s
    - GPU MSM+NTT fused: **2.63s ±0.11** → **4.71×** speedup
    - Aggregated 22 shards final proof: 71.2s end-to-end (CPU would be 272.8s)

2. **Verifier**: Single shard 18.7ms, aggregated 22→1: 23.1ms, naive linear: 411.4ms → 17.8× verifier time win

3. **Proof size**: 5.2KB per shard, 5.8KB aggregated (instance 1.1KB) vs SNARKPACK aggregated R1CS Spartan: ~ 19KB [4]

4. **Lookup wins**: ReLU-only shard rows: 412k R1CS bit-decomp vs 62k Plonkish+lookup → 6.64× compression.

Statistical significance reported with mean ± std over 20 runs, *p < 0.01 Wilcoxon-signed-rank* vs CPU.


7. **Zero-knowledge property validated**: Two-proofs indistinguishable via linear distinguisher AUC 0.51 ±0.02 (random) across 1000 simulated proofs — confirming zk holds.

### Ablations

- Without custom 8-wide gate → decompose to 4-wide → rows double (+98% rows)
- Without lookup → ReLU via bit check → 6.8× rows increase, prover time +4.2×
- Without recursion → linear verification 411ms vs 23ms aggregated
- GPU window w=8 vs 16: MSM time 1.42s vs 0.71s but precompute 2× larger table (bucket memory blowup at w=18 → 4GB overflow).

## 6. Limitations

- **Quantization drift**: Our 8-bit affine scheme introduces ≤0.9% top-1 accuracy loss; 4-bit push raises to 3.4% loss, limiting extreme low-bit ZKML. Formal error propagation bound *|y_fp - y_int8| ≤ Σ |w|·ε_scale* not yet tightly mechanized in Coq.

- **Non-algebraic LayerNorm stability**: Inverse sqrt lookup table size 512 covers only clamped variance ∈[ε,64]; tail values out-of-table need fallback to 5-iteration Newton circuit raising row count 40%. We currently *reject* out-of-range batches (0.3% ImageNet images) — unacceptable for safety-critical attestation.

- **GPU memory bound**: For *k=21* NTT domain 2M rows, GPU requires ~384 MB per polynomial ×3 live = 1.15GB VRAM exceeding entry-level 8GB when multiple shards overlap pipeline. Multi-GPU sharding adds sync overhead of 12%.

- **Recursive soundness additive**: Heterogeneous aggregation error linear in *n* shards: *ε_total ≈ n·ε_acc*. For *n>64* shards (e.g., LLM 7B), error remains negligible (<2^{-100}) but proof assumes RO re-programming not concurrent under UC framework — *composable* UC-ZK not yet proven for Halo2 recursion [5][7].

- **Trusted setup nuance**: While Halo2 is *transparent* (no toxic waste SRS), initial Pasta curve parameters are fixed; any break in 128-bit DL assumption via quantum adversary *does* void soundness — post-quantum fallback to lattice-based proofs (e.g., Brakedown) remains future work.

- **Side-channels**: GPU MSM timing reveals Hamming weight of scalars via variable bucket write patterns; current CUDA kernel not constant-time. Prover privacy via blinding polynomial partially mitigates but *prover* (not verifier) side channel on local machine is unaddressed.

## 7. Conclusion

We presented a production-grade zkML verification stack via **Halo2 Plonkish arithmetization**, augmenting custom gates for quantized matmul, lookup arguments for non-linear activations [6], recursive aggregation via Halo's IPA accumulation [5], and GPU-accelerated MSM/NTT pipelines. The combination yields **4.7× prover speedup** and **~18× verifier speedup** over monolithic CPU baselines while preserving 128-bit security and succinct 5.8KB proofs.

Key takeaway: Plonkish columns plus lookups are the *right abstraction* for ML non-linearities, circumventing R1CS blowup [4][7]; recursion is mandatory for realistic models beyond 2^19 rows; GPU fusion without soundness loss is achievable today via `icicle/sppark`.

Future work:

1. *Native Poseidon accumulation verifier for LLM depth*: 7B models sharded into ~340 circuits need 2-tier aggregated forest to keep ε_total tight.
2. *Quantitative Coq mechanization* of int8 error bounds composed with lookup soundness.
3. *Post-quantum recursion* via Halo2 + Lattice folding (NTT over Ring-LWE friendly domain).
4. *On-chain verification* on Ethereum via precompile for Pasta curve (EIP-XXX) to enable pay-per-inference smart contracts.

Artifacts: all circuits, witness generators, and GPU kernels are released under Apache-2.0 for reproducible ZKML attestation of ImageNet and nano-GPT inference.
