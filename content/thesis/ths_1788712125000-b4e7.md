# Scalable Vector ISAs: The RISC-V Vector Extension, Arm Scalable Vector Extension, Predicated Execution, and Compiler Auto-Vectorization at Variable Length

## Abstract

Scalable vector ISAs decouple vector length from binary compatibility, letting one binary exploit implementations whose register widths differ by an order of magnitude. This thesis compares the two dominant designs — the **RISC-V Vector Extension (RVV 1.0)** and **Arm SVE/SVE2** — through a unified framework: (i) vector-length-agnostic programming via RISC-V's `vtype`/`vsetvli` configuration state versus Arm's predicate-generated loop control (`WHILELT`, `INCD`); (ii) *predicated execution*, including governing predicates P0–P15, first-faulting speculative loads, and the First-Fault Register; (iii) register grouping parameterized by *VLEN*, *SEW*, and *LMUL*; and (iv) compiler auto-vectorization at unknown length via LLVM's `<vscale × N>` scalable types and the VPlan vectorizer. Empirical grounding comes from published silicon (Ara/Ara2, A64FX-class SVE). We quantify strip-mining overhead, LMUL front-end amortization, and predicate setup costs, and identify open limits: heterogeneous-VLEN performance portability, width-parametric cost models, and ecosystem maturity. Central claim: both ISAs converge on *predicate-guarded, configuration-driven strip-mining*, differing in how much length management lives in hardware versus the compiler.

## 1 Introduction

For four decades, single-instruction-multiple-data (SIMD) ISA design faced a fundamental dilemma: widening the vector registers improved peak throughput but invalidated the installed software base. Intel's trajectory from MMX (64-bit) through SSE, AVX, AVX-512, and AMX; Arm's from NEON (fixed 128-bit) to SVE; and the proliferation of packed-SIMD DSP extensions all shared one structural property: the vector width was an *architectural* constant. Every width increase demanded a new ISA revision, new intrinsics, recompilation, and — critically — a new binary. The 2016 introduction of Arm's Scalable Vector Extension [2], followed by the ratified RISC-V Vector Extension version 1.0 in 2021 [1], offered a different contract: the vector length becomes an *implementation* parameter, while the binary remains valid across implementations.

The consequences of this contract ripple through every layer of the computing stack. Hardware vendors gain freedom to trade area and energy for vector width without fragmenting software. Programmers gain "write once, scale everywhere" binaries — at least in principle. Compilers, however, inherit a genuinely new problem: they must generate code for a *quantity they cannot know at compile time*. This thesis studies that compiler problem and the ISA mechanisms that make it tractable, through a comparative lens on the two principal scalable vector ISAs.

The remainder of this thesis is organized as follows. Section 2 reviews the background of vector architectures, from Cray to NEON. Section 3 describes our analytical methodology, including a formal model of the vector-length-agnostic (VLA) execution state and the corpus of primary sources. Section 4, the deep dive, dissects the RISC-V configuration model, Arm's predicate architecture, first-fault speculative vectorization, register grouping and element-width polymorphism, and the LLVM scalable-vector type system with VPlan auto-vectorization. Section 5 presents an empirical evidence plan grounded in published measurements. Section 6 enumerates limitations of current scalable vector systems, and Section 7 concludes.

## 2 Background

### 2.1 A brief history of vector ISAs

Vector processing began with the Cray-1 (1976): fixed 64-element vector registers, chaining, and a memory subsystem designed around sustained streaming. The 1990s brought packed-SIMD to general-purpose processors — Intel MMX, AMD 3DNow!, Motorola AltiVec, and later Arm NEON — all *fixed-width*. The performance-portability trap was set: software written against 128-bit NEON could not exploit 512-bit SVE hardware without recompilation, and binaries tuned for one microarchitecture were often suboptimal on another.

A second tradition, *variable-length* vector ISAs, dates to the vector-length register of the Cray X-MP and the CDC STAR-100. These designs exposed an architectural vector length (VL) register, and software "strip-mined" loops into VL-sized chunks. Cray's model kept the *maximum* vector length implementation-defined but required the runtime to query it — an idea SVE and RVV would later refine into full binary portability.

> **Theorem: Vector-Length-Agnostic Binary Portability.** *A program binary is portable across implementations with vector widths VLEN₁ ≠ VLEN₂ iff every quantity depending on the vector width is either computed at runtime from an architectural query (vsetvli, WHILELT, INCD) or expressed in the predicated, length-relative instruction semantics of the ISA. Any compile-time constant derived from an assumed width breaks the theorem's hypothesis.*

### 2.2 The fixed-width ceiling

Fixed-width SIMD encountered three structural limits:

1. **Opcode-space exhaustion.** Each width doubling (SSE→AVX→AVX-512) consumed encoding space and multiplied the intrinsic API surface.
2. **Software fragmentation.** Binaries carried dispatch logic (`cpuid`-gated function multi-versioning) that ballooned code size and testing matrices.
3. **Diminishing compiler returns.** Auto-vectorizers tuned cost models to one width; wider hardware frequently delivered far less than linear speedup on legacy binaries.

### 2.3 The scalable turn

Arm's 2016 announcement of SVE [2] introduced *Vector Length Agnostic* (VLA) programming: vector registers Z0–Z31 have an implementation-defined length from 128 to 2048 bits in 128-bit increments; predicate registers P0–P15 (plus the First-Fault Register, FFR) are 1/8 the data-register width. The RISC-V "V" extension [1], ratified as v1.0 after a long gestation (drafts 0.7–0.10 were implemented by Ara [5] and others), took a different path to the same goal: 32 architectural vector registers of implementation-defined *VLEN* ≥ 128 bits, configured at runtime through the `vtype` CSR and the `vsetvli`/`vsetvl` instructions.

| Feature | Arm SVE/SVE2 | RISC-V V (RVV 1.0) |
|---|---|---|
| Vector registers | 32 × Z (128–2048 bit) | 32 × v (VLEN ≥ 128 bit) |
| Predicate/mask regs | 16 × P + FFR | v0 as mask register |
| Length discovery | `WHILELT`, `INCD`, `CNTD` | `vsetvli`/`vsetvl` returns `vl` |
| Element width | Per-instruction suffix (.B/.H/.S/.D) | `vtype` SEW field (e8–e64) |
| Register grouping | N/A (fixed Z width) | LMUL ∈ {1/8,…,8} |
| Fault-tolerant speculation | LDFF1* + FFR/RDFFR | Fault-only-first loads (`vle8ff`) |
| Tail policy | Zeroing/merging predicate (`/Z`, `/M`) | `vtype` ta/mu bits |
| Min vector length | 128 bit | 128 bit (typical); VLEN impl-defined |

## 3 Methodology

Our analysis proceeds from three complementary sources of evidence:

1. **Primary ISA documents.** We treat the ratified *RISC-V Vector Extension Specification v1.0* [1], Arm's SVE whitepapers and reference manuals [2][3], and the Arm C Language Extensions for SVE [4] as ground truth for semantics.
2. **Compiler internals.** We examine LLVM's scalable vector type system — the `<vscale × N × ty>` IR representation documented in the LangRef and the RISC-V backend guide [6] — and the loop-vectorizer's VPlan framework, using the historical SVE enablement RFCs [7] as design rationale.
3. **Published silicon and simulation data.** We draw on the Ara [5] and Ara2 [8] open-source RVV processors (22 nm FD-SOI, up to 97% FPU utilization on DGEMM) and the Fujitsu A64FX (512-bit SVE) literature as empirical anchors.

Analytically, we model a scalable vector machine as a tuple *(VLEN, ELEN, SEW, LMUL, P)* where VLEN is the implementation's physical register width, ELEN the maximum supported element width, SEW the *selected* element width, LMUL the register-group multiplier, and *P* the active predicate state. The *effective* vector length in elements is:

$$VLMAX = \frac{VLEN \times LMUL}{SEW}, \qquad vl \le VLMAX$$

and every loop in the VLA idiom is a *strip-mined* loop whose chunk size `vl` is negotiated at runtime. This single equation explains why RVV needs `vsetvli` (to negotiate `vl` and configure SEW/LMUL) and why SVE instead bakes the negotiation into predicate-generating instructions (`WHILELT`) — two syntactic routes to the same semantic fixed point.

## 4 Deep Dive

### 4.1 The RISC-V configuration model: `vtype`, `vsetvli`, and strip-mining

RVV's central innovation is to make the vector *configuration* — not just the length — a first-class runtime state. The `vtype` CSR encodes the selected element width (SEW ∈ {8, 16, 32, 64}), the register-group multiplier (LMUL ∈ {1/8, 1/4, 1/2, 1, 2, 4, 8}), tail/mask agnostic policies, and an illegal-configuration flag `vill` [1]. The `vsetvli` instruction atomically sets `vtype`, computes `vl = min(AVL, VLMAX)`, and returns the granted length in a scalar register:

```c
// Canonical RVV strip-mined loop (daxpy), from the v1.0 spec idiom [1]
// Compiler-emitted assembly pattern:
//   vsetvli t0, a0, e64, m8, ta, ma   # SEW=64, LMUL=8
// loop:
//   vle64.v v0, (a1);  vle64.v v8, (a2)
//   vfmacc.vf v8, fa0, v0
//   vse64.v v8, (a2)
//   sub a0, a0, t0;  slli t1, t0, 3
//   add a1, a1, t1;  add a2, a2, t1
//   vsetvli t0, a0, e64, m8, ta, ma
//   bnez a0, loop
void daxpy(size_t n, double da, double *x, double *y);
```

Several subtleties deserve emphasis. First, `vsetvli` with `rs1 = x0` requests the *maximum* VLMAX, a useful idiom for straight-line code. Second, an unsupported `vtype` sets `vill` and zeroes `vl` rather than trapping — a deliberate choice enabling lightweight runtime feature interrogation [1]. Third, the *tail-agnostic* (`ta`) and *mask-agnostic* (`ma`) bits give implementations freedom to skip writing tail and inactive elements, which simplifies chaining and reduces register-file write pressure. Fourth, fractional LMUL (1/8–1/2) lets narrow-element code use fewer physical registers, raising *effective* VLMAX for mixed-width kernels — the SEW/LMUL operating-point table in the spec shows, e.g., that SEW=8 with LMUL=1/2 yields the same VLMAX as SEW=16 with LMUL=1 [1].

### 4.2 Arm SVE: predication as the universal control primitive

Where RVV centralizes length management in a CSR, SVE distributes it across *predicates*. Every SVE data-processing instruction takes a governing predicate (P0–P7 for loads/stores/arithmetic; P8–P15 reserved for loop management), and each lane executes only where the predicate bit is true [2][3]. Loop control itself is predicate generation:

```asm
// SVE daxpy: vector-length-agnostic loop [3]
    mov x3, #0                    // i = 0
    whilelt p0.d, x3, x0          // p0 = (x3 + lane < n)
loop:
    ld1d z1.d, p0/z, [x1, x3, lsl #3]
    ld1d z0.d, p0/z, [x2, x3, lsl #3]
    fmla z0.d, p0/m, z1.d, z2.d   // z2 holds broadcast da
    st1d z0.d, p0,   [x2, x3, lsl #3]
    incd x3                       // i += VL/64 (runtime vector length!)
    whilelt p0.d, x3, x0
    b.first loop                  // branch while first lane active
```

Three properties make this remarkable. First, the *same binary* runs on 128-bit and 2048-bit implementations; `INCD`/`WHILELT` read the hardware's actual width at runtime [2]. Second, the `/Z` (zeroing) vs `/M` (merging) predicate qualifiers give the compiler control over inactive-lane semantics without extra instructions. Third, predicates compose: `PTRUE`, `WHILELT`, `BRKA`/`BRKB` (break-partition generation) let compilers express early-exit and data-dependent control flow as pure predicate arithmetic — the foundation of SVE's *fault-tolerant speculative vectorization*.

### 4.3 First-faulting loads and speculative vector partitioning

Vectorizing loops with data-dependent exits (`while (*p++)`, string search) requires *speculative* memory access: the vectorizer must touch elements past the not-yet-known trip count without faulting. SVE solves this with the **first-fault mechanism** [2][4]. A first-faulting load (`LDFF1B/D/H/S`) suppresses faults for every active element *except the first*; on a fault, it records the failing element index in the dedicated First-Fault Register (FFR) and zeroes/merges the rest. Software then reads the FFR into a predicate (`RDFFR`) and continues with a *partition* covering only the successfully loaded prefix:

```c
// SVE strlen idiom (ACLE), from the Arm C Language Extensions [4]
svbool_t pg = svptrue_b8();
uint64_t i = 0;
do {
    svuint8_t v = svldff1_u8(pg, &s[i]);   // first-faulting load
    svbool_t nz = svcmpne_n_u8(pg, v, 0);   // find NUL
    pg = svbrkb_b_z(pg, nz);                // partition before break
    i += svcntp_b8(pg, pg);
} while (svptest_any(pg, nz) == false);
```

RVV 1.0 provides the analogous primitive as *fault-only-first* loads (`vle8ff.v`, …): only the first active element may trap; later elements that fault merely truncate `vl` [1]. Both ISAs thus implement the same abstract operation — *speculative vector memory access with precise fault attribution* — but package it differently: SVE as a persistent FFR plus `RDFFR`, RVV as a `vl`-truncating load whose result length the strip-mined loop naturally consumes. This convergence is strong evidence that first-fault semantics are the *right* primitive for VLA speculation.

> **Theorem: Speculative Partition Soundness.** *Let a first-faulting load execute under governing predicate P, faulting at the first active element k. Then the partition P' = P ∩ [0, k) contains exactly the elements with architecturally defined values, and re-executing the loop body under P' is observationally equivalent to scalar execution up to element k. Any element ≥ k is either re-attempted (becoming a future first element) or excluded by the break partition.*

### 4.4 Register grouping, LMUL, and multi-width execution

RVV's LMUL mechanism deserves close study because it has no SVE counterpart and profoundly affects both hardware and compiler design [1]. LMUL groups 2, 4, or 8 physical registers into one logical operand, multiplying VLMAX at the cost of register count: with LMUL=8, only 4 register groups exist (v0, v8, v16, v24). The spec's register-grouping rules are strict — groups must start at multiples of LMUL — and violating them is *reserved*, a frequent source of codegen bugs.

Why does LMUL exist at all, given that SVE achieves variable length without it? Three reasons:

1. **Instruction-fetch amortization.** Long vectors (LMUL=8 on a 512-bit VLEN gives 4096-bit logical operands) let one instruction drive many cycles of a pipelined functional unit, reducing front-end pressure — the same motivation as Cray's long vectors.
2. **Mixed-width alignment.** Fractional LMUL aligns VLMAX across different SEWs in one kernel (e.g., int8 indices with fp32 data), avoiding re-strip-mining at width boundaries [1].
3. **Widening operations.** Instructions like `vwmul` (widening multiply) *require* LMUL ≥ 2 semantics, producing double-width results in register groups.

The compiler cost is real: LLVM's RISC-V backend must perform *register-group-aware* allocation (VRM2/VRM4/VRM8 register classes), insert `vsetvli` instructions via dataflow analysis to minimize reconfigurations (`RISCVInsertVSETVLI`), and reason about the LMUL↔SEW↔`<vscale × N>` correspondence [6]. SVE's compiler, by contrast, never thinks about grouping — the hardware's fixed Z-register width absorbs it — but pays with less control over front-end amortization.

### 4.5 Compiler auto-vectorization at unknown length: LLVM's `<vscale × N>` and VPlan

The compiler problem is the thesis's crux. LLVM represents scalable vectors with the type `<vscale × N × ty>`: a vector whose element count is an *unknown multiple* `vscale` of the static minimum `N` [6][7]. On AArch64 SVE, `vscale` ranges over {1,…,16} (128–2048 bits); on RISC-V, LLVM defines `vscale = VLEN/64`, so `n` and `ty` jointly determine LMUL and SEW [6]:

| LLVM IR type (ELEN=64) | SEW | LMUL |
|---|---|---|
| `<vscale x 1 x i64>` | 64 | 1 |
| `<vscale x 2 x i64>` | 64 | 2 |
| `<vscale x 4 x i32>` | 32 | 2 |
| `<vscale x 8 x i16>` | 16 | 2 |

The loop vectorizer plans in *element counts* that are symbolic in `vscale`. LLVM's **VPlan** infrastructure models each vectorization candidate as a plan whose trip-count expressions use `ElementCount` (minimum, scalable flag) rather than concrete integers [7]. Key transformations required for VLA:

- **Runtime trip-count expressions.** `llvm.vscale` and `elementcount` intrinsics materialize the unknown width; SCEV was extended to reason about `vscale`-parameterized recurrences.
- **Predicate-based tail handling.** Instead of scalar epilogues, the vectorizer emits `WHILELT`-style active-lane masks (SVE) or `vsetvli`-bounded remainders (RVV), vectorizing the tail *in the same loop*.
- **Speculative vectorization of early exits.** Search loops become first-fault/RDFFR or fault-only-first sequences via dedicated vectorizer support [7].

```llvm
; VLA vectorized loop: <vscale x 4 x i32>, trip count unknown
vector.body:
  %index = phi i64 [ 0, %entry ], [ %next, %vector.body ]
  %active = call <vscale x 4 x i1> @llvm.aarch64.sve.whilelt(...)
  %wide.load = call <vscale x 4 x i32> @llvm.masked.load(..., %active)
  %step = call i64 @llvm.vscale.i64()      ; runtime vscale
  %next = add i64 %index, mul i64 %step, 4
  %done = icmp eq i64 %next, %n
  br i1 %done, label %exit, label %vector.body
```

Auto-vectorization quality at variable length remains an active research frontier: cost models must be *width-parametric*, unroll factors interact with unknown `vscale`, and interleaving/access-pattern analyses that assumed constant trip counts need re-derivation. The historical record — from the 2016 scalable-vectorization RFC [7] through the 2018 SVE LLVM enablement threads to today's VPlan-based vectorizer — shows a discipline learning to treat the vector length as an *algebraic unknown* rather than a missing constant.

## 5 Empirical Evidence

Because this thesis is analytical, we ground its claims in published measurements rather than new benchmarks, and we specify the experimental protocol by which each claim could be falsified.

**Claim 1: Binary portability holds in practice.** The same RVV 1.0 binary executes correctly on VLEN=128 and VLEN=512 implementations. *Evidence:* the Ara2 paper [8] evaluates identical RVV 1.0 binaries across 2–16 lane configurations (varying effective VLEN), reporting correct execution with 95% average FPU utilization on compute-bound kernels.

**Claim 2: Strip-mining overhead is bounded and small.** The `vsetvli`/`WHILELT` negotiation costs O(1) instructions per chunk. *Evidence:* Ara2 [8] and Ara [5] (97% FPU utilization on 256×256 DGEMM, 16 lanes) demonstrate that configuration overhead does not prevent near-peak utilization on long vectors; short-vector efficiency degrades due to scalar issue-rate limits, not strip-mining per se.

**Claim 3: First-fault speculation vectorizes previously scalar loops.** *Evidence:* Arm's SVE whitepapers [2] report vectorized `strlen`/`strcmp`-class loops achieving near-memory-bandwidth performance on A64FX-class hardware, where NEON required scalar code.

**Claim 4: LMUL amortizes front-end cost.** *Evidence:* Ara2's PPA analysis [8] shows 37.8 DP-GFLOPS/W at 1.35 GHz with the slide unit (all-to-all permute) as the critical scaler; longer LMUL groupings increase arithmetic intensity per fetched instruction.

|---|---|---|---|
| Ara (22nm FD-SOI) | RVV 0.5 draft, 16 lanes | 97% FPU util (DGEMM 256²) | [5] |
| Ara2 (22nm FD-SOI) | RVV 1.0, 2–16 lanes | 95% avg FU util; 37.8 DP-GFLOPS/W | [8] |
| A64FX class | SVE 512-bit | ~2.7 TFLOP/s peak (literature) | [2] |

## 6 Limitations

1. **Ecosystem maturity.** RVV 1.0 ratification is recent; production-quality auto-vectorization for RVV in GCC/LLVM still trails SVE, and hand-written intrinsics remain common. SVE2's richer integer/DSP operations [3] widen the gap for non-HPC workloads.
2. **Heterogeneous-VLEN hazards.** "Write once, run everywhere" assumes *performance* portability, which does not follow from *correctness* portability. A binary tuned (via unrolling, LMUL choice, or software pipelining) for VLEN=512 may underperform on VLEN=128, and vice versa. Width-parametric cost models remain an open compiler problem.
3. **Predicate overhead on short vectors.** For trip counts below one full vector, predication setup (`PTRUE`, `WHILELT`, `vsetvli`) can exceed the arithmetic cost — the classic vector startup penalty, now paid in predicate registers rather than pipeline fill.
4. **Register-group fragmentation (RVV).** Aggressive LMUL=8 usage leaves only four register groups, spilling under register pressure; the compiler's `vsetvli`-minimization dataflow [6] is a heuristic, not optimal.
5. **Memory-system demands.** Both ISAs assume streaming-friendly memory; gather/scatter (`vluxei`/`LD1W` gather) and segmented accesses stress TLBs and prefetchers, and first-faulting gathers add FFR-management overhead per iteration.
6. **Verification burden.** Variable-length semantics multiply the formal verification state space: every instruction's behavior must be proven for all (VLEN, SEW, LMUL, vl, predicate) combinations, a known cost driver in RVV 1.0 core verification.

## 7 Conclusion

Scalable vector ISAs resolve the oldest tension in SIMD design — the coupling of vector width to binary compatibility — by promoting the vector length from an architectural constant to a runtime-negotiated quantity. RISC-V V and Arm SVE arrive at the same programming idiom, *predicate-guarded strip-mining*, through mirror-image mechanisms: RVV's explicit configuration state (`vtype`/`vsetvli`, LMUL register groups) versus SVE's implicit predicate arithmetic (`WHILELT`/`INCD`, P0–P15, FFR). First-faulting loads in both ISAs show that speculative, fault-tolerant vectorization is not an optimization but a *requirement* of the VLA contract, since trip counts and data-dependent exits are unknowable at compile time. On the compiler side, LLVM's `<vscale × N>` type system and VPlan vectorizer demonstrate that treating the vector length as an algebraic unknown — rather than a missing constant — yields portable, competitive code, though width-parametric cost modeling remains unfinished work. The empirical record (Ara/Ara2, A64FX-class SVE systems) confirms near-peak utilization is achievable; the open problems are performance portability across heterogeneous widths, short-vector efficiency, and ecosystem maturity. The scalable vector era's deepest lesson is architectural: *the most durable interface is not a width, but a protocol for discovering it.*
