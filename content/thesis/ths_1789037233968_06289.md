# Memory Consistency and Cache Coherence: MESI/MOESI Snooping, Directory Protocols for Many-Core Chips, TSO and Release Consistency, and the Formalized C++11 Memory Model

## Abstract

Shared-memory multiprocessors promise programmers the illusion of a single address space, but behind that illusion lie two distinct, subtle contracts: *cache coherence*, which governs how cached copies of a block stay mutually consistent, and *memory consistency*, which governs the order in which reads and writes by different processors appear to take effect. This thesis gives a unified, PhD-level treatment of both layers and their interaction. We develop the classical MESI and MOESI snooping protocols as state machines with precise bus-transaction semantics, extend them to directory-based coherence schemes (including bit-vector sharer lists, home-node forwarding, and network ordering) required by many-core chips, and then ascend to consistency models: Lamport's sequential consistency, the total-store-order model of x86 with its store-buffer operational semantics, and the release-consistency regime of ARM and Power. Finally, we examine the C++11 memory model — its formalization in Isabelle/HOL, the happens-before and release-sequence machinery, and the verified compilation of release/acquire primitives onto x86-TSO — showing how language-level atomics bridge the gap between hardware reality and portable concurrent programming.

## 1 Introduction

The shared-memory abstraction is one of the most successful lies in computer science. A program written for a *p*-processor machine reasons as though all threads touch one uniform memory, yet physically each core hides its working set behind private caches whose contents drift apart the moment two cores write to nearby addresses. Two separate specifications repair the lie. **Coherence** answers a per-location question: if several caches hold copies of block *b*, what values may each copy hold, and who arbitrates when one core writes? **Consistency** answers a global ordering question: which interleavings of multi-location reads and writes may a thread actually observe?

These layers are logically independent — a perfectly coherent machine can still have a wildly relaxed consistency model — yet they couple in practice: almost every consistency guarantee is implemented *through* the coherence protocol, via fences, barriers, or release/acquire annotations on coherence transactions. Misunderstanding either layer produces real defects: double-checked locking, correct on uniprocessors, breaks on relaxed hardware; Dekker's and Peterson's algorithms fail without sequential consistency; and single-threaded "as-if" compiler transformations become illegal when threads observe each other.

Our contribution is synthesis: we reconstruct the full stack, from the transistor-adjacent state machine of a snooping cache controller to the axiomatic formalization of the C++11 memory model, with enough rigor to implement from and enough empirical grounding to trust.

---

## 2 Background and Related Work

The classical foundation is Lamport's 1979 definition of **sequential consistency** (SC): a multiprocessor is sequentially consistent when "the result of any execution is the same as if the operations of all the processors were executed in some sequential order, and the operations of each individual processor appear in this sequence in the order specified by its program" [1]. SC matches the uniprocessor mental model but forbids the store buffers, speculative loads, and non-blocking caches that make modern processors fast.

Adve and Gharachorloo systematized the relaxed models vendors actually built, distinguishing *program-order* relaxations (which operation pairs a core may reorder) from *write-atomicity* relaxations (whether all cores observe a write simultaneously) [6]. Intel and AMD documented x86 behavior in ambiguous prose that was later shown unsound with respect to real silicon; Owens, Sarkar, and Sewell repaired this with **x86-TSO**, defined both operationally (per-thread FIFO store buffers) and axiomatically, formalized in HOL4 and validated against hardware [2][5].

Meanwhile, C and C++ had no defined concurrent semantics at all. C++11 introduced a memory model based on *happens-before*, *synchronizes-with*, and a per-location modification order, with six orderings from `memory_order_seq_cst` to `memory_order_relaxed`. Batty et al. gave the first mathematical formalization in Isabelle/HOL, exposed deep problems in the draft standard, and proved the standard x86 mapping of C++ atomics correct against x86-TSO [3]; Boehm's materials document the committee's intent and the "no benign data races" position [4]. We build on these sources, plus the Power/ARM mechanization literature and herd/litmus tooling, to present coherence and consistency as one engineering discipline.

## 3 Methodology

This thesis synthesizes **formal specifications, mechanized proofs, and empirical hardware observation**. Our method is threefold.

First, *specification reconstruction*: we restate MESI/MOESI and a representative directory protocol as labeled transition systems, exposing usually-implicit events (bus upgrades, intervention, transient states), with TLA+ fragments so the transition structure is machine-checkable.

Second, *operational and axiomatic modeling*: we present x86-TSO in the store-buffer style of [2], characterize release consistency via acquire/release partial orders, and develop the C++11 axiomatic model — candidate executions, reads-from and modification-order relations, coherence axioms — following [3].

Third, *empirical anchoring*: we draw on published litmus-test campaigns (thousands of small programs run millions of times on real x86, ARM, and Power silicon) and mechanized artifacts (HOL4 for x86-TSO, Isabelle/HOL for C++11) to separate *architecturally guaranteed* from *observed-but-unpromised* behavior.

> **Methodological note:** A memory model is a contract with two audiences — the programmer, who must know which outcomes are possible, and the implementor, who must know which optimizations are permitted. We judge every definition below against both: does it forbid the litmus outcomes programmers rely on, and does it permit the reorderings implementors require?

## 4 Deep Dive

### 4.1 Snooping Coherence: The MESI and MOESI State Machines

Consider *p* processors with private caches sharing a broadcast bus to memory. A **snooping protocol** requires every controller to observe all bus transactions and react. **MESI** names four stable states per line:

- **Modified (M):** only valid copy here; differs from memory; must write back on eviction.
- **Exclusive (E):** only valid copy here; matches memory; local writes proceed silently.
- **Shared (S):** valid copy, possibly replicated; matches memory; local write needs a bus upgrade.
- **Invalid (I):** no valid copy.

Processor events are `PrRd`/`PrWr`; bus events are `BusRd` (someone wants a shared copy), `BusRdX` (someone wants to write), and `BusUpgr` (I hold it shared and now want to write):

| State | PrRd | PrWr | BusRd | BusRdX / BusUpgr |
|---|---|---|---|---|
| M | hit | hit (stay M) | flush, → S | flush, → I |
| E | hit | hit, → M (silent) | → S | → I |
| S | hit | BusUpgr, → M | — | → I |
| I | BusRd, → S/E | BusRdX, → M | — | — |

Three subtleties matter. First, **E is a silent-write optimization**: exclusivity must be *guaranteed* by the bus (the `I → E` transition requires "no other cache asserted shared"), or silent writes corrupt. Second, `BusRdX` forces an M-owner to **flush** dirty data before invalidating — this flush-then-invalidate dance serializes writes to one location, yielding the *per-location write order* that consistency models build on. Third, the table is a skeleton: real controllers add transient states to handle races between overlapping transactions, plus **intervention** (cache-to-cache data supply) and silent eviction of clean S-lines.

**MOESI** adds **Owned (O)**: a dirty line that is *shared*. The owner supplies data on `BusRd` via intervention without writing back, deferring writeback to eviction — eliminating the M→S→M ping-pong of producer-consumer sharing (AMD's HyperTransport Opterons; Intel's MESIF instead designates one *Forwarder* among sharers). The price is complexity in writebacks and ownership transfer, historically discharged by Murφ model checking before tape-out.

A TLA+ fragment of one line's controller shows how the table becomes checkable:

```tla
------------------------------ MODULE MESI ------------------------------
EXTENDS Naturals
CONSTANTS Procs
VARIABLES state, bus

PrRd(p) ==
  /\ state[p] = "I"
  /\ \E q \in Procs \ {p} : state[q] \in {"M","E","S"}
  /\ state' = [state EXCEPT ![p] = "S"]
  /\ UNCHANGED bus

PrWrExclusive(p) ==          \* silent upgrade: no bus transaction
  /\ state[p] = "E"
  /\ state' = [state EXCEPT ![p] = "M"]
  /\ UNCHANGED bus

BusRdX(p) ==                 \* others invalidate; M-owner flushes
  /\ state' = [q \in Procs |-> IF q = p THEN "M" ELSE "I"]
  /\ bus' = "RdX"

Next == \E p \in Procs : PrRd(p) \/ PrWrExclusive(p) \/ BusRdX(p)
=============================================================================
```

Model-checking this for small *p* catches the classic bug: a `BusRd` to an M-line that flushes but forgets to downgrade to S, silently losing dirty data or leaving two owners.

### 4.2 Directory-Based Coherence at Scale: Beyond the Bus

Snooping scales poorly: every miss broadcasts to every cache, so bandwidth grows with *p²* and the broadcast medium becomes the bottleneck. **Directory-based protocols** replace broadcast with point-to-point messages mediated by a *directory* recording which caches hold each block. Two organizations dominate: **centralized** (one structure at the memory controller — simple but a hotspot) and **distributed** (address space partitioned across nodes; the *home node* of block *b* keeps *b*'s entry), as in the SGI Origin, AMD NUMA systems, and modern meshes where each tile hosts an LLC slice plus the directory for its home addresses.

A full-map entry holds a state (*Uncached* / *Shared* / *Exclusive*) and a **sharer bit-vector** of *p* bits. A read miss from node *n*: *n → home*; if the entry is *Exclusive* at owner *o*, home forwards to *o*, which supplies data and downgrades; home sets *n*'s bit. A write miss triggers **invalidation**: home sends point-to-point invalidates to every set bit, collects acknowledgments, then grants exclusivity. The invariant — *at most one writer or any number of readers per block* — is now maintained by message exchange, introducing **races**: simultaneous exclusive requests, or an invalidation crossing a fresh read in flight. Protocols handle these with transient states at requester and home (pending-ack counters, *IM*/*SM* states); verification shifts from "the bus serializes everything" to proving the distributed algorithm refines the atomic specification — the subject of landmark Murφ and TLA+ campaigns, where transient-state handling harbored most historical bugs.

Directory storage itself costs *O(p)* bits per line for full vectors, so production systems compress with overflow handling:

- **Limited-pointer (DirᵢB):** track up to *i* sharers explicitly; overflow falls back to broadcast.
- **Coarse vectors (DirᵢCVₖ):** each bit covers a *region* of *k* nodes; spurious invalidates stay correct.
- **Sparse lists:** store only actual sharer IDs; compact for the common low-sharing case.

On modern meshes the directory is typically *embedded in the LLC tag*, and coherence traffic rides a dedicated virtual network with deadlock avoidance (separate request/response classes or escape channels). Coherence at scale is thus a distributed algorithm over an on-chip network, and its design space — sharer-tracking precision, transient-state structure, network ordering assumptions — is where contemporary research lives.

### 4.3 Consistency Models: SC, TSO, and Release Consistency

**Sequential consistency** [1] demands a global interleaving respecting each thread's program order — the programmability gold standard and the performance enemy, forbidding store buffering, speculative loads, and most compiler reorderings.

**Total Store Order (TSO)**, the x86 model, relaxes exactly one program-order edge: *store followed by load* (to a different address) may appear reordered. Operationally, each hardware thread has a **FIFO store buffer** [2][5]: stores enqueue locally and drain asynchronously; loads check the thread's own buffer first (*read-own-write-early*, i.e., store-to-load forwarding) and otherwise read shared memory; `MFENCE` — or a `LOCK`'d instruction, which additionally acquires a global lock and drains the buffer — restores order. Axiomatically, TSO needs a total order over stores consistent with program order except for the store→load relaxation, plus the forwarding axiom. The canonical litmus test is **SB (store buffering)**:

```python
# SB litmus test: allowed under x86-TSO, forbidden under SC.
# Initially x = y = 0.
# Thread 0: x = 1; r0 = y      Thread 1: y = 1; r1 = x
# Outcome r0 == 0 and r1 == 0 is ALLOWED on x86
# (both stores still sit in their buffers) and FORBIDDEN under SC.
def sb_outcome_allowed(model: str) -> bool:
    return model == "TSO"   # SC forbids it; TSO observes it routinely
```

The `r0 = 0 ∧ r1 = 0` outcome is the *defining* observable difference between TSO and SC, seen routinely on real x86 silicon — which is why Dekker-style idioms need fences even on "strong" hardware.

**Release consistency** (RC) — the regime of ARM, Power, and RISC-V's weaker modes — relaxes further. In its lazy form (RCpc, adopted by C++ release/acquire), ordinary accesses are unordered across threads; order exists only at **synchronization operations**: a *release* store paired with an *acquire* load makes everything *before* the release visible to everything *after* the acquire. Message passing becomes correct with no fence on the fast path:

```rust
use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
static X: AtomicUsize = AtomicUsize::new(0);
static READY: AtomicBool = AtomicBool::new(false);
// thread A:                             // thread B:
X.store(42, Ordering::Relaxed);           while !READY.load(Ordering::Acquire) {}
READY.store(true, Ordering::Release);     assert_eq!(X.load(Ordering::Relaxed), 42);
// release/acquire synchronizes: the store to X happens-before the
// load of X, so the assert cannot fail. On x86 this compiles to plain
// MOV (TSO already suffices); on ARMv8 to STLR/LDAR.
```

| Model | Store→Load reorder | Ld→Ld / St→St reorder | Write atomicity | Targets |
|---|---|---|---|---|
| Sequential consistency | forbidden | forbidden | multi-copy atomic | idealized; `seq_cst` |
| TSO | **allowed** | forbidden | multi-copy atomic | x86-64 |
| Release consistency (RCpc) | allowed | allowed | multi-copy atomic | ARMv8, RISC-V RVWMO |
| Historic weak | allowed | allowed | **non-atomic** (IRIW) | pre-v8 ARM, old Power |

The last row records a genuine subtlety: old hardware could exhibit *non-multi-copy-atomic* behavior (the IRIW litmus test), where two readers disagree on the order of two independent writes — a phenomenon C++ deliberately forbids for `seq_cst` but which shaped a decade of formalization.

### 4.4 The C++11 Memory Model: Formalization and Verified Compilation

The C++11 model [3][4] is **axiomatic over candidate executions**: a set of *actions* (reads, writes, read-modify-writes, locks, fences); *sequenced-before* (intra-thread program order); *reads-from* (which write each read observes); and a per-location *modification order* over writes. From these derive *synchronizes-with* — a release store synchronizes with an acquire load reading from it or from its *release sequence* (the RMW chain it heads) — and *happens-before* as the transitive closure of sequenced-before and synchronizes-with.

An execution is *consistent* when it satisfies the **coherence axioms** (a read must not read from a write hidden by happens-before: if *r* reads from *w*, no write *w′* to the same location may satisfy *w* happens-before *w′* happens-before *r*), the RMW atomicity axioms, and — for `seq_cst` — a single total order *S* over all SC actions consistent with happens-before and modification order. A program has **undefined behavior** if any consistent execution contains a *data race*: two conflicting accesses, at least one a write and one non-atomic, unordered by happens-before. This yields the **DRF guarantee** — *data-race-free programs execute with sequential consistency*: write race-free code and reason under SC; use `relaxed` or release/acquire and you accept the axiomatic model in full [4].

Batty et al. mechanized the definition in Isabelle/HOL, built the **Cppmem** explorer enumerating candidate executions from the generated definitions, and proved the standard x86 compilation scheme (plain `MOV` for relaxed/release/acquire, `XCHG` or `MOV`+`MFENCE` for `seq_cst` stores, `LOCK`'d RMWs) **correct against x86-TSO** [2][3] — closing the loop: the language model runs on real hardware with no hidden fences on the fast path.

> **Theorem (DRF-SC, informal):** If every sequentially consistent execution of a C++11 program is data-race-free, then every execution the axiomatic model admits is equivalent to a sequentially consistent one. *In practice:* compiler and hardware may exploit the model's full weakness only for programs whose defined executions are already racy.

The formalization also exposed real defects — the **out-of-thin-air** problem (may a relaxed read observe a value no thread wrote?) and the over-strict `consume` ordering — driving C++20 revisions. Formalization here was not academic ornament; it changed the standard.

## 5 Empirical Evaluation and Proofs

Memory models are contracts about *observable outcomes*, so the field's empirical method is the **litmus test**: a tiny program (2–4 threads, a handful of accesses) whose final state is classified per model. The Cambridge *litmus*/*herd* tools generate thousands of tests from axiomatic models and run each millions of times on real hardware:

1. **x86-TSO validation:** Owens et al. ran extensive suites on Intel and AMD silicon; every observed behavior was admitted by x86-TSO, and model-admitted-but-unobserved behaviors traced to microarchitectural conservatism, not unsoundness [2][5]. The SB outcome is observed routinely.
2. **ARM/Power campaigns:** Sarkar et al. ran tens of thousands of litmus tests, discovering undocumented behaviors (including barrier cumulativity subtleties) and refining models until prediction matched observation — genuinely empirical semantics [6].
3. **Cppmem exploration:** enumerating candidate executions from the Isabelle/HOL definitions exposed counterexamples to the draft standard's coherence rules, fixed before finalization [3].
4. **Protocol verification:** snooping and directory protocols have been Murφ/TLA+ model-checked for decades; directory work is notable for verifying *transient-state* races, where most historical bugs lived.

Mechanization is strong but partial: x86-TSO's operational/axiomatic equivalence is proved in HOL4 [2]; C++11 metatheory including DRF-SC for the core fragment is mechanized in Isabelle/HOL and Coq [3]; but the full model with `consume` and repaired out-of-thin-air axioms remains an active target, and verified ARMv8 `LDAR`/`STLR` compilation schemes came only after that architecture's model stabilized.

## 6 Limitations and Open Problems

1. **Out-of-thin-air reads.** The standardized model arguably permits relaxed reads to observe values no thread ever wrote, because axiomatic style constrains *which* write a read sees but not *circular justification*. Fixes (dependency-based or operational models) complicate the standard or break optimizations; C++20 deprecated `memory_order_consume` in response, and the problem is not fully closed.
2. **Heterogeneous coherence.** Modern SoCs mix CPU MESI domains, GPU weak-coherence domains, and accelerators with software-managed coherence, joined by protocols (ARM CHI, CXL.cache) the classical taxonomy strains to describe. A unified, verified account of *cross-domain* coherence with per-domain consistency models is missing.
3. **End-to-end verification.** Proofs cover single protocols and single models, but the full stack — C++ axiomatic model → compiler mapping → ISA model → coherence protocol → RTL — has never been verified end-to-end; each layer assumes the one below, and the assumptions do not always compose.
4. **Cost models.** Consistency models specify *allowed* reorderings, not their cost; architects lack a predictive theory linking model strength to achievable memory-level parallelism, so model selection stays partly empirical.
5. **Persistence and CXL.** Byte-addressable persistent memory adds *durability* ordering (persist barriers, flushes) orthogonal to visibility ordering; the interplay of coherence, consistency, and crash-consistency in disaggregated CXL memory is largely unexplored.

---

## 7 Conclusion

Cache coherence and memory consistency are the two halves of the shared-memory contract: coherence serializes access to each location — MESI and MOESI on snooping buses, directory schemes with sharer tracking and transient-state discipline on many-core fabrics — while consistency defines which global reorderings programs may observe, from sequential consistency through x86's store-buffer TSO to release consistency's acquire/release discipline. The C++11 memory model, formalized in Isabelle/HOL and proved compilable to x86-TSO, shows how a language can offer both a simple DRF-SC guarantee for ordinary code and razor-thin relaxed primitives for experts. The deepest lesson of this literature is methodological: *memory models must be written as mathematics and tested as physics* — formalized in proof assistants, then confronted with millions of litmus executions on real silicon. Wherever the two disagreed, the hardware, the prose specifications, and eventually the standard itself had to change.
