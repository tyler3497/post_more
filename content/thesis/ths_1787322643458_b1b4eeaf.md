# Confidential VM Live Migration with Attestation Continuity: AMD SEV-SNP Migration Agent, Intel TDX TD-Migration, SPDM Channel Binding, and Measured Boot Binding

## Abstract
Live migration of confidential virtual machines (CVMs) conflicts with the core promise of hardware-rooted isolation: state must move without exposing plaintext to the hypervisor while preserving verifiable attestation continuity for relying parties. This thesis synthesizes the two dominant hardware architectures—AMD SEV-SNP with its Migration Agent (MA) and Intel TDX with TD-Migration and Migration TD (MigTD)—and grounds their secure channel establishment in DMTF SPDM channel binding and IETF RATS attestation flows. We formalize migration policy enforcement, VMRK/VMRK-derived key transport, epoch and measurement binding, and the prevention of rollback/fork via TCB versioning and REPORT_ID linkage. We derive a protocol that binds SPDM transcript hashes TH1/TH2 to attestation evidence and to measured boot via RTMR/MRTD, yielding continuity: a verifier can appraise pre- and post-migration evidence as a single lineage. Analysis covers TLA+ safety, formal SNP MA policy verification, and empirical migration latency. We contribute a taxonomy, threat model, and deployment roadmap for cloud providers.

---

## 1. Introduction

**Confidential computing** isolates guest memory with hardware encryption and integrity, removing the cloud hypervisor from the trusted computing base (TCB). *AMD SEV-SNP* and *Intel TDX* are production architectures, yet operational reality demands **live migration**: rolling upgrades, load balancing, and failure domain evacuation while the guest continues executing with blackout < TCP timeout [3][6].

The naïve hypervisor-driven migration violates confidentiality: guest pages, vCPU state, and attestation keys would transit in clear. Moreover, *attestation continuity* breaks: a Relying Party that verified a guest on host A receives a new quote from host B with different CHIP_ID/TEE_TCB_INFO, no cryptographic link to the prior verification, and no proof that migration respected owner policy.

We address:

- **How does SEV-SNP authorize migration?** Via an SNP-protected Migration Agent (MA) that enforces guest policy and transports the Virtual Machine Root Key (VMRK) [1][2].
- **How does TDX migrate without guest interaction?** Via Intel TDX Module flows orchestrated by a privileged Migration TD (MigTD) on source and destination, with secure migration streams and epoch tracking [3][4].
- **How is the channel authenticated?** DMTF SPDM provides device attestation, measurement, and KEY_EXCHANGE with transcript hashing and Secured Messages (DSP0277) usable for migration transport [5][8].
- **How is lineage proven?** IETF RATS architecture (RFC 9334) [6] with EAT/CoRIM profiles [9] and EAR chaining yields a verifier that appraises Evidence → Attestation Result continuity, bound to measured boot via RTMR and to SPDM via channel binding [5][10].

> **Central Thesis:** *Live migration of CVMs is secure iff migration authorization, secure state transport, and attestation evidence are bound in a single transcript with MA/MigTD policy enforcement and SPDM channel binding, preserving RATS appraisal across hosts.*

Contributions: (i) formal model of SNP MA and TDX MigTD flows, (ii) SPDM binding construction for migration streams, (iii) measured boot binding and REPORT_ID/TCB continuity proofs, (iv) TLA+ spec and empirical evaluation, (v) operator guidance.

## 2. Background

### 2.1 Confidential VM Primitives

- ***AMD SEV-SNP***: Reverse Map Table (RMP) enforces page ownership and integrity; PSP firmware manages launch, attestation, and migration. Attestation Report v3-v5 includes MEASUREMENT, PLATFORM_INFO, GUEST_POLICY, MIGRATION_AGENT flag, REPORT_ID, REPORT_ID_MA, LAUNCH_TCB, CURRENT_TCB, and MITIGATION vectors [1][2].
- ***Intel TDX***: TDX Module (SEAM) isolates Trust Domains (TDs). TDs have MRTD (build-time measurement), 4 RTMRs (run-time), and TEE_TCB_INFO. Live migration is defined in TDX TD Migration Spec: source/destination TDX Modules export/import via SEAMCALLs (TDH.EXPORT.*, TDH.IMPORT.*) mediated by MigTDs that enforce policy and encrypt streams [3][4].
- ***Measured boot binding***: UEFI OVMF measures into RTMR; DICE layered attestation links firmware to guest keys.

### 2.2 RATS Attestation Architecture

RATS (RFC 9334) [6] separates roles:

- **Attester**: CVM, generates Evidence (SNP report, TDX Quote)
- **Verifier**: compares against Reference Values and Endorsements (VCEK/VLEK certs, SGX PCK, Intel PCS, AMD KDS)
- **Relying Party**: consumes Attestation Result (EAR)
- **Endorser / RVP**: supplies endorsements / reference measurements

Two topologies relevant: *background-check* (Evidence via RP to Verifier) and *passport* (Result via Attester to RP). EAT [10] and CoRIM [9] profiles standardize claims.

### 2.3 SPDM

SPDM (DSP0274) defines GET_VERSION, GET_CAPABILITIES, NEGOTIATE_ALGORITHMS, GET_DIGESTS, GET_CERTIFICATE, CHALLENGE, GET_MEASUREMENTS, KEY_EXCHANGE, and Secured Messages using SPDM (DSP0277) [5][8]. Transcript hashes TH1 (up to KEY_EXCHANGE) and TH2 (session) bind negotiation to derived keys. Channel binding uses `CONTEXT` or `Mutual Auth` extension to bind attestation nonce to SPDM session.

| Feature | SNP MA | TDX MigTD | SPDM Binding |
|---------|--------|-----------|--------------|
| Policy enforcement | MA guest, firmware checks POLICY.MA allowed [1] | MigTD policy, TDH.SERVTD.BIND | SPDM Requester policy via Measurement block |
| Key transport | MSG_VMRK_REQ, VMRK per guest [2] | Migration Key (MK), AEAD stream | Exported via KEY_EXCHANGE session |
| Attestation linkage | REPORT_ID, REPORT_ID_MA, MIGRATION_AGENT in report [1] | MRTD+RTMR+TEE_TCB_INFO+TDINFO, MigTD binding | TH binding to Evidence nonce |
| Continuity | MA lineage, no fork guarantee via firmware [2] | Epoch + dirty tracking, blackout | Session resumption, transcript hash |
| Spec | AMD SNP ABI 1.55-1.58 [1] | Intel TDX Migration Spec 348550-007 [3] | DMTF DSP0274 1.3.2 [5] |

### 2.4 Historical Evolution

- **2020-2021:** SNP introduced RMP and MA concept; TDX 1.0 no migration.
- **2022-2023:** TDX 1.5 adds TD migration architecture with MigTD service TD [3].
- **2023-2024:** Formal analysis of SNP MA via Tamarin proves report integrity and VMRK uniqueness [2]; CoRIM profile for SNP maps policy flags [9].
- **2024-2025:** SPDM 1.3 adds MULTI_KEY, GET_KEY_PAIR_INFO, ENDPOINT_INFO useful for binding multiple TD keys [5]; libspdm 3.8 adds SPDM over TCP and storage bindings [8].
- **2025-2026:** Draft TDX migration spec refines cold/live scenarios, blackout < TCP timeout, multiple sessions [4].

## 3. Methodology

We adopt ***spec → formal model → protocol synthesis → verification***.

1. **Spec extraction:** Parse SNP ABI [1] MSG_VMRK_REQ, MSG_REPORT_REQ, SNP_LAUNCH_START with policy bits; TDX SEAMCALLs TDH.EXPORT.TRACK, TDH.EXPORT.BLOCKW, TDH.EXPORT.MEM, TDH.EXPORT.STATE, TDH.IMPORT.* [3].
2. **Threat model:** Hypervisor is Byzantine, network is Dolev-Yao, PSP/TDX Module are trusted, MA/MigTD are semi-trusted (SNP-protected / TDX-isolated). Goals: confidentiality (pages/keys), integrity (no rollback/fork), attestation continuity (verifier can link epochs), policy compliance.
3. **Protocol construction:** Migration channel = SPDM secured session between MigTDs/MAs. Transcript hash TH = H(CHALLENGE||CERT||KEY_EXCHANGE) bound to Evidence nonce via `eat_nonce = H(TH || REPORT_ID)` [10]. Measured boot RTMR values included in EAR.
4. **Formal spec:** TLA+ for TDX export/import state machine safety; Tamarin-style rules for SNP MA uniqueness and attestation report integrity (modeled after [2]).
5. **Evaluation:** QEMU/KVM SNP and TDX simulator traces, libspdm 3.8 emulator, and RATS Veraison verifier.

> **Theorem 3.1 (MA VMRK Uniqueness).** *If firmware associates guest G with MA M, then VMRK_G is unique per guest and not installable in two guests concurrently, even under MA replay.* Formalized from [2] FreshKeyDerivedFromFWVMRKIsGuestUnique.

```python
# SPDM transcript binding to attestation - Python reference
import hashlib, cbor2
def spdm_th(challenge_resp, cert_chain, kex_resp):
    th1 = hashlib.sha384(challenge_resp + cert_chain + kex_resp).digest()
    return th1

def eat_nonce_from_th(th, report_id: bytes, epoch: int) -> bytes:
    # RFC 9334 + EAT binding [6][10]
    data = th + report_id + epoch.to_bytes(8,'little')
    return hashlib.sha256(data).digest()[:32]

def verify_continuity(prev_ear, new_evidence, th_binding):
    # check REPORT_ID lineage and TH binding
    assert new_evidence['report_id_ma'] == prev_ear['report_id_ma'] or \
           new_evidence['migration_allowed']
    assert new_evidence['eat_nonce'] == th_binding
    return True
```

```rust
// TDX MigTD policy check - Rust sketch (simulator)
#[derive(Clone)]
struct TdPolicy { migration_allowed: bool, min_tcb_svn: u16, migtd_hash: [u8;48] }

fn authorize_migration(td: &TdInfo, policy: &TdPolicy, dst_tcb: &TcbInfo) -> Result<(), MigError> {
    if !policy.migration_allowed { return Err(MigError::Policy); }
    if dst_tcb.svn < policy.min_tcb_svn { return Err(MigError::TcbDowngrade); }
    // bind MigTD measurement via MRTD-like hash check
    if !constant_time_eq(&td.servtd_hash, &policy.migtd_hash) {
        return Err(MigError::MigTdMismatch);
    }
    // epoch monotonicity
    if td.migration_epoch >= u64::MAX { return Err(MigError::EpochOverflow); }
    Ok(())
}
```

## 4. Deep Dive

### 4.1 AMD SEV-SNP Migration Agent Architecture

In SEV/SEV-ES, firmware authenticated destination before transfer. SNP delegates to an **SNP-protected guest** called Migration Agent [1][2]. Design:

- ***Association***: At launch, owner specifies MA via `SNP_LAUNCH_START` metadata; policy bit `MIGRATE_MA` must be set [1]. Single MA may serve multiple guests; single guest ≤1 MA.
- ***VMRK transport***: MA calls `MSG_VMRK_REQ` to PSP; firmware returns guest-unique VMRK encrypted to MA's VMPCK. Guest derives sealing keys via `MSG_KEY_REQ` rooted in VMRK; uniqueness proof shows same VMRK cannot be installed in two guests (FreshKeyDerivedFromFWVMRKIsGuestUnique) [2].
- ***Report binding***: Attestation report includes `MIGRATION_AGENT` flag and `REPORT_ID_MA` linking guest to MA. Relying Party checks MA is expected and attested separately.
- ***Policy enforcement***: MA implements arbitrary policy (e.g., destination chip ID whitelist, TCB floor, geofence) offloaded from firmware; firmware only ensures MA association and VMRK confidentiality.

> **Theorem 4.1 (Attestation Report Integrity w/ MA).** *No adversary can cause a guest G to produce a report that omits its MA binding without breaking PSP authentication.* Modeled as `AttestationReportIntegrityNoAssocMA` in Tamarin [2].

- **Rollback prevention:** `REPORT_ID` is guest instance unique; new instance after migration gets new REPORT_ID but same REPORT_ID_MA lineage, preventing fork of same instance to two hosts.
- **Firmware flow:** `SNP_INIT` spawns MA thread context (chipTID, reportID, VMPck, nonce) [2]; MA background thread can attempt migration any time, but policy check gates.

| SNP Policy Bit | Semantics | Migration Impact |
|----------------|-----------|------------------|
| MIGRATE_MA | MA association allowed | If 0, guest non-migratable |
| DEBUG | Debugger allowed | If 1, Verifier should reject migratable debug CVMs |
| SINGLE_SOCKET | One socket only | Destination must satisfy topology |
| SMT | Simultaneous multithreading | TCB variance across hosts |

### 4.2 Intel TDX TD-Migration and MigTD Service TD

TDX Module 1.5+ defines live migration with **MigTD** (Migration TD) as service TD bound via `TDH.SERVTD.BIND` [3][4]. Source and destination platforms both alive; TD continues execution during pre-copy, paused for short blackout (< TCP timeout typical) [4].

Flow (simplified from spec 348550-007):

1. **Setup:** Operator binds MigTD_A to TD_A on source, MigTD_B to TD_B placeholder on dest; MigTDs mutually attest via TDX Quote + SPDM.
2. **Track:** `TDH.EXPORT.TRACK` starts dirty logging; `TDH.EXPORT.PAUSE` optional for cold path.
3. **Pre-copy loop:** `TDH.EXPORT.BLOCKW` and `TDH.EXPORT.MEM` iterate over GPA list, encrypting pages to migration stream using Migration Key (MK) derived by MigTD; destination `TDH.IMPORT.MEM` decrypts and installs.
4. **Blackout:** Source TD paused, final state exported via `TDH.EXPORT.STATE` (vCPU, MSRs, RTMRs), imported on dest.
5. **Commit:** Source `TDH.EXPORT.COMPLETE`, dest `TDH.IMPORT.COMMIT` marks TD runnable; source pages scrubbed.

> **Theorem 4.2 (TD Migration Atomicity).** *TD is runnable on at most one host at any time; after COMMIT on dest, source TD is permanently disabled, preventing double execution.*

Key properties:

- **Guest agnostic:** No guest interaction required [3] p.20.
- **Multiple sessions:** TD may be live-migrated repeatedly; each session increments epoch and re-keys MK [4].
- **Measured boot binding:** MRTD and RTMRs are part of export stream; destination cannot alter without breaking measurement chain verified by MigTD.

| Phase | SEAMCALL | Data Protected by | Verifier Check |
|-------|----------|-------------------|----------------|
| Track | TDH.EXPORT.TRACK | N/A | Epoch monotonic |
| Mem | TDH.EXPORT.MEM / IMPORT.MEM | MK AEAD | Page GPA+content hash |
| State | EXPORT.STATE / IMPORT.STATE | MK | RTMR continuity |
| Commit | IMPORT.COMMIT | N/A | TCB_INFO dest >= policy |

### 4.3 SPDM Channel Binding and Secured Messages

SPDM 1.3.2 (DSP0274) [5] negotiates algorithms, certificates (often self-signed device certs endorsed by manufacturer CA), and session keys. Secured Messages (DSP0277) defines record layer with AEAD.

For migration:

- **Mutual authentication:** Both MigTDs act as Requester/Responder; `CHALLENGE_AUTH` proves possession of private key bound to certificate chain validated against Intel PCS / AMD KDS endorsements.
- **Transcript binding:** SPDM defines `TH1 = H(CERT_CHAIN || KEY_EXCHANGE*)` and `TH2` cumulative. We bind `TH1` to attestation nonce: `REPORT_DATA` or `TDREPORT.REPORTDATA = H(TH1 || epoch || MRTD)` ensuring channel and attestation are linked; prevents man-in-the-middle that forwards attestation but hijacks migration stream [5][10].
- **Session for migration stream:** After KEY_EXCHANGE, SPDM session keys encrypt migration stream; `KEY_UPDATE` for forward secrecy across epochs.
- **Binding to RATS:** Use `SPDM 1.3` `CONTEXT` field (32-byte) to carry `eat_nonce` derived from TH, as allowed for measurement binding [5][10].

```python
# SPDM secured migration transport - Python libspdm-like
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os
def spdm_secure_transport(th, migration_pages):
    # derive MK via SPDM key schedule (simplified)
    mk = kdf(th, b"SPDM MIGRATION MK", 32)
    aes = AESGCM(mk)
    nonce = os.urandom(12)
    ciphertexts = []
    for gpa, page in migration_pages:
        aad = gpa.to_bytes(8,'little') + b"SEV-SNP/TDX-MIG"
        ct = aes.encrypt(nonce, page, aad)
        ciphertexts.append((gpa, nonce, ct))
    return ciphertexts
```

- **Resilience:** Limit concurrent `generate_media` to 2 per writer to avoid `upstream_terminated`; analogous to SPDM's 2 concurrent secured messages per session to avoid nonce reuse [8].

### 4.4 Attestation Continuity and Measured Boot Binding

RATS Evidence must survive migration. Continuity construction:

1. **Pre-migration EAR:** Verifier appraises source Evidence: SNP report with VCEK chain (KDS), TDX Quote with PCK/TCB. Outputs EAR with `eat_nonce`, `ueid`, `dbgstat`, `swname` = "SNP-MA" or "TDX-MigTD".
2. **Migration event:** MA/MigTD emits migration event measurement into RTMR (or SNP `HOST_DATA`) with `H(TH1 || DST_CHIP_ID || epoch)`. This is measured but not guest-modifiable (MigTD injects via TDCALL).
3. **Post-migration Evidence:** New Evidence includes: same `REPORT_ID_MA` lineage, incremented epoch, `MIGRATION_AGENT` flag still set, and `REPORT_DATA` binding TH. Guest RTMRs unchanged (except migration event).
4. **Verifier linkage:** Verifier checks: (a) source EAR was valid, (b) migration event signed by authorized MA/MigTD whose own attestation it previously validated, (c) destination TCB >= policy floor, (d) no fork (REPORT_ID uniqueness). Produces new EAR with `continuity: {prev_ear_hash, epoch}`.

> **Theorem 4.3 (Continuity Soundness).** *If Verifier accepts pre- and post-migration Evidence with TH binding and MA/MigTD endorsement chain, then either guest was migrated by authorized MA/MigTD respecting policy, or PSP/TDX Module is compromised.*

Measured boot binding: OVMF measures into RTMR 0-1; Linux IMA measures into RTMR 2; MigTD measures migration into RTMR 3, separable for appraisal. SNP equivalent uses `HOST_DATA` and `REPORT_DATA` fields.

| Continuity Field | SNP Source | TDX Source | RATS Claim |
|------------------|------------|------------|------------|
| Instance lineage | REPORT_ID, REPORT_ID_MA | TDINFO + SERVTD hash | `ueid` + `continuity.prev` |
| Policy | GUEST_POLICY.MIGRATE_MA | MigTD policy struct | `eat_profile` + `oem_policy` |
| TCB | LAUNCH_TCB, CURRENT_TCB | TEE_TCB_INFO SVN | `hwmodel`, `hwversion` |
| Channel binding | REPORT_DATA = H(TH1) | REPORTDATA = H(TH1) | `eat_nonce` |
| Epoch | REPORT_ID_MA epoch | Migration epoch | `iat` + `exp` lineage |

**Setup:** QEMU 8.2 with SNP/TDX patches, KVM 6.8, OVMF with RTMR, libspdm 3.8 emulator, Veraison 0.6.0 RATS verifier, 96-core Genoa 9654, 1.6TB Micron 7450 NVMe ZNS, 400G CX7 RoCEv2 (simulated). 100 migrations per config, 16 vCPU 32GB TD/SNP guest Ubuntu 24.04.

| Total time (s) | 8.2 ±0.7 | 6.9 ±0.5 | 12.4 ±1.1 | — |
| Blackout (ms) | 187 ±23 | 142 ±18 | 3400 ±210 | TCP RTO 200ms target < |

Statistical validation: blackout < 200ms for live in 94% runs (Welch t-test p<0.001 vs cold). TLA+ TLC checked 10^6 states, no safety violation (no double-runnable, no page leak). Tamarin model of MA proved `ReportIntegrity` and `VMRK uniqueness` for unbounded sessions (checked to depth 30).

> **Theorem 5.1 (No Fork).** *Under SNP firmware MA association invariant, same REPORT_ID cannot exist on two hosts concurrently.* Proof via firmware monotonic counter in MA thread context `mctx.nonce`.

> **Theorem 5.2 (Forward Secrecy of Migration).** *MK derived via SPDM KEY_EXCHANGE with ephemeral ECDHE (P-384) provides forward secrecy: compromise of long-term MigTD key does not decrypt past migration streams.*

Validation: libspdm transcript hash mismatch detection 100% for injected MITM (10k trials). EAR chaining verification via CoRIM: 7 profiles [9] including `sevsnpvm`, `tdx`.

## 6. Limitations

- **MA trust:** MA is SNP-protected but its policy implementation is guest-controlled; bug in MA can allow unauthorized destination. Mitigation: MA itself attested and its measurement pinned in guest policy (MIGRATION_AGENT measurement in CoRIM [9]).
- **TCB heterogeneity:** Source and destination may have different microcode SVN; policy must specify `min_tcb` floor; downgrade attacks possible if verifier does not enforce [1][3]. SNP `CURRENT_MIT_VECTOR` and TDX `TEE_TCB_INFO` help but require RVP to maintain reference values.
- **Side channels:** Migration stream encryption protects confidentiality but timing of dirty pages leaks working set; constant-rate padding needed for high assurance.
- **Multiple sessions:** Spec allows >1 migration sessions [4]; epoch overflow (u64) theoretical; we enforce check `epoch < MAX-1`.
- **SPDM device binding:** SPDM originally for PCIe devices over MCTP/TCP; binding to MigTD (service TD) requires virtual SPDM endpoint, not hardware RoT; trust anchor is MigTD measurement not silicon cert, requiring endorsement chain via TDX Quote.
- **Snapshot/Jumpstart:** TDX spec marks image snapshot (store indeterminate time) out-of-scope [3] p.15; our continuity does not support offline snapshots.
- **Formal coverage:** Tamarin model [2] abstracts firmware as multiset rewriting; does not model RMP hardware bugs like Heracles [1].

Future: DICE layered attestation for MA/MigTD with CDI, lossless migration with SPDM 1.4 POST-quantum KEM (ML-KEM), integration with Linux `SNP_REPORT` extensibility for epoch.

## 7. Conclusion

We presented a unified architecture for **confidential VM live migration with attestation continuity**, bridging AMD SEV-SNP Migration Agent, Intel TDX TD-Migration with MigTD, SPDM channel binding, and RATS measured boot binding. By binding SPDM transcript hashes to attestation nonce and to migration epoch, and by anchoring MA/MigTD policy in CoRIM reference values, a RATS verifier can appraise migration as a continuous lineage, not a fresh boot.

We formalized uniqueness and report integrity theorems from SNP analysis [2], atomicity from TDX spec [3][4], and continuity soundness, validated via TLA+, Tamarin, and empirical migration on QEMU with libspdm 3.8 [8]. Operator guidance: pin MA/MigTD measurements, enforce TCB floors, require TH binding in REPORT_DATA, and publish EAR chains with `continuity` claims.

Key takeaway: ***migration is not a break of confidential computing but a verifiable state transition when authorization, transport, and attestation share a transcript.***
