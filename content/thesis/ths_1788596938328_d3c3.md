# Kernel-Bypass User-Space Networking Stacks: DPDK Poll-Mode Drivers, mTCP, and Demikernel for Microsecond-Scale RPC Serving

## Abstract

Modern datacenter applications demand remote procedure call latencies in the low single-digit microseconds and per-core throughputs exceeding ten million requests per second, yet the conventional Linux kernel network stack imposes irreducible costs — interrupts, context switches, socket locks, per-packet allocations, and data copies — that dominate latency once wire times fall below a microsecond. This thesis presents a systematic study of kernel-bypass user-space networking. We analyze three landmark systems: the Data Plane Development Kit (DPDK) with its poll-mode drivers, the mTCP user-level TCP stack (NSDI 2014), and the Demikernel library-OS architecture (SOSP 2021). We develop an analytical cost model decomposing per-packet latency into attributable stages, survey the protection trade-offs of IX (OSDI 2014) and the common-case methodology of eRPC (NSDI 2019), and position XDP and io_uring as the kernel-integrated middle ground. Empirically, bypass cuts median small-message latency by roughly an order of magnitude: eRPC achieves 2.3 µs median RPC latency and 10 million RPCs per second per core on lossy Ethernet. We formalize batching amortization and latency lower bounds, and close with limitations and a device-portable libOS agenda.

## 1. Introduction

The datacenter of the 2020s is a machine of *killer microseconds* [5]. Round-trip times within a rack have fallen below two microseconds on modern 100 GbE fabrics, yet application-observed RPC latencies stubbornly remain an order of magnitude larger. The discrepancy is not in the wire; it is in the software. Every packet that traverses the Linux kernel network stack pays a toll at each layer of a deeply general machinery: the NIC raises an interrupt, the driver allocates an `sk_buff`, the packet climbs through IP, TCP, and socket layers under coarse locks, and the payload is copied into a user buffer before a context switch returns control to the application. Measurements of this stack show that raising the emulated network latency increases TCP-layer cycles per packet by 157% and system-call-layer cycles by 250%, evidence that software overhead, not propagation delay, governs performance [3].

Kernel bypass is the architectural response: remove the kernel from the I/O datapath entirely. By granting user-space processes direct, memory-mapped access to NIC descriptor rings and DMA regions — mediated at setup time by IOMMU-backed drivers such as VFIO or UIO — applications can poll for packet arrivals, process them to completion on dedicated cores, and transmit without a single system call or interrupt. This thesis studies three systems that define the design space: **DPDK**, the industry-standard framework of poll-mode drivers and run-to-completion execution [1]; **mTCP**, a user-level TCP stack that delivered 33%–320% application speedups over Linux TCP (NSDI 2014) [2][3]; and **Demikernel**, a library-OS architecture abstracting heterogeneous kernel-bypass devices behind one portable datapath interface (SOSP 2021) [5][6].

Our central claim is that kernel bypass is not merely a performance hack but a *re-architecture of the operating system's I/O plane*: the dataplane moves into application space while the control plane — configuration, scheduling, resource management — remains in or near the kernel. We formalize this separation, quantify its costs and benefits, and identify the conditions under which bypass strictly dominates kernel-integrated alternatives such as XDP and `io_uring`.

## 2. Background

### 2.1 The anatomy of kernel network overhead

The Linux receive path for a single TCP segment can be decomposed into six attributable cost centers:

| Stage | Mechanism | Approximate cost |
|---|---|---|
| Interrupt delivery | NIC raises IRQ; CPU exits idle, runs ISR | 1–3 µs |
| Driver + NAPI | Softirq processes descriptor ring, allocates `sk_buff` | 0.5–1 µs |
| Protocol processing | IP/TCP traversal, socket lookup under locks | 1–4 µs |
| Scheduling | Wakeup of blocked receiver thread, context switch | 2–5 µs |
| Data copy | `sk_buff` → user buffer via `copy_to_user` | 0.5–2 µs (size-dependent) |
| System call | `recv()`/`epoll_wait()` trap and return | 0.2–0.5 µs |

The totals are sobering: even on fast hardware, a well-tuned kernel delivers small-packet RPC service at 10–50 µs of *software* latency, an order of magnitude above the ~1 µs wire time of a modern fabric [7]. Worse, the costs are heavy-tailed: interrupt coalescing, scheduler jitter, and lock contention inflate the 99th percentile far beyond the median.

### 2.2 A taxonomy of bypass designs

Kernel-bypass systems differ along three axes: **where the stack lives**, **what guarantees it offers**, and **what it sacrifices**.

- **User-space driver frameworks (DPDK).** The NIC is detached from the kernel driver and bound to VFIO/UIO; a user-space poll-mode driver owns the descriptor rings. The application links a run-to-completion loop against the DPDK Environment Abstraction Layer (EAL). There is no TCP stack included — DPDK is packet I/O, not a socket API [1].
- **User-space protocol stacks (mTCP, Seastar).** A complete TCP/IP implementation runs in user space atop a packet-I/O layer (mTCP uses a modified Intel `ixgbe` driver derived from the PSIO framework). Applications are ported to a BSD-socket-like API (`mtcp_socket`, `mtcp_epoll_wait`) with, in mTCP's case, fewer than 100 lines changed in lighttpd [2].
- **Protected dataplanes (IX).** IX argued that bypass need not mean the *kernel's* disappearance: it separates a dataplane kernel (running on dedicated cores, polling NIC queues, processing packets to completion with adaptive batching) from a control-plane Linux kernel, using hardware virtualization for protection. IX saturated a 10 GbE link with only 3 cores and delivered 8.8 million messages/s — 1.9× mTCP and 8.8× Linux [7].
- **Library-OS datapaths (Demikernel).** Demikernel goes further: a single high-level I/O abstraction (DemiAPI) implemented by multiple *libOSes* — `catnap` (kernel TCP fallback), `catnip` (Rust, DPDK/XDP), `catpowder` (FPGA/RDMA) — over a portable datapath interface (PDPIX) that unifies memory registration, scatter-gather, and queue-pair semantics across heterogeneous devices [5].

### 2.3 The kernel-integrated counterpoint

Two Linux mechanisms compete with full bypass. **XDP** (eXpress Data Path) runs eBPF programs at the earliest point in the driver receive path, enabling packet filtering and forwarding at millions of packets per second without leaving the kernel — but it cannot terminate TCP in user space without AF_XDP socket handoff, which reintroduces copies. **`io_uring`** amortizes system-call cost by batching submissions and completions through shared rings, cutting per-I/O syscall overhead to near zero while keeping the kernel stack itself. Both reduce *some* cost centers of §2.1 but leave protocol processing, `sk_buff` allocation, and scheduling intact. The question this thesis answers quantitatively is: *how much of the remaining software latency is essential, and how much is removable?*

## 3. Methodology

Our analysis proceeds in three stages. First, we construct an **analytical cost model** that expresses per-packet service time as a sum of stage costs plus a batching-amortization term, allowing us to predict the latency and throughput of each architecture from its structural choices. Second, we conduct a **comparative design analysis** of DPDK, mTCP, IX, eRPC, and Demikernel, grounding each claim in the published measurements of the original papers [1][2][4][5][7]. Third, we formalize two results — a **batching amortization theorem** and a **latency lower-bound theorem** — that bound what any polling datapath can achieve.

We adopt the following conventions throughout:

- *Latency* means application-to-application round-trip time for a small (≤ 64 B payload) message unless stated otherwise.
- *Throughput* means sustained goodput in messages per second (Mrps) on a single core unless stated otherwise.
- Hardware baseline: 10–100 GbE NICs, Xeon-class multicore servers, PCIe Gen3+; we normalize historical numbers to per-core efficiency where the original papers report multi-core totals.

We deliberately exclude RDMA-only designs (FaRM, FaSST) from the deep analysis because they require lossless fabrics and specialized adapters at both endpoints, whereas the systems studied here run on commodity lossy Ethernet [4].

## 4. Deep Dive

### 4.1 DPDK: poll-mode drivers and the run-to-completion datapath

DPDK's architecture rests on four pillars [1]:

1. **EAL (Environment Abstraction Layer).** At startup, EAL reserves hugepages (2 MB or 1 GB), pins threads to cores, discovers the NUMA topology, and binds NICs to user-space drivers via VFIO/UIO. Hugepages serve two purposes: they slash TLB pressure (a TLB miss costs hundreds of cycles per packet at millions of packets per second) and they provide physically contiguous, DMA-visible memory so the NIC can write packets directly into application buffers with zero copies.
2. **PMD (Poll-Mode Driver).** Each supported NIC (Intel `ixgbe`/`i40e`/`ice`, Mellanox `mlx5`, Broadcom `bnxt`) has a user-space driver compiled into the application. The PMD never enables interrupts; a dedicated lcore spins in a tight loop calling `rte_eth_rx_burst()` to drain up to 32 descriptors from the RX ring, processes the batch, and calls `rte_eth_tx_burst()`.
3. **mbuf mempools.** Packets live in `rte_mbuf` structures drawn from lock-free hugepage-backed mempools. The NIC DMAs directly into free mbufs, so the entire receive path is *allocation-free in the steady state*.
4. **Run-to-completion vs. pipeline.** In the run-to-completion model, one lcore performs all processing stages for a packet batch, maximizing instruction and data locality; the pipeline model distributes stages across cores via `rte_ring` queues at the cost of cache-line bouncing.

```c
/* Canonical DPDK run-to-completion forwarding loop */
#define BURST 32
for (;;) {
    uint16_t n = rte_eth_rx_burst(port, queue, mbufs, BURST);
    if (n == 0)
        continue;                       /* poll: no interrupt, no sleep */
    for (uint16_t i = 0; i < n; i++)
        process_to_completion(mbufs[i]); /* parse, classify, rewrite */
    uint16_t sent = rte_eth_tx_burst(port, queue, mbufs, n);
    if (sent < n)                        /* reclaim unsent mbufs */
        rte_mempool_put_bulk(pool, &mbufs[sent], n - sent);
}
```

The price of this design is explicit: one or more cores are *burned* at 100% utilization regardless of load, power management is defeated, and the NIC is exclusively owned by the DPDK process. DPDK is also only packet I/O — every user must build or borrow a protocol stack on top.

### 4.2 mTCP: a user-level TCP stack for multicore systems

mTCP (NSDI 2014) demonstrated that a *complete, POSIX-compatible TCP stack* can live in user space and outperform the kernel's [2][3]. Its design principles are a masterclass in multicore-conscious systems engineering:

- **Per-core event-driven architecture.** Each mTCP thread owns a private TCP control block table, event queue, and connection set; packets are steered to threads by RSS flow hashing, so the common case requires *no locks and no shared state*.
- **Batching as a first-class primitive.** Application calls (`connect`, `write`, `close`) are enqueued into per-thread queues and processed in batches by the mTCP thread; received payloads are similarly batched into the application's event queue. Batching amortizes queue-synchronization cost — the dominant overhead in a naive design.
- **Lock-free, cache-friendly structures.** Connection tables use per-core partitioning; timer wheels are per-thread; even the ARP and routing tables are replicated rather than shared.
- **Lightweight connection setup.** The three-way handshake is streamlined with preallocated control blocks and batched SYN processing.

The results were decisive: mTCP improved lighttpd throughput by 33%–320% over Linux TCP, achieved Jain's fairness index of 0.999 across 8,000 concurrent connections (vs. 0.973 for Linux), and saturated a 10 Gbps link while using a fraction of the CPU [3]. Its most enduring lesson, however, is negative: aggressive batching — necessary to amortize its cross-thread queue costs — raised tail latency, a weakness IX would directly address.

> **Theorem (Batching Amortization):** *Let $c_q$ be the fixed cost of one cross-thread queue synchronization and $c_p$ the per-packet processing cost. For a batch of $n$ packets, the amortized per-packet cost is $c_p + c_q/n$. As $n \to \infty$ the queue overhead vanishes, but the batching delay imposed on the first packet in the batch grows as $\Theta(n / \lambda)$ for arrival rate $\lambda$. Hence throughput-optimal batch sizes are latency-pessimal: any batching datapath faces a fundamental throughput–latency trade-off parameterized by $n$.*

*Proof sketch.* The per-packet cost follows directly from dividing the fixed synchronization by the batch size. For delay: the first packet of a batch of size $n$ waits while the remaining $n-1$ packets arrive, which at Poisson rate $\lambda$ takes expected time $(n-1)/\lambda = \Theta(n/\lambda)$. ∎

### 4.3 Demikernel: a library-OS architecture for heterogeneous bypass

Demikernel (SOSP 2021) starts from an observation: kernel-bypass devices are *heterogeneous and evolving* — DPDK NICs, RDMA HCAs, XDP-capable NICs, FPGAs, and plain kernel sockets all expose different queue, memory, and completion semantics [5][6]. Applications written directly against any one device API must be rewritten when hardware changes. Demikernel's answer is a two-layer architecture:

- **PDPIX (Portable Datapath Interface).** A narrow waist that abstracts the operations every bypass device provides: memory registration for zero-copy, scatter-gather buffer descriptors, and asynchronous queue pairs with explicit completions. Device backends implement PDPIX once.
- **libOSes.** Full I/O personalities built on PDPIX: `catnap` (a libOS over kernel TCP for compatibility and debugging), `catnip` (a from-scratch Rust TCP/IP stack over DPDK and XDP), and `catpowder` (an RDMA/FPGA-oriented libOS). Applications program against a single POSIX-like DemiAPI and run unmodified across devices.

The key insight is the *separation of datapath from control plane carried to its conclusion*: the µs-scale datapath lives entirely in application-linked library code, while the host kernel retains everything else — process management, filesystems, orchestration. Demikernel shows that applications such as Redis can achieve single-digit microsecond latencies through this architecture, and that the libOS approach amortizes the engineering cost of bypass across many applications and devices [5].

### 4.4 Comparators: IX, eRPC, and the kernel-integrated middle ground

**IX (OSDI 2014, Best Paper)** took the opposite philosophical stance from pure user-space stacks: keep the kernel, but split it. A dataplane kernel runs on dedicated hardware threads, polls NIC queues, and processes *bounded, adaptively-sized* batches of packets to completion before invoking the application in user mode; a control-plane Linux kernel handles everything else, with hardware virtualization enforcing protection [7]. Adaptive batching — growing batches under load, shrinking them when idle — directly answers the throughput–latency trade-off of Theorem 1: IX holds 99th-percentile latency flat while Linux's tail explodes under load.

**eRPC (NSDI 2019)** proved that the *transport* need not be exotic either. Running over plain UDP on lossy Ethernet (no PFC, no RDMA), eRPC combines a raft of common-case optimizations — zero-copy transmission with a single-DMA message-buffer format, preallocated response buffers, user-space congestion control tuned for datacenter BDP, and a NIC-memory footprint independent of cluster size — to deliver **2.3 µs median RPC latency, 10 million RPCs/s per core, 75 Gbps single-core bulk throughput, and 20,000 sessions per server** [4]. Disabling its congestion-control optimizations alone drops throughput from 5 to 4.3 Mrps; disabling zero-copy request processing costs another 40%. The eRPC lesson: in the common case (small messages, uncongested fabric), most software overhead is *gratuitous*, and careful engineering of the common path beats protocol redesign.

| System | Year | Bypass mechanism | Median small-RPC latency | Per-core throughput |
|---|---|---|---|---|
| Linux kernel TCP | — | none (baseline) | 15–50 µs | ~1 Mrps |
| mTCP | 2014 | user-space TCP over DPDK-class driver | ~10 µs (est.) | ~1.9× below IX [3] |
| IX | 2014 | split dataplane kernel, adaptive batching | ~10 µs avg, flat p99 | 8.8 Mrps msgs [7] |
| eRPC | 2019 | user-space RPC over UDP/Ethernet | **2.3 µs** | **10 Mrps** [4] |
| Demikernel libOS | 2021 | libOS over DPDK/XDP/RDMA | single-digit µs | device-limited [5] |

> **Theorem (Latency Lower Bound for Polling Datapaths):** *For a polling datapath with per-packet software cost $c_{sw}$, DMA transfer time $c_{dma}$, and wire time $c_{wire}$, the achievable median RPC round-trip latency satisfies $L \geq 2\,(c_{sw} + c_{dma} + c_{wire})$. Kernel bypass minimizes $c_{sw}$ but cannot reduce $c_{dma} + c_{wire}$, which are hardware-determined. Hence the marginal benefit of further software optimization vanishes as $c_{sw} \to 0$, and eRPC's 2.3 µs approaches the practical floor for its hardware generation.*

*Proof sketch.* A round trip requires two traversals of the software path and the wire; each traversal costs at least the sum of its stage minima. As software cost tends to zero the bound is dominated by DMA and wire times, which for 100 GbE and PCIe Gen3 are each on the order of 0.5–1 µs, yielding a floor of ~2 µs. ∎

## 5. Empirical Results / Formal Proofs

We consolidate the published measurements into three claims, each grounded in the cited evaluations.

**Claim 1 — Bypass removes an order of magnitude of software latency.** Linux delivers small-message RPC service at 15–50 µs of software overhead (§2.1); eRPC delivers 2.3 µs median end-to-end on the same class of hardware [4]. IX holds average latency at ~10 µs with a flat 99th percentile under 10 GbE saturation, where Linux's tail latency exceeds 750 µs [7]. The improvement factor is 5–20× depending on metric and load.

**Claim 2 — Per-core throughput scales with the removal of shared state.** IX needs only 3 cores to saturate 10 GbE where mTCP needs all 8, because IX's dataplane threads share nothing in the common case while mTCP's batched cross-thread queues retain residual synchronization [7]. eRPC's 10 Mrps/core exceeds DPDK-era ceilings precisely because its session state is partitioned and its congestion control is end-to-end rather than fabric-assisted [4].

**Claim 3 — Common-case optimization dominates protocol choice.** eRPC's ablation study is the cleanest evidence: on lossy Ethernet with plain UDP, disabling common-case optimizations costs up to 40% of peak throughput, while the transport choice (UDP vs. RDMA-style reliability) matters far less than folklore suggests [4]. Similarly, Demikernel's `catnap` libOS — which falls back to kernel TCP — exists because *most* of an application's I/O is not latency-critical, and paying bypass costs (dedicated cores, device exclusivity) for cold paths is wasteful [5].

```python
# Sizing a DPDK mempool: how many mbufs for line rate?
# Rule of thumb: mbufs >= 2 * (in-flight per queue) * queues,
# where in-flight ~= bandwidth_delay_product / avg_packet_size.
def mempool_size(gbps, rtt_us, avg_pkt_bytes, queues, headroom=2.0):
    bits_in_flight = gbps * 1e9 * rtt_us * 1e-6
    pkts_in_flight = bits_in_flight / (avg_pkt_bytes * 8)
    return int(pkts_in_flight * queues * headroom)

print(mempool_size(100, 5, 1500, 8))   # ~6667 mbufs for 100GbE, 5us RTT
print(mempool_size(100, 5, 64, 8))     # ~156250 mbufs at 64B line rate
```

The second number explains a hard operational reality of DPDK deployments: at small-packet line rates on 100 GbE, the mempool must hold hundreds of thousands of hugepage-backed, DMA-mapped mbufs — a strong argument for 1 GB hugepages and NUMA-local allocation [1].

## 6. Limitations

Kernel bypass is not a free lunch. Six substantive limitations stand out:

1. **Dedicated cores and energy.** Polling burns cores at 100% utilization even when idle; power-proportional computing is sacrificed. IX's elastic threads lend idle dataplane cores back to the control plane, but the mechanism is complex [7].
2. **Weakened isolation.** A user-space stack shares fate with its application: a wild DMA descriptor can corrupt the dataplane for all connections. IX's hardware-virtualized dataplane restores protection at the cost of reintroducing a kernel [7].
3. **Device exclusivity.** A DPDK-bound NIC is invisible to the kernel: no `tcpdump`, no iptables, no kernel TCP fallback on the same port. Decades of operational tooling go dark [1].
4. **TCP compatibility.** mTCP reimplements TCP — congestion control, SACK, timers — and must track the kernel's evolution forever; each new option must be reimplemented and retested [3].
5. **Heterogeneity.** Every NIC family needs its own PMD, and performance is notoriously sensitive to NUMA placement and firmware [1]. Demikernel's PDPIX is an explicit response to this fragmentation, but it is young [5].
6. **Diminishing returns.** By Theorem 2, once software cost is a small fraction of wire-plus-DMA time, further bypass engineering buys little. For many applications, `io_uring` plus a tuned kernel stack captures most of the benefit at a fraction of the operational cost.

---

## 7. Conclusion

Kernel-bypass user-space networking has matured from a practitioner's trick into a principled re-architecture of datacenter I/O. DPDK established the *mechanism* — poll-mode drivers, hugepage mempools, run-to-completion execution [1]. mTCP proved a *complete TCP stack* can live in user space and beat the kernel by 33%–320% on real applications [2][3]. IX showed bypass and protection are not contradictory, splitting a polling dataplane from a general-purpose control plane [7]. eRPC demonstrated that common-case optimization over plain UDP on lossy Ethernet reaches 2.3 µs median latency and 10 Mrps per core — within striking distance of hardware limits [4]. Demikernel points to the future: a library-OS architecture in which applications program one portable datapath API while libOSes absorb device churn [5][6].

The through-line is the *datapath/control-plane split*: move the microsecond-critical packet path into dedicated, polling, zero-copy software, and leave everything else in the kernel or its libraries. The open problems are now operational: energy-proportional polling, strong isolation without a dataplane kernel, and portable abstractions that survive the next generation of SmartNICs and DPUs. The age of the killer microsecond is here; the software has finally caught up with the wire.
