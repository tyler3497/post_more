# MicroVM Snapshots and Sub-125ms Cold Starts: A Systematic Study of Firecracker's Serverless Execution Substrate

## Abstract

Serverless economics hinge on a hard systems problem: instantiating strongly isolated sandboxes in milliseconds. This thesis studies Firecracker, the KVM-based minimalist virtual machine monitor (VMM) behind AWS Lambda and Fargate, and the snapshot/restore machinery driving cold starts below 125 ms. We dissect Firecracker's design — one Rust process per microVM, direct kernel boot, a five-device virtio model, jailer sandboxing — and formalize the cold-start budget as the sum of scheduling, sandbox, boot, initialization, and network terms. We analyze snapshot-based cold-start elimination: full and diff snapshots, lazy guest-memory population via `userfaultfd`, memory deduplication, and REAP-style working-set prefetching (3.7× reduction [3]). We survey mitigation strategies across platforms, from keep-warm pools and Catalyzer's initialization-less booting [2] to CXL/RDMA hierarchical snapshot pools [5], and close with open problems: snapshot uniqueness, page-fault storms, and the security semantics of cloned environments [4].

---

## 1 Introduction

The serverless model reframes the cloud as a function of events: the provider invokes a registered function per request, scales concurrency to demand, and bills only for executed milliseconds. Utilization approaches 100%, but viability is technical — *every invocation must begin in a fresh, strongly isolated sandbox, ready before the customer notices the wait*.

The dominant sandboxing technologies sit at opposite ends of a painful tradeoff. Containers share the host kernel — fast, but a single privilege-escalation flaw compromises every tenant [1]. Traditional VMs provide hardware-enforced isolation, yet emulated BIOS, ACPI, PCI buses, and legacy devices inflate boot times into seconds and footprints into hundreds of megabytes. Neither satisfies the serverless operator, who must pack thousands of mutually distrustful tenants onto one host while launching each in milliseconds.

Firecracker resolves this dilemma by *specializing* the VMM to the serverless workload: the smallest possible monitor that still runs unmodified Linux — no firmware, no bootloader, no ACPI, only five emulated devices [1]. One Firecracker process hosts exactly one microVM, bounding a guest escape to a single process; the VMM is written in Rust, removing entire classes of memory-safety bugs from the trusted computing base. The measured result: boot under 125 ms with less than 5 MiB of memory overhead — fast enough to provision on the invocation critical path, cheap enough to pack thousands per host.

Booting in 125 ms is only half the battle: a cold start spans request arrival to first output byte, including runtime startup (JVM, Python, Node.js), application initialization (framework wiring, connection pools, model loading), and network attachment. For managed runtimes these terms dominate — a Java function can spend seconds in class loading after the kernel is up. *Snapshot-based cold-start elimination* attacks exactly this term: boot once, initialize fully, capture machine state, and *restore* per invocation. Firecracker restore takes as little as 4 ms [4]; Catalyzer demonstrated sub-millisecond startup [2]. The cold start is amortized — paid once at function-creation time, hidden from every subsequent customer.

This thesis makes the following contributions:

1. **An architectural dissection** of Firecracker's minimalist VMM — KVM integration, device model, jailer sandboxing, vsock (§4.1, §4.4).
2. **A formal latency model** of cold starts and the snapshot/restore optimization (§3, §5).
3. **A comparative survey** of mitigation strategies — keep-warm pools, REAP prefetching [3], Catalyzer init-less booting [2], Aquifer hierarchical pooling [5].
4. **An analysis of open problems**: snapshot uniqueness [4], page-fault storms, and the security semantics of cloned environments (§6).

## 2 Background

### 2.1 The Serverless Execution Model

In the serverless (Function-as-a-Service) model, the unit of scheduling is an *invocation*: an event triggers a short-lived function with bounded memory (128 MiB–10 GiB) and bounded lifetime. Providers multiplex thousands of tenants' invocations onto host fleets. Three properties distinguish this model from classical virtualization:

- **Ephemerality.** Functions run for seconds, so startup latency is a first-order cost, not an amortized one.
- **Burstiness.** Demand can jump from zero to thousands of concurrent invocations in seconds; the platform must provision at the arrival rate.
- **Zero-idle economics.** Customers are not billed for boot time, which *disincentivizes providers from booting from scratch on demand* [3] — yet customers feel every millisecond, aligning pressure to minimize cold starts.

A *cold start* occurs when no warm sandbox exists and one must be created; a *warm start* reuses a live sandbox. The latency budget decomposes as:

$$T_{\text{cold}} = T_{\text{sched}} + T_{\text{sandbox}} + T_{\text{boot}} + T_{\text{init}} + T_{\text{net}}$$

Classical VMs make $T_{\text{boot}}$ dominant (seconds); containers make $T_{\text{init}}$ dominant; Firecracker-class microVMs push $T_{\text{boot}}$ under 125 ms, exposing $T_{\text{init}}$ — the precise term snapshots eliminate — as the new bottleneck.

### 2.2 KVM and Hardware-Assisted Virtualization

Firecracker is built on Linux KVM. KVM exposes hardware virtualization extensions (Intel VT-x, AMD-V) via `/dev/kvm`: a userspace process creates a VM (`KVM_CREATE_VM`), maps guest-physical memory, creates vCPUs (`KVM_CREATE_VCPU`), and runs them (`KVM_RUN`), with the kernel handling exits for privileged operations. KVM provides the *mechanism* — CPU/MMU virtualization with nested page tables — while the VMM provides the *policy*: device emulation, memory management, lifecycle.

This division of labor is what makes a minimalist VMM possible. Firecracker need not emulate a CPU at all; it merely configures KVM and emulates a handful of virtio devices over `virtio-mmio` transports. Everything else — scheduling, paging, interrupt injection — is delegated to the host kernel and hardware.

### 2.3 Prior Approaches to Fast Startup

Three research threads precede and inform Firecracker's snapshot machinery:

- **LightVM (SOSP '17)** demonstrated 2.3 ms VM boot with a redesigned Xen control plane and unikernels, proving VMs can match container density — but required guest cooperation, unlike Firecracker's unmodified-Linux goal.
- **Catalyzer (ASPLOS '20)** [2] introduced *initialization-less booting*: restore a function instance from a well-formed checkpoint image, skipping initialization on the critical path, plus an `sfork` (sandbox fork) primitive. It achieved <1 ms startup best-case and <2 ms for Java SPECjbb — 1000× over gVisor.
- **gVisor** interposes a userspace kernel on syscalls, trading VM-grade isolation for lower startup; its overheads motivated Catalyzer's measurements [2].

## 4 Deep Dive

### 4.1 The KVM-Based Minimalist VMM

Firecracker's central decision is *radical specialization*. QEMU emulates a complete PC — BIOS/UEFI, ACPI, PCI, PS/2, VGA — to boot arbitrary guests. Firecracker assumes one guest contract: *a modern Linux kernel booted directly*, with no firmware or bootloader. It loads `vmlinux` and the rootfs into guest memory, sets boot parameters, and jumps to the kernel entry point — firmware elimination alone removes hundreds of milliseconds from $T_{\text{boot}}$.

**Process model.** One Firecracker process hosts exactly one microVM — a security decision as much as an operational one: a guest escape's blast radius is confined to a single sandboxed VMM process (§4.4). The process contains three logical components:

| Component | Responsibility |
|---|---|
| API server | REST/Unix-socket endpoint for VM configuration (vCPUs, memory, drives, network) |
| VMM core | KVM setup, vCPU threads, memory management, event loop |
| Device model | Emulation of exactly five devices: `virtio-net`, `virtio-blk`, `virtio-vsock`, `virtio-rng`, serial console |

The device model is the most striking economy: five virtio devices over `virtio-mmio` — no PCI bus, no ACPI, no legacy hardware — shrinking the VMM to roughly 50,000 lines of Rust, an order of magnitude smaller than QEMU, which directly reduces both attack surface and boot-time code paths [1].

**KVM integration.** The VMM core maps guest memory with `mmap`, registers it with KVM, and spawns one host thread per vCPU, each looping on `KVM_RUN` and dispatching exits (I/O, MMIO, halt) to the device model. Configurable rate limiters on network/block throughput and request rates bound the host CPU an untrusted guest can consume [1].

A minimal Rust sketch of the vCPU bring-up path illustrates the design's directness:

```rust
// Simplified Firecracker-style vCPU setup (illustrative)
use kvm_ioctls::{Kvm, VcpuFd};

fn spawn_vcpu(kvm: &Kvm, vcpu_id: u8, entry: u64) -> std::io::Result<()> {
    let vm_fd = kvm.create_vm()?;                       // KVM_CREATE_VM
    let vcpu: VcpuFd = vm_fd.create_vcpu(vcpu_id)?;     // KVM_CREATE_VCPU
    let mut regs = vcpu.get_regs()?;
    regs.rip = entry;                                    // direct kernel entry: no firmware
    vcpu.set_regs(&regs)?;
    std::thread::spawn(move || loop {
        match vcpu.run() {                               // KVM_RUN until exit
            Ok(kvm_ioctls::VcpuExit::IoOut(p, d)) => dev_model.io_write(p, d),
            Ok(kvm_ioctls::VcpuExit::MmioRead(a, _)) => dev_model.mmio_read(a),
            Ok(kvm_ioctls::VcpuExit::Hlt) => break,
            r => panic!("unexpected exit: {:?}", r),
        }
    });
    Ok(())
}
```

> **Theorem 1.** *Let $D$ be the set of emulated devices and $B(D)$ the boot time. For a fixed guest kernel, minimizing $|D|$ subject to the guest's driver requirements minimizes the VMM-attributable boot latency, because each device contributes a non-negative, independent initialization term to the critical path.*

*Proof sketch.* Device init is sequential in probe order, so each removed device removes its probe, BAR, and interrupt terms; five is minimal for unmodified Linux guests. ∎

The measured consequence: ~125 ms median end-to-end boot for a 1-vCPU, 128 MiB microVM (including fork and API configuration), 153 ms at the 99th percentile with 100 concurrent starts [1], and under 5 MiB memory overhead beyond guest RAM — the density enabler.

### 4.2 Snapshot and Restore: Amortizing Initialization

Booting in 125 ms solves $T_{\text{boot}}$, but $T_{\text{init}}$ — runtime and application initialization — remains. For a Java function, class loading and framework wiring can take seconds; for ML inference, model deserialization dominates. Snapshots move $T_{\text{init}}$ off the critical path entirely: boot once, initialize fully, capture state, and restore per invocation.

**Snapshot format.** A snapshot consists of [6]:

- **Guest memory file** — the raw contents of guest RAM at snapshot time.
- **VM state file** — serialized VMM, KVM, vCPU, and device state (registers, interrupt controller, virtio queue state).
- **Disk images** — managed by the operator; Firecracker does *not* snapshot block devices, so disk consistency is the operator's responsibility.

The format is versioned independently of Firecracker releases, so snapshots migrate across VMM versions [6]. Two flavors exist: *full snapshots* (production-ready) and *diff (incremental) snapshots* (developer preview; ongoing `guest_memfd` integration work).

**Restore path.** The VMM maps the guest memory file, deserializes VM state into KVM structures, and resumes vCPUs — in as little as ~4 ms [4], because restore skips firmware, kernel decompression, driver probing, *and* application initialization.

> **Theorem 2.** *Let $C_{\text{boot}} = T_{\text{boot}} + T_{\text{init}}$ be the one-time init cost and $C_{\text{restore}}$ the per-invocation restore cost. Snapshotting wins iff $C_{\text{restore}} < C_{\text{boot}} - \epsilon$ (storage/management overhead) — satisfied by 1–2 orders of magnitude in practice.*

The operational timeline (Figure 2 in [4]) hides the entire boot portion from the customer: initialization happens once at function-creation time, and the blocking per-invocation cost collapses to snapshot restore — *entirely under the provider's control*.

### 4.3 Lazy Page Faulting, Working-Set Prefetch, and Memory Deduplication

Naive snapshot restore hides a cost: *guest memory is mapped lazily*. The VMM maps the memory file but populates host page tables on demand, so every first touch of a guest page triggers a host page fault served from disk. REAP [3] quantified this:

- Restored functions run **95% slower** on average than the same function memory-resident (warm).
- Page-fault servicing accounts for **95% of actual function processing time** — the function is I/O-bound on its own memory.
- Yet functions exhibit a **stable working set**: 97% of guest-physical pages touched are identical across invocations.
- Restore's resident footprint (8–99 MiB) is 61–96% smaller than cold boot's (148–256 MiB), because only used pages are ever faulted in.

REAP exploits this with record-and-prefetch: on the first invocation a monitor thread records faulted page offsets via `userfaultfd` and compacts touched pages into a contiguous *working-set (WS) file*; on later invocations the WS file is read in *one sequential disk operation* and eagerly installed before vCPUs resume — eliminating up to 97% of page faults and cutting cold-start latency **3.7×** on average [3].

`userfaultfd` is the enabling kernel primitive: the hypervisor registers the guest-memory region with `UFFDIO_REGISTER`, and the host kernel forwards page faults on that region to a userspace monitor instead of resolving them in-kernel. The monitor serves pages from arbitrary backends — local SSD, a WS file, or a CXL/RDMA pool [5] — with no kernel modifications.

The lazy-vs-eager tradeoff models directly:

```python
# Cold-start latency model: lazy faulting vs working-set prefetch
def t_lazy(n_pages, t_fault_ms, t_restore_ms=4.0):
    """Every touched page faults serially on the critical path."""
    return t_restore_ms + n_pages * t_fault_ms

def t_reap(ws_pages, disk_bw_mbps, page_kb=4, t_restore_ms=4.0):
    """One sequential read of the compact WS file, then zero faults."""
    ws_mb = ws_pages * page_kb / 1024
    return t_restore_ms + (ws_mb / disk_bw_mbps) * 1000

# REAP paper regime: ~20k pages touched, SSD ~500 MB/s
print("lazy : %.1f ms" % t_lazy(20000, 0.05))   # 1004.0 ms
print("reap : %.1f ms" % t_reap(20000, 500))     # 160.0 ms  (~6x here; paper reports 3.7x avg)
```

**Memory deduplication.** Snapshot-derived microVMs share most memory content, so Kernel Samepage Merging (KSM) collapses identical pages into single copy-on-write frames; per-instance marginal memory approaches the *dirty* working set — the basis of thousands-per-host density.

**Hierarchical memory pooling** extends this idea provider-wide: Aquifer [5] tiers snapshots across a pod-local CXL pool (sub-microsecond hot-page serving) and a cluster-wide RDMA pool (cold pages from stranded memory), achieving 2.2× geomean speedup over Firecracker snapshots and 1.1× over REAP. The lesson generalizes: *the snapshot backing store is a tiered memory hierarchy, and restore latency is governed by where the hot pages live*.

### 4.4 vsock and the Jailer: Defense in Depth

Strong isolation is Firecracker's *raison d'être*, engineered in concentric layers — hardware (KVM second-level address translation, VT-x privilege separation) plus three software layers:

1. **The jailer.** Before the Firecracker process `exec`s, the *jailer* — a small privileged helper — builds the sandbox: dedicated **cgroups** (CPU/memory/pid limits), unshared **namespaces** (PID, mount, network, UTS, IPC), `chroot` into an empty directory, dropped capabilities, and tight resource limits. The VMM process has no visibility into sibling microVMs and no escalation path [1][6].

2. **seccomp-bpf.** Each thread installs a filter restricting it to its role's minimal syscall set (vCPU thread: `KVM_RUN` ioctls, futexes; API thread: socket I/O). A compromised thread cannot invoke `execve`, `ptrace`, or `mount` — violation kills the process. With Rust's memory safety, the trusted computing base is exceptionally small.

3. **API and device rate limiting.** Configurable limiters on virtio-net/virtio-blk throughput and IOPS bound the host CPU a malicious guest can burn through interrupt storms [1].

**vsock** is the sanctioned host↔guest channel: an `AF_VSOCK` transport over the virtio-vsock device letting the host agent reach the guest (health checks, invocation delivery, logs) *without* giving the guest a routable interface. The jailer's network namespace contains only the vsock endpoint — no veth pair, no bridge, no iptables — leaving nothing for lateral attack.

### 4.5 Cold-Start Mitigation Strategies Across Platforms

Snapshots are one point in a broader design space, taxonomized below:

| Strategy | Mechanism | Latency class | Cost |
|---|---|---|---|
| **Keep-warm pools** | Retain initialized sandboxes between invocations | Warm: ~0 ms | Memory held idle; 40% of server capex is DRAM [3] |
| **Provisioned concurrency** | Pre-warmed, provider-managed pool (customer-paid) | Warm: ~0 ms | Customer pays for idle |
| **Snapshot restore** | Restore pre-initialized microVM state | 4–130 ms [4] | Snapshot storage; page-fault tail |
| **WS prefetch (REAP)** | Eager working-set install via `userfaultfd` | ~3.7× over naive snapshots [3] | One record-phase invocation |
| **Init-less boot (Catalyzer)** | Restore from checkpoint + `sfork` reuse | <1 ms best case [2] | Guest-OS cooperation |
| **Hierarchical pooling (Aquifer)** | CXL-hot / RDMA-cold snapshot tiers | 2.2× over Firecracker [5] | CXL fabric hardware |
| **Predictive pre-warming** | ML on invocation traces; warm ahead of demand | Varies | Misprediction waste |

The strategies compose: a platform may keep a small warm pool for p99 latency, restore snapshots for the bulk, and prefetch working sets to bound the restore tail. The per-invocation policy is a pure decision function:

```haskell
-- Per-invocation sandbox selection policy (illustrative)
data Sandbox = Warm PoolId | Snapshot SnapId | Fresh deriving (Eq, Show)
data Demand  = Burst | Steady deriving (Eq, Show)

selectSandbox :: Demand -> Maybe PoolId -> Maybe SnapId -> Sandbox
selectSandbox Burst  (Just p) _        = Warm p        -- p99: never restore on a burst
selectSandbox Steady _         (Just s) = Snapshot s   -- amortized path
selectSandbox _      _         _        = Fresh        -- fallback: cold boot
```

Three lessons emerge. **First**, restore is 1–2 orders of magnitude faster than boot, so providers snapshot at function-registration time, never on the invocation path [4]. **Second**, the restore tail is dominated by page faults, not state deserialization — REAP's 95% finding [3] reframes snapshot optimization as a *memory-prefetching* problem. **Third**, the working set is stable (97% page overlap [3]), so record-once/prefetch-forever converges.

A back-of-envelope density calculation shows the economic stakes: a 256 GiB host holds ~2,000 fully-warm 128-MiB instances, but with snapshot restore + lazy population the resident set is 8–99 MiB per instance [3] — ~8,500 restorable instances at a 30 MiB average, a 4× density gain, before KSM collapses shared kernel/runtime pages further. Cold start is simultaneously a latency problem and a *bin-packing* problem, and snapshots improve both.

## 6 Limitations

**Snapshot uniqueness and entropy.** Cloning a microVM clones its entropy pool, RNG state, and in-memory secrets: two invocations restored from one snapshot may emit identical UUIDs, TLS nonces, or session keys — catastrophic for cryptographic protocols. Mitigation requires guest cooperation — RNG reseeding on restore detection, VM Generation IDs, provider-injected entropy refresh [4]. Firecracker's `virtio-rng` offers a reseeding channel, but the guest must use it; the VMM does not enforce the invariant.

The required invariant, in TLA+:

```tla
---- MODULE SnapshotUniqueness ----
EXTENDS Naturals
VARIABLES restored, rngReseeded, invocations
Init == restored = FALSE /\ rngReseeded = FALSE /\ invocations = 0
Restore == restored' = TRUE /\ rngReseeded' = FALSE /\ UNCHANGED invocations
Reseed  == rngReseeded' = TRUE /\ UNCHANGED <<restored, invocations>>
Invoke  == invocations' = invocations + 1 /\ UNCHANGED <<restored, rngReseeded>>
Next == Restore \/ Reseed \/ Invoke
\* Safety: no invocation may execute on restored state without reseeding
Safe == [](restored => (rngReseeded \/ invocations = 0))
====
```

**Page-fault storms.** Lazy restore converts boot latency into fault latency; under burst concurrency, thousands of microVMs faulting at once can saturate disk bandwidth and the `userfaultfd` monitor, reintroducing correlated tails. Prefetching mitigates but does not eliminate this — the WS read becomes the contended resource.

**Disks are not snapshotted.** Snapshots cover memory and device state only [6]; block-device consistency is the operator's problem, forcing external coordination (copy-on-write layers, log-structured disks) for stateful functions.

**Snapshot lifecycle costs.** Snapshots must be stored, versioned, invalidated on function update, and replicated to every eligible host — a distributed placement and coherence problem the VMM papers deliberately exclude.

**Platform constraints.** Firecracker requires KVM (bare-metal or nested-virtualization hosts), targets Linux guests, and keeps diff snapshots in developer preview [6]. The jailer's guarantees assume correct host-kernel behavior — kernel-exploit escapes remain theoretically in scope, hence defense-in-depth.

## 7 Conclusion

Firecracker's contribution is a *co-design of isolation and startup*: specializing the VMM to serverless — direct kernel boot, five virtio devices, one Rust process per microVM, jailer sandboxing — brought VM-grade isolation into the millisecond regime (~125 ms boot, <5 MiB overhead) [1]. Snapshots then eliminated application initialization, driving cold starts to ~4 ms [4], below 1 ms with init-less booting [2]. The frontier moved accordingly: from *how fast can we boot* to *how fast can we fault pages in* [3], *where snapshot pages should live* [5], and *what cloning a running machine safely means* [4].

The enduring lesson is architectural: cold start was never really about virtualization speed, but about *reusing work already done*. Snapshots are memoization applied to machine state — initialize once, cache, serve every future invocation from the cache. The systems that win the next decade of serverless will manage this cache best: predicting working sets, tiering snapshot storage, and preserving the security invariants that cloning threatens to break.
