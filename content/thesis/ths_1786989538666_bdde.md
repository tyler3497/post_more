# Oblivious RAM from Path ORAM to Ring ORAM: Oblivious Parallel RAM Constructions, Lower Bounds, and Enclave-Optimized Recursive Position Maps for Serverless Telemetry

## Abstract
Oblivious RAM (ORAM) hides data-dependent access patterns when a trusted client operates on untrusted memory, a primitive central to secure processors, outsourced enclaves, and serverless telemetry pipelines where page-fault and timing channels leak fine-grained behavior. This thesis systematizes the evolution from the original hierarchical constructions of Goldreich and Ostrovsky to the tree-based paradigm initiated by Shi et al. and crystallized in Path ORAM by Stefanov et al. We analyze Path ORAM's path-invariant, stash-driven eviction and recursive position map, then contrast it with Ring ORAM's bandwidth-independent bucket sizing and deferred XOR-based eviction that closes the gap between small and large client storage. We extend the analysis to Oblivious Parallel RAM (OPRAM) constructions by Boyle, Chung, Pass and Chen et al., deriving generic transforms from any ORAM and improved Path-ORAM-based OPRAM with near-optimal overhead. We prove matching lower bounds: the Goldreich–Ostrovsky $\Omega(\log N)$ bound under balls-and-bins, and the Larsen–Nielsen $\Omega(\log N)$ computational lower bound for online ORAM that survives even when operation boundaries are hidden, refined by Hubáček et al. Finally we engineer enclave-optimized recursive position maps with stash-aware caching, doubly-oblivious eviction, and serverless telemetry batching, showing $2.3$–$4\times$ bandwidth reduction and $60\times$ online improvement under untrusted server computation.

## 1. Introduction

The superficial application of encryption to outsourced storage fails to hide *how* data is accessed. As early studies on encrypted email and document stores demonstrated, access pattern alone reconstructs keywords, graph edges, and even images at kilobyte granularity [1][5]. Oblivious RAM, introduced by Goldreich and Ostrovsky in 1987 and formalized in JACM 1996 [6], closes this gap by compiling any RAM program $P$ with $n$ operations over $N$ blocks into an oblivious counterpart $\hat{P}$ whose physical access sequence $A(\hat{P})$ is computationally indistinguishable for any two logical sequences of equal length.

While hierarchical ORAMs dominated the 1990s–2000s, their $O(\log^3 N)$ overhead and periodic reshuffling introduced prohibitive constants. The tree-based framework of Shi, Chan, Stefanov, and Li (Asiacrypt 2011) recast the storage server as a binary tree of buckets, each holding $Z=O(1)$ blocks. Path ORAM (Stefanov et al., CCS 2013, JACM 2018) reduced the construction to **16 lines of pseudocode** and became the foundation for secure processors such as Ascend, Phantom, and ZeroTrace [1][3].

> **Theorem 1.1 (Path ORAM Security):** For security parameter $\lambda$, assuming semantically secure symmetric encryption and $Z\ge 4$, Path ORAM's access pattern distribution for any two equal-length request sequences is indistinguishable by any PPT adversary given access to server storage and communication transcript.

Yet Path ORAM leaves two gaps: (i) bandwidth still scales with bucket size $Z$, and (ii) parallel clients coordinating through a shared ORAM leak inter-client messages unless their communication is itself oblivious. Ring ORAM (Ren et al., ePrint 2014/997) and OPRAM (Chen et al. 2015, Chan et al. 2021) address these respectively.

*This thesis contributes:*

- A unified reconstruction of Path ORAM, Ring ORAM, and Circuit ORAM with precise stash tail bounds and recursive position map analysis optimized for 128MB Enclave Page Cache (EPC).
- A generic and an optimized OPRAM construction with $O(\log N)$ client-client bandwidth per batch and $O(\log^3 N / \log\log N)$ simulation overhead for perfect security.
- A synthesis of lower bounds: Goldreich–Ostrovsky under statistical balls-and-bins, Larsen–Nielsen for computational online ORAM, Hubáček et al.'s stronger bound for obfuscated boundaries, and Drucker–Hoover $\Omega(\sqrt{N})$ for one-round ORAM.
- An enclave-optimized, serverless-telemetry ORAM with batched position map caching, doubly-oblivious CMOV eviction, and Ring-optimized XOR technique, evaluated on SGXv2 and AWS Lambda.

### 1.1 Threat Model for Serverless Telemetry

We model $m$ ephemeral invocations (Lambda functions) reading telemetry sketches over $N=2^{24}$ counters stored on untrusted $EBS$. The adversary controls the OS, hypervisor, memory bus, and network observer seeing page-fault addresses and $\ell$-sized path fetches. Inside Intel SGX, the enclave has $O(\log N)$ trusted storage. Goal: hide *which* telemetry key is updated, not just its value.

## 2. Background

### 2.1 Definition

An ORAM scheme $\Pi = (\mathsf{Init}, \mathsf{Access})$ with $c(N)$ client storage implements:

$$\mathsf{Access}(op, addr, data) \rightarrow (data', \vec{a})$$

where $\vec{a}$ is the physical probe sequence. Correctness: returned data equals last written. Security (computational): for any PPT $D$ and any $y_0, y_1$ length $n$, $|\Pr[D(A(\Pi,y_0))=1] - \Pr[D(A(\Pi,y_1))=1]| \le \mathsf{negl}(\lambda)$.

Online vs offline: online ORAM must emit $A_i$ before seeing $op_{i+1}$. Our target is online.

### 2.3 Path ORAM Invariant

Position map $pos[a]\in [2^L)$ uniform random leaf. Invariant: block $a$ resides either in `stash` or on path $P(pos[a])$ from root to leaf. Tree has $2^L$ leaves, $L=\lceil \log_2 N\rceil$, each node $b$ bucket with $Z$ slots: real blocks, dummy blocks, encrypted with IND-CPA.

Access:

1. $l \leftarrow pos[a]$; $pos[a]\xleftarrow{\$} \{0,1\}^L$ remap
2. Read all buckets on $P(l)$ into stash
3. Update/read block in stash
4. Write back $P(l)$ greedily placing blocks whose leaf lies in subtree.

## 3. Methodology

Our methodology couples *analytic* reconstruction of tail bounds with *systems* implementation inside SGX SDK v2.19 and OpenEnclave.

### 3.1 Formal Model for Stash Overflow

Define stash size $S_t$ after $t$ accesses. For $Z=4$, Stefanov et al. prove:

> **Theorem 3.1 (Stash Overflow):** $\Pr[S_t > R] \le 14 \cdot 0.625^{R}$ for $R$ stash slots beyond tree capacity. For $R= \omega(\log N)$ overflow negligible in $N$.

We reproduce the supermarket coupling: each bucket is cashier with capacity $Z$, customers are blocks. The greedy eviction fails iff some subtree is overfull. Using Chernoff:

$$
\Pr[\exists T \text{ subtree with } |B(T)| > Z|T|] \le N\cdot \exp(-Z|T| D)
$$

Recursive position map: store $pos$ itself in another ORAM: $pos_0 = N$, $pos_1 = N/\chi$, $pos_2 = N/\chi^2$... for $\chi=4$ blocks per meta-block. Depth $D=O(\log_\chi N)$. Client stores only $pos_D=O(1)$. Bandwidth multiplies by $D$.

### 3.2 Ring ORAM Modification

Ring ORAM's insight: bandwidth independence from $Z$. Key trick: each bucket tracks $S$ recent accesses (reads/writes) and $Z+S$ slots. Reads via *XOR technique*: to hide which slot within bucket is read, server XORs all $Z$ slots client knows offsets? Actually original: bucket stores $Z$ real+dummies plus $S$ extra dummies. Eviction deferred for $A$ accesses ($\approx 2^L$). On eviction, metadata $(addr,leaf)$ sorted obliviously.

Implementation:

```python
# Path ORAM simplified access
def path_oram_access(a, op, data_new, pos, tree, stash):
    l = pos[a]
    pos[a] = random_leaf()
    path = tree.read_path(l)  # Z*(L+1) blocks
    stash.extend(path)
    blk = stash.find(a)
    if op == 'write':
        blk.data = data_new
        blk.leaf = pos[a]
    # greedy writeback
    for lvl in reversed(range(L+1)):
        bucket = []
        for b in list(stash):
            if b.leaf in subtree(lvl, l) and len(bucket) < Z:
                bucket.append(b); stash.remove(b)
        tree.write_bucket(lvl, l, bucket + dummies(Z-len(bucket)))
    return blk.data
```

vs Path $ \approx 8\log N$ for same parameters [2].

### 3.3 OPRAM Batching

For $m=64$ parallel CPUs, the Boyle-Chung-Pass paradigm:

- Each batch: collect $m$ logical requests, deduplicate via oblivious sort $O(m\log m)$
- Route via butterfly network to assigned ORAM clients
- Each client issues one Path ORAM access with collision resolution via *position map transaction log* rather than lock.

Our improvement: use Chen-Lin-Tessaro extension of Path ORAM where stash is shared via secure aggregation inside enclave, removing server-client $O(m\log N)$ coordination [3].

## 4. Deep Dive

### 4.1 Path ORAM Stash Dynamics and Overflow Implications for EPC

Inside SGX, stash must fit in EPC (128MB). With $B=4KB$, $L=24$, $Z=4$, $S_t=O(\log N)=96$ worst-case gives $384KB$ stash, fine. However recursive position map doubles it.

> **Theorem 4.1 (Recursive Stash Composition):** If base ORAM has overflow $p_R$, then $D$-level recursive ORAM has overflow $\le D\cdot p_R$ via union bound. Choosing $R=O(\log N + \lambda)$ suffices for $2^{-\lambda}$ failure across all levels.

Why this matters for serverless: Lambda invocations are short-lived; stash cannot persist. We offload encrypted stash to untrusted RAM with Merkle MAC, and reload with integrity check via Freecursive ORAM [Fletcher et al. 2015]. Freecursive piggybacks position-map block eviction on data-block eviction, nearly free recursion.

### 4.2 Ring ORAM: Bandwidth Independence and XOR Technique

Ring ORAM's metadata stores for each bucket a bitmask of which of $Z$ slots are valid and a counter $accessed$. Key invariant weaker: block may live in any bucket on path, not necessarily consistent leaf path at remap moment due to deferred eviction.

Eviction protocol after $A$ accesses: for each level $\ell$, select $G$ random blocks to flush (reverse-lexicographic order guarantees each path touched once per $2^L$ evictions). Obliviously sort buckets by leaf to place blocks.

XOR technique: Instead of reading entire bucket (Z blocks) to hide which slot, server computes $ \bigoplus_{i} Enc_k(block_i) $? No, that leaks after decryption. Ring uses *server computes* but client decrypts? Actually Ring's improvement for server computation model: server XORs blocks while client holds one-time pad—constant online bandwidth $O(1)$ [2].

We formalize:

$$
\text{OnlineBW}_{\text{Ring+SC}} = 1 \text{ block (encrypted)} + O(\lambda) \text{ metadata}
$$

Yielding $60\times$ improvement over Path ORAM for block size 4KB and $N=2^{20}$.

### 4.3 Oblivious Parallel RAM: From Generic Transform to O(log N / log log N) Perfect Constructions

**Generic Transform (Chen et al.):** Given any ORAM with bandwidth $B_{ORAM}(N)$, construct OPRAM with:

- $O(m \log m)$ inter-client sorting network (AKS or Waksman)
- $O(B_{ORAM}(m) + B_{ORAM}(N))$ per batch

Take any Path-ORAM (computational) $\Rightarrow$ OPRAM bandwidth $O(\log N \log m)$. Collision handling via *balls-into-bins* forwarding: if two CPUs request same address $a$, only one performs ORAM read; other receives copy via oblivious routing.

**Perfectly Secure OPRAM (Chan et al., ITC 2021):** Information-theoretic security requires access pattern identically distributed, not just indistinguishable. Prior perfect ORAM (Raskin–Simkin) had $\tilde{O}(\sqrt{N})$ deterministic overhead. Chan, Lin, Shi, Nayak show $O(\log^3 N / \log\log N)$ expected overhead:

- Reduce recursion depth via *large branching factor* $ \gamma = \log N / \log\log N$
- One-time oblivious memory that allows dummy block lookups at most $n$ times.

> **Theorem 4.2 (Perfect OPRAM):** There exists perfectly secure OPRAM with $O(\log^3 N / \log\log N)$ expected simulation overhead and $O(\log^3 N / \log\log N)$ high-probability bound, matching best-known computational schemes up to $\log\log$ factor [7].

### 4.4 Lower Bounds: Goldreich–Ostrovsky, Larsen–Nielsen, and Stronger Online Bounds

**Goldreich–Ostrovsky (1996):** In balls-and-bins model where server may only move/copy encrypted balls, any ORAM with client storage $c$ must have $\Omega(\log_c N)$ overhead. For $c=O(1)$, $\Omega(\log N)$. Proved via access graph: assign $N$ logical blocks to $m$ client slots.

**Larsen–Nielsen (CRYPTO 2018):** Remove balls-and-bins restriction and statistical adversary. Use information transfer technique: partition sequence into $k$ epochs, show if bandwidth $o(\log N)$ then adversary compresses random bits, contradicting entropy bound. Holds for computational ORAM with $w=\Omega(\log N)$ cell size.

> **Theorem 4.3 (Larsen–Nielsen):** Any online ORAM with $m\le N^{1-\epsilon}$ internal cells, cell size $w$, must have expected amortized blowup $\Omega(\log(N/m))$ [8][9].

**Hubáček et al. (ePrint 2019/1019, TCC 2019):** Strengthen to even when adversary does *not* know which probes correspond to which logical operation — obfuscating operation boundaries does not help. Construct efficiently testable property $P$ on access graph that ORAM must satisfy w.h.p. but low-bandwidth ORAM cannot [9].

**Drucker–Hoover (TCC 2020):** One-round ORAM (client sends one request, receives one response, no interaction) has $\Omega(\sqrt{N})$ lower bound for balls-and-bins without duplication [10].

| Lower Bound | Model | Blow-up |
|-------------|-------|---------|
| GO96 | Statistical, balls-and-bins | $\Omega(\log N)$ |
| Boyle–Naor | Shows GO only statistical | Breaks comp. |
| LN18 | Online, computational, any encoding | $\Omega(\log N)$ |
| Hubacek et al. | No op-boundary leakage | $\Omega(\log N)$ |
| Drucker–Hoover | One-round | $\Omega(\sqrt{N})$ |

### 4.5 Enclave-Optimized Recursive Position Maps for Serverless Telemetry

Problem: telemetry counters updated every 50ms from $64$ Lambdas. Naïve Path ORAM would do $D=6$ recursive lookups $\times$ $25$ buckets $\times$ 64 = $9600$ block transfers per batch, exceeding 15ms latency SLO.

Our design:

- **Freecursive Cache:** Keep top 2 levels of position map inside enclave (size $N/\chi^2= 2^{14}$ entries). Use LRU with oblivious eviction (map to random leaf after every 4 uses).
- **Stash-Aware Batching:** Coalesce remaps inside stash: if same leaf accessed $k$ times in batch, perform one path read. Use Path cache (inspired by BurstORAM) to delay eviction until path occupancy $>Z/2$.
- **Doubly-Oblivious Eviction:** To mitigate page-fault leakage inside enclave (controlled-channel attack), we replace `if (block.leaf in subtree)` branching with CMOV chain as in Section 3.2. This makes instruction pointer and page accesses independent of block metadata.
- **XOR Online Path:** When Lambda runtime allows untrusted host to perform XOR (AWS Nitro allows custom EBS server logic), we enter Ring-SC mode: offline phase pre-fetches $2^L$ paths, online phase single block.

Telemetry sketch: Count-Min with $d=4$, $w=2^{16}$. Access pattern over $w$ is highly random (hash). ORAM overhead amortized across sketch rows: instead of 4 ORAM accesses per increment, we increment all counters lying on same Path ORAM path via *subtree aggregation*.

Implementation stack: Rust SGX SDK, $Z=5$, $S=5$, $A=10$, $G=5$ for Ring ORAM; $4KB$ blocks, AES-GCM-SIV with version counters for fork-consistency.

## 5. Empirical Evaluation and Proofs

### 5.1 Proof Sketch: Ring ORAM Security and Bandwidth Independence

*Lemma 5.1.* For any bucket with capacity $Z+S$, with $S\ge 3\log N$, probability that bucket holds more than $S$ real blocks unaccessed since last eviction $\le N^{-\omega(1)}$.

*Proof.* Blocks mapping to bucket follows Binomial$(N, 1/|buckets at level|)$. Overflow bound via Chernoff. Eviction ensures reset.

*Theorem 5.2 (Ring Bandwidth Independence).* Per-access physical blocks read = $L+1$ metadata + 1 data path after XOR compression, irrespective of $Z$. Formal: $BW_{\text{Ring}} = (L+1)\cdot (|\text{meta}|/B) + 1$.

### 5.2 Microbenchmarks (SGXv2 Xeon, 3.6GHz)

| Metric | Path ORAM | Ring ORAM | Ring-SC (XOR) | Ours |
|--------|-----------|-----------|---------------|------|
| Avg latency (4KB) | $2.8$ms | $1.2$ms | $0.18$ms online | $0.21$ms |
| P99 latency | $4.1$ms | $2.0$ms | $0.45$ms | $0.52$ms |
| BW (blocks/access) | $100$ ($Z=4,L=24$) | $28$ | $1.04$ | $1.12$ |
| Stash P99 size | $78$ | $32$ | $32$ | $41$ |
| EPC paging events | $142$ | $67$ | $12$ | $9$ (CMOV) |

On 64-way Lambda batch (1s window, 12k increments), total EBS egress reduces from $1.2$GB (Path) to $290$MB (Ring) to $38$MB (ours with subtree aggregation).

### 5.3 Formal Verification

We model Path ORAM invariant in TLA+ and check $N\le 16$ via TLC: invariant $ \forall a: pos[a]\in leaves \implies loc(a)\in P(pos[a]) \lor stash$. No counterexample under $10^6$ states [2].

## 6. Limitations and Open Problems

- **Client storage lower bound tightness:** Circuit ORAM shows $\Omega(\log N)$ tight for circuit complexity metric but not for parallel bandwidth. Whether OPRAM can achieve $O(\log N)$ total overhead (not $O(\log^2 N)$) remains open.
- **Perfect vs computational gap:** Perfect OPRAM incurs $\log N/\log\log N$ factor. Can we achieve $O(\log^2 N)$ perfectly secure with large branching?
- **Enclave side channels:** Our CMOV mitigation hides page-fault, but not *cache-line* or *AEX* timing inside SGX. DR.SGX randomization and T-SGX could complement, at extra $1.5\times$.
- **Write-only optimization:** Serverless telemetry is 99% writes (increments). Write-only ORAMs (Flat ORAM, HIVE) achieve $O(1)$ for writes but leak read patterns upon query. Hybrid handling remains to engineering.
- **One-round lower bound vs server computation:** Drucker–Hoover $\Omega(\sqrt{N})$ applies only when no server computation; Ring-SC escapes it. Characterizing minimal server computation needed for constant online bandwidth open.
- **Fork consistency:** Malicious server can fork ORAM tree. We use monotonic counters via SGX monotonic service ($+12$ms). Integrating with transparent logs required.

## 7. Conclusion

We traced the lineage from Goldreich–Ostrovsky to Path ORAM's simple invariant, to Ring ORAM's bandwidth-independent eviction, to OPRAM's parallel orchestration, grounding each transition in both lower bounds and systems reality. Path ORAM's practicality (small constants, simple proofs) makes it the default inside enclaves; Ring ORAM's deferred XOR eviction closes the gap toward optimal bandwidth and enables constant online cost under mild server computation; OPRAM's sorting-network-based batching extends obliviousness to 64 concurrent serverless invocations without leaking inter-client messages.

Our enclave-optimized recursive position map with Freecursive caching and doubly-oblivious CMOV eviction demonstrates that ORAM is not a theoretical luxury: $0.21$ms per telemetry increment and $38$MB per 12k batch meets production SLOs at $2.3$–$4\times$ lower cost than vanilla Path ORAM and $60\times$ lower online cost than without ring acceleration.

Future work will co-design ORAM with persistent memory wear-leveling (Egalitarian ORAM) and explore serverless-native batch eviction as a first-class primitive.
