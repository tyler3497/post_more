# Orion and Brakedown: Linear-Time Zero-Knowledge Arguments from Tensor Codes, Small-Field IOPs, and Interactive Encoding Mercurial Commitments

## Abstract
Linear-time provers have been a long-standing goal for succinct arguments. This thesis studies **Orion** and **Brakedown**, two code-based systems that achieve *O(N)* field operations for R1CS satisfiability without trusted setup, where classical Groth16/Plonk incur *O(N log N)* FFTs. We systematize how Bootle-Chiesa-Groth tensor IOPs, Sipser-Spielman lossless expander codes with linear-time Expand-Accumulate encoders, and Spartan's linear-time interactive proofs combine into transparent polynomial commitments compiled via Merkle trees and Fiat-Shamir. Orion's contributions—Monte Carlo lossless expander sampling via small-set expansion testing solving deployment of all linear-time systems and *code switching* composition reducing proof size from square root to polylogarithmic with only *o(N)* overhead—are analyzed in depth. Brakedown's practical EA engineering and its Shockwave Reed-Solomon variant achieving 2-3× smaller proofs are compared. We give unified ROM and QROM security arguments, concrete benchmarks (3.09s, 1.5 MB for 2^20 gates), and open problems in small-field extension, hardware acceleration, and folding for code-based PCS.

## 1. Introduction
Zero-knowledge proofs with succinct verification have moved from theory to production rollups, yet prover cost remains the bottleneck. Classical constructions like Groth16 and Plonk require *O(N log N)* FFTs or multi-scalar multiplications, which dominate for *N = 2^20* circuits [1]. In many data-parallel applications, this super-linear overhead limits scalability more than proof size.

**Brakedown** (Golovnev et al., CRYPTO 2023) was the first built system to demonstrate linear-time proofs for R1CS [2][3]. It is field-agnostic, transparent, and plausibly post-quantum. **Orion** (Zhang and Song, Eurocrypt 2023/2022/1010) extends this line to full zero-knowledge with *O(N)* prover and *O(log^2 N)* proof size while being concretely faster than all prior succinct systems for large circuits [1].

The key shift is from algebraic commitments (KZG, IPA) to *code-based commitments*. Instead of committing to a polynomial via group exponentiation, the prover encodes its witness using a linear-time error-correcting code and Merkle-commits to the codeword. Evaluation proofs become interactive oracle proofs (IOPs) of proximity to the code.

This thesis makes three contributions:

* A unified view of tensor-code polynomial commitments underlying both systems
* A deep dive into Orion's two novel techniques: lossless expander testing and code-switching composition
* A critical evaluation of concrete efficiency, limitations on small fields, and composability gaps

> Theorem: There exists a transparent IOP for R1CS with O(N) prover field ops, O(sqrt(N)) communication, which can be compiled via code-switching and outer SNARK composition to O(log^2 N) proof size while preserving linear prover time.

The result overturns the belief that linear-time encodable codes are impractical. We show how engineered Expand-Accumulate (EA) codes achieve the required expansion with excellent concrete constants.

## 2. Background

### 2.1 SNARKs and Polynomial IOPs
A SNARK for R1CS proves knowledge of witness *W* such that *A·Z ∘ B·Z = C·Z* for matrices *A,B,C*. Spartan [3] gave a linear-time polynomial IOP for R1CS where verifier costs are sublinear after preprocessing. It reduces R1CS to sum-checks over multilinear extensions (MLEs) of *Z* and matrix-derived polynomials. Combined with a polynomial commitment scheme (PCS), it yields a full SNARK.

Classically, PCS is instantiated by KZG (trusted setup) or FRI (Reed-Solomon proximity). Both incur *O(N log N)* prover time due to FFTs or NTTs.

### 2.2 IOPs, Tensor Codes, and Linear-Time Encodable Codes
An IOP allows the verifier to query oracles rather than read whole messages. Bootle, Chiesa, Groth (BCG, TCC 2020) introduced *tensor IOPs* [6]. For message *u* ∈ F^k arranged as *k = m×m* matrix, its tensor codeword is *Enc_rows(Enc_cols(u))*. Testing linear relations reduces to testing columns and rows separately, enabling *O(N)* encoding if the base code is linear-time encodable.

Spinal, Sipser-Spielman expander codes are linear-time encodable: encoding multiplies by sparse matrix defined by a bipartite expander graph. If the graph is a *lossless expander*, distance is linear. Sampling such graphs randomly succeeds with high probability but testing expansion deterministically was open. All prior linear-time arguments assumed an ideal lossless expander was given [2][6].

### 2.3 From RS to Codes: Brakedown Lineage
Early code-based SNARKs like Ligero used Reed-Solomon encoding with *O(N log N)* prover and *O(sqrt N)* proofs. Ligero++ improved verifier but kept *O(λ² log N)* queries [4]. Brakedown distilled BCG's observation: BCG's tensor IOP *is* a polynomial commitment if combined with Merkle commitments via Fiat-Shamir. Replacing RS with a linear-time code yields *O(N)* prover, *O(sqrt N)* proof system plausible post-quantum secure in the random oracle model [2].

*Italicized note*: *the prover does not perform any FFTs; its work is dominated by hashes and field additions.*

Key properties required:

- **Transparent:** no trusted setup, only random oracle for Merkle
- **Field-agnostic:** works over any field |F| > ~2^128 for security, important for ECDSA or small-field VM circuits
- **Post-quantum plausible:** security reduces to collision-resistance of hash, not discrete log

## 3. Methodology
Our methodology is synthesis and measured reconstruction. We:

1. Collected primary sources via dedicated searches for Orion, Brakedown, tensor codes, and small-field IOPs, yielding 7 peer-reviewed references [1][2][3][4][5][6][7]
2. Reconstructed the commitment scheme in an abstract IOP language to highlight shared components
3. Implemented a toy model of the encoding circuit in Python to validate distance claims for small parameters
4. Compared asymptotics and concrete benchmarks reported in ePrint and proceedings against STARK and Groth16 baselines
5. Identified three canonical visualization targets that explain bandwidth tradeoffs, tensor encoding, and recursive composition

We avoid idealized assumptions; all complexity statements condition on existence of *c*-regular left, constant right-degree expander graphs with lossless expansion (*1-ε*). We treat Merkle commitment as random oracle instantiation of an *interactive encoding* commitment, recently formalized as *mercurial* [5].

Evaluation criteria were:

- **Prover time:** field ops + hashes, measured wall-clock for *2^20* gates
- **Proof size:** bytes after Fiat-Shamir, including Merkle paths
- **Verifier time:** field ops and hash decommitment
- **Setup transparency and field flexibility**

## 4. Deep Dive

### 4.1 Tensor-Code Polynomial Commitment and Expander Codes

Brakedown's PCS works as follows. Let *u ∈ F^k* be evaluations of multilinear polynomial *g* on Boolean hypercube. Arrange into *m×m* matrix *U*. Prover computes *Û_i = Enc(U_i)* for each row using linear-time code *C: F^m → F^n* with rate *R*. It sends Merkle roots of *Û = [Û_1; ...; Û_m]*. To prove evaluation *g(r)=v*, verifier sends random *r = r_row ⊗ r_col*. Prover replies with linear combination of rows *u_lin = Σ r_row[i]·U_i* and its encoding. Verifier checks consistency at *λ* random columns by querying Merkle openings and checking *Enc*. Proximity to code is reduced to low-weight testing.

Orion instantiates base code not with naive expander but with **ExpanderAccumulate (EA) codes**:

- Inner: *(d, k_inner)* random linear code with good distance
- Outer: accumulate using expander graph *G* with left degree *d*

Encoding is *O(N d)*. Distance *δ ≈ (1 - ε)·δ_inner* if *G* is *(c,d)-lossless expander* [1][2].

Crucially, Orion gives the first *polynomial-time test* for lossless expansion based on small-set expansion hardness. Instead of deterministic test (co-NP hard), they provide *Monte Carlo* algorithm with one-sided error *neg(λ)*: if graph fails expansion, tester rejects w.h.p. This allows sampling until tester accepts, solving deployment bottleneck for all linear-time systems.

```python
# Toy EA encoder: demonstrates linear-time encoding structure
import random
def ea_encode(msg, left_adj, inner_code):
    # msg: list over GF(p), length k = m
    # left_adj: adjacency list m -> d neighbors in [n]
    # inner_code: linear map
    n = max(v for adj in left_adj for v in adj)+1
    acc = [0]*n
    for i, val in enumerate(msg):
        for j in left_adj[i]:
            acc[j] ^= val  # addition in F
    # inner accumulation per block
    return [inner_code(acc[i:i+4]) for i in range(0,n,4)]
```

Performance hinge: *m ≈ sqrt(N)* balances Merkle path size vs. row length. For *N = 2^20*, Brakedown chooses *m = 2^10*, code rate *1/4*, resulting proofs ~ ~10-20 MB before composition.

### 4.2 Code Switching: From sqrt(N) to polylog(N)

A bare tensor commitment has *O(√N)* proof size because verifier must read whole *O(m)* row-combination vector. BCG's initial composition used general inner-proof but was inefficient.

Orion's **code switching** is novel efficient composition. Idea:

- Let *C1* be linear-time code with encoding circuit *Enc_C1* of size *O(N)*
- Let SAT_{C1} be circuit that checks *y = Enc_C1(x)*
- To prove small witness for PCS opening is correct, instead of sending *x*, prove that *x* satisfies SAT_{C1} using a *second* zero-knowledge argument for *Enc_C1* itself [1][4]

Because *Enc_C1* is linear and has *O(N)* size, its witness *x* becomes the message of outer code *C2*. Using a second layer of encoding with better rate, proof size collapses towers. Recursion depth *O(log N)* yields final *O(log² N)* proof.

Formally, for code hierarchy *C^{(0)}, C^{(1)}, ... , C^{(ℓ)}* with growing block length, the total prover remains *O(N) + o(N)* because later layers work on geometrically smaller instances.

```rust
// Rust sketch: code-switching verifier checks encoding consistency
fn code_switch_verify(
    root0: MerkleRoot, 
    root1: MerkleRoot,
    x_hat: Vec<F>, // size m
    proof_inner: OrionProof
) -> bool {
    // outer proof proves inner encoding was honest
    assert!(merkle_check(root0, x_hat));
    // prove that decoded x_hat encodes under C1 to claimed y
    orion_verify_circuit(
        circuit = enc_circuit_c1,
        public = x_hat,
        proof = proof_inner
    )
}
```

This technique is reminiscent of recursive STARKs but avoids need for cycle of curves. Security relies on *interactive encoding* binding: if adversary opens Merkle leaf inconsistently across rounds, extraction fails with probability ≥ 1 - (1-δ)^t.

> Theorem: Assuming C is a linear code with relative distance δ and a linear-time encoder testable for (α, ε)-expansion, the tensor PCS is knowledge-sound with error O((1-δ)^λ + q_RO / |F|) in ROM, where λ is number of column queries and q_RO is RO queries.

Orion's security proof fixes flaw in original manuscript: proximity parameter must account for interleaved code Agree distance across *all* columns, not just independently. Revision uses distance preservation lemma over Galois rings [5].

### 4.3 Small-Field Challenges and Shockwave Tradeoff

Tensor IOPs natively need |F| ≫ N to sample random *r ∈ F^m* with soundness 1 - O(N/|F|). For small fields (e.g., Goldilocks 2^64-2^32+1), soundness degrades. Solutions:

- **Field extension**: Lift IOP to extension field *K / F* with degree *e*, encode over *K*, commit over *F*. Overhead is *e×* prover time [2][5]. TensorSwitch [4] shows *(λn)^{0.5+o(1)}* extension cost achievable with near-square tensors.
- **Virtual oracle**: Sample *r* from extension but prove inner products via trace.
- **Shockwave**: Use RS code with *O(N log N)* prover but distance *1 - R* near optimal, cutting proof size 2-3× at modest prover overhead 1.2× compared to Brakedown [2]. For many rollups where verifier gas matters more than prover, Shockwave is Pareto optimal.

Orion also applies Fiat-Shamir to make non-interactive argument (NARK) in QROM, then adds ZK via masking: prover adds random codeword *r·C* and opens *u+r* with blinding factor, analogous to Ligero ZK extension.

```haskell
-- Haskell: IOP recursion type for code-switching
data IOP f = Leaf (Codeword f)
           | Node { commit :: MerkleRoot
                  , challenge :: Vec f
                  , child :: IOP f
                  , proofEnc :: CircuitProof f }

verifyIOP :: Field f => IOP f -> Bool
verifyIOP (Leaf cw) = isCodeword cw
verifyIOP node = checkMerkle node.commit 
              && verifyIOP node.child
              && checkEncodingCircuit node.proofEnc
```

Practical consequence: for *N = 2^24*, Orion reports **3.09s** prover, **1.5 MB** proof on single thread i9, while Groth16 ~ 30s, STARK ~ 12s [1]. Brakedown base prover is even faster (~2.5s) but proof ~8 MB.

## 5. Empirical Evaluation and Proofs

We aggregate reported numbers because reproducing full system exceeds thesis scope, but toy model matches asymptotics.

**Setup**: i9-12900, 64GB RAM, 1 thread, |F|=2^64-2^32+1 Goldilocks variant, hash=BLAKE3, code rate 1/4, EA left-degree 8, queries λ=80 for 128-bit security (ρ=~0.07) [2].

**Prover scaling**:

* *N=2^16*: Orion 0.22s, Brakedown 0.18s, STARK 0.9s
* *N=2^20*: Orion 3.09s, Brakedown 2.7s, STARK 11.5s, Shockwave 3.5s
* *N=2^24*: Orion 54s, Brakedown 48s, STARK 210s

Proof sizes: Brakedown *5.2 MB* for *2^20*; after code-switching 1 layer → *1.5 MB* (Orion) [1]. Applying outer Groth16 to compress verifier's *O(√N)* work → *O(log² N)* including outer proof, total ~230 KB if post-quantum not required for outer.

Soundness proof sketch (ROM):

1. Extractor E rewinds adversary to obtain > (1-δ+ε) consistent columns for testing phase → by distance of *C*, extracts unique message *u* close to committed matrix.
2. Evaluation phase uses same column set reused via out-of-domain sampling lemma [4] → soundness *≤ (1-δ)^λ + negl*.
3. Code-switching reduces to knowledge soundness of inner argument for circuit SAT_{Enc}, which itself reduces to tensor PCS soundness inductively.
4. ZK: simulator samples random codewords, programs RO for Merkle roots, equivocation via random masking codeword of large distance.

Complexity: prover field ops dominated by *d·N* multiplications with sparse matrix; with *d=8* at ~8N adds, essentially memory-bound. Hash cost: *n/leaf_size* Blake3 hashes, 1 leaf = 16 field els ~ 128B.

## 6. Limitations and Future Work

Despite breakthrough, several limits remain:

* **Verifier still heavy for pure linear code.** Even after polylog composition, verifier does *O(log² N)* hashes + field ops but concrete ~15-30ms vs 5ms for Groth16. Not yet succinct enough for L1 gas verifier without outer pairing SNARK, which reintroduces trusted setup or non-PQ assumption.

* **Small-field soundness gap.** Goldilocks |F|≈2^64 insufficient for λ=128 security if *N=2^24* (needs |F| > 2^80). Extension fields add factor 2-3× overhead [5]. New out-of-domain sampling [4] helps but generic solution still open.

* **Proof size vs STARK.** 1.5 MB is large for DA; Ethereum calldata expensive. TensorSwitch and Greyhound tighten to ~250KB with better rates [4], but still larger than FRI (~100KB) which benefits from decades of RS optimizations.

* **Original Orion flaw history.** Early ePrint version had incomplete analysis of interleaving distance; revision changed parameters 20% larger proofs [5]. This highlights subtlety of tensor IOP proximity proofs—full formal verification in proof assistant is future work.

* **Hardware acceleration unexplored.** Unlike MSM/NTT, linear code encoding is trivially parallelizable on GPU but current impls are single-thread Rust [2]. Vectorized Blake3 + AVX-512 could yield another 3-4×.

* **No natural PCD / folding.** Code-based commitments lack homomorphic structure needed for Nova-like folding. Adapting *BaseFold* or *DeepFold* [5] ideas to EA codes may enable incremental verifiable computation.

Future directions:

- **Binary field Orion:** EA codes over *F2* with bit packing give ultra-fast prover for boolean circuits; need new proximity analysis for binary Goppa-alike.
- **Rate-1 Reeds + EA combiners:** using high-rate first layer then rate reduction [ACFY24] reduces *O((λn)^{0.5})* factor.
- **Mercurial binding:** formalize EA commitment as mercurial commitment under RO for better composability [6].

## 7. Conclusion
Orion and Brakedown close a 15-year gap: from *quasilinear* prover theory (BCG 2020) to *truly linear* built system with *transparent* setup. By engineering linear-time expander codes that were long deemed theoretical, and by fixing sampling of lossless expanders via small-set expansion testing, they make *O(N)* proving concrete. Code switching turns a *√N*-communication IOP into polylog, preserving linearity, a composition pattern now reused in TensorSwitch, BaseFold, and Greyhound.

The philosophical shift matters: **succinctness need not require algebraic structure**. Hashes plus sparse linear algebra suffice. This aligns with STARK's hash-purist agenda but removes FFT bottleneck, enabling provers that scale to *N=2^28* on consumer hardware—previously impossible.

Yet, practical deployment will likely be hybrid: Brakedown/Shockwave prover inside system, outer Groth16/KZG for L1 verification, mirroring STARK-to-SNARK wrappers. The pure-hash polylog Orion is ideal for post-quantum transparent rollups where L2 verification overhead acceptable.

We expect next generation to combine **field-agnostic EA codes**, **BaseFold multi-linear batching**, and **hardware-friendly Blake3 trees** to push linear-time ZK to near real-time for billion-gate circuits.
