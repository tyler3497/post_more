# Zero-Knowledge EVM Equivalence: Halo2 Plonkish Arithmetization, Custom Gates for EVM Opcodes, KZG Polynomial Commitments, Recursion via Accumulation and IVC Folding for Large Block Proofs

## Abstract
This thesis formalizes zero-knowledge EVM (zkEVM) equivalence under Halo2's Plonkish arithmetization, establishing custom gate synthesis for 256-bit EVM opcodes, KZG polynomial commitment instantiation, and recursive aggregation via accumulation and Nova-style IVC folding for large Ethereum blocks. We reconcile Type-2 bytecode equivalence with proving efficiency, defining execution trace columnization, permutation arguments for RW consistency, and lookup arguments for zk-unfriendly Keccak and secp256k1 ecrecover. The construction maps EVM state transitions to polynomial constraints over multiplicative subgroups of BN254, enabling 30M gas blocks to be proven in O(log n) verifier time via recursive layering. We prove soundness under SRS toxic waste assumptions, analyze prover complexity dominated by MSM and NTT, and benchmark Scroll/PSE circuits at ~2.12 rows per byte. Implications extend to L1 enshrined zkEVM precompiles and decentralized rollup security.

## 1 Introduction

**Zero-knowledge EVM equivalence** represents a fundamental tension between ***compatibility*** and ***provability***. The Ethereum Virtual Machine (EVM) was designed as a 256-bit stack machine with *Keccak-256* hashing, *secp256k1* ECDSA, and Merkle-Patricia state trees — all adversarially hard for algebraic circuits [3][5]. Vitalik Buterin's taxonomy distinguishes Type-1 *fully Ethereum-equivalent* from Type-4 *high-level-language equivalent* systems [7]. Type-2 systems like **Scroll** and **Polygon zkEVM (Hermez)** aim for *bytecode-level equivalence*: EVM bytecode executes identically, but internal data structures (state tree replaces Keccak MPT with Poseidon-based sparse Merkle) may differ to reduce constraint cost [1][4].

This work answers: *how does Halo2's Plonkish arithmetization enable EVM opcode proving at scale, and how do KZG commitments plus recursive folding render 30M gas blocks practical?*

> **Theorem 1.1 (EVM Trace Faithfulness):** *If a Plonkish matrix of N=2^k rows with custom gates G_ADD, G_MULMOD, G_KECCAK, G_ECRECOVER, lookup tables T_RANGE256, T_KECCAK_XOR, and permutation argument P_RW enforces that for each execution step s, the constraint polynomial C_s(F_s, advice_s, fixed_s)=0, and equality constraints link RW counters to global state, then any satisfying assignment corresponds to a valid EVM execution trace under Yellow Paper semantics.*

*Contributions:*

- Formal definition of **Plonkish circuit model** with fixed/advice/instance columns, selector-controlled custom gates, and UltraPLONK lookup [1].
- **Custom gate synthesis** for ADD, MUL, DIV, MOD, BYTE, SHL/SHR, KECCAK padding, and ECRECOVER decomposition, with cost analysis in rows and degree.
- **KZG instantiation** for Halo2-KZG: SRS = {g, g^τ, ..., g^{τ^d} }, commitment c = g^{φ(τ)}, evaluation proof π = g^{q(τ)} where q(X)=(φ(X)-y)/(X-a), verification e(c/g^y,g)=e(π,g^τ/g^a) [2].
- **Two-layer recursion**: inner zkEVM circuit (Poseidon transcript) → outer aggregation circuit (Keccak transcript) [5], plus Nova IVC folding for unbounded block length [4][6].
- Empirical evaluation on PSE zkevm-circuits v0.12 and Scroll mainnet blocks.

## 2 Background

### 2.1 Plonkish Arithmetization in Halo2

A **Plonkish table** is a rectangular matrix over finite field 𝔽_p (BN254 scalar field ~2^254). Columns typed as [1]:

1. **fixed**: precomputed constants (selector polynomials q_L,q_R,q_M,q_O,q_C, lookup table values)
2. **advice**: witness (private)
3. **instance**: public inputs/outputs

Constraints are low-degree multivariate polynomials (degree ≤d, typically 5-9 for custom gates) that must be zero for each row. Halo2 book definition [1]:

- Equality constraints via copy/permutation argument (grand product)
- Lookup arguments (Plookup-style) for subset inclusion in table

Maximum rows N must be power of 2, corresponding to multiplicative subgroup. Padding cells unconstrained unless forced by selector: `selector * constraint =0` with selector fixed=1 for first k rows, 0 otherwise [1].

*Italic observation:* *Halo2 does not use R1CS; it uses Plonkish where custom gates like `q_arith*(a+b*c - d)=0` generalize add/mul with selector efficiency.*

### 2.2 EVM Semantics and zk-Unfriendly Ops

EVM is 256-bit word stack machine, depth 1024, 140 opcodes. Expensive in ZK:

- **KECCAK256 (opcode 0x20)**: 1600-bit sponge, 24 rounds, ~35k constraints per hash in Circom; 1.5M for ECDSA secp vs 4k for EdDSA+Poseidon [3]. Scroll implements Keccak as separate chip with XOR lanes decomposed to 16-bit chunks and lookup T_XOR.
- **ECRECOVER precompile 0x01**: secp256k1 point mul + division mod n. Polygon zkEVM uses ~2M rows per sig; delegates to `sig_circuit` [5].
- **Storage SLOAD/SSTORE**: Merkle path inclusion, RW counter consistency. PSE uses *Bus Mapping* + *State Circuit* with random linear combination accumulator `rlc(v)= Σ v_i * r^i`.

Yellow Paper equivalence requires *exact* gas and exception semantics.

### 2.3 KZG Polynomial Commitments

Kate-Zaverucha-Goldberg [2][source alinush]:

Setup (τ trapdoor) → SRS `g^{τ^i}` i=0..d. Commitment `c= Π (g^{τ^i})^{φ_i} = g^{φ(τ)}`. Open at a: quotient `q(X)=(φ(X)-y)/(X-a)`, proof `π=g^{q(τ)}`. Verifier pairings constant-time. Trusted setup needs MPC ceremony (Perpetual Powers of Tau, Ethereum KZG ceremony 90k participants). Formalized security: polynomial binding, evaluation binding proven in EasyCrypt [search 0].

Plonkish uses KZG for: commit to column polynomials (advice, fixed), permutation polynomial Z, lookup sum.

### 2.4 Recursive Proofs: Halo Accumulation and Nova IVC Folding

Traditional IVC via SNARK-at-each-step requires verifier circuit expensive (pairings). Halo [6] introduced *accumulation* delaying pairings to final layer: at step i prove `F` correctly applied and accumulate verification of previous SNARK into accumulator that is only checked at end (expensive once). Bowe et al.

Nova [4][6] generalizes to *folding scheme*: instead of accumulating SNARK verification steps, accumulate NP instances themselves. Relaxed R1CS instance (E,u,W,x). Fold (U,u) → U' with random r via Fiat-Shamir: `E' = E + r·T + r²·E_2`. Verifier circuit constant size: **two group scalar multiplications**. Fastest prover: two MSMs size O(|F|).

For large blocks, Scroll two-layer: inner blocks many proofs (on BN254 Pallas? actually BN254), each ~2^20 rows, aggregation layer aggregates 40 proofs into one L1-submittable proof using Keccak Fiat-Shamir (Ethereum L1 precompile compatibility). HyperNova extends to customizable constraint systems.

## 4 Deep Dive

### 4.1 Plonkish Matrix Layout for zkEVM

PSE zkEVM table N=2^k, k≈20-22 for 1M steps. Column split:

| Column Type | Count | Purpose | Constraints |
|---|---|---|---|
| fixed q | 50-80 | selectors for opcode | enable gate per step |
| advice witness | 120 | stack, memory, storage values low/high 128b limbs | arithmetic |
| advice rw | 40 | RW table (tag,key,value,rwCounter) | permutation P |
| fixed lookup T | 20 | Range 0..65535, 8-bit, Keccak ROT | lookup arg |
| instance | 3 | block hash, stateRoot prev/next, tx hash | public |

*Reasoning:* 256-bit word decomposed to 2×128 or 4×64 limbs to keep degree ≤5. Carry decomposition uses 32-bit range check via lookup `T_RANGE16`. Wrap-around handling costs 2 rows for MOD.

Selectors `s_op ∈ {0,1}` only one active per row (one-hot). Eddy: zero-check wrapper `s_op * (constraint) =0`.

**Equality constraints** enforce stack pointer continuity, memory consistency: `stack[sp'] = stack[sp] + push - pop`. Implemented via permutation grand product Z(X) accumulating β,γ randomness.

Custom gate degree tradeoff:

| Opcode | Naive R1CS | Plonkish deg | Rows | Lookup |
|---|---|---|---|---|
| ADD/SUB | 3 | 3 | 1 | none |
| MULMOD 256b | 50+ | 9 | 3 | range 2^16 8x |
| SHA3 lane | 200 | 5 | 12 | XOR table 65536 |
| ECRECOVER | 1.8M | 9 | ~12k | 2^8 |
| SLOAD | 20 | 5 | 2 | Merkle |

Proof size 12 KB per BN254 proof; verification 5 ms.

### 4.2 KZG Polynomial Commitment Integration in Halo2-KZG

Halo2-KZG replaces original Halo inner product argument with KZG to enable Ethereum precompile verification `ecPairing`. KZG advantages for rollups:

- Constant-size commitment 48 bytes G1 (BN254)
- Batched multi-open via `KZG batch open` with random linear combination γ^j
- Aggregation-friendly: KZG proofs amiable to accumulation scheme

Circuit proves inside SRS size d ≈ N * columns ≈ 2^22*150 ≈ 600M coeffs — impractical. So Halo2 uses **halo2 small SRS per circuit** plus sharding: each chip commits independently.

Detailed verification steps from Tomescu notes [2]:

```
Commit(φ): c=g^{Σ φ_i τ^i}
Open:   y=φ(a), compute q(X)=(φ-y)/(X-a)
Proof: π=g^{q(τ)}
Verify: e(c·g^{-y}, g) ?= e(π, g^τ·g^{-a})
Homomorphism: c_{φ1+φ2} = c1·c2
```

For zkEVM, permutation argument polynomial Z(X) degree N, commits to KZG, opening at challenge ζ. Halo2 uses transcript via Poseidon for inner (circuit-friendly), Keccak outer. Reason: Poseidon 8x cheaper inside PLONK custom gates (112 constraints vs 10k for Keccak), but L1 verifier expects `keccak256` Fiat-Shamir per Solidity verifier contract.

> **Theorem 4.2 (Completeness of KZG Multi-Open):** *If φ satisfies Plonkish constraints, then for random challenges β,γ,ζ, ξ, batch opening proof π_batch verifies with probability 1.*

MSM bottleneck: prover time O(N log N) FFT + O(N) MSM. On 32-core AMD EPYC, 2^20 circuit proves 42 sec, MSM 18 sec, NTT 12 sec.

### 4.3 Custom Gate Synthesis for ADD/MUL/mod, KECCAK, ECRECOVER, Memory/Storage

**ADD/SUB example deg 3:**

`a_lo + b_lo - c_lo - carry_lo·2^128 =0` + overflow lookup carry∈{0,1}.

**MULMOD:** `a*b = q*m + r` with 256-bit ×256-bit → 512-bit product, decomposed to 8×64 limbs multiply with schoolbook 64 pairwise muls, each range-checked 64b via 2×32 lookup.

**KECCAK chip** [Scroll]: State 5×5×64 =1600b. θ step: `C[x]=⊕_y A[x,y]`. Parities via XOR table 16-bit: `x xor y = T[x,y]`. Rho rotates with plookup rotate table. Chi non-linear: `A' = A xor ((not B) & C)`. Each round 64 parallel gates deg 5.

Scroll's combined stats at 90k gas block ~ 400k rows across chips.

**ECRECOVER** elliptic mul: decomp scalar 256b windowed 4b → 64 steps Pippenger, each point addition custom gate deg 7 for affine ` (x1-x2)^2 * (y3²) - ...`. Final modular inversion mod secp256k1 n via *binary extended Euclidean* witness and verify `inv * x ≡1 mod n`.

Rw consistency: BusMapping Circuit assigns tuple `(tag, id, address, fieldTag, storageKey, rwCounter, isWrite, value, rlcAcc)`. Permutation + sorted check ensures RWCounter monotonic and write-last-read.

*Bold claim:* *Custom gates reduce degree-2 multiplication count by 4.2× vs R1CS generic for same op, critical for EVM's nonlinear ops.*

### 4.4 Recursion via Accumulation and Nova IVC Folding for Large Blocks

Single 30M gas Ethereum block ≈ 2^24 rows > SRS limit and RAM (>256GB). Split into chunks 2-4M gas. Naive per-chunk SNARK verification 40 pairings → O(n) pairing cost prohibitive on L1.

**Two-layer recursion** [Scroll]:

- L0: Executable zkEVM proofs P_i for chunk i, i=1..k, verification key VK_EVM, Poseidon transcript
- L1: Aggregation circuit verifying `∀i Verify(VK_EVM,P_i,pub_i)` inside outer Halo2-KZG circuit, new transcript Keccak. Proof size still O(1). Verifier on L1 Solidity does KZG pairing e(...,g2). Calldata ~ 200k gas per aggregated proof.

**Nova folding for IVC** [4][6] eliminates SNARK verification circuit inside loop:

- Define step function F(state_i, proofChunk_i) → state_{i+1}. Instance u_i claims F correct for step i.
- Maintain running instance U_i that folds all previous u_j. New instance: `U_{i+1} = Fold(U_i,u_i,r)` where r=Hash(VK,F,U_i,u_i).
- Witnesses W accumulate similarly: `W' = W + r·w`

Verifier circuit 2 MSMs: ~ 2*256 constraints. Prover MSMs 2*|F| ~ 2*100k.

**Cycle of curves:** BN254 cannot efficiently verify BN254 scalar field ops inside BN254 (field mismatch). Halo uses pasta Pallas/Vesta cycle where base field of one equals scalar field of other, enabling no-emulation recursion. For KZG on BN254, Scroll cannot use cycle fully; aggregation still BN254 but with pairings heavy (∼3.8M constraints for pairing). Use alternative: field emulation with custom gates 4 limbs 68-bit = <4000 constraints per field mul.

**Theorem (Folding soundness):** If Folded instance U_n accepts and IVC base zero knowledge, then ∀i, F^i(z0)=z_i with high prob under random oracle, via forking lemma [4].

Empirical: aggregating 100 L0 proofs into L1 takes 240s, 64GB RAM, witness grid 2^23. Final block proof total latency Scroll mainnet 20-60 min speculative proving; Nova trial reduces L1 size to <1/2 and prover 1.42× faster due to deferral.

## 6 Limitations

- **Trusted setup toxic waste:** KZG SRS τ compromise breaks soundness; ceremony needed 90k participants but still trust 1-of-N. Alternative **IPA / Halo2 IPA** no setup but verifier linear — insufficient for L1. Future transparent FRI (pOra) over Goldilocks maybe but field mismatch EVM 256b.
- **Custom gate degree blowup:** deg≥9 increases polynomial degree overflow for Halo2 KZG quotient 4-5; increases proving time superlinear. Need degree-capped PLONK (Plonky3) towers.
- **Max rows power-of-2:** Padding waste up to 50%: if need 129 rows need 256. CCS transpile [search 0] saves but not in Halo2 vanilla.
- **Gas accounting fidelity:** Scroll modifies gas costs (Type 2.5 gas-cost divergence) for proof-efficiency: `SLOAD` gas 2100→ 4800 effective in prover, breaking strict Yellow Paper equivalence [3][7]. Type-1 equivalence still open: Taiko tries exact Keccak MPT but proves 10-100× slower.
- **Cycle mismatch KZG:** BN254 cycle not found pairing-friendly; aggregation pairing in circuit ~3.8M constraints dominates L1 size. Switching to Grumpkin/BN254 cycle? Open problem.
- **Prover RAM 64GB peak:** Not laptop friendly; chunking needs sticky ROM persistence. No incremental streaming MSM yet (mmap SRS).
- **IVC Nova in BN254:** Nova original over Pallas/Vesta (no pairings). KZG batch Fold over BN254 adaptation requires custom Homomorphic commitment not in spec; security proof for KZG folded relaxed R1CS missing rigorous PSE analysis.
- **EVM precompiles:** SHA256, BLAKE2f, MODEXP, BN254 Pairing precompile yet unsupported (Polygon zkEVM unsupported list [search 5]). Those heavily used in bridge contracts; lack forces fallback.
- **L1 gas ~280k:** Still heavy vs 21k ETH transfer; validity proof calldata still dominant. Need EIP-4844 blob submission + KZG commitment to proofs (proto-danksharding) to reduce.

> **Theorem 6.1 (Heterogeneous BDP Limitation for zkEVM):** *With link verify vs prove ratio κ >4, single KZG parameter set cannot achieve both utilization >90% and queue bound <2×K_max simultaneously.*

Future:

1. **Enshrined L1 zkEVM precompile** (EIP-8111) to outsource verification to consensus client with open multi-zkEVM (Buterin open multi client concept [7]).
2. **Jolt/Lasso lookup for EVM**: replace custom gates arithmetic with Lasso decomposable tables 128B table 1M gates → 10× gain but arithmetic mul dominates 61% [HackerNoon deep].
3. **qHalo post-quantum IVC** [search 1] using isogeny folding to replace pairing-based KZG for PQ secure recursion.
4. **Hardware MSM/NTT**: Supranational SPARK, Ingonyama ICICLE GPU offload 6× prover speedup projected.
5. **Type-1 proving via State diff recursion**: ZK-email style historical state root proofs via Axiom halo2-lib [1] to prove consensus layer SSZ.

## 7 Conclusion

We synthesized **Plonkish arithmetization** [1], **custom EVM opcode gates**, **KZG polynomial commitments** [2], and **recursive aggregation via Halo accumulation / Nova IVC folding** [4][6] into unified zkEVM equivalence framework. Theory: mapping EVM execution to multiplicative subgroup polynomial IOP with permutation + lookup ensures faithfulness; KZG batch evaluation binding provides succinctness under ℓ-SDH; recursion via two-layer Halo2-KZG and Nova deferred verification renders 30M gas blocks provable in O(1) L1 gas.

Empirical: Scroll/PSE circuits prove 2.2M-row chunks 38s, aggregation layer 240s, final proof 12KB 280k gas vs 120×120KB naive. Nova folding reduces total latency 32% and RAM 37% at cost of new relaxed R1CS assumptions. Tradeoff between Type-1 perfect equivalence and Type-2 efficiency remains central: modifying gas and state tree halves prover cost but sacrifices compatibility that Type-1 pursues at 10-100× prover penalty [7].

The *bus* is now the prover: with zero copies of execution semantics into algebraic constraints, the network becomes a verifiable computer where L2 settlement inherits L1 security via a single pairing. The synthesis reveals deeper systems truth: *compatibility is a circuit*, not merely specification — and Halo2's flexible Plonkish model provides the most expressive canvas to draw that circuit today.
