# The Rust Borrow Checker: Non-Lexical Lifetimes, the Polonius Datalog-Based Rewrite, Place Capabilities, Two-Phase Borrows, and the Soundness of Stacked Borrows versus Tree Borrows

## Abstract

Rust's memory safety rests on two pillars: a *compile-time* borrow checker that validates region lifetimes over the MIR control-flow graph, and a *runtime* aliasing discipline governing raw pointers in `unsafe` code. We reconstruct Non-Lexical Lifetimes (RFC 2094) as liveness combined with outlives constraints propagated through a subset graph [1][2]; formalize the Polonius rewrite as a Datalog-specified, location-sensitive "unified graph" analysis and survey the 2025–2026 alpha stabilization effort [3][4][5]; explain two-phase borrows as the mechanism that makes `vec.push(vec.len())` sound [6]; and contrast Stacked Borrows (Jung et al., POPL 2020) — a stack of per-location permission items with Coq-mechanized optimization proofs — against Tree Borrows (Villani et al., PLDI 2025), which replaces the stack with a tree, rejects 54% fewer of the 30,000 most-used crates' tests, and repairs Stacked Borrows' unsound handling of two-phase borrows [7][8][9]. Both models are empirically validated inside Miri, which POPL 2026 establishes as the first tool detecting all de-facto undefined behavior in deterministic Rust programs [10].

---

## 1. Introduction

Rust promises *fearless* memory safety without a garbage collector: every value has exactly one owner, temporaries are freed deterministically at the end of their lexical owner, and references (`&T`, `&mut T`) may only observe memory that outlives them. The static enforcement of this discipline is the **borrow checker**, arguably the most scrutinized component of `rustc`. Yet the borrow checker alone cannot tell the whole story. Rust deliberately permits `unsafe` blocks in which raw pointers (`*const T`, `*mut T`) bypass all compile-time aliasing checks; the question that has occupied a decade of research is then: *what aliasing rules must unsafe code obey so that the compiler's aliasing-driven optimizations remain sound?*

This thesis examines the full vertical stack of Rust alias analysis, from source-level region inference to operational memory models: Non-Lexical Lifetimes as flow-sensitive region inference (§4.1), the Polonius Datalog rewrite and its 2026 alpha stabilization (§4.2), two-phase borrows (§4.3), and the Stacked Borrows vs Tree Borrows soundness comparison validated in Miri (§4.4–4.5).

> **Thesis claim.** Sound, *practical* Rust requires **both** a precise compile-time borrow analysis (NLL → Polonius) **and** a runtime aliasing model for unsafe code (Stacked Borrows → Tree Borrows); the two are complementary — the former decides which programs the type system accepts, the latter decides which executions the compiler may assume well-defined — and both are validated by the same oracle: Miri.

## 2. Background

### 2.1 From lexical scopes to flow-sensitive regions

Before Rust 1.31 (December 2018), every borrow's lifetime was tied to a **lexical scope**: a borrow created inside a block lived until the end of that block. This was simple to explain but brutally conservative. Code such as

```rust
let mut s = String::from("works");
let t: &mut String = &mut s;
s.push('?'); // ERROR under lexical lifetimes
println!("{}", s);
```

was rejected even though `t` is never used after line 3 — the borrow of `s` was considered live until the closing brace regardless. Programmers responded with the well-known "add extra braces" workaround, which is not evidence of safety but evidence of the analysis's imprecision [4].

### 2.2 The Mid-level Intermediate Representation (MIR)

The modern borrow checker does not operate on the AST. It operates on **MIR**, a control-flow graph (CFG) of basic blocks containing assignments, borrows, drops, and calls. Lifetimes become *regions*: abstract sets of CFG points, no longer contiguous lexical intervals. Region inference then reduces to a dataflow problem: for each region variable, compute the set of points at which it must be live, and check that every borrow's region is contained within the borrowed place's validity region.

### 2.3 The optimization–unsafe tension

The type system is not merely a safety device; it feeds the optimizer. A guarantee that `&T` data is immutable licenses LLVM to hoist reads and attach `noalias`/`dereferenceable` attributes to function arguments [8][9]. But `unsafe` code can fabricate aliasing `&mut T` values that the compiler cannot see. The community therefore needed an **operational aliasing model**: a precise, executable definition of which pointer uses constitute *undefined behavior* (UB), such that any program avoiding UB is one the optimizer may transform freely. This is the role filled first by Stacked Borrows [7] and now by Tree Borrows [9].

## 3. Methodology

We proceed by reconstructing each analysis from its primary sources and, where available, its executable specification:

1. **NLL** — from RFC 2094 and Niko Matsakis's design notes [1][2]: liveness of locals at each MIR point, liveness of regions derived from the types of live locals, and outlives constraints from subtyping, all combined in a fixpoint over the subset graph.
2. **Polonius** — from the `rust-lang/polonius` Datalog rule set, the 2023 *Inside Rust* update, and the 2025–2026 project-goal documents [3][4][5]: we present the *alpha* design as a "unified graph" `U` whose nodes are `(region, point)` pairs.
3. **Two-phase borrows** — from RFC 2025 ("nested method calls") and the internals discussion [6]: we treat `&mut2` as a borrow with a reservation phase and an activation point.
4. **Stacked/Tree Borrows** — from the POPL 2020 and PLDI 2025 papers [7][9] and the `unsafe-code-guidelines` operational description [8]: per-location permission state, transition rules on access, and protector semantics for function arguments, cross-checked against the reported Miri evaluations [10].

Our evaluation criterion throughout is *two-sided soundness*: an analysis must neither reject too much correct code (precision) nor accept executions that invalidate compiler assumptions (soundness).

## 4. Deep Dive

### 4.1 Non-Lexical Lifetimes: liveness meets outlives

The central insight of NLL (RFC 2094, Matsakis) is that a borrow need only be *live* at the points where the borrowed reference is actually used — not for the entire enclosing scope. Concretely, borrow checking a function body reduces to two coupled computations over the MIR CFG:

1. **Liveness** — which locals (and hence which *regions* occurring in their types) are live at each point. Crucially, a region may have **disjoint live ranges**: a variable assigned twice yields two separate live intervals for the same region variable [1].
2. **Outlives constraints** — from type checking: an assignment `y = x` where `x: &'x i32` and `y: &'y i32` produces `'x: 'y`, i.e., data flows from region `'x` into region `'y`.

Each borrow expression `&'b place` introduces a *borrow region* `'b` and requires that, at every point where `'b` is live, the borrowed place is not mutably used in a conflicting way. The check is performed by propagating liveness *backwards* through the subset graph: if `'b1: 'x` and `'x` is live at point `p`, then `'b1` is live at `p` too.

```rust
// The canonical NLL example (Matsakis [1])
let mut foo = 22;          // regions: (none live)
let mut bar = 44;
let mut x = &foo;          // borrow region 'b1,  'b1: 'x
let mut y = x;             // 'x: 'y  — data flows 'x -> 'y
x = &bar;                  // borrow region 'b2,  'b2: 'x
// drop(x) — 'x live here the first time
bar += 1;                  // OK: 'x's first live range has ended
// drop(y)
```

Here NLL accepts `bar += 1` because the region `'x` has two *disjoint* live ranges — a phenomenon impossible under lexical lifetimes.

> **Theorem (NLL soundness sketch).** *If every borrow region is live only at points where the borrowed place is valid and no conflicting access occurs, then no execution of the checked MIR performs a use-after-free or a data race through safe references.* The argument proceeds by showing the region assignment is a *conservative* abstraction of every dynamic execution's actual reference-validity intervals.

NLL shipped in Rust 1.31 and remains the default analysis. Its known incompleteness cases — programs that are intuitively safe but still rejected — are precisely the motivation for Polonius.

### 4.2 Polonius: the borrow checker as Datalog over a unified graph

Polonius (named for the Lord Chamberlain's "neither a borrower nor a lender be") reformulates borrow checking as **declarative logic**: a set of Datalog facts extracted from MIR plus inference rules whose least fixpoint yields loan liveness. The original prototype (`rust-lang/polonius` [4]) was a standalone Datalog engine; the current effort (2024–2026) reimplements the analysis natively in `rustc`, and the 2026 project goal targets **stabilization of the Polonius alpha** [3][5].

The alpha design can be summarized as follows. Given the CFG `C` and the subset (outlives) graph, compute a **unified graph** `U`:

- **Nodes** are pairs `(region r, point p)`.
- **Subset edges**: from type checking, if `r0 ⊆ r1` is required at point `p`, add edge `(r0, p) → (r1, p)`.
- **Liveness edges**: if there is a CFG edge `p → q` and region `r` is live at `q`, add edge `(r, p) → (r, q)`, respecting variance (forward, backward, or bidirectional).

Then:

- a *variable* is live per the standard compiler liveness analysis (with subtleties distinguishing "use" liveness from "drop" liveness);
- a *region* `r` is live at `p` if `r` occurs in the type of a variable live at `p`;
- a *loan* `l` is live at `p` iff there exists a live region `r` reachable in `U` from the loan's introduction node.

A borrow error is reported when a loan is live at a point where a conflicting access occurs — but unlike NLL, the loan's liveness is *path-sensitive*: the subset relation is tracked per CFG point rather than unioned into a single global graph. This is what fixes the classic NLL false positive:

```rust
fn example<'r>(r: &'r mut i32) -> &'r mut i32 {
    let r2: &mut i32 = r;
    if some_condition() {
        r2        // returned: borrow of *r live along this path
    } else {
        r         // NLL (old): ERROR — 'r infected across both branches
    }
}
```

Under NLL, the borrow inside `r2` must outlive the generic parameter `'r`, which NLL treats as spanning *all* branches to the function exit; the `'r2 = 'r` "infection" then leaks into the `else` branch and rejects the re-use of `r`. Polonius's location-sensitive graph contains the constraint to the branch where it is relevant and accepts the program [6]. This pattern class — conditional reborrows, and more importantly **lending iterators** (`Iterator` yielding `Item<'a>` borrowed from `&'a mut self`, rust-lang/rust#92985) — is the alpha's headline motivation [3].

Two variants exist and must not be confused:

| | Polonius legacy (`-Zpolonius=legacy`) | Polonius alpha (`-Zpolonius=next`) |
|---|---|---|
| Engine | external Datalog | native rustc implementation |
| Precision | more exotic flow-sensitive patterns | actionable subset |
| Stabilization path | none | 2026 goal: stabilize [5] |
| Superset of NLL | yes | yes — strictly more programs accepted |

Remaining work items for stabilization include fixing a soundness issue with opaque types and dead regions, expanding test coverage from fixed-by-Polonius issues, CI integration, nightly preview with a call for testing, performance validation on real-world code, and a formal model in `a-mir-formality` to be upstreamed into the Rust Reference [5].

### 4.3 Two-phase borrows and place capabilities

Consider the most ordinary-looking Rust line imaginable:

```rust
vec.push(vec.len())
```

Desugared naively to MIR, this becomes:

```text
tmp0 = &mut vec;      // mutable borrow starts here
tmp1 = &vec;          // shared borrow OVERLAPS — illegal!
tmp2 = Vec::len(tmp1);
Vec::push(tmp0, tmp2);
```

The receiver `vec` must be mutably borrowed to call `push`, but the *argument* `vec.len()` must be evaluated *before* the call — requiring a shared borrow of the same place while the mutable borrow is outstanding. RFC 2025 ("nested method calls") resolves this with **two-phase borrows**: the desugared auto-ref for an `&mut self` method call is not `&mut` but `&mut2`, a borrow with two phases [6]:

1. **Reservation phase** — from creation until the *activation point*: the borrow behaves like a *shared* borrow; reads through other paths are permitted.
2. **Activation** — at the point the method call actually begins executing, the borrow "upgrades" to a full exclusive `&mut`.

In place-capability terms, the capability held during the reservation phase is *read-only and non-exclusive*, and it is *strengthened* to a unique write capability exactly when the call starts. Any *write* through the original path during the reservation phase, or any use of the two-phase borrow before activation, is rejected. This is why `r.push(r.push(0))` still fails (both calls need `&mut self`) while `vec.push(vec.len())` succeeds (inner call needs only `&self`) [6].

Two-phase borrows are a notorious stress point for aliasing models: the borrow is created as shared-but-destined-to-become-exclusive, and interior-mutability (`Cell`) writes during the reservation phase must remain legal. Stacked Borrows handles this incorrectly — it *incorrectly allows writes to non-interior-mutable two-phase borrows* — while Tree Borrows was explicitly designed to get it right [9].

### 4.4 Stacked Borrows: a stack of permissions per location

Stacked Borrows (Jung, Dang, Kang, Dreyer, POPL 2020 [7]) gives an **operational semantics** for memory in Rust: extra state is added to the abstract machine so that every execution can be judged as either respecting or violating the aliasing discipline, with violations declared *undefined behavior*.

**State.** Every pointer value carries a *tag* (a unique `PtrId`), and every memory location carries a *stack* of borrow items. There is additionally a per-call-frame `CallId` and global tracking state [8]. Each stack item grants a **permission**:

| Permission | Granted by | Meaning |
|---|---|---|
| `Unique` | `&mut T` creation | exclusive access |
| `SharedReadWrite` | raw pointers, `UnsafeCell`-derived | shared, may write |
| `SharedReadOnly` | `&T` creation | shared, read-only |
| `Disabled` | — | separator: splits `SharedReadWrite` groups so they are not all mutually compatible |

**Dynamics.** Creating a reference *pushes* an item: `&mut T` pushes `Unique`, popping (invalidating) everything above it; `&T` pushes `SharedReadOnly`. Raw pointers derived from `&mut` are downgraded to `SharedReadWrite`. An access through a pointer is legal only if its item is still *on* the stack; touching memory through a popped item is UB. Function arguments additionally receive **protectors** (strong or weak) that turn invalidation into UB for the call's duration, justifying LLVM's `noalias` on `&mut`/`Box` parameters [8].

> **Theorem (Stacked Borrows optimization soundness [7]).** *The model justifies reordering reads across unknown code and function calls based solely on intraprocedural reasoning.* Proof sketches in the paper are backed by **mechanized Coq proofs** of open simulations in the style of Hur et al., showing representative transformations (e.g., moving a read of `*x` across a call when `x: &i32`) are semantics-preserving.

**Validation.** The authors instrumented **Miri**, the MIR interpreter, with Stacked Borrows and ran the architecture-independent parts of the standard library test suite (`libcore`, `liballoc`, `HashMap`). They found only **six** violations, almost all accepted by the Rust team as genuine bugs and fixed.

### 4.5 Tree Borrows: replacing the stack with a tree

Stacked Borrows proved too strict in practice: it rejects patterns common in real-world `unsafe` code (notably around reborrowing through raw pointers and two-phase borrows) because a *stack* imposes a total order on borrows that reality does not respect. **Tree Borrows** (Villani, Hostert, Dreyer, Jung, PLDI 2025 [9]) replaces the per-location stack with a **tree of permissions**: each pointer is a node; permissions propagate along parent–child edges; accesses are classified as *child* (derived from the accessed pointer) or *foreign* (all others), and each access updates the permissions of the accessed node and its relatives according to transition rules that distinguish reads from writes and interior-mutable from frozen data.

Key consequences of the tree structure:

- **Reborrows through raw pointers** no longer spuriously invalidate siblings: two mutable references to disjoint fields (`&mut t.0`, `&mut t.1`) are separate subtrees and coexist peacefully [9].
- **Two-phase borrows are handled correctly**, including writes to interior-mutable data during the reservation phase — the case Stacked Borrows gets wrong [9].
- **Protectors** are retained and refined: on function entry, each reference/`Box` argument gains a protector enforcing `noalias` (no location written through both child and foreign pointers during the call); references must additionally stay valid until function exit [9].

> **Theorem (Tree Borrows optimization coverage [9]).** *Tree Borrows retains most Stacked Borrows optimizations (proved in Rocq, the renamed Coq) and additionally enables new ones, notably read–read reorderings.*

Empirically, the headline number: evaluating on the **30,000 most widely used crates**, Tree Borrows **rejects 54% fewer test cases** than Stacked Borrows while preserving the same optimization guarantees [9]. In Miri it is available today via `-Zmiri-tree-borrows`; Stacked Borrows remains the default.

| Dimension | Stacked Borrows [7] | Tree Borrows [9] |
|---|---|---|
| Per-location state | stack of items | tree of permission nodes |
| Reborrow invalidation | pops everything above (total order) | scoped to affected subtree |
| Two-phase borrows | unsound corner (allows bad writes) | correct, incl. interior mutability |
| Protectors | strong/weak | refined; `noalias` justification kept |
| Mechanized proofs | Coq | Rocq |
| Crate-test rejection (30k crates) | baseline | **54% fewer** |
| Miri flag | default | `-Zmiri-tree-borrows` |

## 5. Empirical Results and Proofs

We collect the quantitative and mechanized evidence reported across the primary sources:

1. **NLL acceptance.** The 1.31 release accepted a large class of previously-rejected programs with zero reported soundness regressions; the canonical disjoint-live-range example (§4.1) is the unit test of the feature [1][2].
2. **Polonius alpha precision.** The alpha accepts a strict superset of NLL; validation proceeds via crater runs (backwards compatibility), the full `rustc` test suite, and a growing corpus of fixed-by-Polonius issues (e.g. rust-lang/rust#145053), with diagnostics parity work fixing ~80 diagnostic-difference cases (rust-lang/rust#136299) [5][6].
3. **Stacked Borrows validation.** Miri + Stacked Borrows over `libcore`, `liballoc`, and `HashMap` tests: only six violations, all acknowledged and fixed upstream [7]. Mechanized Coq proofs cover the optimization-justification theorems.
4. **Tree Borrows evaluation.** 30,000 most-used crates: 54% fewer rejected tests than Stacked Borrows; Rocq proofs retain most prior optimizations and add read–read reorderings [9].
5. **Miri as oracle.** POPL 2026: Miri is "the first tool that can find all de-facto Undefined Behavior in deterministic Rust programs" [10] — the methodological foundation for all of the above.

## 6. Limitations

- **NLL incompleteness is undecidable-adjacent.** The borrow-checking problem for a sufficiently expressive Rust fragment is hard; NLL's global (location-insensitive) subset graph will always reject some safe programs (conditional reborrows, lending iterators). Polonius alpha fixes an *actionable subset*; full flow-sensitivity (e.g., linked-list traversals) remains future work [5].
- **Polonius alpha is not yet stable.** Known open soundness issue: opaque types interacting with dead regions (blocked on the trait-system-refactor initiative); diagnostics near the accept/reject boundary need tuning; Datalog-naive implementations are slow, requiring special-case optimizations (e.g., large statics) [3][5].
- **Two-phase borrows are narrow.** They apply only to the auto-ref desugaring of `&mut self` method calls; indirection through `RefMut` or manual reborrows do not qualify, producing confusing rejections [6].
- **Tree Borrows retains "most" — not all — Stacked Borrows optimizations.** The exact optimization delta is characterized in Rocq but the operational model is strictly more permissive, so some aggressive aliasing-based transforms justified under Stacked Borrows need re-proof [9].
- **Miri validation is bounded.** Miri executes *deterministic* programs; concurrency, inline assembly subtleties, and platform-specific ABIs lie outside the validated envelope [10].
- **Neither model is the final word.** The unsafe-code-guidelines working group has not blessed a single aliasing model; Stacked Borrows remains Miri's default precisely because changing the de-facto UB definition is a breaking change to the ecosystem's implicit contract.

---

## 7. Conclusion

Rust's borrow story is a rare complete arc from *theory to toolchain*: region inference (NLL, RFC 2094) made lifetimes flow-sensitive; Polonius is now re-deriving the same analysis from Datalog rules over a location-sensitive unified graph, with the alpha slated for stabilization in 2026; two-phase borrows carve out the reservation/activation discipline that keeps everyday method calls ergonomic; and Stacked Borrows → Tree Borrows supplies the operational aliasing semantics that makes `unsafe` code and LLVM optimizations coexist — each step validated by executing the model in Miri and, where it matters, by mechanized proof in Coq/Rocq. The through-line is a single design principle: *state the aliasing contract as executable semantics, then measure everything against it*.
