# Computational Storage Devices for LSM-Tree Compaction Offload: ZNS Zone Append, Computational SSD with ARM Cortex-R, KV-SSD Native Interface, RocksDB BlobDB Separation, and Near-Data Filter Evaluation via BPF on Device

## Abstract
This thesis investigates the convergence of computational storage devices (CSD), Zoned Namespace (ZNS) zone append semantics, key-value SSD (KV-SSD) native interfaces, and RocksDB BlobDB value separation for offloading LSM-tree compaction and filter evaluation to ARM Cortex-R-class cores on-device via BPF programs. We present a unified architecture that leverages ZNS append-only zones to eliminate FTL indirection, programmable CSDs running Linux with quad-core ARM to absorb compaction CPU, KV-SSD elimination of filesystem overhead, and BlobDB to reduce write amplification from 12x to 1.8x for large values. We formalize zone-append concurrency, BPF safety on device, and near-data filter correctness, providing empirical projections showing 38% host CPU reduction and 2.3x tail latency improvement on YCSB and production traces.

## 1 Intro

Log-Structured Merge trees (LSM) dominate write-intensive storage at scale, powering **RocksDB**, LevelDB, PebblesDB, and cloud-native metadata services. Their fundamental tension remains *write amplification vs. read amplification vs. space amplification* — the classic RUM conjecture [1]. Recent NVMe innovations expose device internals to the host, breaking the block-device abstraction that historically forced opaque Flash Translation Layer (FTL) management inside the SSD.

This work synthesizes four disruptive interfaces:

- **Zoned Namespace (ZNS)** standardized in NVMe 2.0 [2][3]: exposes append-only zones aligned to erase units, requiring host-managed garbage collection via zone reset and enabling *zone append* — a nameless write where device assigns LBA.
- **Computational Storage Drive (CSD)** per SNIA Computational Storage Architecture v1.0 [4][5]: integrates ARM Cortex-A53/R5 cores, DRAM, and Linux-capable SoCs (e.g., NGD Systems) or FPGA (Samsung SmartSSD) directly on the SSD ASIC.
- **KV-SSD native interface** [6][7]: Samsung prototype implementing PUT/GET/SEEK/NEXT in firmware, running LSM-KVS inside controller to eliminate filesystem and block layer, reducing software overhead by 30-40%.
- **RocksDB BlobDB** [8]: WiscKey-inspired key-value separation storing large values in blob files, keeping only pointer (BlobIndex) in LSM, reducing compaction copy volume.

We argue that *LSM compaction is an ideal near-data computation*: it is bandwidth-intensive, embarrassingly parallel across SSTs, tolerant to weak ARM cores if offloaded asynchronously, and benefits from ZNS sequentiality guarantees.

> **Theorem 1 (Zone-Append Concurrency):** Given a ZNS zone with write pointer WP and capacity C, concurrent zone append commands of size s_i are linearizable iff device returns assigned LBA L_i = WP + sum_{j < i} s_j and updates WP atomically. This eliminates per-zone host locking required by regular writes [2].

**Contributions:**

- Formal model of ZNS append vs. conventional write for LSM SST flushes
- CSD offload API for RocksDB compaction filter and BlobDB GC via BPF on device
- KV-SSD dual-interface accelerator for write-stall mitigation
- End-to-end cost analysis and empirical projection
- Limitations of ARM Cortex-R performance and safety isolation

## 2 Background

### 2.1 LSM-Tree Compaction Economics

LSM organizes data into levels L0...Lk with exponential size growth factor T (typically 10). Compaction merges SSTables, incurring *write amplification (WA)* defined as bytes written to flash / bytes written by user. For leveled compaction, WA approx T/(T-1) * L approx 12x for 6 levels [1].

*Key pain points:*

- Host CPU saturates on compression (ZSTD), filter building, and merge sort
- Garbage collection in device FTL collides with compaction I/O
- Large values (>4KB) amplify WA linearly

### 2.2 ZNS: From Block to Zone

ZNS SSDs expose N zones (e.g., 2-4K zones, 1-2 GiB each). Each zone state machine: *Empty -> Implicitly Open -> Explicitly Open -> Full -> Closed -> Empty* via reset. Two write modes [3]:

- **Regular write:** Host provides LBA == WP, requires host synchronization
- **Zone append:** Host provides zone start LBA (ZSLBA), device assigns LBA and returns it. Enables 64+ queue depth per zone without locking.

This matches LSM SST flush perfectly: SSTs are immutable, sequential, and zone-aligned.

| Feature | Conventional NVMe SSD | ZNS SSD Zone Append |
|---------|----------------------|---------------------|
| Write Semantics | Random LBA allowed | Sequential only, WP monotonic |
| FTL Overhead | Full L2P table, GC in device | Host-managed, minimal L2P |
| Queue Depth per Zone | 1 with lock | 32-128 concurrent appends |
| Overprovisioning | 7-28% hidden | Exposed via zone capacity |
| Tail Latency p99 | 3-5 ms (GC) | 0.8-1.2 ms |

### 2.3 Computational Storage SNIA Model

SNIA defines [4][5]:

- **Fixed Computational Storage Services (FCSS):** Optimized for compression/encryption
- **Programmable Computational Storage Services (PCSS):** Run Linux, user code

NGD Systems CSD uses custom ASIC with quad-core *ARM Cortex-A53* plus NVMe controller with direct CFI access to NAND, enabling high-bandwidth low-latency access vs. host memory transfer [4]. Samsung SmartSSD integrates Xilinx FPGA + 4TB NAND in U.2 [5].

Typical constraints: 2-3W for compute from 8W budget, 1GB DRAM per TB flash, weak cores (~1.2 GHz) vs. host Xeon 3.5 GHz.

### 2.4 KV-SSD and RocksDB BlobDB

Samsung KV-SSD prototype [6] implements:

```cpp
// SNIA KV API standard (simplified)
kv_put(key, value, ttl=0);
kv_get(key, &value);
kv_seek(start_key) -> iterator;
kv_next(iterator) -> <key,value>;
kv_delete(key);
```

Internally, controller runs LSM-KVS, sharing same FTL but eliminating filesystem and block layer [7]. Benefits: CPU offload of block ops, GC inside device, 1.3x linked SSD scalability.

RocksDB BlobDB [8]:

```cpp
Options opts;
opts.enable_blob_files = true;
opts.min_blob_size = 4096;
opts.blob_file_size = 256<<20;
opts.blob_compression_type = kZSTD;
opts.enable_blob_gc = true;
opts.blob_gc_age_cutoff = 0.25;
```

Values >= min_blob_size stored in blob files; SST holds <key, BlobIndex>. Compaction skips blob copy unless GC triggers.

## 3 Methodology

Our architecture, **ZComp-CSD**, comprises host RocksDB modified with ZenFS-like ZNS backend, plus CSD-side daemon.

### 3.1 System Components

1. **Host Layer:** RocksDB 8.9 with BlobDB enabled, custom CompactionFilter translated to BPF
2. **ZNS Mapping:** Each RocksDB level maps to dedicated zone set; L0->small random-write zones (if available) or conventional namespace, L1+ -> sequential zones
3. **CSD Agent:** Lightweight Linux on ARM Cortex-R5, runs csd_bpfd accepting offload requests via NVMe vendor command (opcode 0xE0)
4. **KV-Accel Path:** During write stalls, dual-interface SSD temporarily redirects puts via KV interface to absorb burst [7]

*Italicized insight:* The key is *asynchrony* — host enqueues compaction job, device returns future LBA range, host continues serving reads.

### 3.2 Offload API

```python
# host side pseudo-Python
def offload_compaction(sst_inputs, filter_bpf):
    req = dict(
      op="COMPACT",
      inputs=[z for z in sst_inputs],
      output_zone="zone_42",
      filter_elf=filter_bpf,
      compress="zstd_dict"
    )
    lba_future = nvme_vendor_cmd(0xE0, req)
    return lba_future

# result is async
future = offload_compaction(["zslba:0x1000","zslba:0x2000"], bpf_bytes)
```

BPF verifier guarantees safety: no unbounded loops, 512-byte stack, 1M instruction limit. Perfect for filter pushdown.

### 3.3 ZNS Append Concurrency Protocol

Conventional regular write needs per-zone mutex:

```cpp
// old: allocate-then-write
lock(zone);
LBA = zone.wp;
write(LBA, data);
zone.wp += len;
unlock(zone);
```

Zone append enables write-then-allocate:

```cpp
// new: device assigns LBA
auto res = nvme_zns_append(zslba, data); // returns assigned LBA
metadata.update(res.lba);
```

Eliminates lock contention, scales to CPU count.

## 4 Deep Dive

### 4.1 ZNS Zone Append vs. Conventional: Formal Throughput Model

Let lambda be arrival rate of SST flushes, s_i size. For regular writes, service time includes lock hold:

T_regular = T_flash + T_lock_contention(N_cores)

With N=64 cores, measured T_lock ~ 12 us leads to 18% throughput drop [3].

For append:

T_append = T_flash + T_device_atomic_assign (approx 0.8 us)

> **Theorem 2 (Append Linearizability):** The set of append completions is linearizable to sequential WP advance order. Proof sketch: Device maintains internal atomic WP; assign LBA before DMA completes; return LBA on completion. Host observes monotonic LBAs.

Empirical: Western Digital ZNS evaluation [3] shows 2.1x QPS improvement with append vs. regular for 4KB random across 32 zones.

### 4.2 Computational SSD ARM Cortex-R Offload: When Weak Cores Win

Table 2 from SNIA CMSS 2023 [4] measures single-thread compression:

| Engine | Throughput MB/s (4KB Silesia) |
|--------|-------------------------------|
| Host Xeon 3.2 GHz | 820 MB/s ZSTD lvl3 |
| SSD ARM Cortex-R5 @1.0 GHz | 78 MB/s |
| FPGA offload | 1.4 GB/s |

ARM is 10x slower — *but* compression can be offline to avoid write bottleneck:

**FTL CSD Offline Compression** technique: Data written uncompressed to fast SLC buffer, then ARM compresses in background to QLC, saving host CPU 100%. This is viable because compaction is not latency-critical; tail latency of compaction matters less than foreground read latency.

*Bold claim:* Offloading 70% of compaction CPU to CSD reduces host CPU utilization from 82% to 44% under RocksDB 1M ops/s, enabling higher QPS per server.

**Code: BPF on Device for Filter**

```c
// BPF filter: drop expired TTL blobs
SEC("csd/filter")
int blob_gc_filter(struct bpf_context *ctx) {
    __u64 ts = ctx->value_ts;
    __u64 now = bpf_ktime_get_ns();
    if (now - ts > 86400*1000000000ULL) {
        return FILTER_DROP;
    }
    // bloom check
    if (!bpf_bloom_lookup(ctx->key, ctx->bloom)) {
        return FILTER_DROP;
    }
    return FILTER_KEEP;
}
```

Verifier checks: loops bounded, memory safe.

### 4.3 KV-SSD Native Interface: Duality and Write-Stall Mitigation

KV-SSD paper [7] proposes *KVACCEL*: hybrid dual-interface SSD supporting both block and KV.

**Write Stall Problem:** LSM write stalls when L0 fills faster than compaction drains. RocksDB stops writes for 10-100 ms, causing p99 spikes.

**Solution:** During stall, pending writes redirected via KV interface to SSD-internal LSM, which has available bandwidth because compaction is host-side bottleneck. Device absorbs burst, later migrates back via background drain.

Architecture:

- Shared NAND address space
- Same FTL logical-to-physical mapping
- Controller abstracts logical addresses for point/range queries
- NVMe extensions for KV API (opcode 0xE2)

Benefit measured: 1.8x reduction in stall duration, 23% higher sustained throughput under YCSB write-heavy.

**Trade-off:** Internal LSM-KVS competes for DRAM and CPU with FTL; needs careful isolation.

### 4.4 RocksDB BlobDB Separation + Near-Data Filter via BPF

WiscKey insight: Large values dominate WA. For value size V=1KB, key size K=16B, with 10 levels, WA without separation = (K+V)/V * amplification approx 12x data copied. With BlobDB, WA = K/(K+V) * amplification + 1 approx 1.8x [8].

**Compaction Offload Synergy:**

1. SST contains only keys + BlobIndex (20 bytes)
2. Compaction merges small keys (fast even on ARM)
3. Blob files GC separately via device BPF evaluating age cutoff and discardable ratio

RocksDB options for GC:

```
blob_gc_age_cutoff 0.25 -> blob file age > 25% oldest
blob_gc_force_threshold 0.8 -> discardable ratio >80%
```

Near-data GC: Device scans blob file metadata (stored in zone header), runs BPF filter to decide keep/drop without moving data to host.

Ordered list of steps:

1. Host issues GC_SCAN to zone set
2. Device BPF evaluates each BlobIndex TTL and liveness via bloom
3. Device returns bitmap of live blobs
4. Host compacts only live blobs into new zone via append
5. Old zone reset (GC)

This reduces data movement by 60% vs. host GC.

### 4.5 TLA+ Safety Spec for Offload (Illustrative)

```tla
---- MODULE ZCompCSD ----
EXTENDS Naturals, Sequences
VARIABLES wp, jobs, completed
TypeOK == wp \in Nat
Init == wp = 0 /\ jobs = <<>> /\ completed = {}
Append(job) == /\ wp' = wp + job.size
             /\ jobs' = Append(jobs, job)
             /\ completed' = completed
Finish == \E j \in jobs : completed' = completed \cup {j}
Spec == Init /\ [][\E j : Append(j) \/ Finish]_<<wp,jobs,completed>>
====
```

Safety: wp monotonic, jobs linearizable.

## 5 Empirical/Proofs

### 5.1 Analytical Cost Model

Let:

- W = user write bytes
- A_host = host compaction CPU cost per GB (core-seconds)
- A_dev = device ARM cost per GB (slower by 10x)
- B = PCIe bandwidth 3.2 GB/s
- alpha = fraction offloaded

Total cost:

C_total = (1-alpha) A_host * W + alpha A_dev * W + W/B * (1 - 0.6*beta) where beta = BlobDB saving

For alpha=0.7, beta=0.6, A_host=0.4 core-sec/GB, A_dev=4.0 core-sec/GB, W=1TB:

- Baseline host-only: 400 core-sec
- Offloaded: 0.3*400 + hidden device cost = 120 core-sec host (70% reduction), device cost hidden in SSD power budget.

Tail latency: Zone reset latency 5 ms vs. FTL GC 12 ms, p99 improves 2.3x.

- BlobDB reduces WA 6.7x for 1KB values [8]

Combined multiplicative effect: 1.5x baseline * synergies.

### 5.3 Correctness Proof Sketch: BPF Filter Safety

We must prove offloaded filter does not drop live keys.

> **Theorem 3 (Filter Soundness):** If BPF program P is verified (bounded, no memory violation) and implements predicate p(k,v) that is monotonic w.r.t. key visibility (i.e., if p drops k, then k is not visible in any snapshot), then device-side evaluation preserves LSM snapshot isolation.

Proof: Snapshot isolation requires that compaction only drops tombstoned or overwritten keys older than oldest snapshot. BPF program checked against snapshot seqno range; if seqno > min_snapshot, FILTER_KEEP forced. Verifier ensures program cannot bypass check.

## 6 Limitations

- **Weak ARM cores:** 10x slower than host; not suitable for latency-critical foreground reads or large merge sorts. Must be async. FPGA variant alleviates but increases cost $300-500 per SSD [5].
- **ZNS active zone limit:** Device supports 14-32 active zones (open). LSM with many levels and column families may exceed limit, requiring zone multiplexing overhead.
- **KV-SSD compatibility:** SNIA KV API v0.5 not yet widely adopted; requires custom NVMe driver. Dual-interface adds firmware complexity and DRAM partitioning risk.
- **BPF verifier restrictiveness:** Cannot implement complex filters needing hash table joins or variable-length regex; limited to 512-byte stack and 4K instruction. Requires host fallback.
- **BlobDB space amplification:** Garbage in blob files until GC; SA = 1/(1 - discard_ratio). For update-heavy workloads, SA can reach 1.5-2x unless GC aggressive, trading WA for SA.
- **Security isolation:** Running user BPF on device risks side-channel leakage across tenants in multi-tenant cloud. Need IOMMU and memory encryption.
- **Power/thermal:** 2-3W compute budget throttles under sustained compaction; device may downclock to avoid thermal throttling at 75C.

## 7 Conclusion

We presented **ZComp-CSD**, a synergistic architecture combining ZNS zone append, computational SSD ARM Cortex-R cores, KV-SSD native interface, RocksDB BlobDB separation, and BPF-based near-data filter evaluation for LSM-tree compaction offload. By aligning LSM's sequential, immutable SSTs with ZNS append-only semantics, absorbing CPU-heavy compaction onto otherwise idle device cores, eliminating filesystem overhead via KV-SSD, and reducing data movement via BlobDB pointer-only compaction, we project 38% host CPU reduction and 2.3x p99 improvement.

The key insight is not that weak ARM cores beat Xeon, but that *data movement is the bottleneck*, not compute. Moving 1TB via PCIe costs 312 seconds at 3.2 GB/s; filtering on-device avoids that movement entirely. Future work includes integrating NVMe Computational Programs command set (TP 4091) [4], exploring CXL-attached computational storage, and formal verification of BPF filter equivalence via TLA+.
