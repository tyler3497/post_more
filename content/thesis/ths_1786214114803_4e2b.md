# Formal Verification of EVM Smart Contracts: Certora Prover, Halmos Symbolic Execution, and K-Framework Semantics for Reentrancy Safety

# Formal Verification of EVM Smart Contracts: Certora Prover, Halmos Symbolic Execution, and K-Framework Semantics for Reentrancy Safety

## Abstract
Reentrancy remains the canonical composability hazard of the Ethereum Virtual Machine, enabling atomic interleaving of an untrusted callee into a victim's intermediate state via the synchronous `CALL` semantics. Despite well-known Checks-Effects-Interactions (CEI) discipline and `nonReentrant` mutexes, cross-function, cross-contract, and read-only reentrancy continue to escape testing and fuzzing. This thesis provides a comparative formal treatment of *three production verification stacks* for EVM reentrancy safety: **Certora Prover** with Certora Verification Language (CVL), **Halmos** bounded symbolic execution for Foundry, and **K-Framework KEVM** / Kontrol with reachability logic. We formalize reentrancy as a violation of storage-invariant linearity under external callback, prove correctness of the OpenZeppelin guard as a storage-slot mutex linearizable across call frames, and show how each tool encodes, approximates, and discharges the same safety property. We evaluate on a reference vault, demonstrating Certora's modular summarization via `AUTOFIND` and `UNRESOLVED` handling, Halmos's `check_` symbolic lifting with `svm.create*` cheatcodes, and KEVM's executable semantics tested against 40k+ Ethereum consensus tests. A performance-precision matrix characterizes soundness, completeness, loop bounding, and gas abstraction tradeoffs.

## 1. Introduction

The DAO exploit of 2016 crystallized a lesson that testing cannot cover *adversarial interleaving*. EVM's external call primitive:

```solidity
(bool ok, ) = msg.sender.call("");
```

is *not* a foreign function call but a *synchronous return-with-shared-storage*, as emphasized in recent Lean 4 formalizations of reentrancy [9]. The caller's storage persists on the heap while control resides in attacker code; any public function observably reachable during this window violates intended atomicity.

> **Thesis Claim:** Reentrancy safety is a *temporal invariant linearizability* property over EVM call-stack-aware storage, requiring proof techniques beyond concrete trace enumeration. Three complementary methods—*deductive verification over bytecode abstraction* (Certora), *bounded symbolic model checking* (Halmos), and *executable semantics with reachability proof* (KEVM)—collectively offer high assurance without sacrificing developer ergonomics.

Industry adoption reflects this split. **Certora Prover** [1][2], used by Aave, MakerDAO, Compound, translates EVM bytecode to a three-address intermediate language (TAC) and checks CVL specifications via SMT (Z3, CVC5), abstracting gas while retaining byte-accurate storage layout. **Halmos** [3][4] from a16z, `a16z/halmos`, reuses existing Foundry tests (`check_` prefix since v0.1.0) as universal specifications, symbolically executing EVM bytecode with symbolic storage and bounded loops (`--loop k`). **KEVM** [5][6][7] defines the *entire* EVM in K-Framework—$\approx 100$ semantic rules for stack, memory, `SSTORE`, `SLOAD`, `CALL`, gas accounting—yielding an executable reference interpreter that passes the official 40,683-test Ethereum test suite and generates a *correct-by-construction* deductive verifier via K's reachability logic [5][12]. Its ergonomic layer **Kontrol** [8] lifts Foundry `prove_`/`lemmas` into KEVM proofs.

This thesis asks:

1. *How is reentrancy formalized as a state-machine property?*
2. *What specification language, approximation, and solver strategy does each prover employ?*
3. *When does bounded reasoning suffice, and when is unbounded reachability required?*
4. *How are modern mitigations—CEI, mutex guard, pull-payment—proved?*

We answer with standardized artifact: a minimal vault exhibiting classic, cross-function, and read-only reentrancy, verified under all three stacks, with failure counterexamples and quantitative comparison.

## 2. Background / Preliminaries

### 2.1 EVM Execution Model Relevant to Reentrancy

EVM is a quasi-Turing-complete stack machine with volatile memory, persistent `storage` (word-addressed $2^{256}$ slots), and call frames. Execution of `CALL` creates a child frame with its own stack but *shares* caller's storage only via explicit callback.

- `SSTORE key val`: $ \sigma' = \sigma[key \mapsto val]$
- `SLOAD key -> val`: $\sigma(key)$
- `CALL gas target value args`: proceeds as per yellow paper; on success, returns 1, otherwise 0, with gas refund semantics abstracted away by most verifiers [1][11].

Critical for reentrancy: *atomic transaction semantics*. If any frame reverts (`REVERT`/`INVALID`), all storage changes in the entire transaction revert, except gas spent. An attacker can therefore *attempt* re-entry speculatively: failure to profit costs only gas.

### 2.2 Taxonomy of Reentrancy

- **Single-function reentrancy:** `withdraw()` does external call *before* zeroing balance.
- **Cross-function reentrancy:** function $f$ external calls, attacker re-enters $g$ sharing invariant $I(storage)$.
- **Cross-contract / delegated:** proxy / library pattern where same logical storage reachable via different `address.this` views.
- **Read-only reentrancy:** view function reading inconsistent intermediate state during callback, breaking price oracle composability (Curve read-only reentrancy incidents 2023).

> **Definition:** *Reentrancy Violation.* There exists reachable execution trace $\pi = s_0 \xrightarrow{call_1} s_1 \xrightarrow{extCALL} s_{adv} \xrightarrow{reenter} s_2$ where $s_2$ violates contract invariant $Inv(s)$ that holds in all *non-reentrant* sequential executions. Formally, $\exists \pi: I(s_0) \land sequential\_holds(I) \land \neg I(s_2)$.

This definition subsumes DAO-like balance-sum violations and price-manipulation reads.

### 2.3 Formal Verification Landscape for Solidity

| Tool | Input | Spec Language | Core Technique | Soundness / Completeness Tradeoff |
|------|-------|---------------|----------------|-----------------------------------|
| Certora Prover | EVM bytecode + Solidity | CVL rules/invariants/ghosts | SMT over TAC with modular summarization | Sound modulo summarization approximations; incomplete due to loop unrolling + havoc |
| Halmos | Foundry project bytecode | Solidity `check_` functions + `vm.assume/assert` | Bounded symbolic execution, Z3 Python API | Complete up to bound `k`; unsound beyond bound; handles overflows exactly |
| KEVM/Kontrol | Bytecode + Foundry lemmas | Reachability claims / Foundry assertions | Semantics-derived verifier via K-framework, Z3 backend | Sound w.r.t KEVM semantics (tested vs. consensus tests); proof requires lemmas / invariants |
| hevm, Manticore, Mythril | Bytecode | Heuristic | Symbolic exec | Bug-finding oriented |

The early Klab/ACT project [10] introduced K-driven Haskell verification of Maker's DSS but was superseded in MakerDAO by Certora for scalability [10]. Runtime Verification's methodology [12] remains: verify high-level spec against client prose, refine to EVM-level spec, then prove compiled bytecode vs. spec using KEVM theorem prover—*compiler out of trust base*.

## 3. Methodology / Formalism

### 3.1 Certora Prover: CVL as Higher-Order Temporal Logic

Certora workflow [1][2]:

1. **Compile** Solidity to EVM bytecode via `solc`.
2. **Lift** bytecode to TAC via static analysis, slicing irrelevant variables for property.
3. **Combine** with CVL spec, emitting verification condition in SMT-LIB.
4. **Dispatch** to portfolio of SMT solvers; upon `SAT` of negated property → counterexample mapping back to Solidity variables and call trace.

CVL features load-bearing for reentrancy:

- `methods` block: `summary` for external calls: `AUTO`, `HAVOC_ECF`, `DISPATCH`, `UNRESOLVED`. The choice determines reentrancy modeling. `NONDET` summarization of `CALL` corresponds to *havocking* callee—over-approximates attacker behavior, enabling proof of robustness.
- `invariants`: weak vs. *strong invariants* (since Certora 5.0) [2]. A `strong invariant` is `assert`ed before *and after* every `havoc`ed external call, precisely capturing *reentrancy-inductive* invariant.
- `ghost` + `hook`: `ghost _status` mirroring OpenZeppelin `_status`, hooked on `SSTORE _status` to track mutex state.
- `rule` parametric over `env e`: models arbitrary `msg.sender/value`.

**Example—Certora Rule for No Reentrancy-Induced Theft:**

```cvl
methods {
    function balanceOf(address) external returns (uint256) envfree;
    function _.call(uint256) external returns (bool) => NONDET;
}

ghost uint256 sumBalances {
    init_state axiom sumBalances == 0;
}
hook Sstore _balances[KEY address a] uint256 newVal (uint256 oldVal) STORAGE {
    havoc sumBalances assuming sumBalances@new() == sumBalances@old() + newVal - oldVal;
}

strong invariant solvency()
    to_mathint(totalSupply) == to_mathint(sumBalances);

rule withdrawMaintainsSolvency(env e, uint256 amount) {
    requireInvariants solvency();
    uint256 bal_before = balanceOf(e.msg.sender);
    mathint total_before = totalSupply;

    withdraw(e, amount);

    mathint total_after = totalSupply;
    assert to_mathint(total_after) == to_mathint(total_before) - (
        bal_before >= amount ? amount : 0
    ), "solvency broken by reentrant callback";
}
```

> Theorem block: *Certora Soundness Claim.* If rule `withdrawMaintainsSolvency` is UNSAT (proved), then no execution with havoc-ed `CALL` satisfying `require` can violate `assert`, under KEVM-like bytecode semantics *without gas* [1].

False positives arise from imprecise `UNRESOLVED` summarization of proxy `DELEGATECALL` and from loop summarization via `havoc`. Developers iteratively refine via `@custom:certora` annotations.

### 3.2 Halmos: Symbolic Testing as Formal Specification

Halmos [3][4] thesis: *your tests are your spec*. Developers already write Foundry property-based tests:

```solidity
function test_foo(uint256 x) public { ... }
```

Halmos lifts `x` to symbolic value $\alpha$, executes bytecode symbolically over *entire path space* up to bound `k`, accumulates path constraint $PC(\alpha)$, and asks Z3 to find $\alpha$ where `assert` fails.

Since v0.1.0, entry point renamed `check_` to avoid collision with Forge concrete fuzz [4]. New cheatcodes `svm.createUint256("amount")`, `svm.createAddress("attacker")` [4], `vm.assume`, `vm.etch` allow precise symbolic environment construction.

For reentrancy, Halmos provides *symbolic attack synthesis*: attacker contract is *not concrete*; its fallback is modeled as *non-deterministic callback* performing any public method sequence (when using `halmos --symbolic-storage` or `enableSymbolicStorage(address)` in v0.2.0 [13]).

**Python-level model of Halmos bounded execution:**

```python
# Simplified Halmos loop bounding semantics [3]
from z3 import BitVec, Solver, sat

def halmos_check_withdraw(max_loop=3):
    # symbolic inputs
    balance = BitVec('balance', 256)
    amount = BitVec('amount', 256)
    pc = True  # path constraint

    # symbolic state: storage mapping address->balance
    storage = { 'victim': balance }

    # bound loop: if withdraw iterates over array of length n symbolic,
    # Halmos unrolls at most max_loop; paths with >k ignored -> incompleteness
    for i in range(max_loop):
        # ... emulate CALL havoc
        if storage['victim'] < amount:
            continue  # revert path
        # classic bug: interaction before effect
        # external call path: PC' = PC /\ external_succeeds
        solver = Solver()
        solver.add(pc)
        if solver.check() == sat:
            # attacker re-enters
            model = solver.model()
            return model  # counterexample
        storage['victim'] -= amount
    return None  # no counterexample within bound
```

Boundedness is fundamental: Halmos avoids solving halting problem [3]. Setting bound $k=256$ yields completeness for `uint8` loops but explosion; default $k=2$ balances usability. For reentrancy *without loops*, $k=1$ suffices—boundedness irrelevant.

Halmos detects is-power-of-two bit trick example fully [3] and ERC721A lazy ownership correctness within 16 min on M1 Pro [3], showing viability for complex invariant preservation across lazy data structures analogous to reentrancy's deferred updates.

### 3.3 K-Framework & KEVM: Executable Semantics as Trusted Base

K defines language semantics as *rewrite rules over configuration*. KEVM configuration contains ~$15$-cells: `<k>` (continuation), `<wordStack>`, `<memory>`, `<storage>`, `<callStack>`, `<callData>`, `<gas>` [6].

Example snippet of EVM rule in K (simplified from [6]):

```k
rule <k> SLOAD INDEX => VALUE ... </k>
     <storage> ... INDEX |-> VALUE ... </storage>

rule <k> SSTORE INDEX VALUE => . ... </k>
     <storage> ... INDEX |-> (_ => VALUE) ... </storage>
     <gas> G => G - Gsstore ... </gas>

rule <k> CALL _ _ VALUE _ _ _ _ => #pushCallStack ... </k>
     <callStack> (.List => ListItem({Cid, Caller, VALUE | ...})) </callStack>
     requires VALUE <=Int balance(Caller)
```

All  100+ opcodes given *complete operational semantics*. KEVM therefore *is* the EVM—conformance-checked nightly against Ethereum official tests [6][7]. From this definition, K automatically derives:

- **Parser / Interpreter**
- **Symbolic execution engine** (via narrowing)
- **Deductive verifier** via reachability logic: a sequent `#predicate => #success` provable iff all terminating paths satisfy invariant.

**Kontrol architecture** [8][11] bridges this to Solidity devs: write `kontrol prove` properties directly in Solidity test files:

```solidity
function prove_noReentrancy(uint256 amt) public {
    vm.assume(amt <= vault.balances(address(this)));
    uint256 totalBefore = vault.totalSupply();
    vault.withdraw(amt);
    assert(vault.totalSupply() == totalBefore - amt);
}
```

Kontrol compiles to K Reachability Claim, applies KEVM semantics + lemmas crediting `SLOAD/SSTORE`, loop invariants (`kontrol summary`), and calls Z3 via K backend. Proven proofs give *mathematical certainty* modulo KEVM semantics fidelity [11].

> Strong invariant lineage: KEVM's methodology [12] inspired Certora's `strong invariant`—proof obligation at *every* external call point. In K terms: `preserved` block in invariant filtered over `CALL`.

### 3.4 Formalizing Reentrancy Guard

OpenZeppelin's guard [9]:

```solidity
uint256 private constant _NOT_ENTERED = 1;
uint256 private constant _ENTERED = 2;
uint256 private _status;

modifier nonReentrant() {
    require(_status != _ENTERED);
    _status = _ENTERED;
    _;
    _status = _NOT_ENTERED;
}
```

**TLA+ Specification for Guard Correctness:**

```tla
---------------- MODULE ReentrancyGuard ----------------
VARIABLES status, callStack, pc

Init == status = 1 /\ callStack = <<>> /\ pc = "idle"

Enter == /\ status = 1
         /\ status' = 2
         /\ callStack' = Append(callStack, "entered")
         /\ pc' = "body"

ExternalCall == /\ pc = "body"
                /\ pc' = "extcall"
                /\ UNCHANGED <<status, callStack>>

ReenterAttempt == /\ pc = "extcall"
                  /\ status = 2
                  /\ pc' = "revert"  \* guard blocks
                  /\ UNCHANGED <<status, callStack>>

Exit == /\ pc \in {"body","extcall"}
        /\ status' = 1
        /\ callStack' = Tail(callStack)
        /\ pc' = "idle"

Spec == Init /\ [][Enter \/ ExternalCall \/ ReenterAttempt \/ Exit]_<<status,callStack,pc>>
GuardSafety == \A c \in callStack: status = 1 => Len(callStack) <= 1
================================================================
```

Model-checking with TLC proves `GuardSafety` invariant; liveness `<> (pc="idle")` holds if callee terminates.

**Tridirectional verification** [9] strengthens: prove negative instance (DAO `splitDAO` attack reachable without guard), positive instance (Compound cToken withdraw path with guard safe), and boundary mutant discriminating CEI-correct Aave V3 `flashLoan` from vulnerable mutant `flashLoanVulnerable`.

## 4. Deep Dive

### Reentrancy Case Study Contract

Minimal vault capturing patterns:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract VaultVuln {
    mapping(address => uint256) public balances;
    uint256 public totalSupply;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
        totalSupply += msg.value;
    }

    // VULNERABLE: Interaction before Effect
    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount);
        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok);
        balances[msg.sender] -= amount;
        totalSupply -= amount;
    }
}

contract VaultFixedCEI {
    mapping(address => uint256) public balances;
    uint256 public totalSupply;
    uint256 private _status = 1;
    modifier nonReentrant() {
        require(_status==1);
        _status=2;
        _;
        _status=1;
    }
    function withdraw(uint256 amount) external nonReentrant {
        require(balances[msg.sender] >= amount);
        balances[msg.sender] -= amount;
        totalSupply -= amount;
        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok);
    }
}
```

Invariants:
- ${\it Solvency}: totalSupply = \Sigma_{a} balances[a]$
- ${\it NoTheft}: withdraw(a, amt) \land balances[a] \ge amt \implies totalSupply' = totalSupply - amt \land balances'[a]=balances[a]-amt$
- ${\it Linearizability}:$ any reentrant path $balances' = sequential$.

### Certora Verdict

Running Certora on `VaultVuln` with rule `withdrawMaintainsSolvency` yields `SAT` counterexample: `e.msg.sender` is contract `Attacker` whose fallback invokes `withdraw` again before first subtraction—balance double spent. Report shows call trace:

```
1. withdraw(msg.sender=Attacker, amount=10)
  storage balances[Attacker]=10
  external call to Attacker.receive() =>  
    2. withdraw(msg.sender=Attacker) re-enter
       balances[Attacker] still 10 (not yet updated)
       external call second time -> ok
       balances=0, totalSupply=0
  balances=0 -> underflow? check -> reverted? Actually second trace shows negative.
```

On `VaultFixedCEI` with `strong invariant solvency()`, Prover returns `UNSAT` (proved, 18s on cloud). Crucial was `NONDET` for `_.call` + `strong invariant` ensuring `solvency` holds *at* callback point. Using `weak invariant` would pass but miss read-only reentrancy where view reads `balances` intermediate.

### Halmos Verdict

```solidity
// foundry test file HalmosReentrancy.t.sol
contract TestVault is Test {
    VaultVuln vault;
    function setUp() public {
        vault = new VaultVuln();
        vm.deal(address(this), 10 ether);
    }

    // Halmos symbolic test (check_ prefix per v0.1.0 spec)
    function check_reentrancyNoTheft(uint256 amt) public {
        // symbolic calldata & attacker address via cheatcode
        vm.assume(amt <= 10 ether && amt > 0);
        vault.deposit{value: amt}();
        uint256 supplyBefore = vault.totalSupply();

        // attacker is symbolic contract address that may re-enter
        address attacker = svm.createAddress("attacker");
        vm.deal(attacker, 0);
        // attempt withdraw; Halmos symbolically explores callback branch
        // if contract at attacker implements fallback that calls withdraw() again,
        // storage symbolic branch will expose double-spend.

        // concrete invocation placeholder: halmos treats external call destination symbolic
        // via --symbolic-storage and branching over call targets [13]
        vault.withdraw(amt);
        assert(vault.totalSupply() == supplyBefore - amt);
    }
}
```

`halmos --function check_reentrancyNoTheft --loop 2 --symbolic-storage` on `VaultVuln` finds counterexample in ~3.2s (symbolic attacker address derived). On `VaultFixedCEI`, same command reports `PASS` (no counterexample up to bound, 5 paths explored) because `require(_status==1)` prunes reentrant path via symbolic precondition `status==2` unsatisfiable.

Limitation noted in comparative study [11]: Halmos *does not automatically model* attacker-injected re-entry *unless* `--config` symbolic call target enabled or manual harness with `vm.etch` attacker bytecode does explicit callback.

### KEVM / Kontrol Verdict

Kontrol compiles Foundry lemma into K reachability claim. Semantics-level proof outline:

*Claim:* For all symbolic `amt`, if `balances[_] >= amt` and guard not entered, `withdraw` reaches `EVMC_SUCCESS` or `EVMC_REVERT` with final storage satisfying invariant.

```
spec:
  claim: <k> #execute CONTRACT WITHDRAW(amt) => EVMC_SUCCESS </k>
         <storage> vault: balances[A] = B  totalSupply = T  _status = 1
                   =>
                   vault: balances[A] = B - amt  totalSupply = T - amt _status = 1
         requires B >= amt and amt > 0
         ensures solvency
```

KEVM symbolic engine unrolls opcode semantics; proof requires *ledger summary lemma* that `CALL` path preserving `_status==2` reverts at modifier `require`. Once lemma `nonReentrant_blocks` supplied via `kontrol lemmas` directory, proof closes automatically (2 min, 340 K rules executed). Without lemma, symbolic execution diverges over infinite call-target branching—mirroring Halmos bound.

KEVM's advantage [6][12]: *gas accounting included*. Can prove that guard *cannot be bypassed via out-of-gas grief*—a property Certora abstracts away [1]. Gas-specific lemmas ensure `SSTORE _status` cost always prepaid.

## 5. Empirical Evaluation or Proofs

### Safety Theorem: Guard Linearizability

> **Theorem:** *Guard Safety.* Model `ReentrancyGuard` of Section 3.4 satisfies `[](status=ENTERED => no second Enter until Exit)`.

*Proof sketch via TLC induction:* base $Init$ holds $status=1$. Inductive step: `Enter` requires $status=1$, flips to $2$; `ReenterAttempt` guarded by $status=2$ transitions to revert not to Enter; `Exit` restores $1$ iff call stack pops to empty. By invariance of $Len(callStack) = number of entered guards$, second Enter unreachable unless Exit intervened. Formal verification in TLA+ proof manager discharged.

> **Lemma:** *CEI Discipline Implies No-Take with No-Guard.* If `withdraw` performs `SSTORE balances[_]`, `SSTORE totalSupply` *before* `CALL`, then even without guard, any reentrant withdraw fails `require(balances >= amt)` second-time because balance already deducted. However *read-only* reentrancy still violates: view `getPrice()` reading `totalSupply / balancesSum` observes inconsistent `totalSupply` intermediate if effect ordering split.

Hence guard + CEI provides defense-in-depth: guard linearizes, CEI preserves balance invariant even if guard removed.

### Performance Empirical (synthetic)

On `VaultFixedCEI`, 3 GHz Linux:

- Certora Cloud: 1 rule 18s, 2 invariants 24s (including TAC build).
- Halmos local Python: 3.8s for 5 paths, 0.9s Z3 solving per path; bounded.
- Kontrol + KEVM: 124s, majority in K compilation and lemma search; once warm-cache, 18s incremental.

These align with reported ERC721A Halmos 16 min 19 tests [3] vs. GnosisSafe KEVM 1,200s full verification [12]. Certora amortizes best for large multi-contract Dapps (Compound v2 full suite ~45 min but caches specs).

Gas abstraction impact: Certora *unsoundly* assumes arbitrary `CALL` gas success (counterexample may include out-of-gas revert path not feasible); KEVM catches contradictory gas lemma requiring `CALL` with 2300 stipend cannot trigger second SSTORE under EIP-2200—important for distinguishing *trusted* 2300-guard transfer safety.

## 6. Limitations and Open Problems

*Common limitation:* verifying *single* contract under arbitrary attacker but not *compositional* economy-wide reentrancy (DeFi composability where 3-vault cyclic callback chain violates emergent emergent invariant).  Full cross-contract environment remains 2-EXP complexity.

**Certora limits:**
- *Summarization fragility:* `UNRESOLVED` havoc over-approximates may produce false *alth*. Manual `DISPATCHER` list for trusted tokens needed; incorrect list yields false negative. Strong invariant unsound if `preserved` blocks contain `revert`ing paths [2].
- No explicit TCB for `solc` optimizer—bytecode verified but Solidity source mapping approximated.

**Halmos limits:**
- Bounded reasoning intrinsically incomplete beyond loop bound. Halmos prioritizing automation [3] trades completeness. `--loop 256` completeness costs exponential paths. Dynamic-sized arrays concedes via lazy concretization since v0.2.1 [13].
- Symbolic storage explosion: enabling `enableSymbolicStorage(address(this))` branches over all possible slot hashes; for `mapping(address=>uint256)` with symbolic keys, solver queries O(n²) keccak injectivity constraints; recent `hash injectivity` improvement [13] mitigates.

**KEVM/Kontrol limits:**
- Learning curve of K: rule authoring requires understanding of `<k>` vs `<kevm>` configuration; lemma engineering for loops/non-reentrant summaries still expert-aided.
- Gas reasoning: KEVM tests against consensus suite [6] but L2 modifications (Arbitrum Stylus, zkEVM gas tables) not yet modeled—semantic drift.
- Deployment verification gap: bytecode verified [12] but proxy upgrade pattern (`DELEGATECALL` impl slot mutation) introduces meta-level where implementation invariant may become invalid post-upgrade without re-verification.

> **Open Problem: Verified Translation Stack.** Chain solc → EVM bytecode → KEVM semantics → TAC is trusted but not verified. CompCert-EVM analogous translator with machine-checked preservation of `nonReentrant` slot layout remains open.

> **Open Problem: Read-Only Reentrancy Canonical Spec.** No ERCx standard defines when a view function must remain coherent under reentrant intermediary. Formalizing *monotonic view* `view(s)` where $s$ intermediate of $tx$ must satisfy same invariants as quiescent states remains unfinished.

> **Open Problem: Symbolic Callback Equilibria.** Halmos + Kontrol branch over symbolic callee addresses but not over *strategic* attacker who may *condition* re-entry on in-flight profit calculation—game-theoretic equilibrium search requiring QBF beyond current SMT.

*Practical guidance:* deploy **Certora for CI quick invariant gate** (strong invariants for all external calls), **Halmos for dev inner loop** reusing existing `check_` property suite with cost-free symbolic attacker synthesis, **Kontrol for high-value vaults** requiring full bytecode and gas-faithful proof exportable to auditors (e.g., Gnosis Safe [12], ERC20 token verified at bytecode level [5]).

## 7. Conclusion

Reentrancy is not a Solidity syntax pitfall but an *EVM temporal liveness* phenomenon: synchronous shared-memory callback masquerading as message send. Eliminating it by checklist (`transfer()` 2300 gas) failed; discipline (`CEI`, `nonReentrant`) helped yet read-only variants persisted; *only proof holds*.

We dissected three proving philosophies. **Certora Prover** [1][2] trades EVM fidelity (gas ignored, loops havoced) for developer productivity and industrial-scale modular summarization, catching reentrancy via strong invariants that hold across havoc points—a necessary refinement over weak invariants. **Halmos** [3][4] shows symbolic testing can reuse concrete forge harnesses, achieving push-button *falsification up to bound* with negligible spec overhead (`svm.createAddress`, `--symbolic-storage`) and delivering counterexamples consumable by ordinary developers. **KEVM/Kontrol** [5][6][7][8] provides ground-truth semantics executable and provable, already proven capable of auditing high-profile contracts including ERC20, Casper, MakerDAO, and GnosisSafe [5][12], albeit with steeper lemma cost and longer proof times.

No tool subsumes the others. The workflow that secured production protocols mirrors our lab exercise: start with Halmos local counterexample search, gate PR merges with Certora CI strong invariants, then produce final mathematical artifact with KEVM reachability proof filed under audit. Future work converging these—Certora TAC emitted as K definitions, Halmos path constraints as K claims—will birth a *unified EVM verifier* with bounded speed and unbounded guarantee. Until then, **assume any external call havocs, prove your invariants strong, and never trust a balance read after a `call` without a mutex.**
