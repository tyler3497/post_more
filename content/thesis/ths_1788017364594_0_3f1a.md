# Homomorphic Encryption for Private Vector Retrieval: BFV/CKKS Packing, Seal-PIR Doubly-Encoded Queries, and Sublinear Communication via Cuckoo Hashing and NTT-Accelerated Ciphertext Operations

## Abstract
Private Information Retrieval (PIR) over vector databases requires fetching a record without leaking its index, while maintaining sublinear communication and practical server computation. This thesis develops a unified architecture for single-server PIR using leveled homomorphic encryption (BFV and CKKS), Seal-PIR style query compression with doubly-encoded recursion, cuckoo-hashing for sparse keyword-to-index mapping, and NTT-accelerated ciphertext operations on GPUs. We formalize vector retrieval as homomorphic dot-product over RLWE ciphertexts packing N=4096–16384 slots, analyze modulus switching noise growth, and prove correctness under 128-bit security. We demonstrate how probabilistic batch codes and 2-choice cuckoo hashing reduce bucket overflow to <2^{-40}, while NTT pipelines achieve 3.9× speedup for first-dimension expansion. The construction synthesizes XPIR, SealPIR, FastPIR, Spiral and SimplePIR trade-offs, yielding query sizes of 64–128 KB and response expansion below 4.5× for million-record databases.

## 1 Introduction
Single-server Private Information Retrieval (PIR) [1][2] allows a client to retrieve the *i*-th element from a server's database $D \in \mathcal{R}^{n}$ without revealing $i$ to the server, under computational hardness assumptions. The canonical definition requires that the server process the *entire* database per query — the *all-for-one* principle — to avoid access-pattern leakage [3].

Homomorphic-encryption-based PIR has emerged as the most practical instantiation for large databases. XPIR (2016) demonstrated minute-level responses on million-scale databases using multidimensional vector encoding and RLWE operations [4], but query size grew linearly in $n$. **SealPIR** introduced by Angel et al. (2018) at IEEE S&P [1][6] applied polynomial compression, reducing query size by **274×** relative to XPIR, and introduced probabilistic batch codes for multi-query amortization achieving **40×** speedup over naive batching [1].

> **Theorem 1 (PIR Security):** Under RLWE with ring degree $N$ and modulus $Q$, the server's view $\mathsf{View}_{\mathcal{S}}(q)$ is computationally indistinguishable from $\mathsf{Sim}(1^\lambda)$ for any PPT adversary $\mathcal{A}$ with advantage $\mathsf{negl}(\lambda)$. Formally, $\Pr[\mathcal{A}(\mathsf{Enc}_{pk}(e_i)) = i] \le 1/n + \mathsf{negl}$.

Recent advances span two dimensions:

- **Communication:** FastPIR (Ahmed et al. 2022) [2], OnionPIR, Spiral and SimplePIR (Henzinger et al. 2023) [3] reduce response expansion from 100× to 4.2× via Regev-style LWE ciphertexts and RGSW outer products.
- **Computation:** NTT acceleration on GPUs [6] yields 267× speedup in first-dimension processing and 3.9× total cost reduction.

*Vector retrieval* — where each database element is a $d$-dimensional embedding $v_i \in \mathbb{F}_t^d$ — introduces new challenges: packing multiple vectors per plaintext polynomial, handling approximate similarity scores with **CKKS**, and supporting keyword PIR via cuckoo hashing [7][8].

This thesis contributes:

1. A formal model for BFV/CKKS slot packing for vector DBs with coefficient vs. slot encoding trade-offs.
2. A reconstruction of Seal-PIR's doubly-encoded query compression and recursion (dimension $d=2,3$).
3. A cuckoo-hashing layer achieving $O(1)$ lookup with stash size $s=2$ and failure $2^{-40}$ for batch PIR [7][8].
4. An NTT-accelerated homomorphic pipeline with GPU thread mapping and modular reduction analysis [6].
5. Empirical cost model for $n=2^{20}$ records, $d=768$ embeddings.

## 2 Background

### 2.1 RLWE and Leveled HE

Let $R = \mathbb{Z}[X]/(X^N+1)$ with $N=2^k$, $R_q = R/qR$. RLWE [4][5] hardness underpins second-generation schemes. For secret $s \leftarrow \chi$, error $e \leftarrow \chi$, sample $a \leftarrow R_q$, output $(a, b = a s + e)$.

**BFV** (Brakerski-Fan-Vercauteren) [4] provides exact arithmetic over $R_t$:

- Plaintext modulus $t$, ciphertext modulus $Q = \prod_{i=0}^{L-1} q_i$
- Encryption: $\mathsf{ct} = ( -a s + e + \Delta m, a)$ where $\Delta = \lfloor Q/t \rfloor$ [4]
- Decryption: $m = \lfloor t/Q \cdot (c_0 + c_1 s) \rceil \mod t$
- Noise budget: $\nu \approx \log_2(Q/t) - \log_2(||e||_\infty) - \log_2 N$

BFV is *exact* — crucial for index retrieval — but slower than CKKS for approximate inner products [4][5].

**CKKS** (Cheon-Kim-Kim-Song) [5] supports approximate arithmetic over $\mathbb{C}^{N/2}$:

- Encoding: $\mathsf{Ecd}_{\mathsf{slot}}(\mathbf{m}) = \lfloor \Delta \cdot \mathsf{iDFT}(\mathbf{m}) \rceil$ where $\zeta = \exp(i\pi/N)$ [5]
- Scaling factor $\Delta$ controls precision; rescaling after multiplication drops modulus level
- Homomorphic multiplication: $\mathsf{ct}_{\mathsf{mult}} = \mathsf{Relin}(\mathsf{ct}_1 \otimes \mathsf{ct}_2)$ then $\mathsf{Rescale}$

*Both schemes* rely on **Number Theoretic Transform (NTT)** for $O(N \log N)$ polynomial multiplication [6].

| Scheme | Plaintext Space | Exact? | Encoding | Mult Depth w/o Bootstrap | Typical Use in PIR |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **BFV** [4] | $R_t$, $t=2^{16}$–$2^{32}$ | Yes | coeff / slot via CRT batching | 2–4 | Index PIR, keyword PIR |
| **CKKS** [5] | $\mathbb{C}^{N/2}$ | No ($\approx$) | slot via iDFT | 5–10 (rescale) | Similarity scoring, $\ell_2$ distance |
| BGV | $R_t$ | Yes | slot | 3–5 | Baseline comparison |
| TFHE | $\mathbb{T}$ | Yes (bit) | binary | Unlimited via bootstrap | Low-latency comparison |

### 2.2 PIR Definitions

**Definition (Single-Server PIR):** Protocol $\Pi = (\mathsf{Query}, \mathsf{Answer}, \mathsf{Extract})$ with:

- $\mathsf{Query}(i) \rightarrow (q, sk)$ — client encrypts one-hot vector $e_i \in \{0,1\}^n$
- $\mathsf{Answer}(D, q) \rightarrow r$ — server computes $r = \sum_{j} D[j] \cdot \mathsf{Enc}(e_i[j])$ homomorphically
- $\mathsf{Extract}(r, sk) \rightarrow D[i]$

Correctness: $\Pr[\mathsf{Extract}(\mathsf{Answer}(D,\mathsf{Query}(i)))=D[i]] = 1 - \mathsf{negl}$.

Communication: $|q| + |r| = o(n)$. Computational PIR achieves this under RLWE [1][2][3].

SealPIR achieves $|q| = O(\sqrt{n})$ after compression vs XPIR's $O(n)$ [1]. FastPIR [2] achieves $|r| \approx 2$ ciphertexts via modulus switching. SimplePIR [3] achieves *10 Gbps* throughput with *no* homomorphic multiplications using LWE ciphertext preprocessing.

### 2.3 Cuckoo Hashing for Keyword PIR

Keyword PIR maps sparse keyword universe $\mathcal{K}$ ($|\mathcal{K}| \gg n$) to dense table. **Cuckoo hashing** with $k=2$ hash functions $h_1, h_2: \mathcal{K} \rightarrow [b]$ places each keyword in exactly one of $k$ bins, each holding $\ell$ items [7][8].

Parameters from Yeo [7]:

- $b = 1.27 n$ bins, $\ell = 4$, stash $s = 2$ yields failure $\epsilon \le 2^{-40}$ for $n=2^{20}$
- Query overhead $O(k \ell) = O(1)$
- For batch PIR, hypergraph peeling constructs 3-hash Garbled Cuckoo Tables reducing communication by 27% [8]

This avoids PIR over $|\mathcal{K}|$ — instead PIR over $b$ buckets, each small.

## 3 Methodology

Our architecture composes four layers:

**Layer 0 – Vector Packing (BFV/CKKS):** For $n$ vectors $v_i \in \mathbb{Z}_t^d$, choose packing factor $p = N / \lceil \log_t(\text{dim}) \rceil$. BFV batch encoding via CRT: $R_t \cong \mathbb{Z}_t^{N}$ when $t \equiv 1 \mod 2N$ (requires $N$-th roots of unity). This packs $N$ scalars per ciphertext. For $d=768$, $N=8192$, we pack $\lfloor 8192/768 \rfloor = 10$ vectors per plaintext. CKKS packs $N/2 = 4096$ complex slots per ciphertext for cosine similarity: $\mathsf{sim}(q,v) = \langle q, v \rangle / (||q|| \cdot ||v||)$ computed as dot-product followed by approximate inverse square root polynomial.

**Layer 1 – Query Compression (SealPIR):** Client query $e_i$ is $n$ bits. In $d$-dimensional hypercube representation, $n = n_0 \times n_1 \times ... \times n_{d-1}$. XPIR would send $d$ ciphertexts encrypting dimension vectors of sizes $n_j$. SealPIR compresses first dimension using RLWE substitution: encrypt seed $\mathsf{Enc}(s)$, server expands via $\mathsf{Sub}_{2^k}$ automorphism to $n_0$ ciphertexts [1]. Compression ratio $= n_0 / 1$ = up to 64× for $n_0=64$. Doubly-encoded recursion: after first-dimension inner product, intermediate ciphertexts are re-packed into fewer BFV ciphertexts before second-dimension multiplication to keep noise low.

**Layer 2 – Cuckoo Bucket Selection:** For keyword PIR, client computes $h_1(k), h_2(k)$, builds one-hot over buckets $b$. Server's table $T$ where $T[h(k)] = v_k$ else dummy. PIR over $b$ buckets (not $|\mathcal{K}|$) yields sublinear communication $O(\sqrt{b})$.

**Layer 3 – NTT Acceleration:** Polynomial multiplication $a(X) \cdot s(X)$ in $R_q$ dominates. Naive $O(N^2)$ → NTT $O(N \log N)$. GPU implementation [6] maps butterfly stages to warps: for $N=8192$, 13 stages, each stage $N/2$ butterflies. Using 64-bit Barrett reduction, coalesced memory, and on-chip shared memory for twiddle factors, throughput improves 267× for first-dim expansion [6].

> **Theorem 2 (Noise Bound for BFV PIR Dot-Product):** For BFV with modulus $Q$, plaintext $t$, and database size $n$, noise after $\mathsf{Answer}$ satisfies $||e_{\mathsf{ans}}||_\infty \le n \cdot B_{\mathsf{mult}} + B_{\mathsf{enc}}$ where $B_{\mathsf{mult}} = t \cdot N \cdot \sigma \cdot \sqrt{N}$ and decryption succeeds if $||e_{\mathsf{ans}}|| < Q/(2t)$. Hence $Q$ must satisfy $\log_2 Q \ge \log_2 t + \log_2 n + \log_2 N + \log_2 \sigma + 1$.

## 4 Deep Dive

### 4.1 BFV vs CKKS Packing for Vector DBs

**BFV Coefficient Packing:** Encode vector $v = (v_0,...,v_{d-1})$ as polynomial $m(X) = \sum_{j=0}^{d-1} v_j X^j$. Multiplication by query bit $q_i \in \{0,1\}$ (encrypted) yields $q_i \cdot m_i(X)$. Sum over $i$ yields selected vector's polynomial. Advantage: no need for $t \equiv 1 \mod 2N$; works for any $t$. Disadvantage: one vector per plaintext, low throughput.

**BFV CRT Batching (Slot Packing):** Choose $t$ prime with $t \equiv 1 \mod 2N$ → $R_t \cong \prod_{i=0}^{N-1} \mathbb{Z}_t$ via CRT. Then $m$ encodes $N$ independent scalars in slots. We store database transposed: plaintext $j$ holds $j$-th coordinate across $N$ vectors. Query expansion selects slot. This yields amortized $O(1)$ per vector after NTT.

**CKKS Approximate Packing:** For similarity search, client encrypts query $q \in \mathbb{R}^d$ as $\mathsf{Ecd}_{\mathsf{slot}}(q)$. Server stores $v_i$ as plaintext (no encryption). Homomorphic dot-product: $\mathsf{ct}_{\mathsf{dot}} = \sum_{j=0}^{d-1} q_j \cdot v_{i,j}$ via $\mathsf{PlainMult}$ + $\mathsf{Rotate}$ + $\mathsf{Add}$. Since CKKS is approximate, error $ \approx \Delta^{-1} \cdot ||v||_\infty$. Choosing $\Delta = 2^{40}$ yields 12 decimal digits precision, sufficient for top-$k$ ranking.

*Trade-off matrix:*

- **Exact retrieval → BFV** [4]
- **Similarity ranking → CKKS** [5] + BFV index fetch as two-phase protocol (ANN then PIR)
- **Hybrid:** Use CKKS for ANN candidates, BFV for final fetch — avoids leaking approximate distances.

### 4.2 Seal-PIR Doubly-Encoded Query Recursion and Compression

SealPIR [1] core insight: **compress** query ciphertexts by sending only one RLWE ciphertext containing a seed, then homomorphically expanding via automorphisms $X \mapsto X^{2^k+1}$.

Formal: For dimension $d=2$, database reshaped to $\sqrt{n} \times \sqrt{n}$ matrix $D \in R_t^{\sqrt{n} \times \sqrt{n}}$. Client wants $D[i_0,i_1]$. It creates $c_0 = \mathsf{Enc}(e_{i_0})$ (size $\sqrt{n}$ one-hot) and $c_1 = \mathsf{Enc}(e_{i_1})$. XPIR would send both: $|q| = 2 \sqrt{n} |ct|$.

SealPIR compression:

1. Client samples $s \leftarrow R_2$, sends $c_{\mathsf{seed}} = \mathsf{Enc}(s)$ where $s$ encodes expansion index.
2. Server applies $\mathsf{Expand}(c_{\mathsf{seed}}) \rightarrow \{c_0^{(k)}\}_{k=0}^{n_0-1}$ using Galois keys $gk_k$: $c^{(k)} = \mathsf{Automorph}(c, k) = \mathsf{Enc}(s(X^{k}))$.
3. Server computes intermediate $y_j = \langle D[:,j], c_0 \rangle$ homomorphically: $y_j = \sum_{k} D[k,j] \cdot c_0^{(k)}$.
4. Recursively: $y_j$ are themselves ciphertexts. SealPIR **re-encodes** $y_j$ into fewer ciphertexts using modulus switching and windowing: packing $\beta = \lfloor \log_{t} Q \rfloor$ intermediate values per ciphertext (doubly-encoded).

This reduces query upload from $n_0 |ct|$ to $1 |ct|$ + $n_1 |ct|$ = $O(\sqrt{n})$ vs $O(n)$ originally, net compression $n_0 = 64$ → $64×$ [1][6].

For $d=3$, recursion depth 3 yields $|q| = O(n^{1/3})$. Angel et al. report up to **274×** reduction [1].

*Noise analysis for recursion:* Each expansion adds $B_{\mathsf{auto}} \approx N \cdot \sigma \cdot ||gk||$. After two dimensions, noise $B_{\mathsf{total}} = n_0 B_{\mathsf{mult}} + n_1 (B_{\mathsf{mult}} + B_{\mathsf{auto}})$. Modulus switching $Q \rightarrow Q' = Q / t$ after first dimension resets noise.

### 4.3 Cuckoo Hashing for Sublinear Keyword PIR and Batch Codes

Direct keyword PIR over universe $\mathcal{U} = 2^{256}$ is infeasible. Cuckoo hashing [7][8] reduces to PIR over $b \ll |\mathcal{U}|$ buckets.

**Construction:**

- Parameters: $k=2$ hash functions $h_1,h_2 : \mathcal{K} \rightarrow [b]$, bin capacity $\ell=4$, stash size $s=2$ [7].
- Insert: For keyword $w$, try $T[h_1(w)]$; if full, evict existing $w'$ to $h_2(w')$, repeat up to 500 iterations (BFS cuckoo).
- Failure probability: For $b = 1.3 n$, $\Pr[\mathsf{fail}] \le 2^{-40}$ (Theorem 3.2 in [7]).
- Query: Client with keyword $w$ computes $i_1 = h_1(w), i_2 = h_2(w)$, sends PIR query for *both* buckets (one-hot of size $b$). Since $w$ is in exactly one of them, server returns both buckets (size $\ell$ each). Client scans locally.

Batch PIR [8]: For $q$ simultaneous queries, use **Probabilistic Batch Code (PBC)** from Angel et al. [1] — encode database into $m$ buckets such that any $q$-subset can be retrieved via $q$ disjoint bucket queries. PBC achieves amortized $O(1)$ server work per query, **40×** faster than naive batch [1]. Combined with cuckoo hashing, Batch Spiral PIR (2024) achieves GPU acceleration.

Haskell model of insertion:

```haskell
-- Cuckoo hashing insert with stash for PIR bucket mapping
type Bucket = [Keyword]
type Table = Array Int Bucket

insertCuckoo :: Table -> Keyword -> (Table, Maybe Keyword)
insertCuckoo tbl kw = go tbl kw 0 h1
  where
    h1 = hash1 kw `mod` b
    h2 = hash2 kw `mod` b
    go t k depth h
      | depth > 500 = (t, Just k) -- stash
      | length (t!h) < ell = (t // [(h, k : t!h)], Nothing)
      | otherwise = let (evict:rest) = t!h
                        t' = t // [(h, k:rest)]
                        h' = if h == hash1 evict `mod` b then hash2 evict `mod` b else hash1 evict `mod` b
                    in go t' evict (depth+1) h'
```

Security: Cuckoo hashing is *public* — server sees table $T$ (plaintext), not query. Privacy relies on PIR over buckets, not on hiding hash functions. Robust cuckoo hashing [7] ensures adversary who chooses keyword set after seeing hash functions still has $\tilde{O}(\log \lambda)$ query overhead — tight lower bound.

### 4.4 NTT-Accelerated Ciphertext Operations and GPU Mapping

NTT dominates BFV/CKKS multiplication: $a(X) \cdot b(X) \mod (X^N+1, q)$. For each modulus $q_i$ in RNS chain ($L \approx 5$), perform NTT.

**NTT Definition:** For root $\psi$ with $\psi^{2N}=1$, $\mathsf{NTT}(a)[j] = \sum_{i=0}^{N-1} a_i \psi^{i j}$.

Butterfly: $(u,v) \rightarrow (u + \omega v, u - \omega v)$ with twiddle $\omega = \psi^{2k}$.

GPU acceleration [6]:

- **Stage parallelization:** $N=8192$ → 13 stages, each stage $N/2=4096$ independent butterflies → map to 32 warps (128 threads each).
- **Shared memory:** Twiddle factors precomputed in constant memory; intermediate results in shared memory to avoid global memory traffic.
- **Barrett reduction:** $x \mod q_i$ via $\lfloor x \cdot \mu / 2^{2k} \rfloor$, $\mu = \lfloor 2^{2k}/q_i \rfloor$, avoiding division.
- **RNS decomposition:** For $Q = \prod q_i$, perform NTT per $q_i$ in parallel across streams; then combine via CRT for modulus switching.

Performance [6]:

| Operation | CPU (ms) | GPU (ms) | Speedup |
| :--- | :--- | :--- | :--- |
| NTT $N=8192$ | 1.2 | 0.018 | 66× |
| First-dim expand $n=2^{20}$ | 4.8 sec | 0.018 sec | 267× |
| Total PIR $n=2^{20}$ | 8.3 sec | 2.1 sec | 3.9× |

Memory: For $n=2^{20}$, $d=1$ KB record, database 1 GB. Server needs to stream database through GPU: PCIe bandwidth 16 GB/s becomes bottleneck; solution is *on-the-fly* generation of database via PRG (Spiral [2] uses Regev encryption to compress DB to seed).

Rust NTT kernel sketch:

```rust
// NTT butterfly with Barrett reduction - GPU-like CPU emulation
fn ntt_butterfly(a: &mut [u64], twiddles: &[u64], q: u64, mu: u64) {
    let n = a.len();
    let mut len = 1;
    while len < n {
        for i in (0..n).step_by(len*2) {
            for j in 0..len {
                let u = a[i+j];
                let v = mod_mul(a[i+j+len], twiddles[len+j], q, mu);
                a[i+j] = mod_add(u, v, q);
                a[i+j+len] = mod_sub(u, v, q);
            }
        }
        len <<= 1;
    }
}
```

Modulus switching after NTT: $c' = \lfloor c \cdot q_{L-1}^{-1} \rceil$ to reduce noise before second dimension.

### 4.5 Putting It Together: End-to-End Private Vector Retrieval Protocol

**Protocol $\Pi_{\mathsf{PVR}}$:**

1. **Setup:** Server has $D = \{v_i\}_{i=0}^{n-1}$, $v_i \in \mathbb{Z}_t^d$. Builds cuckoo table $T$ with $b$ buckets, each bucket stores $\ell$ vectors padded. Chooses BFV params $N=8192$, $Q \approx 218$-bit (3 primes 60-bit each), $t=2^{20}$, $\sigma=3.2$.

2. **Query:** Client wants keyword $w$ (or index $i$). Computes $h_1(w), h_2(w)$. Builds one-hot $e_{h_1}, e_{h_2} \in \{0,1\}^b$ (or $e_i$ for index PIR). Encrypts with BFV: $q = \mathsf{Enc}_{pk}(e)$. Compresses via SealPIR seed expansion: sends $c_{\mathsf{seed}}$ + $n_1$ second-dimension ciphertexts. Total $|q| \approx 64$ KB.

3. **Answer:** Server:
   - Expands $c_{\mathsf{seed}}$ to $n_0$ ciphertexts via NTT-accelerated automorphisms.
   - First-dim inner product: $y_j = \sum_{k=0}^{n_0-1} D[k,j] \cdot c^{(k)}$ for $j \in [n_1]$ using NTT mult.
   - Modulus switch $y_j$.
   - Second-dim: $r = \sum_{j} y_j \cdot c_{1}[j]$ where $c_1 = \mathsf{Enc}(e_{i_1})$.
   - If CKKS ranking requested, also computes $\mathsf{ct}_{\mathsf{score}} = \langle q_{\mathsf{ckks}}, v_{cand} \rangle$.

4. **Extract:** Client decrypts $r$ via $sk$, decodes CRT batching to recover $v_i$. For cuckoo, decrypts both buckets, scans for $w$.

*Communication analysis:*

- $|q| = O(\sqrt{b})$ = 64 KB for $b=2^{17}$, $N=8192$.
- $|r| = 1$ BFV ciphertext = $2 N \log_2 Q$ bits ≈ $2 * 8192 * 218 /8$ ≈ 436 KB. FastPIR [2] reduces to 2 LWE ciphertexts ≈ 70 KB via modulus switching.
- Total sublinear: $500$ KB vs $n \cdot |v| = 1$ GB for naive.

> **Theorem 3 (Correctness of PVR):** If BFV noise bound $B_{\mathsf{ans}} < Q/(2t)$ and cuckoo hashing succeeds ($\Pr[\mathsf{fail}] \le 2^{-40}$), then $\Pi_{\mathsf{PVR}}$ returns correct $v_i$ with probability $\ge 1 - 2^{-40} - \mathsf{negl}(\lambda)$.

## 5 Empirical/Proofs

### 5.1 Security Proof Sketch

**Hybrid 0:** Real game $\mathsf{Real}_{\mathcal{A}} = \mathsf{View}_{\mathcal{S}}(q)$.

**Hybrid 1:** Replace BFV ciphertexts with random RLWE samples $(a, b \leftarrow R_q)$. Indistinguishable by RLWE assumption [4][5] — advantage $\epsilon_{\mathsf{RLWE}}$.

**Hybrid 2:** Replace CKKS ciphertexts similarly.

Since $q$ encrypts one-hot vector, but RLWE ciphertexts are pseudorandom, server cannot distinguish $e_i$ from $e_j$: $\mathsf{Adv}^{\mathsf{PIR}}_{\mathcal{A}} \le 2 \epsilon_{\mathsf{RLWE}}$.

For cuckoo hashing, table $T$ is public deterministic function of $D$ and hash seeds, independent of query. Hence no leakage beyond bucket count $b$ (public parameter). Robustness [7] ensures adversary choosing $D$ adaptively cannot increase failure probability beyond $2^{-40}$ except with $\mathsf{negl}$.

### 5.2 Cost Model

Let $n=2^{20}$ (1M records), $|v|=768$ int16 (1.5 KB), $N=8192$, $L=3$ moduli.

- **Server compute:** First-dim: $n$ NTT mults = $2^{20} * O(N \log N)$ ≈ $2^{20} * 8192*13$ modular mults ≈ $2^{34}$ mults. At 3 GHz CPU, 1 mult = 3 cycles → 8.5 sec. GPU [6] 2.1 sec.
- **Memory bandwidth:** Streaming $n|v| = 1.5$ GB through cache — 1.5 GB / 20 GB/s = 75 ms, dominated by compute.
- **Noise:** $B_{\mathsf{enc}} = 6 \sigma \sqrt{N} \approx 6*3.2*90 ≈ 1728$. After $n_0=1024$ mults, $B_{\mathsf{ans}} ≈ 1024* t N \sigma ≈ 1024*2^{20}*8192*3.2 ≈ 2^{44}$. Require $Q > 2 t B_{\mathsf{ans}} ≈ 2^{66}$ → 218-bit $Q$ (3×60-bit primes + 38-bit special) satisfies 128-bit security per HomomorphicEncryption.org standard (requires $N=8192$, $\log Q \le 218$ for 128-bit).

## 6 Limitations

1. **All-for-one cost:** Despite NTT acceleration, server must touch entire DB per query — inherent to single-server PIR security [3]. For $n=2^{22}$ (4M vectors, 6 GB), GPU memory 16 GB insufficient for full NTT pipeline; requires chunked streaming, increasing latency to ~9 sec.

2. **Noise growth for deep recursion:** $d=3$ recursion (cube root) yields noise $B \propto n^{2/3} t N \sigma$, requiring $N=16384$ for $n=2^{20}$, halving throughput. Modulus switching helps but consumes levels; bootstrapping would be needed for $d>3$, currently impractical (CKKS bootstrapping ~1 sec per ciphertext).

3. **Cuckoo hashing stash leakage:** If stash size $s>0$, client must fetch stash via separate PIR (or download entire stash). Stash of size 2 leaking that a particular keyword was in stash reveals it was among the $\approx 2^{-40}$ failure cases — negligible but not zero. Robust cuckoo hashing [7] shows $\tilde{O}(\log \lambda)$ overhead is optimal for adversarial sets; achieving $O(1)$ robust is impossible.

4. **CKKS precision vs ranking:** CKKS approximate dot-product error $\approx \Delta^{-1} ||v||$ may flip top-$k$ order when scores differ by $<10^{-6}$. Requires double-precision $\Delta=2^{50}$ and 2 extra levels, reducing depth for subsequent BFV fetch. Exact BFV retrieval avoids this but cannot rank.

5. **Communication lower bound:** Single-server PIR has $\Omega(\log n)$ lower bound for query + response under RLWE [2]. SimplePIR [3] achieves $O(\sqrt{n})$ query but with *hints* — client must download 16 MB hint per DB version, amortized over queries. Our analysis assumes hint reuse; for ephemeral DBs, hint download dominates.

6. **GPU side channels:** NTT timing on GPU leaks access pattern via warp divergence if modulus not constant-time. Barrett reduction is constant-time, but shared memory bank conflicts may leak $h_1(w)$ vs $h_2(w)$ through timing. Mitigation: pad both buckets to same size, always process $\ell$ items.

7. **Vector dimension packing inefficiency:** For $d=768$ not dividing $N=8192$, CRT packing wastes $8192 \mod 768 = 512$ slots per plaintext (6.25% waste). For $d=1024$, waste zero, but for $d=1536$, need 2 ciphertexts per vector batch.

---

## 7 Conclusion

We presented a unified single-server private vector retrieval protocol combining **BFV/CKKS packing**, **Seal-PIR doubly-encoded query compression**, **cuckoo hashing for sparse keyword mapping**, and **NTT-accelerated GPU ciphertext operations**. The construction achieves sublinear communication ($64$ KB query, $70$ KB response with FastPIR optimization [2]), practical server time ($2.1$ sec for $n=2^{20}$ via NTT [6]), and 128-bit RLWE security [4][5].

Key insights:

- **Packing matters:** CRT batching yields $10×$ throughput vs coefficient packing; CKKS enables approximate similarity at cost of precision.
- **Compression is essential:** SealPIR's polynomial expansion reduces query size $274×$ [1], making PIR viable over WAN.
- **Hashing reduces domain:** Cuckoo hashing with $\ell=4$, $b=1.27n$ maps sparse keyword universe to dense buckets with $2^{-40}$ failure [7][8], enabling Batch PIR.
- **NTT is bottleneck:** GPU acceleration yields $267×$ first-dimension speedup [6], but memory bandwidth and noise remain fundamental.

Future work includes integrating Spiral's Regev encryption for response compression [2], exploring SimplePIR-style LWE preprocessing for hint-based $10$ Gbps throughput [3], and developing robust cuckoo hashing with $O(1)$ query overhead against adaptive adversaries [7]. Extending to *multi-client* private ANN via CKKS-encrypted IVF lists with BFV fetch remains open, as does formalizing leakage from approximate CKKS scores in the IND-CPA-D game.

The synthesis demonstrates that homomorphic-encryption-based PIR has crossed from theoretical curiosity to deployable privacy infrastructure — provided careful co-design of cryptography (BFV/CKKS [4][5]), data structures (cuckoo hashing [7][8]), and hardware acceleration (NTT on GPUs [6]).
