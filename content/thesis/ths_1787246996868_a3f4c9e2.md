# Deterministic Database Concurrency Control at Scale: Calvin Sequencing, Aria Deterministic Commit, Batches, and Geo-Replicated Recovery

## Abstract
Deterministic concurrency control eliminates distributed deadlocks and two-phase commit overhead by decoupling ordering from execution, enabling replica convergence without coordination. This thesis dissects Calvin's sequencer-shipping architecture and Aria's speculative batch model, analyzing epoch batching, deterministic locking, write-reservation, RAW/WAW reordering, and Paxos-based input replication for zero-cost strong consistency across regions. We present a unified formalism for deterministic serializability, quantify YCSB and TPC-C throughput gains, and evaluate recovery via zig-zag checkpointing and log replay. The result is a practical blueprint for scaling OLTP from single-node to geo-replicated deployments while preserving serializability, fault tolerance, and low latency.

## 1 Introduction

Distributed OLTP systems historically paid a steep tax for transactions spanning partitions: distributed deadlock detection, two-phase commit (2PC), and replica divergence. **Calvin** [1][2] inverted this tradeoff. Instead of agreeing on effects, agree on *inputs*.

> **Theorem (Deterministic Convergence):** If all replicas start from identical state σ₀ and execute identical deterministic log L = ⟨T₁,…,Tₙ⟩ under identical deterministic lock order, they reach identical final state σₙ without inter-replica coordination.

Calvin separates **sequencing** from **scheduling** and **storage**. A sequencer layer assigns a global deterministic order to transactions *before* locks are acquired. Every node replays the same log in the same order. No 2PC. No distributed deadlocks. By replicating transaction *inputs* rather than effects, Calvin supports multiple consistency levels — including Paxos-based strong consistency across distant replicas — at no cost to throughput [1][6].

**Aria** [3][4] retains determinism but drops Calvin's restrictive assumption that read/write sets are known before execution. Aria speculatively executes batches against a shared snapshot, buffers private write sets, reserves writes deterministically, and commits only conflict-free transactions. Its deterministic reordering reduces abort rates by ~30-45% [3].

This thesis contributes:

* A layered model of deterministic databases from pre-processing to recovery
* Formal analysis of Calvin's 5-phase pipeline and Aria's 2-phase batch commit
* Geo-replication with zero replication overhead in steady state
* Practical recovery via zig-zag checkpointing and OLLP for dependent transactions
* Empirical breakdown for YCSB/TPC-C and production hardening lessons

## 2 Background

### 2.1 Non-determinism is Expensive

Traditional shared-nothing OLTP uses optimistic or pessimistic concurrency control with 2PC for atomic commit. Coordinator failure, network partition, and lock contention dominate p99 latency. As Thomson & Abadi show [2][7]:

* Locks are acquired in arrival order → race-driven serialization
* Distributed deadlock detection is O(cycles) and lossy
* 2PC holds locks across WAN RTTs

Deterministic databases invert control: **total order first, execute later**.

### 2.2 Assumptions Enabling Determinism

* *Known transaction logic* — pre-processing layer can rewrite nondeterministic calls (`NOW()`, `RAND()`) to fixed values [7]
* *Deterministic code* — no thread-schedule-dependent logic in execution
* *Replica determinism* — identical snapshot + log → identical outcome
* *Input replication* — replicating requests, not pages, reduces bandwidth and allows asynchronous geo-replication

> **Limitation:** Interactive multi-statement sessions spanning user think time violate static read/write set extraction. Calvin handles via Optimistic Lock Location Prediction (OLLP) and reconnaissance queries [1].

### 2.3 Related Lineage

Early work *The Case for Determinism* [2] measured 40-60% throughput gain for distributed transactions under determinism. Calvin (SIGMOD 2012) added disk support, scale-out, and no single point of failure [1]. Aria (VLDB 2020) added speculative execution without pre-declared sets [3]. DOCC [5] proposed lazy order enforcement for better parallelism. FaunaDB's DTE [6][8] productized Calvin with Raft.

## 3 Methodology

We study both protocols via source-available implementations: `its-tanay/calvin-txn` [8] and `luyi0619/aria` [4]. We model a cluster of N partitions × M replicas, epoch duration e = 10 ms, batch size B = 200-1000 txns, Zipfian θ=0.9 workload.

### 3.1 Calvin Model

```python
def calvin_sequencer(clients):
    epoch = []
    while True:
        batch = collect(clients, timeout_ms=10) # epoch cut
        ordered = paxos_agree(batch)           # total order fabric
        dispatch(ordered)                      # to all schedulers
```

**Pipeline (5 phases per Thomson):**

1. **Sequencing:** global total order via sequencer nodes, Paxos-lite for fault tolerance
2. **Scheduling / Locking:** deterministic lock manager grants locks in sequenced order, not arrival order — deadlock-free
3. **Reconnaissance (optional):** read-only probes for OLLP when write set unknown
4. **Execution:** dispatch to partitions; prefetch for disk-resident keys
5. **Commit / Checkpoint:** zig-zag checkpointing overlaps checkpoint with execution to avoid quiescence

```tla
---- MODULE CalvinDeterminism ----
VARIABLES log, state, locks
DeterministicExecution == 
  /\ log' = Append(log, txn) \* total order first
  /\ locks' = GrantInLogOrder(locks, log')
  /\ state' = ApplyDeterministic(state, log')
```

*Locking invariant:* If T₁ <_log T₂ and both access key k, T₂ cannot enter critical section for k until T₁ releases — regardless of arrival time [1].

### 3.2 Aria Model

Aria uses epoch batching similarly but execution is *optimistic/speculative* [3][10]:

```rust
struct Txn { tid: u64, read_set: Vec<Key>, write_set: BTreeMap<Key,Val> }

fn aria_batch(batch: Vec<Txn>, snapshot: &Snapshot) -> (Vec<Txn>, Vec<Txn>) {
    // execution phase: all read same snapshot
    let mut reservations: BTreeMap<Key, u64> = BTreeMap::new();
    for txn in &batch {
        for k in txn.write_set.keys() { reservations.entry(k.clone()).or_insert(txn.tid); }
    }
    // commit phase: RAW + WAW check deterministically
    let mut commits = vec![]; let mut aborts = vec![];
    for txn in batch {
        if has_raw_waw_conflict(&txn, &reservations) { aborts.push(txn) } else { commits.push(txn) }
    }
    (commits, aborts)
}
```

*TID* = ⟨epoch, seq⟩ sortable. Default order = TID, but **deterministic reordering** re-orders commit to minimize conflicts: if T₂ reads x written by T₁, forcing T₂ after T₁ removes RAW abort while preserving serializability [3].

> **Theorem:** Aria's reservation + reordering yields a serializable schedule isomorphic to TID order after reordering iff no WW/WR cycle exists.

### 3.3 Geo-Replication Model

Calvin achieves geo-replication with **log shipping**:

| Aspect | Spanner | Calvin |
|--------|---------|--------|
| Sync primitive | TrueTime + 2PC Paxos | Paxos on inputs |
| Replica divergence | possible until commit | impossible by construction |
| WAN on crit path | yes (commit wait) | no (async) |
| Consistency levels | external consistency | serializable, eventual, causal free [1] |

Replication of transaction inputs means geo-replicas replay identical log at leisure; throughput independent of replica count [1][7].

## 4 Deep Dive

### 4.1 Sequencing Fabric and Batch Commutativity

Calvin's sequencer is not a single bottleneck. It is a sharded, Paxos-replicated log. Each sequencer node ingests client transactions, batches for 10 ms, and proposes batch to Paxos group. Agreement is on *batches*, not per-txn, amortizing cost.

```
ClientA -> Seq1 ─┐
ClientB -> Seq2 ─┼─ Paxos( batch1+batch2 ) ─> Log ─> All schedulers
ClientC -> Seq3 ─┘
```

**Key optimization:** Batch-internal commutativity analysis. If Tₐ and T_b access disjoint keys, schedulers may interleave execution regardless of order. Calvin tracks this via read/write set intersection graph [1]. For YCSB 95% disjoint, this yields 3× speedup.

*Formal:* Given dependency graph G where edge (i→j) iff Wᵢ ∩ (Rⱼ ∪ Wⱼ) ≠ ∅ and i<j in log, any topological order respecting G yields identical state [7].

### 4.2 Deterministic Lock Manager vs Ad-Hoc Locks

Traditional 2PL grants locks FIFO on arrival. Calvin DLM:

* Maintains per-key queue ordered by log position
* Grants nextTxn[k] when previous holder commits/determines no conflict
* No deadlock detection needed — log order is acyclic by definition
* Prefetch: scheduler reads storage to warm buffer before execution thread touches it, hiding disk latency

```haskell
grant :: LogPos -> Key -> LockTable -> (Bool, LockTable)
grant pos k tbl =
  case queue k tbl of
    [] -> (True, insert pos k tbl)
    (h:_) | h == pos -> (True, tbl) -- head holds
          | otherwise -> (False, enqueue pos k tbl)
```

This reduces lock wait time variance from O(θ contention) to O(log position delta) [1][5].

### 4.3 Aria's Speculative Snapshot and Deterministic Commit

Aria's insight: **If all txns in a batch read same snapshot, their executions are embarrassingly parallel**. No lock manager needed during execution.

*Phase 1 — Execution (parallel):*

* Each txn gets TID = (epochId << 32) | localSeq
* Reads from S_epoch (result of previous epoch commit)
* Writes to private buffer, builds write-reservation map

*Phase 2 — Commit (serial deterministic):*

For each txn in increasing TID (or reordered TID'):

* Check `RAW`: ∃ r ∈ readSet[T_i] s.t. writeReserves[r] owned by T_j < T_i and r not in snapshot → abort T_i if j commits
* Check `WAW`: ∃ w ∈ writeSet[T_i] s.t. writeReserves[w] owned by smaller TID that commits → abort T_i
* Else commit, materialize buffered writes into next snapshot

Aborted txns re-enqueued to next batch — **no cascading abort** because snapshot never includes uncommitted writes [3][10].

**Deterministic Reordering:** Sort transactions by dependency to minimize aborts.

Example:

* T1: R(a), W(b)
* T2: W(a)
* Original TID order T1<T2: RAW on a (T1 reads a that T2 wants to write) → T1 aborts if T2 commits
* Reordered T2<T1: T1 reads snapshot before T2 write, no conflict → both commit

Aria's reordering algorithm uses write-set clustering and graph cycle elimination within O(B log B) per batch [3].

### 4.4 Recovery, Checkpointing, and Dependent Transactions

*Nondeterministic failures* cannot affect commit status [7]. Widely used ARIES aborts in-flight txns on crash; deterministic DBs must recreate state at crash time and continue.

**Zig-Zag checkpointing:** Two alternating checkpoints CP_even, CP_odd. While CP_even written, transactions continue operating against shadow pages. No quiescence. Recovery replays log from last complete checkpoint.

**OLLP:** For interactive txns where read set not known, run reconnaissance read-only, predict writes, then sequence full txn using predicted sets. On misprediction, fallback to next batch.

**Replication cost table:**

| Config | Throughput (kTPS) | p99 (ms) | Replication overhead |
|--------|-------------------|----------|---------------------|
| Single-replica | 115 | 8.2 | — |
| 3-replica Paxos log | 112 | 9.1 | 2.6% |
| 5 geo-replicas (WAN) | 110 | 11.4 | async 0% on steady [1] |

## 5 Empirical / Proofs

### 5.1 Serializability Proof Sketch

*Lemma 1 (Calvin):* Under DLM, execution order respects log order for conflicting txns.
*Proof:* DLM grants per-key in log order; conflicting txns share key k ⇒ T₂ blocks on k until T₁ releases ⇒ serializes as T₁→T₂. ∎

*Lemma 2 (Aria):* Any txn committed by Aria has read from snapshot S = serial execution of all committed txns from prior epochs + committed preceding txns in reordered order.
*Proof:* By WAW/RAW checks, committed txn's read set untouched by earlier committed writes since snapshot taken after prior epoch. Reordering preserves acyclic WR edges. ∎

*Theorem 2 (Serializability):* Both Calvin and Aria produce serializable schedules equivalent to log order (Calvin) or reordered TID order (Aria).

### 5.2 Performance Decomposition

Data from Aria paper [3] and Calvin evaluation [1][9] on 8-node EC2 m5d.4xlarge, 1TB TPC-C:

* Aria: **~1.8 MTPS single-node YCSB**, 0.92 MTPS 8-node (scale 0.51/drop due to remote read fetch), vs Silo 0.6 MTPS, Calvin 0.55 MTPS 8-node
* Calvin 100% distributed TPC-C NewOrder: **~38k tps** with batch=500, vs 2PL+2PC **~9k tps** → 4.2× due to no 2PC lock hold across WAN [1]
* Reordering benefit: Aria -reorder 0.64 MTPS vs +reorder 0.92 MTPS on high-contention YCSB (θ=0.9) → **+43%** from reduced WAW aborts [3]
* Geo-replication latency: Spanner 2PC commit 12-80 ms cross-region; Calvin steady-state 0 ms added (async log ship) [7][8]

```python
def abort_rate(theta, system):
    if system=='calvin': return 0.0 # deadlock-free

    if system=='2pl': return 0.35 if theta>0.8 else 0.11
```

### 5.3 Fault Tolerance Validation

Crash injection on Calvin txn implementation [8]: kill -9 2/5 nodes mid-epoch, restart with log replay. State hash SHA256 over all keys matches surviving replica. No committed txn lost (Paxos durability). No aborted txn resurrected.

OneBarrier [9] shows 4.6 µs durable write inside barrier vs 3 ms after — similar to Calvin's input replication bypassing effect replication.

## 6 Limitations

* **Read/write set knowledge:** Calvin's pure model requires ahead-of-time sets; real ORM hides sets behind application logic. OLLP reconnaissance helps but adds RTT [1]. Aria relaxes but still requires static transaction procedure, not arbitrary ad-hoc SQL shell.
* **Nondeterminism wall:** `wall-clock, random, thread-race` must be virtualized in preprocessor. Debugging nondeterministic UDFs breaks determinism guarantee [7]. CACM survey emphasizes this as primary adoption barrier [7].
* **Straggler amplification:** Deterministic replay assumes homogeneous performance. Slow partition delays whole batch commit; Aria batch size tuning trades latency for throughput. Epoch 10 ms + batch sync adds tail latency under skew [3][5].
* **Hot-key contention:** DLM serializes hot keys in log order — no escrow, no commutative operation merging. DOCC [5] and escrow transactions proposal partially mitigate but increase abort rate.
* **Interactive sessions:** Multi-round txn with user think time cannot be batched efficiently; reconnaissance round trips add latency.
* **Disk-hosted workload memory wall:** Prefetch helps but checkpoint I/O contention at scale remains.

## 7 Conclusion

Deterministic concurrency control reframes scalability as *ordering* problem, not locking problem. Calvin's sequencing-shipping achieves near-linear scale, zero-coordination replication, and WAN-independence by agreeing on inputs, not outcomes [1][6][7]. Aria demonstrates that determinism does not require a-priori knowledge: speculative snapshot execution plus deterministic WAW/RAW validation and reordering yields up to 2× cluster throughput and eliminates Calvin's declarative burden [3][4].

At scale, the essentials are:

* **10 ms epoch + Paxos batch** → amortized order cost
* **Deterministic lock queue or snapshot reservation** → deadlock-free
* **Input-log replication** → free consistency levels, cheap geo-replication
* **Zig-zag / TLA+-checked recovery** → linearizable exactly-once histories [9]

Future work converges with fabric-level order: 1Pipe, RDMA sequencers, and smartNIC offload for deterministic ordering at µs scale, plus learned dependency reordering to further cut Aria aborts. The deterministic model is not universal, but for partitioned OLTP where serializability and high replica count matter, it remains the strongest challenger to 2PL+2PC.
