# In-Kernel Verification at Scale: The eBPF Verifier's Abstract Interpretation, Bounded Loop Support, and CO-RE Type Relocation

## Abstract

The Linux eBPF verifier is the most consequential deployed instance of abstract interpretation ever shipped: a soundness-critical static analysis, embedded in the kernel's trusted computing base, that must decide in milliseconds whether arbitrary untrusted bytecode may execute with kernel privileges. This thesis unifies the verifier's three load-bearing pillars—*abstract interpretation* over numeric domains, *bounded loop* termination analysis, and *CO-RE* type relocation—into a single formal account of in-kernel verification at scale. We formalize the verifier's value domains (u64/u32/s64/s32 intervals and tristate numbers) as Galois connections, characterize the convergence strategy (state pruning over a product lattice with a hard instruction budget) that bounds verification cost, analyze the transition from DAG-only programs to bounded loops and open-coded iterators, and derive the soundness contract of CO-RE relocation, which rewrites program semantics against target-kernel BTF *after* the compiler but *before* the verifier runs. We survey the mechanized literature now targeting the verifier itself—from CAV-2023 soundness proofs of range-analysis operators to SMT-based precision synthesis—and close with open problems: compositional soundness across helpers, verification under Spectre mitigations, and the completeness gap that rejects safe programs.

## 1 Introduction

No program analysis in production software carries stakes like the eBPF verifier. Every packet filter, tracing probe, congestion controller, and security monitor that runs inside the Linux kernel as eBPF bytecode must first pass through a static analyzer whose verdict is binary and final: *safe to execute* or *rejected*. A soundness bug in this analyzer is not a mere false positive—it is a kernel memory-safety vulnerability, exploitable from unprivileged contexts to achieve arbitrary code execution at ring zero. The verifier's analysis has indeed been the source of several high-profile CVEs [4], and its correctness is now recognized as an open, actively researched problem [3].

Yet the verifier is not a theorem prover in the conventional sense. It performs **abstract interpretation**: it symbolically executes the program over abstract domains that over-approximate the set of concrete machine states reachable at each instruction. The analysis is *path-sensitive* at branch points, *flow-sensitive* over a 512-byte stack and ten registers, and *interprocedural* across bpf-to-bpf calls—all under a hard budget of one million explored instructions. Soundness requires that every concrete execution is covered by the abstract exploration; precision requires that the abstraction not reject programs that are actually safe. These two demands are in permanent tension, and the history of the verifier is the history of negotiating that tension: from the original DAG-only design to bounded loops (kernel 5.3), to function-by-function verification, callbacks, and open-coded iterators [6, 7].

This thesis advances three claims. First, the verifier is best understood as an abstract interpreter over a **product lattice** of type, liveness, value, and privilege domains, and its design decisions—state pruning, instruction budgets, tnum arithmetic—are exactly the classical abstract-interpretation trade-offs (widening, termination, precision) adapted to a hostile adversarial setting. Second, bounded-loop support is a case study in *termination via abstract convergence*: the verifier proves loop termination not by finding ranking functions but by bounding iteration counts with tracked scalar ranges and by pruning loop states under a subsumption relation. Third, CO-RE (Compile Once, Run Everywhere) is not merely a portability convenience but a **verification-relevant transformation**: it rewrites the program's memory-access semantics against the target kernel's type information before verification, and its soundness contract must hold *end-to-end* from relocation records to JITed machine code.

## 2 Background

### 2.1 From packet filters to a general in-kernel VM

Classic BPF (1993) was a minimal packet-filtering VM. Extended BPF (merged in kernel 3.18, 2014) generalized it into a register-based 64-bit VM with ten registers (R0–R9 plus frame pointer R10), a 512-byte stack, maps for persistent state, and a family of kernel helper functions. Programs attach to *hooks*—kprobes, tracepoints, XDP, TC, LSM, socket filters—where they execute at kernel privilege. Because untrusted or semi-trusted code runs with kernel privileges, verification precedes JIT compilation, and JITed code is then indistinguishable from native kernel code [7].

### 2.2 The verifier's safety properties

The verifier enforces, for each program type, a set of invariants that the Linux Foundation's security audit enumerates in detail [4]:

- **Termination**: programs always run to completion; no unbounded loops or blocking operations.
- **Memory safety**: every load/store is bounds-checked against known object sizes; no out-of-bounds or uninitialized reads.
- **Type safety**: registers carry abstract types (scalar, pointer-to-context, pointer-to-map-value, pointer-to-stack, …); dereference and arithmetic are gated on type.
- **Information-flow control**: unprivileged programs must not leak kernel pointers or uninitialized data to userspace.
- **Bounded complexity**: verification itself must terminate within the configured complexity limit.

The verifier is explicitly a *safety* tool, not a *security* tool: it guarantees the program cannot crash or corrupt the kernel, but it does not inspect what the program computes [4].

### 2.3 The verification pipeline

Verification proceeds in phases: (1) CFG validation—reject unreachable instructions, enforce a single exit, bound back-edges; (2) state exploration—a depth-first abstract interpretation that simulates every feasible path while tracking abstract register/stack state; (3) per-instruction safety checks—bounds, types, helper argument constraints; (4) instruction rewriting and JIT. ### 2.4 Classical abstract interpretation in brief

Abstract interpretation (Cousot & Cousot, 1977) computes program properties by executing over an *abstract domain* \(A\) related to the concrete domain \(C\) by a Galois connection \(C \galois{\alpha}{\gamma} A\). An abstract operator \(f^\sharp\) is *sound* when \(f(\gamma(a)) \subseteq \gamma(f^\sharp(a))\) for all \(a \in A\): the abstraction over-approximates. *Precision* measures how little it over-approximates. The verifier's novelty is deploying this machinery inside an OS kernel, against adversaries, with a hard time budget—constraints that force unusual domain choices.

## 3 Methodology

This thesis is an analytic survey grounded in three methods. **(i) Source-level archaeology.** We trace the verifier's design through the kernel's `kernel/bpf/verifier.c` evolution and the kernel's BPF design documentation [7], identifying the invariant each mechanism exists to enforce. **(ii) Formal reconstruction.** We cast the verifier's numeric domains as abstract interpretations with explicit abstraction and concretization functions, drawing on the CAV-2023 mechanization of its range analysis [1] and the SAS-2025 precision study [2], to state soundness theorems in standard form. **(iii) Transformation analysis.** We model CO-RE relocation as a semantics-preserving program transformation parameterized by target-kernel BTF, and state the end-to-end contract that verifier, loader, and JIT must jointly satisfy. Throughout, we distinguish *what the verifier proves* (per-program, per-load safety) from *what remains unproven* (the soundness of the verifier's own implementation).

## 4 Deep Dive

### 4.1 The value domains: intervals and tristate numbers

The heart of the verifier is its tracking of *scalar values*. As documented in the kernel source and formalized by Agni et al. [1], the verifier maintains five numeric abstract domains per scalar register and stack slot:

| Domain | Concrete set | Abstraction |
|---|---|---|
| `u64` interval | \([0, 2^{64})\) | \([lo, hi]\) unsigned |
| `u32` interval | \([0, 2^{32})\) | \([lo, hi]\) unsigned |
| `s64` interval | \([-2^{63}, 2^{63})\) | \([lo, hi]\) signed |
| `s32` interval | \([-2^{31}, 2^{31})\) | \([lo, hi]\) signed |
| `tnum` | bitvectors of width \(w\) | `(value, mask)` tristate |

The four interval domains are the standard interval abstraction duplicated across signedness and width—a pragmatic duplication, because bounds checks and pointer arithmetic in eBPF mix 32- and 64-bit, signed and unsigned operations, and a single domain would lose the precision the verifier needs to accept real programs. The fifth domain, **tristate numbers (tnum)**, is the verifier's signature innovation: each bit of a value is *known-0*, *known-1*, or *unknown*, represented compactly as a `(value, mask)` pair where `mask` marks the unknown bits [1, 2]. Figure 2 illustrates the domain structure.

![Diagram 1](/thesis/ths_1788733800000_7f3a-1.webp)
*Figure 2: The verifier's five numeric abstract domains—four interval domains across width/signedness and the tristate-number (tnum) bitmask domain with abstraction/concretization maps.*

Why both intervals and tnums? They are *complementary*: intervals excel at arithmetic bounds (e.g., proving `i < len` implies `ptr + i` is in-bounds), while tnums excel at bitwise operations (masks, shifts, alignment) where interval arithmetic degenerates. The verifier keeps them in a **reduced product**: each domain's information refines the other through reduction operators \(\rho\), which must themselves be proved sound—a subtlety the CAV-2023 work makes explicit [1]:

> **Theorem (Sound reduction, after [1]):** Let \(\mathbb{A}_1, \mathbb{A}_2\) be abstract domains with concretization \(\gamma_{\mathbb{P}}\) into the product domain \(\mathbb{P}\). A reduction operator \(\rho_2 : \mathbb{A}_1 \times \mathbb{A}_2 \to \mathbb{A}_2\) is sound iff \(\gamma_{\mathbb{P}}(a_1, \rho_2(a_1, a_2)) = \gamma_{\mathbb{P}}(a_1, a_2)\) and \(\rho_2(a_1, a_2) \sqsubseteq_{\mathbb{A}_2} a_2\).

Abstract operators must also be *sound* and ideally *optimal* (the most precise sound operator). The kernel historically lacked formal specifications of these operators, and this gap produced real CVEs—several verifier exploits trace to unsound range arithmetic. Agni et al. provided the first formal specification with soundness and optimality proofs for the interval and tnum operators, and their work was partially adopted upstream [1, 3]. Shachnai et al. went further, building an SMT-based differential-synthesis framework that compares operator precision and *synthesizes concrete witness programs* demonstrating observable precision differences in real verifier runs—work that yielded an upstreamed, strictly more precise multiplication operator `bpf_mul` [2].

```c
/* tnum abstraction: value holds known bits, mask marks unknown bits.
 * concretization: gamma(v,m) = { x | (x & ~m) == (v & ~m) } */
struct tnum { u64 value; u64 mask; };

/* Example: after `r1 &= 0x3f`, the verifier knows the low 6 bits
 * are bounded even if their exact values are unknown: */
struct tnum t = { .value = 0, .mask = 0x3f };
/* gamma(t) = {0, 1, ..., 63}: provably in-bounds for a 64-byte region */
```

### 4.2 Bounded loops: termination by abstract convergence

The original verifier admitted only DAG control flow: any back-edge was rejected, forcing programmers to fully unroll loops. Kernel 5.3 introduced **bounded loop** support, fundamentally changing the verification problem from *acyclic path enumeration* to *fixpoint-adjacent convergence* [6].

The verifier's loop strategy has three components:

1. **Iteration bounding via tracked ranges.** The verifier simulates loop iterations abstractly. For a canonical counter loop, the induction variable's interval domain narrows the possible iteration count; the verifier requires that the loop provably terminates within the explored budget. If the bound cannot be established from the abstract state, the program is rejected—*even if it is actually safe*. This is the completeness price of soundness.

2. **State pruning at back-edges.** When the verifier revisits an instruction with a previously seen abstract state, it compares the current state against saved states under a *subsumption* relation: if the current state is subsumed by (i.e., no more precise than) a previously explored state whose exploration completed safely, the path is pruned. This is the verifier's analogue of widening—an over-approximation that guarantees the *verifier itself* terminates. The one-million-instruction budget is the ultimate backstop [7].

3. **Structured iteration constructs.** Recognizing that raw back-edge analysis is fragile—"there are simply too many possible states and iterations to work through" for realistic loops [6]—the kernel added the `bpf_loop()` helper (kernel 5.3), which moves loop mechanics into trusted kernel code: the helper invokes a callback a bounded number of times, so termination is immediate by construction and the verifier need only check the callback body. More recently, **open-coded iterators** (`bpf_for_each_map_elem`, `bpf_iter_*` patterns) let the compiler emit loop idioms the verifier recognizes structurally, recovering the high-level loop semantics that bytecode erases [6].

Formally, the verifier establishes termination by a *bounded model* argument rather than a ranking-function argument:

> **Theorem (Bounded-loop acceptance, informal):** A loop is accepted only if the abstract interpreter explores every abstract state reachable at the loop head, each exploration strictly decreases a well-founded measure (remaining instruction budget), and every back-edge target state is subsumed by an already-verified state. Hence accepted loops terminate in the concrete semantics.

Note the asymmetry: the *verifier's* termination is guaranteed by the budget and subsumption (a widening-like over-approximation); the *program's* termination is guaranteed because every concrete iteration sequence is covered by an explored abstract path that demonstrably exits. Conflating these two termination arguments is a classic source of unsoundness in the literature, and the kernel's design keeps them deliberately separate.

### 4.3 CO-RE: type relocation as a verification-relevant transformation

eBPF programs read kernel data structures—`struct task_struct`, `struct sock_common`, `struct pt_regs`—whose field layouts change across kernel versions. Hard-coding offsets breaks portability; recompiling per target (the BCC model) breaks the "compile once" distribution story. **CO-RE (Compile Once, Run Everywhere)** resolves this with BTF (BPF Type Format) and load-time relocation [3].

The mechanism, in brief:

1. **Compile time.** Clang emits relocation *records* in the BPF ELF object for every kernel-struct field access, capturing the *accessor chain* (e.g., `task->real_parent->tgid`) as type-level metadata rather than a numeric offset. Macros like `BPF_CORE_READ(src, field)` generate these records.
2. **Load time.** libbpf reads the *target* kernel's BTF (from `/sys/kernel/btf/vmlinux`), resolves each recorded accessor against the actual type layout, and **patches the bytecode** with the correct offsets, enum values, or field-existence guards (`bpf_core_field_exists`).

Figure 4 shows the pipeline. The verification-relevant point is *ordering*: relocation happens **before** the verifier runs, so the verifier checks the *relocated* program against the *actual* target kernel layout. This is what makes CO-RE sound rather than merely convenient—the verifier's memory-safety proofs (offset \(+\) size \(\leq\) object size) are discharged against ground-truth type information.

![Diagram 3](/thesis/ths_1788733800000_7f3a-3.webp)
*Figure 4: CO-RE relocation pipeline—compile-time relocation records and BTF metadata, load-time resolution against the target kernel's BTF, bytecode patching before verification.*

The end-to-end soundness contract can be stated as follows:

> **Theorem (CO-RE relocation soundness, informal):** Let \(P\) be a CO-RE program with relocation records \(R\), and let \(B\) be the target kernel's BTF. If libbpf's relocation function \(\mathit{relocate}(P, R, B) = P'\) succeeds, then for every field access in \(P'\) the patched offset equals the true offset of that field in \(B\) (or the access is guarded by a field-existence check that provably fails closed). Hence any memory-safety property the verifier proves of \(P'\) holds of the executed program.

The failure modes are instructive: a *stale or absent* BTF (kernels before 5.4, or `CONFIG_DEBUG_INFO_BTF` disabled) degrades relocation to best-effort; a *type renamed or restructured* beyond the accessor chain's expressiveness fails closed at load time. CO-RE thus converts a silent-corruption hazard (wrong offsets, right-looking code) into either correct relocation or loud load failure—a textbook fail-closed design.

### 4.4 In-kernel observability engineering

The verifier exists to *enable* observability, not merely to constrain it. The modern eBPF observability stack—tracing (kprobes, tracepoints, fentry), networking (XDP, TC), and security (LSM)—is a co-design of verifier capabilities and program expressiveness:

- **Helper-function contracts.** Each of the 200+ helpers carries a verifier-enforced contract: argument types, return-value nullability, and effects (e.g., `bpf_probe_read_kernel` may read arbitrary kernel memory but only into program memory, and only for privileged program types). The verifier checks *calls*, not helper implementations—an explicit trust boundary and a known soundness gap [4].
- **Ring buffers and maps.** State export to userspace goes through maps and ring buffers whose accessors the verifier bounds-checks. The verifier's *information-flow* rules (no leaking kernel pointers or uninitialized stack to unprivileged contexts) make observability tools safe-by-construction for multi-tenant use.
- **Precision as a feature.** Every false rejection is a lost observability capability. The upstreamed `bpf_mul` precision improvement [2] is not academic polish—it directly expands the set of acceptable tracing programs. The verifier's precision budget is, in economic terms, the platform's expressiveness budget.

## 5 Empirical Evaluation and Proofs

We now consolidate what has been *proven* about the verifier, as opposed to what is merely believed:

1. **Range-analysis soundness (mechanized).** Agni et al. [1] formalized the kernel's interval and tnum domains, their abstract operators, and the cross-domain reduction operators, with machine-checked soundness and optimality proofs (CAV 2023). A portion of this work—corrected abstract operators—was adopted into the upstream kernel, a rare instance of verification research directly patching the artifact it studies [3].
2. **Precision, differentially.** Shachnai et al. [2] built an SMT-based framework that (a) formally compares the precision of competing abstract operators over all valid abstract inputs, and (b) synthesizes *concrete witness programs* exhibiting observable precision differences in actual verifier executions. This closed the loop between theory (operator \(\sqsubseteq\) relations) and practice (programs the kernel accepts or rejects), and their more precise multiplication operator shipped upstream.
3. **JIT correctness (solver-aided).** Nelson et al.'s Jitterbug (OSDI 2020) verified eBPF JIT compilers via Rosette/Serval, finding 16 bugs in kernel JITs [3]. While this targets the JIT rather than the verifier, it secures the pipeline *downstream* of verification: a sound verifier feeding an unsound JIT is still exploitable.
4. **Functional verification of eBPF code (automated).** Bromberger et al. [5] translate eBPF bytecode to Constrained Horn Clauses over bitvectors and arrays, discharging functional properties with Z3 and proving the translation procedure terminates—showing that full-fledged automatic verification of real eBPF programs is feasible.
5. **Audit evidence.** The Linux Foundation's verifier security audit [4] systematized the verifier's invariants, its trust boundaries (helpers, BTF, Spectre mitigations), and its historical vulnerability classes, providing the empirical base rate against which formal claims must be judged.

What remains *unproven* is the headline claim: **there is no comprehensive formal soundness proof of the verifier as a whole** [3]. The verified fragments—range analysis, JITs, path pruning conditions—are genuine progress, but composition across fragments (abstract domains \(\times\) state pruning \(\times\) helper contracts \(\times\) Spectre mitigations) is unverified, and the verifier changes substantially every release, eroding proofs faster than they accumulate.

## 6 Limitations

An honest account must name the gaps:

- **The completeness gap.** The verifier rejects safe programs routinely: imprecise operators, unprovable loop bounds, and state-explosion pruning all cause false rejections. Programmers develop folklore workarounds (restructuring loops, adding redundant masks like `& 0x3f`), which is evidence of a verification tool shaping—and constraining—its ecosystem.
- **Helper trust boundary.** Helper functions are *trusted*, not verified. A helper whose implementation violates its verifier-visible contract silently voids the safety argument. The audit [4] flags this as a structural limitation, not a bug.
- **Spectre and speculative safety.** The verifier inserts speculation barriers (e.g., `nospec` annotations, branchless bounds enforcement) for unprivileged programs, but speculative-execution safety is a property of the *microarchitectural* semantics, outside the verifier's architectural abstract interpretation. This is an active research frontier.
- **Proof erosion.** At ~2,100 lines for range analysis alone in v5.19 [1] and rapid per-release churn [3], the verifier is a moving target. Proofs of the whole artifact face a maintenance burden the current research ecosystem has not solved.
- **Adversarial completeness.** The verifier assumes the *bytecode* is adversarial but the *toolchain* (compiler relocations, BTF, libbpf) is trusted. Supply-chain compromise of BTF or relocation records is outside the threat model.

## 7 Conclusion

The eBPF verifier is abstract interpretation under fire: soundness-critical, adversarially tested, budget-constrained, and load-bearing for the entire in-kernel observability economy. Its numeric domains—intervals duplicated across width and signedness, plus the tnum bitmask domain—are a masterclass in precision engineering; its bounded-loop support shows how termination can be established by abstract convergence plus hard budgets rather than ranking functions; and CO-RE demonstrates that portability mechanisms can be verification-relevant when ordered correctly in the pipeline. The emerging literature that verifies the *verifier itself*—mechanized range-analysis proofs, SMT-based precision synthesis, solver-aided JIT verification—marks the field's maturation from folklore to formalism. The central open problem remains compositional, maintained soundness of the whole artifact across releases. Until that is solved, every verifier patch is both a feature and a hypothesis.
