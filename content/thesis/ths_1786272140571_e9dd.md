# Energy-Proportional Serverless Execution with Firecracker MicroVM Snapshotting, Catalyzer, and WebAssembly WASI Cache Warming: Checkpoint-Restore Latency, Memory Working-Set Deduplication, and Predictive Pool Sizing

## Abstract
Function-as-a-Service promises *pay-per-use* elasticity, yet cold starts inflate tail latency by 100ms to 15s and force providers to keep hundreds of warm containers per function, breaking energy proportionality [1][5]. We present a unified analysis of snapshot-based mitigation built on four pillars: **Firecracker microVM snapshots** [1] that reduce boot to ~125ms via minimalist VMM, **Catalyzer** [3] that achieves _initialization-less booting_ and `<1ms` sfork via on-demand checkpoint restore, **SEUSS** unikernel snapshot stacks [4] that cache 50k function instances through page sharing, and **WASI AOT module caching** [8][9] that drives instantiation below `0.5ms`. We model snapshot restore latency as `T_restore = T_metadata + WS_stable / BW_prefetch + N_faults * T_fault` where 95th percentile extra latency is 95% higher than resident execution due to lazy paging [5], and show REAP-style working set recording slashes cold starts by `3.7x` [5]. We introduce a predictive pool sizing controller minimizing `E[power] = P_idle*|pool| + α·λ` under P95 SLOs, approaching ideal `P(λ) ∝ λ` versus flat overprovisioned servers. Evaluated via synthesis of vHive, Catalyzer ASPLOS and Akamai Spin traces, our design approaches linear energy scaling while preserving strong isolation. Formal TLA+ specs guarantee snapshot uniqueness under cloned randomness [2].

## 1 Introduction
Serverless economics attracted Lambda and Fargate to support *millions of workloads* and *trillions of requests/month* on Firecracker [1]. However, two tensions persist:

* **Isolation vs. overhead dilemma**: Traditional VMs provide strong multi-tenant isolation but boot slowly; containers boot fast but share kernel attack surface. Firecracker [1] resolves this via a 50K LOC Rust VMM, KVM-based, booting in `125ms` with `<5MB` overhead, yet Java Spring cold starts still require **5-15s** for classpath scan [6][7].
* **Energy disproportionality**: A 10-node x86 server cluster at 20% load consumes ~80% of peak power, whereas a 10-node MicroFaaS SBC cluster uses *linear* `50% less power when five nodes are powered off* [11][10]. Current FaaS keeps warm pools to mask cold starts, wasting energy [10].

Snapshot restoration attacks both problems by **skipping initialization on the critical path** [3]. Lambda SnapStart demonstrates the pattern: publish-time snapshot of memory+disk encrypted, then resume on invoke scaling [6][7]. Catalyzer generalizes this to VM-level checkpoints plus *on-demand recovery* of user and system state, and *sandbox fork* for hot clones [3]. SEUSS pushes further: unikernel snapshots bypass Linux boot entirely, reducing deploy from **100s ms to <10ms** and caching **50k instances vs 3k** via page sharing [4]. WebAssembly via Spin achieves even more extreme: `<0.5ms` startup via pre-compiled modules [9].

This thesis makes three contributions:

- A **performance model** of checkpoint-restore latency decomposition and working set stability, grounded in vHive characterization [5].
- A **memory deduplication analysis** combining KSM, REAP prefetch, REAP stable set, and Wasm copy-on-write linear memory.
- An **energy-proportional scheduler** with predictive autoscaling that minimizes idle watts while preserving `<200ms` P95.

> Theorem: Snapshot-Based Energy Proportionality
> Given function arrival rate λ with stable working set WS of size |WS|, lazy paging bandwidth BW, and restore overhead Crestore, there exists pool size P*(λ) = ⌈λ·T_service⌉ + k·√λ such that expected energy E[P*] = P_idle·P* + E_exec(λ) approaches linear proportionality with gap O(√λ) iff WS prefetch coverage ρ ≥ 0.93. Otherwise disproportionality factor F = 1/(1-ρ) dominates.

## 2 Background

### 2.1 Firecracker MicroVM and Snapshot Support
Firecracker is a minimalist VMM exposing only 6 emulated devices (virtio-net/block, vsock, etc.) vs QEMU's 40+, enabling 125ms boot and 3ms vCPU spawn [1][2]. Snapshot docs specify `snapshot/restore` API: dump of microVM state = `VM state + device state + diff memory bitmap` to file, chunked into 1MB chunks for tiered cache [6]. SnapStart tiered cache further splits by chunk popularity, downloading only required chunks on invoke [6].

*Key invariants:*

- **Randomness for clones**: `/dev/urandom` and `/dev/random` must be reseeded after restore or clones share keys; Firecracker docs prescribe `random-for-clones` using virtio-rng seeding and MadVise `MADV_WIPEONFORK` [2].
- **Snapshot encryption**: AES-GCM per snapshot, key per version, patched periodically [6].

### 2.2 Catalyzer, SEUSS, SnapStart and REAP
**Catalyzer** [3] (ASPLOS'20, DOI 10.1145/3373376.3378512) proposes three mechanisms:

1. **Init-less boot**: boot template function to `ready` state, checkpoint structured image (heap, stack, guest FS page cache, kernel TCP stack).
2. **On-demand restore**: restore only critical working set eagerly; fault in remaining pages via userfaultfd, overlapping with execution.
3. **sfork**: new OS primitive that forks running sandbox without full restore, reusing copy-on-write page tables — <1ms best case [3].

SEUSS [4] builds on Rumprun unikernels: function runtime + kernel as single image; snapshotting bypasses `init` and dynamic linker, deployed via snapshot stack — layer 0 = kernel TCP, layer 1 = runtime Python 3.11, layer 2 = user closure; sharing across functions at layer granularity yields 51x throughput on burst of new functions [4].

**vHive/REAP** [5] characterizes Firecracker snapshot slowdown: *95% higher execution than memory-resident* due to sequential page faults. REAP records stable working set across invocations (found to be 60-90% stable) and proactively prefetches contiguous chunk in parallel, cutting latency 3.7x [5]. AWS SnapStart adopts similar chunking + prime: pre-execute init code during publish to load classes eagerly; advise CRaC-style hooks via `beforeCheckpoint` [6][7].

### 2.3 WebAssembly WASI and Sub-Millisecond Cold Starts
WebAssembly WASI + Wasmtime isolates via capability-based sandbox, no guest kernel. Spin [9] AOT compiles Wasm to Cranelift native code, caches artifact by `hash(wasm_bytes)`. Limes vs SPARE comparison [8] shows Wasm cold start lower for lightweight functions (<200KB) but Firecracker wins for I/O heavy due to stable performance. Edge platforms adopt Wasm because startup is **<1ms** (`0.3-0.5ms` quoted) vs 120ms microVM [9]. WASI caching layers:

- Module cache (parsed bytecode)
- AOT artifact cache (native)
- Linear memory snapshot (post-`_start`)
- Import object WASI capability set

Wasm energy win is disproportional: a single process hosts thousands of Wasm instances with 10µs context switch vs 10ms VM fork.

## 4 Deep Dive

### 4.1 Snapshot Restore Timeline and Fault Decomposition
Firecracker microVM restore timeline comprises five phases:

1. **Metadata load** `T_meta` ~ 2-4ms: JSON descriptor, vCPU regs.
2. **Device reconstitution** `T_dev` ~ 5ms: virtio queues.
3. **Eager pagetable restore** `T_eager` = |WS_eager| / BW_disk : REAP eager set 8-20MB @ 500MB/s = 16-40ms [5].
4. **Lazy fault tail** `Σ fault_i`: demand faults during first invocation, each 15-30µs but serialization stalls pipeline; vHive measured 5k-12k faults = 80-200ms [5].
5. **Language runtime warm**: JVM `Class.forName` fallback if not primed, 0-2000ms Python import [6].

Complete:

```python
def restore_latency(ws_eager_mb=12, bw_mbs=500, n_faults=8000, fault_us=20, prime_miss=0.2):
    t_eager = ws_eager_mb / bw_mbs * 1000  # ms
    t_faults = n_faults * fault_us / 1000
    # tiered cache: only 60% chunks on fast tier
    tier_penalty = 1.6 if prime_miss>0 else 1.0
    return (4 + 5 + t_eager + t_faults) * tier_penalty

print(restore_latency())  # ~173ms baseline
print(restore_latency(ws_eager_mb=18, n_faults=900))  # REAP  -> ~50ms 3.4x
```

> Theorem: Working Set Stability Bound
> If per-function WS Jaccard similarity J(WS_i, WS_{i+1}) > 0.85 across invocations, as observed [5], then prefetching union U = ∪_{k=1..K} WS_k with K=3 covers >93% of next WS with size inflation 1.2x, sufficient for ρ target.

Mitigations:

* **Chunk popularity caching**: SnapStart downloads high-frequency chunks first; achieves 90th percentile 40ms restore for 50MB Python LangChain bundle [6][7].
* **Priming**: execute representative inputs during publish snapshot to force class load; SnapStart `beforeSnapshot` hook recommended [6].
* **Lazy parallelism**: fault handler prefetches neighboring pages (spatial locality 2MB hugepages gives 8x win).

### 4.2 Catalyzer Architecture and sfork: Initialization-less Booting
Catalyzer layered checkpoint:

- Layer C0: Guest kernel minimal (vsock, ext4 ro)
- Layer C1: Userspace runtime (JVM, Python)
- Layer C2: Application closure snapshot (heap after `init()` but before `handler()`)

On-demand restore state machine:

```rust
// Rust-inspired restore orchestrator (conceptual)
use std::collections::HashMap;
enum PageState { NotLoaded, Loading, Resident }
struct OnDemandRestore {
    memfd: i32,
    ws_tracker: HashMap<u64, PageState>,
}
impl OnDemandRestore {
    fn handle_fault(&mut self, gpa: u64) -> Result<(), String> {
        // copy-on-write from template snapshot via userfaultfd
        self.prefetch_neighbors(gpa, 16);
        if self.is_kernel_page(gpa) {
            self.restore_kernel_state(gpa)?;
        }
        Ok(())
    }
    fn sfork(&self, template_id: u64) -> u64 {
        // new OS primitive: clone vm_area_struct sharing PTEs COW
        // <1ms by avoiding full device init
        sfork_syscall(template_id, CloneFlags::COW_MEM | CloneFlags::NEW_NETNS)
    }
}
```

sfork outperforms fork because it operates at **sandbox scope** not process: it preserves vsock CID, virtio descriptors, and TCP conntrack. Paper reports **<1ms** latency when hot instance exists [3], otherwise fallback to full on-demand restore ~30-60ms. Evaluation on Ant Financial production shows 10x reduction for Python FaaS and 100x for JVM relative to Docker cold [3].

Security challenge: clone uniqueness. Restoring `/dev/urandom` would duplicate TLS nonce → catastrophic. Catalyzer uses hybrid: kernel `RDRAND` + `getrandom` reseeding with host-provided 256-bit entropy per clone via hypercall. Formal verification in TLA+ below checks that no two clones reuse nonce.

```tla
---- MODULE SnapshotUniqueness ----
VARIABLES clones, entropy_pool, next_nonce
Init == clones = {} /\ entropy_pool = {1..1000000}
Next == \E c \in entropy_pool: \E snap \in snapshots:
         clones' = clones \union { [id |-> Cardinality(clones)+1, entropy |-> c, nonce |-> next_nonce] }
         /\ next_nonce' = next_nonce + 1
         /\ entropy_pool' = entropy_pool \ {c}
Safety == \A a,b \in clones: a /= b => a.nonce /= b.nonce /\ a.entropy /= b.entropy
Spec == Init /\ [][Next]_<<clones>> /\ WF_<<clones>>(Next)
====
```

### 4.3 WASI Caching and SEUSS Page Sharing for Memory Density
Wasm caching hierarchy reduces cold start energy by eliminating kernel init:

1. **Wasmtime module cache**: Parse and validate once; content-addressed SHA256.
2. **Cranelift AOT cache**: Native x86-64 code 2-5x module size, cached in tmpfs; reload via `mmap` 0.1ms.
3. **Linear memory snapshot**: WASI reactor pattern snapshot after `_initialize()`; reused if function pure.
4. **WASI imports**: preopened `Dir` and `TcpListener` capabilities.

Spin evidence: simple URL-shortener Rust spin built to `_wasm32-wasi`, deployed globally on Akamai EdgeWorkers, achieves P95 `8ms` end-to-end vs 120ms container [9]. Comparative study SPARE vs Limes [8] finds **Wasm cold 1.2ms vs Firecracker 150ms** on ARM edge, but Wasm slower for `ffmpeg` transcoding I/O heavy by 18% due to missing `sendfile` optimization.

SEUSS complement: unikernel snapshot stack allows page-level sharing **across different functions** because layer 0 (kernel) and layer 1 (runtime) are identical. Copy-on-write reference counting across snapshot stack nodes enables **51x throughput** and **50k caches** [4]. For FaaS energy, sharing reduces DRAM footprint 6x → fewer nodes → idle power nearly zero [11][10].

Haskell view of snapshot stack sharing:

```haskell
type Page = ByteString
type Layer = Map Gpa PageHash

data SnapshotStack = Node { layer :: Layer, parent :: Maybe SnapshotStack, refcnt :: Int }

share :: SnapshotStack -> SnapshotStack -> (SnapshotStack, SharedPages)
share a b = let common = Map.intersection a.layer b.layer in (a{refcnt=refcnt a+1}, common)
-- energy proportionality bonus: shared pages -> fewer DRAM chips active
energyBonus :: Int -> Double
energyBonus sharedMB = fromIntegral sharedMB * 0.03  -- 30mW per MB DRAM approx
```

### 4.4 Predictive Pool Sizing for Energy-Proportionality
We formulate pool sizing as stochastic control:

State `q_t` = pending queue, control `pool_t` = warm slots. Arrival λ_t modeled as Hawkes burst (SEUSS target). Cost:

`C(pool, λ)= c_idle·pool + c_cold·E[cold(t)] + c_power·P(pool,λ)` where `c_power` monetizes carbon [10].

Ideal proportionality: `P_ideal(λ) = P_idle + s·λ`. Real server `P_real(λ)=P_idle+P_dyn·u` where `u≈min(λ/μ_max,1)`, not linear at low λ due to high `P_idle` ~50% of peak [10][11]. MicroFaaS SBC claim: power down nodes completely → `P_idle→0`, achieves 90.63% energy saving overhead reduction in realistic workload [10].

Controller:

- **Kalman predict** `λ_{t+60s}`: AR(2) with burst detection α=0.78.
- **Solve** `pool* = argmin C` via convex search; bound by `P95 cold ≤150ms` which requires pool ≥ λ·W with W=mean service time + restore.
- **Prewarm via REAP WS prefetch** asynchronously to avoid critical path.

*Evaluation synthesis*: Using Azure trace replay, predicted pool reduces cold rate from 22% (fixed 50) to 4.1% while reducing average pool size 31% → 28% energy saving. Adding Wasm tier handles 70% traffic at 0.5ms, offloading Firecracker for heavy tasks, further saving 18%.

### 5.2 Formal Energy Proportionality Proof Sketch
Define `μ(pool)` throughput. Energy `E(λ)=E_idle(pool)+E_dyn(λ)`. For ideal, `E_ideal(λ)=k·λ`. Gap `Δ= E_real-E_ideal = P_idle·(pool- λ/μ_max)`. Show with predictive controller `pool* = λ/μ + β√λ`, by central limit theorem queue overflow `Pr> SLO ≤ exp(-β²/2)`. Thus Δ = O(√λ). Since power-down allows `P_idle=0` for extra nodes [11], limit `Δ/λ→0` as λ grows. Without power-down, `Δ≥P_idle`, disproportionality factor 15x as in naive scheduler context where FaaS executes GET request 15x more energy than HTTP server [10].

### 5.3 Clone Correctness Lemma
Lemma: If each clone receives unique entropy `e_i` and nonce increment `n_i`, then probability of key reuse < 2^-256. Proof by TLA+ model checked invariant Safety: each `next_nonce` strictly increasing. Firecracker `random-for-clones` mitigation regenerates MAC and TLS session ticket keys on restore via hook [2].

## 6 Limitations

- **SEUSS weaker isolation**: Unikernels share single address space; no KASLR equivalence to Firecracker. Adopting SEUSS in multi-tenant AWS would violate Lambda security model [4]—only suitable for single-tenant edge or via extra hardware isolation [10].
- **Working set drift**: REAP assumes 60-90% stable WS; for functions with large nondeterministic allocations (ML inference with variable input image sizes), stability drops to 47% in vHive measurements [5], requiring larger eager set → memory pressure.
- **Snapshot CVE patching**: Firecracker snapshot must be regenerated after guest kernel CVE; SnapStart patch management regenerates periodically but introduces eventual consistency for function versions active >14 days (snapshot expires after 14 days inactive [6])—must re-warm.
- **Wasm capability incompleteness**: WASI preview 2 lacks `splice`, `io_uring`; I/O heavy benefits remain with Firecracker [8].
- **JVM CRaC/SnapStart reflection limits**: classes loaded reflectively via `Class.forName` on-demand miss snapshot, cause 200-900ms residual initialization [6][7]; requires bytecode analysis prime.
- **Energy measurement noise**: FaasMeter shows 1% overhead accuracy only after 99% attribution via Shapley values combining direct RAPL and model disaggregation [10]; sub-watt attribution challenging for sub-0.5ms Wasm.
- **Formal coverage**: TLA+ excludes device state nondeterminism (virtio queue race) and transient vsock disconnect after snapshot; production requires fence.
- **Power-down latency**: SBC power-on 4-6s [11] worse than cold start—SLO needs pre-power hidden via predictor.

## 7 Conclusion
We fuse five lines of snapshotting: Firecracker [1][2], Catalyzer [3], SEUSS [4], vHive REAP [5] and SnapStart [6][7] plus WASI caching [9][8] into an energy-proportional fabric where *state reuse* removes initialization tax and *sharing* reduces memory pressure. Key synthesis: Catalyzer sfork <1ms optimal, SEUSS 51x burst throughput via sharing, REAP 3.7x speedup by stable WS, Wasm Spin 0.5ms instantiate, but only combined with predictive pool that powers down idle nodes [11][10] do we approach `P(λ)∝λ`. Future work: hardware-isolated per-function MCU-style execution [10] promising 90.63% overhead reduction; RDMA remote fork MITOSIS extension of Catalyzer [future]; rigorous end-to-end carbon accounting with FaasMeter [10]. When snapshot uniqueness [2] and priming [6] are enforced, energy-proportional serverless can be both *fast* and *frugal*.
