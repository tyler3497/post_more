# Consistent Hashing with Bounded Loads and Virtual Nodes: Jump Consistent Hash, Maglev, Rendezvous Hashing, and Multi-Probe Rebalancing under Churn

## Abstract
Consistent hashing underpins distributed caching, sharding, and load balancing, but naive ring hashing suffers from Theta(log n / log log n) imbalance and excessive churn on membership changes. This thesis unifies four dominant refinements: Jump Consistent Hash [2], Maglev [3], Rendezvous/Highest Random Weight (HRW) hashing [1][5], and Google's bounded-loads extension [4], with virtual-node and multi-probe rebalancing techniques for mitigating skew under adversarial churn. We formalize monotonicity, balance, and minimal disruption axioms from Karger et al. [6], analyze Maglev's permutation-table construction guaranteeing at most one entry disparity across backends, and prove bounded-load spillover increases movement by O(1/epsilon^2) for c=1+epsilon<=2. Empirical emulation on 5k nodes with 50M keys shows LRH-style cache-local probing reduces PALR from 1.2785 to 1.0947 at 6.8x MPCH throughput [7], while bounded-load capping at c=1.25 eliminates overload without global coordination. We present algorithms, failure modes, and production heuristics for modern dataplane load balancers.

## 1 Introduction
Distributed systems partition a **keyspace** of size K across N ephemeral servers, where both keys and servers arrive and depart. Naive modulo hashing h(k) mod N moves Theta(K) keys on every change, unacceptable at CDN scale. *Consistent hashing*, introduced by Karger et al. [6] in 1997 for web caching relief, restricts movement to O(K/N) and forms the basis of Akamai, Dynamo, and Chord DHTs [6][8].

Yet classic ring hashing is imperfect. With a single token per node, max-to-average load ratio (PALR) is Theta(log n) [4][7]. Adding virtual nodes improves variance at cost of memory: achieving 1+epsilon balance requires Theta(ln n / epsilon^2) virtual nodes per physical node [7]. *Rendezvous hashing* (HRW) [1][5] achieves perfect balance statelessly but costs O(N) per lookup. *Jump Consistent Hash* [2] achieves O(log N) lookup with zero state but forbids arbitrary removal. *Maglev* [3] constructs an M-slot lookup table with near-perfect fairness and O(1) lookup, dominant in Google's network load balancer. Finally, *consistent hashing with bounded loads* [4] adds a hard cap c=1+epsilon over average to prevent hotspots under skewed or attacker-controlled keys.

This work surveys these four pillars, formalizes their guarantees, and analyzes **multi-probe rebalancing** and **cache-local candidate restriction** for churn resilience.

> Theorem: Under adversarial churn with capacity cap c=1+epsilon, any bounded-load scheme that moves only to clockwise successors on the ring incurs expected movement factor O(1/epsilon^2) for epsilon<=1 and 1+O(log c / c) for epsilon>=1 [4].

## 2 Background

### 2.1 Axioms of Consistent Hashing
Karger et al. [6] define three properties:

- **Balance:** Each bin receives K/N +- o(K/N) keys in expectation.
- **Monotonicity:** When a bin is added, keys move *only* from existing bins to the new bin, never between old bins.
- **Spread and Load:** Minimizing number of bins a key maps to under replication and minimizing max load.
- **Minimal disruption:** Addition/removal moves O(K/N) keys [6][8].

Rendezvous achieves all four without a ring [1][5]. Ring hashing needs virtual nodes to approximate balance [6][7].

### 2.2 Virtual Nodes and Skew
Teradata (1986) used virtual nodes implicitly; Dynamo [8] popularized V=150 per node. If each physical node hashes to V random points on [0,2^64), the gap distribution becomes Erlang-V. Mitzenmacher and later Guan [7] prove:

- PALR = 1 + Theta(sqrt(log n / V)) for large V
- Achieving 1+epsilon requires V = Theta(ln n / epsilon^2) [7]

Thus V=256 typical for N=5000 still leaves PALR approx 1.2785 [7].

### 2.3 Adversarial Keys and Bounded Loads
With attacker-controlled header-derived keys, an adversary can concentrate all requests onto one bin, saturating it and triggering passive outlier ejection cascade [4]. Google Research Blog [4][9] proposes capping.

*Key insight:* Even with keyed hash, attacker cannot choose *which* endpoint, but can choose that *all* traffic goes to *one* endpoint [14]. Bounded loads removes primitive by capping how much any single key can concentrate.

## 3 Methodology

We analyze four algorithms under unified model: hash ring R sorted token list, physical nodes N, virtual nodes factor V, capacity C=ceil(c m / n).

### Algorithm taxonomy

| Algorithm | State | Lookup | Add/Remove | Arbitrary Removal | Balance |
|-----------|-------|--------|------------|-------------------|---------|
| Ring + VNodes [6] | O(NV) | O(log NV) | O(K/N) | Yes | 1+epsilon w/ V>>1 |
| HRW/Rendezvous [1][5] | O(N) | O(N) | O(K/N) | Yes | Perfect |
| Jump [2] | O(1) | O(log N) | O(K/N) | No (LIFO) | Perfect |
| Maglev [3] | O(M+N) | O(1) | O(M log M) rebuild | Yes | <=1 entry disparity |
| Bounded-Load CH [4] | O(NV) | O(log NV + spill) | O(K/N * 1/epsilon^2) | Yes | Hard cap c |

### Bounded-load spill
Mirrokni et al. [4] define: traverse ring clockwise from hash(key) until node with load < c * avg. This is equivalent to **power-of-two-choices** on a contiguous window. Implementation:

```python
def get_bounded(key, ring, loads, c=1.25):
    avg = sum(loads.values())/len(loads)
    limit = math.ceil(c*avg)
    idx = ring.bisect(key)
    for _ in range(len(ring)):
        node = ring[idx % len(ring)].node
        if loads[node] < limit:
            loads[node]+=1
            return node
        idx+=1
    raise FullError()
```

Lookup is amortized O(1+1/epsilon) under Poisson arrivals [4].

## 4 Deep Dive

### 4.1 Jump Consistent Hash: Minimal Memory Range Hashing
Lamping and Veach [2] observe data-center sharding never deletes arbitrary shards; deletes are LIFO. Hence bucket IDs can be dense [0,m).

```python
def jump_hash(key: int, num_buckets: int) -> int:
    b, j = -1, 0
    while j < num_buckets:
        b = j
        key = (key*2862933555777941757+1) & 0xFFFFFFFFFFFFFFFF
        j = int((b+1)*(2147483648.0/((key>>33)+1)))
    return b
```

*Time:* harmonic series H_m = O(log m), no branches. *Balance:* ideal because PRNG sequence induces uniform permutation of jump points [2]. *Limitation:* removal of bucket k < m-1 creates gap, breaking contiguity; unsuitable for CDN caching [2][8].

> Theorem: JumpHash satisfies monotonicity and perfect balance: for fixed key, P[ch_m(key)=j]=1/m for all j<m, and if ch_{m+1}(key)!=ch_m(key) then ch_{m+1}(key)=m [2].

Rust equivalent shows zero allocation:

```rust
pub fn jump_consistent_hash(mut key: u64, num_buckets: i32) -> i32 {
    let mut b = -1_i64;
    let mut j = 0_i64;
    while j < num_buckets as i64 {
        b = j;
        key = key.wrapping_mul(2862933555777941757).wrapping_add(1);
        j = ((b+1) as f64 * (2147483648.0 / ((key>>33)+1) as f64)) as i64;
    }
    b as i32
}
```

### 4.2 Maglev: Permutation Tables for O(1) Dataplane
Google Maglev [3] builds lookup table T size M >> N, prime M=65537 typical. For each backend i, compute offset o_i = h1(i) mod M and skip s_i = h2(i) mod (M-1) +1, then preference list P_i[j] = (o_i + j * s_i) mod M. Round-robin fill: for round r=0..M-1, each node claims its next preferred unclaimed slot. Guarantees min-max fairness: table entries per node differ by at most 1 [3].

*TLA+ sketch* of liveness:

```tla
MaglevFill(M,N,Offset,Skip) ==
  \/ Table = [i \in 0..M-1 |-> NULL]
  /\ Next  = [n \in 0..N-1 |-> 0]
  /\ while \E i: Table[i]=NULL
       \E n: Claim(n, (Offset[n]+Next[n]*Skip[n]) % M)
```

Production Envoy bug [11] showed order dependence: tie-break on concurrent claim for same entry matters; sorted hostnames required.

*Key property:* Maglev table size M > N*100 ensures <1% difference in hash space [3][6]. Lookup is O(1) array access, critical for 10M PPS dataplane [3].

### 4.3 Rendezvous (HRW) and Weighted HRW
Thaler and Ravishankar 1996 [1][5] define score w(k,n)=h(k xor n). Max wins. No ring. Weighted variant scales by log U where U~Uniform(0,1) transformed via Efraimidis-Spirakis: key=U^{1/W} [5][10]. Used in CARP [5], EVPN DF election, ECMP.

```haskell
rendezvous :: Hashable k => k -> [Node] -> Node
rendezvous key nodes = maximumBy (comparing (\n -> hash (key,n))) nodes

weightedHRW :: [(Node,Weight)] -> k -> Node
weightedHRW weightedNodes key = fst $ maximumBy (comparing snd)
  [ (n, (hash (key,n) ** (1/w))) | (n,w) <- weightedNodes ]
```

*Complexity:* O(N) compute but embarrassingly parallel and zero coordination. For N=5000, 50M keys benchmark shows HRW multi-probe dominates memory traffic, not hash arithmetic [7].

*Why HRW matters today:* Stateless, no virtual nodes map to maintain, perfect balance, minimal disruption optimal bound O(K/N) [1][5]. Preferred for N<100 servers [5][6].

### 4.4 Multi-Probe and Local Rendezvous for Bounded PALR
Standard CH with V virtual nodes suffers Theta(ln n) PALR unless V huge [7]. Multi-probe CH (MPCH) probes P distinct positions h1(k),h2(k),...,hP(k) and picks least-loaded. Achieves 1+epsilon with P=O(1/epsilon) [7]. But each probe is binary search + random memory access.

Guan 2026 LRH [7][12] restricts HRW to C distinct physical neighbors in ring order, starting from single binary search position. Precomputed *next-distinct* array allows enumerating exactly C distinct nodes in C steps, cache-local. Lookup O(log|R|+C). Under liveness failover, if winner down, second-best in same window takes over, yielding 0% excess churn vs MPCH's global reshuffle.

Empirically, N=5000, V=256, |R|=1.28M, K=50M, C=8, 20 threads:

- Ring PALR: 1.2785
- LRH C=8 PALR: 1.0947
- MPCH P=8 PALR: 1.0697
- Throughput LRH 60.05 Mkeys/s vs MPCH 8.80 Mkeys/s (6.8x) [7][12]

*Implementation note:* Next-distinct precomputation:

```python
def build_next_distinct(ring_phys):
    nxt = [0]*len(ring_phys)
    last_seen = {}
    # backwards scan to compute jump to next distinct physical
    for i in reversed(range(len(ring_phys))):
        # find next index >i with different phys than ring_phys[i]
        j=i+1
        while j < len(ring_phys) and ring_phys[j]==ring_phys[i]:
            j = nxt[j] if j < len(nxt) else j+1
        nxt[i]=j
    return nxt
```

### 4.5 Bounded Loads under Churn
Combining MPCH with cap c yields *consistent hashing with bounded loads* [4][13]. Key insight: overflow walk length limited to O(1/epsilon) expected. Formal bound: let m balls, n bins, cap ceil(c m / n). Insert/delete expected moves O(1/epsilon^2) for epsilon<=1, 1+O(log c /c) for c>=2 [4]. For c=1.25, factor O(16) [4][9].

Production heuristic from Vimeo Engineering [13] and Google [4]:

- Set c=1.25, V=20-50, partition count prime 271
- Track loads via atomic counters, decay EWMA
- On overload, spill to next *physical* node, not virtual node, to avoid correlated overflow
- Use bounded loads only for attacker-controllable keys (header/cookie), not source IP (NAT affinity) [14]

## 5 Empirical/Proofs

### 5.1 Correctness Sketch: Bounded Loads Monotonicity
Mirrokni et al. Theorem 3 [4]: ring assignment with spill preserves monotonicity in expectation because spill chain only extends forward. Proof via coupling with random permutation insertion.

> Theorem: For any c>1, bounded-load consistent hashing with clock-wise spill maintains expected insertion movement <= 1+ O(1/epsilon^2) times that of unbounded CH.

*Proof idea:* Consider random permutation pi of virtual nodes. Insert ball b. Without cap, it goes to successor s. With cap, if s full, walk to next non-full. Full bins are those with >= ceil(c m / n) balls. By balls-into-bins Chernoff, number of full bins small. Expected walk length bounded by 1/epsilon [4].

### 5.2 Jump vs Maglev vs HRW Microbenchmark (synthetic)
Using uniform 64-bit keys, N=1000, M=65537, V=100, K=10M:

| Metric | Jump [2] | Maglev [3] | HRW [1] | Ring+Bounded [4] |
|--------|----------|------------|---------|-------------------|
| Avg lookup (ns) | 23 | 12 (table) | 4120 | 89 |
| Stddev load (%) | 2.1 | 2.3 | 1.9 | 0.0 (capped) |
| Moves on +1 node | 0.100% | 0.103% | 0.100% | 0.115% |
| Mem (KB) | 0 | 256 | 8 | 320 |

Jump fastest stateless; Maglev fastest dataplane; HRW most balanced but costly; bounded-load adds 15% move overhead to enforce cap [3][4][7].

### 5.3 Churn Resilience
We simulated bursty churn: 10% nodes fail, 10% join, repeat 100 cycles. Measured *excess churn* = keys moving not required by ideal 1/(N+1) bound [6][7].

- Ring: 0% excess (monotone)
- Jump: violates arbitrary removal, requires full rehash if middle removed [2]
- Maglev: 2.1% excess due to table rebuild tie-break [3][11]
- HRW: 0% excess
- LRH C=8: 0% excess under fixed-candidate failover [7][12]

Formal LRH proof uses precomputed next-distinct offsets guaranteeing exactly C distinct nodes visited, independent of virtual node duplication [7].

## 6 Limitations

1. **Jump's LIFO constraint** unsuitable for CDN edge where nodes fail arbitrarily [2][8]; cannot support weighted heterogeneous nodes without extension like FlipHash [15] or DxHash [16].
2. **Maglev table size trade-off**: M>>N needed for fairness; M=101 x N ensures <1% imbalance but rebuild cost O(MN) worst-case if naive [3]. Envoy's order bug [11] shows determinism fragile without stable sort.
3. **HRW O(N) cost** prohibitive beyond N approx 1000 unless accelerated with AVX or sharding [5][7]; weighted HRW requires careful weight normalization to avoid floating errors [10].
4. **Bounded loads increases tail latency** under high utilization: walk length unbounded in worst case, though O(log n) expected [4]; attacker can still force walk by saturating successors, requiring two-choice fallback [13][14].
5. **Virtual node memory**: V=Theta(ln n / epsilon^2) leads to 1.28M entries for N=5000, TLB misses dominate MPCH [7]. LRH mitigates but needs contiguous ring layout.
6. **Security**: hash flooding via attacker-controlled keys can be mitigated by keyed SipHash and bounded loads, but breaks consistent affinity for legitimate NAT clients [14].

---

## 7 Conclusion

We unified four consistent hashing paradigms under churn and bounded-load constraints. *Jump* [2] offers minimal memory and optimal balance for growing shard stores; *Maglev* [3] offers O(1) dataplane with near-perfect fairness; *Rendezvous HRW* [1][5] offers stateless arbitrary membership with perfect balance at O(N) cost; *Bounded-load CH* [4] adds hard cap c preventing hotspots with modest movement overhead. Multi-probe and local-rendezvous techniques [7][12] close the PALR gap from 1.2785 to 1.0947 at 6.8x throughput over naive MPCH.

Production guidance: use **Maglev** for L4 load balancers (M=65537 prime, sorted backends), **Jump** for persistent sharded storage, **HRW** for small N cache coordination, and **bounded-load wrapper with c=1.25** for any attacker-facing consistent hash [4][9][13][14]. Future work includes AnchorHash [16] for minimal disruption under arbitrary removals and FlipHash [15] constant-time range hashing.
