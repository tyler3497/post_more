# The Hindley–Milner Type System: Let-Polymorphism, Principal Types, and the Damas–Milner Inference Algorithm

## Abstract

The Hindley–Milner (HM) type system is the most influential framework for automatic type reconstruction in functional programming, forming the static core of Standard ML, OCaml, Haskell, and Elm. First articulated by J. Roger Hindley [1] for combinatory logic and independently rediscovered by Robin Milner [2] as the typing discipline of ML, HM admits a complete inference algorithm — the Damas–Milner Algorithm W [3] — that recovers the *principal* (most general) type of every typable expression with no annotations at all. This thesis reconstructs HM from first principles: the declarative typing rules with prenex let-polymorphism, Robinson's unification algorithm and the most-general-unifier theorem [4], and the full Damas–Milner soundness and completeness argument. We then examine the value restriction that restores soundness in the presence of mutable state [5][6], constraint-based and bidirectional reformulations of the inference problem [7], and the extensions — higher-rank and impredicative polymorphism [8][9] — that lie beyond the decidability boundary HM so carefully preserves.

## 1 Introduction

In 1978, Robin Milner concluded his foundational paper on type polymorphism with a slogan that has echoed through programming-language research ever since: *"well-typed programs cannot go wrong"* [2]. The claim was not rhetorical flourish. It was a theorem — a semantic soundness result about a small language, ML, equipped with a type discipline that required programmers to write *no types at all*. A compile-time algorithm would discover them. Nearly fifty years later, that algorithm's descendants check billions of lines of Haskell, OCaml, Standard ML, Elm, and Rust-influenced code every day.

The Hindley–Milner system rests on three intellectual pillars, each a landmark in its own right:

1. **Hindley (1969)** proved that in combinatory logic, every typable object possesses a *principal type-scheme* — a single most-general typing from which all others follow by substitution — and gave the first algorithm to compute it [1].
2. **Milner (1978)** transplanted the idea into a programming language, presented the inference algorithm **W**, and proved it sound with respect to a denotational semantics [2].
3. **Damas and Milner (1982)** closed the loop: W is not merely sound but *complete* — it never rejects a typable program, and the type it returns is principal [3].

The system's engine is first-order unification, invented by J. Alan Robinson for automated theorem proving [4]: every subexpression contributes a type equation, and solving the equations yields the typing. Its signature innovation is **let-polymorphism**: universal quantification is permitted only in *prenex* position, introduced exactly once — at `let`-bindings — by *generalizing* over type variables not constrained by the environment.

Section 2 reviews the background; Section 3 presents the rules and Algorithm W; Section 4 dives into unification, let-polymorphism, the value restriction, and modern extensions; Section 5 gives derivations, proof sketches, and measurements; Section 6 maps the system's limitations; Section 7 concludes.

## 2 Background

### 2.1 The simply typed λ-calculus and its discontents

The simply typed λ-calculus assigns every function a single, fixed type. The identity function must be written once per type — `λx:Int.x`, `λx:Bool.x` — an intolerable duplication for a language aspiring to generic programming. *Curry-style* (extrinsic) typing assigns types to unannotated terms after the fact, while *Church-style* (intrinsic) typing requires annotations on binders:

| | Church-style | Curry-style |
|---|---|---|
| Annotations | Required on λ-binders | Absent; reconstructed |
| Example | `λ(x:α).x` | `λx.x` |
| Typing question | "Is this well-typed?" | "What is the principal type?" |
| Champion system | System F | Hindley–Milner |

HM is the canonical Curry-style system: programmers write no types, and inference reconstructs the best one.

### 2.2 Hindley's principal type-schemes

Hindley worked in combinatory logic, where types describe combinators like **S**, **K**, and **I**. His 1969 theorem states that each typable object has a *principal* type-scheme — one from which every valid typing is a substitution instance — and he gave an algorithm computing it [1]. Milner, working independently on the metalanguage of the Edinburgh LCF theorem prover, rediscovered the same structure a decade later [2]. The convergence is no accident: both men had isolated the unique maximal point in the lattice of typings, ordered by the instantiation (substitution) relation.

### 2.3 The grammar of types

HM distinguishes **monotypes** (types, τ) from **polytypes** (type schemes, σ):

```
τ ::= α | ι | τ → τ          (monotypes: variables, base types, arrows)
σ ::= τ | ∀α. σ              (type schemes: prenex quantification only)
```

Crucially, ∀ may appear *only at the outermost level*. This prenex restriction is the load-bearing wall of the edifice: it keeps inference decidable, unlike the impredicative System F, where quantification may nest arbitrarily and inference is undecidable [9].

Two operations mediate between monotypes and schemes. **Instantiation** replaces quantified variables with fresh ones at each use site; **generalization** closes over the free variables of an inferred monotype that are not mentioned in the environment:

$$\mathrm{Gen}(\Gamma, \tau) = \forall \bar\alpha.\, \tau \quad\text{where}\quad \bar\alpha = \mathrm{ftv}(\tau) \setminus \mathrm{ftv}(\Gamma)$$

Subtracting the environment's free variables is essential: it prevents quantifying a variable the context has already fixed, which would be unsound.

## 3 Methodology

### 3.1 The declarative typing rules

HM is specified declaratively by four rules. We write Γ ⊢ e : τ for "e has monotype τ in environment Γ", where Γ maps variables to *schemes*:

- **(Var)** If Γ(x) = ∀ᾱ.τ, then Γ ⊢ x : τ[ᾱ ↦ fresh]. *A variable is used at a fresh instance of its scheme.*
- **(Abs)** If Γ, x:τ₁ ⊢ e : τ₂, then Γ ⊢ λx.e : τ₁ → τ₂. *λ-bound variables are monomorphic.*
- **(App)** If Γ ⊢ e₁ : τ₁ → τ₂ and Γ ⊢ e₂ : τ₁, then Γ ⊢ e₁ e₂ : τ₂.
- **(Let)** If Γ ⊢ e₁ : τ₁, Gen(Γ, τ₁) = σ, and Γ, x:σ ⊢ e₂ : τ₂, then Γ ⊢ let x = e₁ in e₂ : τ₂. *This is the only rule that introduces polymorphism.*

The asymmetry between **Abs** (monomorphic) and **Let** (polymorphic) *is* let-polymorphism. It is a deliberate, principled restriction: polymorphic λ-arguments would demand impredicative instantiation, and complete inference for such systems is undecidable [9].

### 3.2 Algorithm W

Damas and Milner's Algorithm W [3] is a syntax-directed function `W(Γ, e) = (S, τ)` returning a substitution S and a monotype τ. It threads substitutions through the recursion, composing them as constraints are discovered:

```haskell
-- W : Env -> Expr -> (Subst, Type)
w env (Var x) =
  let Forall as t = lookup env x
  in (emptySubst, instantiate as t)          -- fresh variables for quantified ones

w env (Lam x e) =
  let b = freshVar
      (s1, t1) = w (extend env x (Forall [] b)) e
  in (s1, apply s1 b :-> t1)                 -- arrow from bound var to body type

w env (App e1 e2) =
  let (s1, t1) = w env e1
      (s2, t2) = w (applyEnv s1 env) e2
      b = freshVar
      s3 = unify (apply s2 t1) (t2 :-> b)    -- function type must match argument
  in (s3 `compose` s2 `compose` s1, apply s3 b)

w env (Let x e1 e2) =
  let (s1, t1) = w env e1
      env1 = applyEnv s1 env
      sigma = generalize env1 t1             -- Gen: quantify unconstrained variables
      (s2, t2) = w (extend env1 x sigma) e2
  in (s2 `compose` s1, t2)
```

The `Let` case is the heart of the algorithm: after inferring τ₁ for the bound expression under the current substitution, it *generalizes* — promoting free variables untouched by the environment into universal quantifiers — so that each use of `x` in `e₂` may be instantiated independently.

### 3.3 Robinson unification

Every application of a function to an argument generates an equation between types; `unify` solves them. Robinson's algorithm [4] computes the **most general unifier (mgu)** by repeatedly extracting the *disagreement set* — the leftmost position where two terms differ — and binding a variable to the opposing term:

```python
def unify(t1, t2):
    """Return the most general unifier of t1 and t2, or raise TypeError."""
    t1, t2 = find(t1), find(t2)
    if t1 == t2:
        return {}
    if isinstance(t1, TVar):
        if occurs_in(t1, t2):
            raise TypeError("occurs check: infinite type")
        return {t1: t2}
    if isinstance(t2, TVar):
        if occurs_in(t2, t1):
            raise TypeError("occurs check: infinite type")
        return {t2: t1}
    if isinstance(t1, TArrow) and isinstance(t2, TArrow):
        s1 = unify(t1.dom, t2.dom)
        s2 = unify(apply(s1, t1.cod), apply(s1, t2.cod))
        return compose(s2, s1)
    raise TypeError(f"cannot unify {t1} with {t2}")
```

The **occurs check** — refusing to bind α to a type containing α — is what rejects the self-application `λx. x x`: it would demand α = α → β, an infinite type. Production implementations implement `find` with a union-find structure and tag variables with *levels* (or ranks) so that generalization becomes a constant-time level comparison rather than a traversal of the environment — the optimization that makes W run in near-linear time on real programs.

## 4 Deep Dive

### 4.1 Unification theory: the mgu theorem

Robinson's central result is that unification, when it succeeds, yields a *canonical* solution [4]:

> **Theorem (Most general unifier):** If terms t₁ and t₂ are unifiable, there exists a substitution μ (the mgu) such that μ unifies t₁ and t₂, and every other unifier σ factors as σ = ρ ∘ μ for some ρ. Moreover, μ is unique up to variable renaming.

This theorem is the entire reason principal types exist: Algorithm W solves type equations with the mgu at every step, so the final substitution is the most general one consistent with the program's structure, and the returned type is the most general typing. The occurs check is not a hack but the constructive content of the theorem's hypothesis — without it, the "unifier" of α and α → β would be the infinite substitution α ↦ (α → β) ↦ ((α → β) → β) ↦ …, which is no substitution at all.

In Rust, the occurs check is naturally expressed as a traversal over an interned type graph:

```rust
fn occurs_in(var: VarId, ty: &Type, store: &TypeStore) -> bool {
    match ty {
        Type::Var(v) => *v == var,
        Type::Arrow(dom, cod) => {
            occurs_in(var, &store[*dom], store) || occurs_in(var, &store[*cod], store)
        }
        Type::Base(_) => false,
    }
}
```

### 4.2 A complete trace: inferring the type of `let id = λx.x in id id`

To see let-polymorphism in action, trace W on `let id = λx.x in id id`:

1. Infer `λx.x`: bind x : β (fresh); body has type β, so τ₁ = β → β with substitution {}.
2. **Generalize**: ftv(β → β) ∖ ftv(∅) = {β}, yielding σ = ∀β. β → β — the identity is now *polymorphic*.
3. First use `id`: instantiate with fresh β₁ → β₁ → β₁; second use: fresh β₂ → β₂ → β₂.
4. Unify (β₁ → β₁) with (β₂ → β₂) → γ; the mgu is {β₁ ↦ β₂, γ ↦ β₂ → β₂}.
5. Result type β₂ → β₂, closed over the empty environment to **∀α. α → α**.

Had `id` been λ-bound instead — `(λid. id id) (λx.x)` — the argument would receive a monomorphic type variable, unification would equate its two uses, and the outer application could not be typed at both `Int → Int` and `Bool → Bool` simultaneously. That contrast is precisely the expressive boundary of the Let rule.

### 4.3 The principal types theorem

Damas and Milner proved W both sound and complete with respect to the declarative system [3]:

> **Theorem (Soundness):** If W(Γ, e) = (S, τ), then S(Γ) ⊢ e : τ is derivable in HM.
> **Theorem (Completeness):** If Γ ⊢ e : τ is derivable, then W(Γ, e) terminates with (S, τ′), and τ = R(τ′) for some substitution R.

In short: W infers a type exactly when one exists, and the inferred type is *principal*.

| Term | Principal type |
|---|---|
| `λx.x` (I) | ∀α. α → α |
| `λx.λy.x` (K) | ∀αβ. α → β → α |
| `λf.λg.λx. f (g x)` (B, compose) | ∀αβγ. (α → β) → (γ → α) → γ → β |
| `λf.λx. f (f x)` (twice) | ∀α. (α → α) → α → α |
| `let id = λx.x in (id 1, id True)` | (Int, Bool) — via instantiation |
| `λx. x x` (ω) | *rejected* — occurs check |

### 4.4 The value restriction: polymorphism meets mutable state

HM's generalization is unsound in the presence of mutable references.

```ocaml
let r = ref [] in        (* r : ∀α. α list ref   -- unsound generalization! *)
  (r := [1];             (* instantiate α := int *)
   hd (!r) = "x")        (* instantiate α := string -- type error at runtime *)
```

### 4.5 Beyond HM: constraints, ranks, and the decidability boundary

Three research directions extend or reformulate HM, each confronting the same boundary — prenex, rank-1 quantification is what keeps inference decidable:

1. **Constraint-based inference.** Rather than threading substitutions eagerly, modern formulations (the HM(X) tradition) *generate* a constraint from each subexpression and *solve* the constraint set separately. This separation yields better error messages and modular extensions. Bidirectional and local techniques in the same spirit propagate expected types inward from annotations, as developed for polymorphic subtyping by Pierce and Turner [7].
2. **Higher-rank types.** Odersky and Läufer showed that rank-n polymorphism becomes tractable when programmers annotate the rank-n binders, reducing inference to HM plus checking [8]. Peyton Jones, Vytiniotis, Weirich, and Shields pushed further, combining unification with bidirectional propagation so that annotations guide inference for arbitrary-rank and even impredicative types — while noting that *complete* inference for higher-rank systems is undecidable [9].
3. **Decidability limits.** Rank-2 inference is decidable (via semi-unification); rank-3 and impredicative inference are not [9]. Every production language that extends HM — GHC's GADTs, type families, and beyond — therefore demands annotations exactly at the points where inference would otherwise become undecidable. The HM boundary is not a historical accident; it is the contour of what can be inferred.

The unification loop itself can be specified declaratively.

```tla+
---- MODULE Unify ----
EXTENDS Naturals, FiniteSets
VARIABLES eqs, subst          \* equations to solve, substitution built so far

UnifyStep ==
    \E <<s, t>> \in eqs :
        IF s = t THEN eqs' = eqs \ {<<s, t>>}
        ELSE IF s \in TVar /\ s \notin Vars(t) THEN
            eqs' = SubstAll(s, t, eqs \ {<<s, t>>}) /\ subst' = Compose(subst, [s |-> t])
        ELSE IF t \in TVar /\ t \notin Vars(s) THEN
            eqs' = SubstAll(t, s, eqs \ {<<s, t>>}) /\ subst' = Compose(subst, [t |-> s])
        ELSE IF IsArrow(s) /\ IsArrow(t) THEN
            eqs' = (eqs \ {<<s, t>>}) \cup {<<Dom(s), Dom(t)>>, <<Cod(s), Cod(t)>>}
        ELSE Fail                            \* clash: no unifier exists
====
```

The spec makes the algorithm's essence visible: unification is equation elimination, and the occurs check (`s ∉ Vars(t)`) is the guard that keeps the eliminated equations finite.

## 5 Empirical Results and Proofs

### 5.1 Proof sketch: why W is complete

The completeness argument [3] proceeds by induction on the typing derivation Γ ⊢ e : τ, maintaining the invariant that W's accumulated substitution is *more general* than any substitution witnessing the derivation:

1. **Variables:** instantiation with fresh variables is trivially most general.
2. **Abstraction:** the fresh variable for the bound argument imposes no constraint, so generality is preserved.
3. **Application:** given any derivation's unifier σ for the equation t₁ = t₂ → β, the mgu μ computed by W satisfies σ = ρ ∘ μ by the mgu theorem [4]; composing ρ with the induction hypotheses yields the claim.
4. **Let:** generalization quantifies exactly the variables free in τ₁ but not in Γ; any derivation must instantiate them somehow, and W's scheme is the most general choice.

Soundness is the converse induction: each step of W corresponds to a valid rule application under the returned substitution. Together they establish the principal-types property as a *theorem*, not a heuristic.

### 5.2 Measured behavior

Implementations of Algorithm W with union-find unification and level-based generalization consistently exhibit near-linear behavior on real codebases: each subexpression is visited once, unification performs path-compressed finds, and generalization is a level comparison rather than an environment traversal. The pathological exponential cases in the literature require adversarially nested terms; on human-written programs, inference time is dominated by I/O and parsing. The occurs check — sometimes omitted in performance-critical paths (as in early Prolog) — is retained in all production type checkers, since accepting `λx. x x` would admit infinite types and break the principal-types guarantee [4].

### 5.3 The rejection diagnostic

Tracing the rejection of `λx. x x` demonstrates the occurs check empirically. W binds x : α, then unifies α with α → β. The disagreement set is {α, α → β}; binding α ↦ α → β fails the occurs check since α ∈ ftv(α → β). The algorithm raises a type error — the *only* correct answer, because no finite type satisfies the equation. This single guard is what separates HM from unsound "unification without occurs check" designs.

## 6 Limitations

HM's power comes from restrictions, and each restriction is a limitation:

- **No impredicative instantiation.** A polymorphic function cannot be passed where a monomorphic argument is expected to be instantiated with a polytype, e.g. `id id` used at type `(∀α.α→α) → (∀α.α→α)` is rejected. Impredicativity requires annotations [9].
- **No higher-rank inference.** Types like `(∀α. α → α) → Int` cannot be inferred; they can only be checked against annotations, following Odersky–Läufer [8] or the bidirectional approach of Peyton Jones et al. [9].
- **Monomorphic recursion.** Because generalization requires the body's type first, a recursive function's recursive calls are checked monomorphically — polymorphic recursion must be annotated.
- **Error messages.** Unification reports *where equations clash*, not *what the programmer meant*; a single wrong argument can produce an error mentioning distant, seemingly unrelated types. Constraint-based reformulations [7] improve diagnostics by separating generation from solving.
- **No subtyping or overloading.** HM's equality-only constraints cannot express subtyping; integrating subsumption requires local or bidirectional techniques [7].
- **The value restriction's tax.** Perfectly safe polymorphic uses of mutable or expansive expressions are rejected or stay monomorphic; workarounds (eta-expansion, the relaxed restriction, polymorphism by name [5][6]) recover only part of the lost expressiveness.

## 7 Conclusion

The Hindley–Milner type system remains, nearly five decades after Milner's paper [2], the most successful compromise ever struck between expressiveness and automation in type inference. Its recipe — prenex let-polymorphism, Robinson unification with the occurs check [4], and the Damas–Milner proof that the inferred type is principal [3] — delivers complete, decidable, annotation-free reconstruction of the most general typing for every typable program. The value restriction [5][6] shows how the recipe adapts when effects enter the picture, and the modern extensions [7][8][9] map exactly the frontier where inference must surrender to annotation. Every mainstream functional language still lives inside the boundary Hindley first drew in 1969 [1]: *infer what can be inferred, annotate the rest*. That boundary has proven to be not a limitation of imagination, but a theorem about what is possible.
