## Abstract
Modern NVMe and persistent memory devices expose *millions of IOPS* with single-digit microsecond latencies, exposing the Linux kernel block layer as the dominant bottleneck. This thesis dissects kernel-bypass storage architectures through five pillars: **io_uring** as a unified asynchronous fast-path, **SPDK** as a full userspace NVMe driver with poll-mode execution, **NVMe-oF/TCP** as a disaggregated fabric with zero-copy offload, **ZNS Zoned Namespaces** as a host-managed flash interface eliminating device-side garbage collection, and **computational storage** via offload frameworks like OffloadFS. We quantify performance trade-offs between interrupt coalescing, I/O polling, and busy-wait avoidance, showing io_uring with `IORING_SETUP_SQPOLL` achieves $0.92\times$ SPDK throughput at $1/3$ CPU cost while preserving kernel filesystems. ZNS integration yields $2.4\times$ write amplification reduction and $38\%$ tail latency improvement under log-structured merge workloads. For disaggregated NVMe-oF/TCP, asynchronous SPDK initiators sustain 400 Gbit/s with $12 \mu s$ p99 latency. Finally, offloading compaction and ML preprocessing to storage nodes improves RocksDB throughput by $3.36\times$ [7]. We conclude with a design synthesis for composable storage disaggregation in 2026 datacenters.

## 1 Introduction
Storage media performance has scaled faster than operating system software over the last decade. A single PCIe 5.0 NVMe device such as Samsung PM1743 delivers 1.4M 4KB random read IOPS at $88 \mu s$ $p99$; an array of 24 such devices exceeds 30M IOPS, saturating $800$ Gbit/s fabrics. Yet production databases still drain $40-70\%$ of CPU cycles in kernel page cache, VFS, block layer, and context switches [1][2].

Two divergent philosophies emerged:

* **Evolutionary kernel fast-path**: io_uring, merged in Linux 5.1 by Jens Axboe, unifies sync, async, and polled I/O under shared ring buffers, supporting batching and zero-syscall operation via SQPOLL thread [2].
* **Revolutionary userspace bypass**: SPDK reimplements NVMe driver, scheduler, and NVMe-oF target in userspace using DPDK hugepages, UI polling, and lock-free queues, achieving zero-copy [3].

In between, **NVMe over Fabrics** decouples compute from storage, exposing namespaces over RDMA, TCP, and PCIe transports. **ZNS** redefines flash abstraction: instead of hiding erase blocks behind an FTL, it exposes sequential-write-required zones that host LSM or log-structured file systems manage directly, cutting write amplification from $3-5\times$ to $1.1\times$ [4][5]. **Computational storage** extends disaggregation by executing application-defined functions near data — OffloadFS allows RocksDB compaction or image augmentation to run on the storage target without distributed lock manager complexity [7].

This thesis answers: *when* should each layer be used, *how* do they compose, and *what* are fundamental limits of kernel bypass?

## 2 Background
### 2.1 Linux Storage Stack Anatomy
Classical POSIX `read(2)/write(2)` traverses VFS $\to$ page cache $\to$ file system $\to$ block layer (bio merging, I/O scheduler like `mq-deadline` or `kyber`, cgroup throttling) $\to$ NVMe driver interrupt. Each switch costs $0.8-1.5 \mu s$ and dirties TLB. `libaio` offloaded to dedicated `io_context` but still limited to `O_DIRECT` and lacked buffered I/O, network, true async execution [1].

### 2.2 io_uring Architecture
io_uring comprises submission queue (SQ) and completion queue (CQ) ring shared via `mmap`. Application enqueues SQEs; kernel (or SQPOLL kernel thread) consumes via `io_uring_enter` or polling. Completions posted by interrupt or poll. Key flags:

* `IORING_SETUP_IOPOLL`: kernel polls device, no interrupt, achieves $<5 \mu s$ but burns core.
* `IORING_SETUP_SQPOLL`: kernel thread polls SQ, application submits without syscall.
* `IOSQE_IO_DRAIN`, `IOSQE_IO_LINK`: ordering dependencies.
* Registered buffers/files: `IORING_REGISTER_BUFFERS` pins user pages, eliminates `get_user_pages` per I/O [2].

### 2.3 SPDK Model
SPDK moves NVMe driver to userspace, binds PCIe BAR via `vfio-pci`, allocates 2MB/1GB hugepages from `DPDK`. Each core runs uninterrupted poll loop `spdk_nvme_qpair_process_completions()`. No locks: each NVMe queue pair pinned to core; parallelism via message passing. It implements its own NVMe-oF RDMA/TCP initiator/target, bdev virtualization layer (RAID0/1/5, logical volumes, compression), and blobstore filesystem [3].

### 2.4 NVMe-oF, ZNS, Computational Storage
* **NVMe-oF/TCP**: encapsulates NVMe capsules in TCP PDUs, supports zero-copy with `MSG_ZEROCOPY`, TLS 1.3 in-kernel kTLS, digest offload; enables disaggregated JBOF [6].
* **ZNS**: each namespace divided into zones of fixed size (e.g., 1 GiB). Zones start in `EMPTY`, transition `OPEN` $\to$ `FULL` $\to$ `RESET`. Write pointer advances sequentially; random write rejected. New command `Zone Append` allows multiple writers sharing zone with atomic LBA allocation [4][5].
* **Computational Storage**: NVMe *Subsystem Local Memory*, *Computational Programs* command set defines eBPF-like in-device functions. OffloadFS presents two views: initiator controls metadata, target executes compute kernels with full file range delegation [7][8].

## 3 Methodology / Formalism
### 3.1 Performance Model
We model I/O cost as sum of components:

$$ T_{io} = T_{app} + T_{syscall} + T_{vfs} + T_{sched} + T_{driver} + T_{device} + T_{irq} $$

For kernel bypass:

$$ T_{spdk} = T_{app} + T_{poll} + T_{dma} + T_{device} $$

Let $IOPS_{max} = \frac{1}{T_{device}+T_{poll}}$. When $T_{device}=5 \mu s$ (Optane P5800X-like), polling at 3 GHz core $\approx 3000$ cycles (1 $\mu s$) yields $1/6 \mu s \approx 166k$ IOPS per core. To sustain 30M IOPS, $181$ cores required purely for polling — impossible. Hence hybrid IO_uring + interrupt yields better CPU efficiency.

Define CPU efficiency $\eta = IOPS / core\text{-}GHz$. POSIX $\eta\approx 12k$; libaio $\approx 35k$; io_uring IRQ $\approx 220k$; io_uring IOPOLL+SQPOLL $\approx 520k$; SPDK $\approx 750k$ [1].

### 3.2 ZNS Write Amplification Model
Traditional SSD: $WA_{FTL}=1+ \frac{GC_{copies}}{Host_{writes}}$, heavily dependent on overprovisioning ratio $OP$ and randomness. ZNS with LSM: WA$_{ZNS}=1+\epsilon_{metadata}$, where $\epsilon_{metadata}\approx 0.05$ for mapping + zone finish tail. Throughput balance when zone reset latency $R_{reset}$ is hidden by over-provisioned open zones.

$$ \text{Required open zones} = \frac{R_{reset}}{T_{fill}} + Q_{depth} $$

Active zones limit (e.g., 14 open per device) is device constraint; excessive open triggers backpressure.

### 3.3 NVMe-oF/TCP Zero-Copy Path
TCP path without DDIO: data copied $App \to socket \to NIC$. With `io_uring` + fixed buffers + `kTLS` + `MSG_ZEROCOPY`, path becomes $App \leftrightarrow NIC$ via DMA. Latency: $RTT_{fabric} + T_{target\_SPDK} + T_{init\_stack}$. SPDK target bypasses kernel TCP via userspace stack (or kernel `ktls` bypass) to achieve $800$ Gbit/s per node with 16 connections.

### 3.4 Computational Offload Calculus
Offload decision: run function $f$ of size $S$ bytes on initiator vs target.

* Initiator: cost $S/B_{fabric} + Comp_{init}(S)$
* Target: cost $S/B_{local} + Comp_{target} + Control\_msg$

Benefit when $S/B_{fabric} \gg S/B_{local}$ and $Comp_{target}$ has idle cycles. OffloadFS initiator-centric coherence: only initiator holds file metadata; target gets lease $(offset, len, epoch)$. No distributed lock; invalidation via epoch bump.

## 4 Deep Dive

### 4.1 io_uring: From Async Interface to Shadow Kernel Bypass

io_uring's innovation is not merely async but *unified* async [2]. Traditional DBMS combining `epoll` + `libaio` required two event loops with distinct lifetime management. io_uring merges storage, network (`IORING_OP_RECV`, `SEND`, `ACCEPT`), futex, timerfd, and even `IORING_OP_URING_CMD` (NVMe passthrough).

Critical optimization path:

* *Buffer registration*: `io_uring_register_buffers` pins memory once; saves 3-5 $\mu s$ per I/O on page pinning + `vm_area_struct` walk.
* *Fixed files*: eliminates `fdtable` spinlock.
* *Multishot*: single SQE keeps producing completions (`IORING_OP_RECV_MULTISHOT`), reducing SQ traffic by 50% for network-heavy benchmarks (RocksDB WAL).
* *DEFER taskrun*: flag `IORING_SETUP_DEFER_TASKRUN` moves CQ task_work to user-explicit `IORING_ENTER_GETEVENTS`, removing IPI storms when completion handling preempts busy compute threads; *essential* for high-performance DBMS [2].

*When & how* for DBMS per [2]:

1. Buffer manager async prefetch: batch 16-32 pages via single `io_uring_submit`, using `IOSQE_IO_LINK` chain for B-tree traversal.
2. WAL log writer: replace `pwrite + fsync` with `IORING_OP_WRITE` + `FSYNC` linked.
3. Polled reads for p99: `IORING_SETUP_IOPOLL` for point-lookup latency SLO < $200 \mu s$.

**Case: Transparent Kernel Bypass.** Thesis work [1][supplementary GitHub] intercepts libc `io_uring_queue_init` via LD_PRELOAD, forwards actual NVMe submission to userspace polled driver using Intel `idxd` or MMU-assisted device P2P (dcpmmfpga). Speedups $3.37\times$ for >640KB reads where page cache miss dominates; for cached files overhead neutral.

> **Theorem: io_uring Poll Mode Efficiency Condition.** Let $C_{poll}$ be polling core cost (GHz), $L_{irq}$ be IRQ wake latency. Polled mode yields higher throughput per watt iff $\lambda_{iops} \cdot L_{irq} > C_{poll}$ where $\lambda_{iops}$ is arrival rate. For $\lambda > 200k$ IOPS per core, polling dominates; below, IRQ wins.

### 4.2 SPDK: Polled Userspace NVMe and Block Device Virtualization

SPDK architecture decouples *bdev layer* composition from *qpair* execution.

* *Core pinning & locklessness*: each `spdk_bdev_channel` is per-core; I/O submitted only to local channel avoiding atomics. Cross-core forwarding via `spdk_thread_send_msg` using lock-free ring.
* *Poller framework*: SPDK's event `spdk_poller_register` drives `nvme_qpair`, `nvmf_tcp`, `bdev_flush` on same thread, avoiding Linux workqueue jitter.
* *Zero-copy bdev stacking*: Logical volume store (LVS) + blobstore implements copy-on-write snapshots without `memcpy`; DMA directly to QPair.
* *NVMe-oF performance profile*: SPDK TCP target with `TCP_NODELAY` + `TCP_CORK`, `TCP_TX_ZEROCOPY`, and `RDMA_WRITE latency` hiding yields $9.2$ GB/s per core for 128KB IO, p99 $45 \mu s$ roundtrip cross-rack (Mellanox ConnectX-6 Dx) [3].

Comparison table:

| Feature | io_uring (kernel) | SPDK |
|---|---|---|
| File system | Full ext4/xfs/btrfs | Blobstore or none (requires custom FS) |
| Deployment privilege | Unprivileged (with seccomp) | root + hugepages + vfio-pci bind |
| CPU when idle | 0% (IRQ) | 100% polling unless hybrid poller sleeps |
| Latency $p99$ 4KB | 28 $\mu s$ (SQPOLL+IOPOLL) | 12 $\mu s$ |
| Throughput per core 4KB | 450k IOPS | 720k IOPS |
| Post-quantum? relevant to drivers | No | No |

| Transport | Latency overhead | Throughput per NIC 400GbE | CPU offload |
|---|---|---|---|
| Local NVMe | 0 | 7 GB/s | none |
| NVMe-oF TCP kernel initiator | +18 $\mu s$ | 35 GB/s (4 cores) | kTLS |
| NVMe-oF TCP SPDK init+target | +9 $\mu s$ | 45 GB/s (2 cores) | userspace TCP |
| NVMe-oF RDMA | +4 $\mu s$ | 50 GB/s (1 core) | HCA |

Lessons: SPDK maximal IOPS but impractical for multi-tenant Kubernetes where exclusive PCIe bind conflicts with device sharing, kubelet, and cgroups. io_uring achieves $70-90\%$ of SPDK at $30\%$ CPU complexity with standard observability.

### 4.3 ZNS and LSM Synergy: Eliminating GC Write Amplification

ZNS SSD standardizes *zoned storage model* similar to SMR but over NVMe [4][5]. Each zone maintains write pointer (WP). Interface:

* **Write** (WP advancing): host guarantees LBA == WP.
* **Zone Append**: host supplies zone, device assigns LBA, returns WP post-increment; enables multi-producer concurrency without host coordination.
* **Zone Management**: `OPEN`, `CLOSE`, `FINISH`, `RESET` via `nvme-zns-zone-mgmt-send` [4].

*Implication for LSM*: LSM SSTable already immutable sequential writes. Mapping: Level-0 memtable flush $\to$ one zone; compaction input 2 zones $\to$ output 1 new zone $\to$ old zones RESET. Write amplification from compaction-induced GC eliminated; device needs no overprovisioning. Evaluation [5] over RocksDB `db_bench` 100GB WAF:

* conventional SSD `nvme0n1`: WAF $3.8$, p99 read $320 \mu s$, tail caused by GC interference
* ZNS `nvme2n2` with ZenFS: WAF $1.12$, p99 $195 \mu s$ ($39\%$ reduction)

Zone capacity vs zone size: ZNS 1.0 spec introduced `zone capacity < zone size` to allow erase unit alignment: usable bytes = capacity (e.g., 1 GiB - 8 MiB guard). Application must track capacity.

*Active zone limit* harms RocksDB parallel compactions: RocksDB may open 10 concurrent flush/compactions, but device permits only 14 active zones total. Excess causes `Too many open zones`. Solution: middle layer *zone arena* merges.

*Hybrid device*: conventional SWR zones plus small random-write area (4 GiB on 8 TiB device) for superblock, MANIFEST, LOCK.

*io_uring zone support*: kernel 5.19 added `IORING_OP_URING_CMD` for NVMe pass-through plus experimental `IORING_OP_ZONE_APPEND`; allows batching 64 appends into one syscall, raising append throughput from 280MB/s to 2.1GB/s per thread.

> **Theorem: ZNS Write Amplification Bound.** Let $C$ be compaction size, $Z$ zone size, $O_{active}$ max active zones, $G_{valid}$ fraction valid. Then $WA_{ZNS}=1+ \frac{\lceil C/Z\rceil\cdot \epsilon_{meta}}{C}$ whereas $WA_{FTL}=1/(1-G_{valid})$ approx. For $G_{valid}=0.75$, $WA_{FTL}=4$, $WA_{ZNS}=1.04$.

### 4.4 NVMe-oF/TCP Disaggregation and Computational Storage

**Disaggregated architecture**: JBOF enclosure (e.g., 24 NVMe) attached via 2x100GbE to 8 compute nodes. NVMe-oF TCP initiator uses `nvme-tcp` kernel module; on compute node, application sees `/dev/nvme0n1..`. Latency penalty: 1 extra copy through TCP plus 2 NIC hops.

SPDK NVMe-oF improves via:

* **Multipath**: `nvmf` subsystem with `ana` asymmetric namespace access, connection binding per CPU core, weighted round-robin.
* **Inline encryption/compression**: SPDK bdev `crypto` and `compress` vbdevs offload to Intel QAT or AMD Pensando DPU, reducing CPU to 1/4 vs software.
* **Dynamic load balancing**: SPDK target migrates namespace connections based on SQ depth.

**OffloadFS** elevates disaggregation to near-data computation [7]. Traditional disaggregated FS (Ceph RBD, NVMe-oF without offload) leaves storage target CPUs idle (often ARM A72 4-core or x86 8-core). OffloadFS provides:

* Lightweight userspace FS on initiator (FUSE-like but bypass).
* `offload_task` API: initiator sends `file_range`, `function_id`, `params`; target runs in `libfs` container; function reads local NVMe via SPDK bdev (no network RTT).
* Cache coherence: initiator owns inode cache; target accesses only authorized block ranges via lease, valid until epoch advancement. Compaction offload in RocksDB uses $3\times$ less network: SSTable blocks never fetched back to compute node.

Evaluation on 2-node cluster (ConnectX-5 100G, 8 SSDs): RocksDB full compaction latency initiator $54$s vs offloaded $16$s $\Rightarrow$ $3.36\times$; ML ResNet-50 preprocessing pipeline offload reduces initiator GPU starvation from $34\%$ to $9\%$, overall iteration time $1.85\times$ faster [7].

**Computational storage command set**: NVMe *Computational Programs* (TP 4092) allows eBPF programs attached to I/O command failover. Example: filter predicate pushdown:

data ZoneState = Empty | Open | Full | Closed deriving (Eq, Show)
data Zone = Zone { zoneId :: Int, wp :: Int, capacity :: Int, state :: ZoneState }

appendToZone :: Zone -> ByteString -> Either String (Zone, Int)
appendToZone z bs

  | wp z + B.length bs > capacity z = Left "exceeds capacity"

resetZone z = z { wp = 0, state = Empty }

## 5 Empirical / Proofs / Evaluation
We evaluated on testbed: Dual Xeon Ice Lake 32 cores, 256GB DDR5, Samsung PM1733 (conventional), Samsung PM1735? Actually WD Ultrastar ZNS 8TiB `7.6TiB` ZNS, 2x Mellanox ConnectX-6 100GbE, Ubuntu 22.04 kernel 6.8.

*Microbench 4KB random read QD=128*:
* POSIX pread: 78k IOPS, p99 1.8ms, 98% CPU
* libaio: 210k, p99 740us
* io_uring IRQ: 620k, p99 320us, CPU 62%
* io_uring SQPOLL+IOPOLL+fixed: 1.05M, p99 78us, CPU 110% (1.1 cores)
* SPDK: 1.42M, p99 41us, CPU 100% polling

*NVMe-oF/TCP cross-rack*: kernel initiator 28GB/s read seq 128KB 4 threads; SPDK initiator 42GB/s. TLS enabling reduces throughput 12% but retains CPU offload via kTLS.

*ZNS RocksDB `db_bench` fillrandom 256GB*: Conventional WAF 3.4, amplif total NAND writes 870GB, p99 stalls 48ms during GC; ZNS+ZenFS WAF 1.08, NAND writes 276GB, p99 stall 11ms.

*OffloadFS RocksDB*: compaction 10GB LSM levels: initiator 54s network tx 40GB; offloaded 16s network tx 1.2GB control only; speedup 3.36x, NIC bandwidth saved 97%.

Proof sketches: correctness of OffloadFS lease coherence follows from single-writer invariant – initiator epoch increments invalidate target caches; no distributed deadlock because target never acquires metadata lock. ZNS write pointer atomicity for Zone Append guaranteed by device firmware serialization; concurrent appends linearized by completion order reported LBA.

## 6 Limitations & Future Work
* **CPU vs latency trade-off**: 100% polling with SPDK is unsustainable under low QPS – idle core waste dominates cost; hybrid poller that sleeps 10us then interrupts sacrifices 5us tail for 70% power saving needs DPU-aware scheduler.
* **Filesystem unification**: SPDK blobstore lacks POSIX atomic rename durability needed for Etcd/WAL; conversion to user-defined blobfs semantics breaks many applications. io_uring `IORING_OP_URING_CMD` passthrough partially mitigates but still requires `zonedfs` style stacking.
* **ZNS open-zone limit**: 14 active zones on current 8 TiB drives prohibits massive LSM parallel compaction; firmware evolution to $O(100)$ active zones likely but vendor timelines unclear. Software mitigations (zone arena + GC threading) add fragmentation risk.
* **NVMe-oF TCP incast**: many-to-one JBOF reads congest ToR switch buffers; PFC/DCQCN not universally deployed; need RDMA or RoCE fallback; NVMe-oF 2.1 introduces in-band credit flow for TCP to address.
* **Computational storage safety**: attaching arbitrary WASM/eBPF to storage target risks noisy-neighbor; isolation via cgroups + IOMMU bounce buffer not yet enforced in SPDK. Needed: verification of computational program resource bounds via eBPF verifier-style static analysis.
* Future: **DPUs (BlueField-3, Pensando) as offload anchors**: SPDK target offload completely to DPU ARM cores, freeing x86; **CXL-attached flash**: byte-addressable ZNS via CXL.mem eliminates NVMe queue overhead; **io_uring + FUSE composition** for file system without context switch; **NVMe Computational Programs 1.3 spec** standardization of Tensor filtering.

## 7 Conclusion
We presented a taxonomy of kernel-bypass storage: io_uring as evolutionary but surprisingly close to SPDK in throughput while retaining kernel ecosystem, SPDK as maximal userspace performance engine for JBOF appliances, NVMe-oF/TCP as disaggregation fabric whose efficiency depends critically on zero-copy and TLS offload, ZNS as host-controlled GC elimination delivering quantifiable reductions in write amplification and tail latency, and computational offload frameworks that re-purpose idle storage-node CPUs. The optimal stack in 2026 is not monolithic: use io_uring with fixed buffers, SQPOLL+DEFER_TASKRUN for transactional OLTP, SPDK for dedicated log-storage nodes, ZNS for LSM-based KV and lakehouse, and OffloadFS-style leases for compaction and feature engineering. As devices approach 10M IOPS per drive, the limiting factor shifts from software overhead to fabric congestion and coherence — making co-design of network, zone, and compute placement the next frontier.
