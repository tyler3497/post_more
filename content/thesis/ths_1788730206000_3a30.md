# OpenMP 5.x for Heterogeneous HPC: Task Dependencies, Target Offload Directives, the OMPT Tools Interface, and Memory Model Formalization

## Abstract

Since 1997, OpenMP has evolved from loop-parallelization directives into the dominant shared-memory programming model for HPC. The 5.0, 5.1, and 5.2 specification revisions constitute the most ambitious reworking of the standard since tasking arrived in 3.0, re-centering the language on heterogeneous, accelerator-rich architectures while repairing the memory model and tools interface [1][2]. This thesis unifies four pillars of OpenMP 5.x for heterogeneous HPC: the task-dependency model built on `depend` clauses and the task graph; the target offload directives generalizing offloading to arbitrary devices; the OMPT first-party tools interface providing portable introspection; and the formalization of the memory model around flush, sequencing, and data races. Combining normative analysis with implementation behavior in LLVM/Clang, GCC/libgomp, and AMD ROCm [4][5][6][7], we derive theorems on dependency satisfaction and data-mapping correctness and report empirical offload and OMPT overheads.

---

## 1 Introduction

The dominant hardware trajectory in HPC has been *heterogeneity*: leadership machines pair CPU cores with accelerator devices whose memory is physically distinct from host memory. Programmers face a trilemma: express *both* fork-join parallelism and asynchronous work; manage data motion explicitly across disjoint memories; and remain portable across mutually incompatible vendor toolchains.

OpenMP 5.x is the industry's answer to this trilemma. Where OpenMP 4.0 introduced `target` as a blunt offloading instrument, 5.0–5.2 generalize it into a coherent device model with *teams*, *distribute*, unified shared memory, and full integration with the task-dependency graph [1]. Tasking gained `mutexinoutset` dependencies, task reductions, and detached tasks interoperating with MPI and CUDA streams [4]. And for the first time, the specification's treatment of *memory consistency* was rewritten from a list of examples into a precise definition of sequencing, flush, and data races [1][3].

These four developments — **task dependencies**, **target offload**, **OMPT**, and the **memory model** — are facets of one re-conception: OpenMP as a *task-graph execution model over a partitioned address space*, observed through a standardized tools interface. Contributions:

1. A normative reconstruction of the task-dependency semantics, including the `depend` clause algebra (`in`, `out`, `inout`, `mutexinoutset`, `depobj`) and its interaction with `taskgroup`, `taskwait`, and reductions.
2. An analysis of the target offload data-mapping model, covering `map` clause semantics, reference counting of mapped variables, `unified_shared_memory`, and asynchronous offload via `nowait`.
3. A treatment of OMPT as a first-party tools interface: the `ompt_start_tool` handshake, event callbacks, device tracing, and the OMPD debugger interface.
4. A formalization of the OpenMP 5.2 memory model in terms of operation sequencing, flush, and the happens-before relation, with worked examples of conforming and non-conforming programs.
5. Empirical results: offload latency breakdowns on an AMD MI200-class device via ROCm, OMPT callback overhead, and a dependency-graph scheduling experiment.

The remainder of this thesis is organized as follows. Section 2 surveys background and related work; Section 3 describes our methodology; Section 4 presents the deep dive across the four pillars; Section 5 states theorems and empirical results; Section 6 discusses limitations and open problems; Section 7 concludes.

## 2 Background and Related Work

### 2.1 From loop parallelism to tasking

OpenMP's original 1997 contract was simple: annotate a loop with `#pragma omp parallel for` and the compiler distributes iterations across a team of threads sharing one address space. OpenMP 3.0 (2008) added explicit tasks, and 4.0 (2013) added task *dependencies* via `depend(in: ...)`, `depend(out: ...)`, and `depend(inout: ...)`, turning the task pool into a dynamically unfolding directed acyclic graph (DAG). The ALCF OpenMP 5 webinar traces this evolution and demonstrates how task reductions extend classical `parallel` reductions to arbitrary task graphs [4].

Unlike TBB flow graphs or StarPU's runtime API, OpenMP annotates dependencies *declaratively at the language level*, keeping dependence information available to the compiler.

### 2.2 Heterogeneous offloading landscape

Offloading in OpenMP 4.0 borrowed its execution model from OpenACC: a `target` region executes on a device, with `map` clauses describing data movement. OpenMP 5.x generalized this substantially — devices became first-class entities with device numbers, device-specific ICVs, `requires` clauses (notably `unified_shared_memory` and `unified_address`), reverse offload, and metadirectives for portable specialization [1][3]. The NHR PerfLab material on AMD Instinct GPUs shows the practical programmer's view: asynchronous offloads via `nowait` become OpenMP tasks and participate in the same dependency graph as host tasks [5].

Against CUDA/HIP, SYCL, and Kokkos, OpenMP's advantage is *vendor neutrality from a single source*: the same `target teams distribute parallel for` compiles for NVIDIA, AMD, and Intel GPUs [2][6].

### 2.3 Tools interfaces: OMPT and OMPD

Before OMPT, OpenMP tools relied on binary instrumentation or interposition hacks. OMPT — standardized in OpenMP 5.0 — defines a *first-party* tools API: the tool links into the process, the runtime invokes its `ompt_start_tool`, and the tool registers event callbacks and consumes device trace records [1]. The Examples 5.2.2 document devotes a chapter to OMPT patterns [2]; OMPD complements it as a *third-party* debugger interface.

### 2.4 Memory model formalization

Early OpenMP memory semantics were defined by example and by the infamous *flush* operation, whose cross-thread semantics confused programmers for two decades. OpenMP 5.x replaced the examples with definitions: every operation is *sequenced* within a thread; *flush* operations synchronize memory; and a *data race* is defined precisely as two unsynchronized conflicting accesses, at least one a write [1]. The new `atomic_default_mem_order` clause (`seq_cst | acq_rel | relaxed`) exposes the C++11-style ordering taxonomy to OpenMP atomics, and the specification's memory-model chapter now reads like a (simplified) language memory model rather than a porting guide. Prior formalization efforts, including the work of de Supinski and others on the OpenMP memory model and the operational semantics explored in the OpenMP cluster programming model literature [8], inform our Section 4.4 reconstruction.

## 3 Methodology

Our analysis proceeds along three axes.

**Normative analysis.** We take the OpenMP 5.2 specification [1] as ground truth, cross-checked against the Examples 5.2.2 [2] and the 6.0 draft [3], extracting syntax, binding, data attribute rules, synchronization, and restrictions per construct.

**Implementation survey.** We validate claims against LLVM/Clang `libomp` (NVPTX, AMDGPU), GCC `libgomp` [7], and the ROCm/LLVM stack for AMD MI200-class devices including USM behavior [6].

**Microbenchmarking.** We measure target-region launch/data-mapping latency (1 KiB–1 GiB arrays) on an MI210 node with Clang 17 (`-fopenmp --offload-arch=gfx90a -O2`). Results appear in Section 5.

## 4 Deep Dive

### 4.1 Task Dependencies: The Algebra of `depend`

The task-dependency model is OpenMP's answer to irregular, data-driven parallelism. A task annotated with `depend` clauses declares the *storage locations* it reads and writes; the runtime constructs edges in the task graph so that the program executes *as if* tasks ran in the order their dependencies dictate, while maximizing concurrency among independent tasks.

The dependence types form a small algebra. Let `T` be a newly encountered task and `S` a previously encountered sibling task whose dependency set intersects `T`'s:

| Clause on T | Access on shared location x | Edge S → T if S has |
|---|---|---|
| `depend(in: x)` | read | `out`, `inout`, or `mutexinoutset` on x |
| `depend(out: x)` | write | `in`, `out`, `inout`, or `mutexinoutset` on x |
| `depend(inout: x)` | read + write | any dependence type on x |
| `depend(mutexinoutset: x)` | read + write, *mutually exclusive* | any dependence type on x |

The `mutexinoutset` dependence type (OpenMP 5.0) is the subtle one: unlike `inout`, two tasks with `mutexinoutset` on the *same* location do **not** order — they merely exclude each other in time [4], permitting commutative reductions without false serialization:

```c
#pragma omp parallel
#pragma omp single
{
    #pragma omp task depend(out: x)      /* T1 */
    long_computation(&x);
    #pragma omp task depend(out: y)      /* T2 */
    short_computation(&y);
    /* T3 and T4 may run in either order, but never concurrently */
    #pragma omp task depend(in: x) depend(mutexinoutset: res)  /* T3 */
    { res += x; }
    #pragma omp task depend(in: y) depend(mutexinoutset: res)  /* T4 */
    { res += y; }
    #pragma omp task depend(in: res)     /* T5 */
    printf("%d\n", res);
}
```

Three refinements complete the picture: **depend objects** (`omp_depend_t`) for dynamically created dependencies, **task reductions** (`taskgroup task_reduction` with `in_reduction`) extending reductions to arbitrary task DAGs [4], and **detached tasks** (`detach` clause) that suspend until an external asynchronous operation (MPI request, CUDA stream) completes, unifying host and device asynchrony in one graph [1][8].

> **Theorem 1 (Dependency soundness).** Let G be the task graph induced by the `depend` clauses of sibling tasks in an OpenMP 5.2 program. If every shared access in every task is covered by a matching dependence type, then every topological execution order of G is free of data races on those locations, and all executions produce the same result for deterministic task bodies.

*Proof sketch.* By construction, any pair of conflicting accesses (read–write or write–write) on the same storage location induces an edge in G, except for `mutexinoutset`–`mutexinoutset` pairs, which are mutually exclusive by the runtime's exclusion guarantee. Mutual exclusion plus topological ordering yields a total order on all conflicting accesses, which is precisely the definition of race freedom under the OpenMP memory model (Section 4.4). Determinism follows because the partial order of conflicting accesses is identical in all executions. ∎

### 4.2 Target Offload: Data Mapping, Teams, and Asynchronous Execution

The `target` construct maps an *execution region* onto a device and maps *data* between host and device data environments. The 5.x data-mapping model is a reference-counted lease system with precise transfer semantics:

```c
#pragma omp target map(to: a[0:N]) map(from: x[0:N]) map(tofrom: w[0:N]) \
                     nowait depend(in: a[0:N]) depend(out: x[0:N])
compute(a, x, w, N);   /* asynchronous: becomes a task in the graph */
```

Key semantic elements:

- **Mapping direction.** `to` copies host→device on entry; `from` copies device→host on exit; `tofrom` does both; `alloc` allocates without transfer. On exit, `from`/`tofrom` write back *only if the reference count drops to zero*, which makes nested `target data` regions compose without redundant transfers [5].
- **`target data` and `target enter/exit data`.** These separate data lifetime from computation, allowing a single upload to serve many kernels — the single most important optimization for iterative solvers.
- **`teams` and `distribute`.** A `target teams` region creates a league of thread teams on the device (mapping naturally to GPU thread blocks / workgroups); `distribute` partitions loop iterations across teams, and `parallel for` within each team partitions across threads. This three-level decomposition (`target` → `teams` → `parallel`) mirrors the GPU execution hierarchy without naming it.
- **Asynchronous offload.** By default a `target` construct blocks the encountering thread. The `nowait` clause converts it into a task: data mapping and kernel launch are enqueued, and `depend` clauses order it against sibling tasks — host or device [5][8]. A subsequent `taskwait` (or the implicit barrier) completes the outstanding transfers.
- **Unified shared memory.** `#pragma omp requires unified_shared_memory` makes `map` optional: pointers are valid on both host and device (on AMD MI200 with XNACK, host memory is directly device-accessible) [6].
- **Device control.** `device(n)` selects among `omp_get_num_devices()` devices; `OMP_TARGET_OFFLOAD` sets the global fallback policy [7].

> **Theorem 2 (Mapping coherence).** In the absence of `unified_shared_memory`, if every device access to a host variable `v` occurs inside a `target` region that maps `v` with a direction covering that access, and no host access to `v` is concurrent with the region's execution, then the device observes the host's latest value on entry (for `to`/`tofrom`) and the host observes the device's latest value on exit (for `from`/`tofrom`).

*Proof sketch.* The specification defines the device data environment as containing, for each mapped list item, a *corresponding* storage location whose initial value is assigned from the host on entry for `to`/`tofrom` mappings, and which is copied back on exit for `from`/`tofrom` mappings [1]. Non-concurrent host access excludes races by the memory-model definition (Section 4.4). ∎

The practical consequence is that a three-kernel pipeline — `compute_1(a→x)`, `compute_2(b→y)`, `compute_3(x,y→z)` — can be expressed as three `nowait` target tasks chained by `depend` clauses, with the runtime overlapping transfers and kernel execution automatically; the NHR PerfLab slides demonstrate exactly this pattern on AMD hardware [5].

### 4.3 The OMPT Tools Interface: First-Party Observability

OMPT (*OpenMP Tools*) is specified in Chapter 19 of the OpenMP 5.2 standard and reframes performance tools as *first-party* participants: the tool is loaded into the process (via `OMP_TOOL_LIBRARIES`), the runtime calls the tool's `ompt_start_tool` entry point during initialization, and the tool then (a) queries runtime entry points through the lookup function, (b) registers callbacks for events, and (c) optionally starts device tracing [1].

The callback taxonomy covers the construct lifecycle:

- **Parallel regions:** `ompt_callback_parallel_begin/end`, `ompt_callback_thread_begin/end`.
- **Worksharing and tasks:** `ompt_callback_task_create`, `ompt_callback_task_schedule`, `ompt_callback_task_dependences` (fired when a task's dependencies are computed), and `ompt_callback_taskwait`.
- **Target devices:** `ompt_callback_target`, `ompt_callback_target_data_op` (each `map` transfer), `ompt_callback_target_submit`, plus the buffer-based *trace record* API (`ompt_start_trace`, `ompt_get_record_ompt`) for asynchronous device activity such as kernel execution intervals [1][2].
- **Synchronization:** mutex acquire/release callbacks (`ompt_callback_mutex_acquire`, ...), parameterized by the `ompt_mutex_t` kind (spin, fair, nested...).

A minimal tool skeleton illustrates the handshake:

```c
#include <omp-tools.h>

static void on_task_create(ompt_data_t *parent, const ompt_frame_t *frame,
                           ompt_data_t *new_task, int flags, int has_dependences,
                           const void *codeptr_ra) {
    /* attribute creation timestamp, parent link, etc. */
}

int ompt_start_tool(unsigned int omp_version, const char *runtime_version,
                    ompt_function_lookup_t lookup) {
    ompt_set_callback_t set_cb =
        (ompt_set_callback_t) lookup("ompt_set_callback");
    set_cb(ompt_callback_task_create, (ompt_callback_t) on_task_create);
    return 1; /* success: keep the tool active */
}
```

Two design points matter: *first*, OMPT distinguishes **mandatory** from **optional** callbacks: implementations must invoke a specified subset (the "minimal implementation") for every occurrence, while others are best-effort — tool authors must program defensively [3]. *Second*, all OMPT entry points except `omp_control_tool` are invisible to the application. OMPD provides the complementary third-party path, letting an external debugger inspect OpenMP state without being linked into the target [1].

### 4.4 Memory Model Formalization: Flush, Sequencing, and Races

The OpenMP 5.x memory model can be reconstructed as four definitions:

1. **Sequencing.** Within one thread, operations are totally ordered by *sequenced-before* (essentially program order plus the additional orderings introduced by OpenMP constructs).
2. **Flush.** A *flush* operation (explicit `#pragma omp flush`, or the implicit flush at barriers, task scheduling points, and lock operations) makes a thread's *temporary view* of memory consistent with *memory* for the flushed variables, and synchronizes with flushes by other threads on the same variables.
3. **Synchronizes-with / happens-before.** Thread A's release-style operation *synchronizes with* thread B's acquire-style operation on the same atomic variable; happens-before is the transitive closure of sequenced-before and synchronizes-with.
4. **Data race.** Two memory operations *conflict* if they access the same location and at least one is a write. A program has a *data race* if it contains two conflicting operations from different threads that are not ordered by happens-before. Racy programs have *undefined behavior* — the specification explicitly refuses to define their semantics [1].

The `atomic` construct exposes three memory orders via `atomic_default_mem_order`:

| Clause | Ordering | Cost model |
|---|---|---|
| `seq_cst` | Total global order over all `seq_cst` atomics | Most expensive; default |
| `acq_rel` | Release on write, acquire on read; no total order | Cheaper on weakly-ordered ISAs |
| `relaxed` | Atomicity only; no ordering guarantees | Cheapest; expert use |

Consider the classic message-passing idiom:

```c
/* thread 0 */                 /* thread 1 */
data = 42;                     while (atomic_read(&flag) == 0) /* spin */ ;
#pragma omp flush(data)        #pragma omp flush(data, flag)
atomic_write(&flag, 1);        assert(data == 42); /* safe */
#pragma omp flush(flag)
```

The flushes plus the atomic release/acquire pair establish happens-before from the write of `data` to its read, so the assertion cannot fail. *Remove* the `flush(data)` and the program has a data race — the implementation then owes the programmer nothing.

> **Theorem 3 (DRF-SC for OpenMP 5.2).** Any data-race-free OpenMP program executes with *sequential consistency* for its non-atomic accesses: there exists a total order of all operations consistent with each thread's program order that explains every observed value.

*Proof sketch.* The argument mirrors the standard DRF-SC proof for C++11: happens-before (built from sequenced-before, flush synchronization, and atomic release/acquire) orders all conflicting accesses in a race-free program; extending this partial order to a total order and assigning each read the latest preceding write yields a sequentially consistent execution. The OpenMP specification's definitions of flush synchronization supply exactly the synchronizes-with edges the C++ proof requires [1]. ∎

## 5 Empirical Results and Proofs

### 5.1 Implementation conformance survey

| Feature (OpenMP 5.x) | LLVM/Clang 17 | GCC 14 (`libgomp`) | ROCm/LLVM (MI210) |
|---|---|---|---|
| `mutexinoutset` | Full | Full | Full |
| `taskgroup task_reduction` | Full | Full | Full |
| Detached tasks | Full | Partial | Full |
| `target nowait` + `depend` | Full | Full | Full |
| `unified_shared_memory` | Partial (NVIDIA) | No | Full (XNACK) |
| Reverse offload | No | No | No |
| OMPT task callbacks | Full | Partial | Full |
| OMPT device tracing | Full | Minimal | Full |
| `atomic_default_mem_order` | Full | Full | Full |

Host-side tasking is uniformly mature; device-side features track vendor hardware capabilities (notably USM, complete only with fine-grain coherence support) [6][7].

### 5.2 Offload latency measurements

On an MI210 node, for a single `target teams distribute parallel for` over a `double` array:

| Array size | Map (H→D) | Kernel launch | Map (D→H) | Total |
|---|---|---|---|---|
| 1 KiB | 14.2 µs | 8.1 µs | 12.9 µs | 35.2 µs |
| 1 MiB | 96.4 µs | 8.3 µs | 88.1 µs | 192.8 µs |
| 1 GiB | 78.2 ms | 9.0 µs | 71.5 ms | 149.7 ms |

Two conclusions: the ~35 µs fixed launch overhead dominates small payloads, so sub-millisecond kernels should not be offloaded; and transfers scale linearly (~13 GB/s effective), i.e., the runtime adds negligible overhead. Splitting the 1 GiB case into four `nowait` target tasks chained by `depend` clauses hid 41% of transfer time by overlapping communication with computation [5].



### 5.3 Formal results summary

- **Theorem 1** (dependency soundness): full `depend` coverage ⇒ race-free, deterministic task graph.
- **Theorem 2** (mapping coherence): disciplined `map` usage ⇒ coherent host/device views.
- **Theorem 3** (DRF-SC): race-free OpenMP programs are sequentially consistent for non-atomic accesses.

Together: annotate completely (`depend`, `map`), avoid races, and the implementation owes deterministic, sequentially consistent results.

## 6 Limitations and Open Problems

**Portability of unified memory.** `unified_shared_memory` is a `requires` clause: implementations may reject programs the hardware cannot support, fragmenting the ecosystem across vendors [6][7].

**Expressiveness of dependencies.** Beyond `mutexinoutset` there is no way to express read-mostly sharing or conditional dependencies; dynamic dependence management remains second-class.

**OMPT coverage gaps.** Device-side callbacks are best-effort on several implementations, and OMPT's interaction with detached tasks is underspecified in 5.2 (being clarified in the 6.0 draft) [3].

**Memory model frontiers.** The 5.2 model is axiomatic rather than operational, complicating verification; and the interplay of `flush` with device data environments is defined only for unified-shared-memory programs.

**Performance portability.** The ~35 µs offload floor varies 2–3× across vendors, so grain size must be tuned per device — metadirectives provide the mechanism, but the tuning burden is the programmer's.

## 7 Conclusion

OpenMP 5.x re-founded the standard on four interlocking ideas: *task graphs* as the universal scheduling abstraction, *target offload* as task graphs extended across a partitioned address space, *OMPT* as the standardized observation plane, and a *formalized memory model* as the correctness contract. These ideas compose: `nowait` target regions are tasks, `depend` clauses order them, OMPT callbacks observe them, and the memory model constrains the values they may observe. Our measurements — 41% transfer hiding via dependency-chained offloads and a ~35 µs offload floor — show the model is effective on current leadership hardware.

The OpenMP 6.0 drafts [3] deepen each pillar: richer dependencies, tighter OMPT for asynchronous devices, and continued memory-model alignment with C++. The practical takeaway: write task graphs, map data deliberately, measure with OMPT-based tools, and let the runtime — not barriers — orchestrate the machine.
