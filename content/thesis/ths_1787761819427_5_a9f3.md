# Energy-Proportional Disaggregated NVMe-oF: TCP vs RDMA vs CXL Memory Semantics, SPDK Userspace Stack, DPU Offload with NVIDIA BlueField, Computational Storage and ZNS Synergy

## Abstract

Disaggregated NVMe over Fabrics promises resource pooling but naive deployment inflates energy per IOPS by 2.4-3.1x due to host CPU transport tax and stranded power. This thesis characterizes energy-proportional design across three transport semantics—NVMe/TCP, NVMe/RDMA (RoCEv2/iWARP), and emerging CXL.mem/.cache memory semantics—integrated with SPDK userspace polling, NVIDIA BlueField-3 DPU offload via SNAP/DOCA, computational storage pushdown, and Zoned Namespace (ZNS) flash management. We formalize a power model P(Q) = P_idle + α·Q + β·C(Q) capturing NIC, DPU, and SSD GC costs, and evaluate on 100 GbE/200 GbE fabrics with SPDK 24.01, BlueField-3, and Samsung PM1731a ZNS SSDs. NVMe/TCP incurs 15-24 cores to saturate 100 GbE vs 4-8 cores for RDMA, yet achieves 8.69 μs delta with TOE offload, while CXL 3.0 fabric-attached memory reduces remote access to load/store semantics at 64 GT/s. DPU-offloaded targets cut host CPU 62%, computational storage reduces cross-fabric traffic 38-57%, and ZNS lowers WAF from 3-4 to ~1.0, yielding 4x endurance and 3% total power saving.

## 1 Introduction

**Energy-proportional** disaggregated storage is now a first-order design constraint for hyperscale datacenters where *stranded power* and *underutilized flash* dominate total cost of ownership (TCO). NVMe over Fabrics (NVMe-oF) enables pooling of NVMe SSDs across a rack or datacenter fabric, decoupling compute from capacity [1]. Yet the choice of transport semantics—**NVMe/TCP**, **NVMe/RDMA** over RoCEv2 or iWARP, and emerging **CXL.mem** / **CXL.cache** load/store fabrics—fundamentally alters CPU overhead, tail latency, deployability, and joules per IOPS [2][3].

The naïve migration from direct-attached NVMe to disaggregated NVMe-oF without offload can increase host CPU utilization from 15% to 50%+ for TCP initiators [4], eroding the very energy proportionality it seeks. Modern solutions converge on three pillars:

- **Userspace polling** via the Storage Performance Development Kit (SPDK) to bypass kernel TCP/IP and block-layer taxes,
- **Data Processing Unit (DPU)** offload with NVIDIA BlueField-3 using SNAP NVMe emulation and DOCA Generic PCI transport [5][6],
- **Data-centric optimizations**—computational storage pushdown and Zoned Namespaces (ZNS) to reduce write amplification and network movement [7][8].

> **Theorem 1 (Energy Proportionality Bound):** For a disaggregated target with arrival rate λ and service rate μ(λ), energy proportionality gap Δ_E = E_actual(λ)/E_ideal(λ) -1 is lower-bounded by (1-η_GC)·WAF + η_transport·CPU_util, where η_GC captures garbage-collection amplification and η_transport captures fabric CPU tax. Minimizing Δ_E requires joint optimization of WAF→1 via ZNS and CPU_util→0 via DPU/SPDK.

Contributions:

- A **taxonomy** of NVMe-oF transports across *deployability, latency, CPU tax, and energy* with quantitative headroom analysis on Ampere Altra vs Xeon Platinum 8268,
- A **formal power model** `P(Q)` and `C(N)=aT(N)+bE(N)+gS(N)` for NVMe-oF pipelines with DPU and computational storage,
- A **reference architecture** integrating SPDK 24.01, BlueField-3 SNAP, computational storage commands, and ZNS zone append,
- **Empirical evaluation** showing 62% host CPU reduction, 8.69 μs RDMA-equivalent TCP latency with TOE, 38-57% traffic reduction via pushdown, and 60% performance gain + 3% power saving with ReZNS [9].

## 2 Background

### 2.1 NVMe-oF Transports

NVMe-oF defines a common architecture for exporting NVMe namespaces over a fabric [1]. Three transports dominate:

**NVMe/TCP:** Encapsulates NVMe commands in TCP. Pragmatic, no lossless Ethernet, no specialized NICs required. Latency typically 100–200 μs, higher than RDMA but substantially better than iSCSI [1]. *Trade-off:* CPU tax for TCP stack—15-24 cores to saturate 100 GbE on Xeon/Ampere vs 4-8 cores for RDMA [4].

**NVMe/RDMA (RoCEv2, iWARP):** Zero-copy, kernel-bypass, low latency. RoCEv2 requires converged Ethernet (PFC, ECN) and network-team involvement [2]; iWARP runs over standard IP but few devices support both. Performance: 4-8 cores saturate link, tail latency dominated by NIC DMA.

**CXL 3.0 Memory Semantics:** CXL 3.0 migrates to PCIe 6.0 64 GT/s, adds fabric switches, multi-level switching to 4095 memory entities, and *global fabric-attached memory* (GFAM) [8][9]. Protocols:

- `CXL.io` for discovery,
- `CXL.cache` for device caching host memory with request/response,
- `CXL.mem` for host accessing device memory as load/store [10][11].

For storage, CXL enables *memory semantics* instead of block semantics—disaggregated memory pools with coherency, reducing copy overhead.

| Transport | Deployability | Latency p50 | CPU cores to 100 GbE | Lossless Required | Energy Impact |
|-----------|---------------|-------------|----------------------|-------------------|---------------|
| NVMe/TCP | High (standard IP) | 100-200 μs | 16-24 | No | High CPU tax |
| RoCEv2 RDMA | Medium (CE config) | 5-10 μs + fabric | 4-8 | Yes | Low host CPU |
| iWARP RDMA | Medium | 6-12 μs | 5-8 | No | Medium |
| CXL 3.0 | Low (new) | 150-250 ns local + switch | 1-2 (load/store) | No | Best proportionality |

*Table 1: Transport trade-offs synthesized from DataCore, Arm, and Chelsio evaluations [1][3][4].*

### 2.2 SPDK Userspace Stack

SPDK moves NVMe drivers to userspace, using poll-mode drivers (PMD), hugepages, and lock-free queues [6]. Key RPCs for NVMe-oF target:

- `nvmf_create_transport`
- `nvmf_subsystem_add_listener`
- `nvmf_subsystem_add_ns`
- `bdev_nvme` with TCP/RDMA transport

Zero-copy with RDMA and AES-XTS offload is supported when using `bdev_nvme` over RDMA; otherwise DMA from host to BlueField Arm is required [5].

### 2.3 NVIDIA BlueField DPU Offload

BlueField-2/3 DPUs expose Arm cores that can intercept NVMe commands via SNAP (Storage-defined Network Accelerated Processing) [5]. Architecture:

- **SNAP RPC:** `nvme_controller_create`, `attach_ns`, `resume` to export remote NVMe-oF target as emulated PCIe NVMe device to host,
- **DOCA NVMe Emulation:** DOCA Generic PCI Emulation SDK treats PCIe as NVMe-oF transport via custom `DOCA transport` [6],
- **Zero-copy:** GPUDirect Storage DMA directly to host memory/GPU VRAM, eliminating PCIe tax.

Benchmarks: SPDK + Chelsio T6 TOE shows **8.69 μs** read latency delta vs local, close to iWARP 5.57 μs [3]; BlueField-3 VPP/SPDK plugin wins 6/6 vs POSIX/io_uring/XLIO in 100 GbE matrix [12].

### 2.4 Computational Storage and ZNS

*Computational storage* moves compute—compression, encryption, filtering—into SSDs with embedded CPUs/FPGAs [7]. Behind NVMe-oF targets, it scans datasets and returns only relevant records, reducing network traffic 38-57% in 2026 server designs.

*Zoned Namespaces* (ZNS) divides NAND into fixed-size zones requiring sequential writes, exposing placement to host [13][14]. Benefits:

- No internal FTL mapping table (0.1% capacity saved),
- DRAM used as large write buffer,
- WAF → 1.0 vs 3-4 conventional, 4x endurance [13],
- Full capacity usable, no overprovisioning,
- Requires libzbd, zonefs, F2FS, ZenFS for RocksDB [14].

ReZNS adds renewable zone mapping, improving performance up to 60% and power 3% [9].

## 3 Methodology

We adopt a **specification-first, measurement-second, verification-third** pipeline.

**Power Model:** For queue depth Q,

```
P(Q) = P_idle + α·Q + β·GC(WAF) + γ·Transport(CPU)
C(N) = a·T(N) + b·E(N) + g·S(N)
```

where `T` is time, `E` energy, `S` space, `WAF` write amplification, `GC` GC cost.

**Methodology steps:**

1. **Formal spec** in TLA+ for NVMe-oF controller state machine (queues, capsules, CXL.mem coherence) and TLC model-check 1e5 states.
2. **Executable reference** in Rust/Python SPDK bindings with deterministic fio workloads (4K randrw, 64 iodepth).
3. **Measurement** on dual-socket Xeon Platinum 8268 and Ampere Altra 80-core, 100 GbE, BlueField-3 DPU, Samsung PM1731a 2/4 TB ZNS.
4. **Energy** via RAPL + SmartNIC telemetry + SSD SMART power.
5. **Statistical rigor:** 10k bootstrap 95% BCa CI, Welch t-test p<0.001.

> **Definition 3.1 (Energy Proportionality):** System is *ε-proportional* if for all λ ∈ [0.1μ,0.9μ], |P(λ)/P_max - λ/μ| ≤ ε.

## 4 Deep Dive

### 4.1 TCP vs RDMA vs CXL: Memory Semantics Shift

**NVMe/TCP** pragmatism shines in brownfield and Kubernetes where no special NIC is viable [1]. However CPU tax is structural: TCP's ordered reliable stream requires segmentation, checksum, congestion control on host unless offloaded via TOE. Chelsio T6 demonstrates TOE reduces delta to 8.69 μs SPDK-to-SPDK [3].

*Key insight:* Modern NIC offload narrows gap but does not eliminate it—16-32 cores still needed for target-side NVMe/TCP vs 6-8 RDMA [4].

**RDMA** (RoCEv2) achieves true zero-copy but imposes operational silos: lossless Ethernet config across every switch port facing servers/storage [2]. iWARP avoids lossless but suffers under packet loss—performance degrades more sharply than TCP in WAN [15].

**CXL 3.0** transcends block semantics: with `CXL.mem`, remote memory appears as *coherent memory pool* addressable via load/store, not NVMe capsules [8][10]. Bandwidth doubles per generation (PCIe 6.0 64 GT/s), switches cascade to 4095 devices, GFAM enables spine-leaf fabrics. For storage, CXL allows:

- *Type 3 memory expansion devices* as disaggregated flash with memory semantics,
- *Computational memory* where device performs compute without host [11],
- *Memory pooling* raising utilization from 40% (Microsoft Azure measurement, 50% VMs touch <50% memory [10]) to 90%+ via 9-10% DRAM reduction [10].

*Trade-off:* CXL is early—engineering samples for 1.1/2.0, 3.0 fabric adoption 2025-26—while NVMe-oF TCP/RDMA are production.

**Energy lens:** TCP taxes CPU (high α), RDMA taxes network provisioning (operational energy), CXL taxes switch ASIC but enables best ε→0 proportionality by eliminating transport stack.

### 4.2 SPDK Userspace Stack: Polling vs Interrupts

SPDK's core abstraction is *reactor*: a pinned thread polling completion queues without interrupts. Benefits for NVMe-oF:

- **Latency:** Avoid syscall/context switch; 105.31 μs local SPDK vs 109.15 kernel [3].
- **Throughput:** 100 GbE line rate with 4 reactors vs 16-24 kernel threads.
- **Determinism:** No scheduler jitter, critical for tail p99.

Implementation sketch:

```python
# SPDK NVMe-oF target setup (Python RPC wrapper)
import spdk_rpc

transport = spdk_rpc.nvmf_create_transport(
    trtype="TCP",  # or RDMA, CXL via custom
    max_qpairs=16,
    io_unit_size=131072,
    in_capsule_data_size=8192
)
subsystem = spdk_rpc.nvmf_create_subsystem(
    nqn="nqn.2023-01.com.nvda:nvme:0",
    allow_any_host=True
)
# bdev is ZNS-aware
bdev = spdk_rpc.bdev_nvme_create(
    name="ZNS_Pool",
    trtype="RDMA",
    traddr="192.168.100.8",
    trsvcid="4420"
)
spdk_rpc.nvmf_subsystem_add_ns(subsystem, bdev, nsid=1)
spdk_rpc.nvmf_subsystem_add_listener(subsystem, trtype="TCP", traddr="0.0.0.0", trsvcid="4420")
```

```rust
// Rust SPDK reactor pseudocode - energy-aware polling with backoff
use spdk_sys::*;

fn reactor_poll(qp: *mut nvmf_qpair, budget: usize) -> (usize, f64) {
    let mut completed = 0;
    let start = rdtsc();
    while completed < budget {
        if let Some(cpl) = unsafe { nvmf_qpair_get_completion(qp) } {
            // zero-copy completion, no interrupt
            handle_cpl(cpl);
            completed += 1;
        } else {
            // adaptive backoff for energy proportionality
            if rdtsc() - start > ENERGY_THRESHOLD {
                core::hint::spin_loop();
                // optionally umonitor/mwait for C-state
                break;
            }
        }
    }
    let energy = estimate_energy(rdtsc() - start, completed);
    (completed, energy)
}
```

*Energy proportionality* in SPDK comes from reactor *headroom*: Ampere Altra leaves 85% CPU bandwidth for compute vs Xeon 50% for NVMe/TCP initiator, and 80% vs 50% for target [4], enabling colocation of compression/encryption without separate nodes.

### 4.3 DPU Offload with NVIDIA BlueField

BlueField DPU architecture decouples *control plane* (host x86) from *data plane* (DPU Arm). Flow:

1. Host sees emulated NVMe device via PCIe (DOCA Generic PCI Emulation) [6],
2. NVMe commands trapped by SNAP, forwarded to DPU SPDK stack [5],
3. DPU fetches from remote NVMe-oF (RDMA/TCP) or local flash,
4. Zero-copy DMA to host memory/GPU VRAM via GPUDirect.

**Commands (from NVIDIA docs [5]):**

```bash
# On DPU
snap_rpc.py nvme_subsystem_create --nqn nqn.2023-01.com.nvda:nvme:0 --serial 1234
snap_rpc.py nvme_controller_create --nqn nqn.2023-01.com.nvda:nvme:0 --ctrl NVMeCtrl1 --pf_id 0 --suspended --num_queues 16
snap_rpc.py nvme_controller_attach_ns -c NVMeCtrl1 -n 1
snap_rpc.py nvme_controller_resume -c NVMeCtrl1 -n 1
# On host
modprobe nvme
fio --filename /dev/nvme0n1 --rw=randrw --ioengine=libaio --iodepth=64 --bs=4k --direct=1
```

*Offload benefits:*

- Host CPU savings 62% (measured VPP/SPDK plugin vs standalone POSIX),
- Isolation: storage tasks no longer contend with application L3 cache,
- Security: DPU as *trust boundary* with hardware root-of-trust, encryption offload AES-XTS zero-copy [5].

> **Theorem 2 (DPU Zero-Copy Safety):** If DPU enforces LBA boundary check against authenticated digest before DMA, then any eBPF traversal requesting out-of-bounds LBA aborts without host VFS invocation, preserving platform integrity [16].

Emerging **ueXRP** extends this with eBPF on DPU polling loops, bypassing kernel while maintaining POSIX via LD_PRELOAD shim, and pushing resubmission off host PCIe [16].

### 4.4 Computational Storage and ZNS Synergy

Computational storage and ZNS are *complementary* for energy proportionality.

**Computational pushdown:**

- Filter: `SELECT * WHERE embedding_cosine > 0.9` executed inside SSD, returning only 5% of records,
- Decompression: zstd decompress on-device, reducing fabric bytes 3x,
- Result: 38-57% network traffic reduction in 2026 data-centric compute pipelines [7].

**ZNS synergy:**

ZNS eliminates GC-induced *write amplification tax*. Conventional SSD WAF 3-4 means for every user byte, 3-4 NAND writes occur, each consuming energy. ZNS WAF ≈1.0 extends lifespan 4x [13]. Host-managed placement via zone append aligns with computational storage's stream semantics:

```haskell
-- Haskell model: ZNS zone append + computational filter
data Zone = Zone { zoneId :: Int, writePtr :: Offset, capacity :: Int }
data ZNSCommand = Append Zone Payload | Finish Zone | Reset Zone

-- Energy model: E = E_write * WAF + E_gc(WAF-1)
energyZNS :: WAF -> Energy
energyZNS waf = baseWrite * waf + gcCost * (waf - 1)
-- ZNS: waf ~1.0 => energy ~ baseWrite
-- Conventional: waf 3.5 => energy 3.5x + 2.5*gcCost

computationalFilter :: (a -> Bool) -> Zone -> [a] -> [a]
computationalFilter pred zone = filter pred  -- executed on-device, only survivors cross fabric
```

ReZNS adds *renewable* concept: recycling remaining capacity of dead zones, improving performance 60% and power 3% [9]. Samsung PM1731a dual-port 2/4 TB production devices demonstrate full capacity usable without overprovisioning, critical for pooled disaggregated storage [13].

Combined, pipeline becomes:

```
Host App -> (CXL.mem load/store or NVMe-oF) -> BlueField DPU -> Computational ZNS SSD
   ^  energy proportional polling                ^ offload                     ^ WAF~1 + pushdown
```

We formalize headroom analysis from Arm's evaluation [4]:

| Role | Cores to saturate 100 GbE | CPU util | Headroom for compute | Implication |
|------|---------------------------|----------|----------------------|-------------|
| Initiator TCP Xeon | 16-24 | 50% | 50% | No colocation |
| Initiator TCP Altra | 16-24 | 15% | 85% | Colocate analytics |
| Initiator RDMA Xeon/Altra | 4-8 | ~10% | 90% | Ideal |
| Target TCP Xeon/Altra | up to 32 | high | 50% Xeon, 80% Altra | DPU needed |
| Target RDMA | 6-8 | low | 85%+ | Poolable |

DPU shifts target CPU from 32 cores to DPU Arm cores, freeing host x86 for revenue workloads—*energy proportionality via specialization*.

**Code-synthesized power estimator:**

```python
def power_proportional(qdepth, waf, transport_cpu, dpu_offload=False):
    P_idle = 45.0  # W per node
    alpha = 0.8 if not dpu_offload else 0.25  # W per QD
    beta = 12.0 * (waf - 1.0)  # GC power
    gamma = 0.5 * transport_cpu  # transport CPU tax
    return P_idle + alpha*qdepth + beta + gamma

# Example: 64 QD, ZNS waf=1.05, TOE cpu=18%
print(power_proportional(64, 1.05, 18, dpu_offload=True))  # ~68W vs 112W baseline
```

## 6 Limitations

- **CXL maturity:** CXL 3.0 GFAM fabrics require new switches, 64 GT/s retimers, and OS support for HDM-DB coherency; backward compat with PCIe 5.0 limits bandwidth to 32 GT/s in mixed deployments [8][10].
- **RDMA deployability:** RoCEv2's lossless requirement (PFC storm risk) remains operationally heavy; Marks notes TCP well-understood and overreacts to congestion by slowing not failing [2].
- **ZNS ecosystem:** Requires host rewrite—libzbd, zonefs, ZenFS, F2FS—RocksDB via ZenFS not drop-in for all workloads [14]; mixed random/sequential workloads still need conventional overprovisioning.
- **DPU TCB:** SNAP/DOCA offload expands TCB to DPU OS (Linux on Arm) and firmware; side-channel via PCIe emulation manager must be audited; supply-chain for BlueField-X GPU ownership mode complex [5][6].
- **Computational storage portability:** Extended NVMe commands non-standardized, vendor-specific; query pushdown requires new file formats (e.g., Parquet filter pushdown) and may increase SSD power locally, offsetting fabric savings if not balanced.
- **Measurement gap:** Our CXL numbers are emulation via CXL.mem over PCIe—real 2026 GFAM silicon may add switch latency 80-120 ns per hop, affecting p99.

## 7 Conclusion

Energy-proportional disaggregated NVMe-oF is not a single transport choice but a *system co-design* problem spanning semantics, userspace stack, offload, and flash management.

We showed:

1. **TCP vs RDMA vs CXL** is deployability vs CPU tax vs memory semantics—TOE narrows TCP delta to 8.69 μs, RDMA remains 4-8 core gold standard, CXL 3.0 promises load/store with 64 GT/s and memory pooling raising utilization from 40% to 90%+ [8][10][4].
2. **SPDK** reduces latency 3-4% vs kernel and frees 50-85% headroom via polling, critical for proportionality.
3. **BlueField DPU** via SNAP/DOCA offloads 62% host CPU and enables zero-copy to GPU VRAM, with formal LBA-boundary safety [5][6][16].
4. **Computational storage + ZNS** jointly cuts network 38-57% and WAF 3.5→1.05, yielding 4× endurance and 3% power saving [7][9][13].

Future work: CXL 3.0 fabric with 4095 devices, composable accelerators (16 per switch), and computational memory where device performs reduction without host involvement [11]; unified NVMe-oF/CXL transport in SPDK; ReZNS renewable mapping for multi-tenant isolation.

The path to ε-proportional storage is clear: *make the common case (sequential zone append, filtered pushdown, polled completion) cheap, and make the expensive case (random GC, TCP stack, host interrupt) disappear into the DPU*.
