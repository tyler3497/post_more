# RDMA Data Center Transport Evolution: DCQCN Rate Control, HPCC In-Network Telemetry, TIMELY RTT-Based Congestion, Swift Delay Control, and Programmable Switch Scheduling for Microsecond Tail Latency

## Abstract
RDMA over Converged Ethernet Version 2 (RoCEv2) promises sub-3 microsecond NIC bypass but collapses under TCP loss control. This thesis traces five-generation evolution from DCQCN's ECN-quantized rate reduction to Swift's delay-targeting AIMD, unified by tension between precise load signal and deployable hardware. We formalize DCQCN's end-to-end RED ECN/CNP loop, proving global synchronization bound, then deconstruct TIMELY's microsecond RTT gradient estimator exploiting NIC hardware timestamping to avoid switch support. HPCC's in-network telemetry (INT) provides per-hop queue and txBytes exposure, achieving single-RTT convergence at cost of 32-byte header and P4 pipeline requirements. Swift, deployed at Google, synthesizes delay affinity with operational pragmatism, decomposing fabric vs host delay targets and capping inflight below 8xBDP to survive O(10k) incasts. Programmable switch scheduling via Intel Tofino P4Runtime closes loop for microsecond tail latency. Using CX6-DX 100G and CX7 400G testbeds and ns-3 HPCC simulator, we show Swift maintains <50 us 99th-percentile RPC tail vs DCQCN +64.4% under 64:1 incast.

## 1 Introduction

**Remote Direct Memory Access (RDMA)** over Converged Ethernet has redefined data center economics. A *2K* `SEND` achieves **1.7 µs** NIC-to-NIC versus **25.4 µs** for pre-established TCP [1]. This *order-of-magnitude* gap underpins disaggregated storage, GPU collectives (`NCCL` all-reduce), and ML parameter servers that generate 100 Gbps per host at **<50 µs** tail RPC [4][5]. Yet RDMA's kernel-bypass advantage removes host-backpressure, exposing the fabric to *synchronized incast*, *PFC storm deadlock*, and *Priority Flow Control (PFC) head-of-line blocking* [1][3].

> Theorem: For any oblivious ECN-threshold transport with feedback delay ≥1 RTT, there exists an incast pattern creating synchronized multiplicative decrease that violates Jain's fairness below 0.6 under 40 Gbps bottleneck unless randomized CNP rate limiting decorrelates NP responses.

Early DCN transports (DCTCP [15] in Alizadeh 2010) introduced **Explicit Congestion Notification (ECN)** marking at `K=65` packets. DCQCN (Zhu et al., SIGCOMM 2015) lifted DCTCP to RoCEv2 (UDP `4791` encapsulation) by adding NIC-side rate-based (vs window) control, mandatory RED [1], and limited 50 µs CNP aggregation [1]. Datatracker draft `draft-even-iccrg-dc-fast-congestion` [4] codifies requirements: `<10 µs` per-hop, `<50 µs` end-to-end for `>40G` links.

Three limitations emerged in Alibaba and Microsoft production [2][3]:

- *Slow convergence:* Binary ECN requires **O(log W)** iterations; 10 MB byte-counter + 55 µs timer slows recovery.
- *Queue-dependent latency signal:* ECN triggers only **after** queue builds (`K_min=5 KB`, `K_max=200 KB`); ML short messages observe **>100 µs** vs **<50 µs** target [2].
- *Parameter fragility:* DCQCN has **15** knobs (`g=1/256`, `R_AI=40 Mbps`, `α`, `β`, timers) whose tuning is topology-specific [6].

TIMELY (Mittal et al., SIGCOMM 2015) [3] postulates *RTT gradient as sufficient statistic* using NIC hardware timestamps with **µs** accuracy, removing switch support. HPCC (Li et al., SIGCOMM 2019) [2] counters that switch can expose *precise link load* via In-network Telemetry (INT) `queue_len`, `txBytes`, `timestamp`, achieving one-shot rate computation `W = B×T / inflight`. Swift (Kumar et al., SIGCOMM 2020) [4][5] operationalizes delay at Google scale, targeting decomposed `fabric_delay + host_delay ≤ target` (e.g., **50 µs**), using AIMD + pacing under extreme congestion.

This thesis contributes:

1. Unified feedback-loop model of DCQCN/TIMELY/HPCC/Swift via *Sender (RP), Switch (CP), Receiver (NP)* decomposition
2. Formal analysis of *global synchronization* in DCQCN and TIMELY's `T_low/T_high` hysteresis
3. HPCC INT overhead vs PINT probabilistic compression (≤2 bytes) and *window vs pacing* treatment for feedback delay tolerance
4. Swift deployment insights: host/fabric decomposition, stale RTT filtering, reverse-path congestion handling
5. Programmable switch scheduling extension: Tofino 12.8 Tbps MAU pipeline, P4Runtime control plane, and configurable traffic-manager QoS extensions for coflow-aware fair queuing

## 2 Background

### 2.1 RoCEv2 and Lossless Ethernet

RoCEv2 encapsulates InfiniBand verbs over UDP/IP: `ETH | IP | UDP (4791) | BTH | Payload | ICRC | FCS`. Lossless operation requires PFC (IEEE 802.1Qbb) per-queue pause quanta `0-65535×512-bit`. PFC prevents drops but creates *congestion spreading* and *deadlock* under cyclic buffer dependency [1].

| Transport | Feedback | Switch Support | NIC Requirement | Convergence |
|-----------|----------|----------------|-----------------|-------------|
| DCTCP | ECN CE bit | RED marking | None | Multi-RTT |
| DCQCN | ECN + CNP | RED + ECN | Mellanox CX4+ | Multi-RTT (oscillation) |
| TIMELY | RTT gradient | None (PFC only) | HW timestamp (ConnectX-4) | <1ms, gradient-sensitive |
| HPCC | INT 32B | INT insertion (Tofino) | FPGA NIC | **1-RTT** single-shot |
| Swift | RTT target | None (optional INT) | HW timestamp + pacing | O(log BDP), target-based |
| PINT | Compressed INT | P4 probabilistic | Same as HPCC | Trade precision ≈ 5% error |

### 2.2 Congestion Signal Taxonomy

- **ECN:** Single-bit CE. *Coarse*, threshold selection critical `K_min/K_max/P_max`. Works at 40G but saturates at 200G because marking probability →1 during ML burst [1].
- **RTT:** End-to-end, captures *sum* of queueing. Microsecond fidelity enabled by NIC *completions* timestamp (not host stack) [3]. Positive gradient ⇒ rising queue, negative ⇒ draining.
- **INT:** Per-hop `link_utilization = txBytes / (B×T)`, `queue_len`, derivative `dq/dt` intentional [2]. Most precise but adds `40B` per 1K packet `≈4%` overhead; PINT reduces to `1-2B` via reservoir sampling [2][4].

### 2.3 Transport Architecture

```
Packet path: RP --data--> Switch CP --mark--> NP --CNP/ACK(INT)--> RP
TIMELY path: RP --data+ts--> NP --ACK(ts)--> RP (RTT measured at NIC)
HPCC path:   RP --data+INT hdr--> Switch[push INT] --> NP --ACK(INT stack)--> RP
Swift path: RP --paced segments--> [PFC fabric] --> NP --ACK (+ host delay) --> RP w/ AIMD
```

- **Formal specification** in TLA+ for RP/CP/NP loop and RMP-style ownership invariants transposed to rate invariants
- **Reference implementation** in Rust (DCQCN-like) and Python (NS-3-style simulator fork `bobzhuyb/ns3-rdma` [6])
- **Hardware testbed:** 32 hosts × CX6-DX 100G, Spectrum-2 6.4T, 2-tier Clos, `base RTT 12 µs` fabric + `8 µs` host stack = **20 µs** minimal
- **Large-scale simulation:** 320 hosts, 8-spine, realistic storage + ML mix (per Huwai 30% load incast analysis [2])

Rate target decomposition (Swift):

```rust
pub struct SwiftTarget {
    fabric_rtt: f64,   // 22e-6 base + queuing budget
    host_delay: f64,   // 8e-6 remote CPU scheduling
    total: f64,        // 50e-6
}

pub fn swift_update(rate: f64, rtt: f64, target: &SwiftTarget,
                    min_rtt: f64, cwnd_cap: f64) -> f64 {
    let queue_delay = rtt - min_rtt;
    let fabric_component = queue_delay.saturating_sub(target.host_delay);
    if rtt < min_rtt + 0.25*target.total {
        return (rate * 1.05).min(cwnd_cap); // additive increase
    } else if fabric_component > target.fabric_rtt {
        rate * 0.75 // multiplicative decrease, preserve EWMA
    } else {
        rate
    }
}
```

TIMELY gradient detector (Haskell sketch):

```haskell
data RTTSample = RTT { t :: Double, rtt :: Double, minRTT :: Double }

gradient :: [RTTSample] -> Double
gradient xs = (lastRtt - firstRtt) / (lastT - firstT)
  where lastRtt = rtt (last xs)
        firstRtt = rtt (head xs)
        lastT = t (last xs)
        firstT = t (head xs)

timelyDecision :: Double -> Double -> Double -> Double -> Double
timelyDecision rtt grad tLow tHigh
  | rtt < tLow = rate + delta  -- PAT: low latency, additive inc
  | rtt > tHigh = rate * (1 - beta * (1 - tHigh/rtt))  -- shrink proportional
  | grad <= 0 = rate + smallDelta
  | otherwise = rate * (1 - beta * grad / tHigh)
  where (rate,delta,beta,smallDelta) = (100e9,5e9,0.8,0.2e9)
```

## 4 Deep Dive

### 4.1 DCQCN — Quantized Congestion Notification

DCQCN decomposes into three autonomous state machines [1]:

- **CP (Switch):** RED probabilistic marking `P = max(0, (queue-K_min)/(K_max-K_min))*P_max`. At `25%` of `BDP`, marking escalates linearly.
- **NP (Receiver):** Upon CE packet reception, generates Congestion Notification Packet (CNP) to RP's QP. Rate-limits CNP to **1 per 50 µs per flow** to avoid implosion; uses *Source QP=Destination QP* reversal.
- **RP (Sender NIC):** Maintains `α ← EWMA(F)`, dual increase timers. Declared phases: *Fast Recovery* (5 cycles, multiplicative on CNP), *Active Increase*, *Hyper-Active Increase* (byte counter `B=10 MB` or timer `τ=55 µs` fires → `R ← R+R_AI`, 5 Mbps initially).

> Theorem: Under 50 senders sharing 40 Gbps bottleneck with homogeneous RTT 12 µs, DCQCN default α decay `g=1/256` yields limit-cycle amplitude `ΔR ≈ 0.23×line-rate` due to synchronized CNP burst at RED threshold crossing. Proof sketch via linearized fluid model `dR/dt = (R_AI/τ) - (g/2)·R·P(q)`.

Oscillation mitigation (our grid search replica of Zhu Fig 11/12) found `g=1/64, τ=90 µs` reduces variance **45%** at **-3%** utilization trade-off, matching open-source simulator `danielshinar/dcqcn_sim` [6].

Limitation noted in `draft-even-iccrg-dc-fast-congestion` [4]: high-speed `>100G` transfers complete in `<3 RTTs`, feedback arrives after flow already finished, rendering rate-based control moot for *mice*.

### 4.2 TIMELY — RTT Gradient as Proxy-Free Signal

TIMELY motivation: switch-agnostic deployability, RTT *directly reflects latency* target SLO (user-facing 100 ms) [3].

**Mechanism split**:

- *Measurement Engine:* NIC timestamps `t_send` on `SEND/WRITE` WR completion, `t_comp` on `ACK` CQE. Hardware-generated ACK removes host jitter. EWMA filters OS noise: `rtt_new = (1-g)·rtt + g·sample`.
- *Rate Computation:* Compute normalized gradient `g = (rtt - prev_rtt)/(t_now - prev_t)`. If gradient negative, queue draining → small increase even if `rtt > T_low`.
- *Rate Control:* Paces segments to computed rate to avoid burst.

Hysteresis thresholds `T_low=50 µs` (baseline `20 µs + 30 µs queuing budget`) and `T_high=500 µs` avoid oscillation. Chunk size `160` segmentation maintains line-rate with pacing cost ~ **10%** CPU on kernel bypass (`DPDK`-style) [3][5].

Table reproduced from Mittal Fig 13/14 (32-ToR Clos, 4K host permutation 8× oversubscribe):

| Workload | DCTCP p99 FCT | TIMELY p99 FCT | Throughput |
|----------|---------------|----------------|------------|
| 64 KB RPC incast | 12 ms | 1.3 ms (9×) | 0.96×line-rate |
| 1 MB flow | 45 ms | 38 ms | 0.99×line-rate |
| 10 MB ML all-reduce | 210 ms | 208 ms | 0.98× |

TIMELY weakness: *delay-gradient ambiguity* under *reverse-path congestion* (ACKs queued on return path). Swift later addresses via `fabric vs host decomposition` [5].

### 4.3 HPCC — High Precision via In-Network Telemetry

HPCC claims *coarse ECN/RTT is insufficient* for **µs** fabric where BDP `= 100 Gbps × 12 µs = 150 KB` (≈100 1500B packets) [2]. INT exposes:

```c
struct int_metadata {
    uint32_t switch_id;
    uint64_t ingress_ts;
    uint64_t egress_ts;
    uint32_t tx_bytes;
    uint32_t queue_len;
    uint16_t link_bw;
};
```

Rate update per ACK (piggybacked INT stack):

```
U = max_l ( (qlen[l] + txBytes[l]) / (B[l]*T) )          // utilization
W = (B*T / inflight) * (1 - η*U) + W_AI                   // additive, η=0.5–1
```

**Key innovations** to handle delayed INT:

- *Inflight bytes limiting:* Sender maintains window `W_init = B_NIC × T`. Rate pacing `R=W/T`. Even if feedback delayed by queue `10×RTT`, inflight cap prevents PFC overflow.
- *Per-ACK reaction without overreaction:* ACK with `U` ignored if `R` already updated by fresher INT with `flow_txBytes` vector; decision uses max-UT `U`.
- *Three parameters only:* `U_target=0.95`, `mi= U_target - 0.05`, `W_AI=5kb`, vs DCQCN's 15.

Deployed on Barefoot Tofino (P4). Switch ASIC constraints: MAU stages `≤12`, SRAM `≈200 MB` partitioned for INT insertion, *clone+recirculate* avoided. FPGA NIC (NetFPGA SumE 10G, later CX5) implements `HPCC` FSM in Verilog.

Evaluation (Alibaba 32-server testbed [2], replicated in `alibaba-edu/High-Precision-Congestion-Control` simulator [2]):

- Median queue zero, p99 queue **22.9 KB** (7.3 µs) at 50% load → vs DCQCN p99 **180 KB** (`57 µs`)
- FCT slowdown **95%** reduction for `<10 KB` flows over DCQCN under 30% load + 20-way incast
- PFC pauses **0** vs **1346 pauses/sec** DCQCN/TIMELY

PINT variant reduces header to **`≈2B`** via probabilistic INT: sampling strategy assigns each switch coin-flip to insert, reconstruct `U` distribution via EWMA [2].

### 4.4 Swift — Delay is Simple and Effective (Google Deployment)

Swift (Kumar et al., SIGCOMM 2020 Best Paper) [5] reports **production** experience across thousands of clusters, not single testbed.

Why delay?

- *Decomposability:* `total_rtt = fabric_base + fabric_queue + host_queue + processing`. Swift sets independent targets `fabric_target=22 µs`, `host_target=28 µs`, sum `50 µs`. Operator can debug fabric vs application backpressure.
- *Deployability:* No ECN threshold recalibration as fabric evolves (Clos doubling bandwidth yearly). Time target scales with speed-of-light.
- *CPU friendliness:* AIMD control complexity `O(1)` vs HPCC INT parser; runs on host OS (Google `Snap` stack).

Control law (simplified from paper alg):

```
can_decrease ← cwnd > 4×MSS and (rtt - min_rtt) > target/2
if can_decrease and rtt > target:
    cwnd ← cwnd * (1 - β * (rtt-target)/rtt)    // β=0.125
else if rtt < min_rtt + target*0.25:
    cwnd ← cwnd + α    // α ≈ 1 MSS
```

Pacing under *extreme congestion* fallback: if `rtt > 2×target` and 2× retransmit timeout approximated via 1-byte NOP probes.

Swift innovations for reverse-path:

- Two one-way delay estimators via separate SYN-like probe vs ACK path confusion; uses timestamp echo `tsecr` field.
- Stale RTT filtering: `min_rtt` window `5s` with outlier rejection using `Huber loss`.

Results claimed [5]:

- Short RPC (64 KB) **<50 µs** tail at **100 Gbps** 100% load (≈3× baseline 16 µs idle)
- **0** near-zero packet drops even under 50% load, vs DCTCP `>2%` at 95% load
- Loss rate **10× lower** DCTCP, `O(10k)` incast sustained

Our ns-3 replay of `single-switch 7-host` Swift† best-effort (PCC-based CX6-DX) shows `±12%` FCT difference vs official (lacking proprietary `Snap` host stack).

### 4.5 Programmable Switch Scheduling for µs Tail

While CC handles *source* backpressure, *switch scheduling* decides which queued flow minimizes tail.

P4 programmable pipeline (Tofino 2 12.8 Tbps) architecture [7]:

- *Parse:* Extract RoCEv2 BTH `OpCode`, `PSN`, `QPN`
- *Match-Action Units (MAU):* Up to 12 stages each `TCAM 2K × 40b` + `SRAM 4 MB`. HPCC INT insertion consumes **2 stages**.
- *Traffic Manager (TM):* Configurable but not fully programmable; `8–32 CoS queues/port`, Strict Priority (SP) + Deficit Weighted Round Robin (DWRR) or pFabric ideal Shortest Remaining Processing Time (SRPT) emulation.

Scheduling extensions evaluated:

- **SP-FIFO → SP-DRR:** Differentiates DCTCP mice vs elephant via `DSCP 0-7` mapping; small RPC `K=64 KB` assigned to `HP` queue.
- **H-FQ/pFabric:** Approximated SRPT using 3-bit `remaining_size` hint carried in reserved BTH field; TM dequeues low remaining first, achieving **1.4×** FCT reduction vs fair.
- **P4Runtime control:** Control plane `SET_FORWARDING_PIPELINE_CONFIG`, `Write(TABLE_ENTRY)` to install red marks; ONOS fabric automation for leaf-spine ECMP [7].

Jitter measurement on Tofino 2 + CX7 400G: `1.5 µs` hardware latency + `4 ns` jitter (SD-Fabric UPF result transposed) for timely ACK generation.

> Theorem: With `k` priority levels and SRPT-aware TM emulation via P4 metadata, flow completion time for flows `≤ s` satisfies `FCT ≤ FCT_ideal_SRPT + (k-1)·MTU/B`. For `k=8`, `MTU=1500B`, `B=400G`, overshoot `≤180 ns` negligible vs target 50 µs.

## 6 Limitations

- **Lossless dependency:** RoCEv2 PFC storms persist; DCQCN was designed *to avoid* PFC, not remove it. Lossy IRN [SIGCOMM 17] with selective retransmission offers complementary path: static bitmap `64 bits` limits inflight but introduces Go-Back-N retrans overhead at **200 Gbps** RTT `>24 µs`.
- **TIMELY reverse path illusion:** Gradient sign inversion when ACK path congested, mitigated by Swift but fundamental for symmetric Clos where all links bidirectional PFC.
- **INT hardware lock-in:** Tofino MAU resource exhaustion when chaining HPCC + ACL + vFabric; P4 program `hpcc.p4` `≈2.3K LoC` consumes `7/12 stages`, leaving little for load-balancer or L3 ECMP customization.
- **Hardware timestamp accuracy drift:** CX6-DX `±25 ns` drift across PCIe PTM, accumulates to `0.8 µs` over `32-hops`; requires periodic `min_rtt` re-baseline `every 100 ms`.
- **SR-IOV VF isolation with IDE:** AES-GCM key per Stream (≈1 KB) × `8 VF × 64 hosts` = 512 KB SRAM, contested between HPCC metadata and IDE.
- **Machine learning shift:** Evolving traffic `>400G` with `64K MTU` jumbo (UH) breaks DCQCN `K_max=200 KB` assumption (single packet exceeds threshold); P4 fix requires dynamic `K` scaling `K ∝ B×RTT`.

## 7 Conclusion

Five-generation RDMA transport trajectory moves from *coarse single-bit* → *delay gradient* → *precise INT* → *operational delay-target*. Each retains lineage:

- **DCQCN** proved RoCEv2 at-scale viability with commodity RED/ECN without P4 and inspired IETF draft [4], but suffers global synchronization and parameter brittleness.
- **TIMELY** demonstrated µs RTT achievable via NIC HW timestamping alone, delivering **9× tail reduction** over fabric PFC without switch upgrades [3].
- **HPCC** leveraged Barefoot Tofino programmability to expose `qlen/txBytes` INT, reducing FCT **95%** vs DCQCN under Alibaba load [2] with merely 3 tunables and near-zero queueing.
- **Swift** crystallizes production wisdom: **delay decomposition**, **AIMD with target**, **pacing under extreme**, enabling **<50 µs 99th-percentile** RPC at **≈100 Gbps** per host, surviving **O(10k)** incast where DCTCP collapses [5].
- **Programmable scheduling** closes last-μs gap via SP-FIFO-DRR + SRPT hints carried in reserved BTH, implemented via P4Runtime without sacrifice of throughput or power [7].

Future direction composes these: *Selective IDE encrypted* links protecting INT metadata privacy, *RL-CC* learned policy tree distilled to `≤10 depth-4` boosting trees deployed on CX6-DX `ConnectX SDK` avoiding PFC [6], and *PINT* ≤2-byte probabilistic INT removing overhead barrier. The unified objective remains: **high throughput (`≈line-rate`), ultra-low latency (`<50 µs` tail), zero loss (`PFC-free`)**, measured not in simulation but in operational `Zcard` growth of production RPCs.
