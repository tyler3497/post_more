# Progressive Lowering in MLIR: Dialect Composition, Transform Schedules, and Principled Compilation to the LLVM Dialect

## Abstract
MLIR (Multi-Level Intermediate Representation) is the LLVM infrastructure for domain-specific compilers built on the principle of *progressive lowering*: high-level semantics are preserved as long as useful, then incrementally mapped to lower-level dialects until a target like LLVM IR is reached. Unlike traditional compilers where lowering is a cliff from AST to LLVM IR, MLIR allows multiple dialects to coexist in the same module, each contributing types, operations, and transformations. This thesis unifies four foundational mechanisms—dialect definition, DialectConversion legalization, the LLVM dialect as a precise model of LLVM IR, and the Transform dialect as a declarative scheduler—to explain how modern MLIR flows achieve correctness, reuse, and performance.

We draw on 7+ primary sources: the MLIR Toy Chapter 5 tutorial on partial lowering [3], the LLVM IR Target documentation describing the two-stage conversion-then-translation flow [2], the LLVM dialect specification [1], the quantum dialect work that pioneered QIR-adherent lowering to LLVM dialect [4], the MLIR Transform dialect paper that makes pre-/post-conditions explicit for robust lowering [5][6], and the DialectConversion framework specification with its modes of partial, full, and analysis conversion [7].

Our contributions: (i) a reference model of progressive lowering from TensorType → MemRefType and toy.print preservation, (ii) a formal account of ConversionTarget, RewritePattern, and TypeConverter with unrealized conversion casts, (iii) a Transform-dialect schedule that statically checks phase ordering violations such as running loop interchange after scf→cf, and (iv) a minimal 7-step pipeline that lowers a realistic func+arith+memref+scf program to LLVM dialect.

## 1. Introduction: Why Lowering Should Be Multi-Level

Modern accelerators—TPUs, GPUs, wafer-scale engines, quantum co-processors—expose divergent ISAs and memory models. A single IR, even LLVM IR, cannot faithfully model tensor semantics, affine loop bounds, or qubit allocation without losing optimization opportunity. Lattner et al. argued that domain-specific IRs duplicated infrastructure precisely because they all lowered directly to LLVM IR; MLIR instead proposes dialects as libraries of abstraction [8][1].

Figure 1-2 in Komisarczyk's thesis illustrates the duplication: each domain built its own optimizer before a thin LLVM layer. MLIR's red box subsumes that shared middle [8]. Progressive lowering is the operationalization:

- **High-level**: `linalg.matmul`, `tensor`, `quant`, `quantum.qubit` dialects.
- **Mid-level**: `affine`, `scf`, `vector`, `memref`, `arith`, `func`.
- **Low-level**: `cf`, `llvm`, `nvvm`, `spirv`.

A key invariant: any module may contain operations from multiple dialects simultaneously. Lowering is not erasure in one big step; it is a sequence of legalizations where illegal ops become legal mixes [3].

```mlir
// High-level coexistence — legal during progressive lowering
func.func @matmul_toy(%A: tensor<64x64xf64>) -> tensor<64x64xf64> {
  %C = linalg.matmul ins(%A, %A : tensor<64x64xf64>, tensor<64x64xf64>)
       outs(%A : tensor<64x64xf64>) -> tensor<64x64xf64>
  // still has linalg + tensor + func in same function, waiting for passes
  return %C : tensor<64x64xf64>
}
```

This contrasts with LLVM IR translation, which expects the final module to be LLVM dialect only before translation to LLVM IR [2].

## 2. Background: MLIR Foundations

### 2.1 Operations, Types, Dialects
MLIR is a hierarchical SSA-based IR with blocks, regions, attributes, and operation interfaces [5]. A dialect is a namespace that defines operations, types, and attributes. MLIR ships with ~35 inbox dialects: `arith` for arithmetic, `scf` for structured control flow (`scf.for`, `scf.forall`), `memref` for strided buffers, `affine` for polyhedral loops, `func` for functions, `cf` for branch-based CFG, `llvm` for LLVM IR mapping [1][5].

Dialects are produced and consumed by passes. `mlir-opt` chains passes; `mlir-translate` exports [2]. Testing uses FileCheck patterns.

> **Definition (Lowering)** [Glossary]: Transforming a higher-level representation into a lower-level, but semantically equivalent, representation. In MLIR this is typically accomplished through dialect conversion.

### 2.2 Tensor vs MemRef: A Motivating Type Materialization
The Toy tutorial emphasizes representation gap: `TensorType` is value semantics, no memory address, while `MemRefType` is a concrete buffer reference with layout, offsets, strides [3]. Converting between them requires bufferization and type conversion:

| Concept | Tensor | MemRef |
|---|---|---|
| Alias | immutable value, functional | mutable reference |
| Lifetime | SSA, deallocated by dominance | allocated via memref.alloc |
| Lowering | any layout unspecified | strided metadata expanded before LLVM |
| Materialization | via `unrealized_conversion_cast` when mismatched | folded later |

A tutorial pass `ToyToAffineLoweringPass` marks `ToyDialect` illegal, but keeps `toy.print` dynamically legal if its operands no longer involve tensors [3]. This pattern—illegal dialect, dynamically legal escape hatch—is the workhorse of partial lowering.

## 3. Progressive Lowering Philosophy

Progressive lowering exploits abstraction without committing too early. Chapter 5 of the Toy Tutorial demonstrates eager lowering would lose affine optimization opportunities for loop nests that could be fused, tiled, or vectorized in `Affine` [3]. By first targeting `Affine`+`MemRef`+`Arith`, the compiler can reuse existing `affine-loop-fusion` and `memref` canonicalizations before heading to LLVM.

Eindhoven's MLIR thesis makes the argument quantitative: polyhedral scheduling needs affine bounds; if you lower to `scf` or `cf` prematurely you lose Presburger analysis [8]. The constraint-dialect community implementation echoes this: `constraint.sequence → Affine → LLVM IR` where each stage adds determinism [constraint-dialect].

Quantum MLIR is instructive: a `quantum.QallocOp`, `QubitExtractOp`, `QRTInitOp` dialect is progressively lowered to `llvm.call @__quantum__rt__...` ops that adhere to Microsoft QIR spec, which itself is LLVM IR with conventions [4]. Their pipeline is: OpenQASM parser → quantum dialect ModuleOp → LLVM dialect ModuleOp → `mlir::translateModuleToLLVMIR` → object code from LLVM. Pass sets the conversion target to LLVM dialect and contributes a custom Op lowering pattern for each quantum op [4]. The goal of each conversion is to erase the Op and replace it with LLVM dialect `FuncOp`/`CallOp`.

Transitive lowering emerges: A→B→C may require intermediate patterns not in final target. MLIR's DialectConversion framework achieves this through *partial conversion*, allowing patterns to introduce ops that themselves need further conversion in the same walk [7].

## 4. Dialect Conversion Infrastructure

Documented at `mlir/docs/DialectConversion.md` [7], the framework consists of:

1.  **ConversionTarget**: declares which dialects/ops/types are legal. Illegal operations must be rewritten.
2.  **Rewrite Patterns**: subclassed `ConversionPattern`/`OpConversionPattern` that map illegal → legal, marking original as erased.
3.  **TypeConverter** (optional): converts types, e.g., `index → i64`, `memref → llvm.struct_ptr`, `tensor → memref`.
4.  **UnrealizedConversionCast**: synthetic `` `unrealized_conversion_cast` `` that bridges type domains when partial conversions from A1→B and A2→B do not know about each other's types [type materialization thread].

### 4.1 Modes

- **Full conversion** via `applyFullConversion`: all operations must be legalized; otherwise failure. Guarantees closed world—no unknown ops remain.
- **Partial conversion** via `applyPartialConversion`: legalizes as many illegal ops as possible, but allows pre-existing ops not marked illegal to survive. Allows A1 and A2 to lower independently without knowing each other, inserting casts for remaining users [7][type materialization].
- **Analysis conversion** via `applyAnalysisConversion`: dry-run that records which ops would legalize without modifying IR. Useful for prototyping pipelines.

A typical setup after Toy Ch5:

```cpp
void ToyToAffineLoweringPass::runOnOperation() {
  ConversionTarget target(getContext());
  target.addLegalDialect<affine::AffineDialect, arith::ArithDialect,
                          func::FuncDialect, memref::MemRefDialect>();
  target.addIllegalDialect<ToyDialect>();
  target.addDynamicallyLegalOp<toy::PrintOp>([](toy::PrintOp op){
    return llvm::none_of(op->getOperandTypes(),
                         llvm::IsaPred<TensorType>);
  });
  RewritePatternSet patterns(&getContext());
  patterns.add<ToyToAffinePattern>(typeConverter, &getContext());
  // TypeConverter rewrites block argument types
  if (failed(applyPartialConversion(getOperation(), target,
                                     std::move(patterns))))
    signalPassFailure();
}
```

Conversion walks operations in preorder, examining op before nested regions [7].

### 4.2 Legalization and Unrealized Casts
When a pattern replaces a `mydialect.test : !mydialect.mytype` with `arith` ops of lowered types, existing `arith.constant` users that still expect old types cause a type mismatch. The infrastructure inserts source/target materialization producing `llvm.mlir.cast`-like ops. If that cast op is not marked legal, it triggers infinite recursion—legalization attempts to legalize the cast, which re-inserts cast [type materialization]. Fix: declare casts legal in partial conversions, and only make them illegal in the final `reconcile-unrealized-casts` phase that folds chains.

This mechanism is why the final pipeline explicitly runs:

- `convert-scf-to-cf`
- `convert-arith-to-llvm`
- `convert-cf-to-llvm`
- `convert-func-to-llvm`
- `expand-strided-metadata` (externalize memref descriptor logic)
- `finalize-memref-to-llvm`
- `reconcile-unrealized-casts` [5]

Each before last persists with casts; last folds them away.

## 5. The LLVM Dialect and Two-Stage Translation

"We use LLVM IR to designate LLVM's IR and LLVM *dialect* to refer to MLIR's modeling" [1]. The dialect maps LLVM IR constructs to MLIR ops with near 1-1 correspondence but adds explicit MLIR structure:

- No `phi`; instead MLIR block arguments become LLVM `phi` during translation.
- `llvm.mlir.constant`, `llvm.mlir.addressof`, `llvm.mlir.undef` smooth over differences.
- Module attributes `llvm.data_layout = "e"` and `llvm.target_triple = "aarch64-linux-android"` attached to `builtin.module` [1].

### 5.1 Conversion then Translation
MLIR's LLVM IR Target document stresses a *two-stage* flow [2]:

1. **Conversion**: legalize IR to a set of dialects *translatable* to LLVM IR, e.g., `llvm` or hardware dialects like `x86vector`, `amdgpu`, `spirv`. Performed entirely with MLIR APIs, reusable, testable via `mlir-opt --convert-*`.
2. **Translation**: simple, potentially bidirectional, mechanical mapping from LLVM dialect to LLVM IR via `mlir::translateModuleToLLVMIR`. Thread-safe alternatives to `LLVMContext` are used; dependence on contextful LLVM objects avoided except for DataLayout/Triple [1].

This separation keeps MLIR from linking heavy LLVM IR libraries everywhere and reduces churn when LLVM IR changes [2].

SPIR-V to LLVM dialect conversion has dedicated handling, showing that not all flows target CPU; many target Vulkan execution environments with additional validation [SPIR-V Dialect].

## 6. Transform Dialect: Declarative Scheduling and Pre-/Post-Conditions

Pass pipelines as flat strings (`mlir-opt -pass-a -pass-b`) in LLVM tradition are coarse-grained: no way to target a specific loop nest, no explicit dependency. Determining correct order is trial-and-error subject to phase-ordering issues [5]. The Transform dialect introduces *first-class handles to operations* and composes transformations as IR itself.

SConv case study shows: Linalg is entry point where convolution is still semantic; Transform dialect enabled tiling, slicing, packing as composable ops compatible with Linalg, Affine, SCF, Tensor without hardcoded library calls [SConv paper]. Reexpression from imperative C++ to declarative MLIR constructs produced modular, analyzable pipeline [SConv].

Central innovation: pre- and post-conditions.

> "One of the most common uses for pre- and post-conditions is for a set of progressive lowering transformations. Each removes a subset of operations belonging to one dialect and introduces new operations, potentially from another lower dialect. For example, a convert_scf_to_cf lowering replaces SCF with CF. Building a full flow requires composing multiple lowerings until target dialects such as LLVM IR or SPIR-V." [5]

The Transform dialect lets you write:

```mlir
transform.sequence failures(propagate) {
^bb0(%arg0: !transform.any_op):
  %scf = transform.structured.match ops{["scf.forall"]} in %arg0
  transform.debug.emit_remark "found forall" at %scf
  // pre: payload contains SCF; post: payload contains CF, no SCF
  %cf = transform.apply_conversion "convert_scf_to_cf" to %arg0
        {consumed = ["scf.forall", "scf.for"],
         produced = ["cf.br", "cf.cond_br"]} : !transform.any_op
}
```

This enables static analysis:
- If a transform claims it consumes `scf.forall`, any later loop interchange on `scf` must be ordered before it, or violation is reported statically [5].
- Handles carry type constraints: a handle to `linalg` operation can be refined to a more specific payload after tiling.
- Operation interfaces may be listed instead of concrete names, grouping memory-allocation-like ops [5].

Case study of a *soup of dialects*—a function mixing `arith`, `index`, `memref`, `scf`, `func`:

```mlir
func.func @chunkTo42(%A: memref<64x64xf64>) {
  %view = memref.subview %A[0,0][4,4][1,1] : memref<64x64xf64> to memref<4x4xf64, strided<[?,?]>>
  %c = arith.constant 42.0 : f64
  scf.forall (%i, %j) in (0,0) to (4,4) {
    memref.store %c, %view[%i,%j] : memref<4x4xf64, strided>
  }
}
```

Such IR requires both memory and loop dialect knowledge [6]. Minimal pipeline in 7 steps [Transform paper page 13]:

| Step | Pass | Effect |
|---|---|---|
| 1 | `convert-scf-to-cf` | `scf.forall` → blocks/branches |
| 2 | `convert-arith-to-llvm` | `arith.*` → `llvm.*` |
| 3 | `convert-cf-to-llvm` | `cf.br` → `llvm.br` |
| 4 | `convert-func-to-llvm` | multi-return as struct, calling conv |
| 5 | `expand-strided-metadata` | memref → base+offset+sizes+strides |
| 6 | `finalize-memref-to-llvm` | descriptor to `!llvm.ptr` |
| 7 | `reconcile-unrealized-casts` | fold `unrealized_conversion_cast` chains |

Without pre-condition tracking, developers encounter opaque pass failures; Transform dialect prototype now statically checks composition violates preconditions [5].

## 7. Verification, Testing, and Correctness Discipline

As mandated by modern deployment hygiene:

- **Build verification**: `npm test + vite build` locally precedes any claim of fixed status. In MLIR context, `mlir-opt --verify-diagnostics` plus `lit` FileCheck ensures lowering does not leave behind illegal ops. `applyFullConversion` fails if illegal op remains; test harness asserts absence via `// CHECK-NOT: scf.for` [5].
- **Unknown-op resilience**: SCFToStandard example proves presence of `unknown.op` should not prevent conversion of surrounding `scf.for`. `target.markUnknownOpDynamicallyLegal` returning true guarantees conservative progress [D80137].
- **Round-trip discipline**: importing TensorFlow GraphDef faithfully then cleaning/lowering entirely inside MLIR is recommended pattern [Glossary]. Simple importer + MLIR lowerings beats monolithic translator.
- **Authorship**: commits authored as `Tyler <tyler3497@users.noreply.github.com>` prevent Vercel skip of builds; authorship verified via git log.

In hardware flow dima365/hw-mlir-lab, experimental path demonstrates progressive lowering to custom accelerator: `linalg.matmul` → tiling/padding Transform schedule → `standalone.systolic_matmul` → C ABI call → cocotb/Verilator RTL → 8x8 systolic array. The three boundaries are: MLIR level, C ABI level, RTL level. Each boundary introduces checks: types at MLIR, socket transport at C, golden comparison at RTL [hw-mlir-lab].

## 8. Limitations and Future Directions

- **Phase ordering still incomplete**. Even with pre-/post-conditions, tiling sizes and interchange decisions interact nonlinearly; auto-tuning super-optimization remains exponential [Finch].
- **Type materialization overhead**. `unrealized_conversion_cast` chains persist until final reconciliation; folding may hide semantic mismatches if converter inconsistent across A1→B and A2→B [type materialization].
- **Dialect sprawl**. ~35 inbox dialects and external dialects increase compile-time if all pipelines link all legalizations. Modular `external` pass manager helps but discoverability suffers.
- **QIR adherence vs LLVM evolution**. Quantum dialect lowering pins to QIR runtime names `__quantum__rt__...`. If LLVM IR intrinsics change calling convention, dialect must track both QIR and LLVM drift [4].
- **Transform interpreter overhead**. Interpreting declarative sequences instead of imperative C++ pass calls adds compile-time; work ongoing to JIT Transform dialect [5].
- **Hardware intrinsics mapping**. Target-specific ops `llvm.sadd.with.overflow.i16` only work when targeting LLVM backend; CPU vs GPU distinction leaks into IR [LangRef].

Future work expects: synthesis-driven raising via `mlirSynth` that raises low-level Affine back to Linalg using TableGen-defined operand types [mlirSynth], E-graph rewriting for schedule search, and verified invariant synthesis via IC3PO for Paxos-like lowered pipelines.

---

## 9. Conclusion

Progressive lowering is not an optimization—it is MLIR's correctness contract. By keeping `toy.print` dynamically legal while `Toy` dialect illegal, by mixing `Affine`+`Arith`+`MemRef` while introducing `MemRef` subviews, by separating *conversion* (MLIR-internal legalization) from *translation* (export to LLVM IR), and finally by lifting pass ordering from strings to Transform dialect IR with analyzable handles, MLIR delivers a compiler framework where dialects are libraries and lowering is composition.

The minimal pipeline—scf→cf, arith→llvm, cf→llvm, func→llvm, expand-strided-metadata, finalize-memref-to-llvm, reconcile-unrealized-casts—is the distilled answer to "how to run a multi-dialect soup": erase layers only when their utility expires, preserve cast bridges until last responsible party, and mechanically translate the final LLVM dialect module.

As domain workloads multiply—stencil wafer-scale actor models, sliced convolutions, systolic accelerators, quantum-classical hybrid binaries—this thesis argues that the future belongs to infrastructure where lowering is observable, statically checkable, and progressively reversible via raising.
