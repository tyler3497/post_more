# io_uring and Kernel-Bypass I/O: A Rigorous Analysis of Shared-Ring Asynchronous Interfaces for High-Performance Storage and Networking

## 1. Introduction

Linux asynchronous I/O was long a study in compromise: POSIX AIO hid a thread pool, Linux AIO served only O_DIRECT files, and epoll — a readiness notifier, not an async interface — still paid a syscall per operation. In 2019, Jens Axboe's io_uring (Linux 5.1) replaced the trap-per-operation contract with two lock-free shared rings: a submission queue (SQ) the application fills and a completion queue (CQ) the kernel fills, both mmap'd after a single setup call. With SQPOLL, even submission needs no syscall. This thesis gives a rigorous account of that architecture: the SQ/CQ memory-ordering contract, fixed files and buffers that remove per-I/O lookup and page-pinning taxes, multishot accept/recv, and zero-copy send/receive paths converging with device-memory TCP. It compares io_uring analytically against epoll, Linux AIO, and SPDK/DPDK kernel bypass, models the syscall-elimination break-even, examines the security surface — personalities, opcode restrictions, the seccomp dilemma — and surveys production adoption. The conclusion: io_uring is the tier-one substrate for high-performance I/O, with full bypass reserved for workloads that can measure the remaining microseconds.

## 2. Background

### 2.1 The pre-io_uring landscape

Classical UNIX I/O is *completion-synchronous*: `read(2)` traps into the kernel, the task sleeps, and control returns only when data is available. Three async strategies emerged, each deficient:

- **POSIX AIO** (`aio_read`/`aio_write`): in glibc, implemented atop a userspace thread pool — asynchronous only in the colloquial sense, with thread-per-operation scaling pathologies [6].
- **Linux AIO** (`io_setup`/`io_submit`/`io_getevents`): true kernel async, but restricted in practice to `O_DIRECT` file access, without network socket support, and still requiring a syscall per batch submission with per-iocb copy overhead [2].
- **`epoll`**: a readiness notification facility, not an async I/O interface. The event loop learns a socket is readable, then issues `recv(2)` — itself a syscall — per ready descriptor. The *notification* is async; the *I/O* is not.

The fundamental cost model is the syscall itself: a context switch into ring 0 costs on the order of 100–200 ns on contemporary x86-64, plus indirect costs (TLB/cache pollution, Spectre/Meltdown mitigation overheads). At one million IOPS, one syscall per operation consumes roughly 10–20% of a core before any useful work occurs — and networking workloads with `epoll_wait` + `accept` + `recv` + `send` routinely spend *four or more* syscalls per request [6].

### 2.2 Design goals of io_uring

Axboe's design paper articulates four goals: **broad operation coverage** (not just storage), **efficiency** (amortize or eliminate syscalls), **low latency** (polling modes), and **scalability** (per-core rings, no global locks) [1][5]. The interface is *completion-oriented* like Windows IOCP rather than readiness-oriented like `epoll`: the application describes the desired end state, and the kernel reports completion, eliminating the readiness-then-act round trip.

### 2.3 The two-ring architecture

Three shared memory regions are established by `io_uring_setup(2)` and mapped with `mmap` [3]:

1. The **SQ ring** — an array of indices plus head/tail counters. Userspace is the sole producer; the kernel is the sole consumer.
2. The **SQE array** — the actual 64-byte submission entries (128 bytes with `IORING_SETUP_SQE128`), indexed indirectly through the SQ ring.
3. The **CQ ring** — an array of 16-byte completion entries; the kernel produces, userspace consumes.

> **Theorem (Single-producer/single-consumer safety).** If exactly one agent writes the SQ tail and exactly one agent writes the CQ tail, and all cross-agent visibility is ordered by acquire/release semantics on the head/tail counters, then the rings are linearizable without locks.
> *Proof sketch.* The producer writes the payload (SQE) *before* publishing the tail with release ordering; the consumer reads the tail with acquire ordering *before* reading the payload. This is the classic Dekker-free publication pattern. The indirection array for the SQ permits the kernel to consume entries in an order it chooses (e.g., for linked SQE chains via `IOSQE_IO_LINK`) without reordering the userspace-visible ring [3]. ∎

Memory ordering is the contract's sharp edge: the man page documents the exact barrier discipline, and `liburing` encapsulates it [3][4].

## 3. Methodology

This thesis proceeds by **architectural analysis** (Sections 2–4), an **analytical cost model** calibrated against published measurements (Section 5), and a **security and adoption survey** (Sections 4.5, 6). The cost model is parameterized as follows:

| Symbol | Meaning | Typical value |
|---|---|---|
| *t_sc* | One syscall round-trip (user→kernel→user) | 100–200 ns |
| *t_cq* | CQ poll + CQE parse, no syscall | 10–30 ns |
| *t_dev* | Device service time, 4 KiB NVMe read | 10–20 µs |
| *B* | Batch size (SQEs per `io_uring_enter`) | 1–1024 |
| *N* | Requests per network transaction (syscalls in epoll model) | 3–5 |

Reported hardware figures are drawn from the cited primary sources — Axboe's design document [5], the `io_uring(7)` man page [3], the io_uring-vs-SPDK deployment analysis [7], and the zero-copy networking work [8] — and all derived numbers are labeled as model outputs rather than laboratory measurements.

## 4. Deep Dive

### 4.1 Submission and completion: the fast path in detail

Submitting an I/O request is a pure userspace sequence [3]:

```c
struct io_uring_sqe *sqe = io_uring_get_sqe(&ring);   /* no syscall */
io_uring_prep_readv(sqe, fd, &iov, 1, offset);        /* fill opcode, addr, len */
sqe->user_data = correlation_id;                      /* opaque tag echoed in CQE */
io_uring_submit(&ring);                               /* io_uring_enter(2): 1 syscall for B SQEs */
```

The SQE's key fields are `opcode` (e.g., `IORING_OP_READV`), `fd`, `addr`/`len`, `off`, `user_data`, and `flags` [3]. The kernel consumes entries from the SQ head, dispatches each to the appropriate subsystem (block layer, socket layer, VFS), and posts a CQE containing the echoed `user_data`, a `res` field with syscall-style semantics (bytes transferred or negative errno), and `flags` such as `IORING_CQE_F_BUFFER` (buffer selection) and `IORING_CQE_F_MORE` (multishot continuation) [2].

> **Theorem (Syscall amortization).** For a batch of *B* operations, the syscall cost per operation is *t_sc/B* in the default submission mode and *0* in SQPOLL mode, versus *t_sc* per operation for synchronous syscalls.
> *Proof.* `io_uring_enter(2)` submits the entire pending SQ range in one trap; the per-operation share is the quotient. In SQPOLL mode a kernel thread polls the SQ, so no trap occurs on the submit path at all [3][6]. ∎

Completion polling has three modes: interrupt-driven CQ (default, minimal CPU), `IORING_SETUP_IOPOLL` (busy-poll the device CQ, lowest latency for NVMe), and userspace CQ polling (`io_uring_peek_cqe`). The right choice is workload-dependent — busy-polling burns a core, a cost the model in Section 5 accounts for.

### 4.2 Fixed files and fixed buffers: removing the per-I/O lookup taxes

Two per-operation costs survive ring submission: **file table lookup** (`fd` → `struct file`) and **buffer mapping** (pinning userspace pages for DMA). io_uring attacks both with *registration*:

- **`io_uring_register(IORING_REGISTER_FILES)`** installs a dense array of `struct file *` at setup; SQEs then carry a small index with `IOSQE_FIXED_FILE` instead of an fd, replacing an RCU-protected file-table walk (and its refcounting) with a single array indirection [2][4].
- **`io_uring_register(IORING_REGISTER_BUFFERS)`** pre-pins and maps userspace memory; `IORING_OP_READ_FIXED`/`WRITE_FIXED` reference buffers by index, eliminating `get_user_pages` pinning, page-table walks, and scatter-gather construction on the hot path [2].

The performance consequence is qualitative, not merely quantitative: pinning cost is *O(number of pages)* and highly variable (page faults, THP splits), so fixed buffers convert a variable-latency path into a constant one — the single largest contributor to tail-latency reduction in storage workloads [5].

```rust
// tokio-uring style: registered resources reused across the ring's lifetime
let file = tokio_uring::fs::File::open(path).await?;
let buf = Vec::with_capacity(4096);          // registered once, pinned
let (res, buf) = file.read_fixed(buf, 0, 0).await?;  // buf index 0, no pinning
assert!(res.unwrap() == 4096);
```

### 4.3 Multishot operations: one SQE, many completions

Traditional `accept(2)` yields one connection per syscall; high-connection-rate servers loop on it. **Multishot** operations invert this: a single SQE arms a persistent kernel-side trigger that posts one CQE per event, each flagged `IORING_CQE_F_MORE` until the application cancels it [2].

| Multishot op | Kernel | Semantics |
|---|---|---|
| `IORING_OP_ACCEPT` (multishot) | 5.13+ | One CQE per inbound connection |
| `IORING_OP_RECV` / `RECVMSG` (multishot) | 5.18+ | One CQE per datagram/message |
| `IORING_OP_TIMEOUT` (multishot) | 5.19+ | Periodic timer CQEs |

Combined with **provided buffers** (`IORING_OP_PROVIDE_BUFFERS`, buffer rings since 5.13), multishot `recv` becomes a zero-syscall packet pump: the kernel selects a free buffer per datagram, posts the CQE with `IORING_CQE_F_BUFFER` indicating which buffer was used, and the application recycles it — no per-packet `recvmsg` syscall, no per-packet buffer management [2]. This is the mechanism that lets io_uring match or exceed `epoll`+`recvmmsg` networking throughput while issuing *no syscalls at all* in the steady state.

### 4.4 Zero-copy data paths: `send_zc`, `recv_zc`, and the road to device memory

Copying is the other great tax. A classic proxy `read`s from a socket into a userspace buffer (copy 1: kernel→user) and `write`s it onward (copy 2: user→kernel). io_uring provides:

- **`IORING_OP_SEND_ZC` / `RECV_ZC`** (5.19/6.0): zero-copy transmit/receive using DMA-mapped, notification-based buffer lifetime management. For send, the kernel notifies completion only when the NIC has finished with the pages, so userspace knows precisely when reuse is safe [8].
- **Registered fixed buffers** (Section 4.2): pin once, DMA directly between device and userspace — zero copies for storage I/O.
- **Device memory TCP** (`devmem TCP`, Google/Meta): the frontier — NIC DMA lands directly into device memory and io_uring's zero-copy receive path (`zcrx`) hands those pages to userspace without host-memory copies at all, work tracked against both the io_uring and SPDK trees [8].

The end state of this trajectory is a pipeline in which bytes traverse *disk → page cache/DMA buffer → NIC* without ever being copied by the CPU — the kernel-bypass ideal, achieved *within* the kernel's protection model rather than by abandoning it.

### 4.5 The security surface: personalities, opcode restrictions, and the seccomp problem

Powerful kernel interfaces widen attack surface, and io_uring's has been scrutinized intensely [9]. Three mechanisms constitute its security story:

1. **Personalities** — `io_uring_register(IORING_REGISTER_PERSONALITY)`: the ring can be bound to the credentials captured at registration time, so async work executes with a fixed, auditable identity rather than inheriting whatever credentials the submitting thread happens to hold when the kernel thread gets around to the SQE [3].

2. **Opcode restrictions** — `io_uring_register(IORING_REGISTER_RESTRICTIONS)`: the administrator or runtime can install an allowlist of permitted opcodes (and require features like SQPOLL), shrinking the reachable kernel code from the ring's ~60 opcodes to exactly the subset the application needs [3][9].

3. **The seccomp dilemma**: because SQEs describe operations that the kernel executes *without a syscall per operation*, classic syscall filters (`seccomp-bpf`) cannot mediate individual I/Os — the filter sees only `io_uring_setup`/`io_uring_enter`/`io_uring_register`. This is a genuine architectural tension: container runtimes that relied on seccomp syscall allowlists had to treat io_uring as a privileged capability, and several CVEs in io_uring's early years (use-after-free in cancellation paths, missing validation in `IORING_OP` handlers) prompted the restrictions API above as the principled answer [9]. The lesson generalizes: *any* batching interface defeats per-operation reference monitors; the mediation must move to the batch descriptor — which is precisely what the restrictions API does.

## 5. Empirical Results and Proofs

### 5.1 The syscall-elimination ledger

Consider a network proxy handling *R* requests/s, each requiring *N = 4* syscalls in the `epoll` model (`epoll_wait` amortized, `accept`, `recv`, `send`):

| Model | Syscalls per request | Syscall CPU at R = 10⁶ req/s (t_sc = 150 ns) |
|---|---|---|
| `epoll` + blocking I/O | 4 | 0.60 core |
| `epoll` + `sendfile` | 3 | 0.45 core |
| io_uring, batched (B = 32) | 4/32 ≈ 0.125 | 0.02 core |
| io_uring, SQPOLL + multishot | 0 | 0 (1 polling core) |

> **Theorem (Bypass threshold).** Let *C_poll* be the cost of dedicating a core to SQPOLL busy-waiting and *R·N·t_sc* the syscall cost of the interrupt-driven model. SQPOLL is strictly preferable iff *R·N·t_sc > C_poll* (modulo power and latency SLOs).
> *Proof.* Direct comparison of the two cost expressions; the inequality is the break-even point. For *N = 4*, *t_sc = 150 ns*, the threshold is *R ≈ 1.67×10⁶* req/s per core — i.e., SQPOLL wins only at very high connection churn, while batched submission wins essentially everywhere [5][7]. ∎

### 5.2 Storage: IOPS versus queue depth

Published analyses place io_uring 4 KiB random-read latency at **10–20 µs** on consumer NVMe versus **2–5 µs** for SPDK's polled userspace driver on the same hardware — the gap being interrupt and block-layer overhead that io_uring, as an in-kernel interface, cannot shed [7]. Throughput tells the complementary story: with `IORING_SETUP_IOPOLL` and fixed buffers, a single ring saturates high-end NVMe at multi-million IOPS, roughly **1.5–3×** Linux AIO and an order of magnitude above synchronous thread-pool I/O, because the submission path contains no per-operation syscall, no per-I/O thread wakeup, and no page pinning [5].

The queue-depth curve (Figure 4) exhibits the classic knee: linear scaling while the device is underfed, then saturation at the device's internal parallelism limit. io_uring's contribution is to move the *software* knee far to the right — the interface stops being the bottleneck, and the device becomes it.

### 5.3 io_uring versus full kernel bypass (SPDK/DPDK)

| Dimension | io_uring | SPDK / DPDK |
|---|---|---|
| Device access | Via kernel NVMe/net drivers | Userspace driver, VFIO/UIO rebind |
| Syscalls on hot path | 0 (SQPOLL) or 1/B | 0 (MMIO + busy poll) |
| Latency (4 KiB NVMe read) | 10–20 µs [7] | 2–5 µs [7] |
| CPU model | Interrupt or 1 poll thread | ≥1 dedicated poll core, always |
| Deployment | Any modern kernel, `liburing` | Hugepages, IOMMU, root, device unbind |
| Coexistence | Full: filesystem, other processes | Exclusive: device invisible to OS |
| Protection model | Kernel-mediated, restrictions API | None — process owns the hardware |

The synthesis emerging in industry is *tiered*: io_uring as the default high-performance path (no operational heroics), SPDK/DPDK reserved for workloads that can prove, by measurement, that the remaining 5–15 µs matters — exactly the decision discipline documented in production architecture reviews [7]. Notably, the two are converging: zero-copy receive work (`zcrx`/devmem TCP) is being developed against *both* trees, so io_uring applications will inherit NIC-to-userspace DMA without surrendering the kernel [8].

## 6. Limitations

No honest treatment omits the costs:

1. **Kernel version coupling.** Multishot accept needs 5.13, multishot recv 5.18, `send_zc` 6.0. "Linux 5.1+" is not a feature specification; applications must probe opcodes at runtime (`IORING_FEAT_*`, `io_uring_probe`) [2].
2. **Memory footprint.** Rings, registered files, and pinned buffers are allocated up front; a large SQ/CQ pair plus buffer pools can pin tens of megabytes — a poor trade for low-concurrency workloads.
3. **SQPOLL privilege and CPU.** SQPOLL threads historically required elevated privileges (since relaxed), and busy-polling always costs a core; misapplied, it converts a syscall saving into a power and noisy-neighbor regression [7].
4. **Debuggability.** Async completions decouple cause from effect across time; correlating a CQE `res = -EIO` with the guilty SQE requires disciplined `user_data` bookkeeping, and kernel-side failures are opaque to userspace profilers.
5. **Security posture.** The seccomp interaction (Section 4.5) remains a deployment consideration in hardened multi-tenant environments; the restrictions API mitigates but does not eliminate the review burden [9].

## 7. Conclusion

io_uring's contribution is best understood not as "faster syscalls" but as a **change of contract**: from *trap-per-operation* to *shared-memory batching*, from *readiness notification* to *completion reporting*, and from *per-I/O resource acquisition* to *registered, pinned, amortized resources*. The analytical results — syscall amortization (Theorem 4.1), the SQPOLL break-even threshold (Theorem 5.1), and the SPSC safety argument — show *why* the architecture wins rather than merely *that* it wins. Against `epoll` it eliminates the readiness round trip; against Linux AIO it generalizes to every operation class; against SPDK it trades the last microseconds of latency for deployability, coexistence, and a kernel-mediated protection model that the restrictions and personality APIs make auditable.

The trajectory points one way: zero-copy receive via device memory [8] will close much of the remaining gap to full bypass, leaving SPDK/DPDK as the specialist tool for workloads that can measure the difference — and io_uring as the substrate on which the next decade of high-performance I/O is built.
