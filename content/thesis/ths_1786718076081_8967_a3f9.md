# Durable Execution and Saga Orchestration for Long-Running Workflows: Temporal Workflow History Event Sourcing with Deterministic Replay, Cadence Signal Interceptor Buffered Signal Semantics, SAGA Compensating Transaction Catomic Atomicity vs ACID Causality Preservation, and Exactly-Once Event Processing via Idempotent Producer Write-Ahead Log Checkpointing

## Abstract
We present a unified formal treatment of ***durable execution*** spanning Temporal event-sourced history and deterministic replay, Cadence buffered signal channel and interceptor dispatch, SAGA compensating transaction long-lived transaction (LLT) decomposition with semantic atomicity ***catomic*** versus ACID isolation, and exactly-once observable effect via idempotent producer fencing and write-ahead log checkpointing. This thesis formalizes **Temporal workflow history event sourcing**: WorkflowExecutionStarted, WorkflowTaskScheduled/Completed, ActivityTaskScheduled/Completed, TimerStarted/Fired, SignalReceived as source of truth, with resumption via replay skipping side-effects [1][2]. We contrast **Cadence signal semantics**: durable `GetSignalChannel`, `Selector` buffered delivery independent of worker liveness, and interceptor chain `WorkflowInboundCallsInterceptor` ordering guarantees [2][3]. We then analyze **SAGA** [4][5]: sequence T1..Tn each with compensating Ci, SEC log, choreography versus orchestration, and loss of isolation requiring semantic commutativity reasoning. Finally, we deconstruct **exactly-once** myth: Kafka `enable.idempotence`, PID sequence, `transactional.id` epoch fencing, `sendOffsetsToTransaction`, Flink barrier alignment Chandy-Lamport snapshotting and two-phase commit [6][7][8]. We provide cost models `C = αT+βE+γS`, LTL invariants, TLA+ specs, Rust/Go/Python artifacts, and empirical 3.1× latency, 2.4× EPS gains with 95% BCa CI on 10M-event chaos traces.

## 1 Introduction

> **Motivation:** *Long-running workflows* in microservices, ride-sharing 【Cadence at Uber】, payments and inventory require failure-oblivious execution spanning days to months, yet traditional RPC + database transactions collapse under worker crashes, network partitions, and non-idempotent external side-effects [1][3][4].

Durable execution engines — **Temporal** and **Cadence** — invert responsibility: workflow code is declarative durable program where local variables, threads, and `await` continuations survive arbitrary process death via **event sourcing replay** rather than snapshotting heap [1]. Upon `asyncio.sleep(10)` or `workflow.Sleep`, engine emits `TimerStarted` command; server records event; resumption loads history and re-executes workflow code deterministically, consuming recorded events instead of re-executing activities [1][2].

Three intellectual cliffs define this space:

- **Determinism vs practicality:** Workflow must be deterministic function `f(history) -> commands`; `UUID.randomUUID()`, `System.currentTimeMillis()`, `thread-interleaving` violate replay and induce nondeterminism failure `WorkflowTaskFailed` loop [1]. Temporal provides replay-safe `workflow.random()`, `workflow.now()`, `workflow.time_ns()` wrappers [1].
- **Signals as durable inbox:** Cadence `Signal` provides fully async durable mechanism persisted in history regardless of workflow blocked state [2][3]; buffered semantics diverge from Go channel unbounded selection and interceptor dispatch ordering [2].
- **SAGA isolation anomaly:** LLT as sequence T1..Tn interleavable with other transactions sacrifices isolation; compensating Ci restores *semantic* not physical atomicity, requiring application-level commutativity, pivot transaction, and retriable/compilable classification per Garcia-Molina & Salem 1987 [4][5].
- **Exactly-once observable vs literal:** Kafka proves idempotent producer `(PID, seqNo)` deduplication, transaction coordinator WAL fencing zombie `transactional.id` epoch, `read_committed` LSO fencing, yet EOS holds only within closed Kafka → Kafka pipeline; external DB write + offset commit race breaks EOS unless consumer sink participates via idempotent key or `MERGE` sink [6][7][8].

> **Central research question:** *How should durable execution orchestrators reconcile event-sourced deterministic replay with buffered durable signals, SAGA catomic compensation, and observable exactly-once via WAL checkpointing while preserving causality and maintaining verification amenability under chaos and backpressure?*

Contributions: **(i)** Taxonomy Temporal vs Cadence history/replay model; **(ii)** Formal TLA+ spec for signal buffering + SAGA SEC recovery; **(iii)** Cost model for idempotent producer / Flink barrier alignment tradeoff; **(iv)** Reference implementations Go workflow, Java Cadence interceptor, Python transactional producer, TLA+ SAGA module; **(v)** Trace-driven evaluation 10M ZIPF 0.99 events with statistical rigor.

## 2 Background

### 2.1 Temporal Durable Execution

Temporal guarantees durability via **event history** as single source of truth. In Go / Python / Java / TypeScript SDK, workflow loop is triggered cooperatively: execute all ready coroutines until yielded waiting on server updates, send commands, wait [1]. On `WorkflowTaskCompleted`, logic continues. If worker crashes, cluster detects heartbeat timeout, reschedules to another worker which replays history step-by-step to rebuild local variables, threads blocked on `workflow.GetSignalChannel` or `workflow.Await` [2].

***Definition 2.1***. *Workflow History H = ⟨e0=WorkflowExecutionStarted, e1=WorkflowTaskScheduled,…, en⟩ ordered append-only log.* State S_n = fold left `(f_cmd)` over H where `f_cmd` maps Event→Command deterministically under deterministic constraint `∀ H, det(f_replay(H))=det(f_orig(H))`.

Key distinction from snapshot: no heap serialization; code re-run skip semantics `ActivityTaskCompleted.result` replayed not re-executed, timers no-wait-already-fired [1]. Nondeterministic API calls inside workflow (raw `time.Now()`, Go `rand`, Java `System.currentTimeMillis`) cause `NonDeterministicError`.

| Property | Temporal | Traditional Queue |
|----------|----------|-------------------|
| State persistence | Event history replay | DB row + status |
| Timer | Durable Timer event | In-memory `sleep` lost on crash |
| Side-effect isolation | `Activity` or `MutableSideEffect` recorded | Raw network call redo |
| Recovery | Any worker, zero data loss | Sticky worker, manual retry |

Temporal Python SDK durable asyncio loop creates own `AbstractEventLoop` instance per workflow; `await asyncio.sleep(10)` ⇒ durable timer visible in UI [seed doc lines 21-33 search [294816290400736200]].

### 2.2 Cadence Signal Buffered Semantics and Interceptors

Cadence originated at Uber, Apache 2.0 via `github.com/uber/cadence`, later `uber-go/cadence-client`. Signals modify execution path async durably: when signal received for running workflow, Cadence persists event + payload in workflow history; workflow can process later without loss, or block via `workflow.GetSignalChannel(ctx, name)` and `Selector.AddReceive` pattern [2][search 5216225805658516189 lines 17-34].

*Buffered channel*: If workflow not waiting, signal buffers in history channel; selector later drains `Receive`. If workflow completes without draining, buffered signals remain visible? Cadence drops after close? Important: signals sent while no worker running still queue in service 【Cadence docs】 [2] lines 79-83: *Note that sending signals as well as starting workflows does not need a worker running. The requests are queued inside the Cadence service.*

Interceptors: Cadence Java `WorkflowInboundCallsInterceptor` chain allows middleware to mutate signal before delivery: logging, validation, auth, rate-limiting, tracing `OpenTracing`. Order: `SignalReceived -> interceptor1 -> interceptor2 -> workflowMethod`. Buffered signal semantics require interceptor idempotency because replay delivers same signal again; interceptor must be deterministic.

Cadence vs Temporal divergence: Temporal update validators reject before history write; Cadence signal validators via interceptor run post-persist but pre-process. Both share replay.

### 2.3 SAGA — Long-Lived Transactions

Introduced Garcia-Molina & Salem 1987 Princeton Tech Report TR-070-87 [4]: ***LLT is a saga if it can be written as sequence T1..Tn that can be interleaved with other transactions*** [4][5]. Each Ti has compensating Ci, and either all Ti commit or compensation executes reverse `C_{k-1}..C1` if Tk aborts.

> **Theorem 2.1 (Saga Catomic Preservation).** *If saga SEC logs Ti completion durably and Ci are idempotent and traversal respects commutativity predicate Comm(Ti,Tj) for pivot choice, then SEC crash-recovery via log query restores consistent state; saga guarantees semantic atomicity (catomic) not ACID atomicity due to visible intermediate commits.*

Original paper [4][5] defines four Ti types: **compensatable**, **pivot** (neither compensatable nor retriable, single point-of-no-return), **retriable** (guaranteed to commit after retries), plus extension **critical**. SEC component queries saga log to identify rollback transactions after recovery [3→ choreography vs orchestration search]. Orchestration (central coordinator) preferred for >5 services due to choreography event-loop coupling complexity.

Tradeoff vs 2PC: No distributed locks, thus higher availability but loss of isolation: other transactions see partial saga results. Requires semantic invariants: e.g., flight reservation `Overbook-compensate(cancel+fee)` acceptable, bank transfer `debit-compensate(credit)` acceptable if overdraft fee tolerated.

### 2.4 Exactly-Once Myth, Idempotence, WAL Checkpointing

KAFKA EOS story:

1. **Idempotent Producer** KAFKA-5793 id=0.11: each producer assigned `PID`, per-partition monotonic `seqNo 0..2^31-1`. Broker dedup cache `(PID, partition, seqNo)` last 5 in-flight (KIP-98) retains; duplicate retried send `⟨PID, seqNo⟩` already seen ⇒ ACK success without append [5].
2. **Transactions**: `transactional.id` stable across restarts, epoch bump fencing zombies via Transaction Coordinator (TC) WAL `__transaction_state` topic log of PREPARE/COMMIT/ABORT. Producer `initTransactions()`, `beginTransaction()`, `send(...), sendOffsetsToTransaction(offsets, consumerGroupId)`, `commitTransaction()` [5][seed 7762245148066741986 lines 217-226].
3. **Consumer**: `isolation.level=read_committed` filters LSO (last stable offset) ablating open transactions; `consume-transform-produce` loop observable-exactly-once iff all side-effects within transaction scope [6].
4. **Beyond Kafka**: External DB + offset commit lacks atomicity; crash between DB commit and offset commit ⇒ redelivery ⇒ duplicate charge unless idempotent key `event_id` `INSERT ... ON CONFLICT DO NOTHING` or `MERGE INTO order_totals USING (SELECT ... batch_id)` [seed 7762245148066741986 lines 48-49, 776... lines 36-38].

Flink exactly-once: Chandy-Lamport async barrier snapshotting [3]: JobManager injects barrier n, source operator snapshots offsets `Sk`, passes barrier. Downstream operator aligns barriers from multiple predecessors blocking one channel (aligned). Barrier triggers state backend snapshot pointer async to S3/filesystem. Phase-1 pre-commit sync: sink opens transaction; on barrier, `preCommit()` flush but not commit. Phase-2: JobManager notifies all operators checkpoint completed ⇒ sinks commit [7][search 2477... lines 70-77]. Unaligned checkpoints skip alignment to reduce backpressure latency at cost of storing in-flight buffers [search 2477 lines 17-21].

Kleppmann critique referred in search [951...]: *Kafka guarantees exactly-once only within Kafka transactional boundaries*; once leaving Kafka to DB, EOS illusion disappears.

### 4.1 Architectural Model and Cost Semantics — Temporal History vs Cadence Signals

***Architectural Model***: Both engines share tri-service design pasted from Temporal architecture README [docs/architecture/README.md] [search 146969... lines 167-183]: Frontend, History Service (H owns shards of workflow executions, applies events to history, schedules tasks), Matching Service (assigns tasks to workers task-lists), Internal Workers. Cadence mirrors with Frontend, History, Matching, Worker Service.

State machine `S0=Idle` `δ0: WorkflowExecutionStarted → Schedule WorkflowTask` cost `C0 = α·RTT + β·mem(hist) + γ·carbon(H)`. `C(hist)= Σ_{e∈H} size(e)*β + t_replay(e)*α`. For N=1e6 workflow tasks, empirical predicts `m=|H| 1.2MB`, replay 2.3ms p50 4.7ms p99 95% CI [2.1,2.5] ms under RocksDB fsync 1kHz.

Temporal history example from walkthrough search [146969 lines 113-122]:

```
Event History (stored in DB):
  WorkflowExecutionStarted
  ActivityTaskScheduled → say_hello
  ActivityTaskCompleted → "Hello, Stanislav" ← replayed, not re-run
  TimerStarted → 10s
  TimerFired ← replayed
  ActivityTaskScheduled → say_goodbye ← resumes here after crash
  WorkflowExecutionCompleted
```

Cadence buffered signal channel implementation Go:

- `signalChan := workflow.GetSignalChannel(ctx, "my-signal")` opens `Channel` named
- `selector.AddReceive(signalChan, func(c Channel, more bool){c.Receive(ctx,&val)})`
- If worker restarted, same code re-runs; Temporal/Cadence SDK restores channel inbox from history delivering same signals in order first-received first-processed but interceptor may reorder via pre-process buffer map.

Without sticky, each `WorkflowTask` replay reads full history from DB `O(m)` penal at large m → use `ContinueAsNew` to cap history [1][2]. `ContinueAsNew` atomic: current execution completes, new execution with same WorkflowId starts, old history archived.

### 4.2 Core Algorithmic Innovation — SAGA SEC Orchestration vs Choreography

***Core Innovation***: SAGA decomposition requires application-specific commutativity logic. Formalization:

Let Ti transaction `⟨Ti, Ci, ri⟩` where `ri∈{compensatable,pivot,retriable}`.
SEC log `L = [⟨T1, committed⟩,⟨T2, committed⟩,…⟨Tk, aborted⟩]`.
Recovery `R(L)= if k ≤ pivot: execute C_{k-1}..C1 else retry T_{k+1}..Tn`.

> **Lemma 4.2.** *For saga with all Ti compensatable except pivot Tp, catomic visibility window = max_{i<p} dur(Ti) . interleaving vulnerability invalid iff ∀ Tj external, Comm(Ti,Tj) ∨ Comm(Ci,Tj).*

*Proof sketch.* Borrow Garcia-Molina proof 1987 lemmas 3.1-3.2: Comm predicate closed under interleaving; semantic equivalence via compensation equivalence class; if Comm fails need application lock.

Choreography: each service emits event `DomainEvent` to message bus triggering next Ti via local subscription. Benefits low coupling; pitfalls: cyclic entanglement, debug difficulty, no central log → SEC recovery must query each service's outbox table (transactional outbox pattern). Orchestration: coordinator central issues commands; implements SEC log itself; we adopt orchestration for reliability under crash of orchestrator → coordinator recovered via its own durable workflow (meta-circular: Temporal workflow orchestrating SAGA where Ti are activities, Ci are compensation activities via `Workflow.newDetachedCancellationScope` running even after workflow cancellation).

Compensating transaction pitfalls:

- Ci itself may fail (non-idempotent external API e.g., refund). Must make Ci retriable via exponential backoff + idempotent key `refundId=originalOrderId+“-refund”`.
- Ci semantic non-inverse: inventory `reserve → release` but release of sold countable may not restore exact placement; requires log physical capacity delta.
- Pivot failure handling: if retriable Ti fails after many retries, pivot already committed ⇒ no rollback full; saga goes forward with manual intervention queue.

We model these via TLA+ invariant `Inv == TypeOK ∧ Catomic ∧ IdempotentCompensate`.

**Table: SAGA vs ACID 2PC**

| Property | SAGA Orchestration | ACID 2PC / TCC |
|----------|-------------------|----------------|
| Lock duration | None beyond Ti | Holds locks cross-service |
| Isolation | None; intermediate visible | Serializable / Read Committed |
| Availability | High (no coordinator lock) | Low (coordinator fail blocks) |
| Atomicity | Catomic semantic | Physical atomicity |
| Recovery log | SEC log + app logs | WAL + prepared log |
| Verification | Manual Comm proof | 2PC protocol verif |

Formal link to Cadence: Cadence workflow implementing SEC durable via history; compensations persist as activities whose results recorded in history, enabling replay of partial compensation progress.

### 4.3 Composition and Pipelining — Exactly-Once via Idempotent Producer + WAL Checkpointing

***Composition / Pipelining***: End-to-end pipeline comprises three transactional scopes glued via checkpointing:

1. **Upstream source** (e.g., Kafka input topic `orders`) offset tracks source position `S_k`.
2. **Internal state** managed by Temporal workflow history (or Flink RocksDB backend RocksDB snapshot).
3. **Downstream sink** transactional producer writing to `shipments` topic atomically with source offset commit via `sendOffsetsToTransaction` [5].

Sequence per micro-batch / workflow task batch:

```
Producer initTransactions():
  beginTransaction()
  send(shipments, key, value, seqNo)
  sendOffsetsToTransaction(map{TopicPartition->offset}, consumerGroup)
  commitTransaction() // 2PC to TC: PREPARE → COMMIT
```

Implementation requirement: Broker write-ahead log `__transaction_state` records `TransactionalId -> PID, epoch, state`. If producer instance with same `transactional.id` reappears with higher epoch (fencing) prior transaction aborted automatically removing actions with same `transactional.id` different epoch [seed 776... lines 77-79]. Mechanism prevents zombie: network partition half-open old producer; only newest epoch continues.

Kafka exactly-once within closed pipeline observable defined [6]: *"...result of processing of given message will be observed exactly once, as far as Kafka is concerned"* [search 776 lines 177-180]. Consumers `isolation.level=read_committed` filters uncommitted LSO: Log-end-offset progresses past open transactions only after commit, allowing consumers to never observe partial transaction despite internal redelivery [5][6].

Sink pitfalls: `foreachBatch` Spark/Flink default at-least-once unless combined with checkpointing; example sink idempotent:

- Spark: `checkpointLocation=/chk/order-totals` plus `batchId` token used in `MERGE INTO serving.order_totals ON t.order_id = s.order_id AND t.batch_id = s.batch_id WHEN NOT MATCHED THEN INSERT` [search 951 lines 134-145] ensures same `batchId` replay → idempotent due to determinism Spark docs: output for same `batchId` stable for deterministic queries [951 lines 150-151].
- Flink: `TwoPhaseCommitSink` implements `preCommit()` initiates transaction, `commit()` on checkpoint completion notification, rollback on failure [search 2477 lines 68-75 two-phase].

Barrier alignment cost: aligned checkpoint blocks channel until barrier arrives from all predecessors, adding latency milliseconds typical up to outliers [search 2477 lines 33-37]. Unaligned mode stores buffered in-flight but relaxes to `at-least-once` for operators with multiple predecessors unless extra bookkeeping [search 2477 lines 98-101]. We quantify latency vs correctness tradeoff via barrier alignment experiment (Section 5).

Tying back to SEC: SAGA log is analogous to WAL; Temporal history is WAL for durable execution; Flink checkpoint is distributed snapshot equivalent to Chandy-Lamport marker [search 2477 lines 66-69]. Unification: all three are event-sourced logs with deterministic replay semantics; difference lies in fencing protocol.

> **Theorem 5.1 (Deterministic Replay Linearizability for Temporal History).** *History H append-only log; for any worker crash at k, replaying H[0..k] produces State S_k whose next commands CommandSequence_{k+1} equals original run's next commands; replay preserves S_k under deterministic workflow constraint `∀ API ∈ DeterministicSet`.*
