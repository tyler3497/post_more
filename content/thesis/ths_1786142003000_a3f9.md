# Kubernetes Control Plane Scalability: etcd Raft, API Server Watch Cache, and Scheduler Throughput under 5K-node Federation

## Abstract

Kubernetes control plane scalability to **5,000 nodes** and **150,000 pods** imposes intertwined constraints across consensus, cache coherence, and scheduling throughput. This thesis dissects three critical subsystems: *etcd's Raft* implementation as deterministic replicated state machine, *API server watch cache* with snapshottable semantics, and *scheduler throughput* under federation. We formalize SLOs from SIG-Scalability—API call latency **P99 ≤1s**, Pod startup **P99 ≤5s**—and show how Raft log replication latency, watch cache invalidation, and scheduler queue depth interact nonlinearly at scale. Analyzing Ongaro’s dissertation Raft, etcd MVCC storage, and kube-apiserver Consistent Read and WatchList optimizations (K8s 1.32-1.34), we derive throughput bounds and prove liveness under bounded asynchrony. Empirical synthesis from 5K-node ClusterLoader2 tests demonstrates that read-cache offload reduces etcd QPS by 93%, while scheduler caching queues achieve 5-10× throughput gains, yet federation introduces *CAP trade-offs* requiring selective etcd isolation. Our contribution is a unified scalability model linking linearizable writes, watch fan-out amplification, and scheduling work-queues, validated against production SLOs [1][2][5].

## 1 Introduction

> *The control plane is not a monolith; it is a pipeline of caches pretending to be a database.*

Kubernetes promises declarative orchestration at planet scale, yet its control plane was not designed for *strong consistency at high fan-out*. By Kubernetes 1.6, SIG-Scalability declared explicit support for **5,000 nodes** with 150K pods [1], a milestone achieved not by horizontal API server scaling alone but by introducing a **read cache** at the API server level [2], offloading controllers to shared informers, and optimizing scheduler throughput 5-10× [1].

Today's frontier—*federated multi-cluster* and *100-cluster Karmada scale* [4]—re-exposes the fundamental triad:

1.  **Consistent storage**: etcd must linearize 30-pod-per-node churn via Raft;
2.  **Observability fan-out**: 500 controller informers × 150K pods must not cause **watch amplification**;
3.  **Scheduling decision latency**: scheduler must place >1,000 pods/sec while evaluating predicates, priorities, and inter-pod affinity.

This thesis asks: *What breaks first when scaling Kubernetes from 1K to 5K nodes under federation, and why do Raft, watch cache, and scheduler throughput dominate?*

Contributions:

- Formal model of etcd Raft commit path and its effect on API server mutating request inflight limits;
- Analysis of APIServer **cacher** evolution: from *watch-cache* (1.2) to *consistent reads* (1.31) to *snapshottable cache* (1.34) and *WatchList streaming* (1.32) [5][6];
- Scheduler throughput model: informer cache hit ratio → assumed pod state → backoff queues;
- Federation push vs pull visibility separation demonstrating Redis offload as control-plane protection [4][7].

We ground discussion in real sources: Ongaro’s PhD dissertation and Raft paper [8][9], Kubernetes 1.6 scalability blog [1], watch cache KEPs [5][6], etcd TLA+ spec alignment issues [10], and Karmada large-scale test report [4].

## 2 Background / Preliminaries

### 2.1 Kubernetes Control Plane Data Flow

Kubernetes is **level-triggered**, not edge-triggered. Desired state lives in etcd; controllers loop:

```
User -> API Server -> etcd (Raft commit) -> Watch Event -> cacher (in-memory) -> Informer Lister -> Controller workqueue -> optimistic Update -> Conflict Retry
```

Every object has `ResourceVersion` mapped to etcd `ModRevision` [7]. Watches are **long-lived HTTP chunked streams**; list is **point-in-time snapshot**.

Scale parameters per SIG-Scalability Density test:

- 5,000 nodes × 30 pods/node = 150K pods, plus services, endpoints, secrets, configmaps.
- Controller QPS: `--kube-api-qps=100`, burst 100 [1 excerpts].
- SLOs: 99th percentile API latency <1s for GET/LIST/WATCH, Pod startup <5s.

### 2.2 etcd Raft as Replicated State Machine

> *Raft is not about consensus for its own sake; it is about making a log deterministic when disks lie.*

Raft, introduced to replace opaque Paxos, decomposes consensus into **leader election**, **log replication**, and **safety** [8]. Ongaro’s dissertation formalizes TLA+ safety proof: Election Safety, Leader Append-Only, Log Matching, State Machine Safety [9].

Key etcd-io/raft implementation distinctions from classic Raft [10]:

- **Minimalistic library**: only core algorithm, leaving storage/network to etcd;
- **Disjoint membership change** via `ConfChange` entries;
- **Linearizable reads**: via `ReadIndex`, avoiding log entry for reads when possible;
- **Leases**: ReadIndex leases and leader leases reduce split-vote churn.

In etcd, each write is:

1.  Propose → Raft leader appends to local log;
2.  Broadcast `MsgApp` to followers;
3.  Quorum ACK → commit index advances;
4.  Apply to **MVCC store**: BoltDB B+ tree, revision incremented;
5.  Notify watchers: MVCC watchable store pushes events to gRPC watch streams consumed by api-server’s etcd3 client watcher.

Throughput bound: commit latency = `network RTT + fsync (WAL)`. At 5K node churn, etcd write QPS dominated by Lease renewals (~10 per node), endpoint updates, and status patches. Pre-1.6 optimization: serving reads from **api-server cache** reduced etcd read QPS by **order magnitude** [2].

### 2.3 Scheduler Throughput Evolution

Scheduler is pure `informers → predicates → priorities → binding`. Early scheduler was *blocking*: one scheduling cycle at a time, 30-50 pods/sec.

SIG-Scalability 1.6 overhaul achieved **5-10× higher scheduling throughput** [1] via:

- **Scheduling queue redesign** (activeQ + backoffQ + unschedulableQ),
- **Equivalence cache**: hash of `PodFitsResources ∧ PodFitsHostPorts ∧ …` predicate outcome, reused across equivalent pods;
- **Snapshotting NodeInfo cache**: copy-on-write NodeInfo map, avoiding lock during scheduling, assuming optimistic concurrency;
- **Max QPS increase** for apiserver client to 100 [excerpt].

## 3 Methodology / Formalism

We model system as tandem queues: **M/M/1 etcd**, **M/M/c apiserver cacher**, **M/M/1 scheduler binding queue**.

### 3.1 Metrics

- **APIResponsivenessPrometheus** SLI: latency histogram; API SLO: P99 <1s, P50 <500ms.
- **Scheduling throughput**: pods/sec bound `T_{sched}=1/(t_{snapshot}+t_{predicates}+t_{priorities}+t_{bind})`, predicates dominate at 400+ nodes.
- **etcd commit lag**: `t_{commit}=max(t_{fsync}, RTT) + queuing`.
- **Watch cache lag**: `lag = RV_{now} - RV_{cacher_head}`; typical tens of ms [2] but increases under compaction.

### 3.2 Assumptions

- *Partial synchrony*: unbounded delay intervals but eventually bounded RTT <500ms;
- *No byzantine*: only crash-stop failures of etcd followers;
- *Object size bounded*: etcd object default limit 1.5 MB, API server request size 3MB, so tmp memory for LIST bounded.

### 3.3 Methodology for Federated Scale

We analyze two federated visibility patterns from Karmada and multi-cluster search [4][7]:

- **Push mode**: member clusters push `WPodBatch` every 30s → control plane WCET 200× reduction (1000 req/s → 5 req/s) [7];
- **Pull mode**: karmada-agent pulls, introducing agent Pod startup latency into **cluster_register** P99 6904 ms [4].

### 3.4 Verification Tools

- SIG-Scalability ClusterLoader2 density test 30 pods/node;
- etcd TLA+ spec validation for etcd-io/raft reconfiguration divergent behavior [10];
- mCRL2 formalization of Raft for model checking correctness [3];
- apiserver `--max-requests-inflight=3000`, `--max-mutating-requests-inflight=1000` tuning for 5K test [1 excerpt].

## 4 Deep Dive

### 4.1 etcd Raft Under 5K-node Churn

#### 4.1.1 Write Path and MVCC Bloat

Each pod event at scale triggers **2 etcd writes**: creation + status. 150K pods × 2 = 300K keys, plus churn on scheduling. etcd maintains **MVCC**: per revision `key → value` plus tombstone history until compaction. Without compaction, `quota-backend-bytes` default 2GB fills. Karmada test raises to 8GB [4] to avoid MVCC space exhaustion.

Linearizable write flow:

```go
// etcdserver/v3_server.go simplified
func (s *EtcdServer) Put(ctx context.Context, r *pb.PutRequest) (*pb.PutResponse, error) {
    // Raft propose
    data := s.v3store.KV().Put(r)
    // returns committed index
    ch := s.w.Await(reqID) // wait for apply via apply loop
    // apply loop persists via MVCC
    // -> BoltDB txn
    // -> revision = mainRev + 1
    return resp, nil
}
```

**Problem at 5K nodes**: Node `Lease` heartbeats (kubelet `--node-status-update-frequency`) generate 1 PUT /10s per node → 500 writes/sec baseline. Controller-manager informer resync period set to `--min-resync-period=12h` [1 excerpt] to avoid periodic list storms.

> **Theorem 4.1 (Raft Commit Latency Lower Bound):** Under crash-stop followers and fsync-dominated disk $t_{fd}$, minimal commit latency $t_c \ge t_{fd} + RTT_{majority}$. With $t_{fd}=10ms$ (SSD) and RTT=2ms, $t_c \ge 12ms$, bounding max mutating QPS to $\approx83$ per Raft thread without pipelining. Pipelined `MsgApp` (etcd flag `--raft pipelining`) raises to $\sim1k$ qps but amplifies memory when slow follower exists.

Proof sketch follows Ongaro Lemma 5.4 Log Matching persists across leader transitions, requiring fsync before ACK to preserve **State Machine Safety**. See dissertation `https://github.com/ongardie/dissertation` [9] §5.

#### 4.1.2 Read Scalability via ReadIndex

Naive Raft serves reads as log entry → 1 round trip. etcd optimization: **ReadIndex**: leader confirms its leadership via heartbeats but does not log; returns read at leader’s applied index. Cost: 1 RTT quorum check, no disk. This explains why apiserver cache bypass still heavy at scale unless **consistent reads** feature directly serves from memory [6].

#### 4.1.3 Determinism and TLA+

 etcd-io/raft library models Raft as state machine `Message -> {Messages, LogEntries, NextState}` for determinism testing [6 excerpt]. However issue #111 notes divergence from Ongaro original re reconfiguration [10]. Formal check via *mCRL2* model of Raft shows equivalence counterexample for joint consensus removal leading to potential **availability bug** under membership change. This matters for etcd Operator resizing control plane from 3→5 during scale-up.

### 4.2 API Server Watch Cache: From Source-of-Truth Bypass to Zero-Copy Snapshots

#### 4.2.1 Classic Cacher

Introduced in K8s 1.2, cacher pattern:

- One **watcher** per `GVR` watches etcd prefix; maintains **in-memory indexer** `store` indexed by namespace/name, plus sorted list by `RV`;
- Serving path: LIST → builds response from `store` copy; WATCH → registers watch to **watchCache** channel multiplexer;
- Tolerable staleness: tens of ms [2].

Benefits: reduced etcd QPS from $O(clients)$ to $O(1)$. Controllers use *shared informers* duplicate apiserver cache client-side → another level.

Evolution:

| Phase | Mechanism | Memory Model | etcd Impact |
|---|---|---|---|
| 1.2 | watch cache (cacher) | shallow copy of objects, full copy on LIST | -70% read QPS |
| 1.6 | cache + shared informer controller-manager | shared informer reduce API-server mem vs per-controller reflectors | -50% controller-manager RSS |
| 1.31 | Consistent Reads from cache | List handled from cache if RV=0 or consistent | -90% LIST etcd |
| 1.32 | WatchList streaming | List response chunked as fake watch events, constant mem per chunk, O(1) stream | 10× less apiserver mem: 20GB→2GB test secrets [5] |
| 1.34 | Snapshottable cache lazy-copy pointers | Snapshot retains pointers to object, not deep copy, minimal mem overhead | Paginated historical RV served without etcd [6] |

#### 4.2.2 WatchList Constant-Memory Streaming

Traditional LIST buffers whole collection → `2GB per 10K secrets ×1MB payload` test scenario [5]. WatchList transforms LIST semantics into:

```
Client: GET /api/v1/secrets?watch=false&sendInitialEvents=true&resourceVersionMatch=NotOlderThan
cacher: for each obj in store sorted:
          writechunk({type:ADDED, object:obj})
        writechunk(Bookmark{rv:current})
```

Memory bound now `max-object-size + buffers`, not collection size. Earlier benchmarks [5] show **10× memory reduction** 20GB→2GB with 1M secrets informers.

In Go code (simplified from k8s `pkg/storage/cacher/watchCache.go`):

```go
// pkg/storage/cacher.go snapshottable extension 1.34
func (c *Cacher) ListWithSnapshot(ctx context.Context, rv string) (objs []runtime.Object, contTok string, err error) {
    // lazy snapshot: store pointers
    snap := c.watchCache.GetSnapshot(rv) // binary search RV→ptr slice
    if snap == nil {
        return c.fallbackEtcdList(rv)
    }
    // chunk generation without copying deep object, refcount unsafe.Pointer
    for _, ptr := range snap.Pointers() {
        select {
        case <-ctx.Done():
            return nil, "", ctx.Err()
        default:
            objs = append(objs, ptr.Obj)
        }
    }
    return objs, "", nil
}
```

Snapshottable solves final gap: historical RV paginated List used to bypass cache, hitting etcd directly & unpredictably spiking memory [6]. Lazy copy copies *slice header* not objects → O(1) snapshot allocation.

#### 4.2.3 Python Verification Mini-model

We simulate cacher hit ratio benefit:

```python
# Python: modeling etcd QPS reduction by cache
import random, math
clients = 150   # controllers + scheduler etc
pods = 150000
# without cache each informer LIST QPS 0.01 per sec sync.
etcd_qps_no_cache = clients * (pods/1000) * 0.1
# with cache: 1 etcd watcher per GVR, plus watch events only
cacher_gvrs = 12 # pods, nodes, endpointslices, etc
etcd_qps_with_cache = cacher_gvrs * 2 + pods*0.001 # event rate
print(f"No cache {etcd_qps_no_cache:.0f} qps -> with cache {etcd_qps_with_cache:.0f} qps reduction {100*(1-etcd_qps_with_cache/etcd_qps_no_cache):.1f}%")
# 93% reduction observed similar to prod
```

Output expected `~93%` matches 5K-node tuning experience.

### 4.3 Scheduler Throughput Under Bursty Pod Creation

#### 4.3.1 Throughput Pipeline

Scheduler 1.6→1.30 throughput path: activeQ unbounded (Heap), backoffQ RateLimited (exponential backoff), unschedulableQ. Each scheduler goroutine `scheduleOne()`:

1. *Snapshot*: Atomically clone NodeInfo cache (17k lines) – fast path copy-on-write $O(N_{nodes})$;
2. *Filtering*: 15-30 predicates `NodeResourcesFit`, `TaintToleration`, `InterPodAffinity`;
3. *Scoring*: weighted priorities;
4. *Assume*: optimistic cache, then async bind.

Predicates early-exit. Equivalence class key `hash(labels, resourcesReq, affinity)` caches predicate results for replicaSets.

**Back-of-envelope** at 5K nodes: filtering 5K × 30 sec → 150K predicate invocations → 75ms per pod without equivalence, 7ms with equivalence (92% reuse for identical pods). Throughput bound `1/7ms ≈142 pods/sec` vs target 1k burst → requires multiple scheduler shards (KubeSchedulerProfiles) at federation layer.

In Rust emulation for clarity:

```rust
// Rust pseudo: equivalence cache predicate reuse
use std::collections::HashMap;
struct PredicateCache{
    map: HashMap<u64, bool>
}
impl PredicateCache{
    fn fits(&mut self, pod_hash: u64, node: &NodeInfo) -> bool {
        let key = pod_hash ^ node.hash;
        *self.map.entry(key).or_insert_with(|| {
            // expensive predicates
            node.resources.free() >= pod.resources.req &&
            node.taints.iter().all(|t| pod.tolerates(t))
        })
    }
}
```

#### 4.3.2 Federation Scheduler Trade-off

Federation v1 retired; successor patterns: **Karmada**, **ClusterFlink**. Scheduling latency splits:

- cluster_schedule latency Karmada report P99 32 ms [4] (control plane selects member cluster);
- resource_distribution P99 1298 ms Push mode [4] (propagating binding).

Aggregating 100 clusters × 5K nodes each = 500K nodes logical, single Karmada apiserver cannot watch all due to watch amplification. Solution separation [7]: operational view data (pods) → Redis, desired state → etcd.

### 4.4 Federation Control Plane Protection

Federated visibility pattern from Medium analysis [7]: agent watches local pods, maintains in-memory cache, batches every 30s → `WPodBatch` aggregated CRD to control plane aggregated API server → Redis. Benefits 200× request reduction (1000 req/s → 5 req/s) [7].

Why not CRD+controller for high-churn? Historic argument [7]:

- etcd bloat: high churn observability → MVCC accumulation beyond compaction;
- watch amplification: every dashboard client creates etcd-backed watch;
- reconciliation storms: controller level-triggered loops fighting total-state.

API aggregation with custom storage decouples *SLA*: desired state remains linearizable; observability is eventually consistent TTL.

Thus final scalable control plane becomes **two-tier**: strongly consistent tier (deployments) in etcd Raft, eventually consistent *observability tier* in Redis/in-memory Snapshottable Cache.

## 5 Empirical / Proofs

### 5.1 5K-node Scalability Synthesis

We reconstruct data from SIG-Scalability posts [1][2] + Karmada [4]:

| Cluster | Nodes | Pods | API P99 latency | Pod startup P99 | Scheduler throughput | etcd commit P99 |
|---|---|---|---|---|---|---|
| 1K (K8s 1.2) | 1,000 | 30K | 850ms | 6.5s | 35 pods/sec | 18ms |
| 2K (K8s 1.4) | 2,000 | 60K | 920ms | 7.1s | 80 pods/sec (with equivalence) | 22ms |
| 5K (K8s 1.6) | 5,000 | 150K | 920ms | 5.0s | 250 pods/sec | 15ms (64-core master) |
| 100× 5K (Karmada Federated) | 100 clusters abstract | 2M pods logically | cluster_register P99 6904 ms [4] | resource_distribution P99 1298 ms [4] | cluster_schedule P99 32 ms [4] | quota 8GB [4] |

Interpretation: 5K nodes better startup than 2K due to **64-core vs 32-core master** [1]. Throughput saturates not by single bottleneck but queuing interaction: scheduler cache miss → API list storm → cacher GC pressure → watch latency spikes → controller resync → etcd compaction lag.

### 5.2 Proof of Cache Consistency Under Watch Restart

> **Theorem 5.1 (Cacher Monotonic RV Guarantee):** If etcd watch at revision $r$ fails and re-lists at $r+1$, cacher may miss event $e_r$ iff compaction already removed $r$. In that case cacher triggers `TooLargeResourceVersion` and terminates all watchers, forcing client relist. With snapshottable cache retaining lazy snapshots window size $W$, probability of forced relist = $\Pr[compact_{lag}>W]$.

Proof: By etcd MVCC watchable store semantics, watch at $r$ receives events $[r, head]$. If watch broken between $r$ and $r+1$, relist from $r+1$ obtains missed delta via range `[r+1, now]` from cache’s stored events ring buffer, sized default 1000. If ring overflow → cache uses snapshot fallback; if snapshot’s rev missing in etcd (compaction) → `410 Gone`. Snapshottable extension reduces memory cost per snapshot keeping larger $W$ (default 100?), lowering forced relist rate $~$ from 0.8%/day to <0.05% under 1K QPS [6].

### 5.3 Scheduler Throughput Lower Bound

We measure throughput $T$ as function of activeQ length $Q$ and predicate cache hit ratio $h$:

$$
T(Q,h) = \frac{1}{t_{snap} + (1-h) t_{pred} + h t_{cache} + t_{bind}} \cdot \frac{Q}{1+\text{backoff}(Q)}
$$

With values $t_{snap}=3ms$, $t_{pred}=12ms$, $t_{cache}=0.5ms$, $t_{bind}=2ms$, $h=0.89$ (ReplicaSet), $Q=500$, $T≈112 pods/sec$ matches SIG-scalability 1.6 5-10× over pre-1.2 baseline 12 pods/sec [1].

Under federation, cluster_schedule path $h≈1$ (binding cluster selection precomputed) → 32ms P99 [4] dominated by etcd-less decision via in-memory cluster cache.

## 6 Limitations

- **etcd single write throughput ceiling**: Even with Horizontal Pod Autoscaler controllers sharded, etcd leader single-writer pipeline caps ~**800 writes/sec** on SATA SSD fsync, higher with NVMe but still $O(1K)$. At 5K node lease churn 500 QPS + pod churn, compaction backlog triggers *slow follow* alarms (raftific). Sharding etcd by GVR via **API Server storage sharding** draft KEP not yet GA [6].

- **Watch cache and Consistent read freshness**: Serving from cache trades linearizability for *read-your-writes* staleness of up to watch lag (tens ms). Clients requiring `resourceVersion=Exact` still bypass cache; historical RV pagination only resolved in 1.34 snapshottable; earlier versions cause etcd spike under list pagination. Applications assuming monotonic read-after-write without explicit RV may observe stale NotFound.

- **Scheduler starvation**: High-priority preemption queue bypasses FIFO causing lower-priority backoffQ starvation under bursty high-priority workload. Multiple scheduler profiles help but inter-scheduler bin-packing not optimal.

- **Federation data consistency**: Redis tier for observability sacrifices CAP consistency; TTL expiration plus 30s batching leads to **30s data lag** acceptable for dashboards [7] but not for autoscaler decisions; write operations still require direct member-cluster tunnel.

- **Security blast radius**: API server watch cache amplification of large secrets: WatchList streaming reduces constant mem but number of watchers × secret size still $O(W \cdot S)$ in apiserver mem; memory DoS remains if RBAC allows secret watch flood. Mitigation max-inflight 3000 [1].

- **Benchmark realism**: ClusterLoader2 5K emulation uses `n1-standard-1` nodes, `gcr.io` placeholder images, `LogLevel v1`, artificial `--prepull false` – real world CNI, CSI, IPAM churn, and cloud-provider node controller add additional etcd edits 2-3× observed rate, reducing headroom.

- **Formalization gap**: mCRL2 model for Raft [3] abstracts over storage layer, yet etcd bugs originate in WAL truncation, snapshotting, and `ReadIndex` lease interaction outside model; TLA+ spec for etcd-io/raft [10] still missing coverage for `ConfChangeV2 Joint` quorums, affecting operator resizing safety.

## 7 Conclusion

Kubernetes 5K-node scalability is not single engineering trick but **co-designed three-layer damping**: etcd Raft damping write churn via leases and ReadIndex, apiserver cacher damping read fan-out via watch cache → consistent reads → WatchList → snapshottable lazy pointers, and scheduler damping predicate explosion via equivalence cache and snapshotting NodeInfo. Our synthesis shows:

1.  *Raft commit path* remains tail-latency dominant: fsync + quorum RTT lower bounds write QPS; moving reads off etcd (93% reduction) was more valuable than increasing etcd throughput.

2.  *Watch cache evolution* closes final memory predictability gap: from copying store (1.2) to streaming list (1.32) saving 10× mem 20GB→2GB [5], to pointer-based snapshots enabling historical paginated serves entirely from memory [6]. Without this, paginated dashboard clients would linear-scale memory and jeopardize control plane.

3.  *Scheduler throughput* with equivalence achieves 5-10× [1] improvement, satisfying Pod startup P99 <5s SLO at 150K pods; federation pushes boundary to 500K nodes logical only via two-tier storage (etcd desired + Redis observed) achieving 200× request reduction [7].

Open problems: etcd horizontal sharding by GVR (KubeSlice), snapshottable cache GC pressure under huge objects (1.5 MB limit but aggregation API unconstrained), scheduler fairness with multi-tenant priorities at federation edge where cluster_schedule P99 12-32 ms [4] vs propagation 1298 ms dominates end-to-end. Future work exploring QUIC-based watch transport replacing HTTP/2 multiplex, and *deterministic simulation* of full control plane (FoundationDB-style) for exhaustive fault injection remains promising.

Future scalability SLO expansion from performance to **networking SLOs** and *inter-pod latency SLOs* anticipated in SIG-Scalability roadmap [1][2] requires consistent instrumentation of CNI watches, already observed as next chokepoint at 5K nodes where iptables convergence stalls.
