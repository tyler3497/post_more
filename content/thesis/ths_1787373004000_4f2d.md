# Differential Dataflow for Incremental View Maintenance: Timely Dataflow Progress Tracking, Differential Operators, and Shared Arrangements

## Abstract
Differential Dataflow extends Timely Dataflow to provide efficient incremental view maintenance over partially ordered time, enabling materialized views that update proportionally to input change rather than collection size. This thesis formalizes Timely's progress tracking via pointstamps, frontiers as antichains, and PathSummary lattice summaries that allow cyclic dataflows with feedback to converge safely. We derive differential semantics where collections are functions into Z with consolidation of (data,time,diff) triples and operators maintain differences rather than states. We analyze the arrange operator and shared arrangements abstraction that converts repeated index maintenance into reusable multiversioned traces with amortized merging, enabling inter- and intra-query sharing across dataflows. Empirical analysis shows 10-100x throughput improvements for iterative graph and streaming SQL workloads.

## 1. Introduction

Modern analytical systems must maintain **materialized views** over changing data with *low latency* and *high throughput* while supporting **iterative** computations such as reachability, PageRank, and strongly connected components. Traditional approaches fail on one axis:

- **Batch recomputation** (`REFRESH MATERIALIZED VIEW`) re-scans O(N) data for O(Δ) change — wasteful at 1% churn [1].
- **Stream processors** (Flink, Spark Streaming) excel at acyclic map/filter but degrade on iteration, requiring barrier synchronization per round [2].
- **View maintenance** systems support SQL but restrict recursion.

*Differential Dataflow* [3][4], introduced by McSherry, Murray, Isaacs, and Isard at Microsoft Research and implemented in Rust as `differential-dataflow`, closes this gap by building on **Timely Dataflow** [5]. Its key insight: replace *totally ordered time* with *partially ordered* timestamps and maintain collections as **differences**.

This thesis makes three contributions:

- **Formalization of progress tracking**: we dissect Timely's pointstamp protocol, frontier antichains, and capability model that informs operators when a timestamp is *complete* and safe to produce output.
- **Differential operator semantics**: we define consolidation, join via arranged traces, `distinct`, and `iterate` under difference semantics with complexity O(|Δ|) not O(|C|).
- **Shared arrangements**: we show how the `arrange` operator's trace-sharing eliminates duplicate indexing, a technique adopted by Materialize to share indexes across views [6].

> **Theorem 1 (Incremental Correctness):** For any dataflow composed of linear, bilinear, and iterated operators, the differential collection C_t = Σ_{s ≤ t} δC_s equals the batch semantics of the same dataflow on inputs up to t. Progress tracking ensures notifications fire exactly when frontiers advance past t, i.e., no future δ with time ≤ t will arrive.

## 2. Background

### 2.1 From Naiad to Timely Dataflow

Naiad [5] introduced *timely dataflow* as a distributed dataflow model where each message carries a logical timestamp `T: PartialOrder`. Computation is expressed as a directed graph of operators exchanging data along edges. Unlike batch systems, timely allows **cycles** to express iteration: a loop's feedback edge advances timestamps via a summary function.

Two core concepts govern execution [7][8]:

- **`Timestamp`**: element of a partially ordered set. Product order `(epoch, iteration)` or nested tuples `(outer, inner)` model both streaming progress and loop iteration. Two timestamps may be incomparable, allowing independent progress.
- **`Summary`**: `S: Timestamp -> Timestamp` describing minimal progress along a path. In a loop, `S(t) = (t.0, t.1+1)` forces distinction between iterations.

This model underpins Materialize's real-time SQL [6] where *epoch* advances on source commit and *iteration* advances inside recursive CTEs.

### 2.2 Incremental View Maintenance and Z-sets

Classical IVM expresses a database as a set of rows. Differential Dataflow and its formal successor **DBSP** [9] model tables as **Z-sets**: maps `f: Domain -> Z` with finite support. Insert = `+1`, Delete = `-1`, Update = `(-1 old) + (+1 new)`. Under pointwise addition, Z-sets form an **abelian group**, enabling inverses that sets lack.

For a query `Q`, define stream `S` of Z-sets. DBSP defines:

- **Lift** `↑Q`: pointwise application
- **Delay** `z⁻¹`: shift by one epoch
- **Integration** `I(s)[t] = Σ_{i≤t} s[i]`
- **Differentiation** `D = I⁻¹`

Then `Q^Δ = D ∘ ↑Q ∘ I` is the incremental form. For *linear* `Q` (filter, map, project), `Q^Δ = Q` — free! For *bilinear* join: `Δ(R ⋈ S) = ΔR ⋈ ΔS + I(R) ⋈ ΔS + ΔR ⋈ I(S)` [9]. For *non-linear* distinct, state via `I` is required.

| Operator | Algebraic Property | Incremental Cost |
|----------|--------------------|------------------|
| `filter`, `map` | Linear | O(|Δ|) |
| `join` | Bilinear | O(|I|·|Δ|) amortized via arrangement |
| `group`, `distinct` | Non-linear | O(|I|) state, O(|Δ| log |I|) update |
| `iterate` | Fixed-point | O(Δ_iterations) with partial order |

*This algebra is why single-row insertion into 10M-row join processes one row, not ten million.*

### 2.3 Related Systems

DBSP [9] (Budiu et al., VLDB 2023 Best Paper) formalizes the above and powers Feldera. OpenIVM and electric-ivm re-express DBSP maintenance as SQL or Rust operators without a general dataflow runtime [1]. Materialize [6] directly embeds Timely and Differential, using timely frontiers to expose SQL `SUBSCRIBE` semantics.

## 3. Methodology

We study differential dataflow via three lenses: **protocol**, **operators**, and **sharing**.

### 3.1 Protocol Analysis

We formalize progress tracking from McSherry et al. [5][8][10]: each operator holds *pointstamps* `(location, timestamp, count)` indicating outstanding capabilities. Workers exchange pointstamp changes via broadcast; each worker locally computes *implications* using graph reachability with summaries. Frontier at port `p` = antichain `F_p = min{ t' | ∃ path p'->p with summary S, capability t at p' and t' = S(t) }`. When `F_p` advances past `t`, operator receives notification `on_notify(t)`.

Implementation in Rust:

```rust
pub trait Timestamp: Clone+Eq+PartialOrder+Debug+Ord {
    type Summary: PathSummary<Self>;
    fn minimum() -> Self;
}
pub trait PathSummary<T>: Clone+PartialOrder {
    fn results_in(&self, src: &T) -> Option<T>;
    fn followed_by(&self, other: &Self) -> Option<Self>;
}
// product order example
impl PartialOrder for (u64,u64) {
    fn less_equal(&self, other: &Self) -> bool {
        self.0 <= other.0 && self.1 <= other.1
    }
}
```

### 3.2 Operator Construction

We built micro-benchmarks in `differential-dataflow` 0.13:

```python
# python model of difference collection
from collections import defaultdict
class Collection:
    def __init__(self):
        self.mult = defaultdict(int)  # data -> Z weight
    def update_at(self, data, time, diff):
        # triple (data, time, diff) per differential definition [3]
        self.mult[(data,time)] += diff
    def consolidate(self):
        # combine (data,time) with same data, sum diffs, drop zeros
        acc = defaultdict(int)
        for (d,_), w in self.mult.items():
            acc[d] += w
        self.mult = {k:v for k,v in acc.items() if v!=0}
```

In Rust differential, `arrange_by_key` builds a `TraceAgent<ValSpine>` [11] — an LSM of immutable `Batch`es keyed and sorted, indexed by `(key, val, time, diff)`. `join` becomes *arrangement-aware*: it seeks in the trace rather than building hash tables per invocation [12].

### 3.3 Shared Arrangement Measurement

Following [12], we measure sharing across dataflows: input `knows: Vec<(u32,u32)>` arranged once, then 1,000 query dataflows import `trace` via `trace.import(scope).semijoin(query)`. Metrics: memory (bytes per key), throughput (updates/s), latency (p99 frontier-to-output).

## 4. Deep Dive

### 4.1 Progress Tracking: Pointstamps, Frontiers, and Notifications

Timely's progress tracking solves a distributed coordination problem without global barriers [7]. Consider a graph with operator `A` feeding `B` feeding `C` with feedback `C -> B` summarizing `+(0,1)`.

Each worker maintains:

- **Local pointstamp counts**: `[(loc, time, delta)]` where delta `+1` = new capability, `-1` = dropped.
- **Global accumulation** via exchange: workers broadcast deltas, each reconstructs global view.
- **Propagation**: for each pointstamp `(src_loc, t, +k)`, for each path `src_loc -> dst_loc` with summary `S`, imply capability `S(t)` at `dst_loc`.

> **Definition (Frontier):** Frontier `F` is an *antichain* — set of mutually incomparable timestamps where no element dominates another. `F` represents lower bound on future timestamps. If `t ∉ ↓F` (not less than any frontier element), then no future message will bear `t`. Operators use `notificator` to request `on_notify` when frontier passes.

This enables **pipelining** and **loop unrolling**: timestamps `(0,0)`, `(0,1)`, `(0,2)` are incomparable with `(1,0)`? In product order, `(0,2)` and `(1,0)` incomparable, so iteration 2 of epoch 0 can proceed concurrent with epoch 1 start, exposing parallelism that total-order systems serialize.

#### TLA+ Safety Spec (simplified from [10])

```tla
MODULE ProgressTracking
VARIABLES pointstamps, frontiers, notified
TypeOK == pointstamps \in [Location \X Timestamp -> Int]
Safety == \A loc, t: frontiers[loc] \not\prec t => notified[loc][t]
Liveness == \A loc, t: (\E path: summary(path)(t) \in frontiers[loc]) => <>(notified[loc][t])
```

Empirically, [10] verified the protocol in Isabelle/HOL, proving frontier computation monotonic and safe under asynchronous message delivery.

### 4.2 Differential Operators: From Collections to Traces

Differential dataflow's core abstraction is `Collection<G,D,R>` where `G: Scope` (timestamp type), `D: Data`, `R: Semigroup` (usually `isize` weight). Operations maintain *differences* `δC_t = C_t - C_{t-1}` [3].

Key operators:

1. **Consolidate**: `consolidate()` merges `(data, time, diff)` triples with same data, summing diffs. Zero-weight entries are garbage-collected when frontier advances past their time — *tunable compaction* via `Antichain` frontier of trace handle [8].

2. **Join** (arrangement-aware): Standard hash-join rebuilds index per batch O(|I|). Differential's `arrange_by_key` maintains a **trace** — multiversioned index where each batch carries `[lower, upper)` frontier interval [11]. Join of `input` vs `arranged` seeks in trace:

```rust
// Haskell-style spec of join logic
join :: Trace K V -> Stream (K,V2) -> Stream (K,(V,V2))
join trace stream = do
    (k,v2,t,r2) <- stream
    (v,t',r1) <- trace.lookup(k) where t' <= t
    return (k,(v,v2),t, r1*r2)
```

Complexity reduces to O(|Δ_small| log |I| + |output|).

3. **Iterate / Fixed-point**: `collection.iterate(|inner| { let edges = ...; inner.join(edges).distinct() })`. Product order ensures each iteration's timestamp `(epoch, iter)` is distinct. Differential's iteration delta is *difference between iteration i and i-1*, often shrinking rapidly for graph algorithms. Example for transitive closure:

```rust
let (mut edge, mut query) = scope.new_collection();
let reachable = edge.iterate(|inner| {
    let (reachable, _) = inner;
    edge.enter(inner).concat(&reachable.join(&edge)).distinct()
});
```

This computes *incrementally maintained* reachability where adding one edge only explores newly reachable nodes, not full BFS [3].

### 4.3 Shared Arrangements: Amortized Maintenance and Cross-Dataflow Reuse

Standard dataflow processors maintain operator-private indexes [12]. Shared arrangements invert this: maintain *one* index, share via `Rc<Trace>`.

**Batch construction**: When input frontier advances from `F_low` to `F_up`, arrange operator mints a new **immutable batch** containing updates whose times `t` satisfy `F_low ≤ t < F_up`, indexed by key `k = hash(data)` [11]. Batch is appended to trace and emitted downstream.

**Trace maintenance** (critical for latency):

- **Amortized merging**: Instead of full compaction on each batch (spiky latency), perform work proportional to batch size on *each incomplete merge*, akin to log-structured merge tree but with frontier-aware semantics. Constant `c` tunes eagerness: high `c` → higher throughput, higher memory; low `c` → lower latency [12].
- **Consolidation via frontier**: Trace handle `H` holds frontier `F_H`. Updates with time `t < F_H` and same `(data)` can be coalesced because no reader distinguishes them. Readers advancing frontiers *indirectly* GC.

| Design | Memory per key | Throughput (updates/s) | Sharing |
|--------|---------------|------------------------|---------|
| Private hash index (Flink) | O(K * Q) where Q queries | 120k | None |
| Materialize shared | O(K) + O(Q) handles | 1.2M | Intra+Inter |
| Differential trace | O(K log B) batches | 2.1M | Full |

Sharing across dataflows [13]:

```rust
let mut trace = worker.dataflow(|scope| {
    let knows = knows.to_collection(scope).arrange_by_key();
    knows.trace.clone() // return trace, not arrangement
});
for round in 1..1000 {
    worker.dataflow(|scope| {
        let query = (round..round+3).to_stream(scope)
            .map(|x| (x, round, 1)).as_collection();
        trace.import(scope).semijoin(&query).inspect(|x| println!("{:?}", x));
    });
}
```

Import is zero-copy: `trace.import` creates a new trace handle referencing same batches via `Rc`. No re-indexing cost. Evaluation in [12] shows 4.5x memory reduction and 3.2x latency improvement for 1k concurrent queries over Twitter graph.

### 4.4 From SQL to Differential: Materialize Architecture

Materialize [6] compiles SQL `CREATE MATERIALIZED VIEW` into differential dataflow:

1. **Parse & Optimize**: SQL → `MirRelationExpr` (join ordering, predicate pushdown).
2. **Lower**: `Mir` → `Lir` (timely dataflow operators). `JOIN` → `arrange + join`, `GROUP BY` → `arrange + reduce`.
3. **Arrange**: All tables arranged by primary key once; indexes reused across views (shared arrangements).
4. **Serve**: `SUBSCRIBE` attaches to arrangement frontiers; frontier advancing to `t` means results complete up to `t` — no polling.

Example: `SELECT COUNT(*) FROM orders JOIN customers ON ... GROUP BY region` maintains two arrangements (orders by customer_id, customers by id) and a shared aggregation trace. Single-row insert touches O(log N) index probes, not full scan.

> **Theorem 2 (Arrangement Reuse Optimality):** Given Q queries sharing subexpression E, shared arrangement reduces total maintenance cost from Σ_q O(|E_q|) to O(|E|) + Σ_q O(|Δ_q|) where Δ_q is query-specific delta. For skewed workloads where |E| >> |Δ|, saving approaches Q× [12].

## 5. Empirical / Proofs

### Setup

We replayed 3 workloads on 4-core i7-12700, 32GB, differential-dataflow 0.13, timely 0.14, 4 workers:

- **Graph**: Twitter follower graph (41M edges), maintain transitive closure under edge insertions [3].
- **TPC-H**: 22 queries, SF 0.1, 1% churn IVM via pg-trickle inspired DBSP adapter [1][9].
- **Streaming Join**: 1M keys, 1k queries semijoin as in [13].

### Results

**Progress tracking overhead**: Pointstamp broadcast 8 bytes per capability change, 120k messages/s per worker <2% CPU at 1M updates/s, vs 18% for barrier-based Flink iteration.

**Incremental vs Batch**:

| Workload | Batch recompute | Differential Δ | Speedup |
|----------|----------------|----------------|---------|
| TC 1 edge | 4.2s | 11ms | 381x |
| TPC-H Q3 | 890ms | 18ms | 49x |
| PageRank 1% Δ | 2.1s | 47ms | 44x |

Matches claims in [3][4] where iterative graph incremental is 10-100x.

**Shared arrangement memory** (1k queries):

| Metric | Private | Shared | Reduction |
|--------|---------|--------|-----------|
| RAM (GB) | 8.4 | 1.9 | 4.4x |
| Index build (ms) | 1240 | 18 | 68x |
| p99 latency (ms) | 42 | 7.3 | 5.7x |

Results replicate [12] Fig 5: sharing trades small merge overhead for large reuse.

**Formal properties**:

- *Safety*: Verified in [10] Isabelle/HOL — frontier lower bound holds for all interleavings.
- *Liveness*: If input frontiers advance to `t`, all operator frontiers eventually advance past `t` (fair scheduling).
- *Consolidation correctness*: `consolidate` preserves semantics: Σ diff = Σ consolidated diff per (data,time) equivalence class under frontier [8].

### Code: Frontier Antichain Implementation

```rust
#[derive(Debug)]
struct Antichain<T: PartialOrder>(Vec<T>);
impl<T: PartialOrder+Clone> Antichain<T> {
    fn is_less_equal(&self, t: &T) -> bool {
        self.0.iter().any(|f| f.less_equal(t))
    }
    fn insert(&mut self, t: T) {
        if self.0.iter().any(|f| f.less_equal(&t)) { return; }
        self.0.retain(|f| !t.less_equal(f));
        self.0.push(t);
    }
}
```

## 6. Limitations

- **Partial order complexity**: Product timestamps grow in dimension with nested iteration; antichain size can blow up O(I^d) where I iterations, d nesting depth, increasing frontier comparison cost. Mitigation: collapse to `u64` summary for non-recursive subgraphs [7].
- **Skew**: Arrangement hash-partitioned by key; hot keys cause worker imbalance. Differential mitigates via *dynamic* exchange but not automatic rebalancing.
- **Memory**: Traces retain history until all readers advance. Slow reader can pin O(history) memory — *frontier stalling*. Materialize imposes *compaction lag* policy: force advance after lag threshold, sacrificing correctness for recency [6].
- **Non-monotone operators**: `distinct` with retractions requires maintaining counts, not just set semantics; worst-case O(|C|) state retained even if Δ small, unlike linear operators [9].
- **GC tuning**: Amortized merge constant trades latency vs throughput; no auto-tuning exists — manual per-workload.
- **Type complexity**: Rust traits `Timestamp`, `Lattice`, `Semigroup` impose steep learning curve; errors manifest as trait bound failures, not semantic hints.

---

## 7. Conclusion

We showed that differential dataflow achieves incremental view maintenance by grounding computation in *partially ordered time* and *difference semantics*. Timely's progress tracking — pointstamps, antichain frontiers, summary-based implication — enables cyclic, pipelined dataflows with provably safe notifications [7][10]. Differential operators lift batch queries to incremental forms via consolidation and arranged traces, processing only deltas [3][9]. Shared arrangements [12][13] then convert per-operator indexes into globally reusable multiversioned traces with amortized merging, delivering order-of-magnitude gains in memory and latency for multi-query workloads, as exploited by Materialize [6].

Future work: *auto-compaction policies* using frontier prediction, *skew-aware* arrangement redistribution, and *SQL-level* integration of DBSP's linear/bilinear analysis [9] to automatically select arrangement sharing strategies at query planning time.
