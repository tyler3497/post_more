# Self-Sovereign Identity and Verifiable Credentials: DID Resolution, BBS+ Selective Disclosure, Cryptographic Accumulator Revocation, and OID4VC Integration

## Abstract
Self-sovereign identity (SSI) replaces federated identity providers with cryptographic control rooted in *Decentralized Identifiers (DIDs)* and *Verifiable Credentials (VCs)*. This thesis dissects the end-to-end SSI stack: DID resolution for `did:key` and `did:web` as minimal and web-anchored trust anchors, BBS+ signatures over BLS12-381 for selective disclosure and unlinkable zero-knowledge presentations, cryptographic accumulators for privacy-preserving revocation compared to Bitstring Status Lists, and OpenID for Verifiable Credentials (OID4VC) integration via SIOPv2, OID4VCI, and OID4VP. We formalize DID document determinism, prove BBS+ *ProofGen* unlinkability under LRSW, analyze RSA accumulator witness update cost in O(1) with prime representatives, and model OID4VC issuance as an OAuth 2.0-authorized credential endpoint binding. The result is a deployable architecture satisfying W3C VCDM 2.0 [5], DID Core 1.0 [1], and OID4VC High-Assurance Profile while preserving holder privacy against issuer-verifier collusion.

## 1 Introduction

Centralized identity is a liability: *one breach leaks millions*, correlation is default, and revocation requires online checks to the issuer. Self-sovereign identity inverts this: the **holder** controls identifiers and presentations, the **issuer** attests once, the **verifier** checks cryptographically offline.

> **Central Claim:** *DIDs provide self-certifying identifiers, VCs provide data model extensibility, BBS+ provides minimum-disclosure, accumulators provide minimum-leakage revocation, and OID4VC provides OAuth-compatibility — together they yield a W3C-standard, EUDI-wallet deployable SSI layer.*

Four engineering questions dominate production:

1. **Resolution:** How to resolve `did:key:z6Mk...` to a DID Document without a ledger, and when does `did:web` regain human trust via TLS?
2. **Selective Disclosure:** How to reveal *age ≥ 21* without revealing birthday, address, or linkable signature?
3. **Revocation:** How to prove non-revocation without phoning home to the issuer, which would deanonymize holder activity?
4. **Interop:** How to reuse OAuth 2.0 Authorization Servers, PKCE, and `openid://` deep links that mobile wallets already implement?

This thesis answers each via formal constructions and standards mapping.

### Contributions

- Deterministic `did:key` expansion algorithm using *Multicodec* + *Multibase* and `did:web` HTTPS dereferencing with rotation semantics [2][3][4].
- BBS+ selective disclosure pipeline: RDF Dataset Canonicalization → message array → BLS `Sign` → `ProofGen` → `ProofVerify`, with *proof randomization* theorem [6][7].
- Revocation taxonomy: **Bitstring Status List v1.0** [11] O(16KB) herd privacy vs **RSA dynamic universal accumulator** O(1) membership with O(n) issuer update but O(1) holder witness via Bezout [12].
- Complete OID4VC flow: SIOPv2 self-issued ID Token as holder authentication, OID4VCI pre-authorized code and authorization code flows, OID4VP Authorization Request with `presentation_definition` [8][9][10].
- Rust verifiers and JSON DID Document examples, threat model including correlation via `statusListIndex`.

## 2 Background / Preliminaries

### 2.1 Decentralized Identifiers and DID Documents

A DID is defined by W3C DID Core v1.0 as `did:<method>:<method-specific-id>` [1][2]. Resolution is function `resolve(did) → DID Document`. A DID Document contains:

- `id` — the DID itself
- `verificationMethod` — public key material (`Multikey` or `JsonWebKey2020`)
- `authentication, assertionMethod, keyAgreement, capabilityInvocation, capabilityDelegation` — verification relationships [1]
- `service` — endpoints for *DIDComm*, credential repositories, linked verifiable presentations

*Two methods dominate non-ledger SSI:*

| Method | Persistence | Trust Anchor | Use Case |
|--------|-------------|--------------|----------|
| `did:key` | Ephemeral, deterministic | raw public key itself | pairwise peer, testing, ephemeral presentations [3] |
| `did:web` | Mutable via DNS+HTTPS | TLS certificate + domain controller | issuer `did:web:example.com`, organization identity [4] |
| `did:ion`, `did:indy` | Ledger-anchored | blockchain | long-lived public organizational DIDs |

> Theorem: *`did:key` resolution is function pure and offline; `did:web` resolution is deterministic iff TLS P-K and .well-known/did.json are immutable between calls.*

`did:key` encoding: `did:key:MULTIBASE(base58-btc, MULTICODEC(pubkey-type, raw-pubkey-bytes))` [3]. For Ed25519, prefix `0xed01`, then 32 bytes, then base58btc `z6Mk...`.

### 2.2 Verifiable Credentials Data Model 2.0

VCDM 2.0 [5] defines credential as JSON-LD with `@context: ["https://www.w3.org/ns/credentials/v2"]`, `type: ["VerifiableCredential"]`, `issuer: DID`, `validFrom`, `credentialSubject`, and optional `credentialStatus`. Envelope proofs via *Data Integrity* or *VC-JOSE-COSE*:

- **DataIntegrityProof** with cryptosuite `bbs-2023`, `eddsa-rdfc-2022`
- **VC-JWT** with SD-JWT VC profile using selective disclosure via hashing [5]

BBS+ suites [6] process RDF Dataset Canonicalization [RDF-CANON] into `n` messages (statements), enabling per-claim hiding.

### 2.3 BBS+ Signatures Over BLS12-381

BBS+ is secret-key signature variant of Boneh-Boyen-Shacham group signatures [7]. Four algorithms:

- `KeyGen → (sk, pk = w = g2^sk)`
- `Sign(sk, msg[0..L-1]) → signature (A,e)`
- `Verify(pk, msg, sig) → bool` via pairing `e(A, w·g2^e) == e(B, g2)` where `B` commits to messages
- `ProofGen(pk, sig, msg, disclosedIndexes, nonce) → proof`
- `ProofVerify(pk, proof, disclosedMsgs, nonce) → bool`

Security reduces to `q-SDH` and `LRSW` in `G1, G2, GT` [7]. IETF draft defines ciphersuite `BLS12-381-SHA-256` [7].

*Selective disclosure with unlinkability*: holder proves knowledge of signature without revealing signature itself; each proof randomized via `r1,r2` — two presentations of same credential with same disclosed attributes are *cryptographically unlinkable*.

### 2.4 Revocation and Accumulators

Revocation problem: credential may be validly issued then later invalidated. SSI privacy goal:

- **Issuer oblivious** — issuer should not learn when or where credential presented
- **Verifier private** — verifiers should not learn business metrics over other verifiers

Bitstring Status List [11] uses compressed bitstring where index `i` is 0=valid,1=revoked/suspended. List itself is a VC (`BitstringStatusListCredential`) hosted by issuer/status-provider. Size 16KB = 131,072 entries, ZLIB-compressed to ~ few hundred bytes when sparsely revoked. *Herd privacy* proportional to list size.

RSA accumulator [12]: `acc = g^{∏_{x∈S} prime(x)} mod N` where `N=pq` trapdoor held by issuer. Membership witness for `x` is `w = g^{∏_{y≠x} prime(y)}`. Non-membership via Bezout `a·prime(x)+ b·∏_{revoked} =1`. Dynamic universal allows add/delete in O(1) exponentation with trapdoor.

AnonCreds v1.0 revocation uses similar accumulator but interactive; W3C prefers Bitstring for simplicity with *privacy flaw* that `statusListIndex` is stable correlator unless blinded via ZKP enhancement [GitHub issue 203].

### 2.5 OID4VC Triangle

OID4VC reuses OAuth 2.0 / OpenID Connect flows for SSI [8][9][10]:

- *SIOPv2* [10]: End-User controls OP; `openid://?request_uri=` triggers wallet with `id_token` self-signed using `did:key`
- *OID4VCI* [8]: credential offer `openid-credential-offer://`, token endpoint returns `access_token`, credential endpoint returns `credential` with proof-of-possession `jwt` binding `c_nonce`
- *OID4VP* [9]: Verifier as RP sends Authorization Request with `presentation_definition` from DIF PEP, wallet returns `vp_token`

EUDI/ARF mandates OID4VCI/VP+SIOPv2 for EU Digital Identity Wallets.

## 3 Methodology / Formalism

Our system model:

- Actors: Issuer `I` (`did:web:university.example`), Holder `H` (`did:key:z6Mkh...`), Verifier `V` (`did:web:verifier.example`)
- Setup: `I` has `did:web` doc with `assertionMethod: BBS key`, `H` wallet with secure enclave storing private key
- Credential issuance via OID4VCI: `offer → (pre-auth | auth code + PKCE) → token → credential with c_nonce binding`
- Presentation via OID4VP: `vp auth req with nonce → selective BBS proof → verification via ecdsa check on VC + BBS proofVerify + Status List fetch or accumulator non-revocation ZK`
- Revocation check: `credentialStatus: {type: BitstringStatusListEntry, statusListIndex, statusListCredential}` or accumulator `witness`

We formalize DID resolution:

```rust
// DID resolution for did:key and did:web — pure + http
enum DidMethod { Key, Web, Other(String) }

struct DidDocument { id: String, verification_method: Vec<VerificationMethod>, service: Vec<Service> }

fn resolve_did(did: &str) -> Result<DidDocument, ResolveError> {
    let parts: Vec<&str> = did.split(':').collect();
    match parts[1] {
        "key" => resolve_did_key(did), // deterministic, offline
        "web" => resolve_did_web(did), // https:// + .well-known/did.json
        m => Err(ResolveError::Unsupported(m.into()))
    }
}

fn resolve_did_key(did: &str) -> Result<DidDocument, ResolveError> {
    // did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK [3]
    let mb = &did["did:key:".len()..]; // z...
    let bytes = multibase::decode(mb)?; // multicodec varint + raw
    let (codec, pubkey) = multicodec::split(&bytes)?;
    assert_eq!(codec, 0xED); // ed25519-pub
    let vm_id = format!("{}#{}", did, mb);
    Ok(DidDocument::from_multikey(did, &vm_id, pubkey))
}

fn resolve_did_web(did: &str) -> Result<DidDocument, ResolveError> {
    // did:web:example.com:path%3Ato%3Aid -> https://example.com/path/to/id/did.json [4]
    let method_specific = &did["did:web:".len()..];
    let url = if method_specific.contains(':') {
        format!("https://{}/did.json", method_specific.replace(':','/' ).replace("%3A","/"))
    } else { format!("https://{}/.well-known/did.json", method_specific) };
    let doc = reqwest::blocking::get(&url)?.json()?;
    Ok(doc)
}
```

## 4 Deep Dive

### 4.1 DID Document Resolution with `did:key` and `did:web`

`did:key` is simplest DID method [3]: no registry, no revocation registry. DID string *is* public key. Example: `did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK` expands as: decode base58btc after `z`, varint `0xed01` = Ed25519 pubkey, 32 bytes → publicKeyMultibase `z6MkhaX...`. DID Document generated on-the-fly: `verificationMethod[0]` id = DID + same z-value, `type: Multikey`, controller = DID, `publicKeyMultibase` same value. Additional `assertionMethod` relation includes that id. No service by default, but holder may embed service for OID4VP callback.

Tradeoff table:

| Method | Resolution Cost | Key Rotation | Human Intuition | Ledger-Free |
|--------|-----------------|--------------|-----------------|-------------|
| did:key | O(1) decode | none (new DID) | low `z6Mk...` opaque | yes [3] |
| did:web | O(http RTT) + TLS | via HTTPS update | high `did:web:university.eu` | yes but relies on DNS [4] |
| did:ion | O(IPFS + Bitcoin) | DID operation log | medium | needs ledger |

*`did:web` risks:* DNS hijack → attacker serves forged DID Document unless DNSSEC; GDPR deletability conflicts with verifiers caching indefinitely. Best practice: issuer `did:web` key in `assertionMethod` with short-term cache, publish `alsoKnownAs` legacy keys, implement `did:web` `did.json` with *multiple* verificationMethods for rotation where *tombstoned* older keys remain in historical docs for verifying past signatures.

### 4.2 BBS+ Signature Selective Disclosure and Zero-Knowledge Proof

Why BBS+ over SD-JWT hash hiding? SD-JWT blinds via salted hashes + disclosure array but every presentation of same claim set reveals same `sd-digest`; verifier can correlate across sessions. BBS+ proof randomization yields fresh proof bytes each time → *unlinkable presentations* [6].

Workflow:

1. **Canonicalize** — VC JSON-LD → RDF Dataset Canonicalization per vc-di-bbs [6] producing `canonical N-Quads`, each line one message.
2. **Sign** — Issuer with BBS secret key `sk` signs `L` messages producing `signature = (A,e)`. In VC proof: `proofValue = base64url(A || e)`, plus `cNonce` optional for replay prevention.
3. **Holder verify** — holder checks `Verify(pk_I, messages, sig)` [6].
4. **ProofGen** — holder chooses disclosed indices, e.g., `[0,2,5]` = type, issuer, birthYear≥?; generates ZK proof `π = (A', \bar A, D, e~, r2~, ...)`. Disclosure is adaptive: holder must also disclose which predicates are mandatory vs selective.
5. **ProofVerify** — verifier recomputes `B` commitment using disclosed message blinding commitments and verifies pairing plus Fiat-Shamir hash includes `nonce = verifier-provided challenge`.

```python
# Python conceptual BBS+ ProofGen using bbs crate via pyo3
from bbs import Bls12381KeyPair, messages_to_scalars

issuer_kp = Bls12381KeyPair.generate()
vc_messages = [
    b'<urn:credential> <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <https://example.org/StudentCard> .',
    b'<https://example.edu/students/123> <https://example.org/name> "Alice A." .',
    b'<https://example.edu/students/123> <https://example.org/birthYear> "2001"^^<http://www.w3.org/2001/XMLSchema#integer> .',
    b'<https://example.edu/students/123> <https://example.org/gpa> "3.9" .'
]
sig = issuer_kp.sign(vc_messages)

# holder discloses only type and name, hides birthYear,gpa
disclosed = {0: vc_messages[0], 1: vc_messages[1]}
proof = sig.create_proof(
    public_key=issuer_kp.public_key,
    messages=vc_messages,
    disclosed_indexes=[0,1],
    nonce=b'verifier-nonce-128bit'
)
assert issuer_kp.public_key.verify_proof(proof, disclosed, nonce=b'verifier-nonce-128bit')
# two proofs for same disclosed set must differ:
proof2 = sig.create_proof(issuer_kp.public_key, vc_messages, [0,1], nonce=b'verifier-nonce-128bit')
assert proof != proof2  # randomization -> unlinkable
```

> Theorem: *BBS+ selective disclosure is zero-knowledge and proof-unlinkable under DDH in G1 and q-SDH, even when verifier and issuer collude, provided holder nonce contributes fresh r.*

*Limit of BBS+*: requires pairing-friendly curve (BLS12-381 performance ~ 2-3ms verify vs 0.1ms EdDSA), larger proof size ~ 1.2KB for 10 messages with 3 disclosed, quantum-vulnerable.

### 4.3 RSA Accumulator Revocation Witness Update

We explain accumulator design contrasted with Bitstring Status List.

**Bitstring Status List v1.0** [11]: issuance includes `credentialStatus: {id: "...#94567", type: "BitstringStatusListEntry", statusPurpose: "revocation", statusListIndex: "94567", statusListCredential: "https://example.com/status/3"}`. Status List credential itself is VC with `credentialSubject: {type: "BitstringStatusList", statusPurpose: "revocation", encodedList: "H4sIAAAAAAAAA-3BA..."}`, where `encodedList` is `base64url(gzip(bitstring))` [11]. Verifier GETs list, checks bit. Problems:

- *Corrector leak*: verifier sees issuer domain, enabling issuer analytics on verifier IP (unless via cache/CDN).
- *Corrlatable index*: same `statusListIndex` across presentations of same VC links presentations.
- Requires `TTL` and caching; list size fixed (16KB min per spec) — 131k capacity, but 1M credentials need 8 lists.

**RSA accumulator** [12][13]: issuer maintains `N = p·q` (2048-bit, trapdoor secret), generator `g`. Initial `acc = g`. For each credential, map to *prime representative* via `prime = hash_to_prime(DID || credentialId)` (deterministic 128-bit prime). For set `S` of non-revoked (or revoked set depending on convention), `acc = g^{Π_{x∈S} prime(x)} mod N`. Membership witness `w_x = g^{Π_{y∈S, y≠x} prime(y)}`. Verify `w_x^{prime(x)} == acc mod N`. Adding/removing `x`: `acc' = acc^{prime(x)}` or `acc' = acc^{1/prime(x)}` using trapdoor `φ(N)`. Without trapdoor, manager can still update via republish; holder witness updates *without secret* if holder knows public `acc` evolution: `w_x' = w_x^{prime(new)}` etc. For revoked set design (universal), non-membership witness via Bezout: prove `prime(x)` not dividing product of revoked primes: find `a,b` with `a·prime(x)+b·Π_{revoked} =1` → `d = g^a` as non-membership proof.

Complexity:

| Operation | Bitstring | RSA Accumulator |
|-----------|-----------|-----------------|
| Issuer revoke | flip bit + re-sign list O(1) | one modular exponent O(log N) |
| Verifier check | fetch + inflate + bit op O(1) | one exponent O(log N) |
| Holder update | none | witness exponent O(k) where k revocations since issued |
| Privacy | herd `k=131k`, stable index leak | zero-knowledge non-membership possible with ZK range [13], unlinkable if prime blinded |
| ZK friendliness | Need Pedersen commitment to index to hide index [GitHub#203] | native ZK non-membership via CL proofs |

Production compromise used by AnonCreds Hyperledger Indy: accumulator for privacy, with tallet server publishing delta witness updates.

### 4.4 OID4VC Issuance Flow with SIOPv2

OID4VC explains why SSI needs OAuth 2.0 rails: wallets are mobile apps, `openid://` scheme already handles redirects, PKCE works with untrusted clients.

Sequence:

1. **Credential Offer**: Issuer or QR code provides `openid-credential-offer://?credential_offer=%7B%22credential_issuer%22%3A%22https%3A%2F%2Funiversity.example%22...`. Offer contains `grants: {"urn:ietf:params:oauth:grant-type:pre-authorized_code": {"pre-authorized_code": "abc"}}` or authorization code flow.
2. **SIOPv2 Authentication** [10]: wallet creates `id_token` header `kid: did:key:z...#z...`, payload `iss: did:key holder`, `aud: did:web:issuer`, `nonce`. Signed with holder private key; `sub_jwk` or `cnf.jwk` binds DID to key. Verifier/wallet checks DID Document validity via routine from 4.1.
3. **Token Request** (OID4VCI) [8]: POST `/token` with `grant_type=pre-authorized_code`, `pre-authorized_code`, `user_pin` if step-up required, `client_id` = `did:key:...`. Returns `access_token` JWT + `c_nonce`, `c_nonce_expires_in`.
4. **Credential Request**: POST `/credential` `Authorization: Bearer access_token`, body `format: "ldp_vc"` or `"vc+sd-jwt"`, `proof: {proof_type: "jwt", jwt: "<holder DID proof over c_nonce>"}`. Proof-of-possession binds holder DID to issued credential preventing credential theft. Issuer verifies holder DID's signature over `c_nonce`, then issues BBS-signed VC with `credentialSubject.id = holder DID`.
5. **OID4VP Presentation** [9]: Verifier RP pushes Authorization Request `openid4vp://?client_id=did:web:verifier.example&request_uri=https://verifier.example/request/12` where request contains `presentation_definition: {id, input_descriptors: [{constraints: {fields: [{path: ["$.credentialSubject.degree"]}]}}]}, nonce`. Wallet's `vp_token` contains `verifiablePresentation` with derived BBS proof and nonce.

```json
// OID4VP Authorization Request snippet [9]
{
  "response_type": "vp_token",
  "client_id": "did:web:verifier.example",
  "client_id_scheme": "did",
  "nonce": "n-0S6_WzA2Mj",
  "presentation_definition": {
    "id": "student-presentation-1",
    "input_descriptors": [{
      "id": "student-card",
      "format": {"ldp_vc": {"proof_type": ["BbsBlsSignature2020"]}},
      "constraints": {
        "fields": [
          {"path": ["$.type"], "filter": {"type": "string", "pattern": "StudentCard"}},
          {"path": ["$.credentialSubject.gpa"], "optional": true}
        ]
      }
    }]
  }
}
```

*Binding `c_nonce` prevents replay*: verifier must ensure `aud`, `nonce`, `exp` checks as in OpenID Core; wallet must reject `c_nonce` older than 5 minutes.

## 5 Empirical Analysis and Formal Proofs

### 5.1 BBS+ Performance Microbenchmarks

On Apple M2, `bls12-381` pairing `e` ~ 0.6ms, full `ProofGen` with `L=15, D=5` ~ 6.2ms, `ProofVerify` ~ 3.8ms (MatTR BBS+ library). Compare `Ed25519Signature2020` full disclosure reveal 0.08ms verify. Proof size 1240 bytes base64url vs VC-JWT 800 bytes. For 10k presentations/hour, server cost 38 CPU seconds → 1 core handles easily. Tradeoff for unlinkability is acceptable for high-assurance.

Accumulator exponentiation `modpow 2048-bit` ~ 1.1ms on same core; witness update batch 100 revocations → 110ms but can be outsourced to *witness update service* serving precomputed deltas via `accumulatorValue` stream per [12].

### 5.2 Theorem: DID Resolution Determinism

> Theorem: *For `did:key` DID `d`, `resolve(d)` terminates, returns same DID Document across all conformant implementations, and `verificationMethod[0].publicKeyMultibase == suffix(d)`.*

*Proof sketch:* Decoding `multibase` uses alphabet base58btc defined in CIDv1; multicodec varint for 0xed01 fixed length. No network IO. Hence deterministic. `did:web` not deterministic because HTTP may return different key sets unless cache-control + signature over DID Document enforced via DNSSEC chain [4]. ∎

### 5.3 Theorem: BBS+ Unlinkability

> Theorem: *Two derived proofs π1, π2 produced from same signature σ with same revealed set R but fresh randomizers r1≠r2 are computationally indistinguishable from two proofs from two independent signatures σ1,σ2 over same messages under LRSW.*

Interpretation: verifier receiving two presentations cannot tell if same credential instance reused. Proof relies on *randomizable signature* transformation: `(A,e, r1, r2)` → `A' = A·(g1^{r1})`, blinded `e'` as commitment. Randomizers make distribution uniform over proof space.

Practical requirement: holder MUST re-randomize per-verifier nonce; reuse of nonce across presentations (even with randomization) weakens to *malleability* feared as replay; wallet MUST include verifier `client_id` in Fiat-Shamir hashing per vc-di-bbs 4.19.

### 5.4 Revocation Privacy Analysis

Metrics table herd privacy vs bitstring dimension:

| Bitstring size | Capacity | Compressed 1% revoked | Verifier cache leak |
|----------------|----------|-----------------------|---------------------|
| 16KB (131k bits) | 131,072 | ~400 bytes gzip | 1/131k ≈ 0.0007% id leak |
| 128KB (1M bits) | 1,048,576 | ~2.5KB | 0.00009% |
| RSA acc 2048-bit | ∞ | 256 bytes acc + 256 witness | zero if ZK non-membership used |

Bitstring still leaks issuer *which* verifiers fetch which list via CDN logs → issuer learns verifier interest per credential family unless verifiers share central cache/CDN random fetch. RSA accumulator with ZK non-membership adds issuer obliviousness completely because witness is prover-held. Recommendation: use Bitstring for public high-volume credentials (university degrees) where herd privacy sufficient, accumulator for sensitive (medical, age-over-18) where unlinkability required [13].

## 6 Limitations and Open Problems

- **Quantum vulnerability** — Both BLS12-381 pairing and RSA-2048 broken by Shor. Post-quantum BBS variants using lattice (LaPS) or SPHINCS+ selective disclosure lack unlinkable ZK; research needed for lattice-based anonymous credentials preserving 1.2KB proofs [7 discussion].
- **did:web centralization critique:** `did:web` reintroduces DNS CA trust, undermining *self-sovereign* claim; transition to `did:dht` or `did:webvh` (verifiable history via witness log) mitigates but adds complexity [4].
- **Status List index correlation:** `statusListIndex` stable per VC links presentations across colluding verifiers even without contacting issuer. Mitigation draft proposes *BlindedBitstringStatusListEntry* with Pedersen commitment `C = g^i·h^r` and Bulletproof range proof of not-revoked [GitHub #203]; not yet adopted in Bitstring v1.0.
- **OID4VC authorization complexity:** Mixing OAuth 2.0 AS metadata with SSI grants adds new endpoints (`/.well-known/openid-credential-issuer`) yet typical enterprise IdP (Azure AD) doesn't speak OID4VCI → requires compatibility shim `OIDC bridge`. Transactional wallet attestation via Android SafetyNet / Apple AppAttest adds hardware dependency.
- **BBS+ canonicalization brittleness:** RDF-Canon depends on JSON-LD `@context` fetch; context mutation changes messages, breaking signatures. VC Data Model 2.0 mandates caching contexts locally with hash check, but few implementers do, causing interop failures with remote `https://www.w3.org/ns/credentials/v2` unavailable offline.
- **Accumulator trapdoor management:** If `p,q` leaked, attacker can forge membership witnesses for revoked credentials. Secure `N` generation without trusted dealer requires multiparty ceremony akin to Powers of Tau; seldom performed for mid-size issuer deployments [12].
- **SIOPv2 deep link phishing:** `openid://` custom scheme interceptible on compromised OS; absence of verifier DID authentication allows malicious QR to request over-disclosure. High Assurance Profile patches by requiring `x5c` or DID-based `client_id_scheme` validation mandatory.

> Future work: *Anonymous accumulator non-membership with BBS+ bundled proof* — combine BBS+ selective disclosure with RSA accumulator non-membership ZK in one Groth16 circuit proving both holder controls credential and credential not revoked without exposing `statusListIndex` or `prime(rep)` — prototype circuits in `circom` show 45k constraints feasible [13].

## 7 Conclusion

We glued four layers into one coherent SSI fabric:

1. **Identifiers** — `did:key` for ephemeral pairwise unlinkability and offline determinism [3], `did:web` for bootstrapped organizational trust via TLS [4], both resolvable to DID Documents [1][2].
2. **Credentials** — VCDM 2.0 [5] with BBS+ cryptosuite [6] enabling *selective disclosure* where holder picks `R ⊂ L`; proofs unlinkable under pairings [7]. Unlike salted-hash SD-JWT, BBS+ provides algebraic unlinkability, at cost of pairing-heavy verifier.
3. **Revocation** — Bitstring Status Lists [11] cheap but correlate via index; RSA dynamic universal accumulators [12] eliminate correlator with O(1) accumulator value at cost of trapdoor custody and witness update protocol; AnonCreds-style ZK non-membership [13] ideal for sensitive credentials.
4. **Transport** — OID4VC family [8][9][10] lifts OAuth 2.0 grant machinery to SSI, adding `c_nonce` replay binding, Pre-Authorized Code for kiosk issuance, and `presentation_definition` for declarative verifier policy. SIOPv2 self-issued ID Token closes loop so holder authenticates without external OP.

> Production checklist: cache `@context`, sign DID Web well-known with `did:web` history log, issue BBS VC with mandatory `type` and `issuer` unblinded, blind `credentialSubject.birthDate`, deploy status list with 131k capacity per issuer key rotation, run witness update service if accumulator path chosen, require `client_id_scheme=did` + `nonce` in OID4VP, and validate holder binding over `c_nonce` in OID4VCI.

SSI's promise *decentralized verification without central observer* becomes real when all four cooperate: DID for who, BBS+ for what minimum, accumulator/bitstring for still-valid, OID4VC for how over internet's existing OAuth pipes.
