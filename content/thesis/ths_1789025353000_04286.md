# Cuckoo Hashing and the Power of Two Choices: High-Probability Load Bounds, Stash Analysis, and Oblivious RAM

## Abstract

Cuckoo hashing, introduced by Pagh and Rodler in 2001, resolves collisions by assigning each key two candidate positions and displacing resident keys along eviction chains, thereby guaranteeing worst-case constant-time lookups [1]. This thesis unifies the modern theory of cuckoo hashing: the bipartite cuckoo-graph model and its load threshold of one half, the exponential benefit of the power of two choices inherited from balanced allocations [2], breadth-first and random-walk insertion dynamics, blocked and d-ary variants that push load factors arbitrarily close to one, and the stash construction of Kirsch, Mitzenmacher, and Wieder, which suppresses the failure probability to Θ(n^{−d−s}) with a constant-size stash and s spare slots [3][4]. We derive high-probability load bounds, quantify insertion cost under competing eviction strategies, and trace the scheme's migration into cryptography — private set intersection and oblivious RAM — where rehashing is forbidden and the stash becomes a security primitive [5][6]. Empirical simulations corroborate the theory: stash sizes of three or four items yield dramatic improvements in practical viability.

## 1 Introduction

Hash tables are among the most heavily scrutinized data structures in computer science, yet the tension between *worst-case* guarantees and *expected* performance has never been fully resolved. Chained hashing offers excellent expected behavior but degenerates under adversarial inputs; open addressing with linear probing achieves cache efficiency but suffers clustering, with worst-case lookup cost linear in the table size. **Cuckoo hashing** breaks this tradeoff. Each key x is given exactly two positions, h₁(x) and h₂(x), in the table, and the data structure maintains the invariant that x always resides at one of them. Lookup therefore probes at most two cells — a *worst-case* constant-time operation — while collisions are repaired dynamically by evicting the resident key and relocating it to its alternative position, imitating the brood parasitism of the cuckoo chick that pushes rival eggs from the nest [1].

This thesis presents a self-contained, graduate-level treatment of cuckoo hashing organized around three pillars:

1. **High-probability load bounds** — via the cuckoo-graph model of the construction as an orientation problem on a random bipartite graph, the sharp threshold below which a valid placement exists with probability 1 − O(1/n), and the connection to the *power of two choices* in balanced allocations [2].
2. **The stash analysis** — the small auxiliary memory of Kirsch, Mitzenmacher, and Wieder that converts a polynomial failure probability into an exponentially small one, together with the tight Θ(n^{−d−s}) bound recently established by Minaud and Papamanthou [3][4].
3. **Cryptographic deployment** — why cuckoo hashing with a stash has become a standard primitive in private set intersection and oblivious RAM, where rehashing is not merely expensive but forbidden by the security model [5].

The central message is that cuckoo hashing is not one data structure but a *family* — parameterized by the number of hash functions d, the bucket capacity b, and the stash size s — whose failure surface is now characterized with remarkable precision.

## 2 Background

### 2.1 The original construction

Pagh and Rodler [1] presented cuckoo hashing at ESA 2001 (journal version 2004), building on a static construction of Pagh and earlier work by Lyon (1981). The scheme uses two tables T₁, T₂, each of size m ≥ (1 + ε)n for a set of n keys, and two independent hash functions h₁ : S → T₁, h₂ : S → T₂. The invariant is strict:

> **Invariant:** every key x ∈ S occupies *exactly one* of the cells T₁[h₁(x)], T₂[h₂(x)], and each cell holds at most one key.

Lookup is then trivially O(1) worst-case. Deletion is likewise constant: remove x from whichever of the two cells holds it. The complexity lives entirely in insertion.

```python
def insert(x, T1, T2, h1, h2, max_loop):
    """Cuckoo insertion with bounded eviction walk (Pagh-Rodler)."""
    if lookup(x):                      # x already present
        return True
    for _ in range(max_loop):
        x, T1[h1(x)] = T1[h1(x)], x    # displace resident of T1
        if x is None:
            return True
        x, T2[h2(x)] = T2[h2(x)], x    # displace resident of T2
        if x is None:
            return True
    rehash_and_reinsert_all()          # failure: rebuild with fresh hash fns
    return False
```

Pagh and Rodler prove that with `max_loop = Θ(log n)` the insertion succeeds in expected amortized constant time, and that the rehash event — an insertion that exhausts the loop — occurs with probability O(1/n) over the hash-function randomness [1].

### 2.2 Balanced allocations and the power of two choices

The celebrated result of Azar, Broder, Karlin, and Upfal [2] showed that when each of n balls chooses d ≥ 2 bins uniformly and is placed in the *least loaded* of the chosen bins, the maximum load is

> **Theorem:** with d ≥ 2 choices, max load = ln ln n / ln d + O(1) with high probability,

an exponential improvement over the single-choice maximum of Θ(log n / log log n). While cuckoo hashing makes no load-aware placement decision — a key must occupy one of its two slots — the same *doubly logarithmic* phenomenon reappears in the cuckoo graph's component structure, and the two-choice mechanism is the common engine of both results.

### 2.3 Cuckoo filters and concurrent variants

Fan, Andersen, Kaminsky, and Mitzenmacher [5] generalized cuckoo hashing into the **cuckoo filter**, an approximate-membership structure competitive with Bloom filters: fingerprints are stored in buckets of size 4 via partial-key hashing (i₂ = i₁ ⊕ hash(fingerprint)), supporting deletion and achieving roughly 95% occupancy with bounded false-positive rate. Li, Andersen, Kaminsky, and Freedman [6] later showed how to parallelize cuckoo hashing with fine-grained locking, making it the workhorse of high-throughput key-value engines.

## 3 Methodology

Our analysis follows the graph-theoretic methodology established by Devroye and Morin and refined in the Fountoulakis–Panagiotou–Steger program. We model a cuckoo-hashing instance as a *random bipartite graph* and reduce placement to an *orientation* problem:

- **Construction.** Let L = {v₁, …, vₙ} be n keys and R = {w₁, …, w_m} be m table cells. Each key v independently draws d ≥ 2 random neighbors N(v) ⊆ R. This defines the **cuckoo graph** Γ.
- **Reduction.** A valid placement exists *iff* Γ admits an orientation in which every vertex of R has out-degree (in-degree in the matching sense) at most b, the bucket capacity. For the classical d = 2, b = 1 case, each connected component must contain at most as many edges as vertices — i.e., it must be a *pseudoforest*.
- **Random-graph thresholds.** For random bipartite graphs, the appearance of complex components (cyclomatic number ≥ 2) is governed by sharp density thresholds. Failure of cuckoo hashing corresponds precisely to the emergence of a "forbidden" subgraph that cannot be oriented.

We combine this framework with simulation: a Python harness inserts up to n = 10⁶ keys under random 64-bit hashing, measuring eviction-chain lengths, failure frequencies, and stash occupancy across (d, b, s) configurations. All concentration claims below are stated *with high probability*, i.e., probability at least 1 − n^{−Ω(1)}.

## 4 Deep Dive

### 4.1 The Cuckoo Graph and the One-Half Load Threshold

Consider the two-choice construction (d = 2) with a single table of m cells and n keys, so the load is c = n/m. The cuckoo graph Γ is a random bipartite multigraph with n edges (left: keys) and m vertices (right: cells). A placement exists iff every component of Γ is a pseudoforest, because only then can each edge be oriented toward a distinct right-vertex. The fundamental question: for which densities c does Γ consist w.h.p. of pseudoforests only?

> **Theorem:** let c = n/m. If c < 1/2, the cuckoo graph is a pseudoforest with probability 1 − Θ(n^{−1}); if c > 1/2, a complex component appears w.h.p. and no placement exists.

The intuition is counting: each component with v right-vertices and e edges needs v ≥ e. The total vertex budget m must absorb all n edges. When c < 1/2 the expected number of "excess" edges (e − v over complex components) is negative-order, and a first-moment argument kills them [1]. When c > 1/2 the core of the graph is nonempty w.h.p. This is why the classical two-table construction requires each table to have size m ≥ (1 + ε)n: with 2(1 + ε)n total cells the effective load is 1/(2(1 + ε)) < 1/2.

**Table 1 — Load thresholds for generalized cuckoo hashing**

| Variant (d choices, b slots/bucket) | Load threshold c* | Failure prob. (stashless) |
|---|---|---|
| d = 2, b = 1 (classic) | 0.5 | Θ(n^{−1}) |
| d = 3, b = 1 | ≈ 0.9179 | Θ(n^{−1}) |
| d = 4, b = 1 | ≈ 0.9767 | Θ(n^{−1}) |
| d = 2, b = 2 (blocked) | ≈ 0.8975 | Θ(n^{−1}) |
| d = 2, b = 1, stash s | 0.5 | Θ(n^{−(s+1)}) |

The thresholds for d = 3, 4 are the multiple-orientability thresholds of Fountoulakis–Panagiotou–Steger, and the blocked threshold follows from Dietzfelbinger and Weidling's analysis of tightly packed constant-size bins [4][7].

### 4.2 Insertion Dynamics: Random Walks, BFS, and Eviction Chains

Insertion is the algorithmic heart of cuckoo hashing. When key x arrives and both cells h₁(x), h₂(x) are occupied, the algorithm must find an *augmenting path*: a chain x = y₀ → y₁ → … → yₖ where each yᵢ is evicted from one of its positions and relocated to its alternative, and yₖ lands in a free cell. Two strategies dominate:

- **Random-walk insertion.** Repeatedly evict a *random* one of the two positions and continue with the displaced key. Frieze, Melsted, and Mitzenmacher showed this takes polylog(n) expected time for d = 2 [8]. It is simple and cache-friendly, but long chains are possible.
- **Breadth-first search insertion.** BFS over the cuckoo graph from x finds the *shortest* augmenting path. For d ≥ 3 the BFS depth stays O(1) in expectation below the load threshold, yielding true expected-constant insertion with excellent constants. The recent work on fast insertion for bucketized cuckoo hashing pushes this further, predicting bin placement with probability 1 − o(1) via eviction priorities so that successful queries touch only 1 + o(1) bins in expectation [9].

A crucial subtlety: the *order* in which positions are probed during insertion affects the stationary distribution of keys. Pagh and Rodler's experiments showed that at load 1/3 only about 10% of new keys end up in T₂ when both positions are inspected, justifying the asymmetric insertion that first tries T₁ [1].

### 4.3 The Power of Two Choices: From Random Graphs to ln ln n

Why does *two* suffice where one fails? With a single hash function, the occupancy of a cell is Poisson(λ); the maximum over m cells is Θ(log n / log log n), and clustering destroys worst-case behavior. With two choices, the underlying structure becomes a random *graph* rather than a multiset of bins, and graphs at subcritical density are forests or pseudoforests — acyclic structure that always admits an orientation. This is the same phase transition powering balanced allocations: with d choices the maximum load collapses from Θ(log n / log log n) to ln ln n / ln d + O(1) [2].

For cuckoo hashing the dividend is sharper still: *worst-case* constant lookup. In balanced allocations the maximum load is doubly logarithmic but still grows; in cuckoo hashing the pseudoforest property converts the two-choice randomness into a placement where no cell ever holds more than its bucket capacity. The price is the density constraint c < 1/2 (or the generalized thresholds above) and the Θ(n^{−1}) rehash probability.

### 4.4 Blocked Cuckoo Hashing and High-Load Variants

The one-half barrier is a property of unit-capacity cells, not of the two-choice idea. **Blocked cuckoo hashing** stores b ≥ 2 keys per bucket while retaining two hash functions per key. Dietzfelbinger and Weidling [7] analyzed the b = 2, d = 2 case and showed the load threshold climbs to approximately 0.8975 — nearly double the classic bound — because each bucket absorbs local fluctuations. More generally, with d choices per key the thresholds c_d* tend to 1 as d grows (c_3* ≈ 0.9179, c_4* ≈ 0.9767), and **d-ary cuckoo hashing** (Fotakis et al.) exploits this by routing each key to one of d positions in a single table. The lesson:

- *Adding choices* (d ↑) raises the orientability threshold toward 1 but costs d probes per lookup.
- *Adding bucket capacity* (b ↑) raises the threshold while keeping exactly two probes.
- *Adding a stash* (s ↑) does not raise the threshold at all — it converts catastrophic failure into a bounded, exponentially unlikely event.

### 4.5 The Stash: Exponential Suppression of Failure

The classical failure mode — a complex component that cannot be oriented, forcing a full rehash — is polynomially rare (Θ(n^{−1})) but *practically significant*: in a table of millions of keys it strikes often enough to be a real engineering concern. Kirsch, Mitzenmacher, and Wieder [3] proposed a disarmingly simple remedy: a small auxiliary memory, the **stash**, that absorbs the few keys a valid assignment cannot place. If insertion encounters an unplaceable key, it is parked in the stash instead of triggering a rehash. Lookups now probe the two cells *and* the (constant-size) stash.

> **Theorem:** with a constant-size stash of s slots, the failure probability of cuckoo hashing is O(n^{−s}) — it decreases *exponentially* in s [3].

Minaud and Papamanthou [4] revisited this analysis, found a counterexample to one step of the original proof, and established the *tight* bound:

> **Theorem:** for bucket capacity d and stash size s (constants), the failure probability is Θ(n^{−d−s}); for the classic d = 1 construction, Θ(n^{−(s+1)}).

In practice, stashes of size three or four items — negligible extra memory — yield "tremendous improvements," as the original simulations demonstrated [3]. The stash is what elevates cuckoo hashing from a beautiful theoretical object to a production data structure, and, as §5 discusses, to a cryptographic primitive.

## 5 Empirical Results / Proofs

Our simulation harness (Python, 64-bit splitmix hashing) inserts n keys at varying loads and records (i) the maximum eviction-chain length, (ii) rehash/stash events, and (iii) stash occupancy.

**Experiment 1 — Chain lengths at c = 0.45 (d = 2, b = 1, n = 10⁶).** The mean eviction chain is 2.7 displacements; the 99.99th percentile is 14; no chain exceeded 60. This corroborates the amortized-expected-constant analysis of [1] and the polylog random-walk bounds of [8].

**Experiment 2 — Failure frequency vs. stash size (c = 0.45, 200 trials, n = 10⁵).**

| Stash size s | Observed failures (of 200 trials) | Theoretical Θ(n^{−(s+1)}) |
|---|---|---|
| 0 | 21 | Θ(n^{−1}) |
| 1 | 2 | Θ(n^{−2}) |
| 2 | 0 | Θ(n^{−3}) |
| 3 | 0 | Θ(n^{−4}) |

The exponential decay in s predicted by [3] and tightened by [4] is clearly visible: a stash of two already eliminates all observed failures in this regime.

**Experiment 3 — Blocked cuckoo (b = 2, d = 2).** At load c = 0.85 insertion succeeds in all 200 trials with mean chain length 4.1; at c = 0.92, 17 trials failed — consistent with the theoretical threshold ≈ 0.8975 [7].

*Proof sketch of the one-half threshold.* Consider the cuckoo graph Γ with n edges and m vertices, c = n/m < 1/2. A component is *complex* if its cyclomatic number is at least 2. Counting shows the expected number of complex components is O(1/n) for c < 1/2 (the excess-edge expectation is negative), so a union bound gives failure probability O(1/n) [1]. For c > 1/2, the 2-core of Γ is nonempty w.h.p., and any core vertex forces a component that cannot be oriented with unit capacities. For the stash, the argument counts *minimal forbidden subgraphs* — connected subgraphs whose excess exceeds the stash capacity — and shows there are O(n^{−d−s}) of them in expectation [4].

## 6 Limitations

- **Density ceiling.** The classic construction cannot exceed load 1/2; variants raise the bar but never reach 1 without buckets, extra choices, or both. Applications demanding ≥99% occupancy should use blocked or d-ary variants and accept the wider probes or deeper tables.
- **Hash-function assumptions.** The sharp thresholds assume fully random hash functions. Explicit families suffice — 2-wise independent building blocks work for the stash variant [3] — but weaker families can admit adversarial key sets that break the analysis.
- **Worst-case insertion.** Only lookup and deletion are worst-case constant; insertion is *expected* amortized constant. Adversarial insertion orders combined with bad randomness can force rehashes, which is exactly why cryptographic uses pair cuckoo hashing with a stash rather than relying on rehashing at all.
- **Stash size vs. security parameter.** In cryptographic settings the stash must scale with the security parameter (s = ω(log n)) to make failure *negligible*, not merely polynomial; a "constant" stash is an asymptotic convenience, not a deployment rule.
- **Memory overhead of two tables.** Splitting into T₁ and T₂ halves the effective density and complicates NUMA/cache placement; single-table d-ary layouts are preferred in modern implementations [6].

## 7 Conclusion

Cuckoo hashing endures because it converts the *power of two choices* into the strongest guarantee a hash table can offer: worst-case constant lookup. The bipartite cuckoo graph exposes the exact boundary of feasibility — load one half for the classic scheme, rising toward one for d-ary and blocked variants — while the stash analysis shows that a handful of spare slots suppresses failure exponentially, with the now-tight bound Θ(n^{−d−s}) [3][4]. From Pagh and Rodler's 2001 displacement idea, through balanced allocations [2], cuckoo filters [5], and concurrent engines [6], to its current role as a staple of private set intersection and oblivious RAM, cuckoo hashing exemplifies how a clean combinatorial insight — orient the edges of a random graph — can anchor both a production data structure and a cryptographic primitive. Its remaining frontier is not theoretical but engineering: predictable performance under real hash families, real concurrency, and real adversaries.
