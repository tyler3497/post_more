# STARKs for Verifiable Computation: Reed-Solomon Proximity, the FRI Protocol, and Transparent Post-Quantum Arguments of Knowledge

## Abstract

We present a comprehensive technical treatment of STARKs — *Scalable, Transparent ARguments of Knowledge* — the first concretely realized proof system for verifiable computation that simultaneously achieves public-coin transparency with no trusted setup, plausible post-quantum security from collision-resistant hashing alone, and verification exponentially faster than re-execution. Introduced by Ben-Sasson et al. in 2018 [1], STARKs arithmetize computation into an Algebraic Intermediate Representation (AIR): an execution trace over a finite field constrained by low-degree polynomials. A composition polynomial aggregates these constraints, and its low-degreeness is attested by the Fast Reed-Solomon Interactive Oracle Proof of Proximity (FRI) [2] — a linear-time IOP that halves the evaluation domain each round via randomized folding. We analyze DEEP-FRI [3], which samples outside the domain to sharpen soundness past the Johnson bound, quantify the central engineering tradeoff of proof size versus prover time, compare STARKs against pairing-based SNARKs along setup, assumptions, and proof size, and delineate the limitations — prover constants, proof sizes, conjectured soundness — that successors like STIR and WHIR are racing to remove.

## 1. Introduction

The dream of *verifiable computation* is old: a weak verifier outsources an expensive computation to a powerful but untrusted prover, then checks the result in a fraction of the time the computation itself would take. The theoretical machinery — probabilistically checkable proofs (PCPs), multi-prover interactive proofs, Kilian's and Micali's succinct arguments — existed since the 1990s, but for two decades the constructions were, in the verdict of the STARK paper's abstract, *impractical* [1].

The first practical wave was pairing-based **SNARKs** — Groth16 compressing proofs of large computations into ~200 bytes verifiable in milliseconds. Yet SNARKs carried two structural burdens no engineering could remove. First, a *trusted setup*: a secret trapdoor generated in a ceremony that, if recovered, lets its holder forge proofs at will. Second, pairing-based assumptions that a large-scale quantum computer would shred via Shor's algorithm. A proof system meant to anchor global-scale computation could depend on neither an unauditable ceremony nor quantum-fragile hardness.

STARKs, introduced by Ben-Sasson, Bentov, Horesh, and Riabzev [1], attacked both problems at once: *transparent* (public-coin setup — no trapdoor, no ceremony), *post-quantum secure* (collision-resistant hashing as the sole assumption), and *scalable* (polylogarithmic verification — *exponentially* faster than re-execution). The authors reported the first *implemented* transparent system exhibiting this speedup concretely [1]; StarkWare Industries productized it — STARKDEX, StarkEx, StarkNet — settling hundreds of millions of transactions under STARK proofs [5].

We dissect the construction end to end: background (§2), the arithmetization pipeline (§3), a deep dive into proximity testing, FRI, DEEP-FRI, the proof-size/prover-time tradeoff, and the SNARK comparison (§4), theorems and concrete figures (§5), candid limitations (§6), and the research frontier (§7).

## 2. Background

### 2.1 The computational-integrity model

A prover $\mathcal{P}$ and verifier $\mathcal{V}$ agree on a computation $f$ and claimed output $y$; $\mathcal{P}$ produces a proof $\pi$ that $y = f(x)$ for some input $x$, and $\mathcal{V}$ checks $\pi$ quickly. The demanded properties are:

- **Completeness:** an honest prover's proof always verifies.
- **Soundness:** a cheating prover convinces $\mathcal{V}$ of a false statement with only negligible probability (*arguments of knowledge* add an extractor recovering the witness).
- **Scalability:** verification time and proof size grow polylogarithmically in the computation size $T$.

A **SNARK** adds non-interactivity and succinctness; a **STARK** adds the stronger *scalability* demand and *transparency* (public-coin setup).

### 2.2 Why SNARKs were not enough

Groth16-style SNARKs achieve ~200-byte proofs and millisecond verification, but the trusted setup is per-circuit (or a universal SRS with an update ceremony), and the pairing-based knowledge assumptions are both strong and quantum-broken. Bulletproofs removed the setup but kept linear-time verification, surrendering scalability. Nothing implemented had achieved *all three* — transparency, exponential verification speedup, generality — until STARKs [1].

### 2.3 Reed-Solomon codes

The workhorse code of the STARK world: for a finite field $\mathbb{F}$, $S \subseteq \mathbb{F}$ with $|S| = n$, and rate $\rho \in (0,1)$ [2],

> **Definition (Reed-Solomon code):** $\mathrm{RS}[\mathbb{F}, S, \rho] = \{ f : S \to \mathbb{F} \mid f \text{ evaluates a polynomial of degree } < \rho n \}.$

Relative Hamming distance $\Delta(u,v) = \frac{1}{n}|\{i : u_i \neq v_i\}|$ measures disagreement; a function $\delta$-*far* from the code disagrees with every codeword on a $\delta$-fraction of positions. Proximity testing distinguishes codewords from $\delta$-far functions while reading only a *tiny* fraction of the function — the miracle enabling succinctness. (The Johnson bound and list decoding that govern FRI's soundness analysis are treated in §4.1.)

### 2.4 Interactive oracle proofs and Fiat-Shamir

An **Interactive Oracle Proof (IOP)** generalizes PCPs and IPs: each round the prover sends an *oracle* (a long string the verifier queries at a few positions) and the verifier replies with public randomness. An **IOPP** tests proximity to a code or language [2]. Public-coin IOPs become non-interactive via the **Fiat-Shamir transform** — each challenge replaced by a hash of the transcript — yielding arguments secure in the random-oracle model with *no secret setup randomness*. Transparency is thus inherited from the IOP's public-coin structure.

### 2.5 Fields, domains, and vanishing polynomials

STARKs need fields with large smooth subgroups so the Number Theoretic Transform runs in $O(n \log n)$; ethSTARK uses the prime $p = 2^{251} + 17 \cdot 2^{192} + 1$, chosen so high powers of two divide $p-1$ [1, §5]. The **vanishing polynomial** $Z_D(x) = \prod_{a \in D}(x-a)$ converts "constraint $C$ holds at every $x \in D_{\text{trace}}$" into "the composition polynomial is divisible by $Z_D$" — a single low-degree claim.

## 3. Methodology

The STARK pipeline reduces "this computation was performed correctly" to "this Reed-Solomon codeword is close to low degree" in five stages [1][6]:

**Stage 1 — Execution trace.** The computation unrolls into an *Algebraic Execution Trace* (AET): a matrix $A \in \mathbb{F}^{t \times w}$ with $t$ rows (time steps) and $w$ columns (registers). This is the *Algebraic Intermediate Representation* (AIR).

**Stage 2 — AIR constraints.** An $(\mathbb{F}, w, t, d)$-*constraint* is a multivariate polynomial $C$ of total degree $d$ in trace variables; the AET *satisfies* the system if every constraint vanishes at every placement [7, Def. 1]. Constraints split into *boundary* ("register $j$ at step $0$ equals input $x$") and *transition* ("row $i+1$ follows from row $i$") types; degree $d$ stays tiny (usually $\le 8$) since prover cost scales with it.

**Stage 3 — Low-degree extension.** Each trace column is interpolated and evaluated over a larger domain $D$, $|D| = \beta \cdot t$, where $\beta$ is the *blowup factor* (rate $\rho = 1/\beta$); the verifier only ever queries these evaluations.

**Stage 4 — Composition polynomial and ALI.** Fiat-Shamir randomness supplies coefficients $\alpha_j$; the prover forms the *composition polynomial*

$$P(x) = \sum_j \alpha_j \cdot \frac{C_j(\text{trace}(x))}{Z_{D_{\text{trace}}}(x)},$$

dividing by the vanishing polynomial so $P$ is low-degree *iff* every constraint held everywhere. The Algebraic Linking IOP (**ALI**) batches all constraints into this one object; DEEP-ALI sharpens its soundness by evaluating quotients at an out-of-domain point [3, §5].

**Stage 5 — FRI proximity proof.** The prover shows $P$ is close to low-degree — the Reed-Solomon proximity problem FRI solves (§4.2). Fiat-Shamir compiles everything into one non-interactive proof: Merkle roots for the trace LDE, the composition polynomial, and each FRI layer, plus authentication paths for queried positions.

> **Theorem (STARK security, informal [1]):** *Assuming only a collision-resistant hash function, the compiled protocol is a scalable, transparent argument of knowledge for the AIR system: prover time $O(T \cdot \mathrm{polylog}\,T)$, proof size and verifier time $O(\mathrm{polylog}\,T)$, negligible soundness error.*

## 4. Deep Dive

### 4.1 Reed-Solomon Proximity Testing: Codes, Distance, and the Johnson Bound

For $\mathrm{RS}[\mathbb{F}, L, \rho]$, $|L| = n$, the *pair language* $(\mathrm{RS}, \delta)$ has codewords as YES-instances and $\delta$-far functions as NO-instances. An IOPP lets the verifier, with oracle access to $f$ and $q \ll n$ queries, accept codewords always and reject $\delta$-far functions except with small error $\epsilon$.

Why does proximity suffice for integrity? By contrapositive on the composition polynomial: if *any* AIR constraint fails at *any* row, $P$ is not divisible by $Z_D$ as a low-degree object, and with overwhelming probability over the random combination coefficients, $P$ is $\delta$-far from $\mathrm{RS}[\mathbb{F}, D, \rho']$ for a constant $\delta$ set by degree and rate [6]. The verifier never checks the computation directly — it checks *closeness to low-degreeness*, and the algebra does the rest.

The naive degree test needs $\Omega(d)$ queries — not succinct. The route to sublinearity is recursion on the domain, and FRI is the recursion done right.

The **Johnson bound** enters the soundness analysis: if $f$ is $\delta$-far from an RS code of rate $\rho$, the per-round rejection probability is governed by list decoding, whose radius is capped at $J(1-\rho) = 1 - \sqrt{\rho}$. Guruswami–Sudan decoding to the Johnson radius is thus the engine of FRI's soundness proof [2, §4] — and its ceiling on soundness is exactly what DEEP-FRI attacks (§4.3).

### 4.2 The FRI Protocol: Folding, Commit, and Query

FRI [2] tests proximity of $f^{(0)} : L^{(0)} \to \mathbb{F}$ to $\mathrm{RS}[\mathbb{F}, L^{(0)}, \rho]$ in two phases. Let $L^{(0)}$ be a multiplicative coset with $|L^{(0)}| = 2^n$ and $L^{(i+1)} = \{y^2 : y \in L^{(i)}\}$ — squaring halves the domain.

**Commit phase.** For $i = 0, \dots, r-1$: the verifier sends random $x^{(i)} \in \mathbb{F}$; the prover computes the *folded* $f^{(i+1)} : L^{(i+1)} \to \mathbb{F}$ by, for each $y$ with square roots $s_0, s_1 = -s_0$, interpolating the degree-$\le$-1 polynomial $p$ through $(s_0, f^{(i)}(s_0)), (s_1, f^{(i)}(s_1))$ and setting $f^{(i+1)}(y) = p(x^{(i)})$, then Merkle-commits to it. After $r$ rounds the prover sends the constant $f^{(r)}$ directly.

The key fact: if $f^{(i)}$ evaluates a degree $< d$ polynomial, $f^{(i+1)}$ evaluates a degree $< d/2$ polynomial *for every* challenge — folding halves the degree bound honestly [4, §4.1]; a far-from-code $f^{(i)}$ folds to a far-from-code $f^{(i+1)}$ with high probability over $x^{(i)}$.

The folding step is the hot loop of every STARK prover; Rust-flavored pseudocode over a prime field:

```rust
/// One FRI folding step over a coset {s0, s1}, s1 = -s0.
/// Interpolates the line through (s0, f_s0), (s1, f_s1),
/// evaluated at the verifier's random challenge.
fn fri_fold(f_s0: Felt, f_s1: Felt, s0: Felt, s1: Felt, challenge: Felt) -> Felt {
    debug_assert!(s1 == -s0, "coset must be closed under negation");
    let slope = (f_s1 - f_s0) / (s1 - s0);   // line through the two points
    f_s0 + slope * (challenge - s0)          // evaluate line at challenge
}
```

**Query phase.** The verifier samples random $s^{(0)} \in L^{(0)}$ and, per layer $i$, queries $f^{(i)}$ at both preimages and checks consistency:

$$f^{(i+1)}\big((s^{(i)}_0)^2\big) \stackrel{?}{=} \mathrm{Interpolate}\big((s^{(i)}_0, f^{(i)}(s^{(i)}_0)),\, (s^{(i)}_1, f^{(i)}(s^{(i)}_1))\big)(x^{(i)}),$$

every answer Merkle-authenticated — three field elements per layer per query. Repeating for $q$ independent queries drives the error down exponentially, roughly $(1-\delta)^q$ [2, Thm. 1.1]. The same loop in Python:

```python
def fri_fold_layer(evals, domain, challenge):
    """Fold one FRI layer: halve the domain via a random linear
    combination of even/odd parts, evaluated at the challenge."""
    folded, next_domain = {}, []
    for y in domain:
        s0, s1 = y, -y  # the two square roots of y**2
        slope = (evals[s1] - evals[s0]) / (s1 - s0)
        folded[y * y] = evals[s0] + slope * (challenge - s0)
        next_domain.append(y * y)
    return folded, next_domain
```

> **Theorem (FRI soundness, informal [2]):** *FRI is an IOPP for $\mathrm{RS}[\mathbb{F}, L, \rho]$ with perfect completeness, linear prover arithmetic complexity $O(n)$, logarithmic verifier complexity $O(\log n)$, and soundness error at most about $(1-\delta)^q$ after $q$ queries for $\delta$-far functions.*

Recent work recasts this as *round-by-round* soundness with arbitrary folding factors $m$ — the "fold function" interpolates the degree-$<m$ polynomial through each $m$-element block and evaluates at the challenge [4, §4] — the foundation of FRI's successors.

### 4.3 DEEP-FRI: Sampling Outside the Box

FRI's soundness was capped by the Johnson bound, and the ALI constraint-linking step had soundness below $1/8$, forcing many repetitions. Ben-Sasson, Carmon, Ishai, Kopparty, and Saraf's **DEEP-FRI** [3] removed the cap with a simple idea: *query the oracles at points outside the evaluation domain*.

DEEP (Domain Extension for Eliminating Pretenders): before the commit phase, the verifier samples random $z \in \mathbb{F} \setminus L^{(0)}$ and the prover commits to claimed polynomial values at $z$. Claims are *linked* to in-domain oracles by quotienting — for claimed $b = P(z)$, the verifier uses $(P(x)-b)/(x-z)$, low-degree iff the claim was correct. Since $z \notin L$, a cheater cannot precompute answers consistent both in-domain and at $z$ unless the polynomial is genuinely close to low-degree; the analysis shifts from worst-case to *average* distance, approximately $\delta$ for *all* $\delta$ under a plausible list-decoding conjecture [3, §1]. The Johnson ceiling evaporates.

The payoff is twofold [3]: **DEEP-FRI** keeps the linear prover and logarithmic verifier while improving soundness — fewer queries per security level, directly shrinking proofs; **DEEP-ALI** raises the Algebraic Linking IOP's soundness from below $1/8$ to *arbitrarily close to 1*.

One honest caveat: the sharpest DEEP-FRI analysis rests on a *conjectured* list-decoding bound (Conjecture 1.2 in [3]). Unconditional soundness holds with slightly weaker parameters. This seam is live research — STIR and WHIR seek conjecture-free analyses with comparable efficiency [4].

### 4.4 Proof Size versus Prover Time: The Parameter Tradeoff

STARK engineering is dominated by one tradeoff curve with three knobs:

| Parameter | Symbol | Typical range | Effect of increasing |
|---|---|---|---|
| Blowup factor | $\beta = 1/\rho$ | 4–16 | Slower prover (FFTs over $\beta T$), better distance $\Rightarrow$ fewer queries |
| FRI queries | $q$ | 20–100 | Linearly larger proof; exponentially smaller error |
| Grinding (PoW bits) | $g$ | 0–30 | $2^g \times$ prover cost; fewer queries needed |

*Prover time* is dominated by FFTs over domains of size $\beta T$ — $O(\beta T \log \beta T)$ — plus a hashing pass Merkle-committing each layer. STARK provers are *hash-bound* as much as FFT-bound, motivating STARK-friendly hashes (Rescue, Poseidon) of low AIR degree [7].

*Proof size* is roughly: Merkle roots per layer (tiny) $+$ $q$ query responses, each carrying $\log_2(\beta T)$ hashes of authentication path per oracle. The ethSTARK reference produced proofs on the order of $10^5$ bytes — generated in seconds, verified in milliseconds [1, §5]: three orders of magnitude larger than Groth16, with no ceremony and quantum-resistant assumptions.

Raising $\beta$ from $4$ to $16$ roughly quadruples FFT work but improves distance $1-1/\beta$ enough to cut $q$ substantially; grinding $g$ bits multiplies prover effort by $2^g$ while shaving queries. Production systems *batch* — StarkNet shares one proof across thousands of transactions — so marginal cost per transaction collapses [5].

### 4.5 STARKs versus SNARKs: A Systematic Comparison

| Dimension | zk-SNARK (Groth16-style) | zk-STARK |
|---|---|---|
| Setup | Trusted (per-circuit or SRS ceremony) | Transparent: public randomness [1] |
| Core assumption | Pairing-based knowledge assumptions | Collision-resistant hashing [1] |
| Post-quantum | No (Shor breaks pairings) | Plausibly yes |
| Proof size | ~200 bytes | ~40–200 KB (parameter-dependent) |
| Prover time | $O(T \log T)$, small constants | $O(T\,\mathrm{polylog}\,T)$, larger constants |
| Verifier time | Millisecond-scale | Polylogarithmic, millisecond-scale |
| Arithmetization | R1CS / QAP | AIR (uniform, prover-friendly) |
| Recursion maturity | Well-established | Newer; active research area |

SNARKs win where proof size is the binding constraint (L1 calldata); STARKs win where trust-minimization and quantum longevity dominate. The frontier is converging: Plonky2/Plonky3-style "SNARKs" are *FRI-based* — they keep the STARK IOP core (transparent, hash-based) while optimizing small fields and recursion, blurring the old taxonomy. Fair summary: FRI won the arithmetization wars even where the STARK name did not — proximity testing to Reed-Solomon codes is now the default polynomial-commitment substrate for new proof systems [4][6].

## 5. Empirical Results and Proofs

> **Theorem (FRI — Ben-Sasson et al., ICALP 2018 [2]):** *An IOPP for the Reed-Solomon pair language with perfect completeness, linear prover arithmetic complexity, logarithmic verifier complexity, and soundness error about $(1-\delta)^q$ after $q$ queries for $\delta$-far functions.*

> **Theorem (DEEP-FRI [3]):** *Out-of-domain sampling improves FRI soundness past the Johnson bound: under a plausible list-decoding conjecture, average distance from the code is approximately $\delta$ for all $\delta$, so per-query rejection tracks true distance.*

> **Theorem (DEEP-ALI [3]):** *The DEEP technique raises ALI soundness from below $1/8$ to arbitrarily close to $1$, preserving the IOP's efficiency.*

> **Theorem (STARK main result [1]):** *From collision-resistant hashing alone, a public-coin IOP — Fiat-Shamir-compiled to a non-interactive argument — gives a scalable transparent argument of knowledge for any AIR system: quasilinear prover, polylogarithmic proof size and verifier.*

Concretely, ethSTARK reported proofs of roughly $80$–$100$ KB over $\mathbb{F}_p$, $p = 2^{251} + 17\cdot 2^{192} + 1$, proving in seconds and verifying in tens of milliseconds [1, §5]. At systems level, StarkWare moved from the STARKDEX demonstration to StarkEx and StarkNet, settling *hundreds of millions* of transactions under STARK proofs — the largest deployment of transparent, post-quantum-plausible verifiable computation to date [5].

Representative parameter sets (order-of-magnitude, statement-dependent — the shape of the curve is the point):

| Configuration | $\beta$ | FRI queries $q$ | Approx. proof size | Prover profile |
|---|---|---|---|---|
| Aggressive (small proof) | 16 | ~30 + grinding | ~40–60 KB | Heavy FFTs + grinding |
| Balanced (ethSTARK-like) | 8 | ~60–80 | ~80–120 KB | Seconds-scale proving |
| Conservative (fast prover) | 4 | ~100+ | ~150–250 KB | Minimal LDE overhead |

## 6. Limitations

1. **Proof size.** Tens to hundreds of kilobytes versus ~200 bytes for Groth16 remains decisive where bandwidth or calldata is priced. FRI responses are Merkle-path-heavy by construction; shrinking them is the explicit target of STIR and WHIR [4].
2. **Prover constants and memory.** LDEs of size $\beta T$ plus Merkle trees over every oracle must live in RAM, and provers are hash-throughput-bound. Very large traces demand serious hardware; GPU/FPGA acceleration is an active frontier, not a solved problem.
3. **Conjectured soundness.** The tightest DEEP-FRI parameters rest on an unproven Reed-Solomon list-decoding conjecture [3] — a genuine, if narrow, gap between quoted theorems and deployed parameters.
4. **AIR expressiveness.** Uniform transition constraints are prover-friendly but less flexible than Plonkish/R1CS with custom gates and lookups; irregular control flow (e.g., memory) historically required contortions, only recently eased by STARK-adapted lookup arguments.
5. **Field and domain rigidity.** Efficient FRI needs fields with large smooth subgroups and squaring-closed domains; the field choice is load-bearing for performance and complicates cross-field recursion.
6. **Fiat-Shamir in the quantum setting.** Post-quantum security is argued in the (quantum) random-oracle model; instantiating it with a concrete hash is heuristic, and grinding parameters need re-examination against quantum query speedups.
7. **On-chain verification cost.** EVM verification without precompiles is gas-heavy precisely because of proof size — which is why rollups verify STARKs via recursion or optimized off-chain verifiers, adding system complexity.

None of these is architectural; each has a dedicated line of current research.

## 7. Conclusion

STARKs resolved a twenty-year tension: *transparency*, *post-quantum plausible security*, and *exponential verification speedup* can coexist not just asymptotically but in running code [1]. The intellectual core is a two-step reduction — computation $\to$ AIR constraint satisfaction $\to$ Reed-Solomon proximity — with FRI [2] executing the second step in linear prover time and logarithmic verifier time, and the DEEP technique [3] sharpening soundness past the Johnson bound by sampling outside the domain.

The engineering reality is a three-way negotiation between proof size, prover time, and security level, mediated by the blowup factor, the FRI query count, and grinding — a curve every production deployment walks deliberately [5]. Against SNARKs, STARKs trade larger proofs for the removal of trusted setup and quantum-vulnerable assumptions, a trade the industry increasingly accepts for infrastructure meant to last decades.

The frontier is clear: successor IOPPs (STIR, WHIR) attacking proof size with conjecture-free analyses [4]; FRI-friendly recursion making transparent composition routine; hardware acceleration collapsing prover constants; STARK-friendly primitives [7] co-designed with the arithmetization. The evidence suggests the next belongs to transparent, hash-based scalability — arguments of knowledge that ask the verifier to trust nothing but mathematics and a hash function.
