## Abstract

The Berkeley Out-of-Order Machine (BOOM) is the first open-source, industry-competitive, out-of-order superscalar implementation of the RISC-V ISA, and the first high-performance CPU built as a parameterized hardware generator rather than a fixed RTL design. This thesis presents a comprehensive microarchitectural analysis of BOOM: a superscalar front end that fetches and decodes RV64G instructions, a rename stage that maps architectural registers onto a larger physical register file to eliminate name dependences, distributed reservation-station issue windows implementing Tomasulo-style dynamic scheduling, a load-store queue with speculative memory disambiguation, a reorder buffer restoring precise exceptions and speculative state on branch misprediction, and a decoupled branch prediction pipeline. We further examine the Chisel hardware construction language and the FIRRTL compiler framework that make BOOM a true generator, enabling design-space exploration from single-issue embedded cores to quad-issue Linux-capable processors. Synthesized results in TSMC 28nm HPM, FPGA measurements, and IPC comparisons against industry baselines are discussed, together with limitations and open directions.

## 1 Introduction

The open RISC-V instruction set architecture removed the last legal barrier to high-performance processor design, but a barrier of *engineering* remained: the world's fastest out-of-order cores were closed, proprietary artifacts whose microarchitectural knowledge lived behind non-disclosure agreements. The Berkeley Out-of-Order Machine (BOOM), introduced by Celio, Patterson, and Asanovic, is the first open-source, industry-competitive, out-of-order superscalar RISC-V processor - a synthesizable, parameterized design that boots Linux and whose complete RTL is public [1]. BOOMv2 refined the design using data from synthesis, place, and route in TSMC 28 nm HPM, introducing a three-stage front end, a bigger set-associative branch target buffer, pipelined register rename, split integer and floating-point register files, and distributed issue windows [2]. The third generation, SonicBOOM, pushed the design to 3.93 DMIPS/MHz and 6.2 CoreMark/MHz, on par with early-2000s commercial out-of-order parts [3].

This thesis argues that BOOM's significance is twofold. *Microarchitecturally*, it is a complete, synthesizable embodiment of the classical Tomasulo algorithm [4] - reservation stations, register renaming, and a common data bus - extended with modern mechanisms for speculative memory disambiguation and high-accuracy branch prediction [7]. *Methodologically*, it is the first high-performance core constructed as a *hardware generator* in the Chisel embedded language [5], compiled through the FIRRTL intermediate representation [6], which turns microarchitectural parameters into elaboration-time Scala code rather than preprocessor-mangled Verilog. We analyze each subsystem in depth, present empirical results, prove a core correctness property of the rename-and-commit discipline, and close with the design's limitations and open research directions.

## 2 Background

### 2.1 The Tomasulo substrate

Out-of-order execution was born in Robert Tomasulo's 1967 algorithm for the IBM System/360 Model 91 floating-point unit [4]. Three innovations define it: (i) *reservation stations* attached to each functional unit, which buffer instructions until operands are available and thereby decouple in-order issue from out-of-order execution; (ii) *register renaming*, in which the destination architectural register of an instruction is rebound to a fresh buffer tag, eliminating write-after-write (WAW) and write-after-read (WAR) name dependences so that only true read-after-write (RAW) data dependences constrain scheduling; and (iii) a *common data bus* (CDB) on which results are broadcast to every waiting reservation station, preserving precedence while encouraging concurrency. Every modern out-of-order core, BOOM included, is an elaboration of this substrate.

| Scheduling discipline | WAR/WAW handling | Issue vs. execute | Representative |
|---|---|---|---|
| Scoreboarding | stall on name hazards | in-order issue | CDC 6600 |
| Tomasulo (1967) | hardware renaming via tags | out-of-order execute | IBM 360/91 [4] |
| Physical-register renaming | map table plus free list | distributed issue windows | BOOM, BOOMv2 [1][2] |

### 2.2 The RISC-V substrate

BOOM implements RV64G - the 64-bit base integer ISA plus the standard M, A, F, and D extensions - with the privileged architecture needed to boot a full operating system. RISC-V's regular, fixed-length 32-bit encoding (with a compressed 16-bit extension) simplifies decode relative to variable-length CISC ISAs, but the *microarchitectural* challenges of out-of-order execution - dependence tracking, speculation, and precise state - are ISA-independent. This makes BOOM an ideal vehicle for studying superscalar design: the ISA contributes clarity while the microarchitecture contributes the complexity [1].

### 2.3 The generator substrate: Chisel and FIRRTL

Chisel is a hardware *construction* language embedded in Scala: rather than describing one circuit, the designer writes a Scala program (a *generator*) that, when executed, elaborates into a circuit [5]. Parameterization is therefore ordinary host-language abstraction - loops, functions, and type parameters - instead of preprocessor macros. The elaborated circuit is emitted as FIRRTL (Flexible Intermediate Representation for RTL), a low-level hardware IR on which a compiler framework applies target-independent to target-specific transformations - constant propagation, dead-code elimination, memory inference, FPGA versus ASIC mapping - before emitting Verilog [6]. BOOM is written entirely in this style: fetch width, decode width, issue width, reorder-buffer depth, and register-file sizes are generator parameters, so one codebase spans single-issue embedded cores to quad-issue application processors [2].

## 3 Methodology

Our analysis follows the artifact itself. We take the published BOOM [1], BOOMv2 [2], and SonicBOOM [3] descriptions as the primary microarchitectural ground truth, cross-checked against the Tomasulo [4], Chisel [5], FIRRTL [6], and branch-prediction [7][8] literature. The methodology has three strands:

1. **Generator-parameter analysis.** We treat each BOOM configuration as a point in a generator parameter space - fetch/decode/issue widths, issue-window depths, physical register counts, load/store queue sizes - and examine how the microarchitecture scales with each knob, following the design-space exploration performed with TSMC 28 nm synthesis in [2].
2. **Mechanism-level modeling.** For the performance-critical loops (wakeup/select, rename allocation, load-store disambiguation) we present executable Python models and Chisel-style RTL sketches that capture the exact dependence-tracking semantics, allowing the reader to verify the scheduling arguments directly.
3. **Empirical grounding.** Where the literature reports measured numbers - DMIPS/MHz and CoreMark/MHz for SonicBOOM [3], synthesis area and timing trade-offs for BOOMv2 [2] - we reproduce them in tables and discuss what bounds they imply. Correctness of the rename-and-commit discipline is stated as a theorem and proved in Section 5.

## 4 Deep Dive

### 4.1 Distributed Reservation Stations and Dynamic Scheduling

The heart of BOOM's back end is a set of *issue windows* - the modern realization of Tomasulo's reservation stations [4]. In BOOMv1 a single centralized issue window served all execution units; BOOMv2 replaced it with *distributed* issue windows: separate windows for integer, memory, and floating-point micro-operations, each with its own wakeup and select logic [2]. Distribution is a physical-design decision with microarchitectural consequences: a monolithic window with N entries and P issue ports needs P read ports on every entry's tag comparators, and the wakeup broadcast network grows with the product of entries and ports. Splitting the window by execution cluster cuts the per-window port count, which was the dominant timing and area limiter identified in the BOOMv2 synthesis study [2].

Each issue-window entry holds a micro-operation together with the *physical* source tags (post-rename) and a ready bit per operand. Every cycle, the *wakeup* network compares result tags broadcast from the execution units against all waiting source tags; matching entries mark operands ready. The *select* network then picks up to the issue width of ready entries - oldest first - and dispatches them to register-read and then to the functional units. The following Python model captures the exact semantics of one select cycle:

```python
def select_cycle(issue_window, result_tags, max_issue):
    # Wakeup: mark operands whose producer just broadcast
    for entry in issue_window:
        for i, tag in enumerate(entry.src_tags):
            if tag in result_tags:
                entry.ready[i] = True
    # Select: oldest-ready-first, up to issue width
    candidates = [e for e in issue_window
                  if all(e.ready) and not e.issued]
    candidates.sort(key=lambda e: e.rob_idx)  # program order = age
    for e in candidates[:max_issue]:
        e.issued = True
        issue_to_register_read(e)
    return candidates[:max_issue]
```

The critical subtlety is that wakeup and select form a *loop*: a result produced this cycle can wake a dependent selected next cycle (or, with back-to-back scheduling, the same cycle via speculative wakeup). BOOM's select logic is pipelined across the issue-select and register-read stages in BOOMv2, which adds a cycle of scheduling latency but was necessary to close timing at the target frequency [2]. This is the classic tension of out-of-order design: deeper scheduling pipelines buy frequency but cost dependent-instruction latency.

### 4.2 Register Renaming and the Physical Register File

Renaming is what makes out-of-order execution *correct* in the presence of register reuse. At dispatch, each architectural destination register is assigned a fresh physical register drawn from a free list, and the *map table* - indexed by architectural register number - records the current binding. Source operands are translated through the same table. Because every write targets a distinct physical register, WAW and WAR hazards vanish by construction; only true RAW dependences remain, and those are tracked by the tag mechanism of Section 4.1 [4].

BOOMv2 introduced two refinements informed by synthesis data [2]. First, the rename stage is *pipelined*, splitting map-table read, free-list allocation, and map-table update across cycles so that rename does not limit frequency at wide decode. Second, the integer and floating-point register files are *split* into separate physical files with independent free lists, eliminating the false sharing of rename resources between integer and FP code that plagued BOOMv1's unified file (where the floating-point unit shared issue ports and register-access ports with an integer ALU).

The Chisel sketch below shows the essence of a rename map table as BOOM generates it - note how the architectural and physical register counts are plain Scala parameters, so the same generator produces a 32-entry embedded rename table or a 128-entry server-class one:

```chisel
class RenameMapTable(nArch: Int, nPhys: Int) extends Module {
  val io = IO(new Bundle {
    val archSrc = Input(Vec(2, UInt(log2Ceil(nArch).W)))
    val archDst = Input(UInt(log2Ceil(nArch).W))
    val renameEn = Input(Bool())
    val physSrc = Output(Vec(2, UInt(log2Ceil(nPhys).W)))
    val physDst = Output(UInt(log2Ceil(nPhys).W))
  })
```

*Speculative* renaming adds one more requirement: on a branch misprediction, the map table must be restored to the state at the mispredicted branch. BOOM checkpoints the map table (or, equivalently, replays rename from the reorder buffer's architectural-to-physical log), so recovery is a single-cycle table restore rather than a pipeline drain-and-refill of the rename structures [1].

### 4.3 Memory Disambiguation and the Load-Store Queue



- **No match:** the load proceeds to the data cache immediately.
- **Address match with data ready:** *store-to-load forwarding* supplies the value directly from the SQ, bypassing the cache.
- **Address match with data not ready, or address unknown:** the load must wait; issuing it speculatively risks a *memory-order violation*.



| LSQ mechanism | What it resolves | Cost of being wrong |
|---|---|---|
| Store-to-load forwarding | RAW through memory | pipeline flush on mis-forward |
| Speculative disambiguation | load vs. unknown store address | memory-order violation, flush |
| Fence handling | RVWMO ordering guarantees | over-serialization if too strict |

### 4.5 The Generator Methodology: Chisel and FIRRTL in Practice


- **Width parameterization without duplication.** The wakeup comparator network, the select tree, and the CDB arbitration are all generated by Scala loops over the issue width. Changing a 2-issue BOOM into a 4-issue BOOM is a parameter change, not a rewrite - and the BOOMv2 paper's exploration of exactly this trade-off was performed by regenerating and resynthesizing, not by hand-editing RTL [2].
- **Type-safe hardware construction.** Chisel's `UInt`, `Bundle`, and `Vec` types carry widths through the generator; width mismatches are Scala type errors at elaboration time, not silent Verilog truncations found in simulation.
- **Compiler-driven retargeting.** The FIRRTL framework [6] lowers the elaborated circuit through verified passes - and, crucially, *different* pass pipelines for FPGA versus ASIC targets. Memory inference maps the register file and predictor tables to SRAM macros on ASIC (the foundry memory compilers used in [2]) and to block RAM on FPGA, from the same source.

## 5 Empirical Results and Formal Arguments

### 5.1 Measured results across BOOM generations

The three published BOOM generations trace a clear arc from proof-of-concept to industry-competitive performance:

| Generation | Key microarchitectural features | Reported results |
|---|---|---|
| BOOMv1 [1] | Centralized issue window, unified physical register file, RV64G, boots Linux | First open-source OoO RISC-V; competitive IPC on SPEC-like integer code |
| BOOMv2 [2] | 3-stage front end, set-associative BTB, pipelined rename, split int/FP register files, distributed issue windows, split issue-select and register-read | TSMC 28 nm HPM synthesis, place and route; area/timing trade-offs quantified per structure |
| SonicBOOM [3] | Tuned predictor and memory system, RV64GC, 32 KB L1I, 32 KB L1D, 512 KB L2 | 3.93 DMIPS/MHz, 6.2 CoreMark/MHz - on par with early commercial out-of-order cores |

The SonicBOOM numbers deserve emphasis: 3.93 DMIPS/MHz and 6.2 CoreMark/MHz place an open-source, Chisel-generated core in the same IPC class as early-2000s commercial designs - the first time the open-hardware community could make that claim with a synthesizable artifact rather than a simulator [3]. The BOOMv2 synthesis study is equally important for what it *cost*: distributed issue windows, pipelined rename, and split register files were not aesthetic choices but responses to concrete timing failures in the centralized BOOMv1 design, measured in a commercial 28 nm flow [2].

### 5.2 Correctness: precise state under renaming

Performance without correctness is noise. The central invariant of BOOM's back end is that speculation - branch prediction, memory-disambiguation prediction - never becomes architecturally visible, because retirement is strictly in order through the reorder buffer. This is captured by the following theorem:

> **Theorem (Precise state under renaming).** Suppose every dispatched instruction is assigned a unique physical destination register, writes its result exactly once, and instructions retire from the reorder buffer strictly in program order, freeing the previous physical binding of each architectural destination at retirement. Then the architectural register state observable at any retirement boundary equals the state produced by sequential in-order execution of the same instruction stream. In particular, write-after-write and write-after-read hazards are unobservable, and a misprediction flush that discards all unretired instructions restores exact sequential semantics.

*Proof sketch.* Consider the map table as a function M from architectural registers to physical registers, and the reorder buffer as a program-ordered queue of in-flight instructions each carrying its architectural destination a, its fresh physical destination p, and the previous binding q = M(a) at dispatch. By the uniqueness of p, no two in-flight instructions share a destination, so WAW is impossible among unretired instructions; by the rebinding of M(a) to p at dispatch, any younger reader of a observes p, while any older reader already captured q or its value at its own dispatch, so WAR is impossible. Hence the only cross-instruction data flow is through true RAW dependences tracked by tags - exactly the dependences of the sequential program. Retirement processes the queue head-to-tail; when instruction i retires, all older instructions have retired, so the architectural state equals sequential execution through i. Freeing q at retirement is safe because no unretired instruction can name q: any reader of a dispatched after i sees p, and any reader dispatched before i retired before or with i. On a misprediction, discarding the queue and restoring the checkpointed map table M returns the machine to the sequential state at the mispredicted branch, since every discarded instruction is younger than the retirement boundary. ∎

The corresponding TLA+ sketch of the commit protocol - the piece of the design where the theorem bites - is:

```tla
---- MODULE RenameCommit ----
EXTENDS Naturals, Sequences
VARIABLES rob, map, retired

Commit ==
  /\ rob /= <<>>
  /\ LET head == Head(rob) IN
     /\ head.executed              \* head is complete
     /\ head.noException           \* precise-exception check
     /\ map' = [map EXCEPT ![head.archDst] = head.physDst]
     /\ rob' = Tail(rob)
     /\ retired' = Append(retired, head)

FlushOnMispredict ==
  /\ rob' = SubSeq(rob, 1, mispredictIdx)  \* drop wrong-path
  /\ map' = checkpointMap                 \* restore rename state
  /\ UNCHANGED retired
====
```

The model checker's job is to verify that `retired` is always a prefix of the sequential execution trace - the formal shadow of the theorem above. In practice, BOOM's verification relies on co-simulation against the Spike ISA simulator within the Chipyard framework, diffing architectural state at every retirement boundary; the theorem explains *why* that differential testing is sufficient: any deviation from sequential semantics must manifest at a retirement boundary.

## 6 Limitations

No honest treatment of BOOM omits its limits.

1. **The branch-prediction wall.** As Section 4.4 argued, misprediction penalty scales with depth times width, and the remaining mispredictions live in rare branches that history-based predictors cannot learn [8]. BOOM's decoupled front end hides latency but not wrong-path work; each misprediction at quad-issue widths discards tens of instructions. Better predictors (larger TAGE tables, perceptron or neural hybrids) cost area and power faster than they buy accuracy.
2. **LSQ scalability.** Disambiguation is associative: every load compares against every older store, so compare energy grows with the product of queue depths. Widening the memory window - the main source of memory-level parallelism - directly taxes power. Store-to-load forwarding paths add bypass multiplexing on the critical load-use loop.
3. **The generator QoR gap.** Chisel/FIRRTL raise productivity enormously [5][6], but generated RTL still trails hand-tuned commercial RTL in absolute frequency and area on the same process; the FIRRTL pass pipeline cannot replicate decades of manual datapath tuning. Debugging is also harder: the Verilog a designer simulates is two compilation steps removed from the Chisel they wrote.
4. **Verification burden.** An open-source out-of-order core inherits the full verification obligation of any OoO design - memory-model conformance under RVWMO, precise-exception behavior across speculation, predictor-state recovery - with a fraction of the verification resources of a commercial team. Differential testing against Spike catches architectural deviations but not microarchitectural performance bugs or subtle timing-dependent hangs.
5. **Single-thread focus.** BOOM is a single-hart core; the generator methodology has not yet been demonstrated on simultaneous multithreading or tightly-coupled multicore coherence at competitive performance, where shared-resource scheduling interacts with everything analyzed here.

## 7 Conclusion

The Berkeley Out-of-Order Machine demonstrates two propositions at once. First, that the full classical machinery of out-of-order execution - Tomasulo's reservation stations and renaming [4], distributed wakeup/select scheduling, speculative memory disambiguation, reorder-buffer precise state, and TAGE-family branch prediction [7] - can be realized as an open, synthesizable, Linux-booting RISC-V core competitive with commercial designs of its era [1][2][3]. Second, that such a core can be built not as a fixed RTL artifact but as a *generator* in Chisel [5], compiled through FIRRTL [6], so that the entire microarchitecture becomes a point in an explorable parameter space rather than a single frozen design.

The deeper lesson is methodological. For fifty years, out-of-order microarchitecture was a priesthood: the knowledge existed, but the artifacts did not, or not openly. BOOM - and the generator methodology behind it - changed the epistemic terms. A graduate student can now read the Chisel source of a real out-of-order pipeline, change the issue width, regenerate, synthesize, and measure. That is not merely an engineering convenience; it is a change in what computer architecture *is as a science* - from the study of closed artifacts to the study of open, parameterized, reproducible machines.
