# WebAssembly as a Universal Compilation Target: Validation Semantics, Sandboxing, WASI, and the Component Model

## Abstract

WebAssembly (Wasm) has grown from a browser bytecode into a portable, sandboxed compilation target. This thesis gives a rigorous account of the four pillars that make this possible. First, we formalize Wasm's *validation semantics*: a single-pass, linear-time type checker over module function bodies that establishes preservation and progress for the small-step operational semantics, with the soundness proof mechanized in Isabelle/HOL [2]. Second, we analyze the sandboxing model — linear memory disjoint from code, structured control flow with no computed jumps, and type-checked indirect calls — showing how it reduces software-fault isolation to validation plus bounds enforcement, and how zero-cost sandbox transitions are formally characterized [1][4]. Third, we examine the WebAssembly System Interface (WASI) as a capability-based syscall layer that replaces ambient POSIX authority with unforgeable handles [8]. Fourth, we develop the Component Model: WIT interface types, worlds, and the canonical ABI for composing polyglot components under shared-nothing linking. We synthesize published empirical results on validation throughput, sandbox overhead, real-world binary corpora, and binary exploitability [6][7][5], and close with open problems in garbage collection, concurrency, and component-model verification.

---

## 1 Introduction

A *universal compilation target* is language-, platform-, and embedding-independent: any source language compiles to it, it runs on any ISA, and any embedder — browser, serverless runtime, kernel — can host it without changing its semantics. WebAssembly, standardized through the W3C WebAssembly Working Group and Community Group, is the first industrial attempt to realize this idea at scale [1].

Wasm began as a compact, efficiently validatable bytecode for the web, co-designed by engineers from all major browser vendors [1]. Within a few years it had escaped the browser: standalone runtimes execute Wasm on servers, edge networks run it per request, and plugin systems embed it as an untrusted-code sandbox. This migration rests on four technical pillars, each examined in depth below:

1. **Validation semantics.** Every module is type-checked *before* execution by a declarative, single-pass validator — the load-time proof that it cannot violate the embedder's safety invariants.
2. **Sandboxing.** Linear memory, structured control flow, and typed function references confine even buggy or malicious modules to their own address space.
3. **WASI.** The WebAssembly System Interface replaces ad-hoc host bindings with a standardized, capability-based system interface.
4. **The Component Model.** WIT interface types and the canonical ABI lift composition from untyped shared-memory linking to typed, language-agnostic component composition.

The central claim of this thesis is that these four pillars are not independent features but a single coherent design: validation makes sandboxing cheap, sandboxing makes capability-based system interfaces meaningful, and capabilities make typed component composition secure. Section 2 reviews the core language and its formal specification style; Section 3 describes our methodology; Section 4 develops each pillar; Section 5 synthesizes empirical and mechanized results; Section 6 states the limitations; Section 7 concludes.

## 2 Background

### 2.1 The core language

Wasm is a *stack-based virtual instruction set architecture*.

### 2.2 A language specified by inference rules

Unusually for an industry standard, Wasm was "designed with a formal semantics from the start" [1].

### 2.3 From MVP to an evolving standard

The 2017 minimum viable product froze a deliberately small core.

### 2.4 The embedder contract

Wasm has no built-in I/O, no syscalls, and no ambient authority.

## 3 Methodology

This thesis is a synthesis of primary sources:

- **Formal analysis.** We work from the specification's inference-rule presentation [1] and Watt's Isabelle/HOL mechanization — verified checker and interpreter, machine-checked soundness proof [2]; theorems and proof sketches in Section 4.1.
- **Security literature.** Binary-security analyses [5] and large-scale studies of real-world binaries [7], separating the guarantees validation provides from those it does not.
- **Sandboxing formalisms.** The SFI literature applied to Wasm: the characterization of *zero-cost* sandbox transitions and its static verifier [4], and the constant-time type-system extension CT-Wasm [3].
- **Interface and composition design.** For WASI and the Component Model — where peer-reviewed literature is still sparse — the standardization repositories and design documents: the WIT language, the canonical ABI explainer, and WASI's capability-security principles [8].

**Scope.** We treat Wasm core through version 2.0, WASI through the Preview 2 developer release, and the Component Model MVP. Notation follows the specification: *C* for validation contexts, *S* for stores, *t** for type sequences.

## 4 Deep Dive

### 4.1 Validation Semantics: the Type System as a Security Gate

Validation is best understood not as a parser check but as a *type system* whose soundness theorem is the module's safety certificate.

**The validation context.** Validation runs relative to a context *C* recording everything an instruction sequence may legally reference:

| Component | Contents |
|---|---|
| *C.funcs* | function types of all defined and imported functions |
| *C.tables* | table types (limits and element type) |
| *C.mems* | memory types (page limits) |
| *C.globals* | global types (value type × mutability) |
| *C.locals* | value types of parameters and locals of the current function |
| *C.labels* | result types of enclosing structured labels |
| *C.return* | declared result type of the current function (if any) |

**The typing judgment.** The central judgment is *C ⊢ e* : [*t₁**] → [*t₂**]*: under context *C*, instruction sequence *e** maps an operand stack of shape [*t₁**] to [*t₂**]. Instructions have polymorphic stack types — `i32.add : [i32 i32] → [i32]`, while `br l` is well-typed under any stack shape whose arity matches label *l*. Structured instructions introduce labels typed by their block type; `br` and `br_table` target only lexically enclosing labels. Because every branch target is statically known and every stack height follows from the type derivation, validation is a *single forward pass* with an explicit control-frame stack — linear in code size, no fixpoint [1].

```wat
(func (param i32 i32) (result i32)
  local.get 0
  local.get 1
  i32.add)   ;; C ⊢ body : [i32 i32] → [i32]
```

The `block`, `loop`, and `if` instructions each introduce a label whose type is the block type; `br` and `br_table` may only target lexically enclosing labels, and `br_table`'s operands must agree on a common arity.

**Soundness.** The specification's safety claim is the standard type-soundness pair, mechanized end-to-end in Isabelle/HOL [2]:

> **Theorem 1 (Preservation).** If ⊢ₛ *S*; *F*; *e** : [*t**] and *S*; *F*; *e** ↪ *S′*; *F′*; *e′**, then ⊢ₛ *S′*; *F′*; *e′** : [*t**]. Reduction preserves store and configuration typing.
>
> *Proof sketch.* Induction on the reduction derivation. The administrative cases — frame and label manipulation — appeal to store extension (growing memory preserves store typing), frame well-formedness, and the label-arity invariant from validation. The mechanization closes roughly 20,000 lines of proof [2]. ∎

> **Theorem 2 (Progress).** If ⊢ₛ *S*; *F*; *e** : [*t**] and *e** is not a bare value sequence, then either *e** = `trap`, or there exist *S′*, *F′*, *e′** with *S*; *F*; *e** ↪ *S′*; *F′*; *e′**.
>
> *Proof sketch.* Case analysis on the first instruction of *e**. Every well-typed instruction either is a value, reduces by its operational rule, or — for partial operations (`div`, memory access, `call_indirect`) — has a defined trap case covering exactly the inputs where reduction is undefined. No well-typed configuration is stuck. ∎

Two consequences follow.

**Mechanization as specification debugging.** Watt's mechanization was developed *concurrently* with the specification draft, and proving soundness exposed several genuine specification bugs — incorrect typing and reduction rules — corrected before the 1.0 release [2]. A formal semantics written to be mechanized is a qualitatively better artifact than one written only to be read.

**Type-driven extensions: CT-Wasm.** The same machinery enforces stronger policies: CT-Wasm [3] annotates values *secret* vs. *public*, blocking secret flows to public outputs and timing leaks through control flow. The extended type system is likewise mechanized, with proofs of information-flow security and constant-time execution, plus a verified checker and a V8-integrated implementation. CT-Wasm shows validation-time enforcement scales beyond memory safety to *hyperproperties* — at the cost of annotation, with no runtime overhead.

### 4.2 Sandboxing: Linear Memory, Structured Control Flow, and SFI

Sandboxing in Wasm is the composition of three mechanisms, each simple, whose conjunction is strong.

**1. Disjoint linear memory.** A module's memory is a single contiguous byte array, disjoint from engine code, stacks, and heap. Every `load`/`store` computes *ea = i + offset* and traps unless *ea + N ≤ current memory size*. A module cannot name an address outside its sandbox [1]: the boundary is *algebraic*, following from the type of memory operations rather than OS page tables.

**2. Structured control flow.** There are no computed jumps: `br`, `br_if`, `br_table` target only lexically enclosing labels; `call_indirect` consults a table of function references. Control-flow integrity is a *validation-time theorem* — ROP gadgets are inexpressible because arbitrary code addresses cannot be named [1].

**3. Typed indirect calls.** `call_indirect` takes a table index and an expected function type; the engine checks bounds and type equality at runtime, trapping on mismatch. With the call stack hidden, there are no exposed code pointers to corrupt at all.

The contract is asymmetric: the host is trusted, the module is not, and a module's authority is exactly its imports.

**Zero-cost transitions.** Every sandbox–host call naively pays a tax: stack switching, register saving, invariant re-establishment. Kolosick et al. [4] formalize *zero-cost conditions* under which transitions need no such switching, develop **VeriZero**, a static binary verifier checking Lucet-compiled Wasm against these conditions in seconds, and prove VeriZero sound via a logical relation. Their SegmentZero32 prototype, a purpose-built SFI system, matches Native Client's performance — reframing sandboxing overhead as a *verifiable property of compiled code* rather than an intrinsic cost.

**What sandboxing does not give.** Lehmann, Kinder, and Pradel [5] provide the essential corrective: sandboxing confines the module but does not make its *own* code memory-safe. Buffer overflows and use-after-free in C/C++ compiled to Wasm remain fully exploitable *within* the sandbox — overwriting supposedly constant data, corrupting the Wasm-level heap, or diverting control flow where validation permits. Protections routine natively (stack canaries, ASLR, stack/heap guard pages) are frequently absent in Wasm toolchains. The table summarizes the asymmetry:

| Property | Native binary (hardened) | Wasm module |
|---|---|---|
| Escape the process / read host memory | prevented by OS | prevented by validation + bounds checks [1] |
| Arbitrary code pointers / ROP | mitigated (CFI, ASLR) | inexpressible by construction [1] |
| Intra-program buffer overflow | mitigated (canaries, ASLR) | fully exploitable [5] |
| Overwrite constant data | prevented (read-only pages) | exploitable [5] |
| Timing side channels | out of scope | out of scope (cf. CT-Wasm [3]) |

The lesson is precise: validation proves *embedder* safety, not *program* safety.

### 4.3 WASI: Capability-Based System Interfaces

Core Wasm deliberately defines no system calls; every host invented its own import ABI, fragmenting the ecosystem.

**Two kinds of capability.** Following the WASI design principles [8]:

- *Handles* — unforgeable, dynamically passed references (file descriptors, sockets) carrying *rights* (e.g., `fd_read`, `fd_write`) that attenuate what the holder may do. A handle cannot be forged, guessed, or escalated; it can only be received from another holder.
- *Link-time capabilities* — functions requiring no handle arguments, used sparingly and kept interposable so they remain refusable.

This is capability-based security in the object-capability sense — per-resource, unforgeable, transferable — in contrast to POSIX's ambient model:

| Aspect | POSIX | WASI |
|---|---|---|
| Authority model | ambient (uid-based, global namespace) | capabilities (handles + rights) [8] |
| Opening a file | `open("/abs/path")` resolves against global root | only via preopened directory handles |
| Right attenuation | limited (e.g., `O_RDONLY`) | first-class per-handle rights |
| Network access | ambient socket creation | granted socket handles |
| Portability | syscall numbers vary by OS | single stable interface over any host |

**From Preview 1 to Preview 2.** WASI Preview 1 defined a snapshot syscall-like interface. Preview 2 rebuilt WASI on the Component Model: every interface (`wasi:filesystem`, `wasi:http`, `wasi:clocks`, …) is specified in WIT, and a *world* describes a component's full import/export contract. The system interface thereby inherits the component model's typing, versioning, and composition machinery.

### 4.4 The Component Model: WIT, Worlds, and the Canonical ABI

Core modules compose poorly: linking is untyped name matching over a *single shared linear memory*, with no common notion of a string across languages.

**Components vs. modules.**

| Feature | Core module | Component |
|---|---|---|
| Value types | scalars, vectors, references | strings, lists, records, variants, options, results, resources |
| Interface description | none (name-based convention) | WIT, embedded in the binary |
| Memory model | single shared linear memory | each component isolated; data copied across boundaries |
| Composition | static linking into one address space | interface-level linking of typed components |

**WIT: the interface definition language.** WIT declares the contract a component offers and requires; a *world* assembles imports and exports into a complete picture:

```wit
package example:processor@1.0.0;

interface types {
    record image {
        width: u32,
        height: u32,
        pixels: list<u8>,
    }
}

world processor {
    import host-logging;
    export run: func(img: image) -> result<image, string>;
}
```

WIT supports records, variants, enums, flags, options, results, tuples, lists, strings, and *resources*: handle types with ownership semantics, so a file or socket crosses a component boundary with its destructor and access rights intact.

**The canonical ABI.** WIT values are high-level; core Wasm understands only scalars and linear memory. The *canonical ABI* defines the translation: **lowering** converts an interface value into core values plus memory writes (allocating with the component's `realloc`, laying out strings as pointer/length pairs), and **lifting** inverts it. The translation is precise enough that Rust, C, and JavaScript components can exchange a `result<list<string>, error>` without sharing an allocator, a string representation, or a memory [8].

A Python sketch of string lowering (real implementations live in the host runtime):

```python
def lower_string(s: str, mem: bytearray, realloc) -> tuple[int, int]:
    data = s.encode("utf-8")          # canonical ABI mandates UTF-8
    ptr = realloc(0, 0, 1, len(data)) # canonical realloc: align=1
    mem[ptr:ptr+len(data)] = data
    return (ptr, len(data))            # core signature: (i32, i32)

def lift_string(ptr: int, length: int, mem: bytearray) -> str:
    s = bytes(mem[ptr:ptr+length]).decode("utf-8")  # traps on invalid UTF-8
    return s
```

Note the trap on invalid UTF-8: the canonical ABI *validates interface values* at the boundary, extending "validate before trust" from code to data.

**Composition and virtualization.** Because components never share memory, linking is memory-safe by construction: one component cannot corrupt another's state, at the price of copying across boundaries. Components nest, wrap, and virtualize — a host can interpose on any import to enforce policy, which is how WASI Preview 2 implements capability attenuation. Any language with a WIT binding generator (Rust, C/C++, Go, Python, JavaScript, C#) can produce and consume components.

## 5 Empirical Results and Mechanized Proofs

**Validation performance.** Validation is a single-pass algorithm, linear in code size and negligible relative to compilation [1] — which is what makes load-time verification viable at edge scale, where modules are validated per request.

**Execution performance vs. native.** Jangda et al. [6] (arXiv:1901.09056) measured SPEC-class workloads compiled to Wasm against native code and found substantial slowdowns — register pressure from the stack machine, extra branches for bounds checks, reserved registers, immature codegen — rather than any fundamental barrier. The gap has narrowed as compilers matured, but the study remains the canonical quantification of the portability tax.

**The real-world corpus.** Hilbig, Lehmann, and Pradel [7] analyzed thousands of real-world Wasm binaries — dominantly C/C++ via Emscripten, plus Rust and AssemblyScript — used for gaming, libraries, and cryptomining. Their findings ground the sandboxing discussion: most deployed Wasm is memory-unsafe source code, so intra-sandbox exploitability [5] is the common case.

**Sandbox transition costs.** Kolosick et al. [4] showed the boundary need not be expensive: their zero-cost conditions, checked by the VeriZero static verifier in seconds per binary, permit transitions without stack switching, and their SegmentZero32 prototype matches Native Client's performance. Sandboxing overhead is a property to be *verified*, not merely measured.

**Mechanized metatheory.** Watt [2] delivered the first fully mechanized soundness proof for Wasm 1.0 — a verified type checker and interpreter, differential fuzzing against production engines, and specification bug fixes driven by failed proof attempts. CT-Wasm [3] extended the mechanization to information-flow and constant-time properties, with an OCaml reference interpreter and a V8-integrated implementation.

| Study | Claim | Method | Artifact |
|---|---|---|---|
| Haas et al. [1] | linear-time validation; sandbox by construction | formal spec + implementations | Wasm 1.0, spec |
| Watt [2] | type soundness, mechanized | Isabelle/HOL | verified checker + interpreter |
| Watt et al. [3] | constant-time crypto via types | mechanization + V8 port | CT-Wasm toolchain |
| Kolosick et al. [4] | sandbox transitions can be zero-cost | logical relation + verifier | VeriZero, SegmentZero32 |
| Lehmann et al. [5] | classic exploits survive in Wasm | exploit PoCs, 3 platforms | attack primitives |
| Jangda et al. [6] | Wasm slower than native; causes identified | SPEC measurements | performance breakdown |
| Hilbig et al. [7] | real Wasm is mostly unsafe C/C++ | corpus analysis | binary dataset |

## 6 Limitations

**Validation proves host safety, not program safety.** The sharpest limitation is also the most misunderstood: a validated module cannot escape its sandbox, but nothing is guaranteed about what it does *inside* it [5]. Memory-unsafe languages retain their vulnerabilities; validation is a confinement proof, not a correctness proof.

**Side channels are out of scope.** The core semantics say nothing about timing, caches, or speculation: constant-time discipline needs type systems like CT-Wasm [3], and Spectre mitigations remain the engine's burden.

**Concurrency and managed types strain the formalism.** The threads proposal required repairing JavaScript's relaxed memory model first [2]; the GC proposal's type hierarchy re-opens the mechanization effort with each extension.

**The Component Model is still being formalized.** The canonical ABI and WIT semantics live primarily in design documents and a WAST test suite rather than a mechanized specification [8]; the reference interpreter and formal spec are stated future work. Until they exist, component-level safety rests on implementation correctness, not proof.

**Costs of shared-nothing composition.** Copying across component boundaries, canonical-ABI lifting/lowering, and handle management add overhead versus shared-memory linking; the performance envelope of heavily decomposed component graphs is not yet well characterized.

**WASI's capability ergonomics.** Capability discipline is unfamiliar, and the WASI interface set (Preview 2/0.3 async, streams, futures) is still stabilizing; misconfigured preopens can quietly reintroduce ambient authority.

---

## 7 Conclusion

WebAssembly's claim rests on a coherent stack of ideas. *Validation semantics* turns load time into proof time: a linear-time checker establishes preservation and progress, machine-checked [1][2]. *Sandboxing* — disjoint linear memory, structured control flow, typed indirect calls — reduces isolation to validation plus bounds enforcement, with transition costs made formally negligible [4]. *WASI* replaces ambient POSIX authority with unforgeable capabilities [8]. And the *Component Model* lifts composition from untyped shared-memory linking to typed, shared-nothing, polyglot components via WIT and the canonical ABI [8].

The honest accounting of Section 6 does not diminish this achievement; it locates it. Wasm solved the *embedder's* problem — executing untrusted code safely, portably, efficiently — with unusual rigor. The *developer's* problem — correct, side-channel-free, efficiently composable code — remains partially open: mechanizing the component model, verifying the compilers, carrying capability discipline up the stack. The narrow waist of computing is taking shape; what flows through it is up to us.
