# From Wahbe to vWasm: A Lineage of Software Fault Isolation — Native Client, Linear-Memory Sandboxing in WebAssembly, Capability-Based WASI, and the Verified Sandbox

## Abstract

Software-based fault isolation (SFI), introduced by Wahbe, Lucco, Anderson, and Graham in 1993 [1], showed that untrusted native code could be confined to a fault domain by rewriting its memory accesses and control transfers. Google's Native Client industrialized the idea for the web, exploiting x86 segmentation and bundle-aligned code to sandbox native plugins at near-native speed [2], before ceding the field to WebAssembly, whose validation rules enforce sandboxing *by construction* rather than by post-hoc verification [3]. This article traces that lineage and the current drive to verify it end to end. We develop the formal sandboxing invariant shared by NaCl, WebAssembly's linear memory, and WASI's capability-based system interface; we examine the Component Model's world-scoped composition as capability confinement at the module boundary [9]; and we study three verification frontiers: vWasm/rWasm, machine-checked sandboxing compilers [6]; CT-Wasm, a type-driven constant-time extension with a mechanized soundness proof [4]; and CompCertSFI, a Coq-verified SFI transformation inside a verified C compiler [8]. We compare masking versus bounds-checking enforcement, analyze residual side channels, and identify open problems in the verified composition of sandboxed components.

## 1 Introduction

The problem is ancient: run code you do not trust, at speed you cannot sacrifice, without letting it touch anything it should not. Operating-system processes solve it with privilege rings and page tables, at the cost of a context switch per boundary crossing. Language runtimes solve it with type safety, at the cost of abandoning existing low-level code. *Software fault isolation* occupies the middle ground: take arbitrary compiled code, rewrite it so that every dangerous operation is constrained, and prove — or at least check — that the rewriting worked [1].

Three decades of systems research refine that bargain. Wahbe et al. showed two fault domains could share an address space at ~4% overhead on MIPS [1]. Google's Native Client productized it: a modified toolchain, a binary verifier, and an outer sandbox letting browsers execute untrusted x86, x86-64, and ARM code at near-native speed [2]. Then, in 2017, the industry pivoted: rather than verifying native code after the fact, WebAssembly made the sandbox a property of the *bytecode format* — validation is sandboxing, and sandboxing is validation [3].

That pivot relocated trust rather than ending the story: a sandbox enforced "by construction" is still enforced by a specific compiler, validator, and runtime, each a large fallible artifact. The last decade has therefore re-examined SFI through formal methods: vWasm and rWasm replace the trusted sandboxing pass with a machine-checked one [6]; CT-Wasm makes cryptographic code constant-time by typing [4]; CompCertSFI embeds a verified SFI transformation in a verified C compiler [8]. In parallel, the *interface* through which sandboxed code touches the world has been redesigned around capabilities — WASI's resource handles and the Component Model's worlds [9].

This article unifies these threads: the sandboxing invariant (§3); a taxonomy of enforcement mechanisms (Table 1); CT-Wasm's security type system and WASI/Component Model capability confinement; and what remains unverified (§6).

## 2 Background

### 2.1 The Wahbe et al. construction

The 1993 SFI paper [1] considers two distrustful modules — a *distrusted* extension and its host — co-resident in one address space, partitioned into a code segment and a data segment per fault domain. Every store, and every jump through a computed address, is preceded by a *sandboxing sequence* that forces the target address into the domain's segment via a dedicated register:

```
dedicated register d holds the fault domain's segment tag
sandboxing a store through register r:
    r := r & mask        ; clear high bits (segment matching)
    r := r | d           ; force the segment tag
    store [r], v
```

Because the mask-and-or pair executes atomically with respect to the sandbox policy, every store lands inside the domain's data segment and every indirect jump inside its code segment — at roughly 4% overhead on MIPS, establishing SFI's central thesis: *software-enforced confinement can be cheap enough to deploy* [1].

### 2.2 Native Client: SFI at web scale

NaCl [2] industrialized SFI for the hostile x86 ISA. On 32-bit x86 it exploited segment registers for zero-overhead data confinement; computed jumps were masked to 32-byte bundle boundaries and a trusted verifier disassembled from every byte offset to defeat overlapping encodings of forbidden instructions. System calls passed through trampolines into an outer sandbox (seccomp-bpf) for defense in depth. On x86-64 NaCl switched to `%r15`-based address masking into a 4 GB window ringed by guard pages; PNaCl added portability via a stable LLVM-bitcode subset. NaCl shipped in Chrome and was deprecated in 2017 as WebAssembly matured — the handoff from *verified-after-the-fact native code* to *sandboxed-by-construction bytecode* (§4.1 develops the mechanism in full).

### 2.3 WebAssembly: validation as sandboxing

The WebAssembly MVP [3] internalizes the lessons of NaCl at the format level:

- **Linear memory** is a single contiguous byte array per module instance, sized in 64 KiB pages. Every load and store computes an *effective address* as `base + offset` and traps if the access would exceed the current size. There are no raw pointers — only integer offsets into the one array.
- **Structured control flow** (`block`, `loop`, `if`, `br_table` with static labels) eliminates computed jumps into arbitrary offsets; indirect calls go through typed function tables with a dynamic signature check.
- **Validation** is a single-pass, linear-time type check. A validated module *cannot* express an out-of-bounds access or an ill-typed call; engines compile only validated modules, so the sandbox property rides on the validator's correctness.

Where NaCl needed a verifier to re-derive safety from hostile machine code, Wasm needs only a correct validator over a cooperative format. The trust moved, but did not vanish.

## 3 Methodology

Our analysis proceeds in four steps: extract the *sandboxing invariant* shared by every system in the lineage (§3, stated as a theorem schema); classify enforcement mechanisms (Table 1) and verification strategies — post-hoc verification (NaCl), validation (Wasm), verified compilation (vWasm, CompCertSFI), verified type checking (CT-Wasm); reconstruct the two modern extensions SFI alone never provided — *side-channel discipline* via security types (§4.3) and *least-privilege I/O* via capabilities (§4.4); and survey the proved-versus-measured evidence (§5).

| Mechanism | Representative | Enforces memory safety by | Control-flow integrity by | Verifier/validator |
|---|---|---|---|---|
| Segment matching | Wahbe et al. [1] | `and`/`or` sandboxing sequence | masked jumps, shadow returns | none (toolchain trusted) |
| Hardware segments + verifier | NaCl x86-32 [2] | `%cs`/`%ds` limits | 32 B bundles, masked jumps | binary verifier (trusted) |
| Address masking + guards | NaCl x86-64 [2] | `%r15` base + 32-bit mask | masked indirect branches | binary verifier (trusted) |
| Validation | Wasm MVP [3] | `base+offset` + bounds trap | structured control flow, typed tables | validator (trusted) |
| Verified masking | vWasm [6] | proved `&`-masking / check-and-branch | proved table/call bounding | F* proof; printer trusted |
| Security types | CT-Wasm [4] | secret-memory separation | no secret-dependent branches | verified type checker |

*Table 1: Enforcement mechanisms across the SFI lineage. The trend is from trusting the toolchain, to checking its output, to proving the transformation correct.*

> **Theorem (Sandboxing invariant, schema).** Let a module's *code region* be the set of validated instruction addresses and its *data region* the linear memory `[base, base+size)`. Then for every reachable machine state: (i) every memory access has effective address in `[base, base+size)`; (ii) every control transfer targets an address in the code region or a designated host trampoline; (iii) no instruction executes that the validator/verifier would have rejected.

Each system below is an instantiation of this schema with a different proof obligation — and a different TCB in which the unproven residue lives.

A note on method: all performance figures cited are those reported by the primary sources, and all formal claims are attributed to their mechanizations. Where the literature is silent — notably on end-to-end composition — we say so explicitly.

## 4 Deep Dive

### 4.1 Native Client: segments, bundles, and the verifier

The x86-32 NaCl design exploits an architectural accident: with the data-segment descriptor's base and limit set to the sandbox's data region, *every* data access through `%ds` is confined by hardware at zero added cost. The verifier polices only the escape hatches — segment-register writes, privilege changes, system calls — rejecting them outright and defeating overlapping x86 encodings by validating from every byte offset within each 32-byte bundle. Indirect branches are masked to bundle alignment; `ret` is forbidden and rewritten as `pop` plus masked jump; cross-domain calls go through trampolines that switch stacks and segments. The outer sandbox (seccomp-bpf on Linux) means the inner sandbox need only be good enough that escapes require chaining two independent failures.

### 4.2 WebAssembly's linear memory and the sandboxing theorem

WebAssembly inverts NaCl's division of labor: NaCl accepted hostile machine code and verified it, while Wasm defines a format in which hostile code *cannot be expressed*. Because linear memory is an object with a dynamic size and every access is `base + offset` with an implicit bounds check, the sandboxing sequence is no longer something the compiler emits and the verifier re-checks — it is the *only* addressing mode the format provides.

Control-flow integrity follows the same argument: structured branches name only lexically enclosing labels, and `call_indirect` indexes a table of validated functions with a runtime signature check. Engines never decode untrusted bytes as machine code, so there are no misaligned-decoding gadgets to harvest. Later proposals extend the model per-memory (multiple memories) and to wider offsets (memory64) without breaking the invariant.

### 4.3 CT-Wasm: a security type system for constant-time crypto

Sandboxing answers "can it read my memory?" but not "can it *time* my memory?" A Wasm AES implementation is memory-safe by construction and still leaks its key through data-dependent branches or cache-dependent table lookups — and the JIT between bytecode and silicon is free to introduce both. CT-Wasm [4] answers with a *security type system*: secret value types (`s32`, `s64`) and secret memories alongside public ones, with three core rules:

1. **No secret-dependent control flow.** `br_if`, `br_table`, and `call_indirect` on secret conditions are ill-typed.
2. **No secret-dependent addressing.** Loads and stores at secret indices are rejected; secret data moves through registers and secret memories only.
3. **Explicit endorsement.** `classify` lifts public values to secret (always safe); `declassify` lowers secret to public but is permitted only in functions explicitly marked *trusted*, making the trust boundary syntactically visible.

```haskell
-- CT-Wasm secrecy discipline, sketch
data Sec = Public | Secret deriving (Eq, Ord, Show)

classify   :: i32 -> s32          -- Public -> Secret: always safe
declassify :: Trusted f => s32 -> f i32   -- Secret -> Public: trusted code only

checkInstr :: Instr -> Maybe ([Sec] -> [Sec])
checkInstr BrIf      = Just (\[c] -> if c == Public then Just [] else Nothing)
checkInstr (Load _ Secret) = Just (\[a] -> if a == Public then Just [Secret] else Nothing)
-- secret-indexed loads are rejected: the address stack type must be Public
```

The metatheory is the point: a mechanized language definition, a proof of type soundness, a *verified* type checker, and a constant-time security proof — observational noninterference over a leakage model of branches and memory addresses, with non-termination handled coinductively [4]. Two implementations demonstrated practicality: the spec reference interpreter and a V8 port, with `ct2wasm` erasing annotations for unmodified engines. The follow-on WebAssembly *constant-time proposal* [5] carries the idea toward standardization, though it remains unmerged.

### 4.4 The Component Model and capability-safe WASI

SFI confines *computation*; it says nothing about *authority*. A sandboxed module that can invoke `open("/etc/passwd")` is confined but not least-privilege. POSIX gives processes ambient authority, so NaCl-era sandboxes interposed on system calls with hand-written policy. WASI takes the opposite approach: redesign the system interface so authority is carried by *unforgeable capabilities* [9].

WASI Preview 2 (0.2), built on the Component Model, goes further than Preview 1's fd rights bitmasks:

- **Resources with `own<T>`/`borrow<T>` handles.** A file, socket, or clock is a *resource*; code holding an `own<file>` handle may use it, and handles cannot be forged, guessed, or widened. Dropping the last `own` handle revokes the capability.
- **Worlds.** A component's *world* — written in the WIT IDL — declares exactly which interfaces it imports and exports. The host instantiates the component against a world granting only the intended capabilities; an HTTP handler component simply never receives a filesystem capability.
- **Canonical ABI.** Values cross component boundaries through generated *lift*/*lower* functions, with shared-nothing linking by default: components do not share linear memories unless they explicitly opt in. Confinement that SFI achieved *within* an address space is thus extended *between* components.

This is the object-capability paradigm (KeyKOS, EROS, seL4) reincarnated as a portable system interface: a component can only affect what its world grants, and its grants are capabilities, not names. The residual risks — confused deputies via over-broad grants, and the trusted status of the canonical ABI's generated code — are honest limitations (§6).

### 4.5 vWasm, rWasm, and the machine-checked sandbox

If Wasm's sandbox rides on its validator, validator bugs are sandbox escapes. Bosamiya, Lim, and Parno [6] shrink the trusted base to a *verified* artifact, with two compilers sharing a sandboxing strategy but differing in assurance:

**vWasm** is a Wasm-to-x64 ahead-of-time compiler written in F*. Its sandboxing pass is *untrusted code with a machine-checked proof*: F* verifies that, for any input, every emitted memory access is bounded — via bitwise-AND masking when the memory size is a power of two, falling back to check-and-branch otherwise — and that every indirect call and table access is confined. The top-level theorem states that compiled code can interact with the host only through the explicitly provided API. The remaining TCB is explicit: the F* toolchain, the simple x64 printer, the assembler, and the WASI runtime shim.

**rWasm** implements the same sandboxing discipline in Rust, trading proof for performance: *informally* verified — designed for auditability, differentially tested against a Wasm semantics fuzzer — and evaluated on PolyBenchC and an image-conversion pipeline at performance in the same band as mature production engines. The pair shows provable safety need not sacrifice competitive performance.

The lineage has siblings: **CompCertSFI** [8] performs a verified SFI transformation *inside* the CompCert verified C compiler — using well-defined C pointer arithmetic for masking, with a Coq proof of safety and security — and **ARMor** [10] gave fully verified SFI for ARM.

```rust
// The check a sandboxing backend must emit (or prove unnecessary)
fn load_i32(mem_len: usize, base: *const u8, offset: u32) -> Result<i32, Trap> {
    let end = (offset as u64) + 4;
    if end > mem_len as u64 { return Err(Trap::OutOfBounds); }
    // SAFETY: end <= mem_len, so the 4-byte range is in-bounds
    Ok(unsafe { *(base.add(offset as usize) as *const i32) })
}
```

```python
# Masking vs. check-and-branch: the two enforcement primitives
def sandbox_mask(addr: int, base: int, size: int) -> int:
    """NaCl/vWasm-style masking; requires power-of-two size."""
    assert size & (size - 1) == 0
    return base + (addr & (size - 1))

def sandbox_check(addr: int, base: int, size: int, width: int) -> int:
    """Bounds-check fallback for arbitrary sizes."""
    if not (base <= addr and addr + width <= base + size):
        raise Trap("out of bounds")
    return addr
```

## 5 Empirical Results / Formal Proofs

The evidence below divides into *measured* and *proved* — the field's progress is the migration of claims from the first column to the second.

| Artifact | Property | Evidence | Mechanization |
|---|---|---|---|
| Wahbe et al. SFI [1] | isolation, ~4% overhead | measured (MIPS, SPEC-era) | none |
| NaCl [2] | isolation, single-digit % overhead | measured (x86/ARM, Chrome) | none (verifier trusted) |
| Wasm MVP [3] | validation ⇒ isolation | spec + test suite | partial (subsequent mechanizations) |
| CT-Wasm [4] | type soundness, constant-time | machine-checked proof | proof assistant (full development) |
| vWasm [6] | sandboxing pass correct | machine-checked proof | F* |
| rWasm [6] | sandboxing + competitive perf | measured (PolyBenchC, image pipeline) | informal + differential fuzzing |
| CompCertSFI [8] | SFI safety + security | machine-checked proof | Coq |
| WASI Preview 2 [9] | capability confinement | design + implementations | none (spec in progress) |

*Table 2: What is proved versus what is measured across the lineage.*

Three observations. First, the performance story has converged: from Wahbe's 4% through NaCl's single digits to rWasm's near-parity with production engines, sandboxing was never the bottleneck its skeptics feared. Second, the *verified* artifacts bound their theorems precisely: vWasm proves the sandboxing pass, not the printer; CT-Wasm proves constant-time *of the bytecode semantics*, not of the silicon. Third, CT-Wasm's experimental validation — Salsa20, SHA-256, and TEA showing no input-dependent timing on the instrumented V8 build [4] — illustrates the healthy pattern: prove the abstraction, measure the instantiation.

```tla+
---- MODULE Sandbox ----
EXTENDS Naturals
CONSTANTS Base, Size, CodeLo, CodeHi
VARIABLES pc, memAcc
TypeOK == pc \in CodeLo..CodeHi /\ memAcc \in 0..(2^64 - 1)
SandboxInv == pc \in CodeLo..CodeHi
              /\ memAcc \in Base..(Base + Size - 1)
Init == TypeOK /\ pc = CodeLo /\ memAcc = Base
Step == \/ /\ pc' \in CodeLo..CodeHi
           /\ memAcc' \in Base..(Base + Size - 1)
        \/ UNCHANGED <<pc, memAcc>>
Spec == Init /\ [][Step]_<<pc, memAcc>>
THEOREM Spec => []SandboxInv
====
```

*The sandboxing invariant as a TLA+ state machine: every step preserves code-region and data-region confinement. Each system's proof obligation is to show its enforcement mechanism refines this spec.*

## 6 Limitations

**Speculative execution.** Every theorem above is about *architectural* state. Transient-execution attacks exfiltrate through microarchitectural state that SFI, Wasm validation, and CT-Wasm's bytecode-level constant-time property do not model. Engines have responded with mitigations — speculation-hardened index masking, retpolines, site isolation — but these are defense-in-depth, not theorems.

**The constant-time gap.** CT-Wasm proves constant-time behavior of the *bytecode*, but the property must survive lowering through the JIT or AOT backend. An optimization that reintroduces a data-dependent branch voids the guarantee silently. Until the constant-time proposal [5] is standardized *and* backends honor it, CT-Wasm's proof is a contract awaiting its counterparty.

**TCB residue.** vWasm trusts its printer, assembler, and WASI shim; rWasm's assurance is informal by design; NaCl's verifier was always trusted code; the Component Model's canonical ABI *lift*/*lower* functions sit inside every component's TCB. Hardware, microcode, and the proof assistants themselves remain axiomatic.

**Capability discipline is opt-in.** WASI Preview 2's worlds grant least privilege only if the host writes a least-privilege world. A host preopening the whole filesystem, or a component opting into shared-everything linking, reintroduces ambient authority through the back door.

**Composition is unproved.** We have verified sandboxes, verified crypto disciplines, and capability-safe interfaces — but no machine-checked theorem that their *composition* preserves all three properties. The canonical ABI boundary is the most likely place for the next decade's sandbox escapes.

**Denial of service.** SFI never promised availability: a module can spin forever or grow its memory to the 4 GiB limit, and the MVP has no fuel metering.

---

## 7 Conclusion

The arc from Wahbe to vWasm is the arc of a field learning to *say what it means*. SFI began as a rewriting trick with an informal argument; NaCl turned it into infrastructure with a checker; WebAssembly turned the checker into the format; and the current generation — vWasm's proved sandboxing pass, CT-Wasm's proved constant-time discipline, CompCertSFI's proved transformation, WASI's capability-typed interface — is turning the format's promises into theorems. Each step moved assurance from testing to checking to proof, shrinking the remaining trust into a named box.

The open frontier is composition: a machine-checked account of sandboxed components that are *simultaneously* memory-isolated, side-channel-disciplined, and capability-confined, on hardware whose speculative behavior is part of the model. The pieces exist. The proof that they fit together does not — yet.
