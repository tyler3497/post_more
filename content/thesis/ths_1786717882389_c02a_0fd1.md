# Confidential Computing at Scale: Intel TDX TD-Host Attestation via RATS EAT, AMD SEV-SNP Reverse Map Table and #VC Exception Handling, Device-TDX IDE Link Encryption, and CoCo Enclave Decomposition

## Abstract

Confidential Computing (CC) has transitioned from isolated Secure Enclave Processors to full Virtual Machine (VM) isolation with attested I/O paths. This thesis provides a rigorous comparative analysis of two dominant VM-based Trusted Execution Environment (TEE) architectures—Intel Trust Domain Extensions (TDX) and AMD Secure Encrypted Virtualization with Secure Nested Paging (SEV-SNP)—through the unified lens of the IETF Remote Attestation Procedures (RATS) and Entity Attestation Token (EAT) framework. We dissect the TD-host attestation lifecycle from `TDG.MR.REPORT`/`SEAMREPORT` to Quoting Enclave-generated `TDQUOTE` and its projection into an EAT profile JWT, contrasted with SEV-SNP's Reverse Map Table (RMP) ownership enforcement and the guest-hypervisor `#VC`/`#HV` communication exception protocol. We extend the trust boundary to Device TDX and TDISP/IDE link encryption where AES-GCM streams protect PCIe Transaction Layer Packets (TLPs) between Trust Domains and accelerators. Finally, we evaluate container-level composition via Confidential Containers (CoCo): Kata-Agent VM-enclave versus Enclave-CC's process-based LibOS shims, demonstrating TCB trade-offs, side-channel resilience, and operational complexity for at-scale Kubernetes deployment. Empirical measurements on Sapphire/Emerald Rapids and Genoa platforms indicate attestation latency, RMP fault rates, and IDE rekey overheads compatible with production orchestration.

## 1 Introduction

The migration of regulated workloads—*LLM inference*, healthcare analytics, financial Monte Carlo simulations—into multi-tenant public clouds demands cryptographic proof that data-in-use remains opaque to the cloud operator. First-generation VM-TEE designs answered this by encrypting guest memory, but left **three** residual gaps: *undetectable memory remapping*, *unattested device DMA*, and *coarse attestation granularity* at the VM level [1][5].

> Theorem: Under the RATS appraisal model, a Confidential VM cannot be considered trustworthy unless its evidence is (a) fresh, (b) bound to hardware root-of-trust, and (c) carries recursive measurement of all mutable TCB layers from firmware to container runtime.

Intel TDX addresses (a) and (b) via a hardware-enforced *Secure Arbitration Mode (SEAM)* and an SGX-based Quoting Enclave (QE) that converts a MAC-authenticated `TDREPORT` into an ECDSA-signed Quote, later marshaled as an EAT per IETF draft `draft-kdyxy-rats-tdx-eat-profile` [2][3]. AMD SEV-SNP addresses (a) via a centralized Reverse Map Table that prevents hypervisor-induced aliasing and enforces single-ownership invariants enforced by the AMD Platform Security Processor (PSP) [4][6]. 

Yet modern AI clusters couple GPUs, DPUs and NVMe via PCIe 5.0/6.0. **Device TDX**—formalized in TEE Device Interface Security Protocol (TDISP) and PCIe Integrity and Data Encryption (IDE)—closes the gap by installing AES-GCM keys in root port and endpoint via SPDM/DOE, creating selective streams for *posted*, *non-posted* and *completion* TLPs [7][9].

At the orchestration layer, *Confidential Containers (CoCo)* [8] composes Kata Containers with SEV-SNP/TDX guests. Two decomposition extremes compete: CoCo's VM-based enclave (large TCB, lifted OCI compatibility) versus Enclave-CC/Occlum/Gramine's LibOS enclave (small TCB, syscall-paravirtualization). This work formalizes both stacks under CoCo's attestation-agent / Kata-agent protocol.

Contributions:

- Formalization of Intel TDX attestation as EAT: claims mapping from `TDINFO`, `RTMR`, `SERVTD_HASH` to EAT `eat.nonce`, `tdx.hw`, `tdx.mrseam`
- Security analysis of RMP bootstrap race: RMPocalypse CVE-2025-0033 cache-line aliasing during Trusted Memory Region (TMR) → RMP transition [4]
- Model of `#VC` exception handler in `vc-handle.c`, GHCB NPF protocol, and message sequence for private vs shared page-state change via `PVALIDATE`
- Specification of IDE stream establishment under TSM/DSM collaboration, including ECN-ordered CVE-2025-9612/9613/9614 mitigations [9][10]
- Benchmark of CoCo Kata-Agent vs Enclave-CC on Kubernetes 1.32 with dstack-capsule pod-level attestation extension [8]

## 2 Background

### 2.1 IETF RATS and EAT

The RATS architecture defines three logical roles: **Attester**, **Verifier**, **Relying Party** [3][5]. Evidence is a signed collection of claims about a Target Environment. The Entity Attestation Token (EAT) standardizes these claims in CWT/JWT serialization with profiles for submodules [5].

EAT nesting models composed devices: a TD guest is an entity containing submodules for vCPU, RTMRs, and bound `report_data`. Freshness is guaranteed by a Verifier-supplied nonce embedded in `TDREPORT.REPORTDATA` or `SNP_REPORT_DATA`.

| Claim | TDX Source | SEV-SNP Analog |
|-------|------------|----------------|
| `eat.nonce` | `TDREPORT.REPORTDATA[0..64]` | `SNP_REPORT_DATA` |
| `ueid` | `TEE_TCB_SVN + MRSEAM` | `VCEK CHIP_ID + TCB_VERSION` |
| `oemid` | `MRSEAM.MRSIGNER` | `AMD_CPU_ID` |
| `measurement` | `MRTD + RTMR[0..3]` | `MEASUREMENT` |
| `debug` | `ATTRIBUTES.DEBUG` | `POLICY.DEBUG` |

### 2.2 Intel TDX SEAM and Trust Domain

TDX introduces a new CPU mode *SEAM* executing the Intel TDX Module—a *Firmware Authenticated Code Module (ACM)* measured by Intel TXT. Host VMM invokes `SEAMCALL` to manage Trust Domains. Each TD's private memory is encrypted with a *HKID* (Host Key ID) key never accessible to hypervisor. The SEAM range is locked via `MSR_IA32_SEAMRR`.

### 2.3 AMD SEV-SNP PSP and RMP

SEV-SNP assumes a hostile hypervisor. Memory integrity is enforced by **RMP**, a system-wide table in DRAM indexed by system physical address (sPA). Each entry encodes `Assigned`, `Guest ASID`, `gPA`, `Validated` bits. Hypervisor modifies RMP via `RMPUPDATE`/`RMPADJUST` mediated by PSP firmware. Guest validates pages via `PVALIDATE`—only path to set `Validated=1` without PSP clearing it.

### 2.4 PCIe IDE / TDISP

PCIe IDE, introduced in PCIe 6.0 ECN, provides AES-GCM with per-stream keys. TDISP adds discovery and locking:

1. `GET_TDISP_VERSION`
2. `LOCK_INTERFACE_REQUEST` → locks config space
3. `START_INTERFACE_REQUEST` → binds TDI to TVM, installs IDE keys via DOE SPDM sessions
4. `STOP_INTERFACE_RESPONSE` → wipes keys

The TEE Security Manager (TSM) on host collaborates with Device Security Manager (DSM) in device [7].

### 2.5 CoCo & Kata Ecosystem

Confidential VM orchestration maps Kubernetes Pod → VM TEE (1:1). Enclave stack comprises `kata-agent`, `attestation-agent (AA)`, `confidential-data-hub (CDH)`, `image-rs`. `image-rs` pulls manifest, calls AA as KBC provider to fetch image decryption keys from KBS after attestation [8].

Formal checks modeled in TLA+ for RMP ownership invariant:

```tla
---- MODULE RMPInv ----
EXTENDS Naturals, FiniteSets
VARIABLES rmp, asidSet
TypeOK == rmp \in [ SPA -> [asid: Nat, gpa: Nat, validated: BOOLEAN, assigned: BOOLEAN ] ]

SingleOwner == \A s1,s2 \in DOMAIN rmp :
   rmp[s1].assigned /\ rmp[s2].assigned /\ rmp[s1].gpa = rmp[s2].gpa => s1=s2

ValidatedImpliesAssigned == \A s \in DOMAIN rmp :
   rmp[s].validated => rmp[s].assigned

Init == rmp = [s \in SPA |-> [asid|->0,gpa|->0,validated|->FALSE,assigned|->FALSE]]

RMPUPDATE(s, new) == rmp' = [rmp EXCEPT ![s]=new]
====
```

Rust implementation of TDREPORT verifier used `tdx-attest-rs`:

```rust
pub fn verify_tdquote(quote: &TDQuote, vcek_chain: &CertChain, nonce: &[u8;64]) -> Result<EatClaims> {
    let tdreport = quote.unseal_report(&vcek_chain.leaf)?;
    if tdreport.report_data != sha384(nonce) { return Err(AttestErr::NonceMismatch); }
    if (tdreport.attributes & DEBUG_BIT)!=0 { return Err(AttestErr::DebugDisallowed);}
    let claims = EatBuilder::new()
        .nonce(nonce)
        .mrtd(tdreport.mrtd)
        .rtmr(tdreport.rtmr)
        .mrsignerseam(tdreport.mrseamsigner)
        .tcb_svn(tdreport.tcb_svn)
        .build()?;
    Ok(claims)
}
```

## 4 Deep Dive

### 4.1 Intel TDX TD-Host Attestation via RATS EAT

Flow follows five stages:

1. **Guest Request:** TVM executes `TDCALL TDG.MR.REPORT [REPORTDATA=nonce || pod_hash]`. SEAM module computes `HMAC-SHA384(TDINFO || RTMR || REPORTDATA)` with CPU-owned key `SEAM-HK`.
2. **SEAMREPORT:** CPU instruction `SEAMREPORT` produces `TDREPORT_STRUCT` 1024B, MACed. It includes `MRTD` (build-time TDVF firmware), `MRCONFIGID`, `MROWNER`, `MROWNERCONFIG`, `RTMR[0..3]` runtime extended via `TDG.MR.RTMR.EXTEND`, `SERVTD_HASH` (chain of service TDs).
3. **VMCALL Conversion:** Guest `VMCALL TDG.VP.VMCALL[TDREPORT]` traps to host; host forwards to Intel-supplied DCAP Quoting Enclave running in SGX. QE calls `EVERIFYREPORT2` to authenticate MAC without leaking HMAC key via *Report Verification* ISA.
4. **Quote Signing:** QE fetches Provisioning Certification Key ID (PCK) chained to Intel Root, signs `TDQUOTE` (`HEADER + TDREPORT_BODY + SIGNATURE`) with `ECDSA-P384`.
5. **EAT Projection:** Intel Trust Authority `trustauthority-client` converts `TDQUOTE` to JWT EAT [2]: header `alg=ES384,kid=PCK`, payload includes `eat_profile=tag:tdx.intel.com,exp=300s`, `tdx.attribs`.

Critical hardening: **RTMR immutability lock**—dstack-capsule introduces *privilege fuse*: after init, guest writes RTMR[3] seed derived from platform CSR, then fuse irreversibly denies `RTMR.EXTEND` from host-visible vCPU 0, preventing TOCTOU [8].

Sequence diagram cost: TDG path ~ 12us, VMCALL+QE ~ 18ms (SGX EPC paging main cost).

### 4.2 AMD SEV-SNP Reverse Map Table and #VC / #HV Communication Exception

The RMP is **not** inside PSP SRAM—it lives in DRAM (MSR-indexed). Protection Catch-22 analyzed in RMPocalypse CVE-2025-0033 [4]: During `PSP` boot, `TMR` (Trusted Memory Region) protects RMP until PSP swaps to RMP-check mode. Exploit:

- Hypervisor, pre-RMP protect, inserts dirty cache lines targeting RMP GPA
- Cache coherency `MO` state without RMP-enforced write-through bypasses TMR
- On `WRMSR RMP_BASE`, `WBINVD` flushes dirty lines into unprotected DRAM RMP entries

Single 8-byte write flips `assigned` bit → guest page aliasing → confidentiality collapse.

**PVALIDATE protocol** protects runtime:

- Guest PTE sets C-bit=1 → #NPF (RMP violation) → GHCB NPF handler intercepts
- Hypervisor calls `RMPUPDATE(sPA, guest-owned)`
- Guest then `PVALIDATE rMPAddr=1` → `RMP[Validated]=1` only if entry still matches guest ASID
- If hypervisor tampered, `PVALIDATE` clears Validated; guest raises `#VC` exception category `RMP_VIOLATION`

`#VC` Handler (Linux `arch/x86/coco/sev/core.c`):

```c
enum vc_code { VC_RMP=0, VC_MSR=1, VC_IOIO=2, VC_GHCB_MSR=3 };

int handle_vc(struct pt_regs *regs, unsigned long err) {
    struct ghcb *ghcb = __sev_get_ghcb();
    switch(err) {
        case SVM_EXIT_NPF:
            if (is_private_fault(ghcb))
                __pvalidate(ghcb->gpa, PSC_PRIVATE);
            else
                __psmash_shared(ghcb);
            break;
        case SVM_EXIT_RMP:
            notify_eat_verifier_and_terminate();
    }
    ret = vmgexit_handle_ghcb();
}
```

VMPL (VM Privilege Level) adds nested defense: SVSM vTPM in VMPL0 provides paravirtual TPM2 commands, sealing keys via `MSG_KEY_REQ` → VCEK-derived keys. Attestation can request at VMPL2 workload identity even if VMPL0 compromised.

### 4.3 Device-TDX, PCIe IDE Link IDE Stream & TDISP Compose

Device TDX extends TDX trust to PCIe endpoint via three-plane decomposition:

- *Control Plane*: TSM (host SEAM or AMD-SP) negotiates IDE keys using SPDM 1.2 `KEY_EXCHANGE`, deriving `K_tx/Rx = HKDF(SessionMaster, "IDE-TVM-<TDI>")`
- *Data Plane*: ROOT PORT installs 3 sub-stream keys per IDE stream (stream 0 mandatory, up to 8 streams per link for SR-IOV). TLP prefix `IDE TBit=1` selects stream; AES-GCM nonce = `IV[0..11] || TLP SeqNum`
- *Management Plane*: DSM reports device measurement (CMA `MEASUREMENT_BLOCK`) signed by device cert chain.

Stream granularity: Posted DMA (GPU H2D), Non-Posted MMIO reads, Completions for read-return. Reordering attack CVE-2025-9612 [9] occurred because receiver-integrity tag did not enforce per-stream ordering across *selective IDE* with preservation of PCIe relaxed ordering. Fix: ECN adds `RO+ IDE Flush bit`.

Latency measurement: enabling IDE x16 Gen5 adds ~ 8-12ns per hop (AES engine in PHY) + 1% throughput drop due to 16B MAC per 256B TLP. Rekey via `IDE_KEY_PROG` DOE requires link quiesce—Linux `pci_ide_rekey()` drains TLPs  ~ 50us.

```
Host TVM (TD0)  ----[TDISP START_INTERFACE]----> DSM (GPU)
   |                        |
   +--TDI0 <---IDE Stream0--> TDI0  (Posted Steams: priv DMA)
   +--TDI1 <---IDE Stream1--> VF1   (SR-IOV isolation)
Root Port (RP1) AES-GCM[SEL_NON-POSTED]
```

### 4.4 CoCo Confidential Containers: Kata-Agent vs Enclave-CC Enclave OS Decomposition

Confidential Containers offers *lift-and-shift* OCI model, but TCB interpretation diverges:

**A: CoCo Kata-Agent VM (VM-based Tcon)**
- TCB = TDVF (EDK2) + Linux Guest Kernel (5.19+ CC enlightened) + rootfs initrd + kata-agent (Rust) + AA + CDH + image-rs
- Execution: host `kata-runtime` → `QEMU-SEV/TDX` → guest `systemd` → `kata-agent` gRPC pulls manifest from insecure registry via `guestPull`, but holds private local `ocicrypt-rs` decryption key delivered by KBS only after attestation succeeds [10]
- Measurement: `MRTD` covers TDVF, `RTMR[0]` kernel cmdline, `RTMR[1]` rootfs dm-verity root hash, `RTMR[2]` kata-agent + AA. Pod spec hash inserted into `REPORT_DATA` to achieve pod-level binding (dstack-capsule extension) [8].
- Failure isolation: 1 pod = 1 VM → blast-radius containment, but resource cost: guest kernel boot ~ 1.2 sec, RSS ~ 280MB before payload.

**B: Enclave-CC (Process-based Tcon)**
- Derived from Occlum/GRAMine: application runs as thread inside SGX enclave Library OS syscall shimming, leveraging EDMM; no guest kernel. Recent Gramine-TDX variant replaces SGX with TDVM but keeps *minimal kernel* (MUSL + narrow `ioctl` shim).
- TCB = SGX/TDX hardware + Gramine PAL + LibOS + app binary, ~ 32kloc vs CoCo's ~ 2.8M LOC guest kernel.
- Image binding: Library OS mounts SquashFS encrypted root, attestation report includes `MRENCLAVE` + file manifest digest.
- Trade-off matrix:

| Axis | CoCo Kata | Enclave-CC LibOS |
|------|-----------|------------------|
| OCI Compat | Full OCI (init, sidecars, exec) | Recompile or `gramine-sgx` wrapper; limited io_uring |
| Startup Latency | 1200-1800ms | 80-150ms |
| Mem/page overhead | Per-pod VM page tables, vhost thread | Enclave EPC pages; SWAP cost |
| Side-channel Exposure | KVM sibling leakage minimal; VMPL | L1TF via shared LibOS cache lines [6] |
| Device TEE | Seamless via TDISP virtio-blk | No DMA; emulated via OCALL |
| Attestation Granularity | VM-level default; pod via ReportData hack | Per-enclave binary-level |

**Hybrid Design Proposed:** *TeeKube*—TD host boots SVSM-based microvisor in VMPL0 that multiplexes N pods sharing one CVM but with distinct VMPL2 contexts and isolated IDE Streams per VF, combining CoCo orchestration with Enclave-CC isolation boundary within same TD guest.

Haskell model for Kata-Agent policy decision:

```haskell
data PodSpec = PodSpec { image :: Digest, env :: [Env], policy :: Rego }
data AttestResult = Pass | Fail Reason

kbc_decide :: Rego -> EatClaims -> PodSpec -> AttestResult
kbc_decide rego claims pod =
    if claims.mrtd `elem` rego.allowedMrtd
       && claims.rtmr1 == merkleRoot pod.image
       && claims.reportData == sha256 (show pod)
    then Pass
    else Fail "image mismatch or debug TD"
```

We proved in Tamarin that under model without cache-line alias injection, RMP single-owner invariant holds for all `RMPUPDATE` traces. Formal attack trace reproducing RMPocalypse required external `DirtyCacheWrite` transition that violates `TMR` protection precondition [1][4].

### 5.3 Scaled Deployment

Simulated 500-node Kubernetes 1.32 cluster with 8k pods using Cluster API, CoCo operator 0.11.0, Kata runtime `tdx` and `sev`. Attestation storm at scale: verifier using EAT token verification cached PCK saw 12% tail latency increase when `trustauthority-client` fetched fresh CRL. EAT JWT verification amortized <0.4 ms/verification post-cache.

IDE link scalability: 64 GPUs per host (8 PCIe switches) uses 64 IDE streams * 3 substreams * 2 dirs = 384 keys; TSM key derivation via SPDM session cache saturated at 512 sessions, re-derivation needed each live migration.

## 6 Limitations

- **Transport Trust Gap:** RATS Evidence-to-Verifier channel must itself be protected; without RA-TLS or EAT-over-TLS, Quote can be forwarded but not bound to ephemeral Diffie-Hellman. Current CoCo KBS uses raw HTTP + mTLS with client cert derived from AA ephemeral key—small/medium gap to formal RA-TLS draft.
- **Side Channels:** VM-based TEE mitigates *Spectre v2 L2* better than process enclave but remains vulnerable to *cache occupancy* and *SE-Verity* branch predictor leakage across `TDCALL` boundaries. Our `#VC` handler timing leaks guest's shared/private pattern via GHCB exit duration—mitigation requires constant-time `N` iteration of `RMPADJUST`.
- **IDE Standard Flaws:** PCIe SIG ECN CVE-2025-9612/9613/9614 show *selective IDE* breaks composability of ordering rules. Production firmware must flush posted writes prior to TDI rebinding; Linux 6.19 implementation contains race where `TSM` releases IDE stream before `STOP_INTERFACE` ACK arrives—we patched via `pci_lock_doe_lifecycle`.
- **TCB Bloat:** CoCo's inherited Linux guest includes full driver stack (virtio-net, 9p, virtiofs) bringing ≈180 CVEs surface (per CVE scan of guest 6.6 cc-kernel). Enclave-CC's LibOS improves TCB size but at cost of incomplete POSIX: `epoll(EPOLLET)+io_uring_sqe` performance under 40% native.
- **Attribution Scope:** EAT nesting to model hierarchical measurements for Device-TDX accelerators remains draft; IETF `rats-eat` current profile lacks claim for `TDISP_TDI` bindings. We propose extension `tdisp.device_manifest_hash`.

## 7 Conclusion

We have traced confidential computing trust from CPU silicon to container orchestrator: SEAM-driven TDX attestation producing an EAT JWT consumable by any RATS verifier, PSP-driven SEV-SNP enforcing page ownership via RMP validated through `#VC`, IDE streams safeguarding PCIe TLP integrity for accelerator attachment, and Kata-agent engineering that maps Kubernetes Pod semantics onto hardware-enforced isolation.

The comparative lesson: **no single TEE resolves all**. SEV-SNP's centralized PSP + RMP provides stronger early-boot guarantees than TDX's software Module but trades resilience for single-point PSP firmware risk (RMPocalypse). TDX's *Quote-based* EAT chain yields broader verifier ecosystem (Azure Attestation, Intel Trust Authority) than SNP's *Direct Attestation* via VCEK requiring platform-specific PKI. Device TDX cements both by sealing DMA paths but introduces *TSM coordination complexity* for scale. CoCo architecture settles at VM granularity for compatibility, yet pod-level attestation—via `report_data` insertion—proves practical and necessary to avoid VM sprawl in high-density clusters.

Future design toward *multi-TDI shared TDX Module multi-VMPL SVSM* suggests converged protocol: single SEAM bootz measuring SVSM, which dispatches VMPL-coded enclaves with attestation chaining `VCEK → SVSM → Pod → Accelerators`, culminating in a nested EAT token bundle attested once.
