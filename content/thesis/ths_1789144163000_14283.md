# From Stacked Borrows to Tree Borrows: Operational Aliasing Models, Polonius, and the Formal Memory Model of Rust

## Abstract

Rust's borrow checker guarantees memory safety for safe code, yet the compiler also wishes to exploit those same aliasing guarantees for optimization, and unsafe code must know precisely which pointer manipulations constitute undefined behavior. This thesis develops the operational theory that answers both questions. We begin with **Stacked Borrows** [1], the per-location borrow-stack semantics that extends the borrow checker's well-bracketed discipline into unsafe code through tagged pointers, retagging, and protectors, and that is implemented in the Miri interpreter to detect aliasing violations dynamically. We analyze its three structural failures — the prohibition of read-read reordering, static reference ranges, and inadequate two-phase borrow support — and present **Tree Borrows** [2] as their resolution: a per-reference borrow tree with a per-node permission state machine, child/foreign access classification, and dynamic ranges, with Rocq-verified retention of prior optimizations. We then turn to **Polonius** [4], the Datalog-based alias formulation of the borrow checker now enabled on nightly [5], and chart how these threads converge in the Unsafe Code Guidelines working group toward a formal Rust memory model.

---

##1 Introduction

Few type systems in production use carry the dual mandate that Rust's ownership discipline carries. The borrow checker is first and foremost a safety device: it statically rejects data races, use-after-free, and aliasing violations in safe code. But Rust's type system is also an *optimization contract*. A mutable reference `&mut T` is not merely a pointer that the compiler happens to know is unique; it is a promise, encoded in the types, that no other path to the same memory exists for the reference's lifetime. Optimizers feed on such promises. LLVM receives them as `noalias`, `dereferenceable`, and `align` attributes on function parameters, and on their strength the backend may eliminate redundant loads, reorder memory operations across calls, and hoist invariants out of loops [1].

The tension is immediate. Unsafe Rust — the raw-pointer substrate on which `Vec`, `Mutex`, `Cell`, and the entire standard library are built — can manufacture aliasing that contradicts these promises. Consider:

```rust
fn write_both(x: &mut i32, y: &mut i32) -> i32 {
    *x = 13;
    *y = 20;
    *x // could the optimizer fold this to 13?
}

fn main() {
    let mut v = 0;
    let p = &mut v as *mut i32;
    // SAFETY: two &mut from one raw pointer — is this UB?
    let r = unsafe { write_both(&mut *p, &mut *p) };
    println!("{r}");
}
```

Without optimization, this prints `20`. With the `noalias`-justified folding of the final read, it prints `13`. Optimizations must not change program behavior — so we need a principled way to declare the second program *undefined* while accepting all safe Rust. This is precisely the problem an **aliasing model** solves: a formal semantics of pointer validity, defined for both safe and unsafe code, against which optimizer transformations can be proved sound and unsafe code can be judged [2].

This thesis presents the three pillars of Rust's emerging formal aliasing story:

1. **Stacked Borrows**, the first operational aliasing model, whose borrow stacks are enforced dynamically by Miri;
2. **Tree Borrows**, its tree-structured successor, which repairs the empirical and theoretical shortcomings of stacks while retaining their optimization power;
3. **Polonius**, the Datalog-based reformulation of the static borrow checker itself, which supplies the liveness-driven foundation the aliasing story needs on the safe-code side.

We proceed from operational semantics to empirical evaluation to the open problem of the Unsafe Code Guidelines memory model.

##2 Background

### The aliasing contract

Rust's surface rules are deceptively simple: either any number of shared references (`&T`) *or* exactly one mutable reference (`&mut T`) may exist for a given place at any time, and the mutable reference is unique. The borrow checker enforces this statically via lifetimes, a region-based discipline refined over the years from lexical scopes to non-lexical lifetimes (NLL), where a borrow's validity ends at its last use rather than at the end of its lexical scope.

But static enforcement covers only safe code. Unsafe code routinely derives raw pointers from references, casts pointers to integers and back, and temporarily violates the surface rules — legitimately, inside abstractions like `RefCell` or `Vec::as_mut_ptr`. The compiler cannot see inside these abstractions; it must decide what unsafe code is allowed to do based on a specification. As the Unsafe Code Guidelines working group puts it, the goal is to define what it means for unsafe code to be "badly behaved," because only then can type-driven optimizations be sound [3].

### Why an operational model

One might hope for a purely axiomatic specification: "a program has UB iff some optimizer transformation changes its meaning." That definition is circular for compiler engineers who need a checkable criterion. The operational approach instead defines an instrumented abstract machine — borrow stacks or trees threaded through the heap — and declares a program to have UB exactly when the instrumented execution gets stuck. This has three decisive advantages [1][2]: the machine can be **implemented** (as in Miri) so real code can be tested; each optimization is **proved sound** against the machine; and when the model rejects too much real code, its transition rules can be **surgically relaxed** while re-checking the proofs.

### Miri: the dynamic oracle

Miri is Rust's interpreter for the Mid-level Intermediate Representation (MIR), used primarily to detect undefined behavior in test suites — including those of the standard library itself. By instrumenting every memory access with the aliasing model, Miri turns the operational semantics into an executable oracle: run the crate's tests under Miri, and any aliasing violation is reported with the offending pointer's provenance. The Stacked Borrows instrumentation in Miri uncovered 11 aliasing violations in the standard library and ecosystem test suites shortly after deployment, demonstrating that the model had real discriminating power [1].

##3 Methodology

Our analysis follows the methodology of the aliasing-model literature: we (i) reconstruct each model's operational semantics as a state machine over tagged memory; (ii) identify the exact transition rules responsible for accepted and rejected programs; (iii) evaluate the models against their stated goals — optimization soundness and real-code acceptance — using the published empirical data; and (iv) trace the static counterpart, Polonius, from its Datalog formulation to its nightly deployment.

Formally, we work with an instrumented heap

$$\mathcal{H} : \text{Loc} \to (\text{Val} \times \mathcal{S})$$

where $\mathcal{S}$ is the model's per-location aliasing state (a stack in Stacked Borrows, a tree in Tree Borrows). Every pointer carries a **tag** $\tau$; every memory access is a triple $(\tau, \text{op}, \ell)$ with $\text{op} \in \{\text{read}, \text{write}\}$. The transition relation $\mathcal{H} \xrightarrow{\tau, \text{op}, \ell} \mathcal{H}'$ either produces a new aliasing state or is undefined, in which case the program exhibits UB. **Retagging** is the operation that, at each point where surface Rust creates a reference from another pointer (function calls, reborrows, raw-pointer casts), assigns a fresh tag and registers it in $\mathcal{S}$ — critically, retagging is *shallow* in the current model: it registers tags for the outermost reference only, not recursively for references nested inside compound types [3].

We verified all factual claims — paper citations, evaluation numbers, deployment status — against primary sources: the POPL 2020 and PLDI 2025 papers, the Unsafe Code Guidelines working documents, the Polonius repository, the Rust project's 2025H2 goals, and the nightly-enablement announcement [1][2][3][4][5][6].

##4 Deep Dive

### 4.1 Stacked Borrows: per-location borrow stacks

Stacked Borrows attaches to every memory location a **stack of borrow items**, each item a pair $(\tau, \pi)$ of a pointer tag and a permission $\pi \in \{\text{SharedReadWrite}, \text{SharedReadOnly}, \text{Unique}\}$ [1][3]. When a reference is created, its fresh tag is *pushed* with the permission determined by the reference kind:

| Reference kind | Permission pushed |
|---|---|
| `&mut T`, `Box<T>` (non-two-phase) | `Unique` |
| `*mut T` raw pointer, two-phase `&mut` | `SharedReadWrite` |
| `&T` outside `UnsafeCell` | `SharedReadOnly` |
| `&T` inside `UnsafeCell` | `SharedReadWrite` |
| `*const T` | `SharedReadOnly` / `SharedReadWrite` as above |

An access with tag $\tau$ proceeds as follows: find the topmost stack item with tag $\tau$; the access is permitted iff that item's permission allows the operation. Then — and this is the heart of the model — **every item above it is popped**. Popping is invalidation: a mutable reference that is "used again" after a conflicting access has, in effect, ended the borrows stacked above it. This enforces *well-bracketed* usage: uses of references must nest like parentheses, exactly the discipline the borrow checker imposes on safe code, now extended operationally into unsafe code.

```rust
let mut root = 42;
let x = &mut root;      // retag: push (τ_x, Unique); stack: [root, τ_x]
let y = &mut *x;        // reborrow: push (τ_y, Unique); stack: [root, τ_x, τ_y]
*y = 13;                // access via τ_y: found on top, permitted; nothing above
*x = 20;                // access via τ_x: τ_y popped — y is now invalid
// *y = 30;             // UB: τ_y no longer on the stack
```

> **Theorem (Optimization soundness, Stacked Borrows [1]).** If a program executes without UB under the stacked-borrows machine, then the compiler may assume that every `Unique`-permissioned reference is the sole writer of its location for as long as it remains on the stack, and that no write occurs through any `SharedReadOnly` item's location. In particular, the `write_both` read-folding and LLVM `noalias` annotations on `&mut` parameters are sound.

The mechanism that justifies `noalias` is the **protector**. When a reference is passed to a function, its tag is retagged *with protection*: for the duration of the call, the protected item may not be popped, and invalidating it is UB. Protectors encode the callee's right to assume its `&mut` arguments stay valid — the exact assumption LLVM's `noalias` needs [3].

### 4.2 Protectors, two-phase borrows, and the limits of stacks

Two-phase borrows are Rust's quiet concession to ergonomics. In `vec.push(vec.len())`, the receiver is mutably borrowed to evaluate the autoref, yet the *arguments* must still be evaluable — including shared borrows of `vec` itself. The borrow checker therefore splits the mutable borrow into a **reservation phase**, during which only reads are allowed, and an **activation phase** beginning at the first write, from which uniqueness is enforced [3].

Stacked Borrows never properly supported two-phase borrows. Its implementation assigns two-phase `&mut` the `SharedReadWrite` permission — i.e., it treats them *like raw pointers* — with a "barrier" mechanism grafted on to recover activation. This produces genuinely confusing behavior: because implicit reborrows at call boundaries are two-phase, whether a program is accepted can depend on whether a function call was inlined, a difference no programmer can predict [2]:

```rust
let x = &mut 0;
let y = x as *mut i32;   // raw pointer derived from x
write(x);                // call: implicit two-phase reborrow — accepted by SB
unsafe { *y = 15; }
// inline write's body here instead, and SB *rejects* the program
```

Beyond two-phase borrows, the stack discipline has two deeper flaws [2]. First, **read-read reordering is forbidden**: reading through an inner reborrow and then through the outer reference is fine, but reordering those two reads violates well-bracketing and is UB. Since read reordering is among the most basic optimizations a compiler performs, a model that outlaws it is a model the optimizer cannot fully trust. Second, **reference ranges are static**: a reference's tag claims a fixed memory range determined at creation. The ubiquitous C-heritage pattern of taking `&arr[0]`, converting to a raw pointer, and walking the whole array is UB under Stacked Borrows, and this single rule accounts for a large share of real-world violations.

### 4.3 Tree Borrows: permission trees and dynamic ranges

Tree Borrows replaces the stack with a **tree** [2][7]. Every reference or pointer becomes a node; its parent is the unique reference or local variable it was created from. Siblings are therefore genuinely independent — the tree imposes no "at most one live child" constraint — which is exactly what two-phase borrows need: a `Reserved` mutable node and several shared sibling nodes can coexist under one parent until activation.

Each node carries a permission from a small state machine:

```text
                   child read
              ┌──────────────────┐
              │                  ▼
  Reserved ──────────────► Active
  (reservation phase)      (activated &mut)
      │  child write          │  foreign write
      │                       ▼
      │                   Disabled
      │                   (dead: any
      │                    access is UB)
      │  foreign write
      ▼
  Disabled

  Frozen ── foreign write ──► Disabled
  (shared &)   child write ──► UB (cannot activate)
               child/foreign read ──► Frozen (unchanged)
```

Accesses are classified **relative to each node** as *child accesses* (performed through the node itself or any transitive child) or *foreign accesses* (through strict ancestors or unrelated branches). The transition rules encode a simple moral: a node's permission describes what *others* may do to it. A `Frozen` node (shared reference) tolerates foreign reads but is disabled by foreign writes; an `Active` node tolerates foreign reads but is disabled — not merely shadowed — by foreign writes, preserving uniqueness. A `Reserved` node permits sibling reads during reservation and, upon its own first child write, *activates*: it becomes `Active` and all its siblings become `Disabled`, enforcing uniqueness from that point forward [2].

The second innovation is **dynamic reference ranges**. Instead of fixing a tag's claimed range at creation, Tree Borrows *shrinks* permissions based on actual use: reborrowing a struct field narrows the parent's range to exclude that field, so disjoint field accesses through parent and child compose. The C-style `&arr[0]`-to-whole-array walk becomes legal, because the range a reference claims grows from how it is exercised rather than being frozen at birth.

> **Theorem (Tree Borrows optimization retention [2]).** Every intraprocedural optimization justified by Stacked Borrows *except* those that introduce writes (e.g., hoisting a write out of a conditional) is also justified by Tree Borrows; additionally, Tree Borrows justifies **read-read reordering**, which Stacked Borrows forbids. Both directions are mechanized in Rocq.

The "except" clause is instructive: Stacked Borrows permits an optimization that rewrites `while i < n { *x += 1 }` into `*x += n` — introducing a write when `n == 0` — because under SB a `Unique` permission is writable from creation. Tree Borrows' `Reserved` state is not writable until activated, so the transformation is unsound there. The models thus trade off differently along the UB/optimization frontier, and the choice is empirical as much as theoretical.

### 4.4 Polonius: an alias-based reformulation of the borrow checker

While the aliasing models govern the *dynamic* semantics of unsafe code, the *static* borrow checker has its own imprecision problems, and their fix shares the same intellectual lineage. NLL computes, for each borrow, the set of program points where it must be live — but it does so through a region-inference formulation with known false positives, most famously issue #47680, where disjoint closure captures are rejected because a captured variable's borrow is kept alive too long.

**Polonius** reformulates borrow checking as a Datalog problem over facts extracted from the control-flow graph [4]. The core relations, in the notation of the Polonius book, are:

```prolog
% A loan is live at point P if some live origin can reach it
borrow_live_at(P, B) :-
    loan_issued_at(B, P0),
    origin_live_on_entry(P, O),
    subset(O, P0, O).          % simplified: origin reaches the loan's origin

% Errors: a loan that is live where it is invalidated
error(B, P) :-
    borrow_live_at(P, B),
    invalidated_at(P, B).
```

Concretely, Polonius builds a *unified graph* whose nodes are (region, program-point) pairs, with subset edges from type checking and liveness edges from standard dataflow analysis; a loan is live at a point iff it can reach a live region in this graph [6]. Because liveness — not lexical or inferred region extent — drives the analysis, borrows die exactly when they are last used, and patterns like lending iterators (issue #92985), where a mutable borrow is threaded through an iterator across loop iterations, become expressible.

After years as an experiment, Polonius reached a deployable milestone: **Polonius Alpha**, an actionable subset of the full analysis (subset reasoning modulo strongly connected components), was enabled by default on nightly Rust in August 2026, with `-Zpolonius=off` as the opt-out [5]. Evaluation across the 10,000 most-downloaded crates showed few significant compile-time regressions — worst observed cases around 2–3× on borrow-heavy crates — against a strict increase in accepted programs [5]. The 2025H2 project goals commit to stabilizing this subset and then pursuing fuller flow-sensitivity in later phases [6].

The connection to the aliasing models is not accidental. Polonius's `invalidated_at` relation is the static mirror of the operational models' pop/disable transitions: both ask, of every memory access, *which outstanding borrows does it kill?* A future in which Miri's dynamic checks and Polonius's static facts agree on the meaning of "invalidated" is a future in which the borrow checker and the aliasing model are two views of one semantics.

##5 Empirical Results / Formal Proofs

The aliasing-model program is unusual among programming-languages research in being evaluated like systems work: against the corpus of real code. The headline numbers [2]:

| Experiment | Stacked Borrows | Tree Borrows |
|---|---|---|
| Test cases rejected, top 30k crates (Miri) | baseline | **54% fewer** |
| Read-read reordering sound | no | **yes** (Rocq-proved) |
| Two-phase borrows native support | no (raw-pointer fallback) | **yes** (`Reserved`) |
| C-style `&arr[0]` range extension | UB | allowed |
| Write-introducing optimizations | allowed | disallowed |

The 54% reduction in rejections is the empirical core of the Tree Borrows paper: on the 30,000 most widely used crates, more than half of the test cases that Stacked Borrows flags as UB are accepted by Tree Borrows, and manual audit found the newly accepted patterns to be idiomatic unsafe code (interior mutability, range extension, reordered reads) rather than genuine bugs [2].

On the proof side, the Tree Borrows development is mechanized in **Rocq** (formerly Coq): the paper proves that Tree Borrows retains all Stacked Borrows optimizations except write-introducing ones and additionally validates read-read reorderings, by exhibiting the corresponding simulation arguments between the stacked and tree machines [2]. The operational model itself is implemented in Miri behind `-Zmiri-tree-borrows`, so the same test suites that validated Stacked Borrows now differentially test Tree Borrows.

Polonius's evidence is of a different kind: differential testing against NLL over the 10,000 most-downloaded crates, measuring both newly accepted programs and compile-time regressions, with the Alpha subset deliberately chosen as the largest fragment whose performance cost the project deems acceptable for stabilization [5][6].

##6 Limitations

No current model is the final memory model, and the honest limitations are substantial.

*Tree Borrows is still experimental.* It is not the default in Miri, let alone normative; the Unsafe Code Guidelines working group has not endorsed any aliasing model as *the* definition of UB, and its documents warn they describe Miri's implementation rather than prescribing rules [3].

*The optimization frontier moved, not vanished.* Tree Borrows forbids optimizations Stacked Borrows permits (write introduction) and permits ones it forbids (read reordering). There exist programs accepted by SB but rejected by TB and vice versa; neither model dominates the other, so "fewer rejections on crates.io" is evidence of better *fit*, not of correctness.

*Interior mutability remains delicate.* Both models carve out `UnsafeCell` with entirely static detection that recurses through structs and tuples but treats enums and unions conservatively — a pragmatic hack that avoids self-referential analysis (the model analyzing its own memory accesses) but bakes type-layout heuristics into the semantics [3].

*Polonius Alpha is a subset.* The stabilized fragment deliberately excludes full flow-sensitivity during borrow checking; known NLL limitations beyond the Alpha fragment remain, and the performance worst cases (2–3× on borrow-dense crates) are tolerated rather than solved [5][6].

*Dynamic checking does not compose.* Miri can only check executed paths; an aliasing violation on an untested path is silent. The models are therefore necessary but insufficient: they define UB precisely, but only testing plus proof can establish its absence.

---

##7 Conclusion

Rust's aliasing story has matured from folklore into a two-sided formal discipline. **Stacked Borrows** gave the first executable definition of pointer validity, proved the core type-driven optimizations sound, and — via Miri — found real violations in real code. **Tree Borrows** repaired its structural defects with a borrow tree, a permission state machine, and dynamic ranges, halving false rejections on the ecosystem while gaining read-reordering optimizations, all under Rocq-verified proofs. **Polonius** replaced region inference with a liveness-driven Datalog analysis, fixing decade-old borrow-checker false positives and reaching nightly as Polonius Alpha.

What remains is convergence: a single memory model, endorsed by the Unsafe Code Guidelines process, under which Miri's dynamic judgments, Polonius's static facts, and LLVM's `noalias` annotations are three consistent views of one semantics. The machinery surveyed here — tags and retagging, protectors, permission automata, subset graphs — is the vocabulary in which that model will eventually be written. Until then, the responsible practice for unsafe code authors is concrete: run Miri, in both Stacked and Tree Borrows modes, over every test, and treat each reported violation as a bug in waiting.
