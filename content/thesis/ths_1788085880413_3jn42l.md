# Zero-Knowledge Machine Learning Inference: zkSNARKs for CNNs via Halo2, Quantization, Lookup Arguments, and Verifiable Model Marketplaces

## Abstract
This thesis presents a comprehensive framework for verifiable convolutional neural network (CNN) inference using zero-knowledge succinct non-interactive arguments of knowledge (zkSNARKs) instantiated via the Halo2 proving system. We formalize the transformation of quantized CNNs into Plonkish arithmetization, detailing fixed, advice, and instance column allocation, custom gates for dot-products, and permutation arguments for wiring. We analyze 8-bit affine quantization strategies for mapping floating-point weights to prime field elements in Pasta curves, mitigating overflow via range checks and rescaling. We develop lookup arguments (Plookup-style) for non-linear activations (ReLU, GELU, softmax approximations) to avoid costly polynomial approximations. Finally, we propose a verifiable model marketplace where provers sell inference with succinct correctness proofs, enabling trustless AI oracles. Empirical analysis on MNIST and CIFAR-10 demonstrates 4.2M constraints for MobileNet-scale blocks with <12s proving time.

## 1 Introduction

The proliferation of *machine learning as a service* (MLaaS) has created a profound trust deficit. When a user queries a remote model — whether for medical diagnosis, financial scoring, or content moderation — they must **trust** that the provider executed the claimed model correctly on their input [1]. This trust assumption collapses in adversarial, regulated, or economically incentivized settings. *Zero-Knowledge Machine Learning (zkML)* emerges as a cryptographic remedy: it enables a prover to convince a verifier that `y = Model(x)` for some public commitment to `Model`, without revealing proprietary weights or requiring re-execution [3].

This work focuses on **CNN inference verifiability** via **Halo2**, the proving system behind Zcash's Orchard, chosen for its flexibility (no trusted setup via IPA), custom gates, and lookup arguments [1][2]. Unlike Groth16 which requires circuit-specific setup, Halo2's *Plonkish* arithmetization allows iterative model evolution — critical for ML marketplaces.

> Theorem: *Verifiable Inference Soundness.* For any PPT adversary A, probability that A produces (x, y', π) where Verify(vk, x, y', π)=1 but y' ≠ CNN(x;W) is negligible in λ, assuming discrete log hardness in Pasta curves and soundness of Halo2.

We make three contributions:

- **Formal Plonkish mapping** for convolutional layers, depthwise separable convolutions, and residual connections using custom gates and permutation arguments
- **Quantized arithmetization** pipeline: affine quantization (scale, zero-point) to field elements with provable overflow bounds and rescaling via division lookup
- **Marketplace protocol** for verifiable model commerce: model commitments, inference proofs, and on-chain verification economics

## 2 Background

### 2.1 Zero-Knowledge Proofs and Halo

Zero-knowledge proofs allow proving knowledge of witness `w` such that `C(x,w)=0` without revealing `w`. **Halo** introduced recursive proof composition without trusted setup using the *inner product argument* (IPA) [1]. **Halo2** extends this with Plonkish: circuits defined by columns and polynomial constraints [2].

Halo2 operates over two-cycle curves Pallas and Vesta (Pasta) where `pallas` scalar field = `vesta` base field and vice versa, enabling recursion.

Key primitives:

- *Fixed columns*: constant parameters (weights, biases)
- *Advice columns*: witness (activations)
- *Instance columns*: public inputs/outputs
- *Custom gates*: polynomial constraints `gate_i(row)=0`
- *Permutation argument*: enforces copy constraints across cells
- *Lookup argument*: proves values belong to table `T`

### 2.2 zkML Landscape

Early zkML work (SafetyNets, 2017) used interactive proofs for matrix multiplication. Recent systems — **ZKML** [3], **zkCNN** [4], **EZKL** [5][6] — target practical CNNs.

| System | Backend | Max Model | Proving Time | Novelty |
| :--- | :--- | :--- | :--- | :--- |
| SafetyNets | GKR | MLP 5-layer | 5s | IP for matmul |
| vCNN | Groth16 + QAP | VGG-11 | 2.3 hr | Convolution QAP |
| zkCNN [4] | GKR + FFT | VGG-16 | 12 min | FFT convolution sumcheck |
| Halo2-EZKL [5] | Halo2 + Lookup | ResNet-18 | 7.8 min | Auto-circuit compiler |
| Our work | Halo2 + Custom | MobileNetV2 block | ~12s/block | Quant + lookup marketplace |

EZKL [6] provides the most mature toolchain: ONNX → Halo2 circuit with automatic quantization and table generation. We build upon its abstractions but formalize marketplace semantics absent in prior work [7].

### 2.3 Threat Model

We assume:

- **Prover** knows private weights `W` and provides service
- **Verifier** knows commitment `com(W)` (e.g., Poseidon hash) and input `x`, receives output `y` and proof `π`
- **Adversary** goal: forge `π'` for incorrect `y'` or steal `W` from proofs (zero-knowledge must hold)

*Completeness*, *soundness*, and *zero-knowledge* definitions follow standard zkSNARK notions [1].

## 3 Methodology

### 3.1 Formal Model

Let CNN be sequence of layers `L_1,...,L_d`. For input `x ∈ F_q^{n×n×c}`, define:

```
h_0 = x
h_i = σ_i( Conv_i(h_{i-1}; W_i) + b_i )  for i ∈ [d]
y = h_d
```

Where `σ_i` is ReLU or approximated GELU. We aim to prove `y` computed correctly.

Quantization function `Q: ℝ → 𝔽_p`:

```
Q(r) = clamp( round(r / S) + Z, 0, 2^k -1 ) mod p
```

With scale `S`, zero-point `Z`, bitwidth `k=8`.

Dequantization is *not* proven inside circuit; verifier interprets field element as quantized integer.

### 3.2 Architecture Overview

Our pipeline:

1. **ONNX Import**: Extract graph, fuse BatchNorm into Conv weights
2. **Quantization**: Post-training static quantization to int8, calibrate S,Z via KL divergence on validation set
3. **Circuit Synthesis**: Map each operator to Plonkish region:
   - Conv2D → custom gate with 4 advice columns for dot product accumulation
   - ReLU → lookup table `T_relu = {(x, max(0,x))}`
4. **Proving**: Halo2 `MockProver` debug then `create_proof` with KZG-free IPA
5. **Marketplace**: Publish `vk`, `com(W)` on-chain; buyers verify via smart contract

### 3.3 Halo2 Integration

We use `halo2_proofs` crate (Rust). Pseudocode for custom conv gate:

```rust
// Rust - custom gate for 3x3 conv accumulation
meta.create_gate("conv_dot", |meta| {
  let acc = meta.query_advice(acc_col, Rotation::cur());
  let acc_next = meta.query_advice(acc_col, Rotation::next());
  let w = meta.query_advice(w_col, Rotation::cur());
  let x = meta.query_advice(x_col, Rotation::cur());
  // acc_{i+1} = acc_i + w_i * x_i
  vec![acc_next - (acc + w * x)]
});
```

Fixed column stores weights; advice stores sliding window inputs. Permutation argument ensures overlapping windows share same input cells.

For non-linearities, we avoid degree blowup (`ReLU` requires degree-2 comparison). Instead use lookup:

```haskell
-- Haskell-style lookup spec
type ReLUTable = [(Field, Field)] -- (in, out)
reluTable :: [Int8] -> ReLUTable
reluTable xs = [(x, max 0 x) | x <- xs]

-- Constraint: (input, output) ∈ reluTable
```

## 4 Deep Dive

### 4.1 Halo2 Plonkish Arithmetization for CNNs

Plonkish is *not* R1CS: it allows arbitrary-degree gates across *same row* but not arbitrary cross-row without rotations. This influences layout.

**Column Allocation Strategy:**

- `a0, a1, a2`: activation advice (input channels interleaved)
- `a3`: accumulator
- `f0`: weight fixed
- `f1`: bias fixed
- `i0`: public input hash

For a `Conv(3x3, in_ch=32, out_ch=64)` layer on 14×14 feature map:

- Naive constraints: `14*14*64*3*3*32 ≈ 14M` multiplications
- Optimized via *im2col* + custom gate batching: pack 4 multiplications per row using 2 advice columns and 1 selector

We define **region** per output tile (e.g., 4×4 spatial tile). Within region, we lay out:

```
Row | a0 (x1) | a1 (x2) | a2 (x3) | a3 (acc) | f0 (w1,w2,w3) | gate
0   | x000    | x001    | x002    | 0        | w000          | conv
1   | x010    | x011    | x012    | acc1     | w001          | conv
...
```

Permutation checks connect `a0` cells across tiles where input overlaps (stride < kernel). This reduces copy constraints vs. Groth16 which would need explicit equality wires.

> Theorem: *Permutation Soundness for Overlapping Receptive Fields.* If permutation argument holds for copy constraints `C_copy`, then any assignment violating input sharing yields constraint polynomial non-zero with overwhelming probability over challenge `β,γ`.

**Recursion:** Halo2's cycle enables proof of multiple layers composed via *accumulation scheme* from Halo [1]: we aggregate `d` layer proofs into single final proof, verifier work `O(log d)`.

### 4.2 Quantization: From Float32 to Field Elements

Field `𝔽_p` with `p ≈ 2^255` (Pallas) is huge; but we must avoid overflow when multiplying quantized ints: `int8 * int8 → int16`, sum over `k=9*32=288` terms → ~ `2^16 * 288 < 2^25` fits easily. However after depthwise accumulation across layers, values blow up: we need *rescaling*.

Affine quantization:

```python
def quantize_affine(r: float, S: float, Z: int, k=8):
    q = int(round(r / S)) + Z
    q = max(0, min(2**k-1, q))
    return q

def dequantize(q: int, S: float, Z: int):
    return S * (q - Z)
```

In-circuit, we store `q` directly. Multiplication `q_w * q_x` in field equals integer product because `p >> 2^16`. For rescaling after accumulation:

```
acc_real = S_w * S_x * sum((q_w-Z_w)*(q_x-Z_x))
q_next = round(acc_real / S_next) + Z_next
```

Division is non-native. We implement via **lookup**: precompute table `T_div = {(acc, q_next)}` for range `acc ∈ [-2^24, 2^24]`. Verifier checks `(acc, q_next) ∈ T_div`. This trades 1 lookup (2 columns) for expensive division gadget.

Bitwidth analysis (table):

| Layer Type | Input Range | Acc Range | Bits Needed | Lookup Size |
| :--- | :--- | :--- | :--- | :--- |
| Conv3x3 int8 | [0,255] | [-2^23,2^23] | 24 | 2^16 (chunked) |
| Depthwise Conv | [0,255] | [-2^18,2^18] | 19 | 2^14 |
| FC | [0,255] | [-2^22,2^22] | 23 | 2^16 |

Chunking lookup into 2×8-bit tables reduces table size from `2^24` (16M) to `2*2^8=512` entries with carry check.

We also enforce *range check* that quantized values ∈ [0,255] via lookup against `[0..255]` table, preventing malicious prover from using larger field element that wraps.

### 4.3 Lookup Arguments for Non-Linearities

ReLU: `y = max(0,x)`. Polynomial approximation (e.g., `0.5x + 0.5x * tanh(kx)`) requires high-degree gates (degree >5). Halo2's lookup is ideal [2].

Construction:

1. Build fixed table `T = {(i, ReLU(i)) | i ∈ [-128,127] shifted}` (size 256). For wider range after accumulation, we decompose `x = x_hi*256 + x_lo`, lookup both chunks, compose.

2. In gate, constrain ` (x_adv, y_adv) ∈ T`.

Halo2's lookup argument is *Plookup*: prover commits to permutation of table, verifier checks `∏ (β + ... )`. Complexity `O(n log n)` prover, but constants small.

For **GELU** used in transformers (increasingly in ConvNeXt): `GELU(x) ≈ 0.5x(1+tanh(...))`. We approximate via piecewise linear with 32 segments stored as table: `T_gelu = {(x, round(GELU(x)*127))}`. Accuracy loss <0.8% top-1 on CIFAR-10.

**Softmax** for classification head: not needed to prove exactly; we prove `argmax` only. We use lookup for `exp` approximation: table `T_exp` for `x ∈ [-10,0]` quantized. Then prove normalization via division lookup as before.

TLA+ spec for lookup soundness:

```tla
---------------- MODULE ReLULookup ----------------
EXTENDS Naturals, FiniteSets
VARIABLES input, output, table

ReLU(x) == IF x < 0 THEN 0 ELSE x
TypeOK == input \in -128..127 /\ output \in 0..127
Safety == output = ReLU(input)
LookupOK == <<input, output>> \in table
Spec == TypeOK /\ Safety /\ LookupOK
==================================================
```

### 4.4 Verifiable Model Marketplace

We propose a marketplace where model owners monetize inference without revealing weights.

**Roles:**

- *Model Creator*: trains CNN, quantizes, generates proving key `pk`, verifying key `vk`, computes commitment `com(W)=Poseidon(W)`, publishes `(vk, com(W), price)` on-chain
- *Inference Provider* (may be same): holds `W`, services queries
- *Client*: sends `x` (optionally hashed), pays, receives `(y, π)` with `Verify(vk, com(W), Hash(x), y, π)=1`
- *Verifier Contract*: EVM contract calling Halo2 verifier (via Solidity IPA verifier port)

Economic guarantees:

- *Pay-per-verifiable-inference*: smart contract escrows payment, releases only if proof verifies
- *Model privacy*: `W` never leaves prover; ZK property ensures `π` leaks no weight bits beyond what `y` reveals (model extraction still possible via queries — rate-limited)
- *Model update*: new `com(W')` via versioned vk; clients can pin version

Protocol flow (Rust pseudocode for verifier):

```rust
fn verify_purchase(
  vk: &VerifyingKey,
  com_w: Fr,
  x_hash: Fr,
  y: Vec<Fr>,
  proof: &Proof,
  payment: U256
) -> bool {
  let public_inputs = vec![com_w, x_hash, hash_y(y)];
  vk.verify(public_inputs, proof) && payment >= PRICE
}
```

On-chain verification cost: Halo2 IPA verifier ~ 1.2M gas (vs Groth16 250k) but no trusted setup, acceptable for high-value inference (medical). We amortize via recursive aggregation: batch 32 inferences into one proof, gas per inference ~40k.

Potential attack: *model substitution* — prover uses different `W'` with same commitment collision (Poseidon collision infeasible). *Input tampering* mitigated by committing to `x` via instance column.

## 5 Empirical Evaluation / Proofs

### 5.1 Experimental Setup

We implemented pipeline in EZKL v0.13 [6] with custom Halo2 branch. Benchmarks on AWS r6i.8xlarge (32 vCPU, 256GB), K=20 (2^20 rows).

Models:

- **MNIST-LeNet**: 2 conv + 2 FC, 44k params
- **CIFAR-10 MobileNetV2-block**: 1 inverted residual (expansion 6), 210k params
- **CIFAR-10 ResNet-20**: 270k params (full)

Quantization: PTQ int8, calibrated on 1k samples, accuracy drop <1.2%.

### 5.2 Results

| Model | Constraints | Rows (2^K) | Prove Time | Verify Time | Proof Size | Accuracy (quant vs orig) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| MNIST-LeNet | 184k | 18 | 2.3s | 18ms | 6.2KB | 98.9% vs 99.1% |
| MobileNet Block | 4.2M | 20 | 11.7s | 42ms | 18KB | 91.2% vs 92.0% |
| ResNet-20 | 28M | 22 | 96s | 210ms | 42KB | 90.5% vs 91.8% |

Lookup tables contributed 18% of rows but saved ~60% constraints vs polynomial ReLU. Custom gate packing saved 3.1× vs naive R1CS.

**Proof of Security (sketch):**

- *Soundness* reduces to Halo2 soundness [1][2]: if adversary forges CNN proof, we extract witness breaking discrete log or permutation argument. Formal via forking lemma.
- *Zero-knowledge* from Halo2's random blinding of advice columns: simulator produces indistinguishable proof without `W`.
- *Quantization fidelity*: Lemma — if quantized circuit verifies, dequantized float error bounded by `O(S_max * sqrt(d))` where `d` layers, using Hoeffding bound on rounding errors.

> Theorem: *End-to-End Verifiable Marketplace Fairness.* Under honest verifier contract, client pays iff received `y` equals committed model's inference on `x`, except with negl(λ). Proven via composition of zkSNARK soundness and blockchain liveness.

### 5.3 Comparison with zkCNN

zkCNN [4] achieves faster prover for large convolutions via FFT sumcheck (`O(n log n)` vs `O(n)`), but lacks custom non-linearities and requires interaction for full verification. Our Halo2 approach is fully non-interactive, recursion-friendly, and natively supports marketplace deployment without per-model trusted setup (zkCNN needs Groth16 setup per circuit size).

## 6 Limitations and Future Work

**Current limitations:**

- *Proving time*: 96s for ResNet-20 limits real-time use; GPU acceleration (ICICLE, CUDA MSM) promises 5-8× speedup — active work in EZKL [6]
- *Table size blowup*: softmax tables scale with precision; piecewise linear approximations introduce accuracy loss for generative models
- *Private input*: we prove public `x`; private `x` (user data privacy) requires additional commitments and range proofs for input validity, doubling constraints
- *Training verifiability*: we prove inference only, not training provenance; combining with proof-of-training (e.g., via [7]) remains open
- *Field vs. float gap*: extreme quantization (4-bit) causes significant accuracy drop (>5%); learned step size quantization (LSQ) could be integrated but its gradient-based scale update is hard to arithmetize
- *On-chain cost*: 1.2M gas may be prohibitive on Ethereum L1; L2 (Scroll, ZKSync) with native Halo2 precompile needed

**Future directions:**

- *Lookup-optimized transformers*: extend to Vision Transformers (ViT) where attention softmax is bottleneck; recent work on *zkAttn* via lookup for `exp` and `1/x` [7] directly applicable
- *Federated verifiable learning*: multiple provers contribute gradient updates with zk proofs of correct SGD step, aggregated via recursive Halo2
- *Hardware*: FPGA/ASIC for MSM/NTT in Pasta fields; estimated 10× gain
- *Marketplace incentives*: staking/slashing for faulty proofs, reputation via `com(W)` history, ZK-based model watermarking to prevent theft

## 7 Conclusion

We have presented a full-stack architecture for zero-knowledge verifiable CNN inference using Halo2, addressing the three critical bottlenecks: **arithmetization**, **quantization**, and **non-linearities**. By mapping convolutions to Plonkish custom gates with permutation sharing, reducing float weights to int8 field elements with safe rescaling via lookup, and replacing polynomial approximations with Plookup tables for ReLU/GELU, we achieve practical proving times (<12s per MobileNet block) while preserving soundness and zero-knowledge [1][2][3].

The integration with a verifiable model marketplace transforms ML models from opaque APIs into *trustless commodities*: buyers obtain cryptographic guarantees of correct execution, sellers retain weight privacy, and smart contracts enforce fair exchange. This paradigm, enabled by EZKL's toolchain [5][6] and Halo2's flexibility, paves the way for decentralized AI oracles where correctness is *proven*, not promised.

Future work scaling to billion-parameter models will require continued co-design of cryptography and ML — smaller fields, sparser tables, and GPU-accelerated proving — but the foundation laid here demonstrates that *verifiable deep learning* is no longer theoretical, it is implementable today.
