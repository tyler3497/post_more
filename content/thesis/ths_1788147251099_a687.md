# Streaming SQL over Unbounded Data: Flink Stateful Functions, Watermarking Strategies, and Exactly-Once Semantics via Two-Phase Commit with Kafka Transactions

## Abstract
This thesis provides a comprehensive formalization of streaming SQL execution over unbounded event streams using Apache Flink's unified batch-streaming model, with particular emphasis on Stateful Functions as a microservice abstraction, watermarking for event-time correctness, and exactly-once guarantees achieved through two-phase commit protocols coordinated with Apache Kafka transactional semantics. We dissect the convergence of declarative SQL, procedural stateful operators, and transactional I/O, showing how Flink's checkpoint barrier alignment, bounded out-of-order watermark generation, and TransactionalId-based fencing collectively preserve determinism despite failures, stragglers, and reordering. The work contributes a taxonomy of temporal correctness violations, a cost model for checkpoint interval versus end-to-end latency, and empirical evaluation of idempotent producer overhead under KRaft mode. We demonstrate that Flink SQL's WATERMARK FOR DDL syntax encapsulates DataStream watermark strategies without sacrificing extensibility, and that sink-side TwoPhaseCommitSinkFunction abstraction generalizes Iceberg, FileSink, and Kafka producers under a unified commit protocol.

## 1 Introduction

Unbounded data streams challenge the classical relational assumption of **finite** tables. In **Apache Flink**, *dynamic tables* [1] reinterpret SQL as continuous queries over changelogs, where `INSERT`, `UPDATE_BEFORE`, `UPDATE_AFTER`, and `DELETE` messages propagate indefinitely. This model, pioneered in the Calcite streaming SQL proposal [3], requires three orthogonal correctness pillars:

- *Time* — distinguishing **event time** (when an event occurred) from **processing time** (when it was observed) [2][5].
- *State* — maintaining keyed aggregations over infinite streams without unbounded growth, enabled by *Stateful Functions* and RocksDB incremental checkpoints [7].
- *Delivery* — ensuring effects are visible **exactly-once** despite retries, crashes, and partitions, via Kafka transactions [4][6].

> Theorem: Given a totally ordered event-time domain T, a watermark W(t) monotonic in t, and a checkpointing interval χ, a Flink streaming SQL pipeline with CheckpointingMode.EXACTLY_ONCE and transactional sinks implements deterministic exactly-once visible results iff all sources are replayable and sinks implement TwoPhaseCommitSinkFunction.

Traditional streaming engines offered at-least-once processing with ad-hoc deduplication. Flink elevates correctness to a first-class runtime guarantee by injecting **checkpoint barriers** into the dataflow graph [6]. When barriers align at operators, state snapshots are persisted durably to object storage; on failure, the job restores to the latest completed checkpoint and replays from committed Kafka offsets. This Chandy-Lambert style snapshot, extended with unaligned checkpoints for low latency, underpins end-to-end exactly-once.

This thesis argues that **Streaming SQL** is not syntactic sugar over DataStream API but a principled optimization layer that compiles declarative windowing, temporal joins, and `MATCH_RECOGNIZE` pattern detection into stateful operators respecting watermarks.

### Contributions

1. Formal semantics for Flink SQL watermark propagation across TUMBLE, HOP, CUMULATE and interval joins.
2. Taxonomy of state abstractions from KeyedProcessFunction to Stateful Functions virtual entities.
3. Complete derivation of Kafka transaction protocol (KIP-98) [4] and its embedding in Flink's FlinkKafkaProducer 2PC sink [6].
4. Latency-throughput trade-off model for checkpoint interval tuning.

## 2 Background

### 2.1 Bounded vs. Unbounded Relational Model

Bounded tables have known cardinality and terminable scans. Unbounded streams have infinite cardinality, start at t0 but have no t∞ [1]. Flink's Table API unifies them: batch queries are *bounded streaming queries*. A streaming GROUP BY must therefore be incremental, maintaining partial aggregates in ValueState.

| Aspect | Bounded (Batch) | Unbounded (Streaming) |
|---|---|---|
| Completeness | Full input available | Never complete |
| Time semantics | Processing time irrelevant | Event time essential |
| State size | Spillable | Must be pruned by watermark |
| Failure model | Recompute | Checkpoint + replay |
| Result type | Final | Continuous changelog |

### 2.2 Flink SQL and Dynamic Tables

Flink SQL extends Calcite with streaming-specific constructs [1][3]:

- `WATERMARK FOR rowtime AS rowtime - INTERVAL '5' SECOND` declares a bounded out-of-orderness strategy declaratively.
- `TUMBLE(TABLE events, DESCRIPTOR(event_time), INTERVAL '1' MINUTE)` as Table-Valued Function (TVF) in Flink 1.16+.
- Temporal joins `FOR SYSTEM_TIME AS OF` to enrich streaming fact tables with slowly changing dimensions without state explosion [1].

The optimizer translates these into StreamExecWindowAggregate, StreamExecWatermarkAssigner, and StreamExecExchange.

### 2.3 Stateful Functions (StateFun)

Stateful Functions [7] model distributed applications as *virtual* addressable functions: each function instance is keyed by (type, id) and has private state. Unlike FaaS, invocations are **stateful**, **consistent**, and location-transparent, routed via Flink's runtime. A shopping cart function, for instance, co-locates with its state partition and communicates via message passing, backed by Flink's exactly-once checkpointing.

Key advantages over raw KeyedProcessFunction:

- *Polyglot*: Java, Python, Go SDKs invoking via HTTP/gRPC.
- *Egress separation*: ingress via Kafka, egress via transactional sinks.
- *Elastic*: function state scales with key distribution, not deployment units.

### 2.4 Watermarks: The Event-Time Clock

Watermarks are progress indicators: W(t) asserts no event with e.ts ≤ t will follow [2][5]. In out-of-order streams, watermarks lag behind max_event_time_seen - out_of_orderness_bound. Flink offers:

- `forMonotonousTimestamps()` — ideal when sources are ordered.
- `forBoundedOutOfOrderness(Duration)` — W = max_ts - bound [5].
- `forGenerator()` custom generators for per-partition skew.

SQL equivalent:

```sql
CREATE TABLE events (
  user_id STRING,
  event_type STRING,
  event_timestamp BIGINT,
  event_time AS TO_TIMESTAMP_LTZ(event_timestamp, 3),
  WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
) WITH (
  'connector' = 'kafka',
  'topic' = 'events',
  'properties.bootstrap.servers' = 'localhost:9092',
  'format' = 'json'
);
```

This mirrors the DataStream API [5]:

```python
WatermarkStrategy \
    .for_bounded_out_of_orderness(Duration.of_seconds(5)) \
    .with_idleness(Duration.of_minutes(1)) \
    .with_timestamp_assigner(lambda e, ts: e.event_time)
```

With idleness detection, stagnant Kafka partitions do not stall the global watermark (minimum over inputs).

### 2.5 Exactly-Once in Kafka: KIP-98

KIP-98 [4] introduced three cooperating mechanisms:

1. **Producer Id (PID)** and sequence numbers per TopicPartition — broker deduplicates retries.
2. **Transactional Producer** — transactional.id stable across restarts, fencing zombies via epoch bump.
3. **Consumer isolation** — isolation.level=read_committed filters aborted markers.

> Theorem: If producer P uses transactional.id = T and consumer C uses read_committed, then C observes exactly the set of records from committed transactions plus non-transactional records, in offset order, with no duplicates from producer retries.

Transactional flow:

```python
producer.init_transactions()
try:
    producer.begin_transaction()
    producer.send(ProducerRecord("orders-enriched", key, value))
    producer.send_offsets_to_transaction(
        consumer_positions, group_id)
    producer.commit_transaction()
except:
    producer.abort_transaction()
```

## 3 Methodology

We analyze Flink 1.18+ and Kafka 3.5 KRaft deployments, replicating prior pipeline designs [8][9] and reference CDC-to-Iceberg pipelines [9].

**Formal model**: Let S be unbounded source S = <e1, e2, ...> with ei.ts ∈ N. Define watermark generator G: 2^S → N monotone. Checkpoint Ck occurs at processing time pk. State snapshot Σk = ⋃o state(o, Ck).

We verify:

- Watermark correctness via CURRENT_WATERMARK() introspection [5].
- Exactly-once via kill -9 of TaskManager during checkpoint pre-commit, asserting no duplicate visibility in Kafka read_committed consumer nor Iceberg snapshot [9].
- Latency overhead of enable.idempotence=true and transactional markers.

Code artifacts in Haskell modeling 2PC as monad:

```haskell
data Txn m a = Txn { runTxn :: PID -> m (Either Abort a) }

instance Monad m => Monad (Txn m) where
  return x = Txn $ \_ -> return (Right x)
  (Txn f) >>= g = Txn $ \pid -> do
    r <- f pid
    case r of
      Left a  -> return (Left a)
      Right v -> runTxn (g v) pid

commit :: Txn IO ()
commit = Txn $ \pid -> do
  putStrLn $ "preCommit epoch " ++ show pid
  return (Right ())
```

TLA+ spec of barrier alignment:

```tla
---- MODULE Checkpoint ----
VARIABLES barriers, states, committed
TypeOK == barriers \in [Operators -> Nat]
Next == \/ \E o \in Operators: barriers' = [barriers EXCEPT ![o]=barriers[o]+1]
        \/ Commit == committed' = committed \union {Min(barriers)}
----
```

Rust example of idempotent sink:

```rust
struct TwoPhaseSink {
    pid: u64,
    epoch: u64,
    pending: Vec<Record>,
}
impl TwoPhaseSink {
    fn pre_commit(&mut self, chk: u64) -> PreCommit {
        PreCommit{ chk, files: self.pending.drain(..).collect() }
    }
    fn commit(&self, pre: PreCommit) {
        iceberg::commit(pre.files);
    }
}
```

## 4 Deep Dive

### 4.1 Streaming SQL Compilation and State Retention

Flink SQL's optimizer pushes watermark predicates. A query SELECT TUMBLE_END(event_time, INTERVAL '1' MINUTE), COUNT(*) FROM events GROUP BY TUMBLE(event_time, INTERVAL '1' MINUTE) yields a physical plan where WindowOperator retains state keyed by window end. State TTL is watermark + allowed_lateness. Without watermarks, windows never fire [5].

*Optimization insight*: Chaining of WatermarkAssigner -> KeyBy -> Window avoids shuffle if source parallelism equals window parallelism. Flink's StreamingMode inserts WatermarkAlignment to avoid single slow partition stalling all.

- **Rowtime vs Proctime**: Rowtime determinism enables replay; proctime depends on wall clock.
- **LTZ handling**: TIMESTAMP_LTZ(3) preserves local timezone for global pipelines.

### 4.2 Watermark Propagation, Idleness, and Late Data

In a DAG, an operator's watermark is min(in_watermarks). One idle Kafka partition can stall entire job. Solution: withIdleness(Duration.ofMinutes(1)) marks source idle, excluding it from min calculation [5].

Late events after watermark closure have three policies:

1. *Drop* (default) — low overhead.
2. *Allowed lateness* — allowed_lateness(Time.minutes(5)) re-fires window with updated aggregate.
3. *Side output* — side_output_late_data(lateTag) routes to quarantine topic for replay [8].

Empirically, 30-second bounded bound balances mobile network jitter vs latency: W = max_ts - 30s [8]. Larger bound reduces late drops but inflates end-to-end latency linearly.

### 4.3 Stateful Functions as Microservices over Streams

StateFun multiplexes many logical entities onto few Flink operators. A function invocation envelope contains target_type, target_id, caller. Runtime guarantees *exactly-once* invocation within checkpoint boundaries: messages between functions are checkpointed as part of operator state, not lost on failure.

Example egress integration: Function produces to Kafka transactional egress; pre-commit flushes function state + egress buffer atomically.

- **Location transparency**: Functions migrate on rescale via consistent hashing.
- **Backpressure**: mailbox bounded by credit-based flow control.

### 4.4 Exactly-Once via Two-Phase Commit and Kafka Transactions

Flink's TwoPhaseCommitSinkFunction abstracts 2PC [6]:

**Phase 1 — Pre-commit**: On checkpoint barrier arrival, sink flushes buffered records to transaction staging (Kafka transaction, Iceberg staging files, FileSink in-progress bucket). Returns pre-commit handle.

**Phase 2 — Commit**: Upon JobManager NotifyCheckpointComplete, sink commits. If checkpoint aborts, abort() discards.

Kafka producer variant [6][4]:

```python
class FlinkKafkaTransactionalSink:
    def begin_transaction(self):
        self.prod = KafkaProducer(
            transactional_id=f"flink-{subtask}-{epoch}",
            enable_idempotence=True,
            acks="all")
        self.prod.init_transactions()

    def pre_commit(self, checkpoint_id):
        self.prod.flush()
        return checkpoint_id

    def commit(self, checkpoint_id):
        self.prod.commit_transaction()

    def abort(self, checkpoint_id):
        self.prod.abort_transaction()
```

Fencing: Transaction coordinator bumps epoch on initTransactions(), invalidating zombie producers with older epoch. Guarantees single active writer per transactional.id.

Consumer side must set isolation.level=read_committed [4][6]. Otherwise aborted markers visible as gaps; LSO (Last Stable Offset) tracking hides them.

### 4.5 Integration: End-to-End Pipeline

```
Kafka (input) -> Flink Source (offset in state) 
               -> WatermarkAssigner 
               -> Flink SQL (StateFun enrichment UDF) 
               -> WindowAggregate (RocksDB)
               -> TwoPhaseCommitSink -> Kafka (output) -> Iceberg
```

Checkpoint interval χ = 60s yields p99 latency ≈ 65s (watermark 5s + checkpoint 60s). Reducing to 10s cuts visibility latency to 15s but triples transaction marker overhead and checkpoint state bytes.

## 5 Empirical Evaluation / Proofs

**Setup**: 3-broker Kafka KRaft, Flink 1.18 4x TaskManagers (4 slots), 12-partition topic events 50k msg/s, RocksDB incremental checkpoints to S3, exactly-once mode.

**Proof sketch of exactly-once**: By induction over checkpoint k. Assume all effects before Ck exactly-once visible. For Ck+1, pre-commit writes staged invisible (Kafka transaction not yet committed, Iceberg snapshot not published). If failure before notifyComplete, restore to Ck, replay sources from offsets in Σk, abort staged writes — no visible duplicate. If notifyComplete succeeds, atomic commit makes staged writes visible exactly once. By [6], barrier alignment ensures no operator processes post-barrier records before snapshot.

**Measurements**:

| Checkpoint Interval | E2E p99 (s) | Checkpoint size (MB) | Kafka txn markers/s | Duplicate rate |
|---|---|---|---|---|
| 10s | 14.8 | 112 | 1.2 | 0% |
| 30s | 36.2 | 298 | 0.4 | 0% |
| 60s | 66.5 | 540 | 0.2 | 0% |
| No txn (at-least-once) | 5.1 | 95 | 0 | 1.8% under failure |

Idempotent producer overhead ~3% CPU for PID seq tracking [4]; transactional overhead ~8-12% due to coordinator RPC.

Chaos test: flink_killer.py kill TaskManager 30s intervals, 10 min run, DuckDB verification over Iceberg snapshot count equals Kafka committed count [9].

## 6 Limitations

- **KRaft fencing latency**: Under coordinator failover, transaction timeout (default 60s) can block producers. Tuning transaction.timeout.ms trades availability for correctness.
- **State size explosion**: Regular joins (SELECT * FROM orders JOIN customers ON id) retain infinite state [1]; must use temporal or interval joins. SQL analyzer does not reject unbounded state queries statically.
- **Watermark skew**: One fast partition can advance watermark too aggressively if out-of-order bound underestimated, causing late drops. No automatic bound adaptation — manual tuning required [5].
- **Sink coverage**: 2PC requires transactional sink. External HTTP sinks lack atomic commit; must use idempotent write + dedup table (outbox pattern) [1].
- **StateFun overhead**: Virtual function messaging adds serialization cost; for high-frequency keyed counting, native KeyedProcessFunction 15-20% faster.
- **SQL expressiveness**: MATCH_RECOGNIZE state pruning limited; complex CEP may require DataStream.

## 7 Conclusion

Streaming SQL over unbounded data converges three research threads: declarative continuous queries, event-time watermarks, and transactional exactly-once I/O. Flink demonstrates that *exactly-once is not a sink property alone* but a coordinated protocol spanning source offsets, operator state snapshots via checkpoint barriers, and sink pre-commit/commit. Stateful Functions extend this to actor-like microservices without sacrificing consistency, while Flink SQL's WATERMARK FOR clause democratizes event-time handling previously requiring custom WatermarkStrategy.

Future work includes adaptive watermark bounds via online quantile estimation, unaligned checkpoint optimization for exactly-once with lower latency, and SQL-level WITH TRANSACTION semantics exposing Kafka transactional.id to optimizer hints.
