# Verified Compilation from Source to Silicon: CompCert, CakeML, Proof-Carrying Code, and the Compositional Correctness of Optimizing Compilers

## Abstract

Compilers are the most trusted and least trustworthy components of the software stack: every assurance argument about source code is void if the compiler mis-translates it. This thesis surveys *verified compilation* — compilers accompanied by machine-checked proofs that generated code preserves source semantics. We develop the mathematical core of correctness through **simulation relations** and **behavior refinement**, then examine three landmark achievements: **CompCert**, a verified optimizing C compiler in Coq whose per-pass forward simulations compose into an end-to-end semantic preservation theorem over a realistic block-offset memory model [1][2]; **CakeML**, a verified functional-language compiler in HOL4 whose twelve intermediate languages, verified garbage collector, and in-logic bootstrapping reach concrete machine code for five architectures [4][5]; and **proof-carrying code**, in which untrusted binaries carry checkable proofs of safety, minimizing trust to a proof checker [6][7]. We then treat the compositional frontier — structured simulations, open-module semantics, and verified linking — and close with an empirical comparison of the major artifacts, the residual trusted base, and directions for end-to-end verified toolchains.

## 1 Intro

In 1984, Ken Thompson observed that no amount of source-level auditing can detect a compiler that inserts a back door, because the compiler can also miscompile the compiler [6]. Four decades later, the observation is sharper, not duller: modern optimizing compilers are among the largest symbolic transformation systems ever built, and miscompilation bugs are discovered routinely — automated testing campaigns have uncovered hundreds of wrong-code bugs in production compilers. The standard mitigations — test suites, differential testing, manual review of generated assembly with optimizations disabled — are expensive and fundamentally incomplete.

*Verified compilation* attacks the problem at its root. Instead of testing that a compiler *usually* preserves meaning, a verified compiler is a program paired with a **machine-checked proof** that it *always* preserves meaning, relative to formal semantics of its source and target languages. The proof is checked by a small, independent proof checker, so trust migrates from hundreds of thousands of lines of optimizer code to the proof checker and the language semantics.

## 2 Background

### 2.1 The correctness statement

Let *S* range over source programs and *C* over compiled programs. Write **Beh(P)** for the set of *observable behaviors* of a program *P* — the traces of external events (system calls, volatile accesses, I/O) it may produce, including divergence and abnormal termination. A compiler **Comp** is *correct* when, for every source program *S*,

> **Definition (Semantic preservation).** If **Comp(S) = OK(C)**, then **Beh(C) ⊆ Beh(S)**.

The inclusion is deliberately asymmetric: the compiled program may exhibit *fewer* behaviors than the source. This asymmetry captures three realities of real compilers [2]:

1. **Compilation may fail.** The compiler may refuse a program (syntax errors, type errors, or exhausted internal capacity, e.g. a function whose frame exceeds addressable memory).
2. **Nondeterminism may be resolved.** C leaves evaluation order partially unspecified; the compiler is free to pick any one of the source's admissible behaviors.
3. **Behaviors may be improved.** An *improvement* converts undefined behavior into defined behavior — for instance, when an optimization deletes a division whose result is unused, the compiled program no longer traps on division by zero. Crucially, if the source program is provably free of undefined behavior, improvement never fires and **Beh(C)** equals one of the source's genuine behaviors.

### 2.2 Simulations and intermediate languages

No realistic compiler is proved correct in one leap. Instead, compilation is factored into a pipeline of passes, each translating one *intermediate language* (IL) to the next. Every IL carries a formal operational semantics, and every pass is justified by a **simulation theorem**: a relation *R* between source and target states such that each step of the source is matched by zero or more steps of the target while preserving *R*.

> **Theorem: (Forward simulation implies refinement).** If pass *P* admits a forward simulation from the semantics of IL *i* to the semantics of IL *i+1*, then the observable behaviors of the translated program refine those of the original. Forward simulations compose: chaining the simulations of all passes yields whole-compiler correctness.

*Backward* simulations (target steps matched by source steps) are the dual notion and are used where forward simulation is awkward, e.g. across passes that introduce new nondeterminism. The art of verified compilation is choosing ILs whose semantic distance is small enough that each simulation is provable, yet large enough that the pipeline mirrors the architecture of real compilers.

## 3 Methodology

The methodology of this thesis is that of the field itself: we reconstruct, from the primary literature and mechanized artifacts, how compiler correctness is *stated*, *decomposed*, and *discharged* in practice [1][2][4][5][6][7][8][9].

**Corpus.** We take as primary sources the canonical papers and developments: Leroy's CompCert papers and user manual [1][2][3], the CakeML backend papers and characteristic-formulae work [4][5][8], the PCC literature from Necula–Lee through the Open Verifier framework [6][7], and the Isabelle/HOL-to-CakeML verified front end [9]. Every technical claim below is traceable to these sources.

**Analytical framework.** For each system we identify (i) the exact correctness theorem and its statement of refinement; (ii) the decomposition into passes and the simulation discipline used; (iii) the memory and machine model; (iv) the trusted computing base — what is proved, what is assumed; and (v) the compositionality story: separate compilation, linking, and interaction with unverified code.

**Validation of claims.** Where the literature reports quantitative facts — numbers of intermediate languages, target architectures, proof-engineering scale — we reproduce the figures as stated by the artifact authors and flag where figures have evolved across versions. We deliberately avoid inventing precision the sources do not provide.

## 4 Deep Dive

### 4.1 CompCert: simulation-based semantic preservation in Coq

CompCert, developed by Xavier Leroy and collaborators beginning in 2005, is the landmark verified compiler: a realistic optimizing compiler from a large subset of C (*CompCert C*) to assembly for x86, ARM, PowerPC, and RISC-V, written and proved correct inside the Coq proof assistant [1][3].

**Pipeline.** Compilation proceeds through roughly ten intermediate languages: CompCert C → *Clight* → *Cminor* → *CminorSel* → *RTL* (register transfer language) → *LTL* → *Linear* → *Mach* → *Asm*. Early passes are *verified by construction* — the translation is written in Coq's Gallina language and its simulation proved directly. The classic example is the front end (C to Cminor), proved by Blazy, Dargaye, and Leroy [1]. Later passes use **translation validation**: an unverified, heuristic implementation (e.g. graph-coloring register allocation, lazy code motion) is paired with a *verified validator* that checks each run's output against its input; only validated translations are accepted [1].

**The simulation discipline.** Each pass carries a forward simulation theorem. A representative instance is register allocation: pseudo-registers of RTL are mapped to hardware registers or stack slots of LTL, and the simulation invariant states that related states agree on all live values. Because allocation is heuristic, the validator re-derives the mapping and checks it; the proof then shows that *any* validated mapping yields a correct translation. This pattern — *unverified oracle plus verified checker* — recurs throughout CompCert and was later generalized in CompCertS, where oracles are given an explicit logical status [2].

**The memory model.** CompCert's memory model is arguably its deepest intellectual contribution. Memory is a finite map from *block identifiers* to blocks; each block has lower and upper bounds, a content function from offsets to values, and permissions per access. Values include integers, floats, pointers (block, offset pairs), and *undefined*. The operations are:

```tla
------------------------------- MODULE CompCertMem -------------------------------
EXTENDS Naturals, FiniteSets
VARIABLES blocks, nextblock
Alloc(n) ==  /\ nextblock' = nextblock + 1
             /\ blocks' = blocks \cup {[id |-> nextblock, lo |-> 0, hi |-> n]}
             /\ UNCHANGED vars
Free(b)  ==  blocks' = {x \in blocks : x.id /= b}
Store(b, ofs, v) == LET blk == CHOOSE x \in blocks : x.id = b IN
                   blk.lo <= ofs /\ ofs + size(v) <= blk.hi
Load(b, ofs, t)  == LET blk == CHOOSE x \in blocks : x.id = b IN
                   blk.lo <= ofs /\ ofs + size(t) <= blk.hi
=============================================================================
```

Permissions (*Freeable*, *Writable*, *Readable*, *Nonempty*) govern which operations are legal, and *memory injections* relate memories across passes: an injection maps source blocks to target blocks with offsets, allowing the simulation to survive spilling, coalescing, and stack-frame layout. The CompCertS variant extends the model with *finite* memory and explicit failure on exhaustion, closing a soundness gap in which the original model assumed unbounded allocation [2].

**Semantic subtleties.** The top-level theorem is exactly the refinement statement of Section 2.1, including the three allowances: compile-time failure, nondeterminism resolution, and behavior improvement. Floating-point arithmetic is handled with a full IEEE-754 formalization by Boldo, Jourdan, Leroy, and Melquiond, so the compiler's claims extend to floating-point code [1].

### 4.2 CakeML: end-to-end functional compilation in HOL4

CakeML is, to quote its authors, "the most realistic verified compiler for a functional programming language to date" [4]. Developed in the HOL4 theorem prover, it compiles a substantial subset of Standard ML — including modules, exceptions, and arbitrary-precision integers — through a backend of **twelve** intermediate languages down to *concrete machine code* for five architectures: x86-64, ARMv8, ARMv6, MIPS-64, and RISC-V [4][5].

**End-to-end reach.** Where CompCert stops at assembly text (leaving the assembler and linker trusted), CakeML's correctness theorem relates the source-level semantics directly to the behavior of *machine code as executed by detailed, validated models of real instruction set architectures* [5]. This closes a notorious gap: instruction encoders are subtle, and offset-overflow or field-encoding bugs in unverified assemblers would silently void a compiler correctness proof. CakeML generates machine code with a verified encoder and reasons about fetching and decoding in the ISA model.

**Verified runtime services.** A functional language needs a runtime, and CakeML verifies its own: a **generational copying garbage collector** and an **arbitrary-precision integer (bignum) library** are both implemented and proved correct against their specifications. The compiler's passes include closure conversion, multi-argument function optimization, data representation selection, and register allocation — resembling a mainstream strict-functional-language compiler, but every pass proved [4].

**Characteristic formulae.** Reasoning about CakeML programs is supported by *characteristic formulae* (CF): a program logic in the style of separation logic whose assertions are generated compositionally from CakeML syntax. Guéneau, Myreen, Kumar, and Norrish give verified CF for CakeML, enabling proofs of imperative CakeML programs — including the compiler's own I/O wrapper — against abstract specifications [8]. The CF work is also the bridge used by the **proof-producing translation** from HOL4 functions to CakeML: Myreen and Owens' translator emits CakeML code together with a theorem certifying that the code refines the original HOL function, with refinement invariants relating HOL values to deeply embedded CakeML values [8][9].

**Bootstrapping in the logic.** Perhaps the most striking engineering feat: the CakeML compiler is *bootstrapped inside HOL4*. The compiler, written as HOL functions, is applied to its own source via HOL4's symbolic evaluation (evaluation that produces theorems, not just values), yielding a verified binary of the compiler itself [4]. The top-level theorem then states that running this binary on source text produces machine code whose ISA-level behavior matches the source semantics — a self-hosting verified compiler with a machine-checked certificate.

```haskell
-- Sketch of a verified CakeML-style pass: closure conversion
-- Each pass is a pure function; correctness is a simulation theorem.
data Exp = Var Name | Lam Name Exp | App Exp Exp | Let Name Exp Exp

freeVars :: Exp -> Set Name
freeVars (Var x)     = singleton x
freeVars (Lam x e)   = delete x (freeVars e)
freeVars (App f a)   = union (freeVars f) (freeVars a)
freeVars (Let x e b) = union (freeVars e) (delete x (freeVars b))

-- closeConv e env  replaces each Lam by an explicit closure record
-- Theorem (simulation): eval (closeConv e env) ~= eval e  under env
closeConv :: Exp -> Env -> CExp
closeConv (Lam x body) env =
  let fvs = toList (freeVars (Lam x body)) in
  MkClosure x fvs (closeConv body (extend env fvs))
closeConv e env = mapExp (flip closeConv env) e
```

### 4.3 Proof-carrying code: certificates instead of trust



```python
# Sketch of the PCC trust architecture (producer side)
def vcg(binary, policy):
    """Generate verification conditions: safety of every instruction."""
    vcs = []
    for instr in binary:
        pre  = precondition(instr.addr)          # from annotations / inference
        post = strongest_postcondition(pre, instr)
        vcs.append(implies(pre, safety_obligation(instr, policy)))
        vcs.append(implies(post, precondition(instr.next_addr)))
    return vcs

def produce(binary, policy, prover):
    proof = prover.prove(vcg(binary, policy))    # expensive, done once
    return (binary, proof)                       # shipped to consumer

def consume(package, policy, checker):
    binary, proof = package
    assert checker.check(vcg(binary, policy), proof)  # cheap, trusted base
    return execute_natively(binary)                   # no runtime checks
```





> **Theorem: (PCC soundness, schematic).** If the VCGen is sound (validity of the verification conditions implies the safety predicate holds of all executions) and the proof checker accepts only valid proofs, then any executed PCC binary satisfies the consumer's safety policy — regardless of what the producer did.

### 4.5 Verified optimization passes and end-to-end toolchains





- **Verified cryptography.** Fiat Crypto synthesizes low-level field-arithmetic C from high-level specifications with correctness proofs; compiling it with CompCert yields binaries resting on two machine-checked links [2].
- **Verified hardware/software stacks.** Kami verifies hardware descriptions down to synthesizable RTL; composing a verified processor with a verified compiler carries source-level theorems all the way to gates.
- **Verified operating systems.** DeepSpec-style projects compose verified compilers with verified kernels and file systems, so applications proved correct in logic run correctly on hardware.
- **Self-hosting verified compilers.** CakeML's in-logic bootstrap [4] is the purest end-to-end result: the compiler binary is itself the product of verified compilation, certified by the prover's own kernel.

> **Theorem: (Vertical composition).** Let passes *P₁ … Pₙ* have forward simulations *R₁ … Rₙ* between successive IL semantics. Then the relation obtained by relational composition *R₁ ⨾ R₂ ⨾ … ⨾ Rₙ* is a forward simulation from the source semantics to the target semantics, and the whole compiler enjoys semantic preservation. This is the formal content of "correct passes compose into a correct compiler" [1][3].

> **Theorem: (Horizontal composition, schematic).** If modules *M₁*, *M₂* compile to *M₁'*, *M₂'* with open-simulations respecting complementary import/export interfaces, then linking commutes with compilation up to behavioral refinement: **link(M₁', M₂')** refines **link(M₁, M₂)**. This is the CompCertO/SepCompCert compositionality result.

> **Theorem: (Translation validation soundness).** If an unverified oracle *O* and a verified validator *V* satisfy "whenever *V(S, O(S))* accepts, *O(S)* refines *S*", then the composite pass is correct *even though O is arbitrary code*. Trust is confined to *V* [1].

## 6 Limitations

An honest survey must state what the theorems do *not* cover — the **trusted computing base** (TCB) of each system.

1. **The proof assistant kernel.** CompCert's theorems are only as trustworthy as Coq's kernel and its extraction to OCaml; CakeML's rest on the HOL4 kernel. Kernel bugs have occurred historically in every major assistant; independent checkers mitigate this, but the kernel remains axiomatic trust.
2. **Unverified pipeline stages.** CompCert does not verify its parser, elaborator, assembler, or linker; a bug in elaboration of C surface syntax to CompCert C ASTs voids the guarantee. CakeML closes the assembler gap by emitting machine code directly but trusts its parser and pretty-printer.
3. **Semantics fidelity.** A compiler proved against a *formal model* of x86 is correct relative to that model; if the model misdescribes silicon (e.g. weak-memory subtleties, undocumented instructions), the theorem does not transfer. CakeML's ISA models are extensively validated but remain models.
4. **Concurrency.** The classical results are sequential. CompCertTSO extends CompCert to x86-TSO weak memory, but verified compilation of relaxed-memory concurrent programs remains frontier research with weaker, more qualified theorems.
5. **Optimization gap.** Verified compilers implement fewer and gentler optimizations than GCC or LLVM; floating-point reassociation, vectorization, and link-time optimization are largely absent. Translation validation partially addresses this, admitting aggressive unverified oracles behind verified checkers.
6. **Proof maintenance.** Compiler proofs are brittle under language evolution: adding a feature to CompCert C requires updating every downstream IL semantics and simulation. Keeping a verified compiler current with its unverified cousins is the field's central practical challenge.

## 7 Conclusion

Verified compilation has moved, in two decades, from a tantalizing idea to an engineering discipline with multiple complete artifacts. **CompCert** showed that a realistic optimizing C compiler admits a machine-checked semantic-preservation proof, and that its block-offset memory model with injections is the right abstraction for making per-pass simulations tractable [1][2]. **CakeML** showed that the proof can reach all the way to concrete machine code — verified encoder, verified garbage collector, verified bignums, in-logic bootstrap — for a high-level functional language [4][5]. **Proof-carrying code** showed that when the compiler cannot be verified, the *binary* can carry its own evidence, shrinking trust to a checker [6][7]. And the compositional program — SepCompCert, CompCertO, contextual refinement — is extending these theorems from whole programs to the modular, separately compiled, linked software the world actually builds.
