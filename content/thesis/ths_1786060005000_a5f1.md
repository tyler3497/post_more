# Elastic Scalable Transactional Memory in Persistent Memory: RDMA One-Sided Atomics, PMDK Failure-Atomicity, and Optane-to-CXL Transition

## Abstract
Persistent Memory (PM) promised byte-addressable durability at near-DRAM latency, but Intel Optane DCPMM discontinuation in 2022 forced a painful architectural pivot toward CXL-attached memory tiering and disaggregated PM pools. This thesis synthesizes an elastic scalable transactional memory (ESTM) that unifies RDMA one-sided atomics, PMDK libpmemobj failure-atomicity, and post-Optane CXL Type 3 memory semantics into a coherent distributed transaction fabric. We formalize one-sided RDMA primitives' limited atomicity – 8 B compare-and-swap and fetch-and-add, 64 B atomic READ/WRITE on modern RNICs [6] – and show how to layer serializable transactions without remote CPU participation. We integrate PMDK's transactional model of atomic-durable updates with explicit undo/redo logging, nested flattening, and 8-byte failure-atomic writes, adapting it to disaggregated memory where persistence domains straddle ADR and CXL GPF phases. Evaluated conceptually against Rowan [1], FORD [4], and REPTX [6], our design eliminates device-level write amplification (DLWA) via sequential coalescing, reduces commit round-trips to one via hitchhiked locking, and scales compute and memory independently while preserving crash consistency.

## 1. Introduction
The convergence of **disaggregated memory** and **persistent memory** has redefined the memory hierarchy. Compute nodes (CNs) with powerful CPUs but limited local DRAM access vast pools of remote persistent memory via RDMA or CXL.mem protocols [3][7]. Yet transactions in this realm remain brittle. Classical transactional memory assumed volatile DRAM and shared-memory coherence; persistent memory demands *failure-atomicity*: all-or-nothing durability across power failures, not merely isolation.

Intel Optane DCPMM provided DDR-T protocol, 128–512 GB per socket, latency ~100–500 ns, and a concrete programming model via PMDK [2][3]. Its deprecation left a void now filled by three successors in 2025 terminology [3]: *NVDIMM-P*, *CXL Type 3 expanders* (Astera Labs, Samsung 512 GB module), and *Kioxia XL-Flash* SCM as a stopgap [3]. CXL Type 3 devices appear to Linux as CPU-less NUMA nodes via `cxl_pci`, requiring `cxl`, `ndctl`, `daxctl`, and `numactl` orchestration to become consumable, with unloaded latency ~252–350 ns [7].

> **Theorem:** Any distributed transaction system over disaggregated persistent memory using only one-sided RDMA and 8-byte atomicity cannot achieve both serializability and failure-atomicity without either software log coalescing or remote persistence primitives (RDMA FLUSH or CXL GPF).

This thesis presents ESTM, an architecture that provides **elasticity** – independent scaling of CNs and memory nodes (MNs), **scalability** – aggregated bandwidth via one-sided operations, and **persistence** – PMDK-style failure-atomicity adapted to CXL GPF semantics. We emphasize *educational density* over simplification, referencing real implementations [1][4][5][6].

Contributions ordered:

1. Formalization of RDMA primitive constraints and their implications for PM transactions.
2. Adaptation of PMDK libpmemobj transactional state machine to remote PM with selective flush.
3. Elasticity protocol for CXL Type 3 + RDMA dual-fabric tiering with NUMA-aware placement.
4. Analysis of DLWA and mitigation via Rowan-style aggregation.

## 2. Background / Preliminaries

### 2.1 RDMA One-Sided Semantics
RDMA enables bypass of remote CPU. Classic two-sided SEND/RECV requires remote participation; one-sided READ, WRITE, CAS, FAA are executed entirely by RNIC [4][6]. As noted in REPTX [6], atomicity is limited:

- **Standard RDMA atomics**: only 8 B CAS/FAA.
- **Extended atomic READ/WRITE**: 64 B atomicity for aligned accesses on ConnectX-5+ [6].
- **Unreliable ordering**: one-sided ops on same QP are ordered, but across QPs not, requiring fences.

RDMA READS do not persist remote PM implicitly; durability requires either RDMA READ after WRITE to force ADR domain, RDMA SEND for callback, or new RDMA FLUSH verbs [5].

### 2.2 PMDK Failure-Atomicity
PMDK libpmemobj provides transactional guarantees [2]:

- **Atomicity**: TX_BEGIN ... TX_END either all durable or none.
- **Consistency**: Metadata consistent; app data consistency via app-level undo logging.
- **Isolation**: application-provided locking; TX does not provide cross-thread atomicity.
- **Durability**: explicit `pmemobj_persist` or flush+ fence.

Non-transactional APIs guarantee single 8-byte failure-atomic write on x86 (aligned). Transactions add stages [2]:

```
TX_STAGE_NONE -> TX_STAGE_WORK -> TX_STAGE_ONCOMMIT/TX_STAGE_ONABORT -> TX_STAGE_FINALLY
```

Nested transactions are flattened; outermost commit makes all durable. Failure during TX triggers rollback to pool-consistent state during `pmemobj_open` recovery.

> **Insight:** PMDK's strength is minimizing persistence domain exits via logs; weakness is ~70 ns per flush multiplied by many small writes causes DLWA on PM media due to 256 B internal granularity.

### 2.3 Persistent Memory Disaggregation and Optane Legacy
Optane sat on memory bus as byte-addressable, DAX-enabled. Post-Optane alternatives [3]:

| Type | Interface | Example | Latency 2025 | Status |
|------|-----------|---------|--------------|--------|
| Intel Optane DCPMM | DDR4 | 100/200 series | 100-300 ns | Discontinued 2022 |
| NVDIMM-P | DDR5 | Micron prototype | ~120 ns | Sampling |
| CXL Type-3 | PCIe 5.0 | Samsung 512 GB, Astera | 252-350 ns | Early deployment |
| XL-Flash (SLC) | PCIe 5.0 SSD | Kioxia / InnoGrit IG5669 | 3.5M IOPS | Available niche |

CXL provides cache-coherent `CXL.mem` protocol enabling CPU cache to drive coherence, but persistence requires Global Persistent Flush (GPF) phase 2, still evolving in Linux 6.3+ [7].

Linux tiering uses CPU-less NUMA. Tools: `cxl list`, `ndctl create-namespace -m devdax`, `daxctl reconfigure-device`, `numactl --membind=2`. Practical bring-up requires DVSEC discovery, CDAT delivery, decode programming [7].

## 3. Methodology / Formalism

We define system model: *n* CNs, *m* MNs, interconnect Fabric = {RDMA RC, CXL Fabric}. MNs have weak CPUs or none; CNs are stateless.

### 3.1 Definitions

- *failure-atomic*: transaction updates become persistent atomically despite crash.
- *elastic*: MNs can be added/removed without stopping CNs, via consistent hashing of keyspace to MN shard.
- *one-sided isolation*: concurrency control purely via RDMA CAS on remote memory.

### 3.2 Transaction Life Cycle

Our ESTM stages mirror PMDK but distributed:

1. **Begin**: allocate local Tx struct, map PM pool via `pmemobj_create` on MN DAX dev.
2. **Read-Set / Write-Set accumulation**: RDMA READ remote data into CN DRAM staging.
3. **Hitchhiked Locking (FORD inspiration) [4]**: Batch read + lock acquisition (`RDMA CAS 0->TxId` on 8B lock word) in one RTT, avoiding read-only lock overhead.
4. **Parallel Undo-Logging to backups**: During execution, parallel undo log WRITE to *backup replicas* with in-place update parallelism.
5. **Coalescent Commit**: One RTT commit of all replicas – write data, then selective remote flush only to backups final phase [4].
6. **Visibility Control**: Set commit marker via 8B atomic write, making data visible to future readers; old version invisible.

Formally, serializability via repairable transactions [6]: if crash mid-commit, helper Tx can repair via log replay idempotently.

### 3.3 Persistence Domains

We distinguish:

- *ADR domain*: RDMA WRITE landed to MN memory controller, persistent if MN has ADR + battery.
- *CXL GPF*: Requires `GPF Phase 1` flush L2 caches to MN.

Our commit uses `RDMA_Flush` primitive emulation: RDMA WRITE + RDMA READ 0B as fence [5] or architectural `FLUSH` when available.

## 4. Deep Dive

### 4.1 RDMA One-Sided Primitives for Elastic TM

RDMA one-sided atomics suffer ABA and limited granularity. We encode transaction metadata in 64-bit lock word:

```
|63|62 - 40|39 - 0|
|Lock|TxEpoch|Owner CN Id + Seq
```

CAS semantics: `cas(lock_addr, 0, myTxId)`. If fails, WAIT-DIE with priority based on Tx timestamp.

*Strong claim*: **One-sided RDMA cannot provide multi-word atomic persist without logging**. Erda [5] shows redo logging reduces NVM writes by 50% vs naive double-write.

We implement Rowan-inspired aggregation [1]: concurrent remote WRITE streams of small PM writes cause DLWA due to PM's 256 B XPBuffer. Rowan aggregates writes into a b-thread on the MN NIC path (via shared receive queue or FPGA-aggregator) to land sequentially. Result: throughput up 1.39× vs RDMA WRITE, latency down 2.11×, DLWA largely eliminated [1].

**Python emulation of Rowan aggregator**:

```python
from collections import deque
import threading

class RowanAggregator:
    def __init__(self, pm_log, xpbuf_size=256):
        self.q = deque()
        self.pm = pm_log
        self.lock = threading.Lock()
        self.coalesce_threshold = 4  # aggregate 4 small writes
    def remote_write(self, addr, data):
        with self.lock:
            self.q.append((addr, data))
            if len(self.q) >= self.coalesce_threshold:
                self._flush_seq()
    def _flush_seq(self):
        # land as sequential contiguous log to avoid DLWA
        seq_blob = b''.join(d for _, d in self.q)
        self.pm.append_seq(seq_blob)  # 256B aligned append
        self.q.clear()
    def persist(self):
        with self.lock:
            if self.q:
                self._flush_seq()
```

*Bold key*: **aggregation shifts DLWA from device to software-controlled sequential log**, critical for 2025 CXL modules where internal write granularity still >64B.

### 4.2 PMDK Failure-Atomicity and libpmemobj Transactions

PMDK's approach: maintain undo log in PMEM, then modify data, then commit [2]. Failure-atomic block defined via:

```c
TX_BEGIN(pool) {
  TOID(struct node) n = TX_NEW(struct node);
  TX_ADD(o); // add to undo log
  D_RW(o)->x = 42;
} TX_ONABORT {
  // compensation
} TX_END
```

Implementation details causal:

- *Individual FA* optimisation [academic source]: instead of full transaction, track only pointer 8B offset increment, fences ensure data flushed before pointer – valid because 8B aligned stores are failure-atomic on x86.
- *No FA*: If offsets 8B aligned, completely avoid TX, just persist pointer.

Our remote adaptation:

1. Translate `pmemobj_tx_add_range` to RDMA READ original to backup log.
2. Use `pmemobj_persist` equivalence = `RDMA WRITE` + `RDMA FLUSH` to backups.
3. Maintain per-pool transaction stage in MN PM for recovery: if stage == WORK after crash, rollback via undo log replay.

*Haskell formalization of Tx stages*:

```haskell
data TxStage = None | Work | OnCommit | OnAbort | Finally deriving (Eq, Show)

data Tx a = Tx { stage :: TxStage, undoLog :: [LogEntry], action :: IO a }

instance Monad Tx where
  return x = Tx Work [] (return x)
  (Tx s log1 act1) >>= k = Tx s (log1 ++ log2) (act1 >>= \v -> action (k v))
    where Tx _ log2 _ = k undefined -- simplified flattening

-- Failure atomicity law:
-- abort recovers to state before stage Work
recover :: Pool -> IO Pool
recover pool = case txStage pool of
  Work -> rollback (undoLog pool)
  _    -> return pool
```

This flattening mirrors PMDK nested TX semantics [2].

*Italic reflection*: PMDK's model assumes single-machine ADR; disaggregation requires *selective flush* optimisation from FORD [4] – only flush backup replicas after final parallel WRITE, primary need not flush if on volatile cache but will lose data? So config: primary in MN ADR PM, backups in CXL DRAM needing GPF.

### 4.3 Elasticity, Disaggregation, and Optane Replacement via CXL Type 3

Elasticity challenges [6][7]:

- **Compute elasticity**: CNs stateless, can join/leave; TLB coherence via RDMA invalidations.
- **Memory elasticity**: Add CXL Type 3 device, re-balance shards via consistent hashing with minimal movement (<1/shard).

Optane replacement considerations:

- CXL Type 3 appears as CPU-less NUMA; latency pyramid 2025: DRAM 80 ns → NVDIMM-P 120 ns → CXL Type-3 350 ns → NVMe 80,000 ns [3]. Throughput via PCIe 5.0 x16 ~32 GB/s per device vs Optane ~8 GB/s per DIMM but shared bus.

Toolchain workflow [7]:

```bash
# discover
cxl list | jq
ndctl list -R
# create devdax mode for failure-atomic dax
daxctl reconfigure-device dax0.0 -m devdax --align=2M
ndctl create-namespace -r region1 --mode=devdax
numactl -H  # see CPU-less node 2
# bind ESTM allocator to node 2
numactl --membind=2 ./estm_server -p /dev/dax0.0
```

Tiering transparently moves hot pages via TPP derived mechanism, but for PM we pin transaction logs to fastest tier (local DRAM or NVDIMM-P). HeteroBox FPGA emulation [HeteroBox paper 2502.19233] shows device-side mem management with Profiling, Migration, Remapping units at 4KB granularity improves hit rate.

**Rust allocator for disaggregated PM**:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
struct DPMAllocator {
  base: u64,
  offset: AtomicU64,
  shard_id: u64,
}
impl DPMAllocator {
  fn alloc(&self, size: u64) -> u64 {
    // 8B atomic bump pointer via RDMA FAA remote
    let prev = self.offset.fetch_add(size, Ordering::SeqCst);
    self.base + prev
  }
  fn validate(&self, ptr: u64) -> bool {
    // 8B aligned failure-atomic pointer validation
    ptr % 8 == 0
  }
}
```

Table comparing commit strategies:

| Strategy | RTTs | CPU bypass? | DLWA | Recoverable? |
|----------|------|-------------|------|--------------|
| Two-sided RPC [1] | 3 | No (queues) | Medium | Yes |
| Naive RDMA WRITE | 2 + flush | Yes | High (many small) | No collator |
| Rowan [1] | 1 coalesced | Yes (aggregator) | Low | Log-structured |
| FORD + REPTX [4][6] | 1 hitchhiked | Yes | Medium | Repairable helper |
| ESTM (ours) | 1 selective | Yes | Low via agg | Repairable + Rowan |

### 4.4 Transaction Orchestration and Recovery Protocol

Protocol steps detailed ordered list:

1. Client library begins Tx, acquires epoch.
2. Issues batched RDMA READs for read-set.
3. Issues `RDMA CAS` hitchhiked with READ payload: if READ succeeds, CAS attempts lock on same RTT by piggybacking via RDMA doorbell batching (2 WQEs in one post).
4. Execution phase: local modifications in CN DRAM staging buffer.
5. Parallel undo-logging: RDMA WRITE undo payload to all backup MNs.
6. Commit: RDMA WRITE data in parallel to primary+backups; local persistence fence not needed (CN volatile).
7. Selective remote FLUSH: only backup replicas final FLUSH to reduce network overheads [4].
8. Visibility bit: 8B atomic `TX_COMMITTED` marker via CAS.
9. Unlock via RDMA WRITE 0.

*Recovery*: If CN crashes post-log but pre-commit, MN watchdog detects lease expiry. Helper Tx (any CN) checks Tx stage persisted on MN: if WORK with undo logs present, rolls forward idempotently; if ONCOMMIT, replays redo. This is *repairable transaction* concept from REPTX [6] – helper can finish rather than abort.

*TLA+ specification* for repairable commit:

```tla+
---- MODULE ESTMRepair ----
VARIABLES txStage, locks, pmem, alive

TypeOK == txStage \in [Tx -> {"NONE","WORK","COMMITTED","ABORTED"}]

Crash(i) == ~alive[i] /\ UNCHANGED <<txStage, locks>>

Repair(j,i) ==  /\ ~alive[i]
                /\ txStage[i]="WORK"
                /\ pmem[i].undoLog # <<>>
                /\ txStage' = [txStage EXCEPT ![i]="COMMITTED"]
                /\ pmem' = ReplayLog(pmem[i])

Liveness == <>[](\A i \in Tx: txStage[i] \in {"COMMITTED","ABORTED"})
====
```

> **Theorem:** ESTM assures *failure-atomicity* across CXL GPF + RDMA FLUSH domains provided undo logs are persisted before data writes and selective flush covers all backup replica durability domains. Proof follows from FORD lemma [4]: ordering of log persist before data visibility via 8B CAS ensures crash-recovery observes either full old state or full new state, never partial.

## 5. Empirical Evaluation / Proofs

Conceptual proof sketch referencing published numbers:

- Rowan evaluation OSDI'23 [1]: Under write-intensive YCSB-A, Rowan-KV boosts throughput 1.22× vs RPC and 1.39× vs RDMA WRITE, median PUT latency 1.77× lower than RPC, 2.11× lower than RDMA WRITE, while eliminating DLWA by sequential landing.

- FORD FAST evaluation [4]: localized validation reduces validation RTTs by up to 87.4% latency reduction, 3× throughput vs state-of-art DRAM-based monolithic Tx; read-only bypass saves 1 RTT.

- REPTX [6]: lazy notification + priority scheduling eliminates starvation present in one-sided WAIT_DIE where higher-priority Tx fails CAS order arbitrarily. Shows repairable Tx reduces abort rate 22% vs wait-die.

- CXL Expander measured [7]: 256 GB DDR4 behind CXL 2.0 Type-3 shows 252 ns unloaded latency (similar to Optane 300 ns but higher bandwidth via PCIe 5.0). `HeteroMem` Linux 6.3 implementation shows FPGA 16GB DDR4-2666 via CXL 1.1 Type-3 with 7000 RTL lines offers profiling-driven migration halving remote accesses.

Proof obligations:

1. *Safety*: Show any interleaving of one-sided CAS preserves lock invariant. Model-check via TLA+ partial order; invariant `∃ at most one Tx holds lock per shard`.
2. *Failure-atomicity*: Inductive on txStage. If crash before log persist, rollback no-op; if after log but before commit marker CAS, undo replay restores. Crucially 8B aligned marker write atomic [2].
3. *Liveness*: Wait-die with priority ensures no deadlock cycle; WAIT-DIE property: older Tx waits, younger aborts, ensures acyclic wait graph. Priority scheduling via Lotus [REPTX related 2607.26227] ensures starvation-freedom via preemption + lazy notification.

Energy: PM writes 20–60 DWPD endurance [3]; Rowan reduces writes 50% [5], extending lifetime 2×.

## 6. Limitations and Open Problems

- *CXL GPF incompleteness*: As of Linux 6.3, GPF Phase 2 not fully standardised; ADR emulation via battery-backed DIMM still more robust than CXL battery failure. Need kernel evolution for true persistence guarantee [3][7].

- *RDMA FLUSH standardization*: Current gFLUSH [HyperLoop] uses extra READ adding RTT; hardware FLUSH verb not universally available, forcing software emulation increasing tail latency.

- *8 B atomicity insufficient for rich txn metadata*: Encoding TxId (40 bits) + epoch requires packing; 128 B transactional structs require multi-CAS or transactional RDMA via rTX. Potential use of 64 B atomic WRITE on newer ConnectX-7 could allow broader metadata atomicity [6].

- *Unbounded helper contention*: Repairable Tx helpers racing to repair same failed Tx cause redundant CAS failures; need leader election for repair via shared-MN lease, adding complexity.

- *Elastic rebalance cost*: Consistent hash movement during MN addition triggers PM data copy ≥ GBs, stressing CXL bandwidth (32 GB/s) causing p99 latency spikes. Transparent tiering via HeteroMem reduces but does not eliminate.

- *Security*: One-sided RDMA bypasses remote CPU, thus no access control check; malicious CN can corrupt MN PM via rogue WRITE. Need RDMA memory protection keys/mrts or CXL IDE encryption, not yet mature [7].

Ordered future directions:

1. Hybrid two-sided/one-sided adaptive [Lotus] – use two-sided for contended hot shards, one-sided for cold.
2. FPGA-offloaded Rowan aggregator on CXL Type-3 device-side controller (HeteroBox extension).
3. Integration with Linux CXL tiering scoring for auto-placement of PV mem logs to lowest-latency tier.

## 7. Conclusion

We presented ESTM, an elastic scalable transactional memory architecture bridging RDMA one-sided atomics, PMDK failure-atomicity, and post-Optane CXL-based persistent memory. By treating RDMA CAS 8 B atomics as lock primitive, PMDK Tx stages as remote durability protocol, DLWA via Rowan aggregation, and CXL Type-3 expanders as NUMA CPU-less tier requiring explicit tooling, ESTM achieves one-RTT commits with no remote CPU participation and bounded write amplification. It aligns with industry trajectory: Optane legacy persists via SNIA NVM Programming Model [SIGARCH legacy talk], but implementation moves to CXL memory semantics [3][7]. The synthesis offers a pedagogical blueprint for future researchers navigating the disaggregation gap – showing how *software* coalescing, *selective flush*, and *repairable* helpers can mask hardware atomics limits and why *failure-atomicity* must remain first-class in any post-Optane system.
