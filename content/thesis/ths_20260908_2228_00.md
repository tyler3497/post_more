# Zero-Knowledge Virtual Machines: Proving General-Purpose Computation via RISC-V Constraint Systems, Continuations, and STARK Recursion

## Abstract

Zero-knowledge virtual machines (zkVMs) have displaced hand-crafted arithmetic circuits as the dominant frontend for succinct verifiable computation: a program compiled to an instruction set architecture (ISA) — most commonly RISC-V — is executed by a prover, and the execution is attested by a succinct non-interactive argument of knowledge. This thesis develops the design theory of modern zkVMs end to end. We formalize the arithmetization pipeline that converts RISC-V execution traces into algebraic intermediate representation (AIR) constraints over small-characteristic prime fields, analyze the FRI-based STARK proof system that attests trace correctness without trusted setup, and prove how *continuations* — segmenting long executions and recursing over segment proofs — yield amortized constant verification cost. We compare three engineering generations: RISC Zero with its recursion and STARK-to-SNARK composition, SP1 with its precompile-centric Plonky3 backend, and Valida's ISA co-designed for proving efficiency. Finally we contrast the AIR paradigm with the lookup-singularity approach of Jolt/Lasso [2,3], quantify empirical prover bottlenecks from recent head-to-head benchmarks [7,9], and enumerate the open problems — memory proving, proving economics, and formal ISA-verification gaps — that bound current practice.

## 1 Introduction

The classical formulation of succinct zero-knowledge arguments assumes a *circuit*: the witness-checking procedure is flattened into a fixed acyclic network of gates, and the prover attests that the network is satisfiable. This formulation is expressive but ergonomically catastrophic. Real software is loops, recursion, dynamic dispatch, and heap allocation; expressing a modern program as a monolithic circuit forces the developer to become a cryptographer, and the audit surface of hand-rolled circuits is notorious for soundness bugs.

A zero-knowledge virtual machine inverts the relationship. The statement to be proved is *the program*: the developer writes ordinary code — Rust, C++, or any language with an LLVM frontend — compiles it to a target ISA, and the zkVM proves correct execution of the resulting machine code. The verifier learns nothing beyond the declared public outputs and the fact that execution was faithful. The frontend/backend separation is now canonical: the *frontend* reduces execution to a set of algebraic constraints, and the *backend* — a polynomial interactive oracle proof (PIOP) combined with a polynomial commitment scheme (PCS) — compiles those constraints into a succinct argument [1,2].

This thesis is a systematic treatment of that pipeline. We answer three questions: (i) how is a general-purpose ISA arithmetized into constraints that are *cheap* to prove, (ii) how do long executions scale beyond the memory and time limits of a single prover, and (iii) where do the remaining costs concentrate, and which architectural choices — precompiles, field selection, lookup arguments — attack them. Our analysis is grounded in deployed systems: RISC Zero's RISC-V zkVM [8], Succinct's SP1 [7], and the Delendum/Lita Valida design [5], together with the Jolt/Lasso lookup-singularity line of work [2,3,4] and the first independent multi-zkVM benchmarking studies [9].

## 2 Background

### 2.1 From circuits to execution traces

A zkVM replaces the circuit's gate network with an *execution trace*: a matrix $T \in \mathbb{F}^{N \times w}$ whose rows are successive machine states (program counter, registers, memory ports, instruction fields) and whose columns are *registers* of the arithmetization. Correct execution is expressed as a set of *transition constraints* $C_j$ such that $C_j(T_t, T_{t+1}) = 0$ for every row $t$, plus boundary constraints on the first and last rows. This is the Algebraic Intermediate Representation (AIR): a uniform constraint system in which the same transition polynomial applies to every row, so the constraint degree stays small while $N$ grows with program length [1].

> **Theorem (AIR soundness reduction).** Let $T$ be an $N \times w$ execution trace and $\{C_j\}_{j=1}^{m}$ transition polynomials of degree at most $d$. If all $C_j$ vanish on consecutive rows and boundary constraints hold on $T_0, T_{N-1}$, then $T$ is a faithful execution of the specified machine, provided each machine transition is uniquely determined by the constraint set. The STARK protocol then reduces the claim "$T$ satisfies all constraints" to a low-degree test on a composed polynomial, with soundness error bounded by the FRI proximity gap [1].

Concretely, the prover interpolates each column into a polynomial over a domain $D$ of size $N$, forms the *composition polynomial* $Q(x) = \sum_j \alpha_j C_j(\cdot) / Z_H(x)$ where $Z_H$ is the vanishing polynomial of $D$, and commits to $Q$ using a Merkle tree over a Reed–Solomon codeword with blowup factor $\beta$ (typically 2–4). The FRI protocol [1] then proves that $Q$ has degree below the required bound; a handful of queries yields $\approx 100$–128 bits of conjectured security, with grinding adding further bits [6].

### 2.2 Small fields and the cost model

Proving cost is dominated by finite-field arithmetic on trace columns and by hashing inside the PCS. Early systems used the 64-bit Goldilocks field; the modern generation uses 31-bit fields — Baby Bear ($p = 2^{31} - 2^{27} + 1$) in RISC Zero's stack [8], Mersenne31 ($p = 2^{31} - 1$) in Valida's design [5] — because 31-bit limbs fit in native 64-bit multiplies without overflow, vectorize cleanly under AVX2/AVX-512/NEON, and still provide a large smooth multiplicative subgroup for FFTs. The Plonky3 toolkit [6] exposes exactly this menu (BabyBear, Mersenne31, Goldilocks), FRI-based and Brakedown-based commitment schemes, and Poseidon2/BLAKE3/Keccak hashing, and both SP1 and Valida build on it.

### 2.3 SNARKs, STARKs, and recursion

A STARK [1] is transparent (no trusted setup) and plausibly post-quantum, but its proofs are large — tens to hundreds of kilobytes — because FRI opening proofs carry Merkle paths per query. A *recursion* step proves, inside the arithmetization itself, the verification of one or more STARK proofs, compressing many segment proofs into one; repeating this yields a single constant-size proof for an arbitrarily long execution. Finally, a *wrapping* step embeds the recursion verifier in a pairing-based SNARK such as Groth16, producing a $\approx 200$-byte proof verifiable on-chain for roughly 275k EVM gas [7]. RISC Zero open-sourced exactly these three primitives — high-speed recursion, proof composition, and a STARK-to-SNARK wrapper — under Apache-2.0 in 2023 [8].

## 3 Methodology

Our method is comparative-architectural: we fix a common evaluation frame and instantiate it across the major zkVM designs, validating each claim against primary sources (protocol specifications, peer-reviewed papers, and reproducible benchmarks).

**Frame.** A zkVM design is decomposed along five axes:

1. *ISA choice*: RISC-V (RISC Zero, SP1, Jolt) versus a proving-native ISA (Valida), and the resulting cycle-count inflation for cryptographic workloads.
2. *Arithmetization*: AIR transition constraints over small fields versus lookup-centric (Jolt) representations.
3. *Memory model*: how reads/writes are proved consistent — offline memory checking via permutation/multiset arguments, or Merkleized memory — and its share of trace width.
4. *Scaling*: continuations (segmented proving) and recursion topology for long executions.
5. *Acceleration*: precompiles — dedicated constraint "chips" for SHA-256, Keccak, secp256k1, ed25519 — versus naive instruction-by-instruction execution.

**Evidence.** Performance claims are taken from (a) Succinct's reproducible SP1 vs. RISC Zero and SP1 vs. Jolt benchmark suites (Tendermint light client, Merkle SSZ withdrawal proofs, and Reth executing real Ethereum blocks) [7]; (b) the first peer-reviewed head-to-head study of six zkVMs presented at zkProof 2025, measuring CPU/memory bottlenecks and continuation parallelization [9]; and (c) the Zeth Type-0 zkEVM report, the first production-scale demonstration of continuation-based proving on RISC Zero [8]. Theoretical claims rest on the STARK [1], Jolt [2], and Lasso [3] papers and the a16z crypto engineering write-ups [4].

## 4 Deep Dive

### 4.1 ISA design: why RISC-V won, and what it costs

Choosing RISC-V as the proving ISA is an *ecosystem* decision, not a cryptographic one. The RISC-V toolchain — `rustc`/`clang` targets, `cargo prove`, standard libraries — lets developers compile unmodified programs, including full Ethereum clients (Reth) and light clients (Tendermint), and prove their execution [7,8]. The cost is arithmetization inefficiency: a RISC-V ISA was designed for silicon, not for field arithmetic. A single SHA-256 compression executed instruction-by-instruction costs tens of thousands of cycles; an ECDSA verification, millions. Cycle count is the fundamental cost driver, because the trace has one row per cycle and proving work scales (at least) linearly in trace length.

Valida [5] takes the opposite bet: a RISC-inspired but proving-native ISA with no general-purpose registers (the machine operates directly on memory), constraints of degree at most 3, minimal instruction decoding, and an extensible instruction set in which cryptographic accelerators are first-class instructions rather than bolted-on precompiles. Its authors argue that co-designing the ISA for the constraint system beats retrofitting RISC-V — at the price of abandoning the mature RISC-V toolchain (their LLVM-IR-to-Valida backend was still under development, and the repository has since moved to Lita's stewardship). The tradeoff is therefore *toolchain maturity vs. constraint efficiency*, and every production zkVM today sits somewhere on this spectrum: SP1 keeps RISC-V but surrounds it with precompiles; RISC Zero keeps RISC-V and relies on recursion economics.

```rust
// SP1-style guest program: ordinary Rust, compiled to RISC-V, proven by the zkVM [7]
use sp1_sdk::{ProverClient, SP1Stdin};

fn main() {
    let client = ProverClient::from_env();
    let mut stdin = SP1Stdin::new();
    stdin.write(&block_header);          // public input: Ethereum block
    let (pk, vk) = client.setup(ELF);    // one-time setup for the program
    let proof = client.prove(&pk, &stdin).run().expect("proving failed");
    client.verify(&proof, &vk).expect("verification failed");
}
```

### 4.2 STARK constraint systems over small fields

In the AIR paradigm, each RISC-V instruction family becomes a set of transition constraints. A representative 32-bit ADD in a Baby Bear AIR looks schematically like:

```python
# Schematic AIR transition constraint for ADD rd, rs1, rs2 (Baby Bear field)
def transition_add(row, nxt, F):
    # decode: opcode selects the ADD chiplet
    is_add = row["opcode"] - OPCODE_ADD
    # register file consistency is enforced by a separate memory argument
    a = row["rs1_val"]; b = row["rs2_val"]; c = nxt["rd_val"]
    # 32-bit addition with carry, constrained limb-wise over a 31-bit field
    carry = row["carry"]
    return [
        is_add * (a + b - c - carry * 2**32),   # arithmetic correctness
        is_add * carry * (carry - 1),            # carry is boolean
        is_add * (nxt["pc"] - row["pc"] - 4),    # pc advances by 4
    ]
```

Because the field is only 31 bits, 32-bit values are handled limb-wise (e.g., two 16-bit limbs), and range checks — ubiquitous in decoding, memory addressing, and carry handling — are proved with *lookup arguments* such as LogUp, the log-derivative construction SP1 uses to avoid Merkleized-memory overhead [7]. The composition polynomial is committed with a blowup factor of 2 in SP1 (versus 4 in some RISC Zero configurations), halving the Reed–Solomon domain and the hashing work that dominates FRI [7]. This is where Plonky3 [6] matters as infrastructure: its FRI variant commits to tables of *different sizes*, improving trace-area utilization, and its field/hash menu lets each zkVM tune the field-to-hashing cost ratio.

> **Theorem (Preprocessing-free soundness).** A STARK over a 31-bit field with FRI soundness parameters $(\rho, s, \zeta)$ — code rate $\rho$, $s$ queries, $\zeta$ grinding bits — achieves $\lambda \geq \min(\zeta + s\log_2 \rho^{-1},\, \cdot)$ bits of conjectured security, where the second term is the field-size bound; with $s = 28$ queries, $\rho^{-1} = 4$, and $\zeta = 16$ the standard configuration targets $\approx 100$ bits [6].

### 4.3 Continuations and STARK recursion

A single STARK proof over a billion-cycle trace is infeasible: the prover's memory grows with the trace, and latency grows superlinearly. *Continuations* solve this by executing the program once in a fast native emulator, snapshotting machine state at configurable intervals, and proving each segment independently — typically capped near $2^{20}$–$2^{21}$ cycles per shard. Segments are assigned to a pool of workers and proved in parallel; a recursion layer then proves the verification of pairs of segment proofs, and the recursion tree collapses to one constant-size proof [8]. The Zeth Type-0 zkEVM demonstrated this at production scale: each shard stays small (a few seconds of proving), and with enough workers the wall-clock time for the whole execution approaches the time for a single shard [8].

Recursion depth is logarithmic in the number of segments, and each recursion node re-runs the STARK verifier *inside* the constraint system — which is why the verifier's arithmetization must itself be proving-friendly, and why the recursion field is usually the same small field as the base layer. The empirical study [9] measured continuation scaling directly: on 8 cores, SP1 showed the highest parallel speedup among the tested zkVMs, and logarithmic extrapolation predicts saturation near $\approx 10.6\times$ for SP1 and $\approx 9.9\times$ for Ceno at 40 cores — continuations scale well but sublinearly, bounded by aggregation and commitment-generation overhead.

| Stage | Input | Output | Asymptotic cost |
|---|---|---|---|
| Execution + trace gen | RISC-V ELF, public input | Trace $T \in \mathbb{F}^{N \times w}$ | $O(N)$ |
| Sharding (continuations) | Trace of $N$ cycles | $k$ shards of $\le 2^{21}$ cycles | $O(N)$ |
| Core proving (parallel) | $k$ shards | $k$ STARK proofs | $O(N \log N)$ total, $O(N/k)$ wall-clock |
| Recursion | $k$ segment proofs | 1 aggregated proof | $O(k \log k)$ |
| SNARK wrap (Groth16) | Aggregated STARK proof | $\approx 200$-byte proof | Constant; $\approx 275$k EVM gas [7] |

### 4.4 Precompile-accelerated proving

Precompiles are the single largest performance lever in deployed zkVMs. Instead of executing SHA-256 or secp256k1 as thousands of RISC-V instructions, the VM traps to a dedicated AIR *chiplet* whose constraints natively express the primitive — e.g., a Keccak-$f$ permutation chiplet with one row per round. SP1's precompile-centric architecture reports 5–10$\times$ cycle-count reductions on blockchain workloads [7], and the effect is visible in the benchmarks: on the Tendermint light client and Reth programs, SP1's cycle counts are dramatically lower than RISC Zero's precisely because of first-class precompile support [7]. The Jolt line makes the same point from the other direction: its subtables *are* the precomputations, and structured tables of size $2^{128}$ cost no more than the subtables actually touched [2].

Designing a precompile is a constraint-engineering problem. The chiplet must (i) express the primitive in low-degree AIR, (ii) interface with the main trace through bus/memory arguments so that inputs and outputs are consistent, and (iii) be cheap enough in the recursion layer, since the verifier will re-verify chiplet-heavy proofs. The payoff compounds: fewer cycles means fewer shards, less recursion, and lower aggregation cost.

```haskell
-- Schematic: precompile dispatch as an AIR bus constraint
-- main trace posts (opcode, inputs) on the bus; the chiplet consumes them
dispatch :: Trace -> Chiplet -> Constraint
dispatch trace chiplet =
  busLookup (opcodeOf trace) (inputsOf trace)   -- main -> bus
  <> busLookup (opcodeOf chiplet) (outputsOf chiplet)  -- bus -> chiplet
  <> boundary (pcNext trace == pcOf trace + trapCost)
```

### 4.5 The lookup-singularity alternative: Jolt and Lasso

Jolt [2] rejects the AIR-per-instruction paradigm. Every RISC-V instruction is expressed as *lookups* into a small set of structured tables; the tables are indexed by chunked operands (e.g., 8-bit limbs of 32-bit words), and the full $2^{128}$-entry virtual table is never materialized — Lasso [3] commits only to the subtables actually accessed plus per-entry access counts, all of them *small* field elements, which makes the polynomial commitments (MSM-based, e.g., Hyrax/KZG) dramatically cheaper than committing to random field elements [4]. For 64-bit RISC-V datatypes, the dominant prover cost is committing to roughly six 256-bit field elements per CPU step, with no FFTs anywhere in the pipeline [2].

The tradeoff is subtle. Jolt's prover is arithmetically lean but its per-step constant is paid on *every* step, and its memory-checking still requires an offline argument. In head-to-head benchmarks [7], SP1 outperformed Jolt on proving time (1.66–3.23$\times$) and proof size (1.29–3.60$\times$ smaller) at comparable cycle counts — the AIR+precompile approach currently wins on real workloads, though Jolt's auditability (constraints are *just lookups*) and its avoidance of hash-heavy FRI remain attractive. An independent ACL2 formalization has now machine-checked Jolt's RV32I semantics against its Rust implementation, finding and fixing real inefficiencies (removing redundant lookups, shrinking three subtables by 87.5%) — a sign that ISA-level formal verification is becoming a practical engineering tool.

## 5 Empirical Evaluation / Formal Results

**Benchmark design.** The most careful public comparisons fix hardware (AWS `r7i.16xlarge`, 64 vCPUs), enable precompiles on both sides, and measure end-to-end proving: witness generation plus core proving plus recursion to constant size, excluding one-time setup [7]. Workloads are real programs — Merkle SSZ withdrawal proofs, a Tendermint light client, and Reth executing Ethereum blocks — rather than synthetic loops.

**Headline results.**

1. *SP1 vs. RISC Zero (v1.1.1 vs. v1.0.0):* SP1 is faster end-to-end on all three workloads, with the gap largest where precompiles apply; both use constant-size proofs via recursion, but SP1's Groth16 wrapper adds a $\approx 50$-second "shrinking" stage absent from RISC Zero's pipeline [7].
2. *SP1 vs. Jolt:* at matched proof size and cycle count, SP1 proves 1.66$\times$ (SHA-256 chain), 3.23$\times$ (Fibonacci), and 1.93$\times$ (loop) faster, with proofs 1.29–3.60$\times$ smaller [7].
3. *Six-way study [9]:* across SP1, RISC Zero, Jolt, Nexus, and Ceno, the dominant CPU bottlenecks are proof aggregation and commitment generation (SP1, RISC Zero), Lasso's sumcheck (Jolt), and folding (Nexus); the dominant memory bottleneck is Merkle tree construction. No zkVM scales linearly with cores; continuations help all of them, most for SP1.
4. *Real-time Ethereum proving:* Succinct's Hypercube backend (multilinear, GPU-oriented) reports proving $\approx 93\%$ of Ethereum blocks in under 12 s (average $\approx 10.3$ s) — the threshold for L1-slot proving, though these vendor-demonstration figures await independent replication.

**Formal results.** Beyond benchmarks, two proof-theoretic facts anchor the field. First, the STARK IOP+FRI composition gives transparent, plausibly post-quantum succinct arguments with prover time $O(N \log N)$ and verifier time polylogarithmic in $N$ [1]. Second, the Jolt/Lasso analysis shows that for *decomposable* tables the prover commits to only $O(cm + cN^{1/c})$ field elements for $m$ lookups into a size-$N$ table — sublinear in the table size — which is what makes the "lookup singularity" (circuits that only perform lookups) asymptotically viable [2,3].

## 6 Limitations and Open Problems

1. **Memory proving remains the tax.** Whether via offline memory checking (Jolt), multiset/bus arguments (SP1's LogUp design), or Merkleized memory, proving RAM consistency is a large fraction of trace width and prover time. Merkle tree construction is the top memory bottleneck in the six-way study [9].
2. **Proving economics are opaque.** Wall-clock time and dollar cost diverge: continuations trade latency for worker parallelism, and recursion adds fixed overhead per shard. The Zeth team reported $\approx \$10$ of compute per Ethereum block in 2023 [8]; current per-block costs are lower but rarely published with reproducible methodology. The field needs a standard cost model (dollars per million cycles, at stated security parameters).
3. **Precompile governance.** Precompiles are consensus-critical: a bug in a SHA-256 chiplet breaks soundness for every program that uses it. There is no established process for standardizing, auditing, or versioning precompiles across zkVMs.
4. **Formal verification gaps.** The ACL2 verification of Jolt's RV32I semantics is a landmark, but it covers one ISA in one zkVM; RISC-V privileged modes, the memory subsystem, and the recursion verifiers themselves remain largely unverified. A soundness bug in a recursion verifier collapses the entire aggregation tower.
5. **The field-security frontier.** 31-bit fields rely on extension fields ($\approx 128$-bit) for security; the concrete FRI soundness analysis over small fields with grinding is still being tightened [6], and any future break in the conjectured FRI soundness would affect every STARK-based zkVM simultaneously — a monoculture risk.
6. **Lookup vs. AIR convergence.** Jolt's lookup-only circuits and SP1's AIR+precompile circuits are converging in practice (both now use lookup arguments internally), but no unified theory tells us which representation minimizes prover work for a given ISA. The "lookup singularity" remains a vision, not a theorem, for general computation.

---

## 7 Conclusion

The zero-knowledge virtual machine has matured from a research curiosity into infrastructure: compile ordinary code to RISC-V, execute, shard via continuations, prove each shard with a FRI-based STARK over a 31-bit field, recurse to constant size, and wrap in Groth16 for on-chain verification. Each layer of this stack exists because the layer below it was too expensive — AIR replaced monolithic circuits, continuations replaced monolithic traces, recursion replaced linear-size proofs, and precompiles replaced instruction-by-instruction cryptography. The empirical record [7,9] shows the strategy working: order-of-magnitude speedups from precompiles, near-real-time block proving on the horizon, and a healthy competition between the AIR paradigm (RISC Zero, SP1, Valida) and the lookup paradigm (Jolt/Lasso). The remaining problems — memory proving, cost transparency, precompile governance, and end-to-end formal verification — are now engineering and economic rather than purely cryptographic, which is itself the strongest signal that zkVMs have arrived.
