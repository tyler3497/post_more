# Formalizing the eBPF Verifier: Abstract Interpretation, Sound Abstract Operators, and Mechanized Safety Proofs

## Abstract

The Linux kernel's eBPF verifier is one of the most consequential static analyzers ever deployed: it gates the execution of untrusted, user-supplied programs inside kernel address space, and a single soundness bug can yield privilege escalation. This thesis develops a formal account of the verifier as an abstract interpreter over the eBPF instruction set architecture. We present the concrete operational semantics of the eBPF ISA, the verifier's two-phase architecture (control-flow validation followed by path-sensitive symbolic simulation), and its numerical abstract domains — intervals and tristate numbers (*tnums*) — with an emphasis on the recently mechanized soundness and optimality proofs for tnum operators [1,2]. We examine how the verifier establishes termination through bounded-loop analysis and state pruning, how it hardens against transient-execution (Spectre) attacks by verifying speculative paths, and how independent verification efforts — PREVAIL [4], Jitterbug [5], CertrBPF, and bit-precise CHC-based checkers [7] — complement or challenge the in-tree implementation. We close with open problems: full mechanization of the production verifier, compositional reasoning about helper functions, and principled co-design of the JIT and the abstract domains it must preserve.

## 1 Introduction

Extended Berkeley Packet Filter (eBPF) allows unprivileged users to load small programs into the Linux kernel, where they run at events such as packet arrival, system calls, or tracepoints. The security argument for this extraordinary privilege is the **verifier**: a static analyzer in `kernel/bpf/verifier.c` that must reject every program that could read or write arbitrary kernel memory, leak data, or fail to terminate [8]. Unlike most program analyzers, the verifier is a *gatekeeper* — its verdict is the only thing standing between hostile bytecode and ring 0.

The verifier is large (on the order of ten thousand lines), subtle, and historically buggy: soundness issues have repeatedly been found in its range analysis, pointer arithmetic, and Spectre mitigations, several carrying CVE identifiers [8]. This has motivated a sustained formal-methods campaign to understand, specify, and verify it. The central insight of this thesis is that the verifier is best understood not as an ad-hoc checker but as an **abstract interpreter**: it computes, for every program point, an over-approximation of the set of reachable concrete machine states, and accepts the program only if every approximated state is safe.

We make three contributions. First, we give a precise, self-contained description of the verifier's concrete semantics, abstract domains, and transfer functions, grounded in the mechanized results of Vishwanathan *et al.* [1,2,3]. Second, we analyze termination and speculation-safety as abstract-interpretation problems, showing how bounded loops, state pruning, and speculative-path exploration fit the same theoretical frame. Third, we survey the ecosystem of alternative and complementary verifiers — PREVAIL's zone-based analysis [4], Jitterbug's symbolic JIT verification [5], CertrBPF's end-to-end Coq proof, and CHC-based bit-precise checking [7] — and distill the open problems that remain.

## 2 Background

### 2.1 The eBPF machine model

An eBPF program is a sequence of fixed-width 64-bit instructions operating on eleven 64-bit registers (`R0`–`R9` plus the read-only frame pointer `R10`) and a 512-byte stack. Each instruction encodes an opcode class (ALU, jump, load/store, call), source and destination registers, a 16-bit offset, and a 32-bit immediate. Programs may call a restricted set of **helper functions** (e.g., map lookups) and may tail-call into other eBPF programs, but they cannot perform arbitrary indirect jumps: every jump target is a static offset, which makes the control-flow graph (CFG) fully recoverable — a prerequisite for static analysis.

> **Theorem (CFG recoverability):** Because eBPF jump targets are immediate offsets and indirect jumps are prohibited, the complete control-flow graph of an eBPF program is computable by a single linear scan. The verifier exploits this in its first phase.

### 2.2 The two-phase verifier

Verification proceeds in two phases. **Phase one** builds the CFG and checks structural properties: the program must be a directed acyclic graph modulo explicitly bounded loops (admitted since Linux 5.3), must contain no unreachable instructions, must end in an `exit`, and must respect the instruction limit (raised from 4,096 to one million in Linux 5.2). **Phase two** is the heart of the analyzer: a path-sensitive abstract simulation that walks every feasible path, maintaining an abstract state of registers and stack slots, and rejects the program on any unsafe operation — an out-of-bounds access, a read of an uninitialized register, an illegal helper call, or an unbounded loop [8].

The abstract state tracks, per register and stack slot, a *type* (`NOT_INIT`, `SCALAR_VALUE`, `PTR_TO_CTX`, `PTR_TO_MAP_VALUE`, `PTR_TO_STACK`, …), and for scalars and pointer offsets, numerical abstractions: an **interval** `[min, max]` and a **tristate number** (*tnum*).

## 3 Methodology

Our methodology is the classical abstract-interpretation recipe of Cousot and Cousot, instantiated for the eBPF ISA:

1. **Concrete semantics.** Define the collecting semantics of eBPF as sets of concrete machine states (register files, memory, program counter) and per-instruction transfer functions on these sets.
2. **Abstraction.** Define the verifier's abstract domains — the type lattice, the interval domain, and the tnum domain — with Galois connections to the concrete powerset domain.
3. **Soundness.** Prove that each abstract transfer function over-approximates its concrete counterpart: $\alpha \circ F \sqsubseteq F^\sharp \circ \alpha$. Soundness of the operators is the load-bearing property; Vishwanathan *et al.* mechanized it for the full tnum operator suite [1] and the interval domain [2], in the process discovering latent unsoundness in the shipped kernel code [3].
4. **Termination of analysis.** Show that the abstract fixpoint computation terminates via widening (interval bounds), finite-height domains (tnums), loop bounding, and *state pruning*: when the verifier revisits a program point with an abstract state already subsumed by a previously explored state, the path is discarded [8].
5. **Empirical validation.** Cross-check the formal model against the kernel implementation using differential testing and symbolic execution (Serval [6], Jitterbug [5]).

This frame lets us treat the verifier's disparate checks — range analysis, alignment, Spectre mitigations — as instances of one theory rather than a bag of tricks.

## 4 Deep Dive

### 4.1 Concrete semantics of the eBPF ISA

We model a concrete state as $\sigma = \langle pc, R, M \rangle$ where $pc$ is the program counter, $R : \mathit{Reg} \to \mathbb{B}^{64}$ the register file, and $M$ the memory (stack, maps, packet buffers, context). The semantics of representative instructions:

```c
// STX_MEM: *(u64 *)(dst + off) = src
M' = M[(R[dst] + off) <- R[src]]   // defined only if R[dst]+off is a writable address
// JEQ: if (dst == imm) pc += off
pc' = (R[dst] == imm) ? pc + off : pc + 1
```

Memory safety is a property of *executions*: no execution may access an address outside the regions the program is entitled to. The verifier's job is to decide a sound approximation of this property statically.

### 4.2 Numerical abstract domains: intervals and tristate numbers

The verifier tracks scalar values with two complementary abstractions. **Intervals** $[lo, hi]$ bound each register between a minimum and maximum; they are cheap and suffice for most bounds checks. **Tristate numbers** are more unusual: a tnum is a pair $(v, m)$ of 64-bit words where each bit position is known-0, known-1, or *unknown* (mask bit set). The concretization is the set of values agreeing with all known bits:

$$\gamma(v, m) = \{\, x \mid (x \,\&\, \sim m) = v \,\}$$

Tnums shine where intervals are weak: bitwise operations and alignment. If a pointer's tnum ends in known-zero bits, the verifier can prove alignment; if a mask is shifted, tnums track the result precisely where an interval would degrade to $[0, 2^{64})$. The two domains are used *together*: an operation updates both, and each check consults whichever is more precise [1].

```python
def tnum_add(a: tuple[int,int], b: tuple[int,int]) -> tuple[int,int]:
    """Abstract addition on tnums. Soundness requires:
    for all x in gamma(a), y in gamma(b): x+y in gamma(tnum_add(a,b))."""
    v1, m1 = a; v2, m2 = b
    sm = m1 + m2          # over-approximate unknown-bit propagation
    sv = v1 + v2
    sigma = sm + (sv & sm) # carry into unknown positions
    gamma = (sm | m1 | m2) ^ (sigma & ~sm)
    return (sv & ~gamma, gamma)
```

The subtlety — and the source of real kernel bugs — is that operators like the one above must be *sound* for all $2^{64}$ inputs, a property no test suite can establish by enumeration. Vishwanathan *et al.* proved soundness **and optimality** (no precision is needlessly lost) for the complete tnum operator suite, mechanized in a proof assistant [1]. Their work also uncovered operators in the shipped verifier that were *unsound* — the abstract result failed to cover some concrete behaviors — and these were fixed upstream [3]. This is formal methods paying rent: the proofs found bugs that testing missed.

### 4.3 Soundness and optimality of abstract operators

Soundness composes: if every abstract transfer function over-approximates its concrete counterpart, then the abstract states computed at each program point over-approximate all concrete states reachable there, and a verifier that rejects every abstractly-unsafe program is *sound* (it never accepts an unsafe program). Optimality — the abstract operator returning the *most precise* sound result — matters for a different reason: an imprecise operator rejects safe programs, and in the eBPF ecosystem, false positives are a daily tax on developers.

The CAV 2023 work of the same group extended mechanization to the verifier's **range (interval) analysis** [2], proving the interval transfer functions sound with respect to a formalized concrete semantics. Together, [1] and [2] cover the numerical core on which every memory-safety check rests. The remaining gap is the *type* domain and pointer-arithmetic rules — larger, more entangled with kernel internals, and the natural next target.

| Domain | Concretization | Height | Mechanized? |
|---|---|---|---|
| Intervals $[lo,hi]$ | $\{x \mid lo \le x \le hi\}$ | Infinite (widened) | Yes [2] |
| Tnums $(v,m)$ | $\{x \mid (x\,\&\,\sim m) = v\}$ | Finite ($3^{64}$) | Yes [1] |
| Type lattice | Sets of tagged values | Finite | No — open |
| Zone/octagon (PREVAIL) | Relational constraints | Infinite (widened) | Partial [4] |

### 4.4 Termination: bounded loops and state pruning

Abstract interpretation over a CFG with cycles requires a termination argument for the *analysis itself*. The verifier combines three mechanisms:

- **Bounded loops.** Since Linux 5.3, the verifier admits loops whose trip count it can bound statically; it unrolls or iterates the abstract state until a fixpoint or the bound is reached, rejecting programs whose loops it cannot bound.
- **State pruning.** The verifier memoizes visited states per program point. If the current abstract state is *subsumed by* (less precise than or equal to) an already-explored state at the same point, exploration of the current path stops: everything reachable from here was already covered. This is exactly the classic abstract-interpretation technique of exploring the abstract reachability tree with subsumption, and it is what lets the verifier scale to the one-million-instruction limit [8].
- **Precision management.** When precision is lost (e.g., a loop merges too aggressively), the verifier may *reject* rather than analyze forever — soundness is never sacrificed for completeness.

PREVAIL [4] takes the complementary approach: by merging paths with a zone abstract domain rather than exploring them, it accepts a strictly larger class of programs (including variable-sized loops) at the cost of a more complex domain. The trade-off between the Linux verifier's path-sensitive precision and PREVAIL's merge-based scalability remains the central design tension in eBPF verification.

### 4.5 Spectre mitigations and speculative path verification

Transient-execution attacks (Spectre) broke the verifier's threat model: a program that is safe on all *architectural* paths may still leak via *speculative* paths — the CPU can transiently execute a mispredicted branch and access out-of-bounds memory before the misspeculation is squashed. The kernel's response was to extend the abstract interpretation to **speculative semantics**: at each conditional branch, the verifier pushes the *mispredicted* successor state onto its exploration stack and verifies it too, with speculative-only mitigations (such as masking pointer arithmetic or forcing branches) applied along those paths.

> **Theorem (Speculative soundness, informal):** If the verifier accepts a program, then no speculative path reachable under the processor's branch predictor can perform an unsafe memory access that is not neutralized by an inserted mitigation.

This elegant idea — verify the speculative semantics with the same abstract interpreter, just seeded with more start states — has itself been a source of CVEs when the modeling of speculation was incomplete [8]. The Linux Foundation's verifier security audit [8] treats speculative-path verification as one of the highest-risk areas, precisely because the hardware behavior being modeled is under-specified.

## 5 Empirical Results and Mechanized Proofs

The formalization campaign has produced concrete, checkable artifacts:

- **Mechanized tnum proofs [1]:** full soundness and optimality for the tnum operator suite, with discovered unsoundness in shipped operators fixed upstream [3]. The proofs are machine-checked, eliminating the possibility of human error in the trickiest bit-level reasoning.
- **Mechanized range analysis [2]:** machine-checked soundness of the interval domain's transfer functions against a formal concrete semantics.
- **Jitterbug [5]:** applied Serval's symbolic evaluation [6] to the kernel's BPF JIT compilers, finding real bugs in JITs the verifier trusts. This closes a critical gap: the verifier reasons about *bytecode*, but the CPU executes *JIT-compiled native code*; Jitterbug verifies that the JIT preserves the safety properties the verifier established.
- **CertrBPF:** an end-to-end Coq proof of an eBPF virtual machine for microcontrollers, including a verified (linear-time, deliberately simple) verifier — demonstrating that full mechanization is achievable when one controls the whole stack.
- **bpfverify [7]:** translates eBPF to constrained Horn clauses over bitvectors and arrays and discharges functional properties with Z3, with a termination proof for the translation — bit- and memory-precise, at the cost of automation limits on large programs.

Differential testing between the kernel verifier and these independent implementations continues to be productive: every disagreement is either a bug or a previously undocumented assumption, and both outcomes improve the ecosystem.

## 6 Limitations

Despite this progress, the production verifier is **not** fully verified, and several gaps are fundamental rather than incidental:

1. **The type domain is unverified.** The register-type lattice and the pointer-arithmetic rules that depend on it — the logic deciding when `ptr + scalar` stays within a map value or stack region — have no mechanized soundness proof, yet they carry the bulk of the memory-safety argument.
2. **Helper functions are trusted.** Calls into kernel helpers are checked against per-program-type allow-lists and prototypes, but the helpers' own contracts (e.g., "this helper returns a valid pointer or NULL") are informal. A compositional specification of the helper interface is missing.
3. **The JIT gap.** The verifier analyzes bytecode; the JIT translates it. Jitterbug [5] and JIT synthesis work [Geffen *et al.*] address this, but per-architecture JITs evolve faster than their proofs.
4. **Speculation modeling.** The speculative semantics the verifier checks is a model of hardware behavior that vendors do not fully specify; soundness relative to a model is only as good as the model.
5. **Completeness.** The verifier rejects many safe programs. PREVAIL [4] and annotation-guided toolchains reduce the burden, but the fundamental tension — a sound, decidable, *and* complete verifier for a Turing-incomplete-but-expressive ISA — admits no perfect solution.

## 7 Conclusion

The eBPF verifier is abstract interpretation deployed at planetary scale: every eBPF program loaded anywhere in the world passes through it. Viewing it through the formal lens — concrete semantics, Galois connections, sound and optimal abstract operators, widening and subsumption — turns a 10,000-line gatekeeper from inscrutable to intelligible, and, crucially, to *checkable*. The mechanized results on tnums [1] and range analysis [2] show that the most bug-prone components can be proved correct, and that the proofs find real bugs. The frontier is clear: mechanize the type domain, specify the helper interface, keep the JITs in sync with their proofs, and harden the speculation model. Until then, the verifier remains what it has always been — the most audited, most attacked, and most important abstract interpreter in production.
