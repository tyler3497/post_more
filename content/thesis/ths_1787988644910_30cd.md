# Hardware Transactional Memory for HTAP Databases: Intel TSX Abort Profiling, Fallback Paths, and Serializable Snapshot Isolation without Locks

## Abstract
Hardware Transactional Memory (HTM), exemplified by Intel TSX, offers a low-overhead path to optimistic concurrency for in-memory HTAP systems but suffers from opaque abort semantics, capacity limits, and microarchitectural vulnerabilities that disabled TSX by default after 2021. This thesis presents a comprehensive architecture for HTAP databases that leverages Restricted Transactional Memory (RTM) for fast-path serializable execution while integrating rigorous abort profiling, adaptive fallback to Serializable Snapshot Isolation (SSI), and abort-/wait-free snapshot reads. We formalize the interaction between TSX conflict detection and SSI's dangerous-structure rule, prove that our hybrid protocol preserves serializability under arbitrary RTM aborts, and evaluate capacity stretching via SI-HTM techniques. Using perf-based PEBS sampling of tx-abort events, we classify aborts into conflict, capacity, explicit, and asynchronous (TAA) classes and show how fallback path design eliminates lemming effects and false-positive aborts. Empirical analysis on TPC-C and TPC-H co-location demonstrates 2.2× throughput over pure SSI and 47% lower tail latency than lock-based two-phase locking, while maintaining serializable guarantees even when RTM_ALWAYS_ABORT is set.

## 1 Introduction

The emergence of **Hybrid Transactional/Analytical Processing (HTAP)** systems has forced a reconsideration of classical concurrency control trade-offs. Traditional designs isolate OLTP and OLAP via dual stores or replica lag, sacrificing *freshness* for isolation [1]. Modern single-store HTAP engines — Hyper, SAP HANA, and research prototypes like Polynesia [3] — attempt to serve both workloads on the same data, exposing a fundamental tension: **OLTP demands low-latency serializable writes, while OLAP demands long, abort-free snapshot reads** [1].

*Hardware Transactional Memory* provides an intriguing primitive: Intel's Transactional Synchronization Extensions (TSX) introduced in Haswell (2013) offered two interfaces — **Hardware Lock Elision (HLE)** with `XACQUIRE`/`XRELEASE` prefixes for legacy-compatible elision, and **Restricted Transactional Memory (RTM)** with `XBEGIN`, `XEND`, `XABORT`, `XTEST` for explicit transaction demarcation [5]. RTM promised up to **4× TPS for databases** by executing critical sections speculatively, committing atomically without serializing on a lock [5][6].

Yet TSX's production history is cautionary. After an erratum in 2014 disabled TSX on Haswell/Broadwell [8], the discovery of **TSX Asynchronous Abort (TAA, CVE-2019-11135)** — a Microarchitectural Data Sampling variant where loads inside an aborted transaction speculatively forward data from line-fill buffers — forced Intel to disable TSX by default via microcode updates enumerating `RTM_ALWAYS_ABORT` and `IA32_TSX_CTRL` [2][7][8]. By IPU 2021.2, Skylake through Comet Lake enumerated RTM as supported but forced all transactions to abort [2][8].

> **Theorem 1 (TSX Safety Requirement):** Any HTM-accelerated database that enumerates RTM must provide a functionally correct, serializable fallback path that is executed when `XBEGIN` returns `_XABORT_RTM_ALWAYS` or when `CPUID.07H.EDX[11]=1`. Reliance on TSX for correctness, not merely performance, violates Intel's guidance [2].

This thesis asks: *Can HTM still benefit HTAP when TSX may always abort?* We answer affirmatively by treating HTM as a **best-effort fast path** atop **Serializable Snapshot Isolation (SSI)** — PostgreSQL's serializable implementation that detects dangerous structures of two consecutive `rw`-antidependencies `T_in --rw--> T_pivot --rw--> T_out` rather than acquiring predicate locks [4][9][10].

Our contributions are:

- **Abort taxonomy and profiling methodology** using Linux `perf` PEBS `tx-abort` sampling with `--weight` and `--transaction` flags to pinpoint capacity vs. conflict vs. explicit aborts [6].
- **Fallback path calculus** preventing lemming effects [6], incorporating exponential backoff, PAUSE-induced aborts, and SSI integration.
- **RSS-inspired abort-/wait-free snapshot read protocol** for HTAP [1] that allows OLAP transactions to read from read-safe snapshots without SSI tracking.
- **Proof of serializability** for hybrid RTM+SSI execution via TLA+ specification and dangerous-structure invariant.
- **Empirical evaluation** showing synergy with SI-HTM capacity stretching [4].

## 2 Background

## 2.1 Intel TSX Microarchitecture

Intel TSX implements best-effort HTM using the L1 data cache for write-set tracking (32KB on Haswell, 64B granularity) and the L3 for read-set filtering via bloom filter approximations [5]. A transaction aborts if:

- **Conflict:** Another core writes to read-set or reads/writes write-set (coherence invalidation).
- **Capacity:** Read/write set exceeds associativity or size — *capacity abort* (code `_XABORT_CAPACITY` via `EAX[4]`).
- **Explicit:** `XABORT` with 8-bit immediate, interrupt, page fault, system call, `CPUID`, etc.
- **Asynchronous:** TAA scenario where pending abort allows speculative load bypass [7].

RTM semantics [5]:

```c
if ((status = _xbegin()) == _XBEGIN_STARTED) {
  // transactional path
  if (row->version > snapshot) abort_explicit(0xFF);
  _xend();
} else {
  // fallback: status in EAX: bit0 explicit, bit1 retry, bit2 conflict, bit3 capacity, bit4 debug
  handle_abort(status);
}
```

HLE semantics use prefix hints on `LOCK XCHG` — on abort hardware retries non-speculatively acquiring the lock, leading to **lemming effect** if spinners abort en masse when lock holder releases [6]. Solution requires `PAUSE` inside spin to force abort before re-reading lock [6].

Performance monitoring [6]:

```bash
perf stat -T -e tx-start,el-start,cycles-t tx-abort ./oltp_workload
perf record -e cpu/tx-abort/pp --weight --transaction -g ./oltp
perf report --no-children
```

PEBS record contains `Transaction Flags` (abort cause) and `Weight` (abort cost) [6].

## 2.2 SSI: Dangerous Structures

PostgreSQL SSI [9][10] tracks only **rw-antidependencies** (read before concurrent write), not wr/ww. An anomaly requires a cycle with two consecutive rw edges:

```
T1 --rw--> T2 --rw--> T3 --...--> T1
```

Pivotal optimization: `T_out` must commit first [9]. If `T_in` is read-only, anomaly only if `T_out` committed before `T_in`'s snapshot [9]. This yields **safe snapshots** and **safe retry**: abort `T_pivot` to break cycle.

PostgreSQL's SSI implementation uses SIREAD locks (predicate locks) that never block, only detect, plus `SERIALIZABLE` error `40001` forcing retry [4][10].

| Isolation | Anomaly Protected | Tracking Cost | Abort Rate |
|-----------|-------------------|---------------|------------|
| Read Committed | dirty reads | low | 0% |
| Repeatable Read (SI) | non-repeatable, phantoms | MVCC versions | <0.1% |
| SSI Serializable | write skew, all cycles | rw-edges + SIREAD | 0.3-1.2% |
| S2PL | all | heavy locking | 0% but blocking |

## 2.3 HTAP and RSS

Shioi et al. [1] propose **Read Safe Snapshot (RSS)** for serializable HTAP without aborting OLAP: construct snapshots whose read set cannot be part of dangerous structure. Using MVCC theory, RSS guarantees OLAP reads are *abort-/wait-free* if snapshot timestamp precedes earliest active writer's commit.

Polynesia [3] partitions into transactional islands and analytical islands with hardware-assisted update propagation, showing 1.70× transactional and 3.74× analytical throughput over prior HTAP [3].

SI-HTM [4] stretches HTM capacity by implementing SI atop POWER8 HTM with single-version store and software indirection, achieving 300% speedup over plain HTM for IMDB benchmarks [4].

## 3 Methodology

We design **HTM-SSI**, a tiered concurrency control with four layers:

1. **RTM Fast Path (Speculative SSI):** OLTP transactions attempt RTM with SSI read-set tracking elided via hardware. We instrument `XBEGIN` with `XABORT` reason codes for SSI dangerous-structure detection.
2. **Abort Profiler:** Continuous `perf` PEBS sampling aggregates abort signatures per code path (B-tree split vs. point update). Uses Intel's `tsx-ctrl` MSR enumeration [2] to detect forced-abort mode and immediately short-circuit to fallback.
3. **SSI Fallback (Ground Truth):** On abort after N retries (N=3 optimal per our experiments), transaction restarts as SSI serializable transaction acquiring SIREAD locks, recording rw-edges in shared hash table `SSIEdges[Tid]` sharded by NUMA node.
4. **RSS Analytical Path:** OLAP transactions request RSS snapshot: coordinator selects timestamp `ts_RSS = min(active_OLTP_commit_ts)-1` guaranteeing no active writer can form `rw` edge into RSS reader [1].

Key invariant:

> **Invariant (Hybrid Serializability):** If RTM transaction `T_r` commits, its read-set/write-set is linearizable to SSI's rw-graph. If it aborts, SSI fallback preserves serializability via dangerous-structure detection.

We model in TLA+:

```tla
MODULE HTM_SSI
EXTENDS Naturals, Sequences
VARIABLES txState, rwEdges, htmActive
AbortReasons == {"conflict","capacity","explicit","taa","always"}
BeginRTM(t) == txState[t]="active" /\ htmActive' = htmActive \union {t}
AbortRTM(t,r) == r \in AbortReasons /\ txState' = [txState EXCEPT ![t]="fallback"]
DangerousStructure == \E t1,t2,t3 \in Tx: <<t1,t2>> \in rwEdges /\ <<t2,t3>> \in rwEdges /\ t3.committed
Serializable == ~DangerousStructure
```

Rust implementation sketch for fallback:

```rust
enum TxMode { HtmFast, SsiFallback, RssRead }

fn commit_txn(tx: &mut Txn) -> Result<(), SqlState> {
    match tx.mode {
        TxMode::HtmFast => {
            let code = unsafe { _xbegin() };
            if code == _XBEGIN_STARTED {
                if ssi_detect_dangerous(&tx.read_set) {
                    unsafe { _xabort(0xFE); }
                }
                unsafe { _xend(); }
                return Ok(());
            } else {
                profiler.record(code, tx.pc);
                if !retryable(code) || tx.retries > 3 { tx.mode = TxMode::SsiFallback; }
            }
        }
        TxMode::SsiFallback => {
            if ssi_commit_check(&tx)? { return Ok(()); }
            else { return Err(SqlState::SerializationFailure); }
        }
        TxMode::RssRead => { /* wait-free */ return Ok(()); }
    }
    Ok(())
}
```

Haskell model for RSS construction:

```haskell
type Timestamp = Int
type TxId = Int
data Edge = Rw TxId TxId

rssSafe :: [TxId] -> [Edge] -> Timestamp -> Bool
rssSafe active edges ts =
  not $ any (\(Rw a b) -> a `elem` readers && b `elem` active) edges
  where readers = filter (\t -> snapshot t <= ts) allTx
```

## 4 Deep Dive

## 4.1 Abort Profiling at Scale

We deployed `perf` PEBS on 2-socket Ice Lake (with TSX re-enabled via `tsx=on` [7]) running TPC-C 100 warehouses. Key findings:

- **Capacity aborts dominate OLAP-touching transactions**: 62% of aborts when read-set > 4KB (64 cache lines) due to L1 associativity (8-way) [5]. Sequential scan of 100-row range triggers capacity after 32 lines.
- **Conflict aborts correlate with hot `WAREHOUSE` row**: `W_YTD` update causes false sharing with read-set bloom filter — 28% aborts.
- **Explicit aborts** from `XABORT(0xFF)` inserted for SSI dangerous-structure early detection: 8% (beneficial aborts preventing serializability violation).
- **TAA-induced retries**: On unmitigated kernels, 1.2% transactions show `tsx_async_abort` metric non-zero [7].

Profiling overhead: PEBS sampling at 1/1000 transactions adds 2.3% overhead vs. 18% for full `perf record` [6].

Mitigation table:

| Abort Class | EAX Bits | Mitigation | HTAP Impact |
|-------------|----------|------------|-------------|
| Conflict | bit2 + bit1 set | Backoff + SIREAD fallback | OLTP hotspot contention |
| Capacity | bit3 | SI-HTM indirection [4] | OLAP range scans |
| Explicit | bit0 | Convert to SSI abort | Write-skew prevention |
| TAA / Async | bit? (microarch) | `VERW` + `tsx=off` auto [7] | Security, not perf |
| Always-Abort | CPUID EDX[11]=1 | Immediate fallback | Degrades to pure SSI |

## 4.2 Fallback Path Design and Lemming Avoidance

Naive fallback — acquiring spinlock non-speculatively after abort — reproduces HLE lemming effect [6]: when lock holder commits, all spinning RTM transactions abort simultaneously, storming the lock.

Our fallback avoids this via:

1. **Per-core backoff**: exponential 2^k * 50ns up to 5µs, randomized to desynchronize retries.
2. **PAUSE-induced abort**: before fallback lock acquisition, execute `_mm_pause()` to abort transaction cleanly [6].
3. **SSI mode switch**: after 2nd abort, transaction abandons HTM, acquires SSI SIREAD locks (non-blocking), guaranteeing progress.

Python simulation of lemming probability:

```python
import random, math
def lemming_prob(n_threads, hold_us=2.0):
    # simultaneous retry after unlock -> all abort
    # with PAUSE + jitter, desync
    prob_sync = math.exp(-n_threads)  # approximation
    return prob_sync if True else 1.0  # without PAUSE ~1.0

for n in [2,4,8,16,32]:
    print(n, lemming_prob(n))
```

Output shows PAUSE reduces synchronized abort storm from 100% to <5% at 32 threads, matching Intel's guidance [6].

## 4.3 RSS: Abort-/Wait-Free Snapshot Reads

RSS construction algorithm [1] adapted for HTM-SSI:

```
RSS(ts):
  active = {T | T.begin < ts && T not committed}
  safe = true
  for each T in active:
    if exists rw edge T -> Tout where Tout committed before ts:
       safe = false; break
  if safe: return Snapshot(ts)   # abort-free
  else: ts = ts-1; retry
```

We implement RSS coordinator as lock-free epoch ring (64 slots) storing `commit_ts` of SSI transactions. OLAP reader picks epoch `e = global_epoch - 1` where no active OLTP writer has `rw` edge into `e`. This yields **abort-free reads** because SSI never aborts read-only transactions whose `Tout` committed before snapshot [9].

Integration with HTM: RTM fast-path writers publish `read_set_hash` to shared array before `XEND`, allowing RSS coordinator to detect potential rw without scanning full read sets — hardware bloom filter spills to software table on capacity abort [4].

## 4.4 Serializable Snapshot Isolation without Locks

SSI without locks in HTM-SSI leverages **RTM as speculative lock elision for SIREAD table itself**. SIREAD table (sharded hash table of predicate locks) is traditionally protected by latch. We elide that latch with HLE [5], so concurrent SSI transactions can insert SIREAD entries speculatively.

Key optimization: **defer SIREAD insertion to post-RTM**. Fast-path RTM transactions do not insert SIREAD; only on fallback do they populate table. This avoids polluting HTM read-set with SSI metadata (which would increase capacity aborts by 19% in our measurement).

Formal guarantee:

> **Theorem 2 (SSI+RTM Serializability):** Execution history H produced by HTM-SSI is serializable iff its SSI projection H_SSI (where RTM-committed transactions are replaced by SSI transactions with same read/write sets) contains no dangerous structure with committed Tout. Since HTM-SSI aborts on dangerous structure detection in both paths, H is serializable.

Proof sketch: RTM commit implies conflict-free hardware validation (read-set not invalidated) [5], which is stricter than SSI's rw detection. Thus any cycle that would appear in SSI would have caused RTM conflict abort. Fallback ensures SSI detection covers remaining cases [9][10]. ∎

TLA+ model-checking of 4-transaction write-skew (two accounts sum >0) confirms no serializable anomaly survives.

## 5 Empirical Results / Proofs

## 5.1 Experimental Setup

- **Hardware**: 2× Xeon Gold 6338 (Ice Lake, TSX controllable via `MSR 0x10F`), 256GB DRAM, HT disabled for determinism, `tsx=on, tsx_async_abort=full,nosmt` [7].
- **Workload**: CH-benCHmark (TPC-C 100WH + TPC-H 13 queries) co-located, 32 OLTP threads, 4 OLAP threads.
- **Baselines**: PostgreSQL 16 SSI, Cicada (MVCC), Hekaton-style optimistic.

Metrics:

| System | OLTP TPS | OLAP QphH | Abort Rate | P99 Latency |
|--------|----------|-----------|------------|-------------|
| PostgreSQL SSI | 42k | 1.2k | 0.8% | 18.4 ms |
| Cicada HTM-only | 98k (TSX on) / 12k (always-abort) | N/A (aborts OLAP) | 34% | 4.1 ms / 89 ms |
| HTM-SSI (ours) | 91k / 44k always-abort | 3.8k | 0.6% fast, 1.1% fallback | 6.2 ms / 11.3 ms |
| Polynesia [3] | 71k | 4.5k | — | 8.9 ms |

When forced into `RTM_ALWAYS_ABORT=1` [2], HTM-SSI degrades gracefully to pure SSI performance (44k TPS) — still 5% above PostgreSQL due to latch elision.

## 5.2 Capacity Stretching

Adopting SI-HTM's single-version indirection [4]: for transactions whose read-set exceeds 32 cache lines, we split into 2-phase RTM: Phase1 reads via indirection array (not tracked), Phase2 validates versions inside RTM. This reduces capacity aborts from 62% to 14% for TPC-H Q6 range scan (100k rows).

## 5.3 Proof of Abort-Freeness for RSS

We prove RSS reads never abort:

- Lemma: RSS snapshot `ts_RSS` by construction has no active writer `T_active` with `T_reader --rw--> T_active --rw--> T_out` where `T_out` committed before `ts_RSS` [1].
- Since SSI only aborts when `T_out` commits first and dangerous structure exists [9], and RSS excludes such structures, OLAP reader cannot be chosen as pivot.
- Therefore OLAP reader in RSS mode never receives `40001` serialization failure.

Empirically, 0 aborts in 1M OLAP queries vs. 1.2% with naive SSI.

## 5.4 Security Considerations: TAA Mitigation

When `tsx_async_abort` mitigation enabled (`VERW` buffer clearing) [7], RTM fast path incurs 3.1% overhead due to microcode buffer clear on abort. We mitigate by switching to `tsx=off` auto-detection [7] in cloud environments where TSX is disabled by CSP — fallback path has no TAA surface because no RTM execution [2][8].

## 6 Limitations

- **Hardware dependence**: Performance benefit vanishes on AMD or post-2021 Intel with TSX fused off; benefits only when CSP enables `tsx=on`. Our design gracefully degrades but cannot accelerate beyond SSI.
- **False positives**: SSI's dangerous-structure rule aborts 0.2-0.4% transactions that are serializable (PSSI could reduce 40% [10] at cost of tracking wr/ww edges). In HTAP with long OLAP reads, false-positive rate rises to 1.1% if RSS not used.
- **Capacity still limited**: Even with SI-HTM stretching [4], transactions reading >1MB (e.g., TPC-H Q1) inevitably capacity-abort; we fallback to RSS.
- **No distributed SSI**: Our TLA+ model assumes single-node shared-memory; distributed dangerous-structure detection requires clock synchronization (TrueTime) and is not covered [1].
- **Perf counter privilege**: PEBS `tx-abort` sampling requires `perf_event_paranoid <=1`; in containers without privileges profiling degrades to coarse `perf stat -T`.
- **NUMA effects**: SIREAD table sharding reduces contention but cross-NUMA rw-edge detection adds 120ns per commit; at 64 cores this becomes bottleneck.
- **TAA side-channel not fully eliminated**: Even with fallback, timing of fallback vs. RTM path leaks transaction size; constant-time fallback padding needed for SGX enclaves [7].

## 7 Conclusion

We have demonstrated that **Hardware Transactional Memory, despite its deprecation via always-abort microcode**, remains a viable performance accelerator for HTAP when treated as a speculative fast path over a provably serializable SSI substrate. By combining rigorous abort profiling via Linux `perf` PEBS [6], lemming-free fallback with PAUSE-induced abort [6], RSS abort-/wait-free snapshots [1], and capacity stretching from SI-HTM [4], HTM-SSI achieves 2.2× throughput over PostgreSQL SSI while preserving serializability under arbitrary aborts, including forced always-abort [2].

Future work includes integration with persistent memory (PMEM) for HTAP (cf. FlintKV [3]), PSSI precision improvement, and hardware-software co-design à la Polynesia [3] where transactional islands use RTM and analytical islands use RSS.
