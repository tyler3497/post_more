# CHERI Capabilities and Hardware-Enforced Memory Safety: Fat-Pointer Provenance, Monotonic Derivation, the Morello Prototype, and Compartmentalized C/C++

## Abstract

The CHERI (Capability Hardware Enhanced RISC Instructions) programme replaces conventional integer pointers with *hardware capabilities*: unforgeable tokens of authority that bind every memory reference to its provenance, bounds, and permissions. By enforcing *provenance validity* and *monotonic derivation* in the instruction-set architecture — checked against tagged memory on every access — CHERI delivers deterministic spatial memory safety and a principled foundation for software compartmentalization for C and C++ [1][2]. This thesis develops the complete argument: the 128-bit compressed fat-pointer representation and its 1-bit-per-word integrity tags; the lattice of monotonic derivation under which privileges may only shrink; sealed capabilities and object types as the mechanism for least-privilege compartmentalization; the Arm Morello prototype — a multi-GHz, multi-core, Neoverse N1-based evaluation platform whose 60,000-line Sail specification carries the first machine-checked proof of an industrial-scale processor's security properties [3]; and the CheriBSD porting discipline (hybrid versus pure capability). We close with empirical results, formal guarantees, and the open problems — notably temporal safety — that define the research frontier.

## 1 Introduction

Memory unsafety remains the dominant class of software vulnerability. Decades of mitigations — stack canaries, ASLR, control-flow integrity, sanitizers — share a structural weakness: they defend an *integer-pointer* machine in which any sufficiently creative adversary can forge a reference to arbitrary memory. The CHERI programme, a collaboration between the University of Cambridge and SRI International begun in 2010 under DARPA's CRASH and MRC programmes, attacks the problem at its root: it changes what a pointer *is* [1]. A CHERI pointer is a *capability* — an unforgeable, hardware-interpreted token carrying the address, the bounds of the object it may reference, the permissions governing its use, and a hardware-managed provenance record. Capabilities cannot be fabricated by software; they can only be *derived* from existing capabilities, and derivation is *monotone*: every derived capability holds a subset of the authority of its parent. The result is an architecture in which spatial memory safety is not a software convention but a hardware invariant.

This thesis traces that argument end to end: the compressed 128-bit representation and tagged memory (§4.1); provenance validity and monotonic derivation, stated as a formal theorem (§4.2); sealed capabilities and compartmentalization (§4.3); the Arm Morello prototype and its machine-checked proof of reachable capability monotonicity (§4.4); and the CheriBSD porting discipline in hybrid and pure-capability modes (§4.5). Section 5 evaluates empirical and formal results; §6 confronts the limitations, notably temporal safety; §7 concludes.

## 2 Background

### 2.1 Capability systems before CHERI

Capability-based addressing predates modern memory protection by decades. Dennis and Van Horn's 1966 formulation treated capabilities as unforgeable references combining designation with authority; commercial realizations included the Plessey System 250, IBM's System/38, and Intel's iAPX 432. These systems enforced fine-grained protection but paid for it in complexity: capabilities lived in special segments or required privileged management, and performance on general-purpose workloads was uncompetitive. The dominant compromise became the page-granular model — processes as flat address spaces guarded by an MMU — which is coarse (4 KiB minimum), expensive to reconfigure, and blind to intra-process structure: a buffer overflow *within* a process is invisible to the MMU. CHERI's insight is that capabilities need not be heavyweight kernel objects: with tagged memory and a compressed encoding, every pointer-sized datum can carry capability metadata at near-zero marginal cost, making *object-granular* protection the default [1][9].

### 2.2 The CHERI threat model and security principles

CHERI assumes a powerful adversary: arbitrary memory-safety bugs in C/C++ code — overflows, use-after-free, type confusion — exploitable to forge pointers, inject code, and escalate privilege. The architecture's security rests on four interlocking principles:

1. **Pointer integrity via tags.** Every capability-sized, capability-aligned word of memory and every capability register carries an *unaddressable* 1-bit tag tracking provenance validity. Overwriting any portion of a capability clears the tag atomically; dereferencing an untagged value as a capability raises a hardware exception. Software cannot set tags; tags propagate only through legitimate capability operations [1].
2. **Provenance validity.** Tagged capabilities are constructed only by deriving them from existing tagged capabilities, so every live capability has an unbroken chain of custody to an architectural root of trust.
3. **Spatial safety via bounds.** Every dereference is checked against the capability's base and top; out-of-bounds access faults deterministically.
4. **Monotonicity.** Derivation may only narrow authority: bounds may shrink, permissions may be cleared, but never widened. No sequence of legal operations increases privilege [3].

Crucially, CHERI is designed for *incremental deployability*: hybrid capability modes let legacy C/C++ run with integer pointers alongside capability-aware code, trading protection for source compatibility while codebases migrate [5][9].

## 4 Deep Dive

### 4.1 Fat-pointer representation: compressed capabilities and tagged memory

A CHERI capability is a *fat pointer*: alongside the 64-bit address (or cursor), it carries the object's lower and upper bounds (*base* and *top*), a permission mask, and — for sealed capabilities — an object type. On Morello this is packed into 128 bits using a compressed bounds encoding in the spirit of *CHERI Concentrate*: the full precision of base and top is preserved for small objects, while an exponent field trades precision for range on large objects, keeping the common case exact and the encoding fixed-width. The 129th bit — the tag — lives outside addressable memory, maintained by the memory subsystem alongside each 128-bit line and following capabilities through registers, caches, and (in principle) DMA [1].

The tag is the linchpin of unforgeability. Integer arithmetic on a capability's address field remains permitted (pointer arithmetic must work), but the result stays tagged only because the operation consumed a *tagged* input, with bounds and permissions carried along. Any store overwriting part of a capability in memory clears the tag atomically, and no instruction sets a tag from data; loading a capability from an untagged word faults on dereference [1].

The table below summarizes the Morello capability fields and their security roles:

| Field | Size (Morello) | Security role |
|---|---|---|
| Address / cursor | 64 bits | The pointer value manipulated by arithmetic |
| Base / Top (compressed) | within 64-bit metadata | Spatial bounds; every access checked |
| Permissions | subset of metadata bits | Least privilege: load, store, execute, seal |
| Object type | subset of metadata bits | Sealing domain for compartmentalization |
| Tag | 1 bit, unaddressable | Provenance validity; cleared on corruption |

The tag density — one bit per 128-bit word, roughly 0.78% of DRAM — is the price of integrity, and it is paid in the memory controller rather than in software checks. This is what makes the protection *deterministic*: unlike probabilistic mitigations, a bounds violation cannot be "lucky."

```c
/* CHERI C: pointers become capabilities in pure-capability mode [5] */
void *__capability buf = malloc(256);   /* bounds = [buf, buf+256) */
char *__capability p = (char *__capability)buf;
p[300] = 'x';   /* hardware trap: out-of-bounds, tag intact, bounds violated */

/* Provenance pitfall: round-tripping through integers strips the tag */
uintptr_t raw = (uintptr_t)buf;          /* capability -> integer: metadata lost */
void *__capability q = (void *__capability)raw; /* untagged: dereference faults */
```

The second idiom — casting pointers to integers and back — is ubiquitous in systems code (XOR linked lists, tagged pointers, custom allocators) and is the single largest source of porting friction: the CHERI C/C++ programming guide documents precisely which conversions preserve provenance and which deliberately do not [5].

### 4.2 Provenance validity and monotonic derivation

The deepest property of the architecture is *monotonicity*: authority flows downhill. Formally, let the architectural state contain a set of tagged capabilities; define the *reachable authority* of a capability as the set of (address, permission) pairs it authorizes. The security theorem, machine-checked for Morello, is:

> **Theorem (Reachable capability monotonicity):** For any execution trace of the Morello ISA, the reachable authority available to any protection domain is non-increasing except across explicit domain transitions (e.g., sealed-capability invocation or exception delivery). No instruction sequence available to unprivileged software can widen the bounds, add permissions, forge a tag, or unseal a capability without the corresponding sealing authority [3].

The proof — by Bauereiss, Campbell, Sewell, Armstrong, Esswood, Stark, Barnes, Watson, and Sewell against the 60,000-line Sail specification translated from Arm's ASL — is the first machine-checked security proof at the scale of an industrial processor, and it validates the specification rather than any single RTL implementation [3][10]. Its structure is what made it scale: the authors define local monotonicity properties of arbitrary CHERI instruction execution and lift them to the global trace property, where separation-logic approaches to full *capability safety* did not [3].

A compact formal sketch of the derivation discipline, in the style of a TLA+ action specification, illustrates the constraint every instruction must satisfy:

```tla
---- MODULE CheriMonotonicity ----
VARIABLES caps  \* set of tagged capabilities held by the domain

Derive(c, base2, top2, perms2) ==
    /\ c \in caps
    /\ c.tag = TRUE
    /\ base2 \in c.base .. c.top        \* new base within old bounds
    /\ top2  \in base2 .. c.top         \* new top within old bounds
    /\ perms2 \subseteq c.perms          \* permissions only shrink
    /\ caps' = caps \cup {[c EXCEPT !.base = base2,
                                     !.top  = top2,
                                     !.perms = perms2]}
    \* No action exists with base2 < c.base, top2 > c.top,
    \* perms2 \not\subseteq c.perms, or tag := TRUE from data.
====
```

*Every* capability-modifying instruction in the ISA — `CSetBounds`, `CAndPerms`, `CSeal`, derivation through `CIncOffset` — is a refinement of this action. The hardware simply has no opcode for the forbidden transitions, which is why the property is architectural rather than conventional.

### 4.3 Sealed capabilities and compartmentalization

Spatial safety confines *where* a pointer may reach; *compartmentalization* confines *who* may reach what. CHERI supports it through **sealed capabilities**: a capability whose object-type field is set and whose permissions are restricted so that it can be neither dereferenced nor modified — only *invoked* (for sealed code capabilities) or *unsealed* by a holder of the matching sealing authority. Sealing converts a capability into an opaque, unforgeable token: the basis of cross-domain calls, callbacks, and object-capability discipline [1][2].

A canonical compartmentalization pattern works as follows:

1. The trusted supervisor allocates each compartment a disjoint set of capabilities (its code, data, and stack), sealed where they must cross boundaries.
2. Entry points are exposed as *sealed code/data capability pairs*; invoking the pair atomically switches domain, installing the callee's capabilities and sealing the caller's state for return.
3. Because invocation is a domain transition, the monotonicity theorem's exception is tightly scoped: authority moves *between* compartments only through these gates, never by ambient forging.

This yields *intra-address-space* isolation at the cost of a capability invocation rather than a context switch — orders of magnitude cheaper than process separation and fine-grained enough to isolate individual libraries, parsers, or protocol handlers. The CHERIoT project pushes the model furthest: a clean-slate RTOS for microcontrollers with under 256 KiB of SRAM, where compartments are first-class, the heap allocator enforces non-overlapping bounds on every allocation, and a revocation service sweeps memory to delete capabilities pointing at freed objects, giving *deterministic* use-after-free protection [6]. In the application-processor world, the same primitives underpin CheriBSD's library compartmentalization and research systems such as CompartOS, which applies linkage-based compartmentalization to Linux kernel modules — containing even a compromised driver so it cannot take down the system [8].

### 4.4 The Morello prototype: industrial-scale validation

Paper architectures prove little until silicon — or at least a faithful high-performance prototype — exists. The **Arm Morello** platform, developed under the UKRI-funded Digital Security by Design (DSbD) programme, is a CHERI-extended, multi-GHz, multi-core, superscalar implementation based on the Arm Neoverse N1, delivered on evaluation boards running CheriBSD, customized Android, and Linux [4][9]. It is explicitly a *superset architecture for evaluation*, not a production core: its purpose is to answer the questions that only real hardware can — performance overhead of bounds checks at superscalar issue rates, the behavior of tagged memory through a realistic cache hierarchy, and the software cost of porting at scale.

Three results from the Morello programme stand out. **First**, the evaluation platform paper (Grisenthwaite et al., *IEEE Micro* 43(3), 2023) demonstrates CHERI-based security running a full software stack at performance levels that make deployment plausible rather than aspirational [4]. **Second**, the machine-checked proof of §4.2 gives unprecedented confidence that the 60,000-line specification contains no flaw letting attackers sidestep the intended protection [3]. **Third**, the 2024 IEEE ecosystem paper documents the maturing software stack — compiler, OS, libraries, porting experience — that turns an ISA extension into deployable technology [2].

| Platform | ISA base | Capability width | Target |
|---|---|---|---|
| CHERI-MIPS (research) | MIPS64 | 256-bit | Original prototype |
| **Morello** | Armv8-A (Neoverse N1) | 128-bit + tag | Application processors, evaluation |
| CHERI-RISC-V | RISC-V | 128-bit + tag | Open research cores, FPGA |
| CHERIoT | RISC-V (RV32) | 128-bit + tag | Microcontrollers, deterministic temporal safety |

### 4.5 Porting C/C++ at scale: CheriBSD and the hybrid discipline

The hardest problem in CHERI adoption is not hardware but *software*: millions of lines of C/C++ written under the assumption that pointers are integers. The CheriBSD project — a full FreeBSD-derived operating system adapted to CHERI — pioneered the porting discipline, and its lessons are codified in the CHERI C/C++ Programming Guide [5][9]. The strategy rests on two compilation modes:

- **Hybrid mode.** Only explicitly annotated pointers (`__capability`-qualified) become capabilities; the rest remain integers. Legacy code compiles nearly unchanged, and protection is applied selectively — for example, to harden specific pointers or sandbox specific libraries. This is the incremental on-ramp.
- **Pure-capability mode.** Every pointer is a capability; `sizeof(void *)` becomes 16, and the entire address space is spatially safe. This is the destination, and it is *source-breaking* in principled ways: integer-to-pointer casts lose provenance, pointer/integer size assumptions fail, and custom allocators must be made provenance-aware.

The porting workflow that emerged is empirical and tool-assisted: compile in hybrid mode, promote annotations outward from security boundaries, and run under CheriBSD, where violations trap deterministically — turning latent bugs into loud failures. Experience reports consistently find that the bugs CHERI exposes are *real* bugs: latent overflows and provenance violations that happened to be benign on integer-pointer machines, which reframes porting effort as vulnerability discovery with a hardware oracle.

## 5 Empirical Evaluation and Formal Results

The evidence for CHERI now spans formal proof, prototype measurement, and ecosystem scale:

1. **Machine-checked security.** Reachable capability monotonicity is proven in Isabelle/HOL against the Sail Morello model generated from Arm's ASL snapshots — the first proof of its kind for an industrial-scale ISA, with test suites generated from the same specification [3][10].
2. **High-performance feasibility.** The Morello evaluation platform runs a complete CHERI software stack on a superscalar, multi-core, multi-GHz design, establishing that capability enforcement is a plausible deployment technology rather than a microcontroller curiosity [4].
3. **Ecosystem scale.** The 2024 IEEE paper documents the full hardware-software stack — ISA, toolchain, languages, OS, applications — required for "complete pointer and memory safety" in C/C++ at scale [2].
4. **Embedded completeness.** CHERIoT demonstrates object-granularity spatial safety *plus* deterministic temporal safety (allocator discipline with revocation sweeping) and lightweight compartmentalization on devices with under 256 KiB of SRAM — a regime where MMUs and MPUs are unavailable or inadequate [6].
5. **Temporal-safety frontier.** FRESCO, realized on CHERI-RISC-V QEMU and the out-of-order CHERI-Toooba FPGA softcore with CheriBSD support, closes the remaining gap — stack use-after-return — by "coloring" the stack pointer with per-invocation provenance identifiers that hardware-invalidates on function exit. It reports only 4% geometric-mean overhead on SPEC CPU and 10–14% on SQLite/PostgreSQL while systematically preventing use-after-return, use-after-free, and double-free across the NIST Juliet suite and real CVEs [7].
6. **OS-level compartmentalization.** The embedded-Linux case study builds kernel and userland in pure-capability mode, isolates user programs as separate ELFs with per-program capability tables, and compartmentalizes kernel modules via CompartOS linkage-based isolation — containing driver compromise in a way MMU-based Linux structurally cannot [8].

Taken together, these results move CHERI from conjecture to *measured* technology: spatial safety with low overhead, formal guarantees at industrial scale, and a credible path to temporal safety.

## 6 Limitations and Open Problems

A candid assessment must weigh what CHERI does not yet solve:

- **Temporal safety in the baseline.** Classic CHERI guarantees *spatial* safety; use-after-free requires additional machinery (revocation, coloring, or allocator discipline) whose cost and completeness at application-processor scale remain active research — FRESCO is promising but recent [7].
- **Pointer-size costs.** Doubling pointer width to 128 bits grows memory footprint and cache pressure in pointer-dense workloads; the 0.78% tag storage is minor by comparison, but the *bandwidth* cost of wider pointers is real.
- **Source churn.** Provenance discipline breaks idioms — XOR linked lists, tagged pointers, intptr round-trips — that pervade systems code; porting is vulnerability discovery, but it is still labor [5].
- **Speculative execution.** CHERI constrains *architectural* authority; transient-execution attacks operate below the ISA contract and need complementary mitigations [4].
- **Compartmentalization policy.** The hardware provides sealing and invocation; *what* to isolate and how to manage sealing authority without reintroducing confused deputies remains a software-design problem with no universal answer [2][6].
- **Adoption economics.** An ISA extension requires new silicon, new toolchains, and recompilation — a coordination problem across the industry that the CHERI Alliance and the DSbD programme exist to solve, but which no proof can discharge.

None of these limitations undermines the core result; they delineate the boundary between what hardware enforcement guarantees and what the surrounding system must still earn.

---

## 7 Conclusion

CHERI reframes memory safety from a software aspiration into an architectural invariant. By making every pointer a *capability* — tagged, bounded, permissioned, and derivable only monotonically — it removes the attacker's fundamental primitive: the forgeable reference. Morello and its machine-checked proof show this works at industrial scale and performance; CheriBSD shows real C/C++ systems can be carried across; CHERIoT shows the model descends to microcontrollers; FRESCO points toward complete temporal safety. The remaining work — revocation economics, porting at industry scale, compartmentalization policy — is substantial but well-posed. After half a century of capability-system research, CHERI is the first instantiation with a credible path from formal proof to deployed silicon.
