# In-Situ Analysis at Exascale: ADIOS2 Data Staging, Catalyst Pipelines, and Particle Tracing Without the I/O Wall

## Abstract

Exascale systems such as Frontier deliver over an exaflop of compute while parallel file system bandwidth remains measured in terabytes per second, producing an I/O wall that renders classical write-then-analyze workflows infeasible at full fidelity. This thesis develops the architecture and theory of in-situ analysis as the structural remedy: the ADIOS2 adaptable I/O framework with its Sustainable Staging Transport (SST) engine streams data directly from simulation producers to analysis consumers over RDMA-capable dataplanes, bypassing the file system entirely; ParaView Catalyst 2 and the Ascent/Conduit flyweight library provide standardized in-situ visualization and analysis APIs; in-situ particle advection tracing demonstrates how memory-resident data can be interrogated with Lagrangian techniques at full temporal resolution; and error-bounded lossy compressors such as SZ and ZFP, with inline Blosc lossless codecs, shrink the residual traffic by one to two orders of magnitude. We formalize the in-situ/in-transit/post-hoc design space, present the SST rendezvous protocol, quantify reported speedups including 10x WRF I/O acceleration and beyond-file-system streaming bandwidths, and analyze the error-bounded guarantees of modern compressors, concluding with the residual limitations that still bound adoption.

---

## 1 Introduction

The transition from petascale to exascale computing widened a gap that had been growing for two decades: while peak floating-point performance increased roughly 1000-fold between 2008 and 2022, aggregate parallel file system (PFS) bandwidth improved by perhaps two orders of magnitude in the same interval. On OLCF's **Frontier**, the first U.S. exascale machine, the theoretical write bandwidth of the Orion file system is measured in single-digit terabytes per second, while the machine's compute fabric can generate simulation state at rates exceeding hundreds of terabytes per second. This *I/O wall* [4] means that the classical scientific workflow --- simulate, checkpoint to disk, analyze offline --- can no longer operate at full spatial and temporal fidelity. Analysts are forced to choose among **temporal subsampling** (writing every *k*-th timestep), **spatial decimation** (writing coarsened fields), or **write starvation** (throttling the simulation to match I/O), all of which discard the very phenomena the exascale investment was made to resolve.

In-situ analysis inverts the data-movement hierarchy: instead of moving petabytes to the analysis, the analysis is moved to the data while it still resides in compute-node memory. The last decade has matured this idea from hand-rolled co-processing hooks into a layered software stack:

- **Data-movement middleware** --- chiefly **ADIOS2**, whose *engines* are selected at runtime and include both high-performance file writers (BP4/BP5) and the **Sustainable Staging Transport (SST)** streaming engine, which connects producers and consumers directly over the high-speed interconnect [4].
- **In-situ analysis APIs** --- **ParaView Catalyst 2** (formerly coprocessing), with its Conduit-Blueprint-based data model [5,6], and the lighter-weight **Ascent** framework from LLNL, built on the **Conduit** mesh-data description library.
- **Algorithmic exemplars** --- in-situ **particle advection tracing** (streamlines, pathlines, FTLE fields) computed on memory-resident velocity fields at every timestep, which would be prohibitively expensive to store.
- **Compression operators** --- error-bounded lossy compressors (**SZ**, **ZFP**) and lossless codecs (**Blosc**) applied inline to the data stream, compounding the effective bandwidth by 5--100x [7,8,9].

## 2 Background

### 2.1 The I/O wall

The I/O wall is not merely an empirical observation; it follows from scaling laws. Let $F$ be peak flops, $B_{fs}$ the file-system bandwidth, and $\\rho$ the bytes of state produced per flop (typically $10^{-3}$--$10^{-1}$ for stencil codes). The *write-limited time* of one full state dump is $T_{dump} = \\rho F / B_{fs}$, while the *compute time* per timestep scales with the timestep's flop count divided by $F$. As $F$ grows faster than $B_{fs}$, $T_{dump}$ dominates, and any workflow requiring full-fidelity output becomes I/O-bound. 

### 2.2 ADIOS2: the adaptable I/O system

**ADIOS2** is the second generation of the Adaptable Input/Output System [2]. Its core abstraction separates the *logical I/O description* (variables, attributes, steps) from the *physical transport*, called an **engine**, chosen at runtime via XML or programmatically. This means a simulation instrumented once can write to BP5 files, stream via SST, or stage through DataMan transports with zero source changes --- the "adaptability" of the name. ADIOS2 provides C++, C, Fortran, Python, and Matlab bindings, N--M writer/reader semantics without global data sharing (unlike MPI-I/O's two-phase aggregation), node-local burst-buffer draining threads, and an **operator** framework for inline data transformations such as compression [2,3].

### 2.3 A taxonomy: in-situ, in-transit, post-hoc

Following the community consensus, we distinguish:

| Mode | Where analysis runs | Data movement | Latency | Resource contention |
|------|--------------------|---------------|---------|---------------------|
| **Post-hoc** | After job completion, separate allocation | Full state to PFS | Hours--days | None |
| **In-situ** (tightly coupled) | Same nodes/memory as simulation | None (shared memory) | Zero | CPU/memory shared with solver |
| **In-transit** | Staging/analysis nodes | Streamed over interconnect | Seconds | Separate cores, requires data motion |
| **In-line** | Within the data path (compression, filters) | Inline operators | Negligible | Minimal |

The SST engine natively supports both in-situ and in-transit deployment: the same API streams to consumers colocated on compute nodes or to dedicated staging nodes [4]. The choice is governed by the *resource balance equation*: colocated analysis steals a fraction $p$ of FLOPs and $m$ of memory from the solver; staging pays $D/B_{net}$ transfer time per step but leaves the solver untouched. We formalize this trade-off in Section 5.

## 3 Methodology

### 3.1 SST: Sustainable Staging Transport

SST is an ADIOS2 engine that implements **direct application-to-application streaming** using the standard ADIOS2 write/read API [4]. Its architecture has three planes:

1. **Control plane (rendezvous).** Writer and reader processes discover each other through a contact-info exchange, negotiate the number of writers $W$ and readers $R$ (which need not match), and establish step-wise synchronization. Each *step* of data is a transactional unit: writers block or buffer until the reader cohort signals readiness, providing natural backpressure.
2. **Data plane.** Bulk transfer uses RDMA-capable transports. The recent SST upgrade added **UCX (Unified Communication X)** as a dataplane [1], replacing older transports with a low-level RDMA interface that works across InfiniBand, Slingshot, and other fabrics, improving hardware compatibility and reducing CPU involvement in transfers.
3. **Buffering policy.** Data is buffered in the producer's memory until the consumer is ready [2]. SST supports queue-full policies (block the writer, or discard oldest steps) so that a slow consumer does not deadlock an exascale simulation.

Crucially, because the engine is runtime-selectable, "many existing file-oriented ADIOS workflows can utilize SST for direct application-to-application communication without any source code changes" [4].

### 3.2 Catalyst 2 and Ascent/Conduit pipelines

**ParaView Catalyst 2** refactored the original coprocessing API around the **Conduit Blueprint** data model [6]: the simulation describes its mesh once per timestep as a Conduit node (a hierarchical, schema-described in-memory data structure), and Catalyst executes a ParaView pipeline on that description --- no deep copy, no VTK conversion. The revised API reduces integration to `catalyst_initialize`, `catalyst_execute`, `catalyst_finalize` calls plus an adaptor that maps simulation arrays into Conduit [6]. Catalyst 2 supports both in-situ (linked into the simulation) and in-transit deployment.

**Ascent** (LLNL) is a *flyweight* alternative: a small, dependency-light C++ library exposing actions (extracts, renders, queries) driven by a YAML/Conduit action tree, designed for exascale integration where building full ParaView is prohibitive. Both frameworks sit atop **Conduit**, whose Blueprint protocol standardizes mesh descriptions (uniform, rectilinear, unstructured) so that tools, not simulations, own the data-model complexity.

### 3.3 In-situ particle tracing

Particle advection is the canonical *memory-resident* analysis: a velocity field $\\mathbf{u}(\\mathbf{x}, t)$ exists only transiently, and integrating $d\\mathbf{x}/dt = \\mathbf{u}$ for millions of seeds across timesteps would require storing the full 4D field. In-situ tracing seeds particles in the live field, advects them with the simulation's own timestepping, and extracts only the *trajectories* (pathlines) or derived quantities (finite-time Lyapunov exponent ridges, residence times). 

### 3.4 Inline compression operators

ADIOS2's operator framework applies compression *in-line* on the data stream before the engine transmits it. Two classes dominate:

- **Lossless codecs** via **Blosc** (a meta-compressor orchestrating LZ4/Zstd with shuffle filters), used in the WRF integration for bit-exact preservation [2].
- **Error-bounded lossy compressors**: **SZ** [9] (prediction plus linear-scaling quantization with guaranteed pointwise error bounds) and **ZFP** [7,8] (block-transform coding of $4^d$ blocks with fixed-rate, fixed-precision, or fixed-accuracy modes).

The error-bounded guarantee is the key theoretical property: unlike heuristic quantization, SZ and ZFP let the scientist *prescribe* the maximum pointwise or PSNR distortion, so compression becomes a controlled approximation, not data corruption. ALPINE/ZFP, an Exascale Computing Project product, explicitly pairs in-situ visualization infrastructure with lossy floating-point compression capability for exascale applications [7].

## 4 Deep Dive

### 4.1 Engine architecture: from BP5 files to SST streams

ADIOS2's engine interface exposes `BeginStep`/`EndStep`/`Put`/`Get` semantics. File engines (BP4/BP5) serialize steps into the self-describing BP format with subfiles per rank (aggregators), achieving high write bandwidth by avoiding global coordination. The streaming engines (SST, DataMan, SSC) implement the *same* step API over the network: `Put` serializes into staging buffers, the control plane matches producer/consumer steps, and the dataplane performs RDMA reads of writer memory by the reader. This duality is what makes engine selection a runtime parameter rather than a code change [4]. The **node-local burst buffer** mode writes subfiles to node-local NVMe and drains them asynchronously to the PFS [2], hiding PFS latency without full in-situ analysis.

> **Theorem (Step-consistency of SST).** *Let $W$ writers and $R$ readers execute the SST protocol with queue-full policy BLOCK. Then every step $s$ produced by the writer cohort is delivered exactly once, in order, to the reader cohort before step $s+1$ is released, and no writer proceeds past $EndStep(s)$ until all readers have consumed step $s$ or the queue-full policy explicitly discards it.*

*Proof sketch.* The rendezvous protocol assigns each step a monotonically increasing sequence number at the writer; the control plane's readiness handshake acts as a distributed barrier per step. RDMA data movement is fenced by the control plane's completion signals, so ordering follows from the barrier semantics. Discard policies are the sole relaxations, and they are opt-in. ∎

### 4.2 The SST rendezvous protocol and UCX dataplanes

The SST control plane solves a distributed coordination problem: $W$ producers and $R$ consumers, unknown to each other at startup, must pair up and stream $S$ steps with flow control. The protocol proceeds in phases: (1) **bootstrap** --- writers publish contact info (hostname, port, RDMA keys) via a shared registry; (2) **handshake** --- readers request connections, and each side learns $W$, $R$, and the rank mapping; (3) **per-step exchange** --- writers announce step metadata (variable extents, offsets), readers issue RDMA read descriptors for the subregions they need (supporting N--M redistribution without writer-side repacking); (4) **release** --- readers signal consumption, freeing writer buffers. The UCX dataplane [1] implements phase (3) with zero-copy RDMA reads/writes and hardware-offloaded atomics, so the CPU cost per byte approaches zero and the achievable bandwidth approaches the fabric's injection limit. This is why SST streaming can feed ML training "with substantially higher bandwidth than the theoretical limits of Frontier's file system" [4]: the comparison is fabric bisection bandwidth versus PFS gateway bandwidth, and the fabric wins by an order of magnitude.

```python
# Minimal ADIOS2 SST streaming pattern (Python high-level API)
import adios2

# Writer (simulation): identical code writes BP5 files if engine="BP5"
with adios2.open("sim_output", "w", engine="SST") as fh:
    for step in fh.steps():          # one step per timestep
        fh.write("temperature", T)   # T: numpy array, no copies to disk
        fh.write("pressure", P)
        fh.end_step()                 # handshake with reader cohort

# Reader (analysis): runs on staging nodes, receives via RDMA
with adios2.open("sim_output", "r", engine="SST") as fh:
    for step in fh.steps():
        T = fh.read("temperature")   # arrives via UCX dataplane
        render_isosurface(T)          # in-transit visualization
        fh.end_step()
```

### 4.3 Catalyst and Ascent: two philosophies of in-situ API

Catalyst 2 and Ascent represent opposite ends of the integration-cost/capability spectrum:

- **Catalyst 2** brings the *full ParaView pipeline* in-situ: arbitrary filters, Cinema extracts, Live connections to a remote ParaView client for steering. The cost is the ParaView dependency stack and the adaptor-writing effort, mitigated by Conduit Blueprint (describe, don't convert) and the simplified three-call API [6]. It has been demonstrated at 256K MPI ranks on PHASTA [2] and is the in-situ backend for codes like PyFR, MPAS-Ocean, and VPIC [10].
- **Ascent** brings *curated actions* with minimal dependencies: the simulation passes a Conduit node and an action list; Ascent executes them using VTK-m/DPP backends where available. The flyweight design targets ECP applications where the full ParaView stack cannot be built or deployed.

Both converge on **Conduit Blueprint** as the lingua franca: a simulation describes meshes, fields, and topologies in a schema both frameworks consume. This standardization is arguably the deepest contribution --- it decouples simulation codes from analysis tools, so a code instrumented once can serve Catalyst, Ascent, or custom consumers interchangeably.

### 4.4 In-situ particle tracing: Lagrangian analysis without the 4D field

Consider a time-varying velocity field on $N$ grid points over $S$ timesteps. Storing the full field costs $O(N \\cdot S)$ floats; for a $4096^3$ grid over $10^4$ steps at double precision, that is on the order of exabytes --- physically unstoreable. Particle tracing reduces the output to $O(P \\cdot S)$ floats for $P$ particles, where $P \\ll N$ typically ($10^5$--$10^7$ seeds). The in-situ algorithm:

1. **Seed** $P$ particles (uniform, random, or feature-guided, e.g., near vorticity maxima).
2. **Advect** each step with the live field using RK2/RK4 with trilinear interpolation --- reusing the simulation's own ghost-cell infrastructure for cross-rank particle migration.
3. **Extract** pathlines, or accumulate derived fields: finite-time Lyapunov exponents from the Cauchy--Green tensor of the flow map, computed via finite differences of neighboring trajectories.

The hybrid BIT1 PIC-MC integration [3] shows the pattern in production: OpenMP-task-parallel particle movers, openPMD streaming API, and ADIOS2 SST in-memory staging let analysts watch particle dynamics evolve in real time. The theoretical payoff is a **temporal-resolution theorem**: in-situ tracing achieves the simulation's native $\\Delta t$ resolution, whereas any post-hoc scheme is limited by the write cadence $k\\Delta t$, aliasing all dynamics faster than $k\\Delta t$.

```cpp
// In-situ particle advection kernel (per rank, per step)
for (Particle &p : local_particles) {
    Vec3 v = trilinear_interpolate(velocity_field, p.x); // live memory
    p.x += dt * v;                                       // Euler/RK step
    if (!domain_contains(p.x)) migrate_particle(p);      // MPI handoff
    if (p.age % sample_every == 0) trace_buffer.push(p); // sparse extract
}
// trace_buffer streams via ADIOS2 SST to the analysis consumer
```

### 4.5 Compression theory: SZ, ZFP, and the error-bounded contract

Lossy compression is only scientifically defensible with a *contract* on distortion. The two dominant scientific compressors offer complementary contracts:

**SZ** [9] predicts each value from its neighbors (Lorenzo predictor or regression), quantizes the prediction residual with linear-scaling quantization, and entropy-encodes the quantization codes. The quantization bin width $2\\epsilon$ guarantees a pointwise error bound $\\lVert x - \\tilde{x} \\rVert_\\infty \\le \\epsilon$ --- an absolute error bound the user sets. Multidimensional prediction exploits the smoothness of physics fields, routinely achieving 10--100x compression on smooth fields.

**ZFP** [7,8] partitions the array into $4^d$ blocks, applies a near-orthogonal decorrelating transform, and encodes bit planes with embedded coding, supporting three modes: *fixed-rate* (bits per value, enabling random access into compressed arrays), *fixed-precision* (bit planes kept), and *fixed-accuracy* (pointwise error bound). ZFP's fixed-rate mode is unique: compressed arrays support $O(1)$ random access, so downstream tools can read subregions without decompressing the whole field --- ideal for in-transit extracts.

> **Theorem (Error-bounded composition).** *If field $F$ is compressed with pointwise bound $\\epsilon_1$ and a derived quantity $Q = \\mathcal{L}(F)$ is $L$-Lipschitz in the compressed norm, then $\\lVert Q(F) - Q(\\tilde{F}) \\rVert \\le L\\epsilon_1$. For linear operators with stencil norm $\\lVert\\mathcal{L}\\rVert$, the derived-field error is bounded by $\\lVert\\mathcal{L}\\rVert\\,\\epsilon_1$.*

This composition bound is why in-situ pipelines compress *before* analysis: as long as the analysis operators are Lipschitz (true for most differential and integral operators on resolved fields), the scientist can budget the total error a priori. ADIOS2's operator framework [2] makes this compositional: attaching a ZFP/SZ operator with a prescribed accuracy to a variable means every downstream consumer inherits the guarantee.

### Break-even analysis: when does in-situ win?

Let $T_{sim}$ be solver time per step, $T_{wr}$ the full-state write time, and $T_{tx} = D/B$ the transfer time. In-situ beats post-hoc whenever $T_{wr}$ exceeds the contention cost $p T_{sim}$ --- true by orders of magnitude at exascale. In-transit additionally beats colocated in-situ when the analysis needs far fewer ranks than the solver (e.g., rendering), avoiding stranded ranks during a serial bottleneck.

### Guarantees

The stack's guarantees compose: (i) **SST step-consistency** (Section 4.1) ensures no step is lost or reordered under BLOCK policy; (ii) **Conduit Blueprint schemas** give type-safe, zero-copy data description, eliminating a class of adaptor bugs; (iii) **error-bounded compression** (Section 4.5) gives a priori distortion budgets. Together they make in-situ pipelines *auditable*: a scientist can state, with proof, that the published figure deviates from the true simulation state by at most $\\epsilon$ in $L_\\infty$.

## 6 Limitations

1. **Temporal irreversibility.** In-situ analysis sees each timestep once. If the analyst later asks a question the pipeline was not instrumented to answer, the data is gone --- there is no rewind. Mitigations (deep temporal buffers, reactive triggers that dump full state on detected events) are heuristic, not complete.
2. **Resource contention.** Tightly-coupled in-situ analysis shares FLOPs, memory bandwidth, and capacity with the solver. Memory-hungry analyses (e.g., global FFTs, large ghost regions for tracing) can degrade solver performance or trigger OOM kills at scale.
3. **Fault tolerance.** A streaming pipeline couples the fate of producer and consumer: if the analysis crashes, the simulation may block (BLOCK policy) or silently lose steps (DISCARD policy). Checkpoint/restart of a *coupled workflow* remains harder than of a single code.
4. **Compression-analysis interaction.** Error bounds compose through Lipschitz operators, but *nonlinear, non-Lipschitz* analyses (thresholding, topological feature extraction, shock detection) can amplify pointwise error unpredictably. Error-bounded compression is not a license to compress before discontinuity-sensitive analysis.
5. **Standardization gaps.** Conduit Blueprint covers common meshes, but particle data and deep AMR hierarchies still require custom adaptors, fragmenting the ecosystem.

---

## 7 Conclusion

The I/O wall is a structural consequence of divergent scaling laws, and no file-system upgrade will close it: the answer is to stop routing science through storage. ADIOS2's SST engine [4] makes streaming a runtime engine choice rather than a rewrite; Catalyst 2 [6] and Ascent bring production-grade in-situ analysis APIs with Conduit as the shared data language; in-situ particle tracing [3] recovers Lagrangian diagnostics at native temporal resolution; and error-bounded compressors SZ [9] and ZFP [7,8] shrink residual traffic with provable distortion budgets. The empirical record --- 10x WRF I/O acceleration [1], beyond-file-system streaming bandwidths [4], 256K-rank in-situ visualization [5] --- shows the stack working at production scale. The remaining work is resilience and standardization: making coupled streaming workflows as routine as writing a file.
