# Optimizing After the Link: Sampling-Driven Profile-Guided Compilation from AutoFDO to BOLT, Propeller, and ThinLTO at Warehouse Scale

## Abstract

Profile-guided optimization has migrated steadily from instrumentation toward sampling and from compile time toward post-link time. This thesis presents the sampling-driven compilation pipeline now standard at warehouse scale: Linux perf with Last Branch Records harvests production profiles at under 2% overhead; AutoFDO converts noisy samples into source-keyed profile forests via DWARF discriminators, yielding roughly 10% speedups without instrumented builds; ThinLTO contributes scalable cross-module optimization through summary-based whole-program analysis and profile-scaled function importing; and post-link optimizers repair the layout decisions that inlining invalidated — BOLT by disassembly-driven binary rewriting (+7% on Meta's HHVM, up to +5% on the Linux kernel) and Propeller by relinking with basic-block sections (1.1%–8% beyond PGO and ThinLTO across Google's fleet, at 30–70% lower memory overhead). We formalize basic-block reordering as a traveling-salesman problem, prove discriminator stability under source edits, quantify fleet-scale impact, and analyze limitations including profile staleness, sampling skid, and binary-rewriting safety.

## 1 Introduction

For three decades, the dominant cost model of program optimization has drifted from the processor back end toward its front end. Arithmetic is nearly free; fetching the *next instruction* is not. Instruction caches have barely doubled in twenty years — 32 KB to 64 KB on mainstream Intel cores — while warehouse-scale binaries have ballooned past a hundred megabytes [6]. When hot code is scattered across that address space, the processor stalls on instruction-cache, branch-target-buffer, and instruction-TLB misses, fetching dead code alongside code executed billions of times.

Compilers have fought this since Pettis and Hansen's 1990 procedure positioning [7]: *place code that executes together, together*. Yet compile-time layout is systematically wrong, because the compiler optimizes a program it has never seen run. Profile-guided optimization (PGO) closes the gap — but classical instrumentation PGO perturbs the measured program, doubles build complexity, and collapses under continuous deployment.

This thesis argues a stronger claim, validated across Meta's and Google's fleets: **the most valuable profile is the one injected latest**. Sampling profilers (Linux `perf` with Last Branch Records) observe production binaries at under 2% overhead; *AutoFDO* converts noisy samples into compiler-grade profiles; *ThinLTO* makes whole-program optimization scale; and post-link optimizers — *BOLT* by rewriting, *Propeller* by relinking — repair layout decisions every earlier stage got wrong. The gains compound: AutoFDO alone yields ~10% [2]; BOLT and Propeller each add several percent *on top of* fully optimized PGO+LTO builds [1][3].

## 2 Background

### 2.1 The front-end bottleneck

Out-of-order cores retire several instructions per cycle only if the front end supplies them. The supply chain — L1 instruction cache, BTB, micro-op cache, instruction TLB — is small and unforgiving. Ayers et al.'s AsmDB study showed front-end stalls are a first-order tax on warehouse workloads, whose flat, enormous instruction working sets defeat caches tuned for tight loops [8]. A hot path spanning 200 distinct 4 KB pages touches 200 iTLB entries; packing it into 20 pages cuts iTLB pressure tenfold and lets 2 MB transparent huge pages cover the region with a single entry.

> **Theorem (Layout locality bound).** Let *H* be the basic blocks executed in a steady-state window and *P(H)* the distinct pages containing them. Front-end stall cycles from instruction fetch are monotone non-decreasing in *P(H)* for fixed |*H*|, since each new page risks a cold iTLB fill and evicts a resident entry. ∎

Minimizing *P(H)* by co-locating hot blocks is therefore a primary optimization objective, not cosmetics.

### 2.2 A lineage of layout optimizers

**Pettis–Hansen (1990)** [7] ordered procedures so callers sit near callees, via greedy clustering over the weighted call graph. Later work refined both granularities — function reordering (temporal ordering, HFSort-style merging) and intraprocedural basic-block placement. LLVM's and GCC's `-freorder-blocks`, and the hot/cold partitioning of `-freorder-blocks-and-partition` (`.text.hot`, `.text.unlikely`) [6], perform local versions at compile time. Their shared flaw is *stale information*: inlining and code growth invalidate the profile the layout was based on, and the compiler never observes the final binary layout at all.

### 2.3 Profiles: instrumentation versus sampling

Classical PGO instruments binaries with edge counters (LLVM IRPGO, GCC `-fprofile-generate`): exact profiles, but 20–50% slowdown, a mandatory second build, and a training workload that must mirror production. **Sampling PGO** inverts the tradeoff: the PMU interrupts every *N* events and records the instruction pointer; with **Last Branch Records**, each sample carries the last 16–32 taken branches — a short *exact* trace. Overhead drops below 2%, profiles harvest continuously from *production* traffic, and no instrumented build exists. The cost is noise — statistical samples, skid displacing attribution — and reconstructing edge frequencies becomes a flow-inference problem. AutoFDO, BOLT, and Propeller are, at bottom, machinery for turning that noise back into signal.

| Profile source | Fidelity | Overhead | Fleet-friendly |
|---|---|---|---|
| Instrumentation (IRPGO) | Exact | 20–50% | Poor |
| `perf` sampling, IP only | Noisy | <1% | Excellent |
| `perf` + LBR branch stacks | High (short exact traces) | 1–2% | Excellent |
| AutoFDO (converted) | Medium–high | 0 (offline) | Excellent |

### 2.4 The pipeline, end to end

1. **Sample** — `perf record -e cycles:u -j any,u` on production binaries.
2. **Compile-time PGO** — *AutoFDO* maps samples to source via debug info; *ThinLTO* adds cross-module optimization at scale.
3. **Post-link layout** — *BOLT* rewrites the linked ELF; *Propeller* relinks via basic-block sections.
4. **Deploy and re-sample** — the optimized binary becomes the next profiling target, closing the loop.

Stage 3 is not polish: because inlining during stages 1–2 destroys the correspondence between profiled and final code, only a post-link pass observes the *actual* binary it optimizes.

## 3 Methodology

### 3.1 Profile collection at fleet scale

At Meta and Google, profiling is infrastructure. Daemons sample production binaries continuously, and profile stores pin samples to binary build IDs so a profile is never applied to a binary it was not collected from — the cardinal rule against stale-profile misoptimization:

```bash
# 1. Sample the production binary (~1-2% overhead, unprivileged)
perf record -e cycles:u -j any,u -F 1000 -- ./workload --benchmark

# 2a. Convert for BOLT
perf2bolt ./workload -p perf.data -o workload.fdata

# 2b. Convert for AutoFDO / Propeller
create_llvm_prof --binary=./workload --profile=perf.data \
    --format=extbinary --out=workload.afdo
```

`perf2bolt` aggregates samples into per-function block and edge counts (`.fdata`); `create_llvm_prof` (in `google/autofdo`) emits the extended-binary AutoFDO profile consumed by both the compiler and Propeller [5].

### 3.2 From samples to source: AutoFDO reconstruction

AutoFDO (Chen et al., CGO 2010 [2]) solves the *attribution problem*: map sampled addresses to stable source-level frequencies. Three insights:

- **Extended source locations** — `(function, file, line, discriminator)` tuples. *Discriminators* distinguish statements sharing a line and, crucially, distinct *inline instances* of one function. Source-keyed profiles survive recompilation; address-keyed ones do not.
- **The profile forest** — per-function trees whose inner nodes are inline instances and leaves are statements, mirroring the profiled binary's inlining.
- **Maximum-frequency aggregation** — debug info in optimized binaries is skewed, so co-located instructions may disagree; AutoFDO takes the *maximum* instruction frequency per location, a robust estimator under mapping noise [2].

Consumed via `-fauto-profile` (GCC) or `-fsample-profile-use` (LLVM), this drives inlining, unrolling, and branch probabilities — the same decisions as instrumentation PGO, at a fraction of the operational cost.

### 3.3 ThinLTO: whole-program analysis without the whole program in memory

Full LTO merges all IR into one module — precise but serial and memory-hungry. **ThinLTO** (Amini et al. [4]) replaces the monolith with *summaries*: each module emits a compact per-function summary (instruction count, references, linkage, profile hotness). The *thin link* performs whole-program analysis over summaries alone — the only serial phase, never touching IR — and fully parallel backends then import only needed functions:

```llvm
; The thin link decides imports from summaries, not IR inspection.
define void @hot_callee() #0 {
entry:
  ret void
}
; Summary (conceptual): instrs=12, refs={@lookup}, hotness=hot,
;   linkage=internal -> import into hot callers
```

Import thresholds are **profile-scaled**: hot call edges justify importing larger callees. AutoFDO hotness flows into summaries, summaries steer importing, and importing creates the large, hot, cross-module functions whose *layout* BOLT and Propeller then perfect. Each stage's output is the next stage's most valuable input.

### 3.4 Post-link passes: repairing layout after the fact

**BOLT** (Panchenko et al., CGO 2019 [1]) treats the linked ELF as its input IR: disassemble each function, rebuild the CFG on LLVM's MC layer, attach the `perf2bolt` profile, and run block reordering (`-reorder-blocks=ext-tsp`), function reordering (`-reorder-functions=hfsort+`), function splitting (`-split-functions`, quarantining cold code in `.text.cold`), plus shrink-wrapping and indirect-call promotion. It then re-emits functions and relinks references internally, rewriting the ELF in place. Because it sees the *final* binary, it observes the cross-function hot chains that inlining created — information compile-time layout never had. It is toolchain-agnostic (GCC or Clang, any linker), supports x86-64, AArch64, and RISC-V, and joined LLVM in 2022 [6].

**Propeller** (Shen et al., ASPLOS 2023 [3]) reaches the same destination by *relinking instead of rewriting*. Compiling with `-fbasic-block-sections=labels` labels every block and records the CFG in the object file — no disassembly needed. Propeller's whole-program analysis combines the AutoFDO profile with these labels, computes the desired order, and simply relinks with `lld`. Relinking composes with caching and distributed build actions: no monolithic rewrite, no disassembler to confuse with hand-written assembly.

> **Theorem (Late-injection dominance, informal).** Let *L₁* be compile-time PGO layout and *L₂* post-link layout from a profile of the final binary. Whenever inlining or code growth changes the executed bytes between profiling and linking — the common case — the profile informing *L₂* has strictly smaller staleness error, so the expected front-end cost of *L₂* is no worse and typically strictly better. This is the formal content of the "two-step pipeline" in [1]: PGO for inlining, post-link for layout. ∎

### 3.5 Interaction with huge pages

Packing hot code into contiguous pages shrinks the iTLB working set, makes 2 MB transparent huge pages dramatically more effective (one entry covering a region that spanned dozens of 4 KB pages), and reduces `khugepaged` promotion churn. Function splitting amplifies this: cold code in `.text.cold` never shares a page with hot code, so huge-page promotion of the hot region is never blocked by a cold byte. LLVM's kernel-BOLT documentation attributes up to **5%** system-performance improvement to these layout effects [9].

## 4 Deep Dive

### 4.1 LBR: how hardware tells the truth

PMU sampling suffers **skid** — pipeline delay between counter overflow and interrupt — smearing attribution by a few instructions: harmless for hot functions, dangerous for hot edges. LBR fixes this: each sample carries the last 16–32 taken branches as exact (source, destination) pairs. Millions of such micro-traces reconstruct edge frequencies by counting, and `perf2bolt`/`create_llvm_prof` then run **flow-conservation repair** — incoming sample mass must equal outgoing mass at every block — to distribute counts onto unobserved edges. Residual noise perturbs only the *ranking* of lukewarm edges, which layout heuristics barely depend on. The hardware does the tracing; the software only denoises.

### 4.2 AutoFDO: why source-keyed profiles survive

The deepest idea in [2] is keying profiles by what the *source* defines. Binary addresses shift with every compiler version and inlining decision; extended source locations do not. The converter walks DWARF, recovers each sampled address's inline stack via `DW_TAG_inlined_subroutine` chains, and assigns discriminators so two dynamic instances of one line are distinct keys. Staleness is then *graceful*: unmatched locations are ignored, never misapplied — the property that makes continuous fleet profiling sound. Empirically, [2] reports binaries on average **10% faster** than non-FDO builds, a figure replicated across Google's fleet for over a decade.

### 4.3 Block reordering as a traveling salesman problem

Given a CFG with weighted edges, the layout problem asks for a linear block order minimizing expected transfer cost: fall-through ≈ 0, short forward branches small, long jumps large (destroyed i-cache/TLB locality). This is a **TSP on the CFG** — NP-hard — so production systems use heuristics:

- **Pettis–Hansen (1990)** [7]: greedy clustering over the weighted call graph, merging the heaviest edge's endpoints — still the core of function reordering.
- **Ext-TSP** (BOLT's default): a distance-sensitive TSP variant rewarding hot branch targets placed *near* the branch, with reward decaying in distance; greedy chain construction plus 2-opt-style local search lands within noise of optimal on real CFGs.
- **HFSort+** (BOLT's function reorder): hierarchical merging on call frequencies and temporal affinity.

```llvm
; AutoFDO branch weights let the backend — and later BOLT — keep the
; hot successor as fall-through and move the cold path out of line:
define i32 @dispatch(i32 %c) {
entry:
  %t = icmp eq i32 %c, 0
  br i1 %t, label %hot_path, label %cold_path, !prof !0
hot_path:
  ret i32 1
cold_path:
  ret i32 0
}
!0 = !{!"branch_weights", i32 9500, i32 500}
```

The decisive point: the compiler lays out the *pre-inlining* CFG, but after inlining the true hot chains run *across* former function boundaries — chains only a post-link pass ever sees.

### 4.4 Propeller's relinking pipeline in detail

Propeller's build is a choreography across three parties. The compiler emits labeled basic-block sections (`-fbasic-block-sections=labels -funique-internal-linkage-names`, the latter improving profile fidelity [5]). The profile converter turns `perf.data` into an AutoFDO profile plus a *propeller profile* mapping labels to execution counts. Whole-program analysis then runs the same layout algorithms as BOLT — ext-TSP within functions, HFSort across them — but emits a *link order* instead of a rewritten binary, and `lld` materializes it. Because relinking is an ordinary build action, it is cacheable, distributable, and incremental: change one translation unit and only its link order recomputes. Google's ASPLOS paper reports **1.1%–8% beyond PGO and ThinLTO** (7% on Clang, 1% on MySQL), with tens of millions of cores running Propeller-optimized code and **30–70% lower** single-machine peak memory than BOLT [3].

### 4.5 BOLT versus Propeller: the engineering tradeoff

| Dimension | BOLT [1] | Propeller [3] |
|---|---|---|
| Input | Linked ELF | Objects + profile |
| CFG recovery | Disassembly + MC heuristics | Block-section labels; no disassembly |
| Toolchain coupling | None (GCC/Clang, any linker) | Clang + LLD |
| Materialization | In-place rewrite | Relink |
| Peak memory, huge binaries | High (monolithic) | 30–70% lower [3] |
| Incremental / distributed builds | Poor fit | Native fit |
| Extra transforms | Shrink-wrap, ICP, branch folding | Layout-focused; prefetch-insertion prototype [10] |

BOLT optimizes *anything* — third-party libraries, JIT runtimes, the kernel itself — needing only a binary and a profile: Meta's fleet (HHVM **+7%**, TAO, Proxygen, Multifeed [1][6]) and the kernel work [9] show the breadth. Propeller optimizes only what your toolchain builds, but as a build action. The two are converging: Propeller is being upstreamed into LLVM, and its framework now hosts experiments like automatic `PREFETCHIT0/1` insertion on Intel Granite Rapids and AMD Turin [10].

## 5 Empirical Results and Formal Guarantees

The evidence is unusually strong because it was measured on revenue-generating fleets, not just benchmarks.

| Workload | Stack | Reported gain | Source |
|---|---|---|---|
| Google warehouse apps | AutoFDO | ~10% vs non-FDO | [2] |
| HHVM (Meta) | PGO + BOLT | +7% | [1][6] |
| Linux kernel | BOLT | up to +5% | [9] |
| Clang | PGO + ThinLTO + Propeller | +7% beyond | [3] |
| MySQL | PGO + ThinLTO + Propeller | +1% beyond | [3] |
| SPEC cpu2006 + large apps | ThinLTO | ≈ full LTO | [4] |

Critically, the BOLT and Propeller numbers are measured *on top of* binaries already built with full LTO and PGO — the strongest available baseline — via the two-step pipeline (PGO for inlining decisions, post-link for layout) advocated in [1].

> **Theorem (NP-hardness of optimal layout).** The decision version — is there a linear block order with weighted transfer cost below *K*? — is NP-hard, by reduction from TSP: cities become blocks, tour edges become hot CFG edges, fall-through cost encodes tour length. All production systems are therefore necessarily heuristic; the engineering question is heuristic quality per millisecond, not optimality. ∎

> **Theorem (Discriminator stability).** In AutoFDO's profile forest, editing the statement at extended source location *ℓ* leaves every key *ℓ′ ≠ ℓ* unchanged, since keys are source-derived, not address-derived. Profiles thus remain *applicable* across edits that invalidate every address-keyed profile [2]. ∎

## 6 Limitations

**Representativeness.** Profiles describe the past. Traffic shifts, new features, and diurnal patterns can make yesterday's profile actively harmful; continuous re-profiling and build-ID pinning mitigate, but the hazard is structural.

**Sampling noise and skid.** LBR tames skid, yet rare edges stay poorly estimated and short-lived processes never accumulate enough samples. Heuristics tolerate ranking noise but not systematically missing edges.

**Rewriting safety.** BOLT must preserve unwinding tables, jump-table semantics, CET/IBT landing pads on x86, and pointer authentication / BTI on AArch64. Hand-written assembly and function-pointer deltas demand conservative heuristics; the input requirements (unstripped symbol table, ideally `--emit-relocs`) are explicit [6]. Propeller sidesteps this by never disassembling — at the price of toolchain lock-in.

**Debuggability and size.** Rewritten debug info is imperfect for highly optimized code; BOLT can grow binaries (`-use-old-text` mitigates); split functions complicate stack traces; Propeller's block sections inflate objects pre-link.

**Build complexity.** Sample → convert → AutoFDO-compile → ThinLTO → post-link → redeploy → re-sample is a multi-stage distributed workflow [5]. For small projects the operational cost can exceed the gains — these are unapologetically warehouse-scale technologies.

**Diminishing returns.** Layout, inlining, and prefetching interact non-additively. The honest numbers above use the strongest baselines; MySQL's +1% shows that when front-end pressure is not the binding constraint, layout cannot manufacture one.

## 7 Conclusion

The arc of profile-guided compilation bends toward later injection. Instrumentation PGO proved runtime knowledge beats static heuristics; AutoFDO proved sampling supplies that knowledge at fleet scale; ThinLTO proved whole-program optimization need not be monolithic; BOLT and Propeller proved the final word on layout belongs to whoever sees the final binary. Optimization spent decades as a static discipline — analyze the source, predict the hardware, hope; the sampling pipeline inverts it into an empirical one: *measure the hardware, then compile*. The frontier — interprocedural block layout (cf. AI-Propeller's evolved heuristics [11]), automatic prefetch insertion [10], co-design with huge-page management — suggests the compounding logic has not run its course. Each stage corrects the last; the only question is how many stages we can afford.
