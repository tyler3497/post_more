# Capability Hardware Enhanced RISC Instructions: Hardware-Enforced Memory Safety via Fat-Pointer Capabilities, Monotonicity, and Compartmentalization

## Abstract

Capability Hardware Enhanced RISC Instructions (CHERI) is a hybrid capability-system architecture that extends conventional 64-bit RISC ISAs with hardware-enforced fat-pointer capabilities, embedding bounds, permissions, sealing, and an out-of-band integrity tag in every pointer. This thesis develops the architectural, formal, and empirical account of CHERI: capability monotonicity and provenance guarantees that make pointers unforgeable; sealed-capability invocation enabling fine-grained, low-overhead software compartmentalization; CHERI Concentrate bounds compression; the CHERI-RISC-V ISA instantiation; and the Arm Morello prototype, an industrial-scale demonstrator backed by formally verified security properties. We examine the porting of operating systems to the capability model, centering on CheriBSD's hybrid and pure-capability modes, and survey measured performance overheads from Morello silicon and FPGA studies. CHERI's decisive contribution is the composition of spatial memory safety and scalable compartmentalization in a single architectural primitive, adoptable through recompilation of existing C and C++ code bases with minimal source modification.

## 1. Introduction

Memory unsafety in C and C++ remains the dominant source of exploitable vulnerabilities in systems software. Buffer overflows, use-after-free errors, and out-of-bounds reads and writes have persisted for four decades despite compilers, static analyzers, sanitizers, and operating-system mitigations. The root architectural defect is that pointers in commodity ISAs are *integers with intent*: the address space is flat, pointers are forgeable by arithmetic, and no hardware mechanism constrains a pointer to the object it was meant to reference. Software mitigations — stack canaries, ASLR, control-flow integrity — are statistical or partial, and spatial safety instrumentation in software (e.g., AddressSanitizer) imposes overheads of 2x or more that preclude always-on deployment [8].

CHERI answers this defect architecturally. Developed by the University of Cambridge and SRI International under DARPA sponsorship [1][2], CHERI is a *hybrid capability-system architecture*: it retains the conventional flat virtual address space and MMU-based virtualization, but replaces raw pointers with **architectural capabilities** — unforgeable tokens of authority that combine an address with hardware-checked bounds, permissions, an object type for sealing, and a one-bit integrity tag held out of band in tagged memory. A capability cannot be fabricated by casting an integer; it can only be *derived* from an existing capability through instructions that enforce **monotonicity** (authority may only decrease) and preserve **provenance** (every capability traces to a root of trust). The result is deterministic, non-probabilistic spatial memory safety enforced on every load, store, and instruction fetch, composable with conventional protection domains and available to unmodified source code through recompilation.

The significance of CHERI extends beyond memory safety to **software compartmentalization**. Because capabilities are first-class and sealed capabilities can be invoked atomically, CHERI supports fine-grained least-privilege decomposition of software at costs orders of magnitude below MMU-based isolation. This thesis treats CHERI as a complete system: ISA semantics, formal security properties, the CHERI-RISC-V instantiation, the Arm Morello prototype — a high-performance industrial demonstrator with formally verified security properties [3][5] — operating-system adaptation in CheriBSD [6], and measured performance [4].

## 2. Background

### 2.1 From capabilities to CHERI

Capability-based addressing descends from the 1960s–1970s capability systems (Dennis and Van Horn, CAL-TSS, HYDRA, the Cambridge CAP computer, IBM System/38): references to objects were unforgeable tokens interpreted by hardware, and security policy reduced to the distribution of capabilities. Classical capability machines, however, demanded entirely new software stacks and were widely judged incompatible with the flat, pointer-rich programming models of C. CHERI's insight is *hybridization*: keep the commodity ISA, the virtual memory system, the ABI, and the toolchain, and introduce capabilities as an enriched pointer representation alongside — and ultimately in place of — integer pointers [1].

CHERI extends the ISA with a capability register file (merged into the general-purpose register file in current designs), tagged memory (one tag bit per capability-sized, capability-aligned granule), and capability-aware instructions. Pointers in *pure-capability* C and C++ are 128-bit capabilities; in *hybrid* mode, ordinary integer pointers continue to work, constrained by a default data capability (DDC), while selected pointers are capabilities [2][6].

### 2.2 Threat model and design goals

CHERI assumes an attacker with arbitrary read/write capability over the vulnerable program's data memory — the standard spatial-safety adversary — and seeks to prevent that attacker from (a) accessing memory outside any legitimately held object's bounds, (b) forging authority not granted by the program, or (c) escalating permissions. Goals include *incremental adoptability* (recompile, don't rewrite), *low performance overhead* for memory protection, *dramatic* improvement in compartmentalization cost, *formal grounding* of security properties, and *programmer-friendly underpinnings* for least privilege and intentional use [2].

### 2.3 Prior art in hardware memory safety

Fine-grained protection tables (Mondrian Memory Protection), hardware fat pointers (Hardbound), and Intel MPX each attempted per-pointer bounds enforcement. MPX's table-based design was deprecated by Intel after performance and usability failures; Hardbound's fat pointers lacked the permission/sealing model and required similar software changes without the compartmentalization story. CHERI subsumes these by making the capability — with bounds, permissions, sealing, and monotonic derivation — the *architectural* unit of reference, enforced in the microarchitecture's critical path rather than in software tables [1].

## 3. Methodology

This thesis proceeds by architectural analysis grounded in the primary CHERI literature and technical reports: the original CHERI research-platform report [1], the current ISA specification (Version 9, with Version 8 [2] elaborating the Morello-relevant feature set), the Morello evaluation platform description [3], Morello performance studies [4], the formal verification program [5], the CheriBSD system description [6], and secondary quantitative studies [7][8].

We reconstruct the protection model from first principles — capabilities, monotonicity, provenance, sealing — and examine each mechanism's hardware encoding, ISA semantics, and software consequences. We then trace the two principal instantiations: **CHERI-RISC-V**, the current reference architecture replacing CHERI-MIPS [1][2], and **Arm Morello**, the industrial prototype. Operating-system porting is analyzed through CheriBSD's hybrid and pure-capability ABIs. Performance claims are evaluated against published SPECint measurements on Morello silicon and FPGA, and against the CHERI-SIMT study's overhead accounting [4][7]. Throughout, we state where results are formally proven (ISA-level noninterference-style properties, Morello's verified security goals [5]) versus empirically measured.

## 4. Deep Dive

### 4.1 The capability as a fat pointer: representation and tagged memory

A CHERI capability is a 128-bit value (in the canonical 64-bit-address configuration) comprising an address, compressed bounds (base and top), a permissions mask, an object type field, and reserved bits, plus a single **tag bit** stored out of band in tagged memory and propagated through the register file. The tag is the linchpin of unforgeability: it is set only by legitimate capability-creating or capability-copying operations, and any non-capability-aware write to the memory granule — or any bitwise manipulation that violates capability invariants — clears it. A capability whose tag is clear cannot be dereferenced or used as an authority-bearing operand; it is merely data.

Bounds compression uses **CHERI Concentrate**, a floating-point-inspired encoding that stores base and top relative to the address with an exponent, achieving precise bounds for small objects and gracefully degrading precision for very large ones, all within the 128-bit budget [2]. Permissions include *Permit_Load*, *Permit_Store*, *Permit_Execute*, *Permit_Load_Capability* / *Permit_Store_Capability* (authority to move capabilities, the basis of capability *distribution* control), *Permit_Seal* / *Permit_Unseal*, and *Access_System_Registers* [2].

> **Theorem:** *(Capability unforgeability.)* In the CHERI abstract protection model, no execution can produce a tagged capability whose authority exceeds that of the capabilities from which it was derived, nor synthesize a tagged capability from non-capability data. *Proof sketch.* Tags are cleared by any store not performed through a capability with `Permit_Store_Capability`, and by all ALU operations on capability operands except the whitelisted monotonic derivation instructions; the ISA's formal model in Sail/Isabelle establishes this as a preservation invariant over all transitions [2][5].

Representative capability semantics can be sketched functionally:

```haskell
-- Abstract capability derivation: monotonicity is enforced by construction
data Permission = Load | Store | Execute | LoadCap | StoreCap | Seal | Unseal
data Capability = Cap { addr   :: Word64
                     , base   :: Word64
                     , top    :: Word64
                     , perms  :: Set Permission
                     , otype  :: Maybe ObjectType
                     , tag    :: Bool }

narrow :: Capability -> Word64 -> Word64 -> Set Permission -> Maybe Capability
narrow c b t p
  | not (tag c)              = Nothing              -- unforgeable: untagged input
  | b < base c || t > top c  = Nothing              -- bounds may only shrink
  | not (p `isSubsetOf` perms c) = Nothing          -- permissions may only drop
  | otherwise                = Just c { base = b, top = t, perms = p }
```

The Haskell sketch captures the essential discipline: every derivation is a *restriction*, never an amplification [2].

### 4.2 Monotonicity and provenance

**Monotonicity** — the rule that capability-manipulating instructions can only narrow bounds, reduce permissions, and never set the tag — is CHERI's central security invariant. It guarantees that a compartment or library handed a capability for a buffer can never parlay it into access to adjacent memory or elevated rights. **Provenance** complements it: every valid capability is transitively derived from a root capability (ultimately, the initial capabilities provided at process or domain creation, such as PCC and DDC), and the ISA maintains this chain by clearing tags on any operation that would break the derivation discipline. Notably, current CHERI designs clear the tag rather than raising an exception on non-monotonic manipulation attempts, simplifying speculative microarchitectures [2].

Provenance has semantic consequences for the C language itself. The ASPLOS 2024 work on the formal mechanized semantics of CHERI C shows that pointer provenance — which allocation a pointer is *derived from* — must be part of the language's defined behavior to justify CHERI's hardware checks, resolving long-standing ambiguities about out-of-bounds pointer construction in C [5].

A concrete enforcement example in the Linux-adjacent CHERI C dialect:

```c
/* Pure-capability C: p is a capability; hardware checks every access */
char *p = malloc(64);          /* capability: bounds [p, p+64), RW */
p[63] = 'x';                   /* OK: within bounds */
p[64] = 'y';                   /* TRAP: capability bounds violation */
uintptr_t i = (uintptr_t)p;    /* provenance-carrying integer cast... */
char *q = (char *)i;           /* ...round-trips only via provenance rules */
char *r = (char *)0x1000;      /* untagged: tag clear, cannot dereference */
```

The bounds violation raises a synchronous capability exception (`CP2`/`CHERI` trap), which CheriBSD delivers as `SIGPROT`, terminating the offending compartment rather than permitting exploitation [6].

### 4.3 Sealed capabilities and compartmentalization

Sealing binds a capability to an **object type**, rendering it non-dereferenceable until unsealed with a matching unseal authority. Sealed *pairs* of code and data capabilities constitute **sealed capability invocations**: the `CInvoke` (or Morello `BLRS`) instruction atomically unseals both, installs the code capability as the new PCC and the data capability as the new IDC/DDC, and transfers control — a hardware domain transition with no kernel involvement [2][3].

This yields compartmentalization at *function-call* granularity and cost. Traditional MMU-based isolation pays TLB shootdowns, page-table switches, and system-call round trips; CHERI compartment switches cost on the order of a hundred cycles. The security property is strong: sealed entry points expose exactly the authority encoded in the sealed data capability, and the callee cannot retain or amplify that authority beyond the call (monotonicity again), nor can the caller forge entry points (unforgeability). The architecture thus supports both *library compartmentalization* (sandboxing untrusted parsers, codecs, protocol handlers) and *application compartmentalization* (mutually distrustful components), all expressible in a capability-aware userspace runtime (`libcheri`) [2][6].

```rust
// Conceptual model of a sealed invocation (illustrative, not Morello asm)
struct SealedEntry { code: SealedCap, data: SealedCap, otype: u32 }

fn cinvoke(entry: SealedEntry, args: &[u64]) -> Result<u64, Trap> {
    // Hardware atomically: check tags, check otypes match,
    // unseal both, install PCC <- code, IDC <- data, jump.
    // Software CANNOT emulate this without privilege: the
    // unseal authority for `otype` is not held by the caller.
    if !entry.code.tagged() || !entry.data.tagged() { return Err(Trap::TagViolation); }
    if entry.code.otype() != entry.data.otype()      { return Err(Trap::SealMismatch); }
    Ok(unsafe { hardware_domain_transition(entry, args) })
}
```

Compartment identifiers (CIDs), exposed via `CGetCID`/`CSetCID` and a `Permit_Set_CID` permission, additionally allow the microarchitecture to partition branch predictors and other structures by compartment, mitigating cross-compartment Spectre-style leakage — a deliberate co-design of architectural and microarchitectural security [2][3].

### 4.4 CHERI-RISC-V and the Arm Morello prototype

**CHERI-RISC-V** is the current reference instantiation, substantially elaborated toward standardization: merged register files, capability-aware load/store and jump instructions, exception handling with capability cause registers, and the compressed-capability encoding integrated with RISC-V's variable-length instruction fetch [2]. It supersedes CHERI-MIPS as the primary vehicle for ecosystem work.

**Arm Morello** is the industrial-scale validation: a CHERI-enabled prototype CPU based on Arm's Neoverse N1, delivered as a full SoC and development board under the UKRI Digital Security by Design programme [3]. Morello implements the CHERI ISAv8-class feature set in a high-performance out-of-order multiprocessor with speculative execution, caches, and a full software stack — a scale unreachable by FPGA prototypes or Sail emulators. Critically, the Morello ISA carries *formally verified security properties*: the ESOP 2022 work proved capability monotonicity and related invariants of the Morello specification in Isabelle/HOL, directly against the Arm architecture model [5]. The Morello programme also published explicit architectural security goals and known limitations [3], an unusual and commendable transparency.

Key Morello facts: `C64` 129-bit capabilities, capability-aware `ADRP`/`LDR` sequences for globals, capability branch prediction (with noted prototype limitations), and compartment-aware microarchitectural tagging hooks [3][4].

### 4.5 Porting operating systems: CheriBSD

CheriBSD — a CHERI-adapted FreeBSD — is the reference OS port and the deepest study of what capability hardware demands of system software [6]. It operates in two modes:

| Aspect | Hybrid ABI | Pure-capability ABI |
|---|---|---|
| Pointer size | 64-bit integers + selected capabilities | 128-bit capabilities everywhere |
| Spatial safety | Opt-in per pointer | Complete (stack, heap, globals) |
| Kernel changes | DDC-bounded legacy pointers; capability-aware pmap, copyin/out | Capability-aware throughout; `SIGPROT` on violation |
| Compatibility | Runs unmodified binaries via DDC | Requires recompilation; stronger guarantees |
| Compartmentalization | Available via `libcheri` | Native; per-library domains |

Porting lessons are substantive. The kernel required a machine-independent/machine-dependent split for capabilities, capability-aware boot and exception code, pmap changes for tagged-memory management, and a capability-safe `copyin`/`copyout` path. Userspace required a new dynamic linker (`rtld`) that enforces *secure linking* — PLT/GOT entries as capabilities so that control-flow and data-flow integrity hold across DSO boundaries — plus capability-aware C startup code and libc [6]. The hybrid kernel mode proved the incremental-adoption thesis: legacy binaries run, bounded by DDC, while capability-aware components gain fine-grained protection.

## 5. Empirical Evaluation and Proofs

### 5.1 Formal verification

CHERI is among the most formally scrutinized architectures in existence. The Sail ISA models generate Isabelle/HOL definitions used to *prove* ISA-level security properties: capability monotonicity, the absence of privilege escalation through capability manipulation, and correct handling of sealed invocation [5]. For Morello specifically, Bauereiss et al. (ESOP 2022) verified the security properties of the actual Arm prototype architecture model — the first machine-checked proof of full-scale architecture security properties for a commercial-class processor design [5]. The ASPLOS 2024 CHERI C semantics work closes the loop to the programming language, giving compiler and programmer a sound provenance model [5].

### 5.2 Performance: Morello silicon and FPGA studies

The headline empirical question is overhead. The Morello early-performance technical report (UCAM-CL-TR-986) measured SPECint on prototype silicon and FPGA variants under multiple code-generation models [4]:

| Configuration | Approx. overhead vs. baseline | Notes |
|---|---|---|
| Hybrid ABI (Morello) | ~0–5% | Integer pointers bounded by DDC |
| Pure-capability ABI (early) | ~10–25% geomean | 128-bit pointers; unoptimized codegen |
| Benchmark ABI (integer branches) | Lower | Weakens control-flow protection; for evaluation only |
| Compartment switch (CInvoke-class) | ~10^2 cycles | vs. ~10^3–10^4 for MMU process isolation |

The report is candid about prototype artifacts: capability branch prediction was unoptimized (PCC metadata stalls on `BL`/`BLR` and `ADRP` sequences), and the "benchmark ABI" deliberately relaxes security to model second-generation microarchitectural expectations [4]. The direction of travel is clear — overheads are dominated by fixable microarchitectural immaturity, not by the protection model.

Independent corroboration comes from the CHERI-SIMT study, which extended a SIMT GPGPU core with CHERI and, via targeted techniques, reduced register-file storage overhead from 103% to 7%, logic-area overhead by 44%, and execution-time overhead to **1.6%**, versus 34% for software bounds checking on the same benchmarks [7]. The lesson generalizes: capability checks are cheap when co-designed with the pipeline; software-only bounds checking is not.

### 5.3 Security evaluation

Morello's evaluation program subjected the platform to adversarial assessment under the Digital Security by Design programme, and the published architectural security goals document enumerates both guarantees and *known limitations* — including temporal safety (use-after-free), which CHERI's spatial model does not address without extensions such as Cornucopia-style revocation or quarantine [3]. This honesty about the threat-model boundary is itself a methodological contribution: CHERI claims deterministic *spatial* safety and least-privilege compartmentalization, not total memory safety.

## 6. Limitations and Open Problems

1. **Temporal safety.** CHERI capabilities enforce spatial bounds, not lifetime. Use-after-free remains exploitable unless the allocator quarantines or revokes capabilities (e.g., Cornucopia's sweeping revocation), an area of active research with real performance cost [3].
2. **Pointer size and ABI disruption.** 128-bit pointers double pointer-heavy memory footprints, alter struct layouts, and break ABIs that assume `sizeof(void*) == sizeof(long)`. CHERI Concentrate mitigates encoding cost, but ecosystem churn (recompilation of the world, new ABIs) is the price of pure-capability deployment [2][4].
3. **Compartmentalization programming model.** Hardware makes domain crossing cheap; software still must decide compartment boundaries, manage sealed entry-point distribution, and avoid confused-deputy patterns at the interface. `libcheri`-style runtimes are young, and large-scale compartmentalized applications remain rare [6].
4. **Side channels.** CHERI is an *architectural* protection mechanism; speculative and microarchitectural leakage (Spectre-class) requires the CID-tagging co-design and disciplined microarchitecture. The Morello report's candor about prototype branch-prediction gaps illustrates the distance between ISA guarantees and silicon reality [2][4].
5. **Formal gaps.** Proofs cover the ISA and its security properties; the C/C++ language semantics, compiler correctness, and the full CheriBSD trusted computing base are only partially verified [5][6].
6. **Adoption economics.** CHERI demands new silicon. Unlike software mitigations, it cannot be deployed by patch — its protection is predicated on hardware ubiquity, making the transition a decade-scale industrial effort [3].

---

## 7. Conclusion

CHERI reframes memory safety as an *architectural* contract rather than a software aspiration. By making every pointer a hardware-checked capability — bounded, permissioned, sealable, tagged, and governed by monotonicity and provenance — it converts the two largest classes of systems vulnerability, spatial memory errors and over-privileged components, into violations the processor refuses to execute. The research program's distinctive strength is its vertical completeness: a formal ISA model with machine-checked proofs [5], a standardizing RISC-V instantiation [2], an industrial prototype in Arm Morello with published security goals [3], measured performance within striking distance of baseline [4][7], and a full operating system in CheriBSD demonstrating incremental adoptability [6].

Open problems — temporal safety, ABI transition cost, compartment design methodology, side-channel co-design, and the economics of new silicon — are substantial but well-posed, each with active research lines. The central thesis stands: *capabilities, hybridized into commodity ISAs, are the most credible path yet demonstrated to deterministic spatial memory safety and scalable least-privilege compartmentalization for the world's existing C and C++ code.*
