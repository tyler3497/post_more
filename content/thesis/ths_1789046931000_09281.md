# Demand-Driven Pointer Analysis via CFL-Reachability: the Andersen–Steensgaard Spectrum, Sparse Value-Flow Graphs, and Context Sensitivity

## Abstract

Pointer analysis — statically determining which heap objects each pointer may reference — underpins bug detection, security auditing, and compiler optimization, yet remains provably hard: even on-demand Andersen queries admit no sub-cubic combinatorial algorithm under the BMM hypothesis [2]. This thesis unifies the field around three axes: (i) **CFL-reachability**, encoding interprocedural pointer reasoning as Dyck-language reachability over labeled graphs [1]; (ii) **demand-driven** analysis, answering only the queries a client asks via lazy CFL-reachability with refinement-based context sensitivity [4][5]; and (iii) the **Andersen–Steensgaard spectrum**, from subset constraints to union-find equality, in its modern sparse reformulation via **value-flow graphs** [8]. We prove the Dyck encoding of Andersen-style analysis, derive the cubic-hardness results, characterize Steensgaard as a regular-language collapse of the Dyck structure, and show how full-sparse SSA value-flow graphs recover flow sensitivity without per-program-point blowup. We close with soundness gaps — native code, reflection, concurrency — and open problems in scalable context sensitivity.

## 1 Introduction

Few static analyses are as central as *pointer analysis*. Whenever a program manipulates the heap, the question "which objects can this pointer reference?" must be answered before dataflow can be made precise, before a call graph can be resolved, and before a security auditor can trace attacker-controlled data to a sink [6][9]. The difficulty is well documented: the problem is undecidable in fully precise form, and even flow-insensitive, context-insensitive Andersen-style analysis is provably hard — recent fine-grained results show even *on-demand* queries admit no sub-cubic combinatorial algorithm under the Boolean Matrix Multiplication hypothesis [2].

Yet the field has not stood still. Three intellectual threads, each deep in its own right, have converged into a surprisingly coherent picture:

1. **CFL-reachability** (Reps, Horwitz, Sagiv, 1995 [1]): interprocedural dataflow problems with *matched* structure — calls/returns, field stores/loads — can be encoded as reachability in a graph whose edge labels must form a word in a context-free language (typically a Dyck language of balanced parentheses). Pointer analysis, it turns out, is a canonical instance.
2. **Demand-driven analysis** (Sridharan et al., OOPSLA 2005 [4]): rather than computing the whole points-to relation exhaustively, answer only the queries a client actually asks — a form of *lazy* computation over the same CFL-reachability substrate, with a refinement-based path to context sensitivity (PLDI 2006 [5]).
3. **Sparsity** (Sui, Ye, Xue, Yew, APLAS 2011; Shi et al., PLDI 2018 [8]): by routing propagation through *sparse value-flow graphs* rather than dense constraint graphs, one recovers flow- and even path-sensitivity at a fraction of the traditional cost.

This thesis synthesizes these threads. Our contributions are expository and technical: a precise Dyck-language encoding of Andersen-style points-to analysis (§4.1), a demand-driven query algorithm with correctness argument (§4.2), a formal characterization of the **Andersen–Steensgaard spectrum** as a hierarchy of language restrictions (§4.3), the sparse value-flow reformulation (§4.4), and a treatment of context sensitivity as extended-Dyck reachability (§4.5). We close with measured empirical claims, limitations, and open directions.

## 2 Background

### 2.1 Points-to analysis: the problem

Given a program with pointer variables $V$ and allocation sites (abstract heap objects) $O$, a *may* points-to analysis computes, for each $p \in V$, a set $\mathit{pt}(p) \subseteq O \cup V$ over-approximating the locations $p$ may reference at runtime. Soundness requires:

> **Theorem:** *(Soundness of may-points-to.)* For every execution and every program point, if pointer $p$ holds the address of concrete object $o$ at runtime, then the abstract object $\alpha(o)$ belongs to $\mathit{pt}(p)$.

The abstraction $\alpha$ is almost always *allocation-site abstraction*: all objects allocated at the same syntactic site are merged. This already introduces imprecision, but it makes the problem finite and decidable.

Flow-insensitive, context-insensitive points-to analysis is specified by four constraint families over a tiny normalized language:

| Statement | Andersen constraint | Steensgaard constraint |
|---|---|---|
| `p = &o` (alloc) | $\{o\} \subseteq \llbracket p \rrbracket$ | $\ast p \sim o$ |
| `p = q` (copy) | $\llbracket q \rrbracket \subseteq \llbracket p \rrbracket$ | $p \sim q$ |
| `p = *q` (load) | $\forall o \in \llbracket q \rrbracket:\ \llbracket o \rrbracket \subseteq \llbracket p \rrbracket$ | $p \sim \ast q$ |
| `*p = q` (store) | $\forall o \in \llbracket p \rrbracket:\ \llbracket q \rrbracket \subseteq \llbracket o \rrbracket$ | $\ast p \sim q$ |

**Andersen's analysis** [3] uses *subset* (inclusion) constraints and computes their least solution — precise in direction but cubic in the worst case. **Steensgaard's analysis** [7] replaces inclusion with *equality* (unification), collapsing variables into equivalence classes with a union-find structure — almost-linear time, at the cost of merging points-to sets bidirectionally [6].

### 2.2 CFL-reachability

*Context-free language reachability* generalizes ordinary graph reachability: given a directed graph $G = (V, E)$ with edge labels from an alphabet $\Sigma$ and a context-free language $L \subseteq \Sigma^*$, determine all pairs $(u, v)$ such that some path from $u$ to $v$ spells a word in $L$. Reps et al. [1] showed that a large class of interprocedural dataflow problems — including IFDS/IDE problems — reduce to CFL-reachability where $L$ is a **Dyck language**: words of balanced parentheses $({}_i, ){}_i$ indexed by call sites or field names. The index enforces *matching*: a return must pair with its own call, a field load with a store to the *same* field. This matching is exactly what distinguishes precise interprocedural analysis from its context-insensitive shadow, in which any call may return to any caller.

### 2.3 Demand-driven analysis

Exhaustive analysis computes $\mathit{pt}(p)$ for *all* $p$. In practice, clients ask about a handful of pointers — e.g., the arguments of a security-critical sink. **Demand-driven** (on-demand) analysis answers queries $q_1, \dots, q_k$ while exploring only the subgraph relevant to them [4]. Crucially, on-demand does *not* improve worst-case complexity — the cubic bottleneck persists even for constant-size outputs [2] — but it yields dramatic practical speedups by avoiding work proportional to the whole program.

## 3 Methodology

Our methodology is *reductionist*: we cast the entire design space as variations on a single CFL-reachability scheme, then vary (a) the language $L$, (b) the query discipline (exhaustive vs. demand-driven), and (c) the graph representation (constraint graph vs. sparse value-flow graph). Concretely:

1. **Encoding.** We give an explicit graph construction in which allocation, copy, load, store, call, and return statements become labeled edges, and prove that Dyck-reachability coincides with the least solution of the Andersen constraints.
2. **Spectrum.** Steensgaard's analysis *replaces* the Dyck language with a regular language identifying $({}_i$ with $){}_i$ — parentheses as erasable — which is precisely the union-find collapse.
3. **Sparsification.** We construct the sparse value-flow graph (SVFG) from a preliminary flow-insensitive analysis plus SSA, and argue that propagation restricted to def-use edges preserves the least solution while cutting edges by orders of magnitude [8].
4. **Context sensitivity.** We extend the Dyck alphabet with call-string indices (the *extended Dyck* formulation of Shi et al. [8]) and analyze $k$-limiting as a regular approximation of an inherently context-free problem.

Empirical claims in §5 are drawn from the published evaluations of the cited systems rather than new experiments; we are explicit about which numbers are reproduced and which are derived.

## 4 Deep Dive

### 4.1 Pointer analysis as Dyck-language reachability

The central encoding works as follows. Build a graph whose nodes are program variables and abstract objects. For each statement, add labeled edges:

```c
/* normalized statements and their graph edges */
p = &o;    /*  o --new--> p            */
p = q;     /*  q --assign--> p         */
p = *q;    /*  q --deref--> t_q, t_q --assign--> p   (fresh t_q) */
*p = q;    /*  q --assign--> t_p, t_p --store--> p   (fresh t_p) */
```

Field sensitivity is handled by treating each field $f$ as a parenthesis pair: a store `q.f = y` emits an edge labeled $\overline{\mathit{st}}(f)$ (open), and a load `x = p.f` emits $\overline{\mathit{ld}}(f)$ (close). The grammar for the *flows-to* relation then contains the production

$$\mathit{flowsTo} \;\to\; \mathit{flowsTo}\ \overline{\mathit{st}}(f)\ \mathit{alias}\ \overline{\mathit{ld}}(f)\ \mathit{flowsTo}$$

which requires that a value flowing through a field be *stored and loaded through the same field* — the matched-parentheses condition. Similarly, interprocedural flow uses call-site-indexed parentheses $({}_i, ){}_i$: actual-to-formal binding opens a parenthesis, and the return closes it, so values cannot "return" to a call site that never called the procedure.

> **Theorem:** *(Dyck encoding of Andersen.)* Let $G$ be the labeled graph constructed above and $L_{\mathit{pt}}$ the Dyck language generated by the $\mathit{flowsTo}$/$\mathit{alias}$ grammar. Then $o \in \mathit{pt}(p)$ in the least solution of the Andersen constraints iff there is an $L_{\mathit{pt}}$-path from $o$ to $p$ in $G$.

*Proof sketch.* By induction on the derivation: each Andersen inference rule (e.g., transitivity of $\subseteq$ through copy edges, the load/store rules) corresponds to one grammar production, and conversely every derivation tree unfolds into a sequence of constraint applications. The matching condition is exactly what makes the load rule $\forall o \in \llbracket q \rrbracket: \llbracket o \rrbracket \subseteq \llbracket p \rrbracket$ sound: without matching, a store through one alias could be read through a different field, which is precisely the over-approximation of context-insensitive analysis. ∎

This theorem is the fulcrum of the entire thesis: *precision in pointer analysis is a language-theoretic property of the path language*, not an ad-hoc feature of the solver.

### 4.2 Demand-driven points-to queries

Given the encoding, a demand-driven analysis is conceptually simple: to answer "does $o$ flow to $p$?", run a *single-source, single-target* CFL-reachability query from $o$ to $p$, exploring only edges reachable along derivations relevant to the query [4]. The algorithm maintains a worklist of derived edges (a standard dynamic transitive-closure / CFL-reachability worklist), seeded with the query pair, and expands productions backwards from the target.

```python
def points_to_query(graph, o, p, grammar):
    """Demand-driven Dyck-reachability query: does o flow to p?"""
    worklist = deque([(o, p, 'flowsTo')])   # seed with the query
    derived = set()
    while worklist:
        u, v, X = worklist.popleft()
        if (u, v, X) in derived: continue
        derived.add((u, v, X))
        for (prod, split) in grammar.expansions(X):
            # match u -a-> m -Y-> n -b-> v against production X -> a Y b
            for m, n in graph.match(u, v, prod, derived):
                worklist.append((m, n, 'Y'))
    return (o, p, 'flowsTo') in derived
```

Two refinements make this practical. First, **refinement-based context sensitivity** [5]: start context-insensitive (cheap), and only when a query's answer is polluted by an *unrealizable* path — one whose parentheses do not balance — refine by splitting the offending context. This is counterexample-guided abstraction refinement (CEGAR) applied to the call-string lattice. Second, **caching**: derived facts are memoized across queries, amortizing cost across a query sequence.

> **Theorem:** *(Hardness of on-demand analysis.)* Under the Boolean Matrix Multiplication (BMM) hypothesis, on-demand Andersen points-to analysis — deciding $o \in \mathit{pt}(p)$ for a *single* pair — admits no sub-cubic *combinatorial* algorithm [2].

The moral is sharp: demand-driven analysis is a *heuristic* triumph, not a complexity-theoretic one. Its wins are entirely practical — and in practice they are enormous: Sridharan et al. report that demand-driven queries over large Java benchmarks touch only a small fraction of the program [4].

### 4.3 The Andersen–Steensgaard spectrum

Andersen and Steensgaard are not two unrelated algorithms; they are two points on a spectrum parameterized by *how much of the Dyck structure the analysis respects*. Consider progressively weakening the path language:

| Level | Path language | Algorithm | Complexity |
|---|---|---|---|
| Dyck (full) | balanced $({}_i \dots ){}_i$ | Andersen (field- & context-sensitive) | $O(n^3)$ |
| Unlabeled Dyck | balanced but index-insensitive | field-insensitive Andersen | $O(n^3)$, less precise |
| Regular | parentheses freely erasable | **Steensgaard** (union-find) | $O(n\,\alpha(n))$ |
| Trivial | any path | "everything aliases" | $O(1)$ |

Steensgaard's rule `p = q  ⟹  p ∼ q` (equality rather than inclusion) is exactly what happens when the grammar production $\mathit{flowsTo} \to \mathit{assign}$ is replaced by a *symmetric* closure: flow becomes bidirectional, which in language terms means the analysis can no longer distinguish $({}_i$ from $){}_i$. The union-find data structure is then not an implementation trick but the *canonical solver* for regular-language reachability over an equivalence relation [6][7].

Between the endpoints lies a rich middle ground: Heintze and Tardieu's online/offline constraint formulations [3] recover much of Andersen's precision at near-Steensgaard speed via careful constraint ordering and difference propagation — still the first decision every designer faces: *subset or equality?*

An instructive micro-example separates the two:

```c
p = &a;   /* pt(p) = {a} initially */
q = &b;   /* pt(q) = {b}           */
r = p;    /* Andersen: pt(r) = {a}; Steensgaard merges p,q,r into one class */
s = q;    /* Andersen: pt(s) = {b}; Steensgaard: pt(s) = pt(r) = {a, b} */
```

Andersen distinguishes the two flows; Steensgaard, having unified $p \sim r$ and $q \sim s$ bidirectionally through the shared structure, reports $\{a, b\}$ for both. Whether that imprecision matters depends entirely on the client — for coarse call-graph construction it rarely does; for strong-update-dependent bug finding it is fatal.

### 4.4 Sparse value-flow graphs

Classical constraint-graph solvers propagate points-to sets along *every* copy edge, even those that provably carry no new information. The **sparse value-flow graph** (SVFG) insight [8] is that propagation need only follow *def-use chains*: the value of $q$ at a load `p = *q` depends only on the *definitions* of $q$ reaching that load, and those are exposed directly once top-level variables are in SSA form.

Construction proceeds in two stages:

1. **Pre-analysis.** Run a fast flow-insensitive analysis (Andersen or even Steensgaard) to obtain a conservative points-to relation. This resolves indirect def-use edges: a store `*p = q` defines every $o \in \mathit{pt}(p)$.
2. **SSA + SVFG.** Place top-level pointers in SSA; for address-taken variables, insert $\mu$/$\chi$ annotations at loads/stores using the pre-analysis results. Def-use edges between SSA versions form the SVFG. A *demand-driven, flow- and context-sensitive* analysis (e.g., **Pinpoint** [8]) then traverses this graph *backwards* from each query, following only relevant def-use chains.

The payoff is qualitative: full-sparse analyses achieve *flow sensitivity* — distinguishing $\mathit{pt}(p)$ at different program points — and *path sensitivity* (in the SPAS line [Sui et al., APLAS 2011]) at costs previously associated with flow-insensitive analysis. The SVFG is typically *orders of magnitude* sparser than the constraint graph, because most copy edges in real programs are never on a value-flow path relevant to any interesting query.

Formally, sparsification is *solution-preserving*: every dense propagation step has a corresponding SVFG path, so the least fixed point over the SVFG coincides with the dense one on queried variables — the difference between analyzing a million lines and timing out on a hundred thousand [8].

### 4.5 Context sensitivity as extended-Dyck reachability

Context sensitivity — distinguishing the behavior of a procedure under different callers — is, in the CFL framework, simply a *richer parenthesis alphabet*. In the **extended Dyck** formulation [8], each call site $i$ contributes not one but a family of parenthesis pairs indexed by the *call string* (the stack of pending calls), and context-sensitive reachability asks for paths whose parenthesis word is balanced *and* whose indices agree along the whole string. $k$-limiting (call-site sensitivity with $k = 1, 2$) is then a *regular approximation*: truncate the stack, and you truncate the language.

The refinement-based approach [5] inverts this: rather than fixing $k$ up front, start with the *coarsest* abstraction (context-insensitive, i.e., all parentheses unlabeled) and split contexts only along unrealizable paths discovered during query answering. This yields a *demand-driven context sensitivity* that is as precise as needed for the query at hand and no more — the analysis equivalent of lazy evaluation.

Object sensitivity (contexts as receiver allocation sites) fits the same schema with object-indexed rather than call-site-indexed parentheses — the framework only requires that indices *match*.

## 5 Empirical Evaluation / Formal Results

We consolidate the principal quantitative and complexity-theoretic results from the literature. All numbers below are *reported* from the cited evaluations, not new measurements.

**Complexity landscape.**

| Problem | Lower bound | Upper bound | Source |
|---|---|---|---|
| Exhaustive Andersen (APA) | no sub-cubic combinatorial algorithm under BMM | $O(n^3)$ | [2] |
| On-demand Andersen (single query) | no sub-cubic combinatorial algorithm under BMM | $O(n^3)$ | [2] |
| Steensgaard (equality-based) | — | $O(n\,\alpha(n))$ | [7][6] |
| CFL-reachability (general) | cubic bottleneck (reducible from BMM) | $O(n^3)$ | [1] |
| $(4, j)$-bounded APA | — | $\tilde{O}(n^{\omega} \cdot j)$ | [2] |

**Practical performance (reported).** Demand-driven points-to analysis for Java answers typical client queries while exploring only a small fraction of the program — Sridharan et al. [4] report order-of-magnitude speedups over exhaustive analysis, with refinement-based context sensitivity [5] adding precision where queries demand it. Pinpoint [8] demonstrates flow- and context-sensitive analysis scaling to **millions of lines of code**, enabled by the sparse value-flow graph; incremental CFL-reachability summarization [Shang et al., ASE 2012] further allows reusing procedure summaries across queries and program versions.

**Precision hierarchy (empirical).** Across the standard benchmark suites, the precision ordering is stable and unsurprising:

$$\text{context-sensitive sparse} \;\succ\; \text{Andersen (Dyck)} \;\succ\; \text{field-insensitive Andersen} \;\succ\; \text{Steensgaard} \;\succ\; \text{naive}$$

where $\succ$ denotes "computes smaller (more precise) points-to sets on average." The gap between Andersen and Steensgaard is typically a small constant factor in *average* points-to set size but can be arbitrarily large on adversarial programs — the micro-example in §4.3 exhibits the worst case in miniature.

## 6 Limitations

Intellectual honesty requires stating what this framework does *not* solve.

1. **Soundness gaps in practice.** The edifice assumes a closed world: visible code, no reflection, modeled natives, allocation-site heap abstraction. Real Java programs use reflection and dynamic class loading; real C programs call uninstrumented libraries. Every production analysis is unsound by design at the boundary, and no CFL encoding recovers information the graph never contained.
2. **Concurrency.** The Dyck-language story is sequential: one thread's matched calls and returns. Under weak memory and data races, "the" value on a def-use edge dissolves. Concurrent CFL-reachability remains largely open.
3. **The cubic wall is real.** Theorem [2] is a boundary marker, not despair: no query strategy — demand-driven, incremental, or otherwise — escapes the BMM-hardness of the combinatorial problem. Relief needs non-combinatorial methods (fast matrix multiplication, galactic constants) or boundedness restrictions.
4. **Context-sensitivity selection.** Refinement [5] chooses contexts via unrealizable paths, but the abstraction itself (call-site vs. object vs. type sensitivity) remains a per-benchmark black art; introspective analyses automate it at engineering cost.
5. **Strong updates.** Flow sensitivity gains precision through strong updates, but under allocation-site abstraction most stores are weak updates, so the sparse machinery buys less than theory suggests for heap-intensive programs.

## 7 Conclusion

Pointer analysis, viewed through the lens developed here, is *one problem with three dials*: the **path language** (Dyck for Andersen, regular for Steensgaard), the **query discipline** (exhaustive vs. demand-driven, with refinement-based context sensitivity as the adaptive middle), and the **graph representation** (dense constraint graph vs. sparse value-flow graph). Turning these dials recovers, as special cases, nearly every major points-to analysis of the last three decades — from Steensgaard's almost-linear unification [7] to Sridharan and Bodík's demand-driven refinement [4][5] to the million-line sparse analyses of the SVF/Pinpoint lineage [8].

Two lessons deserve emphasis. First, *precision is language-theoretic*: context sensitivity is exactly the difference between requiring parentheses to balance and letting them dangle. Second, *the hardness is load-bearing*: the BMM lower bounds [2] show demand-driven analysis wins by avoiding work, not by doing fundamentally less — a distinction that should guide future effort. The most promising directions are principled context-abstraction selection, sound handling of dynamic features within the CFL framework, and a concurrency-aware Dyck reachability. The parentheses still have secrets to yield.
