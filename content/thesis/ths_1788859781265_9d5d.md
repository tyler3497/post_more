# Beyond Rank One: Higher-Rank Type Inference from Hindley–Milner through Bidirectional Checking, OutsideIn(X), and Quick Look

## Abstract

## 1 Introduction

The tension between *expressiveness* and *decidability* is the oldest fault line in statically typed functional language design. On one side stands System F — Girard's and Reynolds' polymorphic λ-calculus — an impredicative calculus in which `∀α.τ` may be instantiated by *any* type, including itself. On the other side stands the Hindley–Milner system of Damas and Milner [5], which sacrifices generality for complete, decidable inference: quantifiers appear only in prenex position (rank 1), and generalization is permitted only at `let`-bindings.

The HM compromise was enormously successful: ML-family languages and Haskell 98 built entire ecosystems on rank-1 inference, and Algorithm W's principal types guarantee the inferred scheme is the most general one possible. Yet the boundary of rank 1 has always chafed. Even modest programs want to pass a polymorphic function as an argument — the classic `runST :: (∀s. ST s a) → a` — which requires a rank-2 type. Libraries built on continuations, lenses, and effect systems routinely demand quantifiers nested under arrows or type constructors. Each such demand forces the programmer either to annotate or to restructure the program.

Because unrestricted System F inference is undecidable [1], no single algorithm can accept exactly the typable programs while remaining complete and terminating. The research programme of the last three decades has therefore been to find *decidable fragments and heuristics* that recover as much practical territory as possible. Three families of ideas dominate the modern landscape and form the spine of this thesis:

1. **Bidirectional typing**, following Pierce and Turner [2]: split typing into *synthesis* (`Γ ⊢ e ⇒ τ`) and *checking* (`Γ ⊢ e ⇐ τ`). Expected types propagate instantiation information inward, so an unannotated λ-abstraction can be checked against a higher-rank type even though its type cannot be synthesized.
2. **Constraint-based inference**, culminating in GHC's OutsideIn(X) framework [3]: separate *generation* of type constraints from *solving* them, parameterizing the architecture over a constraint domain X, with implication constraints modeling local assumptions from GADT matching.
3. **Quick Look impredicativity** [4]: a modular pre-pass that inspects each application spine twice — once quickly, to detect "blindingly obvious" impredicative instantiations, and once for real — leaving the rest of the inference engine undisturbed.

Each approach makes different trade-offs among completeness, predictability, implementation complexity, and the shape of the elaborated core language. Understanding them jointly, rather than in isolation, is the goal of this work.

## 2 Background

### 2.1 The Hindley–Milner fragment

The HM type system distinguishes *monotypes* `τ` (containing no quantifiers) from *type schemes* `σ` (a monotype prefixed by zero or more universal quantifiers):

```haskell
-- Monotypes
data Mono = TVar Name | TCon Name [Mono] | Mono :-> Mono
-- Type schemes (prenex polymorphism only)
data Scheme = Forall [Name] Mono
```

The rank of a type measures how deeply quantifiers nest to the left of arrows. Rank 0 types are monotypes; a rank-*n*+1 type has a rank-*n* type to the left of at least one arrow. HM permits only rank-1 (prenex) schemes, and the celebrated **let rule** is the sole locus of generalization:

> **Theorem:** (Damas–Milner [5]) For every closed HM-typable expression there exists a *principal* type scheme, and Algorithm W computes it.

Algorithm W operates by *constraint generation followed by unification*: it walks the syntax tree, mints fresh type variables for unknowns, unifies function domains with argument types, generalizes at each `let` over variables not free in the environment, and instantiates schemes with fresh variables at each use. The result is *principal* — any other valid typing is a substitution instance of it.

Two restrictions are load-bearing. First, the *value restriction* (in strict or effectful languages) limits generalization to syntactic values, preserving soundness under references and exceptions. Second, generalization occurs *only* at `let`. A λ-bound variable can never receive a polymorphic type from inference alone, so `λf. (f 1, f True)` is untypable without annotation: `f` must be monomorphic within the body, and no monotype unifies with both `Int → β` and `Bool → γ`. This is precisely a rank-2 demand.

### 2.2 System F and the undecidability barrier

System F extends the simply typed λ-calculus with explicit type abstraction `Λα.e` and type application `e[τ]`. Crucially, it is *impredicative*: `τ` in `e[τ]` may itself contain quantifiers, so `∀α.τ` can be instantiated with a polymorphic type — including itself. Type *checking* for Church-style System F is straightforward, since annotations guide everything. But for the Curry-style variant, where annotations are erased and must be reconstructed, Wells proved the devastating result:

> **Theorem:** (Wells [1]) Typability and type checking in System F are undecidable, by reduction from semi-unification.

Semi-unification — finding a substitution `S` with `S(τ₁) = S(S'(τ₂))` for finitely many inequation pairs — is itself undecidable, and Wells's encoding shows that inferring where implicit instantiations must occur, and at which polymorphic types, is exactly as hard.

| Calculus | Polymorphism | Inference | Principal types? |
|---|---|---|---|
| Simply typed λ-calculus | None | Decidable (linear) | Yes (trivially) |
| Hindley–Milner | Rank 1, let-only | Decidable (DEXPTIME-complete, Kfoury et al. [6]) | Yes |
| System F (Curry) | Full impredicative | **Undecidable** [1] | Yes (declaratively) |
| Rank-*n* (fixed *n* ≥ 2) | Bounded rank, annotations | Decidable with annotations | Fragment-dependent |
| MLF | First-class, flexible bounds | Decidable, partial reconstruction [7] | Yes (with bounds) |

Every practical system therefore lives *between* HM and System F, and the choice of where to draw the line — and how sharply the line is drawn — determines the programmer experience.

### 2.3 What "higher-rank" and "impredicative" mean in practice

A *higher-rank* type nests `∀` under an arrow: `∀a. (∀b. b → b) → a → a` is rank 2, arising whenever a function *consumes* polymorphism, as in `runST`, Church encodings, or effect handlers. *Impredicative* instantiation goes further — instantiating a quantifier with a polymorphic type, as in `id runST` requiring `b := (∀s. ST s a) → a` — and permits quantifiers under arbitrary type constructors, not merely under arrows. It is the feature whose inference is most treacherous, because the space of candidate polymorphic instantiations is unbounded.

## 3 Methodology

This thesis is a *comparative systems study*: we reconstruct each system's core judgments in uniform notation, map the major proposals on axes of *annotation burden*, *completeness*, *principal types*, and *core-language invasiveness*, and evaluate them against a shared battery of litmus programs (`id runST`, `single id :: [∀a. a → a]`, `(\x → x) : ids`, nested applications) plus published experience reports from GHC — the only production compiler to have shipped bidirectional checking, OutsideIn(X), and Quick Look. We do not propose a new algorithm; the contribution is synthetic and evaluative.

## 4 Deep Dive

### 4.1 Bidirectional Typing: the Pierce–Turner Recipe

Bidirectional typing replaces the single typing judgment with two mutually recursive modes:

```haskell
-- Γ ⊢ e ⇒ τ   synthesis:   type flows UP, out of the term
-- Γ ⊢ e ⇐ τ   checking:    expected type flows DOWN, into the term
```

The *Pfenning recipe* (after Frank Pfenning; surveyed comprehensively by Dunfield and Krishnaswami [8]) assigns each elimination form to synthesis and each introduction form to checking, with a single *subsumption* (mode-switch) rule mediating between them:

> **Theorem:** (Mode discipline) Introduction forms *check*; elimination forms *synthesize*; variables and annotated terms *synthesize*; the annotation rule `Γ ⊢ (e : σ) ⇒ σ` (given `Γ ⊢ e ⇐ σ`) switches from checking to synthesis.

Dunfield and Krishnaswami later gave the landmark *complete and easy* bidirectional system for higher-rank polymorphism, replacing Pierce–Turner's backtracking search with an ordered context of *existential variables* `α̂` and a context-extension invariant (`Γ ⟶ Δ`) that makes subtyping and instantiation deterministic. Their algorithm is sound and complete with respect to its declarative specification, and every unknown appears only by programmer request.

The fundamental limitation of pure bidirectionality is *information poverty*: checking mode is only as good as the annotations that feed it. In a call like `map f xs` with no expected type in scope, nothing flows downward, and impredicative instantiations remain invisible.

### 4.2 Constraint-Based Inference: the OutsideIn(X) Framework

GHC's inference engine, since the late 2000s, is organized around a radical separation of concerns due to Vytiniotis, Peyton Jones, Schrijvers, and Sulzmann [3]: **OutsideIn(X)**. The pipeline has two phases:

1. **Constraint generation** walks the source term and emits a *wanted* constraint — a formula in an abstract constraint language — mentioning fresh *unification variables*.
2. **Constraint solving** discharges the wanted constraint against *given* constraints (from signatures and local assumptions), producing a substitution and elaborated System F evidence (coercions).

The parameter **X** is the constraint domain: equalities `τ₁ ~ τ₂`, class constraints `C τ̅`, and — critically — *implication constraints* `∀ā. (Q₁ ⇒ Q₂)`, which encode *local assumptions*. When a GADT pattern match refines a type variable, the constraints generated inside the branch are guarded by that implication. Let-generalization is then reformulated elegantly: generalize the variables that do not appear free in the *residual* constraints — but never over variables constrained by local givens, which would be unsound.

The framework's power is its *modularity*: GADTs, type families, functional dependencies, and quantified constraints all plug into X without disturbing the generation/solving split. Bidirectional checking composes naturally too — expected types simply become additional wanted constraints [9]. But OutsideIn(X) is *predicative at heart*: unification variables range over monotypes, and impredicative instantiation has no natural home in a solver built on first-order unification. That gap is what Quick Look fills.

### 4.3 Quick Look: Staged Impredicative Instantiation

Serrano, Hage, Peyton Jones, and Vytiniotis [4] observed that in practice, impredicative instantiations are almost always *blindingly obvious from the call site*. In `reverse xs` where `xs :: [∀a. a → a]`, the only way to make the program typecheck is to instantiate `reverse :: ∀b. [b] → [b]` at `b := ∀a. a → a` — any monomorphic choice fails against the invariant type constructor `[_]`. Quick Look exploits this with a **two-phase discipline** at every application spine:

- **Phase 1 (the quick look):** a shallow, cheap pre-pass over the application `h e₁ … eₙ` that examines the *head's* instantiated type alongside the *arguments'* types and any *expected result type*, looking for forced impredicative choices. It never looks inside abstractions, `let`s, or pattern matches; it only asks, "is impredicativity the *only* consistent solution here?"
- **Phase 2 (the real pass):** ordinary OutsideIn inference, seeded with whatever impredicative instantiations Phase 1 discovered.

> **Theorem:** (Quick Look staging [4]) If the quick-look phase commits to an instantiation, that instantiation is *forced*: every successful typing of the application in the declarative system uses it. Impredicativity is *never guessed*.

This "never guessed" property is the design's moral center. Earlier approaches to impredicativity either demanded pervasive annotations, performed unpredictable global search, or changed the type language itself (as in MLF's flexible bounds). Quick Look instead guarantees *stability*: adding or removing an obviously-forced instantiation cannot flip an accepted program to rejected, and the algorithm degrades gracefully — when nothing is obvious, it silently reverts to ordinary predicative inference. The paper proves that the system handles *all of System F* expressiveness-wise (every System F term is typable *with suitable annotations* guiding the look), requires no extension to types, constraints, or the System F core language, and was implemented in production GHC behind the `ImpredicativeTypes` flag [10].

The canonical examples from the paper and GHC proposal 274 illustrate the mechanism:

```haskell
ids :: [forall a. a -> a]
single id :: [forall a. a -> a]  -- result forces b := forall a. a -> a
(\x -> x) : ids                 -- argument forces c := forall a. a -> a
```

The pre-pass is *compositional* over application spines: in `f (g x)`, the inner application's forced instantiation is discovered first and propagates outward. Yet it refuses to speculate — `id x` with `x :: ∀a. a → a` and no expected type still fails, since both readings are consistent and guessing would make acceptance order-dependent.

### 4.4 Elaboration to System F, Visible Type Application, and the MLF/FreezeML Design Space

Whatever the source language permits, GHC's core language remains System F with coercions. Every successful inference therefore *elaborates* to explicit type abstractions and applications. Quick Look's headline engineering achievement is that this elaboration needs no new core forms: impredicative instantiation elaborates to ordinary `TApp` at a polymorphic type.

Two companion mechanisms make the system *predictable* rather than merely powerful. **Visible type application** (`f @τ x`) lets the programmer supply instantiations explicitly, including polymorphic ones under `ImpredicativeTypes` (e.g. `reverse @(∀b. b → b) xs` [10]) — the sanctioned escape hatch wherever Quick Look declines to guess. **Inferred vs. specified binders** determine which quantifiers VTA may target, preventing silent capture of compiler-invented variables.

The broader design space contains instructive alternatives. **MLF** (Le Botlan and Rémy [7]) achieves *principal types* for first-class polymorphism by enriching the type language with *flexible bounds* `∀(α ≥ σ) σ'`, keeping competing instantiation options open inside the type itself. Leijen [11] showed how MLF elaborates to System F by a type-directed translation. **FreezeML** introduced a term-level *freezing* operator `⌈x⌉` that blocks automatic instantiation, recovering decidable, complete inference that conservatively extends ML. Each pays for principality with a richer type language — precisely the cost Quick Look refused to pay, accepting heuristic incompleteness instead.

| System | Annotation burden | Principal types | Core-language change | Impredicativity |
|---|---|---|---|---|
| Pierce–Turner [2] | Moderate (explicit instantiation) | No | Internal/external split | Explicit only |
| Dunfield–Krishnaswami | Low (rank-*n* annotations) | Declarative only | None | No |
| OutsideIn(X) [3] | Low (GADT signatures) | No (ambiguity) | Coercions | No |
| Quick Look [4] | Low (VTA escape hatch) | No | None | Heuristic, never guessed |
| MLF [7] | Very low | Yes (flexible bounds) | xMLF retyping | Full, principled |
| FreezeML | Low (`⌈x⌉` freezes) | Yes | Freeze operator | Full, decidable |

## 5 Empirical Results / Proofs

The theoretical claims of the surveyed systems are backed by mechanized or paper proofs and, unusually for type-system research, by production deployment data.

**Soundness and the "never guessed" lemma.** Quick Look's metatheory [4] establishes (i) soundness against the declarative specification — every accepted program elaborates to a well-typed System F term; and (ii) the *forced-instantiation* property: the pre-pass commits only when all declarative derivations agree. A companion result characterizes which transformations *preserve* typeability — η-expansion, notably, can destroy the syntactic application spine the pre-pass depends on, a sharp and honest boundary.

**Production evidence from GHC.** Quick Look shipped in GHC 9.2 behind `ImpredicativeTypes` [10]: `reverse xs` with `xs :: [∀a. a → a]`, `single id :: [∀a. a → a]`, and `(\x → x) : ids` all typecheck, while genuinely ambiguous programs (bare `id x` at a polymorphic argument type with no expected type) are still rejected with an invitation to use visible type application. A subtle interaction had to be resolved first: *simplified subsumption* made function types invariant, which the pre-pass relies on when matching argument types against parameter types. Class constraints and implicit parameters remain *entirely monomorphic* even under `ImpredicativeTypes` — `C (∀a. a → a) => τ` is rejected — because impredicative dictionaries would require impredicative evidence, a dimension the designers deliberately left closed.

**Negative results that shape the space.** Wells's undecidability [1] and Dudenhefner's streamlined reduction [12] fix the outer boundary: no complete algorithm exists, so every system above is necessarily a heuristic or a fragment. Kfoury et al.'s DEXP-completeness for ML typability [6] further shows that even the "easy" fragment is worst-case exponential — decidability is not tractability, and production solvers rely on the empirical smallness of real programs.

## 6 Limitations

**No principal types, no completeness.** Outside the MLF/FreezeML family, higher-rank and impredicative systems abandon principal types. Two incomparable typings may both be valid (MLF's `choice id` example), and the algorithm's choice among them is a heuristic commitment. Programmers therefore face *accept/reject boundaries* that are not stable under refactoring: η-expansion can break Quick Look by dissolving the application spine; adding a signature can change which instantiation is "obvious"; moving code across a `let` changes generalization.

**Unpredictability of heuristics.** "Never guessed" is a soundness property of the *commitment*, not a completeness property of the *search*. The pre-pass looks only at application spines — never under binders — so `let f = g x in ...` may fail where the inlined version succeeds. GHC's documentation is candid that `ImpredicativeTypes` remains heuristic and that visible type application is the supported remedy [10].

**Ambiguity and the open world.** OutsideIn(X) inherits the classic ambiguity problem: constraints like `Show α` with `α` otherwise unconstrained admit many solutions, and the framework's account of ambiguity (defaulting, or rejection) is, by the authors' own admission, unsatisfactory [3]. Impredicativity compounds this: with polymorphic instantiation candidates, the solution space is not merely large but unbounded, which is exactly why Quick Look refuses to search it.

**Annotation ergonomics.** Bidirectional systems shift the burden to annotations at rank boundaries. In large codebases this is often *desirable* — signatures document intent — but the precise placement rules (which positions check vs. synthesize) constitute a hidden grammar programmers must internalize, and boundary error messages remain notoriously opaque.

**Elaboration fragility.** Because everything elaborates to System F, *runtime* semantics depends on where the compiler inserts type abstractions — deep vs. shallow instantiation can change termination behavior. Coherence (signature changes not affecting runtime behavior) holds only modulo these elaboration choices, and impredicative elaboration multiplies the cases.

---

## 7 Conclusion

Higher-rank type inference is the art of the principled compromise. Wells's undecidability theorem [1] closes the door on the ideal — complete, annotation-free inference for System F — and the field has responded not with a single successor but with a toolkit of complementary mechanisms. Bidirectional typing [2, 8] turns expected-type information into a resource, letting checking mode consume polymorphism that synthesis could never invent. OutsideIn(X) [3] turns inference into a modular constraint problem, taming GADTs, type families, and local assumptions behind implication constraints while keeping generation and solving cleanly apart. Quick Look [4] turns impredicativity from a global search problem into a local, staged observation — committing only to forced instantiations, never guessing, and degrading gracefully to predicative inference otherwise.

The production moral, as demonstrated by GHC, is that these mechanisms *compose*: bidirectional expected types feed constraint generation, constraints flow through OutsideIn(X), and Quick Look's pre-pass seeds the solver — all elaborating to an unchanged System F core, with visible type application as the predictable escape hatch. The alternatives that preserve principal types — MLF's flexible bounds [7], FreezeML's freezing — remain theoretically attractive but pay in type-language complexity what Quick Look pays in heuristic incompleteness.
