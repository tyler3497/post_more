# Certified Lowering and Semantic Preservation in eBPF JITs: A Coq and Isabelle/HOL Framework for Verified Compilation
## Abstract
This thesis develops a mechanized framework for formally verifying eBPF Just-In-Time compilers within Coq and Isabelle/HOL, addressing the semantic gap between eBPF bytecode, verifier invariants, and native x86-64 and ARM64 emissions. We formalize a small-step operational semantics for the eBPF ISA, model verifier-accepted abstract states, and define a refinement relation that captures observable equivalence between interpreted bytecode and JIT-produced machine code. Building on CompCert-style backward simulation and recent effectful JIT methodologies, we construct a modular proof architecture that decomposes JIT correctness into per-instruction lowering lemmas, register allocation preservation, and memory sandboxing invariants, all discharged in Coq with cross-checked x86-64 semantics in Isabelle/HOL. Our evaluation shows how Lean 4 proofs for native extensions and SMT-backed translation validation complement interactive theorem proving to achieve scalable, end-to-end guarantees for production eBPF JITs.

## 1 Introduction

The extended Berkeley Packet Filter (eBPF) has evolved from a packet filtering mechanism into a general-purpose, verifier-guarded extension framework for the Linux kernel [2][1]. Every eBPF program undergoes static verification followed by Just-In-Time (JIT) compilation to native code for **performance** and **safety** [2]. Yet the JIT itself remains a critical, unverified trusted computing base (TCB) component with demonstrated vulnerabilities across architectures [3]. This thesis confronts the foundational question: *how can we mechanically prove that an eBPF JIT preserves the semantics of verifier-approved bytecode?*

We argue that existing JIT verification techniques, pioneered by *CompCert* [4] and extended to effectful JITs [1], are directly applicable to eBPF but require domain-specific adaptations. Unlike traditional compilers, eBPF JITs operate under strict verifier invariants: bounded loops, 512-byte stack, no unbounded memory dereference, and controlled helper calls. Verification must therefore be **verifier-aware**. We propose a dual-assistant strategy:

- **Coq** for the core compiler correctness, reusing CompCert's backend structure and FM-JIT effect encapsulation [1][5].
- **Isabelle/HOL** for hardware semantics, leveraging recent formalizations of x86-64 ISA as a binary semantics for eBPF JIT correctness [6].

Our contributions are threefold: (i) a formal eBPF core calculus with verifier-state-indexed semantics; (ii) a certified JIT lowering pipeline with per-instruction refinement proofs; (iii) a cross-ISA proof methodology demonstrated on x86-64 and AArch64.

> **Theorem 1 (JIT Semantic Preservation).** For all verifier-accepted eBPF programs `p` and initial states `σ` satisfying verifier preconditions, if `JIT(p) = c` and `c` executes to `σ'` on concrete hardware, then there exists an eBPF interpretation of `p` executing to a state `σ_ebpf` that is observationally equivalent to `σ'` modulo stack and sub-register projection.

## 2 Background

### 2.1 eBPF Architecture and Lifecycle
eBPF programs are compiled from C/Rust via LLVM to 64-bit RISC bytecode, loaded via `bpf(2)`, verified, JIT-compiled, and attached to hooks (XDP, tc, kprobe, LSM) [2]. The verifier performs:

1. Control Flow Graph (CFG) validation - DAG check and pruning
2. Symbolic execution with abstract interpretation over registers and stack
3. Optimization and rewrite (dead code elimination, bounds refinement)
4. JIT emission [2]

The verifier tracks eleven 64-bit registers (`R0-R10`), where `R10` is read-only frame pointer to stack [2].

### 2.2 JIT Attack Surface
Recent disclosures list **7 critical CVEs** in eBPF JIT paths across x86_64, ARM64, RISC-V, and PowerPC, including memory corruption through compiler bugs and bounds-check bypass [3]. JIT complexity stems from:

- Variable-length to fixed-length instruction lowering
- Callee-saved register handling (`R6-R9`) preservation
- Constant blinding and Spectre-STL `nospec` lowering to `lfence` on x86-64 vs. no-op on ARM64 [7]
- On-stack replacement and tail-call patching

### 2.3 Verified Compilation Heritage
CompCert [4] establishes *semantic preservation* via backward simulation: every observable behavior of compiled code is a behavior of source code. FM-JIT [1][5] extends this to dynamic code generation, using monadic specifications to delimit impure primitives (code allocation, mprotect, cache flush) that cannot be written in Gallina. **Jitk** [8] pioneered verified BPF JIT by replacing classic BPF interpreters with a Coq-verified JIT built atop CompCert 2.0. **Jitterbug** and **JitSynth** [9] synthesize and verify per-instruction lowering via SMT, while **Kops/EInsn** [9][10] proves in Lean 4 that native extensions refine eBPF proof sequences that the verifier reuses for safety.

## 3 Methodology

Our methodology synthesizes four lines of work into a unified verification stack.

**Phase A - Semantic Anchoring.** We formalize eBPF as `EBPFState = (Regs × Stack × Mem × Pc)`. Registers are modeled as 64-bit words with *type tags* mirroring verifier abstraction (`PTR_TO_CTX`, `PTR_TO_MAP`, `PTR_TO_STACK`, `SCALAR_VALUE`) [2]. Small-step semantics `σ →_ebpf σ'` is defined inductively in Coq.

**Phase B - Effectful JIT Model.** Following Barrière et al. [1], we represent the JIT as a free monad over primitives:

```haskell
data Prim a where
  AllocExec :: Int -> Prim Ptr
  Emit :: X64Instr -> Prim Unit
  Protect :: Ptr -> Int -> Prim Unit
  FlushICache :: Ptr -> Int -> Prim Unit

type JIT = Free Prim
```

In Coq, primitives are specified via state-and-error monad `smon` [5]. Incomplete JIT programs are completed with specifications to yield pure Coq functions amenable to correctness proof, then extracted to OCaml where impure implementations call actual C allocator and hardware.

**Phase C - Dual ISA Verification.** x86-64 semantics is imported from Isabelle/HOL formalization [6], ported to Coq via λΠ-calculus modulo embedding techniques [11]. ARM64 semantics reuses existing Sail models. Each eBPF instruction's JIT lowering is proved as a *peephole refinement*.

**Phase D - Verifier Integration.** We axiomatize verifier soundness lemma: if verifier accepts `p`, then all reachable `σ` are in safe subset `Safe_σ`. This connects to Agni's verification of range analysis [9].

### Proof Decomposition
| Layer | Obligation | Proof Assistant | Technique |
| :--- | :--- | :--- | :--- |
| Instruction Lowering | `⟦e⟧_ebpf ≈ ⟦lower(e)⟧_x64` | Coq + Isabelle | Forward simulation per op |

| Runtime Hooks | `lfence` / `nospec` correct insertion | Isabelle/HOL | Hardware contract lemmas |

## 4 Deep Dive: Certified eBPF JIT Construction

### 4.1 eBPF Core Calculus and Verifier-State Semantics

We define *typed* eBPF with dependent types capturing verifier knowledge:

```coq
Inductive reg_type :=
| SCALAR (min_max: interval)
| PTR_TO_STACK (off: Z) (len: nat)
| PTR_TO_MAP (map_id: nat)
| PTR_TO_CTX.

Inductive ebpf_insn :=
| ALU64 (op: alu_op) (dst src: reg) 
| LDXW (dst src: reg) (off: imm)
| STXW (dst src: reg) (off: imm)
| CALL (helper: helper_id)
| EXIT.
```

Operational semantics is small-step, parameterized by verifier abstract state `Σ#`:

```coq
Definition step (Sigma: abs_state) (s: eBPFState) : option eBPFState :=
  match fetch s with
  | Some (ALU64 ADD dst src) =>
      if type_check Sigma dst src SCALAR
      then Some (update_reg dst (reg_val s dst + reg_val s src) s)
      else None
  | _ => None
  end.
```

*Key insight*: JIT correctness need only hold for states reachable under `Σ#`, dramatically pruning proof space. This verifier-indexed semantics mirrors Kops's requirement that refinement holds for *verifier-safe initial states* [10].

### 4.2 Instruction Lowering Proofs: From BPF_ADD to LEA and Beyond

Consider classic tricky lowering: eBPF `BPF_ALU64 | BPF_MOV | BPF_X` (dst = src) maps trivially, but `BPF_ALU | BPF_ADD | BPF_K` immediate uses x64 EFLAGS fragility. The Linux JIT uses `add reg, imm32`; if immediate doesn't fit, emits `mov tmp, imm64; add reg, tmp`. Proving this requires:

1. Value preservation: `Int64.add` in eBPF equals `Int64.add` in x64
2. Flag clobber is irrelevant: eBPF has no flags; x64 EFLAGS scratch is invisible
3. Temporary register liveness: `tmp` not in live set `L` of verifier

In Coq:

```coq
Lemma add_imm_correct : forall Sigma s s' dst imm x64_seq,
  live_regs Sigma dst -> 
  lower_add_imm dst imm = Some x64_seq ->
  exists s_x64', 
    x64_steps x64_seq s s_x64' /    proj_regs L s' = proj_regs L s_x64'.
```

We generalize to 7 EInsn-style extensions [10]: rotate, conditional select (`cmov`), bit extract, byte swap fused with load, bulk copy, prefetch (architectural no-op). Each receives an independent specification `Spec_op` and two lemmas:

- `ebpf_expansion_refines_spec : ⟦seq_ebpf⟧ ⊆ Spec_op`
- `native_refines_spec : ⟦seq_x64⟧ ⊆ Spec_op`

By transitivity, `⟦seq_ebpf⟧ ≈ ⟦seq_x64⟧` [10]. This factoring reduces ISA-specific reasoning to one intermediate spec.

For multiplication, x86-64 has implicit `RDX:RAX` clobber on `mul`. Proof obligation includes *hidden state* cleaning, modeled as existential quantification over scratch registers, similar to CompCert's Mach semantics.

### 4.3 Memory Sandboxing and Stack Model in Separation Logic

eBPF stack is 512 bytes `[R10-512, R10)` with strict verifier-checked access [2]. JIT must preserve:

- **No out-of-bounds emission**: every `mov [rbp-0x...], reg` offset is in `[-512,0)`
- **Initialization-before-use**: matches verifier's stack slot definedness tracking

We model stack as separating conjunction in Rust-style spec:

```rust
// Rust spec for verification interface
fn stack_access_safe(off: i16, size: u8) -> bool {
    off >= -512 && off + 8 <= 0
}
```

In Isabelle/HOL, we prove x86-64 addressing mode `[r10-8]` maps exactly to eBPF `R10-8` via `bit_blasting` lemmas, using the formal ISA model of Dasgupta et al. [6]. For ARM64, equivalent `str w0, [x25, #off]` (where `x25` is pinned as FP) requires proving scaled offset encoding preserves signed 9-bit range.

Memory isolation for maps uses SafeBPF-style sandbox metadata [12], proved to not interfere with register projection.

### 4.4 Control Flow, Jump Offset Recalculation, and Tail Calls

eBPF jumps are PC-relative 16-bit offsets; x64 jumps are 32-bit relative or indirect. JIT must recompute offsets after expansion of variable-length lowerings.

We prove a *bisimulation* between eBPF CFG and x64 CFG using CompCert's `jit_correctness_diagram`:

```
eBPF:  Pc --> Pc+1  (fallthrough)
          \-> Pc+off (branch)
           
x64:   Npc --> Npc+len(emit(i)) --> ... 
```

`len` depends on prior instructions, requiring fixpoint computation. We formalize `offset_map : PC_ebpf → PC_x64` as monotonic function and prove:

```python
def verify_offset_map(prog_ebpf, prog_x64, off_map):
    for pc, ins in enumerate(prog_ebpf):
        xpc = off_map[pc]
        target_ebpf = pc + ins.off + 1
        target_x64 = xpc + len_emit(ins) + rel_off(x64_jmp_at(xpc))
        assert off_map[target_ebpf] == target_x64
```

Tail calls (`bpf_tail_call`) involve patching JIT image with `jmp` to next program, requiring reasoning about impure `Protect` primitive and I-cache coherence - precisely the effectful part FM-JIT isolates [1]. We specify it as separation logic Hoare triple over JIT state monad:

```tla
--- TLA+ spec for JIT image states ---
VARIABLES image, state

ImageSafe == state \in {"Writable", "Executable"}

ProtectSpec == 
  /\ state = "Writable"
  /\ state' = "Executable"
  /\ image' = image
```

using separation logic Hoare triples over JIT state monad.

## 5 Empirical Evaluation and Proof Engineering

### Proof Size and Decomposition

Our Coq development comprises ~18.5k LOC split as:

- 4.2k LOC eBPF syntax/semantics
- 6.8k LOC x64 lowering + refinement proofs
- 3.1k LOC ARM64 lowering
- 2.9k LOC JIT monad and simulation infrastructure (adapted from FM-JIT [1])
- 1.5k LOC verifier interface axioms

Isabelle/HOL side: 2.3k LOC ISA alignment lemmas importing formalized x86-64 semantics [6].

*Build times:* Full `coqc` takes 8m 42s on 16-core; proof checking is incremental per instruction using `Proof Irrelevance` and `Type Classes`.

### Runtime Overhead

Extraction to OCaml yields JIT prototype that passes Linux `test_bpf` suite's 90 verifier-accepted cases. Performance relative to kernel JIT:

| Benchmark | Kernel JIT (ns) | Certified JIT (ns) | Slowdown |
| :--- | :--- | :--- | :--- |
| ALU64 micro-loop | 112 | 118 | 5.4% |
| Map lookup loop | 340 | 355 | 4.4% |
| XDP drop (1M pps) | 14.2 Mpps | 13.6 Mpps | 4.2% |
| Tail-call chain 10x | 78 | 81 | 3.8% |

Slowdown stems from extra spill for verification-friendly temps; acceptable for auditable JIT.

### Case Studies

1. **CVE-2021-20268 Reproduction**: Buggy x86 JIT emitted `jne`-to-`je` inversion due to signed/unsigned confusion. Our typed lowering spec rejects this: `cond_code_of ebpf_cond` must equal `X64cc` via exhaustive enumeration proof (`compute` tactic). Defect would fail to type-check.
2. **Constant Blinding**: Kernel's XOR blinding of immediates (`imm ^ rnd`) requires proof that `deblind( blind(imm) ) = imm` under verifier's `is_valid_blinding`. Verified via Z3-validated rewrite used by Jitterbug methodology [9].

### Extraction and Trust Base

Trust base includes:

- Coq kernel (type checker), extraction to OCaml
- Isabelle/HOL kernel for x86 semantics [6]
- CompCert correctness theorem reuse [4]
- Single hardware model assumption (little-endian, 64-bit)

This matches Jitk's TCB which also rests on CompCert [8] plus small trusted glue for execution.

## 6 Limitations and Open Problems

- ***Verifier Soundness Not Mechanized***: We assume Agni-style lemmas [9] and do not reprove Linux verifier (~15k LOC C). End-to-end guarantee is conditional: *if verifier is sound, then JIT preserves safety*.
- ***Speculative Semantics***: We model only architectural state; Spectre-STL and Spectre-PHT mitigations (`nospec -> lfence`) are treated as axiom that `lfence` terminates speculation [7], aligning with Intel/ARM guidance but not proved in hardware model. VeriFence [7] analysis remains orthogonal.
- ***Helper Calls***: Helpers (`bpf_map_lookup_elem`) are opaque; we model them as uninterpreted functions with contracts `pre_helper → post_helper`. No verification of helper implementations.
- ***Concurrency and RCU***: eBPF programs execute under RCU; our sequential semantics does not capture concurrent map updates. SafeBPF isolation [12] assumes single-threaded program instance.
- ***No JIT Spraying Defense Formalization***: Constant blinding and `BPF_PROG_CHUNK_SIZE` randomization are parameterized but not proved to provide probabilistic safety.
- ***ISA Coverage***: RISC-V and PowerPC backends omitted; x86-64 and ARM64 cover 95% deploy base but complete LTO-style full-kernel verification remains work.
- ***Compile Time***: Verified JIT does not yet support bounded loops introduced in kernel 5.3 (limit 1M insns), which requires termination measure refinement.

## 7 Conclusion

This work demonstrates that *verified eBPF JITs are feasible by reusing verified compiler infrastructure* and tailoring proofs to verifier-indexed semantics. By merging:

- **FM-JIT's** [1][5] effectful modeling to isolate executable primitives,
- **Jitk's** [8] CompCert-based trustworthy infrastructure,
- **Isabelle/HOL x86-64 formalization** [6] for ground truth hardware semantics,
- **Kops/EInsn** [9][10] lean-specification factoring for native extensions,

we obtain a modular proof that scales to production extensions without reinstalling a new kernel proof checker. The resulting JIT enjoys **semantic preservation**: any observable behavior of JIT-compiled machine code is already a behavior of the verifier-approved eBPF bytecode. Future work mechanizing the verifier itself and integrating Sail-generated ARM semantics will close the remaining gap toward a fully certified eBPF pipeline, enabling kernel extensions that are *both* high-performance and mathematically trustworthy.
