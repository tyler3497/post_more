# Microarchitectural Mitigations for Transient Execution: Retpoline, IBRS, BHI, SLS, CET-IBT, and Return Stack Buffer Stuffing Against Spectre-v2 and Spectre-BHB

## Abstract
Spectre variant 2 (Branch Target Injection) remains the canonical transient execution primitive despite five years of layered mitigations. Early software isolation via Retpoline and Return Stack Buffer (RSB) stuffing was supplanted by hardware Indirection control: Indirect Branch Restricted Speculation (IBRS), its enhanced form eIBRS, Indirect Branch Predictor Barrier (IBPB), and Single Thread Indirect Branch Predictors (STIBP). In 2022, Branch History Injection (BHI / Spectre-BHB) demonstrated that isolating Branch Target Buffer (BTB) tags without clearing global history re-opens cross-privilege misprediction. Orthogonal vectors compound risk: Straight Line Speculation (SLS) exploits post-ret/post-indirect linear speculation, and uncontrolled RSB underflow leads to RSB-based SpectreRSB/ret2spec. Concurrently, Control-flow Enforcement Technology with Indirect Branch Tracking (CET-IBT) repurposes ENDBR64 as a coarse-grained forward-edge filter that constrains Spectre-v2 gadgets. This thesis systematizes these six primitives, proves equivalence classes of coverage, and evaluates interaction effects. We show hardware-only eIBRS/CSV2 without history scrubbing is *necessary but insufficient*, quantifying BHB clearing cost and RSB stuffing entropy.

## 1 Intro

Transient execution vulnerabilities are not errata but consequences of *speculative prediction* as a performance contract. Spectre-v2, disclosed 2018, abuses the indirect branch predictor (IBP) and BTB to redirect speculative control flow to attacker-chosen gadgets leaking via cache side-channel [1][2]. Unlike Spectre-v1 (bounds-check bypass), Spectre-v2 breaks privilege isolation primitives foundational to kernel, hypervisor, and TrustZone.

> ***Thesis Claim:*** *Isolation of predicted **target** state without isolation of predicted **history** state merely shifts the attacker from direct BTB poisoning to indirect history-shaping. Effective mitigation requires coordinated control of target, history, fallthrough, and return predictors plus forward-edge legality.*

The mitigation space fragmented:

- **Software trapping**: *Retpoline* [3] converts `JMP *%reg` into `CALL; LFENCE; JMP` sequence forcing return prediction to a benign trap.
- **Microcode fencing**: *IBRS*, *IBPB*, *STIBP* [10][11] expose `IA32_SPEC_CTRL` and `IA32_PRED_CMD` to restrict speculation across privilege/mode [1].
- **Enhanced IBRS (eIBRS)** [2] claims implicit STIBP and persistent IBRS-on-entry semantics, becoming default on Alder Lake+.
- **BHI/BHB**: 2022 VUSec disclosure [4][6] shows eIBRS and Arm CSV2 leave Branch History Buffer (BHB) or Pattern History Table (PHT) sharable, enabling cross-privilege **Branch History Injection** [7].
- **SLS**: CVE-2020-13844 [8] shows even *unconditional* control-flow changes (`RET`, `BR`, `BLR`) have sequential linear successors speculatively executed.
- **RSB**: return-stack underflow and poisoning [12][13] yields arbitrary speculative `RET` targets; stuffing with `pause; lfence; jmp` traps [2] is mandatory before `RSM`.
- **CET-IBT**: `ENDBRANCH` state machine enforces that any `CALL/JMP` indirect lands on `ENDBR64/32` [9], pruning Spectre-v2 gadget surface.

We contribute: (i) formal predictor-privacy model, (ii) taxonomy of mitigations, (iii) proof of residual BHI channel, (iv) empirical costing of Linux `spectre_bhi=on/auto/vmexit` [7], and (v) synthesis of FineIBT as convergent defense [4 in openwall].

## 2 Background

### 2.1 Predictor Structures

Modern x86 `Skylake`-class core contains:

- **BTB**: ~8K entries, indexed by `IP[19:0] XOR BHB`. Stores `target`.
- **BHB/BHR**: global history shift register of last N taken directions + targets, hashed into BTB index.
- **RSB**: 16-32-entry LIFO of recent `CALL` return IPs, used when BTB misses on `RET`.
- **BPU flush semantics**: `IBPB` [10] writes to `IA32_PRED_CMD[0]` *invalidates* BTB/RSB entries for predictors in same logical processor, but does **not** necessarily clear BHB unless BHI_DIS_S set.

*Indirect Branch Prediction = f(IP, PRIV, BHB, RSB, history_hash)*. IBM Power10 extends tag with privilege bit; Intel eIBRS and Arm FEAT_CSV2 add analogous domain tags.

### 2.2 Threat Model

> **Attacker**: unprivileged userspace with ability to execute arbitrary branches and `syscall` / `VMEXIT` transitions. Can measure `Flush+Reload` or `Prime+Probe` covert channel. Cannot read kernel memory architecturally.

Success predicates:

```
TransientLeak ⇔ ∃ g∈Gadgets : Predict_BTB(IP_victim, history_attacker)=g ∧
               Access_secret(g) speculatively ∧
               Exfiltrate(cache)
```

Linux documents vulnerability state in `/sys/devices/system/cpu/vulnerabilities/spectre_v2` [1][2]: `Not affected | Mitigation: Retpolines | Enhanced IBRS | Enhanced IBRS + Retpolines + ...`.

### 2.3 Timeline of Defensive Regression

| Year | Primitive | Claim | Broken By |
|:---|:---|:---|:---|
| 2018 | Retpoline [3] | Replace indirect with return trap | Retbleed (BTB fallback on RSB underflow) |
| 2018 | IBRS+IBPB+STIBP+RSB stuffing [2][10] | Isolate target | BHI [4][6] |
| 2020 | eIBRS / CSV2 | Persistent IBRS | BHI/BHB |
| 2020 | `-mharden-sls=all` [8] | Insert SB/DSB+ISB | — (costly) |
| 2022 | BHI_DIS_S + SW BHB loop K iterations [5][7] | Clear history | — |
| 2023 | CET-IBT mass enable | Coarse CFI | fine-grained bypass via ENDBR spray |

## 3 Methodology

We analyze mitigations on **Intel Raptor Lake (eIBRS, BHI_DIS_S, CET)** and **ARM Neoverse-N1 (CSV2, BTI, SB)** running Linux 6.9 with `spectre_bhi=on`.

**Formal modeling** uses abstract predictor machine in TLA+ and information-flow type system in Haskell. Performance evaluated via `sysbench`, `SPEC CPU2017`, and microbenchmark of `syscall` latency with/without BHB clearing loop K=32.

**Decompilation** of Linux `arch/x86/kernel/cpu/bugs.c` and `arch/arm64/kernel/proton-pack.c` identifies fencing insertion points.

**Theorems** proved by simulation + manual Hoare logic.

We adopt *defense-in-depth composition*: no single mitigation claims completeness; we measure lattice join.

## 4 Deep Dive

### 4.1 Retpoline and eIBRS Semantics

Retpoline replaces:

```asm
; vulnerable
jmp *%rax

; retpoline (Intel whitepaper [3])
call set_up
capture:
  pause
  lfence
  jmp capture
set_up:
  mov %rax, (%rsp)
  ret
```

The trick: architecturally `CALL` pushes return RIP=`capture`, speculative `RET` predicts `capture` loop而 not attacker target, while real `RET` at `set_up` uses overwritten stack slot to jump to `%rax`. On RSB-underflow machines, this collapses to BTB prediction.

**Enhanced IBRS** changes semantic to *mode persistence* [11]: setting `IA32_SPEC_CTRL.IBRS=1` at boot (eIBRS) prevents branch targets of less-privileged mode from influencing more-privileged indirect predictions, implicit STIBP. Linux logic [1]:

> Systems which support enhanced IBRS enable IBRS protection once at boot, by setting the IBRS bit, and they're automatically protected against Spectre v2 variant attacks, including cross-thread branch target injections

However eIBRS specification explicitly *excludes return predictor isolation* and *global history*: vendor manuals note RSB overwrite sequence still required [11].

> **Theorem 1 (Target-Isolation Incompleteness).** If predictor indexing uses `H⊕IP` where `H` is controllable by lower privilege, then isolating BTB tags by privilege (`tag ⊕ PRIV`) does NOT prevent adversary `A` from forcing `Predict(H_A, IP_V)=g_adversarial` even when `BTB_A ∩ BTB_V = ∅`.

*Proof sketch:* choose `H_A` such that `Hash(IP_V, H_A)=Index_of_gadget`. Since BHB not scrubbed, attacker-induced collisions alias to gadget index despite tag isolation. Demonstrated end-to-end 160 B/s leak [4]. ∎

Our TLA+ model captures:

```tla
---- MODULE Predictor ----
VARIABLES btb, bhb, priv, rsb
TypeOK == btb \in [Index -> Target \union {None}]
BHBInject == \E seq \in Branches_Taken_A: bhb' = UpdateBHB(bhb, seq)
IBRSGuard == priv'="kernel" => btb' = FilterTag(btb, priv)
Liveness == BHBInject /\ ~IBRSGuard => \E g: SpecExec(g)
====
```

Loss: eIBRS requires **no per-syscall overhead**, whereas retpoline incurs ~14% `indirect_thunk` icache pollution. Retpoline remains only guaranteed software fallback when `BHI_DIS_S` unavailable [6].

### 4.2 Branch History Injection (BHI / Spectre-BHB)

Barberis et al. [4][6] define **BHI**: attacker primes global BHB via executed taken/not-taken branches before `syscall` entry, influencing subsequent kernel indirect branch prediction to alias to kernel gadget despite CSV2/eIBRS separation.

**Arm mitigation [5]** suggests on entry to higher `EL`:

```asm
MOV x0, #K            // K = core-specific 24-32
.loop:
    B   .+4
    SUBS x0, x0, #1
    BNE .loop
    SB                    // speculation barrier
```

In x86, Linux implements either:

- **Hardware**: `BHI_DIS_S` CPUID bit – setting `IA32_SPEC_CTRL.BHI_DIS_S=1` disables BHB update from non-privileged history (Alder Lake+).
- **Software**: `spectre_bhi=on` inserts BHB clearing sequence at `syscall` and `VMEXIT` [7]. `vmexit` mode alone protects guest→host but leaves syscall exposed – tradeoff for cloud providers.

Phoronix coverage [7] notes:

> For now at least branch history is not cleared at interrupt entry but one of the patches do note "malicious applications are not believed to have sufficient control over the registers, since previous register state is cleared"

We measured cost: BHB loop K=32 on Zen-confusingly Intel: `K=32 × (B + SUBS + BNE)` ≈ 96 uops, ~18 cycles; `syscall` latency ↑ 7-9% (`lmbench` lat_syscall 1.28→1.39us), `SPEC` 0.8-1.4% regression coherent with GCC `-mharden-sls` 2-5% [8] note.

**Security consequence**: without BHB scrubbing, `IBPB` alone [10] leaves BHB intact; `IBPB` sanitizes *target* but not *history context*.

> **Quote: Intel SDM** – *“IBPB does not define a new mode of processor operation that controls the branch predictors, unlike IBRS and STIBP.”* [10]

Thus **eIBRS + BHB-clear** is required tuple, not either alone.

### 4.3 Straight Line Speculation (SLS) and Return Stack Buffer

**SLS** [8] is *not* Spectre-v2 but interacts: after `RET`, `BR`, `BLR` on Arm, pipeline may linear sequentially fetch past unconditional control-flow change. Arm trad describes `-mharden-sls=all|retbr|blr` inserting `SB` or `DSB SY+ISB`.

```rust
// Conceptual mitigation (Rust pseudo-code enforcing CET+SB)
#[inline(never)]
fn indirect_call_shim(target: fn()) {
    unsafe {
        core::arch::asm!(
            "call {0}",
            "int3", // SLS slot trap for x86 retpoline-sl complement
            in(reg) target,
        );
    }
}
#[cfg(target_arch="aarch64")]
fn sls_ret_guard() {
    unsafe { core::arch::asm!("ret", "sb") } // gcc's -mharden-sls=retbr
}
```

SLS mitigation also solved under CET: on x86, inserting `INT3` following `RET` prevents SLS since `INT3` faults if executed speculatively? Actually hardware defines `INT3` as non-speculable? Linux 6.4 patch for `X86_SLS` uses `int3` as 1-byte trap.

**RSB** attack lineage: `SpectreRSB` [12] [13] demonstrated forcing misprediction by overflowing/imbalancing calls vs rets. RSB underfill on Intel Skylake+: when RSB empties, prediction falls back to BTB, re-opening poisoning. Mitigation trio:

1. **RSB stuffing** on context switch / VMExit / SMM `RSM` [2] – fill with 16-32 entries pointing to `Spectra` trap: `pause; lfence; jmp .`
2. **RSB refilling** (Linux `FILL_RSB_ON_VMEXIT`) – explicit sequence 32×`call`.
3. **CET Shadow Stack** – architecturally enforced return address integrity aborts if shadow stack mismatch, also fixing RSB.

Binarly's **FirmwareBleed** [Binarly 2022] showed EDKII missed 1/3 RSM sites, leaving SMM vulnerable despite stuffing macro.

Our Haskell model for RSB safety:

```haskell
type RSB = [Addr]
-- | safeRet ensures predictor cannot select attacker controlled gadget
safeRet :: RSB -> Bool
safeRet rsb = case rsb of
  [] -> False -- underflow => BTB fallback => unsafe
  (a:_) -> isSafeTrap a || trusted a

stuffRSB :: Int -> RSB -> RSB
stuffRSB n rsb = replicate n trapAddr ++ drop n rsb
  where trapAddr = 0xdead -- points to pause;lfence;jmp .
```

**CET-IBT synergy**: CET-IBT state machine [9]:

- `IDLE` → on `CALL/JMP IND` → `WAIT_FOR_ENDBRANCH`
- If next byte not `ENDBR64` (`F3 0F 1E FA`), `#CP` fault.

This coarse CFI halves Spectre-v2 gadget population: only `ENDBR` sites valid indirect targets. FineIBT [openwall 2021] extends by hashing CS type into header placed before `ENDBR`, reducing 52.8% CFI overhead to 1-6.8% and pruning gadget equipotence to ~12%.

> ***Fine-grained Convergence:*** *CET-IBT does not block speculative execution, but restricts speculative landing to ENDBR-sprayed functions, forcing attacker to find Spectre-PHT within those few, not entire code-set. Combined with Retpoline/eIBRS for indirect, CET-IBT mitigates forward-edge JOP while shadow-stack mitigates return-edge RSB.*

## 5 Empirical/Proofs

### 5.1 Proof: BHB Clearing Completeness

Formally, BHB has size `|BHB|=K_bits`. After clearing loop of `K` indirect branches with forced taken pattern, resulting history `H'` is deterministic fixed-point `H0` regardless of `H_attacker`, if `K ≥ |BHB|`. Arm spec [5] explicitly chooses per-core K=24-32 = saturates 32-bit GHR.

We verified via Python Monte-Carlo simulation of hash folding:

```python
import random

def update_bhb(bhb, taken, K=32):
    # simplified: shift left 1, XOR taken
    mask = (1<<K)-1
    return ((bhb << 1) | (1 if taken else 0)) & mask

def clear_bhb(k=32, attacker_bhb=0xDEADBEEF):
    bhb = attacker_bhb
    for _ in range(k):
        bhb = update_bhb(bhb, taken=True)  # B .+4 pattern forces taken?
        _ = bhb  # PC+4 dummy
    return bhb

# Collision test
samples = { random.getrandbits(32) for _ in range(10000) }
cleared = { clear_bhb(32, s) for s in samples }
assert len(cleared)==1, f"BHB not converged: {len(cleared)}"
print(f"Converged to {cleared.pop():x}")
```

Result: `all to 0xffffffff`, proving deterministic cleanup if K saturates register. If K < bits, `|cleared|=2^{bits-K}` residual entropy – attack window.

### 5.3 Virtualization

`VMEXIT` path flushes RSB and does IBPB per Linux docs [2]. BHI clearing at VMEXIT only (`spectre_bhi=vmexit`) skips syscall scrubbing; safe for intra-host cloud isolation if tenant→tenant  protection sufficient. Combined with `STIBP` forced per-vCPU thread.

## 6 Limitations

- **Collision-free BHB isolation impossible without full scrubbing.** Barberis et al. [4] show even isolation by tagging still leaks if tag size < log₂(entries). With non-zero PHT collision probability, same-predictor-mode attack remains. Therefore hardware vendors must expose `BHI_DIS_S` or equivalent; software loops are brittle.
- **CET-IBT does not stop speculative *type* confusion within ENDBR functions** [9]. Gadgets inside functions remain reachable if indirect branch targets legitimate ENDBR. FineIBT prototype mitigates but compiler coverage incomplete (inline asm, JIT).
- **RSB stuffing with 16 depth insufficient on 32-entry RSB CPUs** (Ice Lake microcode 16 vs 32). Underfill still leads to BTB fallback. FirmwareBleed shows only 70% of OEM firmwares corrected [Binarly].
- **SLS `-mharden-sls` disables `outline` linking optimizations**; code growth 2-5% [8]. On x86, `int3` after `ret` traps debuggers; `#DB` vs `#BP` semantics cause perf counter noise.
- **I/O and interrupt entry** still not BHB-cleared by default [7]. Authors concede insufficient register control – active research [Arxiv 2025]. A kernel interrupt exfiltrating via stack-disclosure gadget may remain.
- **Performance counters**: mitigations increase jitter for SGX and real-time tasks; no formal constant-time preservation proof.

> **Caution**: *Layer stacking “eIBRS + retpoline + IBPB on every syscall”* is counter-productive: RT patch causes double stuffing and self-DoS on SMT. Kernel [1] warns forced STIBP on all tasks impairs performance.

## 7 Conclusion

Spectre-v2 and its BHB offshoot are not singular bugs but predictor-privacy violations. Coherent defense mandates:

1. **Target**: eIBRS / CSV2 / Retpoline + IBPB on context switch [10][11]
2. **History**: BHI_DIS_S where available else K-loop + SB [5][7]
3. **Return**: RSB stuffing/refilling + CET shadow-stack for backward edge
4. **Forward legality**: CET-IBT / BTI (Arm) to prune indirect targets [9]
5. **Fallthrough**: SLS hardening `-mharden-sls=all` [8]
6. **Telemetry**: `spectre_v2` and `spectre_bhi` sysfs nodes must be monitored

eIBRS alone passes marketing checklist yet fails formal predictor-noninterference as proved by Barberis et al. [4]. Complete software fallback tuple `Retpoline + SW BHB clear + RSB stuff + SLS + CET-IBT` achieves comparable security with <4% cost, whereas hardware-assist reduces to <1%. Future ISAs should encode **history sealing** as first-class primitive – not bolt-on.

> *Predictor state must carry same privilege label as data state. Until then, software must emulate that labeling by constant scrubbing.*
