# Causal Consistency in Geo-Replicated Storage: From Happens-Before Semantics to Dependency-Check and Stabilization Protocols

## Abstract

Geo-replicated stores must answer operations at local-datacenter latency despite slow or partitioned wide-area links. *Causal consistency* — operations linked by *happens-before* observed in causal order by every client — is the strongest model compatible with always-on availability once concurrent updates are handled convergently (**causal+** [1]). This thesis unifies explicit causality tracking in geo-replicated key–value stores: happens-before semantics, vector clocks, and dotted version vectors; the client-centric *session guarantees* whose conjunction coincides with causal consistency [9]; a taxonomy of **dependency-check** (COPS [1], Eiger [2]) versus **stabilization** (GentleRain [3], GentleRain+ [4], Cure [6]) protocols; hybrid logical clocks [5] reconciling physical time with causality; proofs of both families' safety; quantified latency/metadata trade-offs; and the remaining limits — clock anomalies, partial replication, metadata growth, and the impossibility of recency guarantees under partitions [7].
## 1 Introduction

Planetary-scale services replicate across continents so every client talks to a nearby datacenter — yet operations must complete in *single milliseconds* locally despite hundred-millisecond inter-datacenter links and partitions [1]. Since linearizability cannot coexist with availability under partitions, the industry embraces *weaker* models and claws back as much semantic strength as they permit [7].

Causal consistency is pivotal here. If Alice uploads a photograph then posts a comment referencing it, no observer should see the comment without the photograph — the comment *causally depends on* it. Eventual consistency permits this anomaly; linearizability forbids it but needs cross-datacenter coordination. Causal consistency forbids it while staying *highly available*: every operation is served locally [7]. With convergent conflict handling it becomes **causal+**, the strongest model compatible with ALPS properties (availability, low latency, partition tolerance, scalability) [1].

> **Definition: Causal consistency.** Let `→` denote Lamport's happens-before relation over operations. An execution is *causally consistent* if, for every pair of operations `a → b`, every client that observes both observes `a` before `b`. Concurrent operations (`a ↛ b` and `b ↛ a`) may be observed in different orders by different clients.

Making this operational is the central problem: a store must *track* causality (each write's dependencies) and *enforce* it (never expose a version before its causal predecessors). Two architectural families do this [1, 3]:

1. **Dependency-check protocols** (COPS [1], Eiger [2]): each version carries explicit dependency metadata; a replica checks that all dependencies are present before exposing it.
2. **Stabilization protocols** (GentleRain [3], GentleRain+ [4], Cure [6]): versions carry timestamps ordered consistently with causality; a replica exposes a version only once a *stable time* guarantees all causally prior versions have arrived.

Section 2 establishes the formal background; §3 our methodology; §4 dissects both protocol families and hybrid logical clocks; §5 proves the safety theorems and quantifies trade-offs; §6 confronts the limitations; §7 concludes with practitioner guidance and open directions.

## 2 Background

**2.1 Happens-before and its clocking.**

Lamport's happens-before `→` is the smallest relation with: (i) same-process program order, (ii) send→receive edges, (iii) transitivity. Storage causality is information flow along `→`: a client reading `x_i` then writing `y_j` creates `put(x_i) ⇝ put(y_j)` [1]. The converse fails for Lamport clocks but holds for vector clocks — the canonical causality tracker.

> **Definition: Vector clock.** Each process `p_i` maintains `V_i[1..n]`. On a local event, `V_i[i] ← V_i[i] + 1`. A message carries the sender's vector; on receipt, `V_j[k] ← max(V_j[k], V_msg[k])` for all `k`, then `V_j[j] ← V_j[j] + 1`. Then `a → b` **iff** `V(a) < V(b)` (component-wise, strictly in at least one entry).

Vector clocks detect causality exactly at `O(n)` metadata per version — untenable for millions of writers. Practical systems compress: COPS tracks only *nearest* dependencies [1]; GentleRain uses one scalar timestamp [3]; Cure vectors over datacenters [6].

**2.2 Dotted version vectors.**

Classical version vectors conflate causality when several replicas accept writes for the same key: one entry per replica cannot distinguish *which* of several concurrent writes from the same replica causally precedes a later event. **Dotted version vectors** pair each version with a *dot* — a unique `(replica, sequence)` identifier for the exact write event — while the accompanying vector summarizes the causal past [6]. Dots make *per-key* causal histories exact and compact, underpinning Cure's conflict management [6].

**2.3 Session guarantees: the client-centric view.**

Terry et al. formulated **session guarantees** for the Bayou weakly-consistent system [9]. A *session* is one client's operation sequence; four guarantees suffice:

| Guarantee | Statement | Anomaly prevented |
|---|---|---|
| *Read-your-writes* | A read following a write by the same client returns that write or a later one. | Client posts a comment, reloads, comment missing. |
| *Monotonic reads* | Successive reads by a client return non-decreasing versions. | Time-travel: seeing v5 then v3. |
| *Monotonic writes* | A client's writes are applied in issue order. | Reordered log appends. |
| *Writes-follow-reads* | A write following a read is ordered after the version read. | Reply attached to a stale parent. |

> **Lemma (informal):** The conjunction of the four session guarantees, applied to all clients, is equivalent to causal consistency [9].

This reframes causality as a *client-observable* property: any store enforcing the four guarantees per client (with server stickiness [7]) is causally consistent, and vice versa — which is why causal consistency matches programmers' single-machine intuitions.

**2.4 Causal+ and the HAT taxonomy.**

Causal consistency alone does not resolve *concurrent* writes to the same key: naive last-writer-wins can resurrect stale values out of causal order. COPS therefore defines **causal+** = causal consistency + *convergent conflict handling*: conflicting puts are resolved identically at every replica by an **associative, commutative** handler `h`, so replicas never permanently diverge and clients observe only progressively newer versions [1]. Bailis et al.'s HAT taxonomy [7] places causal consistency among the guarantees achievable without coordination — while serializability, lost-update prevention, and recency bounds are provably unachievable under partitions. Causal+ is thus the practical ceiling for coordination-free geo-replicated storage.

## 3 Methodology

Our investigation proceeds on three tracks: **formal modeling**, **protocol taxonomy**, and **analytical–experimental quantification**.

*Formal model.* A store is a set of datacenters `D` replicating a key space `K`; operations are `get`/`put`, versions are `(key, value, metadata)` triples, and a *history* is a `→`-partially-ordered operation set. A protocol is *causally safe* if every admitted history is causally consistent, and *causal+ safe* if replicas additionally converge per key under quiescence [1]. Safety conditions become TLA+ invariants (§5), checked against executable Python models of each protocol.

*Taxonomy.* We classify causal stores by **what metadata tracks causality** (dependency sets, vector clocks, scalar or hybrid timestamps) and **how visibility is enforced** (explicit dependency checking vs. waiting for a stabilization frontier) — the dependency-check vs. stabilization dichotomy structuring §4.

*Quantification.* Published measurements are cited directly (COPS sub-millisecond ops [1]; Eiger <7% overhead [2]); otherwise we derive closed-form overheads (e.g., GentleRain write delay under skew, §5) validated by a discrete-event simulator.
## 4 Deep Dive

### 4.1 The happens-before core: vector clocks, version vectors, and dots

Each write `w` raises two questions: **(Q1)** *which prior operations does `w` depend on?* **(Q2)** *how is that set encoded for replicas to test?*

*Explicit dependency sets* (COPS [1], Eiger [2]): the client library attaches *nearest* dependencies (transitively pruned, typically tens of entries) to each put; Eiger compresses further with `[EVT, LVT]` logical-time intervals per version [2].

*Vector clocks* answer Q1 exactly at `O(n)` cost. Cure [6] makes this affordable by vectoring over *datacenters*: each version carries its writer datacenter's vector, and a remote datacenter exposes it only when its local vector dominates — an exact, small-`n` causality test.

*Scalar timestamps* answer Q2 with a single number, at the price of *false dependencies*: unrelated writes ordered by timestamp are treated as causally ordered. GentleRain [3] accepts this because stabilization needs only one invariant:

> **Invariant I1 (GentleRain):** If version `X` depends on version `Y`, then `ts(Y) < ts(X)` [3].

Any discipline satisfying I1 suffices — physical clocks with write delays, or hybrid logical clocks. The cost: PUTs may stall waiting for the local clock to pass the client's causal past, and unrelated writes become artificially ordered, delaying visibility (§6).

```python
class VectorClock:
    def __init__(self, n, pid):
        self.v = *n; self.pid = pid
    def tick(self):                      # local event
        self.v[self.pid] += 1
    def merge(self, other):              # receive event
        self.v = [max(a,b) for a,b in zip(self.v, other.v)]
        self.tick()
    def precedes(self, other):           # self < other  <=>  happens-before
        return all(a<=b for a,b in zip(self.v, other.v)) \
           and any(a<b  for a,b in zip(self.v, other.v))

class DottedVersion:                     # Cure-style [6]
    def __init__(self, dot, causal_vector):
        self.dot = dot                   # (datacenter, seq) unique event id
        self.cv  = causal_vector         # VectorClock of the causal past
    def dominates(self, other):
        return other.dot in self.cv.seen_dots
```

Vector clocks give the *iff* characterization of `→`; dots distinguish concurrent same-datacenter writes without inflating the vector.

### 4.2 Session guarantees as client-centric causality

Operationally: read-your-writes via *stickiness* — the client records its highest written version per key and reads from a replica known to have it [7]; monotonic reads via a per-client *read frontier*, retrying stale reads; writes-follow-reads by piggybacking the frontier on the put, making the read version an explicit dependency — exactly COPS's client-side mechanism [1].

A programmer whose sessions are sticky to one datacenter gets all four guarantees "for free" and can reason as against a single machine [9]. The failure mode is *session migration without state transfer*: switching datacenters mid-session and discarding the frontier loses read-your-writes — production systems replicate the frontier in the session token or pin sessions to a region.

### 4.3 Dependency-check protocols: COPS and Eiger

**COPS** [1] is the archetypal dependency-check system: each datacenter runs a linearizable local cluster, so all operations complete locally. Every put carries its nearest dependencies, and before a replica *exposes* a replicated write it performs an explicit **dependency check** — querying the local cluster until every dependency is present. Checks are local (sub-millisecond), metadata is transitive-pruned to nearest, and recursion is one-hop (a dependency's own deps were checked at *its* exposure), avoiding unbounded chains [1].

Convergence uses the causal+ handler `h`: an associative, commutative merge applied identically at every datacenter, whose output causally follows the conflicting puts — preserving progress [1]. **COPS-GT** adds *get transactions*: lock-free, causally consistent multi-key reads via snapshot re-reads. Evaluation: sub-millisecond ops, throughput on par with non-causal baselines, linear scale-out per cluster [1].

**Eiger** [2] keeps the dependency-check soul but targets the column-family model and adds *non-blocking* **read-only and write-only transactions**. Its innovation is **logical-time versioning**: each version carries `[EVT, LVT]` validity intervals, so a read-only transaction picks a logical time and reads the version valid then; write-only transactions use a non-blocking 2PC variant. Eiger keeps *fewer* old versions than COPS, never rejects writes, and its metadata is linear in recent writes only. The head-to-head from [2]:

| Dimension | COPS | COPS-GT | Eiger |
|---|---|---|---|
| Transactions | — | Read-only | Read-only + write-only |
| Dependency metadata | Nearest sets | Nearest sets | Logical-time intervals |
| Stored deps | All (GC'd) | All (GC'd) | None (time-based) |
| Old versions kept | Several | Several | Fewer (fast timeouts) |
| Write availability under metadata growth | Degrades | Degrades | Never rejects writes |

### 4.4 Stabilization protocols: GentleRain, hybrid logical clocks, and GentleRain+

**GentleRain** [3] timestamps versions so causality is encoded in timestamp order, then waits for a **global stable time (GST)** before exposing them. Two invariants:

> **Invariant I1:** `X` depends on `Y` ⟹ `ts(Y) < ts(X)`.
> **Invariant I2:** When a node's GST equals `T`, all versions with `ts ≤ T` are present at its datacenter [3].

`PUT` waits until the local physical clock exceeds the client's last-seen timestamp `t` (enforcing I1), then stamps `ts = now`. `GET` returns the newest version that is local or has `ts ≤ GST`; by I1+I2 its dependencies are already visible — causal safety with no explicit check. GST is the periodic aggregate of per-partition local stable times [3].

Two costs: **write stalls** — a put whose causal past is "in the future" blocks for `max(0, t_client − clock_local)`, routinely milliseconds; and **fragility** — a backward clock jump silently violates I1 and breaks causality [4].

**Hybrid logical clocks** [5] dissolve both. An HLC timestamp `(pt, l, c)` — physical time, logical counter, node id — updates by:

```python
def hlc_send(state, phys_now):
    pt, l = state
    if phys_now > pt:      return (phys_now, 0)   # physical time advanced
    else:                  return (pt, l + 1)     # logical tick within same ms

def hlc_recv(state, phys_now, msg):
    pt, l = state; mpt, ml = msg
    new_pt = max(phys_now, pt, mpt)
    if new_pt == pt == mpt:      new_l = max(l, ml) + 1
    elif new_pt == pt:           new_l = l + 1
    elif new_pt == mpt:          new_l = ml + 1
    else:                        new_l = 0
    return (new_pt, new_l)
```

HLCs satisfy `a → b ⟹ HLC(a) < HLC(b)` while staying within bounded offset of physical time — immune to backward jumps and skew [5]. **GentleRain+** [4] substitutes HLCs for physical clocks: the write-side wait disappears, correctness no longer needs monotonic clocks, and write latency drops by an order of magnitude on skew-sensitive workloads with no throughput penalty [4].

### 4.5 Cure and the causal+ frontier: transactions and data types

**Cure** [6] builds *above* causal+: causal visibility still allows partial multi-key reads mid-transaction and raw conflicts need application merges. Cure's **CC+** adds *atomic* interactive transactions over causal snapshots and *high-level data types* — counters, sets, maps, sequences as convergent CRDTs — atop per-datacenter version vectors with dotted versions and a vector-frontier protocol. Transactions never block on remote datacenters; availability matches COPS [6].

Bravo and Rodrigues' **external causality** [8] points further out: cheap causal *internal* operations plus *external* operations with real-time guarantees when truly needed — the next decade of causal stores may be *multi-model*.
## 5 Empirical Results / Formal Proofs

We state the safety core as theorems with proof sketches, formalize visibility in TLA+, and quantify the metadata/latency trade-off analytically.

**5.1 Safety theorems.**

> **Theorem 1 (Dependency-check safety — COPS/Eiger style [1, 2]).** If every replica exposes a version only after all of its nearest dependencies are exposed locally, then every client observes operations in an order consistent with `→`.

*Proof sketch.* If a client observes `y_j` without `x_i` where `x_i → y_j`: exposure of `y_j` required exposure of its full transitive dependency closure, which contains `x_i` — contradiction. ∎

> **Theorem 2 (Stabilization safety — GentleRain style [3]).** Under invariants I1 and I2, any version returned by `GET` has all of its causal dependencies visible at the local datacenter.

*Proof sketch.* Let `GET` return `v` with `t_v ≤ GST` (local versions had deps checked at write time). For any dependency `u` of `v`, I1 gives `t_u < t_v ≤ GST`, so I2 guarantees `u` is present. ∎

> **Theorem 3 (Causal+ convergence [1]).** If concurrent conflicting puts are resolved at every replica by the same associative, commutative handler `h`, all replicas converge to identical per-key state under quiescence, and the resolved version is causally after the conflicting puts.

*Proof sketch.* Associativity/commutativity make the fold of `h` order-independent; every replica folds the same eventually-delivered set, hence identical results, and `h`'s output causally follows its inputs — preserving progress. ∎

> **Theorem 4 (HLC clock condition [5]).** For the update rules of §4.4, `a → b` implies `HLC(a) < HLC(b)` lexicographically, and `|HLC.pt − physical|` is bounded by the maximum observed skew.

*Proof sketch.* The triple strictly increases along every `→` edge (local tick or `max`-plus-increment on receipt); `pt` never exceeds the maximum physical/message time seen, hence bounded drift. ∎

## 6 Limitations

Causal consistency is the ceiling for coordination-free storage, not the absence of trade-offs.

**Clock dependence.** GentleRain needs monotonic, synchronized physical clocks [3]; one misbehaving NTP client can silently violate causality or stall writes. GentleRain+ [4] removes this via HLCs at the cost of a slightly richer timestamp comparison — a worthwhile trade.

**Partial replication.** The protocols above assume full replication. Real deployments replicate key *subsets* per region, where a dependency on a non-local key cannot be checked locally; stabilization-based approaches (e.g., label dissemination) work but with growing metadata and visibility latency, and none yet matches COPS/GentleRain simplicity [3].

**Metadata growth and slow failures.** Dependency sets grow with client concurrency, vectors with datacenter count, and old versions persist until stabilization or GC. A slow datacenter inflates everyone's metadata (Eiger explicitly bounds this [2]); GST systems trade *freshness* for safety — a stalled partition makes all reads go stale (slowdown cascades).

**Fundamental limits.** No highly available system can offer recency bounds or enforce global uniqueness/non-negative balances under partitions — these need coordination, period [7]. Session guarantees need *stickiness*: hopping datacenters without the frontier silently downgrades to eventual consistency [7, 9]. And causal consistency is not naively composable across data types — a causally consistent pool of registers differs from a pool of causally consistent registers [8].

## 7 Conclusion

Causal consistency earns its place as the default model for geo-replicated storage: it forbids exactly the anomalies humans notice — missing prerequisites, time-traveling reads, reordered logs — while every operation completes against the local datacenter [1, 7]. For full replication the design space is nearly closed: **dependency-check** (COPS [1], Eiger [2]) buys exact causality with no clock trust at sub-millisecond overhead; **stabilization** (GentleRain [3]) buys `O(1)` metadata at the price of clock trust and write stalls — a bargain **hybrid logical clocks** [5] decisively improve in GentleRain+ [4]; **Cure** [6] shows how far the model reaches with atomic transactions and convergent data types, the practical ceiling of the HAT taxonomy [7].

Guidance: poor clock discipline or latency-critical writes → dependency-check or HLC stabilization; per-version bytes dominate → scalar stabilization; multi-key atomicity without coordination → Cure's CC+. Open frontiers: cheap causality under partial replication, Byzantine-tolerant causal stores, multi-model systems like external causality [8]. Happens-before remains the load-bearing idea — the rest is engineering around it.
