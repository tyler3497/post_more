# gVisor Application Kernel: The Sentry Platform Layer, Go-Based Memory Management, KVM Acceleration, and Container Escape Mitigation

## Abstract

Container runtimes built on Linux namespaces expose the full host system call surface — roughly four hundred entry points — to every sandboxed process, and history shows a single exploitable call suffices for container escape. This thesis presents a rigorous treatment of **gVisor**, Google's application kernel, which replaces namespace isolation with a userspace kernel, the *Sentry*, written in memory-safe Go and interposed between workload and host. We dissect the platform layer that intercepts syscalls via ptrace, KVM, or the newer systrap mechanism; the Go-based memory manager re-implementing address spaces and page faults; and the defense-in-depth stack — seccomp-bpf, a ~53-syscall host ABI, the Gofer filesystem proxy, and a userspace netstack — that makes escape infeasible without a second independent vulnerability. Drawing on primary gVisor documentation and an MIT container/VM study, we quantify interception costs (~6.2 µs per getpid under systrap with user dispatch) and formalize the isolation guarantee as a theorem of *interface narrowing*. We close with open problems in side-channel coverage, ABI completeness, and device support.

## 1 Introduction

Operating-system-level virtualization has become the substrate of modern cloud infrastructure, yet its security posture rests on a precarious foundation. A standard container shares its kernel with every other tenant on the host; the *threat boundary* is therefore the entire Linux system call interface, comprising roughly 450 entry points on x86-64, of which a historically disproportionate fraction — `socket`, `open`, `clone`, `bpf`, `keyctl` — has been implicated in privilege-escalation exploits. The *adversarial model* for multi-tenant clouds is unforgiving: the attacker controls arbitrary code execution inside the sandbox, and must be denied any channel to the host kernel or to co-tenant state.

**gVisor** answers this problem with an architectural relocation of the kernel boundary. Rather than filtering which host syscalls a container may invoke — the strategy of seccomp-bpf profiles — gVisor *interposes a new kernel* between the workload and the host. The **Sentry** is a from-scratch reimplementation of the Linux system call ABI, process model, memory management, virtual filesystems, and TCP/IP stack, written in the memory-safe Go language and running as an ordinary, unprivileged userspace process [1]. Every system call issued by the sandboxed workload is intercepted by the *platform layer* and redirected into the Sentry; **no workload syscall is ever passed through to the host kernel**. Host interaction is restricted to a fixed, narrow ABI of roughly fifty to seventy syscalls (depending on platform and networking mode), each individually reviewed, and the Sentry itself is further confined by seccomp-bpf, namespaces, and minimal capabilities [2][5].

This thesis is organized as follows. Section 2 situates gVisor among namespace containers, microVMs, and unikernels. Section 3 describes our documentary and analytical methodology. Section 4 is the technical core: we examine the Sentry's process and threading model, the platform layer's three interception strategies (ptrace, KVM, systrap), the Go-based memory manager, the Gofer/netstack I/O architecture, and the escape-mitigation argument. Section 5 presents empirical interception costs and a formal isolation theorem. Section 6 discusses limitations — partial ABI coverage, syscall-heavy workload overhead, and side channels — and Section 7 concludes.

## 2 Background and Related Work

### 2.1 The container isolation problem

Classical containers (Docker on `runc`) isolate via Linux namespaces (PID, mount, network, UTS, IPC, user) and resource-control cgroups. The security-critical observation is that *namespaces virtualize identity, not the kernel interface*: all containers on a host execute system calls against the same monolithic kernel. Empirical exploit history — CVE-2019-5736 (`runc` container breakout via `/proc/self/exe`), the long series of `bpf()` and `userfaultfd` vulnerabilities — demonstrates that interface breadth is the dominant risk factor. A 2023 MIT course analysis of Firecracker and gVisor frames the design space explicitly as a spectrum from *paravirtualized syscall interposition* (gVisor) to *hardware-virtualized guests* (Firecracker/KVM), noting that gVisor "uses paravirtualization to isolate containerized applications from the host system without the heavyweight resource allocation that comes with full virtual machines" [3].

### 2.2 Alternative isolation technologies

| Technology | Isolation primitive | Trust boundary | Typical overhead |
|---|---|---|---|
| `runc` containers | Namespaces + cgroups + seccomp | Host kernel syscall ABI (~450 calls) | ~0% |
| **gVisor (`runsc`)** | Userspace kernel + syscall interception | Sentry (~274 implemented of ~350) + ~53 host calls | 2–30% (workload-dependent) |
| Kata Containers | Hardware-virtualized microVM per pod | Guest kernel | ~100–300 ms boot |
| Firecracker | KVM microVM per function | Guest kernel + VMM | ~125 ms boot |
| Unikernels | Library OS, single address space | Hypervisor | Variable |

gVisor occupies a distinctive point in this space: it retains the *process model* (no virtualized hardware layer, no guest kernel) while achieving isolation *stronger than namespace filtering* and *cheaper than a VM* [6]. As the gVisor architecture documentation states, "gVisor acts as an application kernel, but runs in userspace," handling system calls and page faults from the workload entirely within memory-safe Go code [1].

### 2.3 Language-based safety as a security primitive

The decision to write the Sentry in Go is a deliberate *memory-safety* defense. A substantial fraction of historical kernel vulnerabilities are memory-corruption bugs (use-after-free, buffer overflows, uninitialized reads). By implementing the syscall surface in a garbage-collected, bounds-checked language, gVisor eliminates entire bug classes from the most-exposed code — the code that parses untrusted, attacker-controlled syscall arguments. This mirrors the rationale of Rust-based kernel experiments (e.g., RedLeaf, Theseus) while retaining Go's mature concurrency model, which maps naturally onto the Sentry's goroutine-per-task threading design.

## 3 Methodology

This thesis is primarily an *architectural analysis* grounded in primary sources: the gVisor architecture guides [1][2], the gVisor source repository's platform-layer commits (notably the systrap user-dispatch work [4]), independent security evaluations [6], a Kubernetes-focused threat-model exposition [5], and the MIT comparative study of Firecracker and gVisor [3], supplemented by a 2019 Software Engineering Daily interview with gVisor engineers on overhead characterization [7].

Our method has three components:

1. **Documentary reconstruction.** We trace the syscall path from workload trap to Sentry dispatch to host-kernel interaction across the three platform backends, extracting the exact interception mechanism (PTRACE_SYSEMU, KVM world-switch, seccomp-notify + `PR_SET_SYSCALL_USER_DISPATCH`) and the confinement policy applied to each.
2. **Quantitative synthesis.** We compile published interception-cost measurements (per-syscall latencies, workload-level overhead bands) into a coherent performance model, identifying the regimes where each platform dominates.
3. **Formal reduction.** We state the isolation guarantee as a theorem of interface narrowing and defense-in-depth composition, making explicit the assumptions (Go memory safety, seccomp correctness, no shared mutable host state) on which the guarantee rests.

We do not claim novel measurements; our contribution is the integrated, formally stated analysis that the primary sources imply but do not assemble.

## 4 Deep Dive

### 4.1 The Sentry: a userspace kernel in Go

The Sentry is the largest component of gVisor and is best understood as a *userspace operating system kernel*. It implements, from scratch:

- **The system call interface** — approximately 274 of ~350 amd64 syscalls, fully or partially, presenting an environment equivalent to upstream Linux v4.4 [2].
- **Process and thread management** — its own PID table, `clone`/`fork`/`execve` semantics, and signal delivery. Crucially, sandboxed processes are *not* host processes: `top` on the host does not display them [1].
- **Memory management** — a full virtual-memory subsystem (Section 4.3).
- **Virtual filesystems** — tmpfs, procfs, sysfs, devpts, and FUSE-like host bridging, with out-of-sandbox file operations delegated to the Gofer.
- **Networking** — a userspace TCP/IP stack (*netstack*) bound to an `AF_PACKET` socket on a veth device, so the workload observes ordinary sockets while the host boundary stays intact [1].

The Sentry's threading model maps each sandboxed task to a set of goroutines, exploiting Go's lightweight concurrency to multiplex tens of thousands of sandboxed threads over a modest pool of host threads. The Sentry presents *one kernel per sandbox*: each container (or pod) receives its own Sentry instance, so kernel-state sharing across tenants is eliminated by construction — there is no global dentry cache, no shared socket table, no cross-container `/proc`.

> **Theorem (Interface Narrowing).** *Let H be the set of host syscalls reachable by a native container (|H| ≈ 450) and let S be the set reachable through the Sentry (|S| ≈ 53–68, fixed and audited). If the Sentry never forwards a workload syscall to the host and the platform layer cannot be bypassed, then any host-kernel exploit requires a vulnerability in S rather than in H ∖ S — reducing the exposed attack surface by roughly an order of magnitude.*

The theorem's second premise — non-bypassability of interception — is discharged by the platform layer, to which we now turn.

### 4.2 The platform layer: ptrace, KVM, and systrap

gVisor requires a *platform* to implement three primitives: syscall interception, basic context switching, and memory mapping [2]. Three backends exist, each a different point on the security/performance/portability triangle:

| Platform | Mechanism | Isolation strength | Relative syscall cost | Requirements |
|---|---|---|---|---|
| **ptrace** | `PTRACE_SYSEMU` — Sentry debugs the workload, emulating syscalls without executing them | Good | Highest (multiple context switches per syscall) | Anywhere ptrace works |
| **KVM** | Sentry acts as both guest OS and VMM; workload runs in *guest mode*, traps via VM-exit | Strongest (hardware boundary) | Low | `/dev/kvm`, bare metal or nested virt |
| **systrap** | seccomp-notify + syscall user dispatch (`PR_SET_SYSCALL_USER_DISPATCH`); traps handled by in-process syscall threads | Good | Low–moderate | Linux ≥ 5.x, no special hardware |

**ptrace.** The original backend. The Sentry attaches to the workload like a debugger; `PTRACE_SYSEMU` causes the tracee's syscalls to be *emulated* (never executed) while the tracer is notified at each entry. This works even inside VMs without nested virtualization, but each intercepted syscall incurs several host context switches, making syscall-heavy workloads expensive.

**KVM.** The Sentry becomes its own virtual machine monitor: the workload executes in hardware guest mode, and syscalls (plus page faults, privileged instructions) cause VM-exits that the Sentry handles directly. Address-space switches become EPT pointer swaps rather than page-table rewrites, and the hardware boundary adds a second, independent isolation layer. The cost is the `/dev/kvm` requirement and VM-exit latency on the trap path.

**systrap.** The modern default on bare Linux. The workload's syscalls are redirected by seccomp-bpf `SECCOMP_RET_USER_NOTIF` to supervisor threads, and the 2025 *syscall user dispatch* optimization [4] lets the kernel itself vector trapped syscalls to a userspace handler address, cutting the per-syscall cost to approximately **6.2 µs for `getpid`** (down from ~7.0 µs), measured on a cloudtop instance. systrap achieves near-KVM trap costs with no hardware dependency, at the price of a more intricate in-process concurrency design (shared syscall-dispatch contexts, careful TOCTOU avoidance on thread IDs — see the 2026 fix for the `ThreadID` double-read race [4]·commit `2a22300`).

The platform is thus *pluggable*, and the security argument is deliberately *agnostic* to the interception mechanism: what matters is that *all* syscalls are intercepted [7].

### 4.3 Go-based memory management

The Sentry's memory manager (`pkg/sentry/mm`) re-implements a virtual memory subsystem in Go, presenting each sandboxed process with a Linux-compatible address space:

1. **Address-space representation.** Virtual memory areas (VMAs) track mappings with Linux-equivalent semantics: private/shared, anonymous/file-backed, `mmap`/`mprotect`/`munmap`/`mremap`, copy-on-write, and demand paging.
2. **Page-fault handling.** Faults from the workload are delivered to the Sentry (via the platform: signal-based on ptrace/systrap, EPT violation VM-exits on KVM). The Sentry resolves the fault against its VMA tree, populates the page — from the page cache, zero-fill, or the Gofer for file-backed regions — and resumes the workload. The host kernel never observes the workload's page tables.
3. **KVM acceleration.** Under the KVM platform, the Sentry manages *shadow page tables* / EPT mappings so that guest-virtual → host-physical translation is hardware-walked, while the Sentry retains authoritative control of the mapping policy. This is what the architecture guide means by "leverag[ing] virtualization extensions ... to improve isolation and performance of address space switches" [2].
4. **Memory safety dividend.** Page-table and VMA manipulation — historically a rich source of kernel exploits (e.g., dirty-COW-class races) — executes in bounds-checked, garbage-collected Go. Reference counting of physical frames uses Go's type system rather than manual `get_page`/`put_page` discipline.

A simplified illustration of the Sentry's mapping lifecycle (pseudocode in the style of the actual Go implementation):

```go
// Simplified: Sentry establishes a workload mapping.
func (mm *MemoryManager) Map(addr usermem.Addr, length uint64, opts MapOpts) error {
    // 1. Validate against the sandbox's address-space limits.
    ar, ok := mm.layout.ValidMapping(addr, length, opts)
    if !ok {
        return syserr.ENOMEM
    }
    // 2. Insert the VMA into the interval tree; no host syscall involved.
    mm.vmas.AddMapping(ar, opts.ToMappable())
    // 3. Lazily fault pages in on first touch via platform-delivered faults.
    // 4. Under KVM, mirror the mapping into the EPT for hardware walking.
    return mm.platform.MapAddressSpace(mm, ar)
}
```

Note what is absent: no `mmap(2)` on the host per workload mapping (host mappings are coarse, pre-allocated arenas), and no exposure of host page-table state to the workload.

### 4.4 Filesystems, networking, and the Gofer

I/O that must escape the sandbox is mediated by two dedicated components, following the *principle of least privilege*:

- **The Gofer** is a slightly more privileged sidecar process that brokers host filesystem access on the Sentry's behalf. The Sentry itself is *forbidden* from opening host files directly; instead it speaks the 9P protocol to the Gofer, which applies its own policy (read-only mounts, allowlists). Consequently, even a fully compromised Sentry cannot directly read or write arbitrary host files [1][6]. A writable tmpfs may be overlaid to provide complete host-filesystem isolation [3].
- **netstack** is the Sentry's userspace TCP/IP implementation. The workload's `socket`/`connect`/`accept` calls terminate in netstack; packets egress through a raw `AF_PACKET` socket on a veth pair. The host kernel's TCP state machine — a historically fertile attack surface — is never reachable. A `hostinet` mode exists that trades this isolation for native performance, but it is not the default.

Together with the Sentry, this yields a *three-process* trust decomposition (workload → Sentry → Gofer/host), where each layer holds strictly fewer privileges than the one above it.

### 4.5 Container escape mitigation and defense in depth

Container escape requires the attacker to cross from workload code to host-kernel code execution. Against gVisor, the crossing must defeat *all* of the following, in sequence:

1. **The reimplemented ABI.** The workload never speaks to the host kernel; it speaks Go. Exploiting a syscall handler bug yields control of the Sentry, not the host.
2. **The narrowed host ABI.** The Sentry issues only ~53–68 host syscalls, each audited; there is no `bpf`, no `keyctl`, no `userfaultfd` reachable from the sandbox.
3. **seccomp-bpf confinement of the Sentry.** Even the Sentry's host syscalls are filtered; unexpected calls terminate the sandbox.
4. **Namespace and capability confinement.** The Sentry runs unprivileged, in its own namespaces, with minimal capabilities; the Gofer's filesystem view is separately restricted.
5. **Language safety.** The most-exposed parsing code is memory-safe, removing the dominant historical exploit primitive.

> **Theorem (Defense-in-Depth Composition).** *Let p₁…p₅ be the independent per-layer escape probabilities above. The sandbox escape probability is bounded by ∏pᵢ. Because the layers share no code — the Sentry's Go implementation and the host kernel's C implementation are fully disjoint — a single vulnerability cannot simultaneously defeat multiple layers; independence is structural, not assumed.*

This is the precise sense in which gVisor "reduces the attack surface": not by perfect code, but by ensuring that no single bug class, in no single component, suffices for escape [5][6].

## 5 Empirical Results and Proofs

### 5.1 Interception microbenchmarks

Published measurements from the gVisor project and independent harnesses establish the following (amd64, Linux 5.x+):

| Metric | ptrace | systrap (user dispatch) | KVM | Native |
|---|---|---|---|---|
| `getpid` latency | ~15–25 µs | **~6.2 µs** [4] | ~3–5 µs | ~0.1 µs |
| `read`/`write` small | ~20–40 µs | ~8–12 µs | ~5–8 µs | ~0.3 µs |
| Hackbench (pipe/thread) | baseline | −17.6% vs. older systrap [4]·commit `ed4f838` | — | — |
| Redis SET (µs/op) | ~45 | ~28 | ~25 | ~10 |

The systrap user-dispatch optimization reduced `getpid` from 6957 ± 450 ns to 6167 ± 407 ns per operation [4], and a 2026 false-sharing fix in systrap's `contextQueue` improved Hackbench throughput by ~17.6% and geomean benchmark time by ~5.2% [4]·commit `ed4f838`.

### 5.2 Workload-level overhead bands

The gVisor team characterizes overhead by workload shape rather than a single number [7]:

- **CPU-bound, batched I/O** (e.g., ffmpeg transcoding): **~2–5%**.
- **Moderate syscall rates** (web serving, Redis): **~10–15%** latency increase [5].
- **Syscall-saturated micro-workloads**: up to **~30%**.

Independent evaluations concur: syscall-heavy and I/O-heavy workloads are "noticeably slower than runc," while compute-bound workloads run near-native, with a small fixed per-sandbox memory overhead (~15 MB) and ~150 ms startup [6].

### 5.3 Isolation proof sketch

We formalize the Section 4.5 argument. Define the *reachable host interface* R as the set of (syscall, argument-domain) pairs the workload can cause the host kernel to process. **Lemma 1 (Non-bypass).** The platform layer vectors every workload trap (syscall, fault, privileged instruction) to the Sentry; the workload has no executable path to a host syscall instruction that is not first intercepted. *Justification:* ptrace emulates via `PTRACE_SYSEMU`; KVM guest mode cannot execute host syscalls; systrap's seccomp filter plus user dispatch covers the full syscall table, and the filter is installed before workload code runs. **Lemma 2 (Narrowing).** R ⊆ S, the audited ~53–68 syscall set, because the Sentry's host interactions are its only channel to the host. **Theorem.** Any workload-to-host exploit must exploit a vulnerability in the implementation of S, not of the full host ABI. ∎

The proof's assumptions are explicit: correctness of the platform's trap coverage (audited per backend), memory safety of the Sentry's argument parsing (Go), and correctness of the seccomp filter program. Hardware side channels (Spectre/MDS-class) are *outside* the threat model — gVisor provides no defense against them [6] — and we treat this as a stated limitation rather than a gap in the proof.

## 6 Limitations and Open Problems

1. **Partial ABI coverage.** Only ~274 of ~350 amd64 syscalls are implemented (fully or partially) [2]. Workloads depending on unimplemented calls — certain `io_uring` patterns, exotic `prctl` options, some `perf` functionality — fail or degrade. ABI completeness is asymptotic work.
2. **Syscall-heavy workload tax.** The interception cost is fundamental: every syscall pays the trap price. For I/O-saturated services the 10–30% overhead may dominate the security benefit, pushing operators toward `hostinet` or plain `runc` for trusted workloads [5][6].
3. **No side-channel defense.** Spectre, Meltdown, MDS, and cross-tenant cache timing attacks are explicitly out of scope. On shared hardware, gVisor must be composed with core scheduling or hardware mitigations.
4. **GPU and device passthrough.** The Sentry has no device model; workloads needing GPUs, DPDK, or direct hardware access cannot run meaningfully sandboxed. A principled *device platform* for gVisor remains an open research problem.
5. **Concurrency subtlety in systrap.** The in-process trap architecture admits TOCTOU races on shared dispatch state (cf. the 2026 `ThreadID` fix [4]·commit `2a22300`); each such fix is evidence that the fastest platform is also the most intricate to verify.
6. **Formal verification gap.** The isolation theorem of Section 5.3 is a proof sketch over an unaudited-by-machine codebase. Mechanically verifying trap coverage and the Go safety argument (e.g., in Coq or Lean against the Go memory model) is a major open challenge.

## 7 Conclusion

gVisor's application kernel reframes container isolation from *filtering a shared kernel* to *replacing the kernel the workload sees*. The Sentry — a Go userspace kernel implementing the Linux ABI, memory management, filesystems, and networking — interposes on every system call through the ptrace, KVM, or systrap platform layer; KVM acceleration and syscall user dispatch bring interception costs down to single-digit microseconds; and a defense-in-depth stack (narrowed host ABI, seccomp-bpf, the Gofer, netstack, language safety) composes independent mitigations so that escape demands multiple, structurally unrelated vulnerabilities. The price is real but bounded: 2–30% overhead depending on syscall intensity, partial ABI coverage, and no side-channel defense. For multi-tenant clouds executing untrusted code — the precise deployment of Google Cloud Run and GKE Sandbox — this trade is decisively favorable, and the architecture stands as the clearest existing demonstration that *interface narrowing plus memory-safe reimplementation* can deliver VM-adjacent isolation at container density.
