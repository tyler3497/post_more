## 1 Introduction

Cloud computing's original sin is the *semantic gap* between the tenant's trust assumptions and the provider's actual privilege. A tenant's most sensitive data — encryption keys, model weights, patient records — is decrypted *in use* on hardware controlled by a party the tenant has never met, inside a hypervisor the tenant cannot audit, administered by operators the tenant cannot vet. Memory encryption at rest and TLS in transit leave this gap untouched: data in use remains plaintext to anyone with sufficient privilege on the host.

Confidential computing closes the gap with hardware-enforced trusted execution environments (TEEs). The first generation — application-enclave TEEs such as Intel SGX — demanded that software be rewritten against an enclave SDK, a programmability tax that limited adoption to niche workloads. The second generation, VM-based TEEs, removes that tax: an *entire virtual machine* becomes the trust boundary. Two architectures now define this space on x86-64: **Intel Trust Domain Extensions (TDX)**, shipping in 4th-generation Xeon Scalable (Sapphire Rapids) processors, and **AMD SEV-SNP**, shipping in 3rd-generation EPYC (Milan) processors since 2021 [1][2].

Yet "the hypervisor is untrusted" is a slogan, not a security argument. What exactly is measured, who signs the evidence, how freshness is guaranteed, where the performance costs concentrate, and what remains *outside* the protected envelope are questions that demand architectural precision. This thesis answers them through four contributions:

1. A comparative dissection of the TDX and SEV-SNP hardware roots of trust, memory-protection mechanisms, and privilege architectures.
2. A formalization of both attestation flows — TD quote generation and verification, and SNP report issuance and VCEK chain validation — in the vocabulary of the IETF RATS architecture [4].
3. A treatment of measured-boot semantics, including the MRTD/RTMR register file and the vTPM PCR binding problem.
4. A synthesis of peer-reviewed performance measurements against bare metal, real deployment architectures, and the compliance consequences for regulated industries.

## 2 Background

### 2.1 From Enclaves to Confidential VMs

Enclave TEEs partition a *process*: trusted code runs inside an enclave while the OS remains untrusted. CVMs invert the partition: the *entire guest* — kernel, userspace, and applications — is trusted, while everything outside the VM, including the hypervisor, is not. The guest requires no source modification; an unmodified Linux distribution can boot as a confidential guest, with TDX/SEV-SNP-aware drivers handling the paravirtualized boundaries (shared-memory I/O, attestation requests) [6].

### 2.2 Memory Encryption Foundations

Both architectures encrypt DRAM traffic in the memory controller, but differ in cipher and key management:

| Property | Intel TDX | AMD SEV-SNP |
|---|---|---|
| Cipher | AES-XTS-128 (MKTME engine) | AES-128 (SME engine) |
| Key scope | Per-TD ephemeral key | Per-VM key (ASID-tagged) |
| Integrity | MKTME integrity + TDX module checks | Reverse Map Table (RMP) |
| Key management | CPU-generated, never leaves package | AMD Secure Processor |

AMD's lineage is instructive: original SEV (2017, Naples) provided confidentiality only; SEV-ES (Rome, 2019) added encrypted CPU register state on VM exit; SEV-SNP (Milan, 2021) added *integrity* — the missing property that made replay and remapping attacks practical against earlier generations [2]. Integrity without a Merkle tree is achieved through the **Reverse Map Table**: a hardware-walked structure with one entry per 4 KiB system-physical page recording the owning ASID and a validated bit, consulted on every nested page-table walk [2][3].

### 2.3 The RATS Vocabulary

The IETF Remote Attestation Procedures (RATS) architecture (RFC 9334) gives us vendor-neutral roles we will reuse throughout: the **attester** (the CVM producing evidence), the **verifier** (the entity appraising evidence against reference values and endorsement chains), and the **relying party** (the entity making a trust decision, e.g., releasing a key) [4]. Evidence must be *fresh* (bound to a verifier-supplied nonce), *authentic* (signed by a hardware-rooted key), and *appraisable* (measurements comparable against known-good reference values, increasingly expressed in CoRIM format) [4].

## 3 Methodology

This thesis is an architectural synthesis. Primary sources are the vendor specifications — the Intel TDX Module Base Architecture Specification [1] and AMD's SEV-SNP firmware ABI as documented in the recent primer literature [2] — cross-checked against three independent evidence classes: (a) formal symbolic analyses of the SEV-SNP software interface [3]; (b) the IETF standardization of attestation evidence formats [4]; and (c) peer-reviewed empirical performance studies on production silicon, principally the systematic SIGMETRICS 2025 analysis of both architectures [6], Intel's confidential-AI system-level study with NVIDIA H100 GPUs [5], and Google Cloud's published TDX benchmarking [7]. Deployment claims are grounded in Microsoft's public attestation documentation [8]. Where vendor marketing and measured data conflict, measured data prevails.

## 4 Deep Dive

### 4.1 Intel TDX: Trust Domains, the TDX Module, and the SEAM Root of Trust

A **Trust Domain (TD)** is a hardware-isolated virtual machine whose private memory is encrypted with a TD-specific ephemeral key and whose execution is managed by the **TDX Module** — Intel-signed firmware that runs in a new CPU operating mode, **SEAM** (Secure Arbitration Mode), entered via the `SEAMCALL`/`SEAMRET` instructions. The ordinary hypervisor (running in VMX root mode) retains *resource management* — it schedules vCPUs and assigns physical pages — but is cryptographically excluded from *observing or modifying* TD private state. Every TD entry and exit is mediated by the TDX Module, and TD-private pages are integrity-checked on access [1].

The trust anchor is the CPU package itself: the TDX Module's measurements are recorded by microcode at load time, and TD launch measurements (initial memory image and configuration) are accumulated into the **MRTD** (Measured Root of Trust for the TD) register. At runtime, guest software extends four **RTMR** (Runtime Measurement Register) registers — extend-only, SHA-384-chained — conventionally assigned to firmware (TDVF/OVMF), bootloader, OS kernel, and application layers respectively [1].

> **Theorem 1 (TD memory confidentiality).** *Assume the MKTME engine correctly implements AES-XTS-128 with per-TD ephemeral keys that never leave the CPU package, and the TDX Module correctly enforces that only the owning TD's key decrypts its private pages. Then no software executing outside SEAM mode — including the hypervisor, host OS, SMM, or DMA-capable devices — can recover TD-private plaintext from DRAM or interconnect traffic.*

The theorem's assumptions are exactly what attestation exists to check: the verifier confirms it is speaking to a genuine TDX Module at an acceptable security version before trusting the conclusion.

The guest↔module interface is `TDCALL`, a leaf-function ABI through which the TD requests services — including the attestation entry point `TDG.MR.REPORT`:

```python
# Conceptual verifier-side logic for a TDX attestation flow
def verify_td(td_quote: bytes, expected_mrtd: bytes, nonce: bytes) -> bool:
    quote = parse_td_quote(td_quote)          # ECDSA-P256 signed by QE attestation key
    if not verify_cert_chain(quote.cert_chain, intel_root_ca):
        return False                          # [1] TDX Module spec, Ch. 12
    if not ecdsa_verify(quote.signature, quote.body, quote.att_key):
        return False
    if quote.body.mrtd != expected_mrtd:      # build-time measurement
        return False
    if quote.body.report_data != sha384(nonce || ephemeral_pubkey):
        return False                          # freshness + key binding
    return check_tcb_svn(quote.body.tee_tcb_svn)  # firmware patch level
```

### 4.2 AMD SEV-SNP: The Secure Processor, the RMP, and VMPL

AMD's root of trust is the **AMD Secure Processor (AMD-SP)**, an on-die ARM Cortex-A5 microcontroller running signed firmware. The AMD-SP owns the memory-encryption keys, enforces the guest *policy* (a 64-bit field set at launch controlling migration, debugging, and SMT restrictions), computes the launch measurement, and signs attestation reports [2].

Three mechanisms distinguish SNP from its predecessors:

- **Reverse Map Table (RMP).** The hypervisor still manages nested page tables, but every guest-physical→system-physical mapping is cross-checked against the RMP in hardware. A page assigned to a guest cannot be aliased to another guest, remapped while validated, or rolled back to a stale ciphertext — defeating the remap/replay attacks that plagued first-generation SEV [2][3].
- **VMPL (VM Privilege Levels).** Four privilege levels *inside* the guest (VMPL0 most privileged) enable in-guest security layering. The **SVSM** (Secure VM Service Module) specification places a minimal firmware module at VMPL0 to host a virtual TPM and secure services, letting the guest OS run at VMPL1+ while the vTPM's state enjoys the same hardware protection as guest memory [2].
- **VMPCK-secured firmware channel.** Guest↔AMD-SP messages (e.g., attestation requests) travel over the GHCB page encrypted with per-VM Platform Communication Keys, so the hypervisor observes only ciphertext [2].

The formal analysis of Horvat et al. [3] built the first comprehensive symbolic model of this interface — covering remote attestation, key derivation, page swap, and live migration — and proved critical secrecy, authentication, and freshness properties *while also finding a genuine weakness*: the platform-agnostic format of SNP↔firmware messages permits attacks on attestation-report integrity, including undetectable migration of a guest to a vulnerable platform. Their proposed fix binds messages to platform identity, a reminder that the *protocol framing* around hardware primitives deserves the same scrutiny as the silicon [3].

```haskell
-- Measurement as an extend-only fold (applies to RTMRs, PCRs, and launch digests)
extend :: Digest -> Measurement -> Digest
extend d m = sha384 (d <> m)

launchDigest :: [PageImage] -> Digest
launchDigest = foldl extend zeroDigest   -- order-sensitive: page insertion order matters
```

### 4.3 Attestation Flows: TD Quotes versus SNP Reports

Both architectures implement the RATS evidence flow, but with mirrored trust topologies.

**Intel TDX (two-phase, quote-based).** *Phase 1:* TD software invokes `TDG.MR.REPORT`, passing 64 bytes of `REPORTDATA` (typically `SHA-384(nonce ‖ ephemeral_pubkey)`); the TDX Module returns a **TDREPORT** — MAC integrity-protected with a CPU-private key, containing MRTD, the four RTMRs, the module's own measurements, and the report data [1]. *Phase 2:* a special **TD Quoting Enclave** — an SGX enclave written for TDX — verifies the TDREPORT's MAC via the new `EVERIFYREPORT2` instruction leaf, then signs a **TD Quote** with an attestation key certified through Intel's Provisioning Certification Service. The Quoting Enclave may run anywhere SGX is supported; notably, SGX enclaves *inside* a TD are not supported [1]. The verifier checks the certificate chain to Intel's root, the signature, the measurements against reference values, the TCB security-version numbers, and the nonce binding.

**AMD SEV-SNP (report-based).** The guest issues `SNP_REPORT_REQ` (via GHCB/`MSG_REPORT_REQ`) carrying 64 bytes of caller-supplied `REPORT_DATA`; the AMD-SP returns an **attestation report** signed by the **VCEK** (Versioned Chip Endorsement Key), a chip-unique ECDSA key derived from fused secrets and bound to the firmware TCB version. Verification is refreshingly self-service: fetch the VCEK certificate chain from AMD's Key Distribution Service, validate it to AMD's root CA, verify the report signature, compare the SHA-384 launch digest and guest policy against expectations, and check the nonce-derived report data for freshness [2]. SNP's decisive usability win over legacy SEV is that attestation can be requested *from inside the running guest* rather than orchestrated by the hypervisor [2].

| Attestation property | Intel TDX | AMD SEV-SNP |
|---|---|---|
| Evidence artifact | TD Quote (SGX-QE signed) | Attestation report (VCEK signed) |
| Root of trust | CPU + TDX Module, Intel PCS chain | AMD-SP firmware, AMD KDS chain |
| Build measurement | MRTD | Launch digest (SHA-384) |
| Runtime measurement | RTMR0–RTMR3 (extend-only) | vTPM PCRs via SVSM (no native RTMR) |
| Freshness | REPORTDATA binds nonce + key | REPORT_DATA binds nonce + key |
| Request origin | In-guest `TDCALL` | In-guest `SNP_REPORT_REQ` |

A subtle but consequential asymmetry: TDX provides *native* runtime measurement registers, while SEV-SNP's measured story ends at launch — runtime integrity must be reconstructed through a vTPM hosted in the SVSM, whose PCR values a verifier must then correlate with the SNP report. Recent work on data-center execution assurance shows this binding is achievable but non-trivial: PCR0 alone is insufficiently unique, and dedicated in-TD logic must extract the TPM event log to produce values comparable with the hardware report [4][9].

### 4.4 Measured Boot: From Silicon to the Application

Measured boot answers a narrower question than attestation: *what software stack produced this evidence?* The chain is only as strong as its first link — the hardware root that measures the firmware that measures the bootloader that measures the kernel. In TDX deployments the conventional assignment extends RTMR0 with the TDVF firmware measurement, RTMR1 with the OS loader and kernel, and RTMR2/3 with application-defined measurements, all under the Linux kernel's TSM (Trusted Security Module) abstraction that presents TDX RTMRs behind a uniform measurement-register API [1]. In SNP deployments the analogous chain terminates in the vTPM's PCRs, measured by the SVSM at VMPL0 and quoted in TPM 2.0 format [2].

The relying party's decision procedure is then uniform across vendors: recompute or look up the expected digest chain for a known-good image (increasingly published as signed CoRIM reference values [4]), compare, and — only on match — release secrets. This is the **Secure Key Release** pattern productionized by Azure: the key vault's release policy names exact PCR/RTMR values, so disk-encryption keys and TLS identities are cryptographically confined to unmodified images [8].

```
UEFI/TDVF ──measure──▶ RTMR0 / PCR0 ──measure──▶ bootloader ──measure──▶ kernel
   │                                                              │
   └────────────── hardware root of trust (CPU / AMD-SP) ─────────┘
```

### 4.5 Performance Overheads: Where the Cycles Go

Security is never free; the question is where the tax is levied and whether it is proportional to the workload. The most systematic study to date — Misono et al.'s SIGMETRICS 2025 analysis on 4th-gen EPYC and 5th-gen Xeon silicon — identifies three dominant cost centers [6]:

1. **Memory-allocation tax.** CVM-specific page acceptance (`EACCEPT`/SNP page validation) inflates initial memory allocation by up to **92%** in microbenchmarks. This is a one-time boot/mmap cost, but it punishes short-lived, allocation-heavy workloads [6].
2. **Costly context switches.** Frequent vCPU-sleep events (HLT exits) trap to the TDX Module / AMD-SP boundary; the NAS Parallel Benchmarks show up to **431% overhead** in the worst case. Guest-side polling (halt-polling/idle-polling) largely mitigates this, collapsing UDP-throughput overheads from 81% (TDX) and 75% (SNP) to the 28–32% range or better [6].
3. **I/O bounce buffers.** Because DMA devices cannot read TD/SNP-private memory, I/O traverses *shared* (unencrypted) bounce buffers with explicit copies. Under saturated CPUs this costs up to **60%** of heavy network throughput (iperf TCP); with CPU headroom the overhead is absorbed [6]. Ping latency grows modestly: +16 µs (TDX) and +17 µs (SNP) versus a normal VM [6].

For compute-bound AI workloads the picture is kinder. Intel's system-level study of TDX with NVIDIA H100 GPUs finds modest, predictable overhead — GPU execution dominates runtime, so the CPU-side encryption tax fades into the noise [5]. Google Cloud's published experiments concur: ML training on TDX-enabled C3 instances reached a 4.14× speedup over baseline N2 VMs versus 4.54× without TDX — a single-digit relative penalty — with larger batch sizes amortizing the memory-encryption cost of I/O [7].

```rust
// Verifier-side freshness check, shared logic for both architectures
fn check_freshness(report_data: &[u8; 64], nonce: &[u8], pubkey: &[u8]) -> bool {
    let mut h = Sha384::new();
    h.update(nonce);          // verifier-supplied, unpredictable
    h.update(pubkey);         // binds evidence to the session key
    &h.finalize()[..] == report_data
}
```

## 5 Empirical Evaluation

We consolidate the published measurements into a comparative ledger (all figures relative to a non-confidential VM on identical hardware):

| Workload | Intel TDX | AMD SEV-SNP | Dominant cost |
|---|---|---|---|
| Memory allocation (microbench) | up to +92% | up to +92% | Page acceptance/validation [6] |
| NPB compute (worst case) | up to +431% | up to +431% | HLT/vCPU-sleep exits [6] |
| iperf TCP (saturated CPU) | up to −60% | up to −60% | Bounce-buffer copies [6] |
| UDP throughput (with polling) | −28 to −32% | +2 to +11%¹ | Exit mitigation [6] |
| Ping latency | +16 µs | +17 µs | Exit path length [6] |
| LLM inference (GPU-bound) | ≈ −5% tok/s | n/a | CPU-side encryption [5][7] |
| ML training (AMX, large batch) | ≈ −9% rel. speedup | n/a | I/O encryption [7] |

¹ Negative overhead (speedup) reflects polling-behavior differences versus the baseline configuration.

Two further "proofs" deserve mention. First, the *formal* evidence: Horvat et al.'s symbolic verification of the SNP interface establishes secrecy, authentication, attestation, and freshness properties for the protocol as specified — while precisely characterizing the residual platform-identity weakness [3]. Second, the *negative* result that sharpens the threat model: neither architecture claims side-channel resistance, and the empirical study confirms that timing, cache, and speculative-execution channels remain the verifier's blind spot [6].

A TLA+-style invariant captures the attestation contract both designs aim to uphold:

```tla
---- MODULE Attestation ----
VARIABLES evidence, nonce, trusted
Verify == /\ evidence.signatureValid
          /\ evidence.measurements \in ReferenceValues
          /\ evidence.reportData = Hash(nonce \o sessionKey)
          /\ evidence.tcbVersion >= MinAllowedTCB
ReleaseKey == Verify => trusted' = TRUE
====
```

## 6 Limitations

**Side channels are out of scope.** Cache-timing, branch-predictor, and transient-execution attacks can extract secrets across the VM boundary on both architectures; constant-time kernels and core scheduling are the tenant's burden, not the hardware's promise [6].

**The firmware supply chain is trusted.** TDX trusts Intel's signed module and PCS availability; SNP trusts AMD-SP firmware and the KDS. A compromised vendor signing key or a coerced firmware update is outside both threat models — the attestation chain terminates in *vendor trust*, not mathematics [1][2].

**Availability is unprotected.** The hypervisor cannot read TD/SNP-private memory, but it can refuse to schedule the VM, throttle it, or destroy it. Confidentiality and integrity are guaranteed; liveness is not [6].

**SEV-SNP lacks native runtime measurement.** The launch digest covers only initial state; runtime integrity requires the SVSM/vTPM construction, which is younger, more complex, and harder for verifiers to appraise than TDX's RTMRs [2][9].

**Migration and I/O remain sharp edges.** Live migration of CVMs requires re-attestation protocols with TOCTOU windows; device I/O (TDX Connect, SPDM-based device attestation) is still maturing, and today's bounce-buffer path is both the performance bottleneck and a software-complexity risk [1][6].

**Compliance is evidence, not security.** A signed quote satisfies an auditor's demand for *proof of configuration*, but misconfigured reference values, stale TCB minima, or nonce reuse silently void the guarantee. The cryptography is only as rigorous as the verifier's policy [4][8].

## 7 Conclusion

Intel TDX and AMD SEV-SNP represent a genuine phase change in cloud security: the tenant's trust anchor moves from the provider's *promises* to the silicon's *evidence*. TDX buys this with a CPU-mode-based module, native runtime measurement registers, and a two-phase quote flow that reuses battle-tested SGX infrastructure; SEV-SNP buys it with a firmware root of trust, a hardware-enforced page-ownership table, and a refreshingly simple VCEK-signed report verifiable against a public key service. Both confine the once-omnipotent hypervisor to resource management, both bind evidence freshness to verifier nonces, and both impose their heaviest taxes on memory allocation, vCPU exits, and DMA — taxes that shrink to single digits for the GPU-bound AI workloads driving current adoption [5][6][7].

The honest summary is narrower than the marketing: CVMs deliver *confidentiality and integrity of data in use against privileged software adversaries, with remotely verifiable evidence*. They do not deliver side-channel resistance, availability, or freedom from vendor trust. For regulated industries — where GDPR, HIPAA, and PCI DSS increasingly demand technical enforcement of data-in-use protection, and where auditors accept cryptographic attestation as control evidence — that narrower guarantee is precisely the product being bought, as Azure's confidential-VM portfolio, guest-attestation services, and Secure Key Release patterns demonstrate [8]. The hypervisor is no longer trusted. It is *verified* — and that is a far stronger claim.
