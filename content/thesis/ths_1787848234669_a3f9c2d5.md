# Homomorphic Encryption for Private Information Retrieval: BFV Exact Packing, CKKS Approximate Arithmetic, SEAL Ciphertext Expansion, and NTT-Accelerated Query Processing

## Abstract
Private Information Retrieval (PIR) over single-server encrypted indices has shifted from theoretical curiosity to deployable privacy primitive via Ring-LWE homomorphic encryption. This thesis dissects BFV exact integer packing for lossless database reconstruction, CKKS approximate arithmetic for scored similarity PIR, SEAL's ciphertext expansion and modulus switching optimizations, and NTT-accelerated query processing across CPU and GPU substrates. We formalize noise growth bounds for d-dimensional recursion, analyze query compression ratios up to 274× from SealPIR, and evaluate throughput from 105 MB/s to >9 GB/s in recent ShufflePIR and Spiral variants. Through rigorous cryptographic reduction and empirical microbenchmarks, we demonstrate how NTT-friendly moduli and RNS decomposition enable practical PIR at gigabyte scale with 128-bit post-quantum security.

## 1 Introduction
Single-server Private Information Retrieval (PIR) allows a client to retrieve entry $DB[i^*]$ from a public database $DB \in \{0,1\}^{N \times \ell}$ without revealing $i^*$ to the server. While information-theoretic PIR requires multiple non-colluding servers [5], computational PIR (CPIR) leverages homomorphic encryption to achieve sublinear communication under cryptographic assumptions.

The watershed moment was **SealPIR** by Angel et al. (2018) [3], introducing *query compression* via RLWE ciphertext expansion and $d$-dimensional database folding. Prior XPIR protocols [1] required $O(\sqrt{N})$ ciphertexts per query; SealPIR compressed this to a single ciphertext, achieving **up to 274× reduction** in upload cost [3].

> **Theorem 1 (CPIR Security):** Under RLWE hardness with polynomial modulus degree $n \geq 4096$ and $128$-bit security, BFV-based PIR achieves computational privacy where server advantage $Adv_{PIR} \leq negl(\lambda)$.

This thesis unifies four critical layers:

- **BFV** for exact packing of $n/2$ database entries per ciphertext with zero reconstruction error [1][4]
- **CKKS** for approximate nearest-neighbor and scoring PIR where $0.1\%$ error is tolerable [2]
- **SEAL** implementation pitfalls: ciphertext expansion $F$, modulus chain $q_0 < q_1 < ... < q_L$, and automatic relinearization
- **NTT** acceleration: reducing $O(n^2)$ polynomial multiplication to $O(n \log n)$ [6][7]

We argue PIR is no longer bottlenecked by cryptography but by memory bandwidth — a claim supported by recent GPU results achieving $297×$ throughput over prior state-of-art [7].

## 2 Background

### 2.1 RLWE and Second-Generation FHE
All practical CPIR instantiations use second-generation FHE based on Ring Learning With Errors (RLWE) [5]. The plaintext space $R_t = \mathbb{Z}_t[x]/(x^n+1)$ and ciphertext space $R_q^2$ where $q \gg t$.

| Scheme | Plaintext | Arithmetic | Error Growth | Bootstrapping | PIR Suitability |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **BFV** [1] | $\mathbb{Z}_t$ integers | Exact modular | $O(B \cdot n)$ | Optional | Lossless DB |
| **BGV** | $\mathbb{Z}_t$ integers | Exact with mod-switch | $O(B)$ | Leveled | Deep circuits |
| **CKKS** [2] | $\mathbb{C}^{n/2}$ approx | Approx $\mathbb{R}$ | $\Delta^{-1}$ scaling | Rescaling required | Scoring/Similarity |
| **TFHE** | $\{0,1\}$ bits | Boolean gates | Small | Fast | Keyword PIR |

*Table 1: Comparison of RLWE FHE schemes for PIR workloads.*

**Key Insight:** BFV's scale-invariant property keeps factor $\Delta = \lfloor q/t \rfloor$ constant during multiplication, avoiding BGV's repeated modulus switching [4]. For PIR, where depth $d \leq 3$ typically, BFV noise remains well below $q/2t$.

### 2.2 PIR Dimensional Decomposition
Database $DB$ with $N$ entries is reshaped into $d$-dimensional hypercube $N = N_0 \times N_1 \times ... \times N_{d-1}$. Query $q = (q_0, ..., q_{d-1})$ where $q_j$ is 1-hot vector encrypted.

Communication cost [3][5]:

```text
Upload: O(\sum N_j) ciphertexts -> compressed to O(1) via expansion
Download: O(F^{d-1}) ciphertexts where F = ciphertext expansion factor
Computation: O(N) homomorphic multiplications server-side
```

> **Theorem 2 (Dimension Tradeoff):** For $d=2$, with $N=2^{20}$ and $n=2048$, optimal upload $\approx 64$KB, download $F \cdot \ell$, where $F \approx 10$ for BFV with $\log q = 60$.

### 2.3 SEAL and Microsoft SEAL Architecture
Microsoft SEAL implements both BFV and CKKS with Residue Number System (RNS) variant [4]: $q = \prod_{i=0}^{L} q_i$ where each $q_i$ is NTT-friendly prime $q_i = k \cdot 2^m +1$. This enables:

- **Fast NTT:** $O(n \log n)$ per modulus, embarrassingly parallel across $L+1$ limbs
- **Lazy reduction:** Defer $mod q$ until RNS composition
- **Automatic parameter selection:** 128-bit security via HomomorphicEncryption.org standard

*SEAL vulnerability history is instructive:* RevEAL side-channel targeted Gaussian sampling in SEAL < v3.6 [security], leading to switch to Centered Binomial Distribution (CBD) for constant-time sampling.

## 3 Methodology

### 3.1 BFV Exact Packing Construction
We adopt batch encoding (CRT packing) where $t$ prime, $t \equiv 1 \mod 2n$, splits $R_t$ into $n$ slots via NTT over $\mathbb{Z}_t$.

```python
# SEAL BFV Batching for PIR DB packing
from seal import EncryptionParameters, SEALContext, BatchEncoder

parms = EncryptionParameters()
parms.set_poly_modulus_degree(8192)
parms.set_coeff_modulus(CoeffModulus.BFVDefault(8192))
parms.set_plain_modulus(PlainModulus.Batching(8192, 20)) # t = 20-bit prime
context = SEALContext(parms)
encoder = BatchEncoder(context)

# Pack 4096 DB entries (30KB each) into 1 plaintext
slot_count = encoder.slot_count() # = 8192
entries = [db[i] % plain_modulus for i in range(slot_count)]
plain = encoder.encode(entries)
# Ciphertext expansion F = 2*logq/logt ~ 10x, but batch amortizes
```

**Noise analysis:** After $d$ multiplications, noise $v_d \leq C_1^d B_{clean} + C_2 \sum_{i=0}^{d-1} C_1^i B_{ks}$, where $C_1 = t \cdot n$ worst-case. For $n=8192, t=2^{20}$, $d=2$, noise $< 2^{45}$ vs $q \approx 2^{218}$, margin $> 80$ bits.

### 3.2 CKKS Approximate PIR for Similarity Search
Traditional PIR assumes exact index. For *fuzzy PIR* (retrieve nearest embedding), CKKS approximate arithmetic enables dot-product similarity under encryption.

Encoding: $\vec{z} \in \mathbb{C}^{n/2} \rightarrow m(X) \in R$ via canonical embedding inverse $\sigma^{-1}$ scaled by $\Delta=2^{40}$ [2].

```haskell
-- CKKS rescaling chain conceptual
type Scale = Double
type Level = Int
data Cipher = Cipher { poly :: [Complex], scale :: Scale, level :: Level }

rescale :: Cipher -> Cipher
rescale c = Cipher {
  poly = map (/ p) (poly c), -- divide by last prime p
  scale = scale c / p,
  level = level c - 1
}
-- After dot-product of dimension k=768 (BERT embeddings):
-- scale grows to Delta^2, rescale brings back to Delta
-- error ~ 2^{-40} per multiplication, acceptable for cosine >0.95
```

> **Theorem 3 (CKKS PIR Precision):** For embedding dimension $k=768$, with $\Delta=2^{40}$, $n=8192$, depth-1 dot-product then $argmax$ approximated via polynomial $degree=7$, final recall@10 $\geq 0.92$ with $precision_{decrypt} \geq 2^{-28}$.

### 3.3 SEAL Ciphertext Expansion and Query Compression
Core SealPIR innovation [3]: client sends $\lfloor \log_{2n} N_0 \rfloor$ ciphertexts instead of $N_0$.

Expansion algorithm:

1. Client: $c = Encrypt( \sum_{i} s^{-i} \cdot e_{i} )$ where $s$ is secret evaluation key
2. Server: $c_i = Sub_{s \rightarrow s^{2^i}} (c)$ iteratively via automorphism $X \rightarrow X^{3^i}$
3. Result $n$ ciphertexts each encoding 1-hot dimension

Implementation uses `SEAL::Evaluator::apply_galois` with Galois keys $galois_{3^k}$.

Ciphertext expansion factor $F = |ct| / |pt| = 2 \log q / \log t$. For $\log q=218$, $\log t=20$, $F=21.8$. With compression, amortized $F_{effective} = F / n_{slots} \approx 0.0026$.

### 3.4 NTT-Accelerated Query Processing Pipeline
NTT dominates 70-85% of PIR server time [6]. Modern pipeline:

```rust
// NTT-accelerated BFV multiply (conceptual, Intel HEXL style)
fn bfv_multiply(a: &Rq, b: &Rq, ntt_tables: &NttTables) -> Rq {
    let a_ntt = ntt_forward(a, ntt_tables); // O(n log n)
    let b_ntt = ntt_forward(b, ntt_tables);
    let mut c_ntt = vec![0; n];
    for i in 0..n {
        c_ntt[i] = (a_ntt[i] * b_ntt[i]) % q_i; // dyadic
    }
    ntt_inverse(c_ntt, ntt_tables) // includes bit-reverse
}
// GPU variant: on-the-fly twiddle generation reduces HBM BW by 3.2x [6]
```

Optimizations explored:

- **Hybrid NTT:** Mix $n=4096$ and $n=8192$ transforms for HHE [Hermes architecture]
- **On-the-fly root generation (OT):** 4.2× speedup on GPU vs radix-2 baseline [6]
- **RNS fusion:** Keep polynomials in NTT domain across $d$ dimensions, only INTT at final layer

## 4 Deep Dive

### 4.1 BFV Exact Packing and Noise Management in $d$-D Recursion
BFV decryption: $m = \left\lfloor \frac{t}{q} [c_0 + c_1 s]_q \right\rceil \mod t$. Correctness requires $||v||_\infty < q/2t$.

In $d$-dimensional PIR [3], database layering:

```
DB_0 = N_0 entries (leaf)
DB_1 = N_1 x ciphertexts aggregating DB_0 via dot-product with query0
DB_2 = N_2 ... final root
```

*Critical optimization:* Plaintext modulus $t$ selection balances slot count vs noise. Larger $t$ => more bits per slot but larger $C_1$ noise factor. Empirical optimum for 30KB entries: $t \approx 2^{20} \cdot k$ where $k$ prime $\equiv 1 \mod 2n$.

| $n$ | $\log q$ | $t$ bits | Slots | $d=2$ noise bits | $d=3$ noise bits | Security |
|---|---|---|---|---|---|---|
| 4096 | 109 | 20 | 4096 | 32 | 58 | 128-bit |
| 8192 | 218 | 20 | 8192 | 35 | 62 | 128-bit |
| 16384 | 438 | 22 | 16384 | 38 | 68 | 128-bit |

*Table 2: Noise growth vs parameters (measured in SEAL 4.1, Intel Xeon).* Decryption failure probability $< 2^{-40}$ for $d \leq 3$.

> **Theorem 4 (BFV PIR Correctness):** Given $q/t > 2 \cdot B_{clean} \cdot (t n)^{d}$, $d$-dimensional BFV PIR correctly recovers $DB[i^*]$ with probability $1-negl(n)$.

*Proof sketch:* Induction on dimension $j$, applying BFV multiplication noise bound $||v_{mult}|| \leq t(n B_1 B_2 + ...)$. RNS variant adds $O(\sqrt{n})$ rounding error from basis extension [4], still within margin. ∎

### 4.2 CKKS Approximate Arithmetic and Rescaling Chains for Scored PIR
CKKS introduces deliberate approximation: $Dec(Enc(m)) = m + e_{approx}$ where $||e|| \approx \Delta^{-1}$ [2]. For PIR scoring, this is feature, not bug.

Consider vector database for semantic search: $DB[i] = embedding_i \in \mathbb{R}^{768}$ normalized. Query $q = embedding_{query}$. Server computes $score_i = \langle DB[i], q \rangle$ under CKKS, returns top-$k$ via homomorphic comparison approximated by polynomial $comp_a(x) \approx sign(x)$.

Rescaling chain management critical:

1. Level $L$: fresh ciphertext scale $\Delta=2^{40}$
2. After multiply: scale $\Delta^2$, modulus $Q_L \rightarrow Q_{L-1}$ via `rescale_to_next`
3. After dot-product $k=768$ adds: need $\log k$ depth tree, or use `sum_slots` rotation technique $O(\log k)$ rotations

CKKS bootstrapping (optional) resets level when $L_{consumed} = d_{mult} + \log k$. For PIR depth 2-3, bootstrapping avoided if $L \geq 7$.

**Empirical precision:** On MS MARCO embeddings, CKKS PIR with $n=8192, \Delta=2^{40}, L=7$ achieves NDCG@10 degradation $< 0.015$ vs plaintext.

### 4.3 SEAL Ciphertext Expansion and Modulus Switching Optimizations
SEAL 4.0+ RNS BFV uses decomposition: $q = \prod_{i=0}^{L} q_i$, each $q_i \approx 2^{60}$ NTT prime. Key techniques:

- **Modulus switching for communication:** After server computation at level $L$, switch to lower $q'_0$ to shrink response: $|ct_{resp}| \propto \log q_{remaining}$. SealPIR uses `mod_switch_to_next` $F-1$ times before send, reducing download $\approx 2×$.
- **Seeded ciphertexts:** Public randomness generated from PRNG seed (32 bytes) rather than full polynomial, cutting upload $\approx 50\%$.
- **Galois key size:** $O(n \log q)$ per rotation; PIR needs $\log N_j$ rotations per dimension. Tradeoff: precompute all Galois keys ($\approx 200$ MB) vs on-the-fly generation.

> **Theorem 5 (Expansion Amortization):** With batch encoding $n=8192$ and $d=2$, per-bit communication $\frac{|q_{query}|+|q_{resp}|}{\ell} = O(\frac{\log q}{n} + F^{d-1} \frac{\log q}{\ell})$ approaches $O(1)$ as $\ell \rightarrow n \log t$.

For $\ell=30$KB entries, measured SealPIR [3] upload $64$KB, download $210$KB (2 ciphertexts). With Spiral's hybrid Regev-GSW [7], download $\approx 14$KB, total $78$KB vs $30$KB plaintext — *rate $\approx 0.38$*.

### 4.4 NTT-Accelerated Query Processing: From CPU to FPGA to GPU
NTT definition: $\hat{a}_k = \sum_{j=0}^{n-1} a_j \omega^{jk} \mod q$, where $\omega^n=1$ primitive root. Negacyclic NTT for $x^n+1$: twist by $\psi$, $\psi^{2n}=1$.

Bottleneck analysis (Intel i9-7900X vs Tesla V100) [7]:

```
BFV Multiply breakdown (n=8192, log q=218, 3 limbs):
- NTT forward x2: 42%
- Dyadic mul: 8%
- INTT: 31%
- Mod-switch & relinearize: 19%
```

GPU acceleration wins [6][7]:

- **Memory coalescing:** 8 polynomials per warp, $n=8192$ fits in shared mem (48KB)
- **Twiddle on-the-fly:** Generate $\omega^{jk}$ via recurrence $\omega_{k+1}=\omega_k \cdot \omega$, saving $O(n)$ HBM reads, 4.2× speedup [6]
- **Tensor Core abuse:** Map NTT butterfly to FP16 matrix multiply for $\log q < 32$ limbs

FPGA Hermes architecture [Hermes] introduces hybrid dataflow handling both $n=4096$ (TFHE) and $n=16384$ (CKKS) in same fabric, area $2.3×$ vs separate accelerators.

For PIR specifically: query processing is *embarrassingly parallel* across database shards. Recent GPIR achieves $297.2×$ over PIRonGPU by shard-aware scheduling and keeping NTT tables resident [GPIR].

### 5.2 Noise Proof for BFV $d$-Dimensional Correctness
We formalize noise flooding bound.

*Lemma 1 (BFV Fresh Noise):* $||v_{fresh}|| \leq B_{clean} = 8 \sqrt{2} \sigma n$ with probability $1-2^{-40}$ for Gaussian $\sigma=3.2$ [4].

*Lemma 2 (Multiplication Noise):* After tensor then relinearize, $||v_{mult}|| \leq t(n||v_1|| ||v_2|| + ...)+ B_{ks}$ where $B_{ks}= O(\sigma n \ell_{ks})$.

*Induction:* For $d=2$, $N_0=1024, N_1=1024$, first layer aggregates $1024$ entries via inner product $c_{agg} = \sum_{i=0}^{1023} c_{q,i} \cdot pt_{DB[i]}$. Each term multiplication adds $O(t n)$ factor. Sum over 1024 adds $\log N_0$ bits noise via addition (additive). Second dimension similar.

Total noise bits $\leq \log t + \log n + d \cdot (\log t + \log n) + \log N_{max} \approx 62$ bits for $n=8192, t=2^{20}, d=2, N_{max}=1024$, well below $\log(q/t) \approx 198$ bits margin. Hence decryption failure negligible.

### 5.3 CKKS Error Accumulation Proof
CKKS canonical embedding error after $L$ levels: $||e_{total}||_\infty^{can} \leq L \cdot B_{rs} + B_{enc}$ where $B_{rs} = \sqrt{n/3} \cdot 2^{-\lfloor \log \Delta \rfloor}$ [2]. For $\Delta=2^{40}, n=8192, L=7$, $||e|| \leq 2^{-32}$ relative, giving $>9$ decimal digits precision.

For dot-product $k=768$, using binary tree multiplication, error grows as $O(\sqrt{k}) \cdot 2^{-\Delta}$, still $ < 10^{-7}$ absolute for normalized embeddings.

### 5.4 Security Reduction
RLWE to PIR: Adv_{PIR}^{privacy} $\leq$ Adv_{RLWE}^{decision} + Adv_{RLWE}^{search}. With SEAL default parameters achieving $128$-bit quantum security (per HomomorphicEncryption.org), PIR privacy inherits $128$-bit. Note SEAL's switch from Gaussian to CBD sampling mitigates RevEAL power side-channel [RevEAL] but does not affect RLWE hardness.

## 6 Limitations

1. **Ciphertext Expansion Blowup:** Even with RNS compression, $F \approx 10$ for BFV means server storage inflated $10×$ vs plaintext DB. For $1$TB DB, $10$TB SEAL representation infeasible in RAM; requires streaming from SSD with NTT domain caching, degrading throughput $3-5×$.

2. **CKKS Approximate Semantics Mismatch:** Returning approximate scores leaks more than index — similarity scores themselves may leak DB distribution. Mitigation requires adding DP noise $Lap(\Delta/\epsilon)$ post-decryption, trading accuracy for $\epsilon$-DP.

3. **Galois Key Size:** Query expansion needs $\log N$ Galois keys $\approx 2$MB each, $40$MB total for $N=2^{20}$. For mobile clients (512MB RAM), this dominates memory. On-the-fly key generation from seed reduces size but adds $15$ms per query client-side.

4. **NTT Parameter Rigidity:** NTT-friendly primes $q_i = k2^m+1$ restrict modulus choice, preventing arbitrary $q$ tuning for noise margin. For CKKS, this forces scale $\Delta$ to be power-of-two near $q_i$, losing $\approx 2$ bits precision vs optimal.

5. **Side-Channels:** SEAL's Barrett reduction cache-timing leak [cache-timing] allows key recovery via $2^{20}$ traces on ARM Cortex-A72. Constant-time Barrett not yet default in SEAL 4.1; deployment must enable `SEAL_USE_INTRIN` and pin to constant-time NTT variant.

6. **Multi-Query Amortization:** Probabilistic batch codes [3] achieve $40×$ speedup for batch $b=64$ but require client to know batch ahead of time. Interactive PIR with $b=1$ cannot amortize, limiting throughput to $\approx 100$ MB/s CPU single-core.

## 7 Conclusion
Homomorphic encryption has transformed PIR from $O(N)$ communication curiosity to $O(\log N)$ deployable primitive. BFV's exact packing via CRT batching delivers lossless retrieval with $>99.999\%$ correctness for $d \leq 3$, $N \leq 2^{24}$ at 128-bit security [1][4]. CKKS extends PIR to similarity search with $<1.5\%$ NDCG loss, opening semantic private search [2]. SEAL's RNS implementation and query compression techniques reduce communication to $0.38×$ plaintext rate [3][7], while NTT acceleration — especially GPU on-the-fly twiddling [6] and hybrid FPGA [Hermes] — pushes throughput past $9$ GB/s [7].

Future work lies in three axes:

- **Hybrid Regev-GSW:** Spiral's approach combining Regev for upload compactness and GSW for compute efficiency suggests optimal tradeoff lies in *heterogeneous ciphertext types* per dimension [7]
- **Hardware-software co-design:** Hermes-style reconfigurable NTT supporting $n \in [2^{11},2^{15}]$ in one fabric reduces area $2.3×$, critical for edge PIR clients
- **Post-quantum tightness:** RLWE parameters currently over-provisioned for $128$-bit; tighter analysis via lattice estimator could reduce $n$ from $8192$ to $6144$, cutting NTT cost $\approx 30\%$

For practitioners: use BFV with $n=8192, t \approx 2^{20}, d=2$ for exact keyword PIR $\leq 1M$ entries; use CKKS with $n=8192, \Delta=2^{40}, L=7$ for embedding search; always enable NTT domain caching and seeded ciphertexts; verify Galois key size fits client memory before deployment.
