# Capability-Based Hardware Security with CHERI on RISC-V and Arm Morello: Compartmentalization, Pointer Provenance, and Formal Monotonicity Proofs for Memory Safety at Scale

## Abstract

Capability Hardware Enhanced RISC Instructions (CHERI) augments conventional instruction-set architectures with hardware-enforced, unforgeable capabilities that replace raw pointers, deterministically mitigating spatial and referential memory-safety violations while preserving source compatibility with legacy C and C++ codebases. This thesis synthesizes the architectural, microarchitectural, formal, and software dimensions of CHERI as instantiated on CHERI-RISC-V and the Arm Morello prototype, itself derived from the Neoverse N1. We formalize the reachable capability monotonicity property at the heart of CHERI's security argument and survey its mechanized proofs in Isabelle/HOL over a translation of the official 62,000-line Morello specification. We analyze CHERI Concentrate bounds compression, pointer provenance in hybrid versus pure-capability C, and the sealed-capability mechanism underpinning scalable compartmentalization. Drawing on published SPECint evaluations and model-based testing campaigns, we quantify performance costs and specification coverage, and close by characterizing CHERI's residual gaps — temporal safety, microarchitectural side channels, and the formalization gap between ISA models and silicon — together with the standardization trajectory toward mass-market adoption.

## 1 Introduction

Memory-safety violations — buffer overflows, use-after-free, wild pointer dereference — have
remained the single largest class of exploitable software vulnerabilities for more than three
decades, surviving successive waves of mitigations from stack canaries to address-space layout
randomization to control-flow integrity [1][5]. The persistence of the problem is structural:
conventional architectures treat pointers as forgeable integers, so *every* memory access in C
and C++ rests on unenforced programmer discipline. Capability Hardware Enhanced RISC Instructions
(CHERI) attacks this root cause directly by extending commodity instruction-set architectures
with **hardware-supported capabilities** — unforgeable, bounded, permission-carrying tokens that
replace integer pointers — and by enforcing, in silicon, the invariant that software can never
amplify the authority it was granted [3][4].

CHERI's intellectual lineage runs from the tagged capability machines of the 1970s and 1980s —
Dennis and Van Horn's supervisor, the CAL-TSS, Intel's ill-fated iAPX 432, the M-Machine — but
its decisive innovation is the *hybrid capability model*: rather than demanding a clean-slate
software stack, CHERI composes capabilities with existing ISAs (MIPS, RISC-V, Armv8-A) and
existing C/C++ code, so that historically memory-unsafe programs can be recompiled to gain
deterministic spatial safety and scalable compartmentalization with only minor source changes
[1][2]. The Arm **Morello** program, backed by the £187M UKRI Digital Security by Design
initiative, realized this vision at industrial scale: a CHERI-enabled prototype processor, SoC,
and board extending the high-performance Neoverse N1, with an ISA whose security properties are
formally verified [1][6].

This thesis makes four contributions. *First*, we give a precise account of the CHERI
protection model — capabilities, tags, permissions, bounds, and sealing — and its two
instantiations of interest, CHERI-RISC-V and Arm Morello. *Second*, we formalize the
**reachable capability monotonicity** property that constitutes CHERI's fundamental security
claim, and survey its mechanized proof in Isabelle/HOL against the official Morello
specification [1]. *Third*, we analyze pointer provenance and the hybrid/pure-capability
spectrum in CHERI C/C++, and the sealed-capability mechanism that enables fine-grained,
in-address-space compartmentalization. *Fourth*, we evaluate the empirical evidence: formal
proof scale, model-based test generation, and published SPECint performance data from Morello
[7], and we delineate the residual limitations — temporal safety, side-channel interaction, and
the ISA-to-silicon verification gap — that bound what CHERI can promise today.

## 2 Background

### 2.1 The capability idea, old and new

A *capability* is an unforgeable token of authority: possession of the token both designates an
object and authorizes operations upon it. Early capability machines enforced this in hardware
through tagged memory, but paid for security with radical software-stack rewrites and poor
performance, and the idea retreated to operating-system kernels (Hydra, KeyKOS, seL4) and
language runtimes. CHERI's wager is that the idea can be *retrofitted*: keep the conventional
flat address space and the conventional toolchain, but make every pointer a capability whose
integrity is guarded by a single **validity tag bit**, stored out-of-band so that ordinary
data manipulation cannot forge it [3].

> Theorem: *Reachable capability monotonicity.* During execution of arbitrary (potentially
> adversarial) code within a compartment, the set of capabilities reachable by that code —
> directly via registers or indirectly via tagged memory it can load — can never grow in
> authority: no instruction sequence can widen bounds, add permissions, or forge a tag [1][5].

In CHERI, each capability carries:

- **Tag** (1 bit, out-of-band): validity; cleared by any non-monotonic manipulation.
- **Sealed** (1 bit): whether the capability is sealed with an *object type*.
- **Permissions** (bitmask): load, store, execute, capability-load/store, seal/unseal, and
  architecture-specific rights.
- **Object type** (*otype*): a small integer enabling temporary sealing for opaque references.
- **Bounds** (*base*, *top*): the valid address range, compressed via CHERI Concentrate [6].
- **Address** (*cursor*): the current pointer value, which may transiently stray out of bounds
  provided it is brought back before dereference.

### 2.2 Hybrid versus pure-capability execution

CHERI supports two software models. In the **hybrid** model, only explicitly annotated pointers
become capabilities; the rest of the program uses integer addresses constrained by the ambient
*default data capability* (DDC) and *program counter capability* (PCC). In the
**pure-capability** model, *every* pointer — including `pcc` and the stack pointer — is a
capability, and spatial safety is complete for the compiled unit [3]. The two models form a
migration path: harden the most exposed libraries first, then expand.

| Feature | CHERI-MIPS (prototype) | CHERI-RISC-V (reference) | Arm Morello (industrial) |
|---|---|---|---|
| Base ISA | MIPS64 | RV64GC | Armv8-A (Neoverse N1) |
| Capability width | 256 b (uncompressed) / 128 b | 128 b + tag | 129 b (128 + tag) |
| Bounds encoding | CHERI Concentrate | CHERI Concentrate | CHERI Concentrate |
| Formal model | L3 → Isabelle/HOL | Sail → Isabelle/Coq | Sail → Isabelle/HOL |
| Key proof | Compartment monotonicity [5] | In progress (standardization) | Reachable monotonicity [1] |
| Software | CheriBSD (hybrid + pure) | CheriBSD / Linux experiments | CheriBSD, Linux, Android studies |

### 2.3 Compartments, not just processes

Conventional isolation is *coarse*: processes separated by the MMU, with IPC across protection
domains costing thousands of cycles. CHERI enables **compartmentalization** at sub-process
granularity — libraries, codecs, parsers — within a single address space, using sealed
capabilities as *opaque, unforgeable references* and capability-aware calling conventions. A
compromised JPEG parser holding only a sealed entry capability to its caller cannot even
*name* memory outside its grant, let alone corrupt it [5].

## 3 Methodology

Our analysis proceeds along four methodological axes, mirroring the CHERI project's own
rigorous-engineering discipline [5]:

1. **Specification as executable mathematics.** We take the Sail specifications of
   CHERI-RISC-V and Morello as ground truth. Sail definitions generate C/OCaml emulators
   (fast enough to boot CheriBSD), SMT backends for test generation, and theorem-prover
   embeddings in Isabelle/HOL, HOL4, and Coq — keeping documentation, model, and proof
   synchronized by construction [3][4].
2. **The narrow abstraction.** Following Bauereiss et al. [1], we factor the Morello proof
   through a minimal interface: an arbitrary CHERI ISA is characterized by a monadic
   intra-instruction semantics exposing only memory actions and capability manipulations. The
   62,000-line official specification translates to 210,000 lines of Isabelle, but the
   security proof reasons *only* through the abstraction, making it robust to specification
   churn.
3. **Model-based test generation.** We survey the instruction-sequence test generator that
   achieves specification coverage on Morello QEMU and early silicon, cross-validated against
   Arm's internal test suite [1].
4. **Quantitative evaluation.** We draw on published Morello SPECint results across code
   models (hybrid, pure-capability) [7] and on compartmentalization case studies (SOAAP,
   library sandboxing) to assess cost and security benefit.

*Threat model.* We assume an adversary who controls arbitrary code inside a compartment and
seeks to escalate authority: forging capabilities, widening bounds, or escaping the
compartment. We assume the hardware correctly implements the Sail specification — the
ISA-to-RTL gap is explicitly out of scope (see §6) — and that tags are physically protected.

## 4 Deep Dive

### 4.1 Capability representation and CHERI Concentrate

A naive fat pointer doubles pointer size *and* doubles memory traffic for pointer-heavy
workloads. **CHERI Concentrate** [6] compresses 256-bit capabilities into 128 bits (plus tag)
by encoding bounds relative to the address with a floating-point-like exponent, trading
representable precision at large region sizes for compactness:

```c
/* CHERI Concentrate: bounds share upper address bits; exponent E
   selects alignment 2^E. Not all (base, top) pairs are encodable. */
struct cheri_concentrate {
    uint64_t cursor;      /* full 64-bit address */
    uint64_t base_top;    /* compressed bounds, exponent-encoded */
    uint32_t perms;       /* hardware-enforced permission mask   */
    uint32_t otype : 18;  /* object type when sealed             */
    uint32_t sealed : 1;
};
```

The compression is *security-preserving* because bounds-setting instructions
(`CSetBounds`, RISC-V `YBNDSW`) **round inward** on inexact encoding and clear the tag when
rounding would violate monotonicity [4]. The ISA thus maintains the invariant that a
capability's authority never exceeds its parent's, even under lossy compression — a subtle
property verified down to the bit level for CHERI Concentrate [3].

In *RISC-V CHERI*, capabilities live in an extended register file; `pcc` governs instruction
fetch and the default data capability (`ddc`) bounds ambient data access. Derivation
instructions (`YSCBNDS`, `YANDPRM` for permission masking) are the *only* legal constructors,
and every one is monotonic by construction [4].

### 4.2 Pointer provenance and the hybrid/pure-capability spectrum

CHERI gives hardware teeth to the C notion of **pointer provenance**: every pointer value is
associated, at creation, with the capability (allocation) it derives from. Temporal
out-of-bounds arithmetic is tolerated — the cursor may wander — but dereference is checked
against bounds *at use time*, and provenance cannot be laundered through integers:

```cheri-c
/* Pure-capability CHERI C: provenance flows with the pointer. */
char * __capability buf = malloc(64);   /* capability: base..base+64 */
char * __capability p = buf + 128;      /* legal arithmetic, tagged   */
*p = 'x';  /* hardware trap: cursor outside [base, top) */
/* Casting through uintptr_t strips the tag: provenance is destroyed,
   never forged — (char * __capability)(uintptr_t)buf is untagged. */
```

This yields a crisp provenance theorem: *a dereference succeeds only if a chain of
monotonic derivations links the accessed capability to a root of authority* (boot capabilities
covering all memory, progressively narrowed by the kernel, runtime, and allocator) [1][5].
Hybrid C weakens this deliberately — integer pointers are checked only against DDC — which is
why the security argument for hybrid binaries is *per-pointer* rather than whole-program.

```rust
// Rust analogy: CHERI enforces at the ISA what borrowck enforces statically.
fn parse(buf: &[u8]) -> &[u8] {
    &buf[..64]  // borrowck narrows the borrow; CHERI narrows the capability
}
```

Where Rust's borrow checker proves narrowing at compile time for safe code, CHERI *re-checks*
narrowing at every derivation and dereference at run time — extending the guarantee to unsafe
Rust, C, and even hand-written assembly within a compartment.

### 4.3 Sealed capabilities and scalable compartmentalization

Unsealed capabilities implement *spatial* safety; **sealed** capabilities implement
*isolation*. Sealing binds a capability to an *otype* such that it can be passed around but
neither dereferenced nor modified until unsealed by code holding the corresponding unseal
authority. Sealed *entry* capabilities additionally permit controlled domain transition —
the hardware unseals, switches `pcc`/`csp`, and enters the callee atomically:

```asm
# RISC-V CHERI compartment call sequence (simplified)
 cseal   ct0, ct1, ct2      # seal data cap ct1 with otype in ct2 -> ct0
 ccall   centry, cdata      # invoke sealed entry: atomic domain transition
 # hardware: unseal centry, install callee pcc/idc, jump; callee cannot
 # forge cdata's otype, cannot widen bounds, cannot retain ambient rights
```

Because sealing is a *controlled, auditable* exception to monotonicity — rights are not
broadened, merely rendered opaque — the compartmentalization proof characterizes exactly
which rights a compartment's arbitrary code can reach: those in its register file plus those
loadable through its capabilities, and nothing else [5]. This is the formal basis for
claims like "the sandboxed libpng cannot touch the TLS private key even after arbitrary
code execution inside the sandbox."

Compartmentalization policies compose hierarchically: a browser can nest a renderer
compartment inside a tab compartment inside the browser compartment, each transition
mediated by sealed entry points, with *linear* rather than process-like overhead —
historically measured in tens of cycles per transition versus thousands for IPC [5].

### 4.4 Reachable capability monotonicity and the narrow abstraction

The centerpiece of CHERI's formal story is the mechanized proof that the **Morello
architecture satisfies reachable capability monotonicity** [1]. The proof's architecture is
as interesting as its result. Directly reasoning about a 62,000-line production ISA
specification is infeasible; instead, Bauereiss et al. define a *narrow abstraction*: any
CHERI ISA is modeled as a state monad over intra-instruction steps, exposing an enumerated
set of *abstract actions* (memory read/write, capability derive, tag clear, seal/unseal,
exception). The security property is stated over traces of abstract actions; each concrete
instruction is then shown, once, to refine its abstract actions.

> Theorem: *Reachable capability monotonicity (Morello).* For any execution trace of the
> Morello ISA model, the authority reachable from any compartment's initial capability set
> is non-increasing: every capability derivable at step *n+1* is dominated (bounds ⊆,
> permissions ⊆, tag ⇒) by some capability reachable at step *n*, except via explicitly
> characterized sealing transitions whose otypes are drawn from the compartment's grant [1].

The proof factors further: per-instruction monotonicity lemmas, a trace-level induction over
the monadic semantics, and a lifting argument from the abstraction to the full translated
specification. Mechanization in Isabelle/HOL (~210,000 generated lines plus hand-written
proof scripts) means the theorem is checked by a small trusted kernel, not by human review
of a paper proof — the appropriate standard of evidence for a *hardware* security claim [1][5].

## 5 Empirical Results and Proofs

**Formal verification scale.** The Morello proof [1] remains the largest mechanized
ISA-security proof attempted: 62,000 lines of official ASL specification, translated to
210,000 lines of Isabelle definitions, with the monotonicity proof factored through the
narrow abstraction so that specification revisions require re-proving only the refinement
step. Complementary proofs cover CHERI Concentrate's bit-level correctness and the
monotonicity of individual CHERI-MIPS instructions [3][5]. The practical payoff was
demonstrated early: the model-based test generator derived from the same Sail model produced
instruction-sequence tests achieving high specification coverage, used in Morello QEMU
development and early silicon bring-up, and cross-validated against Arm's internal suite [1].

**Performance.** The central empirical question is whether hardware capabilities cost too
much for mass-market adoption. Published Morello results (UCAM-CL-TR-986 [7]) evaluate
SPECint across code-generation models on both the baseline Neoverse N1 microarchitecture
and FPGA-modified designs. The headline findings, consistent across the CHERI literature,
are:

- **Hybrid binaries** pay low single-digit percent overhead on SPECint: capabilities are
  used only where annotated, and the capability-aware pipeline (wider register file,
  bounds checks folded into the load/store unit) rarely stalls [7].
- **Pure-capability binaries** pay more — pointer doubling increases cache footprint and
  memory bandwidth — but remain within the range historically accepted for major security
  features, and compartmentalization *saves* the IPC costs it replaces.
- **Compartment transitions** cost tens of cycles (sealed entry/exit), two orders of
  magnitude cheaper than process isolation, making fine-grained decomposition
  performance-viable [5].

**Coverage and testing.** Beyond proofs, the Sail-derived emulators boot CheriBSD in
minutes (~320 kips), enabling whole-stack differential testing: the same test suite runs
against the Sail model, QEMU, and RTL simulation, so divergences surface as engineering
bugs rather than security incidents [3]. Randomized instruction generation plus
theorem-prover-guided SMT test synthesis [3] complements directed tests.

**Security evaluation.** Industrial evaluations on Morello — including red-team exercises
under the DSbD program — have confirmed the expected deterministic mitigation of spatial
violations: classic buffer-overflow exploits fail closed with hardware traps rather than
silent corruption, and compartment-escape attempts are bounded by the reachable-rights
characterization [2][5].

## 6 Limitations

CHERI's guarantees are strong but carefully scoped, and overstating them would repeat the
history of mitigations that promised more than they delivered.

1. **Temporal safety is not included.** CHERI as standardized enforces *spatial* safety and
   referential integrity; use-after-free remains possible unless the allocator revokes or
   quarantines. Research extensions (Cornucopia/CHERIvoke-style revocation sweeps, and the
   recent FRESCO design targeting complete temporal safety [8]) close this at a cost in
   complexity and pause times — an active frontier, not a solved problem.
2. **Side channels and speculation.** CHERI is an *architectural* protection technique; it
   does not by itself close Spectre/Meltdown-class microarchitectural channels. Capability
   checks performed during speculation need explicit treatment, and compartment identifiers
   must be plumbed into the microarchitecture to avoid cross-compartment leakage [3].
3. **The ISA-to-silicon gap.** The mechanized proofs [1][5] are about ISA *models*
   translated from specifications — not about the Verilog, the physical tag storage, or the
   package. A bug in tag propagation through the cache hierarchy would not be caught by the
   Isabelle proof. Closing this requires RTL-level verification, still nascent.
4. **Software-side obligations.** Monotonicity is a property of the *mechanism*; the
   *policy* — which capabilities a compartment is granted at creation — is software's job.
   An over-privileged initial grant voids the guarantee, and auditing compartment
   manifests at scale is an unsolved tooling problem.
5. **Ecosystem inertia.** Pure-capability deployment demands recompilation of the world,
   ABI decisions (e.g., `sizeof(void *)` doubling), and toolchain maturity; the
   standardization of CHERI-RISC-V [4] is the vehicle, but adoption will be measured in
   years.

## 7 Conclusion

CHERI reframes memory safety from a software-discipline problem into a **hardware-enforced
invariant**: pointers are capabilities, capabilities are unforgeable, and authority only ever
narrows. The Morello program demonstrated that this invariant can be realized in a
high-performance, industrially relevant processor and — crucially — *proved*, in Isabelle/HOL
against the official specification, that the architecture delivers the reachable monotonicity
it promises [1]. CHERI-RISC-V carries the model into the open standardization process [4],
while the software stack (CheriBSD, compartmentalized libraries, hybrid migration paths)
shows how legacy C/C++ can be hardened incrementally rather than rewritten.

The remaining work is substantial: temporal safety, speculative side channels, RTL-level
verification, and the long labor of ecosystem migration. But the direction of travel is now
supported by an unusual combination in computer security — a principled mechanism, a
mechanized proof at production scale, and silicon on which to measure the cost. If the
industry's memory-safety crisis is to end, it will likely end the way CHERI proposes: not
with another mitigation layered atop forgeable pointers, but with pointers that cannot be
forged.
