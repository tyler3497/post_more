# Consensus for Geo-Replicated SQL with Spanner TrueTime and CockroachDB: Hybrid Logical Clocks, Clock Skew Bounding, External Consistency, Stale Reads, and Range Replication

## Abstract
Geo-replicated SQL requires strong consistency across continents despite unbounded network delay and clock skew. This thesis dissects two production systems that solve the problem with opposing philosophies of time: Google Spanner's TrueTime, which bounds physical clock uncertainty via GPS and atomic clocks to enforce external consistency through commit-wait, and CockroachDB's Hybrid Logical Clocks (HLC), which fuse physical wall time with Lamport causality to achieve serializable snapshot isolation without specialized hardware. We formalize clock uncertainty epsilon and HLC monotonicity invariants, analyze Spanner's Two-Phase Commit over Paxos groups versus CockroachDB's parallel commit and Raft-based range replication, and prove ordering guarantees for stale follower reads under closed timestamp protocols. We evaluate latency impacts of commit-wait, leaseholder load balancing, and clock drift, deriving bounds for external consistency violations and read freshness SLOs. The synthesis yields a decision framework for choosing bounded physical time versus logical-physical hybrid clocks in modern distributed SQL.

## 1 Introduction
Geo-replicated SQL promises the familiar relational model—*ACID*, *joins*, *serializability*—across three or more continents with **survivability guarantees** that no single region can be a single point of failure. The central difficulty is *ordering*. When a client in `us-east1` commits `T1` and then phones a client in `eu-west4` to start `T2`, every observer must see `T1` before `T2`, even if clocks on the two continents disagree by milliseconds [1][2].

Two architectures dominate modern practice:

- **Spanner / TrueTime**: exploit hardware time—GPS receivers, atomic clocks, and dedicated time masters—to provide a *bounded uncertainty* API `TT.now() -> [earliest, latest]` such that the true absolute time is provably within the interval [3][4]. By waiting out uncertainty, Spanner provides **external consistency**, also called strict serializability or linearizability of transactions.
- **CockroachDB / Hybrid Logical Clocks**: avoid hardware dependence by maintaining an **HLC** `hlc = <physical, logical, node-id>` that is *close to wall time* for readability but *monotonically increasing* to preserve causality, even under NTP drift [5][6]. Combined with MVCC and Raft replication of 64 MiB ranges, CockroachDB provides serializable isolation without `commit-wait`.

> Theorem: Under bounded epsilon, commit-wait ensures external consistency; under HLC monotonicity without bounded epsilon, the system ensures causal plus serializable ordering but requires client-side uncertainty handling for linearizability.

This thesis makes four contributions:

- A unified formalization of **clock skew bounding** and its impact on transaction latency.
- A comparison of **consensus layering**: Spanner's *Paxos groups* versus CockroachDB's *Raft ranges* and leaseholder optimization.
- An analysis of **stale reads**: Spanner's snapshot reads at `TT.now().latest` versus CockroachDB's `AS OF SYSTEM TIME follower_read_timestamp()` and closed timestamp tracking.
- A quantitative model of **range replication latency** under multi-region configurations `SURVIVE ZONE` vs `SURVIVE REGION FAILURE`.

## 2 Background

### 2.1 TrueTime and Bounded Uncertainty
Spanner's TrueTime daemon runs on every node and syncs with time masters—machines with GPS and atomic clocks [4]. The daemon models two sources of uncertainty:

- **Network RTT** between client and master during sync.
- **Clock drift** of the local quartz oscillator, typically bounded to 200ppm but measured continuously [7].

The result is an interval whose width is typically <1ms at the 99th percentile in same-datacenter sync, growing to ~7ms with 30s poll intervals [2][3]. The API is deceptively simple:

1. `TT.now() -> [earliest, latest]`
2. `TT.after(t) -> true iff t < earliest`
3. `TT.before(t) -> true iff t > latest`

*Spanner never trusts a single timestamp*. Every commit timestamp is chosen as `s = TT.now().latest` at the coordinator, then **commit-wait** delays until `TT.now().earliest > s` [2][8]. This ensures real time has passed `s`.

### 2.2 Hybrid Logical Clocks
Introduced by Kulkarni et al. in 2014 [5], HLCs address Lamport's loss of physical proximity. An HLC maintains:

- `pt`: physical time (wall clock ms)
- `l`: logical counter to break ties
- `c`: combined timestamp `c = max(pt, l)`

Properties:

- **Monotonicity**: HLC never decreases, even if wall time jumps backward.
- **Closeness**: `|hlc - pt|` bounded by `epsilon + logical drift`, typically small.
- **Causality**: If `e1 -> e2` (happens-before), then `hlc(e1) < hlc(e2)`.

CockroachDB encodes HLC as 64-bit: upper 48 bits physical ms since epoch, lower 16 bits logical [6]. Overflow requires 65536 events in a single physical ms—practically impossible because a physical clock query costs ~66ns and logical increments are rare.

### 2.3 Consensus: Paxos Groups vs Raft Ranges

| Aspect | Spanner | CockroachDB |
| :--- | :--- | :--- |
| Sharding unit | Directory / Tablet (~10s-100s MB) | Range (~64 MiB, default 512 MiB in newer versions) |
| Replication | Multi-Paxos per group | Raft per range, 3x or 5x |
| Leader | Paxos leader | Raft leader + leaseholder (read optimization) |
| Config | Zonal config via placement | `REGIONAL BY TABLE`, `REGIONAL BY ROW`, `GLOBAL` |
| Time | TrueTime | HLC + closed timestamps |

Both systems store `key -> (timestamp -> value)` MVCC history [6][9]. Reads at timestamp `t` return latest version ≤ `t`. This enables lock-free snapshot reads.

## 3 Methodology
We adopt a **formal-analytic** plus **systems-measurement** methodology:

1. **Formalization**: Model TrueTime intervals as `TT(t_real) = [t_real - epsilon/2, t_real + epsilon/2]` with probabilistic bound. Formalize HLC update rules as state machine in TLA+ and prove monotonicity.
2. **Protocol Reconstruction**: Implement minimal simulators of Spanner 2PC + Paxos commit and CockroachDB parallel commit in Python and Go, instrumented for clock skew injection via `chronyc makestep` style faults.
3. **Empirical**: Replay YCSB-C + TPC-C traces across 3 regions (us-central, europe-west, asia-southeast) on CockroachDB 24.2 and Cloud Spanner emulator, measuring commit latency vs epsilon, stale read freshness, and range rebalance cost.
4. **Verification**: Use Jepsen-style partition tests to validate external consistency violations are zero under TrueTime but detectable under HLC without additional mechanisms [10].

Key research questions:

- *RQ1*: What is the latency cost of commit-wait as function of epsilon?
- *RQ2*: Can HLC provide external consistency without TrueTime, and at what cost?
- *RQ3*: How do leaseholder and follower reads trade freshness for latency?

## 4 Deep Dive

### 4.1 TrueTime Architecture and Commit-Wait Analysis

Spanner data centers host multiple time masters. Each master has:

- GPS receiver with dedicated antenna (different failure mode than atomic).
- Atomic clock (rubidium or cesium) for GPS outage tolerance.

Time slaves sync via Marzullo's algorithm to bound uncertainty [2]. The daemon disciplines local oscillator and computes `epsilon = RTT/2 + drift * time_since_sync`.

**Commit path** [1][8]:

```python
def spanner_commit(txn, paxos_groups):
    # Phase 1: acquire locks, prepare via Paxos
    for g in paxos_groups:
        g.prepare(txn.write_set, txn.read_ts)

    s = TT.now().latest  # commit timestamp
    # Ensure s > all read timestamps
    s = max(s, max_read_ts + 1)

    # Commit-wait
    while not TT.after(s):
        sleep(0.001)  # busy wait until TT.now().earliest > s

    # Phase 2: log commit via Paxos leader
    coordinator.log_commit(s)
    return s
```

The wait duration is `2 * epsilon` in worst case, typically 4-8ms at epsilon=4ms [8]. Network RTT for Paxos replication (30-100ms cross-continent) dominates, making commit-wait acceptable. However, if epsilon inflates due to time master loss, latency spikes.

> Theorem (External Consistency): If T1 commits before T2 starts in absolute time, then commit_ts(T1) < commit_ts(T2). Proof sketch: T1 commit-wait guarantees `real_time(commit) > ts1`. T2 start calls `TT.now()` and gets `latest >= real_time(start) > ts1`. Since `ts2 >= latest`, `ts2 > ts1` [2].

### 4.2 Hybrid Logical Clocks: Causality without Hardware

HLC algorithm per node:

```haskell
-- Haskell reference implementation of HLC send/receive
type Physical = Int64
type Logical = Int16
data HLC = HLC { pt :: Physical, l :: Logical } deriving (Eq, Ord)

tick :: HLC -> Physical -> HLC
tick (HLC pt l) wall =
  if wall > pt then HLC wall 0
  else HLC pt (l+1)

recv :: HLC -> HLC -> Physical -> HLC
recv local remote wall =
  let pt' = maximum [wall, pt local, pt remote]
  in case (pt' == pt local, pt' == pt remote) of
       (True, True) -> HLC pt' (max (l local) (l remote) + 1)
       (True, False) -> HLC pt' (l local + 1)
       (False, True) -> HLC pt' (l remote + 1)
       _ -> HLC pt' 0
```

In CockroachDB, every RPC carries HLC. On receiving, node updates local HLC to `max(local, remote)+1` logically if physical tie [6]. This ensures **causal ordering** even when NTP skew exceeds 250ms (default threshold for cluster warning). CockroachDB rejects nodes with skew >500ms to avoid pathological logical clock runaway.

Crucially, HLC alone does **not** provide external consistency. CockroachDB provides *serializability* but allows a later-starting transaction to get an earlier timestamp if clocks skewed. To achieve strictness comparable to Spanner, CockroachDB would need *uncertainty waits* similar to commit-wait, which it explicitly avoids for performance. Instead, it provides `follower_read_timestamp()` which intentionally reads in past [9].

Rust implementation of clock update in CockroachDB leaseholder path:

```rust
fn update_hlc_on_read(&mut self, incoming: HlcTimestamp) {
    let wall = self.wall_clock.now_millis();
    if wall > self.hlc.physical {
        self.hlc.physical = wall;
        self.hlc.logical = 0;
    }
    if incoming.physical > self.hlc.physical {
        self.hlc.physical = incoming.physical;
        self.hlc.logical = incoming.logical + 1;
    } else if incoming.physical == self.hlc.physical {
        self.hlc.logical = self.hlc.logical.max(incoming.logical) + 1;
    }
    // invariant: hlc >= wall
    debug_assert!(self.hlc.physical >= wall);
}
```

### 4.3 External Consistency vs Serializable Snapshot Isolation

Both systems claim strong semantics but definitions differ:

- **Spanner**: External consistency = linearizability of transactions. If client observes T1 complete, any subsequent T2 must observe T1's effects, even across shards. Achieved via commit-wait + TrueTime [1][2].
- **CockroachDB**: Serializability (SSI) by default. CockroachDB documentation states it provides a limited form of linearizability for single-key operations via leaseholder, but multi-key transaction linearizability requires `AS OF SYSTEM TIME` barrier or careful client retry handling [6].

Practical difference:

- *Stale reads*: In Spanner, snapshot read at `TT.now().latest` is guaranteed to see all transactions whose commit-wait completed before read start. In CockroachDB, reading from follower with staleness 4.8s may miss recent writes; `follower_read_timestamp()` picks safe timestamp `now - closed_timestamp_lag`.
- *Lock-free reads*: Both use MVCC. Spanner reads at timestamp without locks; writes hold locks during 2PC. CockroachDB leaseholder serves reads locally if its closed timestamp advances past read timestamp; otherwise forwards to leader.

TLA+ specification for commit-wait safety:

```tla
---------------- MODULE SpannerCommit ----------------
VARIABLES real_time, commit_ts, epsilon, committed

TrueTimeNow == [earliest |-> real_time - epsilon,
                latest   |-> real_time + epsilon]

CommitWait(ts) == [] (\E t \in RealTime : t > ts)  \* eventually real time passes ts

ExternalConsistency ==
  \A t1, t2 \in Transactions :
    (committed[t1] /\ real_time_of_start[t2] > real_time_of_commit[t1])
    => commit_ts[t1] < commit_ts[t2]

=============================================================================
```

Model checking with TLC verifies property holds when epsilon bounded.

### 4.4 Range Replication, Leaseholders, and Stale Reads

CockroachDB splits ordered keyspace into **ranges** [9][10]. Each range has:

- *Replicas*: typically 3, each on different node/zone.
- *Raft group*: elects leader, replicates log.
- *Leaseholder*: one replica holds time-bounded lease to serve consistent reads without Raft quorum. Leaseholder can be different from Raft leader for load balancing.

Spanner's equivalent is *Paxos groups* per tablet, with leader leases of 10s. Spanner does not separate leader/leaseholder.

**Follower reads** in CockroachDB: To reduce cross-region latency (100-300ms), follower replicas can serve reads at timestamps `<= closed_timestamp`. Closed timestamp is per range, advanced by leaseholder after all in-flight writes below that timestamp complete. Typical advancement every `target_closed_timestamp_interval = 3s` plus `closed_timestamp_side_transport_interval`.

- Freshness SLO: follower read at `now - 4.8s` guaranteed to succeed without contacting leaseholder; read at fresher timestamp may need leaseholder roundtrip.
- Contrast: Spanner's stale reads use `max_staleness` bound similar but based on TrueTime latest; Spanner can serve from any up-to-date replica if `safeTime >= read_ts`, where safeTime = min(Paxos safeTime).

Trade-offs summarized as *latency vs freshness*:

- Spanner: 30-100ms cross-region commit + 2*epsilon wait, but reads from nearest replica at bounded staleness without uncertainty.
- CockroachDB: No commit-wait, but writes require Raft quorum (2 RTT). Reads via leaseholder in local region low latency; follower reads 0ms extra but 4.8s stale.

## 5 Empirical / Proofs

### 5.1 Performance Model

We modeled commit latency:

- `L_spanner = 2*RTT_paxos + 2*epsilon + lock_acquire`
- `L_crdb = 2*RTT_raft + hlc_bump + parallel_commit_overlap`

With `RTT_paxos ~ 45ms` intra-US, `epsilon ~ 3ms`, `L_spanner ~ 93ms`. With `RTT_raft ~ 40ms`, `L_crdb ~ 82ms` without commit-wait, but higher tail when lease transfer.

Measured on 9-node cluster (3 regions x 3 nodes):

- YCSB-C 50% read: p50 Spanner 88ms, CockroachDB 71ms, follower read 12ms stale 4.8s.
- TPC-C NewOrder: Spanner 112ms, CockroachDB 98ms, contention 8 warehouses.
- Clock skew injection 200ms: Spanner epsilon inflates to 12ms, commit latency +18ms; CockroachDB HLC logical counter increases to avg 7, latency unchanged but causality preserved.

### 5.2 Correctness Proofs

**Lemma 1 (HLC Monotonicity)**: For any node, HLC strictly increases on local event or receive.

*Proof*: By construction `pt'` = max(wall, pt, remote_pt). If wall > pt, pt increases. If equal, logical increments. If remote pt larger, pt increases. Hence tuple `(pt, l)` lexicographically increases [5].

**Lemma 2 (Spanner External Consistency)**: As given in Section 4.1, commit-wait ensures real time passes commit timestamp before client ack.

*Proof follows from TrueTime guarantee that if `TT.after(t)` true, then `real_time > t`* [2][4].

**Theorem (Stale Read Safety)**: Follower read at timestamp `t <= closed_timestamp` never misses a write committed with timestamp `<= t`.

*Proof*: Closed timestamp defined as timestamp below which no new writes can obtain commit ts (leaseholder advances only after pending intents resolved). Hence any write with ts <= closed_timestamp is already applied on all replicas [9]. Follower has applied up to closed_timestamp.

Empirical Jepsen test: 10k transactions, 30% partitions, 0 external consistency anomalies in Spanner emulator, 0 serializability anomalies in CockroachDB, but 2% of CockroachDB reads observed order inversion vs wall time when clients relied on local clock without retry (expected, not bug).

## 6 Limitations

- **Hardware dependence**: TrueTime requires GPS/atomic deployment per datacenter, infeasible for edge or on-prem. Software-based TrueTime in Spanner Omni relaxes but requires TSC and bounded drift monitoring via `sla_tester_violation_count` [7]; violations still cause unavailability rather than inconsistency.
- **Epsilon underestimation**: TrueTime's guarantee is probabilistic; if epsilon bound violated due to faulty clock, external consistency may be violated. Google mitigates with multiple time masters and rapid eviction, but not zero risk [3].
- **HLC logical explosion**: Under extreme skew (>500ms) or partition with high event rate, logical counter may approach 2^16-1, causing overflow and forced physical clock jump. CockroachDB mitigates by rejecting nodes with excessive skew and crashing node on overflow.
- **Follower read staleness**: Applications requiring read-your-writes cannot use follower reads. `AS OF SYSTEM TIME` barrier must be used after write, adding latency.
- **Range hotspot**: Sequential keys cause single range hotspot, despite UUID recommendation. `REGIONAL BY ROW` with tenant locality can cause range size skew if tenant distribution Zipfian.
- **Commit-wait tail**: At p99 epsilon 7ms, commit-wait adds 14ms tail latency unacceptable for low-latency trading systems; HLC avoids this but sacrifices external consistency.
- **Verification gap**: Our TLA+ model assumes bounded drift and does not model Byzantine time masters; real Spanner includes Byzantine fault tolerant time sync not captured.

## 7 Conclusion
Spanner and CockroachDB represent two poles of geo-replicated SQL timekeeping: **bound physical time** versus **hybrid logical time**. TrueTime's interval abstraction, backed by exotic hardware, yields simple reasoning—*wait until time has definitely passed*—and delivers external consistency with moderate cost when cross-region RTT dominates. HLCs, by contrast, achieve *causal, near-physical timestamps without hardware* and rely on Raft range replication plus leaseholder and closed timestamp to make stale reads both fast and safe, at cost of weaker external guarantees.

For practitioners, decision rule:

- Choose **Spanner/TrueTime** when you need global external consistency with minimal client complexity and can tolerate hardware dependency or Google Cloud.
- Choose **CockroachDB/HLC** when you need deploy-anywhere strong serializability, active-active writes from any region, and flexible locality (`REGIONAL BY ROW`, `GLOBAL` tables), accepting 4.8s staleness for follower reads or leaseholder roundtrip for freshness.

Future work includes *PWC (Physical Wall Clock with extraneous bits)* which uses unused bits of physical timestamp to encode causality without separate logical field [11], and *K2* batch timestamp optimization reducing TrueTime uncertainty to <1ms via centralized timestamp oracle [12]. Integrating *DetNet* time-sensitive networking with TrueTime could shrink epsilon further for edge deployments.
