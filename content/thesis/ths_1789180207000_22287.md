# QUIC: The UDP-Based Transport Redesign — Cryptographic Handshakes, 0-RTT, Loss Recovery, and Congestion Control

## Abstract

QUIC re-architects Internet transport by fusing the cryptographic handshake, multiplexed streaming, loss detection, and congestion control into a single user-space protocol carried over UDP datagrams, standardized as RFC 9000 with TLS 1.3 integration (RFC 9001) and recovery (RFC 9002). This thesis traces QUIC from its 2012 Google origins [5] to IETF standardization in 2021, dissecting long and short headers, the three packet number spaces, and the always-encrypted invariant set that resists middlebox ossification. We analyze the 1-RTT and 0-RTT handshakes, anti-amplification validation, and Retry; derive the RFC 9002 machinery — time-threshold detection, the probe timeout, persistent congestion; and formalize how NewReno, CUBIC, and BBR mount on QUIC's pluggable framework [2][3]. We map the HTTP/3 binding (RFC 9114), examine migration and version negotiation as ossification countermeasures, and synthesize deployment evidence — Google's 8.0% search-latency and 18.0% rebuffering reductions [5] against recent findings of QUIC lagging HTTP/2 on fast networks [6] — closing with structural limitations.

## 1 Introduction

Transport protocols ossify. TCP's wire format froze decades ago: sequence numbers, flags, and options became inputs to middlebox state machines that no operator could alter without breaking unknown firewalls, NATs, and load balancers scattered across the path. The consequence was a design loop in which improving transport behavior required inventing application-layer hacks — HTTP/2's multiplexing over a single TCP connection, for example, which merely relocated head-of-line blocking from TCP's segment stream to HTTP/2's stream layer whenever a packet was lost [4][6]. Google's QUIC project, begun in 2012 and published by Langley et al. at SIGCOMM 2017 [5], proposed a radical escape: build a *new* transport that middleboxes already permit — UDP — and encrypt nearly everything, so that the middleboxes which froze TCP's format could never again accumulate a dependency on transport internals. An IETF working group, chartered in 2016, separated QUIC's fused layers into cleanly specified parts and published the QUIC version 1 standard in May 2021 [1][2][3].

QUIC's design goals were simultaneously conservative and ambitious. Conservatively, it aimed to make HTTPS faster and more robust: fewer round trips to establish security, independent streams so that one loss event stalls only the streams whose bytes the lost packet carried, and connections that survive a client's address change when a mobile device migrates from Wi-Fi to cellular. Ambitiously, it aimed to make the transport *evolvable*: implemented in user space, deploying with applications rather than operating systems, and encrypting everything not strictly needed for routing, so that future versions could renegotiate features on the wire without new middlebox permissions. This thesis dissects how those goals were realized across the protocol's four interlocking systems — packet architecture, the cryptographic handshake, loss detection and recovery, and congestion control — and critically examines where the realization falls short.

## 2 Background

### 2.1 The TCP inheritance and its failures

TCP coupled reliability, ordering, congestion control, and flow control into a single byte stream delivered in-order. Any segment loss forced the receiver to buffer subsequent segments until retransmission completed — *head-of-line blocking* — and because HTTP/2 multiplexed all object streams over one TCP connection, a single loss event stalled every concurrent HTTP transaction. Connection identity was bound to the 5-tuple (protocol, source and destination addresses and ports), so address changes broke connections. The three-way handshake plus TLS 1.2 negotiation cost two to three round trips before application data could flow. And because TCP lives in the kernel, every congestion-control or option innovation required operating-system rollouts measured in years [5].

### 2.2 gQUIC: the prototype years

The original Google QUIC (gQUIC) fused the transport, the cryptographic handshake, and the HTTP/2 mapping into one design. Its contributions were architectural: connection identity carried by an explicit *connection ID* rather than the 5-tuple; streams as the unit of multiplexing; and a cryptographic handshake based on Google's bespoke QUIC Crypto that folded transport and security negotiation into one round trip, with repeat-connection 0-RTT using cached server configuration [5]. The IETF working group retained the architecture but replaced QUIC Crypto with TLS 1.3, modularizing the design into the transport [1], the TLS integration [2], and loss detection and congestion control [3], with HTTP/3 specified separately [4].

### 2.3 Design constraints: UDP as substrate

Choosing UDP rather than a new IP protocol number was pragmatic: UDP packets traverse existing NATs, firewalls, and load balancers, which know how to demultiplex UDP by port. The price is that QUIC must reimplement everything TCP provided — reliability, ordering, flow control, congestion control, PMTUD — above the datagram layer, all in user space. The further price is *middlebox discrimination*: some networks throttle or block UDP outright, and UDP's best-effort semantics mean the stack cannot rely on kernel behavior such as segmentation offload.

## 3 Methodology

This thesis proceeds by specification archaeology and comparative analysis rather than by new measurement. We read the version 1 RFC suite [1][2][3][4] against the SIGCOMM 2017 design paper [5] and the post-deployment measurement literature [6], extracting the normative mechanisms of each subsystem and checking their consistency across documents. For the handshake, we reconstruct the packet flows from RFC 9001's encryption-level architecture and the TLS 1.3 state machine it borrows; for recovery, we restate the RFC 9002 algorithms in pseudocode and verify their invariants by hand; for congestion control, we compare NewReno, CUBIC, and BBR as instantiations of QUIC's recovery framework rather than as wire behaviors, since QUIC deliberately standardizes the *signals* and leaves the *controller* pluggable [3]. Empirical claims are sourced from published measurements: Google's at-scale deployment results [5], the RFC 9000 overview literature, and recent independent studies of QUIC performance on fast networks [6]. ## 4 Deep Dive

### 4.1 Packet architecture: headers, connection IDs, and packet number spaces

Every QUIC packet begins with a header whose first bit discriminates *long headers* (used only during connection establishment and version negotiation) from *short headers* (used for the steady state). Long headers carry the version, a destination and source connection ID, and a type-dependent remainder — Initial, 0-RTT, Handshake, or Retry packets. Short headers are minimal: a destination connection ID and a truncated packet number, with almost everything else encrypted. RFC 8999's *invariant* definition constrains this further: across all future versions, the first byte's long/short bit, the fixed-bit requirement, the version field position in long headers, and the connection-ID length field position are immutable, so that middleboxes can implement version-agnostic routing without understanding any version's internals. Header *protection* — an AES/ECB or ChaCha20 mask applied over the packet-number field and header flags — hides even the packet number length from observers, defeating passive inference attacks that TCP's cleartext sequence numbers permit.

A subtler innovation is the *packet number space*: QUIC maintains three independent numbering domains — Initial, Handshake, and Application Data — each with its own loss detection state and cryptographic keys. Packet numbers are *never reused* across a connection, unlike TCP sequence numbers which wrap, and ACK frames explicitly name ranges within a single space. Retransmissions are therefore *new packets with new numbers*; the ambiguity that plagues TCP's RTT measurement (Karn's dilemma) disappears by construction, because an ACK of packet *n* unambiguously identifies which transmission of the underlying frames was received.

Frames — STREAM, ACK, CRYPTO, CONNECTION_CLOSE, NEW_CONNECTION_ID, PATH_CHALLENGE, DATAGRAM, and others defined in RFC 9000 §19 — are the units of protocol logic; packets are merely their envelopes, and a single UDP datagram may carry multiple coalesced packets of different types (though QUIC forbids, for instance, mixing Initial and 1-RTT protection levels carelessly).

### 4.2 The TLS 1.3 handshake: 1-RTT, 0-RTT, and Retry

QUIC replaces the TLS record layer entirely. TLS 1.3 handshake messages travel as the payload of CRYPTO frames, and QUIC derives packet-protection keys from TLS traffic secrets at each *encryption level* (Initial, Handshake, 0-RTT, 1-RTT) per RFC 9001. The client's first flight carries the ClientHello in an Initial packet, padded by the client to at least 1200 bytes so the server can enlarge its anti-amplification allowance. A typical full handshake completes in **one round trip**: ClientHello → (ServerHello, EncryptedExtensions, Certificate, CertificateVerify, Finished, plus the server's first application data) → client Finished and application data. TLS 1.3's own design — encrypted extensions, downgraded-but-authenticated negotiation — is inherited wholesale, and QUIC adds *transport parameters* (idle timeout, maximum UDP payload, flow-control windows, the stateless-reset token, preferred address) as a TLS extension, so transport and security negotiate atomically.

> **Theorem: 0-RTT safety.** QUIC 0-RTT early data enjoys the same security properties as TLS 1.3 0-RTT — forward secrecy for the application data keys derived from the resumption secret — *provided* the application layer treats early data as replayable. RFC 9001 requires servers to remember rejected or accepted 0-RTT to bound replay, and forbids 0-RTT for requests whose side effects are not idempotent unless the application accepts the risk.

*Stateless Retry* protects servers against source-address spoofing and handshake-flood amplification: the server responds to an Initial with a Retry packet containing an opaque, integrity-protected token, and the client must echo the token in a second Initial — proving it can receive at the claimed address — before the server commits cryptographic state. Anti-amplification caps the server's pre-validation output at three times the bytes received, bounding the reflector gain available to attackers.

### 4.3 Loss detection and recovery: RFC 9002

QUIC's recovery design, specified in RFC 9002 [3], discards TCP's timer taxonomy (RTO, fast retransmit) for two unified mechanisms: **time-threshold detection** and the **probe timeout (PTO)**.

*Round-trip sampling.* Each newly acknowledged packet in a number space that carries the largest acknowledged number updates `latest_rtt`; the smoothed RTT follows an exponentially weighted moving average, and `rttvar` tracks deviation. Because packet numbers are never reused, samples are never ambiguous.

*Time-threshold loss detection.* A packet is declared lost when a packet sent later, in the same number space, is acknowledged and the earlier packet was sent more than `time_threshold` earlier, where `time_threshold = max(kTimeThreshold × max(smoothed_rtt, latest_rtt), kGranularity)` with `kTimeThreshold = 9/8`. The nine-eighths factor absorbs reordering without declaring spurious loss, and it applies per number space.

*The probe timeout.* If no acknowledgment arrives, the PTO fires at `smoothed_rtt + max(4 × rttvar, kGranularity) + max_ack_delay`, sending one or two probe packets (new data if available, otherwise retransmitted frames in *new* packets) and arming the timer again with exponential backoff on consecutive expirations. This design eliminates TCP's tail-loss pathology: there is no distinction between "fast recovery" and "timeout recovery" at the probing level — the PTO simply guarantees that forward progress resumes, while persistent congestion (all packets in a PTO window lost) collapses the congestion window to the minimum and stretches the timer, mirroring RTO semantics without TCP's timer disambiguation hacks.

```python
# Simplified RFC 9002 loss-detection core
K_TIME_THRESHOLD = 9/8
K_GRANULARITY = 0.001  # 1 ms

def detect_lost(sent_packets, acked_packet, smoothed_rtt, latest_rtt):
    threshold = max(K_TIME_THRESHOLD * max(smoothed_rtt, latest_rtt),
                    K_GRANULARITY)
    lost = [p for p in sent_packets
            if p.time_sent + threshold <= acked_packet.time_sent]
    return lost

def probe_timeout(smoothed_rtt, rttvar, max_ack_delay, pto_count):
    pto = (smoothed_rtt + max(4 * rttvar, K_GRANULARITY)
           + max_ack_delay) * (2 ** pto_count)
    return pto
```

### 4.4 Congestion control: NewReno, CUBIC, and BBR over QUIC

RFC 9002 normatively specifies a NewReno-style controller — slow start, congestion avoidance with additive increase (`cwnd += max_datagram_size` per window of acknowledged bytes... precisely, *max_datagram_size × acked_bytes / cwnd*), multiplicative decrease on loss (`cwnd ×= 0.5`, bounded below by two datagrams), and ECN-based reaction — while explicitly permitting alternatives: the recovery *signals* (loss detection, RTT estimates, ECN counts, persistent congestion) are standardized, but the *controller* is an endpoint choice. This separation is one of QUIC's most consequential design decisions: TCP coupled Reno/CUBIC evolution to kernel release trains; QUIC lets CUBIC, BBR, and future algorithms (Prague, Copa-style delay controllers) deploy with the application.

CUBIC over QUIC behaves as on TCP — a cubic window-growth function of time since last loss, with the β = 0.7 decrease factor — but benefits from QUIC's cleaner loss signals: no RTO ambiguity, per-space accounting, and ECN feedback that survives header protection. BBR models the path instead of reacting to loss: it estimates bottleneck bandwidth and minimum RTT, paces packets to the bandwidth-delay product, and cycles through ProbeBW and ProbeRTT states. Mounting BBR on QUIC is natural precisely because QUIC's user-space implementation already paces transmissions and measures RTT without kernel mediation, though it inherits BBR's known pathologies — unfairness against loss-based flows in shallow buffers, and RTT-unfairness among BBR flows.

### 4.5 Streams, flow control, datagrams, and the HTTP/3 mapping

Streams are QUIC's multiplexing primitive: each is an independent, ordered byte flow identified by a 62-bit ID whose two low bits encode initiator (client/server) and directionality (bidirectional/unidirectional). Stream frames carry offsets, so a lost packet stalls *only* streams with bytes in that packet — head-of-line blocking is confined to the genuinely dependent data. Flow control operates at two levels: per-stream (`MAX_STREAM_DATA`) and connection-wide (`MAX_DATA`), both credit-based and receiver-driven, preventing a fast sender from overwhelming a slow receiver or exhausting reassembly buffers. RFC 9221's DATAGRAM extension adds unreliable datagrams — multiplexed but neither retransmitted nor flow-controlled — for latency-sensitive payloads such as game state, media, and WebTransport.

HTTP/3 (RFC 9114) maps HTTP semantics onto this substrate: each request/response exchange uses a bidirectional stream, with unidirectional control and QPACK encoder/decoder streams per connection. QPACK replaces HPACK because QUIC's stream independence breaks HPACK's assumption of total order across the connection — a striking example of how thoroughly the transport redesign propagated into the application mapping. Server push, whose utility was always marginal, was removed.

## 5 Empirical Results and Proofs

The deployment record is the strongest evidence for the design. At Google scale, Langley et al. reported that QUIC reduced mean Google Search latency by **8.0% for desktop and 3.6% for mobile** users and cut YouTube rebuffer rates by **18.0% for desktop and 15.3% for mobile** relative to TCP+TLS+HTTP/2, attributing the gains to faster handshakes (especially 0-RTT on repeat visits), the absence of head-of-line blocking on lossy mobile paths, and improved loss recovery [5]. The mechanism-level reasoning is straightforward: on a 100 ms RTT path, eliminating one handshake round trip saves 100 ms of time-to-first-byte; with loss rates of a few percent, confining stalls to affected streams converts correlated multi-stream stalls into isolated ones.

A more recent independent study complicates the picture: on fast, low-loss Ethernet paths, QUIC/HTTP-3 underperformed HTTP/2 — roughly doubling download times in one testbed while consuming substantially more CPU — because user-space packet processing, per-packet encryption, and the absence of kernel segmentation offload dominate when the network itself is not the bottleneck [6]. The lesson is architectural rather than damning: QUIC optimizes for the *adversarial* Internet (loss, latency, mobility, ossified middleboxes), and pays a compute tax where the Internet is benign.

On the handshake, the security reduction is inherited: RFC 9001 proves QUIC's packet protection equivalent to TLS 1.3's record protection by deriving keys through the same HKDF schedule, and the mandatory encryption of transport parameters closes the downgrade and fingerprinting channels that plagued TCP+TLS composition. Formal analyses of the QUIC handshake in symbolic models have confirmed authentication and key-secrecy properties under the standard TLS 1.3 assumptions.

## 6 Limitations

QUIC's limitations cluster around four tensions. **First, user-space cost.** Per-packet AEAD, header protection, and userspace-to-kernel copies raise CPU utilization measurably; high-throughput servers must invest in receive-side scaling, batch syscalls (`sendmmsg`/`recvmmsg`), and sometimes hardware crypto offload to approach kernel-TCP goodput [6]. **Second, UDP discrimination.** Networks that rate-limit, deprioritize, or block UDP degrade or break QUIC; the specified fallback is Happy-Eyeballs-style racing with TCP, which reintroduces the stack QUIC sought to replace. **Third, ossification resistance is partial.** The invariant set is minimal by design, but QUIC version 1's 1200-byte minimum datagram, its Retry token format expectations, and load-balancer reliance on connection-ID routing already constitute new ossification surfaces; version negotiation itself requires a round trip and remains rarely exercised in practice. **Fourth, complexity.** Reimplementing loss detection, congestion control, PMTUD (via DPLPMTUD, RFC 8899), ECN handling, and migration in every stack multiplies implementation bugs; the QUIC working group's extensive interop testing mitigated this, but the attack surface of a user-space transport parsing untrusted bytes before authentication (Initial packets are only integrity-protected by a publicly known key) remains a live concern, as amplification and version-downgrade probes demonstrate.

## 7 Conclusion

QUIC is the first successful replacement of TCP's role for web traffic in four decades, and its success is architectural: by moving the transport into user space over UDP, encrypting everything but routing invariants, fusing the cryptographic handshake with connection establishment, and standardizing recovery *signals* while leaving congestion *control* pluggable, it solved head-of-line blocking, multi-RTT handshakes, and connection fragility in one coherent design. The empirical record — substantial latency and rebuffering wins at Google scale [5], tempered by user-space overhead on fast paths [6] — confirms both the design's thesis and its costs. Open problems remain: reducing per-packet CPU cost toward kernel-TCP parity, hardening version negotiation and migration against middlebox interference, maturing BBR-style model-based control over QUIC's signals, and extending the datagram and multipath extensions (MPQUIC) toward a transport that is not merely TCP's successor but a platform for transport innovation itself.
