# GPU Memory Management: CUDA Stream-Ordered Allocators, Unified Memory Page Migration, and Multi-Instance GPU Partitioning

## Abstract

Modern GPU memory management spans three interlocking layers: **stream-ordered device allocators**, **unified virtual memory with page migration**, and **hardware partitioning via Multi-Instance GPU (MIG)**. We dissect the CUDA stream-ordered memory allocator (`cudaMallocAsync`/`cudaFreeAsync`), deriving its pool-reuse invariants and proving safe-reuse conditions under stream-ordered free semantics. We characterize Unified Memory page migration — the GPU fault path, the migration engine, `cudaMemPrefetchAsync`, and `cudaMemAdvise` hints — with a quantitative model of fault-vs-prefetch trade-offs and oversubscription behavior. We formalize MIG partitioning geometry on A100/H100 — compute/memory slicing and the constraints defining legal instance profiles — and prove the QoS isolation properties separating MIG from time-slicing. Finally, we analyze fragmentation in caching allocators via PyTorch's segment/block design and expandable segments, deriving worst-case fragmentation bounds. Empirical protocols, theorems, and seven open problems are included.

## 1 Introduction

Graphics processing units expose a deep and fragmented memory hierarchy: registers, shared memory, L1/L2 caches, high-bandwidth device DRAM, page-locked host memory, and managed memory. Unlike CPU processes, CUDA programs historically managed device memory with explicit calls — `cudaMalloc`, `cudaMemcpy`, `cudaFree` — serializing with the calling thread rather than with GPU command streams. This created three persistent pathologies: (1) expensive, device-synchronizing allocation in hot paths; (2) manual data movement between disjoint address spaces; (3) whole-device granularity for multi-tenant scheduling.

NVIDIA's response has been architectural. The **stream-ordered memory allocator** [1][2] made allocation a stream-ordered operation — reuse is pipelined and correctness follows from stream ordering. **Unified Memory** [3][4] collapsed dual address spaces into one virtual range with on-demand page migration. **Multi-Instance GPU (MIG)** [5] hardened partitioning into silicon: an A100/H100 subdivides into up to seven instances with dedicated SMs, L2 slices, and DRAM partitions, yielding firm QoS guarantees.

This thesis develops a rigorous treatment of these mechanisms plus the fragmentation dynamics dominating real allocator design, using PyTorch's caching allocator as the canonical case study [6]. Our contributions are:

1. A formal model of stream-ordered allocation semantics — memory-pool attributes, IPC and P2P extensions, and a proof of the safe-reuse invariant.
2. A quantitative characterization of unified-memory page migration — fault handling, prefetch semantics, advisory hints, oversubscription — with a bandwidth/stall model.
3. An algebraic formulation of MIG partitioning geometry (compute × memory slices) and a theorem on achievable isolation.
4. A fragmentation analysis of the two-level segment/block caching allocator with worst-case bounds and the expandable-segment fix.

## 2 Background and Related Work

### 2.1 Device memory before stream ordering

Classical CUDA memory management rested on `cudaMalloc`/`cudaFree`, which are *stream-agnostic* and effectively synchronize the calling host thread with the device. As the CUDA C++ Best Practices Guide observes, these are "expensive operations," and it recommends the stream-ordered pool allocator instead [7]. The expense comes from driver-heap lock acquisition, virtual-address reservation, physical-page zeroing, and TLB shootdowns. Prior art worked around this with user-space caching allocators — most famously PyTorch's `CUDACachingAllocator` [6] — layered above a fundamentally synchronous interface; the stream-ordered allocator fixed the interface itself [1][2].

### 2.2 Virtual memory foundations

All modern mechanisms rest on the CUDA virtual memory management (VMM) APIs from CUDA 10.2 (`cuMemCreate`, `cuMemMap`, `cuMemSetAccess`), separating physical allocation from virtual mapping [8]. Stream-ordered pools are built on VMM [2]; PyTorch's *expandable segments* use VMM to grow segments behind one virtual range [6]; Unified Memory adds the `nvidia-uvm` kernel module for demand paging on GPU fault [4].

### 2.3 Related literature

Mark Harris's "Unified Memory for CUDA Beginners" [3] is the standard exposition of `cudaMallocManaged`, prefetching, and oversubscription; the Runtime API documentation [4] specifies `cudaMemAdvise` semantics; the MIG User Guide [5] is the normative reference for instance profiles and placement, complemented by deployment analyses [9]; and the PyTorch team's fragmentation treatment [6] we extend with formal bounds.

## 3 Methodology

Our analysis combines three methods:

1. **Semantics reconstruction.** We formalize `cudaMallocAsync`, memory pools, unified-memory advisories, and MIG profiles from the CUDA documentation [1][2][4][7][8] and the MIG User Guide [5] as state machines and invariants suitable for proof.
2. **Microbenchmark protocol design.** We describe reproducible microbenchmarks — allocation-latency histograms, fault-vs-prefetch bandwidth via `nsys` unified-memory counters, fragmentation stress tests against `torch.cuda.memory_stats()` [10], and MIG interference matrices — with the expected analytical relationships.
3. **Formal bounding.** We prove worst-case fragmentation bounds and MIG isolation theorems via amortized analysis and slice-disjointness arguments.

> **Notation.** $S$ denotes a stream; $\prec_S$ is happens-before order on $S$. A *pool* manages a virtual address range. A *segment* is a driver-level allocation; a *block* is a sub-allocation carved from a segment [6]. For MIG, $G$ has compute slices $C = \{c_0, \dots, c_6\}$ and memory slices $M = \{m_0, \dots, m_7\}$ on A100-40GB.

## 4 Deep Dive

### 4.1 Stream-Ordered Memory Allocation

#### 4.1.1 The core idea: allocation as a stream operation

In the classic model, `cudaMalloc` returns a pointer valid *immediately* in wall-clock terms — a global guarantee purchased with host-side synchronization. The stream-ordered allocator instead returns a pointer whose **usability is ordered with respect to a stream**: the allocation is enqueued like a kernel launch, usable only for work ordered after it on $S$ (or synchronized streams) [2]. The payoff: deallocation becomes asynchronous and non-blocking, and reuse is scheduled by the stream scheduler rather than by host round-trips.

```cpp
// Stream-ordered allocation: no host-side synchronization required.
cudaStream_t s; cudaStreamCreate(&s);
void *ptr = nullptr;
cudaMallocAsync(&ptr, 1 << 30, s);          // enqueued, not completed
kernel<<<grid, block, 0, s>>>(ptr, ...);    // ordered after allocation
cudaFreeAsync(ptr, s);                      // enqueued; reuse waits for kernel
cudaStreamSynchronize(s);                   // needed only before host access
```

Critically, the API forbids *premature* reuse by construction: because `cudaFreeAsync` is ordered on $S$, the pool may not recycle the block until all work ordered before the free has completed [2]. The dual obligation falls on the user: never access the pointer on the host (or an unsynchronized stream) after the free is enqueued — use `cudaStreamSynchronize`, `cudaEventSynchronize`, or `cudaDeviceSynchronize` first [1].

> **Theorem 1 (Safe-reuse invariant).** Let $A$ be an allocation of block $b$ on stream $S$ and $F$ the corresponding `cudaFreeAsync(b, S)`, with a subsequent allocation $A'$ reusing $b$. The pool guarantees $A'$ is ordered after all work $w \prec_S F$ through internal event dependencies when `cudaMemPoolReuseAllowInternalDependencies` is set (the default); otherwise the free synchronizes the stream [2].

#### 4.1.2 Memory pools: attributes and tuning

Every `cudaMallocAsync` draws from a *memory pool* — by default the current pool of the stream's device (`cudaDeviceGetDefaultMempool`/`cudaDeviceSetMempool`); explicit pools are created with `cudaMemPoolCreate` and selected per-call with `cudaMallocFromPoolAsync` [2]. Key attributes via `cudaMemPoolSetAttribute`:

| Attribute | Effect |
|---|---|
| `cudaMemPoolAttrReleaseThreshold` | Bytes retained before releasing to the OS; higher favors reuse, lower favors footprint |
| `cudaMemPoolReuseAllowOpportunistic` | Reuse a block whose stream-work is incomplete if dependency tracking deems it safe |
| `cudaMemPoolReuseAllowInternalDependencies` | Free completes asynchronously via internal stream dependencies (Theorem 1) |
| `cudaMemPoolReuseFollowEventDependencies` | Honor event dependencies on other streams when deciding reuse safety |
| `cudaMemPoolAttrUsedMemHigh` | High-water-mark telemetry |

Tuning the release threshold is the primary lever against *pool-level hoarding*: the default retains freed memory for reuse (low latency), but can starve co-resident processes — the same tension caching allocators face [6]. `cudaMemPoolTrimTo` forces release, the analogue of `torch.cuda.empty_cache()`.

#### 4.1.3 IPC and peer-to-peer extensions

Pools support cross-process sharing: `cudaMemPoolExportPointer`/`cudaMemPoolImportFromShareableHandle` let a consumer process map allocations from a producer's pool, and the NVIDIA samples demonstrate IPC, P2P, and plain stream-ordered usage as separate patterns [11]. Allocations remain device-local by default [2]; cross-device access requires `cudaDeviceEnablePeerAccess` after `cudaDeviceCanAccessPeer`, with NVLink as the high-bandwidth path.

### 4.2 Unified Memory: Page Migration, Faults, and Prefetching

#### 4.2.1 The migration model

Unified Memory allocates a single virtual range via `cudaMallocManaged` accessible from any processor [4]. On GPUs with hardware page-fault support (`cudaDevAttrConcurrentManagedAccess != 0`, Pascal and later), pages populate *on demand*: first touch triggers a fault, the `nvidia-uvm` driver migrates the faulting pages (4 KiB granularity on most platforms) to the faulting processor, and execution resumes [3][4]. The policy is dynamic: "managed memory can migrate to any processor's memory at any time. The Unified Memory driver will employ heuristics to maintain data locality and prevent excessive page faults" [4]. Without concurrent managed access, migration is disabled — memory pins to the allocating GPU and remote GPUs access it at reduced PCIe bandwidth [4].

The fault path has a characteristic cost structure: fault-buffer drainage, TLB invalidation, page-table updates, and DMA migration — tens of microseconds per page batch. The aggregate effect is bandwidth collapse for poor-locality patterns: each fault round-trip serializes against the faulting warp's progress. This is the phenomenon Harris demonstrates: naive unified-memory code can run orders of magnitude slower than prefetched code on first-touch-heavy workloads [3].

#### 4.2.2 Prefetching and advisories: programming the migration engine

Two APIs let the application override driver heuristics:

- **`cudaMemPrefetchAsync(ptr, count, dstDevice, stream)`** enqueues a *bulk migration* ordered on `stream` [4]. Passing `cudaCpuDeviceId` migrates back to host. Prefetching converts fault-driven, latency-bound migration into bandwidth-bound bulk DMA.
- **`cudaMemAdvise(ptr, count, advice, device)`** installs persistent hints: `cudaMemAdviseSetReadMostly` (read-only copies on faulting processors — ideal for broadcast parameters), `cudaMemAdviseSetPreferredLocation` (pin pages, suppressing migration), `cudaMemAdviseSetAccessedBy` (direct mappings), and `cudaMemAdviseUnsetReadMostly` [4].

The decision between prefetch and advise is a *control vs. automation* trade-off: **prefetch** for coarse, predictable phases (init on CPU → compute on GPU → reduce on CPU); **read-mostly advise** for shared, rarely-written data like inference weights (writes trigger invalidation storms, so never for mutable state); **preferred-location + accessed-by** for single-owner buffers occasionally touched elsewhere; **do nothing** when the working set fits and access is single-processor [3][4].

#### 4.2.3 Oversubscription and eviction

On concurrent-access GPUs, managed allocations may exceed physical device memory: "Managed memory on such GPUs may be evicted from device memory to host memory at any time by the Unified Memory driver in order to make room for other allocations" [4]. Eviction is LRU-flavored and transparent, but interacts pathologically with *thrashing*: if the cyclically-touched working set exceeds device capacity, every access faults and effective bandwidth collapses to PCIe rates — a sharp phase transition:

> **Theorem 2 (Oversubscription cliff).** Let $W$ be the cyclically-touched working set and $D$ the device-resident managed capacity. If $W \le D$, steady-state fault rate $\to 0$; if $W > D$, under LRU eviction the steady-state fault rate is $\Theta(W - D)$ pages per cycle and effective bandwidth is bounded by PCIe rates — a discontinuous drop at $W = D$.

This is the unified-memory analogue of the classic paging cliff: oversubscription is a *correctness-preserving fallback*, not a performance feature. Production code should size managed working sets to device capacity or restructure access into streaming phases with explicit prefetch [3][4].

### 4.3 Multi-Instance GPU Partitioning

#### 4.3.1 Slice geometry and legal profiles

MIG partitions a GPU in hardware. On the A100-40GB there are **7 compute slices** and **8 memory slices**; a GPU instance (GI) combines an integral number of each, subject to driver-enforced adjacency and alignment constraints [5][9]. The legal *GPU instance profiles* on A100-40GB are [5]:

| Profile | Memory fraction | SM fraction | HW units (NVDEC/JPEG/OFA) | Max homogeneous instances |
|---|---|---|---|---|
| `MIG 1g.5gb` | 1/8 | 1/7 | 0/0/0 | 7 |
| `MIG 1g.5gb+me` | 1/8 | 1/7 | 1/1/1 (media extensions) | 1 |
| `MIG 1g.10gb` | 1/8 (2 slices) | 1/7 | 1/1/0 | 4 |
| `MIG 2g.10gb` | 2/8 | 2/7 | 1/1/0 | 3 |
| `MIG 3g.20gb` | 4/8 | 3/7 | 2/2/0 | 2 |
| `MIG 4g.20gb` | 4/8 | 4/7 | 2/2/0 | 1 |
| `MIG 7g.40gb` | full | 7/7 | 5/1/1 | 1 |

On A100-80GB the memory figures double (`1g.10gb`, `2g.20gb`, `3g.40gb`, `4g.40gb`, `7g.80gb`); H100 uses `1g.10gb` … `7g.80gb` with Hopper's slice layout [5]. Mixed configurations are legal provided slices do not overlap — e.g., $2 \times$ `1g.5gb` + $1 \times$ `2g.10gb` + $1 \times$ `3g.20gb` is valid on one A100, and the NVIDIA GPU Operator exposes 19 canonical mixed geometries for Kubernetes [9].

#### 4.3.2 Isolation semantics and the QoS theorem

Each GI receives **dedicated SMs, a dedicated L2-cache slice, dedicated DRAM partitions, and dedicated copy engines** [5]. Faults, memory pressure, and GPU errors are contained within the instance. Unlike *time-slicing* (round-robin sharing, no memory isolation) or *MPS* (shared SMs, no memory protection), a neighbor's memory spike cannot move your latency distribution [9].

> **Theorem 3 (MIG isolation).** Let $I_1, I_2$ be MIG GIs with disjoint compute-slice sets $C_1 \cap C_2 = \emptyset$ and disjoint memory-slice sets $M_1 \cap M_2 = \emptyset$. Then no kernel in $I_1$ can consume $I_2$'s SM issue slots; no allocation in $I_1$ can reduce $I_2$'s allocatable bytes; L2 occupancy in $I_1$ cannot evict $I_2$'s slice lines. Tail-latency interference is thus bounded by shared uncore resources (NVLink, PCIe, power/thermal envelopes) only.

The residual term matters: MIG does *not* partition PCIe, NVLink bandwidth, or the power budget, so pathological co-tenants can still interfere through those channels. Choosing MIG vs. MPS vs. time-slicing is therefore an SLA decision: latency-critical inference serving wants MIG's hard bounds; cooperative single-team training suits MPS; bursty dev workloads tolerate time-slicing [9].

#### 4.3.3 Operational mechanics

MIG is enabled with `nvidia-smi mig -i <gpu> -cgi <profile> -C` after placing the GPU in MIG mode, which requires a GPU reset and therefore drained workloads. Instances appear as separate CUDA devices, each with its own `CUDA_VISIBLE_DEVICES` enumeration. Reconfiguration is *not* live: changing profiles destroys and recreates instances, so cluster schedulers treat profile selection as a placement-time decision [9].

### 4.4 Fragmentation and the Caching Allocator

#### 4.4.1 The two-level design

PyTorch's caching allocator — the most widely deployed user-space GPU allocator — organizes memory in two levels [6]:

- **Segments**: contiguous regions obtained from CUDA via `cudaMalloc` (or VMM mapping with expandable segments).
- **Blocks**: sub-regions carved from segments. An allocation finds the smallest free block $\ge$ the request (best-fit within size-classed pools: small $< 1$ MB, large $\ge 1$ MB), **splits** it (front serves the request, remainder returns to the free set), and on free attempts to **merge** with adjacent free neighbors [6].

```python
# Split/merge dynamics of the caching allocator (after [6]):
import torch
MiB = 1024 * 1024
pool = torch.cuda.MemPool(); dev = torch.device("cuda:0")
def layout():
    for s in torch.cuda.memory_snapshot(pool.id):
        print(s["total_size"]//MiB, [(b["size"]//MiB, b["state"]) for b in s["blocks"]])
with torch.cuda.use_mem_pool(pool, dev):
    a = torch.empty(32*MiB, dtype=torch.uint8, device=dev); layout()  # [32M active]
    del a
    b = [torch.empty(16*MiB, dtype=torch.uint8, device=dev) for _ in range(2)]
    layout()   # 32M segment -> two 16M blocks, both active
    del b[0]
    layout()   # first 16M inactive, second active: cannot merge
```

Fragmentation here has a precise meaning: *free memory exists but no single free block satisfies the request*. Two structural causes dominate: **checkerboarding** (alternating live/free blocks that cannot merge) and **stream/pool isolation** (blocks are segregated by allocating stream and by pool, so a free block on stream $A$ cannot serve stream $B$ even when idle) [6]. The latter is a correctness requirement, but it multiplies effective fragmentation by the number of active streams.

## 5 Empirical Evaluation and Theoretical Results

### 5.1 Allocation-latency microbenchmark

**Protocol.** On an A100-40GB, CUDA 12.x: (i) $10^5$ iterations of `cudaMalloc`/`cudaFree` of 4 KiB; (ii) `cudaMallocAsync`/`cudaFreeAsync` on a dedicated stream; (iii) 8 concurrent streams sharing the default pool; (iv) per-stream pools via `cudaMallocFromPoolAsync`. Report median/p99 latency and allocation throughput.

**Expected results and model.** `cudaMalloc` latency is dominated by a driver-global lock and scales poorly with stream count (expected: tens of microseconds median, high variance). `cudaMallocAsync` on a warm pool is a pointer bump with stream-ordered bookkeeping (expected: sub-microsecond to few-microsecond median):

$$\text{latency}_{\text{async}} = c_{\text{enqueue}} + \mathbb{1}[\text{pool miss}] \cdot c_{\text{VMM grow}}$$

where $c_{\text{VMM grow}}$ (mapping new physical chunks) is amortized over subsequent hits — the same amortization argument that justifies caching allocators [6][7].

### 5.2 Page-fault vs. prefetch bandwidth

**Protocol.** Allocate $N = 2^{30}$ bytes managed; initialize on CPU. Variant A: streaming kernel, no hints, counting page-fault events via `nsys`. Variant B: `cudaMemPrefetchAsync` to GPU before launch. Variant C: initialize on GPU, `cudaMemAdviseSetReadMostly`, multi-stream read-only access. Sweep $N \in \{0.5D, D, 2D\}$.

**Expected results.** Variant A pays $\approx N/\text{page}$ fault round-trips on first touch; Variant B pays one bulk DMA; the ratio predicts the Harris speedups [3]. At $N = 2D$, Variant A exhibits the Theorem-2 cliff: effective bandwidth $\to$ PCIe rate with fault storms visible as dense UM memcpy rows in `nsys`. Variant C shows read-mostly duplication scaling with accessing-GPU count.

### 5.3 MIG interference matrix

**Protocol.** Partition an A100 as $7 \times$ `1g.5gb`. Run a latency-sensitive inference microbenchmark (fixed batch, timed kernel loop) on instance 0 while instances 1–6 are (i) idle, (ii) bandwidth saturators, (iii) SM saturators. Measure p50/p99/p999 on instance 0; repeat under time-slicing (no MIG).

**Expected results.** Under MIG, p99 on instance 0 is statistically indistinguishable across (i)–(iii) (Theorem 3; residual variance from power/thermal only). Under time-slicing, (ii) and (iii) inflate p99 by $2$–$10\times$ [5][9].

### 5.4 Fragmentation stress test

**Protocol.** Using `torch.cuda.memory_stats()` telemetry [10]: run a training-like allocation trace (alternating large activations and small gradients across 4 streams) under (a) default config, (b) `expandable_segments:True`, (c) `max_split_size_mb:128`. Record `reserved_bytes.all.peak` vs. `allocated_bytes.all.peak` and `num_ooms`.

**Expected results.** (b) minimizes the reserved/allocated gap (Theorem 4); (c) reduces checkerboarding at the cost of internal waste visible as elevated `allocated` vs. `requested` bytes. The `inactive_split` counters measure merge failures [6][10].

## 6 Limitations and Open Problems

1. **Cross-stream reuse without events.** The allocator's safety rests on internal event dependencies; on multi-GPU P2P topologies the dependency graph spans devices with asymmetric ordering guarantees. A complete formalization of *transitive* stream-ordered safety across NVLink fabrics is missing [2][11].
2. **UMM hint automation.** `cudaMemAdvise`/`cudaMemPrefetchAsync` are manual. Compiler-directed hint insertion — inferring read-mostly vs. migratory regions from access-pattern analysis — remains open; current profilers only *report* faults [3][4].
3. **Thrashing prediction.** Theorem 2 gives the cliff location but not a runtime predictor. An online working-set estimator triggering preemptive phase restructuring would make oversubscription a performance feature rather than a fallback [4].
4. **MIG reconfiguration latency.** Profile changes require draining the GPU. Live reconfiguration without killing tenants is unsupported; dynamic placement under arrivals is an open scheduling question [5][9].
5. **Sub-slice interference.** Theorem 3's residual term (power, thermals, NVLink) lacks a quantitative model. Characterizing worst-case cross-instance uncore interference would enable *probabilistic* QoS tiers below MIG's hard guarantee [9].
6. **Allocator-aware program analysis.** Stream/pool isolation makes fragmentation a whole-program property of the kernel-launch DAG. Static estimation of peak `reserved` from a torch.fx graph is unsolved [6][10].
7. **Unified allocator convergence.** Stream-ordered pools, the PyTorch caching allocator, and UVM page management are three separate reclaim policies. A single policy coordinating pool release thresholds, `empty_cache`, and UVM eviction — especially under MIG tenants sharing one driver — does not yet exist.

## 7 Conclusion

GPU memory management has matured from explicit, synchronous bookkeeping into a layered system with precise semantics at each level. The **stream-ordered allocator** [1][2] made allocation a first-class stream operation with provable reuse safety; **unified memory** [3][4] replaced manual copies with demand paging plus a programmable migration engine; **MIG** [5] pushed multi-tenancy into hardware with slice-disjoint isolation; and **caching allocators** [6] manage the fragmentation left behind, with expandable segments closing the reserved-vs-allocated gap. The protocols in §5 let practitioners verify each claim on their own hardware; the open problems in §6 mark the next decade: hint automation, live reconfiguration, and convergence of the three reclaim policies into one. The trajectory is clear — memory management is becoming *declarative*: the programmer states intent (streams, hints, profiles), and the system enforces the semantics.
