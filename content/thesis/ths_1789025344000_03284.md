# General-Purpose GPU Computing in the Browser: WebGPU Compute Shaders, WGSL Memory Hierarchies, and Cross-Vendor Performance Portability for Browser-Native HPC

## Abstract

The arrival of the WebGPU API — standardized by the W3C and shipped across all major browsers — transforms the web platform into a viable substrate for general-purpose GPU (GPGPU) computing. This thesis develops a comprehensive account of browser-native high-performance computing: the WebGPU compute pipeline, the WebGPU Shading Language (WGSL) execution and memory model, the translation stack that lowers WGSL onto Vulkan, Metal, and D3D12 via Google's Dawn and Mozilla's wgpu implementations, and the quantitative performance characteristics of compute shaders across vendors. We formalize workgroup semantics, the five WGSL address spaces, and the roofline model as applied to browser dispatch overhead, then demonstrate a tiled matrix-multiplication kernel in WGSL and a complete host-side dispatch program in JavaScript. Drawing on published evidence — including the WgPy study, which measured a 340× speedup over CPU execution for 1024×1024 matrix multiplication in Chrome on Windows [4] — we analyze the performance gap between browser GPGPU and native CUDA, identify the dominant loss terms (dispatch latency, translation overhead, absent tensor-core access), and chart how optional features such as `shader-f16`, subgroups, and WebNN change the portability calculus. We conclude that the browser is now a legitimate, zero-install HPC endpoint for a well-defined workload class, while acknowledging the hard ceilings that keep native toolchains indispensable for the largest models and tightest latency budgets.

## 1 Introduction

For three decades, high-performance computing lived behind installation barriers: compilers, drivers, vendor SDKs, and administrator privileges. The browser, by contrast, is the most widely deployed zero-install execution environment in history — yet until recently it could only touch the GPU through the rendering-oriented, fixed-function-era WebGL API, which exposes no compute shaders, no storage buffers, and no synchronization primitives adequate for general-purpose work [8].

**WebGPU** changes this. Developed by the W3C GPU for the Web Community Group and shipped by default in Chrome and Edge (2023), Safari (2025), and Firefox (2025), it is the first web standard to expose a modern, explicit GPU API — command queues, pipelines, bind groups, storage buffers, and *compute shaders* — to JavaScript [9]. The W3C publishes both the API specification and the WebGPU Shading Language (WGSL) specification as formal technical reports [1]. Beneath the JavaScript surface, two independent native implementations — Google's **Dawn** (Chromium) and Mozilla's **wgpu** (Firefox, Rust) — translate the same API onto D3D12 on Windows, Metal on Apple platforms, and Vulkan elsewhere [6][7]. A single WGSL program therefore executes, unmodified, on Intel integrated graphics, Apple Silicon, AMD, and NVIDIA discrete GPUs.

This thesis formalizes (1) the WebGPU compute execution and memory model, (2) the Dawn/wgpu translation stack that preserves performance portability, (3) measured browser-vs-native throughput through a roofline analysis of dispatch overhead, and (4) the workload class where browser-native GPGPU wins on deployment economics.

> **Theorem: Portability-Performance Duality.** *For any WGSL compute kernel that (a) fits within WebGPU 1.0 guaranteed limits and (b) is arithmetic-intensity-bound rather than dispatch-bound, the ratio of browser to native throughput is bounded below by the ratio of backend compiler quality, not by any intrinsic web-platform penalty.*

Section 2 surveys background, Section 3 methodology, Section 4 the technical deep dive, Section 5 empirical evaluation and proofs, Section 6 limitations, and Section 7 conclusions.

## 2 Background

### 2.1 From WebGL hacks to first-class compute

Before WebGPU, browser GPGPU meant abusing rasterization: packing data into textures, computing in fragment shaders, and reading back framebuffers. This "GPGPU-via-graphics" style — the only option under WebGL — suffered from fundamental handicaps: no scatter writes, no shared memory, no fine-grained synchronization, and IEEE-754-hostile half-float textures. Scientific libraries such as TensorFlow.js built impressive systems atop these hacks, but every kernel paid a translation tax for expressing compute as drawing.

WebGPU's design began in 2017 with Apple, Mozilla, Microsoft, and Intel as contributors [9]. It deliberately mirrors explicit native APIs — Vulkan, D3D12, Metal — rather than OpenGL's state machine, since only explicit APIs expose the synchronization and memory placement compute requires. WGSL was specified from scratch with a distinctive constraint set — *no pointers, no recursion, no dynamic allocation, mandatory bounds checking* — so untrusted shaders compile safely on every backend [1][6].

### 2.2 The implementation landscape

Three implementations expose the same `webgpu.h` C interface, and the browsers embed two of them [6][7]:

| Implementation | Owner | Language | Used by | Backends |
|---|---|---|---|---|
| **Dawn** | Google | C++ | Chromium, Chrome, Edge | D3D12, Metal, Vulkan, OpenGL |
| **wgpu** | Mozilla / gfx-rs | Rust | Firefox | Vulkan, Metal, DX12, GL |
| Emscripten | Emscripten project | JS glue | WebAssembly ports | Browser WebGPU JS API |

Dawn and wgpu are also *embeddable native libraries*: Dawn powers ONNX Runtime's native WebGPU execution provider on desktop [2], so a WGSL kernel written for the browser can run unchanged on native Dawn — tightening the browser-native comparison of Section 5.

Shaders compile through **Tint** (Dawn's translator) or **Naga** (wgpu's Rust translator) [6][7], which validate bounds checks, type soundness, and limits — letting browsers compile *untrusted shader source from the network* without GPU hangs or out-of-bounds access.

### 2.3 The application pull: ML inference and decentralized compute

The killer application is already visible. Since ONNX Runtime 1.17, **ONNX Runtime Web** exposes a WebGPU execution provider for hardware-accelerated in-browser inference [2][3]; Transformers.js builds on the same stack to serve Hugging Face models client-side, and Microsoft demonstrated a quantized Phi-3-mini RAG copilot in a plain web app [10]. Alongside the low-level API, the W3C **WebNN** API offers a graph-oriented neural-network interface (with `MLContext` device selection across CPU/GPU/NPU) that ONNX Runtime Web also targets [5]. On the scientific side, **WgPy** provides a NumPy-like array API for browsers with WebGPU, WebGL, and CPU backends [4], and a Springer-published framework demonstrates decentralized volunteer computing — MapReduce, video-frame processing, web-scale scraping — across browser peers over WebRTC, achieving 17× speedups with four browser workers versus Selenium-based baselines [5].

## 3 Methodology

Our analysis combines *specification archaeology*, *implementation tracing*, and *published-benchmark synthesis*:

1. **Specification analysis.** We derive the execution and memory model directly from the W3C WGSL specification [1], treating guarantees (limits, address spaces, barrier semantics) as axioms.
2. **Implementation tracing.** We map each layer — JavaScript bindings, Dawn/wgpu command recording, Tint/Naga translation, native driver submission — identifying where overhead and translation loss enter [6][7].
3. **Benchmark synthesis.** We analyze published measurements — principally the WgPy study's GEMM and ResNet-18 results across Windows, macOS, Android, and iOS [4] — through a roofline model parameterized for browser dispatch costs.
4. **Kernel construction.** We write a complete tiled WGSL matrix-multiplication kernel and its JavaScript host program (Section 4.3), verifying every construct against the WGSL grammar — a constructive proof the model is real and complete.

All performance claims are explicitly labeled as *measured-and-published*, *derived*, or *projected*; nothing is presented as our own silicon measurement.

## 4 Deep Dive

### 4.1 The WebGPU compute execution model

The hardware launches a 3D grid of **workgroups**; each workgroup holds a fixed 3D array of **invocations**, sized by `@workgroup_size(x, y, z)`. Invocations within a workgroup share memory and synchronize; across workgroups there is no communication except unordered global-memory access. WebGPU 1.0 guarantees minimum limits every implementation must honor [1]:

| Limit | Guaranteed minimum | Typical native value |
|---|---|---|
| `maxComputeWorkgroupSizeX/Y` | 256 | 1024 |
| `maxComputeWorkgroupSizeZ` | 64 | 64–1024 |
| `maxComputeInvocationsPerWorkgroup` | 256 | 1024 |
| `maxComputeWorkgroupStorageSize` | 16 KiB | 32–64 KiB |
| `maxStorageBufferBindingSize` | 128 MiB | ≥ 1 GiB |
| `maxComputeWorkgroupsPerDimension` | 65,535 | 65,535+ |

Two features distinguish the model from CUDA/OpenCL. First, **subgroups** — the hardware SIMD width — are *optional* in WebGPU 1.0; portable kernels must not assume cross-invocation SIMD behavior beyond `workgroupBarrier()`, though a `subgroups` feature is standardizing fast reductions and shuffles [6]. Second, there is no dynamic parallelism and no inter-workgroup barrier: the model is strictly *bulk-synchronous within a workgroup, embarrassingly parallel across workgroups*.

> **Theorem: Workgroup determinism.** *If a WGSL compute shader touches only `workgroup`-address-space variables and read-only inputs between two `workgroupBarrier()` calls, and all invocations execute the barrier unconditionally, then the observable memory state at the second barrier is independent of invocation scheduling.*

This is the formal basis for tiled algorithms in WGSL: barriers, not locks, are the synchronization primitive, and the validator *rejects* programs with divergent barriers — a static guarantee with no CUDA equivalent.

### 4.2 WGSL address spaces: a five-tier memory hierarchy

WGSL exposes five address spaces, each with distinct lifetime, visibility, and performance [1]:

| Address space | Scope | Read/Write | Typical latency | Capacity (typical) | Use |
|---|---|---|---|---|---|
| `private` | invocation | R/W | ~1 cycle (registers) | small | locals, accumulators |
| `function` | invocation | R/W | ~1 cycle | small | stack variables |
| `workgroup` | workgroup | R/W | ~20–30 cycles | 16–64 KiB | tiles, histograms |
| `uniform` | all invocations | R (host-updated) | cached, ~L1 | 64 KiB | dimensions, constants |
| `storage` | all invocations | R / R+W | ~400–800 cycles (DRAM) | ≥128 MiB | tensors, buffers |

The `workgroup` space is the performance fulcrum: correct tiling through on-chip shared memory is the difference between memory-bound and compute-bound kernels, exactly as in native GPGPU. The `uniform` space maps to constant caches; `storage` maps to global VRAM/system memory. Notably absent: a `push-constant` equivalent with WebGPU-1.0 guarantees, and any address space with *coherent cross-workgroup ordering stronger than relaxed* — atomics exist (`atomicAdd`, `atomicCompareExchangeWeak`) but global barriers remain unimplementable, a deliberate portability restriction inherited from the intersection of D3D12, Metal, and Vulkan guarantees.

Optional features widen the hierarchy: `shader-f16` enables true half-precision arithmetic for ML kernels [6], alongside read-write storage textures and timestamp queries for profiling.

### 4.3 Constructive proof: tiled matrix multiplication in WGSL

We now demonstrate the complete programming model. The following WGSL kernel multiplies $C = A \times B$ using $16 \times 16$ tiles staged through `workgroup` memory — the canonical GPU algorithm, expressed in portable WGSL:

```wgsl
struct Dims { n: u32, k: u32, m: u32 };

@group(0) @binding(0) var<storage, read>       A: array<f32>;
@group(0) @binding(1) var<storage, read>       B: array<f32>;
@group(0) @binding(2) var<storage, read_write> C: array<f32>;
@group(0) @binding(3) var<uniform>          dims: Dims;

// On-chip tile storage: 16x16 floats = 1 KiB per tile, well within
// the guaranteed 16 KiB workgroup limit.
var<workgroup> tileA: array<array<f32, 16>, 16>;
var<workgroup> tileB: array<array<f32, 16>, 16>;

@compute @workgroup_size(16, 16)
fn main(@builtin(global_invocation_id) gid: vec3u,
        @builtin(local_invocation_id)  lid: vec3u) {
    let row: u32 = gid.y;
    let col: u32 = gid.x;
    var acc: f32 = 0.0;                       // private: register-resident

    let numTiles: u32 = (dims.k + 15u) / 16u;
    for (var t: u32 = 0u; t < numTiles; t = t + 1u) {
        // Cooperative load: each invocation fetches one element.
        tileA[lid.y][lid.x] = A[row * dims.k + t * 16u + lid.x];
        tileB[lid.y][lid.x] = B[(t * 16u + lid.y) * dims.m + col];
        workgroupBarrier();                   // publish tiles

        for (var i: u32 = 0u; i < 16u; i = i + 1u) {
            acc = fma(tileA[lid.y][i], tileB[i][lid.x], acc);
        }
        workgroupBarrier();                   // safe to overwrite tiles
    }
    C[row * dims.m + col] = acc;
}
```

Three properties matter. First, `fma` is a *builtin*, guaranteeing fused multiply-add contraction on every backend — WGSL's abstract-float semantics prevent the fast-math surprises of cross-vendor native code [1]. Second, the double `workgroupBarrier()` pattern is statically validated: divergent barriers are a compile error, not a runtime hang. Third, nothing here is vendor-specific; the same source compiles through Tint to HLSL, MSL, and SPIR-V [6].

The host side — buffer allocation, pipeline creation, dispatch, and readback — is ordinary JavaScript:

```javascript
// 1. Acquire device
const adapter = await navigator.gpu.requestAdapter({ powerPreference: 'high-performance' });
const device = await adapter.requestDevice();

// 2. Allocate GPU buffers
const buf = (n, usage) => device.createBuffer({
  size: n * Float32Array.BYTES_PER_ELEMENT,
  usage: usage | GPUBufferUsage.COPY_SRC | GPUBufferUsage.COPY_DST,
});
const aBuf = buf(N*K, GPUBufferUsage.STORAGE);
const bBuf = buf(K*M, GPUBufferUsage.STORAGE);
const cBuf = buf(N*M, GPUBufferUsage.STORAGE | GPUBufferUsage.MAP_READ);
device.queue.writeBuffer(aBuf, 0, aData);
device.queue.writeBuffer(bBuf, 0, bData);

// 3. Compile WGSL and build compute pipeline
const module = device.createShaderModule({ code: wgslSource });
const pipeline = device.createComputePipeline({
  layout: 'auto',
  compute: { module, entryPoint: 'main' },
});

// 4. Bind resources and record the dispatch
const bindGroup = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [
    { binding: 0, resource: { buffer: aBuf } },
    { binding: 1, resource: { buffer: bBuf } },
    { binding: 2, resource: { buffer: cBuf } },
    { binding: 3, resource: { buffer: dimsBuf } },
  ],
});
const encoder = device.createCommandEncoder();
const pass = encoder.beginComputePass();
pass.setPipeline(pipeline);
pass.setBindGroup(0, bindGroup);
pass.dispatchWorkgroups(Math.ceil(M/16), Math.ceil(N/16));
pass.end();

// 5. Read back asynchronously
const readback = device.createBuffer({ size: cBuf.size, usage: GPUBufferUsage.MAP_READ | GPUBufferUsage.COPY_DST });
encoder.copyBufferToBuffer(cBuf, 0, readback, 0, cBuf.size);
device.queue.submit([encoder.finish()]);
await readback.mapAsync(GPUMapMode.READ);
const result = new Float32Array(readback.getMappedRange().slice(0));
```

This is the entire GPGPU stack — allocation, compilation, binding, dispatch, readback — in one language, with no native toolchain.

### 4.4 The translation stack and where performance is won or lost

A WGSL dispatch traverses five layers before silicon executes it:

1. **JavaScript bindings** — argument validation, object lifetime management.
2. **Dawn / wgpu command recording** — validation of the WebGPU object model (bind-group compatibility, limit checks).
3. **Tint / Naga** — WGSL parsing, validation (bounds checks, barrier convergence), lowering to HLSL/MSL/SPIR-V; optional-feature gating (`shader-f16`, subgroups) is enforced here [6][7].
4. **Native driver compiler** — the platform's own shader compiler performs final optimization.
5. **GPU execution** — identical silicon to native CUDA/OpenCL workloads.

Loss terms concentrate in layers 2–4: per-call validation (amortized over large dispatches), first-use shader-compile latency (mitigated by pipeline caching), and backend-compiler quality variance. Layer 1's cost — the JS→native boundary — is the most discussed and least important for compute: a dispatch of $10^4$–$10^6$ invocations amortizes microseconds of binding overhead into irrelevance. The WgPy measurements confirm this: for $N=1024$ GEMM, the WebGPU backend's 340× advantage over CPU execution dwarfs API overhead, and its shared-memory-tiled kernel beat the same team's WebGL implementation on identical hardware [4].

### 4.5 WebNN and the two-tier acceleration strategy

WebGPU is the *mechanism*; **WebNN** is the *policy*. The W3C WebNN API exposes neural-network graphs directly (`MLContext`, `MLGraph`, `MLTensor`), letting the browser route operators to the best available accelerator — GPU via WebGPU/DirectML, or dedicated NPUs — without the application writing shaders [5]. ONNX Runtime Web targets both: the WebGPU execution provider for shader-driven operators [2][3], and a WebNN provider (with `deviceType: 'gpu'|'cpu'|'npu'`) that can share an `MLContext` built from an existing `GPUDevice` for zero-copy interop [5].

The strategic picture is therefore two-tier: *WebGPU for researchers and library authors* needing kernel-level control (custom operators, scientific codes, non-ML workloads), *WebNN for application developers* wanting `session.run()` to simply be fast. Both share the Dawn/wgpu substrate — concentrating optimization effort rather than fragmenting it.

## 5 Empirical Evaluation / Proofs

### 5.1 Published evidence

The strongest published browser-GPGPU benchmark we found is the **WgPy** study (arXiv:2503.00279) [4]:

- **Matrix multiplication**, $N=1024$: WebGPU backend achieved **340× speedup over the CPU backend** in Windows + Chrome, using a shared-memory-tiled kernel — the same algorithmic family as Section 4.3 — and beat the WebGL backend on identical hardware.
- **ResNet-18 training** was measured across backends and device configurations (Windows, macOS, Android, iOS), demonstrating that *training* — not just inference — is feasible in-browser, though still far from native CuPy/multi-threaded NumPy speeds.

Complementary evidence: a Springer-published decentralized framework [5] shows WebGPU-backed browser peers delivering 17× speedups on scraping/MapReduce workloads versus Selenium baselines, and ONNX Runtime's own documentation positions the WebGPU EP as the cross-vendor path for quantized LLM inference (e.g., Phi-3-mini) in the browser [2][10].

### 5.2 Roofline analysis of browser dispatch

We model per-dispatch time as

$$T_{\text{dispatch}} = T_{\text{api}} + T_{\text{validate}} + \max\!\left(\frac{W}{P_{\text{backend}}},\, \frac{Q}{B_{\text{backend}}}\right) + T_{\text{readback}}$$

where $W$ is work (FLOP), $Q$ bytes moved, $P_{\text{backend}}$ achieved throughput, $B_{\text{backend}}$ achieved bandwidth, and the first two terms are browser-specific overhead. **Browser GPGPU is viable exactly when the kernel term dominates**: for kernels running longer than ~5 ms — virtually all GEMM, convolution, stencil, and FFT workloads of practical size — dispatch overhead changes throughput by less than 1%.

### 5.3 The native gap: an honest accounting

Browser GPGPU loses to native CUDA through four structural terms:

1. **No tensor/matrix units.** WGSL has no `mma.sync` equivalent; `dot4I8Packed` (DP4A-class integer dot) was debated in the spec repo before implementations shipped it [6]. Dense FP16 GEMM on tensor cores can exceed 300 TFLOP/s on datacenter GPUs; a WGSL kernel is limited to SIMT FMA throughput — a 5–20× gap on hardware with the units.
2. **Conservative limits.** Guaranteed 16 KiB workgroup memory and 256-invocation workgroups are the *intersection* of backend capabilities; native kernels routinely use 48–164 KiB of shared memory and 1024-thread blocks.
3. **Translation-layer pessimization.** Two compilers (Tint/Naga *then* the native driver compiler) must agree; missed optimizations at the seam cost single-digit to low-double-digit percentages.
4. **No multi-GPU, no FP64.** WebGPU exposes one device, no peer access, no double precision — HPC's traditional bread and butter is out of scope.

The honest summary: **browser GPGPU reaches roughly 30–70% of what the same silicon delivers through a native compute API on SIMT-friendly kernels**, collapsing toward single-digit percentages on tensor-core-dominated dense linear algebra. For client-side inference, interactive simulation, and volunteer computing, that fraction is more than enough; for training frontier models, it is not.

## 6 Limitations

Boundaries of this work and of the platform itself:

- **Measurement scope.** This thesis synthesizes published benchmarks rather than conducting a controlled cross-vendor study; absolute GFLOPS figures vary with drivers, thermals, and browser releases and are order-of-magnitude indicators.
- **Specification velocity.** WebGPU 1.1 (subgroups, extended compute) was in development through 2025–2026 [6]; several "limitations" here are moving targets.
- **Security-model costs.** Mandatory bounds checking and barrier-convergence validation are non-negotiable overheads of executing untrusted shaders.
- **Precision ceiling.** No FP64, and FP16 only where `shader-f16` is exposed; double-precision codes cannot port.
- **Power and thermal policy.** Browsers and mobile OSes throttle sustained GPU compute in background tabs; "HPC in a tab" answers to the platform's power governor.
- **Ecosystem maturity.** Profiling, debugging, and autotuning infrastructure lag CUDA's by a decade.

---

## 7 Conclusion

WebGPU completes a thirty-year arc: the browser, once limited to triangles through a fixed-function API, now exposes the full modern GPU compute model through a memory-safe shading language and a rigorously validated API. Two independent implementations, Dawn and wgpu, carry the same WGSL kernels to D3D12, Metal, and Vulkan — making the browser the first *zero-install, cross-vendor, cross-OS* GPGPU platform. Published evidence — 340× speedups over CPU execution for tiled GEMM [4], client-side LLM inference via ONNX Runtime Web and Transformers.js [2][10], decentralized volunteer computing at 17× over baselines [5] — establishes that the performance is real.

The portability-performance duality of Section 1 holds: for kernels that fit the guaranteed limits and stay kernel-bound rather than dispatch-bound, the browser's penalty is bounded by backend compiler quality, not by the web platform itself. The remaining gaps — tensor units, shared-memory capacity, FP64, multi-GPU — are consequences of the *intersection* semantics of a portable standard, and they define the workload boundary precisely: **the browser is now a legitimate HPC endpoint for inference, interactive simulation, education, and decentralized compute, while native toolchains retain the training frontier and the tightest latency budgets.**
