This thesis unifies the theory and practice of differential and metamorphic testing for language runtimes. Beginning with Csmith, the randomized C program generator that exposed more than 325 previously unknown bugs in GCC and LLVM by avoiding undefined behavior and comparing compiler outputs, we trace the lineage through YARPGen's generation policies, which delay fuzzer saturation without heavyweight safety wrappers. We formalize Equivalence Modulo Inputs as a metamorphic relation — mutating only code unexecuted under profiling inputs — and analyze its realizations Orion, Athena, and Hermes, which found hundreds of deep optimizer defects, including P1 release-blockers, using a single-compiler oracle. We then examine WebAssembly engine differential fuzzing, where wasm-smith generates spec-valid modules and Wasmtime's continuous fuzz targets compare execution against V8, wasmi, and the authoritative spec interpreter. Finally, we treat JIT correctness oracles, where tiered compilation and warmup histories demand trace-level metamorphic relations, and Alive2, which complements randomized testing with SMT-based bounded translation validation of individual optimizations. We conclude with a research agenda: JIT-aware oracles, specification-driven generation, hybrid verification-testing pipelines, and saturation science.

# Differential and Metamorphic Testing of Language Runtimes: Csmith Lineage, WebAssembly Engine Differential Fuzzing, and JIT Correctness Oracles

## 1. Introduction

The correctness of language runtimes — compilers, interpreters, just-in-time (JIT) compilers, and virtual machines — is a foundation of all software reliability. A miscompilation is among the most pernicious defects in computing: the program a developer writes and tests is silently transformed into a different program by the tool charged with faithfully translating it. Traditional test suites are fundamentally insufficient here because the space of valid programs is infinite and a compiler's specification is *relational*: it must preserve semantics, not match individual test cases. This motivates **randomized differential and metamorphic testing**, which derives test oracles not from a ground-truth implementation but from *relations* among the system's own artifacts.

The lineage of this approach traces to 2011, when Xuejun Yang, Yang Chen, Eric Eide, and John Regehr published "Finding and Understanding Bugs in C Compilers" at PLDI, introducing **Csmith**, a randomized generator of C programs avoiding undefined and unspecified behavior [1]. Over three years, Csmith-driven differential testing reported more than **325 previously unknown compiler bugs** in GCC and LLVM [1]. Every compiler tested was found both to crash and to silently miscompile valid input. Csmith showed that the test oracle problem could be dissolved by comparing outputs of several compilers on the same input: any divergence is a bug in at least one of them.

This thesis presents a comprehensive treatment of the differential and metamorphic testing lineage that followed Csmith. We trace three interwoven threads. First, the **Csmith lineage** proper: generation-based random program synthesis, its successors such as **YARPGen** [4], and the engineering problems of avoiding undefined behavior while targeting optimizer subsystems. Second, **Equivalence Modulo Inputs (EMI)** [2] and its realizations **Orion**, **Athena** [3], and **Hermes** — metamorphic techniques that construct new test programs from existing seeds by mutating only code regions unexecuted under a profiled input, yielding a *single-compiler oracle* that needs no reference implementation. Third, the contemporary frontier: **differential fuzzing of WebAssembly engines** (Wasmtime versus V8 versus the official Wasm spec interpreter), powered by generators such as **wasm-smith** [8], and **JIT correctness oracles**, where the test subject is a dynamic, adaptive optimization pipeline. These threads share a common theoretical core — the *differential oracle* as an instance of a metamorphic relation — and we analyze how the oracle must be strengthened as the artifact under test grows more complex, from ahead-of-time C compilation through formally specified peephole optimization (the **Alive2** [6] verifier-as-oracle) to the full WebAssembly execution stack.

Our contributions: (i) a unified formalization of differential and metamorphic oracles for language runtimes; (ii) a critical analysis of Csmith's design decisions — undefined-behavior avoidance, generation policies, saturation management — and YARPGen's improvements; (iii) the EMI family as metamorphic relations with quantitative evidence of bug-finding power; (iv) a synthesis of WebAssembly engine differential fuzzing and JIT oracle design, with a research agenda.

## 2. Background

### 2.1 The Oracle Problem in Runtime Testing

Testing a language runtime is distinguished by the **oracle problem**: the "input" is a program drawn from an infinite language, and the "expected output" is a machine-code artifact whose correctness is defined only *relationally* — the compiled program must behave as the source specifies. Because no feasible reference implementation exists (the compiler *is* the reference), direct oracle specification is impractical at scale. Two strategies circumvent this:

- **Differential testing** [10]: run the same input through multiple independent implementations (or configurations) and flag divergence. The oracle is the *agreement* of the implementations.
- **Metamorphic testing**: define a *metamorphic relation* — a transformation on inputs such that outputs must change predictably (often, not at all). EMI [2] is the canonical compiler example: mutate only unexecuted code regions, and observable behavior on the profiling input must be identical.

Both trade the impossible requirement of a ground-truth oracle for *consistency constraints*, and both have proved remarkably productive.

### 2.2 Randomized Program Generation

Early compiler fuzzers were defeated by **undefined behavior (UB)**. In C, UB (signed overflow, out-of-bounds access, uninitialized values, data races) leaves program semantics unconstrained: cross-compiler divergence then cannot be attributed to a compiler bug. Csmith's central innovation was generating programs that *avoid* UB almost surely — safe arithmetic wrappers, valid pointer arithmetic, initialized variables, no unsequenced side effects — via static analysis during generation plus dynamic runtime checks [1][7], making every generated program a legitimate differential test.

The landscape after Csmith expanded along axes surveyed in [10]: generation-based construction from scratch (Csmith [1], YARPGen [4], RustSmith, wasm-smith [8]); transformation-based semantics-preserving mutation of seeds (EMI/Orion [2], Athena [3], Hermes, wasm-mutate); and learning-based approaches. Orthogonal to these, **Alive** [5] and **Alive2** [6] verify individual peephole optimizations against a formal semantics with SMT solvers — *oracles for the optimizer itself* (Section 4).

### 2.3 JIT Compilers and WebAssembly Engines

JIT compilers (V8's TurboFan, SpiderMonkey's IonMonkey, HotSpot C2) add a temporal dimension: the same function is compiled repeatedly at rising optimization levels, guarded by speculative assumptions (type feedback, inline caches, deoptimization). Bugs surface under particular warmup histories.WebAssembly engines (Wasmtime, V8, wasmi, the spec interpreter) add a *portable bytecode* with formally specified semantics [8][9]: the spec interpreter is a slow but authoritative oracle, enabling **differential execution** of the same module across engines [8]. **wasm-smith** [8] is the Csmith of this ecosystem, generating arbitrary valid modules over a configurable feature set (SIMD, threads, GC); **wasm-mutate** applies semantics-preserving mutations for coverage-guided fuzzing.

## 3. Methodology

This thesis is a systematic synthesis combining (a) a chronological reconstruction of the Csmith-to-EMI-to-wasm-smith lineage, (b) a formal unification of the oracle designs, and (c) analysis of design tradeoffs evidenced by reported bug counts and architectural decisions in the primary sources [1][2][3][4][6][8][9][10][11].

### 3.1 Formalizing the Differential Oracle

Let *P* be the space of valid programs, *I* the space of inputs, and *C₁, …, Cₙ* compiler or runtime implementations. Define the observable behavior *obs(C, p, i)* as the output (including traps, crashes, timeouts) of compiling *p* with *C* and executing it on *i*. The **differential oracle** asserts:

> **Theorem:** If all *Cₖ* correctly implement the same language semantics, then for all *p ∈ P*, *i ∈ I*: *obs(C₁, p, i) = … = obs(Cₙ, p, i)*. Any divergence implies a defect in some *Cₖ* (or the harness).

Its practical value depends on two engineering quantities: the probability that a generated *p* is actually valid (*validity rate*), and the probability that divergence reflects genuine bugs rather than harness artifacts (*oracle precision*). Csmith maximizes both by eliminating UB; WebAssembly differential fuzzing achieves near-perfect validity because wasm-smith generates only spec-valid modules [8]; residual imprecision comes from *allowed nondeterminism* (e.g., NaN bit patterns), handled by canonicalization [8].

### 3.2 Formalizing the Metamorphic (EMI) Oracle

Let *P′* be an **EMI variant** of *P* w.r.t. *I₀* if *P′* differs from *P* only in statements outside ⋃ᵢ cover(P, i). The **EMI oracle** asserts that for all *i ∈ I₀*, *obs(C, P, i) = obs(C, P′, i)* — a single compiler *C*, no reference implementation needed [2]. Orion deletes unexecuted AST statements stochastically; Athena [3] additionally inserts code into dead regions and uses MCMC sampling to maximize variant diversity; Hermes mutates *live* regions with guarded, provably-dead snippets. Soundness requires complete coverage measurement (Orion compensates for gcov's line-granularity ambiguity [2]) and avoidance of *coverage-volatile* constructs.

### 3.3 Research Questions

**RQ1** — Which Csmith-lineage design decisions most affect bug-finding yield, and how did successors improve them? **RQ2** — When does the EMI metamorphic oracle outperform multi-implementation differential testing? **RQ3** — How must oracle design change for JIT compilers and WebAssembly engines, where execution is dynamic and the reference is an interpreter? **RQ4** — What role do formal verifiers (Alive2) play as oracles, and how do they complement randomized testing?

## 4. Deep Dive

### 4.1 The Csmith Lineage: Engineering Validity and Combating Saturation

Csmith's architecture solves one hard constraint: *generate expressive programs while avoiding undefined behavior with overwhelming probability*. The generator maintains a model of program state — variables, types, initialization, live pointers with proven bounds — consulted at every step [1]. Risky arithmetic goes through safe wrappers computing in a wider type; dereferences are restricted to proven-in-bounds accesses; division is guarded against zero. The result covers a large subset of C — structs, unions, bitfields, arrays, pointers, control flow — while remaining almost surely UB-free, so compiler disagreement on a Csmith program is a compiler bug, not a UB artifact.

Over three years, more than 325 previously unknown bugs were reported to GCC and LLVM developers, including crashes and silent miscompilations [1]. Miscompilations clustered in the optimizers — the passes hardest to verify by inspection. Csmith thus validated a *methodology*: randomized differential testing as a permanent component of compiler quality assurance.

**YARPGen** [4] refined the design by asking whether expressive UB-free programs could be generated *without* Csmith's heavyweight dynamic safety wrappers, which bias the program distribution toward guarded arithmetic. Its answer is **generation policies**: parameterizable mechanisms that systematically alter emitted code to target different optimizer subsystems and delay *saturation* — the phenomenon where a mature fuzzer exhausts its distribution's novelty and stops finding bugs. YARPGen found 83 new bugs in GCC, 62 in LLVM, and 76 in the Intel C++ Compiler [4]. Automated reduction (C-Reduce) turned each divergence into a minimal report — now standard practice [10].

### 4.2 EMI: Metamorphic Relations from a Single Implementation

Equivalence Modulo Inputs [2] is the most elegant idea in the lineage. Where Csmith needs *two* compilers for an oracle, EMI needs only one — plus a seed corpus (e.g., the compiler's own regression suite). A seed program run on input *i* exercises only part of its code; the unexecuted regions are *dead modulo i* and can be mutated arbitrarily without changing observable behavior on *i*. This **metamorphic relation** — *P* and *P′* must agree on *i*, any disagreement being a miscompilation — converts one test into an infinite family of structurally novel variants.

**Orion** [2] stochastically prunes unexecuted AST statements (147 new bugs), but variant count is bounded by prunable statements, and optimizers that delete dead code can render the transformation vacuous. **Athena** [3] adds code *insertion* into dead regions with **MCMC** sampling toward variants differing substantially in control and data flow — 72 new bugs in 19 months, 17 of them P1 release-blockers in GCC [3]. **Hermes** mutates *live* regions by inserting snippets guarded by provably-false predicates (e.g., `if (x*x < 0)`), perturbing the optimizer's view of the hot path while preserving semantics [10].

The deeper lesson: *metamorphic relations compose with profiling*. Coverage data, usually a measure of test adequacy, becomes a *generator* — the profile tells the mutator exactly which transformations are semantics-preserving.

### 4.3 WebAssembly Engine Differential Fuzzing

WebAssembly offers differential testing something C never had: a **formal, executable specification**. The official Wasm spec interpreter is slow but authoritative; any divergence between an engine and the interpreter is, by definition, an engine bug [8][9]. The Bytecode Alliance operationalized this through continuous fuzz targets in the Wasmtime repository [8]. The centerpiece is the **`differential` target**: wasm-smith generates a random valid module, each exported function is evaluated with random inputs under Wasmtime, and results are compared against a reference — the Wasm spec interpreter, the wasmi interpreter, V8, or Wasmtime under a different configuration [8]. Additional targets compare Cranelift against V8, the spec interpreter, and the CLIF interpreter [9]. wasm-smith generates only modules passing the Wasm validator, so validity is structural rather than heuristic [8]. Its configuration space — enabled proposals (SIMD, threads, GC, exceptions), memory limits, fuel metering — functions like YARPGen's generation policies [4]. The oracle handles allowed nondeterminism by canonicalizing NaN payloads and comparing traps [8].Complementary targets (`compile`, `instantiate`, `spectests`, `table_ops`) provide crash and assertion oracles, while **wasm-mutate** supplies the EMI-analogous transformation layer: semantics-preserving mutations driving coverage-guided fuzzing deeper into engine code [9].

```c
/* The classic differential-testing harness, as documented for Csmith [7]: */
csmith > prog.c                                   /* random valid program   */
R1 prog.c -o prog_r1 && R2 prog.c -o prog_r2      /* two implementations    */
./prog_r1 > out1.txt; ./prog_r2 > out2.txt        /* execute both           */
diff out1.txt out2.txt || report_bug(prog.c)      /* divergence => bug      */
```

```python
# The Wasmtime differential target [8]: per-function differential execution
module = wasm_smith.generate(config)      # arbitrary valid Wasm module
for func, args in exported_functions(module, random_args()):
    r1 = wasmtime.execute(module, func, args)      # engine under test
    r2 = reference.execute(module, func, args)    # spec interp / V8 / wasmi
    assert canonicalize(r1) == canonicalize(r2), "differential mismatch"
```

### 4.4 JIT Correctness Oracles and Alive2: From Random Programs to Verified Rewrites

JIT compilers stress the differential oracle in a new way: the "compiler" is a *trajectory* of tiered compilations, and bugs are history-dependent — a miscompilation may require a specific sequence of type feedback, inlining, and deoptimization. The Wasmtime lineage addresses a slice of this by differential-testing *configurations* (Cranelift at different opt levels, with or without specific passes) [8][9]: optimization level must not change observable semantics. For JavaScript engines, Fuzzilli's Wasm-extended IR enables cross-language differential fuzzing of JS/Wasm interoperation [11]. The general JIT oracle remains open: warmup histories are hard to sample, and "the same program" must mean "the same program *under the same profiling history*".

**Alive2** [6] attacks from the opposite direction: instead of testing whole compilations against each other, it *verifies* individual optimizer transformations. Building on Alive [5] — a DSL for LLVM peephole optimizations with SMT-based proofs — Alive2 performs **bounded translation validation** on LLVM IR: source and target IR are encoded into SMT, loops unrolled to a bound, and refinement proved or refuted. Over LLVM's unit tests it found **47 new bugs, 28 fixed**, and prompted eight Language Reference patches [6]. Alive2 is an *oracle for the optimizer*: where Csmith asks "do two compilers agree?", Alive2 asks "is this transformation provably correct?" — complementary: differential testing finds bugs in the wild while translation validation certifies the rewrites it implicates.

> **Theorem (Alive2 refinement [6]):** Target *T* is a correct optimization of source *S* iff every behavior of *T* is a behavior of *S* and *T* introduces no undefined behavior absent in *S*. Alive2 decides a bounded approximation of this relation via SMT and is *sound* (no false positives) within its bounds.

## 5. Empirical Results and Proofs

### 5.1 Quantitative Bug-Finding Record

Csmith's 325+ bugs [1] accrued over three years, but the discovery *rate* declined as easy defects were fixed — the saturation YARPGen's policies were designed to combat [4]. EMI's contribution is best measured in *severity*: 17 of Athena's 40 GCC bugs were P1 release-blockers, showing metamorphic variants reach deep optimizer defects that random generation misses [3]. Alive2's 47 bugs [6] are fewer but higher in *value per bug* — each with a machine-checked proof of incorrectness, often exposing IR specification ambiguities.

For WebAssembly the metric shifts to *continuous assurance*: the Wasmtime differential targets run 24/7 under OSS-Fuzz [8][9]. The record includes concrete miscompilations — e.g., an `i32.shr_s` mismatch between Wasmtime and the spec interpreter [8] — proving even formally specified languages harbor backend bugs.

### 5.2 Proof Sketches

> **Theorem (Differential soundness):** If all tested implementations are deterministic and the test program is free of undefined behavior and implementation-defined nondeterminism (modulo canonicalization), then any observed divergence *obs(C₁, p, i) ≠ obs(C₂, p, i)* implies a defect in at least one of *C₁, C₂*, or the harness.

*Sketch.* By validity, *p* has unique defined semantics *S(p, i)*, and a correct *C* satisfies *obs(C, p, i) = S(p, i)*. Divergent observations imply some implementation differs from *S(p, i)*. The harness clause covers the two classic false-positive sources — UB slipping through generation and uncanonicalized nondeterminism — addressed by Csmith's UB avoidance [1] and wasm-smith's NaN canonicalization [8]. ∎

> **Theorem (EMI soundness [2]):** If *P′* is an EMI variant of *P* w.r.t. *I₀*, mutating only statements outside ⋃_{i∈I₀} cover(P, i), then for all *i ∈ I₀*: *obs(C, P, i) = obs(C, P′, i)* for any deterministic *C*.

*Sketch.* Execution of *P* on *i* never reaches the mutated statements, so the executed operation sequence — hence observable behavior — is identical. The entire proof obligation falls on the coverage measurement's *completeness*, which Orion secures by conservative AST-level analysis compensating for gcov's line granularity [2]. ∎

A minimal harness implementing the differential oracle:

```python
import subprocess, tempfile, os

def differential_oracle(source: str, compilers: list[str]):
    outputs = []
    with tempfile.TemporaryDirectory() as d:
        for cc in compilers:
            exe = os.path.join(d, "a.out")
            subprocess.run([cc, source, "-o", exe, "-O2"], check=True, timeout=60)
            r = subprocess.run([exe], capture_output=True, timeout=10, text=True)
            outputs.append((r.returncode, r.stdout, r.stderr))
    for o in outputs[1:]:
        if o != outputs[0]:
            return f"DIVERGENCE: {compilers} disagree"
    return None
```

## 6. Limitations

**Saturation.** Bug discovery rates decline as implementations mature; YARPGen's generation policies [4] and Athena's MCMC diversification [3] counter this, but no theory predicts when a fuzzer has saturated — the field lacks a principled *stopping criterion*.

**Shared blind spots.** Differential testing cannot find bugs common to all implementations (e.g., a shared misreading of the specification — the defect class Alive2's specification patches [6] address). Configuration-differential testing (O0 vs O3) misses bugs present at every optimization level. EMI needs only one compiler but inherits its seed corpus's blind spots.

**JIT history dependence.** Current harnesses sample programs but not *warmup histories*; a JIT miscompilation requiring a specific deoptimization sequence may never be exercised. Formalizing the JIT oracle over execution traces — generalizing EMI's profiling inputs — remains open.

**Boundedness of formal oracles.** Alive2's soundness holds only within its unrolling bounds [6]; deeper loop interactions escape. Bounded verification and randomized testing are complementary: the former certifies what it covers, the latter covers what it reaches.

**Cost and triage.** Continuous differential fuzzing (OSS-Fuzz [8][9]) consumes substantial compute, and each divergence needs human triage and reduction. Automated reducers help, but the marginal cost per *novel* bug rises steeply as easy defects are fixed.

## 7. Conclusion

From Csmith's 325 bugs [1] through EMI's metamorphic elegance [2][3], YARPGen's generation policies [4], Alive2's verified rewrites [6], to continuous differential fuzzing of WebAssembly engines [8][9], one principle unifies the field: *when no ground-truth oracle exists, consistency is the oracle*. Differential testing demands agreement among implementations; metamorphic testing demands agreement between a program and its semantics-preserving variants; translation validation demands agreement between a transformation and its formal specification.

The agenda: (1) **JIT-aware oracles** — extend differential and EMI-style testing from static programs to *execution histories*, sampling warmup traces and deoptimization events as first-class inputs; (2) **specification-driven generation** — a formal executable semantics turns the reference interpreter into a near-perfect oracle, so language designers should treat fuzzability as a design goal; (3) **hybrid verification–testing pipelines** — use randomized differential testing to *find* suspicious transformations and bounded verifiers like Alive2 to *certify or refute* them; (4) **saturation science** — information-theoretic measures of fuzzer novelty so generation policies adapt online rather than by intuition.

Compilers will never be proved correct in full — the multi-million-line reality of LLVM [6] forbids it. But randomized generation, metamorphic relations, differential execution, and bounded verification together can drive the residual defect rate toward the limits of engineering relevance. The oracle problem is not solved; it is *managed* — and managing it well is among the most successful applications of automated testing ever demonstrated.
