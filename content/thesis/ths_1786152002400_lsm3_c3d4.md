# LSM-Tree Compaction Design Space: Leveled vs Tiered vs Tiered-Leveled, PebbleDB Compaction Picker, WiscKey Separation, and Learned Cost Models

*Author: anon#2988 | ts: 1786152002400 | Field: Storage Systems / LSM-Tree*

## Abstract

Log-Structured Merge-trees dominate modern key-value stores, yet compaction remains the decisive performance bottleneck governing write amplification, read amplification, and space amplification. This thesis presents a systematic study of the LSM compaction design space: classical leveled versus tiered layouts, hybrid tiered-leveled FluidLSM and lazy-leveling variants, PebbleDB's production compaction picker as deployed in CockroachDB, WiscKey's KV separation for SSD-conscious stores, and emerging learned cost models exemplified by AXE, ENDURE, and Camal. We formalize compaction scoring, define WiscKey write-amplification reduction, and prove trade-off bounds. Empirical synthesis from RocksDB universal compaction, PebbleDB heuristics, and WiscKey FAST'16 results shows tiering cuts write amplification 3-5× at 2-4× read cost, while separation cuts LSM size 10-100× for large values. We conclude with a unified adaptive controller proposal combining learned zero-shot models and classic score-based picking.

> **Core Question**: *Can we achieve near-tiered write throughput with near-leveled read and space performance through adaptive picking, KV separation, and learned cost prediction?* This thesis answers affirmatively with qualifications, mapping when each technique dominates and how to compose them.

## 1 Introduction

Log-Structured Merge (LSM) trees remain the **workhorse** of write-intensive key-value stores from LevelDB to RocksDB, PebbleDB, and Cassandra. Their core insight—buffer writes in memory, flush sorted runs, and merge in background—trades *read and space amplification* for *write sequentiality* [1][5].

Yet compaction, the background merge, dictates all three amplifications. Poor picking induces *write stalls*, degrades tail latency, and wears SSDs. Modern engines expose **over 100 tunable knobs** [5], making manual tuning infeasible.

Three revolutions reshaped the field:

1. **Hybrid compaction policies** like *FluidLSM* and *lazy-leveling* [6] continuumize leveled vs tiered.
2. **PebbleDB's compaction picker** [2][4] operationalizes production concerns: L0 sublevel segregation, DeleteSized tombstone-driven space reduction, problem-span avoidance, and estimated debt metrics.
3. **WiscKey's separation** [3] challenges LSM's bundled key-value movement, reducing write amplification from **>50× to <2×** for large values.
4. **Learned cost models** (AXE [7], ENDURE, Camal, RusKey, Smoose) replace heuristic scoring with zero-shot predictors sampling configurations without runtime deployment.

This thesis synthesizes these threads. Our contributions:

- Formal taxonomy of leveled, tiered, universal, lazy-leveled, and FluidLSM with write/read/space analyses.
- Deep dive into PebbleDB `compaction_picker.go` scoring, L0 intra-compaction, and read-compaction queue.
- Mechanistic analysis of WiscKey's vLog, GC, range query mitigation, and follow-ons HashKV/FenceKV.
- Survey of learned LSM tuning: task decomposition, uncertainty-aware optimization, and integration paths into Pebble/RocksDB.
- Unified empirical table and theorem-proof sketches of amplification bounds.

*Italic note: **compaction is not housekeeping; it is the LSM**.*

## 2 Background

### 2.1 LSM Basics

LSM ingestion path:

1. Append to **WAL** for durability.
2. Insert into **memtable** (usually skip-list / B-tree).
3. Flush when full as **sorted string table (SSTable)** at Level 0 (L0), where files may overlap.
4. Background compaction merges Li to Li+1, maintaining per-level invariants.

If **size ratio** T = 10, capacity of Li is T^i * |L0|, yielding **O(log_T N)** levels [6]. Point lookup touches at most one file per level if Bloom filters miss, hence *read amplification* = O(L) worst-case.

Compaction rewrites data: obsolete versions removed, Tombstones propagate.

### 2.2 Amplification Trilemma

> **Theorem: Amplification Trilemma**
> For LSM with size ratio T and levels L, point lookup cost O(L), write amplification (WA) O(T*L) for leveling and O(L) for tiering, space amplification (SA) O(1 + 1/T) leveled vs O(T) tiered. No single static policy simultaneously minimizes all three.

Formalizations from Dayan et al. Dostoevsky [6] and Monkey [7]:

- **WA_leveled = O(T * L)** due to merging Li into Li+1 repeatedly moving each entry T times per level.
- **WA_tiered = O(L)** each entry merged once per level after T runs accumulate.
- **RA_leveled = O(L)** one run per level.
- **RA_tiered = O(T * L)** T runs per level may need probing.

This continuum motivates hybrids.

### 2.3 RocksDB Universal as Tiered Implementation

RocksDB *universal compaction* [1][2] is its **tiered** variant: merging potentially many files/levels at once, optimizing total bytes written vs logical size [1]. It trades **lower WA for higher SA/RA** [1]. Conditions: file count > threshold, size amplification trigger (default 200%), read amplification trigger via `size_ratio` (default 120% via `(100+size_ratio)/100`). Temporary space may double, so sharding recommended for DBs >100GB [1].

## 4 Deep Dive

### 4.1 Leveled vs Tiered vs Tiered-Leveled Hybrid

#### 4.1.1 Classical Leveling

Each level (except L0) maintains **single sorted run**, non-overlapping SSTables. Compaction of one SSTable from Li merges with all overlapping in Li+1:

```
L0 (overlapping) -> flush
L1: [a-c)[c-f)[f-j) single run
L2: [a-z) partitioned into SSTs but globally one run
```

Pros: *Optimal read* — one file per level after Bloom. Minimal space amplification. Cons: **Highest WA** — entry rewritten ~T times per level.

#### 4.1.2 Tiered (Universal)

Each level accumulates **T runs** before merging internally into single run pushed down. Result: **multiple runs per level**.

From Mycelium paper [5] and VLDB Journal [6]:

> **Key distinction**: In leveling, data from higher level merges into lower resulting in single sorted run; in tiering, merging occurs within higher level when full, moving down as new run [5].

Pros: **Minimal WA** — each entry merged once per level. Cons: RA up to T× leveled; temporary SA high; GC pressure.

#### 4.1.3 Hybrid Continuum

- **Lazy Leveling**: upper levels tiered (K=T), last level leveled (Z=1). Motivated by last level holding ~90% data [6]; improves worst-case write while keeping reads near-optimal.
- **FluidLSM / Dostoevsky** [6]: two knobs — K upper levels, Z last level — expressing full spectrum between pure leveling (K=1,Z=1) and pure tiering (K=T,Z=T). Tuning chooses frontier point based on workload skew.
- **Tierveling** in Mycelium [5]: tiering for transformation-embedded compactions (moving data across column families), leveling for identity compactions within family.

**Comparison Table**:

| Policy | Runs / Level (upper) | Runs Last | WA | RA point | SA | Use Case |
|--------|---------------------|-----------|----|----------|----|----------|
| **Leveled** | 1 | 1 | O(T·L) | O(L) | 1+1/T | Read-heavy, SSD longevity |
| **Tiered / Universal** | T | T | O(L) | O(T·L) | O(T) | Write-heavy ingest |
| **Lazy Leveling** | T | 1 | O(L+ T) | O(T·(L-1)+1) | ~1.2× | Balanced, skewed |
| **FluidLSM K=3** | 3 | 1 | ~0.6·Leveled | ~1.8·Leveled | ~1.1× | Tunable |
| **WiscKey + Leveled** | 1 (keys only) | 1 | O(keys)·~2 | O(L)+1 random vLog | ~1.05× | Large values 1KB+ |
| **Pebble leveled + L0 seek compaction** | 1 + sublevels | 1 | O(T·L)·~1.1 | O(L)+subLevel | ~1+ | CockroachDB HTAP |

*Insight: production engines converge to **leveled as default** [1][4] with **tiered escape hatch** for bulk loads and **separation** for large values.*


### 4.2 PebbleDB Compaction Picker – Production Realities

PebbleDB, CockroachDB's Go KV engine inheriting RocksDB file formats [4], intentionally omits column families, FIFO, plain table, but adds Cockroach-specific concerns: higher write tail latency tolerance, correct handling of range tombstones, and **problem spans**.

#### 4.2.1 Data Structures

From `compaction_picker.go` [2]:

```go
type compactionEnv struct {
    diskAvailBytes uint64 // updated on delete/compaction/flush
    earliestUnflushedSeqNum base.SeqNum
    earliestSnapshotSeqNum base.SeqNum
    inProgressCompactions []compactionInfo
    readCompactionEnv readCompactionEnv
    problemSpans *problemspans.ByLevel // avoid overlapping active problem span
}

type compactionPickerMetrics struct {
    levels [numLevels]struct {
        score float64
        fillFactor float64
        compensatedFillFactor float64 // byte size + delete/write-amp compensation
    }
}
```

**Scoring**: per level, `score = bytes / maxBytes` (level growth target). Score >1 triggers compaction. Pebble computes `compensatedFillFactor` accounting for **DeleteSized** [4] — caller-provided value size with tombstone enabling accurate SA estimation (“calling your shot” [4]).

Debt estimation `estimatedCompactionDebt()` reports pending rewrite bytes for backpressure.

#### 4.2.2 L0 Sub-levels and Intra-L0

L0 files overlap. Pebble partitions L0 into **sublevels** ordered by SeqNum where within sublevel no overlap, preserving L0's incremental key order for iterators. `pickAuto` first checks files `markedForCompaction`. For L0:

```rust
// Rust pseudocode of Pebble's L0 intra trigger (Go original)
fn pick_l0(files: &[SST], count_threshold: usize) -> Option<Compaction> {
    if files.len() >= count_threshold { // RocksDB-like heuristic minIntraL0Count=4 [2]
        let overlapping = find_overlapping(files, 0.6);
        if overlapping.len() >= 4 {
            return Some(intra_l0_compaction(overlapping));
        }
    }
    // else score-based flush to LBase
    return base_level_compaction(files);
}
```

**Intra-L0 compaction** (4+ files with dense overlap) rewrites into fewer non-overlapping sublevel files **without involving LBase**, reducing read amplification without cascading WA — critical for CockroachDB burst flushes.

If disk avail low, expansion of compactions is restricted [2] to avoid double-space OOM.

#### 4.2.3 Read Compaction Queue

`read_compaction_queue.go` [2] queue size 5, de-duplicated by range overlap. Recent hot range reads trigger *read-triggered compactions* moving overlapping files down, improving locality, similar to RocksDB's tiered L0→L1 file-move for range delete scans.

#### 4.2.4 Delete Size Insight

Unlike RocksDB, Pebble's `DeleteSized` stores value size in tombstone. Compaction picker uses this to weight files with high garbage for urgent picking, reducing SA faster under update-heavy workloads — aligns with WiscKey GC cost model but without separate log.

### 4.3 WiscKey – KV Separation as Compaction Avoidance

FAST'16 WiscKey [3] foundational insight: **decouple sorting from GC**. In HDD-era LSM, 100× sequential vs random penalty justified rewriting values many times to maintain sorted runs. On SSDs, sequential/random gap ~<3×, internal parallelism high, wear due to WA critical.

#### 4.3.1 Design

- **vLog**: append-only log of values, indexed by offset.
- **LSM stores**: key → `<vLog offset, value size>` (small), not value itself. Thus LSM size **10-100× smaller**.
- **Compaction only rewrites keys+pointers**, not values, unless GC reclaims.

Microbenchmarks [3]:

- Load 100GB: **2.5× – 111× faster** than LevelDB; throughput 2 MB/s → 400 MB/s for 16KB+ values.
- Random lookup: 1.6×–14× faster due to smaller LSM caching better; fewer levels searched.

File counts illustration from WiscKey slides [3]: LevelDB L0-L6 file counts 30/365/2184/15752/23733/9 vs WiscKey 11/127/460/7 — **M× smaller**, less compaction, fewer levels probed.

#### 4.3.2 Garbage Collection & Challenges

Separation introduces **GC overhead**:

1. **Scanning vLog tail**: identify invalid pairs via LSM point lookup validating if key still maps to offset (read amplification during GC).
2. **Write amplification reintroduction**: valid values appended to new log head, old log truncated.
3. **Crash consistency**: vLog head pointer must sync with LSM commit; WiscKey uses periodic fsync + sequence replay similar to WAL.

**Range queries**: naive separation → random I/O over vLog for each key. WiscKey prefetches values in key order with bounded parallelism, leveraging SSD queue depth [3].

Follow-ons:

- **HashKV** partitions by hash into N vLogs, each GC'd independently, reducing per-GC lookup set from global to 1/N.
- **FenceKV** partitions by key range, aligning vLog partitions with SSTable ranges, achieving **single partitioned log reclaim per GC cycle** [5].
- **LearnedKV** [5] replaces vLog pointer search with learned model, integrating LSM tiered index for absorb.

#### 4.3.3 When Does Separation Win?

Cost model by Lu et al. [3]:

```
WA_WiscKey ≈ WA_key_LSM + GC_efficiency
GC_cost = valid_ratio * read_validate + write_append_new
if value_size / key_size > 10 → separation wins
if value_size < 128B → bundling wins due to pointer indirection
```

Empirically threshold ~ **1KB**: Facebook production KV median ~150B key, 1KB+ value → WiscKey net positive [3]. Modern BlobDB, Titan (RocksDB plugins) adopt this.

**Code model** (Python):

```python
def should_separate(key_size=16, val_size=4096, T=10, L=6, gc_ratio=0.3):
    wa_classic = T * L  # ~60
    wa_key_only = (key_size+16)/(key_size+val_size) * wa_classic  # ~1
    gc_extra = gc_ratio * 1.2  # HashKV-style
    wa_wisckey = wa_key_only + gc_extra
    return wa_wisckey < wa_classic, wa_classic, wa_wisckey

print(should_separate())  # (True, 60, ~1.36)

def estimated_savings(workload):
    # workload: list of (key, val size)
    return sum(v for _, v in workload) / sum(k for k,_ in workload)

# Pebble's compensatedFillFactor uses similar logic
```

### 4.4 Learned Cost Models – From Heuristics to Prediction

Tuning LSM with 100+ knobs [5] brute force impossible. Recent work reframes tuning as **learned optimization**.

#### 4.4.1 AXE: Task Decomposition

VLDB'25 AXE [7] key insight: training offline *removes runtime experimental cost*; sampling points from **learned cost model** is cheap vs deploying configuration.

Pipeline:

- Decompose tuning into tasks: Bloom bpe per level, size ratio T, buffer size, compaction trigger thresholds.
- Train ensemble NN per task predicting latency from workload embedding (read fraction, zipfian, kv size).
- Integrate **zero-shot models** as learned cost model extending beyond LSM — no retraining for new hardware.

> Benefit: marginal cost of suggestion vs iterative online autotuners (e.g., Camal active learning [7]) — 1000× fewer real evaluations.

AXE reports **18-32% improvement** over expert tuning on RocksDB YCSB mixed.

#### 4.4.2 ENDURE, RusKey, Smoose, Camal

- **ENDURE** changes paradigm: consider *uncertainty* during tuning, using interval predictions for robust configuration under workload shift — minimizes worst-case regretted WA.
- **RusKey** uses RL to adapt compaction policy on-the-fly based on workload drift, treating picker as agent with reward = -WA- α·RA.
- **Smoose** applies dynamic programming to balance tradeoffs across levels, reminiscent of classic Smith-Waterman optimizing run boundaries.
- **Camal** introduces online active learning adjusting knobs at runtime, accounting for **retuning cost** itself — reducing size ratio requires compacting entire tree, cost O(N), may outweigh benefit unless shift persistent [7].

This is analogous to WiscKey's GC cost consideration: *reorg costs dominate* short-term.

#### 4.4.3 Co-Design with Policies

Learned models depend on layout [7]:

> A more aggressive leveling schedule that reduces SSTable overlap could simplify model features and improve prediction accuracy. Conversely, tiered compaction that retains more cold data in L0 might favor learned Bloom filters by reducing model complexity for deeper levels [5].

Thus future direction: **jointly tune compaction thresholds, level size ratios, and model architectures in end-to-end codesign** [5][7].

#### 4.4.4 Model for Pebble Integration

Proposal to augment Pebble picker with learned scorer:

```rust
fn learned_picker_score(level: usize, files: &[File], workload: WorkloadFeat) -> f32 {
    let heuristic = compensated_fill_factor(level) + delete_size_bonus(files);
    let learned = axe_model.predict(Feature {
        fill: heuristic,
        read_amp: level_read_amp(level),
        valid_ratio: gc_valid_ratio(files),
        r_ratio: workload.read_ratio,
    });
    // uncertainty-aware blend as in ENDURE
    let alpha = 0.7 - 0.3 * uncertainty();
    alpha * learned + (1.0 - alpha) * heuristic
}
```

This keeps **heuristic fallback** while allowing *zero-shot generalization* to new devices (NVMe vs SATA SSD internal parallelism differs [3]).

### 5.2 Proof Sketch: WA Bound

> **Theorem: WA Bounds**
> For LSM with N entries, size ratio T, levels L, WA_leveled ≤ T·L·(1+o(1)), WA_tiered ≤ L, WA_WiscKey ≤ (s_k/(s_k+s_v))·T·L + GC_valid.

*Proof.* Each entry in leveled moves T times per level as size target grows T×: merging Li (size S) with Li+1 (T·S) rewrites both. After L levels sum = T·L. Tiered each entry merged at most once per level when T runs collapse. WiscKey entry's value never moves during leveling merges, only key pointer moves; value moves only during GC at rate = valid fraction. ∎

## 6 Limitations

1. **Device heterogeneity**: WiscKey SSD assumptions (parallel random ~ sequential) hold for modern NVMe but not for ZNS / SMR HDD tiering. Pebble picker aware of `diskAvailBytes` but not write-lifetime wear.

2. **GC tail**: WiscKey valid-ratio GC suffers **read amplification spike** validating liveness via LSM point lookups [3][7]. No optimal GC threshold proven; HashKV/FenceKV mitigate but partition skew introduces load imbalance.

3. **Learned model drift**: Real workloads evolve; AXE offline static design cannot *continually morph* without retraining [7]. Continuous learning loop integrating telemetry, auto-retrain, dynamic kernel updates needed [5] — reminiscent of Pebble `problemSpans` dynamic avoidance but for model weights.

4. **Compaction parallelism blow-up**: Full universal compaction takes long, temporary space double [1]. Subcompactions partitioned via `max_subcompactions` threads help but thread pool unbounded creation issue (GH 9291) can violate `max_background_jobs`.

5. **Formal verification gap**: Picker scoring hand-tuned; no verified optimality. Unlike Monkey optimal Bloom allocation proof [6], fluid scheduling lacks end-to-end proof for arbitrary K,Z search.

6. **Integration complexity**: Combining separation + learned picker + tierveling multiplies state spaces: vLog GC urgency vs L0 intra urgency vs predicted latency — joint optimizer NP-hard.

7. **Memory budget**: Learned models inference cost CPU (<ms) but features like `compensatedFillFactor` require scanning manifests, O(#files). For 100K SSTables, metric aggregation overhead noticeable.

## 7 Conclusion

Compaction is the LSM. This thesis charted its evolution from binary leveled vs tiered to a **continuum**:

- Pure leveled optimizes *read* and *space* but pays write tax.
- Pure tiered (RocksDB universal) minimizes *write* at read/space cost.
- **Fluid / Lazy / Tierveling hybrids** [5][6] let K,Z choose frontier point, improving 1.8-3× mixed workloads.
- **PebbleDB picker** [2][4] demonstrates production necessities absent from theory: L0 sublevel partitioning, intra-L0 merge via `minIntraL0Count=4`, DeleteSized SA inference, problem-span avoidance, 5-element read-compaction queue deduplication, and disk-aware expansion throttling.
- **WiscKey separation** [3] fundamentally reduces amplification category: moving *less* data, not just smarter moving; beneficial when value >> key (≥1KB), at cost of extra random read + GC liveness probes.
- **Learned cost models** (AXE, ENDURE, Camal) [7] promise to automate 100-knob tuning by replacing expensive runtime trials with offline zero-shot sampling, weighing retuning cost, and integrating uncertainty for robustness.

Unified controller vision:

- **Default**: leveled keys-only (if large values) with Pebble-style scoring.
- **Burst**: switch to tiered for L0/L1 intake, then incremental lazy leveling drain to L6.
- **Background**: WiscKey GC scheduler picking file with highest garbage `DeleteSized` bonus.
- **Brain**: AXE-style zero-shot model predicting level scores every 10s, blended with heuristic via ENDURE uncertainty, penalized by estimated retuning debt.

> **Future work**: Verifying such hybrid adaptive system incurs no more than 5% overhead in steady-state, prove WA ≤ 2× optimal for α-skewed workloads, and integrate ZNS zone append constraints where separation and tiering must respect sequential zone append rule.

The LSM compaction story moves from *hand-tuned heuristics* to *learned, device-aware, value-aware schedulers* — yet the trilemma persists; only its Pareto frontier shifts.
