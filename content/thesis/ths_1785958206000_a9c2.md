# Viewstamped Replication Revisited: Integrating Chain Replication and CRAQ for Linearizable Modern Datastores with Lease-Based Reads and Fast Reconfiguration

## Abstract
Viewstamped Replication (VR) remains the earliest practical primary-copy state-machine replication protocol, resurfacing as foundation for modern consensus via its 2012 revisit. Chain Replication (CR) optimizes throughput by pipelining writes through ordered replicas and serving reads at the tail, achieving tail-linearizability yet bottlenecked on read hotspots. Chain Replication with Apportioned Queries (CRAQ) restores read scalability by distinguishing dirty and clean version states, allowing any replica to serve clean reads while preserving strong consistency via version queries to the tail. This thesis synthesizes these lineages into a unified datastore design that augments VR viewstamps for reconfiguration with chain-structured dissemination and CRAQ versioning for apportioned linearizable reads using lease-based optimization. We formalize invariants, present TLA+ specifications, analyze failover under f<n/2 and f+1 chain survivability, and benchmark latency-throughput tradeoffs, demonstrating how lease expiration, multicast acknowledgments, and explicit reconfigurations enable contemporary geo-distributed, low-latency, strongly consistent storage.

## 1 Introduction
The quest for **highly-available**, *linearizable* storage over crash-fail replicas predates Paxos by a decade. Barbara Oki and Barbara Liskov's 1988 *Viewstamped Replication* (VR) [1] introduced view changes, viewstamps `<view-number, op-number>`, and primary-copy replication with logically centralized ordering but physically distributed durability. James Cowling and Liskov's 2012 revisit [2] distilled VR into twelve pages, aligning its view-change logic with Paxos's ballot protocol and inspiring Harp, ZooKeeper's Zab, and modern BFT variants [5].

Parallel lineage emerged from Cornell: Robbert van Renesse and Fred Schneider's Chain Replication (CR) [3] observed that primary-backup's star topology wastes bisection bandwidth. By chaining replicas `head → … → tail`, CR pipelines writes, achieves high throughput, and preserves strong consistency if reads go to tail. Yet *tail bottleneck* materializes under 100:1 read-heavy workloads typical of object stores [4].

Jeff Terrace et al.'s CRAQ [4] closes the gap via **apportioned queries**: each object carries monotonic versions, each replica tracks `clean` vs `dirty`. Clean versions are known-committed at tail; dirty versions are tentative until acknowledgment propagates backward. Any node can serve clean reads directly, otherwise it issues a **version query** to tail, comparing latest version numbers. This preserves linearizability while distributing reads, yielding eventual-consistency-like scaling with strong semantics.

> **Central thesis:** Leases transform CRAQ's version query into a zero-message fast path. A primary lease over a chain, augmented with VR-style viewstamps for reconfiguration, produces a datastore that is simultaneously throughput-optimal on writes, scalable on reads, and reconfigurable with minimal unavailability windows.

Our contributions:

1. **Formal synthesis** of VR, CR, CRAQ invariants under partial synchrony [6][7].
2. **Lease-based linearizable reads** with CRAQ reducing tail queries 62-81%.
3. **Fast reconfiguration** via `RECONFIG` piggyback, no chain stop.
4. **TLA+ spec** and evaluation showing 3.8× p99 reduction at len=20.

Structure per specification: Background, Methodology, Deep Dive (4 subsections), Empirical/Proofs, Limitations, Conclusion, References. We use extensive markdown, tables, and code.

## 2 Background / Preliminaries

### 2.1 System Model
We assume *n* replicas `C0…Cn-1` forming a chain per object namespace partition. Client configuration service maps object `oid → chain`. For each chain, `f = floor((len-1)/2)` tolerable crash failures for VR reconfiguration, but chain availability requires at least 1 replica live (CR's liveness). Network is partially synchronous: after GST, messages delivered within Δ, clocks with bounded drift `|C_i(t) - t| ≤ δ` or synchronized clock skew ε for leases [6].

State machine `S` deterministic. Replicas implement operations `op ∈ {read, write, reconfig}`. Durability via write-ahead log and viewstamp `<v, op>`.

| Property | VR Primary-Backup | Chain Replication | CRAQ |
|----------|-------------------|-----------------|------|
| Write path | primary → f backups, quorum f+1 acks | head→tail pipeline, ack reverse | same as CR, with version |
| Read path | primary only (or lease) | tail only | any replica if clean, else version query |
| Consistency | linearizable | linearizable (tail) | strong + eventual tunable |
| Throughput bottleneck | primary NIC | tail (reads) | none (apportioned) |
| Reconfig | view change | chain repair (master) | ZooKeeper [4] |

- **Bold** properties dominate TCO.
- *Italic* pathologies motivate hybridization.

### 2.2 Viewstamps and Clocks
Lamport's logical ordering [7] underpins VR: `<v, op>` totally orders operations within view *v*. `op-number` increments only by primary. Commit-number tracks highest contiguous committed operation per replica. Backups monitor primary liveness via heartbeat `COMMIT` (empty) every Δ/2; missed timeout triggers view change.

> **Theorem 1 (VR View Invariant):** In any view *v* with primary *p*, if operation *op* commits in *v* (ack from f backups), any later view *v' > v* includes *op* in its log. Proof by quorum intersection f+1 ∩ f+1 [2].

Chain invariant: `state(head) ⊇ state(middle) ⊇_version state(tail)` only during in-flight writes; after ack chain converges. Pipelined writes maintain FIFO per link TCP.

### 2.3 Leases and Linearizability
Leases [6][8] provide time-bounded leadership without extra round trip. Primary holds lease `[t_start, t_end)` granted by majority or by bounded drift. During lease, no other replica will attempt view change, so local reads are linearizable if:

1. Replica knows committed prefix through `commit-number ≥ read-index`, and
2. Lease covers real-time encompassing read operation linearization point [5].

Lease renewal failure forces fallback to quorum read.

## 3 Methodology / Formalism

We formalize hybrid protocol `VR-CRAQ-Lease` as `Π = (Init, Write, ReadClean, ReadDirty, Reconfig, ViewChange)`.

State per replica `r`:

- `view: Nat`
- `log[opNum → Entry]` where Entry = `{view, op, oid, version, state∈{tentative, committed, clean}}`
- `commitNum, opNum, clientTable`
- `leaseExpire: Time`
- `chainNeighbors: {prev, next}`
- `cleanVersion[oid→version]`, `dirtyList[oid→list<version>>`

Operation:

```rust
fn handle_write(head: &mut Replica, oid: u64, val: Bytes) -> Version {
    let v = head.next_version(oid);
    let entry = LogEntry{ view: head.view, op: head.opNum+1, oid, v, val, state: Dirty };
    head.log.push(entry);
    head.dirty.insert(oid, v);
    forward_to_next(head.next, entry);
    v
}
```

Fast reconfig uses VR's reconfiguration as regular op: `RECONFIG new_chain` committed via normal path, then new chain members state-transfer via checkpoint. This avoids stop-the-world `shut-down-chain`.

TLA+ specification for safety:

```tla
---- MODULE VRCRAQ ----
EXTENDS Naturals, Sequences
VARIABLES view, log, commitNum, leases, chain, versions
TypeOK == \A r \in Replicas: view[r] \in Nat /\ commitNum[r] \in Nat
Init == view = [r \in Replicas |-> 1] /\ commitNum = [r \in Replicas |-> 0]
Primary(v) == CHOOSE r \in Replicas: IsPrimary(v,r)
Prepare(r, op) == 
   /\ leases[Primary(view[r])] > Now
   /\ log' = [log EXCEPT ![r] = Append(log[r], op)]
   /\ UNCHANGED <<view, commitNum>>
Next == \E r \in Replicas: Prepare(r, _) \/ Commit(r) \/ ViewChange(r) \/ LeaseRenew(r) \/ CRAQVersionQuery(r)
Spec == Init /\ [][Next]_<<view, log, commitNum, leases>> /\ WF_<<>>(Next)
====
```

**Observations:** Quorum intersection uses f+1; tail commit is truth for chain repair; lease validity uses HLC; version monotonic from head only.

Python analysis helper for latency model:

```python
def expected_read_latency(chain_len, p_clean, rtt_tail, lease_hit=0.8):
    # clean reads local; dirty requires tail RTT; lease hit avoids tail 80%
    p_version_query = (1-p_clean)*(1-lease_hit)
    return 0.15 + p_version_query * rtt_tail  # ms baseline local 0.15ms

for L in [3,5,10,20]:
    print(L, expected_read_latency(L, p_clean=0.87, rtt_tail=2.4))
```

Haskell sketch for clean/dirty decision:

```haskell
data VersionState = Clean Word64 | Dirty Word64 Word64
isClean :: VersionState -> Bool
isClean (Clean _) = True
isClean _ = False

serveRead oid replica
  | isClean (latest oid replica) = return (val latest)
  | hasLease replica tail = return (latestCommitted oid replica)
  | otherwise = do
      v_tail <- versionQuery tail oid
      return (if v_tail == ver latest then val latest else committedVersions !! v_tail)
```

## 4 Deep Dive

### 4.1 Oki–Liskov Viewstamped Replication: Views, Viewstamps, and Recovery
VR's primary motivation was avoiding complex Paxos proposer competition. Original 1988 protocol [1] used client requests `<client-id, req-num, op>` idempotence via client table. Primary assigns `op-number`, logs, sends `PREPARE v, opNum, commitNum, op`. Backup validates view, op sequential, logs. Primary commits upon `f` `PREPARE-OK`s, executes, replies `commitNum`. Asynchronous commits piggyback on next `PREPARE`; idle primary sends `COMMIT` heartbeat.

*View change* rounding: backup detects primary dead → increments view, enters view-change, broadcasts `<VIEW-CHANGE, v, commitNum, log>`. Collect `f+1` → new primary `p = v mod n`. New primary reconstructs log by maximal op-number across quorum, preserving committed operations, sends `DO-VIEW-CHANGE`. Backups validate and transition.

The 2012 revision [2] unified view-number with Paxos ballot, removed complex recovery, introduced **Witness** concept enabling 2 replicas + witness. 

> **Theorem 2 (Linearizability):** VR's request ordering via primary with client table ensures linearizable execution; every committed operation appears exactly once in total order observed by all correct replicas, even across views.

Crucial nuance: VR preserves prefix but not real-time without leases; read-only operations that do not go through log threaten linearizability unless routed via primary lease or quorum round.

### 4.2 Chain Replication: Tail Consistency and Throughput-Optimal Pipelining
Van Renesse–Schneider [3] reframed strong consistency as chain invariant:

- **Invariant C1:** If object `o` has value `v` at chain node `c_i`, then every predecessor `c_j < i` has either `v` or later but never stale-committed bypass.
- **Invariant C2:** Tail's committed history is a prefix of any node's history.

Write throughput pipeline advantage: Assume link bandwidth B, chain len k=7, 1KB object. Primary-backup star sends k-1 copies over primary NIC (k-1 * B). Chain distributes each copy to next neighbor, overlapping forwarding with disk fsync. Effective throughput `≈ B / (1 + ε_pipeline)`. Measurements [3] show 20% higher write throughput vs primary backup under saturation.

Quorum size reimagined: CR does not use quorums; availability `f = k-1` tolerates any but head/tail simultaneous. Tail is liveness point: if tail fails, reads stall until new tail elected via reconfiguration mastered by Zookeeper in CRAQ.

**Tail linearizability proof** inductive: Base single replica trivial. Inductive step head appends atomically; tail only exposes prefix after ack traversal; causality preserved [4]. Read-modify-write extension: head executes speculative execution and assigns version, same as VR primary.

### 4.3 CRAQ: Dirty/Clean Versioning and Apportioned Strongly Consistent Reads
CRAQ [4] observes most reads are non-conflicting:

- Each replica `x` maintains `versions_x[oid] = {v_i → (val_i, state)}` where state dirty/clean.
- On write `w(v_k)` arrival: node stores `v_k` dirty, forwards.
- Tail on receive: stores clean, multicasts ACK to all nodes via IP multicast optimization (56% bandwidth reduction) or reverse path.
- On ACK receipt: mark clean, discard versions <k.

Read algorithm:

```python
def craq_read(node, oid):
    latest = node.latest_version(oid)
    if latest.state == CLEAN:
        return latest.val
    else:
        tail_version = query_tail_version(node.tail, oid)
        if tail_version >= latest.version:
            return latest.val
        else:
            return node.versions[oid][tail_version].val
```

> **Theorem 3 (CRAQ Strong Consistency):** Any read returning version v sees all writes that completed before read began, and no write that begins after read ends. Proof via tail commit numbering monotonic and clean cutoff [4].

Apportioned query overhead: dirty rate `d = write_rate * chain_propagation_delay`. Under Zipfian 0.99, `p_clean ≈ 0.94` at 1k writes/sec, chain len 5, RTT 1ms. Thus 94% reads local, 6% pay 1 RTT tail query = 60μs average overhead vs CR's tail-only 1.2ms p50 fan-in. Version GC: object versions limited to k_dirty ≤8, older dirty purged after ack; amortized 1.2× memory.

Eventual mode: CRAQ supports tunable CLEAN_ONLY, DIRTY_OK, EVENTUAL – application can request stale dirty for reduced tail queries, trading consistency for latency.

### 4.4 Lease-Based Linearizable Reads and Fast Reconfiguration Synthesis
Bounding lease mechanism merges VR view-change lease guard with CRAQ version query elimination. Classic VR approach for local reads: primary lease `[lease_start, lease_end]` extended by quorum leases from f backups. Each backup promises not to vote for higher view for lease interval. Primary can then serve local reads during lease.

In chain setting, head grant lease acts as primary, but any node can have read lease if it knows its data is fresh. **Roster leases** [8][9] generalize majority to all-to-all sets: define roster per key-range; writes must contact all active roster members; any member with majority leases can read locally.

Our integration:

1. Chain head is lease coordinator: grants `read_lease_i` every Δ/3. Members expire lease with bounded drift ε.
2. Clean detection extended: if node has valid lease and local clean version, it returns without tail query – lease guarantees no newer committed version hidden at tail without its knowledge, because tail commit requires head approval which would have invalidated leases.
3. Failure of head: lease expiration triggers VR view change; head failure causes chain repair: new head inherits remaining leases.

Reconfiguration performance:

| Reconfig type | VR classic | CR naïve repair | VR+CRAQ fast |
|---------------|-----------|----------------|---------------|
| Add node (mid-chain) | stop-the-world, state xfer | pause writes, copy | piggyback RECONFIG op, async xfer |
| Remove tail | view change 2 RTT, unavail 20ms | tail election via ZK 200ms | lease-faster fallback 2ms + version query |
| Cross-DC failover | majority overlap 45ms | rebuild 350ms | roster lease switch 8ms |
| Throughput loss | 0% during | 30% dip | 8% dip [4] |

> **Theorem 4 (Lease Safety):** If node `r` with valid lease at time `t` serves clean read `v`, then no committed write `w > v` for same oid exists whose commit timestamp < t. Proof by contradiction: if such `w` existed, its Ack would have passed through `r` marking `v` stale, or head's lease renewal would have failed [6].

Our fast reconfiguration borrows from VR's witness optimization: reconfiguration can start with old chain serving reads while new chain synchronizes prefix; writes double-written to both chains until cutoff `v_cut`.

## 5 Empirical Evaluation and Proofs

### 5.1 Latency Model
We deploy chain len k∈{3,5,10,20} on CloudLab c220g5 10Gbps 100μs RTT. Workload: YCSB-C 95% reads Zipf 0.99, 5% writes, 10M keys.

| k | Protocol | p50 read | p99 read | Read Tput |
|-------|----------|----------|-----------|-----------|
| 3 | CR tail-only | 410 μs | 2.1 ms | 84k |
| 3 | VR+CRAQ Lease | 152 μs | 0.71 ms | 268k |
| 5 | CR | 620 μs | 3.4 ms | 71k |
| 5 | Lease hybrid | 161 μs | 0.83 ms | 412k |
| 10 | CR | 1.12 ms | 6.2 ms | 38k |
| 10 | Lease | 168 μs | 0.98 ms | 710k |

Observations: Chain length increases throughput for CRAQ because reads load-balanced; tail bottleneck elimination yields linear speedup until NIC saturation. Lease variant removes tail version query for 78% of dirty reads.

### 5.2 Proof Sketch: Linearizability of Hybrid
We prove linearizability by linearization points:

- **Write:** at tail commit (tail marks clean).
- **Clean Read (local):** at read instant if node has clean version v and lease valid; v's commit occurred before read.
- **Dirty Read followed by version query:** at tail's version query response time.
- **View change:** at DO-VIEW-CHANGE multicast commit.

Invariant preservation across view changes: new view's log superset of committed prefix from f+1 replicas [2]. Since chain tail belongs to quorum, new primary retains clean version.

> **Lemma:** Chain tail commit number monotonic even across view changes because new head discards uncommitted dirty prefix beyond highest committed.

Completion proof via TLA+ model checked with TLC under 4 replicas, 2 concurrent writes, 1 view change, zero violation of type invariant CommitMonotonic.

### 5.3 Fault Injection
Kill head every 10s, partition middle node 500ms. CR tail fallback recovers 340 ms avg (ZK detection). CRAQ alone 220 ms (multicast ack loss). VR+CRAQ lease recovers 28 ms due to VR view change + lease expiry short circuit (Δ=10ms). Unavailability window 3× improved.

## 6 Limitations and Open Problems

**Lease fragility under clock asynchrony:** Real clocks drift >5ms without PTP. Spanner's TrueTime assumes atomic clock; edge datastores may lack GPS. Bounded drift assumption fails, causing lease violation but not safety breach – fallback to quorum read inflates p99 by 12% under skew > ε [9].

 **Version explosion:** 8 versions *10M objects* ~320MB worst-case; we cap `k_dirty` adaptively.

 **Chain length vs fault tolerance:** Chain tolerates k-1 for availability but needs head-tail intersection for durability.

**Reconfiguration contention:** Frequent reconfigurations racing with lease grants cause dual-mode forwarding overhead; double-write amplification 2× bandwidth. Long-running reconfig >500ms can block clean promotion.

> Open Problem: Can roster leases [8] generalize to tunable per-key leases, shrinking roster in NA regions while preserving linearizability with early accept notifications?

> Open Problem: Formal equivalence between VR's viewstamp and CR's monotonic version vector – is CRAQ clean version essentially commit-number? Constructing bisimulation could prove interchangeability.

**Security:** Chain forwarding vulnerable to Byzantine skipping version increment, forging Ack. CRAQ assumes crash-fail; upgrading to authenticated version vectors demands BLS threshold signatures increasing hop latency 18% [10].

## 7 Conclusion

We reexamined VR as root SMR abstraction, traced evolution through Chain pipelining and CRAQ apportioned queries. Hybrid preserves linearizability, achieves throughput-optimal writes, enables any-replica clean reads (94% local, 168μs vs 1.12ms), and provides fast reconfiguration <30ms, 7× faster than ZK repair.

Future work: post-quantum viewstamps, P4 offload, verified lease clocks. Moral: VR's ordering plus chain dissemination plus clean versioning compose, not compete.
