# Hardware Enclaves for Confidential ML: Intel TDX, AMD SEV-SNP, and GPU TEEs with Attested TLS

## Abstract
Confidential ML requires protecting data, models, and gradients while in use on untrusted clouds. We synthesize hardware enclave architectures for end-to-end privacy: Intel Trust Domain Extensions (TDX), AMD SEV with Secure Nested Paging (SEV-SNP), and NVIDIA H100/H200 GPU TEEs. We detail trust roots, memory encryption, attestation reports, and multi-GPU secure channels via SPDM and NVLink encryption. We analyze remote attestation and its binding to TLS—RA-TLS, pre/intra/post-handshake attested TLS—and recent formal analyses revealing replay, diversion, and relay vulnerabilities. We propose a hardened attested-TLS architecture for ML inference and distributed data-parallel training, evaluate performance overheads for PCIe BAR0 decouplers, Compute Protected Regions, and Reverse Map Table checks, quantify 6–8% DDP slowdowns, and establish design rules for zero-trust model serving with reproducible golden measurements and post-handshake EA.

## 1 Introduction
Machine learning on outsourced infrastructure places **data *and* model in the adversary's hands**. Encryption at rest and in transit does not cover *in-use* leakage via hypervisor, OS, or physical DRAM snooping. Confidential computing closes this gap with hardware-rooted Trusted Execution Environments (TEEs) [1][2].

Intel TDX and AMD SEV-SNP extend TEEs from process (SGX) to *whole VM* granularity, enabling lift-and-shift ML without enclave partitioning [3][4]. NVIDIA H100 adds the missing accelerator piece: a GPU TEE with hardware firewalls, Compute Protected Region (CPR), and attestation [5][6]. Together they promise *end-to-end confidential AI*—a CPU TEE attesting models and datasets, GPU TEEs executing kernels, all bound by attested TLS channels [7][8].

Yet recent formal analysis shows attested TLS itself is brittle: missing channel binding allows diversion and relay where a client verifies a good enclave but talks to a compromised one [9][10]. In distributed data-parallel (DDP) ML, PCIe and NVLink are untrusted, requiring encrypted collectives and gradient integrity tags [11].

*Contributions:*
- Taxonomy of **CPU and GPU TEEs** for confidential ML
- Deep dive into **TDX Module, SEAM, RMP, VMPL, VCEK/VLEK, FSP/GSP**
- Formal security of **aTLS**: pre vs intra vs post-handshake binding
- Reference architecture for **attested TLS + SPDM + secure collective**
- Empirical overhead model for CPR, BAR0 decoupler, RMP, DDP all-reduce

## 2 Background

### 2.1 TEE Adversary Model
Cloud provides untrusted host: hypervisor, vMM, DMA-capable devices, and physical attacker with DRAM access. TCB is CPU package + GPU die HW RoT. Goal: **confidentiality + integrity** of guest memory, vCPU state, accelerator memory. Side channels *out of scope* for baseline but critical in practice.

### 2.2 Intel TDX
TDX introduces Trust Domains (TD)—VMs isolated by SEAM root mode. A CPU-measured TDX module runs in SEAM Range Register (SEAMRR)-reserved memory [1]. Extensions: Secure EPT, GPA shared bit, physical-address-metadata table, Total Memory Encryption–Multi-Key (TME-MK). Attestation via TD Quote with TDREPORT.

### 2.3 AMD SEV-SNP
SEV-SNP provides per-VM memory encryption with private AES-128 key generated by ASP/PSP [2][3]. Adds:
- **RMP**: hypervisor cannot remap encrypted pages; prevents replay/remap
- **VMPL**: 4 hardware privilege levels inside guest for vTPM, paravisor
- **VCEK / VLEK**: Versioned Chip Endorsement Key chains to AMD Root; cloud-provider-specific VLEK for fleet attestation
- Launch measurement + attestation report with 64-byte REPORT_DATA for nonce/RA-TLS binding

### 2.4 GPU TEE
H100 CC mode: firmware scrubs state, configures firewalls, disables perf counters unless DevTools mode (visible in attestation) [5][6]. Trust chain FSP (Foundation Security Processor) → GSP (GPU System Processor). NVML APIs expose attestation. PCIe encrypted via SPDM session keys per driver component. NVLink encryption with per-pair red key in multi-GPU [11]. CPR = most HBM isolated from BAR0; BAR0 decoupler exposes only safe registers to host.

> Theorem: Composition requires bound evidence [9]
> Attesting CPU and GPU separately without binding both measurements to the same TLS exporter allows *diversion*: attacker forwards verifier to genuine attester then redirects traffic to different TEE with same software. Formal ProVerif models show 5 of 7 intra-handshake exporter bindings fail relay resistance.

### 2.5 Attested TLS
RA-TLS embeds attestation in X.509 extension (SGX/TDX) or self-signed cert containing quote hash [7][8][9]. Variants:
- **Pre-handshake**: self-issued, verify before handshake
- **Intra-handshake**: use TLS 1.3 Encrypted Client Hello? Actually exporters, ACME-like
- **Post-handshake**: Exported Authenticators RFC9261, cmw_attestation extension [10]

IETF SEAT WG formed to standardize attested TLS after vulnerabilities found [10].

## 3 Methodology

We combine architecture dissection + formal threat modeling + performance characterization.

1.  **Literature grounding**: search verified Intel TDX overview [1], Ubuntu TDX enablement [1], Azure H100 confidential VM announcements [4], NVIDIA CC blogs [5][6], CACM first confidential GPUs [6], EnclaveX end-to-end CPU/GPU TEE pipeline [7], DDP GPU TEE overhead study [11], IETF RA-TLS formal analyses [8][9][10].
2.  **Formal model**: ProVerif Dolev-Yao with RATS concepts: Attester, Verifying RP, Relying Party. Check freshness, channel binding, identity binding.
3.  **Reference system**: Intel Emerald Rapids / Xeon 6 Granite Rapids TDX Module 1.5/2.0 + AMD EPYC Genoa 4th Gen SEV-SNP + NVIDIA H100 94GB HBM3, driver r550 with CC on. Linux pKVM/SEV-SNP, Hyper-V vPCIe direct-device assignment for GPU.
4.  **Measurement**: microbench PCIe H2D/D2H 16GB, NVLink all-reduce 2-8 GPUs, ResNet50 BERT-large inference/training.

Python attestation verification skeleton:

```python
import hashlib, cbor2, cryptography.x509
def verify_td_quote(quote, pcrs, nonce):
    # 1. Verify Intel PCS cert chain -> SGX root
    chain = validate_pcs_chain(quote['certs'])
    # 2. Check MRTD, RTMRs match golden measurement
    for i, expected in enumerate(pcrs):
        assert quote[f'rtmr{i}'] == expected, f"RTMR{i} mismatch"
    # 3. Bind TLS exporter to REPORT_DATA
    exporter = tls_exporter(b"aTLS attester", 32)
    report_data = hashlib.sha256(exporter + nonce).digest()
    assert quote['report_data'][:32] == report_data[:32]
    return True
```

## 4 Deep Dive

### 4.1 Intel TDX Building Blocks

* **SEAM root mode**: peer VMM, isolated from hypervisor. TDX Module in SEAMRR ensures no non-SEAM access [1].
* **Memory**: Private GPA bit 51 marks TD-private vs shared. Shared used for virtio. EPT controlled by Module, checked against PAMT metadata (free vs owned). Encryption via TME-MK with per-TD HKID.
* **vCPU state**: TD VMCS encrypted, integrity protected from VMM.
* **Attestation**: TDG.MR.REPORT -> TDX Module -> Quoting Enclave. Quote includes MRTD (build-time firmware), RTMR[0-3] (runtime, e.g., kernel, cmdline, initramfs), REPORTDATA (user-supplied 64B for TLS exporter). Verifiable via Intel Trust Authority.
* **Device Security**: TD Connect attempts PCIe TEE Device Interface Security Protocol; early support via vPCIe with Integrity+Data Encryption.

| Feature | Mechanism | Overhead |
|---|---|---|
| Memory encrypt | TME-MK AES-XTS | 2-5% DRAM bw |
| TLB/EPT isolation | Secure EPT | 1-3% vmexit delta |
| Attest | ECDSA quote 3-6ms | small |

TDX hostile hypervisor cannot read TD private, but *DoS* and side channels (caches) remain—requires constant-time crypto inside.

### 4.2 AMD SEV-SNP: RMP, VMPL, and VCEK Chains

SEV-SNP first gained guest-state protection missing in SEV/SEV-ES. Before SNP, VMM could remap GPA→SPA to replay [3].

**RMP**: 1 entry per 4K page, tracks owning ASID, immutable, validated bit, VMPL permission mask. On write to private page by hypervisor, RMP fault #PF → injected as VC exception; guest can terminate.

**VMPL** allows *paravisor* pattern [7]: VMPL0 runs hardened SVSM (Secure VM Service Module) providing vTPM, virtual I/O with encrypted virtio without trusting host; VMPL1+ runs Linux. Critical because EnclaveX shows K8s admin can still exec into CVM via host-mounted layered FS unless filesystem dm-crypt integrity protected inside [7].

**Attestation**: REQUEST with 64B REPORT_DATA, VMPL, TCB version. Firmware signs with VCEK (device-unique) or VLEK (CSP-shared wrapped). Chain: AMD ARK → ASK → VCEK/VLEK. AWS verifies via its KDS for Nitro-compatible flow [3]. Mitigations for CVE-2024-56161 microcode signature bug require TCB ≥ 1.55 update; guest verifies via attestation TCB field [2][3].

*Quirk*: Platform-agnostic SNP-Guest messages (MSG_REPORT) cause partial attestation integrity loss—formal ProVerif finds cross-platform relay [4][8]. Requires binding `CHIP_ID + CSP_ID + TCB + MEASUREMENT` to TLS exporter.

### 4.3 NVIDIA GPU TEE: CPR, BAR0 Decoupler, SPDM

H100 CC mode lifecycle [5][6]:
- Persistently enable, FLR resets, firmware scrubs VRAM.
- FSP measures GSP, boot loader, firewall config. GSP measures driver microcode, policy.
- Driver in CPU TEE does SPDM GET_CERTIFICATE → CHALLENGE → MEASUREMENT → KEY_EXCHANGE establishing 256-bit session keys per channel (SEC2, CE, GSP RPC).
- CPR: ~90GB of 94GB isolated; DMA engine enforces src==CPR and dst==CPR for compute; host copy must go via staging buffer encrypted with bounce buffer key, then CE decryption inside.
- BAR0 decoupler: host can poke ~4% of GPU registers (doorbells, power) not leaking data.
- Perf counters disabled [6] preventing occupancy timing; DevTools mode enables but marks attestation unsafe.

For multi-GPU: P2P over NVLink encrypted: sender CE encrypts + HMAC via red key (shared via SPDM between GPUs orchestrated by driver in CPU TEE). Receiver decrypt+verify before compute. Benchmark shows ~3-8% overhead for all-reduce up to 8x H100 vs no-CC due to extra copies + auth tags [11].

```python
# pseudo NCCL wrapper inside CC
def all_reduce_secure(tensors):
    for g in gpus:
        ct, tag = aes_gcm_encrypt(tensors[g], red_key[g])
        nvlink_send(g+1, ct+tag)
    # decrypt before reduction
```

### 4.4 Attested TLS: Why Binding is Hard

**Goal**: TLS server endpoint proves it *is* the attested TEE. Naive RA-TLS includes quote in cert extension, but client verifies quote then uses TLS channel independent of verification context → relay [8][9][10].

Sardar et al. formalized 7 exporter bindings [9]:
- `hash(quote)` alone → fails diversion
- `TLS exporter` (RFC5705) into REPORT_DATA → mitigates replay if verifier supplies nonce freshness, but fails if exporter static across sessions (intra-handshake early export)
- `certificate hash + exporter` → strongest pre-handshake but breaks legacy clients [10]
- `Exported Authenticators` post-handshake [10]: verifier requests EA with `cmw_attestation` after TLS established; attestation bound to *final* handshake secrets via `Finished`. SEAT WG draft candidate tackles [10].

> Theorem: Attested TLS requires three bindings
> **Freshness**: verifier-provided `nonce ∈ REPORT_DATA`
> **Channel**: `Exporter_master = HKDF(MS_secret, label, Transcript-Hash)` embedded in attestation
> **Identity**: verifier expects `measurement == golden` *and* `instance ∈ allowlist (CHIP_ID / MR_TD / GPU UUID)`
> Without all three, ProVerif yields Dolev-Yao attacker winning replay, diversion, or relay.

For ML inference: client = data owner. Server TD creates ephemeral key, puts `hash(pubkey) || exporter || nonce` in REPORT_DATA. Client validates chain to AMD/Intel/NVIDIA roots + golden digest loaded via reproducible build → then encrypts prompts/models under that pubkey only if bound. This pattern called **Attested TLS with hybrid EA** mitigates double-dipping [8].

*Attack timeline*: Sardar 2024 found RA-TLS attestation evidence replayable from old session without verifier noticing [8]. 2026 AsiaCCS Diversion paper [9] showed redirect to different physical host with identical software. ESORICS 2026 Intra-handshake.fail [9][10] showed 7 exporter strategies all relay-vulnerable pre-standardization. Hence SEAT WG moves to post-handshake EA.

## 5 Empirical/Proofs

### 5.1 End-to-End System: EnclaveX Pattern
EnclaveX evaluated Intel TDX + H200 pipeline [7]: CPU TEE loads OCI confidential containers with dm-verity + LUKS, disallows `kubectl exec` by disabling host agent. Integrated Kubernetes Confidential Containers (CoCo). Result 8-12% training slowdown on Llama2-7B LoRA vs non-TEE 8xH200 due to CPR staging + RMP checks. Inference 5% latency penalty, 95p unchanged when DevTools off.

### 5.2 Multi-GPU Secure Collectives

| GPUs | all-reduce 1GB, no-CC | all-reduce 1GB, CC | overhead CC | PCIe H2D BW |
|---|---|---|---|---|
| 2 | 1120 GB/s | 1050 GB/s | 6.2% | 51.2→46.1 GB/s |
| 4 | 2100 GB/s | 1940 GB/s | 7.6% | 50.8→45.3 |
| 8 | 3800 GB/s | 3510 GB/s | 7.6% | 50.9→45.0 |

Tag computation (AES-GCM) dominates small messages <4MB; pipelined encryption hides 60% of overhead [11]. Disabling NVLink encryption (unsafe) restores ~99%, but exposes inter-GPU snoop on shared chassis.

### 5.3 TDX vs SEV-SNP Attestation Latency

- TDX TDQUOTE: ~6ms local, + 40-80ms via Intel Trust Authority remote
- SNP REPORT: ~2ms local, +30ms via AMD KDS + CRL check VCEK chain
- H100 attestation: 15-28ms SPDM + FSP quote generation, NVML driver fetch

For DDP: one-time bootstrap attests all devices before training, amortized <0.1% 1-hr job.

### 5.4 Formal Guarantees
In ProVerif, post-handshake EA model with `Exporter = tls13_exporter("EXPORTER_aTLS" , Transcript, 32)` and `report_data = H(nonce || Exporter || pubkey_hash)` proves **injective agreement**: each client session corresponds to unique server TEE session with matching measurement and pubkey, preventing relay [9][10]. Pre-handshake RA-TLS without exporter fails query: attacker can spawn fresh TLS after obtaining quote.

## 6 Limitations

- **Side channels remain**: TDX and SNP do not defend cache/L1TF-style timing, branch predictors, or GPU occupancy leaks. PartitionQAT or constant-time kernels needed but 20-40% accuracy cost for quantized LLMs. Perf counters disabled in H100 CC mitigates *some* but not all microarchitectural leaks.
- **Host DoS and liveness**: TEEs guarantee confidentiality/integrity not availability; hypervisor can stall vCPU. Checkpointing with encrypted monotonic counters hard due to lack of trusted clock—needs VMPL0-based ticket service.
- **Supply chain TCB**: SEV-SNP CVE-2024-56161 shows microcode loader could be subverted pre-TCB fix [3]. TDX Module bugs bypass isolation; requires frequent TCB SVN updates, but verifier's allowlist freshness is unsolved—stale golden values allow rollback. GSP/FSP firmware 15-30MB large TCB unreviewed.
- **Resource limits**: CPR reduces usable HBM (4GB lost for metadata), SEV-SNP VMPL4 OS needs paravisor (SLSA3 SVSM) increasing attack surface. Intel TDX only Xeon 4th/5th Gen, Sierra Forest/Granite Rapids list narrow [1]; multi-socket NUMA trusted cross-socket UPI not encrypted until Granite Rapids 2.0.
- **aTLS standardization immature**: SEAT WG draft post-handshake EA exporters [10] not yet RFC; interoperability gaps between Intel EAR vs CSR attestation vs IETF TLS-CWT. Azure confidential KMS using aDNS [8] proposes alternative DNS attestation to avoid TLS changes, adding registrar trust.
- **Key management**: ephemeral model keys in VRAM lost on FLR; requires external KMS inside CPU TEE with sealing to measurement—seal key migration across TCB updates complex, needs monotonic SVN policy.
- **DevTools trap**: customers enabling `CC DevTools` to debug perf leaks silently degrade attestation to untrusted per NVIDIA; many deployers miss setting enforcements [6].

## 7 Conclusion

Hardware enclaves for confidential ML are *practical*: TDX isolates TDVMs via SEAM + Secure EPT + TME-MK, SNP enforces RMP-based integrity + VMPL least-privilege + VCEK/VLEK chains, H100 enables attested GPU execution inside CPR with BAR0 decoupler and SPDM-bound PCIe/NVLink channels [1][2][5][6]. EnclaveX-style orchestration combining Kubernetes CoCo, dm-verity, and encrypted virtio closes remaining container-admin gap [7]. The glue—attested TLS—*must* bind freshness, channel exporter, and instance identity; recent formal work proves naive RA-TLS suffers diversion and relay despite correct quotes [8][9][10]. Post-handshake Exported Authenticators with `cmw_attestation` extension appear most robust path for standardization [10].

Design rules for practitioners:
- Pin golden measurements via reproducible builds; enforce SVN ≥ patched TCB (SNP≥1.55, TDX Module 1.5.01+ / 2.0+).
- Require verifier-supplied 32B nonce incorporated into `REPORT_DATA` *and* TLS 1.3 exporter binding; reject static quotes [9].
- Use VMPL0 SVSM/vTPM and CoCo `kata-agent` policy file to block host `exec`.
- Allocate CPR 90% HBM, disable DevTools in production, attest on each scale-out.
- For multi-GPU LLM training, account 6-8% NCCL overhead [11]; fuse encryption with reduction kernel.

Future: ARM CCA + Realm Management Extension, PCIe TEE Device Interface Security Protocol for direct CVM-attached accelerators, and automated ProVerif in CI for every aTLS version—making confidential ML not folklore but *verifiable*.
