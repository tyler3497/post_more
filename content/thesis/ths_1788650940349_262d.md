# Differential Fuzzing of Database Engines: SQLancer TLP, Query Plan Equivalence Oracles, and Logic Bug Detection at Scale

## Abstract

Database management systems are among the most heavily tested software artifacts in existence, yet they continue to harbor *logic bugs* — defects that silently return incorrect query results rather than crashing. Because the SQL standard under-specifies edge semantics (three-valued logic, implicit type coercion, collation order) and because any given query may execute correctly while a semantically equivalent rewriting does not, classical crash-oriented fuzzing cannot detect this class of defect. This thesis presents a comprehensive treatment of differential and metamorphic oracles for relational database engines, centered on the open-source SQLancer framework and its principal test oracles: Non-Optimizing Reference Engine Construction (NoREC), Ternary Logic Partitioning (TLP), and Pivoted Query Synthesis (PQS). We formalize these oracles as metamorphic relations over SQL query space, analyze their soundness conditions, extend the discussion to query-plan equivalence oracles including Query Plan Guidance (QPG) and multi-plan execution, and review the empirical record — over 450 confirmed logic bugs across SQLite, PostgreSQL, MySQL, MariaDB, TiDB, and CockroachDB reported through SQLancer and its descendants. We close by identifying fundamental limitations, including self-consistent oracle blind spots and the dialect-generator scaling bottleneck, and outline SQLancer++'s adaptive generation architecture as the path toward universal DBMS testing.

## 1 Introduction

The relational database engine is arguably the most consequential artifact of applied computer science: trillions of dollars of economic activity flow through query planners and storage engines whose correctness is taken on faith. A single silently wrong answer — a dropped row, a miscounted aggregate, a join that misses a match — can propagate through business logic undetected for months. These are *logic bugs*, and they differ from memory-safety crashes in one decisive respect: there is no observable signal that anything went wrong. The process exits cleanly, the connection stays open, and the result set arrives with full confidence and partial truth [4].

The *test oracle problem* is the central difficulty. For a crash, the oracle is trivial: did the process die? For a logic bug, the oracle must answer the question "is this result set correct?" for an arbitrary SQL query against an arbitrary database state — a question that in general requires an independent, trusted implementation of SQL semantics. Differential testing against a second engine is the classical answer, but it suffers from two deep problems. First, SQL dialects differ in semantics and supported features, so expected discrepancies produce false positives. Second, when two engines share an implementation lineage, they may agree on the *wrong* answer, and the bug escapes [5].

The research program that began with SQLancer takes a different route: instead of comparing two engines, it compares *one engine against itself*, using semantically constrained query transformations whose expected relationships are known a priori. These are *metamorphic oracles* — instances of metamorphic testing applied to SQL. The two most influential are NoREC and TLP, both implemented in SQLancer and both responsible for hundreds of confirmed bugs in production database systems [1][2].

> **Theorem:** *A metamorphic oracle for SQL is sound with respect to a formal semantics Σ iff the transformation T preserves the query's denotation under Σ for all database states. Every confirmed logic bug found by such an oracle is either a genuine engine defect or a defect in the oracle's model of Σ.*

This central observation frames the entire field: all differential fuzzing of database engines is a negotiation between the oracle's model of SQL semantics and the engine's actual behavior.

## 2 Background

### 2.1 SQL semantics and the oracle problem

SQL is a declarative language whose semantics are defined, at best, loosely. The SQL standard leaves significant latitude in evaluation order, NULL handling, implicit type conversion, and floating-point aggregation. A *logic bug* is conventionally defined as a defect in which the DBMS returns an incorrect result without any error signal — in contrast to crashes, assertion failures, and hangs. The canonical taxonomy, following Rigger and Su, distinguishes:

- **Optimization bugs**: incorrect results produced only when the query optimizer is enabled; disabling optimizations yields the correct answer.
- **Logic bugs (general)**: incorrect results regardless of optimization, often in the executor, type system, or index access paths.
- **Crash bugs**: segmentation faults, aborts, and stack overflows — easily detected but less interesting precisely because they are self-reporting.

Traditional DBMS fuzzers such as SQLsmith generate syntactically valid queries and watch for crashes. This leaves the far more dangerous logic-bug class entirely unaddressed, motivating *semantic* oracles.

### 2.2 Differential and metamorphic testing

*Differential testing* runs the same input on two or more implementations and flags disagreements [5]. *Metamorphic testing* generalizes this: given a source input and a metamorphic relation — a known relationship between the outputs of the source and a transformed (follow-up) input — the oracle checks whether the relation holds, without requiring ground truth. Query Partitioning [2] is the database instance of this idea:

> **Lemma:** *If Q₁, Q₂, Q₃ partition the result of Q under a metamorphic relation R, then compose(R(Q₁), R(Q₂), R(Q₃)) must equal R(Q) in any correct engine; violations localize a defect to the execution of at least one of the four queries.*

The beauty of the approach is that the engine under test serves as its own reference implementation: the "reference" query deliberately avoids the code paths (optimizations, indexes, partition pruning) suspected of harboring the bug.

### 2.3 The SQLancer ecosystem

SQLancer is a Java-based automated testing tool implementing these oracles across multiple DBMSs, with per-dialect SQL generators. Its design separates three concerns: a *schema and database generator* (random DDL/DML producing tables, indexes, views, and data), a *query generator* (rule-based random SQL conforming to the target dialect's grammar), and a *test oracle* (NoREC, TLP, or PQS) that validates result sets. To date, SQLancer has found over 450 unique previously unknown bugs in production DBMSs, most of which have been fixed by the developers [4].

## 3 Methodology

### 3.1 The testing loop

Every SQLancer-family fuzzer instantiates the same abstract loop:

1. **State generation.** Execute random DDL/DML to build a database state *S*: tables with random schemas (types, constraints, collations), indexes (including partial and expression indexes), and rows with boundary values — NULLs, empty strings, extreme integers, NaN, infinities.
2. **Query generation.** Synthesize a query *Q* valid against *S*, biased toward feature interactions (correlated subqueries, window functions, mixed-type comparisons).
3. **Oracle transformation.** Derive follow-up queries {Q′ᵢ} with a known result relation to *Q*.
4. **Validation.** Execute *Q* and {Q′ᵢ} on the engine; if the metamorphic relation is violated, minimize the test case (delta debugging over statements and rows) and report.

The minimization step is critical: a raw failing case may involve hundreds of statements, but SQLancer's reducer typically produces a 5–15 statement reproducer, which is what makes developer uptake possible — a bug report with a minimal reproducer is fixed; one without is closed [2].

### 3.2 Soundness discipline

An oracle is only as good as its model of SQL semantics. Each oracle must handle:

- **Three-valued logic.** In SQL, predicates evaluate to TRUE, FALSE, or UNKNOWN (NULL). `WHERE p` keeps only TRUE rows; this is the entire basis of TLP.
- **Nondeterminism.** Queries without `ORDER BY` have unspecified row order; aggregates over floats are order-dependent. Oracles compare *multisets*, never sequences, and typically avoid float aggregates or normalize where the type system permits.
- **Dialect divergence.** Implicit casts (`'1' = 1`), collation (`COLLATE NOCASE`), and date arithmetic differ across engines. Differential *across* engines must model these; metamorphic *within* one engine sidesteps them — a key advantage.

### 3.3 Bug triage pipeline

Candidate violations pass through a confirmation stage: re-execution on a fresh database, execution with optimizations disabled where applicable, and cross-checking against a second oracle. Confirmed bugs are reduced, deduplicated by stack trace or behavior signature, and reported upstream. The empirical record shows fix rates above 85% for SQLancer-reported bugs, a striking figure for automated testing [3][4].

## 4 Deep Dive

### 4.1 Ternary Logic Partitioning (TLP)

TLP, introduced in "Finding Bugs in Database Systems via Query Partitioning" at PLDI 2020 [2], is the single most productive logic-bug oracle ever deployed. Its core observation is disarmingly simple: any boolean predicate *p* in SQL evaluates to one of three truth values — TRUE, FALSE, or NULL. Therefore, for any query *Q* of the form `SELECT ... FROM ... WHERE p`, the result set can be *partitioned* into three queries:

```sql
-- original query
SELECT * FROM t WHERE p;
-- TLP partitions; UNION ALL must equal SELECT * FROM t as a multiset
SELECT * FROM t WHERE p;
SELECT * FROM t WHERE NOT p;
SELECT * FROM t WHERE p IS NULL;
```

The metamorphic relation is that the `UNION ALL` of the three partitions must equal the unpartitioned `SELECT ... FROM ...` (with no WHERE clause) as multisets. Because the partitioning queries are *more complex* than the original — they force the engine through predicate negation, NULL-checking, and different plan shapes — they stress code paths the simple query never touches, and discrepancies reveal logic bugs [2].

TLP generalizes beyond WHERE clauses. The same partitioning applies to:

- **GROUP BY / HAVING**: partition the grouping key space.
- **Aggregates**: `SELECT SUM(x) FROM t WHERE p` decomposes into three partial sums.
- **DISTINCT queries**: partitioning commutes with duplicate elimination.
- **JOINs**: the join condition itself is a predicate and can be partitioned.

A celebrated example from MySQL [9]: with a table holding a single integer row `0`, the query `SELECT * FROM t WHERE 0.9 > i` should match (since 0.9 > 0), yet all three partitions returned empty — a type-conversion defect in the comparison path that the MySQL team classified as critical. The property failure was precisely the TLP relation: the partitions did not unify to the original query's result.

> **Theorem (TLP soundness):** *For any predicate p and table t, the triple (σ_p(t), σ_{¬p}(t), σ_{p IS NULL}(t)) partitions t under SQL three-valued logic, because every row's evaluation of p is exactly one of TRUE, FALSE, or UNKNOWN, and WHERE retains exactly the TRUE rows.*

The subtlety lies in the word *exactly*: engines that mishandle NULL propagation in `NOT p` (a notorious source of bugs) break the partition, which is exactly what the oracle detects.

### 4.2 Non-Optimizing Reference Engine Construction (NoREC)

NoREC, published at ICSE 2020 [1], targets *optimization bugs* specifically. The insight: a query optimizer bug can be detected by comparing the optimized query's result against the *same query executed without optimizations*. NoREC constructs the "non-optimizing reference" not by building a second engine, but by *rewriting the query* so the optimizer cannot apply the transformation under test:

```sql
-- original (optimized) query
SELECT * FROM t WHERE t.a > 0;
-- NoREC reference: move the predicate where the optimizer cannot fold it
SELECT * FROM (SELECT *, (t.a > 0) AS pred FROM t) WHERE pred;
```

More precisely, NoREC translates `SELECT ... FROM t WHERE φ` into a form where the predicate is evaluated as a projection over a full table scan — inhibiting index selection, predicate pushdown, and constant folding. If the two result sets differ as multisets, an optimization is unsound. NoREC uncovered more than 150 new bugs in widely-used DBMS in its original evaluation [1].

```haskell
-- NoREC as a metamorphic relation, idealized
norec :: Query -> (Query, Query)
norec (Select cols t (Where p)) =
  ( Select cols t (Where p)            -- optimized path
  , Select cols t NoWhere              -- unoptimized reference
      `withProjection` (Case p KeepRow DropRow) )
```

The Haskell sketch captures the essence: the reference query must be *denotationally identical* but *operationally distinct*, exercising the naive executor rather than the optimized plan.

### 4.3 Pivoted Query Synthesis (PQS)

PQS, presented at OSDI 2020, inverts the oracle direction. Instead of transforming a query and comparing, it *synthesizes a query guaranteed to return a known row*. The generator first selects a random "pivot row" from a table, then constructs a query whose WHERE clause is engineered — through the same random expression generator that built the data — to certainly match that row. If the pivot row is absent from the result, a logic bug is certain, with *zero* false positives by construction (modulo generator bugs).

PQS is particularly effective at finding bugs in expression evaluation and index scans, because the pivot-row guarantee forces the engine to actually retrieve a specific row through whatever access path the planner chooses. It complements TLP and NoREC: where TLP stresses predicate partitioning and NoREC stresses the optimizer, PQS stresses row retrieval fidelity.

### 4.4 Query plan equivalence and Query Plan Guidance

A newer family of oracles treats the *query plan itself* as the test object. The observation, developed in "Testing Database Engines via Query Plan Guidance" (QPG), is that logic bugs cluster in unusual plan shapes: a hash join fed by a partial index scan is exercised far less than a sequential scan. QPG therefore *guides* generation toward unseen plans: it maintains a set of observed plan signatures and mutates the database state when no new plans appear, explicitly maximizing plan-space coverage. Validation reuses the NoREC/TLP oracles [10].

Related techniques include:

- **Multi-plan execution (MPE)** [8]: force the engine to execute the same query under multiple plans (by toggling optimizer flags or hints) and require identical results — a within-engine differential oracle over the plan space.
- **Equivalent intermediate representations (ERIQ)**: rewrite subqueries as views, CTEs, or temporary tables and require result consistency, stressing the decorrelation and materialization paths.
- **CODDTest / EET**: apply algebraically equivalent expression transformations (e.g., `a + b ≡ b + a`, De Morgan rewrites) and compare.

| Oracle | Relation type | Target bug class | Reference implementation |
|---|---|---|---|
| NoREC [1] | Metamorphic (optimized vs. de-optimized) | Optimizer unsoundness | SQLancer |
| TLP [2] | Metamorphic (partitioned vs. whole) | Predicate/index logic | SQLancer, SQLRight |
| PQS | Constructive (pivot row must appear) | Retrieval/executor logic | SQLancer |
| QPG [10] | Plan-space coverage + metamorphic | Plan-shape-dependent logic | QPG prototype |
| MPE [8] | Differential across plans | Plan-sensitive logic | Kangaroo |
| Cross-engine diff | Differential across engines | General logic | SQLancer++ [3] |

### 4.5 Scaling: SQLancer++ and adaptive generation

The Achilles' heel of the SQLancer line is the *dialect-specific generator*: supporting a new DBMS historically required weeks of manual grammar engineering [3]. SQLancer++ introduces an *adaptive SQL generator* that emits statements from a broad superset grammar and learns, through interaction, which features the target DBMS accepts — converging on mostly-valid SQL without per-dialect handcrafting. Evaluated across 18 DBMSs, it discovered 196 unique previously unknown bugs, 180 fixed after reporting [3]. This is the scaling story: oracles are universal, generators were the bottleneck, and adaptivity removes it.

## 5 Empirical Results and Proofs

### 5.1 The bug record

The quantitative record of this research line is, by the standards of automated testing, extraordinary:

- **NoREC** (original evaluation): 150+ bugs across SQLite, MySQL, PostgreSQL, and MariaDB [1].
- **TLP** (original evaluation): 100+ bugs; combined SQLancer total exceeding 450 unique previously unknown bugs by early 2021, "most of which have been fixed by the developers" [2][4].
- **SQLancer++**: 196 unique bugs across 18 DBMSs, 180 fixed after reporting [3].
- **SQLRight** (coverage-guided): demonstrated higher path coverage than SQLancer's rule-based generator and found bugs in code regions SQLancer never reached [6].
- **QPG**: showed that plan-guided generation discovers logic bugs faster than random generation at equal query budgets [10].

These bugs include wrong-result defects in SQLite's query planner (skip-scan and partial-index paths), MySQL type-coercion errors in comparisons, PostgreSQL executor defects, and TiDB/CockroachDB planning inconsistencies [1][2][3][9].

### 5.2 Why the oracles work: a proof sketch

The effectiveness of TLP-style oracles admits an information-theoretic intuition. Let *E* be the engine as a function from (query, state) to result, and let *C* be the correct semantics. A logic bug is a point where *E ≠ C*. Random query generation samples the input space uniformly, but bugs are not uniform: they concentrate at *feature interactions* (NULL × index, coercion × join, collation × aggregate). A metamorphic oracle multiplies each sampled query into *k* related queries exercising *different* code paths (different plan shapes, different predicate forms), effectively sampling the bug-concentrated regions *k* times per generation step. Formally, if a bug manifests on a fraction *ε* of the query space but the oracle's transformations map a benign query into the bug's triggering region with probability *δ ≫ ε*, the oracle amplifies detection by *δ/ε* — which is why TLP's deliberately *more complex* partitioning queries outperform naive differential testing [2].

### 5.3 Case study: the MySQL float comparison bug

The `0.9 > i` bug [9] illustrates the full pipeline. TLP generated the three partitions of `SELECT * FROM t WHERE 0.9 > i` over a single-row table; all three returned empty while the unpartitioned query should have returned the row. Minimization reduced the reproducer to a handful of statements; the root cause was MySQL's constant-folding path converting the integer column to float incorrectly during comparison. The fix touched type-coercion logic shared by all comparison operators — one silent bug with blast radius across every mixed int/float comparison.

### 5.4 Concrete reproducer: the SQLite collation/index bug

SQLaser documents a minimal SQLite logic bug found by these oracles [7]:

```sql
CREATE TABLE t0(c0 COLLATE NOCASE, c1);
CREATE INDEX i0 ON t0(c0) WHERE c0 >= c1;
INSERT INTO t0 VALUES('a', 'B');
SELECT * FROM t0 WHERE t0.c1 <= t0.c0;
-- output: {}, expected: {a|B}
```

The partial index `i0` interacts with the `NOCASE` collation: the optimizer selects the partial index for the comparison, but the index's predicate semantics under case-insensitive collation diverge from the query's — a textbook index-path logic bug of exactly the kind NoREC and TLP were designed to catch.

## 6 Limitations

No oracle is complete, and intellectual honesty requires enumerating the blind spots:

1. **Self-consistent bugs.** If the engine is wrong in *all* of the original and transformed queries identically — e.g., a broken aggregate that miscomputes in every plan shape — metamorphic oracles cannot observe it. This is the fundamental limit of within-engine differential testing; only cross-engine or specification-based oracles escape it, and they bring their own false-positive burdens [5].

2. **Oracle-model bugs.** Every confirmed "bug" is relative to the oracle's model of SQL semantics. SQLancer's history includes invalid reports where the oracle, not the engine, was wrong — a tax on the approach that minimization and developer feedback gradually amortize.

3. **Generator ceiling.** TLP can only partition predicates the generator can express. SQLancer's rule-based generators avoid correlated subqueries, window functions, recursive CTEs, and complex DDL — precisely the features where modern engines accumulate logic bugs [6][8]. Coverage-guided successors (SQLRight, SQLaser, Kangaroo) raise this ceiling but do not remove it.

4. **Nondeterminism and flakiness.** Parallel execution, autovacuum timing, and statistics-dependent plan choices make some violations non-reproducible, complicating triage. Oracles must be conservative (multiset comparison, deterministic data) at the cost of reduced bug-finding power.

5. **Scale economics.** Even with SQLancer++'s adaptive generation, each new DBMS requires oracle-porting effort for dialect-specific validation, and the 24-hour evaluation cycles in the literature [8][10] reflect a genuinely expensive testing loop.

---

## 7 Conclusion

Differential fuzzing of database engines has matured from a clever trick into a disciplined subfield with its own oracles, proof techniques, and empirical canon. Together, implemented in SQLancer and its descendants, they have found and fixed many hundreds of logic bugs in the world's most widely deployed database systems — bugs that no crash fuzzer could ever have seen.

The open problems are now architectural rather than conceptual: adaptive generation to cover the long tail of DBMSs [3], coverage-guided oracles that learn which transformations pay off [6][7], and principled handling of the self-consistency blind spot. The deeper lesson endures: *correctness is a relation, not a property* — and the strongest oracles check relations derived from the logic of the language itself.
