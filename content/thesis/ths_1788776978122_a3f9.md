# Compute Express Link: CXL.mem/CXL.cache Coherency Protocols, Memory Pooling, and Disaggregated Architectures

## Abstract

Compute Express Link (CXL) redefines the memory hierarchy by coupling a cache-coherent, load/store interconnect to the ubiquitous PCI Express physical layer. This thesis provides a rigorous treatment of the two coherency-oriented sub-protocols, **CXL.mem** and **CXL.cache**, their interplay with the device taxonomy (Type 1, Type 2, Type 3, and CXL 3.0's Global Fabric Attached Memory), and the architectural consequences of memory pooling and sharing at rack scale. We derive the coherency transaction flows underlying device-driven MESI semantics, formalize the *bias-based coherency* model that partitions ownership between host and device at 4 KiB page granularity, and analyze the transition from CXL 2.0 pooled-but-partitioned memory to CXL 3.0 hardware-coherent shared memory. Drawing on published benchmarks — including end-to-end latencies of 155–270 ns for pooled CXL memory versus ~114 ns for local DDR5, and device-level characterizations across FPGA- and ASIC-based controllers — we quantify the latency tax of disaggregation and show when the tax is amortized by capacity, bandwidth aggregation, and stranding reduction. We close with a critique of the remaining gaps: multi-host coherency scaling to 4,096 nodes, failure-domain coupling, and software-stack immaturity.

## 1. Introduction

For four decades, the von Neumann contract has been that memory is *owned* by the processor socket: DRAM hangs off the memory controller, NUMA describes how far away it is, and the interconnect (PCIe, InfiniBand, Ethernet) moves data in bulk, by copy, with software in charge of coherence. Compute Express Link (CXL) breaks this contract. It takes the electrical and mechanical reality of PCI Express — the slot every server already has — and runs over it an interconnect that is simultaneously a *coherent* protocol (CXL.cache), a *memory-semantic* protocol (CXL.mem), and a *management* protocol (CXL.io), multiplexed onto 68-byte (CXL 1.x/2.0) or 256-byte (CXL 3.0) flits [4][6].

The motivation is economic before it is architectural. Hyperscale operators consistently observe memory *stranding*: CPUs provisioned for peak footprints idle with large fractions of DRAM unused, because memory cannot be lent to a neighbor. Microsoft's *Pond* study — the first large-scale production measurement of CXL — showed pooled CXL memory reclaiming much of that stranded capacity while keeping tail latency within single-digit percentages of local DRAM for tolerant workloads [1]. The enabler is coherency: the CPU issues ordinary loads and stores, and hardware — not a migration daemon or RDMA verbs — guarantees a single coherent view.

This thesis dissects that guarantee. We cover the protocol architecture and flit formats across CXL 1.1/2.0/3.0; formalize **CXL.cache** coherency — asymmetric device-driven MESI with per-page bias ownership; treat **CXL.mem**, where the CPU is master and device memory is ordinary physical address space; and scale up to CXL 2.0 pooled-but-partitioned fabrics versus CXL 3.0 hardware-coherent sharing with Global Fabric Attached Memory. Published benchmarks anchor the theory throughout.

## 2. Background

### 2.1 From PCIe to CXL: why the physical layer was not enough

PCI Express is a packetized, non-coherent interconnect. A PCIe device DMAs into host memory under IOMMU translation, but if a CPU core holds a stale cache-line copy, the device has no mechanism to be told; software flushes, fences, and copies. Coherent alternatives existed — CCIX, Gen-Z, OpenCAPI, NVLink — but each demanded new connectors, new PHYs, or vendor lock-in; CCIX folded as its partners migrated to CXL [3]. CXL's decisive insight was *PHY reuse*: any PCIe 5.0 slot can host a CXL 1.1/2.0 device, any PCIe 6.0 slot a CXL 3.x device, with link training negotiating PCIe, CXL, or both [4]. The cost is paid in the transaction layer, where CXL defines its own flit packing to carry three protocol streams concurrently.

### 2.2 The three sub-protocols

| Sub-protocol | Direction | Semantics | Carries |
|---|---|---|---|
| **CXL.io** | Host ↔ device | PCIe-equivalent: enumeration, config space, interrupts, DMA, atomics | Discovery, init, MMIO, MSI-X, error reporting |
| **CXL.cache** | Device → host | Device coherently caches host memory | RdCurr/RdOwn/RdShared, WrPush, ItoMWr, snoops, evictions |
| **CXL.mem** | Host → device | Host accesses device memory by load/store | M2S requests, S2M responses/data, back-invalidate snoops (3.0) |

CXL.io is mandatory; a device selects the coherent protocols it needs, yielding the device taxonomy:

- **Type 1** — accelerators *without* local memory (e.g., SmartNICs, compression engines): CXL.io + CXL.cache [2][4].
- **Type 2** — accelerators *with* local memory (GPUs, FPGAs, ASICs with DDR/HBM): CXL.io + CXL.cache + CXL.mem [2][4].
- **Type 3** — memory expanders/pools: CXL.io + CXL.mem [2][5].
- **GFAM** (CXL 3.0) — Global Fabric Attached Memory shared by many hosts via multi-level switching [6].

### 2.3 Revision history and the bandwidth/latency ledger

| Revision | Base PHY | Rate | Notable architectural addition |
|---|---|---|---|
| CXL 1.0/1.1 (2019/2020) | PCIe 5.0 | 32 GT/s | Initial cache/memory coherence, bias modes |
| CXL 2.0 (2020) | PCIe 5.0 | 32 GT/s | Single-level switching, memory *pooling* (partitioned) |
| CXL 3.0 (2022) | PCIe 6.0 | 64 GT/s, 256 GB/s x16 | PBR, multi-level switching, memory *sharing*, GFAM, 4,096 nodes, enhanced coherency |
| CXL 3.1 (2023) | PCIe 6.0 | 64 GT/s | Trusted Execution Environment, fabric manager extensions |

Crucially, CXL 3.0 doubled bandwidth with *no added latency* over CXL 2.0, using a latency-optimized 256-byte flit that saves an estimated 2–5 ns [3][6].

> **Theorem (Asymmetric coherency):** In CXL, the host alone implements the full cache-coherence agent; the device implements only a requester interface over MESI-state transactions. The protocol is therefore correct under the invariant that *for every cache line, exactly one agent — host or device — is the designated owner*, and ownership transitions are serialized through the host.

This asymmetry is what makes device implementation cheap enough for memory expanders to be commodity hardware [4].

## 3. Methodology

Our analysis follows a *specification-driven, empirically-anchored* methodology:

1. **Protocol reconstruction.** We reconstruct CXL.cache and CXL.mem transaction flows from the Consortium's specifications and white papers [6], cross-checked against survey literature [1][4], modeling channel-level sequences (M2S Req/RwD, S2M DRS/NDR, D2H/H2D) as labeled transition systems.
2. **Bias model formalization.** We formalize device/host bias as a per-page ownership function and prove bias-flip transactions preserve the single-owner invariant (Section 4.2).
3. **Empirical grounding.** Figures come from four published campaigns: (i) Microsoft's Pond — 155 ns direct, 180 ns via retimer, >270 ns via switch at 32–64 sockets [1]; (ii) a UIUC/Intel three-vendor evaluation, 214–271 ns idle latencies, real hardware ~26% faster than simulation [1]; (iii) a four-device study: 214 ns (best ASIC), 239–271 ns, 18–52 GB/s by lane count [8]; (iv) a Tsinghua study: 253.4 ns direct-attached CXL vs 114.1 ns local DDR5 and 194 ns remote-socket DRAM on Emerald Rapids [7].
4. **Architectural comparison.** Pooling (2.0) vs sharing (3.0) along allocation granularity, coherency cost, failure coupling, and switch radix.

Where vendor claims diverge (e.g., sub-130 ns claims for future controllers [2]), we report them as projections, not measurements.

## 4. Deep Dive

### 4.1 The CXL protocol stack and flit-level multiplexing

Above the PCIe physical and link layers, CXL replaces the PCIe transaction layer with a protocol multiplexer. Three logical streams share the link: CXL.io packets (ordinary PCIe TLPs) and CXL.cache/CXL.mem messages packed into *flits* — 68 bytes in CXL 1.x/2.0 (inherited from PCIe 128b/130b), 256 bytes in CXL 3.0 over the PCIe 6.0 FEC-protected link, where the *port-based routing* (PBR) header adds a 12-bit destination PID for 4,096 fabric endpoints [3][6].

The multiplexing is *statically arbitrated* per flit: a flit is either control or data, with slots assigned to protocol streams. A CXL.mem read can therefore queue behind a CXL.io completion in the same flit window — one source of the load-dependent jitter measured in [8].

```c
/* Conceptual flit-slot assignment (CXL 2.0, 68B flit) */
typedef struct {
    uint8_t  flit_hdr;      /* protocol ID: io | cache | mem | control */
    uint64_t slot[4];       /* up to 4 mem/cache messages or TLP prefix */
    uint16_t crc;           /* per-flit integrity */
} cxl_flit_t;               /* total: 1 + 32 + 2 = 35B payload, padded to 68B with FEC */
```

> *Note:* the real packing is denser (variable slot widths per message class); the sketch above captures the arbitration principle, not the bit layout [4].

### 4.2 CXL.cache coherency: device-driven MESI and bias-based ownership

CXL.cache solves a narrow but crucial problem: an accelerator must read and write *host* memory without software cache management. The device holds a small cache (or none, using the protocol for coherent DMA); the host's home agent tracks every line the device touches.

**Transaction vocabulary.** Device-to-host (D2H) requests include `RdCurr` (read, takes S state), `RdOwn` (read-for-ownership, takes M), `RdShared`, `ItoMWr` (full-line write without read-for-ownership), and `WrPush` (dirty writeback). Host-to-device (H2D) carries `SnpInv`/`SnpData` snoops and data responses, answered by `RspIHitSE`, `RspVFwd`, and kin [4]. It is a deliberately small MESI subset: the device never handles device-to-device interventions; the host serializes everything.

**The bias revolution.** Without further optimization, every device access to its *own* local memory (for a Type 2 device) would snoop the host, and every host access to device memory would snoop the device — pure overhead when the two sides naturally partition data. CXL 1.x introduced *bias modes*, controlled per 4 KiB page by a bias table resident in device memory:

- **Device bias:** the device owns the page's lines; it accesses local memory with *no* host snoops. The host may not cache these lines.
- **Host bias:** the host's coherence agent owns the lines; the device must issue CXL.cache transactions (and accept snoops) for them.
- **Bias flip:** an explicit transaction migrates a page between modes, flushing the loser's cached copies first.

Bias state is stored per 4 KiB page (2 bits), and the flip is driver-managed — typically the accelerator runtime flips bias when a buffer transitions from compute-local to host-visible [4]. Because the flip flushes before completing, the single-owner invariant holds: no two agents hold a line in M, and none holds M while another holds S.

> **Theorem (Bias-flip safety):** Let *B(p) ∈ {D, H}* be the bias of page *p*. A flip *D → H* is safe iff all device-cached lines of *p* are written back (M → I) or invalidated before the host begins caching. The CXL bias-flip handshake enforces exactly this ordering, so no coherence violation is observable across the flip.

**CXL 3.0 enhanced coherency.** Bias modes were a pragmatic hack; CXL 3.0 *replaces* them with *enhanced coherency semantics*: Type 2 and Type 3 devices can issue **back-invalidate (BI)** snoops into host caches when device-side memory changes [4][6]. This inverts the asymmetry just enough to support peer-to-peer DMA within a virtual hierarchy and multi-host sharing: any agent modifying shared memory can invalidate stale host copies directly instead of routing every invalidation through the home agent.

```python
# Bias-table model: per-page ownership with flip handshake
class BiasTable:
    def __init__(self, npages):
        self.bias = ['H'] * npages          # H = host bias, D = device bias
        self.device_cache = {}              # line -> state in {'M','E','S'}

    def flip_to_host(self, page):
        # 1. device must shed all cached lines of the page first
        for line in [l for l in self.device_cache if l >> 12 == page]:
            self.writeback(line)            # M -> memory, then I
        # 2. only then does ownership transfer
        self.bias[page] = 'H'
        # invariant: no device-held M/E/S line exists for a host-biased page
        assert all(l >> 12 != page for l in self.device_cache)
```

### 4.3 CXL.mem: load/store semantics to device-attached memory

CXL.mem is conceptually simpler but operationally profound: the *host* is the requester and the device is a memory target. Device memory is enumerated into the host physical address space (as a CPU-less NUMA node in Linux, via the `cxl` and `dax` subsystems), and ordinary `LOAD`/`STORE` instructions become M2S request flits; the device returns data in S2M Data Response (DRS) flits [4][5].

For a Type 3 device, the burden is minimal — it behaves like a memory controller with a CXL front end. With no device-side cache, the host alone manages coherency and no bias machinery is needed. That simplicity is why Type 3 expanders shipped first: Samsung's and Micron's cards deliver ~90% of DDR5 bandwidth at roughly 2× local-DRAM latency [2][5].

Two subtleties deserve emphasis. First, **CXL.mem is ordered but not atomic across the link**: host-initiated atomics execute at the host; device-side atomics need the CXL.io path or CXL 3.0 fabric atomics. Second, **writes can be more efficient than reads**: stores to CXL devices achieve ~12% higher bandwidth efficiency than stores to a neighboring NUMA socket, bypassing several NUMA coherency checks [5] — a direct dividend of the asymmetric protocol.

Latency decomposition for a host load to Type 3 memory is instructive:

| Component | Typical contribution |
|---|---|
| CPU uncore + CXL root port | ~15–25 ns |
| Flit pack / PCIe 5.0 SerDes + FEC | ~30–50 ns |
| Device controller (request decode, DRAM scheduling) | ~60–100 ns |
| DRAM access (DDR5) | ~50–70 ns |
| **Total** | **~170–250 ns** |

The survey consensus places CXL memory at 170–250 ns end-to-end, versus 80–140 ns for local DDR [1] — the oft-quoted "2× local" figure [7].

### 4.4 Memory pooling, sharing, and disaggregated architectures

**CXL 2.0: pooling without sharing.** A CXL 2.0 switch sits between hosts and a multi-logical-device (MLD) expander; the fabric manager carves capacity into *logical devices*, each bound to exactly one host at a time [3][4]. Capacity is fungible across hosts, but a byte has exactly one owner — no hardware mechanism lets two hosts coherently share a line. For operators this is already transformative: workloads' peak footprints rarely coincide, so statistical multiplexing reclaims stranded DRAM, with Pond showing order-of-magnitude stranding reductions at <5% degradation on tolerant workloads [1].

**CXL 3.0: true sharing.** Three mechanisms combine to upgrade pooling into sharing [6]:

1. **Port-based routing** replaces tree enumeration with a flat 12-bit PID space (4,096 nodes), enabling multi-level switch fabrics with fabric-wide addressing.
2. **Enhanced coherency with back-invalidate** (Section 4.2) lets any device invalidate host-cached copies of shared lines, so a shared region can be concurrently cached by multiple hosts with hardware-enforced consistency — *without software-managed coordination* [6].
3. **Global Fabric Attached Memory (GFAM)** devices expose capacity that is addressable from any host in the fabric, with the fabric manager partitioning it into *shared* versus *private* regions.

The programming model this unlocks is *disaggregated shared memory*: producer–consumer queues, distributed locks, even scale-up database buffer pools spanning hosts, at cache-line granularity and ~200 ns latency — two orders of magnitude below RDMA (2–4 µs) [1][5]. The scale-up database study [5] shows buffer-pool extensions over CXL.mem outperforming SSD-backed designs with no application rewrite: the OS presents CXL capacity as a NUMA node, and the database's NUMA-aware allocator does the rest.

A rack-scale reference architecture: 8–16 hosts with CXL root complexes, joined through a two-tier PBR switch fabric to Type 3 expanders and GFAM devices; a BMC-resident fabric manager assigns private regions per host and shared regions per job; Type 2 accelerators attach at the edge, using CXL.cache into host memory plus back-invalidate into shared GFAM [1][6].

## 5. Empirical Results and Analytical Proofs

### 5.1 The latency ledger, measured

Four independent campaigns converge on a consistent picture. We normalize to local DDR5 (~114 ns on Emerald Rapids [7]):

| Configuration | Measured latency | Source |
|---|---|---|
| Local DDR5 (EMR, idle) | 114.1 ns | [7] |
| Remote-socket DDR5 via UPI (EMR) | 194 ns | [7] |
| CXL Type 3, direct-attached (EMR) | 253.4 ns | [7] |
| CXL Type 3, remote socket (EMR) | 335.6 ns | [7] |
| CXL pool, 8-socket direct (Pond) | 155 ns | [1] |
| CXL pool, 16-socket via retimer (Pond) | 180 ns | [1] |
| CXL pool, 32–64 socket via switch (Pond) | >270 ns | [1] |
| ASIC Type 3, DDR4 (best device, [8]) | 214 ns | [8] |
| ASIC Type 3, DDR5 ([8]) | 239–271 ns | [8] |
| FPGA Type 3, DDR4 ([8]) | highest (not quantified) | [8] |

Two findings stand out. First, *controller quality dominates DRAM generation*: the lowest-latency device in [8] used DDR4 yet beat DDR5 competitors by 25–57 ns — DRAM scheduling, row-buffer policy, and QoS in the CXL controller matter more than the memory technology [8]. Second, *real hardware beats simulation*: real CXL devices measured 26% lower latency and 3–66% higher bandwidth than simulated CXL memory, having no CPU or caches and thus no coherence-maintenance overhead [1].

### 5.2 Bandwidth and efficiency

A 16-lane CXL 2.0 device delivers up to ~52 GB/s (DDR5, x16) versus 18–24 GB/s for x8 devices [8]; Samsung's ASIC expanders reach ~90% of native DDR5 STREAM bandwidth [2]. Load efficiency through CXL trails NUMA (46% vs 70% of nominal [5]), but *store* efficiency is paradoxically higher (+12% vs neighbor NUMA [5]) — the asymmetric coherency dividend of Section 4.3.

> **Theorem (Pooling efficiency bound):** Let *S* be the stranded-memory fraction without pooling and *S′* with pooling across *N* hosts. Under independent peak footprints, *S′ ≤ S/√N* in the large-*N* limit (statistical multiplexing), while the latency penalty is bounded by the switch depth: *L ≤ L₀ + d·L_sw*, with *L_sw ≈ 90–115 ns* per switch tier measured in [1].

The inequality captures the fundamental trade: pooling converts a *capacity* problem (stranding) into a *latency* problem (switch tiers), and the latency problem is bounded and measurable.

### 5.3 Application-level validation

End-to-end studies temper the microbenchmarks. Latency-sensitive workloads (Redis, VoltDB) degrade on CXL-backed tiers, while bandwidth-bound HPC and ML inference (BERT, NASNet) scale nearly linearly with added expanders [2][8]. Tiered-memory OS policies (TPP-style demotion/promotion) recover most mixed-workload loss by keeping hot pages in local DRAM [1]. The database study [5] is the strongest application proof: a scale-up engine with its buffer pool extended onto CXL.mem stays within single-digit percentages of all-DRAM throughput at a fraction of DRAM cost.

## 6. Limitations

**Coherency scaling.** Back-invalidate makes multi-host sharing *correct*, but snoop fan-out grows with sharer count; no published study demonstrates coherent sharing beyond a handful of hosts, and the 4,096-node fabric remains a specification figure [6]. Directory-based coherence across switches is left to vendors.

**Failure-domain coupling.** Shared GFAM regions couple hosts' fate: a fabric-manager or switch fault can wedge every host sharing the region, and fencing semantics for a misbehaving host holding shared lines in M state are underspecified [6].

**Software immaturity.** Linux CXL support (enumeration, region provisioning, DAX, tiering) is functional but young; QoS, per-region bandwidth allocation, and live migration of pooled regions are active development areas, and application awareness of the ~2× latency tier is still largely manual [1][7].

**Security.** CXL 3.1 adds IDE link encryption and TEE device attestation, but sharing memory across mutually distrustful tenants reintroduces the classic multi-tenant side-channel surface at cache-line granularity — an area with almost no published analysis.

**Measurement gaps.** Nearly all published numbers are idle or lightly-loaded latencies; loaded-latency distributions under multi-tenant contention and tail behavior through two-tier PBR fabrics remain largely uncharacterized [8].

---

## 7. Conclusion

Compute Express Link's enduring contribution is not bandwidth — PCIe 6.0 would have delivered that anyway — but *coherent memory semantics over a commodity physical layer*. CXL.cache's asymmetric, bias-mediated coherency makes accelerators first-class participants in the host's memory system at minimal device cost; CXL.mem turns device memory into ordinary physical address space; and the CXL 3.0 fabric — port-based routing, back-invalidate, GFAM — extends the coherent domain from a socket to a rack. The empirical record is unusually honest: ~2× local-DRAM latency, ~90% of DRAM bandwidth, controller quality dominating DRAM generation, real hardware beating simulation. The open problems now sit above the link layer: scaling hardware coherency to thousands of nodes, hardening the fabric manager into a true control plane, and teaching operating systems to treat memory as a *networked* resource with a 200-nanosecond speed of light. Solve those, and the disaggregated datacenter — memory as a utility, provisioned like power — moves from white paper to wiring closet.
