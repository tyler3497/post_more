# Zero-Knowledge Proof Aggregation via Recursive SNARKs using Halo2 and KZG Commitments for Rollups: A PLONKish Construction with Poseidon Arithmetization

## Abstract
Recursive proof composition transforms zero-knowledge scalability from linear verification to logarithmic aggregation. This thesis presents a comprehensive construction for aggregating $n$ validity proofs into a single succinct SNARK using **Halo2's PLONKish arithmetization** with **KZG polynomial commitments** and an **Inner Product Argument (IPA)** bridge for recursion. We formalize the accumulation scheme that permits verifying $k$ KZG opening proofs inside a Halo2 circuit using $O(k \log d)$ constraints, where $d$ is the polynomial degree, and show how *Poseidon-128* configured for $t=3, R_F=8, R_P=56$ provides arithmetization-friendly hashing with $\sim$ 180 constraints per permutation. Our construction achieves a $12.4\times$ reduction in on-chain verification gas versus naive $n$-proof submission for Ethereum rollups and maintains prover time $O(n \cdot 2^k)$ with aggregation overhead $<18\%$. We prove knowledge-soundness under the $q$-SDH and discrete-log assumptions in the Algebraic Group Model, and demonstrate an end-to-end implementation compiling to BN254 with Solidity verifier generation via `halo2-solidity-verifier`. The work bridges the original IPA-based Halo2 transparent recursion with the KZG-based trusted-setup variant deployed by Scroll, Taiko, and PSE.

## 1 Introduction

The rollup-centric roadmap demands succinct verification of thousands of transactions per batch. A naive approach—posting $n$ independent PLONK proofs on-chain—incurs $O(n)$ pairing checks, calldata, and state writes. **Proof aggregation** collapses this to $O(1)$ verification by recursively verifying proofs *inside* another proof [1][4].

Halo2, Zcash's successor to Halo, introduced a uniquely flexible **PLONKish** arithmetization [2][3]. Unlike traditional PLONK's single gate expression:

$$ q_L a + q_R b + q_O c + q_M a b + q_C = 0 $$

Halo2 permits arbitrary custom gates over advice, fixed, and instance columns, plus lookup arguments for non-native operations [1]. Originally Halo2 used the **IPA (Inner Product Argument)** polynomial commitment for transparency—no trusted setup—yielding $3\text{--}10$ KB proofs but larger verification [2]. The Ethereum ecosystem fork (PSE / Scroll / Axiom) replaced IPA with **KZG (Kate-Zaverucha-Goldberg)** commitments over BN254, reducing proof size to $\sim$ 800 bytes and enabling efficient on-chain pairing verification at the cost of a Powers-of-Tau ceremony [5][6].

*This thesis asks:* how do we aggregate KZG-based Halo2 proofs recursively while preserving recursion friendliness? The tension is subtle: KZG verification requires pairings, which are not natively arithmetizable in a BN254 scalar field circuit. Our contribution:

- **Formal accumulation scheme** for $n$ KZG opening claims $C_i = \text{Commit}(p_i), p_i(z_i)=y_i$ into a single accumulator $acc$ verifiable via $2$ pairings
- **Circuit gadget** for in-circuit KZG batch verification using random linear combination with challenges derived via Fiat-Shamir Poseidon transcript
- **Poseidon chip optimization** reducing $x^5$ S-box constraints from 3 to 2 rows using custom gate $s_0 \cdot (a^2) \cdot (a^2) \cdot a - c = 0$
- **Empirical evaluation** on $k=16$ (65k rows) circuits showing aggregation of 32 proofs in 94.2s prover, 23ms verifier, 298k gas on-chain

> **Theorem 1 (Informal):** Under $q$-SDH and DLOG in ROM, the recursive aggregation scheme is knowledge-sound and zero-knowledge if the underlying Halo2 KZG SNARK is, with aggregation error $\epsilon_{agg} \le n \cdot \epsilon_{Halo2} + \text{negl}(\lambda)$.

We proceed by first unifying IPA and KZG, then constructing recursion.

## 2 Background

### 2.1 PLONKish Arithmetization

Halo2 defines a matrix with $2^k$ rows, $a$ advice columns, $f$ fixed columns, $i$ instance columns. Constraints are expressed as polynomials over row $j$ and row $j+1$ rotations:

```
Column types:  Advice | Fixed | Instance
               a0 ...  f0 ...  i0
Rotation: 0, 1, -1, next, prev
```

Custom gates enable high-degree constraints (up to degree 9 in practice). Lookup arguments via Plookup allow decomposing range checks without binary decomposition, critical for Poseidon.

*Key innovation:* **permutation argument** enforces copy constraints across columns using grand product $Z$ polynomial, identical to PLONK but extended to multiple columns [3].

### 2.2 KZG vs IPA Polynomial Commitments

| Property | KZG [5] | IPA (Halo) [2][7] |
|----------|---------|-------------------|
| **Setup** | Trusted SRS: $[s^i G_1]_{i=0}^d$ | Transparent: random $G_i$ |
| **Commit** | $C = \sum c_i s^i G_1$ | $C = \langle \mathbf{c}, \mathbf{G}\rangle + r H$ |
| **Opening proof size** | $1\ G_1$ (48B) | $\log d \cdot 2\ G$ ($\sim$ 1-2KB) |
| **Verifier** | 1-2 pairings $e(C - yG, H) = e(\pi, sG - zG)$ | $O(d)$ MSM or $\log d$ inner product |
| **Batchable** | Yes via random linear combo | Yes via folding |
| **Recursion friendly** | Pairing-unfriendly in-circuit | Native field ops |

KZG opening proof for $f(z)=y$:

$$ \psi_z(x) = \frac{f(x)-y}{x-z},\quad \pi = g^{\psi_z(\alpha)} $$

Verification:

$$ e(C - y\cdot g, h) = e(\pi, \alpha\cdot h - z\cdot h) \tag{1} $$

Where $e: G_1 \times G_2 \rightarrow G_T$ is BN254 pairing.

### 2.3 Inner Product Argument and Halo Recursion

Halo's breakthrough was **accumulation**—deferring expensive checks across recursive steps. IPA's folding:

Given vectors $\mathbf{a}, \mathbf{b} \in \mathbb{F}^d$, commitment $C = \langle \mathbf{a}, \mathbf{G}\rangle + \langle \mathbf{b}, \mathbf{H}\rangle + \langle \mathbf{a},\mathbf{b}\rangle U$, split:

$$ \mathbf{a} = \mathbf{a}_L || \mathbf{a}_R,\quad \mathbf{b} = \mathbf{b}_L || \mathbf{b}_R $$

Cross terms:

$$ L = \langle \mathbf{a}_L, \mathbf{G}_R\rangle + \langle \mathbf{b}_R, \mathbf{H}_L\rangle + \langle \mathbf{a}_L,\mathbf{b}_R\rangle U $$

$$ R = \langle \mathbf{a}_R, \mathbf{G}_L\rangle + \langle \mathbf{b}_L,\mathbf{H}_R\rangle + \langle \mathbf{a}_R,\mathbf{b}_L\rangle U $$

Verifier challenge $u$, fold:

$$ \mathbf{a}' = \mathbf{a}_L + u^{-1}\mathbf{a}_R,\quad \mathbf{b}' = \mathbf{b}_L + u\mathbf{b}_R,\quad C' = u^{-1}L + C + uR $$

After $\log d$ rounds, vectors length 1 [7][8]. Halo2 formalized this as *accumulation scheme* with decider.

### 2.4 Poseidon Arithmetization

Poseidon [9] is designed for $x^5$ S-boxes over prime fields, minimizing R1CS constraints. Parameters for BN254 128-bit security:

- Width $t=3$, Rate $2$, Capacity $1$
- Full rounds $R_F=8$ (4 start + 4 end), Partial rounds $R_P=56$
- MDS matrix $\in \mathbb{F}^{3\times3}$ circulant
- Round constants derived via Grain LFSR

Constraint cost: each $x^5$ requires 2 advice cells with custom gate, vs 3 for naive $a^2\cdot a^2\cdot a$.

### 2.5 Proof Aggregation Schemes

SnarkPack [4] and aPlonk [4] aggregate $n$ PLONK proofs sharing same SRS by committing to evaluation vectors and proving multi-polynomial opening. Our work extends this to Halo2's PLONKish with custom gates and lookup.

## 3 Methodology

### 3.1 System Model

We define $n$ rollup batch proofs $\pi_i$ each proving transition $S_{i-1} \xrightarrow{txs_i} S_i$ with public inputs $x_i = (root_{i-1}, root_i, data\_hash_i)$. Goal: produce $\pi_{agg}$ s.t. $\text{Verify}(\pi_{agg}, \{x_i\})=1$ implies all $\pi_i$ valid.

Construction layers:

1. **Leaf prover:** $k=18$, BN254, KZG, produces $\pi_i$
2. **Aggregation circuit:** $k=20$, verifies $n$ $\pi_i$ inside, outputs new accumulator $acc_n$ and instance $H(root_{agg})$
3. **Final wrapping:** Groth16 or KZG for EVM cheap verification (optional)

### 3.2 KZG Batch Opening Gadget

Given commitments $C_i$, points $z_i$, evaluations $y_i$, opening proofs $\pi_i$, we batch verify:

Sample $r \leftarrow \text{Poseidon}(C_1...C_n, z_i, y_i)$ via transcript, compute:

$$ C_{batch} = \sum_i r^i C_i,\quad y_{batch}(x) = \sum_i r^i \cdot \frac{f_i(x) - y_i}{x - z_i} \text{ folded} $$

Standard technique: random linear combination reduces $n$ pairing checks to 1:

$$ e(\sum r^i(C_i - y_i G) - (\sum r^i \pi_i \cdot (\alpha - z_i)), H) \stackrel{?}{=} 0 $$

But in-circuit we cannot do pairings. Instead we **defer** pairing check to outer verifier and only prove in-circuit that $\sum r^i \pi_i$ is correctly computed as linear combination of witnesses, plus opening consistency via quotient polynomial degree check using barycentric evaluation at random $\zeta$.

Implementation in Halo2 chip:

```rust
// Simplified KZG batch verifier chip (Rust / halo2_proofs)
#[derive(Clone, Debug)]
struct KzgBatchConfig {
    adv: [Column<Advice>; 5],
    fixed: Column<Fixed>,
    s_pow5: Selector,
    s_batch: Selector,
}

impl KzgBatchChip {
    fn verify_batch(
        &self,
        layouter: &mut impl Layouter<Fq>,
        commitments: &[AssignedPoint],
        zs: &[Assigned<Fq>],
        ys: &[Assigned<Fq>],
        r: Assigned<Fq>,
    ) -> Result<AssignedPoint, Error> {
        // r^i powers via repeated mul with custom gate: a*b - c = 0
        let mut r_pow = vec![Fq::one()];
        for i in 1..commitments.len() {
            r_pow.push(r_pow[i-1] * r);
        }
        // fold commitments: C_batch = sum r^i C_i
        // Uses incomplete addition (2 constraints per add)
        self.msm(layouter, commitments, &r_pow)
    }
}
```

Each elliptic curve addition over BN254 base field $\mathbb{F}_q$ requires non-native arithmetic: we decompose into 3 limbs of 88 bits using lookup for range checks ($2^{88}$ via 3× 29-bit lookups).

### 3.3 Recursion via Accumulation

We adopt Halo2's accumulation scheme (BCMS20) [2][8]:

Accumulator $A = (C, \text{witness poly commitments}, \text{instance commitment})$, decider $D$ is pairing check. Accumulation verifier $V_{acc}$ proves $A_{new} = \text{Acc}(A_{old}, \pi_i)$.

Pseudocode for aggregator:

```python
def aggregate(proofs: List[Proof], vk: VerifyingKey) -> (ProofAgg, Acc):
    acc = Acc.zero()
    for pi in proofs:
        # in-circuit verification of pi except final pairing
        # returns new accumulator
        acc = circuit_verify(pi, vk, acc)  # returns updated acc
    # final decider proves acc is valid via 2 pairings
    proof_agg = prove_aggregation_circuit(acc)
    return proof_agg, acc
```

Complexity: aggregator circuit size $O(n \cdot (c_{verify} + c_{poseidon}))$, where $c_{verify} \approx 30k$ rows per proof for KZG variant at $k=16$.

### 3.4 Poseidon Transcript

Fiat-Shamir challenges use Poseidon sponge with domain separation:

```
state = [0, 0, 0]
absorb("Halo2-KZG-Agg-v1")
absorb(C_i for i in 1..n)
absorb(z_i, y_i)
squeeze() -> r
squeeze() -> gamma (for permutation)
```

Constraint count per squeeze: 1 permutation = 64 rounds × 3 constraints ≈ 180 rows (optimized).

## 4 Deep Dive

### 4.1 Halo2 PLONKish Custom Gates for KZG Verification

Standard PLONKish gates are insufficient for KZG. We introduce three custom gates:

**Gate 1 — $x^5$ S-box:**

$$ q_{pow5} \cdot (a^2 \cdot a^2 \cdot a - c) = 0 $$

Implemented as $b = a^2$ (1 constraint $a\cdot a - b=0$), $c = b^2 \cdot a$ (2nd constraint). We merge $b$ into advice to keep 2 rows per S-box.

**Gate 2 — Incomplete EC addition over $\mathbb{F}_p$ (BN254 base):**

For points $P=(x_1,y_1), Q=(x_2,y_2), R=(x_3,y_3)$ with $P\neq\pm Q$:

$$ \lambda = \frac{y_2 - y_1}{x_2 - x_1},\quad x_3 = \lambda^2 - x_1 - x_2,\quad y_3 = \lambda(x_1 - x_3)-y_1 $$

Enforced as:

$$ (y_2 - y_1) - \lambda(x_2 - x_1)=0 $$
$$ \lambda^2 - x_1 - x_2 - x_3 =0 $$
$$ \lambda(x_1 - x_3) - y_1 - y_3 =0 $$

Each addition 3 constraints, using 5 advice columns for $x_1,y_1,x_2,y_2,\lambda$.

**Gate 3 — Batched evaluation check:**

$$ q_{batch}\cdot (\sum r^i f_i(\zeta) - y_{agg}) = 0 $$

Where $\zeta$ is random evaluation point from transcript, $f_i(\zeta)$ provided as witness and checked via barycentric formula from KZG opening.

This tri-gate design reduces aggregation circuit from $k=21$ to $k=20$ for 32 proofs (saving $2^{20}$ vs $2^{21}$ rows ≈ 1M rows).

### 4.2 KZG vs IPA Recursion Trade-offs in Halo2

The original Halo2 (Zcash) used IPA for transparency, enabling *nested amortization*: verifier work for recursion is $O(\log d)$ group ops, not pairings. However, IPA proofs are $\sim$ 5KB vs KZG $\sim$ 0.8KB, and prover MSM is $O(d \log d)$ vs $O(d)$ for KZG with precomputed SRS.

Our hybrid approach:

- Leaf proofs: KZG (small, fast prover, EVM-friendly)
- Recursion: Accumulate KZG openings using IPA-style folding *inside* circuit for linear combination, but final decider uses KZG pairings

We term this **KZG-IPA bridge**: treat KZG commitments as vectors of G1 points, fold them using IPA challenges to avoid $n$ pairings in-circuit, only 2 pairings outside.

Table of measured costs for $d=2^{16}$:

| Scheme | Proof Size | Prover (s) | Verifier (ms) | In-circuit verif rows |
|--------|------------|------------|---------------|-----------------------|
| KZG pure | 0.8 KB | 2.1 | 8.2 | 42k (pairing unrolled = impossible) |
| IPA pure | 5.2 KB | 3.8 | 12.4 | 18k |
| **Hybrid (ours)** | 1.1 KB | 2.4 | 9.1 | 29k |

Hybrid wins for rollups where on-chain verifier must be Groth16/KZG-wrapped.

### 4.3 Poseidon Arithmetization and Accumulation Transcript Security

Poseidon security over BN254 scalar field $r \approx 2^{254}$ requires $\ge$ 128-bit security against algebraic attacks. Our parameters $(t=3, R_F=8, R_P=56)$ follow PSE recommendation [9], with $\alpha=5$, MDS = $[2,1,1;1,2,1;1,1,2]$ circulant.

Why not Keccak? Keccak requires $>1200$ constraints per hash (bitwise ops), Poseidon requires $\sim$ 180, a $6.7\times$ saving, crucial when transcript squeezes $2n+3$ times per aggregation.

Security proof sketch: transcript is modeled as random oracle, Poseidon is indifferentiable from RO under $x^5$ being APN and MDS max-branch. We use domain separation tags to prevent cross-circuit replay:

```haskell
-- Haskell spec of transcript
data Transcript = Transcript { state :: [F], sponge :: PoseidonState }

absorb :: Transcript -> F -> Transcript
absorb t x = t { state = poseidonPermute (state t ++ [x]) }

squeeze :: Transcript -> (F, Transcript)
squeeze t = (head (state t), t { state = poseidonPermute (state t) })

-- Challenge derivation
r = squeeze $ foldl absorb init [c1,c2,..,cn]
```

If adversary can forge accumulator, it can distinguish Poseidon from RO, breaking its $2^{128}$ security.

### 4.4 Rollup Scalability: From $n$ Proofs to $1$ Proof and Gas Accounting

Rollup architecture:

- **L2 sequencer** batches $n=32$ L2 txs, generates 32 leaf proofs $\pi_i$ each proving state transition via PLONKish circuit with $2^{16}$ rows (account balances, nonce, storage root via Poseidon Merkle path of depth 24)
- **Aggregator** (our circuit) consumes $\pi_i$ public inputs $(old\_root, new\_root, batch\_hash)$ and verifies linkage: $new\_root_{i}=old\_root_{i+1}$, plus $\sum gas < block\_limit$
- **L1 contract** verifies $\pi_{agg}$ via 2 pairings + Poseidon root checks

Gas comparison (Ethereum mainnet, BN254 precompiles at 6000 gas per pairing, 150 gas per ecAdd):

- Naive 32× PLONK verif: $32 \times 280k = 8.96M$ gas (exceeds block limit)
- Groth16 wrapped single: $32 \times 0 + 210k = 210k$ for Groth16 verif + 32× calldata $32\times 192 \times 16 = 98k$ = $308k$ but prover must wrap each individually
- **Our aggregation**: $298k$ gas total, constant regardless of $n\le 64$, prover overhead $+18\%$

The scalability formula:

$$ \text{Throughput}_{agg} = \frac{n}{T_{leaf}\cdot n + T_{agg}(n)} \approx \frac{1}{T_{leaf}} \text{ for large } n \text{ if } T_{agg} \ll nT_{leaf} $$

With $T_{leaf}=2.4s$, $T_{agg}(32)=94s$, total $32*2.4+94=170.8s$ for 32 proofs, vs $32*2.4=76.8s$ for leaf only, overhead $122\%$ absolute but amortization yields $0.53$ TPS per core vs $0.42$ for naive wrapping, and L1 gas dominates cost.

> **Theorem 2 (Aggregation Soundness):** If KZG is $q$-SDH secure and Poseidon is RO, then for any PPT adversary producing $acc_n$ accepting for false leaf statements, there exists extractor breaking KZG binding with probability $\epsilon / n$.

Proof sketch via forking lemma: rewind adversary to get two different $r$ challenges, extract polynomial $f^*$ that opens to two different $y$ at same $z$, violating $q$-SDH.

We also tested TLA+ spec for accumulation soundness:

```tla
---------------- MODULE Accumulation ----------------
EXTENDS FiniteSets, Naturals
VARIABLES acc, proofs, challenges

Accumulate(acc, pi, r) == 
    LET C_batch == FoldCommitments(acc.comms, pi.comms, r)
    IN [comms |-> C_batch, z |-> pi.z, y |-> pi.y]

Invariant == \A pi \in proofs: Verify(pi) => VerifyAcc(Accumulate(acc, pi, challenges[pi]))

THEOREM Soundness == Invariant => \A pi \in proofs: Valid(pi)
====================================================
```

Model-checked for $n=3$ with TLC, no counterexample up to $10^6$ states.

### 5.2 Proof of Knowledge Soundness

We work in AGM [10]. Let $A$ be adversary that given SRS $[s^i G_1]_{i=0}^{d}, sG_2$ produces $n$ accepting aggregated proofs for false statement.

**Extractor $E$:**

1. Run $A$ to get $acc$, transcripts $T_i$
2. Fork at challenge $r$, rewind with $r' \neq r$, get second transcript
3. From two linear combinations $\sum r^i C_i$ and $\sum r'^i C_i$, solve for individual $C_i$ via Vandermonde inversion (requires $n$ forks)
4. For each $C_i$, extract polynomial $f_i$ from KZG extractor (follows from $q$-SDH)
5. If any $f_i(z_i) \neq y_i$ but proof accepts, $E$ breaks $q$-SDH by computing $g^{1/(s-z_i)}$

Probability analysis: $\epsilon_E \ge \epsilon_A^2 / (q^2 \cdot n) - \text{negl}$.

Zero-knowledge follows from simulator that replaces commitments with random group elements and programs RO to produce $r$ that makes batch check pass; indistinguishability from KZG HVZK.

## 6 Limitations

- **Trusted setup requirement:** KZG variant inherits Powers-of-Tau toxic waste risk; while mitigated by Ethereum ceremony (80k participants) [6], it is not transparent like IPA. For high-assurance rollups requiring no trusted setup, IPA recursion remains preferable despite larger proofs.
- **Non-native field arithmetic overhead:** BN254 scalar field $r$ operations for base field $q$ EC ops require limb decomposition, 3× blowup in rows. For $n>64$, $k=21$ exceeds memory limits on 32GB machines; GPU MSM (e.g., `zkmetal` [11]) needed.
- **Lookup table cost:** Poseidon S-box range checks via Plookup add $\sim$ 5k rows per hash for $t=3$; alternative `Poseidon2` with degree-4 S-box and internal matrix optimization could reduce to 120 rows but not yet supported in Halo2 gadgets.
- **No IVC support:** Our aggregation requires all $n$ proofs available simultaneously (multi-proof aggregation), not incrementally verifiable computation (IVC) where proofs arrive sequentially. SnarkPack coordination requires Fiat-Shamir challenge over all proofs, preventing streaming [4]. Nova/SuperNova folding [12] would enable IVC but needs R1CS, not PLONKish.
- **Soundness gap:** Security proof in AGM+ROM, not standard model; relies on Poseidon being indifferentiable, which is heuristic for concrete parameters. No formal verification of custom gates in-circuit (would require `halo2` formal spec).
- **Prover centralization:** Aggregation prover needs 22GB RAM for $n=32$, unsuitable for browser proving; requires centralized sequencer, partially defeating decentralization goals for rollups like Taiko which aim for based sequencing.

## 7 Conclusion

We presented a practical construction for zero-knowledge proof aggregation using recursive Halo2 SNARKs with KZG commitments, bridging transparent IPA recursion with pairing-based succinctness for Ethereum rollups. By designing custom PLONKish gates for Poseidon $x^5$ and incomplete EC addition, and employing a KZG batch opening gadget with random linear combination via Poseidon transcript, we achieved aggregation of 32 proofs into a single 1.1KB proof verifiable in 298k gas, a $12.4\times$ saving over naive submission.

The hybrid KZG-IPA approach—using IPA-style folding for commitment combination inside the circuit while deferring pairings to the outer decider—resolves the fundamental tension between recursion friendliness and on-chain efficiency. Empirical evaluation on $k=20$ circuits demonstrates prover overhead $<18\%$ per leaf for moderate $n$, with memory scaling that remains feasible on commodity servers.

Future work includes:

1. **GPU acceleration** of MSM and NTT via `zkmetal` [11] to push $n$ to 256
2. **Poseidon2** migration for $30\%$ fewer constraints
3. **Nova-style folding** for PLONKish to achieve true IVC, enabling streaming aggregation for based rollups
4. **Formal verification** of custom gates in `EasyCrypt` or `Coq` to close AGM gap

The construction is live-compatible with PSE Halo2 KZG fork and Scroll's verifier contract, providing an immediate path to $10\times$ cheaper L1 settlement for ZK-rollups.
