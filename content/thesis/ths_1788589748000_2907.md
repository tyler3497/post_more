## Abstract

This thesis develops a unified formal-verification pipeline for Ethereum smart contracts combining four complementary technologies: (i) the Certora Verification Language (CVL) for machine-checkable rules and invariants over contract state transitions [3][5]; (ii) the KEVM complete executable semantics of the Ethereum Virtual Machine in the K framework — the first fully formal EVM semantics to pass the entire 40,683-test official compliance suite, from which a reference interpreter and verifier are mechanically derived [1]; (iii) symbolic and concolic execution of EVM bytecode using 256-bit bitvector path conditions discharged by SMT solvers, as in tools descended from Oyente and Mythril [6][7]; and (iv) invariant-guided auditing for DeFi protocols, where structural, economic, and access-control invariants prune the symbolic search space and focus verification on solvency, reentrancy-freedom, and oracle consistency. We formalize the soundness relationships between layers and evaluate the approach against large-scale empirical studies [6][8]. No single layer suffices: executable semantics provide ground truth, symbolic execution provides scalable bug-finding, CVL provides intent specification, and invariant-guided auditing provides the economic relevance separating a verified contract from a merely scanned one.

## 1. Introduction

Smart contracts are immutable programs custodying large asset pools, executing without human intervention behind a public adversarial interface. Testing is structurally inadequate for this threat model: a test suite samples finitely many inputs, while attackers explore the full input space — transaction sequences, interleavings with hostile contracts, and manipulation of block environment variables. Formal verification reasons about *all* executions rather than a sampled subset [3].

The field progressed from heuristic bug-finding to rigorous proof. Oyente pioneered symbolic execution of EVM bytecode for vulnerability classes such as reentrancy and transaction-ordering dependence [7]; Mythril generalized this with concolic execution over 256-bit bitvector semantics via Z3 [6][7]. These are *bug finders*: they detect built-in patterns, not arbitrary specifications. KEVM instead defined the EVM itself as a complete executable semantics in K's reachability logic, mechanically deriving interpreters and verifiers [1], with later alternatives such as an executable EVM semantics in Dafny [2]. At the specification layer, the Certora Prover introduced CVL for invariants and parametric transition rules, compiled with contract bytecode into constraints discharged by SMT solvers [3][5].

This thesis unifies these strands into one pipeline and one DeFi auditing methodology. Contributions: (1) a reference architecture with KEVM as ground truth, symbolic execution as triage, and CVL as intent specification, with stated soundness relationships; (2) a CVL rule-engineering methodology with worked examples; (3) a formal treatment of symbolic execution over EVM bytecode and its core trade-offs; (4) an invariant-guided auditing framework for DeFi organizing properties into structural, economic, temporal, and access-control classes; (5) an empirical assessment grounded in the largest published tool evaluations [6][8].

## 2. Background and Related Work

### 2.1 The EVM execution model

The EVM is a quasi-Turing-complete stack machine over 256-bit words. State decomposes into machine state *μ* (program counter, gas, stack, memory) and world state *σ* (balances, storage, code). Execution is gas-metered: every opcode consumes gas and exhaustion deterministically aborts with state revert. Gas is a *semantic* feature, not merely economic — any faithful semantics must model it, since exhaustion changes observable behavior [1]. The Yellow Paper's informal specification contained ambiguities exposed precisely by the attempt to formalize it completely in K [1]: informal specifications of consensus-critical systems hide defects that only executable formalization reveals.

### 2.2 Symbolic execution for EVM bytecode

Oyente (2016) showed symbolic execution is practical for EVM bytecode: unknown inputs (calldata, storage, block parameters) become symbolic variables; explored paths accumulate *path conditions* characterizing driving inputs; an SMT solver decides feasibility and synthesizes concrete witnesses [7]. Mythril added concolic execution, taint analysis, and modular detection modules over 256-bit bitvectors via Z3 [6][7]. Both target *known patterns* (SWC classes: reentrancy SWC-107, integer overflow SWC-101, timestamp dependence SWC-116), not user specifications.

Empirics temper enthusiasm. Durieux et al.'s SmartBugs framework ran nine tools over 47,518 real contracts and 69 annotated vulnerable ones (~428,337 analyses): all tools combined detected only 42% of annotated vulnerabilities, Mythril led single tools at 27%, and 97% of wild contracts were flagged — an enormous false-positive burden [6]. A later large-scale scanner study confirmed weak reentrancy recall on audit datasets [8]. Symbolic execution remains the best automated triage, but pattern-based bug-finding complements rather than substitutes specification-driven verification.

### 2.3 Executable semantics: KEVM and successors

KEVM specifies the complete EVM in K as rewrite rules over a 70+-cell configuration capturing machine state, world state, and execution context [1]:

- **Complete**: all opcodes, gas accounting, memory expansion, and exceptions specified.
- **Executable**: K derives a reference interpreter from the same rules used for reasoning — the unification of execution and logic.
- **Validated**: the derived interpreter passes the full official suite (40,683 tests), the first fully formal EVM interpreter to do so [1].
- **Verifiable**: reachability-logic proof rules over the same semantics yield a program verifier; the authors verified an ERC-20 transfer's functional correctness *and* gas complexity [1].

Later work includes a formal, executable EVM semantics in the verification-friendly language Dafny [2] and applied studies of KEVM-based semantic verification of real contracts, confirming K's decisive advantage: one definition generates parser, interpreter, and verifier [2].

### 2.4 The Certora Prover and CVL

The Certora Prover takes EVM bytecode plus a CVL specification and checks whether *all* executions satisfy it [3]. Bytecode and spec compile to constraints discharged by an SMT portfolio; a satisfying assignment to the negated spec becomes a concrete counterexample trace. CVL offers two styles [5]: **invariants** (state predicates holding at every reachable state, proved inductively over transitions) and **rules** (parametric transition specifications combining pre-state requirements, possibly partially-specified calls, and post-state assertions). Comparative studies identify Certora and the Solidity compiler's SMT checker as the principal Solidity verification tools, with CVL's transition-level expressiveness as its distinguishing strength [5]. Practitioner accounts stress methodology: enumerate state variables, classify functions by privilege and effect, tabulate properties in natural language, then encode in CVL with harnesses and summaries to manage solver complexity [4].

## 3. Methodology

A four-stage pipeline; each stage states its soundness obligation relative to the one below.

**Stage 1 — Ground truth: executable semantics.** Fix *S* (KEVM [1] or the Dafny EVM [2]) as the reference EVM definition. All claims about bytecode behavior are claims about *S*; gas, exceptions, the full opcode set, and the storage/memory hierarchy must be modeled, with official-suite validation as the fidelity evidence [1].

**Stage 2 — Triage: symbolic execution.** Run symbolic/concolic execution over compiled bytecode to (a) cheaply discover concrete counterexamples to candidate invariants and (b) enumerate reachable transition patterns informing specification. Deliberately *unsound both ways*: bounded exploration misses deep paths; coarse environment models yield spurious alarms [6][8]. Output: hypotheses, not proofs.

**Stage 3 — Specification: CVL rule engineering.** Encode intent as CVL invariants and parametric rules, checked against all executions via SMT. Summaries abstract called functions; ghost variables track auxiliary state (e.g., sums over mappings) the contract never stores [3][4].

**Stage 4 — Audit: invariant-guided review.** Organize verification around a protocol-specific invariant taxonomy (Section 4.4). Stage-2 violations become priority audit targets; Stage-3 proofs of economically vacuous properties flag *intent-conformance* gaps — the prover is only as good as the properties fed to it.

> **Theorem (Layered soundness, informal).** Let *S* be an executable EVM semantics and *P* a CVL specification verified over bytecode *B*. If the pipeline's bytecode model soundly abstracts *S* and every summary over-approximates its code in *S*, then every *S*-execution of *B* satisfies *P*. The theorem is *relative*: it transfers trust from the model and summaries, and says nothing about whether *P* captures economic intent.

## 4. Deep Technical Dive

### 4.1 CVL rule engineering: from intent to machine-checked rules

A CVL spec has a `methods` block (signatures, summarization), invariants, and rules. The canonical ERC-20 `transfer` integrity rule is *parametric* — proved for all senders, recipients, amounts:

```cvl
methods {
    function balanceOf(address) external returns (uint256) envfree;
    function totalSupply() external returns (uint256) envfree;
}

rule transferIntegrity(address to, uint256 amount) {
    env e;
    address from = e.msg.sender;

    uint256 fromBalBefore = balanceOf(from);
    uint256 toBalBefore   = balanceOf(to);
    uint256 supplyBefore  = totalSupply();
    require from != to;

    transfer(e, to, amount);

    assert balanceOf(from) == fromBalBefore - amount;
    assert balanceOf(to)   == toBalBefore + amount;
    assert totalSupply()   == supplyBefore;
}
```

The `env e` models the transaction environment; `envfree` marks view functions as pure state readers. `require from != to` excludes self-transfer arithmetic — typical of the case-splitting rule engineering demands. Unsaid: reentrancy (the call is atomic at this abstraction), gas, and callee behavior of `to` if it is a contract — each needs further rules or summaries [3][4].

**Invariants** are proved inductively; the `preserved` block supplies the step:

```cvl
invariant solvency()
    totalAssets() >= totalDebt()
    {
        preserved withdraw(uint256 amount) with (env e) {
            require totalAssets() >= totalDebt();
        }
    }
```

Functions added later without spec updates silently escape the induction — a routine source of coverage gaps [5].

**Ghost state and summaries.** Aggregates auditors need (e.g., Σ balances) are recovered via *ghost variables* updated by hooks on storage writes. *Summaries* replace callee code with pre/postconditions: havoc-everything summaries are sound but weak; precise ones restore provability at manual cost. The Certora white paper names summarization the primary user lever for decomposing solver-overwhelming proofs [3].

**Discipline** (distilled from [4]): (1) enumerate state variables; classify every external function by privilege and state effect; (2) write the natural-language property table *before* CVL; (3) order work: structural invariants, then transition rules, then economic properties; (4) treat each counterexample as bug or missing `require`, and record which; (5) pin summaries and loop bounds for reproducibility.

### 4.2 KEVM: executable semantics as ground truth

In K, a language is a *configuration* plus *rewrite rules*. KEVM's configuration spans 70+ cells; the essential fragment:

```
<k> $PGM </k>                // current computation
<evm>
  <id> ... </id>             // executing account
  <program> ... </program>   // pc -> opcode map
  <pc> ... </pc>             // program counter
  <wordStack> ... </wordStack>
  <localMem> ... </localMem>
  <gas> ... </gas>
  ...
</evm>
```

A representative rule constrains integers to 256-bit words:

```
syntax Int ::= chop(Int) [function]
rule chop(I:Int) => I %Int pow256 requires I <Int 0
rule chop(I:Int) => I          requires I >=Int 0 andBool I <Int pow256
```

`requires` side conditions optimize execution and simplify Z3 queries during symbolic reasoning [1]. Opcodes become rewrite rules: `ADD` pops two words, pushes the modular sum, deducts gas; `SSTORE` updates the storage cell per the gas schedule. Exceptions (out-of-gas, stack underflow, bad jumps) are an explicit mechanism consuming `<k>` until caught — failure modes as first-class reasoning objects [1].

Consequences of executability: (1) **the interpreter is derived, not written** — no drift between spec and implementation; (2) **differential testing is automatic** — the 40,683-test pass is fidelity evidence no paper review can match [1]; (3) **verification is reachability** — proof obligations are reachability claims discharged by the same engine that executes programs, as demonstrated on ERC-20 transfer correctness and gas complexity [1]. In our pipeline KEVM arbitrates disputes: when prover model and symbolic executor disagree on an opcode, the KEVM rule is the tiebreaker.

### 4.3 Symbolic execution of EVM bytecode

Each explored path carries a symbolic state and path condition:

```python
    gas_used: Expr

```

Core modeling decisions, each a soundness/completeness trade-off:

| Decision | Faithful | Common approximation | Cost |
|---|---|---|---|
| Word arithmetic | 256-bit bitvectors, modular | Mathematical integers | Misses wraparound |
| `KECCAK256` | Uninterpreted + injectivity axioms | Fully uninterpreted / concretized | Storage-collision reasoning lost or unsound |
| External calls | Full callee semantics | Havoc returns; arbitrary reentrancy assumed | Cross-contract invariants missed; reentrancy mis-modeled |
| Block env | Symbolic (`TIMESTAMP`, `NUMBER`) | Concrete / bounded | Miner-manipulable logic missed (SWC-116) or explosion |
| Gas | Precise schedule | Ignored | Out-of-gas reverts missed |
| Loops | Bounded unrolling + widening | Small fixed bound | Deep-loop bugs missed |

Concolic execution (Mythril's LASER-SVM) mixes concrete values (simplifying constraints, e.g., hash preimages) with symbolic generality [7]; detection modules match explored states against vulnerability patterns and synthesize witnessing transactions via the solver.

**Path explosion** is the fundamental limiter: each symbolic `JUMPI` doubles the path space; DeFi functions routinely admit thousands of paths, with cross-function sequences multiplying further. Industrial tools use depth-first search, loop bounds, and summaries — and, crucially, *property-directed pruning*: a symbolic executor that knows `totalAssets ≥ totalDebt` discards subtrees incapable of violating it, concentrating solver budget on the economically relevant frontier. That is the technical core of invariant-guided auditing.

### 4.4 Invariant-guided auditing of DeFi protocols

A DeFi protocol is a state machine with economic meaning. Invariant-guided auditing organizes verification around four classes:

**Structural invariants** — accounting identities:
- *Supply conservation*: `totalSupply == Σ balances`; vault share/asset correspondence within rounding (ERC-4626).
- *No phantom value*: every liability-token mint pairs with asset inflow; every burn destroys exactly the redeemed claim.

**Economic invariants** — solvency and pricing:
- *Solvency*: `totalAssets ≥ totalDebt` at every reachable state.
- *Oracle consistency*: price-dependent transitions require `|t_now − t_update| ≤ Δ_max`.
- *Slippage bounds*: AMM swaps satisfy quoted minimums under the pool invariant (e.g., `x·y = k` modulo fees).

**Temporal invariants** — ordering and liveness:
- *Checks-effects-interactions*: state updates precede external calls (reentrancy discipline), checkable as a call-order rule.
- *No read-only reentrancy*: view-function outputs are invariant under reentrant state changes. This class evaded pattern detectors precisely because the attack *writes nothing* [8].

**Access-control invariants** — privilege discipline:
- *Only-owner-mutates-config*; *pause semantics*: no value-moving transition enabled while paused.

**Workflow:** (1) *Elicit* 15–40 invariants from docs and economic design, each with a severity (what loss does violation enable?). (2) *Symbolic triage* with invariants as watch properties — cheap, concrete, severity-prioritized violations. (3) *CVL formalization* with ghost aggregates (e.g., `ghostDonations`, `sumBalances`) and summaries for oracles/tokens. (4) *Adversarial spec review*: for each proven invariant ask how an attacker could violate intent while preserving the formal statement — home of read-only reentrancy, rounding exploits, donation attacks. (5) *Compositional audit*: verify invariants under adversarial composition — arbitrary public-function orderings with flash-loan-funded atomic sequences modeled explicitly.

A quantitative sketch — donation resistance for an ERC-4626-style vault:

```cvl
ghost uint256 ghostDonations; // cumulative direct donations

rule donationResistance(uint256 assets) {
    env e;
    uint256 ppsBefore = pricePerShare();
    donate(e, assets);              // adversary inflates vault, mints no shares
    uint256 ppsAfter = pricePerShare();
    assert ppsAfter <= ppsBefore + MAX_DRIFT,
        "donation cannot inflate share price beyond bound";
}
```

`MAX_DRIFT` derives from virtual-share offsets — a *quantitative* invariant. DeFi questions are rarely "can the price move?" but "by how much, and at what cost to the attacker?" Economic invariants thus pair with *attacker-cost analysis*: manipulation costing more than it yields is not a vulnerability, and the proof must establish the inequality.

## 5. Empirical Results and Formal Arguments

### 5.1 What the tools achieve

| Tool class | Representative | Input | Specification | Soundness | Empirical note |
|---|---|---|---|---|---|
| Symbolic bug-finder | Oyente [7] | Bytecode | Built-in patterns | Unsound (bounded) | Baseline; arithmetic false positives [6] |
| Concolic analyzer | Mythril [7] | Bytecode/Solidity | Built-in + custom | Unsound (bounded) | Best single tool: 27% on annotated set [6] |
| Executable semantics | KEVM [1] | Bytecode | Reachability claims | Sound rel. K rules | 40,683/40,683 official tests |
| Deductive verifier | Certora [3] | Bytecode + CVL | Arbitrary CVL | Sound rel. model + summaries | Real-world proofs; effort dominated by summaries [4] |
| Scanners (meta) | — [8] | Bytecode | Built-in patterns | Unsound | Weak reentrancy recall on audits |

Two structuring arguments. First, *duality*: symbolic executors search `∃ execution. ¬P` (existential, bounded, concrete witness); deductive verifiers establish `∀ executions. P` (universal, unbounded, abstract proof). A counterexample refutes a claimed proof only if feasible in the ground-truth semantics — KEVM's arbiter role (Section 4.2). Second, *specification is the scarce resource*: CVL practice shows invariants and rules, not solver power, bind — real audits verify roughly ten properties per engagement against dozens of state-changing functions, skewing toward easily-stated structural invariants over the economic ones that are expensive to violate [5].

### 5.2 The intent-conformance gap, formally

Let `I` be economic intent (informal), `P` the CVL formalization, `B` the bytecode. Verification gives `B ⊨ P`; the audit must argue adequacy `P ⇒ I`. The gap `P ⇏ I` hosts the costliest DeFi incidents: code provably satisfying specs that miss the economic game. Read-only reentrancy is canonical — no "variable X changes only in F" invariant breaks, because the attack reads stale views without writing.

> **Theorem (Adequacy is not checkable).** No general mechanical procedure decides, given `B` and `P` with `B ⊨ P`, whether `P` captures the designers' economic intent `I`. Adequacy arguments are informal, economic, adversarial — they belong to the audit, not the prover.

This is why the pipeline ends with human auditing, not a green checkmark.

## 6. Limitations and Open Problems

1. **Semantic drift.** Prover bytecode models are not KEVM; discrepancies in gas, precompiles, or new opcodes (`TSTORE`/`TLOAD`, `MCOPY`) can admit proofs failing on-chain. A *verified* translator from prover models to KEVM remains open [1][3].
2. **Summaries as trust anchors.** Every summary is an unverified lemma; unsound ones yield vacuous proofs. Compositional summary verification at scale is open engineering [3][4].
3. **Quantitative/probabilistic properties.** Oracle deviation bounds, MEV races, manipulation cost-vs-profit are probabilistic or quantitative; CVL-style verification is boolean. Integrating these into proof obligations is largely unexplored.
4. **L2 and cross-chain semantics.** KEVM models L1; sequencers and bridges lack comparably complete executable semantics [1].
5. **Specification mining and adequacy.** Auto-proposing candidate invariants (from traces, docs, learning) — and assessing adequacy against intent — stays human-intensive; symbolic triage plus economist-in-the-loop review is the promising pairing.
6. **Upgradeability.** Proxies and governance upgrades mean verified bytecode is not executed bytecode indefinitely; upgrade-path and timelock invariants remain mostly manual.

## 7. Conclusion

Each technology earns its role: **KEVM-style executable semantics** arbitrate all behavioral claims [1][2]; **symbolic/concolic execution** provides scalable, unsound-by-design triage with concrete witnesses [6][7][8]; **CVL rule engineering** turns intent into machine-checked universal claims via invariants, parametric rules, ghost state, and summaries [3][4][5]; **invariant-guided auditing** directs effort at solvency, oracle consistency, reentrancy-freedom, and manipulation-cost bounds — the properties whose violation loses money.

The lesson is modest and load-bearing: *proofs are relative* — to a bytecode model, to summaries, to specification adequacy — and each relativity is managed by a different layer. Together, practiced with this thesis's discipline, they move assurance from pattern-matching toward intent-directed proof — while the adequacy theorem of Section 5.2 keeps us honest about what proof cannot do.
