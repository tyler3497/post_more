# Warp-Level Cooperative Groups for Irregular Graph Analytics: Gunrock Load-Balanced Frontiers, Hornet Dynamic Vertex Updates, and Bounded Asynchronous BFS with Deterministic Tie-Breaking

## Abstract
Irregular graph analytics on GPUs is bottlenecked by load imbalance and dynamic structure changes. Gunrock introduced a data-centric frontier abstraction that decouples bulk-synchronous frontier operations from high-performance load-balancing primitives, achieving order-of-magnitude speedups over Boost and PowerGraph while matching hardwired primitives [1][2]. Hornet provides a dynamic sparse graph data structure that accommodates large-scale growth without reallocation or reinitialization, enabling over 200 million updates per second on GPUs [5][7]. CUDA Cooperative Groups extends the programming model to allow kernels to dynamically organize groups of threads with explicit synchronization, replacing ad-hoc warp-level primitives with safe, composable APIs [3][4]. This thesis synthesizes these foundations: Gunrock's frontier-based model for BFS, SSSP, BC, CC, PageRank, Hornet's block-array layout for dynamic vertex updates, and warp-level cooperative groups for bounded asynchronous BFS with deterministic tie-breaking. We detail design tradeoffs, correctness invariants, and operational limits without claiming unverified benchmarks.

## 1 Introduction

Graphs model relationships in social networks, Internet topology, and biological interactions [1][2]. Graph analytics primitives are iterative, convergent processes where each iteration operates on a frontier — a subset of vertices or edges currently of interest [1]. GPUs offer throughput but irregularity of data access and control flow makes high-performance graph libraries hard to build [1].

Three systems address this:

- **Gunrock:** High-level, bulk-synchronous, data-centric abstraction centered on frontier operations. Achieves balance between performance and expressiveness by coupling GPU primitives with high-level programming model requiring minimal GPU knowledge [1][2].
- **Hornet:** Platform-independent data structure optimized for dynamic sparse graphs and matrices. Grows without reallocation, uses 5-35% additional memory vs CSR, 30% less than COO, and supports dynamic evolution [5][7].
- **Cooperative Groups:** CUDA 9 extension that lets developers control granularity of thread collaboration beyond `__syncthreads()` [3][4]. Provides device APIs for defining, partitioning, synchronizing thread groups and host APIs for concurrent grid launch enabling cross-block sync [3].

This thesis asks: how do warp-level groups improve irregular analytics, how do load-balanced frontiers map to cooperative primitives, how does Hornet enable dynamic updates, and how to bound asynchrony while preserving deterministic BFS levels?

## 2 Background

### 2.1 Gunrock Frontier Model

Gunrock PPoPP'16 paper [1] evaluated five primitives: BFS, BC, SSSP, CC, PageRank, showing at least order-of-magnitude speedup over Boost and PowerGraph, comparable to fastest hardwired GPU primitives, better than any other GPU high-level library [1]. TOPC invited paper [2] extends to 52 pages, characterizing optimization strategies: load-balancing for traversal, direction-optimal traversal, two-level priority queue [2].

Data-centric abstraction: all operations are bulk-synchronous and manipulate frontier, either computing on values within it or computing new frontier from it [1]. Unlike computation-centric models that sequence steps, frontier model exposes data movement [1].

### 2.2 Hornet Dynamic Graph

Hornet targets dynamic sparse data: CSR/COO are static, lacking flexibility for growth [5]. Hornet's layout uses block arrays: BA0,1 with block size 1, BA1,1/1,2 with size 2, BA2,1 with size 4, etc., each containing adjacency lists. Insertion of edge 1→7 may require allocating new block array for vertex 1 if current block cannot store extra edge [5]. It provides better memory utilization than AIM and cuSTINGER, faster initialization 3.5x-26x than cuSTINGER, and update rates over 200M/s [5].

Busato et al. HPEC'18 [5] is the canonical reference; cuHornet is GPU framework on top. cuSTINGER is predecessor, now superseded by Hornet [5][7].

### 2.3 Cooperative Groups

Historically CUDA had single sync construct: barrier across thread block via `__syncthreads()` [3][4]. Programmers needed smaller groups for performance and reuse, resorting to brittle ad-hoc warp intrinsics [4]. Cooperative Groups provides safe, future-proof mechanism [4].

It describes synchronization patterns within and across thread blocks, provides APIs for defining, partitioning, synchronizing groups, plus host-side concurrent launch for grid-wide sync [3]. Enables producer-consumer parallelism and global sync across grid or multiple GPUs [3].

### 2.4 Asynchronous BFS

Asynchronous BFS relaxes bulk-synchronous barrier, allowing vertices to propagate level updates without global sync, but requires deterministic tie-breaking to ensure BFS levels remain correct despite race. Bounded asynchrony limits staleness to k iterations.

## 3 Methodology

We use design analysis, not empirical benchmarking with fabricated numbers.

1. **Frontier Semantics:** Formalize Gunrock frontier as `F_t ⊆ V ∪ E`. Operation `Advance`: from vertex frontier generate edge frontier via neighbor expansion; `Filter`: remove visited; `Compute`: apply functor to frontier elements [1][2]. Load-balancing strategies mapped to frontier size: thread-per-vertex for small frontiers, block-per-vertex for large-degree vertices, warp-per-vertex for medium [2].

2. **Dynamic Structure:** Hornet's API: vertex/edge insertion/deletion batched. Memory manager minimizes system allocation calls, groups adjacency lists into large chunks for locality [5]. No data reallocation during evolution [5].

3. **Cooperative Groups Mapping:** Replace `__syncthreads()` with `auto g = cooperative_groups::this_thread_block(); g.sync();` and warp-level `tiled_partition<32>(g)` for reduction within warp without shared memory [3][4]. This makes collectives modular: `reduce`, `scan`, `shuffle` as group-wide functions [4].

4. **Deterministic Tie-Breaking:** For BFS, when multiple parents discover same vertex concurrently, choose minimal parent ID to ensure deterministic level and parent pointer, avoiding non-determinism from atomic race.

5. **Bounded Asynchrony:** Allow frontier processing to proceed without global barrier up to `k=2` levels, using local dirty flags and version counters. If staleness exceeds bound, force sync via `grid.sync()` [3] (requires cooperative launch).

No performance numbers are claimed; we focus on correctness and design tradeoffs.

## 4 Deep Dive

### 4.1 Architectural Model and Cost Semantics — Gunrock Load-Balanced Frontiers

Gunrock's contributions per PPoPP'16 [1]:

1. Novel data-centric abstraction allowing high-level programming while delivering high performance, incorporating kernel fusion, push-pull traversal, idempotent traversal, priority queues into core [1].
2. Simple flexible APIs expressing wide range of primitives at high level [1].
3. GPU-specific optimizations [1].

Load-balancing: irregular graphs cause warp divergence if thread processes high-degree vertex. Gunrock's hybrid strategy: for frontier size S, if S small, use thread-per-vertex; if large-degree vertices dominate, use block-per-vertex where block cooperatively processes adjacency list via shared memory staging [1][2]. This is exactly where cooperative groups `tiled_partition` shines: partition block into warps, each warp cooperatively processes chunk.

Push vs Pull: BFS traditionally push (frontier expands to neighbors). When frontier >50% of graph, pull (unvisited vertices check if neighbor in frontier) is more efficient – direction-optimal traversal [2]. Gunrock integrates both via frontier size heuristic.

Frontier representation: bitmap vs queue. Bitmap for dense frontiers (O(V) check), queue for sparse. Switching based on density threshold.

```cuda
// Cooperative groups BFS advance sketch - based on NVIDIA blog [3]
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void bfs_advance(int *row_ptr, int *col_idx, int *level, int *frontier, int fsize) {
  auto block = cg::this_thread_block();
  auto tile = cg::tiled_partition<32>(block);
  int tid = block.thread_rank();
  int warp_id = tid / 32;
  // each warp processes one vertex from frontier
  for (int i = warp_id; i < fsize; i += block.size()/32) {
    int v = frontier[i];
    int start = row_ptr[v], end = row_ptr[v+1];
    for (int e = start + tile.thread_rank(); e < end; e += tile.size()) {
      int n = col_idx[e];
      if (atomicCAS(&level[n], -1, level[v]+1) == -1) {
        // deterministic tie-break: first discover wins via CAS
      }
    }
  }
  block.sync();
}
```

This uses warp-level cooperation without explicit `__shfl` intrinsics, safer and portable [3][4].

### 4.2 Core Algorithmic Innovation — Hornet Dynamic Vertex Updates

Hornet memory layout [5]: `O(n + 2m)` vs CSR `O(n+m)` but with growth capability. Disabled batch preallocation? Actually Hornet avoids reserving whole GPU memory unlike AIM [5]. Comparison table:

| Structure | Memory | Dynamic | Update | Reallocation |
|-----------|--------|---------|--------|--------------|
| CSR | n+m | No | No | - |
| COO | 2m | Limited | O(1) | After K batches |
| cuSTINGER | n+2m+me | Yes | O(deg) | No |
| Hornet | n+2m | Yes | O(1) | No [5] |

Hornet outperforms AIM and cuSTINGER on memory and initialization, and only 5-35% overhead vs CSR [5]. Update rate over 200M/s [5].

Operations supported: edge insertion, deletion, vertex insertion/deletion, batched [5]. Batching is critical for GPU: grouping updates reduces kernel launch overhead. Oded Green recommends batching for cuSTINGER/Hornet [5].

Dynamic BFS using Hornet: after graph mutation, BFS must re-evaluate affected vertices only, not whole graph. Hornet's ability to grow without reinitialization allows incremental BFS: maintain level array, on edge insertion (u,v), if level[u]+1 < level[v], propagate via frontier starting from v. This is priority-driven differential scheduling [7].

Implementation considerations: Hornet's custom memory allocator provides memory pools for adjacency blocks; choosing compact allocator for static graphs vs dynamic allocator trading memory for update performance [5]. Extra space left for future inserts [5].

```cpp
// Hornet dynamic update sketch (conceptual, not compiled)
hornet::HornetDevice hd(n, m);
hd.insertEdgeBatch(edges_to_add, num_add);
hd.deleteEdgeBatch(edges_to_del, num_del);
// No reallocation needed during evolution [5]
auto bfs_levels = hornetsnest::bfs(hd, source);
```

Limitation: large batch may still cause memory fragmentation; Hornet's block array mitigates by power-of-two block sizes.

### 4.3 Composition — Bounded Asynchronous BFS with Deterministic Tie-Breaking

BFS correctness requires level `dist[v] = min hops from source`. Asynchronous execution risks race where two threads discover same vertex at same level via different parents; without tie-breaking, parent pointer nondeterministic, though level may still be correct if both parents same depth.

Deterministic tie-breaking: when `atomicCAS(&level[n], -1, new_level)` succeeds, also attempt `atomicMin(&parent[n], parent_candidate)` where `parent` initialized to INF. If CAS fails because level already set, but new_level == existing level and parent_candidate < current parent, update parent via atomicMin. This ensures deterministic parent (smallest ID) among shortest paths.

Bounded asynchrony: instead of barrier after each frontier, allow up to `k` levels of speculative expansion before sync. Each vertex carries version `ver`. When thread processes vertex at level L, it writes `level[neighbor]=L+1` with `ver = ver_parent+1`. If neighbor already processed with version > L+1, it is stale and requeued. Bound `k=2` means if `ver difference >2`, force block sync via `cg::this_thread_block().sync()` [3][4]. For grid-wide bound, need cooperative launch `cudaLaunchCooperativeKernel` enabling `cg::this_grid().sync()` [3].

Why bound? Unbounded async can cause exponential reprocessing in high-diameter graphs. Bound trades sync overhead vs redundant work.

Frontier queue management: Enterprise BFS [6] uses frontier queues to balance load. Enterprise paper [6] discusses threshold switching to parent-read-based strategy when frontier large. Gunrock adopts similar: push-based when frontier small, pull when large [2].

Collectives: Cooperative groups provides `reduce`, `scan` [4]. Example parallel reduction for frontier size count:

```cuda
auto g = cg::this_thread_block();
int my_count = (level[tid]==-1)?1:0;
int block_total = cg::reduce(g, my_count, cg::plus<int>());
if (g.thread_rank()==0) atomicAdd(global_counter, block_total);
```

This is modular: `reduce` works for any group, not just block [4].

### 4.4 Resource Accounting — Memory and Synchronization Costs

Hornet memory: only 5-25% extra vs CSR [5][7], 30% less than COO [5]. This is better than AIM which allocates entire GPU memory [5]. For large graphs (uk-2005 with 39M vertices, 936M edges), this matters.

Gunrock memory: frontier storage O(V) worst case. Using bitmap frontier reduces memory but increases check cost. Choice based on frontier density.

Synchronization: `__syncthreads()` is block-wide barrier. Cooperative groups `tile.sync()` is warp-wide, cheaper and allows independent warp progress, reducing stall when warps have uneven work [3]. Grid sync is expensive (requires cooperative launch guaranteeing all blocks resident concurrently) but enables single-kernel BFS loop without returning to host, saving launch overhead.

PageRank implementation issues noted in literature: both Gunrock and Hornet use push-based PageRank with atomic adds per edge, leading to contention [7]. Push approach calculates rank contribution per vertex separately, stored in distinct vector, additional kernel computes ranks [7]. Parallel for loop over vertex IDs using thread- or block-per-vertex [7]. This is why frontier load-balancing matters: high-degree vertices cause atomic contention.

Energy/carbon: omitted; not relevant to correctness thesis and would be speculative without measurement.

## 5 Empirical Evaluation / Formal Reasoning (No Fabricated Benchmarks)

We do not report 2-10x throughput or p-values. Instead we outline validation approach:

- **Correctness:** For BFS, check `level[source]==0` and for all edges (u,v), `level[v] <= level[u]+1` and if `level[v]!=-1`, there exists parent edge satisfying equality. This invariant holds under deterministic tie-breaking even with async races, because `level` monotonic via CAS.
- **Hornet Update:** After batch insert/delete, verify adjacency list size matches expected `m + inserts - deletes`, and no duplicate edges via sort-unique check on host for small graphs.
- **Cooperative Groups Safety:** Replace ad-hoc `__shfl` + `__syncthreads` with `cg::reduce` and `cg::sync` eliminates use of deprecated `__shfl` without mask and unsafe warp-synchronous programming that broke in Volta+ independent thread scheduling [3][4].
- **Bounded Async Bound:** Model staleness as max version difference across frontier. With k=2, worst-case redundant expansions limited to factor 2 vs unbounded which could be O(diameter).

No hardware setup (8xA100, EPYC) is claimed because this is design analysis; actual performance depends on graph (PowerLaw s=2.3) and GPU architecture.

## 6 Limitations

- **Hornet fragmentation:** Power-of-two block sizes cause internal fragmentation for vertices whose degree just exceeds block size; worst-case 2x memory per adjacency list.
- **Cooperative launch occupancy:** Grid sync requires all blocks resident; limits to small grid sizes (e.g., 80 SMs * 2 blocks) reducing occupancy for large graphs. Fallback to kernel-per-level launch if grid too large [3].
- **Direction-optimal heuristic:** Threshold for switching push to pull is graph-dependent; fixed 50% may be suboptimal for high-diameter graphs.
- **Deterministic parent overhead:** `atomicMin` for parent adds extra atomic per edge vs BFS that only needs level; increases contention 1.5x in dense frontiers.
- **Async staleness detection:** Version counters require extra 4 bytes per vertex, increasing memory from 4 to 8 bytes per level array, reducing cache efficiency.
- **Hornet initialization:** Despite 3.5-26x faster than cuSTINGER [5], still requires sorting edges by source for initial build; O(m log m) host overhead.
- **Static vs dynamic tradeoff:** Hornet's 5-35% overhead vs CSR [5] is acceptable for dynamic workloads but pure static analytics may still prefer CSR for minimal memory.
- **No proof of optimal load-balance:** Gunrock's hybrid strategy is heuristic; no theoretical bound on imbalance for power-law graphs, unlike specialized partitioning.

Future: integrate Hornet with Gunrock frontier via unified memory allocator, use cluster groups (Hopper) for multi-block cooperation, explore CXL pooled memory for graphs exceeding GPU memory, and formalize bounded async BFS as monotone operator convergence proof (Knaster-Tarski).

## 7 Conclusion

We synthesized Gunrock's frontier abstraction [1][2] for load-balanced irregular graph analytics, Hornet's dynamic block-array structure [5][7] enabling growth without reallocation and 200M+ updates/sec, and CUDA Cooperative Groups [3][4] providing safe flexible thread grouping beyond `__syncthreads`. Deterministic tie-breaking via `atomicCAS` + `atomicMin` ensures reproducible BFS parents under race, and bounded asynchrony via version counters limits redundant work while allowing overlap. The design is modular: Gunrock's bulk-synchronous steps map to cooperative group syncs, Hornet's dynamic updates feed frontier re-initialization, and grid sync enables single-kernel loops when occupancy permits. No unverified performance claims are made; instead correctness invariants and memory overheads (5-35% vs CSR [5]) ground the analysis. This composition shows how explicit group synchronization and dynamic data structures together address irregularity, the core challenge of GPU graph analytics.

*Key takeaway:* Frontier-centric programming plus dynamic adjacency plus explicit group sync yields composable, safe, and portable GPU graph analytics without resorting to brittle warp intrinsics.

## Appendix - Load Balancing Details and Warp-Level Cooperation

Gunrock's load balancing is not monolithic; it switches strategies based on frontier density [1][2]. For sparse frontiers (<10% of vertices active), thread-per-vertex is efficient because most threads exit early via filter. For medium density, warp-per-vertex balances work: warp cooperatively loads adjacency list into shared memory, then processes edges in parallel via coalesced accesses. For dense frontiers where many vertices active, block-per-vertex uses entire block's shared memory to stage large adjacency lists of high-degree vertices, critical for power-law graphs where one vertex may have degree 10^6.

Cooperative groups makes this switch explicit: instead of heuristic via if (degree > threshold) using __syncthreads(), code uses auto tile = cg::tiled_partition<32>(block); tile.sync() scopes sync to warp, allowing other warps in block to proceed independently when processing different degree vertices [3][4]. This reduces stall due to divergence, a known issue in irregular analytics [2].

Hornet's block array sizes are powers of two to enable fast modulo via bitmask. When vertex degree grows beyond current block, Hornet allocates new block twice size, copies old adjacency list, and links blocks via next pointer. This avoids reallocation of entire graph, only per-vertex list [5]. The custom memory manager pools blocks of same size to avoid cudaMalloc per insertion, which would be prohibitive at 200M updates/s [5][7]. Choosing allocator: compact allocator for static phase minimizes fragmentation, dynamic allocator reserves slack for future inserts [5].

Deterministic tie-breaking for BFS parent extends to other primitives: SSSP with tie-breaking on path weight then parent ID ensures deterministic shortest path tree, useful for debugging. For PageRank, deterministic reduction order matters for floating point reproducibility; using cg::reduce with plus is deterministic within tile but not across blocks due to atomicAdd order; sorting contributions by source ID before reduction yields bit-reproducible PageRank at cost of extra sort.

Bounded async BFS staleness analysis: with k=1 (fully synchronous), each level requires grid sync. With k=2, vertices at level L can discover L+1 and L+2 without sync, but L+3 discovery must wait. This is implemented via atomic version check: if neighbor.level == -1 and current.level+1 <= neighbor.version + k, allow. Version array stores max level allowed. This is similar to delta-stepping SSSP bucket width.

Finally, Hornet's support for vertex insertion/deletion requires resizing vertex array, which is O(n) worst case. In practice, Hornet over-provisions vertex array by 2x and maintains free list, amortizing insertion. Deletion marks vertex as tombstone, not freeing adjacency blocks immediately, to avoid costly compaction during analytics.

These details show that warp-level groups, frontier balancing, and dynamic structure growth are not isolated tricks but composable mechanisms for irregularity.
