# Recursive Folding for Scalable ZK Rollups: Unifying Nova IVC, Plonk, and Halo2 under Modern Folding Schemes

## Abstract
The shift from pairing-based recursion to folding-based Incrementally Verifiable Computation (IVC) has redefined the economics of ZK rollups. Nova showed that verifying a proof inside a circuit need not require a full SNARK verifier: a non-interactive folding scheme (NIFS) can reduce two R1CS instances into one with a single random challenge and one multi-scalar multiplication (MSM) [1][2]. HyperNova generalized folding to customizable constraint systems (CCS) covering Plonkish, R1CS, and AIR simultaneously, achieving optimal prover MSM cost and a la carte execution for VM steps [3]. Halo introduced accumulation schemes that amortize verification over many proofs on a cycle of elliptic curves without trusted setup [5], and Halo2 married that accumulator with Plonk's efficient arithmetization [8]. Plonky2 replaced KZG with FRI over the Goldilocks field, yielding ~170ms recursion on commodity hardware [6][7], while Goblin Plonk decoupled proving and verification cycles to avoid curve bouncing [9]. This thesis synthesizes these threads into a single framework for recursive rollups: how folding schemes enable O(1) L1 verification, O(λ) memory, and horizontal prover scaling, enabling 10k-transaction batches with instant finality.

## 1. Introduction
ZK rollups post a state root and a validity proof to L1. Without recursion, L1 still verifies one proof per batch, linear in batch count. Recursive rollups verify proofs inside proofs, collapsing N batches into one supernatant proof. Early recursion used Groth16 on a two-cycle of BN254/BW6-761, incurring ~10k constraints for the verifier and requiring a universal trusted setup [10].

Nova's insight: you do not need to verify at each step. Defer verification by folding [1]. At step i, the prover holds a running instance U_i and a step instance u_i. NIFS.P produces a cross-term T and folds: U_{i+1} = U_i + r * u_i + r^2? No, for relaxed R1CS: error vector E updated via r·T [1][4]. Only at the final step does a compressed SNARK (Spartan) wrap U_n into a succinct proof π. The verifier circuit is ~10k gates, constant-sized, and prover work per step is dominated by two MSMs.

Contributions:
- Formalize relaxed R1CS, NIFS, and CCS folding.
- Contrast accumulation (Halo) vs folding (Nova) vs lazy recursion (Goblin Plonk).
- Map each to ZK rollup architectures: Polygon Zero's Plonky2 recursion, AETH's Halo2+Nova on Solana, and zkSync's Gateway aggregation [10].
- Benchmarks from nova-bench: Nova memory ~1.6GB constant vs Halo2 KZG 32GB at k=1000 due to SRS growth.

## 2. Preliminaries

### 2.1 ZK Rollup Pipeline
Sequencer → Executor → Prover → L1 Verifier Contract. Proofs are PLONK/KZG or STARK/FRI. Data availability is separate. Finality is instant after proof acceptance, unlike optimistic 7-day windows [10].

### 2.2 IVC
Definition: Let F be a nondeterministic circuit. IVC proves z_n = F^{(n)}(z_0) by producing π_i at each step proving knowledge of witness w_i and correctness of π_{i-1} verification inside F'. Formal construction in [1] §4, augmented circuit that hashes vkNIFS,i,z0,zi,U.

### 2.3 Arithmetizations
- **R1CS:** (A·z)∘(B·z)=C·z. Simple but wastes constraints for lookups.
- **Relaxed R1CS:** Adds error vector E and scalar u: A z ∘ B z = u·C z + E. Folding-closed.
- **Plonkish (Halo2):** Columns = Lagrange basis over 2^k roots. Rows are instances. Custom gates, permutation argument for equality, lookup argument for range checks. More expressive → 5–10× fewer rows vs R1CS for hash [8].
- **CCS:** superstructure with 2^? matrices, includes R1CS/Plonk/AIR as special cases [3].

## 3. Folding Schemes: Core Primitive
Folding scheme is weaker than SNARK: public reduction of two instances (U1,W1),(U2,W2) → (U,W) such that U satisfiable ⇒ both U1,U2 satisfiable (knowledge-sound). Non-interactive via Fiat-Shamir. Instance size equal to circuit size, not proof size. T is the crucial cross-term for zero-knowledge.

For relaxed R1CS:
Given U=(E,u,W,x) and u1, sample r= Hash(vk,E...), compute T = A Z1∘B Z2 + A Z2∘B Z1 - u1 C Z2 - u2 C Z1. Then E' = E1 + r·T + r^2·E2. Witness Z' = Z1+ r·Z2 [1][4]. Cost: 2 MSMs to commit E', W'.

Optimality: HyperNova proves single MSM of size = #variables when using KZG/MSM commitments [3]. Folding multiple instances at once yields PCD friendly tree folding.

Zero-knowledge for free: Fold randomization witness + random r makes IVC proofs randomized without ZK SNARK at each step [3].

## 4. Nova, HyperNova, and CycleFold
Nova constructs IVC from NIFS for relaxed R1CS + Spartan SNARK. Applications: Rollups, VDFs, succinct blockchains, EVM/RISC-V proofs over two-curve cycle (Pallas/Vesta where base field of one = scalar field of other, enabling native verification) [2].

Limitation: Second-circuit step F uniform. For VMs where each step invokes different opcode circuit (e.g., ADD vs MUL vs KECCAK), Nova proves the super-circuit (max cost). HyperNova solves a la carte: CCS allows different shapes per step; prover cost proportional only to invoked instruction [3]. Second, HyperNova scheme folds all gates including high-degree custom gates without extra overhead.

CycleFold: General technique to instantiate folding over curve cycles without bespoke field emulation, applicable to all folding arguments [3].

Benchmarks [privacy-ethereum/nova-bench]: At SHA256 recursive hashing, k=10000 steps, Nova seq 265s vs Halo2 KZG 389s, with 1.6GB vs 245GB RAM. Parallel Nova (PoC) 226s but OOM at larger k due to software bug [sources 2]. Folding's win is memory efficiency and constant recursion overhead (~10k constraints) vs Plonk verifier (~2 pairing checks expressed as ~100k constraints when emulated).

## 5. Halo and Halo2: Accumulation
Halo (2019) introduced nested amortization: instead of fully verifying proof inside circuit, accumulate verification equations into an accumulator; final check is expensive once [5]. No trusted setup, uses inner product argument (IPA) accumulator. Cycle of curves avoids field emulation: prove on Pallas (Fp scalar Fq) → verify Fq arithmetic natively in Vesta circuit where scalar = Fq [source 5].

Halo2 = Halo accumulation + Plonk arithmetization [8]. Adds fixed/advice/instance columns, selector polynomials, vanishing argument over multiple columns, multipoint opening proof. Recursion via IPA: each recursive prover adds ~120k constraints (400 native field group ops × 300 constraints each) [source 4]. Deployed in Zcash Orchard 2021 as first production transparent recursive system.

Difference vs Nova: Halo accumulates *proofs*, Nova folds *instances*. Folding is cheaper prover (1 MSM vs IPA's O(log n) group ops inside circuit). Halo2 prover time < Nova for Plonkish-native circuits with lookups (SHA256 2.5s vs 19s at k=100 in bench) due to lookup-optimized custom gates.

## 6. Plonk, Plonky2, Plonky3, Goblin Plonk
Plonk uses KZG (univ trusted setup). ~6-10 polynomials committed, opening at ζ via 3 pairings [9]. Batched openings keep verifier O(1). Recursion unfriendly because KZG verification needs pairing-friendly curve (BN254) whose field arithmetic is expensive in-circuit on that same curve.

Plonky2 breakthrough: FRI commitment over 64-bit Goldilocks field (p = 2^64-2^32+1). Field ops are extremely fast on x86 (no big-int). Can express many wires per custom gate for recursion-optimized circuits. Proof size larger (800B vs 192B Groth16) but recursion 100× faster: 170ms on MacBook Pro vs 60s prior Halo on Ethereum [6][7]. Yet FRI proofs big for L1 (expensive calldata), so Plonky2 → KZG wrapper for Ethereum proof size.

Plonky3 (2024) generalized Plonky2 into toolkit for ZK VMs, MIT/Apache [source 3].

Goblin Plonk: lazy recursion – avoid bouncing between cycles at each layer. If prover is constrained but verifier tolerates larger final proof (rollup prover feeding into L1 prover), batch layers of recursion on same curve, then single switch. Ideal for ZK rollup: user proofs recursively aggregated client-side (Goblin, large), rollup prover (resourceful) compresses into small SNARK [9].

## 7. Systemization for Recursive Rollups
### 7.1 Recursive Rollup Definition
Proof verifying two batch proofs can verify other batch proofs recursively. Final L1 proof summarizes validity of vast tx count, L1 verifies one proof [encrypthos definition]. Many implementations use binary folding tree height log N: ~960 bytes per aggregated Halo2 proof in demo [source aggregation pipeline].

### 7.2 Case Studies
- **Polygon Zero (Mir):** Generates proofs for all txs in batch simultaneously, rolls up via Plonky2 recursion, 0.17s recursion, 3k tx/block, consumer laptop prover in 0.3s, decentralized via recursive horizontal scaling [Alchemy docs].
- **AETH on Solana:** Stack: libp2p gossipsub + Halo2 + Nova folding + GPU prover marketplace bidding + VRF MEV-resistant sequencer. Prover pays 40% fee. Nova folding compresses t ECDSA batch, but naive folding loses consistency of which signatures proven; must anchor u.x = hash(vk,i,z0,zi,U) [journal.hep paper].
- **ZKStack Gateway:** Not typical rollup recursion but cross-chain: ZKChain's BatchRoot → FullRoot → ChainRoot → AggregatedRoot via merkle path manipulation index + 2^N trick for Gateway final fullRoot = hash(LocalLogsRoot,R aggregated) [10]. Allows consistent Rollup → Settlement communication and scalable cross-chain proof.

### 7.3 Design Space
| Dimension | Nova/HyperNova | Halo2 IPA | Plonky2 FRI | Goblin Plonk |
|---|---|---|---|---|
| No trusted setup | Yes (discrete log) | Yes | Yes | Yes (with KZG wrapper optional) |
| Arithmetization | R1CS/CCS | Plonkish | Plonkish Goldilocks | Plonkish BN254 |
| Per-step prover | 1 MSM optimal | O(log n) group ops | O(n log n) FRI | Lazy batch |
| Verifier circuit | ~10k gates | ~120k constraints | ~15k gates (many wires) | Large intermediate |
| Best for | EVM/RISC-V IVC | Privacy circuits with lookups | Commodity hardware prover | User-side recursion → server compression |

## 8. Security and Costs
Knowledge soundness requires non-malleable commitment + Fiat-Shamir random oracle heavy? Nova relies on DLOG over cycle. Halo2 KZG requires powers-of-tau. FRI transparent (CRHF). All IVC constructions need extra assumptions §4.2 [1] inherited by SNARK wrapper.

Cycle security: Pasta curves half size (255-bit) vs BN254 254-bit, comparable ~128-bit security. No pairing → quantum-resistant-ish vs IPA (not STARK-FRI-level resistance).

Gas: KZG proof 192-768B cheap CALLDATA (~4k gas for Groth16 2 pairings) vs FRI 800B-45KB higher but compress via aggregation reduces L1 calls to 1 per many batches.

## 9. Limitations and Open Problems
- Sangria/PastaVM: folding scheme for Plonkish custom gates natively, not via R1CS translation that loses lookup benefit. Halo2 benchmark win at SHA256 shows R1CS vs Plonkish gap significant [bench comments].
- Non-uniform IVC a la carte cost proven in HyperNova but concrete EVM opcode table (via Miden VM) still heavy.
- Memory OOM parallel Nova PoC needs fix.
- Batch integrity issue: folding batch not binding to claimed ECDSA instances without hash anchor (ECDSA folding critique). Must include merkle root of signatures in public input.
- Cycle vs single-curve: Goblin's large intermediate proofs problematic for light clients.

## 10. Conclusion
Folding turned recursion from heavy verifier-circuit problem into MSM-bound accumulator. For recursive rollups, that matters: proving 10k chained blocks previously needed 23 powers of tau (~9GB SRS, linear growth, infeasible) [bench], now 1.6GB constant. Combined with Plonk's custom gates and FRI's Goldilocks speed, modern stacks can generate recursion on mobile-grade hardware, enabling decentralized proving marketplace and instant finality. Future is Hybrid: Goblin-style client-side folding over Goldilocks for latency, Nova/HyperNova CCS for state-machine steps, single KZG pairings wrapper for Ethereum L1 economy, with Gateway aggregation indexing trick for cross-chain trees.
