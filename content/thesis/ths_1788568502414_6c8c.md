# Securing the Software Supply Chain: SLSA Provenance, Sigstore Keyless Signing, in-toto Attestation Layouts, and Reproducible Builds

## Abstract

Modern software is assembled, not written: a typical application transitively depends on thousands of open-source packages, container base images, and build tools, any one of which is a vector for compromise. This thesis presents a systematic treatment of software supply chain security grounded in four complementary mechanisms — SLSA (Supply-chain Levels for Software Artifacts) provenance attestations [1], in-toto supply-chain layouts [2], Sigstore keyless signing with certificate transparency [3,5], and reproducible builds [4] — situated within the NIST Secure Software Development Framework [6]. We formalize the canonical threat model of the SLSA specification (threats A–H), derive graded security levels from concrete builder properties (scripted, hosted, hermetic, two-party review), and show how provenance attestation, functionary-signed in-toto layouts, and Fulcio/Rekor keyless trust anchors compose into an end-to-end integrity argument. We analyze adoption data from major package ecosystems, quantify the cost of hermetic reproducible builds, and identify open problems including first-party key recovery, hermeticity economics, and policy-distribution trust. Our conclusion is that verifiable provenance, not provenance alone, is the necessary condition for software integrity at scale.

## 1. Introduction

The 2020 SolarWinds Orion compromise — adversaries injecting malicious code into a legitimate build pipeline and distributing trojanized updates to roughly 18,000 customers — and the dependency-confusion attack class, in which namespace-resolution ambiguity routes builds to adversary-controlled packages, share a root cause: consumers of software artifacts generally cannot determine *who built* an artifact, *from what inputs*, *on what infrastructure*, or *whether the received artifact matches the producer's intent* [1,6].

This thesis develops a unified technical treatment of the mechanisms that answer these questions. Four interlocking ideas structure the field:

- **SLSA** (Supply-chain Levels for Software Artifacts) defines graded security levels and a provenance attestation format binding artifacts to their builders and materials [1].
- **in-toto** provides a framework of *layouts*: signed, threshold-quorum policy documents describing every step of the supply chain, verified by inspecting functionary-signed link metadata [2].
- **Sigstore** supplies keyless code signing: ephemeral keys bound to short-lived certificates issued by Fulcio, with all signatures recorded in the append-only Rekor transparency log, authenticated via OpenID Connect identity rather than long-lived key custody [3,5].
- **Reproducible builds** make the build function deterministic, so independent parties can verify that a binary derives from claimed source [4].


## 2. Background and Related Work

### 2.1 A taxonomy of supply-chain attacks

Supply-chain compromises partition naturally along the axis of *where* in the pipeline the adversary injects malicious effect. We adopt the following taxonomy, widely used in the literature and reflected in the SLSA threat model [1]:

1. **Source tampering.** Direct modification of source repositories (credential theft, malicious pull requests, compromised maintainer accounts). The 2022 compromise of the `ctx` and `phpass` PyPI packages via maintainer credential reuse is representative.

2. **Build-system compromise.** Subversion of the build environment itself so that benign source yields malicious artifacts — the SolarWinds pattern. Because the build executes with ambient authority over its outputs, this class defeats source-only review.

3. **Dependency confusion / substitution.** Exploiting namespace resolution to substitute attacker artifacts for legitimate internal dependencies at resolution time.

4. **Artifact tampering in transit or at rest.** Modification of built artifacts between the builder and the consumer: registry compromise, CDN poisoning, or mirror manipulation.

5. **Toolchain compromise.** Subversion of compilers or build tools themselves (the *trusting trust* attack), where even audited source produces compromised binaries through a compromised compiler.


> **Theorem: (Integrity decomposition).** Let *A* be an artifact, *S* its claimed source, *B* its builder, and *P* the build procedure. Consumer confidence in *A* decomposes into four independent claims: (i) *S* is authentic source (source integrity); (ii) *P(S) = A* deterministically (build integrity); (iii) *P* executed on trusted infrastructure (builder integrity); (iv) the binding *S → A* is attested by an accountable identity (provenance integrity). No single mechanism establishes all four.

### 2.3 The SLSA threat model (threats A–H)

The SLSA specification [1] enumerates eight threats against the software supply chain:

| ID | Threat | Mitigated by |
|----|--------|----------------|
| A | Artifact publication tampering | Provenance + signing |
| B | Source control tampering | Two-person review, branch protection |
| C | Source platform compromise | Hardened source platform |
| D | Dependency tampering | Hermetic builds, dependency pinning |
| E | Build platform compromise | Hardened / ephemeral builders |
| F | External parameter tampering | Non-falsifiable provenance |
| G | Dependency service compromise | Hermetic builds, vendored deps |
| H | Builder control compromise | Two-party review, provenance |

SLSA levels address primarily threats **A, E, F, H** (build integrity), while SSDF practices [6] and in-toto layouts [2] extend coverage to source and dependency threats **B–D, G**.

## 3. Methodology


We model a supply chain as a directed acyclic graph of *steps*, each step *s* mapping *materials* *M(s)* to *products* *P(s)* under the authority of a *functionary* set *F(s)*. An *attestation* is a signed statement binding (*s*, *M(s)*, *P(s)*, *F(s)*, *env*) for build environment *env*. Verification is a predicate *Verify(policy, attestations, artifact)* → {accept, reject}.

```python
# Simplified model of in-toto-style verification (illustrative)
def verify_layout(layout, links, artifact):
    # 1. layout signature must meet threshold over project-owner keys
    assert threshold_verify(layout, layout.owner_keys, layout.threshold)
    for step in layout.steps:
        # 2. each step's link metadata must meet its functionary threshold
        step_links = [l for l in links if l.step == step.name]
        assert threshold_verify(step_links, step.authorized_keys, step.threshold)
        # 3. artifact-flow: products of step i must equal materials of step i+1
        assert materials_match_products(step, links)
    # 4. inspections re-derive expected properties from the artifact itself
    return all(run_inspection(i, artifact) for i in layout.inspections)
```

## 4. Deep Dive

### 4.1 SLSA levels and the provenance attestation

SLSA defines four build levels [1]. **Level 1** requires scripted builds with provenance recording the build definition — documentation, not security. **Level 2** requires a *hosted* build platform generating signed provenance, so consumers can verify the builder's identity; this defeats casual artifact substitution (threat A). **Level 3** hardens the platform: builders run on hardened, ephemeral infrastructure with non-falsifiable provenance, defeating build-platform compromise (threat E) and parameter tampering (threat F) short of a full platform breach. **Level 4**, the highest, adds **hermetic builds** (no network access; all dependencies declared and fetched by a trusted control plane) and **two-party review** of all changes, addressing dependency threats D/G and insider threat H.

The SLSA *provenance* attestation is the evidentiary core. Version 1.0 models provenance as an in-toto-style attestation with three parts [1]:

- **`builder`**: the identity of the build platform (e.g., a specific GitHub Actions workflow at a pinned version), authenticated so consumers can apply policy such as *"accept only artifacts built by workflow X"*.
- **`buildType` / `buildDefinition`**: the build recipe and its *resolved* external parameters — every input the build actually consumed, preventing parameter-substitution attacks (threat F).
- **`materials`**: the complete list of inputs with cryptographic digests, and the subject artifacts produced.

> **Theorem: (Provenance soundness).** If a builder at SLSA Level 3+ emits provenance *P* for artifact *A*, and *Verify* accepts *P* under a policy naming the expected builder identity and source digests, then *A* was produced by that builder from those materials, unless the builder platform itself is compromised. Hermeticity (Level 4) additionally guarantees that no undeclared network-fetched input influenced *A*.


### 4.2 in-toto layouts: steps, functionaries, inspections, and thresholds

Where SLSA attests the final build, **in-toto** [2] models the *entire* chain. The project owner authors a *layout*: a signed document declaring an ordered set of *steps* (e.g., `fetch`, `build`, `package`, `deploy`), each naming the *functionaries* authorized to perform it (by public key) and a *threshold* *t-of-n* of required signatures. Each functionary, upon completing its step, emits signed *link metadata* recording the step name, materials (input hashes), products (output hashes), command, and environment.

*Inspections* are the distinctive in-toto primitive: verification-time commands executed by the *verifier* against the delivered artifact — e.g., "unpack the tarball and assert it contains no setuid binaries" — whose results must match expectations in the layout. Inspections close the gap between *what functionaries claim* and *what the artifact is*.

Threshold signing provides Byzantine-style resilience: a layout requiring 2-of-3 release-engineer signatures tolerates one compromised or unavailable key without either halting releases or permitting unilateral malicious release. Key rotation is handled by layout re-signing — itself a threshold operation — so no single keyholder can unilaterally rewrite policy.

```yaml
# Illustrative in-toto layout fragment
steps:
  - name: build
    expected_materials: [["MATCH", "src/*", "WITH", "PRODUCTS", "FROM", "fetch"]]
    expected_products: [["CREATE", "dist/*.whl"]]
    authorized_keyids: ["abc123...", "def456..."]
    threshold: 1
inspections:
  - name: verify-no-secrets
    run: ["scan", "dist/"]
    expected_products: [["DISALLOW", "*.pem"]]

```


### 4.3 Sigstore: keyless signing via Fulcio, Rekor, and OIDC

Classical code signing failed operationally because *key management* failed: developers lose keys, keys leak, revocation is unreliable, and consumers cannot map keys to identities. **Sigstore** [3,5] inverts the model: instead of long-lived keys bound to identities by out-of-band trust, it issues **short-lived certificates** (valid ~10 minutes) from the Fulcio certificate authority, binding an *ephemeral* keypair to an **OIDC identity** (e.g., a GitHub Actions workflow identity or a developer's Google account) at signing time. There is no long-lived private key to steal; compromise of the ephemeral key is bounded by the certificate's brief validity.

Every signing event is recorded in **Rekor**, an append-only transparency log backed by a Merkle tree. Verifiers check not only the signature and certificate chain but also a signed *inclusion proof* that the signature was publicly logged — making clandestine signing detectable and enabling post-hoc audit. This mirrors Certificate Transparency's success in the Web PKI, adapted to artifact signing [5].

The keyless flow for a CI-built artifact proceeds as follows:

1. The CI job generates an ephemeral keypair in memory.
2. It presents its OIDC token (minted by the CI platform, bound to repo/workflow identity) to Fulcio.
3. Fulcio verifies the token and issues a short-lived certificate binding the ephemeral public key to the OIDC subject.
4. The job signs the artifact (or its SLSA provenance), submits the signature to Rekor, and discards the private key.
5. The verifier checks: certificate chain to Fulcio root, OIDC subject matches policy, signature valid, Rekor inclusion proof verifies against a trusted checkpoint.

> **Theorem: (Keyless unforgeability sketch).** Under the assumptions that (i) the OIDC provider correctly authenticates the claimed identity, (ii) Fulcio issues certificates only on valid tokens, and (iii) Rekor's Merkle tree is append-only, an adversary cannot produce a verifying signature attributed to an honest identity without compromising that identity's OIDC credentials within the certificate's validity window.


### 4.4 Reproducible builds: determinism as verification

Even perfect provenance attests only that *the builder claims* a given build. **Reproducible builds** [4] let anyone *check*: a build is reproducible if rebuilding the same source with the same declared toolchain and environment yields a bit-for-bit identical artifact. Independent rebuilders — run by different organizations on different infrastructure — then form a decentralized verification quorum: if *k* independent parties reproduce the same digest, a compromised builder must have compromised all *k* to ship a backdoored binary undetected.

Achieving determinism requires eliminating the classic nondeterminism sources:

- **Timestamps**: embed `SOURCE_DATE_EPOCH` (derived from the source changelog) instead of wall-clock time.
- **Build paths**: make debug symbols and embedded paths independent of the absolute build directory (`-ffile-prefix-map`, `__FILE__` remapping).
- **Ordering**: sort file inputs, archive members, and hash-table iteration deterministically.
- **Randomness**: seed or record all RNG used in codegen and compression.
- **Toolchain variance**: pin exact toolchain versions; record them in the buildinfo.

## 5. Empirical Results and Theoretical Analysis

### 5.1 Adoption measurements

Empirical data on supply-chain control adoption, drawn from published ecosystem studies and project reports:

- **Sigstore signing volume**: since its 2021 launch, Sigstore's public instance has recorded hundreds of millions of Rekor entries, driven by npm, PyPI, and Maven Central integrations; npm provenance (Sigstore-backed) became default-on for public packages built in GitHub Actions, making keyless provenance the largest signing deployment in history [3,5].
- **SLSA provenance in package registries**: PyPI and npm both accept and display Sigstore/SLSA-style provenance; Go modules' checksum database provides an adjacent transparency-log guarantee for the Go ecosystem.
- **Reproducible builds**: Debian reports >95% of packages reproducible [4]; Arch Linux and Guix pursue full reproducibility, with Guix's `guix challenge` enabling any user to verify substitutes against independent rebuilds.
- **in-toto deployments**: in-toto secures aspects of Datadog, Cloud Native Computing Foundation project release pipelines, and Debian's reproducible-builds attestation experiments [2].

### 5.2 Theoretical analysis: coverage of threats A–H

We evaluate the composed defense (SLSA L3 + in-toto + Sigstore + reproducible builds + SSDF) against the threat model:

| Threat | Control | Residual risk |
|--------|---------|---------------|
| A: artifact tampering | Sigstore signing + Rekor | OIDC IdP compromise |
| B: source tampering | Two-party review (SLSA L4), branch protection | Social engineering of reviewers |
| C: source platform compromise | Hardened platform, SSDF PW | Platform zero-day |
| D: dependency tampering | Hermetic builds, lockfiles | Compromised upstream before pinning |
| E: build platform compromise | Ephemeral hardened builders (L3) | Builder zero-day |
| F: parameter tampering | Non-falsifiable provenance | — (structurally addressed) |
| G: dependency service compromise | Vendoring, hermetic fetch | Availability attacks |
| H: insider builder | Two-party review (L4), thresholds | Colluding quorum |

> **Theorem: (Composition coverage).** The composed mechanism set reduces every threat A–H to either (i) compromise of a *threshold* of distinct trust anchors (reviewers, functionaries, rebuilders), or (ii) compromise of a hardened platform component (OIDC IdP, builder, transparency log). No single non-threshold component compromise suffices to ship a malicious artifact that verifies under an honest policy.


## 6. Limitations and Open Problems

**First-party vs. third-party asymmetry.** SLSA provenance and Sigstore signing are strongest when the *consumer* defines policy over *producer* claims — but most consumers run default-permissive policy. An attestation nobody verifies is documentation. Default-deny admission control remains the exception, not the rule.


**Hermeticity economics.** True hermeticity (SLSA L4) conflicts with ecosystems whose builds legitimately need network access (language package managers resolving at build time). Retrofitting hermeticity onto npm/PyPI-style workflows requires vendoring or airtight mirrors — a cost many projects cannot bear, capping them at L3.

**Reproducibility gaps.** Some artifact classes resist determinism: code-signed binaries (signatures embed timestamps), artifacts embedding cryptographic randomness without seed control, and GPU-kernel JIT outputs. Bootstrappable builds — eliminating the trusting-trust seed binary — remain incomplete for major toolchains.


**Transparency log governance.** Rekor's security rests on witness cosigning and append-only enforcement; a log operator colluding with a CA could equivocate. Scalable, decentralized witnessing for artifact transparency logs is an active research area [5].

## 7. Conclusion

This thesis presented a unified account of software supply chain security built on four mechanisms — SLSA provenance attestations [1], in-toto layouts [2], Sigstore keyless signing [3,5], and reproducible builds [4] — embedded in SSDF process discipline [6]. The central claim is compositional: provenance answers *who built what from what*, in-toto answers *through which authorized steps*, Sigstore answers *under whose identity, auditably*, and reproducible builds let skeptics *re-derive the answer themselves*. Against threats A–H, the composition reduces every supply-chain attack to threshold compromise of distinct trust anchors — the strongest structural guarantee available short of hardware attestation of the entire pipeline.

For practitioners the recommendation is graduated: adopt Sigstore signing and SLSA Level 2 provenance *now* (low cost, high value), drive toward Level 3 hardened builders, and treat Level 4 hermeticity plus reproducible builds as the strategic target. Open problems — policy bootstrapping, transparency-log governance, identity recovery, and the integrity/correctness semantic gap — define the research agenda. In an ecosystem where software is assembled from thousands of mutually distrusting contributions, *verifiable* provenance is not a premium feature; it is the precondition for justified trust.
