# Affine Types in the Wild: Rust's Ownership System, Non-Lexical Lifetimes, Polonius, and the Stacked Borrows Operational Model of Aliasing

## Abstract

Rust's ownership system is the most consequential deployment of substructural type theory in a production language: an affine type system guaranteeing memory and thread safety without a garbage collector. This thesis traces its complete arc, from linear and affine logic through its two complementary realizations — the syntactic borrow checker and the dynamic aliasing model — to the frontier of active research. We analyze the borrow checker's migration from lexical scopes to control-flow-graph regions under RFC 2094 (non-lexical lifetimes), why the resulting constraint propagation was necessarily location-insensitive, and how Polonius reframes borrow checking as Datalog evaluation over loans, origins, and liveness facts. We then examine the Stacked Borrows operational model, which defines precisely when raw-pointer aliasing in unsafe code is undefined behavior, and its successor Tree Borrows, validated across 30,000 crates in Miri. We close with RustBelt's machine-checked soundness proofs and the open problems: the location-sensitive alpha algorithm, opaque-type liveness, and the convergence of syntactic checking with semantic models.

## 1 Intro

Few questions in programming language design have been as consequential — and as long open — as this: can a systems language offer memory safety and data-race freedom *statically*, without a garbage collector, and without surrendering the performance and control that make C and C++ indispensable? Rust's answer is its ownership system, and that answer is now arguably the most important type-theoretic technology deployed at scale since type classes or generics. Every Rust program is accepted or rejected by an analysis that tracks *who owns what*, *who borrows what*, and *when those borrows are live* — a discipline formalized in the substructural type theory of linear and affine logic, and operationalized across two very different engines: the borrow checker in `rustc`, a syntactic, constraint-based region analysis; and Miri's dynamic aliasing models, which give an operational semantics to the borrow checker's *intent* for unsafe code.

This thesis argues that understanding Rust's ownership system requires understanding both engines, and the interplay between them. The borrow checker is what programmers interact with; it is the gatekeeper. But it is a *syntactic* artifact: it rejects programs it cannot prove safe, and it says nothing about what unsafe code may legally do with raw pointers. The semantic question — what aliasing patterns does Rust's type system *promise* the optimizer it will never see, even in `unsafe` code — is answered by operational models: Stacked Borrows and its successor Tree Borrows. Between these poles sits Polonius, an ongoing effort to rebuild the borrow checker itself on a more principled, declarative foundation.

## 2 Background

### 2.1 Linear and affine logic

Classical logic treats propositions as eternally true: once proven, a fact may be used any number of times. Linear logic, introduced by Girard [1], rejects the structural rules of *contraction* (duplication of hypotheses) and *weakening* (discarding of hypotheses), so that formulas become *resources* — consumed by use. Affine logic restores weakening while keeping contraction rejected: resources may be discarded but never duplicated. Rust's ownership system is an affine type discipline in this sense: every value has exactly one owner; ownership can be *moved* (transferring the obligation to destroy the value) or the value can be *dropped* (weakening — discarding the resource without using it), but it cannot be implicitly copied (no contraction). Types implementing `Copy` reintroduce a controlled form of duplication, but only for values whose duplication is bitwise and effect-free.

The type-theoretic formulation of these ideas predates Rust by decades: Wadler's "Linear types can change the world!" [2], uniqueness types (Clean), and region-based memory management (Tofte and Talpin [3]) all contributed to the design space. What distinguishes Rust is *scale*: these ideas are deployed in a language with pattern matching, traits, generics, and closures — and enforced *before the program ever runs*.

### 2.2 The ownership discipline

The Rust Book states three rules of ownership: each value has an *owner*; there can only be *one* owner at a time; and when the owner goes out of scope, the value is *dropped* [4]. Borrowing overlays a second discipline, "aliasing XOR mutability": at any point, a value may be borrowed by any number of *shared* references (`&T`), or by exactly *one* *mutable* reference (`&mut T`), but not both simultaneously. These rules are what the compiler's borrow checker enforces, and they are what the Stacked Borrows model *assumes* the optimizer may rely upon.

A crucial observation, first articulated clearly in the RustBelt project [5], is that these rules have two different audiences. The *safe* programmer sees them through the borrow checker's error messages. The *unsafe* programmer is not checked at all, yet the optimizer still assumes the aliasing discipline holds. The bridge is the aliasing model, which must be permissive enough to accept the unsafe code real programs need, yet strict enough to justify the compiler's optimizations.

### 2.3 Syntactic versus semantic checking

The borrow checker in `rustc` is a syntactic analysis over the Mid-level Intermediate Representation (MIR), Rust's control-flow-graph IR. It is necessarily *conservative*: it rejects some programs that are in fact safe, because it cannot prove them safe — the canonical examples are the "problem cases" of RFC 2094 [6].

The aliasing model, by contrast, is a *semantic* artifact: an operational semantics that instruments memory accesses with additional state and declares violating programs to have *undefined behavior* — the compiler's license to optimize [7]. The two engines are complementary: the borrow checker is a *sufficient* condition for safety the compiler can check cheaply; the aliasing model is the *definition* of the safety contract unsafe code must respect.

## 3 Methodology

This thesis is a survey and synthesis; our methodology is to reconstruct each component of the ownership system from its primary sources, and to cross-validate claims across the syntactic and semantic lines of work.

**Borrow-checker internals.** We reconstruct the NLL architecture from RFC 2094 [6] and the Polonius design documents [8][9][10]: outlives constraints emitted during MIR type checking; region inference by constraint propagation over strongly connected components; liveness analysis of loans; conflict detection at CFG points. We explain precisely *why* NLL is location-insensitive — the RFC's planned location-sensitive subtyping was deemed too expensive, a deferral that directly motivates Polonius.

**Polonius as Datalog.** We present Polonius's formulation — borrow checking as Datalog evaluation over input facts (`loan_issued_at`, `loan_killed_at`, `region_live_at`, `subset`) — and its central move: origins as the unit of analysis. Instead of computing concrete regions, Polonius computes *where origins must be live* and derives every error from a single principle, the subset error [10].

**Aliasing models.** We reconstruct Stacked Borrows from the POPL 2020 paper [11] — per-location stacks, permissions (Unique, SharedReadOnly, SharedReadWrite), retagging, protectors, the foreign-access rule — and Tree Borrows from the PLDI 2025 paper [12], with tree-structured permissions (Reserved, Active, Frozen, Disabled). For empirical grounding we use Miri [13], the std-test-suite validation in [11], the 30,000-crate Tree Borrows evaluation [12], and the foreign-function-boundary UB study [14].

**Formal foundations.** We anchor the discussion in RustBelt [5], the first machine-checked (Coq/Iris) soundness proof for a realistic Rust subset, including its lifetime logic — the separation-logic account of borrowing giving *semantic* content to the syntactic loan.

## 4 Deep Dive

### 4.1 Ownership as affine resource typing

To see why Rust's type system is *affine* rather than merely "strict," consider what happens at a move:

```rust
let s: String = String::from("hello");
let t: String = s;          // move: ownership transfers to t
// println!("{}", s);       // ERROR: use of moved value
```

After the move, `s` is unusable; its destructor runs exactly once, at the end of `t`'s scope. The resource is *consumed* by the move, and it may also be *discarded* — dropped — without being used, which is the affine weakening rule. The absence of implicit contraction is what makes `drop` total and predictable: the compiler knows, statically, the single program point at which each value's destructor runs, which is what makes RAII-style resource management sound without runtime bookkeeping.

> **Theorem (Unique ownership, informal):** In safe Rust, every live value has exactly one owner at every program point, and the compiler can compute a unique drop point for each value from the control-flow graph alone.

Borrowing refines this picture. A shared borrow `&T` is a *temporary, read-only view*: the owner cannot mutate or move the value while any shared borrow is live. A mutable borrow `&mut T` is *unique*: while it is live, the owner cannot use the value at all, and no other borrow may coexist. The borrow checker enforces this *dynamic-seeming* discipline — uniqueness of writers, multiplicity of readers — *statically*, over the CFG. This "aliasing XOR mutability" invariant is the single most load-bearing invariant in the Rust ecosystem: the optimizer's alias analysis, the soundness of `Cell` and `RefCell`, and the entire `Send`/`Sync` story all rest on it.

One subtlety deserves emphasis: *reborrowing*. When a function takes `&mut T` and passes it along, the compiler automatically creates a *reborrow* — a new, shorter mutable borrow derived from the original — so that the caller's borrow is merely *suspended*, not ended:

```rust
fn push_twice(v: &mut Vec<i32>) {
    v.push(1);
    v.push(2); // reborrow of v happens implicitly at each call
}
```

Reborrowing is the mechanism by which mutable borrows flow through call chains while preserving uniqueness; it is also the operation the Stacked Borrows model tracks explicitly as a stack push.

### 4.2 Non-lexical lifetimes: regions on the control-flow graph

Before NLL, lifetimes were *lexical*: a borrow's lifetime was the innermost AST scope enclosing all its uses. This produced the infamous problem cases of RFC 2094 [6] — for instance, borrowing from a map in one `match` arm and inserting in another, or holding a `&mut` slice in a variable across a call that no longer uses it. Programmers worked around these with artificial blocks and restructured control flow; the borrow checker was, in effect, reasoning about *scopes* rather than *flows*.

NLL, proposed in RFC 2094 (2017) and stabilized in Rust 1.31 (December 2018), moved lifetime inference onto the MIR control-flow graph:

1. **Constraint generation.** During MIR type checking, the compiler emits *outlives constraints* (`'a: 'b`) at the CFG points where borrows and subtyping relationships occur.
2. **Region inference.** A constraint-propagation solver computes, for each region variable, a *region*: a set of CFG points. The shipped implementation propagates over *strongly connected components* of the constraint graph — efficient but *location-insensitive*: once `'a: 'b` holds, it holds everywhere, ignoring the point where the constraint was generated.
3. **Liveness and conflict checking.** For each *loan* (the borrow checker's record of a borrow), the compiler computes the CFG points where the loan is *live* — reachable from a use without passing through an invalidating point — and verifies that no two live loans conflict at any point.

The payoff was immediate: borrows now end at their last use rather than at the end of an enclosing block. But the location-insensitivity of step 2 is a real precision loss: the compiler computes *larger* regions than the ideal location-sensitive semantics would, compensating with liveness. This two-level design — coarse regions, fine loans — is precisely what Polonius aims to replace with a single principled mechanism.

A companion feature, *two-phase borrows* (RFC 2025, stabilized alongside NLL), permits a method receiver to be mutably borrowed while its arguments are evaluated — which is what makes `vec.push(vec.len())` legal. It is the borrow checker's acknowledgment that *evaluation order* matters — a theme that returns with a vengeance in the operational models.

### 4.3 Polonius: borrow checking as Datalog

Polonius, Niko Matsakis's long-running project to replace the NLL borrow checker, starts from a deceptively simple question: what if, instead of computing regions as sets of CFG points and then checking loans against them, we computed *directly* the answer to the question the borrow checker actually asks? That question is: *at each program point, which loans are live, and do any of them conflict?*

The Polonius formulation treats the borrow checker as a Datalog program [9][10]. The inputs are *facts* extracted from the MIR:

| Fact | Meaning |
|---|---|
| `loan_issued_at(origin, loan, point)` | A borrow creating `loan` for region variable `origin` occurs at `point` |
| `loan_killed_at(loan, point)` | An action at `point` invalidates `loan` (e.g., a conflicting use) |
| `var_used_at(var, point)` / `var_defined_at` / `var_dropped_at` | Liveness scaffolding for locals |
| `subset(origin1, origin2, point)` | At `point`, `origin1` must outlive `origin2` |
| `cfg_edge(p, q)` | Control-flow edges |

From these, Datalog rules derive the pivotal relation `origin_live_on_entry(origin, point)`: the origins that must be live at a point, computed by propagating liveness *backwards* through the CFG along the subset relation.

The elegance is threefold.

Polonius remains a work in progress: the November 2025 project-goals update [8] reports active work on liveness for opaque types (needed for soundness with the new trait solver), on modeling borrow checking in `a-mir-formality`, and on integrating the alpha algorithm with Prusti's Place Capability Graphs.

### 4.4 Stacked Borrows: an operational model of aliasing

If the borrow checker is the syntactic gatekeeper, Stacked Borrows [11] is the semantic lawbook: the optimizer assumes `&mut T` never aliases, but unsafe code can manufacture arbitrary raw-pointer aliasing.

Stacked Borrows instruments the semantics with a *borrow stack* per memory location, each item carrying a *permission*:

- **Unique**: read and write; corresponds to a live `&mut T`.
- **SharedReadOnly**: read only; corresponds to `&T`.
- **SharedReadWrite**: read, plus write via interior mutability (`Cell`, `UnsafeCell`).

Three operations define the model.

The model is *executable*: implemented in Miri [13], any Rust program can be run under Stacked Borrows and checked for violations.

Stacked Borrows is, however, *strict* in ways real code found painful — notably around raw-pointer-heavy patterns.

### 4.5 Tree Borrows: permissiveness by construction

Tree Borrows [12] (PLDI 2025) replaces stacks with *trees*: each reference is a node, children derive from parents, and permissions are per-node states — **Reserved** (mutable borrow not yet written), **Active** (written, hence unique), **Frozen** (shared), **Disabled** (invalidated).

This accepts a large class of previously-rejected patterns, notably `&mut`s created speculatively or passed through abstraction layers without being written.

---

The arc from Stacked to Tree Borrows illustrates a general principle: the *semantic* model of borrowing is not fixed by syntax but is a *design choice* balancing optimization power against ecosystem compatibility — revisable in light of empirical evidence.

## 5 Empirical Results and Proofs

### 5.1 RustBelt: machine-checked soundness

The foundational result is RustBelt (Jung, Jourdan, Krebbers, and Dreyer, POPL 2018) [5]: the first machine-checked safety proof for a realistic Rust subset, λRust. Built on Iris, a higher-order concurrent separation logic in Coq, it introduces the *lifetime logic* — a separation-logic account of borrowing in which a loan is a resource governed by rules mirroring the borrow checker's. Well-typed λRust programs are memory- and thread-safe, and the proof is *extensible*: each unsafe library (`Cell`, `Mutex`, `Arc`) is verified against a semantic typing judgment, so new libraries can be added without redoing the whole proof. RustBelt makes "safe Rust is sound" a theorem rather than a slogan.

### 5.2 Miri validation of the aliasing models

The Stacked Borrows paper's empirical core is its Miri implementation [11][13]: large parts of the std test suite executed under the instrumented semantics, confirming the model permits the unsafe idioms the standard library relies on. This methodology — *executable* semantics plus ecosystem-scale testing — became the template for Tree Borrows, whose 30,000-crate evaluation [12] is the largest dynamic validation of a Rust aliasing model to date: 54% fewer rejections *without* sacrificing the aliasing optimizations the compiler performs (except the narrow, characterized class of write-inserting optimizations).

### 5.3 Borrow checking in practice: what NLL changed

On the syntactic side, the empirical record is the ecosystem itself: NLL's stabilization in Rust 1.31 eliminated entire classes of borrow-checker workarounds (artificial scoping blocks, control-flow restructuring around `get_mut`/`insert`) with no change to soundness. The cost was location-insensitive region inference — a precision gap Polonius's alpha algorithm is designed to close, with ongoing validation through `a-mir-formality` and Place Capability Graphs [8].

### 5.4 Aliasing violations at the FFI boundary

McCormack, Sunshine, and Aldrich's study of UB across foreign-function boundaries [14] is the sobering counterpoint: jointly executing Rust libraries with an LLVM interpreter for foreign calls, they found 46 instances of undefined or undesired behavior in 37 libraries — three in libraries averaging over 10,000 daily downloads — many of them aliasing violations. Tree Borrows was *significantly* more permissive than Stacked Borrows on this corpus, validating the model's evolution and underscoring the urgency: the aliasing contract is load-bearing for real code, and cross-language checking tooling remains Miri-shaped and incomplete.

## 6 Limitations

**The syntactic–semantic gap persists.** The borrow checker rejects programs the aliasing model would accept (it is conservative), and the aliasing model governs unsafe code the checker never sees. No theorem today states that every borrow-checker-accepted program is accepted by Tree Borrows — only Miri-run evidence. Closing this gap, even partially, is a major open problem.

**NLL's location-insensitivity is still with us.** The shipped NLL implementation computes regions via location-insensitive SCC propagation [6], which the RFC itself flagged as a precision compromise. Polonius's alpha algorithm promises location-sensitive reasoning, but Polonius is not yet the production borrow checker, and its performance at rustc scale remains to be demonstrated.

**Two-phase borrows and desugaring subtleties.** Features like two-phase borrows interact delicately with both the borrow checker and the operational models; the Tree Borrows paper notes elaboration-level differences between surface Rust and MIR that affect which model behaviors are observable.

**Unsafe code guidelines are incomplete.** The Reference documents UB [7] and the Rustonomicon discusses aliasing [15], but the *official* unsafe aliasing rules remain unfinished — the Unsafe Code Guidelines have not converged. Until they do, Miri's current model is the de facto standard, an unusual position for a language's semantics.

**Concurrency and relaxed memory.** The models discussed here are fundamentally *sequential*: RustBelt handles data-race freedom at the type level (via `Send`/`Sync`) atop the Iris concurrent separation-logic framework [16], but the operational aliasing models' interaction with the C++-style memory model of `std::sync::atomic` remains less developed than the sequential story.

## 7 Conclusion

Rust's ownership system is two systems in one: the *syntactic* borrow checker, which proves programs safe before they run; and the *semantic* aliasing models, which define what safety *means* for unsafe code the checker cannot see. From affine logic through lexical lifetimes, NLL's regions, Polonius's Datalog reformulation, Stacked Borrows' stacks, and Tree Borrows' lazy trees, both systems have grown simultaneously more precise and more principled — borrow-checker precision against ergonomics, aliasing-model strictness against ecosystem-scale Miri runs.

The open problems are now well-posed. Can Polonius's alpha algorithm deliver location-sensitive borrow checking at production performance? Can the syntactic and semantic accounts be *proved* to agree, rather than merely observed to? And can the Unsafe Code Guidelines converge on a final, official aliasing specification? Whatever the answers, the methodology this community has built — executable semantics, machine-checked proofs, and ecosystem-scale empirical validation, all in dialogue — is itself a contribution of lasting value: a template for how to evolve the foundations of a language that millions of programmers depend on, without breaking the code they have already written.
