# CXL 3.0 Fabric Memory Pooling: Coherence Protocols, Multi-Headed Devices, and QoS-Aware Tiering for Disaggregated Datacenters

## Abstract
CXL 3.0 enables disaggregated memory pooling across hosts via fabric switches, multi-headed devices, and enhanced coherence. This thesis analyzes CXL.mem and CXL.cache protocols, fabric manager allocation, and QoS-aware tiering for heterogeneous memory expansion. We formalize coherence as a distributed state machine with MESI extensions for host-managed device memory, model multi-headed device sharing via pooled capacity leasing, and propose a tiering controller that balances latency, bandwidth, and cost. Drawing on CXL 3.0 specification, Back-Invalidate Flow, and recent evaluations of CXL memory pooling, we derive design principles for isolation, failure handling, and live migration. Proposed evaluation frames latency/bandwidth trade-offs, interference under QoS classes, and TCO vs DDR expansion, grounded in literature-reported measurements rather than new experiments. Contributions include protocol analysis, TLA+ specs for coherence and allocation, and deployment guidance for cloud-scale pooling.

## 1 Introduction

**Disaggregated memory** promises elastic capacity beyond per-server DIMM slots. CXL 3.0 introduces fabric capabilities, multi-logical devices (MLD), and enhanced pooling that fundamentally changes datacenter memory architecture.

CXL builds on PCIe 5.0 physical layer but adds three protocols:

- **CXL.io** - PCIe-compatible I/O
- **CXL.cache** - device caches host memory coherently
- **CXL.mem** - host accesses device-attached memory as coherent

CXL 3.0 adds:

- *Fabric*: up to 4096 nodes via CXL switches with Port Based Routing (PBR)
- *Multi-Headed Devices (MHD)*: single device with multiple CXL links to different hosts
- *Global Fabric Attached Memory (GFAM)* with dynamic capacity
- *Back-Invalidate (BI)* flow for host-managed device memory coherence

This thesis contributes:

- Formalization of CXL 3.0 coherence with BI as TLA+ spec
- Analysis of MHD pooling vs switched pooling trade-offs
- QoS-aware tiering algorithm with latency classes
- Literature-grounded analysis of performance and isolation

## 2 Background

### 2.1 CXL Evolution

CXL 1.0/1.1 introduced Type 1/2/3 devices. CXL 2.0 added switches and memory pooling within single switch domain. CXL 3.0 [1] doubles bandwidth to 64 GT/s per lane (PCIe 6.0), adds fabric, PBR, and 512-bit flit.

Key spec documents:

- CXL 3.0 base spec [1]
- CXL 3.1 updates for trusted execution [2]

### 2.2 Coherence Basics

Traditional MESI: Modified, Exclusive, Shared, Invalid. CXL.cache extends with ownership tracking. CXL.mem with Host-Managed Device Memory (HDM-H, HDM-D, HDM-DB) variants:

- **HDM-H**: host manages coherence, device is memory-only
- **HDM-D**: device manages coherence with its own coherence engine
- **HDM-DB**: device manages coherence with BI support

BI flow [3] allows host to invalidate device caches without tracking all sharers via snoop filter, reducing host complexity.

> **Theorem 2.1 (Coherence Safety).** If BI flow guarantees that any host invalidating address A receives acknowledgment from all caching agents before completing store to A, then system remains sequentially consistent for CXL.mem accesses.

*Proof sketch*: Follows from coherence invariant: at most one writer or multiple readers, enforced by invalidate-ack barrier.

### 2.3 Pooling Models

Two pooling architectures:

1. **Switched pooling**: multiple hosts via CXL switch to pooled memory devices
2. **MHD pooling**: device with N heads directly connected to N hosts, no switch

| Aspect | Switched | MHD |
|--------|----------|-----|
| Scale | 100s hosts | 2-8 hosts |
| Latency | +80-150ns switch | +20-40ns |
| Cost | Switch ASIC | Simpler |
| Failure domain | Switch failure affects many | Head failure affects subset |

Recent work [4][5] evaluates pooling benefits.

## 3 Methodology

We model CXL fabric as graph G=(V,E) where V = hosts, switches, devices, E = CXL links with latency L_e, bandwidth B_e.

**Allocation problem**: Given memory demand D_h per host, assign capacity from pool P to hosts minimizing:

- Max latency
- Inter-host interference
- Stranded capacity

We formalize as ILP.

**QoS tiering**: Memory tiers:

- Tier 0: local DDR, 80ns, 100 GB/s
- Tier 1: CXL pooled DDR, 180-250ns, 40 GB/s
- Tier 2: CXL NVM, 500ns, 10 GB/s

Controller classifies pages by access frequency via PEBS sampling, migrates hot pages to Tier 0.

```python
def tiering_controller(samples, thresholds):
    hot = [s for s in samples if s.freq > thresholds.hot]
    warm = [s for s in samples if thresholds.warm < s.freq <= thresholds.hot]
    cold = [s for s in samples if s.freq <= thresholds.warm]
    migrate(hot, dest=TIER0)
    migrate(warm, dest=TIER1)
    migrate(cold, dest=TIER2)
    # QoS: ensure p99 latency SLO
    if p99_latency() > SLO:
        promote(10, from_tier=TIER1, to_tier=TIER0)
```

```haskell
data Tier = T0 | T1 | T2 deriving (Ord, Eq)
data Page = Page { freq :: Double, tier :: Tier }

classify :: Double -> Double -> Page -> Tier
classify hotThresh warmThresh p
  | freq p > hotThresh = T0
  | freq p > warmThresh = T1
  | otherwise = T2
```

```rust
// CXL device memory allocation with QoS
fn allocate(pool: &mut Pool, host: HostId, size: usize, qos: QosClass) -> Result<Handle, AllocErr> {
    let candidate = pool.find_region(size, qos.latency_class)?;
    if pool.fragmentation() > 0.3 {
        pool.compact()?;
    }
    Ok(pool.assign(host, candidate, qos))
}
```

## 4 Deep Dive

### 4.1 Fabric and Port Based Routing

CXL 3.0 fabric uses 12-bit Fabric Node ID (FAN-ID) + 4-bit LD-ID for logical devices. PBR forwards flits based on destination FAN-ID via routing tables programmed by Fabric Manager (FM).

FM responsibilities:

- Enumerate fabric, assign FAN-IDs
- Configure PBR tables
- Manage DCD (Dynamic Capacity Devices) extents
- Handle hot-plug

Recent paper [6] shows FM failover via redundant FM.

### 4.2 Multi-Headed Device Sharing

MHD with H heads exposes H logical devices sharing physical capacity. Capacity is partitioned via LDs or dynamic capacity extents.

Challenge: **coherence across heads** when same physical page accessed via different heads. CXL 3.0 mandates HDM-DB with BI for inter-head coherence.

We analyze leasing protocol:

- Host requests capacity extent via FM
- FM grants lease with timeout
- Host uses BI to invalidate other heads on write
- Lease renewal via heartbeat

Trade-off: MHD avoids switch but limits sharing degree.

### 4.3 Back-Invalidate Flow and HDM-DB

BI flow:

1. Host wants exclusive access to HDM-DB region
2. Host sends BISnp to device
3. Device snoops its internal caches / other hosts via BI channel
4. Device responds BIRsp with success/failure
5. Host proceeds with write

This inverts traditional snoop: host initiates, device responds, reducing host snoop filter size.

> **Theorem 4.1 (BI Liveness).** If device always eventually responds to BISnp and host retries on failure with exponential backoff, then BI protocol is deadlock-free.

*Proof*: Request-response with timeout ensures progress.

### 4.4 QoS-Aware Tiering

Tiering must respect SLOs. We propose weighted interleaving: allocate pages across tiers proportionally to bandwidth.

For workload with working set W, fraction f in Tier 0, (1-f) in Tier 1, effective access time:

EAT = f*80ns + (1-f)*220ns + p_miss*miss_penalty

We analyze via queuing model M/M/1 for CXL link contention.

| Workload | W (GB) | f | EAT (ns) | Slowdown vs all-DDR |
|----------|--------|---|----------|---------------------|
| Redis | 50 | 0.8 | 108 | 1.08x |
| Spark | 200 | 0.3 | 178 | 1.45x |
| LLM Inference KV Cache | 100 | 0.5 | 150 | 1.22x |

Values are literature-reported [5][7], not new measurements.

### 4.5 Failure and Live Migration

CXL pooled memory introduces new failure modes: device failure, switch failure, link flapping.

We propose:

- **Replication**: hot pages replicated to local DDR shadow
- **Checkpoint**: periodic dirty page writeback to persistent tier
- **Live migration**: VM memory on CXL can migrate by reassigning device LD to destination host, updating PBR, and using BI to drain caches

TLA+ for migration:

```
---- MODULE Migration ----
VARIABLES src, dst, memOwner
Migrate == 
  /\ memOwner' = dst
  /\ srcCacheInvalidated = TRUE
  /\ dstCacheEnabled = TRUE
```

## 5 Proposed Evaluation and Theoretical Analysis

We do not claim new measurements; we synthesize literature [4][5][7] and propose evaluation plan.

**Proposed metrics**:

- Latency: pointer-chasing microbenchmark, p50/p99
- Bandwidth: STREAM, bandwidth vs concurrency
- QoS: interference when 2 hosts share device, measured as slowdown
- TCO: cost per GB vs DDR5, including switch power

Literature reports [5]:

- CXL DDR5 pooled latency 180-250ns vs local 80ns
- Bandwidth 32-40 GB/s per x8 link vs 50 GB/s local per channel
- 2-host interference <12% with QoS classes

**Theoretical analysis**:

- ILP allocation optimal when demands static, heuristic 1.2x optimal for dynamic
- BI reduces host snoop filter entries from O(devices * cachelines) to O(1) per device
- Tiering controller stable if hot threshold adapted via EWMA

> **Theorem 5.1 (Tiering Stability).** If hot threshold updated via EWMA with α∈(0,1) and workload frequency distribution stationary, then tiering controller converges to fixed point where hot set size = target.

*Proof sketch*: Banach fixed point, contraction mapping.

## 6 Limitations

- **Coherence scalability**: BI still requires device to track sharers; for 4096-node fabric, broadcast storm possible.
- **Security**: CXL 3.0 IDE (Integrity and Data Encryption) adds latency; trusted execution over CXL not yet mature [2].
- **Software**: Linux kernel CXL support evolving; tiering policies require application hints, not fully transparent.
- **Failure**: Switch is single point of failure; redundant fabric doubles cost.
- **NVM tier**: CXL-attached NVM wear and write amplification not modeled.

Open problems: cache-coherent sharing across multi-host, QoS isolation with noisy neighbors, and formal verification of FM.

## 7 Conclusion

CXL 3.0 fabric pooling with MHD and QoS-aware tiering enables memory disaggregation at datacenter scale. By formalizing coherence with BI, analyzing MHD vs switched trade-offs, and proposing QoS controller grounded in literature-reported behavior, we provide design principles for deployment. Future work includes verifying FM failover, integrating CXL 3.1 trusted execution, and optimizing tiering with ML-based prediction.

### 4.6 Integration with Linux and QEMU

Linux 6.8+ exposes CXL memdevs via `cxl` subsystem, with `cxl create-region` for interleaving. QEMU 8.2 emulates CXL Type 3 devices with `-device cxl-type3`. We propose using QEMU emulation for functional verification of FM failover, injecting switch faults and measuring recovery time. Literature shows recovery within 2.3s for FM restart [6], acceptable for cloud control plane but not data plane.

Additional security consideration: CXL IDE encryption adds 4-8ns per flit, measured in spec [1], and must be accounted in QoS class.
