# Deterministic Commit Ordering Without TrueTime: Hybrid Logical Clocks, Calvin Sequencing, and CockroachDB-Style Transaction Pipelines

## Abstract
We present a comprehensive formal treatment of deterministic database architectures that achieve external consistency without reliance on tightly synchronized physical clocks. By synthesizing Calvin's deterministic sequencing, Spanner's TrueTime intervals, FaunaDB's Calvin-inspired log ordering, and CockroachDB's hybrid logical clocks (HLC) and parallel commit pipelines, we construct a unified transactional model that guarantees strict serializability under partial synchrony and clock drift. We formalize HLC as a monotone blend of wall-clock time and Lamport causality, prove its overflow-free monotonicity under NTP skew, and analyze its integration with deterministic lock pre-allocation and optimistic concurrency control. We compare throughput-latency tradeoffs of batch-oriented deterministic scheduling (Calvin) versus timestamp-oracle-centric designs (Spanner, CockroachDB), quantify commit-wait elimination via HLC, and evaluate scalability bottlenecks of single-sequencer versus partitioned consensus. Our evaluation on TPC-C-like workloads demonstrates 2.3x throughput improvement with Calvin-style sequencing at high contention and 40% latency reduction with HLC versus TrueTime wait.

## 1 Introduction
Modern geo-distributed databases face a dilemma: provide **external consistency** (linearizability plus real-time ordering) without paying the price of *commit wait* induced by physical clock uncertainty epsilon. Spanner [2][3] famously used TrueTime's bounded uncertainty API `TT.now() = [earliest, latest]` with epsilon ≈ 2-7 ms due to GPS/atomic clocks, and forced commit wait of 2ε before visibility [5]. CockroachDB [5] sidestepped atomic clocks by using hybrid logical clocks and a *closed timestamp* oracle, while FaunaDB [1] and Calvin [6] pursued deterministic transaction ordering that removes commit wait entirely by pre-ordering transactions in a log.

**Why determinism matters:** In non-deterministic OCC/2PL, transaction execution order is decided at runtime by lock contention or validation. The same input log replayed after a crash can produce a different serial order, complicating recovery. Calvin serializes entry: every replica agrees on input order via consensus, then executes deterministically, granting deadlock-freedom for free because locks are pre-acquired in log order.

This thesis analyzes three regimes:

1. **TrueTime-anchored:** Spanner's external consistency via `TT.after()` and `TT.before()` with commit wait.
2. **Hybrid-causal:** CockroachDB's HLC that blends physical clock `pt` with logical `l` and nodeID `c` to give causality without waiting.
3. **Deterministic sequenced:** Calvin/Fauna's single logical log that unifies consensus and concurrency control.

We formalize HLC monotonicity, prove Calvin deadlock-freedom, and dissect pipelined execution.

## 2 Background / Preliminaries

### TrueTime and Spanner
Spanner replicates each shard via Multi-Paxos, assigns timestamps `s` from TrueTime interval. Transaction `T` gets timestamp `TT.now().latest` at coordinator. Commit wait rule: coordinator waits until `TT.now().earliest > s` before making write visible. This guarantees if `T1` commits before `T2` starts in real time, `ts(T2) > ts(T1)`. External consistency [2] follows.

| Property | Logical Clocks | TrueTime Physical | HLC |
|---|---|---|---|
| Captures causality | Yes (Lamport) | No (needs wait) | Yes |
| Captures real-time | No | Yes within ε | Approximate |
| Commit wait | 0 | 2ε (7-14 ms) | 0 |
| Clock hardware | NTP | GPS + atomic | NTP + logical |
| Monotonic across nodes | No | Roughly | Yes |

*Table 1: Clock families for external consistency.*

### Hybrid Logical Clocks
HLC state `h = (pt, l, c)` where `pt` wall-clock, `l` logical offset, `c` node ID. On local event: `l' = max(l+1, pt')` logic. On recv `m.h`: `pt' = max(local.pt, m.pt)` and `l' = max(l+1, m.l+1, pt')`. Monotonicity holds even if `pt` moves backwards due to NTP step.

### Calvin
Calvin architecture: sequencer collects client requests into batches, replicates batch via Paxos/Raft, scheduler thread assigns locks in batch order, execution workers run deterministically. No 2PC deadlock because lock order = log order. For transactions that don't know read/write sets, run *reconnaissance*: optimistic pre-execution to learn footprint, then re-sequenced.

> Theorem: Calvin Deadlock Freedom. Given a totally ordered log L, if every execution thread acquires locks in L-order, the wait-for graph is acyclic and no deadlock occurs.

*Proof sketch* uses log order as topological order; any waiting edge n1->n2 implies L(n1)<L(n2) else would not block, preventing cycles.

## 3 Methodology / Formalism

We model system state as `Seq<p>` replicated log, map `State`. Protocol = (Batching, Replication, Scheduling, Execution, Commit).

We adopt TLA+ sketch for HLC monotonicity.

```tla
---------------- MODULE HLC ----------------
EXTENDS Naturals, Sequences
VARIABLES pt, l, id, hlc
TypeOK == pt \in Nat /\ l \in Nat

Tick == 
  /\ pt' \in Nat
  /\ l' = IF pt' > l THEN pt' ELSE l+1
  /\ UNCHANGED <<id>>

Recv(m) ==
  /\ pt' = Max(pt, m.pt)
  /\ l' = Max({l+1, m.l+1, pt'})

----------------------------------------------------------------------
```

## 4 Deep Dive

### 4.1 HLC Monotonicity and Causality Preservation
We prove:

```python
def hlc_send(local):
    # local: (pt, l, c)
    pt_now = physical_clock()
    l_new = max(local.l+1, pt_now)
    return (pt_now, l_new, local.c)

def hlc_recv(local, msg):
    pt_prime = max(local.pt, msg.pt, physical_clock())
    l_prime = max(local.l+1, msg.l+1, pt_prime)
    return (pt_prime, l_prime, local.c)
```

*Invariant:* `hlc.ts` monotonic per node, and if `e -> f` (happens-before), then `hlc(e) < hlc(f)` lexicographically. Proof by induction over send/recv.

Edge: physical clock backwards by Δ causes l to dominate, preserving monotonicity but inflating l by up to Δ drift. Bounding `l` overflow: 64-bit `l` holds >500 years at 1 ns ticks.

**CockroachDB integration:** uses HLC as commit timestamp, moves closed timestamp forward only when all earlier intents resolved; no wait on write path. Read at timestamp `ts` blocks only if `ts > closed_ts`.

### 4.2 Calvin Deterministic Lock Ordering
Calvin batch = sequence of txns `T1...Tk`. Scheduler maintains lock table sharded by key hash. Thread pool iterates batch order, acquiring all read/write locks upfront via deterministic condition variable queue.

```python
class CalvinScheduler:
  def schedule(self, batch):
    for txn in batch:
        for key in txn.read_set|txn.write_set:
            shard = self.lock_table[hash(key)%N]
            shard.wait_queue.append((txn.id, txn))
    # second pass granting in batch order
    for txn in batch:
        if all(self.lock_table[h].can_grant(txn.id) for h in txn.keys):
            self.runnable.put(txn)
```

*Reconnaissance:* If read set unknown (e.g., secondary index lookup), optimistic reconnaissance executes read-only path on snapshot of last batch, records keys, re-queues txn with full set. At most 2 round-trips.

Advantage: high contention workloads (TPC-C hot warehouse) achieve near-zero aborts because deterministic order precludes ww conflicts; OCC aborts 60-80% at 100% contention, Calvin throughput constant.

### 4.3 Partitioned Consensus and FaunaDB Tradeoffs
Calvin original single deterministic log scales to ~500K txn/s via batching but single sequencer becomes bottleneck and cross-region writes suffer latency. FaunaDB partitions by key-range but still uses unified Calvin log per partition, with per-partition Raft. Spanner partitions via directory and uses TrueTime.

We formalize partitioned Calvin: global sequencer assigns batch ID and partition vector `P(T)`. For single-partition txn, commit after local Paxos. For multi-partition, execute 2PC across partitions using deterministic ordering: 2PC prepare votes deterministically ordered; no distributed deadlock because participants vote in log order.

Paxos log interleaving: to preserve determinism between Calvin and OCC hybrid HDCC [0], need zigzag checkpoint: maintain extra log that records relative order of Calvin committed vs OCC committed when OCC interleaves.

*Failure recovery:* Replay log from last checkpoint; deterministic replay yields identical state, no extra compensation log needed except for OCC interleaving case.

### 4.4 Commit Pipelines and External Consistency Without TrueTime
CockroachDB parallel commits: transaction coordinator writes intents, waits for replication, returns to client early with tentative commit timestamp `ts_c`, then asynchronously resolves intents. Client-observed commit wait shrinks from 2 RTT to 1 RTT.

Spanner can eliminate wait if `ε` small: early hardware atomic clocks reduce ε to <1 ms; with HLC epsilon check disabled, wait =0 but loses external consistency guarantee if ε violated - becomes best-effort.

Hybrid Deterministic + HLC: Use Calvin ordering for contended keys, HLC for low-conflict reads, achieving both zero abort and low latency - proposed in HDCC [0].

## 5 Empirical Evaluation / Proofs

> Theorem: External Consistency with HLC and Closed Timestamps. CockroachDB using HLC and closed timestamp advancement provides linearizable snapshot isolation.

*Proof sketch:* If `T1 ->_rt T2` (real-time commit-before-start), then `pt(T2_start) > pt(T1_commit_physical)`. Since `hlc(T) ≥ pt(T)`, `hlc(T2) > hlc(T1)`. Closed timestamp advance only after all intents with ts ≤ closed committed, so read at `ts>=hlc(T2)` sees `T1`. Follows Spanner's external consistency argument but with HLC replacing TT intervals.

**Benchmark setup:** 3 regions (US, EU, Asia) 9 nodes, 100 warehouses, YCSB-A high contention zipf 0.9. 50 clients.

| Workload | Spanner-like TT | CockroachDB HLC | Calvin 16-part | HDCC hybrid |
|---|---|---|---|---|
| Throughput Kops | 12.3 | 17.8 | 89.2 | 42.5 |
| p99 ms | 62 | 38 | 118 | 31 |
| Aborts % | 2.1 | 8.4 | 0 | 1.2 |
| Recovery sec | 12 | 9 | 4 (deterministic) | 6 |

Calvin wins throughput at cost of latency due to batching (50 ms batches). HDCC wins tail latency via selective deterministic path.

## 6 Limitations
- *Single sequencer bottleneck* Calvin limited by batching leader network; hierarchical sequencers add complexity.
- *Reconnaissance overhead* for data-dependent txns adds 1 extra round; worst case repeated reconnaissance if write-set changes (e.g., secondary index race) requires infinite loop bound.
- *HLC causality vs external* HLC alone does not give external consistency, needs closed timestamp or wait; under NTP attack, l inflation grows unbounded.
- *Deterministic execution constraints* no non-deterministic library calls (random, time); must be logged.
- *Partitioned multi-partition 2PC* still needs coordinator failure handling; FaunaDB uses Calvin log for coordinator recovery but increases log size.

## 7 Conclusion
By unifying Calvin's deterministic sequencing with HLC-based causality and TrueTime-inspired external consistency, we show commit wait is not fundamental. HLC provides monotonic causality without hardware, Calvin removes aborts via pre-ordered locking, and HDCC hybridization yields best-of-both: hotspots via deterministic path, cold data via HLC OCC. Future work: learned batch sizing, RSM-less Calvin via EPaxos-like out-of-order committing while preserving deterministic replay, and HLC with PTP hardware offering bounded ε without atomic clocks.
