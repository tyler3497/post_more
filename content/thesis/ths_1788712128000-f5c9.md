# Bitwise Reproducibility: Functional Package Management with Nix and Guix, Hermetic Builds, and Supply-Chain Attestation via SLSA

## Abstract

Modern software supply chains routinely convert untrusted source text into privileged binaries through opaque, environment-dependent build pipelines. This thesis unifies three historically disjoint research programs—Eelco Dolstra's purely functional deployment model (2006), the Reproducible Builds project's elimination of build non-determinism, and the SLSA/in-toto attestation frameworks for provenance—into a single end-to-end argument: *bitwise reproducibility is achievable at industrial scale, and functional package management is the architecture that makes it practical.* We formalize hermetic evaluation, content-addressed storage, and fixed-output derivations; quantify the sources of non-determinism (timestamps, absolute paths, filesystem ordering, entropy) and their canonical remediations (SOURCE_DATE_EPOCH, path prefix remapping, deterministic archives); and evaluate empirical evidence from Nixpkgs, GNU Guix, and Debian. We argue that reproducibility defeats the *Trusting Trust* class of attacks only when paired with provenance attestation, and we identify residual risks—compiler bootstrapping, nondeterministic parallelism, and floating-point hardware variance—that bound the guarantees.

---

## 1 Introduction

The dominant model of software deployment circa 2005 treated a build as a side-effecting script executed against a mutable machine. Dependencies were resolved by global mutable state (`/usr/lib`, the `PATH`, the package database), builds mutated shared filesystems, and the resulting artifacts carried no verifiable link to the inputs that produced them. Eelco Dolstra's 2006 dissertation, *The Purely Functional Software Deployment Model* [1], diagnosed this as a category error: deployment should be a **pure function** from declared inputs to outputs, with the entire dependency closure captured explicitly and the result stored under a cryptographic hash of those inputs.

Two decades later, that model underpins Nix and GNU Guix, which manage tens of thousands of packages across production infrastructure. In parallel, the Reproducible Builds project [2] demonstrated that eliminating non-determinism from compilers, archivers, and build systems is feasible across entire distributions, and the SLSA framework [3] together with in-toto [4] supplied the missing vocabulary for *provenance*—statements, signed and auditable, about how an artifact came to exist. The convergence is not accidental: functional package management provides the hermetic inputs that reproducibility requires, and reproducibility provides the verifiable claim that attestation frameworks need to attest *to*.

This thesis contributes:

1. A formal account of the purely functional deployment model, its store semantics, and fixed-output derivations.
2. A taxonomy of build non-determinism with canonical remediations and their empirical coverage.
3. An analysis of how SLSA levels and in-toto layouts compose with reproducible builds to bound the *Trusting Trust* attack surface first articulated by Ken Thompson [5].
4. A candid assessment of residual limitations: the bootstrap problem, hardware-level variance, and attestation trust roots.

## 2 Background

### 2.1 The purely functional deployment model

Dolstra's thesis [1] treats software deployment as evaluation in a purely functional language. A *derivation* is a description of a build: the builder executable, its arguments, environment variables, system type, and the complete set of input derivations. Evaluating a derivation produces *store objects* placed at paths of the form:

```
/nix/store/<hash>-<name>
```

where `<hash>` is a cryptographic hash (historically SHA-256 truncated to 160 bits, now full 256-bit in newer Nix) over *all inputs* to the derivation—including transitive dependencies. This input-addressing (as opposed to content-addressing) means that changing any dependency, however distant, changes the store path of every dependent. The resulting structure is a directed acyclic graph of derivations whose roots are the desired packages and whose leaves are fixed-output derivations such as source tarballs pinned by hash.

Key properties follow directly:

- **Immutability.** Store paths are never modified after creation; builds that would write to an existing path fail.
- **Isolation.** Multiple versions and variants of a package coexist without conflict, since each occupies a distinct store path.
- **Atomic upgrades and rollbacks.** A system configuration is a symlink into the store; switching generations is a single atomic symlink swap.
- **Referential transparency of deployment.** Identical derivation inputs yield identical store paths, so caching, substitution (binary caches), and distributed builds are sound by construction.

### 2.2 GNU Guix and the Scheme lineage

GNU Guix [6] reimplements the functional model with Scheme (Guile) as the configuration language, treating packages as first-class values in a functional DSL. Guix's contributions include `guix challenge`, which rebuilds a store item on independent machines and compares hashes, and the *time-machine* (`guix time-machine --commit=...`) for pinning the entire package graph to a revision—addressing the long-standing "which nixpkgs commit built this?" question. Guix also pioneered the **bootstrappable builds** effort, reducing the binary seed required to bootstrap a full toolchain from hundreds of megabytes to a minimal auditable core.

### 2.3 Reproducible Builds

The Reproducible Builds project [2] defines a build as reproducible when rebuilding from the same source, with the same build environment, produces **bit-for-bit identical** artifacts. Its catalog of non-determinism sources—timestamps, absolute build paths, filesystem ordering, archive metadata, uninitialized memory, ASLR-derived values, unseeded randomness, and locale/timezone leakage—paired with the `SOURCE_DATE_EPOCH` specification (a distribution-wide environment variable fixing the reference timestamp), converted reproducibility from folklore into an engineering discipline with CI dashboards across Debian, Arch, and other distributions.

### 2.4 SLSA and in-toto

SLSA (Supply-chain Levels for Software Artifacts) [3] grades build *integrity*: Level 1 requires provenance to exist, Level 2 requires a hosted build service with signed provenance, Level 3 adds hardened, non-falsifiable provenance, and Level 4 adds hermetic builds plus two-person review. in-toto [4] provides the layout and attestation machinery: a signed *layout* declares the expected supply-chain steps, and each step emits *link metadata* recording materials, products, and command lines, enabling clients to verify that an artifact passed through exactly the prescribed pipeline. Notably, SLSA attests to *how* something was built; reproducibility lets a third party verify *that the claimed how produces this exact what*.

### 2.5 Trusting Trust

Ken Thompson's 1984 Turing Award lecture, "Reflections on Trusting Trust" [5], demonstrated a self-replicating compiler backdoor: a compromised compiler can insert a Trojan into the binaries it produces—including future versions of itself—while the backdoor remains invisible in all source code. This is the foundational threat model of supply-chain security: **source auditing is insufficient if the build pipeline is untrusted**.

## 3 Methodology

Our method is constructive and comparative. We (a) formalize the functional deployment model as an evaluation semantics over derivations; (b) compile the Reproducible Builds non-determinism catalog into a remediation matrix, mapping each source of variance to the build-system, toolchain, and packaging mechanisms that neutralize it; (c) model the composition of reproducible builds with SLSA/in-toto attestation as a verification game between builder, attestor, and independent verifier; and (d) assess empirical coverage using published statistics from the Nix, Guix, and Debian ecosystems. All claims about tooling behavior are grounded in the cited manuals and specifications [1][2][3][4][6]; no new implementation was required, as the analysis concerns the architecture shared by existing systems.

> **Theorem:** Given a hermetic evaluator over derivations with content-addressed fixed-output inputs, two evaluations of the same derivation on distinct machines produce store objects that are byte-identical if and only if the builder is a deterministic function of its declared inputs.

*Proof sketch.* The store path commits to the complete transitive input closure. Hermeticity guarantees no undeclared input can influence evaluation. Hence any output divergence between two evaluations must originate in non-determinism of the builder itself—i.e., the builder is not a function of its declared inputs. Conversely, a deterministic builder over identical inputs yields identical outputs. ∎

## 4 Deep Dive

### 4.1 Derivation semantics and the store

A derivation `d` is a tuple `(name, system, builder, args, env, inputs)` where `inputs` is the set of referenced store objects. Nix computes the output path as:

```nix
storePath(d) = /nix/store/ H(serialize(inputs(d), builder, args, env, system)) - name
```

with `H` a cryptographic hash. The critical subtlety is *fixed-output derivations*: for fetching source tarballs from the network, the output hash is declared in advance, so the store path is computed from the *declared content hash* rather than the derivation inputs. This reconciles purity with the impure act of downloading: the network fetch is allowed precisely because its result is pinned and verified.

```nix
stdenv.mkDerivation {
  pname = "hello";
  version = "2.12";
  src = fetchurl {
    url = "mirror://gnu/hello/hello-2.12.tar.gz";
    sha256 = "sha256-jZkUKv2SV28wsM18tCqNxoCZmLxdY4IdIxIp9qX04as=";
  };
  # builder runs with ONLY declared inputs visible:
  # empty network namespace, chroot store, fixed PATH
}
```

Guix expresses the same idea in Scheme, where `(package ...)` forms are values and `origin` records carry `(sha256 (base32 "..."))` pins [6]. The practical consequence: `nix-store --verify-path`, `guix challenge`, and binary-cache substitution are all *sound* operations, because a path's name commits to its provenance.

### 4.2 Hermetic evaluation and sandboxing

Hermeticity is enforced, not assumed. Nix builds execute with:

| Mechanism | Effect |
|---|---|
| Network namespace / no network | Builders cannot fetch undeclared inputs |
| Chroot / mount namespace | Only declared store paths visible |
| Fixed `PATH`, cleared env | No host toolchain leakage |
| Private `/tmp`, PID namespace | No cross-build interference |
| `SOURCE_DATE_EPOCH`-aware defaults | Canonical timestamps |

Guix uses Linux namespaces and a containerized build daemon to the same end [6]. This is what elevates SLSA's Level 4 requirement—*hermetic builds* [3]—from aspiration to default behavior: every Nix and Guix build is hermetic unless the user explicitly relaxes it (e.g., `__noChroot` or impure `fetchurl` without hash, both of which are auditable deviations).

> **Theorem:** A hermetic evaluator with input-addressed storage makes undeclared-dependency attacks detectable, because any output influenced by an undeclared input cannot be reproduced by an independent verifier.

### 4.3 The non-determinism taxonomy and its remediations

The Reproducible Builds catalog [2] identifies the principal variance sources. Each has a canonical remediation:

1. **Timestamps** — embedded via `__DATE__`, `__TIME__`, archive mtimes, or `ar` headers. Remediation: `SOURCE_DATE_EPOCH` (seconds since epoch, typically the last source-modification time) consumed by GCC, `ld`, `gzip -n`, `tar --mtime`, and `zip -X`.
2. **Absolute build paths** — leaked into debug info, `__FILE__` macros, and RPATHs. Remediation: `-ffile-prefix-map=$SRCDIR=.`, `-fdebug-prefix-map`, and Nix's practice of rewriting store paths only at well-defined boundaries.
3. **Filesystem/archive ordering** — `readdir` order, tar entry order, hash-table iteration. Remediation: sorting inputs, deterministic archivers, fixed locale (`LC_ALL=C`).
4. **Build IDs and UUIDs** — `ld --build-id` embeds a hash of contents (benign if inputs are fixed, but must be stable); random UUIDs must be seeded or removed.
5. **Uninitialized memory / padding** — zero-fill structures; deterministic allocators in build tooling.
6. **Parallelism** — nondeterministic task scheduling affecting link order or generated code layout. Remediation: deterministic scheduling or serialized critical sections.

The `diffoscope` tool [2] renders residual differences between two builds as structured, human-readable diffs—recursively unpacking archives, disassembling binaries, and normalizing formats—so that the *last mile* of non-determinism is diagnosable rather than mysterious.

```bash
export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
# Build twice in isolated environments, then:
diffoscope build-a/pkg.tar.gz build-b/pkg.tar.gz --html report.html
# Exit 0 with empty diff  =>  bitwise reproducible
```

### 4.4 Content-addressed derivations and the trust boundary

Classical Nix is *input-addressed*: the store path hashes the inputs. Recent work adds *content-addressed derivations* (CA derivations), where the output path hashes the *output content* instead. This has a profound verification consequence: with CA derivations, two different build graphs that produce identical content converge on the same store path, and—crucially—an independent verifier can confirm that a published binary's *content* matches without trusting the builder's claimed input graph. CA derivations are the mechanism by which Nix is closing the gap between "this path was built from these inputs" and "this content is what these inputs produce."

### 4.5 Attestation: SLSA provenance and in-toto layouts

Reproducibility answers "can anyone re-derive this artifact?"; attestation answers "what does the builder claim happened?" SLSA provenance [3] is a signed statement binding artifact digests to builder identity, build type, materials (source digests), and parameters. in-toto [4] generalizes this: a *layout* signed by the project owner lists required steps (`clone`, `test`, `build`, `package`), authorized functionaries per step, and expected artifacts; each step's *link metadata* records what went in and what came out. Verification is then a graph-matching problem the client performs locally.

The composition is strictly stronger than either part alone:

- **Provenance without reproducibility** proves *who* built it and *from what source*, but a compromised builder can substitute a Trojan and the provenance will faithfully describe the lie.
- **Reproducibility without provenance** lets anyone verify the artifact matches *some* source, but does not bind which source the publisher intended, nor who ran the build.
- **Together**, a client verifies the signature chain (in-toto/SLSA), rebuilds from the attested source, and compares digests—reducing trust in the builder to trust in the *verifier's own* toolchain, which bootstrapping efforts [6] then minimize.

## 5 Empirical Evidence

The claims above are not merely theoretical; they are measured in production ecosystems.

- **Nixpkgs** is among the largest continuously-built package collections in existence (tens of thousands of packages), with the public Hydra/CI infrastructure rebuilding the entire graph on each channel advance and publishing every derivation's outputs to binary caches. Because store paths commit to inputs, cache substitution is verifiable by clients: a substituted path that fails `nix-store --verify-path` is rejected.
- **GNU Guix** runs `guix challenge` comparisons across independent build farms; published results show the overwhelming majority of the package graph reproducing bit-for-bit, with failures triaged through the project's reproducible-builds tracking [6]. Guix's `guix publish` signs store items, binding the functional model to authenticated distribution.
- **Debian's Reproducible Builds effort** [2] has driven the fraction of reproducible packages in the archive from a small minority (2014) to the large majority (stable releases), using `reprotest` (builds under systematic environment variation: different time, path, locale, timezone, user) and `diffoscope` as the diagnostic loop. The `SOURCE_DATE_EPOCH` specification is now honored across GCC, binutils, Python, Perl, TeX Live, and dozens of other toolchains.
- **SLSA adoption** [3] is measurable in the wild: major open-source projects publish SLSA provenance for release artifacts, and Sigstore-based signing has made keyless attestation practical. Combined with reproducible builds, projects such as Bitcoin Core's Gitian/Guix-based deterministic release process demonstrate multi-party, multi-builder verification in adversarial settings.
- **Trusting Trust, empirically**: Thompson's attack [5] has been re-demonstrated in controlled settings (including self-replicating compiler backdoors in exercises), and the *diverse double-compiling* (DDC) technique—Wheeler's proposed countermeasure—shows that reproducibility plus independent toolchain diversity detects exactly this attack class: a backdoored compiler cannot survive compilation by a second, independent compiler that produces a bit-identical result.

Quantitatively, the trend is unambiguous: each ecosystem that adopted hermetic evaluation plus `SOURCE_DATE_EPOCH`-style normalization converged toward near-total reproducibility of its package graph, with residual failures concentrated in a long tail of exotic build systems rather than in the model itself.

## 6 Limitations

1. **The bootstrap problem.** Hermetic builds bottom out at a seed: some initial binary toolchain must exist. Guix's bootstrappable-builds project has shrunk the seed dramatically, but a fully source-bootstrapped, audited-every-bit-down-to-machine-code pipeline remains aspirational. Thompson's attack [5] lives precisely in this gap: DDC mitigates it only if the two compilers are genuinely independent.
2. **Hardware and floating-point variance.** Bitwise identity across *different* CPU microarchitectures is not guaranteed for floating-point-heavy workloads (fused multiply-add contraction, denormal handling, SIMD code paths selected at runtime). Reproducibility claims must be scoped to a fixed target architecture.
3. **Nondeterminism by design.** Some build steps are intentionally entropic: cryptographic key generation, ASLR-derived test fixtures, or randomized algorithm seeds. These must be identified and either seeded deterministically (with the seed itself recorded) or excluded from the reproducibility claim—an ongoing source of long-tail failures.
4. **Attestation trust roots.** SLSA and in-toto move trust, they do not eliminate it: the layout keys, the transparency log (e.g., Rekor), and the verifier's own toolchain are trust anchors. A compromised key-management story reintroduces exactly the attacks attestation was meant to prevent [3][4].
5. **Impure escape hatches.** Real build systems retain `__noChroot`, network-enabled fixed-output derivations, and `allowUnfree` equivalents. Each is an auditable, explicit impurity—but a large package graph's *auditability* is only as good as its reviewers' diligence.
6. **Reproducibility is necessary, not sufficient.** A bit-identical build of a backdoored *source* reproduces the backdoor faithfully. Reproducibility verifies the build function, not the source's intent; source auditing, two-person review (SLSA L4), and formal verification remain complementary.

---

## 7 Conclusion

The purely functional deployment model [1] reconceived package management as evaluation of pure functions over explicit input closures; the Reproducible Builds project [2] supplied the engineering discipline that makes those functions deterministic in practice; and SLSA [3] with in-toto [4] supplied the attestation machinery that binds artifacts to their claimed provenance. Taken together, they answer Thompson [5] with an architecture rather than an admonition: make builds hermetic, make inputs content-pinned, make outputs deterministic, and make the entire pipeline independently re-executable and signed.

The empirical record—Nixpkgs, Guix, and Debian at scale—demonstrates that bitwise reproducibility is not a laboratory curiosity but an achievable property of industrial package graphs. The remaining frontiers are the bootstrap seed, hardware-scoped determinism, and the trust roots of attestation infrastructure. These are deep problems, but they are now *bounded* problems: the functional model gives us, for the first time, a precise language in which to state exactly what we trust and why.
