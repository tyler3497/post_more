# The Adya Formalism and the Theory of Serializability: Dependency Graphs, Predicate Locking, and Snapshot-Isolation Anomalies in Modern Databases

## Abstract

This thesis presents a unified treatment of the Adya formalism — the dependency-graph framework introduced in Atul Adya's 1999 MIT doctoral dissertation and refined with Liskov and O'Neil — as the canonical mathematical foundation for reasoning about transaction isolation levels and serializability [1][2]. We formalize the three dependency edge types (read-from, write-write, and anti-dependency), the phenomena hierarchy G0 through G2 that characterizes isolation strength, and the precise cycle conditions under which a history is serializable. We then analyze why snapshot isolation (SI), despite forbidding a large fragment of these phenomena, still admits non-serializable executions: write skew, phantoms, and the read-only anomaly [4][7]. We develop the dangerous-structure theory of Fekete, Liarokapis, and their collaborators, which proves that every SI anomaly contains two consecutive vulnerable read-write edges, and trace how this theorem became the runtime serializable snapshot isolation (SSI) implemented in PostgreSQL via SIREAD predicate locks [5][6]. Finally, we discuss the declarative reformulations of the framework and its modern role in static anomaly detection, robustness checking, and transaction chopping [8].

## 1 Introduction

The question of what it means for concurrently executing transactions to be *isolated* from one another has occupied database theory since the earliest work on concurrency control. The ANSI SQL-92 standard attempted to answer it with four isolation levels — READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, and SERIALIZABLE — each defined by the *prohibition* of three phenomena: dirty reads, non-repeatable reads, and phantoms. Berenson, Bernstein, Gray, Melton, O'Neil, and O'Neil demonstrated in their celebrated critique that this phenomenon-based specification was both ambiguous and insufficient: several widely deployed locking implementations permitted histories the standard appeared to forbid, and the standard forbade nothing at all about the write-write and anti-dependency structures that actually determine serializability [3].

Atul Adya's 1999 MIT PhD thesis, *Weak Consistency: A Generalized Theory and Optimistic Implementations for Distributed Transactions*, resolved this confusion by replacing the ad hoc ANSI phenomena with a single implementation-independent mathematical object: the **dependency serialization graph (DSG)** [1]. In Adya's framework, every isolation level — from READ COMMITTED to SERIALIZABLE, including commercial levels such as Cursor Stability and Snapshot Isolation — is specified as a constraint on which cycles may appear in the DSG.

This thesis reconstructs the Adya formalism from first principles, proves the central cycle theorems that connect graph structure to serializability, and uses the framework to explain one of the most practically important facts in modern database engineering: **snapshot isolation is not serializable**, and the precise shape of its non-serializability is now completely understood. We trace the line from Adya's anti-dependency through Fekete et al.'s dangerous-structure theorem [4], through the runtime SSI algorithms of Cahill, Röhm, and Fekete [5] and their production incarnation in PostgreSQL [6], to the declarative axiomatizations of Gotsman and collaborators [8].

## 2 Background

### 2.1 Histories, versions, and the multiversion model

We work in the standard multiversion transaction model. A *history* $H$ is a partial order of operations — reads $r_i[x]$, writes $w_i[x]$, commits $c_i$, aborts $a_i$ — over data items, where each write installs a new *version*. A history is *serializable* if it is view-equivalent to some serial history. Classical theory characterizes serializability through conflict-based serialization graphs; Adya generalized this graph to the multiversion setting and added the third edge type that conflict serializability omits [1][2].

### 2.2 The three dependency edges

For committed transactions, Adya defines three relations over pairs of transactions:

- **Read-dependency (wr, "read-from"):** $T_j$ *read-depends* on $T_i$ (written $T_i \xrightarrow{wr} T_j$) if $T_j$ reads a version of some item $x$ that was written by $T_i$.
- **Write-dependency (ww, "overwrite"):** $T_i \xrightarrow{ww} T_k$ if $T_k$ installs the version of $x$ immediately following $T_i$'s version in the version order.
- **Anti-dependency (rw):** $T_j$ *anti-depends* on $T_i$ (written $T_i \xrightarrow{rw} T_j$) if $T_i$ reads a version of $x$ and $T_j$ installs a later version of $x$ in the version order. Equivalently, $T_j$ overwrites a value that $T_i$ observed.

The anti-dependency is the formalism's key innovation. Classical conflict graphs record only read-write *conflicts* between concurrent operations; Adya's rw-edge is *derived* from the wr- and ww-edges together with the version order, and it is defined even for transactions that never overlap in time [2].

### 2.3 The phenomena hierarchy

Adya re-expresses isolation anomalies as *phenomena* — forbidden patterns in the DSG — replacing the ANSI list with a mathematically precise hierarchy [1]:

| Phenomenon | Name | Graph characterization |
|---|---|---|
| G0 | Write cycle | Cycle consisting solely of ww-edges |
| G1a | Aborted read | Committed $T_j$ reads a version written by aborted $T_i$ |
| G1b | Intermediate read | $T_j$ reads a version of $x$ that $T_i$ later overwrites within $T_i$ |
| G1c | Circular information flow | Cycle consisting solely of wr-edges |
| G-single | Lost update (single item) | ww-cycle on a single item with an intervening read |
| G2-item | Anti-dependency cycle (single item) | Cycle with one or more rw-edges over one item |
| G2 | Anti-dependency cycle | Cycle with one or more rw-edges (general) |

Each isolation level is then defined by the phenomena it forbids [2]:

- **READ COMMITTED** forbids G1a, G1b, G1c.
- **Snapshot Isolation** additionally forbids G0, G-single, and G2-item — but *permits* G2 in general, which is precisely why SI is not serializable.
- **SERIALIZABLE** forbids all phenomena, i.e., requires an acyclic DSG.

> **Theorem (Serializability via acyclicity):** A history $H$ over committed transactions is serializable iff its DSG contains no directed cycle. *Proof sketch.* If the DSG is acyclic, any topological order yields a serial history with identical wr-, ww-, and rw-relations, hence view-equivalent to $H$. Conversely, a serial history's DSG is acyclic because every edge type respects commit order, and view-equivalence preserves all three edge types. ∎

This theorem is the engine of the entire framework: it reduces the semantic question "is this execution serializable?" to the graph-theoretic question "does this graph contain a cycle?" [1].

## 3 Methodology

Our method is *formal-analytic*: we reconstruct Adya's definitions, derive the cycle theorems, and apply them as a diagnostic instrument to snapshot isolation. The analysis proceeds in three stages.

First, we formalize SI operationally — start-timestamp snapshots, first-committer-wins write-write conflict detection — and derive exactly which DSG phenomena SI can and cannot produce, reproducing Adya's result that SI forbids G0, G-single, and G2-item while admitting G2 [1].

Second, we present the *dangerous-structure* refinement due to Fekete, Liarokapis, and co-authors: every SI anomaly contains **two consecutive rw-edges**, each between concurrent transactions [4]. The transaction at the junction is the *pivot* — a runtime-detectable pattern that converts an abstract graph property into an enforceable check.

Third, we trace the engineering path from theorem to system: Cahill, Röhm, and Fekete's SSI algorithm, which tracks rw-antidependencies at runtime using non-blocking SIREAD locks and aborts transactions that complete a dangerous structure [5], and Ports and Grittner's production implementation in PostgreSQL 9.1, which added predicate locking, safe snapshots, and deferrable transactions [6].

Throughout, we validate claims against the primary sources and cross-check the graph-theoretic arguments with executable specifications.

## 4 Deep Dive

### 4.1 The DSG, precisely

Let $H$ be a history and let $<_H$ denote the version order induced by $H$. The **dependency serialization graph** $\mathrm{DSG}(H)$ has as vertices the committed transactions of $H$, with edges defined as follows [1][2]:

1. $T_i \xrightarrow{wr} T_j$ iff $T_j$ reads $x$ from a version installed by $T_i$.
2. $T_i \xrightarrow{ww} T_j$ iff $T_j$ installs the next version of $x$ after $T_i$'s version in $<_H$.
3. $T_i \xrightarrow{rw} T_j$ iff $T_i$ reads a version of $x$ installed before $T_j$'s version, i.e., $T_j$ overwrites data $T_i$ observed.

Note the asymmetry: wr- and ww-edges record *information flow* and *overwrite order*, while rw-edges record *missed* information flow — $T_i$ read a value that $T_j$ subsequently invalidated. A cycle containing an rw-edge therefore represents transactions whose observations are mutually inconsistent with any serial order. We can express the DSG construction directly:

```tla
------------------------------- MODULE DSG --------------------------------
EXTENDS Naturals, FiniteSets
CONSTANTS Txn, Item
VARIABLES wr, ww, rw  \* edge relations over Txn \times Txn

TypeOK == /\ wr \in SUBSET (Txn \times Txn)
          /\ ww \in SUBSET (Txn \times Txn)
          /\ rw \in SUBSET (Txn \times Txn)

\* Anti-dependency derived from read and write relations:
\* Ti -rw-> Tj iff Ti read x before Tj overwrote x in version order.
DeriveRW(readVer, writeVer) ==
    rw = { <<ti, tj>> \in Txn \times Txn :
             \E x \in Item : readVer[ti][x] < writeVer[tj][x] }

Acyclic(R) == \A S \in SUBSET Txn : S # {} =>
    \E t \in S : \A u \in S : <<u, t>> \notin R

Serializable == Acyclic(wr \cup ww \cup rw)
=============================================================================
```

The final predicate is the executable content of Adya's theorem: serializability *is* acyclicity of the union of the three relations [1].

### 4.2 Phenomena as forbidden subgraphs, and the isolation lattice

The phenomena G0–G2 are best understood as *forbidden subgraph families*. G0 (a pure ww-cycle) is exactly the lost-update pattern: two transactions each overwrite the other's write with no intervening read, so one update is silently lost. G1c (a pure wr-cycle) is circular information flow — $T_1$ reads from $T_2$ which reads from $T_1$ — impossible in any system that orders versions coherently, and indeed forbidden even at READ COMMITTED. G2, the general anti-dependency cycle, is the watershed: it is the *only* cyclic phenomenon that SI admits, and forbidding it (in addition to everything SI already forbids) yields exactly SERIALIZABLE [2].

This yields the clean lattice:

```
                    SERIALIZABLE
                   (acyclic DSG)
                        |
              forbids G2 (general rw-cycle)
                        |
               SNAPSHOT ISOLATION
        (forbids G0, G1, G-single, G2-item)
                        |
              forbids G-single, G2-item
                        |
        REPEATABLE READ / CURSOR STABILITY ...
                        |
                   READ COMMITTED
              (forbids G1a, G1b, G1c)
```

Each step up the lattice forbids a strictly larger family of cycles. The ANSI standard's failure, diagnosed by Berenson et al. [3] and repaired by Adya [1], was that its three phenomena (dirty read, non-repeatable read, phantom) corresponded to *no* consistent cut through this lattice: they were neither necessary nor sufficient for the levels they purported to define.

### 4.3 Predicate locking: from items to predicates

Real transactions do not only read and write individual items; they evaluate *predicates* — `SELECT ... WHERE balance < 0`, range scans, joins. Adya extended the DSG to predicate-based operations by defining *predicate read-dependencies* and *predicate anti-dependencies*: a transaction that evaluates predicate $P$ and a transaction that inserts, deletes, or modifies a tuple matching $P$ are related by a predicate rw-edge, even though no single pre-existing item is shared [1].

This gives the first implementation-independent account of *phantoms*: a phantom is precisely a predicate rw-dependency that participates in a cycle. Adya further specified two implementation strategies. **Exact predicate locking (EPL)** tracks the logical predicate itself, while **approximate predicate locking** conservatively covers predicates with coarser granules (tables, index ranges), trading false positives for tractability [1][7].

```haskell
-- Predicate dependency detection, in the spirit of Adya's EPL
data Op = Read Item | Write Item | PredRead Predicate | PredWrite Predicate

-- A predicate anti-dependency: T_i evaluated P, T_j later wrote a tuple matching P
predAntiDep :: [Op] -> [Op] -> [Predicate]
predAntiDep reads writes =
  [ p | PredRead p <- reads
      , PredWrite q <- writes
      , overlaps p q ]
  where overlaps p q = satisfiable (p `intersect` q)  -- conservative: may over-approximate
```

The `overlaps` check is necessarily conservative in practice — exact satisfiability of arbitrary predicates is undecidable in general — which is why production systems (notably PostgreSQL's SSI) implement predicate locking at page and relation granularity [6].

### 4.4 Snapshot isolation through the Adya lens

Snapshot isolation, introduced by Berenson et al. [3] and deployed in Oracle, PostgreSQL, and SQL Server, gives each transaction $T$ a *start timestamp* $s(T)$; $T$ reads the latest versions committed before $s(T)$, and at commit $T$ aborts (first-committer-wins) if any concurrent transaction committed a write to an item $T$ also wrote. In DSG terms [1][4]:

1. **Reads never block and never observe concurrent writes** (they read from the snapshot), so G1a and G1b are impossible.
2. **First-committer-wins** forbids concurrent ww-edges on the same item, eliminating G0 and G-single.
3. **Snapshot reads plus write-write detection** forbid G2-item: a single-item rw-cycle would require a ww-edge the protocol prevents.

But **G2 in general survives**. The canonical counterexample is *write skew*:

```
H_ws = r1[x] r1[y] r2[x] r2[y] w1[x] w2[y] c1 c2
```

with invariant $x + y \ge 0$, initially $x = y = 50$. Each transaction reads both balances, then withdraws 100 from a *different* account after checking the invariant. The DSG contains $T_1 \xrightarrow{rw} T_2$ (via $y$: $T_1$ read $y = 50$, $T_2$ overwrote it) and $T_2 \xrightarrow{rw} T_1$ (via $x$) — a two-edge rw-cycle, hence non-serializable, yet both transactions commit under SI because their write sets are disjoint [4]. The database ends at $x = y = -50$, violating the invariant each transaction individually preserved.

A subtler anomaly is the **read-only transaction anomaly** of Fekete, O'Neil, and O'Neil: a *read-only* transaction executing concurrently with update transactions can observe a state that never existed in any serial order — even though it writes nothing and the update transactions are pairwise serializable [7].

### 4.5 Dangerous structures: the pivot theorem

Fekete, Liarokapis, and colleagues transformed Adya's existential observation ("SI admits G2 cycles") into a precise structural characterization with direct algorithmic consequences [4]:

> **Theorem (Dangerous structure):** In any non-serializable execution admitted by SI, the DSG cycle contains **two consecutive rw-edges** $T_i \xrightarrow{rw} T_j \xrightarrow{rw} T_k$, each connecting *concurrent* transactions. The middle transaction $T_j$ is called the **pivot**.

The practical import is enormous. Rather than materializing the entire DSG — infeasible at runtime — a system need only detect the local pattern: a transaction with **both an incoming and an outgoing rw-edge to concurrent transactions**. Such a *dangerous structure* is a necessary condition for an SI anomaly, and SSI resolves it by aborting one participant — sacrificing some serializable executions to guarantee that no anomaly ever commits [5]. The runtime check is a local graph query:

```python
class TxnState:
    def __init__(self, tid, start_ts):
        self.tid = tid
        self.start_ts = start_ts
        self.in_rw = set()   # tids with rw-edge INTO self (they overwrote what I read)
        self.out_rw = set()  # tids with rw-edge OUT of self (I overwrote what they read)

def concurrent(a: TxnState, b: TxnState, commit_ts: dict) -> bool:
    # lifetimes [start, commit] overlap
    return not (commit_ts[a.tid] < b.start_ts or commit_ts[b.tid] < a.start_ts)

def is_pivot(t: TxnState, commit_ts: dict, states: dict) -> bool:
    """Dangerous structure: incoming and outgoing vulnerable rw-edges."""
    in_vuln = any(concurrent(t, states[u], commit_ts) for u in t.in_rw)
    out_vuln = any(concurrent(t, states[v], commit_ts) for v in t.out_rw)
    return in_vuln and out_vuln
```

A pivot *may* be part of a genuine cycle (a true anomaly) or a false positive (the edges belong to no common cycle). SSI resolves this by aborting one transaction in the dangerous structure — sacrificing some serializable executions to guarantee that no anomaly ever commits [5].

## 5 Empirical Results and Proofs

### 5.1 The SSI algorithm and its correctness argument

Cahill, Röhm, and Fekete's **Serializable Snapshot Isolation (SSI)** [5] implements the dangerous-structure theory as follows. Every read acquires a lightweight, non-blocking **SIREAD lock** (at tuple, page, or relation granularity); a later write to a SIREAD-locked item or predicate range records an rw-antidependency edge. At commit, the system checks whether the committing transaction completes a dangerous structure — i.e., whether it is, or is adjacent to, a pivot — and aborts if so. The central theorem:

> **Theorem (SSI correctness):** If every dangerous structure is resolved by aborting at least one participating transaction before commit, no non-serializable execution commits. *Proof.* By the pivot theorem, every SI anomaly's DSG cycle contains a dangerous structure with a pivot; aborting a participant breaks every such cycle; the surviving DSG is acyclic, hence serializable by Adya's theorem. ∎

Cahill et al. validated SSI empirically on a multiversion storage engine: on TPC-C-like and microbenchmark workloads, SSI achieved throughput within a few percent of plain SI while aborting only transactions forming dangerous structures — far fewer than serializable 2PL, with zero anomalies across millions of committed transactions [5].

### 5.2 PostgreSQL: SSI in production

Ports and Grittner brought SSI to PostgreSQL 9.1, replacing its former "serializable-is-actually-SI" behavior with true serializability [6]. Their implementation added several production necessities the theory paper elided:

1. **Predicate locking via SIREAD locks** at multiple granularities, with promotion from tuple to page to relation level under memory pressure — the engineering realization of Adya's approximate predicate locking [1].
2. **Safe snapshots**: a read-only transaction using a snapshot with no concurrent read-write transactions is provably anomaly-free without SSI bookkeeping, directly exploiting the analysis of the read-only anomaly [7].
3. **Deferrable transactions**: `SERIALIZABLE, DEFERRABLE` blocks until a safe snapshot is available, giving read-heavy workloads serializability at essentially zero abort cost.
4. **Summarization and cleanup** of serialization-graph state, bounding the memory overhead of tracking rw-edges in long-running systems.

Measured results showed SSI matching plain-SI throughput on standard benchmarks while providing genuine serializability — the first widely deployed database to do so on a multiversion engine [6].

### 5.3 Static analysis: making programs anomaly-free by construction

The pivot theorem also enables *static* guarantees. Jorwekar, Fekete, Ramamritham, and Sudarshan developed automated analyses that examine transaction *programs* (rather than executions) and identify the minimal set of programs that must be modified — e.g., by promoting selected reads or adding explicit locking — to guarantee that no dangerous structure can ever arise [4, and follow-up work]. Gotsman, Cerone, and collaborators later recast the entire Adya framework declaratively, axiomatizing isolation levels as constraints over abstract executions (visibility and commit-order relations) and proving the dependency-graph characterization sound and complete; their framework supports *robustness* checking (does a program behave the same under a weaker level as under serializability?) and *transaction chopping* (splitting transactions without introducing new behaviors) [8].

This static direction closes the loop Adya opened: from a mathematical characterization of isolation, to a runtime enforcement mechanism, to compile-time verification that enforcement is unnecessary [4][8].

## 6 Limitations

The Adya formalism has well-understood boundaries. First, it is a theory of **single-node, non-replicated** histories: the DSG is defined over one version order, and replicated or geo-distributed stores need additional machinery [8]. Second, it characterizes *which* executions are permitted but says nothing about *performance*: SSI's abort-based resolution of dangerous structures can, under adversarial workloads, abort far more than necessary [5]. Third, predicate reasoning remains fundamentally approximate — exact predicate locking is infeasible for expressive predicate languages, so phantom protection in real systems is always conservative, and conservatism means false-positive aborts [1][6]. Fourth, the pivot condition is *necessary* but not *sufficient* for anomaly: most runtime-detected dangerous structures are benign, which is why SSI aborts speculatively and static analysis remains active research [4][8]. Finally, the formalism assumes a closed world of known transactions; ad hoc queries complicate both runtime tracking and static verification [4].

## 7 Conclusion

Adya's dependency-graph formalism accomplished something rare in systems research: it replaced a confused, implementation-entangled standard with a single mathematical object — the DSG — from which every isolation level falls out as a cycle-avoidance condition [1][2]. Its most enduring practical consequence is the complete theory of snapshot-isolation anomalies. Because SI forbids every cyclic phenomenon *except* the general anti-dependency cycle G2, every SI anomaly is a G2 cycle; because every such cycle contains two consecutive vulnerable rw-edges, every anomaly has a pivot; and because pivots are locally detectable via SIREAD predicate locks, serializability can be enforced at runtime with near-SI performance [4][5][6]. The line from the 1999 thesis to PostgreSQL's SSI is thus unusually direct: a graph-theoretic characterization became, within a decade, the concurrency control of one of the world's most widely deployed databases [8].
