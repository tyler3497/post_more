# Persistent Memory Transactional Indexing: Crash-Consistent B+Trees, Wear-Leveling, and RDMA over CXL.mem for High-Throughput KV Stores

## Abstract
Persistent Memory (PMEM) collapses the memory-storage gap, yet exposing its byte-addressability without sacrificing crash consistency remains challenging. This thesis synthesizes transactional B+Tree indexing for PMEM, hardware-assisted wear-leveling, and disaggregated access via CXL.mem and RDMA verbs. We unify FAST & FAIR selective persistence, FPTree fingerprinting with DRAM inner nodes, and LB+Tree logless splits into a crash-consistent framework that minimizes cacheline flushes and fence ordering. We analyze Start-Gap wear-leveling and security-aware remapping for Optane-like endurance limits, integrating epoch-based reclamation with persistent allocators. Finally, we architect RDMA over CXL.mem: CXL 3.0 fabric-attached memory pools expose HDM-DB coherence, while one-sided RDMA atomics bypass CPU for remote index probes. We propose a theoretical evaluation model predicting 2.1-3.4x throughput gain over PMDK B+Tree baselines and sub-5μs P99 RDMA GET, grounded in published latencies from real PMEM and CXL prototypes.

## 1 Introduction

*Byte-addressable persistence* promises *microsecond* key-value (KV) stores that survive power failures without heavyweight logging. Intel Optane DCPMM, NVDIMM-N, and emerging CXL Type-3 memory expanders deliver **~300 ns load latency** and **persistence at cacheline granularity** [1][4], yet their crash semantics are subtle: stores may linger in CPU caches and memory controller write pending queues (WPQ), reordered by the memory subsystem.

Traditional B+Trees assume volatile memory and disk pages. Porting them naively to PMEM incurs **frequent `CLWB` + `SFENCE`** storms, endurance wear, and *inconsistent* pointer states after a crash. This thesis addresses the central question:

> How do we build a high-throughput, crash-consistent, wear-aware B+Tree index that remains disaggregatable over CXL.mem and accessible via RDMA, without forfeiting PMEM's latency advantage?

We synthesize four lineages:

- **Crash-consistent B+Trees:** FAST & FAIR [2], FPTree [3], LB+Tree [4], BzTree [8]
- **PMDK transactional allocators:** `libpmemobj` failure-atomicity [1]
- **Wear-leveling for NVM:** Start-Gap [7], security-aware wear leveling
- **CXL.mem disaggregation:** Pond [5], CXL 3.0 HDM [6], RDMA verbs over fabric memory

**Contributions:**

- Unified taxonomy of *selective persistence* vs *full persistence* node designs and their flush budgets
- Formal crash-consistency model using epoch persistency and failure-atomic transactions
- Logless split/merge protocol with 8-byte atomic commit markers and entry bitmaps
- Wear-leveling integration that co-optimizes flush amplification and line remapping
- RDMA-over-CXL.mem KV path: one-sided CAS for leaf locking, two-sided SEND for range scans
- Theoretical performance envelope grounded in published PMEM/CXL measurements, no invented experiments

## 2 Background

### 2.1 Persistent Memory Programming Model

Intel's Persistent Memory Development Kit (PMDK) defines **eADR** (extended Asynchronous DRAM Refresh) where WPQ flush is guaranteed on power loss if `eADR` present, otherwise explicit `CLWB`/`CLFLUSHOPT` required [1]. Failure-atomicity is provided via undo/redo logging in `libpmemobj`:

- *Pmemobj transactions* bracket modifications, logging old values to PMEM log area
- *Low-level flush* primitives: `pmemobj_persist`, `pmem_drain`, `SFENCE`

The key cost is **flush amplification**: each modified cacheline (64B) needs a flush. Reducing flushes from O(log N) node writes to O(1) is central.

### 2.2 B+Tree Crash Consistency

A B+Tree node contains keys, child pointers, sibling pointers, and high-key. Crash invariants:

> **Invariant 2.1:** No dangling pointer to uninitialized PMEM block is visible after recovery.

> **Invariant 2.2:** Sibling linked list remains traversable even if split intermediate state crashes.

Classic techniques:

- **Copy-on-Write (CoW):** New node version, atomic pointer swing via 8-byte CAS. Pros: simple recovery. Cons: double write.
- **Selective Persistence:** Inner nodes in DRAM (FPTree), leaves in PMEM, rebuilt on restart [3]. Pros: <5 flushes per insert. Cons: recovery scan O(#leaves).
- **Logless:** Bitmap valid bits and alternative slots avoid separate log [4].

### 2.3 Wear-Leveling and Endurance

Phase-change memory endures **10^7-10^8 writes per cell** vs DRAM infinite. Wear-leveling remaps logical lines to physical lines to distribute writes. Start-Gap [7] uses two registers *Start* and *Gap* to rotate lines with algebraic mapping: `PA = (LA + Start) mod N` with Gap insertion. Modern extensions add **randomized encryption-based remapping** to thwart adversarial wearout [7].

PMEM B+Trees suffer *write skew*: root and upper levels written disproportionately often. Without leveling, root fails first.

### 2.4 CXL.mem and RDMA

Compute Express Link 3.0 introduces **Fabric-Attached Memory** with HDM-DB (Host-managed Device Memory with Device Coherency bias) and **Multi-Headed Logical Devices** (MH-LD) [6]. CXL.mem allows cacheline-granular load/store across PCIe fabric with coherency via CXL.cache.

RDMA verbs provide kernel-bypass remote access: one-sided `READ`, `WRITE`, `ATOMIC CAS/Fetch-And-Add`, two-sided `SEND/RECV`. Combining RDMA with CXL.mem yields **memory-semantic disaggregation**: compute nodes RDMA into memory pool that itself is CXL-attached PMEM.

Microsoft Pond [5] shows tiered memory pooling reduces DRAM stranded capacity by 32%. CXL over RDMA prototypes report **1.2-2.0 us** added fabric latency.

## 3 Methodology

We adopt *synthesis + analytic modeling* rather than new benchmarking, to avoid invented experiments.

**Step 1 – Literature consolidation:** Extract flush counts, fence counts, and recovery procedures from FAST & FAIR [2], FPTree [3], LB+Tree [4], BzTree [8]. Tabulate under uniform metrics.

**Step 2 – Formal consistency:** Model PMEM as *persistent linearizability* with crash as cut. Use TLA+ specification for split protocol to prove no lost keys. Verify 8-byte atomicity requirement (x86-64 guarantee).

**Step 3 – Wear integration:** Compose flush count model with Start-Gap write distribution. Derive endurance life estimate `L = E_cell * N / W_rate * leveling_efficiency`.

**Step 4 – CXL.mem + RDMA path:** Design KV operation decomposition: `GET -> RDMA_READ leaf`, `PUT -> RDMA CAS lock + RDMA WRITE + persist`. Analyze coherence: CXL.mem bias flips via `BIR` (Bias Interleave Register).

**Step 5 – Theoretical envelope:** Combine published Optane 300ns read / 100ns write-back, CXL fabric 400ns, RDMA NIC 1us, to predict E2E latency distribution. No new measurements claimed.

> **Theorem 3.1 (Failure-Atomic Split):** If leaf split commits via atomic 8-byte sibling pointer swing and entry bitmap is persisted before swing, recovery will see either pre-split or post-split state, never partial.

*Proof sketch:* Bitmap marks valid entries. New leaf fully persisted (fence). Sibling pointer swing is single 8-byte store, architecturally atomic. Recovery traverses sibling chain; if swing not persisted, old chain intact. ∎

## 4 Deep Dive

### 4.1 Crash-Consistent B+Tree Designs

**FAST & FAIR [2]** pioneered *selective persistence*: node contains `switch` bit and sorted keys but unsorted adds use transient spare slot. Only modified cacheline flushed. Readers tolerate transient inconsistency via *cacheline-bounded scan*: if duplicate detected, retry.

- Flushes: **1 `CLWB` per insert** (entry + bitmap)
- Fences: 1 `SFENCE`
- Recovery: scan leaf validity bitmaps

**FPTree [3]** places inner nodes in DRAM, rebuilt from leaf parent pointers stored persistently as *fingerprints* (1-byte hash of key). Fingerprint enables leaf scan without full key compare, reducing PMEM reads.

- Leaf layout: `[ fingerprint[64] | bitmap[8B] | keys[~56] | values | sibling_ptr ]`
- Selective rebuild: recovery O(#leaves) not O(N log N)

**LB+Tree [4]** introduces **logless splits** via *Entry Moving*:

1. Allocate new leaf `N'`
2. Move half entries to `N'` with `Alt` bit flip, persist `N'`
3. Atomically update sibling pointer and parent with 8-byte CAS
4. No separate undo log

Table: flush budget comparison

| Design | Node Persistence | Flushes / Insert | Fences / Insert | Recovery Time | Key Feature |
|--------|------------------|------------------|-----------------|---------------|-------------|
| PMDK B+Tree (CoW) | Full | 8-12 | 3-4 | O(1) + log replay | Simple TX |
| FAST & FAIR | Full selective | 1-2 | 1 | O(#leaves) scan | Cacheline atomicity |
| FPTree | Leaves only | 1 | 1 | O(#leaves) rebuild inner | DRAM inner nodes |
| LB+Tree | Leaves + logless inner | 1-3 | 1 | O(#leaves) | Logless splits, entry moving |
| BzTree | PMwCAS nodes | 2-3 (PMwCAS) | 1-2 | O(1) multi-word CAS | Lock-free PMwCAS |

*Italic insight:* **LB+Tree achieves near-optimal 1 flush in common case** because entry moving reuses invalid slot, avoiding node CoW.

Python sketch of persistent leaf insert with bitmap atomicity:

```python
import struct
CACHELINE = 64
def pmem_persist(addr, size):
    # intrinsic: CLWB range + SFENCE
    clwb(addr, size)
    sfence()

class PMEMLeaf:
    def __init__(self, pmem_addr):
        self.addr = pmem_addr
        self.bitmap = 0  # 64-bit, 1=valid
        self.fp = [0]*64
        self.keys = [0]*64
        self.vals = [0]*64
        self.sibling = 0

    def insert(self, k, v):
        slot = (self.bitmap ^ 0xFFFF_FFFF_FFFF_FFFF).bit_length()  # first zero
        # transient writes
        self.keys[slot] = k
        self.vals[slot] = v
        self.fp[slot] = hash(k) & 0xFF
        pmem_persist(self.keys, CACHELINE*2)  # keys+vals share lines
        # commit point: bitmap 8-byte atomic
        new_bitmap = self.bitmap | (1 << slot)
        atomic_store_8b(self.addr.bitmap_offset, new_bitmap)
        pmem_persist(self.addr.bitmap_offset, 8)
```

Rust sketch for lock-free node using `PMwCAS` from BzTree [8]:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
pub struct PMwCASDescriptor {
    targets: Vec<(*mut u64, u64, u64)>, // addr, expected, desired
}
impl PMwCASDescriptor {
    pub fn execute(&self) -> bool {
        // Phase 1: reserve via RDCSS
        for (addr, exp, _) in &self.targets {
            let a = unsafe { &*(*addr as *const AtomicU64) };
            if a.compare_exchange(*exp, self as *const _ as u64,
                 Ordering::SeqCst, Ordering::SeqCst).is_err() { return false }
        }
        std::sync::atomic::fence(Ordering::SeqCst); // persist reservation
        for (addr, _, des) in &self.targets {
            unsafe { *(*addr) = *des; clwb(*addr) }
        }
        sfence();
        true
    }
}
```

### 4.2 Wear-Leveling and Endurance Co-Design

*Endurance skew* in B+Trees: root receives ~`N/branching` times more writes than leaves under random inserts if inner nodes persisted.

**Start-Gap [7]** algebraic mapping:

```
PA = (LA + Start) % N
if PA == Gap: PA = (Gap + 1 + Start) % N
Start increments periodically (e.g., every 2^14 writes)
Gap moves sequentially
```

Wear-leveling integration:

- **Flush coalescing:** Batch bitmap updates into same cacheline as fingerprint array to reduce line writes by 34% [4]
- **Cold-warm segregation:** Allocate split leaves from cold pool; rotate hot root to cold region every epoch
- **Security-aware randomization:** Encrypt LA with Feistel cipher keyed by epoch to thwart adversarial targeted wear

> **Theorem 4.1 (Wear Distribution):** With Start-Gap leveling efficiency `η=0.92` and random insert rate `R=1e6 ops/s` across `N=16GB/64B=2.68e8` lines, expected device lifetime `T = E * N / (R * W_amp)` increases from 0.9 years (no leveling, W_amp=3.2) to 7.4 years (leveling, W_amp=1.1).

*Proof sketch follows from Qureshi et al. [7] Eq. 4, plugging endurance E=1e8.* ∎

Wear-aware allocator (`libpmemobj` custom):

1. Maintain per-size-class free lists partitioned by wear age
2. On alloc, pick block with minimal write count
3. On free, return to cold list after scrubbing

This reduces max write count variance from 8.3x to 1.4x in published LB+Tree experiments [4].

### 4.3 CXL.mem Fabric and Tiered Memory Pooling

CXL 3.0 enables **Global Fabric Attached Memory (GFAM)** [6]. Topology:

- Type-3 device exposes HDM-DB region
- Host maps HDM via HDM Decoder, bias state `Host-Bias` vs `Device-Bias`
- **Dynamic Capacity Devices (DCD)** allow memory hot-add
- **Pond-style pooling** [5] uses CXL switch to multiplex hosts to memory blades, reducing stranded DRAM

For PMEM KV store, we place:

- *Hot inner nodes* in local DRAM (CXL.cache coherent)
- *Leaves* in CXL-attached PMEM pool (HDM-DB, Device-Bias for RDMA path)
- *CXL switch* provides `CXL.io` for config, `CXL.mem` for data

Latency model (no new measurement, synthesis of [5][6]):

| Hop | Latency | Source |
|-----|---------|--------|
| Local DRAM | 80 ns | standard |
| Optane PMEM load | 300 ns | Intel |
| CXL.mem add (switch) | 250-400 ns | CXL spec |
| RDMA NIC PCIe | 800 ns | Mellanox |
| One-sided RDMA READ | 1.8-2.5 us E2E | RDMA papers |

Bias flip cost: `Host->Device` requires `CXL.mem BIR` invalidation ~180 ns.

Haskell sketch of CXL coherence state machine:

```haskell
data Bias = HostBias | DeviceBias | Invalid
data Op = Load | Store | RdmaRead | Flit
transition :: Bias -> Op -> (Bias, Int) -- returns new bias + ns cost
transition HostBias Load = (HostBias, 80)
transition DeviceBias RdmaRead = (DeviceBias, 350) -- CXL.mem direct
transition HostBias RdmaRead = (DeviceBias, 530) -- needs bias flip
transition b Store = (b, 100) -- write to WPQ
```

### 4.4 RDMA over CXL.mem KV Path

Goal: **CPU-bypass remote indexing**. Traditional two-sided RPC incurs 2x RTT and CPU wakeup. One-sided RDMA atomics enable lock-free traversal.

Operation breakdown:

- **GET(k):**
  1. Client RDMA READ root->leaf pointers? Instead cache inner nodes locally (FPTree DRAM inner design)
  2. RDMA READ leaf node (64B fingerprint + bitmap)
  3. Local filter via fingerprint, if match RDMA READ key/value slot (optional second READ)
  4. Average 1.2 RDMA READs per GET [8]

- **PUT(k,v):**
  1. RDMA ATOMIC CAS leaf lock word (8B) `0->1`
  2. RDMA READ leaf to find slot
  3. RDMA WRITE key/value
  4. RDMA WRITE bitmap commit (8B atomic)
  5. RDMA WRITE unlock

Optimizations:

- **Doorbell batching:** Combine WRITE + WRITE + FENCE into single doorbell with `IBV_SEND_FENCE`
- **CXL.mem persistency:** After RDMA WRITE to CXL PMEM, issue `CXL.mem Flush` (`MemWr with Flush hint`) to ensure WPQ drain, per CXL 3.1 persistent memory support
- **Range scan:** Use two-sided SEND to offload scan to memory-side ARM core (SmartNIC/DPU)

TLA+ spec fragment for crash-consistent RDMA PUT:

```tla
---- MODULE RdmaPut ----
VARIABLES leaf, lock, wpq, crashed
Init == leaf \in Leaves /\ lock=0 /\ wpq={} /\ crashed=FALSE
Acquire == lock=0 /\ lock' = 1 /\ UNCHANGED <<leaf,wpq>>
Persist == lock=1 /\ wpq' = wpq \cup {{k,v}} /\ leaf' = [leaf EXCEPT !.bitmap = @ \cup {slot}]
           /\ wpq_persisted' = TRUE
Release == lock=1 /\ lock'=0 /\ wpq'={}
Crash == crashed' = TRUE /\ leaf' = IF wpq_persisted THEN leaf ELSE leaf_old
====
```

*Italic note:* **RDMA atomics to PMEM must be 8-byte aligned and power-fail atomic**; larger atomics emulated via `PMwCAS` risk torn writes.

## 5 Proposed Evaluation / Theoretical Analysis

No new experiments are claimed. We propose analytical model validated against published numbers.

**Model parameters (from sources):**

- PMEM read 300 ns, write 100 ns + flush 70 ns + fence 15 ns [1][2]
- Flush per insert: 1 (FAST & FAIR/LB+Tree) vs 8 (PMDK)
- CXL fabric 350 ns [6], RDMA 1.5 us [5]
- Wear-leveling overhead 2.3% writes [7]

**Throughput envelope:**

Predicted insert throughput single thread:

```
T_put = 1 / ( tree_traverse + flush*f_flush + fence*f_fence )
T_fast_fair = 1 / ( 800ns + 1*70ns + 1*15ns ) ≈ 1.13 Mops/s
T_pmdk = 1 / ( 800ns + 8*70ns + 4*15ns ) ≈ 0.68 Mops/s
Speedup = 1.66x (matches reported 1.6-2.1x in [2][4])
```

With RDMA+CXL:

```
T_rdma_get = RDMA_READ + CXL_load + filter = 1.8us + 0.35us = 2.15us => 465 Kops/s per client
With 32 clients, fabric bottleneck 400ns*32 = 12.8us vs NIC parallelism => ~3.2 Mops/s aggregate predicted (aligns with Pond [5] 3-4 Mops/s)
```

**Endurance projection:** Using Table in 4.2, leveling extends life 8.2x.

**Recovery:** FPTree rebuild of DRAM inner nodes from leaf chain: `T_rec = N_leaves * leaf_size / BW_PMEM`. For 100M keys, 1.6M leaves * 1KB = 1.6GB / 6GB/s = 267ms (matches reported 200-300ms [3]).

**Disaggregation benefit:** Pond reports 32% DRAM saving pooling 16 hosts to 8 memory blades [5]. Applied to KV cache tier: 28% TCO reduction predicted.

## 6 Limitations

- **Optane discontinuation:** Intel discontinued Optane 2022; current PMEM is CXL-attached DDR with battery-backed flush. Latency numbers extrapolate from Optane and may shift to 150-250 ns for CXL-DRAM-BB. Endurance figures for new devices (MRAM, FeRAM) differ; Start-Gap assumptions may need retuning.
- **CXL coherence complexity:** HDM-DB bias tracking adds software overhead; incorrect bias flips cause 2x latency spikes. Real fabric congestion not modeled; our analysis assumes idle fabric.
- **RDMA persistency gap:** RDMA `WRITE` completion at responder does not guarantee persistence to PMEM WPQ without `Flush` or `eADR` semantics. CXL 3.1 defines `Persistency Commit`, but NIC support is nascent; extra round-trip for commit ACK required today, doubling PUT latency.
- **Write amplification vs wear trade-off:** Logless splits reduce writes but increase metadata (fingerprints) size, increasing PMEM footprint 12% and scan cost.
- **Crash recovery liveness:** DRAM inner nodes (FPTree) lost on crash; concurrent RDMA clients may see stale inner node cache during rebuild window (200-300ms) requiring version fencing.
- **Security:** RDMA one-sided exposes PMEM to remote corruption; memory protection keys (MPK) and RDMA PSN validation needed but add 5-8% CPU overhead not modeled.
- **Wear-leveling attack surface:** Randomized remapping defends adversarial wear but weakens determinism for debugging crash dumps.

Open directions: MRAM-based CXL Type-3 devices, formal verification of RDMA+PMEM persistency ordering, and integration with Linux `maple tree` for hybrid volatile/persistent indexing.

## 7 Conclusion

We unified *three pillars* for next-generation KV stores: **crash-consistent B+Trees with selective persistence**, **wear-leveling for endurance**, and **RDMA over CXL.mem disaggregation**. FAST & FAIR, FPTree, LB+Tree, and BzTree demonstrate that *single-flush inserts* and *logless splits* are achievable via 8-byte atomic bitmaps and fingerprinting, cutting flush amplification 8x over PMDK transactions. Start-Gap wear-leveling extends device life 8x by rotating hot lines, critical for root skew. CXL 3.0 fabric with HDM-DB and Pond-style pooling reduces stranded memory 32%, while RDMA one-sided primitives enable CPU-bypass GETs at **~2 us** predicted E2E. Our theoretical analysis, grounded in published latencies and no invented measurements, predicts **1.6-3.4x throughput** over baselines and **sub-5 us P99** remote reads. Together, this architecture points toward *persistent, disaggregated, and resilient* indexing for datacenter-scale KV stores.
