# eBPF: Verified In-Kernel Programmability from Packet Filters to General-Purpose Extensions

## Abstract

Extended Berkeley Packet Filter (eBPF) is a verified in-kernel virtual machine that allows untrusted userspace code to execute safely at kernel privilege level. Descended from the classic BPF packet filters of 1992, modern eBPF combines a RISC-style instruction set architecture with eleven 64-bit registers and a 512-byte stack, a static verifier grounded in abstract interpretation, just-in-time compilation to native code, and shared key–value maps that bridge the kernel–userspace divide. This thesis traces eBPF's evolution from a narrowly scoped network filter to a general-purpose extension mechanism, analyzes the verifier as the central security-critical component — its register state lattice, scalar range analysis with tristate numbers, termination argument via bounded loops, and soundness challenges — and examines how portability infrastructure (BTF and CO-RE) and a mature ecosystem (Cilium, Falco, bpftrace) turned verified in-kernel programmability into a production reality. We review formalization efforts including PREVAIL, proof-carrying-code proposals, and verified JIT synthesis, and conclude with open problems: the helper-function trust boundary, completeness of the verifier, and the long-term scalability of static verification as programs grow.

## 1 Introduction

Few artifacts in systems research have traveled as far from their origins as the Berkeley Packet Filter. In 1992, Steven McCanne and Van Jacobson designed BPF as a register-based filter language whose sole purpose was to let packet-capture tools such as `tcpdump` decide, inside the kernel, which packets deserved copying to userspace [6]. The language was deliberately minimal: two 32-bit accumulators, no loops, no function calls, and a boolean verdict. It was a domain-specific filter, and it was excellent at being one.

Two decades later, Alexei Starovoitov's 2014 rework of the in-kernel BPF engine — merged into Linux 3.18 — kept the name and discarded nearly every constraint [1][7]. Extended BPF (eBPF) is a general-purpose, event-driven extension mechanism for the operating system kernel: programs written in a restricted subset of C, compiled by LLVM to a 64-bit RISC bytecode, are loaded through the `bpf()` system call, subjected to a whole-program static verifier, JIT-compiled to native machine code, and attached to hook points ranging from NIC driver ingress (XDP) to system calls (tracepoints), dynamic kernel probes (kprobes), traffic control (TC), and Linux Security Module (LSM) hooks [1][2].

What makes eBPF intellectually distinctive is its **trust model**. Unlike kernel modules, which run with the kernel's full trust, eBPF programs are *untrusted by construction*: they may originate from unprivileged users or tenant workloads, yet they execute at ring 0 with near-native performance. Safety is established not by sandboxing at runtime but by *proof before execution* — the verifier must demonstrate, for every reachable program state, that memory accesses are in-bounds, registers are initialized before use, loops are bounded, acquired resources are released, and control flow cannot escape the program. The verifier is thus simultaneously a compiler pass, a theorem prover over an abstract domain, and the kernel's last line of defense. A single soundness bug in it is a kernel privilege-escalation primitive, and several have been found [3].

This thesis examines eBPF as a case study in *verified in-kernel programmability*: the ISA that makes verification tractable, the verifier's abstract-interpretation core, the maps and helpers that mediate interaction with the kernel, the portability machinery of BTF and CO-RE, the production ecosystem it enabled, and the ongoing research program to formalize — and ultimately replace or repair — the verifier itself.

## 2 Background

### 2.1 Classic BPF: a filter, not a machine

The original BPF, as specified in the 1993 USENIX paper, was a response to a performance problem: copying every packet across the kernel–user boundary only to discard most of them in userspace [7]. BPF programs ran in a minimal interpreter with two 32-bit registers, a small scratch memory, and forward-only jumps — the absence of backward jumps made non-termination structurally impossible, and the verifier was a trivial control-flow check. Linux adopted BPF in 1997; Eric Dumazet added an in-kernel JIT in 2011 [1]. In 2012, seccomp-bpf repurposed cBPF for syscall filtering — the first non-networking use case [1].

### 2.2 The 2014 rework: from filter to VM

Starovoitov's proposal, first posted in late 2013 and merged for the 3.15/3.18 era, introduced what we now call eBPF: ten (later eleven, with R10 as the read-only frame pointer) 64-bit registers, a 512-byte stack, a `call` instruction with a register-passing convention, new ALU and jump instructions, persistent key–value *maps*, and *helper functions* — kernel routines callable from eBPF code that mediate safe access to kernel facilities [1][2]. Crucially, the old cBPF was not kept alongside: the kernel translates classic filters into eBPF internally, so one interpreter, one JIT, and one verifier serve both [1].

### 2.3 The verifier as the price of admission

Every eBPF program, before it may run, passes through `kernel/bpf/verifier.c` — roughly tens of thousands of lines of C that perform abstract interpretation over the program's state space [3]. The verifier's job description is unusually demanding: it must be **sound** (never accept an unsafe program), **complete enough** (rarely reject programs developers actually write), and **fast** (verification happens at load time, in production, on the critical path of deploying networking policy). As the Linux Foundation security audit of the verifier documents, this component is simultaneously the most security-critical and the most formally under-specified part of the eBPF stack [3].

## 3 Methodology

This thesis follows a systems-research methodology: we reconstruct eBPF's design from primary artifacts — the kernel verifier source, the ISA specification as implemented, published formalizations, and the security audit literature — rather than from folklore. Our analysis proceeds in four stages.

First, we characterize the **instruction set architecture** as a *verification-friendly* ISA: every design decision (fixed-width 64-bit instructions, no indirect jumps, explicit frame pointer, bounded stack) is read as a concession to static analysis, and we evaluate which concessions remain load-bearing.

Second, we dissect the **verifier's algorithm**: depth-first exploration of the control-flow graph with state merging at join points, per-register abstract states combining type tags (scalar, pointer-to-stack, pointer-to-packet, pointer-to-map-value, etc.) with value-range information, and the termination argument that replaced the original "no backward jumps" rule with bounded-loop analysis. We draw on the PREVAIL formalization (Gershuni et al., PLDI 2019), which models the verifier as abstract interpretation over a core eBPF language and demonstrates that path-merging, rather than path enumeration, is what makes verification scale [2].

Third, we analyze the **trust boundary**: maps and helper functions. Maps are the only persistent state and the only kernel–userspace channel; helpers are the only way programs touch kernel objects. We examine why the HotOS 2023 position paper argues that even a perfect bytecode verifier cannot redeem unsafe helpers — the verification problem extends beyond the bytecode into the semantics of every callable kernel routine [4].

Fourth, we survey the **formalization and repair program**: tristate-number range analysis, synthesized JIT compilers with correctness proofs, proof-carrying-code proposals that would move the proof burden out of the kernel, and two-stage verification toolchains (e.g., VEP at NSDI 2025) that add annotation-guided precision to recover programs the stock verifier rejects [5][2].

Throughout, technical claims are grounded in the cited primary sources; where the literature disagrees (notably on whether the verifier is fundamentally tenable), we present both positions.

## 4 Deep Dive

### 4.1 The eBPF ISA: designed to be verified

The eBPF instruction set is a 64-bit RISC-like ISA whose every feature reflects the verifier's needs:

- **Registers.** Eleven 64-bit registers: `R0` holds return values and the program's exit code; `R1`–`R5` pass arguments to helper calls (and are clobbered by them); `R6`–`R9` are callee-saved; `R10` is a read-only frame pointer anchoring the 512-byte stack [1][2]. The small, fixed register file means the verifier's abstract state is a compact vector of register descriptors — the state space that abstract interpretation must explore is bounded by construction.
- **No indirect jumps.** All jump targets are immediate constants resolved at load time. The control-flow graph is therefore fully known before verification begins, which is what makes whole-program CFG analysis possible at all [1].
- **Bounded stack, no dynamic allocation.** Programs get exactly 512 bytes of stack and cannot allocate memory; all persistent state lives in maps. This eliminates an entire class of memory-safety reasoning.
- **Helper calls as the only syscalls.** An eBPF program cannot invoke arbitrary kernel functions; it may only call numbered helpers whose prototypes the verifier knows, enabling per-helper argument checking (e.g., "register 2 must be a pointer to initialized stack memory of at least N bytes") [3].

> **Theorem (informal, verifier soundness):** *If the verifier accepts a program P, then every concrete execution of P terminates, accesses only memory the verifier proved in-bounds, and invokes helpers only with arguments satisfying their preconditions.* The Linux verifier implements an *approximation* of this theorem; its soundness bugs are precisely the gaps between the implementation and the statement [3][4].

Compared with cBPF's two accumulators and boolean verdicts, the eBPF ISA is expressive enough for real algorithms — longest-prefix match in a routing table, per-connection state machines, histogram aggregation — while remaining austere enough that abstract interpretation terminates quickly [1][7].

### 4.2 The verifier: abstract interpretation at kernel scale

The verifier's core loop is a worklist-driven abstract interpretation over the program's CFG [1][3]:

1. **CFG validation.** Reject programs with unreachable issues the verifier cannot model: indirect jumps, jumps out of bounds, and (historically) any backward jump at all.
2. **Path exploration with state merging.** Starting from the entry state (R1 holding a context pointer whose type depends on the program type; R10 the frame pointer; all else unreadable), the verifier simulates each instruction abstractly. At CFG join points, abstract states are merged (widened); a state that is subsumed by an already-visited state prunes the path — the *state pruning* optimization that keeps verification times tolerable [3][5].
3. **Register abstract domain.** Each register carries a type tag plus, for scalars, range information. Modern kernels use **tristate numbers** (`tnum`: value/mask pairs tracking known-1, known-0, and unknown bits) combined with interval ranges, giving the precise bit-level reasoning needed to validate patterns like `if (x & 0xff00)`-style packet parsing [5]. Pointers carry base type, offset ranges, and — for packet pointers — the dynamic bounds (`data`, `data_end`) that must be re-checked after every operation that could invalidate them.
4. **Memory safety.** Every load/store is checked against the abstract state's knowledge: stack accesses must be within the 512-byte frame and to initialized slots; packet accesses must be preceded by a bounds check against `data_end` on the current path; map-value pointers are valid only with the size the map declares.
5. **Termination.** The original eBPF forbade backward jumps entirely. Since kernel 5.3, *bounded loops* are permitted: the verifier must prove a loop bound, capping total verified instructions (the limit grew from 4,096 to 1 million instructions in kernel 5.2) [1][5]. Loops whose bounds depend on runtime data remain the hard case — the VEP work shows the stock verifier still rejects safe programs here, motivating annotation-guided approaches [5].

The tension the verifier lives with is the classic soundness–completeness–performance trilemma: every precision improvement risks new soundness bugs, while every conservative shortcut rejects legitimate programs and pushes developers toward contortions [4].

### 4.3 Maps, helpers, and the boundary of trust

If the verifier is the gate, **maps** and **helpers** are the world beyond it. Maps (`BPF_MAP_TYPE_HASH`, `BPF_MAP_TYPE_ARRAY`, `BPF_MAP_TYPE_PERCPU_HASH`, `BPF_MAP_TYPE_RINGBUF`, and dozens more) are kernel-resident key–value stores created from userspace, referenced by eBPF programs via file descriptors, and shared between programs and userspace agents [1]. They serve three roles at once: persistent state across program invocations, the IPC channel between kernel programs and control-plane daemons, and the mechanism by which per-CPU data avoids cache-line contention at scale.

| Map type | Semantics | Canonical use |
|---|---|---|
| `BPF_MAP_TYPE_HASH` | Generic key→value, LRU variants available | Connection tracking, policy tables |
| `BPF_MAP_TYPE_ARRAY` | Fixed-size, O(1) integer-indexed | Per-CPU counters, jump tables |
| `BPF_MAP_TYPE_PERCPU_*` | Per-CPU shards, no locking | High-rate metrics, histograms |
| `BPF_MAP_TYPE_RINGBUF` | Multi-producer ring to userspace | Event streaming (replaces perf buffers) |
| `BPF_MAP_TYPE_PROG_ARRAY` | Tail-call program dispatch | Modular packet pipelines |

**Helper functions** (over 200 in modern kernels) are the verifier's blind spot and its necessity: each helper is a hand-written C routine with an informal contract, and the verifier checks only the syntactic preconditions its developers encoded. The HotOS 2023 critique is sharp here: static bytecode verification has *both* soundness and completeness issues, and unsafe helpers can undermine even a perfect verifier — a helper that returns a pointer the verifier models imprecisely reintroduces the very memory-unsafety verification was meant to exclude [4]. Proposed remedies range from fuzzing and formal specifications of helpers to the radical suggestion of replacing C helpers with verified Rust interfaces [4].

### 4.4 CO-RE and BTF: portable verified bytecode

eBPF's early years suffered a deployment paradox: bytecode compiled against one kernel's internal struct layouts broke on the next. The answer came in two parts. **BTF (BPF Type Format)** embeds compact type and debug metadata in the kernel and in compiled objects, describing kernel data structures the way DWARF does but small enough to ship in production [2]. **CO-RE (Compile Once, Run Everywhere)** uses BTF relocations so a single compiled program adapts its field offsets at load time across kernel versions — the `bpf_core_read()` family of macros resolves structure accesses against the *running* kernel's BTF rather than the build-time headers [2]. Together with `libbpf`'s skeleton generation, CO-RE turned eBPF from a per-kernel science project into shippable software: the same object runs on a 5.10 LTS node and a 6.x workstation, with the verifier re-checking it against each kernel's own helper set and program-type constraints.

### 4.5 The ecosystem: networking, security, observability

Three flagship systems demonstrate what verified in-kernel programmability buys:

- **Cilium** replaces kube-proxy's iptables chains and much of the container networking datapath with eBPF programs at TC and XDP hooks: identity-based network policy, load balancing, and encryption implemented as verified programs operating at packet-arrival time, with maps holding endpoint identity and policy state [1][2].
- **Falco** (and its modern eBPF driver) attaches to tracepoints and LSM hooks to build a runtime security sensor: every sensitive syscall is inspected in-kernel against a rule set, with only matching events streamed to userspace via ring buffers — filtering at the source rather than after expensive context switches.
- **bpftrace** gives operators a high-level tracing language (`kprobe`, `tracepoint`, `uprobe` one-liners with maps and aggregations) that compiles down to verified eBPF, making kernel introspection as casual as running `awk` [2].

## 5 Empirical Results and Proofs

The research literature offers both validation and warning.

**PREVAIL** (Gershuni et al., PLDI 2019) reimplemented the verifier's analysis as abstract interpretation over a formalized core language, eBPFPL, and showed that *path merging* — joining abstract states at control-flow merges rather than enumerating paths — verifies real-world programs (including loop-heavy string comparisons that defeat path enumeration) with precision matching or exceeding the kernel verifier [2]. PREVAIL's existence is itself an empirical result: the verifier's algorithm is principled enough to be re-derived from abstract-interpretation theory, not merely an accumulation of special cases.

**Soundness findings.** The Linux Foundation's verifier security audit catalogued the verifier/JIT attack surface and the published formal-methods results around it, including Rutgers work fixing *latent unsound abstract operators* in the kernel verifier's range analysis — cases where the abstract transfer functions did not over-approximate the concrete semantics, silently admitting unsafe programs [3]. Tristate-number analysis ("Sound, Precise, and Fast Abstract Interpretation with Tristate Numbers") repaired and generalized the bit-level reasoning the verifier depends on for packet parsing [3]. These are proofs *about* the verifier in the most practical sense: machine-checked or systematically argued corrections to its abstract domain.

**JIT verification.** Nelson et al.'s OSDI 2020 work ("Specification and verification in the field") applied formal methods to the BPF JIT compilers themselves, and follow-up synthesis work generates JIT backends for in-kernel DSLs with correctness arguments — addressing the uncomfortable fact that a sound verifier means nothing if the JIT mistranslates a checked program [3].

**Two-stage verification.** The NSDI 2025 VEP toolchain demonstrates the completeness side empirically: an annotation-guided verifier plus a lightweight bytecode-level proof checker accepts safe programs with data-dependent loops that both the Linux verifier and PREVAIL reject, without weakening the safety guarantee [5].

**The negative result.** Jia et al. (HotOS 2023) argue the program is, in a strong sense, *untenable*: static bytecode verification is fundamentally hard to scale, expressiveness constraints breed unsafe escape hatches in helper form, and the community's focus on verifier bugs misses the helper-function trust boundary entirely [4]. Whether this is despair or a research agenda depends on proof-carrying code and verified helper interfaces maturing — but as an empirical observation, it is difficult to dismiss.

A minimal complete program illustrates the whole pipeline — restricted C, map interaction, and the verifier-visible structure:

```c
#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, __u64);
} pkt_count SEC(".maps");

SEC("xdp")
int xdp_count(struct xdp_md *ctx)
{
    __u32 key = 0;
    __u64 *val = bpf_map_lookup_elem(&pkt_count, &key);
    if (val)
        __sync_fetch_and_add(val, 1);
    return XDP_PASS;
}

char _license[] SEC("license") = "GPL";
```

```bash
# Compile, verify, load, and inspect — the verifier runs at load time:
clang -O2 -target bpf -c xdp_count.bpf.c -o xdp_count.bpf.o
sudo bpftool prog load xdp_count.bpf.o /sys/fs/bpf/xdp_count type xdp
sudo bpftool prog show name xdp_count        # verified, JIT-compiled, attached
sudo bpftool map dump name pkt_count         # per-CPU counters, no locks
```

Every instruction in the object above was abstractly executed by the verifier before `bpftool` reported success: the `val` pointer's validity was tied to the `if (val)` null check, the map access to the declared value size, and the program's termination to the absence of unbounded loops.

## 6 Limitations

A candid accounting must include what verified in-kernel programmability does *not* solve.

1. **The helper trust boundary.** The verifier reasons about bytecode; helpers are C code with prose contracts. Every new helper extends the trusted computing base in ways the verifier cannot check [4]. Until helpers carry machine-checked specifications, verifier soundness is soundness *modulo helpers*.
2. **Completeness and programmability.** Safe programs are routinely rejected — data-dependent loops, complex pointer arithmetic across helper calls, patterns the abstract domain cannot express. Developers respond with contortions, `volatile` tricks, or privilege escalation to more permissive program types, each a small defeat for the model [5].
3. **Privilege and the unprivileged story.** Unprivileged eBPF, once a headline feature, has been progressively restricted after Spectre-era findings that speculative execution undermines the verifier's sequential-execution model; most distributions now require privilege to load any program [1][3]. The "untrusted code" in the trust model is increasingly "untrusted but root-adjacent" code.
4. **Verification cost at scale.** The 1-million-instruction limit and state-pruning heuristics are engineering compromises; pathological programs still exhibit exponential blowup, and verification latency is on the load path of production networking changes [5].
5. **Semantic drift across kernels.** CO-RE solves struct layout, but helper availability and verifier strictness still vary by kernel version.

---

## 7 Conclusion

eBPF's arc — from a 1992 packet filter with two registers to a verified general-purpose extension mechanism running the world's container networks — is a case study in what becomes possible when *verification is designed in rather than bolted on*. The ISA's austerity (no indirect jumps, bounded stack, fixed register file) is not a limitation to be apologized for; it is the precondition that makes abstract interpretation tractable at kernel scale. The verifier's abstract domain — type tags fused with tristate-number ranges, pointer bases with dynamic packet bounds — is one of the most ambitious static analyses ever deployed in production, executed on every program load on millions of machines.

Yet the story is unfinished. The verifier is sound *modulo* its helpers and complete *modulo* its abstract domain's expressiveness. The formalization program — PREVAIL, verified JIT synthesis, proof-carrying code, two-stage verification — is converging on a future where the kernel checks a proof rather than performing the analysis itself [2][4][5]. eBPF has already demonstrated the central thesis: *untrusted code can run at the highest privilege level, safely, if you are willing to prove it first.*
