# Type-Theoretic Foundations of Algebraic Effects, Capabilities, and Effect Handlers: From Eff to Koka and OCaml 5

## Abstract
Algebraic effects separate effectful operations from their interpretation, modeling effects as operations of an algebraic theory and handlers as algebras or homomorphisms from the free model. This thesis develops the type-theoretic foundations of algebraic effects, capability-based tracking, and effect handlers, tracing the design lineage from Eff to Koka and OCaml 5. We present the non-monotone effect systems of Bauer and Pretnar where handlers delete effects, contrast row-polymorphic effect types in Koka that support duplication, encapsulation, and inference, and analyze OCaml 5's one-shot fiber-based continuations as a runtime for deep and shallow handlers. We formalize capability-passing as in Effekt and Zhang-Myers, translating effectful terms to System Xi with second-class functions for lexical safety. Coverage includes contextual modal types, sound Hindley-Milner polymorphism without value restriction for algebraic effects, polymorphism via instances, and parallel handlers. The work supplies operational, denotational, and categorical semantics with proofs.

## 1 Introduction

Algebraic effects, introduced by **Plotkin and Power** and systematized by **Plotkin and Pretnar** [1][2], recast computational effects as *operations* in a signature extended with equational laws. Exceptions, state, nondeterminism, I/O, probabilistic choice, and concurrency emerge as instances of a single uniform idea: **effects are algebraic operations**, and **handlers are interpretations**. This decomposition resolves the monad transformer ordering problem by deferring interpretation to handling sites.

The promise was elegant, but the practice exposed deep type-theoretic problems: *how do we track effects*, *how do we ensure handlers are safe*, *how do we preserve polymorphism*, and *how do we compile continuations efficiently*? Three language families answered differently:

- **Eff** [2][3] pioneered instances and first-class handlers with a non-monotone type-and-effect system where handling *removes* effects.
- **Koka** [4][5] recast effects as row-polymorphic labels with duplicate-aware unification, semantic correspondence theorems, and Perceus reference-counting compilation.
- **OCaml 5** [6][7] retrofitted effect handlers onto a production runtime via heap-allocated *fibers*, one-shot delimited continuations, and a multicore-aware GC.

A fourth view — **capabilities as effects** from **Brachthäuser et al. Effekt** and **Zhang & Myers** [8] — inverts the intuition: an effect type denotes not what a computation *does*, but what capability it *requires* from its context. This yields lightweight polymorphism without row variables.

> **Theorem 1 (Free Model Universality):** For any algebraic theory T = (Sigma, E), the free model F_T(X) with unit eta : X -> F_T(X) is initial among T-algebras under X. Every handler h : Sigma -> A extends uniquely to a homomorphism hat{h} : F_T(X) -> A.

This thesis traces these threads, unifying operational semantics, typing, and implementation.

## 2 Background and Related Work

### 2.1 From Monads to Algebraic Theories

Moggi's monadic semantics made effects first-class but **modularity remained painful**. Monad transformers impose linear stack ordering, non-commuting lifts, and n^2 instances. Plotkin and Power's algebraic view [1] observed that many monads are *free* models of simple operations:

- *Exceptions*: `raise : exn -> 0`
- *State*: `get : 1 -> S`, `put : S -> 1` with equations `get; put(s) = ()`, `put(s); get = s`
- *Nondeterminism*: `choose : 1 -> bool` with semilattice laws
- *I/O*: `read : 1 -> char`, `write : char -> 1`

Combinations are coproducts of theories, not transformer stacks. This insight is **composition over stratification**.

### 2.2 Handlers as Algebras

Plotkin and Pretnar [1][2] generalized exception `catch` to arbitrary operations. A handler supplies:

1. A *return clause* `return x -> N`
2. For each `op : A -> B` in signature, a clause `op(p, k) -> M` where `k : B -> C` is the **delimited continuation**

Semantically, `handle M with H` folds the computation tree of `M` with algebra `H`. Operationally, `perform op(v)` captures the stack up to the nearest enclosing handler for `op`.

> *The handler boundary defines the delimiter; the continuation is the captured context as a first-class value.*

### 2.3 Problems in Effect Typing

Traditional effect systems are **monotone**: effects accumulate upward. Handlers break monotonicity because they *delete* effects. Bauer and Pretnar [3] showed:

```
Gamma |- M : A ! Delta
Gamma |- H : A ! Delta => B ! Delta'
-------------------------
Gamma |- handle M with H : B ! Delta'
```

where `Delta'` may be smaller than `Delta`. The effect row `Delta = {get, put, raise}` after `h_state` becomes `Delta' = {raise}`. Order matters for semantics when operations interact.

*Polymorphism and effects* also clash. Hindley-Milner value restriction exists because `ref` breaks soundness. Kammar et al. [9] proved **no value restriction needed for pure algebraic effects and handlers** without instances — handlers are sufficiently pure in the categorical sense of preserving relational parametricity. With dynamic instance generation (Eff's `new ref`), the restriction returns.

## 3 Methodology: Formal System

### 3.1 Core Calculus λ_eff

We define **Core Eff**, à la Bauer-Pretnar 2014 [3]:

```
Values      V,W ::= x | λx.M | () | true | false
Computations M,N ::= return V | V W | let x = M in N
                  | perform op(V) | handle M with H
Handlers    H ::= { return x -> M_ret } ∪ { op p k -> M_op }
Effect Rows Δ ::= ∅ | { l1:A->B, ..., ln:A->B } ∪ ε
Types       A,B ::= α | Unit | A ->_Δ B ! Δ | ...
```

Typing judgments:

- `Γ ⊢ V : A`
- `Γ ⊢ M : A ! Δ` — computation returning `A` potentially performing `Δ`
- `Γ ⊢ H : A ! Δ => B ! Δ'`

**Key rule — Perform:**

```
(op : A_op -> B_op) ∈ Σ
Γ ⊢ V : A_op
------------------------------
Γ ⊢ perform op(V) : B_op ! {op}
```

**Key rule — Handling:**

```
Γ ⊢ M : A ! {op} ∪ Δ
Γ, x:A ⊢ M_ret : B ! Δ'
Γ, p:A_op, k:B_op -> B ! Δ' ⊢ M_op : B ! Δ'   for each op
---------------------------------------------------------
Γ ⊢ handle M with H : B ! Δ' ∪ Δ  (if op handled, removed)
```

### 3.2 Denotational Semantics

We follow [3] using **domain-theoretic PERs** and minimal invariant relations à la Pitts. For each effect theory `T`, the free domain model `F_T(D)` solves:

```
F_T(D) ≅ D + Σ_{op} (A_op × (B_op -> F_T(D)))
```

Handlers are interpreted as algebra homomorphisms. Adequacy follows from existence of least fixed point. Safety theorem: well-typed programs never perform unhandled operation.

### 3.3 Capability-Passing Translation

For **Effekt**, we translate to **System Xi** [8]:

```
⟦ A ! {e} ⟧ = ∀κ. (Cap(e) -> ⟦A⟧)
⟦ perform op ⟧ = λcap. cap.op
⟦ handle M with H ⟧ = λcap_outer. let cap_inner = mkCap(H, cap_outer) in ⟦M⟧ cap_inner
```

Second-class function restriction ensures capabilities do not escape lexical scope, guaranteeing **effect safety without row polymorphism**.

## 4 Deep Dive

### 4.1 Eff: Instances, Resources, and Dynamic Effect Generation

Eff [2] is *historically pivotal* because it introduced **effect instances**:

```haskell
-- Eff-like pseudo Haskell for instances
type 'a ref = effect
  operation get : unit -> 'a
  operation set : 'a -> unit
end

let r = new ref  -- fresh instance ρ
in handle
  let x = perform (r#get ()) in
  perform (r#set (x+1));
  x
with
| r#get _ k -> k 0
| r#set _ k -> k ()
| val v -> v
```

Each `new` generates a distinct name `ρ` in a nominal style akin to ML refs or generative exceptions. The type becomes `{ρ#get, ρ#set}`. This increases modularity but complicates inference:

- Instance freshness breaks simple row unification
- Pretnar 2014 [10] gives Hindley-Milner inference for Eff with effect *sets*, constraint `Δ₁ ⊆ Δ₂`, and region-like instance tracking
- Subtyping on dirt sets (effects) and skeleton types (erasure)

*Resource example* in Eff notation:

```ocaml
effect State : int -> unit
effect Get : int

let stateful comp =
  handle comp () with
  | effect Get k -> (fun s -> continue k s s)
  | effect State s k -> (fun _ -> continue k () s)
  | x -> (fun s -> x)
```

The result is `0` (state handler initialized to `0`). Swapping handlers yields different semantics.

**Limitation:** Eff 3.0 used for meta-theory still lacks optimized separate compilation; prototype compiles via OCaml or direct denotational translation.

### 4.2 Koka: Row Polymorphism with Duplicate Labels

Koka [4][5] is the most production-hardened algebraic effects language from Microsoft Research (Daan Leijen). Its innovation is **row-polymorphic effect types with duplicate labels** and **closed handlers**.

Type syntax in Koka:

```
fun map(xs:list<a>, f: a -> e b) : e list<b>
fun catch(action: () -> <exn|e> a, handler: exn -> e a) : e a
fun localState(action: () -> <st<h>|e> a) : e a   -- st<h> eliminated!
```

Novelties:

1. **Duplicate labels allowed:** `<exn, exn>` ≠ `<exn>`. Catching one `exn` leaves `<exn>` residual if another might throw. This gives precise typing to:

```koka
fun foo() {
  try { throw() } catch { _ -> throw() }  // : <exn> a   not pure
}
```

2. **Semantic effect theorems:** If `|- e : a` with empty effect row `<>`, then evaluation is **pure**. More strongly:
   - If `exn ∉ ε` then `e` never throws unhandled exception
   - If `div ∉ ε` then `e` terminates
   - If `st<h> ∉ ε` then no observable heap mutation escaping `h`

3. **Perceus and evidence passing:** Koka compiles to C via Perceus reference counting with reuse analysis. Effects translate to dictionary passing (evidence of handlers), enabling zero-cost `tail-resumptive` optimization [11].

| Feature | Eff | Koka | OCaml 5 | Effekt |
| :--- | :--- | :--- | :--- | :--- |
| Types | sets + instances | rows + dup | untyped effects (stdlib Effect) | capabilities / intersection |
| Poly | value restriction w/ instances | row poly + general | OCaml value restriction | second-class funs |
| Cont | multi-shot | multi-shot (linear checks) | **one-shot** only | multi-shot via monad |
| Infer | Hindley-Milner + constraints | HM row inference | OCaml inference (effect untyped) | HM + capability |
| Comp | to OCaml | to C (mimalloc+Perceus) | native fibers + GC | Scala / Chez |

Koka's type inference is *complete* for polymorphic rows via Remy-style unification extended to duplicate labels.

### 4.3 OCaml 5: Fibers, One-Shot Continuations, and Effect Syntax

OCaml 5.0 (2022) shipped **Multicore + Effect Handlers** [6][7], retrofitting handlers onto a 25-year-old industrial GC.

#### Runtime model

- **Fibers** are heap-allocated stacklets, 4KB initial, grown via linked chunks. The OCaml execution stack *is* a cactus stack of fibers.
- `perform` walks the fiber stack popping until it finds matching handler; popped fibers become the continuation `k`.
- `continue k v` pushes `k` back; `discontinue k exn` resumes with exception.
- **One-shot** restriction: continuations invalidated after single resume. Prevents unsoundness with mutable state and avoids copying costs. Multi-shot emulated via `Obj.clone_continuation` removal → `ocaml-multicont` library copies fiber chunks.

New syntax (OCaml 5.4+):

```ocaml
effect Ask : int
effect State : int -> unit
effect Get : int

let comp n =
  perform Ask + perform Get

let handled =
  match comp 42 with
  | x -> x
  | effect Ask k -> continue k 1
  | effect Get k -> continue k 99
```

Deep vs Shallow:

- **Deep:** handler wraps continuation (`try_with` folds). Resumed computation handled again.
- **Shallow:** handler does not re-wrap; case split. Requires recursive loop.

Performance: Dolan et al. PLDI 2021 [6] show effect handlers *within 5-10% of hand-written callback state machines* for scheduler benchmarks; < 20ns per `perform/continue` on ARM64 M1 after inlining.

**Type system gap:** OCaml's effects are intentionally **untyped** in stdlib `Effect` module, using extensible GADT `type _ Effect.t +=`. Full effect typing left as experimental future work; safety via GC and affine continuation check, not static effect rows.

### 4.4 Capabilities, Contextual Modal Types, and Lexical Scoping

Contextual Modal Type Theory (CMTT) inspired **ECMTT** [12]:

```
□_Ψ A   — modal type "A is possible under effects Ψ"
box_Ψ(M) — introduce capability context Ψ
let box_Ψ(u) = M in N — eliminate / handle
```

In ECMTT, effects *are* the context of modal variables. Handlers are *explicit substitutions* reaching one context from another, giving local soundness/completeness via β-reduction.

**Effekt** [8] uses a similar inversion:

> *Don't ask what effects M has; ask what capabilities it needs.*

Operationally:

```rust
// Pseudo-Rust for Effekt mindset with capability traits
fn map<A,B,C>(xs: Vec<A>, f: impl Fn(A) -> B + Uses<Reader>) -> Vec<B>
where Reader: Cap<Read: String>
{
    xs.into_iter().map(|x| f(x)).collect()
}

trait Cap<E> { fn with_cap<R>(self, f: impl FnOnce() -> R) -> R; }
```

Capability passing solves three hard problems:

1. **Effect polymorphism:** `map` polymorphic over `e` without effect variables — because capabilities are *values*, ordinary generics suffice.
2. **Effect masking/hiding:** `runState` introduces capability `st` lexically, not in return type.
3. **Lexical reasoning:** non-escape proved by second-class restriction, simpler than non-trivial uses of value restriction.

TLA+ spec for one-shot safety:

```tla
---- MODULE OneShotCont ----
EXTENDS Naturals
VARIABLE k_state  \* "valid", "used", "discontinued"

Continue(k) ==
  /\ k_state[k] = "valid"
  /\ k_state' = [k_state EXCEPT ![k] = "used"]
  
Discontinue(k) ==
  /\ k_state[k] = "valid"
  /\ k_state' = [k_state EXCEPT ![k] = "discontinued"]

ResumeTwiceViolation ==
  \E k: k_state[k] # "valid" /\ AttemptResume(k)
  
Spec == [] (\A k \in DOMAIN k_state: k_state[k] = "used" => [] (k_state[k]="used"))
====
```

This liveness specification rejects double-resume states unreachable in OCaml 5 runtime.

## 5 Empirical Evaluation and Proof Sketches

### 5.1 Soundness Proof Outline

**Theorem 2 (Effect Safety for Core Eff [3]):** If `∅ ⊢ M : A ! Δ` and `M ⇓* N` then `N` is a value or `N` performs `op ∈ Δ`.

*Proof sketch by progress/preservation*:

1. Define form for evaluation contexts `E[perform op]`.
2. Show preservation under `β`, handler unfolding, `perform` bubbling.
3. Show canonical forms: `⊢ V : A` has shape consistent with `A`.
4. Handler case: if `op ∈ handled`, reduction applies; else bubbles.

Extension to PER denotational semantics: Define relation `∼_A` on domains; show fundamental lemma. Adequacy bridges operational → denotational.

### 5.2 Termination via Divergence Effect

In Koka, effect system enforces termination without separate totality checker:

```
div ∉ ε  =>  ∀ M : ε A . M ⇓ V   (theorem in Leijen 2014 §6)
```

*Idea:* Functions that allocate and recurse through higher-order state accrue `div` via `st<h>` not being pure. `run` prevents leaking `h` that could capture diverging closure.

Empirical measurement by Leijen on 2000 LOC Markdown parser: **0.97 precision** predicting divergence-sensitive ops vs explicit annotation.

### 5.3 Benchmarks: Fibers vs State Machines

From Dolan et al. PLDI 2021 reproduced table:

| Benchmark | Handlers (fibers) | Hand-written callbacks | Ratio |
| :--- | :--- | :--- | :--- |
| async echo server (100k conn) | 1.12M req/s | 1.18M req/s | 0.95x |
| generators pipeline 10 stages | 42 ns/elt | 39 ns/elt | 1.07x |
| backtracking N-Queens | 18 ms | 16 ms (exceptions) | 1.12x |
| transactional state | 2.3 µs/txn | 2.1 µs/txn (ST) | 1.09x |

One-shot fibers avoid copying entire stack; cost dominated by cactus stitching and DWARF unwind table probing.

### 5.4 Capability Polymorphism Simplification Metric

Brachthäuser et al. [8] surveyed 184 Koka programs. Row polymorphism accounted for:

- 73% of type errors due to Row unification mismatch
- Effect variable generalization heuristics needed in 41 cases

Capability version in Effekt/Scala eliminated effect variable syntax; all examples typed with ordinary Scala polymorphism. Type annotation size median decreased 22% (LoC) while preserving safety.

Python illustration for handler semantics via free monad folding:

```python
from typing import Callable, Any

class Op:
    def __init__(self, name, arg): self.name=name; self.arg=arg

def handle(comp, handlers, ret):
    # comp is generator yielding Op, receiving resume values
    try:
        v = next(comp)
        while True:
            if v.name in handlers:
                # k is delimited continuation
                def k(resume_val, gen=comp):
                    try:
                        v2 = gen.send(resume_val)
                        return handle(gen, handlers, ret)
                    except StopIteration as e:
                        return ret(e.value)
                return handlers[v.name](v.arg, k)
            else:
                # bubble
                yield v
    except StopIteration as e:
        return ret(e.value)

# Example: state handler
def state_example():
    # perform get
    x = yield Op("get", ())
    yield Op("set", x+1)
    return x

h = {
 "get": lambda _, k: k(0),
 "set": lambda _, k: k(())
}
print(handle(state_example(), h, lambda x: x))
```

## 6 Limitations and Open Problems

### 6.1 Interaction of Instances and Polymorphism

Eff's generative instances `new ref` give precise effect tracking but revive value restriction. The combination **polymorphic generalization + dynamic instance names** unsound without restriction:

```python
# Unsound if instances generalized like ML refs
# let f = new ref in   # : (unit -> <ρ#get|...> int) fresh?
# let g = f () in      # unsound if ρ unified across uses
```

Koka avoids generative names via lexical `h` heap parameters `st<h>`, using quantified `∀h. <st<h>> a -> a` for encapsulation. OCaml avoids static effect names entirely. Outstanding problem: *nominal instances + polymorphism* that is both sound and principal without heavy regions.

### 6.2 Effect Equations and Non-free Theories

Most implementations work with **free** models (operations without equations). Theories with equations (e.g., `get; get = get`, `put(s); put(s') = put(s')`) require quotienting continuation trees. Loss of confluence if handlers don't respect equations. **Scoped effects** (Wu et al.) extend signature with `scope` operators for `once`, `catch`, local state — hierarchy not just algebraic.

### 6.3 Performance and Parallelism

- One-shot vs multi-shot tradeoff: multi-shot enables probabilistic programming and backtracking but needs copying GC; OCaml chose one-shot for runtime simplicity; Xie et al. [13] show parallel `for` with handlers needs careful discipline to avoid races on continuation clone.
- Perceus reference counting shines for tail-resumptive handlers (`k` called in tail position) where stack frame reused in-place. Non-tail-resumptive pays allocation.

### 6.4 UX of Effect Types

Row-polymorphic error messages remain unreadable for beginners:

```
error: inferred effect <exn, st<local>, div> is not a subtype of <exn>
hint: possible effect extension because `map` closes over `ref`
```

IDE visualization (Koka's VS Code extension, Effekt IntelliJ plugin) helps but not universal. Capability-passing error: "missing implicit capability reader in scope" more familiar to Scala implicits programmers, yet still novel.

## 7 Conclusion

Algebraic effects recast effects from *monolithic wrappers* to *algebraic signatures interpreted by handlers*. This thesis unified three engineering philosophies:

* **Eff's question:** what if instances and handlers were first-class enough to model ML refs modularly?
* **Koka's answer:** row polymorphism with duplicate labels, semantic effect theorems, and evidence-passing compilation makes effects *practical* for systems C code.
* **OCaml 5's compromise:** fibers as runtime chunks with one-shot delimited continuations bring handlers to production without rewriting type checker.
* **Capabilities:** inverting effect judgment to *requires* yields lightweight polymorphism and lexical safety via second-class functions.

> ***Bold synthesis:*** The future of effect-typed intermediate languages lies neither in pure rows nor pure capabilities alone, but in *evidence-passing with contextual modal qualifications* — where `□_Ψ A` tracks the exact capability set `Ψ` as a context, row unification becomes context decomposition, and fiber-based zero-copy resume supplies the runtime.

Future work points to **typed OCaml 5 effects** with row polymorphism and capability qualifiers, **parallel algebraic handlers** with deterministic `for`, and **per-handler equation checking** à la Quantitative Type Theory.
