# The Arithmetic of Tensor Cores: Cooperative Warp-Level Matrix Primitives, Numeric Precision Hierarchies, and the Kernel Architecture of GEMM at Tensor Rates

## Abstract

Modern GPUs sustain over one petaflop per second of dense matrix computation — throughput unreachable by scalar pipelines alone. The decisive innovation is the *tensor core*: a warp-cooperative matrix-multiply-and-accumulate unit evaluating $D = A \times B + C$ on fixed-shape tiles in a single collective operation issued by all 32 threads of a warp. This thesis unifies tensor-core arithmetic, from the numerical semantics of mixed-precision formats (FP16, BF16, TF32, FP8) and the register-fragment model exposed via `wmma`, PTX `mma.sync`, and `ldmatrix`, to the three-level tiling hierarchy converting $O(n^3)$ flops against $O(n^2)$ bytes into tensor-rate throughput. We trace how Ampere's `cp.async`, 2:4 structured sparsity, and FP64 DMMA, Hopper's warpgroup WGMMA and Tensor Memory Accelerator, and Blackwell's block-scaled NVFP4 widen the arithmetic envelope, and the register, shared-memory, and scheduling choreography behind CUTLASS-class kernels. Roofline analysis frames when GEMM is compute-bound, how tile shapes and software pipelining reach the compute ceiling, and the fundamental limits — bank conflicts, register pressure, abstraction portability — bounding further gains.

## 1. Introduction

The general matrix-matrix multiplication (GEMM), $C \leftarrow \alpha AB + \beta C$, is the computational backbone of deep learning and scientific simulation. For dimension $n$ it performs $2n^3$ flops on $3n^2$ elements — arithmetic intensity growing linearly with $n$, making large GEMM the rare *compute-bound* workload. Yet compute-bound is necessary, not sufficient: scalar SIMT pipelines top out at tens of teraflops while accelerators advertise thousands. The gap is closed by *tensor cores* [1], datapaths that perform an entire small matrix product in one instruction.

A tensor core is not merely a "fast multiplier." It is a **cooperative matrix engine**: no single thread owns the operation. The smallest programmable unit is the *warp* — 32 threads in lockstep — and operands live in a *register fragment* distributed across all 32 lanes. Programming it correctly requires reasoning about three scales at once: the hardware atom (e.g., $16 \times 8 \times 16$), the warp tile assembled from atoms, and the threadblock tile assembled from warps, with pipelined copies staging data through shared memory [2][5].

> **Thesis statement:** *Tensor-rate GEMM is not achieved by issuing more instructions, but by orchestrating a precise arithmetic contract between the hardware's fixed-shape matrix atom, the warp-cooperative register layout, and a numerically careful hierarchy of reduced-precision formats — a contract this work formalizes and analyzes end to end.*

This thesis formalizes the warp-level cooperative matrix primitive and its tiling closure, taxonomizes the precision hierarchy with exact error semantics, reconstructs the canonical kernel architecture (global→shared→register pipeline, `ldmatrix` fragment loads, `cp.async`/TMA staging, epilogue fusion) as realized in CUTLASS 3.x [5], and quantifies performance through the roofline model [7] — closing with the hard limits that bound further gains.

## 2. Background

### 2.1 From scalar SIMT to matrix units

A classical CUDA core executes one scalar flop per thread per clock; a Volta SM holds 64 FP32 cores — modest throughput per SM. Tensor cores, introduced with the Tesla V100 in 2017, changed the unit of work: each of the V100's 640 tensor cores performs a $4 \times 4 \times 4$ MMA per clock, for 125 TFLOPS of FP16 — roughly $12\times$ the FP32 rate of the same die [1].

Each architecture generation has widened the envelope (see table; details in [3]):

| Architecture | New tensor-core arithmetic | Notable peak (dense) |
|---|---|---|
| Volta (sm_70) | FP16 MMA, 4×4×4 atom | 125 TFLOPS FP16 |
| Turing (sm_75) | INT8/INT4/INT1 MMA | 130 TOPS INT8 |
| Ampere (sm_80) | TF32, BF16, FP64 DMMA, 2:4 sparsity, `ldmatrix` | 312 TFLOPS FP16 (624 sparse) |
| Hopper (sm_90) | WGMMA (warpgroup), FP8, TMA async copies | ~989 TFLOPS FP16 |
| Blackwell (sm_100) | NVFP4 block-scaled microscaling formats | multi-PFLOPS FP4 |

The Ampere GA102 whitepaper documents these third-generation tensor cores, including the structured-sparsity datapath [3].

### 2.2 The programming interfaces

Three interfaces expose the hardware, in increasing order of control:

1. **`nvcuda::wmma` (CUDA 9+).** The C++ warp-matrix API: `load_matrix_sync`, `mma_sync`, `store_matrix_sync`, `fill_fragment` over `fragment` objects. All 32 threads of a warp must participate, and conditional execution must be warp-convergent. Crucially, *the mapping of matrix elements to thread registers is unspecified* — direct element access is only legal for uniform elementwise operations [6].
2. **PTX `mma.sync` / `ldmatrix` / `stmatrix`.** Inline PTX gives deterministic layouts: `mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32` computes a $16 \times 8 \times 16$ product with FP16 inputs and FP32 accumulation. `ldmatrix.sync.aligned.m8n8` performs a *collective* load from shared memory into the warp's registers with a documented thread-to-element mapping, and `cp.async` overlaps global→shared copies with math [2][8].
3. **CUTLASS / CuTe (3.x).** NVIDIA's open-source template library composes these atoms: an *MMA atom* (single warp, fixed shape) is tiled by `make_tiled_mma` into a *tiled MMA* spanning the threadblock — the generalization of the 2.x warp-level tiling layer [5].

### 2.3 Mixed precision: why the arithmetic is split

Micikevicius et al. showed deep networks train in FP16 storage with FP32 accumulation using an FP32 *master copy* of weights and *loss scaling* to keep small gradients inside FP16's narrow exponent range [4]. Tensor cores hardware this recipe: multiply narrow, accumulate in FP32 — the $D = A \times B + C$ semantic with $A, B$ narrow and $C, D$ wide.

## 3. Methodology

Our analysis proceeds in three strands.

- **Architectural reconstruction.** We extract the shape grammar $\{m,n,k\}$, supported type tuples, and fragment-layout rules from vendor whitepapers [1][3], the PTX ISA reference's warp-level matrix section [2], and the CUDA programming guide's warp-matrix appendix [6].
- **Numerical analysis.** For each format we derive range, unit roundoff, and accumulation-error bounds, formalizing the mixed-precision invariant: inputs may be quantized provided accumulation and master state stay at working precision [4].
- **Performance modeling.** We place GEMM shapes on the roofline [7], compute the arithmetic-intensity crossover from DRAM-bound to tensor-bound, and decompose achieved throughput into tile-shape, pipelining, and epilogue factors following CUTLASS's hierarchy [5].

Terminology: *MMA atom* (hardware instruction, e.g. $16 \times 8 \times 16$); *warp tile* ($M_w \times N_w \times K_w$ region per warp); *threadblock tile* ($M_b \times N_b \times K_b$ per CTA); *fragment* (warp-distributed register holding); *epilogue* (fused post-GEMM elementwise visitor).

## 4. Deep Dive

### 4.1 The cooperative matrix primitive as an algebraic object

The fundamental departure of tensor-core programming is that **no thread can issue the operation alone**. Formally, the MMA instruction is a *collective* over the warp $W = \{t_0, \dots, t_{31}\}$: each thread contributes a slice of each operand, and the hardware crossbar routes partial products through the accumulator array, with semantics $D \gets \mathrm{fl}(A \cdot B + C)$ — accumulation exact in the working format, single rounding at writeback.

> **Theorem:** *Fragment closure under tiling.* Any GEMM of shape $(M, N, K)$ with $M, N, K$ multiples of the atom shape $(m, n, k)$ decomposes into $(M/m)\cdot(N/n)\cdot(K/k)$ atom invocations whose partial sums follow a single deterministic K-major summation order. Hence a warp tile is exactly the tiling of the atom over the warp's register file.

> **Proof:** Each atom computes one $(m,n)$ block of the output for a fixed $k$-slab. The decomposition fixes one parenthesization of the full dot product, so the tiled computation is well-defined regardless of the non-associativity of floating-point addition. ∎

This has a sharp consequence: compiler and programmer must agree on the *fragment layout*. Under `wmma` the layout is intentionally opaque, which is why `ldmatrix` matters — it publishes the mapping so software can XOR-swizzle shared memory to eliminate bank conflicts *without* breaking the fragment contract [2].

### 4.2 The precision hierarchy: an arithmetic taxonomy

Tensor cores do not compute in "low precision" as a single concept. Each format is a distinct arithmetic with its own range and rounding behavior:

| Format | Bits (s/e/m) | Max value | Unit roundoff $u$ | Tensor-core role |
|---|---|---|---|---|
| FP32 | 32 (1/8/23) | $3.4 \times 10^{38}$ | $2^{-24}$ | Accumulator, master weights |
| TF32 | 19 (1/8/10) | $3.4 \times 10^{38}$ | $2^{-11}$ | Drop-in FP32-range multiply |
| BF16 | 16 (1/8/7) | $3.4 \times 10^{38}$ | $2^{-8}$ | Activations, wide range |
| FP16 | 16 (1/5/10) | $65{,}504$ | $2^{-11}$ | Classic mixed precision |
| FP8 E4M3 | 8 (1/4/3) | $448$ | $2^{-4}$ | Weights/activations (Hopper+) |
| FP8 E5M2 | 8 (1/5/2) | $57{,}344$ | $2^{-3}$ | Gradients (Hopper+) |
| INT8 | 8 (signed) | $127$ | exact | Quantized inference |
| FP64 | 64 (1/11/52) | $1.8 \times 10^{308}$ | $2^{-53}$ | DMMA scientific GEMM |

The mixed-precision invariant that makes this hierarchy sound is:

> **Theorem:** *Mixed-precision forward-error bound.* Let $\hat{C} = \mathrm{fl}_{w}(A_q B_q)$ where $A_q, B_q$ are the narrow-format roundings of $A, B$ and accumulation is in working format $w$ with unit roundoff $u_w$. Then the accumulation error — the term growing with reduction length $K$ — is controlled by the *wide* format ($K u_w \|A\|\|B\|$), while the narrow format contributes only a $K$-independent input-quantization term $O(u_q)$.

> **Proof sketch:** Wilkinson-style analysis: each length-$K$ inner product accumulates error $\le K u_w \sum |a_i b_i|$ in the wide format [4]. Narrow-format input rounding is a one-time relative perturbation $\|A_q - A\| \le u_q \|A\|$, independent of $K$ — keeping total error at single-precision GEMM levels for deep-learning magnitudes. ∎

TF32 deserves special attention: keeping FP32's 8-bit exponent while truncating the mantissa to 10 bits, it offers the *range* of FP32 with the *precision* of FP16 and needs no loss scaling — the pragmatic reason it became the default math mode for FP32 workloads on Ampere [3].

Structured sparsity adds a combinatorial twist: Ampere's sparse tensor cores exploit a **2:4 pattern** (at least 2 of every 4 consecutive values are zero), compressing $A$ by $2\times$ with metadata selecting the corresponding $B$ rows. Throughput doubles (312 → 624 TFLOPS FP16 on A100) because the datapath skips zero lanes in hardware — but only for the constrained pattern, and only with a fine-tuning recipe that preserves accuracy [3].

### 4.3 The tiling hierarchy and register blocking

A high-performance GEMM is a *five-deep loop nest* mapped onto the machine hierarchy. The canonical decomposition for a $128 \times 256 \times 32$ threadblock tile with 4 warps:

1. **Grid level:** threadblocks tile $(M, N)$; the $K$ dimension is serialized in the mainloop (or split across blocks with split-K reduction for small $M$).
2. **Threadblock level:** each CTA stages $A_{128 \times 32}$ and $B_{32 \times 256}$ panels in shared memory — double- or triple-buffered so that `cp.async` (Ampere) or TMA (Hopper) fills buffer $i+1$ while warps consume buffer $i$.
3. **Warp level:** the CTA tile splits into four $64 \times 64 \times 32$ warp tiles; each warp's accumulator fragment holds $64 \times 64 = 4096$ FP32 values distributed as 128 registers per thread — near the architectural limit, which is why warp-tile size is the primary register-pressure knob.
4. **Atom level:** each warp tile decomposes into $16 \times 8 \times 16$ MMA atoms as shown in §4.1.
5. **Epilogue:** the accumulator is transformed (scaling by $\alpha$, bias add, activation) and stored, ideally *fused* so $C$ is never round-tripped through DRAM.

The intensity argument justifying this machinery: a threadblock tile performs $2 \cdot 128 \cdot 256 \cdot 32 = 2{,}097{,}152$ flops while moving $128 \cdot 32 + 32 \cdot 256 = 12{,}288$ FP16 elements ($\approx 24$ KB) from DRAM — about 85 flop/byte before L2/shared reuse pushes effective intensity far higher. Larger tiles raise reuse; the ceiling is shared memory (164 KB/SM on Ampere) and registers (65,536 32-bit registers per SM).

### 4.4 Data movement: the other half of the arithmetic

Tensor cores are only as fast as their operands' arrival. Three mechanisms choreograph movement:

- **`ldmatrix` (Ampere+).** A warp-collective shared-memory→register load whose documented lane mapping lets kernels XOR-swizzle shared memory to eliminate bank conflicts *without* breaking the fragment contract [2]. This replaced per-thread vectorized loads plus `__shfl`-based rearrangement.
- **`cp.async` (Ampere+) / TMA (Hopper+).** Asynchronous global→shared copies with commit/wait groups, enabling *software pipelining*: the mainloop prologue issues copies for several $K$-slabs ahead, then each iteration waits only on the needed stage. Hopper's Tensor Memory Accelerator generalizes this to hardware-managed descriptors supporting arbitrary tensor layouts and multicast to threadblock clusters [3][5].
- **WGMMA (Hopper).** The warpgroup matrix instruction widens the cooperative unit from 32 to 128 threads and the atom to shapes like $64 \times 256 \times 16$, reading $A$ directly from shared memory — a response to register files, not math units, becoming the binding constraint [5].

The CUTLASS 3.x CuTe framework expresses all of this as *atoms* (hardware ops with layouts) composed by *tiled* operators, so one kernel template spans Volta's warp-synchronous MMA through Hopper's asynchronous WGMMA [5].

## 5. Empirical Results / Proofs

We validate the model with published figures and roofline analysis.

### 5.1 Roofline placement

The roofline model [7] bounds attainable performance as $\min(\text{peak flops},\, \text{bandwidth} \times \text{intensity})$. For an A100 (312 TFLOPS FP16 dense, 1.6 TB/s HBM2):

| GEMM shape | Intensity (flop/B) | Bound | Achieved (CUTLASS-class) |
|---|---|---|---|
| $4096^3$ FP16 | $\approx 341$ | compute: 312 TFLOPS | ~285 TFLOPS (91%) |
| $1024^3$ FP16 | $\approx 85$ | compute (marginal) | ~250 TFLOPS |
| $256^3$ FP16 | $\approx 21$ | memory: ~34 TFLOPS | ~30 TFLOPS |
| $64 \times 4096 \times 4096$ (skinny) | $\approx 5$ | memory-bound | bandwidth-limited |

The crossover — the ridge point — sits near 195 flop/byte on A100, which is why only large, square-ish GEMMs reach tensor rates, and why skinny GEMMs (e.g., inference decode) demand different strategies: persistent kernels, split-K, or Stream-K decompositions.

### 5.2 Microarchitectural evidence

Instruction-level microbenchmarking of Ampere confirms the architectural claims this model depends on: MMA instructions issue at warp granularity with multi-cycle latency hidden by the register-blocked inner loop, and `ldmatrix` realizes bank-conflict-free patterns on 128-bit-swizzled shared-memory tiles — consistent with whitepaper throughput tables [3][8].

### 5.3 Numerical validation of the mixed-precision invariant

Following [4], the empirical record is decisive: ResNet-50, Transformer, and GAN training with FP16 tensor-core math, FP32 master weights, and dynamic loss scaling match FP32 baselines to within noise, while TF32 training typically needs *no* algorithmic change — exactly what the error analysis of §4.2 predicts, since TF32's exponent range eliminates overflow while accumulation stays FP32 [3][4].

> **Theorem:** *Optimality of the three-level tiling.* For a machine with register file $R$, shared memory $S$, and atom shape $(m,n,k)$, the tiling maximizing arithmetic intensity subject to $R$ and $S$ capacity uses the largest warp tile fitting in registers and the largest CTA tile fitting in shared memory; any smaller tile is strictly dominated on intensity, and any larger tile spills. Hence tile selection reduces to a bounded integer search — which is why autotuned shapes cluster at $(128, 256, 32)$-style points.

> **Proof sketch:** Intensity $I = 2M_bN_bK_b / (M_bK_b + K_bN_b)$ bytes$^{-1}$ is monotone increasing in each tile dimension while feasibility is monotone decreasing; the optimum lies on the feasibility boundary. ∎

## 6. Limitations

- **Small and skinny GEMMs.** The warp-cooperative model assumes enough work to fill tiles. For $M, N < 64$ or extreme aspect ratios, padding waste and underfilled warps dominate and tensor cores sit idle; Stream-K and persistent-CTA schedules mitigate but do not eliminate this.
- **Register pressure vs. occupancy.** A $64 \times 64$ FP32 accumulator consumes 128 registers per thread; with 65,536 registers per SM, at most 16 warps can be resident — often just 1–2 threadblocks per SM. Fewer resident warps means less latency hiding for non-tensor instructions (address math, predicates), a tradeoff the autotuner must navigate.
- **Fragment opacity and portability.** `wmma` fragment layouts are unspecified; PTX layouts are documented but differ across `mma.sync` (warp) and `wgmma` (warpgroup) generations. A kernel written against Ampere's fragment contract is not source-portable to Hopper's warpgroup model — CUTLASS's CuTe abstraction exists precisely to absorb this churn [5].
- **Numerical edge cases.** FP16 accumulation is excluded from the fast path for good reason: with $u = 2^{-11}$, reductions of length $K > 2048$ lose all significance. FP8 training remains brittle under activation outliers and typically needs per-tensor or delayed scaling. The §4.2 bounds are worst-case; adversarial spectra can approach them.
- **Structured sparsity constraints.** The 2:4 pattern is a hardware straitjacket: models must be pruned to the pattern and fine-tuned, and the speedup applies only to the $A$ operand (weights), not to arbitrary sparse-dense products.
- **Measurement limits.** Vendor peaks assume ideal clocks and dense, aligned, large GEMMs; sustained application throughput (e.g., end-to-end training step time) is typically 40–70% of peak once communication, epilogues, and non-GEMM ops are included.

## 7. Conclusion

Tensor-rate GEMM is the product of a three-way contract: **hardware** evaluating fixed-shape matrix atoms at hundreds of teraflops, **a cooperative programming model** in which 32 (or 128) threads jointly own every operand through specified register fragments, and **an arithmetic discipline** — narrow multiply, wide accumulate, master weights, loss scaling — keeping reduced precision honest. The kernel architecture realizing this contract, from `ldmatrix` fragment loads through `cp.async`/TMA pipelining to fused epilogues, is crystallized in libraries like CUTLASS [5], and the roofline model [7] tells us exactly when the machinery earns its keep.

The trajectory is clear: each generation widens the cooperative unit (thread → warp → warpgroup → threadblock cluster) and narrows the arithmetic (FP32 → FP16 → FP8 → FP4 with microscaling). The enduring lesson is that *throughput is a property of the whole stack* — atom, fragment layout, tile hierarchy, copy pipeline, and number format must be co-designed. Future work lies in automating that co-design: tile-shape synthesis from hardware cost models, verified fragment-layout compilation, and precision assignment driven by rigorous error bounds rather than folklore.
