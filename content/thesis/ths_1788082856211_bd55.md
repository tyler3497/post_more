# Isolation Without Containers: gVisor Sentry, Firecracker MicroVM Boot Time, Kata Containers 3.0, and Intel TDX Confidential Containers for Multi-Tenant Serverless

## Abstract
Multi-tenant serverless platforms require strong isolation without sacrificing sub-second startup, density, and orchestration compatibility. This thesis synthesizes four isolation paradigms that avoid traditional Linux container sharing: gVisor Sentry as a user-space kernel interposing on 260+ Linux syscalls, Firecracker MicroVMs as minimal Rust VMMs achieving 125 ms boot and 5 MB overhead, Kata Containers 3.0 as a Rust-runtime blending hypervisor-in-shim with a single-process-per-pod model, and Intel Trust Domain Extensions (TDX) Confidential Containers (CoCo) as hardware-rooted encrypted VM execution with remote attestation. We present a comparative architecture analysis, threat-model decomposition, and empirical synthesis from published NSDI, USENIX, MDPI, and vendor specifications. Quantitative results show Firecracker snapshot-restore reduces cold start from ~200 ms to 1–5 ms (40–200×), gVisor's systrap and DirectFS improve stat() microbenchmarks by >2× and Ruby load by 17%, Kata 3.0 collapses 2+ host processes into one reducing memory footprint while adding VFIO GPU pass-through, and Intel TDX adds PAMT-tracked private memory with TD Quote attestation via report_data binding. We propose a decision matrix for platform

## 1 Introduction

Traditional containers share the host kernel via namespaces and cgroups. For untrusted multi-tenant workloads — Lambda functions, CI jobs inspecting malicious packages, LLM agents executing AI-generated code — sharing is insufficient. An escape via CVE-2019-5736-style runc overwrite or io_uring vulnerability becomes cross-tenant breach.

Four production systems attempt *isolation without containers* in the strict sense:

1. **gVisor** reimplements Linux in Go as Sentry, using only <20 host syscalls to talk to the kernel [3].
2. **Firecracker** strips QEMU to four emulated devices (virtio-net, virtio-block, serial, i8042 reset), written in Rust, boots in <125 ms [1].
3. **Kata Containers 3.0** wraps each pod in a lightweight VM with its own kernel (v5.19.2) but presents OCI semantics [4][5].
4. **Intel TDX + Confidential Containers** encrypts guest memory, moves image pull inside the Trust Domain (TD), and requires Key Broker Service (KBS) attestation before secret release [6][7].

> **Theorem:** *Isolation Strength Hierarchy.* For attacker controlling untrusted workload, isolation strength ordered as `runc < gVisor (syscall interposition) < Kata (VM + kernel) < Firecracker (minimal VMM) < TDX-CoCo (hardware-encrypted + attested)` under metric of reachable host kernel CVEs, with tradeoff in cold-start latency and I/O amplification.

This thesis provides the first unified treatment across these four, drawing from **Agache et al. NSDI'20 Firecracker paper** [1], gVisor DirectFS optimization [2], Kata 3.0 release analysis [4][5], Intel TDX Module Base Spec May 2026 [6], Intel's CoCo overview [7], MDPI file I/O comparative study [8], AWS Lambda MicroVM launch [9], and dstack-capsule Pod-level attestation arXiv [10].

## 2 Background

### 2.1 Linux Container Weaknesses
Linux containers assume benign tenants. Seccomp-BPF default Docker profile blocks ~44 of 300+ syscalls, leaving 256 reachable. User namespaces mitigate privilege but not kernel attack surface. Historical escapes exploited `procfs` symlink traversal, `cgroups` release_agent, and overlayfs.

### 2.2 gVisor Sentry Model
gVisor architecture comprises **Sentry** (kernel-like Go process intercepting syscalls) and **Gofer** (9P file server) [3]. Historically ptrace-based, default now is **systrap** — seccomp trap raising SIGSYS to bounce to handler, faster than ptrace. KVM platform optionally uses hardware virtualization. Sentry implements signals, futexes, pipes, mm, netstack (netstack or host). Gofer holds FDs; sandbox cannot walk `..` to escape. Defense-in-depth: Sentry itself is seccomp-filtered and capability-dropped.

Critical innovation: *DirectFS* (2023) allows sandbox to make `openat(2)` directly with `O_NOFOLLOW`, no procfs, no dir FDs from host, reducing RPCs to Gofer. Result: stat() >2× faster, Ruby load -17% [2].

### 2.3 Firecracker MicroVM Minimalism
AWS Firecracker started 2017, open-sourced 2018. Design goals: <5 MB per MicroVM, <150 ms boot, <5K lines Rust for device model, 1000s MicroVMs per `i3.metal` host [1]. Device model: virtio-net (TAP + cgroup rate limiter), virtio-block, serial console, i8042 keyboard controller for reset only. No BIOS — kernel loaded directly to guest memory, vCPU jumps to entry. API-driven REST over Unix socket: PUT `/boot-source`, `/drives/rootfs`, `/machine-config`, then `InstanceStart`.

**Jailer** binary adds second isolation layer: cgroups, namespaces, chroot, seccomp-bpf. Snapshot/restore: boot once, snapshot memory/disk, restore 1–5 ms on cold start [9].

### 2.4 Kata Containers Evolution to 3.0
Kata Containers merges Intel Clear Containers and Hyper.sh runV. Kata 2.0 migrated to Rust runtime; Kata 3.0 rewrites runtime fully in Rust, integrates optional Rust hypervisor, yielding **single process per pod** vs ≥2 previously [4]. Supports hypervisors: QEMU, Cloud Hypervisor, Firecracker. Components: `kata-runtime` (shim v2 interface to containerd/CRI-O), `kata-agent` inside guest handling OCI lifecycle, guest kernel 5.19.2. Kubernetes integration via `RuntimeClassName: kata`. Blocks `kubectl exec` in CoCo mode for confidentiality. Adds cgroup v2, static resource management, GPU VFIO pass-through [5].

### 2.5 Intel TDX and Confidential Containers
Intel TDX creates Trust Domains (TDs) with private memory tracked by **Physical Address Metadata Table (PAMT)** — three levels for 4K/2M/1G pages [6]. TDR (Trust Domain Root) encrypted with global private HKID, first allocated last freed. TDCS multipage control structure encrypted with TD ephemeral key. Secure EPT (Extended Page Tables) maps TD private GPA. Attestation via TD Quote containing MRTD (build-time measurement), RTMR[0-3] (runtime), and `report_data` (64B custom, used for pod UID binding) [10].

CoCo combines TEE + Kata: process isolation via SGX enclaves, VM isolation via TDX/SEV-SNP, unifying under one Kubernetes operator. Images encrypted, pulled inside TD, decrypted after KBS attests platform patched level, measurements [7].

## 4 Deep Dive

### 4.1 gVisor Sentry Internals: Systrap, KVM, and DirectFS

Sentry's syscall table implements >70% of 319 Linux syscalls [3]. Missing coverage handled via passthrough or ENOSYS with fallback. Example: `clock_gettime` fast-path via Go time vs host vdso. Seccomp filter for Sentry process denies dangerous calls like `mount`, `ptrace` self.

```go
// runsc configuration snippet
runsc --platform=systrap --network=sandbox \
  --file-access=exclusive --overlay2-root \
  run -d nginx
```

*DirectFS* trade-off: giving sandbox `CAP_DAC_OVERRIDE` and `openat` increases reliance on Linux FS isolation vs syscall filter. Security proof obligation shifts: verify no `..` traversal via malicious symlink — Gofer still provides FD root.

> **Theorem:** *Sentry Non-Escape.* If Gofer is trusted and only provides FDs within container rootfs, and DirectFS enforces O_NOFOLLOW + no procfs, then sandbox process cannot obtain FD outside rootfs even with CAP_DAC_OVERRIDE.

*Limitation:* mmap-heavy workloads trigger Sentry page faults emulated in userspace, costing 2-4×.

### 4.2 Firecracker Boot Time Optimization: From 125 ms to 1–5 ms Snapshot

Firecracker boot pipeline:

1. Jailer fork + cgroup setup (~10 ms)
2. API socket config (~5 ms)
3. Kernel decompress + vCPU start (~30 ms)
4. Guest init (Alpine) + agent vsock listen (~80 ms)

Total 125 ms. For Lambda scale, pre-boot pool kept. Snapshot flow:

```python
# Firecracker snapshot create via API
import requests_unixsocket
session = requests_unixsocket.Session()
session.put('http+unix://%2Ftmp%2Ffirecracker.socket/snapshot/create',
  json={"snapshot_type":"Full","snapshot_path":"/snap/mem","mem_file_path":"/snap/memfile"})
# restore
session.put('http+unix://%2Ftmp%2Ffirecracker.socket/snapshot/load',
  json={"snapshot_path":"/snap/mem","mem_file_path":"/snap/memfile","enable_diff_snapshots":False})
```

Snapshot restores avoid re-running language runtime init, reducing cold start to 1–5 ms [9]. Tricky: snapshot timing — too early misses runtime init, too late captures live vsock state causing collision.

**Rate limiting:** Firecracker VMM implements token-bucket for net/block I/O at VMM layer, preventing noisy neighbor propagation without guest cooperation [1].

### 4.3 Kata Containers 3.0: Single-Process-per-Pod and Hypervisor Choice

Kata 2.0: `kata-runtime` (Go) + `kata-shim` + `QEMU` = 2+ processes. Kata 3.0 Rust runtime embeds hypervisor logic, single host process.

```rust
// Rust shim pseudo - single process model
fn handle_create(oci_spec: &Spec) -> Result<Pod> {
    let vm = match hypervisor {
        Hypervisor::CloudHypervisor => CHVM::new(oci_spec)?,
        Hypervisor::Firecracker => FcVM::new(oci_spec)?,
        Hypervisor::QemuTdx => QemuTdxVM::new(oci_spec)?,
    };
    vm.boot()?; // 150-400ms
    vm.agent_exec(oci_spec.process)
}
```

Kata agent inside guest runs as PID 1, communicates via vsock `kata-agent` protocol, handles `CreateContainer`, `StartContainer`. File sharing via 9P or virtiofsd (async). MDPI study finds virtiofsd does frequent `memcpy` host<->VM, burning 143.7% CPU avg, causing lowest throughput (581-752 MB/s seq, 13.7% of Firecracker) [8].

Kubernetes pod example:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  runtimeClassName: kata
  containers:
  - name: app
    image: busybox
    command: ["sh","-c","echo hi && sleep 3600"]
```

Kata 3.0 adds `image-rs` signature verification, offline filesystem KBC for air-gapped confidential containers, static resource management for speed.

### 4.4 Intel TDX Confidential Containers: PAMT, RTMR, and Pod-Level Attestation

TDX module manages PAMT entries: `PT_NDA` (not assigned), `PT_REG` (TD private), `PT_TDR`, `PT_TDCX`, etc [6]. Memory assigned via `TDH.MEM.PAGE.AUG`. SEAMCALL is privileged root-mode call into Intel TDX module running in SEAM range.

TD lifecycle:

1. `TDH.MNG.CREATE` — allocate TDR
2. `TDH.MNG.KEY.CONFIG` — generate ephemeral key
3. `TDH.MNG.ADDCX` × N — add TDCS pages
4. `TDH.MEM.SEPT.ADD` — populate Secure EPT
5. `TDH.MNG.INIT` — finalize measurement MRTD
6. `TDH.VP.CREATE` — add vCPUs
7. `TDH.VP.ENTER` — run

Remote attestation: TDX Quote structure contains:

- `TD_INFO`: attributes, XFAM, MRTD, MRCONFIGID
- `RTMR[0-3]`: runtime measurements extendable via `TDG.MR.RTMR.EXTEND`
- `REPORT_DATA`: 64-byte custom, used by dstack-capsule to embed `pod_uid`, `pod_spec_hash`, `workload_id` [10]

```go
// Pod-level attestation binding pseudo
reportData := sha256(podUID || podSpecHash || workloadID)
quote := tdx.GetQuote(reportData) // TDG.MR.REPORT + QE
kbs.Verify(quote, expectedRTMR3) // frozen platform
```

dstack-capsule insight: freeze RTMR[3] platform measurement via irreversible *privilege fuse* after setup, then dynamic pod identities in `report_data` signed each request, enabling **multiple pods per confidential VM** while retaining independent hardware-backed proof [10]. CoCo default enforces one Pod per VM, incurring per-VM overhead.

Confidential image flow:

```yaml
spec:
  runtimeClassName: kata-qemu-tdx
  containers:
  - image: docker.io/enc/llama:encrypted
```

KBS must attest before releasing image decryption key.

### 4.5 Comparative Threat Model & Multi-Tenant Serverless Mapping

**Threats:**

- Container escape to host kernel
- Cross-tenant memory disclosure (e.g., L1TF, MDS)
- Malicious image or supply-chain
- Untrusted cloud provider (CoCo addresses)

**Mapping:**

- *Edge CDN multi-tenant*: gVisor ideal — process-like density, grows/shrinks like process, no pre-alloc [3].
- *FaaS scale-up*: Firecracker — pre-booted pool, snapshot-restore 40-200× improvement, API-driven orchestration [1][9].
- *K8s untrusted third-party*: Kata 3.0 — OCI compat, RuntimeClass selective, GPU VFIO for AI [4].
- *Financial/LLM-as-a-Service*: TDX-CoCo — hardware-encrypted memory, no host-readable, attestation proof for compliance [7][10].

**Isolation theorem formal:**

> **Theorem:** *TDX Confidentiality.* If SEAM range correctly isolates TDX module, PAMT correctly tracks ownership, and HKID encryption uses AES-XTS 128-bit with integrity via TD Owner bit, then adversary with Ring-0 host privileges cannot read TD private memory without detection, under Intel TDX threat model [6].

## 5 Empirical Evaluation / Proofs

### 5.1 Aggregated Numbers (Synthesis, not fresh benchmark)

From sources:

- **Boot latency:**
  - QEMU MicroVM: ~600 ms (2.5× worse than QEMU normal) per Firecracker NSDI data discussion [1 discussion thread]
  - Firecracker: 125 ms cold, 5 MB overhead, 4000 MicroVMs on i3.metal 72 vCPU 512 GB [1]
  - Firecracker snapshot-restore: 1–5 ms vs full 200 ms = 40–200× [9]
  - Kata: 150–400 ms native, optimized Firecracker/Cloud Hypervisor closer to native [Kata doc]
  - CoCo pod creation 30s dominated by LLM image pull [7 demo]

- **File I/O (MDPI edge study, block 4K–1M):**
  - Seq read avg: runc 2458 MB/s, Firecracker 4749 MB/s @1M (highest), gVisor 4058 MB/s read / 2578 MB/s write @1M scaling with block, Kata 581–752 MB/s (13.7% Firecracker) [8].
  - CPU: Kata 143.7% avg, Firecracker 112.8% mostly Guest (87.6% read 92.2% write), gVisor System category grows with block, Gofer work counted in System [8].
  - Random read: runc 2458 avg, Kata 422 avg lowest, Firecracker 4749 @1M 4.3× Kata [8].

- **gVisor DirectFS:** stat() >2×, Ruby load -12% absolute, -17% load time [2].

- **TDX PAMT overhead:** logical PAMT Block = 1×1G entry + 512×2M + 512×4K entries per 1G TDMR Block [6]. Memory overhead ~1/256 for tracking.

### 5.2 Security Proofs Sketch

**Lemma 1 (Sentry syscall confinement):** Sentry uses seccomp to allow <20 host syscalls. If Sentry implementation in Go is memory-safe, attacker controlling workload cannot directly issue host `execve`, `mount`, `ptrace`.

**Lemma 2 (Firecracker minimal device):** With 4 devices, attack surface LOC ~ 5K Rust vs QEMU ~1.4M C. CVE count proportionally smaller; Rust eliminates use-after-free class [1].

**Lemma 3 (Kata VM boundary):** Guest kernel CVE does not directly grant host access; need hypervisor breakout (QEMU/CH). With Cloud Hypervisor Rust, hypervisor CVE count lower than QEMU.

**Lemma 4 (TDX encryption):** Memory encryption with private HKID + Secure EPT prevents host from mapping TD private pages as shared without TDH.MEM.RANGE.BLOCK + TDG.VP.VMCALL.

Combined theorem above follows from lemmas + TDX module spec verification.

## 6 Limitations & Open Problems

1. **gVisor compatibility:** Not full Linux; 200+ syscalls implemented, missing `io_uring`, `eBPF` passthrough limited. Performance penalty for mmap/mprotect heavy workloads remains.

2. **Firecracker feature gaps:** No device passthrough → no GPU, no live migration, no complex storage, Linux/OSv only [1]. Snapshot timing fragility; vsock state inheritance bug.

3. **Kata virtiofsd amplification:** Asynchronous notification + memcpy burns CPU, lowest I/O throughput. Need DAX-enabled virtiofs or block-based image with guest page cache.

4. **TDX side channels:** Encrypted memory protects confidentiality but not access-pattern; controlled-channel via page faults still possible. PAMT overhead for 1G pages tracking still ~0.4% memory. Attestation revocation list (TCB Info) freshness problem.

5. **Pod-level attestation scaling:** dstack-capsule privilege fuse irreversible — setup error bricks node; requires Sysbox for multi-layer sandbox, complexity. CoCo one-Pod-per-VM wastes memory; multi-Pod-per-TD needs storage/runtime/admission/network isolation layers [10].

6. **Economics:** TDX requires Emerald Rapids+ with TDX enabled BIOS; cloud availability limited to Azure, GCP C3D confidential VMs; cost 20-30% premium.

7. **Formal verification gap:** No end-to-end proof combining Sentry Go memory safety, Firecracker Rust type safety, Kata Rust shim, and TDX hardware. Need TLA+ spec for snapshot/restore consistency.

## 7 Conclusion

Isolation without containers is not one technology but a spectrum. **gVisor Sentry** offers process-density isolation for edge multi-tenancy with <20 host syscalls and Go memory safety, accelerated by systrap and DirectFS. **Firecracker MicroVMs** deliver 125 ms cold, 1–5 ms snapshot-restore, 5 MB overhead, and Rust minimal device model enabling 4000 MicroVMs per host, forming Lambda's isolation backbone. **Kata Containers 3.0** collapses multi-process to single Rust process per pod, adds VFIO GPU, cgroup v2, and OCI/Kubernetes seamlessness, at cost of virtiofsd I/O overhead. **Intel TDX Confidential Containers** encrypt guest memory via PAMT-tracked private pages, move image inside TD, and attest via Quote + RTMR + report_data, enabling Pod-level remote attestation for LLM-as-a-Service.

For platform builders:

- Choose **gVisor** when density and syscall filtering suffice, workloads untrusted but not hostile cloud.
- Choose **Firecracker** when millisecond scale-up and API-driven orchestration dominate.
- Choose **Kata 3.0** when Kubernetes untrusted workload with GPU and pod semantics required.
- Choose **TDX-CoCo** when provider untrusted or compliance demands hardware-rooted proof.

Future work: DAX virtiofs for Kata, TDX live migration with encrypted state, Pod-level attestation standardization in CNCF CoCo, and TLA+ verification of snapshot/restore vsock quiescence.
