# Formalizing Rust's Borrow Checker: Stacked Borrows versus Tree Borrows, Miri Interpretation, Unsafe Code Guidelines, and Provenance Models for Raw Pointer Optimization

## Abstract

Rust's ownership type system statically guarantees memory safety for safe code, yet the language simultaneously permits unsafe code that bypasses the borrow checker, creating a fundamental tension between the compiler's aliasing assumptions and real program behavior. This thesis formalizes the operational aliasing models mediating this tension: Stacked Borrows, the stack-based model long serving as Miri's default undefined-behavior detector, and Tree Borrows, its tree-structured successor reframing aliasing as a dynamic permission state machine over pointer-derivation trees. We present Miri's operational semantics for both models - retagging, protector invariants, two-phase borrows, interior mutability via UnsafeCell, and strict versus exposed pointer provenance. We show how each model's transition rules bound the aliasing assumptions a compiler may soundly exploit for read-read reordering and noalias-based register promotion. An empirical survey of the 30,000-crate ecosystem evaluation and stdlib adaptations quantifies the trade-off: Tree Borrows rejects 54 percent fewer real-world test cases while retaining the key optimizations Stacked Borrows enabled. We conclude with the optimizer soundness theorems, limitations around integer-to-pointer casts, and open problems on the path to a stabilized model.

## 1. Introduction

The Rust programming language has achieved remarkable industrial and academic impact by promising *fearless concurrency* and *zero-cost abstraction* without a garbage collector. At the core of this promise lies the ownership and borrowing discipline: every value has exactly one owner; references (`&T`, `&mut T`) are statically checked against aliasing and mutation; lifetimes bound the scope of borrowing. For safe code, the borrow checker suffices. For `unsafe` code, however, the static rules are suspended, and the question arises: *what aliasing discipline governs raw pointers?*

The answer matters not merely for bug detection but for the soundness of the optimizer itself. The Rust compiler — like LLVM-based compilers for C/C++ — assumes aliasing information from types when reordering memory accesses, eliminating loads, and promoting values to registers. If unsafe code violates the discipline the optimizer assumes, the resulting miscompilations are silent and devastating. The Unsafe Code Guidelines (UCG) working group [3] was chartered to define precisely which unsafe patterns constitute undefined behavior (UB), thereby drawing the contract between programmer and compiler.

This thesis unifies four strands of that effort:

1. **Stacked Borrows** [1]: an operational aliasing model in which each memory location carries a *stack* of tagged borrow items with fixed permissions; memory accesses pop invalidated items and report UB on permission violations.
2. **Tree Borrows** [2]: a successor model replacing the stack with a *tree* of pointer-derivation relationships, in which each node carries a *state machine* over permissions that evolve with access history, and reference ranges are tracked dynamically rather than statically.
3. **Miri** [4]: the MIR interpreter implementing both models as runtime UB detectors, with flags (`-Zmiri-tree-borrows`, `-Zmiri-strict-provenance`) for auditing unsafe libraries.
4. **Provenance models**: the theory of where pointer *provenance* comes from — which allocation a pointer may access — and how strict provenance, exposed provenance, and wildcard provenance govern integer-to-pointer casts, a critical frontier for the models' completeness [5].

Our contributions are: (a) a unified, self-contained formalization of both models' transition systems with comparative tables; (b) an analysis of how each model's rules delimit the optimizer's sound program transformations, including the Stacked Borrows `write_both` theorem and Tree Borrows' read-read reordering proof in Rocq; (c) an empirical evaluation synthesizing the 30,000-crate study, stdlib case studies, and Miri flag semantics; and (d) a catalog of limitations and open problems, including two-phase borrows, interior mutability granularity, and the eventual stabilized model.

## 2. Background and Related Work

### 2.1 Rust's Ownership Discipline and `unsafe`

Rust's borrow checker enforces three invariants: (i) one `&mut` *or* many `&`, never both; (ii) references cannot outlive referents; (iii) data races require `Sync`/`Send`. The `unsafe` keyword relaxes the borrow checker's enforcement for five operations — dereferencing raw pointers, calling `unsafe` functions, accessing `static mut`, implementing `unsafe` traits, and accessing union fields — but crucially does *not* suspend the aliasing invariants themselves. As the Rustonomicon and UCG materials stress: **`unsafe` does not give you C semantics**; all other Rust invariants (provenance, aliasing, validity, layout) remain in force [6].

The canonical failure is aliasing mutable references constructed through raw pointers:

```rust
fn f(x: &mut i32, y: &mut i32) { *x = 7; *y = 42; }

let mut v = 5;
let p = &mut v as *mut i32;
unsafe { f(&mut *p, &mut *p) } // two &mut to the same location: UB
```

The compiler may assume `x` and `y` do not alias; Stacked Borrows declares two live `&mut` to the same location undefined behavior [7].

### 2.2 Stacked Borrows: Origins and Mechanization

Stacked Borrows was introduced by Jung, Dang, Kang, and Dreyer in "Stacked Borrows: An Aliasing Model for Rust" (OOPSLA 2020) [1]. Its central insight: model the borrow checker's guarantees *operationally*, as a runtime discipline on memory accesses, and declare violations UB. The model was mechanized in Coq (now Rocq), yielding proofs that the rules admit key optimizations — reordering accesses around unknown code and function calls — based on intraprocedural reasoning alone. The model was validated by executing large parts of the Rust standard library test suite inside Miri, confirming it permits realistic unsafe code [1].

> **Theorem (Stacked Borrows optimization soundness, informal):** Under Stacked Borrows, the compiler may reorder a read of location ℓ before a call to unknown code, provided no live mutable borrow of ℓ could have been passed to that code — a condition checkable intraprocedurally.

### 2.3 Tree Borrows: Motivation and Design

Stacked Borrows nonetheless rejects patterns common in real-world unsafe Rust [2]:

- **Two-phase borrows** (used in `vec.push(x)` autoref desugaring): a reserved `&mut` coexists with shared reborrows during the reservation phase; the stack model cannot track multiple children of one parent, so it punishes legitimate code.
- **Eager invalidation**: creating a reborrow in Stacked Borrows immediately invalidates the parent for future reads of disjoint fields, famously breaking `Vec::push` with outstanding interior references even absent reallocation [8].
- **Static reference ranges**: footprints are computed statically from types, punishing harmless out-of-range accesses.

Tree Borrows (Villani, Hostert, Dreyer, Jung, PLDI 2025) [2] replaces the stack with a tree, where each reference has a unique parent — the reference or local it was derived from — and each node runs a permission state machine updated on every access. Critically, a reborrow "pays the cost" only for locations it actually reads or writes, and reference ranges are computed dynamically. The evaluation on the 30,000 most widely used crates showed Tree Borrows rejects **54% fewer test cases** than Stacked Borrows, while Rocq proofs establish that it retains most Stacked Borrows optimizations and enables new ones, notably *read-read reordering* [2].

### 2.4 Miri and the Interpreter Approach

Miri [4] interprets Rust MIR with full tracking of allocations, provenance tags, and aliasing state — the reference implementation of both models, with `-Zmiri-tree-borrows` selecting Tree Borrows and sub-flags tuning permissiveness [5]. Its philosophy — *execute the abstract machine precisely enough to catch UB before the optimizer exploits it* — makes it the primary UCG validation instrument.

### 2.5 Pointer Provenance

Independent of borrow stacks, every pointer carries *provenance*: the allocation (and derivation history) it may legally access. Strict provenance (tracking issue rust-lang/rust#95228) [9] forbids integer-to-pointer casts outright, since a bare integer has no provenance; exposed provenance (`expose_addr`) and wildcard provenance are progressively weaker alternatives. Under Tree Borrows, `-Zmiri-tree-borrows` currently implies `-Zmiri-strict-provenance` because integer-to-pointer casts remain unsupported [5].

## 3. Methodology

Our method is that of programming-languages meta-theory combined with empirical systems validation:

1. **Formalization.** We reconstruct both models as small-step operational semantics over an abstract machine with per-location borrow metadata, defining state spaces, access transitions, and UB predicates.
2. **Optimizer analysis.** For each model we characterize the set of sound program transformations as those preserving observable behavior for all UB-free executions (the *blame* framing of [1]), and we tabulate which classical optimizations each model admits.
3. **Empirical synthesis.** We aggregate (i) the 30,000-crate differential evaluation between models [2]; (ii) the stdlib adaptation history (VecDeque, Futures, str, BTreeMap, LinkedList patches required for Stacked Borrows compliance) [3]; and (iii) Miri's flag semantics as documented in its README [5].
4. **Limitations audit.** We catalog the known incompleteness results: integer-to-pointer casts, weak-memory interactions, union/enum `UnsafeCell` detection, and the eventual-model uncertainty explicitly acknowledged by Miri's documentation [5].

We worked from the primary sources — the two papers, the UCG working documents, and the Miri README — rather than secondary summaries, and all citations below reference artifacts we directly consulted.

## 4. Deep Dive

### 4.1 Stacked Borrows: Stacks, Tags, Permissions, and Retagging

In Stacked Borrows, every memory location carries a *borrow stack*: a sequence of items, each a pair `(tag, permission)`. Tags are fresh identifiers minted at each reborrow; permissions are drawn from `{Unique, SharedReadWrite, SharedReadOnly, Disabled}`. The top of the stack represents the currently active borrow.

**Retagging.** When MIR executes `Retag(kind, place)` — at function entry for reference arguments, on reference creation, and on raw-pointer casts when `-Zmiri-tag-raw-pointers` is set — the interpreter mints a fresh tag and *grants* it permission over every location in the place [3]:

```rust
pub enum RefKind {
    /// `&mut` and `Box`.
    Unique { two_phase: bool },
    /// `&` with or without interior mutability.
    Shared,
    /// `*mut`/`*const` (raw pointers).
    Raw { mutable: bool },
}
```

The granted permission depends on `RefKind` and `UnsafeCell` membership [3]:

| RefKind | Permission |
|---|---|
| `Unique { two_phase: false }` | `Unique` |
| `Unique { two_phase: true }`, `Raw { mutable: true }` | `SharedReadWrite` |
| `Shared`, `Raw { mutable: false }` outside `UnsafeCell` | `SharedReadOnly` |
| `Shared`, `Raw { mutable: false }` inside `UnsafeCell` | `SharedReadWrite` |

**Accesses.** An access through tag `t` searches the stack from the top; incompatible items above `t` are *popped*. Writes pop everything except raw-pointer items; reads pop `Unique` items above a `SharedReadOnly` reader. If `t` is absent or its permission forbids the access, the machine reports UB [1].

**Protectors.** References passed at function boundaries receive *protectors*: a call-id-keyed guard asserting the borrow remains valid for the call's duration. On return, and on deallocation (which additionally performs a write-access check), any still-active protector whose borrow was invalidated triggers UB. Protectors are what make `&mut` parameters behave like `noalias` across unknown callees — the load-bearing assumption behind intraprocedural optimization [3].

> **Theorem:** *If a program executes without Stacked Borrows UB, then every `&mut` reference observed by the optimizer is the unique live path to its location; hence stores through disjoint `&mut` parameters may be reordered freely.*

### 4.2 Tree Borrows: Permission State Machines over Derivation Trees

Tree Borrows keeps the tagging and retagging infrastructure but replaces each location's stack with membership in a *tree* of nodes. Each node corresponds to one pointer; its parent is the pointer it was derived from (or the allocating local). Each node carries a **permission state machine** whose states include `Reserved`, `Active`, `Frozen`, and `Disabled`, evolving on every read/write performed by any node in the tree [2].

The crucial departure from Stacked Borrows is that permissions are *dynamic*: a `&mut` node begins `Reserved` and becomes `Active` only upon its first write; a `&` node is `Frozen` and tolerates foreign reads. Accesses are classified as *local* (performed by the node or its descendants) versus *foreign* (performed by parents, siblings, or their descendants), and the state transition depends on this classification [2]:

| Node state | Local read | Local write | Foreign read | Foreign write |
|---|---|---|---|---|
| `Reserved` (`&mut`, not yet written) | stays `Reserved` | → `Active` | stays `Reserved` | → `Disabled` |
| `Active` (`&mut`, written) | ok | ok | → `Frozen` | → `Disabled` |
| `Frozen` (`&`, interior-mutable-aware) | ok | → `Disabled` (outside `UnsafeCell`) | ok | → `Disabled` |
| `Disabled` | **UB** | **UB** | — | — |

Because a reborrow costs nothing until an actual access occurs, the `Vec::push` pattern — `&mut v[0]` outstanding across a non-reallocating push — is accepted [8], eliminating the most complained-about Stacked Borrows false positive while preserving the optimizer's `Active`-`&mut` uniqueness assumption.

Tree Borrows also introduces **dynamic reference ranges** — tracking actually-accessed locations rather than static type footprints [2] — and handles two-phase borrows naturally: the reserved `&mut` and shared reborrows are sibling nodes, with activation of the mutable child disabling its siblings [2].

```haskell
-- Sketch of the Tree Borrows transition function
transition :: PermState -> Accessor -> AccessKind -> Maybe PermState
transition Reserved Foreign Write = Just Disabled
transition Reserved Local   Write = Just Active
transition Active   Foreign Read  = Just Frozen
transition Active   Foreign Write = Just Disabled
transition Frozen   Local   Write = Nothing   -- UB outside UnsafeCell
transition Disabled _       _     = Nothing   -- UB: use of dead borrow
transition s        _       _     = Just s
```

### 4.3 Miri: Interpreting the Models

Miri executes Rust MIR — the compiler's desugared, control-flow-graph IR — in a software interpreter that mirrors rustc's borrowck-adjacent `Retag` instrumentation (`-Zmir-emit-retag`) [5]. Key architectural points:

- **Determinism.** `-Zmiri-seed` governs allocation addresses and preemption; `-Zmir-opt-level=0` is forced so optimizations cannot hide UB [5].
- **Model selection.** `-Zmiri-tree-borrows` swaps the borrow tracker; sub-flags (`-Zmiri-tree-borrows-no-precise-interior-mut`, `-Zmiri-tree-borrows-implicit-writes`) adjust strictness. Notably, Miri's own documentation warns that *Tree Borrows is even more experimental than Stacked Borrows* and that the eventual official model will likely be *stricter* than Tree Borrows — code accepted under Tree Borrows today may be declared UB in the future [5].
- **Provenance enforcement.** `-Zmiri-strict-provenance` halts on integer-to-pointer casts, implementing the strict-provenance proposal [9]; `-Zmiri-symbolic-alignment-check` avoids false negatives where alignment holds "by luck" of concrete addresses [5].
- **Diagnostics.** `-Zmiri-track-pointer-tag` and `-Zmiri-backtrace=full` connect a UB report to the reborrow that created the offending tag, essential because aliasing UB is *non-local*.

Miri's data-race detector and weak-memory emulation (`-Zmiri-preemption-rate`, `-Zmiri-track-weak-memory-loads`) sit orthogonally to the borrow models but share the interpreter's allocation provenance, illustrating how provenance is the common substrate of Rust's dynamic UB checking [4][5].

### 4.4 Provenance Models: Strict, Exposed, and Wildcard

Provenance answers: *given a pointer value, which allocations may it touch?* Under strict provenance, a pointer is `(address, allocation-id, borrow-tag)`; casting an integer to a pointer is UB because the integer carries no provenance [9]. The alternatives form a strictness lattice:

1. **Strict provenance** — `with_addr`/`map_addr` preserve provenance; `expose_addr` is explicit; int-to-ptr casts are UB. Enforced by `-Zmiri-strict-provenance` [5][9].
2. **Exposed provenance** — casting a pointer to an integer *exposes* its address; a later int-to-ptr cast recovers provenance only for exposed addresses. Weaker, admits more legacy code.
3. **Wildcard provenance** — int-to-ptr casts yield a pointer usable on any allocation (the C-like extreme); unsound with `noalias` optimizations.

Tree Borrows currently *requires* strict provenance in Miri because its tree structure cannot accommodate provenance-less pointers [5]; stabilizing an aliasing model thus requires stabilizing a provenance model jointly [3][9].

### 4.5 The Optimizer's Contract: What Each Model Admits

The purpose of an aliasing model is to license optimizations. We compare the transformation sets:

| Optimization | Stacked Borrows | Tree Borrows | Notes |
|---|---|---|---|
| Reorder read before unknown call | ✅ proven [1] | ✅ proven [2] | Core `noalias` reasoning |
| Reorder write before unknown call | ✅ | ⚠️ restricted | TB: write must have occurred |
| **Read-read reordering** | ❌ | ✅ proven [2] | New in Tree Borrows (Rocq) |
| `write_both`-style store forwarding | ✅ | ✅ | Canonical example |
| Eliminate redundant `&` loads | ✅ | ✅ | Frozen-node reasoning |
| `noalias` on `Box`/`Unique` | ✅ | ✅ (`-Zmiri-unique-is-unique`) | Experimental TB flag [5] |

The Stacked Borrows logical-relation proof technique was adapted for Tree Borrows in Rocq, with the `Active`-vs-`Reserved` distinction replacing fixed permissions [1][2].

## 5. Empirical Evaluation / Formal Proofs

### 5.1 The 30,000-Crate Differential Study

Running the test suites of the 30,000 most widely used crates under Miri with each model, **Tree Borrows rejects 54% fewer test cases** than Stacked Borrows [2]. The eliminated failures are dominated by the two-phase-borrow and eager-invalidation classes — precisely the targeted patterns — while the remaining rejections are, by manual audit, predominantly *true* aliasing bugs.

### 5.2 Standard Library Adaptation History

Stacked Borrows' validation against the stdlib test suite forced real fixes, documented in the UCG working notes [3]:

- `VecDeque` creating overlapping mutable references (rust-lang/rust#56161)
- Futures turning `&` into `&mut` (rust-lang/rust#56319)
- `str` turning `&` into `&mut` (rust-lang/rust#58200)
- `BTreeMap` overlapping `&mut` with `&` (rust-lang/rust#58431)
- `LinkedList` overlapping mutable references (rust-lang/rust#60072)

Each fix restructured unsafe code to respect the stack discipline or introduced `UnsafeCell` where interior mutability was genuine — evidence the model tracks programmer intent, with stdlib maintainers acknowledging each as a latent soundness bug [3].

### 5.3 Formal Proof Artifacts

- **Stacked Borrows (Coq):** adequacy of the operational semantics; soundness of access reordering around unknown code [1].
- **Tree Borrows (Rocq):** retention of the Stacked Borrows optimizations plus read-read reordering [2].
- **Miri:** no full soundness proof; validation is empirical via differential testing and the `tests/pass` / `tests/fail` suites [4][5].

## 6. Limitations and Open Problems

1. **No stabilized model.** Neither Stacked Borrows nor Tree Borrows is the official Rust aliasing model. Miri's documentation explicitly warns that the final model will likely be *stricter than Tree Borrows* [5]. All unsafe code written today is validated against a moving target.
2. **Integer-to-pointer casts.** Strict provenance is unimplemented in the compiler; the design space (strict vs. exposed vs. wildcard) remains open, and Tree Borrows cannot currently model int-to-ptr casts at all [5][9].
3. **Interior mutability granularity.** Tree Borrows' byte-level `UnsafeCell` tracking is expensive and its default unsettled [5]; Stacked Borrows' static detection is conservative around enums/unions [3].
4. **Weak memory.** The interaction of borrow-model UB with the Rust memory model (a separate UCG track) is largely unexplored [4].
5. **Protector expressiveness.** The mapping from model protectors to LLVM `noalias` facts is validated by testing, not proof.
6. **Two-phase borrow completeness.** Autoref method-resolution edge cases of the borrow checker's two-phase semantics may still be rejected [2].
7. **Performance of interpretation.** Miri is orders of magnitude slower than native execution; ecosystem-scale validation (30k crates) is a batch undertaking, not a CI gate — limiting the feedback loop for model iteration [2][4].

> **Theorem:** *No aliasing model can simultaneously (a) accept all currently-deployed unsafe Rust, (b) license the full LLVM `noalias` optimization suite, and (c) be checkable by a decidable runtime monitor — the ecosystem's existing UB and the optimizer's appetite are jointly inconsistent; some code must change.*

This impossibility-flavored observation (informal) explains why the UCG process is fundamentally *negotiative*: each candidate model chooses which existing code to bless and which optimizations to enable.

---

## 7. Conclusion

Stacked Borrows gave Rust its first rigorous operational answer to "what does `unsafe` promise the optimizer?" — a stack discipline, mechanized in Coq, validated against the standard library, and shipped as Miri's default UB detector [1][4]. Tree Borrows refines it with a derivation tree and dynamic permission state machines, accepting the two-phase and lazy-invalidation patterns of real unsafe code while *strengthening* the optimizer with newly-proven read-read reorderings, mechanized in Rocq and validated across 30,000 crates [2]. Miri remains the indispensable instrument where candidate models meet real code [5]; beneath both models, pointer provenance — strict, exposed, or wildcard — determines what a pointer even *is* [9].

The Unsafe Code Guidelines effort continues toward a stabilized model likely stricter than Tree Borrows [3][5]. Until then: run Miri under both models, enable `-Zmiri-strict-provenance`, treat every diagnostic as a bug in the `unsafe` code, and write new unsafe code against the stricter model. The borrow checker made safe Rust fearless; Stacked and Tree Borrows are making *unsafe* Rust honest.
