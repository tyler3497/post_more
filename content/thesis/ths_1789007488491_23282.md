# The eBPF Verifier: Abstract Interpretation, Path Pruning, and the Soundness of Static Analysis for Untrusted Kernel Programs

## Abstract

The extended Berkeley Packet Filter (eBPF) verifier is among the most consequential static analyzers ever deployed: it decides, at program-load time, whether arbitrary untrusted bytecode may execute inside the Linux kernel with full privilege. This thesis dissects the verifier's architecture — a two-pass engine combining control-flow graph construction, abstract interpretation over the tnum and interval domains, symbolic execution of every feasible path, state checkpointing and pruning, bounded-loop analysis, and per-type helper-function checking — and evaluates the soundness and precision guarantees that the design actually delivers. We formalize the verifier as an abstract interpreter over a lattice of register states, prove the pruning relation sound with respect to the concrete collecting semantics, and characterize the exact points at which engineering concessions (precision markings, speculative execution mitigations, `BPF_COMPLEXITY_LIMIT_INSNS`) sacrifice completeness or, in historic failure modes, soundness. We survey the empirical record of verifier escapes (CVE-2020-8835, CVE-2021-3490, CVE-2022-23222, CVE-2026-53671-class bugs) and the formal-verification counteroffensive — mechanized range-analysis checking [4], differential synthesis of abstract operators [1], the PREVAIL zone-domain analyzer [7], and the Linux Foundation security audit [6]. The thesis concludes with a taxonomy of open problems: compositional helper contracts, verified JIT equivalence, and the fundamental soundness–precision tension of verifying an unbounded language with a bounded analysis budget.

## 1. Introduction

Few programs enjoy a security posture as paradoxical as eBPF. A user-space process may submit bytecode that will execute *inside the kernel* — in interrupt context, with access to network packets, system-call arguments, scheduler internals, and arbitrary kernel data structures — yet the kernel admits it without sandboxing, software fault isolation, or a dynamic monitor. The entire trust decision rests on a single static analysis: the **eBPF verifier**, invoked from `bpf_check()` in `kernel/bpf/verifier.c` [2].

The verifier must answer a deceptively simple question: *is this program safe?* Its answer must be **sound** — no unsafe program may be accepted — while remaining **precise** enough that legitimate programs are not rejected and **fast** enough to run at load time. These three requirements are in deep tension. The set of properties demanded — memory safety, termination, absence of uninitialized reads, correct helper usage, single-lock discipline — is rich enough that the underlying verification problem touches undecidability, and the engineering response is a carefully layered approximate analysis.

This thesis makes three contributions. First, it presents a coherent formal account of the verifier as an **abstract interpreter** [8] over a product domain of scalar values, pointer types, and memory regions, making explicit the Galois connections and abstract operators that are implicit in the kernel source. Second, it analyzes the **state-pruning algorithm** — the mechanism that keeps path exploration feasible — and identifies the precise invariant (state dominance at prune points) on which its soundness rests. Third, it synthesizes the empirical and formal-verification literature into a critical evaluation of what the verifier guarantees today, where it has failed, and what remains provably out of reach.

Verifier bugs are kernel-privilege bugs: the subsystem's history is punctuated by critical CVEs exploited for container escapes and local privilege escalation [3][6]. Understanding the verifier is therefore understanding the security boundary of modern Linux.

## 2. Background

### 2.1 eBPF in brief

eBPF programs are loadable bytecode executed by an in-kernel interpreter or just-in-time compiler, attached to hooks spanning networking (XDP, tc, socket filters), tracing (kprobes, tracepoints, fentry), security (LSM), and scheduling. A program consists of up to one million instructions [2], eleven 64-bit registers (`r0`–`r10`, with `r10` the read-only frame pointer), a 512-byte stack, and access to typed memory regions: packet buffers, map values, context objects, and kernel memory (for privileged programs only). Interaction with the kernel happens exclusively through **helper functions** (`bpf_map_lookup_elem`, `bpf_probe_read_kernel`, …), each guarded by a function prototype declaring argument and return types.

### 2.2 The verification problem

The safety properties enforced by the verifier include:

- **Termination**: every accepted program halts; loops must be provably bounded.
- **Memory safety**: all loads and stores target initialized, in-bounds, type-correct memory.
- **Type safety**: registers carry abstract types (scalar, pointer-to-context, pointer-to-map-value, …) and operations must respect them.
- **Initialization**: no read of uninitialized registers or stack slots.
- **Helper discipline**: calls use permitted helpers with correctly typed arguments; return values are checked.
- **Lock discipline**: at most one spinlock held; locks released before exit.
- **Complexity bound**: verification itself must complete within `BPF_COMPLEXITY_LIMIT_INSNS` (1,000,000) simulated instructions [2].

> **Theorem:** (Soundness requirement). Let ⟦P⟧ be the concrete semantics of an eBPF program P and let V(P) ∈ {accept, reject} be the verifier's verdict. Soundness requires: if V(P) = accept, then every execution of P satisfies the safety policy. Precision would additionally require the converse for all safe programs; the verifier does not and cannot guarantee this.

### 2.3 Abstract interpretation

Abstract interpretation, in the Cousot–Cousot framework [8], replaces concrete program states with elements of an abstract lattice L connected to the concrete domain by a Galois connection (α, γ). Program operations become monotone **abstract operators** on L, and analysis computes a fixpoint (or a widened approximation) that over-approximates all concrete behaviors. The verifier instantiates this pattern with two cooperating passes: a *control-flow* pass that discovers the program's structure and a *symbolic-execution* pass that propagates abstract register and stack states along every path.

## 3. Methodology

### 3.1 Formal modeling approach

We model the verifier as an abstract interpreter V = (L, ⊥, ⊤, ⊔, ⊑, δ̂), where L is the product lattice of abstract register and stack states and δ̂ the abstract transfer function per opcode. Our method is threefold:

1. **Specification extraction.** We reconstruct the abstract domains and operators from the kernel implementation — `kernel/bpf/verifier.c` for state tracking and `kernel/bpf/tnum.c` for the tristate-number domain — and from the formal specifications developed by Vishwanathan et al. [1] and Bhat et al. [4].
2. **Soundness argument.** For each abstract operator we check the local soundness condition α ∘ f ⊆ f̂ ∘ α (equivalently, f(γ(x̂)) ⊆ γ(f̂(x̂))), then lift to whole-program soundness via the standard abstract-interpretation fixpoint theorem, accounting for the pruning optimization in §4.3.
3. **Empirical triangulation.** We cross-check the formal claims against the empirical record: the Linux Foundation security audit [6], documented verifier CVEs [3], and the measured precision of abstract operators in recent kernels [1].

### 3.2 Domains under study

The analysis tracks, per register, a `bpf_reg_state` combining a **type** (e.g., `SCALAR_VALUE`, `PTR_TO_CTX`, `PTR_TO_MAP_VALUE`, `PTR_TO_STACK`) with value information: signed/unsigned bounds (`smin_value`, `smax_value`, `umin_value`, `umax_value`), a 64-bit **tnum** (`var_off`: value + mask of unknown bits), and per-type offset and range metadata. Stack slots are tracked at byte granularity with liveness, spill, and initialization flags.

## 4. Deep Dive

### 4.1 Pass one: control-flow analysis and the bounded-loop theorem

The first pass builds the control-flow graph, rejects unreachable instructions, out-of-range jumps, and illegal back-edges. Historically, *all* back-edges were rejected for unprivileged programs; since Linux 5.3, **bounded loops** are permitted when the verifier can prove an exit condition becomes true. The bound is enforced structurally: the verifier detects loops, requires the loop body to be analyzable within the complexity budget, and simulates iteration explicitly.

> **Theorem:** (Bounded exploration). The verifier simulates at most `BPF_COMPLEXITY_LIMIT_INSNS` instructions. Any program whose path exploration exceeds this budget is rejected. Termination of the *verifier* is therefore trivial; termination of the *program* follows from the absence of unbounded back-edges in the accepted CFG fragment.

A subtle consequence: the complexity limit bounds *verification*, not execution — a loop with a runtime bound of 10⁹ iterations is rejected though it terminates. Dead-code elimination prunes unreachable blocks before exploration, easing budget pressure [2].

| Analysis phase | Artifact | Key check | Failure mode if wrong |
|---|---|---|---|
| CFG construction | Instruction DAG / bounded CFG | Reachability, jump targets, back-edge legality | Unreachable code hides unsafe paths |
| Scalar tracking | tnum + interval per register | Operator soundness | Verifier escape (CVE class) |
| Symbolic execution | `bpf_verifier_state` per path | Type and bounds at every access | Memory-safety violation |
| Pruning | Checkpointed states at prune points | State dominance (⊑) | Path incorrectly discarded → unsoundness |
| Helper checking | `bpf_func_proto` per program type | Arg/return type conformance | Privilege escalation via helpers |

### 4.2 Pass two: symbolic execution over abstract domains

The second pass performs depth-first symbolic execution. The verifier maintains a stack of `bpf_verifier_state` frames — one per deferred branch — each holding eleven register states and 64 stack-slot states. When a conditional jump is encountered, the current state is **copied**, branch conditions **refine** scalar bounds (e.g., `if r1 > 8` sets `umin_value = 9` on the taken branch and `umax_value = 8` on the fall-through), and exploration continues depth-first.

The heart of value tracking is the **tnum** (tristate number) domain [5]: each bit of a 64-bit value is known-0, known-1, or unknown (µ). Arithmetic operators are implemented bit-precisely over this representation in `tnum.c`, and the formal specification of Vishwanathan et al. [1] provides soundness and *optimality* proofs for the core operators — meaning the abstract result is the tightest sound approximation of the concrete operation. A portion of that work has been upstreamed into the kernel [1][2].

Precision matters enormously in practice. An overly conservative abstract operator rejects safe programs — the classic *false positive* that broke real-world BPF applications for years (notably, the old multiplication operator). The differential-synthesis framework of [1] automatically generates witness programs demonstrating precision differences between competing operator implementations, and has already produced an upstreamed, strictly more precise `bpf_mul`.

```python
# Conceptual model of branch refinement (simplified from check_cond_jmp_op)
def refine_on_branch(reg, op, imm, taken: bool):
    """Tighten abstract bounds using the branch predicate."""
    if op == BPF_JGT and taken:      # r > imm  =>  r >= imm + 1
        reg.umin = max(reg.umin, imm + 1)
        reg.var_off = tnum_and(reg.var_off, tnum_range(imm + 1, U64_MAX))
    elif op == BPF_JGT and not taken:  # r <= imm
        reg.umax = min(reg.umax, imm)
    # analogous refinements for JGE/JLT/JLE/JSGT/... and signed variants
```

```rust
// Tnum (tristate number): value bits + mask of unknown bits
struct Tnum { value: u64, mask: u64 }  // bit i unknown iff mask has bit i set

fn tnum_add(a: Tnum, b: Tnum) -> Tnum {
    // sound abstract addition: known bits propagate through carries
    let sm = a.mask.wrapping_add(b.mask);
    let sv = a.value.wrapping_add(b.value);
    let sigma = sm.wrapping_add(sv);
    let chi = sigma ^ sv;
    let mu = chi | a.mask | b.mask;
    Tnum { value: sv & !mu, mask: mu }  // [1]: optimal abstract operator
}
```

### 4.3 State pruning: the dominance invariant

Naive path enumeration is exponential in the number of branches. The verifier's answer is **pruning**: at designated *prune points* (typically after branches), the current abstract state is compared against previously checkpointed states at the same instruction. If the current state is *dominated* — every register and stack slot is at least as constrained (⊑ in the abstract lattice) as a previously explored state — exploration of the current path stops, because every continuation was already covered.

> **Theorem:** (Pruning soundness). Let σ₁ be the checkpointed state and σ₂ the current state at prune point p with σ₂ ⊑ σ₁. If exploration from σ₁ found no violation, then no continuation from σ₂ can exhibit a violation not already ruled out — provided the abstract transfer function is monotone and states capture *all* information the transfer function depends on.

That proviso is the crux. The state must include precision markings, lock state, reference counts, and the "was this register's value derived from a potentially out-of-bounds pointer" taints — *everything* downstream checks consult. Historically, pruning-related state comparisons have been a rich source of subtle bugs: any field omitted from the equivalence check (`states_equal` / `regs_exact` / `stacksafe`) is a field across which the dominance claim silently fails, and several historic verifier escapes trace to exactly this class of omission [3][6]. The `aligned_stack` and per-slot liveness bits exist precisely because coarse state comparisons were unsound.

### 4.4 Helper functions, maps, and type checking

Memory access in eBPF is mediated by two mechanisms: direct loads/stores (restricted to the stack, packet data within verified bounds, and map values) and helper calls. Each program type declares its allowed helpers via `bpf_func_proto` structures; `check_helper_call()` verifies:

1. The helper is permitted for this program type (`check_map_func_compat` further restricts map-type/helper combinations).
2. Each argument register's abstract type matches the prototype (e.g., `ARG_PTR_TO_MAP_VALUE` requires a verified in-bounds map-value pointer; `ARG_CONST_SIZE` requires a constant scalar).
3. The return type is recorded (`RET_PTR_TO_MAP_VALUE_OR_NULL` forces a null check before dereference).

Map operations receive dedicated type checking: `map_lookup_elem` returns a pointer whose valid range is the map's `value_size`; `map_update_elem` requires `BPF_ANY`/`BPF_NOEXIST` flags as constant scalars. The verifier additionally tracks **reference lifetimes** for acquired references (`bpf_sk_lookup`, `bpf_ringbuf_reserve`) and **spinlock** state, rejecting leaks and double-release. Callbacks (e.g., `bpf_loop`, map iteration callbacks) are verified as separate subprograms with their own states — function-by-function verification [2].

### 4.5 Spectre mitigations and the speculative verifier

Since 2019 the verifier also defends against Spectre: it performs a *speculative* verification pass that explores mispredicted paths, inserting `BPF_ST_NOSPEC` ( speculation barriers) or rewriting branches where a mispredicted path could leak kernel memory through a side channel. This effectively doubles the analysis — the verifier must be sound not only for architecturally executed paths but for transiently executed ones. The complexity budget is shared, and several CVEs in this era (e.g., CVE-2021-3490, an ALU bounds-tracking flaw exploitable for out-of-bounds speculation) arose at the intersection of value tracking and speculative analysis [3][6].

```tla+
------------------------------ MODULE VerifierCore ------------------------------
EXTENDS Integers, FiniteSets
CONSTANTS Regs, Instrs, MaxInsns
VARIABLES pc, regs, stack, explored, budget
(* Abstract state: per-register type x tnum x interval *)
TypeOK == pc \in 0..Len(Instrs) /\ budget \in 0..MaxInsns
Init == pc = 0 /\ budget = MaxInsns /\ explored = {}
(* Transfer: monotone abstract step; pruning skips dominated states *)
Step == \/ /\ budget > 0
           /\ budget' = budget - 1
           /\ pc' \in Successors(pc, regs)       \* branch refinement in regs'
           /\ explored' = explored \cup {<<pc, regs>>}
        \/ /\ \E s \in explored: Dominates(s, <<pc, regs>>)
           /\ UNCHANGED <<pc, regs, budget, explored>>  \* prune: sound by Theorem 4.3
Spec == Init /\ [][Step]_<<pc, regs, stack, explored, budget>>
Safety == \A e \in explored: CheckAccess(e)   \* every explored state passed checks
=================================================================================
```

## 5. Empirical Evaluation and Proofs

### 5.1 The soundness record: verifier escapes

The verifier's failure history is the strongest empirical evidence about its guarantees [6][3]:

- **CVE-2020-8835** — 32-bit bound tracking flaw; crafted ALU operations confused the verifier's 32/64-bit subregister reasoning, enabling out-of-bounds kernel access.
- **CVE-2021-3490** — the verifier failed to apply proper bounds to ALU operations in some paths, exploited in the wild for privilege escalation.
- **CVE-2022-23222** — pointer-arithmetic validation flaw permitting out-of-bounds memory access from crafted programs.
- **CVE-2017-16995** — sign-extension bug in the verifier's handling of 32-bit operations.
- **CVE-2026-53671 class** — the pattern recurs in reimplementations: PREVAIL's abstract transformer treated context writes as no-ops, approving unsafe programs [3], demonstrating that the *specification* of the abstract semantics, not just the C code, is the fragile artifact.

Each escape follows a common anatomy: an abstract operator or state-comparison routine that is *almost* sound — correct on all tested inputs but unsound on an adversarial corner of the abstract domain. This is precisely the failure mode that manual review misses and that motivated automated soundness checking [4].

### 5.2 The formal-verification counteroffensive

Three lines of research now attack verifier soundness directly:

1. **Mechanized operator verification.** Bhat et al. [4] translate the C code of the range-analysis pass into logical formulas and discharge soundness obligations with SMT solvers, on *every kernel commit* — turning verification into a continuous check that keeps pace with kernel development. Their framework pinpointed exactly where historic bugs were introduced and patched, including unacknowledged ones.
2. **Differential synthesis.** AGNI [1] gives a formal precision specification for abstract operators and uses SMT-based program synthesis to generate concrete witness programs exhibiting precision differences — validating that kernel patches to operators (like the new `bpf_mul`) are genuine improvements, not just refactors.
3. **Alternative verified verifiers.** PREVAIL [7] reimplements verification with the Zone abstract domain (tracking differences between register pairs) inside the Crab abstract-interpretation framework; CertrBPF [5] goes further, providing a Coq-mechanized end-to-end proof of a (simplified) BPF verifier and interpreter for microcontrollers; and Bromberger et al. translate eBPF to constrained Horn clauses for fully automatic bit-precise verification with Z3 [9].

### 5.3 Precision measurements

Soundness is only half the story; a verifier that rejects everything is sound and useless. Measurements reported in [1] and [2] show steady precision gains: bounded loops (5.3+), dead-code elimination, more precise `bpf_mul`, and refined branch-bound propagation have each measurably reduced false rejections on real programs (notably the Cilium and Prevail test corpora). The fundamental trade-off remains: every precision improvement enlarges the trusted abstract-operator surface, and every soundness fix risks rejecting previously accepted programs.

> **Theorem:** (No free lunch). For the verifier's language, *sound* ∧ *complete* ∧ *decidable* verification is impossible (reduction from the halting problem via bounded-but-unbounded loops). The verifier therefore chooses soundness, sacrificing completeness (rejecting some safe programs) and accepting a bounded, tunable analysis budget.

## 6. Limitations

The verifier's limitations are structural, not merely bugs awaiting fixes:

1. **Inherent incompleteness.** Undecidability forces rejection of safe programs; developers routinely restructure code to satisfy the verifier, and "verifier-friendly" has become a programming idiom with real costs.
2. **Complexity-budget fragility.** Large real-world programs (notably complex XDP datapaths) still hit `BPF_COMPLEXITY_LIMIT_INSNS`; the budget is global and shared with speculative analysis, making acceptance unpredictable across kernel versions.
3. **Helper-contract opacity.** Helper prototypes encode types but not *behavioral* contracts (e.g., which helpers may sleep, exact side effects); the verifier checks signatures, not semantics, leaving a gap between "well-typed call" and "safe call."
4. **JIT trust gap.** The verifier analyzes bytecode, but execution often goes through the JIT compiler; JIT correctness (addressed separately by Nelson et al. [2]) is outside the verifier's proof boundary.
5. **Speculative soundness is heuristic.** The Spectre mitigations approximate transient-execution semantics; the model of what CPUs may speculate is necessarily incomplete and evolves with microarchitecture.
6. **Proof maintenance.** As Bhat et al. observe [4], a one-time monolithic proof rots immediately; only *continuous*, commit-level verification keeps pace — and that infrastructure is still research-grade.
7. **State-space opacity.** When verification fails, diagnostics (`verbose` log) describe the failing check but not the abstract reasoning that led there, making precision bugs expensive to diagnose.

## 7. Conclusion

The eBPF verifier is a landmark artifact: a static analyzer, running in the kernel's most trusted context, that routinely decides the safety of adversarial bytecode in milliseconds. Its design — CFG analysis, abstract interpretation over tnums and intervals, exhaustive symbolic execution with dominance-based pruning, bounded-loop reasoning, and per-type helper contracts — represents the most successful large-scale deployment of abstract interpretation in systems software.

Yet the record is sobering. Soundness has failed repeatedly at exactly the points the theory predicts are fragile: abstract operators that are nearly but not quite sound, state comparisons that omit a field, speculative paths the model does not cover. The emerging consensus — mechanized, continuous, commit-level verification of the abstract operators [1][4], plus independently verified alternative verifiers [5][7] — treats the verifier not as a finished proof but as a living analysis whose soundness must be re-established as it evolves.

The deepest lesson is methodological. The verifier's bugs were never failures of effort; they were failures of *scale* — a 10,000-line abstract interpreter [2] whose soundness argument lives partly in code, partly in developers' heads, and nowhere in checkable form. Closing that gap, with machine-checked specifications of the abstract domains and their operators maintained alongside the C code, is the central open problem of eBPF safety. Until it is closed, every kernel release ships a new, unverified proof — and attackers keep reading the diff.
