# Hardware Memory Safety with CHERI Capabilities: The Morello Architecture, Capability Monotonicity, Compartmentalization, and Pointer Provenance

## Abstract

This thesis provides a systematic, evidence-grounded analysis of hardware-enforced memory safety through the CHERI capability model, anchored by Arm's Morello demonstrator — the first industrial-scale processor whose 60,000-line architectural specification carries machine-checked security proofs. Memory safety remains the dominant failure mode in systems software: Microsoft research reports that roughly 70% of vulnerabilities addressed by security updates each year stem from memory-safety defects. CHERI replaces integer pointers with hardware-protected capabilities carrying bounds, permissions, and integrity tags, subject to *capability monotonicity* — the invariant that derived capabilities never exceed the authority of their parents — and *provenance validity*. We develop a formal account of these properties, trace their realization in the Morello SoC and its Sail/Isabelle-verified instruction-set architecture, and examine scalable compartmentalization built on sealed capabilities and object types. Drawing on porting evidence from CheriBSD, CheriABI, PostgreSQL, and recent temporal-safety extensions, we quantify performance costs and residual gaps, concluding that hardware capabilities offer the most credible path to spatial memory safety at scale, while temporal safety and ecosystem adoption remain open challenges.

## 1 Introduction

Memory unsafety is the longest-running catastrophe in computer security: buffer overflows, use-after-free errors, and out-of-bounds accesses have driven most critical vulnerabilities for four decades. Microsoft's security research has repeatedly measured that approximately **70% of vulnerabilities** addressed through security updates each year remain memory-safety issues [1]. Software mitigations — stack canaries, ASLR, shadow stacks — are probabilistic or bypassable; safe languages like Rust eliminate whole bug classes, but the world's critical software is C and C++, and rewriting it is infeasible.

The **Capability Hardware Enhanced RISC Instructions** (CHERI) project — a SRI International / University of Cambridge collaboration begun around 2010 — proposes a different bargain: push the reference monitor *into the hardware*. Instead of plain-integer pointers, CHERI extends the ISA with architectural *capabilities*: unforgeable tokens of authority bundling an address with bounds, permissions, and an integrity tag. Every memory access is authorized against this metadata in hardware, making spatial memory safety *non-bypassable* rather than advisory [2].

Arm's **Morello** program translated this research into industrial practice: an experimental CHERI-extended, multicore, superscalar Armv8-A SoC demonstrator, built on the Neoverse N1 platform and delivered to industry partners for evaluation [3][4]. Its architectural specification — written in the Sail ISA description language, some 60,000 lines — carries machine-checked proofs of fundamental security properties in Isabelle, making Morello the first industrial-scale processor with mathematically proven architectural security properties [3][5].

This thesis makes three contributions:

1. A precise account of the CHERI capability model, centered on the twin pillars of **capability monotonicity** and **pointer provenance**, and their formal treatment.
2. A technical analysis of how Morello realizes these properties in silicon — including the compressed-capability encoding and the role of sealed capabilities and object types in **compartmentalization**.
3. A critical evaluation of the empirical evidence: porting studies (CheriBSD, PostgreSQL, WebKit), performance measurements, and recent work on temporal safety, followed by an honest accounting of limitations.

## 2 Background and Related Work

### 2.1 Capabilities: a long lineage

Hardware capabilities are not new. The idea traces to Dennis and Van Horn's 1966 programming semantics for multiprogrammed computation, and to systems such as **HYDRA**, the **CAP** computer, the MIT **M-Machine**, and **EROS**. In each, a capability is an unforgeable reference conferring authority: to dereference is to be authorized. What distinguishes CHERI is *intentional compatibility*: unlike prior capability systems that demanded wholesale redesign, CHERI's hybrid capability model maps conventional C pointers onto capabilities, allowing existing C and C++ code to be recompiled with fine-grained protection largely unchanged [2][10].

### 2.2 Fat pointers and software enforcement

Software approaches encode bounds alongside pointers — the "fat pointer" family (**CCured**, **Cyclone**, SoftBound) — or retrofit provenance tracking into compilers. Cerberus, an executable formal semantics for C, demonstrated two coherent provenance models, validated against GCC torture tests, KCC, and Csmith suites — treating the CHERI port of FreeBSD as the reference implementation that *traps on exactly the violations* its semantics deems undefined behavior [8].

### 2.3 The CHERI program and Morello

CHERI has progressed through successive research architectures (CHERI-MIPS, CHERI-RISC-V) and ISA versions, with the *Morello* architecture representing its full-scale integration into Armv8-A [2]. Complementary designs extend the model in other directions: **CHERIoT** targets embedded microcontrollers with a verified compartmentalization model and RTOS [11]; **CAPSTONE** proposes revocation trees for efficient temporal safety [12]; **FRESCO** adds complete, scalable temporal safety to CHERI application processors [13]; and **Griotte** provides a verified compartmentalization framework via logical relations in Iris [14].

Related hardware mechanisms — Intel CET, Arm Pointer Authentication, and Arm Memory Tagging Extension — offer only *probabilistic* or *partial* protections; none enforces complete spatial safety deterministically [5].

## 3 Methodology

This thesis synthesizes the published experiments of the CHERI research program and its industrial partners through a unified analytical lens.

**Threat model.** We consider an attacker who controls some inputs to a program (network data, files, IPC) and can trigger memory-corruption primitives in memory-unsafe C/C++ code. The attacker cannot fabricate hardware capabilities: the tag mechanism (Section 4.1) guarantees integrity. Side-channel attacks and physical tampering are out of scope [5].

**Analytical framework.** We proceed in three layers:

1. *Architectural*: we formalize capability monotonicity and provenance as invariants over an abstract capability machine, following the operational style of the Sail ISA models [5][9].
2. *Mechanism*: we dissect the concrete realizations — tagged memory, compressed capabilities, sealed capabilities and object types — and their security consequences.
3. *Empirical*: we synthesize published porting and performance evidence (CheriBSD, CheriABI, PostgreSQL, WebKit, CRuby, SPEC CPU) and formal-verification results (Isabelle proofs of the Morello ISA, HOL4 proofs of CHERI Concentrate decode logic).

**Verification posture.** We treat claims as established only when supported by the primary sources. Capability monotonicity for the Morello ISA is *proved*, not merely asserted, in Isabelle [5]; CHERI Concentrate's decode logic carries a HOL4 machine-checked proof [6]. Performance figures are quoted from the originating papers with their benchmark suites.

## 4 Hardware Memory Safety via Capabilities: A Deep Dive

### 4.1 Capability Anatomy: Tags, Bounds, and Permissions

A CHERI capability is a fat pointer with hardware teeth. On a 64-bit platform it occupies **128 bits in registers and memory**, plus one additional *validity tag bit* stored separately so that non-capability-aware instructions cannot tamper with it [2][13]. Architecturally, a capability comprises:

- **Address (cursor):** the pointer value used for dereference, equal to *base + offset*.
- **Bounds:** the range of bytes within which the address may be dereferenced — a lower *base* and upper *limit*.
- **Permissions:** a bitmask of permitted operations (load, store, execute, sealing, system-register access).
- **Object type (otype):** indicates whether the capability is *sealed* (immutable, opaque) and under which type; only the matching unsealing authority can open it.
- **Tag:** a single bit protecting capability validity — the integrity/provenance anchor. Preserved by valid capability-aware instructions; *cleared* by unauthorized manipulation or by writing a capability through ordinary data stores [2][13].

The tag is the linchpin: because ordinary stores clear tags, an attacker overwriting a pointer in memory produces *data*, not a capability — any subsequent dereference traps. Pointer integrity is enforced structurally, not probabilistically.

The **Default Data Capability (DDC)** authorizes legacy loads/stores in hybrid code and the **Program Counter Capability (PCC)** governs instruction fetch — control-flow integrity falls out naturally, since jumps must target an execute-permissioned capability with covering bounds [2].

```python
# Abstract CHERI capability model (Sail-style).

from dataclasses import dataclass

@dataclass(frozen=True)
class Capability:
    tag: bool        # validity / integrity bit
    base: int        # lower bound
    top: int         # upper bound (exclusive)
    cursor: int      # current address
    perms: int       # permission bitmask
    sealed: bool     # sealed capabilities are immutable/opaque

PERM_LOAD, PERM_STORE, PERM_EXEC = 0x1, 0x2, 0x4

def check_deref(cap: Capability, op: int) -> bool:
    """Hardware dereference authorization, evaluated atomically."""
    if not cap.tag:
        raise CapabilityFault("tag violation: forged capability")
    if cap.sealed:
        raise CapabilityFault("sealed capability cannot be dereferenced")
    if not (cap.perms & op):
        raise CapabilityFault("permission violation")
    if not (cap.base <= cap.cursor < cap.top):
        raise CapabilityFault("bounds violation")
    return True
```

The real Morello pipeline evaluates these checks in parallel with address translation, with the ISA specification proving no instruction path bypasses them [5].

### 4.2 Capability Monotonicity and Pointer Provenance

The two semantic invariants that give CHERI its strength are **provenance validity** and **monotonicity**:

- *Provenance:* every valid capability is derived from a prior valid capability through an authorized manipulation. Capabilities cannot be conjured from integers, ambient authority, or thin air.
- *Monotonicity:* derivation can only *narrow* authority. A child capability's bounds are a subset of its parent's; its permissions are a subset of its parent's. Rights never increase as capabilities flow through a program.

> **Theorem (Capability Monotonicity).** *For any execution trace of a CHERI machine, the authority held by a compartment at any step is a subset of the authority derivable from the capabilities it initially held, except via explicitly authorized sealing/unsealing transitions. Consequently, no sequence of capability manipulations can grant access to memory outside the transitive closure of the initial capability set.* [2][9]

This *reachability* property makes CHERI's guarantees compositional: auditing a compartment means auditing the capabilities it was granted. It is mechanized — Nienhuis et al. proved monotonicity for the Morello ISA in Isabelle [5] — and the ISA specification defines these properties as what distinguishes capabilities from mere fat pointers [2].

Monotonicity's disciplined exception is **sealing**: sealed capabilities are immutable and opaque, inspectable only by the holder of matching unsealing authority (`CSeal`/`CUnseal` plus object-type capabilities). This introduces *limited, controlled non-monotonicity* — mediated by explicit hardware gates, never by pointer arithmetic [2][13].

The Haskell sketch below captures the monotonicity discipline as a pure model, where derivation is the only constructor for child capabilities:

```haskell
-- Monotonic capability derivation.

data Perm = Load | Store | Exec deriving (Eq, Show)
data Cap = Cap { base :: Int, top :: Int
               , perms :: [Perm], sealed :: Bool }

-- | Derive a child capability: bounds and permissions may only shrink.
derive :: Cap -> Int -> Int -> [Perm] -> Maybe Cap
derive parent b t ps
  | sealed parent          = Nothing
  | b < base parent        = Nothing   -- cannot widen below
  | t > top parent         = Nothing   -- cannot widen above
  | not (all (`elem` perms parent) ps) = Nothing  -- cannot add perms
  | otherwise              = Just (Cap b t ps False)
```

*Pointer provenance* connects this hardware story to language semantics. The Cerberus project showed that C's pointer semantics can be made coherent by associating a provenance (allocation identity) with every pointer and integer value, with undefined behavior on provenance-violating accesses [8]. CHERI hardware *enforces* a compatible provenance discipline at runtime: casting an integer to a pointer succeeds only when the integer is `intptr_t`-derived from a live capability with covering bounds — a lesson VM implementers learned porting CRuby, where `size_t`-based pointer-arithmetic idioms had to be rewritten [15].

### 4.3 Sealed Capabilities, Object Types, and Compartmentalization

Capabilities protect *memory*; **compartmentalization** protects *software structure*. CHERI enables both with the same primitives. A compartment is a protection domain whose code and data are reachable only through the capabilities it holds. Cross-compartment calls use **sealed capabilities**: a callee's entry point is exposed as a capability sealed with a specific object type, and invoking it performs a controlled domain transition in which the caller's state is encapsulated [14].

This yields *scalable* compartmentalization — no address-space switches, no kernel mediation, non-bypassable enforcement. CHERIoT demonstrates the model at the embedded extreme: compartments hold only their own code and private memory, communicating through export tables and opaque imports via a privileged switcher [11]. Griotte goes further, using Iris logical relations to *prove* local-state encapsulation for compartments linked against arbitrary low-level code [14].

These calling conventions enforce **local state encapsulation**: when A calls B through a sealed entry capability, B cannot reach A's stack or private data except through explicitly passed capabilities. A buffer overflow in one compartment cannot corrupt another's memory — the attacker's derived capabilities are bounded by monotonicity to the compromised compartment's grants [11][14].

```rust
// Sealed entry capability: invokable, never inspectable.

/// Opaque handle to a sealed entry capability; otype is the
/// unforgeable "key" authorizing the domain transition.
pub struct SealedEntry {
    otype: u64,      // capability object type (hardware-sealed)
    sealed: bool,    // tag + sealed bit enforced by hardware
}

impl SealedEntry {
    /// Cross-compartment call: the ONLY operation the hardware
    /// permits on a sealed entry capability. Arguments cross the
    /// boundary as explicitly granted (monotonic) capabilities.
    pub fn invoke(&self, args: &[u8]) -> Result<Vec<u8>, CompartmentFault> {
        if !self.sealed {
            return Err(CompartmentFault::Unsealed);
        }
        // Hardware atomically: unseal, switch domain, encapsulate caller state.
        domain_transition(self.otype, args)
    }
}
```

### 4.4 CHERI Concentrate: Practical Compressed Capabilities

A naive capability doubles pointer size (128 bits plus tag versus 64-bit pointers), threatening cache footprint and memory bandwidth. **CHERI Concentrate** solves this with a compressed encoding that represents bounds in a floating-point-like format: an internal exponent, compressed base, and compressed top, with the cursor address stored at full precision [6]. Most allocations' bounds are *representable* with limited precision relative to the pointer value, and the encoding adds no load-to-use delay on pointer arithmetic — the hot path.

CHERI Concentrate achieves a **50–75% reduction in L2 misses** for compiled C benchmarks versus the uncompressed 256-bit format, with a **HOL4 machine-checked proof** of the decode and pointer-modify logic [6] — the difference between a research curiosity and a deployable technology.

| Format | In-memory size | Cache impact | Pipeline cost |
|---|---|---|---|
| 256-bit uncompressed | 32 B + tag | baseline (high) | none |
| 128-bit CHERI Concentrate | 16 B + tag | −50–75% L2 misses [6] | zero added load-to-use delay [6] |
| 64-bit (32-bit address space) | 8 B + tag | minimal | none |

## 5 Empirical Results and Formal Proofs

### 5.1 The Morello verification milestone

The Morello ISA specification — Sail, elaborated from Arm's ASL, roughly 60,000 lines — was subjected to machine-checked Isabelle proofs of fundamental security properties: capability monotonicity, no instruction bypassing capability checks, and invariant-preserving exceptions. Test suites *generated from the specification* aided hardware development and QEMU bring-up [3][5]. As Peter Sewell noted, a specification flaw "could let attackers side-step the intended CHERI protection" — this proof effort was the first to rule out such flaws at industrial scale [3].

> **Theorem (Morello ISA Security).** *The Sail specification of the Morello ISA satisfies capability monotonicity and complete mediation: every memory access and control transfer is authorized by a valid, unsealed capability with sufficient permissions and covering bounds. Machine-checked in Isabelle; no specification flaw permitting bypass was found.* [3][5]

Subsequent work extended verification down to the microarchitecture (Bauereiss et al., IEEE S&P 2022) and to the CHERIoT-Ibex embedded core via a Sail-to-SystemVerilog flow with assume-guarantee and *k*-induction reasoning [16].

### 5.2 Porting evidence: real software, real safety

The strongest evidence for CHERI is not a proof but a port. **CheriABI** adapted the full FreeBSD userspace — kernel, C library, dynamic linker — to capability-clean C, enforcing valid pointer provenance throughout the POSIX runtime (ASPLOS 2019 Best Paper) [7]. Building on this, researchers demonstrated **complete spatial and referential memory safety** for an enterprise workload — FreeBSD running PostgreSQL — with acceptable overhead versus the pre-CHERI baseline and software-only approaches [10].

Further data points accumulate:

| Workload / Study | Finding |
|---|---|
| PostgreSQL on CheriBSD [10] | Full spatial + referential safety; acceptable overhead vs. baseline |
| CheriABI / FreeBSD userspace [7] | POSIX environment ported; provenance enforced at ABI level |
| SPEC CPU, SQLite, PostgreSQL, gRPC on FRESCO [13] | Complete temporal safety added; efficacy on real benchmarks |
| CRuby VM port [15] | Pointer-arithmetic idioms identified and fixed; lessons for VM implementers |
| WebKit [10] | Large browser engine ported to capabilities |
| Automotive IDS on Morello board [17] | Spoofed-packet and rule-manipulation attacks blocked by CHERI protections |

The Morello boards themselves — multicore SoCs delivered to industry and academic partners from 2022 — enabled evaluation of software performance, microarchitectural choices, compartmentalization strategies, and source compatibility at a scale no FPGA prototype permitted [4].

### 5.3 The 70% argument, quantified

If ~70% of patched vulnerabilities are memory-safety issues [1], and CHERI deterministically eliminates the spatial subset plus pointer forgery, the expected vulnerability reduction is substantial — modulo the caveats of Section 6. Notably, the bugs found during the CheriABI port were disproportionately the latent memory-safety defects CHERI is designed to trap [7].

## 6 Limitations and Future Work

**Temporal safety is incomplete.** CHERI's core model provides *spatial* safety; use-after-free remains possible when a capability outlives its allocation. Mitigations exist — revocation via sweeping and quarantine, **CHERIvoke**, and newer designs such as **CAPSTONE**'s revocation trees [12] and **FRESCO**'s complete temporal safety [13] — but they add complexity and cost.

**Hybrid code and the DDC.** For compatibility, CHERI supports hybrid compilation where legacy integer pointers are authorized by the Default Data Capability. This preserves binary compatibility but dilutes guarantees wherever hybrid code runs; the security argument applies fully only to *pure-capability* code [2].

**Side channels and physical attacks.** The Morello verification covers the *architectural* specification; microarchitectural side channels (timing, speculation) and physical probing are separate concerns. Extensions exploring safe speculation exist but are early [13].

**Ecosystem and ABI churn.** Adopting CHERI requires recompilation, ABI changes (128-bit pointers alter struct layouts), and porting effort — the CRuby experience shows even idiomatic C contains provenance-hostile patterns [15]; compilers, linkers, and loaders must be capability-aware and correct.

**Compartmentalization policy.** Hardware provides the mechanism; the *policy* — which compartments exist, what they may share — remains a software design problem. Verified frameworks like Griotte [14] are promising but nascent.

Future work converges on: complete temporal safety with bounded overhead, verified compartmentalization policies for real systems, automated porting and provenance-repair tooling, and standardization of the CHERI extensions for mainstream ISAs.

## 7 Conclusion

CHERI reframes memory safety from a software aspiration to a hardware guarantee. Its two invariants — **capability monotonicity** and **provenance validity** — are simple enough to state, strong enough to be proved, and practical enough to have been realized in the Morello demonstrator: an industrial-scale Armv8-A SoC whose 60,000-line Sail specification carries machine-checked security proofs in Isabelle. Compressed capabilities make the model affordable; sealed capabilities and object types make compartmentalization scalable; a decade of porting evidence — from FreeBSD and PostgreSQL to WebKit and CRuby — shows it works on real software at acceptable cost.

The remaining gaps are real but bounded: temporal safety needs its FRESCO moment to become routine, the ecosystem must absorb ABI change, and policies must be built atop verified mechanisms. Against a threat landscape where most patched vulnerabilities remain memory-safety defects, hardware capabilities are the most credible path yet demonstrated to eliminating entire vulnerability classes *by construction*.
