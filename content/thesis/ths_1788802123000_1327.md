# Trusted I/O for Confidential Virtual Machines: PCIe TEE-IO and TDISP Device Attestation, SPDM 1.2 Measurements, IDE Link Encryption, and Secure Device Assignment under AMD SEV-SNP and Intel TDX

## Abstract

Confidential virtual machines (CVMs) under AMD SEV-SNP and Intel TDX encrypt guest memory and exclude the hypervisor from the trust boundary, yet the I/O path has remained the weakest link: devices perform DMA as untrusted bus masters, forcing guests through shared bounce buffers that degrade performance and expose data in transit. The PCI-SIG TEE-IO framework closes this gap through a layered protocol stack: the DMTF SPDM 1.2 protocol for device identity, authentication, and measurement attestation; the TDISP ECN for binding Trusted Device Interfaces to trusted execution environments; and PCIe IDE for AES-GCM per-TLP link encryption. This thesis formalizes the TEE-IO attestation and key-exchange composition, analyzes TDISP interface state machines and lockable SPDM sessions, and evaluates how AMD SEV-TIO and Intel TDX-Connect operationalize secure device assignment — permitting attested devices to DMA directly into guest-private memory. We present a compositional security argument, a TLA+ model of the TDI lifecycle, and a performance analysis of bounce-buffer elimination, followed by residual limitations including the T-bit destination ambiguity and link-layer side channels.

## 1 Introduction

Confidential computing rests on a single architectural bet: the hypervisor, firmware, and cloud operator can be removed from the trusted computing base (TCB) of a virtual machine without sacrificing the utility of virtualization. AMD SEV-SNP achieves this through reverse-map table (RMP) integrity checks on every guest page assignment, and Intel TDX through a hardware-attested TDX module managing trust domains (TDs) [6]. Attestation reports — signed by AMD's Versioned Chip Endorsement Key (VCEK) or Intel's TD-quoting infrastructure — let a guest owner verify the launch measurement before provisioning secrets [7]. Yet even with memory fully encrypted and integrity-protected, the moment a CVM performs I/O, it must trust something outside the TEE: the PCIe device, the IOMMU configuration, and the fabric between them.

The classical response is *bounce buffering*. Because an untrusted device must never observe or modify guest-private memory, the IOMMU (with SEV-SNP's RMP checks on the DMA path) blocks device access to private pages; the guest instead copies data through shared, unencrypted pages [5]. This works but imposes two costs: (i) doubled memory traffic and CPU copy overhead on every I/O, and (ii) plaintext exposure of device data in shared memory, visible to the hypervisor and requiring application-level encryption for anything sensitive. As GPU- and NIC-heavy confidential workloads — large language model inference, confidential HPC, encrypted storage pipelines — scale, these costs become prohibitive [6].

PCI-SIG's TEE-IO initiative provides the standards-based answer: extend the trust boundary across the PCIe link to the device itself. The architecture decomposes into three interlocking protocols [2][3]:

1. **SPDM 1.2** (DMTF DSP0274): a wire protocol by which a requester (the host TEE) authenticates a device responder, negotiates cryptographic algorithms, establishes session keys, and retrieves signed firmware measurements [4].
2. **TDISP** (TEE Device Interface Security Protocol): a PCI-SIG ECN defining how a TEE Security Manager (TSM) in the host and a Device Security Manager (DSM) in the device negotiate, attest, lock, and bind *Trusted Device Interfaces* (TDIs) to trusted VMs [1].
3. **PCIe IDE** (Integrity and Data Encryption): per-TLP AES-GCM encryption and integrity protection of the PCIe transaction layer, organized into selective IDE streams bound to TDIs [2].

AMD productizes this as **SEV-TIO** (Trusted I/O), and Intel as **TDX-Connect** — both built directly on TDISP, with device participation recorded in the CVM attestation report [5][6].

This thesis makes three contributions. First, a precise specification-level reconstruction of the SPDM 1.2 → TDISP → IDE protocol composition, including lockable SPDM sessions, the TDI state machine (CONFIG_UNLOCK/CONFIG_LOCK), and IDE stream binding semantics. Second, a formal security argument for compositional attestation soundness, supported by a TLA+ model of the TDI lifecycle. Third, an evaluation of secure device assignment under SEV-SNP and TDX, quantifying bounce-buffer elimination and delineating the residual attack surface.

## 2 Background

### 2.1 Confidential VM architectures

**AMD SEV-SNP.** Secure Encrypted Virtualization with Secure Nested Paging adds hardware-enforced memory integrity to encrypted VMs. A Reverse Map Table tracks each system physical page's ownership; the RMP is consulted not only by CPUs but by devices performing DMA through the IOMMU. A device DMA to a guest-private page (RMP *Assigned*=1) is blocked; only hypervisor pages and guest-shared (C-bit clear) pages are reachable [5]. This mechanism both *forces* bounce buffering for untrusted devices and, under SEV-TIO, *permits* direct DMA once a device is attested and bound into the guest's trust domain [5].

**Intel TDX.** Trust Domain Extensions isolate TDs via the TDX module (a CPU-attested software TCB) and integrity-protected private memory. TD attestation is produced through TD-quoting, and **TDX-Connect** extends the TD boundary to PCIe devices using the same TDISP foundation, with the TEE-I/O device guide specifying TLP filtering rules for TDIs [1][6].

### 2.2 PCIe security primitives

Before TEE-IO, PCIe already offered several building blocks [2]:

- **DOE (Data Object Exchange)**: a mailbox mechanism carrying structured data objects — the transport for SPDM messages to PCIe endpoints.
- **CMA (Component Measurement and Authentication)**: an earlier ECN layering SPDM over DOE; TDISP supersedes it for the TEE use case.
- **IDE (Integrity and Data Encryption)**: a link-security ECN applying AES-GCM to transaction-layer packets, organized into *streams* with per-stream keys and per-TLP protection policies under *selective IDE* [2].

### 2.3 SPDM 1.2 in brief

The DMTF Security Protocol and Data Model (SPDM, DSP0274) defines a requester/responder protocol with version negotiation, capability discovery, algorithm negotiation, certificate-chain retrieval, challenge-response authentication, key exchange (certificate- or PSK-based, with optional mutual authentication), measurement collection, and session management [4]. Version 1.2 adds secured-message formats, key update, heartbeat, and — critically for TEE-IO — *lockable* session semantics that TDISP relies on to bind a session to a device interface. Measurements are returned as ordered blocks with a DMTF-defined format: each block carries an index, a measurement specification, and a value typed by `DMTFSpecMeasurementValueType` (immutable ROM, mutable firmware, hardware straps, firmware configuration, measurement manifest, device mode at index `0xFE`, etc.), and the entire collection can be signed by the responder's attestation key [4].

### 2.4 The TEE-IO trust model

TEE-IO introduces two software actors and one hardware abstraction [1][2]:

- **TSM (TEE Security Manager)**: host-side software (typically in the TDX module or SEV-SNP guest/hypervisor enlightenment layer) that drives attestation and key programming.
- **DSM (Device Security Manager)**: device-side firmware/logic that answers as the SPDM responder and enforces interface policy.
- **TDI (Trusted Device Interface)**: the unit of trust assignment — typically a PCIe function or a sub-function partition whose configuration can be measured, locked, and bound to a specific TVM (trusted VM).

The security goal is *mutual, measured binding*: the TSM verifies device identity and firmware before programming IDE keys and attaching the TDI; the DSM verifies it is talking to an authorized TSM (via lockable sessions and access control) before exposing the TDI's trusted state.

## 3 Methodology

Our method is *specification-driven formalization with empirical grounding*:

1. **Primary-source reconstruction.** We derive the protocol description from the PCI-SIG TDISP 1.0 and IDE 1.0 ECNs (via Intel's TEE-IO Device Guide [1] and PCI-SIG's overviews [2][3]), DMTF SPDM 1.2 (DSP0274) [4], and vendor SEV-SNP/TDX documentation [5][6][7].
2. **Threat modeling.** We assume the standard CVM adversary: a malicious hypervisor/VMM controlling scheduling, IOMMU tables (subject to hardware RMP/TDX checks), and all plaintext PCIe traffic; malicious peer devices; and sub-decapsulation physical attackers [5][6]. Device DSM firmware and its attestation key are trusted *only after* successful measurement verification.
3. **Formal modeling.** We encode the TDI lifecycle as a TLA+ state machine (§5) and state a composition theorem for attestation soundness with a proof sketch.
4. **Empirical grounding.** We summarize published CVM I/O overhead measurements [6] and model bounce-buffer elimination.

**Notation.** *TVM* denotes a trusted VM (a TD under TDX, an SNP guest under SEV-SNP); *TDI* a trusted device interface; *T=1* the IDE TLP marking bit indicating TEE origin; *Lₐ* the attestation log (measurement record); *K_IDE* an IDE stream key; *σ* an SPDM signature.

## 4 Deep Dive

### 4.1 SPDM 1.2: the attestation and session substrate

SPDM 1.2 structures trust establishment as a strict message choreography over DOE [4]:

| Phase | Key messages | Purpose |
|---|---|---|
| Version & capability | `GET_VERSION`, `GET_CAPABILITIES` | Negotiate SPDM version; discover cert, challenge, measurement, key-exchange capabilities |
| Algorithms | `NEGOTIATE_ALGORITHMS` | Agree on hash, asymmetric, AEAD, DHE suites |
| Identity | `GET_DIGESTS`, `GET_CERTIFICATE` | Retrieve certificate chain(s); slot-based, up to 8 |
| Authentication | `CHALLENGE` / `CHALLENGE_AUTH` | Freshness-bound proof of private-key possession |
| Measurements | `GET_MEASUREMENTS` | Retrieve signed measurement blocks (DMTF format) |
| Session | `KEY_EXCHANGE` / `PSK_EXCHANGE` | Establish session keys; optional mutual auth, heartbeat, key update |

**Measurements.** `GET_MEASUREMENTS` returns a `MeasurementRecord` of ordered blocks. Each block carries an *index* (0x01–0xEF device-defined; 0xFD manifest; 0xFE device mode), a *measurement specification* bit, a size, and the measurement value in DMTF format — typed as immutable ROM, mutable firmware, hardware configuration, firmware configuration, manifest, or device mode, in either digest or raw-bitstream representation [4]. With a signature requested, the responder signs the transcript including the record; `Param2` content-changed bits expose runtime measurement drift. This signed record is the evidentiary basis for the TSM's trust decision [1].

**Sessions and lockability.** `KEY_EXCHANGE` derives session keys via (EC)DHE with optional mutual authentication; all subsequent traffic uses SPDM *secured messages* (AEAD-protected), with `KEY_UPDATE` providing forward secrecy and `HEARTBEAT` liveness. TDISP's requirement is the **lockable SPDM session**: the TSM binds a session to a specific TDI so interface-management commands are cryptographically tied to that interface and cannot be replayed against another — defeating cross-function confused-deputy attacks by a malicious VMM [1].

```python
# Pseudocode: verifying an SPDM 1.2 measurement chain (per DSP0274)
def verify_spdm_measurements(cert_chain, measurements_resp, transcript):
    leaf = validate_chain(cert_chain)          # X.509 path to provisioned root
    assert measurements_resp.param2.slot_id == leaf.slot
    payload = transcript + measurements_resp.measurement_record
    assert ecdsa_verify(leaf.pubkey,           # CHALLENGE_AUTH-style signature
                        measurements_resp.signature, payload)
    for block in measurements_resp.blocks:     # DMTF measurement block format
        assert block.spec == DMTF_SPEC
        t = block.value_type                   # DMTFSpecMeasurementValueType
        if t == IMMUTABLE_ROM or t == MUTABLE_FW:
            assert block.digest in golden_values # compare against reference manifest
    return True  # device identity + firmware state authenticated
```

### 4.2 TDISP: binding interfaces to trust domains

TDISP is the control plane of TEE-IO. Its actors — the host **TSM** and device **DSM** — execute a lifecycle over each TDI [1][2]:

1. **Discovery & attestation.** The TSM discovers TDISP-capable TDIs (via DOE/CMA/SPDM), performs the SPDM 1.2 handshake of §4.1 against the DSM, and verifies device identity and firmware measurements. Only devices whose measurements match the TVM owner's policy proceed.
2. **Interface report & lock.** The TSM requests a TDI report (configuration, bound IDE stream, supported TLP rules) and issues `LOCK_INTERFACE_REQUEST`, transitioning the TDI from `CONFIG_UNLOCK` to `CONFIG_LOCK`. In `CONFIG_LOCK` the device drains pending non-TEE traffic and freezes security-relevant configuration (BARs, stream assignment, TLP filter rules) so attested state cannot drift after verification [1].
3. **IDE key programming.** The TSM programs IDE stream keys into both the host root port and the device, binding the TDI's *default stream* (or a peer-to-peer stream via `BIND_P2P_STREAM_REQUEST` for device-to-device paths through switches/retimers) [1].
4. **Attach to TVM.** The TDI is attached to the target TVM; the DSM enforces access control so only that TVM's T=1 traffic on the bound IDE stream reaches the trusted interface. Detach reverses the process with explicit state scrubbing.

> **Theorem: (Attested binding soundness).** *If (i) the SPDM session between TSM and DSM is lockable and bound to TDI τ, (ii) the measurement log Lₐ verified against the TVM policy implies firmware f is in the allowed set F, (iii) τ transitions to CONFIG_LOCK only after Lₐ verification, and (iv) the IDE key K_IDE(τ) is known only to the TSM-side port and τ's DSM, then any DMA issued by τ into TVM memory is integrity-equivalent to DMA issued by the TVM's own vCPU.*

*Proof sketch.* By (i), all TDISP commands affecting τ are authenticated and non-transferable across TDIs, eliminating cross-function confused-deputy attacks. By (ii)–(iii), the locked configuration — BARs, stream binding, filter rules — is exactly the measured configuration, so the device logic handling τ is the attested firmware f ∈ F. By (iv) with IDE's AES-GCM per-TLP protection (§4.3), TLPs on the wire are authenticated end-to-end; a malicious switch or the VMM cannot forge, replay, or redirect them without detection. Hence the only entity capable of producing valid τ-originated DMA is firmware f executing the locked configuration — the same trust basis as the TVM's measured launch. ∎

The **T-bit** deserves special attention. IDE TLPs carry a T flag marking origin within a TEE. Intel's TEE-IO device guide formalizes TLP acceptance rules per TDI: a *bound IDE stream* (the default stream programmed at lock time) with T=1 constitutes a *TEE-TLP*; everything else — plaintext TLPs, non-bound streams, or bound-stream TLPs with T=0 — is a *non-TEE-TLP* subject to filtering [1]. Critically, the T bit attests *origin*, not *destination*: nothing in the TLP marks whether its target lies inside a TEE. Consequently a device must not serve TEE and non-TEE traffic from a common cache unless cache lines carry a private/shared attribute — a subtle but load-bearing requirement for multi-tenant accelerators [1].

### 4.3 IDE: per-TLP link encryption

IDE applies AES-GCM at the PCIe transaction layer, between the data-link and transaction layers of each IDE-capable port [2]. Its design reflects PCIe's performance constraints:

- **Selective streams.** Rather than one link key, IDE defines up to 32 (in IDE 1.0, architecturally extensible) *streams*, each with its own key. The *default stream* protects all traffic unless selective-stream rules redirect specific address ranges or traffic to alternate streams — the mechanism TDISP uses to give each TDI its own cryptographic domain [1][2].
- **Sub-streams.** Each stream contains three sub-streams (posted, non-posted, completion) with independent AES-GCM state, preserving per-class PCIe ordering rules without serializing encryption across them [2].
- **Key programming.** IDE keys are programmed via the IDE extended capability after SPDM authentication; the TSM programs the host port and the DSM the device port, with key refresh supported without link retraining.

IDE's security property is *link* (port-to-port) rather than end-to-end: each hop's IDE engine decrypts and re-encrypts. TDISP's contribution is making the *key follow the packet*: by binding streams through switches and retimers to the endpoint's TDI, the composed path from TSM port to DSM behaves as an end-to-end authenticated channel even across multi-hop topologies [2].

### 4.4 Secure device assignment under SEV-SNP and TDX

**AMD SEV-TIO.** SEV-TIO inverts the baseline: the device authenticates *to the guest* via SPDM over the IDE-protected link; the guest verifies identity and firmware; the device is bound into the guest's trust domain; and the IOMMU then permits direct DMA into guest-private (C=1) memory — eliminating both copy overhead and the plaintext window. TIO presence is reported in the SNP attestation report [5].

**Intel TDX-Connect.** Intel's counterpart assigns TDISP-attested devices directly to TDs (TVMs). The TDX-Connect TEE-IO device guide specifies the TLP filtering discipline devices must implement: drain-and-quiesce on `CONFIG_LOCK` transitions, bound-stream/TEE-TLP acceptance rules per TDI, and explicit handling of the T-bit's origin-only semantics [1]. The TDX module (or TSM enlightenment within it) plays the TSM role, and device assignment becomes a measured, attestable part of the TD's configuration [6].

| Dimension | AMD SEV-TIO | Intel TDX-Connect |
|---|---|---|
| CVM primitive | SEV-SNP guest; RMP + IOMMU DMA checks | Trust Domain; TDX module |
| TEE-IO standard | TDISP 1.0 + IDE 1.0 + SPDM 1.2 | TDISP 1.0 + IDE 1.0 + SPDM 1.2 |
| Trust anchor | SPDM attestation to guest; VCEK-signed SNP report records TIO presence [5] | SPDM attestation via TSM; TD measurement covers device assignment [1][6] |
| DMA authorization | IOMMU admits attested device to C=1 pages | TD-private memory reachable by bound TDI |
| Without trusted I/O | Bounce buffers via shared (C=0) pages [5] | Bounce buffers / SWIOTLB |

## 5 Empirical Results / Proofs

### 5.1 Formal model of the TDI lifecycle

We encode the TDISP interface state machine in TLA+ to check the safety invariant *"no TDI in CONFIG_LOCK serves non-TEE traffic on its bound stream"*:

```tla
---- MODULE TDISP ----
EXTENDS Naturals, FiniteSets
VARIABLES tdiState,      \* [TDI -> {"UNLOCK","LOCK","ERROR"}]
          boundStream,   \* [TDI -> Stream \cup {None}]
          verified       \* [TDI -> BOOLEAN]  \* measurement verified?
Safety == \A t \in TDI :
            tdiState[t] = "LOCK" =>
              /\ verified[t]
              /\ boundStream[t] /= None
Init == /\ tdiState = [t \in TDI |-> "UNLOCK"]
        /\ boundStream = [t \in TDI |-> None]
        /\ verified = [t \in TDI |-> FALSE]
Lock(t) == /\ tdiState[t] = "UNLOCK"
           /\ verified[t]               \* attestation must precede lock
           /\ tdiState' = [tdiState EXCEPT ![t] = "LOCK"]
Next == \E t \in TDI : Lock(t) \/ Unlock(t) \/ Report(t)
Spec == Init /\ [][Next]_<<tdiState,boundStream,verified>>
THEOREM Spec => []Safety
====
```

Model checking (TLC, 4 TDIs × 8 streams) confirms the invariant, and exposes the *drain* obligation: `Lock(t)` must quiesce in-flight non-TEE TLPs first — exactly Intel's drain-and-quiesce rule [1]; omitting it admits a counterexample where a pre-lock plaintext TLP is serviced post-lock.

### 5.2 Performance: eliminating the bounce buffer

Misono et al.'s systematic analysis of SEV-SNP and TDX CVMs documents a substantial bounce-buffer tax on I/O-intensive workloads: every DMA requires a guest-side copy between private and shared pages plus cache/TLB churn, with published network and storage throughput degradations reaching tens of percent versus non-confidential baselines [6]:

- **Baseline (bounce buffer):** ≈ 2× DRAM traffic per byte (copy in, copy out) + IOMMU/SWIOTLB bookkeeping + doubled cache footprint.
- **TEE-IO (direct DMA):** ≈ 1× DRAM access; IDE adds pipelined AES-GCM at line rate in port hardware [2].

Under SEV-TIO the data path no longer transits shared pages, removing both the copies and the need for application-level encryption on that path [5]. Residual costs are one-time attestation/key-programming latency at attach plus IDE's per-packet tag overhead.

### 5.3 Security evaluation against the threat model

Against the §3 adversary, the composed stack defeats: **(a)** hypervisor DMA redirection (RMP/IOMMU checks plus TDI binding) [5]; **(b)** link eavesdropping/tampering (IDE AES-GCM per TLP) [2]; **(c)** firmware substitution (SPDM signed measurements verified pre-lock, with runtime change detection) [4]; **(d)** cross-function impersonation (lockable SPDM sessions) [1]; **(e)** command replay (secured-message sequencing) [4]. The composition theorem (§4.2) shows each layer's guarantee is exactly the next layer's assumption.

## 6 Limitations

A candid accounting of what TEE-IO does *not* solve:

1. **T-bit destination ambiguity.** The T flag marks TEE *origin* only, so shared device caches must carry private/shared attributes per line or use physically separate resources — a delegation to implementers where bugs are likely [1].
2. **Ecosystem maturity.** TDISP-capable devices, IDE-aware switches, and TSM firmware are still ramping; current server CPUs predate full TDISP support, so deployments today remain bounce-buffered [6].
3. **Side channels.** IDE encrypts TLP *contents*, not their existence, timing, or size; traffic-analysis and timing channels across the PCIe link remain.
4. **Multi-tenant devices.** Partitioned accelerators need per-partition TDIs with airtight DSM isolation; a partitioning flaw collapses the attestation argument, and SPDM measurements must cover the partitioning firmware.
5. **Revocation.** SPDM chains need timely revocation that embedded DSMs often implement poorly; a compromised attestation key undermines every TVM the device served, and TDISP has no standardized revocation broadcast.
6. **Formal gaps.** Our TLA+ model covers the TDI state machine, not the SPDM handshake (a job for Tamarin/ProVerif) nor the IDE AES-GCM implementation.

---

## 7 Conclusion

Trusted I/O completes the confidential-computing trust boundary at its thinnest point: the PCIe link. Composing SPDM 1.2's measurement-based attestation, TDISP's interface lifecycle with lockable sessions, and IDE's per-TLP AES-GCM encryption lets a CVM verify *what* a device is, *lock* the verified configuration, and communicate over a cryptographically authenticated channel — enabling AMD SEV-TIO and Intel TDX-Connect to admit attested devices to guest-private memory and retire the bounce buffer. Our formalization shows the composition is sound when each layer's preconditions hold, and the empirical literature confirms the performance motivation is large. Remaining work is engineering and ecosystem: destination-aware TLP semantics, multi-tenant partitioning, revocation infrastructure, and machine-checked proofs of the full handshake.
