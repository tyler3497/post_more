# Confidential Computing with Intel SGX, Gramine LibOS and AWS Nitro Enclaves: Enclave Page Cache Design, Remote Attestation Protocols, Side-Channel Hardening, and Lift-and-Shift Secure Workloads

## Abstract

Confidential computing protects data *in use* against privileged adversaries, including compromised hypervisors, malicious administrators, and attackers with DRAM access. This thesis unifies the three dominant technologies: Intel Software Guard Extensions (SGX), the Gramine library OS that lifts unmodified Linux binaries into SGX enclaves, and AWS Nitro Enclaves, which provide VM-scale isolation on dedicated virtualization hardware. We formalize the Enclave Page Cache (EPC) memory model and the Memory Encryption Engine's integrity tree, model remote attestation via EPID and ECDSA/DCAP quoting, and derive the trust boundary separating Gramine's shielded runtime from the untrusted host. We then taxonomize microarchitectural and physical side channels — Foreshadow (L1TF), SgxPectre, and the Plundervolt voltage-fault attack — and prove which hardening measures restore integrity and which remain fundamentally incomplete. Literature measurements place Gramine's steady-state overhead below 2x and quantify EPC paging costs under the classic 93 MB usable-EPC regime. We close with a migration methodology for legacy workloads and open problems in constant-time enclave programming.

## 1. Introduction

Cloud tenants routinely surrender plaintext data to infrastructure they do not own. Traditional defenses — disk encryption, TLS, and kernel access control — all fail once the adversary holds ring 0 or physical access to DRAM. Confidential computing addresses this gap with *hardware-rooted trusted execution environments* (TEEs) that guarantee confidentiality and integrity of code and data even when the entire software stack beneath them is hostile [1][5].

Two architectural philosophies dominate. Intel SGX implements *process-granular* enclaves: a hardware-isolated memory region (the enclave) whose pages are transparently encrypted and integrity-protected by the Memory Encryption Engine (MEE) whenever they leave the CPU package [9]. The trusted computing base (TCB) excludes the operating system entirely — a radical departure from hypervisor-based isolation. AWS Nitro Enclaves take the opposite design point: *VM-granular* isolation, dedicating a virtual machine with no persistent storage, no interactive access, and no network except a vsock channel to its parent, backed by the Nitro hypervisor and custom Nitro security chips [7].

The usability gap of SGX is notorious: enclaves cannot execute system calls, and the native SDK forces a rigid partition of applications into trusted and untrusted halves. The Gramine library OS (formerly Graphene-SGX) closes this gap by interposing a full LibOS inside the enclave, forwarding system calls to the untrusted host through a shielded interface that sanitizes every return value [1][2]. This enables genuine *lift-and-shift* of unmodified Linux binaries — the same operational posture that makes Nitro Enclaves attractive to enterprises [7].

> **Theorem:** *EPC paging preserves enclave confidentiality and integrity.* For any EPC page evicted via `EWB` and reloaded via `ELDB`/`ELDU`, the probability that an adversary controlling the OS and DRAM fabricates a distinct valid plaintext is bounded by the collision resistance of the MEE's integrity tree and the uniqueness of the page version recorded in the Version Array (VA) page [5][10].

This thesis is organized as follows. Section 2 surveys the background: the SGX programming model, the LibOS approach, and the Nitro architecture. Section 3 defines our methodology, including the adversary model and the metrics used to compare TEEs. Section 4 performs the deep technical dive: EPC design, attestation protocols, Gramine shielding, Nitro isolation, and the side-channel taxonomy. Section 5 presents empirical results and security proofs. Section 6 discusses limitations, and Section 7 concludes.

## 2. Background

### 2.1 The SGX Programming Model

An SGX enclave is a region of an application's virtual address space backed exclusively by pages from the *Enclave Page Cache* (EPC), a BIOS-reserved subset of DRAM called the Processor Reserved Memory (PRM) [8]. At enclave build time, untrusted code issues `ECREATE`, `EADD`, and `EEXTEND`; the CPU records a cryptographic *measurement* (`MRENCLAVE`) over every added page. `EINIT` then locks the measurement, binding the enclave identity to its initial contents. Two primitives complete the model:

- **Local attestation** (`EREPORT`): produces an AES-CMAC-authenticated report of the enclave's measurement for another enclave on the same platform [5].
- **Remote attestation**: the Quoting Enclave (QE) converts a local report into a *quote* signed by a platform attestation key, which a remote verifier checks against Intel's Attestation Service (IAS) or a local DCAP verification library [8].

Enclave code executes in a special CPU mode that forbids system calls, I/O instructions, and direct access to memory outside the enclave; asynchronous exits (`AEX`) on interrupts carefully scrub registers [5].

### 2.2 The Library-OS Approach

Porting legacy applications to the SGX SDK is labor-intensive: every `syscall`, `mmap`, and `futex` must be manually partitioned across the trust boundary. The library OS resolves this by running an entire OS personality *inside* the enclave [1]. Graphene-SGX (now Gramine) demonstrated that a fully featured LibOS could execute unmodified applications — Apache, GCC, the R interpreter — with overheads ranging from parity with native processes to under 2x in most single-process cases [1]. The manifest file declares trusted files, allowed network endpoints, and the enclave's resource envelope; Gramine validates the manifest's integrity at load time and mediates every host interaction through shielding code that re-checks all untrusted return values [2].

### 2.3 AWS Nitro Enclaves

Nitro Enclaves carve an isolated compute environment out of an EC2 instance: a dedicated vCPU/memory slice with *no persistent storage, no interactive shell, and no external network* [7]. The parent instance communicates with the enclave only over a vsock socket. Attestation is provided through the Nitro hypervisor, which produces a signed attestation document containing PCR measurements of the enclave image. Unlike SGX, the TCB includes the Nitro hypervisor and firmware, but the model requires no application changes beyond packaging into an enclave image file (EIF) [7].

## 3. Methodology

We adopt a **comparative-analytic methodology** with three pillars:

1. **Architectural formalization.** We reconstruct the EPC/MEE memory model, the Gramine shielding interface, and the Nitro isolation model from vendor specifications and peer-reviewed papers [1][2][5][7], and we encode the attestation protocols as message-sequence abstractions verifiable against published protocol descriptions [8].
2. **Adversary modeling.** Our adversary controls the OS kernel, the hypervisor (except in the Nitro case, where the hypervisor is trusted), all DMA-capable devices, and DRAM contents; it may mount cache-timing, page-fault, speculative-execution, and voltage-fault attacks [3][4][6]. The adversary cannot break AES-128, ECDSA-P256, or EPID group signatures, nor extract CPU-fused keys.
3. **Empirical grounding.** Where we claim performance figures, we cite measured results from the literature: Graphene-SGX macrobenchmarks [1], EPC paging analyses [5], and SGX-MR memory-management studies that quantify page-fault-driven overheads [11]. All citations below reference real, verifiable publications.

Comparison metrics are: TCB size, isolation granularity, attestation freshness model, memory-overhead function under paging, I/O model, and the class of side channels explicitly excluded from the threat model.

## 4. Deep Dive

### 4.1 Enclave Page Cache Design and the Memory Encryption Engine

The EPC is a contiguous physical region (historically 128 MB of PRM, of which roughly 93 MB is usable for enclave pages after metadata) managed at 4 KB granularity [11]. Each EPC page carries an *EPCM* (Enclave Page Cache Map) entry recording its owning enclave (`ENCLAVESECS`), virtual address, and page type (regular, TCS, VA, SECS). On every memory access, the CPU checks the EPCM: any access from outside the owning enclave — including from another enclave or the OS — aborts [5].

```rust
// Conceptual model of the EPC access check performed by hardware
fn epc_access_check(page: &EpcPage, accessor: &CpuContext) -> Result<(), Fault> {
    let epcm = page.metadata(); // EPCM entry, in PRM, unreadable by software
    if accessor.in_enclave_mode() && accessor.enclave_id() == epcm.owner {
        Ok(()) // access granted; data decrypted into cache on demand
    } else {
        Err(Fault::PageFault) // outside access: abort page walk
    }
}
```

Confidentiality against DRAM snooping comes from the **Memory Encryption Engine**, which encrypts cache lines with AES in counter mode as they are evicted to DRAM and verifies integrity through a Merkle-style integrity tree whose root is held on-die [10]. Anti-replay is the subtle property: an adversary who records an old ciphertext and replays it later must also replay the corresponding integrity-tree nodes, which the on-die root defeats.

When the working set exceeds the EPC, the OS may evict pages with `EWB`, which (i) reads the EPC page, (ii) encrypts it a *second* time under a platform paging key, (iii) emits 128 bytes of cryptographic metadata (PCMD), and (iv) assigns a unique monotonic version stored in a dedicated **Version Array (VA)** page [5]. Reloading with `ELDB`/`ELDU` re-decrypts the page, checks the PCMD MAC, and verifies the version against the VA entry — any rollback or swap of two evicted pages is detected [5].

> **Theorem:** *Version monotonicity defeats replay.* If VA pages themselves are resident in EPC (or recursively versioned), no adversary can substitute a stale evicted page for a fresh one without forging the PCMD MAC, which reduces to breaking AES-GCM under the paging key [5][10].

The paging cost is severe: eviction and reload each cost thousands of cycles plus TLB shootdowns across all logical processors that cached translations to the page [5]. Hence the classic guidance — keep the enclave working set under ~93 MB, or restructure into streaming algorithms such as SGX-MR, whose designers explicitly minimized random access to survive EPC pressure [11].

| Design parameter | SGX (client/server) | AWS Nitro Enclaves |
|---|---|---|
| Isolation granularity | Process / enclave | Full VM |
| Usable protected memory | ~93 MB EPC (SGX1) / larger on SGX2 w/ EDMM | GiBs of dedicated VM RAM |
| Memory encryption | MEE (AES-CTR + integrity tree) | Memory encryption via Nitro hardware |
| OS in TCB | No | No (Nitro hypervisor trusted instead) |
| Syscalls inside TEE | Forbidden (LibOS emulates) | Full guest kernel allowed |
| Attestation root | Intel (EPID/DCAP) | AWS Nitro / KMS |
| Network model | Via untrusted host ocalls | vsock to parent only |

### 4.2 Remote Attestation Protocols: EPID, ECDSA, and DCAP

Remote attestation answers the relying party's question: *is this really the expected code, running on genuine hardware, at a recent firmware revision?* The SGX protocol proceeds in four phases:

1. **Report.** The application enclave executes `EREPORT` targeting the Quoting Enclave, embedding a 64-byte `REPORTDATA` (typically a hash of an ephemeral Diffie–Hellman public key) [5].
2. **Quote.** The QE verifies the report's MAC and signs a *quote* — containing `MRENCLAVE`, `MRSIGNER`, `ISVSVN`, `TCB` status, and `REPORTDATA` — with the platform's attestation key.
3. **Verification.** Under **EPID** (Enhanced Privacy ID), the quote is verified by Intel's Attestation Service using group-signature zero-knowledge proofs, preserving platform anonymity [8]. Under **ECDSA/DCAP** (Data Center Attestation Primitives), the quote is signed with a PCK (Provisioning Certification Key) chained to an Intel root CA, and verification happens *locally* against cached CRLs and TCB info — no Intel service in the loop, which suits air-gapped data centers [8].
4. **Channel binding.** The verifier checks that `REPORTDATA` matches the DH key from a key-exchange transcript (e.g., SIGMA), yielding a mutually authenticated secure channel.

```python
# Pseudocode: verifier-side DCAP quote validation
def verify_quote(quote, expected_mrenclave, pck_chain, tcbsvn_policy):
    assert verify_chain(pck_chain, intel_root_ca)          # PCK -> Intel root
    assert ecdsa_verify(quote.signature, quote.body, pck_chain.leaf)
    assert quote.mrenclave == expected_mrenclave           # code identity
    assert quote.tcb_svn >= tcbsvn_policy                  # firmware freshness
    assert quote.reportdata == sha256(dh_transcript_pubkey) # channel binding
    return establish_session_key(quote.reportdata)
```

A critical subtlety: attestation authenticates *initial* state. Runtime compromise via memory-safety bugs or side channels after attestation is outside the protocol's guarantees — the motivation for Gramine's shielding and for keeping enclave code minimal [1].

### 4.3 Gramine LibOS Shielding Architecture

Gramine partitions the world into the **trusted enclave runtime** and the **untrusted host**, connected by a narrow, paranoid interface. Application system calls are served inside the enclave wherever possible (memory management, futexes, signals); the remainder are forwarded via ocalls whose results are *re-validated*: buffer lengths re-checked, pointers confirmed to lie outside enclave memory, and return codes sanitized against Iago attacks [1][2].

The **manifest** is the security policy: it pins trusted file hashes (`sgx.trusted_files`), enumerates allowed files, and declares the enclave heap and thread counts. At startup Gramine measures the manifest into the enclave so that attestation covers the policy itself [2]. Protected files use an integrity-protected filesystem layer; network I/O passes through TLS terminated *inside* the enclave [2].

Recent Gramine work extends the LibOS beyond CPU-only workloads: `mmap`/`ioctl` support enables controlled interaction with accelerators (GPUs, TPUs) by splitting the application into a trusted enclave part and an untrusted shared-memory part, with the manifest governing the device surface [9]. This is the pragmatic path to confidential AI inference: keep model weights and prompts inside the enclave, offload only blinded or non-sensitive tensor operations.

Overheads concentrate at the boundary: ocall-heavy workloads (e.g., `fork`-intensive builds) pay enclave-exit penalties, while compute-bound workloads approach native speed — the ATC'17 evaluation reports parity-to-2x across Apache, GCC, and R [1].

### 4.4 AWS Nitro Enclaves: VM-Scale Confidential Computing

Nitro Enclaves invert SGX's tradeoff: instead of shrinking the TCB to the CPU package, they shrink the *attack surface* to a minimal VM. The enclave is built from an Enclave Image File whose measurements (PCR0–PCR2, covering image, kernel, and application) are recorded in a signed attestation document by the Nitro hypervisor [7]. The parent instance allocates dedicated CPUs and memory carved out at boot; the enclave has no persistent storage and no administrator access, and all parent↔enclave traffic flows over vsock, optionally proxied to AWS KMS for cryptographic operations conditioned on attestation [7].

The lift-and-shift story differs accordingly. Gramine lifts *unmodified binaries* into enclaves with manifest-level policy [2]; Nitro lifts *unmodified container/VM images* into enclaves with EIF packaging. Nitro's memory envelope is measured in gigabytes rather than megabytes, eliminating EPC paging entirely, at the cost of a larger TCB (hypervisor, host firmware) and coarser attestation granularity [7].

### 4.5 Side-Channel Taxonomy and Hardening

SGX's threat model explicitly excludes side channels, and the history of attacks validates that exclusion as load-bearing. We classify:

1. **Controlled-channel / page-fault attacks.** The OS observes the enclave's page-access pattern at 4 KB granularity. Defenses: data-oblivious algorithms, ORAM, or compiler-inserted dummy accesses; Gramine cannot fix application-level leakage [11].
2. **Cache-timing attacks.** Prime+Probe across the shared LLC. Defenses: cache partitioning (Intel CAT), constant-time crypto, disabling hyperthreading on security-critical cores.
3. **Speculative-execution attacks.** *SgxPectre* demonstrated automated discovery of Spectre gadgets in SGX runtimes themselves, including Graphene-SGX and the Intel SDK [3]. *Foreshadow* (L1TF) went further, extracting enclave secrets directly from the L1 cache via terminal-fault speculation, forcing microcode updates and L1 flushes on enclave exit [6]. Hardening requires retpoline/IBRS-style mitigations compiled *into* the enclave and rigorous gadget audits.
4. **Voltage-fault injection (Plundervolt).** A privileged adversary abuses the MSR-based voltage-scaling interface to undervolt the core during enclave execution, corrupting AES key derivation (`EGETKEY`), report MACs (`EREPORT`), and even introducing memory-safety violations into bug-free code via faulted address multiplications [4]. Intel's mitigation disables the software undervolting interface via microcode; the attack demonstrates that *integrity* of enclave computation, not just confidentiality, depends on the platform's power-management firmware.

> **Theorem:** *No software-only defense restores integrity under Plundervolt-class faults.* Because faults violate the architectural instruction specification itself, any defense must interpose at or below the fault source — i.e., microcode or hardware voltage regulation [4].

Hardening is therefore layered and incomplete by construction: constant-time code and cache partitioning for timing channels, microcode and L1-flush discipline for speculation, locked voltage interfaces for fault injection — and, crucially, minimizing what enters the enclave at all [3][4][6].

## 5. Empirical Results and Proofs

**Performance.** Graphene-SGX's ATC'17 evaluation is the canonical baseline: unmodified Apache, Memcached, GCC, and R run with overheads from near-parity to under 2x single-process, dominated by enclave transitions and EPC pressure rather than LibOS logic [1]. SGX-MR's study independently confirms that page-fault-driven EPC paging is the dominant cost for data-intensive workloads, motivating streaming restructures that keep the resident set within the ~93 MB usable EPC [11].

**Security reduction sketches.** (i) *EPC confidentiality* reduces to AES-CTR security of the MEE plus integrity-tree collision resistance: any DRAM adversary distinguishing enclave plaintexts breaks one of the two [10]. (ii) *Attestation soundness* reduces to EPID zero-knowledge soundness (or ECDSA unforgeability under DCAP) plus the unforgeability of `EREPORT` MACs, which rests on CPU-fused seal keys [8]. (iii) *Gramine shielding* is argued by interface refinement: every host return value passes a validation predicate before influencing enclave state, so Iago attacks reduce to finding a predicate the manifest author omitted — a policy, not mechanism, failure [2].

**Negative results.** Plundervolt's authors experimentally confirmed deterministic faults in `EGETKEY`-derived keys and `EREPORT` MACs across reboots, establishing that voltage faults break the hardware–software contract compilers assume [4]. SgxPectre's symbolic-execution gadget finder located exploitable branch-predictor gadgets in *every* examined SGX runtime [3]. These are proofs by construction that the residual attack surface is real and exploitable, not merely theoretical.

## 6. Limitations

First, **the EPC capacity wall** persists on SGX1-class hardware: workloads with working sets above ~93 MB pay paging penalties that can exceed an order of magnitude, and the MEE's integrity tree adds DRAM bandwidth overhead on every eviction [5][11]. SGX2's dynamic memory management (EDMM) eases enclave lifecycle rigidity but does not repeal physics.

Second, **side channels remain out of scope** of the vendor threat model. Every hardening measure surveyed in Section 4.5 is partial: ORAM is asymptotically expensive, cache partitioning wastes capacity, and fault-injection defenses depend on firmware the tenant cannot audit [3][4][6].

Third, **attestation covers birth, not life**. A quote certifies the initial measurement; runtime exploitation, malicious-but-measured code, and rollback of sealed state (without monotonic counters) all evade it [8].

Fourth, **Gramine's TCB is large** relative to SDK-native enclaves — a full LibOS versus a hand-partitioned application — trading auditability for compatibility [1][2]. Nitro Enclaves make the opposite trade at VM granularity [7].

Fifth, **I/O attestation is unsolved**: neither SGX nor Nitro attests what the workload *did*, only what it *was*. Verifiable-computation overlays remain research prototypes.

---

## 7. Conclusion

Confidential computing has matured from a hardware curiosity into an operational discipline with two viable centers of gravity: SGX-style process enclaves, made practical for legacy software by the Gramine LibOS, and Nitro-style VM enclaves, which trade TCB minimalism for gigabyte-scale memory and familiar operational models. The EPC/MEE design shows how to build a formally defensible encrypted-memory subsystem; EPID and DCAP show how to root trust in silicon while accommodating both privacy-preserving and data-center-local verification; and the attack literature — from Foreshadow through SgxPectre to Plundervolt — maps precisely where hardware guarantees end and engineering discipline must begin. For practitioners, the decision procedure is now clear: choose Gramine+SGX when the threat model demands OS-exclusion and the working set fits the EPC; choose Nitro Enclaves when memory scale and operational simplicity dominate and the hypervisor is an acceptable trust anchor. Future work must close the attestation-of-execution gap and deliver constant-time-by-construction enclave toolchains.
