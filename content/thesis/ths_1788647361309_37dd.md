# Transient Execution Attacks: Spectre and Meltdown, Speculative Side Channels, and the Architecture of Modern Mitigations

## Abstract

Transient execution attacks redefined the boundary between architectural semantics and microarchitectural reality. By exploiting the gap between speculative, transient instruction execution and the eventual squashing of misspeculated state, adversaries can coax privileged or isolated data into observable side channels — most notably the cache hierarchy — without any software vulnerability. This thesis presents a comprehensive treatment of the transient-execution attack surface, beginning with the discovery of Spectre [1] and Meltdown [2] and extending through L1 Terminal Fault [3], Microarchitectural Data Sampling variants including RIDL, Fallout, and ZombieLoad, and the CacheOut eviction-sampling refinement [4]. We formalize the transient-execution threat model, dissect the anatomy of speculation gadgets and covert channels, survey the layered mitigation stack — retpolines [5], IBRS/eIBRS, KPTI, SSBD, *lfence* placement, and hardware taint-tracking proposals such as STT [6] — and quantify the persistent performance-security tradeoff. We conclude that transient execution is not a correctable erratum but a foundational design tension, and we chart a path toward hardware contracts that reconcile speculation with principled information-flow security.

## 1 Introduction

For four decades, the instruction set architecture (ISA) served as an effective security contract: software reasoned about privilege and isolation as defined by architectural state, and hardware was free to reorder, predict, and speculate beneath that abstraction, so long as *committed* results matched the ISA model [7]. The disclosures of January 2018 — Spectre [1] and Meltdown [2] — shattered that assumption by demonstrating that *uncommitted*, transient microarchitectural state is observable through side channels, and that transient instructions can access data the architectural model would never permit.

The central insight is deceptively simple: modern out-of-order processors execute instructions *before* knowing whether they should execute. Branch predictors guess control flow; memory disambiguation predicts whether loads alias stores; exception checks complete *after* dependent instructions have already issued. When a prediction proves wrong, the pipeline squashes the transient instructions and rewinds architectural state — but microarchitectural state, such as which cache lines were touched, persists. An adversary who controls either the predictor's training or the victim's input can steer transient execution to encode secrets into that persistent state, then decode them with cache-timing probes [1][2].

This thesis contributes the following:

1. A formalized **transient-execution threat model** that distinguishes *transient* from *architectural* leakage and catalogues covert-channel primitives.
2. A systematic dissection of **Spectre variants** (v1 bounds-check bypass, v2 branch-target injection, v4 speculative store bypass), **Meltdown-class faulting attacks**, **L1TF**, and **MDS-class buffer sampling** (RIDL, Fallout, ZombieLoad, TAA, CacheOut).
3. A layered taxonomy of **mitigations** — compiler barriers, trampoline constructs, page-table isolation, hardware prediction controls, and speculative taint tracking — with analysis of their composability gaps.
4. An evaluation of the **performance-security tradeoff** and the emerging hardware contracts (Intel CET-IBT, ARM CSV2/CSV2-extended, domain isolation) that attempt to close the loop.

The remainder of this thesis proceeds as follows: background on speculative execution and cache channels (Section 2), our systematization methodology (Section 3), the deep technical dive (Section 4), empirical results and proof sketches (Section 5), limitations (Section 6), and conclusions (Section 7).

## 2 Background

### 2.1 Speculative and out-of-order execution

Modern superscalar processors sustain high instruction throughput by overlapping work: *out-of-order execution* reorders instructions according to data dependencies, while *speculative execution* executes instructions before their control or data dependencies are resolved. The **reorder buffer (ROB)** tracks in-flight instructions and commits them in program order, rolling back — *squashing* — any instruction whose speculation was invalidated [7].

Key speculative mechanisms include:

- **Branch prediction.** Conditional branches are predicted by pattern-history tables and global-history predictors; indirect branches by the Branch Target Buffer (BTB) and the Return Stack Buffer (RSB).
- **Memory dependence prediction.** Loads may execute speculatively ahead of older stores whose addresses are unresolved, rolling back if an aliasing violation is detected.
- **Deferred exception handling.** Faulting instructions (e.g., page faults) raise exceptions only at *retirement*; dependent instructions may execute transiently in the interim [2].

The **speculation window** — the number of instructions that can be in flight between prediction and resolution — spans hundreds of cycles on modern cores, ample time for a transient instruction sequence to touch memory and encode secrets into the cache.

### 2.2 Cache side channels

Because transient state must be *decoded*, every transient-execution attack pairs a *transient transmitter* with a *covert channel*. The canonical channel is the cache hierarchy:

- **Flush+Reload** [1][2]: the attacker flushes shared cache lines (`clflush`), waits, then reloads them, timing each access. A fast reload reveals the victim accessed that line. Requires shared memory (e.g., shared libraries, page deduplication).
- **Prime+Probe**: the attacker fills (*primes*) cache sets, waits, then probes for evictions. Requires no shared memory, only cache-set contention.
- **Evict+Reload / Flush+Flush**: variants trading resolution for stealth.

Timing resolution historically came from `rdtsc`; even where unavailable (browsers, sandboxes), counting threads and `performance.now()`-based timers suffice [1][7].

### 2.3 The security contract before 2018

Prior to 2018, the dominant threat model for microarchitectural attacks was *physical* or *co-resident* side channels against cryptographic implementations — timing attacks on RSA and AES keyed operations that software could harden with constant-time coding. The **architectural** contract — that an unprivileged process cannot read kernel memory, that one VM cannot read another, that an SGX enclave's contents are opaque — was treated as a hardware-enforced guarantee. Spectre and Meltdown showed these guarantees were enforced only for *committed* instructions, not for transient ones [1][2].

> **Theorem (Informal): Architectural isolation is insufficient.** *If a processor (a) executes instructions transiently before privilege or bounds checks resolve, and (b) permits transient instructions to alter shared microarchitectural state, then no software-only memory-isolation mechanism can prevent information leakage between the domains separated by those checks.* [6][7]

## 3 Methodology

Our analysis combines literature-driven systematization with microarchitectural reasoning grounded in published proof-of-concept behavior:

1. **Variant taxonomy** along three axes: the *speculation primitive* (branch misprediction, BTB poisoning, store bypass, deferred fault, buffer sampling), the *secret source* (same address space, kernel, enclave, cross-VM, cross-SMT-thread), and the *covert channel* (cache, port contention, TLB).
2. **Gadget anatomy**: decomposing each variant into *mistraining*, *transient access*, and *covert transmission* phases.
3. **Mitigation mapping**: which attack phase each defense disrupts, and where composability breaks down (e.g., LVI [4]).
4. **Empirical grounding**: leakage rates, window depths, and overheads drawn from the primary literature [1][2][4][6].

## 4 Deep Dive

### 4.1 The Transient-Execution Threat Model: Speculation Windows, Gadgets, and Covert Channels

A transient-execution attack has a canonical four-phase structure [1][6]: **setup** (mistraining predictors, priming caches), **transient access** (a victim gadget reads the secret speculatively), **covert transmission** (secret-dependent instructions encode it into shared microarchitectural state), and **decoding** (cache-timing probes recover it).

The threat model assumes an attacker who can execute unprivileged code on the target (natively or in a sandbox/browser), possibly co-located on a sibling SMT thread or in a neighboring VM. The attacker needs no software bug in the victim: Spectre gadgets are *benign* code — bounds checks, array indexing, indirect calls — weaponized by predictor state [1][7].

Two channel classes matter for defenses. An **explicit channel** passes the secret directly to an instruction whose hardware resource usage is operand-dependent (e.g., a load whose address depends on the secret changes cache state). An **implicit channel** lets the secret *indirectly* influence which instructions execute — for example, a transient branch outcome steering subsequent memory traffic [6]. The STT framework formalizes this distinction and shows that protecting only explicit channels is insufficient.

The canonical Spectre v1 gadget, in C, is:

```c
if (x < array1_size) {          /* bounds check, mistrained to true */
    uint8_t s = array1[x];     /* transient out-of-bounds read of secret */
    uint8_t y = array2[s*4096]; /* secret-dependent load: encode into cache */
}
```

The attacker first trains the branch predictor with in-bounds `x`, flushes `array1_size` from cache (lengthening the resolution window), then supplies an out-of-bounds `x` pointing at the secret. The bounds check resolves *after* both transient loads have issued; the squash discards the architectural effects but the cache line `array2[s*4096]` remains, leaking `s` via Flush+Reload [1].

### 4.2 Spectre Variants: v1, v2, v4, and the Gadget Zoo

| Variant | CVE | Speculation primitive | Typical gadget | Primary mitigation |
|---|---|---|---|---|
| v1 Bounds-check bypass | CVE-2017-5753 | Conditional branch misprediction | `if (x < bound) y = a[x]` | `lfence`, `array_index_nospec` |
| v2 Branch-target injection | CVE-2017-5715 | BTB/RSB poisoning | Indirect call/jump | retpoline, IBRS/eIBRS, IBPB |
| v3 Rogue data-cache load (Meltdown) | CVE-2017-5754 | Deferred fault handling | Kernel pointer dereference | KPTI |
| v3a Rogue system-register read | CVE-2018-3640 | Deferred MSR fault | `rdmsr` in userspace | Microcode |
| v4 Speculative store bypass | CVE-2018-3639 | Memory disambiguation misprediction | Store then dependent load | SSBD |
| L1TF / Foreshadow | CVE-2018-3615/3620/3646 | Terminal page fault | Non-present PTE | L1D flush, PTE inversion |
| MSBDS (Fallout) | CVE-2018-12126 | Store-buffer sampling | Faulting/assisted load | Microcode buffer overwrite |
| MLPDS (RIDL) | CVE-2018-12127 | Load-port sampling | Faulting load | Microcode buffer overwrite |
| MFBDS (ZombieLoad) | CVE-2018-12130 | Fill-buffer sampling | Faulting load | Microcode buffer overwrite |
| TAA | CVE-2019-11135 | TSX abort sampling | Transactional region | TSX disable / microcode |
| L1DES (CacheOut) | CVE-2020-0549 | L1D eviction sampling | Eviction + faulting load | Microcode |

**Spectre v2 (branch-target injection)** poisons the BTB so that a victim's indirect branch speculatively jumps to an attacker-chosen gadget. Because the BTB is shared across privilege levels and (historically) not tagged by context, an attacker can train entries from userspace that the kernel later consumes speculatively [1]. The canonical defense, **retpoline** [5], replaces indirect branches with a construct that traps speculation in an infinite loop:

```c
/* retpoline: indirect call replaced by return-trampoline */
call set_up_target;
capture_ret: pause;
  jmp capture_ret;      /* speculation spins here forever */
set_up_target:
  mov %r11, (%rsp);     /* overwrite return address with real target */
  ret;                  /* architectural path returns to real target */
```

Because `ret` prediction consults the software-controlled RSB rather than the attacker-poisoned BTB, speculation cannot be steered to a gadget [5].

**Spectre v4 (speculative store bypass)** exploits memory disambiguation: a load speculatively bypasses an older store whose address is unresolved. If the store was a bounds-check sanitization, the transient load observes the *stale* value [4]. Mitigation is **SSBD**, an MSR bit forcing loads to wait for older stores to resolve.

### 4.3 Meltdown, L1TF, and MDS: Faulting Loads and Buffer Sampling

**Meltdown** [2] is conceptually the simplest transient attack: on affected Intel CPUs, a user load from a kernel address *executes* before the privilege check faults. The fault is raised only at retirement, so a transient dependent load can encode the kernel byte into the cache first:

```c
/* Meltdown core: exception deferred until retirement */
uint8_t s = *(uint8_t *)kernel_addr;  /* faults, but transiently returns data */
uint8_t y = probe[s * 4096];          /* encode into cache before squash */
```

Meltdown dumped kernel memory at hundreds of KB/s and broke every isolation boundary built on page tables, including KVM guests [2]. The fix, **KPTI** (Kernel Page-Table Isolation, née KAISER), unmaps the kernel from user page tables, removing the secret from the transient load's reach at the cost of TLB-flush-heavy context switches.

**Foreshadow (L1TF)** [3] refined the faulting-load idea: by clearing the *present* bit in a page-table entry, the attacker induces a *terminal* page fault, and vulnerable CPUs forward data from the **L1 data cache** (indexed by the physical address bits embedded in the non-present PTE) before the fault resolves. Three variants targeted SGX enclaves (CVE-2018-3615), OS/SMM memory (CVE-2018-3620), and hypervisors (CVE-2018-3646) [3]. Notably, later work showed the "L1-only" restriction was an artifact of prefetch gadgets: with *speculative dereferencing* of registers, Foreshadow-style leakage could reach beyond L1, and complete mitigation additionally required Spectre-BTB (v2) defenses — a composability gap the original guidance missed [3].

**Microarchitectural Data Sampling (MDS)** [4] moved the secret source from *addressable memory* to *in-flight microarchitectural buffers*. RIDL, Fallout, and ZombieLoad showed that faulting loads could sample stale data from the **load ports** (MLPDS), **store buffer** (MSBDS), and **line-fill buffers** (MFBDS) — data the attacker never addressed, belonging to another process, VM, or the kernel. Mitigations overwrite the buffers on privilege transitions via microcode (`VERW` / MD_CLEAR), and conservative guidance added disabling SMT [4].

**CacheOut** [4] defeated the 2019 MDS mitigations by a new sampling primitive: forcing *eviction* of L1D lines into the fill buffers, then sampling them — showing that buffer-overwrite-on-transition is a point fix, not a principled one. **TAA** (CVE-2019-11135) similarly reused the MDS machinery inside aborted TSX transactions, and **LVI** (Load Value Injection, CVE-2020-0551) inverted the direction entirely: instead of *reading* victim data, the attacker *injects* chosen values into the victim's faulting loads, turning Meltdown's primitive into an integrity attack that bypassed all deployed Spectre/Meltdown mitigations [4].

### 4.4 The Mitigation Stack: Barriers, Trampolines, Isolation, and Taint Tracking

No single mitigation covers the space; production systems layer defenses by attack phase:

1. **Constrain speculation at gadgets.** Compiler-inserted `lfence` (serializing) instructions after bounds checks close Spectre v1 at its source; Linux's `array_index_nospec()` masks indices with branchless arithmetic so the transient address is clamped even under misprediction. Coverage is inherently incomplete — it requires finding every gadget [1].
2. **Redirect speculation.** **Retpoline** [5] converts indirect branches into returns, isolating them from BTB poisoning; **IBRS/eIBRS** restricts indirect-branch speculation across privilege levels in hardware; **IBPB** flushes predictor state on context switch; **STIBP** isolates predictor state between SMT siblings.
3. **Remove the secret.** **KPTI** unmaps kernel pages from user address spaces, defeating Meltdown by denying the transient load its target [2]. SGX and VM mitigations flush L1D on enclave/VM exit to starve L1TF [3].
4. **Scrub shared buffers.** Microcode buffer-overwrite (`VERW`) on privilege transitions addresses MDS-class sampling [4].
5. **Principled hardware tracking.** Research proposals move beyond point fixes. **Speculative Taint Tracking (STT)** [6] taints data loaded by *doomed-to-squash* instructions and delays only the *transmit* instructions — loads, stores, branches that could form explicit or implicit covert channels — until the taint resolves.

> **Theorem (STT non-interference):** *If every instruction that can create an operand-dependent microarchitectural observable is delayed until its operands are non-speculative, then transient execution cannot leak speculatively accessed data through any modeled covert channel.* [6]

STT's insight is that *speculative execution is safe unless speculatively accessed data reaches a covert channel* — the first load in the v1 gadget leaks only an attacker-chosen address, so it may execute freely; only the second, secret-dependent load must wait. This yields a principled defense with far lower overhead than stalling all speculative loads [6]. Related proposals include InvisiSpec (shadow buffering of speculative loads), SafeSpec (shadow structures discarded on squash), NDA (delay broadcast of speculative data), and MuonTrap (speculative filter caches).

### 4.5 Performance-Security Tradeoffs and the Hardware Future

Security here is purchased directly with speculation — the engine of three decades of single-thread performance. Measured costs include:

- **KPTI:** 5–30% on syscall- and context-switch-heavy workloads (databases, web servers); negligible on compute-bound code [2].
- **Retpoline + IBRS-era v2 mitigations:** 2–14% on 8th-generation Core platforms in early benchmarks, workload-dependent [1][5].
- **MDS buffer overwrites + SMT considerations:** single-digit percentages for `VERW`-on-transition; disabling SMT — the conservative MDS guidance — costs up to ~30% throughput on threaded workloads [4].
- **STT (simulated):** ~8–14% on SPEC for the full protection model, versus the catastrophic cost of stalling all speculative memory access [6].

Hardware is slowly absorbing the lessons. **Intel CET-IBT** constrains indirect-branch targets architecturally; **eIBRS** makes cross-privilege BTB isolation cheap enough to leave on by default. **ARM** introduced **CSV2** firmware interfaces, **DIT** (Data Independent Timing), and speculation-barrier instructions (`SB`, `SSBB`). The trajectory is from emergency software tourniquets (KPTI, retpoline) toward **hardware-software contracts for secure speculation** [6][7] — formal models in which the ISA states what speculation may leak, compilers target those guarantees, and verification checks them.

## 5 Empirical Results and Proofs

**Leakage rates (reported in primary literature).** Meltdown achieved ~500 KB/s–1 MB/s reads of kernel memory [2]. Spectre v1 PoCs leaked at ~10 KB/s in-process and across the browser sandbox [1]. RIDL-family sampling is far slower — bits to bytes per second — because the attacker samples *whatever* transits the buffers ("drinking from the firehose"), requiring long observation and statistical decoding [4].

**Proof sketch: why barriers compose poorly.** Consider mitigations M1 (lfence at known gadgets) and M2 (retpoline for indirect branches). A program hardened with M1+M2 remains vulnerable to Spectre v4 (store bypass needs SSBD) and to LVI, which needs neither a bounds-check gadget nor an indirect branch — it injects into the victim's *own* faulting load [4]. Formally:

> **Theorem (Mitigation non-composition):** *Point mitigations that each close one speculation primitive do not compose into a whole-program guarantee, because the set of speculation primitives is defined by microarchitectural implementation, not by the ISA, and is therefore not enumerable by software.* [7]

This is the core argument for STT-style *mechanism* defenses over *pattern* defenses: STT protects the *data flow* (tainted data may not reach transmitters) rather than enumerating dangerous patterns [6].

**Verification results.** The STT formal model proves non-interference for its modeled channels [6]; follow-up work mechanizes speculative semantics and verifies contract satisfaction for fenced programs. Conversely, automated gadget-discovery tools continue to find unhardened Spectre v1 gadgets in the Linux kernel years after `array_index_nospec()` was introduced — evidence that pattern-based hardening does not converge [7].

## 6 Limitations and Open Problems

1. **The gadget-discovery gap.** Hardening relies on finding speculation gadgets; automated discovery remains incomplete, and new primitives (retbleed, straight-line speculation, BHI) keep expanding the set [7].
2. **Implicit channels.** Most deployed mitigations target explicit cache channels; implicit channels (transient control flow influencing port contention, ALU timing, prefetcher state) are poorly covered, and no shipping silicon implements full STT [6].
3. **Cross-domain predictor state.** eIBRS/CSV2 raise the bar for cross-privilege BTB poisoning, but intra-privilege and cross-SMT attacks persist.
4. **TSX.** TAA showed transactional-abort paths re-expose MDS primitives; vendors have largely disabled TSX rather than secure it [4].
5. **Browsers and JITs.** JIT compilers emit new gadgets at runtime; site isolation and reduced timer resolution raise cost but the in-JS attack surface is structurally hard to close [1][7].
6. **Formal contracts.** Hardware-software contracts for speculation exist as research prototypes; no mainstream ISA has published a complete, verified speculative-leakage contract [6].

## 7 Conclusion

Transient execution attacks demonstrated that performance optimization and security isolation were built on contradictory assumptions: the ISA promised that only committed instructions have effects, while microarchitecture made transient effects observable [1][2][7]. The decade since has produced an extraordinary catalog — Spectre v1/v2/v4, Meltdown, Foreshadow, RIDL, Fallout, ZombieLoad, TAA, CacheOut, LVI — and a layered mitigation stack — *lfence* placement, retpolines [5], KPTI [2], SSBD, buffer scrubbing [4], and principled proposals like STT [6] — that manages but does not eliminate the class.

Three conclusions stand. First, **transient execution is a design flaw, not a bug**: it is foundational to speculative microarchitecture and cannot be patched away without redefining the hardware-software contract [7]. Second, **pattern-based mitigations do not compose**; only mechanism-based defenses that track speculative data flow (STT, NDA, InvisiSpec) offer whole-class arguments, and none ship in mainstream silicon yet [6]. Third, the endgame is **contractual**: ISAs must specify what speculation may observably do, compilers must target those contracts, and verification must check them — the direction mapped by hardware-software contracts for secure speculation.

Until then, every new speculation primitive is a new vulnerability class waiting for its paper, and defense remains what it has been since January 2018: layered, expensive, and necessarily incomplete.
