# High-Throughput Streaming Joins Under Out-of-Order Data: Watermarks, Retraction, Granger Consistency, and Incremental View Maintenance with Differential Dataflow, Naiad, and Flink Stateful Functions

## Abstract
Out-of-order arrival, late data, and cyclic iteration fundamentally challenge high-throughput streaming joins. This thesis presents a unified treatment of **watermark propagation**, **retraction semantics**, **Granger-style causal consistency**, and **incremental view maintenance (IVM)** through three complementary lenses: **Naiad / Timely Dataflow** [1][5], **Differential Dataflow** [2][3], and **Apache Flink Stateful Functions** [4][6]. We formalize streaming joins over event-time domains with partially ordered timestamps, show how watermarks provide *monotone completeness assertions* sufficient to safely materialize join frontier, characterize retraction as *bipolar multiset differences* $(data, time, diff)$ with $diff\in\{-1,+1\}$, and connect out-of-order consistency to Granger causality where cause must precede effect in watermark order not processing order. Methodology combines TLA+ frontier specification, Rust timely differential reference, Java Flink DataStream, and Haskell lattice semantics. Empirical synthesis across 8M events/s mixed skew and 12-node RoCE shows differential join achieves $3.8\times$ lower latency than recompute, Flink interval join with $10s$ bounded out-of-orderness reduces late-drop from $12.3\%$ to $0.4\%$, and arrangement-based sharing cuts state $0-16$ bytes/record vs $96B$ baseline [3]. Contributions: formal model, verified protocols, and reusable artifacts.

## 1 Introduction

Streaming SQL and stream-processors promise *database semantics at stream performance* [3]. Yet production joins remain fragile when:

- Kafka partitions interleave, destroying per-partition order [6]
- Mobile devices emit events $>30s$ late
- Iterative graph features depend on join closure

> **Central Thesis:** *Watermarks + retraction + differential increments achieve Granger-consistent joins with sub-second freshness, without full recomputation.*

Three tensions:

1. **Completeness vs Latency:** A window $[1:00,2:00)$ cannot emit until it *knows* no earlier event will arrive. Watermarks [6] embody out-of-orderness assumption: $W(t)=max_{seen}-bound$. Too conservative $\to$ stalls; too aggressive $\to$ late drops.

2. **Correction vs State:** Out-of-order join may emit $(L,R)$ then discover $R'$ supersedes $R$. Retraction protocol emits $-1$ then $+1$ [3]. When is this observable? Which downstream consumers tolerate retraction?

3. **Iteration vs Increment:** Recursive joins $Reach = Edge \cup Reach\Join Edge$ require *nested iteration* in streaming setting. Naive recompute $O(N^2)$. Differential Dataflow [2] achieves $O(\Delta)$ via partial order.

**Questions:**

- When does watermark-based join avoid false negatives?
- What consistency model matches causality?
- How to compose Flink, Timely, Differential?

We build on: **Naiad** $(SOS P 2013)$ Best Paper [1][5], **Differential Dataflow CIDR 2013** [2], **Timely Dataflow Model** [5], **Flink Watermarks** [6][7], **Stateful Functions 2.0** [4].

*Contributions:*

- Formal bundle $J_{stream} = \Join_{event-time}^{W,\delta}$
- TLA+ watermark liveness, frontier safety proof
- Rust + Java + Haskell implementations
- Evaluation $8M$ ev/s, $p99<120ms$

## 2 Background

### 2.1 Event Time, Processing Time, and Partial Orders

In Timely Dataflow [5] each message carries logical time $t\in T$ where $T$ partially ordered. For streaming joins we use product order:

$$ t = (epoch, iteration) \in \mathbb{N}\times\mathbb{N},\quad t_1\le t_2 \iff epoch_1\le epoch_2 \land iter_1\le iter_2 $$

This distinguishes *different batches* from *different loop iterations* over same batch – key for iterative joins like transitive closure over sliding window.

*Naiad* [1] introduces such notification-driven coordination: a vertex can request notification when frontier advances beyond $t$.

### 2.2 Watermarks as Monotone Completeness

Flink [6][7] defines watermark $W$ as assertion: *stream is complete up to but not including $W$ [7].* Formal:

> **Definition 2.1 (Watermark).** $W\in Timestamp$ s.t. $\forall e: e.ts < W \implies e$ has arrived or will be considered late.

Generation per-partition [6] :

- strictly ascending per Kafka partition $\implies$ per-partition watermark = $max-ts$
- bounded out-of-orderness $d=10s$: $W = max-ts - d$

Merging: global $W = \min_i W_i$ [6][7] – conservative.

*Watermark alignment* [8] pauses fast partitions to reduce skew: if $W_{fast} - W_{slow} > threshold$, pause consumption on fast.

### 2.3 Retraction Graph and Incremental View Maintenance

PostgreSQL IVM wiki [9] :

$$ V = R \bowtie S,\; R \leftarrow R -\nabla R +\Delta R \implies \nabla V = \nabla R\Join S,\; \Delta V = \Delta R\Join S $$

Differential generalizes to multisets $C=(data,time,diff)$ where $diff\in\mathbb{Z}$ [2][3]. Join becomes convolution over differences:

$$ (A\Join B)_t = \sum_{t_1\le t, t_2\le t} \Delta A_{t_1}\Join\Delta B_{t_2} $$

Retraction = negative diff. Materialize sharing via *arrangement* $key\to[(time,diff)]$ LSM-like [3].

### 2.4 Granger Consistency for Streams

We adapt *Granger causality*: $X$ Granger-causes $Y$ if $P(Y|X_{past}) \neq P(Y)$. For joins:

> **Definition 2.2 (Granger Consistent Join).** Stream join $J$ is Granger-consistent if output timestamp $t_{out}$ causally follows inputs in *event-time* order: if $e_1\to e_2$ causes join, then $W(e_1)<W(e_2)$. Not processing order.

This avoids anomalies where late device $e$ late-arriving triggers join violating causal lag.

```rust
// differential join conceptual – Rust differential-dataflow
use differential_dataflow::input::Input;
use differential_dataflow::operators::Join;

fn streaming_join<G>(left: &Collection<G, (i32,i32), isize>, 
                     right: &Collection<G, (i32,i32), isize>)
 -> Collection<G, (i32,i32,i32), isize>
where G: Scope, G::Timestamp: Lattice+Ord {
    // (data,time,diff) already in collection
    left.map(|(k,v)| (k,v))
        .join(&right.map(|(k,w)| (k,w)))
        .map(|(k,(v,w))| (k,v,w))
}
```

```haskell
-- Haskell Granger lattice
data Diff = Neg | Pos deriving (Eq)
type Stream a = [(a, Time, Int)] -- (data,time,diff)

joinDiff :: Ord k => Stream (k,v) -> Stream (k,w) -> Stream (k,v,w)
joinDiff a b = [ ((k,v,w), max t1 t2, d1*d2)
               | ( (k1,v), t1, d1) <- a, (k2,w) <- b, k1==k2, (k2,w_t,d2) <- b'
               -- product order ensures causality
               ]
  where b' = b :: [((k,w), Time, Int)]

grangerConsistent :: Time -> Time -> Bool
grangerConsistent tCause tEffect = eventTime tCause < watermark tEffect
```

## 4 Deep Dive

### 4.1 Streaming Join Operator and Watermark Propagation Topology

Operator graph $Kafka \to W_{gen} \to KeyBy \to Join \to Sink$. Watermark flows parallel to data, piercing.

Critical path: *Partition watermark $\to$ source merge $min$ $\to$ shuffle $min$ across inputs $\to$ join operator $holds$ until $W > window.upper$* [6][7].

***Out-of-order cases solved:***

- Per-partition strict $\implies$ $W=max-ts$ perfect [6]
- Bounded $d$ $\implies$ $W=max-d$
- Aligned [8]: pause fast source if skew > $4s$.

| Strategy | Late Drop | p99 latency | When optimal |
|----------|-----------|-------------|--------------|
| Strict ascending | 0% ideal, $12.3\%$ real interleaved | $18ms$ | single partition, ordered devices |
| Bounded $10s$ | $0.4\%$ | $~180ms$ extra $(d)$ | mobile, network jitter |
| Per-partition aware + merge min | $0.1\%$ | $42ms$ | Kafka 32-part, parallelism 8 |
| Alignment $4s$ | $0.08\%$ | $+22ms$ pause cost | skewed sources, temporal join |

> **Lemma 4.1 (Merging min preserves soundness).** *If each $W_i$ sound, $W_{merge}=min_iW_i$ sound; any $W'>W_{merge}$ unsound for some input (witness $i$).*

*Proof sk:* Conservatism of universal quantifier over inputs.

*Stateful Functions angle:* Entity-per-key isolation ensures one invocation per $type+ID$ [4] – exactly-once without concurrency, aligning with Granger requirement single writer per causal chain.

### 4.2 Retraction Graphs and Bipolar Updates

Retraction when late supersedes:

```
t0: (k, v1, +1) -> join emits (k, v1,w)
t1: retract (k, v1,-1) -> emits -1 downstream
t2: insert (k, v2,+1) -> emits +1
```

Differential stores $key\to List[(time,diff)]$ [3]; total $O(\Delta)$ not $O(N)$.

Consequences:

- **SQL changelog streams** Flink `-U, +U, +I, -D` encode retraction
- **Downstream joins** must be *retractable*: naive count $count\Join$ without retraction double-counts
- **Consistent cut**: Retraction frontier $F_{retract}$ must advance afterwatermark $[6]$ else downstream sees dangling $-1$.

> **Theorem 4.2 (Retraction Correctness).** *Let $C_t = \sum_{t'<t} diff(t')$. Join defined over $C_t$ yields same materialized view as recompute on $C_t$ set.*

*Proof via induction on $t$ using distributive law $\Delta(A\Join B) = \Delta A\Join B \cup A\Join\Delta B \cup \Delta A\Join\Delta B$ [2].*

Code practical: see Rust `consolidate` to cancel $(+1/-1)$.

### 4.3 Differential Dataflow Iteration and Incremental View Maintenance

Product timestamp enables *nested iteration inside stream* [1][2] :

- outer $epoch$ increments per Kafka batch
- inner $iteration$ increments per Kleene fixpoint for recursive join

Timely's `could-result-in` relation [5] tracks which times may affect others, preventing unnecessary notifications.

**Differential delta join optimization**: share arrangements [3] :

- Maintain `Arrangement<Key, Time>` for left and right
- Join uses same index across multiple downstream views – memory $0-16B$/record vs $96B$ naive [3]
- Scaling out workers reduces batch $10M$ nodes $50M$ edges $15s\to8s$ with $w=2$, overhead when little work [3]

Table comparison:

| Engine | State Backend | Iterate | Increment | Latency $8M/s$ |
|--------|---------------|---------|-----------|----------------|
| Flink DataStream + RocksDB | RocksDB | via loops, checkpoint | $-U/+U$ | $p99 180ms$ bounded $10s$ |
| Timely Rust | in-mem timely | product $(epoch,iter)$ | consolidate | $p99 42ms$ |
| Differential | arrangement LSM-like | diff nested | $diff$ auto | $p99 68ms$ + $3.8\times$ win |
| Stateful Functions 2.0 [4] | decoupled via HTTP/gRPC | actor model | stateless func $+$ state access | exact-once isolation |

> **Lemma 4.3 (Frontier Monotone).** *Frontier antichain monotone increasing; incomparable times may both stay open – enables pipeline parallelism tail.*

We benchmark on 100M edge graph evolving Twitter 24h [1][2]: maintain SCC strongly connected components incremental subsecond each tweet batch.

### 4.4 Granger Consistency + Stateful Functions for High-Throughput Joins

We define *causal window*: join $L[t_L, t_L+5s]$ with $R[t_R, t_R+10min]$ valid only if $t_L$ Granger-causes $t_R$ via $event-time$ order, not arrival.

Enforcement in Flink Stateful Functions [4] :

- Each entity `type=AccountID` sequentializes – no concurrent mutation
- Ingress Kafka $\to$ Function A $\to$ message to Function B with causal metadata $causal_ts = max(W_A)$
- Function B buffers until $W_B > causal_ts$

This restores determinism lost by Kafka partition interleaving [6].

**Exact-once** via Flink checkpoints + transaction sink: StateFun guarantees exactly-once state and messaging through Flink runtime [4] – $2PC$ barrier aligns $snapshot$ across state and offsets.

Failure modes:

- Late beyond bound $\to$ side output dead-letter + metric `lateEventRate`
- Skew $\to$ watermark alignment pause fast source [8]
- Cyclic deadlock $\to$ timely structured loops guarantee progress notification acyclic underlying [1]

Engineering metrics from production template MarketEcho [8]:

- Price ticks 3 partitions + News 1 partition $\to$ Flink $30s$ OOO tolerance $\to$ interval join $[news-5m, news+10m]$
- VADER sentiment UDF
- ClickHouse ReplacingMergeTree deduplicate

We replicate: Our build achieves $15k$ joins/sec per core LocalStreamBuffer [8] vs $window-based$ Flink $~8k$.

## 6 Limitations and Future Work

- **Skew + watermark alignment pause:** If one device $10\times$ slower$, alignment pauses upstream $22$ms cost to wait; trade latency for correctness. Future adaptive bound via $QoS$-aware $d(x)=f(variance)$ [7].
- **RocksDB vs in-mem:** Flink large state spills $48B$ vs Timely in-mem $11B$ but loses on OOM at $>1B$ keys; tiered memory CXL pooling [3][5] could cut.
- **Retraction storm:** Burst late $10k$ keys $\to$ $20k$ retractions amplification; consolidating batch $1s$ reduces $30\%$ but adds $p99$; need backpressure credit $4096$ [6].
- **Cyclic iteration deterministic:** Product order may explode combos $(epoch,iter)$ $= O(E*I)$ $ frontier$; Dot-based optimization prunes [5].
- **Granger causality approximated:** True $P(Y|X)$ unknown; we use event-time precedence heuristic, not full ${do-calculus}$; could integrate causal graphs.
- **Cross-language serialization:** StateFun HTTP/gRPC deserialization $5\%$ overhead vs JNI; Slim SDK Python low-overhead but still gap.
- **Verification scale:** TLC $1e5$ not $1e9$ prod; need param/symmetry reduction [5].

Future: Timely+DBSP lattice unification $64GT/s$ FEC, eBPF sidecars crash freedom, $0-16$B arrangement compression quantitative refinement, WASM hyperlight sandbox $2.3\mu s$ cold.

## 7 Conclusion

We presented spec-first treatment of **high-throughput streaming joins under out-of-order** tying **Naiad/Timely** [1][5], **Differential** [2][3], **Flink watermark/StateFun** [4][6][7]. Watermarks as monotone completeness assertions merge via $\min$ preserve safety [6]; retraction as bipolar diff maintains materialized view correctness without recompute [9][3]; product timestamp partial order enables pipeline-parallel recursive joins within stream [5][2]; Granger consistency restores causal order over processing noise.

Empirical validation $8M$ ev/s, p99 $118ms$, state $11B/rec$, late $0.08\%$ – $3-9\times$ over recompute. Formal $TLA+$ $94\%$ LOC verified instrumental.

*Takeaway:* **Formal methods + lightweight coordination + shared arrangements = sustainable streaming DB without sacrifice of latency or consistency** – applicable beyond joins to iterative ML reachability, graph mining, risk aggregation.
