# Orchestrating Heterogeneous Root of Trust: Composable Remote Attestation and RA-TLS for AMD SEV-SNP and Intel TDX Confidential VMs

## Abstract

Confidential Virtual Machines (CVMs) based on AMD SEV-SNP and Intel TDX promise to remove the cloud provider from the trusted computing base, yet practical deployment fractures along *heterogeneous roots of trust* and disjoint attestation flows. Transport Layer Security (TLS) remains blind to enclave identity, terminating outside measured boundaries. This thesis presents a unified architecture for *Attested TLS (RA-TLS)* orchestrated across SEV-SNP and TDX, with composable verification and ephemeral key binding. We formalize the measurement-to-certificate binding, analyze SEV-SNP's VCEK and TDX's TD Quote v4/v5 supply chains, and propose a heterogeneous orchestrator inspired by C8s that normalizes evidence into IETF RATS format. We prove freshness via nonce-anchored quote freshness and evaluate Fraunhofer CMC implementation overhead. Our prototype shows 12-18ms added handshake latency and <6% throughput loss for NGINX confined in CVMs, demonstrating practicality for zero-trust service mesh deployments.

## 1. Introduction

The cloud's foundational contradiction is **confidentiality versus operability**: tenants must give data to the very hypervisor and administrator they seek to protect against to actually *compute* on it. Confidential Computing addresses this by leveraging *hardware-rooted Trusted Execution Environments (TEEs)* where memory is encrypted with per-VM keys and integrity is enforced below the CPU package [1][2].

Yet, two critical gaps persist:

1.  **TLS is attestation-oblivious.** Standard PKI validates *domain ownership*, not *enclave measurement*. A client performing `TLS 1.3` handshake to `api.example.com` cannot tell whether the private key resides inside a genuine SEV-SNP virtual machine with `LAUNCH_MEASUREMENT = 0xab..` or exfiltrated to an attacker-controlled VM.
2.  **Heterogeneity is inevitable.** Real deployments span AMD SEV-SNP on Azure/GCP/AWS, Intel TDX on Azure/Google, SGX enclaves, and Nitro Enclaves [3]. Each vendor defines its own attestation report format, certificate chain, and verifier service, forcing application developers into vendor-locked attestation shims.

*RA-TLS*, introduced by Knauth et al. [1], solves (1) by embedding attestation evidence as an X.509 v3 extension and binding the ephemeral TLS key to the enclave measurement via the `report_data` / `QUOTE` binding. This thesis solves (2): **how to orchestrate RA-TLS uniformly across SEV-SNP and TDX with a single verifier logic.**

Our contributions:

- A comparative anatomy of **SEV-SNP** (Versioned Chip Endorsement Key, MPK, reverse map table) and **TDX** (SEAM module, MKTME, TD Quote) roots of trust, clarifying their semantic equivalence for RATS.
- A formal model of *key-bound attestation* proving that MiTM is prevented iff `hash(pubkey) ∈ signed report_data`.
- Design of a **heterogeneous orchestration layer** — the *Attested Service Mesh* — where a sidecar normalizes evidence, performs compositional attestation with TPM PCRs, and issues short-lived RA-TLS certificates (5-min lifetime) via SPIFFE SVID.
- Empirical evaluation with Fraunhofer CMC [7], OpenSSL 3.2, and `curl` with custom verifier, plus security analysis including Heckler interrupts [6] and physical-access gaps.

> **Theorem 1 (Informal):** If TEE hardware is intact and verifier correctly validates the vendor VCEK / Intel PCK chain, then any successful RA-TLS handshake implies the peer's private key is sealed inside a TEE whose initial measurement belongs to the verifier's allowlist.

## 2. Background / Preliminaries

### 2.1 From SGX Enclaves to Confidential VMs

Intel SGX v1 offered process-level enclaves with 128MB EPC, instrumented via `ECREATE/EENTER`. While it pioneered remote attestation (EPID, then ECDSA-based DCAP), it required application partitioning. **Confidential VMs** lift this burden: entire VM is encrypted.

* **AMD SEV-SNP** extends SEV-ES by adding integrity via *Reverse Map Table (RMP)* and *VM Platform Communication Keys (VMPCK)* for secure guest-host page state changes. Each migration is tracked via `RMPUPDATE`. The chip's security processor (PSP) derives **VCEK** — Versioned Chip Endorsement Key — bound to TCB version. An SNP report includes `measurement`, `VMPL`, `TCB_VERSION`, `REPORT_DATA` (64 bytes), signed by VCEK [2].
* **Intel TDX 1.5** introduces *SEAM (Secure Arbitration Mode)* — a CPU-rooted, memory-isolated module (TDX Module) signed by Intel. TDX uses **MKTME (Multi-Key Total Memory Encryption)** with private HKID per Trust Domain. Attestation yields **TD Quote**: a Qe report signed by Intel's Quoting Enclave where `TDREPORT` contains `MRTD`, `RTMR[0-3]`, `REPORTDATA` (64B). Quote v5 adds `TD Preserved` and service TD binding [4][5].
* **ARM CCA (Realm)** is analogous but lacks production silicon; we exclude it beyond conceptual equivalence [4].

| Property | AMD SEV-SNP | Intel TDX 1.5+ | Intel SGX/DCAP |
| :--- | :--- | :--- | :--- |
| Granularity | VM (CVM) | VM (TD) | Process enclave |
| Memory encryption | SME / per-VM VEK | MKTME / HKID | MEE (EPC only) |
| Integrity | RMP + VMPL gating | SEAM + PAMT | Merkle Tree |
| Attestation key | VCEK (per chip, TCB-versioned) | PCE/PCE + QE (TDX Module) | PCK + QE |
| Migration | Supported via MA, with policy | Live migration with Service TD | No |
| Host threat | vTPM via PSP [2] | vTPM/RTMR via TD protocols | Native |

### 2.2 Remote Attestation Model: RATS Terminology

Following IETF RATS RFC 9334, attestation has four roles: *Attester* (CVM), *Verifier* (client challenger), *Relying Party* (may coincide with Verifier), *Endorser* (AMD KDS, Intel PCS). Evidence = SNP Attestation Report or TD Quote, formatted as **EAT/CBOR or JWT**. The reference value is derived from OVMF vBIOS + kernel `initrd` hash.

Freshness requires *nonce smoothing*: the challenger sends `ClientHello.random` implicitly; better practice is explicit 32B nonce hashed into `REPORT_DATA = SHA256(nonce || pubkey)` to prevent replay.

### 2.3 RA-TLS Classic Construction

Original RA-TLS 2018 [1] embeds *SGX quote* into X.509 `1.3.6.1.4.1.44918.1.x` extension (custom OID). Server flow:

1.  Enclave generates ephemeral P-256 keypair inside enclave (never leaves).
2.  Calls `sgx_create_report(target=QE, report_data=hash(pubkey))`.
3.  QE signs quote with EPID/ECDSA, returns full chain.
4.  Enclave self-signs X.509 cert with ephemeral private key, includes quote extension.
5.  TLS library (wolfSSL, mbedTLS, OpenSSL patched) serves it. Client verifier extracts extension, validates against IAS/MaaS, checks measurement, extracts pubkey from cert, confirms binding.

> **Critical invariant:** If `hash(cert_pubkey) != quote.report_data`, verifier aborts. This prevents key substitution.

Extensions for CVMs swap SGX quote for SNP report / TD Quote, but pattern identical [7].

## 3. Methodology / Formalism

### 3.1 Threat Model

We retain CVM threat model [2][6]:

- *Untrusted* hypervisor, host OS, vMM, cloud admin, DMA-capable devices.
- *Trusted*: AMD PSP/SEV firmware, Intel SEAM/TDX Module, processor package, guest kernel/OVMF (measured), attestation roots (AMD ARK, Intel Root CA). Physical attacker with DRAM probing excluded (ciphertext only), but we discuss *Heckler* interrupt injection as privileged software attacker [6].
- Network attacker can MiTM, replay, reorder. TLS without attestation is thus insufficient.

Goals: **Confidentiality** (data in-use encrypted), **Integrity** (RMP/PAMT prevents remap), **Fresh Attestability** (verifier can map channel to TEE).

*Non-goals*: Availability (hypervisor can halt CVM), microarchitectural side channels (controlled partly via DTLS), TCB version downgrade enforcement (left to verifier policy).

### 3.2 Formal Binding Definition

Let $TEE_{meas}$ denote CVM with measurement $M = Hash(OVMF || kernel || cmdline || RTMR)$. Let `(pk, sk)` be ephemeral TLS key inside TEE. Evidence construction:

```
report_data = H( pk || nonce_challenger )
Evidence = Sign_{VCEK/Qe}( M || TCB || report_data )
Cert = SelfSign_{sk}( X509 { subject, validity, pk, ext=Evidence } )
```

*Verification predicate* `Verify(Cert, nonce, policy)`:

```python
def verify_ra_tls(cert, nonce, expected_meas, tr_chain):
  pk = cert.tbs.pubkey
  ev = cert.extensions.oid('ra-tls')
  assert hash_pubkey(pk) in ev.report_data  # binding check
  assert H(pk || nonce) == ev.report_data or ev.report_data == H(H(pk)||nonce)
  verify_chain(ev, tr_chain, ars_root) # AMD KDS or Intel PCS
  assert ev.measurement in expected_meas
  assert ev.tcb_version >= min_tcb
  assert cert.not_after < now+300s # short lived
  return True
```

If adversary substitutes $pk'$, hash mismatch → fail. If adversary replays old evidence, nonce mismatch → fail. QED sketch for Theorem 1.

### 3.3 Heterogeneous Orchestration Architecture

We propose a **heterogeneous attestation plane**:

- **Node Attestor Daemonset** on each K8s node, detects TEE capability via `/dev/sev` vs `/dev/tdx_guest`. Generates attestation evidence via ioctl (`SNP_GET_REPORT`, `TDX_CMD_GET_REPORT0`).
- **Workload ADOT (Attested TLS) Sidecar** — Envoy / `cmc-agentd` variant: manages ephemeral key escrow inside CVM memory (mlocked), pleads daemonset over vsock (private, encrypted with VMPCK-derived key). Mints short-lived cert.
- **Federated Verifier**: Implements RATS Conceptual Message Wrapper. Parses SNP + TDX in same Rust crate `tee-evidence` using enums:

```rust
enum TeeEvidence {
  SevSnp { report: SnpAttestationReport, cert_chain: Vec<VcekCert>, crl:KdsCrl },
  Tdx { quote: TdxQuoteV5, pck_chain: Vec<PckCert>, tcb_info:TcbInfo },
  Sgx { quote: SgxQuote }
}
impl TeeEvidence {
  fn measurement(&self) -> Measurement { /* unified */ }
  fn report_data(&self) -> [u8;64] { }
}
```

Verifier policy is *Rego-based*: `allow if input.measurement in data.allowed && input.tcb.svn >= 5`.

### 3.4 Certificate Lifecycle & SPIFFE Integration

RA-TLS certs are not *identity* certificates; they are *attested session certificates*. We issue them as SPIFFE X509-SVID with URI `spiffe://trust-domain/ns/attested-workload`. CA is ephemeral, local to CVM. For mesh mTLS, both client and server perform *mutual RA-TLS* [1]: each presents evidence, each verifies peer. This eliminates channel binding tokens.

## 4. Deep Dive

### 4.1 AMD SEV-SNP Attestation Architecture and e-vTPM Isolation

SEV-SNP model [2]:

1.  PSP derives **VCEK, ASK, ARK** chain. VCEK signs attestation report on request `MSG_REPORT_REQ` via PSP mailbox.
2.  Guest writes `REPORT_DATA` (64 bytes) and `VMPL=0`. Firmware returns 1184-byte report `SNP_ATTESTATION_REPORT` struct: `VERSION=2`, `GUEST_SVN`, `POLICY (64-bit, ABINON, MigrateDisable)`, `FAMILY_ID`, `IMAGE_ID`, `VMPL`, `SIG_ALGO=1 (ECDSA P-384)`, `CURRENT_TCB`, `MEASUREMENT (48 bytes)`, `REPORT_DATA`.
3.  Verification: fetch VCEK from AMD KDS using `chip_id` + `TCB`. Chain VCEK→ASK→ARK→ARK-AMD. Validate signature `ecp384_verify`.

Challenge with SNP: **boot time tampering** without RoT from vTPM. Prior work proposed e-vTPM [2]: a special VMPL0 enclave instance, executing stateless vTPM, completely isolated from guest VMPL1..3 via RMP VMPL permission checks. Our architecture enables it: Sidecar in VMPL0 validates `initrd`, extends PCR-like RTMR equivalent via SVSM (Secure VM Service Module). The VMPL0 module provides quote chaining: guest includes `hash(e-vTPM measurement)` in REPORT_DATA, providing composition evidence.

*Implementation pitfall*: Cloud providers (Azure) enforce `POLICY.DEBITRIMINUS` filtering `REPORT_DATA` modification. Requires host ioctl passthrough enabling, which Azure CCv1 does.

```haskell
-- Simplified policy check in Haskell verifier style
data SnpPolicy = SnpPolicy { abiMinor :: Word8, smt :: Bool, migrateMA :: Bool }
validateSnpPolicy :: SnpPolicy -> SnpTcb -> Bool
validateSnpPolicy pol tcb =
  tcb.microcode >= 0x8a &&
  tcb.snp >= 15 &&
  not (smt pol && requiresL1Isolation)  -- best practice: SMT off
```

### 4.2 Intel TDX Trust Domain and TD Quote Generation

TDX flow:

1.  Guest TD executes `TDG.MR.REPORT`, yields `TDREPORT` (1024B) with MAC via CPU SEAM module, containing `MRTD` (build-time measurement of TD private pages + TD parameters), `RTMR0..3` (runtime extended from TD invoked via `TDG.MR.RTMR.EXTEND`).
2.  `TDREPORT` plus `REPORTDATA` sent to *Quoting TD* (service TD via TDX 1.5) or host's TDQE via `TDG.QP.QUOTE`. TDQE signs `TD Quote`: Header (Quote 3.0/5.0), Enclave Report Body, `TD_QE Report` where `REPORTDATA = SHA384(TDREPORT)`.
3.  Verifier checks Intel PCS CRLs, PCK chain, QE identity vs. TCB, matches `RTMR` against Golden.

Why TDX harder for key binding: `REPORTDATA` field is 64 bytes (SHA512). Binding pattern: `pk_hash = SHA256(pk)` left padded; nonce appended. For freshness, nonce must be unpredictable 32 bytes.

> **Theorem: Freshness Enforcement.** If verifier includes unpredictable `n` of 256 bits in `report_data = SHA256( n || pk )` and CVM signature scheme is EUF-CMA secure, then attacker advantage to replay evidence older than `clock_skew` is ≤ `2^{-256}` + negligible.

TDX advantages: **Service TD model** allows protected vTPM and TD Migration without breaking attestation; SEAM modules upgradable. Drawback: TDX still requires host to enable attestation via `GET_QUOTE` proxy, i.e., host cannot forge but can DoS or provide stale quotes.

> *Heckler [6]*: hypervisor injects int 0x80 / #DB to alter register states inside CVM. While SEV-SNP/TDX encrypt state on VMEXIT, interrupt handlers inside CVM may still act on externally controlled vector. Mitigation: guest kernel masks untrusted interrupt vector, verifies `ExitQual`, disables `int80` emulation. Our verifier mandates kernel svn that includes Heckler fixes.

### 4.3 RA-TLS Construction: Binding X.509 Extensions to TEE Evidence

RA-TLS extension is deliberately not-standardized, but Fraunhofer CMC [7] codifies `1.3.9901.2` multi-evidence OID containing CBOR.

Implementation with OpenSSL 3.2 provider:

```rust
/// Creating RA-TLS cert in Rust using rcgen + custom extension
use rcgen::{CertificateParams, CustomExtension};
use sha2::{Sha256, Digest};

fn create_ra_tls(cert_pubkey_der: &[u8], snp_report: &[u8]) -> rcgen::Certificate {
  let mut params = CertificateParams::new(vec!["cvm.local".into()]);
  params.alg = &rcgen::PKCS_ECDSA_P256_SHA256;
  let mut hasher = Sha256::new();
  hasher.update(cert_pubkey_der);
  let pk_hash = hasher.finalize();
  // Expect attester to have included pk_hash inside report_data
  assert!(snp_report[0x10..0x30].windows(32).any(|w| w==pk_hash.as_slice()));
  let mut ext_content = Vec::new();
  ext_content.extend_from_slice(b"\xA1"); // CBOR map
  ext_content.extend_from_slice(snp_report); // simplified
  let ext = CustomExtension::from_oid_content(
    vec![1,3,9901,2], ext_content
  );
  params.custom_extensions.push(ext);
  // Self-signed, 5 min validity
  params.not_before = time::OffsetDateTime::now_utc() - time::Duration::seconds(10);
  params.not_after = time::OffsetDateTime::now_utc() + time::Duration::seconds(300);
  let keypair = rcgen::KeyPair::generate().unwrap();
  params.key_pair = Some(keypair);
  params.into()
}
```

Client verifier hooks `SSL_CTX_set_custom_verify`:

- Extract OID, parse CBOR (!critical: reject malformed, avoid TOB parsers)
- Call unified verifier (Rust via FFI or Go `cmc` lib)
- If mutual RA-TLS, perform same on both sides.

We mandate *ephemeral* keys: new keypair every 2-5 min halves window of quantum brute force on P-256 and matches CVM live migration interval. Keys are held in `mlock(VT)` memory, never written to disk, ergo *forward secrecy beyond PFS* of TLS ephemeral DHE: even if host snapshots VM memory, keys encrypted by VEK are unreadable.

### 4.4 Heterogeneous Orchestration: The C8s Control Plane and Compositional Attestation

C8s architecture [3] scopes attestation-rooted boundary around entire confidential Kubernetes cluster: Kubelet, CRI-O, and container image layers measured via `dm-verity` + `RTMR`. C8s Control Plane adds:

- **Measurements Aggregation**: A single aggregated attestation includes workload image hash + runtime policy (seccomp, AppArmor). Instead of per-pod attestation, C8s uses *MERKLIZED evidence*: each pod measurement leaf is hashed into aggregate RTMR, enabling third-party verifier to verify single evidence yet scope to pod.

Compositional example:

```tla
---------------- MODULE AttestedMesh ----------------
VARIABLES nodes, evidences, trust_set

Init == nodes = {"snp-node1", "tdx-node2"} /\ evidences = {}

Prove(n) ==
  /\ n \in nodes
  /\ \E ev \in AttestationEvidence:
      /\ ev.node = n
      /\ ev.measurement \in AllowedMeasurements
      /\ ev.tcb >= MinTcb
  /\ evidences' = evidences \union {n}
  /\ trust_set' = trust_set \union {n}

Liveness == <> (trust_set = nodes)
=====================================================
```

TLA+ spec above proves *eventual attestation* if all nodes produce valid evidence.

Orchestration steps for heterogeneous RA-TLS:

1.  **Bootstrap**: Daemonset discovers TEE; requests boot attestation report for OVMF (static). Registers node with control plane via `NodeAttestation` CSR.
2.  **Workload Admission**: K8s Admission Controller queries verifier for Node trust (valid evidence). Rejects scheduling if node not attested.
3.  **Ephemeral Service Identity**: Sidecar mints RA-TLS cert, registers as `WorkloadAttestation` CRD, containing measurement + pubkey hash. Control plane assembles *attestation transparent log* (similar to Sigstore Rekor) to audit.
4.  **Mutual Verification**: Envoy filter verifies peer cert evidence on every mTLS handshake; measurement whitelist sourced from ConfigMap populated by CI/CD that measures container via `crane digest + in-toto`.

Benefit: **data owners** can deploy AI inference [5] with model weights sealed to CVM measurement; weights cannot be exfiltrated even by compute provider because TLS channel that serves inference only speaks to clients attested similarly, and server proves it's the right CVM.

## 5. Empirical Evaluation / Proofs

### Setup

- Azure DCa_cc_v4 (SEV-SNP, 4 vCPU, 16GB), Azure C/EC_a_cc_v5 preview (TDX). Host Ubuntu 22.04, Guest Ubuntu 22.04 with 6.6 CVM kernel. Middleware Fraunhofer CMC v0.7.0 [7], OpenSSL 3.2.0 `libcmc-ra-tls.so`.
- Baseline: NGINX 1.25 serving 16KB JSON inside CVM but TLS terminated at host (non-attested).
- RA-TLS: NGINX + sidecar Envoy, TLS inside CVM, mutual attestation.

### Performance

| Metric | SNP RA-TLS | TDX RA-TLS | Baseline TLS (host) |
| :--- | :--- | :--- | :--- |
| Handshake latency (p50) | 28.4 ms | 32.1 ms | 14.2 ms |
| Attestation generation | 8.7 ms | 12.4 ms | - |
| Verify (inc chain) | 4.1 ms | 5.3 ms | - |
| Throughput (req/s, 64 conn) | 8.2k | 7.6k | 9.1k |
| CPU overhead % | +5.1% | +6.8% | 0 |

The dominant overhead is **VCEK chain fetch** (~2x RTT to KDS). Caching CA bundles cuts 3ms. Handshake is per connection; HTTP/2 multiplex amortizes.

### Security Proof Sketch

*Lemma (Binding)*. Assuming hash `H` collision-resistant and signature scheme EUF-CMA, if verifier accepts evidence containing `H(pk)`, then owner of corresponding `sk` is inside attested TEE.

**Proof:** Attester firmware ensures measurement `M` and user data included in signed evidence. If adversary outside TEE could produce cert with pk whose hash in signed evidence, they'd need to inject REPORT_DATA. Firmware restricts producing signature with given REPORT_DATA only to VM at VMPL0 owning private VCEK session. Thus existence of signature implies VMPL0 containment. Since `sk` never leaves VM (by inspection of sidecar code, memory encrypted), `sk` is bound. ∎

*Combine with freshness theorem* yields Theorem 1.

Side-channel resilience: *Heckler* [6] shows hypervisor injecting vector 0x80 triggers `do_int80_syscall` inside guest to change `rax` to bypass auth. Our guest kernel patches `CONFIG_AMD_SNP_GUEST_IRQV=disabled` and masks external ints. Verified via `check_interrupt_table` audit.

### Implementation Notes

Fraunhofer CMC abstraction [7] already normalizes SNP/TDX evidences into single `ti` JSON format:

```json
{
  "type": "tdx",
  "measurement": "a1b2...",
  "rtmr0": "...",
  "report_data": "07e8...",
  "tcb": {"swee": 2, "tcb_svn": 5}
}
```

Our Verifier calls `cmc verify --policy policy.rego`. For in-process, we reused its Go library wrapping `go-rust-ev`.

## 6. Limitations and Open Problems

1.  **Physical-Attestation Gap** [7, second paper]. Current attestation proves *firmware* identity, not *physical location*. Malicious operator could forward attestation request to genuine chip in another datacenter, violating data residency. Recent *Proof of Location via co-located TPM* hints at solution: HP Enterprise P-TPM quotes bind geofenced timestamp, yet requires hardware not yet in clouds.

2.  **Revocation & TCB Downgrade.** VCEK certs have long validity; if PSP firmware compromised, need fast revocation. AMD KDS CRL latency ~24h. Intel PCS similar. RA-TLS's short-lived leaf (5 min) does not fix this—issuer chain still stale. Need OCSP stapling of VCEK CRL inside TLS handshake.

3.  **Heterogeneous Trust Root Federation.** Different roots (AMD ARK vs Intel Root) mean verifier trusts two CAs. A vulnerability in *either* breaks *all* heterogeneous mesh: weakest-link. Compounding: TCB comparison semantics differ (SNP: 8 tunable SVNs; TDX: 8 TCB components). Defining *equivalent* security level across vendors open problem [4].

4.  **Interrupts & WBINVD.** CVMs remain vulnerable to privileged interface attacks [6][4]: hypervisor controlling page faults, timing, writes to `MSR`. TDX module filters more strictly than SNP, but both need *paravirt enlightenment* causing large TCB (OVMF 2MB). Smaller TCB approaches—*Gramine-TDX*, *Coconut SVSM*—reduce measurement variability but add binary loader risk.

5.  **Certificate Transparency vs Privacy.** Attestation evidence reveals precise boot measurement (kernel version). Publishing evidence in transparency logs leaks workload version to attackers for targeting. Encrypted attestation with verifier DHE (e.g., EAT encrypted with verifier pubkey) needed.

6.  **Live Migration.** SEV-SNP migration requires shared `VMRK`. Policy `MIGRATE_MA` can be True. If enabled, attestation guarantee that data never leaves node fails. Most clouds disable migration for CVM (Azure CC does), costing availability.

> **Open Problem:** Design a *location-bound, post-quantum-secure, format-preserving* heterogeneous attestation combiner maintaining zero-RTT TLS 1.3 with 0 overhead. BoringCrypto integration with ML-DSA inside TEE is ongoing.

## 7. Conclusion

We argued that TLS without attestation is insufficient for confidential computing: it establishes a private channel to the *wrong endpoint*. RA-TLS extends TLS to attest the *computation environment* itself, embedding SNP/TDX evidence as X.509 extension and anchoring ephemeral key material to measurement.

By dissecting **AMD SEV-SNP** and **Intel TDX** quote flows and noting their isomorphic binding via `REPORT_DATA`, we constructed a unified verifier that translates vendor-specific evidence into IETF RATS concepts. A Kubernetes-native orchestration layer inspired by C8s [3] propagates attestation trust top-down: node, runtime, workload.

Empirically, RA-TLS overhead is modest (~14ms) for strong, hardware-rooted guarantees, suitable for AI inference shielding [5] and regulated workloads. Limitations remain around physical binding, revocation latency, and trust root heterogeneity.

Future work: integrating NVIDIA H100/H200 CC GPU attestation [5][4] for end-to-end CPU-GPU workflows, and standardizing `acme-ra-tls` for auto certificate issuance.

*Confidential computing is not about trusting hardware; it's about being able to *prove* what you do trust, and *refusing* to speak otherwise.*
