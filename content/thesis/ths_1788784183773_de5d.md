# WebGPU and the wgpu Rendering Pipeline: Render Bundles, Bind Groups, and Cross-API Shader Translation

## Abstract

WebGPU re-imagines GPU programming for the web as an *explicit*, *portable*, and *validation-first* API, discarding the implicit state machine of WebGL in favor of command encoders, immutable pipeline objects, and statically-checked resource binding. This thesis presents a deep technical analysis of the **wgpu** rendering pipeline, the Rust implementation of WebGPU that powers Firefox, Bevy, and a growing ecosystem of native applications. We study three load-bearing abstractions in detail: (i) **render bundles**, pre-recorded sequences of render commands that can be replayed across frames to amortize CPU-side encoding cost; (ii) **bind groups**, the resource-binding abstraction that reconciles the divergent descriptor models of Vulkan, Direct3D 12, and Metal behind a single portable interface; and (iii) **cross-API shader translation** via **naga**, a single-intermediate-representation compiler that parses WGSL, GLSL, and SPIR-V and emits SPIR-V, MSL, HLSL, GLSL, and WGSL. We quantify bundle encoding amortization, formalize a replay-determinism theorem, and characterize binding-model lowering. We close by identifying the residual portability hazards — driver-defined limits, shader-translation feature lag, and validation gaps —.

---

## 1. Introduction

The history of graphics programming on the web is a history of narrowing abstraction. OpenGL ES, exposed through WebGL 1.0 (2011) and WebGL 2.0 (2017), presented a single global state machine: bind a texture, set a uniform, issue a draw, and trust the driver to serialize the resulting hazard graph correctly. First, *driver magic* — the implicit synchronization and state validation performed by OpenGL drivers — accounted for a large fraction of CPU time in draw-call-heavy workloads and was a perennial source of cross-vendor behavioral divergence. Second, the web's security model demanded validation of every GPU operation, yet OpenGL's imperative style scattered validation checks across thousands of entry points, enlarging the attack surface of the browser's GPU process.

The native graphics world had already moved on. Metal (2014), Direct3D 12 (2015), and Vulkan (2016) converged on a new consensus: **explicit APIs** in which the application, not the driver, owns command-buffer construction, resource lifetime, and synchronization.

**WebGPU** is the web's answer to this consensus.  Two production implementations anchor the ecosystem: **Dawn**, Google's C++ implementation used by Chromium and backed by the **Tint** shader compiler [8], and **wgpu**, the Rust implementation maintained by the gfx-rs community and used by Firefox [3].

This thesis dissects the wgpu rendering pipeline along three axes, each corresponding to a distinct portability problem that explicit APIs must solve:

1. **Command encoding amortization** — how do applications avoid paying per-frame CPU cost to re-encode identical command streams? Answer: *render bundles*.
2. **Resource binding portability** — how does one API express descriptor sets (Vulkan), root signatures (D3D12), and argument tables (Metal) simultaneously? Answer: *bind groups*.
3. **Shader language portability** — how does a single WGSL source run on Metal's MSL, D3D12's HLSL, and Vulkan's SPIR-V? Answer: the *naga* shader translator and its single-IR architecture.

Our contributions are as follows: (i) a precise operational account of render bundles grounded in the W3C WebGPU specification [1]; (ii) a formal treatment of bind-group layout compatibility and dynamic-offset addressing; (iii) a comparative analysis of the naga and Tint translation architectures; (iv) a replay-determinism theorem with proof sketch; and (v) a reproducible synthetic microbenchmark quantifying bundle encoding amortization. The remainder of this thesis is organized as follows: §2 surveys background and related work, §3 describes our methodology, §4 presents the deep technical analysis, §5 reports empirical results and formal statements, §6 discusses limitations, and §7 concludes.

## 2. Background and Related Work

### 2.1 From implicit to explicit GPU APIs

The explicit-API revolution rests on a simple observation: the driver cannot efficiently infer what the application already knows.  WebGPU follows suit: a `GPURenderPipeline` is immutable after creation, and draw calls reference it by handle [1].

### 2.2 Pre-recorded command sequences: prior art

The idea of recording a command sequence once and replaying it many times predates WebGPU.  WebGPU's **render bundles** (`GPURenderBundleEncoder` / `GPURenderBundle`) are the web-safe synthesis of these ideas: they may be recorded once, must be *fully validated at encode time*, and are replayed inside a render pass via `executeBundles` [1].

### 2.3 Shader translation ecosystems

Cross-API shading has historically been solved by *transpilation*. Khronos's **glslang** compiles GLSL to SPIR-V; **SPIRV-Cross** lowers SPIR-V to MSL, HLSL, and GLSL; **SPIRV-Tools** optimizes and validates the intermediate form. The WebGPU ecosystem instead converges on *direct* WGSL-to-backend compilers with a shared IR: Google's **Tint** (C++, part of Dawn) and gfx-rs's **naga** (Rust) [5]. Both parse WGSL natively, validate against the WGSL specification [2], and emit backend languages directly, avoiding the SPIR-V round trip entirely on the WGSL path.

### 2.4 WebGPU implementations

Dawn and wgpu share the WebGPU API surface but differ architecturally. Dawn is C++, integrated with Chromium's GPU process, and translates WGSL with Tint. wgpu is layered Rust: `wgpu` (public API) → `wgpu-core` (WebGPU semantics, resource management, validation) → `wgpu-hal` (thin backends for Vulkan, D3D12, Metal, GLES) → `naga` (shader translation) [3].

## 3. Methodology

Our investigation combines *specification archaeology*, *source-code analysis*, and *synthetic experimentation*:

1. **Specification analysis.** We studied the W3C WebGPU Working Draft of 20 September 2021 [1], which documents the render-bundle encoding model (`GPURenderBundleEncoder`), the bind-group and pipeline-layout model, and the normative *rendering algorithm*.

2. **Source inspection.** We analyzed the gfx-rs/wgpu repository's documented architecture (the `wgpu-hal` / `wgpu-core` / `wgpu` / `naga` layering [3]) and the wgpu 23.0.0 changelog [4].

3. **Comparative evaluation.** We compared the Tint and naga translation architectures on maturity, footprint, diagnostics, and integration effort [5], and consulted Chrome's WebGPU release notes for Dawn-side bundle behavior [9].

4. **Synthetic microbenchmark.** We designed a reproducible Python-driven experiment (described in §5) that models CPU-side command-encoding cost with and without render bundles, isolating encoding cost from GPU execution time.

## 4. Deep Dive

### 4.1 Render Bundles: Capture Once, Replay Everywhere

#### 4.1.1 The encoding model

A WebGPU frame is built by a `GPUCommandEncoder`, which spawns *pass encoders* — `GPURenderPassEncoder` for rendering, `GPUComputePassEncoder` for compute. Each pass encoder accumulates state-setting commands (`setPipeline`, `setBindGroup`, `setVertexBuffer`, `setIndexBuffer`, `setViewport`, `setScissorRect`, `setBlendConstant`, `setStencilReference`) and draw commands (`draw`, `drawIndexed`, `drawIndirect`, `drawIndexedIndirect`), and is terminated by `end()` [1]. **Render bundles** break this tax. A `GPURenderBundleEncoder` is created from the device with a descriptor fixing the color/depth formats it is compatible with:

```rust
// wgpu (Rust) — creating and recording a render bundle
let mut bundle_encoder = device.create_render_bundle_encoder(
    &wgpu::RenderBundleEncoderDescriptor {
        label: Some("static-geometry"),
        color_formats: &[Some(surface_format)],
        depth_stencil: None,
        sample_count: 1,
        multiview: None,
    },
);
bundle_encoder.set_pipeline(&render_pipeline);
bundle_encoder.set_bind_group(0, &frame_independent_bind_group, &[]);
bundle_encoder.set_vertex_buffer(0, vertex_buffer.slice(..));
bundle_encoder.draw(0..vertex_count, 0..1);
let bundle = bundle_encoder.finish(&wgpu::RenderBundleDescriptor {
    label: Some("static-geometry"),
});
```

The bundle is replayed each frame with a single call:

```rust
let mut pass = encoder.begin_render_pass(&wgpu::RenderPassDescriptor { /* ... */ });
pass.set_bind_group(1, &per_frame_bind_group, &[]); // dynamic state stays outside
pass.execute_bundles(std::iter::once(&bundle));
pass.end();
```

> **Theorem (Bundle replay determinism).** *Let B be a successfully encoded `GPURenderBundle` and let S₀ be the render-pass state immediately before `executeBundles([B])`. Then executing B is semantically equivalent to issuing B's captured command sequence verbatim from S₀, and this equivalence holds independently of the frame in which replay occurs.*

> **Proof (sketch).** Bundle commands may reference pipelines, bind groups, and buffers, but the encoder captures resource *handles* plus the full render state (pipeline, bind groups, vertex/index buffers, viewport state) rather than deltas against ambient pass state. Re-execution therefore denotes a total function *f_B : State → State* determined solely by the captured sequence. Since the resources referenced by B are required to remain valid for the bundle's lifetime (validation rule: resources used by a bundle must outlive it), *f_B* is frame-independent. ∎

#### 4.1.2 What bundles can and cannot contain

The bundle encoder exposes a *restricted* subset of the render-pass interface: pipeline/binding/buffer state plus draw calls. This restriction is what makes encode-time validation tractable and backend lowering uniform: a bundle is, in effect, a closed term in the render-command language, and each backend (Vulkan secondary command buffers with inheritance info, D3D12 bundles, Metal encoder re-recording) can lower closed terms without consulting per-frame context.

A useful cost model clarifies when bundles win. Let *E* be the CPU cost of encoding one draw's state and command tokens, *R* the cost of replaying one pre-encoded draw, and *N* the number of frames over which the bundle is reused. Direct encoding costs *N·E* per draw; the bundle costs *E + N·R*. The bundle wins whenever:

$$R < E \cdot \frac{N - 1}{N} \approx E \quad \text{for large } N,$$

i.e., essentially whenever replay is cheaper than re-encoding — which holds whenever the implementation caches any validation or translation work at encode time.

#### 4.1.3 Backend lowering strategies

| Implementation | Bundle lowering strategy |
|---|---|
| **wgpu / Vulkan** (`wgpu-hal`) | Secondary command buffers with `VkCommandBufferInheritanceInfo` fixing render-pass compatibility; recorded once, submitted via `vkCmdExecuteCommands` |
| **wgpu / D3D12** | Native `ID3D12GraphicsCommandList` bundles executed with `ExecuteBundle` inside the direct list |
| **wgpu / Metal** | Re-encoded `MTLRenderCommandEncoder` sequences or indirect command buffers, depending on device capability |
| **Dawn / Chromium** | Backend-native equivalents selected per platform; `dump_shaders`-style debug toggles expose the lowered form [9] |

### 4.2 Bind Groups: One Binding Model for Three Native Worlds

#### 4.2.1 The portability problem

The three native APIs disagree profoundly on resource binding:

- **Vulkan** uses *descriptor sets*: numbered sets of typed descriptors, allocated from pools, bound with dynamic offsets; pipeline layouts declare the set/binding/type triple statically.
- **D3D12** uses *root signatures*: a flat parameter space of root constants, root descriptors, and descriptor tables; binding is pointer-heavy and driver-visible.
- **Metal** uses *argument tables* indexed by `[[buffer(n)]]` / `[[texture(n)]]` attributes, with *argument buffers* (tier-2) for indirection.

 WebGPU's answer is the **bind group**: an immutable bundle of resources (buffers, textures, samplers, storage textures, external textures) created against a **`GPUBindGroupLayout`** that declares, per binding index, the resource type and shader-stage visibility [1].

#### 4.2.2 Layouts, compatibility, and the `auto` trap

A `GPUBindGroupLayout` entry specifies `binding` (index), `visibility` (a bitmask of `GPUShaderStage`: `VERTEX`, `FRAGMENT`, `COMPUTE`), and exactly one of `buffer` (`{type: 'uniform'|'storage'|'read-only-storage', hasDynamicOffset, minBindingSize}`), `sampler`, `texture`, or `storageTexture`. 

```rust
// wgpu (Rust) — explicit layout shared across pipelines enables bind-group reuse
let bgl = device.create_bind_group_layout(&wgpu::BindGroupLayoutDescriptor {
    label: Some("frame-uniforms"),
    entries: &[
        wgpu::BindGroupLayoutEntry {
            binding: 0,
            visibility: wgpu::ShaderStages::VERTEX | wgpu::ShaderStages::FRAGMENT,
            ty: wgpu::BindingType::Buffer {
                ty: wgpu::BufferBindingType::Uniform,
                has_dynamic_offset: true,   // per-draw offset supplied at set_bind_group
                min_binding_size: None,
            },
            count: None,
        },
        wgpu::BindGroupLayoutEntry {
            binding: 1,
            visibility: wgpu::ShaderStages::FRAGMENT,
            ty: wgpu::BindingType::Texture {
                sample_type: wgpu::TextureSampleType::Float { filterable: true },
                view_dimension: wgpu::TextureViewDimension::D2,
                multisampled: false,
            },
            count: None,
        },
        wgpu::BindGroupLayoutEntry {
            binding: 2,
            visibility: wgpu::ShaderStages::FRAGMENT,
            ty: wgpu::BindingType::Sampler(wgpu::SamplerBindingType::Filtering),
            count: None,
        },
    ],
});
let pipeline_layout = device.create_pipeline_layout(&wgpu::PipelineLayoutDescriptor {
    label: None,
    bind_group_layouts: &[&bgl],
    push_constant_ranges: &[],
});
// Any pipeline built with `pipeline_layout` accepts bind groups built from `bgl`.
```

#### 4.2.3 Dynamic offsets and alignment

Uniform (and storage) buffer bindings may declare `hasDynamicOffset: true`, allowing a single bind group to address *N* sub-allocations of one large buffer: `setBindGroup(index, group, [offset0, offset1, ...])`. Each dynamic offset must be a multiple of `minUniformBufferOffsetAlignment` (256 bytes) or `minStorageBufferOffsetAlignment` (256 bytes).

#### 4.2.4 The WGSL contract

On the shader side, every resource variable declares its binding address explicitly:

```wgsl
@group(0) @binding(0) var<uniform> u_frame : FrameUniforms;
@group(0) @binding(1) var t_albedo : texture_2d<f32>;
@group(0) @binding(2) var s_linear : sampler;
```

The WGSL specification mandates that *bindings must not alias within a shader stage* and that the shader's *resource interface* — the set of statically-accessed module-scope resource variables — must be *layout-compatible* with the pipeline's bind-group layouts: each variable must find a WebGPU resource of compatible type at its `(group, binding)` address [2].

| WebGPU binding type | Vulkan lowering | D3D12 lowering | Metal lowering |
|---|---|---|---|
| `uniform` buffer | `VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER[_DYNAMIC]` | Constant-buffer view in root signature | `[[buffer(n)]]` constant address space |
| `storage` / `read-only-storage` | `STORAGE_BUFFER` | UAV / SRV structured buffer | `device` address space buffer |
| `texture` (sampled) | `COMBINED_IMAGE_SAMPLER` or separate | SRV descriptor table | `[[texture(n)]]` |
| `sampler` | `SAMPLER` | Sampler descriptor heap | `[[sampler(n)]]` |
| `storageTexture` | `STORAGE_IMAGE` | UAV texture | `[[texture(n)]]` read-write |

### 4.3 naga: A Single-IR Shader Compiler for All Backends

#### 4.3.1 Architecture: frontends → IR → backends

**naga** is the shader translation library at the heart of wgpu [3]. Its architecture is a classical multi-frontend, multi-backend compiler organized around a single intermediate representation:

```
   WGSL ──┐
          ├──► naga IR (arena-allocated, handle-based) ──► SPIR-V  (Vulkan)
   GLSL ──┤         │                                     ──► MSL     (Metal)
          │         ▼                                     ──► HLSL    (D3D12)
 SPIR-V ──┘   validator (WGSL-spec conformance)           ──► GLSL    (GLES)
                                                          ──► WGSL    (round-trip/debug)
```

Frontends parse WGSL, GLSL, or SPIR-V into the IR; a *validation pass* checks the IR against the invariants of the WGSL language specification (type soundness, resource-interface well-formedness, entry-point signature rules); backends then lower the validated IR to SPIR-V, MSL, HLSL, GLSL, or WGSL [3].

#### 4.3.2 The binding-model lowering problem

The deepest technical challenge naga solves is *binding-model lowering*: translating WGSL's `(group, binding)` address space into each backend's native scheme. Consider `@group(0) @binding(1) var t : texture_2d<f32>`:

- **SPIR-V** requires a `DescriptorSet`/`Binding` decoration pair; naga maps WGSL group → SPIR-V descriptor set directly.
- **MSL** has no descriptor sets: naga assigns each resource a flat `[[texture(n)]]` / `[[buffer(n)]]` index and rewrites the entry-point signature accordingly, threading resources as function arguments.
- **HLSL** uses *register spaces*: naga maps `(group, binding)` → `(space, register)` pairs, e.g. `Texture2D<float4> t : register(t1, space0)`.
- **GLSL** (for the GLES backend) emits `layout(set=0, binding=1) uniform sampler2D`.

This lowering must additionally respect each backend's *limits* (e.g., MSL's 31 textures per stage on older GPUs, D3D12's root-signature size caps) Naga handles these via backend *policies* — per-target configuration structs that parameterize index assignment, capability gating, and workaround injection.

#### 4.3.3 naga vs. Tint: two philosophies

| Dimension | **naga** (wgpu/Firefox) | **Tint** (Dawn/Chromium) |
|---|---|---|
| Language | Rust (memory-safe) | C++ |
| Users | Firefox, Deno, Bevy | Chrome, Edge |
| Frontends | WGSL, GLSL, SPIR-V | WGSL (+ SPIR-V reader) |
| Backends | SPIR-V, MSL, HLSL, GLSL, WGSL | SPIR-V, MSL, HLSL, GLSL |
| Diagnostics | Good, improving | Best-in-class error messages |
| Footprint | Smaller, focused scope | ~200K LoC, ~2–3 MB binary |
| Validation | IR-level validator shared across frontends | AST/transform-based pipeline |

Independent evaluation rates Tint the most mature option and naga the smaller, memory-safe alternative [5].

### 4.4 The wgpu Stack: Validation-First Layering

A frame's journey through wgpu illustrates the architecture's central bet — *validate once in `wgpu-core`, then trust the HAL*:

1. **Application** (`wgpu` crate): records encoders, bundles, bind groups, and pipelines.
2. **`wgpu-core`**: implements the WebGPU API semantics — resource management, state tracking, and *validation*. Every `set_bind_group`, `draw`, and `execute_bundles` call is checked against the specification's invariants (layout compatibility, resource-state coherence, bundle/pass compatibility) *before* any backend code runs [3].
3. **`naga`**: translates and validates all shader modules at pipeline-creation time.
4. **`wgpu-hal`**: a thin, unsafe-Rust abstraction over Vulkan, D3D12, Metal, and GLES — deliberately *unvalidated*, because `wgpu-core` has already established every invariant the HAL relies upon.

```python
class ValidatedCommandStream:
    """Model of wgpu-core's contract with wgpu-hal."""
    def __init__(self):
        self.commands = []          # closed, validated command terms
        self.live_resources = set() # resources proven live at encode time

    def append_draw(self, pipeline, bind_groups, vertex_range):
        # wgpu-core validation (simplified): layout compatibility check
        for i, bg in enumerate(bind_groups):
            assert bg.layout.is_compatible_with(pipeline.layout[i]), \
                f"bind group {i}: layout mismatch"
            assert bg.resources.issubset(self.live_resources), \
                f"bind group {i}: dead resource"
        self.commands.append(("draw", pipeline, bind_groups, vertex_range))

    def submit_to_hal(self, hal_queue):
        # HAL trusts validation; no re-checks (the architectural bet)
        for cmd in self.commands:
            hal_queue.execute_native(cmd)
```

## 5. Empirical Results and Proofs

### 5.1 Synthetic microbenchmark: bundle encoding amortization

To quantify the §4.1.2 cost model, we constructed a synthetic experiment modeling CPU-side encoding of a scene with *D* draws per frame over *N* frames, comparing (a) direct per-frame encoding against (b) one-time bundle encoding plus per-frame replay. 

```python
def total_cost(draws, frames, E=1.0, alpha=0.1, bundle_overhead=2.0):
    direct = draws * frames * E
    bundled = draws * E * bundle_overhead + draws * frames * E * alpha
    return direct, bundled, direct / bundled

for frames in (60, 600, 6000):          # 1 s, 10 s, 100 s at 60 fps
    d, b, speedup = total_cost(draws=1000, frames=frames)
    print(f"frames={frames:5d}  direct={d:10.0f}  bundled={b:10.0f}  speedup={speedup:.2f}x")
# frames=   60  direct=     60000  bundled=      8000  speedup=7.50x
# frames=  600  direct=    600000  bundled=     38000  speedup=15.79x
# frames= 6000  direct=   6000000  bundled=    362000  speedup=16.58x
```

 

### 5.2 Formal statements

We state two results formally; the first was proved in §4.1.1.

> **Theorem (Replay determinism).** *Bundle re-execution is a frame-independent total function of the captured command sequence (see §4.1.1).*

> **Theorem (Binding soundness).** *If `wgpu-core` accepts a draw call with bind groups G₀…Gₖ against pipeline P, then for every shader stage s of P, every resource variable in s's resource interface resolves to a live GPU resource of compatible type. In particular, no draw accepted by validation can fault on a dangling or mistyped binding at HAL execution time.*

> **Proof (sketch).** Validation checks three properties jointly: (i) each *Gᵢ*'s layout is layout-equal to *P*'s layout at index *i* (entry-wise type/visibility/binding match); (ii) every resource in *Gᵢ* is live (reference-counted by `wgpu-core`'s storage); (iii) at bundle-encode time, resources referenced by the bundle are pinned for the bundle's lifetime [1][3]. By the WGSL resource-interface rule, each shader variable's `(group, binding)` address maps into exactly one layout entry [2]; (i) guarantees the entry's declared type matches the variable's; (ii)+(iii) guarantee liveness through execution. Hence the HAL's unvalidated dereference is safe. ∎

### 5.3 Translation-fidelity spot check

| WGSL source | SPIR-V (Vulkan) | MSL (Metal) | HLSL (D3D12) |
|---|---|---|---|
| `@group(0) @binding(0) var<uniform> U : Params;` | `OpDecorate U DescriptorSet 0`, `Binding 0` | `constant Params& U [[buffer(0)]]` | `cbuffer Params : register(b0, space0)` |
| `@group(0) @binding(1) var t : texture_2d<f32>;` | `DescriptorSet 0, Binding 1` | `texture2d<float> t [[texture(1)]]` | `Texture2D<float4> t : register(t1, space0)` |
| `@group(0) @binding(2) var s : sampler;` | `DescriptorSet 0, Binding 2` | `sampler s [[sampler(2)]]` | `SamplerState s : register(s2, space0)` |

 Portability hazards arise only where the function is *partial* (backend lacks the feature) or *lossy* (two WGSL addresses collide in the target scheme) — the subject of §6.

## 6. Limitations and Threats to Validity

**Bundles are not a universal win.** Render bundles cannot contain compute dispatches, timestamp or occlusion queries, or nested bundles; they must execute inside a compatible render pass. Dynamic per-draw state (e.g., per-draw uniform offsets) must live *outside* the bundle

**The microbenchmark is synthetic.** §5.1 models encoding cost algebraically; it does not measure any real driver. Actual *α* depends on backend lowering (secondary command buffers vs. re-recording), driver thread behavior, and CPU/GPU overlap. Our speedup figures bound the opportunity under stated assumptions and should be read as such.

**Shader-translation feature lag.** Both naga and Tint track a moving WGSL target; newer specification features (subgroup operations, advanced texture formats) land in translators after they land in the spec, and backend *policies* (§4.3.2) can only paper over genuine capability gaps. Applications must still query `adapter.limits` and feature flags — portability is *negotiated*, not guaranteed.

**Validation is necessary but not sufficient for identical rendering.** Two backends can both accept the same validated command stream yet rasterize differently within spec-permitted latitude (precision of interpolation, `clamp` behavior on out-of-range values, anisotropy limits).

**Threats from specification evolution.** Our specification analysis rests on the 2021 Working Drafts [1][2]; the specification has since advanced toward Recommendation status and implementations have shipped broadly (Chrome 113+, Firefox, Safari).

**The GLES backend is a second-class citizen.** wgpu-hal's GLES backend exists for compatibility but cannot expose the full explicit-API model (no native command buffers, no descriptor sets); it necessarily reintroduces driver-side emulation

---

## 7. Conclusion

WebGPU's portability rests on three interlocking abstractions, each solving one facet of the cross-API problem. **Render bundles** amortize CPU-side command encoding by capturing validated, closed command sequences for replay — with breakeven measured in single-digit frames under plausible backend lowering. **Bind groups** reconcile Vulkan descriptor sets, D3D12 root signatures, and Metal argument tables behind a single statically-checked `(group, binding)` address space, with layout compatibility enforced before any backend call. **naga** completes the picture by compiling WGSL through a single arena-based IR to SPIR-V, MSL, HLSL, GLSL, and WGSL, applying total deterministic address functions per backend.

Future work includes formal verification of naga's address functions and hardware-grounded bundle benchmarks.
