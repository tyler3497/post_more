# Compute Express Link: Cache-Coherent Memory Disaggregation, CXL.mem and CXL.cache Protocols, and Memory Pooling at Rack Scale

## Abstract

Compute Express Link (CXL) re-architects the server memory hierarchy by extending cache coherence beyond the processor socket. Built on the PCIe physical layer, CXL multiplexes three sub-protocols — CXL.io for discovery and configuration, CXL.cache for device-side caching of host memory, and CXL.mem for host-side access to device-attached memory — onto a single link. Successive specification generations (1.0 through 4.0) have transformed CXL from a point-to-point accelerator-attach technology into a full fabric supporting up to 4,096 endpoints, multi-level switching with port-based routing, back-invalidation-based coherence, and hardware-coherent memory shared across hosts. This paper presents a comprehensive technical treatment of the CXL.mem and CXL.cache protocols, the device and switch topology model, and the mechanisms of memory pooling and sharing at rack scale. It further analyzes Linux kernel support for tiered memory — NUMA-based tiering, transparent page placement, demotion and promotion policies, and DAMON-driven migration — and derives an analytical bound on the utilization gains of pooled versus stranded memory, concluding with measured fleet-scale evidence from hyperscale deployments.

---

## 1 Introduction

For four decades, server memory has been defined by a single architectural constraint: DRAM must be soldered or socketed within the electrical reach of a memory controller. Capacity scaled with the number of DIMM slots per CPU, bandwidth with the number of channels, and the ratio of memory to compute was fixed at procurement time. The consequences are well documented in datacenter economics: individual servers are provisioned for peak memory demand, and because peaks rarely coincide across machines, a large fraction of installed DRAM sits idle — *stranded memory* — while the total spend on memory has become the dominant component of server cost [3].

Compute Express Link (CXL) attacks this constraint at the protocol layer. Rather than inventing a new physical interconnect, CXL reuses the PCIe electrical and link layers and overlays three coherent sub-protocols that together deliver byte-addressable, cache-coherent memory semantics across an extended fabric. The intellectual lineage is clear: from NUMA's remote-access domains, to Gen-Z and OpenCAPI's coherent attach proposals, to CXL's industry-consolidated standard maintained by the CXL Consortium [1][2].

This paper makes three contributions. First, it provides a precise technical account of the CXL.io, CXL.cache, and CXL.mem protocols, including the device taxonomy, host-managed device memory (HDM) decoding, and the coherence mechanisms (snooping, snoop filters, back-invalidation) that make multi-host shared memory possible. Second, it formalizes the transition from CXL 2.0 *memory pooling* — a partitionable resource allocated through switches — to CXL 3.0 *memory sharing* — hardware-coherent shared regions across virtual hierarchies — and derives a utilization bound quantifying the pooling gain. Third, it analyzes the Linux kernel's tiered-memory management stack, from the NUMA-based memory tiering framework through Transparent Page Placement (TPP) and DAMON-driven migration, as the software substrate that makes disaggregated memory performant in production.

## 2 Background

### 2.1 The memory wall and the disaggregation imperative

Memory demand in hyperscale workloads — key-value caches, in-memory databases, large-model training and inference — has outgrown per-socket DIMM capacity. Memory is now routinely 30–50% of server bill-of-materials cost, yet fleet telemetry shows most allocated memory is cold: Meta measured 55–80% of allocated memory untouched within two-minute intervals, with anonymous pages running hotter than file-backed pages [3]. Provisioning every server for its own peak therefore wastes capital and power.

Memory *disaggregation* proposes to decouple memory from compute: pool memory at rack or pod scale, attach it through a low-latency coherent fabric, and allocate it dynamically. Early software disaggregation systems (e.g., RDMA-based far-memory paging) proved the concept but exposed the cost of software-managed coherence and page-granularity movement. CXL's contribution is to move the coherence and addressing machinery into hardware, presenting pooled memory as ordinary byte-addressable RAM — visible to the operating system as CPU-less NUMA nodes [3][4].

### 2.2 PCIe as the physical substrate

CXL deliberately layers on the PCIe physical interface: devices plug into standard PCIe slots (CEM form factors, EDSFF, and others), and CXL.io is essentially PCIe with added CXL-specific configuration semantics. This decision traded novelty for deployability: existing boards, retimers, and chassis infrastructure carry over. Each specification generation has tracked PCIe signaling advances:

| CXL generation | Base technology | Data rate | Flit size | Key fabric features |
|---|---|---|---|---|
| 1.0 / 1.1 (2019) | PCIe 5.0 | 32 GT/s | 68 B | Point-to-point attach, device types 1–3 |
| 2.0 (2020) | PCIe 5.0 | 32 GT/s | 68 B | Switches, pooling, persistent memory, IDE security |
| 3.0 (2022) | PCIe 6.0 | 64 GT/s | 256 B | Multi-level switching, 4,096 nodes, port-based routing, sharing, GFAM |
| 3.1 / 4.0 (2024–2026) | PCIe 6.0 | 64 GT/s | 256 B | Fabric refinements, extended telemetry and manageability |

The central physical achievement of CXL 3.0 was doubling the rate to 64 GT/s with PAM-4 signaling while holding latency constant; the 256-byte flit amortizes header overhead and aligns with cache-line-multiple transfers [1][2][5].

### 2.3 Related interfaces

CXL is not the first coherent-attach proposal. NVLink/NVSwitch and AMD Infinity Fabric provide coherent GPU fabrics but remain vendor-proprietary and GPU-centric; CCIX and OpenCAPI offered open coherent attach but were ultimately superseded by CXL. What distinguishes CXL is the combination of an open multi-vendor standard, the PCIe installed base, and an explicit rack-scale fabric story — coherence across hundreds of endpoints and multiple hosts.

## 4 Deep Dive

### 4.1 The Three Sub-Protocols: CXL.io, CXL.cache, CXL.mem

CXL's core design decision is *protocol multiplexing*: three logically independent protocols share one physical link, negotiated at link training. Every CXL device must implement CXL.io; CXL.cache and CXL.mem are optional and determine the device's type.

**CXL.io** is the foundational protocol. Derived from PCIe, it handles device discovery, enumeration, configuration-space access, interrupts (MSI-X), DMA via the IOMMU, and link management. A CXL device first appears as an ordinary PCIe endpoint; only after CXL.io negotiation do the coherent protocols become available [5][9].

**CXL.cache** provides coherent caching of host memory by the device. Its direction is device→host: an accelerator with CXL.cache may read and write host-attached memory with hardware-maintained coherence against the host CPU's caches. The protocol is a request/response/snoop dialogue carried over dedicated channels (request, response, snoop, data). A Type 1 device — an accelerator without local memory, such as a SmartNIC — uses only CXL.io and CXL.cache [5].

**CXL.mem** provides the complementary direction: the host accesses device-attached memory with load/store semantics and coherence. CXL.mem supports host-managed device memory (HDM), where host decoders route physical addresses into device memory, and device-managed flows for fabric topologies. CXL 3.0 added back-invalidate channels, letting devices invalidate host-cached copies of device memory — the primitive enabling direct peer-to-peer access and multi-host sharing without routing coherence through a host [1][5].

The three protocols and their roles:

| Protocol | Direction | Purpose | Required by |
|---|---|---|---|
| CXL.io | Host ↔ device | Discovery, configuration, interrupts, DMA | All devices |
| CXL.cache | Device → host | Device caches host memory coherently | Type 1, Type 2 |
| CXL.mem | Host → device | Host accesses device memory as RAM | Type 2, Type 3 |

**Device taxonomy.** Type 1 devices implement CXL.io + CXL.cache (cache-only accelerators). Type 2 devices implement all three protocols (accelerators with local memory, e.g., GPUs and FPGAs, whose memory the host can also map). Type 3 devices implement CXL.io + CXL.mem (pure memory expanders — the workhorse of memory pooling). A *multi-logical device* (MLD) partitions one physical Type 3 device into up to 16 logical devices, each assignable to a different host through a switch — the hardware primitive of fine-grained pooling [1][10].

### 4.2 Device Taxonomy, HDM Decoders, and Switches

Addressing CXL memory requires a decode hierarchy. Each switch and endpoint contains *HDM decoders* mapping host physical address (HPA) ranges to device-local addresses. Platform firmware publishes CXL Early Discovery Table (CEDT) entries describing fixed memory windows (CFMWS); the OS then programs root, switch, and endpoint decoders to route each HPA range through the fabric. Interleave sets stripe addresses across devices to aggregate bandwidth; Linux's `cxl` tooling exposes this topology (`cxl list -BDMu`) for verification [8].

Switches are the pooling enabler. CXL 2.0 introduced single-level switches connecting up to 16 hosts to pooled memory devices; CXL 3.0 generalizes to multi-level switch fabrics with up to 4,096 ports, non-tree topologies at rack and pod scale, and *port-based routing* (PBR), in which flits carry a destination port identifier and switches forward without host involvement [1]. Quality-of-service and link-level integrity and data encryption (IDE) protect the extended trust domain.

### 4.3 Coherence Mechanics: Snooping, Back-Invalidation, and Global Fabric-Attached Memory

Coherence is CXL's hardest problem and its central differentiator. In the CXL 1.x/2.0 model, coherence was *host-centric*: device caches were kept coherent by snooping the host's coherence domain, and inter-host sharing required software mediation. CXL 3.0 decentralizes coherence with three mechanisms:

1. **Snoop filters in devices.** Type 2 and Type 3 devices may implement snoop filters tracking which agents cache which lines of device memory, allowing precise invalidation instead of broadcast snoops [1].
2. **Back-invalidate channels in CXL.mem.** A device can now push invalidations *toward* hosts and peer devices that cache its memory. This inverts the traditional direction and is what permits direct peer-to-peer access to HDM memory — e.g., an accelerator reading another device's memory — without host mediation [1].
3. **Global Fabric-Attached Memory (GFAM).** A new device class exposing memory directly to the fabric, addressable by multiple hosts with hardware coherence. GFAM is the substrate for CXL 3.0's headline feature: *memory sharing*, in which the same physical region is simultaneously mapped by multiple hosts with the fabric guaranteeing that every host observes the most recent data, eliminating software-managed coordination [1][10].

> **Theorem (Coherence correctness of back-invalidation):** *In a CXL 3.0 fabric with snoop filters, a write to a shared GFAM line is globally visible once the writing agent has received back-invalidate acknowledgments from all agents recorded by the snoop filter as caching the line. Proof sketch:* the snoop filter maintains a conservative superset of sharers (it may over-approximate, never under-approximate); back-invalidate requests are delivered reliably over the fabric's ordered channels; acknowledgment implies the agent has discarded its copy before any subsequent load can be satisfied from its cache. No stale copy survives acknowledgment, so linearizability follows; the cost is that filter over-approximation becomes spurious invalidations — a bandwidth tax.

### 4.4 Memory Pooling, Memory Sharing, and Port-Based Routing at Rack Scale

It is essential to distinguish the two disaggregation models, because they solve different problems:

- **Memory pooling (CXL 2.0):** the fabric presents memory as a fungible resource that is *partitioned* among hosts. Each host receives exclusive logical devices (or MLD partitions); capacity can be attached, detached, and rebalanced as workloads shift. Pooling attacks *stranding*: the rack's memory is provisioned for the rack's aggregate peak rather than the sum of per-server peaks [10].
- **Memory sharing (CXL 3.0):** the fabric presents *the same* memory to multiple hosts simultaneously with hardware coherence. Sharing attacks *coordination*: semaphores, message queues, and shared indexes across hosts no longer require software coherence protocols or RDMA round trips [1].

Port-based routing is what makes both models scale. In CXL 2.0, routing was hierarchical and host-rooted; in CXL 3.0, switches forward 256-byte flits by destination port across multi-level, potentially non-tree fabrics, supporting up to 4,096 endpoints — enough to treat an entire rack, and eventually a pod, as one coherence domain. Combined with UIO (unordered I/O) for peer-to-peer access, the fabric begins to resemble a distributed shared-memory machine built from commodity parts [1].

### 4.5 Tiered Memory Management in the Linux Kernel

Hardware coherence solves *correctness*; *performance* requires the OS to place pages on the right tier. CXL-attached memory is byte-addressable but slower than socket-local DRAM: a realistic operating point is ~100–150 ns loaded latency for local DDR5 versus ~200–400 ns for CXL-attached DRAM, depending on link width, retimers, and switch hops [11]. Treating all NUMA nodes as equivalent destroys performance: hot working sets land on CXL while cold data occupies fast DRAM.

Linux's answer is the **memory tiering framework** (v5.18–v6.1). The kernel models each NUMA node as a memory type with an *abstract distance* (adistance) derived from firmware-provided latency and bandwidth attributes (HMAT, and for CXL devices the Coherent Device Attribute Table — CDAT — with its DSMAS/DSLBIS structures). Nodes are sorted into tiers: top tiers are CPU-attached DRAM, lower tiers are CXL and persistent memory [4][8]. Three mechanisms then manage placement:

1. **Demotion.** Under reclaim pressure on a fast tier, the kernel demotes cold pages to the next-slower tier instead of swapping them to disk (`/sys/kernel/mm/numa/demotion_enabled`). Demotion is the safety valve that keeps the fast tier available for new allocations.
2. **Promotion via NUMA balancing.** Setting `numa_balancing` to `NUMA_BALANCING_MEMORY_TIERING` (value 2) makes the fault-based NUMA balancer treat nodes as tiers: pages that fault repeatedly on a slow tier are promoted to the fast tier, while the balancer's hysteresis avoids ping-ponging [11].
3. **Transparent Page Placement (TPP).** Meta's TPP, merged substantially into Linux v5.18, decouples allocation from reclamation: the fast tier is kept under artificial headroom so that new allocations land on DRAM and promotion of hot pages trapped on CXL can succeed even under pressure. TPP uses active-LRU-based hot-page detection to add hysteresis, cutting the promotion rate 11× while improving promotion success by 48% [3].

A fourth, userspace-driven mechanism is **DAMON** (Data Access MONitor), which samples access patterns with low overhead and applies migration schemes (`DAMOS_MIGRATE_HOT` / `DAMOS_MIGRATE_COLD`) between tiers; recent work reports it cuts tiering slowdown from ~17–18% to ~4–5% under fast-tier pressure [6].

Typical production configuration on a CXL Type 3 platform:

```bash
# Treat NUMA nodes as memory tiers; promote hot pages to fast DRAM
echo 2 > /proc/sys/kernel/numa_balancing
# Demote cold pages to CXL under reclaim instead of swapping
echo 1 > /sys/kernel/mm/numa/demotion_enabled
# Reclaim aggressively from the local node before spilling
echo 7 > /proc/sys/vm/zone_reclaim_mode
```

On top of the kernel, Intel's Flat Memory Mode demonstrates the alternative *hardware-managed* extreme: cacheline-granular, hardware-controlled tiering between near (DRAM) and far (CXL) memory at a fixed ratio, trading software flexibility for zero OS overhead and no page-migration stalls [12].

## 5 Empirical Evaluation and Proofs

### 5.1 Fleet-scale evidence: TPP at Meta

The strongest empirical validation of tiered CXL memory comes from Meta's TPP deployment. Using Chameleon — a PMU-based profiler sampling LLC and TLB misses with duty-cycled, low-overhead collection — the authors characterized fleet workloads and evaluated TPP at a 2:1 local-to-CXL capacity ratio [3]:

- TPP improved performance by **up to 18% over default Linux** and **5–17% over NUMA balancing and AutoTiering**, converging to within 1% of an idealized all-DRAM baseline.
- Decoupling allocation from reclamation raised the local-node allocation rate 1.6× at the 95th percentile; without it, promotion "almost halts" under pressure, trapping pages on CXL that then generate 55% of memory traffic and a 12% throughput drop.

Independent DAMON-based studies corroborate the headroom: access-aware migration reduces tiering slowdown from roughly 17–18% to 4–5% on Redis/YCSB workloads under fast-tier pressure [6]. The lesson is consistent: *the hardware provides the tiers; the placement policy determines whether the system wins or loses.*

### 5.2 Analytical model of pooled-memory utilization

We now formalize the pooling argument. Consider $n$ hosts, where host $i$ has random memory demand $D_i$ with mean $\mu$ and variance $\sigma^2$, independent across hosts.

> **Theorem (Pooling gain):** *To guarantee that demand is satisfied with probability at least $1 - \epsilon$, unpooled provisioning requires total capacity $n(\mu + z_\epsilon \sigma)$, while pooled provisioning requires $n\mu + z_\epsilon \sigma \sqrt{n}$, where $z_\epsilon$ is the standard-normal quantile. The pooling gain — the capacity saved — is $z_\epsilon \sigma (n - \sqrt{n}) = \Theta(n)$.*
>
> *Proof sketch.* By the central limit theorem, aggregate demand $\sum_i D_i$ is approximately normal with mean $n\mu$ and standard deviation $\sigma\sqrt{n}$. The $(1-\epsilon)$-quantile of the aggregate is $n\mu + z_\epsilon\sigma\sqrt{n}$; provisioning this much pooled memory satisfies total demand with probability $1-\epsilon$. Without pooling, each host must independently provision its own quantile $\mu + z_\epsilon\sigma$, totaling $n\mu + z_\epsilon\sigma n$. The difference is $z_\epsilon\sigma(n-\sqrt{n})$, which grows linearly in $n$. The key step — replacing a sum of quantiles by the quantile of a sum — is valid because independent fluctuations partially cancel. ∎

Concretely, for $n = 16$ hosts per rack, $z_{0.01} \approx 2.33$, and demand variability $\sigma = 0.3\mu$, pooling saves roughly $2.33 \times 0.3\mu \times 12 \approx 8.4\mu$ — over eight hosts' worth of mean demand. This is the quantitative content of the industry claim that pooling lets designers "not overprovision every server in the rack" [10]. The bound assumes independence; correlated demand (e.g., fleet-wide diurnal peaks) weakens it, so production pool sizing must be calibrated against measured joint demand distributions.

### 5.3 Latency model of a CXL.mem access

A host load to CXL-attached memory traverses the following pipeline, yielding an additive latency model:

$$T_{\text{CXL}} = T_{\text{DRAM}} + T_{\text{flit-pack}} + T_{\text{SerDes}} + h \cdot T_{\text{switch}} + T_{\text{device}}$$

where $h$ is the number of switch hops (0 for direct attach). With $T_{\text{DRAM}} \approx 100$ ns, per-hop switch latency $\approx 50$–$100$ ns, and SerDes plus flit packing $\approx 40$–$80$ ns, a single-switch topology lands near $250$–$350$ ns loaded latency — consistent with published Type 3 expander measurements of roughly 2× local-DRAM latency [11]. Two consequences follow: (i) latency-sensitive, pointer-chasing workloads must stay on local DRAM — the entire point of TPP's headroom mechanism; and (ii) bandwidth-bound streaming workloads tolerate CXL well, especially under heterogeneous interleaving, which stripes requests across local and CXL channels to aggregate bandwidth [11].

## 6 Limitations

CXL is not a universal solvent, and an honest accounting must name its boundaries.

- **Latency is fundamental.** No protocol revision repeals the speed of light or SerDes delay. CXL memory remains a slower tier; workloads whose hot set exceeds local DRAM pay. Hardware-managed tiering hides some of this at cacheline granularity but at a fixed tier ratio and with metadata overhead [12].
- **Coherence does not scale for free.** Snoop-filter over-approximation, back-invalidate storms on widely shared lines, and directory state that grows with the sharer set all bound how far a single coherence domain can practically extend. The 4,096-node fabric limit is a routing ceiling, not a coherence guarantee.
- **Software maturity lags hardware.** Multi-host sharing, GFAM orchestration, fabric-wide QoS, and hot-plug at rack scale remain sparsely supported in mainline kernels; much of the CXL 3.0 feature surface is specified but not yet productized.
- **Security and multi-tenancy.** Extending the coherence domain across hosts extends the trust domain. Link IDE encrypts flits in flight [2], but shared-memory side channels between mutually distrustful tenants on one fabric are an open research problem.
- **The pooling theorem's independence assumption.** Real datacenter demand is correlated; the $\Theta(n)$ gain is an upper bound, and synchronized fleet-wide peaks can erase it.

## 7 Conclusion

Compute Express Link represents the most significant change to server memory architecture since the adoption of DDR: a standards-based, PCIe-compatible fabric multiplexing discovery (CXL.io), device-side coherent caching (CXL.cache), and host-side coherent memory access (CXL.mem) onto one link, scaling — through switches, port-based routing, back-invalidation, and fabric-attached shared memory — from a single accelerator to a rack-scale disaggregated memory system. The hardware story is now substantially complete through CXL 4.0; the frontier has moved to software. Linux's tiered-memory framework, transparent page placement, and access-aware migration determine whether disaggregated capacity is a performance asset or a latency trap, and fleet-scale evidence shows the penalty of a deepened hierarchy can be driven into the low single digits with the right policies.
