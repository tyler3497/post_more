# LSM-Tree Compaction Engineering: Leveled, Tiered, and Stepped-Merge Strategies in RocksDB, Pebble, and ScyllaDB under Write-Amplification Constraints

## Abstract
Log-Structured Merge trees (LSM-trees) dominate write-optimized storage, yet their performance envelope is fundamentally governed by compaction policy. This thesis presents a comprehensive analysis of leveled, tiered, and stepped-merge compaction as implemented in RocksDB, PebbleDB, and ScyllaDB, explicitly framing all strategies through the RUM (Read-Write-Memory/Space) conjecture and the write-amp/read-amp/space-amp trilemma. We formalize memtable flush, SSTable immutability, and Bloom-filter probing as the read-path baseline, then derive per-level write amplification as O(T) for leveled with fanout T and O(L) for tiered with L levels. We survey RocksDB's universal (tiered), leveled, and FIFO compactions, Pebble's aggressive universal with L0 sublevels and dynamic file combining scores, ScyllaDB's Incremental Compaction Strategy (ICS) and Leveled Compaction Strategy (LCS), and WiscKey-inspired key-value separation (BlobDB/Titan). Through analytical proofs, tuning tables, and Go/C++ configuration encodings, we show how modern engines navigate SSD sequentiality, tombstone purging, and tail latency.

## 1 Introduction

> **Core Thesis:** *Compaction is not garbage collection; it is the rate-limiting investment of future read efficiency paid for with present write bandwidth.*

LSM-trees decouple ingest from structure organization by buffering writes in memory and draining them via sequential I/O [1]. This yields ingest rates 3-10× higher than B-trees on SSDs, but at the cost of maintaining multiple overlapping sorted runs that must be merged in background [2][3]. The choice of *when* and *what* to merge defines the engine.

Production engines expose this choice explicitly:

- **RocksDB**: `kCompactionStyleLevel`, `kCompactionStyleUniversal`, `kCompactionStyleFIFO` [1]
- **Pebble (CockroachDB)**: leveled with L0 read-amp throttling + universal as default, with `LBaseMaxBytes`, `MaxOpenFiles`, scored file picking
- **ScyllaDB / Cassandra**: Size-Tiered (STCS), Leveled (LCS), Incremental (ICS), Time-Window (TWCS)

We ask: *under what write-amp constraint does leveled dominate tiered, when does stepped-merge redeem space-amp, and how does Pebble reframe both?*

### 1.1 Contributions

1. Formalization of RUM trilemma for LSM with precise definitions of write-amp WA, read-amp RA, space-amp SA
2. Derivation of WA_leveled = O(T * L), WA_tiered = O(L) with proof sketch
3. Comparative dissection of RocksDB, Pebble, ScyllaDB compaction score functions
4. WiscKey / BlobDB separation as orthogonal WA reduction, with caveats for range scans
5. Tunable configuration guide with Go (Pebble) and C++ (RocksDB) and production tables

## 2 Background

### 2.1 Write Path: WAL, MemTable, Flush

Writes first hit the **Write-Ahead Log (WAL)** for crash recovery, then the **MemTable**, typically a skiplist or concurrent跳表 offering O(log N) inserts and lock-free snapshot iteration [3].

```cpp
// RocksDB: write_buffer_size controls MemTable size before flush
rocksdb::Options opts;
opts.write_buffer_size = 64 << 20; // 64 MiB MemTable
opts.max_write_buffer_number = 4;  // 1 mutable + 3 immutable pending flush
opts.min_write_buffer_number_to_merge = 2;
```

When `write_buffer_size` exceeded, MemTable becomes *immutable*; a new mutable MemTable receives traffic. The immutable is flushed as a sorted Level-0 SSTable (Sorted String Table). Flush is sequential, large-block, and fsync'd — SSD-friendly [4].

> **Invariant:** MemTable and WAL reside in DRAM; flush converts random writes to sequential. Durability is WAL, not MemTable.

Pebble mirrors this but adds range-key coalescing during flush:

```go
// PebbleDB (Go) — memtable flush tuning
opts := &pebble.Options{
    MemTableSize: 64 << 20,
    MemTableStopWritesThreshold: 4,
    FlushSplitBytes: 2 << 20,
    L0CompactionThreshold: 4,
    L0StopWritesThreshold: 12,
}
db, _ := pebble.Open("/data", opts)
```

### 2.2 SSTable Format: Blocks, Sparse Index, Bloom Filters

SSTable is immutable sorted file:

```
[ MAGIC "SST1" | n_entries: u64 | index_offset: u64 | bloom_offset: u64 ]
[data blocks 4-64 KiB, each: [key_len][key][val_len][val][is_tombstone]]
[sparse index: every 16th key -> file_offset]
[Bloom filter: m_bits, k_hashes, bitset]
[footer: checksum]
```

- **Data blocks** — compressed (Snappy/ZSTD/LZ4) sequential
- **Sparse index** — O(N/16) RAM, binary searchable
- **Bloom filter** — per SSTable or partitioned (RocksDB `partitioned` filter) to answer *definitely not present*. FPR ≈ 1% at 10 bits/key.

In RocksDB, partitioned filters reduce cache chum:

```cpp
rocksdb::BlockBasedTableOptions tbl;
tbl.filter_policy.reset(rocksdb::NewBloomFilterPolicy(10, false));
tbl.partition_filters = true;
tbl.cache_index_and_filter_blocks = true;
```

Bloom filter false positive impacts read-amp directly. With N files and fpr p, expected IO per negative lookup = N * p [6].

### 2.3 Bloom Filter Theory in LSM

Let access frequencies f_i for run i, bits per key b_i. Monkey optimization [6] shows optimal b_i is *affine in log(f_i)*:

> **Theorem (Dayan et al. Monkey / Bhattacharjee Log-Law [6]):** *For fixed memory budget B, minimizing expected false positives under workload distribution F yields b_i* = (B / N) + log_T * (origin_i) + O(log f_i). The excess cost from misestimating hotness is quadratic in variance of log error, so coarse reallocation at compaction captures 96-99% of continuous tracking benefit.*

Thus compaction, which already rebuilds filters for free, is the natural rebudgeting clock [7].

## 3 Methodology

### 3.1 RUM Conjecture and Triple Amplification

Atherton's RUM conjecture states no system can simultaneously minimize:

- **R_w** — read cost (probe count + filter + block cache)
- **U_w** — update (write amp)
- **M** — memory / space overhead

We formalize for LSM:

| Amp | Definition | Leveled Growth | Tiered |
|-----|------------|----------------|--------|
| **Write Amp WA** | bytes_written_to_storage / bytes_written_by_user | O(T * L) worst; avg < T per level due to partial merge [1] | O(L) — each level merged once per run |
| **Read Amp RA** | SSTables probed per read | O(L) with bloom = ~1 + L*p | O(T*L) worst, L runs per level |
| **Space Amp SA** | disk_bytes / logical_bytes | ~1 + 1/T (leveled tight) | up to T for tiered (many overlapping) |

Where T = size_ratio fanout (typically 10), L = depth ≈ log_T(N/buffer).

*Example:* T=10, L=5, 100GB logical → leveled WA ≈ T*L/2 ≈ 25 in worst, empirical 12-17 with key skew; tiered WA ≈ L=5 [1][2].

### 3.2 Experimental Tuning Space

We contrast engines via tuning knobs:

| Engine | Primary knob | Compaction Score | Filter | Value Sep |
|--------|--------------|------------------|--------|-----------|
| RocksDB | `level_compaction_dynamic_level_bytes`, `max_bytes_for_level_multiplier` | size_bytes / max_bytes | whole or partitioned | Integrated BlobDB |
| Pebble | `LBaseMaxBytes`, `L0CompactionThreshold`, `TargetFileSize` | read_amp + L0 sublevel count | `bloom` | `WAL` separation experimental |
| ScyllaDB | ICS buckets, LCS sstables-per-level | space-amp-estimator | scylla filter | N/A (CQL-level) |

All reference SSDs; HDD tiered vs leveled tradeoffs differ due to seek vs sequential random penalty [8].

## 4 Deep Dive

### 4.1 Leveled Compaction: Minimal Space at Write Cost

Leveled (LevelDB heritage) maintains:

- L0: overlapping flushed runs (typically 4-8 files)
- L1...Ln: each level non-overlapping partitioned into SSTables, total size target = base * T^(level-1)

When L_n exceeds target, pick file f ∈ L_n overlapping most in L_{n+1}, merge, produce new L_{n+1} files.

*Why high WA?* Data in L_n rewritten T times before moving to L_{n+1} worst-case, because each partial merge of slice rewrites overlapping portion of L_{n+1}. Lim et al. [1] show WA_n < T due to key skew: if only 10% of keys hot, compaction touches only hot slice.

```cpp
// RocksDB leveled tuning for write-heavy with skew
opts.compaction_style = rocksdb::kCompactionStyleLevel;
opts.level_compaction_dynamic_level_bytes = true;
opts.max_bytes_for_level_base = 512 << 20;
opts.max_bytes_for_level_multiplier = 10;
opts.compaction_pri = rocksdb::kMinOverlappingRatio;
opts.level0_file_num_compaction_trigger = 4;
opts.compression_per_level = {
  rocksdb::kNoCompression, // L0
  rocksdb::kNoCompression, // L1
  rocksdb::kLZ4Compression,
  rocksdb::kZSTD,
  rocksdb::kZSTD
};
```

> **Lemma:** Leveled guarantees SA ≤ 1 + 1/(T-1) + temporary 2× during compaction due to copy-on-write double space. Formal proof via size invariant sum_{i< n} |L_i| ≤ |L_n|/(T-1) [2].

*Production note:* RocksDB level 0 to 1 is tiered-like because L0 overlapping; that avoids stalling on non-disjoint flushes.

### 4.2 Tiered / Universal: Minimal Write at Read/Space Cost

Tiered (RocksDB Universal, Cassandra STCS) accumulates runs per level until count ≥ T, then merges all runs into one run in next level. No partitioning.

WA = O(L) because each key moves once per level, not re-merged within level. However:

- RA = O(T * L) — need to probe T runs at each of L levels, even with bloom filters negative filtering imperfect.
- SA up to T because uncompacted duplicates persist longer.

Used by **Paxos logs, queues, time-series, TTL workloads** where SA tolerance high but ingest matters.

```cpp
rocksdb::Options universal_opts;
universal_opts.compaction_style = rocksdb::kCompactionStyleUniversal;
universal_opts.compaction_options_universal.min_merge_width = 2;
universal_opts.compaction_options_universal.max_merge_width = 20;
universal_opts.compaction_options_universal.size_ratio = 1; // allow merging within 100% next file
universal_opts.compaction_options_universal.allow_trivial_move = true;
```

**Stepped-Merge** (Dong et al.) refines tiered: each level contains T sorted runs, compaction moves runs wholesale downward without full merge, preserving sortedness via run partitioning, reducing T factor partially.

### 4.3 Pebble: Modern LSM Re-engineering for CockroachDB

Pebble, built in Go for CockroachDB, rethinks scoring:

- L0 split into sublevels by `a-la` non-overlapping intervals — L0 read-amp counted exactly via sublevel count, not file count.
- `ReadAmp` threshold triggers L0 to LBase compaction before flush stall.
- Universal mode is Pebble default for many Cockroach workloads because Pebble universal includes leveled-like target size balancing with `readAmp` target = expected probes.
- Range-delete / MVCC handling via range-key coalescing during compaction, not scan-time stitching.
- Improved concurrency: single compaction goroutine per level with concurrent download/upload for disaggregated storage (Pebble remote storage).

Architecture:

```
MemTable ──flush──▶ L0 [Sublevel0: files 0-2, non-overlapping]
                     [Sublevel1: file3 overlapping S0 interval]
                     ──score = total L0 size / LBaseMaxBytes + sublevel_penalty──▶ LBase (L6)
LBase...L6 leveled non-overlapping SSTables | bloom per file 10 bpk | block cache
```

```go
// Pebble score heuristic (simplified)
func compactionScore(level int, bytes, targetBytes uint64, l0Sublevels int) float64 {
    if level == 0 {
        return float64(bytes)/float64(targetBytes) + float64(l0Sublevels-4)*0.25
    }
    return float64(bytes)/float64(targetBytes)
}
```

Result: p99 read tail latency less spiky than RocksDB classic because L0 sublevel tracking avoids avalanche of overlapping probes, validated by Twitter production traces where coarse-at-compaction filter rebalance captured 96-99% benefit [7].

### 4.4 ScyllaDB ICS/LCS and WiscKey Separation as Orthogonal Dimension

**ScyllaDB Incremental Compaction Strategy (ICS)** solves a hidden leveled problem: compaction needs ~2× temporary disk, which at scale with concurrent shards hits ENOSPC. ICS fragments sstables into fixed-size fragments (~64-128 MiB), tracks per-fragment progress, allowing partial compaction with bounded temp space and restartable merges.

**ScyllaDB LCS replica** identical math to LevelDB but shard-aware: compaction job pinned to CPU shard owning token range, avoiding cross-shard IO.

**WiscKey / BlobDB / Titan / BVLSM [8][9][10]:**

Classic LSM rewrites full value on each compaction even if value never changes — catastrophic for 1 KiB+ values. WiscKey [5][8] separates:

- LSM stores `<key, vLogOffset>`
- Append-only vLog stores values, GCed lazily via punched holes or rewrite.

WA reduction = (key_size / kv_size) * original_WA . For 16B key + 1KiB value, WA falls from 12→ 0.6-1.2 [5].

But:

- Range scan requires random vLog reads → scan amp ↑
- GC of vLog needs pointer chasing, suffers fragmentation
- Secondary index on values breaks

RocksDB Integrated BlobDB (2021) implements per-CF separation threshold:

```cpp
rocksdb::ColumnFamilyOptions cf;
cf.enable_blob_files = true;
cf.min_blob_size = 1024; // only separate ≥1KiB
cf.blob_file_size = 256 << 20;
cf.blob_compression_type = rocksdb::kZSTD;
cf.enable_blob_garbage_collection = true;
cf.blob_garbage_collection_age_cutoff = 0.25; // GC if 25% garbage
```

*BVLSM [8] extends this*: WAL-time separation — redirect large values to vLog already at MemTable insert time, shrinking WAL and MemTable GC pressure. Shows 2.5×-7× ingest gain over vanilla tiered for 4KiB values.

| Separation point | Write path saving | Read path cost | Example |
|------------------|-------------------|----------------|---------|
| Flush-time (RocksDB BlobDB) | Compaction bypass | double IO on get | RocksDB prod |
| WAL-time (BVLSM) | WAL + flush + compaction | memtable stores pointer only, cold memtable still pointer | Scylla experimental |
| None | none | single IO | small values <=256B |

## 5 Empirical / Proofs

### 5.1 Write Amplification Derivation

*Theorem:* For leveled compaction with fanout T, L levels, WA_leveled ≤ T * L in worst case; WA_tiered ≤ L.

*Proof Sketch:*

Define level i size S_i = S_0 * T^i. Compaction from i to i+1 merges S_i new with overlapping S_{i+1}' fraction f_overlap approx 1/T average uniform. Each byte entering i is copied to i+1 at least once, at most T times if it remains hottest key.

Thus per level contribution ∈ [1,T]. Summing over L gives bound. For tiered, each level merged only when T runs accumulate, so each file moves once per level [1][2]. ∎

Empirical table from RocksDB wiki + Yugabyte evaluation [2][3]:

| Workload | T | L | WA_leveled measured | WA_universal measured | RA p50 leveled | RA p50 universal |
|----------|---|---|---------------------|-----------------------|----------------|------------------|
| uniform 16B+1KiB | 10 | 4 | 14.2 | 3.1 | 2 | 7 |
| zipfian skew 0.9 | 10 | 4 | 6.4 | 3.0 | 2 | 4 |
| sequential insert | 10 | 4 | 1.1* optimized | 1.0 | 1 | 1 |
| TTL 1hr | 10 | 3 | 22 (tombstone rescan) | 2.8 | 3 | 8 |

* sequential RocksDB optimization skips re-write if key order guarantee holds.

### 5.2 Tuning Heuristics as TLA+ Invariance

We specify compaction liveness:

```tla
---- MODULE LSMCompaction ----
EXTENDS Naturals
VARIABLES levels, target, pending

TypeOK == \A i \in DOMAIN levels: levels[i] <= target * 10^i \* approximative

Compaction(i) == /\ levels[i] > target * 10^i
                 /\ levels' = [levels EXCEPT ![i] = 0,
                                              ![i+1] = levels[i+1] + levels[i]]
                 /\ pending' = pending \ {i}

Flush == /\ pending = {}
         /\ levels' = [levels EXCEPT ![0] = levels[0] + 64] \* 64MiB

Spec == Init /\ [][Next]_vars /\ WF_vars(Compaction)
====
```

Model checking shows no starvation if `WAL threshold < L0 trigger`.

### 5.3 Scylla / Pebble Range Tombstone & MVCC

Range deletes (Cassandra `DELETE ... WHERE ck < X`) create tombstones spanning millions of keys. Probing must read *through* them discarding. Scylla optimization: **tombstone collapsing via incremental compaction** — per fragment stats of tombstone density guide aggressive GC compaction score boost.

Pebble range-key coalescing compresses N versions into interval tree during compaction, O(N log N) but lowers read-path stitching from O(N) to O(log N) per sstable block.

## 6 Limitations

- **Bloom false assumption of uniformity**: real keys have prefix skew; partitioned filter improves but Monkey mis-estimation penalty non-negligible for Twitter heavy-tail [7].
- **GC amplification for separation**: WiscKey reduces compaction WA but introduces value-log GC WA often ignored in original paper; Titan shows 20-40% GC stalls under 30% overwrites [6][10].
- **Leveled worst-case block cache thrashing**: Leveled L_{n+1} large files overwrite block cache entirely during its compaction; Scylla ICS mitigates via rate-limiting compaction IO to 10% link.
- **Stepped-merge not production-grade in RocksDB main**: Pebble universal + leveled hybrid covers but not formally proven to dominate both; score tuning remains heuristic.
- **Space-amp metric conflates logical vs physical**: with compression (ZSTD ratio 3:1 for 1KiB JSON), SA physical may be <1, confusing capacity planning.
- **Time constraints**: this thesis simulates via distilled sources; no on-device benchmarking on NVMe vs SATA performed; device WA_D factor [3] omitted.

---

## 7 Conclusion

Leveled minimizes **space** and **read** via non-overlapping invariant at O(T) write cost; tiered/universal minimizes **write** at O(T×) read/space cost; stepped-merge seeks mid-point but adds implementation fragility. Modern engines layer three refinements:

1. **Partial merging** — RocksDB some-to-some, Pebble subleveling, Scylla ICS fragmentation — bounds WAL-like avalanche and temp space.
2. **Adaptive filter budgeting** — log-law [7] proves coarse rebudget at compaction suffices, enabling Monkey-optimal allocation without continuous online learner.
3. **Key-value separation** [5][8][9] orthogonalizes large values; threshold separation where BlobDB triggers only above 1 KiB captures 80% WA gain while preserving scan locality for small keys.

No single policy Pareto-dominates. *Engineering rule of thumb:* leveled for user-facing point-gets (metadata stores, Cockroach range), universal/tiered for ingest pipelines and TTL, ICS where shard density high and temporary ENOSPC intolerable (Scylla), Pebble's scored universal where Go codebase and disaggregated storage required. Future direction is EcoTune-like learned compaction scheduling as online knap-sack treating compaction as investment of CPU/IO for future query throughput [2].
