# Proof-Carrying Constant-Time Code: Machine-Checked Correctness and Side-Channel Resistance from HACL\* and EverCrypt to Verified TLS

## Abstract

Cryptographic software fails in two orthogonal dimensions: it computes the wrong function, and it leaks secrets through its physical behavior even when the function is right. This thesis develops the engineering and proof discipline of *proof-carrying constant-time code*: implementations whose shipped artifacts are accompanied by machine-checked evidence that they are functionally correct with respect to published standards and that their execution traces are independent of secret data. We survey the HACL\* verified library and its F\*/Low\* pipeline [1], the EverCrypt agile provider that multiplexes many verified implementations against one specification [2], the Vale verified assembly language that emits proof terms as first-class artifacts [3], and the Jasmin certified compiler whose Coq-verified passes preserve constant-time security from source to x64 assembly [4]. We formalize constant-time as trace noninterference over an instrumented leakage semantics, show how composition reduces the security of the TLS 1.3 record layer to AEAD assumptions [10], and argue that the Everest stack constitutes the first credible demonstration that high-assurance cryptography can ship at hand-written performance with proofs that compose.

## 1. Introduction

Cryptographic software fails in two orthogonal dimensions: it computes the wrong function, and it leaks secrets through its physical behavior even when the function is right. A single branch on a secret bit, a table lookup indexed by a key byte, or a carry loop bounded by a nonce can convert a sound construction into an oracle that hands the key to a remote adversary. Timing and cache side channels resist conventional testing because they are properties of *relations between executions*, not of single runs.

Two research traditions attacked this problem from opposite ends. The *verified cryptography* tradition, exemplified by HACL\* [1], writes primitives in the proof-oriented language F\* and proves them functionally correct against specifications derived directly from RFCs, and *secret independent* — observably independent of secret inputs. The *verified assembly* tradition, exemplified by Vale [3] and Jasmin [4], attacks the performance gap: hand-optimized assembly is where real deployments live, so verification must reach down to `AESENC` rounds and vectorized Poly1305 lanes without surrendering machine-checked guarantees. EverCrypt [2] composes these layers: an agile provider API dispatching at runtime to whichever verified implementation the CPU supports — portable C, Vale assembly, or vectorized HACLxN — all proved against one shared specification. Finally, the verified TLS work [10] lifts primitive-level guarantees into protocol-level theorems, reducing the security of the TLS 1.3 record layer to AEAD assumptions.

> **Theorem (Compositional reduction, informal).** *If each primitive used by the TLS 1.3 record layer is functionally correct and secret independent, and if the record-layer construction is a secure stateful AEAD under its ciphers' idealizations, then the record layer implements a secure channel. Each hypothesis is discharged by a distinct machine-checked proof at a distinct layer [1,2,3,10].*

The thesis of this document is that these systems jointly realize an old idea — *proof-carrying code* — in a form strong enough for production cryptography: the compiler (or extraction pipeline) carries proofs of functional correctness and side-channel resistance from the source language all the way to the bytes that execute, and composition theorems stitch per-primitive guarantees into per-protocol guarantees.

## 2. Background

### 2.1 The two enemies: incorrectness and leakage

A cryptographic implementation is a program $P$ mapping inputs $(pub, sec)$ — public and secret data — to outputs. Functional correctness asks that $P$ compute a specified mathematical function $f$: for instance, that the ChaCha20 keystream block equals the quarter-round construction of RFC 8439. Side-channel resistance asks something relational: two executions of $P$ on the same public inputs but different secret inputs must be *observationally indistinguishable* to an attacker who can measure time, count instructions, or observe cache-line accesses.

We formalize the second property with an instrumented (*leakage*) semantics: execution produces a *leakage trace* $\ell$ — branch targets visited and memory addresses accessed. The field has converged on cryptographic constant-time [4,5]:

> **Definition (Constant-time).** *A program $P$ is constant-time with respect to a partition of its inputs into public and secret if, for any two secret inputs $sec_1, sec_2$ and equal public inputs $pub$, the leakage traces of $P(pub, sec_1)$ and $P(pub, sec_2)$ are equal: $\ell_1 = \ell_2$.*

Constant-time forbids branching on secrets and forbids memory accesses at secret-dependent addresses. It permits *data-independent* arithmetic of variable latency on some platforms — the definition is deliberately conservative, and its conservatism is its strength: it is checkable by a combination of type systems, self-composition, and verified compilation, without modeling the microarchitecture.

### 2.2 F\*, Low\*, and the KaRaMeL extraction pipeline

F\* is a dependently typed, effectful ML-like language whose typechecker discharges proof obligations with an SMT solver [5]. Specifications are types: a ChaCha20 block function can be given a type stating exactly which permutation of the 16-word state it computes. Low\* [5] is a carefully chosen *subset* of F\* — essentially a shallow embedding of C — restricted to first-order, stack-allocated code so it compiles to C. KaRaMeL is the verified extraction pipeline translating Low\* to readable C, preserving memory safety, functional correctness, and secret independence [1,5]. The critical decision: *the same language* serves for specification, implementation, and proof.

```fstar
(* F*: functional specification of the ChaCha20 quarter round, from RFC 8439 *)
val quarter_round: a:idx -> b:idx -> c:idx -> d:idx -> s:state -> Tot state
let quarter_round a b c d s =
  let s = line a b d 16 s in   (* s[a] += s[b]; s[d] ^= s[a]; s[d] <<<= 16 *)
  let s = line c d b 12 s in
  let s = line a b d  8 s in
  let s = line c d b  7 s in
  s
```

The `line` operator above is a pure function on the state; the Low\* implementation is then proved — by refinement typing and SMT — to compute the same function on mutable buffers, and KaRaMeL extraction yields C consumable by mainstream or verified (CompCert) compilers [1].

### 2.3 Proof-carrying code, then and now

Necula's proof-carrying code (PCC) proposed that shipped binaries carry *proofs* of safety properties, checkable by a small trusted verifier at load time. Vale [3] is arguably the first industrial-scale realization of PCC for cryptography: it *emits proof terms* in Dafny as inspectable certificates, which a verified validator checks. Jasmin [4] takes the complementary certified-compiler route: the compiler itself is proved correct in Coq and proved to *preserve* constant-time, so a source-level constant-time proof survives lowering to x64.

## 3. Methodology

Our methodology is a layered verification discipline with four interlocking techniques, each chosen to match the abstraction level at which it operates.

**Layer 1 — Pure specification in F\*.** For each primitive, we write a succinct functional specification as pure F\* functions, derived line-by-line from the published standard (RFC 8439, FIPS 197/198, RFC 7748/8032) [1]. The specification is executable, tested against published test vectors, and shared by every implementation.

**Layer 2 — Secret independence by construction and by type.** Low\* programs are written in constant-time style — no secret-dependent branches, no secret-dependent memory accesses — and F\*'s type system checks it [1,5]. At the assembly level, Vale and Jasmin programs are checked against an explicit leakage model in which every instruction is annotated with the leakage it produces [3,4]. The proof method is *self-composition*: the program is composed with a renamed copy of itself, and a relational logic or the SMT solver proves that equal public inputs imply equal leakage traces, regardless of secrets.

**Layer 3 — Property-preserving translation.** Three translation strategies carry proofs downward:

| System | Translation | Trust mechanism | Properties preserved |
|---|---|---|---|
| HACL\* / KaRaMeL [1,5] | Low\* → C | Type-preserving extraction | Memory safety, functional correctness, secret independence |
| Vale [3] | Vale → x64 | Proof terms; verified validator checks them | Functional correctness, memory safety, timing-attack resistance |
| Jasmin [4] | Jasmin → x64 | Compiler proved correct in Coq; per-pass simulation | Functional correctness, safety, constant-time security |

**Layer 4 — Composition into protocols.** Primitive guarantees are lifted to protocol theorems by game-based reductions. The TLS 1.3 record layer is verified in F\* against a stateful AEAD security definition; its proof assumes only idealizations of the underlying ciphers, which the primitive layers discharge [10]. EverCrypt [2] provides the compositional API: one agile interface, many verified implementations, runtime CPU dispatch, all verified against the shared specification — so the protocol layer never depends on *which* implementation executes.

```haskell
-- Leakage-trace model: constant-time as noninterference over traces
data Leakage = BranchTaken PC | MemAccess Addr | ArithOp
  deriving (Eq)

type Trace = [Leakage]

constantTime :: Program -> Public -> Secret -> Secret -> Bool
constantTime p pub s1 s2 =
  leakageOf (run p pub s1) == leakageOf (run p pub s2)
-- A proof of constant-time is a proof that this equality holds
-- for all choices of secrets: a 2-safety hyperproperty.
```

The Haskell sketch above makes explicit what the F\* and EasyCrypt developments prove for real: constant-time is a *2-safety hyperproperty* — a property of pairs of executions [1,4].

## 4. Deep Dive

### 4.1 HACL\*: a verified library at production scale

HACL\* (Zinzindohoué et al., CCS 2017) is a portable C cryptographic library whose every primitive is written in Low\*, proved memory-safe, functionally correct, and secret independent, then extracted to C by KaRaMeL [1]. Its coverage is broad: ChaCha20, Salsa20, Poly1305, SHA-256/512, HMAC, Curve25519, Ed25519, AES-GCM, and the NaCl box API, making it a drop-in replacement for libsodium and TweetNaCl [1].

Three properties of HACL\* deserve emphasis. First, the specifications are *succinct and standard-derived*: the ChaCha20 spec is a few dozen lines of pure F\* mirroring RFC 8439, and the proof that the stateful implementation refines it is where the verification effort concentrates [1]. Second, the library includes what the authors believe is the first verified *vectorized* implementation of a cryptographic primitive — a SIMD ChaCha20 proved equivalent to the scalar RFC specification [1]. Third, HACL\* *ships*: its code is deployed in Mozilla's NSS (hence Firefox), in WireGuard's Curve25519 in the Linux kernel, in mbedTLS, in Microsoft's msquic QUIC stack, and in the Tezos blockchain [6] — the methodology's strongest argument.

Performance is the perennial objection to verified code, and HACL\* answers it with measurements: compiled with GCC on 64-bit platforms, its primitives are as fast as the fastest pure-C implementations in OpenSSL and Libsodium, significantly faster than the reference C in TweetNaCl, and between 1.1× and 5.7× slower than the fastest hand-optimized vectorized assembly in SUPERCOP [1]. The remaining gap — the assembly gap — is precisely what Vale and Jasmin close.

### 4.2 Vale: proofs as first-class artifacts for assembly

Cryptographic assembly is where performance lives and where conventional verification dies: x86-64 AES-GCM interleaves `AESENC` rounds with carry-less multiplication for GHASH, schedules around port pressure, and allocates registers by hand. Vale (Bond et al., USENIX Security 2017, Distinguished Paper) is a *verifiable assembly language*: programmers write assembly annotated with preconditions, postconditions, and loop invariants, and the Vale tool generates *proof terms* — explicit certificates — that a small verified validator checks [3].

The architecture inverts the usual trusted-base calculation. Instead of trusting a large verifier, Vale trusts a small checker and distrusts everything else: the annotated program, the proof-generating transformers, and the optimization passes are all untrusted inputs to the validator. Vale further provides *verified transformers* — proof-producing program transformations such as verified peephole optimizations — so performance engineering itself carries proofs [3]. The POPL 2019 follow-up embeds Vale efficiently inside F\*, letting Everest proofs compose across the C/assembly boundary in a single logic [7].

> **Theorem (Vale validation [3]).** *If the verified validator accepts a Vale proof term for an assembly program $A$ against specification $S$ (a Hoare triple plus a leakage bound), then every execution of $A$ satisfies $S$: it is memory safe, functionally correct, and its timing-relevant behavior matches the verified model.*

Vale's verified code — AES-GCM, SHA-256/512, Curve25519 field arithmetic — became the assembly tier of EverCrypt, running at parity with OpenSSL's hand-written assembly while carrying proofs OpenSSL's code cannot [2,3].

### 4.3 Jasmin: a certified compiler that preserves constant-time

Jasmin (Almeida et al., CCS 2017) attacks the same assembly gap from the compiler side [4]: cryptographers write in a high-level language with *predictable* compilation — control over register allocation, scheduling, and spilling — while a Coq-verified compiler guarantees the generated x64 is a correct translation. Its passes (inlining, unrolling, verified register allocation, linearization, emission) are each proved correct by forward simulation in Coq [4].

Jasmin's distinctive contribution is its treatment of *constant-time preservation*. Each pass is proved not only semantics-preserving but *leakage-preserving*: compiling $p$ to $p'$ comes with a *leakage transformer* $F$ mapping source leakage traces to target leakage traces, such that equal source leakages imply equal target leakages [4]. Concretely: the compiler never introduces secret-dependent branches (conditional moves become `CMOV`), never introduces secret-dependent addressing, and every pass's simulation relation is instrumented to track how leakage transforms.

> **Theorem (Constant-time preservation, Jasmin [4]).** *If a Jasmin source program $p$ is safe and constant-time under the instrumented source semantics, then the compiled x64 program $p'$ is constant-time under the instrumented target semantics. The proof proceeds pass by pass, each pass carrying an explicit leakage transformer.*

Source-level constant-time proofs are conducted in EasyCrypt using an explicit-leakage model and discharged by self-composition: $i_1 = i_2 \Rightarrow \ell_1 = \ell_2$ [4]. The methodology has since been extended toward post-quantum cryptography, including a mechanized framework carrying KEM-IND-CCA game-based security from Jasmin sources to compiled assembly for ML-KEM [8], and toward speculative-execution models [4].

```rust
/// Constant-time select: the primitive idiom both Vale and Jasmin
/// programs (and their proofs) are built from. No branches, no
/// secret-dependent addresses — leakage is identical for all secrets.
#[inline(always)]
fn ct_select(secret_bit: u32, a: u32, b: u32) -> u32 {
    // mask is all-ones iff secret_bit == 1, all-zeros otherwise
    let mask: u32 = 0u32.wrapping_sub(secret_bit);
    (a & !mask) | (b & mask)
}
```

### 4.4 Composition: EverCrypt multiplexing and the verified TLS record layer

Verified primitives are necessary but not sufficient: real systems need *agility* — the ability to choose implementations by platform — and *protocol-level* theorems. EverCrypt (Protzenko et al., IEEE S&P 2020) solves agility [2]: a single verified interface per primitive (hash, MAC, AEAD, signatures), beneath which sit many implementations — portable C from HACL\*, Vale assembly, vectorized HACLxN [6] — each proved against one shared mathematical specification. At initialization, EverCrypt probes CPU features and dispatches to the fastest verified implementation available. The verification is *modular in the dimension that matters*: adding a new platform-specific implementation requires proving it against the same spec, never re-proving clients.

Above EverCrypt sits the verified TLS 1.3 record layer [10] — TLS's cryptographic core: it fragments application streams, multiplexes subprotocols, pads to hide lengths, and applies AEAD (AES-GCM or ChaCha20-Poly1305) with per-record nonces. Bhargavan et al. built and verified a reference implementation of this layer in F\*, proving it a secure *stateful* authenticated encryption scheme by reduction to idealizations of its ciphers [10]. The integration with HACL\* closes the loop: the AEAD idealization that miTLS previously assumed — concretely realized by unverified OpenSSL bindings, a known leap of faith after vulnerabilities like CVE-2016-7054 — is replaced by the verified Low\* AEAD construction, whose C extraction interoperates with mainstream TLS 1.2 and 1.3 implementations on ChaCha20-Poly1305 ciphersuites [5,10].

No single tool proves all four; the stack's thesis is that four *composable* proof disciplines, each at its natural abstraction level, jointly cover them.

## 5. Empirical Results and Proofs

The Everest project's empirical claim is twofold: verification finds real bugs, and verified code performs. On the first: the verification of HACL\* and Vale code repeatedly caught discrepancies between implementations and standards — off-by-one carries in bignum code, incorrect padding edge cases — that test vectors had missed, because proofs quantify over *all* inputs while tests sample [1,3]. On the second, the performance story is quantitative and public:

- **HACL\* vs. pure C:** as fast as the fastest pure-C OpenSSL/Libsodium implementations; significantly faster than TweetNaCl reference C [1].
- **HACL\* vs. assembly:** 1.1×–5.7× slower than the fastest hand-optimized SUPERCOP assembly — the gap Vale and Jasmin were built to close [1].
- **Vale assembly:** at parity with OpenSSL's hand-written assembly for AES-GCM and SHA-2 while carrying machine-checked proofs [3].
- **Jasmin:** compiled ChaCha20-Poly1305 and Gimli within small factors of hand-tuned assembly, with the constant-time theorem covering the *generated* code, not just the source [4].
- **EverCrypt:** runtime dispatch achieves the best verified implementation per platform with zero proof burden on clients [2].

The proof artifacts are independently re-checkable by third parties — the defining property of proof-carrying code [1,3,4,10]. And verification effort amortizes: HACLxN (Polubelova et al., CCS 2020) showed one generic SIMD proof development specializing to many platforms [6], contrary to the folk belief that every optimization invalidates every proof.

## 6. Limitations

The stack's guarantees are strong but bounded, and the bounds matter. **Specification fidelity:** Vale's and HACL\*'s proofs are only as good as their specifications — Parno's warning that "you're only as good as your specification" applies with full force [3]. A proof of AES-GCM correctness against a mis-transcribed GHASH polynomial proves the wrong theorem flawlessly. **The leakage model's conservatism:** constant-time as defined here does not model speculative execution; Spectre-class attacks leak through prediction, not committed instructions. Extending Jasmin's leakage transformers to speculative semantics is active research [4]. **Trusted computing base:** the F\* typechecker and Z3, the Coq kernel, the Vale validator, KaRaMeL's extraction, the hardware's `AESENC` semantics, and the C compiler (unless CompCert) all remain trusted. **Coverage:** only a fraction of deployed cryptography is verified — RSA, post-quantum schemes beyond the ML-KEM frontier work [8], and most protocol logic remain outside the verified perimeter. **Proof maintenance:** specifications evolve (TLS 1.3's record layer changed during standardization), and proofs must be re-engineered; the amortized-cost results [6] mitigate but do not eliminate this tax. Finally, **side channels beyond time and cache** — power, electromagnetic emanation, fault injection — are outside the leakage model entirely; constant-time code is necessary but not sufficient against a physical adversary.

---

## 7. Conclusion

Proof-carrying constant-time code has moved, in under a decade, from research prototype to production infrastructure. HACL\* proved that a full modern library could be verified for correctness and secret independence without surrendering C-level performance [1]; Vale proved that hand-optimized assembly could carry its own machine-checked certificates [3]; Jasmin proved that a compiler could preserve constant-time security pass by pass to x64 [4]; EverCrypt proved that many verified implementations could hide behind one agile, dispatching API [2]; and the verified TLS record layer proved that primitive guarantees compose into protocol theorems [10]. The common thread is *composition of evidence*: each layer's proof is independently checkable, and the layers' theorems interlock — specification to implementation, source to assembly, primitive to protocol. The remaining work is widening the verified perimeter — post-quantum primitives [8], speculative leakage models, and the long tail of protocol logic — but the methodology for doing so is no longer in doubt.
