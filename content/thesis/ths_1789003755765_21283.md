# Confidential Computing at the Hardware Boundary: Intel SGX, AMD SEV-SNP, Arm CCA, and the Architecture of Trusted Execution

## Abstract

Confidential computing re-architects the trust relationship between a workload and its host: data is protected while *being processed*, closing the gap left by encryption at rest and in transit. This thesis compares the four dominant hardware trusted-execution environments — Intel SGX, AMD SEV-SNP, Intel TDX, and Arm CCA — across trust models, memory-protection mechanisms, attestation protocols, and residual attack surfaces. We formalize the distinction between process-based enclaves (SGX) and VM-based confidential computing (SEV-SNP, TDX, CCA Realms), derive a unified threat model with the hypervisor as a fully untrusted adversary, and evaluate each design's trade-offs between TCB size, compatibility, and side-channel resilience. Evidence from formal verification and published micro-architectural attacks — ciphertext side channels, transient-execution exfiltration, and replay attacks defeated by SNP's Reverse Map Table — shows that memory encryption without integrity is necessary but insufficient. We conclude that VM-centric confidential computing with hardware-enforced memory integrity and runtime attestation is the correct primitive, while I/O confidentiality, cache-side-channel mitigation, and secure migration remain open frontiers.

## 1. Introduction

The public cloud presents a paradox. Tenants outsource computation to infrastructure operators who are, by business necessity, able to observe everything the tenant's software does. Historically this paradox was resolved by *contract and process*: background checks, access audits, network segmentation, and legal agreements [6]. These controls are administrative rather than cryptographic; they do not alter the underlying architecture, in which a privileged hypervisor holds complete read and write access to guest memory and register state [1].

Confidential computing changes the architecture rather than the administration. A *trusted execution environment* (TEE) enforces, in silicon, a cryptographic perimeter around a workload: memory leaving the CPU package is encrypted with keys the hypervisor never possesses, integrity violations are detected by hardware checks on memory access, and a remote party can verify the workload's identity through *remote attestation* before provisioning secrets [3]. The workload need not trust the operator, the hypervisor, the host OS, or even other tenants sharing the socket.

> **Theorem (Confidentiality Reduction):** *If a TEE's memory-encryption engine guarantees IND-CPA security of DRAM contents under a hardware-held key, and the TCB excludes all software above the firmware boundary, then no polynomial-time adversary controlling that software can distinguish two equal-length plaintext workloads with advantage exceeding the engine's own distinguishing bound.*

The field has now produced not one TEE but a family of incompatible designs, and the differences are architectural, not cosmetic. **Intel SGX** partitions a process into an *enclave* living in a reserved region (the Enclave Page Cache), requiring application refactoring. **AMD SEV-SNP** and **Intel TDX** instead protect an entire virtual machine, preserving the "lift-and-shift" property that made virtualization commercially dominant [1][6]. **Arm CCA** introduces a new architectural world — the *Realm* world — with granule-level physical-address-space isolation enforced by the Memory Management Unit itself [7][8]. Choosing among them is not a matter of taste but of trust model: what the TCB includes, what the adversary is assumed capable of, and which side channels are considered in scope.

This thesis makes three contributions. First, it systematizes the hardware mechanisms of all four designs into a single comparative framework (Section 4). Second, it derives a unified threat model with the hypervisor as a *fully untrusted* adversary and maps each design's residual attack surface onto it (Section 5). Third, it argues, on the evidence, that the industry has converged on the correct primitive — VM-based confidential computing with hardware-enforced memory integrity — while identifying the problems that remain genuinely open.

## 2. Background

### 2.1 From TrustZone to confidential computing

Hardware-enforced isolation predates the term "confidential computing." Arm TrustZone (2004) split the processor into Secure and Normal worlds, a coarse partition that protected firmware secrets but did not serve multi-tenant cloud workloads: the Secure world was a single monolithic TCB shared by all trusted code on the device. Intel's response was *application-centric*: **SGX**, introduced with Skylake (2015), lets an ordinary user-space process carve out private memory regions — enclaves — that even ring-0 software cannot inspect [3][5][9].

The cloud then demanded something SGX could not easily give: protection for *unmodified* virtual machines. AMD answered with **SEV** (2016), encrypting each VM's memory with a per-VM key generated and held by the processor's security processor [2]; **SEV-ES** (2017) extended encryption to CPU register state on VM exit, closing the VMCB-leakage channel; and **SEV-SNP** added the missing piece, memory *integrity* [1]. Intel's VM-centric answer, **TDX**, shipped with 4th-generation Xeon (Sapphire Rapids, 2023). Arm's answer, **CCA**, is the most architecturally ambitious: it redefines the address-space model itself [8].

### 2.2 The attestation primitive

All confidential computing rests on one cryptographic protocol: *remote attestation*. A hardware root of trust (an AMD Security Processor, an Intel Management Engine / TDX module, an Arm EL3 Monitor) measures the initial state of the workload — typically a SHA-256 hash chain over loaded pages, the *measurement* — and signs it together with a verifier-supplied nonce [1][3]. The verifier checks:

1. The signature chains to a hardware manufacturer's root certificate (AMD's ASK/ARK, Intel's PCK via DCAP).
2. The measurement matches a known-good value (e.g., a reproducible build hash).
3. The nonce is fresh, binding the evidence to this protocol run and defeating replay.

SGX historically offered two attestation models: **EPID** (Enhanced Privacy ID, group signatures hiding which CPU attested, mediated by Intel's Attestation Service) and **DCAP** (Data Center Attestation Primitives), in which the quoting enclave produces an ECDSA-signed *quote* chained to a platform certificate (PCK) that data-center operators can cache and verify locally [4]. DCAP is now the standard deployment model for server SGX and, conceptually, the template for all subsequent designs.

### 2.3 Why integrity matters as much as encryption

Early SEV provided encryption *without* integrity: ciphertext was protected from passive observation but not from active tampering. A malicious hypervisor could not read plaintext but could swap, replay, or remap ciphertext — attacks formalized as *memory aliasing* (mapping two guest-physical addresses to one system-physical page) and *replay* (restoring an old ciphertext snapshot) [1]. SEV-SNP's central innovation is the **Reverse Map Table (RMP)**, a hardware-walked structure recording, per physical page, its owning ASID, guest-physical address, and validation state; the memory controller consults the RMP on every access, making aliasing and replay structurally impossible [1][2].

## 3. Methodology

This thesis is an architectural-systems study, not an experimental measurement paper. Our method is *comparative mechanism analysis*:

- **Source base.** We ground every mechanism claim in primary sources: vendor architecture specifications [2][7][8], the Intel SGX developer documentation [3][4], the formal-methods literature on SEV-SNP [1], and published attack papers and patents documenting residual vulnerabilities [6].
- **Threat-model derivation.** We adopt the strongest published adversary model — the SNP model, in which the hypervisor is fully untrusted and may tamper with page tables, inject arbitrary events, and supply false system information [1] — and evaluate each design against it, rather than against its own marketing threat model.
- **Empirical anchoring.** Where quantitative claims appear (attestation latency, RMP overhead, side-channel bandwidth), we cite the measurement study or formal result directly and flag estimates as such.
- **Scope discipline.** We analyze CPU/DRAM isolation and attestation. Secure I/O (TDISP, SEV-TIO), GPU TEEs, and firmware-update governance are discussed as boundaries of the current analysis in Section 6.

## 4. Deep Dive

### 4.1 Process-based enclaves: Intel SGX

SGX's unit of protection is the *enclave*, a set of pages in the Enclave Page Cache (EPC) — a Processor Reserved Memory region whose contents are encrypted by the Memory Encryption Engine (MEE) whenever they leave the package [5][9]. The hardware enforces that EPC pages are accessible only to the owning enclave's logical processors; even the OS kernel, system-management mode, and DMA engines are excluded [3].

**Measurement and identity.** Enclave construction is a measured sequence: `ECREATE` establishes the enclave with its attributes; each `EADD`/`EEXTEND` of a page folds the page's contents into a SHA-256 log whose final value is **MRENCLAVE**; `EINIT` (authorized by an `EINITTOKEN` from a launch enclave) finalizes it [3][9]. A second identity, **MRSIGNER**, binds the enclave to its author's key, enabling upgrade policies ("any enclave signed by vendor *V*") as an alternative to exact-measurement policies. Sealing keys are derived via `EGETKEY` from a hardware fuse secret mixed with the caller's choice of identity, so data sealed by one enclave (or signer family) is cryptographically inaccessible to any other [9].

**Attestation flow.** Local attestation uses the `EREPORT` instruction: enclave *A* obtains a MAC'd report over its measurement, verifiable only by enclave *B* on the same platform via a shared report key [3]. Remote attestation escalates through a *quoting enclave*: the application enclave's report is handed to the quoting enclave, which signs it with an attestation key (EPID group key or ECDSA PCK-bound key), producing a *quote* the verifier checks against Intel's root [4].

```rust
// Conceptual sketch: verifying an SGX DCAP quote (pseudo-Rust)
fn verify_quote(quote: &SgxQuote, pck_chain: &CertChain, expected_mrenclave: &[u8; 32]) -> Result<()> {
    pck_chain.verify_against_intel_root()?;                 // 1. trust anchor
    let tcb = quote.tcb_info();                             // 2. platform SVN levels
    require!(tcb.is_up_to_date(), "stale TCB");
    let report = quote.verify_ecdsa_signature(&pck_chain.leaf())?; // 3. signature
    require!(report.mrenclave == expected_mrenclave, "wrong enclave");
    require!(report.report_data == session_nonce_binding, "replay risk");
    Ok(())
}
```

**Costs.** The enclave model exacts a price: applications must be partitioned (ECALL/OCALL boundary crossings cost thousands of cycles), the EPC was historically limited (128–256 MB on early parts, paging encrypted pages out to untrusted memory), and the TCB per enclave is small but the *platform* TCB (microcode, ME, launch enclave) remains large. Side-channel history has been unkind: controlled-channel attacks exploit page-fault sequences, and the entire *transient-execution* family (Foreshadow/L1TF, SGAxe, ÆPIC) repeatedly extracted enclave secrets, because the enclave shares micro-architectural state with its untrusted host [9].

### 4.2 VM-based isolation I: AMD SEV-SNP

SEV-SNP protects a whole guest VM, and its threat model is the honest one: the hypervisor is *fully adversarial* [1]. The design rests on four pillars.

| Pillar | Mechanism | Defeats |
|---|---|---|
| Per-VM memory encryption | AES-XEX engine; key in AMD-SP, never exposed | Passive DRAM snooping, cold-boot reads |
| Register-state encryption (SEV-ES) | VMSA encrypted on VMEXIT | VMCB/register inspection by hypervisor |
| **Memory integrity (SNP)** | **Reverse Map Table (RMP)** + page validation | Replay, aliasing, remapping attacks [1][2] |
| Runtime attestation | `SNP_REPORT` / guest messages via VMPCK | Launch-only attestation limitation of SEV [1] |

The **RMP** is the design's signature contribution. For each 4 KiB system-physical page, the RMP records the owning guest ASID, the guest-physical address it is mapped at, and whether the page is validated. On every nested-page-table walk, the hardware checks the RMP entry: a mismatch between the walk's (ASID, GPA) and the recorded values raises a fault. This single check simultaneously defeats aliasing (two GPAs → one SPA would require two RMP entries for one page) and replay (restoring stale ciphertext fails because the RMP's recorded GPA/ASID binding, plus the per-page encryption tweak, no longer matches the attacker's snapshot) [1][2].

Attestation in SNP is *runtime-capable*, a decisive improvement over SEV's launch-only model. The guest requests services from the SNP firmware through encrypted **guest messages** protected by the Virtual Machine Platform Communication Key (VMPCK), installed at launch [1]. An `SNP_REPORT` binds the launch measurement, the TCB version structure (so verifiers can enforce firmware freshness [1]), and 64 bytes of caller-supplied data — the standard hook for binding a session key or a workload hash into the hardware-signed evidence.

**Formal verification.** The SNP software interface is among the few TEE interfaces with machine-checked analysis: a 2024 formal model covers launch, attestation, key derivation, page swap, and migration, proving secrecy, authentication, and freshness properties — and, tellingly, *finding* attacks on authentication when the interface is used naively, including a report-integrity confusion a cloud provider could exploit to mislead a third-party verifier about firmware freshness [1]. Formal methods here are not decoration; they discovered real protocol-shape vulnerabilities.

### 4.3 VM-based isolation II: Intel TDX and the convergence argument

Intel TDX mirrors the VM-centric philosophy with Intel-specific machinery: a CPU-attested **TDX module** (SEAM), private memory marked in a physical-address-metadata table (PAMT, the conceptual sibling of the RMP), and integrity via a MAC-based scheme (TME-MK with integrity) rather than AES-XEX. The *trust domain* (TD) runs unmodified guest kernels; attestation quotes flow through the same DCAP infrastructure as SGX [4], unifying Intel's attestation story.

The instructive observation is **convergence**: two vendors, starting from different legacies (AMD from SME/SEV, Intel from SGX/MKTME), arrived at the same architecture — *protect the whole VM, encrypt with per-domain keys, enforce integrity in hardware on every access, attest at runtime*. The market reason is compatibility (no application rewrite), and the security reason is that integrity, not just encryption, is what neutralizes the malicious-hypervisor adversary [1][6].

### 4.4 Arm CCA: worlds, granules, and the Realm Management Extension

Arm CCA is the most radical redesign. Where x86 bolted confidential computing onto paging structures, **Armv9-A's Realm Management Extension (RME)** redefines the physical address space model itself. There are now four *worlds* — Normal, Secure, Realm, and Root — each with its own Physical Address Space (PAS), and every granule (4 KiB) of DRAM is assigned to exactly one PAS by the **Granule Protection Table (GPT)** [7][8].

The MMU performs a **Granule Protection Check (GPC)** downstream of address translation on every access: a Normal-world hypervisor touching a Realm granule faults with a Granule Protection Fault, in hardware, with no software mediation [8]. Delegation is clean: the EL3 Monitor (Root world) owns the GPT; a small **Realm Management Monitor (RMM)** at R-EL2 manages Realm VMs on behalf of the Normal-world hypervisor, which retains scheduling and resource management but gains no visibility [7]. Memory assigned to any world is encrypted before reaching DRAM, and attestation follows the CCA token format rooted in the platform's hardware identity.

> **Theorem (World Isolation):** *If the GPT assigns each granule to a single PAS and the GPC is enforced on every translation, then no agent executing in world W can observe or modify a granule in PAS(W′) for W′ ≠ W, regardless of the translation tables it controls — because the check is downstream of translation.*

CCA's elegance is that the *isolation primitive is the address space itself*, not an auxiliary table. Its practical cost is ecosystem immaturity: RME silicon, RMM firmware, and CCA-aware hypervisors (KVM-CCA) remain early relative to x86 deployments [7].

### 4.5 The attestation protocol, unified

Across all four designs, remote attestation has the same cryptographic skeleton, differing only in roots and formats:

1. **Measure:** hardware/firmware hashes initial state → *measurement*.
2. **Bind:** caller supplies a nonce or public key → *report_data* / challenge binding.
3. **Sign:** root of trust signs (measurement ‖ TCB versions ‖ binding) with a device key chained to the vendor root.
4. **Verify:** relying party validates the chain, checks measurement against policy, and enforces TCB freshness.

```haskell
-- Attestation verification as a pure function (pseudo-Haskell)
verifyEvidence :: VendorRoot -> Policy -> Evidence -> Either AttestationError ()
verifyEvidence root policy ev = do
  checkChain root (certChain ev)            -- signature chains to vendor
  checkFresh (tcbVersions ev) (minTcb policy) -- no downgraded firmware
  checkMember (measurement ev) (allowedImages policy) -- known-good code
  checkBinding (userData ev) (expectedNonce policy)    -- freshness, key binding
```

The security-critical subtlety, confirmed by the SNP formal analysis [1], is step ordering and binding discipline: an attestation report is only as meaningful as the freshness and key-binding fields the *verifier* demands. Protocols that omit them invite relay and report-substitution attacks regardless of how strong the silicon is.

## 5. Empirical Results and Proofs

### 5.1 What formal verification has proven — and found

The machine-checked model of the SEV-SNP interface [1] proves the properties the design claims — secrecy of VMPCK-derived keys, authentication of guest messages, freshness of reports — under its stated assumptions. Equally important are the *counterexamples* it produced: authentication failures when guest messages are composed without the intended bindings, including a scenario in which a provider convinces a third party that a guest runs on up-to-date firmware when it does not [1]. The lesson generalizes: **a TEE's security is a property of the protocol, not just the silicon**.

### 5.2 What attacks have demonstrated

- **Ciphertext side channels (SEV family).** Because AMD's memory-encryption engine uses AES in XEX mode with per-address tweaks, equal plaintexts at the same address produce equal ciphertexts. A hypervisor that can read (but not decrypt) guest ciphertext can therefore observe *when* a 16-byte block changes — a one-bit-per-block oracle sufficient, in published work, to exfiltrate secrets such as RSA keys from co-located VMs (US patent application US20230059273A1 documents the attack class [6]). SNP's integrity checks do not close this channel; determinism of the cipher under a fixed tweak is the root cause.
- **Transient execution (SGX).** Foreshadow (L1TF) demonstrated extraction of sealed and attested enclave data through L1-cache timing, prompting microcode and SDK mitigations; subsequent variants (SGAxe, ÆPIC Leak) showed the pattern repeating wherever enclave and attacker share micro-architectural predictors [9].
- **Integrity attacks defeated.** Pre-SNP aliasing and replay attacks — demonstrated against SEV/SEV-ES in the academic literature — are structurally closed by the RMP [1][2]. This is the clearest *empirical* validation of the "encryption is not enough" thesis: the attacks worked, the integrity mechanism stopped them, and the formal model confirms the closure.

### 5.3 Performance reality

Published measurements consistently show single-digit percentage overhead for SEV-SNP on compute-bound workloads, dominated by RMP checks on nested-page-table walks and VMPCK-protected guest-message round trips; TDX and CCA report comparable profiles. Attestation itself is a rare operation (milliseconds, dominated by signature verification and certificate-chain fetching), so its cost is architecturally negligible — the expensive part is *policy*: maintaining reproducible measurements of VM images across updates.

## 6. Limitations

No honest treatment of confidential computing can omit its boundaries.

1. **Side channels are out of scope by design.** None of the four architectures claims to close cache-timing, power, or ciphertext-change channels; they protect *architectural* state, not micro-architectural observables. Workloads with data-dependent memory-access patterns remain vulnerable, and mitigations (constant-time code, ORAM) are the workload's burden [6][9].
2. **I/O is the next frontier.** A confidential VM whose disk and network traffic are handled by an untrusted hypervisor needs encrypted, integrity-protected I/O paths (TDISP, SEV-TIO); these standards are nascent, and today's deployments often terminate I/O confidentiality at the guest kernel.
3. **Availability and migration.** A malicious hypervisor cannot read the guest, but it can *refuse to schedule* it, corrupt its devices, or roll back its persistent state. SNP's Migration Agent addresses live migration [1], but rollback protection for persistent storage remains an application-level problem.
4. **TCB freshness governance.** Attestation is only meaningful if verifiers enforce TCB minimums; the SNP formal analysis shows providers can otherwise mislead verifiers about firmware versions [1]. The cryptography is sound; the *ecosystem discipline* is the weak link.
5. **Supply-chain trust.** Every design roots trust in the vendor's key ceremony and firmware signing. A compromised signing key or a malicious microcode update defeats all of it — confidential computing moves trust, it does not eliminate it.

## 7. Conclusion

The decade-long arc from SGX enclaves to SEV-SNP, TDX, and Arm CCA tells a coherent story. *Process-based* enclaves proved the concept but imposed a rewrite tax and a side-channel-hostile sharing model; *VM-based* confidential computing preserved compatibility while adding the missing primitive — **hardware-enforced memory integrity**, via the RMP, PAMT, or GPT/GPC — that makes the malicious-hypervisor threat model actually hold [1][2][7]. Remote attestation, in its DCAP-descended ECDSA form, has become the industry's common trust-establishment language [4].

The converged architecture is therefore: encrypt per-domain, check integrity on every access, attest at runtime, and verify TCB freshness as policy. What remains open is not the CPU boundary — it is everything around it: side-channel-hardened workloads, confidential I/O, and the governance of firmware freshness. Confidential computing has solved the problem it set out to solve — *the operator cannot read your data* — with unusual completeness. The problems it did not set out to solve are now the field's agenda.
