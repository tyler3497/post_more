# Scaling Symbolic Execution: The KLEE Architecture and Systematic Path-Explosion Control via Solver Caching, State Merging, and Veritesting

## Abstract

Symbolic execution is among the most powerful techniques for automatic software testing, yet its practical adoption has been persistently constrained by *path explosion*: the number of distinct execution paths grows exponentially with program size, overwhelming state management and constraint solving. This thesis treats the architectural and algorithmic advances that transformed symbolic execution from a research curiosity into a production-grade bug-finding instrument. We dissect the KLEE symbolic virtual machine [1] — its LLVM-based executor, symbolic memory model, environment modeling, and search heuristics — and analyze four families of path-explosion countermeasures: *constraint independence and counterexample caching*, which exploit query redundancy to cut solver load by orders of magnitude; *state merging* [3], which reconverges forked states via query-count estimation; *veritesting* [2], a hybrid static–dynamic technique summarizing multi-path regions as disjunctive formulas; and *compile-time concolic execution* [4], which eliminates interpreter overhead. Drawing on the DART [5] and CUTE lineage, we formalize soundness properties of merging operators, present KLEE's empirical results on Coreutils and BusyBox, and characterize fundamental limits — the expressiveness–scalability trade-off, environment fidelity, and solver incompleteness.

## 1. Introduction

The idea of symbolic execution predates modern constraint solving by decades: King and Boyer observed in the 1970s that a program could be "executed" on symbolic rather than concrete inputs, accumulating algebraic constraints — a *path condition* — characterizing the inputs driving execution down each path. For every feasible path, solving its path condition yields a concrete test input reproducing the path, and any assertion violation, crash, or memory error along a feasible path is a genuine bug — symbolic execution produces *no false positives* for the paths it explores. Yet the technique languished for thirty years. Two developments revived it in the mid-2000s: dramatic progress in SAT/SMT solvers for bit-vector and array theories, and the LLVM compiler infrastructure [1], which exposed program semantics in a clean, analyzable intermediate representation.

The renaissance crystallized around two landmark systems. **DART** (Directed Automated Random Testing) [5], by Godefroid, Klarlund, and Sen, introduced *concolic* execution: drive the program with concrete random inputs while tracking symbolic constraints alongside, then negate a branch condition and solve for new inputs steering subsequent runs down unexplored paths. This hybrid trades completeness for robustness — operations the solver cannot model are *concretized* to observed runtime values. **EXE**, and its successor **KLEE** [1], took the opposite pole: a fully symbolic virtual machine over LLVM bitcode, forking execution states at every symbolic branch and modeling the entire program environment. KLEE's evaluation remains one of the most striking empirical demonstrations in software testing: on all 89 standalone GNU Coreutils programs, KLEE-generated tests achieved over 90% line coverage on average, surpassing the developers' own hand-written suites; applied to 452 applications totaling over 430,000 lines of code, it uncovered 56 serious bugs, including three in Coreutils that had survived more than fifteen years of testing [1].

But KLEE's success exposed the discipline's central wound. At each symbolic branch the executor forks its state; a program with *n* sequential symbolic branches can generate up to *2^n* states. This *path explosion* dominates cost: state management, constraint accumulation, and solver invocations all scale with path count. This thesis organizes the countermeasures into a taxonomy and analyzes each in depth:

1. **Search heuristics** — choosing *which* state to execute next to find bugs fast without exploring everything.
2. **Constraint independence and counterexample caching** — exploiting massive solver-query overlap to cut solving cost by orders of magnitude.
3. **State merging** [3] — reconverging states at join points so *n* sequential branches cost *O(n)* rather than *O(2^n)* states, at the price of disjunctive path conditions.
4. **Veritesting** [2] — statically summarizing straight-line, transition-free code regions into single formulas, opportunistically switching between dynamic and static symbolic execution.
5. **Compile-time instrumentation** [4] — moving symbolic execution out of the interpreter into the compiled binary, achieving order-of-magnitude speedups.

Section 2 surveys theoretical background; Section 3 presents the KLEE architecture; Section 4 develops each countermeasure; Section 5 formalizes key theorems and reports empirical results; Section 6 delineates limitations; Section 7 concludes.

## 2. Background

### 2.1 Classical Symbolic Execution

A symbolic execution engine maintains *execution states*, each comprising a **symbolic store** σ mapping variables to expressions over input symbols α₁, …, αₖ; a **path condition** π recording branch decisions; and a program counter with call stack. Initially π = true and inputs bind to fresh symbols. Assignments update the store; a conditional `if (c)` *forks* the state into π ∧ ⟦c⟧σ and π ∧ ¬⟦c⟧σ [6]. Before forking, the solver prunes infeasible outcomes. When a state terminates or hits an error, solving π yields a concrete reproducing input. Because explored paths are solver-certified feasible, reported bugs are real — but unexplored paths yield no guarantees.

> **Theorem 1 (Path Explosion).** *In the worst case, forking symbolic execution maintains S(b) = 2^b live states after b symbolic branches, and total exploration work is Ω(2^b · q), where q is mean per-state solver-query cost.*

*Proof sketch.* Each symbolic branch with both outcomes satisfiable doubles the state count; solver queries grow at least linearly in state count. ∎

Loops with symbolic bounds compound the problem: a loop iterating up to *N* symbolic times generates *N+1* states per level, and unbounded loops diverge. Practical engines impose search budgets (time, memory, instruction counts) and rely on heuristics to spend them wisely [6].

### 2.2 Concolic Execution: The DART and CUTE Lineage

DART [5] reframed symbolic execution as *dynamic* symbolic execution (DSE). Rather than forking states, DART executes *concretely* on random inputs while building the symbolic path constraint alongside. At run end, it negates one conjunct, solves for a satisfying assignment, and re-executes — systematically flipping branch decisions. Only one concrete path is live at a time, so memory is *O(path length)* rather than *O(2^b)*. Constraints outside solver theories are *concretized* to observed values, sacrificing completeness for progress. CUTE refined the idea for C unit testing with data-structure-aware input generation [5]. The concolic philosophy — *never let the perfect be the enemy of the explored* — underlies industrial executors including Microsoft's SAGE [6].

### 2.3 The Solver Bottleneck

Modern executors target quantifier-free bit-vectors with arrays (QF_ABV), using STP or Z3 [2]. Solver queries dominate runtime: a KLEE run issues millions of queries, each potentially NP-complete. Two empirical regularities make this bearable [1]: **query redundancy** (path conditions share massive prefixes; sub-queries recur thousands of times) and **constraint independence** (branch conditions touch few symbols, so queries decompose into independent sub-problems). These motivate the caching and independence optimizations of Section 4.2, which KLEE's authors credit with order-of-magnitude solver-time reductions — without them, KLEE would be impractical [1].

## 3. Methodology

Our analysis centers on the KLEE architecture [1], extended by Kuznetsov et al.'s state-merging framework [3], Avgerinos et al.'s veritesting hybrid [2], and SymCC's compile-time approach [4]. We (i) decompose each system into executor, memory model, solver interface, and search strategy; (ii) formalize each countermeasure as a state operator with cost models; (iii) state soundness theorems with proof sketches; and (iv) ground the analysis in published data — KLEE's Coreutils/BusyBox campaign, MergePoint's Debian evaluation, and SymCC's comparison against QSYM.

**KLEE pipeline.** KLEE compiles C to LLVM bitcode, links a POSIX environment model, and interprets the bitcode in its *Executor*, maintaining `ExecutionState` objects carrying path constraints, symbolic memory, and call stacks. Branches consult the solver; feasible outcomes fork via copy-on-write. `klee_init_env` creates symbolic `argv` of symbolic length, symbolic stdin, and symbolic files — the environment is the dominant input surface of systems programs, and modeling it separates KLEE from unit-level tools [1]:

```c
/* Symbolic environment setup (simplified from KLEE's KleeMain) */
int main(int argc, char **argv) {
    klee_make_symbolic(&argc, sizeof(argc), "argc");
    klee_assume(argc >= 0 && argc <= 3);   /* bound to control explosion */
    for (int i = 0; i < argc; i++) {
        char *arg = malloc(SYM_LEN);
        klee_make_symbolic(arg, SYM_LEN, "argv");  /* symbolic strings */
    }
    return real_main(argc, argv);
}
```

**Memory model.** KLEE's memory maps addresses to `MemoryObject`s — contiguous regions that may be concrete, symbolic, or mixed. A symbolic read at address expression *a* is resolved by the solver into feasible offsets; small sets fork per offset, large sets concretize [1]. Symbolic writes fork over candidate objects or concretize. This *forking memory model* is precise but expensive: symbolic pointer dereferences are a notorious explosion amplifier.

**Environment modeling.** Systems programs are *environmentally intensive*: files, filesystems, hundreds of syscalls. KLEE implements a symbolic filesystem and models 40+ POSIX calls in its runtime library. Unmodeled calls are concretized or user-modeled. The modeling boundary is the principal source of false negatives and engineering cost [1][6].

## 4. Deep Dive

### 4.1 KLEE's Search Heuristics

With forking execution, *which state runs next* determines bug-finding efficiency. KLEE's searcher portfolio [1]:

| Searcher | Policy | Strength | Weakness |
|---|---|---|---|
| DFS | Deepest state first | Low memory, fast deep bugs | Starves in deep loops |
| BFS | Queue-ordered | Fair coverage | RAM explosion |
| Random path | Weighted descent down process tree | Unbiased path sampling | Ignores coverage feedback |
| Coverage-guided | Prefer states near uncovered code | Maximizes line coverage | Frontier thrashing |
| Bug-directed | Prefer states near `klee_assert` | Fast assertion violations | Misses emergent bugs |

KLEE's default interleaves random path selection with coverage guidance. The random-path searcher samples *paths* uniformly by walking the process tree with child probabilities inversely proportional to subtree weight — counteracting the bias toward shallow, numerous states [1]. Coverage-guided search drove KLEE past Coreutils' own test suites by systematically closing hard-to-reach branches. When memory exhausts, KLEE *randomly kills* states — a pragmatic admission that a diverse surviving population beats a deadlocked complete one [1].

### 4.2 Constraint Independence and Counterexample Caching

KLEE's solver chain exploits query structure before reaching STP/Z3 [1]:

1. **Caching solver** — memoizes every query result.
2. **Independence splitting** — decomposes queries into variable-disjoint subsets. A branch condition touches few symbols, so a path condition with thousands of conjuncts splits into one small *relevant* query plus cached-satisfiable remainders. If π = π₁ ∧ π₂ with disjoint variable sets, SAT(π ∧ c) reduces to SAT(π₁ ∧ c) when Vars(c) ⊆ Vars(π₁) [1].
3. **Counterexample cache** — validates cached concrete assignments against new queries; a hit avoids the solver entirely. Successive path conditions differ by one conjunct, so old models usually still satisfy new queries — the cache answers the *majority* of queries without solver contact [1].

> **Theorem 2 (Soundness of Independence Splitting).** *Let q = π ∧ c with π = π_rel ∧ π_irr, Vars(π_irr) ∩ (Vars(π_rel) ∪ Vars(c)) = ∅, π_irr known-satisfiable. Then SAT(q) ⟺ SAT(π_rel ∧ c), and any model of π_rel ∧ c extends to a model of q.*
>
> *Proof sketch.* Variable-disjoint assignments compose independently (combination lemma for stably-infinite theories); extend with any model of π_irr. ∎

### 4.3 State Merging: Query Count Estimation and Dynamic Merging

State merging reconverges states at join points: one state whose store maps variables to *ite* expressions and whose path condition is the *disjunction* of merged conditions [3]. This trades *state count* for *formula complexity* — disjunctive queries can be exponentially harder. Kuznetsov, Kinder, Bucur, and Candea [3] show merging must be *selective*: positioned on a spectrum between pure forking (KLEE/DART) and full merging at every join (bounded model checking).

Their framework parameterizes a generic executor by a **scheduling function**, a **state similarity relation**, and a **branch feasibility checker** — unifying KLEE-style search, BMC, and VC generation [3]. Two mechanisms drive selectivity:

- **Query Count Estimation (QCE).** A static pre-pass counts future branch-condition mentions per variable. Merging states that differ in *high-QCE* variables inflates every subsequent solver query; QCE predicts this future cost, and the engine merges only when predicted cost beats keeping states separate.
- **Dynamic state merging.** At runtime, the engine opportunistically merges states with *similar* stores (differing in few low-QCE variables), reconciling differences with ite-expressions.

```python
def merge_states(s1, s2):
    """Merge two states at a join point (after Kuznetsov et al. [3])."""
    assert s1.pc == s2.pc
    merged_pc = Or(s1.path_condition, s2.path_condition)
    merged_store = {}
    for var in s1.store.keys() | s2.store.keys():
        v1, v2 = s1.store.get(var), s2.store.get(var)
        if equiv(v1, v2):
            merged_store[var] = v1
        else:
            merged_store[var] = Ite(s1.path_condition, v1, v2)
    return ExecState(s1.pc, merged_store, merged_pc)
```

> **Theorem 3 (Soundness of State Merging).** *For s = merge(s₁, s₂), the concrete executions of s are exactly the union of those of s₁ and s₂: no feasible path lost, none introduced.*
>
> *Proof sketch.* π₁ ∨ π₂ is satisfiable iff a disjunct is; under a model of π₁ the ite-store equals σ₁ (symmetrically π₂). Concretizations are precisely the union. ∎

Empirically [3], selective merging cut explored paths by *orders of magnitude* on Coreutils-derived benchmarks — while QCE guards the failure mode where disjunctions overwhelm the solver. The enduring contribution: merging reframed from a binary choice into an *optimization problem*.

### 4.4 Veritesting: The Static–Dynamic Spectrum

Avgerinos, Rebert, Cha, and Brumley's **veritesting** [2] pushes merging to its static extreme. Dynamic execution forks even on *trivial* code — a 20-deep nest of simple `if`s with no syscalls generates a million states for what one disjunctive formula could capture. Veritesting hybridizes DSE with static symbolic execution (SSE):

1. Execute **concolically** from a seed input (as in Mayhem [2]).
2. When the upcoming CFG region is *veritestable* — bounded, no syscalls, no symbolic indirect jumps — switch to **SSE**: symbolically execute the region *without forking*, accumulating one large ite-formula, as a VC generator would.
3. Merge all region paths into a single state carrying the disjunctive summary; resume DSE.

*Transition points* (syscalls, symbolic indirect control flow) force return to DSE. MergePoint builds on BAP for CFG recovery, PIN for instrumentation, and Z3 [2]. Its evaluation scaled remarkably: over *all Debian binaries*, veritesting covered more code and found more bugs than DSE alone in equal budgets — the exponentially smaller path count outweighs larger per-query cost [2].

The conceptual spectrum [3]: DART/KLEE (fork every branch) → dynamic merging (opportunistic) → veritesting (region summaries) → BMC (whole-program formula). Each step rightward cuts path count exponentially while raising per-query burden; the art is choosing the operating point per region.

### 4.5 Compile-Time Symbolic Execution: SymCC

KLEE interprets LLVM bitcode; angr interprets VEX; Mayhem lifts x86 — interpretation imposes 10–100× slowdown, and executors spend most time in the interpreter loop, not the solver. **SymCC** [4] eliminates it: a *compiler wrapper* injecting symbolic-backend calls into LLVM IR at compile time. The instrumented binary runs near-natively; concrete computations proceed untouched (guarded by *concreteness checks* skipping backend calls when no input is symbolic), while symbolic computations build expressions and report branches to the runtime driving concolic exploration.

Source → clang with SymCC pass → instrumented bitcode → native binary linked against the runtime library. Compiler optimizations (constant folding, DCE) *simplify the symbolic workload for free* — unobtainable for interpreters. Evaluation [4] shows SymCC beating QSYM with statistical significance on benchmarks and real targets (OpenJPEG, libarchive, tcpdump), finding CVEs 2020-6851 and 2020-8112 that QSYM missed. SymQEMU later ported the philosophy to binaries via QEMU's TCG [4].

The strategic lesson: *countermeasures multiply with execution speed*. Every technique in 4.2–4.4 gains when each path costs less, since fixed budgets then cover exponentially more program. Compile-time instrumentation is thus a complement to the algorithmic techniques, not mere engineering.

## 5. Empirical Results and Formal Proofs

### 5.1 KLEE's Coreutils and BusyBox Campaign

KLEE's evaluation [1] is the empirical gold standard. Method: compile each of 89 Coreutils utilities, link the POSIX model, run KLEE with symbolic `argv` (≤3 args) and stdin under per-tool budgets, replay generated tests on unmodified binaries, measure line coverage with `gcov`:

| Target | Programs | Mean line coverage | Notable bugs |
|---|---|---|---|
| GNU Coreutils | 89 | >90% (median >94%) | 3 bugs missed for 15+ years |
| BusyBox | 75 | higher; 100% on 31 tools | divergences vs Coreutils |
| Bug-finding corpus | 452 apps, 430 KLOC | — | 56 serious bugs |

The cross-checking experiment is illuminating: running KLEE-generated Coreutils tests against BusyBox equivalents exposed functional divergences — *differential* symbolic execution needing no specification, only the assumption the implementations should agree [1]. Coverage beat developers' hand-written suites on most tools, establishing symbolic execution as complementary to human testing.

### 5.2 Soundness and Completeness

> **Theorem 4 (No False Positives).** *If a forking executor reports an error on path condition π, then π is satisfiable and its model drives the concrete program to the same error. Every reported bug is genuine.*
>
> *Proof sketch.* Feasibility checks make π satisfiable by construction; the solver's model replays deterministically to the error. ∎

> **Theorem 5 (Relative Completeness).** *Modulo solver decidability, resource bounds, and model fidelity, a fair-search forking executor explores every feasible bounded path. Concolic executors with concretization are complete only relative to concretization choices.*
>
> *Proof sketch.* Fair scheduling visits every live state; forks preserve all feasible successors. Concretization substitutes constants for symbolic subterms, possibly pruning feasible paths — hence the relativization. ∎

The contract: symbolic execution is *sound* (no false alarms) but *practically incomplete* (bounds, undecidable theories, modeled environments). Merging (Theorem 3) and independence splitting (Theorem 2) preserve soundness exactly; concretization and state killing are the deliberate, bounded sacrifices.

### 5.3 Comparative Cost Model

Let *b* symbolic branches, *q* mean solver cost, *m* merge-induced inflation:

| Technique | States | Per-query cost | Total (order) |
|---|---|---|---|
| Pure forking (KLEE) | 2^b | q | O(2^b · q) |
| + independence/caching [1] | 2^b | q/k, k≈10–100 | O(2^b · q/k) |
| + selective merging [3] | 2^β, β≪b | m·q | O(2^β · m · q) |
| + veritesting [2] | O(regions) | M·q, M≫m | O(R · M · q) |
| + compile-time (SymCC) [4] | as base | c·q wall-time, c≪1 | scaled by 1/c |

The design space made explicit: caching divides the constant, merging/veritesting attack the exponent, compile-time execution divides wall-clock cost. Production systems stack all of them.

## 6. Limitations

**The expressiveness–scalability trade-off is fundamental.** Each Section 4 technique buys scalability by surrendering precision: concretization sacrifices feasibility, merging sacrifices query simplicity, state killing sacrifices completeness, models sacrifice fidelity. There is no free lunch — only better operating points [6].

**Solver incompleteness.** Nonlinear arithmetic, hashes, and floating-point routinely defeat QF_ABV solvers. Concolic concretization handles these *unsoundly-but-usefully*; pure symbolic engines stall. Hence DART-style concretization remains the industrial default [5][6].

**Environment fidelity.** KLEE's POSIX model covers common calls, but networks, GUIs, databases, and racy concurrency are unmodeled. Under-modeling yields false negatives; whole-system over-approximation (S2E) reintroduces explosion at the OS boundary [6].

**Merging can backfire.** Disjunctive formulas can overwhelm solvers so badly that merging *reduces* throughput [2][3]; QCE is heuristic and adversarial programs defeat it. Veritesting's static regions must be conservatively bounded, and transition-point detection on stripped binaries is fragile.

## 7. Conclusion

This thesis traced the arc from symbolic execution's 1970s formulation, through the DART/CUTE concolic revival [5], to KLEE's demonstration that automatic high-coverage testing of real systems software is achievable [1] — and through the countermeasure families that make it scale: solver redundancy elimination via independence and counterexample caching; QCE-guided state merging [3]; veritesting's static–dynamic hybridization [2]; and compile-time instrumentation removing the interpreter tax [4]. The unifying principle: path explosion is a *budget allocation* problem across states, queries, and wall-clock time, and each technique rebalances the trade-off between paths explored and cost per path.

The formal core (Theorems 1–5) shows the precision sacrifices are *characterizable*: merging and independence splitting are exactly sound; concretization and state killing are the explicit, bounded sources of incompleteness. Empirically, the stacked techniques deliver what none could alone: >90% Coreutils coverage, dozens of long-lived bugs, order-of-magnitude concolic speedups.

Open directions: *compositional* symbolic execution — function summaries scaling with interfaces rather than paths — is the most promising route past the exponential barrier [3][6]. Learned, solver-aware merge policies could adapt the forking/merging operating point per program. And hybrid fuzzing (Driller/QSYM lineage) suggests the future belongs to portfolios spending each budget where it buys the most coverage. Path explosion will never be *solved*; the research program is to keep renegotiating its terms — and, from KLEE to SymCC, each renegotiation finds real bugs in real software.
