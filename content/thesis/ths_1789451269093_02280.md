## Abstract

Rust's borrow checker statically enforces an aliasing discipline — no mutable aliasing, no conflicting use of borrowed data — that underpins both memory safety and aggressive compiler optimization. Yet the *unsafe* fragment of the language, in which raw pointers bypass these checks entirely, requires a precise dynamic contract: what aliasing rules must raw-pointer code obey so that the optimizer's assumptions remain sound? This thesis surveys the research answering that question. We trace the static story from non-lexical lifetimes to the Datalog-based Polonius reformulation deployed as Polonius Alpha, then develop the two operational aliasing models defining de-facto undefined behavior for unsafe Rust: **Stacked Borrows** [1], which tags every pointer and maintains a per-location borrow stack, and **Tree Borrows** [2], which replaces the stack with a permission tree and rejects 54% fewer real-world test cases while retaining the key optimization guarantees. We connect both to the semantic foundations of RustBelt [3] and their enforcement in the Miri interpreter [4], and evaluate the empirical evidence from large-scale crate and foreign-function-interface studies [5] that these models permit the unsafe idioms the ecosystem depends on.


##1 Intro

Rust is unusual among systems languages in that its type system is not merely a safety device but an *optimization contract*. The ownership and borrowing rules — each value has a single owner; a value may be immutably borrowed arbitrarily often or mutably borrowed exactly once, but not both simultaneously — guarantee the absence of data races and dangling pointers in safe code. The compiler would like to exploit these guarantees: if a function takes an exclusive reference `&mut T`, the optimizer can assume no other code path mutates that memory, and reorder accesses around calls to unknown code. But this is only legitimate if *unsafe* code, which manipulates raw pointers with no static aliasing restrictions, obeys a set of rules strong enough to justify the optimizer's reasoning. Without such rules, every type-based aliasing optimization is unsound in the presence of unsafe code — and Rust's standard library is built on unsafe code.

The formalization of this contract has proceeded on two fronts. On the static front, the borrow checker itself has been reformulated: non-lexical lifetimes [8] recast lifetime inference as a flow analysis over control-flow graphs, and the Polonius project [7] re-expresses borrow checking in Datalog for flow-sensitivity. On the dynamic front, the aliasing models **Stacked Borrows** [1] and **Tree Borrows** [2] give operational semantics for memory accesses: an instrumented interpreter (Miri [4]) tracks extra borrow state per allocation and declares programs that violate the aliasing discipline to be undefined behavior, giving the compiler a precise license to optimize.

This thesis presents a unified account of these efforts: the static background, both aliasing models with worked examples, the mechanized proofs of optimization soundness, the empirical validation on tens of thousands of crates, and the open problems that remain.


##2 Background

### 2.1 Ownership, borrowing, and lifetimes

Rust's ownership system assigns every value a unique *owner*. Ownership can be transferred (moved) or temporarily lent (*borrowed*) through references, written `&T` for shared borrows and `&mut T` for exclusive borrows. The borrow checker's central invariant is that while a borrow is *live* — the interval of the program during which the reference may still be used — the borrowed place cannot be accessed in a conflicting way.

The original borrow checker computed lifetimes lexically, from syntactic scopes. Non-lexical lifetimes (NLL), shipped in the 2018 edition following RFC 2094 [8], compute liveness from the control-flow graph instead: a borrow's lifetime ends at its last use, not at the end of the enclosing block. NLL is flow-insensitive in an important sense, however: its outlives analysis does not account for the fact that a borrow may be dead along some paths. The Polonius project, begun by Nicholas Matsakis in 2018, reformulates the analysis declaratively in Datalog [7], enabling a flow-sensitive analysis of lifetime outlives relationships. The concrete payoff is familiar to practitioners:

```rust
fn get_mut_or_default<K: Hash + Eq + Copy, V: Default>(
    map: &mut HashMap<K, V>,
    key: K,
) -> &mut V {
    match map.get_mut(&key) {
        Some(value) => value,
        None => {
            map.insert(key, V::default());
            map.get_mut(&key).unwrap()
        }
    }
}
```

Under NLL, the `Some(value) => value` arm forces the borrow returned by `map.get_mut(&key)` to be considered live for the entire function body, because the return type demands it — even though that borrow is dead in the `None` arm where `map.insert` needs a fresh mutable borrow. The borrow checker rejects the program. Polonius Alpha, enabled by default on nightly in August 2026 [7], performs a flow-sensitive analysis that knows the borrow is not live in the `None` branch, and accepts it. This is the static half of the story; it governs safe code.

### 2.2 Unsafe Rust and the specification gap

Safe Rust cannot express everything a systems language needs: dereferencing raw pointers, calling foreign functions, implementing lock-free data structures. The `unsafe` keyword marks regions where the programmer, not the compiler, guarantees memory safety. Raw pointers `*const T` and `*mut T` carry no borrow information and are exempt from the borrow checker entirely.

The specification gap is then: **what aliasing rules do raw pointers obey?** LLVM's `noalias` metadata assumes that pointers derived from `&mut T` do not alias in ways the type system forbids, and rustc emits such metadata. If unsafe code violates those assumptions, miscompilation follows — silently. Stacked Borrows [1] was the first proposal to give this the status of a formal operational semantics with mechanized proofs, validated against the standard library test suite.

### 2.3 Operational semantics as specification technique

Both aliasing models follow the same methodological template [1][2]. Rather than axiomatizing undefined behavior declaratively, they *instrument* an interpreter: every allocation carries extra metadata (a borrow stack or a permission tree), every pointer value carries a tag identifying the borrow it derives from, and every memory access performs two steps — a *proof obligation* (the tag must still be authorized) and an *operational effect* (the access updates the metadata, possibly invalidating other tags). A program that fails a proof obligation is declared undefined behavior. This dynamic characterization doubles as the compiler's optimization license: any transformation valid for all programs passing the checks is sound.


##3 Methodology

Our exposition follows the primary sources directly. The formal content is drawn from the Stacked Borrows POPL 2020 paper and its Coq development [1], the Tree Borrows PLDI 2025 paper and its Rocq development [2], Ralf Jung's dissertation [6], and the Miri POPL 2026 paper [4]. The static-checker material follows the Rust blog announcement of Polonius Alpha [7] and the NLL RFC [8]. The empirical claims are taken from the papers' own evaluations: the 30,000-crate study in [2] and the foreign-function-interface study [5].

We adopt a uniform notation. Memory is a map from locations to values plus borrow metadata. A pointer value is a pair of a location and a tag, written `(l, t)`. Tags are natural numbers assigned in allocation order, with `⊥` denoting the untagged raw pointers produced by casts. We describe the models as state machines over these structures and illustrate them with small Rust programs, tracing the metadata step by step.

##4 Deep Dive

### 4.1 The static story, completed: from NLL to Polonius Alpha

The borrow checker's job can be stated as computing, for each program point, the set of *loans* (active borrows) and checking that conflicting loans never coexist. NLL [8] formulates this as constraint solving over *regions*: sets of points in the MIR (mid-level intermediate representation) control-flow graph. For each borrow expression, the checker introduces a region variable; constraints of the form `'a: 'b` (region `'a` outlives `'b`) flow from the type system; liveness analysis determines where each region must be live.

The limitation NLL cannot escape within its architecture is flow-insensitivity of outlives reasoning, as the `get_mut_or_default` example shows. Polonius recasts the entire analysis as Datalog rules [7]: facts about the program are fed to a fixpoint solver that computes derived facts such as "loan L is live at point P" and "region R1 outlives R2 at point P". Because the solver reasons per program point, outlives relationships become flow-sensitive. The engineering history is instructive: the original Datalog-based Polonius was too slow for production, so the 2023 "Polonius revisited" formulation re-architected the existing NLL implementation minimally, and "Polonius Alpha" — a native rustc implementation — was enabled on nightly in August 2026 with no known remaining soundness issues and acceptable performance [7].

### 4.2 Stacked Borrows: stacks, tags, and retagging

Stacked Borrows [1] equips every memory location with a *borrow stack*: a list of items, each either `Unique(t)` for a mutable borrow with tag `t`, `SharedReadOnly(t)` for a shared borrow, or `SharedReadWrite` for raw pointers. Creating `&mut T` performs a *retag*, assigning a fresh tag `t` and pushing `Unique(t)`; creating `&T` pushes `SharedReadOnly(t)`; casting `&mut T` to `*mut T` first uses the reference and then pushes `SharedReadWrite` with the untagged marker `⊥`.

Every use of a pointer `(l, t)` then obeys two rules [1]:

> **Theorem (Stack discipline):** For every use of a pointer value `(l, t)`: (i) the *proof obligation* requires that the item matching `t` be present in the borrow stack of `l` — `Unique(t)` for a tagged reference, or `SharedReadWrite` anywhere in the stack for the untagged `⊥`; (ii) the *operational effect* pops every item above the matching item. If the matching item is absent, the program has undefined behavior.

The popping rule is the heart of the model: using an older borrow invalidates all newer, conflicting borrows — the dynamic analogue of the borrow checker's exclusivity rule. Consider the canonical example:

```rust
fn main() {
    let mut x = 0;                       // stack: [Unique(0)]
    let xref = &mut x;                   // retag: stack: [Unique(0), Unique(1)]
    let raw = xref as *mut i32;          // use xref, push: [Unique(0), Unique(1), SharedReadWrite]
    *xref = 1;                           // pops SharedReadWrite: [Unique(0), Unique(1)]
    unsafe { *raw = 2; }                 // SharedReadWrite not in stack -> UB
    *xref = 3;
}
```

The write through `raw` after `*xref = 1` is undefined behavior: the raw pointer's `SharedReadWrite` item was popped when `xref` was used. Note what this captures that the static checker cannot: the invalidation is *temporal* and *flow-dependent*, arising only from the actual execution order. The model also handles the subtle cases that motivated its design: two-phase borrows (used in method-call autoref), interior mutability via `UnsafeCell` (exempted from the stack discipline, mirroring the language's escape hatch), and the "protector" mechanism that forbids invalidating a reference passed as a function argument for the duration of the call [1].

```haskell
data Item = Unique Tag | SharedReadOnly Tag | SharedReadWrite
  deriving (Eq, Show)
type Tag = Int
type Stack = [Item]

-- A memory access: find the granting item, pop everything above it.
access :: Tag -> Stack -> Either String Stack
access t stack = case findIndex (grants t) stack of
  Nothing -> Left "UB: tag not present in borrow stack"
  Just i  -> Right (take (i + 1) stack)
  where
    grants ⊥ SharedReadWrite = True
    grants t (Unique t')      = t == t'
    grants t (SharedReadOnly t') = t == t'
    grants _ _               = False
```

The Coq mechanization in [1] proves the payoff: this discipline justifies the optimizations rustc wants — reordering reads across unknown code, eliminating redundant reads after writes through `&mut` — using only intraprocedural reasoning, via a simulation argument relating optimized and source executions.

### 4.3 Tree Borrows: permissions in a tree

Stacked Borrows was validated against the standard library test suite, but as unsafe code in the wild was exercised, patterns emerged that the stack discipline rejects yet experienced programmers consider legitimate [2]. The canonical failure is the *reborrow-after-raw-write*: code that creates `&mut`, derives a raw pointer, writes through the raw pointer, and then uses the original `&mut` again. The stack pops the reference's item on the raw write; the subsequent use is UB. Real code — including, famously, fragments of the standard library's own `Vec` and `RefCell` implementations — does this.

Tree Borrows [2] replaces the per-location stack with a per-allocation *tree* of permission nodes. Each pointer maps to a node; the root represents the allocation itself. Nodes carry permissions drawn from a state machine:

| Permission | Meaning |
|---|---|
| `Reserved` | A mutable borrow not yet written through; may become `Active` on first write |
| `Active` | Currently usable for both reads and writes |
| `Frozen` | Read-only (shared borrows, and references never written through) |
| `Disabled` | Permanently invalidated; any access is UB |

The key structural difference: on a conflicting access, Tree Borrows does not pop a stack — it *transitions* the affected nodes and their descendants to `Disabled`, while unrelated branches survive. A raw-pointer write disables the sibling subtree containing the raw pointer's node but leaves the original `&mut` node intact (as `Reserved`, becoming `Active` when written through). The example that Stacked Borrows rejects is accepted.

Two further refinements distinguish the models. First, Tree Borrows *delays* the validity assertion: a reference need only be valid when first used, not at creation — accommodating two-phase borrows, which Stacked Borrows handles only through special machinery [2]. Second, Tree Borrows permits a valid permission to access *any* location within its allocation, whereas Stacked Borrows confines each borrow to the exact range it borrowed; the FFI study [5] documents accesses that Stacked Borrows flags and Tree Borrows accepts. The trade is not free: the `Reserved` permission makes Tree Borrows *less* permissive than Stacked Borrows for certain aliasing patterns, notably where a mutable reference is passed around but never written through [5].

### 4.4 What unsafe code may and may not do

The verdicts:

1. **Reborrow after raw-pointer write.** `let r = &mut x; let p = r as *mut T; *p = v; *r = w;` — *UB* under Stacked Borrows (the raw write pops `r`'s item), *allowed* under Tree Borrows (the write disables only its own branch) [2].
2. **Read-only sharing then mutation.** `let a = &x; let b = &x;` followed by a write through a raw pointer derived from `&mut x` — *UB* under both models: the write conflicts with the `SharedReadOnly`/`Frozen` items.
3. **Two-phase borrows.** `vec.push(vec.len())` — the autoref borrow of `vec` for the method receiver overlaps the argument borrow. Stacked Borrows requires dedicated two-phase machinery; Tree Borrows handles it uniformly by deferring validity to first use [2].
4. **Protector violations.** Passing `&mut T` to a function and invalidating it inside the callee — *UB* under both models: the argument's permission is *protected* for the call's duration [5].
5. **Interior mutability.** Accesses through `UnsafeCell` bypass the aliasing discipline in both models, matching the language's designated escape hatch [1].

These verdicts are not academic: Miri implements both models (Stacked Borrows as default, Tree Borrows via `-Zmiri-tree-borrows`), and the Miri POPL 2026 paper describes it as the first tool able to detect all de-facto undefined behavior in deterministic Rust programs, integrated into the standard library's own CI [4].

### 4.5 Optimization soundness: what each model buys the compiler

An aliasing model earns its keep by justifying optimizations. Stacked Borrows was proven, in Coq, to permit the two transformations rustc cares about most [1]: moving reads of `&mut`-derived locations across calls to unknown code (any such call writing through an alias would have popped the item — contradicting the successful read), and forwarding a value read before a call to a read after it. The proofs are intraprocedural, which is exactly the compiler's setting.

Tree Borrows retains *most* of these optimizations — proven in Rocq [2] — and additionally enables *read-read reorderings*: because `Frozen` permissions are stable under reads from any branch, two reads through different pointers may be reordered even when Stacked Borrows' popping semantics would forbid it. This is not a free upgrade: hoisting a write out of a loop is unsound under Tree Borrows when the loop body might execute zero times, because a `Reserved` permission only becomes `Active` (writable) upon an actual write — the optimized program would introduce a write where none existed. Recovering such optimizations by making Tree Borrows more restrictive in targeted ways is ongoing work.

##5 Empirical/Proofs

The evidence for these models comes in two kinds: mechanized proof and large-scale dynamic validation.

**Mechanized proofs.** Stacked Borrows' optimization theorems are fully mechanized in Coq [1]; Tree Borrows' are mechanized in Rocq, covering both the retained Stacked Borrows optimizations and the new read-read reorderings [2]. Beneath both lies RustBelt [3]: a model of Rust's type system in the Iris separation logic, mechanized in Coq, which introduced the *lifetime logic* — a novel logical account of borrowing — and proved type-system soundness including tricky standard-library APIs (`Cell`, `Rc`, `Arc`) implemented with unsafe code. Jung's dissertation [6] unifies the two projects, presenting Stacked Borrows as the dynamic counterpart to RustBelt's static semantics.

**Large-scale validation.** The Tree Borrows evaluation ran the test suites of the 30,000 most widely used crates under both models in Miri [2]. Tree Borrows rejected **54% fewer test cases** than Stacked Borrows, quantifying the permissiveness gain on real-world unsafe idioms while the Rocq proofs pin down which optimizations survive. A complementary study executed Rust libraries calling foreign functions under Miri jointly with an LLVM interpreter, finding 46 instances of undefined or undesired behavior across 37 libraries — including three averaging over 10,000 daily downloads and one maintained by the Rust project itself — and confirming Tree Borrows is significantly more permissive than Stacked Borrows on FFI-heavy code [5].

**Tooling reality.** Miri's POPL 2026 paper [4] establishes it as the reference implementation of both models (Stacked Borrows by default, Tree Borrows via `-Zmiri-tree-borrows`) and documents its integration into the standard library's CI. The Python sketch below illustrates the shared empirical methodology: differential testing of the two models over a corpus, counting rejections.

```python
def evaluate(models, corpus):
    """Differential evaluation of aliasing models over a test corpus."""
    results = {m: {"rejected": 0, "total": 0} for m in models}
    for test in corpus:                      # e.g. 30k crates' test suites
        for m in models:
            verdict = miri_run(test, aliasing_model=m)
            results[m]["total"] += 1
            if verdict is UB_ALIASING:
                results[m]["rejected"] += 1
    for m in models:
        r = results[m]
        print(f"{m}: {r['rejected']}/{r['total']} rejected")
    # Tree Borrows rejects ~54% fewer than Stacked Borrows [2]
```


##6 Limitations

No current model is the final specification, and the papers are candid about the gaps.

**Patterns Tree Borrows still rejects.** The `Reserved` permission makes Tree Borrows stricter than Stacked Borrows on code that passes a `&mut` around without writing through it [5]. The loop-write-hoisting example of section 4.5 shows a real optimization the model currently forbids; whether the fix is to restrict the model or bless the pattern is an open design question.

**Patterns both models reject that the ecosystem disputes.** Protector violations on function arguments remain controversial: is it truly undefined behavior to free an allocation through a raw pointer derived from a `&mut` argument, when the reference is never used again? Tree Borrows says yes [5]; some systems programmers consider this overly strict.

**The static checker's own incompleteness.** Polonius Alpha accepts strictly more programs than NLL, but it is not complete relative to the original Datalog Polonius — programs exist that compile under legacy Polonius but not Alpha, and vice versa [7]. The borrow checker remains an approximation of the aliasing discipline, not its definition.

**Dynamic checking is inherently partial.** Miri detects undefined behavior only along executed paths. Concurrency is covered only by a data-race detector, not a full weak-memory model, and nondeterministic inputs bound what "all de-facto UB in deterministic programs" [4] can promise.

**No blessed specification yet.** Perhaps the deepest limitation is sociological: neither Stacked Borrows nor Tree Borrows is the official Rust specification. Unsafe code authors today must choose which model to validate against, knowing the answer may change.


##7 Conclusion

The formalization of Rust's aliasing discipline is one of the most sustained interactions between programming-language theory and an industrial language in current practice. The static line — from lexical lifetimes through NLL's flow analysis to Polonius's Datalog formulation and its nightly deployment as Polonius Alpha [7][8] — has made the borrow checker accept more of the programs programmers consider correct. The dynamic line — from Stacked Borrows' per-location stacks with mechanized optimization proofs [1], through RustBelt's semantic foundations in Iris [3], to Tree Borrows' permission trees with their 54% reduction in false rejections on 30,000 crates [2] — has given unsafe code a precise, checkable, and increasingly permissive contract, enforced daily by Miri in the standard library's own CI [4].

What remains is the hardest step — not a better model but a *blessed* one: a specification the language team and the community can jointly commit to, so that every raw pointer in every crate has an unambiguous answer to the question of what it may do. Until then, Stacked Borrows and Tree Borrows stand as the two best-articulated candidates, and the distance between them measures exactly how much of unsafe Rust we have yet to fully understand.
