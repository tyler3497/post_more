# Verified Parsing of Binary Data Formats: EverParse, Dependent Data Descriptions, and the F*-Based Assurance of Zero-Copy Parsers and Serializer Duality

## Abstract

Message parsing remains one of the most heavily exploited attack surfaces in systems software, yet parser development is still largely an ad hoc craft vulnerable to buffer overflows, integer overflows, and differential-parsing ambiguities [6]. This thesis gives a comprehensive account of *verified parsing* as pioneered by **EverParse**, which generates verified zero-copy parsers and serializers from dependent data descriptions [1]. We survey the **LowParse** verified combinator library embedded in F*, the **3D** specification language with its three machine-checked denotations — type, parser, and validator — related by refinement theorems [3], and the parser–serializer duality guaranteeing round-trip inversion. We contrast this proof-based lineage with **Nail**, a grammar-driven generator whose single-source specifications eliminate format-description inconsistencies through dependent fields and transformations [6]. Drawing on real deployments — TLS 1.0–1.3 in miTLS, the IETF QUIC record layer [5], and Hyper-V kernel message parsers in production since 2022 — we examine empirical performance, non-ambiguity and injectivity proofs, and the practical limits of SMT-driven automation. We conclude that verified parsing has crossed the threshold from research prototype to a practical hardening technique for critical attack surfaces.

## 1. Introduction

Few components of modern software fail as spectacularly as parsers. A parser is the program's first point of contact with untrusted input, and defects in parsing logic — length miscalculations, unchecked pointer arithmetic, confusion between syntactic and semantic validation — have underwritten decades of remote code execution vulnerabilities, from the Android ZIP signature verification bug to repeated TLS parser flaws [6]. The LangSec movement argues that this is not merely a bug-density problem but a *design* problem: security-relevant input should be described by a formal grammar, and the code that processes it should be generated from — or proven against — that grammar.

Two research lineages have pursued this vision for binary formats. The first, exemplified by **Nail**, treats a grammar as a single source of truth from which the in-memory data type, the parser, and the output generator are all derived, eliminating the inconsistencies that arise when the same format is described three separate times in grammar, data structures, and semantic actions [6]. The second, exemplified by **EverParse**, goes further: it generates parsers *and* serializers in C from high-level format specifications and proves, mechanically in the F* proof assistant, that the generated code is memory-safe, functionally correct, and that parsing is the inverse of serialization [1].

This thesis studies the EverParse lineage in depth. Its contributions are: (i) a precise exposition of the LowParse verified combinator library and its zero-copy parsing discipline; (ii) an account of the 3D language ("Dependent Data Descriptions") and its three denotations — type denotation, parser denotation, and validator denotation — connected by machine-checked refinement theorems [3]; (iii) an analysis of the parser–serializer duality, injectivity, and non-ambiguity proofs that give EverParse its security guarantees; (iv) a comparative treatment of Nail's dependent fields and transformations; and (v) an empirical review of real-world deployments and measured performance. Throughout, we anchor claims in published artifacts: the USENIX Security 2019 EverParse paper [1], the PLDI 2022 EverParse3D paper [3], the IEEE S&P 2021 verified QUIC record layer [5], the OSDI 2014 Nail paper [6], and the project's public documentation and source releases [2][7].

## 2. Background

### 2.1 F*, Low\*, and KaRaMeL

EverParse is built on **F***, a general-purpose functional programming language with *dependent types* aimed at program verification [1]. In F*, types may mention program values, so a function's contract — its preconditions, postconditions, and even memory-safety invariants — can be written as part of its type; an SMT solver (Z3) then discharges most proof obligations automatically, with interactive tactics (Meta-F*) available for the remainder [1]. F* programs targeting systems code are written in a low-level subset, **Low\***, which models the C memory model explicitly, and compiled to C by **KaRaMeL**, a verified extraction pipeline that preserves the semantics proved in F* [1]. This stack — specification in dependent types, proof by SMT automation, extraction to C — is what makes *verified* parsing attainable at industrial scale: the proofs live in F*, and the deployed artifact is ordinary, fast C.

### 2.2 Parser combinators and the zero-copy discipline

At the core of EverParse lies **LowParse**, a verified library of parsing and serialization combinators [1]. A parser combinator in LowParse is not merely a function from bytes to values: it is a specification-indexed computation whose type records exactly the set of byte sequences it accepts and the values it produces. The crucial design decision is **zero-copy parsing**. Rather than deserializing input into freshly allocated structures, LowParse validators *validate in place*: they scan the input buffer, check all length and tag constraints, and return *slices* — pointers into the original buffer — that the application can read directly. No copying occurs, no allocation failure modes are introduced, and the memory-safety proof reduces to showing that every slice lies within the bounds of the input buffer. This is both a performance choice (parsing at near hand-written speeds) and a verification choice: fewer allocations mean a smaller trusted reasoning surface.

### 2.3 The LangSec context and Nail

The LangSec community has long argued that input-handling code must be generated from declarative format descriptions. **Nail** (OSDI 2014) embodies a pragmatic version of this idea: a single Nail grammar describes a binary format *and* the internal data type representing it, from which Nail generates both a parser and an output generator [6]. Nail's two key abstractions are **dependent fields**, which capture fields whose values depend on other parts of the format (length fields, offsets, checksums), and **transformations**, which let programmers write custom code for structures Nail's core cannot express, while keeping the generated parser and generator consistent by construction [6]. Nail's DNS server (300 lines) and unzip implementation (220 lines) demonstrated that grammar-generated code could be both compact and competitive with hand-written parsers — the Nail DNS server outperformed BIND on authentication workloads [6]. Nail does not, however, produce *proofs*: its guarantees are by-construction consistency (a semantic bijection between the external format and the internal model) rather than machine-checked theorems. EverParse can be read as Nail's formally verified successor, replacing by-construction discipline with mechanically checked proof.

## 3. Methodology

Our methodology is expository and comparative, grounded in primary sources. We reconstruct EverParse's architecture from the USENIX Security 2019 paper [1] and the project's living documentation [2]; the 3D language semantics and refinement theorems from the PLDI 2022 EverParse3D paper [3]; deployment evidence from the IEEE S&P 2021 verified QUIC record layer [5] and the Microsoft Research retrospective [7]; and the grammar-based alternative from the Nail paper [6]. The central technical thread we trace is the *three-denotation* methodology of 3D:

1. **Type denotation** — a 3D program denotes an F* type of the values the format describes.
2. **Parser denotation** — the same program denotes a pure function from byte sequences to values, the mathematical specification of the wire format.
3. **Validator denotation** — the program denotes an imperative Low\* program that validates a byte stream while executing user-supplied parsing actions.

The main theorem, mechanically checked in F*, states that the validator *refines* the parser, which in turn parses values of the type denotation [3]. This single theorem collapses the gap between specification and implementation: if the validator accepts a buffer, the buffer denotes a well-typed value, and the value is exactly what the pure parser function would produce.

```fstar
(* Simplified sketch of the refinement statement in the style of [3] *)
val validator_refines_parser :
  t:threed_type ->
  Lemma (forall (input: bytes).
    validator t input == Accepts ==>
    parser t input == Some (value_of input) /\
    value_of input `has_type` t)
```

Alongside this, EverParse maintains a **duality invariant**: every parser is paired with a serializer, and the framework proves that serialization is a left inverse of parsing and that parsing is injective — i.e., each value has at most one valid binary representation [5]. This is the formal content of "parsing is the inverse of serialization" from the EverParse abstract [1], and it is what rules out the *differential parsing* vulnerabilities (two components disagreeing on the meaning of the same bytes) that plague ad hoc implementations.

## 4. Deep Dive

### 4.1 LowParse: verified combinators for zero-copy validation

LowParse structures parsing as a hierarchy of *validators* rather than deserializers. A validator for a type `t` is a Low\* function that takes a pointer and a length and either rejects the input or returns the number of bytes consumed, leaving the validated bytes in place for the application to read through accessor functions [1]. Combinators compose validators: sequencing, choice, repetition, and — critically — *data-dependent* combinators where the parse of a later field depends on the *value* of an earlier one (length-prefixed arrays being the canonical example).

```python
# Conceptual Python model of a LowParse-style zero-copy validator
def validate_tlv(buf: bytes, off: int):
    """Validate a tag-length-value record in place; return end offset."""
    if off + 4 > len(buf):
        return None                      # reject: truncated header
    tag = buf[off]
    length = int.from_bytes(buf[off+1:off+4], "big")
    end = off + 4 + length
    if end > len(buf) or end < off:      # reject: overflow / overrun
        return None
    # zero-copy: the value is buf[off+4:end]; nothing is allocated
    return end
```

The verification burden is to prove, for each combinator, *frame* properties (untouched memory is unchanged), *safety* (no out-of-bounds access, no integer overflow), and *correctness* (acceptance coincides with the pure parser denotation) [1]. Because combinators are proved once in the library, each new format inherits these properties by composition — the per-format proof effort is limited to the 3D-level refinement theorem, which 3D's code generator discharges mostly automatically [3].

### 4.2 The 3D language: three denotations, one theorem

**3D** ("Dependent Data Descriptions") is EverParse's C-like front end: format authors write what look like C `struct`, `enum`, and `union` definitions, extended with *data dependencies* — fields whose types or constraints mention earlier fields — and bit-level precision [3]. From one 3D source, EverParse3D generates verified C validators plus F* specifications. The PLDI 2022 paper gives 3D three semantic denotations inside F* and proves the refinement chain validator ⊑ parser ⊑ type [3]:

> **Theorem 1 (3D refinement, informal).** *For every well-formed 3D program P, the generated C validator accepts an input buffer b iff the pure parser denotation of P maps b to a value v, and every such v inhabits the type denotation of P [3].*

This is stronger than it looks. Because the validator runs *user-provided parsing actions* during validation, the theorem also covers the application's view of the data: the actions observe exactly the values the pure parser would compute. In effect, 3D gives programmers a C-flavored syntax while the framework maintains a fully formal semantics — the "external source of truth" (an RFC, legacy code) is transcribed once into 3D, and everything downstream is proved [3].

### 4.3 Parser–serializer duality and round-tripping

EverParse generates not only parsers but *serializers*, and proves them dual [1][5]. The duality comprises two directions:

- **Serialization is a left inverse of parsing** (round-trip): for every value `v`, `parse (serialize v) = v`.
- **Parsing is injective**: if `parse b₁ = parse b₂ = v` (both succeed), then `b₁ = b₂` — each value has a *unique* binary encoding.

Injectivity is the deep security property. Non-injective encodings are the root cause of signature-verification bypasses (the same logical message with two byte representations, only one of which was signed) and of parser differentials. The EverQUIC work [5] made this concrete: expressing QUIC's packet-number truncation and recovery in EverParse yielded an automatic proof that there is at most one valid binary representation of each QUIC packet header — and the verification effort *found two bugs* in the IETF reference implementation's packet-number expansion (an off-by-one and an overflow), both fixed in draft 24 following the report [5].

### 4.4 Nail: dependent fields, transformations, and the semantic bijection

Nail approaches the same problem without a proof assistant. A Nail grammar simultaneously defines the external format and the internal data model; the generator emits type declarations, a parser, and a *generator* (serializer) from that single source [6]. Two mechanisms handle real-world awkwardness:

1. **Dependent fields** (written `@field` in Nail grammars) capture fields whose values are computed from the rest of the message — e.g., `@ac uint16` counts in a DNS packet that must equal the number of answer records that follow. The parser *reads* them; the generator *recomputes* them, so they can never be inconsistent [6].
2. **Transformations** allow arbitrary C code for structures like compression pointers or checksums, with the parser-side and generator-side transforms kept dual by the grammar structure [6].

Nail thus achieves a *semantic bijection* between bytes and values by construction. Its limitation is precisely what EverParse supplies: Nail's guarantees are only as strong as its generator's implementation, whereas EverParse's are theorems checked by F* and Z3 [1][6].

### 4.5 Non-ambiguity proofs and semantic equivalence with protocol grammars

A subtle verification target is **non-ambiguity**: the guarantee that no input admits two distinct parses. In EverParse this falls out of the injectivity half of the duality — a pure parser denotation that is a *function* from bytes to values cannot be ambiguous by construction, and the refinement theorem lifts that property to the C validator [3][5]. The remaining question is *semantic equivalence with the protocol grammar*: does the 3D specification faithfully transcribe the RFC? This step is necessarily human — EverParse's **QuackyDucky** front end addresses it by accepting format descriptions in the tabular style of IETF RFCs, narrowing the transcription gap for protocols like TLS and QUIC [2]. The methodology is therefore: humans transcribe once into a declarative form close to the RFC, and machines prove everything downstream.

| Approach | Specification | Guarantee | Output | Proof burden |
|---|---|---|---|---|
| Hand-written C parser | None (code is the spec) | None | Fast, buggy | N/A |
| Nail [6] | Single grammar | By-construction consistency | Parser + generator (C) | None (trusted generator) |
| LowParse/EverParse [1] | F* combinators | Machine-checked safety + duality | Verified C validators | Library-level, amortized |
| EverParse3D [3] | 3D dependent descriptions | Machine-checked refinement | Verified C + F* specs | Mostly automated |
| QuackyDucky [2] | RFC-style tables | Inherits LowParse proofs | Verified C | Transcription review |

## 5. Empirical Results and Formal Proofs

The EverParse papers report deployment evidence unusual for verification research — not just theorems, but production use and performance numbers.

**Scale of verified artifacts.** The miTLS verified TLS stack incorporated EverParse-generated parsers covering 293 datatypes across TLS 1.0–1.3 [1]. EverParse3D was evaluated on message formats including the full TLS handshake, the QUIC record layer, and Bitcoin's wire format [3]. The EverParse repository further documents deployment in Hyper-V kernel message parsers (on the order of one hundred message types in production since 2022), DICE measured boot, COSE/CBOR, and ASN.1 DER [2][7].

**Bugs found by verification.** The strongest empirical signal is not performance but *defects discovered*. The EverQUIC verification found two errors in the IETF QUIC reference implementation's packet-number expansion — an off-by-one in one case analysis branch and an integer overflow in another — both corrected in draft 24 of the specification after disclosure [5]. This is verification paying for itself: the proof attempt failed exactly where the code was wrong.

**Performance.** Because validators are zero-copy and compile to tight C loops, EverParse-generated parsers perform comparably to hand-written code; the USENIX Security 2019 evaluation reports parsing throughput on par with unverified baselines, with the TLS case study showing no prohibitive overhead [1]. The PLDI 2022 paper similarly reports that 3D-generated validators match hand-optimized C on TLS record parsing [3].

**Proof automation.** A recurring quantitative claim is the *ratio of proof to code*: F*'s SMT automation discharges the bulk of verification conditions, so format authors write specifications (the 3D source) rather than proofs. The 3D refinement theorem is proved once per language construct in the generator; per-format obligations are largely automatic [3]. This amortization — prove the combinators once, generate many verified parsers — is what separates EverParse from one-off verification efforts.

## 6. Limitations

Verified parsing is not a panacea, and the literature is candid about its boundaries.

- **Transcription trust.** The refinement theorems relate the *3D specification* to the C code; they say nothing about whether the 3D source faithfully captures the RFC. QuackyDucky narrows but does not close this gap [2]. A mis-transcribed length bound yields a verified parser for the wrong format.
- **Expressiveness edges.** The original EverParse lacked bit fields, which the QUIC work had to add before variable-length integer encodings could be expressed [5]. Recursive and highly context-sensitive formats strain the combinator model, and Nail's transformations remain more flexible for ad hoc encodings [6].
- **SMT brittleness.** F* proofs depend on Z3 heuristics; solver upgrades or small specification changes can turn automatic proofs into manual ones. The EverParse team mitigates this with proof hints and canonicalization, but proof maintenance is a real cost [1][3].
- **No liveness or availability properties.** The theorems cover safety, functional correctness, and duality — not denial-of-service resistance (e.g., algorithmic complexity of validation) or side-channel freedom.
- **Adoption friction.** Writing 3D or QuackyDucky specifications requires learning a new toolchain, and integrating generated validators into large legacy C codebases (as opposed to greenfield verified stacks like miTLS) demands careful FFI discipline [7].

## 7. Conclusion

EverParse demonstrates that the oldest attack surface in systems software — the parser — can be addressed not with more careful hand-written C but with *proof*. Its architecture layers three ideas: LowParse's verified, zero-copy combinators in F* [1]; the 3D language's three denotations tied together by a machine-checked refinement theorem [3]; and a parser–serializer duality whose injectivity half rules out ambiguous encodings and parser differentials [5]. Nail's earlier, proof-free approach [6] shows how far single-source grammars with dependent fields can go on engineering discipline alone — and, by contrast, what machine-checked proof adds: not just consistency, but theorems. The deployments — TLS in miTLS, the QUIC record layer with its two specification bugs caught, Hyper-V kernel parsers in production — suggest verified parsing has matured past the prototype stage [2][5][7]. The remaining frontier is the transcription gap between RFC prose and formal specification, and the proof-engineering cost of keeping SMT automation stable. If those yield, the default way to write a parser for a security-critical format may finally become: write the grammar, prove the rest.
