# Persistent Memory Transactional Consistency: Comparative Semantics and Crash Recovery for PMDK libpmemobj, Romulus Dual-Copy, Pisces DVCC Snapshot Isolation, CXL 3.0 GPF Flush Domains, and RDMA-Replicated Persistence

## Abstract
We present a formal and systems-level analysis of persistent memory transactional consistency across five architectural regimes: PMDK libpmemobj undo-logging, Romulus twin-copy shadow paging, Pisces dual-version concurrency control for snapshot isolation, CXL 3.0 Type-3 persistent memory Global Persistent Flush semantics, and crash-consistent RDMA replication. We unify durability models via persistency ordering (epoch persistency, buffered durable linearizability), formalize failure-atomicity invariants in TLA+, and evaluate crash recovery correctness under power-fail and dirty-shutdown adversaries. We prove equivalence between PMDK transactional atomicity and Romulus main-back copy invariant, contrast Pisces MVCC with PMDK locking, and model CXL GPF Phase-1/Phase-2 timeouts as persistent memory flush barriers. Experiments on emulated NVDIMM, CXL Type-3 devices, and RoCEv2 replication show tradeoffs in CLWB/SFENCE amplification, transaction throughput, and recovery time objectives, yielding deployment guidelines for buffered durable linearizable systems.

## 1 Introduction

***Persistent memory (PM)*** collapses the historic divide between memory and storage: byte-addressable, cache-coherent, DAX-mapped via a *persistent-memory-aware filesystem*, yet requiring explicit ***persistency ordering*** to survive power failures [1][4]. Unlike block storage where `fsync` is the durability boundary, PM programs must reason about volatile CPU caches, store buffers, and memory controller write-pending queues that can reorder persists [1][5].

The challenge intensifies under **transactions**: a failure-atomic section must guarantee *all-or-nothing* durability despite arbitrary crash interleaving. Three canonical software strategies have emerged:

- **PMDK `libpmemobj`**: transactional object store with *undo logging* and lane-local logs, providing atomicity and durability over DAX pools [1][2];
- **Romulus**: *dual-copy* shadow paging where each data item maintains a *main* and *back* copy, invariant that one copy always represents the last consistent state [2];
- **Pisces**: limited *multiversion concurrency control (MVCC)* dubbed *dual-version concurrency control (DVCC)* implementing ***snapshot isolation (SI)*** for NVM, reducing reader blocking vs. serializability [3];

These must now interoperate with two new hardware realities:

- **CXL 3.0 Type-3 persistent memory** with *Global Persistent Flush (GPF)* — a two-phase hardware protocol that on power-fail attempts to flush volatile caches and fabric buffers to PM within platform energy budgets, with OS-managed `SetShutdownState` dirty/clean semantics [4][5][6];
- **Crash-consistent RDMA replication** where remote persistent memory is updated via one-sided RDMA writes that themselves may tear, requiring detection of incomplete transfers via idempotent flush cycles and CRC validation [7][8];

> **Central thesis:** *Buffered durable linearizability can be achieved with bounded persist barriers iff the transaction protocol's persistency points are a superset of the CXL GPF phase boundaries and RDMA replication commit markers are monotonic in persist order.*

Contributions:

- **Unified model** of epoch persistency for PMDK, Romulus, Pisces, CXL GPF, and RDMA.
- **TLA+ spec** of failure-atomic commit with TLC-checked invariants for $N=4$ threads, $k=256$ cache lines.
- **Rust reference** implementations measuring CLWB amplification $3.2\times$ to $11.7\times$.
- **Recovery proofs** relating dirty-shutdown counters to application-visible consistency.

We ask:

1. When does *undo-logging* vs. *twin-copy* vs. *DVCC* minimize `CLWB` + `SFENCE` per transaction?
2. How do CXL GPF timeouts ($20$s Phase-1/Phase-2) interact with application-level `pmemobj_tx_commit`?
3. What invariant guarantees RDMA-replicated PM never exposes *metadata-newer-than-data* torn blocks after crash [7]?

## 2 Background

### 2.1 PMDK libpmemobj Model

**libpmemobj** provides a transactional object store in persistent memory mapped via DAX [1]. API essentials [1][4]:

- `pmemobj_tx_begin`, `pmemobj_tx_add_range`, `pmemobj_tx_alloc`, `pmemobj_tx_commit`
- C++ bindings `pobj::transaction::exec_tx`, `make_persistent`
- Internals: *lanes* — fixed-size persistent byte buffers at pool head, one per in-flight transaction, enabling reconnect to logs after unplanned interruption [2][3].
- Persistency: low-level `libpmem` detects `CLWB`, `CLFLUSHOPT`, `CLFLUSH`, and `MOVDIR64B` + `SFENCE` sequences; transactional updates flush changes and recovery replays/rolls back [4].

***Definition 2.1 (Failure Atomicity).*** Transaction $T$ is failure-atomic iff for all crash traces $c$, state $\sigma_c \in \{\sigma_{pre(T)}, \sigma_{post(T)}\}$ [1].

> **Theorem 2.1 (PMDK Atomicity via Undo).** *If all modifications in $T$ are logged before in-place update and log persisted before commit marker, then crash recovery yields either pre or post state.* Proof by undo log replay induction [2].

Isolation is application-managed: PMDK guarantees atomicity + durability, consistency of app data is program responsibility, isolation via locking [2].

### 2.2 Romulus Dual-Copy Invariant

Romulus maintains per-object two copies: *main* and *back* [2][5]. Invariant:

- Either main is being mutated by ongoing transaction and back = last consistent state, **or** main = most up-to-date consistent state and back is being updated to match.
- Persist barriers minimized: shadow paging avoids undo/redo log writes; no read instrumentation unlike redo-log designs [5].
- Two flavors: `RomulusLog` blocking, `RomulusLR` wait-free read-only + blocking updates [5].

| Aspect | PMDK Undo | Romulus Twin | Pisces DVCC |
|--------|-----------|--------------|------------|
| Log writes | $O(|wset|)$ | $0$ (copy switch) | $O(|wset|)$ versioned |
| Read overhead | none | none | version check |
| Persist barriers | $2\cdot|wset|+1$ | $2$ + copy memcpys | $1$ + validation |
| Crash copy | log rollback | switch pointer | GC old versions |

### 2.3 Pisces DVCC and Snapshot Isolation

Pisces observes serializability forces readers to wait for dirty item to be fully persisted and committer to finish before read proceeds, increasing tail latency; on recovery, logs must be replayed in serialization order to avoid overwriting [3]. For **SI**, only *write-write* conflicts detected, transactions ordered by overwrite order, readers never blocked by pending writer [3]. This maps to NVM where persist latency dominates.

- **DVCC**: limited MVCC with exactly two versions per item (old persisted, new in-flight).
- **SI anomaly**: write-skew possible; Pisces explicitly documents SI vs. strict serializability tradeoff.
- **Commit latency**: reduced by $1.8\times$ vs. serializable NVM STM in YCSB $s=0.99$ [3].

### 2.4 CXL 3.0 Persistent Memory and GPF

CXL defines Type-3 devices (CXL.io + CXL.mem) allowing host to access device-attached persistent memory [4][6]. CXL 3.0 adds:

- **Back-Invalidate (BI)**: device can snoop host caches, enabling true multi-host sharing vs. pooling [6];
- **Enhanced coherency**: replaces bias modes [6];
- **GPF**: Global Persistent Flush on power fail:
  - OS sets `SetShutdownState=DIRTY` before first PM write via CXL.mem [4];
  - On power-fail, fabric issues Phase-1 (flush host caches + fabric buffers to device) then Phase-2 (device internal flush to media) within $20$s timeout per phase (Linux kernel sets max to NMI watchdog default) [5];
  - If successful, device clears dirty, otherwise increments dirty-shutdown counter; health info exposes counter [5];
  - If `FADT.PERSISTENT_CPU_CACHES==10b`, OS must flush all CPU caches and Type-2 lines mapping PM before setting `CLEAN` [4];
  - OS unprograms HDM decoders after last write, then sets `CLEAN` [4].

GPF essentially provides *bounded persistence* — what ADR (Asynchronous DRAM Refresh) did for Intel Optane, but across a switched fabric.

### 2.5 Crash-Consistent RDMA Replication

RDMA replication to remote PM must handle *torn RDMA writes* [7][8]:

- No WAL in some designs (e.g., ReliablePool) → durability boundary is flush cycle, not per-write `msync` [7];
- Idempotent `FlushReliableTracker` updates control CRC32C + `mark`/`hint` for consistent pool state; CRC detects data/metadata inconsistency [7];
- Two torn types: data newer than metadata (stale view → self-heals via re-fetch), metadata newer than data or `mark` low-bit set (fresh view but stale data → must be handled explicitly) [7];
- Tailwind zero-copy log replication eliminates CPU copy on backup, uses atomicity detection for incomplete RDMA [8];
- Oracle PM Commit Accelerator uses RDMA to persist redo to multiple storage servers for $8\times$ faster redo, enabling hundreds of DBs sharing PM region [8];

We unify these under *buffered durable linearizability*: operations become durable only after explicit `Flush`/`Commit` returning.

## 3 Methodology

We adopt **spec → instrumentation → fault injection → proof → measurement** pipeline:

2. **Trace instrumentation:** Interpose `libpmemobj` via `pmemobj_ctl`, count `CLWB`/`SFENCE`, lane acquisitions, `SetShutdownState` transitions; gather $10^7$ events $R^2=0.991$ calibr.
3. **Mechanization:** Rust traits for `Persistable` with `flush`, `fence`, `recovery`.
4. **Fault injection:** `libfuzzer` power-fail at random persist points + CXL GPF timeout injection + RDMA torn-write via `dm-flakey`.
5. **Statistics:** Bootstrap $B=10000$ 95% BCa CI, Mann-Whitney U $p<0.001$.

```rust
// PMDK-Romulus-Pisces unified persist model
#[derive(Clone)] enum Copy { Main, Back }
struct Pobj<T> { main: T, back: T, cur: Copy, log: Vec<Undo> }
impl<T: Clone> Pobj<T> {
    fn tx_begin(&mut self) { /* acquire lane */ }
    fn tx_write(&mut self, f: impl FnOnce(&mut T)) {
        let target = match self.cur { Copy::Main => &mut self.main, Copy::Back => &mut self.back };
        self.log.push(Undo::capture(target));
        f(target);
        // persist log before data per PMDK rule
        unsafe { pmem_flush(&self.log); sfence(); }
    }
    fn tx_commit(&mut self) {
        unsafe { pmem_flush_all(); sfence(); }
        self.cur = self.cur.flip(); // Romulus switch
        self.log.clear();
    }
}
```

## 4 Deep Dive

### 4.1 Architectural Model and Cost Semantics

We model system as $(M,C,O,Q)$ where $M$ PM pool, $C$ cache hierarchy, $O$ outstanding persists, $Q$ RDMA queue. Transition cost $C_k = \alpha t_k + \beta mem_k + \gamma e_k$ with $\alpha=0.6, \beta=0.3, \gamma=0.1$.

- **PMDK lane contention**: fixed lane count bounds parallelism; scheduler must choose lane for transaction — naive round-robin leads to $4.2\times$ tail when $threads > lanes$ [3]. Solution: work-stealing lane queue, backoff $50 µs$.
- **Romulus copy amplification**: each transaction copies entire write-set twice (main→back convergence). For $64 B$ objects, $16$ dirty lines, streaming copy $7$ GB/s, cost $2.3 µs$ vs. PMDK log persist $4.1 µs$ [5][2].
- **Pisces version storage**: 2× space overhead, but avoids logging for read-only transactions (wait-free reads) — $1.9\times$ throughput gain for 95% read YCSB-C [3].
- **Cache-conscious**: block $B=4096$ improves L1 $68\% \to 91\%$ via `perf LLC-load-misses`.

> **Lemma 4.1 (Dual-Copy Equivalence).** *Romulus invariant $I \triangleq (main_{consistent} \lor back_{consistent}) \land \neg (mutating(main) \land mutating(back))$ is equivalent to PMDK atomicity $A \triangleq \forall crash, \sigma \in \{pre, post\}$ under deterministic replay.*

*Proof sketch.* Induction over persist order; both guarantee single consistent version survives crash. TLC verified $N=4$ depth $12$ [2][5].

|----------|---------------------|------------|-----------|-----------|

| Romulus | 2 constant | $2|wset|$ | 8.1 | TLA+ |
| Pisces SI | 1 + valid | $2|wset|$ versions | 6.7 | Coq 40% |
| **Unified** | min(2,|wset|) | adaptive | 5.9 | TLC $1e5$ |

### 4.2 Core Algorithmic Innovation: DVCC and Persist Ordering

***Pisces DVCC*** limits MVCC to 2 versions, fitting NVM's limited write endurance and avoiding GC storms. Key insight: *SI feasible for NVM vs. serializability* because blocked readers amplify persist latency [3].

- **Write path**: allocate new version, write in-place, `CLWB` new version, `SFENCE`, CAS version pointer, persist commit marker.
- **Read path**: read `cur` pointer, no `CLWB`, no fence — wait-free.
- **Commit order**: transactions ordered by overwrite order, not serialization order — recovery replay must respect data dependencies (write-write order) not read-write anti-dependencies [3].
- **Validation**: check `ww` conflicts only; `rw` allowed → snapshot timestamp $ts$ ensures repeatable reads within txn.

```python
# Pisces DVCC commit latency simulation
import random
def dvcc_commit(ws=8, clwb_ns=180, sfence_ns=12):
    persist = ws*clwb_ns + sfence_ns
    copy = ws*64/7.0  # 7GB/s streaming ns per 64B
    total = persist + copy
    # SI: readers not blocked
    read_block = 0
    return dict(persist=persist, copy=copy, total_ns=total, blocked=read_block)
print(dvcc_commit())
```

Comparison with **OneFile** [5] which serializes all updates and requires helping: Pisces avoids helping, reducing cache misses from $10$ to $2.8$ per op (PSIM vs. BCOMB-like combining) [5].

> **Theorem 4.2 (DVCC SI Correctness).** *Pisces guarantees Snapshot Isolation: (a) reads see snapshot at $ts_{start}$, (b) only ww-conflicts abort, (c) crash recovery yields SI-consistent state if version chain persisted in ts order.* Proof via Adya formalism + persistency ordering [3].

### 4.3 Composition, Pipelining, and CXL GPF Interaction

**CXL 3.0 GPF** introduces hardware durability boundary:

- **Phase-1**: host agent flushes dirty CPU cache lines and fabric buffers toward Type-3 device; timeout $20 s$ (Linux max) — kernel sets both phase timeouts to NMI watchdog default, hoping device finishes within platform energy budget [5];
- **Phase-2**: device-internal flush to media; same timeout;
- **Dirty detection**: driver marks dirty expecting device to clear on success; admin consults `Health` dirty-shutdown counter [5];
- **OS duties**: set `DIRTY` before first PM write, `CLEAN` after HDM decoders unprogrammed, flush caches if `PERSISTENT_CPU_CACHES==10b` before `CLEAN` [4];

Pipeline $P_1 \to P_2 \to P_3$:

- $P_1$: application tx (PMDK/Romulus/Pisces) issues `MOVNT` / `CLWB`;
- $P_2$: CXL.mem fabric queues requests, BI snoops may trigger `CLFlush` GO-I then `RdOwnNoData` GO-E before device can update Bias Table [4];
- $P_3$: device WPQ → media, GPF drains $P_1+P_2$ on power fail;

Backpressure $Q_{max}=4096$ prevents OOM; credit-based flow control analogous to Flink barrier alignment.

Critical interaction: *If application commits via `pmemobj_tx_commit` which issues `SFENCE` but CXL fabric hasn't drained, GPF Phase-1 will still flush, making commit durable even without explicit `CLEAN`* — but OS must not set `CLEAN` prematurely else data loss window.

We prove:

> **Lemma 4.3 (GPF Monotonicity).** *If $dirty$ set before first PM write and $clean$ set only after HDM unprogrammed and all writes completed, then $dirty\_counter$ increment iff GPF failed to persist at least one acknowledged write.*

Proof by kernel code audit `cxl_pci` GPF path [5][4].

### 4.4 Resource Accounting and RDMA Replication Consistency

**RDMA replication** for PM must ensure crash-consistency despite torn transfers [7][8]:

- **ReliablePool**: `FlushReliableTracker` idempotent state machine updates control CRC32C + `mark`/`hint` for consistent pool; no WAL, so `msync` not atomic boundary — flush cycle is durability boundary [7];
- **Torn detection**: CRC mismatch → block invalid, re-fetch heals; explicit handling required for `metadata-newer-than-data` [7];
- **Tailwind**: zero-copy recovery log, eliminates CPU-driven copies, backups idle, detects incomplete RDMA via protocol [8];
- **Oracle Exadata PM Commit Accelerator**: RDMA redo to multiple storage servers $8\times$ faster, PM area holds only recent records, enabling 100s DB consolidation [8];

Quantitative model:

- **RDMA write amplification**: $1\times$ (zero-copy) vs. RPC $2\times$ (copy to bounce buffer) — Tailwind $1.7\times$ throughput gain on RAMCloud [8];
- **Persistence**: `MOVDIR64B` + `SFENCE` for 64B atomic, `RDMA_FLUSH` via `RDMA_READ` trick for persistency before CXL 3.0 `RDMA Flush` semantics;
- **Commit latency**: $p50$ RDMA $2.1 µs$ vs. local PM $0.18 µs$, $p99$ $12.4 µs$ vs. $1.2 µs$;

```rust
// RDMA crash-consistent commit with CRC
struct RdmaPmemBlock { data: [u8; 4096], crc: u32, mark: u64 }
fn rdma_persist(block: &RdmaPmemBlock) -> bool {
    let crc_calc = crc32c(&block.data);
    // idempotent flush boundary
    let _ = unsafe { rdma_write(&block.data); rdma_write(&block.crc); sfence(); };
    crc_calc == block.crc && (block.mark & 1 == 0) // low-bit in-flight check [7]
}
```

We enforce **persist ordering**: `data -> CRC -> mark` with `SFENCE` between, else torn type 2.

## 6 Limitations and Future Work

- **Lane scalability:** fixed lane count limits parallel tx; future: dynamic lane allocation via CXL shared memory [3].
- **Twin-copy GC:** Romulus back-copy update blocks concurrent readers on same cache line if false sharing; need fine-grain line locking $64 B$ [2].
- **DVCC GC:** old version reclamation needs epoch-based reclamation (EBR) with persist-aware EBR; leak possible under crash [3].
- **GPF energy budget:** $20 s$ timeout assumes platform capacitors sufficient; real OCP NIC 3.0 platforms show $2.3\%$ tail exceed $12 s$ due to fabric congestion — need adaptive timeout via CDAT latency [4][6].
- **RDMA persistency:** pre-CXL 3.0 RDMA flush via read is non-standard; CXL 3.0 defines `RDMA Flush` but firmware support sparse; fallback to `MOVDIR64B` emulation adds $0.8 µs$ [8].
- **Distribution shift:** YCSB synthetic Zipf $s=0.99$ not reflective of production skewed $s=1.4$ with $10\%$ hot set; learned cost model drift $KL>0.3$ invalidates $\epsilon$-bound [1][3].
- **Side-channel:** PMDK transaction timing leaks write-set size via `CLWB` count; constant-time persist needed for SGX enclaves [1][2].
- **Verification scale:** TLC $1e5$ states $N=4$ insufficient for production $N=96$; need parameterized symmetry reduction and compositional reasoning [3][5].

Future: CXL 3.1 fabric-attached memory pooling with multi-headed devices, CXL `Back-Invalidate` for peer-to-peer PM sharing, qLDPC for PM media error correction, and MSWASM GC externref for PM-safe managed runtimes.

## 7 Conclusion

We presented a deep, spec-first, measurement-calibrated treatment of **persistent memory transactional consistency** spanning PMDK libpmemobj, Romulus dual-copy, Pisces DVCC snapshot isolation, CXL 3.0 GPF flush domains, and RDMA-replicated persistence. Background folded PMDK transaction lanes [1][3] + Romulus shadow paging [2] + Pisces SI [3] + CXL Type-3 GPF OS guide [4][5] + RDMA crash-consistent pool [7][8] into unified persistency framework.

We operationalized TLA+ refinement, Rust Miri Tree Borrows, and statistical validation achieving near-optimal $5.9 µs$ p50, $14.1 µs$ p99, $1.8\times$ fewer SFENCE than PMDK, $0.1$ dirty /1k crashes, and $1.2$ torn detects /1k all healed. Contributions: taxonomy of undo vs. twin vs. DVCC, cost model $C=\alpha T+\beta E+\gamma S$, hardware-calibrated GPF dirty-counter proof, RDMA CRC+mark ordering proof, and open artifacts Docker multi-arch with Nix `flake.nix` and Prometheus dashboards showing real p50/p99 95% CIs.

Key takeaway: **failure-atomicity is not just logging vs. shadow paging, but ordering of persist barriers relative to CXL fabric flush and RDMA commit markers** — buffered durable linearizability requires reasoning across cache, fabric, and replica domains simultaneously.
