# Verified In-Kernel Programming with eBPF: Abstract Interpretation in the Verifier, Tristate-Number Domains, and Verified JIT Compilation for Observability

## Abstract

The extended Berkeley Packet Filter (eBPF) permits unprivileged users to load programs that execute inside the Linux kernel. Safety is established not by trust but by proof: the in-kernel verifier performs abstract interpretation over every reachable path of the submitted bytecode, tracking register types, scalar ranges, and bit-level uncertainty before any instruction executes. This paper presents a systematic account of that verification pipeline. We formalize the verifier's abstract domains, with emphasis on intervals and the tristate-number (tnum) domain for bitwise reasoning; we examine the soundness arguments underpinning the abstract operators; we survey the formal-verification research that has audited, repaired, and in some cases proved correct components of this stack, from range analysis to just-in-time compilers; and we evaluate the consequences for observability workloads. The published record shows verified JIT compilation uncovering sixteen previously unknown code-generation bugs across five deployed backends, a proved-optimal tnum multiplication operator improving both precision and verifier throughput, and differential synthesis converting precision gaps into upstream kernel patches.

## 1 Introduction: Programs as Kernel Extensions

Operating system kernels face a perennial tension: applications demand extensibility, yet every extension enlarges the trusted computing base. The extended Berkeley Packet Filter broke this stalemate. Originating as a packet-filtering virtual machine, eBPF has grown into a general in-kernel execution environment supporting networking datapaths such as XDP and traffic control, observability through kprobes, uprobes, and tracepoints, security enforcement via LSM hooks, and even CPU scheduling policy.

The enabling insight is that *safety can be decided statically*. Rather than sandboxing eBPF programs at run time, the kernel requires each program to carry an implicit proof of its own safety, discharged by an in-kernel static analyzer — the verifier — before admission. The verifier's verdict must be *sound*: every accepted program must be memory-safe, must terminate, and must not leak kernel state. It need not be *complete*: safe programs may be rejected, and in practice many are [4].

This asymmetry shapes the entire discipline around eBPF. It explains why the verifier is simultaneously one of the most analyzed and one of the most vulnerability-prone components of the modern kernel: its analysis must over-approximate all possible executions, and any gap between the abstraction and reality is either a usability cliff (false rejection) or a privilege-escalation primitive (false acceptance). The Linux Foundation's security audit catalogs both the attack surface and the growing body of formal-verification work brought to bear on it [6].

This paper contributes a unified exposition of the verifier as an abstract interpreter; a formal treatment of the tnum domain following the first published soundness and optimality proofs [2]; a survey of verified compilation centered on the Jitterbug framework [3], synthesis-based JIT construction [5], and synthesis-based optimization [7]; a precision analysis based on differential synthesis [8]; and a candid discussion of limits.

> **Theorem (informal, roadmap):** *The eBPF verifier's abstract interpretation is sound with respect to the concrete semantics of the BPF instruction set, provided each abstract transfer function over-approximates its concrete counterpart and state merging at control-flow joins computes a sound upper bound. Precision — how tight that over-approximation is — determines which safe programs load and which are rejected.*

## 2 Background

### 2.1 The BPF instruction set and execution model

eBPF programs are expressed in a RISC-like 64-bit instruction set with eleven 64-bit registers (`R0`–`R10`), where `R10` is a read-only frame pointer anchoring a 512-byte stack. Each instruction is a fixed 8-byte encoding (`struct bpf_insn`); the ISA supports arithmetic, memory load/store at 1/2/4/8-byte widths, conditional jumps, calls into helper functions, and atomic operations [4]. Programs attach to hooks — network device drivers for XDP, the traffic-control layer, tracepoints, kprobes — and persistent state lives in *maps*: key-value stores shared between kernel and user space that underpin the counters, histograms, and ring buffers of observability tooling.

Execution may proceed through the in-kernel interpreter or, far more commonly, through a just-in-time compiler translating BPF bytecode to native machine code at load time. The JITs are per-architecture backends (x86-64, arm64, riscv, s390, and others) that must preserve exact bytecode semantics while emitting efficient native code.

### 2.2 The verifier's two phases

The kernel documentation describes verification as a two-step process [4]. First, the verifier builds the program's control-flow graph and validates it: unreachable instructions are rejected, jumps must land within bounds, and back edges are permitted only for bounded loops whose trip counts can be proved finite. This phase also enforces the instruction-count limit, historically 4096 and raised over time toward one million, reflecting the verifier's evolution from a simple DAG checker into a full symbolic-execution engine.

Second, the verifier *simulates execution along every possible path*, starting from the first instruction with `R1` holding a pointer to the program context (type `PTR_TO_CTX`) and all other registers unreadable (`NOT_INIT`). After each instruction it updates its abstract model of registers and stack. Any operation it cannot prove safe — an out-of-bounds access, a misaligned access, a disallowed helper call, reading an uninitialized register — causes rejection. When in doubt, the verifier rejects: the analysis is deliberately conservative [4].

### 2.3 Abstract interpretation in one page

Abstract interpretation replaces concrete program states with elements of an *abstract domain* ordered by precision, and concrete operations with *abstract transfer functions* that over-approximate them. If abstract execution reaches a fixed point without encountering an unsafe abstract state, no concrete execution can be unsafe — the soundness theorem on which the verifier rests.

Three design decisions dominate the eBPF instantiation:

1. **Path sensitivity with bounded merging.** The verifier explores paths distinctly but merges states at join points to guarantee termination, computing least upper bounds in the abstract lattice. Merging loses precision; heuristics such as tracking "similar" scalars propagate bounds learned about one register to others known to hold related values [6].
2. **A product of small domains.** A *type domain* (scalar vs. pointer, and which kind of pointer), an *interval domain* (unsigned and signed min/max bounds), and the *tristate-number domain* (per-bit known/unknown information) each answer questions the others cannot: types rule out pointer forgery, intervals bound memory accesses, and tnums sharpen the bitwise masking idioms ubiquitous in packet parsing.
3. **Termination via state subsumption.** The verifier records visited states keyed by instruction; when a newly computed state is subsumed by a previously visited one, exploration of that path stops — the abstract analogue of loop-invariant inference.

### 2.4 The trust model

The verifier is the *only* barrier between unprivileged bytecode and kernel memory, and its analysis must be sound even for fully adversarial programs, because verifier bugs have repeatedly yielded privilege escalation [6]. Complementary hardening — the ALU sanitizer rewriting speculative paths, constant blinding against JIT spraying, Spectre mitigations — assumes the verifier's static guarantees as a foundation. Defense in depth (unprivileged loading disabled by default, `CAP_BPF` gating, a "secure mode" forbidding pointer arithmetic [4]) contains the blast radius of the soundness bugs that a 10,000-plus-line abstract interpreter, having grown roughly 117% between 2020 and 2024, will continue to harbor [6].

## 3 Methodology

This paper is a *synthesis and formal exposition*. We ground the architecture in the kernel's own verifier documentation — the two-phase design, the register-type system, and value tracking via `struct bpf_reg_state` [4] — and in the Linux Foundation's independent security audit [6]. For the abstract domains we follow the peer-reviewed formalizations: Gershuni et al.'s interval-domain model (PLDI 2019) [1] and Vishwanathan et al.'s tnum specification with soundness and optimality arguments for its arithmetic operators (CGO 2022) [2]. For JIT correctness we rely on Nelson et al.'s Jitterbug framework (OSDI 2020) [3] and Van Geffen et al.'s synthesis of JIT compilers for in-kernel DSLs (CAV 2020) [5]. Quantitative claims — bug counts, performance deltas, patch histories — are taken from the cited papers' published evaluations: K2's synthesis-based optimization (SIGCOMM 2021) [7], the tnum multiplication improvement merged into the kernel [2], and Shachnai et al.'s differential-synthesis study of abstract-operator precision (SAS 2025) [8].

## 4 Deep Dive

### 4.1 The register-type lattice and value tracking

Every register and stack slot carries a `struct bpf_reg_state` unifying type and value information [4]. The type component ranges over `NOT_INIT`, `SCALAR_VALUE`, and a family of pointer types — `PTR_TO_CTX`, `PTR_TO_STACK`, `PTR_TO_MAP_VALUE` (and its `_OR_NULL` variant), `PTR_TO_PACKET`, `PTR_TO_PACKET_END`, `PTR_TO_SOCKET`, and others — each encoding both the memory region and the permitted operations. Arithmetic on `PTR_TO_MAP_VALUE_OR_NULL` is forbidden until a null check refines it: *path-sensitive type refinement*.

Scalar values are tracked as a variable offset with coordinated components: unsigned minimum and maximum, signed minimum and maximum, and a tristate number capturing per-bit knowledge [4]. The subtlety — and the source of both precision wins and soundness bugs — is that these components must stay *mutually consistent*; the kernel has repeatedly patched cases where one component was updated while another went stale [6].

State merging at join points computes component-wise least upper bounds: types merge toward their common supertype, intervals take the union, and tnums merge per-bit (a bit known 0 on one path and 1 on another becomes unknown). Merging is where path sensitivity is sacrificed for termination, and where precision engineering concentrates.

### 4.2 The tristate-number domain: soundness and optimality

The tnum domain answers a question intervals answer poorly: *which bits of this value are known?* Packet code is rich in masking, and interval arithmetic on a masked value yields the correct range but discards the knowledge that the high bits are *zero* — knowledge later operations can exploit.

A tnum is a pair `(value, mask)` of machine words. A bit position whose mask bit is 0 is known, with its concrete value given by the value bit; a mask bit of 1 marks the bit unknown. The tnum for "low four bits unknown, rest zero" is `(value=0, mask=0xf)` [2]. The domain forms a lattice under bitwise precision ordering, and each arithmetic instruction needs an abstract operator that is both *sound* (over-approximating every concrete outcome) and, ideally, *optimal* (the least such over-approximation).

```haskell
-- Tristate numbers: each bit is known-0, known-1, or unknown.
data Tri = T0 | T1 | TX deriving (Eq, Show)
newtype TNum = TNum [Tri]   -- LSB first

-- Concretization: the set of machine words this tnum may denote.
gamma :: TNum -> [Word64]
gamma (TNum bits) = map bitsToWord (sequence (map expand bits))
  where expand T0 = [False]; expand T1 = [True]; expand TX = [False, True]

-- Soundness obligation for an abstract operator f#:
--   x in gamma(a), y in gamma(b)  ==>  f x y `elem` gamma (f# a b)
```

> **Theorem (Soundness of tnum addition, after [2]):** *Let `add#` be the kernel's abstract addition on tnums. For all tnums `a`, `b` and all concrete words `x ∈ γ(a)`, `y ∈ γ(b)`, the sum `x + y` lies in `γ(add#(a, b))`. Moreover `add#` is optimal: no strictly more precise sound operator exists.*

Vishwanathan et al. gave the first formal specification of this domain, proved soundness and optimality for the kernel's addition and subtraction operators, and designed a novel multiplication algorithm both more precise and 33% faster on average than the kernel's prior algorithm — subsequently merged upstream [2]. Optimality matters operationally: every precision gap below optimality is a potential false rejection, a developer forced to rewrite safe code because the verifier's arithmetic was needlessly coarse.

### 4.3 Precision engineering: differential synthesis of abstract operators

Soundness is non-negotiable, but precision determines usability, and precision bugs are silent: the verifier rejects a safe program and nobody files a CVE. Shachnai et al. addressed this with a framework that *compares* competing abstract operators formally, then uses SMT-based synthesis to generate concrete eBPF programs witnessing observable precision differences in real verifier executions [8]. Their canonical example: masking a register to keep only the low two bits guarantees an index into a 4-byte array is safe — yet an imprecise abstract AND yielding an interval stretching to 8 forces rejection of a provably safe access [8]. Witness programs produced this way directly motivated upstream kernel patches, including a more precise multiplication operator that was merged [8]. Abstract-interpretation engineering is thus a two-front war — soundness against attackers, precision against developer frustration — and both fronts benefit from mechanized reasoning.

### 4.4 From verified bytecode to native code: JIT compilation and Jitterbug

Once the verifier accepts a program, the JIT translates each BPF instruction into native machine code — a translation trusted absolutely, since a miscompiled bounds check voids every guarantee the verifier established. Nelson et al. confronted this with Jitterbug, "the first framework to provide a precise specification of JIT correctness capable of ruling out real-world bugs, and an automated proof strategy that scales to practical implementations" [3]. Built on the Serval symbolic-evaluation framework and the Rosette solver-aided language, Jitterbug verifies each JIT backend against a formal specification relating BPF bytecode semantics to emitted native code.

The results were striking: a new, verified 32-bit RISC-V backend designed and proved correct from the start, **sixteen previously unknown bugs found and fixed across five deployed JITs**, new JIT optimizations, and every change upstreamed to the Linux kernel [3]. Complementary work by Van Geffen et al. showed that JIT compilers for in-kernel DSLs can themselves be *synthesized* rather than hand-written, with correctness checked by construction [5]. The quantifier in such proofs ranges over all 2^64 register values and memory configurations — discharged by SMT solving, not testing. This is what "verified" means here: not high coverage, but proof over the entire input space of each translation rule.

```rust
/// Specification fragment: compiling BPF_ALU64_ADD must preserve semantics.
/// For every concrete machine state `s`, executing the emitted native code
/// from `s` must equal the BPF interpreter's transition, including flags
/// and 32-bit subregister zero-extension behavior.
fn jit_add64_correct(emitted: &[u8], dst: Reg, src: Operand) -> bool {
    forall_states(|s: MachineState| {
        bpf_interp_add64(s, dst, src) == emulate_native(emitted, s)
    })
}
```

### 4.5 Hardening the boundary: speculation and sanitization

Verification establishes safety of the *architectural* execution; modern CPUs add a speculative dimension. The verifier models speculative hazards explicitly: the ALU sanitizer rewrites arithmetic on pointer-derived values so speculative out-of-bounds accesses are redirected to a safe region, and branches are hardened against Spectre-style training. These mitigations are themselves part of the trusted base — the audit documents proof-of-concept code exercising the sanitizer and the capability requirements around it [6]. A fully verified story must eventually unify speculative-execution reasoning with the abstract-interpretation soundness argument; today the two live in separate formalisms.

## 5 Empirical Results and Formal Guarantees

| Result | Source | Reported outcome |
|---|---|---|
| Interval-domain model of the verifier | Gershuni et al., PLDI 2019 [1] | Formal static-analysis model of untrusted kernel extensions |
| Tnum specification; soundness + optimality of add/sub | Vishwanathan et al., CGO 2022 [2] | First proofs for tnum operators; new multiplication 33% faster, merged into kernel |
| Jitterbug verified JIT framework | Nelson et al., OSDI 2020 [3] | Verified RV32 JIT; 16 unknown bugs across 5 deployed JITs; all fixes upstreamed |
| Synthesized JITs for in-kernel DSLs | Van Geffen et al., CAV 2020 [5] | JIT compilers synthesized with correctness guarantees |
| K2 synthesis-based BPF optimizer | Xu et al., SIGCOMM 2021 [7] | 6–26% smaller code, 1.36–55.03% lower latency vs. best clang output, with equivalence proofs |
| Differential synthesis for operator precision | Shachnai et al., SAS 2025 [8] | Formal precision comparison + synthesized witnesses; improved multiplication upstreamed |

Three patterns emerge. **First, verification pays in bugs found, not just theorems proved** [2][3]. **Second, synthesis complements verification**: Jitterbug proves hand-written JITs correct, while Van Geffen et al. synthesize JITs and K2 synthesizes *optimizations*, each carrying equivalence or safety proofs [5][7]. **Third, precision is measurable and actionable**: differential synthesis turns "the verifier is conservative" from folklore into witness programs and patches [8].

For observability, the consequences are concrete. Tracing programs — kprobe handlers counting syscalls, uprobes sampling latency, XDP programs exporting flow telemetry — parse variable-length headers, walk bounded loops over maps, and pack bitfields: exactly the idioms that strain the verifier. Every false rejection is a blind spot the developer must code around; every soundness bug is a potential sandbox escape. The record above is the evidence base for trusting eBPF as production telemetry substrate.

## 6 Limitations

**The moving-target problem.** Formal models describe a snapshot; the kernel's verifier evolves monthly. Range-analysis verification efforts have had to re-target newer kernels, discovering fresh bugs in older versions along the way [6]. A proof of today's `verifier.c` is stale by the next merge window unless maintained with the same cadence as the code.

**Path explosion and the complexity ceiling.** The verifier explores paths distinctly until states merge, and complex programs can exhaust its limits — instruction count, stack depth, explored states — causing rejection. Bounded loops help, but the verifier remains a *bounded* decision procedure: sufficiently intricate safe programs are still un-loadable, and developers resort to manual loop unrolling and verifier-pleasing contortions.

**Precision is not monotonic in effort.** Each new domain or heuristic adds proof obligations at every domain interaction. The history of verifier CVEs is largely a history of such interactions: bounds tracking that lost precision across 32-bit overflow, scalar-identity tracking that enabled type confusion, speculative paths the abstract model did not cover [6].

**Completeness gaps in the literature.** K2's numbers apply to packet-processing benchmarks from Cilium, Facebook, and kernel samples; generalizing to arbitrary tracing programs remains open [7]. Differential synthesis reasons about operator precision, not end-to-end verifier precision [8]. Jitterbug verifies translation correctness, not the *specification* of BPF semantics itself — a bug in the reference model would be faithfully preserved in every "verified" backend [3].

## 7 Conclusion

The eBPF verifier is the most consequential abstract interpreter ever deployed: a static analyzer standing between arbitrary user bytecode and the kernel's address space, executed on every program load across the world's infrastructure. Its design — a product of type, interval, and tristate-number domains, path-sensitive exploration with lattice-based merging, and conservative rejection — embodies classical abstract interpretation under extreme constraints: sound against adversaries, fast enough for program load, precise enough that developers can ship observability tooling.

The research surveyed here shows the theory taken seriously as engineering practice. Gershuni et al. gave the verifier a formal interval-domain account [1]; Vishwanathan et al. proved the tnum operators sound and optimal and shipped a faster multiplication into the kernel [2]; Nelson et al. verified the JITs and found sixteen real bugs [3]; Van Geffen et al. and Xu et al. showed JITs and optimizations can be synthesized with proofs [5][7]; Shachnai et al. made precision measurable and improvable [8]. The kernel documentation and the independent security audit provide the ground truth these models are checked against [4][6].

Open problems remain: synchronizing proofs with a rapidly growing implementation, unifying speculative-execution reasoning with the soundness story, and pushing precision far enough that safe programs load without contortion. But the trajectory is clear. In-kernel programming is no longer an act of trust — it is an act of proof, mechanically checked, adversarially tested, and increasingly machine-generated.
