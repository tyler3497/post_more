# Sequential-Append Concurrency in Zoned Storage: Formal Semantics of NVMe ZNS Zone Append, SMR ZBC/ZAC Device Integration, ZenFS Log-Structured Allocation, and In-Storage eBPF Computation

## Abstract

Zoned storage interfaces — NVMe Zoned Namespaces (ZNS) for flash and the ZBC/ZAC command sets for shingled magnetic recording — relocate data placement from device firmware to the host, replacing hidden flash-translation-layer garbage collection with explicit zone lifecycles. This thesis gives a unified formal and empirical treatment of the sequential-append concurrency model underlying these interfaces. We formalize the NVMe Zone Append command as a fetch-and-add primitive over per-zone write pointers, prove its linearizability and lock-free multi-writer safety under bounded active-zone resources, and derive a closed-form bound on write amplification under lifetime-separated placement. We examine two integration layers: host-managed SMR integration through libzbc and dm-zoned in the Linux zoned block layer, and ZenFS, the log-structured RocksDB backend mapping SSTable extents onto zones with lifetime-hint segregation. Finally, we analyze computational storage offload under the SNIA architecture and the NVMe Computational Programs command set, showing how in-drive eBPF programs compose with zone-append semantics to cut host data movement.

---

## 1 Introduction

For three decades the block device contract promised a flat, uniformly random-access array of logical blocks while the device concealed a far more constrained reality: NAND pages that must be erased in bulk before rewriting, and shingled magnetic tracks whose overlapping geometry forbids random in-place updates. The reconciliation layer — the flash translation layer (FTL), the persistent cache in drive-managed SMR disks — absorbed this mismatch through over-provisioning and background garbage collection, at the cost of unpredictable tail latency, write amplification, and endurance loss [1][4].

Zoned storage inverts the arrangement. The **NVMe Zoned Namespace (ZNS) command set** [1] exposes the SSD as zones, each writable only sequentially, with an explicit write pointer and lifecycle operations (open, close, finish, reset). The **ZBC** (SCSI) and **ZAC** (ATA) command sets do the same for SMR drives [3]. The host — not the firmware — decides data placement, and device-side garbage collection can be eliminated.

This thesis makes four contributions:

1. **Formal semantics of Zone Append.** We model it as atomic fetch-and-add over the zone write pointer, prove linearizability of concurrent appends, and characterize the lock-free multi-writer contract: the device serializes appends and reports each command's assigned LBA in its completion.
2. **Host-managed SMR integration.** We compare ZBC/ZAC device models, the `libzbc` library [3], and the `dm-zoned` target [8], identifying where each preserves or breaks the append-only contract.
3. **A ZenFS design study.** We dissect the log-structured RocksDB backend [2] mapping files to zone extents with lifetime-hint segregation and journal-based recovery.
4. **Composition with computational storage.** We show how the SNIA architecture [5] and the NVMe Computational Programs command set [6] compose with zone-append semantics so in-drive eBPF programs can filter, compress, or aggregate zone-resident data without PCIe transfers.

## 2 Background and Related Work

### The zoned device model

A *zoned block device* partitions its LBA space into fixed-size *zones*, each with a *write pointer* and a lifecycle state. Table 1 summarizes the NVMe ZNS states [1].

| State | Abbrev. | Meaning |
|---|---|---|
| Empty | ZSE | Write pointer at zone start; no valid data |
| Implicitly Opened | ZSIO | Opened by a write/append; counts toward open-zone limits |
| Explicitly Opened | ZSEO | Opened via Zone Management Send |
| Closed | ZSC | Valid data; no further writes until reopened |
| Read Only | ZSRO | Readable but immutable without reset |
| Full | ZSF | Write pointer reached zone capacity |
| Offline | ZSO | Defective; data may be inaccessible |

Writes to *Sequential Write Required* zones must land exactly at the write pointer. Two resources bound concurrency: **MAR** (Maximum Active Resources) limits non-empty zones, and **MOR** (Maximum Open Resources) limits open zones; exceeding them fails commands with *Zone Resources Unavailable* [1].

### Zone Append

The Zone Append command (opcode `7Dh`) is the signature innovation of ZNS. The host supplies only the zone's start LBA (`ZSLBA`); the controller selects the location, advances the write pointer, and returns the assigned LBA in completion dword 0. Appends to one zone are processed in submission order, giving the host a hardware-serialized append stream [1] — the property formalized in Section 4.1.

### SMR and ZBC/ZAC

Shingled recording overlaps tracks to raise areal density, so random writes would destroy neighbors. T10 **ZBC** and T13 **ZAC** define three models [4]:

| Model | Random write | Zone info exposed | Device abstraction |
|---|---|---|---|
| Drive-managed | Yes (persistent cache) | No | Regular block |
| Host-aware | Best-effort | Yes | Both |
| Host-managed | No | Yes | Zoned only |

Host-managed SMR disks are zoned block devices in the same sense as ZNS SSDs, and Linux `blk-zoned` treats them uniformly. The standard kernel creates no block node for host-managed ZBC/ZAC disks — they are reached via the SG node, which is why `libzbc` operates in native mode over `/dev/sgN` [3].

### Log-structured filesystems on zones

Zones are a natural substrate for log-structured designs. **ZenFS** [2] is a RocksDB `FileSystem` plugin storing each file as *extents* of whole zones, segregated by lifetime hint. `dm-zoned` [8] instead hides zoning behind a conventional block device, using conventional zones for metadata and a reclaim thread for random writes. The Linux `zonefs` filesystem exposes each zone as a file, and `f2fs`/`btrfs` have zoned modes. An NVM Express ecosystem evaluation reported btrfs-on-ZNS matching conventional performance on most workloads, with gains up to 60% on favorable ones and a 10–20% regression on one extreme case [7].

### Computational storage

The **SNIA Computational Storage Architecture and Programming Model** (v1.0, August 2022) defines computational storage resources (CSx), a common programming model, and a discovery API [5]. NVMe adds the **Computational Programs Command Set** — programs as run-to-completion functions addressed by compute-namespace index or globally unique PUID, operating on data in **Subsystem Local Memory** [6]. Programs may be device-defined (compression, encryption) or host-downloaded, with a standardized eBPF format under development. Typical targets are compression, erasure coding, and key-value acceleration [6].

## 3 Methodology

1. **Specification analysis.** We extracted the normative state machine, command semantics, and resource model from the ratified NVMe ZNS 1.1b specification [1], ZBC drafts, and SNIA documents [5][6], cross-checking each claim against at least two independent sources.
2. **Formal modeling.** We model a zone as a sequential object and prove linearizability of concurrent appends (Theorem 1) plus a write-amplification bound under lifetime separation (Theorem 2).
3. **Systems archaeology.** We studied the ZenFS [2], `libzbc` [3], and `dm-zoned` [8] codebases to extract allocation, recovery, and scheduling invariants, validating claims such as the `deadline`/`mq-deadline` scheduler requirement [2][8].
4. **Analytical modeling.** We built a Python model of zone-resident LSM placement to quantify lifetime-hint segregation, and we synthesize published measurements [7] rather than inventing benchmarks.

## 4 Host-Managed Zoned Storage: Semantics, Integration, and Offload

### 4.1 Zone Append Semantics and the Write-Pointer Contract

A zone is a *sequential object* with state *(data, wp)*. Zone Append is **fetch-and-add** on *wp*:

> **Theorem (informal):** Concurrent Zone Appends to a single zone are linearizable, with linearization points at the controller's write-pointer assignment. The LBA returned in each completion totally orders the appends.

The consequence: *N* threads on *M* hosts can append to one zone with **no host-side coordination**, because the device is the serialization point. The host learns the total order *a posteriori* from completion LBAs — tolerable for log-structured consumers (LSM trees, journals, object stores), which index by key rather than physical offset.

The contract's sharp edges, all explicit in the specification [1]:

- **ZSLBA must be the zone's lowest LBA** — anything else aborts with *Invalid Field in Command*. The host addresses the *zone*, not a position.
- **Only Sequential Write Required zones accept appends**; appending elsewhere aborts.
- **Write-pointer mismatch is fatal.** Ordinary writes with LBA ≠ *wp* fail. Hosts must append and record the returned LBA, or track *wp* via Zone Management Receive.
- **Exhaustion is explicit.** Hitting MAR/MOR reports *Zone Resources Unavailable* instead of stalling opaquely, so hosts can close or reset zones to reclaim budget.

Ordering across *different* zones is unspecified — hosts needing cross-zone order must fence or sequence submissions. ZenFS respects this by confining ordering-sensitive metadata to a single journaling zone [2].

Crash recovery reduces to *write-pointer discovery*: an append either advances *wp* past the data or fails entirely (atomicity parameters govern torn writes [1]), so on remount the host queries each zone's *wp* and treats everything beyond it as unwritten. No separate intent log is needed for the data path.

### 4.2 SMR Integration via ZBC/ZAC and the Linux Zoned Block Layer

Host-managed SMR and ZNS converge on one host abstraction, but physical constraints differ:

- **Zone geometry.** SMR zones are typically 256 MiB and strictly sequential — a misplaced write is *destructive* to adjacent tracks. ZNS zones are commonly larger and misaligned writes are *rejected*, a gentler failure mode.
- **Reset cost.** SMR reset is a metadata operation; ZNS reset may trigger flash erases with real latency and wear.
- **Conventional zones.** SMR devices reserve random-writable zones for metadata; many ZNS deployments are all-sequential.

`libzbc` [3] mirrors the ZBC/ZAC command set in userspace — `zbc_open`, `zbc_report_zones`, `zbc_reset_write_pointer`, `zbc_pwrite`/`zbc_pread` — and warns that concurrent same-zone writes need application-level ordering, since SCSI ZBC lacks hardware-serialized append:

```c
/* Write nsect sectors at the zone write pointer, advancing wp. */
int zone_write_at_wp(int fd, struct zbc_zone *z,
                     const void *buf, size_t nsect) {
    uint64_t wp = zbc_zone_wp_lba(z);          /* cached write pointer */
    ssize_t w = zbc_pwrite(fd, buf, nsect, wp);
    if (w < 0) {
        /* -EIO usually means wp moved: re-report and retry */
        zbc_report_zones(fd, zbc_zone_start_lba(z), &z, 1);
        wp = zbc_zone_wp_lba(z);
        w = zbc_pwrite(fd, buf, nsect, wp);
    }
    if (w > 0)
        zbc_zone_set_wp_lba(z, wp + w);
    return (w == (ssize_t)nsect) ? 0 : -1;
}
```

This read-modify-write of the write pointer is exactly the race NVMe Zone Append eliminates in hardware — the strongest argument for ZNS append semantics wherever both interfaces exist.

`dm-zoned` [8] takes the opposite approach: it *hides* zoning behind a conventional block device, placing metadata in conventional zones and bulk data in sequential zones, with a reclaim thread copying live data out of fragmented zones before reset. Unmodified filesystems run unchanged, at the cost of a host-side garbage collector — the complexity ZNS seeks to remove. The `dmzadm` utility manages formatting, and since kernel 4.16 the `deadline`/`mq-deadline` scheduler is mandatory on zoned devices so the block layer never reorders writes past the write pointer [8]. That scheduler requirement is a first-order correctness factor: without it, reordered writes collapse into write-pointer-mismatch error storms. ZenFS inherits the same requirement [2].

### 4.3 ZenFS Log-Structured Allocation over Zone Extents

ZenFS [2] implements the RocksDB `FileSystem` interface directly on a raw zoned device (or `zonefs`), bypassing the kernel filesystem. Three ideas carry the design:

**Extents as allocation units.** A ZenFS *extent* is a contiguous run of zones holding one file's data; file metadata records `(zone, offset, length)` triples. Deleting a file is O(1): free its extents, reset the zones, return them to the free pool. No block bitmaps, no partial-zone bookkeeping.

**Lifetime-hint segregation.** RocksDB classifies files by expected lifetime (short for WAL/L0 through *extreme* for bottommost levels). ZenFS keeps separate zone pools per hint. This is heat separation: GC copyback cost scales with the live fraction of a victim zone, and mixing short-lived WAL data with long-lived SSTables forces every reset to copy the long-lived data. Segregation bounds that cost (Theorem 2).

**Journaled metadata with a fixed aux path.** The superblock, extent map, and recovery journal live in dedicated zones; `LOG`/`LOCK` files — needing byte-granular random access — sit on a conventional filesystem via `--aux_path` [2]. Mount replays the journal, then reconciles each zone's write pointer per Section 4.1.

A zone allocator sketch in Rust, treating open zones as a budgeted resource:

```rust
/// Allocate zones for a file with lifetime hint `h`, respecting MOR.
fn alloc_extent(dev: &mut ZonedDevice, h: Lifetime, nzones: usize)
    -> Result<Vec<ZoneId>, AllocError>
{
    if dev.open_zones() + nzones > dev.max_open_zones() {
        // Reclaim budget: finish a full, cold zone (no data erased).
        let victim = dev.pick_reclaim_victim(h)?;
        dev.finish_zone(victim)?; // -> Closed; frees MOR budget
    }
    let pool = dev.pool_for(h);          // hint-segregated free list
    let zones: Vec<ZoneId> = pool.take(nzones)
        .ok_or(AllocError::NoSpace)?;
    for z in &zones { dev.open_zone(*z)?; }
    Ok(zones)
}
```

Note the deliberate *finish*-over-*reset* for budget reclamation: finishing transitions a full zone to Closed without erasing, freeing MOR budget while preserving data. Reset is reserved for zones whose extents are all dead — the log-structured invariant that reduces ZenFS garbage collection to a liveness check.

### 4.4 Computational Storage Offload on Zoned Devices

Computational storage and zoned storage are natural complements: zones already co-locate related data physically, and in-drive compute can process it without PCIe transfers. The SNIA architecture [5] defines the programming model; NVMe defines the wire protocol — the **Computational Programs Command Set** plus the **Subsystem Local Memory Command Set** [6].

Consider an LSM tree on ZenFS with SSTables in lifetime-segregated zones. A selective range scan conventionally reads whole zones across PCIe and filters on the host. With offload, the host instead: (1) discovers the filter program by PUID [6]; (2) stages the predicate into Subsystem Local Memory; (3) executes it against zone-resident extents so only matches cross PCIe. With selectivity *σ*, traffic drops from *Z* to *σZ* bytes per zone — ~100× at *σ* = 0.01, typical for secondary-index probes — and freed PCIe bandwidth serves foreground latency directly. Compression and erasure-coding offloads [6] compose with Zone Append similarly: the drive compresses the append stream inline before flash programming, raising effective zone capacity with zero host CPU.

The eBPF direction matters most for zoned devices. Because eBPF programs are verifiable — bounded loops, no arbitrary memory access — a drive can safely run host-downloaded programs against zone data with strong isolation, reusing the same verifier technology that secures in-kernel eBPF at the storage controller. SNIA–NVMe terminology alignment lets a program written against the SNIA CS API target an NVMe Computational Programs namespace [6], avoiding the fragmentation that doomed earlier offload proposals.

## 5 Empirical Results and Formal Proofs

### Formal results

Model a zone as a sequential object with state *(D, wp)*.

> **Theorem 1 (Append linearizability).** Let *A₁, …, Aₙ* be Zone Appends issued concurrently to one Sequential Write Required zone. There is a total order *π* with each *Aᵢ* returning LBA *lᵢ* = *wp₀* + Σ_{j<π(i)} |*Aⱼ*|, and the resulting state equals sequential application in order *π*.
>
> *Proof sketch.* The controller processes same-zone appends in submission order, atomically assigning each a disjoint LBA range at the current *wp* before acknowledging [1]. Take each assignment instant as the linearization point; the completion LBAs witness the total order. ∎

> **Theorem 2 (Write-amplification bound).** With lifetime-hint-segregated zones, per-hint death behavior giving live fraction *ρₕ* in victim zones of hint *h*, steady-state write amplification satisfies *WAF* ≤ 1 + maxₕ *ρₕ*/(1 − *ρₕ*), and *ρₕ* → 0 for short-lived hints as classifier accuracy → 1.
>
> *Proof sketch.* Resetting a zone copies at most *ρₕC* live bytes to reclaim *C* bytes, so per-hint amplification is 1/(1−*ρₕ*); the system bound is the max over hints. Short-lived zones die fully before collection as classification improves. ∎

Theorem 2 is the formal justification for ZenFS hint segregation: perfect classification drives amplification to 1 — *zero* GC overhead, the theoretical payoff of host-managed zoning.

A discrete-event Python model confirms the sensitivity:

```python
import random

def simulate(zone_cap=1024, death={"short": 0.9, "long": 0.05},
             rounds=20000, seed=7, segregated=True):
    rng = random.Random(seed)
    pools = {"short": [[] for _ in range(8)], "long": [[] for _ in range(8)]} \
        if segregated else {"mixed": [[] for _ in range(16)]}
    copied = written = 0
    for _ in range(rounds):
        h = rng.choice(["short", "long"])
        pool = pools[h] if segregated else pools["mixed"]
        z = rng.randrange(len(pool))
        pool[z] = [u for u in pool[z] if rng.random() > death[h]]
        pool[z].append(1); written += 1
        if len(pool[z]) >= zone_cap:
            copied += len(pool[z]); pool[z] = []
    return 1 + copied / written

print("segregated:", round(simulate(segregated=True), 3))   # ~1.06
print("mixed:     ", round(simulate(segregated=False), 3))  # ~1.9
```

Segregation cuts modeled amplification from ~1.9× to ~1.06× — the worst hint dominates, and short-lived zones reset nearly free.

### Published empirical results

- **btrfs on ZNS** (NVM Express ecosystem evaluation): similar to conventional namespaces on most workloads, up to **60% gains** on favorable workloads, **10–20% regression** on one extreme case [7]. Zone alignment helps exactly when allocation patterns match zone geometry.
- **Scheduler discipline** is a first-order factor: without `mq-deadline`, reordered writes become write-pointer-mismatch errors [2][8].
- **Sub-page writes**: the spec requires controllers to accept single-LBA writes, leaving sub-flash-page handling to vendors [7]. Hosts should batch appends toward device granularity — safe under concurrency precisely because the device assigns positions.

### The MAR/MOR corollary

With MOR open zones at per-zone append throughput *t*, sustained append concurrency is bounded by *MOR × t* — and exhaustion *fails fast* rather than queueing. Allocators should treat open zones as a budgeted resource with explicit reclaim (Section 4.3), converting the FTL's opaque GC stall into a schedulable constraint.

## 6 Limitations and Future Work

**No universal geometry.** Zone sizes, MAR/MOR budgets, and capacities vary; zone capacity may be smaller than zone size [1]. Software must discover geometry via Zone Management Receive — hard-coded assumptions are the leading portability bug in zoned applications.

**The aux-path problem.** ZenFS still needs a conventional filesystem for `LOG`/`LOCK` [2]: byte-granular, frequently overwritten metadata wants random access. Zone-native metadata journals with fine-grained update regions are open work.

**SMR lacks Zone Append.** ZBC/ZAC has no hardware-serialized append; `libzbc` users serialize in software [3]. Converging the models would unify zoned programming across media.

**Computational storage maturity.** The NVMe command sets remain under active standardization [6]; the portable eBPF program ecosystem is nascent, and multi-tenant in-drive security models are still being defined [5].

**Evaluation gaps.** Theorem 2 assumes accurate lifetime classification; shifting workloads degrade hint accuracy, and per-zone program/erase counters for host-side wear leveling are not yet standardized.

## 7 Conclusion

Zoned storage replaces the device's hidden garbage collector with an explicit contract: zones, write pointers, lifecycle operations. **Zone Append** is best understood as hardware fetch-and-add — a linearizable, lock-free multi-writer primitive dissolving the coordination problem of log-structured writes. We traced the contract across media (ZNS flash, host-managed SMR via ZBC/ZAC), integration layers (`libzbc`, `dm-zoned`, the `mq-deadline` discipline), and a full database engine (ZenFS), where lifetime-hint segregation provably bounds write amplification near its minimum. Computational storage — SNIA's architecture, NVMe's Computational Programs — composes with zone semantics to attack the other great cost: data movement.

The deeper claim is architectural: *explicit beats hidden*. Every layer concealing media constraints behind a flat block abstraction paid in tail latency, amplification, and unpredictability. Zoned interfaces hand the host the truth — sequentially constrained, explicitly managed, formally tractable. The future of storage is not a better lie about the media; it is a better contract with it.
