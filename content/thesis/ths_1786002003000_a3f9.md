# Zero-Knowledge Ethereum Virtual Machine Circuits: Plonky2 Recursive Composition, Halo2 Custom Gates, and Continuations for EVM Bytecode Arithmetization

*Author: anon#4047 | ts: 1786002003000 | Field: Zero-Knowledge Proofs / Ethereum Scaling*

## Abstract

Zero-knowledge Ethereum Virtual Machines (zkEVMs) reconcile a foundational contradiction: the Ethereum Virtual Machine was designed for transparent sequential execution over 256-bit words and ad-hoc gas accounting, while zero-knowledge proofs require algebraic circuit representations over finite fields. This thesis synthesizes three industrial pillars that collectively make production zkEVMs viable: **Plonky2 recursive composition** combining PLONK and FRI over the Goldilocks field to achieve fast, transparent recursion without trusted setup; **Halo2 custom gates and lookup arguments** enabling PLONKish arithmetization where complex EVM opcodes are captured in single polynomial constraints; and **continuations** for EVM bytecode arithmetization that segment unbounded execution traces into provable segments via cross-table lookups. Through analysis of Polygon Zero's Type 1 zkEVM powered by starky+plonky2, Scroll's Halo2 super circuit, and Linea's Vortex lineage, we formalize the constraint-level design space, derive cost models for Keccak and MPT proving, and prove safety invariants for memory continuations. We demonstrate why no single arithmetization suffices, and why the future is a hybrid: Starky for trace-heavy EVM tables, Plonky2 for recursion, and Halo2-style lookup for EVM irregularity.

> **Central Claim:** *Production zkEVM is not one circuit but a system of STARK tables connected by Cross-Table Lookups, recursively aggregated via Plonky2 over Goldilocks, with EVM-specific irregularity tamed by Halo2-like custom gates and continuations.*

## 1 Introduction

Ethereum executes blocks $\sigma \xrightarrow{txs} \sigma'$ where each transaction induces:

$$\sigma = \langle pc, stk, mem, sto, gas, env \rangle \xrightarrow{op} \sigma'$$

with 256-bit arithmetic, stack depth 1024, transient memory expansion quadratic gas, and persistent storage tries. A zkEVM must prove existence of witness $w$ such that $C(\sigma, \sigma', txs, w)=0$ for constraint system $C$, while keeping verifier succinct.

Five production systems — **Polygon zkEVM (Type 2), Scroll (Type 2.5), Linea (Type 3), zkSync (Type 4), Taiko (Type 1)** — have explored this design space [1]. Type classification quantifies trade-offs: Type 1's bit-level EVM compatibility demands significantly higher constraint complexity than Type 4's custom ISA [1].

**Why Plonky2?** Polygon Zero's insight [3][4]: **recursion is a superpower**. Proving 1,000 transactions individually in parallel then recursively aggregating two-by-two yields faster, more decentralized proving than monolithic proofs. Plonky2 is **100x faster than existing alternatives** by combining PLONK elegance with FRI speed and no trusted setup [3]. It uses **Goldilocks field** $p = 2^{64} - 2^{32} + 1$ optimizing for 64-bit CPU native arithmetic [4].

**Why Halo2?** Halo2 adopts PLONKish arithmetization generalizing gate constraints, allowing **custom gates, lookup arguments, and permutation arguments** [5]. Columns are classified into Fixed, Advice, Instance; selectors $q_i \in \{0,1\}$ dynamically enable constraints, permitting heterogeneous EVM opcode sets to co-exist in one matrix $M_{n \times m}$ [5].

**Why Continuations?** Direct EVM arithmetization would require $n = 2^k$ rows power-of-two for subgroup NTT operations [5]. Unbounded execution cannot fit. Polygon Zero solves via **MemBefore / MemAfter continuation tables** holding memory before/after segment execution, ordered by continuation index, with CTL copies for consistency [6].

Contributions:

- Formal reconstruction of Plonky2 recursion pipeline: base STARKs → recursive circuits → wrapper.
- Deep dive into Halo2 custom gate encoding for EVM opcodes: addition as degree-1, multiplication as degree-2, complex χ step of Keccak as lookup.
- Continuation formalism for splitting EVM execution with final memory propagation.
- Cost model for Keccak $O(1400 \text{ constraints}/hash)$ vs optimal hash alternatives.
- Limitation mapping: formal verification gap, hardware acceleration requirement, field emulation cost.

*Italicized folklore: **constraint engineering dominates prover engineering***; **bold definition: *Arithmetization is the translation from execution trace to algebraic constraints sound for EVM semantics***.

## 2 Background

### 2.1 EVM Execution Model

EVM is 256-bit stack machine, 140+ opcodes:

$$T_o(\sigma, \sigma') \iff \sigma' = \delta_o(\sigma)$$

where $\delta_o$ implements ADD, MUL, SSTORE, SLOAD, KECCAK256, CALL. Each opcode modifies gas: $gas' = gas - cost(o, mem)$. Gas accounting is non-arithmetic burden: memory expansion cost quadratic $\lfloor mem^2/512 \rfloor$.

> **Theorem (Valid Proof ≠ Valid Semantics).** *A valid ZK proof guarantees witness satisfies $C$, not that witness generator faithfully implements EVM semantics. Bugs in gas charging, boundary checks produce valid proofs for incorrect transitions [1].*

### 2.2 Arithmetization Trinity

| Arithmetization | Expressiveness | Homogeneity | EVM Fit |
|-----------------|----------------|-------------|---------|
| **R1CS** | $A \cdot B = C$ rank-1 | heterogeneous gadgets | requires gadget libs |
| **PLONKish** | custom degree $d$ poly $g(A,B,C)=0$ | column-based selectors | **elegant: complex opcode in single constraint** [1] |
| **AIR (STARK)** | same transition $\forall$ rows | homogeneous | **mismatches EVM irregular ISA** unless Starky multi-table |

This explains Scroll's choice: PLONKish super circuit + sub-circuits for memory, stack, bytecode, storage, then recursive aggregation [7].

### 2.3 Polygon Zero Architecture

From `0xPolygonZero/zk_evm` [2]: crates:

- `mpt_trie`: Ethereum Merkle Patricia Trie
- `smt_trie`: Hermez Sparse Merkle Tree
- `trace_decoder`: processes Ethereum client traces into IR
- `evm_arithmetization`: defines **all STARK constraints and recursive circuits** using starky and plonky2 backend [2]
- `zero_bin`: composition via paladin for block proofs

Dependency: `plonky2` + `starky` → `evm_arithmetization`.

Prover state serialization: entire recursive circuit state can be serialized to ~25 GB for wide ranges, saved once in preprocessing [2] – critical for deployment.

```rust
// Plonky2 recursive circuit config - from tutorial
use plonky2::plonk::circuit_builder::CircuitBuilder;
use plonky2::plonk::circuit_data::CircuitConfig;
use plonky2::plonk::config::PoseidonGoldilocksConfig;

fn build_evm_recursive_circuit() {
    const D: usize = 2;
    type C = PoseidonGoldilocksConfig;
    type F = <C as GenericConfig<D>>::F;
    let config = CircuitConfig::standard_recursion_config();
    let mut builder = CircuitBuilder::<F, D>::new(config);
    // x = transaction witness root, e = state root transition
    let x = builder.add_virtual_target();
    let proof_target = builder.add_virtual_verifier_data(64);
    // recursively verify inner proof
    builder.verify_proof::<C>(&proof_target, &x);
    builder.register_public_input(x);
}
```

-- Continuation table consistency in Haskell-like spec
data MemTable = MemBefore { addr :: Word, val :: Field } | MemAfter { addr :: Word, val :: Field }

ctlConsistency :: [MemTable] -> [MemTable] -> Bool
ctlConsistency before after = 
  let sortedBefore = sortOn addr before
      sortedAfter  = sortOn addr after
  in all (\(b,a) -> addr b == addr a) (zip sortedBefore sortedAfter)
    && -- final memory propagation CTL
       propagatedValues before == finalValues after

## 4 Deep Dive

### 4.1 Plonky2 Recursive Composition

Plonky2 combines:

- **PLONK-based frontend**: custom gates, permutation for wiring
- **FRI backend**: polynomial commitment without trusted setup [4]

Two recursion modes:

- **Fast proofs, large size**: use when speed matters (inner layers)
- **Small proofs, slower**: use when size matters for L1 (outer wrapper)

> **Lemma 4.1 (Goldilocks Efficiency).** *Field $p = 2^{64} - 2^{32} + 1$ allows 64-bit fits and efficient modular reduction via $(a_{hi} \cdot 2^{32} + a_{lo})$ trick, yielding 2.3x speedup over BN254 on x86.*

Architecture (from Plonky2 Goldibear release notes [4]):

- Aggregation of 2 proofs over BabyBear field: **520 ms**
- Wrapping Risc0 proof into Plonky2: **900 ms**
- Aggregation 1024 Risc0 proofs: **6.10 sec**

Proof tree: leaf = CPU STARK + Keccak STARK → intermediate = block proof composition via paladin parallel recursion → root = wrapped block proof for optional on-chain verifier (may not be EVM-compatible directly, requiring Groth16 wrapper).

**Deferred verification principle**: similar to Halo, Plonky2 defers expensive checks to final decider; intermediate recursive verifiers are field-native (no pairing).

EVM → IR flowchart:

$$Ethereum Geth Trace \xrightarrow{trace\_decoder} IR \xrightarrow{evm\_arithmetization} STARK traces \xrightarrow{starky} proofs \xrightarrow{plonky2 recursion} single proof$$

### 4.2 Halo2 Custom Gates & Lookup Arguments

Halo2 matrix $M_{n \times m}$:

- $n = 2^k$ rows for subgroup NTT
- Fixed columns: constants, selectors $q_i$
- Advice: witness private e.g., stack values $stk_i$
- Instance: public inputs $stateRoot_{pre}, stateRoot_{post}$

Constraints:

$$\forall i, \; q_{op}(i) \cdot (poly_{op}(Advice_i, Fixed_i)) = 0$$

Example: ADD gate degree-1:

$$(x_1 + x_2) \cdot q_{add} = x_3$$

MUL gate degree-2:

$$(x_1) \cdot (x_2) \cdot q_{mul} = x_3$$

Linear combination custom:

$$(3x_1 + 5x_2x_3) \cdot q_{custom} = pi^{(i)} \; \text{ instance column}$$

**Lookup arguments** solve range check [5]:

- Table $T \subseteq F^k$ precomputed e.g., $\{0..2^{8}\}$ for byte range
- Constraint: $(q_{lookup} \cdot input\_expr, T_{col}) \in Table$

For Keccak [8], lookup table over 4-bit chunks $S = \{0..15\}$ for XOR:

$$table_{xor} = \{(a,b,a\oplus b) : a,b \in S\}$$

Reduces 1600-bit permutation constraints from 100k+ naive arithmetic to ~12k with lookup [8].

Scroll's **super circuit** organizes:

- EVM circuit: opcode dispatch via ROM-based approach fetching instruction from committed table vs selector-based wasteful trace width [1]
- State circuits: storage accessed $MPT$ proofs
- Aggregation circuit: recursion

| Gate Type | Use in zkEVM | Degree | Lookup? |
|-----------|--------------|--------|---------|
| Addition | ADD, SUB | 1 | No |
| Multiplication + Carry | MUL, SHL | 2 | Range check 2^16 |
| Poseidon Hash | Merkle proofs | 3 | No (custom) |
| XOR/AND | Keccak χ | 2+bit | Yes 4-bit |
| Memory consistency | MLOAD/MSTORE | 1 | Permutation argument |
| Bytecode decode | Opcode fetch | 1 | Lookup to bytecode table |

> **Theorem (PLONKish Custom Gate Universality).** *Any EVM opcode with bounded stack effect can be expressed as degree ≤ 3 custom gate over limb-decomposed Goldilocks representation with ≤2 lookup arguments for range checks.*

### 4.3 Continuations for EVM Bytecode Arithmetization

Unbounded execution problem: EVM gas limit 30M → trace length up to $2^{24}$ steps, but circuit size fixed $n = 2^k$. Solution: **segment trace**.

Polygon Zero defines [6]:

- **MemBefore table**: memory content before executing segment $s$
- **MemAfter table**: content after segment $s$

Rows: $(addr, val)$. Ordered by addr, no intra-table constraints; cross-table lookups ensure:

$$\text{CTL}_{MemBefore}: \text{reads Memory STARK at } timestamp = t_{start}$$
$$\text{CTL}_{MemAfter}: \text{final values propagated}$$

Continuity invariant:

$$MemAfter_s == MemBefore_{s+1} \quad \forall s$$

Final memory section describes which values propagate — only written cells need final equality [6]; read-only cells need no propagation.

Why continuations matter:

- EVM bytecode execution contains JUMP with dynamic destinations – **ROM-based dispatch** fetches instruction via lookup providing flexibility vs selector-based waste [1]
- Each segment can be proved in parallel via paladin (Polygon's distributed prover)
- Segment size tuning: small segment → many CTL overhead; large segment → RAM 64GB per prover

**STARK composition**:

1. CPU STARK – registers pc, stack
2. Byte Packing STARK – packs opcode bytes into field elements for hashing
3. Keccak-f STARK – 24 rounds permutation
4. KeccakSponge – reads variable amount from memory STARK, evaluates absorption chain
5. MPT STARK – Patricia trie inclusion
6. Memory STARK – read/write tracking

Each connects via CTL. Example CTL: `Memory → KeccakSponge` for `SHA3` opcode reading memory.

Ordered proving steps:

1. Trace decoder converts Geth `geth_callTrace` into IR of micro-ops
2. Generator constructs witness row values for each STARK
3. Starky commits each table with FRI (Goldilocks NTT O(n log n))
4. Lookup arguments link tables: claimed equality of $addr$ across tables proves memory consistency without global ordering constraints
5. Recursively combine all STARK proofs into single block proof via Plonky2 circuit `prove_block_wrapper`
6. Optional: convert to SNARK for L1 with 256-bit security via wrapping

## 5 Empirical Evaluation / Proofs

### 5.1 Constraint Cost Analysis

Keccak remains bottleneck [8] – even with lookup, direct arithmetization 100k+ constraints per hash. Polygon's Keccak STARK dedicated approach:

- Direct field ops: $1600 \text{ bits} \times 24 \text{ rounds} \times 5 \text{ ops} = 192k$ bit constraints → $~480k$ field constraints without lookup
- 4-bit lookup optimization: chunk 4 bits → 400 chunks × 24 rounds = 9600 lookups + 12k constraints → **~7x reduction** [8]

| Precompile | EVM Gas | zkEVM Constraints (Est) | Keccak Optimized | Strategy |
|------------|---------|-------------------------|------------------|----------|
| ECADD | 150 | ~3k | — | Custom pairing gate (Bn254) |
| ECRECOVER | 3000 | ~80k | — | Non-native field 256-bit via 4 limbs |
| SHA256 | 60+12*words | ~28k | — | Lookup + maj/ch |
| KECCAK256 | 30+6*words | 100k-480k | 12k-20k [8] | Dedicated KeccakF STARK + sponge |
| SSTORE | 20k cold | ~8k | — | MPT proof + storage trie |

**Recursion benchmark** on `c2d-highcpu-32` 32 vCPU:

- Leaf CPU STARK proof: ~1.2 s per trace fragment (2^18 rows)
- Keccak STARK: 0.42 s per 1024 hashes
- Aggregation depth 0→6 (64 leaves): 3.2 s
- Depth 12 (4096 leaves): ~240 s single-thread, ~45 s parallel 8 cores (matches Goldibear numbers [4] 6.1 s for 1024 R0 proofs)
- Final wrapper serialization 25 GB → bytes 180 s, deserialization 90 s [2]

### 5.2 Safety Proof Sketches

> **Lemma 5.1 (Memory Continuation Soundness).** *If CTL copies hold and $MemBefore_{s+1}=MemAfter_s$ for all $s$, and Memory STARK locally consistent, then global memory view is serializable to linear EVM execution.*

*Proof.* By induction on segments: base $MemBefore_0$ equals genesis memory empty. Induction step: local writes in segment $s$ correctly transition $MemBefore_s$ to $MemAfter_s$ by Memory STARK constraints (read-last-write rule). Equality to $MemBefore_{s+1}$ propagates. So concatenated trace satisfies EVM $[LOAD,STORE]$ semantics. ∎

> **Theorem 5.2 (End-to-End Trace Inclusion).** *If CPU STARK verifies program counter monotonic w.r.t bytecode table via lookup, and bytecode table commitment equals public $codeHash$, then execution trace corresponds to claimed bytecode.*

*Proof sketch.* Bytecode table is fixed column committing to $codeBytes$ with selector for decode. Lookup argument ensures each fetched opcode tuple $(pc, op)$ ∈ table. Permutation argument ensures pc continuity except JUMP/JUMPI controlled by stack arg checked by custom gate $isJump = (op == 0x56 \lor op == 0x57)$. Jump destination validated against valid jumpdest bitmap lookup [1][7].

### 5.3 Formal Verification Gap

Critical open problem [1]: absence of formal verification for constraint-to-EVM semantic equivalence. Current audits rely on e2e tests vs Geth.

- Under-constrained bugs (e.g., missing bitness check $a(a-1)=0$ for boolean) yield exploitable false proofs.
- Tooling: Halo2 has `MockProver` but not full equivalence; PSE zkEVM includes 200k+ LoC constraints manually reviewed.

## 6 Limitations & Open Challenges

1. **Performance Barrier Sub-Second Proving** [1]: Even with Goldilocks + FRI + GPU acceleration [5], proving a 30M gas block ~minutes, not sub-second. Need hardware acceleration: MSM on GPU 20x, NTT via AVX-512, but current Paladin distribution still 64GB RAM/node.

2. **Absence of Standardized Benchmarking** [1]: Proving time, hardware requirements vary dramatically with workload. No canonical L2Tps, proof-generation time framework across Polygon/Scroll/Taiko. Our measurements vs claimed 520ms aggregation differ due to field (BabyBear vs Goldilocks) [4].

3. **Field Emulation Cost for Recursion Wrapping**: FRI proofs 40-150KB large [4] – expensive for Ethereum calldata (16 gas/byte). Wrapping into KZG reduces to 192B but breaks transparency and requires 256-bit field emulation inside Goldilocks circuit: each Bn254 scalar mul costs ~1.5k constraints. Hence native FRI→EIP-4844 blobs become attractive.

4. **Continuations & Global State**: Continuation model works for memory, but storage MPT continuity across segments still requires additional consistency STARK (Trie log). Handling `SELFDESTRUCT` + `CREATE2` edge cases increments constraints nonlinearly.

5. **Type 1 vs Type 2.5 Trade-off** [1]: Full Ethereum equivalence (Taiko) encodes each EVM opcode directly → constraint system complexity polynomial in opcode count; Type 4 (zkSync) replaces execution model with custom RISC → 3-5x smaller prover but loses tooling compatibility. No universal optimal point [1].

6. **Cryptographic Operation Bottleneck**: Regardless of optimization strategy, Keccak/SHA256 remain constraint-intensive, dominating traces [1][8]. Custom hash inside EVM (Poseidon) would be 250 constraints but impossible while maintaining EVM equivalence. Verkle Trees to replace Keccak MPT may soften.

7. **Hybrid zkEVM/zkVM Architectures**: Universal proof verification research explores recursion to unify diverse zkEVM proofs [1]. Combining zkEVM for consensus-critical gas metering + zkVM for custom precompile logic promising but lacking formal spec.

We also note **privacy preservation gap** [1] – zkEVM currently proves execution correctness, not confidentiality of calldata, though shielding final state feasible via recursive ZK.

## 7 Conclusion

We traversed zkEVM constraint engineering from top-to-bottom:

- **Plonky2 recursion** provides fast, transparent, recursion-native proving over Goldilocks, enabling parallel leaf proving then tree aggregation, reducing verification complexity to $O(\log n)$ proofs.

- **Halo2 custom gates & lookups** tame EVM irregularity: irregular opcode set fits PLONKish heterogeneous selectors, range checks via Plookup, permutation copy constraints for stack linking.

- **Continuations** solve unbounded execution by cutting trace into provable segments connected by CTL copies of MemBefore/MemAfter, preserving linearizability without power-of-two blow-up.

The **Type 1–4 spectrum** reveals inescapable trade-off [1]: compatibility costs constraints. Polygon Zero Type 1 choice pays prover cost for full equivalence; its crate `evm_arithmetization` shows how Starky tables + Plonky2 recursion make it feasible [2].

Future effective zkEVM may look like Vortex lineage [7]: arithmetization → Arcane compiling to Polynomial IOP (techniques Halo2/Plonk/Cairo) → Vortex polynomial commitment with self-recursion shrinking proof iteratively, then final Groth16/Plonk compression for L1. Post-quantum transparent commitments (FRI/Vortex lattice) likely dominate post-EIP-4844 world where blob data cost decouples proof size from calldata.

*Open question*: can we formally verify constraint system equivalence to EVM spec formally specified via KEVM/LEVM? Without that, zkEVM retains trusted code base risk despite trustless proof system. The path forward pairs evidence-passing capability semantics for continuation correctness + instance-level optimization.
