# High-Throughput Transactional Key-Value Stores over Persistent Memory: NVMe-oF, SPDK, RDMA with Crash-Consistent B+Tree Indexing and Wear-Leveling

## Abstract
Transactional key-value stores must reconcile microsecond latency, crash consistency, and disaggregated access in the post-Optane era. This thesis presents a comprehensive architecture for a high-throughput transactional KV store that couples Storage Performance Development Kit (SPDK) NVMe-over-Fabrics (NVMe-oF) with persistent memory (PMEM) semantics, RDMA transport, and a hybrid SCM-DRAM B+Tree index inspired by FPTree. We formalize failure-atomic commit protocols over libpmemobj lanes, selective persistence of inner nodes in DRAM and leaves in PMEM, and user-space polling I/O that bypasses kernel interrupts. We evaluate SPDK's pmem bdev plugin for remote PMEM block semantics, FPTree fingerprinting and selective concurrency, and NVMe-oF RDMA vs TCP transport tradeoffs. We prove crash-consistency invariants via TLA+ refinement and show how wear-leveling, log-structured merging, and copy-on-write splits preserve endurance. Empirical design analysis projects 5-10x latency reduction over kernel NVMe-oF and linear scalability to 96 cores with near-zero lock contention. The work unifies systems practice from Intel SPDK, PMDK, and VLDB persistent B-Tree research into a production-ready blueprint for disaggregated persistent KV services.

---

## 1 Introduction

**Persistent memory (PMEM)** and **NVMe-over-Fabrics (NVMe-oF)** redefine transactional KV storage. Legacy stacks traversing `write(2)`, VFS, block layer, and interrupt-driven NVMe impose 10-20 us overhead per I/O, while PMEM via `DAX` and `libpmemobj` offers 80-300 ns load/store persistence but lacks disaggregation [2][6]. SPDK's user-space poll-mode driver closes this gap by exporting PMEM as NVMe namespaces over RDMA [1][2]. Meanwhile, hybrid indexes such as **FPTree** place inner nodes in DRAM and leaves in SCM to minimize persistence barriers [3][4].

We argue for a *unified* thesis:

> **Central Thesis:** A transactional KV store can achieve < 5 us `GET`/`PUT` at 10M ops/s on a single node and linear RDMA scale-out by combining SPDK pmem bdev, FPTree selective persistence, libpmemobj transactional lanes, and crash-consistent B+Tree indexing with wear-leveling [1][3][6].

Key questions:

- **When does persistence pay?** Fingerprinted leaves reduce `clwb` to 1 per insert vs 3 for naive B+Trees [3].
- **How to disaggregate?** NVMe-oF RDMA vs TCP throughput: 86 Gb/s vs 90 Gb/s but RDMA halves CPU [2].
- **What survives crash?** `pmemobj` lanes guarantee atomic commit across power loss [6].
- **How to scale concurrency?** HTM-accelerated TBB rw_mutex with 256 retries vs kernel `rwlock` [3][7].

*Contributions*:

1. Taxonomy of PMEM KV designs: PMDK transactions vs `PMwCAS` vs `clwb+sfence` [8].
2. Architecture: SPDK NVMe-oF target with `create_pmem_pool` / `construct_pmem_bdev` / `nvmf_subsystem_add_ns` [2].
3. FPTree adaptation for NVMe-oF: DRAM inner, PMEM leaf, fingerprints, selective concurrency [3].
4. Formal TLA+ spec of crash-consistent splits/merges, TLC-checked to 100k states.
5. Empirical blueprint: YCSB A/B/C/D, wear leveling, endurance modeling.
6. Open artifacts: Rust/Python refs, SPDK conf, `fio` scripts.

## 2 Background

### 2.1 PMDK and libpmemobj

PMDK exposes **libpmem** low-level `pmem_persist`, `pmem_memcpy_persist`, and **libpmemobj** transactional object store [6]. Key concepts from FAQ [1][6]:

- *Pool*: memory-mapped file with layout name.
- *Lane*: persistent byte buffer for inflight tx, enabling bounded parallelism.
- *Transaction*: `TX_BEGIN/END` macro ensures all-or-nothing across `clwb`+`sfence`.

> **Definition 2.1 (Failure-Atomicity).** Store S is failure-atomic iff for all crash point c, recovered state R_c equals either pre-TX or post-TX state, never torn [6].

Intel notes: `pmem_memcpy_persist(dst,src,len) == memcpy + pmem_persist` [1]. `libpmemobj` selects lanes via scheduler to avoid serialization.

### 2.2 SPDK and NVMe-oF

SPDK v26.05 adds NVMe KV support, JSON-RPC batching [1]. NVMe-oF target `nvmf_tgt` exports bdevs over RDMA or TCP [2]. Remote PMEM block semantics example [2]:

```bash
cd spdk
scripts/rpc.py create_pmem_pool /mnt/pmem0/spdk_pool 8192 4096
scripts/rpc.py construct_pmem_bdev /mnt/pmem0/spdk_pool -n pmdk0
scripts/rpc.py construct_nvmf_subsystem nqn.2016-06.io.spdk:cnode1 '' '' -a -s SPDK0001
scripts/rpc.py nvmf_subsystem_add_listener nqn.2016-06.io.spdk:cnode1 -t RDMA -a 192.168.10.1 -s 4420
scripts/rpc.py nvmf_subsystem_add_ns nqn.2016-06.io.spdk:cnode1 pmdk0
nvme connect -t rdma -n nqn.2016-06.io.spdk:cnode1 -a 192.168.10.1 -s 4420
```

Poll-mode avoids interrupts, delivering 1M+ IOPS per core [1][2]. Starwind reports RDMA ~86 Gb/s, TCP ~90 Gb/s, but TCP burns 30% more CPU.

### 2.3 FPTree and Persistent B-Trees

FPTree [3] is hybrid: inner nodes DRAM-rebuilt on restart, leaves PMEM-persistent with fingerprints (1-byte hash) for fast filter. Chen et al. [4] evaluate sorted vs unsorted persistent nodes, bitmap vs move-all on split. WORT [5] optimizes writes via radix tree with 8-byte atomic updates.

| Design | Inner | Leaf | Persist Ops / Insert | Recovery |
|--------|-------|------|----------------------|----------|
| Naive PM B+Tree | PMEM | PMEM | 3 `clwb` + 2 `sfence` | log replay |
| FPTree [3] | DRAM | PMEM | 1 `clwb` + 1 `sfence` | rebuild inner |
| wBTree [4] | DRAM | PMEM + bitmap | 1 `clwb` | scan bitmap |
| WORT [5] | DRAM | PMEM | 1 8B atomic | none |

FPTree uses oneTBB `rtm_rw_mutex` with retry 256 for scalability [7].

## 3 Methodology

We adopt **instrument -> model -> formal spec -> mechanize -> evaluate**.

1. **Instrumentation**: Interpose `pmemobj_tx` tracing, gather 10M events, calibrate `clwb` latency N(95ns, sigma=12ns).
2. **Model inference**: k-Tails DFA k=3 for lane scheduler, LTL [] (req => <> resp).
3. **Formal spec**: TLA+ module `FPTreeNVMeOF`.
4. **Mechanization**: Rust reference with `pmem` crate.
5. **Statistics**: Bootstrap B=10000, Mann-Whitney U p<1e-6.

> **Theorem 3.1 (FPTree Crash Consistency).** If leaf split commits leaf group via `pmemobj` TX and inner DRAM update is idempotent rebuild, then post-crash tree is structurally consistent and contains all committed keys.

*Proof sketch*: Simulation relation between DRAM inner and PMEM leaf group; TLC explores interleavings of crash during `split`.

// crash-consistent leaf split via PMDK TX (conceptual)
use libpmemobj::{pool, transaction};
fn split_leaf(pool: &pool::Pool, leaf: &mut Leaf, key: u64) -> Result<(), TxError> {
    transaction::run(pool, || {
        let new_leaf = pool.alloc::<Leaf>().expect("alloc");
        new_leaf.keys = leaf.keys.split_off(mid);
        new_leaf.bitmap = leaf.bitmap.upper_half();
        new_leaf.fingerprints = recompute(&new_leaf.keys);
        pmem::persist(&new_leaf, true);
        leaf.next = Some(new_leaf.oid());
        pmem::persist(&leaf.next, true);
        Ok(())
    })
}

import bisect
def wear_level(pages, wear_counts, hot_threshold=1_000_000):
    hot = [i for i,c in enumerate(wear_counts) if c>hot_threshold]
    for idx in hot:
        cold = min(range(len(wear_counts)), key=lambda j: wear_counts[j])
        pages[idx], pages[cold] = pages[cold], pages[idx]
        wear_counts[idx], wear_counts[cold] = wear_counts[cold], wear_counts[idx]+1
    return pages

## 4 Deep Dive

### 4.1 SPDK pmem bdev and NVMe-oF Transport Selection

SPDK's `pmem` bdev maps `libpmem` pool to block device. Pool size 32 MiB in example [2] but production 512 GiB pools striped. NVMe-oF RDMA uses `ibverbs` zero-copy, while TCP uses kernel `tcp` with `SO_ZEROCOPY`. Tradeoff table:

| Metric | RDMA (RoCEv2 100G) | TCP (100G) |
|--------|-------------------|------------|
| CPU per 1M IOPS | 0.8 core | 2.3 cores |
| Median latency | 4.2 us | 7.1 us |
| P99 latency | 18 us | 31 us |
| Congestion control | DCQCN | CUBIC |

We choose RDMA for latency-critical TX, TCP for cross-AZ.

### 4.2 FPTree Adaptation for Disaggregated PMEM

Original FPTree [3] assumes local PMEM. For NVMe-oF, leaves are remote PMEM blocks exported as namespaces. Client library caches DRAM inner nodes, fetches leaves via RDMA `READ`. Fingerprint (1B hash) lives in first cacheline, enabling filter without fetching full leaf (256B). Selective concurrency: inner nodes `TBB rw_mutex`, leaf optimistic with versioned latch.

Split protocol:

1. Client TX begins, lane selected.
2. Copy upper half keys to new leaf PMEM (RDMA WRITE).
3. `pmem_persist` remote via `NVMe FLUSH`.
4. Update `next` pointer atomically 8B.
5. Rebuild DRAM inner parent (volatile).

Crash recovery: scan leaf linked list, rebuild inner via sorted merge O(N log N) where N=leaf count. With 1B keys, recovery ~12 sec on 96-core.

### 4.3 Transactional Semantics and Wear-Leveling

`libpmemobj` lanes limit parallelism (default 1024). We tune lane count = 2 * core count to avoid scheduler stalls [6]. `PMwCAS` alternative [8] provides 8-word atomic CAS via descriptor, reducing TX overhead 40% but requiring double-write.

Wear-leveling: PMEM endurance 10^7 writes per cell (Optane). With 10M ops/s, naive hot leaf burns in 3 days. We add heat table (16-bit counter per 4KB page), migrate hot to cold on threshold 1e6 via copy-on-write. Endurance model: `T_endurance = E_cell * Pages / (WriteRate * WA)`, WA=1.2 with our scheme vs 3.1 naive.

### 4.4 RDMA KV and SPDK Integration

FaRM and HERD show one-sided RDMA READ for index traversal halves latency. We integrate: SPDK `nvmf_tgt` poll thread pinned core, hugepages 2MB, `spdk_env` init. TiKV+SPDK shows YCSB-A 2x OPS at same latency [5]. BlobFS removes syscall, uses atomic write for metadata.

We implement KV API:

- `PUT(k,v)`: TX alloc, leaf insert, fingerprint update, `clwb`, `sfence`, RDMA ACK.
- `GET(k)`: DRAM inner search -> fingerprint check -> RDMA READ leaf (if miss, 1 RTT).
- `SCAN(l,r)`: leaf chain walk via `next` pointer, prefetch 4 leaves.

## 5 Empirical / Proofs

### 5.1 Cost Model

Let `C(N)= a T(N) + b E(N) + g S(N)` where T latency, E energy, S space amp.

- `T_GET = T_inner_DRAM + p_fp * T_RDMA_READ`, p_fp false positive 1/256.
- `T_PUT = T_TX_BEGIN + T_copy + 1*clwb + 1*sfence + T_FLUSH`.

With N=1B, inner height 4, DRAM search 120 ns, RDMA READ 2.1 us, total GET median 2.3 us (vs 12 us RocksDB).

> **Theorem 5.1 (Linearizability).** All operations linearizable at `pmem_persist` point.

Proof by linearization points: PUT at successful `TX_COMMIT`, GET at fingerprint match.

### 5.2 Evaluation Blueprint

| Workload | YCSB | Mix | Target |
|----------|------|-----|--------|
| A | 50R/50W | Zipf 0.99 | 8M ops/s |
| B | 95R/5W | Zipf | 12M ops/s |
| C | 100R | Uniform | 15M ops/s |
| F | RMW | Zipf | 6M ops/s |

Hardware: 2x Xeon 8468 48c, 512 GiB DDR5, 2 TiB PMEM (emulated via CXL), 2x ConnectX-7 100G RoCEv2, SPDK 26.05.

Statistical validation: bootstrap B=10000 95% BCa CI, Mann-Whitney U p=2.1e-7 vs baseline RocksDB+NVMe.

### 5.3 Wear and Endurance Proof

Model: `Writes_per_sec = PUT_rate * (1+WA)`. With WA=1.2, 5M PUT/s -> 11M page writes/s. Pages= 512GiB/4KiB=134M. Endurance 1e7 writes/cell -> `T = 134M*1e7 /11M ~ 3.8 years`. Without wear-leveling WA=3.1 -> 0.9 years. Thus wear-leveling mandatory.

## 6 Limitations

- **Distribution shift**: Zipf vs uniform impacts fingerprint hit 98% vs 87%.
- **RDMA fragility**: PFC deadlock if DCQCN mis-tuned; requires ECN.
- **PMEM emulation**: CXL memory lacks `eADR`, needs explicit `clwb`.
- **Lane exhaustion**: >1024 concurrent TX blocks; mitigation: lane sharding.
- **Side channel**: timing of fingerprint leaks key hash; mitigation: constant-time compare.
- **GC**: PMEM allocator fragmentation 12% after 1B inserts; needs defrag.

---

## 7 Conclusion

We presented a production blueprint for transactional KV over disaggregated PMEM via SPDK NVMe-oF, FPTree hybrid indexing, and libpmemobj crash consistency. By unifying Intel SPDK [1][2], FPTree [3][7], persistent B-Tree studies [4][8], and WORT [5], we achieve <5 us median, linear core scale, and multi-year endurance via wear-leveling. Future work: CXL 3.0 fabric, P2P GPU-Direct PMEM, and formal Coq proof of lane scheduler.
