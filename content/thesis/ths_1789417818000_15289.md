# Register Allocation in Optimizing Compilers: From Chaitin-Style Graph Coloring and Iterated Coalescing to Linear Scan and Optimal SSA-Based Allocation on Chordal Graphs

## Abstract

Register allocation maps an unbounded set of symbolic virtual registers to the finite physical register file of a target machine, inserting spill code to memory when demand exceeds supply. This thesis unifies the dominant allocation paradigms of four decades of compiler research. We formalize classical Chaitin-style graph coloring with its interference-graph construction, simplify-select heuristics, and spill-cost model; analyze Briggs conservative and George-Appel iterated coalescing, which eliminate redundant copies without sacrificing colorability; derive the linear-scan algorithm of Poletto and Sarkar as an interval-graph approximation trading code quality for compilation speed; and prove how Hack, Grund, and Goos recast allocation as optimal polynomial-time coloring on chordal interference graphs induced by strict static single-assignment form. Spilling heuristics, register targeting, and live-range splitting are developed as coupled subproblems deciding which values leave registers, where spill code lands, and how ranges subdivide to relieve pressure. Empirical evidence from LLVM, GCC, and HotSpot shows graph coloring remains the quality leader for static compilation while linear scan dominates just-in-time settings, and SSA-based allocators close much of the historical gap between heuristic coloring and optimal assignment.

## 1 Intro

Among all problems a compiler backend must solve, register allocation occupies a uniquely central position: nearly every optimization performed upstream — constant folding, loop unrolling, inlining, vectorization — is eventually judged by how well the allocator converts a sea of temporaries into a tight schedule over a few dozen physical registers. A poor allocator undoes careful loop restructuring by spilling the very values the unroller exposed; a good allocator can make a simple loop nest run at memory bandwidth. The problem is *NP*-hard in its general formulation [1], and yet every production compiler must solve it thousands of times per second, in JIT contexts, or once per function with maximum care, in ahead-of-time settings.

The landscape of solutions can be organized along three axes: **fidelity of the model** (interference graphs versus live intervals), **optimality ambitions** (heuristic coloring versus provably optimal assignment on restricted graph classes), and **compilation-time budgets** (iterated aggressive coalescing versus single-pass scans). This thesis walks each axis in depth. Section 2 establishes the mathematical foundations: liveness, interference, register pressure, and the reduction to graph coloring. Section 3 develops a common methodology — building live ranges, estimating spill costs, coloring under constraints — that every subsequent algorithm instantiates. Section 4 dives into the four major algorithm families and the three coupled subproblems of spilling and splitting. Section 5 gives the theoretical analysis and empirical results that determine which allocator wins where, and Section 6 catalogues the limitations that remain open research problems.

## 2 Background

### 2.1 Liveness and live ranges

The primitive concept beneath all allocation is *liveness*: a variable is live at a program point if its current value may be read along some future path before being overwritten. Liveness is computed by a backward dataflow analysis with the classic equations

```
LiveIn(n)  = Use(n) ∪ (LiveOut(n) − Def(n))
LiveOut(n) = ∪ LiveIn(s)  over successors s of n
```

iterated to a fixed point [1]. From liveness we derive *live ranges* — contiguous (in the control-flow sense) regions where a virtual register holds a value that will be used. A range begins at a definition and ends at the last use. Two ranges *interfere* when they are simultaneously live at some program point and cannot share a register, because the physical register could then hold only one of the two values at the point of overlap.

### 2.2 The interference graph and the coloring reduction

The interference graph *G = (V, E)* has one node per live range and an edge between every interfering pair. Register allocation becomes the problem of assigning each node one of *k* colors (physical registers) such that adjacent nodes differ — a *k*-coloring. This reduction is due to Chaitin and co-workers at IBM in the early 1980s, and its appeal is structural: it separates the program-specific analysis (building ranges, computing interferences, estimating spill costs) from a clean combinatorial core (coloring with *k* colors) that decades of graph theory can attack [1][3]. The tragedy is that *k*-colorability is *NP*-complete, so all practical allocators are heuristics.

### 2.3 Register pressure and spill code

The *register pressure* at a program point is the number of simultaneously live values there; the maximum over a function, *Maxlive*, is a hard lower bound on the registers any valid allocation needs. When *Maxlive > k*, some values must be *spilled*: stored to a stack slot and reloaded before each use. Spilling is never free — each spill introduces loads and stores on hot paths — so the allocator's central economic decision is *which* values to spill and *where* the spill code goes. Every allocator discussed here answers these two questions differently.

## 3 Methodology

All modern allocators share a methodological spine, which we now make explicit so the variants in Section 4 can be compared on common ground.

1. **Range construction.** From the intermediate representation, build live ranges for every virtual register. In SSA form each definition dominates its uses, which makes ranges subtree-shaped on the dominance tree [4][5].
2. **Interference computation.** Determine which ranges overlap. Two strategies dominate: Chaitin-style per-instruction liveness iteration [1], and interval-based overlap tests used by linear scan [3].
3. **Spill-cost estimation.** Assign each range a cost approximating the penalty of spilling it, classically *Σ 10^depth(use)* over uses weighted by loop-nesting depth, so that values used inside hot loops are spilled last [1].
4. **Coloring under constraints.** Assign registers respecting interferences, machine constraints (precolored nodes for calling conventions, register classes, aliased subregisters), and copy affinities (preferences that move-related ranges share a register) [2].
5. **Spill and iterate.** If coloring fails under *k* colors, insert spill code for selected ranges and repeat from step 1 on the rewritten program. The loop terminates because spilling strictly reduces register pressure [1].

Within this spine, the deep design decisions are *when* coalescing is attempted relative to simplification, *whether* the coloring is allowed to revisit its spill decisions (optimistic coloring), and *whether* the underlying graph class admits polynomial-time optimal coloring — the topics of the next section.

## 4 Deep Dive

### 4.1 Chaitin-style graph coloring and Briggs conservative coalescing

Chaitin's allocator [1] proceeds in five phases. **Build** constructs the interference graph from liveness. **Simplify** repeatedly removes a node of degree less than *k*, pushing it on a stack; if no such node exists, the **spill heuristic** selects the node with the lowest spill cost, pushes it as a potential spill, and continues. **Select** pops nodes in reverse order and assigns each the lowest-numbered color not used by its already-colored neighbors; a node whose neighbors consume all *k* colors becomes an *actual* spill. **Spill-code insertion** rewrites the program and restarts.

> **Theorem:** If every node removed during simplification has degree less than *k*, the graph is *k*-colorable by greedy selection in reverse removal order.

The proof is immediate: each popped node has fewer than *k* colored neighbors, so a free color always exists. The difficulty is only in nodes the heuristic pushed as potential spills.

**Coalescing** attacks the move instructions compilers emit liberally. If *x := y* is a copy and *x* and *y* do not interfere, their nodes can be merged (coalesced) into one, eliminating the move at code-generation time. Chaitin's original coalescing was *aggressive*: it merged whenever non-interference held, but merging two non-interfering nodes can union their neighbor sets into a node of degree *≥ k*, destroying colorability that existed before — the allocator then pays in spills what it saved in moves [2].

Briggs and co-workers repaired this with **conservative coalescing**: merge the copy-related pair only if the combined node has fewer than *k* neighbors of significant degree, a criterion that provably preserves the colorability of the original graph [1]. The price of conservatism is missed opportunities — many harmless moves survive. George and Appel's **iterated register coalescing** [2] resolves the tension by interleaving simplification with coalescing: whenever simplification exposes new low-degree nodes, coalescing is retried, so the algorithm is simultaneously safe (never makes an uncolorable graph) and far more aggressive than Briggs's one-shot pass. Their measurements showed iterated coalescing removing substantially more moves than conservative coalescing while introducing no additional spills [2]. Later work established that coalescing in full generality is *NP*-hard even on restricted graph classes, which explains why every practical scheme remains heuristic [7].

### 4.2 Linear-scan allocation

Poletto and Sarkar observed that the heavy machinery of graph coloring is wasted where compilation speed matters more than the last few percent of runtime performance — dynamic compilers, JITs, and interactive environments [3]. Their **linear-scan** allocator replaces the interference graph with *live intervals*: each range is approximated by a single interval from its first definition to its last use, and intervals are processed in order of increasing start point. An *active* set holds the intervals live at the current point, sorted by end point; when a new interval starts, expired intervals (those ending before it) release their registers back to a free pool. If no register is free, one interval — typically the one ending furthest in the future, or the new one — is spilled [3].

```
LinearScanRegisterAllocation:
    active ← ∅
    for each live interval i in order of increasing start point:
        ExpireOldIntervals(i)
        if no free register: SpillAtInterval(i)
        else: register[i] ← a free register; add i to active (sorted by end)
```

The algorithm runs in near-linear time and is dramatically faster than even a fast graph-coloring allocator. Yet its code quality is surprisingly competitive: Poletto and Sarkar measured generated code within 12% of an aggressive iterated-coalescing allocator on most benchmarks [3]. The quality gap comes from three approximations: intervals over-approximate true live ranges (holes where a value is dead but the interval persists), the greedy order is fixed by start point rather than by spill economics, and coalescing is absent in the original formulation. Traub, Holloway, and Smith's *second-chance binpacking* variant invests more compile time to close part of the gap [3]. Modern JITs — HotSpot's C1, V8's TurboFan lineage, LLVM's fast register allocator — all descend from this idea.

### 4.3 SSA-based optimal allocation via chordal graphs

The most striking theoretical advance in register allocation came from re-examining the input representation. Hack, Grund, and Goos proved that the interference graphs of programs in **strict SSA form** — where every variable is defined once and each definition dominates its uses — are *chordal*: every cycle of length four or more has a chord [4]. The proof is elegant: live ranges in SSA are subtrees of the dominance tree, and interference graphs of subtrees of a tree are exactly the chordal graphs. Chordal graphs are *perfect* — their chromatic number equals their clique number — and, crucially, they admit a **perfect elimination ordering** (PEO): an ordering of the vertices such that each vertex's later neighbors form a clique. Greedy coloring along a PEO is optimal and runs in linear time.

> **Theorem:** Ignoring φ-functions, the interference graph *G* of a strict SSA program is chordal and *χ(G) = ω(G) = Maxlive* [7].

The consequences are profound. A postorder walk of the dominance tree yields a PEO directly, so the interference graph never needs to be built explicitly; coloring is optimal in *O(k·|V|)*; and the number of registers needed is *exactly* the register pressure — if pressure is lowered below *k* by spilling, no further spills will ever be introduced by coloring [5]. This collapses the classical allocator's iteration: spilling becomes the *only* decision, and coloring is a solved problem. Hack's SSA'09 design [5] shows how φ-functions are handled as parallel copies on control-flow edges (register permutations), how register constraints and precoloring integrate, and how coalescing can be reformulated as graph recoloring with affinity costs. Pereira and Palsberg independently observed that the vast majority of methods in real Java libraries already produce chordal interference graphs, and built industrial-strength allocators on puzzle-solving and punctual coalescing atop the same insight.

### 4.4 Spilling heuristics

Spilling is where allocators spend their economic judgment, and the heuristics differ sharply across families.

- **Chaitin-style:** spill cost *Σ 10^depth* penalizes uses in deep loops exponentially; the simplify phase ejects the cheapest node when stuck. Briggs's *optimistic coloring* improves on Chaitin by deferring the spill decision: potential spills pushed during simplification may still be colorable at select time, because their neighbors may have received non-conflicting colors [1]. Only genuine failures become actual spills.
- **Linear scan:** the spill decision is local and greedy — when the active set is full, spill the interval with the furthest end point (*farthest-next-use* intuition), splitting its range at the current point so the head keeps a register. This is optimal for pure interval graphs but suboptimal once intervals are split, because the choice ignores loop depth and use density [3].
- **SSA-based:** spilling is reduced to *register-pressure lowering*: spill decisions are made on the SSA program to bring *Maxlive* below *k*, after which coloring is guaranteed spill-free [5]. Braun and Hack's improved spilling algorithm for SSA form places spill code to minimize the number of inserted loads and stores rather than merely minimizing the number of spilled values, exploiting the fact that SSA live ranges are contiguous on the dominance tree.

The common failure mode is *spill-everywhere* versus *spill-selective*: Chaitin's original design spilled a live range at every point (spill everywhere), while modern allocators split ranges and spill only the high-pressure segments — the subject of the next subsection.

### 4.5 Live-range splitting

Live-range splitting subdivides a range so that only the congested portion is spilled, letting the remainder keep a register. The classical mechanism is **splitting at basic-block boundaries**: a range live across a hot loop and cold surrounding code can be split so that the loop-carried portion is spilled while the cold portions stay in registers, at the cost of shuffle code (loads/stores or moves) at the split points [6]. SSA form makes splitting almost free in one direction: φ-functions *are* live-range splits — each φ-argument is a distinct range, so the allocator can color arguments and results differently and only pays for the copies that survive coalescing.

Splitting interacts with every other decision. Splitting reduces the degree of interference-graph nodes, which helps simplification; it creates new copy instructions, which coalescing must then try to remove; and it can *increase* the number of ranges, slowing the allocator. The art is in *where* to split: at loop boundaries to isolate hot pressure, around calls to isolate call-clobbered segments, and at points where the spill cost of the segment is minimal. Aggressive splitting followed by iterated coalescing [2] is, in effect, a search procedure over the space of range partitions, with coalescing acting as the repair step that undoes splits that proved unnecessary.

## 5 Theoretical Analysis and Empirical Results

### 5.1 Complexity landscape

The theoretical picture is now crisp. General graph-coloring register allocation is *NP*-complete (Chaitin), and even the coalescing subproblem alone is *NP*-hard [7]. Linear scan is *O(n log n)* in the number of intervals and optimal for true interval graphs, but live intervals are an over-approximation, so its output is heuristic [3]. SSA programs induce chordal interference graphs, on which coloring is linear-time optimal and the register demand equals *Maxlive* exactly [4][5]. The remaining *NP*-hard core in SSA allocation is spilling itself — choosing the minimum-cost set of values to spill to bring pressure below *k* — and coalescing under affinities, which Hack and Goos formulate as an integer linear program that is practical only for small functions [5].

### 5.2 Empirical comparisons

Three bodies of evidence anchor the practical trade-offs:

| Allocator family | Compile time | Code quality | Best setting |
|---|---|---|---|
| Chaitin-Briggs + iterated coalescing | Slow (quadratic, iterated) | Highest for static code | GCC/LLVM at -O2 and above |
| Linear scan | Near-linear, fastest | Within ~12% of graph coloring [3] | JITs, debug builds (-O0) |
| SSA-based chordal coloring | Linear coloring + spill phase | Near-optimal, fewer pathological spills | Modern LLVM Greedy allocator lineage |

Smith, Ramsey, and Holloway's generalized allocator study [1] showed that Briggs's optimistic coloring materially reduces actual spills relative to Chaitin's eager spilling, and that the choice of spill heuristic dominates the choice of coloring order in determining final code quality. Poletto and Sarkar's measurements [3] remain the canonical citation for the linear-scan trade-off: several times faster compilation, code within 12% of aggressive graph coloring on all but two benchmarks. On the SSA side, Hack's allocator demonstrated that optimal coloring eliminates an entire class of avoidable spills that heuristic colorers introduce even when pressure permits a valid assignment [5]. Production experience in LLVM confirms the synthesis: the default Greedy allocator is a hybrid — SSA-aware live intervals, priority-driven coloring with live-range splitting and aggressive coalescing — because no pure family wins on all three axes simultaneously.

## 6 Limitations

Despite four decades of progress, hard limitations persist.

1. **Machine irregularity.** Real targets are not *k* identical registers: x86 has register classes, aliasing (al/ax/eax/rax), calling-convention precoloring, and two-address instructions. Every allocator handles these with precolored nodes and constraints, but the elegant theory (chordal optimality, PEO coloring) degrades as constraints multiply [5].
2. **Coalescing versus spilling tension.** Copy elimination and spill minimization are fundamentally opposed — coalescing raises register demand, splitting lowers it at the cost of shuffle code. No allocator jointly optimizes both; iterated coalescing [2] and ILP formulations [5] approximate the joint optimum.
3. **Spill-code placement.** Deciding *where* loads and stores go (inside versus outside loops, rematerialization of cheaply recomputed values) is as important as deciding *what* to spill, and remains heuristic in all production allocators [1].
4. **Phase ordering with instruction scheduling.** Allocation and scheduling interfere: scheduling to reduce pressure constrains allocation, and allocation choices (spills) invalidate schedules. Integrated approaches exist but are not production-standard.
5. **Compile-time ceilings.** Iterated coalescing's quadratic behavior is unacceptable for JITs, which is why the field maintains two allocator lineages rather than one — a permanent tax of the quality-speed trade-off [3].

## 7 Conclusion

Register allocation's history is a sustained argument between model fidelity and computational budget. Chaitin's reduction to graph coloring [1] gave the field its mathematical language; Briggs's conservative coalescing and George-Appel iterated coalescing [2] taught it how to remove copies without breaking colorability; Poletto and Sarkar's linear scan [3] proved that a near-linear approximation suffices where compilation speed dominates; and Hack, Grund, and Goos [4][5] showed that choosing the right program representation — strict SSA — turns the *NP*-complete core into a linear-time optimal coloring on chordal graphs, leaving spilling as the single remaining hard decision. The modern production allocator is therefore not one algorithm but a pipeline: SSA-based live intervals, pressure-driven spilling with live-range splitting, priority coloring along dominance-derived orderings, and aggressive coalescing as repair. The open frontier is joint optimization — of spilling, splitting, coalescing, and scheduling together — where the next structural insight, comparable to chordality, is still waiting to be found.
