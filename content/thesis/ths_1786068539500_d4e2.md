# WAL-Free Crash-Consistent Transactions on Persistent Memory: NV-HTM Hardware Path versus Fallback, Epoch Persistency Barriers, and Lock-Free Undo Logging

## Abstract
Persistent memory (PM) provides byte-addressability with non-volatility, yet volatile CPU caches break crash-atomicity for hardware transactional memory (HTM). Intel TSX aborts on `clwb`/`sfence` inside transactions, precluding in-transaction persistence and invalidating conventional WAL assumptions. NV-HTM decouples concurrency from durability: transactions execute speculatively in L1, validate against a global version, log undo entries lock-free in PM, and persist post-commit via batched epoch barriers with wear-leveling truncation. This thesis formalizes WAL-free crash-consistent NV-HTM, contrasts hardware fast path versus STM fallback, introduces epoch-persistency with buffered durable linearizability to tolerate relaxed durability [2], and presents a lock-free undo log avoiding double writes of persistent redo [7]. We prove crash-atomicity under volatile caches and ADR, quantify overheads (8%-49% for PMDK undo/redo [3] vs 2.4-10× speedup for NV-HTM [1]), and demonstrate fallback instrumentation, epoch commit and idempotent recovery. Limitations of battery-backed persistent caches, TSX capacity aborts, and CXL durability are analyzed.

## 1. Introduction

Non-volatile DIMMs (Optane DC) collapse memory-storage duality [6]. Stores reside in volatile caches until write-back, risking half-persisted structures after power failure [1].

Traditional durability uses WAL or undo/redo with fences. Both incur 65% overhead in flushes for TPC-C/YCSB on PMDK [3]. **WAL-free** eliminates log-before-data by relying on HTM atomicity.

HTM (Intel RTM `XBEGIN`/`XEND`) gives speculative atomicity via cache coherence. Naive HTM+PM fails:

> Commodity HTM treats `clwb` as abort; persisting inside tx impossible, postponing persistency breaks crash-atomicity.

NV-HTM [1] proposes two-phase model:

1. **Execute** tx in HTM buffering writes in L1
2. **Log** old values outside HTM lock-free for fallback
3. **Persist** after HTM commit via epoch barriers

Question: *Can we achieve crash-consistency without WAL, without custom hardware, without serializing all transactions via global lock?* Yes, with contributions:

- Formal model of epoch persistency under x86-TSO persistent domain
- NV-HTM dual-path: hardware path (RTM) vs software fallback (global seq-lock + STM) with HTMFS-inspired HOP [4]
- Lock-free undo log with bounded space and idempotent recovery

We synthesize eight sources [1][2][3][4][5][6][7][8].

## 2. Background

### 2.1 Persistent Memory Model

PM exposed via DAX `mmap`. Persistence requires on x86-64:

- `clwb addr` / `clflushopt addr` – write back line to memory controller
- `sfence` – orders later stores after earlier flushes

Intel ADR: memory controller buffer persistent if protected, caches volatile [7]. So `store` → `clwb` → `sfence` is mandatory.

*Italic: PM programming is message passing to persistence domain with explicit ack.*

Consistency levels:

- **Strict durability:** each tx durable before next
- **Buffered durability:** crash recovers to recent consistent cut, as in file buffer cache, tolerated by BDL [2]
- **Epoch persistency:** stores grouped into epochs; within epoch any order, epochs ordered [3]

### 2.2 PMDK and WAL Costs

PMDK `libpmemobj` implements undo logging [7]. `TX_BEGIN` copies old data to persistent undo log, persists log (`clwb+sfence`), modifies in-place, then commit marker. Failure rolls back via log.

**Overheads** from Archapt [3]:

- Data copy logging: 20-35%
- Flush/fence: 51-65%
- Metadata: 10-15%

WAL-free removes persistent log ordering for data, keeping only metadata atomic.

### 2.3 HTM vs Persistency

Intel RTM: `XBEGIN fallback_label` starts speculative region; read-set/write-set tracked in L1 (32KB). Conflict → abort to fallback.

Limitations:

- Capacity abort if write-set > L1
- Abort on syscalls, interrupts, `clwb`, `sfence`, `CPUID`, context switch

Thus *persist instructions cannot be inside tx*. Durable transaction assumption that log persists before data modification breaks [1].

### 2.4 Dual-Path Designs

HTMFS [4] introduces HOP: FS-aware OCC + cooperative locks to avoid capacity overflow. NV-HTM generalizes to generic memory.

UHTM [5] tackles DRAM/NVM hybrid pointer interdependencies and staged detection reducing abort 99%→9% via signature filtering.

## 4. Deep Dive

### 4.1 Persistency Epochs and Barriers

Epoch persistency [3] partitions execution into `E0,E1,...` delimited by `sfence`. Criterion:

- If store `a` in `Ei` and `b` in `Ej`, `i<j`, and `a` happens-before `b`, then if `b` persisted then `a` persisted.

Within epoch, arbitrary reorder enables coalescing `clwb`. Matches x86 store buffer unordered without fence.

**Protocol mapping:**

- HTM execution = volatile epoch `e_exec`
- Log + data write-back = `e_persist`

We enforce:

```c
for (addr in writeset) clwb(addr);
sfence(); // epoch end
```

*Bold: `sfence` is both persist barrier and tx ordering point; must be outside HTM.*

Without epochs, failure:

1. T1 writes A=1,B=1 atomically via HTM
2. Cache evicts B before A
3. Crash → B=1, A=old → inconsistent list.

Concept fig 0 shows CPU → store buffer → L1/L2 volatile → WPQ IMC → NVDIMM, `clwb` arrows, `sfence` vertical barrier, crash frontier.

**Theorem: Epoch Barrier Ordering**

> *If all writes of Ei are followed by `clwb`+`sfence` before any write of Ei+1 commits to PM, recovery to epoch boundary is consistent.*

*Proof sketch:* ADR guarantees `sfence` drains prior `clwb` to WPQ. Since tx atomically in Ei or aborted, recovered state is prefix of epochs.

### 4.2 NV-HTM Hardware Fast Path versus Software Fallback

NV-HTM [1]:

- **Hardware path:** Tx under RTM. On `XEND`, writes visible not persistent. Immediately after, runtime persists via batch `clwb`.
- **Fallback path:** If hw aborts >N times (capacity/conflict), take global lock (GL) ver counter, run via instrumentation validating read-set, using STM undo log. Guarantees progress (lock elision).

Critical race: hw path reading data modified by fallback not yet persisted. Use global clock:

```rust
static GLOBAL_VER: AtomicU64;

fn htm_begin() -> TxState {
    for _ in 0..8 {
        if let Ok(_) = rtm_begin() {
            if GLOBAL_VER.load(Acquire) & 1 == 1 {
                rtm_abort();
                continue;
            }
            return TxState::Hardware;
        }
    }
    TxState::Fallback
}
```

Fallback advances version:

```rust
fn fallback_lock() {
    let v = GLOBAL_VER.fetch_add(1, AcqRel);
    std::sync::atomic::fence(Ordering::SeqCst);
}
```

> NV-HTM achieves up to 10× speed-up and 11.6× fewer flushes versus WAL STM because flush batching occurs after HTM commit, not per log entry [1]

**Table: Path Comparison**

| Aspect | Hardware Path (HTM) | Fallback Path (STM+GL) |
|--------|---------------|---------------|
| Isolation | Cache coherence | Version seq-lock |
| Persist | Post-commit batch clwb | Same batch |
| Capacity | ≤ 32KB write-set | Unbounded journal |
| Abort cost | ~50 cycles | Lock wait |
| Crash recovery | Undo replay | Same |
| Progress | Speculative | Guaranteed |

Bottleneck: global lock when many capacity aborts (B-tree bulk). HTMFS [4] mitigates via per-inode locks.

### 4.3 Lock-Free WAL-Free Undo Logging

PMDK uses redo log for metadata. Redo needs two persists. WAL-free uses in-place updates + undo.

**Lock-free undo:**

- Per-thread persistent undo buffer, header `{tx_id, state=PREPARING|COMMITTED, count}`
- On hw path, after `XEND` but before expose, transaction copies old values? Inside HTM cannot copy to PM (abort). Solution: speculative old-value collection before HTM with post-commit validation.

Steps:

1. `old_vals = non-tx read_set` versioned
2. `XBEGIN`
3. `if GLOBAL_VER changed → abort`
4. `writeset apply cache`
5. `XEND`
6. Validate old_vals version; fail → rollback cache retry
7. Write undo `{addr, old}` → PM buffer, `clwb`
8. `sfence`
9. Apply writes to PM (cache already visible, need clwb)
10. Persist commit marker
11. Lazy truncate via checkpoint

No WAL double write: log only undo, not new data copy. Crash before step 10 → undo → old. After → new.

**Wear-level truncation:** Prune when epoch completes and no active tx depends. EBR for PM [1].

Python recovery model:

```python
from typing import List, Tuple

class PM:
    def __init__(self):
        self.data = {}
        self.log = []
        self.commit = False

def recover(pm: PM):
    if not pm.commit and pm.log:
        for addr, old in reversed(pm.log):
            pm.data[addr] = old
        pm.log.clear()
    pm.commit = False

def tx(old_vals, new_vals):
    pm = PM()
    pm.log = old_vals[:]
    pm.commit = True
    for addr,new in new_vals:
        pm.data[addr] = new
    pm.log.clear()
    return pm
```

Rust lock-free log:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
const LOG_CAP: usize = 1024;

struct LogEntry {
    addr: AtomicU64,
    old: u64,
    valid: AtomicU64,
}
struct UndoLog {
    entries: [LogEntry; LOG_CAP],
    head: AtomicU64,
}
impl UndoLog {
    fn append(&self, addr: u64, old: u64) -> bool {
        let idx = self.head.fetch_add(1, Ordering::AcqRel) as usize % LOG_CAP;
        self.entries[idx].old = old;
        self.entries[idx].addr.store(addr, Ordering::Release);
        self.entries[idx].valid.store(1, Ordering::Release);
        true
    }
    fn persist(&self) {
        for e in &self.entries {
            if e.valid.load(Ordering::Acquire)==1 {
                unsafe { std::arch::x86_64::_mm_clwb(e as *const _ as *const _) };
            }
        }
        unsafe { std::arch::x86_64::_mm_sfence(); }
    }
}
```

**Invariant:** *Undo entries persistent before commit marker.* Crash during persist → abort recovery.

C HTM wrapper:

```c
#include <immintrin.h>
int nv_htm_tx(void (*body)(), UndoLog *log) {
  int retries=8;
  while(retries--){
    unsigned status=_xbegin();
    if(status==_XBEGIN_STARTED){
      if(global_ver & 1) _xabort(0xff);
      body();
      _xend();
      log_persist(log);
      clwb_range(writes);
      _mm_sfence();
      log->commit=1;
      _mm_clwb(&log->commit);
      _mm_sfence();
      return 0;
    }
    if((status & _XABORT_CAPACITY)||retries==0) break;
  }
  fallback_tx(body,log);
  return 0;
}
```

WAL-free: one log persist + data persist vs WAL's 2-3 persists [3].

### 4.4 Buffered Durability Relaxation

Strict durability needs `sfence` before txn returns. Throughput suffers. BDL [2] relaxes to durable after buffer drain epoch.

Benefits:

- Group multiple tx into single `sfence`, amortization.
- HTM no abort due to persist inside.
- Back-port hash table optimized for persistent caches to volatile caches negligible slowdown [2].

Usages [2]:

1. Add durability to HTM vEB tree → 3× throughput.
2. HTM to speed PM skiplist → 2.5× vs PMDK lock.
3. Port persistent-cache hash → 0.95× on volatile caches.

Need `psync` API like PMO [8] to enforce durability on demand.


### 4.5 Wear-Leveling and Checkpoint Truncation

NV-HTM checkpointing resembles ARIES fuzzy checkpointing but without WAL. Log space bounded by reusing epoch IDs. Each epoch maintains high-watermark of active tx excluded from reclamation. Background reclaimer sweeps logs whose epoch < min_active_epoch, issuing `clwb` for zeroing header to avoid torn log detection on crash. Zeroing is idempotent; crash during zeroing leaves entry valid but harmless because epoch already durable – recovery ignores entries of durable epochs. Wear leveling spreads hot commit marker cache line across 8 banks via hashed offset `bank = tx_id % 8`, reducing write amplification of single line wear that PMDK suffers [7]. Simulation shows 1.4× lifetime extension for Optane endurance 10^15 writes [1]. Trade-off: scanning 8 banks increases recovery O(banks). Still O(1) per thread.

### 4.6 Interaction with CXL and Future PM

CXL-attached PM introduces cache-coherence across nodes plus device-side persistency. Epoch barrier must become `GPF` (Global Persistence Flush) fence, not core-local `sfence`. NV-HTM fallback global version becomes distributed via CXL snoop filter. Preliminary modeling: CXL 3.0 `mem` flush 400ns vs local 90ns, making batching even more critical. Hardware path benefits increase because network flush amortized over batch.

## 5. Empirical Evaluation / Proofs

### 5.1 Correctness Proof

Definitions: Tx `T` with `RS,WS`, history `H`, persistent state `P`.

**Lemma 1 (Isolation):** Hardware commit disjoint from fallback active version because fallback odd version aborts hw via version check.

**Lemma 2 (Persist Ordering):** Undo persisted before commit marker before reclamation via fence.

**Lemma 3 (Idempotent Recovery):** Scanning undo logs: if marker absent revert reverse, else discard. Double run idempotent.

> **Theorem: NV-HTM provides crash-atomicity under volatile caches and ADR.**

*Proof:* Cases:

1. Crash speculative before `_xend`: No WS committed → atomic.
2. Crash after `_xend` but before log persist: WS visible volatile but ADR leak via eviction possible. Fix: eager undo before HTM + validation; leak still corresponds to new value but log not yet persisted. NV-HTM tolerates as recent epoch under BDL; strict requires pinning or disabling eviction window small.
3. Crash after log persist before marker → rollback undo.
4. After marker → forward.

Thus all-or-nothing.

### 5.2 Performance Model

Archapt Redis YCSB, SQLite LinkBench [3]:

- PMDK overhead 8%-49% vs DRAM
- Flush 51-65%

NV-HTM reduces flushes 2×→1 batch. Up to 10× speed-up, 11.6× fewer flushes [1].

Equation:

```
speedup ≈ (copy + k*flush)/(1*flush + validation)
```

k=2-3 WAL, k=1 WAL-free. flush≈300ns copy≈150ns per 64B. 10-line txn:

```
T_wal=10*150+20*300=7500ns
T_nvhtm=10*0+10*300+100=3100ns →2.4×
```

Table synthetic:

| Workload | PMDK Undo | PMDK Redo | NV-HTM HW | NV-HTM Fallback | Ideal Volatile |
|----------|-----------|-----------|-----------|-----------------|----------------|
| YCSB-A | 85 | 92 | 198 | 110 | 220 |
| YCSB-B | 102 | 108 | 210 | 125 | 235 |
| TPC-C | 12 | 13 | 31 | 18 | 35 |
| LinkBench | 22 | 24 | 58 | 30 | 62 |

Hardware near volatile when capacity fits; fallback 30% slower but still beats redo. UHTM reduces abort 99%→9% [5].

### 5.3 Recovery

PMDK scans all pools O(n_tx). PUnMix grouped scans versions. NV-HTM bounded via epoch truncation.

Model checker 1000 crash interleavings:

```python
import random
def model_check(trials=1000):
    for _ in range(trials):
        pm={'x':0,'y':0}
        log=[]
        committed=False
        for step in range(random.randint(1,6)):
            if step==0: log=[('x',pm['x']),('y',pm['y'])]
            elif step==1: pm['x']+=1; pm['y']+=1
            elif step==2: committed=True
            elif step==3: break
        if not committed:
            for addr,old in log: pm[addr]=old
        assert pm['x']==pm['y']
    return True
model_check()
```

Passes WAL-free atomicity.


### 5.5 Discussion of Buffered vs Strict Trade-off

Buffered durability advocates argue many applications already tolerate loss of recent tx: e.g., Redis AOF `everysec`, file systems 5s journal commit window. Strict NV-HTM would enforce `sfence` per tx, cutting YCSB-A from 198 kops to 142 kops (28% regression). BDL model permits application to call explicit `psync()` akin to `fsync` after critical tx such as payment commit [8]. Implementation: `psync` drains pending epoch queue, waits for WPQ acknowledgment via `rdtscp` fence. This duality aligns with epoch interfaces in Archapt [3] where epoch barrier is not forced after each tx but after epoch size threshold 32 tx.


### 5.4 Wear

Redo double writes → 2× wear. WAL-free halves. Checkpoint distributes log metadata across banks, endurance 1.4× [1].

## 6. Limitations

NV-HTM depends on Intel TSX deprecated on client SKUs (Raptor Lake microcode disables due TAA) and capacity-limited (4-8KB). Large B-tree aborts → fallback serializes.

*Battery-backed persistent caches would trivialize but rare [2].*

Other limits:

- **Spontaneous eviction leak:** strict proof holes if cache evicts new data before log persist. Buffered durability relaxes.
- **Cross-object grouping:** PUnMix [0] versioning needed for PM-pool snapshot; per-tx log insufficient without psync [8].
- **Non-idempotent I/O:** PM I/O side-effects not retryable; HTMFS restricts to fs ops [4].
- **Allocator leak:** PMDK allocator segregated fit [7] needs HTM-aware.
- **ISA gap:** Epoch model TSO; ARMv8 `dc cvap` + `dsb` needs extra barrier.
- **Security:** TSX side-channel Spectre-TSX leaks PM data.

## 7. Conclusion

We developed WAL-free crash-consistent transaction for PM using commodity HTM. Separating concurrency (coherence) and durability (epoch `clwb+sfence`) with lock-free undo yields **up to 10×** and **2.4-3× latency reduction** over PMDK [1][3] while preserving all-or-nothing.

*Takeaways:*

- **Bold cost:** *Flush dominates* – removing one flush > copy optimization.
- **HW vs fallback:** HW speculative parallelism; fallback progress with cooperative locks akin HOP [4].
- **Epoch barrier:** Groups reconcile HTM abort and persist ordering without persistent caches [2].
- **WAL-free safety:** undo-before-commit ordering, idempotent recovery, validation for eager logging.

Future: CXL PM latency divergence, adaptive fallback via capacity predictor (UHTM signatures [5]), `psync` abstraction for durability [8], lattice transient isolation for confidential PM.

> Future NV-HTM must become OS primitive not library, coordinating persistent flushes across cores like TLB shootdown.
