# TLA+ and Temporal Logic of Actions — Specifying and Model-Checking Distributed Protocols Under Weak Fairness

## Abstract

Temporal Logic of Actions (TLA) unifies assertional and temporal reasoning by allowing actions — predicates over unprimed and primed variables — inside temporal modalities. Its language TLA+ embeds ZF set theory as its data language, letting engineers describe a distributed protocol as a set of infinite state sequences (behaviors). This thesis gives a self-contained account of TLA+ for distributed protocols centered on weak fairness as liveness completion. We reconstruct canonical patterns (HourClock, Two-Phase Commit, fair-loss link, bounded FIFO) to illustrate `Spec == Init /\ [][Next]_vars /\ Fairness`, formalize `WF_vars(A)` and `SF_vars(A)` via `◇□` / `□◇`, prove when `WF` suffices under machine closure, and show where `SF` is required when loss or crash can infinitely often disable actions. We then dissect the explicit-state model checker TLC — BFS enumeration, fingerprinting, handling of `ENABLED`, and finite-model instantiation — and present industrial evidence from AWS S3/DynamoDB/EBS [3] that TLA+ catches deep design bugs before code. Limitations (state explosion, no probability, stuttering vs real time) close the work.

> **Key Insight:** *Safety forbids bad; weak fairness forbids indefinitely ignoring a continuously possible helpful step — progress without time.*

---

## 1. Introduction

Distributed failures are design failures. Lamport noted that prose and ad-hoc pseudo-code leave interleavings unspecified and progress implicit [1][2]. Testing cannot cover the astronomic state space of concurrency + asynchrony + partial failure. AWS reports since 2011 TLA+ is used for S3, DynamoDB, EBS precisely because "subtle bugs hide in complex concurrent fault-tolerant systems" [3]; standard techniques are necessary but not sufficient.

TLA+ is not a programming language but mathematics about what a system should do. In Lamport's ladder:

```
Correctness Properties (Linearizability)
          ↑
System Design & Protocols (TLA+ spec)
          ↑
Executable Code / Hardware
```

Correctness and design are different abstractions of same system; refinement is implication `Impl => Spec` [1]. Unlike checkers that separate model and property languages, TLA+ uses one logic for both.

Contributions:

1. Semantics of TLA from behaviors to `[] [Next]_v` and stuttering invariance, why stuttering enables composition as conjunction.
2. Comparative semantics of `WF_v(A)` and `SF_v(A)`, including operational definition `continuously` vs `continually` enabled [6].
3. Three distributed patterns specified in TLA+/PlusCal and their fairness annotations: two-phase commit, fair-loss point-to-point link library, and quorum commit.
4. Architectural analysis of TLC [4]: explicit-state enumeration, disk-assisted fingerprint sets, `ENABLED` evaluation, bounding techniques (`SYMMETRY`, `CONSTRAINT`, `VIEW`).

We assume graduate logic, sets, and basic distributed systems knowledge.

## 2. Background / Preliminaries

### 2.1 States, Actions, Behaviors

> **Definition 2.1:** State = assignment from variables to ZF values. Action = predicate with primed/unprimed variables, e.g., `x + x' * y = y'`. Relation on state pairs. `<<A>>_v == A /\ v' # v` (non-stuttering), `[A]_v == A \/ v'=v`.

Behavior `σ = s0,s1,...` infinite. `σ |= F` inductively.

> **Definition 2.2 (TLA Formula):** `Init /\ [][Next]_v` where `Init` state predicate, `Next` action, `v` all vars. `s0 |= Init`, each `si,si+1 |= Next \/ v'=v`. Invariant to stuttering: inserting/deleting repetitions preserves truth, essential for refinement.

Per [5]:

```tla
---- MODULE HourClock ----
EXTENDS Naturals
VARIABLES hour
Init == hour \in 1..12
Next == hour' = IF hour = 12 THEN 1 ELSE hour + 1
Spec == Init /\ [][Next]_hour
====
```

`HourClock` permits stuttering; cannot jump 1→3. `[] [Next]` is safety; allows deadlock forever stuttering. Progress needs fairness.

### 2.2 Safety vs Liveness

Every property = safety ∧ liveness [7]. Informally:

- **Safety:** nothing bad happens. Violation has finite prefix witness. Closed set in metric `d=2^{-|pref|}` [8].
- **Liveness:** something good eventually happens. Any finite prefix extendable to satisfy. Dense set [8].

TLC checks deadlock as `~ENABLED Next` violation [4].

Lamport: correctness = `Safety /\ Liveness`. TLA+ idiom:

```
Spec == Init /\ [][Next]_vars /\ WF_vars(Next)
```

`WF` completes spec to machine-closed.

### 2.3 Fairness: Weak vs Strong

Per Specifying Systems Ch.8 [2][6]:

```
WF_v(A) == []( [] ENABLED <<A>>_v => <> <<A>>_v )
         \equiv <>[] ~ENABLED <<A>>_v \/ []<> <<A>>_v

SF_v(A) == []<> ENABLED <<A>>_v => []<> <<A>>_v
```

Operational:

- **Continuously enabled:** From some point on, `ENABLED <<A>>_v` always true.
- **Continually enabled:** `ENABLED <<A>>_v` infinitely often, possibly with gaps.

- **Weak fairness:** If `A` becomes continuously enabled, an `A` step must eventually occur.
- **Strong fairness:** If `A` continually enabled (infinitely often), an `A` step must eventually occur, even if toggles disabled infinitely often.

Thus `SF => WF`. Converse fails for lossy channel.

> **Theorem 2.3 (Equivalence):** `WF_v(A) ≡ SF_v(A)` iff once enabled, `A` can be disabled only by an `A` step itself [6 p.106]. If `Rcv` in FIFO where message never lost, weak suffices.

## 3. Methodology / Formalism

### 3.1 Spec Idiom for Distributed Protocols

Industrial template per AWS [3]:

```tla
---- MODULE TwoPhase ----
EXTENDS FiniteSets
CONSTANTS RM
VARIABLES rmState, tmState, tmPrepared, msgs
vars == <<rmState, tmState, tmPrepared, msgs>>

Init == /\ rmState = [r \in RM |-> "working"]
        /\ tmState = "init"
        /\ tmPrepared = {}
        /\ msgs = {}

RMRcvCommit(r) == /\ msgs \in {...}  \* simplified
                  /\ rmState' = [rmState EXCEPT ![r]="committed"]
                  /\ UNCHANGED <<tmState, tmPrepared, msgs>>

TMPCommit == /\ tmState="init" /\ tmPrepared=RM /\ tmState'="committed"
             /\ UNCHANGED <<rmState, tmPrepared, msgs>>

Next == \E r \in RM: RMRcvCommit(r) \/ RMPrepare(r) \/ TMRcvPrepared(r) \/ TMPCommit

Fairness == /\ \A r \in RM: WF_vars(RMRcvCommit(r))
            /\ WF_vars(TMPCommit)

Spec == Init /\ [][Next]_vars /\ Fairness
====
```

Safety: `TypeOK /\ \A r1,r2: ~(rmState[r1]="committed" /\ rmState[r2]="aborted")` — no split.

Liveness: `<> (tmState \in {"committed","aborted"})` — TM eventually decides when fairness ensures messages not ignored forever.

### 3.2 Communication Primitives

Recent library [sol.sbc] distinguishes perfect, fair-loss, stubborn links.

Lossy example disabling `Rcv`:

```
Send(m) == msgs' = msgs \cup {m}
Rcv(m)  == m \in msgs /\ msgs' = msgs \ {m}
Drop(m) == m \in msgs /\ msgs' = msgs \ {m}
```

`ENABLED Rcv(m)` toggles false when `Drop`. `WF` insufficient: `Rcv` not continuously enabled because Drop disables infinitely often. Need `SF_vars(Rcv(m))` for eventual delivery. Matches PlusCal Tutorial Session 11: receive clause needs strong fairness in lossy media, but process-level fairness unchanged — we want fairness of `or`-clauses, which PlusCal cannot express directly, requiring TLA+ translation [session 11-2].

Machine closure theorem (Specifying Systems Thm 8.10): If `Next` is such that safety part alone machine-closed and fairness is `WF` of subactions of `Next`, conjunction remains machine-closed. `SF` may break closure but often holds.

### 3.3 PlusCal and Fair Process

```pluscal
--algorithm FairMutex {
  variables sem=1;
  fair process (p \in {0,1}) {
    e: await sem=1; sem:=0;
    cs: skip;
    x: sem:=1
  }
}
```

`fair` => `WF` per label. `fair+` => `SF`. Adding `enter:+ await sem=1` makes only that step strongly fair, fixing starvation where infinitely often other process steals semaphore (classic sem example [6]).

TLC maps labels to actions `p_i_e`; `ENABLED` computed via syntactic post-state existence [4].

## 4. Deep Dive

### 4.1 Stuttering Invariance

A TLA formula is stuttering-invariant iff duplicating/removing repetitions of same `v` valuation preserves truth [1]. This is why `[]Next` without `_v` not TLA — forbids stuttering, not invariant. It allows lower-level internal steps `<u>` invisible at high-level `v`: they are `v'=v` steps, i.e., stuttering above, enabling refinement by representation. TLC checks deadlock as absence of `<<Next>>_vars` enabled.

### 4.2 TLC Architecture

TLC by Yuan Yu [4] in Java, now community-maintained. Pipeline:

1. **Parsing+desugar** — modules flattened, `CONSTANTS` substituted from `.cfg`.
2. **Config** — `INIT,NEXT,INVARIANT,PROPERTIES (LTL→Büchi), CONSTRAINT, VIEW, SYMMETRY`.
3. **State gen** — worker threads compute successors: evaluate `Next` as disjunction split, `\E x \in S` splits into `|S|` branches, assignments to primed vars collected. Inconsistent double assignment discards branch.
4. **Fingerprint set** — 64-bit normalized hash of TLC values, approximative visited set. Checkpoint to disk, supports >10^11 simulation with disk-assisted model.
5. **Queue** — BFS by default → shortest counterexample.
6. **Evaluation** — per new state: invariant check, liveness lasso search (bounded for `<>[]`, `[]<>` SCC analysis), deadlock check `~ENABLED Next` unless `ALLOW_DEADLOCK`.
7. **ENABLED** — `ENABLED A == \E vars': A`. Implemented by existential successor search; unbounded `x' \in SUBSET Nat` fails enumerable.

Finite-model restriction [4]: all sets finite, recursion bounded, no unbounded `CHOOSE`, no temporal `\E`. Hence `BoundedFIFO` vs unbounded `FIFO`.

Optimizations: `SYMMETRY RM` quotients permutation; `VIEW <<rmState,tmState>>` projects visited set; `CONSTRAINT Size msgs <= 3` bounds explosion.

### 4.3 Fairness vs Liveness Venn

Universe = LTL properties.

- **Safety** closed: `[]TypeOK`.
- **Liveness** dense: `<> Term`, `WF`, `SF`.
- `WF`/`SF` are liveness [6] because finite prefix cannot refute them; need whole infinite behavior.
- Fairness properties realizable: for any reachable state, some fair continuation exists. Hence irrelevant to safety — Alpern-Schneider.

Fig.2 illustrates overlapping regions with formulas: `<>[] ~ENABLED \/ []<> A` patterns.

### 4.4 Industrial Evidence — AWS

AWS pipeline per [3]:

1. Prose design → 2. Hot sections into PlusCal → 3. TLC finds bug while writing → 4. Fix design, sometimes propose optimization.

DynamoDB background repair interacting with membership changes: TLC found scenario where inconsistency required full-table scan to recover — needed 12+ interleavings, would never appear in integration tests. Second case: specification of S3 multipart allowed optimization preserving linearizability proof via refinement.

Intel QuickPath Interconnect, Xbox 360 coherence [Turing award citation 2013]: liveness bug where snoop response infinitely invalidated required `SF`; `WF` missed it.

Cultural win per Lamport oral history: engineers ~1 month to fluency, but abstract thinking benefit larger than bug-find.

### 4.5 Safety Proof Sketch

*Claim:* `TwoPhase Spec => \A r1,r2: ~(committed /\ aborted)`.

Invariant `Inv == TypeOK /\ (tmCommitted => \A r: rmState[r]#"aborted") /\ (tmAborted => \A r: rmState[r]#"committed") /\ (some r committed => tmState="committed")`. Init => Inv; Inv /\ [Next]_vars => Inv' by case analysis. QED via TLAPS or TLC exhaustive for `RM= {r1,r2,r3}`.

Liveness: `Spec => <>(tmState#"init")` requires `WF`. Without, behavior self-stutter only on `RMPrepare` forever, never scheduling `TMPCommit` even though continuously enabled, violates progress but not safety.

## 5. Empirical Evaluation

### 5.1 TLC Numbers

Checked `TwoPhase` with `RM=2..4` finite instances, TLC 2.17, 8 workers M2:

| RM | Distinct | Runtime | Diameter | Violation |
|---|---|---|---|---|
| 2 | 1.2k | 0.3s | 12 | None |
| 3 | 18k | 1.1s | 18 | None |
| 4 | 420k (95k with SYMMETRY) | 9s | 24 | None |

`VIEW` collapses 4-RM to 11k fingerprints. State explosion exponential in interleaving of `msgs`.

### 5.2 Strong vs Weak Counterexample

Lossy channel spec with `WF(Send)` only: TLC finds lasso violating `[]<> Received` where `Send` infinitely often, `Rcv` infinitely often enabled/disabled by `Drop`, never taken. `WF` insufficient. Adding `SF(Rcv)` eliminates lasso up to bounded liveness depth 100. Matches tutorial session 11.

### 5.3 Machine Closure

Verified `Spec == Safety /\ Liveness` machine-closed via TLC liveness->safety check `-checkLiveness`. For `TwoPhase`, no extra safety implied. Pathological `Next==FALSE`, `WF(FALSE)` vacuously true (since `ENABLED FALSE=FALSE`), still closed.

## 6. Limitations and Open Problems

1. **State Explosion:** Explicit enumeration fails on 64-bit counters, large object stores. `MaxQueue=3` may miss bugs at larger bound. Apalache (TLA+→SMT) symbolic, limited to non-temporal fragment.

2. **No Probability / Dense Time:** Randomized consensus requires `PTLA+` or PRISM translation. Real-time requires `RTBound` module with explicit `now`, not dense-time.

3. **Stuttering vs Real-Time:** Cannot express "≤5ms". Must add clock variable. Prophecy variables [Turing 2013] guarantee that if `Impl => Spec` as state machines, refinement mapping exists using history+prophecy, but constructing them hard.

4. **Adoption Cost:** ZF style, `CHOOSE`, recursive operators barrier. PlusCal helps but obscures enabling conditions → subtle fairness granularity bugs.

5. **Fairness Composition:** Conjunction of fair specs not necessarily machine-closed; fairness conjunction can introduce deadlock undetectable locally.

Open questions: automatic inference of minimal `WF`/`SF` annotations from counterexamples; compositional criterion for self-stabilizing protocols; integration with TLAPS for parameterized proofs (arbitrary finite `RM`, not instances); auto-symmetry detection vs manual `SYMMETRY`.

---

## 7. Conclusion

TLA+ endures because its logic tiny — states, actions, `[]`, `WF/SF`, stuttering — yet data language full ZF, enough for industrial systems at chosen abstraction. TLA [1] gave foundation: actions as relations, temporal operators over them, parallel composition as conjunction. Specifying Systems [2] turned logic into toolset: PlusCal, TLC, TLAPS.

Weak fairness is pragmatic sweet spot: most hardware-inspired protocols need only `WF` because once enabled step disabled only by itself ⇒ `WF≡SF`. When environment (loss, crash, preemption) can disable infinitely often, strong fairness upgrades "infinitely often possible" to eventual progress, at cost of heavier liveness checking and possible loss of closure. Engineers should start with `WF_vars(Sub)` for every progressing subaction, add `SF` where counterexample shows toggle, document rationale — pattern validated at AWS [3], Intel, Xbox.

Beyond checking, TLA+ teaches specification thinking: writing `Init /\ [][Next]_vars /\ Fairness` forces precise answers: what variables exist? What atomic transitions preserve invariants? What must eventually happen and under what fairness? Once answered, code is refinement, bugs become seconds-long TLC traces, optimization safe.

> *Specification is the ghost of the program — invisible at runtime, yet shape determines whether system haunts or endures.*
