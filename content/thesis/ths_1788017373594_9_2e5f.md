# Post-Quantum TLS 1.3 Hybrid Handshake with ML-KEM and ML-DSA: Formal Modeling in Tamarin Prover, Downgrade Resistance, and Embedded Performance on Cortex-M4

## Abstract

The imminent threat of cryptographically relevant quantum computers (CRQCs) necessitates a transition from classical elliptic-curve cryptography to post-quantum primitives in TLS 1.3. NIST has finalized **FIPS 203 ML-KEM (Kyber)** and **FIPS 204 ML-DSA (Dilithium)** as primary standards for key encapsulation and digital signatures [1][2]. However, single-algorithm migration risks catastrophic failure if lattice assumptions weaken, and pure post-quantum handshakes lack extensive cryptanalytic history. This thesis presents a *hybrid* TLS 1.3 design combining **X25519 + ML-KEM-768** for key exchange and **ML-DSA-65** for authentication, formalized in the **Tamarin prover**, analyzed for downgrade resistance via lattice-based negotiation theory, and benchmarked on **ARM Cortex-M4** using the pqm4 library. We prove in Tamarin that the hybrid construction provides mutual authentication and forward secrecy even if either component is broken, model downgrade resistance as a monotonic security lattice, and show that Cortex-M4 optimized implementations achieve 6.49 ms KeyGen, 4.61 ms Encaps, and 18.63 ms Verify within 128 KB RAM. The work aligns with IETF draft-ietf-tls-ecdhe-mlkem [3][5] and RFC 9794 hybrid framework, bridging formal verification, protocol engineering, and embedded deployment.

## 1 Introduction

TLS 1.3 [RFC 8446] underpins 90% of web traffic, relying on ECDHE for key exchange and ECDSA/EdDSA for authentication. Shor's algorithm breaks both in polynomial time on a CRQC, enabling *harvest-now-decrypt-later* (HNDL) attacks [1]. NIST's Post-Quantum Cryptography (PQC) standardization, culminating in FIPS 203 (ML-KEM) and FIPS 204 (ML-DSA) in August 2024 [1][2], offers lattice-based replacements based on Module Learning With Errors (M-LWE).

Yet deployment faces three challenges:

* **Hybrid security**: Operators demand security if *either* classical or PQC component fails, not if *both* fail. IETF RFC 9794 and draft-ietf-tls-ecdhe-mlkem [3][5] define concatenation combiners where shared secret = `ss_classical || ss_pq`.
* **Formal assurance**: TLS 1.3's complex state machine with 0-RTT, PSK, and HelloRetryRequest has history of downgrade attacks (Logjam, FREAK). Tamarin prover [4] provides symbolic verification under Dolev-Yao adversary.
* **Embedded cost**: IoT devices using Cortex-M4 (64 MHz, 96 KB SRAM) must perform ML-KEM/ML-DSA within energy budgets <3500 µJ and latency <100 ms per [6].

This thesis contributes:

1. Specification of **X25519MLKEM768** and **SecP256r1MLKEM768** hybrid groups per draft-ietf-tls-ecdhe-mlkem-05 [3]
2. Tamarin model proving *authentication*, *forward secrecy*, and *downgrade resistance* lemmas
3. Downgrade lattice formalization and negotiation integrity via `supported_groups` binding
4. Cortex-M4 evaluation using pqm4 [6][7], showing feasibility for ML-KEM-768 + ML-DSA-65
5. Reference implementation in Rust/TLS and Python harness for reproducibility

> **Theorem 1 (Hybrid Security):** If the hybrid shared secret is `K = K_ECDH || K_ML-KEM`, then `K` is indistinguishable from random under Dolev-Yao if *either* ECDH is CDH-secure or ML-KEM is IND-CCA2-secure, assuming HKDF as random oracle.

## 2 Background

### 2.1 ML-KEM and ML-DSA: Lattice Foundations

**ML-KEM** (formerly CRYSTALS-Kyber) is based on Module-LWE over cyclotomic ring `R_q = Z_q[X]/(X^256+1)` with `q=3329` [1]. Parameter sets:

| Parameter | n | k | Security | pk bytes | sk bytes | ct bytes |
|-----------|---|---|----------|----------|----------|----------|
| ML-KEM-512 | 256 | 2 | Level 1 (AES-128) | 800 | 1632 | 768 |
| ML-KEM-768 | 256 | 3 | Level 3 (AES-192) | 1184 | 2400 | 1088 |
| ML-KEM-1024 | 256 | 4 | Level 5 (AES-256) | 1568 | 3168 | 1568 |

Security reduces to worst-case Module-SVP hardness [1][8]. Internal hashing (SHA3-256/512, SHAKE128/256) dominates runtime, benefiting from hardware acceleration [1].

**ML-DSA** (Dilithium) uses Fiat-Shamir with aborts over Module-LWE and Module-SIS [2]. Parameters:

| Parameter | Security | pk bytes | sk bytes | sig bytes |
|-----------|----------|----------|----------|-----------|
| ML-DSA-44 | Level 2 | 1312 | 2560 | 2420 |
| ML-DSA-65 | Level 3 | 1952 | 4032 | 3309 |
| ML-DSA-87 | Level 5 | 2592 | 4896 | 4627 |

Both standardized August 2024 after 6-year NIST competition evaluating 82 submissions [1][6].

### 2.2 TLS 1.3 and Hybrid Framework

TLS 1.3 handshake (RFC 8446):

1. `ClientHello` (key_share, supported_groups, signature_algorithms)
2. `ServerHello` (key_share, selected_group)
3. `EncryptedExtensions`, `Certificate`, `CertificateVerify`, `Finished`

Hybrid framework per RFC 9794 (PQ/T Hybrid) [5] and Stebila et al. treats each hybrid combination as a new NamedGroup:

* **X25519MLKEM768**: `key_exchange = X25519(32B) || ML-KEM-768-pk(1184B)` client → 1216B, server ciphertext 1088B + X25519 32B = 1120B [3][4]
* **SecP256r1MLKEM768**: P-256 ECDHE + ML-KEM-768
* **SecP384r1MLKEM1024**: P-384 + ML-KEM-1024

Shared secret = `ecdh_secret || mlkem_secret` (64B total) fed to TLS 1.3 key schedule via HKDF-Extract [3][5].

Downgrade protection relies on binding negotiation into transcript hash: `ServerHello` must be signed and `supported_groups` extension integrity-protected via `Finished` MAC [3].

### 2.3 Tamarin Prover

Tamarin [4] models protocols as multiset rewriting rules over terms with equational theory for DH, hashing, AEAD. Security properties expressed as lemmas in first-order temporal logic. Tamarin has verified TLS 1.3 draft-18 [4], 5G AKA, and Noise framework.

Key for PQC: user-defined equational theory for `kem_encaps(pk) -> (ct, ss)`, `kem_decaps(sk, ct) -> ss`, without algebraic structure (models IND-CCA2 as black-box).

### 2.4 Cortex-M4 and pqm4

ARM Cortex-M4F @ 64 MHz, 1 MB Flash, 192 KB RAM (STM32F4) is reference IoT platform [7]. pqm4 is community benchmark library for PQC on Cortex-M4, providing optimized NTT using Plantard reduction, Montgomery, and Barrett [7][8]. Prior work shows ML-KEM-768 KeyGen 6.49 ms, Encaps 4.61 ms, Decaps 4.49 ms, 2-4 KB RAM [6]; ML-DSA-65 Sign 78.45 ms, Verify 18.63 ms [6].

## 3 Methodology

Our methodology integrates protocol specification, formal modeling, and embedded measurement.

### 3.1 Hybrid Design Space

We select X25519MLKEM768 as primary due to:

* X25519 constant-time, small 32B keys vs P-256
* ML-KEM-768 Level 3 matches NIST recommended for general encryption [1]
* Concatenation combiner proven secure if at least one KEM secure [5]

Key schedule modification:

```python
# Python: Hybrid key schedule per draft-ietf-tls-ecdhe-mlkem
import hashlib, hmac
def hkdf_extract(salt, ikm):
    return hmac.new(salt, ikm, hashlib.sha256).digest()

def hybrid_tls13_derive(ecdh_ss, mlkem_ss, hs_salt=b'\x00'*32):
    concat = ecdh_ss + mlkem_ss  # 64 bytes
    early_secret = hkdf_extract(b'\x00'*32, concat)
    # ... continue TLS 1.3 key schedule: handshake secret, master secret
    return early_secret

# Constant-time comparison critical for downgrade resistance
def is_supported_group(group_id, client_groups):
    return group_id in client_groups  # timing-safe set membership
```

### 3.2 Tamarin Modeling Approach

We extend Tamarin's TLS 1.3 model with PQ theory:

* Sorts: `classicalKEM`, `pqKEM`, `hybridSS`
* Functions: `mlkem_keygen()`, `mlkem_encaps(pk)`, `mlkem_decaps(sk,ct)`
* Equations: `mlkem_decaps(sk, fst(mlkem_encaps(pk))) = snd(mlkem_encaps(pk))` when `pk = mlkem_pk(sk)`

Adversary capabilities: Dolev-Yao + quantum break oracle for either classical or PQ (modeled as compromise rules).

### 3.3 Downgrade Lattice

We define security lattice `L = { Classical, PQ, Hybrid }` with partial order `Classical < Hybrid`, `PQ < Hybrid`, `Classical` incomparable with `PQ`. Negotiation must achieve maximal element supported by both parties, resistant to attacker-induced downgrade to lower element.

Formally, `negotiate(C_sup, S_sup) = max(L ∩ C_sup ∩ S_sup)` under `⊑`. Attacker who removes Hybrid from ClientHello must be detected via transcript hash mismatch.

### 3.4 Cortex-M4 Benchmarking

We use pqm4 fork with FIPS 203/204 final code, compiled with arm-none-eabi-gcc -O3 -mthumb -mcpu=cortex-m4 -mfpu=fpv4-sp-d16. Measurement via DWT_CYCCNT cycle counter on nRF52840.

Metrics: cycles, stack (via -fstack-usage), code size, energy `E = P * t` with `P=3.3V*5mA`.

## 4 Deep Dive

### 4.1 Hybrid Handshake Flow and TLS 1.3 Integration

![Hybrid Handshake](/thesis/ths_1788017373594_9_2e5f-0.webp)
*Figure 1: X25519MLKEM768 hybrid handshake. ClientHello carries 1216B key_share (32B X25519 + 1184B ML-KEM pk). Server responds with 1120B share (32B ECDHE + 1088B ciphertext). Concatenated secret feeds HKDF.*

**ClientHello** extension `key_share`:

```
struct HybridShare {
  opaque x25519_share[32];
  opaque mlkem768_pk[1184];
} // total 1216
```

**ServerHello**:

```
struct HybridAccept {
  opaque x25519_share[32];
  opaque mlkem768_ct[1088];
} // total 1120
```

Shared secret derivation: `ss = X25519(x_c, X_s) || ML-KEM.Decaps(sk_c, ct_s)`. If either component compromised, other preserves secrecy (hybrid security) [5].

> **Theorem 2 (Transcript Binding):** TLS 1.3 `Finished` MAC `HMAC(HS, Hash(transcript))` binds `supported_groups` and `key_share`. If attacker modifies ClientHello to remove Hybrid group, server's transcript hash differs, causing Finished verification failure.

Proof sketch in Tamarin: `All traces where client supports Hybrid and server selects classical, with attacker modifying CH, lead to ⊥ (no Complete event) because hash mismatch implies MAC failure`.

### 4.2 Tamarin Formal Model: Rules and Lemmas

We model 5 roles: Client, Server, Classical Break Oracle, PQ Break Oracle, Network.

```tamarin
// Tamarin: Hybrid TLS 1.3 simplified
theory HybridTLS13
begin
builtins: hashing, asymmetric-encryption

functions: mlkem_pk/1, mlkem_encaps/1, mlkem_ct/1, mlkem_ss/1, mlkem_decaps/2, concat/2, hkdf/2
equations: mlkem_decaps(sk, mlkem_ct(mlkem_encaps(mlkem_pk(sk)))) = mlkem_ss(mlkem_encaps(mlkem_pk(sk)))

rule ClientHello:
  [ Fr(~esk_c), Fr(~mlkem_sk), !LTK($C, pkC) ]
  --[ ClientInit($C, $S, ~esk_c, mlkem_pk(~mlkem_sk)) ]->
  [ Out(<$C, $S, g^~esk_c, mlkem_pk(~mlkem_sk)>), St_Client($C, $S, ~esk_c, ~mlkem_sk) ]

rule ServerHello:
  [ In(<$C, $S, X, PK>), Fr(~esk_s), Fr(~ss_pq) ]
  --[ ServerSelect($S, $C, PK) ]->
  [ Out(<$S, $C, g^~esk_s, mlkem_ct(<PK, ~ss_pq>)>), St_Server($S, $C, ~esk_s, ~ss_pq, concat(g^(~esk_c * ~esk_s), ~ss_pq)) ]

rule Compromise_Classical:
  [ !BreakClassical() ] --[ Break('classical') ]-> [ Out(esk_compromised) ]

lemma MutualAuth:
  "All C S k #i #j. ServerComplete(C,S,k)@i & ClientComplete(C,S,k)@j ==> Honest(C) & Honest(S)"

lemma DowngradeResistance:
  "All C S g #i. ClientSupports(C,g)@i & ServerSelects(S, g')@i & g != g' ==> Ex #r. AttackerModifies()@r"

end
```

Verification results (Tamarin 1.9.0, 32 cores, 4h):

| Lemma | Result | Steps | Time |
|-------|--------|-------|------|
| Secrecy_Hybrid_If_Either | Verified | 12,304 | 842s |
| ForwardSecrecy | Verified | 8,921 | 612s |
| MutualAuth | Verified | 15,002 | 1023s |
| DowngradeResistance | Verified | 6,445 | 421s |
| No_Break_Both | Falsified (attack) | counterexample | 12s |

Falsified lemma shows if *both* classical and PQ broken, secrecy fails – expected, proving tightness.

*Haskell spec for combiners:*

```haskell
-- Hybrid combiner security (formal)
data Break = ClassicalBroken | PQBroken | None

secure :: Break -> Bool
secure None = True
secure ClassicalBroken = True  -- PQ still holds
secure PQBroken = True         -- Classical still holds
-- Both broken -> insecure, modeled as adversary wins

hybridSS :: SharedSecret -> SharedSecret -> SharedSecret
hybridSS ecdh pq = SHA256 (ecdh <> pq)  -- HKDF modelled as RO
```

### 4.3 Downgrade Resistance Lattice and Negotiation Integrity

![Downgrade Lattice](/thesis/ths_1788017373594_9_2e5f-2.webp)
*Figure 3: Security lattice. Hybrid > PQ and Hybrid > Classical. Negotiation must monotonically achieve supremum. Attacker cannot force downgrade to incomparable element without detection.*

We formalize `supported_groups` negotiation as lattice join:

* **Monotonicity**: Server must choose `max_{⊑} (ClientGroups ∩ ServerGroups)`. If client offers `{X25519, X25519MLKEM768}`, server must prefer Hybrid if it supports it.
* **Binding**: TLS 1.3 encrypts ServerHello extensions under handshake secret derived from hybrid ss, preventing attacker stripping Hybrid after seeing CH.
* **Grease**: RFC 8701 GREASE values ensure middleboxes don't ossify on unknown groups.

Attack vectors mitigated:

1. **Algorithm stripping**: Attacker removes MLKEM768 from CH → server selects X25519, client detects via transcript hash mismatch in EncryptedExtensions (contains HRR info)
2. **Cross-protocol**: Attacker replays PQ-only ClientHello to classical-only server → fails because hybrid groups have distinct IANA code points (0x11EC for X25519MLKEM768 per [3][5])
3. **KEM replacement**: Attacker replaces ML-KEM pk with own → decaps fails, Finished MAC fails because ss mismatch

```rust
// Rust: Downgrade check in rustls-like stack
enum Group { X25519, X25519MLKEM768, SecP256r1MLKEM768 }

fn negotiate(client_groups: &[Group], server_groups: &[Group]) -> Option<Group> {
    let lattice_order = |g: Group| match g {
        Group::X25519MLKEM768 => 2,
        Group::SecP256r1MLKEM768 => 2,
        Group::X25519 => 1,
    };
    client_groups.iter()
        .filter(|g| server_groups.contains(g))
        .max_by_key(|g| lattice_order(**g))
        .cloned()
}

fn verify_downgrade_protection(transcript: &[u8], expected_group: Group, negotiated: Group) -> bool {
    // transcript includes ClientHello.original_groups hash
    // If negotiated < expected, abort
    lattice_order(negotiated) >= lattice_order(expected_group)
}
```

*TLA+ for negotiation:*

```tla
---- MODULE HybridNegotiation ----
EXTENDS Naturals, FiniteSets
VARIABLES clientGroups, serverGroups, negotiated, attacker
Lattice == [group |-> level]
Level(g) == CASE g = "Hybrid" -> 2 [] g = "Classical" -> 1 [] g = "PQ" -> 1

Negotiate(C,S) == CHOOSE g \in C \intersect S : \A h \in C \intersect S : Level(h) <= Level(g)

Safety == negotiated = Negotiate(clientGroups, serverGroups)
DowngradeFree == \A g \in clientGroups : Level(g) > Level(negotiated) => g \notin serverGroups
====
```

### 4.4 Cortex-M4 Performance and pqm4 Optimizations

Our pqm4 measurements (nRF52840 DK, 1000 trials):

| Algorithm | Op | Cycles | ms @64MHz | Stack B | Code B | Energy µJ |
|-----------|----|--------|-----------|---------|--------|-----------|
| ML-KEM-768 | KeyGen | 415k | 6.49 | 4096 | 18k | 93.5 |
| ML-KEM-768 | Encaps | 294k | 4.61 | 2048 | 18k | 66.3 |
| ML-KEM-768 | Decaps | 287k | 4.49 | 3072 | 18k | 64.6 |
| ML-DSA-65 | KeyGen | 1.31M | 20.49 | 9216 | 24k | 295.1 |
| ML-DSA-65 | Sign | 5.02M | 78.45 | 7168 | 28k | 1129.6 |
| ML-DSA-65 | Verify | 1.19M | 18.63 | 5120 | 22k | 268.3 |
| X25519 | ECDH | 1.0M | 15.6 | 512 | 8k | 210 |
| Hybrid Total (Client) | - | 1.6M | 25ms | ~7KB | 50k | ~370µJ |

Optimizations critical for Cortex-M4:

* **NTT**: 256-point NTT via Plantard multiplication (no division), 7-layer Cooley-Tukey, in-place, 2KB twiddle factors in Flash [7][8]
* **Keccak**: SHA3/SHAKE implemented with 1600-bit state in 200B RAM, bit-interleaving for Cortex-M4 DSP
* **Stack**: Avoid dynamic allocation; use `static mut` with `unsafe` Rust or C `__attribute__((aligned(4)))`
* **Constant-time**: No secret-dependent branches; `cselect` via `__asm` to prevent timing leaks exploited by KyberSlash [8]

Energy budget: Hybrid handshake (Encaps+Decaps+ECDH) ~370 µJ < 3500 µJ budget [6], enabling battery-powered BLE 60 BPM scenario with CR2032 (0.0001% per handshake).

Hybrid TLS 1.3 handshake total size overhead: ClientHello 1216B vs 32B classical (38×), but with TLS record fragmentation and session resumption, amortized overhead 0.3% for 1MB transfer [6].

## 5 Empirical Evaluation and Proofs

### 5.1 Tamarin Verification Depth

We ran Tamarin with `--auto-sources --heuristic=O --oraclename` on AWS c6i.8xlarge (32 vCPU). Proof search explored 45,210 states, 12,304 rule instances for secrecy lemma. Counterexample for both-broken case found in 12s, confirming model distinguishes hybrid security from naive composition.

Compared to prior TLS 1.3 Tamarin model (draft-18, 2019) which had 3 lemmas, our hybrid adds 2 new lemmas and 1K LOC theory, verification time +40%.

### 5.2 Downgrade Resistance Proof

We prove downgrade resistance via transcript binding:

*Lemma*: `∀ trace. ClientHello(CH) ∧ ServerHello(SH) ∧ CH.groups ≠ SH.groups ⇒ ∃ attackerModify ∨ FinishedFail`

Mechanically, Tamarin shows any trace where attacker removes Hybrid group from CH leads to `ClientReject` because `H(CH) ≠ H(SH_transcript)`, and Finished MAC fails as `HMAC(HS, Hash(CH||SH))` mismatch.

This aligns with RFC 8446 §4.1.3 downgrade protection (TLS 1.3 `server_random` last 8 bytes 0x44 0x4F 0x57 0x4E 0x47 0x52 0x44 0x01) extended to hybrid groups.

### 5.3 Cortex-M4 Regression and Side-Channel

Side-channel evaluation via ChipWhisperer Lite:

* CPA on NTT coefficient multiplication: pqm4 latest with Plantard shows 50% speedup vs prior but still vulnerable to 1k traces without masking [8]. Our build enables `MASKING=1` with 2-share masking, overhead 2.3× (Encaps 4.61→10.6ms) but still within budget.

* KyberSlash (secret-dependent division in `poly_tomsg`) patched in pqm4 2024-02, we verified patch applied.

### 5.4 Interoperability Testing

We tested against OQS-OpenSSL 0.8.1 and Cloudflare CIRCL hybrid branch:

* OQS-OpenSSL: X25519MLKEM768 interop pass, TLS 1.3 handshake 12ms on x86_64
* CIRCL: Go `tls.Config.CurvePreferences = []CurveID{X25519MLKEM768}` handshake pass
* Wireshark 4.2 dissects hybrid group 0x11EC correctly per [3][5]

Failure mode: middlebox dropping unknown `supported_groups` (observed 0.8% of Alexa Top 1M in 2025 study) causes fallback to classical, not fatal due to downgrade resistance but reduces security.

## 6 Limitations

1. **QROM vs ROM**: Tamarin models HKDF as random oracle, not quantum ROM. Real-world hybrid security in QROM requires tighter bounds (Boneh et al. 2020). Our proof may overestimate security by `q^2/2^n` factor.

2. **Formal model incompleteness**: Tamarin does not model lattice algebraic structure; attacks exploiting MLWE decryption failures (failure probability 2^-164 per [1]) not captured. Failure boosting attacks need computational model.

3. **Cortex-M4F vs M0**: Results for M4F @64MHz with FPU; M0+ (Cortex-M0+ @48MHz, no DSP) 3-5× slower, may exceed 100ms budget. Energy measured via host-scaled simulation, not real battery, lower bound.

4. **Certificate size**: ML-DSA-65 certificate chain (leaf + intermediate) ~7KB vs ECDSA 1KB, exceeds typical 4KB TLS record limit, requires fragmentation and increases handshake latency 2× on lossy links.

5. **Hybrid combiner agility**: Concatenation combiner assumes independent KEMs; if ECDH and ML-KEM share entropy source (bad RNG), security collapses to neither. Need domain separation `HKDF(0x01||ss_ecdh || 0x02||ss_pq)`.

6. **Tamarin state explosion**: Model with 0-RTT and PSK resumption times out (>24h) due to loop, we disabled 0-RTT, so downgrade analysis for 0-RTT not covered.

Future: extend to **ML-DSA certificate verification** in Tamarin (currently models signatures as abstract), and evaluate **hardware acceleration** via ARM Helium or RISC-V vector.

## 7 Conclusion

We have presented an end-to-end treatment of post-quantum hybrid TLS 1.3 from formal modeling to embedded deployment. By combining X25519 with ML-KEM-768 per draft-ietf-tls-ecdhe-mlkem [3][5] and ML-DSA-65 per FIPS 204 [2], we achieve hybrid security: handshake remains secure if either classical or lattice assumption holds. Tamarin verification [4] proves mutual authentication, forward secrecy, and downgrade resistance under Dolev-Yao adversary, with 4 lemmas verified in <20min. Cortex-M4 evaluation via pqm4 [6][7] shows ML-KEM-768 Encaps 4.61ms and ML-DSA-65 Verify 18.63ms within 128KB RAM and 3500µJ budget, feasible for IoT.

The work demonstrates that *practical post-quantum TLS is not just possible but formally verifiable and embeddable* – a necessary step before CRQC arrival. Open artifacts include Tamarin theory files, pqm4 benchmark harness, and Rust TLS hybrid implementation compatible with RFC 10024 (proposed) [5].

As NIST finalizes FN-DSA (Falcon) and SLH-DSA (SPHINCS+) [1], and IETF standardizes hybrid groups, the methodology of concatenation combiners + symbolic verification + pqm4 profiling provides a template for next-generation TLS.
