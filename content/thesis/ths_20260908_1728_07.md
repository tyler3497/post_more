# Post-Link Code Layout as a Compilation Stage: BOLT's Binary Rewriting, Propeller's Basic-Block Sections, and AutoFDO's Sampling Profiles in the LLVM Pipeline

## Abstract

Large warehouse-scale binaries routinely exceed the reach of the instruction cache and the instruction TLB, yet modern compilers cannot place code optimally: aggressive inlining, link-time optimization, and multi-million-line codebases defeat compile-time layout heuristics. This thesis studies three mechanisms that reintroduce precise execution profiles *late* in the toolchain: BOLT, a post-link binary rewriter that disassembles ELF binaries, reconstructs control-flow graphs, and emits an entirely new layout; Propeller, a relinking optimizer replacing monolithic rewriting with per-basic-block sections and a linker symbol-ordering pass; and AutoFDO, a sampling-based feedback-directed optimization converting hardware counter samples into source-annotated profiles without instrumentation. We analyze their shared dependence on `perf`-style sampling, their divergent trade-offs between rewriting and relinking, and the algorithmic core of profile-driven layout — hot/cold splitting, hierarchical function reordering, and extended traveling-salesman block ordering — with quantitative evidence from the primary literature. The synthesis shows late profile injection is a principled architectural response to the information loss incurred by inlining and modular compilation [1][2][3][4].

## 1 Introduction

The dominant cost in large server software is *instruction supply*. A data-center binary — a PHP VM, a load balancer, a C++ compiler — spans tens of megabytes of code, while the L1 instruction cache stays at 32–64 KB and has barely doubled in two decades [7]. When the hot working set exceeds these structures, i-cache misses, i-TLB misses, and mispredictions dominate, and no backend optimization recovers the loss. Code layout — *which bytes sit adjacent in the address space* — is therefore a first-order performance determinant, and profile information is the only reliable guide [6].

Classical compilers address layout at compile time: basic-block chaining places frequently-taken successors contiguously, and function ordering groups hot callers with hot callees. But three modern developments erode compile-time layout. First, *inlining* relocates code across function boundaries, so a profile recorded against one address maps to many source locations with conflicting optimal layouts. Second, *modular compilation and separate linking* mean the compiler never sees the whole program when it decides order. Third, *stale or absent profiles* force layout decisions on heuristics rather than measurements. Instrumentation-based PGO mitigates some of this, but instrumented binaries run 5–10× slower and are operationally infeasible for production fleets [3].

The response of the last decade has been to push profile consumption *later*: into the linker, or past it into a post-link step.

1. **BOLT** (*Binary Optimization and Layout Tool*), developed at Meta and merged into LLVM in 2022, disassembles a linked ELF binary, rebuilds CFGs from `perf` samples, and emits a new binary [1][5].
2. **Propeller**, developed at Google (ASPLOS 2023), achieves BOLT-like whole-program block layout without disassembly: the compiler emits each basic block in its own section, and the linker orders sections from a profile-derived ordering file [4].
3. **AutoFDO**, Google's automatic feedback-directed optimization, closes the loop at the source level: it converts PMU samples into profiles GCC and LLVM consume via `-fauto-profile`, enabling sampling-based PGO with none of instrumentation's overhead [3].

This thesis unifies the three mechanisms into one framework — *late profile injection* — asking what information must survive from execution to layout, what each architecture (rewrite vs. relink vs. recompile) gains and forfeits, and what the empirical record says about their effectiveness alone and in the two-stage pipelines (AutoFDO→BOLT, AutoFDO→Propeller) deployed at hyperscale.

> The central claim: code layout is a whole-program optimization whose optimal input — the executed binary's CFG with measured edge frequencies — exists only *after* linking. Earlier decisions use less information, and the measured 5–35% deltas are the price of that gap.

## 2 Background

### 2.1 Why layout matters: the frontend bottleneck

A modern out-of-order core retires several instructions per cycle only if the frontend delivers them. Frontend stalls come from three layout-sensitive phenomena: *i-cache misses* when the stream leaves the cached 32–64 KB window; *i-TLB misses* when it leaves the mapped instruction pages; *branch mispredictions* that flush speculative work. Placing hot blocks contiguously shrinks the cache footprint, packing hot functions into few pages shrinks the TLB footprint, and making the likely successor the fall-through improves prediction [6][2]. Pettis and Hansen's 1990 work established the two-level decomposition still used today [6]: *basic-block chaining* within functions and *procedure positioning* across functions, isolating cold code. Every system in this thesis refines this decomposition under different information and engineering constraints.

### 2.2 The information problem: inlining destroys profiles

The BOLT paper's motivating example states why *late* matters [1]. Consider `foo` with one conditional branch, inlined into `bar` (true-branch hot) and `baz` (false-branch hot). A binary-level profile records two branches with opposite biases — the context-sensitive truth. Mapped to source lines, they merge into one "50/50" branch no compiler can lay out correctly for both copies. Post-link optimizers observe the final, fully-inlined binary and see the true per-instance biases [1].

### 2.3 Sampling versus instrumentation

All three systems consume *sampled* profiles, typically from Linux `perf` with precise event-based sampling and Last Branch Records. Sampling trades accuracy for practicality: profiles come from production binaries at negligible overhead. The cost is *skid*, *shadowing*, and aggregation noise; BOLT's aggregation lifts sample accuracy from ~84% to above 92% [1]. AutoFDO's key contribution is the *discriminator*: debug info assigns distinct discriminator values when statements share a line, so samples map to the correct extended source location [3]. LLVM's `llvm-profgen` performs the same conversion for Propeller [4].

### 2.4 Historical predecessors

Late profile injection has deep roots. *iSpike* was a post-link optimizer for Itanium; *HFSort* performed link-time function reordering from call-graph profiles; *PLTO* and *LIPO* explored link-time and lightweight IPO. Newell and Pupyrev note that AutoFDO, iSpike, PLTO, HFSort, and BOLT each deliver roughly 5–15% depending on workload and microarchitecture [2]. What distinguishes the modern trio is deployment scale, LLVM integration, and — for Propeller — a deliberate redesign for distributed build systems.

## 3 Methodology

### 3.1 Analytical framework

We compare the three systems on five axes: (i) *injection stage* (compile, link, post-link); (ii) *profile representation* (source gcov, binary clusters, reconstructed CFGs); (iii) *layout mechanism* (recompilation, relinking, rewriting); (iv) *engineering cost* (build invasiveness, memory/time, toolchain coupling); (v) *measured effect* (reported speedups). Evidence comes from peer-reviewed publications, upstream documentation, and vendor production reports.

### 3.2 Reconstructing the layout problem as executable analysis

To make the algorithmic core concrete, we formalize the block-ordering objective that BOLT's `ext-tsp` pass and Propeller's clusterer both approximate, with a reference Python solver. Let $G = (V, E)$ be the CFG with edge weights $w(u,v)$ and block sizes $s(v)$. A layout is a permutation $\pi$; the *linear distance* between blocks is $d_\pi(u,v) = |\mathrm{pos}_\pi(u) - \mathrm{pos}_\pi(v)|$. The extended-TSP objective [2]:

$$F(\pi) = \sum_{(u,v) \in E} w(u,v)\cdot \phi(d_\pi(u,v)) - \lambda \sum_{v \in V} s(v)\cdot \kappa(\mathrm{pos}_\pi(v))$$

where $\phi$ rewards small distances (fall-through receives maximal weight) and $\kappa$ penalizes displacement of large, rarely-executed blocks into hot regions. The following reference implementation computes this objective and applies a greedy hot-path chaining heuristic of the Pettis–Hansen family [6], demonstrating how profile data drives the combinatorial decision:

```python
from collections import defaultdict

def layout_objective(order, succ, weight, size, lam=0.1):
    """Extended-TSP-style objective for a block permutation [2]."""
    pos = {b: i for i, b in enumerate(order)}
    def falloff(d):
        return 1.0 / d if d > 0 else 0.0  # fall-through scores 1.0
    edge_term = sum(w * falloff(abs(pos[u] - pos[v]))
                    for (u, v), w in weight.items())
    cold_term = lam * sum(size[b] * pos[b] / len(order) for b in order)
    return edge_term - cold_term

def greedy_hot_chain(entry, succ, weight):
    """Pettis-Hansen chaining: follow the hottest unplaced successor;
    restart at the hottest unplaced block [6]."""
    placed, order = set(), []
    def hottest_unplaced():
        return max((b for b in succ if b not in placed),
                   key=lambda b: sum(weight.get((p, b), 0)
                                     for p in succ), default=None)
    cur = entry
    while len(placed) < len(succ):
        if cur is None or cur in placed:
            cur = hottest_unplaced()
            if cur is None:
                break
        placed.add(cur); order.append(cur)
        nxt = [v for v in succ.get(cur, []) if v not in placed]
        cur = max(nxt, key=lambda v: weight.get((cur, v), 0),
                  default=None)
    return order

# Example: diamond CFG A -> {B, C} -> D with hot path A-B-D
succ   = {'A': ['B', 'C'], 'B': ['D'], 'C': ['D'], 'D': []}
weight = {('A', 'B'): 900, ('A', 'C'): 100,
          ('B', 'D'): 900, ('C', 'D'): 100}
size   = {b: 32 for b in succ}
print(greedy_hot_chain('A', succ, weight))  # ['A', 'B', 'D', 'C']
```

Running this on production CFGs with millions of edges is what BOLT's `-reorder-blocks=ext-tsp` and Propeller's clusterer do at scale [1][2][4]; the greedy heuristic is the pedagogical kernel of both.

## 4 Deep Dive

### 4.1 BOLT: disassembly-driven binary rewriting

BOLT treats the linked binary as the compilation unit. Its pipeline has four stages [1][5].

**Profile collection.** The production binary runs under `perf record -e cycles:u -j any,u`, capturing LBR stacks at low overhead. BOLT's `perf2bolt` converts samples into a YAML profile of address execution counts and branch outcomes — the *edge* frequencies layout algorithms need.

**Disassembly and CFG reconstruction.** BOLT disassembles every function with LLVM's disassembler and rebuilds CFGs, recovering jump tables by pattern-matching compiler idioms. Indirect branches and hand-written assembly can defeat reconstruction, so BOLT requires an unstripped symbol table and, for maximum fidelity, `--emit-relocs` at link time [1].

**Optimization passes.** On the reconstructed CFGs, BOLT runs a selectable pipeline:

- `-reorder-blocks=ext-tsp` — extended traveling-salesman block ordering, generalizing Pettis–Hansen chaining with learned i-cache/i-TLB trade-offs [2];
- `-reorder-functions=hfsort+` — hierarchical function sorting by call-graph affinity;
- `-split-functions` / `-split-all-cold` — outline cold blocks into distant `.text.cold`;
- `-icf=1` — binary-level identical code folding;
- plus peepholes: shrink-wrapping and indirect-call promotion from sampled targets [1].

**Emission.** BOLT writes a new ELF, rewriting relocations, exception tables, and debug info — a drop-in replacement binary; no rebuild, no relink, no source access required.

The performance record is striking because BOLT applies *on top of* already-optimized binaries: up to **8.0%** on Meta data-center workloads over PGO+LTO+function reordering; up to **15.3%** on Clang/GCC with FDO+LTO; up to **35.5%** without FDO/LTO [1]. The lesson: even whole-program LTO with profiles leaves a large layout gap, because the compiler decides layout before final address assignment and before all inlining resolves.

The cost is monolithicism: one process disassembles, optimizes, and rewrites the whole binary, with superlinear memory/time growth. This motivated *Lightning BOLT* (2021: lite mode, parallel passes, lower peak memory [5]) and, more radically, Propeller.

### 4.2 Propeller: layout as a linker concern via basic-block sections

Propeller's founding observation is that *the linker already performs layout* — it concatenates input sections into output sections in a specified order. If the compiler places each basic block in its own section, any profile-demanded block ordering becomes a section order, and the linker — already incremental and distributed-build friendly — performs the optimization [4].

The workflow has four stages:

1. **Labels build.** Compile with `-fbasic-block-sections=labels -funique-internal-linkage-names`: each block gets a stable label; internal names are uniquified for profile precision [4].
2. **Profile and cluster.** Run under `perf`; `create_llvm_prof --format=propeller` emits `cluster.txt` (labels → contiguity clusters) and `symorder.txt` (linker section order).
3. **Propeller build.** Recompile with `-fbasic-block-sections=list=cluster.txt`; link with `-Wl,--symbol-ordering-file=symorder.txt -fuse-ld=lld` [4].
4. **Relink at will.** Layout lives in the link step — re-optimizing for a new profile is a relink: incremental, cacheable, distributable.

The algorithmic core is *whole-program basic-block layout*: Propeller's clusterer places blocks across function boundaries in one pass, so splitting and hot/cold partitioning emerge from a single objective [4].

Empirically, Propeller matches BOLT on large applications and SPEC at roughly **20% of BOLT's memory and time** [4]. Its deeper advantage is build-system compatibility: no disassembler, no CFG reconstruction, no monolithic rewrite — the optimization composes with ThinLTO and distributed compilation because it *is* compilation, deferred. Google's 2025–2026 proposal to upstream Propeller into LLVM and enable AutoFDO+Propeller for the Linux kernel reports **5–10%** on kernel microbenchmarks and ~5% on warehouse benchmarks [8].

The trade is expressiveness. A linker reorders sections but cannot rewrite instructions: BOLT's peephole passes (shrink-wrapping, ICF, branch simplification) have no Propeller equivalent, and the labels build roughly doubles object-file section counts, perturbing the profiled binary. The rustc community's evaluation of the Propeller proposal notes that Propeller's memory claim concerns peak single-machine usage in the distributed scenario, not total cluster memory — scalability claims must be read with their experimental setup attached.

### 4.3 AutoFDO: sampling profiles for the compiler itself

AutoFDO answers a different question: *what if the profile never needs instrumentation?* Its pipeline converts binary-level PMU samples into a source-level profile the compiler consumes like any FDO input [3]:

1. **Sample.** `perf record` on the production binary, sampling `br_inst_retired.near_taken` or cycles.
2. **Lift.** `create_gcov` (GCC) or `llvm-profgen` (LLVM) walks debug info, mapping each sampled address to an *extended source location* — file, line, column, **discriminator**. The discriminator is AutoFDO's central invention: a per-basic-block tag so blocks sharing one source line get distinct profile keys [3].
3. **Annotate.** Samples aggregate into a gcov (`-fauto-profile`) or extended-binary (`-fprofile-sample-use`) profile; existing FDO machinery — inlining, unrolling, block placement — consumes it unchanged.

The result: ~**10% faster** binaries on average, approaching instrumented-FDO quality at negligible profiling overhead [3]. Operationally significant is profile *longevity*: six-month-stale profiles retain roughly half their benefit, since extended source locations survive local edits better than raw addresses [3].

AutoFDO's fundamental limitation is the one BOLT was built to escape: the profile is consumed *before* inlining and linking, so context-sensitive layout truths are averaged away. Hence the modern two-stage pipeline — AutoFDO first, to guide inlining and mid-level optimization, then a *second* profile of the resulting binary feeding BOLT or Propeller for final layout [1][4].

### 4.4 The layout algorithms: chaining, splitting, and the extended TSP

All three systems solve variants of one combinatorial problem.

*Basic-block chaining* (Pettis–Hansen [6]) remains the workhorse: sort blocks by execution count, then repeatedly merge the hottest block with its hottest successor/predecessor into fall-through hot paths. It is linear-time, profile-robust, and still the default in GCC and LLVM backends.

*Function splitting and hot/cold partitioning* shrink the hot working set: cold blocks and unlikely functions move to distant pages, saving cache lines and TLB entries. BOLT's `-split-all-cold` and Propeller's cold clusters implement this [1][4].

*Extended TSP* (Newell–Pupyrev [2]) generalizes chaining with the distance-sensitive objective of §3.2 plus i-cache/i-TLB terms — and, distinctively, *learns* the trade-off weights by black-box optimization over a workload corpus. Learned parameters transfer across binaries and beat pure fall-through maximization on Meta's HHVM, Multifeed, Proxygen fleets and on Clang [2]: optimal layout depends on undocumented cache details, so the weights are better *fit* than derived.

## 5 Empirical Results

### 5.1 Headline numbers

| System | Workload | Baseline | Reported gain | Metric |
|---|---|---|---|---|
| BOLT [1] | HHVM, Multifeed, Proxygen (Meta fleets) | PGO + LTO + function reordering | up to **8.0%** | CPU utilization / throughput |
| BOLT [1] | Clang 7, GCC 8.2 | FDO + LTO | up to **15.3%** | workload runtime |
| BOLT [1] | Clang 7, GCC 8.2 | no FDO, no LTO | up to **35.5%** | workload runtime |
| ext-TSP in BOLT [2] | HHVM, Clang, SPEC CPU2006 | BOLT with classic chaining | positive on all; largest on large-footprint binaries | CPU utilization / score |
| AutoFDO [3] | Google warehouse binaries | non-FDO `-O2/-O3` | ~**10%** average | benchmark runtime |
| Propeller [4] | large apps + SPEC CPU | BOLT-optimized equivalent | parity at **~20%** of BOLT's time/memory | runtime; build resources |
| AutoFDO + Propeller [8] | Linux kernel | Clang baseline | **5–10%** microbench; ~5% warehouse | benchmark runtime |

Two patterns stand out. *Gains stack*: PGO, LTO, then post-link layout each add percent-level improvements, because each stage sees information earlier stages destroyed or never had. *Footprint predicts benefit*: the largest wins accrue to the most frontend-bound binaries — compilers, VMs, load balancers — while tight compute kernels see little.

### 5.2 A formal statement of the hardness

> Theorem: The maximum fall-through block-ordering problem — given a control-flow graph $G=(V,E)$ with edge weights $w$ and seeking a permutation $\pi$ of $V$ maximizing $\sum_{(u,v)\in E} w(u,v)\cdot\mathbf{1}[\mathrm{pos}_\pi(v)=\mathrm{pos}_\pi(u)+1]$ — is NP-hard, by reduction from the maximum traveling-salesman problem on the weighted CFG digraph.

*Proof sketch.* On complete digraphs with arbitrary weights (realizable as branch-heavy dispatchers) the objective coincides with asymmetric Max-TSP tour weight, which is NP-hard. The ext-TSP objective [2] generalizes this and inherits the hardness. ∎

The practical consequence is that every production system uses heuristics — chaining, hierarchical sorting, learned-weight local search — and the research frontier is better *models* of the hardware cost [2] rather than exact solvers.

### 5.3 Why the two-stage pipeline wins

The BOLT paper's artifact evaluation makes compositionality explicit: one profile pass is insufficient, because the first profile guides inlining (changing what the second observes); only the second profile, on the linked binary, captures the true executed layout [1]. The pipeline: fleet sampling → AutoFDO for inliner/loop opts → rebuild → fleet sampling → Propeller relink (or BOLT rewrite) [3][4][8]. Each stage profiles the artifact the *next* stage consumes, eliminating single-shot PGO staleness.

## 6 Limitations

**Profile fidelity ceilings.** Sampling is lossy: skid misattributes samples near branches, short-lived processes yield sparse profiles, and multi-tenant noise pollutes attribution. BOLT's aggregation lifts accuracy from ~84% to ~93% [1], but residual error makes layout decisions on lukewarm edges statistically fragile — the dominant operational risk in practice.

**Representativeness and staleness.** A profile is a snapshot of one workload mix; binaries tuned to it can regress on others. AutoFDO's discriminator-keyed profiles degrade gracefully [3], but BOLT's address-anchored profiles are brittle across rebuilds — hence continuous re-profiling rather than one-shot optimization.

**Correctness hazards of rewriting.** BOLT's disassembly must be perfect: misidentified jump tables or unrecognized indirect branches produce miscompilations. The `--emit-relocs` requirement and symbol-table dependence reflect this fragility [1]. Propeller sidesteps the hazard class entirely by never disassembling [4].

**Diminishing returns on small binaries.** Layout optimization taxes frontend-bound programs; binaries whose hot code fits in L1i gain nothing. The 35.5% BOLT figure [1] is against unoptimized baselines — layout matters most where the compiler was given the least help.

**Toolchain coupling.** AutoFDO needs discriminators and debug info; Propeller needs backend section support and LLD's `--symbol-ordering-file`; BOLT needs ELF, specific ISAs, relocation metadata. Composing all three multiplies the pipeline's moving parts.

---

## 7 Conclusion

BOLT, Propeller, and AutoFDO answer one question: *where in the toolchain should measured behavior re-enter compilation?* AutoFDO: "at the source," converting fleet samples into compiler-grade profiles without instrumentation (~10% on warehouse binaries [3]). Propeller: "at the link," making the linker a whole-program layout engine via basic-block sections, matching BOLT at a fifth of the cost [4]. BOLT: "after everything," disassembling the final binary to recover the ground-truth CFG, extracting up to 8% beyond the best compiler-only pipelines — 35% where the compiler was unaided [1].

Their convergence on a *two-stage* deployment — sample-based FDO for mid-level optimization, then a second profile driving link- or post-link layout — suggests the field has settled on an architecture: inject profiles at every representation boundary where information is otherwise lost, each stage profiling the artifact the next stage consumes. Open problems remain: learned layout models transferring across microarchitectures [2], profile formats surviving code motion, upstreaming Propeller into LLVM [8]. The shift is durable: code layout is now a standing, profile-driven compilation stage, and binaries that ignore it pay a measurable, permanent tax on every cycle they execute.
