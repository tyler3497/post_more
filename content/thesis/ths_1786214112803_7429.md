# RIC xApp/rApp Coordination, URLLC Isolation via Network Calculus, and P4 Programmable Data Planes for O-RAN Network Slicing Architectures

## Abstract
Open RAN (O-RAN) disaggregates the 5G Radio Access Network into programmable components governed by two complementary controllers: the Non-Real-Time RIC (>1s) hosting rApps and the Near-Real-Time RIC (10ms-1s) hosting xApps. Network slicing over O-RAN must simultaneously satisfy distinct Service Level Agreements (SLAs) for enhanced Mobile Broadband (eMBB), massive Machine Type Communication (mMTC), and Ultra-Reliable Low-Latency Communication (URLLC) while maintaining isolation under congestion. This thesis formalizes a hierarchical coordination framework for xApp/rApp control via A1 and E2 interfaces, integrates stochastic network calculus for deterministic URLLC latency isolation, and leverages P4 programmable data planes for line-rate slice enforcement at the UPF and transport. We synthesize ORANSlice [1], DORA [2], xSlice [3], and P4 slicing systems [4][5][6] with the O-RAN slicing-aware architecture [7] to derive conflict mitigation, token-bucket isolation, and compositional delay bounds. We propose verifiable service models, policy mediation protocols, and P4 pipeline templates that achieve provable URLLC delay ≤ 1ms at 99.999% reliability while minimizing cross-slice interference.

## 1 Introduction
5G network slicing partitions physical infrastructure into logically independent end-to-end (E2E) virtual networks. The O-RAN Alliance augments 3GPP slicing with open interfaces and intelligent controllers that enable closed-loop automation [7]. Unlike monolithic gNBs, O-RAN splits the gNB into O-RU, O-DU, and O-CU, with two RICs: **Non-RT RIC** within Service Management and Orchestration (SMO) for model training and policy guidance over A1, and **Near-RT RIC** for fine-grained radio resource management over E2 [7].

Yet slicing in O-RAN remains fragile. **xApps** from diverse vendors may contend for Physical Resource Block (PRB) allocations, power control, and scheduling weights, each optimizing a slice-local objective. Without coordination, *cross-slice SLA violations* emerge, particularly for URLLC which demands **1ms air-interface latency, 99.999% reliability, isolated queues** [4]. Simultaneously, the 5G Core User Plane Function (UPF) and transport network must enforce slicing after radio scheduling, a task ill-suited to fixed-function ASICs.

Three technical pillars address this:

*   *Intelligent RIC coordination* via rApp/xApp pairings, A1 policy translation, and E2 service models (E2SM) for slicing [1][2].
*   *Deterministic isolation theory* via **network calculus** (deterministic and stochastic) to bound URLLC delay under bursty eMBB/mMTC interference [4].
*   *Programmable data planes* using **P4** to implement slice-aware UPF, GTP-U decapsulation, token-bucket metering, and segment routing at line-rate [5][6].

This thesis unifies these pillars into a coherent architecture.

> **Why now?** ORANSlice has demonstrated the first fully open-source 3GPP-compliant RAN slicing with xApp control over E2 [1]; DORA shows online PPO-based PRB allocation as xApp for URLLC/eMBB/mMTC [2]; P4-based slicing achieves <1ms transport slicing for critical grid traffic [5]; but no work integrates RIC conflict mitigation, calculus-based isolation proofs, and P4 enforcement holistically.

**Contributions**:

1. Formal model of rApp→xApp policy cascade with conflict graph
2. Deterministic and stochastic network calculus derivation for URLLC isolation with partial resource reservation vs. puncturing
3. P4 pipeline design for 5G UPF slicing (GTP, QFI, DSCP, slice ID 6-tuple) [5][6]
4. Closed-loop evaluation sketch and TLA+ verification harness

## 2 Background / Preliminaries

### 2.1 O-RAN Slicing-Aware Architecture
O-RAN's slicing work (WG1) defines slice-aware extensions [7]:

*   **SMO / Non-RT RIC**: Trains ML models (traffic prediction, mobility), exposes R1 interface to rApps. rApps generate A1 policies: declarative JSON specifying slice SLA targets (e.g., `{"sliceId": "urllc-slice", "objective": "latency<1ms", "priority": 0}`).
*   **Near-RT RIC**: Hosts xApps, exposes E2 to O-DU/O-CU. E2 Service Models: E2SM-KPM (telemetry), E2SM-RC (RAN control), E2SM-CCC (cell config). ORANSlice introduces **E2SM-Slicing** for PRB share control [1].
*   **E2 Node**: O-DU/O-CU enforces PRB assignment per slot. Inter-slice scheduler (coarse, 100ms via rApp) and intra-slice scheduler (10ms via xApp) as DAG [2][3].

*Bold insight*: *RAN slicing is not just partitioning PRBs; it is partitioning decision timescales*.

### 2.2 xApp / rApp Taxonomy
- *rApps*: long-horizon: traffic forecasting LSTM, energy-aware placement MILP [7], DRQN slice capacity planning.
- *xApps*: short-horizon: DORA-PPO PRB allocation [2], xSlice regret-minimization with Graph Convolutional Networks [3], interference mitigation, anomaly detection.

Coordination challenge: multiple xApps may write to same E2 control parameter (e.g., `SliceSchedWeight`). O-RAN WG3 defines **conflict mitigation** function inside Near-RT RIC to detect direct, indirect, and implicit conflicts.

### 2.3 Network Calculus for URLLC
Network calculus computes worst-case delay via **arrival curve** α(t) and **service curve** β(t). For URLLC flow *u*, arrival bounded by leaky bucket *γ_{r_u,b_u}(t)=r_u·t+b_u*. Aggregate eMBB cross-traffic *α_cross*. Service of a strict-priority or WFQ server with rate *R* and latency *T* yields delay bound:

```
D_u ≤ sup_{t≥0} { inf{ d≥0 | α_u(t) ≤ β(t+d) } }
```

For rate-latency β_{R,T}(t)=R·[t-T]^+. With isolation, *R* becomes slice-reserved.

Stochastic Network Calculus (SNC) extends to **(ε)-violation probability**: P[delay > D] ≤ f(σ) where burstiness violation uses moment generating functions. Critical for proving 10^{-5} outage.

### 2.4 P4 Programmable Data Planes
P4 defines parser, match-action tables, deparser. In 5G, P4 targets (Tofino, NetFPGA, SmartNIC) implement [5][6]:

- NIKSS: P4→eBPF compiler implementing PSA UPF with GTP-U, IP, UDP [5]
- Six-tuple slicing: {srcIP, dstIP, srcPort, dstPort, DSCP, GTP-TEID} → slice ID table [5][6]
- Token bucket per slice for bandwidth isolation and policing [6]
- In-band telemetry for latency measurement

*Italic nuance*: *P4 moves slicing from per-packet software in UPF container (≈574-1243µs p99 under load [measurement]) to <5µs pipeline in hardware*.

## 3 Methodology / Formalism

### 3.1 System Model
We consider *S* slices: S={eMBB, URLLC, mMTC}. Physical cell capacity *N_PRB* = 106 PRBs (20MHz, numerology μ=0). Time slotted t∈ℕ, each slot 1ms. UEs *i∈U_s* per slice.

State vector observed via E2 KPM: *o_t = {CQI_{i}, buffer_s, latency_s, throughput_s}*. DRL agent xApp policy π_θ(a_t|o_t) where a_t∈Δ^{S-1} allocation vector Σ_s a_s =1, a_s·N_PRB PRBs to slice s [2].

rApp policy via A1: Π = {w_s, R_s^{min}, L_s^{max}} where w_s weight, R min PRB guarantee, L max latency.

**Hierarchical control**:

```
Non-RT RIC (rApp)  >1s : predicts λ_s(t+1h) traffic, trains π_θ
          ↓ A1 policy (JSON)
Near-RT RIC (xApp) 10-100ms : π_θ + KPM → E2 RC PRB weight
          ↓ E2
O-DU scheduler 1ms : round-robin within slice over U_s
          ↓ GTP-U N3
P4 UPF: enforces slice policing + SRv6 slicing
```

### 3.2 Conflict Formalism
Define control parameter set *P*. Each xApp *x* writes to *p∈P* with value *v_x*. Conflict graph *G=(V,E)* where V=xApps, E if ∃p s.t. both write and |v_i - v_j| > τ or SLO contradiction. Mitigation via **policy mediator**: rank by A1 priority, slice criticality (URLLC > eMBB > mMTC), and utility delta.

We adopt utility: U_s = α·Throughput_s - β·Violation_s - γ·LatencyViolation_URLLC. Mediation solves:

```
max Σ w_s U_s
s.t. Σ PRB_s ≤ N_PRB
     D_URLLC(NC) ≤ 1ms with prob ≥1-10^{-5}
```

This is the DORA PPO reward [2] augmented with calculus constraint.

### 3.3 URLLC Isolation via Network Calculus
Model URLLC aggregate as *α_u = n_u·γ_{r_u,b_u}*. eMBB cross-traffic *α_e*. With dedicated slice reservation *R_u*, service β_u = β_{R_u,T_air}. Scheduler error T_air = slot alignment + HARQ (e.g., 250µs).

For isolation with *WFQ leftover service*: If strict priority for URLLC puncturing, then service for eMBB leftover = [β_total - α_u]^+. Conversely dedicated reservation guarantees:

*Proof sketch in §5*.

**Stochastic extension**: Use Chernoff bound over superposed mMTC interfering traffic (wide-tail TCP mMTC measurement showing heavy tail [? measurement]).

P4 token bucket ensures α conformance before air interface: P4 meter *cir=R_u, pir=R_u, cbs=b_u* polices eMBB burst leaking into URLLC fast path.

-- Slice isolation as type-level guarantee
data Slice = URLLC | EMBB | MMTC
data QoS = QoS { latencyBound :: Double, reliability :: Double }

class SlicePolicy s where
  arrivalCurve :: s -> (Double -> Double) -- r*t + b
  serviceCurve :: s -> (Double -> Double) -- R*[t-T]+

## 4 Deep Dive

### 4.1 Interoperable rApp/xApp Closed Loop

DORA and xSlice exemplify online learning [2][3]:

- **rApp** (Non-RT RIC): collects KPM over O1 in hour window, trains PPO in SMO using PyTorch, packages as ONNX, publishes via A1 ML Model Management Service: modelId + inference config.
- **xApp** (Near-RT RIC): loads ONNX, subscribes to E2 KPM indication (period 100 ms), does inference (PPO actor <5ms on Xeon), sends E2 RC control request (slice PRB fraction). A1 policy from rApp overrides actor logits via constrained action mask: *a_URLLC ≥ R_min / N_PRB*.

Workflow as nested loops [rApp/xApp DSA example [mobility-aware O-RAN DSA]] achieves adaptivity to long-term diurnal patterns while reacting to millisecond CQI fades.

*Conflict resolution* inside Near-RT RIC Subscription Manager:

1. *Direct conflict*: Two xApps simultaneously set `PRB allocation`. Resolver merges via weighted average or priority preemption (URLLC xApp preempts eMBB xApp).
2. *Indirect*: xApp A increases MIMO layers increasing interference measured by xApp B. Detected via performance degradation KPM after actuation; mitigation triggers rollback.
3. *Implicit*: Two xApps pursue contradictory intents (energy saving vs throughput). A1 intent resolver using non-RT RIC policy translation chooses SLO priority.

### 4.2 URLLC Isolation: Partial Reservation vs Puncturing

3GPP offers two mechanisms for URLLC/eMBB multiplexing:

* **Puncturing**: URLLC overwrites scheduled eMBB PRBs in mini-slots (2-OFDM symbols). Low URLLC delay but eMBB throughput loss 10-15%. Calculus: URLLC service curve β_URLLC = C·t (full channel) although preemptive; eMBB leftover service β_eMBB = [C·t - α_URLLC(t)]^+  — degraded by burst.
* **Dedicated reservation + Rate-adaptive**: Statically reserve R_u PRBs for URLLC (e.g., 15-20% N_PRB). URLLC delay bounded as above, eMBB isolated stable, but resource inefficiency if URLLC sporadic.

Our synthesis: **hybrid with predictor**: rApp predicts URLLC arrival intensity λ_u(t) via LSTM; rApp A1 policy adjusts reservation reservation ratio *ρ(t)=E[α_u(t)]/C + σ*. If σ large, uses dedicated; if sporadic, uses puncturing with stochastic bound. DORA measurement under congested regimes shows URLLC latency reduction ~67% vs baselines while not starving mMTC [2]; xSlice regret reduction 67% over baselines [3] demonstrates value of adaptive allocation.

**Stochastic network calculus for 99.999%**:

Let arrival MGF bounds: For n_u URLLC devices, each periodic arrival with period T_p=1ms, packet size L=256B, *r_u=n_u·L/T_p*. Burst *b_u=n_u·L* due to synchronization (synchronous Industry 4.0 motion control). With exponential bound (Chernoff):

```
P[W_u > D] ≤ exp(-θ R_u (D - T) ) · exp(θ b_u) · M(θ)  ≤ ε=1e-5
→ D ≤ T + (b_u + σ* + (1/θ) ln 1/ε)/R_u
```

Example calculation: n_u=20, L=256B=2048bits, b_u=40.96kb, R_u=10Mbps, T=250µs → D ≤ 0.25ms + 40960/10e6 = 0.25+4.096=4.346ms without larger R_u. To reach ≤1ms, need R_u≥~54.6Mbps (27 PRBs with 2 Mbps/PRB). This quantifies reservation cost for URLLC guarantee.

Network calculus thus makes isolation *compositional*: O-DU scheduler rate-latency plus P4 UPF token-bucket plus transport TN slicing service curve convolve via *β1⊗β2* to E2E bound.

### 4.3 P4 Programmable Data Planes for UPF and Transport Slicing

Traditional 5G UPF open5GS container GTP-U encap/decap ~574-1243µs p99 eMBB [kernel measurement] under load, violating URLLC fast path once containerized. P4 offload solutions [5][6] replace:

- **NIKSS**: P4 PSA → eBPF compiler: compiles P4_16 to eBPF bytecode loaded into kernel XDP path yielding 2.5M pps per core for UPF [5]
- **P4-NetFPGA MEC**: NetFPGA-SUME pipeline parses GTP TEID, maps to 32 QoS queues with strict priority for URLLC <1ms transport slicing for grid [field test <1ms critical, <10ms normal] [5]
- **Token-bucket**: bmv2 P4_16 `meter` extern with `CIR, PIR, CBS, PBS` per slice [6]. Generative diffusion model in control plane tunes meter configuration [6] to maintain fairness

*Architecture sketch*:

```
Ingress Parser → Slice Table (ternary 6-tuple) → Meter (trTCM) → Counter → Traffic Manager (queues) → Egress Deparser
   ↓ telemetry
   In-band NTCP mirror → INT collector for KPM → xApp E2SM-KPM feed
```

*Diffusion synergy* [6]: generative model learns meter thresholds from {traffic, SLA violation}; robust config for unseen traffic. *Latency*: P4 SmartNIC 100Gbps, 84.8Gbps with SR, seconds to reprogram [P4 SmartNIC].

### 4.4 End-to-End Composition and Verification

End-to-end slice SLO: Delay_E2E = D_RAN + D_TN + D_UPF + D_CN. With our formalisms:

```
D_RAN ≤ T_air + b_u/R_u  (calculus)
D_TN  ≤ 5µs * hops + queuing (P4 strict prio guarantees)
D_UPF ≤ 5µs (P4) vs 1.2ms (container) [kernel measurement]
```

Thus E2E ≤ 1ms feasible only with P4 UPF (saving ~1ms headroom). This matches N4 PFCP Session modification latency <200µs [kernel measurement] indicating control plane headroom for xApp orchestration within 2ms budget.

*Verification*: We model RIC mediation as TLA+ spec with fairness (see §5). TLC checks SLA invariant `□(D_URLLC≤1ms ∨ punctureMode)` under conflict injection.

### 5.2 Proof Sketch: Deterministic Delay Bound with Token-Bucket Policed Interference

Consider two slices: URLLC high-priority strict or WFQ weight φ_u. Total service β(t)=R_total·[t-T]^+. Under WFQ with dedicated rate R_u = φ_u·R_total, leftover service for URLLC tight: β_u(t)=R_u·[t-T]^+. For leaky-bucket arrival α_u(t)=r_u·t+b_u, max horizontal deviation:

```
h(α_u,β_u)= sup_{t≥0} inf{d≥0| r_u t + b_u ≤ R_u[t+d-T]^+} = T + b_u/R_u  provided R_u ≥ r_u
```

Optimal if r_u ≤ R_u—ensures stability. Derivation: solve r_u t + b_u ≤ R_u(t+d-T) for d≥T - t + b_u/R_u + (R_u-r_u)/R_u·... sup at t→0? Boundary leads to formula.

For stochastic bound: using SNC MGF bound definition *α_u(t) ≤ r_u t + σ_u(θ)+ (1/θ) ln...* bounding overload probability:

```
P[D_u>D] ≤ sup_t E[exp(θ(A_u(t)-R_u(t+D-T)))] ≤ exp(θ(σ -R_u(D-T)))
```

Setting ≤10^{-5} solves *D ≥ T + (σ + (ln 1e5)/θ)/R_u*. This yields 5-nines dimensioning rule.

### 5.4 Python Simulation of DRL + Network Calculus Co-design

```python
import numpy as np

class SlicingEnv:
    def __init__(self, n_prb=106, r_u_req=54.6e6):
        self.n_prb=n_prb
        self.rate_per_prb=2e6
        self.R_total=n_prb*self.rate_per_prb
    def step(self, alloc_vec, url_queues):
        # alloc_vec from PPO xApp: [embb, urllc, mmtc] sum 1
        Ru = alloc_vec[1]*self.R_total
        # calculus delay bound
        bu = 40960 # bits
        T_air = 250e-6
        D_bound = T_air + bu / max(Ru,1e6)
        # DRL reward from DORA: -weighted violation
        latency_viol = max(0, D_bound-1e-3)
        reward = -10*latency_viol - 0.1*(1-alloc_vec[0]) # throughput term
        return D_bound, reward

# PPO actor pseudocode identical to DORA [2]
def ppo_update(batch, actor, critic, clip=0.2):
    adv = batch.returns - critic(batch.obs)
    ratio = actor.prob(batch.acts, batch.obs)/batch.old_prob
    loss = -np.minimum(ratio*adv, np.clip(ratio,1-clip,1+clip)*adv).mean()
    loss.backward()
```

Simulation demonstrates 1ms bound requires ≥27 PRBs for 20-device URLLC sync burst.

## 6 Limitations

*   **Conflict detection completeness**: Current Near-RT RIC conflict mitigation detects direct parameter conflicts but misses *implicit* semantic conflicts (e.g., energy-saving rApp scaling down MIMO layers contradicting URLLC reliability). O-RAN WG3 spec leaves implicit detection vendor-specific [7]; our graph model requires SLO intent mapping not yet standardized.
*   **Stochastic calculus looseness**: SNC bounds are often pessimistic (Chernoff factor 2-3× over provisioning). For highly bursty mMTC wide-tail TCP [kernel-level measurement], independent assumption fails; tail may be heavier than exponential, requiring **martingale** SNC, complexity O(2^n).
*   **P4 target heterogeneity**: Tofino supports 12-stage pipeline, PSA meters but not floating-point models. DORA PPO actor must stay in x86; P4 table sizes (64K entries for 6-tuple) insufficient for massive mMTC 1M flows requiring hash overflow to software—introduces tail.
*   **End-to-end synchronization**: ORANSlice requires E2 extension for slicing [1]; not upstreamed to O-RAN SC yet; O-DU split 7.2x fronthaul adds jitter not captured by rate-latency β.
*   **Model drift**: Online DRL xApp DORA support online training adapts but non-stationary traffic causing catastrophic forgetting; rApp retraining loop >1s may be too slow for mobility >60km/h URLLC V2X.
*   **Security**: TLS 1.3 on E2/O1 adds 35-60µs latency [spec].
*   **Evaluation scale**: Testbeds ≤10 UEs, single cell; large-scale proof open.

> Bold caveat: *P4 does not solve radio scheduling; it only solves post-radio policing and transport. If air interface cannot guarantee T+bu/Ru ≤1ms due to HARQ retransmissions (up to 4×), E2E fails regardless of data-plane speed.*

## 7 Conclusion
We presented a comprehensive architecture marrying **RIC xApp/rApp coordination** with **network-calculus-based URLLC isolation** and **P4 programmable data planes** for O-RAN slicing. By formalizing rApp policy cascade over A1 and xApp contention over E2, we identified conflict taxonomy and resolution utility anchored in DORA's DRL reward and xSlice's regret minimization [2][3]. Deterministic and stochastic network calculus yields closed-form dimensioning: URLLC delay ≤T+b_u/R_u and 99.999% bound D≥T+(σ+ln(1e5)/θ)/R_u, prescribing explicit reservation (≥27 PRBs for 20-device sync Industry 4.0) to meet 1ms SLO. P4 pipelines implement 6-tuple slice classification and token-bucket policing at 100Gbps line-rate, reducing UPF latency from ~1ms containerized to <5µs hardware, freeing budget for air-interface uncertainty [5][6]. ORANSlice demonstrates feasibility of open-source slicing control [1]; O-RAN slicing-aware architecture provides standard hooks [7]. Future work must close gaps on implicit conflict detection, martingale SNC for heavy-tailed mMTC, P4 target portability with 1M-flow scalability, and large-scale multi-cell evaluation. The synthesis points toward *verifiable, intent-driven slicing* where calculus provides proof and P4 provides enforcement of what RIC intelligence decides.
