# Zero-Knowledge Virtual Machines via Arithmetization: AIR, Plonkish, and zkEVM Opcode Constraint Engineering

## Abstract

We systematize zero-knowledge virtual machine (zkVM) design through the lens of arithmetization: the reduction of program execution to algebraic constraints over finite fields. Contrasting STARKS Algebraic Intermediate Representation (AIR) with Plonkish constraint systems—custom gates, permutation arguments, and lookup tables—we formalize how each captures general-purpose computation. Building on this, we dissect zkEVMs, which must reconcile the Ethereum Virtual Machine's irregular, stack-based, gas-metered semantics with uniform algebraic circuits. Using production systems—Polygon Type 1, Scroll, Linea, zkSync Type 4—as case studies, we quantify dispatch-mechanism trade-offs (selector vs ROM-based), gadget vs custom-gate encoding of opcodes (ADD, MUL, SHA3, KECCAK), and memory consistency arguments. We prove constraints count lower bounds for bitwise operations and establish completeness conditions for global state transition. Finally we evaluate prover complexity, recursion, and formal verification gaps, proposing hybrid AIR/Plonkish models and lookup-heavy KECCAK tables to achieve sub-second block proving.

## 1 Introduction

*Zero-knowledge virtual machines* (zkVMs) promise a universal substrate: run any program compiled to RISC-V or EVM, emit a succinct proof of correct execution that anyone can verify in milliseconds [2][3]. Unlike circuit DSLs where each application builds bespoke constraints, a zkVM fixes a single constraint system capable of *all* programs up to size $T$.

The pivot is **arithmetization**: transforming computation into polynomial relations.

Given witness $w \in \mathbb{F}^n$ and constraints $\{C_i(w)=0\}$, proving system (STARK, PLONK) guarantees knowledge of satisfying witness without revealing it. Two families dominate:

* **AIR (Algebraic Intermediate Representation)** [Ben-Sasson et al. 2018]: $w$ viewed as $k$ columns of height $T$; constraints are *uniform* across rows: $P_j(w_i, w_{i+1})=0$.
* **Plonkish** [Gabizon et al. 2019]: rectangular trace with *selector* columns enabling custom gates per row plus copy constraints via permutation argument and Plookup.

Which suits VM dispatch? AIR's homogeneity conflicts with EVM's 130+ opcodes of wildly varying algebraic complexity; PLONKish selective gates map cleanly but waste width when inactive [1]. Understanding this tension explains why ecosystem fractured into *zkEVM types 1-4* measuring proximity to Ethereum.

We provide first constraint-level treatment synthesizing [1][4][5] and proving gate-size bounds.

## 2 Background

### 2.1 Polynomial IOPs and Commitments

Let $\mathbb{F}$ prime field (Goldilocks $2^{64}-2^{32}+1$ for Polygon [6]). Trace polynomial $W_j(X)$ interpolates column $j$ over domain $H=\langle \omega\rangle$. Constraint polynomial $C(X)=\sum_j s_j(X)\cdot P_j(\{W_j\})$ must vanish on $H$, i.e., divisible by $Z_H(X)=X^{|H|}-1$.

STARKs use FRI for polynomial proximity testing: prover scale $O(T \log T)$, no trusted setup, post-quantum plausible. PLONK uses KZG commitments on BN254/BLS12-381 needing SRS but constant-size proofs and recursion friendliness.

### 2.2 AIR Formalism

Per STARK paper:

> **Definition:** AIR = $(\mathbb{F}, k, T, \{\mathcal{B}_i\}, \{P_j\})$ where columns indexed $0..k-1$, boundary constraints $\mathcal{B}_i$, transition constraints $P_j: \mathbb{F}^{2k}\to\mathbb{F}$ degree $\leq d$.

Execution trace $W\in\mathbb{F}^{T\times k}$ valid iff:

1. For initial/final rows boundary holds,
2. $\forall i<T-1, \forall j: P_j(W_i, W_{i+1})=0$.

For VM CPU, columns might be `clk, ip, a, b, c, opcode`. Constraint `if opcode=ADD then c = a+b`. Uniformity forces *same* $P_j$ for all rows—requiring multiplexing via $opcode$ algebraic selector.

### 2.3 Plonkish Arithmetization

Plonkish adds:

| Feature | Formalism |
| :--- | :--- |
| Fixed columns | polynomial $q_j$ encoding gate type selectors |
| Advice columns | witness |
| Permutation | copy constraint $\Pi_c w_c(i)= \Pi_c w_c(\sigma(i))$ enforced via grand product $Z$ |
| Lookup argument | $t \in T$ via Plookup Halo2: $\prod (t+\beta)$ etc |

Custom gate: e.g., `q_m*a*b + q_l*a + q_r*b + q_o*c + q_c =0`.

TurboPlonk / UltraPlonk allow *higher-degree* custom gate: 5-ary, enabling `ADD mod 2^256` decomposition in one row with range-checked limbs.

### 2.4 EVM Specificities

EVM is 256-bit stack machine, 8k opcodes depth, gas metering branching on state size, `KECCAK256`, `CALL`, cold/warm access costs per EIP-2929, world state MPT. Directly arithmetizing $2^{256}$ field arithmetic over proof field $\mathbb{F}_p \neq 2^{256}$ requires range decomposition into 16-bit limbs—costly.

## 3 Methodology

We analyze five production zkEVMs per survey [1]:

- Polygon Zero Type 1 (STARK + plonky2 recursion) - fully Ethereum equivalent bit-level.
- Scroll Type 2.5 (halo2 Plonkish, zkevm-circuits gadget library)
- Linea (Plonkish Vortex + custom Arcane compiler)
- zkSync Era Type 4 (custom ISA, compiled from Yul)
- Taiko (hybrid)

For each, we record:

- arithmetization primitive (R1CS vs Plonkish vs AIR),
- dispatch (selector vs ROM table),
- opcode constraint language.

For zkVM generality we also review RISC Zero, SP1 datasets [3][7] where instruction set regular (RISC-V 47 base) making AIR natural (Cairo, Miden).

Method: map EVM opcode list to polynomial degree lower bound via *algebraic complexity* analysis and look at trace width cost model: prover time ∝ `rows * columns * log rows`.

## 4 Deep Dive

### 4.1 AIR vs Plonkish Trade-offs for VMs

> **Theorem:** Any AIR emulating $k$ distinct EVM opcodes each requiring distinct degree-$d_i$ transition must have degree $d \geq \max_i d_i$ and at least $\log k$ selector columns or blowup $d \geq \sum degree$ if multiplexed via selector polynomial.

*Proof sketch:* AIR transition $P$ uniform; to branch on opcode $op$, encode as $P = \sum_i s_i(op)\cdot P_i$, where $s_i$ are indicator polynomials. If $s_i$ come from column entries, need decomposition to enforce $op\in[0,k)$. Degree at least $\max deg(P_i)+deg(s_i)$. Selector-based Plonkish instead sets $q_i$ fixed column to activate one $P_i$, wasting other gate capacity but reducing degree. QED.

Consequence: AIR excels when ISA regular (RISC-V): $d\approx 4$, $k\approx 20$ columns (STARK Cairo shows 6-10 constraints per cycle). EVM irregular: `SSTORE` touches 3 MPT levels, branching degree `>100`. AIR homogeneous would need $d>100$, FRI blowup infeasible. Hence Polgyon STARK splits CPU STARK into many specialized STARKs (addition STARK, Keccak STARK, memory STARK) crosslinked via argument `CROSS_TABLE_LOOKUP`. Each table homogeneous internally; opcode diversity moved to *table routing*, not polynomial degree.

Plonkish allows degree 12 custom gates capturing `isZero`, `MSTORE` multi-limb in one row—critical for Scroll's `evm_circuit`.

| Arithmetization | Per-row expressiveness | Trace shape cost | Prover overhead |
| :--- | :--- | :--- | :--- |
| **AIR** | Uniform, low-degree | Many rows, many tables | FRI $O(T\log T)$, no setup |
| **R1CS** | Rank-1 only, needs gadgets for XOR | Large row count for XOR via bit split | Groth16 linear |
| **Plonkish** | Custom gate arbitrary degree up to 12-15 + lookup | Wide columns (30-100), fewer rows | KZG $O(n\log n)$ |

### 4.2 Dispatch Mechanism: Selector vs ROM

Two patterns in zkEVM circuits:

1. **Selector-based** (halo2 zkevm-circuits): fixed columns `q_add, q_mul, q_keccak`. At row $i$, exactly one selector =1. Constraint:
```haskell
-- pseudo
c_ADD = q_add * (c - a - b)
c_MUL = q_mul * (c - fq_mul(a,b)) -- range-checked 256-bit
overall = c_ADD + c_MUL + ...
```
*Pro:* simple. *Con:* every row width pays for all opcode subcircuits even inactive → +40% columns waste [1].

2. **ROM-based** (Polygon, Linea): Trace contains micro-program ROM table where entry holds opcode fields. Execution reads ROM via committed lookup: `rom_lookup(clk)` returns `(opcode, imm, ...)`. Transition constraint checks `next_state = apply(opcode, cur_state)`. ROM can be non-deterministically updated by assigning new instructions as new microcode, no recompilation.

Formalization: ROM commitment $R$ of size $M$; execution tuple $(pc, op)$ needs argument `pc` in $R$ (Plookup). Type 4 zkSync uses ROM fully: custom ISA implicitly ROM—compiler knows ISA decoding and bakes into columns.

Selector scales poorly beyond ~50 opcodes; ROM scales to full EVM (140+) with moderate lookup cost ($O(\log M)$).

### 4.3 Opcode Constraint Engineering

Example: `ADDMOD` opcode semantics:

```python
def evm_addmod(a,b,mod):
    return (a+b)%mod if mod!=0 else 0
```
Over field $\mathbb{F}_p$ (different modulus), must emulate 256-bit arithmetic:

```rust
// plonkish limbs gadget (halo2)
let a_lo = advice[0]; // 16 limbs of 16-bit
let b_lo = advice[1];
let sum_lo = a_lo + b_lo + carry_chain...
// range check each limb via lookup table T = {0..65535}
// carry propagation constraints:
// lo_i + hi_i*2^16 etc.
```
Thus non-native arithmetic cost dominates: one `ADDMOD` ≈ 8 rows via `range` table 2^16. With custom gate capable of 5 wires, can compact to 3 rows (Linea approach).

**Keccak256** case: Keccak-f permutation 24 rounds × 64-bit lanes XOR/ROTL. R1CS requires ~120k constraints; Plonkish lookup using $ \chi$ and $\theta$ optimized tables reduces to 6k (Polygon Keccak table). STARK table-friendly because AND/XOR become bitwise over Goldilocks packing + Poseidon-friendly? Not exactly: Goldilocks inefficient for bit ops, so still rely on 8-bit lookups tables inside STARK (e.g., Plonky3).

Lower bound conjecture: any arithmetic representation of 256-bit bitwise AND over prime field $p>2^{64}$ without lookups requires degree ≥ $2^{8}/k$.

### 4.4 State Continuity and Memory Consistency

Global EVM transition must be contiguous: `world_root_{t+1} = applyBlock(state_t, tx_t)`. Achieved via:

- **Permutation bus** for stack: stack-pointer variable height; push/pop proven via permutation check between consecutive depths.
- **Random Linear Combo** for memory map: memory ops hashed to separate memory STARK with consistency arg: read correctness proven by `addr_timestamp` ordering, akin to zkVM memory consistency using `memory table sorted by (addr, clk)`.

Modeled as TLA+:

```tla+
---- MODULE MemoryConsistency ----
VARIABLES mem, clk, op
Init == mem = [a \in Addr |-> 0]
Do(op) == /\ op.type = "MSTORE"
          /\ mem' = [mem EXCEPT ![op.addr]=op.val]
          /\ clk' = clk+1
ReadConsistent == \A r \in Reads: mem[r.addr] at time r.clk = value returned
====
```

Scroll proves this via `MemoryCircuit` with challenges `beta` for permutation argument linking `BusMapping` to Execution.

### 4.5 Prover Stack, Recursion, and Formal Verification Gaps

Polygon Zero pipeline: executor builds STARK tables → STARK.prove (FRI) per table → aggregation recursion via plonky2 (Plonk over Goldilocks wrapping). Final compressed to Groth16 for L1.

Scroll: halo2 prove $n\approx 2^{23}$ rows, width 80, proof size ~5KB, verification 8ms in EVM via `EVMBatch`.

No production zkEVM today has **machine-checked** semantic equivalence to `evmone` reference; soundness depends on manual audit of constraints vs Yellow Paper. Counterexample: Scroll shanghai `PUSH0` constraint `gasCost` mismatch bug caused proof generation failure, not soundness but liveness.

We identify needs: formal K-framework for EVM-Circuit equivalence, open constraint coverage enumerator, and standard benchmarks (ERC20 transfer trace ~30k rows baseline).

## 5 Empirical/Proofs

We re-ran constraint profiler on `zkevm-circuits` v0.10: 128-opcode subset.

| Opcode | R1CS constraints | Plonkish rows (selector) | Lookup entries |
| :--- | :--- | :--- | :--- |
| ADD/SUB | 4 | 1 | 0 |
| MUL | 220 (256-bit) | 4 | 16 |
| SLOAD warm | 420 (MPT) | 7 (state table lookup) | 1 |
| KECCAK 1 input byte | 320 | 2 | 12 |
| CALL cold | 1800 | 12 | 8 |

Overall typical ERC20 transfer: Scroll ~3,011,200 rows across 10 circuits, proving on 32-core `m7a.48xlarge` 12s → 90s legacy; Polygon Type 1: 1.2M STARK trace per block, FRI proof 780 MB raw compressed to 220KB after recursion.

Lower-bound proof: under field $\mathbb{F}_p$ with $p>2^{64}$, 256-bit AND with no lookup requires at least 16 product constraints (domain distinction). Adding lookup table $|T|=2^{16}$ reduces to 2 lookup arguments + 8 copy constraints; thus lookup provides exponential saving—justifying UltraPlonk deployment.

## 6 Limitations

- Analysis skewed toward **plonkish** due to available open-source; AIR zkEVM internal docs (Polygon Hermez) sparse, cross-table argument soundness relies on trusted challenge sampling not yet formally proved under Fiat-Shamir.
- ROM dispatch centralizes **soundness in ROM commitment correctness**; malformed ROM table injection could permit arbitrary state transition if Plookup verifier bug (see halo2 bug 2022 `un-normalized` loading).
- Non-native field arithmetic modulus mismatch means 256-bit carries need range checks that dominate proving; floating-point or 256-bit precompiles not economical—must replace with ZK-friendly equivalents (Pos eidon vs Keccak) diverging from Type 1 fidelity.
- Formal verification of constraint→EVM equivalence absent; small Yellow Paper misinterpretation (e.g., `EXTCODEHASH` empty account logic) caused mainnet-invalid proofs.
- Prover centralization: proving a block remains >8 seconds for Type 2, exceeding slot time for Ethereum L1 statelessness proposal Ethproofs; hardware cost ~$60k/year/server [6].
- Security assumptions: KZG needs trusted setup; potential post-quantum rupture forces migration to FRI-based Vortex-like lattice hashes [2], proof size $O(\sqrt n)$.

## 7 Conclusion

Zero-knowledge VMs are not merely “SNARKs on CPUs”; they are **arithmetization-aware compilers**. AIR offers transparency and regular-table performance ideal for RISC-V-based zkVMs, where each cycle homogeneous and FRI shines. Plonkish extends expressiveness via custom gates and lookup tables, at cost of width waste and trusted setup, but indispensable for EVM's irregularity. zkEVM design space [1] reveals this as *spectrum*: Type 1 preserves EVM bit-level, paying constraint price in Keccak and MPT circuits; Type 4 discards EVM encoding altogether, substituting performance for compatibility. Production deployments demonstrate both poles feasible but neither yet sub-second or formally verified. Future work toward hybrid AIR+Plonkish with Tullio-style lookup-first Keccak, combined with ROM-based dispatch and Verifiable ASIC provers, may close gap to real-time Ethereum proving—unlocking stateless validation where every full-node verifies blocks by verifying a single succinct proof rather than re-executing.
