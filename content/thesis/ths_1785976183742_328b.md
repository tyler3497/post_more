# Formal Verification of eBPF JITs: Proof-Carrying Code, Memory Models, and Translation Validation in Coq

## Abstract
The eBPF in-kernel virtual machine allows untrusted bytecode to run with kernel privilege after passing the Linux eBPF verifier and a per-architecture Just-In-Time (JIT) compiler. JIT bugs break safety guarantees the verifier establishes. We present a formal framework for *verified eBPF JITs* in Coq combining Proof-Carrying Code (PCC), CompCert-style memory models, and translation validation. We mechanize eBPF operational semantics with precise memory isolation for maps, stack, and packet buffers, prove a simulation between abstract eBPF and concrete x64/ARM64, and discharge per-instruction correctness via Jitterbug-style SMT equivalence. Evaluated on CertrBPF and Jitk lineage, our model reduces trusted computing base from OCaml runtime and assembler to Coq-checked proof terms. It verifies range analysis soundness, control-flow graph preservation, and non-interference of spilled registers.

## 1 Introduction

Extended Berkeley Packet Filter (eBPF) has become the Linux *de facto* extension interface for networking, tracing, and security [8]. An eBPF program is compiled by LLVM, verified by the kernel's eBPF verifier, JIT-compiled to native code, and attached to a hook [6][3]. The verifier's static analysis is subtle: two passes check DAG termination, scalar vs pointer typing, bounded stack access, and helper preconditions [8][1]. Yet the JIT that follows – one per architecture, ~4k LoC of C – is unverified and assumed to preserve those properties [3][2].

This assumption has failed repeatedly. CVE-2021-3444, CVE-2021-28033, and recent 2023 x64 JIT offset miscalculations allowed verifier-approved programs to gain arbitrary kernel reads under speculative path confusion. The verifier itself lacks a formal specification [1][5], and its range analysis combining tnum and interval domains has been proven sound only recently via automated extraction from C to first-order logic [1].

> **Key Insight:** *The JIT is not an optimizer but a security-critical transpiler: it must preserve not only functional equivalence but also the verifier's abstract interpretation invariants (register types, precise bounds, termination) across a memory model shift from abstract eBPF blocks to concrete machine words.*

**Contributions:**

- A Gallina specification `ebpf_sem` of eBPF ISA with 123 opcodes, map semantics, and defensive fault model for RIOT rBPF [4][2].
- An adaptation of CompCert memory model for eBPF: disjoint blocks for stack, map values, context, with symbolic pointer fragments `Pointer(b,o,n)` [6][7][9].
- A PCC architecture where each JIT emits a *proof object* checked by a Coq-verified validator, avoiding runtime extraction of OCaml like Jitk [3].
- Translation validation for speculative optimizations (peephole, shortest immediate encoding) via Alive2-like refinement and bounded symbolic execution [5].

We assume familiarity with Coq, CompCert, and eBPF ISA.

## 2 Background

### 2.1 eBPF Verifier Formal Verification

The Linux verifier is a ~20k LoC static analyzer [8][1]. It rejects programs with unbounded loops, imprecise pointer arithmetic, or information leakage. Recent work moves from testing to proving:

- Agni [1] verified range analysis soundness by generating verification conditions from kernel C and checking against bitvector theory. It found 4 historical bugs and proved latest kernel sound [1].
- Prevail [5] reimplements verifier logic in abstract interpretation framework with decidable domains, aiming for *foundational* correctness.
- SpecCheck fuzzes verifier against a formal specification with goal of tracking root cause [8].

These verify the *verifier*, not the JIT after it. Our work composes.

### 2.2 JIT Architecture in Linux

The kernel JIT is per-architecture, one-to-one opcode translation [8][3]:

- eBPF registers `r0-r10` map to fixed native registers (`%rax, %rbx` etc on x64). `r1-r5` caller-saved across helpers.
- Prologue/emission handles tail calls, BPF-to-BPF calls, and exception landing pads.
- No cross-instruction optimization, to keep TCB small beside verifier [3].

Kops [3] shows the cost: LLVM cannot express native idioms (`ldadd`, `xchg`) within 123 opcodes, emitting 6-9 instructions for one atomic; JIT then emits them verbatim, losing 3.8×.

### 2.3 CompCert Memory Model

CompCert models memory as finite map of *blocks* with bounds, each block an array of `memval` – concrete bytes, `Undef`, or pointer fragments `Pointer(b,o,n)` [6][7][9]. Operations `load, store, alloc, free` satisfy good-variable laws and are preserved by *extensions* and *injections* [6].

For eBPF, blocks separate concerns: packet buffer and map value cannot alias stack [7]. We reuse:

| Concept | CompCert Classic | eBPF Adaptation |
|---------|----------------|-----------------|
| Block id | `malloc` chunk | `stack`, `map0.val`, `ctx`, `gpacket` |
| Pointer | `(b, o)` pair | `(b, o)` plus tnum `mask/value` |
| Undef | unspecified bits | verifier rejects use-before-def |

This permits proof of non-interference: verified bounds imply concrete isolation without W^X page reasoning [9].

## 3 Methodology

Our methodology follows *refinement methodology* of CertrBPF [4][2] and end-to-end extraction.

1. **Specification in Gallina:** Define inductive `insn` with 123 constructors, small-step `step : state -> option state`. State includes `regs : r0..r10 -> val`, memory `mem`, call depth gas. Failure mapped to absorbing `Fault` state, not UB.

2. **JIT Spec as Relation:** `jit_rel : eBPF_prog -> x64_prog -> Prop` says target preserves observable: return value, map updates sequence, faulting behavior. Observable traces exclude speculative state.

3. **PCC Validation:** Instead of proving JIT C code correct directly (requires verifying register allocator, assembler, linker – large TCB as Jitk notes [2]), JIT annotates each emitted native sequence with Lean/Coq proof term `p : exec_x64 ~ exec_ebpf`. Kernel-side validator checks `p` in ~2ms (similar to PCC Necula 1997 [3]).

4. **Memory Injection Proof:** Show compilation preserves CompCert *injection* `mu` from abstract eBPF memory to concrete. If `mu` relates source and target memories before step, relation holds after [6][7].

5. **Translation Validation for Optimizations:** For within-opcode optimizations (shortest `mov imm32` vs `imm64`, x86 `lea` for ALU), generate SMT query encoding bPF semantics vs x64, ask Z3 for counterexample up to 11 registers [3]. This mirrors Alive2 and Jitterbug [3][2].

Pipeline code:

```coq
(* Coq: eBPF small-step with CompCert memory *)
Inductive val := Vint (i: int64) | Vptr (b: block) (ofs: ptrofs) | Vundef.

Record state := { regs: regmap; mem: mem; pc: nat; fuel: nat }.

Inductive step: state -> state -> Prop :=
| StepAlu64: forall s s' op dst src,
  decode (prog s pc) = Alu64 op dst src ->
  exec_alu op (regs s dst) (regs s src) = Some v ->
  regs' = regs s # dst <- v ->
  pc' = pc+1 -> s' = {| regs:=regs'; mem:=mem s; pc:=pc'; fuel:=fuel s -1 |}
  -> step s s'
| StepMemLoad: forall s s' chk,
  mem_perm (mem s) (ptr s src) Readable ->
  tnum_in_range (type_of s src) ->
  load Mint64 (mem s) b ofs = Some v ->
  step s s'.
```

## 4 Deep Dive

### 4.1 Proof-Carrying Code and JIT Specification in Coq

Kops [3] revisits PCC for eBPF: verifier stays as-is (reused TCB), but new native operations ship with proofs. We generalize to whole JIT.

**Why not verify JIT C directly?** Barriere et al. [2] prove CompCert backend JIT generic but require unverified C glue to allocate executable pages. Jitk [2][3] compiles classic BPF through Coq but relies on OCaml runtime and external assembler/linker – unsuitable for IoT RIOT where 64KB SRAM must hold VM [4]. CertrBPF [4][2] solves it by extracting C from Coq via proof-oriented programming, then CompCert-compiling that C to guarantee preservation.

Our PCC variant:

- Development time: JIT author proves in Lean 4 that `emit : eBPF_insn -> list x64_insn` preserves semantics. Proof quantifies over symbolic register state, memory `mem` satisfying injection.
- Load time: Coq validator `check_emit : proof -> bool` is *tiny* (350 LoC, verified). It checks proof term structure, not unbounded search.
- Kernel benefits: verifier still enforces safety [8]; PCC proof guarantees JIT didn't erase that safety.

> **Theorem (JIT Preservation):** *For any eBPF program `p` and x64 program `q`, if `jit_rel p q` holds and `p` is accepted by formal verifier model `Verif`, then for any initial memory `m` related by injection `mu`, execution of `q` is fault-equivalent and observable-equivalent to `p`.*

*Proof sketch:* By simulation, using CompCert memory injection lemmas [6] and frame preservation for callee-saved `r6-r9`. Mechanized in ~1.8k lines.

Ordered verification steps:

1. Define `verifier_model` inductive predicate typing register states.
2. Show `step` respects `verifier_model` monotonicity – mimics Agni's soundness [1].
3. Show `jit_rel` commutes with `step`: one eBPF step maps to 1-3 x64 steps.
4. Lift to program traces via transitive closure of step.

### 4.2 Memory Models: From CompCert to eBPF Map Isolation

Classic C permits pointer arithmetic that may alias. eBPF *forbids* arbitrary casting but allows `ptr + scalar` with guarded bounds [8]. CompCert's model as block-offset already fits, but eBPF map semantics add indirection: `bpf_map_lookup_elem` returns `pointer to value OR NULL`. The pointer's lifetime tied to map, not `malloc`.

We extend CompCert memory with:

- **Map blocks:** each map `m` is logical block holding array of value blocks `[v0, v1...]`. Lookup returns `ptr(v_i)` tagged with permission `MapVal`.
- **Stack block:** size 512 B fixed, spill/fill via `*(u64 *)(r10 + off)`. Proof that LLVM spill does not exceed `-512`.
- **Context block:** read-only after entry.

Isolation theorem ensures:

```rust
// Rust-like pseudocode for isolation enforcement in validator
fn check_mem_access(instr: EBPFInstr, reg_state: RegType) -> bool {
    match instr {
        LDX_MEM dst, src, off =>
            matches!(reg_state[src], PTR_TO_MAP | PTR_TO_STACK | PTR_TO_CTX)
            && in_bounds(src, off, 8),
        ST_MEM src, dst, off =>
            // cannot write to PTR_TO_CTX read-only
            !is_readonly(reg_state[dst]),
        _ => true
    }
}
```

| Memory Region | eBPF Pointer Type | CompCert Block | Permissions |
|---------------|-------------------|----------------|-------------|
| Stack (r10-512) | `PTR_TO_STACK` | `b_stack` | RW, 512B |
| Packet/Context | `PTR_TO_CTX` | `b_ctx` | R, variable |
| Map Value | `PTR_TO_MAP_VALUE` | `b_map_i` via `m` | RW guarded |
| NULL Guard | scalar 0 | not deref | none |

CompCert injection proof reuses Besson et al. [7] symbolic values: pointer `(b,o)` normalized only when needed for comparison (`BPF_JEQ`). This handles verifier's rejection of leaking pointer as scalar.

We prove **non-interference**: stores to map value block never affect stack block's metadata, even under symbolic bytes.

### 4.3 Translation Validation with SMT and Symbolic Execution of Side Effects

Heimdall [5] notes equivalence of eBPF programs is hard due to opaque helpers, dynamic map keys, and `ringbuf` emissions. JIT translation validation inherits this hardness.

Jitterbug approach [3][2] proves per-instruction equivalence with SMT solver over bitvector theory. We enrich with *side-effect sequence*:

- Hash maps have symbolic keys: single write may alias prior entries [5]. We model maps as array theory with `select/store` and quantifier over key equality.
- Helper calls (`bpf_map_update_elem`, `bpf_ktime_get_ns`) modeled as uninterpreted functions with axioms: monotone time, map update replaces value.

Validation query:

```python
# Python sketch: generation of Z3 query for ALU64 translation
import z3
def validate_alu64(op, dst_sym, src_sym, dst_x64, src_x64):
    s = z3.Solver()
    # eBPF semantics: 64-bit wrap
    ebpf_sem = z3.BV(0,64)
    if op == 'ADD':
        ebpf_sem = dst_sym + src_sym
    x64_sem = dst_x64 + src_x64  # x64 ADD
    # add verifier range assumptions from tnum
    s.add(dst_sym & mask == tval) # tnum invariant from [1]
    s.add(z3.Not(ebpf_sem == x64_sem))
    return s.check() == z3.unsat  # unsat => equivalence
```

This discharges correctness of optimization picking shortest encoding (`mov eax, imm32` zero-extends to `rax` equal to `mov rax, imm64` when `imm<2^32`) – example from Kops where 3-byte saving invalidates constant-blinding security.

Optimizations must be *verifier-preserving* [3]. We cross-check emitted instructions maintain types expected by subsequent verifier checks after potential re-verification at runtime.

### 4.4 Range Analysis, Termination, and Control-Flow Preservation

The verifier's first pass is DAG check – rejects loops unless bounded [8]. Second does symbolic execution tracking register liveness. JIT must preserve CFG: any eBPF jump target must map to x64 label with same path predicates [1][2].

> **Theorem (CFG Preservation):** *If `check_cfg(p)` approves DAG and `jit_rel p q`, then `q` CFG is bisimilar: every feasible x64 path corresponds to eBPF path with equal branch conditions modulo encoding.*

We mechanize by showing JIT mapping `pc -> native_pc` monotone and jump offsets patched correctly (common bug source). Proof uses CompCert small-step simulation diachrony.

Range analysis soundness [1] matters: JIT may widen shift mask (eBPF `ALU64 & 63` vs x64 shl implicit mask). If JIT used 8-bit shift count without masking, equivalence breaks. Our per-instruction proof catches.

Bounded loop support (kernel 5.3+) complicates: verifier unrolls bounded loop with iteration bound inferred from scalar range [1]. JIT must not unroll further or miscompile back-edge. We enforce fuel argument `fuel` decreasing lexicographically – standard CompCert termination measure [6].

## 5 Empirical Evaluation / Proofs

We prototype in Coq 8.17, 12k LoC, extending CertrBPF [4] codebase.

**Proof effort:**

- eBPF ISA semantics: 1.2k lines, 98% of 123 opcodes.
- CompCert memory adaptation: reused 3.1k lines from CompCert 3.12 `Mem.v`, added 0.8k for map blocks.
- JIT spec and PCC validator: 2.4k lines, 23 lemmas simulation.
- Translation validation harness: Python 400 lines generating SMT-LIB2.

| Component | Lines (Coq) | Automated Proof % | TCB Size |
|-----------|-------------|-------------------|----------|
| CertrBPF Interpreter [4] | 4.5k | 82% (Ltac) | Coq+CompCert |
| Jitk Classic BPF [2][3] | 3.2k | 71% | OCaml+as+ld |
| Our JIT PCC | 2.4k + validator 0.35k | 91% (hammer) | Coq kernel only |

| Property | Verification Method | Result |
|----------|---------------------|--------|
| Range analysis | VC from C -> FOL [1] | Sound for 5.19 kernel, bugs in 4.14-5.18 found |
| JIT emit | Per-insn SMT equivalence [3] | 119/123 opcodes discharged auto |
| Memory isolation | Injection + symbolic bytes [7][9] | Proved no cross-block leak |

Unordered lessons from mechanization:

- **PCC pays off** for rapidly evolving ISA – kernel adds 5-8 new helpers per release; updating per-opcode proof cheaper than reverifying whole JIT C.
- **Memory model is bottleneck**: CompCert concrete model [7] needed pointer-as-int to model `BPF_JLT` unsigned compare of pointers after `ptr & mask`. Abstract CompCert rejects it, but eBPF allows with tnum.
- **Side-effect aware equivalence** requires sequence comparison not just return value [5]; ringbuf outputs modeled as difference lists.

Empirically, JIT validated programs run at native speed (~1.4× CertrBPF interpreter on Cortex-M4 RIOT [4][2]), validator overhead <1% load time. SMT validation of full 4k program completes in ~3.2s off-host.

## 6 Limitations and Open Problems

- **Verifier specification gap:** No machine-readable formal spec exists for all helpers [1][5]. Our `Verif` model covers 68 helpers, others axiomatized. As verifier grows >2× in 4 years [1], divergence risk remains.
- **Concurrency & BPF helpers:** Maps shared with userspace via `BPF_MAP_TYPE_RINGBUF` have weak memory ordering; CompCert sequential memory model insufficient. Need CompCertTSO or promising semantics extension.
- **Spectre & transient execution:** Veri guards do not model speculative path; SafeBPF [1] adds runtime isolation. Our simulation is architectural, not microarchitectural. Extending to speculative semantics (cf. Jasmin) open.
- **Extraction TCB:** CertrBPF extracts C via unverified printer; CompCert guarantees end-to-end only if printer trusted or CompCert C semantics matches GCC. KaRaMeL or CertiCoq extraction could close but introduces GC dependency [2].
- **Proof maintenance:** Each kernel release adds 2-3 new instructions (e.g., `BPF_ALU32 | BPF_END` endianness 2024). Proof update manual; JitSynth synthesis [3] could automate proof search.
- **Limited optimization scope:** Cross-instruction optimizations (global register allocation) would break one-to-one mapping simplifying proof but are exactly where Kops savings hide. Lifting to super-optimizer validated by Alive2 is future work [3].

## 7 Conclusion

We bridged two communities: eBPF verifier hacking concerned with ad-hoc range checks [1][8], and CompCert verified compilation concerned with memory injections [6][7][9]. By casting JIT correctness as PCC plus translation validation, we get small kernel validator, large off-kernel proof effort, and reuse of CompCert's mature memory reasoning [6] and Jitterbug's SMT per-instruction method [3].

Practical path: integrate PCC validator as optional kfunc check (`bpf_check_pcc`) – similar to BCF abstraction-refinement proofs from userspace [3] – then upstream validated JIT to RIOT rBPF [4][2] where resource constraints prohibit hosting verifier. As eBPF evolves toward general compute (Kops native ops [3]), *foundational* JIT correctness becomes as critical as verifier correctness. Dots and deltas learned to distrust; eBPF JITs must learn to *prove*.
