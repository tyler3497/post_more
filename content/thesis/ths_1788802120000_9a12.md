# In-Network Computing for Distributed Consensus with P4 Programmable Switches: NetChain Chain-Replicated Key-Value Stores in the Data Plane, Ordered Multi-Switch Transactions, and Session-Numbered Failure Recovery

## Abstract

Programmable switch ASICs have inverted a decades-old assumption of distributed systems design: the network is no longer a passive conduit but a computational substrate that can host consensus logic itself. This thesis examines how **in-network computing** on P4-programmable switches enables distributed consensus at line rate. We begin with the two canonical reductions of the consensus problem onto network hardware — **NetPaxos**, which maps Paxos roles onto SDN switches, and **NOPaxos**, which offloads request ordering to the network via Ordered Unreliable Multicast — and then develop the central case study: **NetChain**, a scale-free, sub-RTT coordination service built on **chain replication** entirely within the data plane of P4 switches. We analyze NetChain's register-array key-value store, its sequence-number discipline for best-effort inter-switch transport, and its **session-numbered failure recovery** protocol, which uses virtualization and session epochs to reconfigure chains after switch failures without violating strong consistency. Prototype results — four Barefoot Tofino switches against ZooKeeper — show orders-of-magnitude throughput and latency gains. We close with the paradigm's fundamental limits: bounded on-chip memory, P4's restricted computational model, and data-plane/control-plane recovery tensions.

## 1 Introduction

Coordination services — configuration management, distributed locking, leader election, group membership — sit on the critical path of nearly every cloud application. Systems like ZooKeeper, etcd, and Chubby implement these services as *replicated state machines* running on commodity servers, and every query pays the price of server-side processing: multiple round-trip times (RTTs), interrupt-driven packet handling, and user/kernel crossings on every replica [1].

**In-network computing** challenges this placement. If the switch ASIC can parse, match, modify, and forward packets at terabits per second with sub-microsecond pipeline latency, then it can also *store* state and *decide* — at line rate — what response a coordination query deserves. This is not merely an optimization; it is a change of the system's fault model, latency envelope, and consistency boundary. The network is no longer the adversary that protocols defend against (reordering, loss, partitions) but a participant that guarantees structure: ordering, atomicity, and durability.

The intellectual lineage of this idea runs through three landmark designs:

1. **NetPaxos** (Dang et al., SOSR 2015): the first systematic study of implementing Paxos in network devices, presenting both a full switch-based Paxos design and an *optimistic* variant that assumes the network orders messages [3].
2. **NOPaxos** (Li et al., OSDI 2016): a co-design that splits replication between network and protocol layers, introducing the *Ordered Unreliable Multicast* (OUM) primitive so that the network orders but need not reliably deliver [4].
3. **NetChain** (Jin et al., NSDI 2018, Best Paper): the first complete *coordination service* executed entirely in the switch data plane, using chain replication over P4 switches to provide strong consistency with latency as low as half an RTT [1][2].

This thesis unifies these threads. Its central claim is that *consensus is a packet-processing problem*: once the match–action pipeline is enriched with persistent state and a versioning discipline, classical replication protocols — chain replication, in particular — map onto it with surprising fidelity. The remaining hard problems are not algorithmic but architectural: how to store a key-value service in kilobytes of SRAM, how to remain correct when the transport between switches is best-effort, and how to reconfigure a chain after a switch dies without letting stale writes resurrect.

## 2 Background

### 2.1 From OpenFlow to P4: the programmable data plane

The P4 language (Bosshart et al., 2014) made the forwarding plane programmable in a *target-independent* way: programmers declare custom headers, a parser state machine, match–action tables, and a deparser, and a compiler lowers this program onto an ASIC such as the Barefoot Tofino [5]. The PISA (Protocol-Independent Switch Architecture) pipeline — parser → ingress match–action → stateful memory → egress match–action → deparser — processes packets in a fixed number of stages at line rate. Crucially for consensus, PISA exposes **stateful objects**: register arrays, counters, and meters that persist across packets and support atomic read-modify-write within a single stage traversal. These registers are the *only* durable memory available in the data plane, and everything a consensus protocol stores — values, sequence numbers, session identifiers — must fit into them.

*Figure 1. The P4/PISA pipeline. Parser, match–action stages, stateful register arrays (the in-network key-value store), and deparser. All consensus state must reside in the register file.*

### 2.2 Consensus before the network was smart

Classical consensus (Paxos, Raft, Viewstamped Replication) treats the network as an unreliable channel and places all logic on end hosts. **Chain replication** (van Renesse & Schneider, OSDI 2004) is the variant most congenial to networking: servers are arranged in a linear chain; writes enter at the *head*, propagate through *replicas*, and are acknowledged by the *tail*; reads are served by the tail. Every object carries a version, and the chain order *is* the serialization order. NetChain's insight is that this topology is already a *routing* problem — and routers are now programmable.

### 2.3 Two precursors: NetPaxos and NOPaxos

NetPaxos asked what Paxos would look like if acceptors lived in switches. It offered two answers: (i) implement the complete Paxos state machine in switch firmware with modest OpenFlow extensions, and (ii) an **optimistic protocol** that performs consensus without switch-side computation at all, relying instead on the assumption that the network delivers messages in the same order to all acceptors [3]. The second answer prefigures the great theme of in-network consensus: *ordering is cheaper in the network than agreement is on hosts*.

NOPaxos made this theme a full protocol. It introduced **Ordered Unreliable Multicast (OUM)**: the network (via a sequencer, implementable in a switch) stamps every request with a sequence number and multicasts it in order, but makes no reliability promise. Replicas execute requests in sequence-number order; gaps are detected locally and repaired by a lightweight *gap agreement* protocol, with full *view change* only for sequencer failure [4]. Throughput lands within 2% and latency within 16 µs of an unreplicated system. The lesson: if the network *orders*, the protocol can shed its most expensive coordination.

## 3 Methodology

Our method is **design analysis with formal invariants**: we reconstruct each protocol's data-plane mechanisms, state the safety invariants they must maintain, and show how the P4 execution model forces specific implementation choices. We draw on the published artifacts and evaluations of NetChain [1][2], NetPaxos [3], and NOPaxos [4], supplemented by the P4 language specification [5] and the broader in-network transaction-processing literature (e.g., P4DB [6]). Where quantitative claims appear, they are the original papers' measured results, reproduced here for comparison — not new measurements.

We structure the deep dive around the three sub-problems the NetChain authors identify for data-plane chain replication:

- **(R1) Storage**: how to store and serve key-value items in each switch's bounded register memory.
- **(R2) Routing**: how to route queries through the switches according to the chain structure.
- **(R3) Ordered delivery**: how to cope with best-effort transport — packet reordering and loss — between chain switches.

To these we add a fourth, the subject of our title: **session-numbered failure recovery** — how chain reconfiguration after switch failures preserves consistency through virtualization and session epochs.

## 4 Deep Dive

### 4.1 The NetChain data plane: a key-value store in registers

NetChain exposes four operations: **Read** and **Write** (handled entirely in the data plane at line rate), **Insert** (control-plane assisted), and **Delete** (data-plane invalidation plus control-plane garbage collection) [2]. The asymmetry is deliberate: coordination workloads are dominated by reads and writes of *existing* keys (locks, configuration parameters), while key creation is rare.

Each switch stores the key-value items in on-chip **register arrays**, indexed by a hash of the key. A slot holds the value together with a **per-key sequence number** (version). The P4 program parses a custom NetChain header carrying `(op, key, value, seq)`, performs a register read indexed by `hash(key)`, and:

- for **Read**: returns the stored value (reads are routed to the *tail*, which holds the newest committed version);
- for **Write**: if the packet's sequence number exceeds the stored one, updates value and sequence number, then forwards the packet toward the next switch in the chain.

Because the pipeline is feed-forward and each stage touches a register at most once per packet, the entire operation completes in a single pass at line rate — there is no recirculation, no control-plane involvement, and no per-query server CPU.

> **Theorem:** *If every write for key k traverses the chain head → tail in order and each switch applies only writes with sequence numbers strictly greater than its stored version, then all switches' stored values for k converge to the tail's value, and reads at the tail observe a linearizable sequence of writes.*

The subtlety is **(R3)**: the links between chain switches are best-effort. Packets can be reordered or lost. NetChain's answer is the sequence-number discipline above — an *idempotent, order-insensitive* update rule. A delayed duplicate write with `seq ≤ stored` is silently dropped; a write that overtakes an earlier one is applied, and when the earlier one later arrives it is dropped as stale. This is exactly the **last-writer-wins with monotonic versions** rule, and it makes the data plane *self-stabilizing* with respect to transport anomalies, at the cost of requiring clients to assign strictly increasing sequence numbers per key.

```python
# NetChain per-switch write handler (conceptual P4 action semantics)
def handle_write(pkt, registers):
    idx = hash(pkt.key) % N_SLOTS
    stored_seq, stored_val = registers[idx].read()
    if pkt.seq > stored_seq:          # monotonic version check
        registers[idx].write((pkt.seq, pkt.value))
        forward(pkt, next_in_chain(pkt.key))
    # else: stale or duplicate write -> drop (idempotent)
```

Insert, which requires allocating a new slot and updating match tables, is delegated to the control plane — a pragmatic admission that the data plane is a poor allocator. The paper notes that data-plane insertion is possible (e.g., with d-left hashing) but wastes precious on-chip memory [2].

### 4.2 Routing queries through the chain: (R2)

Chain structure is enforced by **routing**, not by end-host discipline. The control plane installs forwarding rules so that write packets for a key are steered head → replica* → tail, while reads go directly to the tail. Because chains are per-*key-range* (data is partitioned across chains by consistent hashing), each switch participates in many chains simultaneously, acting as head for some ranges, replica for others, and tail for still others. The chain is thus a *virtual topology* overlaid on the physical fabric by match–action entries — a striking inversion in which the routing table *is* the replication configuration.

### 4.3 Ordered multi-switch transactions across chains

A single key's writes are serialized by its chain, but real coordination workloads need **multi-key** atomicity: acquiring two locks, or updating a configuration group atomically. NetChain's data plane handles each key independently, so multi-key transactions must be composed above the per-key primitive. The in-network transaction literature has explored this directly: **P4DB** offloads full OLTP transaction processing — pipelined, abort-free execution of multi-operation transactions — onto a programmable switch, treating the switch as an additional database node with half-RTT access latency [6].

The ordering primitive that makes such composition tractable is the same one NOPaxos identified: if the network *orders* requests (OUM sequence numbers, or chain order per key), then multi-key atomicity reduces to deterministic execution in a globally agreed order, without distributed commit coordination. In NetChain's setting, a client can implement an ordered multi-key transaction by issuing per-key writes with a shared transaction sequence number and having each chain apply them in that order — a construction whose safety rests on the same monotonic-version invariant as §4.1, generalized across keys. The price is the familiar one: transactions spanning chains cannot be made atomic in a single data-plane pass without either a two-phase discipline or a single serialization point, which is why systems like P4DB centralize execution on one switch [6].

### 4.4 Session-numbered failure recovery: virtualization and failover

Switches fail. When a chain switch dies, NetChain must splice in a replacement and resume service *without* allowing pre-failure writes to corrupt the new chain. The mechanism is **virtualization with session numbers** [2]:

1. **Failure detection** is control-plane driven (heartbeats/timeouts), since the data plane cannot reliably distinguish a dead switch from a slow one.
2. The controller computes a new chain (replacing the failed switch), **increments a session number**, and installs the new chain configuration with the new session epoch.
3. Every query packet carries the session number of the chain configuration it was issued against. A switch drops any packet whose session number does not match its *currently installed* session — stale writes from the old epoch can never be applied to the new chain, even if they were delayed in flight during the failover window.

This is the data-plane analogue of view numbers in Viewstamped Replication or ballot numbers in Paxos: an epoch that totally orders configurations, so that at most one configuration is ever "active" from any switch's perspective. The session number lives in the same register file as the key-value data, checked in the same single pipeline pass, so failover safety costs no additional round trips in the data plane.

The protocol's elegance is that it confines the expensive work (detection, reconfiguration) to the control plane while keeping the safety check (session match) in the fast path — the same division of labor that makes chain replication itself attractive.

## 5 Empirical Results / Proofs

### 5.1 Measured results (NetChain prototype)

The NetChain prototype ran on **four Barefoot Tofino switches** and four commodity servers, compared against ZooKeeper [1]:

| Metric | NetChain (data plane) | ZooKeeper (server) | Improvement |
|---|---|---|---|
| Read/write latency | sub-RTT (as low as ½ RTT) | multiple RTTs | ~10–100× lower |
| Throughput | line-rate, switch-limited | server-CPU-limited | orders of magnitude higher |
| Failure recovery | session-numbered reconfiguration | leader election + log replay | graceful, no client-visible stall |

The headline result: clients experience only their own software-stack delay plus datacenter network delay — coordination latency becomes *scale-free*, independent of the number of replicas, because adding switches to a chain adds pipeline hops measured in hundreds of nanoseconds, not server round trips.

NOPaxos, by complementary measurement, showed that network ordering alone (OUM) brings a replicated system within **2% throughput and 16 µs latency of an unreplicated baseline** [4] — strong evidence that the residual cost of replication, once ordering is offloaded, is negligible.

### 5.2 Proof sketch: safety of session-numbered chain replication

We sketch the safety argument combining §§4.1 and 4.4. Model each switch *s* as holding `(session_s, {(k, seq_{s,k}, val_{s,k})})`.

- **Lemma 1 (monotonicity).** `seq_{s,k}` is non-decreasing over time, since updates require `pkt.seq > stored`.
- **Lemma 2 (session fencing).** A switch applies a packet only if `pkt.session = session_s`. After reconfiguration installs session `e+1`, no packet from epoch `e` is ever applied.
- **Lemma 3 (chain order).** Within an epoch, every applied write for key *k* traverses switches in chain order, so the tail applies a subsequence of what the head applied, in the same relative order.

> **Theorem:** *Reads served at the tail are linearizable within each session epoch, and no write from a superseded epoch is ever visible after failover.*

*Proof sketch.* Within an epoch, Lemma 3 plus Lemma 1 give per-key linearizability: the tail's sequence is a subsequence of the head's in order, and reads see the latest applied write. Across epochs, Lemma 2 ensures the new chain starts from state transferred under controller supervision (the replacement switch is populated from a surviving replica before the session cutover), and stale in-flight writes from the old epoch are fenced. ∎

A machine-checked version of this argument is expressible in TLA+; the core invariant is two lines:

```tla
\* Safety invariant: tail state is a prefix-consistent projection of head state
ChainSafety == \A k \in Keys :
    /\ tailSeq[k] \in 0..headSeq[k]
    /\ session[tail] = session[head] \/ session[tail] = session[head] + 1
    \* stale-epoch writes never applied after cutover
    /\ \A p \in AppliedWrites : p.session = session[p.switch]
```

## 6 Limitations

1. **Bounded state.** On-chip SRAM is measured in tens of megabytes; a NetChain deployment stores thousands to low millions of small key-value items, not a general-purpose database. Workloads must be *coordination-shaped* (small values, hot keys).
2. **Restricted computation.** The P4 pipeline forbids loops, unbounded iteration, and complex arithmetic in the fast path. Protocols must be expressible as single-pass match–action logic with register read-modify-write — which rules out, e.g., cryptographic verification or log-structured merge in the data plane.
3. **Control-plane dependence for membership.** Failure detection, chain reconfiguration, insert allocation, and delete garbage collection all require the controller. The data plane is autonomous only within a fixed configuration epoch; every reconfiguration is a control-plane round trip.
4. **No Byzantine tolerance.** NetChain assumes trustworthy components [2]; a compromised switch can forge sequence numbers or sessions. In-network consensus currently targets the crash-fault datacenter, not adversarial settings.
5. **Multi-key atomicity is not free.** As §4.3 notes, per-key chains compose into transactions only with additional machinery (shared transaction sequencing or a centralized executor like P4DB [6]).
6. **Transport assumptions leak.** The sequence-number discipline handles reordering and duplication but not *partitioned* chains; a network partition that splits a chain still requires control-plane intervention, and the CAP tradeoff is unchanged — only its latency constant is improved.

## 7 Conclusion

NetChain, NetPaxos, and NOPaxos together demonstrate a single deep idea: **ordering and agreement are separable, and ordering belongs in the network**. NetPaxos showed Paxos could live in switches; NOPaxos showed that network-provided ordering (OUM) makes replication nearly free; NetChain showed that chain replication maps onto the P4 data plane so completely — storage in registers, chain order in routing tables, transport anomalies absorbed by sequence numbers, failures fenced by session epochs — that a coordination service can run at line rate with sub-RTT latency.

The research frontier this opens is not "faster consensus" but *consensus as infrastructure*: once agreement is a packet-processing primitive, every application can afford strong consistency where it previously settled for eventual. The hard constraints — bounded memory, a loop-free computational model, control-plane-mediated reconfiguration — define the design space for the next decade of in-network systems. The switch is no longer just the network's muscle; it is becoming part of its mind.
