# The Purely Functional Software Deployment Model: Content-Addressed Storage, the Derivation Calculus, Lazy Evaluation, and Flake-Based Reproducibility in Nix

## Abstract

Software deployment remains among computing's most failure-prone activities: nominal dependency specifications, mutable global installation prefixes, and unvalidated build environments produce systems that cannot be reproduced, rolled back, or reasoned about [1][2]. This thesis presents a deep technical treatment of **Nix**, the purely functional package manager originated by Eelco Dolstra at Utrecht University in 2003 [2][4], whose core idea is to give software deployment pure-function *semantics*. We formalize the content-addressed Nix store, where every component's path derives from a 160-bit cryptographic hash of its complete build closure [4]; the derivation calculus, a low-level build specification language evaluated to fixed-point `.drv` artifacts; and the lazy, dynamically typed Nix expression language generating those derivations. We analyze the NixOS module system as a typed configuration-merging algebra [3], flakes with their transitive lock graph [6][7], and the signed binary-cache substitution protocol unifying source and binary deployment [5]. We prove the key safety invariant — a built store path is immutable with an exactly known dependency closure — and close with the model's limitations and its implications for supply-chain security [8].

---

## 1. Introduction

The deployment of software — transferring components from a build environment to the machines where they execute — is deceptively simple to describe and notoriously hard to perform safely. Dolstra's thesis catalogues conventional deployment's pathologies: dependency specifications that are not validated; *inexact* nominal specifications; no side-by-side versions; interference through shared mutable prefixes; no rollback; non-atomic upgrades; administrator-only deployment; the missing link between binaries and their build provenance; and the artificial schism between source and binary deployment [8].

Each defect shares a root cause: *mutable shared state*. A conventional manager (RPM, dpkg) maintains a global component database and mutates shared directories such as `/usr/lib`, making installation an *effectful* operation whose outcome depends on ambient machine state — the class of reasoning problems purely functional languages were designed to eliminate. Dolstra, de Jonge, and Visser drew the analogy explicitly: the deployment pathologies resemble "the lack of referential transparency in imperative programming languages," whose absence "is a principal feature of purely functional languages such as Haskell" [3].

Nix embodies that analogy: a build is a **pure function** from inputs to outputs, and every output is *named* by a cryptographic hash of its inputs. Because a component's name encodes everything required to reproduce it, components never change after building, never collide, and never interfere. The remainder of this thesis reconstructs the model formally: the store (§4.1), the derivation calculus (§4.2), the lazy expression language (§4.3), compositional configuration via modules and flakes (§4.4), and the signed substitution protocol (§4.5).

## 2. Background

### 2.1 The imperative deployment model

Imperative managers identify packages *nominally* — by name and version constraint, e.g. `Requires: python >= 2.4` [3]. Constraints resolve against a global registry at install time, but the binary records only the nominal requirement — not the precise dependency instance present at build time. The same source built on two machines may thus link different libraries, with no record sufficient to reproduce either build [3]. Specifications are typically *not validated*: a package invoking `python` builds on the developer's machine and fails mysteriously on a clean one [3]. Upgrades mutate shared files in place; concurrent library versions cannot coexist in `/usr/lib`; post-install scripts run arbitrary code as administrator.

### 2.2 Functional programming as a design discipline

In a purely functional language, an expression's value depends only on its subexpressions — no mutable variables, no ambient state, no observable effects. This *referential transparency* enables equational reasoning. Dolstra's thesis argues deployment deserves the same discipline; his ICSE 2004 paper calls it "imposing a memory management discipline on software deployment": as collectors manage heap objects by reachability, Nix manages components by reachability from *GC roots* (profiles, running processes), not explicit uninstallation [9]. Unreachable components are collected; reachable ones never mutate.

### 2.3 Antecedents

Nix has antecedents: Vesta (Compaq SRC) pioneered immutable repositories and a functional build language, and Dolstra's thesis situates Nix against it [1]; GNU Stow showed per-package prefixes symlinked into a shared view, without hashing or purity. Nix's distinction is the *combination* — cryptographic naming, lazy specification, sandboxed realization, signed substitution — into one model scaling from a package to a distribution [3].

## 3. Methodology

This thesis is a reconstructive formal treatment grounded in primary sources: Dolstra's dissertation [1], the LISA 2004 [2] and ICFP 2008 [3] papers, Dolstra's 2019 retrospective on the Nix DSL [4], the Tweag series on content-addressed Nix [5], and the flake specifications [6][7]. Where the literature states a mechanism informally, we restate it as a definition or theorem and sketch the proof from documented behavior. Our analytical vocabulary:

- **Store**: the immutable directory `/nix/store` holding all components.
- **Store path**: `/nix/store/<hash>-<name>`, where `<hash>` encodes build inputs.
- **Derivation** (`.drv`): a serialized build specification — the "assembly instructions" of the system.
- **Realisation**: the act of building a derivation, producing store paths.
- **Closure**: the transitive set of store paths a component depends on.
- **Substitution**: fetching a prebuilt store path from a binary cache instead of building locally.

Our threat model for §4.5 assumes an adversary controlling the network between client and binary cache but not the cache's signing key, and builders that are *untrusted programs* confined by the sandbox.

## 4. Deep Dive

### 4.1 The Nix Store: Input-Addressed Naming as Purity Enforcement

The Nix store holds every component as an isolated `/nix/store/<hash>-<name>`, where `<hash>` is a **160-bit hash** (SHA-256 truncated to 20 bytes, base-32) over the *complete serialized build inputs*: sources, dependency store paths, builder script, system type, and all build environment variables [2][4].

Consequences:

1. **Immutability by construction.** The path *is* the hash of the inputs, so in-place modification is self-contradictory: modified content no longer matches its own name. The daemon enforces read-only permissions after realization.
2. **Side-by-side variants.** Builds differing in any input receive different hashes and coexist without interference — "dependency hell" is structurally impossible with no shared `/usr/lib`.
3. **Reproducibility as identity.** Two parties computing the same derivation compute the same store path *before building anything*. Agreement on the path is agreement on the entire build closure.

![Nix store path hashing with an input-addressed derivation graph](/thesis/ths_1788755470610_6026_nix-0.webp)
*Figure 1 — Derivation nodes hashed over their input closure yield input-addressed store paths.*

> **Theorem (Store path uniqueness).** Let `D₁` and `D₂` be derivations whose serialized input closures differ. Then `path(D₁) ≠ path(D₂)`, except with probability negligible in the 160-bit hash (birthday bound ≈ 2⁸⁰ work for a collision).

*Proof sketch.* `path(D) = H(serialize(inputs(D)))`; distinct serializations collide only by breaking `H`'s collision resistance. ∎

The components contributing to the hash preimage are summarized below.

| Input class | Examples | Effect on hash |
|---|---|---|
| Sources | tarballs, patches, builder scripts | Any byte change ⇒ new path |
| Dependencies | store paths of libraries, compilers | Transitive: rebuild cascades |
| Build instructions | builder path, arguments, env vars | Flag change ⇒ new path |
| Platform | `x86_64-linux`, `aarch64-darwin` | Cross builds isolated |
| Output name | package name/version string | Cosmetic, but hashed |

Garbage collection completes the analogy: the daemon deletes every store path not *reachable* from GC roots — user profiles, running processes, registered roots [9]. Uninstallation is *root removal*, not mutation; rollback re-adds an older root, always safe because old paths were never modified.

### 4.2 Derivations: A Low-Level Build Calculus

A **derivation** reifies the pure function "build this component" as a small text file (ATerm-derived serialization) at `/nix/store/<hash>-<name>.drv`, listing:

- `outputs`: the output names (usually just `out`, but also `dev`, `doc`, `bin`, …) and their *precomputed* store paths;
- `inputDrvs`: the derivations this build depends on, with the specific outputs required;
- `inputSrcs`: source files already in the store;
- `platform`, `builder` (an executable, typically a shell), `args`, and the full environment variable map.

Derivations bridge expression language and build daemon: the evaluator emits the `.drv` file, which the daemon "realize[s] (builds) … in a sandboxed environment" [5]. The evaluator never builds; the builder never evaluates. This phase separation is load-bearing: the complete build plan, and its hash, are known *before* compilation starts — exactly what enables binary substitution (§4.5).

A crucial refinement is the **fixed-output derivation** (FOD) used for fetching sources: the builder is granted network access (a controlled impurity), but the output path derives from the *expected content hash* (`outputHash`/`outputHashAlgo`), which the daemon verifies post-build, rejecting mismatches. FODs are thus **content-addressed** in the strong sense, while regular derivations are **input-addressed** — their path is a function of what went *into* the build, not what came out [5].

```nix
# A minimal derivation: the "hello world" of the derivation calculus.
derivation {
  name = "hello-2.12";
  system = "x86_64-linux";
  builder = ./builder.sh;          # copied into the store as an inputSrc
  args = [ ./hello-2.12.tar.gz ];
  PATH = "${coreutils}/bin";       # every tool referenced by store path
}
```

```bash
# Inspect the serialized build plan of any derivation:
$ nix show-derivation /nix/store/abc123...-hello-2.12.drv
```

Note the `PATH` line: every tool is named by store path, so a builder *cannot* accidentally depend on ambient software. Undeclared dependencies are not merely discouraged — they are unnameable, and under the sandbox unreachable [3].

### 4.3 Lazy Evaluation and the Nix Expression Language

Nix expressions are written in a **dynamically typed, lazy, purely functional language** [3]: attribute sets (optionally `rec`), anonymous functions (`{ stdenv, fetchurl, … }: …`), lists, `let…in…`, `if…then…else`, `with`, interpolation (`"${…}"`), `inherit`. The key primitive is the builtin `derivation` function, mapping an attribute set describing a build to its `.drv` store path — the single point where the pure language touches the effectful world, and only by *describing* the effect.

Laziness is what makes the system scale: `nixpkgs` is one gigantic lazy attribute set, and `nix build nixpkgs#hello` forces only the thunks on the transitive path to `hello`'s derivation. The `callPackage` idiom — auto-filling a package function's formals from the enclosing scope — composes with laziness into a *modular* package set: overriding one dependency (an "overlay") re-thunks only packages that transitively mention it.

The sharp edges:

- **Strictness leaks.** `builtins.toJSON`, `builtins.hashString`, and interpolation force evaluation; deep strictness over huge sets (e.g. `builtins.attrNames pkgs`) can exhaust memory.
- **`with` scoping.** `with pkgs;` introduces dynamic-like scoping that defeats static reasoning about name resolution — widely considered a wart, avoided in modern nixpkgs.
- **Phase confusion.** *Import from derivation* (IFD) — evaluation depending on a build result — breaks the §4.2 phase separation, complicates caching, and is restricted under flakes.

> **Theorem (Evaluation determinism).** Closed Nix expressions always evaluate to the same value; a package's derivation is thus a pure function of the expressions and files in scope.

This is why flakes can *ban* the ambient impurities of the legacy model — no `NIX_PATH` lookups, no `builtins.currentTime`, no undeclared file access — without changing the language: purity was always the semantics; flakes merely enforce the hermeticity that the semantics promises [6].

### 4.4 The NixOS Module System and Flakes: Composition at Scale

NixOS extends the model to *entire operating systems*: kernel, services, `/etc` files, users — all one derivation built from Nix expressions, so a running machine is a realized closure with a bootloader entry pointing at it [3]. Composing thousands of configuration fragments requires its own discipline: the **module system**.

A module is `{ config, pkgs, lib, … }:` returning `{ options; config; imports; }`: *options* declare typed configuration points, *definitions* assign values, merged per type (lists concatenate, attrsets merge, scalar conflicts resolve by priority or fail). Pipeline: collect → merge → typecheck → `config` → system derivation [3].

![NixOS module system evaluation pipeline](/thesis/ths_1788755470610_6026_nix-1.webp)
*Figure 2 — Module option declarations merged through type-directed rules into one system derivation.*

**Flakes** (RFC 0049) solve the complementary problem: *which* Nix code is evaluated at all. A flake declares `inputs` (other flakes, pinned by URL) and an `outputs` function mapping them to packages, dev shells, and `nixosConfigurations` [6][7]. The companion `flake.lock` records the *transitive* closure of locked inputs — exact revisions and content hashes — in a graph supporting `follows` directives for diamond-dependency deduplication [6]. With a complete lock file, evaluation needs no network and no ambient state: the same flake at the same lock always yields the same derivations, and each input's `narHash` allows substitution from binary caches [6]. Flakes thus close the last open variable in the reproducibility equation — the *source* of the Nix expressions — just as the store hash closed the build inputs.

### 4.5 Binary Caches, Substitution, and the Trust Model

Local builds of all of nixpkgs would take days, so **substitution** resolves the tension: output paths are computable pre-build, letting the client fetch a prebuilt NAR (Nix Archive) for `/nix/store/<hash>-foo` from a *binary cache*. The cache replies with a signed `.narinfo` record: path, NAR hash, size, references, signature [5].

The trust model is deliberately narrow: caches sign narinfo records with Ed25519 keys (libsodium); the client verifies against locally configured `trusted-public-keys`. Under our threat model — adversary controls the network, not the signing key:

> **Theorem (Substitution integrity).** An accepted substituted path `p` was produced by a trusted-key holder for the derivation `D` with `path(D) = p`, unless the signature scheme is broken.

*Proof sketch.* The client verifies the Ed25519 signature over `(p, narHash, references, …)`, downloads the NAR, and checks `H(NAR) = narHash`. A network adversary can forge neither the signature nor the content. What is *not* guaranteed: that the cache built `D` correctly — the signature attests provenance ("this key holder claims this NAR realizes `p`"), not correctness. Reproducible builds are the complementary mechanism letting anyone *audit* the claim by rebuilding [8]. ∎

This yields Dolstra's elegant unification: source and binary deployment are the *same* operation — a "binary" install is a fast-forwarded realization of the identical derivation. The ASE 2005 work on secure sharing between untrusted users extends the idea multi-user: content-named, immutable paths let users share build results without trusting each other, the daemon mediating access [10].

## 5. Empirical Results and Proofs

### 5.1 Scale: Hydra and the nixpkgs corpus

The demanding empirical test is `nixpkgs` itself, built continuously by the **Hydra** farm and published to `cache.nixos.org` (NixOS 19.09: 960 contributors, 22,000 commits [4]). Each commit instantiates tens of thousands of derivations; successful realizations are signed and cached, so users overwhelmingly *substitute* rather than build. Content-addressed naming makes this sound: identical derivations yield identical paths for Hydra and user alike, so a cache hit is definitionally correct.

### 5.2 The core safety invariant, proved

We now state and prove the invariant on which every Nix deployment rests.

> **Theorem (Closure integrity).** Let `p` be a realized store path. Then (a) the contents of `p` are immutable for the lifetime of `p`; (b) the complete set of runtime dependencies of `p` — its *closure* — is computable from the store database without executing anything in `p`.

*Proof sketch.* (a) The daemon sets store paths read-only at realization; only the privileged daemon writes the store, so users cannot mutate `p` — any "modification" yields a new path `p' ≠ p` by the §4.1 uniqueness theorem. (b) At build time the daemon scans outputs for input store paths (hash rewriting) and records references in its database; `nix path-info -r` reads exactly this graph. Since the sandbox hides every undeclared store path, undeclared dependencies are invisible at build time and cannot appear at runtime outside the declared closure. ∎

Two deployment-level corollaries follow immediately:

1. **Atomic upgrades and rollbacks.** A NixOS generation is one store path (the "toplevel" derivation); switching generations is a bootloader pointer swap plus an atomic profile symlink update — never a partial mutation. Rollback re-selects the older generation, safe by immutability (a).
2. **Multi-user safety.** Unforgeable content-bound names let mutually untrusting users share `/nix/store` without interference; the daemon's trusted-substituter model extends this to the network [10].

### 5.3 Content-addressed derivations: the experimental frontier

The Tweag programme on content-addressed Nix [5] attacks the model's deepest remaining impurity: *input addressing* assigns different paths to byte-identical outputs whenever any input differed. With **content-addressed derivations**, output paths derive from the *output content hash*, and the build *registers a realisation* mapping `derivation!output → store path`. This enables *early cutoff*: a rebuild whose content hash matches a previous realisation lets downstream derivations — resolving identically — skip rebuilding entirely. The engineering is subtle (derivations build in "resolved" form [5]) and remains experimental: the completion of the arc from nominal, to input-addressed, to fully content-addressed deployment.

### 5.4 Supply-chain evidence

Recent supply-chain attacks provide the adversarial validation the model was designed for [8]. Three properties compose a defense-in-depth story absent from nominal managers: (i) *pinning by hash* — flake locks and FOD hashes make dependency confusion structurally impossible; (ii) *provenance by signature* — substitution is authenticated (§4.5); (iii) *auditability by rebuild* — anyone can re-realize a derivation and compare hashes, turning "trust me" into "verify me." Bootstrapping still requires trusting *some* key holder, but the trusted base shrinks from the entire mutable package universe to key management.

## 6. Limitations

Intellectual honesty requires stating where the model falls short of its own pure-function ideal.

1. **Builders are arbitrary programs.** A derivation is a pure *specification*, but its *builder* is an untrusted script that may embed timestamps or behave nondeterministically. Sandboxing confines the damage but cannot enforce determinism; bit-reproducible outputs demand builder discipline (`SOURCE_DATE_EPOCH`, deterministic ordering), an ongoing community effort. Fixed-output derivations *permit* network access by design — a principled impurity, but an impurity nonetheless.
2. **Evaluation is expensive.** Laziness makes giant `nixpkgs` tractable, but evaluating a NixOS closure still takes seconds to minutes and gigabytes of RAM; import-from-derivation punctures the eval/build phase separation and defeats caching.
3. **Input addressing is not content addressing.** Trivial input perturbations cascade into mass rebuilds and path churn (§5.3). Content-addressed derivations are the answer, but experimental, interacting subtly with signatures, remote builders, and the cache ecosystem.
4. **Flakes remain experimental.** RFC 0049 was drafted in 2020; years later, flakes are still gated behind an experimental flag, the CLI surface is still stabilizing, and lock-file churn in large monorepos is a real workflow cost [6][7].
5. **Cryptographic margins.** The 160-bit truncated hash offers a ≈2⁸⁰ birthday bound — comfortable today, but a narrower margin than full 256-bit addressing, and a deliberate trade-off for shorter, human-tolerable path names [4].
6. **Adoption impedance.** The learning curve is steep: a new language, a closures-not-packages mental model, and a store layout breaking decades of FHS assumptions. `patchelf`-style interpreter rewriting is a pragmatic concession to a `/usr/lib` world.

---

## 7. Conclusion

Nix shows software deployment — long treated as an inherently stateful art — admits a *denotational* treatment: a build is a pure function, a component is named by its inputs' hash, a system is the fixed point of a lazy functional program. From that idea flow atomic upgrades, trustworthy rollbacks, side-by-side variants, unprivileged installs, garbage-collected storage, and substitution with explicit, minimal trust assumptions. Modules and flakes compose the model from packages to distributions; content-addressed derivations point at the remaining gap to true content addressing.

The broader lesson is methodological. Where the industry answered deployment fragility with thicker layers of containers, golden images, and imperative orchestration — each reintroducing the mutable state it meant to tame — the purely functional model *removed* the state. Two decades after Dolstra's thesis [1], as supply-chain integrity becomes a first-order security concern [8], that removal looks less like academic elegance than engineering foresight. The pure function was the deployment primitive we needed all along.
