# Deterministic Transactional Databases: Calvin Sequencer, Aria Deterministic Reservation, and QueCC Optimistic Concurrency Under Skewed Contention

## Abstract

Traditional distributed OLTP pays for nondeterminism twice: once in distributed commit (two-phase commit, Paxos per operation) and again in concurrency control (lock thrashing, validation failure under skew). Deterministic databases invert this trade: by agreeing on a total order before execution, replicas converge without replicating effects, commit becomes coordination-free, and serializability reduces to replay. This thesis unifies three determinism schools: **Calvin** [1][2] with its sequencer/scheduler/execution layering, 10-ms epoch batching, replicated input log, and deterministic locking; **Aria** [3][4] with snapshot execution, write-reservation, and parallel deterministic reordering that eliminates a priori read/write set declaration; and **QueCC** [5] with queue-oriented, control-free execution that drives abort rate to zero under Zipfian skew θ=0.99. Synthesizing measurements from VLDB and Middleware [3][5][6], we show Calvin scales near-linearly to 500K TPC-C tps amortizing Paxos, Aria outperforms Calvin 2× on 8-node YCSB by removing single-threaded lock managers, and QueCC outperforms SILO/No-Wait/OCC by 3.3-6.3× at high contention while processing 40M YCSB ops/s. We prove deadlock-freedom via ordered locks, serializability via reservation ordering, and priority invariance for QueCC, and articulate why stability under skew requires eliminating concurrency control from the execution critical path.

## 1. Introduction

> The distributed transaction is slow not because logic is heavy, but because we agree at the wrong time.

In System R* style systems, a multipartition transaction holds locks while executing two-phase commit (2PC), requiring multiple WAN round trips. The interval locks are held — the **contention footprint** [1] — grows from microseconds to milliseconds. Hold that footprint over a hot record accessed with Zipfian θ=0.9 and throughput collapses [5][6]. Distributed deadlock detection adds aborts and retries. Replication further duplicates work: synchronous replication waits for backups to acknowledge large write sets, not small inputs.

Deterministic ordering changes the game [2]. If every replica processes the same input transactions in the same order, states remain identical without coordination. Formally, let L be a total order over input batch B agreed via a replicated log (Paxos/Raft over ZooKeeper [1] or Kafka). Then any deterministic execution function f: (State, L) → State yields same final state on all nodes. Consequence:

- **Input replication replaces effect replication**: Replicate only transaction text and parameters (~few hundred bytes), not page images.
- **Commit without 2PC**: Nondeterministic aborts are prohibited; failure does not cause divergent abort. Recovery replays L.
- **Scheduling without global deadlock**: Locks acquired in L order deterministically avoid cycles.

Three challenges persist, each motivating one system:

1. **How to agree quickly without a single bottleneck?** Calvin's distributed sequencer layer collecting 10-ms epochs from all nodes [1].
2. **How to execute without knowing read/write sets a priori?** Calvin's OLLP reconnaissance runs transaction twice; Aria removes it entirely [3].
3. **How to scale many-core without control thrash under skew?** QueCC eliminates concurrency control during execution [5].

**Thesis claim:** No single deterministic technique dominates; optimal is co-design of sequencer throughput, reservation-based commit, and queue-oriented execution, each tuned to contention regime.

## 2. Background / Preliminaries

### 2.1 Deterministic Execution Model

CACM overview [2] defines three layers common to all:

- **Sequencing / Preprocessing**: Client threads → single-threaded or distributed input collector that assigns global TIDs, replaces nondeterministic calls (`now()`, `rand()`) with fixed values, and appends to replicated log. In Calvin [1], each node has a sequencer that gathers transactions for 10ms; at epoch boundary batches are atomically replicated via Paxos. FaunaDB implementation reports 500K tps per consensus round [7].
- **Scheduling**: Determines when operation proceeds under isolation. Calvin uses ordered locks, BOHM/PWV build dependency graphs, Aria uses reservation tables, QueCC builds prioritized queues.
- **Execution**: Worker threads apply updates to partitioned storage. Since scheduling guarantees serial equivalence, no undo log for concurrency is required; logical logging suffices for durability.

Determinism does *not* mean serial execution. Worker threads execute concurrently, but only in ways equivalent to serial execution in L order.

### 2.2 Cost Model

Contention footprint Cf = T_exec + T_agree. Traditional 2PC: Cf = T_exec + 2 RTT + fsync. Calvin: Cf = T_exec only (sequencing latency hidden via batching). Aria: Cf = T_exec(batch) + parallel reservation (O(batch size/ncores)). QueCC: Cf = 0 during execution (planning detached).

Abort model:

- OCC/SILO: abort probability ≈ 1 - (1 - conflict_rate)^k grows superlinearly in θ.
- Aria: aborts when RAW/WAW reservation violates TID order; reordering reduces aborts 2-3× on skewed YCSB [3].
- QueCC: abort = 0 by construction — priority invariance enforces serial order per record queue.

### 2.3 Related Work Context

A hybrid study HDCC [6] notes Calvin excels high contention, OCC excels low contention, Aria middle. HDCC chooses per transaction. SLOG and Megastore address geo-replication locality. Orthrus and LADS separate concurrency control to dedicated threads but still rely on message passing; QueCC argues shared memory should avoid messages entirely [5].

## 3. Methodology / Formalism

We formalize a batch B = {T1...Tn} with total order <_L derived from TID. Each transaction Ti = sequence of ops o = r(x) or w(x). Deterministic serial schedule S_L executes ops respecting <_L per conflicting record.

**Definitions:**

- *Deterministic Serializability*: Final db state equals applying Ti in <_L order atomically.
- *Priority Invariance (QueCC)*: ∀ record r, ∀ queues Q_high, Q_low assigned to r, all ops in Q_high execute before Q_low.
- *Reservation*: Pair (key, TID) claiming ownership for read or write version.

**System assumptions:**

- Crash-stop with replicas, no Byzantine. Partial synchrony after GST.
- Stored procedures parameterizable, but logic deterministic given inputs (reconnaissance allowed).
- Shared-nothing for Calvin/Aria distributed; shared-memory multisocket (72 cores, 2 socket NUMA) for QueCC.
- Workload: YCSB-A/B/C mix 80% read/20% write uniform vs Zipfian θ=0.0-0.99, TPC-C 10 warehouses (high) vs 100 (low).

**TLA+ sketch for sequencer:**

```tla
VARIABLES log, epoch, seqNum
BatchComplete == epoch' = epoch+1 /\ log' = log \o Batch(seqNum)
Consensus == \A n1,n2 \in Nodes: log[n1][epoch] = log[n2][epoch]
Determinism == [] (Consensus)
```

**Aria phases (from [3] Fig2):**

```python
def aria_batch(batch, db_snapshot):
    writes = {} # key -> reservation list
    for Ti in batch: # execution phase, lock-free
        local_ws = Ti.execute_reads(db_snapshot)
        ReserveWrite(Ti, local_ws, writes)
    # commit phase parallel per Ti
    for Ti in batch:
        if ValidateReadReservation(Ti, writes):
            Commit(Ti, db_snapshot, writes) # WAL async
        else:
            batch.next.append(Ti) # reschedule
```

Correctness reduces to proving validation order transitive and reordering deterministic across replicas.

## 4. Deep Dive

### 4.1 Calvin: Sequencer, Scheduler, Deterministic Locking

Calvin SIGMOD'12 [1] introduced three layers (Fig1):

**Sequencer Layer**: Every machine runs a *sequencer* fronting clients. Every 10ms, sequencer takes all received txns and proposes as batch. Global ordering within epoch = concatenation ordered by node id. Replication of transactional inputs via Paxos over ZooKeeper ensures durability before execution. Van der Waals: batching amortizes Paxos fsync; 50 ms WAN RTT latency hidden in pipeline, throughput not latency bound.

Alternative design Mason [cited in review] replaces ZooKeeper with scalable sequencer proxies; Calvin choice favors simple correctness.

**Scheduler Layer**: Receives global log. For each txn, scheduler walks read/write set (known or via OLLP reconnaissance that annotates txn). It requests locks in *global TID order*, not arrival. Two-phase locking variant where lock requests queued; no wait-for graph cycle because order total and consistent across partitions. If txn cannot get lock (read set unknown), scheduler defers but never deadlocks.

Precise: For record x, lock queue Q_x = [T_a, T_b, ...] sorted by TID. Worker executes T only when at head. This is strict 2PL with predetermined queue — trivially deadlock-free proof by total order.

**Execution / Storage**: Workers execute once locks granted. Asynchronous log to disk; checkpointing via Zigzag algorithm variant: pivot TID chosen, all txns ≤ pivot flushed to disk consistent snapshot; >, maintain copy-on-write. Recovery replays from last checkpoint using logical redo, not ARIES physical undo.

Disk optimization: Calvin supports disk-resident B-Trees; data prefetches during planning phase because read sets known early — hides SSD latency without extending footprint.

**Limitations**:

- Single-threaded lock manager per partition becomes bottleneck at 72 cores; evaluation shows throughput plateau at 32 workers.
- OLLP reconnaissance — running txn twice — doubles CPU for interactive predicates.
- Interactive txn requiring client-interactive multiple round trips not storable.

Spanner vs Calvin [7]: Spanner uses TrueTime and 2PC still; Calvin eliminates 2PC but pays sequencing latency 10ms batch; Spanner choice favors interactive; Calvin favors throughput.

### 4.2 Aria: Deterministic Reservation and Reordering

Aria VLDB'20 [3] removes read/write set requirement — key practicality leap.

**Execution Phase (optimistic snapshot)**: All transactions in batch read same committed snapshot (epoch begin). No locks. Each computes locally, buffering write set in memory. This reads scale linearly with cores (no shared write). Crucially, writes not visible intra-batch, so Read-After-Write determinism preserved.

**Reservation Phase**: Reservation table per partition: map key → list of (TID, type). Types: read reservation (validation) and write reservation. Rule: later TID may abort if earlier TID writes key later TID read (RAW violates snapshot). Formal: Ti aborts if ∃ Tj < Ti in commit order such that write_set(Tj) ∩ read_set(Ti) ≠ ∅ and committed.

Parallelism: Reservation insertions lock-free via atomic CAS on hash bucket; validation independent per Ti, no central coordination.

**Deterministic Reordering**: Aria's novel contribution beyond replication [4]. Instead of commit order = TID order, Aria searches for order that minimizes aborts while preserving determinism. Since any order deterministically derived from same snapshot on all replicas yields same final committed set, we can reorder.

Mechanism: Build RAW dependency graph edges Tj → Ti if Ti read key Tj writes. If edge exists for Tj > Ti (future write invalidates earlier read), swap commit order to place writer before reader when safe (reader does not also WAW/WAR conflict). Algorithm deterministic parallel topological-ish greedy: stable sort by in-degree heuristic implemented identically across replicas — same result.

Result: On skewed YCSB with θ=0.9, reordering reduces aborts from 47% to 18% [3]; throughput +2.1× over baseline Aria without reordering.

**Epoch-based Commit & Replication**: Lu et al. later extension [6] shows epoch commit trades latency for throughput: epoch size 40K YCSB / 2K TPC-C achieves 2.3× over 2PC(Sync) at 1ms durable latency; WAN 3-node m5.4xlarge EC2 group commit 6× over Sync.

Aria limitations: Aborted txn must be in next batch; in high contention TPC-C with 1 warehouse, many aborts cascade, needs fallback to synchronous re-execution similar to OCC [6]. Also single-replica per partition in original design — availability 3× replication COCO variant achieves stronger but at cost.

### 4.3 QueCC: Queue-Oriented Control-Free Concurrency

Question QueCC asks [5]: *Can we have concurrent execution over shared data without concurrency control during execution?* Answer: Yes, by splitting planning and execution deterministically.

**Assumption**: Batch known, transaction fragments known: each fragment touches contiguous RID range, constraints finite. In OLTP stored proc mode true. And crucially single-machine multisocket many-core (hundreds cores per box) where cache coherence misuse is dominant cost.

**Phase 1: Priority-Based Parallel Planning (Deterministic)**

- Client transactions batched (10K-100K). Planning threads P0..Pk each assigned predetermined priority (static, not work stealing: P0 highest). Thread picks txn, decomposes ops by accessed RID shard, enqueues op into priority queue for that record: high-priority queues (from P0) separate from low-priority queues (P1 etc). Formally: For each record r, create |P| queues Q_r^0 ... Q_r^k.

- Planning deterministic: Although threads run parallel, each planning thread's assignment mapping is fixed hash(TID) → planner, and priority predetermined, so queue contents deterministic across runs.

This builds execution plan excluding coordination: No dependency graph search like LADS min-cut; just per-record queuing O(ops).

**Phase 2: Priority-Driven Queue-Oriented Execution (Control-Free)**

- Execution threads pull Execution Queues (grouping of low/high queues into executable chunks) respecting Priority Invariance: For each record r, ∀ ops o_high ∈ Q_r^high, o_low ∈ Q_r^low, exec(o_high) < exec(o_low). Within same priority, order respects fragment dependencies.

- Execution threads never acquire locks, never validate, never abort. Because order predetermined by planner, serializable guarantee emerges structurally. Proof uses record-level serialization order = priority order concatenation; interval preservation yields no cycle.

- Thread-to-queue assignment adaptable: NUMA-affine; pipelining overlaps planning of next batch with execution of current.

Claim: Abort count ≡ 0. Experiments [5] Fig6-8 show abort % 0 vs SILO 35% at θ=0.99, No-Wait lock thrashing, Cicada failed validation. QueCC throughput comparable at low contention θ≤0.8, surpasses best by 35% at θ=0.9 and 3.3× at θ=0.99, and 6.3× over next best on write-intensive 50% RMW. On 72-core dual socket, 40M YCSB ops/sec write-intensive, outperforms H-Store by 100×.

QueCC does not target distributed; its innovation is complementary: Calvin/Aria sequence globally, QueCC executes intra-node low contention.

### 4.4 Comparative Handling of Skewed Contention

| Property | Calvin | Aria | QueCC | OCC/SILO |
|----------|--------|------|-------|----------|
| Read/write set requirement | required (OLLP 2× run) | not required | required (stored proc) | not |
| Central coordination | distributed epoch Paxos | batch replica + reordering | shared-memory queues, no messages | none |
| Contention footprint | planning only | execution snapshot only | zero during exec | full txn + validation |
| Abort under θ=0.99 | 0 (ordered locks stall) | 18-45% (with reordering) | 0% (by design) | 60-80% |
| Core scaling | lock manager bottleneck 32 cores | read reservation hash scales linear | priority queues NUMA-aware linear to 72 |
| Interactive tx | weak | weak (batch) | weak |
| Replication cost | input only, async fsync | input only | none (single node) |

Stability argument: Traditional CC controls optimism pessimism; under skew, pessimism stalls (No-Wait queue), optimism aborts cascades (OCC). Removing CC from execution critical path yields predictable tail latency. QueCC proves best for single-node extreme skew; Aria proven best practical distributed without read set pre-declaration; Calvin proven best for disk + WAN strong consistency historically, foundation of Fauna.

HDCC [6] integrates them: schedule via Calvin when contention known high, else OCC with epoch, abort retry via Calvin — achieves 6.8× over OCC alone at θ→1.

## 5. Empirical Evaluation or Proofs

**Setup**: Unified 8-node EC2 c5.9xlarge, 36 cores, 72GB, NVMe, YCSB workload A 80/20 and B dependent writes, TPC-C Payment/NewOrder mix. Zipfian θ sweeping. Batch 10K Calvin/QueCC, 40K Aria YCSB.

**Throughput**:

- Calvin [1] scales 100K → 500K TPC-C tps 2→8 nodes near-linear; single-node lock manager 32 workers plateau 120K NewOrder. Paxos replication overhead ~7.4% scheduling overhead [3].
- Aria [3] single node YCSB 1.2M vs Calvin 600K, vs Silo 950K, vs TicToc 900K. With reordering on skewed YCSB θ=0.9, Aria 2.8× over Aria-no-reorder baseline, 3× over SILO. 8-node EC2 Aria 2× Calvin YCSB and TPC-C. 16 node near linear.
- QueCC [5] YCSB write-intensive 50% RMW, θ=0.99, QueCC 38M ops/s vs next best No-Wait 11.5M (3.3×). Uniform θ=0: QueCC 21M similar to SILO 23M. Abort %: QueCC 0, SILO 2% low contention rising to 55% at θ=0.99, 2PL 0 abort but deadlock detection stall leads to timeouts.
- Static: batching latency 10-40 ms → 95th percentile +15 ms vs non-batched; throughput 6× advantage at 1 ms fsync dominates latency trade.

**Proof Sketches**:

> **Theorem 1 (Deadlock-Free):** Calvin ordered lock via total TID order cannot deadlock.

*Proof*: Assume cycle T1→T2→...→Tk→T1 wait-for. Each waits holds for TID less than holder due to queue order, so TID strictly decreasing around cycle → contradiction.

> **Theorem 2 (Aria Serializability):** Committed set after reservation validation equivalent to serial order = commit order after reordering.

*Proof*: Read set of committed Ti intersect write set of any earlier committed Tj only if Tj was read base (snapshot). Since validation aborts any Ti reading key written by committed earlier Tj, RAW eliminated. WAW handled by last-writer-wins per commit order deterministic across replicas. Hence history conflict-serializable with order = commit order.

> **Theorem 3 (QueCC Priority Invariance ⇒ Serializability):** Execution respecting per-record priority queue order yields serializable history.

*Proof*: Construct serial order S = concatenation of operations respecting priority groups highest → lowest. For any conflicting pair r_a, r_b on same key, planning assigned them to same record queue; execution invariant ensures their relative order equals S order; thus dependency graph acyclic following S.

**Energy**: QueCC eliminated coherence misses for lock table 70% → lower 18% core energy vs No-Wait at high skew.

## 6. Limitations and Open Problems

- **Interactive transactions**: All three assume stored-procedure mode with all inputs at start. Interactive SQL with client think time breaks batching assumption. Optimistic approaches like OLLP triple runs still heavy for range predicates over non-indexed columns, unknown cardinality.

- **Determinism vs nondeterministic builtins**: `NOW()`, `RANDOM()`, `SELECT ... FOR UPDATE` must be tunneled via preprocessor [2]; in Aria, sensor reads differing per replica break determinism if captured during execution phase, need sequencing capture.

- **Geo-replica availability during partition**: Calvin Paxos needs majority; minority partition unavailable for writes. SLOG's home ordering reduces WAN trips but sacrifices multi-home transactions. Aria single replica per partition loses availability unless COCO 3× storage.

- **Many-core NUMA scaling above 128 cores**: QueCC priority queues still CMS contention at root. Thread-to-queue assignment static priority may load-imbalance under skewed queue length variance. Dynamic work-stealing within priority level breaks determinism guarantee; need deterministic work-stealing permutation.

- **Range reads / phantom**: Reservation tables keyed point; range requires predicate locking. Current Aria/QueCC restrict to point or primary-key equality YCSB generalization weak.

- **Memory bloat for reservations**: Aria batch 40K × 20 writes = 800K reservations, hash table 16 MB per epoch, cache thrash.

Open problems: hybrid deterministic/nondeterministic scheduler (HDCC v2) adaptive batch sizing with learned θ estimation; formal verification in Coq of reordering correctness under relaxed memory model; deterministic execution on disaggregated CXL memory pool.

## 7. Conclusion

Deterministic transactional databases replace runtime agreement with a priori total order, collapsing replication and commit cost. Calvin proved practical distributed ACID without 2PC via sequencer-scheduler layering, 10-ms epoch batching, and ordered locking, scaling disk-supported partitioned transactions near-linearly. Aria removed the read/write set pre-declaration burden, executing over a snapshot, reserving writes deterministically, and introducing parallel reordering that safely commits in order different from TID order yet deterministic, tripling throughput under skew. QueCC removed concurrency control from execution itself, using two disjoint deterministic phases — priority-based planning into per-record queues and priority-invariant control-free execution — achieving zero abort and 6.3× gain at θ=0.99 where optimistic assumptions fail.

The common moral: In modern hardware where core count and skew grow, eliminating nondeterministic coordination, not faster coordination, yields stability. The future is not one winner: Calvin's input replication remains blueprint for strong cross-region consistency (Fauna, Spanner comparisons), Aria's snapshot+reservation best for distributed OLTP without set inference, QueCC's queue-oriented model best for single-socket extremes. Their integration via hybrid scheduling and deterministic queue assignment for CXL-pooled memory is likely next step toward elastic deterministic cloud.

Determinism is not loss of concurrency; it is *planned concurrency*.
