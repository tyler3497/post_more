# From Causality to Silicon: The RC11 Repaired C++ Memory Model, ARMv8 and RISC-V RVWMO Hardware Models, and Mechanized Compilation via the IMM Intermediate Model

## Abstract

Modern concurrent software rests on a tower of formal memory models: language-level models such as the C++20 memory model, hardware models such as ARMv8 and RISC-V RVWMO, and intermediate models that mediate between them. This thesis unifies that tower. We begin with the repaired model **RC11** of Lahav et al., which fixes the broken sequential-consistency axioms of C++11 and formalizes the *catch-fire* semantics that turn data races into undefined behavior while restoring the DRF-SC guarantee [1]. We analyze the litmus tests **WRC** and **IRIW** that separate multicopy-atomic architectures from their non-multicopy-atomic predecessors, and the *out-of-thin-air* read problem, still resisting complete formalization [5]. We examine the revised multicopy-atomic ARMv8 axiomatic and operational models of Pulte et al. [2] and the RISC-V RVWMO specification [6], detailing C++-to-hardware fence mappings. We introduce the **IMM** intermediate model of Podkopaev et al. [3] and its machine-checked compilation-correctness proofs, and describe **GenMC**'s exploration-based verification under these models [4]. We conclude that convergence on multicopy atomicity, together with mechanized metatheory, has made weak memory a tractable engineering discipline.

## 1. Introduction

A *memory consistency model* answers one question with unusual precision: which values may a load return in a concurrent execution? The answer matters because it is the contract between four parties — the programmer, the compiler, the language, and the silicon — and each party exploits the contract's weakness. Programmers want the illusion of sequential consistency (SC) [8]; compilers want freedom to reorder, eliminate, and merge accesses; hardware wants freedom to speculate, buffer, and forward. The history of the C++11 memory model is the history of a contract that tried to serve all four parties and, as Batty et al. first formalized [5] and Lahav et al. later demonstrated [1], failed in subtle ways: its SC axioms admitted neither the intended Power compilation scheme nor even the DRF-SC guarantee it advertised.

This thesis reconstructs the modern settlement of that contract. Our central objects of study are:

1. **RC11** — the *repaired* C++ model (Lahav, Vafeiadis, Kang, Hur, Dreyer, PLDI 2017), which fixes SC, formalizes catch-fire semantics, and admits a Coq-verified compilation to Power [1].
2. **The revised ARMv8 model** — multicopy-atomic axiomatic and operational models (Pulte, Flur, Deacon, French, Sarkar, Sewell, POPL 2018), proved equivalent to each other and co-developed with ARM's architecture revision [2].
3. **RISC-V RVWMO** — the RISC-V Weak Memory Ordering model, specified with normative prose, an Alloy axiomatization, and a herd formalization in the ISA manual [6].
4. **IMM** — the Intermediate Memory Model (Podkopaev, Lahav, Vafeiadis, POPL 2019), which modularizes compilation-correctness proofs from language models to hardware models weaker than x86-TSO, all mechanized in Coq [3].
5. **GenMC** — a stateless model checker (Kokologiannakis, Vafeiadis, CAV 2021) that verifies concurrent programs directly against axiomatic models such as RC11 and IMM [4].

Our thesis is that these five developments jointly constitute a *complete and mechanized* story: a language model strong enough for programmers (DRF-SC, no thin air), hardware models faithful to silicon (multicopy atomicity), and a verified bridge between them (IMM), with automated verification closing the loop (GenMC, herd7).

## 2. Background

### 2.1 Sequential consistency and its discontents

Lamport's sequential consistency requires that the result of any execution be the same as if the operations of all processors were executed in some sequential order, with each processor's operations appearing in program order [8]. Real multiprocessors violate SC routinely: store buffers delay the visibility of writes (x86-TSO), speculative and out-of-order execution reorder reads past writes, and — on pre-2017 ARM and on Power — writes could become visible to different threads at different times (*non-multicopy-atomicity*).

Language models therefore expose a spectrum of *access modes*. In C++20, `std::atomic` operations take a `memory_order`:

| C++20 `memory_order` | Guarantee |
|---|---|
| `memory_order_relaxed` | Atomicity only; no ordering |
| `memory_order_consume` | Orders data-dependent reads (deprecated in practice) |
| `memory_order_acquire` | Synchronizes-with a releasing write; no later read/write moves before |
| `memory_order_release` | No earlier read/write moves after; synchronizes-with an acquiring read |
| `memory_order_acq_rel` | Both directions (read-modify-write) |
| `memory_order_seq_cst` | Global total order consistent with happens-before |

Non-atomic (plain) accesses are the default, and the model treats races on them with extreme prejudice.

### 2.2 Axiomatic execution graphs

Following Batty et al. [5], a candidate execution is a graph whose vertices are memory *events* — reads `R_o(ℓ,v)`, writes `W_o(ℓ,v)`, read-modify-writes, and fences `F_o` annotated with access modes `o` — and whose edges are relations:

- `po`: program order within a thread;
- `rf`: reads-from, mapping each read to the unique write whose value it returns;
- `co`: coherence order, a total order per location over writes;
- `fr`: from-reads, defined as `rf⁻¹; co`, relating a read to writes coherence-after the write it read from.

Derived relations include *happens-before* `hb = (po ∪ sw)⁺`, where `sw` (synchronizes-with) connects a release write to an acquire read that reads from it (via release sequences), and the *extended coherence order* `eco = (rf ∪ co ∪ fr)⁺`. A model is a set of *consistency axioms* — typically acyclicity or irreflexivity constraints over these relations — and the program's behaviors are the executions satisfying them. The herd7 tool of Alglave et al. evaluates litmus tests against such axiomatic models written in the `.cat` language ("Herding Cats", TOPLAS 2014), enumerating all consistent executions.

### 2.3 Data races and catch-fire semantics

A *data race* in C++ is a pair of conflicting accesses (same location, at least one a write, at least one non-atomic) not ordered by happens-before. The C++ rule is draconian and deliberate:

> **Catch-fire semantics.** If any consistent execution of a program contains a data race, the program's semantics is *undefined behavior* — the execution may do anything, and the compiler owes the programmer nothing.

This harshness is a feature: it licenses compilers to treat non-atomic accesses as if sequentially consistent, applying aggressive reordering, common-subexpression elimination, and register promotion without proving race-freedom. The programmer's side of the bargain is the **DRF-SC guarantee**:

> **Theorem 1 (DRF-SC).** If every consistent execution of a program is data-race-free, then every observable behavior of the program is sequentially consistent.

C++11 famously failed to deliver this theorem as stated [1]; RC11 restores it.

## 3. Methodology

Our investigation is formal and tool-driven, following the methodology of the primary sources [1,2,3,4,6]:

1. **Axiomatic modeling.** We work with execution graphs and relation-algebraic axioms (`hb`, `rf`, `co`, `fr`, `eco`), expressed in the style of Lahav et al. [1] and encoded for machine checking in the herd7 `.cat` format.
2. **Litmus-test analysis.** We use the canonical tests **WRC** (write-to-read causality) and **IRIW** (independent reads of independent writes) as discriminators between models, and the **LB** (load buffering) family to study thin-air reads.
3. **Compilation-mapping verification.** We study the pointwise mappings from C++ access modes to ARMv8 (`LDAR`/`STLR`/`DMB`) and RISC-V (`lw.aq`/`sw.rl`/`fence`) instructions, and the mechanized correctness proofs that factor through IMM [3].
4. **Mechanized metatheory.** We rely on Coq developments: the RC11 compilation proof to Power [1] and the IMM framework (~33K lines of Coq) proving compilation from promising/C11/RC11 semantics to Power, ARMv7, and ARMv8 [3].
5. **Automated verification.** We describe GenMC's stateless exploration of execution graphs under RC11/IMM [4] and herd7's exhaustive litmus enumeration [2,6].

All theorems stated are theorems of the cited papers; all litmus outcomes reported are those established by the cited tools and specifications.

## 4. Deep Dive

### 4.1 The RC11 Axiomatization

RC11 retains the C++11 event vocabulary but restructures the consistency predicate. Let `E` be the set of events, `po` program order, and define synchronizes-with `sw` from release/acquire pairs (including release sequences and fences). Happens-before is `hb = (po ∪ sw)⁺`. The axioms are:

1. **Coherence.** `hb ∪ eco` is acyclic, where `eco = (rf ∪ co ∪ fr)⁺`. This single axiom subsumes C++11's scattered coherence conditions and forbids reading stale values in ways inconsistent with happens-before.
2. **Reads-from completeness.** Every read has exactly one `rf`-predecessor; every `rf` edge respects the value written.
3. **Atomicity of RMWs.** `fr; co` is irreflexive: no write may intervene in modification order between the read and the write of a read-modify-write.
4. **No thin air.** `po ∪ rf` is acyclic. This forbids the classic load-buffering outcome in which two threads read each other's not-yet-performed writes (see §4.3).
5. **Sequential consistency.** There exists a strict total order `S` over all SC events extending happens-before restricted to SC events and consistent with `eco`, with the additional *SC-reads restriction* that an SC read may not read from a write that is `S`-after a write it is `hb`-after. This replaces C++11's seven mutually inconsistent SC axioms.

The payoff is twofold. First, **Theorem 1** (DRF-SC) holds as stated — C++11's version failed because its SC axioms were simultaneously too strong (forbidding the intended Power compilation) and too weak (admitting non-SC behaviors in race-free programs) [1]. Second, the standard compilation schemes to Power are *sound*: Lahav et al. give Coq proofs that mapping release/acquire to `lwsync`/`sync` and SC to `sync`-fenced accesses preserves every RC11 behavior.

> **Theorem 2 (RC11 compilation to Power, [1]).** For the standard mapping (relaxed → plain accesses, acquire → `lwsync`+load / `cmp;bc;isync`, release → `lwsync`+store, SC → `sync`-fenced), every behavior of the compiled Power program is a behavior of the source RC11 program.


### 4.2 Litmus Tests: WRC, IRIW, and Multicopy Atomicity

Litmus tests are the experimental atoms of memory-model research. Two tests carry most of the conceptual weight.

**WRC (write-to-read causality).** Three threads:

```python
# WRC litmus test — forbidden outcome: r1 == 1 and r2 == 0
T0:  x = 1
T1:  r0 = x      # reads 1
     y = 1
T2:  r1 = y      # reads 1
     r2 = x      # reads 0  <-- forbidden under MCA / cumulativity
```

The question is *cumulativity*: does observing `y=1` force observing the causally prior `x=1`? Cumulative barriers (Power `sync`, ARMv8 `DMB`, RISC-V `fence rw,rw`) forbid the outcome for fenced/release-acquire accesses; plain relaxed accesses permit it everywhere.

**IRIW (independent reads of independent writes).** Four threads:

```tla+
---- MODULE IRIW ----
\* IRIW: forbidden outcome is r0=1 /\ r1=0 /\ r2=1 /\ r3=0
VARIABLES x, y
T0 == x' = 1
T1 == y' = 1
T2 == r0' = x /\ r1' = y   \* observes x=1, y=0
T3 == r2' = y /\ r3' = x   \* observes y=1, x=0
====
```

Two readers disagree about the *order* in which two independent writes became visible: T2 sees `x` before `y`, T3 sees `y` before `x` — possible only under **non-multicopy-atomicity**, where writes propagate to different threads at different times. Allowed on Power and pre-2017 ARMv7; forbidden on x86-TSO, ARMv8 (revised), and RISC-V RVWMO.

The discriminator table summarizes the landscape:

| Model | WRC (relaxed) | WRC (rel/acq + cumul. fence) | IRIW | LB (`r=42`) |
|---|---|---|---|---|
| Sequential consistency | ✗ | ✗ | ✗ | ✗ |
| x86-TSO | ✗ | ✗ | ✗ | ✗ |
| C++11 / RC11 | ✓ | ✗ | ✓ | C++11 ✓ / RC11 ✗ |
| Power | ✓ | ✗ | ✓ | ✓ |
| ARMv7 (pre-2017) | ✓ | ✗ | ✓ | ✓ |
| **ARMv8 (revised, MCA)** [2] | ✓ | ✗ | ✗ | ✗ |
| **RISC-V RVWMO** [6] | ✓ | ✗ | ✗ | ✗ |

(✓ = outcome allowed, ✗ = forbidden.) The decisive architectural shift of the last decade is the industry-wide convergence on **multicopy atomicity**: ARM revised ARMv8 to a multicopy-atomic model precisely because non-MCA behavior was never exploited by implementations yet complicated every formalization [2]; RISC-V's RVWMO was specified multicopy-atomic from the start [6].

### 4.3 Out-of-Thin-Air Reads and the No-Thin-Air Axiom

The most notorious open problem in language memory models is the *out-of-thin-air* (OOTA) read: a value that appears in an execution without any write ever producing it. The canonical example is load buffering with a fabricated value:

```haskell
-- LB+fake: can r1 == r2 == 42 with no write of 42 anywhere?
t0 :: Thread
t0 = do r1 <- load x      -- reads 42 ??
        store y r1
t1 :: Thread
t1 = do r2 <- load y      -- reads 42 ??
        store x r2
```

No hardware produces `42` here — the outcome requires a *causality cycle* in which each read is justified by a write that is itself justified by the read. Yet axiomatic models that permit LB-shaped reorderings (C++11) could not exclude this outcome without also excluding legitimate compiler optimizations; any syntactic "dependency" can be optimized away, so dependency-tracking is no defense.

RC11's answer is axiom 4: **`po ∪ rf` acyclic**. In the LB outcome above, `po` edges run `Rx → Wy` and `Ry → Wx` while `rf` edges run `Wx → Rx` and `Wy → Ry`, forming a cycle — forbidden. This is the *no-thin-air* guarantee: every value read must be traceable through `rf` edges to a write that does not causally depend on the read. It is strictly stronger than C++11 and matches all observed hardware.

The *general* OOTA problem remains open: control-dependency and speculation cycles can still fabricate values past `po ∪ rf` acyclicity. Responses include the *promising semantics* of Kang et al. (POPL 2017) and the *event-structure* model of Chakraborty and Vafeiadis (POPL 2019); the committee's pragmatic stance (Boehm's N3786/N3710) is that compilers must simply never introduce OOTA.

### 4.4 Compilation Mappings: C++20 Atomics to ARMv8 and RISC-V

The mappings below are the standard ones proved correct in [1,2,3,6]; each must ensure every hardware-observable behavior of the compiled program is already a source-program behavior (compilation *soundness*).

**C++ → ARMv8 (AArch64).** ARMv8 provides `LDAR` (load-acquire) and `STLR` (store-release) with release/acquire semantics, plus `DMB ISH` full barriers:

| C++20 operation | ARMv8 mapping |
|---|---|
| `load(relaxed)` | `LDR` |
| `store(relaxed)` | `STR` |
| `load(acquire)` | `LDAR` |
| `store(release)` | `STLR` |
| `load(seq_cst)` | `LDAR` |
| `store(seq_cst)` | `STLR` |
| `fence(acquire)` | `DMB ISHLD` |
| `fence(release)` | `DMB ISHST` |
| `fence(seq_cst)` | `DMB ISH` |
| RMW `exchange(acq_rel)` | `LDAR`/`STLR` loop (`LDAXR`/`STLXR`) |

Because ARMv8 is multicopy-atomic, `LDAR`/`STLR` alone suffice for SC loads/stores — no trailing fence is needed, unlike Power. The mapping's correctness rests on the equivalence between the axiomatic and operational ARMv8 models proved in [2].

**C++ → RISC-V (RVWMO).** RISC-V's `A` extension annotates loads/stores with acquire/release bits (`.aq`/`.rl`), and the base ISA provides `fence` with predecessor/successor read/write sets:

| C++20 operation | RISC-V mapping |
|---|---|
| `load(relaxed)` | `lw` |
| `store(relaxed)` | `sw` |
| `load(acquire)` | `lw.aq` |
| `store(release)` | `sw.rl` |
| `load(seq_cst)` | `fence rw,rw; lw.aq` |
| `store(seq_cst)` | `sw.rl; fence rw,rw` |
| `fence(seq_cst)` | `fence rw,rw` |
| AMO `swap(acq_rel)` | `amoswap.w.aqrl` |

The surrounding `fence rw,rw` instructions restore full sequential consistency for SC accesses, compensating for the fact that `.aq`/`.rl` bits alone provide only RCpc-style ordering. These mappings appear in the RISC-V manual's Appendix A.5 and were model-checked against the Alloy formalization of RVWMO [6].

In Haskell-like pseudocode, the mapping is a pointwise instruction selection:

```haskell
compile :: MemOrder -> Access -> [AArch64]
compile Relaxed   (Load r x)  = [LDR r x]
compile Acquire   (Load r x)  = [LDAR r x]
compile Release   (Store x r) = [STLR x r]
compile SeqCst    (Load r x)  = [LDAR r x]
compile SeqCst    (Store x r) = [STLR x r]
compile SeqCst   Fence        = [DMB ISH]
compile _         Fence       = []  -- relaxed/acquire/release fences
                                   -- need DMB ISHLD/ISHST per table above
```

The subtlety — why mechanized proofs matter — is that *soundness is not compositional by inspection*: a plausible mapping can fail on a four-thread litmus test no human would think to check. The IMM proofs [3] check exactly this, exhaustively over the model's axioms.

### 4.5 IMM: The Intermediate Memory Model

Proving compilation correctness directly from a language model (RC11, promising semantics) to a hardware model (Power, ARMv7, ARMv8) is a formidable proof-engineering task: the two sides speak different languages (language-level `hb`/`sw` vs. hardware-level propagation and cumulativity). **IMM** (Podkopaev, Lahav, Vafeiadis, POPL 2019) [3] factors the proof through an *intermediate* model:

```
  Language model (RC11 / Promising)
        |  proved in Coq
        v
  IMM (intermediate axiomatic model)
        |  proved in Coq
        v
  Hardware model (Power / ARMv7 / ARMv8)
```

IMM's events carry modes `{rlx, acq}` for reads, `{rlx, rel}` for writes, and `{acq, rel, acqrel, sc}` for fences. Its consistency predicate is deliberately *close to hardware*: acyclicity of `po ∪ rf` (no thin air, as in RC11), coherence over `eco`, and fence-induced ordering, but *without* language-level concepts like release sequences or SC-reads restrictions. The key metatheorems, all mechanized (~33K lines of Coq), are:

> **Theorem 3 (Language → IMM, [3]).** Compilation from the promising semantics (and from C11/RC11) to IMM is sound: every IMM behavior of the compiled program is a behavior of the source program.

> **Theorem 4 (IMM → Hardware, [3]).** Compilation from IMM to Power, ARMv7, and (revised) ARMv8 is sound.

By composition, the full language-to-silicon chain is verified — the first machine-checked compilation-correctness results for models weaker than x86-TSO. IMM's design lesson is methodological: *introduce the right intermediate abstraction and the hard proof decomposes into tractable, reusable lemmas*. Subsequent work has extended the pattern (Promising 2.0 → IMM, WeakestMO → IMM).

## 5. Empirical Results and Formal Proofs

Theory in this area is validated by *exhaustion*: litmus tests enumerated by tools, and proof assistants checking every case the human might miss.

**herd7 litmus enumeration.** The revised ARMv8 models of [2] were validated by exhaustively checking the possible behaviors of a loop-unrolled Linux kernel lock implementation against both the axiomatic and operational models, confirming their equivalence on the test corpus; the operational model is integrated into the rmem exploration tool with a web interface. The RISC-V manual's Appendix A works through litmus executions (MP, WRC, IRIW, LB variants) against the RVWMO axioms, showing precisely which `ppo`/`rf`/`co`/`fr` edges forbid each outcome, and ships a suite of over seven thousand litmus tests [6].

**GenMC verification.** GenMC (Kokologiannakis & Vafeiadis, CAV 2021) [4] is an LLVM-based *stateless* model checker: it explores execution graphs directly, using dynamic partial-order reduction to visit each distinct execution exactly once. Parametric in the memory model (RC11, IMM, LKMM), it verifies lock-free data structures — the clients of the §4.4 mappings — against the full tower. Its optimal DPOR ("TruSt", POPL 2022) is sound and complete within the bound while never exploring equivalent executions twice.

A typical GenMC target is a C++ lock-free structure using exactly the atomics of §4.4:

```rust
use std::sync::atomic::{AtomicUsize, Ordering};

// Treiber stack push: release/acquire pairing à la RC11 sw edges
pub fn push(stack: &AtomicUsize, node: *mut Node) {
    unsafe { (*node).next = stack.load(Ordering::Relaxed).cast(); }
    let mut head = stack.load(Ordering::Relaxed);
    loop {
        unsafe { (*node).next = head as *mut Node; }
        match stack.compare_exchange_weak(
            head as usize, node as usize,
            Ordering::Release,   // sw edge to Acquire poppers
            Ordering::Relaxed,
        ) {
            Ok(_) => break,
            Err(h) => head = h as *mut u8,
        }
    }
}
```

Under RC11, the `Release` store synchronizes-with any `Acquire` load that reads it, establishing `hb` and making the node's initialization visible — the exact guarantee Theorem 1 promises to race-free programs, and exactly what GenMC verifies execution by execution.

**Mechanized proof scale.** The IMM Coq development is roughly 33,000 lines covering language→IMM and IMM→hardware for three architectures [3]; RC11's artifact proves the Power scheme [1]. These are not pencil proofs — exhaustive case analysis is exactly where weak-memory proofs fail, as C++11's history shows.

**The convergence result.** The headline empirical finding across [1,2,3,6] is *convergence*: ARMv8, RISC-V RVWMO, and (morally) RC11's hardware-facing fragment agree on the discriminating tests — IRIW forbidden (multicopy atomicity), WRC forbidden under cumulativity, LB's fabricated values forbidden (no thin air). The remaining disagreements are confined to corners no implementation exploits.

## 6. Limitations

The tower does *not* deliver everything:

1. **Out-of-thin-air, still.** RC11's `po ∪ rf` acyclicity forbids the classic LB fabrication, but the general OOTA problem — values emerging through control-dependency and speculation cycles — has no accepted complete solution. The promising semantics and event-structure models are proposals, not consensus, and C++20's standard text still relies partly on normative discouragement rather than a watertight axiom.
2. **Mixed-size and byte-granular accesses.** The axiomatic treatments model accesses at a fixed granularity; real hardware and compilers operate on bytes, and mixed-size RMWs introduce behaviors the clean event model does not capture.
3. **Beyond regular memory.** Instruction fetches, page-table walks, virtual-memory effects (`FENCE.I`, `SFENCE.VMA`), I/O memory, and persistent-memory orderings are excluded from RVWMO's formalization [6] and from IMM; the Linux kernel memory model handled by GenMC is a separate, ongoing formalization effort.
4. **Bounded verification.** GenMC is a *bounded* checker: loops must be unrolled, recursion bounded. Unbounded correctness still requires deductive verification (e.g., separation logics over RC11), which remains labor-intensive.
5. **Performance vs. strength.** The mappings in §4.4 are *sound* but not always *optimal*: full `DMB ISH`/`fence rw,rw` barriers around every SC access cost cycles, and production compilers invest heavily in fence-elision analyses whose correctness arguments live outside the verified tower.
6. **Silicon conformance.** The models describe what the architecture *permits*; whether a particular chip conforms is a testing question (litmus runs on hardware), not a proof. Errata happen.

## 7. Conclusion

A decade of work has transformed weak memory from folklore into a mechanized engineering discipline. **RC11** repaired the language contract: catch-fire semantics for races, DRF-SC for the disciplined, no-thin-air for the skeptical, and a verified path to Power [1]. **ARMv8's revision** and **RISC-V's RVWMO** converged the hardware contract on multicopy atomicity, each with dual axiomatic/operational characterizations proved equivalent [2,6]. **IMM** factored the language-to-silicon correctness argument through a reusable intermediate model, machine-checked end to end [3]. And **GenMC** and **herd7** turned the models into push-button tools that enumerate behaviors and find bugs [4].

The open frontier is now clear: a fully satisfactory treatment of out-of-thin-air reads, extension to virtual memory and persistency, and deductive logics that scale to real systems code. But the methodology — axiomatic models, litmus-driven validation, intermediate models, mechanized proof — is settled. The next memory model will be born verified.
