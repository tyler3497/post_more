# Machine-Checked Formal Verification at Scale: Dependent Type Theory, Proof Automation, and the Engineering of Verified Systems

## Abstract

Machine-checked formal verification has matured from an academic curiosity into an engineering discipline that produces artefacts of unprecedented assurance: compilers whose machine code is proved to preserve source-language semantics, operating-system kernels whose C implementations are proved to refine abstract specifications, and mathematical libraries comprising hundreds of thousands of mechanically checked theorems. This thesis unifies these achievements through dependent type theory, the logical foundation that turns proofs into programmable objects amenable to mechanical checking. We examine the Lean 4 proof assistant and its mathlib ecosystem as a modern synthesis of interactive proving and metaprogrammable automation [6][7]; the CompCert certified C compiler as the canonical application of compositional forward-simulation proofs [1][2]; and the seL4 microkernel as the flagship of refinement-based verification, where a three-level proof links an abstract Isabelle/HOL specification through an executable prototype down to parsed C code [4][5]. Comparing proof architectures, automation regimes, and the economics of proof engineering at scale, we close with a critical assessment of trusted computing bases, specification fidelity, and the intrinsic limits of verification.

---

## 1 Introduction

Software is the load-bearing infrastructure of modern civilization, and it is, by any honest measure, riddled with defects. Testing, the industry's dominant quality instrument, samples a vanishing fraction of a program's state space. As Dijkstra observed, testing can show the presence of bugs but never their absence. For systems where failure is measured in lives or billions of dollars — avionics, medical implants, cryptographic infrastructure, operating-system kernels — sampling is not enough. We need *proof*: a mathematical argument that a program satisfies its specification in every possible execution, checked not by fallible human referees but by a machine.

Machine-checked formal verification delivers exactly this. A program's semantics is written as a mathematical definition inside a proof assistant; the desired properties are stated as theorems; and every logical step is validated by a small, trustworthy kernel. Three intellectual currents have converged to make this practical at industrial scale. First, **logical foundations**: dependent type theory and the Curry–Howard correspondence, which identify proofs with programs and make proof checking a decidable computation. Second, **proof automation**: tactics, elaborators, and metaprogramming frameworks that compress person-years of manual reasoning into reusable procedures. Third, **flagship artefacts**: the CompCert certified C compiler [1], the seL4 verified microkernel [4], and the Lean mathematical library mathlib [7], which together demonstrate that verification scales from kernels of logic to kernels of operating systems.

---

## 2 Background

The architecture of every trustworthy proof assistant descends from Milner's **LCF** (Logic for Computable Functions): proofs are values of an abstract datatype `thm` whose constructors are exactly the primitive inference rules of the logic. Arbitrary user code — tactics, decision procedures, even machine-learning-guided search — may manipulate proof states freely, but a theorem value can only be produced by the kernel. Soundness therefore reduces to the correctness of a few thousand lines: the **de Bruijn criterion**. A proof script may be megabytes long; what matters is that the checker is small enough to audit.

The logical engine inside most modern kernels is some variant of **dependent type theory**. The Curry–Howard correspondence identifies propositions with types and proofs with programs:

| Logic | Type theory |
|---|---|
| Proposition | Type |
| Proof of a proposition | Term (program) inhabiting the type |
| Implication | Function type |
| Universal quantification | Dependent function type |
| Proof checking | Type checking |

Under this identification, *proof checking is type checking*, and type checking in these theories is decidable. The Coq proof assistant implements the Calculus of Inductive Constructions; Isabelle/HOL implements classical higher-order logic in the LCF tradition; Lean implements a dependent type theory with quotient types and proof irrelevance, rebuilt from scratch in its fourth version as a self-hosting system in which the elaborator, tactics, and even the compiler are written in Lean itself [6].

Program verification adds Floyd–Hoare logic to this substrate: a triple *{P} c {Q}* asserts that command *c*, started in a state satisfying *P*, ends in a state satisfying *Q*. Deductive verification scales Hoare logic to real languages via weakest preconditions, separation logic for heap reasoning, and refinement calculi for stepwise development.

---

## 3 Methodology

This thesis is a comparative case study. We select three artefacts — Lean 4 with mathlib, CompCert, and seL4 — because each is the most complete representative of a distinct verification *style*: foundational library building, translation correctness, and refinement of an imperative implementation. Our evidence is drawn from primary sources: the system-description papers, user manuals, and published proof developments [1][2][3][4][5][6][7][8], cross-checked where independent summaries exist.

We compare the artefacts along four axes: (i) **logical architecture** — the kernel, the trusted computing base, and the axioms admitted; (ii) **proof technique** — simulations, refinements, and inductive invariants; (iii) **automation regime** — how much of the proof burden is discharged by tactics and decision procedures versus manual guidance; and (iv) **economics** — proof size relative to code size, checking time, and defect yield.

## 4 Deep Dive

### 4.1 Dependent Type Theory: The Logical Substrate

Dependent type theory derives its power from a single idea: *types may depend on values*. The dependent function type, written in Lean as `(x : A) → B x`, generalizes both the ordinary function type and universal quantification: a term of this type is simultaneously a function and a proof that *B* holds for every *x*. Dually, the dependent pair type generalizes existential quantification. Inductive families such as length-indexed vectors push the idea further, baking invariants into types so that ill-formed states become unrepresentable:

```lean
inductive Vec (α : Type u) : Nat → Type u where
  | nil : Vec α 0
  | cons {n : Nat} : α → Vec α n → Vec α (n + 1)

theorem append_length {n m : Nat} (xs : Vec α n) (ys : Vec α m) :
    (xs.append ys).length = n + m := by
  induction xs with
  | nil => simp
  | cons _ _ ih => simp [ih, Nat.succ_add]
```

Several design decisions distinguish the major theories. **Universe polymorphism** stratifies types into levels `Type 0 : Type 1 : Type 2 ...` to avoid Girard's paradox, the type-theoretic analogue of Russell's. **Definitional equality** — what the kernel decides by computation, including unfolding definitions — is distinguished from **propositional equality**, which requires explicit proof; this separation is what keeps type checking decidable while proofs remain expressive. **Proof irrelevance** collapses all proofs of a proposition into one, enabling efficient proof handling. Lean's kernel admits exactly three axioms beyond the core theory — propositional extensionality, quotient soundness, and choice — which together recover classical reasoning while remaining consistent relative to set theory [6]. Everything else, including the vast tactic framework, is untrusted code that must ultimately produce kernel-checkable proof terms.

> Theorem: *Type checking in the core theory is decidable.* Consequently, any purported proof can be validated by the kernel in finite time, and no tactic, however clever or buggy, can smuggle a false theorem past it. This is the precise content of the de Bruijn criterion.

### 4.2 Proof Automation: From Tactics to Metaprogramming

A tactic is a program that transforms a proof goal — soundness is guaranteed because tactics can only assemble theorems through kernel primitives. Early LCF tactics were simple combinators; modern frameworks are full metaprogramming environments. Lean 4 exposes its internals through a tower of monads — `MetaM` for metavariable management and unification, `TermElabM` for term elaboration, `CommandElabM` for top-level commands — so that tactics are ordinary Lean programs with access to the elaborator's state [6]. A tactic author can inspect goals, synthesize terms, invoke unification, and register custom syntax, all inside the same language used for the proofs themselves.

Elaboration is where most automation lives. When the user writes an incomplete term, the elaborator inserts **metavariables** for the missing pieces, propagates type information bidirectionally, and solves the resulting unification constraints — a process that quietly discharges enormous numbers of routine obligations. On top of elaboration sit layered search procedures:

- **`simp`**: ordered rewriting with congruence closure, driven by discrimination-tree indexing over tens of thousands of lemmas;
- **`aesop`**: best-first proof search combining safe and unsafe rule applications with backtracking;
- **`omega`**: a complete decision procedure for linear integer arithmetic (Presburger arithmetic);
- **`decide`**: proof by evaluation for any proposition with a `Decidable` instance, reducing proof to computation.

A further paradigm is the **hammer**: premise selection via machine learning, dispatch to external automated theorem provers, and reconstruction of the discovered proof inside the kernel. Isabelle's Sledgehammer pioneered this architecture; Lean's `hammer` tactic ports it. Finally, **proof by reflection** proves a decision procedure correct once and then applies it by computation — the verified-procedure pattern that makes `decide` scale.

```lean
-- Automation discharging arithmetic and rewriting obligations
theorem poly_bound (x : Nat) (h : x < 10) : x ^ 2 + 3 * x < 130 := by
  have h2 : x ^ 2 < 100 := by nlinarith
  omega
```

### 4.3 CompCert: Semantic Preservation by Compositional Simulation

A verified compiler addresses a foundational anxiety: every property proved of source code is void if the compiler miscompiles it. CompCert, developed by Leroy and collaborators in Coq, is a realistic optimizing C compiler — supporting most of ISO C99 with a formally verified core — accompanied by a machine-checked proof that compilation preserves program semantics [1][2].

The proof's backbone is **forward simulation**, proved independently for each of the compiler's roughly twenty passes. Every intermediate language — CompCert C, Clight, Cminor, RTL, LTL, Linear, Mach, and finally assembly — is given a formal small-step operational semantics over a block-and-offset memory model. For a pass from language *S* to language *T*, the verification establishes a relation between source and target states such that each source step is matched by zero or more target steps:

> Theorem: *Forward simulation.* If source state *s* is related to target state *t*, and *s* steps to *s′*, then *t* steps in zero or more steps to some *t′* related to *s′*.

Simulations compose: chaining the per-pass simulations yields an end-to-end theorem relating C source to assembly. The final statement is carefully qualified, because C itself is a treacherous language [2]:

> Theorem: *Semantic preservation (CompCert).* If compilation of program *P* succeeds and produces *Q*, then every observable behavior of *Q* — terminating, diverging, or going wrong — is admitted by the source semantics of *P*, except that the compiler may *improve* behavior by replacing undefined or erroneous executions with defined ones (for instance, by deleting a division whose result is unused).

Three caveats from the user's manual are worth stating plainly [2]: the compiler may fail rather than miscompile; it may resolve nondeterministic evaluation order as it pleases; and it may convert runtime errors into defined behavior. None of these weaken the guarantee that matters: *a source program proved free of undefined behavior compiles to a target program with exactly the source's observable behavior.* The trusted computing base is correspondingly narrow but nonzero: the Coq kernel, the extraction mechanism, the assembler and linker, and the hardware — a TCB analyzed explicitly in later work [3], which also records the subtle cross-logic concern that CompCert's Coq-based guarantees and a client's Isabelle-based proofs rest on different formalizations of C.

### 4.4 seL4: Refinement from Abstract Specification to C

Where CompCert verifies a *translation*, seL4 verifies an *implementation*: the seL4 microkernel — some 8,700 lines of C plus 600 lines of assembly — is proved in Isabelle/HOL to correctly implement its specification [4]. The proof is organized as a **three-level refinement tower**:

1. **Abstract specification (A):** a high-level operational model in higher-order logic — deliberately nondeterministic, total, and obviously correct;
2. **Executable specification (E):** a detailed functional prototype, translated from a working Haskell model into Isabelle/HOL, deterministic enough to run;
3. **C implementation (C):** the actual kernel C code, automatically parsed into Isabelle/HOL and lifted through the Simpl intermediate language into a shallow embedding by the AutoCorres tool.

Two large refinement proofs connect the levels [5]. The *abstract-to-executable* step (*R_A*) is a data refinement: an abstraction relation maps concrete states to abstract ones, and every concrete transition is shown to correspond to an abstract transition preserving the relation. The *executable-to-C* step (*R_C*) relates the functional model to the imperative C semantics via a heap correspondence, handling pointer reasoning, machine-word arithmetic, and the C memory model explicitly. Composing them yields the project's headline theorem:

> Theorem: *The C implementation of seL4 refines its abstract specification.* Every behavior of the binary produced from the verified C code is a behavior permitted by the abstract model.

The proof's assumptions are stated with unusual honesty: correctness is assumed of the compiler, the assembly routines, the boot code, cache and TLB management, and the hardware — everything else is derived [4]. Later work extended the guarantee from functional correctness to integrity, authority confinement, and information-flow noninterference, and pushed verification down toward the binary. The economics are striking: over 200,000 lines of Isabelle proof script, and a defect yield of 144 bugs found in an early version of the C code plus roughly 150 issues each in the design and specification — verification paid for itself in bugs that testing had missed.

```haskell
-- Executable specification style: kernel as a state monad over abstract state
type Kernel = StateT KernelState (Either SyscallFault)

invokeEndpoint :: Endpoint -> MessageInfo -> Kernel ()
invokeEndpoint ep msg = do
  st <- get
  case lookupEndpoint ep st of
    Nothing  -> throwFault Fault_InvalidCap
    Just tcb -> do
      deliverIPC tcb msg
      reschedule
```

### 4.5 Proof Engineering at Scale

Large verification projects behave like large software projects, and they demand the same engineering discipline. The **de Bruijn factor** — the ratio of formal proof size to informal proof size, typically estimated around four — quantifies the tax of formality. mathlib, the community mathematical library for Lean, manages this tax through software-engineering practices transplanted into mathematics: strict naming conventions, continuous integration that rebuilds the entire library on every change, automated style linters, and a review culture in which hundreds of contributors maintain a single coherent development [7]. The result is a library of hundreds of thousands of theorems that still checks in reasonable time on commodity hardware.

Two trends are reshaping the economics. First, **independent checking**: the Lean4Lean project built a second, complete verifier for Lean 4 inside Lean itself, capable of checking all of mathlib while running within a modest factor of the reference C++ implementation's speed — and it opens the path to verifying the verifier against a formalized metatheory, shrinking the oldest worry in the TCB [8]. Second, **proof maintenance**: as libraries evolve, proofs break; research on proof repair, semantic versioning of lemmas, and regression-proof CI aims to make formal developments as refactorable as ordinary code.

## 5 Empirical Results and Proof Artefacts

The table below compares the three flagship efforts on the axes introduced in Section 3. Figures are orders of magnitude drawn from the primary reports; all three projects have grown since their landmark publications.

| System | Code verified | Proof size | Proof-to-code ratio | Headline result |
|---|---|---|---|---|
| CompCert | C compiler, ~20 passes | Tens of thousands of lines of Coq | High (compiler + semantics) | Semantic preservation; code within ~7–12% of GCC -O1/-O2 [1] |
| seL4 | 8,700 lines C + 600 asm | 200,000+ lines Isabelle/HOL | ~20:1 | C refines abstract spec; 144 implementation bugs found [4][5] |
| mathlib | Library (no runtime code) | Hundreds of thousands of theorems | N/A (pure mathematics) | Entire graduate curriculum formalized; independently rechecked [7][8] |

```python
# Verification economics: tracking proof-to-code ratios across snapshots
snapshots = [
    ("CompCert 1.0 (2006)", 30000, 40000),
    ("seL4 (SOSP 2009)", 9300, 200000),
    ("seL4 (2024, extensions)", 12000, 480000),
]
for name, code, proof in snapshots:
    print(f"{name:28s} proof/code = {proof/code:5.1f}x")
```

Three patterns emerge. First, *ratio tracks semantic subtlety, not just size*: seL4's ratio dwarfs CompCert's because kernel invariants over heaps, capabilities, and concurrency-adjacent state are harder than per-pass simulations over well-structured intermediate languages. Second, *defect yield is front-loaded*: the seL4 proof found its 144 bugs early, during the first serious confrontation between code and specification — verification acts as an unusually thorough design review. Third, *performance need not suffer*: CompCert's near-GCC code quality [1] and seL4's competitive IPC latency refute the folk belief that verified systems are slow systems.

## 6 Limitations

Verification's guarantees are only as strong as its assumptions, and an honest account must state them.

**The trusted computing base.** Every proof rests on unverified ground: the proof kernel's implementation (mitigated but not eliminated by independent verifiers such as Lean4Lean [8]), the extraction or code-generation path, the compilers that build the tools, the hardware and firmware, and — in Lean's case — the three classical axioms admitted by the kernel [6]. The elaborator, which turns surface syntax into kernel terms, is among the largest and least verified components; a soundness bug there could in principle admit a false proof. TCB analysis is therefore a first-class verification activity, not an afterthought [3].

**The specification gap.** A verified system satisfies its *formal specification*, not its *informal intent*. If the seL4 abstract model omits a security property the designers cared about, the proof is silent. If CompCert's formal C semantics diverges from a programmer's mental model of C, verified compilation preserves the wrong thing. Gernot Heiser's critique sharpens the point: CompCert's Coq logic and seL4's Isabelle logic are different formal systems with independently formalized C semantics, so naively composing their guarantees does not yield a fully verified stack without bridging work [3].

**Economics and brittleness.** Verification remains expensive — multi person-decades for the flagships — and proofs are brittle under change: modifying a verified codebase can break proofs far from the edit site. Until proof maintenance is as routine as code maintenance, verification will lag behind rapidly evolving systems.

**Fundamental limits.** Gödel's incompleteness theorems forbid a system from proving its own consistency; every kernel assumes the consistency of its logic. Rice's theorem and the undecidability of rich semantic properties mean the interesting obligations can never be fully automated — human insight remains load-bearing. Concurrency, weak memory models, and liveness properties remain frontier territory where the proof techniques are far less mature than for sequential safety.

None of these limitations diminishes what has been achieved; they delimit it. A verified compiler does not promise your program is correct — it promises the compiler did not introduce the bug. That narrower promise, kept with mathematical certainty, is already transformative.

---

## 7 Conclusion

Dependent type theory turned proofs into programs; LCF turned programs-that-prove into trustworthy checkers; tactics and metaprogramming turned checking into an engineering discipline; and CompCert, seL4, and mathlib turned the discipline into artefacts — a compiler that cannot miscompile, a kernel that cannot deviate from its model, a library of mathematics no referee need re-examine [1][4][7]. The three styles compose conceptually: refinement connects implementations to specifications, simulation connects translations to sources, and automation connects human insight to machine-checked detail.

The research frontier is the *verified stack*: a verified application, compiled by a verified compiler, running on a verified kernel, checked by a verified verifier — each link's assumptions discharged by the next link's guarantees, with the residual TCB driven toward hardware and logic alone [3][8]. Neural proof search and large-scale premise selection promise to shift the automation frontier further, converting more of the mathematician's and engineer's intuition into kernel-checked evidence. The trajectory of the last two decades suggests a simple moral: where correctness matters most, proof will eventually replace testing — not because testing is useless, but because, for the load-bearing parts of civilization's infrastructure, sampling was never enough.
