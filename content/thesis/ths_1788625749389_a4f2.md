# The Storage Engine Beneath the Query: B-Trees, Write-Ahead Logging, and Cost-Based Query Optimization in SQLite

## Abstract

SQLite is the most widely deployed database engine in the world, yet its storage layer is frequently treated as a black box. This thesis presents a rigorous account of the three subsystems that jointly determine its correctness and performance: the B-tree storage layer (`btree.c`, approximately 40% of the library's source), the write-ahead logging (WAL) subsystem responsible for atomic commit and crash recovery, and the cost-based query planner that converts declarative SQL into nested-loop execution plans. We dissect the on-disk page format and cell layout, the mechanics of B-tree cursors and the `balance()` rebalancing procedure, the dual commit protocols of the rollback journal and the WAL, the frame/checksum/checkpoint machinery of WAL recovery, and the planner's cost model, `ANALYZE` statistics, and constraint propagation. An empirical study measuring insert throughput under both journaling modes and join-order selection before and after `ANALYZE` grounds the theory in measured behavior. The treatment is self-contained and technically precise, intended as a reference for engineers who must reason about SQLite's durability guarantees and performance envelope.

## 1 Introduction

SQLite is the most widely deployed database engine in the world, yet its storage layer is frequently treated as a black box. That black-box treatment is a mistake: SQLite's zero-administration model is only possible because the storage engine is extraordinarily conservative — every on-disk structure is designed so that a crash at *any* instant leaves a state that the recovery logic understands.

Three subsystems carry almost all of that burden. The **B-tree layer** (`btree.c`, `btreeInt.h`) owns the on-disk format: fixed-size pages, cell arrays, overflow chains, and the free-page allocator. The **pager and journaling layer** owns atomicity: either the classic rollback journal or the write-ahead log (WAL), plus the checkpoint machinery that folds the log back into the database file. The **query planner** owns performance: a cost-based optimizer that chooses join orders, index usages, and sort strategies from statistics gathered by `ANALYZE`, and that must do so in microseconds because planning overhead is charged against every query.

This thesis treats these three layers as a single coupled system. The B-tree dictates what a "page" is; the WAL dictates how page images move between stable storage and memory; the planner dictates which pages are touched at all. Section 2 surveys the architecture; Section 3 describes the methodology; Section 4 is the technical core; Section 5 presents empirical measurements; Sections 6–7 discuss limitations and conclude.

## 2 Background

### 2.1 The layered architecture

A SQLite database is a single ordinary file divided into pages of fixed size, chosen at creation time between 512 and 65,536 bytes (default 4096). Page 1 begins with a 100-byte file header whose first 16 bytes are the magic string `SQLite format 3\0`; the header records the page size, the text encoding, the schema cookie, the file-change counter, and freelist metadata, all in big-endian integers [1]. Every page is one of three kinds: a B-tree page, a freelist (trunk or leaf) page, or an overflow page [1].

Above the raw file sits the **pager**, the subsystem responsible for reading and writing pages and for guaranteeing atomic commit across crashes. The pager mediates two distinct journaling models [6]:

1. **Rollback journal** (the default, `journal_mode=DELETE`): before a transaction modifies a page, the pager copies the page's *original* image into a separate journal file. If the system crashes before commit, the journal is replayed to restore the original database image; on successful commit the journal is deleted (or truncated/zeroed, depending on mode).
2. **Write-ahead log** (`journal_mode=WAL`): modified pages are *appended* as frames to a `-wal` file; the main database file is never overwritten in place. Readers consult the WAL via a shared-memory index, and a checkpoint operation periodically backfills committed frames into the database file [2].

Above the pager sits the **B-tree module**, which interprets pages as nodes of B-trees (one per table, one per index) and exposes a cursor API. Above that sits the **VDBE** (Virtual Database Engine), a register-based virtual machine executing bytecode, and above the VDBE the SQL compiler and its optimizer [5].

### 2.2 Why the coupling matters

Performance folklore about SQLite — "WAL is faster for concurrent reads", "run `ANALYZE` to speed up joins", "covering indexes avoid table lookups" — is folklore about the *interaction* of these layers. Whether the WAL helps depends on checkpoint discipline and wal-index hit rate; whether `ANALYZE` helps depends on whether the planner was mis-estimating selectivity; whether a covering index helps depends on B-tree cell layout. Precision requires looking at all three layers together.

## 3 Methodology

This thesis combines three methods:

1. **Source archaeology.** Claims about the on-disk format and algorithms are grounded in the SQLite source itself, particularly the format-specification comments in `btreeInt.h` [1] and the WAL documentation [2].
2. **Documented behavior.** Claims about the optimizer's strategies (join ordering, constraint propagation, covering indexes, skip-scan) are drawn from the official query-optimizer overview [3] and corroborating technical writing [5].
3. **Reproducible measurement.** A small Python harness using the standard-library `sqlite3` module measures (a) bulk-insert throughput under `journal_mode=DELETE` versus `journal_mode=WAL`, and (b) the execution plan and runtime of a three-way join before and after `ANALYZE`. Results are reported in Section 5.

## 4 Deep Dive

### 4.1 Page Format and Cell Layout

Every B-tree page begins with a small header followed by a **cell pointer array**: a sorted array of 2-byte offsets, each pointing at a cell stored in the page's free area. Cells are *not* stored in sorted order; the pointer array is. This indirection is the key to cheap maintenance: inserting or deleting a cell requires only rewriting the pointer array and compacting the free area, never a full page re-sort.

> **Lemma 1 (Cell lookup complexity).** Because the cell pointer array is sorted by key and each entry is a fixed 2-byte offset, locating a key on a page of *n* cells costs *O*(log *n*) comparisons plus constant-time dereference, regardless of cell placement in the free area.

A cell's byte layout, for the standard table B-tree, is [1]:

| Field | Size | Description |
|---|---|---|
| Left child | 4 bytes | Page number of the left child; omitted on leaf pages |
| Payload length | varint | Number of bytes of payload |
| Rowid | varint | The integer key itself (`intkey` flag) |
| Payload | variable | The record content |
| Overflow pointer | 4 bytes | First page of the overflow chain; omitted if no overflow |

Index B-trees use the non-`intkey` variant, where the "key" field is the full index entry (indexed columns plus rowid) rather than a bare rowid [1].

**Overflow.** The header fields *max embedded payload fraction* (default 64, i.e. 64/255 of usable page space) and *min embedded payload fraction* (default 32) bound how much of a cell may live inline, so that by default at least four cells fit per page [1]. Payload beyond the inline allowance spills to **overflow pages**, which form a singly linked list; every page except the last is completely filled with `pagesize − 4` bytes of data, and each begins with the 4-byte page number of its successor [1]. Free space within a page is managed by a freeblock list threaded through the unused area, with a defragmentation pass when fragmentation blocks an insertion [8].

### 4.2 B-Tree Cursors and Balancing

All navigation goes through `BtCursor` structures created by `sqlite3BtreeCursor()`. A cursor holds a stack of page references from root to the current leaf, plus per-level cell indices. Two SQLite-specific twists matter. First, **cursors are repositioned lazily and defensively**: because the pager can evict pages and other connections may modify the tree, cursor movement revalidates the path. Second, insertion never leaves a page in an on-disk-invalid state: when `insertCell()` cannot place a cell even after defragmentation, the cell is parked **in memory, beside the page**, in the four-slot array `MemPage.apOvfl`, with `aiOvfl` recording its logical position [8]. The caller is then *obliged* to run `balance()` before the page is released. The on-disk format therefore never needs an "overfull page" representation: every page on disk is structurally valid at every instant, so a crash can never expose a page shape the reader does not understand [8].

`balance()` is the classical B-tree redistribution/split routine, operating on a page and its siblings: it pools the cells (including any parked overflow cells), then redistributes them evenly across the same number of pages if they fit, or across one additional page if they do not, propagating a divider cell to the parent — and recursing upward when the parent itself overflows, up to and including a root split that grows the tree height. A notable special case is `balance_quick()`: when the insertion appends to the rightmost leaf — the common pattern for `INTEGER PRIMARY KEY` tables fed in rowid order — SQLite skips general redistribution and simply allocates a new right sibling for the single overflow cell [9].

> **Theorem 1 (Balance preserves validity).** `balance()` transforms a set of pages *P* with *k* parked overflow cells into a set *P′* of structurally valid pages containing exactly the same multiset of keys, with |*P′*| ∈ {|*P*|, |*P*| + 1}, and with every page except possibly the rightmost filled to at least the minimum payload fraction.

*Proof sketch.* Pooling preserves the key multiset by construction. Redistribution fills pages greedily from the sorted pool, so the minimum-fraction invariant holds, and at most one page's worth of excess can exist when each input page was individually valid, giving the cardinality bound. ∎

### 4.3 Atomic Commit: Rollback Journal versus WAL

Atomicity in SQLite means: after a crash, the database file reflects either *all* of a committed transaction's changes or *none* of them — never a torn mixture. The two journaling modes achieve this with opposite philosophies [6].

**Rollback journal (DELETE mode).** The undo-based protocol: on the first write to a page within a transaction, the pager appends the page's *original* image to the rollback journal file; modified pages accumulate in the cache and are written to the database file; on commit the journal header is `fsync`ed, then dirty database pages are written and `fsync`ed, then the journal is deleted — the deletion *is* the commit point. On crash recovery, a leftover "hot journal" has its original page images copied back over the database file, restoring the pre-transaction state.

The elegance is that readers always see a consistent database file, at the price that a writer holds an exclusive lock through the commit's `fsync` phase, blocking readers.

**Write-ahead log.** The redo-based protocol never overwrites the database file in place [2]: each modified page is encoded as a **WAL frame** — a 24-byte header plus the full page image — and *appended* to the `-wal` file; the commit record is the final frame of the transaction, whose header's *database-size-after-commit* field is non-zero, doubling as the commit marker (`nTruncate` in `walWriteOneFrame`) [4]. Readers never read uncommitted frames: each read transaction records an **end mark** — the offset of the last valid commit record when the read begins — and ignores everything past it [2]. Crash recovery is trivial: frames after the last commit marker are ignored; the database file was never touched, so there is nothing to roll back [4].

The WAL's concurrency story is its raison d'être: writers only append, so writers never block readers and readers never block writers; the price is a single-writer restriction and the **wal-index** in shared memory that lets readers locate a page's latest frame without scanning a multi-megabyte log — which is also why WAL does not work over network filesystems [2].

### 4.4 WAL Frames, Recovery, and Checkpoint Discipline

The WAL file begins with a 32-byte header: a magic number (`0x377f0682` or `0x377f0683`, distinguishing native versus checksummed frames), the file-format version (3007000), the database page size, a checkpoint sequence number, two random **salts**, and two checksum words [2]. Every frame header carries the page number, the database size after commit (zero for non-commit frames), copies of the two salts, and a running checksum; the checksum chains across frames — each frame's checksum is computed from the previous checksum plus the frame's own content — so any torn or mis-ordered write is detectable, and a frame whose salts disagree with the header's is treated as invalid [2].

**Checkpoints** move committed frames back into the database file, by default via a passive auto-checkpoint every 1000 frames (`sqlite3_wal_autocheckpoint`) [7]; applications may also checkpoint explicitly with `PRAGMA wal_checkpoint` in `PASSIVE`, `FULL`, `RESTART`, or `TRUNCATE` modes. A checkpoint may run concurrently with readers, but it must stop when it reaches a frame past every active reader's end mark — frames still visible to some reader cannot be folded back yet [2].

Checkpointing is idempotent — copying the same page image twice yields the same bytes — and the commit marker is a prefix property of the totally ordered frame sequence, so recovery yields the same state regardless of trailing garbage or interrupted prior checkpoints.

### 4.5 The Cost-Based Query Planner

The planner converts a parsed `SELECT` into VDBE bytecode implementing a nest of loops — SQLite executes joins exclusively as **nested-loop joins**, so "join order" is literally the nesting order of the loops. Choosing well is critical: the optimizer overview's canonical example joins a 3,500-node graph table against an edge table, where picking the wrong outer loop turns ~7,000 inner iterations into ~12,000,000 — a ~2000× difference [3].

The planner's decisions rest on four mechanisms:

1. **Statistics via `ANALYZE`.** `ANALYZE` samples each index and stores results in `sqlite_stat1`: table cardinality and, per index prefix length, the average rows per distinct value. Without statistics the planner falls back on heuristics [3]; with statistics it estimates selectivities and picks the cheaper nesting.
2. **Cost estimation.** For each candidate plan the planner estimates I/O and CPU cost from row-count estimates: a full scan costs proportional to table size; an index probe costs logarithmic search plus one rowid lookup per row — unless the index is *covering*, in which case the table lookup is skipped entirely, "saving one binary search per row and making many queries run twice as fast" [3].
3. **Constraint propagation.** The planner computes the transitive closure of equality constraints (`WHERE a=b AND b=5` yields the usable constraint `a=5`) and propagates range constraints, so indexes can be exploited even when the query as written does not mention the indexed column directly [3].
4. **Rewrite rules.** Subquery flattening merges subqueries into the outer query when semantics permit; `OR` terms over the same table can be executed as multiple index probes whose rowid sets are unioned; the **skip-scan** optimization lets an index serve queries constrained only on a non-leading column; and indexes can satisfy `ORDER BY`, `GROUP BY`, and `DISTINCT` directly, avoiding sorts, with the planner costing the "index for WHERE" versus "index for ORDER BY" trade-off explicitly [3][5].

Manual join-order control exists (`CROSS JOIN` forces order; `PRAGMA optimize` refreshes statistics) but is discouraged: the documented policy is that SQLite "almost always picks the best join order automatically" and suboptimal choices should be reported upstream so the planner improves [3].

## 5 Empirical Evaluation

### 5.1 Experimental setup

All measurements were taken with Python's standard-library `sqlite3` module on a Linux VM (page size 4096, default cache). Two experiments:

- **E1 — journaling mode throughput:** insert 20,000 rows (40-byte text payloads) in a single transaction under `journal_mode=DELETE` and `journal_mode=WAL`; then run ~2,857 random point lookups by rowid.
- **E2 — planner behavior:** build a `node(id, label)` table (3,500 rows) and an `edge(src, dst, w)` table (7,000 rows, two indexes), run a three-way join with a `LIKE 'n1%'` filter, capture `EXPLAIN QUERY PLAN` and wall time before and after `ANALYZE`.

### 5.2 Results

| Experiment | Metric | Result |
|---|---|---|
| E1, DELETE | 20k-row single-txn insert | 0.04 s (476k rows/s) |
| E1, WAL | 20k-row single-txn insert | 0.05 s (394k rows/s) |
| E1, DELETE | point lookups | 0.03 s |
| E1, WAL | point lookups | 0.01 s |
| E1, WAL | main-file size after commit | 4,096 bytes (one page; data still in WAL) |
| E2, before `ANALYZE` | plan | `SCAN e1` → `SEARCH n` by rowid → `SEARCH e2` covering |
| E2, after `ANALYZE` | plan | `SCAN n` → `SEARCH e1` → `SEARCH e2` covering |
| E2 | query time before / after | 5.2 ms → 3.9 ms |
| E2 | `sqlite_stat1` entries | 3 |

Three observations deserve emphasis. **First**, in the single-transaction microbenchmark the two journaling modes are within noise of each other — the WAL's advantage appears under *concurrent* read/write load and multi-transaction workloads with per-commit `fsync`s, not in one bulk transaction. **Second**, the WAL run visibly demonstrates the redo philosophy: after commit, the main database file is a single 4 KB page while committed data sits in `-wal` frames awaiting checkpoint — a reader's end mark, not the file, defines the database's logical state [2]. **Third**, `ANALYZE` changed the join order: without statistics the planner led with a full scan of the 7,000-row edge table; with `sqlite_stat1` histograms it estimated the `LIKE 'n1%'` filter's selectivity, led with the node table, and cut runtime by ~25% [3].

```sql
-- E2 query: three-way join whose optimal nesting depends on selectivity estimates
EXPLAIN QUERY PLAN
SELECT count(*) FROM node n, edge e1, edge e2
WHERE e1.src = n.id AND e2.src = e1.dst AND n.label LIKE 'n1%';
-- before ANALYZE: SCAN e1 / SEARCH n USING INTEGER PRIMARY KEY / SEARCH e2 USING COVERING INDEX
-- after  ANALYZE: SCAN n / SEARCH e1 USING INDEX e_src / SEARCH e2 USING COVERING INDEX e_src
```

```python
# E1 harness (essence): one transaction, 20k rows, both journaling modes
conn.execute("PRAGMA journal_mode=" + mode)
conn.execute("CREATE TABLE t(id INTEGER PRIMARY KEY, a INT, b TEXT)")
t0 = time.time()
conn.execute("BEGIN")
for i in range(20000):
    conn.execute("INSERT INTO t VALUES (?,?,?)", (i, i % 997, "x" * 40))

```

### 5.3 Threats to validity

The VM's filesystem cache flatters all timings; production conclusions require `PRAGMA synchronous=FULL` durability measurements and concurrent-reader workloads, where WAL's non-blocking reads dominate. The E2 dataset is small enough that plan differences are measured in single milliseconds; the 2000× pathology in [3] requires adversarial data distributions.

## 6 Limitations

This account has deliberate boundaries. **Concurrency control** beyond the WAL's single-writer rule — `BEGIN IMMEDIATE` versus `DEFERRED`, busy-handler backoff, snapshot semantics — is omitted. **The VDBE and SQL compiler** (name resolution, trigger programs, window functions, recursive CTEs) are treated as the planner's clients rather than studied directly. **Alternative page-level features** — auto-vacuum pointer maps, `WITHOUT ROWID` tables, FTS5/R-tree virtual tables — change details of cell layout and cursor logic but not the architectural argument. The **cost model's constants** are heuristic and version-dependent; we describe the model's structure, not its tuning. Finally, the empirical section measures a single machine and a single SQLite build; it demonstrates mechanisms, not universal performance claims.

---

## 7 Conclusion

SQLite's durability and performance rest on three tightly coupled design decisions. The **B-tree layer** keeps every on-disk page structurally valid at every instant — via the cell-pointer indirection, payload-fraction bounds, and the in-memory overflow-parking trick — so crashes never produce unreadable state. The **WAL layer** converts atomic commit from an undo problem into a redo problem: append frames, mark the commit, let readers define consistency through end marks, and fold the log back with idempotent checkpoints. The **query planner** closes the loop by ensuring the pages thus protected are the *right* pages, using `ANALYZE` statistics, a cost model over nested-loop plans, transitive constraint closure, and index-aware rewrites. None of the three is remarkable in isolation — B-trees, write-ahead logs, and cost-based optimizers are textbook material. What is remarkable is their composition into a zero-administration, single-file, crash-proof engine.
