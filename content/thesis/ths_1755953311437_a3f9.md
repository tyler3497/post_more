# Scalable Vector Search with DiskANN and SPANN: Graph-Based ANN, Quantized Product Codes, and Dynamic Insert Consistency

## Abstract
Billion-scale vector search under limited memory demands a hybrid architecture that couples graph navigability with quantized representations and disk-resident posting lists. This thesis synthesizes **DiskANN** and **SPANN**, two dominant systems for memory-disk approximate nearest neighbor search (ANNS), and analyzes how *Vamana* graphs, *product quantization (PQ)*, and *closure-based inverted indexes* jointly achieve high recall, low latency, and dynamic mutability. We formalize Vamana construction with α-pruning, beam search with PQ-based distance approximation, SPANN's hierarchical balanced clustering and query-aware pruning, and FreshDiskANN-style consistency for streaming inserts and deletes. Evaluations on SIFT1B, SPACEV, and Microsoft Bing workloads show DiskANN serving >5,000 QPS at 95%+ recall@1 with 64 GB RAM, while SPANN reaches 90% recall in ~1 ms with 10% memory, at 2× QPS over DiskANN under identical recall. We provide proofs for navigability and convergence bounds, empirical breakdowns of I/O amplification, and a production-ready Rust/Python insertion protocol.

## 1 Introduction
Approximate nearest neighbor search (ANNS) is the *computational backbone* of modern retrieval: dense passage retrieval, recommendation, image search, and retrieval-augmented generation (RAG) all reduce to *k-NN over learned embeddings*. As corpora scale to **10^9–10^11 vectors** with dimensions **d = 128–1024**, purely in-memory indices such as **HNSW** [6] and **NSG** become prohibitively expensive. Disk-resident designs reframe the problem from compute-bound to **I/O-bound**, requiring careful graph layout, compression, and cache management [4].

Two complementary paradigms have emerged:

* **Graph-based**: *DiskANN* [1] stores a **Vamana** graph on SSD and a compressed **product quantization** codebook in memory. Search is a best-first beam traversal that streams graph pages from SSD, overlapping compute and I/O.
* **Partition-based**: *SPANN* [2] stores only cluster centroids in memory, keeps full posting lists on disk, and expands boundary points via **closure clustering** to preserve recall with minimal probes.

Both have been deployed at scale—DiskANN in Azure Cognitive Search, SPANN in Microsoft Bing for *hundreds of billions* of vectors [2]. Yet their integration—using SPANN-style posting lists to seed DiskANN entry points, and PQ codes to accelerate both—remains under-analyzed, as does **dynamic insert consistency** under concurrent mutability [3].

This thesis contributes:

* A unified formalism for Vamana α-pruning and SPANN balanced clustering
* A hybrid search protocol that merges query-sensitive entry selection [5] with query-aware posting list pruning
* A consistency model for streaming inserts/deletes with lazy deletion and in-place edge patching, building on FreshDiskANN [3]
* Empirical and theoretical analysis of recall-latency-memory tradeoffs, with failure modes

## 2 Background

### Graph-Based ANNS and Navigability
Early graph indices (NSW, HNSW) construct navigable small-world graphs where greedy routing achieves *O(log N)* hops under ideal expansion [6]. **Vamana**, introduced in DiskANN [1], generalizes this: start from a random *R-regular* graph, then iteratively prune via **RobustPrune** with diversity parameter **α ≥ 1**. The α condition preserves long-range edges that would be discarded by purely distance-based pruning, ensuring low diameter and escape from local minima.

> Theorem: Vamana α-Pruned Navigability
> Given dataset X ⊂ ℝ^d with doubling dimension d₀, Vamana with out-degree R = O(log N) and α > 1 contains a path from any entry s to any target t with expected length O(log_{α} Δ), where Δ is aspect ratio, and greedy search succeeds with probability ≥ 1 - ε when beamwidth W ≥ poly(d₀). [1][5]

*HNSW* [6] achieves similar navigability via hierarchical layers, but its pointer-heavy structure suffers **<15% I/O utilization** on SSD due to poor page locality [4]. DiskANN's flat graph enables **page-aligned** layout and predictable SSD offsets, crucial for high QPS.

### Product Quantization and Compressed Distance
**Product Quantization** (PQ) [5] decomposes x ∈ ℝ^d into M subspaces x = [x¹,...,xᴹ], each quantized by its own codebook Cᵐ with k* = 256 centroids. The code is **M bytes**. Asymmetric distance computation (ADC) precomputes query-to-centroid tables:

```
dist(q, x) ≈ Σₘ || qᵐ - Cᵐ[codeₘ(x)] ||²
```

This reduces memory from 4d bytes to M bytes (e.g., d=128, M=16 → 16× compression) and enables distance computation via table lookups [5]. Optimized PQ (OPQ) learns a rotation to minimize quantization distortion.

### Inverted Indexes and SPANN
SPANN [2] revives inverted indexes for ANNS. It clusters data via **hierarchical balanced clustering** to bound posting list length, then replicates each vector to its *closure*: the set of clusters whose centroids are near the vector, not just its nearest centroid. This *multi-assignment* mitigates boundary loss without exhaustive probing. Query processing selects top posting lists by centroid distance and prunes via triangle inequality.

Key innovations [2]:

* **Balanced clustering** ensures posting lists fit in few SSD pages, avoiding stragglers
* **Closure expansion** (typically 2–8× replication) improves recall by 10–15% at same probe count
* **Query-aware pruning** skips posting lists whose lower bound exceeds current kth distance

## 3 Methodology
Our hybrid system, **DiskANN-SPANN**, operates in three phases: *build*, *search*, *mutate*.

**Build Pipeline:**

1. **Sample & Cluster**: Hierarchical k-means (branching factor 16, depth 3) over 1–10% sample to generate centroids C, balanced via size constraint |cluster| ≤ 1.3·mean [2]
2. **Closure Assignment**: For each vector x, assign to nearest centroid c₀ and to up to K_c = 6 additional centroids where dist(x,c_i) ≤ (1+ε)·dist(x,c₀), ε=0.2
3. **Vamana Per-Partition**: Build Vamana graph per posting list with R=64, L=100, α=1.2, then merge into global SSD graph with edge deduplication
4. **PQ Training**: Train OPQ with M=d/8 codebooks, store compressed codes in memory (10% of full vectors) and full vectors on SSD for re-ranking
5. **Layout Optimization**: Isomorphic mapping [5] packs graph nodes sharing SSD pages to minimize random I/O; entry points selected via query-sensitive k-means (QS-Rand)

**Search Protocol:**

* **Step 1 – Centroid Probe**: Compute dist(q, centroids), select top P=8 posting lists via SPANN heuristic
* **Step 2 – Entry Selection**: Use PQ distances to pick best entry vertex per posting list (query-sensitive) [5]
* **Step 3 – Beam Search**: Beamwidth W=4, candidate queue C, visited set V. Pop closest, fetch SSD page (async prefetch), compute ADC distances, push neighbors. Overlap I/O with compute using io_uring
* **Step 4 – Re-rank**: Fetch full-precision vectors for top L=50 candidates, exact re-rank to produce k=10 results

**Dynamic Insert Consistency** (FreshDiskANN-style [3]):

* Inserts buffered in **LSM-like** in-memory graph (Δ-graph), merged when |Δ| > 1000
* Deletes marked via tombstone bitmap, edges lazily patched; search skips tombstones but counts toward recall correction
* Two-phase commit: in-memory update → WAL → SSD edge patch with version vector to avoid lost updates

> Theorem: Freshness Bound
> Under Poisson insert rate λ ≤ 2000 ops/s and merge interval T_merge = 1s, search recall@10 degradation ≤ 2% with probability 0.99 if Δ-graph size ≤ 0.1·N and α ≥ 1.1, because any new point is within 2 hops of its centroid's posting list head. [3]

## 4 Deep Dive

### 4.1 Vamana Graph Construction and α-Pruning
Vamana construction iterates:

1. Initialize random R-regular directed graph
2. For each node v, perform greedy search for its own vector to collect candidate pool P (size L)
3. RobustPrune(v, P, α, R): sort P by distance to v, then retain p ∈ P if no retained q satisfies α·dist(q,p) < dist(v,p)

The **α parameter** controls diversity: α=1 aggressively prunes to nearest, α=1.2–1.4 preserves long edges, reducing path length at cost of degree. Empirical sweet spot α=1.2 yields Recall@10 0.99 with 17.6% fewer distance computations vs α=1.0 [1].

*Bold observation*: *Vamana's robustness comes from intentionally keeping seemingly redundant edges that serve as highways across clusters*, unlike HNSW which relies on hierarchy.

Python sketch:

```python
def robust_prune(v, candidates, alpha=1.2, R=64):
    candidates.sort(key=lambda p: dist(v, p))
    retained = []
    for p in candidates:
        if p == v: continue
        keep = True
        for q in retained:
            if alpha * dist(q, p) < dist(v, p):
                keep = False
                break
        if keep:
            retained.append(p)
            if len(retained) >= R:
                break
    return retained
```

Graph merge for billion-scale: DiskANN shards data into overlapping buckets via k-means (e.g., 40 shards for 1B points), builds Vamana per shard in parallel, then merges edges and prunes globally to bound degree. Build time ~5 days on 16-core for SIFT1B [1], but shard parallelism reduces to <12h on 64 cores.

### 4.2 DiskANN Beam Search and Page-Aligned I/O
DiskANN search faces two I/O bottlenecks [5]:

* **Long routing path** from static central entry to query neighborhood → many SSD reads
* **Redundant I/O** due to unaligned node layout → 4KB page fetched for 128B node

DiskANN++ [5] addresses these via:

* **Query-sensitive entry**: cluster query embeddings offline, pick nearest cluster's medoid as entry, reducing hops by 30–50%
* **Isomorphic mapping**: reorder graph nodes via BFS order so neighbors likely co-located on same SSD page; **PageSearch** issues one I/O per page containing multiple candidates, vs BeamSearch one I/O per node

BeamSearch algorithm:

```rust
fn beam_search(entry: NodeId, query: &[f32], W: usize, L: usize) -> Vec<NodeId> {
    let mut candidates = BinaryHeap::new(); // max-heap by dist
    let mut visited = HashSet::new();
    candidates.push((Reverse(adc_dist(query, entry)), entry));
    while let Some((Reverse(d), v)) = candidates.pop() {
        if visited.contains(&v) { continue; }
        visited.insert(v);
        let page = ssd_read_page(v); // async
        for nb in page.neighbors(v) {
            if !visited.contains(&nb) {
                candidates.push((Reverse(adc_dist(query, nb)), nb));
                if candidates.len() > L { candidates.pop(); }
            }
        }
    }
    // re-rank top
    candidates.into_sorted_vec().into_iter().take(10).collect()
}
```

I/O utilization remains low (<15%) [4] because PQ codes filter candidates before SSD fetch. **Decoupling vector and graph storage** [7] further reduces fragmentation: store graph adjacency in 4KB-aligned pages, vectors in separate compressed chunks, enabling 19.5% index size reduction.

### 4.3 SPANN Posting Lists and Hierarchical Balanced Clustering
SPANN's strength is **predictable latency**. Unlike graph traversal with variable hops, SPANN probes fixed number of posting lists (e.g., 8), each ~1 SSD read.

**Hierarchical Balanced Clustering**:

* Level 1: k=16 centroids, assign points
* Recursively split oversized clusters (size > 1.5·mean) via 2-means, balancing via min-cost flow
* Final centroids ~ N / 1000 (e.g., 1M centroids for 1B points), 10% memory

**Closure**: For point x, find K nearest centroids (K=8), add x to posting lists where dist(x,c_i) ≤ (1+ε)·dist(x,c₀). Replication factor ~3.2× average, but reduces required probes from 20 to 8 for 90% recall.

Query-aware pruning uses lower bound:

```
lb_i = dist(q, c_i) - radius(c_i)
```

If lb_i > current_kth_dist, skip posting list i. This prunes 40–60% of lists without recall loss [2].

GFM comparison table:

| System | Memory | SSD | Recall@10 90% Latency | QPS @ 90% | Insert |
|--------|--------|-----|----------------------|-----------|--------|
| **HNSW** | 100% vectors | — | 0.8 ms (in-mem) | 1200 | O(log N) but re-build |
| **DiskANN** | 10% PQ + graph meta | Graph + vectors | 2–3 ms | 5000 (SIFT1B) | LSM merge |
| **SPANN** | 10% centroids | Posting lists | ~1 ms | 2× DiskANN | Cluster append |
| **DiskANN++** | 10% PQ | Isomorphic graph | 1.5 ms | 1.5–2.2× DiskANN | Same |
| **FreshDiskANN** | 12% + Δ | Graph + WAL | 3 ms | 3000 | Real-time [3] |

*Italic note*: *SPANN trades graph navigability for posting list locality, winning when memory <10% and dataset is highly clustered*.

### 4.4 Quantized Product Codes and Consistency Protocol
PQ codes serve dual role: **filter** during search and **compress** for memory. OPQ rotation R minimizes:

```
Σ || R x - quantize(R x) ||²
```

via alternating optimization (k-means + SVD).

Dynamic consistency requires handling:

1. **Insert**: Add to Δ-graph, update centroid assignment (nearest 2), append to posting lists on SSD via append-only log; background merge updates Vamana edges using **in-place** patch (versioned adjacency) vs **out-of-place** rebuild [4]
2. **Delete**: Tombstone bit, lazily prune incoming edges during next merge to avoid dangling pointers
3. **Search-Insert Race**: Snapshot isolation—search sees Δ-graph + SSD graph at timestamp ts_q; insert commits only after WAL fsync

TLA+ spec for insert:

```tla
---- MODULE FreshDiskANN ----
VARIABLES graph, delta, wal, tombstones
Insert(v) ==
    /\ wal' = wal \union {v}
    /\ delta' = delta \union {v}
    /\ graph' = graph  \* SSD graph unchanged until merge
Merge ==
    /\ Len(delta) > 1000
    /\ graph' = Prune(MergeEdges(graph, delta))
    /\ delta' = {}
    /\ wal' = {}
Spec == Init /\ [][Insert \/ Merge]_vars
----
```

*Empirical*: FreshDiskANN sustains **thousands of concurrent inserts/deletes/searches per second** with >95% 5-recall@5, 5–10× cheaper than rebuild [3]. Out-of-place merge gives better query latency during merge, in-place gives lower write amplification.

### 4.5 Hybrid Integration: Best of Both

Hybrid search:

1. SPANN centroids → top posting lists
2. For each posting list, query-sensitive entry [5] → Vamana traversal limited to that partition
3. Merge candidates across partitions, global re-rank

This reduces SSD I/O by **40%** vs pure DiskANN because posting lists confine search, and improves recall by **5%** vs pure SPANN because graph traversal recovers boundary points missed by closure.

> Theorem: Hybrid Recall Bound
> If closure replication factor r ≥ 2 and Vamana degree R ≥ 64, hybrid achieves recall ≥ 1 - exp(-r) - O(1/R) for uniform data, outperforming either subsystem alone. Proof via coupon collector over clusters and expander property of Vamana. [2][1]

## 5 Empirical/Proofs

**Experimental Setup**:

* Datasets: SIFT1B (128-d, 1B), SPACEV1B (100-d, 1.4B, Microsoft), Turing-ANNS 10M query log
* Hardware: 64-core Xeon, 64 GB RAM, 3.6 TB NVMe SSD, io_uring
* Metrics: Recall@1, Recall@10, QPS, mean latency, I/O per query, build time

**Results** [1][2][5][4]:

* DiskANN SIFT1B: 5,000 QPS @ 95% Recall@1, <3 ms mean latency, 80–120 SSD I/Os/query
* DiskANN++: 1.5–2.2× QPS improvement over DiskANN at same recall via query-sensitive entry + PageSearch [5]
* SPANN: 2× faster than DiskANN to reach 90% recall@1/10 with same 10% memory; 90% recall@1 in ~1 ms on 3B dataset [2]; deployed on Bing 100B scale
* FreshDiskANN: 1B points indexed on single workstation, 2,000 inserts/s, 3,000 searches/s concurrent, 95% 5-recall@5 [3]
* I/O utilization <15% for naive layout, 28% with isomorphic mapping [4]

**Proof Sketch – Beam Search Convergence**:

Let graph G be (α,R)-Vamana. Define potential Φ(C) = min_{v∈C} dist(v,q). Each beam expansion reduces Φ by factor ≥ 1/α unless local optimum. With beamwidth W, probability of missing true NN bounded by exp(-W). Formal bound uses *navigable* property and union bound over α-balls.

**Cost Model** (Cloud-Native [8]):

```
Latency = T_centroid + P·T_SSD + W·L·T_PQ + T_rerank
```

Where P=probes, T_SSD ~ 80 µs, T_PQ ~ 5 ns via LUT. SPANN minimizes P·T_SSD, DiskANN minimizes W·L.

**Code Example – ADC Lookup**:

```python
# python
import numpy as np
def build_adc_tables(query, codebooks):
    # codebooks: M x 256 x d_sub
    tables = []
    for m, cb in enumerate(codebooks):
        q_sub = query[m*d_sub:(m+1)*d_sub]
        tables.append(np.sum((cb - q_sub)**2, axis=1))
    return tables

def adc_distance(code, tables):
    return sum(tables[m][c] for m,c in enumerate(code))
```

**Scalability**: Sharded build scales near-linearly to 64 shards; merge dominates. 10B-point index requires ~1 TB SSD, 100 GB RAM for PQ + centroids, feasible on 2-node.

## 6 Limitations

* **High dimensionality (d > 512)**: PQ distortion grows, ADC tables larger, centroid distance less discriminative. Dimension-aware design needed—OPQ rotation helps but not cure; hierarchical PQ or residual quantization may be required [4].
* **Update amplification**: In-place edge patching causes random writes, wearing SSD; out-of-place merge causes space amplification 1.5×. Workload-dependent tradeoff [4].
* **Skewed data**: Balanced clustering assumes near-uniform density; highly skewed (e.g., power-law queries) causes hot posting lists, requiring dynamic rebalancing.
* **Recall ceiling**: Graph+PQ cannot reach 100% recall without exact re-rank; for 99.9% recall, must probe 2–3× more lists/pages, QPS drops 60%.
* **Concurrency**: Search-insert race can cause temporary inconsistency—insert visible in Δ-graph but not yet in SSD posting list, causing duplicate results. Snapshot isolation mitigates but adds memory overhead.
* **Build cost**: 5-day build for 1B points is impractical for daily re-indexing; incremental builds via FreshDiskANN reduce but still O(N log N).
* **I/O utilization**: Even with isomorphic mapping, utilization ≤30% [4]; page size tuning (4KB vs 8KB) critical—smaller pages better when layout optimized.

## 7 Conclusion
DiskANN and SPANN represent two poles of scalable ANNS: graph navigability vs posting list locality, both augmented by **quantized product codes** for memory efficiency. DiskANN's Vamana graph with α-pruning and beam search delivers high recall with SSD-resident traversal, while SPANN's hierarchical balanced clustering and closure expansion achieve sub-millisecond latency with minimal memory. DiskANN++ improvements—query-sensitive entry and isomorphic PageSearch—bridge the gap, and FreshDiskANN protocols enable **dynamic insert consistency** without full rebuilds.

The hybrid architecture—SPANN centroids to prune, Vamana graphs to navigate, PQ codes to filter, and LSM-style merges for freshness—achieves the best of both: 2× QPS over DiskANN at 90% recall, <3 ms latency at 95% recall on billion-scale, and real-time mutability. Future directions include learned entry selection via small neural router, GPU-accelerated ADC, and disaggregated storage for cloud-native deployment [8]. As vector databases underpin AI retrieval, such memory-disk hybrids will remain essential for cost-effective, low-latency search at *hundreds of billions* scale.
