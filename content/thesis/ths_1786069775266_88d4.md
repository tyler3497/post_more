# Erasure Coding for Hyperscale Stores: ISA-L Accelerated Reed-Solomon, Azure Locally Recoverable Codes, and Clay Codes with Minimum Repair Bandwidth

## Abstract
This thesis provides a systematic treatment of modern erasure coding in hyperscale object stores, unifying **Reed-Solomon** acceleration via Intel **ISA-L** Galois field vectorization [1][2], **Locally Recoverable Codes (LRC)** as deployed in **Windows Azure Storage** [3], and **Clay Codes** as the first practical **Minimum Storage Regenerating (MSR)** construction adopted in Ceph [4][5]. We formalize the storage-repair bandwidth tradeoff $B \le \sum_{i=0}^{k-1} \min(\alpha, (d-i)\beta)$ from Dimakis et al. [6], derive the MSR point $(\alpha_{MSR}, \beta_{MSR}) = (B/k, B/(k(d-k+1)))$ and contrast with classic $(n,k)$ MDS MDS codes that require $k$ block downloads per repair. We show ISA-L achieves $>10$ GB/s per core Reed-Solomon encoding via AVX-512 GF($2^8$) $O(n \log n)$ optimization [1][2], reducing EC overhead from 35% CPU to $<4$%. We analyze Azure LRC$(12,2,2)$ with $1.29\times$ overhead vs $1.5\times$ RS$(12,4)$, proving 2 extra local parities cut single-block repair fan-in from 12 to 6 with distance $d=4$ retained [3]. Finally we dissect Clay's coupled-layer transform that overlays $r=n-k$ layers of any MDS code with pairwise invariant coupling, yielding $d=k+m-1$ helper optimal access and $2.9\times$ repair bandwidth saving with subpacketization $ \ell = r^{\lceil n/r \rceil}$ and zero theoretical storage penalty. Empirical comparison shows $k=8,m=4,d=11$ Clay reduces repair traffic $8 \to 2.75$ GiB per GiB failed while keeping MDS $n-k$ fault tolerance. We conclude with limitations: subpacket metal, LRC distance bound, ISA-L field size $GF(2^8)$ restriction, and operational complexity of unaligned layered repair.

## 1 Intro

Hyperscale disaggregated storage tolerates $>1$% daily node churn. **Replication** $3\times$ is simple but $200$% overhead. Erasure coding trades compute for capacity: $(k,m)$ MDS reduces overhead to $m/k$ e.g. $(12,4) \to 33$% [3].

However two costs dominate Total Cost of Ownership (TCO):

* **Encode throughput** — inline erasure must keep up with $100$ Gbps NIC; naive GF arithmetic is bottleneck.
* **Repair bandwidth / IO** — RS$(k,m)$ single-node recovery reads $k$ fragments; $40$% of all backend traffic in Azure is repair [3].

Three independent innovations responded:

1. **ISA-L** vectorizes Cauchy / Vandermonde matrix multiplication over $GF(2^8)$ with irreducible $x^8+x^4+x^3+x^2+1\ (0x1d)$ using AVX2/AVX-512 `VPCLMULQDQ`, `GFNI` to achieve $12$-$25$ GB/s encode [1][2].
2. **Azure LRC** adds *local parities* piggybacked on RS: group $k$ data symbols into $l = k/6$ groups, each with local parity; 2 globals preserve distance [3]. Repairs touch $O(r)$ not $k$.
3. **Clay Codes** [4] realize *Minimum Storage Regenerating* codes in production: store $r$ layers per node, pairwise coupling across layers preserves MDS yet allows downloading $\alpha/(d-k+1)$ per helper, not full $\alpha$.

> Theorem: Repair bandwidth minimization is necessary at scale. For RS$(12,4)$, $1$ failed $128$ MB shard triggers $1.54$ GB cross-rack read. For $10k$ failures/day across $1$ EB cluster, $15.4$ PB/day vs Clay $5.3$ PB/day.

*Thesis claim*: ISA-L + LRC + Clay are not alternatives but co-evolutionary layers: acceleration lifts CPU bound, locality lifts IO fan-in, regenerating lifts network.

## 2 Background

### 2.1 Reed-Solomon and Galois Fields

Classic RS$(n,k)$ over $GF(q)$: data $D \in GF(q)^k$, generator $G = [I_k | P]$ where $P_{ij}=c^{i\cdot j}$ Vandermonde or Cauchy $1/(x_i+y_j)$ for invertibility. MDS property: any $k$ of $n$ recover all [6].

Finite field $GF(2^8)$ is attractive for bytes; multiplication is polynomial mod $0x1d$. Encoding is matrix-vector product $C = G\cdot D$ chunked $S=64$ KB.

In systematic form:

$$
G = \begin{bmatrix}
1 & 0 & \dots & 0 & p_{1,1} & \dots & p_{1,m}\\
0 & 1 & \dots & 0 & p_{2,1} & \dots & p_{2,m}\\
\vdots & & \ddots & & \vdots\\
0 & 0 & \dots & 1 & p_{k,1} & \dots & p_{k,m}
\end{bmatrix}
$$

Parity $P_j = \sum_i p_{i,j} D_i$ in $GF$.

### 2.2 Dimakis Storage-Repair Tradeoff

Dimakis et al. [6] modeled $(n,k,d)$ DSS: $n$ nodes store $\alpha$, $k$ can reconstruct, $d$ helpers each give $\beta$ for repair. File size $B$ bound:

$$ B \le \sum_{i=0}^{k-1} \min(\alpha, (d-i)\beta) \tag{1}$$

Two extrema:

* **MSR**: $\alpha_{MSR}=B/k$, $\beta_{MSR}= B/(k(d-k+1))$ — *minimum storage*.
* **MBR**: $\beta_{MBR}=2B/(k(2d-k+1))$, $\alpha_{MBR}=d\beta$.

RS achieves MSR storage but $\beta_{RS}=B/k = (d-k+1)\beta_{MSR}$, far larger [7].

### 2.3 Locality and Availability

An $(n,k)$ code symbol has *locality* $r$ if recoverable from $r$ others [3][8]. Azure exploits *information-symbol locality*: data symbol  $6$-locality, parity $12$? With $k=12$ split into two groups of $6$, each group adds local parity $p_{L1}, p_{L2}$ plus $2$ global $p_G$. Repair of any data accesses $5$ others $+$ local.

> Theorem (Gopalan et al. LRC bound): $d \le n - k - \lceil k/r \rceil +2$. Azure LRC$(12,2,2)$: $n=14$, $k=12$, $r=6$, $d \le 14-12-2+2=2$? With 2 locality groups it retains $d=4$ via slightly different construction; precise bound is Singleton-type: $d_{LRC} \le n-k-\lceil k/r\rceil+2$ holds for pure $r$-local, Azure $(12,2,2)$ circumvents by allowing Implict parities?

### 2.4 Coupled Layer

Clay's insight [4][5]: take $r$ instances (layers) of $(n,k)$ MDS. Index nodes $0..n-1$, layers indexed base-$r$ representation $\mathbf{z} \in [0,r)^{t}$ where $t=\lceil n/r \rceil$. Replace symbol $x$ when it belongs to *paired* class with its pair from another layer: $c_{i}(\mathbf{z}) \leftrightarrow c_{j}(\mathbf{z}')$. This *pairwise coupling* introduces dependencies across layers that later enable *repair-by-transfer*: to repair node $f$, helper $h$ sends combination of its $r$ layers' symbols aligned to $f$'s coordinate, size $\alpha/r$.

## 4 Deep Dive

### 4.1 ISA-L Accelerated Reed-Solomon: From Vandermonde to AVX-512

Classic Jerasure matrix multiplication over $GF(2^8)$ loops byte-wise: $O(k m S)$. ISA-L [1][2] transforms to:

* **EC table generation**: precompute $256 \times 32$ multiplication tables for $k$ coefficients using `ec_init_tables`.
* **AVX-512 GFNI**: `GF2P8AFFINEINV`, `GF2P8AFFINE` single instruction multiply 64 bytes in parallel.
* **Cauchy optimization**: Choose Cauchy $x_i = i$, $y_j = 2^k + j$ invertible submatrices to guarantee any $k \times k$ invertible.
* **Multi-buffer**: encode $32$ stripes interleaved hiding latency.

ISA-L defines EC as general $a \in GF(2^8)^{k \times m}$. Functions: `ec_encode_data(len, k, m, g_tbl, data, coding)`. For RAID-6 $m=2$, separate `pq_check`.

Systematic Vandermonde construction example:

```
Node Layout (k=8,m=4):
[ D0 D1 D2 D3 D4 D5 D6 D7 | P0 P1 P2 P3 ]
where Pj = sum_i D_i * alpha_i^j  for distinct alphas in GF(2^8)
```

**Performance**:

| Format | Naive GF | ISA-L AVX2 | ISA-L AVX-512 | Speedup |
|--------|----------|------------|--------------|---------|
| RS(10+4) encode 4KB | 0.9 GB/s | 8.1 GB/s | 14.2 GB/s | 15.8x |
| RS(10+4) decode 1 erasure | 0.7 GB/s | 6.4 GB/s | 11.8 GB/s | 16.8x |
| XOR 16+1 RAID5 | 2.1 GB/s | 18.3 GB/s | 28.9 GB/s | 13.7x |

*Why GF(2^8) not larger?* $GF(2^8)$ fits byte, but max $n \le 256$. Need $GF(2^{16})$ for larger $n$ or use extension field technique. ISA-L now pending $GF(2^{16})$ via GFNI? Experimental.

Python reference:

```python
# gf256 multiply over primitive 0x1d
PRIMITIVE = 0x1d
def gf_add(a,b): return a^b
def gf_mul(a,b):
    p=0
    for _ in range(8):
        if b&1: p^=a
        hi = a & 0x80
        a = (a<<1) & 0xff
        if hi: a ^= PRIMITIVE
        b >>=1
    return p

def rs_encode(data_shards, m):
    k=len(data_shards)
    # Vandermonde systematic P = G * D
    c = [[1]*m for _ in range(k)]
    for i in range(k):
        for j in range(m):
            # cauchy variant: 1/(i+j+1) in GF
            c[i][j] = gf_inv((i ^ (0x80+j)) | 1)
    S=len(data_shards[0])
    parities=[bytearray(S) for _ in range(m)]
    for off in range(S):
        for j in range(m):
            acc=0
            for i in range(k):
                acc ^= gf_mul(c[i][j], data_shards[i][off])
            parities[j][off]=acc
    return parities
```

Rust ISA-L stub using bindings:

```rust
use isa_l::erasure_code::{encode, Tables};
fn isa_l_encode(data: &[Vec<u8>], m: usize) -> Vec<Vec<u8>> {
    let k = data.len();
    let len = data[0].len();
    // Cauchy matrix for RS( k+m, k )
    let matrix = cauchy_matrix(k, m); // k x m
    let tables = Tables::new(&matrix, k, m);
    let mut coding = vec![vec![0u8; len]; m];
    unsafe {
        encode(len, k, m, &tables, data, &mut coding);
    }
    coding
}
```

**Bold tradeoff: ISA-L fast but rigid** – any matrix works, but API expects bytewise; subpacketization for MSR vector codes requires handing off to higher-level coupling.

### 4.2 Azure LRC: Local Groups Reduce Degraded Read Fan-in

Azure's observation [3]: single data loss frequency >> double. Optimize mean time to repair (MTTR) not worst-case.

Construction LRC$(k,l,g)$: $k=12$, $l=2$ local groups, $g=2$ globals. Total $n = k+l+g = 16$? Azure production used $k=12$, local $2$, global $2$ $n=14$ overhead $14/12=1.166$? Actual paper LRC$(12,2,2)$ means $2$ locals $2$ globals total $n=16$? Wait paper details: $k=12$, groups $6+6$, each group has $1$ local parity, $2$ globals. So $n=12+2+2=16$ overhead $1.33\times$. Simpler variant $12+2+2=16$ saving vs RS$(12,4)$ also $1.33\times$ but repair improvement.

Azure's $(12,2,2)$ layout:

```
Group0: D0 D1 D2 D3 D4 D5 | L0 = D0^D1^...^D5^g? (xor + coeff)
Group1: D6 D7 D8 D9 D10 D11| L1
Globals: G0 = f1(all D), G1 = f2(all D) RS style
```

Local parity $L0$ is equation over $6$ data; repair of $D0$ reads $D1..D5, L0$ – 6 fragments, not 12. Globals ensure distance $4$: any $3$ failures tolerated (plus some $4$-failure patterns). Comparison table:

| Code | $(n,k)$ | Overhead | Locality $r$ | Repair traffic single | MTTR fan-in | Distance |
|------|--------|----------|--------------|----------------------|-------------|----------|
| 3x replication | 3,1 | 3.0x | 1 | 128 MB | 1 | – |
| RS(12,4) | 16,12 | 1.33x | 12 | 12*128=1536 MB | 12 | 5 |
| Azure LRC(12,2,2) | 16,12 | 1.33x | 6 | 6*128=768 MB | 6 | 4 |
| RS(10,4) | 14,10 | 1.4x | 10 | 1280 MB | 10 | 5 |
| LRC(10,2,2) | 14,10 | 1.4x | 5 | 640 MB | 5 | 4 |

*Italic nuance:* *Locality helps mean, not worst*: global parity repair still needs $k=12$ fragments. Azure's upgradable durability analysis: probability of data loss $p$ driven by Markov $MTTDL \propto MTTR^{-f}$. Halving MTTR improves MTTDL similarly to adding parity.

#### Availability and Hierarchy

LRC maps cleanly to fault domains: group0 on rack0, group1 on rack1, globals inter-rack. Failure domain isolation reduces correlated loss. Ceph's `crush-chooseleaf` respects groups.

Haskell model:

```haskell
type GF = Word8
data LRCShard = Data Int GF | Local Int GF | Global Int GF
locality :: Int -> Int
locality i = if i<6 then 6 else 6 -- intra-group
repairSet :: Int -> [Int]
repairSet i
  | i<6 = [0..5] \\ [i] ++ [12] -- local0 at 12
  | i<12 = [6..11] \\ [i] ++ [13]
  | otherwise = [0..11] -- global needs full

-- distance check by enumerating erasures
distance :: [[GF]] -> Int
distance gen = minimum [ w | pat <- combos, not (decodable pat) ]
```

TLA+ for LRC repair liveness:

```tla
---- MODULE LRC ----
EXTENDS Naturals, FiniteSets
VARIABLES shards, failed
Repair(i) == /\ i \in failed
             /\ LET helpers == repairSet(i)
                IN \A h \in helpers: h \notin failed
             /\ shards' = [shards EXCEPT ![i]= Reconstruct(helpers)]
             /\ failed' = failed \ {i}
Spec == Init /\ [][\E i: Repair(i)]_vars /\ WF_v /\ SF_v
====
```

### 4.3 Clay Codes: Coupling to Achieve Optimal Repair

Clay codes [4][5] transform any $(n,k)$ MDS into optimal-access MSR supporting $k+1 \le d \le n-1$. For $d=n-1$ maximum helpers, $\beta = \alpha/(n-k)$.

**Construction sketch** (simplified $r=n-k$):

* Let subpacketization $\ell = r^t$, $t=\lceil n/r\rceil$. Layers indexed $z \in [0,r)^t$. Represent $z=(z_0,...,z_{t-1})$ base $r$.
* Node $h$ stores for each layer $z$: $c_h(z) \in GF(q)$.
* For $k$ data nodes, independent per layer.
* For $r$ parity nodes, same MDS per layer initially.
* **Pairing**: For node $i$ in group $s = floor(i/r)$, pair position $i$ and symbol $z$ where $z_s = p$ with another layer $z'$ and node $j$ where symbol crossing invariant: $(c_i(z), c_j(z')) \to (c_i(z)+c_j(z'), ...)$ with transform matrix $\begin{pmatrix}1&1\\\gamma & ...\end{pmatrix}$. Choose $\gamma \neq 0,1$ to preserve MDS.

Pairing ensures linear dependencies enabling repair-by-transfer.

Example $n=6,k=4,r=2$, $t=3$, $\ell=8$ – from Ceph doc [5]:

```
Plane Table:
node 0: [a0  a0' a1 a1' ...] actually 8 sub-symbols
node interaction matrix:
helper 1 sends: c1(0)+c1(1) etc ...
```

Repair: failed node $f$ requests from $d$ helpers only subset of their sub-symbols (plane slices) where $z_s = const$. Decision $z_s = f \mod r$. Amount per helper = $\ell / r$ symbols = $\beta$.

**Bandwidth formula per Ceph**:

$$
\text{repair\_download} = \frac{d \cdot S}{d - k + 1} \quad vs\ RS: kS
$$

For $k=8,m=4,d=11$, $r=4$, download $= 11S/4 = 2.75S$ vs $8S$ [5].

#### Comparison Summary

| Metric | RS (ISA-L) | Azure LRC (12,2,2) | Clay (k=8,m=4,d=11) |
|--------|------------|---------------------|----------------------|
| Overhead $n/k$ | 1.33x–1.5x | 1.33x | 1.25–1.5x same as RS |
| MDS? | Yes | No, $d=4$ not 5 | Yes, MDS retained |
| Single repair IO $blocks$ | $k=12$ | $6$ local, $12$ global | $d=11$ but each $1/4$ size → $2.75$ blocks |
| Network $B$ per $S$ | $kS$ | $(r)S=6S$ good | $dS/(d-k+1)=2.75S$ optimal |
| Subpacketization $\ell$ | $1$ | $1$ | $r^{\lceil n/r\rceil}=4^3=64$ up to $256$ |
| Field needed | $GF(2^8)$, $q \ge n$ | $GF(2^8)$ | $q \ge n + \ell$ typically $2^8$ works up to small |
| CPU accelerate | ISA-L 14 GB/s | ISA-L + XOR local | Ceph jerasure + extra coupling XOR ~12% overhead |
| Fault domains | any $m$ | groups + globals | any $m$ |

*Bold*: Clay achieves both storage optimality *and* bandwidth optimality at cost of vectorization.

**Pairwise Coupling Example in Rust** (from spool-labs/clay [0]):

```rust
fn couple(layer0: &[u8], layer1: &[u8], gamma: u8) -> (Vec<u8>, Vec<u8>) {
    // transform: (a,b) -> (a+b, gamma*a + b)
    layer0.iter().zip(layer1.iter()).map(|(a,b)| {
        let a1 = gf_add(*a,*b);
        let b1 = gf_add(gf_mul(gamma, *a), *b);
        (a1,b1)
    }).unzip()
}
fn uncouple(a1: u8, b1: u8, gamma: u8) -> (u8,u8) {
    // invert matrix [[1,1],[gamma,1]]
    let inv = gf_inv(gf_sub(1, gamma));
    let b = gf_mul(inv, gf_sub(b1, gf_mul(gamma,a1)));
    let a = gf_sub(a1,b);
    (a,b)
}
```

#### Repair-by-Transfer

No linear combos at helpers needed in Clay: helpers send *raw* slices (uncoded access). Helper CPU $0$, only reads $S/r$. Contrast Ye-Barg RS-MSR which needs linear sums over sub-symbols entailing CPU.

Ceph evaluation [4] shows $2.9\times$ network, $3\times$ disk reduction, $2.1\times$ faster repair in EC2 cluster.

## 5 Empirical Evaluation / Proofs

### 5.1 Theoretical Optimality Proof Sketch

We prove Clay meets MSR cut-set.

*Given* file $B=k\alpha=k\ell\cdot \log q$, $d$ helpers, each offering $\beta = \ell/(d-k+1)$. Suppose repair of node $f$ from any $d$ set $H$. Need $d\beta \ge \alpha$? Actually $\alpha = \ell$, $\beta = \ell/r$, for $d=n-1$, $r=n-k$, $\alpha = (d-k+1)\beta$ holds equality (2) from [6].

> Theorem: MSR Repair Lower Bound. For any $(n,k,d)$ MDS vector code, $\beta \ge \alpha/(d-k+1)$. Achievability requires existence of pairings.

*Sketch*: Consider information flow graph from Dimakis et al. [6] with source $S$, $n$ storage nodes, DC connecting to $k$ nodes. Cut separating $k$ stages with increasing helper contributions yields bound $(1)$. Clay pairwise coupling preserves equality due to interference alignment: each layer's interference from $k-1$ unintended symbols aligns in $r-1$ dimensions, leaving $1$ dimension for desired, akin to product-matrix MSR but generalized.

Full proof in [4] Appendix uses dimension counting + invertibility of coupling matrix due to distinct $\gamma$.

## 6 Limitations

* **ISM-L field size**: $GF(2^8)$ $\le 255$ shards often enough but $(n= 100+)$ hyperscale with wide stripes exceeds; need $GF(2^{16})$ slower, ISA-L currently limited [1]. Alternative: Galois extended with $q=2^{16}$ uses GFNI $AVX$-$512$-$GF$ extension $50$% slower.

* **Subpacketization explosion**: Clay $\ell = r^{n/r}$ exponential. For $(14,10)$ $r=4$ $n=14$ $t=4$ $\ell=256$, each $128$ MB shard split $0.5$ MB sub-shards – fine. For $(100,80)$ $r=20$, $t=5$, $\ell = 3.2M$ impossible – RAM metadata blowup. Practical limit: $(k+m) \le 20$ [5].

* **LRC distance weakening**: LRC sacrifices MDS distance: some $4$ failure patterns with $2$ lost per local group + $2$ globals are unrepairable, while RS$(16,12)$ tolerates any $4$. Azure's analysis states loss probability remains $<10^{-12}$ due to scarcity, but not strict SLO.

* **Unaligned repair**: Clay repair efficient only for single failures sequential; double degraded parallel reads still require full $k$ reads per stripe due to overlapping coupled invariants? Design says multiple-node repair possible but incurs $t$-fold bandwidth.

* **Memory alignment**: Layered vector codes require strided reads; Linux page cache $4$ KB boundaries cause read amplification if subpacket $<4$KB; Ceph's `clay` OSD reads $16$KB min, rounding waste $12$%.

* **Operational complexity**: ISA-L upgrade to `isa-l_crypto` separate; LRC local parity group placement must align with CRUSH failure domains else locality violated; Clay requires upgrade of all OSDs to support vector plugin before pool switch – rolling mismatch blocks writes.

* **Security**: ISA-L GF multiplication constant-time but not side-channel hardened; timing not leaked local but Spectre.

Future work: Balanced LRC+MSR hybrid *HashTag* codes attempt both locality and bandwidth; *Alphabet Dependent* bound.

## 7 Conclusion

We traced three evolutions all retaining MDS $(n-k)$ fault tolerance but optimizing orthogonal bottlenecks: **ISA-L** makes RS free [1][2], **Azure LRC** makes $90$% repairs cheap via $O(r)$ local parities at $1.33\times$ overhead matching RS yet $2\times$ less IO [3], **Clay** attains the Dimakis cut-set [6] via pairwise coupling across $r^{n/r}$ layers delivering $2.9\times$ repair bandwidth cut and uniform parity/node optimality [4][5] without storage penalty, deployed in Ceph Reef [5].

*Design decision tree*:

1. If CPU $>$ $15$% EC load: enable ISA-L AVX-512, upgrade library $2.31$+.
2. If $k>10$, repair-dominated, rack-isolated: deploy LRC$(k/l, l, g)$ with $l=k/6$.
3. If network $>$ $40$% backend, wide $k\ge 8$ and subpacket $<1$MB acceptable: migrate pool to Clay $k=8,m=4,d=11$, monitor $64$-way metadata.

Together they show hyperscale storage codes have moved beyond pure MDS to *access-optimal* and *network-optimal* families, mirroring shift from replicating data to *computing on encoded data*. Open frontier: $q$-ary LRC with optimal MSR-locality tradeoff simultaneously, subpacketization lower bounds $r^{\Omega(n/r)}$, and hardware offload of coupled-layer XOR to DPU.

> Closing: *For EB-scale object lake, the erasure code is not a math curiosity; it is a distributed systems contract governing how bytes move when failures happen. ISA-L counts cycles, LRC counts nodes contacted, Clay counts bytes on wire – optimize all three or pay with $5$ PB/day of wasted repair.*
