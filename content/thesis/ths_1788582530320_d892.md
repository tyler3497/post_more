# Zero-Copy Columnar Exchange in Distributed Query Engines: The Apache Arrow IPC Format, SIMD Vectorized Compute, and Flight RPC over gRPC

## Abstract

The movement of structured data between processes, languages, and machines has long been dominated by serialization costs: row-oriented formats force per-value parsing, type checking, and memory allocation on every boundary crossing. Apache Arrow replaces this regime with a standardized columnar in-memory format whose inter-process communication (IPC) representation is bit-identical to its in-memory layout, enabling genuine zero-copy exchange. This thesis develops a complete account of that architecture: the FlatBuffers-encoded metadata layer that describes schemas and record batches, the physical buffer layout of validity bitmaps, offsets, and values with 8-byte alignment invariants, the SIMD vectorized compute kernels that exploit columnar contiguity, and Arrow Flight, a gRPC-based RPC framework that streams record batches across distributed query engines without serialization. We formalize the zero-copy reconstruction theorem, analyze the memory-bandwidth economics of columnar vectorization, and review empirical throughput results showing Flight saturating 95% of available interconnect bandwidth and outperforming ODBC-class protocols by an order of magnitude. We conclude with limitations and open research directions.

---

## 1. Introduction

Modern analytical workloads are *data-movement workloads*. A distributed SQL engine executing a simple aggregation over a billion rows spends the majority of its elapsed time not in arithmetic but in moving column values between storage, memory, CPU caches, processes, and machines [1][2]. Each boundary historically demanded a translation step: Parquet pages decoded into row batches, rows serialized into protocol buffers or JSON, JSON parsed back into rows on the receiving side. Studies of big-data pipelines consistently report that more than **80% of data-access time** is consumed by serialization and deserialization rather than by the query logic itself [2].

Apache Arrow attacks this cost at its root. Rather than defining yet another serialization format, Arrow standardizes the *in-memory* representation itself: a columnar layout shared across C++, Java, Python, Rust, Go, JavaScript, C#, and more than a dozen other language runtimes [1]. When every participant agrees on the physical layout of an `int32` array — its validity bitmap, its contiguous value buffer, its alignment — the bytes produced by a Rust writer can be consumed directly by a Python reader through pointer arithmetic alone. The Arrow IPC format makes this agreement wire-compatible: the on-disk and on-the-wire representation of a record batch is byte-identical to the in-memory buffers, preceded only by a small FlatBuffers metadata header [1].

This thesis is organized as follows. Section 2 surveys the background: columnar storage, the memory-wall problem in analytical engines, and the lineage from MonetDB/X100 vectorized execution to contemporary systems. Section 3 describes our methodology — a specification-driven analysis of the Arrow format grounded in the normative documentation and published benchmarks. Section 4 provides the deep technical core: FlatBuffers metadata, the record batch physical layout, SIMD vectorized kernels, and the Flight RPC protocol. Section 5 presents empirical results and a formal treatment of zero-copy reconstruction. Section 6 discusses limitations, and Section 7 concludes.

> **Thesis statement:** *By unifying the in-memory, on-disk, and on-the-wire representations of columnar data under a single alignment-disciplined layout, Apache Arrow reduces cross-boundary data exchange to pointer arithmetic, and Arrow Flight extends this property across the network, fundamentally changing the cost model of distributed query execution.*

## 2. Background

### 2.1 The serialization tax

Classical data interchange formats — CSV, JSON, XML, and even binary protocols such as Protocol Buffers and Thrift — are *self-describing value streams*. A receiver must parse the stream, allocate objects per value, and convert textual or varint-encoded representations into native types. This cost is paid *per boundary crossing*: disk to memory, process to process, machine to machine. For analytical queries that scan billions of values to compute a handful of aggregates, the parse cost dwarfs the compute cost [2].

Columnar storage formats such as Parquet and ORC improved the *storage* side by grouping values by column, enabling compression, predicate pushdown, and vectorized decoding. However, they remain storage formats: each engine decodes Parquet pages into its own proprietary in-memory representation, so the boundary between the storage layer and the execution engine still exacts a translation toll.

### 2.2 Columnar in-memory processing and the memory wall

The case for columnar in-memory layouts rests on two hardware realities. First, analytical queries exhibit *column locality*: a query `SELECT sum(price) FROM lineitem` touches one column of many, so storing values of the same column contiguously maximizes useful bytes per cache line fetched. Second, contiguous homogeneous arrays are the ideal input for **SIMD (Single Instruction, Multiple Data)** execution: a single AVX-512 instruction can operate on sixteen 32-bit integers simultaneously, provided the data is laid out as a dense, aligned array — precisely what a columnar format provides [4].

The lineage of this idea runs through MonetDB/X100, which introduced vectorized query execution — processing columns in cache-fitting vectors rather than one tuple at a time — and demonstrated order-of-magnitude speedups over tuple-at-a-time volcano-style engines. Arrow can be understood as the *standardization* of the X100 insight: a common physical layout so that vectorized engines can exchange data without translation.

### 2.3 FlatBuffers: zero-parse metadata

Arrow's metadata layer (schemas, field types, record batch headers) is encoded with FlatBuffers, a serialization library designed so that serialized data can be accessed *without parsing or unpacking* [3]. A FlatBuffer is read by following offsets from the buffer's root — field access is O(1) pointer arithmetic with no allocation. This property is load-bearing for Arrow: the IPC metadata header must be interpretable with negligible cost relative to the bulk data buffers it describes.

## 3. Methodology

Our analysis is *specification-driven and evidence-anchored*. We proceed in four stages:

1. **Normative specification review.** We analyze the Arrow Columnar Format specification [1], which normatively defines the IPC message envelope, the FlatBuffers schema definitions (`Schema.fbs`, `Message.fbs`), buffer alignment rules, and the physical layout of every logical type.
2. **Implementation archaeology.** We examine the Gandiva LLVM-based expression compiler [4][5] as the canonical example of vectorized compute over Arrow buffers, and the Flight benchmark study [2] for the RPC layer.
3. **Cost modeling.** We construct analytical models of memory-bandwidth consumption for row-wise versus columnar-vectorized exchange, deriving the conditions under which zero-copy IPC dominates.
4. **Empirical synthesis.** We report published benchmark figures for Arrow Flight throughput and scalability [2], interpreting them through our cost model.

We do not introduce new benchmark measurements; our contribution is the unified formal account and the analysis connecting layout invariants to system-level performance.

## 4. Deep Dive

### 4.1 IPC Message Envelope and FlatBuffers Metadata

Every Arrow IPC message — whether in the streaming format or the random-access file format — has the same two-part structure [1]:

| Component | Contents | Cost to interpret |
|---|---|---|
| `metadata_flatbuffer` | Serialized `Message` FlatBuffer: version, header variant (`Schema`, `RecordBatch`, `DictionaryBatch`), body length, `custom_metadata` | O(1) field access, zero allocation |
| `body` | Flat sequence of data buffers, each 8-byte aligned | Zero-copy slice |

The `Schema` message carries no data buffers at all — only type metadata. Each `Field` records the field name, logical type, nullability, child fields for nested types, and dictionary-encoding information [1]. Because FlatBuffers permits direct access without deserialization [3], a reader obtains the body length from the metadata, reads exactly that many bytes, and then reconstructs every array via pointer arithmetic.

The critical design decision is the *separation of description from data*. The metadata is small (kilobytes for typical schemas) and parsed with negligible cost; the body is large (megabytes to gigabytes) and never parsed at all. Contrast this with Protocol Buffers, where every value in the body would require varint decoding and object allocation.

```cpp
// Conceptual zero-copy reconstruction (C++17, arrow::ipc)
std::shared_ptr<arrow::ipc::RecordBatchReader> reader =
    arrow::ipc::RecordBatchStreamReader::Open(input).ValueOrDie();
std::shared_ptr<arrow::RecordBatch> batch;
while (reader->ReadNext(&batch).ok() && batch != nullptr) {
  // batch's buffers alias the input memory region: no memcpy occurred.
  auto prices = std::static_pointer_cast<arrow::DoubleArray>(batch->column(0));
  const double* raw = prices->raw_values();  // direct pointer into IPC body
}
```

> **Theorem (Zero-copy reconstruction):** *Let B be the body of a valid Arrow IPC record batch message with 8-byte aligned buffers, and let M be its FlatBuffers metadata. Then the in-memory array structures described by M can be reconstructed from B using only pointer arithmetic — O(number of buffers) time and O(1) additional space — with no copying of value bytes.*

*Proof sketch.* By the specification [1], each buffer's offset and length are recorded in the `RecordBatch` header, and buffers are written end-to-end with padding to 8-byte boundaries. Reconstruction sets each array's data pointer to `base + offset` for the recorded length. Validity bitmaps and offsets buffers are likewise slices. No transformation of value bytes is specified or required; therefore the reconstruction is a pure function of `(base, M)` performing only integer addition. ∎

### 4.2 Record Batch Physical Layout: Validity Bitmaps, Offsets, and Values

Each Arrow array is a *struct of buffers* whose composition depends on the logical type [1]:

- **Primitive types** (`int32`, `double`, …): two buffers — a *validity bitmap* (1 bit per slot, `1` = valid) and a *values* buffer of densely packed fixed-width slots.
- **Variable-length binary / UTF-8**: three buffers — validity bitmap, *offsets* buffer of `int32` (or `int64` for large variants) with `length + 1` entries, and a *data* buffer of concatenated bytes. Value *i* occupies `data[offsets[i] .. offsets[i+1]]`.
- **Nested types** (`list`, `struct`, `map`): a validity bitmap plus child arrays, recursively flattened; the header records length and null count per flattened field.

Three invariants make this layout machine-friendly:

1. **8-byte alignment.** Every buffer in the IPC body begins at an 8-byte boundary [1]. This guarantees that SIMD loads (`_mm512_load_pd` and friends) never fault on alignment and that 64-bit atomic access is well-defined.
2. **Bit-packed validity.** Nulls cost one bit per row rather than a sentinel value or a sidecar boolean array, and null checks compile to a single `BT`/`TEST` instruction per 64-row word.
3. **Offset indirection for variable-width data.** The offsets buffer converts variable-length access into two array lookups, preserving random access without a scan.

```rust
// Zero-copy slicing of a Utf8Array's buffers (Rust, arrow-rs idioms)
let validity: &[u8] = &body[validity_offset..validity_offset + validity_len];
let offsets: &[i32] = bytemuck::cast_slice(&body[offsets_offset..offsets_offset + offsets_len]);
let data: &[u8] = &body[data_offset..data_offset + data_len];
// Row i of the string column:
let s = std::str::from_utf8(&data[offsets[i] as usize..offsets[i+1] as usize]).unwrap();
```

The table below summarizes per-type buffer structure and asymptotic access cost:

| Logical type | Buffers | Random access | Null check |
|---|---|---|---|
| `int32` / `double` | validity, values | O(1) | 1 bit test |
| `utf8` | validity, offsets, data | O(1) via offsets | 1 bit test |
| `list<T>` | validity, offsets, child | O(1) to child slice | 1 bit test |
| `struct` | validity, children | O(1) per child | 1 bit test |
| `dictionary` | validity, keys (+ dictionary batch) | O(1) + dictionary lookup | 1 bit test |

### 4.3 SIMD Vectorized Compute Kernels

Columnar contiguity is not merely a storage convenience — it is the precondition for *vectorized execution*. A kernel operating on a `double` column processes a dense, aligned array: the exact memory pattern that SIMD units require. Gandiva, Arrow's LLVM-based expression compiler, compiles expression trees directly against this layout, generating native code specialized to the runtime CPU [4][5].

The performance argument is quantitative. Consider a filter kernel `price > 100.0` over *n* doubles:

- **Row-wise (volcano model):** per-tuple virtual function dispatch, branch mispredictions on the comparison, and strided memory access as the engine hops between fields of each row. Effective throughput is bounded by dispatch overhead, typically a few hundred MB/s.
- **Vectorized over Arrow buffers:** the kernel loads 8 doubles per AVX2 instruction (16 per AVX-512), applies a vector compare, and writes a selection vector — with the validity bitmap folded into the predicate mask at negligible cost. Gandiva's published results show up to **70× improvement** on SQL queries relative to non-vectorized execution [4].

```python
# Vectorized filter over Arrow buffers via pyarrow.compute (C++ kernels underneath)
import pyarrow as pa
import pyarrow.compute as pc

prices = pa.array([10.5, 200.0, None, 150.25, 99.99], type=pa.float64())
mask = pc.greater(prices, pa.scalar(100.0))   # SIMD kernel; null -> null (Kleene logic)
result = pc.filter(prices, mask)              # zero-copy slice of the values buffer
```

Two subtleties deserve emphasis. *First*, null semantics interact with vectorization: Arrow adopts Kleene three-valued logic, and kernels must AND the predicate mask with the validity bitmap. Because the bitmap is bit-packed, this is a word-level operation over `n/64` words — amortized O(1/64) per row. *Second*, dictionary-encoded columns vectorize over integer keys, deferring the dictionary lookup; the kernel's working set is the compact key array, improving cache behavior by the compression ratio.

### 4.4 Arrow Flight: RPC over gRPC for Distributed Query Engines

If the IPC format solves the *process* boundary, **Arrow Flight** solves the *machine* boundary. Flight is a gRPC-based protocol for high-performance bulk transfer of Arrow record batches, providing parallel, secure, cross-language data movement for analytics workloads [2][6]. Its API surface is minimal and batch-oriented:

1. `GetFlightInfo(descriptor)` — the client sends a query descriptor (e.g., SQL text); the server returns a schema plus a set of *endpoints*, each with a *ticket* and a location. This is the planning phase and the hook for distributed scheduling: endpoints may point at different cluster nodes holding different partitions.
2. `DoGet(ticket)` — the client redeems a ticket and receives a stream of `FlightData` messages, each carrying a record batch in IPC format. Multiple endpoints are fetched in parallel streams.
3. `DoPut(descriptor, stream)` — the dual operation for bulk ingestion.
4. `ListFlights`, `GetSchema`, `DoAction`, `Handshake` — catalog, introspection, and authentication operations.

Because the wire encoding *is* the IPC encoding, a Flight server can transmit buffers straight from its execution engine's memory into gRPC streams, and the client reconstructs arrays by pointer arithmetic on receipt — the zero-copy property survives the network hop, modulo the unavoidable kernel TCP copy. There is no row materialization, no per-value serialization, and no schema negotiation per batch [2].

Flight's design explicitly targets the distributed query engine use case: a planner node fans a query out to executor nodes, each streams its partition's record batches back over parallel `DoGet` streams, and the client concatenates them — all in the same columnar layout the engines computed in. Authentication and encryption ride on gRPC's TLS and extensible auth handlers at no format cost [2].

## 5. Empirical Results and Theoretical Proofs

### 5.1 Throughput measurements

The definitive benchmark study of Arrow Flight reports [2]:

- **DoGet throughput up to 6,000 MB/s** and **DoPut up to 4,800 MB/s** on localhost loopback.
- On Mellanox ConnectX-3 / Connect-IB interconnects, Flight utilizes **up to 95% of available network bandwidth**.
- Flight scales to use roughly half of available CPU cores efficiently for bidirectional communication.
- Against ODBC-class interfaces on Dremio query workloads, Flight-backed retrieval performs **20× better than turbodbc and 30× better than ODBC**.

These figures are consistent with our cost model: once serialization is removed, throughput is bounded by `min(memory bandwidth, network bandwidth, gRPC framing overhead)`, and the measurements show the system operating at the network bound — the theoretical optimum for any wire protocol.

### 5.2 A bandwidth cost model

Let a record batch contain *n* rows and *c* columns of width *w* bytes, with total value bytes *V = n·c·w*. Define:

- *S*: serialization cost per byte (parse + allocate + convert), typically 3–10 CPU cycles/byte for binary protocols, far higher for text.
- *M*: memory bandwidth (bytes/s); *N*: network bandwidth (bytes/s).

**Row-serialized exchange time:** *T_row ≈ V·S + V/N + V/M* — the serialization term dominates whenever *S > 1/N + 1/M* in per-byte time units, which holds on all modern hardware.

**Arrow Flight exchange time:** *T_flight ≈ V/N + V/M + ε*, where *ε* is the FlatBuffers metadata handling — O(kB) per batch, amortized to zero as batch size grows.

> **Theorem (Serialization dominance):** *For fixed per-byte serialization cost S > 0, the speedup of zero-copy columnar exchange over row-serialized exchange, T_row / T_flight, grows without bound as V → ∞ for any fixed batch metadata size, and is lower-bounded by (V·S)/(V/N + V/M) = S/(1/N + 1/M) for large V.*

*Proof sketch.* *T_row − T_flight = V·S − ε*. Dividing by *T_flight ≈ V(1/N + 1/M)* gives the ratio *1 + (V·S − ε)/(V(1/N+1/M))*, which tends to *1 + S/(1/N+1/M)* as *V → ∞*. Since *S > 0* strictly, the speedup exceeds 1 and grows with *S*; for text protocols where *S* is large, the bound is correspondingly large. ∎

### 5.3 Vectorization speedup bound

For a compute kernel over a primitive column, let *L* be the SIMD lane count (e.g., 8 for AVX2 double, 16 for AVX-512). The idealized vectorized throughput is *L×* the scalar throughput, minus overheads: validity-mask folding (*n/64* word operations), loop prologue/epilogue, and memory-bandwidth saturation. In practice, kernels become memory-bound when *L · w · f > M*, where *f* is clock frequency — i.e., the SIMD unit can consume data faster than DRAM supplies it. This is precisely why columnar layouts emphasize *compression* (dictionary, run-length, bit-packing): reducing *w* pushes the saturation point outward, converting memory bandwidth into effective compute throughput.

## 6. Limitations

Arrow's design involves real trade-offs that bound its applicability:

1. **Row-oriented access patterns suffer.** Transactional (OLTP) workloads that read and write entire rows pay a gather cost across columns; Arrow is an OLAP-oriented format and makes no apology for this.
2. **Small-batch overhead.** The per-message FlatBuffers metadata and gRPC framing are amortized only for large batches. Streaming single rows over Flight would be pathological; the protocol assumes batches of thousands to millions of rows.
3. **Alignment and padding waste.** The 8-byte alignment invariant [1] introduces padding, and bit-packed validity bitmaps are rounded up to 64-byte multiples in some implementations — measurable overhead for narrow tables with few rows.
4. **Mutation is expensive.** Arrow arrays are semantically immutable; updates require rebuilding buffers. Engines needing in-place mutation maintain a separate mutable representation and convert on exchange boundaries.
5. **gRPC head-of-line and CPU costs.** Flight inherits gRPC/HTTP-2 framing overhead and flow-control dynamics; at very high message rates, per-stream bookkeeping can become the bottleneck rather than the data path [2].
6. **Schema rigidity across versions.** While FlatBuffers provides forward/backward compatibility [3], evolving logical types (e.g., new timestamp units) requires coordinated upgrades of all participants' Arrow libraries.
7. **Security surface.** Zero-copy parsing means a malformed offsets buffer can induce out-of-bounds reads; readers must validate that offsets are monotonically non-decreasing and within the data buffer — validation the specification recommends but implementations must enforce.

## 7. Conclusion

Apache Arrow reframes data exchange as a *layout agreement* rather than a *translation process*. The IPC format's bit-identity between memory and wire representations, described by FlatBuffers metadata and disciplined by 8-byte alignment, reduces cross-process exchange to pointer arithmetic — a fact we formalized as the zero-copy reconstruction theorem. SIMD vectorized kernels, exemplified by Gandiva's LLVM-compiled expression engine, convert columnar contiguity into order-of-magnitude compute speedups. Arrow Flight carries these properties across the network, letting distributed query engines stream record batches over gRPC at up to 95% of interconnect bandwidth and outperforming ODBC-class protocols by 20–30×.

The deeper lesson is architectural: serialization is not an inherent cost of distribution but an artifact of representation disagreement. Standardize the representation — down to the bit layout of nulls and the alignment of buffers — and the tax disappears. Open problems remain in adaptive batch sizing, hardware-accelerated (GPU/RDMA) zero-copy paths, and verified readers that preserve the performance guarantees while closing the validation gap. As analytical systems continue their migration to disaggregated, multi-engine architectures, the columnar interchange layer Arrow defines is likely to become as foundational as the relational model itself.
