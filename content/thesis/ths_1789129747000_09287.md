# Egalitarian Replication: EPaxos, Mencius, and Generalized Consensus Beyond the Single-Leader Paradigm

## Abstract

State machine replication has long relied on a distinguished leader to impose a total order on client commands, as in Multi-Paxos and Raft. This design concentrates load, adds wide-area latency, and stalls the system during re-election. This thesis examines the multi-leader and leaderless alternatives that relax the single-leader orthodoxy while preserving linearizability: Mencius, which partitions consensus instances among rotating coordinators; Egalitarian Paxos (EPaxos), which replaces preordered instance slots with dynamically agreed dependency graphs; and the generalized consensus lineage of Lamport's generalized Paxos and Fast Paxos. We develop a unified framework for quorum composition, fast-path commit conditions, and the commutativity relation enabling independent commits. We prove EPaxos's fast-path quorum cardinality theorem, present the linearizability argument via monotonic execution graphs, and recount the Sutra counterexample exposing a ballot-tracking flaw in EPaxos's original specification. Empirical results from the EPaxos EC2 evaluation and Mencius WAN experiments are reinterpreted through a latency-contention model. We conclude that generalized, leaderless replication dominates wherever command interference is rare, while single-leader protocols retain advantages under high contention and write skew.

## 1 Introduction

The replicated state machine (RSM) is the canonical abstraction for fault-tolerant services: replicas agree on a command sequence and apply it deterministically [5]. For three decades the dominant strategy has been *single-leader replication*. Lamport's Paxos [5] elects a distinguished proposer; its Multi-Paxos optimization grants one stable leader ownership of the entire unbounded instance space, collapsing the prepare phase for steady-state commands. Ongaro and Ousterhout's Raft [3] strengthens this leadership: log entries flow only from leader to followers, and leader election is an explicit, randomized sub-protocol. The leader is a serializing bottleneck, but also a simplifying one — a single total order is trivially consistent.

This thesis argues that the single-leader total order is *stronger than necessary*. Linearizability [6] does not require every pair of commands to be ordered; it requires only that the real-time order of non-overlapping operations be respected and that every operation appear atomic. Two commands that *commute* — that access disjoint state, or whose relative order is unobservable — can be executed in any order, or concurrently. This observation, first exploited systematically by Lamport in generalized consensus and Fast Paxos [4], and refined by Pedone and Schiper's generic broadcast, opened the door to protocols that replicate *without a leader*:

- **Mencius** [2] keeps the preordered instance space but partitions it round-robin among all replicas, so every replica is a coordinator for its own turns; cheap *skip* messages let idle replicas advance the log without global coordination.
- **EPaxos** [1] abandons the instance space entirely: each command carries a set of *dependencies* on interfering commands, agreed upon by a fast quorum; replicas linearize the resulting dependency graph independently and identically.

The contributions of this thesis are:

1. A unified framework comparing single-leader, multi-leader, and leaderless SMR on quorum size, message complexity, commit latency, and load balance.
2. A self-contained proof sketch of EPaxos's fast-path quorum cardinality theorem and its linearizability argument via monotonic execution graphs, including the dependency-agreement invariants (E1)–(E2).
3. An analysis of the EPaxos safety controversy: Sutra's discovery that a single ballot-tracking variable is insufficient, the admissible counterexample, and what it teaches about the gap between pseudocode and specification [6].
4. A reinterpretation of published empirical results through an analytical latency–contention model, with a comparative protocol table.

## 2 Background

### 2.1 Paxos, Multi-Paxos, and the cost of a leader

In classic Paxos [5], each consensus instance elects a leader for a ballot; the leader runs phase 1 (prepare) to seal prior ballots, then phase 2 (accept) to propose a value. A value is *chosen* once a majority quorum accepts it at some ballot. Multi-Paxos observes that phase 1 can be run once for infinitely many future instances, so a stable leader commits each command in a single round trip to a majority. In the failure-free common case it needs just two message delays per command, but concentrates Θ(*N*) messages per command on the leader while followers handle O(1) [1]. Three costs follow:

1. **Load imbalance** — the leader saturates while followers idle, capping throughput.
2. **Wide-area latency** — remote clients pay an extra cross-region round trip before replication even begins.
3. **Availability gaps** — a leader failure halts processing until a new leader is elected and re-runs phase 1.

Raft [3] doubles down on strong leadership for *understandability* — randomized election timeouts, exclusive leader-owned log replication, joint-consensus membership changes — and inherits all three costs.

### 2.2 Commutativity and the weakening of consensus

Lamport's generalized consensus [4] reformulates the problem: instead of agreeing on a *sequence* of commands, replicas agree on a *partially ordered set* — a *c-struct*. Non-interfering commands need never be ordered relative to each other, so concurrent, non-interfering commands can always commit in *two message delays* without any leader. Fast Paxos [4] realizes a special case of this idea for single-decree consensus, permitting *fast rounds* in which any proposer may send directly to acceptors, at the cost of larger fast quorums (⌈3*N*/4⌉ acceptors) to tolerate collisions. The invariant that replaces Paxos's quorum intersection is a triple intersection: any two fast-ballot quorums and any classic-ballot quorum share a common acceptor, so recovery observes at most one "most-voted" value.

### 2.3 Quorum arithmetic

Throughout this thesis we use *N = 2f + 1* replicas tolerating *f* crash failures. A *classic quorum* has *f + 1* members. Fast-path protocols use enlarged quorums to let recovery disambiguate collisions:

| Protocol | Fast path | Quorum size | RTTs (no contention) |
|---|---|---|---|
| Multi-Paxos / Raft | leader, classic quorum | *f + 1* | 1 (client→leader→majority) |
| Fast Paxos [4] | fast round | ⌈3*N*/4⌉ | 1 |
| Mencius [2] | coordinator + skip protocol | *f + 1* | 1 (local coordinator) |
| EPaxos [1] | fast quorum, spontaneous agreement | *f + ⌊(f+1)/2⌋ + 1* | 1 |

We prove the necessity and sufficiency of the EPaxos fast-quorum size in §5.

## 3 Methodology

Our method is comparative-analytic rather than experimental. We reconstruct each protocol's commit path as a message-exchange skeleton, derive fast-path commit conditions as quorum-intersection theorems, map the protocols onto a common latency–contention model parameterized by interference probability *p* and the RTT matrix, and reinterpret the published EC2/WAN measurements [1][2] as data points in that model. Correctness arguments are theorem/proof-sketch pairs, with ballot-tracking invariants stated in TLA+-like notation.

## 4 Deep Dive

### 4.1 Mencius: partitioned instance leadership and rotating coordination

Mencius [2] begins from a derivation of Paxos and asks: what if *every* replica is a leader, each owning a disjoint residue class of instance numbers? With *n* servers, server *i* coordinates instances *i, i+n, i+2n, …*. A client sends to its *local* server, which is (usually) the coordinator of the next free instance in its own class — eliminating the remote-leader round trip and distributing the Θ(*N*) per-command message load evenly across all replicas.

The subtlety is the commit rule: a server may execute instance *k* only after learning the outcome of *all* instances *< k*, including instances owned by other servers. A slow or crashed coordinator would stall the entire log — the classic "head-of-line blocking" of partitioned leadership. Mencius solves this with *simple consensus* and **skip messages**: a server with no client load may fill its own instances with *no-op* (skip) values without running a full Paxos round. By piggybacking skips on ordinary traffic, the protocol advances the log with near-zero overhead. The commit rule is then relaxed: a server commits instance *k* as soon as all *non-skipped* prior instances are learned, because skipped instances contribute nothing to the state.

> **Theorem (Mencius commit safety).** If all correct servers eventually learn the same chosen value for every non-skipped instance, and skipped instances are eventually learned as skips by all correct servers, then all correct servers execute the same sequence of non-skip commands.
> *Proof sketch.* Total order is by instance number; skipping is itself a consensus decision, so agreement on values extends to agreement on the executed subsequence. ∎

Mencius's weakness is its dependence on *all* replicas being responsive: skip messages must still arrive, so one slow replica forces its turns through full consensus, degrading the protocol toward single-leader behavior. Mao et al. [2] are candid — Mencius is "effective, but only when the nodes are homogeneous," confirmed by the EPaxos authors' re-evaluation [1].

```
# Mencius instance ownership (n=3), local commit pointer per server
instances:  s0: 0 3 6 9 ...   s1: 1 4 7 10 ...   s2: 2 5 8 11 ...
commit rule at server si:
    execute k  iff  for all j < k: learned(j) and (value(j) != SKIP or j is skipped)
skip fast path:  si piggybacks SKIP(j) for its own empty turns on Accept/Learn traffic
```

### 4.2 EPaxos: dependency graphs and the leaderless fast path

EPaxos [1] discards the instance space. A command *c* submitted to any replica (its *command leader*) carries a dependency set *dep(c)* — the interfering commands the leader knew about when *c* arrived. The protocol's job is to get all correct replicas to agree on *dep(c)* for every *c*; execution is then a deterministic linearization of the resulting dependency DAG (topological order, breaking ties by command id). The two core invariants are:

- **(E1)** All correct replicas agree on *dep(c)* for every committed *c*.
- **(E2)** For any two committed, non-commuting *c, d*: *c ∈ dep(d)* or *d ∈ dep(c)*.

(E1)∧(E2) imply that every replica linearizes the same partial order, so non-commuting commands execute in the same relative order everywhere — linearizability follows from the monotonicity of the execution graph [6].

The commit path has two branches. In the **pre-accept phase**, the command leader sends *c* to a *fast quorum* *Q* of size *f + ⌊(f+1)/2⌋ + 1*; each member replies with its local interfering set. If all replies agree on *dep(c)* — *spontaneous agreement* — the leader commits *c* after a single round trip: the **fast path**. Otherwise the leader runs a classic Paxos **accept phase** over a majority (the **slow path**), proposing the union of the returned dependency sets. Any replica can be a command leader, and non-interfering commands proposed concurrently commit independently, in one RTT to the nearest fast quorum.

```tla
---- MODULE EPaxosBallots ----
\* Per-replica ballot tracking (corrected: two variables required [6])
VARIABLES bal,      \* last ballot joined
          vbal,     \* last ballot at which this replica voted
          vval      \* dep(c) value voted at vbal
JoinBallot(p, b) == /\ b > bal[p]
                    /\ bal' = [bal EXCEPT ![p] = b]
                    /\ UNCHANGED <<vbal, vval>>
\* Sutra's finding: the original TLA+ spec collapsed bal/vbal into one
\* variable, admitting an execution where dep(c2) = {} at p2 but {c1} at p1.
====
```

### 4.3 Generalized Paxos and Fast Paxos: consensus on command structures

Lamport's generalized consensus [4] is the intellectual ancestor of EPaxos's dependency model, though the mechanism differs: generalized Paxos runs Paxos instances whose *values are c-structs* — command sequences modulo commutation — and a leader proposes c-structs extending what acceptors have seen, so concurrent proposals commute and merge without conflict. Fast Paxos [4] supplies the other ancestor: the uncoordinated fast round in which proposers contact acceptors directly, with quorum size ⌈3*N*/4⌉ guaranteeing that any two fast quorums and one recovery quorum intersect, so recovery can always reconstruct the unique most-voted value. EPaxos's pre-accept phase is precisely a Fast-Paxos-style fast round restricted to ballot 0, with the interference relation replacing value collision as the trigger for the slow path.

The table below summarizes the design space:

| Design | Order primitive | Leader? | Handles contention by | Fast-path quorum |
|---|---|---|---|---|
| Multi-Paxos / Raft [3][5] | total order (log) | single, stable | leader serializes | *f+1* |
| Mencius [2] | total order (log) | partitioned, rotating | skip protocol + full Paxos | *f+1* |
| Fast Paxos [4] | single decree | none (fast rounds) | larger quorums + recovery | ⌈3*N*/4⌉ |
| Generalized Paxos [4] | c-struct (partial order) | single proposer of c-structs | merge commuting appends | *f+1* |
| EPaxos [1] | dependency DAG | none (any command leader) | slow-path accept phase | *f+⌊(f+1)/2⌋+1* |

### 4.4 Safety debates: ballots, dependencies, and the Sutra counterexample

The most instructive episode in the leaderless-consensus literature is Pierre Sutra's 2019/2020 discovery [6] that EPaxos's TLA+ specification *and* its Go implementation tracked only a single ballot variable per replica, where the protocol's safety proof requires two: *bal* (last ballot joined) and *vbal* (last ballot at which the replica voted), with *vval* the value voted. This is the standard (A1)–(A5) ballot discipline of repeated consensus: a process joining ballot *b* must seal all lower ballots and report the value voted at the *highest* lower ballot it voted in. Collapsing the two variables lets a replica report a stale *vval* as if voted at a recent ballot, or vice versa.

> **Theorem (Sutra [6]).** There exists an admissible execution of the single-variable EPaxos specification with three replicas {*p1, p2, p3*} and two interfering commands *c1, c2* such that *dep(c2) = ∅* at *p2* while *dep(c2) = {c1}* at *p1* — violating (E1) and hence linearizability.
> *Proof sketch.* The counterexample chains consecutive recovery phases: *p3* accepts *{c2}* at ballot 1; *p1, p2* accept *∅* at ballot 2; *p3* then joins ballot 3, and because it reports only one ballot number, the recovering leader cannot tell whether *p3*'s vote for *{c2}* occurred at ballot 1 or later. It commits *{c2}* at ballot 4 while *p2* has already committed *∅* — permanent disagreement on the dependency set. ∎

The lesson is methodological: the SOSP pseudocode [1, Fig. 3] correctly identifies the need to report "the most recent ballot number accepted," but the mechanized specification and the running code both dropped the second variable — and the original proofs did not catch it. Leaderless protocols multiply the distributed state that must be tracked correctly; machine-checked specification is the primary line of defense, and later EPaxos derivatives adopt the two-variable discipline.

## 5 Empirical Results and Proofs

### 5.1 The fast-path quorum theorem

> **Theorem (EPaxos fast-quorum cardinality).** With *N = 2f + 1* replicas, a fast quorum of size *Q_fast = f + ⌊(f+1)/2⌋ + 1* is necessary and sufficient for the fast path to be safe under *f* crash failures.
> *Proof sketch.* Sufficiency: a slow-path recovery contacts a classic quorum *Q_c* of *f+1*. Any two fast quorums *Q1, Q2* and *Q_c* must share a common member — the *triple intersection* invariant (A4′) inherited from Fast Paxos [4][6] — so recovery observes at most one spontaneously-agreed dependency set and can always recover it as the most-voted value. With *Q_fast = f + ⌊(f+1)/2⌋ + 1*, we have *|Q1 ∩ Q2 ∩ Q_c| ≥ 1* by counting: *2Q_fast + (f+1) > 2N + f* ⟺ the bound. Necessity: a smaller fast quorum admits two disjoint-ish fast quorums whose spontaneous agreements on *different* dependency sets a recovery quorum cannot disambiguate, breaking (E1). ∎

For *f = 1*, *Q_fast = 3 = N* (unanimity); for *f = 2*, *Q_fast = 4* of 5. The cost of leaderlessness is thus paid in quorum width, not in latency.

### 5.2 Linearizability via monotonic execution graphs

> **Theorem (EPaxos linearizability [1][6]).** If (E1) and (E2) hold and each replica's execution graph grows monotonically, then the replicated service is linearizable.
> *Proof sketch.* (E2) totally orders every non-commuting pair by the agreed dependency relation plus real-time precedence; monotonicity prevents executing *c* before a later-discovered dependency *d* — *d* is already in *dep(c)* by (E1), so execution waits. Commuting pairs may interleave arbitrarily. Every operation thus appears to take effect atomically between invocation and response. ∎

### 5.3 Reinterpreting the published measurements

Moraru et al. [1] evaluated EPaxos on Amazon EC2 across five regions with *N = 5*. Key results, reinterpreted:

- **Latency.** At low contention EPaxos commits in one RTT to the nearest fast quorum, beating Multi-Paxos by up to ~50% in the wide area by avoiding the detour to a fixed leader's region.
- **Throughput.** Uniform load balancing lets EPaxos scale throughput roughly linearly with *N* until network saturation, whereas Multi-Paxos plateaus at the leader's capacity.
- **Robustness.** Under a slow replica EPaxos's flexible quorum composition excludes the straggler; Multi-Paxos's tail latency degrades when the leader's majority includes the slow node, and leader failure triggers a full election stall. EPaxos shows graceful degradation with no availability gap.
- **Contention sensitivity.** As the interference probability *p* rises, the slow-path fraction rises with it: at high contention EPaxos converges to two-RTT commits and its advantage over Multi-Paxos narrows.

Mao et al. [2] report that Mencius achieves low latency under low load and high throughput under high load, but document its sensitivity to variance: one slow server inflates commit latency for *all* servers via the in-order commit rule — the head-of-line blocking of §4.1. This is where EPaxos's dependency model dominates: no global log order means no head-of-line blocking at all.

```python
# Latency-contention model: expected commit latency vs interference probability p
def expected_latency(p, rtt_fast=1.0, rtt_slow=2.0, leader_detour=0.0):
    """p: fraction of commands that interfere with a concurrent command."""
    return leader_detour + (1 - p) * rtt_fast + p * rtt_slow

# Wide-area, 5 replicas, client far from any fixed leader:
# Multi-Paxos: detour ~1 extra RTT to leader region
# Mencius:    local coordinator, but slow-path on contention & stragglers
# EPaxos:     nearest fast quorum, no detour
for p in (0.0, 0.1, 0.5, 0.9):
    print(p,
          round(expected_latency(p, leader_detour=1.0), 2),   # Multi-Paxos/Raft
          round(expected_latency(p, leader_detour=0.0), 2))   # EPaxos
# 0.0 2.0 1.0 | 0.1 2.1 1.1 | 0.5 2.5 1.5 | 0.9 2.9 1.9
```

The model omits batching, pipelining, and read leases, but captures the first-order effect in both papers' measurements: leaderless protocols win by subtracting the leader detour, and lose ground in proportion to contention.

## 6 Limitations

1. **Contention collapse.** EPaxos's fast path needs spontaneous agreement; under highly interfering workloads the slow path dominates and the protocol can underperform a well-provisioned single leader. Mencius has no such cliff but pays the skip/straggler tax.
2. **Quorum width.** Fast quorums exceed majorities (*f + ⌊(f+1)/2⌋ + 1* vs *f + 1*), so EPaxos is more exposed to tail latency within the fast quorum — though flexible composition mitigates this.
3. **Execution complexity.** Linearizing a dependency DAG per replica costs more than replaying a log; dependency sets grow with concurrency, and deciding when *dep(c)* is stable for garbage collection is a non-trivial burden.
4. **Specification fragility.** The Sutra counterexample [6] shows leaderless protocols have more distributed state to get right, and the gap between pseudocode, spec, and implementation is where safety is lost. The two-ballot-variable discipline is necessary and reimplementations must be model-checked against it.
5. **Read asymmetry.** Single-leader protocols support cheap *read leases* anchored at the leader; leaderless protocols must route reads through dependency agreement or add a separate read protocol, eroding the latency win for read-heavy workloads.
6. **Scope of guarantees.** All protocols here assume crash failures and partial synchrony for liveness; none of the fast-path results transfer to Byzantine settings without substantial redesign.

## 7 Conclusion

The arc from Paxos to EPaxos is the arc from *agreeing on an order* to *agreeing on just enough order*. Single-leader protocols — Multi-Paxos, Raft [3] — buy simplicity at the cost of load concentration, wide-area detours, and election stalls. Mencius [2] showed leadership can be parallelized by partitioning the instance space, paying with a global commit rule that reintroduces head-of-line blocking. Generalized consensus [4] supplied the theory: commands form a partial order and non-interfering commands need never be serialized. EPaxos [1] made it practical, with a fast path committing in one RTT to the nearest fast quorum and quorum cardinality *f + ⌊(f+1)/2⌋ + 1* provably necessary and sufficient. The Sutra episode [6] is the cautionary coda: distributing the leader's duties distributes the opportunities for subtle error, and mechanized verification must track every ballot variable the proof requires. When command interference is rare — the common case in geo-replicated services — leaderless generalized consensus strictly dominates single-leader replication; under high contention and severe write skew, the humble leader still earns its keep.
