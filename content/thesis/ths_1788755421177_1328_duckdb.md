# In-Process Columnar Analytics at Vector Scale: Vectorized Execution, Morsel-Driven Parallelism, MVCC with Hybrid Scans, and Adaptive Radix Indexing in DuckDB

## Abstract

DuckDB proves a full analytical DBMS can live inside a host process — no server, no protocol, no daemon — while rivaling distributed OLAP engines on a single machine. This thesis analyzes the five pillars enabling this: (i) a vectorized execution engine from the MonetDB/X100 lineage [2], replacing per-tuple interpretation with tight loops over columnar batches; (ii) morsel-driven parallelism [3], fragmenting pipelines into dynamically scheduled work units for near-linear multi-core scaling; (iii) HyPer-style MVCC [4] reconciling transactional writes with analytical scans via hybrid scans of committed and transaction-local data; (iv) columnar storage in row groups with zone maps and lightweight compression codecs; and (v) adaptive radix tree (ART) secondary indexes [5] preserving point-lookup and range performance. We formalize the vectorization amortization argument, derive morsel-scheduling bounds, and quantify how compression, zone maps, and vectorized scans interact — a precise account of server-class analytics with library-class deployment.

## 1. Introduction

The popularity of SQLite proved that there is enormous demand for *in-process* data management: a database that is a library, linked into the application, with zero administrative overhead [1]. Yet SQLite is a row-oriented, tuple-at-a-time OLTP engine, and the analytical workloads that dominate modern data science — aggregations over billions of rows, multi-way joins, window functions — are precisely the workloads on which row stores perform worst. The embedded-analytics niche was long served by shipping data out-of-process to a server or by tolerating a row store's order-of-magnitude analytical gap.

DuckDB [1] closes this gap by transplanting a modern columnar analytical engine into a dependency-free, embeddable library — a synthesis of five ideas from landmark publications, each adapted to running inside someone else's process:

1. **Vectorized execution**, inspired by MonetDB/X100's hyper-pipelining model [2]: operators consume and produce *vectors* — contiguous arrays of column values — rather than single tuples, amortizing interpreter overhead and exposing data-level parallelism.
2. **Morsel-driven parallelism**, from Leis, Boncz, Kemper, and Neumann [3]: a query pipeline is fragmented into small morsels of work that are dispatched dynamically to worker threads, yielding elastic, NUMA-aware scaling on many-core machines.
3. **MVCC with hybrid scans**, following the serializable main-memory MVCC of Neumann, Mühlbauer, and Kemper [4]: a single-writer/multiple-reader protocol in which scans transparently merge committed columnar data with transaction-local deltas.
4. **Columnar storage with zone maps and compression**: tables are partitioned into row groups of approximately 122,880 rows, each carrying per-column minimum/maximum statistics, with per-segment codecs including RLE, dictionary encoding, bit packing, patched frame-of-reference (PFOR), and FSST for strings.
5. **Adaptive radix tree (ART) indexes** [5], providing space-efficient secondary indexes for constraints (`PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY`) and selective predicates.

The in-process constraint shapes every choice: no shared buffer pool, no background checkpoint process, no assumption that the machine belongs to the database. DuckDB must be a good citizen — bounded memory, cooperative scheduling, crash-safe storage. This thesis analyzes how each pillar meets that constraint.

## 2. Background

### 2.1 The execution-model spectrum

Classical Volcano-style engines interpret one tuple at a time: each operator exposes a `next()` method, and a tuple climbs the operator tree through a chain of virtual-function calls. The per-tuple overhead — dispatch, branching, type checks — dominates when the actual work per tuple is a few integer comparisons. MonetDB/X100 [2] made the *vector* the unit of interpretation: operators are invoked once per batch of values, and the inner loop is a tight, branch-predictable, compiler-vectorizable sequence over a contiguous array. X100's "hyper-pipelining" recovers most of the performance of hand-written code while retaining an interpreted engine's flexibility. DuckDB adopts this model with a default vector size of 2048 [1].

### 2.2 Parallelism for the many-core age

Static partitioning divides work before execution and suffers under skew. Morsel-driven parallelism [3] instead treats the pipeline as a stream of small input fragments — *morsels* — pulled by whichever worker thread becomes free. Load balancing is therefore automatic and fine-grained, and the scheme is NUMA-aware when morsels are preferentially scheduled on the socket holding their data.

### 2.3 Concurrency control for mixed workloads

HyPer's MVCC design [4] showed that serializable multi-version concurrency control can be nearly free in a main-memory system: readers operate on immutable snapshots identified by transaction timestamps while a single writer appends new versions. DuckDB follows this lineage — multiple concurrent readers, one writer — matching the embedded pattern of bulk loads interleaved with heavy read queries.

### 2.4 Indexing main-memory columns

The adaptive radix tree [5] adapts its node fan-out (4, 16, 48, 256 children) to the actual key distribution, giving trie-ordered traversal — hence range scans — with near-hash-table space efficiency. DuckDB builds ART indexes for declared constraints and explicit `CREATE INDEX` statements, with version-aware entries preserving transactional semantics.

## 3. Methodology

We reconstruct each subsystem from its primary publication and DuckDB's documented design, stating key invariants as theorems. We then model the subsystems *jointly*: a zone map that skips a row group also skips its decompression and vectorization work, and MVCC visibility checks must themselves be vectorized. Finally we derive quantitative bounds — amortization factors, makespan bounds, hybrid-scan cost models — grounded in the SIGMOD 2019 demonstration paper [1], the five foundational papers DuckDB's documentation cites [2][3][4][5], the optimizer literature [7], the window-function work it implements [6], and an independent TPC-H study of its compressed vectorized execution [8].

## 4. Deep Dive

### 4.1 Vectorized execution: hyper-pipelining in an embedded engine

The core abstraction is the **vector**: a contiguous array of one logical type with a validity (null) mask and a *selection vector* representing filtered subsets without data movement. A physical operator implements one method — `execute(input_chunk, output_chunk)` — transforming whole vectors; a `DataChunk` groups the vectors of all columns in a pipeline stage, so each invocation does useful work on thousands of values per dispatch.

> **Theorem (Vectorization amortization):** Let *c<sub>d</sub>* be the fixed dispatch cost of invoking a physical operator and *c<sub>t</sub>* the marginal cost of processing one tuple within the operator's inner loop. For a vector of *V* tuples, the per-tuple cost is *c<sub>d</sub>/V + c<sub>t</sub>*, versus *c<sub>d</sub> + c<sub>t</sub>* for tuple-at-a-time interpretation. As *V → 2048*, the dispatch term becomes negligible, and the achievable throughput approaches the memory-bandwidth limit of the inner loop. *This is the quantitative content of the X100 hyper-pipelining argument [2].*

Three mechanisms make the inner loops fast in practice:

- **Selection vectors.** A filter writes surviving row indices into a selection vector instead of copying rows; downstream operators iterate it, touching only live values — filtering becomes an indexing problem, not a data-movement problem.
- **Type-specialized primitives.** Each operator is specialized per physical type, so the inner loop over an `INTEGER` column has no type checks or runtime branches — just arithmetic the compiler auto-vectorizes into SIMD.
- **Late materialization.** Variable-length data is referenced through offsets and dictionary codes until an operator genuinely needs the bytes; FSST-compressed strings can even be probed in compressed form.

The following sketch captures the operator contract in DuckDB's C++ core:

```cpp
// Simplified physical operator interface (vector-at-a-time)
class PhysicalOperator {
public:
    // Processes one DataChunk (up to STANDARD_VECTOR_SIZE = 2048 rows)
    virtual OperatorResultType Execute(ExecutionContext &context,
                                       DataChunk &input,
                                       DataChunk &chunk) const = 0;
};

// Example: vectorized filter using a selection vector
void FilterIntegerGT(DataChunk &input, DataChunk &output,
                     idx_t col, int32_t threshold) {
    auto &vec = input.data[col];
    auto *data = (int32_t *) vec.GetData();
    sel_t sel[STANDARD_VECTOR_SIZE];
    idx_t n = 0;
    // Tight, auto-vectorizable loop: one branch per 2048 values' worth
    // of work is amortized; the inner predicate is branchless-friendly.
    for (idx_t i = 0; i < input.size(); i++) {
        if (data[i] > threshold) sel[n++] = i;
    }
    output.Slice(input, sel, n); // zero-copy via selection vector
}
```

*Figure 1 — The vectorized pipeline. Columnar batches flow left to right through physical operators; each operator invocation amortizes dispatch cost over 2048 values, and selection vectors propagate filters without data movement.*

Throughput is thus bounded by memory bandwidth rather than interpreter overhead — the regime of hand-tuned columnar loops — while the optimizer and executor remain fully general.

### 4.2 Morsel-driven parallelism: elastic scheduling on many cores

Parallelism in DuckDB is not a property of individual operators; it is a property of the *pipeline*. The optimizer's physical plan is divided into pipelines separated by pipeline breakers (hash-table builds, sorts, aggregations). Each pipeline is then fragmented into morsels — small, self-contained units of input, typically a few row groups or a partition of a hash table — and a dispatcher hands morsels to a pool of worker threads.

The design has three decisive advantages over static partitioning:

1. **Automatic load balancing.** A thread that finishes its morsel immediately takes another; data skew cannot strand work on one core while others idle — the dispatcher *is* the load balancer.
2. **Elasticity.** Active workers adapt to available parallelism; a small pipeline generates few morsels and wastes no threads.
3. **NUMA awareness.** Morsels carry locality hints and the dispatcher prefers the socket holding their data [3], avoiding cross-interconnect traffic on scan-heavy queries.

> **Theorem (Morsel scheduling bound):** Let *T<sub>1</sub>* be the total work of a pipeline and *T<sub>∞</sub>* its critical-path length. With *p* workers pulling morsels of maximum processing time *m*, the makespan satisfies *T<sub>p</sub> ≤ T<sub>1</sub>/p + T<sub>∞</sub>*, and the granularity term contributed by the final partial wave of morsels is *O(m)*. Choosing *m* small (thousands of rows) makes the *O(m)* term negligible while keeping dispatch overhead — one queue operation per morsel — far below the per-morsel useful work. *This is the standard greedy-scheduling bound instantiated for morsel dispatch [3].*

```sql
-- Morsel parallelism is transparent: the same query scales with thread count
PRAGMA threads=8;
SELECT l_returnflag, l_linestatus,
       sum(l_quantity) AS sum_qty,
       avg(l_extendedprice) AS avg_price,
       count(*) AS count_order
FROM lineitem
WHERE l_shipdate <= DATE '1998-12-01' - INTERVAL 90 DAY
GROUP BY l_returnflag, l_linestatus
ORDER BY l_returnflag, l_linestatus;
-- The scan pipeline is fragmented into morsels (row-group granularity);
-- the aggregation pipeline re-partitions morsels by grouping key.
```

![Morsel-driven parallelism: pipeline fragmented into morsels dispatched to worker threads across CPU cores with NUMA-aware scheduling](/thesis/ths_1788755421177_1328_duckdb-2.webp)

*Figure 2 — Morsel-driven scheduling. The pipeline graph is fragmented into small work units; a dispatcher assigns morsels to worker threads, preferring the NUMA node holding each morsel's data.*

Morsels compose with vectorization: each morsel runs the *same* vectorized pipeline code, so parallelism multiplies vectorized throughput. The mechanisms are orthogonal by construction — one scales the inner loop, the other the number of loops.

### 4.3 MVCC and hybrid scans: transactions inside the process

DuckDB implements ACID transactions with a single-writer/multiple-reader MVCC protocol in the HyPer tradition [4]. Each transaction gets a monotonically increasing identifier; committed data carries its writer's id, and each transaction observes the database as of its start timestamp. The writer appends into **transaction-local storage** — an uncommitted row-oriented delta — while readers scan the committed columnar image; on commit the delta merges into main storage and indexes update atomically.

The scan operator that makes this transparent is the **hybrid scan**. Rather than forcing the transaction-local delta through a separate code path, the scan merges both sources into the vectorized stream:

| Source | Layout | Visibility rule |
|---|---|---|
| Committed storage | Columnar, compressed, row-grouped | Visible iff commit-ts ≤ reader start-ts |
| Transaction-local delta | Row-oriented, uncommitted | Visible only to the owning transaction |
| Deleted rows | Version chain / delete markers | Invisible iff delete-ts ≤ reader start-ts |

The merge is vectorized: the scan emits vectors from committed segments, then appends vectors materialized from the local delta, applying the snapshot predicate as a selection vector. The delta holds only one transaction's writes, so merge cost is negligible for analytical scans:

> **Theorem (Snapshot isolation of the hybrid scan):** A hybrid scan returns exactly the set of row versions whose validity interval contains the reader's start timestamp: versions committed by transactions with commit-ts ≤ start-ts, plus the reader's own uncommitted writes, minus versions deleted by transactions with commit-ts ≤ start-ts. *This is the standard MVCC snapshot property [4], preserved by DuckDB's merge of committed and transaction-local sources.*

Conflict handling is deliberately simple: one active writer means no write-write conflicts, and readers on immutable snapshots never block the writer. Superseded versions are cleaned cooperatively at checkpoints. DuckDB is therefore not a multi-writer OLTP engine — a conscious trade for its bulk-load-then-analyze target.

### 4.4 Columnar storage: row groups, zone maps, and compression

DuckDB partitions each table into **row groups** of approximately 122,880 rows, stored column by column as independently compressed **column segments**. Each segment records **zone-map statistics** (minimum and maximum), letting scans skip entire row groups whose range excludes the filter predicate [8].

A scan reads one column segment at a time, decompresses it into 2048-value vectors, and feeds the pipeline. Predicate pushdown operates at two granularities — row-group skipping via zone maps, then vectorized filtering within survivors — and they multiply: a selective predicate on a clustered column eliminates most I/O before a single vector is produced.

Each segment's codec is chosen from a portfolio matched to physical types:

| Codec | Target data | Principle |
|---|---|---|
| RLE (run-length encoding) | Low-cardinality runs | `(value, run-length)` pairs |
| Dictionary encoding | Low-cardinality columns | Integer codes into a dictionary |
| Bit packing | Small-range integers | Minimal fixed bit-width per value |
| PFOR (patched frame-of-reference) | Integers with outliers | Delta base + packed residuals, exceptions patched |
| FSST | Strings | Fast single-symbol entropy coding |
| ALP / Chimp / Patas | Floating point | Leading-zero and XOR-based float schemes |

> **Theorem (Compression–scan composition):** If a column segment of *N* values compresses by ratio *r* and decompression throughput is *D* values/s while the scan pipeline consumes *C* values/s, the effective scan rate is *min(r·B, D, C)* where *B* is the storage bandwidth in values/s. Compression therefore accelerates scans whenever the workload is I/O-bound (*r·B < C*) and decompression keeps pace (*D ≥ r·B*) — the regime DuckDB's lightweight codecs are engineered for. *Independent measurements of DuckDB's compressed vectorized scans under TPC-H confirm the I/O-bound acceleration [8].*

![Columnar storage layout: row groups of 122880 rows split into compressed column segments with zone-map min/max statistics](/thesis/ths_1788755421177_1328_duckdb-0.webp)

*Figure 3 — Physical storage. Tables are partitioned into row groups; each column segment carries zone-map statistics and a per-type compression codec, so scans skip irrelevant groups and read only queried columns.*

Row-group granularity harmonizes with morsel scheduling: a morsel is naturally a row group, so the unit of parallelism, the unit of I/O, and the unit of zone-map pruning coincide.

### 4.5 Adaptive radix trees and secondary access paths

Columnar scans excel at bulk predicates but not point lookups or highly selective ranges. DuckDB therefore maintains **ART indexes** [5] for `PRIMARY KEY`, `UNIQUE`, and `FOREIGN KEY` constraints and explicit `CREATE INDEX` statements. The ART adapts node sizes to key density, so sparse 64-bit keys cost little more than a hash table while supporting ordered range traversal — lookup is *O(k)* in key length, independent of table size.

Index maintenance is version-aware: uncommitted entries carry the writer's transaction id and become visible atomically at commit alongside the §4.3 data merge. The optimizer's choice between ART probe and pruned scan is cost-based [7]: low selectivity favors the columnar scan, high selectivity the ART probe — decided per query block by the DPsize-style dynamic-programming optimizer with decorrelation of nested queries.

```sql
-- ART index backs the constraint and accelerates selective predicates
CREATE TABLE events (
    event_id BIGINT PRIMARY KEY,
    event_ts TIMESTAMP,
    category VARCHAR
);
-- Point lookup: ART probe, O(key length), no scan
SELECT * FROM events WHERE event_id = 42000117;
-- Range on indexed key: ordered ART traversal
SELECT * FROM events WHERE event_id BETWEEN 42000100 AND 42000200;
```

## 5. Empirical Results / Proofs

We now instantiate the §4 theorems with DuckDB's documented constants and published independent measurements [8].

**Vectorization amortization (instantiated).** With *V = 2048* and dispatch cost *c<sub>d</sub>* of tens of nanoseconds, *c<sub>d</sub>/V* falls below 0.1 ns per tuple — three orders of magnitude under Volcano iteration. The residual *c<sub>t</sub>* is dominated by memory traffic, which is why vectorized engines converge to memory-bandwidth limits on scans [2].

**Morsel scaling.** For a scan-aggregate over *R* rows, *T<sub>1</sub> = R·w* and *T<sub>∞</sub>* is the longest stage over one morsel plus the final merge. Instantiating *T<sub>p</sub> ≤ T<sub>1</sub>/p + T<sub>∞</sub>* for a 600M-row scan-aggregate (64 s single-threaded, morsel ≈ one 122,880-row group):

| Threads *p* | Model bound *T<sub>p</sub>* (s) | Ideal *T<sub>1</sub>/p* (s) | Efficiency |
|---|---|---|---|
| 1 | 64.0 | 64.0 | 100% |
| 2 | 32.4 | 32.0 | 99% |
| 4 | 16.6 | 16.0 | 96% |
| 8 | 8.7 | 8.0 | 92% |
| 16 | 4.9 | 4.0 | 82% |
| 32 | 3.2 | 2.0 | 63% |

Efficiency decays at high core counts as the *T<sub>∞</sub>* term asserts itself — serial merge and dispatcher contention bound speedup, matching morsel-driven engines [3] and the plateau in independent DuckDB TPC-H studies [8].

**Hybrid-scan overhead.** Merging transaction-local deltas adds *O(δ)* work per scan with *δ* the uncommitted write volume; the per-vector visibility check is one integer comparison folded into selection-vector computation — overhead well under 5% when *δ ≪ R* [4][8].

**Zone-map pruning.** On a table clustered by the filtered column, a range predicate of selectivity *s* prunes ≈*(1 − s)* of row groups, cutting I/O by the same factor before vectorization begins — tight zone maps convert *O(R)* scans into *O(s·R)* scans [8].

**ART vs. scan crossover.** An ART probe costs *O(k + s·R)* versus *O(s′·R)* for the zone-map-pruned scan (*s′* the surviving fraction). The cost model [7] picks the ART path when *k + s·R < s′·R* — highly selective predicates on indexed keys.

## 6. Limitations

The architecture's strengths are inseparable from its boundaries:

- **Single-writer concurrency.** The MVCC protocol admits exactly one concurrent writer. Workloads with many simultaneous small writers — the OLTP mainstream — are not DuckDB's domain; write-write conflicts are resolved by exclusion rather than by optimistic concurrency.
- **In-process resource contention.** DuckDB shares the host's memory and CPU; memory limits and thread counts must be configured cooperatively, with no server-style isolation boundary.
- **Vector-size rigidity.** The fixed 2048-value vector suits wide scans but taxes operators with tiny inputs (filter tails, small dimensions) with dispatch cost on near-empty vectors.
- **Compression–update tension.** Per-segment compression assumes append-mostly writes; frequent small updates force segment rewrites, deferred to commit by the transaction-local delta (§4.3) but still fragmenting the layout.
- **Index maintenance cost.** Each ART index adds *O(k)* per inserted key at commit, serializing part of the writer's path — the classic write-amplification trade-off.
- **NUMA limits of morsel scheduling.** Locality hints are heuristics; on larger or asymmetric NUMA topologies, interconnect bandwidth can remain the binding constraint [3].

## 7. Conclusion

DuckDB's achievement is compositional. Vectorized execution [2] removes the interpreter tax; morsel-driven parallelism [3] converts it into multi-core speedup with automatic load balancing; HyPer-style MVCC with hybrid scans [4] adds transactions without breaking the vectorized scan path; row-grouped columnar storage with zone maps and per-type codecs minimizes the one resource that matters — I/O; adaptive radix trees [5] restore selective access without a row store. A dynamic-programming optimizer [7] with decorrelation and cost-based access-path selection binds these into near-optimal plans, while segment-tree aggregation [6] extends the vectorized model to window functions.

The deeper lesson is about *embedding*: accepting life inside a host process — no daemon, no isolation, no administration — forced the decisions that make DuckDB fast: zero-copy exchange with the host language, cooperative resource usage, crash-safe storage without a background process. The in-process OLAP engine is not a lesser database but the analytical database with deployment friction removed — and its architecture of vectors, morsels, versions, row groups, and adaptive indexes is a durable template for embedded analytics.
