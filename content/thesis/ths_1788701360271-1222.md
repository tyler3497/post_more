# Vectorized Columnar Query Execution in DuckDB and ClickHouse: Late Materialization, SIMD-Optimized Operators, MergeTree vs Parquet Storage Layouts, and Analytical Performance at Billions of Rows

## Abstract

Analytical workloads scanning billions of rows demand engines and storage layouts that respect modern hardware: deep cache hierarchies, wide SIMD units, and limited memory bandwidth. This thesis examines the vectorized columnar execution paradigm shared by DuckDB and ClickHouse, tracing its lineage from the MonetDB/X100 hyper-pipelining model through morsel-driven parallelism to today's production engines. We formalize vector-at-a-time execution, analyze *late materialization* strategies that defer tuple reconstruction until absolutely required, and quantify how SIMD-optimized operator kernels exploit data-level parallelism on cache-resident vectors. A central comparison contrasts ClickHouse's MergeTree engine family — ordered, sparse-indexed, immutable parts with background merges — against the Apache Parquet format consumed by DuckDB scans, evaluating I/O amplification, predicate pushdown granularity, and compression. Drawing on published benchmarks and micro-benchmarks, we show vectorized execution delivers order-of-magnitude speedups over tuple-at-a-time Volcano iteration, late materialization cuts memory traffic by 40–70% on narrow projections over wide tables, and storage layout choice dominates end-to-end performance at billion-row scale more than any execution micro-optimization.

## 1. Introduction

The dominant cost in analytical query processing has shifted. Two decades of processor evolution — wider issue widths, 512-bit vector registers, deep cache hierarchies — have made computation cheap and data movement expensive. A scan-heavy query such as TPC-H Q6 is bound not by arithmetic but by the memory bus. Row-oriented tuple-at-a-time engines, descendants of the Volcano iterator model [1], pay a per-tuple interpretation tax on top of that data movement, achieving instruction-per-cycle (IPC) efficiencies as low as 0.7 on decision-support workloads.

Two systems exemplify the modern response, from opposite ends of the deployment spectrum. **DuckDB** [2] is an embedded, in-process analytical database — "the SQLite of OLAP" — processing vectors of typically 2048 tuples through a pull-based pipeline. **ClickHouse** is a distributed columnar DBMS whose MergeTree engine family [4] stores petabytes in sorted, immutable parts and executes queries with hand-tuned SIMD kernels over blocks of columns. Despite their different topologies, both converge on one insight: process *vectors* of column values, keep intermediate state cache-resident, and exploit data-level parallelism aggressively.

We answer these questions through a synthesis of the foundational literature [1, 3, 7, 8], the systems' own architectural documentation [2, 4, 5], and a reproducible micro-benchmark methodology (§3) that isolates each effect.

## 2. Background

### 2.1 The Volcano Iterator Model and Its Costs

The classical Volcano execution model implements each relational operator with `Open()`, `Next()`, and `Close()` methods; `Next()` returns a single tuple to its parent. This model is elegant but suffers three compounding inefficiencies on modern CPUs: (i) a virtual function call per tuple per operator, defeating instruction-cache locality and branch prediction; (ii) interpretation overhead, since generic operators test type and nullability per tuple; and (iii) no SIMD opportunity, since there is no contiguous homogeneous array to vectorize over [1].

### 2.2 MonetDB/X100: Hyper-Pipelining

Boncz, Zukowski, and Nes [1] diagnosed the problem by instrumenting TPC-H Q1 across MySQL, MonetDB/MIL, and a prototype vectorized engine. Their finding: tuple-at-a-time engines spent the overwhelming majority of cycles on *interpretation* rather than arithmetic. Their remedy, MonetDB/X100, processes *vectors* — vertically partitioned fragments of a single column, typically ~1000 entries — through type-specialized primitives. Vectors are small enough to remain in L1/L2 cache while a pipeline of operators processes them, and per-call overhead amortizes across the vector length. The paper also introduced the **selection vector**, an index array naming the qualifying positions within a vector, letting filters apply without copying data: downstream operators iterate only over the selected indices.

This is the direct intellectual ancestor of both DuckDB and ClickHouse: DuckDB's `Vector` type (FLAT, CONSTANT, DICTIONARY, SEQUENCE representations) and 2048-tuple standard vector size descend from X100's design space [2], while ClickHouse's `Block` — a collection of column arrays processed by template-specialized functions — is the same idea in a server-oriented engine.

### 2.3 Columnar Storage and Materialization

Columnar storage decomposes relations into per-attribute files or column chunks, so a query reading *k* of *n* columns touches only the *k* relevant ones [8]. The layout creates a new scheduling question: when should the engine *materialize* — reconstruct full tuples from positional column values? Abadi et al. [7] formalized a spectrum from **early materialization** (reconstruct tuples at the scan, evaluate row-wise) to **late materialization** (propagate row-IDs through operators, fetching only the columns each operator needs). Late materialization saves bandwidth because columns never touched by predicates or the final projection are never read; however, it can randomize access when positions must be gathered from disk out of order.

### 2.4 SIMD and Data-Level Parallelism

Single-Instruction-Multiple-Data (SIMD) units execute one operation across 4, 8, 16, or 32 lanes in a single cycle. Columnar data is the ideal input: a scan over a contiguous `int32` array is a perfectly vectorizable loop. Kersten et al. [3] measured SIMD speedups of up to **8.4×** on a selection microbenchmark, but cautioned that the gain collapses to ~1.4× on full TPC-H queries where the engine is memory-bandwidth bound. The practical lesson: SIMD matters most combined with cache-resident vectors and compression that keeps the working set in the cache hierarchy.

> **Theorem (Vectorization Amortization):** *Let a pipeline of p operators each incur fixed per-call cost c when processing a batch, with per-tuple work w. The per-tuple overhead is c/v + w for batch size v. As v grows, per-tuple overhead approaches w; however, when v × tuple-width exceeds L1/L2 capacity, intermediate materialization forces DRAM traffic, and the effective per-tuple cost rises again. The optimal vector size is therefore the largest v such that the pipeline's working set remains cache-resident.*

### 2.5 Storage Layouts: MergeTree and Parquet

**MergeTree** [4] is ClickHouse's canonical table engine family. Data is ingested as sorted, immutable *parts*, indexed by a sparse *primary key index* (one entry per 8192-row granule) plus optional data-skipping indices; background merges compact parts. **Parquet** [5] is the open columnar file format derived from Google's Dremel record shredding [6]: row groups of column chunks with per-chunk statistics, encodings, and compression, which DuckDB scans natively with predicate pushdown [2].

## 3. Methodology

Our analysis combines three evidence sources:

1. **Literature synthesis.** We reconstruct each engine's design rationale from the primary sources [1–8], emphasizing quantitative claims (IPC measurements, speedup factors, vector sizes) that can be cross-checked.
2. **Analytical modeling.** First-order cost models for the vectorized pipeline (§4.1), late-materialization bandwidth savings (§4.2), and storage-layout I/O amplification (§4.4), parameterized by vector size *v*, selectivity *σ*, projection width *k*, and compression ratio *r*.
3. **Reproducible micro-benchmarks.** A reference harness (Python orchestration over both engines) with three workloads: **W1** — scan-filter-aggregate over a 1-billion-row synthetic table (8 columns), mirroring TPC-H Q6; **W2** — narrow projection over a wide table (2 of 64 columns, σ = 0.05), isolating late-materialization effects; **W3** — range scan with point-lookup tail (σ = 0.001 on a sorted key), isolating sparse-index and statistics-based skipping. Each runs under cold and warm page cache, five repetitions, median wall-clock time (§5).

## 4. Deep Dive

### 4.1 Vectorized Execution: Semantics, Selection Vectors, and Morsels

A vectorized operator consumes and produces **DataChunks**: a batch of *v* rows as one contiguous array per column plus a shared validity bitmap. The pull-based pipeline from Volcano is retained — a parent calls `GetData()` on its child — but each call returns thousands of tuples, amortizing call overhead by a factor of *v* [1, 2].

Filtering without materialization is the subtle part. A naive filter would compact qualifying values into a new dense array (a *memcpy*-heavy operation). The **selection vector** avoids this: an index array `[i₁, i₂, …, iₘ]` of the *m* qualifying positions. Downstream operators are *selection-vector aware*: instead of iterating `0..v-1`, they iterate over the selection vector. In DuckDB, operators branch to a specialized inner loop when the input carries a selection vector, and the physical type system lets the engine skip work entirely in degenerate cases — a CONSTANT vector needs no loop at all.

Parallelism comes from **morsel-driven scheduling** (Leis et al., SIGMOD 2014, as adopted by DuckDB): the input is partitioned into *morsels* (tens of thousands of rows), and worker threads pull morsels from a shared pool, executing the entire pipeline on each. This yields automatic load balancing and NUMA-aware placement with no synchronization *within* a morsel. Pipeline breakers (hash-table builds, sorts, aggregations) use thread-local pre-aggregation followed by a global combine, or partitioned parallel builds.

The cost model for a scan-filter-aggregate pipeline is instructive:

> **Theorem (Vectorized Pipeline Cost):** *For a scan over N rows with selectivity σ, vector size v, per-vector call overhead c, and per-tuple kernel cost w, total CPU cost is approximately N·(c/v + w). Memory traffic is N·σ·k·s bytes for k projected columns of average width s. The dominant term at billion-row scale is memory traffic — which is why late materialization and compression (§4.2, §4.4) matter more than shaving cycles from w.*

### 4.2 Late Materialization: Deferring Tuple Reconstruction

In a column store, a query plan touches only a subset of columns at each operator. Early materialization reconstructs full tuples at the scan: every operator then pays the bandwidth cost of wide tuples, even if it examines one column. Late materialization instead propagates **positions** (row IDs) through the operator tree and fetches column values lazily, only for the columns and rows that survive to each stage [7].

Consider W2: a 64-column table, query projects 2 columns with selectivity σ = 0.05. Early materialization reads all 64 columns for every row. Late materialization reads only the *predicate* columns for all rows, then fetches the 2 projected columns for the surviving 5% of positions:

| Strategy | Bytes read (per row, widths normalized) |
|---|---|
| Early materialization | 64 · s |
| Late, predicate cols *p*, projected *k* | (p + σ·k) · s |
| Example: p=1, k=2, σ=0.05 | 1.1 · s — a **58×** reduction |

In practice, position-based fetching randomizes disk access. Both DuckDB and ClickHouse therefore implement *hybrid* strategies: within a vector (a few thousand rows), positions are effectively contiguous, so late materialization inside a pipeline stage is nearly free, while cross-stage materialization points are chosen by the optimizer where access would otherwise degenerate [7]. The literature reports 40–70% memory-traffic reductions on narrow projections over wide tables, with the benefit saturating — and occasionally reversing — when σ is high (position indirection adds overhead without saving I/O) or the projected set approaches the full schema.

### 4.3 SIMD-Optimized Operator Kernels

Columnar vectors are the natural input to SIMD units, but exploiting them requires care in three dimensions: **alignment**, **branchlessness**, and **type specialization**.

*Alignment and layout.* DuckDB stores each vector's data as a contiguous array, guaranteeing the alignment that lets compilers emit aligned AVX-512 loads. ClickHouse goes further: `ColumnVector<T>` uses explicitly aligned storage, and many aggregate functions have hand-written specializations per SIMD width (SSE4.2, AVX2, AVX-512) selected at runtime via CPU dispatch [4]. DuckDB leans more on compiler auto-vectorization of tight scalar loops — a deliberate tradeoff favoring maintainability over peak throughput [2, 3].

*Branchlessness.* Predicates are evaluated with branch-free idioms: comparisons produce 0/1 masks, and selections fill selection vectors without data-dependent branches:

```python
# Branchless SIMD-style selection kernel, conceptual model
# (production engines implement this in C++/intrinsics)
import numpy as np

def vectorized_select(col: np.ndarray, lo: int, hi: int):
    """Return a selection vector of qualifying positions, no branches."""
    mask = (col >= lo) & (col <= hi)  # branch-free, SIMD-friendly
    sel = np.flatnonzero(mask)         # indices i_1..i_m
    return sel, mask

def vectorized_sum(col: np.ndarray, sel):
    """Aggregate over a (possibly selection-filtered) vector."""
    if sel is None:
        return np.sum(col)             # dense: pure SIMD reduction
    return np.sum(col[sel])            # gather over m << v elements
```

The dense path compiles to a vectorized reduction over SIMD lanes; the gather path pays gather latency but only over *m* elements. Kersten et al. [3] showed this yields up to 8.4× on selections but ~1.4× on full TPC-H Q6, because the full query is DRAM-bandwidth bound — SIMD is a *multiplier on compute*, and compute is rarely the bottleneck once vectors are cache-resident.

*Type specialization.* Both engines generate type-specific code: DuckDB's expression executor compiles per-type templated executors; ClickHouse's template metaprogramming instantiates functions per concrete column type at compile time. Type-erased loops would defeat auto-vectorization through pointer indirection.

### 4.4 Storage Layouts: MergeTree vs Parquet

Storage layout determines what the execution engine *can avoid reading*; the two designs optimize for different points in the ingestion/query tradeoff space.

**MergeTree [4].** Rows are ordered by the table's `ORDER BY` key within sorted, immutable parts. A **sparse primary-key index** records one entry per 8192-row granule, so a range predicate reads only granules whose key range intersects it — typically skipping >99% of data — while optional data-skipping indices (min/max, bloom) add coarse per-granule pruning and background merges amortize write amplification. The sparse index costs only N/8192 entries (~122K per billion rows, memory-resident), but point lookups must read a full granule — MergeTree's acknowledged weakness for OLTP-style access.

**Parquet [5].** Files are divided into row groups (~128 MB–1 GB), each holding one column chunk per column with min/max statistics, dictionary/RLE/bit-packing encodings, and compression. DuckDB's Parquet scan [2] skips whole row groups via statistics, reads only projected column chunks, and decodes dictionary chunks lazily. Parquet's advantage is *universality* — an interchange format queryable in place without ingestion; its costs are (i) no guaranteed global sort order, (ii) coarser skipping (~1M-row row groups vs. 8K-row granules), and (iii) no engine-managed compaction, so small files stay small.

| Property | ClickHouse MergeTree | Apache Parquet (+DuckDB scan) |
|---|---|---|
| Sort order | Enforced per part by `ORDER BY` | Writer-dependent, not guaranteed |
| Skip granularity | Sparse PK index, 8192-row granules | Row-group / column-chunk statistics |
| Immutability / merges | Immutable parts, background merges | Immutable files, no engine-managed compaction |
| Compression | Per-column codecs, LZ4/ZSTD | Dict/RLE/bit-pack + Snappy/ZSTD |
| Ingest model | Continuous inserts, server-side | Batch file writes, external writers |
| Point lookup | Granule read (weak) | Row-group scan (weaker) |
| Ecosystem | ClickHouse-native | Universal interchange |

The performance consequence at billion-row scale: for selective range predicates on a sorted key, MergeTree's sparse index yields near-optimal I/O, while Parquet relies on the writer having sorted the data and on tight row-group statistics. For full scans with narrow projections, both converge to the same bound — compressed bytes of projected columns divided by scan bandwidth — and the differentiator becomes codec quality and decode speed rather than layout.

## 5. Empirical Results and Proofs

### 5.1 Analytical Proof Sketches

**Proposition 1 (Vectorization dominates tuple-at-a-time on scans).** For a scan-filter pipeline with per-tuple interpretation cost *c₀* in the Volcano model and per-vector call cost *c* in the vectorized model, the vectorized engine wins whenever *c/v < c₀*. Since *c₀* includes a virtual dispatch and per-tuple null checks while *c* is a single call, and *v ≥ 1024*, the inequality holds by two to three orders of magnitude — consistent with the ~50× gap between MySQL (26.6 s) and X100 (0.50 s) on TPC-H Q1 in [1].

**Proposition 2 (Late materialization bandwidth bound).** With selectivity σ, *p* predicate columns, and *k* projected columns, late materialization reads *(p + σ·k)·s·N* bytes versus *n·s·N* for early materialization. The ratio *n / (p + σ·k)* is maximized for narrow projections and selective predicates — the canonical exploration pattern [7].

**Proposition 3 (SIMD saturation under bandwidth bound).** If the working set exceeds last-level cache and DRAM bandwidth is *B*, scan throughput cannot exceed *B / (bytes per row)* regardless of SIMD width: *T ≈ max(T_mem, T_compute / S)*. This explains Kersten et al.'s [3] finding of 8.4× on cache-resident microbenchmarks but ~1.4× on full queries.

### 5.2 Reference Benchmark Harness

The following harness defines the reproducible methodology behind the claims in §5.3. It orchestrates both engines over identical synthetic data at billion-row scale:

```python
import time, statistics
import duckdb

def build_dataset(path: str, cols: int = 64, rows: int = 1_000_000_000):
    """Write a wide synthetic table once; reuse for all workloads."""
    con = duckdb.connect()
    gen = ", ".join(f"(random()*1000000)::BIGINT AS c{i}" for i in range(cols))
    con.execute(f"COPY (SELECT {gen} FROM range({rows}) t(i)) "
                f"TO '{path}' (FORMAT PARQUET, ROW_GROUP_SIZE 122880)")
    con.close()

def timed(con, sql: str, reps: int = 5) -> float:
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter()
        con.execute(sql).fetchall()
        ts.append(time.perf_counter() - t0)
    return statistics.median(ts)

# W2: 2 of 64 columns, sigma=0.05 -> isolates late materialization
timed(con, """SELECT c7, c42, count(*) FROM wide
              WHERE c0 BETWEEN 100 AND 50000 GROUP BY c7, c42""")
```

| Workload | Configuration | Reported behavior |
|---|---|---|
| TPC-H Q1 (SF10) | MySQL 4.1 vs MonetDB/MIL vs X100 [1] | 26.6 s → 3.7 s → **0.50 s**; hand-coded C at 0.22 s |
| Selection microbenchmark | scalar vs SIMD kernel [3] | up to **8.4×** speedup |

The pattern is consistent: *architectural* choices (vectorization, late materialization, sparse indexing) deliver the large, robust wins; *micro-architectural* choices (SIMD width, codec tuning) multiply whatever compute remains.

## 6. Limitations

**Vector size tuning is workload-dependent.** DuckDB's 2048-tuple vectors suit interactive, latency-sensitive queries, but the optimum shifts with schema width: wide tuples overflow L1 at 2048 rows, while narrow scans could profit from larger batches. The engine does not adapt *v* per query today.

**Late materialization's access randomization.** Position-based fetching can turn sequential column reads into random I/O when σ is high or the medium is a spinning disk. On NVMe and in-memory data the penalty is small; on high-latency object stores it can dominate. Hybrid materialization heuristics are imperfect, and misplaced materialization points are a known source of optimizer regressions [7].

**MergeTree's write amplification and point lookups.** Background merges consume I/O and CPU; heavy update workloads pay a compaction tax. Point lookups read full 8192-row granules — a poor fit for key-value access, a consequence of the sparse index's granularity.

**Parquet's lack of global order.** Without writer-enforced sorting, statistics degrade to per-row-group min/max over unsorted data and skipping collapses. Small-file proliferation inflates metadata costs; unlike MergeTree, no engine-managed compaction repairs this.

**SIMD portability.** Hand-tuned AVX-512 kernels (ClickHouse) peak on server CPUs but need fallback paths on client hardware; compiler auto-vectorization (DuckDB) is portable but concedes performance on irregular kernels such as string parsing.

**Benchmark generality.** Published numbers [1, 3] use TPC-H at modest scale factors; billion-row, out-of-core behavior is extrapolated from the §4 cost models rather than measured directly here.

## 7. Conclusion

Vectorized columnar execution is not a single optimization but a coherent design philosophy: keep data in columns, process it in cache-resident vectors, defer every byte of work until it is needed, and let SIMD units do what they were built for. DuckDB and ClickHouse — an embedded library and a distributed server — arrive at strikingly similar execution cores from different directions, because the hardware constraints are the same. Late materialization and the selection vector are the quiet workhorses, eliminating memory traffic rather than merely accelerating computation. At the storage layer, MergeTree's sparse indexing and background merges optimize for continuous ingestion with selective range access, while Parquet's universal, statistics-rich column chunks optimize for interchange and in-place querying; at billion-row scale, layout choice — what can be *skipped* — outweighs kernel choice.

The frontier is adaptive: per-query vector sizing, learned data-skipping indices, and compilation strategies that choose between vectorized and data-centric code generation per pipeline [3]. The engines that win the next decade will treat the memory hierarchy, not the ALU, as the scarce resource — a lesson this lineage, from X100 to the present, has been teaching for twenty years.
