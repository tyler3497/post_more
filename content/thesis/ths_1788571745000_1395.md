# Inside the Tokio Runtime: Work-Stealing Scheduling, the Reactor, and Async I/O Architecture in Rust

## Abstract

The Tokio asynchronous runtime is the dominant execution engine for concurrent Rust programs, yet its internal architecture — a work-stealing multi-threaded scheduler, a reactor built on `mio`, a hierarchical timer wheel, a per-task execution budget, and a dual driver-thread model for I/O and time — is understood by most users only at the level of slogans. This thesis presents a systematic, PhD-level dissection of the Tokio runtime. We formalize the **M:N task model** induced by `async`/`await` state machines and `Send` bounds, characterize the **LIFO-slot/FIFO-deque work-stealing scheduler** with its global injection queue, detail the **reactor loop** mapping readiness events from `epoll`, `kqueue`, and `IOCP` onto woken tasks, and analyze the **timer wheel** and **128-unit cooperative task budget** that together bound tail latency. We derive empirical micro-benchmark methodology for scheduler throughput, spawn latency, and I/O fan-out, contrast the design with the Go `G/M/P` scheduler, and close with a catalog of `Send`/`Sync` pitfalls and open limitations — including the cooperative-yield blind spots and `!Send` confinement via `LocalSet`.

## 1. Introduction

Asynchronous programming in Rust is built on two separable ideas: *futures*, which encode suspended computation as pollable state machines, and *executors*, which drive those machines to completion [3]. The Rust language supplies the former through `async`/`await` desugaring and the standard-library `Future` trait; it deliberately supplies **no executor**. Into this gap steps Tokio, an event-driven, non-blocking I/O platform whose runtime has become the de facto standard for high-performance Rust networking, underpinning production systems at Discord, AWS Lambda, and within Deno [8].

A user's mental model of Tokio is often one sentence: *many tasks, few threads*. That sentence is true but dangerously incomplete. Production incidents — unexplained tail latency, starved low-priority tasks, tasks that never resume, panics from `!Send` futures — all trace to internals that the one-sentence model cannot express. The goal of this thesis is to replace the slogan with a precise, mechanistic account of what happens between `tokio::spawn(f)` and the final `Poll::Ready`.

> **Theorem (Cooperative Scheduling Contract):** *No Tokio task is ever preempted. A task that returns `Poll::Pending` without registering a waker is permanently lost; a task that never yields can delay every other task on its worker indefinitely. All scheduling guarantees in the runtime follow from this single axiom.*

We proceed as follows. Section 2 grounds the discussion in futures, `Pin`, and the `Send`/`Sync` auto-traits. Section 3 describes our methodology: source-level analysis of the runtime plus micro-benchmark design. Section 4 — the deep dive — covers the multi-thread and current-thread schedulers, the reactor and I/O driver, the timer wheel, task spawning and budgeting, and the async state machine. Section 5 proposes empirical measurements. Section 6 catalogs limitations, and Section 7 concludes.

## 2. Background

### 2.1 Futures, polling, and the executor loop

A Rust `Future` is a value implementing

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

Polling is *pull-based*: the executor calls `poll`, and the future either completes (`Poll::Ready`) or suspends (`Poll::Pending`), having arranged — typically by registering the `Waker` carried in `Context` with some event source — to be woken later [3]. A minimal executor is roughly: pick a ready task, poll it, on `Pending` park it until its waker fires, on wake re-enqueue it. *Tokio is this loop, industrialized.*

### 2.2 State machines from `async fn`

An `async fn` returning `T` desugars to a function returning an opaque `impl Future<Output = T>`. The compiler builds a **state machine**: each `.await` point becomes a state holding the awaited sub-future, and `poll` advances the machine from state to state. Because the machine owns local variables *across* await points, it may hold non-`Unpin` values, which is why `poll` takes `Pin<&mut Self>` and why spawned tasks must be pinned in memory.

### 2.3 `Send`, `Sync`, and thread mobility

> **Invariant:** *A future is `Send` iff it can be polled on one thread, suspended, and resumed on another without data races. A future holding `Rc<T>` or `Cell<T>` across an await point is not `Send`.*

`tokio::spawn` requires `F: Future + Send + 'static` precisely because the work-stealing scheduler moves tasks between worker threads. This bound is the single most common source of compile errors for newcomers, and it is load-bearing: the entire scheduler's correctness argument assumes tasks are freely relocatable. For futures that cannot move, `LocalSet` confines a set of tasks to one thread [4].

### 2.4 The Go scheduler as a reference design

The closest architectural cousin to Tokio's scheduler is the Go runtime scheduler, described by Vyukov and popularized in Morsing's essay [7]: goroutines (`G`), machine threads (`M`), and logical processors (`P`) form an **M:N scheduler**, each `P` holding a local run queue and stealing work when empty, with a global queue for overflow. Tokio's design is the direct analogue — workers instead of `P`s, tasks instead of `G`s — with one decisive difference: Go gained **asynchronous preemption** in 1.14, whereas Tokio remains strictly *cooperative*, compensating with a task budget (§4.5) rather than signals.

## 3. Methodology

This thesis combines two methods:

1. **Source-architecture analysis.** We trace the runtime's public API surface (`tokio::runtime::{Builder, Runtime}`, `tokio::spawn`, `tokio::task::{spawn_blocking, block_in_place}`) to its internal modules — the multi-thread and current-thread schedulers, the I/O driver ("reactor"), and the time driver — as documented in the crate's API reference and the Tokio team's engineering posts [1][2][4].
2. **Empirical micro-benchmarking.** We design a criterion-style harness (outlined in §5) measuring task-spawn latency, per-poll overhead, wake throughput, and timer/I/O fan-out, and relate the results to published measurements such as the reported 10× scheduler speedup [2] and production metrics from `tokio-metrics` [1].

The runtime is configured through `Runtime::builder()`: `new_multi_thread()` (default, one worker per CPU core) or `new_current_thread()` (a single-threaded event loop), plus thread-name, stack-size, blocking-pool, and I/O/time driver toggles.

## 4. Deep Dive

### 4.1 The multi-threaded work-stealing scheduler

The default runtime spawns **N worker threads**, where N defaults to the number of available CPU cores. Each worker owns:

- A **local run queue** implemented as a Chase–Lev-style work-stealing deque plus a **LIFO slot** — a single-task fast path. Newly spawned tasks land in the local queue (or slot) of the spawning worker, preserving cache locality: a task typically keeps running on the same thread [6].
- Access to a **global injection queue**, an MPSC queue fed by tasks spawned from outside any worker thread (or by overflow when a local queue fills).

The scheduling loop on each worker is, in essence:

```rust
loop {
    // 1. LIFO slot: hot-path for the most recently scheduled task
    if let Some(task) = local.lifo_slot.take() { poll(task); continue; }
    // 2. Local deque, FIFO order for fairness
    if let Some(task) = local.queue.pop() { poll(task); continue; }
    // 3. Steal: batch-steal half of a victim's queue
    if let Some(task) = steal_from_random_worker() { poll(task); continue; }
    // 4. Global injection queue
    if let Some(task) = inject.pop() { poll(task); continue; }
    // 5. Park the OS thread until notified
    park_until_work_arrives();
}
```

Work stealing proceeds in **batches** (stealing roughly half of a victim's queue) to amortize the cost of the atomic operations on the deque, and victims are chosen at random to avoid systematic contention. The LIFO slot is a subtle but important optimization: when a task spawns a child or wakes a sibling, the fresh task is likely to touch the same cache lines, so polling it *first* minimizes cache misses [2].

> **Invariant (Queue discipline):** *A worker never idles while any runnable task exists anywhere in the system: local queue, injection queue, or a sibling's deque — modulo the atomicity window of the steal protocol.*

**Spawn path.** `tokio::spawn(f)` wraps the future in a `Task` (an `Arc` of the future plus its `Waker` machinery and scheduling metadata), and: if called from within a worker, pushes to that worker's local queue; if called externally, pushes to the global injector and notifies a parked worker. Spawning is lock-free in the fast path and returns a `JoinHandle<T>` for the output.

### 4.2 The current-thread runtime

`new_current_thread()` builds a **single-threaded** scheduler: one OS thread, one run queue, no stealing. All tasks share one thread, so `Send` is not required *within* the runtime — this is the natural home of `LocalSet` and `!Send` futures. Semantics worth memorizing:

| Property | Multi-thread | Current-thread |
|---|---|---|
| Worker threads | N = #cores (configurable) | 1 |
| Work stealing | Yes (LIFO slot + deque + injection queue) | No |
| `tokio::spawn` requires `Send` | Yes | Yes (API-level; but `LocalSet::spawn_local` avoids it) |
| `block_in_place` | Allowed | **Panics** |
| `spawn_blocking` | Allowed (separate pool) | Allowed |
| Cache locality | Strong (task–thread affinity) | Trivial |

The current-thread scheduler is also the right choice for embedding Tokio inside another executor's thread or for deterministic testing, since its FIFO queue makes execution order reproducible.

### 4.3 The reactor: I/O driver and readiness

Network I/O in Tokio follows the **reactor pattern**. Each runtime owns an **I/O driver** that wraps `mio` [5], the portable non-blocking I/O library that abstracts `epoll` (Linux), `kqueue` (macOS/BSD), and `IOCP` (Windows). The flow for a single read:

1. `TcpStream::readable().await` polls the socket; if no data is ready, the task **registers interest** with the driver and returns `Poll::Pending`.
2. The I/O driver blocks in the OS readiness call (`epoll_wait` et al.) on its dedicated driver thread.
3. When the socket becomes readable, the driver marks the interest complete and invokes the task's **`Waker`**, which schedules the task onto a worker queue.
4. The worker polls the task again; the read now succeeds.

Two architecture notes matter. First, the I/O driver runs on its **own thread(s)**, separate from the worker pool, so a saturated worker pool delays polling but does not stop readiness *detection*. Second, `wake` is decoupled from `poll`: readiness is a *notification*, not a data transfer — the task must re-poll to consume the event. Misunderstanding this is the root cause of the classic "spurious wakeup" confusion.

On Linux, Tokio can additionally exploit `io_uring` through the `tokio-uring` companion crate for true submission/completion-queue async I/O [8], though the `mio`-based reactor remains the default path.

```
task.await on TcpStream ──► register interest with I/O driver ──► Poll::Pending
        ▲                                                              │
        │                    epoll/kqueue/IOCP event                    │
        └──────── wake() ◄── readiness detected ◄──────────────────────┘
```

### 4.4 The timer wheel

Timers (`tokio::time::sleep`, `interval`, `timeout`) are managed by a **time driver** — a hierarchical hashed **timer wheel** — running on its own driver thread. Inserting a timer is O(1): the deadline is hashed into a wheel slot. When the driver's clock passes a slot, all timers in it fire, and their wakers schedule the awaiting tasks. The wheel structure is what lets Tokio support *millions* of concurrent timers without a priority-queue bottleneck; only the granularity of the wheel (millisecond-order) bounds precision.

> **Theorem (Timer fairness):** *A timer's wake is no earlier than its deadline, but may be arbitrarily late under worker saturation — timers guarantee a lower bound on waiting, never an upper bound.*

The time driver is also what makes `tokio::time::pause()` possible in tests: the clock becomes virtual and only advances when the test says so, giving deterministic time control.

### 4.5 Task spawning, budgeting, and cooperative yielding

Because Tokio is cooperative, a task that polls in a hot loop without awaiting could **starve** every other task on its worker. Tokio's answer is the **task budget**: each task is granted a fixed budget of poll "fuel" (128 units in current implementations). Every time the task is polled — and for certain operations such as mutex acquisition — budget is consumed. When the budget hits zero, Tokio's synchronization primitives and I/O resources begin returning `Poll::Pending` *even when ready*, forcing the task to yield; the task is re-queued and its budget refilled. This mechanism, introduced to reduce tail latency without preemption, is documented in the team's "automatic cooperative task yielding" work [2].

Practical consequences:

- `tokio::task::yield_now().await` voluntarily surrenders the worker — the manual escape hatch.
- CPU-heavy loops **must** periodically yield (or be moved to `spawn_blocking` / a separate Rayon-style pool); the budget only constrains *Tokio-aware* operations, not raw computation [6].
- Budget exhaustion is *per task poll cycle*, not per wall-clock time: a single long `poll` (e.g., a big synchronous computation inside an async fn) is invisible to the budget.

### 4.6 Async state machines and `Send`/`Sync` pitfalls

Compiling the pieces: `tokio::spawn` requires the future be `Send`; the scheduler may move the task between workers at any await point; the future's state machine holds locals across awaits. The classic pitfalls follow deductively:

1. **`Rc`/`RefCell` across `.await`.** `Rc<T>` is `!Send`; holding it across an await poisons the whole future's `Send`-ness. Fix: `Arc`/`Mutex`, or restructure so the `Rc` is dropped before awaiting.
2. **`std::sync::MutexGuard` across `.await`.** `MutexGuard` is `!Send`; holding it across an await fails to compile with the multi-threaded runtime. Use `tokio::sync::Mutex`, whose guard *is* `Send`, or scope the guard tightly.
3. **Blocking inside `poll`.** `std::thread::sleep`, filesystem reads, or heavy computation stall the worker — and, with the current-thread runtime, the *entire program*. Use `spawn_blocking` (backed by a separate pool, default cap 512 threads) or `block_in_place` (multi-thread only), which moves the worker's remaining tasks elsewhere while the thread blocks.
4. **Forgetting `Send` on trait objects.** `Box<dyn Future<Output=T> + Send>` is required wherever tasks cross thread boundaries; the missing `+ Send` is a perennial source of confusing errors.
5. **Waker misuse.** A future that returns `Pending` without arranging a wake is *dead* — the executor has no timer to rescue it. Custom `Future` impls must guarantee the wake contract.

> **Invariant (Wake contract):** *Every `Poll::Pending` must be paired with a prior or eventual `wake()` on the current task's `Waker`. Violation yields silent task death, not an error.*

The following minimal program exercises the spawn–budget–wake machinery end to end:

```rust
use tokio::time::{sleep, Duration};

#[tokio::main(flavor = "multi_thread", worker_threads = 4)]
async fn main() {
    let mut handles = Vec::new();
    for i in 0..1000 {
        // Each spawn: Task allocation -> local queue -> poll -> timer wheel -> wake
        handles.push(tokio::spawn(async move {
            sleep(Duration::from_millis(10)).await; // Pending + waker + timer entry
            i * 2
        }));
    }
    let mut sum = 0;
    for h in handles { sum += h.await.unwrap(); } // JoinHandle: oneshot wake
    println!("sum = {sum}");
}
```

The Go analogue makes the design tradeoffs explicit:

```go
// Go: goroutines are preemptible since 1.14; Tokio tasks are not.
for i := 0; i < 1000; i++ {
    go func(i int) {
        time.Sleep(10 * time.Millisecond) // runtime parks G; M is reused
        results <- i * 2
    }(i)
}
```

Go's runtime can asynchronously preempt a CPU-hogging goroutine via signals; Tokio *cannot* — it relies on budget exhaustion at Tokio-aware yield points. This is the fundamental scheduler-level difference between the two systems [7].

## 5. Empirical Results / Proofs

We propose a benchmark harness (criterion, pinned cores, isolated from frequency scaling) measuring five quantities:

| Metric | Method | Expected order |
|---|---|---|
| Task spawn + first poll latency | `spawn` 1M no-op tasks, divide | hundreds of ns |
| Context switch (yield round-trip) | `yield_now` ping-pong between 2 tasks | ~µs |
| Wake throughput | timer wheel, 1M `sleep(0)` | millions/s |
| I/O fan-out | 100k concurrent TCP echo conns, req/s | NIC-bound |
| Steal overhead | 1 producer, N−1 idle workers | steal rate vs. throughput |

Published evidence anchors the design: the Tokio team's scheduler rewrite reported roughly **10×** throughput gains on scheduling micro-benchmarks [2]; production telemetry via `tokio-metrics` exposes budget exhaustion, worker steal counts, and I/O driver latency distributions [1]; and the InfluxData experience report [6] demonstrates that cache affinity (task–thread stickiness) is the dominant term in CPU-bound async workloads — stealing exists to bound *imbalance*, not to maximize movement.

**Sketch of the budget-fairness guarantee.** Model each worker as serving its local queue FIFO with the LIFO-slot fast path, budget *B* = 128 per task per scheduling quantum. A task consuming more than *B* units is forcibly re-queued behind at most *Q* other tasks. Hence any ready task waits at most *(Q+1)·B* poll-units before being polled — a **bounded overtaking** property that fails *only* for budget-invisible work (raw CPU inside one `poll`). This is the formal content of "cooperative yielding reduces tail latency" [2].

## 6. Limitations

1. **No preemption.** A task executing a long synchronous section inside a single `poll` is invisible to the budget; it stalls its worker (or the whole program on `current_thread`). The runtime cannot fix user code that never reaches a yield point.
2. **Budget granularity.** The 128-unit budget is a heuristic: too coarse for latency-critical services (a task can still monopolize a worker for 128 Tokio-aware operations), too fine to matter for I/O-bound workloads where tasks yield immediately.
3. **Steal-induced cache effects.** Work stealing optimizes *utilization*, not locality; under imbalance, stolen tasks suffer cold caches. Affinity hints do not exist in the public API.
4. **`!Send` confinement is all-or-nothing.** `LocalSet` pins tasks to one thread with no migration; there is no middle ground between "freely stealable" and "immobile."
5. **Timer precision.** The wheel offers millisecond-order granularity; sub-millisecond deadlines are not meaningful, and virtual time (`pause()`) diverges from wall time in ways that leak into tests of timeouts.
6. **Blocking pool bounds.** `spawn_blocking` caps at 512 threads by default; a flood of blocking tasks exhausts the pool and *those* tasks queue — blocking work can still deadlock an application that awaits it from async tasks without timeouts.
7. **Observability cost.** `tokio-metrics` and Console instrumentation perturb the very scheduling they measure; production profiling of the scheduler remains an observer-effect problem [1].

---

## 7. Conclusion

Tokio's runtime is a carefully layered machine: a **work-stealing scheduler** (LIFO slot, per-worker deques, global injector) multiplexes `Send` tasks over OS threads; a **reactor** built on `mio` translates `epoll`/`kqueue`/`IOCP` readiness into waker invocations on a dedicated I/O driver thread; a **hierarchical timer wheel** on a time-driver thread fires deadlines in O(1); and a **128-unit task budget** enforces cooperative fairness where preemption is unavailable. The async/await state machine, the `Pin` discipline, and the `Send` bound are not incidental language details — they are the load-bearing contracts the scheduler's correctness depends on.

Understanding these internals converts entire classes of production mysteries into deductions: starvation becomes budget arithmetic, dead tasks become wake-contract violations, and `!Send` errors become statements about task mobility. Compared with Go's preemptible `G/M/P` scheduler [7], Tokio trades preemption for zero signal overhead and relies on cooperation plus budgeting — a defensible trade, but one whose failure modes every serious Tokio user should be able to derive from first principles. That derivability is the real lesson: in a cooperative runtime, *the scheduler is a contract, and the fine print is load-bearing*.
